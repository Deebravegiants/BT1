### Title
Unauthenticated cross-chain RuntimeCall dispatch via decoded `message.from` bypasses signature verification - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
The `fabric8-maven-plugin` advisory (CVE-2020-10721) is a CWE-502 case: attacker-controlled bytes are deserialized into an executable object and run without adequate origin authentication. The structural analog in this codebase is `pallet-hyper-fungible-token`'s `on_accept` handler, which SCALE-decodes an attacker-supplied byte blob into a `T::RuntimeCall` and dispatches it, deriving the dispatch origin from unauthenticated message fields when no signature is supplied.

### Finding Description
In `on_accept`, after minting/transferring bridged tokens, the pallet processes optional calldata attached to the cross-chain `Message`: [1](#0-0) 

The `SubstrateCalldata.runtime_call` bytes are decoded straight into `T::RuntimeCall` and dispatched: [2](#0-1) 

Authorization for this dispatch has two branches:
1. If `substrate_data.signature` is present, a `MultiSignature` over `(nonce, runtime_call)` is checked against the recipient (`beneficiary`) key. [3](#0-2) 
2. If no signature is present, the origin is derived directly and unconditionally from the `message.from` bytes of the incoming ABI-decoded `Message`, with **no cryptographic check that this origin actually authorized the runtime call**: [4](#0-3) 

The only gate on the dispatched call is `BaseCallFilter`: [5](#0-4) 

`Message.from` is an arbitrary `bytes` field defined in the ABI-compatible struct decoded from the request body — it is not authenticated by any signature scheme on the destination chain, it is simply whatever bytes the source-side EVM contract call populated: [6](#0-5) 

Because ISMP's cross-chain message delivery authenticates only that a `PostRequest` genuinely originated from the registered source contract (`ContractToAsset` lookup keyed on `source`/`from` contract address) — [7](#0-6)  — it does not constrain what the EVM contract puts in the `Message.from` payload field itself. If the paired EVM `HyperFungibleToken` contract allows a caller to set an arbitrary `from` value in the message it emits (rather than hard-coding `msg.sender`), any account able to invoke a bridge send can cause an arbitrary `RuntimeCall` to be dispatched on the destination Substrate chain as `RawOrigin::Signed(<attacker-chosen account>)`, with no signature verification at all, subject only to the (typically permissive) `BaseCallFilter`.

### Impact Explanation
`RawOrigin::Signed` dispatch of an attacker-influenced `RuntimeCall`, gated only by a generic call filter (not by per-call authorization), can be used to invoke any dispatchable not explicitly filtered out — including asset transfers, governance-adjacent calls, or other pallet extrinsics — as an account the attacker does not control the private key of. This can lead to unauthorized app actions and, depending on which calls `BaseCallFilter` leaves open, theft or corruption of state for the impersonated account. This matches the report's core bug class: untrusted, deserialized data is turned directly into unrestricted "code execution" (dispatchable calls) with insufficient authentication of the actor.

### Likelihood Explanation
Reachable from a single relayed cross-chain PostRequest through this HFT bridge app — the exact "unprivileged message dispatcher/token bridger" surface this scan is scoped to. Exploitability hinges on whether the counterpart EVM contract (`HyperFungibleToken.sol` / `HyperFungibleTokenUpgradeable.sol`) lets the caller freely set the `from` field of the emitted `Message` rather than hard-binding it to `msg.sender`; I was not able to fully confirm this from the Solidity source within the available search results (no `Message{...}`/`from:` construction site was found in `HyperFungibleToken.sol` via grep), so this should be verified directly against the Solidity emitting code before treating it as fully confirmed.

### Recommendation
- Require the signature-verified path for any calldata execution — remove or gate the unsigned fallback that derives dispatch `origin` from `message.from` without a corresponding signature check.
- If the unsigned fallback is intentionally kept for same-account "self" calls, ensure the source-chain contract binds `from` to `msg.sender` unconditionally (not caller-suppliable), and additionally verify this invariant on the pallet side (e.g., re-derive from a value bound to the transfer's escrow debit, not a free-form ABI field).
- Constrain `BaseCallFilter` (or add a dedicated allow-list) for cross-chain-dispatched calls, independent of the runtime's general call filter, since this is a much higher-risk dispatch path than a normal signed extrinsic.

### Proof of Concept
1. Attacker controls (or is) the account invoking the send function on the EVM-side `HyperFungibleToken` contract for a registered token/chain pair.
2. If the EVM contract does not hard-bind the emitted `Message.from` to `msg.sender`, attacker sets `Message.from` to bytes representing a target account's EVM address they wish to impersonate, and appends `data` encoding a `SubstrateCalldata { signature: None, runtime_call: <arbitrary allowed call> }`.
3. Relayer delivers the resulting ISMP `PostRequest` to the destination Substrate chain; `ContractToAsset` lookup succeeds because `source`/registered contract address is legitimate.
4. `on_accept` reaches the `data.is_empty()==false` branch, decodes `SubstrateCalldata`, takes the `else` branch at [4](#0-3) , converts the attacker-chosen `from` bytes into the target account, and dispatches the embedded `RuntimeCall` as that account with no signature check — [8](#0-7) .
