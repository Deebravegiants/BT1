### Title
Emporium `runAction`'s "Stateless Interaction" branch drains tokens outside the balance equation, allowing theft of residual Emporium funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction()`'s CASE 2 "Stateless Interaction" branch lets any unprivileged EOA with a valid Hinkal proof execute an arbitrary `endpoint.call(callData)` directly from the Emporium contract's own context and balance [1](#0-0) . Because both `Hinkal.transact()` and `Emporium.runAction()` only reconcile balances for the tokens explicitly listed in `circomData.erc20TokenAddresses`, an attacker can target a token that the Emporium contract holds (e.g. leftover/residual balance from a previous user's DeFi interaction) but that is *not* included in his own transaction's token list, and move it out with zero accounting impact on the balance equation.

### Finding Description
`Emporium.runAction()` is called by `Hinkal._externalTransact()` after Hinkal has already transferred the user's negative-delta funds to the Emporium contract [2](#0-1) . Inside `runAction`, each `EmporiumOperation` can either:
- CASE 1 (stateful): route through the user's per-signer `HinkalWallet`, restricted by `onlyEmporium` [3](#0-2) , or
- CASE 2 (stateless): call `op.endpoint.call{value: op.value}(op.callData)` **directly from the Emporium contract itself**, with the only restriction being that the selector isn't `callHinkalWallet` or `doSendToRelay` [1](#0-0) .

`verifyWallet()` only checks that `stack.ops`/`maxFee`/`deadline` were signed by `stack.signerAddress` if one is supplied — it does not check that `stack.ops` don't call unrelated tokens, and if `stack.signerAddress == address(0)` verification is skipped entirely, aside from marking the message used [4](#0-3) . Even when a signer is used, the signer is the attacker himself signing his own arbitrary op list, so there is no external gatekeeping on what `op.endpoint`/`op.callData` can be.

Crucially, both the outer `Hinkal.transact()` slippage/balance-equation check and the inner `runAction` balance-equation check only iterate over `circomData.erc20TokenAddresses` — the array the *caller* chooses to declare for his own transaction:
- `Hinkal.transact()`'s balance diff loop: `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++) { ... }` [5](#0-4) 
- `Emporium.runAction()`'s before/after balance snapshot: `getBalancesForArray(circomData.erc20TokenAddresses)` [6](#0-5) [7](#0-6) 

The code even documents that Emporium is expected to sometimes hold pre-existing balances across transactions ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") [8](#0-7) . Such residual balances (dust from prior swaps/DeFi ops whose output token wasn't fully swept into a UTXO, undistributed relay fees, or rounding remainders) sit at the Emporium contract address between transactions.

An attacker only needs a normal, unprivileged UTXO of trivial value (obtainable via a normal deposit) to produce a valid Hinkal proof. He then submits a `transact()` call whose `circomData.erc20TokenAddresses` **omits** the victim token, but whose `externalActionData` points at Emporium with `externalActionMetadata` encoding an `EmporiumStack` containing a CASE 2 op: `endpoint = <victim token>`, `callData = transfer(attacker, residualBalance)`. Because the target token is absent from `erc20TokenAddresses`, neither `Hinkal.transact()`'s balance-diff check nor `Emporium.runAction()`'s before/after check ever observes the drain, so both equalities pass trivially and the call succeeds, moving Emporium's residual token balance to the attacker.

This is the direct analog of the referenced report: the callback/action mechanism (`runAction`) performs an externally-directed asset movement (`op.endpoint.call`) that is not tied to — and not verified against — the accounting/authentication context (here, the enumerated token list used for the balance equation), letting an unrelated caller move value that was never authorized to be part of their transaction.

### Impact Explanation
This breaks the balance equation invariant that "value moved by Hinkal or an external action" must be counted (`onChainCreation`/`amountChanges`/UTXO reconciliation). It allows unauthorized theft of funds sitting at the Emporium contract (residual user/protocol funds, e.g., relay fees or unswept dust from prior legitimate Emporium interactions) by any unprivileged EOA holding a trivial valid UTXO — a direct theft of protocol/relay or in-flight user funds via an unauthorized asset movement never accounted for by the prover's own transaction, meeting the High/Critical impact bar (theft of protocol/relay fees, or theft of value belonging to other users left in a shared contract).

### Likelihood Explanation
Likelihood is moderate-to-high: it requires (1) the attacker to hold any valid Hinkal UTXO (trivially obtainable by any user through a normal deposit) and (2) the Emporium contract to hold a non-zero balance of some token not enumerated in the attacker's own `erc20TokenAddresses` list at call time. Given DeFi/swap interactions routed through Emporium commonly leave dust, or relay-fee tokens can be temporarily held, this condition is realistically reachable, and the exploit itself requires no privileged role, no admin key, and no cooperation from other users.

### Recommendation
- Require that every token touched by any `EmporiumOperation.endpoint` call (or at minimum, any ERC-20/ETH balance change resulting from CASE 2 calls) be included in and reconciled against `circomData.erc20TokenAddresses`, so no balance change can bypass the equation in `Hinkal.transact()`/`Emporium.runAction()`.
- Alternatively, disallow stateless (CASE 2) calls to arbitrary `endpoint` addresses that are ERC-20/ERC-721/ERC-1155 tokens not already declared in the transaction's token list, or force CASE 2 execution to go through the isolated per-user `HinkalWallet` (as CASE 1 does) so it can never touch shared Emporium balance.
- Ensure Emporium never retains residual token balances between transactions (sweep any leftover balance into a UTXO or revert if non-zero remainder exists for tokens outside the declared list).

### Proof of Concept
1. Some earlier, legitimate Emporium interaction (e.g., a swap via `EmporiumOperation`) leaves a residual `TOKEN_X` balance sitting on the `Emporium` contract (dust from rounding, unswept surplus, or a fee token not withdrawn).
2. Attacker (any EOA) performs a normal small deposit into Hinkal to obtain a spendable UTXO and valid proof material.
3. Attacker calls `Hinkal.transact(...)` with:
   - `circomData.erc20TokenAddresses` = `[TOKEN_Y]` (any token, deliberately **excluding** `TOKEN_X`)
   - `circomData.externalActionData.externalAddress` = Emporium, `externalActionId` = Emporium's id
   - `circomData.externalActionData.externalActionMetadata` = abi-encoded `EmporiumStack` with `signerAddress = attacker`, one `EmporiumOperation{ invokeWallet: false, endpoint: TOKEN_X, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance) }`, validly signed by the attacker himself for his own stack.
4. In `Emporium.runAction()`, CASE 2 executes `TOKEN_X.call(transfer(attacker, residualBalance))` directly from Emporium's balance [1](#0-0) ; `TOKEN_X` is not in `circomData.erc20TokenAddresses`, so neither the inner balance snapshot nor the outer `Hinkal.transact()` balance-diff loop ever inspects it.
5. Both balance equations pass trivially (comparing only `TOKEN_Y` before/after), the transaction succeeds, and `TOKEN_X.residualBalance` has been transferred to the attacker with no corresponding nullifier spend, UTXO creation, or fee payment.
