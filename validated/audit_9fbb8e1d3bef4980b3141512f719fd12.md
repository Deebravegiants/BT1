### Title
`Webhooks::Registry.process` trusts unsigned `shop-domain`/`topic` headers as the request identity, enabling shop/topic confusion via HMAC replay - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only that the raw request body was HMAC-signed with the app's shared secret, then blindly trusts the unsigned `X-Shopify-Topic` and `X-Shopify-Shop-Domain` headers to select the handler and populate `WebhookMetadata#shop`. Because the HMAC signable string is the body only, an attacker who can obtain any single genuinely-signed `(body, hmac)` pair (trivially, by installing the app on their own shop and receiving one real webhook) can replay that exact body+hmac to the app's public webhook endpoint while swapping the `topic` and `shop-domain` headers to arbitrary values, defeating the single-identity invariant.

### Finding Description
The claimed invariant is the equality `WebhookMetadata#shop == the shop whose action produced this HMAC-authenticated body`. Tracing the code:

- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares to the `hmac` header — it never touches `topic` or `shop`: [2](#0-1) 
- `Registry.process` gates only on this body-HMAC check, then dispatches on `request.topic` and forwards `request.shop` straight into `WebhookMetadata`, both read directly from attacker-suppliable headers with no binding to the HMAC: [3](#0-2) [4](#0-3) 

Root cause: `api_secret_key` is a single secret shared by the app across every merchant shop that installs it — it is not per-shop. A valid HMAC over a body therefore only proves "signed by someone holding the app's secret," not "this body/topic/shop triple is what Shopify actually sent." Since `topic` and `shop` are excluded from the signable string, they float free of the signature.

Attacker exploit flow:
1. Attacker installs the target app on their own throwaway development shop and triggers any webhook (e.g. `products/create`), capturing a genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair.
2. Attacker POSTs directly to the app's public webhook route (bypassing Shopify's delivery infrastructure entirely, which the attacker is free to do since the route is a normal HTTP endpoint) with the same body/HMAC but arbitrary `X-Shopify-Topic` and `X-Shopify-Shop-Domain` headers, e.g. topic set to a handler the app registered for privileged flows, and shop set to a victim merchant's domain.
3. `HmacValidator.validate` passes because it only checks the body signature. `Registry.process` picks the handler keyed by the forged `topic` and constructs `WebhookMetadata.new(topic: <forged>, shop: <forged victim domain>, ...)`. [3](#0-2) 
4. Any app logic in the handler that keys session lookup, staff-user context, or data association off `WebhookMetadata#shop`/`#topic` now operates on attacker-chosen identity while believing it passed cryptographic authentication.

None of the existing guards prevent this: `ShopValidator.sanitize!` is never called in this path; there is no `state`/`aud`/`sub` comparison (that machinery belongs to OAuth/JWT flows, not webhooks); `Context.setup?`/`private?`/`embedded?` are unrelated to webhook header trust; Sorbet's `sig` only enforces types (`String`), not provenance or binding to the HMAC.

### Impact Explanation
An attacker who legitimately controls one shop can make the app process a webhook body of their choosing under an arbitrary forged `topic` and `shop` value, once they hold any single valid `(body, hmac)` pair (they can obtain arbitrarily many, for arbitrary topics, since they fully control their own shop's webhook traffic). This breaks the single-identity binding required for the app to safely route data/session context by shop, enabling cross-tenant confusion inside apps that trust `WebhookMetadata#shop` as an authenticated value — repeatable against any shop domain string, for any registered topic, at will. This matches the cross-tenant class of impact described in the rules, contingent on how the host app's handler consumes `WebhookMetadata#shop`.

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: create/own a development shop, install the target app, trigger one webhook to capture a valid `(body, hmac)` pair, then send a crafted POST directly to the app's public webhook path with modified `topic`/`shop-domain` headers. No secret, token, or victim cooperation is required, and the attack is repeatable against any topic/shop combination.

### Recommendation
Bind `topic` and `shop` into the signable string (or otherwise cryptographically verify them, e.g. by re-deriving/confirming the shop via a signed source such as session/token data) before dispatch, and call `ShopValidator.sanitize!` on `request.shop` prior to constructing `WebhookMetadata`, so the identity used for dispatch and handler context is the same one covered by the HMAC.

### Proof of Concept
```ruby
# test/webhooks/registry_shop_topic_confusion_test.rb
require_relative "../test_helper"

class RegistryShopTopicConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    @captured_shop = nil
    handler = Class.new do
      define_method(:handle) { |data:| RegistryShopTopicConfusionTest.captured_shop = data.shop }
    end.new
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: handler
    )
  end

  def test_replayed_body_with_forged_shop_and_topic_is_accepted
    body = '{"id":1}'
    hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", "secret", body)).strip

    request = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-topic" => "orders/create",       # attacker-chosen
        "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unsigned
        "x-shopify-api-version" => "2023-10",
        "x-shopify-webhook-id" => "1",
      },
    )

    ShopifyAPI::Webhooks::Registry.process(request)

    # Assert: HMAC covers only body, so forged shop passes through untouched
    assert_equal "victim-shop.myshopify.com", RegistryShopTopicConfusionTest.captured_shop
  end
end
```
This demonstrates that `Registry.process` accepts a body signed for one shop while dispatching under an attacker-forged `shop` value, confirming the single-identity binding is violated.
