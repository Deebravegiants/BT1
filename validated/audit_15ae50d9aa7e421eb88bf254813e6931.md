### Title
Predictable, unsigned session identifiers enable session fixation across shops - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
The library's non-embedded (cookie-based) session lookup trusts the raw browser-supplied cookie value as the authoritative session identifier, and that identifier is a fully deterministic, guessable string (`offline_#{shop}` or `#{shop}_#{user_id}`) rather than a random or cryptographically bound token. This breaks the intended binding `cookie_value == server-issued, unforgeable session id`, enabling a classic session-fixation pattern once an attacker can influence the session cookie for the app's origin.

### Finding Description
`SessionUtils.current_session_id` is the gem's documented mechanism for host apps to resolve the "current session" from an incoming request. For non-embedded apps (and as fallback for embedded apps without a JWT), it returns whatever value is in the `SESSION_COOKIE_NAME` cookie, unmodified: [1](#0-0) [2](#0-1) 

That cookie value is exactly the session's `id`, which is generated with a fully deterministic, non-secret format: [3](#0-2) [4](#0-3) 

When the OAuth callback completes for a non-embedded app, the SDK sets this exact deterministic value as the browser cookie: [5](#0-4) 

confirmed by the test fixture value `"offline_#{@shop}"`: [6](#0-5) 

The gem's own documented reference pattern (and the `BREAKING_CHANGES_FOR_V16.md` migration guide) instructs host apps to store/retrieve sessions keyed by exactly this `session.id` value returned from `current_session_id`: [7](#0-6) 

Because `offline_#{shop}` (and `#{shop}_#{user_id}` for online sessions, where the numeric Shopify user id is often discoverable) is entirely computable from a publicly-known shop domain, this "session id" carries no secret entropy. The equality the system depends on — *cookie value presented by the browser == a session id that only the legitimate, authenticated shop could have obtained* — does not hold: any party who knows a target shop's `myshopify.com` domain can compute the exact same string that the SDK would have written into a legitimate victim's cookie. `cookie_session_id` performs no HMAC/signature check on the cookie value (unlike `HmacValidator` for OAuth queries or `JwtPayload` for App Bridge session tokens), so nothing in the gem itself prevents an attacker-supplied/fixated cookie from being accepted as a valid session identifier and handed to the host app's `SessionRepository.retrieve(id)`.

### Impact Explanation
If an attacker can set or fixate the app's session cookie in a victim's browser (or induce the app to process a request carrying an attacker-chosen cookie value — e.g., via a subdomain cookie-tossing/CSRF vector, or by directly hitting the app with a forged cookie for their own request), the host application — following the SDK's own documented pattern — will resolve and load a completely different shop's persisted `Session` (including its access token) via `SessionRepository.retrieve_session`. This results in cross-tenant access: actions are performed, or data is returned, under another merchant's access token, mapping to the report's "Critical – cross-tenant access" and "High – session fixation" impact categories.

### Likelihood Explanation
Exploitation requires: (1) knowledge of a target shop's `myshopify.com` domain, which is normally public, and (2) some ability to place/replace the app's session cookie value for the victim's session (a session-fixation precondition many web apps do not fully mitigate, e.g. cookie not scoped/regenerated on privilege change, or CSRF-style cookie injection). This is a design weakness rather than a memory-safety or crypto-break issue, so likelihood depends on the host app's cookie-handling hygiene, but the SDK itself provides no defense (no signing, no random component, no binding to a separate secret) once the cookie can be influenced.

### Recommendation
Do not use a deterministic, guessable value (`offline_#{shop}`, `#{shop}_#{user_id}`) as the bearer session identifier trusted directly from an unauthenticated cookie. Either (a) sign/MAC the session cookie value (e.g., HMAC with `api_secret_key`) and verify it in `cookie_session_id` before returning it, or (b) use an opaque, high-entropy random session identifier that is unrelated to the shop domain, so that knowledge of a shop's domain alone cannot produce a valid session id.

### Proof of Concept
1. Determine a target shop's domain, e.g. `victim-shop.myshopify.com` (public information for most stores).
2. Compute the deterministic offline session id the SDK would have generated: `offline_victim-shop.myshopify.com` (see `SessionUtils.offline_session_id` / `Session.from`).
3. Set the app's session cookie (`ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME`) to this value in a request to the host application (via cookie fixation/CSRF or by directly crafting the request if the app trusts client-supplied cookies without additional isolation).
4. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` verbatim from `cookie_session_id` with no verification.
5. The host app's `SessionRepository.retrieve("offline_victim-shop.myshopify.com")` returns the victim shop's stored `Session` (including its real `access_token`), and the attacker's request is now serviced using the victim shop's credentials.

        def from(shop:, access_token_response:)
          is_online = access_token_response.online_token?

          if is_online
            associated_user = T.must(access_token_response.associated_user)
            associated_user_scope = access_token_response.associated_user_scope
            id = "#{shop}_#{associated_user.id}"
          else
            id = "offline_#{shop}"
          end

          if access_token_response.expires_in
            expires = Time.now + access_token_response.expires_in.to_i
          end

          if access_token_response.refresh_token_expires_in
            refresh_token_expires = Time.now + access_token_response.refresh_token_expires_in.to_i
          end

          new(
            id: id,
            shop: shop,
            access_token: access_token_response.access_token,
            scope: access_token_response.scope,
            is_online: is_online,
            associated_user_scope: associated_user_scope,
            associated_user: associated_user,
            expires: expires,
            shopify_session_id: access_token_response.session,
            refresh_token: access_token_response.refresh_token,
            refresh_token_expires: refresh_token_expires,
          )
        end
