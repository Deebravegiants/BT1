### Title
Unchecked ERC20 `transfer` return-data in `IntentGatewayV2.withdraw` and `SweepDust` permanently freezes escrowed user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` uses low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` in `withdraw()` and the `SweepDust` handler, and only checks that the external call itself did not revert (`success`). It never decodes/validates the returned boolean payload, so a non-compliant ERC20 that signals failure by returning `false` (instead of reverting) is treated as a successful transfer.

### Finding Description
`withdraw()` releases escrowed order tokens to a beneficiary: [1](#0-0) 
and the token branch performs:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The returned data from the low-level `.call` is discarded (`(bool success,)`), so only reversion is checked — the ABI-encoded `bool` return value of `transfer` is never inspected. The identical unsafe pattern also appears for the transaction-fee payout: [3](#0-2) 
and in the `SweepDust` request handler used to sweep protocol dust to a beneficiary: [4](#0-3) 

Note that `placeOrder` in the same contract correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom`, which does validate the returned boolean: [5](#0-4) 
`using SafeERC20 for IERC20;` is declared at the top of the contract, confirming the safe wrapper is available and used elsewhere, but not on the outbound/redeem/sweep paths: [6](#0-5) 

Because `success` only reflects whether the low-level call reverted (not whether the token itself reports success), any ERC20 that returns `false` on a failed transfer (rather than reverting) — a well-documented non-standard-but-existing behavior — will cause `withdraw()` to proceed as if the transfer succeeded. It then unconditionally decrements the escrow accounting and marks the order `_filled`: [7](#0-6) 

`withdraw()` is reached from the normal ISMP-authenticated `RedeemEscrow`/`RefundEscrow` message flow in `onAccept`: [8](#0-7) 
and from `onGetResponse`, both of which are part of the standard order-fill/refund lifecycle triggered by relayed cross-chain messages, not privileged admin calls: [9](#0-8) 

### Impact Explanation
If the escrowed input token silently returns `false` on transfer failure (e.g. insufficient allowance edge cases in some non-standard tokens, blocklisting tokens like USDC-style tokens that return `false` instead of reverting, or a paused/blacklist state), the beneficiary receives nothing while the contract (a) decrements its internal escrow ledger for that commitment and (b) marks `_filled[commitment] = beneficiary`, permanently finalizing the order. The tokens remain stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them, since the order is already marked filled/refunded and cannot be retried. This is a permanent freezing-of-funds condition for the user's or solver's escrowed assets, matching the accepted impact category.

### Likelihood Explanation
This triggers whenever a token used as an order input or output implements the "return false instead of revert" failure pattern — a known, non-hypothetical ERC20 behavior class (explicitly called out in the source audit report). No attacker privilege is required; any user placing an order with such a token, or any relayer delivering a legitimate `RedeemEscrow`/`RefundEscrow`/`SweepDust` message, can trigger the faulty path through normal protocol usage.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20` elsewhere in this same file) for all outbound token transfers in `withdraw()` and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol`, instead of raw `token.call(...)` with only a `success` check. This ensures both call-reversion and returned-boolean failures are correctly treated as transfer failures.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer` decrements internal balances but returns `false` (instead of reverting) when, e.g., the recipient is blacklisted or balance conditions aren't met, while still returning `true`/no-revert on the call itself.
2. Place an order using this token as an input asset via `placeOrder` (escrowed correctly via `safeTransferFrom`).
3. Have the destination fill the order and dispatch a `RedeemEscrow`/`RefundEscrow` request back to this `IntentGatewayV2` instance, or trigger `onGetResponse`.
4. In `withdraw()`, `token.call(...)` executes without reverting and returns encoded `false`; `success` is `true`, so `if (!success) revert TransferFailed();` does not trigger.
5. `_orders[body.commitment][token] -= amount;` executes and `_filled[body.commitment] = beneficiary;` is set, finalizing the order despite the beneficiary never receiving the tokens — the tokens remain permanently locked in the contract with no further redemption path.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));

                if (!success) revert TransferFailed();
