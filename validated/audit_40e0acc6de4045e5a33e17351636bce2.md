### Title
Webhook shop/topic/webhook-id identity not bound by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `Registry.process` validates authenticates the body bytes but never authenticates the `shop-domain`, `topic`, or `webhook-id` headers that are attached to that body and handed to the app's handler as trusted tenant/event identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC purely over `verifiable_query.to_signable_string` [5](#0-4) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [3](#0-2) . Meanwhile, `shop`, `topic`, and `webhook_id` are all pulled from HTTP headers that are completely outside of that signed payload [6](#0-5) .

`Registry.process` raises `InvalidWebhookError` only if the body HMAC fails, then immediately trusts `request.topic`, `request.shop`, and `request.webhook_id` to construct `WebhookMetadata` that is passed to the app's `WebhookHandler#handle` [4](#0-3) . The binding this breaks (stated as an equality that should hold but doesn't) is:

`shop header value used to route/attribute the event == shop whose secret/body the HMAC actually authenticates`

Because the header is never part of the signed bytes, anyone who can reach the app's webhook endpoint with a *body+HMAC pair that is valid for the app's shared `client_secret`* (e.g., a value captured from a genuine webhook delivery, or — for topics with static/predictable bodies such as `app/uninstalled` payloads that may repeat across merchants — a forged pair) can attach an arbitrary `shop-domain`/`topic`/`webhook-id` header set. The handler then processes the event as if it originated from, and pertains to, the attacker-chosen shop, even though nothing in the cryptographic check ties that shop identity to the payload.

### Impact Explanation
This falls under cross-tenant access: an app's webhook handler makes tenant-scoped decisions (e.g., looking up the session/store record for `request.shop`, updating billing/subscription state, redacting or deleting data for `shop/redact`, `customers/redact`, `customers/data_request` mandatory topics) based on a `shop` value that is never covered by the signature verification in this gem. A mismatch between the shop that produced the signed bytes and the shop attributed to the event by the (unauthenticated) header lets an attacker misattribute a webhook event to a different tenant than the one it was actually signed for.

### Likelihood Explanation
Exploitability depends on the attacker being able to submit an HTTP request directly to the app's webhook receiving endpoint (bypassing Shopify's normal delivery, e.g., if the endpoint isn't restricted to Shopify's IP ranges) with a body/HMAC pair that validates. This is plausible when the attacker is themselves a merchant with the app installed on their own shop: legitimate webhook payloads for their own store are delivered to them by the app owner's server logs/observability, or, when the payload is static/predictable for a topic, they can independently compute or reuse a valid HMAC without ever seeing another shop's secret, because the HMAC key is the single shared `client_secret` for the whole app across all installs (not per-shop). This makes it a realistic identity-binding gap rather than a purely theoretical one, though it is somewhat constrained by the need to have (or construct) a body whose HMAC validates under the app's `api_secret_key`.

### Recommendation
Include the tenant/event identity fields (`shop-domain`, `topic`, and ideally `webhook-id`) in the signed payload used for verification — i.e., override `to_signable_string` to canonically bind the header values Shopify actually signs against, or, since Shopify's real webhook HMAC is computed over the raw body only by design, have `Registry.process`/`WebhookMetadata` cross-check the `shop` header against an independently-trusted source (e.g., look up the shop from the app's own session store keyed by a value derived from verified data, not solely from the unauthenticated header) before invoking the handler, and document to consumers of this gem that they must not treat `request.shop`/`request.topic` as authenticated on their own.

### Proof of Concept
1. Capture (or otherwise obtain) any valid `(raw_body, X-Shopify-Hmac-Sha256)` pair that passes `HmacValidator.validate` for the app (e.g., a legitimately delivered webhook to the attacker's own shop, or a topic with a static/predictable body).
2. POST that exact `raw_body` and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and/or replace `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [7](#0-6) , and `Registry.process` validates only the (unchanged) body HMAC [8](#0-7) , then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [9](#0-8)  to the app's handler.
4. The handler executes tenant-scoped logic (e.g., data redaction, subscription state change) attributed to `victim-shop.myshopify.com`, even though the HMAC never authenticated that shop identity.
