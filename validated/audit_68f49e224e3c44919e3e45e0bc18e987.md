### Title
Bridge/HTTP task URLs with embedded Basic-Auth credentials are logged unredacted at Debug/Trace level, exposing secrets to lower-privileged Run-role/webhook triggers - ([File: core/services/pipeline/task.bridge.go], [File: core/services/pipeline/task.http.go])

### Summary
Chainlink's `HTTPTask` and `BridgeTask` pipeline tasks build outbound requests from a URL that may contain HTTP Basic-Auth credentials embedded in the userinfo portion (e.g. `https://TOKEN@host/path`, the same pattern the Composer advisory describes for GitHub PATs). When these tasks log the destination URL for debugging, they call `url.String()`, which — unlike `net/url.URL.Redacted()` — does not mask the password (let alone the username) and prints the URL exactly as configured, credentials included.

### Finding Description
`HTTPTask.Run` resolves the task URL and immediately logs it with `url.String()` at Debug level: [1](#0-0) 
and again after the response is received: [2](#0-1) 

`BridgeTask.Run` does the same for bridge URLs (which are admin-configured `bridges.BridgeType.URL` values, potentially containing embedded credentials for a third-party external adapter) at Trace/Debug level in multiple places, including the initial "sending request" log and the failure/cache-fallback paths: [3](#0-2) [4](#0-3) [5](#0-4) 

None of these call sites use Go's `url.Redacted()` (which masks only the password) — they use plain `.String()`, so both the username and password portions of any embedded credential are emitted verbatim into the logger output. This is directly analogous to the Composer bug: Composer partially fixed this class of leak by masking the password in verbose output but still leaked a credential placed in the username slot; here, chainlink doesn't even mask the password, let alone the username, when the URL is written to Debug/Trace logs.

By contrast, the codebase elsewhere shows the "correct" pattern is well understood and used for database URLs: `periodicbackup` masks the password using `url.Redacted()` before logging pg_dump arguments [6](#0-5) , and `models.SecretURL`/`config.SecretURL` exists specifically to redact secret URLs when formatted [7](#0-6) . The HTTP/Bridge task URL logging paths were never brought in line with this pattern.

Bridge task execution is reachable by a lower-privileged "Run" role account or an authenticated External Initiator through `POST /v2/jobs/:ID/runs`, which is gated by `auth.RequiresRunRole` rather than the stronger Edit/Admin role required to view or manage bridges themselves: [8](#0-7) 

This means a principal who is authorized only to trigger job runs (not to view or manage bridge configuration) can cause the node to execute a bridge/HTTP task whose URL an administrator configured with embedded Basic-Auth credentials, and that action alone causes the credential to be written into the node's logs in cleartext once `LOG_LEVEL=debug` (or `Trace`) is enabled — a common operational setting, not an esoteric `-vvv` flag.

### Impact Explanation
If a node operator configures a bridge or HTTP task pointing to an external adapter that authenticates via a token embedded in the URL (a supported and common pattern, matching the exact GitHub-PAT-in-username case called out in the Composer advisory), that credential becomes visible in the node's own logs to anyone with log access, and the *action of causing the leak* can be triggered by an account that only has Run-role/webhook-trigger privileges, not the Edit/Admin privileges needed to read the bridge configuration directly. This is a real confidentiality impact (CWE-532), matching the CVSS profile of the reference advisory (local/low-privilege actor, high confidentiality impact, no integrity/availability impact).

### Likelihood Explanation
Requires: (1) an admin/NOP embeds credentials in a bridge or HTTP task URL (a documented usage pattern for external adapters), and (2) the node is run with Debug or Trace log level, which is common in staging/CI or during troubleshooting. Given these two realistic preconditions, a Run-role/webhook-authenticated caller can trivially trigger the leak simply by causing the job to run — no special crafting needed. Likelihood is Medium, matching the referenced advisory's Medium severity.

### Recommendation
Replace all `url.String()` calls used for logging in `task.http.go` and `task.bridge.go` with `url.Redacted()` (or a custom redactor that also masks the username, since arbitrary tokens can be placed there) before passing the URL into any `Debugw`/`Tracew`/`Infow` call. Consider introducing a shared "loggable URL" helper (extending the existing `models.SecretURL` idea) that is used consistently across all outbound-request logging, and audit other pipeline tasks/log sites that print `url.String()` for the same issue.

### Proof of Concept
1. As an admin, create a bridge (or HTTP task job spec) whose URL embeds a secret token as Basic-Auth username, e.g. `https://ghp_verysecrettoken@adapter.example.com/query`.
2. Run the node with `Log.Level = 'debug'`.
3. As a user/API-key holder who only has the Run role (or as an authenticated External Initiator), call `POST /v2/jobs/:ID/runs` to trigger the job.
4. Observe the node's log output contains the full task/bridge URL including `ghp_verysecrettoken` in cleartext, e.g. via the "Bridge task: sending request" or "HTTP task: sending request" log lines [3](#0-2) [1](#0-0) .
