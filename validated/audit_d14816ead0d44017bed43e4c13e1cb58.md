### Title
Unrestricted arbitrary calls in `EmporiumUpgradeable.runAction` allow an attacker to self-approve and drain any residual/stranded ERC20 balance held by the action, bypassing the `deltaAmountChanges`/`balanceChange` invariant - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction`'s "stateless" op path executes `op.endpoint.call(op.callData)` with the Emporium contract as `msg.sender` and blocks only two selectors (`callHinkalWallet`, `doSendToRelay`). An attacker can inject an `EmporiumOperation` that calls `ERC20.approve(attacker, type(uint256).max)` on any token the Emporium contract holds. Because this call causes no balance delta inside the transaction, it passes the `BalanceChangeShouldBePositive` check trivially, and the attacker later drains the approved balance with a plain `transferFrom`, entirely outside the `deltaAmountChanges` accounting.

### Finding Description
The invariant the protocol relies on is: *tokens leaving Emporium in a transaction == `-deltaAmountChanges` Hinkal sent it that transaction*, enforced in `runAction` via [1](#0-0) 
This check only reasons about **balance deltas inside the current call**, and never inspects the ERC20 *state* (allowances) that arbitrary calls can mutate.

The ops loop lets the attacker target any endpoint/calldata, blocking only two selectors: [2](#0-1) 

Crucially, this arbitrary-call ability is entirely unconstrained when the attacker sets `stack.signerAddress = address(0)`, because `verifyWallet` skips all EIP-712 signature verification in that case: [3](#0-2) 

The ops array is decoded directly from attacker-supplied `externalActionMetadata`: [4](#0-3) 

The ops execution is not tied to `circomData.erc20TokenAddresses` at all — the attacker can include an `approve` op for a token that never appears in `erc20TokenAddresses`/`deltaAmountChanges`, so no balance-change check ever fires for it.

**Attacker's exact call:** call `Hinkal.transact` with a trivial/self-funded proof, `circomData.externalActionData.externalActionId` pointing at Emporium, and `externalActionMetadata` = `abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: strayToken, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max)})], ...}))`.

**Exploit flow:**
1. Residual/stray balance `R` of `strayToken` accumulates in the Emporium contract (e.g., from a previous run's ops that called a router — such as LI.FI — whose refund of an unlisted token landed on Emporium's own balance and was never swept because it wasn't in that transaction's `erc20TokenAddresses`).
2. Attacker calls `Hinkal.transact` with the malicious `approve` op above. Since no balance for `strayToken` changes during this call, `balanceChange` for any tracked index stays `0`/consistent and `BalanceChangeShouldBePositive` never reverts.
3. In a separate, ordinary (non-Hinkal) transaction, the attacker calls `strayToken.transferFrom(emporium, attacker, R)`, draining the balance completely outside the `deltaAmountChanges`/UTXO accounting.

**Why existing guards fail:** `performHinkalChecks`, `verifyProof`, nullifier insertion, and `dimensionsCheck` validate only the shielded input/output side of the attacker's own proof; none of them inspect or restrict what `runAction`'s op execution does to third-party contract state. `onlyAllowedRecipient` only gates *who* may call `runAction` (must be Hinkal itself), not the content of `op.endpoint`/`op.callData`. The `balanceChange >= 0` check is a same-transaction, same-token delta check and is blind to allowance mutations that enable theft in a later transaction.

### Impact Explanation
Any ERC20 balance stranded on the Emporium contract — which the protocol's own design intends to fully sweep back to depositors via `handleOut` — can instead be permanently diverted to an unprivileged attacker via a self-granted `approve`. If the stranded balance originated from another user's in-flight funds (e.g., an unswept router refund from that user's swap-through-Emporium operation), this is direct theft of in-flight user funds (Critical). At minimum, it allows an attacker to execute calls that move assets never authorized by any wallet owner or prover (High).

### Likelihood Explanation
No privileged role is required. The attacker only needs the ability to call `Hinkal.transact` with a self-generated proof (any unprivileged user can do this, even with trivial/zero-value inputs) and to construct `externalActionMetadata` for Emporium with `signerAddress = address(0)` (which is explicitly permitted and skips all signature checks). The only precondition is that Emporium currently holds a nonzero stray/residual balance of some ERC20, which is plausible any time a routed call inside an Emporium op (e.g., a LI.FI swap) leaves an untracked refund on the Emporium contract, or from any accidental/incidental balance. The attack is repeatable for every stray balance that ever appears and costs only gas plus one cheap Hinkal transaction.

### Recommendation
Restrict the stateless op path in `EmporiumUpgradeable.runAction` so it cannot call state-mutating ERC20/ERC721 functions that grant allowances or operator rights (`approve`, `increaseAllowance`, `setApprovalForAll`, `permit`, etc.) on any token, or more generally maintain an explicit allow-list of callable selectors/endpoints for the stateless path instead of a deny-list of two selectors. Additionally, sweep or account for any token balance change resulting from ops regardless of whether the token is present in `erc20TokenAddresses`, so no value can silently remain parked in the Emporium contract between transactions.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as an allowed recipient/external action), and a mock ERC20 `strayToken`.
2. Seed residual: directly `strayToken.mint`/`transfer` some amount `R` to the Emporium contract address (simulating an unswept router refund) — do not go through any user's accounting.
3. As attacker (unprivileged EOA), craft a normal `Hinkal.transact` call with a valid proof for a trivial/self-owned UTXO, whose `externalActionData` targets Emporium with `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: strayToken, invokeWallet:false, value:0, callData: approve(attacker, type(uint256).max)}]}`.
4. Assert the transaction succeeds (`BalanceChangeShouldBePositive` never reverts, no UTXO minted for `strayToken`), i.e. LHS "tokens leaving Emporium this tx" == 0 == RHS "`-deltaAmountChanges` this tx" (both zero, invariant apparently holds within the tx).
5. As attacker, call `strayToken.transferFrom(emporium, attacker, R)` directly (not via Hinkal).
6. Assert `strayToken.balanceOf(attacker) == R` and `strayToken.balanceOf(emporium) == 0`, proving value left the action with no corresponding `deltaAmountChanges` ever recorded by Hinkal — breaking the claimed equality across the two transactions.
