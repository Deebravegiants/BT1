## Title
Webhook `shop` (and other identifying headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values are all taken from HTTP headers that sit entirely outside the HMAC's signed payload. Any party who can obtain one valid `(body, hmac)` pair — trivially available to any merchant/tenant who installs the app, since they can trigger webhooks for their own shop — can replay that pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, and the app's handler is invoked believing the payload belongs to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other identifying fields are read straight from headers without any cryptographic binding: [2](#0-1) 

`Registry.process` validates only this HMAC and then trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the metadata passed to the host application's handler: [3](#0-2) 

The HMAC computation itself only ever hashes the signable string (the body) against the secret: [4](#0-3) 

This breaks the intended binding: `HMAC(secret, body) == received_hmac` is treated as proof that `shop-domain header == originating tenant`, but the header is never part of what is hashed. The equality that should hold — `shop claimed in header == shop that produced the signed body` — is not enforced anywhere in this library.

### Impact Explanation
An app can receive many merchants as tenants. A malicious merchant who installs the app can generate a legitimate webhook for their own shop (e.g., by creating an order, updating a product, etc. — anything that triggers a subscribed topic) and thereby obtain a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared secret. Because the `shop-domain` header carries no cryptographic binding to that body, the attacker can resend the same body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. `Registry.process` will accept it as valid and dispatch it to the host application's handler tagged as belonging to the victim tenant. Depending on how the host application keys work off `WebhookMetadata#shop` (e.g., updating per-tenant records, revoking sessions, syncing inventory), this enables cross-tenant data corruption/injection — satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Any merchant who installs the app already has everything needed: they can generate their own valid webhook, capture the body and its HMAC, and resend it against the endpoint with a spoofed `shop-domain` header (webhook endpoints are public HTTP endpoints, not authenticated by TLS client certs or IP allow-listing in this gem). No access to `api_secret_key` or another tenant's credentials is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api_version`, `webhook_id`) in the signed payload verification, or independently verify that the shop asserted in the header matches an application-level record for that installation before trusting it. At minimum, document that host applications must not rely on `WebhookMetadata#shop` as an authenticated value without additional verification (e.g., cross-checking against the shop associated with the currently stored session/token for that webhook subscription).

### Proof of Concept
1. Attacker installs app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a subscribed webhook topic (e.g., `orders/create`) on their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this is a validly-signed `(body, hmac)` pair.
3. Attacker replays this exact body/HMAC to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `HMAC(secret, raw_body)`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata` with `shop: request.shop` = `"victim.myshopify.com"` and invokes the host app's handler, which processes the attacker-controlled body as if it originated from the victim tenant.
