### Title
Webhook shop/topic attribution bypass via unauthenticated headers not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` uses to route and attribute the webhook are read straight from HTTP headers that are never included in the signed bytes. An attacker who possesses one genuine `(body, hmac)` pair signed by the app's real secret can replay that exact body/HMAC while freely rewriting the `x-shopify-shop-domain` and `x-shopify-topic` headers, and the gem's own `HmacValidator` will report the request as valid.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed from headers that are outside that signed string: [3](#0-2) 

`Registry.process` then uses these unauthenticated header-derived values as the ground truth for both **handler dispatch** (`@registry[request.topic]`) and **tenant attribution** (`shop: request.shop` passed into `WebhookMetadata`): [4](#0-3) 

This is the exact binding break described in the bug class: a field (`shop`, `topic`) is *acted on* by the library but *not covered by the HMAC*. The equality that should hold is:

`hmac_signer(secret_of_shop_S) == hmac_of(raw_body)` **and** `S == request.shop`

but the code only checks the first half; `request.shop`/`request.topic` are trusted unconditionally and independently of what actually produced the HMAC. Any party who can obtain one legitimate `(raw_body, hmac)` pair — trivially available to any developer who installs their own app instance and receives a single real webhook, no `api_secret_key` needed — can resend that identical body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` still passes because it only re-derives the HMAC from `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the attacker-chosen shop/topic.

### Impact Explanation
Downstream webhook handlers (including the mandatory compliance topics `shop/redact`, `customers/redact`, `customers/data_request` that this gem explicitly special-cases) key their tenant-scoped logic off `WebhookMetadata#shop`. By replaying a self-obtained valid webhook body under a forged `shop-domain`/`topic` header, an unprivileged caller can make the app process/act on data as belonging to a different, victim shop — a cross-tenant confusion in the library's own trust boundary between "HMAC-authenticated bytes" and "header-attributed tenant." This matches the Critical cross-tenant-access impact category.

### Likelihood Explanation
Any developer with a working app instance can trivially capture one legitimate `(body, hmac)` pair from their own store's webhook delivery — no privileged secret, leaked credential, or social engineering required. Constructing the replay with rewritten headers is a simple HTTP request; the flaw is deterministic and always present in `Request`/`Registry.process`, not a race condition.

### Recommendation
Bind the header-derived identifiers into the signed material, or otherwise cryptographically tie `shop`/`topic` to the HMAC before trusting them: e.g., verify the `x-shopify-shop-domain` against the session/shop context the request is expected for, or extend `to_signable_string` (or a secondary check) to incorporate the shop domain and topic so that a mismatch invalidates the HMAC rather than silently passing.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; wait for (or trigger) one genuine webhook delivery, e.g. `orders/create`. Capture the raw body `B` and the `x-shopify-hmac-sha256` header `H` — both valid because Shopify signed `B` with the app's real secret.
2. Replay an HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally change `x-shopify-topic` to `shop/redact` or another registered topic).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Registry.process(request)` calls: [5](#0-4) 
   `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B) == H`, which still holds — the shop/topic headers were never part of the signed input.
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and/or a spoofed `topic`, despite the payload never having been generated for that shop/topic by Shopify.
