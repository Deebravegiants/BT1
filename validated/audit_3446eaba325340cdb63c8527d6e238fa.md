This confirms the finding: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` verifies only `Utils::HmacValidator.validate(request)` (which HMACs `to_signable_string`, i.e. the body) and then dispatches the handler using `request.shop` taken straight from the header, unbound to the signature [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw request body only. The `shop-domain` (and `topic`, `webhook-id`, `api-version`) headers are never included in the signed material, yet `Registry.process` trusts `request.shop` to identify which tenant a webhook body belongs to when invoking the registered handler.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field [4](#0-3) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [1](#0-0) , so the signature only proves "this body was signed with the app's client secret" — it proves nothing about which shop the body is associated with, because `shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is not part of the signed input [5](#0-4) .

`Registry.process` relies on this unbound header to route the payload: it validates the HMAC, then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and calls the merchant-specific handler with that `shop` value [3](#0-2) .

Because Shopify apps typically share a single `api_secret_key` across all installations of the app (it is not shop-specific), any actor who has access to one legitimate, validly-signed webhook body/HMAC pair (e.g. by installing the app on their own store and capturing a webhook delivery) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it only checks the body signature, and `Registry.process` will hand the attacker-chosen `shop` value to the handler together with the attacker's own (but validly-signed) body — breaking the equality that should hold: *shop authenticated by the signature == shop the handler acts on*.

### Impact Explanation
This is a cross-tenant identity-binding failure: the tenant (`shop`) that the webhook payload is attributed to is not cryptographically bound to the payload that was actually signed. Any application built on this gem that uses `WebhookMetadata#shop` to select which merchant's records to update (the documented and expected usage pattern) can be made to apply attacker-controlled webhook data under another merchant's identity, i.e. cross-tenant access/data corruption — meeting the Critical bar for cross-tenant access.

### Likelihood Explanation
Exploitation requires: (1) the webhook receiving endpoint to be reachable from the internet (true by design, since Shopify itself delivers webhooks over HTTP(S) to a public URL), and (2) the attacker to obtain one valid signed body/HMAC pair, which is trivial for any unprivileged user who can install the app for free on their own shop (or observe/replay one of their own webhook deliveries). No access to the app's `client_secret`, an access token, or another merchant's credentials is required.

### Recommendation
Bind the shop identity into the verified material — e.g. include `shop-domain` (and `topic`) in the signable string, or require that `request.shop` be cross-checked against a shop that this application instance has actually installed the app for/registered a webhook for (as `shopify_app`-style integrations typically do via a persisted `Shop` lookup keyed on the domain that received an authenticated OAuth install), rather than trusting the header value produced by an unauthenticated caller as-is.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and captures a legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(secret, B)`, and `secret` is the same `api_secret_key` for every shop that has the app installed).
2. Attacker sends a POST directly to the app's public webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses the forged shop header [6](#0-5) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B` [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process attacker-controlled data as if it originated from the victim's shop.
