### Title
POA Bridge withdrawal status/hash matched only by assetId lets one batched withdrawal's completion be reported for another - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` and the standalone `waitForWithdrawalCompletion()` helper in `internal-utils` resolve which withdrawal record from the POA Bridge API response corresponds to a given `WithdrawalIdentifier` using `findMatchingWithdrawal`, which matches **only by `assetId`** (`nep141:${near_token_id}`), ignoring the `index`, destination address, and amount. When a single NEAR transaction batches multiple withdrawals of the *same* token (e.g., to two different destination addresses), this lookup returns the *first* matching record in the API response for every one of those withdrawals.

### Finding Description
The SDK supports batching several `WithdrawalParams` into one NEAR transaction (`createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` iterates `args.withdrawalParams: WithdrawalParams[]` and assigns each a `bridge`-scoped `index`) [1](#0-0) . For the POA route, `createWithdrawalIdentifier` builds a `WithdrawalIdentifier` that carries the `index`, but that `index` is **never used** when resolving status [2](#0-1) .

`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which is documented in-code as only matching by `assetId`:
```
// NOTE: Currently only matches by assetId. This means multiple withdrawals
// of the same token in a single transaction are not supported.
``` [3](#0-2) [4](#0-3) 

The same matching-by-`assetId`-only logic (and the identical caveat comment) exists in the standalone helper used by other integrators of `internal-utils`: [5](#0-4) 

Because the POA Bridge API returns an unsorted list of withdrawal records for the transaction hash, and matching keys only on `nep141:<near_token_id>`, if a batch contains withdrawal A (asset X → address A) at index 0 and withdrawal B (asset X → address B) at index 1, `watchWithdrawal` for **both** identifiers will resolve to whichever matching record `Array.prototype.find` returns first — typically the same one. The equality broken is: *the status/txHash reported for withdrawal B is not the on-chain outcome of withdrawal B's specific transfer* — it is withdrawal A's outcome, misattributed to B (or vice versa).

### Impact Explanation
If an integrator relies on `sdk.waitForWithdrawalCompletion` / `waitForWithdrawalCompletion` to determine when to release/credit funds tied to a specific withdrawal (e.g., crediting a user's off-chain ledger when their specific withdrawal completes, or reconciling per-request destination tx hashes), a same-token multi-destination batch will make one withdrawal appear "completed" with a `txHash` that actually belongs to a different destination/withdrawal. This can cause: crediting a withdrawal as done when it is not (funds might not have actually reached that destination yet or ever, if only one leg completed), or attributing the wrong destination transaction hash to the wrong request — a status/hash misreport that can make an integrator credit twice or fail to detect a still-pending/failed leg. This matches the "High" impact category: *a status or hash misreport making an integrator credit or refund twice*.

### Likelihood Explanation
This requires no malicious actor — it is triggered by ordinary use of the SDK's own supported batching feature (multiple `WithdrawalParams` of the same asset in one call), which the code explicitly anticipates and only partially guards against with a comment, not an actual index/amount/address-based match. Any integrator batching withdrawals of the same token to different destinations in a single NEAR transaction will hit this deterministically once the POA bridge processes more than one leg for that asset.

### Recommendation
Match POA withdrawal records using more than `assetId`: incorporate destination address and/or amount (as the code comment itself suggests — sort both API results and requested withdrawals by amount for the same asset and pair them positionally), or reject/require POA to disambiguate batched same-asset withdrawals with a unique reference before reporting completion. Until the POA API supports per-leg identifiers, the SDK should either disallow batching multiple same-asset POA withdrawals in one transaction or clearly surface an error/ambiguous state instead of silently reporting one leg's hash for another's identifier.

### Proof of Concept
1. Withdraw 100 nep141:btc.omft.near to address A and 50 nep141:btc.omft.near to address B in the same NEAR transaction (batched via `sdk.processWithdrawal`/`waitForWithdrawalCompletion` with two `WithdrawalParams` sharing the same `assetId`).
2. POA Bridge API returns two withdrawal records for `tx_hash`, both with `near_token_id: "btc.omft.near"`, differing `transfer_tx_hash`/`address`.
3. `watchWithdrawal` for index 0 (→A) and index 1 (→B) both call `describeWithdrawal`, which both resolve via `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")` — returning the same first-matching record (e.g., A's completed record) for both identifiers, as shown in the existing test `"matches withdrawal by assetId, not by index"` [6](#0-5)  which demonstrates index is not used at all — this test only differentiates by using different `assetId`s, but if both entries shared the *same* `assetId`, both indices would resolve to the same record.
4. The integrator polling for withdrawal to address B receives address A's `txHash`/completion status, misreporting B's on-chain outcome.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
