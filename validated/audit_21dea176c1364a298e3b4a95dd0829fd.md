### Title
Permanent desynchronization of `amm.lp_amount` from actual `lp_mint.supply` via out-of-band LP token burn causes pool insolvency / stranded funds - ([File: program/src/processor.rs])

### Summary
Raydium's AMM does not use the LP SPL-mint's actual `supply` as the source of truth for pro-rata share calculations in `Deposit` and `Withdraw`. Instead it maintains a separately tracked counter, `AmmInfo.lp_amount`, which is only ever mutated inside `process_deposit` and `process_withdraw`. Because the LP mint is a standard SPL token, any LP holder can burn their own LP tokens directly via the SPL Token program's `Burn` instruction (bypassing Raydium's `Withdraw` instruction entirely). This permanently reduces the real `lp_mint.supply` while leaving `amm.lp_amount` unchanged, causing the two values to diverge forever — analogous to the reported griefing pattern where a token-holder can permanently corrupt an accounting invariant (`totalSupply`) by taking a path that bypasses the code that keeps it in sync.

The only place actual mint supply is even consulted in withdraw is a loose sanity bound: [7](#0-6) 

This check only ensures `withdraw.amount` doesn't exceed `lp_mint.supply` or `amm.lp_amount` — it does not reconcile the two values, nor does anything else in the program.

Because `Invokers::token_burn` only requires the LP token account owner as signer (not the mint/AMM authority), any LP holder can call the SPL Token program's `Burn` instruction directly on their own LP ATA: [8](#0-7) 

This SPL `Burn` call is entirely outside Raydium's instruction set (it doesn't invoke the AMM program at all) and irreversibly reduces `lp_mint.supply`. Since `amm.lp_amount` has no code path that re-derives it from the mint's real supply, it permanently retains an inflated (stale) value once any holder burns LP tokens this way.

### Impact Explanation
Once `amm.lp_amount` is desynchronized (larger than the true circulating `lp_mint.supply`), every subsequent `Deposit` mints LP tokens using an inflated total, and every subsequent `Withdraw` computes `coin_amount`/`pc_amount` as `withdraw.amount / amm.lp_amount * pool_total`, understating each unit of real LP's rightful share of the pool. The value that should have belonged to the "phantom" burned LP (an amount of coin/pc tokens sized in the same proportion as the burned share) can never be withdrawn by anyone, since no LP token exists to redeem it, yet `amm.lp_amount` continues to account for it as claimable. This produces:
- Permanent under-payment to every future LP withdrawer (each LP token is worth strictly less than it should be).
- Permanently stranded/unbacked pool assets equal to the proportional value of the maliciously (or accidentally) burned LP, which can never be recovered by any instruction in the program (Deposit, Withdraw, WithdrawPnl, or swaps do not touch/reset `lp_amount` outside the two update sites shown above).

This is a permanent insolvent-accounting / fund-freezing condition reachable by any unprivileged LP holder in a single transaction, matching the report's core bug class (an accounting invariant permanently and irreversibly corrupted by bypassing the program's own update path).

### Likelihood Explanation
High. No special privileges are required — any LP holder can submit a standard SPL Token `Burn` instruction against their own LP token account at any time. This requires no interaction with the Raydium program, no signature from the AMM authority, and no restriction is imposed by the SPL Token program (self-burns are always permitted by token account owners). The attacker only needs to hold any nonzero amount of LP tokens for a pool.

### Recommendation
Do not maintain `amm.lp_amount` as an independently tracked counter that can diverge from ground truth. Instead:
- Read the LP mint's actual `supply` field directly from the `amm_lp_mint_info` account at the start of `process_deposit`/`process_withdraw` (as is already unpacked via `Self::unpack_mint`) and use it as the denominator/token_total for `InvariantPool` calculations instead of `amm.lp_amount`.
- If `amm.lp_amount` must be retained for logging/back-compat, resynchronize it from `lp_mint.supply` on every instruction that touches LP shares, rather than trusting incremental updates that can be bypassed by direct SPL Token operations.

### Proof of Concept
1. Pool is initialized normally; `amm.lp_amount == lp_mint.supply == L`.
2. Any LP holder Alice, owning `X` LP tokens in her own ATA, submits a standalone transaction invoking the SPL Token program's `Burn` instruction (not Raydium's `Withdraw`) burning `X` of her LP tokens.
   - `lp_mint.supply` becomes `L - X`.
   - `amm.lp_amount` remains `L` (Raydium's program was never invoked, so nothing in `processor.rs` updates it).
3. Any subsequent LP holder Bob calls `Withdraw` for `w` LP tokens. `coin_amount`/`pc_amount` are computed via `InvariantPool { token_input: w, token_total: amm.lp_amount (== L) }.exchange_pool_to_token(pool_total, Floor)` — using the stale, inflated `L` instead of the true `L - X`, so Bob receives `w/L * pool_total` instead of the correct `w/(L-X) * pool_total`, permanently under-crediting every future withdrawer by a factor proportional to `X/L`.
4. The `X/L` fraction of pool coin/pc value that should have been distributable to Alice's now-nonexistent LP tokens is never paid out to anyone and remains locked in the vaults indefinitely, since no code path ever reduces `amm.lp_amount` to reflect Alice's out-of-band burn.
