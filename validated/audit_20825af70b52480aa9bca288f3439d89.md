### Title
Webhook HMAC signature does not bind `shop-domain` header, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, while the `shop` identifier used to route/attribute that webhook to a tenant is taken from an HTTP header that is never covered by the HMAC. This breaks the identity binding `hmac-authenticated bytes == shop attributed to the event`, letting anyone who can obtain one valid `(raw_body, hmac)` pair (e.g., from their own shop's legitimate webhook deliveries, which requires no special credential) replay it to the app with a forged `shop-domain` header pointing at an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers, independent of the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only from `to_signable_string` (i.e. the body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` uses this validation result as the sole authentication check, then immediately trusts `request.shop` (the unauthenticated header) as the tenant identity handed to the app's handler: [4](#0-3) 

Because the signature covers only the body bytes and not the shop, an attacker who legitimately owns any shop that has the app installed can capture a genuinely Shopify-signed `(raw_body, hmac)` pair from their own webhook deliveries (no `api_secret_key`, access token, or other privileged material required — Shopify sends this pair to the attacker's own endpoint as part of normal webhook delivery) and then submit an HTTP request to the app's webhook endpoint with that same body/hmac but with the `X-Shopify-Shop-Domain` header rewritten to a different, victim shop's domain. `HmacValidator.validate` will still return `true` (the body is unchanged and correctly signed), and `Webhooks::Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain, `WebhookMetadata#body` containing attacker-influenced content that was never associated with the victim.

### Impact Explanation
This is a cross-tenant confusion/injection primitive: data or events attributable to one shop can be attributed to an arbitrary other shop purely by forging an HTTP header, without needing any secret belonging to the victim shop or the app. Depending on how the host application's `WebhookHandler#handle` uses `data.shop` (e.g., to look up the target shop's session, update per-shop caches/state, or trigger shop-scoped side effects), this can lead to writing attacker-controlled data into another tenant's context — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires a party with a normal (unprivileged) shop that has the target app installed, which is a low bar (any merchant can install a public app or the attacker can install their own test app instance if the app is available). No `api_secret_key`, access token, or other privileged/leaked credential is required — the attacker uses body/HMAC pairs that Shopify legitimately delivers to their own endpoint. The forgery only requires rewriting one HTTP header on replay.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the HMAC-signed payload verification, or independently verify the `shop-domain` header against a known/expected shop for the webhook subscription (e.g., cross-check against a stored per-shop webhook registration) before trusting it in `Webhooks::Registry.process`. At minimum, document that consumers of `WebhookMetadata#shop` must not treat it as cryptographically authenticated and must independently validate the shop against their own tenant records before taking shop-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (no special privilege beyond being a normal merchant).
2. Attacker triggers a webhook event on their own shop (e.g., `orders/create`) and captures the raw POST body and the legitimate `X-Shopify-Hmac-Sha256` value that Shopify sends to the app's webhook endpoint.
3. Attacker replays this exact `(raw_body, hmac)` pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks the body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31), and `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker's body> ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host app to process attacker-supplied data as if it originated from `victim.myshopify.com`.
