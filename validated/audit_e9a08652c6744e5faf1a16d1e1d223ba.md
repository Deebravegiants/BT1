### Title
Backend-updated `Config` (self_serve, self_serve_button, operator_qr_expiration_time) is snapshotted once at `MasterPlan::run` start and never refreshed for the lifetime of the signup loop - (File: src/plans/mod.rs)

### Summary
`MasterPlan::run` destructures the shared, backend-controlled `Config` object exactly once before entering its main signup loop, and reuses those stale local copies of `self_serve`, `self_serve_button`, and `operator_qr_expiration_time` across every subsequent loop iteration (i.e. every subsequent signup) for as long as the process runs. Meanwhile, `Observer`'s `DefaultPlan::config_update` concurrently downloads fresh configuration from the backend and writes it into the very same `Arc<Mutex<Config>>` on a fixed interval. This is structurally the same desync described in the external report: a governance-controlled value (`Core.vcon`, updatable by `GOVERNOR`) is cached once by a dependent component (`CoreRef._vcon`) and never re-synchronized, so updates made through the authoritative channel silently fail to propagate to the component enforcing security-relevant behavior.

This shows the correct/expected pattern is "read the live value each time," which `MasterPlan::run`'s outer-loop values fail to do — exactly analogous to the report's first mitigation ("dynamically fetch ... whenever used, avoid storing a static copy").

### Impact Explanation
`operator_qr_expiration_time` is the authorization re-validation window: an operator's scanned QR code remains trusted to authorize new user signups until this duration elapses, after which the orb is supposed to require a fresh operator QR scan (see `scan_initial_qr_codes`/`scan_remaining_qr_codes` checks against `operator_data.timestamp.elapsed() < operator_qr_expiration_time`). If the backend (the "governor" of this policy) shortens this expiration window — e.g. to react to detected operator credential abuse or a compromised operator QR code — a long-running `orb-core` process will keep enforcing the old, longer expiration value it captured at `run()` startup, since the value is never re-read from the live `Config`. This permits the orb to continue authorizing user signups under a stale (looser) operator-QR validity policy after the backend intended a stricter one, i.e. a misattributed/unauthorized-signup enforcement bypass. Similarly, `self_serve`/`self_serve_button` control whether unattended self-serve signups are permitted at all; toggling these off via backend config will not take effect on an already-running signup loop.

### Likelihood Explanation
This does not require any special privilege or hardware access to trigger — it manifests purely from normal backend configuration updates during ordinary long-running operation of `orb-core` (the process is designed to loop through many signups without restarting, per `oneshot`/`has_biometric_input` gating). Any legitimate backend config change to these fields during that window is silently ignored until the process restarts, making the desync highly likely to occur in production operation whenever the backend adjusts these settings.

### Recommendation
Re-fetch the relevant `Config` fields (`self_serve`, `self_serve_button`, `operator_qr_expiration_time`, `orb_relay_shutdown_wait_for_pending_messages`, `orb_relay_shutdown_wait_for_shutdown`) from `orb.config.lock().await` inside the `loop` on each iteration (as already done in `do_signup`/`verify_user_qr_code`) instead of destructuring them once before the loop in `MasterPlan::run`. This ensures backend-driven policy updates (e.g., tightening the operator QR expiration or disabling self-serve) take effect immediately rather than only after a process restart.

### Proof of Concept
1. Start `orb-core` with `Config.operator_qr_expiration_time` = 23h (default) and `self_serve = true`.
2. `MasterPlan::run` captures these values once at `src/plans/mod.rs:328-336` and enters its signup loop.
3. While the loop is running (processing multiple signups), the backend management API updates the orb's config to shorten `operator_qr_expiration_time` to e.g. 5 minutes and/or disable `self_serve`.
4. `Observer::DefaultPlan::config_update` (`src/brokers/observer.rs:187-205`) downloads this new config and overwrites the shared `Arc<Mutex<Config>>`.
5. `MasterPlan::run`'s loop, however, keeps using its original local `operator_qr_expiration_time`/`self_serve` values for `scan_initial_qr_codes`/`idle_wait_for_signup_request` on every subsequent iteration, so an operator QR scanned hours earlier remains accepted well past the backend's new intended expiration, and self-serve signups continue even though the backend disabled them — until the `orb-core` process is restarted.

                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
