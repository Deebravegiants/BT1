### Title
Unused ETH from relayer-fee swaps is refunded to `EvmHost` instead of the original caller in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all convert `msg.value` into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`, but never handle or forward back any leftover native token to the caller who supplied `msg.value`.

### Finding Description
`swapETHForExactTokens` on a standard Uniswap V2 router refunds any unspent ETH (`msg.value - amounts[0]`) to `msg.sender` of that call. Because `EvmHost` itself is the caller of the router (`EvmHost` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)`), the refund from the router lands back on the `EvmHost` contract, not on the original transaction sender who funded `msg.value` on `dispatch`/`fundRequest`. [1](#0-0) [2](#0-1) [3](#0-2) 

None of these three functions capture the return value of `swapETHForExactTokens` (the actual amount spent) or check `address(this).balance` before/after the swap to compute and refund any excess back to `_msgSender()`/`post.payer`/`get`'s sender. The excess native token is simply left sitting in `EvmHost`'s balance, permanently unaccounted for and unreachable by the depositor.

This is directly analogous to the reported `ArrakisV2Router.addLiquidityPermit2` bug class: a code path that is supposed to (and in similar sibling code paths, does) refund unspent native tokens to the caller fails to do so, causing user funds to be silently absorbed by the contract. Notably, sibling logic in `IntentGatewayV2.placeOrder` explicitly tracks `msgValue -= amounts[0]` after calling `swapETHForExactTokens` and refunds the remainder to `msg.sender` via `_sendValue`, proving the protocol is aware refunds are needed for exactly this swap pattern — but this handling is missing at the `EvmHost` layer itself. [4](#0-3) 

Any unprivileged caller invoking `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, or `EvmHost.fundRequest` with slightly more `msg.value` than the exact swap cost for `post.fee`/`get.fee`/`amount` (which is generally unavoidable since exact swap-in cost cannot be known in advance due to price movement across the same block/tx) will have the leftover ETH captured by `EvmHost` with no mechanism to reclaim it.

### Impact Explanation
Every relayer-fee-paying dispatcher/relayer/app that funds a `POST`/`GET` request or tops up a pending request's fee with native ETH (rather than pre-approved `feeToken`) permanently loses any ETH sent in excess of the exact amount the router needs to buy the specified fee. Since it is effectively impossible for a caller to compute the exact wei needed to buy an exact-output amount of `feeToken` at the moment the transaction executes (due to price/slippage), essentially every native-ETH-funded dispatch will overpay and lose the difference. This is a direct, permanent loss of user funds with no recovery path — meeting the "permanent freezing/loss of funds" bar for this scan.

### Likelihood Explanation
High. This triggers on the ordinary, permissionless, and expected usage path: any external caller (app, relayer, user) dispatching a POST/GET request or funding a request while paying the relayer fee in native ETH, which is an explicitly documented supported payment method. No governance or privileged role is required — a plain user transaction triggers the loss every time `msg.value` doesn't exactly match the router's required input.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest`, capture the `amounts` array returned by `swapETHForExactTokens` (or snapshot `address(this).balance` before/after the swap) and refund `msg.value - amountSpent` back to `_msgSender()` (or the designated `payer`), mirroring the pattern already used in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch(DispatchPost)` with `post.fee = X` (in `feeToken` units) and sends `msg.value = Y` ETH, where `Y` is a conservative overestimate of the ETH needed to buy `X` feeToken (unavoidable in practice since the exact on-chain price at execution is unknown beforehand).
2. Inside `dispatch`, `EvmHost` calls `IUniswapV2Router02.swapETHForExactTokens{value: Y}(X, path, address(this), block.timestamp)`.
3. The router spends only `amounts[0] < Y` ETH to acquire exactly `X` feeToken, and refunds `Y - amounts[0]` ETH to its caller — which is `EvmHost` (`msg.sender` from the router's perspective), not the original transaction sender.
4. `dispatch` proceeds to emit the `PostRequestEvent` and returns; the refunded `Y - amounts[0]` ETH remains stranded in `EvmHost`'s balance with no code path to return it to the caller.
5. Repeat for `dispatch(DispatchGet)` and `fundRequest` — identical pattern, identical loss. [5](#0-4)

    /**
     * @dev Dispatch a POST request to Hyperbridge
     *
     * @notice Payment for the request can be made with either the native token or the feeToken.
     * If native tokens are supplied, it will perform a swap under the hood using the local uniswap router.
     * Will revert if enough native tokens are not provided.
     *
     * If no native tokens are provided then it will try to collect payment from the calling contract in
     * the feeToken.
     *
     * @param post - post request
     * @return commitment - the request commitment
     */
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
