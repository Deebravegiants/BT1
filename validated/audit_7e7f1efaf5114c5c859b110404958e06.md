### Title
Missing zero-address recipient check allows withdrawal of an entire position to an unrecoverable address - ([File: contracts/controller/src/positions/supply.rs])

### Summary
`withdraw` lets an authorized caller choose an arbitrary external recipient, while a withdrawal amount of `0` requests the account’s entire position in that asset. A caller that supplies the zero/unrecoverable Stellar account address as `to` therefore burns the supply position and sends all underlying tokens to an address nobody can control. [1](#0-0) [2](#0-1) 

### Finding Description
`process_withdraw` defaults `to` to `caller`, but accepts any other `Address`. Its only recipient validation rejects the controller and pool; it does not reject the all-zero account address or another provably uncontrolled burn address. [3](#0-2) [2](#0-1) 

The aggregated withdrawal uses `ZeroLeg::MeansAll`, so an input amount of `0` is converted to the withdraw-all sentinel and passed to the pool. [4](#0-3) [5](#0-4) 

The pool then burns the corresponding supply shares, debits cash, and invokes the token transfer to the supplied recipient. [6](#0-5) [7](#0-6) 

### Impact Explanation
Medium: an authorized caller can permanently lose the account’s entire collateral position in one transaction by combining `amount = 0` with an unrecoverable recipient. The position is burned and the tokens are transferred away, with no protocol-level recovery path. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
The call requires owner or delegate authorization, so this is a user-input mistake rather than third-party theft. It is nevertheless reachable through the public `withdraw` endpoint and only requires selecting the wrong recipient while using the supported withdraw-all amount. [10](#0-9) [3](#0-2) 

### Recommendation
Extend `require_external_recipient` to reject the canonical all-zero Stellar account address and any other known protocol burn/uncontrolled recipient. The check should run before payment aggregation or pool accounting so the position cannot be burned before a rejected transfer. [2](#0-1) 

### Proof of Concept
1. Create an account and supply collateral so it owns a positive supply position.
2. Call `Controller::withdraw(caller, account_id, vec![(hub_asset, 0)], Some(zero_account))`, where `zero_account` is the all-zero Stellar account address.
3. `process_withdraw` authorizes the caller, accepts `zero_account` because it is neither the controller nor pool, and converts amount `0` into a full withdrawal. [11](#0-10) 
4. The pool burns the account’s shares, debits cash, and transfers the full underlying amount to `zero_account`, permanently removing it from the caller’s control. [6](#0-5) [7](#0-6)

pub(crate) fn process_withdraw(
    env: &Env,
    caller: &Address,
    account_id: u64,
    withdrawals: &Vec<HubPayment>,
    to: Option<Address>,
) -> Vec<HubPayment> {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_payments(env, withdrawals, payments::ZeroLeg::MeansAll);

    let paid = settle_withdraw(env, &mut account, &recipient, &aggregated, &mut cache);
