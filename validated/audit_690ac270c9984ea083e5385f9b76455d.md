### Title
Attacker-controlled BEEFY consensus proof panics the runtime via `.expect()` in `Commitment`→`SpCommitment` conversion - ([File: evm/rust/src/conversions.rs])

### Summary
`ismp_abi`'s `From<Commitment> for SpCommitment` conversion (`evm/rust/src/conversions.rs:334-353`) unwraps attacker-controlled, ABI-decoded proof fields with bare `.expect(...)` calls instead of returning a typed error. This is the closest in-scope analog to the DeepFaceLab CVE's "deserialization of untrusted data drives unchecked processing": here, ABI-decoding an untrusted proof (deserialization) feeds directly into infallible-looking conversions that actually panic on adversarial input.

### Finding Description
`pallet_beefy_consensus_proofs::Pallet::verify_and_apply` (`modules/pallets/beefy-consensus-proofs/src/lib.rs:805-838`) is reachable from a signed, unprivileged `submit_proof` extrinsic. For `PROOF_TYPE_NAIVE`, it does:

```rust
let abi_proof = <ismp_abi::ecdsa_beefy::BeefyConsensusProof as SolType>::abi_decode_params(abi_payload)
    .map_err(|_| Error::<T>::AbiDecodeFailed)?;
let scale_proof: beefy_verifier_primitives::ConsensusMessage = abi_proof.into();
``` [1](#0-0) 

The `.into()` call chains through `From<BeefyConsensusProof> for ConsensusMessage` → `From<RelayChainProof> for MmrProof` → `From<Commitment> for SpCommitment`:

```rust
fn from(value: Commitment) -> Self {
    let mut iter = value.payload.into_iter();
    let first = iter.next().expect("commitment has at least one payload entry");
    ...
    block_number: value.blockNumber.try_into().expect("block number out of bounds"),
    validator_set_id: value.validatorSetId.try_into().expect("validator set id out of bounds"),
}
``` [2](#0-1) 

`Commitment.payload`, `blockNumber`, and `validatorSetId` are all ABI-decoded straight from the submitter-supplied `proof` bytes with no upstream bound check before this conversion runs. The same file also carries several sibling `.expect("... out of bounds")` calls (`Vote`→`SignatureWithAuthorityIndex`, `RelayChainProof`→`MmrProof`'s `leafIndex`, `IntermediateState`→`local::IntermediateState`'s `height`/`timestamp`) that are all reachable through the identical decode path. [3](#0-2) 

Because none of these fields are validated by the ABI type system (a Solidity `uint256`/dynamic array with zero elements, or a value exceeding `u32`/`u64` range, is perfectly valid ABI encoding), an attacker who is any signed relayer account can submit a `submit_proof(proof)` extrinsic whose ABI-encoded `Commitment.payload` is an empty array, or whose `blockNumber`/`validatorSetId` exceeds `u32`/`u64`, and trigger a Rust panic during `verify_and_apply`. This is functionally the same bug class as the CVE: untrusted, attacker-supplied serialized data is deserialized/converted without validating its structural invariants before it is trusted by downstream logic, and the failure mode is an unhandled fault instead of a typed error.

### Impact Explanation
A panic inside pallet dispatch, rather than a graceful `DispatchError`, is far more severe on a Substrate runtime than an ordinary "reverted extrinsic": it is caught by the executor as a runtime trap. Depending on how it surfaces (dispatch vs. block-import context), this can abort block execution/import for that block, and because `submit_proof` is a normal signed extrinsic anyone can resubmit, a hostile actor can repeatedly craft such proofs to disrupt BEEFY consensus-state updates on `pallet-beefy-consensus-proofs` — the pallet responsible for advancing the trusted BEEFY consensus state and unlocking new parachain state commitments for message delivery. A consensus client that cannot be advanced blocks delivery of any ISMP messages relying on it, i.e. "a route unable to deliver messages."

### Likelihood Explanation
Likelihood is limited by the difficulty of reliably reaching this exact conversion path deterministically without deeper testing of the `AbiDecodeFailed`/dedup checks around it, and it requires only crafting a syntactically valid but semantically-empty/over-range ABI payload — no cryptographic breakage is needed, mirroring the CVE's own "attack complexity high but exploit known/disclosed" characterization. It is reachable by any signed account (permissionless from a protocol-security standpoint) without needing to forge any signatures, since the panic happens before or independent of cryptographic verification.

### Recommendation
Replace every `.expect(...)`/`try_into().expect(...)` in `evm/rust/src/conversions.rs`'s `beefy` module with fallible conversions that propagate a typed decode error (mirroring the pattern already used elsewhere in the codebase, e.g. `beefy_verifier::error::Error::DecodeConsensusState`), specifically:
- `Commitment.payload.into_iter().next()` — return `Err` on an empty payload instead of `.expect(...)`.
- All `try_into().expect("... out of bounds")` calls on `blockNumber`, `validatorSetId`, `leafIndex`, `authorityIndex`, `stateMachineId`, `height`, `timestamp` — convert to `try_into().map_err(|_| Error::...)?`.
Thread these errors up through `From<...>` (converting the blanket `From` impls to `TryFrom`) so `verify_and_apply` surfaces `Error::<T>::AbiDecodeFailed` (or a new dedicated variant) instead of panicking.

### Proof of Concept
1. Craft `abi_payload` such that, after `abi_decode_params::<BeefyConsensusProof>`, `abi_proof.relay.signedCommitment.commitment.payload` is an empty dynamic array (valid ABI: length-prefix `0`), while other fields are well-formed enough to pass `AbiDecodeFailed`.
2. Prefix with `PROOF_TYPE_NAIVE` and submit via `pallet_beefy_consensus_proofs::submit_proof(proof)` from any signed account (`modules/pallets/beefy-consensus-proofs/src/lib.rs:805-838`).
3. `Self::verify_and_apply` calls `abi_proof.into()`, which runs `From<Commitment> for SpCommitment` (`evm/rust/src/conversions.rs:338-341`) and panics on `.expect("commitment has at least one payload entry")` instead of returning a `DispatchError`.
