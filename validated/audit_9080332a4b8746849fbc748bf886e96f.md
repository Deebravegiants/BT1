### Title
Webhook shop identity is unauthenticated (`shop-domain` header not covered by HMAC) allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity for an inbound webhook from the `X-Shopify-Shop-Domain` header, but the HMAC signature that authenticates the webhook only covers the raw request body, never the shop header. `Registry.process` validates the HMAC and then hands the unauthenticated `shop` value straight to the app's webhook handler, breaking the equality "shop authenticated by HMAC == shop the payload is processed for."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a field that is not part of the signable string at all: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` calls this validator, then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's registered handler: [4](#0-3) 

This is the same class of bug as the reported `accruePackageReward` issue: a value that is *acted upon* (tokens transferred / shop the webhook is processed for) is not the same value that was *verified* (rewards accrued / HMAC-signed bytes). Here, the equality that should hold is:

`shop_covered_by_hmac == shop_used_by_handler`

but in fact `shop_covered_by_hmac` doesn't exist — the HMAC signable string never includes `shop`, so any value can be placed in that header without invalidating the signature.

### Impact Explanation
Any actor who can obtain one legitimately Shopify-signed webhook body/HMAC pair (trivially achievable by installing the app on their own, attacker-controlled shop and triggering a webhook event) can replay that exact `raw_body` + `hmac-sha256` value to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will dispatch the handler with `shop: <victim shop>`. If the host application uses this `shop` value to select which merchant's session/data the webhook event applies to (the intended and documented use, per `WebhookMetadata`), this results in cross-tenant data confusion — writes, deletions, or state changes intended for the attacker's own shop get attributed to/executed against a different tenant. This satisfies the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who is able to install the app on their own developer store (a standard, unprivileged action for any Shopify app), capture one authentic webhook delivery, and replay it with a modified header — no access to `api_secret_key`, tokens, or privileged accounts is required.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the HMAC-signable representation, or independently verify that the shop header corresponds to a shop that is actually authorized/expected to send this event, before passing it to the handler. At minimum, document/require host applications to bind webhook processing to a shop that was already established via OAuth for that specific webhook subscription, not the raw header value.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger an event so Shopify sends a legitimately signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `client_secret`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same HTTP request to the app's webhook endpoint, only changing `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only, and it matches `H` → validation passes.
4. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and invokes the app's handler for `victim-shop.myshopify.com`, even though Shopify never signed anything for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
