### Title
Unrestricted `receive()` combined with unauthenticated `dispatch()` permanently exposes/locks ETH in `CallDispatcher` - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` implements an unguarded `receive() external payable {}` [1](#0-0)  with no `msg.sender` restriction, matching the exact bug pattern in the referenced UXD report. Unlike `UXDController`, `CallDispatcher` has no owner or any privileged recovery/withdraw function at all — the only way ETH ever leaves the contract is through the fully public, unauthenticated `dispatch()` function [2](#0-1) .

### Finding Description
`CallDispatcher.dispatch()` is `external` with no access-control modifier, and it forwards native value out of the contract's own balance to any `to` address supplied in the caller-provided `Call[]` array: [3](#0-2) 

Because `receive()` accepts ETH from any EOA or contract with no sender check [1](#0-0) , and `dispatch()` has no restriction on who may invoke it or where value is sent, any balance the contract holds (whether from a mistaken direct transfer, or from residual/dust ETH left behind after `IntentGatewayV2`'s intended sweep flow that funds the dispatcher before calling `dispatch()`) is a race: whoever calls `dispatch()` first can drain the entire native balance to an address of their choosing. This is worse than the original UXD finding — instead of merely being unrecoverable, misdirected/residual ETH sitting in `CallDispatcher` can be stolen by an unprivileged third party, or, if no one races it, remains permanently stuck since there is no owner-controlled sweep/withdraw function in the contract at all.

The gateway code (`IntentGatewayV2.sol`) documents that it expects to receive "swept balances from the CallDispatcher" [4](#0-3) , confirming that ETH is expected to transiently sit in `CallDispatcher` between being funded and being swept back — exactly the window during which the unauthenticated `dispatch()` can be front-run by any address.

### Impact Explanation
Any ETH transiently or mistakenly held by `CallDispatcher` — whether from direct erroneous transfers via the unguarded `receive()`, or from the intended sweep-back flow used by `IntentGatewayV2` — can either be permanently locked (no recovery path exists in the contract) or stolen by any unprivileged caller front-running the intended sweep via the unauthenticated `dispatch()`. This satisfies both the "permanent freezing of funds" and "concrete theft" criteria, since the contract's design provides no way for the legitimate owner/gateway to reliably reclaim value once it lands in `CallDispatcher`'s balance.

### Likelihood Explanation
`CallDispatcher` is a standalone, deployed utility contract (not access-restricted) that any EOA or contract can send ETH to and any EOA or contract can call `dispatch()` on directly (it has no `onlyOwner`/`onlyGateway` guard). Given `IntentGatewayV2`'s comment indicates ETH is expected to transiently reside there as part of normal sweeping operation, the window for exploitation/loss is a normal part of the protocol's operation, not a purely hypothetical edge case — making likelihood at least Medium.

### Recommendation
Restrict `dispatch()` to only be callable by the authorized gateway/owner contract (e.g. an `onlyOwner`/`onlyGateway` modifier), and/or restrict `receive()` to only accept ETH from the expected privileged caller (mirroring the report's suggested `require(msg.sender == weth, ...)` pattern, replaced with the appropriate authorized sender). Additionally, add an owner-only rescue/withdraw function so that any ETH that does land in the contract by mistake is not permanently unrecoverable.

### Proof of Concept
1. `IntentGatewayV2` (or any actor) sends ETH to `CallDispatcher` as part of normal operation, or a user mistakenly sends ETH directly to `CallDispatcher`'s address (accepted unconditionally by `receive()`).
2. Any external address calls `CallDispatcher.dispatch()` directly (no access control prevents this) with an encoded `Call[]` containing `{to: attacker, value: <CallDispatcher.balance>, data: ""}`.
3. `dispatch()` executes `to.call{value: call.value}(call.data)` [5](#0-4) , transferring the entire native balance to the attacker-controlled address, ahead of the legitimate gateway's own sweep-back call.
4. If no attacker races the call, the ETH remains stuck forever since `CallDispatcher` exposes no owner-only withdrawal function.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
