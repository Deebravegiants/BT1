Webhook shop-domain is trusted but not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but the HMAC signature that the gem validates only ever covers the raw request body. The tenant-identifying field (`shop`) is never bound to the signature, so any request carrying a valid `(body, hmac)` pair — regardless of who legitimately generated it — will be accepted for any `shop` value an attacker chooses to put in the header.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from unauthenticated headers with no cryptographic binding to the signature: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`, i.e. against the body only, since `Request` implements `VerifiableQuery` this way: [4](#0-3) 

`Registry.process` validates the HMAC and then dispatches the handler using the unverified `request.shop` value as the tenant identifier passed to the app's business logic: [5](#0-4) [6](#0-5) 

This is the exact bug class described in the report (a field acted on but not covered by the HMAC), reachable via this gem's own code path rather than host-application misuse: the equality the gem is supposed to enforce is `shop_bound_by_hmac == shop_used_for_dispatch`, but in reality `shop_bound_by_hmac = ∅` (nothing) while `shop_used_for_dispatch = request.shop` (attacker-controlled header). The two sides are never checked against each other.

### Impact Explanation
An unprivileged internet user who owns/controls one Shopify store can receive genuine webhooks from Shopify for their own store (body + valid HMAC, since it's a real webhook signed with the app's real secret for a real event on their own store). They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to name a victim shop. Because the signature check only covers the body, `HmacValidator.validate` still passes, and `Registry.process` calls the handler with `shop: <victim-shop>` and the attacker's body content. Any host application that trusts this `shop` field for looking up or mutating per-tenant state (the documented, intended use of `WebhookMetadata#shop`) will apply attacker-controlled webhook data to a different merchant's tenant context — a cross-tenant integrity violation reachable purely through this gem's verification logic.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker needs at least one valid `(body, hmac)` pair, which they can obtain legitimately by triggering any webhook event on a shop they control (installing the app on their own dev/test store is sufficient, no privileged credentials of the target needed). No knowledge of `api_secret_key` is required — only replay/header substitution. The victim `shop` value is a free-form string not checked against any registry of installed shops before dispatch.

### Recommendation
Include the shop-identifying header(s) (at minimum `shop-domain`, ideally also `topic`/`webhook_id`) in the HMAC-signed content, or otherwise cryptographically bind the header-derived tenant identity to the signature verification (e.g., compute the signature over a canonical string of `headers + body` rather than body alone). At minimum, document that host applications must independently correlate `WebhookMetadata#shop` against session/tenant records they already trust before acting on it — but the safer fix is inside `Request#to_signable_string` in this gem.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and triggers any webhook (e.g. orders/create). Shopify sends:
#      headers: { "x-shopify-shop-domain" => "attacker.myshopify.com",
#                 "x-shopify-hmac-sha256" => VALID_HMAC_FOR_BODY,
#                 "x-shopify-topic" => "orders/create" }
#      body: RAW_BODY

# 2. Attacker captures (RAW_BODY, VALID_HMAC_FOR_BODY) from their own inbox/proxy.

# 3. Attacker replays to the same app endpoint, only changing the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => VALID_HMAC_FOR_BODY,   # unchanged, still verifies
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: RAW_BODY, headers: headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true, because it only checks
#    HMAC(secret, RAW_BODY) == VALID_HMAC_FOR_BODY — the shop header is irrelevant.
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
#    The host app now processes attacker-controlled webhook data as if it belongs
#    to "victim-shop.myshopify.com".
```
