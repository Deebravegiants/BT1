Based on the investigation, the strongest analog to the Uniswap TWAP "unverified-field-used" bug class in this repository is a genuine identity-binding gap in the webhook HMAC verification.

### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Registry.process` dispatches the webhook to the app's handler using the unauthenticated `shop`, `topic`, and `webhook_id` HTTP headers. Any actor who can obtain one valid `(body, hmac)` pair — trivially available to anyone who installs the app on their own store — can replay that exact body and signature to the app's public webhook endpoint while substituting a different shop domain in the header, and the signature check still passes.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only `@raw_body`: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e. only the body) and then dispatches to the app's handler using the unauthenticated `shop`/`topic`/`webhook_id` values: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(body) == true` is treated by the library as proof that `(shop, topic, webhook_id, body)` as a whole is authentic, when in fact only `body` is authenticated. Formally, the equality the code implicitly relies on is:
`HMAC_valid(raw_body) ⟺ shop_header is authentic for raw_body`
but the actual guarantee provided is only `HMAC_valid(raw_body) ⟺ raw_body was produced by Shopify for *some* shop`, with no guarantee that `shop_header` matches the shop that produced `raw_body`.

### Impact Explanation
Any user can install the target app on their own (even free/development) Shopify store, which is not a "privileged account" or a leaked credential — it is the same level of access any internet user can obtain. Shopify will deliver that user legitimate, correctly-signed webhooks containing a real `(raw_body, hmac)` pair for their own shop. Because the signature check ignores the `shop`, `topic`, and `webhook_id` headers, the attacker can POST that exact captured body and signature directly to the app's public webhook endpoint while overriding the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to point at a victim shop that also has the app installed. `HmacValidator.validate` still returns `true`, and `Registry.process` invokes the handler believing the data belongs to the victim shop. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g. to select which merchant's records to update, cancel orders for, or grant entitlements to), this enables cross-tenant data injection/confusion — the Critical-class impact of "cross-tenant access" defined in scope.

### Likelihood Explanation
Likelihood is high for any app that processes multiple shops with shared webhook handler logic keyed off `WebhookMetadata#shop`: no secret material is required, only a standard app install (obtainable by anyone) plus the ability to POST arbitrary headers/bodies to the app's public webhook route — both trivially available to an unprivileged internet user.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-protected signable string for webhook requests, or otherwise cryptographically bind these header values to the verified body (e.g., have the HmacValidator's signable payload include the concatenation of the canonicalized headers and body, matching what Shopify actually signs, and reject any request where recomputing the signature over headers+body fails). At minimum, document that `Request#shop`/`#topic`/`#webhook_id` are not authenticated by `HmacValidator.validate` and must not be trusted for authorization decisions without additional binding by the host application.

### Proof of Concept
1. Attacker creates a free development store and installs the target Shopify app; the app registers a webhook (e.g. `orders/create`) using this gem.
2. Shopify delivers a legitimate webhook POST to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and some JSON `raw_body`.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new POST directly to the app's public webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — this succeeds because the body is unchanged.
6. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, causing the app to process attacker-controlled order data as if it belongs to `victim-shop`.
