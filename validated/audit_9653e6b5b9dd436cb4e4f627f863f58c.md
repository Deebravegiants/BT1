Audit Report

## Title
Data race on `authorizedKeys` map allows unsynchronized authorization check in `WorkflowMetadataHandler.Authorize` - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` reads the shared `h.authorizedKeys` map without holding `h.mu`, while `syncMetadata` reassigns the entire map under `h.mu.Lock()` on a periodic background ticker. This is an unsynchronized concurrent map access, which is undefined behavior in Go and can cause a runtime panic (`fatal error: concurrent map read and map write`) that crashes the gateway process, and in the worst case theoretically an inconsistent read during authorization.

## Finding Description
`Authorize` reads `h.authorizedKeys[workflowID]` directly at line 92 with no lock: [1](#0-0) . Meanwhile, `syncMetadata` fully replaces `h.authorizedKeys` under `h.mu.Lock()`/`Unlock()`: [2](#0-1) . All other accessors of the protected fields (`WorkflowShards`, `GetWorkflowID`, `GetWorkflowReference`) correctly take `h.mu.RLock()`: [3](#0-2) [4](#0-3) . `syncMetadata` is scheduled on a periodic ticker started in `Start`: [5](#0-4) , and `Authorize` is invoked from `httpTriggerHandler.authorizeRequest` on every incoming HTTP trigger request, which is reachable by any client able to submit a trigger request through the `MethodWorkflowExecute` gateway method. This is an inconsistency between the lock discipline used for writes (protected) and this particular unprotected read, and it is a genuine, structural bug in the code as written.

## Impact Explanation
Concurrent unsynchronized access to a Go map is undefined behavior. When a read races with a write (as here, `Authorize`'s unlocked read vs. `syncMetadata`'s locked write), the Go runtime's built-in race detection in the map implementation can trigger `fatal error: concurrent map read and map write`, which crashes the entire gateway process — a real, concrete denial-of-service impact reachable by any client sending trigger requests during a metadata sync cycle. This falls within an in-scope DoS/service-crash impact category. The claim's assertion of a possible "false negative/positive on signer membership" from a torn read is speculative and not concretely demonstrated, but the panic/crash impact alone is a legitimate and concrete finding.

## Likelihood Explanation
The race window recurs on every `MetadataAggregationIntervalMs` tick of the background sync loop, and `Authorize` is exercised on every incoming HTTP trigger request from any unprivileged client that can reach the gateway and possesses a JWT-signed request for a registered workflow (note: this does still require a validly signed JWT to reach the map-read code path, since `VerifyRequestJWT` and JTI replay checks precede the map read — but the crash can still occur since these checks happen before the unsynchronized read, and a client only needs to be one of the workflow's legitimately configured signers, or simply cause enough concurrent requests during a sync window with any valid JWT). Given production configurations run this sync ticker frequently and process trigger traffic continuously, the race window is realistically exercised, and Go's map read/write race detection makes a fatal crash a plausible outcome under load, especially in busy/high-throughput gateway deployments.

## Recommendation
Acquire `h.mu.RLock()`/`h.mu.RUnlock()` around the `h.authorizedKeys[workflowID]` lookup (and the subsequent `keys[key]` membership check) in `Authorize`, matching the locking discipline used by `GetWorkflowID`, `GetWorkflowReference`, and `WorkflowShards`, to eliminate the unsynchronized map access.

## Proof of Concept
Run `go test -race` against a test that: (1) starts a goroutine calling `syncMetadata(ctx)` in a tight loop (or drives it via the ticker with a very short `MetadataAggregationIntervalMs`), while (2) concurrently calling `Authorize(workflowID, validJWT, req)` in a loop from other goroutines for a registered `workflowID`. The Go race detector will report a data race between the unlocked read at `workflow_metadata_handler.go:92` and the locked write at `workflow_metadata_handler.go:178`, and under sufficient load this can also manifest as a `fatal error: concurrent map read and map write` runtime crash.

		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),

	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
