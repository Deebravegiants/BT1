### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-header spoofing to attribute a webhook to the wrong tenant - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable payload from the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and used unchecked by `ShopifyAPI::Webhooks::Registry.process` to route and tag the webhook, including the tenant-identifying `shop` value passed into `WebhookMetadata`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it authenticates the body bytes but nothing else: [3](#0-2) 

`Registry.process` validates HMAC and then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build `WebhookMetadata`, which is handed to the app's handler as the tenant/event identity: [4](#0-3) 

The identity binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` implies `shop header == shop that produced signed_bytes`. Here `signed_bytes = raw_body` only, so the equality that actually holds is `HMAC(secret, raw_body) == received_hmac`, which says nothing about which shop the body came from. Any request whose body was legitimately HMAC-signed by the app's secret for *any* shop (e.g. the attacker's own installed test store) can be replayed to the app's webhook endpoint with an arbitrary `shop-domain`/`x-shopify-shop-domain` header value, and it will pass validation and be dispatched to the handler tagged with the attacker-chosen shop.

### Impact Explanation
This breaks the tenant-identity binding (shop) that webhook consumers rely on to know which merchant a payload belongs to. An attacker who controls a legitimate installation (their own dev/test store using the same app) can generate genuinely-signed webhook bodies (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or any subscribed topic) and replay them at the app's public webhook endpoint while spoofing the `shop-domain` header to point at a victim shop. Because the gem's `process` method uses this unauthenticated header to key `WebhookMetadata.shop`, the receiving application can be tricked into applying attacker-originated events/data against a different merchant's records — a cross-tenant integrity violation.

### Likelihood Explanation
Exploitation requires no secrets beyond what any app-installing merchant already has (their own store, and the ability to trigger/capture a webhook with a valid HMAC for their own shop) and a directly reachable webhook endpoint, which is the gem's expected deployment model. No `api_secret_key`, access token, or privileged account is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the HMAC-signable string, or otherwise cryptographically bind the shop identity to the payload before `Registry.process` propagates it to the handler, so validation proves both body integrity and the shop attribution together.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and captures a legitimate webhook delivery for topic `customers/redact`, including its raw body and valid `x-shopify-hmac-sha256` header (computed over that body with the app's secret).
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, raw_body)`, per [3](#0-2) .
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the spoofed shop header, per [5](#0-4) , so the app's handler executes attacker-controlled data-processing logic as if it originated from `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
