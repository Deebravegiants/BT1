Confirmed: `pallet_assets::Config::CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId32>>` — any signed account can permissionlessly create a `pallet-assets` asset and set its own metadata (`decimals`) via `pallet-assets::set_metadata`, which is callable by the asset's owner (no `ForceOrigin`/root needed). `CreateOrigin` for `register_token` in `pallet-hyper-fungible-token` is `EnsureRoot`, so registration itself is governance-gated, but the decimals value it snapshots is never re-checked afterward.

### Title
Stale decimals-bound check lets a token owner desync `Precisions` from live `Assets` decimals, corrupting cross-chain amount scaling - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`register_token` validates `config.decimals >= local_decimals` exactly once, at registration time, using the `local_asset`'s decimals read from `pallet-assets` at that moment `<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(...)`. But `send`, `on_accept`, and `on_timeout` all re-fetch `local_decimals` live and combine it with the pinned `Precisions` (`erc_decimals`) value on every call, exactly like the reported `RioLRTAssetRegistry::_addAsset` bug where a bound was checked once on write but the underlying assumption (decimals staying within a safe range relative to another value) was never re-verified against a value that can drift later.

### Finding Description
`register_token` (`modules/pallets/hyper-fungible-token/src/lib.rs:330-368`) checks:
```rust
ensure!(config.decimals >= local_decimals, Error::<T>::ErcDecimalsBelowLocal);
``` [1](#0-0) 

`local_decimals` is read from `pallet-assets` metadata for `registration.local_id` at registration time, and `config.decimals` (the EVM-side decimals) is then pinned into `Precisions` forever. [2](#0-1) 

However `pallet-assets` in this runtime uses `CreateOrigin = AsEnsureOriginWithArg<EnsureSigned<AccountId32>>`, meaning any signed, unprivileged account can create the asset that later gets bridged, and — as the owner/issuer of that asset — can call `pallet-assets::set_metadata` to change its `decimals` at will, at any point after `register_token` runs. [3](#0-2) 

Every subsequent `send`, `on_accept`, and `on_timeout` call re-reads `local_decimals` fresh from the mutable `pallet-assets` metadata and feeds it, together with the immutable `Precisions` value, straight into `convert_to_erc20` / `convert_to_balance`:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
``` [4](#0-3) 
```rust
let decimals = <T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(params.asset_id.clone());
...
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
``` [5](#0-4) 

Because `saturating_sub` clamps to zero, if the asset owner later raises `local_decimals` above the pinned `erc_decimals`, the exponent silently collapses to `0` instead of reverting or scaling down — the outbound `send` (burn-and-message) stops scaling up at all, sending the *raw* local-denomination integer as if it were already in EVM decimals. The symmetric `convert_to_balance` used by `on_accept`/`on_timeout` divides by the same clamped power of ten, so an inbound message minted against a since-inflated `local_decimals` mints far more (or, in the opposite direction, an owner lowering decimals causes far less) local balance than the burn/escrow on the other side actually backs. [6](#0-5) [7](#0-6) 

This is the same bug class as the reported `RioLRTAssetRegistry::_addAsset` issue: a decimals-consistency invariant is enforced only at the moment a config entry is written, on a value sourced from a party who is not the invariant's guardian, and never re-validated before the value is used in scaling math that directly determines minted/released amounts.

### Impact Explanation
An asset owner (any signed, non-privileged account that created the bridged asset via `pallet-assets`) can, after root approves `register_token` once, unilaterally change `decimals` on their own asset to desynchronize it from the pinned `Precisions` entry. This breaks the amount-conversion invariant that `register_token` was designed to guarantee, and can:
- Cause `send` to under-scale the outbound ERC-20 amount (mint fewer/very few tokens on the EVM side for a given burn), permanently trapping value, or
- Cause `on_accept`/`on_timeout` to over-mint local balance relative to what was actually escrowed/burned on the EVM side, allowing unbacked minting of the local asset — a direct fabrication of value that other pallet users (holders of the same asset) would be diluted against.

This reaches "unbacked mint" / "permanent freezing of funds" territory depending on direction of the decimals drift, matching the required severity bar.

### Likelihood Explanation
Medium-High: exploitation requires only (1) getting an asset registered once via `register_token` (a one-time governance action any team wanting to list their token would legitimately request) and (2) later calling the ordinary, permissionless `pallet-assets::set_metadata` extrinsic as the asset's owner — no consensus/proof forgery, no governance compromise, and no special privilege beyond owning the asset that was bridged.

### Recommendation
Do not trust live `pallet-assets` metadata decimals for scaling math after registration. Snapshot `local_decimals` into `Precisions` (or a parallel storage item) at `register_token` time and use the pinned value in `send`/`on_accept`/`on_timeout`, or re-validate `config.decimals >= local_decimals` (and reject/rescale) on every use rather than only at registration. Alternatively, freeze the asset's metadata (`pallet-assets::Mutate::freeze_metadata` or an owner-transfer to a non-signer) as part of `register_token` so decimals cannot drift after being pinned.

### Proof of Concept
1. Alice (unprivileged) creates asset `X` via `pallet-assets::create` and sets `decimals = 6` via `set_metadata`.
2. Governance calls `register_token` for asset `X` with `chains: { Evm(1): { decimals: 18, ... } }`. This passes because `18 >= 6`. `Precisions[X, Evm(1)] = 18` is pinned.
3. Alice calls `pallet-assets::set_metadata` again, raising `X`'s `decimals` to `20`.
4. Alice calls `send(asset_id: X, amount: 1_000 * 10^20, destination: Evm(1), ...)`. `convert_to_erc20(amount, erc_decimals=18, local_decimals=20)` computes `10u128.pow(18u8.saturating_sub(20) as u32) == 10^0 == 1`, so `erc20_amount = amount` unscaled — instead of dividing by `10^2` to normalize to 18-decimal EVM units, the raw 20-decimal integer is sent as the 18-decimal ERC-20 `Message.amount`, minting on the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract 100x more tokens than the value actually burned/escrowed on the substrate side.
