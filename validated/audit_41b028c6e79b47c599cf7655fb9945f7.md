### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop` (and `topic`) values used to route and attribute the webhook come from unauthenticated HTTP headers. `Registry.process` validates the HMAC but then hands the *unverified* `shop` header value straight to the app's handler via `WebhookMetadata`, breaking the binding `shop authenticated == shop acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, and once that check passes, it forwards `request.shop` unchanged into `WebhookMetadata`, which the app's `WebhookHandler#handle` uses to decide which tenant/merchant the event belongs to: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., strictly the body bytes, never the shop header: [4](#0-3) 

`WebhookMetadata` is a plain struct that simply carries whatever `shop` string it was given, with no additional authentication: [5](#0-4) 

The `api_secret_key` used to compute/verify the HMAC is a single per-app secret shared across every merchant/shop that installs the app — it is not shop-specific. Consequently, anyone who can obtain one genuine `(body, hmac)` pair for the app (e.g., by installing the app on their own development/test shop and capturing one of its real webhook deliveries) possesses a signature that is valid for that exact body under the app's secret, **regardless of which shop domain header accompanies it**. That attacker can replay the identical `raw_body` + `hmac-sha256` header to the merchant's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim shop's domain, or any string), and `Registry.process` will accept it as HMAC-valid and dispatch it to the handler labeled with the attacker-chosen `shop`.

This is exactly the class of bug flagged by the external report — an important security invariant ("the shop this event is attributed to" ) is not cryptographically enforced, only assumed/documented via the `shop-domain` header, which is trivially attacker-controlled and outside the HMAC's coverage.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` as the tenant/session key to look up a merchant's stored access token, update per-shop state, or make decisions (a very common and Shopify-documented pattern for multi-tenant apps), an attacker can inject a "genuine-looking" (valid-HMAC) webhook that is falsely attributed to a different shop than the one that actually produced it. This enables cross-tenant data confusion/injection — e.g., forcing processing of attacker-controlled body content under a victim shop's identity, or triggering shop-scoped side effects (order/inventory updates, uninstall/GDPR handling, etc.) against a tenant that never sent that event. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Low-to-Medium: it requires the attacker to obtain at least one legitimate `(raw_body, hmac)` pair from the same app (trivial for any developer who installs their own test/dev shop with the target app, since `api_secret_key` is shared across all installs of the app) and to be able to send an HTTP request directly to the app's public webhook endpoint with custom headers — no privileged credentials, access tokens, or `api_secret_key` are needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed payload check, or otherwise cryptographically bind the `shop` header to the verified body — e.g., verify the shop domain against an expected/whitelisted value from the app's install records before trusting `WebhookMetadata#shop`, or extend `to_signable_string`/`HmacValidator` to incorporate the shop header, and document/enforce that `Registry.process` must not treat the `shop-domain` header as authenticated on its own.

### Proof of Concept
1. App developer installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they control) and captures a real webhook delivery: raw body `B` and its valid `x-shopify-hmac-sha256` header `H`, both signed with the app's single, shared `api_secret_key`.
2. Attacker sends a forged HTTP POST to the merchant-facing webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid because only `B` is signed)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (arbitrary)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, secret) == H`, per [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, per [7](#0-6) , even though the payload never originated from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
