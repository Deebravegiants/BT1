### Title
Relayer fee ledger (`pallet-ismp-relayer::Fees`) is disbursed from a shared `RELAYER_FEE_ACCOUNT` pot with no reservation, and the withdrawal POST is dispatched with `timeout: 0`, so a relayer's zeroed claim can permanently fail to settle - (File: `modules/pallets/relayer/src/withdrawal.rs`, `modules/pallets/ismp/src/dispatcher.rs`)

### Summary
This mirrors the Olympus TRSRY finding: a module computes "capacity" (here, a relayer's withdrawable fee amount) from an internal ledger that is never reconciled against the actual token balance of the account that must fund the payout.

### Finding Description
Relayer fees are collected into a shared, non-earmarked pot: every `dispatch_request` call transfers `fee.fee` from the payer into `RELAYER_FEE_ACCOUNT` with no per-request reservation [1](#0-0) . The same account is later drawn down by two independent, uncoordinated paths:

1. Timeout refunds pull directly from `RELAYER_FEE_ACCOUNT` back to the original payer [2](#0-1) .
2. Relayer fee withdrawals pull from `RELAYER_FEE_ACCOUNT` to the relayer's beneficiary [3](#0-2) .

Meanwhile, the authoritative "how much does the protocol owe this relayer" figure lives entirely on Hyperbridge in `pallet-ismp-relayer::Fees`, populated purely by verifying state proofs of the original request/delivery — it never inspects the actual token balance sitting in `RELAYER_FEE_ACCOUNT` on the destination/source chain [4](#0-3) . This is structurally identical to Olympus's `TRSRY.getReserveBalance` computing withdrawal capacity from a ledger while `TRANSFER_FAILED` occurred because the actual token balance had already been drawn down elsewhere.

Compounding this, `Pallet::withdraw` unconditionally zeroes the relayer's `Fees` entry in the same extrinsic that merely *dispatches* the withdrawal POST — before the message is ever delivered — and dispatches it with `timeout: 0` (no expiry) [5](#0-4) . If `RELAYER_FEE_ACCOUNT`'s actual balance on the destination chain is insufficient when `HyperbridgeWithdrawalModule::on_accept` executes `T::Currency::transfer(..., Preservation::Expendable)`, the transfer errors out [3](#0-2) . Because the request never times out (`timeout: 0`), there is no automatic refund/retry path, and the relayer's claim (already zeroed on Hyperbridge) is unrecoverable.

### Impact Explanation
This is a permanent-freezing-of-funds / undeliverable-message class bug: a relayer that has correctly delivered messages and proven that delivery loses its earned fee entirely if the destination chain's pooled `RELAYER_FEE_ACCOUNT` balance ever falls short of what Hyperbridge's ledger believes is owed — with no way to retry since the dispatched withdrawal request cannot time out. This directly matches the "route unable to deliver messages" / "permanent freezing of funds" acceptance criteria.

### Likelihood Explanation
`RELAYER_FEE_ACCOUNT` is a shared pot drawn by both timeout refunds and relayer-fee withdrawals with no accounting reconciliation between them and the state-proof-derived `Fees` ledger on Hyperbridge. Any divergence between "fees provably paid for delivered messages" (tracked on Hyperbridge) and "fees still physically present in the pooled account" (on the settling chain) — which can arise from ordinary concurrent activity (timeouts, multiple in-flight dispatches, replayed accumulation across chains) — triggers the failure. No malicious actor or privileged role is required; it can occur from unprivileged relayers/users interacting with the normal dispatch/timeout/withdraw flow.

### Recommendation
Reserve/earmark relayer fee amounts at dispatch time instead of pooling into a shared account, or have `withdraw()` verify the destination chain's actual `RELAYER_FEE_ACCOUNT` balance (via a state proof) before zeroing `Fees`. Alternatively, give the `WithdrawRelayerFees` POST a non-zero timeout and only zero `Fees` once delivery is confirmed (or refund it back into `Fees` on timeout/failure), so a temporary balance shortfall cannot permanently destroy the relayer's claim.

### Proof of Concept
Analog derived from code inspection (no reproducible harness available in this index): (1) chain A dispatches several fee-bearing requests, pooling fees into `RELAYER_FEE_ACCOUNT`; (2) some of those requests time out, refunding their fee back out of `RELAYER_FEE_ACCOUNT` to the payers [2](#0-1) ; (3) a relayer that delivered a different, non-timed-out request accumulates a claim in `pallet-ismp-relayer::Fees` on Hyperbridge and calls `withdraw()`, which zeroes the claim and dispatches a `timeout: 0` POST [5](#0-4) ; (4) if `RELAYER_FEE_ACCOUNT`'s remaining balance on the settling chain is now below the claimed amount, `HyperbridgeWithdrawalModule::on_accept`'s `T::Currency::transfer` fails [3](#0-2) , and since the request has no timeout, the relayer's already-zeroed claim can never be recovered.
