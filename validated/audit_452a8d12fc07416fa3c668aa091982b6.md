### Title
Intent order withdrawal and dust-sweep on Tron IntentGatewayV2 don't check the ERC20 `transfer` return value, allowing silent-failure tokens to be marked as paid while funds remain locked - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` uses `SafeERC20`/`safeTransferFrom` consistently when *pulling* tokens into escrow (`placeOrder`), but switches to a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` when *paying out* escrowed funds in `withdraw()` and in the `SweepDust` handler inside `onAccept`. Only the low-level call's `success` boolean is checked; the ABI-encoded boolean return value of `transfer()` is never decoded or validated.

### Finding Description
In `withdraw()`, escrowed input tokens and transaction fees are released to the beneficiary/solver via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

and the fee payout: [2](#0-1) 

The same pattern appears in the `SweepDust` request handler: [3](#0-2) 

A low-level `.call()` only reports `success = true` when the callee doesn't revert; it does not verify the returned `bool` payload. ERC20 tokens that follow the "return false on failure" pattern instead of reverting (a known non-standard-but-common behavior, e.g., some legacy or non-compliant tokens) would cause `success` to be `true` even though no tokens were actually moved. Since this function is reached from `onAccept`, triggered by a relayed `RedeemEscrow`/`RefundEscrow` ISMP message (i.e., any relayer submitting a valid cross-chain proof) and from `onGetResponse`, the escrow accounting (`_orders[commitment][token] -= amount`, deletion of `TRANSACTION_FEES`) is unconditionally decremented/finalized as though the transfer succeeded, and the order is marked filled/refunded (`_filled[body.commitment] = beneficiary`), even when the token transfer silently failed.

This is inconsistent with the escrow crediting side of the same contract, which correctly uses `SafeERC20.safeTransferFrom` throughout `placeOrder`, and with the non-Tron `IntentGatewayV2.sol`/`IntentsBase.sol` counterparts, which use `IERC20(...).safeTransfer(...)`.

### Impact Explanation
If the input or fee token used in an order is a non-reverting-on-failure ERC20, a call to `withdraw()` (triggered by relayer-delivered `RedeemEscrow`/`RefundEscrow` messages or `onGetResponse`) can complete successfully, mark the order filled/refunded, and zero out escrow accounting without the beneficiary ever receiving the tokens. The tokens remain stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them (since `_orders[...]` was already decremented and the order marked filled), resulting in permanent loss of user/solver funds. The `SweepDust` protocol path has the same flaw for dust-collection payouts to arbitrary beneficiaries.

### Likelihood Explanation
Likelihood is contingent on a source-chain input or fee token being a non-standard ERC20 that returns `false` instead of reverting on failure (e.g., due to blacklist, paused state, or insufficient balance checks implemented via return-false rather than revert). Since token selection for `order.inputs`/fee token is effectively controlled by whoever places an order (subject to any allowlisting) and the delivery path is reachable by any relayer submitting a valid cross-chain proof, this is a realistic Medium-severity path once such a token is in scope, matching the original audit finding's classification.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer(IERC20(token), beneficiary, amount)`, consistent with the rest of the file's `safeTransferFrom` usage and with the non-Tron `IntentsBase.sol`/`IntentGatewayV2.sol` implementations, so that non-standard/silently-failing tokens correctly revert the whole transaction instead of finalizing escrow state.

### Proof of Concept
1. Deploy (or use) an ERC20 token whose `transfer()` returns `false` on failure instead of reverting (e.g., paused/blacklisted transfer attempt returns `false`).
2. A user places a cross-chain order on the source chain using this token as an input, and it gets escrowed in `IntentGatewayV2` (Tron).
3. A solver fills the order on the destination chain; the source-chain `IntentGatewayV2.onAccept` is invoked via a relayed `RedeemEscrow` message, calling `withdraw(body, false)`.
4. Suppose the token transfer to `beneficiary` fails silently by returning `false` (e.g., beneficiary is momentarily blacklisted, or a supply-cap/allowance-like internal check returns false rather than reverting) — `token.call(...)` still returns `success = true` because the call itself didn't revert.
5. `withdraw()` proceeds: `_orders[body.commitment][token] -= amount;` zeroes escrow accounting and emits `EscrowReleased`, but the beneficiary's balance never changed — the tokens are stuck in the contract with no remaining path to recover them. [4](#0-3)
