### Title
Division-by-zero panic in `Zap._executeBuy`'s fee-proration when `mint` yields `ltMinted == 0` - ([File: packages/contracts/src/Zap.sol])

### Summary
CVE-2019-20051 is a floating-point exception (division/modulo by zero) in UPX's `elf_hash`, crashing the tool whenever a hash table size derived from attacker-influenced input is zero. The Solidity analog is an unguarded integer division whose denominator is derived from an external, live-priced input that can legitimately go to zero, causing every call on that path to revert with an EVM arithmetic panic (`0x12`).

### Finding Description
In `Zap._executeBuy` (curve, pre-graduation branch), the LT actually minted is used as a divisor with no zero-check: [1](#0-0) [2](#0-1) 

```
$.usdc.forceApprove(lt, baseToConvert);
ltMinted = IBounceLeveragedToken(lt).mint(address(this), baseToConvert, 0);
(tokensOut, amountInUsed) = _buyOnCurve(tokenAddress, lt, ltMinted);
...
uint256 effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted;
```

`ltMinted` is the LT amount returned by the external `IBounceLeveragedToken.mint`, computed on BounceTech's side as `baseToLtAmount(baseAmount) = baseAmount * 1e18 / exchangeRate()` (mirrored by the project's own `IBounceLeveragedToken.baseToLtAmount` docstring: [3](#0-2) ). `exchangeRate()` is the live, ever-drifting USDC-per-LT price of an external rebasing leveraged token with no cap enforced anywhere post-launch — `Bonding._deployAndSeed` only rejects `exchangeRate == 0` and a too-*low* rate at launch time, never bounds how high the rate can drift afterward: [4](#0-3) .

If `exchangeRate()` ever grows large enough that `baseToLtAmount(baseToConvert)` rounds down to `0` for the smallest `baseToConvert` the flow can produce (the `minUsdcAmount()`-floored buy, forced by the floor-bump branch a few lines above), `mint` returns `ltMinted == 0`, and the division `(amountInUsed * baseToConvert) / ltMinted` reverts with a division-by-zero panic. Because `baseToConvert` is bottomed out at `minUsdcAmount()` specifically to satisfy BounceTech's own mint floor (`BelowMinTransactionSize`), there is no smaller buy size Zap can fall back to — every subsequent `Zap.buy`/`createToken` call for that token on the curve reverts identically, permanently.

### Impact Explanation
This is a permanent denial-of-service on the buy side of a bonding-curve token once the underlying LT's exchange rate drifts past the critical threshold: no trader can buy through `Zap` again (the curve can never reach graduation via the USD leg through further buys, and new buyers/creators cannot enter). Funds already staged on the curve are not directly stolen, but the buy path is bricked — a permanent freezing of the token's future tradability, matching the "permanent freezing of trader funds" acceptance criterion. This mirrors the CVE's DoS class: an unguarded division whose denominator is externally influenced collapses to zero and crashes the operation.

### Likelihood Explanation
Reachability is unprivileged — any trader calling `Zap.buy`/`createToken` on a curve-stage token triggers `_executeBuy`. However, the trigger condition (`exchangeRate()` growing large enough that `minUsdcAmount()` worth of USDC mints `0` LT) requires an extreme, long-horizon price drift on a leveraged reserve asset. This is architecturally *possible* (no ceiling exists on `exchangeRate()` post-launch, and the protocol explicitly supports leveraged/compounding LTs), but is not attacker-triggerable in a single transaction — it depends on organic (or leverage-compounded) price movement over time, making exploitation likelihood low-to-moderate rather than immediate.

### Recommendation
Guard the division in `Zap._executeBuy`: check `if (ltMinted == 0) revert ...` immediately after the `mint` call (mirroring the existing `exchangeRate == 0` guard pattern in `Bonding._deployAndSeed`), and treat a zero-mint result as equivalent to "amount below floor" so the transaction fails with a clear, decodable error rather than an EVM arithmetic panic. Consider also whether `previewBuy`/`previewLtUntilGraduation` should surface this degenerate state so front-ends can detect and block trading before it becomes unrecoverable.

### Proof of Concept
1. Launch a token against a BounceTech LT via `Bonding.launch`/`Zap.createToken`.
2. Let (or, in a controlled test environment, force via a mock LT) `exchangeRate()` drift/appreciate until `baseToLtAmount(minUsdcAmount())` rounds to `0` (i.e., `exchangeRate() > minUsdcAmount() * 1e18`).
3. Call `Zap.buy(tokenAddress, minUsdcAmount(), ...)` (or any buy that lands in the floor-bump branch of `_executeBuy`).
4. `IBounceLeveragedToken(lt).mint(...)` returns `ltMinted == 0`.
5. Execution reaches `effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted;` and reverts with an EVM division-by-zero panic (`Panic(0x12)`), bricking all further buys on that token via `Zap`.
