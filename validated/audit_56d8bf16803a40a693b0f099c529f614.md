### Title
Zone-B GetSecrets restriction can be bypassed via stale cached DON zone membership after a transient capabilities-registry lookup failure - (File: core/capabilities/vault/zone_b_restriction.go)

### Summary
`zoneBRestrictor.isZoneBWorkflowDON` resolves whether a calling workflow DON belongs to the restricted `zone-b` family by querying the in-process capabilities registry, and caches the last successfully-resolved result per `WorkflowDonID`. If the registry lookup transiently fails, the code falls back to the cached value rather than failing closed for DONs that have a cached entry. If a DON's family membership changes to `zone-b` *after* a non-`zone-b` result was cached, and the registry lookup subsequently fails (a normal, un-attacker-controlled operational event), the security check silently returns `isZoneB = false` and the owner-allowlist restriction is skipped entirely, allowing that DON's `GetSecrets` calls to read vault secrets outside the allowlist.

### Finding Description
`enforce` is the sole gate that restricts `GetSecrets` reads originating from a `zone-b` workflow DON to an allowlist of workflow owners: [1](#0-0) 

The zone determination is delegated to `isZoneBWorkflowDON`, which caches results and, on registry error, returns the previously cached membership instead of failing closed: [2](#0-1) 

The comment explicitly documents the fallback rationale ("only a never-before-resolved DON fails closed"), which is a deliberate availability trade-off but creates a **stale-security-state** window: the cache is populated as `false` (not zone-b) the first time the DON is resolved, and there is no invalidation path tied to actual DON family changes on-chain/in-registry — only a fresh successful lookup overwrites it. This is structurally the same bug class as the reported Vault.vy issue: a security/financial decision is made using a value (`minimumCollateralization` / `isZoneB`) that is expected to be static but can change out-of-band, and the code has no mechanism to detect the staleness and safely halt instead of proceeding with the outdated value.

### Impact Explanation
If exploited (via the natural combination of a DON's family reassignment to `zone-b` and a transient capabilities-registry error, e.g., during a metadata sync/update window), the restriction that vault secrets read by `zone-b` DONs must be limited to an owner allowlist is silently bypassed. This results in unauthorized disclosure of encrypted vault secrets for owners not on the `VaultZoneBGetSecretsAllowed` allowlist to a DON that should be restricted — a concrete secret-disclosure impact, matching the "key/secret disclosure" acceptance criterion.

### Likelihood Explanation
The trigger does not require a malicious actor to forge any credentials; it only requires (a) an operational DON re-classification into `zone-b` and (b) a transient registry read error (explicitly acknowledged in code comments as occurring, e.g., "not yet synced after startup, or nil mid-update"). Both conditions are realistic, non-adversarial operational events, similar in nature to the referenced report's "TVL changes over time" precondition — not an attacker-crafted exploit, but a systemic staleness gap in a security control.

### Recommendation
Tie the cached zone-b membership to a freshness/version indicator from the capabilities registry (e.g., registry state version or last-sync timestamp) and fail closed (deny non-allowlisted reads) whenever the cached value's provenance is older than an acceptable staleness bound, rather than unconditionally trusting the last successfully-resolved value forever. Alternatively, when a registry lookup fails, deny GetSecrets for any DON category unless zone-b membership can be freshly and authoritatively confirmed as `false`, inverting the current "fail open when previously non-zone-b" behavior to "fail closed unless previously confirmed zone-b" — closing the window where a DON transitions into the restricted category during a registry outage.

### Proof of Concept
1. Workflow DON `X` initially has no `zone-b` family membership; `isZoneBWorkflowDON` resolves it via `capabilitiesRegistry.DONByID` and caches `zoneCache[X] = false`. [3](#0-2) 
2. DON `X`'s registry entry is updated (via normal capability registry governance) to include the `zone-b` family.
3. Before the node's next successful `DONByID(X)` call, the capabilities registry view becomes transiently unavailable (a scenario the code comments explicitly call out).
4. A `GetSecrets` request for an owner not on `VaultZoneBGetSecretsAllowed` arrives from DON `X`. `isZoneBWorkflowDON` hits the `DONByID` error path, finds `zoneCache[X] = false` cached, and returns `false, nil`. [4](#0-3) 
5. `enforce` sees `isZoneB == false` and returns `nil` (no restriction applied), allowing the unauthorized `GetSecrets` read to proceed despite DON `X` now actually being a restricted `zone-b` DON. [5](#0-4)

// enforce denies GetSecrets reads originating from a zone-b workflow DON unless
// the calling workflow owner is allowlisted. It is a no-op unless the master
// gate (VaultZoneBWorkflowGetSecretsRestrictEnabled) is open and the caller
// resolves to a zone-b DON. The owner is read from ctx, which must already carry
// the (normalized) CRE owner via RequestMetadata.ContextWithCRE.
func (z *zoneBRestrictor) enforce(ctx context.Context, workflowDonID uint32) error {
	enabled, err := z.restrictEnabled.Limit(ctx)
	if err != nil {
		return fmt.Errorf("could not evaluate zone-b vault read restriction gate: %w", err)
	}
	if !enabled {
		return nil
	}

	isZoneB, err := z.isZoneBWorkflowDON(ctx, workflowDonID)
	if err != nil {
		// Fail closed: if we cannot authoritatively resolve the caller's zone, do
		// not proceed. The registry is in-process, so this only fires for an
		// unknown/unregistered WorkflowDonID.
		return err
	}
	if !isZoneB {
		return nil
	}

	if err := z.ownerAllowed.AllowErr(ctx); err != nil {
		return fmt.Errorf("zone-b workflow DON may only read vault secrets for allowlisted workflow owners: %w", err)
	}
	return nil

func (z *zoneBRestrictor) isZoneBWorkflowDON(ctx context.Context, workflowDonID uint32) (bool, error) {
	don, err := z.capabilitiesRegistry.DONByID(ctx, workflowDonID)
	if err != nil {
		// The registry view can be transiently unavailable (e.g. not yet synced
		// after startup, or nil mid-update: DONByID returns "metadataRegistry
		// information not available"). That error is not specific to zone-b
		// callers, so failing closed here would block every vault GetSecrets read
		// DON-wide. Fall back to the last successfully-resolved membership for this
		// DON; only a never-before-resolved DON fails closed.
		if cached, ok := z.cachedZoneMembership(workflowDonID); ok {
			z.lggr.Warnw("capabilities registry lookup failed; using cached zone-b membership",
				"workflowDonID", workflowDonID, "isZoneB", cached, "err", err)
			return cached, nil
		}
		return false, fmt.Errorf("could not resolve caller workflow DON %d for zone-b vault read restriction: %w", workflowDonID, err)
	}
	// Case-insensitive match: family casing may vary across registry sources.
	isZoneB := slices.ContainsFunc(don.Families, func(family string) bool {
		return strings.EqualFold(family, zoneBFamily)
	})
	z.storeZoneMembership(workflowDonID, isZoneB)
	return isZoneB, nil
}
