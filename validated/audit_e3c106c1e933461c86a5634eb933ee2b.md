### Title
Unbounded external call to attacker-controlled destination module in `EvmHost.dispatchIncoming` can grief the relaying transaction with an OOG revert - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` forwards an incoming POST request to its destination module via a low-level `.call()` that carries no gas limit, so it forwards essentially all gas remaining in the relayer's transaction. Because the destination address (`request.to`) is chosen by whoever dispatched the message on the source chain — not validated to be any particular trusted app — a malicious sender can address the message at a contract that deliberately burns gas, forcing the relayer's `handlePostRequests`/`handleGetResponses` transaction toward an out-of-gas condition and wasting the relayer's paid gas fee, exactly the "arbitrary external call → OOG grief" pattern in the reference report.

### Finding Description
`EvmHost.dispatchIncoming` is restricted to the handler and is invoked once per leaf inside `HandlerV2.handlePostRequests`/`handleGetResponses` after proof verification: [1](#0-0) 

The relevant call is:
```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
```
No gas stipend is supplied, so Solidity forwards effectively all gas available at the call site (minus the 1/64th reserve). `destination` is `_bytesToAddress(request.to)`, taken verbatim from the request body that was originally set by whoever called `dispatch()`/`dispatchPost` on the source chain host — an ordinary, unprivileged action reachable by any user, analogous to how a Gladius order maker freely sets `additionalValidationContract`. Nothing in the dispatch path restricts `to` to a "well-known" or vetted application address. [2](#0-1) 

`handlePostRequests` loops over a batch of leaves and calls `host.dispatchIncoming` once per leaf inside the same relayer transaction. Because the sub-call to the malicious module can consume nearly all of the transaction's remaining gas (e.g., via a deliberate gas-burning loop), it can:
- push the relayer's overall transaction toward running out of gas while attempting to process the rest of the batch (subsequent iterations, event emissions, or storage writes after the malicious call), and
- in any case burn most of the gas the relayer paid for, since only 1/64 is guaranteed to remain reserved for the caller and the rest is consumed by the callee regardless of whether it ultimately reverts.

The `(bool success,)` pattern only protects the host's own state (it rolls back the request receipt on failure) — it does nothing to bound gas consumption by the callee, so it does not prevent the griefing effect described.

The same unbounded-gas-forwarding pattern also exists in the sibling dispatch paths for GET responses and both timeout callbacks in the same file: [3](#0-2) 

### Impact Explanation
An attacker who wants to grief relayers can dispatch a cross-chain POST (or GET) request addressed to a contract they control that intentionally consumes as much forwarded gas as possible (e.g., an unbounded loop, deep recursion, or storage-thrashing operation) before reverting or running out of gas itself. When an honest relayer later submits the proof through `HandlerV2.handlePostRequests`/`handleGetResponses`, the resulting call into `EvmHost.dispatchIncoming` forwards nearly all remaining transaction gas to that malicious contract. This can force the relayer's whole batched transaction to run out of gas (losing all the gas paid for the transaction and failing to deliver any of the other, legitimate messages batched alongside it), or at minimum burns a large, attacker-controlled amount of the relayer's gas for no useful protocol work. Since relayer economics rely on relayer fees covering gas costs, this directly degrades relaying reliability and profitability, and can be used to repeatedly stall delivery of a batch containing time-sensitive messages (this qualifies as a Medium-severity griefing/OOG issue per the cited Sherlock convention).

### Likelihood Explanation
Likelihood is high: dispatching a request with an arbitrary `to` address is an ordinary, unprivileged action available to any user of the source-chain host (no special permission needed), and deploying a gas-burning contract as the destination is trivial. The attack requires no cooperation from Hyperbridge, consensus, or governance — only a single dispatched message and a relayer that later delivers it, which is the expected, permissionless relaying flow.

### Recommendation
Bound the gas forwarded to destination modules in `EvmHost.dispatchIncoming` (and the analogous GET-response/timeout dispatch paths) to a fixed, sane stipend (e.g., `destination.call{gas: FIXED_MODULE_GAS_LIMIT}(...)`), configurable per host, so that a malicious module can, at worst, exhaust only its own allotted gas budget and cannot threaten the surrounding relayer transaction or the rest of a batched delivery.

### Proof of Concept
1. Attacker deploys `EvilModule` implementing `IApp.onAccept` that runs an unbounded/expensive loop (e.g., repeated `SSTORE`s or a `while(true)` guarded only by gas checks) so it burns essentially all gas forwarded to it.
2. Attacker calls `dispatch()`/`dispatchPost` on the source-chain `EvmHost` with `to = address(EvilModule)` and a destination state machine equal to the target host, no special privilege required.
3. After timeout/finality, a relayer submits `HandlerV2.handlePostRequests` with a valid MMR proof containing this request (potentially batched with other legitimate requests).
4. `EvmHost.dispatchIncoming` executes `destination.call(...)` with no gas cap; `EvilModule.onAccept` consumes nearly all forwarded gas.
5. Depending on gas provisioning, either the relayer's overall transaction runs out of gas (reverting delivery of the whole batch and consuming all gas paid), or the relayer's gas is mostly consumed by `EvilModule` with no useful delivery achieved, degrading relayer economics — reproducing the OOG-grief pattern described in the source report.
