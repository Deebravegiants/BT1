### Title
Unvalidated swap paths can add unauthorized wallet transfers to the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

Critical. The controller accepts caller-supplied opaque swap paths for `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, then invokes the configured router while the caller’s authorization is active. [1](#0-0)  A malicious route-selected contract can request an additional token transfer from the caller during router execution, causing that transfer to appear as a child of the signed controller authorization; the controller’s checks only measure controller token balances and final account risk. [2](#0-1) 

### Finding Description

The strongest reachable path is `swap_collateral(caller, account_id, current, amount, new, swap)`: the controller authenticates `caller`, authorizes the account owner or delegate, withdraws collateral into controller custody, and forwards the caller-controlled `swap` bytes to the router. [3](#0-2)  `swap_tokens` authorizes only the controller’s exact input transfer to the router, but it does not decode the route, restrict hop targets, or constrain additional caller-auth sub-invocations introduced by code reached through that route. [4](#0-3) 

After execution, `swap_tokens` rejects controller-input overspending, refunds unused controller-held input, and requires a positive controller-output delta. [5](#0-4)  These checks do not detect a malicious hop contract that invokes `wallet_token.transfer(caller, attacker, amount)` because that transfer spends the caller’s wallet balance rather than reducing the controller’s measured input or output. [5](#0-4) 

The same boundary is reachable through `multiply`’s primary and conversion routes, `swap_debt`, and `repay_debt_with_collateral`, all of which pass caller-controlled `Bytes` into the router boundary. [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation

A crafted route can steal arbitrary tokens held by the account owner or delegate who signs the strategy transaction, beyond the collateral or debt amount intentionally routed through the swap. [9](#0-8)  The theft commits atomically with a valid-looking strategy because the route can still return enough output to satisfy controller receipt measurement and post-operation solvency checks. [10](#0-9) [11](#0-10) 

This is theft of user funds rather than ordinary slippage or route-quality loss: the malicious hop moves unrelated wallet assets by joining the caller’s signed authorization tree. [9](#0-8) 

### Likelihood Explanation

Any unprivileged user can submit arbitrary route bytes to the affected strategy entrypoints, and no controller-side venue or pool allowlist bounds the contracts reached by the route. [1](#0-0) [12](#0-11)  Exploitation requires the victim to sign the poisoned authorization tree produced during simulation, so wallet or client validation can prevent it, but the on-chain controller does not provide that protection. [9](#0-8) 

### Recommendation

Constrain router execution to governance-approved venue and pool targets, and reject routes containing contracts outside that allowlist. [4](#0-3)  The router/controller boundary should expose a verifiable route manifest so callers can distinguish expected token transfers from unrelated caller-auth children before signing. [13](#0-12)  Clients should additionally decode the route and reject any signed authorization tree containing children other than the expected controller strategy and exact input transfer. [14](#0-13) 

### Proof of Concept

1. Deploy `RoguePool`, whose swap entrypoint calls `token::Client::new(env, wallet_token).transfer(victim, attacker, victim_balance)` and then lets the route return a fair `new` asset output. [10](#0-9) 
2. Construct a `swap` payload whose route passes through `RoguePool` and submit `swap_collateral(victim, account_id, current, amount, new, swap)`. [15](#0-14) 
3. During simulation, `RoguePool`’s wallet transfer is recorded beneath the victim’s `swap_collateral` authorization; signing that tree authorizes both the intended strategy and the unrelated transfer. [9](#0-8) 
4. The controller withdraws collateral, invokes `execute_strategy`, receives positive output, deposits it, and passes final risk checks while `RoguePool` transfers `victim_balance` of `wallet_token` to `attacker`. [16](#0-15) [17](#0-16)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
```
