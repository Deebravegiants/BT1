### Title
Unbounded standing router allowance + unvalidated `externalActionMetadata` let a LiFi swap credit a UTXO derived from tokens the caller never deposited - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`LifiExternalAction.callRouter` measures `swappedAmount` purely as a before/after balance delta of `outputToken` and never checks that the router actually consumed `inputAmount` of `inputToken`, while `approveUnlimited` (`contracts/TransfererBase.sol:32-43`) leaves a permanent `type(uint256).max` allowance from the action contract to the fixed `router` address that survives across every future transaction. Because `externalActionMetadata` is fully attacker-controlled raw calldata forwarded via low-level `.call` with only `require(success)`, an attacker can craft calldata that pulls more of `inputToken` than they deposited (up to the whole balance the contract holds, including any prior users' residue) via the standing allowance, and directs a corresponding output back into the contract, which the contract then credits 1:1 as a UTXO to the attacker.

### Finding Description
The invariant the protocol needs is: *the value credited to Hinkal as a UTXO (`amountToSendToHinkal`) must be derived exactly from the `inputAmount` of `inputToken` that this specific caller supplied in this transaction* — not from any other token balance the action contract happens to hold.

In `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`), `inputAmount` is computed from the caller's own `deltaAmounts[0]` and passed to `callRouter`. But `callRouter` in `LifiExternalAction.sol:16-36` does nothing with `inputAmount` except forward it as a raw parameter that is *only used for the native-ETH `msg.value` amount*; for ERC-20 input it does:

```
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
require(success, "LI.FI swap failed: erc-20 token");
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [1](#0-0) 

There is no assertion that the router's calldata pulls exactly `inputAmount` of `inputToken` (or even that it touches `inputToken` at all). `approveUnlimited` (`contracts/TransfererBase.sol:32-43`) grants the fixed `router` a `type(uint256).max` allowance the first time it's under `max/2`, and this approval is never revoked or reduced after the swap — it is a standing allowance on the LifiExternalAction contract's entire balance of `inputToken`, callable by anyone who can get the router to execute a `transferFrom(LifiExternalAction, ..., amount)` using calldata they fully control: [2](#0-1) 

Because the action contract is a shared, persistent contract (not per-transaction), any ERC-20 dust or residue left in it from a prior transaction (rounding, partial consumption by a router path, a transaction whose leftover input wasn't fully swapped) sits there with the router already holding max approval over it. A later, unprivileged caller can submit `externalActionMetadata` whose only requirement is `router.call(...)` returning `success == true` — nothing in `callRouter`/`swap` constrains which router function is invoked or how much of `inputToken` it moves. That calldata can direct the router to pull the contract's entire `inputToken` balance (not just this caller's `inputAmount`) via the standing allowance, and swap it for `outputToken`, which lands back in the action contract. `swappedAmount` is then simply `balanceAfter - balanceBefore` of `outputToken`, so this larger, foreign-funded output is credited entirely to the current caller:
```
uint256 amountToSendToHinkal = swappedAmount - totalFee;
transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);
utxoSet[0] = UTXO({ amount: amountToSendToHinkal, ... });
``` [3](#0-2) 

No proof-level constraint prevents this: the ZK circuit only fixes what the *caller* declared as `deltaAmounts`/`inputAmount` and the resulting UTXO commitment structure; it has no visibility into how many extra tokens `callRouter` actually pulled from the shared action contract via the pre-existing allowance, so `verifyProof`/`performHinkalChecks` cannot detect that `swappedAmount` was inflated by funds that don't belong to this transaction's declared input. The `slippageValues[1] != 0` check (`ExternalActionSwap.sol:53-56`) only requires a floor to be *set*, it is never compared against `swappedAmount`, so it provides no protection either.

### Impact Explanation
An attacker can have Hinkal mint a UTXO backed by tokens that were never actually deposited by the attacker in this transaction, but rather drained from the action contract's standing allowance/balance (which may hold residue belonging to the protocol or other in-flight transactions). This is theft of in-flight/protocol funds and a minting of shielded value not backed by the attacker's own declared input — Critical severity per the given rubric ("direct theft of shielded or in-flight user funds, minting shielded value without backing"). It is repeatable every time residual balance or a permissive router path exists, and the standing `approveUnlimited` allowance means the attack surface persists indefinitely once granted.

### Likelihood Explanation
Preconditions: (1) the action contract must hold or be able to accumulate a nonzero `inputToken`/`outputToken` balance beyond what the current caller intends to swap (achievable by the attacker themselves seeding it in a prior transaction, or by naturally-occurring rounding/partial fills), and (2) the LI.FI router must expose some callable path that lets the caller (the action contract, via its own standing allowance) move more than the intended amount, which is realistic for a generic multiplexer/diamond router that accepts arbitrary encoded swap instructions. Attacker cost is one or two ordinary `Hinkal.transact` calls with self-crafted `externalActionMetadata` and no privileged role required.

### Recommendation
- Do not rely purely on balance deltas without correlating them to the declared `inputAmount`: track pre/post balance of `inputToken` around the router call and require `balanceBefore(inputToken) - balanceAfter(inputToken) == inputAmount` (or `<=` with reconciled residual handling), reverting otherwise.
- Avoid standing unlimited approvals on a stateful, multi-user action contract; approve exactly `inputAmount` per call (`approveERC20Token(inputToken, router, inputAmount)`) and reset to zero after use, instead of `approveUnlimited`.
- Enforce the declared slippage floor: `require(swappedAmount >= circomData.slippageValues[1], ...)`.
- Ensure any leftover `inputToken`/`outputToken` balance is swept back to depositors or explicitly disallowed rather than left sitting in a shared contract with standing router allowance.

### Proof of Concept
Foundry plan:
1. Deploy `LifiExternalAction` with a mock router that:
   - On a first "seed" call, accepts `transferFrom` up to its allowance and does nothing else (simulate leftover residue by having a prior transaction leave `inputToken` dust in the action contract, e.g., by under-consuming a declared `inputAmount`).
   - On a second "drain" call (attacker-controlled `externalActionMetadata`), calls `IERC20(inputToken).transferFrom(actionContract, mockRouter, entireBalance)` using the standing `approveUnlimited` allowance, then mints/transfers a corresponding `outputToken` amount back to the action contract.
2. Have attacker call `Hinkal.transact` → `ExternalActionSwap.swap` with a small declared `inputAmount` (e.g., 1 token) but `externalActionMetadata` that triggers the mock router's "drain" path, pulling the full residual balance (e.g., 1000 tokens).
3. Assert: `swappedAmount` returned equals value derived from 1000 tokens, not the declared 1 token input — i.e. `amountToSendToHinkal != f(inputAmount)`, breaking `amountToSendToHinkal == swappedAmount - totalFee` tied to the caller's own declared input.
4. Assert the UTXO minted for the attacker (`utxoSet[0].amount`) reflects the inflated `swappedAmount`, proving the attacker was credited value they never deposited.
