### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body via HMAC, while the `shop` identity that the registry hands to app handlers is read directly from the `shop-domain` header, which is completely outside the HMAC's coverage. Since the HMAC secret (`api_secret_key`/`client_secret`) is shared across every shop that installs the same app, any attacker who can obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store and observing a legitimate webhook they receive) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, but the shop identity trusted by the handler is forged.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw body, excluding all headers: [2](#0-1) 

The `shop` accessor used elsewhere is read straight from the `shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop` to construct the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no further validation, and per the gem's own documented handler contract this is the value app developers are expected to use to key into their multi-tenant data (e.g., "shop, String - The shop domain of the webhook"): [5](#0-4) 

The equality this breaks: `shop authenticated by the signing secret` (∅ — the HMAC binds nothing about shop identity) vs. `shop trusted by the handler as the tenant key` (`request.shop`, taken verbatim from an attacker-controlled header). Because Shopify apps use one `client_secret`/`api_secret_key` for the app itself, not per-shop, this single secret validates webhook bodies for *every* shop that installs the app. An attacker with a legitimate install of the same app can therefore harvest a valid `(raw_body, hmac)` pair from their own store's webhooks and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop that also uses the app — the HMAC check still passes because it only checks the body's integrity/secret knowledge, not the claimed shop.

### Impact Explanation
This is a cross-tenant boundary break: an attacker-controlled `shop` value flows into the app's business logic (multi-tenant record lookups, order/customer processing, background job enqueueing per shop as shown in the docs' `perform_later(shop_domain: data.shop, ...)` pattern) despite never being authenticated by the signature. This directly matches the "Critical - cross-tenant access" impact category, since a merchant using the app can inject or spoof webhook events attributed to any other merchant/tenant using the same app.

### Likelihood Explanation
Exploitation requires only that the attacker be an unprivileged internet user who can install the target app on their own Shopify store (a normal, unprivileged action) to obtain a valid signed body/HMAC pair for a topic of their choosing, and then send an HTTP POST directly to the app's public webhook endpoint with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged account is needed beyond what any ordinary merchant already has by installing the app.

### Recommendation
Bind the `shop` identity into the value that is cryptographically verified — e.g., include the shop domain in the signable string/HMAC input, or independently verify that the shop domain in the header corresponds to a shop with an active, matching session/webhook registration before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` which still equals `H`, since the check never touches the shop header (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` accepts the request and calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the app to process attacker-supplied data under the victim's tenant identity.
