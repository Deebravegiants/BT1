### Title
Webhook `topic` and `shop-domain` headers are not bound to the HMAC signature, allowing cross-tenant/cross-topic replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` (via `Registry.process`) authenticates the body bytes but never authenticates the `shopify-topic` or `shopify-shop-domain` headers. Because the same `api_secret_key` is shared across every shop that has the app installed, an attacker who legitimately receives one signed webhook for their own shop possesses a body/HMAC pair that remains valid no matter what topic or shop-domain header is sent alongside it.

### Finding Description
The binding the app relies on is: `(topic, shop)` authenticated by HMAC == `(topic, shop)` acted on by `handler.handle`. Tracing the code shows this equality is false:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#topic` and `Request#shop` are read directly from attacker-controlled HTTP headers with no cryptographic tie to the body [2](#0-1) .
- `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it only to the received signature - `topic`/`shop` never enter the computation [3](#0-2) .
- `Registry.process` validates only the HMAC, then looks up the handler using `request.topic` and constructs `WebhookMetadata` using `request.topic`/`request.shop`, both taken straight from headers [4](#0-3) .

Exploit flow: attacker installs the app on their own dev shop, captures one legitimate webhook delivery (`raw_body = B`, `hmac = HMAC(secret, B)`, any topic). They replay a request to the app's public webhook endpoint with the same `raw_body`/`hmac-sha256` but rewritten `x-shopify-topic: shop/redact` and `x-shopify-shop-domain: victim.myshopify.com`. `HmacValidator.validate` still passes because the signed bytes (`B`) are unchanged, and `Registry.process` dispatches the `shop/redact` handler with `WebhookMetadata.shop == "victim.myshopify.com"`.

No existing guard in the gem prevents this: there is no shop-allowlist check, no session lookup, and no per-shop signing key mixed into the HMAC computation anywhere in `Request`, `Registry`, or `HmacValidator`.

### Impact Explanation
This is a genuine authentication-bypass / cross-tenant issue in the gem's own webhook-processing code: the `shop-domain` and `topic` headers presented to `handler.handle` are entirely unauthenticated, even though `Registry.process` behaves as if HMAC success vouches for them. Any app whose webhook handlers key logic off `WebhookMetadata#shop` or `WebhookMetadata#topic` (e.g. GDPR mandatory handlers like `shop/redact`, `customers/redact`, `customers/data_request`) can be tricked into executing tenant-specific logic for an arbitrary victim shop, using body content the attacker legitimately possesses for their own shop. This is repeatable against arbitrary victim shop domains from a single captured delivery, since the attacker only needs to change headers, not re-forge the HMAC.

### Likelihood Explanation
Preconditions are low-cost and match the threat model: an unprivileged attacker only needs to install the app on their own (free) development store and register/receive one webhook of any topic to obtain a valid `(raw_body, hmac)` pair. The webhook receiving endpoint is a normal public HTTP endpoint with no additional network-level authentication, so headers are fully attacker-controlled on a direct request to that endpoint. This is exploitable per-request and is trivially repeatable.

### Recommendation
Bind `topic` and `shop` cryptographically or contextually to the signature/validation step rather than trusting the raw headers verbatim:
- Have `Registry.process`/`Request` require the caller to supply the expected shop domain (e.g. from an already-authenticated session lookup keyed by an app-known installed-shop list) and reject the webhook if `request.shop` does not match a known/installed shop for that app.
- Alternatively, since Shopify's own webhook protocol does not sign headers, document this limitation prominently and require host apps to verify `shop-domain` against their installed-shops registry before invoking handlers, and consider adding this check as a built-in `Registry.process` option to close the gap by default.

### Proof of Concept
```ruby
# test/webhooks/registry_forgery_test.rb
def test_process_allows_shop_and_topic_header_forgery_on_valid_signature
  raw_body = '{"id": 1}'
  secret = ShopifyAPI::Context.api_secret_key
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)

  # Attacker's own legitimately-signed delivery for their own shop/topic
  attacker_headers = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),
    "x-shopify-shop-domain" => "attacker.myshopify.com",
  }

  # Attacker rewrites topic + shop-domain, keeps body & hmac identical
  forged_headers = attacker_headers.merge(
    "x-shopify-topic" => "shop/redact",
    "x-shopify-shop-domain" => "victim.myshopify.com",
  )

  received_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(lambda do |data|
    received_shop = data.shop
  end)

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "shop/redact", path: "path", delivery_method: :http, handler: handler,
  )

  ShopifyAPI::Webhooks::Registry.process(
    ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers),
  )

  # Demonstrates the broken binding: HMAC was computed for attacker's body only,
  # yet the handler received victim's shop domain and a different topic.
  assert_equal("victim.myshopify.com", received_shop)
end
```
This test does not require a live shop; it only reuses the gem's own `Context.api_secret_key`, `Request`, and `Registry` classes, matching the constraints.
