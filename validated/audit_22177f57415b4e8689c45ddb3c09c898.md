### Title
`onPostRequestTimeout` gated by `whenNotPaused` blocks users from reclaiming locked/burned funds on message timeout - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, `WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`HyperFungibleToken`/`WrappedHyperFungibleToken` (and their upgradeable variants) implement `onPostRequestTimeout`, the callback invoked by the ISMP host to refund a user whose cross-chain `send()` failed to be delivered before its timeout. This refund path is gated by the `whenNotPaused` modifier, the same pattern flagged in the external report for `lockForAnOrder`/`increasePosition`. If the contract owner pauses the token while a user's cross-chain transfer is in-flight, and that message subsequently times out, the refund call reverts and the user's burned/locked tokens cannot be recovered for as long as the pause is in effect.

### Finding Description
`send()` burns (`HyperFungibleToken`) or locks (`WrappedHyperFungibleToken`) the sender's tokens immediately and dispatches an ISMP `POST` request through the host [1](#0-0) . If the message is never delivered before `timeout`, the ISMP host calls back into the app's `onPostRequestTimeout` to re-mint (or unlock/transfer back) the funds to the original sender:

```solidity
function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
    Message memory message = abi.decode(incoming.request.body, (Message));
    address refundee = _toAddr(message.from);
    _mint(refundee, message.amount);
    emit Refunded({to: refundee, amount: message.amount});
}
``` [2](#0-1) 

The same modifier is present on the wrapped variant's timeout handler, which unwraps/refunds locked ERC20 or native tokens: [3](#0-2) 

Because `whenNotPaused` is applied to this refund entry point, an owner-initiated pause (for maintenance or security reasons, per `pause()`) blocks the host's timeout-refund call from succeeding while the user's underlying funds have already been irreversibly burned or locked in `send()`. This mirrors exactly the root cause pattern in the external report: a critical fund-recovery path is dependent on a `whenNotPaused`-gated function, so pausing the protocol strands users who need to recover value rather than only pausing new outbound risk-taking actions (`send()`/`onAccept()`, which are legitimately pausable since they are forward-looking operations).

### Impact Explanation
Users who dispatched a `send()` prior to a pause have already had funds burned/locked. If their message times out while the contract is paused, they cannot claim the refund via `onPostRequestTimeout` until the owner unpauses. If the pause is prolonged (e.g., an extended security incident, migration, or a malicious/compromised owner key that never unpauses), the affected user's funds are frozen for the duration, and if the ISMP host's underlying timeout-processing does not allow indefinite retry of the exact same relayed proof, this can result in effectively permanent loss for the affected transfer. This satisfies the "permanent freezing of funds" bar for a valid finding, since it strands funds that are otherwise fully validated and entitled to be returned to the user.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the owner pausing the contract, and (b) at least one in-flight `send()` timing out during that window. This is a normal, expected operational sequence — pausing during an incident is precisely when in-flight transfers are also more likely to fail to be delivered (e.g., if the pause is a reaction to a bridge/relayer issue), making the coincidence plausible rather than contrived.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout` (and any other pure fund-recovery/refund callback) in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol`, while keeping the pause gate on forward-looking operations such as `send()` and `onAccept()`. This ensures pausing can still stop new risk (new outbound transfers, new inbound mints/executions) without blocking users from recovering funds that are already committed to be refunded.

### Proof of Concept
1. Alice calls `send()` on `HyperFungibleToken`, burning her tokens and dispatching a POST request with a timeout of `T`. [1](#0-0) 
2. Before delivery, the contract owner calls `pause()` for an unrelated operational reason. [4](#0-3) 
3. The destination chain never processes the request in time; timeout `T` elapses.
4. The relayer submits the timeout proof and the ISMP host invokes `onAccept`/`onPostRequestTimeout`; the call reverts because `whenNotPaused` fails (the existing test suite explicitly verifies this revert behavior for `onAccept` when paused, confirming the same modifier blocks calls: `testOnAcceptRevertsWhenPaused`). [5](#0-4) 
5. Alice's burned tokens cannot be re-minted to her until the owner unpauses — if the pause persists or is never lifted, her funds remain unrecoverable.
