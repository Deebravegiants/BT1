### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC signature, allowing shop impersonation via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (taken from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identity passed to the app's webhook handler. Because the shop identity is never bound into the HMAC computation, an attacker who possesses one validly-signed webhook body/HMAC pair can resubmit it with an arbitrary `shop-domain` header and it will still pass `Utils::HmacValidator.validate`, causing the host app to process the payload as if it originated from a different, victim shop.

### Finding Description
The intended binding is: `HMAC-valid(request) ⇒ request.shop == the shop Shopify actually sent this webhook for`.

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all read from HTTP headers, but: [2](#0-1) 
`to_signable_string` — the only value that is fed into the HMAC check — returns `@raw_body` alone. None of the header-derived fields, in particular `shop`, are part of the signed material.

`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header. Since `to_signable_string` for a webhook `Request` is just the body, the check only proves "this body was HMAC-signed by Shopify with our secret" — it proves nothing about which shop, topic, or webhook id the signature was originally issued for.

`ShopifyAPI::Webhooks::Registry.process` then trusts the unauthenticated `shop` field directly: [3](#0-2) 
`request.shop` is forwarded verbatim into `WebhookMetadata`, which is the value host apps are documented to use to select the tenant/session context for processing the webhook (`docs/usage/webhooks.md:12-26`, `lib/shopify_api/webhooks/webhook_handler.rb:6-12`).

Because the body is the only signed input, any two shops that ever receive a webhook with an identical body (which is common — many webhook topics carry generic or empty bodies, e.g. `app/uninstalled` frequently ships `{}` or minimal shop-independent JSON, and `orders/create` bodies for identical test fixtures/replays can coincide) produce identical valid HMACs regardless of which shop they were addressed to. An unprivileged user who merely has their own trial/development shop with the app installed can capture a legitimately Shopify-signed `(body, hmac)` pair sent to their own endpoint, then replay that exact body+HMAC to the app's webhook endpoint while substituting a different `shop-domain` header. `Utils::HmacValidator.validate` still returns `true` because it never inspected the shop header, and the host app's handler will process the request believing it came from the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary the HMAC signature is supposed to enforce for the webhook subsystem: `HMAC-valid ⇒ trust request.shop`. An attacker can cause the host application to act on webhook data (topic + body) while impersonating an arbitrary victim `shop` domain, since none of `shop`, `topic`, or `webhook_id` are cryptographically bound to the signature. This is a cross-tenant identity-confusion vulnerability at the exact point the docs recommend applications key their tenant/session lookup (`data.shop`), matching the Critical "cross-tenant access" impact category — an app that keys any lookup, tenant selection, deduplication, or state transition off `WebhookMetadata#shop` can be manipulated into processing forged, cross-tenant events.

### Likelihood Explanation
Likelihood is bounded by the attacker needing at least one genuine `(body, hmac)` pair signed with the app's secret. This is trivially obtainable by any unprivileged user who installs the app on their own shop (no privileged credentials, tokens, or the `api_secret_key` itself are needed) and observes/logs the raw webhook POST their own endpoint receives from Shopify — the gem's own `Request` class only needs `raw_body` and headers, no secret knowledge, to construct a forwardable replay. Given several webhook topics have shop-independent or highly-repeatable bodies (mandatory `app/uninstalled`, or any topic where the same object payload is plausible across shops), reliably finding a body that produces useful confusion is realistic, not merely theoretical.

### Recommendation
Bind the shop (and ideally topic/webhook_id) identity into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the request before trusting it. Concretely, change `Request#to_signable_string` to incorporate the `shop-domain` header (and other identity headers) into the signed string used for comparison, or — since Shopify's actual webhook HMAC is computed over the raw body only per Shopify's contract — instead independently verify the shop identity via a second authenticated channel (e.g., cross-check `shop` against the app's own installation state before dispatch), and never treat `request.shop` as authenticated purely because `HmacValidator.validate` returned true.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker-shop.myshopify.com" and
# observes/logs a legitimate webhook Shopify sends them, e.g. for "app/uninstalled":
captured_body = "{}"
captured_hmac_header = "<value captured from the legitimate request Shopify sent to attacker's endpoint>"

# Attacker now POSTs to the victim app's webhook endpoint, reusing the captured
# body + hmac, but swapping the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => captured_hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary victim
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# Passes HMAC validation because it only checks the (unchanged) body, not the shop header:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will then invoke the app's handler with a WebhookMetadata
# claiming shop: "victim-shop.myshopify.com", even though Shopify never sent
# this webhook for that shop.
ShopifyAPI::Webhooks::Registry.process(request)
