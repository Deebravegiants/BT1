### Title
Webhook `shop` (and topic/version/id) header identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate(request)` verifies solely that the body bytes match a signature computed with the app's secret. The `shop-domain`, `topic`, `api-version`, and `webhook-id` values, however, are read straight from HTTP headers (`shopify_header`) and are never part of the signed content, yet `Registry.process` trusts `request.shop` as the tenant identity when constructing `WebhookMetadata` and routing to the handler.

### Finding Description
The identity binding that should hold is:
`HMAC-verified bytes == bytes used to determine the tenant (shop) and dispatch routing`

In this gem that equality does not hold:
- `hmac` is computed over `@raw_body` only [4](#0-3) .
- `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from mutable HTTP headers with no cryptographic tie to the body [5](#0-4) .
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` — which re-derives the signature from `to_signable_string` (the body) — before trusting `request.shop`/`request.topic` to select the handler and construct the metadata passed to app code [2](#0-1) .

Because Shopify's genuine HMAC only ever signs the raw JSON body (this is inherent to how Shopify signs webhooks, and this gem faithfully reproduces that by only including the body in `to_signable_string`), any entity capable of obtaining one legitimately-signed webhook body/HMAC pair for *any* shop under the app (e.g., an attacker who installs the app on their own shop and receives a real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) headers to name a *different* shop. The signature check passes because it never inspected those headers, and the app-level handler receives `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity binding relied upon by every webhook handler registered through `Registry.add_registration`. An app that uses `data.shop` (from `WebhookMetadata`) to select which merchant's records to update, delete, or unsubscribe (e.g., `customers/redact`, `shop/redact`, order/product sync) can be made to apply another shop's genuine webhook payload under an attacker-chosen shop identity — a cross-tenant data confusion/injection vector, since the app has no independent way to know the header was forged (the HMAC gives false assurance of complete authenticity).

### Likelihood Explanation
Exploitation requires the attacker to have obtained at least one legitimately HMAC-signed body from Shopify — trivially achievable by installing the app (even as a development/free trial store) and capturing one webhook delivery, which needs no privileged credentials, access tokens, or `client_secret`. From there, forging the header value is a simple HTTP replay; likelihood is moderate-to-high for any app that trusts `WebhookMetadata#shop` as an authenticated tenant identifier, which the docs explicitly encourage.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-covered signable string, or independently re-verify that the `shop` header matches a shop context already established for the session before dispatching. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must not be trusted as tenant boundaries without additional verification (e.g., cross-checking against a known/allow-listed shop list).

### Proof of Concept
1. Install the app on `attacker.myshopify.com` and receive a real webhook, e.g. `orders/create`, giving `raw_body = B` with a valid `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the app's secret) and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same `B` and `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com"})` builds successfully [6](#0-5) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`B` only) and matches `H`, so validation succeeds [2](#0-1) .
5. The registered handler for the topic is invoked with `WebhookMetadata` claiming `shop: "victim.myshopify.com"`, even though the payload actually originated from `attacker.myshopify.com`.
