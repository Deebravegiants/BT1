### Title
Attacker-sized HyperSwap V2 pre-seed reserves make `Bonding._noFeeSwapInput`'s `Math.mulDiv` overflow-revert, permanently bricking `finalizeGraduation` and freezing the curve-raised LT and 250M reserved tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._noFeeSwapInput` computes a rebalancing swap size from attacker-influenced HyperSwap V2 pair reserves and validates only a lower bound (zero-checks) on its inputs, never an upper bound on the resulting product before it is fed into `Math.mulDiv`. This mirrors the FFmpeg RV60 `qp` bug class: a check exists at one edge of the valid range but the other edge — the one that actually protects the fixed-capacity arithmetic slot (there `rv60_qp_to_idx[64]`, here `uint256`'s `Math.mulDiv` result-fits check) — is missing/insufficiently bounded, and the code's own comments concede the omission ("Constructed adversarial inputs that violate this would `revert`") while dismissing it as impractical.

### Finding Description
`_seedRebalancing` (`Bonding.sol:1279-1354`) is reached in Regime 3 of `finalizeGraduation` whenever a HyperSwap V2 `TOKEN/LT` pair already has `totalSupply() > 0` at the time phase 2 runs — i.e., anyone pre-minted that pair before graduation, which the scope rules explicitly treat as reachable ("pre-creating or pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation"). It reads the pool's live `uint112` reserves and, unless both sides fall under the tiny `DIRECT_MINT_PRESEED_BPS` (1 bp) escape band (`Bonding.sol:1297-1302`), calls `_pairRebalance`, which calls: [1](#0-0) 

`_noFeeSwapInput` only guards the **lower** bound of its inputs (`== 0` checks) and returns `0` for those cases. It performs no **upper**-bound check on `reserveIn`, `reserveOut`, `targetN`, or the product `reserveIn * reserveOut * targetN` before dividing by `targetD` inside `Math.mulDiv`. The function's own natspec admits the gap: [2](#0-1) 

`reserveIn`/`reserveOut` come straight from the attacker-controlled V2 pair (`_seedRebalancing`, `Bonding.sol:1287-1289`), while `targetN`/`targetD` are `ltFromPair`/`tokensForLP` — real curve values that can legitimately be extremely lopsided: `tokensForLP` follows the parabola `sold·(S−sold)/S` (`Bonding.sol:1057-1072,1089`) and is near-zero whenever a token graduates via the **USD** trigger with very little of the curve sold (dual-trigger graduation, `canGraduate`, `Bonding.sol:680-695`, driven by LT `exchangeRate()` appreciation rather than volume). A near-zero `tokensForLP` as `targetD` massively amplifies `Math.mulDiv`'s numerator-to-denominator ratio, so even moderate attacker-chosen V2 reserves (well under `uint112.max`, and easily satisfying the "not both under 1 bp" escape condition at `Bonding.sol:1297-1302`) push `reserveIn * reserveOut * targetN / targetD` past `uint256.max`. `Math.mulDiv` reverts on overflow, and that revert propagates unguarded through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation` (`Bonding.sol:1000-1034`).

Because `finalizeGraduation` is the only path that clears `Lifecycle.Graduating`, deletes `pendingGraduation`, and calls `LPLock.recordLock` (`Bonding.sol:1023-1031`), a token stuck reverting here can never reach `Lifecycle.Graduated`. All curve-raised LT already pulled into `Bonding` via `Router.graduate` in phase 1 (`_prepareGraduationLiquidity`, `Bonding.sol:1084-1087`) and the 250M tokens reserved for the LP (`tokensForLP`/`lpBurned` accounting, `Bonding.sol:1089-1095`) remain permanently parked on `Bonding` with no rescue path — trading is already frozen (`Lifecycle.Graduating` blocks `buy`/`sell`, `Bonding.sol:574,592`), and `triggerGraduation`/`finalizeGraduation` cannot be re-run to a different outcome since the revert is deterministic given the frozen `pendingGraduation` snapshot and the still-hostile V2 reserves.

### Impact Explanation
This permanently freezes: (a) the entirety of the curve-raised LT that funded that token's launch (all buyer capital), and (b) the 250M tokens earmarked for the LP, with the token stuck forever in `Lifecycle.Graduating` — no sells, no buys, no graduation. This satisfies the "permanent freezing of trader, creator, or LP funds" bar in the Validate section. Severity is Medium/High-adjacent: it is a targeted griefing attack against a specific launched token (not protocol-wide), reachable by any unprivileged address that pre-seeds the HyperSwap V2 pair for that token/LT combination before its graduation fires.

### Likelihood Explanation
Reaching Regime 3 only requires permissionlessly calling `IUniswapV2Factory.createPair` + `IUniswapV2Pair.mint` on the `TOKEN/LT` pair before the target token graduates — explicitly listed as in-scope reachable in this exercise's rules. The attacker does not need reserves anywhere near `uint112.max`: they need reserves large enough, combined with a low `tokensForLP` (achievable by targeting a token that is likely to graduate via the USD/exchange-rate trigger while `sold` is still small), to push the `Math.mulDiv` product over `uint256.max`. This is a deliberate, low-cost setup rather than an accidental edge case, but it does require the attacker to correctly anticipate/target a low-`tokensForLP` graduation, which narrows — but does not eliminate — the practical window.

### Recommendation
Add an explicit upper-bound / overflow guard in `_noFeeSwapInput` before calling `Math.mulDiv`, and treat overflow as "swap not safely computable" (return `0`, matching the existing fallback semantics) rather than letting the call revert:
- Use `Math.mulDiv` with an early feasibility check (e.g., compare `reserveIn`/`reserveOut` magnitude against `targetD`/`targetN` and short-circuit to the `_seedDirectMint` fallback) so `finalizeGraduation` never reverts due to attacker-influenced V2 reserves.
- Wrap the `_pairRebalance` call path in a try/catch (or pre-validate) so any arithmetic failure falls back to `_seedDirectMint`, preserving the "brick resistance" guarantee the natspec already claims for other overflow classes.

### Proof of Concept
1. Attacker identifies a soon-to-graduate token where graduation will fire via the USD/exchange-rate trigger while `sold` (curve tokens purchased) is still small, so `tokensForLP = sold·(S−sold)/S` will be tiny relative to `ltFromPair`.
2. Before that token's `_enterGraduating` fires (or immediately after, before `finalizeGraduation` is called), attacker permissionlessly calls `IUniswapV2Factory.createPair(token, lt)` and `pair.mint(attacker)` after transferring skewed reserves (e.g., a large `LT` amount vs. `TOKEN` amount, chosen so neither side falls under the `DIRECT_MINT_PRESEED_BPS` escape band relative to the eventual `(tokensForLP, ltFromPair)`).
3. Once `_enterGraduating` computes the tiny `tokensForLP`, anyone calling `finalizeGraduation(token)` reaches `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, where `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` overflows `uint256` and reverts.
4. `finalizeGraduation` reverts unconditionally on every subsequent call (the inputs are frozen in `pendingGraduation` and the hostile V2 reserves persist), leaving the token permanently stuck in `Lifecycle.Graduating` with its curve-raised LT and 250M LP-reserved tokens locked in `Bonding` indefinitely.     function _noFeeSwapInput(
```text
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```
