## Title
`Webhooks::Request#shop`/`#topic`/`#webhook_id`/`#api_version` are read from unsigned headers while `to_signable_string` only covers `@raw_body` — ([File: lib/shopify_api/webhooks/request.rb])

## Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and only feeds `@raw_body` into `to_signable_string`, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers that are never part of the HMAC-signed material. `HmacValidator.validate` only proves that `@raw_body` was signed with `Context.api_secret_key`; it says nothing about which shop the header claims to be from. Because `client_secret`/`api_secret_key` is shared by a single app across every merchant that installs it, an attacker who legitimately installs the app on their own shop can capture one valid `(body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`, which `shopify_header` prefers), producing an HMAC-valid request that `Webhooks::Registry.process` will attribute to a shop the attacker never proved ownership of.

## Finding Description
The broken binding: the code assumes `HmacValidator.validate(request) == true` implies `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` are all authenticated values originating from Shopify for that shop. In reality:

- `to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, `api_version` are all derived from `shopify_header`, which reads directly from attacker-supplied HTTP headers with no further validation of format or content, and prefers the newer `shopify-<name>` header over `x-shopify-<name>` if both are present: [2](#0-1) [3](#0-2) 
- `initialize` only checks that a `topic`/`hmac-sha256`/`shop-domain` header *exists* (`headers.key?`), never that its value is well-formed or consistent with anything: [4](#0-3) 
- `HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header value; it never touches `shop`, `topic`, or any other header: [5](#0-4) 
- `Registry.process` validates the HMAC and then hands the caller-controlled `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) straight to the handler as `WebhookMetadata`, trusting it as if it had been authenticated by the signature check that just passed: [6](#0-5) 

Exploit flow: the attacker (per the threat model, an unprivileged internet user who may install the target app on their own development shop) receives one legitimately signed webhook for their own shop — a valid `(raw_body, x-shopify-hmac-sha256)` pair computed with the app's single `api_secret_key`. Because `api_secret_key` is per-app, not per-shop, and the signature never covers `shop-domain`, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or the higher-precedence `shopify-shop-domain`) with any victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body against the secret, and `Registry.process` calls the handler with `shop: <victim domain>` sourced from the header the attacker fully controls.

No existing guard prevents this: `HmacValidator.validate` (body-only check), `ShopValidator.sanitize!` (not invoked anywhere in this path), and `initialize`'s presence check (existence, not correctness) all fail to bind `shop` to the signature.

## Impact Explanation
An app that trusts `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) as authenticated — which is the documented, intended usage of this accessor — can be made to process a webhook payload under an arbitrary shop identity chosen entirely by the attacker. This is a cross-tenant confusion: order/customer/app data belonging to the attacker's own shop can be recorded, applied, or acted upon as if it belonged to a victim merchant, or vice versa, depending on how the host app keys its per-shop state off `WebhookMetadata#shop`. This falls into the Critical "cross-tenant access" category since one tenant's (attacker's) webhook body is trusted as authenticated for another tenant's (victim's) identity.

## Likelihood Explanation
Preconditions are modest: the attacker only needs the ability to install the target app on their own development shop (explicitly allowed in the threat model) and to send arbitrary HTTP requests to the app's public webhook endpoint (also explicitly allowed). No secrets, tokens, or privileged access are required — only a body/HMAC pair from one legitimately triggered webhook of the attacker's choosing (e.g. `orders/create` on their own store), which can be captured and replayed indefinitely against arbitrary victim shop-domain values in the header.

## Recommendation
Bind the shop/topic/webhook identity to the signature. Include `shop-domain`, `topic`, and `webhook-id` (and ideally the `api-version`) in `to_signable_string`, or independently verify `request.shop` against the set of shops actually installed for this app (e.g., a lookup keyed by an already-authenticated session/access-token store) before trusting it in `Webhooks::Registry.process`. At minimum, document clearly that `request.shop` is unauthenticated and must be cross-checked by host apps against known installations.

## Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_trusts_unsigned_shop_domain_header
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  signed_hmac_header = Base64.encode64(hmac)

  received_shops = []
  handler = TestHelpers::FakeWebhookHandler.new(->(data) { received_shops << data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(topic: @topic, path: "path", delivery_method: :http, handler: handler)

  # Same signed body+hmac, two different shop-domain headers -> both accepted
  ["attacker-shop.myshopify.com", "victim-shop.myshopify.com"].each do |shop|
    headers = {
      "x-shopify-topic" => @topic,
      "x-shopify-hmac-sha256" => signed_hmac_header,
      "x-shopify-shop-domain" => shop,
    }
    request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
    ShopifyAPI::Webhooks::Registry.process(request)
  end

  assert_equal(["attacker-shop.myshopify.com", "victim-shop.myshopify.com"], received_shops)
  # Demonstrates one signature accepted for two different shop identities
end
```
This confirms the equality `HmacValidator.validate(request) == true` holds identically for both requests despite `request.shop` differing, proving `shop` is outside signature coverage.
