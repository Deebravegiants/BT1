### Title
Webhook `shop` domain (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `ShopifyAPI::Webhooks::Registry.process` uses `request.shop` — parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — as the trusted tenant identifier passed to the app's handler via `WebhookMetadata`. The HMAC never binds the shop-domain header to the signed payload, so the "shop verified by HMAC" and "shop the app trusts" are not the same value.

### Finding Description
`HmacValidator.validate` checks the request's `hmac` against `to_signable_string`: [1](#0-0) . For `Webhooks::Request`, `to_signable_string` is defined as only `@raw_body`: [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to that HMAC: [3](#0-2) .

`Registry.process` validates only the HMAC-over-body, then immediately trusts `request.shop` as the tenant identity handed to the app's business logic: [4](#0-3) . The documented handler contract explicitly tells app authors to treat `data.shop` as the authoritative shop domain for the webhook and to use it for tenant-scoped work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) .

The identity binding broken is: **the shop the gem verifies (via HMAC, which covers only the body) ≠ the shop the gem hands to the app as the trusted tenant (via the `shop-domain` header)**. Any attacker who can obtain one valid `(raw_body, hmac)` pair — trivially available since they can install the app on their own shop and receive legitimate webhooks for their own tenant, or because two shops can produce byte-identical bodies (e.g. an empty `{}` payload, or any payload with identical field values) — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will pass because it never inspects the shop header, and `Registry.process` will dispatch to the handler with an attacker-chosen `data.shop`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged internet user who owns any single shop (or has captured any one valid webhook body/HMAC pair for a topic with a static/predictable body) can cause the host application to process webhook data under a `shop` value of their choosing. Any app logic keyed off `data.shop` — tenant selection, session lookup, per-shop feature flags, redaction/GDPR request routing (`shop/redact`, `customers/redact`, `customers/data_request` are explicitly mandatory topics processed through this same path) — can be attributed to a victim shop chosen by the attacker, i.e., cross-tenant access/confusion driven entirely by gem-trusted, unauthenticated header data.

### Likelihood Explanation
Moderate-to-high for topics with static or attacker-controllable bodies (e.g., empty/near-empty payloads, or payloads whose relevant fields the attacker controls in their own shop to match a target scenario). The attacker only needs: (1) a working webhook endpoint URL (documented as a fixed, discoverable Rails route), and (2) one legitimately-signed `(body, hmac)` pair from any shop where the app is installed, including their own. No secret material is required — this fully avoids the "requires api_secret_key/access token" exclusion, since the attacker never needs the app's secret, only a replayed signature.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook_id`) inside the HMAC-signed payload used for verification, or otherwise cryptographically bind the header-derived `shop` value before trusting it — e.g., by using Shopify's per-webhook signature verification against the *combination* of headers and body rather than body alone, or by cross-checking `request.shop` against a known/registered shop set instead of blindly trusting it after body-only HMAC validation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for `customers/data_request` with body `{}` and a valid `hmac` header signed by the app's real `client_secret` over that body.
2. Attacker replays the exact same raw body and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` to the desired topic.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks the (unchanged) body: [2](#0-1) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`: [6](#0-5) , causing the app to perform tenant-scoped actions (e.g., data deletion/redaction handling) against the victim shop's data based on attacker-controlled input.
