### Title
Stale Address Caching in `ConnectedOrigins` Lets a dApp Retain Access to a Wallet-Account Slot's Old Identity After the Underlying Account Changes - (File: features/connected-origins/module/connections.js)

### Summary
`ConnectedOrigins` caches per-account addresses in `connectedAccountsAtom`, keyed only by the wallet-account *name* (e.g. `exodus_1`), and lazily reuses that cached value instead of re-deriving it whenever the underlying account occupying that name/slot changes. This mirrors the C4 finding's root cause: an accounting/identity value is checkpointed against a mutable slot (vault owner / wallet-account name) and is never invalidated when the slot's underlying content changes, so a stale value keeps being trusted.

### Finding Description
`#getWalletAccountAddresses` in `features/connected-origins/module/connections.js` resolves an address for a wallet account as follows: [1](#0-0) 
It first checks `connectedAccounts[walletAccount]?.addresses[assetName]` and, if present, returns that cached value directly — it never re-derives or diff-checks it against the live `walletAccount` object.

The only place this cache is refreshed is `updateConnectedAccounts`, wired to `enabledWalletAccountsAtom.observe(...)`: [2](#0-1) [3](#0-2) 

Crucially, `updateConnectedAccounts` only recomputes the cache when the **set of wallet-account names (keys)** differs (`xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))`). If a wallet-account *name/slot* is reused — for example via index-gap-filling on re-creation (`fillIndexGapsOnCreation`, see `getNextIndex`/`createMany`) — the key set stays identical even though the account occupying that slot is now a different underlying account (different label, potentially different `id`/source for imported or hardware accounts): [4](#0-3) [5](#0-4) 

Because the key-diff check reports "up-to-date" in this case, `updateConnectedAccounts` short-circuits and never calls `#getAccounts`/`#getWalletAccountAddresses` again for that slot, so the origin keeps whatever address was cached for the old occupant of that name. This is structurally identical to the C4 bug: an identity/ownership checkpoint (`_getDepositedBalance` / cached address per account) is bound to a mutable slot (vault / wallet-account name) and the code fails to invalidate the checkpoint when the slot's true owner/content changes, relying only on a coarse-grained diff (key membership) instead of value equality.

Additionally, `getConnectedAccounts` — the method actually consumed by the RPC/dApp bridge to decide what a connected origin can see — returns every wallet account's cached address regardless of the `walletAccount` field stored on the origin's own connection record, further widening what stale data an origin can be served: [6](#0-5) 

### Impact Explanation
If exploited, a previously-trusted origin (dApp) could be served an address (identity) belonging to a different, no-longer-existing account occupying the same `exodus_N` slot, because the cache is keyed by slot name and only invalidated on key-set changes, not content changes. In a wallet-account-isolation model, this breaks the assumption that the address exposed to a dApp accurately reflects the currently active identity for that account slot — a cross-account identity/privilege bleed within the trust boundary the origin/connected-accounts system is meant to enforce. This does not directly cause fund loss or unauthorized signing on its own (signing flows separately resolve addresses/keys at sign-time), which keeps the severity below the original wallet-compromise class, but it is a genuine violation of the "checkpoint on every ownership-relevant change" principle called out in the report's recommended mitigation.

### Likelihood Explanation
Triggering this requires an account-index reuse scenario (e.g., `fillIndexGapsOnCreation` re-populating a deleted slot with a new account) combined with a previously trusted/connected origin whose `connectedAccountsAtom` entry for that slot was already populated. This is a narrower trigger condition than the original C4 report (which required only ordinary vault `give()`), and I was not able to fully verify within the available index whether any downstream consumer (e.g. signing or WalletConnect/solana-provider flows) treats the cached `connectedAccounts` addresses as authoritative for authorization decisions beyond display — that would need further verification with full repository access.

### Recommendation
Invalidate/recompute the per-account cached address whenever the underlying `WalletAccount` object bound to a name changes in any way (not just when the set of names changes), e.g. by diffing full account objects (or a content hash/version) rather than `Object.keys()`. Additionally, `getConnectedAccounts` should respect and filter by the `walletAccount` scoping recorded on the origin's connection record instead of returning all cached accounts.

### Proof of Concept
1. Trust origin `dapp.example` with `connectedAssetName: 'ethereum'`; this populates `connectedAccountsAtom.exodus_1.addresses.ethereum` for the wallet account currently at slot `exodus_1`.
2. Disable/delete the wallet account at index 1, then create a wallet with `fillIndexGapsOnCreation: true` so a new, distinct account is assigned to the same slot name `exodus_1` (see `features/wallet-accounts/src/module/__tests__/index.test.ts:376-398` for the underlying gap-fill mechanism).
3. Because `Object.keys(walletAccounts)` is unchanged (`exodus_1` still present), `updateConnectedAccounts` treats the cache as up to date and never refreshes `connectedAccountsAtom.exodus_1.addresses`.
4. `getConnectedAccounts({ origin: 'dapp.example' })` returns the stale, previously-cached address for `exodus_1` even though it no longer corresponds to any live account occupying that slot. [1](#0-0) [3](#0-2)

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

export const getNextIndex = ({
  walletAccounts,
  seedId,
  source,
  compatibilityMode,
  fillIndexGapsOnCreation,
}: GetNextIndexParams) => {
  const existing = Object.values(walletAccounts)
    .filter(
      (w) =>
        w.source === source &&
        w.compatibilityMode === compatibilityMode &&
        w.seedId === seedId &&
        !w.id &&
        (!fillIndexGapsOnCreation || w.enabled)
    )
    .sort((a, b) => (a.index ?? 0) - (b.index ?? 0))

  if (fillIndexGapsOnCreation) {
    return (
      [...existing.keys()].find((i) => existing[Number(i)]?.index !== Number(i)) ?? existing.length
    )
  }

  const indexes = existing
    .map(({ index }) => index)
    .filter((i): i is number => typeof i === 'number')
  return Math.max(-1, ...indexes) + 1
}
