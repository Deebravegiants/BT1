### Title
Governance-set `OutboundConsensusDeliveryReward` (or the default of zero) can be too low to compensate relayers, permanently stalling a destination chain's BEEFY light client - ([File: modules/pallets/relayer/src/lib.rs])

### Summary
`pallet-relayer`'s `set_outbound_consensus_delivery_reward` lets a trusted admin (`RelayerOrigin`) set a per-destination `$BRIDGE` reward that compensates relayers for delivering *mandatory* authority-set rotation proofs to an EVM destination. This is functionally identical to Sentiment's `minDebt`/`minBorrow`: a governance-settable threshold that is supposed to keep an economic actor (there, a liquidator; here, a relayer) incentivized to perform a protocol-critical action. If the value is left at its documented default of zero, or set too low relative to the destination chain's gas costs, no relayer has an economic reason to submit the mandatory proof, and the destination's on-chain consensus client permanently falls behind.

### Finding Description
`OutboundConsensusDeliveryReward` is a `StorageMap<StateMachine, BalanceOf<T>>` whose documented default (`0`) explicitly means "rewards are off for the chain": [1](#0-0) 

It is set only through governance/admin action: [2](#0-1) 

The reward exists specifically to offset the gas cost of delivering *mandatory* (authority-set rotation) consensus proofs — messages that must land even when there is no compensating user fee, because skipping them causes the destination's client to desync: [3](#0-2) [4](#0-3) 

The relayer's own outbound pipeline confirms this dependency in code comments: without the mandatory rotation proof landing, "the destination's BEEFY light client stays at the old set_id, every subsequent messaging proof's signature verification fails, and the relayer can't deliver until a fresh mandatory proof arrives": [5](#0-4) 

The claim path (`claim_outbound_consensus_delivery_reward` → `process_outbound_consensus_delivery_claim`) explicitly rejects a claim if the configured reward is zero: [6](#0-5) 

This mirrors the Sentiment `minDebt`/`minBorrow` bug class exactly: a single admin-set numeric threshold that is meant to be adjustable across a wide range (including down to zero, per design), but whose value directly determines whether a self-interested actor is willing to perform an action the protocol depends on for solvency/liveness. In Sentiment, too-low `minDebt`/`minBorrow` removes liquidator incentive and lets bad debt accumulate. Here, too-low or zero `OutboundConsensusDeliveryReward` removes relayer incentive to submit mandatory rotation proofs on chains with infrequent user traffic (exactly the scenario the docs call out — "destinations that see infrequent user traffic would be unprofitable to keep up to date"), and the destination's on-chain BEEFY consensus client falls behind and stops accepting further Hyperbridge proofs.

### Impact Explanation
Once a destination is behind on authority-set rotations, no further messaging proof (from any application, including token bridges, intents, or bandwidth) can be verified against it until the missing rotation(s) land, because BEEFY signature verification is checked against the currently-known authority set. If nobody is economically motivated to submit the catch-up rotation (each rotation must typically be submitted in order, up to `MAX_CONSENSUS_PROOFS_PER_BATCH` per batch), the destination chain's route becomes permanently unable to deliver messages — a "route unable to deliver messages" freeze impacting every app relying on that destination. This is systemic: a single misconfigured/zero reward for one chain freezes the entire inbound message path to that chain until an operator manually funds/relays it altruistically or governance corrects the reward and someone chooses to catch up (potentially several sequential proofs deep).

### Likelihood Explanation
The default value of the reward is literally zero and is explicitly documented as "rewards are off for the chain" — this is not a hypothetical edge case but the out-of-the-box state for any destination until governance actively configures a reward. Any chain where governance forgets to set the reward, sets it too low relative to that chain's gas price, or a gas spike outpaces a previously-adequate reward, will experience this failure mode as soon as an authority-set rotation occurs and organic relayer traffic to that chain is otherwise unprofitable/absent.

### Recommendation
- Enforce a protocol-level floor so `OutboundConsensusDeliveryReward` cannot be set (or left) below a value that covers a conservative gas-cost estimate for the destination, or require it to be re-validated against current gas prices periodically.
- Alternatively, decouple mandatory rotation delivery from a single per-chain reward knob and make delivery permissionless/subsidized directly from protocol funds (similar to how request-level `OutboundRequestDeliveryReward` was designed with an explicit allowlist), so an admin oversight or a stale reward value cannot leave a chain permanently unable to receive proofs.
- Emit an alert/monitor when a destination's `OutboundConsensusDeliveryReward` is zero or when its BEEFY client falls behind by more than one rotation, so operators can intervene before the backlog compounds.

### Proof of Concept
1. Governance registers a new EVM destination but never calls `set_outbound_consensus_delivery_reward` (default remains `0`), or sets a reward far below the destination's actual gas cost for a 3-proof rotation batch.
2. Hyperbridge's validator set rotates (`ProofAccepted` with `new_set_id`), making delivery of the mandatory proof to that destination mandatory per `catch_up_rotations`/`submit_for_dest` logic [7](#0-6) .
3. Because the destination sees little organic user-message traffic and `OutboundConsensusDeliveryReward` for it is zero/too-low, no relayer is willing to front the gas cost purely for the (missing or inadequate) `$BRIDGE` reward — `process_outbound_consensus_delivery_claim` would reject a claim on a zero reward anyway [6](#0-5) .
4. The destination's on-chain `EvmHost` BEEFY client remains pinned at the old `set_id`. Every subsequent messaging proof signed by the new authority set fails signature verification on that destination.
5. The destination chain is now unable to receive any further Hyperbridge messages (token transfers, intents settlement, bandwidth purchases, etc.) until someone alters the reward and a relayer chooses to submit the backlog of rotation proofs — a protocol-level freeze of the message route to that chain.

### Mandatory vs opportunistic submissions

Not every accepted proof reaches every chain.

- **Authority-set rotations (mandatory).** When the Hyperbridge
  validator set rotates, every destination chain must be notified or
  its on-chain client will fall behind and stop accepting Hyperbridge
  proofs altogether. The outbound task always propagates these, even
  if there are no messages targeting that chain.
- **Messaging-only proofs (opportunistic).** When an accepted proof

  with no pending messages, avoiding gas on chains that gain nothing
  from the update.

## Mandatory consensus proof rewards (EVM chains)

When the outbound task delivers an authority-set rotation (a
*mandatory* consensus proof) to an EVM destination, the destination
