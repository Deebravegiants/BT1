### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the merchant/tenant identity (`shop`) from an HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body, never the `shop-domain` (or `x-shopify-shop-domain`) header. Since the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, any user who can install the app on their own store — an unprivileged action requiring no special credentials — can capture a legitimate, validly-signed webhook body and replay it with a forged `shop-domain` header pointing at a victim shop. The signature still validates because it never binds to the `shop` field, so the app's webhook handler will process the (possibly attacker-crafted) payload under the identity of a shop the attacker doesn't control.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` — which computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` — never includes `shop`, `topic`, `webhook_id`, or `api_version` in the signed material: [3](#0-2) 

Yet `Registry.process` trusts `request.shop` as the tenant identity when dispatching to the handler, after only checking `Utils::HmacValidator.validate(request)`: [4](#0-3) 

This breaks the identity binding: `shop header used to route/authorize webhook data` ≠ `shop field actually covered by the cryptographic signature`. Because the same `client_secret` is used by Shopify to sign webhooks for *every* shop that has installed a given app (it is not a per-shop secret), an attacker can:
1. Install the target app on their own Shopify store (an ordinary, unprivileged action).
2. Receive a legitimate webhook delivery to their own endpoint/proxy, capturing `raw_body` and the valid `shopify-hmac-sha256` header.
3. Replay that exact body + HMAC pair to the app's webhook endpoint, but substitute the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain.
4. `HmacValidator.validate` still returns `true` because the signature only ever covered `raw_body`, which is unchanged.
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is now the attacker-chosen victim domain, at line 198.

Any downstream logic that uses `WebhookMetadata#shop` to look up/act on tenant-scoped state (e.g., "delete this shop's data," "mark this shop's subscription cancelled," "update settings for this shop") will now execute for the victim shop using attacker-controlled body content, despite believing it received an authentic Shopify-signed event for that shop.

### Impact Explanation
This is a cross-tenant integrity/authenticity break: the webhook signature verified by the gem does not actually authenticate the shop the payload claims to be about. An attacker with no privileged access—only the ability to install the app on an account they control—can forge the shop identity on an otherwise-legitimately-signed webhook, causing the app to take shop-scoped actions (uninstall handling, data deletion, GDPR-style webhooks, order/product mutations relayed from webhook handlers, etc.) against a shop they do not control. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (a) ability to install the target Shopify app on an attacker-owned development/test store (routinely available, no special approval), and (b) knowledge that the shop-identifying header is not signed, which is evident directly from the gem's own `to_signable_string`/`HmacValidator` implementation. No leaked secrets, TLS interception, or social engineering are needed.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`/`webhook_id`) in the signed/verified material, or equivalently do not trust `request.shop` unless it is cryptographically bound to the signature. Since Shopify signs webhook bodies over the raw payload only (per Shopify's actual webhook HMAC spec, which is body-only), the safer remediation within this gem is to require callers/handlers to independently confirm that `request.shop` matches an already-known, previously-authenticated shop session (e.g., looked up via install records) before trusting it, rather than treating the passing HMAC check as proof that the `shop-domain` header is authentic.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`.
2. Trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and header `shopify-hmac-sha256: H` sent to the app's callback URL — `H` is valid because `HMAC(client_secret, B) == H`, per `HmacValidator.validate`/`compute_signature`: [5](#0-4) 
3. Resend the identical body `B` and header `shopify-hmac-sha256: H` to the app's webhook endpoint, but set `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` accepts the request (`HmacValidator.validate` passes because it never inspected `shop-domain`) and invokes the registered handler with `shop: "victim-shop.myshopify.com"`, per [4](#0-3) , causing the app to process attacker-controlled webhook content under the victim's tenant identity.
