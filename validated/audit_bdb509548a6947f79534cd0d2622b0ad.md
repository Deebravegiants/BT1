This confirms the key vulnerability: the webhook `hmac` in `to_signable_string` is computed **only over the raw request body**, while the `shop` field returned by `Webhooks::Request#shop` (lib/shopify_api/webhooks/request.rb:20-23) comes straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header — a field that is never included in the HMAC-signed payload.### Title
Webhook shop-domain attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value passed to app webhook handlers from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `HmacValidator` only covers the raw request body. The shop identity is therefore never bound to the cryptographic signature, breaking the equality `hmac_signed_bytes == bytes_used_to_attribute_the_tenant`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes and compares an HMAC over exactly that signable string against the `hmac` header: [2](#0-1)  and [3](#0-2) .

Once the HMAC check passes, the shop attribute used to attribute the webhook to a tenant, `request.shop`, is read straight from the unauthenticated `shop-domain` header: [4](#0-3) . That value is forwarded as-is into the handler payload: [5](#0-4) .

This is exactly the class of bug the report describes analogically: a field that is *acted on* (the `shop` used to key the webhook data/session lookup) is not part of the data that is *covered by the HMAC* (only `@raw_body` is signed). Contrast this with the OAuth callback flow, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, correctly binding shop identity to the signature: [6](#0-5) . The webhook path lacks this equivalent binding.

Because all webhooks for an app are signed with the same `api_secret_key` regardless of which shop triggered them, an attacker who controls a shop with the app installed (or who can otherwise obtain one legitimately-signed webhook body+HMAC pair, e.g. by triggering an event on their own store) can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` header value with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds (it only checks the body), and the host application's webhook handler will process/store the (attacker-controlled) body as if it originated from the victim shop.

### Impact Explanation
This crosses the tenant boundary defined in the rules: cross-tenant access via a field that is acted upon but not authenticated by the HMAC. Any host application that keys shop-scoped state (webhook idempotency records, order/customer records, session or install bookkeeping, mandatory GDPR redact handling, etc.) off `WebhookMetadata#shop`/`request.shop` can be made to associate attacker-controlled webhook payloads with a victim shop, since this gem provides no cryptographic binding between the claimed shop and the verified bytes.

### Likelihood Explanation
The attacker only needs the ability to have the app installed on any shop (a normal merchant/dev shop) in order to obtain a validly-signed body+HMAC, and needs to intercept/replay their own outbound webhook request to the app's endpoint with an edited header — both of which are within reach of an "unprivileged internet user" per the scope rules (no access token, no `api_secret_key`, no TLS interception of Shopify's traffic required — only editing of a header on their own outbound HTTP call to the app's webhook endpoint before the app receives it, e.g. via a local proxy).

### Recommendation
Include the shop domain (and ideally topic/api-version) as part of the signable payload verified by `HmacValidator`, or otherwise cryptographically bind `request.shop` to the verified HMAC (e.g., derive/verify shop identity independent of the unauthenticated header, similar to how `AuthQuery#to_signable_string` binds `shop`). At minimum, document prominently that `Webhooks::Request#shop` is unauthenticated and must not be trusted for tenant attribution without additional verification by the host application.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives (or triggers) a legitimately signed webhook request: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker intercepts their own outbound webhook call before it reaches the app's endpoint (e.g., local proxy) and rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping body `B` and HMAC `H` unchanged.
3. App receives the request; `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (== `B`) and matches `H` — validation succeeds: [2](#0-1) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, even though `victim-shop` never sent this webhook: [5](#0-4) .
