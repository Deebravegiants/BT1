### Title
Attacker-controlled HyperSwap V2 pre-seed can exceed `Bonding`'s fixed rebalance budget, forcing the graduation LP to seed at an off-curve-close ratio - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The GHSA-m4f3-qp2w-gwh6 class is: an attacker plants malicious/adversarial state on an asset ahead of time, and a later privileged-but-permissionless operation (Nova's `resize`) processes that state with an unrestricted/insufficiently-bounded operation, causing destructive results. In `Bonding.finalizeGraduation`, the analogous "later operation" is the permissionless LP-seeding into the HyperSwap V2 pair, and the "malicious pre-planted state" is an attacker-minted, heavily-imbalanced pre-seed of that same pair. The rebalance mechanism that is supposed to neutralize such a pre-seed caps its corrective swap at a **fixed budget derived only from the protocol's own graduation inventory** (`tokensForLP` ≤ 250M tokens, `ltFromPair` bounded by the curve's raise), not from the size of the attacker's pre-seed. An attacker who accumulates enough curve TOKEN (up to 750M sellable supply) and LT can mint a V2 position large enough that the corrective swap budget is insufficient to restore the curve-close ratio, so the graduation LP is permanently seeded off the curve-close price.

### Finding Description
`_seedRebalancing` handles a hostile "mint pre-seed" of the HyperSwap V2 `TOKEN/LT` pair (Regime 3) by swapping toward the curve-close ratio before depositing: [1](#0-0) 

The swap input is computed by `_noFeeSwapInput` and explicitly capped at `maxSwap`: [2](#0-1) 

`maxSwap` itself is derived only from `_swapBudget`, which is 99% of *this graduation's own inventory* — either the LT this graduation raised (`_ltSwapInventory`, bounded by `ltFromPair`) or the tokens reserved for the LP (`tokensForLP`, hard-capped at `LP_RESERVE = 250,000,000e18`): [3](#0-2) 

The natspec on `_swapBudget` explicitly acknowledges the assumption underpinning the design but does not enforce it — it only asserts that "for any realistic pre-seed `s_unconstrained` is orders of magnitude below `maxSwap`": [4](#0-3) 

Nothing on-chain actually bounds the size of the attacker's pre-seed relative to `maxSwap`. The V2 pair (`HyperSwapV2Factory.createPair` + `pair.mint`) is permissionless and reachable before `Lifecycle.Graduating` is entered — `_ensureUniswapV2Pair` will simply reuse whatever pair already exists: [5](#0-4) 

An unprivileged actor can:
1. Buy a large share of the curve's sellable 750M `TOKEN` supply via `Zap.buy`/`Bonding.buy` (curve TOKEN is available up to `CURVE_BPS = 7500` of `TOTAL_SUPPLY`), while the token is still `Lifecycle.Curve`.
2. Acquire LT (BounceTech mint/market) and mint an arbitrarily large, heavily skewed `TOKEN/LT` position directly into the HyperSwap V2 pair for this token (`IUniswapV2Pair.mint`), well before graduation.
3. Complete the buy that crosses the graduation threshold (or call `Bonding.triggerGraduation`), entering `Lifecycle.Graduating` and freezing `(tokensForLP, ltFromPair)` in `pendingGraduation` at the curve-close ratio.
4. Call the permissionless `finalizeGraduation`. Because `tokensForLP` is capped at 250M tokens and `ltFromPair` is capped by the curve's total raise (bounded near the fixed `graduationThresholdUsd`/`exchangeRate`), while the attacker's pre-seeded V2 reserves can be scaled arbitrarily higher (limited only by capital, not by any protocol-enforced ceiling), `_noFeeSwapInput`'s required `s` to reach the target ratio exceeds `maxSwap` and gets clamped. The clamped swap only partially corrects the ratio, and `_routerDepositAndDispose` then deposits Bonding's remaining balanced subset at the router's `quote()`-derived split — which reflects the **still-skewed, post-clamp pool ratio**, not the curve-close ratio: [6](#0-5) 

The resulting liquidity, minted to `LPLock` via `recordLock`, is therefore locked at a price materially different from the curve's closing price: [7](#0-6) 

### Impact Explanation
This is a concrete, permanent freezing/mispricing of protocol-controlled LP funds: the entire raised-LT and 250M-token LP allocation is deposited and irrevocably locked (`LPLock.recordLock` is documented elsewhere as a one-shot operation with no rescue path) at a ratio the attacker chose rather than the curve-close price. The attacker's own pre-existing V2 LP position captures the value differential — effectively extracting value from the honest curve buyers/creator's locked LP, satisfying the "LP seeded away from the curve close price" impact bucket called out for this contest.

### Likelihood Explanation
The attack requires capital (to acquire curve TOKEN and LT and mint a large V2 pre-seed) but no privileged access, no timing race with the keeper (the attacker seeds ahead of triggering graduation themselves), and no protocol bug beyond the unenforced sizing assumption in `_swapBudget`'s natspec. Every step — curve buy, HyperSwap `mint`, `triggerGraduation`, `finalizeGraduation` — is callable by any address, so likelihood is bounded only by capital cost, which scales sub-linearly with the fixed, small `LP_RESERVE`/raised-LT budget the protocol must defend.

### Recommendation
Do not size the rebalance budget solely off the protocol's own graduation inventory. Either (a) detect when the required corrective swap `s` (uncapped) exceeds a safety margin of `maxSwap` and fall back to a mode that protects the protocol's deposit (e.g., refuse to deposit into an existing, adversarially-sized pair and instead route the LP into a fresh pair/vault pending manual/owner remediation), or (b) bound how large a pre-graduation V2 pre-seed can legitimately be relative to `tokensForLP`/`ltFromPair` and treat any excess as hostile, aborting the direct deposit rather than depositing at the residual skewed ratio.

### Proof of Concept
1. Launch a token normally via `Zap.createToken` (curve enters `Lifecycle.Curve`).
2. As an unprivileged attacker, buy a large fraction of the 750M curve-sellable `TOKEN` supply via repeated `Zap.buy`/`Bonding.buy` calls, staying just below the graduation threshold.
3. Acquire a matching large amount of the LT reserve asset and call `IUniswapV2Factory.createPair(TOKEN, LT)` then `IUniswapV2Pair.mint(attacker)` to seed the V2 pair at a ratio wildly different from the curve's current price, using an amount that dwarfs `LP_RESERVE` (250M tokens) and the curve's bounded LT raise.
4. Execute the threshold-crossing buy (or call `Bonding.triggerGraduation`) to enter `Lifecycle.Graduating`, freezing `(tokensForLP, ltFromPair)`.
5. Call the permissionless `Bonding.finalizeGraduation(tokenAddress)`. Observe that `_pairRebalance`'s swap is clamped by `_swapBudget` (99% of the fixed `tokensForLP`/`ltFromPair` inventory), the post-swap ratio remains skewed toward the attacker's pre-seed, and `_routerDepositAndDispose` deposits at that skewed ratio — confirmable by comparing the resulting `TokenGraduated` liquidity/ratio against the curve's `Trade`-event closing price. The attacker's pre-existing LP now holds a disproportionate, favorably-priced share of the graduated pool.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    /// @dev Saturating subtract matches `_routerDepositAndDispose` so a
    ///      future violation of the `balanceOf >= protectedLT` invariant
    ///      can't brick `finalizeGraduation`.
    function _ltSwapInventory(
        address lt,
        uint256 protectedLT
    ) internal view returns (uint256) {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        return bal > protectedLT ? bal - protectedLT : 0;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
