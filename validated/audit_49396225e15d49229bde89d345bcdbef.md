### Title
Webhook `shop-domain` header is trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` authenticates the *body bytes* only. The shop-tenant identity that the handler acts on, `request.shop`, is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed string. This breaks the intended binding "shop the handler acts on == shop the HMAC authenticates."

### Finding Description
`Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

only `@raw_body` is returned - none of the Shopify headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) participate in the signable string. `Request#shop` simply reads the header: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately hands `request.shop` (the unauthenticated header) to the registered handler as the tenant identity: [3](#0-2) 

Compare this with the OAuth callback path, where the equivalent identity field (`shop`) *is* part of the signed string, `Oauth::AuthQuery#to_signable_string` includes `shop` alongside `code`, `host`, `state`, `timestamp`: [4](#0-3) 

This shows the gem is aware that fields used for tenant identification should be inside the signed payload, but for webhooks that guarantee only extends to the body, not the header that actually carries the "which shop is this for" claim.

The equality being broken is:
`shop asserted by request.shop (unauthenticated header)` == `shop authenticated by the HMAC (which only covers @raw_body)`

Before the attacker's action: for a legitimate Shopify-delivered webhook, header `shop-domain` and body both correspond to the same store, and HMAC(body, secret) matches.
After the attacker's action: an attacker who controls any shop that has the app installed (a fully unprivileged action - installing a free/trial app on their own store) receives a real webhook delivery with a valid `hmac-sha256` header computed by Shopify over a body they fully control/observe. They can replay that exact `raw_body` + `hmac-sha256` to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `topic`) with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only recomputes the HMAC over `@raw_body`, and `Registry.process` never cross-checks the header-derived `shop` against anything authenticated.

### Impact Explanation
This falls under the accepted High-severity class "cross-tenant access": the webhook handler executes application business logic (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` handlers, or any app-defined handler registered via `add_registration`) believing it is acting on behalf of an arbitrary shop of the attacker's choosing, while the only cryptographic guarantee provided by the gem is that *some* app-owned webhook body was signed by Shopify - it never states *which* store. Any host application that (reasonably, given the gem's API surface) uses `WebhookMetadata#shop` as the trusted tenant key for a redact/uninstall/data action is exposed to cross-tenant data manipulation using only an attacker-owned shop's own legitimately-delivered webhook as raw material.

### Likelihood Explanation
Likelihood is High: the attacker only needs the ability to install the app on a shop they control (a normal, unprivileged Shopify merchant action) and the ability to POST HTTP requests with modified headers, e.g. via `curl`, to the app's public webhook endpoint. No leaked credentials, TLS interception, or privileged access is needed - the `client_secret`/`api_secret_key` is never exposed and is not required by the attacker, since they reuse a genuinely-signed body/HMAC pair issued by Shopify to their own store.

### Recommendation
Include the tenant-identifying headers (`shop-domain` at minimum, and ideally `topic`, `webhook-id`) in the value that is HMAC-checked, or otherwise cryptographically bind them to the authenticated body before they are exposed via `Request#shop`/`WebhookMetadata#shop`. Concretely:
- Extend `Webhooks::Request#to_signable_string` to combine the raw body with the shop/topic headers before hashing, and validate against a canonicalized signable string that matches what Shopify guarantees, or
- If Shopify's delivered HMAC genuinely only covers the body (matching Shopify's actual webhook HMAC scheme), then `Registry.process` (or documentation for `WebhookHandler#handle`) must make explicit that `shop` is unauthenticated and must be cross-checked by the host application against a known/installed shop list before being trusted, and the gem should provide a helper to do that check rather than silently handing an unauthenticated field to handlers as if it were verified.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal unprivileged action).
2. Shopify delivers a genuine webhook, e.g. `orders/create`, to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(raw_body, api_secret_key)` and matches the (unmodified) `hmac-sha256` header, so validation passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., the app now executes webhook logic believing it pertains to `victim-shop.myshopify.com`, even though nothing about that value was ever authenticated: [6](#0-5)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
