### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature payload from the raw HTTP body only, while the `shop-domain` header — the value the gem uses to identify which merchant/tenant a webhook belongs to — is read separately and is never included in the signed material. `Registry.process` accepts any request whose HMAC matches the body, then forwards the unauthenticated `shop` header value to the app's handler as the tenant identifier.

### Finding Description
`VerifiableQuery` requires implementers to provide `hmac` and `to_signable_string`, and `HmacValidator.validate` recomputes the signature strictly from `to_signable_string` and compares it to the caller-supplied `hmac` [3](#0-2) .

For OAuth callbacks, `AuthQuery#to_signable_string` correctly folds `shop` into the signed string, so the shop claim is bound to the HMAC [4](#0-3) .

For webhooks, however, `Request#to_signable_string` returns only `@raw_body`, and `Request#shop` reads a separate header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never mixed into the signed string [5](#0-4) . `Registry.process` validates only the body/HMAC pair and then uses the unauthenticated `shop` header to build `WebhookMetadata`, which is the sole tenant identifier passed to the app's `WebhookHandler#handle` [2](#0-1) [6](#0-5) .

This breaks the identity binding `authenticated(shop) == shop_used_for_tenant_dispatch`. Because the app's shared `api_secret_key` is identical for every merchant using the app (it is not per-shop), any merchant who has the app installed on their own store legitimately receives HTTP webhook deliveries with a valid HMAC for a given raw body. That same merchant — an unprivileged holder of one legitimate tenant's webhook traffic, with no access to the app's secret or any other merchant's data — can resend the exact same body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will dispatch the payload to the handler tagged with the victim's shop, letting one tenant's traffic be attributed to a different tenant.

### Impact Explanation
This is a cross-tenant confusion: data that was only ever authenticated as "some payload signed with this app's secret" is delivered to the host application labeled as belonging to an arbitrary shop domain chosen by the attacker. Any host application that uses `WebhookMetadata#shop` (the field this gem's own documented interface exposes for exactly this purpose) to key data storage, trigger the correct tenant, or apply tenant-scoped side effects will process or store attacker-influenced data under another merchant's identity. This matches the Critical "cross-tenant access" impact bucket, since the tenant boundary the gem's `shop` attribute is meant to represent can be forged without any credential beyond legitimate access to one's own installed app.

### Likelihood Explanation
Likelihood is realistic: it requires no secret material, no privileged account, and no interception — only owning any shop where the target app is installed (a normal unprivileged merchant/developer relationship), capturing one real webhook delivery, and replaying it to the app's public endpoint with a modified header, which any HTTP client can do.

### Recommendation
Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the material verified against the HMAC, or independently verify that the shop domain in the request corresponds to a shop with an active, previously-established session/installation before dispatching `WebhookMetadata` to handlers, so the `shop` value returned to the app is cryptographically or record-bound rather than a bare, unauthenticated header value.

### Proof of Concept
1. App installs on `attacker.myshopify.com`; Shopify delivers a legitimate webhook, e.g. body `{"id":1}` with headers `x-shopify-hmac-sha256: <valid-hmac-for-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request and POSTs it again to the app's webhook endpoint, keeping the body and `x-shopify-hmac-sha256` unchanged but setting `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) and it matches, so validation succeeds [1](#0-0) .
4. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-controlled header value `"victim.myshopify.com"` and invokes the app's handler with it [7](#0-6) , causing the app to process/store the attacker's data as if it belonged to the victim shop.
