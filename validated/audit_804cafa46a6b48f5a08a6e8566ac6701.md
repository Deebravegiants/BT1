### Title
`EvmHost.dispatchIncoming(GetResponse)` reverts entire delivery when fee-token balance is insufficient to pay relayer, permanently blocking response delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` for `GetResponse` executes the destination module's `onGetResponse` callback and then unconditionally attempts `IERC20(feeToken()).safeTransfer(relayer, fee)` with no check that the host actually holds `fee` worth of the fee token. If the balance is insufficient, `safeTransfer` reverts, rolling back the entire transaction — including the already-successful application callback — exactly mirroring the `GmxAdapter.withdrawClosedSize()` root cause: an outbound fee push that assumes funds are always available.

### Finding Description
`dispatchIncoming(GetResponse memory response, address relayer)` is invoked by `HandlerV2` (restricted via `restrict(_hostParams.handler)`) whenever a relayer submits a valid GET-response proof: [1](#0-0) 

After the destination module's `onGetResponse` executes successfully, the function reads the escrowed fee metadata and pays it out with a bare `safeTransfer`:
```solidity
uint256 fee = _requestCommitments[commitment].fee;
if (fee != 0) {
    IERC20(feeToken()).safeTransfer(relayer, fee);
}
```
There is no check that `IERC20(feeToken()).balanceOf(address(this)) >= fee` before attempting the transfer, and no fallback path (unlike the `PostRequest` delivery path in the same file, which wraps the app callback in a low-level `.call()` and deletes the receipt on failure so it can be retried safely — see `dispatchIncoming(PostRequest...)`): [2](#0-1) 

Because the fee-payout line sits *after* the successful callback and is not wrapped in a similarly defensive pattern, any shortfall in the host's fee-token balance reverts the whole transaction, undoing the already-executed application state change. The host's fee-token balance is a single commingled pool used both for escrowed relayer fees (credited at `dispatch()`) and for protocol revenue withdrawable by governance via `withdraw()`: [3](#0-2) 

Nothing in the contract reserves/segregates the portion of the balance that is owed to pending GET-response fees from the portion considered "excess" protocol revenue. A `test_host_manager_insufficient_balance` test in the test-suite already demonstrates this exact failure mode reverting on the analogous `withdraw()` path when the ERC20 balance is short: [4](#0-3) 

The same unguarded-transfer pattern exists on the `GetResponse` fee payout, which is reachable by any relayer submitting a valid proof — not gated behind privileged/governance access.

### Impact Explanation
When the host's fee-token balance dips below the sum of outstanding relayer fees (e.g. due to governance `withdraw()` draining commingled balance, native-token/Uniswap-swap rounding during `dispatch()`, or any other balance drift), delivery of the corresponding GET response permanently reverts on every retry attempt, since the shortfall condition does not change between attempts. This is a "route unable to deliver messages" condition: the destination application's response can never be delivered/executed even though the underlying state proof is valid, and legitimate relayers cannot collect the fee they are owed for an otherwise successful proof submission. This qualifies as Medium-risk denial of message delivery / stuck protocol state, consistent with the original report's classification.

### Likelihood Explanation
Likelihood is moderate: it does not require a malicious actor, only a benign balance-accounting gap between escrowed relayer fees and protocol revenue that governance believes is "free" to withdraw, or minor swap/rounding drift from the native-token dispatch path. Any relayer submitting a legitimate GET-response proof exercises this code path, making the trigger condition (insufficient balance at payout time) fully attacker-independent and realistically reachable during normal operation once the fee-token pool is thin.

### Recommendation
Before calling `safeTransfer` in `dispatchIncoming(GetResponse...)` (and the analogous timeout refund paths), check `IERC20(feeToken()).balanceOf(address(this))` against the owed `fee` and either (a) cap the transfer to the available balance and emit an event flagging the shortfall for reconciliation, or (b) maintain an explicit "reserved for pending fees" accounting variable that `withdraw()` cannot dip into, so governance withdrawals can never leave the escrowed-fee pool underfunded. Additionally, consider decoupling the fee payout from the callback execution (e.g., wrap it so a payout failure doesn't roll back the already-successful `onGetResponse` state change), matching the defensive `.call()` + retry pattern already used for `PostRequest` delivery.

### Proof of Concept
1. Governance (via `HostManager.onAccept` → `EvmHost.withdraw`) withdraws fee-token revenue down to a level below the sum of currently escrowed `GetResponse` fees tracked in `_requestCommitments`.
2. A relayer submits a valid GET-response proof to `HandlerV2`, which calls `EvmHost.dispatchIncoming(GetResponse, relayer)`.
3. `onGetResponse` on the destination module executes successfully.
4. `IERC20(feeToken()).safeTransfer(relayer, fee)` reverts because `balanceOf(address(this)) < fee`.
5. The entire transaction reverts, discarding the destination module's state change; every subsequent retry hits the same shortfall and reverts identically, permanently blocking delivery of that response.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

fn test_host_manager_insufficient_balance() {

	let params = WithdrawalParams {
		beneficiary_address: H160::random().as_bytes().to_vec(),
		amount: SubstrateU256::from(500_000_000_000_000_000_000u128),
		token: H160::from_slice(env.fee_token.as_slice()),
	};

	let post = router::PostRequest {
		source: StateMachine::Kusama(2000),
		dest: StateMachine::Evm(1),
		nonce: 0,
		from: env.sender.as_slice().to_vec(),
		to: vec![],
		timeout_timestamp: 100,
		body: params.abi_encode().expect("20-byte beneficiary"),
	};
	let evm_request: EvmPostRequest = post.into();

	let host_addr = env.host;
	let calldata = onaccept_calldata(evm_request, env.sender);
	let err = env
		.call_as_may_revert(host_addr, manager, calldata)
		.expect_err("expected revert");

}
