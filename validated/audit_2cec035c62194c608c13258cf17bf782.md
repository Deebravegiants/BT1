## Custody Analog Found

### Title
Staking-contract reward/principal distribution can be permanently locked by a single unreceivable shareholder in a push-based payout loop - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
The Sherlock bug's root cause is a **push-based refund inside a fixed-capacity loop**: removing/settling one entry requires an external token transfer to an address the protocol does not control, and if that transfer can be made to fail (blacklist), the entire loop — and therefore all other participants' funds — becomes permanently stuck. The Aptos-native analog is `staking_contract::distribute_internal`, which iterates over every shareholder in a `Pool` and pushes `AptosCoin` to each one via `aptos_account::deposit_coins` inside a single atomic `while` loop.

### Finding Description
`distribute_internal` withdraws all withdrawable stake first, then loops: [1](#0-0) 

For every shareholder it calls `distribution_pool.redeem_shares(...)` (which mutates the in-memory pool state) and then `aptos_account::deposit_coins(recipient, ...)`. `deposit_coins` will abort if the recipient account doesn't exist/isn't registered for `AptosCoin` and has explicitly disabled direct transfers via `set_allow_direct_coin_transfers(false)`: [2](#0-1) 

Because the whole `distribute`/`distribute_internal` call is a single Move transaction, an abort on **any** recipient's deposit reverts the entire transaction — including the `stake::withdraw_with_cap` and all `redeem_shares` calls for every *other* shareholder in the same pool. There is no partial-progress or pull-based fallback: the only override present is `beneficiary_for_operator`, which lets the *operator's* payout be redirected, but the *staker's* payout (added via `add_distribution` for principal/withdrawals) has no such redirection mechanism: [3](#0-2) 

Since the `OwnerCapability` for the underlying stake pool is permanently custodied inside the `StakingContract` resource (the staker never holds it directly), the staker has **no alternative path** to withdraw once `distribute()` cannot succeed: [4](#0-3) 

This mirrors the exact custody invariant broken in the Plaza report: a single recipient in a shared settlement loop can make itself permanently un-payable, and because the settlement is all-or-nothing and push-based, this blocks every other legitimate shareholder in the same pool from ever settling.

### Impact Explanation
If the operator's payout address (or, if `add_distribution` is also used to queue staker payouts through this same pool — which the `Pool`/`buy_in` API and the shared `distribution_pool` field structurally allow) is made unable to receive `AptosCoin` (unregistered account + `allow_arbitrary_coin_transfers = false`), then `distribute()` for that `(staker, operator)` pair can never succeed again. The staker's already-unlocked (inactive) stake is then **permanently locked** inside the resource-account-controlled stake pool with no recovery path, matching the "Permanent lock or non-recoverable loss of ... resource-account-held value" custody-impact category.

### Likelihood Explanation
Likelihood is moderate rather than trivially high: the attacker must control or coerce the address that becomes a shareholder in the `distribution_pool` (typically the operator, which the staker chooses and trusts to some degree). I was not able to fully confirm within the available search budget whether `add_distribution` is also invoked with the **staker's own address** as `recipient` on unlock (which would make this a griefing vector purely from the operator side against an otherwise-uninvolved staker) versus only for operator commission. This detail materially affects severity and should be verified by reading all call sites of `add_distribution` (e.g., in `unlock_stake`/`request_commission`) before treating this as confirmed-critical.

### Recommendation
Convert the payout mechanism in `distribute_internal` from push to pull: instead of calling `aptos_account::deposit_coins` inside the loop, credit each shareholder's redeemed amount to a per-address claimable balance (e.g., a `Table<address, u64>` or individual escrow), and let each shareholder withdraw independently via a separate entry function. This isolates a single unreceivable address's failure from all other shareholders, exactly as the Plaza Finance fix did (PR converting push refunds to pull claims).

### Proof of Concept
Not independently constructed/run — this analysis is based on static code tracing of `distribute_internal`, `aptos_account::deposit_coins`, and `set_allow_direct_coin_transfers`, not an executed Move test. A concrete PoC would need to:
1. Create a `staking_contract` between a staker and an operator.
2. Have the operator's beneficiary/commission address call `aptos_account::set_allow_direct_coin_transfers(false)` while remaining unregistered for `AptosCoin`.
3. Accumulate rewards/unlock stake, then call `staking_contract::distribute` and observe the abort.
4. Confirm no other entry point can extract the staker's inactive stake once this state is reached.

Given I could not fully verify point (2)'s exact shareholder set (staker vs. operator-only) within the available tool budget, this should be treated as a **high-confidence candidate requiring one more verification pass** on `add_distribution`'s call sites before being reported as a fully confirmed critical finding.
