### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) Headers Are Trusted Without Being Covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC of the raw request body, then blindly trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are **not** part of the signed payload. An attacker who can produce (or intercept) any body+HMAC pair that validates against the app's secret — most simply, a real webhook that Shopify sent for a shop the attacker legitimately controls — can resend that exact body/HMAC to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header. The HMAC will still validate (it only signs the body), and the handler will process the data under the attacker-chosen `shop` value, breaking the binding `shop authenticated == shop the data is attributed to`.

### Finding Description
The webhook `Request` object exposes `shop`, `topic`, `webhook_id`, and `api_version` purely from headers: [1](#0-0) 

Its `to_signable_string` — the value that is actually HMAC-verified — only covers the raw body, not any of the headers: [2](#0-1) 

`HmacValidator.validate` computes the signature strictly from `to_signable_string`: [3](#0-2) 

`Registry.process` uses the HMAC result as the sole authentication gate, then forwards the unauthenticated `request.shop` (along with `topic`, `webhook_id`, `api_version`) straight into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant/event identity: [4](#0-3) 

The identity binding that should hold is: **`shop` value trusted by the handler == `shop` value cryptographically bound to the signed body**. Because the header is outside the signed content, this binding does not hold — the gem authenticates the body but attributes it to whatever `shop` header accompanies the request.

### Impact Explanation
This enables cross-tenant data confusion: an attacker who owns/controls their own Shopify store can trigger a webhook of a topic the target app also registers, capture the resulting valid `(body, hmac)` pair, and replay it against the same app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. The app's registered handler (`WebhookHandler#handle`) receives `WebhookMetadata` claiming the data belongs to the victim shop, even though it never originated there. Depending on what the host application does with `data.shop` (e.g., looking up sessions, updating per-tenant records, gating billing/compliance events such as `customers/redact` or `shop/redact`), this can lead to cross-tenant data corruption or a spoofed compliance/administrative action attributed to the wrong shop — matching the High-impact "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires the attacker to obtain one genuine `(body, hmac)` pair signed with the app's secret. This is trivially achievable by installing the target app on a shop the attacker controls (a normal, unprivileged action) and capturing any webhook it triggers, then replaying it with a modified `shop` header at the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to be a merchant/tenant of the app, which is the standard unprivileged-attacker model for this class of report.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed content instead of trusting bare headers:
- Include the `shop` domain (and topic) in the value passed to `to_signable_string`/HMAC comparison, or
- Cross-check `request.shop` against an application-level registry of shops that installed the app (session store) before invoking the handler, rejecting requests where the header-derived shop isn't an expected/registered tenant, and
- Document clearly that host applications must not rely on the `shop` header alone as an identity boundary without this additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook event the app subscribes to (e.g. `orders/create`). Shopify sends the app a valid request:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw body, computed with app's real secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   body: {"id": 1, ...}
   ```
2. Attacker captures this exact `body` and `x-shopify-hmac-sha256` value (network capture on their own traffic, or from app logs if exposed).
3. Attacker resends the identical body and HMAC header to the same webhook endpoint, but sets:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the secret — validation succeeds: [5](#0-4) 
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from that shop, letting the attacker inject/replay data attributed to a shop they don't control.
