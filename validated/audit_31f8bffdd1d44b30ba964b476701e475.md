### Title
Unconstrained `calldataHash` public signal allows proof replay with different fee/relay/hook/external-action data - (File: `circuits/MainEVMCircuit.circom`, `circuits/MainEVMCircuitMin.circom`, `contracts/HinkalHelper.sol`)

### Summary
`calldataHash` is declared as a circuit input and is fed into the SNARK public-input vector via `formBasicInput`/`formInputEmporiumMin`, but it is never used inside any circuit constraint in `MainEVMCircuit.circom` or `MainEVMCircuitMin.circom`. Because it is a "dangling" public signal with no algebraic link to any other signal, a previously generated valid proof will still verify against a different `calldataHash` value, since it is not tied to any R1CS constraint.

### Finding Description
`CircomDataBuilder.formBasicInput` inserts `circomData.calldataHash` directly into the `uint256[] input` array that is passed to the verifier as a public input [1](#0-0) . `getHashedCalldata` computes this hash on-chain from the ancillary fields of `CircomData` — `externalActionData`, `hookData`, `feeStructure`, `relay`, `slippageValues`, `onChainCreation`, `originalSender`, `extraData`, `encryptedOutputs`, `onChainEncryptedOutput` — none of which are part of `getSignedMessageHash` or the core circuit constraints [2](#0-1) . `HinkalHelper.performHinkalChecks` only verifies that this recomputed hash equals `circomData.calldataHash` on-chain [3](#0-2) .

However, inside `MainEVMCircuit.circom`, `signal input calldataHash;` is declared but never appears on either side of any `<==` or `===` constraint anywhere else in the template [4](#0-3) . The same is true of `MainEVMCircuitMin.circom`, whose only real constraint is `message <== Poseidon(1)([messageSeed]);`, entirely independent of `calldataHash` [5](#0-4) .

In Groth16 (and PLONK) circuits generated by circom, a public signal whose column is zero in every constraint matrix contributes nothing to the verification equation: the corresponding `vk.IC` term is derived from an all-zero linear combination, so multiplying it by any input value yields the same (identity) contribution to `vk_x`. Concretely, this means the proof verification result is independent of the actual value supplied for `calldataHash` — a witness/proof generated once remains valid for *any* `calldataHash` value substituted at verification time.

This breaks the intended equality: "the SNARK proof is bound to the full `CircomData`, including its ancillary/fee/hook/relay fields via `calldataHash`." In reality the proof is only cryptographically bound to the core transaction fields (`rootHashHinkal`, `erc20TokenAddresses`, `amountChanges`, `inNullifiers`, `outCommitments`, stealth-address fields, `signedMessageHash`) — the ancillary fields are only checked by a Solidity `keccak256` recomputation, and the "link" of that hash into the actual proof is a no-op.

### Impact Explanation
An attacker who has captured a single valid `(proof, circomData)` pair (e.g., their own past transaction, or one submitted through a relay) can construct a new `circomData` that keeps the core proof-bound fields identical (same nullifiers, same commitments, same amounts, same root, same stealth address, same `signedMessageHash`) but freely rewrites the ancillary fields that are only covered by `calldataHash`:
- `feeStructure` (increase `variableRate`/`flatFee` to steal more from the recipient, or redirect `feeToken`),
- `relay` (redirect relay fee payout to attacker-controlled relay address),
- `hookData` (point `postHookContract`/`preHookContract` at attacker contracts that receive `circomData` in `afterTransact`),
- `externalActionData` (change `externalActionMetadata` or target a different registered external action, since `externalActionMap` lookup is by `externalActionId`, not proof-bound),
- `originalSender`.

Because `getHashedCalldata` is recomputed from these attacker-chosen fields, the on-chain check passes trivially, and the (unconstrained) `calldataHash` public input can be set to match — the same proof will verify. This allows theft/redirection of protocol or relay fees and execution of hook/external-action calls that the original prover never authorized, satisfying the "High" impact bar (theft of protocol/relay fees, unauthorized asset movement/calls).

### Likelihood Explanation
Any relayer or any user who has visibility into a previously submitted `(proof, circomData)` pair (all of this data is emitted on-chain, e.g., via `NewCommitment`/`Nullified` events and the calldata itself is public on L1) can attempt this without needing any privileged role, admin key, or another user's private key — it only requires reusing already-public proof bytes with modified ancillary calldata fields. The barrier is understanding that `calldataHash` is unconstrained, which is a subtle but verifiable circuit-design flaw rather than a runtime race condition.

### Recommendation
Add an explicit constraint inside `MainEVMCircuit.circom` (and `MainEVMCircuitMin.circom`) that binds `calldataHash` to the witness, e.g. incorporate it into the `message`/`signedMessageHash` computation or otherwise force it through a non-trivial arithmetic constraint (e.g., `calldataHash * 1 === calldataHash` is insufficient — it must be combined with signals that are otherwise constrained, such as folding it into the Poseidon hash that produces `message`, or including it as an operand in the signature/message hash check). Re-audit every public signal declared in both circuit templates to ensure each one is actually used in at least one constraint before being trusted as a security boundary.

### Proof of Concept
1. Attacker observes a valid Hinkal transaction on-chain: `(proof, circomData_A)` where `circomData_A.feeStructure = {flatFee: 0, variableRate: 10}`, `relay = relayA`.
2. Attacker crafts `circomData_B` identical to `circomData_A` in all core fields (`rootHashHinkal`, `erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `outCommitments`, `timeStamp`, stealth address fields) but with `feeStructure = {flatFee: 0, variableRate: 10000}` (max fee) and `relay = attackerRelay`.
3. Attacker computes `calldataHash_B = CircomDataBuilder.getHashedCalldata(circomData_B)` off-chain (pure function, no secrets needed) and sets `circomData_B.calldataHash = calldataHash_B`.
4. Attacker submits `transact(circomData_B, proof)` reusing the *original* `proof` bytes (unchanged, since it was generated for `circomData_A`'s core witness).
5. `HinkalHelper.performHinkalChecks` passes: `getHashedCalldata(circomData_B) == circomData_B.calldataHash` ✓ [3](#0-2) .
6. `formInputForCircom`/`formBasicInput` produces a public input array identical to the one used at proof-generation time except for the `calldataHash` slot [6](#0-5) .
7. Because `calldataHash` is unconstrained in `MainEVMCircuit.circom`, the Groth16/PLONK verifier accepts `proof` against this new public input array despite the different `calldataHash` value.
8. `_internalTransact`/relay fee logic in `contracts/Hinkal.sol` then executes using `circomData_B.feeStructure` and `circomData_B.relay`, over-paying `attackerRelay` at `variableRate = 10000` (100%) — full theft of the recipient's withdrawal to the attacker-controlled relay [7](#0-6) .

(Note: I was unable to locate a `component main {public [...]}` declaration file in the indexed repo content, which normally fixes the exact list of public vs. private signals for the compiled circuit; this may be generated by a build script outside the index. This does not affect the core finding, since `calldataHash` is documented as a public parameter in the file's own header comment and is treated as such by all on-chain callers, but it is flagged here as an area I could not directly verify from the indexed files.)

    function formBasicInput(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData,
        uint256[] memory input,
        uint256 index,
        uint256 emporiumMessage
    ) internal pure returns (uint256[] memory) {
        // 1) First we list public inputs as in the body of the main template (not the one with exact dimensions)
        input[index++] = circomData.stealthAddressStructure.H1x;
        input[index++] = circomData.stealthAddressStructure.H1y;
        input[index++] = circomData.stealthAddressStructure.stealthAddress;
        input[index++] = emporiumMessage; // this is for Emporium message signature verification

        // 2) Then we list the private inputs as in the body of the main template
        input[index++] = circomData.rootHashHinkal;
        input[index++] = getSignedMessageHash(
            chainId,
            verifyingContract,
            circomData,
            emporiumMessage
        );

        for (uint16 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            input[index++] = uint256(
                uint160(circomData.erc20TokenAddresses[i])
            );
        }

        for (uint16 i = 0; i < circomData.amountChanges.length; i++) {
            require(
                circomData.amountChanges[i] < MAX_AMOUNT &&
                    circomData.amountChanges[i] > -1 * MAX_AMOUNT,
                "amount changed is too large"
            );

            input[index++] = circomData.amountChanges[i] >= 0
                ? uint256(circomData.amountChanges[i])
                : CIRCOM_P - uint256(-circomData.amountChanges[i]);
        }

        for (uint16 i = 0; i < circomData.inputNullifiers.length; i++) {
            for (uint16 j = 0; j < circomData.inputNullifiers[i].length; j++) {
                input[index++] = circomData.inputNullifiers[i][j];
            }
        }

        input[index++] = circomData.timeStamp;

        for (uint16 i = 0; i < circomData.outCommitments.length; i++) {
            for (uint16 j = 0; j < circomData.outCommitments[i].length; j++) {
                input[index++] = circomData.outCommitments[i][j];
            }
        }
        input[index++] = circomData.calldataHash;

        input[index++] = circomData.stealthAddressStructure.H0x;
        input[index++] = circomData.stealthAddressStructure.H0y;

        return input;
    }
