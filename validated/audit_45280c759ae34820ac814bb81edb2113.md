### Title
Omni Bridge `describeWithdrawal()` Trusts Positional Array Index Into Unsorted Transfer List, Causing Cross-Withdrawal Status/Hash Misreport - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.describeWithdrawal()` fetches all transfers for a NEAR transaction hash and picks the one at `args.index` without validating that this transfer actually belongs to the withdrawal being queried (no check against `recipient`, `token_id`, or `amount`). The codebase already fixed this exact bug class for the PoA bridge — matching by `assetId` instead of array index, because "the response list is unsorted" [1](#0-0)  — but the identical unsafe pattern remains in the Omni Bridge implementation.

### Finding Description
For batch withdrawals, the SDK assigns each withdrawal a purely positional, per-bridge `index` based on its order in the caller-supplied `withdrawalParams` array: [2](#0-1) .

`OmniBridge.createWithdrawalIdentifier()` stores this `index` directly on the `WithdrawalIdentifier` with no additional binding data (no transfer ID, no recipient hash): [3](#0-2) .

`describeWithdrawal()` then retrieves the transfer at that same index from the externally-returned array and reports its `txHash` as the outcome of the local withdrawal, with no cross-check against `recipient`/`destinationAddress`, `token_id`/`assetId`, or `amount`: [4](#0-3) 

This assumes an equality that is never validated: `getTransfer(transactionHash)[index]` (external, indexer-ordered data) === "the withdrawal the caller submitted at position `index`" (local, submission-ordered data). The PoA bridge's own comment and regression test prove this equality does not generally hold for these bridge indexers, since results can be returned unsorted relative to submission order: [5](#0-4) 

Because different destination chains finalize at very different speeds (e.g., an EVM transfer vs. a UTXO transfer bundled in the same NEAR transaction), the Omni Bridge indexer has no inherent reason to return transfers in the same order they were submitted, particularly once some are `finalised` and others are still `Initialised`. A caller polling `describeWithdrawal` for "their" withdrawal (index 0) can therefore receive another withdrawal's (index 1's) `recipient`-derived chain classification and `txHash` as the reported completion.

### Impact Explanation
This is a status/hash misreport, not a self-inflicted loss: an integrator that batches multiple withdrawals to different destinations/assets in one NEAR transaction and relies on `describeWithdrawal`/`waitForWithdrawalCompletion` to confirm "withdrawal N is completed with tx hash H" can be told the wrong `txHash` belongs to the wrong withdrawal. This can make an integrator credit or reconcile a user's withdrawal against a transaction that actually paid a different recipient, or fail to detect that the real destination for that index is still pending while treating it as settled — matching the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
No privileged access is required — any user of the SDK who submits multiple withdrawals in one intent execution (a supported, documented flow — see batch `estimateWithdrawalFee`/`processWithdrawal` examples in the README) can trigger this simply by mixing destination chains/assets with different finalization latencies through the Omni Bridge route, exactly the scenario the PoA bridge fix explicitly guards against.

### Recommendation
In `OmniBridge.describeWithdrawal()`, do not index blindly into `getTransfer()`'s result. Match the transfer using stable, verifiable fields supplied at withdrawal-identifier creation time (e.g., `recipient` compared against `destinationAddress`, and `token_id`/`amount` compared against `assetId`/expected amount), analogous to how `findMatchingWithdrawal` disambiguates PoA withdrawals by `assetId`/`near_token_id` rather than index.

### Proof of Concept
1. Attacker/integrator submits one NEAR transaction batching two Omni Bridge withdrawals: withdrawal #0 to `recipientA` (slow-finalizing UTXO chain) and withdrawal #1 to `recipientB` (fast-finalizing EVM chain).
2. `createWithdrawalIdentifiers` assigns `index: 0` to A and `index: 1` to B based on array order: [2](#0-1) .
3. The Omni Bridge indexer, however, returns the array with B (finalized first) before A once queried, e.g. `[transferB, transferA]`.
4. `describeWithdrawal({..., index: 0})` for A executes `(await getTransfer(...))[0]`, which is actually `transferB`, and returns `transferB`'s recipient-chain classification and `txHash` as if it were A's completion: [6](#0-5) .
5. The integrator records A as completed with B's destination transaction hash — a status/hash misreport for a different, unrelated withdrawal.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
