### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the handler is invoked with are read straight from unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are not part of the signed bytes: [3](#0-2) .

`Registry.process` validates the HMAC and then passes `request.shop`, `request.topic`, and other header-derived values straight to the application's webhook handler as trusted metadata: [4](#0-3) .

This is the same class of bug as the report: an identity-bearing field (`shop`) is *acted on* by the library (used to identify which tenant the event belongs to) but is not covered by the cryptographic check (`hmac`) that is supposed to authenticate the whole request. The equality that should hold is:

`shop used to attribute webhook data == shop cryptographically bound to the signed payload`

but instead the gem only enforces `hmac(raw_body) == valid`, leaving `shop` (and `topic`/`webhook_id`) completely unauthenticated.

### Impact Explanation
Since a merchant/attacker who installs the app on their own store receives legitimately HMAC-signed webhook deliveries for their own shop (the secret is the app's shared secret, not something the attacker controls, but the *headers* Shopify sends alongside a valid signed body are attacker-observable and, since the endpoint is a plain HTTP endpoint reachable from the internet, an attacker who controls the request to the app's webhook URL can replay a validly-signed body while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain or a different topic. Because `Registry.process` never checks that the header-derived `shop`/`topic` correspond to anything cryptographically bound to the signature, the host application's webhook handler will process attacker-supplied data as if it belongs to, or was addressed to, a different tenant (cross-tenant confusion), potentially triggering tenant-scoped side effects (e.g. data deletion/redaction handlers such as `shop/redact` or `customers/redact`, or app-uninstall cleanup) against the wrong shop.

### Likelihood Explanation
Exploitation requires the attacker to be able to send an HTTP POST with attacker-chosen headers to the app's public webhook endpoint (any unprivileged internet user can do this, since the endpoint by design accepts unauthenticated Shopify-originated POSTs) and to have obtained at least one validly-signed body/HMAC pair (trivially available to anyone who installs the app on a shop they control, since Shopify will send them signed webhooks for their own store). No access token, `client_secret`, or privileged credentials are required.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-signed material (or otherwise cryptographically verify them, e.g. by confirming `shop` against a known/registered shop record after signature validation) rather than trusting header values purely because the raw body's HMAC matched. At minimum, `Registry.process` should cross-check that the shop associated with the webhook is one the app actually has an active session/installation for before dispatching to handlers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic to receive a body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (correctly computed by Shopify over `B` with the app's real secret).
2. Attacker sends `POST /webhooks` to the target app with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only covers `B`), but `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `Utils::HmacValidator.validate` succeeds because it only checks `hmac(B)` [5](#0-4) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the spoofed `shop`/`topic` values [6](#0-5) , causing the host application to act on `victim.myshopify.com` using attacker-supplied data.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
