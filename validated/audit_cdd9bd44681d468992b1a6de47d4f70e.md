### Title
Panic-inducing arithmetic underflow in `calc_take_pnl` reachable via ordinary Deposit/Withdraw, permanently bricking pool funds - (File: `program/src/processor.rs`)

### Summary
The quic-go advisory describes a nil-pointer dereference triggered when an internal invariant assumed by loss-recovery code (that certain packet/ACK bookkeeping stays consistent) is violated by attacker-influenced state, causing an unchecked dereference to panic. The analogous bug class here is an **unchecked arithmetic operation (`.unwrap()` on `checked_sub`) whose safety depends on an invariant that is validated using a numerically inconsistent proxy check**, in `Processor::calc_take_pnl` [1](#0-0) .

### Finding Description
`calc_take_pnl` guards the PnL-taking branch with:
```
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
``` [2](#0-1) 

This check is intended to guarantee `x2 <= x1` and `y2 <= y1` before the code unconditionally executes:
```
let diff_x = U128::from(x1.checked_sub(x2).unwrap().as_u128());
let diff_y = U128::from(y1.checked_sub(y2).unwrap().as_u128());
``` [3](#0-2) 

However, `pool_pc_amount`/`pool_coin_amount` are raw vault token amounts, while `calc_pc_amount`/`calc_coin_amount` are derived from `target.calc_pnl_x`/`calc_pnl_y` via `Calculator::restore_decimal`, which performs truncating fixed-point multiplication/division through `sys_decimal_value` and `10^native_decimal` [4](#0-3) . Meanwhile `x2`/`x1`/`y1`/`y2` used in the subtraction are computed in the *normalized* (`sys_decimal_value`) domain via `Calculator::calc_x_power` and `integer_sqrt` [5](#0-4) . Because the guard comparison and the actual subtraction operate on values produced through two different, independently-rounding decimal conversion paths, repeated truncation (accumulated over many ordinary Deposit/Withdraw/Swap calls that mutate `total_pc_without_take_pnl`/`total_coin_without_take_pnl` and `calc_pnl_x`/`calc_pnl_y`) can desynchronize the two representations enough that the guard passes (`pool_pc*pool_coin >= calc_pc*calc_coin`) while the normalized-domain computation nonetheless yields `x2 > x1` or `y2 > y1`. In that case `checked_sub(...).unwrap()` on lines 213/214 panics.

`calc_take_pnl` is invoked from `process_deposit` and `process_withdraw` [6](#0-5) [7](#0-6) , both reachable by any unprivileged liquidity provider through a single transaction with attacker-chosen amounts, with no privileged signer required.

### Impact Explanation
A panic inside `calc_take_pnl` aborts the enclosing transaction (Solana reverts all state changes on panic), so it does not directly mint or drain funds. But because the desynchronization between the two decimal-rounding paths accumulates monotonically with normal pool activity (every swap/deposit/withdraw nudges `calc_pnl_x/y` and the vault balances independently), once the pool state crosses into the inconsistent zone, **every subsequent Deposit and Withdraw call that reaches `calc_take_pnl` will panic identically**, since the underlying stored `calc_pnl_x`/`calc_pnl_y` and vault balances are unaffected by the aborted transaction. This produces a permanent denial-of-service for LP withdrawals/deposits on that pool — a form of permanent freezing of LP funds (LPs can no longer withdraw their principal through `Withdraw`, and `WithdrawPnl`/`Deposit` paths that also route through PnL-related decimal math are similarly exposed).

### Likelihood Explanation
Likelihood is moderate-to-low without a concrete numeric counterexample: the rounding-path mismatch is real (two independent truncating decimal conversions guarding an unwrap), but I was not able to construct or verify concrete amounts/decimals that flip the guard while breaching `x2<=x1`/`y2<=y1` within this analysis session. This is analogous to the quic-go issue in that it requires a specific, non-adversarially-obvious sequence of state-mutating operations (swaps/deposits across different mints/decimals) to desynchronize an invariant that is normally assumed to hold by construction.

### Recommendation
- Compute the guard comparison and the `x2`/`y2` derivation in the same fixed-point domain and with the same rounding direction as `calc_pnl_x`/`calc_pnl_y`, rather than mixing raw vault amounts with restored-decimal amounts.
- Replace the panicking `.unwrap()` calls in `calc_take_pnl` (lines 213–214 and related sites in `process_deposit`/`process_withdraw`) with `checked_sub().ok_or(AmmError::CalcPnlError)?`, so an invariant violation returns a graceful program error instead of panicking, and add a fallback (e.g., skip PnL-taking for that call) so LPs can still withdraw/deposit even if PnL-taking cannot be computed.
- Add fuzzing/property tests analogous to the quic-go patch's randomized packet-sequence test, generating randomized sequences of Swap/Deposit/Withdraw calls with varying decimals to verify `calc_take_pnl` never panics.

### Proof of Concept
Not constructed with concrete numeric inputs in this session — the finding is a structural/root-cause analysis of the mismatched rounding domains guarding an `unwrap()`-based subtraction reachable from unprivileged `Deposit`/`Withdraw` instructions. A full PoC would require simulating many `SwapBaseIn`/`SwapBaseOut`/`Deposit`/`Withdraw` calls with asymmetric coin/pc decimals to accumulate truncation drift between `pool_pc_amount*pool_coin_amount` and `calc_pc_amount*calc_coin_amount` until the guard at [2](#0-1)  passes while `x2 > x1` or `y2 > y1`, then issuing a further `Deposit`/`Withdraw` to trigger the panic at [3](#0-2) .

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }
