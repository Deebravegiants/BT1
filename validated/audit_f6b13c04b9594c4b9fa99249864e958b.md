### Title
`recapitalize` refunds unfunded "excess" from pool custody while crediting phantom cash — (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`ops::recapitalize::apply` credits the pool's `cash` book with `min(amount, backing_shortfall)` and then unconditionally transfers `amount - applied` back to the caller-supplied `payer`. The function never verifies that the controller (or anyone) actually transferred `amount` into the pool first — it trusts the bookkeeping. This is the exact analog of the QV "poolAmount not decreased after distribution" bug: an accounting figure (`cash`) is mutated independently of real token flows, so the book and custody diverge. An unprivileged caller who invokes `recapitalize` without funding it either drains existing custody as a "refund" (theft) or leaves `cash` overstated so that later withdrawals/liquidations revert inside the SAC transfer (funds stuck), exactly as demonstrated by `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3407-3483`. ### Finding Description
In `accounting`, `applied = amount.min(backing_shortfall(&cache))` is credited to the cash book via `cache.credit_cash(applied)` and committed, while `refund = amount - applied` is computed for the refund leg [3](#0-2) . `apply` then pays `refund` to `payer` from the pool's own balance via `outcome.cache.transfer_out(&payer, outcome.refund)` [4](#0-3) . Two consequences fall out of the missing custody check:

1. **On a healthy market** (`backing_shortfall == 0`): `applied = 0`, `refund = amount`. A caller passing `payer = self` and `amount` equal to the pool's token balance receives the entire custody as a "refund" for tokens never deposited. The test proves this path: `t.client().recapitalize(&hub(&t.asset), &payer, &custody)` leaves `token.balance(&t.pool) == 0` with the payer having sent nothing [5](#0-4) .
2. **On a shortfall market**: `applied` is booked into `cash` without matching custody. Because `require_reserves` and the utilization/solvency guards read the book rather than the balance (`contracts/pool/src/ops/withdraw.rs:111-118` debits `cache.debit_cash` after guards that consult `cash`), subsequent `withdraw`/`claim_revenue` calls pass every pool guard and then revert inside the SAC `transfer` with `BalanceError = 10`, permanently blocking exits [6](#0-5) [7](#0-6) .

### Impact Explanation
Two acceptable impact classes are hit: (a) theft of user funds — suppliers' deposited tokens can be drained by an unfunded recap call that pays the "refund" out of real custody; and (b) permanent freezing of funds — once custody is drained or `cash` is overstated, every supplier withdrawal reverts inside the token transfer, so remaining supplier principal is unrecoverable. The book-vs-custody divergence is structural: `cash` is credited/debited purely from arguments, never reconciled against `token.balance(pool)`.

### Likelihood Explanation
`recapitalize` is listed among the externally reachable entrypoints and the pool function takes `payer` as an arbitrary caller-supplied `Address` — the refund goes wherever the caller points it. On any market with zero backing shortfall (the normal state of a healthy market), a single call with `amount = pool balance` suffices. No privileged role, timing window, or multi-step setup is required beyond reachability of the entrypoint; the only residual uncertainty is whether the pool contract restricts `recapitalize` to the controller address (not fully verified in this pass — the controller-side caller in `contracts/controller/src/markets.rs` was not read). If the entrypoint is permissionless as the test harness exercises it, likelihood is high. Even if controller-gated, the controller's own recapitalize path does not establish that tokens moved before `credit_cash` is committed — the pool still trusts rather than measures.

### Recommendation
Measure the injection instead of trusting the declared amount:

```rust
let before = token::Client::new(env, &cache.params().asset_id)
    .balance(&env.current_contract_address());
// ... caller transfers amount in ...
let received = balance_after - before;
let applied = received.min(guards::backing_shortfall(&cache));
cache.credit_cash(applied);
// refund only what was actually received in excess of applied
```

Alternatively, split the flow: require the payer's token transfer into the pool to be provably bound to the call (e.g., have `recapitalize` pull the tokens via `transfer_from`/`require_auth` on `payer`), and never pay a `refund` exceeding the measured delta. At minimum, revert when `refund > 0` would exceed the actual inflow, and add an invariant check that `cash <= token.balance(pool)` at commit time.

### Proof of Concept
1. Supplier deposits 10,000 units; `cash == balance(pool) == 10_000`.
2. Market has no backing shortfall (healthy market): `backing_shortfall == 0`.
3. Attacker calls `pool.recapitalize(hub_asset, payer = attacker, amount = 10_000)` sending zero tokens.
4. `accounting` computes `applied = 0`, `refund = 10_000`; `apply` calls `transfer_out(attacker, 10_000)` — the pool's full custody moves to the attacker while `cash` still reads ≥ 10,000.
5. The legitimate supplier calls `withdraw(i128::MAX)`: `require_reserves` passes (book claims the cash exists), then the SAC transfer aborts with `BalanceError = 10`. All supplier exits revert permanently.

This is the exact scenario codified in `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3407-3483`), which asserts custody hits zero, the book still overstates it, and the withdraw fails inside the SAC transfer rather than any pool guard.

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();

    RecapitalizationOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: applied,
        },
        refund,
    }
}

/// After an unfunded refund, `cash` overstates custody. `Cache::require_reserves`
/// reads the book, not the balance, so it admits exits that then fail inside
/// the SAC transfer. The market reports itself solvent and cannot pay.
#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );
