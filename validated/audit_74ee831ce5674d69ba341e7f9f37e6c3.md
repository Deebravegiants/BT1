## Title
Webhook shop identity spoofing — HMAC covers only the raw body, not the `shop-domain` header used to attribute webhook events - (File: lib/shopify_api/webhooks/request.rb)

## Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is passed to webhook handlers from an HTTP header, while the HMAC signature that `Registry.process` validates only covers the raw request body. This breaks the equality `shop used by the handler == shop that produced the signed bytes`, allowing an attacker who can generate a validly-signed webhook body (e.g., by installing the target app on their own shop) to relabel that signed body as coming from a different, victim shop.

## Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) is read straight from an HTTP header that is never part of the signed material: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC over that signable string (the body) and, once it passes, forwards `request.shop` and `request.topic` directly into the handler's metadata without any check that the shop actually matches whichever shop's secret produced the signature: [4](#0-3) 

`HmacValidator.validate` itself only ever validates `verifiable_query.hmac` against `verifiable_query.to_signable_string`, so any field outside `to_signable_string` — here, the shop header — is unauthenticated: [5](#0-4) 

The vulnerable equality: the code implicitly trusts `shop_header == shop_that_signed_the_body`, but the HMAC only proves `hmac == HMAC(secret, raw_body)`; it proves nothing about which shop the body belongs to. Since a single app uses one `api_secret_key` shared across *all* shops that install it, any merchant who installs the app on their own (attacker-controlled) store can trigger a webhook, capture the resulting `(raw_body, hmac)` pair signed with the app's real secret, and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to a victim shop's domain. `HmacValidator.validate` will still succeed because the body/hmac pair is genuinely valid for that secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

## Impact Explanation
This is a cross-tenant identity confusion: application logic that trusts `WebhookMetadata#shop` (e.g., to look up/update a specific merchant's session, data, or billing state) can be made to act on the wrong tenant using data an attacker fully controls (their own shop's genuine webhook), because the shop attribution is not bound to the signature. This matches the Critical "cross-tenant access" impact category.

## Likelihood Explanation
Exploitation only requires installing the target app once on an attacker-owned/free development store (a normal, low-privilege action available to any developer), triggering any webhook topic the app subscribes to, capturing the raw body + HMAC pair, and re-posting it to the app's webhook endpoint with a modified shop header — no access to the app's `api_secret_key`, tokens, or the victim's credentials is needed.

## Recommendation
Bind shop identity into the signed material, or otherwise cryptographically tie the header-derived shop to the request that produced the HMAC (e.g., require the app to independently verify `request.shop` against a webhook subscription registered for that specific shop/topic/webhook_id combination before trusting it, rather than trusting the header value on its own once the body HMAC passes).

## Proof of Concept
1. Attacker creates/uses their own dev shop `attacker.myshopify.com` and installs the target app (legitimately obtaining webhook deliveries signed with the app's real `api_secret_key`).
2. Attacker triggers a subscribed webhook topic (e.g., `orders/create`) on their own shop and captures the POST request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC(api_secret_key, B)`).
3. Attacker resends this exact request to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `HMAC(api_secret_key, B) == H`, ignoring the shop header entirely.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` calls the registered handler with `shop: "victim-shop.myshopify.com"`, causing the app to perform whatever business logic the handler implements (e.g., record creation, cache invalidation, billing/order side effects) attributed to the victim shop instead of the attacker's own.
