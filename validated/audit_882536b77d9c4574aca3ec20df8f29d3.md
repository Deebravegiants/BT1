## Title
Webhook Shop-Domain Header Is Not Covered by the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the shop identity used for tenant dispatch is read from an unsigned HTTP header. Any holder of one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — such as a merchant who has legitimately installed the app on their own store and thus receives real, correctly-signed webhooks — can replay that exact body/HMAC pair while substituting a different `shopify-shop-domain` / `x-shopify-shop-domain` header. `Registry.process` accepts the request because the HMAC check only validates body integrity, then dispatches the payload to the app's handler under the attacker-chosen shop identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled from HTTP headers that are never part of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC (`Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`, i.e. the body) and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata handed to the app's registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field — for webhooks this signable string is only the body: [4](#0-3) 

The broken identity binding, stated as an equality that the code assumes but never enforces:

`shop_the_HMAC_was_computed_for == shop_used_for_tenant_dispatch (request.shop)`

In reality, `HMAC(secret, body)` proves only "some party holding the shared `api_secret_key` produced this exact body" — it says nothing about which shop that body was originally destined for. Because all shops installing the same app share the same `api_secret_key`, a valid `(body, hmac)` pair captured from one tenant's genuine webhook remains valid when replayed with a forged `shop-domain` header pointing at a different tenant. `Registry.process` and the resulting `WebhookMetadata` (built from `request.shop`) have no way to detect this substitution, since the header is outside the signed content.

### Impact Explanation
This is a cross-tenant identity-binding break: the webhook body (and any tenant-scoped side effects the host application performs based on `data.shop`, e.g. writing to the target shop's data store, revoking access, applying GDPR redaction actions for `shop/redact`/`customers/redact`/`customers/data_request`, etc.) can be attributed to an arbitrary shop that the attacker does not control, purely because the shop header rides outside the cryptographic envelope. Given the impact criteria call out "cross-tenant access" as Critical, and this flaw lets one tenant's authenticated webhook traffic be relabeled to affect another tenant's data/processing path, this constitutes a cross-tenant access vulnerability rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant/installer of the target app (an "unprivileged internet user" relative to other tenants) who can capture one of their own genuine webhook deliveries (trivial — install the app, trigger any webhook topic, capture the raw request) and replay it with a modified `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or any other privileged material is required, and no interaction with Shopify's own trust boundary is needed beyond being an app installer, which is the normal, expected access level for this attack surface.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the signature verification, not just the body. Concretely, extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) so the shop domain, topic, and webhook id are included in the material the HMAC is computed/verified over — mirroring how OAuth's `AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` together: [5](#0-4) 
If Shopify's actual webhook HMAC scheme signs only the body (as it does today upstream), then `Registry.process` cannot rely on the header alone for tenant identity and should require the consuming application to independently cross-check `request.shop` against an authenticated/known session before acting — the library should not silently hand an unauthenticated `shop` value into `WebhookMetadata` as if it were verified.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, which shares the app's single `api_secret_key` with all other installs.
2. Attacker triggers any webhook topic (e.g. `orders/create`) and captures the raw POST: body `B`, and header `x-shopify-hmac-sha256: H` where `H = HMAC(api_secret_key, B)`, along with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body `B` and `H` to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, B)` — which still equals `H` since only the body is signed — and returns `true`, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb` (`to_signable_string` returns only `@raw_body`).
5. `Registry.process` proceeds to call the registered handler with `WebhookMetadata` built using `shop: request.shop`, i.e. `"victim-shop.myshopify.com"`, even though that shop never sent this webhook — the request is now processed as if it belonged to the victim tenant.
