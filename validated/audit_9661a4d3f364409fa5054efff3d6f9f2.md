### Title
Webhook `shop` identity is taken from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then dispatches to the app's handler using a `shop` value read directly from the `x-shopify-shop-domain` header. That header is never included in the signed material, so the "which shop does this payload belong to" claim is unauthenticated even though the overall request passes HMAC verification.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it with `secure_compare`: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `shop-domain` header, which is part of `@headers` but is never mixed into `to_signable_string`: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body authenticity) before forwarding `request.shop` verbatim to the registered handler as the tenant identifier: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but does not:
`shop_bound_by_hmac(raw_body) == shop_delivered_to_handler(request.shop)`
Since `to_signable_string` is `raw_body` alone, the left side is undefined/independent of the `shop-domain` header, while the right side is taken directly from that same unauthenticated header. A valid HMAC only proves "this body was signed with `api_secret_key`" — it proves nothing about which shop the header claims it came from.

### Impact Explanation
`api_secret_key` is shared across every shop that installs the same app. Any merchant who installs the app can legitimately trigger events on their own store (e.g. edit an order note, update a product, add a customer) and thereby obtain a genuinely Shopify-signed `(raw_body, hmac)` pair for content they control. Because the `shop-domain` header is outside the signed scope, that attacker-obtained `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Registry.process` will accept it (HMAC still validates) and hand the handler a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain paired with attacker-controlled body content. Any host application following the library's documented dispatch flow and trusting `data.shop`/`data.body` together (e.g., to update per-shop state, sync order/customer data, or drive `shop/redact`-style logic) processes forged, cross-tenant data — a tenant-boundary violation stemming entirely from this gem's own webhook verification/dispatch code.

### Likelihood Explanation
Exploitability requires only: (1) the attacker's own legitimate install of the target app (a normal, unprivileged merchant relationship, not a leaked credential), and (2) the ability to make an HTTP POST to the app's public webhook endpoint with a modified header — both trivially available to any app-installing user. No access token, `client_secret`, or privileged access is needed.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the signed material used for verification, or independently bind `request.shop` to a value cryptographically derived from the signed payload (e.g., verify that `shop-domain` matches a value embedded in/derived from the HMAC-covered content) before it is trusted by `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) with attacker-controlled body content.
2. Capture the legitimate `raw_body` and its valid `x-shopify-hmac-sha256` value sent by Shopify (same `api_secret_key` is used for all shops of the app).
3. Replay a POST to the app's webhook endpoint with the identical `raw_body`/`hmac` header but `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-31`) since only the body is checked; `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though that shop never sent this payload.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
