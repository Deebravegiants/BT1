### Title
Missing re-initialization guard in `LockupContract::new` allows unauthorized takeover and theft of locked/vested NEAR - (File: `lockup/src/lib.rs`)

### Summary
The lockup contract's `#[init]` function `new()` never checks `env::state_exists()` before overwriting contract state, unlike every other initializer in the codebase (`whitelist/src/lib.rs`, `staking-pool/src/lib.rs`, `multisig/src/lib.rs`, `staking-pool-factory/src/lib.rs`, `voting/src/lib.rs`). Since NEAR contract calls do not require the caller to hold access keys of the receiver account, any unprivileged account can call `new` again on an already-deployed and already-initialized lockup contract, completely overwriting `owner_account_id`, `vesting_information`, `transfers_information`, `lockup_duration`, and `foundation_account_id`.

### Finding Description
`LockupContract::new` at [1](#0-0)  is annotated with `#[init]` but performs no check that the contract is already initialized. Compare this to the pattern used everywhere else in the codebase, e.g. `whitelist/src/lib.rs`: [2](#0-1) 
and `staking-pool/src/lib.rs`: [3](#0-2) 
and `multisig/src/lib.rs`: [4](#0-3) 

In NEAR, calling a contract method (`new` included) only requires targeting the receiver account ID in a `FunctionCall` action; it does not require possession of that account's access keys. Because `LockupContract::new` is a plain public `#[init]` method with no `state_exists` guard, any unprivileged external account can call:

```
near call <lockup_account> new '{"owner_account_id": "<attacker>", "lockup_duration": "0", "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "0"}}, "vesting_schedule": null, "release_duration": null, "staking_pool_whitelist_account_id": "<any-valid-account>", "foundation_account_id": null}' --accountId <attacker>
```

This completely overwrites the `LockupContract` struct, setting `owner_account_id` to the attacker's account, `lockup_information.lockup_amount` to the current account balance (i.e., all previously locked funds), and `transfers_information` to `TransfersEnabled` with `transfers_timestamp: 0` and `lockup_duration: 0`, meaning tokens are unlocked immediately. Note `lockup_information.lockup_amount` is recomputed from `env::account_balance()` on every call to `new`, so it re-captures whatever balance is currently on the lockup account, including all previously deposited/locked funds - and also nullifies any prior `vesting_information`/`termination` state, erasing NEAR Foundation's vesting termination rights.

Once re-initialized, the attacker (now `owner_account_id`) can immediately call the owner-only `transfer` function: [5](#0-4) 
which only checks `self.assert_owner()`, `assert_transfers_enabled()`, `assert_no_staking_or_idle()`, `assert_no_termination()`, and available liquid balance - all satisfied by the attacker's crafted init arguments - draining the entire contract balance to any address the attacker chooses.

### Impact Explanation
This is a Critical impact per the scope's "Unauthorized transfer, withdrawal, spending, or release of locked, vested, pooled, or multisig-controlled NEAR through public-call... accounting failure reachable by an unprivileged user," and also "Permanent... irrevocable loss of user or protocol funds in lockup release... flows." An unprivileged attacker can seize ownership of any deployed lockup contract and steal all locked/vested NEAR tokens held by it, and simultaneously erase the NEAR Foundation's ability to terminate vesting for that account (since `vesting_information`/`foundation_account_id` are reset).

### Likelihood Explanation
High/certain likelihood: the vulnerable `new` method is a standard public contract entrypoint with no authorization check whatsoever, callable by any account on NEAR at any time after the lockup contract is deployed and funded. No privileged role, secret, or race condition is required — a single unprivileged transaction from any account suffices.

### Recommendation
Add the same guard used elsewhere in the codebase as the first statement of `LockupContract::new`:
```rust
assert!(!env::state_exists(), "The contract has already been initialized");
```
This mirrors the existing pattern in `whitelist/src/lib.rs`, `staking-pool/src/lib.rs`, `multisig/src/lib.rs`, `staking-pool-factory/src/lib.rs`, and `voting/src/lib.rs`.

### Proof of Concept
1. Deploy and initialize the lockup contract normally (e.g. via `lockup-factory`), funding it with N NEAR, with `owner_account_id = victim`.
2. An unprivileged attacker account calls:
```
near call <lockup_account_id> new '{
  "owner_account_id": "attacker.near",
  "lockup_duration": "0",
  "lockup_timestamp": null,
  "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "0"}},
  "vesting_schedule": null,
  "release_duration": null,
  "staking_pool_whitelist_account_id": "whitelist.near",
  "foundation_account_id": null
}' --accountId attacker.near --gas=25000000000000
```
This succeeds because `new()` at [1](#0-0)  has no `state_exists` check, and overwrites `owner_account_id` to `attacker.near`, with `lockup_information.lockup_amount` set to the full current balance and transfers unlocked immediately (`lockup_duration = 0`, `transfers_timestamp = 0`).
3. Attacker then calls:
```
near call <lockup_account_id> transfer '{"amount": "<full_balance_minus_storage>", "receiver_id": "attacker.near"}' --accountId attacker.near --gas=50000000000000
```
`assert_owner()` in `transfer` (line 468 of `owner.rs`) now passes because `owner_account_id == attacker.near`, and the full locked/vested balance is transferred to the attacker.
