### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook by verifying an HMAC over the raw request body only, while the `shop` value that the gem hands to the application's webhook handler (used to attribute the webhook, and therefore any tenant-scoped action, to a merchant) is read from an HTTP header that is never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header, with no cryptographic binding to that value: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` claim: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards `request.shop` — the unauthenticated header value — straight into `WebhookMetadata`, which is the tenant-identifying value passed to the application's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`hmac == HMAC(secret, signable_string)` **and** `signable_string` must determine (or include) `shop`.

What actually holds is:
`hmac == HMAC(secret, raw_body)` **while** `shop` is read independently from a header outside `raw_body`.

Because the header is disjoint from the signed body, any request whose body+HMAC pair is valid for *some* shop (e.g., a webhook the attacker's own store legitimately received, or a body they can otherwise obtain with a matching valid HMAC for their own tenant) can be replayed to the same endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop domain. `Registry.process` will accept it — the HMAC check passes because it only checked the body — and the handler will be invoked believing the event belongs to the victim shop. This is the same structural defect as the M-19 report: a value that is *acted upon* (there: vote weight; here: tenant identity) is not the value that is actually *covered* by the cryptographic check (there: sum vs. sum-of-squares; here: header vs. signed body).

### Impact Explanation
Any application built on this gem that trusts `WebhookMetadata#shop` to select the tenant/session/store record to mutate (a documented, intended usage pattern — see `docs/usage/webhooks.md` and the `WebhookHandler#handle(data:)` contract) can be made to apply an attacker-controlled body to a victim shop's data merely by sending a POST with a forged `Shop-Domain` header and *any* raw_body/HMAC pair that is valid under the app's secret for the attacker's own registered webhook. This is a cross-tenant identity confusion at the boundary the gem is responsible for authenticating — the exact function `Request`/`Registry` exist to provide.

### Likelihood Explanation
The attacker needs no privileged credentials: they only need to control (or install) the app on their own store to obtain at least one genuine, valid `raw_body` + `hmac` pair for a topic of interest (e.g., `customers/data_request`, `orders/create`, etc.), then replay that exact byte-for-byte body/HMAC to the app's public webhook endpoint while swapping only the `Shop-Domain` header value to the victim's domain. No secret, token, or the app's `client_secret` is required — the header is simply never checked.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the signed material used for verification, or otherwise cryptographically tie the header to the payload before trusting it. At minimum, `to_signable_string` (or an equivalent check inside `Registry.process`) should incorporate the shop-domain header so that a mismatch between the header-derived shop and the shop implied by the signed body/HMAC context causes rejection, mirroring how `AuthQuery#to_signable_string` includes `shop` in its own signable string for the OAuth callback.

### Proof of Concept
1. Install the app (as an attacker) on `attacker.myshopify.com` and register a webhook (e.g. `customers/data_request`) so Shopify delivers a legitimately-signed request to the app's endpoint: headers include `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and some `raw_body`.
2. Capture that exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Replay an HTTP POST to the same webhook endpoint with the identical `raw_body`/`X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body`, which is unchanged (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the application to act on the victim tenant using attacker-supplied data — a cross-tenant data/action injection with no credential beyond running the attacker's own installed instance of the app.

          received_signature = verifiable_query.hmac
