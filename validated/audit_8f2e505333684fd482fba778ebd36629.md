## Title
Beefy consensus client silently defaults the ISMP overlay root to zero when the ISMP digest is missing, persisting an unsound state commitment that permanently blocks message delivery for that height - (File: `modules/ismp/clients/beefy/src/consensus.rs`)

### Summary
`BeefyConsensusClient::verify_consensus` derives two values from a verified parachain header's digest logs: `timestamp` and `overlay_root`, both initialized to zero/default before the digest scan. The code explicitly validates that `timestamp` was actually found (`if timestamp == 0 { Err(BeefyError::TimestampNotFound) }`), but performs **no equivalent check for `overlay_root`**. If the scanned header's digest logs do not contain an `ISMP_ID` consensus log, `overlay_root` silently remains `H256::default()` (zero) and is committed to intermediate state as `overlay_root: Some(overlay_root)` — a "valid" `Some` value indistinguishable downstream from a correctly-derived root.

### Finding Description
In `modules/ismp/clients/beefy/src/consensus.rs`: [1](#0-0) 

`timestamp` and `overlay_root` are both initialized to zero-valued defaults at line 124, and only overwritten inside the digest-log loop if the corresponding `DigestItem::Consensus` entry is present. The `TimestampNotFound` guard at line 148-150 proves the developers recognized that an unset/default value must not be committed as legitimate consensus data — but the identical hazard for `overlay_root` has no such guard. The resulting `StateCommitmentHeight` is persisted directly: [2](#0-1) 

Downstream, every substrate-family `StateMachineClient::verify_membership` / `verify_non_membership` implementation trusts this `overlay_root` field as the authoritative ISMP child-trie root for that state commitment height, e.g.: [3](#0-2) 

and the relayer fee-accumulation path does the same: [4](#0-3) 

Both call sites only check `Option::is_some()` (`.ok_or(...)`) — they cannot distinguish "correctly extracted root" from "default zero root silently substituted because the digest was absent." Once a state commitment for a given height is stored with the wrong (zero) `overlay_root`, it becomes the permanent value returned by `state_machine_commitment` for that height; it is never re-derived. Any subsequent genuine ISMP request/response commitment or receipt proof for that height — which lives at the chain's *real* (non-zero) overlay root — can never be verified: `verify_membership` will fail (the honest root won't match the corrupted stored root) and `verify_non_membership`/timeout proofs will fail identically, since neither can be checked against the wrong root.

### Impact Explanation
This is a "route unable to deliver messages" / permanent freezing scenario: any POST/GET request or response committed at a parachain height whose header digest omitted (or the client failed to observe) the `ISMP_ID` consensus log becomes permanently unprovable — neither delivery (membership) nor non-delivery/timeout (non-membership) can ever be established for that height, because the trusted root recorded on-chain no longer matches the chain's actual overlay root. Funds locked in escrow contracts (e.g., token bridge or intents-solver flows) awaiting proof of delivery or timeout at that height become permanently stuck, since no future proof submission can ever satisfy the corrupted root. This qualifies as concrete permanent freezing of funds / unsound state commitment as defined in-scope.

### Likelihood Explanation
Reachability requires no attacker privilege beyond being a normal relayer submitting a valid BEEFY (or SP1) consensus proof containing a legitimately-finalized parachain header whose digest log set omits the ISMP consensus item (e.g., due to upgrade windows, block-production edge cases, a tracked parachain not yet running pallet-ismp at that height, or any code path in the source chain that skips `deposit_log` for `ISMP_ID` on a particular block). Since header content is authenticated via the real BEEFY/MMR signature, this is not a forgeable-by-relayer condition, but it is a plausible operational condition the client fails to guard against, unlike the parallel `timestamp` case that is explicitly checked.

### Recommendation
Mirror the existing `TimestampNotFound` pattern for `overlay_root`: track whether the `ISMP_ID` digest was actually observed (e.g., via an `Option<H256>` instead of a zero-initialized default), and reject the parachain header with a dedicated error (e.g. `OverlayRootNotFound`) if it was not, exactly as `BeefyError::TimestampNotFound` does today at `modules/ismp/clients/beefy/src/consensus.rs:148-150`.

### Proof of Concept
1. A tracked parachain produces a finalized block whose digest logs include the `ISMP_TIMESTAMP_ID` log but omit the `ISMP_ID` consensus log (any real-world condition causing this, e.g. temporary runtime misconfiguration).
2. A relayer submits the corresponding BEEFY/MMR consensus proof to `BeefyConsensusClient::verify_consensus`.
3. `overlay_root` remains `H256::default()` throughout the loop at `consensus.rs:124-147`; the `timestamp != 0` check passes since the timestamp digest was present.
4. `StateCommitmentHeight { commitment: StateCommitment { overlay_root: Some(H256::zero()), .. }, .. }` is stored for that height via the intermediates map (`consensus.rs:161-172`).
5. Any later relayer submits a genuine membership proof for a request commitment against that height; `SubstrateStateMachine::verify_membership` (`modules/ismp/state-machines/substrate/src/lib.rs:140-143`) selects `root = Some(H256::zero())` and the trie lookup against the honest storage proof fails because the real overlay root differs from zero — the request can never be proven delivered or timed-out at that height, permanently freezing any escrowed funds gated on that proof.
