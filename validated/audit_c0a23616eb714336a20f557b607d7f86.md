### Title
Auto-Generated Wallet Passphrase Derived Solely From Device RNG Is Stored Unencrypted Alongside The Seed It Protects - (File: features/wallet/module/wallet.js)

### Summary
When a Hydra-based wallet is configured with `useAutoGeneratedPassword: true`, the mnemonic seed is not protected by a user-chosen password. Instead, `@exodus/wallet` generates a "passphrase" using nothing but the platform RNG and persists that passphrase, unencrypted, in the very same storage namespace as the passphrase-encrypted seed. Anyone who can read the underlying storage layer (e.g. the browser-extension's `unsafeStorage`, a device backup, or any storage exfiltration) recovers both the encryption key and the ciphertext, fully defeating the encryption.

### Finding Description
`genPassphrase` derives the "master" passphrase used to encrypt the seed purely from `randomBytes(32)`, with no user-supplied entropy: [1](#0-0) 

`Wallet#setSeed` uses this auto-generated passphrase (when `usePassword && useAutoGeneratedPassword && !passphrase`) to encrypt the seed, and separately persists the raw passphrase value itself under `GENERATED_PASSPHRASE_KEY` in the same `walletStorage` — but that write is made **without** passing `{ passphrase }`, so it goes through the storage's unencrypted code path: [2](#0-1) 

The concrete storage adapter used for this purpose (`@exodus/browser-extension-adapters/seco-storage`) only encrypts a value when a `passphrase` option is explicitly supplied to `set()`; otherwise it falls straight through to the raw underlying storage: [3](#0-2) 

The SDK documentation confirms this is by design: `seedStorage` is described as holding both "seed and autogenerated passphrase (if present)" in the same storage instance: [4](#0-3) 

Consequently, the key material that "protects" the seed is (1) derived solely from device randomness — exactly the weakness class described in the external report — and (2) stored unencrypted right next to the ciphertext it decrypts, which is strictly worse than the reported scenario, since no additional secret (password, keychain-gated hardware key, etc.) is required at all to decrypt the seed once the storage is read.

### Impact Explanation
Any actor capable of reading the raw storage backing `seedStorage` (e.g., a malicious/compromised browser extension co-installed in the same browser profile that can read `chrome.storage.local`, a stolen device backup, or any bug that exposes storage contents) can retrieve `GENERATED_PASSPHRASE_KEY` in plaintext and immediately decrypt `SEED_KEY`, obtaining the full BIP-39 mnemonic. This is a direct wallet-compromise: total loss of funds with no further secret (PIN, password, biometric) required, since the "protection" the auto-generated passphrase adds is defeated by its own storage location.

### Likelihood Explanation
This path is only active when a consuming Hydra app is configured with `usePassword: true` and `useAutoGeneratedPassword: true` (e.g., in "no password" wallet UX flows) — confirmed exercised in the feature's own test matrix: [5](#0-4) 

For any deployment using this configuration on browser extension or similar storage that isn't independently OS-encrypted, the passphrase and seed live in the same accessible storage, so exploitation only requires local storage read access rather than a jailbreak/root, making this at least as likely as — and in practice easier to exploit than — the original reported issue.

### Recommendation
Do not store the auto-generated passphrase in the same storage/namespace as the data it encrypts, and do not rely purely on RNG-derived material as the sole protection for the seed when `useAutoGeneratedPassword` is enabled:
- Store the auto-generated passphrase in a genuinely separate, higher-trust boundary (e.g., platform keychain/secure enclave with hardware-backed access control), never as plaintext in the same storage instance as `SEED_KEY`.
- Where a real user password is available, always mix it into the KDF used to derive the storage key, per the external report's Argon2id-based recommendation, rather than falling back entirely to `useAutoGeneratedPassword`.
- Audit all `seedStorage`/`walletStorage` consumers (browser extension `seco-storage`, mobile `keystore-mobile`, etc.) to guarantee that any auto-generated secret protecting the seed is never persisted unencrypted alongside the ciphertext it protects.

### Proof of Concept
1. Initialize `@exodus/wallet` with `config: { usePassword: true, useAutoGeneratedPassword: true }` and call `wallet.create()` without a `passphrase` (mirrors `features/wallet/module/__tests__/index.test.js` matrix entry `{ usePassword: true, useAutoGeneratedPassword: true }`).
2. Internally, `#setSeed` calls `genPassphrase()` (`randomBytes(32).toString('base64')`) and stores it via `walletStorage.set(GENERATED_PASSPHRASE_KEY, passphrase)` with no `{ passphrase }` option, and stores the seed via `walletStorage.set(SEED_KEY, seed, { passphrase })`.
3. Read the underlying `unsafeStorage`/`chrome.storage.local` entries directly (as would a co-installed malicious extension or anyone with access to a storage export/backup): `GENERATED_PASSPHRASE_KEY` returns the raw base64 passphrase in cleartext.
4. Use that passphrase to call `seco.decryptString({ data: <SEED_KEY raw value>, key: passphrase })` (same routine `seco-storage` uses internally) to recover the plaintext mnemonic — no password, biometric, or device unlock required.
