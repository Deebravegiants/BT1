Confirmed vulnerability. `WrappedHyperFungibleToken.send()` (and the identical `WrappedHyperFungibleTokenUpgradeable.send()`) locks tokens via `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` at [1](#0-0) , then unconditionally cross-chain-dispatches a `Message` whose `amount` field is the caller-supplied `params.amount`, not the actually-received balance delta, in `_buildDispatchPost` at [2](#0-1) . By contrast, `IntentGatewayV2.placeOrder` already defends against this exact bug class by snapshotting `balanceOf` before/after the transfer and using the delta as the escrowed/committed amount at [3](#0-2) , confirming the codebase is aware of this bug class but the fix wasn't applied to `WrappedHyperFungibleToken`.

### Title
Trusting caller-supplied `amount` instead of actual `safeTransferFrom` proceeds enables unbacked cross-chain mint via max-uint256-transfer tokens (e.g. cUSDCv3) - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain `Message.amount = params.amount` without verifying that `params.amount` of tokens were actually received. Certain tokens (e.g. Compound's cUSDCv3) special-case `amount == type(uint256).max` to mean "transfer the caller's entire balance" instead of reverting for insufficient balance/allowance. A user can call `send()` with `amount = type(uint256).max`, causing the contract to actually receive only their (small) balance, while the dispatched message and destination-chain `onAccept` unlock/mint `type(uint256).max` worth of the underlying token to the recipient.

### Finding Description
In `send()` at [1](#0-0) , the ERC20 path does:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
```
The actual amount received is never measured. `_buildDispatchPost` then encodes `params.amount` verbatim into the outgoing ISMP `PostRequest` body as `Message.amount` at [4](#0-3) , and `Sent` is emitted with the same unverified value at [5](#0-4) .

On the destination chain, `onAccept` trusts `message.amount` completely and pays it out directly from the locked pool: `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` at [6](#0-5) . For tokens like cUSDCv3 that implement the well-known "max-uint256 means transfer full balance" convention, a caller who has approved `type(uint256).max` allowance but holds a small balance can set `params.amount = type(uint256).max`: the `safeTransferFrom` call succeeds (moving only the caller's actual balance into the wrapper), but the wrapper still records/dispatches `amount = type(uint256).max`. The identical pattern exists in `WrappedHyperFungibleTokenUpgradeable.send()` at [7](#0-6) .

The codebase's `IntentGatewayV2.placeOrder` already mitigates this exact class of bug by snapshotting `balanceOf(address(this))` before and after `safeTransferFrom` and using the observed delta rather than the caller-specified amount, both to compute escrow amounts and the order commitment, e.g. [8](#0-7)  and its Tron equivalent [9](#0-8) , demonstrating this bug class is a recognized risk in the codebase that was not fixed in the `WrappedHyperFungibleToken` app.

### Impact Explanation
On the destination chain, `type(uint256).max` (or any amount far exceeding what was actually locked) of the underlying token is released/unlocked to the attacker's designated recipient via `safeTransfer`, up to draining the entire locked reserve backing the wrapper on that chain — an unbacked release of funds and direct loss for all other users/liquidity of the wrapped token pair. This is a High-severity, protocol-fund-draining bug reachable by any unprivileged user with `send()`.

### Likelihood Explanation
Requires the underlying token configured for a `WrappedHyperFungibleToken` deployment to implement the max-uint256-means-full-balance transfer convention (e.g. Compound's cUSDCv3/cTokens, and other tokens following this pattern). Given cUSDCv3's market relevance, an operator configuring the wrapper with such a token — or an attacker submitting/proposing such a token pairing where governance approval is not strict about underlying token semantics — makes this practically exploitable with no privileged access required, only a standard `type(uint256).max` allowance and a `send()` call.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2`: measure `balanceOf(address(this))` before and after `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) both for the dispatched `Message.amount` and the `Sent` event, in both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` configured with an underlying token implementing the max-transfer convention (e.g. a cUSDCv3-like mock where `transferFrom(from, to, type(uint256).max)` transfers `balanceOf(from)` instead of reverting).
2. Attacker holds `1` unit of the underlying token and approves `type(uint256).max` allowance to the wrapper.
3. Attacker calls `send({dest: ..., to: attackerOnDest, amount: type(uint256).max, ...})`.
4. `safeTransferFrom(attacker, wrapper, type(uint256).max)` succeeds, moving only `1` unit into the wrapper.
5. The dispatched `Message.amount` is `type(uint256).max`; once relayed and delivered, destination `onAccept` calls `safeTransfer(beneficiary, type(uint256).max)`, draining the destination-chain locked reserve to the attacker.

        }

            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
