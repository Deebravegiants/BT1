## Title
Webhook `shop`, `topic`, and `webhook_id` Are Not Bound to the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook HTTP request as authentic for whichever shop the caller claims in the `X-Shopify-Shop-Domain` header, but the HMAC signature only ever covers the raw request body. Since the same `api_secret_key` is shared across every shop that installs the app, anyone who can get Shopify to send *one* legitimately-signed webhook (e.g. by installing the app on their own free/dev store and triggering an event) obtains a valid `(body, hmac)` pair that they can replay to the app's public webhook endpoint with an arbitrary `shop-domain`, `topic`, `webhook-id`, or `api-version` header, since none of these are covered by the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then trusts these header-derived fields to build the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature purely against `to_signable_string`, i.e. the body: [4](#0-3) 

Because the identical `api_secret_key` is used for every shop installing the app (as seen throughout the OAuth/token-exchange flows, e.g. `lib/shopify_api/auth/oauth.rb:75-76`, `lib/shopify_api/auth/token_exchange.rb:53-54`), any party who legitimately installs the app on a shop they control can obtain a validly-signed `(raw_body, hmac)` pair from Shopify. They can then replay that exact body/hmac to the app's webhook endpoint while substituting the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers to any value they choose (including a victim shop's domain), and `Utils::HmacValidator.validate(request)` will still return `true` because it never inspects those fields.

The binding that is broken:
`shop authenticated by HMAC` ≠ `shop stored/acted-on by the handler` — the handler receives `request.shop` (header-derived, attacker-controlled) while the cryptographic guarantee only covers `request.body` (also attacker-controlled, since it's their own shop's event data).

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`, an access token, or any privileged account — only the ability to install the app on any shop (including a free/trial one) and capture one webhook delivery. A host application that uses `WebhookMetadata#shop` (populated at `lib/shopify_api/webhooks/registry.rb:198`) to scope any data lookup, write, or business logic (which is the intended and documented use of this field) can be tricked into executing that logic against a victim shop's tenant context using attacker-supplied topic/body content. This is cross-tenant access/data confusion caused entirely by a signature that fails to bind the claimed identity fields.

### Likelihood Explanation
Likelihood is non-trivial but bounded: the attacker must be able to install the target app (trivial for any app, since installing on your own shop requires no special privilege) and must know or guess a victim shop's exact domain (public information, easily enumerable). No secrets, tokens, or social engineering are required — only crafting an HTTP POST with headers changed and the (accessible) body/hmac replayed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (or otherwise cryptographically bind them, e.g. by deriving the expected shop from a per-shop secret/session lookup rather than trusting the header), so that a valid signature for one shop's webhook cannot be replayed as if it belonged to another shop or topic. At minimum, document and encourage host applications to independently verify that `request.shop` corresponds to a shop that actually has this specific `webhook_id`/topic combination registered (e.g. via a lookup against stored registrations) rather than trusting the header value as-is.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they fully control) and enables a webhook topic the app has registered (e.g. `orders/create`).
2. Attacker creates an order on their own shop, causing Shopify to POST a webhook to the app's endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-webhook-id: <id>`, and a valid `shopify-hmac-sha256` computed over the JSON body using the app's shared `api_secret_key`.
3. Attacker captures this raw body and hmac value.
4. Attacker sends their own POST request directly to the same public webhook endpoint URL, keeping `raw_body`/`shopify-hmac-sha256` identical, but changing `shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the untouched raw body) against the untouched hmac — validation succeeds.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker-controlled order JSON>, ...)`, causing the host app to process attacker-controlled content under the victim shop's tenant identity. [3](#0-2) [5](#0-4)

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
