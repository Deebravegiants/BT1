### Title
Shared custody of external protocol state via `EmporiumUpgradeable.runAction` lets any user claim shares/positions left behind by another user's `Emporium`-executed call - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes CASE 2 ops as `op.endpoint.call{value: op.value}(op.callData)`, so `msg.sender` observed by the target protocol (e.g. an ERC4626 vault) is always `address(Emporium)`, never the individual end user. Because `Emporium` is a single shared proxy for every Hinkal user, any external state that accrues to `Emporium`'s own address (vault shares, staked balances, claimable positions) is not bound to the depositor and can be swept by an unrelated, later caller through the same generic `handleOut`/balance-diff mechanism.

### Finding Description
Broken equality: shares/positions credited to `address(Emporium)` by user A's deposit call should be redeemable only by user A's own subsequent `transact()`, but nothing in `runAction` enforces that — any user B can encode an `EmporiumOperation` calling `redeem(shares, receiver, owner=address(Emporium))` (or any withdrawal call whose `owner`/`msg.sender` check is satisfied by `Emporium` itself) and collect the proceeds.

Code path: `EmporiumUpgradeable.runAction` (lines 76-160) takes `balancesBefore`, executes each `EmporiumOperation` — CASE 2 with `stack.signerAddress == address(0)` or `!op.invokeWallet` runs `op.endpoint.call{value: op.value}(op.callData)` (line 112), so the callee sees `msg.sender = address(Emporium)`. After running the ops it takes `balancesAfter`, computes `balanceChange = balancesAfter[i] - balancesBefore[i]`, adjusts by `deltaAmountChanges[i]` (attacker-controlled via the proof's `amountChanges`), and if positive calls `handleOut` (lines 132-151, 162-184), which unconditionally transfers the delta to `msg.sender` (the calling `Hinkal` contract, ultimately to the caller's own new UTXO/stealth address) and mints a fresh UTXO for that exact amount.

There is no linkage in `EmporiumStorage`/`EmporiumUpgradeable` between a specific vault position (shares held by `Emporium`) and the depositor's stealth identity — the only "authorization" enforced is `verifyWallet` (an EIP-712 signature check binding `stack.ops` to `stack.signerAddress` for CASE 1 wallet calls), which is skipped entirely for CASE 2 (`stack.signerAddress == address(0)`, line 314-316). Since `deltaAmountChanges`/`amountChanges` are values the current caller's own circuit proof freely sets (a user can set them to 0 for a token they are not depositing/withdrawing from their own shielded balance), the runtime balance-equality check in `Hinkal.sol` (`balanceDif == amountChanges[i] + utxoAmount`, lines 137-146) is trivially satisfied because `utxoAmount` is derived from the very same observed `balanceChange`, not from any independent record of who owns the underlying vault position.

Exploit flow:
1. Victim submits `transact()` with an `EmporiumStack` op calling `vault.deposit(amount, receiver=address(Emporium))` (ERC4626), leaving vault shares owned by `address(Emporium)`.
2. Attacker later submits an independent, self-generated valid `transact()` proof whose `EmporiumStack` op calls `vault.redeem(shares, attackerHinkalRecipient, address(Emporium))`. Since `msg.sender` at the vault is always `address(Emporium)` and `owner == address(Emporium)`, the ERC4626 `msg.sender == owner` check passes regardless of who submitted the transaction.
3. `runAction`'s balance-diff logic captures the redeemed underlying as `balanceChange`, `handleOut` mints a new UTXO of that amount to the attacker's stealth address, and `Hinkal.sol`'s balance-equality check passes because it only checks internal consistency of the current call, not provenance of the funds.

None of the existing guards prevent this: `verifyWallet`/EIP-712 signature only applies to CASE 1 (`invokeWallet==true`, `signerAddress!=address(0)`); `onlyAllowedRecipient` only checks `msg.sender == Hinkal`, not per-user custody; `nonReentrant` and slippage/`balanceDif` checks are agnostic to whose deposit originated the balance; the circuit constraints (`inTotal + amountChanges === outTotal`) only bind the prover's own declared `amountChanges`, which the attacker sets to 0 for the token they never deposited.

### Impact Explanation
Direct theft of another user's shielded value routed through any external protocol integration where CASE 2 stateless calls leave persistent, fungible state (ERC4626 shares, staking positions, LP tokens, claimable balances, allowances) under `address(Emporium)`'s custody. This matches Critical severity: "direct theft of shielded ... user funds." The attack is repeatable against every deposit-then-redeemable-later integration routed through Emporium's CASE 2 path, for any victim, at zero cost to the attacker beyond gas and constructing their own valid proof.

### Likelihood Explanation
Preconditions: an integrated protocol accessible via Emporium's CASE 2 (stateless) ops whose custody/ownership check is based on `msg.sender`/`owner` parameters rather than an individually-tracked balance per depositor (ERC4626 vaults are the canonical example — `redeem`/`withdraw` check `msg.sender == owner` or allowance). The attacker needs no privileged role: they must only be able to submit their own valid `transact()` proof with a crafted `externalActionMetadata`/`EmporiumStack`, which is explicitly within the stated attacker capability set. The victim's leftover state must exist on-chain (deposit executed, redeem not yet executed by the victim) — feasible since deposit and redemption are necessarily separate transactions. This is realistically and repeatably exploitable whenever the protocol wires up an Emporium integration to any share-based vault/staking contract.

### Recommendation
Do not allow arbitrary users to interact with externally-held state that isn't bound to their own transaction. Options: (1) require CASE 2 ops to be atomic (deposit and any subsequent claim/redeem must occur within the same `runAction` call, with no persistent shares/positions left owned by `address(Emporium)` between calls); (2) route external protocol interactions through per-user ephemeral sub-accounts/proxies instead of the shared `Emporium` address, so custody/ownership checks at the callee are scoped to the individual user; (3) if per-op wallet signing is desired for accountability, require an EIP-712 signature (as already done for CASE 1) binding CASE 2 ops as well, and additionally record/track any vault-share-like balances left under `Emporium`'s control per depositor, only permitting redemption ops whose declared shares/owner match the depositor that created them.

### Proof of Concept
Foundry fork/unit test plan:
1. Deploy a mock ERC4626 vault and an underlying ERC20; deploy `EmporiumUpgradeable` behind the standard Hinkal proxy setup with the vault as an allowed endpoint.
2. Generate a valid snarkjs proof for "victim" `transact()` whose `CircomData.externalActionData` encodes an `EmporiumStack` with one op: `vault.deposit(amount, address(Emporium))`, `amountChanges[underlying] = -amount` (victim spends `amount` from their shielded UTXO into the vault). Submit via `Hinkal.transact()`. Assert `vault.balanceOf(address(Emporium)) == expectedShares` and victim's owned shares are not tracked anywhere per-user.
3. Generate an independent snarkjs proof for "attacker" `transact()` whose `EmporiumStack` op is `vault.redeem(expectedShares, address(Emporium), address(Emporium))`, with `amountChanges[underlying] = 0` (attacker deposits nothing of their own).
4. Submit attacker's `transact()`. Assert it does not revert, and that the newly created UTXO (`handleOut`'s output, verifiable via the emitted commitment/`utxoAmount`) has `amount == amount` (the victim's original deposit), i.e., `attacker's minted UTXO amount == victim's deposited principal`, while `vault.balanceOf(address(Emporium))` drops to 0 and the victim retains no claim.
5. This demonstrates the equality "shares minted to Emporium from victim's deposit are redeemable only by the victim" is false — any subsequent, unrelated caller's own valid proof can capture them via `deltaAmountChanges`/`handleOut`.
