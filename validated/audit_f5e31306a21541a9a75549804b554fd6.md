### Title
Per-call WASM instantiation cost (globals/data-segments/element-segments re-initialization) is not fully covered by gas, allowing underpriced CPU work per `FunctionCall` receipt - ([File: runtime/runtime-params-estimator/src/vm_estimator.rs])

### Summary
The Megapot finding is a case of computation whose cost scales with an attacker/deployer-controlled parameter (`bonusballMax` combined with the number of tickets) while the gas charged for it is effectively a fixed/underestimated cost, letting real work exceed the enforced gas/block limit. The closest structural analog in this nearcore snapshot is the explicitly-flagged, but only partially mitigated, "adversarial load" pattern in the WASM contract runtime: contracts with very large numbers of globals, active data segments, or active element segments impose Wasmtime instantiation work on *every* `FunctionCall` invocation that is not linearly priced by the corresponding gas parameters.

### Finding Description
When a `FunctionCall` action is executed, the contract's compiled WASM module is instantiated before running the target export. Instantiation re-initializes all module globals, active data segments, and active element segments. The runtime-params-estimator explicitly documents three cost categories built to probe this: [1](#0-0) 

which are measured via `adversarial_load_many_globals`, `adversarial_load_many_data_segments`, and `adversarial_load_many_element_segments`, each explicitly commented as exposing "unbounded per-call ... work not covered by gas": [2](#0-1) 

The only backstop against unbounded scaling is the static `max_globals_per_contract` (100,000) limit enforced at contract preparation time: [3](#0-2) [4](#0-3) 

A companion test acknowledges that a contract deployed near this limit (e.g. 50k–100k globals) can pass `prepare` and only fails later at Wasmtime module load due to the unrelated `max_core_instance_size` pooling-allocator limit — meaning the "backstop" that currently prevents pathological behavior is an implementation detail of the Wasmtime allocator, not an explicit, linearly-charged gas cost for the re-initialization work itself: [5](#0-4) 

Unlike the EVM analog, NEAR's protocol philosophy requires *every* dynamic host/VM operation to have an explicit per-unit gas cost proportional to its complexity, as documented in the gas architecture docs ("Each host function must clearly define what its costs are and how they depend on the input."): [6](#0-5) 

The presence of dedicated "Adversarial" estimator cost categories whose doc comments state the corresponding work is "not covered by gas" indicates this per-instantiation cost has not been fully folded into a linear, per-global/per-segment gas parameter, unlike other dynamic costs (e.g. `wasm_sha256_byte`, `add_function_call_key_byte`) which are explicitly charged per unit of attacker-controlled input.

### Impact Explanation
If the instantiation-time re-initialization cost genuinely scales with globals/data-segments/element-segments count but is not charged proportionally, a contract author could deploy a contract just under the configured limits (up to `max_globals_per_contract` = 100,000, `max_elements_per_contract_table` = 10,000, and up to 100,000 data segments allowed by the WASM module validation limits) and call it repeatedly. Each call would consume disproportionate validator CPU time relative to the gas burned, potentially:
- Slowing chunk application beyond the 1ms-per-Tgas budget the estimator is designed to enforce, which can delay chunk/block production (chain-wide latency/throughput degradation), analogous to the report's "drawing can never be settled" chain-stall impact.
- Allowing underpriced execution, i.e., getting more CPU work per unit of gas paid than the protocol intends, which is a concrete underpriced-execution class of bug.

This impact is real but bounded by the current static WASM limits (100k globals, 10k table elements, 100k data segments per module) and by orthogonal Wasmtime pooling-allocator constraints (`max_core_instance_size`) that reject the largest configurations at module load time rather than at execution time. Whether the *sub-limit* configurations (e.g. 50k globals, under all hard caps) actually produce validator-node CPU cost per call that meaningfully exceeds the gas charged cannot be fully confirmed from the indexed documentation/comments alone — this would require examining the actual instantiation gas-charging code path (e.g. `wasm_contract_loading_base`/`_bytes` parameters and any per-global/per-segment charging logic), which was not retrievable within the available search budget.

### Likelihood Explanation
Reachability is straightforward and unprivileged: any account can deploy a contract via `DeployContractAction` with up to the configured limits and then invoke it repeatedly via ordinary `FunctionCall` actions/receipts — no validator or node-internal privilege is required. However, likelihood of causing a *significant* stall is tempered by:
- The presence of hard per-contract structural limits (`max_globals_per_contract`, `max_elements_per_contract_table`, and the 100k data-segment module validation limit) that bound the worst case.
- The fact that this exact scenario is already flagged as a known area of concern by nearcore's own estimator/test suite (the "Adversarial" cost names and the explicit test comment about the Wasmtime backstop), suggesting the nearcore team is aware of and actively tracking this boundary case, and may have partially or fully compensated for it via other charged costs (e.g., contract loading base/byte fees) that were not fully traceable in this investigation.

### Recommendation
- Verify and, if necessary, extend the gas charged for `FunctionCall` invocation (`wasm_contract_loading_base`/`_bytes` or a new dedicated parameter) to include an explicit per-global, per-active-data-segment, and per-active-element-segment linear cost, matching the estimator's `AdversarialLoadManyGlobals`/`AdversarialLoadManyDataSegments`/`AdversarialLoadManyElementSegments` measurements.
- Ensure these adversarial cost estimations are run against the 1ms = 1Tgas budget and used to set or update `wasm_regular_op_cost`/dedicated instantiation parameters, closing the gap called out in the code comments ("not covered by gas").
- Consider tightening `max_globals_per_contract`/`max_elements_per_contract_table`/data-segment limits if per-unit charging is impractical to implement precisely.

### Proof of Concept
Not independently reproducible from the indexed documentation alone. The PoC pattern implied by the codebase's own adversarial estimator functions would be: deploy a contract generated via `near_test_contracts::contract_with_num_globals(N)` (or `many_data_segments_contract(N)` / `many_element_segments_contract(N)`) near the configured limits, then repeatedly invoke a trivial exported method and measure wall-clock/gas-burnt ratio versus a baseline contract with few globals/segments — exactly as done by `adversarial_load_many_globals`/`adversarial_load_many_data_segments`/`adversarial_load_many_element_segments` in `runtime/runtime-params-estimator/src/vm_estimator.rs:168-184`. Actual on-chain confirmation that the gap is unmitigated (i.e., that the resulting per-call cost is not already compensated elsewhere in the fee schedule) would require running this estimator or a live transaction test, which was outside the scope of a read-only code search.

        code: &[u8],
        features: crate::features::WasmFeatures,
        config: &near_parameters::vm::Config,

        let (function_count, local_count, table_count, element_count) =
            wasmparser_decode(code, features).map_err(|e| {
                tracing::debug!(target: "vm", err=?e, "wasmparser failed decoding a contract");
                PrepareError::Deserialization
            })?;
        // Verify the number of functions does not exceed the limit we imposed. Note that the ordering
        // of this check is important. In the past we first validated the entire module and only then
        // verified that the limit is not exceeded. While it would be more efficient to check for this
        // before validating the function bodies, it would change the results for malformed WebAssembly
        // modules.
        if let Some(max_functions) = config.limit_config.max_functions_number_per_contract {
            if function_count.ok_or(PrepareError::TooManyFunctions)? > max_functions {
                return Err(PrepareError::TooManyFunctions);
            }
        }
        // Similarly, do the same for the number of locals.
        if let Some(max_locals) = config.limit_config.max_locals_per_contract {
            if local_count.ok_or(PrepareError::TooManyLocals)? > max_locals {
                return Err(PrepareError::TooManyLocals);
            }
        }
        // Similarly, do the same for the number of tables.
        if let Some(max_tables) = config.limit_config.max_tables_per_contract {
            if table_count.ok_or(PrepareError::TooManyTables)? > max_tables {
                return Err(PrepareError::TooManyTables);
            }
        }
        // Similarly, do the same for the number of table elements.
        if let Some(max_elements) = config.limit_config.max_elements_per_contract_table {
            if usize::try_from(element_count).map_err(|_| PrepareError::TooManyTableElements)?
                > max_elements
            {
                return Err(PrepareError::TooManyTableElements);
            }
        }
        Ok(())

/// Compile and load a contract with 100k globals.
///
/// Each defined global occupies 16 bytes of a core instance's `VMContext`, so
/// globals alone add ~1.6 MB. That breaches the 1MiB `max_core_instance_size`
/// slot of the Wasmtime pooling allocator, so loading the module at
/// `Module::deserialize` fails.
///
/// With `max_globals_per_contract` set to 100k this contract still passes
/// `prepare` and is caught by the Wasmtime backstop at load time.
///
/// Pre-`FixContractLoadingError` this surfaces as `VMRunnerError::LoadingError`,
/// which the runtime maps to a zero-gas nop — the contract-loading work is left
/// uncharged. Post-feature the same failure finalizes as a gas-bearing abort
/// that charges the contract-loading fee. Either way it must not panic / crash
/// the node.
