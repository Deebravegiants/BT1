### Title
Protocol/Hinkal fee is stranded in `ExternalActionSwap` when `circomData.relay == address(0)` - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
In `ExternalActionSwap.swap()` the `hinkalFee` (and `relayFee`) are always computed and subtracted from the amount that is ultimately sent back into the Hinkal shielded pool, but they are only actually paid out through `sendToRelay`, which silently no-ops when `circomData.relay == address(0)`. If a prover submits a swap with `relay == address(0)` (a legitimate "no relay" / self-relayed transaction), the deducted fee amount is never transferred anywhere and there is no sweep/claim function to recover it, so it becomes permanently stuck in the `ExternalActionSwap` contract's token balance.

### Finding Description
`swap()` always computes the protocol fee `hinkalFee` via `hinkalHelper.calculateRelayFee(...)` regardless of whether a relay is used, and subtracts it (together with `relayFee` when the tokens match) from `amountToSendToHinkal`: [1](#0-0) 

Payout of that fee is delegated to `sendToRelay`, which only transfers when the relay address is non-zero: [2](#0-1) 

Compare this with the internal (non-external-action) path in `Hinkal._internalTransact`, where the relay fee is computed *only if* `circomData.relay != address(0)` — i.e. no fee is deducted at all when there is no relay: [3](#0-2) 

`ExternalActionSwap.swap()` does not follow this same guard for the `hinkalFee` portion: the fee is deducted from the user's `amountToSendToHinkal` unconditionally, but the transfer to a recipient is guarded independently inside `sendToRelay`. When `circomData.relay == address(0)`, the deducted `hinkalFee` (and, if the fee token matches the output token, the `relayFee` too) is not sent anywhere — it remains as an unaccounted-for balance held by the `ExternalActionSwap` contract, which has no owner-only sweep/claim function to recover it (confirmed by reviewing `ExternalActionSwap.sol` and its base `ExternalActionBaseV2.sol`, neither of which defines a withdrawal/claim mechanism for stranded token balances).

This breaks the intended equality that "fee deducted from swap output == fee actually paid to relay/protocol": part of the deducted value disappears from the balance equation entirely, permanently freezing protocol/relay revenue for every self-relayed (`relay == address(0)`) swap.

### Impact Explanation
This is a permanent freezing of protocol/relay fees (High per the given severity classification): any unprivileged EOA that constructs a valid proof/transaction for `ExternalActionSwap` with `relay == address(0)` causes the computed `hinkalFee`/`relayFee` to be silently stranded in the external-action contract with no path to recovery. Because `relay == address(0)` is an explicitly supported, legitimate state elsewhere in the protocol (Hinkal's own internal-transact path treats it as "no relay used, no fee"), a normal user/self-relaying flow through the swap action will trigger this loss on every such call, and the funds accumulate unclaimably in the contract.

### Likelihood Explanation
Likelihood is straightforward: no privileged role is required, only a normal transaction where the prover sets `relay = address(0)` in `CircomData` (self-relay scenario). This is a normal, unprivileged usage path through `Hinkal.transact` → `_externalTransact` → `ExternalActionSwap.runAction/swap`.

### Recommendation
In `ExternalActionSwap.swap()`, guard the fee computation the same way `Hinkal._internalTransact` does: only compute/deduct `hinkalFee`/`relayFee` from `amountToSendToHinkal` when `circomData.relay != address(0)`; otherwise skip fee calculation entirely so the full `swappedAmount` is returned to the user. Alternatively, if the "hinkal fee" must always be charged regardless of relay presence, route it to a dedicated protocol treasury address (not gated by `circomData.relay`) instead of relying on `sendToRelay`, and add an owner-only sweep function to recover any tokens that end up stuck in the contract.

### Proof of Concept
1. Prover builds a Hinkal `transact()` call targeting `ExternalActionSwap` with `circomData.relay = address(0)` (self-relayed swap; a state accepted by the protocol elsewhere), a positive `feeStructure.variableRate`/`flatFee`, and a valid input UTXO/proof.
2. `Hinkal.transact` → `_externalTransact` invokes `ExternalActionSwap.runAction` → `swap()`.
3. `swap()` computes `hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, variableRate)` (and `relayFee = flatFee`), unconditionally.
4. `sendToRelay(address(0), relayFee + hinkalFee, outputToken)` (or the split-token branch) is called; because `relay == address(0)`, the guard in `Transferer.sendToRelay` (`contracts/Transferer.sol:183`) causes the function to return without transferring anything.
5. `amountToSendToHinkal = swappedAmount - totalFee` is still computed with `totalFee` subtracted, and only that reduced amount is sent to `msg.sender` (Hinkal) and encoded into the user's new UTXO.
6. The difference `totalFee` remains as a real ERC20/ETH balance sitting in the `ExternalActionSwap` contract, with no function anywhere in `ExternalActionSwap.sol` or `ExternalActionBaseV2.sol` able to withdraw it — the fee is permanently frozen.
