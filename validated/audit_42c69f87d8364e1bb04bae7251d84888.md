### Title
Webhook Shop Domain Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` (tenant) identity used by the app's handler is taken from an unsigned HTTP header. This breaks the intended binding: `hmac_valid(body) == authentic(shop, body)`. An attacker who can obtain any one genuinely-signed webhook payload (e.g. from their own store's installation of the same app) can replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the library will report it as fully verified for that victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all read straight from HTTP headers and are never included in the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the body) against `request.hmac`, then immediately trusts `request.shop` and `request.topic` to construct `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` and compare against the supplied `hmac`, with no binding to headers such as shop domain: [4](#0-3) 

The `WebhookMetadata` struct built from these unauthenticated header fields (particularly `shop`) is exactly what the host application is documented to use as the tenant identifier for processing: [5](#0-4) [6](#0-5) 

Because Shopify HMAC-signs only the body (using the app's shared secret) and never binds the signature to the shop domain header, a valid `(body, hmac)` pair captured from one legitimate webhook delivery (e.g., for a shop the attacker controls, or any shop-triggerable event they can observe) remains a valid `(body, hmac)` pair regardless of which shop-domain header accompanies it. The library treats this as full authentication and passes an attacker-chosen `shop` value straight to the app's handler as trusted tenant context.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-processed identity binding, allowing cross-tenant webhook spoofing: an attacker can cause the app to process fabricated/replayed webhook events as if they originated from a victim merchant's shop. Depending on the handler's logic (order creation, app/uninstalled, customer data requests, etc.), this can lead to data corruption, false business events, or unauthorized actions being taken against a shop the attacker does not control — a cross-tenant integrity violation, rated Critical per the applicable impact categories.

### Likelihood Explanation
Exploitation requires no access to the app's `client_secret`/`api_secret_key`: the attacker only needs one legitimate, Shopify-signed webhook body+HMAC pair (trivially obtainable by installing the target app on their own development/test store, which most Shopify apps allow) and the ability to POST to the app's public webhook callback URL with a modified `shop-domain` header — both are unprivileged, internet-reachable actions. Likelihood is high wherever the host app relies on `WebhookMetadata#shop` (as documented) without independently re-verifying shop identity.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the authenticated signable material, or otherwise cryptographically tie the shop-domain header to the payload before trusting it. At minimum, `Registry.process`/`Request` should not treat `shop-domain` as verified data — the shop used for tenant lookup must be re-validated against something bound to the HMAC (e.g., corroborated with an active, previously-established session/shop record rather than trusted verbatim from the unsigned header).

### Proof of Concept
1. Attacker installs the vulnerable app on their own Shopify dev store (`attacker-shop.myshopify.com`) and triggers a webhook event (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — both are valid and correctly signed with the app's real secret.
2. Attacker replays this exact `(raw_body, hmac)` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the HMAC against the (unchanged) body — see `lib/shopify_api/webhooks/request.rb#to_signable_string` and `lib/shopify_api/utils/hmac_validator.rb#validate_signature`.
4. `process` builds `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-supplied header value `victim-shop.myshopify.com` and calls the app's `handler.handle`, which processes the (attacker-controlled) payload as an authenticated event for the victim shop — see `lib/shopify_api/webhooks/registry.rb#process`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
