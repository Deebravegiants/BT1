OAuth callback exchanges `client_secret` with an unvalidated `shop` host, bypassing the trusted-domain allowlist enforced everywhere else - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request host directly from `auth_query.shop`, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other grant flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.exchange_token`) validates the `shop` parameter against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before using it to construct the request host that receives `client_id`/`client_secret`. `oauth.rb` is the outlier that skips this check.

### Finding Description
`validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` (lines 60-113) does the following:
1. Validates the incoming `AuthQuery` HMAC via `Utils::HmacValidator.validate(auth_query)` (line 64). The signable string covers `code, host, shop, state, timestamp` (`lib/shopify_api/auth/oauth/auth_query.rb` lines 34-43), so an attacker who does not know `api_secret_key` cannot forge an `AuthQuery` with an arbitrary `shop` value that passes HMAC validation.
2. Builds `auth_base_uri(shop)` (line 118) = `"https://#{shop}/admin"` using the *unsanitized* `auth_query.shop`.
3. POSTs `{client_id, client_secret, code, expiring}` to that host via `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` (lines 74-90). `HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` (`lib/shopify_api/clients/http_client.rb` line 18), so the destination host is taken verbatim from `session.shop`, which equals `auth_query.shop`.

There is no call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` anywhere in this path, unlike the parallel flows:
- `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` before using it as the session shop (`lib/shopify_api/auth/client_credentials.rb` line 25).
- `RefreshToken.refresh_access_token` does the same (`lib/shopify_api/auth/refresh_token.rb` line 24).
- `TokenExchange.exchange_token` derives `dest_shop` from a cryptographically-verified JWT `dest` claim rather than an arbitrary caller-supplied string (`lib/shopify_api/auth/token_exchange.rb` lines 40-41).

This breaks the identity binding that the rest of the gem enforces: "the host that receives the app's `client_secret`" should equal "a host in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`" — but here it is only bound to "whatever `shop` value produced a valid HMAC over the callback query," which is a strictly weaker guarantee that this specific code path does not otherwise re-derive or re-check.

### Impact Explanation
If any code path allows an attacker (or a malicious/compromised legitimate merchant flow) to obtain a validly-HMAC'd callback query for a `shop` value that is not actually a `myshopify.com`/trusted Shopify domain (e.g., host confusion via reused `state`/replay of a callback recorded against a different `shop`, or a host application that mistakenly re-signs data itself), `validate_auth_callback` will send the application's `client_secret` to that attacker-controlled host in cleartext POST body. This matches the "High: SSRF with the app's credentials / credential leakage" impact class — the gem sends its own `client_secret` to a host derived from a field that the rest of the codebase treats as requiring domain-allowlist validation, and this function alone omits that check.

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can get a validly-HMAC'd `AuthQuery` for a non-Shopify `shop` value without knowing `api_secret_key`. Under normal operation, Shopify itself computes this HMAC when redirecting the merchant back to the app, and Shopify would not sign a non-`myshopify.com` `shop` value. This makes the practical, purely-external-attacker likelihood of forging such a query low, since it requires a legitimate HMAC without secret knowledge — I could not identify a concrete forgery path within this gem's own code (no oracle, no signature confusion, no replay-across-shop vector visible in the files reviewed). Given the "no credential, no privileged access" constraint, this is best characterized as a defense-in-depth gap (missing an allowlist check that is present everywhere else in the codebase) rather than a demonstrated, standalone exploitable vulnerability from this gem's code alone.

### Recommendation
Add `Utils::ShopValidator.sanitize!(auth_query.shop)` (or `sanitize_shop_domain`) in `validate_auth_callback` before constructing `null_session`/`auth_base_uri`, mirroring `ClientCredentials`, `RefreshToken`, and `TokenExchange`, so that the host receiving `client_secret` is always independently constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of HMAC validity.

### Proof of Concept
Not reproducible as a standalone exploit from this gem's code alone: constructing a callback query with a non-Shopify `shop` value that still passes `Utils::HmacValidator.validate` requires knowledge of `Context.api_secret_key`, which is out of scope per the rules. The concrete code-level gap demonstrated is:

```ruby
# -> lib/shopify_api/clients/http_client.rb:18
# @base_uri = "https://#{api_host || session.shop}"       # client_secret POSTed here
```
versus the sanitized equivalents in `lib/shopify_api/auth/client_credentials.rb:25` and `lib/shopify_api/auth/refresh_token.rb:24`.
