### Title
Weight-exhaustion during XCMP page enqueue permanently drops trailing fragments (including channel-management notifications) with no retry - (File: cumulus/pallets/xcmp-queue/src/lib.rs)

### Summary
`XcmpMessageHandler::handle_xcmp_messages` decodes each inbound HRMP page into a list of concatenated XCM fragments and hands them to `enqueue_xcmp_messages`, which pushes each fragment into the generic message queue while consuming a shared `WeightMeter`. When that meter is exhausted mid-loop, the pallet emits the `defensive!("Out of weight: cannot enqueue entire XCMP messages batch; dropped some or all messages in batch")` warning and simply stops processing the remaining fragments in that page — it does not re-queue or defer them.

### Finding Description
`handle_xcmp_messages` reads and consumes HRMP page bytes for a channel in a single pass; once a page's bytes are taken from the HRMP transport (relay-chain side accounting marks the message as delivered/consumed), there is no way to re-fetch it. Inside the pallet, `enqueue_xcmp_messages` iterates the decoded fragment list and calls the message-queue `enqueue_message`/`EnqueueMessage` implementation for each fragment, charging `T::WeightInfo::enqueue_xcmp_message()` (a fixed, attacker-knowable per-fragment weight) against a shared `WeightMeter` that bounds the whole inherent's XCMP-processing budget. If the meter's remaining weight is insufficient to enqueue the next fragment, the loop breaks and logs the defensive warning found verbatim in `cumulus/pallets/xcmp-queue/src/lib.rs` [1](#0-0) ; any fragments after that point in the page are never enqueued, never retried, and never surface to the runtime again.

Because the enqueue budget (a fixed reserved weight for the XCMP inherent) and the per-fragment enqueue cost are both runtime constants known in advance, a sibling parachain operator can precompute how many minimal-size filler fragments are needed to exhaust the meter, pack that many into a single HRMP page (bounded only by the channel's configured max message size), and place one more fragment — e.g. an XCM encoding a `HrmpChannelClosing`-style notification or other important instruction — at the very end of the page. That trailing fragment will be dropped deterministically, not merely delayed, because the page bytes were already consumed from the HRMP channel by the time the meter ran out.

No signature, origin, or barrier check applies here since this executes at the transport/enqueue layer before XCM barriers or origin conversion even run; the only gating factor is channel-open status (attacker only needs an open HRMP channel to the victim, which is a normal, permissionless-by-design parachain-to-parachain relationship once the channel is accepted).

### Impact Explanation
A malicious or compromised sibling parachain can reliably and repeatedly cause loss of specific messages addressed to a victim parachain by hiding them behind a weight-exhausting flood of filler fragments in the same HRMP page. This breaks the invariant that "critical queues and validation paths must not be permanently halted/dropped by valid input" for any XCM instruction that is transport-critical and has no independent redundancy (e.g., channel state notifications, one-shot governance/config XCMs, or asset-transfer completions relied upon by downstream logic). Because the drop happens at the transport-consumption boundary, there is no automatic resend by HRMP/XCMP.

### Likelihood Explanation
Preconditions are modest: the attacker needs only an already-open HRMP channel to the victim, which is achievable by any parachain participating in the ecosystem (channel opening is a normal, permissionless-adjacent parachain manager action, not something the victim's *runtime users* need to approve per-message). The per-fragment enqueue weight and reserved inherent weight budget are runtime constants, so the number of filler fragments needed is computable offline, making the attack deterministic and repeatable every block the attacker chooses to send such a page.

### Recommendation
- On meter exhaustion inside `enqueue_xcmp_messages`, persist the *remaining unprocessed fragments* (not just log and discard) into a per-channel "pending fragments" storage item, and resume processing them at the start of the next block's `handle_xcmp_messages` call before pulling new HRMP pages.
- Alternatively, bound the *number of fragments per page* processed atomically, and require that if a page cannot be fully enqueued, the entire page (not just the fragment list) is deferred as a whole rather than partially executed, preserving in-page ordering guarantees for consumers who rely on later fragments (e.g., channel-management notifications).
- Add a metric/alert when the defensive branch triggers, and consider making the reserved enqueue-weight budget elastic (e.g., scale with the number of open channels/senders) to reduce practical feasibility of precomputing the exhaustion threshold.

### Proof of Concept
Rust unit test in `cumulus/pallets/xcmp-queue/src/tests.rs` style:
1. Build a `WeightMeter::with_limit(W)` where `W` corresponds to the runtime's reserved XCMP-enqueue weight.
2. Construct a single HRMP page (`XcmpMessageFormat::ConcatenatedVersionedXcm` prefix) containing `N = W / T::WeightInfo::enqueue_xcmp_message() + 1` minimal no-op XCM fragments followed by one marker fragment (e.g. a `Xcm` wrapping a distinguishable instruction/`SetTopic` used as a sentinel).
3. Call `XcmpQueue::handle_xcmp_messages` (or directly `enqueue_xcmp_messages`) with this page and the bounded meter.
4. Assert: (a) the `defensive!` warning/log path is hit (or equivalent event), (b) the marker fragment's hash never appears in the message-queue footprint/storage for that channel, (c) re-invoking `handle_xcmp_messages` on a subsequent block with no new data does not recover/enqueue the marker fragment — proving permanent, non-deferred loss rather than delay.
