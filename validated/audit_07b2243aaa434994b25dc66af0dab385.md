### Title
`Processor::calc_take_pnl` silently drops accrued PnL when one side rounds to zero, corrupting pool PnL baseline and `need_take_pnl_*` accounting - (File: `program/src/processor.rs`)

### Summary
The reported analog bug class — a conditional that discards a legitimately non-zero value when a related percentage/amount happens to be zero — is reproduced in `Processor::calc_take_pnl`. The function computes `pc_pnl_amount` and `coin_pnl_amount` independently (each derived from different decimal-scaled quantities), then gates *all* PnL bookkeeping on both being simultaneously non-zero.

### Finding Description
Inside `calc_take_pnl`, `delta_x`/`delta_y` (the sys-decimal deltas used to advance the pool's `calc_pnl_x`/`calc_pnl_y` baseline) are computed unconditionally from `diff_x`/`diff_y`: [1](#0-0) 

Immediately after, `pc_pnl_amount` and `coin_pnl_amount` are computed by restoring `diff_x`/`diff_y` to native token decimals (`amm.pc_decimals` / `amm.coin_decimals`) — which differ per pool and can be very different in magnitude — and only if **both** are non-zero does the code update `need_take_pnl_pc/coin` and reduce `total_pc/coin_without_take_pnl`; otherwise it zeroes out `delta_x`/`delta_y` entirely and discards the whole computed PnL step: [2](#0-1) 

Because `pc_decimals` and `coin_decimals` can differ significantly (e.g. a 9-decimal coin paired with a 2-decimal stable pc token), small `diff_x`/`diff_y` values can restore to a non-zero `coin_pnl_amount` while `pc_pnl_amount` rounds down to `0` (or vice versa). In that case the `if pc_pnl_amount != 0 && coin_pnl_amount != 0` guard fails and the *entire* PnL delta for both sides is dropped — even though one side had a real, non-zero, restorable amount. This mirrors exactly the reported analog: the function should still book the correct non-zero side's value instead of discarding both when only one rounds to zero.

`calc_take_pnl` is invoked from every code path that mutates the AMM's PnL baseline and `need_take_pnl_*` state: `process_withdrawpnl`, and the deposit/withdraw liquidity flows, each of which is reachable via a normal user/LP transaction with attacker-influenced vault balances (via prior swaps) since the trigger condition depends purely on pool reserve ratios and decimals, not on any privileged signer. [3](#0-2) [4](#0-3) 

### Impact Explanation
When the guard is not satisfied, `target.calc_pnl_x`/`calc_pnl_y` (the baseline reference the whole PnL/K-invariant tracking system relies on) is advanced by the caller using `delta_x = delta_y = 0`, while `total_pc_without_take_pnl`/`total_coin_without_take_pnl` are *not* reduced and `need_take_pnl_pc/coin` are *not* incremented for that step, even though real accrued value (on the side that did round to non-zero) existed. This causes the pool's internal `calc_pnl_x`/`calc_pnl_y` reference values (used by `calc_x_power`/`integer_sqrt` in the next PnL calculation) and the "amount owed to protocol" counters (`need_take_pnl_pc`/`need_take_pnl_coin`, subsequently subtracted from vault balances in `calc_total_without_take_pnl_no_orderbook`, which directly feeds the constant-product swap math) to drift from the true economic state of the pool over repeated swap/deposit/withdraw cycles. This is an insolvent-pool-accounting class issue: swap output amounts, LP redemption amounts, and protocol PnL withdrawals are all derived from `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, so a persistently incorrect baseline can misprice swaps and misallocate LP/protocol funds over time.

### Likelihood Explanation
Any AMM pool where `pc_decimals != coin_decimals` (a very common configuration on Raydium, e.g. stablecoin/SPL pairs with 2–9 decimal differences) can hit the rounding-to-zero condition on ordinary, unprivileged deposit/withdraw/withdrawpnl calls once accumulated `diff_x`/`diff_y` are small relative to the decimal gap. No special account privileges or malicious validator behavior are required — it is a deterministic consequence of the decimal-restoration math combined with the all-or-nothing gating condition.

### Recommendation
Do not gate the entire PnL update on both `pc_pnl_amount != 0 && coin_pnl_amount != 0`. Each side's PnL amount, `need_take_pnl_*` accumulation, and `total_*_without_take_pnl` reduction should be applied independently (or the `delta_x`/`delta_y` baseline advance should track exactly what was actually booked), so that a zero on one side does not cause the non-zero side's legitimately accrued PnL to be silently dropped.

### Proof of Concept
1. Set up a pool where `pc_decimals` and `coin_decimals` differ substantially (e.g. pc_decimals = 2, coin_decimals = 9), as permitted by `AmmInfo::initialize`. [5](#0-4) 
2. Perform a sequence of small swaps (`process_swap_base_in`/`process_swap_base_in_v2`) that move reserves such that, on the next `Deposit`/`Withdraw`/`WithdrawPnl` call, the computed `diff_x` (pc side) restores to `pc_pnl_amount == 0` after `Calculator::restore_decimal` while `diff_y` (coin side) restores to a non-zero `coin_pnl_amount`. [6](#0-5) 
3. Call `process_withdraw` (or `process_deposit`/`process_withdrawpnl`), which invokes `calc_take_pnl`; observe that despite `coin_pnl_amount != 0`, the `else` branch fires because `pc_pnl_amount == 0`, causing both `delta_x` and `delta_y` to be zeroed and `need_take_pnl_coin`/`need_take_pnl_pc` to remain unchanged. [7](#0-6) 
4. Repeat over multiple deposit/withdraw/swap cycles: `target.calc_pnl_x`/`calc_pnl_y` no longer track the true reserve growth, and `need_take_pnl_pc`/`need_take_pnl_coin` under-accumulate relative to actual accrued fees, producing a divergence between the pool's tracked PnL baseline and its real economic state that compounds with each subsequent `calc_take_pnl` invocation.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
