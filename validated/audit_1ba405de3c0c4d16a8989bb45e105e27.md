### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated for a given shop once `Utils::HmacValidator.validate` succeeds, and then dispatches `request.shop`, `request.topic`, and `request.webhook_id` to the app's handler as trusted metadata. However, the HMAC is computed only over the raw request body, not over the `shop-domain`, `topic`, or `webhook-id` headers, so those fields are never bound to the signature that was verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string`: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` only checks that the HMAC over the body is valid, then forwards the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` to the handler as if they were verified: [4](#0-3) 

This breaks the identity binding: `shop that produced a validly-HMAC'd payload == shop that the handler is told the payload came from`. Because `api_secret_key` is the same shared app secret used for every shop that installs the app (it is not a per-shop secret), any merchant/tenant who has installed the app can legitimately trigger a webhook on their own store to obtain a body + valid HMAC pair, then replay that body with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header claiming to be a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects the headers, and `Registry.process` will happily hand the forged `shop` value to the app's registered handler.

### Impact Explanation
This allows cross-tenant impersonation: a low-privilege tenant (any shop that installed the multi-tenant app) can make the host application believe a webhook event/body came from an arbitrary other shop. Any host application that uses `WebhookMetadata#shop` to key per-tenant data (e.g., updating orders/inventory/settings for "that shop", or looking up the shop's session/access token) can be tricked into writing attacker-supplied body content under another tenant's identity — a cross-tenant access/data-integrity issue that maps to the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Any existing customer of a multi-tenant app (an unprivileged actor relative to other tenants) can generate a validly-signed webhook body from their own shop's events (they fully control the timing/content of many webhook topics, e.g. `app/uninstalled`, `products/update`, `orders/create` if they have a store), then simply resend it to the app's webhook endpoint with a different `shop-domain` (and/or `topic`) header. No secrets, tokens, or privileged access are required beyond normal merchant use of the app.

### Recommendation
Bind the identity-carrying headers into the signed material, or otherwise cryptographically verify them against the HMAC:
- Include `shop-domain`, `topic`, and `webhook-id` (or at minimum `shop-domain`) in the string that is HMAC-verified, not just the raw body, mirroring how OAuth/App-proxy signatures bind all query parameters.
- Alternatively, have `HmacValidator`/`Request` accept and verify a canonicalized string composed of `raw_body + shop + topic` (Shopify's actual delivery guarantees would need to support this) so header tampering invalidates the signature.
- At minimum, document prominently that `shop`/`topic`/`webhook_id` on `Request`/`WebhookMetadata` are NOT covered by the HMAC and must not be trusted for tenant routing without independently confirming the shop has an active session/installation record.

### Proof of Concept
1. App installs on Shop A and Shop B (same `api_secret_key` for both, since it's an app-level secret, not per-shop).
2. Attacker controls Shop A and triggers a webhook event (e.g., updates a product) causing Shopify to POST a signed webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `api_secret_key`) and `X-Shopify-Shop-Domain: shopA.myshopify.com`.
3. Attacker captures this legitimate request, then replays it to the same endpoint but rewrites the header to `X-Shopify-Shop-Domain: shopB.myshopify.com` (victim), keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and calls the handler with `WebhookMetadata.new(shop: "shopB.myshopify.com", ...)`, i.e., the host application now processes attacker-controlled data as if it originated from Shop B.
