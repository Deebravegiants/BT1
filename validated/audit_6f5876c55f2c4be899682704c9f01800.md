### Title
WrappedHyperFungibleToken.send() and onAccept()/onPostRequestTimeout() use the user-specified amount instead of actual tokens received, causing insolvency for fee-on-transfer/rebasing/deflationary underlying tokens - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken` locks an underlying ERC20 on the source chain and unlocks/mints the same nominal amount on the destination chain, but it trusts the caller-supplied `params.amount` as the amount actually held in escrow rather than measuring the real balance delta from the `safeTransferFrom` call. If the configured `underlying` token is fee-on-transfer, deflationary, or rebasing, the contract systematically promises to release more underlying tokens across all cross-chain messages than it actually possesses, producing an accounting deficit that manifests as reverted unlocks/refunds (frozen funds) for other users once the pool is depleted.

### Finding Description
In `send()`, the contract calls: [1](#0-0) 
and then dispatches a cross-chain message that encodes `params.amount` (not the actual amount received) as the value to be unlocked on the destination peer: [2](#0-1) 

Unlike `IntentGatewayV2.placeOrder()`, which explicitly snapshots the gateway's balance before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received amount to stay solvent under fee-on-transfer tokens: [3](#0-2) 

`WrappedHyperFungibleToken.send()` has no equivalent balance-diff check. If `underlying` charges a transfer fee, rebases downward, or is otherwise deflationary, the contract receives `params.amount - fee` but still commits to deliver `params.amount` on the destination chain via `Message.amount`: [4](#0-3) 

On the destination side, `onAccept()` unconditionally transfers `message.amount` of underlying to the beneficiary: [5](#0-4) 

and `onPostRequestTimeout()` similarly refunds `message.amount` to the original sender on the source chain: [6](#0-5) 

Because the amounts promised (`message.amount`) are never reconciled against amounts actually escrowed, every `send()` call with such a token under-collateralizes the wrapper by the fee/rebase delta. This deficit accumulates across all users of that deployment (each `WrappedHyperFungibleToken` custody pool is shared across all senders/receivers for a given underlying token and chain pair).

### Impact Explanation
Each `send()` with a fee-on-transfer/deflationary/rebasing underlying token leaves the wrapper holding strictly less of the underlying than the sum of `message.amount` values it has promised to honor via `onAccept` (destination unlock) or `onPostRequestTimeout` (source refund). As more such transfers accumulate, the contract's actual underlying balance falls behind its total obligations. Eventually, a legitimate `onAccept` or `onPostRequestTimeout` call for some other user's message will attempt to `safeTransfer` more underlying than the contract holds and revert, permanently freezing that user's funds (their tokens were burned/locked on the source side but can never be unlocked/refunded). Users who transact earlier can drain the shared pool at others' expense, effectively front-running the insolvency. This is a shared-custody-pool insolvency/fund-freezing bug reachable by any single unprivileged `send()` call, matching the analog root cause from the Metrom report (rebasing/deflationary token balance mismatch leading to reverts on downstream operations).

### Likelihood Explanation
Likelihood depends on the operator configuring `WrappedHyperFungibleToken` with a fee-on-transfer, deflationary, or rebasing ERC20 as `underlying` via `configure()`. Since "any ERC20 is allowed" per the analog report's premise and this contract is explicitly designed as a generic wrapper for "existing ERC20 tokens" (per its NatSpec), and no allow-list/weird-token restriction exists in this file, deployment against such a token is plausible and the bug triggers on the very first `send()` call — no special conditions or repeated interactions needed beyond normal use.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.placeOrder()`: measure the underlying token balance of the contract before and after `safeTransferFrom` in `send()`, and use the actual received delta (not `params.amount`) as `Message.amount` in the dispatched request. Reject sends where the received amount differs from the requested amount if exact-amount semantics are required, or explicitly document that this contract's custody pool is limited to standard (non-fee-on-transfer, non-rebasing) ERC20s, e.g. by validating expected behavior at `configure()` time.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `underlying` set to a fee-on-transfer token (e.g., 1% fee) and registers a peer on chain B.
2. User A calls `send({amount: 1000e18, ...})` on chain A. `safeTransferFrom` pulls only 990e18 into the contract (1% fee burned/redirected), but the dispatched `Message.amount` is `1000e18`.
3. The relayed message is delivered to chain B; `onAccept` mints/unlocks `1000e18` to the beneficiary from the wrapper's custody pool there, i.e., 10e18 more than was actually escrowed on chain A for this transfer.
4. Repeat with more users; the aggregate deficit grows. Eventually a subsequent user's legitimate `onAccept` or `onPostRequestTimeout` call attempts `safeTransfer` for an amount exceeding the contract's actual underlying balance and reverts, permanently freezing that user's bridged funds. This is directly analogous to the referenced `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived` test pattern that had to be added to `IntentGatewayV2` — no such protection exists for `WrappedHyperFungibleToken`.     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
