## Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a given shop as long as `Utils::HmacValidator.validate(request)` succeeds. However the HMAC signature only ever covers the raw request body — never the `shopify-shop-domain` header that the library (and the app built on top of it) uses to determine *which tenant* the webhook belongs to. This breaks the identity binding `hmac_covers(fields) == fields_trusted_for_tenant_identification`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no further verification: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature purely from `to_signable_string` (i.e., the body) against the app-level `Context.api_secret_key`: [3](#0-2) 

`Registry.process` accepts any request whose body HMAC validates, then forwards `request.shop` — taken directly from the unauthenticated header — to the app's handler as the tenant identifier, with no cross-check that the HMAC-signing key/context actually belongs to that shop: [4](#0-3) 

Because `Context.api_secret_key` is the **app's single client secret**, shared across every shop that installs the app (not a per-shop secret), any unprivileged merchant who installs the public app can:
1. Receive a legitimately signed webhook for their *own* shop (valid body + valid HMAC, since it is signed with the same secret used for all installs).
2. Replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim's shop domain).
3. `HmacValidator.validate` still succeeds, because it never inspects the shop header — only the body bytes are covered.
4. `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

This is precisely the "field acted on but not covered by the HMAC" analog from the report: the withdrawal amount wasn't checked against available collateral before use, just as the shop domain isn't checked against what was actually signed before being used to select tenant data/behavior.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (or `request.shop`) to look up per-tenant session/data (a documented, expected usage pattern) can be tricked into writing/reading/acting on data under a victim shop's identity using attacker-controlled webhook payload content. This is a cross-tenant access vector: a single low-privilege app installer (any merchant who installs the app) can forge events attributed to any other shop that uses the same app installation's client secret.

### Likelihood Explanation
Requires only that the attacker be a legitimate but unprivileged installer of the target app (no special access, no leaked credentials beyond what any installer already legitimately receives via their own webhook deliveries). The `api_secret_key` is shared per-app, not per-shop, so this path is broadly reachable for any public/multi-tenant app built with this gem.

### Recommendation
Bind the shop identity into the value that is cryptographically verified before it is trusted for tenant routing — e.g., require the webhook handler/registry to cross-validate `request.shop` against the shop the webhook subscription was registered for (via `webhook_id`/topic ownership lookup) rather than trusting the header value merely because the body HMAC validated, or document/enforce that consumers must not use `request.shop` as a sole tenant key without an independent shop-ownership check.

### Proof of Concept
1. App merchant M1 installs the target Shopify app; app receives a legitimate webhook: body `B`, header `shopify-shop-domain: shop1.myshopify.com`, header `shopify-hmac-sha256: HMAC(secret, B)`.
2. M1 (attacker) resends `POST /webhooks` to the app with the same body `B` and same valid `hmac` header, but sets `shopify-shop-domain: shop2.myshopify.com` (a different, victim shop that installed the same app).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (all required headers present).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)` — which only rehashes `B`, matches, returns `true`.
5. Handler is invoked with `WebhookMetadata.new(shop: "shop2.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data as if it originated from `shop2`. [5](#0-4) [6](#0-5)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []

          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          else

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
