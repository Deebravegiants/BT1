### Title
Excess native-token payment sent to `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host itself instead of the caller, permanently trapping the caller's ETH - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and forward it to `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), ...)`. This mirrors the `OperatorProposal` bug class: value is forwarded to an external call that may not consume all of it, and the excess is refunded by the *callee* to its immediate caller — which is `EvmHost` itself, not the original transaction sender — and `EvmHost` never forwards that excess back out.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
the swap call's return value (`amounts`) is discarded entirely — the code does not even capture it. Any wrapper used as `_hostParams.uniswapV2` (e.g. `UniV3UniswapV2Wrapper.swapETHForExactTokens` / `UniV4UniswapV2Wrapper.swapETHForExactTokens`, or a standard `UniswapV2Router02`) refunds unspent ETH to `msg.sender` of that inner call: [2](#0-1) [3](#0-2) 
Since `EvmHost` is the caller of the router/wrapper, that refund lands in `EvmHost`'s own balance, not back to the user who originally called `dispatch()`/`fundRequest()` with excess `msg.value`. `EvmHost` has no subsequent step that measures the actual amount spent and returns the difference to `_msgSender()`. The identical pattern is repeated in `dispatch(DispatchGet)`: [4](#0-3) 
and in `fundRequest()`: [5](#0-4) 

This is directly analogous to the `OperatorProposal` finding: ETH sent along with a call is spent by a downstream contract that may not use all of it, the leftover is sent back to the immediate caller of the downstream contract, and that immediate caller (here, `EvmHost`) fails to relay the leftover back to the original externally-owned sender, resulting in silent, permanent loss of the excess ETH for the caller.

By contrast, the codebase's own `IntentGatewayV2.placeOrder` correctly avoids this trap by capturing the swap's returned `amounts[0]` and explicitly computing/forwarding the remainder to `msg.sender`: [6](#0-5) 
`EvmHost` has no equivalent accounting/refund step, so this specific vulnerability appears real and unmitigated for direct `EvmHost.dispatch()` / `fundRequest()` callers.

### Impact Explanation
Any user or contract calling `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native token payment providing `msg.value` greater than the exact amount of native token needed to swap for `post.fee`/`amount` fee-tokens loses the difference permanently — it becomes stuck in `EvmHost`'s balance with no code path to reclaim or forward it to the caller. Because it is difficult for callers to predict the *exact* AMM-determined native-token cost of a given fee-token amount at execution time (price can move between quote and execution, and `HyperApp.dispatchWithFeeToken`/direct callers must estimate `msg.value` up front), any caller who slightly over-provisions ETH for safety suffers an unrecoverable loss. This is a direct loss of funds for the caller (Medium severity per the analogous report and sponsor's own confirmation of the pattern).

### Likelihood Explanation
High likelihood of occurrence in normal operation: callers dispatching a message with native-token payment must estimate `msg.value` before the AMM swap executes, and Uniswap V2 exact-output pricing fluctuates with pool state, so exact-match payments are effectively unachievable in practice — over-payment (and thus loss) is the common case, not an edge case. Any contract or user directly integrating with `EvmHost.dispatch`/`fundRequest` (rather than going through `IntentGatewayV2`'s more careful wrapper) is exposed.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and explicitly refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated `payer`), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Deploy `EvmHost` with `_hostParams.uniswapV2` pointing to a standard `UniswapV2Router02` (or the repo's `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper`).
2. Call `dispatch(DispatchPost)` (or `fundRequest`) with `msg.value` set intentionally higher than the ETH cost required to obtain `post.fee` fee-tokens (a realistic scenario given AMM price movement between quoting and execution).
3. Observe: `swapETHForExactTokens` spends only the exact ETH needed and refunds the remainder to `msg.sender` of that call, which is the `EvmHost` contract address (verifiable since `EvmHost.dispatch` never reads/uses the returned `amounts` array).
4. Check the original caller's ETH balance after the transaction: it is reduced by the *full* `msg.value` sent, not just the amount actually consumed by the swap — the difference is now sitting in `EvmHost`'s contract balance with no function exposed to return it to the caller.
