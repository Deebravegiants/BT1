### Title
Front-running a single leaf in a `HandlerV2` batch reverts the entire relayer submission, blocking delivery of unrelated messages - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` are unprivileged, public entry points that accept a batch of leaves plus a single membership proof, and for each leaf perform a hard-revert duplicate check against `EvmHost`'s receipt mappings before dispatching. Because these checks abort the *entire* transaction rather than skipping the already-delivered leaf, anyone can front-run a legitimate relayer's batch by resubmitting just one of its leaves (with a validly re-derived proof) ahead of it, causing the honest relayer's whole multi-message batch to revert with `DuplicateMessage()` — mirroring the reported `DKIMRecoverySigValidator` pattern where a front-runner sets a "done" flag for the exact arguments a legitimate caller is about to use, causing the real transaction to revert on its “already done” check.

### Finding Description
`handlePostRequests` verifies a Merkle Mountain Range proof once for the whole batch of `PostRequestLeaf`s, then loops over each leaf and reverts the whole call if any single leaf commitment is already marked as delivered: [1](#0-0) 

The same all-or-nothing pattern exists for GET responses: [2](#0-1) 

The replay-protection state (`_requestReceipts` / `_responseReceipts`) that these checks read is only mutated by `EvmHost.dispatchIncoming`, which is itself gated to the handler: [3](#0-2) [4](#0-3) 

However, `handlePostRequests`/`handleGetResponses` themselves are not access-controlled — any address can call them with a proof for messages that are already committed on the source chain (the state commitment and message contents are public once relayed to Hyperbridge). Because the source chain's request/response commitments and Hyperbridge's overlay root are public data, an attacker can observe an honest relayer's pending batch transaction in the mempool, extract a single leaf plus a valid sub-proof for it, and submit a minimal one-leaf transaction with higher gas to land first. That transaction succeeds and marks the corresponding receipt as delivered. When the honest relayer's original larger batch transaction is then mined, the loop hits `host.requestReceipts(leaf.request.hash()) != address(0)` for that one already-delivered leaf and reverts `DuplicateMessage()` for the *entire* batch — including all the other, distinct messages bundled in it that were not yet delivered.

This is structurally the same bug class as the reported issue: a permissionless actor can pre-empt a call with the exact same identifying arguments to flip a "done" flag, causing the legitimate caller's transaction (which bundles that same identifier among others) to revert via an existence/duplicate check, with no precondition beyond visibility of the pending call.

### Impact Explanation
The impact is a delivery-availability regression rather than fund theft: the front-run relayer's transaction reverts and must be resubmitted (typically excluding the already-delivered leaf), wasting gas and delaying delivery of every other message bundled in that batch. For latency-sensitive cross-chain flows (e.g., large batched settlement or liquidation messages), an attacker can selectively grief specific batches by repeatedly front-running one cheap leaf out of an expensive batch, forcing costly re-batching and delivery delays — a "route unable to deliver messages" condition for the duration of the griefing. It does not by itself permanently freeze funds, since the remaining messages can be resubmitted in a new batch, but it materially degrades the reliability guarantee that a relayer's proof-verified batch will be delivered atomically.

### Likelihood Explanation
Likelihood is high for any relayer that batches multiple messages under one proof: no special permission, secret, or race against consensus is needed — the attacker only needs to observe a pending `handlePostRequests`/`handleGetResponses` transaction (or independently construct a competing one-leaf proof from the same finalized state commitment) and outbid it in gas. This applies to every call to these two functions, with no precondition beyond a state commitment already being available on `EvmHost` (`stateMachineCommitment` non-zero and challenge period elapsed).

### Recommendation
Do not let a single already-delivered leaf abort the whole batch. Instead of `revert DuplicateMessage()` inside the per-leaf loop in `handlePostRequests`/`handleGetResponses`, skip leaves whose receipt already exists (mirroring how `EvmHost.dispatchIncoming` itself tolerates a failed downstream call by rolling back only that leaf's receipt) and continue dispatching the rest of the batch. This preserves idempotency for the "first relayer wins" reward semantics while preventing one contested/duplicate leaf from denial-of-servicing an entire otherwise-valid batch.

### Proof of Concept
1. Honest relayer submits `handlePostRequests(host, msg)` with a batch of N `PostRequestLeaf`s (leaf₀ … leaf_{N-1}), including a valid `MerkleMountainRange` multiproof against the current `overlayRoot`.
2. Attacker observes this pending transaction in the mempool (or independently reconstructs proof data for `leaf₀` from the same finalized Hyperbridge state), and submits `handlePostRequests(host, attackerMsg)` containing only `leaf₀` and a valid single-leaf sub-proof, with higher gas price.
3. Attacker's transaction lands first: `host.dispatchIncoming(leaf₀.request, attacker)` runs, setting `_requestReceipts[leaf₀.request.hash()] = attacker` per `evm/src/core/EvmHost.sol` lines 806-807.
4. The honest relayer's original batch transaction is then mined; in the loop at `evm/src/core/HandlerV2.sol` lines 204-209, the check `host.requestReceipts(leaf₀.request.hash()) != address(0)` is now true, so the call reverts `DuplicateMessage()` for the whole batch — leaf₁ … leaf_{N-1} are not delivered even though they were never delivered before and remain valid.
5. Honest relayer must resubmit a new batch excluding `leaf₀`, incurring wasted gas and delivery delay for leaf₁…leaf_{N-1}.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
