### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the webhook HMAC over the raw body only, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are taken from unauthenticated HTTP headers that are never included in the signed data. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` header to build the `WebhookMetadata` object handed to the host application's handler, which the gem's own documentation instructs developers to use as the tenant identifier.

### Finding Description
The HMAC binding that should hold is:
`HMAC(secret, signed_bytes) == signature` implies `signed_bytes` (and everything acted upon) is exactly what Shopify sent for shop `S`.

Instead, `to_signable_string` only returns `@raw_body`: [1](#0-0) 

while `shop` is read straight from the `shop-domain` header, outside the signed data: [2](#0-1) 

`HmacValidator.validate` verifies exactly `to_signable_string` (i.e., only the body) against the secret: [3](#0-2) 

`Registry.process` accepts any request whose body HMAC validates, then passes the unauthenticated `request.shop` header straight into `WebhookMetadata` given to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is documented as "The shop domain of the webhook" and is the field host apps are told to key their tenant-scoped processing on: [5](#0-4) [6](#0-5) 

Because all shops that install a given app share the same `api_secret_key`, an HMAC computed over a given body is valid regardless of which shop it is claimed to belong to. Any merchant who has installed the app can capture a legitimate webhook delivery to their own store (a valid `body` + valid `x-shopify-hmac-sha256` for that body), then resend it to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the (unmodified) body, and `Registry.process` will invoke the handler with `data.shop` set to the victim's domain while `data.body` is fully attacker-controlled (limited to whatever body they can obtain a valid signature for, e.g. from their own store's webhooks).

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-upon binding described in the rules: the request is authenticated only for "some HMAC-valid body", not for "this body belongs to this shop". A host application using this gem as documented will process attacker-supplied webhook data under another tenant's identity — a cross-tenant access/injection issue. Depending on the topic (e.g. `orders/create`, `app/uninstalled`, `shop/update`), this can lead to fabricated business data being attributed to a victim shop, or forged deletion/uninstall-triggered flows being run against a tenant the attacker doesn't own.

### Likelihood Explanation
Likelihood is high for any multi-tenant app: no access to `api_secret_key`, access token, or any privileged credential is required. The attacker only needs to be a legitimate installer of the app for their own shop (an "unprivileged" tenant relative to others) to obtain one valid `(body, hmac)` pair, then simply replay it with a modified `shop-domain` header value against the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/api_version/webhook_id) in the HMAC-signed data, or otherwise cryptographically bind the `shop-domain` header to the signature before trusting it as the tenant identifier in `WebhookMetadata`. At minimum, `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` should not allow a body signed for one shop to be replayed as if it belonged to another.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a real webhook, e.g. body `{"id":1,...}` with headers `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256` computed by Shopify over that body.
2. Attacker resends the identical raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the request; `HmacValidator.validate` computes the HMAC over `@raw_body` only and it matches (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim.myshopify.com"` and the attacker's body, even though Shopify never sent this event for `victim.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:188-200`).

          received_signature = verifiable_query.hmac
