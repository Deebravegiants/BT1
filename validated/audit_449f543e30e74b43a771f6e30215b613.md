### Title
Webhook shop/topic binding forged — HMAC covers only the raw body, not the `shop-domain`/`topic` headers used for tenant routing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `Utils::HmacValidator.validate` checks never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless uses the unauthenticated `request.shop` and `request.topic` values to route and label the payload delivered to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(..., verifiable_query.to_signable_string)` and compares it to the `hmac` field of the request: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be exactly `@raw_body` — nothing else: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then uses `request.topic` for handler dispatch and `request.shop` to construct the `WebhookMetadata` that is handed to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is:

`shop asserted to the app's handler == shop that Shopify actually generated/signed this payload for`

Because the HMAC only signs `@raw_body`, this equality is never checked. Any `(raw_body, hmac)` pair that is valid for *some* shop under the app's `client_secret` will pass `HmacValidator.validate` regardless of which `shop-domain` header accompanies it, because the header is not part of the signed content.

### Impact Explanation
A Shopify app's `client_secret` is shared across every shop that installs the app — it is not per-tenant. An unprivileged internet user can:
1. Create their own free/dev Shopify store and install the target app (no special privileges, no victim credentials needed).
2. Receive a genuine webhook for their own store — a real `(raw_body, x-shopify-hmac-sha256)` pair, correctly signed with the app's `client_secret`.
3. Replay that exact `raw_body` + `hmac` to the app's public webhook endpoint, but substitute the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header with a victim shop's domain / a different topic.
4. `HmacValidator.validate` still succeeds (it only checks the body bytes), so `Registry.process` dispatches the handler with `WebhookMetadata` claiming the event came from the victim shop.

Since apps typically use the `shop` value from `WebhookMetadata` to look up the corresponding merchant session/access token or to write into per-tenant storage, this breaks tenant isolation — attacker-controlled/forged event data can be attributed to, and processed against, a shop the attacker does not control. This is a cross-tenant confusion condition reachable without any credential belonging to the victim or the app.

### Likelihood Explanation
Exploitation requires only the ability to (a) install the app on an attacker-owned store to obtain one genuine `(body, hmac)` sample, and (b) send an arbitrary HTTP POST to the app's public webhook endpoint with forged headers — both trivially available to an unprivileged internet user. No `api_secret_key`, access token, or victim credential is required.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content, or otherwise cryptographically bind them to the body before computing/verifying the HMAC, e.g.:

```ruby
def to_signable_string
  "#{shop}|#{topic}|#{webhook_id}|#{@raw_body}"
end
```

so that forging any of these fields invalidates the HMAC, matching Shopify's actual webhook-signing contract where the signature is meant to authenticate the whole delivery, not merely the JSON body.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and captures a genuine webhook delivery:
raw_body = '{"id": 1, "note": "legit event for attacker shop"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays the SAME body/hmac pair, but forges the shop header
#    to point at a victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation succeeds because to_signable_string only checks raw_body
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches the handler believing this event
#    originated from "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
```
