### Title
Incorrect Decimal Conversion in `pallet-hyper-fungible-token` Causes Unbacked Cross-Chain Mint/Burn Amount Mismatch - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers `convert_to_balance` and `convert_to_erc20` use `saturating_sub` to compute the scaling exponent between the local asset's decimals and the remote ERC20 token's decimals. When the local asset has **more** decimals than the registered remote (`erc_decimals`), the subtraction saturates to `0`, and the functions silently skip the required scaling instead of dividing/multiplying in the correct direction. This is the same decimal-conversion class of bug described in the external report (imprecise conversion between differing token decimals producing incorrect balances), but here it also corrupts the cross-chain `Message.amount` that is dispatched to (or received from) the EVM `HyperFungibleToken`/`BridgeToken` contracts, which mint/burn using that raw amount with no additional scaling.

### Finding Description
`convert_to_balance` and `convert_to_erc20` are defined as: [1](#0-0) 

```
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions only handle the case `erc_decimals >= local_decimals` correctly (division/multiplication by `10^(erc_decimals - local_decimals)`). When `local_decimals > erc_decimals`, `saturating_sub` returns `0`, so the exponent becomes `10^0 = 1` and **no scaling is applied at all**, even though the correct behavior would be to scale in the opposite direction (multiply in `convert_to_balance`, divide in `convert_to_erc20`).

This is exercised on the `send` extrinsic — reachable by any signed account, i.e. an unprivileged relayer/dispatcher analog: [2](#0-1) 

Here `erc_decimals` comes from the admin-configured `Precisions` storage for the destination chain, and `decimals` is the local asset's own decimals (which can be set arbitrarily via `pallet-assets`, e.g. `18`). If the destination EVM token declares fewer decimals than the local asset (e.g. `erc_decimals = 6`, `local_decimals = 18`), `convert_to_erc20(amount, 6, 18)` returns `amount` unchanged instead of `amount / 10^12`, inflating the on-chain `Message.amount` encoded into the dispatched ISMP request by a factor of `10^12`.

The same flaw exists symmetrically in the receive/timeout paths, which convert an incoming ERC20 amount back to the local balance type: [3](#0-2) [4](#0-3) 

On the EVM side, `HyperFungibleToken`/`BridgeToken` mint/burn the raw `message.amount` value directly with no further decimal conversion (confirmed by the doc comment noting the EVM contract itself is fixed at 18 decimals and any scaling must happen in the pallet): [5](#0-4) 

Since minting/burning on the EVM side trusts the pallet's computed `Message.amount` verbatim, a broken conversion on the substrate side directly translates into an incorrect number of tokens minted or burned cross-chain, with no independent validation to catch the discrepancy.

### Impact Explanation
When a local asset's decimals exceed the registered remote ERC20 decimals for a destination chain (a valid, admin-set configuration since `pallet-assets` decimals are arbitrary and independent from EVM token decimals), `send()` computes an `erc20_amount` that is not scaled down. This causes the dispatched message to claim mint amount `10^(local_decimals - erc_decimals)` times larger than the amount actually escrowed/burned locally. Because the remote `HyperFungibleToken`/`BridgeToken` contract mints exactly `message.amount` upon `onAccept`, this results in an unbacked over-mint on the destination chain — a direct loss/inflation of protocol funds, matching the "unbacked mint" acceptance criterion. The reverse direction (`convert_to_balance` under-scaling on receipt) instead permanently strands/burns value that can never be credited back correctly, a fund-freezing outcome.

### Likelihood Explanation
This is triggered by any account calling the public, signed `send` extrinsic on an asset/destination pair where `local_decimals > erc_decimals` — no special privilege required beyond having the asset registered (a routine governance action performed for legitimate cross-chain assets, e.g. an 18-decimal substrate asset bridged to a 6-decimal wrapped ERC20 representation). No malicious admin/governance/relayer collusion is needed; a correctly-configured asset with this decimal relationship makes every `send` call miscompute the bridged amount.

### Recommendation
Fix `convert_to_balance` and `convert_to_erc20` to handle both directions explicitly instead of relying on `saturating_sub`:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
Add regression tests covering `local_decimals > erc_decimals` for both `send`/`on_accept`/`on_timeout` paths.

### Proof of Concept
1. Register a local asset with `decimals = 18` and set `Precisions[asset_id][dest_chain] = 6` (a valid remote ERC20 with 6 decimals, e.g. USDC-style wrapped representation).
2. Call `send(SendParams { asset_id, destination: dest_chain, amount: 1_000_000_000_000_000_000 (1 token, 18 decimals), ... })`.
3. Inside `send`, `erc_decimals = 6`, `decimals = 18`; `convert_to_erc20(1e18, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, so `erc20_amount = 1e18` is dispatched unchanged in the `Message.amount` field, instead of the correct `1e18 / 10^12 = 1_000_000` (1 token at 6 decimals).
4. On the destination EVM chain, `HyperFungibleToken.onAccept` mints `1e18` raw units directly (interpreted at its native decimals), producing a mint amount `10^12` times larger than the single token that was actually escrowed/burned on the source chain — an unbacked mint of destination tokens. ///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
