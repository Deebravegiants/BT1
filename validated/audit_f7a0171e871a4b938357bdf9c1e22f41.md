### Title
Unprotected subtraction `assetReserve - virtualLtReserve` in `Bonding.canGraduate`/`_prepareGraduationLiquidity` lacks the saturating guard used elsewhere in the same contract - (File: packages/contracts/src/Bonding.sol)

### Summary
This is the same bug class as the GaugeController `Math.max` mix-up: a subtraction meant to strip out a "virtual"/base component from a raw value is implemented with an unprotected `a - b` in one code path, while functionally identical subtractions elsewhere in the very same file (`_ltSwapInventory`, `_routerDepositAndDispose`, `finalizeGraduation`'s `protectedLT` calc) are deliberately written with a saturating `a > b ? a - b : 0` guard, with comments explicitly calling out that this is done "so a future violation of the invariant can't brick" the function with a Panic. The `assetReserve - _launchTimeVirtualLtReserve(...)` subtraction in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity` has no such guard.

### Finding Description
`Bonding.canGraduate` computes the USD-trigger leg as: [1](#0-0) 
and `_prepareGraduationLiquidity`, called from `_enterGraduating` on every threshold-crossing buy, repeats the identical pattern: [2](#0-1) 

`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT seed as `Pair.k() / Token.TOTAL_SUPPLY()`, a value derived from immutable, never-updated state (`Pair.k` is set once in `Pair.mint` and never touched by `Pair.swap`) [3](#0-2) . Meanwhile `assetReserve` is the pair's live, mutable stored reserve, updated by every buy/sell through `Pair.swap`, which itself tolerates a `+1` K-invariant slack: `(newTokenReserve+1)*(newAssetReserve+1) >= k` rather than an exact equality [4](#0-3) .

The developers were clearly aware that "balance below expected floor" states are reachable in this codebase — they wrote saturating-subtraction helpers for exactly this reason elsewhere: [5](#0-4) [6](#0-5) 

But the `assetReserve - virtualLtReserve` computation — which is on the hot path of *every* buy (via `canGraduate` in `_executeBuy`) and of phase-1 graduation (`_prepareGraduationLiquidity`) — uses a bare `-`. This is structurally the same class of mistake as the GaugeController report: a subtraction meant to be underflow-safe (and treated as underflow-safe by sibling code in the same file) is left unguarded in one specific call site, because the invariant that "stored `assetReserve` can never fall below the immutable virtual seed" is assumed to hold by construction rather than defended in code.

### Impact Explanation
If this invariant were ever violated — e.g. by a future code change to `Pair.swap`/`Router` that changes how `assetReserve` is updated, by a new LT/pair implementation, by a Router upgrade (`Router.sol` is explicitly documented as effectively-frozen but not literally immutable across a full re-deploy), or by any accounting drift introduced by future maintenance touching the graduation math (which `AGENTS.md` explicitly warns is "the most bespoke piece of the protocol" and easy to get wrong) — the unguarded subtraction reverts with a raw arithmetic `Panic(0x11)` instead of failing gracefully. Because `canGraduate` is invoked inside `_executeBuy` on **every** buy, and `_prepareGraduationLiquidity` is invoked inline at the exact moment a curve crosses its graduation threshold, an underflow here would:
- Permanently DoS `Zap.buy` for the affected token (every buy calls `canGraduate` → revert), freezing all trader funds already routed into that curve since sells are separately rate-limited by the LT's redemption buffer, and
- Brick the graduation transition itself if it fires inside `_enterGraduating`, leaving the token stuck mid-lifecycle with curve-raised LT and the 250M token LP reserve parked in `Bonding` with no phase-2 path forward (since `_enterGraduating` itself would never complete to flip the lifecycle and cache `pendingGraduation`).

This matches the C4 report's own characterization ("preventing votes for the user" / DoS on a core user-facing action), scaled to alt.fun's equivalent action (buys/graduation) rather than voting.

### Likelihood Explanation
Low-to-medium under the current, audited AMM math: the existing analysis in the repo (and the `test_donation_realBalanceExceedsReserveToken` regression test, which fixed a **very similar prior underflow** in `previewLtUntilGraduation`'s supply leg caused by a token-donation attack) shows the team has already hit real-world cases where "safe by construction" reserve assumptions broke under donation/dust attacks. `previewLtUntilGraduation`'s supply-trigger leg was patched with a `realBalance >= reserveToken` guard after exactly this failure mode was found [7](#0-6) , but the analogous USD-trigger leg subtraction (`assetReserve - virtualLtReserve`) in the same function, in `canGraduate`, and in `_prepareGraduationLiquidity` was left as a bare, unguarded subtraction. Given the demonstrated history of this exact reserve-accounting invariant being violated once already on the token side, the LT side is a plausible target for the same class of regression, especially across future upgrades to `Router`/`Pair` or LT integrations.

### Recommendation
Apply the same saturating-subtraction pattern already used in `_ltSwapInventory` / `_routerDepositAndDispose` / `finalizeGraduation` to every `assetReserve - _launchTimeVirtualLtReserve(...)` call site (`canGraduate`, `previewLtUntilGraduation`'s USD leg, and `_prepareGraduationLiquidity`):
```solidity
uint256 realLtRaised = assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0;
```
This converts a potential hard revert/Panic-based DoS into a benign `0`, consistent with how the team already treats the sibling invariant on the token-reserve side.

### Proof of Concept
Not exploitable purely from the current, in-scope Pair/Router math as verified: `Pair.swap`'s exact-floor-division `assetOut` computation in `Router._computeSell` and the token-side conservation invariant (`tokenReserve == realBalance + LP_RESERVE`, verified by `test_inv_virtualReserveAlwaysExceedsRealBalance`) together guarantee `assetReserve` cannot legitimately drop below the recovered `virtualLtReserve` through any sequence of ordinary buys/sells reachable by an unprivileged trader today. I could not construct a concrete unprivileged-caller transaction sequence, within the current `Router.sol`/`Pair.sol` code as read, that drives `assetReserve` below `virtualLtReserve`, so I cannot demonstrate on-chain impact with today's code. The finding is reported as a code-quality/defense-in-depth gap analogous to the report's bug class (missing underflow guard on a subtraction that sibling code in the same contract treats as unsafe) rather than a proven, currently-exploitable underflow — flagging it because the guard is inconsistent within the same file and the identical invariant class (reserve-vs-virtual-seed) has already broken once on the token side (`previewLtUntilGraduation`'s donation-attack regression).

        uint256 assetIn,

        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();
