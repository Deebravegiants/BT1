### Title
`CostTracker` block cost can wrap/underflow when removing a transaction cost larger than what was actually added, causing stuck block-cost accounting - ([File: cost-model/src/cost_tracker.rs])

### Summary
The KangarooVault bug is a class of "internal accounting counter can go out of sync with the real quantity it tracks, and later arithmetic on that counter uses unchecked/plain subtraction instead of validating the invariant." The Agave analog is `CostTracker::block_cost`, a `SharedBlockCost` (backed by a plain `AtomicU64`), which is incremented via `add_transaction_execution_cost` and decremented via `sub_transaction_execution_cost`/`remove()` using raw, non-checked `fetch_add`/`fetch_sub` on the atomic [1](#0-0) .

### Finding Description
`CostTracker::try_add` calls `add_transaction_cost`, which increments both the per-account cost map (via `saturating_add`) and `block_cost` via `SharedBlockCost::fetch_add` [2](#0-1) . `CostTracker::remove` calls `remove_transaction_cost` → `sub_transaction_execution_cost`, which decrements the per-account map with `saturating_sub` (safe) but decrements `block_cost` with `SharedBlockCost::fetch_sub`, which is a plain `AtomicU64::fetch_sub` with **no saturating/checked semantics** [3](#0-2) [4](#0-3) .

This mirrors the KangarooVault pattern exactly: `block_cost` (analogous to `usedFunds`/`totalFunds`) is adjusted by two independent code paths (`try_add` when a transaction cost is provisionally reserved, and the "actual cost" update/removal after execution based on `executed_units` reported by SVM), and there is no invariant check ensuring the amount being subtracted was actually present in `block_cost`. If `remove()` (or the "adjust down" path used to true-up estimated vs. actual execution cost, exercised by `test_adjust_transaction_execution_cost` [5](#0-4) ) is ever invoked with a cost value greater than what is currently accounted for in `block_cost` (e.g., due to a mismatch between the transaction's estimated cost added pre-execution and its actual executed cost calculated post-execution via `CostModel::calculate_cost_for_executed_transaction` in `runtime/src/transaction_execution.rs` [6](#0-5) ), `AtomicU64::fetch_sub` wraps around to a value near `u64::MAX` instead of erroring or saturating.

### Impact Explanation
If `block_cost` wraps to a near-`u64::MAX` value, `CostTracker::would_fit` will reject essentially every subsequent transaction for the rest of that bank/slot with `WouldExceedBlockMaxLimit` [7](#0-6) , since `self.block_cost().saturating_add(cost) > self.limits.block_cost` will always be true. This is the direct structural analog to KangarooVault being permanently unable to close trades once `usedFunds > totalFunds`: the tracker becomes permanently (for that bank) unable to admit new work, effectively halting transaction packing/inclusion for that block — a liveness/DoS condition on block production rather than a fund-loss condition.

### Likelihood Explanation
I was not able to fully verify, within the available tool budget, a concrete unprivileged-user-triggerable call sequence where `remove()`/the "adjust down" path is invoked with a cost strictly greater than the amount currently tracked for that transaction in `block_cost` (this requires deeper tracing through `core/src/banking_stage/consumer.rs`, which I confirmed references `cost_tracker`/`update_execution_cost`/`remove(` but did not have remaining iterations to fully read). The safe per-account `saturating_sub` next to the unchecked `block_cost.fetch_sub` strongly suggests this asymmetry is either intentionally relied upon (i.e., callers guarantee `remove` is only ever called with a previously-added, matching cost) or is a latent gap — this needs further code reading of `consumer.rs`'s cost-tracker interactions and the unified scheduler's equivalent paths to confirm reachability and rule out an invariant enforced elsewhere.

### Recommendation
Add a bounds/invariant check in `sub_transaction_execution_cost`/`SharedBlockCost::fetch_sub` (or the callers) so that `block_cost` cannot be decremented below zero, analogous to the KangarooVault report's recommendation to check `totalFunds >= usedFunds` before mutating either counter — e.g., use `fetch_update` with `checked_sub`/`saturating_sub` instead of raw `fetch_sub`, and assert/log if the value being removed exceeds the tracked amount for that account/block.

### Proof of Concept
Not independently reproduced end-to-end due to remaining investigation needed in `core/src/banking_stage/consumer.rs` to construct a concrete call sequence; the structural bug (unchecked `AtomicU64::fetch_sub` paired with a `saturating_add`-based increment path with no matching invariant check) is demonstrated at [1](#0-0)  and exercised (without an over-subtraction case being tested) by the existing unit tests [8](#0-7) .

/// Wrapper around blockcost to allow fast sharing of the value without locking.
/// Value is read-only outside of cost-tracker.
#[derive(Debug, Clone)]
pub struct SharedBlockCost(Arc<AtomicU64>);

impl SharedBlockCost {
    pub fn new(value: u64) -> Self {
        Self(Arc::new(AtomicU64::new(value)))
    }

    fn fetch_add(&self, value: u64) -> u64 {
        self.0.fetch_add(value, Ordering::Release)
    }

    fn fetch_sub(&self, value: u64) -> u64 {
        self.0.fetch_sub(value, Ordering::Release)
    }

    pub fn load(&self) -> u64 {
        self.0.load(Ordering::Acquire)
    }
}

// Get actual transaction execution costs from transaction commit results
fn get_transaction_costs<'a, Tx: TransactionWithMeta>(
    bank: &Bank,
    commit_results: &[TransactionCommitResult],
    sanitized_transactions: &'a [Tx],
) -> Vec<Option<TransactionCost<'a, Tx>>> {
    assert_eq!(sanitized_transactions.len(), commit_results.len());

    commit_results
        .iter()
        .zip(sanitized_transactions)
        .map(|(commit_result, tx)| {
            if let Ok(committed_tx) = commit_result {
                Some(CostModel::calculate_cost_for_executed_transaction(
                    tx,
                    committed_tx.executed_units,
                    committed_tx.loaded_account_stats.loaded_accounts_data_size,
                    &bank.feature_set,
                ))
            } else {
                None
            }
        })
        .collect()
}
