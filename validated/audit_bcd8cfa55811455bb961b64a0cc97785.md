### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` identifier that is handed to the app's webhook handler as the authoritative tenant, however, comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed material [2](#0-1) . Because the webhook signing secret (`Context.api_secret_key`) is the app's single client secret shared by every shop that installs the app — not a per-shop secret — any shop that installs the app can obtain a validly-HMAC'd `(body, hmac)` pair from its own legitimate webhook deliveries and replay it to the app's webhook endpoint with an arbitrary `shop-domain` header, causing the handler to execute attributing the event to a victim shop it never came from.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show that the signable material is exactly `@raw_body`: [3](#0-2) [4](#0-3) 

The `shop` accessor simply reads an unauthenticated header: [5](#0-4) 

`HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` field, never touching `shop`, `topic`, `webhook_id`, or `api_version`: [6](#0-5) 

`Registry.process` accepts the request once that body-only HMAC passes, then dispatches to the handler using the unauthenticated `request.shop`: [1](#0-0) 

Because `Context.api_secret_key` is the app's single OAuth client secret — identical for every shop that installs the app, not scoped per-tenant — a malicious (but otherwise completely unprivileged) merchant who installs the app on their own store can:
1. Cause any webhook topic to fire on their own shop, obtaining a `(raw_body, hmac)` pair that is fully valid according to `HmacValidator` (since the secret is the same for all installs).
2. Replay that exact body+HMAC to the app's public webhook endpoint, substituting the `shop-domain` header with any other installed shop's domain (or a domain that hasn't installed the app at all, if the app doesn't restrict which shops it accepts webhooks for).
3. `Registry.process` validates the HMAC successfully (it never checked `shop`) and invokes the handler with `WebhookMetadata#shop` set to the attacker-chosen value, confirmed by test expectations: [7](#0-6) .

This breaks the identity binding "the shop that produced/authenticated this webhook == the shop the gem attributes the resulting action to," letting one tenant's authenticated event be replayed under another tenant's identity.

### Impact Explanation
This is a cross-tenant confusion primitive: any application built on this gem that trusts `WebhookMetadata#shop` (returned by `ShopifyAPI::Webhooks::Registry.process`) as the authoritative tenant for side effects (writing per-shop data, revoking access, processing `app/uninstalled`, GDPR/customer data requests, billing events, etc.) can be made to act on behalf of a shop the request did not actually originate from, using data/body content chosen by the attacker's own store. This matches the Critical "cross-tenant access" impact category defined for this assessment.

### Likelihood Explanation
Exploitation requires no privileged credential, no access token, and no `client_secret`/TLS interception — only the ability to install the app on any shop (which for a public app is the normal, unprivileged install flow) and issue an HTTP replay with a different header value, both of which are within reach of an ordinary internet user/merchant.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is authenticated, not just the raw body — e.g., include the shop-domain header in the signable string used by `HmacValidator`, or independently verify that the `shop-domain` header matches a shop known to have a valid, active session/installation before invoking the handler.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic (e.g. `products/create`) to receive a body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (both signed with the app's shared `api_secret_key`, per `HmacValidator.validate`).
2. Send a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` accepts the request (`Utils::HmacValidator.validate` only checks `B`/`H`) and calls the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"`, as shown by `Request#shop` reading directly from the (attacker-controlled) header [5](#0-4)  and `Registry.process` passing it straight through [8](#0-7) .
