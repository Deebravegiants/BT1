### Title
Relayer fee balance is zeroed before delivery is guaranteed, permanently losing funds if the withdrawal request never lands - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in `pallet-relayer` dispatches an ISMP POST request instructing the destination to pay out a relayer's accrued fee, and unconditionally zeroes the `Fees` storage entry immediately afterward — before the destination chain confirms delivery/execution. The request is dispatched with `timeout: 0` (no expiry), so there is no timeout-refund path if delivery permanently fails. This mirrors the reported bug class: a reward/accounting entry is destroyed with no way for the beneficiary to reclaim it once the corresponding "token"/payout path is gone.

### Finding Description
`Pallet::withdraw` reads the relayer's accrued balance from `Fees::<T>`, dispatches an ISMP POST to the destination (either the substrate `HYPERBRIDGE_MODULE_ID` handler or the EVM `HostManager`), and then immediately zeroes the balance: [1](#0-0) 

The doc comment for this module explicitly acknowledges the assumption underpinning the design: "The on-chain effect is just dispatching the message; the destination chain settles the payout when the ISMP request is delivered there." [2](#0-1) 

Because the balance is zeroed at dispatch time rather than at confirmed-delivery time, and because the outbound `DispatchPost` is built with `timeout: 0` (i.e., never times out and can never trigger `on_timeout`/refund logic), any scenario where the destination-side execution permanently fails to credit the relayer leaves the `Fees` entry at zero with no recovery mechanism — the accrued reward is gone. Contrast this with the regular fee-escrow path in `pallet-ismp`'s dispatcher, where a payer's fee is only released/refunded on confirmed timeout or delivery: [3](#0-2) 

Concrete failure vectors that permanently orphan the payout, after the source-side `Fees` entry is already zeroed:
- On the substrate destination, the built-in `HyperbridgeWithdrawalModule::on_accept` only accepts messages whose `request.source` matches the configured `Coprocessor`; any mismatch (e.g., misconfiguration, or the module being removed/reconfigured on the destination) causes `on_accept` to error permanently, and since `timeout` is `0`, this request can never expire to trigger a refund: [4](#0-3) 

- On the EVM destination, the withdrawal is routed through `HostManager.onAccept`, which is gated by `restrict(incoming.relayer, _params.admin)` — only a single designated admin relayer may deliver it. If that admin key is lost, rotated incorrectly, or the destination `HostManager`/`fee_token` is reconfigured incompatibly with the encoded `WithdrawalParams.token`, the withdrawal can never be delivered, yet the source-side balance is already zero: [5](#0-4) 

This is analogous to the reported Olympus finding: a value (rewards) is destroyed from an internal accounting map based on an action (removing/losing the delivery path) that leaves no mechanism to reclaim the already-recorded value, even if the underlying configuration is later restored (the `Fees` entry is already `0`, so restoring the coprocessor id, admin key, or fee token does not restore the balance).

### Impact Explanation
This is a Medium-severity fund-loss bug: relayers permanently lose already-accrued protocol-owed fees if the one-shot, non-timing-out withdrawal message cannot be delivered/executed on the destination for any of the above reasons. Given `pallet-ismp` best practice (used elsewhere in this very codebase for regular fee escrow) is to refund on timeout, the omission of any such safety net here — combined with `timeout: 0` making the request un-timeoutable — converts a delivery failure into unrecoverable loss of relayer revenue.

### Likelihood Explanation
Likelihood is moderate: it does not require a malicious actor, only an operational/configuration mismatch on the destination side (coprocessor id drift, admin/relayer key rotation issues, or host-manager/fee-token reconfiguration) that causes the withdrawal `on_accept` to permanently fail while the source-side ledger has already been decremented to zero. Given relayer withdrawals are a routine, frequently exercised path (per the docs, auto-withdraw runs on a fixed interval), any transient destination misconfiguration during that window can trigger the loss.

### Recommendation
Do not zero the `Fees` entry until delivery is confirmed. Options:
1. Keep the balance intact until the destination emits a delivery/execution receipt that is proven back to `pallet-relayer` (mirroring the existing `accumulate_fees` state-proof pattern), only then debiting the ledger.
2. Alternatively, set a non-zero `timeout` on the dispatched `DispatchPost` and wire a genuine `on_timeout` handler for `HYPERBRIDGE_MODULE_ID`/`HostManager` withdrawals that re-credits `Fees` on confirmed timeout, matching the pattern already used for regular ISMP-fee refunds in `modules/pallets/ismp/src/dispatcher.rs`.
3. At minimum, add a governance/admin recovery path to re-credit `Fees` for provably undelivered/irrecoverable withdrawal requests.

### Proof of Concept
1. A relayer accrues a balance in `Fees::<T>` via `accumulate_fees` on some `StateMachine` destination.
2. The relayer calls `withdraw_fees` → `Pallet::withdraw`, which dispatches the ISMP POST (`timeout: 0`) and immediately sets `Fees::<T>::insert(dest_chain, address, U256::zero())` (`modules/pallets/relayer/src/withdrawal.rs:161-177`).
3. Destination-side delivery fails permanently — e.g., substrate `HyperbridgeWithdrawalModule::on_accept` rejects because `request.source != Coprocessor::get()` (`modules/pallets/ismp/src/dispatcher.rs:190-195`), or EVM `HostManager.onAccept` reverts because `incoming.relayer != _params.admin` (`evm/src/core/HostManager.sol:134-139`).
4. Because the request timeout is `0`, it can never time out to trigger a refund path.
5. The relayer's `Fees` entry remains `0` forever — the funds are unrecoverable even though the destination never paid them out.

impl<T: Config> IsmpModule for HyperbridgeWithdrawalModule<T> {
	fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
		// Only the configured coprocessor may instruct withdrawals.
		let source = request.source;
		if Some(source) != T::Coprocessor::get() {
			Err(IsmpError::Custom(format!("Invalid request source: {source}")))?
		}

		let message = Message::<T::AccountId, T::Balance>::decode(&mut &request.body[..])
			.map_err(|err| IsmpError::Custom(format!("Failed to decode message: {err:?}")))?;

		match message {
			Message::WithdrawRelayerFees(WithdrawalRequest { account, amount }) => {
				T::Currency::transfer(
					&RELAYER_FEE_ACCOUNT.into_account_truncating(),
					&account,
					amount,
					Preservation::Expendable,
				)
				.map_err(|err| {
					IsmpError::Custom(format!("Error withdrawing protocol fees: {err:?}"))
				})?;

				Pallet::<T>::deposit_event(Event::<T>::RelayerFeeWithdrawn { amount, account });
			},
		}

		Ok(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 0))
	}
