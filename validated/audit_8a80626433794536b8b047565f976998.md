## Analysis

The reported bug class is a **value used for authorization/gating differs from the value used for the actual sensitive action** — the check binds on `amount`, but the credited value is `bias`. Searching this gem's OAuth/auth code for the same pattern (a binding check on one value vs. a different value used to build the destination of a privileged request) surfaces a real gap in `ShopifyAPI::Auth::Oauth`.

### Title
Unsanitized `shop` parameter used to build the OAuth authorize/token-exchange host in `Oauth.begin_auth` / `Oauth.validate_auth_callback` - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Utils::ShopValidator.sanitize!` exists specifically to constrain a caller-supplied `shop` string to a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`) before it is used to construct a request host. [1](#0-0) [2](#0-1) 

Other OAuth-adjacent flows in the gem reference this validator, but `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` do not: they take the `shop` value as-is and use it directly to build the destination host of the OAuth authorize redirect and of the access-token POST request (which carries the app's `client_secret`).

### Finding Description
`begin_auth` builds the redirect URL for the user's browser directly from the caller-supplied `shop` argument via `auth_base_uri(shop)`, with no call to `ShopValidator.sanitize!`: [3](#0-2) [4](#0-3) 

`validate_auth_callback` similarly takes `auth_query.shop` and uses it, unsanitized, to construct the `Auth::Session` whose `shop` attribute determines the host that `Clients::HttpClient` sends the `client_secret`-bearing POST to: [5](#0-4) [6](#0-5) 

The only gate on `auth_query.shop` in `validate_auth_callback` is `Utils::HmacValidator.validate(auth_query)`, and `shop` is one of the fields included in the HMAC-signed string in `AuthQuery#to_signable_string`: [7](#0-6) 

Because that HMAC is only ever produced by Shopify (using `api_secret_key`, which the gem's scope rules exclude an attacker from possessing), an attacker without the secret cannot forge a `validate_auth_callback` request with an arbitrary `shop` that still passes HMAC validation — so the `client_secret`-exfiltration path through `validate_auth_callback` is not reachable by an unprivileged attacker.

`begin_auth`, however, has **no such binding at all**: the `shop` value is whatever the calling application passes in (typically taken straight from an unauthenticated `?shop=` query parameter on the app's own login route, per the documented flow), and the library performs no format/domain validation before using it to build the URL the user's browser is redirected to. An attacker can supply `shop=attacker-controlled-host` and the library will happily construct `https://attacker-controlled-host/admin/oauth/authorize?client_id=...&redirect_uri=...&state=<nonce>&...`, sending the app's `client_id`, `redirect_uri`, requested `scope`, and — critically — the freshly generated CSRF `state` nonce (which the app has already bound to a cookie set on the victim's browser) to a host the attacker controls. [8](#0-7) 

### Impact Explanation
This breaks the binding: **host validated (should be a trusted `*.myshopify.com`/`myshopify.io` domain) ≠ host that actually receives the OAuth `state`/redirect metadata.** An attacker who controls the destination host learns the app's `state` nonce (already tied to the victim's session cookie) and can use it to complete or redirect a fabricated OAuth flow, enabling forced OAuth completion / session fixation against the victim — matching the High-severity category defined in scope.

### Likelihood Explanation
Likelihood depends on the host application passing an unauthenticated, attacker-influenced `shop` value straight into `begin_auth` without its own validation — which is exactly the documented usage pattern shown in `docs/usage/oauth.md` (`shop` comes from the login route). Since the gem itself provides and elsewhere uses `ShopValidator.sanitize!` for this exact purpose (in `token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`), but omits it in `begin_auth`/`validate_auth_callback`, this is an internal inconsistency in the gem's own trust boundary rather than solely reliance on host-app diligence.

### Recommendation
Call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` and use the sanitized value both for `auth_base_uri` and (in `validate_auth_callback`) for constructing the `null_session` used to build the access-token request host, mirroring the pattern already used in `TokenExchange`, `ClientCredentials`, and `RefreshToken`.

### Proof of Concept
1. Attacker sends a victim a link to the app's own login route: `https://victim-app.example.com/login?shop=attacker.example.net`.
2. The app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")` without independently validating `shop`. [3](#0-2) 
3. `auth_base_uri("attacker.example.net")` returns `https://attacker.example.net/admin`, since `.my.shop.dev` suffix check does not match, and no trusted-domain check is applied. [9](#0-8) 
4. The victim's browser is redirected to `https://attacker.example.net/admin/oauth/authorize?client_id=<app_client_id>&redirect_uri=<callback>&state=<nonce>&...`, with the `state` cookie already set on the victim's browser, leaking the CSRF-binding nonce to the attacker's server.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
