### Title
Front-run mint pre-seed on the HyperSwap TOKEN/LT pair still lets an attacker's dust LP capture a bounded but nonzero share of graduation LP via the `_seedDirectMint` subsidy path - ([File: packages/contracts/src/Bonding.sol])

### Summary
The RaspAP finding is a CWE-276/732 class bug: an unprivileged principal (`www-data`) can overwrite a resource (`enablelog.sh`) that a privileged flow (root cron/sudo) later executes with elevated trust, turning a "safe" no-password sudo rule into full root code execution. The alt.fun analog is structural rather than literal file permissions: `Bonding`'s permissionless two-phase graduation writes real curve-raised LT and 250M reserved tokens into a HyperSwap V2 pair that *any unprivileged address can pre-create and pre-seed* between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`). `finalizeGraduation` then executes with elevated trust (moving `Bonding`'s own escrowed funds and calling `LPLock.recordLock`) against that attacker-influenceable resource. The protocol has built an elaborate three-regime defense for this, but its own documentation and tests admit the defense has a residual, quantified subsidy window (`DIRECT_MINT_PRESEED_BPS`) where the attacker-controlled pre-seed still receives value from the protocol's deposit — the equivalent of "root will still execute some of the attacker's payload," just capped instead of unbounded.

### Finding Description
`Factory.createPair`/`v2Factory.createPair` for the HyperSwap TOKEN/LT pair is permissionless once a token is created, and pair.mint()/transfer() calls on that pair are also permissionless. This is explicitly acknowledged as "the exploit" in the codebase's own `AGENTS.md`: [1](#0-0) 

`finalizeGraduation` (permissionless, callable by anyone) is the "root-equivalent" trusted executor: it deposits `Bonding`'s escrowed `tokensForLP`/`ltFromPair` into whatever pair state exists at call time and locks the resulting LP via `LPLock.recordLock`: [2](#0-1) 

The seeding logic (`_seedUniswapV2Direct` → `_seedRebalancing` → `_seedDirectMint`/`_pairRebalance`/`_routerDepositAndDispose`) branches on the pre-seed shape an attacker chose: [3](#0-2) [4](#0-3) 

`_seedDirectMint` transfers the full `(tokensForLP, ltFromPair)` and calls `pair.mint(lpLock)`. When called against a pool that already has `totalSupply() > 0` (an attacker's own prior `pair.mint(attacker)` pre-seed sitting within the `DIRECT_MINT_PRESEED_BPS` band), the V2 `mint` formula computes LP proportionally to *existing* reserves — not "sole price input" as it is for a pristine pool — so the attacker's pre-existing LP receives a pro-rata donation of the over-funded side of the deposit: [5](#0-4) 

The protocol's own test suite (`test_hostilePreSeed_atBand_subsidyBoundedByBand`) explicitly demonstrates and *accepts* a nonzero subsidy at the band boundary, and the natspec on `_seedRebalancing` documents the tradeoff by design ("the pre-existing LP's claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`"): [6](#0-5) [7](#0-6) 

Additionally, the codebase itself flags that the dedicated end-to-end regression suite for this attack class (`HostilePreSeed.t.sol`) was removed post-deployment, and the wrong-opening-price / LP-capture / attacker-no-profit / leftover-recovery / concurrent-graduation-isolation properties are **no longer enforced by automated tests**: [8](#0-7) 

This mirrors the RaspAP bug class precisely: a low-privilege actor writes to a resource (`enablelog.sh` / the HyperSwap pair) ahead of time; a higher-trust process (`root` sudoer / `finalizeGraduation`) later executes against that attacker-controlled state, and the "fix" that was shipped (permission restriction / `DIRECT_MINT_PRESEED_BPS` band + rebalance swap) still leaves a bounded, provable value leak to the unprivileged writer, and the regression coverage proving the bound holds has since been removed.

### Impact Explanation
Any address (no roles, no allowlist — `factory.createPair`/`pair.mint` are permissionless) can front-run a token's graduation by pre-creating the HyperSwap pair and seeding a dust ratio inside the `DIRECT_MINT_PRESEED_BPS` band. When `finalizeGraduation` runs, `_seedRebalancing` routes to `_seedDirectMint`, and the attacker's pre-existing LP receives a subsidy bounded by `band/10_000 × ltFromPair` (or the equivalent on the token side) at zero cost beyond the dust deposit and gas — this is a direct, deterministic transfer of value out of the protocol's locked LP to an unprivileged, uncooperative party, i.e. partial theft/dilution of graduation LP that would otherwise go entirely to `LPLock`. Because the removed `HostilePreSeed.t.sol` suite was the only automated proof that "attacker P&L ≤ 0" and "LP capture negligible" hold across the full pre-seed shape space, any future edit to `_seedRebalancing`/`_seedDirectMint`/`DIRECT_MINT_PRESEED_BPS` (or a miscalibration of the current constant) can silently widen this subsidy without any test catching it, escalating a bounded/accepted leak into an unbounded one — analogous to how RaspAP's sudoers misconfiguration escalated a "harmless" no-password sudo rule into full root RCE once the underlying assumption (script not writable) was violated.

### Likelihood Explanation
High reachability: `factory.createPair` and `pair.mint`/`transfer` on HyperSwap are permissionless and require no allowlisting; any wallet holding a trivial amount of the newly-launched token and LT can front-run the phase-1→phase-2 window (the keeper drives `finalizeGraduation` within ~60s, giving a real MEV window). The attack requires no special privileges, no upgrade, and no off-chain compromise — only ordinary transactions from an unprivileged EOA, exactly matching the "www-data-level" actor in the analog report.

### Recommendation
- Re-derive and re-instate automated coverage equivalent to the removed `HostilePreSeed.t.sol` (wrong-opening-price, LP-capture bound, attacker-no-profit, leftover recovery, concurrent-graduation isolation) so any future change to `_seedRebalancing`/`_seedDirectMint`/`DIRECT_MINT_PRESEED_BPS` is guarded by regression tests, not just narrative comments.
- Reconsider whether `DIRECT_MINT_PRESEED_BPS` should gate the direct-mint fallback at all versus routing every nonzero pre-existing-reserve case through `_pairRebalance` + `_routerDepositAndDispose` (which the code shows is P&L-negative for the attacker), accepting the small extra swap/gas cost in the "coarse swap on dust" case instead of a guaranteed proportional subsidy.
- Emit and monitor an event whenever `_seedDirectMint` is invoked against a non-zero-`totalSupply()` pair (i.e., the subsidized path, not the pristine empty-pair path), so operators can track realized value leakage per graduation and re-tune the band if front-running becomes economically attractive at scale.

### Proof of Concept
1. Attacker watches for a token approaching its graduation threshold (public `canGraduate`/`TokenGraduating` event).
2. Attacker calls the HyperSwap V2 factory's `createPair(token, lt)` for the TOKEN/LT pair before `finalizeGraduation` runs (or even before phase 1 fires — the pair address is deterministic and creation is permissionless), matching the front-run described in `AGENTS.md`'s "The exploit" section: [9](#0-8) 
3. Attacker transfers a small amount of TOKEN and LT to the pair sized so that both `reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS` and `reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS` hold (i.e., sits within the direct-mint band), then calls `pair.mint(attacker)` to receive dust LP — reproducing the exact setup in `test_hostilePreSeed_atBand_subsidyBoundedByBand`: [10](#0-9) 
4. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. Because `pair.totalSupply() > 0`, `_seedUniswapV2Direct` routes to `_seedRebalancing`, which — because the pre-seed sits inside `DIRECT_MINT_PRESEED_BPS` — calls `_seedDirectMint` against the non-empty pool: [7](#0-6) 
5. `pair.mint(lpLock)`'s standard V2 formula donates the over-funded side of the protocol's deposit pro-rata to the attacker's pre-existing LP, exactly as demonstrated by the test's own assertion `claimValueLt <= depositValueLt + maxSubsidy` where `maxSubsidy = band/10_000 × ltFromPair` — i.e., the test itself proves a nonzero, protocol-funded subsidy is paid to the unprivileged pre-seeder.

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

This is the same exploit class as the four.meme Feb 2025 incident (~$183K loss).

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _seedUniswapV2Direct(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }

    /// @dev Transfer the full `(tokensForLP, ltFromPair)` to the pair and
    ///      `mint` the LP to `LPLock`, opening at the exact cached
    ///      curve-close ratio. Used by the empty-pair regime and as the
    ///      dust-pre-seed fallback in `_seedRebalancing` — against dust
    ///      reserves the V2 `min()` formula's donation to any pre-existing
    ///      LP is negligible (see `_seedUniswapV2Direct` natspec). Any TOKEN
    ///      remainder (a skimmed pure-donation pre-seed) is burned; the LT
    ///      remainder is left for `finalizeGraduation`'s `_sweepLTToOwner`
    ///      post-bookend.
    function _seedDirectMint(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);
        liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
    }

    function _seedRebalancing(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        (uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();
        bool tokenIs0 = IUniswapV2Pair(pair).token0() == tokenAddress;
        (uint256 reserveToken, uint256 reserveLT) = tokenIs0 ? (uint256(r0), uint256(r1)) : (uint256(r1), uint256(r0));

        // Below the band on BOTH sides, overpower the pre-seed with a direct
        // mint at the cached ratio: the rebalance swap is too coarse to reach
        // the ratio against such small reserves, and the pre-existing LP's
        // claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`. A
        // side that is large relative to its LP target still takes the
        // rebalance path so it isn't donated under the empty-mint `min()`.
        if (
            reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS
                && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS
        ) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Budget reads `balanceOf(this)` rather than `tokensForLP` /
        // `ltFromPair` so any skim donation contributes to the rebalance
        // and not only to `_routerDepositAndDispose`'s deposit.
        // Direction: pool TOKEN-rich vs target ⇒ swap LT in (TOKEN out).
        // Pool LT-rich ⇒ swap TOKEN in (LT out). Bounded by uint112 reserves
        // and curve-close-shape targets, both products fit in uint256.
        // When `_pairRebalance` returns false the seed is too small for any
        // swap to move the ratio (its fee-charging quote rounds to zero), so
        // the reserves are negligible against this graduation's inventory:
        // overpower them with a direct mint at the cached ratio rather than
        // letting the router deposit at the attacker's ratio. A swap that
        // does fire leaves the pool ≈ at target for the router deposit.
        if (reserveToken * ltFromPair > reserveLT * tokensForLP) {
            // Pool TOKEN-rich. tokenIn = lt, tokenOut = tokenAddress.
            // tokenInIs0 = (lt is token0) = !tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: lt,
                        tokenInIs0: !tokenIs0,
                        reserveIn: reserveLT,
                        reserveOut: reserveToken,
                        targetN: ltFromPair,
                        targetD: tokensForLP,
                        maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        } else if (reserveToken * ltFromPair < reserveLT * tokensForLP) {
            // Pool LT-rich. tokenIn = tokenAddress, tokenInIs0 = tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: tokenAddress,
                        tokenInIs0: tokenIs0,
                        reserveIn: reserveToken,
                        reserveOut: reserveLT,
                        targetN: tokensForLP,
                        targetD: ltFromPair,
                        maxSwap: _swapBudget(IERC20(tokenAddress).balanceOf(address(this)))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        }

    /// @notice The residual case: a one-sided pre-seed sitting on the tightened
    ///         band still reaches the direct mint, and the empty-mint `min()`
    ///         still donates the over-funded side to the pre-seeder. This is
    ///         the worst case for the retained direct-mint path (token on the
    ///         band, LT at 1 wei, so the whole LT side is donated). The net
    ///         subsidy must stay bounded by the band fraction of `ltFromPair`,
    ///         which at 1 bp is economically negligible — this pins both the
    ///         bound the M-01 fix relies on and the constant against drifting
    ///         back up.
    function test_hostilePreSeed_atBand_subsidyBoundedByBand() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        uint256 band = bonding.DIRECT_MINT_PRESEED_BPS();
        uint256 reserveToken = (tokensForLP * band) / 10_000;
        uint256 reserveLt = 1;
        // Both sides sit within the band, so the gate routes this to the
        // direct mint rather than the rebalance swap.
        assertLe(reserveToken * 10_000, tokensForLP * band, "token side must sit within the band");
        assertLe(reserveLt * 10_000, ltFromPair * band, "LT side must sit within the band");

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr));

        uint256 claimValueLt = _lpValueInLt(hyperPair, tokenAddr, grieferLp);
        uint256 depositValueLt = (reserveToken * ltFromPair) / tokensForLP + reserveLt;
        uint256 maxSubsidy = (ltFromPair * band) / 10_000;
        assertLe(claimValueLt, depositValueLt + maxSubsidy, "direct-mint subsidy must stay within the band");
    }
