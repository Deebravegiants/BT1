### Title
Token Exchange sends `client_secret` to an unsanitized shop host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound `/admin/oauth/access_token` request (which carries the app's `client_id`/`client_secret` in the body) using a shop host taken directly from the JWT payload's `dest` claim, without ever passing it through `Utils::ShopValidator.sanitize!`. Every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the value as the request host. `exchange_token` is the one path that skips this validation step, breaking the intended invariant that "the host that receives the `client_secret` == a shop value validated against `TRUSTED_SHOPIFY_DOMAINS`".

### Finding Description
`JwtPayload#shop` simply does `@dest.gsub("https://", "")` on the token's `dest` claim with no domain allow-listing: [1](#0-0) . `TokenExchange.exchange_token` takes this raw value as `dest_shop` and uses it, unsanitized, to build the `Session` that determines the HTTP client's target host, then POSTs `client_id`/`client_secret` to it: [2](#0-1) .

Contrast this with the sibling method in the same file, `migrate_to_expiring_token`, which validates the shop before doing the exact same kind of credential-bearing request: [3](#0-2) . The same pattern (`Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the client_secret-bearing request) is also present in `ClientCredentials.client_credentials` [4](#0-3)  and `RefreshToken.refresh_access_token` [5](#0-4) .

`ShopValidator.sanitize!` exists specifically to guarantee the shop string used as a request host is one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an explicitly configured custom domain: [6](#0-5) . `exchange_token` bypasses this guard entirely, so the equality the codebase's own design elsewhere enforces — "host that receives `client_secret` == ShopValidator-sanitized trusted domain" — does not hold for this call path. This mirrors the analog bug-class described in the prompt: a value that is superficially "validated" (the JWT signature check) is used for a purpose (selecting the destination host for a credential-bearing HTTP request) that requires an additional, distinct binding (domain allow-listing) which is missing here specifically, while present in every structurally identical sibling function.

### Impact Explanation
If the `dest` claim can ever contain a value that is not a bare `shop.myshopify.com`-style host (e.g., due to future changes in how session tokens are issued, non-Admin session tokens such as the checkout UI extension tokens shown in the test suite which have differently shaped `iss`/`dest` values, or any host-application misuse where a non-Shopify-issued but otherwise well-formed JWT is fed into `exchange_token`), the gem will construct an outbound HTTPS request to that unsanitized host and place the app's `client_id` and `client_secret` directly in the POST body. That is exactly the "credential leakage / SSRF with the app's credentials" impact category — the app's `client_secret` could be sent to an origin outside the sanctioned Shopify domain list.

### Likelihood Explanation
Exploitation likelihood in the strict "unprivileged internet user" sense is constrained: under intended usage, `dest` is set by Shopify inside a token signed with the app's own `api_secret_key`/`old_api_secret_key`, so an external attacker without that secret cannot forge an arbitrary `dest` value to redirect the secret elsewhere via `JwtPayload`'s own signature check. However, the missing `ShopValidator.sanitize!` call is a clear, provable divergence from this gem's own established pattern for every other client_secret-bearing call, and it removes a defense-in-depth layer that the codebase itself considers necessary (as evidenced by its use in the three sibling functions). Given the difficulty of proving forgeability of `dest` purely through code inspection here (no access to Shopify's token-issuance internals), I can confirm the missing validation as a root-cause code defect with high confidence, but cannot fully confirm a concrete unauthenticated forgery path to weaponize it without further live testing against Shopify's token issuance service.

### Recommendation
Add `validated_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)` in `exchange_token` and use `validated_shop` (not the raw `dest_shop`) both for `shop_session` and for the final `Session.from(shop: ...)` call, mirroring `migrate_to_expiring_token`, `refresh_access_token`, and `client_credentials`.

### Proof of Concept
Not independently reproducible from static analysis alone: a live PoC would require producing (or otherwise obtaining) a session token whose `dest` claim resolves to a non-Shopify host while still passing the HMAC/signature check in `JwtPayload#decode_token`, which requires knowledge of the app's `api_secret_key`. Under the gem's threat model this key is not attacker-controlled, so this finding is reported as a code-level integrity gap (missing `ShopValidator.sanitize!` call that exists in all sibling functions) rather than a demonstrated end-to-end exploit.
