## Title
Webhook `shop-domain` header is trusted as the tenant identifier without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw HTTP body only, while the `shop` value handed to the registered webhook handler is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed data. This breaks the intended binding `shop_used_by_handler == shop_authenticated_by_hmac`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC using only that signable string, and then forwards `request.shop` — parsed straight from an HTTP header — to the handler as the trusted tenant identity for the event: [2](#0-1) 

`request.shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic linkage to the HMAC: [3](#0-2) 

Compare this to `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` is explicitly included in the HMAC-signed payload, correctly binding the shop identity to the signature: [4](#0-3) 

No analogous binding exists for webhook requests. Since the HMAC only proves that a given `raw_body` bytes were signed by the app's `client_secret`, but does not prove which shop that body was signed for, an attacker who is able to obtain any single valid `(raw_body, hmac)` pair for their own tenant (e.g., because they run a legitimate shop with the app installed and can capture the genuine webhook Shopify sends them) can replay that exact body+HMAC while substituting the `shopify-shop-domain` header value with an arbitrary or victim shop domain. `HmacValidator.validate` will still pass because it only recomputes the signature over `raw_body`, and `Registry.process` will dispatch the (attacker-controlled) event to the handler tagged with the forged `shop`.

### Impact Explanation
This is a cross-tenant identity confusion at the library level: the gem itself asserts (via `WebhookMetadata#shop`) a "verified" shop-scoped event, but the shop component of that assertion carries no authentication. Any host application that uses `request.shop`/`data.shop` from `ShopifyAPI::Webhooks::Registry.process` as the tenant key (e.g., to look up which merchant a webhook event belongs to, following the flow endorsed by this gem's own docs) will act on attacker-influenced tenant identity while believing the whole `Request` object was HMAC-verified. This enables cross-tenant event injection/spoofing.

### Likelihood Explanation
Moderate-to-low: it requires the attacker to control at least one legitimate shop with the app installed (to obtain one valid `(body, hmac)` pair for themselves), which is realistic for any public embedded app, since install is open to any merchant. No secret leakage, TLS interception, or privileged account is required — only the ability to receive and replay one's own legitimately signed webhook while forging the `shop-domain` header on the replayed request.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) inside the HMAC-covered signable content for webhooks, or otherwise cryptographically bind the shop identity to the signature (e.g., validate that the `shop` header matches a shop value embedded in and covered by the signed payload). At minimum, `Registry.process` should not present `request.shop` as verified data once `Utils::HmacValidator.validate` has only authenticated the body bytes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook (e.g., `orders/create`) with a valid `x-shopify-hmac-sha256` for `raw_body = B`.
2. Attacker resends the exact same `raw_body = B` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B)`, shown in: [5](#0-4) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim-shop.myshopify.com"` even though it was never signed, shown in: [6](#0-5) 
5. Any host-app logic keyed on `data.shop` now processes attacker-controlled webhook data under the victim shop's identity.
