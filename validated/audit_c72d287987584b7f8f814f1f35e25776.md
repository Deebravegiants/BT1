## Title
Missing `return` After Error in OIDC Token Exchange Grants Authenticated Session Despite Failed Claim Validation - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange` at `core/sessions/oidcauth/oidc.go:226-230`, when the `email` claim type assertion fails, the code writes an HTTP 500 response via `c.String` but does not `return`, letting execution continue to role mapping, `oidc_sessions` row insertion, audit logging, and session-cookie issuance via `ginSession.Save()`. A second missing `return` after the DB insert failure at `core/sessions/oidcauth/oidc.go:257-260` has the same effect. Because `AuthorizedUserWithSession` (`core/sessions/oidcauth/oidc.go:349-391`) validates sessions purely by `sessionID` lookup in `oidc_sessions` and does not re-check that `user_email` is non-empty, a session created this way is fully functional for subsequent requests.

The role assigned to the session is computed from `idClaims` via `IDClaimsToUserRole`, which is a separate, already-validated set of claims (`ExtractIDClaimValues` succeeded at line 220-225) independent of the `email` field. The same broken pattern repeats for the DB-insert-failure branch (lines 257-260): the audit log entry claiming success and the cookie-setting logic still execute even if session persistence failed.

## Impact Explanation
This is a genuine node API authentication/session-integrity defect: `handleTokenExchange` can issue a valid, cookie-backed authenticated session (with a real RBAC role derived from group claims) that is not properly tied to a validated identity (`email` is empty), and falsely records an `AuthLoginSuccessNo2FA` audit entry. This maps to the in-scope "node API authentication or role bypass" impact category since the session cookie is functional against `AuthorizedUserWithSession` and grants access according to the mapped role.

## Likelihood Explanation
Triggering requires the OIDC identity provider's ID token to pass signature verification (`oi.provider.Verifier(...).Verify`) and to contain the configured group/role claim(s) used by `IDClaimsToUserRole`, but omit or non-string-type the standard `email` claim. This is realistic in non-standard OIDC deployments, misconfigured scope requests (e.g., missing `email` scope), or a malicious/compromised IdP endpoint the node is configured to trust — the same threat model cited in the referenced CVE analogy. No special privilege beyond completing the normal `/oidc/callback`-style redirect flow is required from the client side; the bug is unconditional code, not a rare race, so it is reliably reachable whenever this claim-shape condition occurs.

## Recommendation
Add `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call (line 229) and after `c.String(http.StatusInternalServerError, "Error creating session")` (line 259). Additionally, explicitly reject the login when `email == ""` before performing role mapping, DB insertion, audit logging, or cookie issuance, and audit the file for other "log + write response + fall through" patterns.
