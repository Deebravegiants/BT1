### Title
Emporium EIP-712 signature does not bind `CircomData.stealthAddressStructure`/`relay`/`erc20TokenAddresses`, allowing anyone in possession of a signed `EmporiumStack` to redirect the wallet owner's swept funds and fees - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`verifyWallet` only binds `circomData.emporiumMessage`, the hash of `stack.ops`, `stack.maxFee`, and `stack.deadline` into the EIP-712 digest signed by the wallet owner. It does not bind `circomData.stealthAddressStructure` (who ends up owning the shielded UTXO created from swept funds), `circomData.relay`, `circomData.erc20TokenAddresses`, or `circomData.feeStructure.feeToken/variableRate`. Any unprivileged party who obtains a validly signed `EmporiumStack` (e.g. intended for a relay, observed in a relay queue/mempool) can submit it with a `CircomData` of their own construction, causing the wallet owner's swept proceeds to be reshielded to an address the owner never authorized, and/or extracting relay fees they never agreed to (beyond the flat-fee cap).

### Finding Description
The broken equality is: `(assets leaving the wallet, their destination) == (ops, maxFee) the owner signed`.

`verifyWallet` computes the signed digest as: [1](#0-0) 

This only commits to `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, and `stack.deadline`. The struct type itself confirms these are the only signed fields: [2](#0-1) 

After signature verification, `runAction` executes `stack.ops` (which move the wallet owner's funds into the Emporium contract's balance), then sweeps the resulting balance delta out via `handleOut`, minting a new shielded UTXO using `circomData.stealthAddressStructure` and `circomData.erc20TokenAddresses` — both fully attacker-controlled and unrelated to what the owner signed: [3](#0-2) 

Fee payment is similarly governed by attacker-controlled `circomData.feeStructure` and `circomData.relay`, with only `feeStructure.flatFee` checked against `stack.maxFee`: [4](#0-3) [5](#0-4) 

`variableRate` and `feeToken` selection are entirely unconstrained by the signature; only `flatFee` is bounded.

Exploit flow:
1. Wallet owner signs an `EmporiumStack` (ops, maxFee, deadline) for a specific `emporiumMessage`, intending to route the resulting swept funds back to their own shielded balance via a trusted relay.
2. Before the intended relay/self-submission lands on-chain, an unprivileged attacker who has observed this signed stack (e.g., via a public/semi-trusted relay network, or because the owner broadcasts it for gas-sponsored submission) submits it themselves through `Hinkal.transact`, supplying their own `CircomData` with `emporiumMessage` unchanged (required to pass signature verification) but with `stealthAddressStructure` pointing to an address/key the attacker controls, `relay` set to themselves, and `erc20TokenAddresses`/`feeStructure` chosen to their advantage (bounded only by `flatFee <= stack.maxFee`).
3. `verifyWallet` passes (message not yet used, signature matches ops/maxFee/deadline), `usedMessages[emporiumMessage]` is marked, `stack.ops` execute exactly as the owner authorized, and the wallet's proceeds land in the Emporium contract's balance.
4. `handleOut` shields that balance into a new UTXO owned by the attacker's `stealthAddressStructure`, and `payRelayFees` pays the attacker's chosen `relay` address.

Existing guards do not prevent this: `usedMessages` only stops the exact same `(stack, emporiumMessage)` from being replayed twice, it does not bind the destination of the proceeds to the signer's intent; `verifyWallet`'s `flatFee > stack.maxFee` check only bounds one fee field, not `variableRate`, `feeToken`, `relay`, or the output destination.

### Impact Explanation
The wallet owner's real, authorized on-chain fund movement (via `stack.ops`) is hijacked at the point where proceeds are reshielded: the resulting shielded UTXO is created under a spending key the owner never approved, meaning the attacker — not the owner — ends up controlling the swept funds. This is "executing calls or moving assets a wallet owner ... never authorised," matching the **High** severity category (theft of funds/fees a wallet owner never authorized). It is repeatable for every signed `EmporiumStack` the attacker can intercept before its intended submission, and the amount at risk equals the full value moved by `stack.ops` for that message.

### Likelihood Explanation
Preconditions: the attacker needs to obtain a validly signed but not-yet-submitted `EmporiumStack` together with its bound `emporiumMessage` (e.g., via observing a relay's pending queue, an off-chain gas-sponsorship channel, or any other place where a signed-but-unsubmitted stack is transiently visible before being wrapped into a transaction). Given `Hinkal.transact` is meant to be called through relays for gas abstraction, such stacks are plausibly exposed in transit. No privileged role is required — only the ability to front-run the intended submission with attacker-chosen `CircomData` and a self-generated proof over that `CircomData`. This is a straightforward on-chain front-run once the signed payload is known.

### Recommendation
Include all fields whose values determine where funds/fees end up in the EIP-712 typed hash that the wallet owner signs: `circomData.stealthAddressStructure`, `circomData.relay`, `circomData.erc20TokenAddresses`, and the full `feeStructure` (`feeToken`, `flatFee`, `variableRate`), not just `flatFee`. Alternatively, require that `msg.sender`/relay address and destination stealth address be explicitly part of the owner's signed intent (e.g., `EmporiumSignature(message, ops, maxFee, deadline, relay, destinationStealthAddress, feeToken, variableRate)`), so that any deviation invalidates `verifyWallet`'s signature check.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `IHinkalWallet` as `stack.signerAddress`, and register the Emporium contract as an allowed recipient of a mock `Hinkal`.
2. Have the "victim" wallet owner sign an `EmporiumStack` (ops that pull ERC20 tokens from the wallet into the Emporium contract, `maxFee`, far-future `deadline`) over a chosen `emporiumMessage`, intending `circomData.stealthAddressStructure = victimStealthAddr`.
3. As the "attacker", call `Hinkal.transact` → `EmporiumUpgradeable.runAction` with the same `stack`/`emporiumMessage` but `circomData.stealthAddressStructure = attackerStealthAddr` and `circomData.relay = attacker`.
4. Assert: `verifyWallet` does not revert (signature still validates because `stealthAddressStructure`/`relay` are not part of the signed hash); assert the resulting UTXO/emitted output event is keyed to `attackerStealthAddr`, not `victimStealthAddr` — i.e., assert `(destination signed by owner) != (destination actually used)`, demonstrating the broken equality.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }
