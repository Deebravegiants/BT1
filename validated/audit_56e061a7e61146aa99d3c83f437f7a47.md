Audit Report

## Title
Missing role check on `GET /v2/external_initiators` exposes `OutgoingToken` credentials to any authenticated (non-admin/edit) user - (File: core/web/router.go)

## Summary
The `authv2` route group registers `GET /v2/external_initiators` with only `paginatedRequest(eia.Index)`, while `POST` and `DELETE` for the same resource are wrapped with `auth.RequiresEditRole`. Since the `Index` handler serializes each record through `presenters.ExternalInitiatorResource`, which embeds the secret `OutgoingToken`, any authenticated user of any role (including the minimal `view` role) can retrieve outgoing webhook credentials belonging to all registered external initiators.

## Finding Description
`v2Routes` in `core/web/router.go` wires external initiator endpoints as: [1](#0-0) 

The outer `authv2` group only requires successful `AuthenticateByToken` or `AuthenticateBySession` to set a `SessionUserKey` in context — it does not itself gate by role: [2](#0-1) 

`eia.Index` (`ExternalInitiatorsController.Index`) fetches every `ExternalInitiator` and maps it through `presenters.NewExternalInitiatorResource`, which includes the plaintext `OutgoingToken` field: [3](#0-2) [4](#0-3) 

Compare this to `RequiresEditRole`, which explicitly rejects `UserRoleView` and `UserRoleRun`, confirming the intended trust boundary for this resource is "edit or higher": [5](#0-4) 

Because `Index` has none of this gating, a session/token belonging to a `view`-role user — which by design should not be able to create or destroy external initiators — can nonetheless read the `OutgoingToken` secret of every external initiator on the node. This is a genuine inconsistency in role enforcement within the same route block and a concrete confidentiality break: the write-path privilege boundary (`RequiresEditRole`) is not mirrored on the read path that discloses the same secret.

One caveat found during verification: the claim's alternate attack vector via `AuthenticateExternalInitiator` (an EI-derived `run`-role identity) does **not** apply to this route, because `authv2` is only wired with `AuthenticateByToken` and `AuthenticateBySession`, not `AuthenticateExternalInitiator` — that method is used in a different, unauthenticated-webhook code path found elsewhere in the codebase, not as an alternate authenticator for `/v2/*`. However, this does not invalidate the core finding: a legitimately provisioned `view`-role dashboard user (a real, low-privilege, unprivileged-relative-to-edit/admin actor) can still authenticate via normal session/API-token login and call this endpoint to read `OutgoingToken`.

## Impact Explanation
Disclosure of `OutgoingToken`/`OutgoingSecret` lets a low-privileged authenticated user impersonate the node's outgoing calls to any external initiator webhook that trusts those credentials, i.e., secret/credential exfiltration for a resource whose write operations are explicitly gated to `edit`-role and above. This falls into the in-scope "key/secret exfiltration" and "node API authentication/role bypass" impact classes, since the missing role check on `Index` bypasses the role model consistently applied elsewhere in the same handler group (`Create`/`Destroy` require `RequiresEditRole`).

## Likelihood Explanation
The precondition is minimal: the node must have External Initiators enabled and at least one registered, and the attacker needs only a valid `view`-role (or any role) session or API token — not edit/admin privileges. Since `view` is the lowest privilege tier explicitly supported by the system's session/user model and is meant to be read-only for non-secret resources, an operator granting a `view`-role account (e.g., for dashboards/monitoring) would unintentionally give that account access to `OutgoingToken` secrets. This is realistic and repeatable via a single unauthenticated-to-role-check HTTP GET once any valid credential is obtained.

## Recommendation
Wrap `authv2.GET("/external_initiators", ...)` with `auth.RequiresEditRole` (matching `Create`/`Destroy`), or strip `OutgoingToken`/`OutgoingSecret` from the resource returned by `Index`/list operations so that `view`-role sessions cannot read outgoing webhook credentials for initiators they didn't create.

## Proof of Concept
1. Enable External Initiators (`JobPipeline.ExternalInitiatorsEnabled = true`).
2. As an admin/edit user, `POST /v2/external_initiators` to create one; the server persists `OutgoingToken`/`OutgoingSecret` on the record via `bridges.NewExternalInitiator` [6](#0-5) .
3. Create or use a `view`-role user session/API token (e.g., via `POST /v2/users` as admin with role `view`, then log in as that user).
4. As the `view`-role user, call `GET /v2/external_initiators`. The request succeeds (no `RequiresEditRole`/`RequiresAdminRole` check exists on this route) and the JSON response includes `outgoingToken` for every registered initiator, per `presenters.ExternalInitiatorResource`.
5. Confirm that the same `view`-role user receives `401 Unauthorized` on `POST /v2/external_initiators` and `DELETE /v2/external_initiators/:Name`, demonstrating the inconsistent enforcement between read (`Index`, unguarded) and write (`Create`/`Destroy`, `RequiresEditRole`-guarded) operations on the same resource.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func NewExternalInitiator(
	eia *auth.Token,
	eir *ExternalInitiatorRequest,
) (*ExternalInitiator, error) {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(eia, salt)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "error hashing secret for external initiator")
	}

	return &ExternalInitiator{
		Name:           strings.ToLower(eir.Name),
		URL:            eir.URL,
		AccessKey:      eia.AccessKey,
		HashedSecret:   hashedSecret,
		Salt:           salt,
		OutgoingToken:  utils.NewSecret(utils.DefaultSecretSize),
		OutgoingSecret: utils.NewSecret(utils.DefaultSecretSize),
	}, nil
}
