### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) header is trusted for tenant identification but is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant/tenant identity (`shop`) and other routing data (`topic`, `webhook-id`, `api-version`) directly from unauthenticated HTTP headers, while the HMAC signature that `Registry.process` verifies only covers the raw request body. This breaks the intended binding `hmac == HMAC(secret, shop || body)`; in this gem it only enforces `hmac == HMAC(secret, body)`, leaving `shop` completely unauthenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` only validates the HMAC of the body via `Utils::HmacValidator.validate`, then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate`/`validate_signature` compute the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and compare it to the received HMAC — the `shop` header never enters this computation: [4](#0-3) 

This is the exact analog of the external report's class of bug: a field that is *acted upon* (here, the tenant-identifying `shop` used to route/attribute webhook data to a merchant) is not covered by the integrity check (the HMAC), so the check passes while the acted-upon value can diverge from what was actually authenticated.

**Equality that should hold, but doesn't:**
`shop_header == shop_bound_by_hmac`

Before request: HMAC covers `body` only; `shop` header is independent.
After request: `HmacValidator.validate` returns `true` as long as `body` matches the legitimate HMAC — regardless of what `shop` header value accompanies it.

### Impact Explanation
Any user of the app (a legitimate, even low-privilege merchant who has installed the app on their own store) can trigger the app to generate a real webhook with a valid HMAC over an attacker-chosen body (e.g., by editing a customer/order/product field on their own shop). They can then capture that `body`/`hmac` pair and replay it directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different, victim shop that also uses the app. `Registry.process` will accept it as valid (HMAC checks out) and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any host application that uses `data.shop` to look up/update per-tenant state (session/store lookup, webhook deduplication, GDPR data requests, inventory/order sync, etc.) will process attacker-controlled data under the wrong tenant's identity — a cross-tenant data-integrity breach reachable by an unprivileged internet user with no access token, secret, or privileged account required.

### Likelihood Explanation
Likely reachable: the attacker only needs (a) any legitimate install of the app on a shop they control (an ordinary use case, not a privileged internal capability) to legitimately mint a valid `(body, hmac)` pair, and (b) the ability to POST directly to the app's public webhook endpoint with custom headers — something any internet client can do since Shopify's webhook delivery is just an HTTP POST to a public URL. No TLS interception, leaked secret, or social engineering is required.

### Recommendation
Bind the tenant/topic identity into the value that is HMAC-verified, or otherwise cryptographically tie `shop` to the signed body — e.g., include `shop`/`topic`/`webhook_id` in `to_signable_string` (matching Shopify's documented webhook verification, which is body-only by design) is not sufficient by itself; instead the gem should require the caller to supply the shop from a source it trusts independently (e.g. compare the incoming header value against a shop that was registered for that specific webhook subscription/session) rather than trusting the header value outright once the body-only HMAC passes. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a sole tenant key without additional verification (e.g., cross-checking against a known/registered shop list) before use.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on shop "attacker.myshopify.com"
# and causes Shopify to send a real webhook, e.g. by editing a resource,
# producing a genuine (body, hmac) pair signed with the app's api_secret_key.

raw_body = '{"id":1,"note":"forged payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker now POSTs directly to the app's public webhook endpoint,
# replacing the shop-domain header with a victim shop that also has the app installed.
headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (only checks raw_body), and the handler receives
#    WebhookMetadata with shop: "victim-shop.myshopify.com", even though that
#    shop never sent this webhook.
``` [3](#0-2)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
