### Title
Webhook `shop` identity is taken from an unauthenticated header and is never covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by validating the HMAC over the **raw body only**, while the `shop` (and `topic`) values used by the handler are read straight from HTTP headers that are never part of the signed message. Any user who owns a real installation of the app can capture one of their own genuinely-signed webhook payloads and replay it against the same endpoint with a forged `X-Shopify-Shop-Domain` header, causing the app to process the event as if it belonged to a different ("victim") shop while the HMAC check still passes.

### Finding Description
`Utils::HmacValidator.validate` computes and constant-time-compares the HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

But `shop` (and `topic`) are pulled directly out of the HTTP headers, which are attacker-controlled and are *not* included anywhere in the signed bytes: [3](#0-2) 

`Registry.process` only checks the HMAC validity and then hands the unauthenticated `request.shop` value straight to the app's handler as the tenant identity for the event: [4](#0-3) 

This breaks the identity binding the report's bug class describes: the equality that should hold is `shop bound by signature == shop acted upon`, but here `shop acted upon` (`request.shop`, passed into `WebhookMetadata`) is disjoint from what the HMAC actually covers (`@raw_body` only). Because a single app-level `client_secret` (and therefore a single derived HMAC key) is shared across every shop that installs the app, any merchant with a legitimate install can obtain validly-signed `(body, hmac)` pairs from their own shop's real webhook deliveries, then resend that exact body/hmac pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header of any other shop. `HmacValidator.validate` will still succeed because it never looks at those headers, and `Registry.process` will dispatch the event to the handler labeled with the attacker-chosen `shop`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged (but legitimately app-installed) user can cause the library to authenticate and dispatch webhook data under an arbitrary shop domain of their choosing, even though the HMAC only proves the payload originated from *some* real install of the app, not from the claimed shop. Applications that rely on `data.shop` from `WebhookMetadata` (as the library's own docs and generated resources encourage) to select per-tenant state/records will act on the wrong tenant's behalf — e.g., writing attacker-supplied webhook payload data into another merchant's records, or triggering per-shop side effects (uninstall handling, order/customer processing, GDPR handlers, etc.) for a shop the attacker doesn't own. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that has more than one installing shop (the normal case for a public Shopify app): the only prerequisite is that the attacker has their own working installation, which lets them harvest real `(body, hmac)` pairs from their own store's legitimate webhook traffic (e.g. an `orders/create` fire) and replay them with a different `shop` header value. No access to `client_secret`, tokens, or any other shop's credentials is required.

### Recommendation
Bind the shop (and topic) identity into the signed material, or otherwise cryptographically tie the header claims to the authenticated payload before trusting them:
- Include `shop` (and `topic`) in the HMAC-covered signable string for webhook requests, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes all identity fields it later trusts.
- Alternatively/additionally, require callers to supply the expected shop (looked up from their own persisted state) and reject the webhook if it doesn't match `request.shop`, rather than trusting the header value as the source of truth after only a body-only HMAC check.

### Proof of Concept
1. Attacker registers and installs the target app on their own store `attacker.myshopify.com`, obtaining real webhook deliveries signed with the app's shared `client_secret`.
2. Attacker triggers a benign event (e.g., `orders/create`) and captures the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256` header value `H` — both valid because they were generated by Shopify using the real (shared) secret.
3. Attacker sends a new POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid), `X-Shopify-Topic: orders/create`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` succeeds because it only checks `H` against `OpenSSL::HMAC.hexdigest(sha256, secret, B)`, which is unaffected by the spoofed shop header: [5](#0-4) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: attacker-controlled, ...)`, causing the app to process attacker-controlled webhook content under the victim shop's identity.
