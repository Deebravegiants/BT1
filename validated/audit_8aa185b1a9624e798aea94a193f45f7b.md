### Title
Webhook shop-domain (and topic/webhook-id) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` cryptographically authenticates the body bytes but not the `shop-domain`, `topic`, or `webhook-id` headers that `ShopifyAPI::Webhooks::Registry.process` trusts to attribute the payload to a tenant. An attacker who owns any shop that has the app installed can capture one genuine, validly-signed webhook delivery and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the signature check still passes.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature exclusively to `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`Registry.process` validates only the body HMAC, then forwards the unauthenticated `request.shop` value to the app's handler as the tenant identifier: [3](#0-2) 

The equality the code implicitly assumes is:
`shop_that_signed(raw_body) == shop_header_in_request`

but nothing enforces it — the HMAC only proves `raw_body` was produced with the app's `client_secret` at some point, for *some* shop; it says nothing about which shop that was. Because the HMAC secret is the app's single `client_secret` shared across all installing shops, any shop that has the app installed can obtain a validly-signed `(raw_body, hmac)` pair from its own genuine webhook deliveries, then resend that exact pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's identifier. `HmacValidator.validate` recomputes the HMAC over `raw_body` only, finds it matches, and `Registry.process` dispatches the (attacker-chosen) body to the handler labelled as coming from the victim shop.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to route webhook data to the correct tenant record (the documented handler contract explicitly hands `data.shop` to the app as the authoritative tenant identifier). An attacker who is a legitimate merchant on their own shop (unprivileged relative to other tenants, no access token or client_secret needed) can inject attacker-controlled webhook payloads that the app processes as belonging to a different, victim shop — a cross-tenant data-integrity/access issue, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop (normal, unprivileged action available to any merchant), (2) capturing one genuine outgoing webhook and its HMAC header, and (3) resending it with a modified `shop-domain` header to the publicly reachable webhook callback URL. No secrets, tokens, or privileged access are required, making this readily reachable by any external actor who can install the app.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or otherwise verify that the shop asserted in the header actually corresponds to a shop for which the app has an active, matching session/installation and reject mismatches; at minimum, `to_signable_string` should not be the sole means of authorizing which shop a payload is attributed to — cross-check `request.shop` against known, session-bound tenants before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers a webhook topic (e.g. `orders/create`).
2. Attacker triggers a genuine event, capturing the resulting POST: raw body `B`, plus header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical body `B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on attacker-controlled data under the victim shop's identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
