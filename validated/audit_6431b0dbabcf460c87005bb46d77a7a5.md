### Title
Webhook `shop` (and other headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` (and `topic`/`api_version`/`webhook_id`) values taken from unauthenticated HTTP headers when building the `WebhookMetadata` handed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers and are never part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then, without any additional check that the `shop` header actually corresponds to the signed body, forwards `request.shop` straight to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the HMAC using `verifiable_query.to_signable_string` (the raw body only) and the app's single `Context.api_secret_key`, which is identical for every shop that has installed the app: [4](#0-3) 

The identity binding that should hold is: `shop` delivered to the handler == `shop` whose data the HMAC-authenticated body actually belongs to. Because the signature only covers the body and the secret is shared across all shops of the app, this equality is not enforced. Any merchant with a legitimate install of the vulnerable app can capture one of their own valid `(raw_body, hmac)` pairs (e.g. from `orders/create`) and replay it to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a victim shop. `HmacValidator.validate` will still return `true` (the body/HMAC pair is genuinely valid for the shared secret), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, while `body` is attacker-controlled content.

The gem's own documentation reinforces the false assumption that `process` "will verify the request did indeed come from Shopify" as an atomic guarantee covering shop attribution, when in fact only the body bytes are authenticated: [5](#0-4) 

### Impact Explanation
Most host applications key their persisted webhook side effects (order sync, inventory updates, GDPR redaction records, session/shop-scoped state, etc.) by the `shop` field returned in `WebhookMetadata`, exactly as documented: [6](#0-5) 

Since the gem itself supplies `shop` from an unauthenticated header while asserting the request "did indeed come from Shopify," a single legitimate low-privilege merchant install can forge webhooks attributed to any other shop that also has the app installed, causing the host application to process/store attacker-controlled data under a different tenant's record — a cross-tenant data integrity/confidentiality break rooted in this gem's authentication contract, not host misuse.

### Likelihood Explanation
Requires only that the attacker be an unprivileged merchant who has installed the target app (no special privileges, no access token theft, no `api_secret_key` needed) — they only need to capture one of their own legitimate webhook deliveries and replay it with a modified header, which is straightforward for any public-facing webhook endpoint.

### Recommendation
Bind the `shop` domain (and other identity-relevant fields) into the HMAC-covered content, or independently verify that the `shop` header corresponds to a shop for which the receiving app instance is currently installed/session-known before trusting it, rather than relying solely on a body-only HMAC computed with a secret shared across all tenants.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop (`attacker.myshopify.com`) and receives a legitimate webhook, e.g. `orders/create`, with body `B` and valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `client_secret`).
2. Attacker replays this exact `(B, H)` pair to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `H` is a valid HMAC of `B` under the shared secret.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...))`, causing the host app to process attacker-controlled webhook data as if it originated from the victim shop.
