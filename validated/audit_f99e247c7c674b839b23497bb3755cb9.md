### Title
Webhook shop identity is read from an HMAC-unsigned header, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/verifies the HMAC exclusively over that raw body using the app's single, shop-independent `Context.api_secret_key`. `Request#shop`, which downstream handlers use to attribute the webhook payload to a merchant, is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a value that plays no part in the signed payload.

### Finding Description
The broken binding: `HMAC_valid(raw_body, api_secret_key) == true` is treated by `Webhooks::Registry.process` as implying `request.shop == "the shop this raw_body belongs to"`, but no code path enforces that equality.

- `to_signable_string` returns `@raw_body` only: [1](#0-0) [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string`, i.e. `@raw_body`, using `Context.api_secret_key`, which is the app's single client secret shared across every shop that has the app installed - it is not shop-specific: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler, with no cross-check that the body actually belongs to that shop: [4](#0-3) 

Because `Context.api_secret_key` is the app's own secret (not per-merchant), an attacker who installs the app on their own development shop legitimately receives Shopify-signed webhooks computed with that same secret. The attacker can then POST that exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value (e.g. a victim's `*.myshopify.com` domain). `HmacValidator.validate` still returns `true` because the signature only covers `raw_body`, and `Request#shop` will report the attacker-chosen domain. The app's webhook handler, following the gem's own documented usage pattern of trusting `data.shop` from `WebhookMetadata`, will process the attacker's payload as if it originated from the victim shop: [5](#0-4) 

None of the existing guards prevent this: `HmacValidator.validate` only checks payload integrity/authenticity against the app secret, not shop identity; `ShopValidator`, `state` comparisons, and JWT `aud` checks are unrelated to the webhook path; `Request#initialize` only validates header *presence*, not header/body binding: [6](#0-5) 

### Impact Explanation
Any unprivileged attacker who can install the target app on a shop they control (a normal, permitted action for any developer/merchant) can generate arbitrary numbers of validly-HMAC'd webhook bodies, then replay them against the shared webhook endpoint with a forged `shop-domain` header pointing at any victim shop domain they choose. This causes the app to misattribute attacker-controlled webhook data to a victim tenant - a cross-tenant data-integrity/access violation, repeatable against arbitrary victim shop domains without any secret or credential from the victim. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Preconditions are cheap and fully within an unprivileged attacker's reach: create a free development shop, install the target app on it (a legitimate installation flow), and register/receive at least one real webhook to capture a valid `raw_body` + `hmac-sha256` pair. No secrets, tokens, or victim cooperation are required. The forged header substitution is trivial (a single HTTP header change) and can be repeated against any victim shop domain the attacker knows (shop domains are often guessable/enumerable, e.g. via storefront URLs). The only dependency is that the host app trusts `WebhookMetadata#shop` (as the gem's own documentation example does) to select which tenant's data to update, which is the intended/documented usage pattern of this gem.

### Recommendation
Bind shop identity into the verified signature material, or verify it out-of-band per request: e.g. maintain a per-shop allowlist of expected webhook shop domains (populated at OAuth/registration time) and reject/ignore webhooks whose `shop-domain` header does not correspond to a shop that actually has this specific webhook topic registered, or additionally verify the body's own shop-scoped identifiers (e.g. resource ownership) against the claimed shop domain before trusting `request.shop`. At minimum, `docs/usage/webhooks.md` should be updated to explicitly warn that `Registry.process`/`HmacValidator.validate` only prove the payload was signed with the app secret, not that the `shop-domain` header is authentic, since the header is attacker-controllable when the app's secret is shared across all installs.

### Proof of Concept
```ruby
# test/webhooks/cross_tenant_replay_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class CrossTenantReplayTest < Minitest::Test
      def test_same_body_and_hmac_validate_for_different_shop_domains
        raw_body = '{"id":1,"note":"legit-from-attacker-shop"}'
        hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          raw_body,
        )
        encoded_hmac = Base64.encode64(hmac)

        attacker_headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => encoded_hmac,
          "x-shopify-shop-domain" => "attacker-dev-shop.myshopify.com",
        }
        victim_headers = attacker_headers.merge(
          "x-shopify-shop-domain" => "victim-shop.myshopify.com",
        )

        attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
        replayed_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: victim_headers)

        # Binding under test: HMAC validity should not be independent of shop identity
        assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))
        assert(ShopifyAPI::Utils::HmacValidator.validate(replayed_request))

        # Both pass validation, but claim different shops -> broken SHOP_BINDING
        refute_equal(attacker_request.shop, replayed_request.shop)
        assert_equal("victim-shop.myshopify.com", replayed_request.shop)
      end
    end
  end
end
```
This demonstrates that `HmacValidator.validate` returns `true` for identical `raw_body`/HMAC pairs regardless of the `shop-domain` header, while `Request#shop` differs - confirming the signature never covers shop identity and `Registry.process` would forward the attacker's payload under the victim's shop label.

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
