This confirms the asymmetry: `AuthQuery#to_signable_string` explicitly includes `shop` in the HMAC-signed payload [1](#0-0) , but `Webhooks::Request#to_signable_string` returns only `@raw_body`, leaving `shop`, `topic`, `api_version`, and `webhook_id` completely outside the HMAC coverage [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (which checks `to_signable_string`, i.e., the body) and then trusts `request.shop`, `request.topic`, etc. to build `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Title
Webhook `shop` (and topic/webhook-id) header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` accepts the request as long as the HMAC over the body is valid, then forwards the attacker-controlled `shop` value to the app's webhook handler.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature [4](#0-3) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [5](#0-4) , whereas `shop`, `topic`, `webhook_id`, and `api_version` are parsed from the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers with no cryptographic binding to the HMAC at all [6](#0-5) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching `WebhookMetadata.new(topic: request.shop, shop: request.shop, ...)` (i.e., builds metadata straight from the unauthenticated headers) to the registered handler [3](#0-2) . This breaks the identity binding `hmac(body) == hmac(body received)` vs. the actual trust assumption apps rely on: `shop header == the tenant whose secret produced this HMAC`. Since the app's `client_secret` is shared across all shops installed on the same app (it is not shop-specific), any payload+HMAC pair that is valid for shop A's webhook delivery remains a byte-for-byte valid HMAC when the `shop-domain` header is swapped to shop B, because the header is never part of the signed bytes.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who obtains one legitimate webhook delivery (e.g., from their own store's webhook, or a leaked/observed delivery) can replay the exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. Any handler logic that trusts `WebhookMetadata#shop` to select which merchant's record to update (very common pattern, e.g., `shop/redact`, `customers/data_request`, `app/uninstalled`) will act on behalf of a different, attacker-chosen tenant, since the check only verifies the body integrity, not the shop-body binding.

### Likelihood Explanation
Webhook endpoints are internet-exposed and unauthenticated by design (they rely solely on HMAC for trust). Capturing or generating one valid body+HMAC pair (trivial for an attacker's own shop, since webhook payloads for topics like `app/uninstalled` are attacker-triggerable) and replaying it with a modified shop header requires no secret knowledge.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the signed payload used by `to_signable_string`, or otherwise cryptographically bind these header fields to the HMAC before trusting `request.shop` in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a self-serviceable webhook topic (e.g., `app/uninstalled`), capturing the raw body and the `x-shopify-hmac-sha256` value Shopify computed with the app's shared `client_secret`.
2. Attacker POSTs to the app's webhook endpoint with the same raw body and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses `shop` from the forged header [7](#0-6) ; `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body against the (unmodified) HMAC [8](#0-7) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and performs the topic's action (e.g., data deletion/session invalidation) against the victim tenant, even though the HMAC was never generated for that shop.
