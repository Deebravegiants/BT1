## Title
Bandwidth allowance is drained even when message routing permanently fails, letting any relayer grief an app's prepaid subscription - (File: `parachain/runtimes/gargantua/src/ismp.rs`, `modules/pallets/bandwidth/src/lib.rs`, `modules/ismp/core/src/handlers/request.rs`)

## Summary
The CVE describes a NetX Duo HTTP server bug where an error path fails to release a held resource (a file handle), so every *subsequent, unrelated* request is broken (404) until the server is restarted. The Hyperbridge analog is in the `pallet-bandwidth` gate consulted by `ProxyModule::on_accept`: the gate **irreversibly deducts** bytes from an app's prepaid bandwidth allowance *before* the request is actually routed, and ISMP's error-handling model does not roll back that deduction when routing subsequently fails. Combined with the protocol's documented "failed messages get no receipt, so they can be replayed" behavior, an unprivileged relayer can replay an always-failing request indefinitely, draining the target app's bandwidth allowance to zero without ever delivering a usable message.

## Finding Description
`ProxyModule::on_accept` calls the bandwidth gate unconditionally (for non-purchase messages) before attempting to route the request to its destination module: [1](#0-0) 

The gate itself performs an atomic mutate that pops/drains `Subscription.remaining_bytes` from storage — this write commits as soon as `try_consume` returns `Ok`: [2](#0-1) 

If, after the gate succeeds, the destination-module lookup fails (e.g. `pallet_id` doesn't match any registered pallet, or the proxied `Ismp::dispatch_request` call errors), `on_accept` returns `Err(...)`: [3](#0-2) 

Crucially, the ISMP request handler does **not** abort the whole batch/extrinsic when one request's `on_accept` fails — the failure is captured per-request into `Vec<Result<...>>` rather than short-circuiting with `?`, so the overall message/extrinsic still succeeds and its storage changes (including the bandwidth deduction) are committed: [4](#0-3) 

When `cb.on_accept` fails, the only compensating action is deleting the *request receipt* (so the request "can be timed out" / retried) — there is no corresponding refund of the bandwidth bytes that were already consumed: [5](#0-4) 

This "no receipt on failure ⇒ replayable" behavior is explicitly documented as intentional for state-invariant reasons, but it was not designed with irreversible side effects like bandwidth consumption in mind: [6](#0-5) 

Because the underlying request/proof is already valid and verified against the source chain's committed state, any relayer (unprivileged, permissionless — `handle_unsigned` is callable by anyone with a valid proof) can resubmit the identical `RequestMessage` repeatedly. Each resubmission re-enters `on_accept`, re-runs the bandwidth gate (draining more bytes), and then fails again at the same permanently-broken routing step (e.g. an unrecognized `to` pallet id, which will *never* resolve), so the deduction is never "earned" by a successful delivery.

## Impact Explanation
This permits permanent, unrecoverable loss of a paid resource (bandwidth allowance) purchased with real funds via `BandwidthManager.purchase()`. An app that has prepaid for a tier can have its entire allowance drained by a relayer replaying a request that can never succeed, before the app ever gets to send a real message — effectively freezing/destroying purchased funds and denying the app's route to Hyperbridge (`GateError::NoAllowance` for all subsequent legitimate traffic) until it repurchases. This satisfies the "permanent freezing of funds" / "route unable to deliver messages" impact bar.

## Likelihood Explanation
The attack requires only:
1. A single legitimately-relayed `PostRequest` from the victim app whose destination module id is unresolved on Hyperbridge's router (or otherwise causes `on_accept` to fail after the gate check) — this can be triggered by any state-machine sending a message to a non-existent/misconfigured `to` id, or exploited opportunistically whenever such a misconfiguration exists.
2. The ability to submit `Ismp::handle_unsigned` — an unsigned, fee-less, permissionless extrinsic that anyone can call as long as they hold a valid state/membership proof (which they already have, since the same proof can be resubmitted).

No admin, governance, or privileged role is required; it is reachable purely through the standard relayer message-delivery path.

## Recommendation
- Only deduct bandwidth after the destination-module dispatch has succeeded, or perform the gate check and the dispatch atomically such that a failure rolls back the bandwidth mutation (e.g. wrap `on_accept`'s gate-consume + dispatch in a storage transaction that is rolled back on error, similar to how request/response receipts are already reverted).
- Alternatively, treat "destination module not found" and other permanently-fatal routing errors as reasons to persist a receipt (blocking replay) even though the callback failed, so such requests cannot be resubmitted indefinitely.
- Add a test asserting that a request whose `on_accept` fails after the bandwidth gate succeeds leaves the app's `remaining_bytes` unchanged.

## Proof of Concept
1. App A purchases a bandwidth tier via `BandwidthManager.purchase()`, crediting an `Allowance` entry for `(app_chain, app)`.
2. A relayer submits a `PostRequest` from `app` whose `to` field does not match any registered pallet id (e.g. a typo, deprecated module id, or one the app itself constructs incorrectly) on Hyperbridge via `Ismp::handle_unsigned`.
3. `ProxyModule::on_accept` runs `BandwidthGate::try_consume`, which succeeds and deducts `bytes` from the app's `Allowance` (`modules/pallets/bandwidth/src/lib.rs` `try_consume`).
4. `on_accept` proceeds to the `match pallet_id { ... _ => Err(anyhow!("Destination module not found")) }` branch and returns `Err`.
5. In `handlers/request.rs`, this failure only triggers `host.delete_request_receipt(&wrapped_req)`; the message/extrinsic as a whole still succeeds, so the bandwidth deduction from step 3 is committed.
6. The relayer resubmits the same `RequestMessage` (same proof, same request) via `handle_unsigned` again — since no receipt exists, it is not treated as a duplicate and is reprocessed, repeating steps 3–5.
7. Repeat until `Allowance` for `(app_chain, app)` is exhausted (`GateError::NoAllowance` on all subsequent legitimate requests from the app), even though not a single message was ever successfully delivered.

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}

## Security Considerations

<Callout title={'Replay Attack Warning'} type={"warn"}>

The `IsmpHost` does not store receipts for failed messages. ie messages whose `IsmpModule` returns `Err`. This effectively allows messages to be re-executed until they time out. **Therefore you should ensure irreversible state changes occur only after a message effectively meets all success criteria**.
