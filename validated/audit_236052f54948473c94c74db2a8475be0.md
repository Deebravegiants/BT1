### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are not covered by HMAC verification, allowing tenant/topic spoofing with a replayed body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . However, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all taken straight from unauthenticated HTTP headers [3](#0-2) . These header-derived fields are then trusted and forwarded verbatim into `WebhookMetadata`, which the app's handler acts on as if they were part of the authenticated payload [4](#0-3) [5](#0-4) .

### Finding Description
The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_tenant/topic_identity`

In this gem, `hmac_signed_bytes` is only `raw_body` [2](#0-1) , whereas the shop domain, topic, webhook id, and api version used to route and label the webhook come from `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version` headers, none of which contribute to the HMAC computation [6](#0-5) .

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature and compares it against the `hmac` header using `OpenSSL.secure_compare` [7](#0-6) . Because `to_signable_string` for webhooks is body-only, this check proves nothing about which shop sent the webhook or what topic it claims to be for — only that the body bytes were HMAC'd with the app's secret at some point.

Any merchant that has installed the app is an "unprivileged internet user" from the perspective of other tenants, and can legitimately trigger a webhook delivery to the app's endpoint for their own shop (e.g. by causing an `orders/create` event). This gives them one valid `(raw_body, hmac)` pair signed with the app's shared secret. Because the signature does not bind to `shop`, `topic`, or `webhook_id`, this same `(raw_body, hmac)` pair can be replayed to the app's public webhook endpoint with arbitrary values for `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id`, and `Utils::HmacValidator.validate` will still return `true` since it only re-derives the signature from `raw_body` [8](#0-7) .

`Registry.process` then dispatches based on the (spoofable) `topic` header to look up a handler, and builds `WebhookMetadata` using the (spoofable) `shop`, `webhook_id`, and `api_version` header values, passing them to the app's handler as trusted, verified data [9](#0-8) .

### Impact Explanation
This is a cross-tenant identity spoofing vector: an attacker who controls (or has captured a delivery from) one shop can forge webhook deliveries that the app believes originate from a different, arbitrary shop (`shop` field), for a different topic than what was actually signed, and with an arbitrary `webhook_id`/`api_version`. Any application logic keyed on `WebhookMetadata#shop` or `#topic` (e.g., "look up this shop's record and update state," "run mandatory GDPR redaction for this shop," dispatch a handler keyed by topic) can be invoked with attacker-chosen tenant identity and topic, while still passing the library's `InvalidWebhookError` HMAC check. This crosses a tenant boundary (`shop` field), which fits the Critical "cross-tenant access" impact category, mediated entirely through this gem's own webhook verification code (`Registry.process` / `HmacValidator.validate` / `Request#to_signable_string`), not through host-application misuse.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair. The easiest way is to be a legitimate (even trial) merchant who installs the target app, since Shopify will then deliver real webhooks — including the HMAC signature — to the app's public endpoint for events the merchant can trigger themselves (e.g., `orders/create` by placing an order in their own store, or a webhook they can trigger via the Admin API). No secrets, tokens, or elevated privileges are needed beyond being any installer of the app; the forged request is then sent by the attacker directly to the app's public webhook URL with modified headers.

### Recommendation
Bind the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-signable content, or otherwise cryptographically tie them to the signed body, rather than relying on Shopify's TLS-delivered headers arriving unmodified. Concretely, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` (in addition to `raw_body`) before it is used for HMAC comparison, and `Registry.process` should reject requests where header-derived identity fields cannot be verified against the signed content.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com` and triggers any webhook event (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify computed with the app's shared secret.
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but rewrites:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: customers/data_request` (or any registered topic the attacker wants processed)
   - `x-shopify-webhook-id: <arbitrary>`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only hashes `raw_body`, unchanged from step 1 [2](#0-1) [10](#0-9) .
4. `Registry.process` looks up the handler for the attacker-chosen `topic` and invokes it with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", body: ..., ...)` [4](#0-3) , causing the app to run that handler's logic (e.g., data deletion/redaction, state updates) against `victim-shop.myshopify.com` even though the signed body never came from that shop or for that topic.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end
