### Title
Webhook `shop` identity is trusted from an unauthenticated header, not bound by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's `WebhookHandler` from the raw `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while `ShopifyAPI::Utils::HmacValidator` only authenticates the request body. The signature therefore never binds `shop` (or `topic`/`webhook_id`) to the payload, so any bytes verified by the HMAC are decoupled from the tenant identity the host application acts on.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/compares the HMAC solely against that raw body using `Context.api_secret_key`: [1](#0-0) [2](#0-1) 

`Registry.process` only checks this body-only HMAC before dispatching to the handler, and passes `request.shop` (read straight from the unauthenticated header via `shopify_header`) into `WebhookMetadata`, which the app uses as the tenant key: [3](#0-2) [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop_bound_by_HMAC == shop_used_by_handler`. Before the request: the HMAC secret (`api_secret_key`) is shared across every shop that has installed the app, and the signature covers only `raw_body`. After an attacker's request: they can take any legitimate `(raw_body, hmac)` pair obtained from a real webhook delivery to their own store (installing the app in their own dev/test shop lets them observe genuine, correctly signed webhook deliveries) and replay that exact body+HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes because it never inspects `shop`, so `Registry.process` dispatches to the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload never originated for that shop.

### Impact Explanation
This breaks the tenant boundary the host application relies on: `request.shop` is the only signal offered by this gem to identify which merchant a webhook belongs to, yet it is not covered by the cryptographic check. An attacker who can obtain any one valid `(body, hmac)` pair for the app (trivially, by installing the app on their own store and receiving a real webhook) can cause the host app to process/store data under an arbitrary victim shop identifier — a cross-tenant data integrity/confusion issue on the “shop” key surface that this gem exposes to consuming applications.

### Likelihood Explanation
Any user of the app (a normal merchant) can install it in their own store and receive genuine webhook deliveries at will (e.g., by creating an order), giving them attacker-controlled, validly-signed `(body, hmac)` material with no privileged credentials needed. Replaying it against the public webhook endpoint with a modified `shop-domain` header requires no `api_secret_key` knowledge, no access token, and no social engineering — only observation of one legitimate webhook call.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or otherwise cryptographically tie the declared shop header to the payload before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should cross-check `request.shop` against session/shop state already known to the app (e.g., verifying the shop is one for which this webhook topic/registration was actually created) rather than deriving tenant identity purely from an unauthenticated header.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify dev store; trigger an event (e.g., create an order) to receive a legitimate webhook POST with a correctly computed `x-shopify-hmac-sha256` for the exact `raw_body`.
2. Replay the identical POST body and `hmac-sha256` header to the app's webhook endpoint, but change `x-shopify-shop-domain` to a victim shop's domain.
3. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:13-22) succeeds because it only checks `raw_body` against the shared secret.
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb:189-199) dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the app's handler, which processes/stores data as if it came from the victim tenant.
