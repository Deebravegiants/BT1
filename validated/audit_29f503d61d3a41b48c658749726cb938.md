### Title
Unrestricted swap routes can attach arbitrary token transfers to a user’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Severity: Medium

Controller swap strategies accept caller-supplied opaque route bytes and invoke the configured router without restricting which route-selected contracts can execute beneath the caller’s authorization. A malicious venue embedded in the route can request an unrelated `token.transfer(victim, attacker, amount)`; Soroban simulation records it as an additional child of the victim’s controller authorization. If the victim signs the poisoned tree, the malicious transfer succeeds even though the controller only intended to authorize its own exact input transfer to the router. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` requires `caller` authorization and verifies that the caller owns or delegates the target account, but forwards the caller-provided `swap` bytes into the strategy path without validating the venue addresses embedded in the route. [3](#0-2) 

`swap_tokens` rejects only an empty route and calls `SwapAggregatorClient::execute_strategy(&controller, &amount_in, swap)`. [4](#0-3)  The controller separately authorizes only one exact `token.transfer(controller, router, amount_in)` invocation with no sub-invocations, which protects the controller-held input but does not prevent route-selected code from issuing a separate call that requires the original caller’s authorization. [5](#0-4) 

The post-swap validation measures only the controller’s input-token spend and output-token receipt. [6](#0-5)  It therefore cannot detect a second transfer from the victim’s wallet for an unrelated token. The repository’s authorization test demonstrates that simulation attaches such a transfer as a child of the victim’s `swap_collateral` authorization, and that signing the resulting tree drains the victim’s unrelated wallet token to the attacker while the expected collateral swap still completes. [7](#0-6) [8](#0-7) 

The same route boundary is reachable through the other router-backed controller entrypoints that accept route bytes, including `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [9](#0-8) 

### Impact Explanation
A malicious route can steal tokens that were never supplied to XOXNO Lending and are unrelated to the requested collateral or debt swap. The victim can lose the full balance of any token contract for which the malicious venue inserts `transfer(victim, attacker, amount)` into the signed authorization tree, while the lending operation itself remains solvent and produces positive measured output. This constitutes theft of user funds and closely matches the reported double-authorization pattern: the user intends to authorize the lending strategy, but the authorization tree also grants an unrelated transfer. [8](#0-7) 

### Likelihood Explanation
Exploitation requires the victim to submit a crafted route and sign the expanded authorization tree, so an attacker cannot select an arbitrary victim and drain it unilaterally. However, route bytes are opaque to normal users and are commonly generated by an external quote or routing interface; a malicious quote can provide an economically valid swap that also carries the hidden wallet transfer. Clients that automatically sign the complete simulated authorization tree will accept the second authorization. The controller’s economic checks do not mitigate this because they examine only controller-held route input and output balances. [6](#0-5) [10](#0-9) 

### Recommendation
Restrict executable route venues to a governance-controlled allowlist of immutable, reviewed venue adapters or pool implementations rather than allowing route bytes to name arbitrary contracts. In addition, require clients to enforce an authorization-tree policy: controller strategy calls should have no caller-side child token transfer, while a direct router swap should have only the expected input transfer; any additional child must reject signing. Document this policy in the transaction-signing path because the contracts cannot inspect or reject an already-signed host authorization tree. [11](#0-10) 

### Proof of Concept
1. Victim owns lending account `A`, holds collateral `C`, and also holds an unrelated token `T`.
2. Attacker deploys contract `M` exposing the venue callback expected by the configured router. Its callback executes:
   `T.transfer(victim, attacker, T.balance(victim))`.
3. Attacker supplies route bytes `R` that route a valid `C -> N` swap through `M`.
4. Victim invokes:

   `controller.swap_collateral(victim, A, C, amount, N, R)`

   The controller authenticates the victim and account, then forwards `R` to the configured router. [3](#0-2) [1](#0-0) 
5. Simulation returns a root `swap_collateral` authorization containing both the expected call flow and a child `T.transfer(victim, attacker, balance)`. The repository test records exactly this poisoned tree. [12](#0-11) 
6. If the victim signs that simulated tree, `M`’s unrelated transfer executes and the attacker receives the victim’s full `T` balance; the swap can still return the quoted output and pass all controller checks. [8](#0-7)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
