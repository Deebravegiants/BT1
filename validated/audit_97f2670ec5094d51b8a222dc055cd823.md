## Analog Found

### Title
Missing consensus-client expiry check in `validate_state_machine` allows requests/responses/timeouts to be processed against expired (stale) consensus clients - (File: `modules/ismp/core/src/handlers.rs`)

### Summary
The Nextcloud bug (CVE-2026-45284) stemmed from a check that failed to account for a user's revoked/deleted state, letting stale identities keep authenticating. The Hyperbridge `pallet-ismp` message pipeline has the same class of bug: the shared pre-flight validation function that gates request, response, and timeout processing checks that a consensus client is not *frozen*, but never checks that it has not *expired* (i.e. gone past its `unbonding_period` without an update) — even though the dedicated consensus-update path enforces both checks together.

### Finding Description
`update_client` in `modules/ismp/core/src/handlers/consensus.rs` correctly enforces both invalidity conditions before trusting a consensus proof: [1](#0-0) 

But `validate_state_machine`, the single choke point used by every request, response, and timeout handler to establish trust in a `StateMachineHeight`'s proof, only checks the frozen condition and omits the expiry condition entirely: [2](#0-1) 

`is_expired` is a real, meaningful invariant — defined on `IsmpHost` — that returns `Error::UnbondingPeriodElapsed` once `host_timestamp - last_update >= unbonding_period`: [3](#0-2) 

Because `handlers::request::handle`, `handlers::response::handle`, and `handlers::timeout::handle` all route through `validate_state_machine` for their state-machine/proof validation: [4](#0-3) 

none of these three message types ever call `is_expired`. This mirrors exactly the LDAP bug shape: the code has the correct "is this thing still valid?" check available and uses it in one code path (client updates), but a sibling code path that trusts the same underlying entity (the consensus client / its last verified state) omits the check, letting an entity that should be considered stale/untrusted (a `ConsensusState` whose unbonding period has elapsed with no validator accountability) continue to authenticate incoming messages.

### Impact Explanation
The `unbonding_period` exists specifically to bound how long a `ConsensusState` may be trusted without a live update: once it elapses, the validator set's economic security backing the consensus client is gone (deposits can be withdrawn), so an old, unrefreshed `StateCommitment` should no longer be treated as authoritative. By skipping `is_expired` in `validate_state_machine`, any relayer (an unprivileged actor, since `handle_incoming_message` extrinsics require no special permission) can submit `RequestMessage`, `ResponseMessage`, or `TimeoutMessage` payloads whose `proof.height` references a `StateMachineHeight`/`StateCommitment` produced under a now-expired consensus client, as long as the client hasn't been separately frozen. This can result in forged/stale message delivery being accepted (dispatching stale, no-longer-economically-secured `PostRequest`s to modules, releasing funds, minting tokens, or timing out requests based on state that should have been discarded once its security assumptions expired) — i.e. forged message delivery / unsound state-commitment trust, matching the "Accept only ... forged message delivery, unsound state commitment ..." bar in scope.

### Likelihood Explanation
Reaching this requires only: (1) a consensus client whose `unbonding_period` has elapsed without an `update_client` call (a realistic operational condition — chains can go quiet, or an attacker can simply wait), and (2) submitting an ordinary `RequestMessage`/`ResponseMessage`/`TimeoutMessage` with a valid membership/non-membership proof against a `StateCommitment` that was already stored before expiry. No governance/admin/relayer privilege is needed to trigger `handle_incoming_message`; any relayer or self-relaying user can submit it. This makes the bug directly reachable from a single dispatched/relayed message, matching the required "single submitted transaction/relayed proof" reachability bar.

### Recommendation
Add an `host.is_expired(proof_height.id.consensus_state_id)?` check inside `validate_state_machine` (mirroring `update_client`'s check), so that request, response, and timeout handling all reject proofs anchored to an expired consensus client, consistent with how frozen clients are already rejected.

### Proof of Concept
1. Register a consensus client with `unbonding_period = U` via `create_client`, and let it advance to a `StateCommitment` at height `H` via `update_client`.
2. Let time pass so that `host.timestamp() - consensus_update_time >= U` (client is now expired per `is_expired`, but not frozen — no fraud proof was ever submitted).
3. As any relayer, submit a `RequestMessage` (or `ResponseMessage`/`TimeoutMessage`) whose `proof.height == H`, with a valid membership proof against the already-stored (stale) `StateCommitment` at `H`.
4. `handlers::request::handle` calls `validate_state_machine(host, msg.proof.height)`, which only calls `host.is_consensus_client_frozen(...)` — no error is raised for the expired state — and the handler proceeds to verify the membership proof and dispatch the request to `IsmpModule::on_accept`, even though the consensus client backing that `StateCommitment` is no longer economically secured. /// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}

	/// Check if the client has expired since the last update
	fn is_expired(&self, consensus_state_id: ConsensusStateId) -> Result<(), Error> {
		let host_timestamp = self.timestamp();
		let unbonding_period = self
			.unbonding_period(consensus_state_id)
			.ok_or(Error::UnnbondingPeriodNotConfigured { consensus_state_id })?;
		let last_update = self.consensus_update_time(consensus_state_id)?;
		if host_timestamp.saturating_sub(last_update) >= unbonding_period {
			Err(Error::UnbondingPeriodElapsed { consensus_state_id })?
		}

		Ok(())
	}
