## Analysis Result

A valid analog exists in Chainlink's LDAP/OIDC authentication drivers, where role/session revocation depends entirely on an asynchronous background sync rather than being checked live on each request — closely mirroring the GitLab CVE-2022-2227 pattern of a removed/demoted actor retaining stale privileged access.

### Title
Stale-role privilege persistence in LDAP/OIDC session and API-token authentication - (File: `core/sessions/ldapauth/sync.go`)

### Summary
Chainlink's LDAP and OIDC authentication providers cache a user's role at session/API-token creation time in the local `ldap_sessions`/`ldap_user_api_tokens` (and `oidc_sessions`/`oidc_user_api_tokens`) tables. Authorization on every subsequent request is served purely from this local cache, not from a live check against the upstream identity provider. Revocation or downgrade of a user's role upstream is only propagated by a separate, best-effort background job (`LDAPServerStateSyncer.Work`) that can be configured to run only once at startup, and which silently aborts its entire sync cycle on any single upstream query error.

### Finding Description
`AuthorizedUserWithSession` for LDAP reads the previously stored role straight from `ldap_sessions` and only checks time-based expiry — it never re-queries LDAP: [1](#0-0) 

The same pattern exists for API tokens: [2](#0-1) 

And identically for OIDC sessions/tokens: [3](#0-2) [4](#0-3) 

The only mechanism that reconciles local cached roles/sessions with the authoritative upstream LDAP state (e.g., removing a user from the admin group, deactivating an account) is `LDAPServerStateSyncer.Work`, invoked either on a recurring timer or once at startup depending on config: [5](#0-4) 

Critically, if `UpstreamSyncInterval` is left at its zero/"instant" value, the syncer runs `Work` a single time at process start and never again for the lifetime of the node process — there is no periodic re-sync path at all: [5](#0-4) 

Even when a recurring timer is configured, a single failed LDAP group query for any of the four role groups (`admin`, `edit`, `run`, `read`) causes the entire sync cycle to bail out early via `return`, meaning purges/role downgrades for removed or deactivated users do not happen for that cycle: [6](#0-5) 

This is authenticated purely by session cookie or API token via the shared `Authenticator` interface used by the web router, so any request presenting a still-cached session/token is treated as authoritative by `AuthenticateBySession`/`AuthenticateByToken`: [7](#0-6) [8](#0-7) 

This directly parallels the GitLab bug class: an entity whose grant has been revoked or downgraded (a "previous maintainer" analog) continues to be treated as authorized because the authorization check relies on stale cached state rather than the current source of truth, and the reconciliation process (analogous to a job-runner registration/cleanup routine) is asynchronous, misconfigurable, and fails open.

### Impact Explanation
A user removed from an LDAP/OIDC admin or edit group, or deactivated entirely, retains their previously-assumed elevated role (Admin/Edit/Run) for the full `SessionTimeout` (web sessions) or `UserAPITokenDuration` (API tokens) window if `UpstreamSyncInterval` is unset/zero, or indefinitely across sync failures if the recurring sync repeatedly errors on one LDAP group query. This allows continued admin/edit-level access to the Chainlink node's HTTP API — including job/bridge/key management endpoints gated by `RequiresAdminRole`/`RequiresEditRole` — after the operator believed access had been revoked.

### Likelihood Explanation
This requires the LDAP/OIDC authentication driver to be enabled (an opt-in enterprise config), and relies on operators either leaving `UpstreamSyncInterval` at its default/zero value or on transient LDAP query failures. It does not require a malicious peer or network-layer bug — it's triggerable purely through normal user-lifecycle operations (removing/demoting a user upstream) combined with the node's own session/API-token handling, making it a realistic misconfiguration/design gap rather than a purely theoretical issue.

### Recommendation
- Re-validate role/active-status against the upstream provider (or a short-TTL cache) on each `AuthorizedUserWithSession`/`FindUserByAPIToken` call rather than trusting the value cached at session creation.
- Make `UpstreamSyncInterval` mandatory (reject zero/"instant" as a silent "sync once and never again" mode) or explicitly document and alarm on this behavior.
- Change `LDAPServerStateSyncer.Work` to process each role-group query independently (continue-on-error) so a single upstream query failure cannot suppress deactivation of removed/downgraded users across all groups.

### Proof of Concept
1. Enable the LDAP authentication driver with `UpstreamSyncInterval = "0s"` (default/unset).
2. Log in as a user who is a member of the LDAP Admin group; a session is created in `ldap_sessions` with `user_role = 'admin'` per `CreateSession` (`core/sessions/ldapauth/ldap.go:396-457`).
3. Remove the user from the Admin group upstream (or deactivate the account).
4. Because `UpstreamSyncInterval` is instant, `LDAPServerStateSyncer` never re-runs `Work` after startup (`core/sessions/ldapauth/sync.go:56-68`), so `ldap_sessions.user_role` is never updated/purged.
5. The user's existing session cookie continues to authenticate as `admin` via `AuthorizedUserWithSession` (`core/sessions/ldapauth/ldap.go:345-373`) until `SessionTimeout` naturally expires, granting continued access to admin-only endpoints such as `/v2/users`, `/v2/keys/*`, and job/bridge management routes.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

// Authenticator defines the interface to authenticate requests against a
// datastore.
type Authenticator interface {
	AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error)
	FindExternalInitiator(ctx context.Context, eia *auth.Token) (*bridges.ExternalInitiator, error)
	FindUser(ctx context.Context, email string) (clsessions.User, error)
	FindUserByAPIToken(ctx context.Context, apiToken string) (clsessions.User, error)
}

// authMethod defines a method which can be used to authenticate a request. This
// can be implemented according to your authentication method (i.e by session,
// token, etc)
type authMethod func(ctx *gin.Context, store Authenticator) error

// AuthenticateBySession authenticates the request by the session cookie.
//
// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

var _ authMethod = AuthenticateBySession

// AuthenticateByToken authenticates a User by their API token.
//
// Implements authMethod
func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
