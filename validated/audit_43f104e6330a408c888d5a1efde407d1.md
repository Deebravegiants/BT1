### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated headers while `HmacValidator` only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the cryptographic check only binds the raw HTTP body — not the `shop`, `topic`, or `webhook_id` values that the handler receives and that apps use to select a tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate` computes/compares the HMAC solely over that string: [1](#0-0) [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then forwards these header-derived, unsigned fields directly into `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) 

This mirrors the report's bug class exactly: a field (`shop`) is *acted on* by the application (tenant/session lookup, as the gem's own docs recommend: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) but is *not covered by the HMAC* that is supposed to authenticate the request: [6](#0-5) 

The identity binding that should hold is:
`shop used by handler == shop that the HMAC-signed body actually originated from`

but the gem only proves:
`HMAC(secret, raw_body) == received_hmac`

with no binding of `raw_body` to the `shop-domain` header. Because a single app's `api_secret_key` is shared across every shop that installs the app, any merchant that has installed the app can legitimately obtain a validly-HMAC'd body (by triggering their own shop's webhook, or by copying the raw body/HMAC pair from a webhook fired for their own store) and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a victim shop. `HmacValidator.validate` will still pass because it never examines the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
This crosses the tenant boundary described in the rules: an unprivileged installer of the app (attacker's own shop) can cause the host application to process attacker-controlled webhook data under another merchant's `shop` identity, since the HMAC that is supposed to authenticate "this came from Shopify for this shop" does not actually bind the shop. Depending on how the host app uses `data.shop` (e.g., to look up the offline session/access token, write records, or make privileged calls on behalf of that shop), this enables cross-tenant data injection/corruption using another tenant's identity — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires being an app installer on at least one shop (any merchant installing a public/embedded app) — no access to `api_secret_key`, tokens, or privileged accounts is needed. The attacker triggers a real webhook event for their own store (e.g., a `products/update`), captures the raw body/HMAC, and replays the POST to the app's public webhook endpoint with a spoofed `shop-domain`/`topic`/`webhook-id` header. Nothing in `Request` or `Registry` prevents this replay/spoof since headers are unauthenticated by design of `HmacValidator`.

### Recommendation
Bind the header-derived fields into the authenticated material, e.g., include `shop`, `topic`, and `webhook_id` in the signable string used by `HmacValidator`, or otherwise cryptographically verify the correlation between the HMAC'd body and the shop it is attributed to (for example, cross-checking `shop` against a known/authorized shop for the specific webhook subscription, or requiring topic/shop to be embedded in the signed payload rather than trusted headers). At minimum, update documentation to make explicit that `Registry.process` only authenticates the body, not the `shop`/`topic`/`webhook_id` metadata, so host apps do not treat `data.shop` as verified.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a legitimate webhook POST for, e.g., `products/update`, with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays this exact body `B` and HMAC header to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)` against the header value, ignoring `shop`: [7](#0-6) 
4. `Registry.process` invokes the app handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled JSON>)`, and the host application (per the gem's own documented usage pattern) acts on `data.shop` as if the event genuinely originated from the victim shop.
