### Title
Unbounded, statically-weighted `handle_unsigned` batches let an unprivileged relayer trigger unbounded, uncharged proof-verification work — DoS on mempool validation and block execution ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an unbounded `Vec<Message>` [1](#0-0)  and is charged a single fixed, content-independent weight [2](#0-1) . Every unsigned extrinsic gossiped to any full/collator node runs `Self::execute(messages.clone())` — the real, computationally expensive proof/consensus verification path — inside `ValidateUnsigned::validate_unsigned`, before any fee, deposit, or weight gate is applied [3](#0-2) . This is the same bug class as GHSA-vc29-vg52-6643/GHSA-8785-wc3w-h8q6 (CWE-770): an attacker-controlled input triggers expensive processing on every node that merely receives it, unconditioned on whether the message is ever used or paid for.

### Finding Description
- `messages: Vec<Message>` in `handle_unsigned` has no length or size cap enforced at either the `validate_unsigned` or dispatch stage [1](#0-0) . Individual `Message` variants also carry unbounded inner vectors — e.g. `RequestMessage.requests: Vec<PostRequest>`, `ResponseMessage.requests: Vec<GetRequest>`, and `GetRequest.keys: Vec<Vec<u8>>` (tests exercise 1000 requests / 256 keys apiece with no runtime-side rejection) [4](#0-3) [5](#0-4) .
- The dispatchable's declared weight is a fixed constant regardless of batch size or proof complexity: `Weight::from_parts(300_000_000, 0)` [2](#0-1) , with a comment noting it's expected to be "overridden by the FeeHandler" — but that override only adjusts `actual_weight`/fee *after* execution completes; it cannot bound how much CPU time a block producer schedules for the call *before* running it.
- `validate_unsigned` calls `Self::execute(messages.clone())` directly — i.e., full proof verification (trie membership/non-membership, BEEFY/GRANDPA/sync-committee/SP1 consensus checks depending on which client is configured) — every time any node validates the extrinsic for pool admission or gossip relay [3](#0-2) . This is by design ("free" delivery, per the docs: "all cross-chain messages received are executed for free as unsigned transactions") [6](#0-5) , but the design assumes validation is cheap; it is not bounded to be so.
- Because the declared weight does not scale with the true cost of verifying a large batch (many PostRequests/keys, or a message pinned to a consensus client whose proof verification is itself expensive), a single unsigned extrinsic can consume far more CPU/time than the runtime's weight accounting assumes, both during `validate_unsigned` (run by every peer on receipt, unmetered by consensus weight) and during actual block execution (metered only by the understated fixed weight), allowing a block producer to under-budget the real execution cost and stall block import/production across the network.
- This is reachable by any unprivileged relayer via a single dispatched, unsigned, feeless extrinsic (`Ismp::handle_unsigned`) — no signature, no deposit, no privileged role required — matching the prompt's required "single submitted transaction/extrinsic" and "relayer" threat model.

### Impact Explanation
Uncontrolled, unmetered CPU consumption from repeated or oversized `handle_unsigned` submissions can degrade or halt transaction-pool validation and block production/import network-wide — a High-severity availability impact matching the analog CWE-770 report (CVSS AV:N/AC:L/PR:N/UI:N impacting Availability). Because the call is feeless and unsigned, the attack has essentially zero cost to the attacker while imposing real computational cost on every validating/collating node, satisfying the "route unable to deliver messages" bar (a saturated node cannot process legitimate messages) from the validation rules.

### Likelihood Explanation
High: no signature, deposit, or special role is required to submit `handle_unsigned`; the batch/message vectors are unbounded; and the declared weight is a fixed constant unrelated to content size, so an attacker can trivially construct maximal-size (or maximal-verification-cost) message batches and broadcast many such extrinsics.

### Recommendation
- Bound `Vec<Message>` in `handle_unsigned` (and the nested `Vec<PostRequest>`, `Vec<GetRequest>`, `Vec<Vec<u8>>` keys, ancestry/justification lists, etc.) with `BoundedVec` and enforce the cap in `validate_unsigned` before any verification work runs.
- Make `weight()` a function of the actual message count/size (and, where feasible, an upper bound on the consensus client's proof complexity) rather than a fixed constant, so block-weight accounting reflects real cost.
- Consider adding a cheap, size/shape-only pre-check in `validate_unsigned` that rejects obviously oversized batches before invoking `Self::execute` (which performs full cryptographic/trie verification).

### Proof of Concept
1. Construct an unsigned `Ismp::handle_unsigned` extrinsic whose `messages` field contains a very large `RequestMessage` (e.g. thousands of `PostRequest`s, or a `ResponseMessage`/`GetRequest` with many `keys` entries per request) together with a proof shaped to reach the trie-verification code path.
2. Broadcast the extrinsic to the network. Every node that receives it via gossip runs `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())`, performing full proof verification over the entire oversized batch — with no fee paid and no bound rejecting the batch size beforehand.
3. Repeat/parallelize submissions (feeless, unsigned) to sustain high CPU load across mempool-validating nodes; separately, because `weight()` is fixed regardless of batch size, a block producer may include such a call believing it costs only the declared ~0.3 unit weight, while actual execution time is disproportionately larger, risking block-time overruns.

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```
