### Title
Webhook shop identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while the shop identity used downstream (`request.shop`) is read straight from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the body's HMAC and then forwards the header-derived, unverified `shop` value straight into the handler's `WebhookMetadata` [3](#0-2) . The equality the gem implicitly promises host applications — "shop that produced a validly-HMAC'd webhook" == "shop delivered in `WebhookMetadata#shop`" — does not actually hold, because the shop field is never part of the signed material.

### Finding Description
Shopify signs webhook payloads with an HMAC computed only over the raw JSON body, using the app's shared `client_secret` (`api_secret_key`). That secret is the same across every shop that has the app installed. `HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) . None of `shop`, `topic`, `api_version`, or `webhook_id` are part of `to_signable_string`, so none of them are cryptographically bound to the signature.

Because the secret is shared across all shops using the app, any unprivileged user who can install the app on their own store (or otherwise obtain one legitimately-signed webhook body/HMAC pair) can capture that valid `(body, hmac)` pair and replay it to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it only checks the body bytes against the secret, and `Registry.process` will then hand the attacker-chosen shop string to the application's handler as trusted data: [3](#0-2) 

This breaks the binding "shop authenticated by HMAC" == "shop used to identify the tenant" that host applications rely on when using `data.shop` from `WebhookMetadata` to look up or mutate per-tenant records.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (returned to their handler) as an authenticated tenant identifier — the normal, documented usage pattern shown in `docs/usage/webhooks.md` — can be tricked into processing another merchant's webhook body under an attacker-chosen shop identity, or vice versa. This can lead to cross-tenant data confusion/access (e.g., writing shop-A's webhook payload into shop-B's tenant record), which falls under the "cross-tenant access" Critical-impact category. Exploitation only requires the ability to install the app once on any shop (there is no requirement for the app's `client_secret`, an access token, or privileged access to the target merchant).

### Likelihood Explanation
Exploitation requires: (1) obtaining one legitimately signed webhook body/HMAC pair, which is possible for anyone who can install a public app on their own (free) development store and receive a webhook, and (2) sending a crafted HTTP request to the target host application's public webhook endpoint with a modified shop-domain header and the captured, still-valid body+HMAC. Both are within reach of an ordinary unprivileged internet user, and none of the gem's checks (`HmacValidator.validate`, header presence checks in `Request#initialize`) detect the mismatch.

### Recommendation
Bind the shop (and ideally topic/api-version) into the value that is verified, e.g. by requiring host applications to cross-check `WebhookMetadata#shop` against the shop associated with the resolved session/subscription before trusting it, or by having `Registry.process` reject/flag webhooks whose `shop` does not match an expected value supplied by the caller. At minimum, document prominently that `shop-domain` is not authenticated by the webhook HMAC, and add a registry-level mechanism (e.g., look up the webhook subscription's expected shop via `webhook_id`) so `process` can enforce that the delivered shop matches the shop the webhook was actually registered for.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com` and subscribe to a webhook topic (e.g. `orders/create`).
2. Trigger the webhook; capture the raw body and the `x-shopify-hmac-sha256` header Shopify sent (valid signature computed with the app's shared `client_secret`).
3. Replay the exact same body and `hmac` header to the same app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks the body bytes; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker.myshopify.com`.
