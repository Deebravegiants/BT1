### Title
Webhook `shop` (tenant identity) Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` attribute used to identify *which tenant* the webhook belongs to is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. The equality the HMAC is supposed to guarantee — "bytes verified == bytes the app acts on" — does not hold for the shop identity, breaking the tenant-binding the rest of the webhook pipeline implicitly relies on.

### Finding Description
`Utils::HmacValidator.validate` signs/verifies `verifiable_query.to_signable_string`, and for webhook requests `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived entirely from the `shopify-shop-domain` header, which is never included in the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC against the body, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` that is handed to the app's handler as the tenant/shop context: [3](#0-2) 

Because the HMAC only certifies "this body was produced with our secret," and not "this body was produced *for* the shop named in this header," a valid signed body from one shop's webhook delivery can be replayed with an attacker-modified `shopify-shop-domain` header, and the signature will still validate — because the signature never covered that header in the first place. This is exactly the "bytes verified versus bytes parsed" binding break called out in scope: the controller (`Registry.process`) verifies bytes of `@raw_body`, but parses/acts on the `shop` field taken from unauthenticated header bytes.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` as the tenant key (e.g., to look up per-shop settings, associate data, or make decisions) can be made to attribute a legitimately-signed webhook body to a different, attacker-chosen shop. Since a single app `client_secret` signs webhooks for *all* installed shops, an unprivileged merchant who has legitimately received one signed webhook for their own shop can capture that raw body + HMAC and replay it with a different shop-domain header value, causing the host application to process shop-A's data (or an empty/generic body) under shop-B's identity — a cross-tenant confusion. This matches the in-scope "cross-tenant access" Critical impact category, since the tenant boundary (which shop a webhook event belongs to) is not cryptographically enforced by this gem.

### Likelihood Explanation
Exploitation requires the attacker to already have received at least one legitimately signed webhook from Shopify for some shop (trivial for any merchant who installs the app), and requires the target host application's webhook handler to trust `data.shop` for authorization/tenant-scoping without independent verification (e.g., cross-checking against a known subscription ID or stored session) — a very common pattern given the gem's own `WebhookMetadata` API surface. No leaked credentials or privileged access is needed beyond normal use of the app as an installed merchant.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed payload verification, or otherwise cryptographically bind the header-derived `shop` value to the request (e.g., require it be corroborated via a lookup keyed by an unforgeable identifier such as the registered webhook's GraphQL ID, not client-suppliable headers). At minimum, document prominently that `Webhooks::Request#shop` is **not** covered by the HMAC and must not be trusted for tenant-scoping without additional verification.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; Shopify delivers a legitimately signed webhook with headers `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, `x-shopify-shop-domain: shop-a.myshopify.com`, and some `raw_body` (e.g. `"{}"`).
2. Attacker (a normal merchant with access to their own shop's webhook deliveries/logs) captures this raw body and its valid HMAC.
3. Attacker/host resends the identical raw body and HMAC to the app's webhook endpoint, but swaps the header to `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `@raw_body` against the HMAC: [4](#0-3) 
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: {}, ...)`, causing the app to process this event as belonging to `shop-b` even though it was never issued for that shop. [3](#0-2)
