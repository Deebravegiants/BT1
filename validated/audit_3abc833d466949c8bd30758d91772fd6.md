## Title
Webhook shop, topic and webhook_id identifiers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once the HMAC check passes, and then dispatches to a handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from HTTP headers. However, the HMAC signature only ever covers the raw request body — none of these identifying fields are bound to the signature. This is the same bug class as the M-4 report: a field that is *acted upon* (tenant/topic routing) is not covered by the cryptographic check that is supposed to prove authenticity, breaking the intended equality `verified_bytes == acted_on_bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

All other request attributes — `shop`, `topic`, `api_version`, `webhook_id` — are read directly from HTTP headers with no cryptographic linkage to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks): [3](#0-2) 

`Registry.process` treats the HMAC check as full authentication of the request and then forwards the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` to the caller's handler: [4](#0-3) 

The gem's own documentation reinforces the false guarantee, claiming that calling `process` will "verify the request did indeed come from Shopify": [5](#0-4) 

In reality, only the byte-for-byte body is verified. The equality that should hold is://
`hmac_verified(shop, topic, webhook_id, body) == acted_on(shop, topic, webhook_id, body)`
but the actual behavior is:
`hmac_verified(body) != acted_on(shop, topic, webhook_id, body)`

Because `shop` (and `topic`/`webhook_id`) are excluded from the signed bytes, any party who can obtain one valid `(body, hmac)` pair signed with the app's `api_secret_key` — for example a merchant who has legitimately installed the app and therefore receives real Shopify webhooks for their own store — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the data belongs to a different, victim shop.

### Impact Explanation
This breaks the cross-tenant boundary the HMAC is meant to enforce. A host application that (as documented) trusts `data.shop` from a processed webhook to route data into per-tenant storage, trigger per-tenant business logic, or attribute events to a specific merchant can be made to ingest another shop's identifier attached to a different (but validly-Shopify-signed) payload. This satisfies the "Critical – cross-tenant access" impact bar: an actor who is only entitled to their own tenant's webhook traffic can cause the receiving application to process/store data as belonging to another tenant.

### Likelihood Explanation
Exploitation requires possession of one legitimately Shopify-signed `(body, hmac)` pair, which any merchant with the app installed for their own shop naturally receives whenever any subscribed event fires (e.g., `orders/create`). No knowledge of `api_secret_key` or any other tenant's credentials is required — only a header swap on replay. This makes the attack straightforward for a shop-owner-level actor.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the value that is HMAC-verified, or independently verify the shop header comes from a shop currently known to have installed the app (e.g., cross-check against an existing offline session) before acting on `request.shop`/`request.topic`. At minimum, the documentation should not claim the whole request is verified to have "come from Shopify" — only the body is.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., creates an order), causing Shopify to send a legitimately-signed webhook: headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid_hmac_of_body>`, plus `raw_body`.
2. Attacker captures `raw_body` and `<valid_hmac_of_body>` from their own received webhook (they control their own server/endpoint, so this is trivial).
3. Attacker POSTs to the same app's webhook endpoint again, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it still matches, so `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to process attacker-controlled data as though it belonged to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
