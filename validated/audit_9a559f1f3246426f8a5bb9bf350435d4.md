### Title
`verify_operator_qr_code` trusts client-supplied `signup_extension` flag to skip backend operator validation - (File: `src/plans/mod.rs`)

### Finding Description
`verify_operator_qr_code` is supposed to validate an operator QR code against the backend via `backend::operator_status::request(qr_code)` [1](#0-0) . However, before that call is ever made, the function short-circuits: if `qr_code.signup_extension()` is `true` (or a debug override is set), it immediately returns a synthetic, hardcoded `LocationData` with `team_operating_country: "DEV"` and zero coordinates, without contacting the backend at all [2](#0-1) . `qr_code` is of type `qr_scan::user::Data`, which is populated directly from the raw scanned QR payload rather than from an authenticated/signed backend response, so `signup_extension()` reflects attacker-controlled input encoded in the presented QR code, not a cryptographically verified backend attribute. This means the entire authenticity check for an operator QR — its signature/validity/region binding normally enforced server-side by `operator_status::request` — can be bypassed purely by encoding a QR payload whose parsed `signup_extension` flag is `true`, producing a locally-fabricated "always-valid" `LocationData` used downstream for operator/session gating decisions (e.g., `team_operating_country`).

### Impact Explanation
This allows an unprivileged party who can produce/present an arbitrary QR code to force the orb to accept a forged operator verification result and location/country data (`"DEV"`, `0.0/0.0`) without any backend check, bypassing the intended region/operator authorization gate for signup. Depending on how `team_operating_country`/location_data is consumed downstream, this could let signups proceed under a fabricated jurisdiction/operator context that the backend never approved.

### Likelihood Explanation
The precondition is only the ability to craft/scan a QR code with a specific field set — no operator credentials, keys, or backend access are required, which is fully within the "unprivileged attacker with own QR code" threat model. The exact user-facing reachability (whether this code path is triggered outside of an operator-badge scan step reachable to an unprivileged signup participant) could not be fully confirmed from the reviewed context; the QR field parsing in `src/plans/qr_scan/user.rs` was not fully inspected before the tool budget was exhausted.

### Recommendation
Never let a locally-parsed QR flag bypass the backend authenticity check. `signup_extension` (if a legitimate feature) should only be honored after the backend `operator_status::request` call has independently confirmed `valid: true`, or the bypass branch should be restricted strictly to compile-time/debug-only builds (not runtime QR content).

### Proof of Concept
Add a unit test in `src/plans/mod.rs` (or `tests/qr_scan.rs`) that constructs a `qr_scan::user::Data` whose raw string sets the `signup_extension` component to true, calls `verify_operator_qr_code` with a mocked/never-invoked `backend::operator_status::request`, and asserts:
1. The function returns `Ok(Some((_, LocationData { team_operating_country: "DEV", .. })))`.
2. `backend::operator_status::request` was never called (e.g., via a call-counter mock), proving the backend validation was skipped for attacker-controlled input.
