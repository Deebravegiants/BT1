This confirms the vulnerability. The `shop` field is documented explicitly (`docs/usage/webhooks.md:14`) as identifying "The shop domain of the webhook," and the example handler uses it directly as the tenant key (`shop_domain: data.shop`), yet `ShopifyAPI::Webhooks::Request#shop` at `lib/shopify_api/webhooks/request.rb:20-23` reads straight from an HTTP header with no cryptographic binding to the HMAC signature, whose `to_signable_string` covers only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates only that the body matches the app's shared `api_secret_key`, then dispatches to the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` header values.

### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used for tenant attribution and dispatch are read from unauthenticated HTTP headers. Any party able to produce or capture one validly-signed webhook body for the app's shared secret (e.g., a merchant who has the app installed on their own store, which receives genuine Shopify-signed webhooks) can resend that body to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and `Topic`/`Webhook-Id`) header pointing at a different shop, and `HmacValidator.validate` will still accept it because it never inspects those headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from headers with no relation to the signed bytes: [2](#0-1) 
`Utils::HmacValidator.validate` only recomputes the signature over `to_signable_string` and compares it to the `hmac-sha256` header using the app's `api_secret_key`/`old_api_secret_key`: [3](#0-2) 
`Registry.process` trusts this validation and then dispatches using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`: [4](#0-3) 
Because the `api_secret_key` used to compute the HMAC is shared across every shop that has the app installed (it is not shop-specific), a valid HMAC over a given body only proves "some installation of this app produced this body," not "this specific shop produced this body." The equality the code implicitly assumes — `shop_that_produced_the_signed_bytes == request.shop_header` — is never checked; the `shop` header is fully attacker-controlled while the signature covers unrelated bytes. This is documented as the tenant identity itself: `docs/usage/webhooks.md:14` states `shop` is "The shop domain of the webhook," and the sample handler forwards it directly as `shop_domain: data.shop` for downstream business logic (`docs/usage/webhooks.md:26`).

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically verified bytes and the shop the application attributes the webhook to, enabling cross-tenant webhook forgery/injection: a user who controls one shop (or otherwise captures one valid webhook body/HMAC pair) can cause the app to process that payload as if it originated from a different shop, feeding forged data into that other tenant's webhook handler (e.g., order/product/customer events, GDPR request handlers, or the `shop/redact`/`customers/redact` mandatory topics), corrupting per-tenant state or triggering unauthorized tenant-scoped side effects. This matches the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Any developer using this gem's `Webhooks::Registry`/`Request` exactly as documented (`docs/usage/webhooks.md:125-136`, feeding `request.headers.to_h` and `request.raw_post` directly into `Request.new`) is exposed, since the gem itself performs no binding of `shop`/`topic`/`webhook_id` to the signature. Exploitation only requires obtaining one legitimately HMAC-signed webhook body for any shop using the same app (achievable by any merchant who installs the app on their own store and triggers an event) and replaying it with modified headers — no access to `api_secret_key` or any credential is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header used for downstream dispatch/attribution) in the HMAC-signed payload construction, or otherwise cryptographically bind the shop identity to the request (e.g., verify `request.shop` against the shop associated with the session/registration that the webhook is being processed against) before dispatching to a handler.

### Proof of Concept
1. App A is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, sharing one `api_secret_key`.
2. The attacker (merchant on `shop-a`) triggers a real event (e.g., updates a product), causing Shopify to send a webhook to the app's endpoint with body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(api_secret_key, B)`.
3. The attacker captures `B` and `H`, then POSTs a new request to the same endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/webhooks/registry.rb:190`), which succeeds because it only checks `HMAC(api_secret_key, B) == H`, per `hmac_validator.rb:27-31`.
5. `process` then calls the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: ..., body: parsed(B), ...)` (`registry.rb:198-199`), causing the app to process attacker-controlled data as an authentic webhook for `shop-b`, despite it never having originated from `shop-b`.
