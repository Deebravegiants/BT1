### Title
Missing shop-domain validation before sending `client_secret` in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the outbound host that receives the app's `client_secret` from the JWT `dest` claim without ever passing it through `Utils::ShopValidator`, while the two sibling OAuth-flow methods that perform the exact same operation (`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`) both call `Utils::ShopValidator.sanitize!` first. This is the same "code asymmetry" bug class as the referenced report: one code path enforces a binding (host must be a trusted Shopify domain) while a sibling path performing the identical operation does not.

### Finding Description
The library maintains a single list of trusted Shopify domains in `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` and a `sanitize!` method meant to be used whenever an externally-influenced `shop` value is turned into the host that will receive privileged credentials: [1](#0-0) 

`ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` both call this validator before constructing the session/host that is sent the `client_secret`: [2](#0-1) [3](#0-2) 

`TokenExchange.exchange_token`, however, derives the shop directly from the session token's `dest` claim and skips validation entirely before using it to build the request host that receives `client_secret`: [4](#0-3) 

`JwtPayload#shop` performs no domain-format check — it merely strips the `https://` prefix from `dest`: [5](#0-4) 

The resulting `shop_session` is fed to `HttpClient`, whose `@base_uri` (the host the HTTP request — including the `client_secret` in the POST body — is actually sent to) is taken verbatim from `session.shop`: [6](#0-5) 

The documentation itself confirms the trust placed on this unauthenticated-as-to-format value: *"Its `dest` claim determines which shop receives the token exchange request."*

The binding that should hold consistently across all three flows is:
`host validated by ShopValidator.sanitize! (∈ TRUSTED_SHOPIFY_DOMAINS) == host that receives the app's client_secret`

This holds in `client_credentials.rb` and `refresh_token.rb`, but is broken in `token_exchange.rb`, where the host that receives `client_secret` is whatever string is present in the `dest` claim, unchecked against `TRUSTED_SHOPIFY_DOMAINS`.

### Impact Explanation
If a `dest` value that is not a genuine `*.myshopify.com`/trusted-domain host ever reaches `exchange_token` (e.g., through non-standard/headless storefront or multi-domain session-token issuance scenarios where `dest` is not constrained to the classic admin domain), the gem will POST the app's `client_id` and `client_secret` directly to that host. This is credential leakage of the app's `client_secret` to a third-party host — matching the "High: SSRF with the app's credentials... or credential leakage into logs or error output" impact category, since the request effectively becomes an SSRF carrying the app's `client_secret` to an attacker-influenced destination.

### Likelihood Explanation
Likelihood is constrained by the fact that the `dest` claim's value is Shopify-signed content, not directly attacker-forgeable without the shared secret. However, the asymmetry itself is a clear, provable defect: identical logic (turn an inbound `shop`-like value into an outbound host for a `client_secret`-bearing request) is defended in two of three call sites and undefended in the third, exactly mirroring the reported bug class of inconsistent identity-binding enforcement across sibling functions.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` (or an equivalent trusted-domain check) to `dest_shop` in `TokenExchange.exchange_token` before constructing `shop_session`, so the binding "host validated == host receiving `client_secret`" holds consistently across `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`.

### Proof of Concept
1. Compare the three sibling flows:
   - `ClientCredentials.client_credentials(shop:)` → `Utils::ShopValidator.sanitize!(shop)` → `Session.new(shop: validated_shop)` → `HttpClient` sends `client_secret` to `https://#{validated_shop}/admin/oauth`.
   - `RefreshToken.refresh_access_token(shop:, refresh_token:)` → same `sanitize!` call before use.
   - `TokenExchange.exchange_token(session_token:, requested_token_type:, shop:)` → `dest_shop = jwt_payload.shop` (no `sanitize!`) → `Session.new(shop: dest_shop)` → `HttpClient` sends `client_secret` to `https://#{dest_shop}/admin/oauth`.
2. `JwtPayload#shop` only strips `"https://"` from the `dest` claim (`lib/shopify_api/auth/jwt_payload.rb:47-51`) — no check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.
3. `HttpClient#initialize` uses `session.shop` verbatim as the request host (`lib/shopify_api/clients/http_client.rb:16-19`), and `TokenExchange` places `Context.api_secret_key` directly in the POST body sent to that host (`lib/shopify_api/auth/token_exchange.rb:52-59`).
4. Any `dest` value that is not restricted to a trusted Shopify domain when the token is minted results in the app's `client_secret` being POSTed to that host — a validation step present in the two sibling flows but absent here.
