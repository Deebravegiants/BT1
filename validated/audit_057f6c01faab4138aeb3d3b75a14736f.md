### Title
Aleo self-payment guard bypassed via case-variant bech32m encoding accepted by `validateAleoAddress` but rejected by `compareAddresses` - ([File: packages/intents-sdk/src/lib/compareAddresses.ts])

### Summary
`validateAleoAddress` in `validateAddress.ts` calls `bech32m.decodeToBytes(address)`, which — per the Bech32/Bech32m spec (BIP‑173/BIP‑350) implemented by `@scure/base` — accepts an address string that is *entirely* lowercase or *entirely* uppercase as equally valid, decoding both to the identical 32‑byte payload. `compareAddresses`'s `Chains.Aleo` branch, however, does a raw `a === b` string comparison with no case normalization, so an all‑uppercase Aleo address and its all‑lowercase counterpart — which are the same on‑curve public key per `validateAleoAddress`'s own acceptance semantics — are judged "different" by the self‑payment guard.

### Finding Description
The broken equality is:

`validateAleoAddress(A) === validateAleoAddress(B) === true` (both accepted as valid, semantically identical Aleo addresses) **while** `compareAddresses(A, B, Chains.Aleo) === false`.

- `validateAddress.ts` `validateAleoAddress` (lines 758‑799) decodes via `bech32m.decodeToBytes(address)` [1](#0-0)  and then does pure numeric/curve-point checks — it never re-encodes or compares the textual form, so it is agnostic to letter case as long as the bech32m checksum validates (case-uniform strings only, per spec).
- `compareAddresses.ts` handles `Chains.Aleo` (along with several other chains) via the fallback branch that performs plain string equality `a === b`, with an explicit comment that the function's purpose is to compare addresses "using each chain's canonical form... e.g. to block transfers to the token's own address" [2](#0-1) [3](#0-2) .
- Unlike the `Ethereum` branch (`getAddress` normalizes case), the `Aptos/Movement/Sui/Starknet` branch (`compareHexAddress` normalizes case and padding), the `TON` branch (parses to canonical workchain+bytes), and the `Tron` branch (decodes to raw bytes) — all of which normalize before comparing — Aleo has no such normalization despite its underlying encoding (bech32m) permitting case variance for the identical payload.

Exploit flow: an attacker (an ordinary counterparty/solver supplying `destinationAddress`) submits the token custodian's own Aleo address in uppercase form (a valid bech32m encoding of the identical public key, verified by BIP‑173/350's case rule and accepted by `validateAleoAddress`) as the destination. Any self‑payment check implemented as `compareAddresses(destinationAddress, custodianAddress, Chains.Aleo)` returns `false` even though the destination is in fact the custodian address, so the guard that is supposed to block "send funds back to the bridge's own address" is bypassed.

### Impact Explanation
If the self-payment/route-truth guard is bypassed, funds intended to be routed elsewhere can instead be sent to the token's own custodian address on Aleo with no recovery path — this matches the Critical category "funds delivered to a wrong address/chain/contract with no recovery." The party harmed is whichever counterparty relies on the guard to prevent this state (the integrator/user), and the condition is repeatable on every call where an Aleo destination address happens to be supplied in a different (but bech32m-valid) case than the custodian's canonical stored form.

### Likelihood Explanation
This requires: (1) an Aleo route/token where a self-payment check calls `compareAddresses(..., Chains.Aleo)`, (2) the custodian/self address stored in canonical (e.g., lowercase) form, and (3) the attacker-supplied `destinationAddress` being an alternate valid case-casing of that exact same address. Constructing this input costs nothing (just re-casing a known public address) and is trivially repeatable. The main uncertainty is whether any code path in this repo actually invokes `compareAddresses(destination, custodianAddress, Chains.Aleo)` as a self-payment guard — I found `compareAddresses` used in `direct-bridge.ts`, `hot-bridge.ts`, `omni-bridge.ts`, and `poa-bridge.ts`, but I was not able to fetch and confirm the exact call sites/semantics for the Aleo case within the tool-call budget available. This should be verified before treating the finding as confirmed exploitable end-to-end.

### Recommendation
In `compareAddresses.ts`, add a dedicated Aleo branch that decodes both addresses via `bech32m.decodeToBytes` (matching the prefix check `"aleo"`) and compares the raw byte payloads instead of the raw strings, mirroring the pattern already used for `Tron`/`TON`/hex-address chains.

import { describe, it, expect } from "vitest";
import { validateAleoAddress } from "../validateAddress";

describe("Aleo case-variant self-payment bypass", () => {
  const lower = "aleo1<valid-checksum-lowercase-address>";
  const upper = lower.toUpperCase(); // same bech32m payload, spec-valid uppercase form

  it("validateAleoAddress accepts both case-uniform encodings", () => {
    expect(validateAleoAddress(lower)).toBe(true);
    expect(validateAleoAddress(upper)).toBe(true);
  });

  it("compareAddresses treats them as different despite identical payload", () => {
    // Broken equality: both sides valid & semantically equal per validateAleoAddress,
    // yet compareAddresses says they differ.
    expect(compareAddresses(lower, upper, Chains.Aleo)).toBe(false);
  });
});
