## Analysis: Token Allowlist Gap — Analog Found [1](#0-0) 

### Title
Missing Token Allowlist + Checks-Effects-Interactions Violation in Escrow Withdrawal Enables Malicious-Token Exploitation - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` accepts **arbitrary, user-supplied ERC20 addresses** for order inputs at `placeOrder()` with no allowlist, exactly the pattern the Kairos report warns about. Unlike the canonical EVM `IntentsBase._withdraw` (which decrements escrow state *before* calling `safeTransfer`), the Tron `withdraw()` function performs the external token transfer *before* decrementing the escrow accounting, and does so via a raw low-level `.call` rather than `SafeERC20`.

### Finding Description
In `placeOrder`, the token address for each `TokenInfo` is fully attacker/user-controlled — any address can be encoded as `order.inputs[i].token` [2](#0-1) . There is no allowlist check anywhere in `placeOrder` or `withdraw` restricting which ERC20 contracts can be escrowed.

When escrow is later released via `withdraw()` (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` or from `onGetResponse`), the function:
1. Calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` — an external call to a completely unvalidated, user-chosen contract.
2. Only *after* this external call does it execute `_orders[body.commitment][token] -= amount;` [3](#0-2) 

This is a Checks-Effects-Interactions violation: state is mutated *after* an external call to an attacker-supplied contract. The pre-call guard is also weak — it only checks `_orders[body.commitment][token] == 0` (i.e., "is escrow fully empty"), not that `amount <= escrowed`. Combined with the fact that `IERC20.transfer` is invoked via raw `.call` (no `SafeERC20`, no reentrancy guard visible on this function or its known entry points in this file), a token contract with callback/hook semantics (ERC777-style, or any custom malicious implementation the user chooses when placing the order) can execute arbitrary logic mid-transfer, before the escrow ledger reflects the debit.

This is the concrete instantiation of the Kairos report's warning: absent an allowlist restricting escrowed assets to vetted, standard-conforming ERC20s, a user can register a bespoke malicious token as `order.inputs[i].token`, and the withdrawal path's interaction-before-effects ordering becomes exploitable in ways plain "same asset" checks (as flagged in Kairos) never catch.

### Impact Explanation
If the reentrant hook can reach `withdraw()` again for the same commitment/token before the decrement executes (e.g., via any other entry point in this contract that is not individually reentrancy-guarded, or via nested cross-chain message processing), an attacker could cause the escrow ledger to permit more transfers than were actually escrowed, resulting in **fund loss for the protocol/other users** or a **stuck/incorrect accounting state** that could freeze legitimate order funds. Even absent a full double-spend, the stale-state window during an external call to an untrusted contract is a structural weakness that the token allowlist recommendation from the source report directly addresses.

### Likelihood Explanation
Likelihood is **Medium**: the primary EVM `IntentGatewayV2`/`IntentsBase._withdraw` path already follows the safe pattern (decrement-then-transfer, `SafeERC20`, `ReentrancyGuardTransient` on the main contract) [4](#0-3) , so this specific unsafe ordering is isolated to the Tron deployment variant. I could not fully confirm from the retrieved context whether a reentrant call from the malicious token during `withdraw()` can reach another unguarded state-mutating function in the same transaction (the exact reentrancy-guard coverage of the Tron contract's `placeOrder`/`fillOrder` was not fully visible in my search), so the *direct* double-spend path is not 100% proven — but the missing allowlist and CEI violation are concretely confirmed root causes matching the reported bug class.

### Recommendation
- Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to decrement `_orders[body.commitment][token]` **before** performing the external `token.call(...)` transfer, mirroring `IntentsBase._withdraw`.
- Replace raw `.call` + selector encoding with `SafeERC20.safeTransfer`.
- Consider a token allowlist/registry (as recommended in the source report) for assets eligible for escrow, or at minimum document and test against non-standard token behavior (reentrant/hooked tokens) the way `FeeOnTransferToken` is already tested for fee-on-transfer behavior in the main EVM suite.

### Proof of Concept
Not independently executed; based on static code review of `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 691–730 showing external call precedes state decrement, and lines 331–390/421-469 (same file) showing no token allowlist check on `order.inputs[i].token` at `placeOrder`. A full PoC would deploy a callback-enabled ERC20 as the escrowed input token, place an order, trigger fill/redemption, and have the token's `transfer` hook attempt reentry to demonstrate whether escrow can be drained beyond the recorded amount — this last step (concrete reentry target) was not verified within the available context and should be validated by a background agent with full repo/test access.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
