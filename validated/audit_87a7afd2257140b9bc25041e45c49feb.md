### Title
Webhook `shop` identity not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop` (and `topic`) values taken from unsigned HTTP headers to route/attribute the webhook. Because the shared app `client_secret` used to compute the HMAC is the same across every shop that has installed the app, a value obtained from a legitimate webhook delivered to the attacker's own shop can be replayed to the same endpoint with a forged `shop-domain` header, and the library will accept it as authentic and hand it to the handler under a different (victim) shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body bytes: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from unauthenticated HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate_signature` only recomputes the HMAC over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header — it never binds the `shop` header into the signed material: [3](#0-2) 

`Registry.process` performs exactly one check — HMAC validity of the body — and then immediately uses the unverified `request.shop` (and `request.topic`) to dispatch to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`HMAC(client_secret, raw_body) == received_hmac` **AND** `shop == the shop that produced raw_body`.

In this implementation only the first half is enforced. The `client_secret` (api_secret_key) is a single per-app secret shared by every shop that installs the app — it is not shop-specific. Consequently, any of the app's own merchants (an "unprivileged" actor with respect to other tenants) can:
1. Install the app on a store they control and receive a legitimately-signed webhook (e.g. `customers/data_request`, `orders/create`, `app/uninstalled`).
2. Capture the raw body and its valid `x-shopify-hmac-sha256` value.
3. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain.
4. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker's body, ...)`.

If the host application uses `data.shop` returned by this metadata to select which tenant's records to write, delete, or reconcile (a common pattern for webhook handlers, e.g. `customers/redact`, `shop/update`, `app/uninstalled`), the attacker can inject cross-tenant data or trigger tenant-scoped side effects (e.g. forcing app uninstall/cleanup handling) for a shop they do not own.

### Impact Explanation
This breaks the tenant identity binding at the heart of Shopify's multi-tenant webhook model: authenticity of *bytes* is confirmed, but authenticity of *which shop* those bytes belong to is not. An attacker-controlled webhook body can be attributed to an arbitrary victim shop, enabling cross-tenant access/confusion, which maps to the **Critical: cross-tenant access** impact category.

### Likelihood Explanation
Any developer/merchant who can install the target app on their own store (a normal, unprivileged action) can capture genuinely-signed webhook deliveries and replay them with a modified `shop-domain` header against the same publicly reachable webhook endpoint. No access to `api_secret_key`, tokens, or the victim's infrastructure is required — only the ability to intercept/observe the attacker's own legitimate webhook traffic, which is trivially available to any installer of the app.

### Recommendation
Bind the shop identity into the material that is authenticated, or independently verify that the shop asserted by headers actually owns the given webhook subscription:
- Include the `shop-domain` (and `topic`) header values in the signed payload comparison, or
- Require the caller to supply/verify a `shop` value that is validated via `Utils::ShopValidator` against a session/subscription already known to belong to that shop before invoking the handler, or
- Track per-shop expected webhook secrets/subscriptions instead of relying on a single shared `client_secret` to imply tenant identity.

### Proof of Concept
1. App `X` is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both sharing the same `api_secret_key`.
2. Shopify delivers a webhook to the app for `attacker-shop.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: customers/redact
   x-shopify-hmac-sha256: <valid HMAC over BODY using shared secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   BODY: {"shop_id":111,"shop_domain":"attacker-shop.myshopify.com","customer":{...}}
   ```
3. Attacker captures this raw body and its valid `hmac-sha256` value.
4. Attacker resends the identical body and HMAC to the same endpoint, but with:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` matches (since only body bytes are checked) and whose `shop` is `"victim-shop.myshopify.com"`.
6. `Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`).
7. `Registry.process` (per `lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body, despite the data never having originated from that shop.
