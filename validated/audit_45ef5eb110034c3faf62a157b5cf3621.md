### Title
Tightening a `RuntimeConfig` receipt-validation limit (e.g. `max_total_prepaid_gas`) between receipt creation and dequeue causes previously-valid delayed/incoming receipts to be treated as fatal `StorageInconsistentState`, halting the shard - (File: `runtime/runtime/src/lib.rs`, `runtime/runtime/src/action_validation.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
This is the same bug class as the report: a limit that is checked again at *processing* time is allowed to change between when a message/receipt is *created* and when it is *processed*, and the check uses the *current* (possibly tightened) limit instead of the value that was valid when the message was created. In nearcore, several `LimitConfig` values used by `validate_actions_with_mode`/`validate_receipt` (most notably `max_total_prepaid_gas`, `max_actions_per_receipt`, `max_number_input_data_dependencies`, `max_length_returned_data`) are re-checked against the **current** `RuntimeConfig` every time a receipt is dequeued from the delayed queue or arrives as an incoming cross-shard receipt — with no allowance for the possibility that the receipt was legitimately created under an older, more permissive config. Unlike the analogous LayerZero fix, nearcore doesn't just reject the message: a failure here is classified as unrecoverable state corruption (`StorageInconsistentState`) for delayed receipts, or a hard `RuntimeError` for incoming ones, which is a chunk-application failure/chain-halt condition rather than a graceful rejection.

### Finding Description
`validate_actions_with_mode` enforces `limit_config.max_total_prepaid_gas` unconditionally, regardless of whether the receipt is brand-new or an old one being re-validated: [1](#0-0) 

Other limits such as `max_actions_per_receipt` (line 69-74 of the same file) and, in `validate_action_receipt`, `max_number_input_data_dependencies` and `validate_data_receipt`'s `max_length_returned_data`, are likewise checked without any `ValidateReceiptMode` gating: [2](#0-1) 

`ValidateReceiptMode` explicitly distinguishes `NewReceipt` (strict) from `ExistingReceipt` ("has to be less strict because... Older receipts might have been created before new validation rules"), but this leniency is only applied to a subset of checks (e.g. `max_deploy_actions_per_receipt`, empty method name) — the gas/action-count/data-size limits above are not covered by that mode distinction: [3](#0-2) 

These limits live in `LimitConfig`, which is part of `RuntimeConfig` and is looked up fresh from `apply_state.config` (i.e. the config for the *current* protocol version) every time a receipt is validated: [4](#0-3) [5](#0-4) 

A receipt can sit in the delayed-receipt queue or in a buffered/congested cross-shard path for an extended period (delayed receipts persist across chunks/epochs; buffered outgoing receipts persist until bandwidth is granted). If, during that window, a protocol upgrade or config change reduces any of the unconditionally-checked limits (e.g. `max_total_prepaid_gas`, currently `300_000_000_000_000` in `core/parameters/res/runtime_configs/parameters.yaml:272`), a receipt that was perfectly valid at creation time (built against the older, larger limit) will fail `validate_receipt` when it is finally dequeued.

Critically, the failure mode is not a soft rejection:
- For a delayed receipt, the failure is treated as unrecoverable state corruption: [4](#0-3) 
- For an incoming (cross-shard) receipt, the failure is bubbled up as `RuntimeError::ReceiptValidationError`, aborting the chunk application for that shard: [6](#0-5) 

This is explicitly documented as an invariant of the system, showing this is a known, load-bearing assumption rather than an incidental detail: "Delayed receipts must stay valid: a delayed receipt that fails `validate_receipt` on dequeue is treated as `StorageInconsistentState`." [7](#0-6) 

This mirrors the reported bug exactly: the "quorum" (here, a `LimitConfig` value like `max_total_prepaid_gas`) used to validate a message is not the value that was in effect when the message was created, but the latest value at processing time, and any tightening in between makes a legitimately-created message unprocessable.

### Impact Explanation
Unlike the original LayerZero report (message merely fails to be relayed), the nearcore analog is more severe: a delayed receipt failing this check is classified as `StorageInconsistentState`, which nearcore treats as a fatal, unrecoverable error rather than an application-level rejection. Depending on how the caller of `Runtime::apply` handles this error, this can crash the client process or cause the shard to be unable to produce/apply further chunks (a chain stall for the affected shard), since the same delayed receipt will be re-encountered (and re-fail) on every subsequent attempt to apply that shard's chunks. This satisfies the "node panic / unbounded resource use / chain stall" impact bar.

### Likelihood Explanation
Triggering this requires a config/limit change (via protocol upgrade) to reduce one of the unconditionally-checked `LimitConfig` fields while receipts created under the old, looser config are still in flight (in the delayed queue, postponed, or buffered/congested cross-shard path — any of which can persist across chunks and epochs, especially under congestion). This is analogous to the report's admin calling `setRequiredMessagingQuorum`: it does not require a malicious actor to trigger the underlying flaw, only a legitimate governance-driven parameter change occurring while ordinary user transactions are in flight, which is a realistic operational scenario for a live network that regularly ships parameter/config updates.

### Recommendation
Do not re-validate already-admitted receipts (`ValidateReceiptMode::ExistingReceipt`) against config limits that could plausibly shrink across protocol versions (`max_total_prepaid_gas`, `max_actions_per_receipt`, `max_number_input_data_dependencies`, `max_length_returned_data`, and any other checks currently outside the `if mode == ValidateReceiptMode::NewReceipt` gates in `action_validation.rs` and `verifier.rs`). Either:
1. Gate these checks behind `mode == ValidateReceiptMode::NewReceipt` only (consistent with the existing rationale documented on `ValidateReceiptMode::ExistingReceipt`), or
2. Snapshot/pin the limits that applied when the receipt was created and use that pinned value for `ExistingReceipt` validation instead of the live `apply_state.config`.
Additionally, review whether a `ReceiptValidationError`/`StorageInconsistentState` on dequeue should ever be a fatal, unrecoverable condition versus a receipt-level failure (e.g. converting to a failed execution outcome/refund) to avoid permanent chain stalls if such a mismatch does occur.

### Proof of Concept
Conceptual sequence (concrete reproduction would require a background agent with a running testnet/test-loop harness):
1. Submit a `FunctionCall` receipt whose total prepaid gas is close to the current `max_total_prepaid_gas` (e.g. `300_000_000_000_000`), targeting a congested/receiving shard so the receipt is placed into the delayed queue or an outgoing buffer rather than executed immediately (this is straightforward to engineer via the existing congestion-control test harness, e.g. `test-loop-tests/src/tests/congestion_control_limits.rs`).
2. While the receipt is still queued, perform a protocol upgrade / config change that lowers `max_total_prepaid_gas` in `RuntimeConfig` for the new protocol version (this parameter is a normal `RuntimeConfigStore` field, changeable per protocol version via `core/parameters/res/runtime_configs/parameters/NN.yaml`).
3. Advance the chain so the queued receipt is dequeued via `process_delayed_receipts` (or forwarded and received via `process_incoming_receipts`).
4. Observe that `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)` now fails the unconditional `total_prepaid_gas > limit_config.max_total_prepaid_gas` check in `validate_actions_with_mode`, and the failure is converted into `StorageError::StorageInconsistentState` (delayed path) or `RuntimeError::ReceiptValidationError` (incoming path), aborting chunk application for that shard.

Note: I could not find historical evidence in this snapshot that `max_total_prepaid_gas` has actually been reduced across a real protocol version (only a single "Initial commit" is tracked for `parameters.yaml` in this repo), so I cannot cite a concrete historical incident — this is a structural risk in the validation design rather than a demonstrated regression. A background Devin session with full repo/test-harness access would be needed to build and run an actual end-to-end reproduction.

pub enum ValidateReceiptMode {
    /// Used for validating new receipts that were just created.
    /// More strict than `OldReceipt` mode, which has to handle older receipts.
    NewReceipt,
    /// Used for validating older receipts that were saved in the state/received. Less strict than
    /// NewReceipt validation. Tolerates some receipts that wouldn't pass new validation. It has to
    /// be less strict because:
    /// 1) Older receipts might have been created before new validation rules.
    /// 2) There is a bug which allows to create receipts that are above the size limit. Runtime has
    ///    to handle them gracefully until the receipt size limit bug is fixed.
    ///    See https://github.com/near/nearcore/issues/12606 for details.
    ExistingReceipt,
}

fn validate_action_receipt(
    limit_config: &LimitConfig,
    receipt: VersionedActionReceipt,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if receipt.input_data_ids().len() as u64 > limit_config.max_number_input_data_dependencies {
        return Err(ReceiptValidationError::NumberInputDataDependenciesExceeded {
            number_of_input_data_dependencies: receipt.input_data_ids().len() as u64,
            limit: limit_config.max_number_input_data_dependencies,
        });
    }

    if let Some(account_id) = receipt.refund_to() {
        AccountId::validate(account_id.as_ref()).map_err(|_| {
            ReceiptValidationError::InvalidRefundTo { account_id: account_id.to_string() }
        })?;
    }

    validate_actions_with_mode(
        limit_config,
        receipt.actions(),
        receiver,
        current_protocol_version,
        mode,
    )
    .map_err(ReceiptValidationError::ActionsValidation)
}

/// Validates given data receipt. Checks validity of the length of the returned data.
fn validate_data_receipt(
    limit_config: &LimitConfig,
    receipt: &DataReceipt,
) -> Result<(), ReceiptValidationError> {
    let data_len = receipt.data.as_ref().map(|data| data.len()).unwrap_or(0);
    if data_len as u64 > limit_config.max_length_returned_data {
        return Err(ReceiptValidationError::ReturnedValueLengthExceeded {
            length: data_len as u64,
            limit: limit_config.max_length_returned_data,
        });
    }
    Ok(())
}
