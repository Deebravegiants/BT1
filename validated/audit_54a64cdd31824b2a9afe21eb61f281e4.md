## Title
Webhook `shop` (and topic/webhook-id) attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the HMAC over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to attribute the webhook to a specific merchant are read from HTTP headers that are never included in the signed content. The gem's `Registry.process` trusts `request.shop` after only checking that the *body* HMAC is valid, so the identity binding "authenticated payload == the shop it is attributed to" is broken — mirroring the report's bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from headers, which are not part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC only against `verifiable_query.to_signable_string` (the body): [3](#0-2) 

`Registry.process` checks only this body HMAC, then immediately dispatches to the handler using the unauthenticated `request.shop` value as the tenant identity for the callback: [4](#0-3) 

Because `shop` (the value that host applications use to determine *which tenant/session* a webhook belongs to) is never bound into the HMAC computation, any request bearing a *body+hmac pair that was genuinely produced by Shopify for some shop* remains valid even if the `x-shopify-shop-domain` (or legacy `shopify-shop-domain`) header is swapped to name a different shop. The binding the code implicitly relies on —

```
shop_header == shop_that_the_secret-holder_actually_signed_for
```

— does not hold, because the signature never covers `shop_header`.

### Impact Explanation
An unprivileged actor who legitimately operates their own Shopify store (and therefore receives real, validly-signed webhook deliveries addressed to their own shop) can capture one such `(raw_body, hmac)` pair and replay it directly to the app's webhook endpoint with the `shop-domain` header rewritten to a victim merchant's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `WebhookMetadata` claiming the victim's shop as the source: [5](#0-4) 

Any host application that uses `data.shop` from the handler callback to look up the tenant's session/store, without re-deriving the shop from independently-authenticated state, will process attacker-controlled webhook content as if it originated from a different merchant's shop — a cross-tenant data-injection / cross-tenant access condition.

### Likelihood Explanation
Any Shopify merchant (an "unprivileged internet user" with respect to the target app) can trivially obtain a validly-signed webhook body/HMAC pair for their own store (e.g. by triggering an order/create webhook on their dev store), and only needs to change one HTTP header before POSTing to the target app's webhook endpoint. No access to `api_secret_key`, access tokens, or the target's credentials is required.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-verified content, e.g. include the `shop-domain` header in `to_signable_string`, or require host applications/`Registry.process` to cross-check `request.shop` against a value derived from an already-authenticated channel (e.g. the shop tied to the resource IDs in the signed body) before dispatching to handlers. At minimum, document that `data.shop` is unauthenticated and must not be used alone to select tenant state.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and installs the target app; Shopify delivers a legitimate webhook:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-HMAC-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   body: {"id": 123, ...}
   ```
2. Attacker intercepts/replays this exact `body` and `hmac` header, but rewrites only:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `body` only and it still matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb:190-199` proceeds and calls the handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though Shopify never generated this webhook for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
