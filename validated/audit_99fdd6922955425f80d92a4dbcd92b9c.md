### Title
CatFee API key/secret logged in plaintext at `info` level on every TRON relayer startup - (File: tesseract/messaging/tron/src/lib.rs)

### Summary
`TronClient::new` logs the entire `CatFeeConfig` struct via `{:#?}` at `log::info!` when CatFee credentials are configured. `CatFeeConfig` derives `Debug` with no redaction, so `api_key` and `api_secret` are written to the relayer's log stream unmasked, unconditionally, every time the TRON messaging client starts.

### Finding Description
`CatFeeConfig` is defined with `#[derive(Debug, Clone)]` and holds `api_key: String` and `api_secret: String` in the clear: [1](#0-0) 

`TronClient::new` constructs this config from the operator-supplied `catfee_api_key`/`catfee_api_secret` and immediately logs it with the `{:#?}` (pretty Debug) formatter at `info` level — not even gated behind `debug`/`trace`: [2](#0-1) 

Because `Debug` is derived rather than manually implemented with masking (as is done correctly elsewhere in the repo, e.g. `maskToml`/`maskSecret` in the Simplex filler, and `MpcVaultClientConfig`'s injectable logger to avoid leaking credentials into a default process-wide logger), the full plaintext `api_key` and `api_secret` end up in whatever sink the relayer's `log` crate is configured to write to (stdout, file, journal, or a shipped log aggregator). This is the direct analog of CVE-2015-6941: a service credential passed into a config struct is dumped wholesale into logs via a generic formatter instead of being redacted before printing.

### Impact Explanation
CatFee (`https://api.catfee.io`) is the bandwidth/energy purchasing service the TRON relayer uses to buy TRX energy before broadcasting transactions — this is exactly the "bandwidth purchaser" role in scope. `CF-ACCESS-KEY`/`CF-ACCESS-SIGN` (HMAC secret) are the sole authentication factors for CatFee's API: [3](#0-2) 

Anyone who can read the relayer's log output — a shared log aggregation service, a support bundle, CI artifact, crash reporter, or any party with lower-privilege log access than the config file itself — obtains full read/write control of the operator's CatFee account. They can place unauthorized energy orders against the operator's balance (direct financial loss/theft), exhaust the account's funds, or disrupt the relayer's bandwidth-purchasing capability so it can no longer submit TRON transactions (denial of relaying / message-delivery failure for the ISMP bridge on TRON), fitting both the "concrete theft of funds" and "route unable to deliver messages" impact bars.

### Likelihood Explanation
This is triggered unconditionally, with no attacker interaction required, any time `TronClient::new` runs with CatFee credentials configured (i.e., on every relayer process start/restart) — it's not gated behind a debug flag, so any environment where relayer stdout/logs are collected or shipped (the norm for production infrastructure) leaks the secret automatically. The only precondition is that log output is accessible to someone other than the person who owns the config file, which is a very common operational setup (log aggregation, monitoring dashboards, on-call tooling).

### Recommendation
- Implement a manual `Debug` (or `redact`) for `CatFeeConfig` that masks `api_key` and `api_secret` (e.g., show only a short prefix/suffix, mirroring `maskSecret`/`maskToml` already used in the Simplex filler codebase).
- Change the startup log line in `TronClient::new` to log only non-sensitive fields (e.g., `api_base`, whether CatFee is enabled) instead of the full `{:#?}` dump.
- Audit other `Debug`-derived config structs across `tesseract/*` that carry secrets (signers, API tokens) for the same pattern.

### Proof of Concept
1. Configure a TRON chain entry with `catfee_api_key` and `catfee_api_secret` set.
2. Start (or restart) the `tesseract-messaging-tron` relayer process.
3. Observe the `info`-level log line emitted from `TronClient::new`:
   `CatFee integration enabled: CatFeeConfig { api_key: "<plaintext>", api_secret: "<plaintext>", api_base: "https://api.catfee.io", timeout: 30s }`
4. Any consumer of that log stream (log aggregator, support ticket attachment, crash dump) now has full CatFee API credentials and can issue authenticated requests against `https://api.catfee.io` on the operator's behalf. [2](#0-1) [1](#0-0)
