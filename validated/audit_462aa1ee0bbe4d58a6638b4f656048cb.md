### Title
Permanent freeze of escrowed order funds via all-or-nothing push transfer to a beneficiary that reverts (blacklisted/non-receiving address) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` releases all escrowed order tokens plus accumulated transaction fees to a single `beneficiary` address using low-level pushed calls that revert the entire withdrawal if any single transfer fails. Because the beneficiary is fixed at commitment time (`order.user` for refunds) and the withdrawal is triggered by an unprivileged relayed ISMP message, a beneficiary that cannot receive one of the escrowed tokens (e.g., a blacklisted stablecoin address) permanently blocks release of every asset in that order — reproducing the exact "push-not-pull, one bad recipient bricks the whole settlement" root cause flagged in the referenced Cooler H-4 analog.

### Finding Description
`withdraw()` iterates over `body.tokens` and unconditionally reverts the whole call if any transfer fails: [1](#0-0) 

This function is reachable without any privilege from two paths:
1. `onAccept()` — invoked by the host when a relayed `RedeemEscrow`/`RefundEscrow` POST request is delivered, using a `beneficiary` decoded straight from the incoming message body: [2](#0-1) 
2. `cancelOrder()` on the source chain (same-chain path), which builds the `WithdrawalRequest` with `beneficiary: order.user` — an address fixed permanently in the order commitment at `placeOrder` time: [3](#0-2) 
and on the destination-chain `RefundEscrow` dispatch path, again hard-coding `beneficiary: order.user`: [4](#0-3) 

The loop transfers each escrowed token individually with `token.call(...)` and `if (!success) revert TransferFailed();`, then separately sweeps the accumulated `TRANSACTION_FEES` bucket to the *same* beneficiary with the same revert-on-failure semantics: [5](#0-4) 

If any one of the escrowed tokens (e.g. a stablecoin implementing an address blacklist such as USDC) refuses to transfer to `beneficiary` — whether because the beneficiary address was already/later blacklisted, or is a contract that reverts on receipt — the entire `withdraw()` call reverts. Since the relayed message/commitment is immutable (the order hash embeds `order.user`, and the WithdrawalRequest is derived deterministically from it), the message can be resubmitted indefinitely and will fail every time, exactly mirroring the Cooler pattern where `repayTo` could be forced to a non-receiving address to make the corresponding code path permanently un-executable. Unlike Cooler where the lender chooses the failing address deliberately, here the same push-everything-to-one-address design means a single non-receiving output freezes co-mingled funds (unrelated input tokens and protocol fees) that would otherwise be independently redeemable.

### Impact Explanation
All escrowed input tokens and any escrowed transaction fees tied to that specific order commitment become permanently unredeemable — neither refundable to the user nor payable out — because `withdraw()` can never succeed for that beneficiary. This is a concrete permanent freezing of user/protocol funds triggered purely by ordinary cross-chain message delivery (no admin/governance/relayer privilege required to trigger the freeze condition, only a beneficiary address that becomes non-receiving for one of the escrowed tokens).

### Likelihood Explanation
Any regulated stablecoin used as an escrowed input or fee token (USDC, USDT, etc.) can blacklist an address at any time for reasons unrelated to the protocol. Because `order.user`/`beneficiary` is embedded immutably in the order commitment at placement time, there is no way to update the destination of a stuck withdrawal after the fact — the loop's all-or-nothing design converts a single-token blacklist event into a total freeze of the entire order's escrow.

### Recommendation
Do not couple settlement of unrelated escrowed assets into a single all-or-nothing push loop. Either (a) isolate each token's transfer so failure of one does not block the others (try/catch or per-token accounting with partial completion), or (b) switch to a pull-based claim pattern (credit balances per beneficiary/token, let the beneficiary withdraw independently) rather than pushing all tokens/fees to `beneficiary` in one atomic call, consistent with the Cooler recommendation of not letting a single push destination gate the whole payout.

### Proof of Concept
1. User places an order via `placeOrder()`, escrowing `TokenA` (a blacklist-capable stablecoin) and `TokenB`, and paying fees in `feeToken` — see escrow logic in `placeOrder` [6](#0-5) .
2. Before the order is filled/cancelled, `order.user`'s address gets added to `TokenA`'s blacklist (external event, e.g. USDC compliance action) or the user has an address that is a non-payable contract.
3. User calls `cancelOrder()` after expiry; on the source chain this builds `WithdrawalRequest({... beneficiary: order.user})` and calls `withdraw(body, true)` [7](#0-6) .
4. Inside `withdraw()`, the loop reaches `TokenA`'s transfer to `beneficiary`, which reverts because the address is blacklisted: `if (!success) revert TransferFailed();` [8](#0-7) .
5. The entire transaction reverts — `TokenB` and the escrowed fees, which had no issue, are never released. Retrying `cancelOrder`/redelivering the message always hits the same revert, permanently freezing the full escrow.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            // Verify we're on the correct chain
            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
