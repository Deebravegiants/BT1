### Title
Webhook shop-domain header is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only the HMAC of the raw request body, but the `shop` domain that is handed to the app's webhook handler as an authenticated identity is taken from an unauthenticated header, breaking the binding between "bytes verified" and "bytes acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Registry.process` validates the HMAC solely over that signable string via `Utils::HmacValidator.validate(request)` [2](#0-1) . The `shop` attribute, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header without any cryptographic binding to the signed payload [3](#0-2) . `Registry.process` then forwards this unauthenticated `shop` value straight into `WebhookMetadata` passed to the app's handler [4](#0-3) .

Because `Context.api_secret_key` is a single shared secret for all shops that install a given (typically public/multi-tenant) app, any shop that has installed the app can produce a body with an attacker-chosen HMAC-valid signature (e.g., by triggering a webhook for their own store with attacker-controlled content), then replay that request against the app's webhook endpoint while substituting the `shop-domain` header to claim to be a different, victim shop. Since the header isn't part of `to_signable_string`, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the handler with `data.shop` set to the forged victim domain [5](#0-4) .

This breaks the equality the library documents and implicitly promises: `shop authenticated by HMAC` == `shop delivered to handler`. The docs explicitly claim `process` "will verify the request did indeed come from Shopify" [6](#0-5)  and describe `data.shop` as "The shop domain of the webhook" [7](#0-6)  — i.e. a verified attribute — while in fact only the body bytes are verified, not the shop identity.

### Impact Explanation
This is analogous to the audited bug class: a field (`shop`) is acted upon by downstream logic (handler dispatch, tenant identification) but is not covered by the cryptographic check (`HMAC` over `raw_body` only). Handlers commonly key session/data lookups off `data.shop` per the documented API contract shown in the gem's own docs example (`shop_domain: data.shop`) [8](#0-7) . An attacker-controlled webhook body delivered under a forged victim shop identity can lead to cross-tenant data corruption/injection into a victim merchant's records, since the app has no library-level means to detect the mismatch — it can cross a tenant boundary using only the attacker's own legitimately-issued webhook (no access token, secret, or privileged account needed).

### Likelihood Explanation
Exploitation requires only that the attacker operate a shop that has the target app installed (a normal, unprivileged action for any public app on the Shopify App Store) and be able to trigger a webhook with attacker-influenced body content (e.g., renaming a product, editing an order note) whose topic is one the target app subscribes to, then replay the delivered request to the app's public webhook endpoint with a modified `shop-domain` header. No secrets, TLS interception, or social engineering are required — the shared `api_secret_key` model for multi-tenant apps is what makes this straightforward.

### Recommendation
Include the shop domain (and webhook id/topic) inside the HMAC-signed payload comparison, or otherwise cryptographically bind the claimed shop to the request — e.g., require the caller to independently confirm the `shop` header corresponds to a shop that is currently installed/authorized for the app before trusting `data.shop`, and document this requirement explicitly. At minimum, update the "will verify the request did indeed come from Shopify" claim in `docs/usage/webhooks.md` to clarify that only the body integrity is verified, not the shop identity header.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g. `products/update`) with an attacker-controlled body `B` on a topic the app subscribes to; Shopify delivers a request signed with the shared `api_secret_key`, producing `hmac = HMAC-SHA256(secret, B)`.
3. Attacker captures this request and replays it to the app's public webhook endpoint, keeping `x-shopify-hmac-sha256` and the body `B` unchanged, but replacing `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only [9](#0-8)  — validation succeeds because `B` and the HMAC are unchanged.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: B ...)` [5](#0-4) , causing the app to process attacker-controlled data `B` under the victim tenant's identity.
