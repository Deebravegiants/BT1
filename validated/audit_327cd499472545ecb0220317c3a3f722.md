### Title
`migrate_coin_store_to_fungible_store` silently drops the `frozen` flag for zero-balance `CoinStore`s, permanently and permissionlessly unfreezing accounts - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`coin::migrate_coin_store_to_fungible_store` is a permissionless `public entry fun` that anyone can call for **any** list of addresses, converting each address's `CoinStore<CoinType>` into a `FungibleStore` [1](#0-0) . The underlying `maybe_convert_to_fungible_store` only propagates the CoinStore's `frozen` flag to the new/target `FungibleStore` inside the branch that fires when `coin.value > 0`; when the balance is `0`, the `CoinStore` (including its `frozen` field) is simply destroyed with no effect on any existing primary store's freeze state [2](#0-1) . This mirrors the ZetaChain bug class: a critical state field (`gasPriceByChainId` there, `frozen` here) is not carried over during a state-transition/migration path, silently corrupting a control invariant (freeze/custody control) rather than causing a simple revert.

### Finding Description
`maybe_convert_to_fungible_store<CoinType>` destructures the `CoinStore`:
```
let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } = move_from<CoinStore<CoinType>>(account);
if (is_coin_initialized<CoinType>() && coin.value > 0) {
    ...
    if (frozen != fungible_asset::is_frozen(store)) {
        fungible_asset::set_frozen_flag_internal(store, frozen);
    }
} else {
    destroy_zero(coin);
};
``` [3](#0-2) 

The `frozen` copy-over (`fungible_asset::set_frozen_flag_internal`) only executes inside the `coin.value > 0` branch. If `coin.value == 0` (whether or not the store was already frozen by the issuer/freeze authority), the function takes the `else` path, calls `destroy_zero(coin)`, and drops `frozen` on the floor — it never checks whether a primary `FungibleStore` already exists at that address and never applies the frozen state to it.

Critically, `migrate_coin_store_to_fungible_store` has **no signer/authorization check at all** — it accepts an arbitrary `vector<address>` and calls `maybe_convert_to_fungible_store` for each one [1](#0-0) . This means any unprivileged account can trigger the migration for a target address it does not own.

Attack path:
1. An issuer/compliance authority freezes a `CoinStore<CoinType>` for a sanctioned/blacklisted account (e.g. via the coin freeze capability path in `coin.move`), while that account's `CoinStore` balance happens to be `0` (fully withdrawn, or frozen at zero).
2. Any third party calls `coin::migrate_coin_store_to_fungible_store<CoinType>([victim_or_target_address])`.
3. Because `coin.value == 0`, the `else` branch runs, the `CoinStore` (with `frozen = true`) is destroyed, and no `frozen` state is ever written into a `FungibleStore`/primary fungible store for that address.
4. If a primary fungible store for that address is later created (auto-created on next deposit via `primary_fungible_store::ensure_primary_store_exists`, or already existed pre-migration in the "existing primary fungible store" scenario acknowledged in the module's own test `test_migration_with_existing_primary_fungible_store` [4](#0-3) ), it is unfrozen, and the account can freely receive/hold/transfer the asset — bypassing the freeze the issuer intended.

This breaks the custody invariant that "fungible asset metadata, primary and secondary stores, and freeze state must preserve supply and holder identity" — here freeze/holder-control state is lost rather than balance, but the effect is the same class of bug as the ZetaChain report: a state variable that must be copied during a migration/upgrade is silently omitted, and the omission is externally triggerable by an unprivileged party.

### Impact Explanation
Freeze functionality in `coin.move`/`fungible_asset.move` exists specifically to allow issuers to block a sanctioned or compromised account from moving assets. If a permissionless, non-owner-gated function can strip that freeze state for a zero-balance account, an attacker (or the frozen party colluding with a helper) can effectively defeat the issuer's freeze control before the account is funded, or before a legitimate deposit lands into what should still be a frozen store. This is a custody-control bypass: unauthorized/permissionless removal of freeze authority state, tied to real-value-bearing accounts (any `CoinType` migrated to the fungible-asset model, which as of Aptos framework updates includes `AptosCoin`/APT and other registered coins). This qualifies as a broken custody invariant with mainnet relevance since `migrate_coin_store_to_fungible_store` is a public, unauthenticated entry function usable against any address.

### Likelihood Explanation
The precondition (a frozen `CoinStore` with zero balance) is realistic — issuers commonly freeze an account after (or while) it has been drained to zero, or freeze immediately upon account creation before funding. The migration function itself requires no special privilege and no signature from the target account, so exploitation only requires observing (or causing) a frozen, zero-balance `CoinStore` and then calling the public entry function once. This makes the likelihood high once such a state exists, though it does depend on freeze being used at zero balance (compliance/issuer-specific behavior), which is why this is best classified as a real but conditional custody-integrity bug rather than a universally-triggerable one.

### Recommendation
In `maybe_convert_to_fungible_store`, always propagate the `frozen` flag regardless of `coin.value`:
- Ensure/create the primary (or corresponding) `FungibleStore` even when `coin.value == 0`, and apply `fungible_asset::set_frozen_flag_internal` to match the source `CoinStore`'s `frozen` state before destroying the `CoinStore`.
- Alternatively, if the design intends to skip store creation for empty/never-funded accounts, explicitly reject migrating a `frozen` `CoinStore` with zero balance (abort) rather than silently discarding the frozen flag, and/or restrict `migrate_coin_store_to_fungible_store` to only allow the account owner or a privileged migrator to migrate frozen stores.

### Proof of Concept
1. Issuer registers `CoinType` for `victim` via `coin::register`, creating `CoinStore<CoinType> { coin: 0, frozen: false, ... }`.
2. Issuer calls the coin freeze path to set `frozen = true` on `victim`'s `CoinStore` (balance remains `0`).
3. Any unprivileged account calls:
   `coin::migrate_coin_store_to_fungible_store<CoinType>(vector[victim_addr])`
   → hits `maybe_convert_to_fungible_store`, `coin.value == 0` → `else` branch → `destroy_zero(coin)`, `frozen` discarded, no `FungibleStore` frozen-flag set.
4. Later, `victim` receives `CoinType` (auto-creating/using a primary `FungibleStore` via `primary_fungible_store::ensure_primary_store_exists`), and this store is unfrozen — the issuer's freeze is bypassed, matching the "supply/custody accounting corruption that... destroys recovery rights" impact class.

This closely mirrors the referenced `verifyState`/`test_migration_with_existing_primary_fungible_store` style test already present in `coin.move` [4](#0-3) , but exercising the zero-balance/frozen branch instead, which is not covered by the existing tests.

    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.
                // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
                // function would convert and deposit the rest coin into the primary store and freeze it to make the
                // `frozen` semantic as consistent as possible.
                if (frozen != fungible_asset::is_frozen(store)) {
                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
            } else {
                destroy_zero(coin);
            };
            event::destroy_handle(deposit_events);
            event::destroy_handle(withdraw_events);
        };
