### Title
BandwidthManager.onAccept fails to authenticate the sending module on Hyperbridge, allowing any account to forge `SetTiers`/`Withdraw` governance actions - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.onAccept` only checks that an incoming ISMP POST request's **chain** of origin (`request.source`) equals Hyperbridge, but never checks the **module** of origin (`request.from`) against `PALLET_BANDWIDTH_MODULE_ID` ("BWMARKET"). Since `from` on a `DispatchPost` is a caller-supplied `Vec<u8>` that `pallet-ismp`'s dispatcher forwards verbatim with no binding to the actual calling pallet's identity, any account able to dispatch an ISMP POST request on Hyperbridge can set `from = b"BWMARKET"` and impersonate `pallet-bandwidth`, triggering privileged `Withdraw`/`SetTiers` actions on the EVM-side `BandwidthManager` contract. This is directly analogous to CVE-2021-38016: a coarser-grained origin check (chain-level) is substituted for the finer-grained one (module-level) that the security model actually requires, allowing the trust boundary to be crossed.

### Finding Description
`BandwidthManager.onAccept` is documented as accepting "inbound governance from `pallet-bandwidth`" and declares `PALLET_BANDWIDTH_MODULE_ID = bytes("BWMARKET")` specifically "because the pallet enforces this on inbound messages" [1](#0-0) , but the actual enforcement never checks `request.from`: [2](#0-1) 

The only origin check performed is:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
```
which only verifies the request came from the Hyperbridge *chain*, not from the specific `pallet-bandwidth` *module* on that chain. `PALLET_BANDWIDTH_MODULE_ID` is only ever used as the outbound `to` field in `purchase()`, never as an inbound authentication check [3](#0-2) .

On the Hyperbridge (Substrate) side, `from` is fully caller-controlled. `pallet-ismp`'s low-level `IsmpDispatcher::dispatch_request` builds the outgoing `PostRequest` by forwarding `dispatch_post.from` verbatim, with no verification that it matches the identity of the pallet/account invoking it: [4](#0-3) 

Documentation confirms this generic dispatch path is reachable by an ordinary signed extrinsic, which freely sets `from` to any module id it likes: [5](#0-4) 

Because `EvmHost.dispatchIncoming`/`HandlerV2` only validate the merkle/consensus proof and destination/timeout of the request (not the semantic `from` field against the target app's expected sender), and because `onlyHost` on `BandwidthManager.onAccept` only guarantees the call came through the legitimate host/handler pipeline (not that the *logical sender module* is `pallet-bandwidth`), any account on Hyperbridge with access to `IsmpDispatcher::dispatch_request` (or any thin wrapper pallet/extrinsic exposing it, as shown in the docs) can dispatch a POST request:
- `dest` = the EVM state machine hosting `BandwidthManager`
- `to` = the `BandwidthManager` contract address
- `from` = `b"BWMARKET"`
- `body` = `[uint8(OnAcceptActions.Withdraw)] ++ abi.encode(Withdrawal{token: feeToken, beneficiary: attacker, amount: <contract balance>})`

Once relayed through the permissionless `HandlerV2.handlePostRequests`/`EvmHost.dispatchIncoming` pipeline, `BandwidthManager.onAccept` will accept it as legitimate governance from `pallet-bandwidth` and execute the withdrawal or tier update.

### Impact Explanation
This allows theft of the entire fee-token/native-currency treasury accumulated in `BandwidthManager` via a forged `Withdraw` action, and/or manipulation of `tierPrice` via a forged `SetTiers` action (e.g., setting all tier prices to zero to obtain unlimited free bandwidth credits, or to an extreme value to grief legitimate buyers). This is concrete theft of funds and an unauthorized app action — a single unprivileged Hyperbridge account/extrinsic plus a permissionless relay is sufficient; no admin, governance, or node compromise is required.

### Likelihood Explanation
High. `IsmpDispatcher::dispatch_request` is a standard, widely-used interface on Hyperbridge for many pallets, and the docs explicitly show `from` being set freely by a signed extrinsic. No special privilege is needed beyond having an ISMP dispatch pathway on Hyperbridge and paying the normal dispatch fee; delivery is done by any permissionless relayer via `HandlerV2`.

### Recommendation
In `BandwidthManager.onAccept`, in addition to the existing `request.source` check, verify `request.from` equals `PALLET_BANDWIDTH_MODULE_ID` before decoding/executing `SetTiers` or `Withdraw`:
```solidity
if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();
if (!request.from.equals(PALLET_BANDWIDTH_MODULE_ID)) revert UnauthorizedAction();
```
This mirrors the pattern already correctly used elsewhere in the codebase (e.g., `ExtrinsicIntents._authenticate`, `HyperFungibleToken.onAccept`, `HyperbridgeLzEndpoint.onAccept`), all of which validate both the source chain and the specific sending module/address before trusting a payload.

### Proof of Concept
1. On Hyperbridge, any signed account calls a pallet exposing `IsmpDispatcher::dispatch_request` (e.g. the documented `send_message`/`dispatch_to_evm` pattern) with:
   ```rust
   DispatchPost {
       dest: StateMachine::Evm(<bandwidth_chain_id>),
       from: b"BWMARKET".to_vec(),               // forged sender, unchecked
       to: <BandwidthManager_address_bytes>,
       timeout: 0,
       body: [OnAcceptActions::Withdraw as u8]
           .iter().chain(abi_encode(Withdrawal {
               token: fee_token_address,
               beneficiary: attacker_address,
               amount: contract_balance,
           })).collect(),
   }
   ```
2. Any permissionless relayer submits the resulting proof through `HandlerV2.handlePostRequests`, which calls `EvmHost.dispatchIncoming` → `BandwidthManager.onAccept`.
3. `onAccept` checks `request.source == hyperbridge()` (true) and never checks `request.from`, decodes the forged `Withdraw` action, and transfers the entire `feeToken`/native balance to the attacker via `IERC20(w.token).safeTransfer(w.beneficiary, w.amount)` / the native `.call{value: w.amount}("")` branch [6](#0-5) .

    /// @notice Inbound governance from `pallet-bandwidth`. The first
    /// body byte selects `OnAcceptActions`; the remainder is the
    /// action's ABI-encoded payload.
    /// @dev Only the configured host may invoke (`onlyHost`); the
    /// request's `source` must additionally equal hyperbridge.
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        PostRequest calldata request = incoming.request;

        if (!request.source.equals(IDispatcher(_host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.SetTiers) {
            Tier[] memory updates = abi.decode(request.body[1:], (Tier[]));
            for (uint256 i = 0; i < updates.length; i++) {
                tierPrice[updates[i].tier] = updates[i].price;
                emit TierSet(updates[i].tier, updates[i].price);
            }
        } else if (action == OnAcceptActions.Withdraw) {
            Withdrawal memory w = abi.decode(request.body[1:], (Withdrawal));
            if (w.token != address(0)) {
                IERC20(w.token).safeTransfer(w.beneficiary, w.amount);
            } else {
                (bool sent,) = w.beneficiary.call{value: w.amount}("");
                if (!sent) revert InsufficientNativeToken();
            }
            emit Withdrawn(w.token, w.beneficiary, w.amount);
        } else {
            revert UnauthorizedAction();
        }
    }
