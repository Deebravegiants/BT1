### Title
Fee-free swap by redirecting LI.FI output to attacker address, bypassing `hinkalFee`/`relayFee` calculation - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction`/`ExternalActionSwap` measure the swap output solely by the before/after token balance of the *external action contract itself*, using attacker-supplied `externalActionMetadata` calldata that is forwarded verbatim to the LI.FI `router`. Since the attacker fully controls this calldata (and only its hash is pinned via `calldataHash`), they can craft a route whose final leg pays the output token to an address they control instead of back to the external-action contract, making the measured `swappedAmount` (and thus the protocol/relay fee) zero while they still receive the real swap proceeds off-chain.

### Finding Description
`ExternalActionSwap.swap` computes the fee entirely from `swappedAmount`, which is derived from a balance diff taken on the calling contract: [1](#0-0) 

```
function callRouter(...) internal override returns (uint256 swappedAmount) {
    uint256 balanceBefore = getERC20OrETHBalance(outputToken);
    ...
    (bool success, ) = router.call(externalActionMetadata);
    ...
    swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
}
```

`externalActionMetadata` is opaque calldata that the user constructs off-chain for the LI.FI aggregator; the only on-chain constraint tying it to the transaction is a hash check performed by the same user who builds the proof: [2](#0-1) 

Nothing forces the swap route encoded in this calldata to deliver its output back to `address(this)` (the `LifiExternalAction` contract). Generic swap aggregators like LI.FI typically allow specifying an arbitrary final `receiver`. If the attacker points the receiver at their own EOA/contract, the tokens never land on the `LifiExternalAction` contract, so:

`swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore == 0`

Then in `ExternalActionSwap.swap`: [3](#0-2) 

```
uint256 swappedAmount = callRouter(...);          // == 0
uint256 hinkalFee = hinkalHelper.calculateRelayFee(swappedAmount, 0, ...); // == 0
...
uint256 amountToSendToHinkal = swappedAmount - totalFee;  // == 0
transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal); // sends 0
```

Back in `Hinkal.transact`, this is reconciled through the on-chain-creation balance equation. The output token index for a swap uses `onChainCreation[i] = true` (amount unknown ahead of proof generation), which forces `amountChanges[i] == 0` and requires the equation `balanceDif == 0 + utxoAmount`: [4](#0-3) 

Since `utxoSet[0].amount == 0` and Hinkal's own balance of `outputToken` never changed (the router paid the attacker directly, not Hinkal), `balanceDif == 0 == utxoAmount`. The equation is *satisfied*, not violated — the check has no way to see the value that left the system through the router call. Meanwhile the input token side is a normal, correctly-accounted shielded spend (`amountChanges[0]` negative, matching the real transfer of `inputAmount` out of the shielded pool into `LifiExternalAction`), so that leg passes as well.

Net effect: the input shielded balance is correctly debited, the swap executes and the real proceeds are paid straight into an address the attacker controls, but the fee-computation basis (`swappedAmount`) and the resulting relay/Hinkal fee are zero. `flatFee` charged on the input side is unaffected by this trick (it's deducted from `inputAmount`, not `swappedAmount`), but `hinkalFee` (the variable-rate protocol fee, and `relayFee`'s output-token component when `feeToken == outputToken`) is completely avoided.

### Impact Explanation
This is theft of protocol/relay fees: the attacker executes a full-value swap through Hinkal's swap external action while paying none of the variable-rate protocol fee that should apply to the swapped amount. This matches the "High — theft ... of protocol/relay fees" impact category, since it is a systemic bypass of the fee mechanism available to any unprivileged user who can build a valid proof and supply arbitrary router calldata.

### Likelihood Explanation
Likelihood is high for any user willing to construct custom LI.FI routing calldata (which the LI.FI SDK/generic-swap contracts commonly support) with a non-default receiver. No relayer, admin, or oracle collusion is required — only building a self-authored proof (`circomData.originalSender == msg.sender`, no relay) and route calldata whose `calldataHash` matches, both fully within the attacker's control.

### Recommendation
Do not compute `swappedAmount` purely from the balance of the `LifiExternalAction`/`ExternalActionSwap` contract when the router call's destination is attacker-supplied. Instead, either (a) validate/force the router calldata to pay out only to `address(this)` (e.g., decode and check the receiver field, or use an adapter that hardcodes the recipient), or (b) require the entire proceeds be pulled via `transferFrom`-style accounting rather than trusting a balance diff after an arbitrary external call whose destination isn't constrained by the protocol.

### Proof of Concept
1. Attacker deposits/holds a shielded UTXO of `inputToken`.
2. Attacker builds a `transact` call with `externalActionData.externalActionId` pointing at `LifiExternalAction`, `erc20TokenAddresses = [inputToken, outputToken]`, `amountChanges[0] = -inputAmount` (normal spend), `onChainCreation[1] = true`, `amountChanges[1] = 0` (per `checkOnchainCreation`).
3. Attacker crafts `externalActionMetadata` for the LI.FI `router` such that the final swap leg's receiver is the attacker's own address (not `address(this)` inside `LifiExternalAction`), and computes `calldataHash` accordingly.
4. Attacker generates a valid ZK proof matching these public inputs (fully self-controlled, no relay needed) and calls `Hinkal.transact`.
5. `_externalTransact` sends `inputAmount` to `LifiExternalAction`; `swap()` calls `callRouter`, which forwards the calldata to `router`; the router swaps and pays the output token directly to the attacker's address.
6. `swappedAmount` measured on `LifiExternalAction` is `0` ⇒ `hinkalFee = 0`; `amountToSendToHinkal = 0`; nothing is transferred back to Hinkal.
7. `Hinkal.transact`'s balance-diff/on-chain-creation equation for `outputToken` is `0 == 0 + 0`, passing without reverting.
8. Attacker walks away holding the full swapped `outputToken` amount in their own wallet, having paid zero protocol/relay fee on the swap.
