Confirmed as a real, exploitable behavior — not a hypothetical.

### Title
`refund_all` sends the entire multi-contributor `NativeDepositOf` hold to whoever calls `terminate`, not to the original depositors - (File: substrate/frame/revive/src/deposit_payment.rs)

### Summary
When a contract's storage deposit has been funded in native currency by multiple distinct accounts (tracked per-contributor in `NativeDepositOf`), calling `terminate`/self-destruct causes `Deposit::refund_all` to release the *entire* native hold to the transaction's signed origin, ignoring each contributor's individual `NativeDepositOf` entitlement. Any unprivileged account that can invoke the contract's public `terminate`/self-destruct entry point (there is no platform-level access control on who may call it) receives other users' storage-deposit-backed native currency.

### Finding Description
`NativeDepositOf<T>` is a double map `(holder, contributor) -> amount` meant to cap how much native currency each specific contributor may reclaim from a contract's hold [1](#0-0) . This cap is correctly enforced in the normal partial-refund path, `refund_on_hold`, which looks up `NativeDepositOf::<T>::get(from, to)` and caps the native refund to that entry [2](#0-1) .

However, at contract termination, `Deposit::refund_all` is used instead, and it explicitly bypasses the per-contributor cap:
- The default `()` backend's `refund_all` simply reads the *total* `balance_on_hold` for the contract and refunds it all to `dst` [3](#0-2) .
- The PGAS backend's `refund_all` does the same for the native portion, then settles PGAS [4](#0-3) .

`do_terminate` in `exec.rs` calls `T::Deposit::refund_all(&contract_account, exec_config.funds(origin.account_id()?))`, where `origin` is the transaction's signed origin (i.e. whoever ultimately triggered the call chain ending in `terminate`) — not the contract-supplied `beneficiary`, and not restricted to any prior contributor [5](#0-4) . The `beneficiary` argument only receives the contract's remaining *free* balance via a separate `Self::transfer` call; the storage-deposit hold goes exclusively to `origin`.

Nothing in the pallet gates who may invoke a contract's `terminate` function — that access control, if any, is entirely up to the contract's own Solidity/PVM logic. A contract such as the test fixture `MultiContributorStorage` exposes `terminate(address beneficiary)` as a public, unrestricted function [6](#0-5) . Any account — including one with zero `NativeDepositOf` entitlement — can call it as the tx origin and, per `refund_all`'s logic, collect the full native storage-deposit hold contributed by every prior depositor.

This is directly confirmed by the pallet's own test and its accompanying comment: *"[`Deposit::refund_all`] bypasses the per-payer [`NativeDepositOf`] cap (one recipient at termination, contract gone), so the full native hold goes to the terminator"* [7](#0-6) . In that test, ALICE and CHARLIE both fund distinct storage slots (each recorded separately in `NativeDepositOf[contract][ALICE]` and `NativeDepositOf[contract][CHARLIE]`), yet when ALICE calls `terminate`, she receives the full combined hold (`alice_entry + charlie_entry`), not just her own share [8](#0-7) . Nothing in that flow requires the terminator to be a contributor at all — ALICE happens to be one in the test, but the mechanism (`dst = origin`, uncapped) applies identically to any caller, contributor or not.

### Impact Explanation
An unprivileged, unrelated account can drain another user's storage-deposit-backed native currency by simply invoking a contract's (unguarded) `terminate`/self-destruct entry point after other users have funded that contract's storage deposit via separate calls. The rightful contributors' `NativeDepositOf` entries are silently zeroed out (or removed by the deletion-queue sweep) with the corresponding native currency routed entirely to the terminating caller instead. This is a direct theft of another user's funds.

### Likelihood Explanation
Preconditions are trivial to satisfy in a real deployment: any contract that (a) accumulates storage deposits from multiple distinct callers over separate transactions in the native-fallback path, and (b) exposes a `terminate`/self-destruct call without contributor-restricted access control, is exploitable by any third party who calls that function. No special privilege, timing, or race condition is required — this is a deterministic, repeatable outcome of the documented `refund_all` semantics.

### Recommendation
At termination, either (a) iterate/settle `NativeDepositOf` per-contributor and refund each contributor their own capped share (splitting the payout across `NativeDepositOf::iter_prefix(contract)` before falling back to distributing any untracked remainder to `origin`), or (b) explicitly document and enforce that pallet-revive's storage-deposit refund model only ever protects "same live contract, partial refund" scenarios and that contract authors bear full responsibility for gating who may terminate — but if theft is in scope, the per-contributor accounting should not be discarded silently at the one point (termination) where multiple contributors' funds are consolidated and handed to a single, potentially unrelated, caller.

### Proof of Concept
Rust integration test (mirrors the existing `refund_all_drains_multi_contributor_native_hold`, but substituting an unrelated terminator instead of a contributor):
1. Instantiate `MultiContributorStorage`.
2. `ALICE` calls `growStorage()` → contributes to `NativeDepositOf[contract][ALICE]`.
3. `CHARLIE` calls `growStorage()` → contributes to `NativeDepositOf[contract][CHARLIE]`.
4. A third, unrelated account `EVE` (never funded any deposit, zero `NativeDepositOf` entry) calls `terminate(beneficiary=DJANGO)`.
5. Assert: `Balances::balance(&EVE)` increases by (approximately) `alice_entry + charlie_entry`, while `NativeDepositOf::<Test>::get(&account_id, &ALICE)` and `NativeDepositOf::<Test>::get(&account_id, &CHARLIE)` are non-zero pre-termination but ALICE's and CHARLIE's actual native balances receive nothing from the termination.
6. This demonstrates the invariant violation: refunded native currency is not distributed to true contributors and is fully captured by an unrelated terminating caller.

	fn refund_on_hold(
		reason: HoldReason,
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> DispatchResult {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let contribution = NativeDepositOf::<T>::get(from, to);
		let native_requested = amount.min(contribution);

		let native_refunded = if !native_requested.is_zero() {
			<() as Deposit<T>>::refund_on_hold(reason, from, dst, native_requested)?;
			let new_val = contribution.saturating_sub(native_requested);
			if new_val.is_zero() {
				NativeDepositOf::<T>::remove(from, to);
			} else {
				NativeDepositOf::<T>::insert(from, to, new_val);
			}
			native_requested
		} else {
			BalanceOf::<T>::zero()
		};

		let pgas_needed = amount.saturating_sub(native_refunded);
		Self::settle_pgas_refund(reason, from, to, pgas_needed)?;
		Ok(())
	}

	/// Refunds the full native hold to `dst` ignoring the per-contributor cap, then settles the
	/// PGAS hold via [`Self::settle_pgas_refund`] (refunding `RefundPercent` to `dst` and burning
	/// the rest). The native cap only makes sense for partial refunds on a live contract; at
	/// termination there is one recipient and the contract is gone.
	///
	/// Note: callers must run inside a storage layer so partial state rolls back on error.
	fn refund_all(
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
	) -> Result<BalanceOf<T>, DispatchError> {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let native = <() as Deposit<T>>::refund_all(from, dst)?;
		let reason = HoldReason::StorageDepositReserve;

		let pgas = Self::pgas_on_hold(reason, from);
		let pgas = Self::settle_pgas_refund(reason, from, to, pgas)?;
		Ok(native.saturating_add(pgas))
	}
