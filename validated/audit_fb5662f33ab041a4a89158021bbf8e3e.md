### Title
Outgoing dispatch on `EvmHost` and `pallet-ismp` accepts requests to arbitrary/unregistered destination chains, permanently locking relayer fees - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)`, the primary permissionless entry points any application or EOA-driven contract uses to send a cross-chain message and pay a relayer fee, perform no validation that `post.dest` / `get.dest` corresponds to a state machine that Hyperbridge actually supports or has a consensus client for. The Substrate-side equivalent, `pallet_ismp::Pallet::dispatch_request` (`modules/pallets/ismp/src/impls.rs`), has the same gap. This mirrors the reported PolygonZkEVMBridge issue where `bridgeAsset`/`bridgeMessage` only checked `destinationNetwork != networkID` but never checked that the destination network actually exists.

### Finding Description
`EvmHost.dispatch(DispatchPost memory post)` collects the relayer fee (native token swapped via Uniswap, or fee-token `safeTransferFrom`), builds a `PostRequest`, and commits it to `_requestCommitments` unconditionally: [1](#0-0) 

There is no check that `post.dest` matches any state machine ID registered in `_hostParams.stateMachines` (the same list used for verifying incoming consensus/state proofs, exercised in `testCanAddwhitelistedStateMachines`), nor that a consensus client for that destination exists anywhere in the protocol. The same absence of a destination-existence check applies to `dispatch(DispatchGet)` right below it.

On the Substrate side, `pallet_ismp::Pallet::dispatch_request` in `modules/pallets/ismp/src/impls.rs` similarly hashes and commits the request with no destination validation: [2](#0-1) 

Contrast this with the *incoming* path, where `HandlerV2.handlePostRequests` explicitly checks that a request's declared `dest` equals `host.host()` before accepting it: [3](#0-2) 

and where `modules/ismp/core/src/handlers/request.rs` checks `req.dest_chain() != host.host_state_machine()`: [4](#0-3) 

So the protocol carefully validates destinations on delivery, but never validates the destination when a message is first dispatched from the source chain. If a user or an unprivileged application contract calls `dispatch()` with an incorrect, decommissioned, or never-configured `dest` (e.g., a `StateMachine.evm(chainId)` for a chain Hyperbridge has no consensus client for), the fee is deducted immediately and the request commitment is recorded, but the request can never be relayed to Hyperbridge/finalized on a destination that no consensus client tracks. It also can never be refunded via `dispatchTimeOut`, because that refund path is only reachable through a valid non-membership/timeout proof relayed and verified via Hyperbridge — which requires the destination (or its host bridging through Hyperbridge) to be known to the protocol in the first place. If `timeout` is 0 (a supported "never expires" mode per the docs), the request/fee is frozen forever with no recovery path at all.

Higher-level apps in this same codebase (`HyperFungibleToken.sol`, `WrappedHyperFungibleToken.sol`, `IntentGatewayV2.sol`) already defend against exactly this class of bug by maintaining an internal `_supportedChains` allowlist and reverting with `UnsupportedChain()` before ever building a `DispatchPost`: [5](#0-4) 
This shows the project is aware of the exact risk described in the report, but the protection is opt-in per-app rather than enforced by `EvmHost`/`pallet-ismp` at the dispatcher level, so any application (or a bespoke/experimental app, or a raw self-relaying integrator calling `IDispatcher.dispatch` directly) that doesn't implement its own destination allowlist is exposed.

### Impact Explanation
Funds (relayer fees, and any value implicitly escrowed by the calling application before dispatch, e.g. burned/locked tokens in a token-bridge app that doesn't itself validate the destination) can be permanently lost/frozen when dispatched to a destination that doesn't exist or isn't supported by Hyperbridge's consensus clients. This is a "permanent freezing of funds" / "route unable to deliver messages" class of impact per the validation criteria — the request/fee is irrecoverable through any refund or timeout mechanism because that mechanism itself depends on the destination being known to Hyperbridge.

### Likelihood Explanation
Medium: this is triggered by a single dispatch call with a malformed/wrong/unsupported `dest` — a mistake any integrator, especially ones building custom apps directly against `IDispatcher` without adopting a `_supportedChains` allowlist (as the SDK's shipped apps do), can make. It requires no malicious actor, just an off-by-one/misconfiguration on the caller's side, similar to the original PolygonZkEVMBridge scenario.

### Recommendation
Add a destination-validity check at the core dispatcher level — `EvmHost.dispatch(DispatchPost)`/`dispatch(DispatchGet)` and `pallet_ismp::Pallet::dispatch_request` — that reverts if `dest` is not present in the host's configured/whitelisted state machines (mirroring the check already used for verifying commitments, e.g. `_hostParams.stateMachines`), so that funds cannot be committed toward an unreachable or non-existent destination.

### Proof of Concept
1. Call `EvmHost.dispatch(DispatchPost({dest: StateMachine.evm(999999999), to: ..., body: ..., timeout: 0, fee: X, payer: msg.sender}))` with a `dest` for which no consensus client is or will ever be configured (see `evm/src/core/EvmHost.sol:921-959`, which contains no destination check).
2. The fee is transferred to the host and `_requestCommitments[commitment]` is set (`evm/src/core/EvmHost.sol:947-948`).
3. Because `timeout == 0`, and because no consensus client for `dest` exists to produce a valid finalization or non-membership proof, neither delivery (`HandlerV2.handlePostRequests` on some other chain) nor `dispatchTimeOut` refund can ever be triggered.
4. The relayer fee (and any value the calling application escrowed prior to dispatch) is permanently stuck.

	/// Dispatch an outgoing request, returns the request commitment
	pub fn dispatch_request(request: Request, meta: FeeMetadata<T>) -> Result<H256, ismp::Error> {
		let commitment = hash_request::<Pallet<T>>(&request);

		if RequestCommitments::<T>::contains_key(commitment) {
			Err(ismp::Error::Custom("Duplicate request".to_string()))?
		}

		let (dest_chain, source_chain, nonce) =
			(request.dest_chain(), request.source_chain(), request.nonce());
		let leaf_index_and_pos = T::OffchainDB::push(Leaf::Request(request));
		// Deposit Event
		Pallet::<T>::deposit_event(Event::Request {
			request_nonce: nonce,
			source_chain,
			dest_chain,
			commitment,
		});

		RequestCommitments::<T>::insert(
			commitment,
			RequestMetadata {
				offchain: LeafIndexAndPos {
					leaf_index: leaf_index_and_pos.index,
					pos: leaf_index_and_pos.position,
				},
				fee: meta,
				claimed: false,
			},
		);

		Ok(commitment)
	}
