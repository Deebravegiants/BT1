### Title
Webhook HMAC validation does not bind the `shop`, `topic`, `webhook-id`, or `api-version` fields, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as the raw request body only, while the shop identity (`shop-domain`), event `topic`, `webhook-id`, and `api-version` are read from HTTP headers that are never included in the signed material. `Utils::HmacValidator` only verifies that the raw body matches the signature computed with the app's shared secret; it never checks that the header-derived fields are consistent with that signature. This breaks the identity binding: `shop`-authenticated (the entity whose HMAC signature is verified) must equal the `shop` that the app's webhook handler is told the event came from — but here they are decoupled.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the body/signature: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the signature over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Webhooks::Registry.process` trusts this validation result, then dispatches based on `request.topic` and forwards `request.shop`, `request.webhook_id`, and `request.api_version` — none of which were actually verified — directly into the app-facing `WebhookMetadata`: [4](#0-3) 

Because the signature only covers the raw body, any request whose body byte-for-byte matches a body Shopify has legitimately signed for the app (e.g., an empty-payload topic, or any topic where the JSON body doesn't itself embed the shop) will pass HMAC validation regardless of what `shop-domain`, `topic`, or `webhook-id` header values are sent alongside it.

### Impact Explanation
This is a cross-tenant identity-binding failure equivalent to the reported bug class: a field acted upon (`shop`, `topic`) is not covered by the authentication mechanism (`HMAC`) that is supposed to bind it. An attacker who operates their own shop with the vulnerable app installed will receive genuine, Shopify-signed webhook deliveries (raw body + valid HMAC) addressed to their own store. Because the signature never encodes which shop or topic it is for, the attacker can replay that same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic` header) for a victim shop/topic of their choosing. `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will hand the forged `shop`/`topic` to the app's `WebhookHandler` as if genuinely originating from Shopify for that shop and topic. Any app logic keyed off `WebhookMetadata#shop` (e.g., uninstall handling, billing state transitions, data sync per shop) can then be triggered against an arbitrary tenant, resulting in cross-tenant access/manipulation.

### Likelihood Explanation
Exploitation requires only that the attacker control a shop that has the app installed (any developer/merchant can do this — no privileged credentials, leaked secrets, or social engineering needed) and be able to capture one legitimate webhook delivery to their own shop for a body-independent or attacker-influenceable topic (many webhook topics, such as `app/uninstalled` or others with static/empty/attacker-controlled bodies, qualify). The replay itself is a simple unauthenticated HTTP POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the value that is HMAC-verified (e.g., concatenate them with the raw body before computing/verifying the signature), or otherwise cryptographically bind these header-derived identity fields to the signed payload so that spoofing any of them invalidates the HMAC.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com` and subscribes to a webhook topic whose body content does not vary per-shop (or is empty), e.g. `{}`.
2. Shopify delivers a legitimate webhook to the app: body `{}` with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: some/topic`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-"{}">`.
3. Attacker captures this `(body, hmac)` pair and replays it directly to the app's webhook endpoint, changing only the headers: `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `"{}"` only, which still matches, so `Registry.process` proceeds: [4](#0-3) 
5. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, believing this is a genuine event for the victim shop, even though Shopify never sent anything about that shop in this request.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
