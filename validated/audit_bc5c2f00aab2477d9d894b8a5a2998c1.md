### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and is validated by `Utils::HmacValidator.validate` before being dispatched to app-supplied handlers. The HMAC is computed and checked only over the raw request body, while the `shop` identity (`X-Shopify-Shop-Domain` header) that is handed to the handler is never part of the signed bytes. This breaks the intended binding "bytes verified == bytes/identity acted on" and lets a holder of one valid, HMAC-signed webhook (from their own, legitimately installed shop) relabel it as belonging to a different merchant, since the app's `api_secret_key` used to compute the HMAC is shared across all shop installations of the app.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads the `shop-domain`/`x-shopify-shop-domain` header directly and is not included anywhere in `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `to_signable_string` and compares it against the `hmac` value taken from the request itself: [3](#0-2) 

`Registry.process` treats a passing `HmacValidator.validate(request)` as proof the whole request — including `request.shop` — is authentic, then forwards `request.shop` unmodified to the app's handler: [4](#0-3) 

That value is placed into `WebhookMetadata#shop`, which the documentation explicitly tells integrators to trust as "The shop domain of the webhook" and to use for business logic such as enqueuing per-shop jobs: [5](#0-4) [6](#0-5) 

The identity binding that is broken, stated as an equality that should hold but doesn't:
`bytes covered by HMAC (raw_body)` ≠ `shop identity handed to the app (shop-domain header)`.

Because Shopify signs webhooks with the app's single `api_secret_key` (the same secret for every shop that installs the app), any attacker who owns a legitimate installation of the target app on their own store can:
1. Trigger any webhook event in their own shop (e.g. `orders/create`) and capture the raw body + valid `X-Shopify-Hmac-Sha256` value Shopify sends them.
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id` if desired) header with a victim shop's domain.
3. `HmacValidator.validate` still passes, because it never inspects the shop-domain header.
4. `Registry.process` calls the handler with `WebhookMetadata.shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's own shop.

If the host application uses `data.shop` from the handler to key per-tenant work (look up the victim's offline session, write into the victim's tenant records, trigger `Registry.register`/`unregister`, enqueue background jobs "for" the victim shop, etc. — precisely the pattern shown in the gem's own documentation example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), the attacker can inject falsely-attributed cross-tenant events, at minimum polluting or corrupting data associated with a shop they do not control, and in apps that use `data.shop` to resolve credentials for privileged action, cause the app to act on the wrong tenant using the attacker's supplied body content.

### Impact Explanation
This qualifies as **High — cross-tenant access**: an attacker with a legitimate installation of the app on their own shop can forge webhook events that the gem certifies as authentic for an arbitrary victim shop domain, because the identity field the gem trusts (`shop`) is disjoint from the bytes actually verified by the HMAC. This is a real boundary crossing between tenants using only capabilities available to any unprivileged merchant who installs the app (no access token, secret, or privileged account required beyond the attacker's own legitimate install).

### Likelihood Explanation
Moderate-to-high likelihood: the attacker only needs a normal installation of the target app (available to any merchant/developer who installs a public app) and the ability to trigger a webhook-eligible action in their own store, then replay the captured request with a modified header — no cryptographic secret, employee access, or privileged account is required.

### Recommendation
Include the shop-domain (and other identity headers like topic/webhook-id, where relevant) in the HMAC-signed content, or independently and cryptographically validate `X-Shopify-Shop-Domain` against a trusted association (e.g. compare it to the shop associated with the specific webhook_id/subscription that was registered) before passing it to `WebhookMetadata`. At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated and must be independently cross-checked by the host app against a known, previously-registered shop before being used for any privileged or tenant-scoped action.

### Proof of Concept
```ruby
# Attacker legitimately installs the target app on their own shop "attacker.myshopify.com"
# and triggers e.g. an "orders/create" event, capturing what Shopify sends:
raw_body = '{"id":1,"note":"hi"}'
hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)
# (In reality this HMAC is computed by Shopify with the app's shared api_secret_key,
#  which the attacker never needs to know — they just capture the header Shopify sent.)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.strict_encode64([hmac].pack("H*")),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # <-- attacker swaps this
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "forged-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# HmacValidator.validate(request) succeeds: it only checks raw_body against hmac,
# never checks shop-domain, so Registry.process happily calls the handler with
# WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled JSON, ...)
ShopifyAPI::Webhooks::Registry.process(request)
```
The handler receives `data.shop == "victim-shop.myshopify.com"` with body content fully controlled by the attacker, despite the event never having originated from that shop.

```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
