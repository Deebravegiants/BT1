### Title
Unbounded `scaled * index` value growth overflows `i128` and permanently freezes all market funds - (File: common/src/rates/index.rs)

### Summary
The lending math stores supply and debt as scaled RAY shares and derives token-denominated totals as `scaled * index`. Every user-facing verb triggers `global_sync`, which accrues interest before touching balances. Once total debt value (`borrowed_scaled * borrow_index`) exceeds `i128::MAX`, accrual panics with `MathOverflow` inside the fixed-point multiply. Because the panic happens *before* the `MAX_BORROW_INDEX_RAY` cap is applied, the overflow is terminal: every subsequent `supply`/`borrow`/`withdraw`/`repay`/`liquidate`/`update_indexes` call re-runs accrual and panics again. The repo's own test harness demonstrates this cliff and confirms all funds become unrecoverable.

### Finding Description
Interest accrual runs chunked, permissionlessly, at the top of every pool operation via `global_sync` in `contracts/pool/src/interest.rs:20-33`, which calls `accrue_step` per chunk (line 40-48). Inside `accrue_step`, `calculate_supplier_rewards` computes `old_total_debt = borrowed.mul(old_index)` and `new_total_debt = borrowed.mul(new_index)` (`common/src/rates/index.rs:80-81`). `Ray::mul` routes to `mul_div_half_up` (`common/src/math/fp_core.rs:108-118`), which panics with `GenericError::MathOverflow` when `scaled * index` does not fit in `i128` — including on the widened i256 path via `.to_i128()`.

The `update_borrow_index` cap at `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:13-19`) only bounds the *index*, not the *value*. The scaled-share total is attacker-influenceable: any user can `supply` and `borrow` up to market caps, and the caps are denominated per-decimals while the RAY scaled totals grow multiplicatively. Once `borrowed_scaled * borrow_index > i128::MAX`, the multiplication panics inside accrual — before the index is ever compared to its cap.

This is a direct analog of the reported bug class: an attacker grows a multiplicand (`scaled shares × index`, analogous to the untrusted chunk length) until an add/multiply overflows and the program panics rather than errors cleanly — except here the panic is sticky and bricks the market instead of a single connection.

### Impact Explanation
Permanent freezing of funds. After the overflow boundary is crossed, `global_sync` panics unconditionally for that market: no withdrawals, repayments, liquidations, or revenue claims can execute, since all of them accrue first. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`) demonstrates exactly this: after ~the index grows past ~170x on a whale-scale market, `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW`, and the test explicitly asserts "the index cap did not engage before the value overflow" and "The market is frozen". All supplied collateral and deposits in that market are locked permanently — there is no administrative path in the accrual flow that skips the panicking multiplication.

### Likelihood Explanation
Medium. Reaching the cliff requires (a) a very large market (the test uses ~1e9 × 1e18 units at 18 decimals on the XLM rate curve) and (b) sustained high utilization over many years so the borrow index compounds ~170x. Caps and oracle bounds constrain how fast a single actor can push scaled totals, but the condition is monotone and irreversible — once debt value approaches `i128::MAX`, ordinary interest compounding on legitimately large markets drives it over the edge without any attacker needing to act at that moment. An attacker can accelerate it by borrowing near-maximum on an uncapped/high-cap market and then simply letting time pass; `update_indexes` is permissionless so anyone can trigger the first fatal accrual. The preconditions are expensive but not impossible, matching the medium severity of the source advisory.

### Recommendation
Bound the *value*, not just the index. Concretely:
- In `calculate_supplier_rewards` and `update_supply_index` (`common/src/rates/index.rs`), compute `borrowed.mul(index)` / `supplied.mul(index)` through a saturating `mul_div` variant (like the existing `mul_div_floor_saturating`) instead of the panicking `mul`, so accrual degrades gracefully near `i128::MAX` rather than bricking.
- Alternatively/additionally, clamp scaled totals at mint/borrow time in `Cache::mint_supply`/`mint_debt` (`contracts/pool/src/cache/shares.rs:15-33`) so `scaled * MAX_*_INDEX_RAY` can never exceed `i128::MAX`, mirroring the headroom cap already used in `protocol_fee_shares` (`common/src/rates/index.rs:94-99`).
- Add a regression test asserting that accrual still succeeds (and markets remain operable) when scaled debt approaches the value ceiling.

### Proof of Concept
The repository already contains a working demonstration; distilled:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))     // steep rate curve
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

// Unprivileged attacker: whale-scale supply + ~98% borrow
t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18));
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98);

// Time passes; anyone calls update_indexes each year
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } // MathOverflow
}

// Market is permanently bricked — every verb accrues first and panics:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),  errors::MATH_OVERFLOW);
```

Root cause chain: `global_sync` → `accrue_chunk` → `accrue_step` → `calculate_supplier_rewards` → `borrowed.mul(index)` → `mul_div_half_up` panics on `i128` overflow before `MAX_BORROW_INDEX_RAY` is ever consulted.
