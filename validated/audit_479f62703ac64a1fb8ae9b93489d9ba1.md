### Title
Unbounded, Uncharged Loop Over Account's Access Keys in `remove_account` Enables Single-Receipt Compute/Gas-Limit Bypass - (File: `core/store/src/utils/mod.rs`)

### Summary
`DeleteAccount` is billed a single fixed base fee (`ActionCosts::delete_account`) regardless of how many access keys or gas-key nonces the target account has. The actual deletion work is performed by `remove_account`, which iterates over every access key and every gas-key nonce belonging to the account in one unbounded loop, all inside a single receipt's execution. Because nearcore only checks the chunk's compute/gas budget *between* receipts (not while a receipt's actions are executing), an account that accumulates a very large number of access keys/gas keys can make a single `DeleteAccount` receipt perform unbounded work for a fixed, non-scaling fee — the same "unbounded list processed by one privileged/critical operation, gas-metered incorrectly" bug class described in the report (there, `liquidateAccount`/`mintOptions` looping over an unbounded `positionIdList`).

### Finding Description
`remove_account` collects and removes *all* access keys and gas-key nonces of an account via unbounded iteration: [1](#0-0) 

This function is invoked from the `DeleteAccount` action handler (`runtime/runtime/src/actions.rs`, which imports `remove_account` from `near_store`): [2](#0-1) 

Yet the gas fee for `DeleteAccount` is a single, size-independent base fee, matching every other simple action: [3](#0-2) [4](#0-3) 

The chunk-level compute/gas budget is only checked *before* starting to process the next receipt in the queue (local, delayed, and incoming receipt loops) — not while a single receipt's actions are being executed: [5](#0-4) [6](#0-5) 

There is no protocol-enforced cap on the number of regular access keys an account may hold (only `MAX_NONCES_FOR_GAS_KEY` bounds nonces *per gas key*, found in `runtime/runtime/src/action_validation.rs` and `core/primitives-core/src/account.rs`) — an attacker can add an arbitrarily large number of `AddKey` actions to their own account over time, each individually and correctly gas-metered at creation time. The asymmetry appears at deletion time: `remove_account`'s per-key removal loop for ordinary access keys is not reflected in any per-key compute charge returned to the caller (unlike the gas-key-nonce removal path in `delete_gas_key`, which does compute `storage_removes_compute` per nonce): [7](#0-6) 

Because `remove_account`'s access-key removal path performs no equivalent per-key compute accounting, and because the compute/gas budget check happens only between receipts, a `DeleteAccount` receipt on an account with a huge access-key set can consume compute/wall-clock time far exceeding what a single fixed-fee receipt is expected to cost, and far exceeding the chunk's `compute_limit`/`gas_limit`, without ever tripping the inter-receipt throttle that would normally defer excess work to delayed receipts.

### Impact Explanation
This is directly analogous to the reported bug class: a critical, unbounded per-account list (access keys) is processed in full within a single state-transition operation whose fee does not scale with the list size. The consequences map to "node panic or unbounded resource use / chain stall": a single `DeleteAccount` receipt could take chunk producers/validators far longer to apply than the chunk's gas/compute budget implies, since the internal budget check is not enforced mid-receipt. This can degrade block/chunk production time for the shard processing that receipt, and it also represents underpriced execution (the attacker pays a fixed ~0.147 Tgas `delete_account` fee for O(N) storage-key removal work, where N can be made arbitrarily large).

### Likelihood Explanation
Building the access-key set requires the attacker to pay individually for every `AddKey` action and to lock storage-staking balance for each key, so there is an economic cost to reach a large N — similar to the "well-collateralized account minting up to ~2000 positions" scenario in the original report. This cost, however, is a one-time, amortizable expense; there is no hard protocol cap preventing an account from growing an arbitrarily large key set over time, after which a single `DeleteAccount` transaction triggers the unbounded, under-metered removal loop.

### Recommendation
Enforce a hard protocol-level maximum number of access keys (and total gas-key nonces) permitted per account, and/or charge `DeleteAccount`/`remove_account` compute costs proportional to the number of access keys and gas-key nonces removed (as is already done for gas-key nonce removal via `storage_removes_compute`), so that the fee reflects the actual per-receipt work and the inter-receipt compute-budget check can meaningfully bound single-receipt execution cost.

### Proof of Concept
Conceptually: (1) an attacker account issues a very large number of `AddKey` transactions to accumulate N access keys (each individually gas-charged and storage-staked); (2) the attacker then submits a single `DeleteAccount` action; (3) `action_delete_account` invokes `remove_account`, which iterates the full unbounded set of access keys/gas-key nonces in one execution while only the fixed `delete_account_cost` fee is charged and no mid-receipt compute-budget check applies — for sufficiently large N this single receipt's real execution time/work can substantially exceed the chunk's intended compute/gas budget.

I was not able to fully confirm within tool-call limits whether any additional, separate protocol-level cap (outside `MAX_NONCES_FOR_GAS_KEY`) restricts the total number of plain (non-gas) access keys per account, or whether a mid-execution abort mechanism exists elsewhere in the codebase that I did not locate; this should be verified with a Devin session that can run the full test suite and trace `action_delete_account`/`remove_account` compute accounting end-to-end.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }
