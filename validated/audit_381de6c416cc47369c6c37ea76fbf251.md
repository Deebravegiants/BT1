## Finding

### Title
Webhook `shop` (and `topic`/`api-version`) identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw body only, while the `shop`, `topic`, and `api-version` values used to route and process the webhook are taken from unauthenticated HTTP headers that are never part of the signed material. Any request bearer that can reuse or forge a body/HMAC pair signed with the app's single `client_secret` can attribute that payload to an arbitrary shop by changing the `X-Shopify-Shop-Domain` header, breaking the binding between the verified payload and the tenant it is dispatched to.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`HmacValidator.validate` verifies exactly that signable string against the app-wide `Context.api_secret_key`: [2](#0-1) 

`Registry.process` only checks this body HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.api_version` — all parsed straight from unauthenticated headers — to build the `WebhookMetadata` dispatched to the app's handler: [3](#0-2) 

And the `shop` accessor itself is read verbatim from the `shop-domain` header with no relation to the signed bytes: [4](#0-3) 

This is a direct analog of the reported bug class: a field that is *acted upon* (`shop`, used by the app to select the tenant/session the webhook data belongs to) is not covered by the integrity check (`HMAC` covers only `@raw_body`). Contrast this with `Auth::Oauth::AuthQuery`, where the equivalent identity field (`shop`) is explicitly included in the signable string alongside `code`, `host`, `state`, and `timestamp`: [5](#0-4) 

Because Shopify's HMAC-SHA256 webhook signature is keyed with the app's single `client_secret` (identical for every shop that has installed the app), a body+HMAC pair that is valid for Shop A's payload remains a byte-for-byte valid signature no matter which shop-domain header accompanies it. An attacker who can capture or replay such a body (e.g., a shop they themselves control sending a webhook to a multi-tenant app, or a payload disclosed/leaked elsewhere) can resubmit that exact body with a forged `X-Shopify-Shop-Domain` header naming a victim shop. `HmacValidator.validate` will report success because it re-derives the HMAC purely from the (unchanged) body, and `Registry.process` will dispatch the payload to the app's handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This breaks the equality that the library is implicitly expected to guarantee: `verified_bytes == bytes_acted_on_for_tenant_attribution`. In a multi-tenant app, the webhook handler typically uses `WebhookMetadata#shop` to look up/activate the corresponding merchant session and write data into that merchant's records. An attacker who owns one installed shop of the app can generate arbitrary, validly-signed webhook bodies for topics they control (e.g., `orders/create`) and then replay them against the app's webhook endpoint while claiming the target is a different merchant shop, causing the app to process attacker-controlled data as if it belonged to another tenant — a cross-tenant integrity/confusion issue that can lead to cross-tenant data injection or corruption depending on how the host app trusts `WebhookMetadata#shop`.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the app's public webhook endpoint with a body the attacker can legitimately obtain a valid HMAC for (e.g., from their own shop's webhook deliveries) and a spoofed `X-Shopify-Shop-Domain` header — no access to the app's `client_secret`, tokens, or TLS interception is needed. This is reachable by any unprivileged internet user who also happens to be a legitimate (even trial) merchant of the target app, which is a low bar for a merchant-facing SaaS app.

### Recommendation
Bind the `shop` (and ideally `topic`/`api-version`/`webhook-id`) values into the material verified by the HMAC, e.g., by having `Request#to_signable_string` incorporate the shop-domain header (mirroring how `AuthQuery` signs `shop`), or by requiring host applications to independently correlate `request.shop` against a shop already known/registered for the delivered `webhook_id`/topic before trusting it for tenant routing. At minimum, document that `request.shop` is unauthenticated and must not be used as the sole tenant identifier without additional verification.

### Proof of Concept
1. App installs the gem on two shops, `shop-a.myshopify.com` and `shop-b.myshopify.com`, both webhooks configured for `orders/create` and sharing the same `Context.api_secret_key` (the app's single client secret, as issued by Shopify for the app, not per-shop).
2. Attacker controls `shop-a.myshopify.com` and triggers an `orders/create` webhook with a chosen body `B`. Shopify signs it: `HMAC = HMAC_SHA256(client_secret, B)`; the attacker intercepts/logs the raw `POST` (headers `X-Shopify-Hmac-Sha256: HMAC`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: orders/create`, body `B`).
3. Attacker resends the same request to the app's webhook endpoint, but rewrites `X-Shopify-Shop-Domain: shop-b.myshopify.com`; body `B` and `HMAC` are unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, per [6](#0-5)  — validation succeeds since only `B` is checked.
5. The registered handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...)` and processes attacker-supplied data as if it originated from `shop-b`, despite `shop-b` never having sent it.
