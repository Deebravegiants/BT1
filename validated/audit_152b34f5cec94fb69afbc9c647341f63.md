### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking `Utils::HmacValidator.validate(request)`, which verifies `OpenSSL::HMAC` over `request.to_signable_string` (the raw body only). The tenant identifier `request.shop`, taken straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, is never part of the signed material, yet it is passed on to the host app's handler as the authoritative shop for that webhook.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Webhooks::Request#shop` simply reads the `shop-domain` header without any cryptographic binding to that body [2](#0-1) . `Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` and then immediately forwards `request.shop` to the handler as the shop identity for the event [3](#0-2) . `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against `verifiable_query.hmac`, i.e. it authenticates `(secret, raw_body)` — never `shop` [4](#0-3) . Critically, the signing secret is `Context.api_secret_key`, a single value shared by the app across *every* installed shop, not a per-shop secret [5](#0-4) .

This is the same class of bug as the CelerIM finding: the field that downstream logic treats as authoritative for tenant/identity binding (`shop`) is not the field that was actually verified (`raw_body` HMAC). The equality the code implicitly assumes — "HMAC-valid request" ⇒ "the `shop` header value is genuinely who sent this payload" — does not hold, because `shop` is disjoint from the signed bytes.

### Impact Explanation
Because the HMAC secret is shared across all shops of a given app installation, any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., by legitimately receiving a webhook for their own installed shop, or via any other channel that produces a valid signature for attacker-influenced JSON) can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Registry.process` will pass HMAC validation (it never inspected `shop`) and will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop [6](#0-5) . Any host application logic keyed off `request.shop`/`WebhookMetadata#shop` (session lookups, data updates, redact/GDPR handling, billing state, etc.) can therefore be triggered under a different tenant's identity — a cross-tenant identity-binding break consistent with the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-chosen headers and a body/HMAC pair that is valid for the shared app secret — no access token, `client_secret`, or privileged account is needed once such a pair is obtained (e.g., from the attacker's own legitimately-received webhook traffic, which is available to any merchant that installs the app). This matches the "unprivileged internet user" threat model: the mismatch between the field validated by the gem (`raw_body`) and the field trusted for identity (`shop` header) is a design property of `Webhooks::Request`/`Registry` in this repository, not a misuse of a documented safeguard by the host app — the gem itself provides no shop binding at any layer.

### Recommendation
Bind the tenant identity into the authenticated material, or require host apps to independently and cryptographically verify `shop` against their own record of installed shops before trusting it (and document this requirement clearly in `Webhooks::Registry.process`). At minimum, `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` should not allow `shop` to be used as an implicit trust anchor when it sits entirely outside the signed payload; the registry should require callers to reconcile `request.shop` against a shop known to have a valid session/access token before invoking the handler.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on shop "attacker.myshopify.com"
# and receives (or otherwise obtains) a valid webhook delivery:
raw_body   = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker resends the exact same body/HMAC to the app's webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (it only checks raw_body),
#    and handler.handle(... shop: "victim-shop.myshopify.com" ...) runs,
#    attributing the payload to a shop the attacker does not own.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
