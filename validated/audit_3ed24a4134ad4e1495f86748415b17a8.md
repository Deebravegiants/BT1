Confirmed root cause: `HmacValidator.validate` computes the HMAC over `Request#to_signable_string`, which returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers and are never included in the signed bytes [2](#0-1) . `Registry.process` only checks `HmacValidator.validate(request)` and then forwards `request.shop` (the unverified header) straight into `WebhookMetadata` used by the app's handler [3](#0-2) . Since Shopify webhook HMACs are computed with the app's single shared `api_secret_key` (or `old_api_secret_key`) rather than a per-shop secret [4](#0-3) , any store that has installed the app can obtain a body+HMAC pair that is valid for the app secret, then replay it with the `shopify-shop-domain` header rewritten to a victim shop domain — `HmacValidator.validate` still returns `true` because it never inspects the shop header.

### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw JSON body, so `HmacValidator.validate` verifies the payload's integrity but never binds it to the `shopify-shop-domain` (or `shopify-topic`/`shopify-webhook-id`) header that `Registry.process` trusts and hands to the app's webhook handler as the identity of the sending tenant.

### Finding Description
The intended binding is: `HMAC-verified(request) == authentic webhook from shop S`. In this gem, the binding actually enforced is `HMAC-verified(raw_body) == signed with app's client secret`, while `shop = header["shopify-shop-domain"]` is asserted independently and never covered by the signature [5](#0-4) . Because Shopify signs webhooks with the app-wide `client_secret` (shared across every shop that installs the app) rather than a per-shop secret, `OpenSSL.secure_compare(computed_signature, received_signature)` in `HmacValidator.validate_signature` succeeds for a body originating from *any* shop that has the app installed [6](#0-5) . `Registry.process` only gates on this HMAC check and then constructs `WebhookMetadata` using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values [3](#0-2) .

### Impact Explanation
An attacker who controls a shop that has installed the target app can capture one legitimately-delivered webhook (valid body + HMAC signed with the app's shared `client_secret`) and resend it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to an arbitrary victim shop domain. Because the header is not part of the signed bytes, the gem reports the forged request as fully authenticated and passes the attacker-chosen `shop` value straight to the host application's handler, which is the qualifying "cross-tenant access" impact: the app will process/store attacker-controlled data under a victim tenant's identity (e.g., triggering `customers/redact`-style flows, corrupting a competitor's records, or causing false `app/uninstalled` state changes) without ever needing the victim's credentials.

### Likelihood Explanation
Requires only that the attacker install the target app on their own (or a disposable) shop — no privileged access, leaked secrets, or social engineering is needed — and standard HTTP tooling to replay the request body with a modified header, which is well within reach of any unprivileged internet user who can create a Shopify dev/partner store.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed string, or independently verify `request.shop` against a per-installation shared secret/expected shop list before trusting it in `Registry.process`, rather than deriving tenant identity solely from an unsigned header.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery (raw body `B`, header `x-shopify-hmac-sha256: H`, computed with the app's shared `client_secret`).
2. Resend the exact same body `B` and HMAC `H` to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)` [7](#0-6) , which passes because it only checks `raw_body` against `H`.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)` [8](#0-7)  and the host app acts on data it believes originated from `victim.myshopify.com`, achieving cross-tenant impact.
