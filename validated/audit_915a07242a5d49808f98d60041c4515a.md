Audit Report

## Title
JWT single-use replay protection has a check-then-act race allowing token reuse - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks `h.jwtCache.isReplay(claims.ID)` at the start and only calls `h.jwtCache.recordUsage(claims.ID)` at the end, after JWT verification and authorized-key lookups complete, with no lock held across the entire sequence. Two concurrent requests carrying the same signed JWT can both observe `isReplay() == false` before either records usage, allowing the same single-use JWT to authorize multiple `WorkflowExecute` dispatches.

## Finding Description
`jwtReplayCache.isReplay` acquires an `RLock`, checks the map, and releases it; `recordUsage` separately acquires a `Lock`, writes, and releases it [1](#0-0) . `Authorize` calls these two methods far apart, with JWT signature verification and the authorized-keys map lookup executed in between [2](#0-1) . Since no single lock spans the "check-then-record" sequence, if two goroutines call `Authorize` concurrently with an identical JWT, both can pass the `isReplay` check before either calls `recordUsage`, both then pass the authorized-key check (since it doesn't depend on jti), and both proceed to be treated as legitimate, distinct authorized requests. This breaks the single-use guarantee that the existing sequential test at `workflow_metadata_handler_test.go:1193-1217` validates only for the non-concurrent case, and is analogous to the correctly-implemented `RequestReplayGuard.CheckAndRecord` pattern used elsewhere in the codebase, which performs check-and-record atomically under one mutex.

## Impact Explanation
This is a genuine, unprivileged-triggerable replay-protection bypass in the gateway's HTTP-trigger authorization path. Any caller in possession of one valid signed JWT (the normal credential for a single trigger request) can, by firing two (or more) concurrent copies of the identical request at the gateway, potentially get the same JWT authorized more than once, causing duplicate/unintended `WorkflowExecute` dispatches to the DON from a single signed request. This maps to an in-scope impact of gateway request impersonation / unauthorized job run via authentication bypass of an anti-replay control, undermining a guarantee the code explicitly implements and tests for.

## Likelihood Explanation
The race window is real but narrow — it spans the interval between the `isReplay` check and the `recordUsage` call, encompassing JWT verification and a map lookup, which are both fast, in-memory, uncontended operations. An attacker fully controls request timing and can send many parallel duplicate requests to increase the odds of winning the race, but because the window is small and CPU-bound (no I/O or lock contention in between under normal conditions), winning it reliably is probabilistic rather than deterministic, and success probability depends heavily on server load, goroutine scheduling, and network jitter. It is nonetheless a legitimate concurrency bug reachable by any unprivileged caller capable of sending duplicate HTTP requests, without requiring any special credential beyond the same JWT they already possess.

## Recommendation
Replace `isReplay`/`recordUsage` with a single atomic `CheckAndRecord(jti string) bool` method that holds one lock across both the lookup and the insertion (check-and-insert), mirroring `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`. Call this method once, immediately after JWT signature verification in `Authorize`, before the authorized-key checks, so that no other goroutine can observe an unrecorded `jti` for the same token between check and record.

## Proof of Concept
Extend the existing sequential test at `workflow_metadata_handler_test.go:1193-1217` ("JWT replay protection") into a concurrent variant: construct one valid signed JWT/request, then launch two goroutines that both call `handler.Authorize(workflowID, tokenString, req)` simultaneously (e.g., synchronized via a start channel/`sync.WaitGroup`), and assert that at most one of the two calls succeeds. To make the race reliably winnable in CI, instrument/slow down the authorized-keys lookup (e.g., inject a small sleep or a mutex-heavy authorized-keys map) between the `isReplay` check and `recordUsage` to widen the window, then verify both goroutines return `nil` error, demonstrating the bypass.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
