### Title
`placeOrder()` predispatch escrow uses raw post-swap dispatcher balance instead of balance delta - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder()`, the predispatch escrow-measurement step checks the CallDispatcher's *total* token/native balance after executing the user-supplied predispatch calldata, rather than the *delta* produced by that calldata. This is the exact bug class described in the external report: a balance check that can be satisfied by funds already present in the target contract, rather than funds actually produced by the swap/call being validated.

### Finding Description
`placeOrder()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` handles predispatch swap-then-escrow orders as follows: [1](#0-0) 

After the (attacker-controlled, order-creator-supplied) predispatch call executes, the contract measures the dispatcher's balance and treats anything above `requiredAmount` as dust, then credits the escrow with the *declared* `reducedInputs[i].amount` rather than any measured delta: [2](#0-1) 

Critically, there is no `balancesBefore` snapshot taken prior to `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`. The check `if (balance < requiredAmount) revert InvalidInput();` (and the native-token equivalent `InsufficientNativeToken`) only validates the *absolute* post-call balance of the shared `dispatcher` contract — it cannot distinguish tokens actually produced by the predispatch swap from tokens that were already sitting in the dispatcher for any other reason (e.g., unflushed/leftover balance from another interaction executing in the same transaction, or funds sent to the dispatcher by a third party). This is structurally identical to the reported `swapOn1INCH()` flaw: checking `IERC20(_assetOut).balanceOf(address(this)) >= _minAmountOut` without subtracting the pre-swap balance.

This is a real regression relative to the mainline EVM contract, `evm/src/apps/IntentGatewayV2.sol`, which was hardened to snapshot `balancesBefore[i]` immediately before the sweep and compute `received = balanceAfter - balancesBefore[i]`, using that measured delta (not the caller-declared amount) to set the escrowed `order.inputs[i].amount`: [3](#0-2) 

The Tron contract never adopted this fix and additionally escrows the caller-declared `reducedInputs[i].amount` (derived directly from `order.inputs[i].amount`, the value the order creator supplies) rather than any value actually measured from the swap: [4](#0-3) 

Because the dispatcher (`_params.dispatcher`) is a single shared `CallDispatcher` instance used to execute both predispatch and postdispatch calls for every order across the gateway, any residual token/native balance left behind by one flow (e.g., a postdispatch fill's leftover funds, or a predispatch call that does not fully drain what it transferred in) becomes fungible with a subsequent (even attacker-crafted) predispatch balance check within the same transaction or block. An order creator can supply `predispatch.assets` amounts far smaller than `order.inputs[i].amount`, and a `predispatch.call` that performs a trivial or degenerate action, then rely on unrelated balance already resident in the dispatcher (topped up via the arbitrary predispatch calldata itself, front-run token transfers, or leftover flows) to satisfy `balance >= requiredAmount`, causing the gateway to escrow (and later pay out to a solver / cross-chain destination) `reducedInputs[i].amount` of value that was never actually backed by the user's real input, while any "surplus" gets misclassified and drained to the gateway as "dust" without ever having been legitimately produced by that order's swap.

### Impact Explanation
This allows an order creator to forge/inflate the token amount escrowed for their own order without providing the funds through the predispatch swap, because the escrow check is a raw balance check on a shared contract rather than a delta-based check anchored to that specific call's output. Escrowed tokens back cross-chain settlement obligations (`RedeemEscrow`/withdraw flows) and are paid out to solvers who fill orders on the destination chain, so an inflated/forged escrow can result in unbacked value being paid out to solvers or withdrawn from the protocol — a direct theft/fund-freezing risk reachable from a single, unprivileged `placeOrder()` transaction. This satisfies the "concrete theft ... unauthorized app action" bar since escrow accounting for an intents-based token bridge is being falsified.

### Likelihood Explanation
Likelihood is Low-to-Medium: exploitation requires the attacker to control the predispatch calldata (which they do, as the order creator) and to arrange for the shared `CallDispatcher` to hold balance not actually sourced from their own predispatch assets at the moment of the check (e.g., by crafting the predispatch call itself to pull in extra funds, or by a timing/ordering quirk in the same or a preceding transaction leaving dust). It does not require any privileged role, consensus compromise, or malicious relayer/collator — only a normal `placeOrder()` call, matching the required "single submitted transaction" reachability bar.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot the dispatcher's (and/or gateway's) balance for each input token *before* dispatching the predispatch calldata, and after dispatching, compute the actually-received amount as `balanceAfter - balanceBefore`. Use this measured delta — not the caller-declared `order.inputs[i].amount`/`reducedInputs[i].amount` — to determine both the dust to sweep and the amount credited to escrow (`_orders[commitment][token]`), exactly analogous to the recommended `swapOn1INCH()` fix of snapshotting `balBefore`/`balAfter` around the swap call.

### Proof of Concept
Conceptual PoC (delta vs. absolute-balance divergence):
1. Attacker calls `placeOrder()` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: X, amount: 1000}` and `predispatch.assets = [{token: X, amount: 1}]` (i.e., only 1 unit actually funded via the normal transfer path).
2. `predispatch.call` is crafted so that, as part of its execution inside `CallDispatcher.dispatch(...)`, it causes token `X`'s balance at `dispatcher` to reach ≥1000 by means unrelated to a genuine 1:1000 swap output (e.g., calling back into a path that leaves residual balance from a different, legitimately-escrowed flow executing in the same call graph, or exploiting any other caller-supplied sequence that inflates `dispatcher`'s balance of `X` beyond what the attacker actually contributed).
3. The check at `evm/tron/contracts/apps/IntentGatewayV2.sol:428-429` (`balance = IERC20(token).balanceOf(dispatcher); if (balance < requiredAmount) revert InvalidInput();`) passes because it only inspects the absolute balance, not the delta attributable to this specific predispatch call.
4. `_orders[commitment][token] += reducedInputs[0].amount` (line 441) credits escrow for the full declared 1000 units, even though the attacker only ever contributed 1 unit through the accounted transfer path — an unbacked escrow entry is created, which can later be redeemed cross-chain via the `RedeemEscrow`/withdraw flow.

Because exact reproduction depends on the specific sequences that can leave/inflate balance in the shared `CallDispatcher` (e.g., interaction with concurrent postdispatch sweeps or attacker-crafted predispatch calldata targets), a definitive step-by-step exploit transaction could not be fully constructed from static analysis alone; the root-cause code divergence from the hardened mainline contract (absolute balance check vs. before/after delta check) is nonetheless clearly and concretely established above.
