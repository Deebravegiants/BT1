Audit Report

## Title
Legacy WebAPI Trigger Handler Overwrites In-Flight Callback on Duplicate MessageID, Causing Cross-Requester Response Hijack/DoS - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` stores a pending callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageID`, with no existence check before overwriting an in-flight entry. Since `MessageID` is fully attacker-controlled and unvalidated for uniqueness, a second in-flight request using the same `MessageID` silently replaces the first request's callback, causing the original requester to hang and the response to be routed to the wrong caller.

## Finding Description
The relevant code is: [1](#0-0)  which unconditionally overwrites `h.savedCallbacks[msg.Body.MessageID]` without checking `if _, found := h.savedCallbacks[msg.Body.MessageID]; found`. `MessageID` originates from the client-controlled `MessageBody` struct [2](#0-1) , and `Message.Validate()` only checks length/format constraints, never uniqueness or per-sender scoping [3](#0-2) . This path is reached via the gateway's unauthenticated legacy request dispatch in `gateway.go`, which calls `h.HandleLegacyUserMessage(ctx, msg, callback)` for any decoded legacy message with a valid signature/DON ID [4](#0-3) .

When a node later responds, `handleWebAPITriggerMessage` looks up and deletes the map entry by `MessageID` and forwards the response to whatever callback currently occupies that slot: [5](#0-4) . If a second request overwrote the slot before the first node response arrived, the original caller's callback is silently dropped and its HTTP connection hangs, while the response is delivered to the second (potentially attacker) caller.

By contrast, the newer v2 HTTP trigger handler explicitly guards against this exact class of bug by rejecting requests with an already in-flight `requestID`: [6](#0-5) . The absence of an equivalent check in the legacy path, combined with the maintainers' own `// TODO: apply allowlist and rate-limiting here` comment at the top of this handler function [7](#0-6) , confirms this is a genuine, unaddressed gap rather than intentional design. Searching the codebase confirms there is no other deduplication or uniqueness check applied to `MessageID` prior to the map write, and `gateway.go` performs no such check either.

## Impact Explanation
An unprivileged, unauthenticated caller of the gateway's legacy `web_api_trigger` endpoint can cause denial of service for another concurrent legacy request that happens to share the same `MessageID` — that request's callback is silently evicted and its HTTP client never receives a response (it will hang until any client-side timeout). In the case where the response for the original request instead becomes deliverable through the replacing callback's slot, this results in cross-requester response confusion, which is an accepted impact category. The severity is bounded: it is confined to the legacy WebAPI trigger surface, requires guessing/colliding another in-flight request's `MessageID`, and does not enable fund movement or authentication bypass directly.

## Likelihood Explanation
Exploitation only requires the ability to send a `web_api_trigger` legacy message to the gateway — no privileged role is needed, matching the "unprivileged actor" requirement. The attacker needs to know or predict another in-flight request's `MessageID` and time the collision within the round-trip window to the DON nodes, which bounds but does not eliminate feasibility; an attacker racing their own duplicate submissions can trivially self-trigger the DoS condition, and the map's `defaultCallbackMaxAgeSec = 120` window provides ample time for exploitation attempts.

## Recommendation
Add a conflict check identical in spirit to the v2 handler's `setupCallback`: before inserting into `h.savedCallbacks`, check if `msg.Body.MessageID` already exists, and if so, reject the new request with an appropriate error rather than silently overwriting. Additionally, consider scoping the map key by `(Sender, MessageID)` so that unrelated senders cannot collide with each other's identifiers at all.

## Proof of Concept
1. Send two `HandleLegacyUserMessage`-routed gateway requests (each independently signed/valid) with identical `MessageID = M` but different senders, request A first then request B before A's DON round-trip completes.
2. Request A stores `savedCallbacks[M] = callbackA`; request B overwrites `savedCallbacks[M] = callbackB` per [1](#0-0) .
3. When a node responds with `MessageID = M`, `handleWebAPITriggerMessage` retrieves and deletes `savedCallbacks[M]`, finding `callbackB`, and delivers the response to caller B while caller A's connection hangs until timeout/prune, per [5](#0-4) . A Go unit test can construct two `HandleLegacyUserMessage` calls with the same `MessageID` and assert that only one callback remains in `h.savedCallbacks` and that the first callback is never invoked.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
