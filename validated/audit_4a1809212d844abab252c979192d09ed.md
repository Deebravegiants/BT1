### Title
Overpaid native ETH sent to `EvmHost.dispatch()` for POST/GET fee payment is permanently captured by the host instead of being refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value` as an alternative fee-payment path, forwarding the entire `msg.value` into a Uniswap V2 `swapETHForExactTokens` call that only needs to spend enough ETH to buy exactly `post.fee` / `get.fee` fee-tokens. Any ETH sent in excess of what the swap actually consumes is refunded by the Uniswap router to its immediate caller, which is `EvmHost` itself, not the original transaction sender who called `dispatch()`. This mirrors the referenced bug class: a caller who overestimates or mis-supplies `msg.value` for a fee payment permanently loses the surplus, because the contract has no logic to return unused value to the original payer.

### Finding Description
`dispatch(DispatchPost)` at [1](#0-0)  and `dispatch(DispatchGet)` at [2](#0-1)  both do:

```solidity
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```

The entire `msg.value` is forwarded to the router as the transaction value, but `swapETHForExactTokens` only needs to spend the exact ETH amount required to receive `post.fee` tokens; standard UniswapV2Router02 semantics refund any leftover ETH to `msg.sender` of that call. In this call chain, `msg.sender` from the router's perspective is `EvmHost`, not the account that originally called `dispatch()`. There is no code path here (nor visible sweep/refund-to-caller logic in this function) that returns the unused native token back to the original caller — the surplus becomes native balance sitting in `EvmHost`, effectively lost to the depositor.

This is structurally the same root cause as the referenced Infinity Exchange bug: a function accepts `msg.value` as payment without strictly validating/refunding the exact amount consumed, so any user-supplied ETH beyond what's actually used is not returned to its owner.

The related pattern also appears in the token-bridge `send()` implementations, where a mis-attached `msg.value` (e.g., when `_isWeth` is false / underlying is a plain ERC20, or when it's insufficient to fully wrap) is not rejected but silently swept into the same `dispatch{value: msgValue}` fee path: [3](#0-2) . This funnels the same excess-ETH-loss issue through the bridging entry point into `EvmHost.dispatch`.

### Impact Explanation
Any unprivileged caller (a normal user, or an app forwarding `msg.value` on behalf of a user, e.g. `WrappedHyperFungibleToken.send`) who supplies more native ETH than is strictly required to purchase `post.fee`/`get.fee` worth of fee-tokens will have the difference silently retained inside `EvmHost`'s balance rather than refunded. Because the swap's exact-input amount depends on live pool pricing (a value the caller cannot compute atomically on-chain before the tx executes, especially under slippage/price movement between quoting and execution), overpayment is a realistic and recurring outcome, not just a one-off mistake — this constitutes a permanent, protocol-level freeze/loss of user funds each time it happens. This satisfies the Medium-severity bar of "permanent freezing of funds" reachable directly from a single dispatched request.

### Likelihood Explanation
Likelihood is high: `dispatch()` is the primary externally-reachable entry point for posting/getting cross-chain messages and is exercised on every message dispatch that opts to pay fees in native token (the documented "pay with native token" path). Since the exact ETH cost of the swap can only be known after execution (AMM pricing), any caller providing a safety margin above their quoted estimate will trigger this loss on essentially every call using the native-fee path.

### Recommendation
After the swap, compute the actual ETH spent (e.g., via the Uniswap Router's returned `amounts[0]`, or by measuring `address(this).balance` deltas) and refund any leftover `msg.value` back to `_msgSender()` (the original caller) rather than leaving it captured in `EvmHost`. Alternatively, require callers to pre-compute the exact input via `getAmountsIn`/a quote function and enforce `msg.value == requiredAmountIn`, reverting otherwise, so no excess ETH is ever transferred into the contract.

### Proof of Concept
1. A user (or `WrappedHyperFungibleToken.send`) calls `EvmHost.dispatch(post)` with `msg.value = X`, intending to pay the `post.fee` fee-token cost via native-token swap.
2. `EvmHost.dispatch` calls `swapETHForExactTokens{value: X}(post.fee, path, address(this), deadline)` on the configured Uniswap V2 router, per [1](#0-0) .
3. The router only consumes `amountIn < X` ETH to purchase exactly `post.fee` fee tokens, and refunds `X - amountIn` to its caller, `EvmHost`.
4. `EvmHost.dispatch` has no logic to forward this refunded ETH back to the original `msg.sender`; the surplus becomes stranded in the host contract's balance, permanently unavailable to the user who sent it.
