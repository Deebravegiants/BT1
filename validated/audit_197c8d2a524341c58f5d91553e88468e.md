## Title
Denial of Service via Reachable Division-by-Zero Panic in `Calculator::calc_x_power` — (File: `program/src/math.rs`)

## Summary
`Calculator::calc_x_power` performs `checked_div(current_y).unwrap()`, which panics (Rust `unwrap()` on `None`) if the divisor `current_y` is zero. This function is invoked from `Processor::calc_take_pnl` in `program/src/processor.rs` with `current_y = y1`, a value derived from the pool's live coin-vault balance normalized by `Calculator::normalize_decimal_v2`. `calc_take_pnl` is reachable from `WithdrawPnl`, `Withdraw`, `SwapBaseIn`/`SwapBaseInV2`, and `SwapBaseOut`/`SwapBaseOutV2` — all instructions callable by unprivileged swappers/LPs with a single transaction.

## Finding Description [1](#0-0) 

```
pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
    let x_power = last_x
        .checked_mul(last_y).unwrap()
        .checked_mul(current_x).unwrap()
        .checked_div(current_y).unwrap();
    x_power
}
```

`checked_div` returns `None` on division by zero, and the trailing `.unwrap()` converts that into an unconditional panic instead of a graceful `ProgramError`. This mirrors the CocoaMQTT root cause: a length/quantity field that legitimately evaluates to `0` is fed, unchecked, into an operation (`ClosedRange` construction there, `checked_div` here) whose preconditions are violated only at the zero boundary, producing a reachable assertion/trap rather than a handled error path.

`y1` is `Calculator::normalize_decimal_v2(total_coin_without_take_pnl, ...)`, i.e. a decimal-scaled representation of the amm's live coin balance net of accrued PnL: [3](#0-2) 

Because `total_coin_without_take_pnl` (and therefore `y1`) is derived directly from `amm_coin_vault.amount` (attacker-observable and, over successive swaps/withdrawals, attacker-drivable toward the `need_take_pnl_coin` floor), an unprivileged actor who repeatedly swaps/withdraws coin tokens out of the pool can force `total_coin_without_take_pnl` — and hence `y1` — down to `0`. The outer guard condition in `calc_take_pnl` (`pool_pc*pool_coin >= calc_pc*calc_coin`) does not prevent entry into the `calc_x_power` branch when both sides are `0` (e.g., in a freshly initialized pool where `target.calc_pnl_x`/`calc_pnl_y` are still `0`, or after PnL has already been fully harvested to `0`), so `0 >= 0` is true and `calc_x_power(0, 0, x1, 0)` executes `checked_div(0).unwrap()`, panicking.

`calc_take_pnl` is reached from every state-mutating trading/withdrawal path: [4](#0-3) [5](#0-4) 

## Impact Explanation
A panic inside a Solana on-chain program aborts the currently executing transaction; the Solana runtime rolls back all state changes made within that transaction, so a single panicking call does not by itself corrupt persisted state. However, because the zero-coin-balance condition is a function of the pool's *persisted* vault balance (not of the calling transaction's own inputs), once the pool's coin balance is driven to the vulnerable boundary, **every subsequent transaction that reaches `calc_take_pnl`** (i.e., `WithdrawPnl`, `Withdraw`, and both swap variants when routed through this pnl-accounting path) will deterministically panic and revert. This effectively freezes LP withdrawals, swaps, and pool-owner PnL collection on that pool — a persistent denial of service against user and LP funds that can only be resolved by external intervention (e.g., someone re-funding the coin vault above the threshold), directly analogous to the "bricking until manual intervention" impact described in the CocoaMQTT advisory.

## Likelihood Explanation
Reaching the vulnerable state requires an unprivileged party to perform a sequence of ordinary swap/withdraw calls that drain the coin vault down to (or keep it at) the `need_take_pnl_coin` floor, and/or exploit the freshly-initialized-pool state where `target.calc_pnl_x == target.calc_pnl_y == 0`. This does not require any privileged signer, leaked key, or malicious validator — only attacker-chosen instruction data/accounts within normal instruction flows (`Deposit`/`Withdraw`/`SwapBaseIn`/`SwapBaseOut`), consistent with the in-scope reachable surface.

## Recommendation
Replace the `.unwrap()` in `Calculator::calc_x_power`'s `checked_div` call with a proper error propagation (`.ok_or(AmmError::CalculationExRateFailure)?` or equivalent), and guard `calc_take_pnl`'s branch so it does not attempt the power calculation when `current_y` (`y1`) is zero, returning a handled `AmmError` instead of panicking.

## Proof of Concept
1. Attacker (or pool creator) initializes a pool via `Initialize2`, leaving `TargetOrders.calc_pnl_x`/`calc_pnl_y` at their default `0` value.
2. Attacker issues a sequence of `SwapBaseIn`/`SwapBaseOut`/`Withdraw` instructions that drain `amm_coin_vault.amount` down to equal `amm.state_data.need_take_pnl_coin` (achievable because these are ordinary, unprivileged, attacker-parameterized instructions), making `total_coin_without_take_pnl == 0` and therefore `y1 == 0`.
3. Attacker (or any user) then calls `WithdrawPnl` (or any subsequent `Withdraw`/`Swap*`), which invokes `Processor::calc_take_pnl` → `Calculator::calc_x_power(target.calc_pnl_x.into(), target.calc_pnl_y.into(), x1, 0)`.
4. `checked_div(U256::zero()).unwrap()` returns `None.unwrap()`, panicking and aborting the transaction; every future call that reaches this code path with the pool in this state will panic identically, freezing further pnl withdrawal/trading on the pool until the coin balance is externally restored.
