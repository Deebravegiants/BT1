### Title
Webhook `shop` domain is not covered by the HMAC signature that `Registry.process` uses to assert authenticity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler. In reality, the cryptographic check only covers the raw request body; the `shop` domain that is handed to the handler (and that host apps use to select which tenant's data to mutate) is read from an HTTP header that is never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is parsed independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, outside the signed material: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The library's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify," and its canonical example forwards `data.shop` directly for shop-scoped side effects (`shop_domain: data.shop`): [4](#0-3) [5](#0-4) 

The binding that should hold is: `hmac_verified_bytes == bytes_that_determine_tenant_identity`. Here it is `hmac_verified_bytes (raw_body) != identity_field_used (shop header)`. Any principal who can obtain one validly-signed webhook body/HMAC pair for a topic (e.g. an attacker who installs the app on their own store and receives a legitimately-signed webhook from Shopify) can resubmit that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header for a different merchant. `Utils::HmacValidator.validate` will report success because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop, even though that shop never sent or authorized this event.

### Impact Explanation
This breaks a tenant-identity boundary: the attacker (a legitimate but unprivileged app-installer for their own store) can cause the host application - acting exactly as this gem's documentation instructs - to process a payload attributed to an arbitrary other merchant's shop domain. Depending on how the host app uses `data.shop` (e.g., looking up that shop's stored session/access token to react to the "verified" event, or writing/deleting records keyed by shop), this enables cross-tenant data confusion/injection without ever touching the victim shop's own credentials.

### Likelihood Explanation
Exploitation requires only: (1) install the target app on an attacker-controlled store to receive at least one genuinely Shopify-signed webhook of a topic the app processes, and (2) replay that body/HMAC to the app's public webhook endpoint with a modified shop-domain header. No secrets, tokens, or privileged access are required beyond ordinary use of the app as any merchant — this is reachable by any unprivileged internet user who can install the app.

### Recommendation
Bind the shop identity into what is verified: either include the shop domain (and ideally topic/webhook-id) as part of the value validated against a per-request-scoped secret, or require host apps to cross-check `request.shop` against an already-known, previously-registered shop record before trusting it, and document this requirement explicitly rather than stating that `process` alone confirms provenance of the whole request (including the shop field).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app registers a webhook (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays a POST to the app's webhook endpoint reusing body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `H` against `B` — this passes.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes `B` as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
