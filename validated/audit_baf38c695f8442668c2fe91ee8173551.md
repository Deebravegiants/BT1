Found the identity binding gap: `Webhooks::Request#shop` (the tenant identity) is taken directly from the `X-Shopify-Shop-Domain` header, but the HMAC signature (`to_signable_string`) only ever covers `@raw_body` — the shop-domain header is never part of the signed bytes. [1](#0-0) 

### Title
Webhook `shop` identity is read from an unauthenticated header not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor derived from the `X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` HTTP header [2](#0-1) , while `HmacValidator.validate` only verifies the raw request body against the `hmac-sha256` header [3](#0-2) [4](#0-3) . The equality the binding is supposed to enforce is: `hmac_verified_bytes == bytes_that_determine_tenant`. Here that equality does not hold — `to_signable_string` returns only `@raw_body`, so the `shop` header used by the host application to select which tenant's session/data the webhook applies to is never authenticated by the signature.

### Finding Description
`Request#initialize` requires the presence of the `shopify-shop-domain`/`x-shopify-shop-domain` header but performs no cryptographic binding of that header to the signed payload [5](#0-4) . The signature check via `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` accessor [6](#0-5) , and for `Request`, `to_signable_string` is simply `@raw_body` [3](#0-2) . This means an attacker who can replay a *validly-signed* webhook body from their own (legitimately-owned) shop can freely swap in an arbitrary `X-Shopify-Shop-Domain` header value pointing at a victim shop, and the gem will report the request as HMAC-valid (`shop` accessor returns the attacker-chosen victim domain) since the body/signature pair is untouched and the shop header carries no cryptographic weight.

### Impact Explanation
Any application that trusts `Request#shop` returned by this gem as the tenant identifier for routing, session lookup, or data attribution (which is exactly the documented purpose of this accessor, per `docs/usage/webhooks.md`'s intended usage of `shop`, `topic`, `body`) can be tricked into processing a webhook under the wrong shop's identity — i.e., cross-tenant confusion, because the gem asserts the payload is verified ("HMAC valid") while the shop attribution is not part of what was verified. This matches the report's bug class: a field (`shop`) acted upon by the consumer but not covered by the HMAC.

### Likelihood Explanation
The attacker needs a validly-signed webhook body/HMAC pair, which they can obtain by owning any Shopify development store or trial shop that installs the target app (or by triggering any real webhook to their own shop), then replaying that exact body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No access token, `client_secret`, or privileged account is required — only network access to the app's public webhook endpoint and control of a body/HMAC pair from any shop, which is attacker-obtainable without credentials belonging to the victim.

### Recommendation
Include the shop-domain header (and ideally `webhook-id`/`api-version`) in the signable string, or otherwise cryptographically bind `shop` to the verified payload before exposing it via `Request#shop`, so that `HmacValidator.validate` failing/succeeding is coupled to shop attribution, not merely body integrity.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` triggers a real webhook; the app receives `raw_body` B and a valid `X-Shopify-Hmac-Sha256: H` computed over B with the app's secret.
2. Attacker replays this exact `raw_body`/HMAC pair to the same webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H})` is constructed; `HmacValidator.validate(request)` returns `true` because `to_signable_string` (`@raw_body`) and `hmac` still match [7](#0-6) [8](#0-7) .
4. The host application, trusting the gem's HMAC validation, calls `request.shop` and gets `"victim.myshopify.com"` [2](#0-1) , causing it to process the attacker's payload as if it belonged to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          received_signature = verifiable_query.hmac
