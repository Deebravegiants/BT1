### Title
Attacker-supplied route executes arbitrary contract under the caller's signed auth tree, draining wallet tokens unrelated to the swap - (File: tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs)

### Summary
Directory traversal resolves attacker-controlled path components outside the intended root. The analog here is the strategy router's caller-controlled "path": the swap payload names the venue (`hop_pool`) and tokens the router invokes, and no allowlist constrains them. A hop contract on that route can issue `token.transfer(victim, attacker, amount)` for any token the victim holds; the Soroban host records that transfer as a child of the victim's signed `swap_collateral`/`swap_debt`/`multiply`/`repay_debt_with_collateral`/`execute_strategy` authorization entry, so it executes even though the victim only intended to authorize the swap's single input pull.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:36-38` calls `router.execute_strategy(&controller, &amount_in, swap)` with fully caller-supplied route bytes. The router performs only measured input/output accounting and keeps no venue allowlist; per `skills/xoxno-swap-aggregator/payload.md` and the threat model (`docs/explanation/threat-model.md:154-165`), "the router calls the pool and token addresses its payload names." A malicious route can therefore place arbitrary attacker-deployed code on the call stack below the caller's authorization.

The test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` proves the mechanism end to end: `RogueHopPool::swap` calls `token::Client::transfer(&victim, &attacker, &amount)` on a wallet token the protocol never listed, and recording mode attaches that transfer as a `sub_invocation` of Alice's `swap_collateral` auth entry. The whole account collateral flow proceeds normally (Alice receives fair `ETH` output, so `verify_router_output` and the final health check pass), while `WALLET_BALANCE` of an unrelated token moves from Alice to the attacker.

### Impact Explanation
Theft of user funds beyond the routed amount. Neither the payload `min_out` nor the controller's output/balance-delta checks bound the loss: the stolen transfer is a sibling authorization, invisible to `in_after`/`out_before` measurements and the post-call risk gates. Any token the signer holds (not just collateral assets) can be drained in one signed swap.

### Likelihood Explanation
A single unprivileged attacker needs only to get a victim to submit a swap transaction carrying the crafted `routeXdr` — a realistic condition, since the route bytes are produced off-chain and users sign whatever simulation attaches. Simulation itself records the malicious child under the caller's entry (test lines 199-222), so the poisoned tree is indistinguishable in standard flows unless the client decodes the route and rejects unexpected children, which the threat model explicitly leaves to the client.

### Recommendation
Constrain the route on-chain rather than trusting payload bytes: the router should enforce a governance-controlled venue/pool allowlist (or at minimum restrict invoked pool/token addresses to the `assets` vector declared in the program), so that no contract outside the declared path runs below the caller's auth. Additionally, document and enforce at the SDK/client level that the signed auth tree for a swap must contain exactly one child (the `token_in` transfer), and reject any tree with extra sub-invocations before submission.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

```rust
// Attacker-deployed "pool": steals any victim token during the hop
pub fn swap(env: Env) {
    let (victim, wallet_token, to, amount): (Address, Address, Address, i128) = ...;
    if amount > 0 {
        token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
    }
}
```

`route_through_pool_stealing(WALLET_BALANCE)` embeds this contract as `hop_pool`; the router invokes it via `env.invoke_contract(&route.hop_pool, "swap", ...)` after pulling `token_in`. Alice's `swap_collateral` succeeds with fair output, but:

```rust
assert_eq!(recorded, vec![(alice, poisoned_root)]); // stolen transfer is a child of her auth entry
assert_eq!(s.wallet(&s.alice), 0);
assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
```

Reproduction: attacker crafts `routeXdr` naming `RogueHopPool`; victim calls `controller.swap_collateral(caller, account_id, usdc_key, amount, eth_key, route)` and signs the simulated tree; the rogue pool's `token.transfer(victim, attacker, victim_balance)` executes under her signature while the swap itself completes normally.
