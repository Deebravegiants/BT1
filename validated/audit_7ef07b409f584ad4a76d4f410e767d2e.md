Based on extensive searching of consensus, proof-verification, and message-decoding paths across this codebase, I found that this class of bug (buffer/index overflow triggered by an unprivileged relayer-supplied packet) has already been the subject of deliberate, well-documented hardening in nearly every location I could find. Rather than a novel unpatched instance of the CVE-2020-26422 bug class, what stands out is a genuine, still-open analog in the intents app's incoming-message dispatch.

### Title
Empty/short `PostRequest.body` causes an out-of-bounds revert in `onAccept`, letting any counterparty dispatch DoS message delivery - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept` and its Tron counterpart `IntentGatewayV2.onAccept` unconditionally read `incoming.request.body[0]` to determine the `RequestKind` before performing any length check or source authentication: [1](#0-0) [2](#0-1) 

If `body.length == 0`, this Solidity indexing operation reverts with a `Panic(0x32)` (array out-of-bounds) — the EVM analog of the Wireshark dissector's buffer overflow on a malformed/short packet: an attacker-controlled, badly-formed message causes an unconditional out-of-bounds access before any validation of its origin.

### Finding Description
`onAccept` is the entrypoint the ISMP host invokes when delivering a verified cross-chain `PostRequest` addressed to this contract (`to == address(this)`). The `RequestKind kind = RequestKind(uint8(incoming.request.body[0]));` line executes before the `_authenticate`/`source == hyperbridge` checks that gate the rest of the function, so it runs for every inbound message regardless of who dispatched it. Any account able to get a `PostRequest` with `to` set to this gateway's address and an empty `body` accepted and proven on the source chain (e.g., by directly calling the source `EvmHost`'s dispatch function, which is permissionless) can produce a message that a relayer will faithfully deliver with a valid membership/consensus proof, yet which reverts in `onAccept` purely due to the zero-length body.

This mirrors the CVE's root cause exactly: a length/bounds check that is missing on the very first field read out of untrusted, relayer-supplied data (SP1/BEEFY/GRANDPA/Tendermint proofs elsewhere in this codebase carry the same "read-length-before-checking" hazard, but those paths have already been patched with explicit regression tests — see `modules/trees/ethereum/src/node_codec.rs` and `modules/consensus/pharos/primitives/src/spv.rs`, which both contain comments describing and fixing this exact panic-on-adversarial-input pattern). `ExtrinsicIntents.sol`/`IntentGatewayV2.sol` were not covered by that hardening pass.

### Impact Explanation
The reachable impact is denial of service on message delivery ("a route unable to deliver messages" per the validation criteria): an attacker can grief the IntentGatewayV2/ExtrinsicIntents route by dispatching cheap, empty-body POST requests targeting the gateway from any connected chain. Whether this is a per-message revert (retryable, low severity) or blocks a larger relayer batch depends on whether `HandlerV2`/the EVM host wraps the `onAccept` call in a try/catch. I was not able to confirm this in the time available — I found references to `HandlerV2.sol` but could not verify its exact error-handling around `onAccept` calls before running out of iterations. If the call is unprotected, a single malicious message can cause the whole containing batch/transaction to revert, which is a stronger DoS than a simple failed single-message delivery.

### Likelihood Explanation
High: dispatching a POST request with an empty body from a connected/counterparty chain is a normal, permissionless action (no special privileges, funds, or consensus fault needed) — a single submitted transaction plus a normal delivery proof is all that's required, matching the "single relayed proof or dispatched request" trigger the scan asks for.

### Recommendation
Add an explicit `require(incoming.request.body.length > 0, ...)` (or equivalent) check in `onAccept` before indexing `body[0]`, in both `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol`, and audit other `onAccept`/`onGetResponse` implementations in the SDK/contracts tree for the same unchecked `body[0]` / `values[0]` pattern (e.g. `sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol` decodes the whole body via `abi.decode` which reverts more gracefully, but any raw indexing should be audited).

### Proof of Concept
1. On a connected source chain, call the local `EvmHost.dispatch(...)` (or the general `IDispatcher.dispatch`) with `to = <ExtrinsicIntents/IntentGatewayV2 address on destination>` and `body = ""` (zero length).
2. Wait for/obtain the standard state/consensus proof for this dispatched request (no special access needed — this is exactly how legitimate messages are proven).
3. Submit the message + proof through the normal relay/handler path on the destination chain.
4. `onAccept` executes `RequestKind(uint8(incoming.request.body[0]))` against an empty `bytes` value, causing a `Panic(0x32)` revert.

Note on confidence: I was unable to verify within the available iterations whether `HandlerV2.sol` isolates per-message reverts (limiting impact to a single retryable message) or propagates them to fail an entire relayed batch (a stronger DoS). This should be confirmed before treating severity as more than "Medium."
