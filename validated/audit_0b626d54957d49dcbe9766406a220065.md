## Title
`IntentGatewayV2.placeOrder` on Tron has no reentrancy guard and no CEI ordering, unlike the audited/fixed EVM version - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The main EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) was patched against reentrancy: `placeOrder` carries a `nonReentrant` modifier [1](#0-0) , and both `_fillSameChain`/`_fillCrossChain` now write `_filled[commitment] = msg.sender` *before* any external token transfer (checks-effects-interactions, confirmed by the dedicated reentrancy regression tests) [2](#0-1) [3](#0-2) .

The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does **not** inherit any reentrancy guard — its contract declaration is `contract IntentGatewayV2 is HyperApp, EIP712` [4](#0-3)  — and its `placeOrder` function is declared `public payable` with no `nonReentrant` modifier at all [5](#0-4) .

### Finding Description
`placeOrder` in the Tron contract escrows user input tokens via `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)`, then writes the escrow accounting *after* that external call: `_orders[commitment][token] += reducedInputs[i].amount` [6](#0-5) . This is a "interaction-before-effect" pattern: the external call (`safeTransferFrom`) happens, and only afterward is escrow state updated.

If a TRC20/ERC20-with-hooks token used as an input asset can transfer control to the caller during `transferFrom` (e.g. a token with transfer hooks, similar to the ERC-777 class of tokens described in the reported bug class), the attacker can re-enter `placeOrder` (or any other state-mutating function reachable from the same contract, e.g. `fillOrder`/`cancelOrder`) before the escrow accounting for the first call is committed. Because there is no `nonReentrant` guard anywhere in this file, and the same commitment-then-escrow ordering issue as in the audited "LOB" report applies, a hook-bearing token could be leveraged to manipulate escrow bookkeeping (e.g. double-counting deposits, or reentering `withdraw`-adjacent code paths from `onAccept`/`onGetResponse`, which in the Tron file also transfers tokens with raw `.call` before decrementing `_orders` in the same statement block) — this mirrors exactly the "Withdraw tokens, reenter, withdraw again" and "Deposit tokens, reenter with placeOrder, double-spend" scenarios described in the report.

This is a real divergence from the hardened EVM contract: the Tron contract was evidently not updated with the same `nonReentrant` fix that was applied to `evm/src/apps/IntentGatewayV2.sol`.

### Impact Explanation
If deployed as-is on Tron (or any chain using this file) with a TRC20/ERC20 token that grants transfer-time control to the sender (fee-on-transfer contracts with callback hooks, or a malicious/compromised token listed for intents), an attacker can re-enter `placeOrder` (and potentially `fillOrder`, `cancelOrder`, `onAccept`/`onGetResponse` withdrawal paths) mid-transfer to manipulate `_orders[commitment][token]` escrow bookkeeping before it is finalized, or to place/cancel/duplicate escrow entries inconsistently with the actual token balance held by the gateway. This can lead to escrow accounting divergent from actual custody, i.e. permanent freezing or theft of user/solver funds — a critical-severity outcome consistent with the reported bug class.

### Likelihood Explanation
Exploitability depends on Tron/TRC20 token support for reentrant hooks during `transferFrom`, which is plausible for the same reasons flagged in the original report (protocol is deployed on multiple networks and supports various tokens, some of which may implement transfer hooks). Given the contract has zero reentrancy protection (no modifier, no `ReentrancyGuard` import) unlike its sibling `evm/src/apps/IntentGatewayV2.sol`, and given the fix was clearly already identified and applied to the main EVM contract but seemingly missed on the Tron variant, the likelihood of this being an unintentional regression left in production code is high.

### Recommendation
Add the same `nonReentrant` protection (OpenZeppelin `ReentrancyGuard`) to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder`, `fillOrder`, `cancelOrder`, `onAccept`, and `onGetResponse` functions, matching `evm/src/apps/IntentGatewayV2.sol`. Additionally, apply the checks-effects-interactions pattern consistently: update `_orders[commitment][token]` escrow accounting before performing the `safeTransferFrom`/`.call` token movement, as was done in the fixed same-chain/cross-chain fill paths (`_filled[commitment] = msg.sender` set before any transfer).

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a malicious ERC20/TRC20 token as an allowed input asset — a token whose `transferFrom` callback invokes an attacker-controlled contract before returning.
2. Attacker calls `placeOrder` with `order.inputs[0].token = maliciousToken`.
3. Inside `IERC20(token).safeTransferFrom(msg.sender, address(this), amount)` at line 459 of `evm/tron/contracts/apps/IntentGatewayV2.sol`, the malicious token's hook re-enters `placeOrder` (or `fillOrder`) before `_orders[commitment][token] += reducedInputs[i].amount` executes for the first call.
4. Because there is no `nonReentrant` guard, the re-entrant call proceeds, allowing the attacker to place/fill/cancel orders using a state where the outer call's escrow accounting has not yet been committed, leading to inconsistent escrow bookkeeping and potential double-spend of the same underlying token balance held by the gateway.
