Audit Report

## Title
Path traversal in workflow artifact HTTP fetcher allows escaping configured base URL - (File: core/services/workflows/syncer/v2/fetcher.go)

## Summary
`newHTTPFetcher` builds the outbound artifact-fetch path by joining the operator-configured base path (`u.Path`) with a workflow-owner-controlled `req.URL` using `filepath.Clean`/`filepath.Join`, which does not strip leading `..` segments before joining. This allows a crafted `BinaryURL`/`ConfigURL` at workflow registration time to make the node fetch resources outside the configured base path on the configured artifact host, unlike the sibling `newFileFetcher`, which explicitly validates the resolved path stays under `basePath`.

## Finding Description
`NewFetcherFunc` dispatches to `newHTTPFetcher` when `CRE.WorkflowFetcher.URL` uses an `http`/`https` scheme [1](#0-0) . Inside `newHTTPFetcher`, the request path is computed as:
```go
cleanPath := strings.TrimPrefix(filepath.Clean(req.URL), "/")
...
u.Path = filepath.Join(u.Path, cleanPath)
fetchURL := u.String()
``` [2](#0-1) 

`filepath.Clean` does not remove leading `..` components from a relative path, and the subsequent `filepath.Join` resolves those `..` segments against the base path — e.g. `filepath.Join("/workflows", "../../etc/passwd")` resolves to `/etc/passwd`, escaping the intended `/workflows` prefix. No check is performed afterward to confirm `u.Path` remains under its original prefix. This contrasts with `newFileFetcher`, which explicitly enforces `strings.HasPrefix(fullPath, basePath+string(filepath.Separator))` after computing the resolved path [3](#0-2) , and has a corresponding regression test verifying rejection of `../../../etc/passwd` [4](#0-3) . No equivalent test or check exists for `newHTTPFetcher`.

`req.URL` originates directly from `binaryURL`/`configURL` passed into `Store.FetchWorkflowArtifacts`, which builds `ghcapabilities.Request{URL: binaryURL, ...}` and calls `h.fetchFn` (the configured `FetcherFunc`) unmodified [5](#0-4) . These `binaryURL`/`configURL` values come from `payload.BinaryURL`/`payload.ConfigURL` on a `WorkflowRegisteredEvent`, which are attacker/workflow-owner-supplied at workflow registration time and flow directly into `FetchWorkflowArtifacts` [6](#0-5) . The only guard preventing arbitrary hosts is that only `u.Path` (not host) is modified — the traversal is confined to the configured host, not a full SSRF to arbitrary domains, which matches the claim's more limited "path traversal within the configured host" framing.

`WorkflowFetcherConfig.ValidateConfig` confirms `http`/`https`/`file` are all valid, supported schemes for this configuration option, so the vulnerable code path is a supported, non-edge-case deployment configuration [7](#0-6) .

## Impact Explanation
When an operator configures `CRE.WorkflowFetcher.URL` with an `http`/`https` scheme pointing at an artifact host that serves other content under the same origin, a workflow owner can supply a crafted `BinaryURL`/`ConfigURL` to make the node issue outbound HTTP GET requests to paths outside the configured base path on that host. This is an information-disclosure/SSRF-style impact scoped to the configured artifact host (not the node's local filesystem, since `newFileFetcher` is correctly guarded). The fetched content is subsequently base64-decoded and treated as workflow binary/config, so unintended content retrieved via traversal could also be misinterpreted/executed as workflow artifacts depending on what is served at the resolved path.

## Likelihood Explanation
Exploitation requires only that a workflow owner (an ordinary, unprivileged workflow-registry actor — not a node operator or DON peer) register a workflow with a crafted `BinaryURL`/`ConfigURL` containing `..` segments; no elevated privilege is needed to trigger the code path once the operator has the `http(s)`-scheme fetcher configured. This matches the "unprivileged actor" bar since the exploit action (submitting a URL at registration) is a normal action available to any workflow owner. The precondition is operator configuration of an `http`/`https` `WorkflowFetcher.URL`, which is one of two explicitly supported schemes for this feature — a realistic, not a contrived, deployment.

## Recommendation
In `newHTTPFetcher`, after computing `u.Path = filepath.Join(u.Path, cleanPath)`, verify the resulting path still has the original base path as a prefix (mirroring the check in `newFileFetcher` at lines 229-231), and/or reject any `req.URL` containing `..` segments before joining.

## Proof of Concept
1. Configure `CRE.WorkflowFetcher.URL = "https://artifacts.internal.example.com/workflows"`.
2. Register a workflow with `BinaryURL = "../../../secret/other-tenant-config.json"`.
3. `FetchWorkflowArtifacts` calls `h.fetchFn` with `ghcapabilities.Request{URL: "../../../secret/other-tenant-config.json"}` [5](#0-4) .
4. `newHTTPFetcher` computes `cleanPath` and joins it into `u.Path`, resolving outside `/workflows` and issuing an HTTP GET to that resolved path on `artifacts.internal.example.com` [2](#0-1) .
5. A unit test analogous to the existing `newFileFetcher` traversal test (`fetcher_test.go` L443-448) but targeting `newHTTPFetcher` with a mock HTTP server would demonstrate that a request for `../../etc/passwd` produces a fetch URL/path outside the base path, with no rejection error, confirming the missing prefix-validation check.

	}

}
