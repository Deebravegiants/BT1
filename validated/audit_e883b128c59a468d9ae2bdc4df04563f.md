### Title
Unprivileged `TransferToGasKey` funding lets an attacker permanently block `DeleteKey`/`DeleteAccount` on a victim's gas key by exceeding `MAX_BALANCE_TO_BURN` - ([File: runtime/runtime/src/access_keys.rs, runtime/runtime/src/actions.rs])

### Summary
`check_actor_permissions` does not restrict `Action::TransferToGasKey` to the target account's own actor, so any unprivileged account/receipt can send NEAR into a gas key that already exists on someone else's account. [1](#0-0)  `delete_gas_key` and `action_delete_account` both reject the operation if the gas key balance (or the aggregate gas-key balance for account deletion) exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, returning `GasKeyBalanceTooHigh` and leaving the key/account untouched. [2](#0-1) [3](#0-2)  This is the same bug class as the reported Solidity DoS: a state-gating check (`liquidityGoalReached()` vs. `balance <= MAX_BALANCE_TO_BURN`) can be flipped/pinned by an attacker who is permitted to unilaterally add funds/tokens to the checked value, permanently denying the legitimate owner an operation (transfer vs. delete-key/delete-account) that was previously available.

### Finding Description
`GasKeyInfo` tracks a balance that funds gas for transactions signed by that key. `TransferToGasKeyAction` deposits into an existing gas key's balance, and the runtime's actor-permission gate explicitly allows this action from *any* actor (unlike `AddKey`, `DeleteKey`, `WithdrawFromGasKey`, and `DeleteAccount`, which require `actor_id == account_id`): [4](#0-3) 

`delete_gas_key` (invoked from `action_delete_key`) enforces that a gas key's balance cannot exceed `GasKeyInfo::MAX_BALANCE_TO_BURN` before it can be deleted/burned: [2](#0-1) 

Similarly, `action_delete_account` sums all gas-key balances on the account and rejects deletion if the total exceeds the same threshold: [3](#0-2) 

Because `TransferToGasKey` has no actor restriction, an attacker who observes any account with an existing gas key can repeatedly send `TransferToGasKey` receipts (funded from the attacker's own balance, exactly like the "donation" in the Solidity report) targeting that gas key's public key, inflating its balance past `MAX_BALANCE_TO_BURN`. From that point on:
- The victim can never `DeleteKey` that gas key (perpetual `GasKeyBalanceTooHigh`), and
- The victim can never `DeleteAccount` while that gas key still exists (since `action_delete_account` sums *all* gas key balances against the same cap), permanently freezing their ability to close/migrate the account.

This mirrors the reported pattern precisely: a legitimate, previously-available state transition (token transfer / key-deletion) is gated by a threshold derived from a balance that an unprivileged third party can unilaterally push over the limit via a permissionless "donation"-style action, weaponizing a safety check into a permanent DoS.

### Impact Explanation
This is a griefing/DoS vector reachable by any account via ordinary signed transactions or function-call promises (`promise_batch_action_transfer_to_gas_key`) targeting a victim's existing gas key. [5](#0-4)  It permanently locks the victim out of deleting that access key, and — more severely — out of deleting their entire account (`DeleteAccountWithLargeState`/`GasKeyBalanceTooHigh` style permanent block), since `action_delete_account` aggregates all gas-key balances under the same ceiling. This blocks account lifecycle operations (key rotation, account reclamation/refund via `DeleteAccount`) for an arbitrary, unprivileged cost to the attacker (they only need to fund an amount above `MAX_BALANCE_TO_BURN`, most of which they lose as it becomes burned/unspendable from the victim's perspective, but the DoS persists indefinitely since the victim cannot reduce this balance below the threshold by normal means once it is that high — `WithdrawFromGasKey` is the only egress and is restricted to the account owner, but requires knowing/controlling the gas key's private key to sign transactions with it. However, `WithdrawFromGasKey` is authorized by `actor_id == account_id` (the account owner via any of the account's access keys, not necessarily the gas key itself, since actor permission checks against the receiving account, not the signing key) — so the owner should generally be able to call `WithdrawFromGasKey` to reduce the balance back below the threshold, making this a **temporary** griefing/annoyance rather than a permanent, un-recoverable DoS.)

Given that mitigation is available (owner can call `WithdrawFromGasKey` to reduce the balance before deleting), the practical impact is a griefing/harassment vector and gas-cost imposition rather than an irrecoverable lock, but it still allows any unprivileged account to force a victim into extra transactions to unblock their own key/account deletion.

### Likelihood Explanation
Medium. Exploitation only requires knowledge of the target account id and the target gas key's public key (which is discoverable via `view_access_keys`), and a `TransferToGasKey` action with a deposit large enough to exceed `MAX_BALANCE_TO_BURN`. No special privileges or races are required, and the action is available both via signed transactions and via a contract's promise batch action.

### Recommendation
Restrict `TransferToGasKey` to only be actionable by the account owner (`actor_id == account_id`), matching the restriction already placed on `WithdrawFromGasKey`, `AddKey`, `DeleteKey`, and `DeleteAccount` in `check_actor_permissions`: [4](#0-3) 
Alternatively, if unprivileged funding of gas keys is an intended feature (e.g., "sponsor a friend's gas"), cap per-transfer/aggregate deposits so `MAX_BALANCE_TO_BURN` cannot be exceeded by a non-owner-initiated transfer, or exempt owner-initiated `WithdrawFromGasKey`/`DeleteKey` paths from ever being blocked by externally-donated balance (e.g., only cap the *self-funded* portion, not funds attributable to third parties).

### Proof of Concept
1. Victim account `victim.near` adds a gas key `gas_pk` via `AddKeyAction` with `AccessKey::gas_key_full_access(...)`.
2. Attacker `attacker.near` (no access key on `victim.near`) submits a transaction/receipt:
   `Action::TransferToGasKey(TransferToGasKeyAction { public_key: gas_pk, deposit: GasKeyInfo::MAX_BALANCE_TO_BURN + 1 })` targeting `victim.near`. This succeeds because `check_actor_permissions` allows `TransferToGasKey` from any actor. [1](#0-0) 
3. Victim now tries `Action::DeleteKey(DeleteKeyAction { public_key: gas_pk })`; `delete_gas_key` returns `ActionErrorKind::GasKeyBalanceTooHigh` and the key remains. [6](#0-5) 
4. Victim tries `Action::DeleteAccount(...)`; `action_delete_account` sums gas-key balances, finds it exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, and returns `GasKeyBalanceTooHigh`, aborting the account deletion. [3](#0-2)
