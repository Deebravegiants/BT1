### Title
Direct token donations to a `Pair` permanently desync the virtual `tokenReserve` from `tokenBalance()`, causing `Router._computeBuy`'s overflow cap to underflow/abort and potentially bricking graduation - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap branch assumes the invariant `pair.tokenBalance() < pair.tokenReserve()` always holds (documented and fuzz-tested in `test_inv_virtualReserveAlwaysExceedsRealBalance`). This invariant relies on `tokenBalance()` and the stored virtual `tokenReserve` only ever moving together, via `Pair.swap`. But an unprivileged holder of a launched `Token` can call a plain `Token.transfer(pair, amount)` — an ERC20 transfer the protocol explicitly allows as an attack surface — which increases `tokenBalance()` without touching the stored `tokenReserve`. This breaks the invariant the cap logic depends on and turns a "should be unreachable" defensive branch into a reachable, unhandled arithmetic panic.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's real balance for oversized buys and then derives `amountInUsed` from a "capped" virtual reserve: [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

This subtraction and the explicit `OverflowCapDegenerate` guard both assume `reserveToken > realBalance` at all times. The repo's own documentation states this is only guaranteed because `Pair.reserve0 = totalSupply` (1B, virtual) while only `curveSupply = 75%` (750M) is real, and the gap (`LP_RESERVE`, 250M) is claimed to be a hard invariant maintained purely by `Router.buy`/`Router.sell` moving `tokenBalance()` and the stored `tokenReserve` in lockstep via `Pair.swap`: [2](#0-1) 

`Pair.swap` is the only function that updates the stored `_pool.tokenReserve`; `Pair.tokenBalance()` is a live `balanceOf` read with no reconciliation (`sync`) function: [3](#0-2) 

Any address holding launched `Token` (e.g. bought earlier off the curve) can call `Token.transfer(pair, amount)` directly — a plain ERC20 transfer that the threat model explicitly treats as in-scope attacker surface. This raises `tokenBalance()` without moving the stored `tokenReserve`, permanently shrinking the 250M gap. Because buys and sells always move both figures by the same amount (`Router.buy`'s `transferToken` + `swap(0, tokensOut, amountInUsed, 0)` and `Router.sell`'s `safeTransferFrom` + `swap(amountIn, 0, 0, assetOut)`), the gap created by a donation is never closed by normal trading — it can only grow via further donations.

If an attacker buys enough of the curve supply and donates it straight back to the `Pair` (bypassing `Router`/`Bonding`), they can shrink the gap to zero or negative. On the next oversized buy that trips the overflow-cap branch (which includes the very buy expected to fully drain the curve and trigger graduation via the supply trigger `tokenBalance() == 0`), `reserveToken - tokensOut` either equals zero (hits `revert OverflowCapDegenerate()`) or underflows (Solidity 0.8 checked arithmetic panic `0x11`) if the donation over-closes the gap. Either way the call reverts unconditionally for any buyer attempting that large buy going forward.

### Impact Explanation
- Any oversized/graduation-triggering buy through `Zap.buy` → `Bonding.buy` → `Router.buy` permanently reverts once the gap is closed, denying legitimate traders from executing large buys on that curve (DoS on trading).
- If the USD-value graduation trigger also never fires for the token/LT pair in question (e.g. a low-`exchangeRate` LT or thin trading), the supply trigger becomes the only path to graduation, and that path is now permanently blocked. The token can never reach `finalizeGraduation`, permanently freezing all curve-raised LT and the 250M `LP_RESERVE` tokens parked in `Bonding`, and preventing the LP from ever being seeded/locked — a permanent freeze of creator/trader/LP funds.
- Even where the USD trigger eventually fires independently, traders attempting large buys in the interim experience unexpected, unrecoverable reverts (Panic) rather than a graceful cap, which is itself unexpected DoS behavior on an unprivileged, permissionless trading path.

### Likelihood Explanation
The action requires only: (1) acquiring some amount of the launched `Token` via a normal curve buy (no special permission), and (2) a plain `Token.transfer` to the `Pair` address. Both are single-transaction, unprivileged operations reachable by any wallet. The size of donation needed to close the 250M-token gap scales with curve depth/cost, so the attack is more practical on shallower/cheaper curves, but is not blocked by any access control, and the protocol's own design notes explicitly acknowledge direct-transfer donations to `Pair` as an accepted attack class it must defend against (see the `skim`-based donation handling in `Bonding._seedUniswapV2Direct`), yet no equivalent defense (e.g. a `sync`/reconciliation call) exists for the curve-side `Router._computeBuy` overflow cap.

### Recommendation
- Do not assume `tokenBalance() < tokenReserve()` unconditionally in `Router._computeBuy`; explicitly bound `cappedReserveToken` and treat `realBalance >= reserveToken` as a valid (not degenerate) input, e.g. by clamping `tokensOut` to `min(tokensOut, realBalance, reserveToken - 1)` and computing `amountInUsed` from the clamped value without subtracting past zero.
- Alternatively, reconcile/ignore donated excess balance by tracking sellable supply independently of `balanceOf`, so donations to the pair cannot influence the cap math at all (mirroring how `Bonding._seedUniswapV2Direct` explicitly `skim`s and disposes of donations before they can corrupt its own accounting).
- Add a fuzz/invariant test that donates arbitrary `Token` amounts directly to `Pair` between buys and asserts `Router.buy`/`_computeBuy` never reverts with `OverflowCapDegenerate` or an arithmetic panic, and that the supply-based graduation trigger remains reachable.

### Proof of Concept
1. Launch a token via `Zap.createToken` (seed buy occurs; curve has `tokenReserve = 1e9e18`, `tokenBalance() = 750_000_000e18`, gap = `LP_RESERVE = 250_000_000e18`).
2. Attacker buys a large chunk of the curve supply (e.g. ~250M+ tokens' worth of LT) via `Zap.buy`/`Bonding.buy` — this reduces both `tokenBalance()` and stored `tokenReserve` by the same `tokensOut`, so the 250M gap is unchanged.
3. Attacker calls `Token.transfer(pair, boughtAmount)` directly (bypassing `Router`/`Bonding`), raising `tokenBalance()` back up without touching the stored `tokenReserve`. Repeating buy+donate cycles closes the 250M gap to zero (or overshoots it negative).
4. Any subsequent large buy (`amountIn` sized to try to consume the remaining real balance, including the buy that would otherwise fully drain the curve and trigger graduation via `tokenBalance() == 0`) enters `Router._computeBuy`'s cap branch, computes `cappedReserveToken = reserveToken - tokensOut`, and either reverts with `OverflowCapDegenerate()` (gap == 0) or panics with arithmetic underflow (gap < 0) — for every account attempting that trade, indefinitely.
5. If the USD-value trigger has not independently fired for this token/LT, the token is now permanently stuck in `Lifecycle.Curve`, unable to reach `_enterGraduating`/`finalizeGraduation`, freezing curve-raised LT and the 250M `LP_RESERVE` tokens in `Bonding`.

Note: I was not able to fully trace the USD-value trigger's exact numeric conditions (`_enterGraduating`'s threshold check and `virtualLtReserve` recovery) in this session due to tool-call limits, so the claim that the USD trigger can be *independently* avoided (making the freeze permanent rather than merely delayed) should be verified against `Bonding._enterGraduating` / `_prepareGraduationLiquidity` before treating the "permanent freeze" impact as certain; the DoS on the overflow-cap buy path itself, however, is fully supported by the code shown above.

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }
