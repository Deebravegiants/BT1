### Title
Deploy-time double ELF-load/verify/JIT cost of `deploy_program` is charged as a fixed builtin instruction cost, decoupling CU pricing from real CPU work - ([File: program-runtime/src/deploy.rs])

### Summary
`deploy_program` (invoked from `Upgrade`/`DeployWithMaxDataLen` via the `deploy_program!` macro) performs two full ELF loads, one full RequisiteVerifier pass, and — via `ProgramCacheEntry::reload` — a second ELF load plus (on x86_64) a JIT compile, on the full program bytes. [1](#0-0) [2](#0-1)  The cost model, however, prices the enclosing `Upgrade`/`DeployWithMaxDataLen` instruction as a fixed non-migrated builtin cost (`MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` = 3,000 CU) that is completely independent of program/ELF size. [3](#0-2) [4](#0-3) 

### Finding Description
`UpgradeableLoaderInstruction::Upgrade` calls the `deploy_program!` macro directly against `buffer`'s data (the attacker-controlled ELF bytes already staged via `Write` instructions), which in turn calls `deploy_program`: [5](#0-4) 

1. `morph_into_deployment_environment` builds a stricter deployment-only environment.
2. `Executable::load` (ELF load #1) + `executable.verify::<RequisiteVerifier>()` against that environment.
3. `ProgramCacheEntry::reload` (unsafe) is then called, which does `Executable::load` again (ELF load #2) against the *execution* runtime environment, skips verification (by design, since it was verified in step 2), and unconditionally JIT compiles the executable on x86_64. [6](#0-5) [7](#0-6) 

All of this work (two ELF parses, one verifier pass, one JIT compile) scales with the size of the ELF/program data (up to the account max size, `MAX_PERMITTED_DATA_LENGTH`), yet the cost-model classification of `Upgrade`/`DeployWithMaxDataLen` treats it as a "non-migratable builtin instruction" charged at the flat `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (3,000 CU), the same price as a trivial system-program instruction. [3](#0-2)  This is confirmed by the existing regression test `test_builtin_ix_cost_adjustment_with_bpf_v3_no_cu_limit`, which shows the entire loader-v3 deploy path billed at `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` minus the constant `UPGRADEABLE_LOADER_COMPUTE_UNITS`, with no scaling factor for the size of the deployed/upgraded program. [4](#0-3)  No other part of the fee/cost pipeline compensates for this: `data_bytes_cost` is based on the *instruction* wire bytes (the `Upgrade` instruction itself carries no ELF payload — it references a pre-filled `Buffer` account) not on account data sizes, and `write_lock_cost`/`loaded_accounts_data_size_cost` are based on account counts / a caller-declared limit, not on the actual real-time verify/JIT cost incurred by `deploy_program`.

The only throttle present is a single per-program-per-slot cooldown enforced in the `Upgrade` handler ("Program was deployed in this block already" check comparing `clock.slot == slot`). [8](#0-7)  That guard limits repeat upgrades of the *same* program to once per slot, but does not limit the number of *distinct* attacker-owned upgradeable programs that can each be upgraded once per slot, nor does it change the flat CU price billed per upgrade regardless of ELF size.

### Impact Explanation
Because `Upgrade` (and `DeployWithMaxDataLen`) CU cost is fixed and program-size-independent while the underlying CPU work (two ELF loads, one verify pass, one JIT compile) scales with ELF size up to the maximum permitted account size, an attacker can materially under-price CPU-heavy work in the cost model used for block-packing/leader scheduling and cost-tracking. This falls under underpriced/mispriced execution enabling low-cost consumption of validator CPU relative to declared compute units — a legitimate cost-model/resource-exhaustion category, since it lets a low-cost transaction (billed ~3,000 CU) consume CPU time proportional to a large ELF's verify+JIT cost, which the cost tracker/cost model cannot see or bound.

### Likelihood Explanation
Preconditions are attainable by any unprivileged user: deploy an upgradeable program up to the maximum permitted size via `DeployWithMaxDataLen`, then repeatedly (i) create a new buffer, (ii) `Write` the max-size ELF into it, (iii) issue `Upgrade` referencing that buffer. Each distinct program can only be re-upgraded once per slot due to the `clock.slot == slot` check, but nothing prevents an attacker from deploying and upgrading many distinct programs concurrently, and from doing this indefinitely over time. This is fully reachable using ordinary, signed, unprivileged transactions with no special access.

### Recommendation
Make the cost-model charge for `Upgrade`/`DeployWithMaxDataLen` scale with the size of the ELF/programdata being loaded, verified, and JIT-compiled (e.g., a per-byte cost component similar to `loaded_accounts_data_size_cost`, or classifying loader-v3 deploy/upgrade instructions with a cost proportional to `buffer_data_len`/`max_data_len` rather than the flat `MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT`), so that the compute-budget/cost-tracker charge upper-bounds the real verify+JIT CPU cost of `deploy_program`.

### Proof of Concept
Integration test plan (extending `core/tests/scheduler_cost_adjustment.rs` style tests):
1. Build two `TestSetup` deploy-with-max-data-len transactions using ELFs of very different sizes (e.g. a minimal `sbpfv3_return_ok.so` vs. a program padded/inflated toward `MAX_PERMITTED_DATA_LENGTH`).
2. Measure the wall-clock time of `deploy_program` (or of `bank_client.send_and_confirm_instruction` executing the `Upgrade` instruction) for both sizes, using `solana_svm_measure::measure::Measure` around the call, analogous to `verify_code_time`/`jit_compile_time` in `program_cache_entry.rs`.
3. In the same test, compute `CostModel::calculate_cost` (or read `programs_execution_cost` from `TransactionCost`) for both transactions.
4. Assert: `execution_time_large_elf >> execution_time_small_elf` (proportional to size), while `programs_execution_cost_large_elf == programs_execution_cost_small_elf == MAX_BUILTIN_ALLOCATION_COMPUTE_UNIT_LIMIT` (i.e., cost does not scale with size though execution time does), reproducing the assertion pattern already used in `test_builtin_ix_cost_adjustment_with_bpf_v3_no_cu_limit`. [4](#0-3)

    fn new_internal(
        loader_key: &Pubkey,
        program_runtime_environment: ProgramRuntimeEnvironment,
        deployment_slot: Slot,
        elf_bytes: &[u8],
        #[cfg(feature = "metrics")] metrics: &mut LoadProgramMetrics,
        reloading: bool,
    ) -> Result<Self, Box<dyn std::error::Error>> {
        let entry_stats = ProgramStatistics::default();
        #[cfg(feature = "metrics")]
        let load_elf_time = solana_svm_measure::measure::Measure::start("load_elf_time");
        let executable = Executable::load(elf_bytes, Arc::clone(&*program_runtime_environment))?;

        #[cfg(feature = "metrics")]
        {
            metrics.load_elf_us = load_elf_time.end_as_us();
        }

        if !reloading {
            #[cfg(feature = "metrics")]
            let verify_code_time = solana_svm_measure::measure::Measure::start("verify_code_time");
            executable.verify::<RequisiteVerifier>()?;
            #[cfg(feature = "metrics")]
            {
                metrics.verify_code_us = verify_code_time.end_as_us();
            }
        }

            executable.jit_compile()?;
            let jit_compile_time = jit_compile_time.end_as_us();
            entry_stats.jit_compiled(jit_compile_time);
            #[cfg(feature = "metrics")]
            {
                metrics.jit_compile_us = jit_compile_time;
