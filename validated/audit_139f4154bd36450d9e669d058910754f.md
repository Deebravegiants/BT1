### Title
Withdrawal status matched only by `assetId` causes duplicate/false "completed" report for co-batched withdrawals of the same asset - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the on-chain withdrawal status for a given `WithdrawalIdentifier` by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely by `assetId` (via `defuse_asset_identifier`/`near_token_id`), with no correlation to the withdrawal's `index`, destination address, or amount.

### Finding Description
`describeWithdrawal` explicitly documents that "Response list is unsorted, so we match by assetId instead of index," and looks up a withdrawal entry using only the asset identifier: [1](#0-0) 

The SDK explicitly supports batching multiple withdrawals in one intent transaction via `createWithdrawalCompletionPromises`, which builds one `WithdrawalIdentifier` per entry in `withdrawalParams` and polls each independently through `watchWithdrawal` → `bridge.describeWithdrawal`: [2](#0-1) 

If two entries in the same batch withdraw the **same asset** (e.g., the same token sent to two different destination addresses/amounts in a single intent — a supported and realistic pattern per the batch-withdrawal design), `findMatchingWithdrawal` has no way to distinguish between them: it selects a withdrawal record from the unsorted API response solely by `assetId`, ignoring `index`, `destinationAddress`, and `amount`. The regression test in the repo confirms the matching key is `assetId` only, not `index`: [3](#0-2) 

Consequently, when two same-asset withdrawals are in flight, both `WithdrawalIdentifier`s resolve against the same underlying withdrawal record, so both `describeWithdrawal` calls can return the identical `status: "completed"` and identical `txHash`, even though only one of the two withdrawals has actually landed on the destination chain (the other API record may not exist yet, or may belong to the other party's withdrawal).

### Impact Explanation
This breaks the equality between the on-chain outcome and the status the SDK reports for a specific withdrawal identifier: a completed txHash meant for one withdrawal is reported as completion for a second, still-pending (or non-existent) withdrawal. An integrator using `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` to gate crediting a user or releasing funds could credit the second withdrawal as done based on a hash that doesn't correspond to it — a status/hash misreport that can cause a double credit, matching the High-impact class defined in scope ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires no malicious actor — it triggers whenever an integrator legitimately batches two or more withdrawals of the same `assetId` in a single `withdrawalParams` array (a documented, supported use case), and the POA bridge processes them at different times so the API response temporarily contains only one matching record while both SDK-side identifiers are polling concurrently.

### Recommendation
Match withdrawal records by a fuller set of identifying fields (e.g., `destinationAddress` and `amount` in addition to `assetId`), or have the POA bridge API return/consume a per-withdrawal correlation id, so that `findMatchingWithdrawal` cannot conflate two distinct same-asset withdrawals within one NEAR transaction.

### Proof of Concept
1. Build one intent with two `ft_withdraw` withdrawals of the same `assetId` (e.g., `nep141:usdc.omft.near`) but different `receiver_id`/amount, submitted in one NEAR tx.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [w1, w2], intentTx })`.
3. Once the POA bridge API reports only `w1`'s withdrawal as `COMPLETED` (e.g., `withdrawals: [{status:"COMPLETED", data:{defuse_asset_identifier: assetId, transfer_tx_hash: "hash-for-w1", ...}}]`), both promises' internal `describeWithdrawal` calls invoke `findMatchingWithdrawal(response.withdrawals, assetId)` and each receives the same `w1` record — see the matching logic at [4](#0-3) .
4. Both `promises[0]` and `promises[1]` resolve to `{ hash: "hash-for-w1" }`, falsely indicating `w2` has completed with `w1`'s transaction hash.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
