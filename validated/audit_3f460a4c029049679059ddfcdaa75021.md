### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop as soon as `Utils::HmacValidator.validate(request)` succeeds. However, the HMAC is computed only over the raw request body (`Request#to_signable_string` returns `@raw_body`), never over the `x-shopify-shop-domain` (or `x-shopify-topic`/`x-shopify-webhook-id`/`x-shopify-api-version`) headers. `Request#shop` simply reads the `shopify-shop-domain` header verbatim and is passed straight into `WebhookMetadata#shop`, which host apps use as the authoritative tenant identifier for the event.

### Finding Description
The equality the gem should guarantee but does not is:

`shop bound by the HMAC signature == shop the handler is told the event came from`

In `HmacValidator.validate_signature`, the signature comparison is computed from `verifiable_query.to_signable_string`: [4](#0-3) 

For `Webhooks::Request`, `to_signable_string` is only the raw JSON body: [5](#0-4) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly from attacker-controlled HTTP headers, with no cryptographic binding to the HMAC at all: [6](#0-5) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally forwards `request.shop` to the handler as the trusted shop identity: [2](#0-1) 

Because the `shop-domain` header is outside the signed payload, any request whose body+HMAC pair is valid for the app's secret — for example a genuine webhook the attacker's own (legitimately installed) shop received, or any other request whose raw body happens to produce a valid signature — can have its `x-shopify-shop-domain` header rewritten to name a different, victim shop, and the app will process it as if it came from that victim shop. This breaks the tenant-identity binding the host application relies on when dispatching webhook data (e.g., writing/deleting records keyed by `data.shop`, as shown in the gem's own documented usage pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), which is directly analogous to the referenced report's core defect: an identity/ownership field being trusted and acted upon despite not being covered by the authenticity check that gates the operation. [7](#0-6) 

### Impact Explanation
An attacker who controls (or previously captured a valid signed webhook payload from) even one shop can forge the shop-domain header on a replayed/relayed request so the app attributes the webhook's data/action to an arbitrary other tenant, since `Registry.process` never binds `shop` to the HMAC. Depending on how the host app consumes `WebhookMetadata#shop` (e.g., looking up/replacing per-tenant records, triggering per-tenant side effects, redact/data-request handling), this is a cross-tenant integrity/confidentiality issue rooted entirely in this gem's `Registry`/`Request`/`HmacValidator` design, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitability requires only a body+HMAC pair valid under the app's secret key for *some* accepted webhook (which any installed shop naturally receives) plus the ability to alter the shop-domain header the app's webhook endpoint receives — no possession of the `api_secret_key`, access token, or victim credentials is required. The header-only tenant binding is unconditional in `Registry.process`, so this applies to every app relying solely on this gem's webhook verification for tenant attribution.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the value that is HMAC-verified, or require the host application to independently confirm `request.shop` corresponds to a shop with an active, legitimate session/installation before trusting it, rather than deriving tenant identity purely from an unauthenticated header alongside a body-only HMAC check.

### Proof of Concept
1. App A (attacker-controlled, legitimately installed) receives a real webhook from Shopify, e.g. body `{"id":1}` with header `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed by Shopify over that body with the app's shared secret.
2. Attacker captures this raw body and its valid HMAC (both are visible to the receiving endpoint's operator, or can be produced by the attacker's own shop on demand), and constructs a new HTTP request to the app's webhook endpoint with the same body and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because it only checks the (unchanged) raw body against the HMAC:
```ruby
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: '{"id":1}',
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => captured_valid_hmac, # valid for the body above
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  },
)
ShopifyAPI::Webhooks::Registry.process(request) # succeeds; handler.handle receives shop: "victim-shop.myshopify.com"
```
4. The registered handler receives `WebhookMetadata#shop == "victim-shop.myshopify.com"` and performs whatever tenant-scoped action the app implements (e.g., data update/deletion), even though the event never truly originated from `victim-shop`.
