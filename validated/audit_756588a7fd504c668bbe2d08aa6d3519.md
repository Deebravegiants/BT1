Found the analog. `Auth::TokenExchange.exchange_token` sends the app's `client_secret` to a host derived directly from the JWT `dest` claim without passing it through `ShopValidator`, unlike every other credential-sending code path in this gem.

### Title
`client_secret` sent to an unvalidated host derived from the session-token `dest` claim in Token Exchange - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` decodes the caller-supplied session token via `Auth::JwtPayload`, takes `dest_shop = jwt_payload.shop` and uses it, unsanitized, as the `Auth::Session#shop` that `Clients::HttpClient` turns into the request host (`https://#{session.shop}`) to which the `client_id`/`client_secret` are POSTed [1](#0-0) . Every other flow that builds this exact request (`ClientCredentials.client_credentials`) validates the shop first with `Utils::ShopValidator.sanitize!` [2](#0-1) , but `TokenExchange` does not.

### Finding Description
`JwtPayload#shop` is computed as `@dest.gsub("https://", "")` with no format/allow-list check against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [3](#0-2) . The only checks performed during JWT decoding are signature validity (`HS256` with `api_secret_key`), expiry/`nbf`/`iat` leeway, and `aud == Context.api_key` [4](#0-3) . There is no validation that `iss`/`dest` is a `*.myshopify.com`/trusted Shopify host.

`HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` [5](#0-4) , and the request body containing `client_secret` is POSTed to that URI [6](#0-5) .

The binding that should hold is: **host that receives `client_secret` == host validated as a trusted Shopify domain**. In `TokenExchange`, the host is instead bound only to "whatever the `dest` claim of a validly-signed JWT contains," which is a weaker, incomplete binding — mirroring the Vyper bug class where a bounds/overflow check omitted an edge case that let out-of-range values slip through. Here, the omitted check is the shop-domain allow-list check that the sibling `ClientCredentials` flow performs.

### Impact Explanation
Exploitation requires the ability to supply a validly-signed session token whose `dest` is not a genuine Shopify shop domain but still passes signature/`aud` checks. If an app operator or a component in the trust chain (e.g., a proxy, a customized App Bridge integration, or any code path that lets `session_token` reach `exchange_token` from a less-trusted context) allows a `dest` value that isn't strictly enforced to be `*.myshopify.com`, the app's `client_secret` would be sent to that host, resulting in `client_secret` exfiltration (SSRF carrying the app's credentials to an attacker-influenced host) — matching the High-impact "SSRF with the app's credentials" category.

### Likelihood Explanation
Likelihood is constrained by the JWT signature check requiring `api_secret_key` to sign the token, which normally is only done by Shopify. However, this is a genuine defense-in-depth gap: the gem inconsistently validates shop-derived hosts across its own OAuth-adjacent flows (`ClientCredentials` validates, `TokenExchange` does not), and the docs explicitly state "the shop always comes from the session token `dest` claim" [7](#0-6)  without mentioning any domain restriction, so any caller relying on this documented contract has no guarantee the resulting host is a trusted Shopify domain.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, sanitize `dest_shop` with `Utils::ShopValidator.sanitize!(jwt_payload.shop)` before constructing `shop_session`/`Clients::HttpClient`, consistent with `client_credentials.rb`.

### Proof of Concept
1. Obtain (or, in a threat model where the leeway/signature path can be influenced, forge) a session token whose payload has `aud` = the app's `api_key`, valid `exp`/`nbf`/`iat`, but `dest` = `"https://attacker-controlled-host.example"`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload.new(token).shop` returns `"attacker-controlled-host.example"` unchanged [3](#0-2) .
4. `HttpClient` builds `https://attacker-controlled-host.example/admin/oauth/access_token` and POSTs `client_id`/`client_secret` there [5](#0-4) , [6](#0-5) , leaking the `client_secret` to the attacker's host.
