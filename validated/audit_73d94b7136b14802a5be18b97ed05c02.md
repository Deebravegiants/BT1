### Title
`Bonding._noFeeSwapInput`'s unchecked `Math.mulDiv` discriminant can be driven past `uint256` by an attacker-controlled hostile pre-seed + a high-priced LT pairing, permanently reverting `finalizeGraduation` and freezing all curve-raised funds - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._noFeeSwapInput` (the closed-form rebalance-swap-size calculator used by the hostile-pre-seed defense) computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` and is explicitly documented as the "load-bearing" math whose safety depends on callers keeping `reserveIn * reserveOut * targetN / targetD ≤ 2^256`. That bound is asserted only in a comment, not enforced by any runtime check. `reserveIn`/`reserveOut` are the live HyperSwap V2 pair reserves, which an unprivileged attacker fully controls via a pre-`finalizeGraduation` hostile pre-seed (`factory.createPair` + `transfer` + `pair.mint`, the exact attack class the project's own AGENTS.md describes at length). `targetN/targetD` is `tokensForLP/ltFromPair`, whose ratio is effectively `LP_RESERVE / virtualLtReserve`, and `virtualLtReserve` can be made arbitrarily small in raw LT units for any token paired against a sufficiently high-priced/high-`exchangeRate` LT (LT choice is the caller's at `Zap.createToken` time). Combining a maximal-reserve hostile pre-seed with a token paired to a high-value LT drives the discriminant far past `2^256`, so `Math.mulDiv` reverts inside `_noFeeSwapInput`, which propagates through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`, permanently bricking that token's graduation.

### Finding Description
`_noFeeSwapInput` in [1](#0-0)  computes:
```
uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
uint256 newIn = Math.sqrt(product);
```
Its own natspec states the safety precondition explicitly: [2](#0-1) , i.e. "Call sites must keep [`reserveIn * reserveOut * targetN / targetD`] ≤ 2^256... Constructed adversarial inputs that violate this would `revert` rather than silently truncate." No code enforces this bound at the call site; it is a documentation-only assumption.

The call sites pass fully attacker-influenced `reserveIn`/`reserveOut` — the live pool reserves after a hostile pre-seed — in [3](#0-2) . This is exactly the pre-seed attack surface the project itself documents as reachable by any unprivileged address between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`): front-run `factory.createPair`, `transfer` tokens/LT into the pair at any attacker-chosen ratio, and `pair.mint(attacker)` [4](#0-3) . Reserves in a real V2 pair can reach up to `type(uint112).max` per side, so `reserveIn * reserveOut` alone can approach `2^224`.

`targetN`/`targetD` are `tokensForLP`/`ltFromPair`, computed in `_prepareGraduationLiquidity` as `ltFromPair = assetReserve - virtualLtReserve` and `tokensForLP = (ltFromPair * tokenReserve) / assetReserve` [5](#0-4) . Near the supply-trigger boundary (`tokenReserve → LP_RESERVE = 250M·1e18`, `assetReserve → virtualLtReserve`), the ratio `tokensForLP/ltFromPair` tends to `LP_RESERVE / virtualLtReserve`. `virtualLtReserve` is the launch-time LT amount that seeds a fixed ~$3K USD market cap, per [6](#0-5)  ("K is computed per token so every token opens at ~$3K market cap regardless of which LT is paired"). Because the paired LT's `exchangeRate()` can be arbitrarily large (a high-value LT, chosen freely by the token creator via `Zap.createToken`), `virtualLtReserve` in raw 18-decimal LT units can be pushed extremely small, making `LP_RESERVE / virtualLtReserve` extremely large.

Multiplying an attacker-maximized `reserveIn * reserveOut` (~2^224) by this inflated `targetN/targetD` ratio drives the mulDiv discriminant far past `2^256`, so `Math.mulDiv` reverts (OpenZeppelin's `mulDiv` explicitly reverts when the quotient can't fit in 256 bits). That revert bubbles all the way up to `finalizeGraduation` [7](#0-6) , which has no try/catch and no alternate path.

This directly violates the protocol's own stated invariant: `_seedUniswapV2Direct` "MUST never revert under any pre-seed shape," ranked as the top-priority security property because "a brick locks every holder in `Graduating` forever" [8](#0-7) . The existing test suite only stresses `_noFeeSwapInput` up to `targetD`/`targetN` bounded by `Token.TOTAL_SUPPLY` scale (~2^90), explicitly noting the discriminant would overflow for arbitrary ratios and relying on the (unenforced) call-site assumption to avoid it [9](#0-8)  — it never fuzzes the case of an LT whose `exchangeRate()` makes `virtualLtReserve` tiny in raw units combined with a maximal attacker pre-seed.

### Impact Explanation
Once `finalizeGraduation` reverts unconditionally for a token (the pre-seed state and the tiny `virtualLtReserve` are both permanent/immutable once set), the token is stuck forever in `Lifecycle.Graduating`:
- All curve-raised LT (`ltFromPair`, already drained into `Bonding` via `Router.graduate` in phase 1) is permanently locked in `Bonding` with no rescue path.
- The 250M `LP_RESERVE` tokens held in `Bonding` are permanently locked.
- Holders can never sell (trading is frozen at `_enterGraduating`) and can never receive their post-graduation LP-backed liquidity.
- No admin function exists to retry or bypass a specific token's stuck `finalizeGraduation`, since it's the sole gate from `Graduating` → `Graduated`.

This is a concrete, permanent freezing of trader/creator/protocol funds, satisfying the High-severity bar analogous to the ClickHouse CVE's crash-via-crafted-payload class: an unauthenticated/unprivileged party submits a crafted input (here, a crafted pool pre-seed + LT choice) that crashes (reverts) a critical code path with no recovery.

### Likelihood Explanation
- `finalizeGraduation` is explicitly permissionless [10](#0-9) , and the hostile pre-seed setup (`factory.createPair`, `transfer`, `pair.mint`) is fully permissionless and requires only gas plus a small self-funded dust/skewed deposit.
- `Zap.createToken` lets any creator pick which BounceTech LT to pair a token against, so an attacker (or a colluding "creator") can deliberately choose a high-`exchangeRate` LT to minimize `virtualLtReserve` in raw units.
- The only limiting factor is achieving a sufficiently extreme `reserveIn * reserveOut * targetN / targetD` product; this is a deterministic, computable condition (no timing/race dependency), and the attacker who set up the pre-seed controls both `reserveIn`/`reserveOut` and, indirectly through LT choice, `virtualLtReserve`.
- This requires precise setup and is not a trivial one-line attack, which is reflected in it being High rather than Critical, but it is fully within reach of a single unprivileged, well-resourced attacker with no special access.

### Recommendation
- Enforce the `reserveIn * reserveOut * targetN / targetD ≤ 2^256` precondition explicitly inside `_noFeeSwapInput` (or its callers) rather than relying on a comment, and define a safe fallback (analogous to the existing `s == 0` / `expectedOut == 0` fallback to `_seedDirectMint`) when the closed-form computation would overflow, instead of letting it revert uncaught.
- Consider computing the discriminant using scaled/normalized reserves (e.g., dividing both `reserveIn`/`reserveOut` and `targetN`/`targetD` by a common large factor before multiplying) so the product provably stays within `uint256` regardless of how extreme the attacker's pre-seed or the paired LT's `exchangeRate()` is.
- Add fuzz coverage in `test/NoFeeSwapInput.t.sol` that varies `targetN`/`targetD` ratios derived from a wide range of `virtualLtReserve` values (not just token-supply-scale bounds), combined with `type(uint112).max`-scale `reserveIn`/`reserveOut`, to catch this overflow class before deployment.
- Wrap the `_noFeeSwapInput` call (or the whole `_pairRebalance` leg) in a try/catch inside `_seedRebalancing` so any unexpected revert degrades gracefully to `_seedDirectMint` rather than bricking `finalizeGraduation`.

### Proof of Concept
1. Attacker calls `Zap.createToken(...)`, choosing a BounceTech LT with a very high `exchangeRate()` (e.g., an LT tracking a high-priced underlying), so that `virtualLtReserve` (the raw LT amount seeding the fixed ~$3K USD market cap, computed in `_deployAndSeed`/`Router.addInitialLiquidity`) is minimized in raw 18-decimal units.
2. Attacker/other traders buy through the curve until the supply trigger fires (`IPair.tokenBalance() == 0`), landing `_enterGraduating` with a small `ltFromPair` and a `tokensForLP`/`ltFromPair` ratio approaching `LP_RESERVE / virtualLtReserve` — as large as the attacker engineered it in step 1.
3. Before `finalizeGraduation` is called, attacker front-runs: calls `factory.createPair(token, lt)`, transfers token and LT amounts sized to push reserves toward `type(uint112).max` on at least one side at a skewed ratio, and calls `pair.mint(attacker)`.
4. Anyone (attacker or keeper) calls `Bonding.finalizeGraduation(token)`. Inside `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, the discriminant `reserveIn * reserveOut * targetN / targetD` exceeds `uint256`, `Math.mulDiv` reverts, and `finalizeGraduation` reverts unconditionally for this token.
5. The token is permanently stuck in `Lifecycle.Graduating`: all curve-raised LT and the 250M `LP_RESERVE` tokens remain locked in `Bonding` forever, with no code path to retry or rescue.

Exact numeric thresholds (minimum LT `exchangeRate()` and minimum attacker pre-seed size needed to guarantee the overflow) were not verified against live HyperSwap V2 `uint112` reserve mechanics or exact `Math.mulDiv`/`Math.sqrt` revert boundaries within this review; a Devin session with test/fuzzing tooling would be needed to derive and confirm the precise attack parameters end-to-end.

```text
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```

```markdown
### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.
```

```markdown
### Brick-resistance contract

`_seedUniswapV2Direct` MUST never revert under any pre-seed shape. The brick-resistance contract is the load-bearing security property — it ranks above the LP-capture defense, because a brick locks every holder in `Graduating` forever. The pre-seed defense is layered to honour this:

- **Regime 1/2 don't touch the router.** Even if the V2 router is misbehaving, the empty + donation paths run on direct pair calls.
- **`_pairRebalance` falls back to a direct mint when no swap can run.** `_noFeeSwapInput` may return `s == 0`, or the pair's fee-charging `getAmountOut(s)` may round to zero, against a pre-seed whose swap-output side is dust — `pair.swap` would otherwise revert with `INSUFFICIENT_OUTPUT_AMOUNT`. In either case `_pairRebalance` returns `false`, and `_seedRebalancing` overpowers the dust with a direct `transfer + pair.mint` at the cached `tokensForLP / ltFromPair` ratio (`_seedDirectMint`), opening the pool on-ratio. This is safe specifically because the swap only rounds to zero when the reserves are negligible against this graduation's inventory: the V2 `min()` donation to the attacker's pre-existing LP is then bounded by `max(reserveToken/tokensForLP, reserveLT/ltFromPair)`, which vanishe ... (truncated)
- **`_routerDepositAndDispose` uses `min0=1, min1=1`.** Slippage protection on `addLiquidity` exists to defend against a third party moving the pool ratio between quote and execution; here we set the ratio ourselves in `_pairRebalance` in the same atomic tx, so there's no third party to defend against. The `=1` (rather than `=0`) trips V2's degenerate-ratio guard so the call can't silently land at near-zero.
- **No external dependency on the router slot being correct post-deploy.** `uniswapV2Router` is set at `initialize` time alongside `uniswapV2Factory` and is rejected if zero. There's no live setter — rotation requires a UUPS upgrade so the change is visible on-chain ahead of any in-flight graduation.
```
