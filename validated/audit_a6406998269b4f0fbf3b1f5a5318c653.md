### Title
Webhook HMAC signs only the raw body, not the `shop-domain` header — cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw HTTP body only, while the `shop` (and `topic`/`webhook-id`) values that `Registry.process` hands to the app's webhook handler are read straight from unauthenticated HTTP headers. Because the app's `api_secret_key` is shared across every shop that installs the app, an attacker who legitimately installs the app on their own shop can capture a valid `(body, HMAC)` pair from a real Shopify-delivered webhook and replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a different (victim) shop. `Registry.process` will accept the HMAC as valid and dispatch the handler with `shop` set to the attacker-chosen victim domain.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are parsed directly from headers with no cryptographic binding to the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then forwards the header-derived `request.shop` straight into the handler's `WebhookMetadata` without any further check that it matches the shop that actually produced the signed body: [4](#0-3) 

`Utils::HmacValidator.validate` only compares the HMAC against `to_signable_string` (the body), never against headers: [5](#0-4) 

Equality that should hold but doesn't:
`shop authenticated by HMAC` ⇒ should equal `shop delivered to the handler`, but instead the gem only proves "some request signed with this app's shared secret", and separately trusts an arbitrary, unauthenticated header for shop identity. Since the `api_secret_key` is one value per app (shared by all installed shops), any tenant of the app can generate/observe a validly-signed `(body, HMAC)` pair for their own shop and then present it under a different shop's identity — there is nothing in the HMAC computation that binds the signature to a specific shop.

### Impact Explanation
An attacker who is a legitimate (even free/trial) installer of the target app on their own store gains the ability to make the app process data as though it came from a shop they do not control. Depending on what the host application does with `WebhookMetadata#shop` (e.g., attribute events, update per-tenant state, trigger emails, adjust billing/inventory records keyed by `shop`), this results in cross-tenant data corruption/spoofing — the app is caused to act on behalf of, or write data associated with, a victim tenant that the attacker never had access to. This matches the "cross-tenant access" Critical impact category: the shop-identity binding that the handler relies on is not actually authenticated by the HMAC the gem verifies.

### Likelihood Explanation
Requires only: (1) ability to install the target Shopify app on any shop (low bar — many apps offer free installs), (2) ability to send an arbitrary HTTP POST to the app's public webhook endpoint (trivial, since that endpoint must be internet-reachable to receive Shopify's callbacks), and (3) capture of one legitimate webhook `(body, HMAC)` pair for a predictable/attacker-controllable body from their own installation. No access token, `client_secret`, or leaked credentials of the victim are required.

### Recommendation
Bind the shop identity (and topic/webhook id) into the signed material, or otherwise cryptographically tie the header claims to the verified payload — e.g., verify that the `shop-domain` header matches a shop the app's server-side session store expects for this specific webhook_id/subscription, and/or include the shop domain in the HMAC computation if Shopify webhook signing scope changes to support it. Short of that, the host application (and ideally this gem) should not trust `request.shop` for identity-sensitive processing without independently confirming the webhook subscription/shop registration server-side (e.g., cross-checking against the webhook_id → shop mapping recorded at registration time).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining real webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker triggers/observes a webhook with a body they control or can predict (e.g., a `themes/publish` event with a fixed/guessable payload), capturing `raw_body` and the corresponding `x-shopify-hmac-sha256` value.
3. Attacker POSTs to the app's public webhook endpoint with the same `raw_body`/HMAC but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic`/`x-shopify-webhook-id` as desired.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only checks the body against the shared secret (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload actually originated from the attacker's own shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
