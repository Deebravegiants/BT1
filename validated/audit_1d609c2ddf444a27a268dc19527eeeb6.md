### Title
Rounding drift between `calc_pnl_x/calc_pnl_y` (sys-decimal) and pool vault amounts (native-decimal) can permanently gate `calc_take_pnl`, bricking deposit/withdraw/swap - (File: program/src/processor.rs)

### Summary
`calc_take_pnl` is invoked unconditionally by `process_deposit`, `process_withdraw`, `process_swap_base_in`/`process_swap_base_out`, and `process_withdrawpnl` (whenever `amm.status != WithdrawOnly`) to keep the "PnL invariant" (`target_orders.calc_pnl_x`/`calc_pnl_y`) in sync with the pool's real token balances. Like the SecondSwap `stepsClaimed`/`numOfSteps` invariant that can drift out of range due to rounding and then permanently gate `claim`, Raydium's `calc_pnl_x`/`calc_pnl_y` invariant is maintained through repeated floor-rounded decimal conversions (`normalize_decimal_v2`, `restore_decimal`) performed in two different numeric scales (native-token decimals vs. `sys_decimal_value`-scaled decimals) and combined with `checked_sub(...).unwrap()` arithmetic. Accumulated rounding drift across many deposit/withdraw/swap/pnl-take cycles can push the stored invariant past the live pool balances, causing the gating comparison in `calc_take_pnl` to permanently fail (or the `.unwrap()` subtraction to panic), which aborts every subsequent deposit/withdraw/swap transaction and freezes user/LP funds in the pool.

`target.calc_pnl_x`/`calc_pnl_y` are persisted on-chain and updated after every deposit/withdraw using `checked_sub(...).unwrap()` chains that mix a value normalized from native-decimal to `sys_decimal_value`-decimal (`Calculator::normalize_decimal_v2`, floor division) with `delta_x`/`delta_y`, which are derived from `diff_x`/`diff_y` computed purely in `sys_decimal_value` scale and then converted back to native decimals through `Calculator::restore_decimal` (also floor division) for the vault-side subtraction: [5](#0-4) [6](#0-5) 

Because `normalize_decimal_v2`/`restore_decimal` both floor-round independently in two different directions of the same round trip (once when persisting `calc_pnl_x/y` in sys-decimal scale, once when converting the pnl amounts back to native-decimal token amounts actually removed from `total_pc_without_take_pnl`/`total_coin_without_take_pnl`), the two representations of "how much has already been taken as pnl" slowly diverge over many operations, exactly as `stepsClaimed` drifted past `numOfSteps` in the SecondSwap report due to integer step-duration rounding. Once `calc_pnl_x * calc_pnl_y` (derived from the stored, drifted invariant) exceeds the live `pool_pc_amount * pool_coin_amount`, the guard at line 190 permanently evaluates false for that pool, and every deposit, withdraw, and swap on the pool reverts with `CalcPnlError` going forward, since the same stale, drifted `calc_pnl_x/calc_pnl_y` values are read again on the next call and the drift only grows (or at best does not self-correct) with continued floor-rounding.

### Impact Explanation
Once the invariant drifts past the pool's real balances, `process_deposit`, `process_withdraw`, `process_swap_base_in`, and `process_swap_base_out` all revert with `AmmError::CalcPnlError` for that AMM permanently, because they all route through `calc_take_pnl` using the same corrupted `target_orders.calc_pnl_x/calc_pnl_y` state. This freezes all LP and swap liquidity in the pool with no user-triggerable recovery path (only `process_withdrawpnl` with `WithdrawOnly` status bypasses the check, and that path is not something an ordinary user or LP can trigger). This matches the SecondSwap report's impact category: permanent freezing of user/LP funds caused by an unrecoverable, rounding-induced state drift gating the funds-moving function.

### Likelihood Explanation
The drift accumulates from ordinary, unprivileged usage — deposits, withdrawals, and swaps performed by any user over the pool's lifetime — with no attacker privilege required, similar to how the SecondSwap bug required only "buy tokens, wait until vesting ends, buy more tokens." The magnitude of drift per operation is small (bounded by decimal-conversion rounding, at most a few units per call), so many operations over a long-lived, low-decimal-precision pool would be needed to trigger it, making this a lower-likelihood, longer-horizon condition rather than a single-transaction exploit — consistent with the judge's characterization of the original SecondSwap finding as "a very rare case" and Medium severity.

### Recommendation
Avoid using `.unwrap()` on the `checked_sub` calls that update `target_orders.calc_pnl_x`/`calc_pnl_y` and on the pnl invariant comparison; clamp negative differences to zero (as recommended for `claimable`) instead of allowing the amounts to grow unboundedly relative to the true pool balance. Additionally, keep `calc_pnl_x`/`calc_pnl_y` and the native-decimal pnl bookkeeping in a single consistent rounding scheme (e.g., always round in the same direction, or track only in native-decimals) so that the two representations of "amount already taken as pnl" cannot structurally diverge over repeated operations.

### Proof of Concept
1. A pool is created with `pc_decimals`/`coin_decimals` different from `sys_decimal_value`'s implied precision, so `normalize_decimal_v2`/`restore_decimal` round trips are lossy (see `program/src/math.rs:80-116`).
2. Many ordinary deposit/withdraw/swap transactions occur over time; each one calls `calc_take_pnl`, which persists `target_orders.calc_pnl_x`/`calc_pnl_y` from `diff_x`/`diff_y` computed in `sys_decimal_value` scale (`program/src/processor.rs:213-226`), while simultaneously subtracting a *separately floor-rounded* native-decimal amount (`pc_pnl_amount`/`coin_pnl_amount`, via `restore_decimal`) from the pool's live `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (`program/src/processor.rs:228-262`).
3. Because these two roundings are independent, the value of the persisted `calc_pnl_x * calc_pnl_y` and the live `pool_pc_amount * pool_coin_amount` can drift apart over many cycles.
4. Once `calc_pc_amount * calc_coin_amount` (derived from the drifted stored invariant) exceeds `pool_pc_amount * pool_coin_amount` (derived from the live vaults), the check at `program/src/processor.rs:190-192` fails and every subsequent `process_deposit`/`process_withdraw`/`process_swap_base_in`/`process_swap_base_out` call for that pool returns `AmmError::CalcPnlError`, permanently freezing the pool's funds.

    pub fn normalize_decimal(val: u64, native_decimal: u64, sys_decimal_value: u64) -> u64 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = Self::to_u64(
            ret_mut
                .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
                .unwrap()
                .as_u128(),
        )
        .unwrap();
        ret
    }
