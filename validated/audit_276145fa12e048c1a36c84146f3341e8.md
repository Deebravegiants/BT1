## Analog Found

### Title
JWT replay-cache uses a fixed independent purge window instead of the token's own `exp`, permitting replay of already-used gateway trigger requests - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
The Sherlock finding describes a class of bug where a system swaps in "fresh" state (a new Chainlink aggregator phase) without validating that the new state's freshness marker (`updatedAt`) is actually newer than what was already accepted, allowing stale data to be treated as valid. The `WorkflowMetadataHandler`'s JWT anti-replay cache exhibits the same root-cause pattern: the "already used" record for a request is evicted from the cache using a freshness marker (`createdAt` + a fixed `cleanupPeriod`) that is completely decoupled from the actual validity window of the credential being tracked (the JWT's own `exp` claim). This can let an already-consumed, still-valid JWT be replayed once its cache record is purged.

### Finding Description
`Authorize` on the `WorkflowMetadataHandler` verifies an incoming request's JWT and then checks a local in-memory cache to prevent reuse of the same `jti`: [1](#0-0) 

The replay cache itself only stores `jti -> createdAt`, and its `cleanupOldEntries` purges entries strictly by comparing `createdAt` to a `cutoff`, with no reference at all to the JWT's actual expiry (`exp`) claim: [2](#0-1) 

The cache is constructed with a fixed `cleanupPeriod` sourced from `cfg.JWTReplayPeriodMs`, independent of the JWT verification logic: [3](#0-2) 

Separately, `VerifyRequestJWT` enforces its own, independently-configured `maxExpiryDuration` (default `maxJWTExpiryDuration`) as the upper bound on how long a token may remain valid between `iat` and `exp`: [4](#0-3) 

There is no code tying these two together — nothing enforces `JWTReplayPeriodMs >= maxJWTExpiryDuration`. If a caller obtains a JWT whose `exp` is set close to the maximum allowed lifetime, uses it once (consuming it, i.e., it gets `recordUsage`'d into the cache), and the cache's `cleanupPeriod` elapses before the token's own `exp`, the `jti` record is purged from the cache while the token is still cryptographically valid per `VerifyRequestJWT`. The same token can then be resubmitted and will pass both signature/claims validation and the (now-empty) replay check, since `isReplay` only inspects the *current* map contents rather than any monotonic/expiry-anchored state.

This is the direct analog of the reported bug: a "freshness"/"already-seen" decision is made against a rotated/reset piece of local state (the replay cache, akin to a new price "phase") without validating monotonicity against the actual validity horizon of the data being protected (the JWT `exp`, akin to `updatedAt`). Compare with the correctly-implemented pattern elsewhere in the same codebase, the Vault `RequestReplayGuard`, which explicitly derives its expiry from the token's own claims (`claims.ExpiresAt... + leeway`) rather than a fixed, unrelated interval: [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged client that can obtain a signed request JWT (per the documented protocol, any holder of a signing key authorized for a workflow) can replay an already-authorized gateway request after the cache eviction window passes but before the JWT's own expiry, bypassing the single-use/anti-replay guarantee the code is explicitly designed to provide. This is a concrete authentication/session-token bypass (replayed request impersonation) reachable from the internet-facing gateway's HTTP handler for workflow triggers.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: `JWTReplayPeriodMs` must be smaller than the effective JWT lifetime a client is permitted to request (bounded by `maxJWTExpiryDuration`/`WithExpiry` options). Because nothing in the code enforces or validates this relationship, misconfiguration silently reintroduces replayability without any error or warning, and the configuration surface (`cfg.JWTReplayPeriodMs`) is separate from the JWT max-expiry constant, making the misconfiguration easy to miss during deployment/tuning.

### Recommendation
Anchor replay-cache eviction to each token's own `exp` claim (as `RequestReplayGuard` already does for Vault), rather than a fixed, unrelated `cleanupPeriod`. At minimum:
- Store the token's `exp` (or `exp + leeway`) alongside `jti` when recording usage, and only purge an entry once `now > exp`.
- Add a startup-time invariant check that `JWTReplayPeriodMs >= maxJWTExpiryDuration` (or simply eliminate the independent config knob and derive purge timing from claims).

### Proof of Concept
1. Configure the gateway's `WorkflowMetadataHandler` with `JWTReplayPeriodMs` set smaller than the JWT expiry a caller can request (e.g., replay period = 10s, JWT `exp` = `iat` + `maxJWTExpiryDuration`, e.g. minutes).
2. Client crafts and signs a request JWT with a long-lived `exp` and calls the workflow-trigger endpoint; `Authorize` succeeds and `recordUsage(claims.ID)` stores `jti -> now`. [7](#0-6) 
3. After `cleanupPeriod` elapses (but before the token's `exp`), the periodic cleanup routine calls `cleanupOldEntries(cutoff)` and evicts the `jti` entry because `createdAt.Before(cutoff)`, even though the JWT itself is still valid. [8](#0-7) 
4. Client resubmits the exact same JWT/request. `VerifyRequestJWT` still accepts it (not expired), and `isReplay` returns `false` because the map entry was purged — the request is authorized a second time.

Note: I was unable to locate, within available tool iterations, the exact call site/interval that invokes `cleanupOldEntries` (it is referenced in `http_handler.go`, unexamined in this pass) and the concrete default values for `JWTReplayPeriodMs` vs. `maxJWTExpiryDuration`; confirming the default configuration actually satisfies `JWTReplayPeriodMs >= maxJWTExpiryDuration` in shipped configs would require further review of `http_handler.go` and the default TOML config for gateway capability handlers.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func newJWTReplayCache(cleanupPeriod time.Duration) *jwtReplayCache {
	return &jwtReplayCache{
		cache:         make(map[string]time.Time),
		cleanupPeriod: cleanupPeriod,
	}
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

// cleanupOldEntries removes expired entries from the cache
func (cache *jwtReplayCache) cleanupOldEntries(cutoff time.Time) int {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	var expiredCount int
	for jti, createdAt := range cache.cache {
		if createdAt.Before(cutoff) {
			delete(cache.cache, jti)
			expiredCount++
		}
	}
	return expiredCount
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
