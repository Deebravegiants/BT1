### Title
Biometric custody package (PCP) is uploaded to backend under the user's `signup_id`/`user_id` before enrollment success/lock is confirmed, with no rollback if enrollment fails - ([File: src/plans/mod.rs])

### Summary
The reported `swap-router` bug is a class of "sequential irreversible actions executed before an atomicity guarantee is obtained, with no way to cancel earlier actions if a later step fails." The orb-core signup pipeline in `do_signup` has an analogous flow: it builds and uploads the encrypted Personal Custody Package (PCP, containing the user's iris codes, iris/face images, and face embeddings) to the backend and only afterwards calls `enroll_user`, which is the step that actually determines whether the signup is accepted (via `signup_post`/`signup_poll`). There is no lock/reservation obtained before the irreversible upload, and no compensating action (delete/cancel) if enrollment subsequently fails.

### Finding Description
In `MasterPlan::do_signup` (`src/plans/mod.rs`), the pipeline executes in this order:
1. `build_pcp` builds the encrypted tier0/tier1/tier2 personal custody packages containing iris codes, normalized iris images, and face embeddings [1](#0-0) .
2. `upload_pcp_tier_0` immediately uploads tier0 (and, for `pcp_version >= 3`, tier1/tier2) to the backend, keyed by `signup_id` and `user_id`, via `backend::upload_personal_custody_package::request` [2](#0-1) [3](#0-2) .
3. Only after this upload does the code call `enroll_user`, which performs `signup_post`/`signup_poll` against the backend to actually determine success, duplicate/fraud detection, or failure [4](#0-3) [5](#0-4) .

This mirrors the `swap-router` defect precisely: an irreversible, sensitive operation (here, persisting encrypted biometric data tied to a real `user_id`/`signup_id` on the backend) is performed before the "commit" step (`enroll_user`/`signup_poll`) confirms the operation should proceed, and there is no lock/reservation mechanism and no rollback ("cancel all previously acquired locks") if the later step fails. If `enroll_user` returns `SignatureCalculationError`, `SignupVerificationNotSuccessful` (duplicate/fraud detected server-side), `ServerError`, or any other failure status, the PCP (biometric package) has already been durably persisted server-side under that `user_id`/`signup_id` [6](#0-5) . No cleanup/delete call for the already-uploaded PCP is issued in this failure path in `do_signup` or `after_signup` [7](#0-6) .

### Impact Explanation
Unlike the `swap-router` case where the loss is purely financial, here the impact is retention/disclosure of biometric data: encrypted iris/face biometric data associated with a specific user_id is written to backend storage regardless of whether the signup is ultimately confirmed, rejected, or detected as fraud/duplicate. This falls in the explicitly allowed "biometric data upload and retention" impact bucket. A user whose signup is rejected (e.g., detected as a duplicate person, fraud, or blocked software version) still has their PCP persisted server-side without a documented, code-enforced compensating deletion tied to enrollment failure, since the code never issues a corresponding "cancel"/delete call in `do_signup`'s failure branches.

### Likelihood Explanation
This is reachable by any legitimate user going through a normal signup flow that later fails enrollment (duplicate detection, software version issues, transient server/network errors during `signup_post`/`signup_poll`, or fraud flags) - no special privileges or attacker capability beyond completing biometric capture are required. `enroll_user::Plan::run` documents several such failure outcomes (`SignupVerificationNotSuccessful`, `ServerError`, `Error`, etc.) that occur strictly after the PCP has already been uploaded [8](#0-7) .

### Recommendation
Defer irreversible persistence of the biometric custody package until after enrollment is confirmed successful (i.e., invert the order: run `enroll_user`/`signup_post`+`signup_poll` first, and only upload/finalize the PCP once a success status is returned), or introduce an explicit two-phase mechanism: upload to a staging/pending location keyed by `signup_id`, and only "commit" (or otherwise explicitly delete/cancel) the package once `enroll_user::Status::Success` is confirmed. If a two-phase commit is not feasible given backend architecture, at minimum add a compensating deletion request for `signup_id`'s uploaded PCP tiers whenever `do_signup` returns via any failure path after `upload_pcp_tier_0`/tier1/tier2 succeeded.

### Proof of Concept
1. Complete a signup normally through biometric capture and pipeline (`biometric_capture`, `biometric_pipeline`) so that `build_pcp` succeeds and `upload_pcp_tier_0` uploads tier0 (and tier1/tier2 for pcp_version>=3) to the backend under the user's `signup_id`/`user_id` [2](#0-1) .
2. Force `enroll_user` to fail after the upload, e.g., cause the backend `signup_poll` to return `success: false` (duplicate/fraud) or `status: Failed`/`Error`, which `enroll_user::Plan::run` maps to `Status::SignupVerificationNotSuccessful` / `Status::ServerError` [9](#0-8) .
3. Observe that `do_signup` returns with `result.success = false` [10](#0-9) , but no request is made anywhere in `do_signup`/`after_signup` to delete or invalidate the already-uploaded PCP tiers for that `signup_id`, leaving the biometric package persisted on the backend for a signup that was never confirmed.

                        success: signup_result.success,
                        failure_feedback,
                    })
