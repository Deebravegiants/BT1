**Analysis:**

The premise misidentifies which side of the comparison is attacker-controlled. In `native_check_dispatch_type_compatibility_impl`, `lhs` corresponds to the Move-level `framework_function` argument, not the attacker-supplied dispatch target.

Tracing the actual call site in `fungible_asset::register_dispatch_functions`, the `lhs`/`framework_function` argument is always a hardcoded `FunctionInfo` constructed in-line with fixed values, e.g. `function_info::new_function_info_from_address(@aptos_framework, string::utf8(b"dispatchable_fungible_asset"), string::utf8(b"dispatchable_withdraw"))`, and the attacker only supplies the second argument (`dispatch_target`/`rhs`), which becomes the withdraw/deposit/balance hook candidate. [1](#0-0) 

The native function itself is also gated behind `public(friend) fun check_dispatch_type_compatibility`, so only friend modules (`fungible_asset`, and via `#[test_only]` the test module) can invoke it with a chosen `lhs`; unprivileged callers cannot supply an arbitrary `lhs` to this native at all. [2](#0-1) 

Since `dispatchable_withdraw`, `dispatchable_deposit`, `dispatchable_derived_balance`, and `dispatchable_derived_supply` are fixed native functions each declared with a non-empty parameter list (store/amount/transfer_ref/function, etc.), `lhs.param_tys()` can never actually be empty at any real call site — the `is_empty()` guard in `native_check_dispatch_type_compatibility_impl` is a defensive invariant check on framework-internal data, not a gate that attacker input can approach. [3](#0-2) [4](#0-3) 

The remaining boolean check (`rhs.is_public() && !rhs.is_native() && lhs_id != rhs_id`, plus type/ability/return-type equality against `lhs.param_tys()[0..lhs.param_count()-1]`) is exactly what constrains the attacker-controlled `rhs` (the actual hook candidate) to be a real, type-compatible, public, non-native Move function — this is the real custody-relevant guard, and it is unaffected by the `lhs` emptiness check. [5](#0-4) 

No unprivileged path exists to make `lhs` (the framework function side) attacker-controlled or zero-parameter, so the described bypass of `is_empty()` guard leading to registration of a malicious FA withdraw hook is not reachable. This does not cross a real custody boundary; it requires control over a value that is never attacker-supplied in any production call path.
