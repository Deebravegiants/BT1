### Title
Cross-token balance aliasing bypasses `Hinkal.transact`'s post-transfer solvency check, minting unbacked shielded UTXOs - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` snapshots balances for the **entire** `erc20TokenAddresses` array once before running `_internalTransact`/`_externalTransact` and once after, then checks per-index that `balanceDif == amountChanges[i] + utxoAmount` [1](#0-0) . Because this check trusts each `erc20TokenAddresses[i]` to represent an independent real-value silo purely via `balanceOf`, an attacker can deploy a second token contract `B` whose `balanceOf` mirrors a real token `A`'s balance while its `transferFrom` is a no-op, causing one real deposit of `A` to also satisfy the balance-diff check for the unrelated slot `B`, letting the attacker mint an output UTXO for `B` with zero real backing.

### Finding Description
The equality the protocol relies on is:
`newBalances[i] - oldBalances[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` for every index `i`, computed from a single batch snapshot taken before and after all transfers in the call [2](#0-1) . This is intended to guarantee that "net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)", but the check is done via two independent `getBalancesForArray` calls per address, using `balanceOf`, which is only correct if each address's reported balance change is caused solely by transfers addressed to that specific token [3](#0-2) .

Root cause and exploit flow:
1. Attacker deploys token `B` where `B.balanceOf(x) == A.balanceOf(x)` for a real, valuable token `A` (e.g., `B` simply forwards `balanceOf` reads to `A`), and `B.transferFrom(...)` is a no-op that always returns `true` without moving any real value or touching `A`'s storage.
2. Attacker crafts a `CircomData` for `Hinkal.transact` (internal path, `externalActionData.externalActionId == 0`) with `erc20TokenAddresses = [A, B]`, `amountChanges = [+N, +N]`, zero input nullifiers for both (fresh deposits), and off-chain output commitments of amount `N` for each of `A` and `B`. The circuit's `distinctErc20AddressChecks` only rejects literally identical addresses, so `A != B` passes trivially even though they alias the same underlying value [4](#0-3) .
3. `Hinkal.transact` takes `oldBalances = getBalancesForArray([A,B])` before any transfer [5](#0-4) .
4. `_internalTransact` runs both deltas: for `A`, it does a real `transferERC20TokenFromOrCheckETH` pulling `N` real tokens from the attacker [6](#0-5) ; for `B`, it calls the same function which invokes `B.transferFrom(attacker, hinkal, N)` — a no-op that moves nothing real.
5. `newBalances = getBalancesForArray([A,B])` is taken after both calls [7](#0-6) . Because `B.balanceOf` mirrors `A`, `newBalances[B] - oldBalances[B] == N` even though no real `B`-labeled value entered the contract.
6. The per-index check `balanceDif == amountChanges[i] + utxoAmount` passes for **both** `A` (genuinely) and `B` (spuriously) [8](#0-7) , and the circuit-side constraint `inTotal + amountChanges[i] === outTotal` is self-consistently satisfiable by the attacker for `B` since it never inspects real-world backing [9](#0-8) .
7. `insertCommitments` then mints a legitimate shielded output UTXO of amount `N` labeled with `erc20Address = B` [10](#0-9) , entirely unbacked by real value transferred into Hinkal.

None of the existing guards catch this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array-length and structural consistency, not real-world balance correlation between distinct addresses [11](#0-10) ; `verifyProof` and the circuit constraints validate only internal accounting per declared token index, with no linkage to actual `balanceOf` semantics; `rootHashExists`/nullifier checks are irrelevant to fresh deposits. Note that `prooflessDeposit`'s per-token `_handleTransfersFromProoflessDeposit` is NOT vulnerable to this because it takes an isolated `balanceBefore`/`balanceAfter` snapshot around each individual token's transfer sequentially [12](#0-11) , so the aliasing benefit from a prior token's real transfer is already baked into the "before" snapshot of the next token and cannot manifest as a fresh matching delta. The vulnerability is specific to `Hinkal.transact`'s batched before/after snapshot pattern.

### Impact Explanation
The attacker mints a shielded UTXO labeled with an arbitrary "distinct" token address backed by zero real value, for the cost of a single genuine deposit of a different token whose balance the malicious token mirrors. This directly matches "minting shielded value without backing (protocol insolvency)" — Critical severity. The unbacked UTXO can later be spent/withdrawn like any legitimate note (subject to whatever real transfer function the attacker gives `B` for withdrawals, or simply left as a phantom credit that permanently unbalances the vault's accounting versus its liabilities), and the technique is repeatable per deposit and per newly-deployed alias token.

### Likelihood Explanation
The attacker needs only to: deploy a simple malicious ERC20-like contract with `balanceOf` proxying an existing real token and a no-op `transferFrom`, and craft a valid Circom proof for their own fresh UTXOs (fully permitted since they are not the owner or a privileged role and can freely construct `CircomData`, `Dimensions`, and deposit arrays). No relayer collusion or victim funds are required — this is a pure single-transaction, self-contained exploit with attacker-controlled state end-to-end. Feasibility is high and cost is limited to gas plus the one real deposit of `A`.

### Recommendation
Do not rely solely on aggregate `balanceOf` snapshots taken over the full `erc20TokenAddresses` array to authorize per-index minted value. Instead, either (a) perform isolated balance-before/transfer/balance-after checks per token index inside `_internalTransact`/`_externalTransact` immediately around that index's own transfer (mirroring the pattern already used in `_handleTransfersFromProoflessDeposit`), so no other token's transfer can be attributed to an unrelated index, or (b) require and enforce that each `erc20TokenAddresses[i]` is added to a registry of vetted, non-aliasing tokens before it can be used to back a deposit-minted UTXO.

### Proof of Concept
Foundry test plan:
1. Deploy real ERC20 `TokenA` (mintable) and give attacker `N` tokens; deploy malicious `TokenB` whose `balanceOf(addr)` returns `TokenA.balanceOf(addr)` and whose `transferFrom`/`transfer` are no-ops returning `true`.
2. Attacker approves `Hinkal` to spend `N` of `TokenA`.
3. Build `CircomData` with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [N, N]`, zero nullifiers, `onChainCreation = [false, false]`, `slippageValues = [0,0]`, and valid off-chain output commitments of `N` each for `TokenA` and `TokenB`, with a real proof generated locally for this statement.
4. Call `hinkal.transact(a, b, c, dimensions, circomData)`.
5. Assert: `TokenA.balanceOf(hinkal)` increased by exactly `N` (one real deposit); assert two output commitments were inserted, one for `TokenA` amount `N` and one for `TokenB` amount `N`; assert `TokenB` never had any real value transferred to `Hinkal` (attacker's off-chain accounting of `TokenB` remains `0` outside the mirrored proxy).
6. This demonstrates `sum(amountChanges) == 2N` credited while only `N` in real value entered Hinkal, i.e., `balanceDif[TokenB] == amountChanges[TokenB] + utxoAmount[TokenB]` holds on-chain while `TokenB`'s vault balance delta is `0` real-value-backed — violating the invariant `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)`.
