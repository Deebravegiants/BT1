## Title
Webhook shop/topic identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler with the `shop` domain taken from the request headers. In reality, the HMAC only authenticates the raw request body — the `shop`, `topic`, `webhook_id`, and `api_version` header values are never included in the signed material, so any holder of one valid `(body, hmac)` pair can relabel it as coming from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string`: [2](#0-1) 

`Registry.process` only checks this body-only HMAC, then trusts `request.shop` (parsed straight from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, with no cross-check against the HMAC or against any known/authorized shop) and forwards it into the handler as the identity of the sending tenant: [3](#0-2) [4](#0-3) 

The equality that should hold is: `bytes covered by HMAC == bytes the handler treats as authenticated (topic + shop + body)`. Here, `bytes verified by HMAC (raw_body only) != bytes acted on (shop, topic, webhook_id headers)` — the shop/topic identity fields are acted upon (passed to `WebhookMetadata` and the app handler) without being bound to the signature that supposedly proves the request "came from Shopify."

The gem's own documentation reinforces the false assumption that verification covers the whole request, and instructs developers to use `data.shop` directly as the trusted tenant identifier: [5](#0-4) [6](#0-5) 

### Impact Explanation
An unprivileged internet user who is themselves a legitimate (or even a free/trial) merchant of the app receives genuine webhooks for their own store, each with a correctly computed body/HMAC pair (since HMAC only covers the body and the attacker controls the body content of their own shop's events, e.g. by editing a product with attacker-chosen field values). The attacker can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the shop header), and the app's handler receives `WebhookMetadata` claiming the (attacker-crafted) body belongs to the victim shop, per the documented usage pattern that keys stored records off `data.shop`. This is a cross-tenant data-confusion/injection primitive: an app that stores webhook payloads keyed by `data.shop` (exactly as the gem's own example code does) can be made to persist or act on attacker-controlled data under another merchant's tenant identity.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged install — no special access token, secret, or privileged account needed) can trivially generate valid `(body, hmac)` pairs for their own shop and replay them under a spoofed shop header. No cryptographic secret needs to be known or broken; the only requirement is one legitimate installation, which is the gem's intended, unprivileged usage path.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the material that is HMAC-verified (or otherwise cryptographically bind them to the signed body), and update `Registry.process`/documentation to make clear that only the body is currently authenticated, or better, verify that `request.shop` matches an expected/authorized shop before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker crafts `B` to contain whatever data they want (e.g., by triggering the webhook via their own store actions), so `H` is fully known/reproducible by them for that `B`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, the valid `H` header, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate`, which only checks `H` against `B` — this succeeds regardless of the shop header, per `lib/shopify_api/webhooks/request.rb` line 36-38 and `lib/shopify_api/utils/hmac_validator.rb` line 26-31.
5. The app's handler executes with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: B, ...)`, causing the attacker-controlled body to be processed/stored as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
