### Title
Webhook `shop-domain` header is trusted without HMAC coverage, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` value it hands to the application's webhook handler is read from the `x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed content. Any party who can produce one validly-signed webhook body (e.g., an attacker who owns their own Shopify development store and registers a webhook against the same multi-tenant app) can replay that exact body/HMAC pair while swapping the `shop-domain` header to any other value, causing the app to process the payload as if it belonged to a different, victim shop.

### Finding Description
The webhook HMAC binding is defined in `Utils::HmacValidator`: [1](#0-0) 

`validate_signature` computes the HMAC only over `verifiable_query.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, that method returns just the raw body: [2](#0-1) 

Meanwhile, `shop` (and `topic`, `api_version`, `webhook_id`) are parsed straight from HTTP headers, completely outside the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` to the application handler as the tenant identity for the event: [4](#0-3) 

The equality the code should enforce is: `shop authenticated by Shopify == shop acted on by the handler`. Because `shop` is not part of `to_signable_string`, the binding is broken: `HMAC(raw_body)` proves only "this body was signed with the app's secret for *some* topic," not "this body concerns shop X." An attacker who can obtain any valid `(raw_body, hmac)` pair for the app — trivially available to anyone who installs the app on their own store and receives one webhook — can present that identical pair with an arbitrary `x-shopify-shop-domain` header value naming a different (victim) shop, and the gem will treat the payload as authentic for that victim shop.

### Impact Explanation
This breaks the multi-tenant isolation the HMAC check is supposed to provide. Depending on what the host application's webhook handlers do with `WebhookMetadata#shop` (e.g., look up a stored session/access token for that shop, delete data on `shop/redact` or `app/uninstalled`, mark a shop's subscription/billing state, invalidate sessions, etc.), an attacker with a self-service Shopify store can trigger actions attributed to a shop they do not own — a cross-tenant access/confusion primitive achieved purely with unauthenticated internet access, matching the "cross-tenant access" Critical-impact category in scope.

### Likelihood Explanation
Any developer/attacker can freely create a Shopify partner/development store, install the target app, and receive at least one legitimately HMAC-signed webhook body for a topic of their choosing (bodies for topics like `app/uninstalled` are often near-empty/predictable, making the exact `raw_body` easy to reuse). Replaying that raw body with a forged `shop-domain` header requires no secret knowledge and no privileged access — only the ability to POST an HTTP request to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cross-check the header-derived `shop` against an independently-trusted source (e.g., re-derive/verify the shop domain via `ShopifyAPI::Utils::ShopValidator` and correlate it against the registered webhook/topic metadata or a stored session) before invoking the handler in `ShopifyAPI::Webhooks::Registry.process`. At minimum, document that host applications must not trust `WebhookMetadata#shop` for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers a webhook for a topic such as `app/uninstalled`.
2. Shopify delivers a request to the app's webhook endpoint with headers including `x-shopify-hmac-sha256: <valid HMAC over raw_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value (the body for many topics is static/predictable, e.g. `{}`).
4. Attacker sends their own POST directly to the app's public webhook endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes (it only checks the body/HMAC pair), then invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to act on the victim shop's behalf/data.
