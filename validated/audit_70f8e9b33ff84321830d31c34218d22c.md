### Title
Stale operator authorization reused for up to 23 hours without re-validating with backend "oracle" - (File: src/plans/mod.rs)

### Summary
`RewardsManager.getAccruedYield()` computed a financial figure from strategy share balances without calling `_tryUpdateOracle()` first, so it trusted a potentially stale on-chain price oracle instead of refreshing it before use. The orb-core signup flow has the same root-cause pattern: the operator's authorization ("valid") status is fetched once from the backend "oracle" (`backend::operator_status::request`) at QR-scan time, cached into `OperatorData`, and then reused as the sole authorization gate for a full signup session — for up to `operator_qr_expiration_time` (23 hours by default) — without ever re-querying the backend to confirm the operator is still authorized.

### Finding Description
When an operator QR code is scanned, `verify_operator_qr_code` calls the backend once via `backend::operator_status::request(qr_code)` and, if `valid == true`, returns the operator's `LocationData` together with a local `Instant::now()` timestamp stored in `OperatorData` [1](#0-0) .

This `OperatorData` (and its `timestamp`) is then reused, without any additional backend call, as the trust anchor for subsequent signups as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time` in `scan_remaining_qr_codes`: [2](#0-1) 

and similarly in `scan_initial_qr_codes` for self-serve mode: [3](#0-2) 

The only "freshness" check performed is an elapsed-time comparison against `operator_qr_expiration_time`, which defaults to 23 hours: [4](#0-3) 

There is no call back to `backend::operator_status::request` (the authoritative "oracle" for operator authorization/validity/location) at any point during that window — unlike the price-oracle example in the report, where `LevelMintingV2` explicitly refreshes before reading. The `Status` returned by the backend explicitly encodes revocation via `valid`/`reason` fields [5](#0-4) , but this state is never re-checked once cached.

### Impact Explanation
If an operator's authorization is revoked, or their permitted location/status changes at the backend mid-session, the orb continues to trust the stale cached `OperatorData` and will proceed with new signups under that operator's authority for up to the full `operator_qr_expiration_time` window (23 hours by default, or a shorter self-serve-configured value) instead of re-validating with the backend. This is a signup-authorization staleness issue analogous to the oracle staleness in the report: state that should gate a sensitive action (starting/attributing a signup to an operator) is cached and reused without refresh from its authoritative source.

### Likelihood Explanation
This occurs automatically in every normal operation cycle once an operator QR code has been scanned and accepted — no attacker action beyond normal device operation is required; the risk window is bounded only by the configured expiration duration, which defaults to a long 23-hour period.

### Recommendation
Re-validate operator authorization against the backend (`backend::operator_status::request`) before trusting cached `OperatorData` for a new signup, rather than relying solely on the local elapsed-time check in `scan_remaining_qr_codes`/`scan_initial_qr_codes`. At minimum, shorten the reuse window or add periodic re-validation so a backend-side revocation of an operator's authorization takes effect promptly.

### Proof of Concept
1. Operator scans their QR code; `verify_operator_qr_code` succeeds and caches `OperatorData { timestamp: Instant::now(), .. }`.
2. Backend revokes/invalidates that operator (e.g., `Status.valid` becomes `false`) shortly after.
3. Within `operator_qr_expiration_time` (up to 23h), `scan_remaining_qr_codes` still matches the `operator_data.timestamp.elapsed() < operator_qr_expiration_time` branch and proceeds directly to `scan_user_qr_code` without ever calling `backend::operator_status::request` again, allowing signups to continue under the now-invalid operator authorization.

    async fn verify_operator_qr_code(
        &self,
        orb: &mut Orb,
        qr_code: &qr_scan::user::Data,
        qr_capture_start: Instant,
    ) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
        if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
            return Ok(Some((0, backend::operator_status::LocationData {
                team_operating_country: "DEV".to_string(),
                session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
                stationary_location_coordinates: None,
            })));
        }
        let http_start = Instant::now();
        match backend::operator_status::request(qr_code).await {
            Ok(backend::operator_status::Status { valid: true, location_data, reason: _ }) => {
                let location_data = location_data
                    .expect("to always have a result from the backend if valid == true");
                orb.ui.qr_scan_success(QrScanSchema::Operator);
                dd_incr!("main.count.global.distr_code_validated");
                tracing::info!("Operator QR-code validated: {qr_code:?}");
                dd_timing!("main.time.signup.distr_qr_code_capture", qr_capture_start);
                return Ok(Some((http_start.elapsed().as_millis() as u64, location_data)));
            }
            Ok(backend::operator_status::Status { valid: false, .. }) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
                dd_incr!("main.count.signup.result.failure.distr_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
            }
        }
        Ok(None)
