### Title
Webhook shop-domain and topic are trusted for tenant routing without HMAC coverage - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by HMAC-verifying the raw body, then dispatches to the handler using the `shop` and `topic` values read directly from unauthenticated HTTP headers.

### Finding Description
The identity binding that should hold is: `shop value authenticated by HMAC == shop value used to route/attribute the webhook`. In this gem that equality does not hold.

`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, none of which participate in the signed string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately uses the unauthenticated header-derived `request.shop` and `request.topic` to select and invoke the handler: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the raw body only) using the app's single, global `Context.api_secret_key`, which is shared across every shop that installs the app: [4](#0-3) 

Because the secret is app-wide (not shop-specific) and the HMAC covers only the body, any entity that can obtain one validly-signed webhook body for the app (e.g., by installing the app on their own shop and receiving genuine webhooks from Shopify) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`) header. `HmacValidator.validate` will still return `true` since it only checks the body bytes, and `Registry.process` will hand the attacker-controlled body to the handler tagged with a victim shop's domain.

### Impact Explanation
This breaks the tenant boundary the host application relies on: the webhook body is proven authentic ("came from Shopify, signed with our secret") but the shop it's attributed to is not. A host application that uses `WebhookMetadata#shop` to look up per-shop state (e.g., load that shop's session/access token, write to that shop's tenant records, or trigger shop-scoped side effects) can be made to process attacker-supplied body content under another tenant's identity — a cross-tenant access primitive that fits the Critical severity bucket for cross-tenant access.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one app-signed webhook body, which any user who installs the app on their own store legitimately receives from Shopify. From there, replaying the same body with a forged `x-shopify-shop-domain` header against the same public webhook endpoint is trivial and repeatable (topic and delivery contents are attacker-influenceable to the extent Shopify lets a merchant control their own store data, e.g. product/order webhooks). No access token, `client_secret`, or privileged account is needed beyond the ordinary ability to install the app on a shop the attacker controls.

### Recommendation
Bind the header-derived `shop` (and ideally `topic`) into the signed material, or otherwise cryptographically tie them to the verified payload — e.g., include them in the signable string, or require host applications to cross-check `request.shop` against an independently verified session/shop record before trusting `WebhookMetadata#shop` for tenant-scoped actions. At minimum, document prominently that `request.shop`/`request.topic` are not covered by the HMAC and must not be used as an authenticated tenant identifier without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger an event so Shopify sends a legitimately HMAC-signed webhook, e.g. body `{"id":1,...}` with header `x-shopify-hmac-sha256: <valid>`.
2. Capture the raw body and its valid HMAC value (both travel over the wire to the attacker's own endpoint, so the attacker legitimately has them).
3. Replay the identical `raw_body` and `hmac-sha256` header to the same webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and optionally change `x-shopify-topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key`.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the host app to act on attacker data under the victim shop's identity.

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
