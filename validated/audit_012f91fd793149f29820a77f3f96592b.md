## Title
Unbounded scrypt parameters from decoded metadata enable DoS in unlock/import flow - ([File: libraries/secure-container/src/crypto.js])

## Summary
The `decrypt()` flow in `secure-container` decodes attacker-supplied metadata (including scrypt `n`, `r`, `p` as raw `UInt32BE` values) and passes them unvalidated into `stretchPassphrase`/`scrypt()` before any authentication succeeds. No bound is enforced on `n`/`r`/`p`, or on the derived memory cost `n*r*p`, allowing a crafted imported file to force scrypt to allocate huge memory / run for a long time.

## Finding Description
`index.js`'s `decrypt()` calls `conMetadata.decode(fileObj.metadata)` then immediately `conMetadata.decryptBlobKey(metadata, passphrase)` [1](#0-0) . `metadata.decode` just runs `struct.decode()` over the varstruct schema where `n`, `r`, `p` are plain `UInt32BE` fields with no range checks [2](#0-1) . `decryptBlobKey` forwards `metadata.scrypt` straight into `boxDecrypt` [3](#0-2) , which merges it with defaults and calls `stretchPassphrase` [4](#0-3) . `stretchPassphrase` passes `n`, `r`, `p` directly into `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')` with zero validation of magnitude or `n*r*p` product [5](#0-4) . Since `n`, `r`, `p` are each `UInt32BE` (up to ~4.29e9), an attacker constructing an import file can set these to extreme values, and this executes before the passphrase is validated (scrypt itself performs the "validation" by producing a wrong key on wrong passphrase — i.e., the expensive computation happens regardless of whether the passphrase is correct).

## Impact Explanation
This causes worker/main-thread CPU exhaustion and multi-gigabyte memory allocation attempts when a user attempts to import/open a crafted `.seco` container, degrading or crashing the unlock/import flow (availability impact). This is a legitimate, reachable DoS surface for any flow that accepts untrusted imported secure-container files (e.g., wallet backup import), scoped strictly to availability degradation of the decrypt path — it does not by itself leak secrets or bypass authentication. Whether this reaches a live wallet-unlock code path (vs. only backup/keyval import tooling used in this repo) is not fully confirmed from the code available; the `secure-container` package here appears used mainly for backup/keyval-style import/export (`seco-keyval`, `seco-file` test helpers) [6](#0-5) , rather than confirmed as the primary wallet unlock/lock-state gate — so "blocking legitimate lock-state checks" as stated in the question is speculative beyond this library's own scope.

## Likelihood Explanation
Feasibility is high and requires no privilege: an attacker only needs to get the victim to import/open a crafted container file (deeplink/file import), a normal reachable user action. The vulnerable code path (`decode` → `decryptBlobKey` → `boxDecrypt` → `stretchPassphrase` → `scrypt`) has no size checks anywhere in this library, so the exploit is deterministic and repeatable, not probabilistic.

## Recommendation
Add explicit bounds checking in `createScryptParams`/`stretchPassphrase` (e.g., cap `n` to a power-of-two ≤ 2^20, `r` ≤ 8, `p` ≤ 1, and enforce `n*r*p ≤` a fixed ceiling) and validate these bounds in `metadata.decode` before any scrypt call, rejecting out-of-range values with a clear error rather than invoking `scrypt()`.

## Proof of Concept
Unit test in `libraries/secure-container/src/__tests__/crypto.test.js`:
```js
test('stretchPassphrase should reject oversized scrypt params', async (t) => {
  t.plan(1)
  const passphrase = 'x'
  const salt = Buffer.alloc(32)
  // huge n*r*p, decodable via UInt32BE from a crafted metadata blob
  const scryptParams = { salt, n: 2 ** 24, r: 255, p: 255 }
  await t.rejects(
    () => scCrypto.stretchPassphrase(passphrase, scryptParams),
    /scrypt params exceed allowed bound/,
    'oversized scrypt params should be rejected before calling scrypt()'
  )
})
```
Expected (current behavior, showing the bug): the call proceeds into `scrypt()` without rejection and either hangs/OOMs or takes excessive time/memory — demonstrating no upper bound is enforced prior to invocation, contrary to the desired invariant.

```javascript
export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
```
