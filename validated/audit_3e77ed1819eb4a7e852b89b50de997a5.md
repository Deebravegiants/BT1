## Finding

### Title
Wrapped bridge token send() dispatches the nominal amount instead of actual tokens received, causing under-collateralization for fee-on-transfer/rebasing underlying tokens - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks `params.amount` of the underlying ERC20 via `safeTransferFrom`, but blindly encodes that same nominal `params.amount` into the cross-chain message body that authorizes an equal unlock on the destination side. If the underlying token has variable transfer/balance semantics (fee-on-transfer, rebasing, or any deflationary/inflationary balance token), the contract actually receives less (or more) than `params.amount`, but the dispatched message always commits to unlocking the full nominal amount, leading to reserve insolvency.

### Finding Description
In `send()`: [1](#0-0) 

the contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then builds the dispatch message with `_buildDispatchPost(params)`, which encodes `params.amount` verbatim as `HyperFungibleToken.Message.amount`: [2](#0-1) 

Unlike a spot-balance based accounting, the code never measures the actual balance delta (`balanceOf(address(this))` before/after) to determine how much was truly locked. For a fee-on-transfer or rebasing-down token, the wrapper's true underlying balance grows by less than `params.amount`, yet the message that reaches the destination-chain (or a later `onPostRequestTimeout` refund) commits to unlocking exactly `params.amount`: [3](#0-2) [4](#0-3) 

This is precisely the reported bug class: the contract's accounting is based on the nominal transferred amount rather than the actual balance received, so the contract's real token holdings and its committed unlock obligations drift apart over repeated `send()` calls. Note that the codebase's own `IntentGatewayV2` explicitly guards against this exact issue by measuring `balanceOf` deltas before/after transfers and mutating `order.inputs[i].amount` to the actually-received value (see `evm/src/apps/IntentGatewayV2.sol` lines 292-306 and 313-323), demonstrating the project is aware of and defends against fee-on-transfer/variable-balance tokens elsewhere — but `WrappedHyperFungibleToken` (and its upgradeable variant `WrappedHyperFungibleTokenUpgradeable.sol`) lacks this same correction.

### Impact Explanation
Because every `send()` call over-commits relative to what is actually escrowed when the underlying token has fee-on-transfer or negative-rebase behavior, the wrapper's on-chain underlying balance becomes insufficient to satisfy the sum of all outstanding unlock/refund obligations. This manifests as:
- Later legitimate `onAccept` unlocks or `onPostRequestTimeout` refunds reverting due to insufficient underlying balance (DoS on withdrawal), since `safeTransfer(beneficiary, message.amount)` will fail once reserves are depleted.
- Effectively an "unbacked" claim: earlier users can fully redeem while later users cannot, causing permanent freezing/loss of funds for the users left unable to redeem.

This satisfies the required impact bar of concrete freezing/loss of funds via the token-bridge lock/unlock accounting path, reachable by any ordinary user calling `send()` — no privileged role required.

### Likelihood Explanation
The vulnerability is triggered simply by an owner configuring (or being configured with) an underlying ERC20 with fee-on-transfer or rebasing semantics — a common token category (e.g., many yield-bearing/rebasing tokens, tax tokens) — and then any regular user calling `send()`. No malicious admin/governance action is required to trigger the loss once such a token is in use; a single ordinary `send()` transaction begins the under-collateralization, and repeated sends accumulate the deficit until unlocks start failing.

### Recommendation
Measure the actual balance received by diffing `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call in `send()`, and use that measured amount (not `params.amount`) when building the dispatch message, mirroring the pattern already used in `IntentGatewayV2.placeOrder()`. Alternatively, explicitly disallow non-standard-balance ERC20s as configured `_underlying` tokens, and document/enforce this restriction in `configure()`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer token (e.g., 1% fee on transfer, similar to the `FeeOnTransferToken` test helper already present in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).
2. User calls `send({amount: 1000e18, ...})`. `safeTransferFrom` moves 1000e18 nominal, but the contract's underlying balance only increases by 990e18 (1% fee taken).
3. `send()` still dispatches a message committing to unlock `1000e18` on the destination side (or in a timeout refund).
4. Repeat `send()` for multiple users; the wrapper's real underlying balance is always 1% short of the sum of dispatched amounts.
5. Eventually, an `onAccept`/`onPostRequestTimeout` call attempts `safeTransfer(beneficiary, message.amount)` for the full nominal amount and reverts due to insufficient underlying balance, freezing funds for that beneficiary while earlier beneficiaries were paid in full. [5](#0-4)

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    /**
     * @notice Handles incoming cross-chain token transfer messages
     * @dev Called by the ISMP host when a POST request is received. Verifies the source
     * address matches the configured contract for that chain, then transfers the underlying
     * ERC20 to the recipient. If calldata is present, executes it via the CallDispatcher.
     * @param incoming The incoming POST request containing the token transfer message
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
