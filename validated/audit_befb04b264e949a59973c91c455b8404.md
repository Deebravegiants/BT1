Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by HMAC-validating the raw request body, then trusts the `shop` and `topic` values taken from HTTP headers that are excluded from that signature, to route and identify the tenant for the handler call.

### Finding Description
The identity binding that should hold is:

`bytes verified (HMAC input)` == `bytes the app acts on for tenant/topic identity`

In `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read directly from HTTP headers, entirely outside the signed payload: [2](#0-1) .

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which only checks `request.to_signable_string` (the body) against the HMAC — and then, without any further cross-check, uses the header-derived `request.topic` for handler lookup and `request.shop` for tenant identity passed into the handler: [3](#0-2) . `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body), never touching headers: [4](#0-3) .

Because the HMAC only binds the body bytes, and the equality that should hold — "identity used by the app" == "identity covered by the signature" — is broken, any raw body + valid HMAC pair (which an attacker can obtain by receiving one legitimate webhook, e.g. to their own trial/dev shop) can be resent directly to the app's public webhook endpoint with an attacker-chosen `x-shopify-shop-domain` header and/or `x-shopify-topic` header. The HMAC check still passes because it only re-derives the signature over the untouched body. The `WebhookMetadata.shop` field handed to the app's `WebhookHandler#handle` is therefore attacker-controlled despite having passed "HMAC validation": [5](#0-4) . There is no `webhook-id` replay/dedup check in `process` either, so the same signed body can be resent indefinitely under different spoofed shop/topic headers.

### Impact Explanation
Apps built on this gem commonly key tenant-scoped side effects (updating local per-shop records, triggering uninstall/GDPR cleanup, billing state changes, etc.) directly off `WebhookMetadata.shop`, believing the whole `Request` object was "HMAC verified." Because `shop` is not actually part of the signed material, an attacker who has captured any one valid `(body, hmac)` pair can impersonate an arbitrary other shop in the app's webhook processing — i.e., cross-tenant data manipulation using a genuine Shopify-issued signature captured from an unrelated event. This matches the "cross-tenant access" Critical-impact category, since the gem's own `Registry.process`/`Request` API is what feeds this unauthenticated header value to app code as if it were verified.

### Likelihood Explanation
Exploitability requires only: (1) a publicly reachable webhook endpoint (standard for embedded/public Shopify apps), and (2) possession of one legitimately-signed body+HMAC pair, which is trivial to obtain by installing the target app on any shop the attacker controls and subscribing to any webhook topic, then replaying that exact body to the same endpoint with forged `shop-domain`/`topic` headers. No access to `api_secret_key`, tokens, or privileged accounts is needed — only unprivileged internet access to the app's public webhook URL.

### Recommendation
Bind the header-derived identity fields into the signable string (or otherwise cryptographically bind them), e.g. include `shop`, `topic`, and `webhook_id` in the HMAC input, or require the app-supplied endpoint to independently confirm the `shop` against a registered webhook subscription/session store before trusting `WebhookMetadata.shop`. At minimum, document prominently that `Request#shop`/`Request#topic` are NOT covered by the HMAC and must not be trusted without additional binding, and add webhook-id based replay protection in `Registry.process`.

### Proof of Concept
1. Install the target app (or any app using this gem) on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` sent to the app's webhook endpoint.
2. Confirm `H == Base64(HMAC-SHA256(client_secret, B))` — this is exactly what `HmacValidator.validate` re-derives from `to_signable_string` (`B`) alone: [6](#0-5) .
3. Resend an HTTP POST to the same app webhook endpoint with the identical body `B` and `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com` and (optionally) a different `x-shopify-topic`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only `B` is checked: [7](#0-6) . The handler then receives `WebhookMetadata` with `shop: "victim.myshopify.com"` populated from the forged header: [8](#0-7) , despite the app believing this request was fully authenticated for that shop.
