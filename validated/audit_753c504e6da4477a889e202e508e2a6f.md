### Title
Non-embedded session identity is a fully deterministic, unauthenticated cookie value used as the storage key for OAuth tokens - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
The external report describes an accounting system where an object's identity/key is split without updating the mechanism that binds reclamation logic to that key, so a lookup ends up operating on the wrong epoch. The reachable analog in this gem is the non-embedded session flow: the "session id" written into and read from the browser cookie is a fully deterministic string derived only from public information (`shop` domain, and for online sessions the numeric `associated_user` id) and carries no cryptographic binding (no HMAC/signature) to prove it was actually issued to the requester who presents it.

### Finding Description
For non-embedded apps, `ShopifyAPI::Utils::SessionUtils.current_session_id` reads the session id straight out of the `shopify_app_session` cookie value with no verification: [1](#0-0) 

That cookie is set during OAuth completion to `session.id`, and `SessionCookie` itself carries no signature — it is a plain `name`/`value`/`expires` struct: [2](#0-1) 

The session id values are constructed deterministically from public inputs: [3](#0-2) 

For an offline (store-level) session the id is literally `"offline_#{shop}"`, where `shop` is the merchant's `*.myshopify.com` domain — public, guessable information, not a secret. For an online session it is `"#{shop}_#{user_id}"`, where the numeric Shopify user id is also frequently discoverable (e.g., via storefront/App proxy responses or other app UI).

In `Oauth.validate_auth_callback`, this same predictable id is written into the outgoing cookie: [4](#0-3) 

The documented integration pattern instructs the host app to key its access-token store by this id: [5](#0-4) 

The bug-class parallel to the report: `split_by_epoch`'s accounting bug let an operation act on the *wrong epoch* because the object's tracked location was decoupled from the actual object after a split. Here, the equality that should hold is `session_id (as verified by the app) == session_id (bound to the authenticated OAuth flow that produced it)`. Because `cookie_session_id` returns the raw, unsigned cookie value unconditionally, and that value-space is fully deterministic/public, this equality can be trivially forged: any party who can set an arbitrary cookie value in the browser context (e.g., because the host app's cookie is not `SameSite=strict`+`Secure`+`HttpOnly` in every deployment, or via a sibling-subdomain/cookie-tossing primitive on the same registrable domain) can present `"offline_<any-known-shop>.myshopify.com"` as their own session id.

### Impact Explanation
If the host application follows the gem's own documented pattern (`SessionRepository.retrieve(session_id)` → look up stored `access_token` by this id, as shown in `docs/usage/oauth.md` and `BREAKING_CHANGES_FOR_V16.md`), then possession of the raw string `offline_<shop>.myshopify.com` — with no proof of having completed OAuth for that shop — is sufficient to have the app's `current_session_id` resolve to another merchant's stored offline access token. That token is then used to make authenticated Admin API calls on the attacker's behalf against a shop they do not control: cross-tenant access to another merchant's store data using the app's real merchant access token.

### Likelihood Explanation
This requires a way to set/override the cookie value in the victim's browser for the app's own origin (cookie injection, cookie tossing from a subdomain, or an app deployment that doesn't enforce the `secure`/`http_only` attributes exactly as shown in the docs). It does not require the attacker's own OAuth completion, the `client_secret`, or any leaked token — only knowledge of a target shop's domain, which is public. This is a plausible but conditional path (it depends on cookie-scoping conditions outside this gem's direct control), so likelihood is moderate rather than trivial.

### Recommendation
Do not treat the raw cookie value as an authenticated identity. Bind the session cookie to the issuing OAuth transaction cryptographically (e.g., sign/HMAC the cookie value with `Context.api_secret_key`, or store an opaque random session id rather than a value deterministically derived from `shop`/`user_id`) so that `cookie_session_id` can verify integrity/origin before returning it from `current_session_id`.

### Proof of Concept
1. Attacker learns the target's shop domain `victim.myshopify.com` (public/guessable).
2. Attacker forces their own browser's cookie jar for the vulnerable app's origin to contain `shopify_app_session=offline_victim.myshopify.com` (via a cookie-setting primitive on the app's domain/subdomain).
3. Attacker visits an app route that calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim.myshopify.com"` verbatim, per [1](#0-0) .
4. The host app's `SessionRepository.retrieve("offline_victim.myshopify.com")` (per the documented pattern) returns the victim shop's stored offline access token, which is then used to serve the attacker's authenticated request.

Note: exploitation depends on the attacker having some means of injecting/overwriting the app's cookie in the victim browser context (outside this gem); I could not verify within this codebase what cookie attributes a given host app sets, since cookie issuance beyond `SessionCookie`'s own `name/value/expires` fields is the host application's responsibility.

```ruby
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
```
