### Title
Permanent freezing of escrowed order funds via a single unchecked/malicious input token blocking `_withdraw` / `withdraw` for the entire order - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` accepts an arbitrary, unvalidated list of input token addresses from the order creator [1](#0-0) . When the order is filled or cancelled, `_withdraw`/`withdraw` iterates over *all* the order's escrowed tokens and transfers them to the beneficiary in a single atomic loop, using `safeTransfer` (main EVM contract) or a raw `.call` that reverts on failure (Tron variant) [2](#0-1) [3](#0-2) . Exactly like the Mellow `getLiquidAssets()`/`hookPullAssets()` bug — which aggregated and pulled balances across multiple subvaults without checking whether each subvault supported the asset, so a single unsupported-asset subvault reverted the whole redemption — this loop has no per-token isolation: if any single token transfer in the array reverts (e.g., a blacklist-style token such as USDC/USDT that blocks the solver's address, a paused token, or any other reverting/malicious ERC-20 the order creator chooses to include as an input), the entire `withdraw` call reverts, and none of the other (otherwise fine) tokens in that order can be released either.

### Finding Description
- `placeOrder` lets the order creator pick any ERC-20 address as an input token with zero allow-listing [4](#0-3) .
- On a successful fill, `_fillCrossChain`/`_fillSameChain` builds a `WithdrawalRequest` covering *all* of the order's escrowed input tokens and calls `_withdraw`, which loops over `body.tokens` and does `IERC20(token).safeTransfer(beneficiary, amount)` for each one [2](#0-1) . There is no per-token try/catch or skip-on-failure — a revert from any single token propagates and reverts the whole transaction, including the storage decrements and event emission for every other (healthy) token in the same order.
- The Tron/legacy variant makes this even more explicit: `withdraw()` uses a raw low-level `.call` per token and explicitly reverts the whole function with `TransferFailed()` if any single transfer fails [3](#0-2) .
- Because a solver only decides to fill an order after inspecting its outputs/inputs, but has no way to guarantee a token won't later revert for its specific receiving address (e.g., a centralized stablecoin blacklists the solver after order placement, or the order creator deliberately embeds a token contract that reverts for any address other than a hand-picked one), the solver can deliver 100% of the required output tokens to the user and dispatch the cross-chain `RedeemEscrow` message, yet the source-chain `onAccept → withdraw` call can permanently revert forever, because `_filled`/`_orders` state is only mutated inside the same atomic call that reverts. The escrow for every token in that order (not just the poisoned one) is then stuck: it can never be pulled by the solver, and it is not automatically returned to the user either, since `_filled` for that commitment gets set to the solver only if `withdraw` succeeds.
- This directly parallels the reported root cause pattern: "the system aggregates balances/transfers across multiple assets/holders without isolating failures, so a single incompatible/blacklisted asset blocks release for the whole batch," reachable purely by an unprivileged order placer or by external token-issuer action (blacklisting) after order placement — no privileged or malicious-admin/relayer/node role is required.

### Impact Explanation
This is a concrete freezing-of-funds bug reachable from a single unprivileged `placeOrder` transaction, matching the "permanent freezing of funds" acceptance criterion. A solver that fills an order containing a blacklist-capable or maliciously-crafted input token loses the output tokens it already delivered to the user (and pays the cross-chain dispatch fee) while never being able to claim the escrowed input tokens — none of which can be recovered by the user either, since the order is not marked filled/cancelled and no other code path releases the escrow. Because a single order can bundle multiple input tokens, funds belonging to entirely unrelated, "clean" tokens in the same order are frozen collaterally by the one poisoned token, mirroring the Mellow report's "one bad asset blocks redemption of everything aggregated with it" DoS class. This can be weaponized deliberately (attacker crafts an order with a token designed to revert once a specific solver interacts, or transfers to specific address) or triggered passively (issuer blacklists an address between order placement and settlement, which is a realistic and previously-seen event for USDC/USDT-style tokens).

### Likelihood Explanation
Likelihood is Medium-High: placing an order with arbitrary ERC-20 addresses requires no special privilege, and there is no validation preventing an order creator from choosing a token that is pausable/blacklistable or custom-written to revert conditionally. Solvers generally do check basic token liquidity/price before filling, but nothing forces them to simulate an actual transfer to their own specific address ahead of time, and external blacklist events (post-placement) are outside a solver's control entirely. The cross-chain path is especially exposed since there is a time delay between fill (destination chain) and withdrawal (source chain), during which a blacklist or pause could be applied.

### Recommendation
Do not let a single token's transfer failure revert release of the rest of the batch:
- In `_withdraw` (`IntentsBase.sol`) and `withdraw` (Tron `IntentGatewayV2.sol`), wrap each per-token transfer in a low-level call with try/catch semantics (or use a pull-based/claim pattern) so that a failing token is skipped/queued for retry (e.g., credited to an internal "stuck balance" ledger the beneficiary can later claim once the token becomes transferable again) rather than blocking `_filled` from being set and blocking every other token's release.
- Decouple `_filled[commitment] = beneficiary` (state finalization) from the per-token transfer loop so a partial-transfer failure cannot leave the order in limbo indefinitely.
- Consider validating/restricting allowed input token types at `placeOrder` time, or requiring solvers to acknowledge each specific input token before committing.

### Proof of Concept
1. Deploy a malicious ERC-20 `EvilToken` whose `transfer` function reverts unconditionally for any recipient other than a hardcoded address (simulating a blacklist/pause).
2. User calls `placeOrder` with `inputs = [ {token: USDC, amount: 1000e6}, {token: EvilToken, amount: 1} ]` and a normal output requirement, e.g. via `evm/src/apps/IntentGatewayV2.sol#placeOrder`.
3. Solver calls `fillOrder`, delivering the required output tokens to the user; for a cross-chain order this dispatches `RedeemEscrow` to the source chain (`ExtrinsicIntents.sol` fill path).
4. On the source chain, the relayer delivers the message and `onAccept` invokes `withdraw`/`_withdraw` with `body.tokens = [USDC, EvilToken]`.
5. The `EvilToken.transfer(solver, 1)` call inside the loop reverts; because the loop has no isolation, the entire `_withdraw`/`withdraw` call reverts — the 1000 USDC that would have safely transferred is also blocked, `_filled[commitment]` is never set, and the solver can never claim any of the escrowed inputs despite already delivering the output tokens, permanently freezing the order's escrow (test can be added alongside `evm/tests/foundry/IntentGatewayV2Test.sol`'s existing `testOnAcceptSettleEscrow`/`testOnAcceptRefundEscrow` tests using a revert-on-transfer mock ERC-20).

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
