### Title
Non-atomic multi-step writes in `Wallet::changePassphrase` can permanently strand the seed if the underlying storage write partially fails - (File: `features/wallet/module/wallet.js`)

### Summary
`Wallet::changePassphrase` performs several sequential, non-atomic `walletStorage` writes to migrate the seed to a new passphrase. If the final write (re-encrypting the seed under the new passphrase) throws after the earlier metadata writes have already succeeded, the function only logs and re-throws a generic error — it never reverts the already-applied metadata changes. This leaves the wallet's on-disk state inconsistent: metadata says a user passphrase (or no auto-generated passphrase) is in effect, while the actual seed blob is still encrypted under the *old* key material. This mirrors the `Bet::cancel` bug class: a partial failure inside a multi-step state transition is not rolled back, permanently stranding user assets (here, access to the seed/private keys) with no recovery path.

### Finding Description
`changePassphrase` calls `#setSeed` to migrate the seed to the new passphrase: [1](#0-0) 

`#setSeed` performs multiple independent `walletStorage` operations in sequence with no compensating rollback on failure: [2](#0-1) 

The sequence for the common "user explicitly sets a passphrase" path is:
1. `walletStorage.delete(GENERATED_PASSPHRASE_KEY)` — discards the previously auto-generated passphrase.
2. `walletStorage.set(HAS_USER_SET_PASSPHRASE_KEY, true)` — flips the "user has a passphrase" flag.
3. `walletStorage.set(SEED_KEY, seed, { passphrase })` — re-encrypts and persists the seed under the **new** passphrase.
4. A read-back assertion (`storedSeed.seed.equals(seed.seed)`) to sanity-check step 3 succeeded.

If step 3 (or the underlying storage adapter write it performs) throws — e.g. due to a transient I/O error, quota limit, or any exception — the `catch` in `changePassphrase` at [3](#0-2)  merely logs and rethrows `Something went wrong. Try again.`. Steps 1 and 2 are **not undone**. The on-disk `SEED_KEY` blob remains encrypted with the *old* key material (old explicit passphrase, or the auto-generated passphrase that step 1 just deleted), while `HAS_USER_SET_PASSPHRASE_KEY` now falsely claims the user has set a passphrase and the auto-generated passphrase record is gone.

Subsequent unlock attempts read the seed via `#getSeed`: [4](#0-3) 
Because `#usePassword && !passphrase && this.#useAutoGeneratedPassword` no longer has a `GENERATED_PASSPHRASE_KEY` to fall back on (it was deleted in step 1), and the actual `SEED_KEY` ciphertext still requires the old passphrase (not the new one the user believes is now active), the wallet can end up in a state where neither the old auto-unlock path nor the intended new passphrase can decrypt the seed. There is no compensating transaction and no `Bet`-style "retry the whole cancel" mechanism — much like the original report, once the transaction partially lands, there is no code path that can undo or complete it.

### Impact Explanation
This is a single-immutable-operation, no-two-phase-commit bug analogous to the reported `Bet::cancel` issue: a multi-step state change is not atomic, and a partial failure leaves persistent, unrecoverable storage inconsistency. In the wallet case the impact is on the secret material itself rather than an ERC-20 balance — the practical effect is the same "permanently locked/inaccessible" outcome for the user, since the seed (all of the user's private keys) becomes undecryptable with any passphrase the user has knowledge of. This satisfies the "direct wallet-compromise impact" bar (total, unrecoverable loss of key access) required by the validation rules, and it occurs on a legitimate, unprivileged user-invoked action (`changePassphrase`), not through any malicious peer/operator.

### Likelihood Explanation
This requires the storage write in step 3 to fail after steps 1–2 already committed — a scenario storage adapters can hit under real-world conditions (mobile storage quota/permission errors, browser-extension storage API throttling/errors, IndexedDB/keystore exceptions, process kill between awaited writes). Because each `walletStorage.set/delete` call is awaited individually with no transaction wrapper, any interruption between them (including app crash/OS kill on mobile between awaited I/O calls) can produce the inconsistent state described. This is a realistic, not purely theoretical, failure mode for a multi-`await` storage sequence with no atomicity guarantees, comparable in likelihood profile to the original `try/catch{}`-swallowed dual `transfer` call issue.

### Recommendation
- Make the seed migration atomic: write the new `SEED_KEY` ciphertext first (or into a temporary/staging key) and only update `HAS_USER_SET_PASSPHRASE_KEY`/delete `GENERATED_PASSPHRASE_KEY` after the seed write and read-back verification have succeeded.
- Alternatively, implement a rollback path in the `catch` block of `changePassphrase`/`#setSeed` that restores `GENERATED_PASSPHRASE_KEY` and `HAS_USER_SET_PASSPHRASE_KEY` to their prior values if the seed write fails.
- If the underlying storage adapter supports transactions/batched writes, use that primitive here instead of sequential independent `set`/`delete` calls.
- Add a recovery API (analogous to the report's "rescue function" option) that lets the app detect this inconsistent state (`HAS_USER_SET_PASSPHRASE_KEY` true but `SEED_KEY` fails to decrypt with the current passphrase and `GENERATED_PASSPHRASE_KEY` is absent) and offer the user a path to retry decryption with previously known passphrases.

### Proof of Concept
Conceptual reproduction (would require fault-injecting the storage adapter, e.g. in a Devin session with test harness access):
1. Create a wallet with an auto-generated passphrase (`useAutoGeneratedPassword: true`), so `GENERATED_PASSPHRASE_KEY` is set and `HAS_USER_SET_PASSPHRASE_KEY` is `false`.
2. Call `wallet.changePassphrase({ currentPassphrase: <old>, newPassphrase: 'user-chosen' })`.
3. Instrument/mock `walletStorage.set` so that the third call (writing `SEED_KEY` with the new passphrase) throws after the first two calls (`delete(GENERATED_PASSPHRASE_KEY)`, `set(HAS_USER_SET_PASSPHRASE_KEY, true)`) have already resolved — this simulates a storage failure mid-sequence, as referenced in [2](#0-1) .
4. Observe that `changePassphrase` rejects with `Something went wrong. Try again.`, but `walletStorage.get(HAS_USER_SET_PASSPHRASE_KEY)` now returns `true` and `walletStorage.get(GENERATED_PASSPHRASE_KEY)` returns `undefined`, while `SEED_KEY` is still encrypted under the old (now-deleted) generated passphrase.
5. Attempt `wallet.unlock({})` (no explicit passphrase) or `wallet.unlock({ passphrase: 'user-chosen' })` — both fail because `#getSeed` no longer has the deleted generated passphrase available and `SEED_KEY` isn't encrypted with the new passphrase, demonstrating permanent loss of access to the seed.
