### Title
Webhook Shop-Domain Spoofing via HMAC Binding Gap — Cross-Tenant Webhook Attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts the `shop`/`x-shopify-shop-domain` header on an incoming webhook request without that value ever being covered by the HMAC signature check. The HMAC only authenticates the raw request body, not the shop-identifying header, so the equality "shop verified by HMAC" == "shop used to attribute the webhook payload" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop` accessor is populated straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards `request.shop` (the unauthenticated header) straight into the handler: [3](#0-2) 

Because Shopify webhook HMACs are computed with the app's single, shop-agnostic `api_secret_key` (the same key is used for every shop that installs the app — confirmed by `HmacValidator` using `Context.api_secret_key`/`old_api_secret_key` globally, not per-tenant), any unprivileged user who installs the app on their own store legitimately receives real webhook deliveries with valid `(body, hmac)` pairs. They can then replay that exact `(body, hmac)` pair to the app's shared webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a victim shop. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` hands the (forged) victim shop identity plus the attacker's own body content to the app's `WebhookMetadata`/handler: [4](#0-3) 

The equality that should hold — `shop authenticated by the signature` == `shop the payload is attributed to` — is broken: the signature authenticates the body only, while the shop used for tenant attribution comes from an unauthenticated header.

### Impact Explanation
This is a cross-tenant data-attribution vulnerability: an attacker with no special privilege beyond installing the (presumably free/public) app on their own store can forge webhook deliveries that a host application will process under a different, arbitrary shop's identity. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., to look up the victim's stored access token/session, write orders/customers into the victim's tenant space, trigger billing or fulfillment logic), this can lead to cross-tenant data injection/corruption or triggering shop-scoped business logic against a victim's tenant — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app built on this gem that keys business logic off `WebhookMetadata#shop`: the attacker only needs to (a) install the target app on any shop they control to obtain a legitimately-signed `(body, hmac)` pair, and (b) send an HTTP POST directly to the app's public webhook endpoint with a forged `shop-domain` header — no TLS interception, no leaked credentials, and no privileged account access are required.

### Recommendation
Bind the shop domain (and other identity-relevant headers such as `topic`, `webhook-id`, `api-version`) into the signed material, or otherwise cross-check the header-provided `shop` against a value independently known to correspond to the same tenant before trusting it (e.g., require the host app to separately look up/confirm the shop from a value verified via signature, such as an authenticated session or a per-shop secret/HMAC). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (no special privilege required — any unprivileged internet user can install a public app).
2. Shopify delivers a legitimate webhook to the app's webhook endpoint:
   - Body: `{"id": 1, ...attacker-controlled-looking order data...}`
   - Header `x-shopify-hmac-sha256`: valid HMAC computed with the app's single, global `api_secret_key`
   - Header `x-shopify-shop-domain`: `attacker-shop.myshopify.com`
3. Attacker captures this `(body, hmac)` pair and replays it directly to the same public webhook endpoint, but with the header changed to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` against the supplied HMAC — this still passes because the body is untouched.
5. `Registry.process` then builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and calls the app's handler, which processes the attacker's payload under the victim shop's identity.
