### Title
Iris-code attestation signature omits `signup_id` context, enabling cross-signup replay of secure-element signatures - (File: `src/plans/enroll_user.rs`)

### Summary
The Orb's secure-element attestation for a signup is computed by `make_signature()` and only commits to the Orb ID, user ID, and iris pipeline data. It never binds the signature to the specific `signup_id` under which the signup is submitted to the backend. This is the same class of defect described in the external report: a cryptographic commitment (the EIP-4337 `userOpHash`) that omits a context identifier (`EntryPoint`) that is supposed to scope validity to one execution context, enabling replay across contexts. Here, the missing context identifier is `signup_id`, which scopes the backend transaction (`POST /api/v2/signups/{signup_id}`) but is absent from what the secure element actually signs.

### Finding Description
`make_signature()` builds the SHA-256 digest that is passed to `secure_element::sign()`: [1](#0-0) 

The digest covers `ORB_ID`, `user_qr_code.user_id`, and the iris pipeline versions/codes/masks for both eyes, but it never includes `self.signup_id` (the `SignupId` that is passed into the `Plan` struct and used to build the HTTP request path): [2](#0-1) [3](#0-2) 

The resulting `signature` is sent as an opaque multipart field alongside — but not cryptographically bound to — the `signup_id`, which is instead only used as a path parameter: [4](#0-3) 

Because the signed payload (`ORB_ID` + `user_id` + iris pipeline data) is fully deterministic for a given user/iris capture and does not vary with `signup_id`, the same secure-element signature is valid input for any number of distinct `signup_id` values submitted to the backend. This mirrors the reported bug class exactly: the signing scheme excludes the value meant to scope the signed artifact to a single logical transaction/session, so the artifact can be legitimately replayed into a different context.

### Impact Explanation
This signature exists to have the tamper-resistant secure element attest that the iris codes/version data being submitted originated from this genuine Orb hardware for this specific user enrollment. Because `signup_id` is not part of the signed digest, a previously-observed `(signature, codes, userId, orbId)` tuple from one signup attempt can be resubmitted under a different `signup_id` without needing the secure element to re-sign anything. Depending on how the backend uses this signature (e.g., as proof of hardware attestation/anti-fraud check rather than the actual biometric uniqueness check, which is separately handled by iris matching), this could let an attacker/operator craft or replay multiple signup records that carry a "verified hardware attestation" signature for iris data that was never freshly signed by the secure element for that transaction — a cross-signup replay of the secure-element trust anchor.

### Likelihood Explanation
The signup flow already transmits both `signup_id` and `signature` over the network for every signup, and `signup_id` is generated per attempt rather than being part of what is signed, so any code path or actor able to observe/store one accepted `(user_id, codes, signature)` triplet (e.g., from logs — note the code explicitly logs `Iris code signature: {:?}` at `src/plans/enroll_user.rs:89` — or from a captured/duplicated request) can trivially replay it against a new `signup_id`. No cryptographic break is required; it only requires reusing an already-produced valid signature in a new request, which is the same low-effort mechanic demonstrated in the reported PoC.

### Recommendation
Include `signup_id` (and ideally a request timestamp/nonce) inside the digest signed by the secure element in `make_signature()`, e.g.:
```rust
fn make_signature(signup_id: &str, user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(signup_id.as_bytes());
    ctx.update(ORB_ID.as_str().as_bytes());
    ...
}
```
and update the single call site in `Plan::run` to pass `self.signup_id`. This binds the secure-element attestation to the exact signup transaction, preventing reuse across different `signup_id`s, consistent with how `EntryPoint` was added back into the `userOpHash` in the referenced fix.

### Proof of Concept
1. Perform a legitimate signup; capture the multipart POST to `/api/v2/signups/{signup_id_A}`, noting the `signature` field value returned by `make_signature()` and the `codes`/`userId` fields.
2. Craft a new signup request to `/api/v2/signups/{signup_id_B}` (a different signup transaction) reusing the exact same `signature`, `userId`, `orbId`, and `codes` fields captured in step 1.
3. Because `make_signature()` never incorporated `signup_id_A`, the signature is byte-for-byte valid for `signup_id_B` as well — the secure element was never asked to attest to `signup_id_B`, yet the replayed signature is indistinguishable from a freshly produced one for that transaction, confirming the missing context-binding vulnerability.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
