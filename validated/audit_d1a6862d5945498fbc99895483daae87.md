Confirmed: `Nonce<T>` is shared per `(address, state_machine)` between the beneficiary-redirect path in `accumulate_fees` and `withdraw`/`withdraw_fees`, and the signed payload never binds the specific commitments or fee amount involved.

### Title
Front-runnable relayer nonce lets an attacker grief pending `accumulate_fees` beneficiary-redirects and `withdraw_fees` calls - (File: modules/pallets/relayer/src/accumulate.rs, modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-relayer`'s `Nonce<T>` map is shared between two independent, publicly-submittable, unsigned-origin extrinsics: the beneficiary redirect embedded in `accumulate_fees` and the fee `withdraw`/`withdraw_fees` call. Both sign only `(nonce, state_machine, beneficiary)` — never the specific commitments, amounts, or proof accompanying the call — and read the current on-chain nonce fresh at execution time rather than binding it immutably to the request they authorize. This is the same bug class as the reported `PrincipalToken.permitCollector` / `TwoCryptoZap` issue: a signature meant to accompany one specific action can be extracted from the public mempool/DB and resubmitted attached to a trivial, unrelated, but validly-provable action, bumping the shared nonce and causing the legitimate pending transaction (built against the stale nonce) to revert with `InvalidSignature`/`InvalidPublicKey`.

### Finding Description
`accumulate_fees` is dispatched via `RuntimeOrigin::none()` (unsigned extrinsic, validated purely by signature checks inside), so anyone can submit it: [1](#0-0) . Inside `accumulate`, the beneficiary-redirect signature is checked against `Nonce::<T>::get(&delivery_address, state_machine)` read fresh at call time, then the nonce is bumped: [2](#0-1) . The signed message itself only covers `(nonce, state_machine, beneficiary)` — it does not bind the specific `commitments`/`withdrawal_proof` in the extrinsic that carries it: [3](#0-2) .

`withdraw` shares the exact same `Nonce<T>` storage key `(address, dest_chain)`, also reads it fresh and bumps it, with a signed payload of `(nonce, dest_chain, beneficiary?)`: [4](#0-3) [5](#0-4) . `withdraw_fees`/`accumulate_fees` are exposed as unsigned dispatchables anyone can submit, per `lib.rs`.

Because the signature only commits to `(nonce, state_machine, beneficiary)` and not to the specific batch of commitments/proof or withdrawal amount that accompanies it in the extrinsic, any third party who observes a pending, mempool-visible `accumulate_fees` call carrying a `beneficiary_details` signature (or a pending `withdraw_fees` signature) for relayer address `R` on chain `C` can:
1. Extract `(beneficiary_address, signature)` (or the `WithdrawalInputData.signature`) from the observed call.
2. Re-wrap that same signature into a new `accumulate_fees` (or `withdraw_fees`) call, paired with a *different*, but independently and publicly provable, `WithdrawalProof`/context for the same `delivery_address == R` and same `state_machine == C` (e.g., any other already-delivered, unclaimed commitment attributable to relayer `R`, which is public information queryable via ISMP events).
3. Submit that resubmitted call first. It passes the same nonce/signature check (since the signature only binds `nonce`+`state_machine`+`beneficiary`, not the payload contents), and bumps `Nonce<T>` for `(R, C)`.
4. The original, legitimate call — built by the tesseract relayer client against the stale nonce — now fails signature verification (`InvalidSignature`/`InvalidPublicKey`) when it lands, and reverts.

This griefs the relayer's intended fee-accumulation/withdraw action, forcing them to re-sign and resubmit, and can be repeated indefinitely by an attacker who simply monitors the mempool for these unsigned extrinsics, exactly mirroring the reported PrincipalToken `permitCollector` front-running pattern where `TwoCryptoZap.collectWithPermit` gets DoS'd because the nonce it depends on is bumpable by anyone independently of the batched call.

### Impact Explanation
This is a Medium-severity temporary denial-of-service on relayer fee accumulation/withdrawal: a griefing party can force repeated reverts of `accumulate_fees`/`withdraw_fees` calls submitted by the tesseract relayer client, delaying (but not permanently blocking, and not stealing) relayer fee payouts. It does not cause fund loss or permanent freezing since the relayer can simply re-sign with the new nonce and resubmit, but it does create a persistent, cheap, and repeatable DoS vector against `IsmpDispatcher`-adjacent reward accounting infrastructure (relayer fee/reward accounting), degrading relayer economics and potentially discouraging relayer participation.

### Likelihood Explanation
Both `accumulate_fees` and `withdraw_fees` are unsigned extrinsics visible in the transaction pool before inclusion, and the underlying signed message never binds to the specific proof/commitments/amount accompanying it — only to `(nonce, state_machine, beneficiary)`. Since delivered commitments and relayer addresses are public on-chain data, an attacker can trivially construct an alternative, validly-provable call reusing the intercepted signature. No privileged access or governance action is required — a single observing party with a normal RPC connection can execute this.

### Recommendation
Bind the signed payload to the specific action it authorizes rather than only to `(nonce, state_machine, beneficiary)`:
- Include a hash/commitment of the actual `withdrawal_proof.commitments` (or the withdrawal amount) inside `beneficiary_message`, so a signature cannot be detached and replayed against an unrelated batch.
- Alternatively, separate the `Nonce<T>` maps used by `accumulate_fees`'s beneficiary-redirect and by `withdraw`/`withdraw_fees`, and/or make nonce advancement idempotent per intended action (e.g., key on a hash of the full signed payload rather than a simple incrementing counter), so front-running with an unrelated but validly-signed message cannot invalidate a different pending call.
- Consider wrapping the try/catch pattern recommended in the original report equivalent for Substrate: have the off-chain relayer client re-fetch the nonce and re-sign transparently on `InvalidSignature`/`InvalidPublicKey` failure, to reduce operational impact while the on-chain binding fix is deployed.

### Proof of Concept
Conceptual sequence (Substrate/pallet-relayer):
1. Relayer `R` (address `A`) has delivered commitment `X` and `Y` (unclaimed) attributable to it on `state_machine = C`, and its off-chain tesseract client builds and broadcasts `accumulate_fees(withdrawal_proof_for_X, beneficiary_details = (B, sig_over_beneficiary_message(nonce=N, C, B)))` as an unsigned extrinsic.
2. Attacker observes this extrinsic in the mempool, extracts `(B, sig)`.
3. Attacker submits `accumulate_fees(withdrawal_proof_for_Y, beneficiary_details = (B, sig))` first — this is a different, independently valid `WithdrawalProof` for the same `delivery_address = A`, `state_machine = C`, so it passes `Nonce::<T>::get(&A, C) == N` and the signature check unchanged (see [2](#0-1) ), advancing `Nonce<T>` to `N+1`.
4. The relayer's originally-broadcast `accumulate_fees(withdrawal_proof_for_X, ...)` extrinsic now lands, recomputes `msg = beneficiary_message(N+1, C, B)`, and the previously-valid signature (signed for nonce `N`) fails `signature.verify`, causing `Error::<T>::InvalidPublicKey`/`InvalidSignature` and reverting the intended fee accumulation for `X`.
5. The same pattern applies symmetrically to `withdraw`/`withdraw_fees` via the shared `Nonce<T>` map, per [4](#0-3) .

/// Signed payload authorising a beneficiary redirect on a specific source chain.
/// Including the relayer nonce alongside the state machine keeps the signature usable for
/// exactly one accumulate call on that chain, mirroring how `withdraw_fees` binds its signed
/// payload.
pub fn beneficiary_message(
	nonce: u64,
	state_machine: StateMachine,
	beneficiary: &[u8],
) -> [u8; 32] {
	sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}

/// Signed payload for [`WithdrawalInputData`]. Includes the per-relayer nonce so a captured
/// signature cannot be replayed.
pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
}
