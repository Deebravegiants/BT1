### Title
Webhook HMAC only signs the request body, allowing shop-domain / topic spoofing to achieve cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and never included in the HMAC-signed content. `Registry.process` validates only the body's HMAC and then dispatches the handler using the unverified `shop` header, breaking the binding "bytes verified == bytes parsed/acted on."

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body-only HMAC), then immediately trusts `request.shop` and `request.topic` to build the data passed to the app's handler: [4](#0-3) 

Because the signature only covers the body, any request whose body+HMAC pair is valid for the app's secret (e.g., one legitimately produced by Shopify for the attacker's own store) can be replayed with an arbitrary `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header value, and the HMAC check will still pass. This is the same class of vulnerability as the vault report: the field the application acts on (`shop`, used to identify the tenant for the handler) is not the field that is covered by the signature/verification (`raw_body`).

### Impact Explanation
This directly enables cross-tenant confusion in the webhook pipeline: the `shop`, `topic`, and `webhook_id` fields delivered to `handler.handle(...)` are attacker-controllable independent of the HMAC check, since the HMAC only binds the JSON body. Any app that keys tenant lookups/persistence off `WebhookMetadata#shop` (which is the intended and documented usage) can be made to associate a legitimately-signed payload (body the attacker can obtain, e.g., from their own store's webhooks) with a victim shop domain of the attacker's choosing. This meets the "Critical - cross-tenant access" bar defined for this analysis.

### Likelihood Explanation
Exploitation requires only the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a body+HMAC pair that is valid for the app's secret — which any unprivileged actor who owns/controls a Shopify shop installed on the app can obtain trivially (their own legitimately delivered webhooks), and then replay with a modified shop-domain header. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
- Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the HMAC-signed material used by `Utils::HmacValidator`, or otherwise cryptographically bind the shop-domain/topic headers to the signed payload before trusting them.
- At minimum, document/enforce that consumers must not treat `WebhookMetadata#shop`/`#topic` as verified unless they are independently confirmed against an out-of-band registered subscription for that shop.

### Proof of Concept
1. Attacker installs the target app on their own controlled shop `attacker.myshopify.com` and receives a legitimately signed webhook (valid `x-shopify-hmac-sha256` computed over `raw_body`, per `lib/shopify_api/webhooks/request.rb#hmac`/`#to_signable_string`).
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation succeeds because the body/HMAC pair is unchanged: [5](#0-4) 
4. The app's registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, even though nothing from `victim-shop.myshopify.com` was ever transmitted or verified.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
