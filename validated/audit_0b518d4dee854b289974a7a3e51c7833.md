I have sufficient evidence to conclude. The `ShopifyAPI::Webhooks::Request` class binds the HMAC signature only to the raw body, while the `shop` field (used downstream for tenant identification) is taken from an unauthenticated header.### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant are read from unauthenticated HTTP headers. This breaks the identity binding `{signed bytes} = {fields acted upon}`: the signature proves the body's integrity/origin, but not which shop the body belongs to.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing an HMAC over `to_signable_string` against the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`, while the `shop` accessor is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Registry.process` validates only this body HMAC, then constructs `WebhookMetadata` using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` header values and forwards them straight to the app's registered handler: [3](#0-2) 

The gem's own documentation recommends apps key downstream work off `data.shop` directly (e.g. enqueuing a job scoped "for that shop"): [4](#0-3) 

Critically, all shops that install a given app share the **same** `api_secret_key` — Shopify signs every shop's webhook body with that one app-wide secret, not a per-shop secret. This means an unprivileged, unprivileged-in-the-victim's-tenant attacker can:
1. Install the same app on their own (attacker-controlled) shop, and receive genuinely Shopify-signed webhook deliveries (valid `HMAC(body, api_secret_key)`), which they fully control the body content of (e.g. by editing their own store's product to fire `products/update`).
2. Replay that exact `raw_body` + valid `hmac-sha256` header to the target app's public webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to the **victim** shop's domain.
3. `HmacValidator.validate` succeeds (it only checks the body against the secret), `Registry.process` proceeds, and the handler receives `WebhookMetadata` claiming the payload came from the victim shop.

This is exactly the analog class called out in scope: a field (`shop`) that is acted upon by the library/handler but not covered by the HMAC that authenticates the request.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (even free/trial) merchant of the app can inject attacker-controlled webhook bodies that the host application will attribute to an arbitrary victim shop domain, since the shop identity is not cryptographically bound to the payload. Depending on how the app's webhook handler uses `data.shop` (as the gem's own docs suggest — to scope database writes, background jobs, cache invalidation, etc.), this enables cross-tenant data injection/corruption for any shop domain the attacker chooses, without needing that shop's access token or any credentials belonging to the victim.

### Likelihood Explanation
Likelihood is high for any app built on this gem following its documented pattern (`data.shop` used to scope work) and exposing a public HTTP webhook endpoint (a mandatory setup for HTTP webhook delivery, including the `MANDATORY_TOPICS` like `shop/redact`, `customers/redact`, `customers/data_request`). Any user can install the app on a shop they control to obtain valid signed payloads, and the header spoofing is a trivial HTTP-level rewrite.

### Recommendation
Include the shop domain (and ideally topic/webhook id) header values in the signable string used for webhook HMAC verification, or otherwise cryptographically bind the `shop` value to the verified payload before it is handed to `Registry.process`/`WebhookMetadata`. At minimum, clearly document in `Request`/`Registry` that `shop`, `topic`, and `webhook_id` are **not** authenticated by the HMAC and must not be trusted for tenant-scoping without an independent verification step (e.g., cross-checking against a shop for which a webhook of that `webhook_id` was actually registered).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining a legitimately Shopify-signed `products/update` webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(B, api_secret_key)`.
2. Attacker crafts an HTTP POST to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: unchanged (still valid for `B`)
   - `x-shopify-shop-domain`: `victim.myshopify.com` (rewritten)
   - `x-shopify-topic`: `products/update` (unchanged or of attacker's choosing)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against the secret and passes: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body: B`, and performs whatever shop-scoped action the app implements for that topic — attributed to a shop the attacker does not own.

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
