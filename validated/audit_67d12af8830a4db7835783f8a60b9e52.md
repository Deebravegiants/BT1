### Title
Webhook shop identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The library's webhook HMAC verification signs only the raw request body, not the `shop`, `topic`, or `webhook_id` values that are read straight from HTTP headers. `Registry.process` trusts these header-derived fields as authenticated tenant identity once the body HMAC passes, so an attacker who possesses one valid `(body, hmac)` pair can relabel it to any shop domain and have it accepted as genuine.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read directly from attacker-controlled HTTP headers and are not part of the signed material: [2](#0-1) 

`HmacValidator.validate` checks the HMAC against `to_signable_string`, i.e. only the body, using the app's single, shop-independent `client_secret`: [3](#0-2) 

`Registry.process` performs exactly this check and then hands the *unauthenticated* `request.shop`, `request.topic`, and `request.webhook_id` straight to the host application's handler as if they were verified: [4](#0-3) 

The identity binding that should hold is:
`shop_the_HMAC_covers == shop_the_handler_receives`

In this implementation, the left side is the empty set (only `raw_body` is signed) while the right side is an arbitrary attacker-supplied header value — the equality is broken by construction.

Because the HMAC secret (`client_secret`) is the same for every shop that has the app installed, any merchant who installs the app on their own store (an unprivileged internet user with respect to other tenants) can capture one legitimate webhook delivery for their own shop — a valid `raw_body` + `X-Shopify-Hmac-Sha256` pair, both of which pass unchanged through Shopify's delivery pipeline — and replay that exact pair to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) with a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body against the shared secret, and `Registry.process` will dispatch the handler with `WebhookMetadata` reporting the victim's shop, even though nothing about the request was ever bound to that shop.

### Impact Explanation
Host applications built on this gem are expected to treat `data.shop` (from `WebhookMetadata`) as an authenticated tenant identifier and use it to look up per-shop sessions/access tokens or write incoming webhook data to the corresponding tenant record. Because that value is forgeable independent of the HMAC, an attacker can inject spoofed or replayed event data into another tenant's processing pipeline — this is a cross-tenant confusion/access vulnerability: attacker-controlled body content (from their own shop) is delivered under a victim shop's identity, and any app logic keyed off `data.shop` (token lookup, data association, side effects) operates against the wrong tenant.

### Likelihood Explanation
Any user who can install the app on a store they control receives real webhook deliveries with valid signatures for arbitrary bodies within the scope of subscribed topics, and can trivially replay them with a modified `Shop-Domain`/`Topic` header to the gem's public, unauthenticated webhook endpoint. No secret material beyond what a normal merchant install grants is required, and the endpoint is internet-reachable by design.

### Recommendation
Bind the shop (and topic/webhook id, if they are relied upon for identity) into the signed material, or otherwise cryptographically tie the header-derived shop to the request rather than trusting it verbatim. At minimum, document explicitly that `request.shop`/`request.topic`/`request.webhook_id` are NOT covered by HMAC verification and must not be used by host applications as an authenticated tenant identifier without additional verification (e.g., cross-checking against the shop for which the webhook subscription was registered).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) with a body they control.
2. Shopify delivers: `raw_body = B`, headers include `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(client_secret, B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and re-POSTs to the app's webhook endpoint with headers changed to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, keeping body `B` and HMAC header `H` unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation passes (`lib/shopify_api/webhooks/registry.rb:190`).
5. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, i.e. attacker-controlled content is accepted as if it originated from the victim shop.
