### Title
Reachable panic (DoS) via unchecked numeric truncation in BEEFY proof ABI→SCALE conversion - (File: evm/rust/src/conversions.rs)

### Summary
The submitted external report (CVE-2022-23571) is a classic *reachable assertion* bug class: attacker-supplied, malformed input reaches a `CHECK`/assert-style failure during decoding, before any semantic validation occurs, crashing the process. The Hyperbridge codebase shows the same anti-pattern in the BEEFY proof ingestion path that converts Solidity-ABI-decoded (attacker-controlled) proof structs into the SCALE types consumed by the verifier.

### Finding Description
`pallet-beefy-consensus-proofs::Pallet::verify_and_apply` [1](#0-0)  is invoked from the pallet's `submit_proof` extrinsic (a permissionless, signed call — see the txpool tests that route malformed/well-formed relayer submissions through it [2](#0-1) ). For both proof types it ABI-decodes attacker-controlled bytes and then converts them into SCALE structs via `Into`:

- `PROOF_TYPE_SP1`: `ismp_abi::sp1_beefy::SP1Beefy::SP1BeefyProof::abi_decode_params(...)` → `.into()` to `beefy_verifier_primitives::Sp1BeefyProof`.
- `PROOF_TYPE_NAIVE`: `ismp_abi::ecdsa_beefy::BeefyConsensusProof::abi_decode_params(...)` → `.into()` to `beefy_verifier_primitives::ConsensusMessage`.

The corresponding `From` implementations use `.try_into().expect(...)` on attacker-controlled `uint256` fields instead of returning a typed error:

`blockNumber`, `validatorSetId`, and `leafIndex` are Solidity `uint256` values fully controlled by the caller of `submit_proof`. No range check is performed before the `try_into().expect(...)` calls, so submitting a value that overflows the target `u32`/`u64` width causes an unconditional Rust panic *before* any cryptographic verification runs. This mirrors the TensorFlow advisory's pattern: an unchecked, reachable assertion triggered purely by malformed/oversized input during decoding.

This is structurally identical to the class of bugs the codebase has already fixed elsewhere (with explicit "must not panic on attacker input" regression tests): the GRANDPA verifier's `RelayHeaderNotInUnknownHeaders` fix [5](#0-4) , the BEEFY verifier's `leaf_indices.len() != 1` guard [6](#0-5) , the sync-committee `multi_proof` length guard [7](#0-6) , the Pharos `MAX_PROOF_DEPTH` guard [8](#0-7) , the Ethereum RLP `empty_hp_prefix` fix [9](#0-8) , and the `as_utf8_string` deserialization fix [10](#0-9) . Unlike those, the `.expect()` calls in `evm/rust/src/conversions.rs` were not found to have an equivalent regression test or bound check.

### Impact Explanation
A panic executed inside pallet dispatch logic during block execution is a runtime trap. Depending on how the collator/validator's executor handles it, this can abort block production/import for the offending block, effectively halting the BEEFY consensus-update path (`pallet-beefy-consensus-proofs`) that Gargantua exclusively relies on for BEEFY state advancement (raw `handle_unsigned` BEEFY updates are explicitly filtered out in favor of this pallet [11](#0-10) ). This satisfies the "route unable to deliver messages" impact bar: a stuck BEEFY consensus client blocks all downstream cross-chain message verification that depends on it.

### Likelihood Explanation
`submit_proof` only requires `ensure_signed` — any funded account can call it (see the deliberate "unsigned origin must be rejected" test, confirming a plain signed call is otherwise accepted) [12](#0-11) . Crafting a `uint256` `blockNumber`/`validatorSetId`/`leafIndex` that exceeds the target `u32`/`u64` width requires no cryptographic material — just a single overlarge integer in the ABI payload, well within the `MaxProofSize` bound already exercised in the oversized-payload test [13](#0-12) . This makes the trigger cheap and repeatable for any unprivileged relayer/user.

### Recommendation
Replace all `.try_into().expect(...)` conversions on attacker-controlled ABI fields in `evm/rust/src/conversions.rs` (`Sp1BeefyProof::from`, `MmrProof::from<RelayChainProof>`, and any sibling `From` impls with the same pattern, e.g. `PartialBeefyMmrLeaf`/`BeefyMmrLeaf` conversions) with fallible conversions that return a typed `Error` (e.g., `AbiDecodeFailed`/`ValueOutOfBounds`) propagated through `pallet_beefy_consensus_proofs::verify_and_apply`, matching the pattern already used for the GRANDPA/BEEFY/sync-committee/Pharos fixes. Add regression tests submitting a `blockNumber`/`validatorSetId`/`leafIndex` at `U256::MAX` (and `u32::MAX + 1` boundary) through `submit_proof` and assert a clean `Err` rather than a panic.

### Proof of Concept
1. Craft a Solidity-ABI-encoded `SP1BeefyProof` (or `BeefyConsensusProof`) where `commitment.blockNumber` (or `validatorSetId`, or `latestMmrLeaf.leafIndex`) is set to a `uint256` value greater than `u64::MAX` (e.g., `2^64`).
2. Prefix the payload with `PROOF_TYPE_SP1` (or `PROOF_TYPE_NAIVE`) and submit it via `BeefyConsensusProofs::submit_proof` as a signed extrinsic from any funded account, following the same submission pattern as the existing test harness [14](#0-13) .
3. During dispatch, `verify_and_apply` calls `abi_proof.into()`, which reaches `.try_into().expect("block number out of bounds")` (or the sibling `.expect()` calls) and panics instead of returning `Error::AbiDecodeFailed`.

**Note on verification confidence**: I was unable to fully confirm within available tool calls that the `evm/rust` crate directory is compiled/published as the exact `ismp_abi` crate referenced by `pallet-beefy-consensus-proofs` (the module paths `crate::sp1_beefy::SP1Beefy` and `ismp_abi::sp1_beefy::SP1Beefy` match structurally, and no separate `ismp-abi` crate root was found in the repo, but the `Cargo.toml` package name for `evm/rust` was not retrieved before the tool budget was exhausted). If `evm/rust` is confirmed to be a different, off-chain-only crate not linked into the runtime that backs `pallet-beefy-consensus-proofs`, this specific instance would not be reachable on-chain and the finding would need re-scoping to wherever the pallet's actual `ismp_abi` dependency defines these `From` impls — a background agent should verify this dependency graph (`modules/pallets/beefy-consensus-proofs/Cargo.toml` → `ismp-abi` path) before remediation.

/// that state and compare against BEEFY. Reading from the host remains correct even as more
/// states (Polkadot, Paseo) are bound to the same client over time.
pub struct IsmpCallFilter;
impl frame_support::traits::Contains<RuntimeCall> for IsmpCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		use ::ismp::{host::IsmpHost, messaging::Message};
		match call {
			RuntimeCall::Ismp(pallet_ismp::Call::fund_message { .. }) => false,
			RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { messages }) => {
				let host = Ismp::default();
				!messages.iter().any(|message| match message {
					Message::Consensus(consensus) =>
						host.consensus_client_id(consensus.consensus_state_id) ==
							Some(ismp_beefy::BEEFY_CONSENSUS_ID),
					_ => false,
				})
			},
			_ => true,
		}
	}
}
