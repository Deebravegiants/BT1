### Title
Attacker drains Emporium's pooled ETH via zero-dimension proof + unsigned ops with unconstrained `op.value` - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `Dimensions.tokenNumber == 0` (i.e. `circomData.erc20TokenAddresses == []`), both `Hinkal.transact`'s balance/slippage check and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` check are skipped entirely, because both loops iterate over `circomData.erc20TokenAddresses`. Combined with the `stack.signerAddress == address(0)` branch of `verifyWallet`, which skips EIP-712 signature verification, and the `MainEVMCircuitMin` circuit, which proves nothing about token amounts, an attacker can submit a trivially-satisfiable proof and an `EmporiumStack` whose `ops[i].value` sum to Emporium's entire ETH balance, draining funds deposited by other users/flows.

### Finding Description
The broken equality: ETH contributed by the caller of this `transact()` call (via `msg.value`/`amountChanges`, here `0`) should equal the ETH moved by the ops the caller authored (`sum(op.value)`). Nothing in the reachable code path enforces this when `erc20TokenAddresses == []`.

Trace:
1. `Hinkal.transact` (`contracts/Hinkal.sol:30-168`) calls `hinkalHelper.performHinkalChecks` → `dimensionsCheck` (`contracts/HinkalHelper.sol:64-171`), which only asserts internal array-length consistency against `dimensions.tokenNumber`; it never requires `tokenNumber > 0`. With `tokenNumber = nullifierAmount = outputAmount = 0`, all the checked arrays are legally empty.
2. `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`) detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and returns the minimal input `[emporiumMessage, timeStamp, calldataHash]` (`formInputEmporiumMin`, lines 150-161). This is the input verified against `MainEVMCircuitMin.circom`, whose only constraint is `message <== Poseidon(1)([messageSeed])` — it does **not** constrain any nullifier, UTXO amount, or `op.value`. The attacker can trivially pick any `messageSeed` and set `emporiumMessage = Poseidon(messageSeed)` to produce a valid proof for free.
3. Back in `Hinkal.transact` (lines 92-147), the per-token balance/slippage `require` loop iterates `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)`. With length `0`, this loop never executes — no slippage check, no "balance change equals amountChanges + utxoAmount" check is ever performed for ETH.
4. `_externalTransact` (lines 234-261) calls `EmporiumUpgradeable.runAction` with `deltaAmountChanges` of length `0` (built from the empty `erc20TokenAddresses`), so no pre-transfer is required from the attacker.
5. In `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`): `balancesBefore`/`balancesAfter` are computed over `circomData.erc20TokenAddresses` (empty ⇒ empty arrays), so the post-loop reconciliation loop (lines 132-151) also never executes and can never catch a discrepancy.
6. `verifyWallet` (lines 302-`) is called with `stack.signerAddress == address(0)`, which `return`s immediately (line 314-316) — no EIP-712 signature is checked, meaning the ops list (including every `op.value`) is entirely attacker-authored and unauthenticated by any wallet owner.
7. The ops loop (lines 91-118) then executes `op.endpoint.call{value: op.value}(op.callData)` for each op with `success` required. Solidity's low-level call only requires `address(this).balance >= op.value`; it does not care whose deposit funded that balance. The attacker sets `op.endpoint = <attacker-controlled address>` and `op.value = <victim's entire balance held by Emporium>`.

Because `erc20TokenAddresses = []` completely disables the two structural safeguards (`Hinkal.transact`'s balance/slippage loop and `EmporiumUpgradeable.runAction`'s `balancesBefore/After` loop) that would otherwise have caught `balanceChange < 0` (`revert BalanceChangeShouldBePositive()`), and because the signerless branch removes the EIP-712 authorization that would otherwise bind `op.value` to a specific wallet owner's intent, there is no remaining guard tying `sum(op.value)` to anything the attacker actually deposited in this transaction.

### Impact Explanation
Critical — direct theft of other users'/flows' ETH held in `EmporiumUpgradeable`. The attacker moves any amount up to Emporium's full ETH balance to an endpoint/address of their choosing with a near-zero-cost transaction (no meaningful deposit, no signature, no genuine token bookkeeping). This is fully repeatable until Emporium's ETH balance is exhausted, and it works against every account that has ETH sitting at Emporium awaiting a signer-based (`signerAddress != address(0)`) or later stateless flow. The `dimensions.tokenNumber == 0` message-only path is a designed feature (evidenced by `formInputEmporiumMin` and `MainEVMCircuitMin.circom`), so it is a realistic combination, not a purely theoretical one — provided its corresponding verifier ID is registered.

### Likelihood Explanation
Preconditions: (1) Emporium holds ETH belonging to other flows/users (a normal operating state for the Emporium message/wallet pattern); (2) a verifier is registered for `buildVerifierId({tokenNumber:0, nullifierAmount:0, outputAmount:0}, HINKAL_EMPORIUM_ACTION_ID)` pointing at `MainEVMCircuitMin`. Given the on-chain code explicitly builds a minimal-input path for exactly this dimension/action combination, it is reasonable to assume this verifier is deployed for the feature to function at all. Attacker cost is minimal (gas + a valid but content-free proof they can generate themselves), requires no special role, and is fully attacker-controlled (endpoint, callData, value, and `signerAddress = address(0)` are all fields inside `externalActionMetadata`, which only needs to hash-match `calldataHash`, a check the attacker trivially satisfies for their own crafted data).

### Recommendation
- Require `dimensions.tokenNumber > 0` (or otherwise disallow empty `erc20TokenAddresses`) whenever `stack.signerAddress == address(0)` in the Emporium action, so the balance/slippage reconciliation loops in `Hinkal.transact` and `EmporiumUpgradeable.runAction` cannot be bypassed.
- Alternatively/additionally, when `signerAddress == address(0)`, require that `erc20TokenAddresses` include `address(0)` (native ETH) whenever `stack.ops` contains any `op.value > 0`, and explicitly assert `sum(op.value) <= uint256(-deltaAmountChanges[ethIndex])` (i.e., ETH spent by ops cannot exceed what this specific transaction moved in), instead of relying solely on the post-hoc `balanceChange < 0` revert which only fires when the token array is non-empty.
- Do not allow the `MainEVMCircuitMin`/zero-dimension verifier path to be combined with unsigned (`signerAddress == address(0)`) `EmporiumOperation` execution at all — the "message-only" proof provides no economic constraint, so unsigned ops must never be reachable through it.

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and register a verifier for `buildVerifierId({0,0,0}, HINKAL_EMPORIUM_ACTION_ID)` mapped to a `MainEVMCircuitMin`-based verifier (matching production wiring for the message-only Emporium flow).
2. Simulate a "victim" flow that leaves Emporium holding, e.g., `10 ETH` (via a legitimate deposit/withdraw-pending flow, or directly funding Emporium to model "other users'/flows' balance").
3. As "attacker" (a plain EOA with no relationship to the victim funds), construct:
   - `dimensions = {tokenNumber: 0, nullifierAmount: 0, outputAmount: 0}`
   - `circomData` with empty `erc20TokenAddresses`, `amountChanges`, `onChainCreation`, `slippageValues`, `inputNullifiers`, `outCommitments`, `encryptedOutputs`; `externalActionData = {externalAddress: Emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: attackerReceiver, invokeWallet: false, value: 10 ether, callData: ""}], maxFee:0, deadline: ...})}`
   - Compute `calldataHash` locally to match `getHashedCalldata`, pick `messageSeed` and set `emporiumMessage = Poseidon(messageSeed)`, generate a real proof for `MainEVMCircuitMin` with these public inputs.
4. Call `hinkal.transact(a,b,c,dimensions,circomData)` with `msg.value = 0`.
5. Assert BEFORE: `attacker contribution == 0`, `sum(op.value) == 10 ether`, `Emporium.balance == 10 ether`.
6. Assert AFTER: transaction succeeds, `Emporium.balance == 0`, `attackerReceiver.balance` increased by `10 ether`, proving `0 (attacker deposit) != 10 ether (ETH moved)` while the transaction did not revert — confirming the equality violation and fund theft.
