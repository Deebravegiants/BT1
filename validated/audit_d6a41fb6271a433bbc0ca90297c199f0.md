### Title
Front-runnable `initialize()` on `HyperFungibleTokenUpgradeable` / `WrappedHyperFungibleTokenUpgradeable` allows attacker to seize token-bridge ownership - (File: `sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
Both upgradeable HyperFungibleToken variants expose an `initialize()` function protected only by OpenZeppelin's `initializer` modifier, which prevents *re*-initialization but not a race to be the *first* caller. Unlike the codebase's own `IntentGatewayV2` and `SimplexPaymaster`, which deliberately bind `initialize` to an atomic CREATE2 proxy-creation transaction (proxy + init calldata in one deployment tx) specifically to defeat front-running, these two token-bridge contracts have no such binding and take the future owner as a plain function parameter.

### Finding Description
`HyperFungibleTokenUpgradeable` sets up the raw implementation with `_disableInitializers()` in its constructor, then exposes a public `initialize` that any address can call once, passing an arbitrary `initialOwner`: [1](#0-0) 

The `__HyperFungibleToken_init` internal call sets `__Ownable_init(initialOwner)` with whatever address the caller passes, and there is no `onlyFresh`/version check, no caller restriction, and no linkage to a deterministic deployer-controlled address: [2](#0-1) 

The same pattern exists in `WrappedHyperFungibleTokenUpgradeable`: [3](#0-2) 

By contrast, the codebase's own high-value upgradeable contracts (`IntentGatewayV2`, `SimplexPaymaster`) explicitly recognize and mitigate exactly this bug class: they add an `onlyFresh` guard plus `reinitializer(VERSION)`, and their deployment scripts always deploy the `ERC1967Proxy` together with the init calldata in a single atomic CREATE2 transaction, so no intermediate uninitialized state is ever externally observable: [4](#0-3) [5](#0-4) [6](#0-5) 

`HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable` have neither of these mitigations. If an integrator (or the protocol itself) deploys a bare `ERC1967Proxy` pointing at the implementation and calls `initialize` in a second, separate transaction (the standard/naive upgradeable-proxy deployment pattern, as opposed to the atomic-CREATE2 pattern used elsewhere in this repo), an attacker monitoring the mempool/pending block can front-run that second transaction and call `initialize(name, symbol, attacker)` first, becoming the `owner`.

### Impact Explanation
Ownership of a `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` instance grants control of:
- `configure()` — sets the ISMP `host` and `dispatcher` addresses (host is set-once, but an attacker-controlled host would forge all cross-chain accept/timeout callbacks for this token forever): [7](#0-6) 
- `addChain()`/`removeChain()` — registers which peer contract on which chain is trusted as the message source for mint/unlock, i.e. controls which "peer" can trigger minting on this chain: [8](#0-7) 
- pause/unpause of all transfers and cross-chain `send`/`onAccept`.

An attacker who wins the initialize front-run can point `host`/`dispatcher` at malicious contracts or register themselves as a "peer," enabling forged mint messages (unbacked mint) or permanently freezing/pausing the token/bridge, and locking out the legitimate deployer since `initializer` prevents any further re-initialization.

### Likelihood Explanation
Requires that the contract be deployed via the naive two-step pattern (deploy bare proxy, then call `initialize` in a separate transaction) rather than the atomic CREATE2+initData pattern the repo uses elsewhere. Given that `IntentGatewayV2`/`SimplexPaymaster` already had to be hardened against exactly this scenario, and these two token contracts carry no equivalent protection, likelihood is Medium-High for any deployment that does not follow the atomic pattern; the attack itself (a plain mempool front-run) is trivial and requires no special access.

### Recommendation
Add the same protections applied to `IntentGatewayV2`/`SimplexPaymaster`: bind `initialize` to the deployer/admin (e.g., an immutable `_owner` set in the constructor and checked in `initialize`, or restrict `initialize` to only be callable atomically as part of proxy construction), and/or mandate deployment exclusively via `new ERC1967Proxy{salt: salt}(implementation, initData)` in one transaction, documenting this as a hard requirement for integrators using these upgradeable variants.

### Proof of Concept
1. Deployer deploys implementation `HyperFungibleTokenUpgradeable` and a bare `ERC1967Proxy(implementation, "")` (two-step deployment, not the atomic CREATE2+initData pattern).
2. Deployer broadcasts a follow-up transaction calling `proxy.initialize("Wrapped USDC", "wUSDC", deployerAddress)`.
3. Attacker observes the pending transaction, front-runs it with `proxy.initialize("Wrapped USDC", "wUSDC", attackerAddress)` at higher gas price.
4. Attacker's call succeeds (no caller restriction), setting attacker as `owner` via `__Ownable_init(attacker)`; the deployer's later call reverts with `InvalidInitialization` because `initializer` is one-shot.
5. Attacker now calls `configure()`/`addChain()` to point the token bridge at attacker-controlled host/peer addresses, or `pause()` to freeze all transfers, with no recourse for the original deployer.
