### Title
Unsigned `handle_unsigned` batches perform full, fee-free message execution inside `validate_unsigned`, enabling a mempool/CPU exhaustion DoS on ISMP message delivery - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is dispatched as an **unsigned transaction** specifically so relayers don't pay fees to deliver cross-chain messages [1](#0-0) . To decide whether such a transaction is admissible to the pool, `ValidateUnsigned::validate_unsigned` does not perform a cheap, bounded check — it calls `Self::execute(messages.clone())`, which is the same function used for real on-chain execution: full state-machine validation, Merkle/membership proof verification, and (transactionally) state mutation [2](#0-1) [3](#0-2) . There is no bound on the number of messages/requests inside a single batch (`messages: Vec<Message>`), and `handle_request`'s proof verification cost scales with the number and complexity of requests and their consensus/membership proofs [4](#0-3) .

### Finding Description
Substrate's transaction pool re-validates queued unsigned extrinsics whenever pool maintenance runs (e.g., on every new best/finalized block, and whenever the pool decides it needs to re-check validity), and `longevity: 25` keeps a submitted batch eligible for re-validation across up to 25 blocks [5](#0-4) . Because `validate_unsigned` executes the entire message batch (state-machine height validation, membership proof verification against the state root, and router dispatch) rather than doing a cheap signature/format check, each re-validation cycle re-runs this expensive work.

This is directly analogous to the go-ethereum bug class: a low-cost (here, fee-free) submission occupies pool resources and forces the node to repeatedly perform expensive work, denying capacity to legitimate senders. Where go-ethereum's flaw let one account flood the pool with 5120 full-balance-draining transactions to evict others, here an attacker needs no balance or fee at all — they can craft unsigned `handle_unsigned` batches with maximal (unbounded) message counts and syntactically-valid-but-ultimately-rejected proofs (e.g. crafted to pass initial parsing but fail deep in membership verification, or valid proofs against real consensus state that a well-resourced attacker can obtain cheaply) and gossip many such batches. Each one is re-validated at full cost on every block by every full node's pool logic before being dropped, and because submission is free and unsigned there is no economic disincentive or per-account priority throttling (unlike signed transactions, which cost fees and are limited by nonce).

Root cause: `validate_unsigned` for `pallet_ismp::Call::handle_unsigned` performs full execution-equivalent work (`Self::execute`) for pool admission instead of a cheap, size/complexity-bounded pre-check, and the message batch has no enforced maximum size or proof-complexity limit at the pool-validation layer [2](#0-1) .

### Impact Explanation
This targets the exact reachable path described in scope: `HandlerV2`-equivalent dispatch/delivery via pallet-ismp's `handle_unsigned`, reachable by any unprivileged relayer/attacker submitting a single extrinsic with no funds required. Sustained exploitation degrades or halts a Hyperbridge-connected chain's ability to process legitimate relayed messages — i.e. "a route unable to deliver messages" — because honest relayer submissions compete for pool slots/CPU against a flood of free, computationally expensive, ultimately-invalid batches. This is a network/liveness-affecting High-severity issue matching CWE-400 (Uncontrolled Resource Consumption), consistent with the CVE-2022-23328 bug class.

### Likelihood Explanation
Likelihood is high: no signature, balance, or governance permission is required to submit `handle_unsigned`; the pool's own validity check (`validate_unsigned`) is the expensive step being abused, so the attacker's cost per submission is essentially free relative to the node's cost to validate it. An attacker only needs to construct maximally-sized message batches with proofs that pass early parsing checks (e.g. plausible-looking but ultimately rejected membership proofs, or replaying/permuting components of legitimately observed proofs) to keep forcing full-cost validation cycles.

### Recommendation
- Bound the number of messages/requests permitted per `handle_unsigned` batch, and reject oversized batches in `validate_unsigned` before any proof verification runs.
- Split `validate_unsigned` into a genuinely lightweight admissibility check (well-formedness, dedup, plausible height/consensus-state existence) and defer expensive membership-proof verification to `pre_dispatch`/execution, so pool re-validation does not repeatedly pay the full verification cost.
- Consider charging a small bond or requiring proof-of-work/rate-limiting per submitting peer for unsigned ISMP messages, or capping how many outstanding unsigned batches per source/consensus-state-id the pool will hold at once.

### Proof of Concept
1. An attacker builds a `pallet_ismp::Call::handle_unsigned` extrinsic whose `messages` field contains a very large number of `RequestMessage`/`ConsensusMessage` entries, each carrying a proof crafted to pass initial decoding/format checks (as in the test harness pattern shown in `parachain/simtests/src/pallet_ismp.rs`) [6](#0-5) .
2. The attacker submits many such extrinsics (no signature/fee needed) via RPC/gossip to multiple full nodes.
3. Each node's transaction pool calls `ValidateUnsigned::validate_unsigned`, which invokes `Pallet::<T>::execute(messages.clone())`, doing full state-machine validation and membership-proof verification for every message in every batch [2](#0-1) [4](#0-3) .
4. Because `longevity: 25`, these transactions remain in the pool and get re-validated repeatedly across ~25 blocks, and the attacker can continuously resubmit fresh variants (nonce-free, since unsigned) to sustain the load, starving legitimate relayer message delivery.

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.

	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}
