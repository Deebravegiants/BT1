### Title
Unhandled Uniswap V2 router revert in `dispatch()` permanently blocks the native-fee message-dispatch route - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens` directly, with no `try/catch`, whenever a caller pays the dispatch fee in native token (`msg.value > 0`). Just as the referenced report shows an unguarded `latestRoundData()` call permanently blocking price-feed access, an unguarded call to the configured Uniswap V2 router permanently blocks the native-token dispatch route for every unprivileged caller until a privileged governance action intervenes.

### Finding Description
In `dispatch(DispatchPost memory post)`: [1](#0-0) 
and identically in `dispatch(DispatchGet memory get)`: [2](#0-1) 

the swap call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is made unconditionally, with no defensive `try/catch`. If this external call reverts — because the configured router/pool becomes illiquid, is paused, is upgraded to a version with different revert semantics, or the router address is later found to misbehave — the entire `dispatch` call bubbles up that revert and fails outright, for every single unprivileged caller who attempts to pay in native token, with no fallback inside the same call. This mirrors the root cause of the referenced Chainlink issue exactly: an external, unguarded call embedded in a core protocol entrypoint whose failure the calling contract cannot gracefully handle.

The router address is stored in `_hostParams.uniswapV2` and can only be changed via governance (`updateHostParams`), not by the affected caller, so recovery for native-fee payers is entirely out of their control — the same "cannot be changed" characteristic that made the original Chainlink feed issue a lock rather than a transient failure.

### Impact Explanation
`dispatch()` is the primary entrypoint by which any application contract or user sends a cross-chain POST/GET request through Hyperbridge, and paying in native token is an explicitly documented, first-class payment path (per the function's own NatSpec). A revert in the router call means:
- Every unprivileged caller attempting to dispatch a message while paying in native token is denied, with `dispatch` reverting instead of degrading gracefully.
- This is a genuine "route unable to deliver messages" condition for the native-fee path, satisfying the required impact bar, since messages cannot even be committed/dispatched, let alone delivered.
- Recovery requires a privileged `updateHostParams` governance call to replace the router — the unprivileged caller has no path to route around the failure within `dispatch` itself.

### Likelihood Explanation
Any state in which the configured Uniswap V2 router or the `WETH/feeToken` pool it targets reverts on `swapETHForExactTokens` (e.g., pool drained/illiquid, pair paused/blacklisted by a token with transfer hooks, router logic upgraded/misconfigured) triggers this deterministically and immediately for all subsequent native-fee dispatch calls, with no attacker action beyond normal use of `dispatch{value: ...}`. This does not require compromising any privileged role — it only requires the external AMM dependency to enter a reverting state, which is realistic given AMM pools can be drained or become imbalanced.

### Recommendation
Wrap the `swapETHForExactTokens` call in a `try/catch` (or a low-level `call` with success check) inside `dispatch`. On failure, refund the caller's `msg.value` and either revert with a clear, catchable error (so callers can immediately retry with the feeToken path) rather than letting the router's opaque revert bubble up, or better, allow `dispatch` to fall back to feeToken-based payment/`safeTransferFrom` when the swap fails, matching the resiliency pattern already used elsewhere in this codebase (e.g., `HyperbridgeLzEndpoint.onAccept`'s `try/catch` around `lzReceive` and the WETH-push/re-wrap fallback in `WrappedHyperFungibleToken.onAccept`): [3](#0-2) [4](#0-3) 

### Proof of Concept
1. Governance configures `_hostParams.uniswapV2` to a router/pool pair for `WETH -> feeToken`.
2. The pool's liquidity is drained (or the router is upgraded/paused, or the feeToken adds a transfer restriction that causes the swap's final transfer to revert) such that `swapETHForExactTokens` always reverts.
3. Any unprivileged user or application contract calls `host.dispatch{value: fee}(post)`.
4. The call to `IUniswapV2Router02(uniswapV2).swapETHForExactTokens(...)` reverts, causing the entire `dispatch` transaction to revert — no request commitment is created, and no message can be dispatched via the native-fee path.
5. This persists for every subsequent native-fee dispatch attempt until a governance `updateHostParams` transaction replaces the router, which the affected unprivileged caller cannot trigger themselves.
