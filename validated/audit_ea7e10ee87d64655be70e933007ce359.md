Audit Report

## Title
Unprivileged "view"-role users can read External Initiator and Bridge secrets via unguarded Index endpoints - ([File: core/web/router.go])

## Summary
`GET /v2/external_initiators` and `GET /v2/bridge_types` are registered without any role-check wrapper, whereas the sibling `Create`/`Update`/`Destroy` handlers for the same resources are explicitly wrapped with `auth.RequiresEditRole`. Any authenticated user, including one with the lowest-privilege `UserRoleView`, can therefore call these list endpoints and retrieve `AccessKey`/`OutgoingToken` secret fields for every configured External Initiator and Bridge.

## Finding Description
The `v2Routes` function registers:
```go
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))
authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))

authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.POST("/bridge_types", auth.RequiresEditRole(bt.Create))
...
``` [1](#0-0) 

The whole `authv2` group is gated only by `auth.Authenticate`, which checks that *some* valid session or API token exists, not the user's role [2](#0-1) . Role enforcement is a separate, explicitly-applied concern implemented by `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` in `core/web/auth/auth.go` [7](#0-6) , and these wrappers are simply absent on the two `Index` routes.

`ExternalInitiatorsController.Index` returns every stored initiator serialized via `presenters.NewExternalInitiatorResource`, which includes `AccessKey` and `OutgoingToken` [8](#0-7) [5](#0-4) . Similarly, `BridgeTypesController.Index` returns every bridge via `presenters.NewBridgeResource`, which includes `OutgoingToken` unconditionally (not `omitempty` like `IncomingToken`) [3](#0-2) [4](#0-3) . These are genuine secrets — `AccessKey`/`HashedSecret` authenticate inbound External-Initiator-triggered job runs, and `OutgoingToken`/`OutgoingSecret` are used by the node to authenticate itself when calling out to the EI service [9](#0-8) .

## Impact Explanation
A `view`-role account — intended to be read-only for dashboards/monitoring and unable to create/modify bridges or initiators — can retrieve `AccessKey`/`OutgoingToken` for every configured External Initiator and every `OutgoingToken` for every Bridge on the node, purely via `GET` requests that only require a generically-authenticated session/token. This maps to an in-scope "key/secret exfiltration" impact and represents a concrete role-based access control bypass: the intended privilege boundary between `view` and `edit`/`admin` roles is not enforced on these two endpoints even though it is enforced on every mutating action for the same resources.

## Likelihood Explanation
Provisioning a `view`-role account for low-trust delegation is a normal, documented usage pattern (`RequiresRunRole`/`RequiresEditRole` exist specifically to support this tiered model). Once such an account exists, exploitation requires a single unauthenticated-role-check `GET` request with no timing, race, or additional exploitation steps — likelihood is high on any node with more than one user role provisioned.

## Recommendation
Wrap `ExternalInitiatorsController.Index` and `BridgeTypesController.Index` with at least `auth.RequiresEditRole` (matching `Create`/`Update`/`Destroy`), or strip `AccessKey`/`OutgoingToken` from the resources returned to non-edit/admin roles. Audit the rest of `authv2` for the same "role wrapper present on mutating verbs but missing on GET/list" pattern (e.g. verify `tx_attempts`, `config`, and other GET routes don't expose similarly sensitive fields).

## Proof of Concept
1. As admin, create a `view`-role user (`POST /v2/users` with `role=view`) and create an External Initiator (`POST /v2/external_initiators`) and a Bridge (`POST /v2/bridge_types`).
2. Authenticate the API as the `view`-role user (session cookie or API token via `POST /sessions` or equivalent).
3. Issue `GET /v2/external_initiators` as the view user — response body includes `accessKey` and `outgoingToken` for the initiator created in step 1, per `presenters.ExternalInitiatorResource` [5](#0-4) .
4. Issue `GET /v2/bridge_types` as the same view user — response includes `outgoingToken` for the bridge created in step 1, per `presenters.BridgeResource` [4](#0-3) .
5. Confirm (as a negative control) that `POST /v2/external_initiators` and `POST /v2/bridge_types` correctly return `401 Unauthorized` for the same view user, demonstrating the inconsistency between mutating and list endpoints for identical resources.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
