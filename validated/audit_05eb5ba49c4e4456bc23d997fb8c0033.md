## Title
Webhook `shop` (and `topic`/`webhook-id`) identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identifier passed to the host application's handler, breaking the binding between "bytes verified by HMAC" and "identity fields acted upon."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` uses `VerifiableQuery#to_signable_string` (the raw body) and `#hmac` to verify authenticity: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` (and `request.topic`/`webhook_id`) as the authenticated tenant identity and hands it to the app's handler: [4](#0-3) 

Because the shop-domain header is excluded from the signed content, `HMAC(body, secret)` stays valid for **any** value of `shopify-shop-domain` sent alongside that exact body. This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes is
`hmac_verified_bytes == identity_bytes_acted_on`
but in reality `hmac_verified_bytes` (raw body) `!= identity_bytes_acted_on` (shop/topic/webhook_id headers), since the latter are never part of the signable string.

### Impact Explanation
Any actor capable of obtaining one legitimately-signed webhook body+HMAC pair (e.g., an attacker who controls their own development/partner store and receives real webhooks such as `app/uninstalled`, `shop/redact`, or `customers/data_request`) can replay that exact body+HMAC to the same webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it never inspects the shop header, and `Registry.process` will dispatch the handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim shop. Depending on how the host app implements its handler (which is the documented, expected usage of this API), this enables cross-tenant actions such as spoofed `shop/redact`/`customers/redact` (triggering deletion of another merchant's data) or spoofed `app/uninstalled` (triggering revocation/cleanup logic for another merchant's session), i.e., cross-tenant access/impact without needing the victim's credentials.

### Likelihood Explanation
The attacker only needs a genuine webhook (body+HMAC) from any shop that has the app installed — including their own store — and the ability to POST to the app's public webhook endpoint with a modified header. No access to `api_secret_key`, tokens, or the victim's infrastructure is required, and the HMAC check itself will report success, so nothing in the gem's own validation flags the mismatch.

### Recommendation
Include the identity-bearing headers (`shop-domain` at minimum, and ideally `topic`/`webhook-id`) in the signable content, or otherwise cryptographically bind them (e.g., require the host app to independently confirm the shop belongs to an existing app installation record before trusting `WebhookMetadata#shop`). At minimum, document prominently that `request.shop` is unauthenticated header data and must never be used as a sole tenant-authorization key.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with topic `shop/redact`: raw body `B`, header `shopify-hmac-sha256: HMAC(B, secret)`, header `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (who legitimately received this webhook for their own shop `shop-a`) resends the identical body `B` and identical `shopify-hmac-sha256` value to the same endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (all required headers present) and `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(raw_body) == received_hmac`, which is unchanged.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to act on `victim-shop.myshopify.com` as if Shopify itself had certified that shop for this event.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
