Verifying webhook signature scope precisely.### Title
Webhook `shop`/`topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, while the `shop` and `topic` fields that the handler uses to make tenant-specific decisions are taken directly from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC over exactly that signable string, using the app's single `api_secret_key` shared across every shop that has installed the app [2](#0-1) . The `shop` and `topic` values, however, are read straight from the `shopify-shop-domain` / `shopify-topic` headers with no cryptographic binding to the signed content [3](#0-2) . `Registry.process` checks only `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` / `request.topic` to build `WebhookMetadata`, which is what the host app's handler uses to route/act on data for a specific tenant [4](#0-3) [5](#0-4) .

The identity binding that should hold is: `hmac == HMAC(secret, body ‖ shop ‖ topic)`, i.e., the authenticated shop/topic should equal the shop/topic the handler acts on. Instead the gem only proves `hmac == HMAC(secret, body)`; `shop`/`topic` are asserted, not authenticated. Because the same `api_secret_key` authenticates webhooks for *every* shop that installs the app, any unprivileged internet user who can install the app on a shop they control (a normal, free action for any public app) receives genuine Shopify-computed `(body, hmac)` pairs for that shop. They can then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop (and/or the `shopify-topic` header) that also has the app installed. `HmacValidator.validate` still returns `true` because it never inspected `shop`/`topic`, and `Registry.process` dispatches the handler with the attacker-chosen `shop`/`topic` as if it were an authentic message about the victim tenant.

### Impact Explanation
This is a cross-tenant integrity/authentication issue: an attacker-installed-shop's genuine webhook credentials can be replayed to make the app process fabricated events "as" a victim shop (e.g., triggering `app/uninstalled`, `shop/redact`, or order/customer webhook handling logic keyed off `data.shop`), since the gem provides no verification that the authenticated bytes correspond to the shop/topic claimed. Depending on how a host app's `WebhookHandler#handle` uses `data.shop`, this can lead to cross-tenant data corruption, spoofed compliance/redact events, or state confusion between tenants — meeting the "cross-tenant access" bar for Critical impact.

### Likelihood Explanation
Requires no privileged credentials: installing a public app on a free/attacker-controlled dev store is an ordinary unprivileged action, and the webhook endpoint is a public HTTP endpoint by design. The only extra step is capturing one's own legitimate webhook body+HMAC (trivial, since the attacker's own store is the target) and replaying it with modified headers.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the HMAC-covered signable content, or otherwise cryptographically bind them (e.g., verify `shop` against a caller-supplied expected shop before dispatch), so that `Registry.process`/`HmacValidator.validate` authenticate the full tuple `(body, shop, topic)` rather than the body alone.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com`, receiving genuine webhooks with body `B` and `hmac = HMAC(secret, B)` computed by Shopify using the app's real `api_secret_key`.
2. Attacker POSTs to the app's webhook endpoint with the same raw body `B` and the same `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: <attacker-chosen>, body: B, ...)` [8](#0-7) , and the host app processes it as an authentic event for the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
