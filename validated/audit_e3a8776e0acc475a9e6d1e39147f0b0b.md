### Title

Stale liquidation threshold blocks risk-parameter tightening and can create bad debt - (File: `contracts/controller/src/risk/params.rs`)

### Summary

Spoke risk-parameter changes update the listing but do not invalidate or flush the liquidation parameters already stamped on existing supply positions. Liquidation continues to calculate health factor from the stale `AccountPosition.liquidation_threshold`, so a permissionless execution of a ready `EditAssetInSpoke` operation can leave an unhealthy account under the new parameters temporarily protected from liquidation. A subsequent price decline can push the position directly into bad debt before the stale threshold permits liquidation.

### Finding Description

Each supply position stores its own `liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`, and `loan_to_value`; risk totals use those stored values rather than reading the current spoke listing. [1](#0-0) 

`edit_asset_in_spoke` writes the new `SpokeAssetConfig` to the spoke listing and emits the update, but performs no enumeration or invalidation of existing positions. [2](#0-1) 

The liquidation tuple is refreshed only through gated paths. When the new tuple favors liquidators and the account has debt, `apply_gated_liquidation_params` refuses to apply it unless the health factor calculated with the new threshold is at least `1.05`; otherwise it returns without changing the stored threshold, bonus, or fee. [3](#0-2) 

The permissionless `update_account_threshold` path uses that same gate and then checks post-refresh health factor, so it cannot force an adverse threshold onto a sufficiently risky account. [4](#0-3) [5](#0-4) 

Liquidation then rejects the account unless `calculate_account_risk_totals` reports `health_factor < 1`, but that health factor was calculated with the stale stored liquidation threshold. [6](#0-5) 

### Impact Explanation

A scheduled risk reduction can therefore fail to take effect for precisely the accounts it is intended to protect against. For example, a position with $10,000 of collateral, a stored liquidation threshold of 80%, and $7,500 of debt remains healthy under the stale threshold (`8000/7500 = 1.066`). If governance reduces the threshold to 55%, the account is deeply liquidatable under the current listing (`5500/7500 = 0.733`), but liquidation still reverts as `HealthFactorTooHigh`.

The collateral can consequently fall from the intended liquidation boundary of $13,636 to the stale boundary of $9,375. If the market gaps below $7,500 before a liquidation succeeds, the debt is undercollateralized and suppliers absorb the resulting bad debt. This is a temporary liquidation freeze with a credible protocol-insolvency outcome.

### Likelihood Explanation

The exploit requires a ready governance operation that lowers an asset's liquidation threshold. Executing a ready, non-expired operation is permissionless when `executor` is `None`. [7](#0-6) 

An attacker can monitor the public proposal, open or maintain a maximally borrowed position while the old parameters remain stamped, and execute the operation once ready. The stale tuple then survives both liquidation and the permissionless threshold-refresh path whenever applying the new threshold would leave health factor below `1.05`. Ordinary liquidators cannot bypass the stale stamp.

### Recommendation

At minimum, liquidation should calculate health factor using the tighter of the stored threshold and the current spoke-listing threshold, or atomically apply the current liquidation tuple during liquidation planning. A safer explicit migration is to stamp each listing with a risk-parameter epoch, record the epoch on every supply position, and make liquidation treat positions with an older epoch as if they used the newer, tighter threshold.

If borrower grandfathering is intentional, add a bounded grace timestamp or maximum overdue interval rather than allowing the stale tuple to persist until price movement or a keeper path happens to clear the `1.05` gate.

### Proof of Concept

1. Attacker opens a controller account before a scheduled risk reduction:
   - `supply(attacker, 0, spoke_id, [(collateral_asset, 10_000 USD-equivalent)])`
   - `borrow(attacker, account_id, [(debt_asset, 7_500 USD-equivalent)], None)`
   - Stored collateral parameters are `LTV <= 75%`, `liquidation_threshold = 80%`.

2. Wait until the publicly scheduled `EditAssetInSpoke` operation that changes the listing to, for example, `LTV = 50%` and `liquidation_threshold = 55%` becomes ready.

3. Execute it without executor authorization:
   - `Governance::execute(None, controller, Symbol::new("edit_asset_in_spoke"), args, predecessor, salt)`

4. Optionally prove a keeper cannot repair the stamp:
   - `Controller::update_account_threshold(keeper, true, [account_id])`
   - `apply_gated_liquidation_params` skips the update because hypothetical health factor is `0.733`, below the `1.05` gate.

5. A liquidator calls:
   - `liquidate(liquidator, account_id, [(debt_asset, repayment)], SeizeMode::Transfer)`
   - `build_liquidation_plan` computes health factor with the stored 80% threshold, obtains `1.066`, and reverts with `HealthFactorTooHigh` even though the live listing's 55% threshold yields `0.733`.

6. If collateral value later falls below $7,500 before liquidation succeeds, the account is undercollateralized; `clean_bad_debt` or residual liquidation accounting socializes the shortfall to suppliers.

    account: &Account,

    position: &mut AccountPosition,
    effective_config: &AssetConfig,
