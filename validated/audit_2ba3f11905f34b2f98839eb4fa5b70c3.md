Audit Report

## Title
CORS Wildcard Origin Bypass via Missing Dot-Boundary Check in `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

## Summary
The gateway's HTTP server's `isAllowedOrigin` function performs a raw `strings.HasSuffix` comparison when matching wildcard CORS origins (e.g., `*.ethereum.org`), without verifying a subdomain-delimiting dot boundary. This allows an attacker-registered domain that merely ends with the same character sequence as the allowed suffix (e.g., `evilethereum.org`) to be incorrectly treated as a trusted subdomain and granted CORS access.

## Finding Description
In `isAllowedOrigin`, when an allowed origin has the `*.` wildcard prefix, the code strips it and checks `strings.HasSuffix(originHost, allowedHost)` [1](#0-0) . This is a pure string suffix match, not a domain-label match — there is no check that the character immediately preceding the matched suffix in `originHost` is a `.` (or that the strings are equal). Consequently, for an allowed wildcard `*.ethereum.org` (`allowedHost = "ethereum.org"`), an attacker-controlled origin `evilethereum.org` also satisfies `HasSuffix` despite not being a subdomain of `ethereum.org`.

This function is called directly in the request path via `handleRequest`, which sets `Access-Control-Allow-Origin` to the raw `Origin` header value whenever `isAllowedOrigin` returns true [2](#0-1) . No other validation intervenes before this header is set, so the flawed suffix check is the sole security gate.

The existing test suite exercises only origins that do not share the suffix at all (`https://ethereum.remix.org` vs `*.ethereum.org`), and does not cover the same-suffix-different-domain attacker case, so this gap goes unnoticed by current tests.

## Impact Explanation
Any unauthenticated web attacker who registers a domain ending in the same substring as an operator-configured wildcard CORS entry can host a page that issues cross-origin requests to the gateway's HTTP endpoint. The server will respond with `Access-Control-Allow-Origin` set to the attacker's origin, letting the attacker's page read gateway JSON-RPC responses in a victim's browser context that should only be reachable from genuinely allow-listed subdomains. This maps to an in-scope "allowlist bypass" / cross-user response exposure impact class for the gateway.

## Likelihood Explanation
Exploitation requires only that the operator configure a wildcard CORS entry (a documented, supported feature) and that the attacker register an inexpensive domain sharing the trailing substring. No credentials, privileged access, or victim social engineering beyond normal browser navigation to an attacker-controlled page are required, making this readily and repeatably exploitable.

## Recommendation
Enforce a proper subdomain boundary in the wildcard match, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
Add regression tests asserting that origins sharing only a character suffix (not a dot-delimited subdomain relationship) with the allowed host, such as `evil<allowedHost>`, are rejected.

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.ethereum.org"]`.
2. Send an HTTP request to the gateway's endpoint with header `Origin: https://evilethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` (since `strings.HasSuffix("evilethereum.org", "ethereum.org")` is `true`), and the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers`, despite `evilethereum.org` not being a genuine subdomain of `ethereum.org`.
