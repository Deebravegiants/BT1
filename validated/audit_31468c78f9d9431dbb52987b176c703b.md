Audit Report

## Title
Password Reset Fails to Revoke Existing API Tokens, Allowing Continued Node Access - (File: core/sessions/localauth/orm.go)

## Summary
The local-auth `SetPassword` implementation only updates the `hashed_password` column and never touches the user's stored API token (`token_key`/`token_hashed_secret`/`token_salt`). Both self-service password-change entry points — the GraphQL `UpdateUserPassword` resolver and the REST `UpdatePassword`/`updateUserPassword` handler — call `ClearNonCurrentSessions` (which only purges cookie sessions) and `SetPassword`, but never call `DeleteAuthToken`. As a result, an API token issued before a password reset remains fully valid and usable after the password is changed.

## Finding Description
`SetPassword` updates only the password hash and `updated_at`, leaving token columns untouched: `core/sessions/localauth/orm.go` lines 298-306. `ClearNonCurrentSessions` (lines 243-251) only deletes rows from the `sessions` table used for cookie-based browser sessions. The REST handler `updateUserPassword` (`core/web/user_controller.go` lines 341-360) and GraphQL resolver `UpdateUserPassword` (`core/web/resolver/mutation.go` lines 934-970) both call these two functions exclusively — neither calls `DeleteAuthToken` (defined at lines 343-346 of orm.go and demonstrably used elsewhere, e.g. in `DeleteAPIToken`, `core/web/user_controller.go` lines 289-330). Token-based authentication (`AuthenticateByToken`, `core/web/auth/auth.go` lines 78-112) looks the user up strictly by `token_key` and validates via HMAC secret comparison, with no dependency on the password or any password-change timestamp. This breaks the implicit security assumption that a password reset revokes all forms of access derived from the old credential.

## Impact Explanation
Any user (or attacker who obtained that user's API token through a leak, insider access, or compromised CI secret) retains full API access at the token's granted role even after the account owner performs a password reset intended to cut off unauthorized access. This maps to the in-scope "node API authentication/role bypass" impact category, since password reset — a standard credential-revocation mechanism — fails to revoke a valid authentication artifact (the API token), enabling continued unauthorized job management, configuration changes, or key/secret operations depending on token role.

## Likelihood Explanation
This occurs on every ordinary password-reset flow with no timing, race, or special configuration required — 100% reproducible. Any user who has an active API token (created via `NewAPIToken`, which requires their password once) and later resets their password via the standard REST (`PATCH /v2/user/password`) or GraphQL (`updateUserPassword`) flow will leave that token active.

## Recommendation
Have `SetPassword` (or its callers in `mutation.go` / `user_controller.go`) also invoke `DeleteAuthToken`, or explicitly rotate `token_key`/`token_hashed_secret`, whenever a password reset occurs, so that a previously issued API token is revoked together with cookie sessions. Alternatively, bind API token validity to a `password_changed_at` timestamp check enforced in `FindUserByAPIToken`/`AuthenticateByToken`.

## Proof of Concept
1. As user A, create an API token via `POST /v2/users/tokens` (invokes `UserController.NewAPIToken`, which sets `token_key`/`token_hashed_secret`).
2. Using the returned `AccessKey`/`Secret`, call any authenticated REST endpoint successfully (`AuthenticateByToken` succeeds).
3. As user A, change the password via `PATCH /v2/user/password` (or the `updateUserPassword` GraphQL mutation) — this invokes `ClearNonCurrentSessions` + `SetPassword` only.
4. Repeat step 2 with the same original API token/secret — the request still succeeds because `token_key`/`token_hashed_secret` were never modified, confirming continued access post-password-reset.
