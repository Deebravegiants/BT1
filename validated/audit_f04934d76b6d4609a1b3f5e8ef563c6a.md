## Analysis

The reported bug class (fee‑on‑transfer tokens bridged without verifying the actual amount received) has a direct, valid analog in `WrappedHyperFungibleToken`, which is Hyperbridge's lock/unlock ERC20 bridge app (mint/burn analog: lock on source, unlock on destination). Unlike `IntentGatewayV2`, which explicitly measures balance-before/after to defend against fee-on-transfer tokens (see `evm/src/apps/IntentGatewayV2.sol` lines 313-328 and the dedicated `FeeOnTransferToken` test suite), `WrappedHyperFungibleToken.send()` and its upgradeable twin never check what the contract actually received before dispatching the cross-chain message with the user-declared `params.amount`.

### Title
Unchecked ERC20 transfer amount in `WrappedHyperFungibleToken.send()` allows fee-on-transfer/deflationary tokens to drain destination-chain reserves - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches an ISMP message carrying `params.amount` as the transfer amount, without ever verifying that `address(this)` actually received `params.amount` of the underlying token.

### Finding Description
In `send()`:
```
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
DispatchPost memory request = _buildDispatchPost(params); // encodes params.amount into the Message
``` [1](#0-0) 

`_buildDispatchPost` blindly encodes `params.amount` (the caller-declared amount) into the cross-chain `Message.amount` field, not the actual balance delta observed on the contract: [2](#0-1) 

On the destination chain, `onAccept` unconditionally releases `message.amount` of the underlying (or unwrapped native token, if `_isWeth`) from the destination-chain reserve to the beneficiary via `safeTransfer`: [3](#0-2) 

If `_underlying` is a fee-on-transfer/deflationary ERC20 (or any token whose `transferFrom` delivers less than the requested amount, e.g. rebasing tokens), the source-chain contract escrows `params.amount - fee`, but the message still asserts `params.amount` was locked. The destination-chain deployment of `WrappedHyperFungibleToken` (holding its own, separately funded custody balance of the underlying token) will pay out the full `params.amount` to the beneficiary, over-releasing tokens relative to what was actually escrowed on the source side.

This is the exact bug class from the external report: `L1NativeTokenVault`/`L1AssetRouter` returning `depositChecked = true` and crediting the requested amount without confirming the post-transfer balance delta, enabling tokens with transfer fees to be bridged without proper accounting. `IntentGatewayV2.placeOrder` in this same repo already implements the correct mitigation pattern (balance-before/after diffing, see `balBefore`/balance-diff logic), confirming the project is aware of and defends against this class elsewhere, but `WrappedHyperFungibleToken` was not updated with the same protection.

An unprivileged token bridger simply needs to call `send()` with a fee-on-transfer/deflationary token configured as `_underlying` (chosen by the wrapper's owner at deployment for a real-world asset — many popular tokens implement transfer fees or rebasing) to trigger the accounting break; no privileged action is required from the caller.

### Impact Explanation
Each `send()` call systematically under-escrows the underlying token on the source chain relative to what is credited/paid out on the destination chain. Over repeated use this:
- Drains the destination-chain custody reserve faster than the source-chain reserve accumulates it, since every cross-chain transfer over-pays the beneficiary by the fee amount.
- Eventually causes the destination `WrappedHyperFungibleToken` to run out of underlying balance, causing `onAccept` (and thus message delivery/finalization) to revert — a permanent denial of the bridge route for that asset once reserves are exhausted, and/or causes early users to effectively withdraw more value than they deposited at the expense of later users/legitimate reserve backing (a fund-theft/insolvency condition for the wrapped-token pool). This matches the required severity bar of concrete theft/permanent freezing of funds.

### Likelihood Explanation
Any unprivileged user with access to `send()` on a `WrappedHyperFungibleToken` deployment configured with a fee-on-transfer or deflationary underlying can repeatedly trigger this discrepancy with ordinary transactions; no elevated privileges, governance compromise, or malicious admin behavior is needed once such a token is (legitimately, not maliciously) chosen as the wrapped asset.

### Recommendation
In `send()`, measure the actual balance delta received by the contract (or the `dispatcher`/WETH deposit outcome) before encoding it into the dispatched `Message`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`:
```solidity
uint256 balBefore = IERC20(_underlying).balanceOf(address(this));
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
uint256 actualAmount = IERC20(_underlying).balanceOf(address(this)) - balBefore;
```
and use `actualAmount` (not `params.amount`) both in `_buildDispatchPost`'s `Message.amount` and the emitted `Sent` event. Apply the same fix to `WrappedHyperFungibleTokenUpgradeable.send()`, which has the identical pattern. [4](#0-3) 

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g. the `FeeOnTransferToken` test helper already present at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2690-2733`, which burns/deducts a bps fee on `transfer`/`transferFrom`) as `_underlying` for a `WrappedHyperFungibleToken` pair deployed on chain A and chain B.
2. On chain A, `alice` calls `send({dest: chainB, to: alice, amount: 1000e18, ...})`. Due to the 1% fee, chain A's contract balance only increases by `990e18`, but the dispatched `Message.amount` is `1000e18`.
3. Once delivered on chain B, `onAccept` calls `safeTransfer(alice, 1000e18)` from chain B's reserve — `10e18` more than was actually escrowed on chain A.
4. Repeating this drains chain B's reserve by the accumulated fee amount across all transfers, eventually causing `onAccept` to revert with insufficient balance (denial of service / broken bridge route), or allowing early exploiters to extract more value than deposited before the reserve is exhausted. [5](#0-4)

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
