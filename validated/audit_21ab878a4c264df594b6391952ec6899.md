Confirmed: the Tron variant of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) tracks `msgValue` while consuming native token legs but never refunds any leftover to the caller, unlike the EVM version at `evm/src/apps/IntentGatewayV2.sol:395-397` which explicitly does `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }`. This is a permanent-freezing-of-funds analog to the reported `payable`-but-unused-`msg.value` bug class, reachable by any unprivileged user submitting a `placeOrder` transaction.

### Title
Tron `IntentGatewayV2.placeOrder` never refunds excess native `msg.value`, permanently locking user funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` is `payable` and tracks unconsumed native value in a local `msgValue` variable as it pays for native input legs and the optional fee-swap, but the function ends without returning any leftover `msgValue` to the caller.

### Finding Description
`placeOrder` decrements `msgValue` for each native-token input leg [1](#0-0)  and again inside the fee-swap branch [2](#0-1) , but unlike its EVM counterpart, which explicitly refunds the remaining `msgValue` to `msg.sender` at the end of the function [3](#0-2) , the Tron version's `placeOrder` reaches its final `emit OrderPlaced(...)` and returns without any such refund step [4](#0-3) . Any native token sent beyond exactly what is consumed by input legs and the fee swap (e.g. `swapETHForExactTokens` returning unused input, or a user simply overestimating the required native amount) is silently retained by the contract with no accounting path to recover it — this mirrors the Allo `registerRecipient` root cause of a `payable` entry point that fails to forward/return `msg.value` it doesn't fully consume.

### Impact Explanation
Users calling `placeOrder{value: X}` on the Tron deployment who send more native token than strictly required (a very likely occurrence given `swapETHForExactTokens` refunds are never pulled back and users must estimate gas/slippage buffers) will have the excess permanently stuck in the `IntentGatewayV2` contract with no withdrawal mechanism for it, since it isn't tracked in `_orders` accounting. This is a direct, permanent loss of user funds reachable from a single unprivileged transaction.

### Likelihood Explanation
High: any Tron-side order placer paying with native token who slightly overestimates the required `msg.value` (a normal, expected client behavior, especially when quoting fee-swap amounts ahead of execution) will trigger the loss on every affected call, with no admin/relayer/malicious actor required.

### Recommendation
Add the same excess-value refund logic present in the EVM `IntentGatewayV2.placeOrder` (`_sendValue(msg.sender, msgValue)` if `msgValue > 0` after all native legs/fees are settled) to the Tron variant of `placeOrder`.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder{value: inputAmount + overpayment}(order, graffiti)` on the Tron deployment with a native-token input leg of `inputAmount`.
2. The loop at [1](#0-0)  decrements `msgValue` by exactly `inputAmount`, leaving `overpayment` unspent.
3. If `order.fees == 0`, the fee-swap branch is skipped entirely; if `order.fees > 0`, the swap will only consume what's needed via `swapETHForExactTokens`, potentially leaving `msgValue` still non-zero.
4. Execution reaches the end of the function and emits `OrderPlaced` without ever transferring the leftover `msgValue` back to `msg.sender`, permanently trapping `overpayment` in the contract (compare with the EVM test `testPlaceOrder_RefundsExcessNativeToken`, which validates refund behavior only exists in `evm/src/apps/IntentGatewayV2.sol` [5](#0-4) ).

    /// @notice Excess msg.value beyond native input legs is refunded to the user.
    function testPlaceOrder_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1 ether;
        uint256 overpayment = 0.5 ether;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(0), amount: inputAmount}); // native ETH

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userBalBefore = user.balance;

        vm.prank(user);
        intentGateway.placeOrder{value: inputAmount + overpayment}(order, bytes32(0));

        // User should only have spent inputAmount, overpayment refunded
        assertEq(user.balance, userBalBefore - inputAmount, "Overpayment should be refunded");
        assertEq(address(intentGateway).balance, inputAmount, "Gateway should only hold escrowed amount");
    }
