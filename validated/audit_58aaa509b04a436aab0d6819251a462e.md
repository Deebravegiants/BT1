### Title
Webhook Shop-Domain Header Is Not HMAC-Covered, Allowing Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used for webhook processing from an unauthenticated HTTP header, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the equality that the library's own documentation promises: "verify the request did indeed come from Shopify" for a *given shop*, when in fact only the payload bytes are verified, not the tenant identity attached to them.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `Request#shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header with no cryptographic binding to the body or its HMAC: [2](#0-1) 

`Registry.process` validates only that HMAC: [3](#0-2) 

and then hands the unauthenticated `shop` value directly to the app's handler via `WebhookMetadata`, which apps use as the tenant identifier (as shown in the gem's own docs example, `shop_domain: data.shop`).

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` — for webhook requests this is `secret` (the app's `api_secret_key`) applied over the body only: [4](#0-3) 

The security-relevant equality that should hold is: *the shop the app treats data as belonging to* == *the shop Shopify actually generated/signed the webhook for*. Because the shop header sits outside the signed bytes, that equality is not enforced by the gem — it is only true as long as the header is not tampered with in transit or forged by whoever can produce a validly-signed body.

Critically, for many webhook topics the body is generic/empty or otherwise identical across all shops for a given event type (e.g. `app/uninstalled`, GDPR redact topics, or any topic where a merchant's own store legitimately triggers a webhook with predictable/empty content). A merchant who owns a store receives real, validly-HMAC-signed webhook deliveries from Shopify for their *own* shop. Because the signature only covers the body (not the shop header), that same `(raw_body, hmac)` pair remains a cryptographically valid signature no matter what `shop-domain` header is attached. The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify," which overstates what is actually checked — it verifies the *body* came from Shopify, not that the *shop attribution* did.

### Impact Explanation
An attacker who legitimately installs the app on their own store (an "unprivileged internet user" with respect to any other tenant) can capture a real webhook delivery for their own shop and replay it directly to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. The HMAC still validates because it is computed only over the body. The app's handler then processes the event as if it originated from the victim shop — a cross-tenant boundary crossing driven entirely by an unauthenticated field, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a merchant/installer of the target app on some shop (unprivileged, self-service), and (2) at least one topic exists whose body content is shop-independent or attacker-influenceable (empty-body topics like `app/uninstalled` are common and standardized). No access to `api_secret_key`, tokens, or the victim's credentials is needed, making this reachable by any internet user who can install the app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material checked by `HmacValidator`, or explicitly cross-validate `request.shop` against an out-of-band trusted mapping (e.g., only accept webhooks for shops with an active, previously-established session/installation) before dispatching to the handler. At minimum, update `docs/usage/webhooks.md` to stop asserting that `Registry.process` "verifies the request did indeed come from Shopify" for the shop attribution, and document that consumers must independently bind `data.shop` to a known installed tenant before trusting it.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger (or wait for) an `app/uninstalled` webhook delivery from Shopify, which for many apps carries an empty JSON body `{}` and a valid `x-shopify-hmac-sha256` computed over that body with the app's `api_secret_key`.
2. Capture the `(raw_body="{}", hmac)` pair from that legitimate delivery.
3. POST directly to the app's webhook endpoint, reusing the identical `raw_body` and `hmac-sha256` header, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because `Request#to_signable_string` only checks `raw_body` [1](#0-0) , and `Registry.process` proceeds to invoke the `app/uninstalled` handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to act (e.g., revoke access/delete data) against a shop the attacker does not control.
