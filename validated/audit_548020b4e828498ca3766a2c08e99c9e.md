### Title
Hostile pair pre-seed can force graduation's locked LP to open materially off the curve-close price when the rebalance budget is exceeded - ([File: packages/contracts/src/Bonding.sol])

### Summary
alt.fun's analog of "front-running pool initialization to set an unfair price" is front-running `Bonding.finalizeGraduation`'s HyperSwap V2 pair creation. The protocol built a three-regime defense (`_seedUniswapV2Direct` / `_seedRebalancing` / `_pairRebalance`) specifically to close this gap, and it works for realistic pre-seed sizes. However, the rebalance leg caps its correcting swap at 99% of the graduation's own inventory (`_swapBudget`), and for a sufficiently lopsided attacker pre-seed the swap cannot fully correct the pool ratio. In that regime the protocol's own tests document that `finalizeGraduation` still succeeds but the LP is locked into `LPLock` at a price materially off the curve-close price — the exact "unfair initial price" outcome the original UniswapV3 report warns about, except here it lands on the protocol's own permanently-locked LP rather than merely the pre-seeder.

### Finding Description
`Bonding.finalizeGraduation` (packages/contracts/src/Bonding.sol lines 1000-1034) calls `_ensureUniswapV2Pair` and `_seedUniswapV2Direct` against a HyperSwap V2 pair that anyone can pre-create and pre-seed between phase 1 (`_enterGraduating`, which caches `tokensForLP`/`ltFromPair` at the last curve price) and phase 2 (`finalizeGraduation`). [1](#0-0) 

For a "mint pre-seed" (attacker calls `pair.mint(attacker)` against a self-funded, hostile-ratio deposit), `_seedRebalancing` computes a no-fee rebalance swap (`_noFeeSwapInput`) and executes it via `_pairRebalance`, capped at `_swapBudget(inventory) = 99% of the available side's inventory` (`tokensForLP` or `ltFromPair`), not at whatever swap size is actually needed to reach the curve-close ratio: [2](#0-1) 

When the optimal correcting swap exceeds that 99% budget (an extreme LT-rich or token-rich pre-seed), the swap only partially rebalances the pool before `_routerDepositAndDispose` deposits the remaining inventory via `router.addLiquidity`, which pulls the optimal amounts at the pool's *current* (still off-target) ratio: [3](#0-2) 

The team's own regression test documents this as an accepted residual: with `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200`, the optimal rebalance swap is shown to exceed the 99% budget, and after `finalizeGraduation` the pool price is asserted to be more than 20% off the curve-close price: [4](#0-3) 

The design note explicitly frames this as tolerated because the *pre-seeder's own* claim on the resulting LP stays non-profitable (P&L ≤ 0) once their over-funded side is arbed and swept to the owner: [5](#0-4) 

That P&L≤0 guarantee only covers the pre-seeder. It says nothing about the price at which `LPLock` — which holds the protocol's locked LP with no rescue/withdraw path in v1 — ends up seeded. Once the LP opens 20%+ (unbounded further for larger multiples, per the accompanying fuzz test bounding `seedMultiple` up to 1000×) off the curve-close price, any third-party arbitrageur (not the original pre-seeder) can trade against the mispriced pool and extract value from the protocol's own locked reserves, exactly analogous to Eve profiting off Bob's mis-initialized pool in the original report — except here the "Bob" whose deposit is drained is the protocol/`LPLock` itself, and the loss is unrecoverable because `LPLock` has no withdraw path.

### Impact Explanation
This satisfies the "LP seeded away from the curve close price" impact criterion directly: `LPLock`'s locked LP is demonstrably seeded at a price that can be an order of magnitude off the curve's fair close price when a hostile pre-seed exceeds the rebalance budget. Because `LPLock.recordLock` is a one-shot action with no subsequent rescue mechanism, and the mispriced reserves are immediately arbable by anyone (not just the original attacker), the value gap is a permanent, unrecoverable loss transferred out of the protocol's LP position to whichever arbitrageur closes the price gap first.

### Likelihood Explanation
Reaching this state requires only permissionless actions any unprivileged address can already take: create the HyperSwap pair via `factory.createPair`, transfer TOKEN and LT into it in a sufficiently lopsided ratio, and call `pair.mint(attacker)` — precisely the front-run window the codebase's own `AGENTS.md` and tests acknowledge exists between `_enterGraduating` and `finalizeGraduation`. The size needed to exceed the 99% swap budget is bounded only by the attacker's own capital (e.g., ~200× `ltFromPair` on one side per the existing test), which is attainable for tokens with a modest `ltFromPair`/`tokensForLP` graduation size. The team's own fuzz test (`testFuzz_hostilePreSeed_neverProfitable_neverBricks`) sweeps `seedMultiple` up to 1000×, confirming the mispricing scales with attacker-supplied capital rather than being capped by protocol logic.

### Recommendation
- Do not let `_routerDepositAndDispose` deposit at a materially off-target ratio when the rebalance swap was budget-capped rather than fully executed; instead, detect the capped case and either (a) burn/refund the excess inventory on the over-supplied side down to the amount that keeps the deposit at (or within a tight band of) the cached curve-close ratio, or (b) revert phase 2 in this specific case and let the keeper retry with a larger allotted budget/multiple transactions rather than accepting a large one-shot price gap.
- Alternatively, remove the fixed 99%-of-inventory cap and instead size the swap dynamically so that the *post-swap-and-deposit* ratio is guaranteed to be within a small, explicit bps tolerance of `ltFromPair/tokensForLP`, falling back to a documented multi-call rebalancing path for pre-seeds large enough that a single swap cannot correct them within slippage/impact limits.
- At minimum, add an explicit maximum-deviation assertion inside `_seedUniswapV2Direct`/`_routerDepositAndDispose` so that if the resulting locked-LP price ever exceeds an acceptable bound, the transaction reverts (favoring a stuck-but-safe state that a privileged rescue can address) rather than permanently locking mispriced LP into `LPLock`.

### Proof of Concept
The existing repository test already demonstrates the mechanics end-to-end: [6](#0-5) 
1. Launch and graduate a token to phase 1 (`_enterGraduating`), caching `tokensForLP`/`ltFromPair`.
2. Front-run: create the HyperSwap pair, deposit `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200`, call `pair.mint(griefer)`.
3. Call `bonding.finalizeGraduation(tokenAddr)` — it succeeds (no brick), but the resulting pool price is >20% off the curve-close ratio, and this gap is directly arbable by any third party against the LP locked in `LPLock`.

    /// @notice Phase 2: seed the V2 LP and lock it. Permissionless —
    ///         keeper drives the happy path; anyone can rescue a stuck token.
    /// @dev Bypasses the V2 router and calls `pair.mint(lpLock)`
    ///      directly. This is brick-proof against a front-runner pre-creating
    ///      the pair and dust-seeding it between phases.
    /// @dev Exchange-rate drift between phase 1 and phase 2 is accepted by
    ///      design. The cached `(tokensForLP, ltFromPair)` are pure pair-
    ///      state arithmetic — see `_prepareGraduationLiquidity`, which
    ///      never reads `exchangeRate()` — so the LP opens at the exact
    ///      LT-per-token ratio the curve closed at, regardless of how long
    ///      phase 2 takes. What drifts is only the USD denomination of the
    ///      LT side, which is inherent to using a leveraged token as the
    ///      curve reserve: holders accept that exposure when they buy in.
    ///      A keeper Worker drives finalize within ~60s of `TokenGraduating`,
    ///      so the practical drift window is single-digit seconds. No
    ///      freshness timestamp / staleness gate: a recompute would return
    ///      byte-identical values (inputs are frozen while
    ///      `Lifecycle.Graduating`), and re-pricing the LP at the live
    ///      `exchangeRate()` would break the zero-gap-in-LT-units invariant.
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

        uint256 protectedLT
    ) internal returns (uint256 liquidity) {

        uint256 remToken = IERC20(tokenAddress).balanceOf(address(this));

        // locked LP.

            IERC20(lt).forceApprove(routerAddr, remLT);

            IERC20(tokenAddress).forceApprove(routerAddr, 0);
            IERC20(lt).forceApprove(routerAddr, 0);

    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );

        // The over-funded LT side is arbed out by the rebalance swap and swept
        // to the owner — the pre-seeder cannot recover it.
        assertGt(
            lt.balanceOf(bonding.owner()) - ownerLtBefore,
            reserveLt / 2,
            "the over-funded LT side must be confiscated to the owner"
        );

        // P&L: the pre-seeder's residual LP, valued at the fair (curve-close)
        // price, is worth a fraction of what they deposited — the attack is
        // cost-negative.
        uint256 claimValue = _lpValueAtCurveClose(hyperPair, tokenAddr, grieferLp, tokensForLP, ltFromPair);
        uint256 depositValue = _depositValueAtCurveClose(reserveToken, reserveLt, tokensForLP, ltFromPair);
        assertLe(claimValue, depositValue, "pre-seeder must not profit (P&L <= 0)");
        assertLt(claimValue * 2, depositValue, "pre-seeder must lose materially, not merely break even");
    }
