### Title
Webhook shop/topic identity is read from unsigned headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies nothing but the request body bytes. However, `Registry.process` uses `request.shop`, `request.topic`, and `request.webhook_id` — all pulled straight from HTTP headers that are never included in the HMAC computation — to route and identify the merchant for a webhook delivery.

### Finding Description
`Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all derived from headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), none of which participate in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` trusts the (unauthenticated) header-derived `shop`, `topic`, and `webhook_id` once the body-only HMAC check passes, and hands them to the app's handler as the merchant/topic identity for the delivery: [4](#0-3) 

This breaks the intended identity binding: `hmac-signed(body) == body` is verified, but the binding the handler actually relies on is `shop-domain header == the shop that produced this signed body`, and that equality is never checked. Any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's shared `client_secret` — for example a malicious merchant who installs the app on their own store and receives a legitimate webhook delivery for a topic they control — can resubmit the identical body and HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) headers for a different, victim shop. `HmacValidator.validate` will still succeed because it only checks the body bytes, and `Registry.process` will dispatch the handler with `WebhookMetadata` claiming the victim shop as the source.

### Impact Explanation
This is a cross-tenant identity-attribution bypass: an unprivileged attacker who legitimately controls one shop can cause the host application to process attacker-supplied webhook bodies under an arbitrary victim shop's identity. Any handler logic keyed on `WebhookMetadata#shop` (e.g., updating that shop's local records, triggering shop-scoped side effects, or feeding `data_request`/`redact` compliance handlers) can be manipulated cross-tenant, meeting the "cross-tenant access" Critical-impact bar.

### Likelihood Explanation
Reaching this requires only an internet-reachable webhook endpoint (which every embedded app that uses this library must expose) and possession of one valid `(body, hmac)` pair — trivially obtainable by installing the target app on an attacker-owned development/test store and capturing a real webhook delivery, since the app's `client_secret` is shared across all shops and topics.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the signed payload used for HMAC verification, or independently bind the header-derived `shop`/`topic` to a value cryptographically tied to the delivery (e.g., verify that the `shop-domain` header matches a shop actually known/authorized for this app, or require callers to pass the full header set into `to_signable_string`). At minimum, document that consumers must not trust `WebhookMetadata#shop`/`#topic` without out-of-band verification, or extend `HmacValidator`/`Request` so the identity headers are bound into the signature check the same way `AuthQuery#to_signable_string` binds `shop`/`host` into the OAuth HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `products/update`) they control the body/topic for.
2. Shopify delivers `POST /webhooks` with body `B`, headers `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: products/update`.
3. Attacker resends the identical `B` and `H` to the same endpoint, replacing the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new(raw_body: B, headers: ...)` builds a request whose `to_signable_string` is unchanged (`B`), so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) still succeeds.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata.new(topic: "products/update", shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the host app to act on `B` as if it originated from `victim.myshopify.com`.
