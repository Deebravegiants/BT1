## Title
Full JSON-RPC request (including the `Auth` bearer token) is logged unredacted at Debug/Info level in the Vault gateway handlers - (File: `core/services/gateway/handlers/vault/handler.go`, `core/capabilities/vault/gw_handler.go`)

## Summary
`core/services/gateway/handlers/vault/handler.go:403` logs the entire `jsonrpc.Request[json.RawMessage]` object (`"request", req`) at Debug level, and `core/capabilities/vault/gw_handler.go:182` and `:231` log the full request/response objects at Debug/Info. The `Request.Auth` field is populated directly from the client-supplied `Authorization: Bearer <token>` header, so any operator running with `Log.Level = 'debug'` will have every caller's raw JWT written to logs in cleartext.

## Finding Description
The `Auth` field on `jsonrpc.Request[json.RawMessage]` is set from the unprivileged client's bearer token, confirmed by the system test helpers `outboundRequestWithoutAuth` (`req.Auth = ""`) and `mustMintVaultJWTForRequest`/`req.Auth = mustMintVaultJWTForRequest(...)` in `system-tests/tests/smoke/cre/vault_don_test_helpers.go:417,550,587,1241,1264`, and by `authorizer_test.go` constructing requests with `Auth: "jwt-token"`. [1](#0-0) [2](#0-1) 

Elsewhere in the same authorization pipeline, developers were careful never to log the raw token — `authorizer.go` and `jwt_based_auth.go` consistently log only `"hasAuth", req.Auth != ""` or derived claims. [3](#0-2) [4](#0-3) 

In contrast, `handler.go` logs the entire request object before authorization: [5](#0-4) 

And `gw_handler.go` logs the full request and full response objects: [6](#0-5) [7](#0-6) 

Notably, there is a regression test guarding against a *different* leak, whose comment explicitly acknowledges this pre-existing Debug log is left out of its scope: [8](#0-7)  This confirms the maintainers are aware of the log statement and have not remediated it, and that no test currently prevents `req.Auth` from being serialized into these two log lines.

Since Chainlink's structured logger (zap sugared logger via `Debugw`/`Infow`) will serialize the passed struct's exported fields, and `Auth` is a plain exported string field with no evident redaction/`MarshalLogObject` override, the raw bearer token will end up verbatim in the log output whenever `Log.Level` is set to `debug` (or `info` for the response log, which doesn't include Auth but could carry other response-side sensitive data — though the primary secret leak is the request's `Auth`).

## Impact Explanation
Disclosure of the raw JWT allows anyone with access to debug logs (log aggregation, journald, shipped logs, support bundles) to replay or otherwise use that token to impersonate the legitimate caller for vault operations (`vault.secrets.create/update/delete/list`), since `jwt_based_auth.go`'s `AuthorizeRequest` treats a valid token plus matching digest as sufficient identity proof. This is a credential/secret disclosure that enables request impersonation and unauthorized secret manipulation — an in-scope impact class (key/secret exfiltration, gateway request impersonation).

## Likelihood Explanation
The trigger requires only a supported node/gateway configuration (`Log.Level = 'debug'`, which is used in multiple standard test fixtures) and any unprivileged external client sending a vault JSON-RPC request with `Authorization: Bearer <token>` to the gateway's public HTTP endpoint. No privileged access, host access, or special network position is needed to cause the log write.

## Recommendation
At both call sites, avoid logging the raw request struct. Replace `"request", req` in `handler.go:403` and `"req", req` in `gw_handler.go:182` with a redacted view, e.g. log `"method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != ""`, mirroring the pattern already used in `authorizer.go` and `jwt_based_auth.go`. Also review the `"resp", response` log at `gw_handler.go:231` for any sensitive payload fields before leaving it at Info level.

## Proof of Concept
1. Start a node/gateway with `Log.Level = 'debug'`.
2. As an unprivileged client, send a `vault.secrets.list` (or create/update/delete) JSON-RPC request to the gateway HTTP endpoint with header `Authorization: Bearer <JWT>`.
3. Inspect the debug log output for the message `"handling vault request"` at `core/services/gateway/handlers/vault/handler.go:403` or `"received message from gateway"` at `core/capabilities/vault/gw_handler.go:182`; the serialized `req` field contains the full JWT in the `Auth` value in cleartext.
4. A Go unit test analogous to `TestVaultHandler_InvalidParamsDoesNotLogRawParams` (`core/services/gateway/handlers/vault/handler_test.go:1016`), but observing at `Debug` level and asserting the log entry for `"handling vault request"` does not contain the token string, would fail against current code, confirming the leak.
