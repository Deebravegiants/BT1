### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then trusts the `X-Shopify-Shop-Domain` header — which is *not* covered by that HMAC — to decide which merchant's data the payload belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (header value) to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature — it never incorporates `shop`, `topic`, or any header into the signed material: [4](#0-3) 

The identity binding that should hold is:

`shop that produced the HMAC-signed body == shop passed to the handler as WebhookMetadata#shop`

This equality is never enforced. The HMAC only proves "this body was signed with the app's `client_secret`" — it says nothing about which shop it belongs to. The shop attribution comes entirely from an attacker-controllable HTTP header.

### Impact Explanation
Any user capable of getting the app to emit one legitimately-signed webhook to their own store (a normal, unprivileged action — installing the app, placing an order, updating a product, or even uninstalling the app to trigger `app/uninstalled`) obtains a valid `(raw_body, hmac)` pair signed with the app's `client_secret`. They can then replay that exact body+signature to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `X-Shopify-Topic`) header to name a **different, victim shop**. `HmacValidator.validate` still passes because it never checked the header, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain.

Host applications built on this gem key their persistence/logic off `WebhookMetadata#shop` (e.g., deleting the victim's stored session/access token on a forged `app/uninstalled` webhook, or writing attacker-controlled order/customer data under the victim's tenant). This is a cross-tenant access/data-integrity break stemming directly from an identity field ("shop") being acted upon while not being covered by the authentication mechanism (HMAC), matching the impact bar for cross-tenant access.

### Likelihood Explanation
Requires no secrets, tokens, or privileged access — only the ability to be a normal user of any shop that has the same app installed (extremely common for public/multi-tenant apps), and the ability to send an arbitrary HTTP POST with modified headers to the app's public webhook endpoint. Straightforward to exploit once one has observed the wire format of one's own legitimate webhook.

### Recommendation
Include the shop domain (and ideally topic) in the signed material, or independently verify that the shop the payload claims comes from a domain to which the `client_secret`-holding app actually has an active install/session, before trusting `request.shop` in `WebhookMetadata`. At minimum, the gem should document/enforce that hosts must independently verify shop ownership rather than trusting the header value that `Registry.process` currently propagates unchecked.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook topic subscribed by the app (e.g., `orders/create`), capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify to the app's webhook URL.
2. Attacker crafts a new POST to the same webhook endpoint with:
   - `raw_body = B` (unchanged)
   - `X-Shopify-Hmac-Sha256 = H` (unchanged)
   - `X-Shopify-Topic = orders/create` (unchanged)
   - `X-Shopify-Shop-Domain = victim.myshopify.com` (attacker-substituted)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares to `H` — this succeeds because the signature only ever covered `B`, per `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) and `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and processes attacker-controlled order data as if it belonged to `victim.myshopify.com`.
