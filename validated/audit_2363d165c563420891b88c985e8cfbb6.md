## Analysis

The reported bug class — an externally callable function that performs an **arbitrary, caller-supplied external call** and then moves out whatever balance the contract is holding, with **no access control** — has a direct structural analog in Hyperbridge's `CallDispatcher` contract.

### Root cause [1](#0-0) 

`CallDispatcher.dispatch(bytes memory encoded)` is `external` with **no caller restriction whatsoever**. It decodes an ABI-encoded `Call[]` array — `to`, `value`, `data` — supplied entirely by the caller, and executes each call with `to.call{value: call.value}(call.data)`. The only guard is that `to` must have code (`NotContract`). Anyone, not just the apps that are supposed to use it (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, etc.), can invoke `dispatch()` directly and force the `CallDispatcher` to send out any native ETH or send/spend any ERC20 balance it currently holds, to any target address they choose.

Compounding this, `CallDispatcher` also has an unrestricted `receive()`: [2](#0-1) 

`CallDispatcher` is used as a **shared singleton** across the intent gateway and token-bridge apps — assets are transferred to it and then swept back via `ICallDispatcher(dispatcher).dispatch(...)` calls inside `IntentGatewayV2`/`IntentsBase`/`HyperFungibleToken`/`WrappedHyperFungibleToken` flows: [3](#0-2) [4](#0-3) [5](#0-4) 

Because `dispatch()` itself carries no restriction to "only the app that funded me" (unlike, e.g., `onlyHost` used on `onAccept`/`onPostRequestTimeout`), any native ETH that ever lands on the `CallDispatcher` — whether from a swap-router refund routed back to the dispatcher, a direct transfer via its permissive `receive()`, or any ERC20 dust that has not yet been swept in the very same atomic transaction — is a balance that **any unprivileged external account can immediately drain** by front-running/back-running with their own `dispatch()` call targeting a contract of their choosing.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows any external caller to drain balances held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` executes an attacker-controlled `Call[]` (arbitrary `to`/`value`/`data`) with no access control, and the contract also accepts arbitrary ETH via an unrestricted `receive()`. Any account can call `dispatch()` at any time to route the dispatcher's current native/token balance to a target of its choosing — exactly the "unauthenticated D3Callee-style external call + fund exfiltration" bug class from the reference report.

### Finding Description
`CallDispatcher` is a shared, address-referenced utility contract used by `IntentGatewayV2`/`IntentsBase` and the `HyperFungibleToken`/`WrappedHyperFungibleToken` family to execute pre/post-dispatch calldata on behalf of orders and cross-chain transfers [6](#0-5) . These apps transiently transfer assets to the dispatcher's address, invoke `dispatch()` to run swap/DeFi calls, then invoke `dispatch()` again to sweep resulting balances back out [7](#0-6) .

The `dispatch()` function itself, however, is completely public and unauthenticated:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [8](#0-7) 

There is no check that `msg.sender` is one of the trusted apps (gateway/HFT contracts) that are supposed to be the only legitimate drivers of this contract. Combined with the unrestricted `receive() external payable` [2](#0-1) , this makes `CallDispatcher` a generic, permissionless "drain whatever is here" primitive: whatever native ETH or ERC20 tokens are resident on the dispatcher's address at any point (from a router refund landing on it mid-flow, a stray direct transfer, or any dust not yet swept) can be redirected by an attacker's own `dispatch()` call to an attacker-controlled contract, mirroring the D3Callee flaw where `router`/`routeData` are fully attacker-supplied and the function then moves out the contract's token balance with no authorization check.

### Impact Explanation
Because `CallDispatcher` is shared across all intent-gateway and HFT-token deployments that reference the same dispatcher address, any balance transiently or accidentally held by it is exposed to theft by an arbitrary, unprivileged account — a permanent loss of funds for whichever order/transfer flow that balance belonged to. This satisfies the "concrete theft of funds" bar via a single unauthenticated call reachable by any address with no special privileges.

### Likelihood Explanation
Exploitation requires only a plain transaction calling `dispatch()` with a self-crafted `Call[]`; no proofs, consensus interaction, or privileged role is needed — identical in triviality to the original D3Callee report. The main variable is whether/when a nonzero balance sits on the dispatcher outside of a single atomic sweep (e.g., ETH refunds from routers landing on the dispatcher, direct sends exploiting the open `receive()`, or partial-fill/edge-case flows that don't fully sweep before returning control). Given `CallDispatcher` is a long-lived, address-pinned singleton reused by many transactions across many users, any window where it holds value is an attacker's opportunity.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allow-list (e.g., an immutable/owner-settable set of authorized app addresses, or pass the authorized caller in the constructor and gate with `onlyAuthorized`), analogous to the `onlyLiquidator` fix recommended in the source report. Additionally, consider restricting or removing the unconditional `receive()` (or sweeping/limiting standing balances) so the dispatcher never holds funds outside of the single atomic call sequence that is supposed to use them.

### Proof of Concept
1. Attacker deploys a trivial contract `Sink` with a `receive()`/fallback so it has code (`extcodesize > 0`).
2. Attacker observes (or otherwise causes) the shared `CallDispatcher` instance to hold a nonzero ETH or ERC20 balance (e.g., ETH sent directly to it, or a residual balance from a router refund not yet swept in the same transaction as a legitimate app's flow).
3. Attacker calls:
```solidity
Call[] memory calls = new Call[](1);
calls[0] = Call({ to: address(sink), value: address(callDispatcher).balance, data: "" });
ICallDispatcher(callDispatcher).dispatch(abi.encode(calls));
```
4. Since `dispatch()` has no caller check, this succeeds and the dispatcher's entire ETH balance is sent to the attacker's `Sink` contract — analogous to the `TestRouter`/`D3Callee` PoC in the source report, where an attacker-supplied call target is unconditionally executed and used to exfiltrate the contract's held funds.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}
```
