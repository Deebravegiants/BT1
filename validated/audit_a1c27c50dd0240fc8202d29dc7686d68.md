### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) header trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable payload solely from the raw HTTP body (`to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's `WebhookHandler` are read directly from unauthenticated HTTP headers. The binding the HMAC is supposed to guarantee — "this request body came from Shopify for shop X" — never actually covers `X` (the shop identity), so an attacker who can obtain any one genuinely-signed webhook delivery (trivially available to them by installing the app on their own store) can replay it with the `shop-domain` header swapped to a victim shop, producing a request that still passes `HmacValidator.validate` but is now attributed to the wrong tenant.

### Finding Description
`Utils::VerifiableQuery` requires two things from any signable object: an `hmac` and a `to_signable_string`. `HmacValidator.validate` recomputes the HMAC exclusively over `to_signable_string` and compares it to the supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, and the signature (`hmac`) comes from the `X-Shopify-Hmac-Sha256` header: [2](#0-1) [3](#0-2) 

But the identity fields that a host application uses to route/attribute the webhook — `shop`, `topic`, `webhook_id`, `api_version` — are pulled straight from HTTP headers with no cryptographic tie to the signed body: [4](#0-3) 

These same header-derived values are what get packaged into `WebhookMetadata` and passed to the app's `handle` callback, which is expected to trust `data.shop` as the tenant identity for the event: [5](#0-4) 

**Broken equality**: the intended invariant is `hmac_signed_bytes == bytes_used_to_identify_the_tenant`. In this implementation, `hmac_signed_bytes == raw_body` while `tenant_identity == headers["shopify-shop-domain"]`, i.e. `hmac_signed_bytes != tenant_identity`. The signature proves "the body was produced by Shopify" but proves nothing about which shop the body belongs to.

### Impact Explanation
This is a cross-tenant data confusion primitive: any unprivileged actor who can install the app on their own (attacker-controlled) shop receives real, validly HMAC-signed webhook deliveries for that shop. Because the shop attribution is carried in a header outside the signed content, that same signed body/HMAC pair remains valid if replayed with the `X-Shopify-Shop-Domain` header changed to a victim's shop domain. An app that keys any behavior off `data.shop` (e.g., looking up the victim's stored access token, updating victim-shop records, billing, GDPR/customer-data webhooks) can be made to process attacker-supplied body content as if it originated from the victim shop — a cross-tenant access condition.

### Likelihood Explanation
Exploitation requires only: (1) attacker-controlled Shopify store installing the app (a normal onboarding capability, no privileged secrets needed), (2) ability to capture a legitimate webhook delivery to their own configured endpoint, and (3) ability to replay the HTTP request to the app's public webhook endpoint with a modified `shop-domain` header. None of this requires the app's `client_secret`/`api_secret_key`, an access token, or any credential belonging to the victim — it is purely a property of how this gem structures the verifiable payload.

### Recommendation
Include the shop-identifying header(s) (and ideally `topic`/`webhook_id`/`api_version`) in the HMAC-covered signable string, or otherwise cryptographically bind the header-derived `shop` to the verified body (e.g., require the body's own shop-scoped fields to match the header before trusting it). At minimum, document that `Request#shop` is unauthenticated and must not be used as a sole tenant key without additional server-side validation (e.g., cross-checking against the shop for which the webhook subscription/access token was registered).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures the app's webhook endpoint to receive, say, `orders/create`.
2. Shopify sends a legitimately signed webhook: headers include `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, plus a JSON body the attacker fully controls (order content on their own store).
3. Attacker captures this exact HTTP request, then re-sends it to the app's public webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` and leaving the body and `X-Shopify-Hmac-Sha256` unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request object; `HmacValidator.validate` recomputes the HMAC over `raw_body` only (per `to_signable_string`) — [3](#0-2)  — and it matches, since the body wasn't altered.
5. The host app's handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and the attacker-controlled body, and processes it as a trusted event for the victim tenant.

Note: I was not able to load `lib/shopify_api/webhooks/registry.rb` in this session to confirm the exact call sequence from raw request to `handler.handle`, so the precise integration glue code could not be cited directly; the vulnerable trust boundary is demonstrated conclusively in `request.rb` and `webhook_handler.rb` above.
