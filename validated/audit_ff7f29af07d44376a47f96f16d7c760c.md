### Title
Webhook tenant identity (`shop-domain`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all taken directly from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` only verifies the bytes returned by `to_signable_string` against the `hmac-sha256` header [3](#0-2) , so the tenant identity (`shop`) that `Registry.process` hands to the app's handler is never cryptographically bound to the signature that authenticates the request [4](#0-3) .

### Finding Description
This is the same bug class as the reported LayerZero issue: a value that is *acted upon* (the destination/tenant identity) is not the value that is *cryptographically verified* (the signed bytes). In `WstUsdcBridge`, the destination chain/address wasn't part of the properly-typed, bound payload. Here, the equality that should hold is:

`shop identity trusted by Registry.process == shop identity covered by HmacValidator.validate`

But in reality:
- `HmacValidator.validate(request)` verifies `HMAC(raw_body, secret) == header["hmac-sha256"]` — a statement only about the *body*.
- `Registry.process` uses `request.shop`, which is `headers["shopify-shop-domain"]` (or `x-shopify-shop-domain"`) — a header value with no signature coverage at all [5](#0-4) .

Because the HMAC is a function of `secret` and `raw_body` only, any request whose body is fixed or predictable (e.g., topics with an empty JSON body, or a body an attacker has already seen delivered to their own shop) produces the *same valid signature* regardless of which `shop-domain` header accompanies it. An attacker who operates their own installed instance of the app (a legitimate, unprivileged merchant/tenant with no special privilege over other tenants) can:
1. Capture one legitimately-signed webhook delivery to their own shop (valid `raw_body` + valid `hmac-sha256`).
2. Replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint, substituting the `shopify-shop-domain` (and/or `shopify-webhook-id`, `shopify-topic`) header with a victim shop's domain.
3. `HmacValidator.validate` still returns `true` because it only checks the untouched body bytes.
4. `Registry.process` dispatches to the topic handler with `WebhookMetadata.new(shop: request.shop, ...)` where `request.shop` is now the victim's domain, even though the signed content actually originated from the attacker's own shop.

This lets a single-tenant attacker forge apparently-authentic webhook events attributed to an arbitrary other shop, breaking the multi-tenant isolation the gem is supposed to provide to host applications that key state (dedup, event logs, per-shop side effects) off `WebhookMetadata#shop`.

### Impact Explanation
This crosses the tenant boundary the gem is meant to enforce: a webhook payload the app is meant to trust as "signed by our client_secret for this exact request" ends up attributing arbitrary content to a shop the attacker does not own, purely because the shop identity is carried outside the signed bytes. This matches the "cross-tenant access" impact category, since any host application that reacts to `WebhookMetadata#shop` (e.g., `shop/redact`, `app/uninstalled`, order/customer topics, most of which have fixed or attacker-observable body shapes) can be tricked into performing shop-B actions/state changes triggered by attacker-controlled, shop-A-signed traffic.

### Likelihood Explanation
Requires only that the attacker control one legitimately-signed webhook delivery for their own tenant (trivial for any merchant who installs the app) and the ability to POST arbitrary headers to the app's public webhook endpoint (the gem does not perform any additional binding, e.g. checking that `shop` was part of the signed payload, or validating that `shop`/`webhook_id` corresponds to a subscription actually owned by that signature). No access to `client_secret`, tokens, or any other credential is required.

### Recommendation
Bind the tenant identity into what is verified: extend `VerifiableQuery`/`HmacValidator` so webhook verification incorporates `shop`, `topic`, and `webhook_id` (or otherwise validate them against Shopify's response independent of headers) rather than trusting header values whose only requirement is "accompanies a validly-HMAC'd body." At minimum, document/enforce that `Registry.process` treat `request.shop` as untrusted unless it is corroborated by a source that is part of the signed bytes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. topic `app/uninstalled` with `raw_body = "{}"`, header `shopify-hmac-sha256 = Base64(HMAC-SHA256(secret, "{}"))`.
2. Attacker replays this exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(secret, "{}")`, matches the supplied signature, and returns `true` [6](#0-5) .
4. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the host app to process a forged uninstall/redact/etc. event as if it genuinely originated from the victim shop.
