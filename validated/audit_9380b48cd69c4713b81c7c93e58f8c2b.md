## Analog Found

### Title
Unbounded `handle_unsigned` message batches and unbounded GRANDPA proof headers allow permissionless, fee-free saturation of every node's transaction-pool validation - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Call::handle_unsigned` accepts an unbounded `Vec<Message>` and is validated as a **free, unsigned, unauthenticated** transaction by `ValidateUnsigned::validate_unsigned`, which runs `Self::execute(messages.clone())` — i.e. full cryptographic proof verification for every message in the batch — on **every full node** that receives the gossiped transaction, before the transaction is even included in a block. Individual message types inside that batch (in particular GRANDPA `FinalityProof::unknown_headers`) are also unbounded in length. This mirrors the Mattermost pattern: content that is cheap to submit (a small, malformed or partially-valid batch/proof) but expensive to process (ancestry-chain construction, per-precommit signature checks, trie/SPV verification for every element) is repeatedly submitted to consume a resource shared by all participants — here the tx-pool validation CPU time on every relaying/full node — degrading message delivery for the whole network rather than a single uploader's server slot.

### Finding Description
`handle_unsigned` is declared with no bound on the message vector: [1](#0-0) 

Its `ValidateUnsigned` implementation runs the same `Self::execute` path used for actual dispatch, purely to compute a `ValidTransaction`, and does this for `TransactionSource::External` — i.e. for every unsigned transaction gossiped to the node, regardless of whether it will ever be included in a block: [2](#0-1) 

`Self::execute` maps every message through `handle_incoming_message`, which performs full proof/consensus verification (trie reads, SPV verification, GRANDPA/BEEFY signature checks, etc.) before any rejection for size or validity is applied at the batch level: [3](#0-2) 

Because the pallet documentation itself states cross-chain messages are "executed for free as unsigned transactions" and relies on transaction-pool validation to filter bad proofs, the entire spam-resistance model depends on `validate_unsigned` being cheap — but it is not: it is exactly as expensive as full message execution.

Compounding this, GRANDPA's `FinalityProof.unknown_headers` has no length cap anywhere in the consensus-client or verifier code path (`grep` for header-length bounds returned nothing), so `verify_grandpa_finality_proof` builds an `AncestryChain` and performs `ancestry()` walks and per-precommit signature verification over an attacker-controlled number of headers: [4](#0-3) [5](#0-4) 

A relayer/attacker can submit an unsigned `handle_unsigned` extrinsic containing (a) many messages in one batch, and/or (b) a GRANDPA `ConsensusMessage` with a large `unknown_headers` list and a syntactically valid-looking but ultimately rejected justification. Each such transaction is small on the wire (cheap to construct and gossip) but forces every node that receives it — and every node it propagates to — to perform the full, expensive verification path in `validate_unsigned` before rejecting it, with no fee charged since the call is unsigned. Repeating this (analogous to "repeatedly uploading small documents that are cheap to upload but expensive to extract") saturates the CPU used for transaction-pool validation across the network, delaying legitimate ISMP message delivery for all users — directly matching the "degrade file uploads for all users on the server" impact class from the reference CVE, translated to "degrade message delivery for all users on the network."

### Impact Explanation
This is a shared-resource denial of service reachable by a single, unauthenticated, fee-free extrinsic submission (`handle_unsigned`), gossiped to and independently validated by every full node. Sustained submission of maximally expensive-but-invalid batches/proofs can starve transaction-pool validation threads network-wide, delaying inclusion of legitimate consensus updates and ISMP requests/responses — a route becoming effectively unable to deliver messages in a timely fashion, which the validation rules for this task class treat as Medium/High-severity impact.

### Likelihood Explanation
No signer, no fee, and no batch-size or header-count bound stand between an attacker and the expensive verification path; `TransactionSource::External` traffic reaches `validate_unsigned` from any peer. The only friction is `longevity: 25` and pool `provides`/dedup tags, which prevent an identical resubmission from lingering but do not stop rapid-fire distinct submissions (varying a single byte changes the `provides` hash and priority-bucket tag), so this is straightforward to automate.

### Recommendation
- Bound `handle_unsigned`'s `messages: Vec<Message>` with a `BoundedVec`/explicit maximum length enforced in `validate_unsigned` before any per-message execution.
- Enforce a maximum `unknown_headers` length (and similarly bound other consensus-message header/route vectors) in the GRANDPA verifier before `AncestryChain` construction and signature verification, mirroring the `MAX_PROOF_DEPTH`/`MAX_VALIDATORS` bounds already applied elsewhere (e.g. Pharos SPV, validator-set proofs).
- Consider a cheap, bounded-cost pre-check (structural/size validation, cached-failure banning) that runs before invoking full `Self::execute` inside `validate_unsigned`, so obviously-malformed or previously-rejected payloads are discarded without repeating expensive cryptographic work on every node.

### Proof of Concept
1. Craft a single unsigned `Ismp::handle_unsigned` extrinsic whose `messages` contains a `Message::Consensus` GRANDPA update with an `unknown_headers` vector of many thousands of minimal (near-empty) headers and a justification that fails verification only after the ancestry walk/signature checks run.
2. Submit it repeatedly with a different trailing byte each time (to avoid `provides`-tag dedup) via `subxt`'s unsigned submission path, as already exercised in the existing test/tooling: [6](#0-5) 
3. Observe CPU time spent in `validate_unsigned` → `Self::execute` → `verify_grandpa_finality_proof` on every full node that receives the gossiped transaction, growing linearly with `unknown_headers.len()`, for zero-fee transactions that are ultimately rejected — demonstrating the cheap-to-submit/expensive-to-verify asymmetry that saturates the network's shared transaction-validation capacity.

pub fn verify_grandpa_finality_proof<H>(
	mut consensus_state: ConsensusState,
	finality_proof: FinalityProof<H>,
) -> Result<(ConsensusState, H, Vec<H256>, AncestryChain<H>), Error>
where
	H: Header<Hash = H256, Number = u32>,
	H::Number: finality_grandpa::BlockNumberOps + Into<u32>,
{
	// First validate unknown headers.
	let headers = AncestryChain::<H>::new(&finality_proof.unknown_headers);

	let target = finality_proof
		.unknown_headers
		.iter()
		.max_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	// this is illegal
	if target.hash() != finality_proof.block {
		Err(Error::LatestBlockMismatch)?;
	}

	let justification =
		GrandpaJustification::<H>::decode_all(&mut &finality_proof.justification[..])
			.map_err(|e| Error::DecodeJustification(alloc::format!("{e:?}")))?;

	if justification.commit.target_hash != finality_proof.block {
		Err(Error::JustificationTargetMismatch)?;
	}

	let from = consensus_state.latest_hash;

	let base = finality_proof
		.unknown_headers
		.iter()
		.min_by_key(|h| *h.number())
		.ok_or(Error::UnknownHeadersEmpty)?;

	if base.number() < &consensus_state.latest_height {
		headers
			.ancestry(base.hash(), consensus_state.latest_hash)
			.map_err(|_| Error::InvalidAncestry)?;
	}

	let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

	// 2. verify justification.
	justification
		.verify(consensus_state.current_set_id, &consensus_state.current_authorities)
		.map_err(|e| Error::JustificationVerify(e.to_string()))?;
