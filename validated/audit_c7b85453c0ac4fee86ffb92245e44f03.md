Audit Report

## Title
Unbounded `web_api_trigger` registrations combined with unbounded caller-supplied `Topics` cause O(N×M) DoS in the WebAPI Trigger gateway handler - (File: core/capabilities/webapi/trigger/trigger.go)

## Summary
`triggerConnectorHandler.RegisterTrigger` places no upper bound on `h.registeredWorkflows`, and `processTrigger` (invoked for every inbound `MethodWebAPITrigger` gateway message) performs a nested loop over all registered triggers × all caller-supplied `payload.Topics` entries, with no explicit cap on either dimension. This confirms the claim's described O(N×M) per-request cost pattern, gated only by the gateway's generic HTTP body-size limit rather than any topic- or trigger-count-specific bound.

## Finding Description
`RegisterTrigger` inserts into `h.registeredWorkflows` without any maximum-count check [1](#0-0) . `HandleGatewayMessage` unmarshals the untrusted payload and dispatches directly to `processTrigger` for `MethodWebAPITrigger` [2](#0-1) . `processTrigger` snapshots all registered triggers and iterates `triggers × topics` in a nested loop with no cap on `len(topics)` before the loop [3](#0-2) , unlike `trigger_subscriber.go`'s explicit `maxBatchedWorkflowIDs` truncation for its analogous fan-in path.

However, unlike the report's framing (which treats `Topics` size as effectively unbounded), the gateway's HTTP server enforces a general `MaxRequestBytesLimiter` on the entire raw request body before it ever reaches `ProcessRequest`/`HandleGatewayMessage` [4](#0-3) , configured via `cresettings.Default.GatewayIncomingPayloadSizeLimit` [5](#0-4) . This does not specifically cap topic count, but it does bound the total payload size (and therefore the practical number of topic strings) per request. I found no equivalent cap on the number of triggers a workflow owner (or the aggregate of all owners) can register via `RegisterTrigger`, and no cap on `AllowedTopics` per trigger — these growth vectors are genuinely unbounded in the code as written.

## Impact Explanation
This is a real, but moderate, quadratic-cost DoS vector: absent a global request-size limit's constraining effect, an attacker (or organic growth of legitimate workflow registrations) could still push CPU/latency cost of `processTrigger` up meaningfully by combining many registered triggers with a payload containing as many short topic strings as fit within the body-size limit. The generic HTTP body-size cap mitigates but does not eliminate the risk, since it is not designed with this nested-loop cost in mind, and there is no cap at all on the number of registered triggers. This matches a legitimate "unbounded iteration causing degraded gateway responsiveness for co-tenants" class of issue, consistent with a Medium-severity DoS classification, though real-world exploitability is somewhat blunted by the existing request-size limiter.

## Likelihood Explanation
Reaching `RegisterTrigger` only requires deploying workflows using the `web_api_trigger` capability (a normal, unprivileged tenant action), and reaching `processTrigger` only requires sending a standard gateway message with method `web_api_trigger` — the capability's intended external entry point, requiring no special privilege beyond being an allowed sender for at least one registered trigger's topic (to pass the `matchedWorkflows` check) or simply supplying garbage topics (which still costs O(N×M) iteration before returning "no Matching Workflow Topics"). The attack is trivially repeatable.

## Recommendation
- Cap the number of concurrently registered triggers in `RegisterTrigger` (return an error past a configurable maximum).
- Cap `len(reqConfig.AllowedTopics)` per trigger at registration time and/or cap `len(payload.Topics)` in `processTrigger` before the double loop, mirroring the `maxBatchedWorkflowIDs` truncation pattern in `core/capabilities/remote/trigger_subscriber.go`.
- Consider indexing triggers by topic (e.g., `map[topic][]*webapiTrigger`) to avoid the O(N×M) linear scan entirely.

## Proof of Concept
1. Register many triggers via `RegisterTrigger` (no cap enforced) to grow `h.registeredWorkflows`.
2. Send a `MethodWebAPITrigger` gateway message with `TriggerRequestPayload.Topics` containing as many short strings as fit under the gateway's `GatewayIncomingPayloadSizeLimit`.
3. Measure `processTrigger`'s wall-clock time relative to trigger count and topic count, verifying near-linear scaling in `len(triggers) * len(topics)`, and observe blocking/delay of subsequent gateway messages processed on the same connection/handler.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
