### Title
Webhook `shop` (and `topic`/`api_version`/`webhook-id`) header fields are trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Webhooks::Registry.process` validates never covers the `X-Shopify-Shop-Domain` (or `topic`/`api-version`/`webhook-id`) headers. This breaks the intended identity binding `hmac == HMAC(secret, body ∧ shop)` down to `hmac == HMAC(secret, body)`, letting an attacker who controls the headers but reuses a body+HMAC pair they legitimately received (e.g., from a webhook delivered to their own, self-installed instance of the same app) reattribute that payload to an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` recomputes the HMAC over whatever `to_signable_string` returns and compares it to the supplied `hmac` [1](#0-0) . For webhooks, `to_signable_string` is defined as just `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to that signature [2](#0-1) .

`Webhooks::Registry.process` only asserts `Utils::HmacValidator.validate(request)` before trusting `request.shop`, `request.topic`, and forwarding them, unmodified, to the app-supplied handler as `WebhookMetadata` [3](#0-2) . Because the client secret used to sign is shared across every shop that has installed the app (it is `Context.api_secret_key`, not a per-shop secret) [4](#0-3) , any body+HMAC pair that is valid for one installing shop is also a valid HMAC for the exact same body regardless of which shop domain header accompanies it.

Concretely: shop == shop the handler believes the data came from, but the gem only proves body == body signed by the app's secret; it never proves shop == shop that produced that HMAC. An attacker who installs the same public/multi-tenant app on their own (unprivileged) store receives real, validly-signed webhook deliveries for their own shop. They can replay that exact raw body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and, since `Request#topic`/`api_version` are likewise unauthenticated header reads, potentially those too) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` invokes the handler with `WebhookMetadata.new(shop: <attacker-chosen victim domain>, ...)`.

### Impact Explanation
Any app built on this gem that persists or acts on webhook data keyed by `WebhookMetadata#shop` (e.g., updating per-tenant order/customer/app-state records, or handling `app/uninstalled`, `shop/redact`, `customers/redact` for GDPR compliance) can be made to apply an attacker-controlled payload against a shop record the attacker does not own and never authorized. This is a cross-tenant data-integrity/access issue: it lets an unprivileged Shopify merchant who merely installs the same app inject or falsify events attributed to a different merchant's tenant, without ever needing that merchant's access token or credentials.

### Likelihood Explanation
Exploitation only requires the attacker to be a normal, unprivileged user of the target app (install it on their own store to receive at least one legitimate webhook), then replay the captured raw body/HMAC pair with a modified `shop`-domain header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed, which makes this readily reachable by any internet user with self-serve access to the app.

### Recommendation
Bind the shop (and other routing metadata) into the signed payload the gem validates, or otherwise cryptographically tie the `X-Shopify-Shop-Domain` header to the specific delivery: e.g., verify shop against a per-shop registered access token/session before invoking the handler, or extend `to_signable_string`/verification to include the shop domain in a way that can be checked against the caller-known destination for that webhook subscription, rather than trusting the header verbatim once only the body's HMAC has been checked.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (self-serve, unprivileged).
2. Shopify delivers a legitimate webhook to the app's endpoint:
   - Headers: `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over body B>`, `X-Shopify-Topic: orders/create`
   - Body: `B`
3. Attacker captures this request, then resends it to the same endpoint with `X-Shopify-Shop-Domain` replaced with `victim.myshopify.com`, keeping body `B` and the HMAC header identical.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC purely over `B` [5](#0-4)  — validation passes because `shop` was never part of the signed string.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"` [6](#0-5) , causing the app to process attacker-supplied data as if it originated from the victim's tenant.
