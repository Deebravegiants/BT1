Audit Report

## Title
Bridge `OutgoingToken` Credential Disclosed in Plaintext to Any Authenticated (View-Role) User - (File: `core/web/resolver/bridge.go`)

## Summary
The GraphQL `Bridge`/`Bridges` queries and the REST `bridge_types` `Index`/`Show` endpoints return each bridge's `OutgoingToken` in plaintext to any authenticated user, including one holding only `UserRoleView`, because these read paths are gated solely by `authenticateUser`, which checks session existence but not role. This lets a low-privilege, view-only account read the credential the node uses to authenticate outbound calls to external adapters.

## Finding Description
`BridgeType.OutgoingToken` is a persisted secret used by the node to authenticate to external bridge adapters, stored without hashing (`core/bridges/bridge_type.go:57-68`), and serialized unconditionally (no `omitempty`) in `presenters.BridgeResource` (`core/web/presenters/bridges.go:10-22`) — unlike `IncomingToken`, which is `omitempty` and only ever populated at creation time.

The GraphQL `Bridge` and `Bridges` resolvers gate access with `authenticateUser(ctx)` only: [1](#0-0) 
`authenticateUser` merely checks for a valid session, granting "view" access with no role check, in contrast to `authenticateUserCanRun`/`authenticateUserCanEdit`/`authenticateUserIsAdmin`, which explicitly reject `UserRoleView`: [2](#0-1) 
The returned `BridgeResolver` unconditionally exposes `OutgoingToken()`: [3](#0-2) 
The REST `BridgeTypesController.Index`/`Show` handlers exhibit the same pattern, with no visible role-based gate and returning `presenters.NewBridgeResource(bt)`, which always includes `OutgoingToken`.

This is a genuine authorization-boundary bug: the codebase already establishes a four-tier role model (View/Run/Edit/Admin) and applies stricter checks elsewhere for mutating operations, but forgot (or intentionally omitted) an equivalent secret-redaction/role-gate for this specific read path, unlike the deliberate `omitempty` treatment given to `IncomingToken`.

## Impact Explanation
`OutgoingToken` is a credential secret (used to authenticate the node's outbound webhook calls to external adapters). Disclosure to a `UserRoleView` account — the lowest privilege tier, explicitly intended to be barred from job/bridge mutation per `authenticateUserCanRun`/`authenticateUserCanEdit` — constitutes credential/secret exfiltration and enables the view-role user to impersonate the node to the external adapter or replay/forge adapter-authenticated calls. This maps to the in-scope "key/secret exfiltration" impact category for node API authentication/role boundaries.

## Likelihood Explanation
Likelihood is high: no exploitation complexity is needed beyond possessing any valid authenticated session (even the lowest-privilege `UserRoleView`) and issuing a single GraphQL query or REST GET request — both `Bridge`/`Bridges` and `Index`/`Show` are directly reachable and return the secret in the normal response body, repeatably, for every configured bridge.

## Recommendation
Gate bridge read access (GraphQL `Bridge`/`Bridges` resolvers and REST `Index`/`Show`) behind `authenticateUserCanEdit` (or a dedicated secret-view permission), and/or redact `OutgoingToken` from list/show responses using `omitempty` semantics identical to `IncomingToken`, exposing it only once at creation/rotation time or via an explicit reveal action requiring re-authentication.

## Proof of Concept
1. Create/obtain a session for a user with `sessions.UserRoleView`.
2. Authenticate via `/sessions` to obtain a session cookie.
3. Issue GraphQL query:
```graphql
query { bridges { results { name outgoingToken } } }
```
or `GET /v2/bridge_types` / `GET /v2/bridge_types/:BridgeName`.
4. Observe the plaintext `outgoingToken` field populated in the response for every bridge, despite the account lacking edit/admin privileges — confirming the missing role gate in `authenticateUser` (`core/web/resolver/auth.go:11-17`) versus the stricter `authenticateUserCanEdit`/`authenticateUserIsAdmin` used for mutations.

// Authenticates the user from the session cookie, presence of user inherently provides 'view' access.
func authenticateUser(ctx context.Context) error {
	if _, ok := auth.GetGQLAuthenticatedSession(ctx); !ok {
		return unauthorizedError{}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'run' role.
func authenticateUserCanRun(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role == sessions.UserRoleView {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}

// Authenticates the user from the session cookie and asserts has 'admin' role
func authenticateUserIsAdmin(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role != sessions.UserRoleAdmin {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}
