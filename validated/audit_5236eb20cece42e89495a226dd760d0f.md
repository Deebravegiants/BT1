### Title
Webhook `shop` (tenant identifier) is taken from an HTTP header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, but exposes `shop`, `topic`, `webhook_id`, and `api_version` as values read directly from HTTP headers that are never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then dispatches the handler using this unauthenticated `shop` value as the tenant identifier, breaking the intended binding `hmac_signed_bytes == authenticated(shop)`.

### Finding Description
`Webhooks::Request#hmac` returns the HMAC read from the `shopify-hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from other HTTP headers (`shopify-shop-domain`, etc.) with no cryptographic tie to the HMAC: [3](#0-2) 

`HmacValidator.validate` (via `VerifiableQuery`) only proves that `@raw_body` was signed by the app's secret; it says nothing about which headers accompanied that body: [4](#0-3) 

The documented processing flow constructs the `Request` from `raw_body` and `headers` and calls `Registry.process`, which is expected to "verify the request did indeed come from Shopify" before invoking the app's handler with `data.shop` as the tenant to act on: [5](#0-4) [6](#0-5) 

Because `shop` is never part of the signable string, an attacker who can produce (or replay/capture) any single body+HMAC pair valid for the app's secret (e.g., from a webhook legitimately delivered to their own shop, or via other means to obtain a valid `(raw_body, hmac)` pair for content they control) can resubmit that same body with a forged `shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` will report success because it only rechecks the raw body against the same secret, and the gem will then hand the handler a `WebhookMetadata` claiming the payload belongs to the victim's shop.

### Impact Explanation
This breaks the equality `shop_used_by_handler == shop_covered_by_hmac`, since the shop is asserted only by an unauthenticated header while the cryptographic proof covers just the body. A host application that (correctly, per the documented API) trusts `data.shop` returned by this gem's webhook processing to route work to the appropriate shop/tenant (as shown in the gem's own example handler: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into associating an attacker-chosen shop with a payload, enabling cross-tenant data injection/misattribution — a High-severity cross-tenant issue arising from the gem's own verification primitive, not from host misuse.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair signed with the app's secret — for example from a webhook Shopify legitimately delivers to the attacker's own shop for the same app — and then replay that exact body to the app's webhook endpoint with a different `shopify-shop-domain` header. Any app that installs on multiple shops (the normal case) creates this condition naturally, making this a realistic, moderate-likelihood scenario without needing any privileged credentials.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the shop-domain header to the signed body (e.g., derive/verify shop identity independently through session/token lookup rather than trusting the header), so `HmacValidator.validate` fails whenever any of these fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the attacker's endpoint for `attacker-shop.myshopify.com` with body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B`).
3. Attacker replays the exact bytes to the app's webhook endpoint, substituting the header `shopify-shop-domain: victim-shop.myshopify.com` while keeping body `B` and HMAC header `H` unchanged.
4. `ShopifyAPI::Webhooks::Request#hmac` reads `H`; `to_signable_string` returns `B`; `HmacValidator.validate` recomputes HMAC of `B` and matches `H` — validation succeeds.
5. `ShopifyAPI::Webhooks::Registry.process` proceeds and invokes the app's handler with `data.shop == "victim-shop.myshopify.com"` even though the payload/HMAC never involved that shop, as shown in the request construction/documentation flow: [7](#0-6) [8](#0-7)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
