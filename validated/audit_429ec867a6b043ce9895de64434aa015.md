## Title
Check-then-act TOCTOU race in JWT replay-guard allows a single-use HTTP trigger token to authorize two concurrent workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtCache.isReplay(claims.ID)` under a read lock, then performs signer authorization, and only afterwards records the token as used via `jwtCache.recordUsage(claims.ID)` under a separate write lock. Because these are two independent, non-atomic lock acquisitions, two concurrent requests presenting the identical JWT can both pass the replay check before either records usage, both being forwarded to the DON as valid single-use triggers.

## Finding Description
`Authorize` verifies the JWT and extracts `claims.ID` (the `jti`), then calls `h.jwtCache.isReplay(claims.ID)`, which takes only a read lock and releases it immediately: [1](#0-0) . Execution then proceeds through workflow lookup and signer authorization, and only afterward calls `h.jwtCache.recordUsage(claims.ID)`, which acquires a separate write lock: [2](#0-1) . The full `Authorize` sequence shows the check and the record are not protected by a single critical section: [3](#0-2) . Two concurrent calls with the same `jti` can both observe `isReplay == false` before either calls `recordUsage`, allowing both to pass. This is forwarded via `authorizeRequest` in the HTTP trigger handler path to `SendToNode`/DON broadcast logic. The codebase's own `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go` demonstrates the correct atomic pattern (single lock covering check-and-insert), and its test explicitly validates race-safety under 100 concurrent goroutines — confirming the project is aware of and has fixed this exact bug class elsewhere, but not in `jwtReplayCache`.

## Impact Explanation
A single "one-time-use" workflow-execution JWT can be replayed exactly once under a race window, causing the DON to receive and process a duplicate `MethodWorkflowExecute` trigger for the same signed request. This undermines the single-use guarantee the code documents and tests for, and constitutes a limited request-duplication/impersonation vulnerability in the gateway's replay-prevention mechanism — an in-scope impact category (gateway request impersonation / unauthorized duplicate job trigger). It does not grant cross-signer authentication bypass since independent signer/authorization checks still apply to both racing requests.

## Likelihood Explanation
Exploitation only requires an attacker/client to send the same signed JWT to the gateway twice in rapid, concurrent succession — fully within the capability of any unprivileged client holding a single valid signed JWT, with no additional privilege, host access, or network manipulation needed. The race window is narrow (between read-lock release in `isReplay` and write-lock acquisition in `recordUsage`), making the timing constraint real but easily reproducible by firing simultaneous requests, especially under concurrent goroutine/connection handling on the gateway.

## Recommendation
Make the replay check-and-record atomic, mirroring `RequestReplayGuard.CheckAndRecord`: introduce a single method on `jwtReplayCache` that acquires the write lock once, checks for existing `jti`, inserts it if absent, and returns an error if already present — replacing the separate `isReplay`/`recordUsage` calls in `Authorize` with this one atomic call.

## Proof of Concept
1. Register a workflow and authorized signer key as in `TestWorkflowMetadataHandler_Authorize`.
2. Create one valid `MethodWorkflowExecute` request signed with a JWT (`jti = X`).
3. Launch two goroutines simultaneously, each calling `handler.Authorize(workflowID, tokenString, req)` with the identical token.
4. Both goroutines can observe `isReplay(X) == false` before either calls `recordUsage(X)`, so both succeed and are forwarded to the DON — unlike the existing sequential test `TestWorkflowMetadataHandler_Authorize/"JWT replay protection"` ( [4](#0-3) ), which only verifies rejection for sequential, non-concurrent calls and does not cover the concurrent race.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
