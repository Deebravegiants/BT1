Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` directly from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). This breaks the identity binding between the cryptographically verified content and the tenant-identifying `shop` value that the host application's webhook handler acts on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop`, `topic`, `webhook_id`, `api_version` are all read straight from HTTP headers with no cryptographic protection [2](#0-1) .

`ShopifyAPI::Webhooks::Registry.process` validates only this body HMAC via `Utils::HmacValidator.validate(request)`, and if it passes, it hands `request.shop` and `request.topic` — taken verbatim from the headers — straight to the app's handler inside `WebhookMetadata`, with no separate verification of those fields [3](#0-2) .

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field [4](#0-3) . Since `to_signable_string` for a webhook request is just the raw body, the signature proves only "this body was signed with our `api_secret_key`" — it says nothing about which shop or topic the payload was originally sent for.

Critically, `api_secret_key` is the app's single `client_secret`, shared across **every** shop that installs the app; it is not a per-shop secret. This means any merchant who has installed the app can receive a legitimate webhook (with a body+HMAC signed under the same shared secret) for their own store, then replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header to name a different victim shop. `HmacValidator.validate` will still return `true` because the body hash matches, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain [5](#0-4) .

This is the same class of bug as the reference report: a field that is *acted upon* (`shop`, used by the app to attribute/store the webhook data) is not covered by the authentication primitive (`HMAC` over the body only), letting the attacker forge the binding between verified bytes and claimed identity.

### Impact Explanation
This enables cross-tenant data injection/misattribution: a malicious merchant of a multi-tenant app can cause the host app to process attacker-controlled (their own legitimately-signed) webhook payloads as if they belonged to another merchant's shop, since the gem provides no protection for the `shop` header. Depending on what the host app's `WebhookHandler#handle` does with `data.shop` (e.g., look up/update records keyed by shop, trigger shop-scoped actions), this can lead to cross-tenant data corruption or unauthorized actions attributed to a different tenant. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires nothing beyond the ability to install the app as a legitimate (even low-trust) merchant/tenant and receive one webhook for one's own store — no `api_secret_key`, access token, or credential theft is required, since the shared secret is used implicitly through the normal webhook the attacker legitimately receives. The header manipulation itself is trivial (a raw HTTP POST to the app's public webhook endpoint with edited headers).

### Recommendation
Bind the tenant/topic identity into the verified signature rather than trusting headers separately from body verification:
- Require the host application (and document this requirement in `docs/usage/webhooks.md`) to independently verify that `request.shop` corresponds to a shop with an active, known installation before acting on the payload, and/or
- Have `Request#to_signable_string` (or a new validation step in `Registry.process`) incorporate the `shop-domain`, `topic`, and `webhook-id` headers into what is verified against Shopify's signature, so that any header tampering invalidates the check, and/or
- At minimum, cross-check that `request.shop` matches a shop domain for which the app currently holds a stored session/access token before dispatching to the handler.

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and `victim.myshopify.com` (multi-tenant app, shared `api_secret_key`).
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com`:
   ```
   POST /webhook
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of raw_body under shared api_secret_key>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"id":1,"note":"hello"}
   ```
   The attacker captures this raw body and its valid HMAC (attacker legitimately has access to their own store's webhook deliveries/logs).
3. Attacker replays the identical body and HMAC to the app's webhook endpoint but swaps the header:
   ```
   POST /webhook
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same valid HMAC as step 2, unchanged>
   X-Shopify-Shop-Domain: victim.myshopify.com
   Body: {"id":1,"note":"hello"}   (unchanged)
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes the unmodified body [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [7](#0-6) , even though the payload was never sent by Shopify for `victim.myshopify.com`.
