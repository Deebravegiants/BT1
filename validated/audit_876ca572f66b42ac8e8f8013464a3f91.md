Confirmed: `WebhookMetadata.shop` is passed directly to the app's handler, and the HMAC signature only covers the raw body, not the shop header, per `Request#to_signable_string` and `Registry.process`.

### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` identity that the app's handler subsequently trusts and acts on is taken from an unauthenticated HTTP header that is not part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) .

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` — i.e., only the body — and then forwards `request.shop` unmodified into `WebhookMetadata` given to the app's handler: [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string` (the body) and compares it with `OpenSSL.secure_compare`: [4](#0-3) .

The `WebhookMetadata` struct — the only identity information handed to the integrating app — carries `shop` as an untrusted, unverified field: [5](#0-4) .

This breaks the equality that should hold: `hmac_signed_bytes == bytes_the_handler_trusts_as_the_tenant_identity`. In reality, `hmac_signed_bytes = raw_body` while `tenant_identity = header["shop-domain"]`, and the two are never bound together.

Because every merchant's webhook is signed with the same app-wide `client_secret` (not a per-shop key), any user who can install the app on their own (e.g., free development) store legitimately receives valid `(raw_body, hmac)` pairs signed with that shared secret. Nothing prevents them from replaying that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a different, victim merchant. `HmacValidator.validate` will still return `true` because the signature check never inspects the shop header, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged user, using only their own legitimately-signed webhook traffic, can make the gem report webhook data as belonging to a shop they do not control. Any host application that uses `data.shop` from `WebhookMetadata` to route the payload to per-tenant business logic (order creation, uninstall handling, GDPR data requests, billing events, etc.) can be tricked into applying attacker-controlled data to another merchant's tenant context, i.e., cross-tenant access/injection.

### Likelihood Explanation
Likelihood is high for any attacker willing to install the target app on their own store: no special privileges, stolen credentials, or knowledge of `client_secret` are required. They only need one genuine webhook delivery from their own installation and the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-signed material, or otherwise authenticate the shop domain against the shop that the app's own webhook registration was created for (e.g., verify that `shop-domain` matches a shop with an active, known session/registration before trusting it), rather than trusting the header without cryptographic binding to the signature. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be independently verified by the consuming application before being used for tenant-scoped actions.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) so Shopify sends a legitimately HMAC-signed request to the app's webhook endpoint, with body `B` and header `x-shopify-hmac-sha256: H` (valid because it is signed with the app's real `client_secret`).
3. Capture `B` and `H`.
4. Send a new POST request directly to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid since the signature only covers the body), but `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` passes because `to_signable_string` never included the shop header: [1](#0-0) .
6. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`: [6](#0-5) , causing the host application to act on `victim.myshopify.com`'s tenant using attacker-supplied body content.
