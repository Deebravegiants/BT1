### Title
Zero-amount output leg in cross-chain `fillOrder` can permanently brick orders that use zero-value-transfer-reverting tokens - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` validates that `order.inputs` is non-empty and that each input asset has `amount != 0`, but performs no such validation on `order.output.assets`. A user (or a malicious order-placer griefing a solver/protocol) can place a cross-chain order with an output leg whose `amount == 0`. When a solver calls `fillOrder` → `_fillCrossChain`, the gateway unconditionally executes `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` for that leg even when `totalRequired == 0` and no surplus is provided, i.e., a zero-value ERC20 transfer.

### Finding Description
`_fillCrossChain` computes `totalRequired = order.output.assets[i].amount` and `solverAmount = options.outputs[i].amount`, requiring only `solverAmount >= totalRequired` [3](#0-2) . If `totalRequired == 0`, a solver satisfying the order with `solverAmount == 0` causes `beneficiaryShare` to also compute to 0 (since surplus = `solverAmount - totalRequired` = 0), and the subsequent `safeTransferFrom(..., 0)` call executes unconditionally for ERC20 output tokens — there is no `if (amount > 0)` guard before this call, unlike the analogous guard present in `_withdraw` (`if (amount == 0) continue;`) and in `IntentGatewayV2.sol`'s input-side loops (`if (order.inputs[i].amount == 0) revert InvalidInput();`).

Per the referenced GMX bug class, some ERC20-like tokens explicitly revert on a zero-value `transfer`/`transferFrom` (e.g., `stakedGLP` via its downstream `RewardTracker._unstake` `require(_amount > 0, ...)`). If Hyperbridge's `IntentGatewayV2`/`ExtrinsicIntents` cross-chain intents system is ever used with such a token as an output asset (the intents system is designed to be generically composable with arbitrary ERC20 tokens specified per-order, not a fixed allowlist), any order containing a zero-amount leg for that token type becomes permanently unfillable: every `fillOrder` attempt reverts inside the token's own zero-value check, and the order can never be completed. Because cross-chain fills are "all-or-nothing" (no partial fills are supported for cross-chain orders, per the contract's own documentation), this single bad leg blocks the entire order.

### Impact Explanation
This blocks legitimate solver fill flows and permanently freezes the user's escrowed input tokens on the source chain: since cross-chain fills are all-or-nothing, an order with one zero-amount output leg (whether placed by an honest user by mistake, or set up adversarially against a solver/keeper) can never be filled. The only recovery path is cancellation after the order's deadline passes, meaning funds are locked for the order's full duration and any surplus/fee value is lost; this satisfies "permanent freezing of funds" for the affected order until expiry-driven cancellation, and can be weaponized to indefinitely deny fills against a specific solver-integrated output token that reverts on zero-value transfers.

### Likelihood Explanation
Likelihood depends on whether any output token compatible with `IntentGatewayV2` reverts on a zero-value `transferFrom` (as `stakedGLP` does) and on an order having a zero-amount output leg — reachable by any unprivileged order-placer since `placeOrder` performs no non-zero validation on `order.output.assets`, so this is trivially triggerable by a single transaction with no special privileges.

### Recommendation
Validate in `placeOrder` that every `order.output.assets[i].amount > 0` (mirroring the existing input-side check), and/or guard the `safeTransferFrom` calls in `_fillCrossChain` and `_fillSameChain`'s beneficiary-transfer paths with an `if (amount > 0)` check before calling `IERC20.safeTransferFrom`, consistent with the pattern already used in `_withdraw`.

### Proof of Concept
1. User calls `placeOrder` with `order.output.assets = [{token: TOKEN_A, amount: 0}]` and a normal nonzero input; `placeOrder` accepts this since only `order.inputs` amounts are validated (`evm/src/apps/IntentGatewayV2.sol` lines 194–330).
2. A solver calls `fillOrder` → `_fillCrossChain` with `options.outputs[0].amount = 0` (satisfies `solverAmount < totalRequired` check trivially since both are 0).
3. `_fillCrossChain` executes `IERC20(TOKEN_A).safeTransferFrom(msg.sender, beneficiary, 0)` [4](#0-3) .
4. If `TOKEN_A` reverts on a zero-value transfer (as `stakedGLP`-class tokens do), this call reverts, and `fillOrder` can never succeed for this order — the escrowed input remains locked until deadline-based cancellation.
