Audit Report

## Title
View-role users can read bridge `outgoingToken` secrets via `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` - (File: core/web/presenters/bridges.go)

## Summary
The `BridgeResource` JSON presenter unconditionally serializes the bridge's `OutgoingToken` field (`json:"outgoingToken"`, no `omitempty`/redaction), and the routes `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` are registered without any `RequiresEditRole`/`RequiresAdminRole` wrapper, unlike the mutating verbs on the same resource. This allows any authenticated `view`-role user — the lowest privileged non-anonymous role in Chainlink's node RBAC — to read the plaintext outbound authentication credential for every configured bridge.

## Finding Description
`BridgeTypesController.Index` and `.Show` call `presenters.NewBridgeResource(bt)` directly on the ORM-fetched `bridges.BridgeType`, copying `b.OutgoingToken` into the response resource with no field-level filtering by caller role: [1](#0-0) 

The `BridgeResource` struct tags `OutgoingToken` as always-serialized JSON, in contrast to `IncomingToken`, which is explicitly `omitempty` and only populated at creation time: [2](#0-1) 

The route table confirms only `POST`, `PATCH`, and `DELETE` on `/v2/bridge_types*` are gated with `auth.RequiresEditRole`; the two `GET` routes have no role wrapper at all beyond the base `auth.Authenticate` middleware applied to the whole `/v2` group: [3](#0-2) 

This is corroborated by the RBAC integration test matrix, which explicitly encodes `viewOnlyAllowed: true` for both bridge GET routes, meaning this is the tested/expected behavior of the router: [4](#0-3) 

`OutgoingToken` is generated as a real secret (`utils.NewSecret(24)`) at bridge creation and stored/served in plaintext — it is the credential the node itself uses to authenticate to the external bridge/adapter URL: [5](#0-4) 

The presenter test fixture confirms `outgoingToken` is always present in the serialized response: [6](#0-5) 

## Impact Explanation
This exposes a live outbound-authentication secret to a role (`view`) that Chainlink's own role model intends to be read-only/monitoring-level, without edit or admin privileges. An attacker who compromises or is granted only a `view`-role account (e.g., a dashboard/monitoring account) can exfiltrate the `outgoingToken` for every bridge on the node and use it to impersonate the node's calls to external bridge/adapter endpoints, or reuse the token if it is used for other purposes by the adapter operator. This maps to the in-scope "key/secret exfiltration" impact category.

However, the RBAC route table is a stable, explicitly tested contract (`viewOnlyAllowed: true` is asserted intentionally in `auth_test.go`), which strongly suggests this is deliberate API design rather than an accidental oversight — bridge names/URLs/tokens are treated in this codebase as operationally-visible metadata to any authenticated node user, not as an admin-only secret comparable to node keys (CSA/ETH/OCR keys, which are properly gated). Chainlink's threat model for the node API generally assumes all four roles (`Admin`, `Edit`, `Run`, `View`) are trusted, non-adversarial internal operator accounts — the RBAC hierarchy exists to limit *write* capability, not to wall off all cross-role data visibility. There is no evidence this was reported/fixed as a vulnerability, nor documentation marking `outgoingToken` as a role-restricted secret.

## Likelihood Explanation
Low, in a bounty-eligible sense: exploitation requires the attacker to already hold valid, authenticated Chainlink node credentials (at minimum a `view`-role account), which is itself a privileged trust boundary inside an operator's node — this is a difference in *internal* privilege tiers among already-trusted node operators, not an unauthenticated-to-authenticated or authenticated-to-admin escalation from a truly untrusted external actor.

## Recommendation
No code change is being recommended as a confirmed vulnerability, but if a stricter secret-handling policy is desired, treat `outgoingToken` like `incomingToken` (redact/omit for read/view-role responses, or gate `GET /v2/bridge_types*` behind `auth.RequiresEditRole`) to align with the principle of least privilege for stored bridge secrets.

## Proof of Concept
1. Create a bridge as an edit/admin user (`POST /v2/bridge_types`), noting the `outgoingToken`.
2. Authenticate as a `UserRoleView` account.
3. `GET /v2/bridge_types/<BridgeName>` returns the plaintext `outgoingToken` in the JSON body, per the fixture in `core/web/presenters/bridges_test.go`.

---

Note: Because Chainlink's own RBAC test suite explicitly and consistently asserts that both `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` are `view`-role accessible, and because exploitation requires already holding a valid node account (not an unauthenticated/external attacker), this reads as intentional API design for internal-operator role separation rather than an unreviewed secret-disclosure bug. It is reported here as a finding for the security team to confirm intent, but does not meet the bar of a clearly unintended, previously-unknown vulnerability with unprivileged (non-operator) reachability required for a high-confidence bounty submission.

// Index lists Bridges, one page at a time.
func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
