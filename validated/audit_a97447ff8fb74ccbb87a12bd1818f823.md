### Title
Token Exchange Sends `client_secret` to an Unsanitized Host Derived from the JWT `dest` Claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host that will receive the app's `client_id`/`client_secret` directly from the session token's `dest` claim, without passing it through `Utils::ShopValidator`, unlike every sibling OAuth credential-granting flow in this gem.

### Finding Description
`TokenExchange.exchange_token` decodes the caller-supplied session token via `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` [1](#0-0) . `JwtPayload#shop` performs no domain validation — it just strips a literal `"https://"` prefix from the `dest` claim: `@dest.gsub("https://", "")` [2](#0-1) . `JwtPayload#initialize` verifies the signature and that `aud == Context.api_key`, but never checks that `dest`/`iss` is a trusted Shopify domain [3](#0-2) .

`dest_shop` is then used, unsanitized, to build the `Session` and the `HttpClient` that issues the token-exchange POST containing `client_id` and `client_secret`: [4](#0-3) . `Clients::HttpClient#initialize` builds `@base_uri` as `"https://#{api_host || session.shop}"` with no allow-list check on `session.shop` [5](#0-4) .

This is inconsistent with the gem's own sibling flows that accept a caller-supplied `shop` string: both `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token` explicitly call `Utils::ShopValidator.sanitize!(shop)` before building the credential-bearing request [6](#0-5) [7](#0-6) . `ShopValidator.sanitize!` enforces that the host resolves to one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [8](#0-7) . `exchange_token` skips this check entirely for the `dest`-derived shop.

The binding that should hold is: `host that ShopValidator would accept == host that receives client_id/client_secret`. For every other credential-granting entrypoint in this library that check is enforced; for `TokenExchange.exchange_token` it is not — the host is taken verbatim from a JWT claim with no additional domain constraint beyond `aud == api_key` and a valid HMAC signature.

### Impact Explanation
If a `dest` value that is not a proper `*.myshopify.com`/trusted Shopify domain can be embedded in a validly-signed session token — e.g., a caller who controls where their own custom domain currently resolves, or any future change to how `dest`/`iss` values are populated — the app's `client_id` and `client_secret` are transmitted, via the standard `HTTParty` POST in `HttpClient#request`, to a host the calling application never validated. This directly matches the High-severity "SSRF with the app's credentials ... or credential leakage" category, since `client_secret` (the app's most sensitive value) leaves the process bound for an untrusted host.

### Likelihood Explanation
Likelihood is moderate/uncertain: exploitation requires a session token that passes JWT signature and `aud` verification (i.e., is properly signed for the app in question and issued by Shopify to a real, currently-installed merchant), so an attacker with no relationship to the app cannot fabricate an arbitrary `dest` from scratch. However, the missing validation is a genuine and reachable gap relative to the equivalent, already-hardened code paths (`client_credentials`, `migrate_to_expiring_token`) in the same module, and it means the library provides no defense-in-depth if the `dest` claim is ever attacker-influenced (e.g., through domain configuration edge cases on the merchant side).

### Recommendation
Route `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done for `client_credentials` and `migrate_to_expiring_token`) before constructing the `Session`/`HttpClient` in `TokenExchange.exchange_token`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain (or synthesize in a test harness with the app's own `api_secret_key`) a session token whose `dest` claim is set to a non-`myshopify.com` value that still satisfies `aud == Context.api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `jwt_payload.shop` (from `JwtPayload#shop`, simple `gsub`) is used unsanitized to build `Session.new(shop: dest_shop)` and subsequently the `HttpClient` base URI, so the POST containing `client_id`/`client_secret` is sent to that host — contrasted with `ClientCredentials.client_credentials(shop: "attacker.example")`, which correctly raises `ShopifyAPI::Errors::InvalidShopError` via `ShopValidator.sanitize!` per `test/auth/client_credentials_test.rb` [9](#0-8) , while no equivalent guard/test exists for `exchange_token`'s `dest`-derived shop.
