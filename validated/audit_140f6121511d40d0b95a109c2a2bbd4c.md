### Title
Attacker-crafted HyperSwap pre-seed reserves cause an unbounded `Math.mulDiv` overflow in `Bonding._noFeeSwapInput`, permanently reverting `finalizeGraduation` and freezing all curve-raised LT and reserved tokens - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The external CVE (Ruby `OpenSSL::ASN1.decode`) is a crafted-input parsing bug that crashes the interpreter (DoS) because the decoder does not bound-check attacker-controlled data before doing unsafe memory arithmetic. The analog in alt.fun is `Bonding._noFeeSwapInput` (`packages/contracts/src/Bonding.sol:1507-1522`), which performs unchecked-scale arithmetic (`reserveIn * reserveOut` then `Math.mulDiv(..., targetN, targetD)`) over pool reserves and LP-seeding targets that an unprivileged attacker can shape via a permissionless HyperSwap V2 pre-seed. A hostile combination of pre-seed reserve magnitude and a self-engineered tiny `ltFromPair` graduation raise drives the `mulDiv` intermediate past `type(uint256).max`, causing an OZ `MathOverflowedMulDiv` revert. This propagates uncaught through `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`, permanently bricking phase 2 of graduation for that token — directly violating the protocol's own documented "brick-resistance contract" (`_seedUniswapV2Direct` MUST NEVER revert under any pre-seed shape, per `packages/contracts/AGENTS.md:191-200`).

### Finding Description
`finalizeGraduation` (`packages/contracts/src/Bonding.sol:1000-1034`) is permissionless phase 2 of the two-phase graduation flow. When the HyperSwap V2 pair already has non-zero `totalSupply()` (i.e., an attacker front-ran with `factory.createPair` + `transfer` + `pair.mint`, the documented "Regime 3 — mint pre-seed" attack, `AGENTS.md:176-189`), the code takes the rebalance path:

`_seedUniswapV2Direct` → `_seedRebalancing` (`Bonding.sol:1279-1354`) reads the pre-seeded pair's live `getReserves()` (uint112-capped, so up to ~5.19e33 each side) and compares them against `tokensForLP`/`ltFromPair` cached from phase 1. If the reserves are large enough relative to `tokensForLP`/`ltFromPair` to skip the small-dust direct-mint fallback (`Bonding.sol:1297-1302`), it calls `_pairRebalance` (`Bonding.sol:1414-1429`), which calls:

```solidity
function _noFeeSwapInput(
    uint256 reserveIn, uint256 reserveOut, uint256 targetN, uint256 targetD, uint256 maxSwap
) internal pure returns (uint256) {
    ...
    uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
    uint256 newIn = Math.sqrt(product);
    ...
}
``` [1](#0-0) 

The contract's own natspec admits this is unsafe outside the "sane" range: *"Constructed adversarial inputs that violate this would `revert` rather than silently truncate, which is the correct failure mode."* [2](#0-1)  — i.e., the developers acknowledge the revert path exists but treat it as acceptable, without recognizing that it directly contradicts the brick-resistance invariant that no pre-seed shape may cause `finalizeGraduation` to revert.

`targetN`/`targetD` are `ltFromPair`/`tokensForLP` (or the inverse), which are cached at phase 1 from the curve's own raised-LT and reserved-token amounts (`Bonding.sol:1054-1090`, `_prepareGraduationLiquidity`). Both `ltFromPair` and `tokensForLP` can be made very small by a creator who engineers a cheap graduation (e.g., a low-liquidity supply-trigger graduation with a depressed LT exchange rate, exactly the pattern the test suite itself uses in `test_inv_overflowCap_refundsLt` to drain the curve for a tiny LT cost — `packages/contracts/test/GraduationInvariants.t.sol:330-351`). With `ltFromPair`/`tokensForLP` pinned small (down to single-digit wei) and `reserveIn`/`reserveOut` pumped to tens of millions of 18-decimal token/LT units (well within the curve's own 750M-token supply and within an attacker's economically reachable LT mint via BounceTech), the discriminant `reserveIn * reserveOut * targetN / targetD` exceeds `type(uint256).max`, and OZ `Math.mulDiv` reverts.

Because `_pairRebalance` has no try/catch around `_noFeeSwapInput`, and `_seedRebalancing`/`_seedUniswapV2Direct`/`finalizeGraduation` have no try/catch around `_pairRebalance`, the revert unwinds the entire `finalizeGraduation` transaction. There is no fallback path once the reserves are large enough to bypass the dust-direct-mint short-circuit (`Bonding.sol:1297-1302`) — the token is permanently stuck: `finalizeGraduation` can never succeed for this token, `LPLock.recordLock` (a documented one-shot call, per the report's own scope rules) is never reached, and the curve-raised LT plus the 250M reserved tokens (`LP_RESERVE`) parked in `Bonding` since phase 1 are permanently frozen with no rescue path (the report explicitly notes `LPLock` "has no withdraw/rescue path in v1").

### Impact Explanation
Once `_enterGraduating` fires (permissionlessly reachable via any threshold-crossing `Zap.buy`/`Bonding.buy`, or via the permissionless `Bonding.triggerGraduation`), the affected token's `Lifecycle` is frozen at `Graduating` forever: `Bonding.buy`/`sell` revert with `TokenIsGraduating`, so no holder can trade the curve, and the HyperSwap V2 pool is never seeded, so no holder can trade post-grad either. This permanently freezes: (a) all real LT raised by the curve (`ltFromPair`), (b) the 250M reserved tokens held by `Bonding` for LP seeding, and (c) every existing holder's launched-token position, with zero recovery path — a concrete, permanent freezing of trader, creator, and LP funds for that token, satisfying the High-severity bar analogous to the CVE's "interpreter crash / total DoS" characterization.

### Likelihood Explanation
The precondition — permissionlessly front-running the HyperSwap V2 pair between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`) — is the exact documented attack surface the codebase already defends against (Regime 3). The only novel step is choosing pre-seed reserve magnitudes (tens of millions of 18-decimal units on each side, well inside the curve's own 1B-token virtual supply and a plausible LT mint budget) combined with steering the target token's own `ltFromPair`/`tokensForLP` to be small via a depressed-exchange-rate supply-trigger graduation the attacker/creator fully controls. All of this is achievable by a single unprivileged EOA acting as the token's own creator (who controls the launch and can engineer a minimal-value graduation) plus a pre-seed transaction on the permissionless HyperSwap factory/pair — no privileged role, oracle manipulation, or off-chain component required.

### Recommendation
Bound `_noFeeSwapInput`'s inputs (or wrap the `Math.mulDiv` call in `_pairRebalance`) so an overflow degrades to a safe fallback (`return false` from `_pairRebalance`, triggering the existing direct-mint fallback) instead of reverting the entire `finalizeGraduation` call. Alternatively, clamp `reserveIn`/`reserveOut` against a sane multiple of `tokensForLP`/`ltFromPair` before entering the rebalance branch, routing any reserve magnitude that would risk overflow straight to `_seedDirectMint`, preserving the documented "must never revert" brick-resistance invariant.

### Proof of Concept
1. Attacker launches a token as creator via `Zap.createToken`, seeding minimally.
2. Attacker drives the token to a supply-trigger graduation while the LT exchange rate is depressed (same technique as `test_inv_overflowCap_refundsLt`), so `ltFromPair` (and/or `tokensForLP`) at phase-1 cache time is pinned to a very small value.
3. Between phase 1 (`_enterGraduating`, fired inline by the threshold-crossing buy) and phase 2, attacker calls `HyperswapFactory.createPair(token, lt)`, transfers large (tens-of-millions-of-unit) amounts of the launched token and LT to the pair at a skewed ratio, and calls `pair.mint(attacker)` — mirroring the existing `_grieferMintPreSeed` test helper (`packages/contracts/test/TwoPhaseGraduation.t.sol:501-516`) but with reserve magnitudes chosen so `reserveIn * reserveOut * targetN / targetD > type(uint256).max`.
4. Anyone calls `Bonding.finalizeGraduation(token)`. Execution reaches `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, where `Math.mulDiv` reverts with `MathOverflowedMulDiv`, unwinding the whole transaction.
5. Every subsequent call to `finalizeGraduation(token)` reverts identically (the pre-seed reserves persist), permanently bricking graduation; the token's holders, its creator's/protocol's already-raised LT, and the 250M reserved tokens sitting in `Bonding` are frozen indefinitely.

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```
