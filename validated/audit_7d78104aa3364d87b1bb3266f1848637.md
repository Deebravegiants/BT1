### Title
Panic (underflow / length-mismatch) decoding `message.from` in `pallet-hyper-fungible-token::on_accept` when executing unsigned cross-chain calldata - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
The `on_accept` handler for incoming ISMP token-transfer messages decodes an ABI `Message` whose `from`/`to`/`data` fields are attacker-influenced bytes originating from whatever contract is registered as the source-chain peer for a given asset (`ContractToAsset`). Both `to` (recipient) and `from`-on-timeout paths are defensively length-checked and return typed errors, but the `from` fallback path used to derive the dispatch `origin` for optional calldata execution is not:

```rust
// modules/pallets/hyper-fungible-token/src/module.rs:176-186
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
``` [1](#0-0) 

### Finding Description
`message.from` is decoded via `Message::abi_decode(&body)` with no length constraint on the `bytes from` field [2](#0-1) . This is the same bug class as the reported PHP Firebird driver issue: a remote counterparty returns "invalid response data that is not parsed correctly," causing a crash. Here, the counterparty is the registered EVM peer contract for the asset (`ContractToAsset::<T>::get(source, &from)`), and the "parsing" is the unchecked slice/copy of `message.from`:

- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows a `usize` subtraction. In a runtime built with overflow checks (the Substrate default for non-release-unchecked builds), this panics; in a wrapping build, it produces an enormous out-of-range index into a follow-up slice, which also panics with an index-out-of-bounds.
- If `source` is not EVM and `from_bytes.len() != 32`, `account.copy_from_slice(from_bytes)` panics directly on a length mismatch (`copy_from_slice` requires equal lengths).

This is only reached when `message.data` is non-empty and has no `signature` set (`substrate_data.signature == None`), i.e. the unsigned-calldata origin-derivation branch [3](#0-2) , start="176" end="187" />.

By contrast, the codebase's own pattern elsewhere in the very same file explicitly guards this exact class of bug: the `to`-decoding above it [4](#0-3)  and the timeout-path `from`-decoding [5](#0-4)  both check `len() == 32`/`len() == 20` and return `HftError::InvalidRecipientLength`/`HftError::InvalidSenderLength` on mismatch, rather than indexing/copying directly. The `from`-in-`on_accept` branch is the one place this defensive pattern was omitted.

### Impact Explanation
A panic inside `on_accept`, which is invoked from `pallet-ismp`'s `handle_incoming_message`/`execute` path [6](#0-5) , aborts the runtime's message-processing extrinsic. Depending on how panics propagate through FRAME's dispatch (typically converted to a failed extrinsic rather than a node crash, but with `overflow-checks` this can also trip debug-assertions/panic handlers in some execution contexts, e.g. off-chain workers or state-transition validation nodes), this can deny service for that specific message and, more importantly, is a from-first-principles memory-safety violation (`copy_from_slice`/slice-index panic) triggered entirely by attacker-supplied cross-chain payload content — the same defect class as the CVE (malformed data from a message-producing counterparty crashing parsing code that should have validated length first). Because it sits in the token-bridge mint/calldata-execution path, a malformed message could disrupt processing of legitimate cross-chain token deliveries routed through this pallet.

### Likelihood Explanation
Reaching this code requires: (1) a message accepted from a `ContractToAsset`-registered peer contract for a supported asset, and (2) `message.data` present with `substrate_data.signature == None`. The `from` field's length is controlled by whatever code path produced the original ABI-encoded body on the source chain — since `bytes from` has no on-chain length enforcement in the `Message` ABI schema itself [7](#0-6) , any sender able to get the registered peer contract to emit/forward an ISMP POST with a non-canonical `from` (e.g., through a compromised/buggy peer implementation, or a peer contract that doesn't rigidly emit `abi.encodePacked(msg.sender)`) can trigger the panic. This is a defense-in-depth gap rather than something exploitable purely by an unprivileged relayer forging content (the relayer cannot forge the message body without breaking the state proof), which somewhat limits likelihood, but the missing length check is a genuine parsing-safety regression relative to the pattern used everywhere else in the same file.

### Recommendation
Validate `from_bytes.len()` before use in the `on_accept` unsigned-calldata origin branch, mirroring the existing `to`/timeout-`from` handling: return a typed `HftError` (e.g. reuse/extend `InvalidSenderLength`) when `from_bytes.len() != 20` (EVM) or `!= 32` (non-EVM) instead of indexing/copying directly.

### Proof of Concept
1. Register a source EVM chain/contract via `ContractToAsset` for some asset.
2. Have that registered contract (or any process capable of producing the ISMP POST body relayed to this pallet) emit a `Message` whose `from` field is ABI-encoded as fewer than 20 bytes (e.g., `bytes from = hex"0011"`), with a non-empty `data` field whose decoded `SubstrateCalldata.signature` is `None`.
3. Relay the resulting request through `handle_incoming_message` to `pallet-hyper-fungible-token::on_accept`.
4. Execution reaches `from_bytes.len() - 20` with `from_bytes.len() == 2`, causing a `usize` subtraction overflow panic (or, in a wrapping build, a subsequent out-of-bounds slice panic), aborting message processing instead of returning a typed error as the codebase does for every structurally similar field elsewhere in this file.
