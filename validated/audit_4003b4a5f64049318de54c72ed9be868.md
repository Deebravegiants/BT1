### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC signature validated by `ShopifyAPI::Webhooks::Registry.process` only proves the integrity of the JSON payload. The `shop` (and `topic`/`webhook_id`/`api_version`) values used by the app to decide which tenant's data to act on are taken from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) that are never included in the HMAC-signed bytes. Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is identical for every shop that installs the app, any merchant who installs the app on their own store can capture a legitimately-signed webhook body+HMAC pair from their own shop and replay it against the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop. The HMAC check still passes (body untouched), yet the handler receives `WebhookMetadata` attributing attacker-controlled body content to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` purely from headers: [1](#0-0) 
but the signable string used for HMAC verification is only the raw body: [2](#0-1) 

`Registry.process` validates the HMAC and then hands the header-derived `shop` (and `topic`, `webhook_id`, `api_version`) straight to the app's handler without any binding to the signed payload: [3](#0-2) 

`HmacValidator.validate` computes the signature only from `to_signable_string` (i.e. the body) against the shared `Context.api_secret_key`: [4](#0-3) 

This breaks the intended identity binding: **`shop` reported to the handler == `shop` whose data the signed body actually pertains to**. The `client_secret`-derived HMAC only ties the *body* to "some shop that has this app installed," not to the specific `shop-domain` header value. Since the secret is shared across every shop installation of the app, an attacker who is merely an ordinary merchant (installs the app on their own dev/free store — an unprivileged, no-special-access action) can:
1. Trigger any webhook on their own shop, capturing `raw_body` and the corresponding `x-shopify-hmac-sha256`.
2. Replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain.
3. `HmacValidator.validate` succeeds because the body is unmodified and was legitimately signed by the shared secret.
4. `WebhookHandler#handle` is invoked with `data.shop == victim-shop.myshopify.com` even though the payload content originates from the attacker's own shop.

This is analogous to the reported RootBank issue: a value used to determine *which account/tenant* an operation applies to (`token_root_bank`/`shop`) is not cross-checked against the value that was actually authenticated/verified (the notional calculation/HMAC), letting an attacker mix mismatched, individually-valid pieces of state to corrupt cross-tenant accounting.

### Impact Explanation
Any app built on this gem that keys per-shop side effects (writes, credits/charges, state transitions, cache invalidation, uninstall handling, etc.) off `WebhookMetadata#shop` can be tricked into applying attacker-controlled webhook content to a different, victim tenant. This is a cross-tenant confusion vulnerability — the exact class of impact ("cross-tenant access") called out as Critical in the assessment rubric — reachable purely through the library's own webhook verification API (`ShopifyAPI::Webhooks::Registry.process` / `ShopifyAPI::Webhooks::Request`), with no code changes required on the host app's side beyond simply trusting the documented `data.shop` field as this gem instructs apps to do.

### Likelihood Explanation
Requires only: (1) becoming an ordinary merchant who installs the target app on any shop (no privileged access, no leaked secrets, no social engineering), and (2) the ability to send arbitrary HTTP requests with attacker-chosen headers to the app's publicly reachable webhook endpoint — both trivially available to any unprivileged internet user. The `client_secret` is intentionally shared across all shop installations of an app, so a signature obtained from one's own store is valid for spoofing another shop's identity in this scheme.

### Recommendation
Bind the shop (and other trust-relevant metadata) into the value that is actually verified. Options:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content used for verification (matching how `AuthQuery#to_signable_string` binds `shop` into the OAuth callback signature), or
- Cross-check the header-derived `shop` against an independently-verified source (e.g. a stored, per-shop offline access token/session lookup) before invoking the handler, rejecting requests where the claimed shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own store, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify.
3. Attacker POSTs the identical body to the app's webhook endpoint, keeping the same `x-shopify-hmac-sha256` and `x-shopify-topic` headers, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` with the shared `Context.api_secret_key`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: <attacker's own order data>, ...)`, causing the app to process attacker-controlled data as if it belonged to the victim shop.
