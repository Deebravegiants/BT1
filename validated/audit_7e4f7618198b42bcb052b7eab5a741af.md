### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-verified payload. `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC over the raw body and then dispatches the handler using the unauthenticated `shop` header value, breaking the equality "shop authenticated by HMAC == shop acted upon by the handler."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  This is what `HmacValidator.validate` HMAC-verifies against `Context.api_secret_key`: [2](#0-1) 

Meanwhile `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and, if it passes, immediately hands the (unauthenticated) `request.shop` to the registered handler as the tenant identity: [4](#0-3) 

Because `Context.api_secret_key` is a single app-wide secret shared by every shop that installs the app (not a per-shop secret), any unprivileged attacker who installs the app on their own shop receives genuinely HMAC-signed webhook deliveries for their own shop. The attacker can take that valid `(body, hmac)` pair — the HMAC only commits to the body — and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain (and optionally a different `topic`/`webhook-id`, which are also outside the signed material). `HmacValidator.validate` will still succeed because the body and signature are untouched, and the handler will be invoked believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant confusion: a message that is only proven to originate from "some shop that has this app installed with this shared secret" is treated by the host application as authoritatively originating from an arbitrary `shop` chosen by the attacker. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., looking up/mutating per-shop data, triggering GDPR redaction flows, updating billing/subscription state, or invalidating sessions), this lets an attacker forge events attributed to a victim tenant — a cross-tenant access primitive built directly on this gem's webhook-verification API.

### Likelihood Explanation
Any actor able to install the app on any shop (including trial/dev stores, which is normally open to the public for public apps) automatically obtains valid signed webhook bodies for arbitrary topics they can subscribe to, and only needs to replay them with a modified header/topic to target a different shop. No access token, `client_secret`, or privileged access is required — only the gem's own documented webhook validation surface (`HmacValidator`/`Webhooks::Request`/`Webhooks::Registry`) is used as designed.

### Recommendation
Include the identity-bearing fields (`shop`, `topic`, and ideally `webhook_id`) inside the signed/verified material, or otherwise cryptographically bind them to the HMAC (e.g., verify against a per-shop secret, or require the caller to additionally confirm the header-derived shop against session/install records before trusting it), rather than trusting `Request#shop` sourced purely from an unauthenticated header once only the raw body's HMAC has been checked.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, subscribing to a webhook topic the handler acts on (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with a body `B` and `X-Shopify-Hmac-Sha256` computed as `HMAC-SHA256(api_secret_key, B)`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, hmac)` and resends it to the app's webhook endpoint, replacing only the header `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches, so `Registry.process` proceeds and invokes the handler with `shop: "victim.myshopify.com"` [5](#0-4)  even though the event never originated from that shop.
