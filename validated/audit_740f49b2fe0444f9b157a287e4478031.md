### Title
`createWithdrawalIntents()` computes withdrawal amount without a fee-exceeds-amount check, allowing underflow into a negative withdrawal amount - (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents()` subtracts the caller-supplied `feeEstimation.amount` from `withdrawalParams.amount` when `feeInclusive` is true, without first verifying `amount > feeEstimation.amount`. The equivalent internal helper `_estimateWithdrawalFee()` performs this exact check before subtracting, but the public `createWithdrawalIntents()` entry point does not, breaking the invariant that "amount debited = amount minus fee, and fee must not exceed amount."

### Finding Description
In `_estimateWithdrawalFee()`, before computing `actualAmount`, the SDK explicitly guards against the fee exceeding the amount: [1](#0-0) 

But `createWithdrawalIntents()`, a separate public method that accepts an arbitrary `feeEstimation` object supplied by the caller, performs the identical subtraction with no such guard: [2](#0-1) 

Because `actualAmount` is a `bigint`, `amount - feeEstimation.amount` does not throw when the fee is greater than or equal to the amount — it silently produces zero or a negative value. This negative/zero `actualAmount` is then passed straight into `bridge.validateWithdrawal()` and `bridge.createWithdrawalIntents()`, which build the `ft_withdraw` intent's `amount` field via `.toString()` (e.g. `omni-bridge-utils.ts`'s `createWithdrawIntentsPrimitive`), producing a malformed/negative amount string in the signed intent payload.

`createWithdrawalIntents()` is a public SDK API — nothing enforces that its `feeEstimation` argument must come from a freshly-validated `estimateWithdrawalFee()` call. A caller (integrator or a component reusing a stale/cached `feeEstimation`, e.g. after fees rose or after combining data from a different call) can pass an `amount`/`feeEstimation` pair where `feeEstimation.amount >= amount`, and the SDK will proceed to build intents with a corrupted amount instead of rejecting the request with `FeeExceedsAmountError` as the sibling method does.

### Impact Explanation
This breaks the equality "amount debited = amount minus fee, fee must not exceed amount" that the SDK otherwise enforces in `_estimateWithdrawalFee()`. Depending on downstream bridge behavior, this can result in: a withdrawal intent built with a negative/garbage amount, an intent that fails on-chain in an unexpected way, or (for bridges that don't strictly validate the numeric string) a withdrawal request with an incorrect amount reaching signature/execution — a fee-error class issue that drains value or produces stuck/incorrect withdrawals. This qualifies at least as a fee/amount-integrity defect on a primary SDK entry point that produces signed intents.

### Likelihood Explanation
Likelihood is moderate: `createWithdrawalIntents()` is a documented public method separate from `estimateWithdrawalFee`, explicitly designed to accept a `feeEstimation` computed earlier (potentially by a different call, environment, or even a stale cache) — this asymmetric validation exists precisely because two independent call sites duplicate the `actualAmount` computation logic, and only one of them re-checks the invariant. Any integrator following the two-step estimate → build pattern with any time gap, retries, or reused fee estimation risks hitting this path.

### Recommendation
Add the same `FeeExceedsAmountError` guard (`args.withdrawalParams.amount <= args.feeEstimation.amount` when `feeInclusive` is true) inside `createWithdrawalIntents()` in `packages/intents-sdk/src/sdk.ts`, mirroring the check already present in `_estimateWithdrawalFee()`, before computing `actualAmount`.

### Proof of Concept
```ts
const sdk = new IntentsSDK({ referral: "", intentSigner });

// Attacker/integrator supplies a feeEstimation whose amount >= withdrawal amount
// (e.g., a stale estimation reused after fees increased)
const feeEstimation = {
  amount: 1000n, // >= amount below
  quote: null,
  underlyingFees: { /* ... */ },
};

const intents = await sdk.createWithdrawalIntents({
  withdrawalParams: {
    assetId: "nep141:eth.bridge.near",
    amount: 500n,          // less than fee.amount
    destinationAddress: "0x...",
    feeInclusive: true,
  },
  feeEstimation,
});
// actualAmount = 500n - 1000n = -500n
// No FeeExceedsAmountError thrown (unlike estimateWithdrawalFee),
// -500n flows into bridge.validateWithdrawal / createWithdrawalIntents
// and ends up as amount: "-500" in the signed ft_withdraw intent.
```
