### Title
Webhook `shop`/`topic`/`webhook_id` identity fields are trusted from unauthenticated headers while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry uses to route and label the webhook are read straight from HTTP headers that are never covered by the HMAC.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all parsed from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`), independently of the body: [2](#0-1) 

`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery`/`HmacValidator` — only checks that `hmac == HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)`. It then dispatches the handler purely based on `request.topic`, and forwards `request.shop`, `request.topic`, `request.webhook_id` unauthenticated into `WebhookMetadata`, which is what the app-supplied `WebhookHandler#handle` acts on: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `bytes verified by HMAC == bytes the app trusts to identify the tenant/topic`. Here it does not: `HMAC-covered content = raw_body` but `trusted routing/tenant identity = headers(shop, topic, webhook_id)`. This is exactly the "bytes verified vs. bytes/headers parsed and trusted" analog: the signature proves the body came from someone holding the app's `client_secret`, but it proves nothing about which shop or which topic that body is attributed to.

Because every shop that installs the same app shares the same `client_secret` for webhook HMAC computation, any party who can obtain one valid `(raw_body, hmac)` pair — trivially, by installing the app on their own store/dev shop and receiving one real webhook — can replay that exact body to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers to any value. The HMAC will still validate (it only checks the body), and `Registry.process` will pass through the forged `shop`/`topic` to the app's handler as if it were authentic.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled webhook body (HMAC-valid because it came from the attacker's own shop installation) can be attributed to an arbitrary victim `shop` domain and/or an arbitrary `topic`, since neither is bound by the signature. Depending on how the consuming app's `WebhookHandler` trusts `data.shop`/`data.topic` (e.g., to look up tenant records, update order/customer state, or trigger side effects keyed by shop), this enables cross-tenant data injection/confusion under the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimately-signed `(body, hmac)` pair for the target app, which is straightforward since anyone can install a public app on their own store and receive a real webhook with a valid HMAC. Forging the routing headers on replay is trivial (webhook endpoints are plain public HTTP(S) endpoints; nothing but the HMAC gates the request). No access token, `client_secret`, or privileged account is required — only that the app is publicly installable, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the identity fields into the signable content, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body — e.g., include them in `to_signable_string`, or require the consuming application to independently re-derive/verify the shop identity (e.g., cross-check against a known list of installed shops) before trusting `WebhookMetadata#shop`/`#topic` for any tenant-sensitive action. At minimum, document explicitly that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be trusted for tenant-identification without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker-shop.myshopify.com`) and triggers any webhook (e.g. `orders/create`), capturing the raw request body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` computed by Shopify with the app's shared `client_secret`.
2. Attacker sends a new HTTP POST to the app's public webhook endpoint with:
   - Body: the identical bytes `B`
   - Headers: `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, `X-Shopify-Webhook-Id: <any>`
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Utils::HmacValidator.validate(request)` succeeds because it only recomputes `HMAC(secret, B)` and compares to `H`, per: [5](#0-4) 
4. `Registry.process` dispatches to the `orders/create` handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the body content actually originated from the attacker's own shop — demonstrating that shop/topic attribution is not bound by the HMAC.
