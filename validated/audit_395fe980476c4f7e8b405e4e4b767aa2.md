Confirmed: the webhook HMAC (`request.hmac`) is computed only over `to_signable_string`, which returns `@raw_body`, and none of the identity headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are part of that signable string.This confirms the finding: the docs explicitly state `data.shop` (the shop domain) is trusted output of webhook processing, handed directly to app logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), while the HMAC only authenticates `@raw_body`.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking that `Utils::HmacValidator.validate(request)` succeeds. That validator computes the HMAC over `request.to_signable_string`, which for `Webhooks::Request` returns only `@raw_body`. The `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header), `topic`, and `webhook_id` are read from unauthenticated HTTP headers and are never included in the signed bytes, yet they are trusted and forwarded verbatim to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are parsed straight from request headers, independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` only re-computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header, so it never binds the shop/topic/webhook-id headers to the signature: [3](#0-2) 

`Registry.process` accepts the request once this single check passes, and forwards the **unauthenticated** `request.shop`, `request.topic`, and `request.webhook_id` straight to the app-defined handler: [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop the HMAC-signed body actually belongs to`. Because the HMAC is keyed to the app's single shared `client_secret` and only covers `@raw_body`, that binding never gets enforced. Any party who can obtain one legitimate `(body, hmac)` pair for the app — trivially available to any merchant who installs the app and receives a real webhook to their own endpoint, since the secret is shared across every shop using the app — can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (and/or `topic`/`webhook_id`). `HmacValidator.validate` will still pass because it only checks the body against the shared secret, and `Registry.process` will invoke the handler with `shop: <attacker-chosen-domain>`.

The gem's own documentation shows the intended trust model — the handler uses `data.shop` as the tenant key for further processing (e.g. `shop_domain: data.shop`): [5](#0-4) 

### Impact Explanation
This breaks the shop/tenant boundary that host apps rely on when using this gem's webhook verification as their sole authentication mechanism. An attacker with legitimate access to any one shop that has the app installed can forge webhook events attributed to a different, victim shop domain — causing the host application to process attacker-controlled data (e.g., `orders/create`, `app/uninstalled`, `shop/redact`) under another tenant's identity. Depending on how the host app persists/acts on `data.shop`, this results in cross-tenant data corruption, spurious mandatory-compliance actions (e.g. faked `shop/redact`), or state confusion for a shop the attacker does not control — satisfying the "cross-tenant access" impact category, since the gem's exposed `Registry.process`/`HmacValidator.validate` API is exactly what a host app is expected to trust for this identity binding.

### Likelihood Explanation
Likelihood is moderate-to-high: no access token, `api_secret_key`, or privileged credentials are needed. The attacker only needs to install the app on any shop (including a free/dev shop) to receive one genuine webhook delivery, capture its raw body and `hmac-sha256` header, then resend that same pair to the app's public webhook endpoint with a modified `shop-domain` header. This is a pure network-level replay against a publicly reachable HTTP endpoint, with no rate limiting or nonce/timestamp binding in the current signature scheme.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api-version`) in the signed material used for verification, or otherwise cryptographically bind them to the body (e.g., verify HMAC over a canonical string containing the raw body concatenated with these header values) inside `Webhooks::Request#to_signable_string` / `HmacValidator`. At minimum, document that `request.shop`/`request.topic` must not be trusted as the exclusive tenant key unless additionally cross-checked against the shop record that the webhook subscription was registered for.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; the app registers a webhook (e.g. `orders/create`) via `Registry.register_all`.
2. Trigger a real order-create event on `attacker-shop.myshopify.com`; Shopify delivers a webhook to the app's endpoint with headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and body `B`.
3. Capture `(B, H)`.
4. Send a new HTTP request to the same webhook endpoint with body `B` unchanged, `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
6. The registered handler's `handle(data:)` is invoked with `data.shop == "victim-shop.myshopify.com"` and attacker-controlled `data.body`, even though `victim-shop` never sent this webhook.

          received_signature = verifiable_query.hmac
