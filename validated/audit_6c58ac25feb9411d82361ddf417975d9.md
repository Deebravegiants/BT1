### Title
Webhook `shop-domain` header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop-domain` header, which the handler uses to identify which tenant/shop a webhook event belongs to, is never included in the signed payload. Since the app's `client_secret` (and therefore the HMAC) is the same across every shop that installs the app, any unprivileged merchant who has legitimately installed the app can capture one of their own valid `(raw_body, hmac)` pairs and replay it with a different `shop-domain` header, making the webhook appear to originate from a different (victim) shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`, which for webhooks is defined as the raw body: [1](#0-0) 

The `shop` accessor is read straight from an unauthenticated header and is never part of what gets signed: [2](#0-1) 

`Registry.process` only checks the HMAC and then dispatches directly using `request.shop` as the tenant identity for the handler: [3](#0-2) 

The intended identity binding is: `shop-domain header == shop that produced/owns this HMAC-signed body`. Because the HMAC covers only the body bytes and is computed with the single, shop-independent `api_secret_key`/`old_api_secret_key`: [4](#0-3) 

the equality that should hold (`hmac == HMAC(body, shop_specific_context)`) actually collapses to `hmac == HMAC(body, app_secret)` with no shop binding at all. An unprivileged actor who legitimately installs the app on their own store receives real, validly-signed webhook deliveries for that store (e.g. `orders/create` with an empty or attacker-influenced body such as `{}`). They can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop domain. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker with no more privilege than "install the app on my own store" can make the gem report webhook data as coming from a shop they do not control/own. Any host application that trusts `WebhookMetadata#shop` (the gem's documented, intended way to route/attribute webhook payloads per merchant) can be tricked into writing, deleting, or acting on data keyed to the wrong tenant — a cross-tenant access primitive that meets the "Critical: cross-tenant access" bar defined in scope.

### Likelihood Explanation
Likelihood is realistic: installing a Shopify app (even a free/public one) requires no elevated privilege, and every installer automatically receives real HMAC-signed webhook deliveries for their own shop, including trivially predictable bodies for topics like `app/uninstalled` or `shop/redact` (bodies are just `{"shop_id":...,"shop_domain":...}` or similar, and for some topics an empty body class of `{}` is possible). Capturing one's own legitimate `(body, hmac)` pair and replaying it with a different header value requires only basic HTTP tooling — no cryptographic secret is ever needed.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is authenticated, not just the raw body:
- Extend `Webhooks::Request#to_signable_string` (or add a parallel check in `Registry.process`) to incorporate the `shop-domain` header (and topic) into the signable data, or
- After validating the body HMAC, additionally verify that the shop header matches an expected/allow-listed shop context for the delivery (e.g., cross-check against the shop associated with the webhook subscription/session the app registered), rejecting mismatches.
At minimum, document prominently that `WebhookMetadata#shop` is *not* cryptographically bound by the current HMAC check and must be independently verified by consuming applications against a known/installed-shop list before being trusted for tenant routing.

### Proof of Concept
```ruby
# Step 1: Attacker installs the target app on their own shop "attacker-shop.myshopify.com"
# and receives a legitimate webhook delivery, e.g. for topic "app/uninstalled":
#   body:  '{"shop_id":123,"shop_domain":"attacker-shop.myshopify.com"}'  (captured raw bytes)
#   header x-shopify-hmac-sha256: "<valid signature for that exact body, signed with the app's real client_secret>"
#   header x-shopify-shop-domain: "attacker-shop.myshopify.com"

# Step 2: Attacker replays the identical body + hmac to the app's public webhook endpoint,
# only changing the shop-domain header to a victim shop they do not control:

require "net/http"
uri = URI("https://victim-app.example.com/webhooks")
req = Net::HTTP::Post.new(uri)
req["x-shopify-topic"] = "app/uninstalled"
req["x-shopify-hmac-sha256"] = captured_valid_hmac        # unchanged, still valid for the body
req["x-shopify-shop-domain"] = "victim-shop.myshopify.com" # forged, not covered by HMAC
req["x-shopify-webhook-id"] = "any-id"
req["x-shopify-api-version"] = "2024-01"
req.body = captured_raw_body                               # unchanged

# Server-side (using this gem):
#   Utils::HmacValidator.validate(request) => true  (only checks body bytes vs. app secret)
#   Registry.process(request) dispatches handler.handle(
#     data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)
#   )
# The host app now believes "victim-shop.myshopify.com" uninstalled the app / sent this event,
# even though the attacker never had access to victim-shop's data or the app's client_secret.
```
