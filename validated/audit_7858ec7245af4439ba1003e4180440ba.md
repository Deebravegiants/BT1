### Title
Unbounded BEEFY signature list forces excessive ECDSA recovery work per submitted proof, disproportionate to the extrinsic's fixed weight - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The Suricata CVE (CVE-2024-23836) is a class of "algorithmic complexity" DoS: crafted, cheaply-produced input forces the parser/verifier to perform far more CPU work than the size/cost of the input would suggest. The closest reachable analog in this codebase is `verify_mmr_update_proof` in `modules/consensus/beefy/verifier/src/lib.rs`, which is reached from a signed extrinsic (`pallet-beefy-consensus-proofs::submit_proof`, PROOF_TYPE_NAIVE) via `handlers::handle_incoming_message` → `BeefyConsensusClient::verify_consensus`.

### Finding Description
`verify_mmr_update_proof` iterates over **every** entry in `mmr.signed_commitment.signatures` and performs a full secp256k1 ECDSA public-key recovery (`H::secp256k1_recover`) plus two Keccak hashes for each one: [1](#0-0) 

The only gate that runs *before* this loop is `check_participation_threshold`, which enforces a **minimum** number of signatures (`len >= (2*total)/3 + 1`) to satisfy supermajority — it does not enforce a **maximum**: [2](#0-1) [3](#0-2) 

Because `secp256k1_recover` on well-formed-but-arbitrary 65-byte signature bytes almost always succeeds (it recovers *some* point on the curve rather than erroring), an attacker cannot be short-circuited by the early `?` on `FailedToRecoverPublicKey` — they can pad the signature vector with any number of syntactically valid 65-byte blobs up to whatever the pallet's outer size bound allows, and every one of them will be recovered and hashed before the merkle-membership check (`merkle_proof.verify`) ever runs and rejects the proof for containing unknown/duplicate authority indices.

This is analogous to Suricata's flaw: the "shape" of the input (number of alleged signatures) is checked only for a lower bound, so a submitter pays for one bounded-size extrinsic (or one bounded proof blob) while the runtime performs `O(n)` expensive elliptic-curve recovery operations for attacker-chosen `n`, with `n` unbounded relative to the actual authority set size. The equivalent Solidity path (`EcdsaBeefy.sol::verifyMmrUpdateProof`) has the same structural issue, but there the cost is paid entirely in gas by the caller, which naturally caps the practical damage; the Substrate/`pallet-beefy-consensus-proofs` path is executed under FRAME's fixed-weight accounting, where computational cost does not automatically scale with the attacker-chosen array length unless the extrinsic's declared `#[pallet::weight]` benchmarks and bounds this specific length.

### Impact Explanation
If the weight declared for `submit_proof` (or the analogous unsigned/consensus-message path) does not scale with, or properly cap, the number of signatures in the submitted BEEFY commitment, a single crafted proof can force block-authoring/import nodes to perform a disproportionate number of ECDSA recoveries relative to the fee/weight charged. Under adversarial network conditions this can slow down or stall block production/import — a network-wide denial of service for a core consensus-update path that every downstream state commitment and message relay depends on.

### Likelihood Explanation
Reachability is direct: `submit_proof` is a signed extrinsic reachable by any account, and the naive (ECDSA) proof type routes straight into the unbounded loop described above. The severity in practice depends on two facts I was not able to fully confirm in this pass:
- the exact value of `MaxProofSize` (the `BoundedVec<u8, T::MaxProofSize>` bound on `submit_proof`'s payload), which caps how many 65-byte signature blobs can be packed into one proof, and
- whether `WeightInfo::submit_proof()` is parameterized on the decoded signature count or is a flat/benchmarked-average weight.

Both of these need to be checked in the repository (`modules/pallets/beefy-consensus-proofs/src/weights.rs`, the runtime configs in `parachain/runtimes/*/src/lib.rs`) to determine whether this is fully mitigated, partially mitigated, or exploitable as described. I could not verify these within the available searches.

### Recommendation
- Add an explicit upper bound on `mmr.signed_commitment.signatures.len()` in `verify_mmr_update_proof` (and the mirrored Solidity `verifyMmrUpdateProof`), e.g. reject any commitment whose signature count exceeds `authority_set.len` (it can never legitimately exceed the authority set size).
- Ensure the extrinsic's declared weight for `submit_proof` scales with the decoded proof's signature count (or is benchmarked against the worst-case bound above), so the fee charged reflects the actual verification cost.
- Consider deduplicating/validating `sig.index` bounds before performing the expensive recovery, so garbage entries with out-of-range indices are rejected before paying the ECDSA cost.

### Proof of Concept
Not executed against a live node (analysis only, based on code inspection). Conceptually:
1. Construct a `BeefyConsensusProof`/`ConsensusMessage` whose `signed_commitment.commitment` is otherwise well-formed (satisfies `checkParticipationThreshold`).
2. Append a large number of additional syntactically-valid but bogus 65-byte "signatures" (up to the `MaxProofSize`/`BoundedVec` limit) to `signed_commitment.signatures`.
3. Submit via `submit_proof` (PROOF_TYPE_NAIVE). `verify_mmr_update_proof` will call `secp256k1_recover` for every one of the padded signatures before the merkle membership check fails and rejects the proof, so verification cost scales with attacker-chosen padding rather than genuine authority count.
