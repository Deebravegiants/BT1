### Title
Webhook `shop` identity is trusted for dispatch but is not bound into the HMAC signature check - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` (a value carried alongside, not inside, the signed payload) to build the `WebhookMetadata` handed to the app's handler. The HMAC check only proves the request *body* was signed with the app's shared `client_secret`; it does not cryptographically bind that signature to the specific shop the request claims to be from.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac` using `OpenSSL.secure_compare` [1](#0-0) . This only proves that *some* payload bytes were signed by an entity possessing `Context.api_secret_key` (or `old_api_secret_key`) — the app's single shared `client_secret`, identical for every shop that has the app installed.

`Registry.process` then does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [2](#0-1) 

`request.shop` is used as the authoritative tenant identifier passed to the app's business logic, but nothing in `Registry.process` re-derives or checks that this shop value is the one that was actually signed — it is trusted as-is once *any* valid HMAC (for *any* shop under the same app) is present. This is exactly the bug-class pattern of "a field acted on but not covered by the HMAC": the identity-binding equality that should hold is

`signed_payload.shop == request.shop_used_for_dispatch`

but the code only ever checks `hmac(signed_payload) == received_hmac`, never checks that `signed_payload` is bound to `request.shop`.

Because the app secret is shared across every shop that installs the app, an unprivileged internet user who legitimately installs the app on their **own** shop can capture a genuine, validly-signed webhook body/HMAC pair that Shopify sent them, then replay that same body+HMAC pair to the app's webhook endpoint while presenting a different shop's domain as the shop header. `Registry.process` will pass Utils::HmacValidator.validate (since the signature is valid for the app secret and the body was untouched), and will dispatch the handler with `shop: <attacker-chosen victim shop>` while the actual event content originates from the attacker's own shop.

### Impact Explanation
If the app's webhook handler uses the `shop` field from `WebhookMetadata` to select which merchant record/session/access-token to act on (a normal and expected usage pattern for this gem's webhook API), this allows a completely unprivileged internet user to inject arbitrary attacker-controlled webhook event data (topic-appropriate JSON body) attributed to a victim shop they do not control. Depending on the topic registered by the host app, this can drive cross-tenant state changes (e.g., triggering data-deletion/redact flows, order/customer processing logic, or any merchant-specific side effects) for a shop the attacker has no relationship with — a cross-tenant confusion vulnerability rooted entirely in this gem's own dispatch code, not in host misuse.

### Likelihood Explanation
Any user can freely install a Shopify app that uses this gem on their own development/test store (Shopify allows free installs on development stores), letting them legitimately observe real signed webhook traffic for their own shop, since `client_secret` is shared across every installation of the app. Replaying that traffic against the same public webhook endpoint with a different `Shop-Domain` value requires no credentials, no access tokens and no social engineering — only network access to the app's public webhook URL, which is a mandatory internet-facing endpoint.

### Recommendation
Bind the `shop` identifier into the value verified by the HMAC (e.g., require the app to look up the shop against its own store of installed/authenticated shops before trusting `request.shop`, or otherwise cryptographically bind shop identity into the signed payload check) instead of trusting it purely because *some* valid HMAC for the shared app secret was presented, inside `Registry.process` at [3](#0-2) .

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers/observes a legitimate webhook of a topic the app has registered (e.g. via `Registry.add_registration`), capturing the raw request body and the `X-Shopify-Hmac-Sha256` header Shopify sent for their own shop.
3. Attacker POSTs the identical body and HMAC header to the app's public webhook endpoint, but sets the shop-identifying header to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in [4](#0-3)  succeeds because the body/HMAC pair is unmodified and still matches the shared `Context.api_secret_key`.
5. `Registry.process` in [3](#0-2)  dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app's business logic to act on the victim shop using attacker-controlled event content.

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
