### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw JSON body of a webhook, while the `shop` domain used to route/attribute the webhook to a tenant is read from an HTTP header that is never included in the HMAC computation.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from the request headers, independent of the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string` (i.e. the raw body), using the app's shared `Context.api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` trusts the HMAC result and then forwards the **unverified** `request.shop` value straight to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop domain bound by signature == shop domain acted upon`. Here, the signature only binds the body bytes to the secret; it says nothing about which shop the payload belongs to. Since every webhook for a given app (across all installed shops) is signed with the **same** `api_secret_key`, any merchant who has installed the app can obtain a validly-signed `(body, hmac)` pair from their own store's webhook traffic, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value naming a different, victim shop. `HmacValidator.validate` will report success (the body and secret match), and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` is the attacker-chosen value, not the shop that actually produced the payload.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC is supposed to provide: an app relying on `WebhookMetadata#shop` (as this gem's own documented usage pattern instructs, e.g. `shop_domain: data.shop`) to select which merchant's data/session to update can be tricked into applying attacker-controlled webhook data under a different shop's identity — a cross-tenant access/injection primitive achievable by any unprivileged, already-installed merchant, without ever knowing `api_secret_key`.

### Likelihood Explanation
Likelihood is high for any multi-tenant app that installs the gem for multiple shops: obtaining a validly-signed body/HMAC pair requires nothing more than being one of the app's own installed merchants (an unprivileged position relative to other tenants), and forging the shop header on an HTTP request to the app's public webhook endpoint requires no special access.

### Recommendation
Bind the shop identity into what is verified: either include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed payload comparison (e.g., verify a canonical string combining headers + body, mirroring how the OAuth `AuthQuery` binds all relevant fields), or independently cross-check `request.shop` against the shop associated with the webhook subscription/session before invoking the handler, rejecting mismatches.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both registered for topic `orders/create` with the same app (`api_secret_key`).
2. Shopify sends a legitimate webhook to the attacker's own shop: body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Attacker replays this exact `(B, HMAC)` pair directly to the app's public webhook route, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` computes `HMAC(secret, B)` again (unchanged, since `to_signable_string` ignores headers) — validation succeeds. [1](#0-0) 
5. `Registry.process` calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_from_B, ...)`, causing the host app to process attacker-controlled data under the victim shop's identity. [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
