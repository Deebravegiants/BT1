Confirmed: in `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb`, lines 33-43), the `shop` value is explicitly included inside the signed string, binding the shop identity to the HMAC. By contrast, `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb`, lines 35-38) returns only `@raw_body`, while `shop` is read out of an unsigned header (lines 20-23) and passed straight into the handler. This is exactly the same class of bug as the depositary report: a field that is *used* (`shop`) is not *covered* by the integrity check (`hmac`), so the two can be made to disagree by an attacker who controls one but not the other.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook shop-spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator.validate` is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The shop header is never part of the signed bytes, so the binding `authenticated_bytes == acted_upon_shop` does not hold.

### Finding Description
- `Webhooks::Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 
- `Webhooks::Request#shop` is pulled from an HTTP header that plays no role in the signature: [2](#0-1) 
- `Registry.process` validates only the HMAC over the body, then immediately trusts `request.shop` to build the data handed to the app's handler: [3](#0-2) 
- Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which deliberately folds `shop` into the signed string precisely to bind shop identity to the HMAC: [4](#0-3) 

Because the app's single `client_secret`/`api_secret_key` is shared across every merchant that installs the app, an attacker who installs the app on their own store legitimately receives correctly-HMAC-signed webhook deliveries (body + hmac) from Shopify. Since the signature never covers the shop header, the attacker can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary victim `x-shopify-shop-domain` value. `Utils::HmacValidator.validate` at [5](#0-4)  still succeeds because it only checks the body bytes, and `Registry.process` will dispatch the handler with `shop: <victim-domain>` sourced from the unverified header, using body content the attacker fully controls.

### Impact Explanation
This breaks the tenant boundary the app relies on: a webhook handler that looks up the victim's stored session/access token by `data.shop` and acts on attacker-supplied `data.body` content (e.g., marks orders fulfilled, updates inventory, triggers refunds, revokes access) will execute those actions against a shop the attacker does not control, using a payload the attacker fabricated. This is a cross-tenant access/spoofing vector enabled entirely by a missing identity-binding in the gem's own HMAC verification, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any unprivileged internet user can install the app for free on their own development/trial store, which is enough to obtain arbitrarily many genuinely-signed `(body, hmac)` pairs signed with the app's real secret. No leaked credentials, TLS interception, or privileged access are required — only a public webhook endpoint reachable over the internet (the gem's documented deployment model) and one benign install.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the signed material verified for webhooks, or independently re-derive/cross-check the shop from data that is itself covered by the HMAC (e.g., a `shop`/`shop_id` field embedded in the JSON body for topics where Shopify includes one), rejecting the request when the header-derived shop disagrees. At minimum, document that `request.shop` is unauthenticated and must not be trusted for authorization decisions without an independent check, or add a mode where the caller supplies the expected shop and `Registry.process` verifies header-shop equals expected-shop before dispatch.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate, unprivileged action).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, body: `{"id": 1, ...attacker-controlled fields...}`.
3. Attacker captures this exact `(raw_body, hmac)` pair (they own the shop, so this is trivial — e.g. via their own server logs).
4. Attacker crafts a new POST to the same public webhook endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) validates successfully because it only hashes `@raw_body`.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)` to the app's handler, which acts on the victim tenant using attacker-forged data.
