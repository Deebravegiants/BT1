### Title
Relay flat-fee token is not bound by the EmporiumStack signature, allowing fee payment in an arbitrary uncounted ERC20 from the wallet - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`payRelayFees`'s "not found" branch pulls `feeStructure.flatFee` of `feeStructure.feeToken` directly from the user's `HinkalWallet` via `payRelay` → `sendToRelayFromWallet` → `doSendToRelay`, whenever that token is absent from `circomData.erc20TokenAddresses`. The EIP-712 signature that authorizes the wallet's session (`verifyWallet`) only binds a numeric cap (`stack.maxFee`) and the ops hash — it never binds `feeStructure.feeToken`. Since `feeStructure` (including `feeToken`) is freely chosen by whoever submits the transaction, the token actually debited from the wallet can be a token the signer's operations never touched and that is never accounted for by the shielded-pool balance/UTXO bookkeeping.

### Finding Description
The invariant that should hold is: **every token leaving the wallet must be one that is present in `circomData.erc20TokenAddresses` and reflected in `deltaAmountChanges`/the pool's balance accounting.** The `!foundToken` branch breaks this: [1](#0-0) 

`foundToken` is only set to `true` when `feeStructure.feeToken` matches one of the entries in `circomData.erc20TokenAddresses` inside the main loop [2](#0-1) . If it doesn't match any entry, `foundToken` stays `false`, and — provided `signerAddress != address(0)` — `payRelay` is invoked with `feeStructure.feeToken` and `feeStructure.flatFee`, which routes to `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, flatFee, feeToken)` [3](#0-2) , which in `HinkalWallet.sol` unconditionally calls `sendToRelay` for that arbitrary token with no reference to `erc20TokenAddresses` at all [4](#0-3) .

The only guard on this path is `verifyWallet`, which recovers the EIP-712 signature over `(emporiumMessage, opsHash, stack.maxFee, stack.deadline)` and checks `flatFee <= stack.maxFee` [5](#0-4) . Crucially, **`feeStructure.feeToken` is never part of the signed payload** — the struct being hashed contains no token address at all (`EMPORIUM_SIGNATURE_TYPEHASH` covers `emporiumMessage`, ops hash, `maxFee`, `deadline` only). This means whoever assembles `circomData` (the transaction submitter, not necessarily the signer) can freely choose which ERC20 the flat fee is denominated in, subject only to a numeric ceiling, not a token identity. Combined with the fact that this token need not be included in `circomData.erc20TokenAddresses`/`deltaAmountChanges` (the arrays that the ZK circuit's balance-conservation constraints and the outer `_internalTransact`/`runAction` balance-diffing logic actually track), the flat fee can be siphoned from any ERC20 balance the wallet happens to hold, entirely outside the accounting that the rest of the protocol relies on to detect unauthorized token movement.

### Impact Explanation
This lets a transaction submitter redirect the wallet's session fee payment into an arbitrary ERC20 token held by the `HinkalWallet`, up to `stack.maxFee` units, that the signer's authorized operations (`stack.ops`) never referenced and the circuit never counted. This matches the "High" category: *executing calls or moving assets a wallet owner or prover never authorised* — the token identity of the debited asset is not part of what the owner signed, so funds can move in a way the signer did not intend. Repeatable per signed `EmporiumStack` message (bounded by `usedMessages` nonce reuse protection, but a new signed message each time reopens the window).

### Likelihood Explanation
Preconditions: a valid EIP-712 signed `EmporiumStack` with `signerAddress != address(0)` and `maxFee > 0`, and the wallet holding some balance of a token not listed in `circomData.erc20TokenAddresses` for that call. The submitter of the transaction (who assembles `circomData`, `deltaAmountChanges`, and the accompanying proof) controls `feeStructure.feeToken` independently of what the signer authorized. Note: I was not able to fully confirm within this session whether `calldataHash` (a field on `CircomData`) is enforced as part of the ZK proof's public inputs in a way that would bind `feeStructure`/`feeToken` to the proof and thus block a party other than the original prover from altering `feeToken` after the fact — this is the main remaining uncertainty, and it should be checked directly against the verifier/circuit code before treating this as fully exploitable by a third-party relay rather than only by the original signer/prover themselves.

### Recommendation
Include `feeStructure.feeToken` (and ideally the full `feeStructure`) in the EIP-712 typed-data hash signed by the wallet owner in `verifyWallet`, so the fee token is cryptographically bound to what the signer authorized. Additionally, require that `feeStructure.feeToken` be present in `circomData.erc20TokenAddresses` (i.e., reject the `!foundToken` fallback path entirely, or restrict it to a token explicitly authorized in the signed message) so that any wallet debit is always reflected in the balance-accounting arrays used elsewhere in the protocol.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a `HinkalWallet` for a signer EOA, and two ERC20 tokens `TokenA` (used in ops) and `TokenB` (unrelated, held by the wallet from an unrelated prior deposit).
2. Have the signer EOA sign an `EmporiumStack` with `ops` referencing only `TokenA`, `maxFee = X`, and a valid `deadline`.
3. Craft `circomData` with `erc20TokenAddresses = [TokenA]` only (excluding `TokenB`), `feeStructure = {feeToken: TokenB, flatFee: X, variableRate: 0}`, `relay = attackerRelay`.
4. Call `runAction` (via the normal `Hinkal` entry point with a matching proof for the `TokenA`-only public inputs).
5. Assert: `TokenB.balanceOf(wallet)` decreases by `X` and `TokenB.balanceOf(attackerRelay)` increases by `X`, while `TokenB` never appears in `circomData.erc20TokenAddresses`/`deltaAmountChanges` — demonstrating the broken equality "tokens leaving wallet == tokens counted in erc20TokenAddresses/deltaAmountChanges."
