### Title
Webhook HMAC does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that returned string. The `shop-domain`, `topic`, and `webhook-id` headers — which are trusted downstream and delivered to the app's handler — are never covered by the signature, breaking the intended binding of "shop authenticated" == "shop acted upon."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Registry.process` validates the HMAC purely off this signable string:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [2](#0-1) 

`HmacValidator.validate_signature` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the received HMAC:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

Because `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers and are never part of the bytes that are HMAC'd, the equality the gem's own documentation implies — "the shop that produced a valid HMAC" == "the shop passed to the handler" — does not hold. Given a single (body, valid-HMAC) pair for one installed shop under the same app `client_secret`, the `shop-domain` header can be swapped freely without invalidating the signature, since the signature check never touches that header.

### Impact Explanation
This crosses a tenant boundary: `Registry.process` hands the handler a `WebhookMetadata` whose `shop` field is attacker-controllable relative to the signature, even though the signature superficially "passed." Any app that uses `WebhookMetadata#shop` to select which merchant's data/session to read, write, or delete (a normal and expected usage pattern for multi-tenant webhook handlers) can be made to act on/for the wrong tenant, i.e., cross-tenant access — meeting the Critical impact bar in the rules (cross-tenant access via a broken identity binding).

### Likelihood Explanation
Any unprivileged internet user who can reach the app's public webhook endpoint and who possesses one legitimately-signed (body, hmac) pair for the app (which is trivial to obtain if they control even one shop that installs the same app, since the gem uses a single `api_secret_key`/`old_api_secret_key` shared across all shop installs) can replay that exact body/HMAC with a modified `shopify-shop-domain` header to a victim-targeting handler. No access token, `client_secret`, or privileged account is required — only the shared per-app secret is implicitly reused across all tenants by design, which is exactly why the shop identity must be bound into the signed bytes and currently is not.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header bytes in `to_signable_string`, or otherwise verify `request.shop` against an independent trust anchor (e.g., cross-check the header against the raw body only after confirming the request originated from Shopify's own signed envelope) before handing `request.shop` to any handler. At minimum, document and enforce that consumers must not trust `WebhookMetadata#shop` for tenant selection without additional verification, or change `HmacValidator`/`Request` so the signable string incorporates all security-relevant headers.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both under the same Shopify app (single `client_secret`).
2. Attacker controls `shop-a.myshopify.com` and thus receives a legitimately-signed webhook: body `B`, header `shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's shared secret), and `shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker resends the exact same request to the app's webhook endpoint but changes the header to `shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(B, secret)`, which still equals `H`, since `to_signable_string` only returns `B` — validation passes.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "shop-b.myshopify.com", body: parsed(B), ...))`, causing the app's handler to act on `shop-b`'s tenant context using attacker-supplied body `B`, despite the signature never having certified that binding.
