### Title
Webhook HMAC only covers the request body, letting an attacker with one valid signature replay it under an arbitrary `shop`, `topic`, or `webhook_id` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body. `HmacValidator.validate` checks the HMAC against that signable string alone. But `request.shop`, `request.topic`, and `request.webhook_id` — the identifiers the host application relies on to route and tenant-scope the webhook — are pulled straight from HTTP headers that are never included in what the HMAC signs.

### Finding Description
`Utils::HmacValidator.validate_signature` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field with `OpenSSL.secure_compare`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body`: [4](#0-3) 

Meanwhile `shop`, `topic`, and `webhook_id` are derived from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers, which are attacker-controllable and not bound to the HMAC in any way: [5](#0-4) 

`Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic`/`request.webhook_id` unconditionally to build the `WebhookMetadata` passed to the host application's handler: [2](#0-1) 

This breaks the intended identity binding: `hmac == HMAC(body ‖ shop ‖ topic ‖ webhook_id)` is what an integrator would assume, but the actual invariant enforced is only `hmac == HMAC(body)`, i.e. `shop` (and `topic`, `webhook_id`) is "a field acted on but not covered by the HMAC." Any signed body remains valid for **any** shop/topic/webhook-id combination an attacker chooses to send it with, since only the body characters feed the signature.

### Impact Explanation
An unprivileged internet user who has *legitimately* installed the app on their own shop (Shop A) — an entirely unprivileged action requiring no credentials — receives real webhook deliveries from Shopify for Shop A, correctly signed with the app's `client_secret`. Because the header carrying the tenant identity (`shopify-shop-domain`) is not covered by that signature, the attacker can capture one such webhook and replay the exact same body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (Shop B), or substituting `shopify-topic`/`shopify-webhook-id` to any registered topic. `HmacValidator.validate` still returns true because the signed bytes (the body) are unchanged, and `Registry.process` forwards `shop: "shop-b.myshopify.com"` (attacker-chosen) together with attacker-controlled body content to the host application's handler as if Shopify itself vouched for that shop/topic pairing. Any host application that trusts `WebhookMetadata#shop` for tenant-scoped writes (a normal and encouraged pattern per this gem's own webhook documentation) can be tricked into cross-tenant data injection/corruption using only a signature that was legitimately obtained for the attacker's own tenant. This is a cross-tenant authentication/identity-binding bypass entirely within the gem's HMAC verification logic, requiring no possession of `api_secret_key`.

### Likelihood Explanation
Getting a validly-signed webhook body requires nothing more than installing the app on any shop — a routine, unprivileged action any internet user can perform (or, on many app setups, webhook endpoints are also directly reachable and any leaked/observed real webhook payload+HMAC pair, e.g. from logs, network capture, or shared dev environments, can be replayed). Forging the `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id` headers on the replayed HTTP request requires no cryptographic material at all, since these headers sit entirely outside the HMAC's protected scope. The likelihood is high given how low-effort the replay is once one valid (body, hmac) pair for any shop is obtained.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material verified by `HmacValidator`, e.g. by having `Webhooks::Request#to_signable_string` incorporate these header values (or by independently validating that Shopify's actual signature scheme — which today only covers body — is supplemented in `Registry.process` with a check that `request.shop`/`request.topic` match what the app expects for that HMAC, such as cross-referencing against a known, previously-registered shop/webhook-id pair) before dispatching to `handler.handle`.

### Proof of Concept
1. Install the vulnerable app on attacker-owned shop `attacker-shop.myshopify.com`. Shopify sends a legitimate webhook to the app's public endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: w-1
   Body: B
   ```
2. Capture this request (attacker fully controls their own inbound traffic/tunnel or can observe it via a proxy in their own infrastructure).
3. Replay the identical body `B` and identical `x-shopify-hmac-sha256` value, but change the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`= B`) only, matches the unchanged signature, and returns `true`.
5. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` and dispatches it to the registered handler, which now processes attacker-supplied data under the identity of `victim-shop.myshopify.com`. [2](#0-1)
