## Title
`usdk::transfer_from` gasless-approval nonce is never consumed, permitting unlimited signature replay to drain the owner's stablecoin balance - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
The `transfer_from` function in the USDK stablecoin example implements an EIP-2612-style "permit"/gasless-approval flow: an off-chain signature from the token owner (`from`) authorizes a `spender` to move `amount` tokens. The signature covers an `Approval{owner, to, nonce, chain_id, spender, amount}` struct where `nonce` is set to `account::get_sequence_number(from)` [1](#0-0) . This is the same anti-pattern as the Biconomy `VerifyingSingletonPaymaster` bug: a signed authorization is validated but never marked "used," so it can be replayed.

### Finding Description
`account::get_sequence_number(from)` only increases when `from` itself is the transaction *sender* and completes a transaction (sequence number bump happens in the VM epilogue for the sending account) [2](#0-1) . In `transfer_from`, the transaction sender is `spender`, not `from` [3](#0-2) . Nothing in `transfer_from` increments, stores, or invalidates the nonce that was embedded in the signed `Approval` message — it is purely read and compared via `account::verify_signed_message` [4](#0-3) .

For any `from` account that does not itself submit on-chain transactions (a very common case for a custodial or delegated wallet whose entire interaction model is "sign approvals for a relayer/spender to submit"), `account::get_sequence_number(from)` remains constant across many calls. Consequently the exact same `proof` bytes produced once by the owner satisfy `verify_signed_message` every single time `transfer_from` is invoked, because the `Approval` struct — and therefore its BCS-serialized signing payload — is identical on every call.

This directly parallels the paymaster bug: `getHash(userOp)` bound the signature to a specific payload, but nothing marked that hash as "spent," so `validatePaymasterUserOp` could be replayed with the same signature indefinitely, draining the paymaster's deposit. Here, `verify_signed_message` binds the signature to `(owner, to, nonce, chain_id, spender, amount)`, but nothing marks that specific approval as consumed, so `transfer_from` can be called repeatedly with the identical `proof`, draining `from`'s USDK balance to `to` in increments of `amount` until the balance is exhausted.

### Impact Explanation
This breaks the custody invariant that a single owner-signed authorization should move value exactly once. A `spender` (or anyone who obtains the leaked/observed `proof`, since `proof` and the `Approval` fields are visible on-chain in the first successful call's transaction payload) can resubmit `transfer_from` with the same arguments repeatedly, draining the full USDK balance of `from`'s primary fungible store without any additional authorization from the owner. This is a direct, unauthorized transfer of custody of fungible-asset value — a high/critical severity issue for any deployment of this pattern, since it defeats the entire point of the "sign an approval" gasless-transfer feature and can fully drain a victim account.

### Likelihood Explanation
Likelihood is high for accounts whose transaction pattern matches the design intent of this feature (accounts that authorize transfers via off-chain signatures rather than by submitting their own transactions — e.g., custodial, resource, or app-delegated accounts). Since `from`'s sequence number does not change as a side effect of `transfer_from`, and there is no explicit re-signing requirement tied to consumption, a single captured `proof` can be replayed by anyone (the proof/approval fields are public once submitted in a transaction) as long as `from`'s sequence number hasn't independently moved. The bug requires no privileged access and no race condition — a straightforward call replay of an already-observed transaction succeeds.

### Recommendation
Track approvals as consumed, exactly as the paymaster fix recommends: store a `nonce` or a mapping of used approval hashes under the `from`/`Management` resource that is independent of the account's transaction sequence number, and increment/invalidate it inside `transfer_from` itself (e.g., `table<address, u64>` per-owner nonce that is checked-and-incremented atomically, or a `used_hash: SmartTable<vector<u8>, bool>` keyed by the hash of the `Approval`). Do not rely on `account::get_sequence_number`, since it is controlled by unrelated transactions from the owner account and is not incremented by this flow at all.

### Proof of Concept
1. Owner `from` signs `Approval{owner: from, to: attacker, nonce: account::get_sequence_number(from), chain_id, spender: relayer, amount: X}` intending to authorize a single transfer of `X` USDK to `attacker` via `relayer`.
2. `relayer` calls `usdk::transfer_from(relayer, proof, from, scheme, pubkey, attacker, X)`. It succeeds: `verify_signed_message` passes, `X` USDK moves from `from` to `attacker` [5](#0-4) .
3. Assuming `from` has not submitted any of its own transactions in the interim, `account::get_sequence_number(from)` is unchanged.
4. `relayer` (or any observer who copies the call's `proof`/arguments from the blockchain) calls `usdk::transfer_from` again with identical arguments. `verify_signed_message` passes again because the `Approval` struct — including `nonce` — is bit-for-bit identical to what was originally signed.
5. Repeat until `from`'s balance is fully drained to `attacker`, without any further owner authorization.

**Caveat/uncertainty:** This file is under `move-examples/`, i.e., it is documentation/example code rather than a core `aptos-framework` production module, so it may not itself be "mainnet-relevant" in the strict sense of governing live protocol assets — but it is presented in the repo as a reference implementation for real-world Move-based stablecoins and is very likely to be copied verbatim by third parties deploying USDK-style tokens on Aptos, making the custody-drain root cause (the same class flagged critical in the paymaster report) directly applicable to any live deployment based on this pattern. If the intent is strictly "framework-only" scope, this candidate would need to be re-scoped or dropped; I was not able to find a fully analogous replay flaw inside `aptos-framework` itself — `multisig_account.move`'s `validate_multisig_transaction` and the newer `nonce_validation.move` module both implement correct, atomic check-and-consume nonce/sequence logic [6](#0-5) , and `object.move`'s `LinearTransferRef`/`TransferRef` gating correctly re-validates ownership at transfer time [7](#0-6) , so those core custody paths did not independently hold as viable candidates.

    /// Create a LinearTransferRef for a one-time transfer. This requires that the owner at the
    /// time of generation is the owner at the time of transferring.
    public fun generate_linear_transfer_ref(self: &TransferRef): LinearTransferRef {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));
        let owner = Object<ObjectCore> { inner: self.self }.owner();
        LinearTransferRef {
            self: self.self,
            owner,
        }
    }

    /// Transfer to the destination address using a LinearTransferRef.
    public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);
        };

        let object = borrow_global_mut<ObjectCore>(self.self);
        assert!(
            object.owner == self.owner,
            error::permission_denied(ENOT_OBJECT_OWNER),
        );
        event::emit(
            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }
