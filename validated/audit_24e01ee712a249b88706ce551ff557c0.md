### Title
`verifyWallet`'s `usedMessages` replay guard binds only to the caller's own `emporiumMessage`, not to the asset created/left at Emporium, letting any unprivileged attacker sweep another user's leftover Emporium-held asset with a fresh message and no signature - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`usedMessages[circomData.emporiumMessage]` in `verifyWallet` only guarantees that a single, caller-chosen `uint256` value can't be consumed twice; it establishes no cryptographic link between that value and any specific asset that a prior `EmporiumStack` execution left sitting in the Emporium contract's own balance. Because the stateless path (`stack.signerAddress == address(0)`) requires no signature at all, any unprivileged actor can supply an unused `emporiumMessage` of their own together with a completely unrelated `EmporiumStack` whose `ops` call out to move whatever asset currently sits at the Emporium contract, and the guard will happily accept it.

### Finding Description
Broken equality: the code implements `one_message_value == one_use`, whereas asset-level security requires `one_asset_created_at_Emporium == one_authorized_claimant`. These are not the same thing, and nothing in the contract enforces the second.

Path:
- `runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) decodes an attacker-supplied `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and calls `verifyWallet(stack, circomData)`.
- `verifyWallet` (lines 302-349) only does: `require(!usedMessages[circomData.emporiumMessage]); usedMessages[circomData.emporiumMessage] = true;` and then, only if `stack.signerAddress != address(0)`, verifies an EIP-712 signature over the ops/message/fee/deadline. If `stack.signerAddress == address(0)` it returns immediately with **no signature check whatsoever** [1](#0-0) .
- In the stateless branch of `runAction` (`op.invokeWallet == false` or `signerAddress == address(0)`), the ops perform a raw `op.endpoint.call{value: op.value}(op.callData)` with `address(this)` (the Emporium contract) as `msg.sender`; the only restriction is that the selector can't be `callHinkalWallet`/`doSendToRelay` [2](#0-1) . `op.endpoint` and `op.callData` are entirely attacker-chosen.
- The `emporiumMessage` is included as a public circuit input (`contracts/CircomDataBuilder.sol:157,192`) and covered by `calldataHash` (`getHashedCalldata1`, `contracts/CircomDataBuilder.sol:20-35`), but this only proves *internal consistency* of the attacker's own `circomData`/proof - it says nothing about which assets the attacker is entitled to act on, because the attacker generates their own proof for their own (possibly zero-value) UTXOs. There is no nullifier, root-hash-of-a-specific-asset, or any other binding from `emporiumMessage`/`calldataHash` to the *victim's* prior transaction or to the specific asset left at Emporium.
- The only asset accounting done afterwards (`runAction`, lines 122-157) is purely balance-delta-based per `circomData.erc20TokenAddresses`, an array the attacker also fully controls in their own `circomData`. Any asset the Emporium contract holds (e.g., an ERC721 minted there by a prior stateless op, or ERC20 dust not swept because it wasn't in a prior `erc20TokenAddresses` list) is simply sitting at `address(EmporiumUpgradeable)` with no owner-tracking, and is reachable by anyone who can call `op.endpoint.call(...)` from that address in a subsequent, unrelated transaction.
- `onlyAllowedRecipient` (`contracts/external-actions/ExternalActionBaseUpgradeable.sol:39-46`) only checks that `msg.sender` is the whitelisted `Hinkal`/relay-routing contract calling `runAction` - it does not check anything about who the ultimate transaction originator is or what asset they're entitled to touch; any unprivileged EOA can drive this call through `Hinkal.transact` with their own proof.

Result: a victim's stateless Emporium op (e.g., minting/receiving an NFT at the Emporium contract, message=1) gets `usedMessages[1]=true`, which only stops *that same message* from being replayed. It does nothing to stop attacker's independent op set under a fresh `emporiumMessage=2` (own proof, own zero-value UTXOs, `signerAddress=address(0)` so no signature needed) from calling `nft.transferFrom(address(emporium), attacker, tokenId)` (or any other transfer of a leftover asset) directly out of the Emporium contract.

### Impact Explanation
This is direct theft of a shielded/in-flight user asset that was routed through Emporium: any leftover asset held by the Emporium contract's own balance (NFT, ERC20 dust, or an asset not covered by that transaction's `erc20TokenAddresses`/slippage accounting) can be stolen by any unprivileged third party who crafts their own valid but unrelated `EmporiumStack`/proof. This matches the Critical category ("direct theft of shielded or in-flight user funds ... proof or nullifier verification bypass") because there is no nullifier or ownership binding over Emporium-created/held assets - `usedMessages` is a nonce-replay guard for the caller, not an asset-custody control. The attack is repeatable against any future leftover balance and costs only gas plus proof generation for the attacker's own trivial transaction.

### Likelihood Explanation
Preconditions: (1) some prior transaction (victim's or even a leftover-dust scenario) leaves an asset in the Emporium contract's own balance that is not fully swept by the balance-delta accounting in `runAction` (e.g., a token/NFT not enumerated in that transaction's `erc20TokenAddresses`, or a non-fungible asset entirely, since the accounting loop only iterates `circomData.erc20TokenAddresses`); (2) attacker can call `Hinkal.transact` with `externalActionId` pointing at Emporium, an unused `emporiumMessage`, `stack.signerAddress = address(0)`, and `ops` targeting the leftover asset. Both preconditions are fully within reach of an unprivileged EOA: they generate their own proof for their own (even zero-amount) circuit inputs, and the `emporiumMessage` space is a 254-bit field so finding an unused value is trivial (they can just pick a value they've never used). No signature, no owner/role check, and no relayer whitelist bypass is required for the stateless path.

### Recommendation
Redesign the Emporium asset-custody model so that assets are never left owned solely by contract balance with no ownership record:
- Require every stateless (`signerAddress == 0`) Emporium `runAction` to fully account for and immediately sweep out *all* assets touched by the `ops` (not just those declared in `erc20TokenAddresses`), or
- Track, per created leftover asset, an explicit owner/claim record (e.g., a mapping from `(token, tokenId or amount)` to the depositor's stealth address or a nullifier derived from the creating transaction) and require any subsequent claim to prove authorization over that specific record - not merely present an unused `emporiumMessage`.
- At minimum, disallow generic `op.endpoint.call` targets in the signature-less path from touching arbitrary tokens/NFTs the caller doesn't declare and doesn't fully account for in the post-call balance reconciliation, and make the reconciliation cover every asset type moved during the `ops` execution, not just the declared `erc20TokenAddresses` array.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as an allowed recipient/external action), and a mock ERC721 contract.
2. Victim (or a setup step) calls `Hinkal.transact` with `externalActionId = Emporium`, `emporiumMessage = 1`, `stack.signerAddress = address(0)`, `ops = [{ endpoint: mockNFT, callData: mint(address(emporium), tokenId), invokeWallet: false }]`. Assert `EmporiumStorage.usedMessages[1] == true` after the call, and `mockNFT.ownerOf(tokenId) == address(emporium)`.
3. Attacker (separate EOA, own proof, own zero-amount UTXOs) calls `Hinkal.transact` with the same `externalActionId = Emporium`, a fresh `emporiumMessage = 2` (never used), `stack.signerAddress = address(0)`, `ops = [{ endpoint: mockNFT, callData: transferFrom(address(emporium), attacker, tokenId), invokeWallet: false }]`.
4. Assert both `usedMessages[1] == true` and `usedMessages[2] == true` (both independently accepted), while `mockNFT.ownerOf(tokenId) == attacker`, proving the NFT the victim created at Emporium was stolen by an unrelated party using an unrelated `emporiumMessage`/stack, with no signature and no relationship to the victim's transaction.
