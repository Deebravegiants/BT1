### Title
Permanent freezing of escrowed order funds if the order's beneficiary is blacklisted by the input token contract - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` releases escrowed input tokens to a fixed `beneficiary` address that is baked into the cross-chain `WithdrawalRequest` at order-fill or order-cancel time, with no path to redirect the transfer to a different address. If that beneficiary — the order creator on refund, or the filling solver on redemption — is later blacklisted by the input token's issuer (e.g. USDC/USDT-style blacklists), the `safeTransfer` call reverts every time the message is (re)delivered, permanently locking the escrowed tokens with no recovery mechanism, exactly mirroring the reported `recoverERC20` blacklist issue but for user escrow rather than admin dust.

### Finding Description
When an order is cancelled or filled, the gateway posts an ISMP request whose body encodes a `WithdrawalRequest{ commitment, tokens, beneficiary }` with `beneficiary` fixed at dispatch time:

- On destination-initiated cancellation, `beneficiary` is hardcoded to `order.user` (the original order creator), and this can be triggered by anyone once the deadline passes: [1](#0-0) 
- On source-initiated cancellation, the GET-response context also fixes `beneficiary: order.user`: [2](#0-1) 
- On a successful fill, `beneficiary` is fixed to the filling solver's address (`msg.sender`): [3](#0-2) 

These requests are dispatched with `timeout: 0`, i.e. they never expire and can be resubmitted indefinitely by relayers: [4](#0-3) 

When the message is delivered, `onAccept` routes `RedeemEscrow`/`RefundEscrow` straight into `_withdraw`, without any way to override the encoded beneficiary: [5](#0-4) 

`_withdraw` then unconditionally transfers each escrowed token — and any accrued relayer fee — to that fixed `beneficiary` via `IERC20.safeTransfer`: [6](#0-5) 

If the input token contract has blacklisted `beneficiary` (order creator or solver) by the time the withdrawal request is delivered, `safeTransfer` reverts, `onAccept` reverts, and the ISMP message delivery fails. Because `beneficiary` is immutably encoded in the already-dispatched request body, every future re-delivery attempt reverts identically — there is no `recoverERC20`-style escape hatch, no way for the user/solver to specify an alternate address, and no governance override for this per-order escrow (governance's `SweepDust` path only touches protocol-owned dust, not order escrow: [7](#0-6) ). The escrowed tokens remain locked in the gateway contract forever.

The identical pattern exists in the Tron variant of the gateway, `IntentGatewayV2.withdraw()`, which also transfers unconditionally to a fixed `beneficiary` decoded from the request body: [8](#0-7) 

### Impact Explanation
This causes permanent freezing of user funds: escrowed input tokens (and accrued relayer fees) for any order whose refund/redeem beneficiary becomes blacklisted on the input token contract can never be withdrawn from the `IntentGatewayV2`/`IntentsBase` escrow. There is no admin or user-controlled path to redirect the payout to a fresh address, unlike the referenced report's suggested fix of adding a beneficiary parameter with appropriate access control. This qualifies as Medium severity per the same reasoning as the original report — real but probability-bound impact (dependent on a third-party token issuer's blacklist action), though the funds-at-risk are user escrow rather than protocol dust, making it at least as severe.

### Likelihood Explanation
Reachable from ordinary, unprivileged flows: any user places an order and later cancels it (or a solver fills it), and Hyperbridge relayers permissionlessly deliver the resulting non-expiring ISMP message. No privileged role is required to trigger the freeze — it only requires that the relevant input token (commonly USDC/USDT-class tokens with blacklist functions) blacklist the order's beneficiary address between order creation and message delivery/redelivery.

### Recommendation
Add a governance- or user-signed override path allowing the beneficiary of a stuck `WithdrawalRequest` to redirect the payout to an alternate address (analogous to the original report's `recoverERC20(token, beneficiary, amount)` pattern), or fall back to a pull-based claim mechanism (e.g., crediting an internal balance the beneficiary can withdraw to any address they control) instead of an unconditional push `safeTransfer` to a single immutable address.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2`, escrowing input tokens (e.g. USDC) with `order.user = Alice`.
2. Before the order is filled, Alice's address is blacklisted by USDC's issuer for an unrelated reason.
3. The order expires; `cancelOrder` is called (by Alice or, post-deadline, by anyone), triggering `_cancelFromDest`/`_cancelFromSource`, which dispatches a `RefundEscrow` request with `beneficiary = order.user = Alice` (`ExtrinsicIntents.sol:297-307`, `240-266`).
4. Hyperbridge delivers the request; `onAccept` calls `_withdraw`, which calls `IERC20(USDC).safeTransfer(Alice, amount)` (`IntentsBase.sol:451-469`). This reverts because Alice is blacklisted.
5. Because the request never times out (`timeout: 0`) and the beneficiary is immutably encoded, every re-delivery attempt reverts the same way — Alice's escrowed USDC (and any accrued relayer fee) is permanently stuck in the gateway with no recovery path.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (finalize) {
            uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
            if (fees > 0) {
                delete _orders[body.commitment][TRANSACTION_FEES];
                IERC20(IDispatcher(host()).feeToken()).safeTransfer(beneficiary, fees);
            }

            if (isRefund) {
                emit EscrowRefunded({commitment: body.commitment, tokens: body.tokens});
            } else {
                emit EscrowReleased({commitment: body.commitment, tokens: body.tokens});
            }
        }
    }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
