No vulnerability found for this question.

**Reasoning:**

The `dependent_edges` map in `CrossShardCommitSender::new` is intentionally designed to associate a single `StateKey` with a `HashSet<(ShardId, RoundId)>` — i.e., broadcasting a single committed write to *every* shard/round that has a legitimate read dependency on that key [1](#0-0) . This is the intended mechanism for the sharded block executor: multiple downstream shards can legitimately depend on the same storage location (e.g., several transactions across different shards reading the same account's balance), and all of them must receive the write op to populate their local `CrossShardStateView` for correct speculative execution [2](#0-1) .

Several factors rule out a custody-relevant vulnerability here:

1. **No unprivileged control over dependency construction.** The `dependent_edges` are derived from `sub_block.txn_with_index_iter()` and `txn_with_deps.cross_shard_dependencies.dependent_edges()`, which are populated by the block partitioner's static analysis of transactions' actual read/write sets — this is validator-side infrastructure, not data an unprivileged transaction can directly inject to create arbitrary target mappings [3](#0-2) .

2. **`CrossShardStateView` is a read cache, not committed state.** The messages populate `CrossShardStateView::set_value`, which is only used as a speculative-read cache for pending shard executions within the same block — it does not itself mutate ledger state or account balances [4](#0-3) . The actual balance mutation is determined by the deterministic execution of the ordered transaction itself and the final state committed via the normal write-set application — replaying the *same* already-committed write value into another shard's read view does not change who owns or controls the underlying value; it only ensures shards see a consistent, correct value for cross-shard reads.

3. **The described "same victim StateKey against two shard targets" scenario is the designed behavior**, not corruption: it is exactly how legitimate cross-shard dependencies (multiple shards needing the same account's post-write value) are supposed to be resolved, and does not permit crediting/debiting the wrong holder — the write op sent is always the correct output of the txn that owns that state key, not attacker-substitutable data.

No custody boundary (deposit/withdraw/transfer/split/merge/burn ownership) is crossed by unprivileged input through this code path.

        sub_block: &SubBlock<AnalyzedTransaction>,

        let mut dependent_edges = HashMap::new();
        let mut num_dependent_edges = 0;
        for (txn_idx, txn_with_deps) in sub_block.txn_with_index_iter() {
            let mut storage_locations_to_target = HashMap::new();
            for (txn_id_with_shard, storage_locations) in txn_with_deps
                .cross_shard_dependencies
                .dependent_edges()
                .iter()
            {
                for storage_location in storage_locations {
                    storage_locations_to_target
                        .entry(storage_location.clone().into_state_key())
                        .or_insert_with(HashSet::new)
                        .insert((txn_id_with_shard.shard_id, txn_id_with_shard.round_id));
                    num_dependent_edges += 1;
                }
            }
            if !storage_locations_to_target.is_empty() {
                dependent_edges.insert(txn_idx as TxnIndex, storage_locations_to_target);
            }
        }
