## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant spoofing in `Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The `StargatePlugin` bug class is "a value used to determine the outcome of a privileged action is not covered by the cryptographic check that authenticates the request." The same class of bug exists in this gem's webhook processing: `ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to the raw body only, while the `shop` (tenant identity) is read from an unsigned header and is trusted downstream without being bound to that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is derived straight from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, with no cryptographic binding to the payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC over exactly `verifiable_query.to_signable_string` (the body), using the app's single, app-wide `api_secret_key` — the same secret for every shop that has the app installed: [3](#0-2) 

`Webhooks::Registry.process` verifies only that HMAC, then immediately trusts `request.shop` (the unsigned header) as the tenant identity when dispatching to the app's handler: [4](#0-3) 

The binding that should hold is: `HMAC-verified(shop)` == `shop used to attribute the event`. Instead, the code verifies `HMAC-verified(body)` and then separately reads `shop` from an unauthenticated header, i.e. `HMAC-verified(body) ⇏ shop-attribution(shop)`. Because the HMAC secret (`Context.api_secret_key`) is shared across every shop/tenant that installs this app (it's the app's client secret, not a per-shop secret), any shop that has legitimately received one authentic webhook delivery (body + valid HMAC, its own genuine traffic from Shopify) possesses a `(body, hmac)` pair that will pass `HmacValidator.validate` regardless of which shop domain is asserted in the header. That tenant can resend the identical body+HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will accept the signature as valid and hand `WebhookMetadata.new(shop: request.shop, ...)` — now the attacker-chosen victim shop — to the app's handler.

### Impact Explanation
This is a cross-tenant confusion / cross-tenant access vector as defined in the impact tiers: a valid signature (proving only "issued with this app's secret," not "issued for this shop") is used to attribute a payload to a shop of the attacker's choosing. Any host application that uses `WebhookMetadata#shop` to look up per-tenant records, update per-tenant state, or make authorization decisions (the intended, documented use of the `shop` field returned by this gem) can be made to act on/against a shop it never received a webhook from. This crosses a tenant boundary using only capabilities an ordinary, already-onboarded merchant/tenant has (the ability to receive and replay their own legitimate webhook traffic) — no `access_token`, `client_secret`, or privileged account is required beyond the attacker's own install.

### Likelihood Explanation
Any current tenant of a multi-tenant app built on this gem naturally receives legitimate `(raw_body, hmac)` pairs for their own shop over time. Replaying such a pair to the app's public webhook endpoint with a modified shop-domain header requires only basic HTTP tooling — no cryptography needs to be broken, since the header is simply never covered by the signature computation in `to_signable_string`.

### Recommendation
Bind the tenant identity into the signed material or otherwise cryptographically pair the `shop` claim with the HMAC before dispatch: e.g., require the app to independently verify `request.shop` against a known/installed shop record before trusting it in `WebhookMetadata`, or extend the signable string construction to reject processing when the shop asserted in the header cannot be corroborated against the session/subscription that registered the webhook.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)` from their own traffic (they are a legitimate recipient of this exact request).
3. Attacker resends a request to the app's webhook endpoint with the same body `B`, same `H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and matches `H` — validation succeeds (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `request.shop` returns `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/request.rb:20-23`), which is passed as-is into `WebhookMetadata` and handed to the app's registered handler (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process/act on data attributed to `victim-shop.myshopify.com` that the attacker actually authored.
