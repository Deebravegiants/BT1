Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but then trusts the `shop-domain` header — which is never included in the signed material — as the tenant identifier passed to the host application's handler. Because the HMAC secret (`Context.api_secret_key`) is shared by the app across all shops that install it, any merchant with the app installed on their own store can capture a legitimately-signed webhook and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a different (victim) shop. The signature check still passes because it never covered that header, causing the application to process attacker-supplied event data as if it originated from another tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that `to_signable_string` value and compares it against the `hmac-sha256` header using the app's global `api_secret_key`: [2](#0-1) 

`Registry.process` uses this validation as the sole authentication gate, then immediately reads `request.shop` (sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header) and forwards it, unauthenticated, into `WebhookMetadata` which is handed to the app's handler as the tenant identifier: [3](#0-2) [4](#0-3) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from headers that are checked for presence but never bound into the signed payload: [5](#0-4) 

The binding that should hold is: `shop-domain header == shop bound by HMAC signature`. In this gem, the equality is broken — the HMAC only proves "this body byte-string was signed with the app's secret key at some point," not "this body was delivered for shop X." Since `Context.api_secret_key` is the same secret for every shop that installs the app (it is the app's client secret, not a per-shop secret), an unprivileged party who is simply a legitimate merchant of the same app can:
1. Install the app on their own shop and receive a real, validly-signed webhook (`raw_body` + `hmac-sha256` for shop A).
2. Replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint, but substitute the `shopify-shop-domain` header with shop B's domain (and optionally change `topic`/`webhook-id`/`api-version`, which are equally unbound).
3. `HmacValidator.validate` still succeeds because it only re-derives the HMAC from `raw_body`, which is unmodified.
4. `Registry.process` builds `WebhookMetadata.new(shop: "shop-B.myshopify.com", body: <attacker's own order/customer data>, ...)` and invokes the host app's handler as if the event belongs to shop B.

### Impact Explanation
This crosses a tenant boundary the gem is responsible for enforcing: it lets one shop inject arbitrary attacker-controlled webhook payloads that the app attributes to a different shop, without the attacker needing shop B's credentials, access token, or any privileged access — only their own (mundane) installation of the app. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up the shop's session/access token, update order/customer records, or trigger uninstall/GDPR flows), this can lead to cross-tenant data corruption, incorrect authorization decisions keyed off the wrong shop, or triggering shop-B-scoped side effects using shop-A-controlled data. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in any app storing/using `data.shop` from webhook metadata to select per-tenant state, because: (1) the attacker only needs their own working installation of the target app (no special privilege), (2) webhook endpoints are typically public HTTP endpoints reachable from the internet, and (3) the replay requires no cryptographic breakage — just header substitution, since the signed material never included the header being spoofed.

### Recommendation
Bind the tenant/shop identity (and other security-relevant headers such as `topic`, `webhook-id`, `api-version`) into the signed material, or otherwise cryptographically tie the `shop-domain` header to the signature — e.g., by having `to_signable_string` incorporate the shop domain, or by independently verifying the shop domain against a value derived from a signed claim rather than trusting a raw header. At minimum, document clearly that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used by host applications as a trusted tenant key without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker-shop.myshopify.com` and receives a real webhook, e.g. for `orders/create`, with:
   - `raw_body` = `{"id": 123, ...}` (attacker-controlled order content, since they can generate real orders on their own store)
   - `x-shopify-hmac-sha256` = valid signature computed by Shopify over `raw_body` using the app's shared `client_secret`
   - `x-shopify-shop-domain` = `attacker-shop.myshopify.com`
2. Attacker POSTs this exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint again, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` succeeds since only `raw_body` is hashed: [6](#0-5) 
   - `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...))` executes with `shop` pointing at the victim, per: [7](#0-6) 
4. The host application's handler processes attacker-supplied data believing it originates from `victim-shop.myshopify.com`, demonstrating the cross-tenant identity confusion.
