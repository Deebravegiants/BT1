### Title
Webhook shop identity spoofing via unauthenticated header — HMAC covers only the raw body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature only ever covers the raw request body. This breaks the identity binding: `signed_bytes == body` but `shop_used_by_handler == unauthenticated_header`. Any actor who can obtain one valid `(body, hmac)` pair signed with the app's shared secret (e.g., by simply installing the public app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` will accept it as valid and dispatch it to the app's `WebhookHandler` tagged with the attacker-chosen shop, causing the host app to process (and potentially persist/act on) attacker-controlled webhook data under another tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `#topic` are read straight from headers that are never included in the signed payload: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e. the body) and compares against the received signature: [3](#0-2) 

`Registry.process` validates the HMAC of the whole request object, then immediately trusts `request.shop` (from the header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the app's webhook secret (`api_secret_key`) is the same for every shop that installs the app, any shop owner who legitimately receives a webhook (a completely unprivileged action — installing a public app) obtains a `(raw_body, hmac)` pair that is valid regardless of which shop the request claims to be from. That same pair can be replayed with any `shop-domain`/`shopify-shop-domain` header value, and `HmacValidator.validate` will still return `true` because the header is never part of `to_signable_string`. This lets an attacker impersonate an arbitrary victim shop for any webhook topic whose body content they can predict or control (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, or any topic where the body is attacker-influenced/predictable), causing the host application to execute tenant-scoped side effects (data deletion, redaction, uninstall cleanup, etc.) attributed to the wrong shop.

### Impact Explanation
This crosses a tenant boundary: the library's own signature check does not bind the claimed shop to the signed bytes, so a party with no relationship to the victim shop can make the host application believe a webhook originated from that shop. This matches "cross-tenant access" — a Critical-severity impact category per the rules, since it lets one merchant's webhook capsule be replayed as if belonging to a different merchant.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair requires nothing more than installing the target app on any store (a normal, unprivileged action available to any Shopify merchant/developer), and topics with static or attacker-influenced bodies (e.g., `app/uninstalled` has an essentially empty/predictable body) make forging a usable payload straightforward. No access to `api_secret_key`, tokens, or TLS interception is required — only capturing a legitimately-received webhook and modifying an outbound header.

### Recommendation
Bind the shop (and topic/webhook id) into the material that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the signed body before trusting it for tenant-scoped dispatch. At minimum, the library should document/enforce that consumers cross-check `request.shop` against the shop associated with a stored, previously-issued webhook registration/session rather than trusting the header value outright, and/or extend `to_signable_string` (or a companion check) to incorporate the shop domain so tampering invalidates the signature.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; Shopify sends a webhook (e.g. `app/uninstalled`) to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker captures `(B, H)` from their own endpoint logs.
3. Attacker crafts a new HTTP request to the app's webhook endpoint using the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` computes the same HMAC over `B` and succeeds because the shop header was never part of the signed string.
5. `Registry.process` dispatches to the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, so the app performs tenant-scoped actions (e.g. uninstall cleanup) against the victim tenant on the attacker's behalf.
