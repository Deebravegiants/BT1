### Title
Webhook shop attribution is not covered by HMAC verification, allowing shop impersonation via header spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` (and `topic`/`api_version`/`webhook_id`) values it hands to the app's handler are taken from unauthenticated HTTP headers that are never included in the signed material. Any party that possesses one validly-signed webhook body/HMAC pair for the shared `api_secret_key` (e.g., a webhook delivered to their own shop's installation of the same app) can replay that exact body to a victim app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, and the library will report a different (attacker-chosen) shop as the source to the handler.

### Finding Description
`Webhooks::Request` mixes in `Utils::VerifiableQuery` and defines the signable string as the raw body only: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read straight from HTTP headers without any cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then forwards the *header-derived* `request.shop` (and other header fields) to the app's handler as authenticated `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is:
`shop_reported_to_handler == shop_that_Shopify_actually_signed_this_body_for`

Because the HMAC only covers `@raw_body`, this equality is not enforced by the gem: the `shopify-shop-domain` header can be swapped for any value while keeping the same body and the same valid HMAC (the secret `api_secret_key` is shared across all shops that installed a given app, so any shop running the app can obtain a legitimately signed webhook body/HMAC pair from Shopify for its own store). Replaying that pair to the same endpoint with a different `shop-domain` header still passes `Utils::HmacValidator.validate`, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain rather than the shop that the body was actually generated for.

### Impact Explanation
This breaks a tenant boundary the gem is expected to enforce for webhook consumers: application code that keys persistence, authorization or business logic off of `WebhookMetadata#shop` (a very common pattern, since it is the only per-shop identifier the gem hands back from `process`) can be made to attribute one shop's payload data to a different, victim shop. This is a cross-tenant integrity/impersonation issue reachable purely through HTTP requests to the app's public webhook endpoint, with no access token, no `client_secret`, and no privileged account required from the attacker — only participation as an ordinary merchant/installer of the same app.

### Likelihood Explanation
Medium. The attacker needs the app already installed on at least one shop they control (a normal, unprivileged action for any Shopify merchant/developer) in order to capture one legitimately signed webhook body+HMAC pair for a known topic. Replaying that pair with a modified `shop-domain` header to the shared webhook endpoint requires no further secrets, since `Registry.process`/`Utils::HmacValidator` never bind the header to the signature.

### Recommendation
Include the shop domain (and topic) in the signed/verified material, or otherwise cryptographically bind the `shopify-shop-domain` header to the authenticated body before trusting it (e.g., verify the header value against Shopify's per-request signature scheme rather than passing it through unchecked, or require callers to independently confirm the `WebhookMetadata#shop` value against a known/expected installed-shop list before acting on it). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted as a tenant identifier without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery for topic `orders/create`, including its raw body and the `x-shopify-hmac-sha256` header (both valid under the shared `api_secret_key`).
2. POST that identical raw body to the victim app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` instead of the attacker's own domain.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `OpenSSL::HMAC.hexdigest(secret, raw_body)` against the header HMAC — the shop-domain header is never part of the signed input (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload was never generated for `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
