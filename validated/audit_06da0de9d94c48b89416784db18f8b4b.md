### Title
Webhook `shop` (and `topic`) header is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `Request#shop` and `Request#topic` are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body only, then passes the header-derived `shop` value on to the host application's handler as the authoritative tenant identifier, without that value ever being bound to the signature.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be exactly `@raw_body` — nothing else: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.), which are attacker-controllable on any request reaching the app's webhook endpoint and are never included in the HMAC computation: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then immediately forwards the unauthenticated `request.shop` value to the registered handler as the tenant identifier in `WebhookMetadata`: [4](#0-3) [5](#0-4) 

**Identity binding broken (as an equality):** the gem implicitly claims `shop header == shop that produced the HMAC`, but the actual invariant enforced is only `HMAC(raw_body) == received_hmac`. The `shop` field is *acted on* (passed to the handler as the trusted tenant key) but is *not covered by the HMAC*. This matches the described bug class directly: "a field acted on but not covered by the HMAC."

### Impact Explanation
Any party who can produce one genuinely-signed webhook body+HMAC pair for the app's client secret (e.g. by legitimately installing the app on their own store and triggering a webhook such as `orders/create`) can replay that exact body/HMAC combination while substituting the `shopify-shop-domain` header for a victim shop's domain. Because `to_signable_string` never includes the shop header, the HMAC check in `Registry.process` still passes. The host application's `WebhookHandler#handle` then receives `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop, since `data.shop` is taken directly from `request.shop`: [6](#0-5) 

Any host app that uses `data.shop` to select which tenant's records to update, credit, or otherwise mutate (a documented, expected usage pattern of this gem) can be made to apply attacker-supplied webhook data to a different merchant's tenant — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
The attacker needs their own valid webhook subscription (any developer/merchant can install their own Shopify app instance or use their own dev store to receive a legitimately-signed webhook) and network access to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is required — only a body/HMAC pair that Shopify legitimately produced for the attacker's own shop, plus the ability to substitute the shop-domain header at delivery/replay time. This is a design flaw in `Webhooks::Request#to_signable_string`, not a misuse of a documented contract by the host app, since the host app is only shown `data.shop` via `WebhookMetadata` with no indication it is unauthenticated.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`) header values into the HMAC-verified signable content, or otherwise cryptographically tie the header-derived `shop` to the signed body (e.g., by including these header values in `to_signable_string`, or by documenting/enforcing that consumers must independently correlate `data.shop` against a shop known to be associated with the corresponding webhook subscription/session before acting on it).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and subscribes to `orders/create`.
2. Shopify delivers a legitimately signed webhook: body `B`, header `shopify-hmac-sha256: HMAC(secret, B)`, header `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends this request to the app's webhook endpoint but changes only the `shopify-shop-domain` header to `victim.myshopify.com`, keeping body `B` and the HMAC header untouched.
4. `Webhooks::Request#hmac` still decodes the same signature, and `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (which equals `B`) — the check passes: [7](#0-6) 
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the spoofed `victim.myshopify.com`, and the host handler acts on attacker-controlled data believing it originated from the victim's shop.
