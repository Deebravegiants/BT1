### Title
Missing shop-domain validation in `TokenExchange.exchange_token` allows the app's `client_secret` to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the target host for the OAuth token-exchange POST directly from the JWT `dest` claim, without running it through `Utils::ShopValidator.sanitize!`, unlike every sibling method in the same trust boundary (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`), which all validate the shop before it is allowed to become the destination host for a request carrying the app's `client_id`/`client_secret`.

### Finding Description
`exchange_token` decodes the caller-supplied session token and takes the shop straight from the token payload: [1](#0-0) 

That value is used, unsanitized, to build the session whose `shop` becomes the request host: [2](#0-1) 

`Clients::HttpClient` turns `session.shop` directly into the base URI that receives the POST body containing `client_id` and `client_secret`: [3](#0-2) 

Contrast this with the three sibling entry points that reach the exact same `HttpClient`/`client_secret`-POST pattern — each of them calls `Utils::ShopValidator.sanitize!(shop)` first and only ever uses the validated result as the host: [4](#0-3) [5](#0-4) [6](#0-5) 

`JwtPayload` itself only checks the signature and the `aud` claim; it never constrains `dest`'s shape or ties it to `iss`, or restricts it to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [7](#0-6) 

The invariant the gem is supposed to enforce — "the host that receives the app's `client_secret` must equal a validated Shopify domain" — is checked on three of the four code paths that reach `HttpClient` with a secret-bearing body, but is silently skipped on the fourth (`exchange_token`), exactly the kind of "parallel path missing a check the sibling path already performs" pattern described in the source report.

### Impact Explanation
If `dest_shop` is not constrained to a `*.myshopify.com`/trusted domain, `exchange_token` will build a request URL of `https://#{dest_shop}/admin/oauth/access_token` and POST the app's `client_id` and `client_secret` to it. Any caller able to influence the `dest` claim value reaching this method (e.g., through host-app bugs in session-token issuance/relaying, or any future weakening of the JWT decode/verify path) would cause SSRF carrying the app's OAuth client credentials to an arbitrary host — a High severity impact per the scope rules (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
Exploitability is bounded by the fact that `dest` sits inside an HS256 JWT verified against `Context.api_secret_key` — under normal operation only Shopify can mint such a token, and `JwtPayload.new` will raise `InvalidJwtTokenError` for any tampered token unless it is re-signed with a secret the caller doesn't have. However, this is precisely a defense-in-depth check that the library enforces in three sibling functions but omits here, so any future change (or edge case) in how `dest` is populated/relayed would bypass the domain check entirely with no compensating control in this function. Given the inconsistency compared to `client_credentials`, `refresh_token`, and `migrate_to_expiring_token`, this is a real gap in the gem's own defense, not merely a host-application misuse.

### Recommendation
Validate `dest_shop` with `Utils::ShopValidator.sanitize!` immediately after extracting it from the JWT payload in `exchange_token`, mirroring `client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token`, before it is used to construct `shop_session` / the `HttpClient` base URI.

### Proof of Concept
Conceptual (bounded by the JWT-signature trust assumption noted above):
1. Obtain or induce a session token whose `dest` claim is `attacker.example` instead of a `*.myshopify.com` host, valid under the app's `api_secret_key` (e.g., via a bug in a component that mints/relays session tokens, or a future regression in `JwtPayload`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop` becomes `"attacker.example"` and is never checked with `ShopValidator`; `HttpClient` posts `{client_id, client_secret, subject_token, ...}` to `https://attacker.example/admin/oauth/access_token`, leaking the app's `client_secret` to the attacker's host — the exact behavior `ShopValidator.sanitize!` exists to prevent, and does prevent, in the three sibling functions.
