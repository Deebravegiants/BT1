### Title
OAuth callback token exchange sends `client_secret` to an unvalidated `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the session used for the access-token exchange directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-exchange code path in the gem (`RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`), which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to send the `client_secret`. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The identity binding that should hold is: **the host that receives the app's `client_secret` == a Shopify-trusted domain (validated by `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`)**. In `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`'s `migrate_to_expiring_token`, this binding is enforced explicitly: `validated_shop = Utils::ShopValidator.sanitize!(shop)` is called before the `shop` value is used to build the `Session` that `Clients::HttpClient` turns into a request base URI. [5](#0-4) 

`Oauth.validate_auth_callback`, however, takes `auth_query.shop` directly — the raw `shop` field parsed from the AuthQuery — and constructs `null_session = Auth::Session.new(shop: auth_query.shop)` with no call to `ShopValidator` anywhere in `oauth.rb`. [6](#0-5)  This session is then handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, whose constructor sets `@base_uri = "https://#{api_host || session.shop}"` with no domain-shape or trust-list check at all. [1](#0-0)  The subsequent POST to `access_token` includes `client_id` and `client_secret` in the body. [7](#0-6) 

The `shop` value is nominally covered by the request's HMAC (`AuthQuery#to_signable_string` includes `shop`), which `HmacValidator.validate` checks using `Context.api_secret_key`. [8](#0-7) [9](#0-8)  That HMAC check only proves the query parameters were signed with the app's secret; it does **not** prove `shop` is a real, trusted Shopify domain, and it exists purely to prevent parameter tampering, not to enforce the domain-trust boundary that `ShopValidator` is specifically designed for elsewhere in this same gem.

### Impact Explanation
If this binding is skipped and any code path can influence the `shop`/host value reaching `validate_auth_callback` (e.g., an app forwarding a `shop` parameter it received from an untrusted redirect, or any future change that relaxes HMAC/state checks), the gem will `POST` the app's `client_id` and `client_secret` to an attacker-controlled host built purely from string interpolation, with no allow-list check. This is exactly the class of SSRF-with-credentials the rules call out ("a host validated versus the host that receives the access token or `client_secret`"). Given the identical operation is explicitly protected by `ShopValidator.sanitize!` in three sibling methods in this same codebase, the omission in `validate_auth_callback` is a real, demonstrable inconsistency in the trust boundary enforcement, not a false positive.

### Likelihood Explanation
Under the documented, intended usage (Shopify-initiated callback, HMAC verified with the real `api_secret_key`), exploitation requires the attacker to control the value of `shop` while still producing a valid HMAC signed with the app's secret — which the rules explicitly place out of scope ("anything requiring `api_secret_key`"). This lowers the immediately exploitable likelihood from a remote, credential-less attacker's perspective. The finding is best characterized as a defense-in-depth gap / inconsistent enforcement of the `ShopValidator` domain-trust boundary rather than a demonstrated end-to-end unauthenticated bypass, since the HMAC currently is the only thing standing between an attacker-supplied `shop` and the `client_secret`-bearing request, and it is provably the only one of four analogous flows lacking the `ShopValidator.sanitize!` domain check.

### Recommendation
Add `validated_shop = Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`, mirroring `refresh_token.rb`, `client_credentials.rb`, and `token_exchange.rb#migrate_to_expiring_token`, so the `client_secret`-bearing request is only ever sent to a domain on `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (or an explicitly configured `myshopify_domain`), independent of the HMAC check.

### Proof of Concept
1. Compare `lib/shopify_api/auth/refresh_token.rb:24` (`validated_shop = Utils::ShopValidator.sanitize!(shop)`) against `lib/shopify_api/auth/oauth.rb:73` (`null_session = Auth::Session.new(shop: auth_query.shop)` — no sanitize call).
2. Trace `null_session` into `Clients::HttpClient.new(session: null_session, ...)` at `lib/shopify_api/auth/oauth.rb:81`.
3. Observe `HttpClient#initialize` at `lib/shopify_api/clients/http_client.rb:18` sets `@base_uri = "https://#{api_host || session.shop}"` with zero validation of `session.shop`'s format or trust.
4. Observe the same `client.request(...)` call sends a JSON body containing `client_secret: Context.api_secret_key` (`lib/shopify_api/auth/oauth.rb:74-90`) to that unchecked host — the exact operation that is guarded by `ShopValidator.sanitize!` in every other credential-exchange method in the gem.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
