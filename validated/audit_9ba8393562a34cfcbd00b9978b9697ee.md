## Analysis

The alt.fun codebase contains a direct structural analog to the reported bug class in `Bonding.transferCreator`.

### Finding

`Bonding.sol`'s `transferCreator` is a single-step, immediate role transfer with no acceptance step and no recovery mechanism — exactly the "Direct Role Transfer" / "Lack of Recovery Mechanism" pattern from the external report: [1](#0-0) 

```solidity
function transferCreator(address tokenAddress, address newCreator) external {
    if (newCreator == address(0)) revert ZeroAddress();
    TokenInfo storage info = _s().tokenInfo[tokenAddress];
    if (msg.sender != info.creator) revert NotCreator();
    if (newCreator == info.creator) revert InvalidInput();
    info.creator = newCreator;
    emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
}
```

The only validation is a zero-address check and a same-address check — there is no acceptance step, no timelock, and no way for the protocol owner to correct a mis-set `creator` afterward.

This `creator` field is exactly what `Zap` reads to attribute every future fee accrual: [2](#0-1) . The fees themselves accumulate in `FeeVault.creatorBalance[creator]`, keyed purely by address, with claim gated to `msg.sender == creator`: [3](#0-2) 

Notably, the rest of the codebase deliberately avoids this exact bug class for every *other* privileged role: `Zap`, `FeeVault`, and `LPLock` all use `Ownable2StepUpgradeable`, requiring the new owner to explicitly `acceptOwnership()` before a transfer takes effect, precisely to prevent bricking control via a fat-fingered address [4](#0-3) , confirmed by the `Ownable2Step` test suite [5](#0-4) . `transferCreator` alone breaks this pattern with a bare single-step assignment, confirmed by the test-suite's simple happy-path/only-creator checks with no acceptance flow [6](#0-5) .

### Impact

If a token creator mistypes `newCreator` (or specifies an address they don't control, or a contract without a `claim`-compatible interface), **all future 0.25% creator-side fee revenue for that token** is unrecoverably diverted to `FeeVault.creatorBalance[newCreator]`. There is no owner-level override in `FeeVault` to reassign a mis-set `creatorBalance` entry — `setFeeTo`, `addDepositor`, `removeDepositor` only touch protocol-side state, not per-creator balances. Every subsequent buy/sell on that token accrues USDC that becomes permanently frozen/unclaimable if the target address has no private key or can't call `claim()`.

Since `transferCreator` is fully permissionless from the current creator's perspective and irreversible, this satisfies the "permanent freezing of creator funds" criterion.

### Recommendation
Adopt a two-step creator transfer (`proposeCreator` / `acceptCreator`) mirroring the `Ownable2StepUpgradeable` pattern already used elsewhere in the protocol, so the new creator address must explicitly accept before fee attribution moves, preventing loss to an unreachable address.

### Title
Single-Step, Unrecoverable Creator-Role Transfer Permanently Diverts Future Fee Accrual - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding.transferCreator` performs an immediate, one-step reassignment of a token's `creator` (used by `Zap`/`FeeVault` for fee attribution) with no acceptance step and no recovery path, unlike every other privileged-role transfer in the codebase (`Zap`, `FeeVault`, `LPLock` all use `Ownable2StepUpgradeable`).

### Finding Description
`transferCreator` at [1](#0-0)  only checks `newCreator != address(0)` and `newCreator != info.creator` before overwriting `info.creator` directly. No acceptance from `newCreator` is required. Once changed, `Zap`'s fee accrual calls `FeeVault.accrue(token, creator, ...)` with the new address [7](#0-6) , and `FeeVault` has no owner-level mechanism to reassign a `creatorBalance` entry once fees have accrued to the wrong address.

### Impact Explanation
A creator fat-fingering `newCreator`, or transferring to an address whose controller can't/won't call `claim()`, permanently and irrecoverably diverts all future 0.25% fee accrual for that token into an inaccessible `FeeVault.creatorBalance` slot. This is a permanent freeze of creator funds with no protocol-level remedy, matching Medium severity per the analog report.

### Likelihood Explanation
Any token creator can trigger this unintentionally on any of their launched tokens at any time — it requires no special conditions, and typos/incorrect addresses in a permissionless, no-confirmation call are a realistic and previously-documented risk class (as evidenced by the rest of the codebase's deliberate use of two-step ownership transfers everywhere else).

### Recommendation
Convert `transferCreator` to a two-step pattern: `proposeCreator(tokenAddress, newCreator)` settable only by the current creator, and `acceptCreator(tokenAddress)` callable only by the proposed address, mirroring `Ownable2StepUpgradeable`'s `transferOwnership`/`acceptOwnership` already used in `Zap`, `FeeVault`, and `LPLock`.

### Proof of Concept
1. Creator `C` launches a token via `Bonding.launch`, becoming `tokenInfo[token].creator`.
2. `C` calls `bonding.transferCreator(token, X)` where `X` is a typo'd address or an address `C` doesn't control.
3. Trading continues; `Zap.buy`/`sell` calls `FeeVault.accrue(token, X, creatorAmount, ...)` for every subsequent trade, per [7](#0-6) .
4. `FeeVault.creatorBalance[X]` grows indefinitely; only `X` can call `claim()` per [8](#0-7) . If `X` is uncontrolled/unreachable, this balance is permanently frozen with no admin recovery path anywhere in `FeeVault.sol` or `Bonding.sol`.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    // ─── Claims ──────────────────────────────────────────────────────────

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```
