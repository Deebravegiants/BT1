Audit Report

## Title
Match-arm ordering in `run_call` grants full `AllowReentry` instead of stipend-restricted `AllowNext` for value-transferring calls at `gas_limit == CALL_STIPEND` - (File: substrate/frame/revive/src/vm/evm/instructions/contract.rs)

## Summary
`run_call` intends to detect Ethereum's classic 2300-gas stipend transfer pattern (`value != 0`, `gas_limit == CALL_STIPEND`) and apply the restrictive `ReentrancyProtection::AllowNext` guard, but the match arms are ordered so that the wildcard `(false, _)` arm (matching any non-zero value) is checked before `(_, true)`. This makes the `AllowNext` branch unreachable whenever `value != 0`, so all value-transferring calls — including the exact stipend case — receive the permissive `ReentrancyProtection::AllowReentry` instead.

## Finding Description
The code in `run_call` reads: [1](#0-0) 

Because Rust matches tuple patterns top-to-bottom and the first arm `(false, _)` is a wildcard on the second element, any call with `value.is_zero() == false` (i.e., a non-zero-value transfer) matches this first arm unconditionally — regardless of whether `gas_limit == CALL_STIPEND` — and receives `(true, ReentrancyProtection::AllowReentry)`. The comment immediately above the second arm `(_, true)` documents the intended heuristic (detect `gas_limit = 2300` for stipend-limited transfers and apply `AllowNext`), but that arm can only ever be reached when `value.is_zero() == true`, which is a contradiction with the "value transfer" scenario the heuristic is meant to protect. This confirms the claim's root-cause analysis: the ordering is backwards relative to the documented intent.

The resulting `reentracy` value is passed directly into `interpreter.ext.call(...)` as the reentrancy-protection parameter for the call, so the weaker `AllowReentry` setting governs the actual call.

## Impact Explanation
This is a real logic defect: the code does not implement its own documented security intent. `ReentrancyProtection::AllowReentry` is the least restrictive setting and does not block a callee from re-entering the calling contract, whereas `AllowNext` is specifically designed to enforce (at the revive gas scale) the guarantee that Ethereum's 2300-gas stipend achieves natively (insufficient gas for the callee to make further state-changing calls). Because PolkaVM/revive's gas-metering scale differs from Ethereum's, the mis-assigned `AllowReentry` removes a protection that contract authors relying on the `.transfer()`/`.send()`-style low-gas pattern would reasonably expect from an EVM-compatibility layer. This is an in-scope logic/security bug in the `pallet-revive` EVM-compatibility execution path, not a node-only, governance-only, or best-practice issue.

## Likelihood Explanation
The condition is fully attacker/user-triggerable and requires no privilege: any contract using the common `call{value: v, gas: 2300}(...)` idiom (as generated by `solc` for `.transfer()`/`.send()`) executed through `pallet-revive`'s EVM-compatible interpreter will hit this exact code path. The trigger condition (`value != 0`, `gas_limit == CALL_STIPEND`) is a compiler-emitted constant, making it deterministic and trivially reproducible in a unit test that directly exercises `run_call`'s match logic or observes the `reentracy` value passed to `Ext::call`.

## Recommendation
Restructure the match/condition so the compound stipend heuristic is evaluated as a distinct, higher-priority condition, independent of value-nonzero wildcard ordering, e.g.:
```rust
let (add_stipend, reentracy) = if !value.is_zero() && gas_limit == CALL_STIPEND {
    (true, ReentrancyProtection::AllowNext)
} else if !value.is_zero() {
    (true, ReentrancyProtection::AllowReentry)
} else {
    (false, ReentrancyProtection::AllowReentry)
};
```
This ensures the `value != 0 && gas_limit == CALL_STIPEND` case is checked and handled before the more general non-zero-value fallback, matching the documented intent in the code comments.

## Proof of Concept
1. Unit test in `substrate/frame/revive/src/vm/evm/instructions/contract.rs`: construct a call with `value = U256::from(1)` and `gas_limit = U256::from(CALL_STIPEND)` (2300), invoke `run_call`, and assert the `reentracy` value passed to `Ext::call`.
   - Expected per code comment/intent: `ReentrancyProtection::AllowNext`.
   - Actual (current code): `ReentrancyProtection::AllowReentry`, confirmed by direct reading of the match arms at lines 193–203.
2. Integration-level exec-stack test: deploy a victim contract using the canonical checks-then-effects-violating withdraw pattern (`call{value: bal, gas: 2300}` before zeroing balance) and an attacker contract that re-enters `withdraw()` from its fallback; show the reentrant call is not blocked under current code, and would be blocked once the match ordering is fixed to select `AllowNext`.
