### Title
Unbounded spot-price venue pricing for Uniswap V4-funded pairs enables oracle manipulation drain of solver funds - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
`FXFiller`'s "venue pricing" path prices curveless, Uniswap-V4-funded pairs directly off a single pool's current `sqrtPriceX96` with no TWAP, no size/impact term, and only an *optional* static-deviation guard. This mirrors the bug class in the Channels Finance incident (an old Compound-v2-style oracle that trusts an instantaneous, thinly-guarded price feed): an attacker can move a thin Uniswap V4 pool's spot price before or during order submission, causing the solver to quote and fill an intent at a manipulated rate and drain solver-held liquidity, exactly the "Price Manipulation" bug class in the report.

### Finding Description
For pairs without static bid/ask curves, `FXFiller.resolveLegRates` (`sdk/packages/simplex/src/strategies/fx.ts:1443-1466`) and `referenceRate` (`fx.ts:1344-1364`) source pricing from `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice`, which in turn calls `computeDirectPoolPriceUsd`: [1](#0-0) 

That function returns the raw pool mid (`sdkPool.token0Price`/`token1Price`) derived straight from the pool's current `sqrtPriceX96`, as also documented in the flow notes: "computeDirectPoolPriceUsd returns the raw pool mid derived from sqrtPriceX96... there is no size or impact term — computeLegPolicyOutput extends the mid linearly across the whole priced quantity." [2](#0-1) 

The only defense is `checkPriceGuard`, which compares the spot quote against a **static** `referencePrice`/`maxDeviationBps` — and this guard is explicitly optional (both fields can be omitted, leaving the chain "unguarded"): [3](#0-2) [4](#0-3) 

Even when the guard is configured, it bounds only *deviation from a fixed reference*, not the pool's actual depth or execution cost against the priced notional — so a pool that is legitimately (or maliciously) shallow can still be pushed anywhere inside the static band and the solver will linearly extend that spot price across the entire order size, exactly as the flow doc warns: "A venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against." Separately, the overfill clamp that used to bound losses from "a manipulated venue price" on this exact path has been intentionally disabled — the filler now only logs a warning and still fills the unclamped, larger amount: [5](#0-4) 

This is the same root cause class as the Channels Finance incident: relying on a single, unprotected, instantaneously-manipulable on-chain price read (no TWAP, no depth/impact accounting, and an optional/misconfigurable band) to value an asset for value-transferring decisions.

### Impact Explanation
An intent submitter (fully unprivileged — anyone can submit an order to the `IntentGateway`) can craft or time an order against a thinly liquid Uniswap V4 exotic/stable pool whose spot price has been pushed away from fair value (large swap, flash-loan-funded swap, or simply low native liquidity). If the operator has left the price guard unconfigured (an explicitly supported, documented configuration) or has set a wide band, `FXFiller` will quote and fill using the manipulated spot price extended linearly over the full order notional, and the disabled overfill clamp means the fill is not capped even when the unclamped output far exceeds the user-requested amount. The result is direct loss of the solver's on-chain liquidity (Uniswap V4 LP positions and/or wallet balance) to the attacker, i.e. theft of funds via price manipulation — matching the reported incident's impact and severity class.

### Likelihood Explanation
The `checkPriceGuard` protection is opt-in per chain/position (`referencePrice`/`maxDeviationBps` are optional fields), and the docs describe running with venue pricing and no curves as a normal supported mode ("Pool-Based Pricing... you can omit bidPriceCurve and askPriceCurve"). Any operator running an unguarded or loosely-guarded venue-priced pair against a pool with moderate-to-thin liquidity is directly exposed, and the attack requires only a standard swap/flash-loan plus a normal intent submission — no privileged access, no protocol bug beyond the pricing design itself.

### Recommendation
- Make the price guard mandatory (not optional) whenever venue pricing is used, or fail closed by default.
- Replace/augment the instantaneous `sqrtPriceX96` read with a time-weighted average price (TWAP) over multiple blocks for venue pricing.
- Incorporate the pool's actual depth/impact cost of the priced notional (rather than linearly extending the mid) into `computeLegPolicyOutput`, and consider the position's fee tier.
- Re-enable (or make configurable and default-on) the overfill clamp specifically for venue-priced legs, since the code comments confirm it was previously the safety net against exactly this "manipulated venue price" scenario.

### Proof of Concept
1. Operator configures `[vault.uniswapV4]` for an exotic/stable pair with no `referencePrice`/`maxDeviationBps` (a documented, valid configuration) or with a wide band.
2. Attacker performs a large swap (optionally flash-loan funded) against the thin Uniswap V4 pool backing that position to move `sqrtPriceX96` far from fair value.
3. Attacker submits an intent order sized to consume the manipulated rate; `FXFiller.resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` returns the skewed spot price.
4. `checkPriceGuard` passes (unconfigured or within a wide static band); `computeLegPolicyOutput` extends the skewed mid linearly over the full notional; the disabled overfill clamp lets the fill proceed unclamped (`fx.ts:678-701`).
5. Solver's `UniswapV4FundingPlanner.planWithdrawalForToken` withdraws LP liquidity to fund the inflated output, transferring it to the attacker; attacker reverses the initial swap, keeping the arbitrage profit extracted from the solver's liquidity.

```typescript
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
```

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
