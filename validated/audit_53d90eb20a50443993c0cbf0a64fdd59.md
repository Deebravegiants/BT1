### Title
Webhook shop/topic identity is not covered by HMAC verification, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are taken from unauthenticated HTTP headers that are never included in the signature. This breaks the identity binding: `shop_header == tenant_dispatched_to` is assumed but never enforced by the cryptographic check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC of the body, then dispatches the handler using the unverified `request.shop`, `request.topic`, etc.: [3](#0-2) 

`Utils::HmacValidator.validate` simply HMACs `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

The identity binding that should hold is:
`HMAC_valid(body, secret) ⇒ shop_header == shop_that_actually_triggered(body)`

But since `shop`/`topic`/`webhook_id` never enter the signed content, the true relationship is only:
`HMAC_valid(body, secret) ⇒ body_was_produced_by_some_install_of_this_app`

Any party who has legitimately installed the target app on their own shop (a normal, unprivileged action available to any internet user for public apps) receives real, correctly-HMAC-signed webhook deliveries for their own shop whose body content they can substantially influence (e.g., product titles/descriptions/metafields, order details, or any field ultimately serialized into the webhook JSON body). Because `Registry.process` is a public HTTP endpoint exposed by the host application and the shop/topic headers aren't bound to the signature, the attacker can replay that captured `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain or a more sensitive topic than what was actually signed.

### Impact Explanation
This crosses a tenant boundary: the app's webhook handler executes attacker-influenced data under the identity of an arbitrary victim shop (`data.shop`), because the HMAC only proves "some legitimate installation produced this exact body," not "this body legitimately corresponds to this specific shop/topic." Depending on how the host application's `WebhookHandler` implementations use `shop`/`topic` (e.g., updating stored records keyed by shop, triggering side effects like data sync, uninstall cleanup, or billing), this enables cross-tenant data corruption/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that exposes a webhook endpoint (which is required to use this feature at all): the attacker only needs to be able to install the target app on a shop they control (a normal unprivileged flow for public apps) to obtain at least one valid `(body, hmac)` pair, and then send a direct HTTP POST to the app's public webhook URL with modified headers — no access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the body) in the value that is HMAC-verified, or otherwise cryptographically/contextually bind the header-derived tenant identity to the signed payload before dispatching to handlers (e.g., cross-check `shop` against an expected/registered shop for the given `topic`/subscription, and reject mismatches). At minimum, document and mitigate the replay risk by requiring additional verification (e.g., delivery UUID de-duplication is not sufficient by itself since `webhook_id` is also unauthenticated).

### Proof of Concept
1. Attacker installs the target Shopify app on their own controlled shop `attacker.myshopify.com`.
2. Attacker triggers a webhook topic they can influence the body of (e.g., renames a product to embed the desired JSON-like content, triggering `products/update`), receiving from Shopify a POST to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` for that exact `raw_body`.
3. Attacker captures `(raw_body, hmac)` and replays it directly to the same public endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes (only `raw_body` is checked), then invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, i.e. the app processes attacker-controlled data as if it came from the victim's shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
