### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then blindly trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers to build the `WebhookMetadata` passed to the app's handler. None of those headers are covered by the HMAC signature, so any party who can obtain one genuine `(body, hmac)` pair signed with the app's secret (e.g. a merchant who has installed the app on their own shop and captured/replayed a webhook Shopify sent them) can re-send that same body/HMAC pair while forging the `shop-domain` and `topic` headers to any value. The gem will accept it as authentic and hand the attacker-chosen `shop`/`topic` to the host app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over this signable string: [2](#0-1) 

Yet `Registry.process` uses `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` — all read directly from unauthenticated headers via `shopify_header` — to build the `WebhookMetadata` delivered to the handler, right after confirming only that the body's HMAC is valid: [3](#0-2) [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop header == shop that produced this body` (and similarly for `topic`). Because the HMAC only certifies "this body was produced by an entity holding `api_secret_key`," not "this body belongs to shop X" or "this body is for topic Y," the equality `authenticated(body) == claimed(shop, topic)` is never checked. Any holder of one valid `(body, hmac)` pair — trivially obtainable by any merchant who installs the app on their own store and captures the webhook Shopify sends them — can resend that exact pair with a different `shop-domain`/`topic`/`webhook-id` header set. `HmacValidator.validate` will still return `true` because it only re-derives the HMAC from `@raw_body`, and `Registry.process` will dispatch the (attacker-controlled) body to the handler tagged with the forged `shop`/`topic`.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: the host app's `WebhookHandler#handle` implementations rely on `WebhookMetadata#shop` to know which merchant's data/session the payload belongs to. An attacker (merely a user who can install the app on their own store, i.e. an unprivileged actor) can:
- Replay a genuine webhook body from their own shop while spoofing `shop-domain` to a victim shop, causing the app to process attacker-influenced data (order/customer fields the attacker fully controls in their own store) under the victim's identity — cross-tenant data injection.
- Spoof the `topic` header to redirect a captured body into a different handler than the one Shopify originally intended (e.g. turning a low-sensitivity event body into a trigger for a `shop/redact` or `app/uninstalled` handler), potentially causing destructive actions (session/data deletion) against an arbitrary shop known to the attacker.

This matches "cross-tenant access" under the Critical impact bucket, since the confused-deputy is entirely within this gem's `Registry.process`/`Request` handling — no access token, `api_secret_key`, or victim credential is needed by the attacker.

### Likelihood Explanation
Likelihood is real but requires the attacker to have installed the app somewhere (any developer/merchant can do this for free/dev-store apps) and to know or guess a target shop's domain, both of which are low-cost for an unprivileged internet user. No secrets are required from the victim or the app operator.

### Recommendation
Include `topic`, `shop-domain`, and `webhook-id` (and any other header the handler trusts) inside the HMAC-signed payload validation, or otherwise cryptographically bind them to the body — e.g. by validating that the signed body's shape/checksum is consistent with the claimed topic/shop server-side against Shopify's known event catalog, or by having `Request#to_signable_string` incorporate the headers so `HmacValidator` can detect tampering with them. At minimum, document and enforce that consumers must independently verify `request.shop` against an app-known/allow-listed set of installed shops before trusting the payload, since the current API surface (`Registry.process`) presents `WebhookMetadata` as if it were fully authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real Shopify webhook (e.g. `orders/create`) whose body fields (customer name/email, line-item titles) are fully attacker-controlled content.
2. Attacker captures the resulting HTTP request, including the genuine `x-shopify-hmac-sha256` header computed by Shopify over that body with the app's real `api_secret_key`.
3. Attacker resends the identical raw body and `hmac-sha256` header to the app's webhook endpoint, but changes:
   - `x-shopify-shop-domain` to `victim-shop.myshopify.com`
   - `x-shopify-topic` to a topic the app has registered a sensitive handler for.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes HMAC over `@raw_body`: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic: "victim-chosen-topic", shop: "victim-shop.myshopify.com", body: <attacker-controlled data>, ...)`, causing the app to act on forged tenant/topic identity.
