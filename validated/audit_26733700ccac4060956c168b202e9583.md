### Title
Webhook shop/topic/webhook-id headers are trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` entirely from HTTP headers, while `Utils::HmacValidator` only authenticates the raw request body against those headers' claims. Because the signable string is just the body, the HMAC never binds the `shop`, `topic`, or `webhook_id` values to the signed payload, letting an attacker who possesses one legitimately-signed body/HMAC pair from their own store replay it with forged tenant-identifying headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `HmacValidator.validate` computes/compares the signature purely against that signable string: [2](#0-1) 

`Registry.process` accepts the request purely based on this body-only HMAC check, then trusts the header-derived `shop`, `topic`, and `webhook_id` to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The test suite confirms the HMAC is computed strictly from the body, independent of the header values: [4](#0-3) 

This breaks the identity binding: `shop authenticated (proven by valid Shopify HMAC) ≠ shop stored/acted upon (arbitrary header value)`. Since a merchant can install the app on their own shop and receive genuinely Shopify-signed webhooks (body + `X-Shopify-Hmac-Sha256`) for events they control (e.g. `orders/create`), that same attacker can resend the identical body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header to point at a victim shop. `Utils::HmacValidator.validate` still returns `true` because it never inspected those headers, and `Registry.process` will hand the attacker-supplied body to the handler tagged as belonging to the victim shop/topic.

### Impact Explanation
This is a cross-tenant data-integrity/confidentiality violation: an unprivileged attacker (any merchant who can install the app) can inject a Shopify-authenticated-looking webhook payload attributed to a shop they do not own, causing the host application to process/store attacker-controlled data under another tenant's identity. This matches the "cross-tenant access" Critical impact category, since no access token, `client_secret`, or privileged credential is required — only possession of one legitimately delivered webhook for the attacker's own store.

### Likelihood Explanation
Low-to-moderate likelihood: it requires the attacker to install the app (or otherwise trigger/receive a webhook) on their own shop, capture the raw body and its HMAC (both directly observable to the receiving endpoint owner or via network capture at their own infrastructure), and replay the request with modified headers to the app's public webhook endpoint. No secret material or victim credentials are needed.

### Recommendation
Bind the tenant/topic identity cryptographically to the signed payload rather than trusting mutable HTTP headers:
- Fold `shop`, `topic`, and `webhook_id` into the value covered by `to_signable_string` (matching Shopify's actual HMAC computation contract), or
- Cross-check the `shop` header against an independently verified source (e.g., a shop already known/registered for that webhook subscription) before dispatching to handlers, and reject requests where the header-derived tenant cannot be corroborated.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger an `orders/create` webhook and capture the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because Shopify signed `B` with the app's real secret).
2. Replay the request to the app's webhook endpoint, keeping `B` and `H` unchanged, but set:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: orders/create`
3. `Request#hmac` and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:11-38`) yield the same values as the legitimate call, so `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata` claiming `shop: "victim.myshopify.com"`, even though the payload actually originated from and was signed for the attacker's own shop.
