### Title
Session ID for non-embedded apps is derived from an unsigned, attacker-controllable cookie value, enabling cross-tenant session retrieval - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` — the library's documented mechanism for non-embedded apps to identify "the current session" — returns the raw, unauthenticated value of the `shopify_app_session` cookie verbatim, with no cryptographic binding (no HMAC, no signature) tying that value to the actual authenticated shop/user who set it.

### Finding Description
The external report's bug class is: a value is trusted and acted upon (an identity/target) without verifying it is bound to what it claims to represent, causing the trusting party to act on attacker-supplied data. The closest in-scope analog is a session identifier that is derived from unauthenticated bytes.

`ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the non-embedded session cookie's value directly to the predictable session `id`: [1](#0-0) 

For offline sessions this ID is simply `"offline_#{shop}"` — a value fully derivable from public information (the shop domain) — as seen in `Session.from`: [2](#0-1) 

`ShopifyAPI::Auth::Oauth::SessionCookie` is a plain value/expiry struct with no signature or MAC field at all: [3](#0-2) 

When retrieving "the current session," `SessionUtils.current_session_id` — for non-embedded apps, and as a fallback for embedded apps without a JWT — reads this cookie value and returns it unmodified as the session identifier, without any verification that the value was actually produced by this library's OAuth flow for the requesting party: [4](#0-3) [5](#0-4) 

The library's own documentation instructs host applications to use exactly this pattern — pass raw request cookies into `current_session_id` to obtain the identifier used to look up the persisted session/access token: [6](#0-5) 

The equality that should hold is: `session_id_returned == session_id_that_the_requesting_browser_was_legitimately_issued_for_its_own_shop`. Because the cookie is unsigned and the offline session ID is a deterministic function of the public shop domain, an attacker can set `shopify_app_session=offline_<victim-shop>.myshopify.com` in their own browser/HTTP client and have `current_session_id` return that exact string — breaking the binding between "bytes verified" and "bytes actually authenticated."

### Impact Explanation
If the host application follows the library's documented pattern (i.e., uses the returned session ID as the key to retrieve a persisted `Session`/access token, as shown throughout `docs/usage/oauth.md`), an attacker can supply a forged/guessed cookie value to make the library return another shop's offline session ID. Any subsequent lookup keyed on that ID will fetch the wrong (victim) shop's stored access token, resulting in cross-tenant access to another merchant's data — a Critical-impact outcome under the given rubric. This is not merely a host-app failure to validate a documented API's output; the vulnerable trust decision (treating an unsigned client-supplied byte string as an authoritative session identifier) is made entirely inside this gem's `SessionUtils.cookie_session_id`/`current_session_id`.

### Likelihood Explanation
The offline session ID format (`"offline_#{shop}"`) is fully deterministic and requires no secret knowledge — only the target shop's domain, which is public. No cryptographic material, access token, or privileged access is needed to construct the forged cookie value; only the ability to set an arbitrary cookie/header value on one's own request, which is available to any unprivileged internet user interacting with a non-embedded app built on this library exactly as documented.

### Recommendation
Do not store or trust a bare, predictable session ID in the cookie. Either:
1. Sign/MAC the cookie value (e.g., HMAC with `Context.api_secret_key`) and verify the MAC in `cookie_session_id`/`current_session_id` before returning it, or
2. Store a high-entropy, unguessable, server-generated token in the cookie that is opaque and unrelated to the deterministic session ID, mapping it server-side to the actual session, or
3. At minimum, document explicitly and enforce in code that the cookie-derived ID must never be used directly as an authorization/session lookup key without an additional authenticated binding step.

### Proof of Concept
1. Attacker knows (or enumerates) a victim shop's domain, e.g. `victim-shop.myshopify.com`.
2. Attacker computes the deterministic offline session ID: `"offline_victim-shop.myshopify.com"` (per `Session.from` / `SessionUtils.offline_session_id`).
3. Attacker sends a request to the vulnerable (non-embedded) app with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unmodified — exactly as demonstrated by the test asserting the cookie value is returned verbatim: [7](#0-6) 
5. If the app's session storage (per the library's documented pattern) retrieves the persisted `Session`/access token using this ID, the attacker receives responses acted upon with the victim shop's access token — cross-tenant access.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
    end
  end
end

        def current_session_id(shopify_id_token, cookies, online)
          if Context.embedded?
            if shopify_id_token
              id_token = shopify_id_token.gsub("Bearer ", "")
              session_id_from_shopify_id_token(id_token: id_token, online: online)
            else
              # falling back to session cookie
              raise Errors::CookieNotFoundError, "JWT token or Session cookie not found for app" unless
                cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

              cookie_session_id(cookies)
            end
          else
            raise Errors::CookieNotFoundError, "Session cookie not found for app" unless
              cookies && cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]

            cookie_session_id(cookies)
          end
        end

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
