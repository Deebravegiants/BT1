## Finding

### Title
Webhook shop domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the shop identity (`shopify-shop-domain` header) is read separately and passed to the app's webhook handler unverified. Any party who can obtain one valid `(body, HMAC)` pair for the shared app secret — including the operator of their own installed shop, who legitimately receives such pairs from Shopify — can replay that pair while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Registry.process` accepts it because HMAC validation never touches the shop field, and forwards the attacker-chosen shop identity to the host app as trusted data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The shop domain is read from a separate, unsigned header: [2](#0-1) 

`Registry.process` validates the HMAC (which only binds the body) and then unconditionally trusts `request.shop` when constructing the object handed to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain, trusted `String` field with no further validation performed by the gem: [4](#0-3) 

The gem's own documentation instructs host apps to key business logic directly off `data.shop` as if it were an authenticated tenant identifier: [5](#0-4) 

The broken binding is: **`shop` used to identify the tenant in `WebhookMetadata` ≠ `shop` covered by the HMAC signature.** Because the app's `client_secret`/`api_secret_key` is shared across all shops installed on the app, anyone operating their own legitimately-installed shop receives genuine `(raw_body, X-Shopify-Hmac-Sha256)` pairs from Shopify. That attacker can resend the exact same body and HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop's domain. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `to_signable_string` (body only) and it matches, so validation succeeds, and the forged shop value flows straight into the handler.

### Impact Explanation
This crosses a tenant boundary: an attacker with their own valid installation can make the host application process webhook data under a different merchant's shop identity. Depending on how the host app consumes `data.shop` (e.g., looking up per-shop sessions/tokens, writing data keyed by shop, or triggering compliance actions like `shop/redact`/`customers/redact` for the wrong tenant), this enables cross-tenant data confusion/corruption — a Critical-class cross-tenant access issue per the scope's impact categories.

### Likelihood Explanation
Exploitation only requires the attacker to control one shop that has installed the app (a normal, unprivileged capability for any developer/merchant) and to be able to POST directly to the app's public webhook endpoint with custom headers — no access token, `api_secret_key`, or privileged account is required. The gem performs no cross-check between the signed body and the shop header, so likelihood is high for any app that trusts `WebhookMetadata#shop` as documented.

### Recommendation
Bind the shop domain into the signed payload verification path, e.g., include the `shop`, `topic`, and `webhook_id` headers as part of the string that is HMAC-verified (or, at minimum, require host apps to cross-check `data.shop` against a known/registered shop list before trusting it), rather than only signing the raw body while treating the shop header as implicitly trusted metadata.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays the request to the app's webhook endpoint unchanged except for the shop header:
   ```
   POST /callback/orders/create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Webhook-Id: <any>
   X-Shopify-Api-Version: 2024-01

   B
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only (`Request#to_signable_string`) and matches `H`, so validation passes.
4. `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)` is passed to the app's handler, which processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
