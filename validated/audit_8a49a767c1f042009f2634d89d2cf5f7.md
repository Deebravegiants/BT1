### Title
Improper decimal scaling in `pallet-hyper-fungible-token`'s `convert_to_erc20`/`convert_to_balance` when remote decimals are lower than local decimals - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token` converts amounts between the local asset's decimal precision and the remote (EVM) chain's decimal precision using `value * 10^(erc_decimals.saturating_sub(local_decimals))` on send and `value / 10^(erc_decimals.saturating_sub(local_decimals))` on receive. `saturating_sub` silently clamps to `0` whenever `erc_decimals < local_decimals`, so the required scale factor is dropped instead of applied in the opposite direction, exactly the "improper token scaling for tokens of differing precision" bug class from the referenced report.

### Finding Description
The conversion helpers are: [1](#0-0) 

`convert_to_erc20` (used in `send`, local → remote) computes `10^(erc_decimals.saturating_sub(local_decimals))`. This is correct only when `erc_decimals >= local_decimals` (scale up). When the remote chain's registered decimals are *lower* than the local asset's decimals, `saturating_sub` returns `0`, so the multiplier becomes `10^0 = 1` and the raw local-precision value is forwarded unchanged instead of being divided down by `10^(local_decimals - erc_decimals)`. [2](#0-1) 

This unscaled value is placed directly into the abi-encoded `Message.amount` field dispatched to the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract via `DispatchPost`.

Symmetrically, `convert_to_balance` (used in `on_accept`/`on_timeout`, remote → local) divides by `10^(erc_decimals.saturating_sub(local_decimals))`, which likewise degrades to a no-op divide (`/1`) instead of the required multiply-up when `erc_decimals < local_decimals`: [3](#0-2) [4](#0-3) 

Both `TokenContracts`/`Precisions` are populated per `(AssetId, StateMachine)` pair via governance-controlled `register_token`/`update_token`, and `decimals` on the EVM side is configured independently per contract per the docs: [5](#0-4) 

Per the pallet's own README, `Precisions` exists specifically to handle differing decimals across chains, confirming this is intended, reachable functionality rather than an edge case nobody exercises: [6](#0-5) 

Any asset registered with a lower-decimal representation on one side of the bridge (e.g. a local 18-decimal asset paired with a 6-decimal ERC20 destination token, which is a realistic and expected configuration per the pallet's own decimals-handling design) triggers the bug on every `send` and `on_accept`/`on_timeout` call for that asset/chain pair.

### Impact Explanation
- **`send` (local → remote, erc_decimals < local_decimals):** the amount forwarded to the destination contract is not scaled down, so it is `10^(local_decimals - erc_decimals)` times larger than intended. If the destination `HyperFungibleToken` mints/releases directly against the message amount (as its escrow/mint model implies), the recipient receives a vastly inflated, unbacked amount relative to what was escrowed/burned on the source chain — an unbacked mint / minting-more-than-backed-value bug enabling direct value extraction by any user who can trigger a `send` for such an asset pair.
- **`on_accept`/`on_timeout` (remote → local, erc_decimals < local_decimals):** the amount credited locally is not scaled up, permanently under-crediting (freezing/losing) the difference in value for legitimate users receiving or being refunded tokens.

Either direction breaks the fundamental "value is conserved across the bridge" invariant for any token pair where the destination's registered decimals are lower than the local asset's decimals — this is a Medium/High severity token-scaling defect matching the reachable "token bridge mint/burn" attack surface.

### Likelihood Explanation
This is triggered automatically by ordinary users calling the public `send` extrinsic (and the corresponding `on_accept`/`on_timeout` handling of any inbound message) for any asset registered with `erc_decimals < local_decimals` on a given `(AssetId, StateMachine)` pair. No privileged or malicious actor is required beyond normal governance registering such an asset pair, which the pallet's design (arbitrary per-chain `Precisions`/`decimals`) explicitly anticipates as a supported configuration.

### Recommendation
Replace the one-directional `saturating_sub` scaling in `convert_to_erc20` and `convert_to_balance` with a signed/bidirectional scale calculation: multiply when `erc_decimals > local_decimals`, divide when `erc_decimals < local_decimals`, and no-op only when equal. E.g.:
```rust
if erc_decimals >= local_decimals {
    value * 10^(erc_decimals - local_decimals)   // convert_to_erc20 scale-up case
} else {
    value / 10^(local_decimals - erc_decimals)   // convert_to_erc20 scale-down case
}
```
and the mirrored logic for `convert_to_balance`. Add regression tests covering `erc_decimals < local_decimals`, `erc_decimals == local_decimals`, and `erc_decimals > local_decimals` for both `send` and `on_accept`/`on_timeout` paths.

### Proof of Concept
1. Governance registers asset `X` via `register_token`/`create_erc6160_asset` with `local_decimals = 18` on the substrate chain and a `ChainConfig`/`Precisions` entry declaring `decimals = 6` for a given destination EVM chain (a supported, documented configuration).
2. A user calls `send(params)` with `params.amount = 1 * 10^18` (i.e., 1 token in local 18-decimal units).
3. In `send`, `erc_decimals = 6`, `decimals (local) = 18`; `convert_to_erc20(1e18, 6, 18)` computes `10u128.pow(6u8.saturating_sub(18u8) as u32) = 10u128.pow(0) = 1`, so `erc20_amount = 1e18` unchanged, instead of the correct `1e18 / 10^12 = 1e6` (1 token at 6 decimals).
4. The dispatched `Message.amount` (`1e18`) is delivered to the destination contract, which mints/releases `1e18` raw units of a 6-decimal token — i.e., `10^12` real tokens instead of `1`, while only `1` token's worth was escrowed/burned on the source chain.

pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
