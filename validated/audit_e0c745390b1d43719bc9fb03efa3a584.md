### Title
Webhook shop identity is trusted from an unauthenticated header not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` header, but `Utils::HmacValidator` only ever authenticates the raw request body via `to_signable_string`. `Registry.process` validates the HMAC and then immediately forwards the unauthenticated `shop` value to the app's `WebhookHandler` inside `WebhookMetadata`, giving the host app the false assurance that everything in the successfully-processed request — including the shop identity — is trustworthy.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the HMAC or any known/registered shop: [3](#0-2) 

`Registry.process` validates the HMAC, then unconditionally trusts `request.shop` and passes it into `WebhookMetadata`, which is delivered to the app's handler as the authoritative tenant identity: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no additional binding or verification: [5](#0-4) 

This is exactly the analog bug class described in the report: a field acted on (`shop`, used for tenant identification/dispatch) is not covered by the identity-binding mechanism (the HMAC). The binding that should hold is:

`HMAC(secret, raw_body) == received_hmac` **AND** `shop == the tenant that actually produced raw_body`

but the library only verifies the first clause. `shop` is bytes parsed from an attacker-controllable header, never bytes verified by the HMAC.

### Impact Explanation
An unprivileged attacker who controls their own Shopify store (a legitimate, unprivileged merchant account) can receive genuinely-signed webhooks from Shopify for their own shop (e.g., `orders/create` with an empty or attacker-shaped body). Because the HMAC signs only the body — not the shop header — the attacker can replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim merchant's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` forwards `shop: <victim-domain>` to the app's handler as if Shopify itself asserted it. Any handler logic that uses `data.shop` to look up sessions, scope database writes, or perform per-tenant actions (a common and expected usage pattern per this gem's documented `WebhookHandler` interface) can be tricked into acting on/associating data with the wrong tenant — a cross-tenant confusion condition reachable purely through this gem's own validation primitive, not by the host app ignoring documented API guidance (the gem's `process` method itself is the boundary that gives this false assurance).

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs a validly-signed webhook body to replay, which they can only obtain by triggering webhook events on their own store (something any merchant/developer testing an app can do trivially), and the practical impact depends on whether the replayed body content is compatible with actions the handler takes for the spoofed shop (e.g., a body-independent action such as a `shop/redact` or `customers/data_request` mandatory webhook, or any handler that only reads `data.shop` and ignores `data.body`). No secret key or privileged access is required.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise force the caller/handler to independently verify `request.shop` against a known/registered shop for the session before trusting it. Concretely:
- Have `Registry.process` (or `Request`) require and verify that `request.shop` corresponds to a shop the app has an active session/installation for, rejecting requests for unknown or unexpected shops before invoking the handler.
- Alternatively, extend `to_signable_string`/HMAC scope (where feasible) or explicitly document and enforce that `WebhookMetadata.shop` is untrusted until independently corroborated, and provide a built-in lookup/verification helper rather than delivering it as if already authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook, e.g. `orders/create`, capturing the raw POST body `B` and its valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` with the app's real secret).
2. Attacker replays the exact same request to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H`, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and compares to `H` — this matches, since the shop header is never part of the signed input, see [1](#0-0)  and [6](#0-5) .
   - `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, see [7](#0-6) .
4. The app's handler, trusting `data.shop` as asserted by Shopify (since the request "passed HMAC validation"), performs a tenant-scoped action against `victim-shop.myshopify.com`'s data/session — a cross-tenant action triggered entirely by an unprivileged attacker replaying their own signed webhook with a forged shop header.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
