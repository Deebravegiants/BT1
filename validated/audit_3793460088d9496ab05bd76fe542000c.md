### Title
Intra-batch conflicting account locks succeed due to check-then-lock split in `AccountLocks::try_lock_transaction_batch` - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` validates every transaction in a batch against the lock table in a first pass, then applies all the locks in a second pass, instead of checking-and-locking each transaction atomically in sequence. Because the validation pass never mutates `self`, two transactions in the *same* batch with conflicting declarations on the same key (one readonly, one writable) are both validated against the identical pre-batch lock state and can both be marked `Ok`, after which the apply pass unconditionally increments both the `readonly_locks` and `write_locks` counters for that key.

### Finding Description
`AccountLocks::try_lock_transaction_batch` is implemented as two sequential passes over `validated_batch_keys`: [1](#0-0) 

The first pass calls `self.can_lock_accounts(keys.clone())` for every transaction's key iterator, but `can_lock_accounts` only reads `self` — it never calls `lock_write`/`lock_readonly`: [2](#0-1) 

Only the second pass actually mutates the lock table via `lock_accounts` → `lock_write`/`lock_readonly`, which are unconditional counter increments with no conflict re-check: [3](#0-2) 

Consequence: consider a batch `[tx_A, tx_B]` where `tx_A` declares key `K` readonly and `tx_B` (later in the same batch) declares `K` writable, and `K` is otherwise unlocked. During the validation pass:
- Checking `tx_A`: `can_read_lock(K)` → true (nothing locked yet) → `tx_A` stays `Ok`.
- Checking `tx_B`: `self` is still unmodified (no lock has been applied for `tx_A` yet, since locking is deferred to the second pass) → `can_write_lock(K)` → true → `tx_B` stays `Ok`.

Both transactions pass validation against the *same stale snapshot* of the lock table. The apply pass then locks `tx_A` readonly and `tx_B` writable on `K` unconditionally, leaving both `readonly_locks[K] > 0` and `write_locks[K] > 0` simultaneously — a state `can_read_lock`/`can_write_lock` are supposed to make impossible. Since account-lock success is precisely what the scheduler/replay stage uses to decide two transactions may execute concurrently within a batch, this breaks the "only writable/unlocked accounts may be mutated while readers observe a stable view" invariant: `tx_B` can mutate `K` while `tx_A` executes assuming a read-only, unmutated `K`.

This is reachable by any unprivileged sender: submitting two ordinary transactions in the same slot/batch that reference a shared account `K`, one declaring it read-only and one declaring it writable, is a completely normal, unprivileged transaction pattern (no special writable-declaration bypass, no forged signatures, no leader control needed) — the bug is triggered purely by the batch composition that `AccountLocks` itself is supposed to validate.

### Impact Explanation
This is a violation of the "only accounts declared writable and unlocked by the message may be mutated" invariant enforced at the account-locking layer, which is what allows the runtime to execute a batch of transactions in parallel. If exploited, a writer and a reader of the same account can run concurrently under the false belief that their access is exclusive/consistent, causing corrupted/undefined account state, non-deterministic execution results depending on scheduling, and potential value corruption for the affected account. This falls under the "account lock/invariant violation leading to memory/state corruption" bounty category.

### Likelihood Explanation
Precondition is simply that two ordinary transactions submitted by any user land in the same lock-batch call with conflicting (readonly vs. writable) declarations on a common account — an entirely ordinary and easily engineered scenario for any client broadcasting transactions to a public RPC/TPU. No elevated privileges, special account state, or timing races across threads are required; the bug is deterministic given the input ordering of `validated_batch_keys` within a single `try_lock_transaction_batch` call.

### Recommendation
Merge the validate-and-lock steps into a single per-transaction pass so that each transaction's lock request is checked against the up-to-date lock state (including locks already taken by earlier transactions in the same batch) immediately before it is applied, e.g.:
```rust
validated_batch_keys
    .into_iter()
    .map(|keys| keys.and_then(|keys| {
        self.can_lock_accounts(keys.clone())?;
        self.lock_accounts(keys);
        Ok(())
    }))
    .collect()
```
This restores the check-then-lock atomicity per transaction and prevents later transactions in the batch from being validated against a stale snapshot.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (add to `mod tests`)
#[test]
fn test_intra_batch_conflicting_locks_should_not_both_succeed() {
    let key = Pubkey::new_unique();
    let mut locks = AccountLocks::default();

    // tx_A: readonly on `key`; tx_B: writable on `key`, same batch.
    let batch: Vec<TransactionResult<std::vec::IntoIter<(&Pubkey, bool)>>> = vec![
        Ok(vec![(&key, false)].into_iter()), // tx_A readonly
        Ok(vec![(&key, true)].into_iter()),  // tx_B writable
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // Invariant: a readonly lock and a writable lock on the same key
    // must never both succeed within the same batch call.
    let both_succeeded = results[0].is_ok() && results[1].is_ok();
    assert!(
        !both_succeeded,
        "conflicting readonly/writable locks on the same key both succeeded in one batch"
    );
}
```
Expected (buggy) behavior: the assertion fails — both `results[0]` and `results[1]` are `Ok(())`, and internally `is_locked_readonly(&key)` and `is_locked_write(&key)` are simultaneously `true`, demonstrating the invariant violation.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_readonly(&self, key: &Pubkey) -> bool {
        self.readonly_locks.get(key).is_some_and(|count| *count > 0)
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

    fn lock_readonly(&mut self, key: &Pubkey) {
        *self.readonly_locks.entry(*key).or_default() += 1;
    }

    fn lock_write(&mut self, key: &Pubkey) {
        *self.write_locks.entry(*key).or_default() += 1;
    }
