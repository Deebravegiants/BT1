### Title
Webhook `shop` identity is trusted from an unauthenticated header while only the raw body is HMAC-covered - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` (and `topic`, `webhook_id`, `api_version`) purely from HTTP headers, while its `to_signable_string` used for HMAC verification returns only `@raw_body`. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` taken straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, handing that value to the host application's handler as the authoritative tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the HMAC check exclusively to the raw request body: [1](#0-0) [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight off caller-controlled HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC of the body and then forwards `request.shop` unchanged to the app's handler as the tenant identity for the payload: [4](#0-3) [5](#0-4) 

The equality the gem implicitly claims to guarantee is: `shop header value == shop that produced/authenticated this webhook payload`. In reality the gem only proves `HMAC(raw_body, api_secret_key) == received_hmac`; it proves nothing about which shop domain the body belongs to. Because `api_secret_key` is shared across every shop that installs a given app, any two webhooks (for the same topic, from any two shops using the app) are validated with the exact same secret. An attacker who can observe or replay one authentic webhook body+HMAC pair for the app (e.g. from their own test/dev store, or a leaked/log-captured delivery) can resend that identical body+HMAC with an arbitrary `shopify-shop-domain` header value substituted, and `Registry.process` will accept it as valid and pass the attacker-chosen `shop` value into `WebhookMetadata`, since nothing re-derives or checks `shop` against data covered by the signature.

The gem's own documentation states processing "will verify the request did indeed come from Shopify," implying the full request (including which shop it is for) is authenticated: [6](#0-5) 
but the implementation only authenticates the body bytes, not the shop binding, so host applications that trust `data.shop` (as the documented usage example explicitly does) to key their per-tenant session/token lookup are exposed to cross-tenant payload injection.

### Impact Explanation
This breaks the tenant identity binding the host application relies on `shopify_api` to establish. A host app that keys per-shop actions/lookups off `WebhookMetadata#shop` (exactly as the gem's own documentation example does — `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) can be made to process/apply data intended for shop A under the identity of shop B, since `shop` is not covered by the HMAC. This is a cross-tenant confusion at the trust boundary the gem is responsible for (webhook shop attribution), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires the attacker to already possess one valid `(raw_body, hmac)` pair for the target app (e.g., by having their own store install the app and capturing a webhook delivery, which is trivial for any developer/attacker who can install the app on their own store, or by intercepting a delivery through logging/proxying infrastructure). Given that, forging the `shop` header is a single unauthenticated HTTP header change requiring no additional secret — moderate likelihood, gated only by obtaining one legitimate delivery.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified before it is trusted downstream: either (a) validate that the header's shop domain matches a shop identifier embedded in the JSON body itself (most Shopify webhook payloads include shop-scoped IDs), or (b) require host applications to cross-check `WebhookMetadata#shop` against their own record of shops that have registered for that specific `webhook_id`, and document explicitly that `shop`/`topic`/`webhook_id`/`api_version` are NOT covered by the HMAC and must not be trusted as authenticated on their own.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` (attacker's own store) and `victim-shop.myshopify.com` (real merchant), both using the same `api_secret_key`.
2. Attacker triggers a webhook on their own store (e.g. `orders/create`) and captures the raw POST body and `X-Shopify-Hmac-Sha256` header — this HMAC is valid because it's computed with the shared `api_secret_key`, independent of shop.
3. Attacker replays the exact same body/HMAC to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any `X-Shopify-Webhook-Id`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `to_signable_string`, i.e., raw body) — see: [7](#0-6) 
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and invokes the host's handler, which believes the (attacker-controlled) body legitimately belongs to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
