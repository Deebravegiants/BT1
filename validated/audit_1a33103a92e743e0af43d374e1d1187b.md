## Finding

### Title
Missing zero-address validation in `set_beneficiary_for_operator` permanently locks delegation-pool commission shares - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
`delegation_pool::set_beneficiary_for_operator` lets an operator redirect their stake-pool commission to any `address`, including `@0x0`, with no validation. `synchronize_delegation_pool` subsequently buys pool_u64 shares for that beneficiary address directly out of the commission cut, on every epoch synchronization. If the beneficiary is the zero address, those shares are permanently bound to a shareholder key (`0x0`) that no signer can ever represent, so the coins backing them can never be withdrawn from the resource-account-controlled stake pool — an irreversible loss of custody, closely mirroring the Celo `setPaymentDelegation` zero-beneficiary bug where reward distribution silently failed to reach any recoverable party.

### Finding Description
`set_beneficiary_for_operator` stores `new_beneficiary` unconditionally: [1](#0-0) 

Every call to `synchronize_delegation_pool` computes the commission owed to the operator and buys shares for whatever address `beneficiary_for_operator(operator)` currently resolves to, with no check that the resolved address is non-zero or capable of holding recoverable value: [2](#0-1) 

The shares are recorded in the `pool_u64` active/pending-inactive share pools keyed by shareholder address. Withdrawal of any shares in this design requires a real `&signer` whose address matches the shareholder key (see `delegation_pool::withdraw`/`unlock` style entry points, which take `delegator: &signer` and derive the address from it). `@0x0` (`vm_reserved`) has no corresponding private key/signer capability that any account holder can produce, so shares credited to it can never be redeemed through the normal delegator-facing API — the backing APT remains physically inside the delegation pool's stake-pool resource account but is permanently unclaimable.

This differs from the analogous `staking_contract::distribute_internal` path, which uses `aptos_account::deposit_coins` (a direct coin deposit) and would instead abort at the point of depositing to a non-existent/invalid `0x0` account — reproducing the Celo failure mode of reverting the whole payout. The `delegation_pool` module avoids that revert by using an internal share-accounting model, but this "fix" trades a recoverable revert for a *silent, non-recoverable* loss: the commission shares are minted successfully, the transaction succeeds, and the value is gone for good.

### Impact Explanation
This breaks the core custody invariant that resource-account-held value must remain claimable by a controllable owner. Every epoch that elapses while `beneficiary_for_operator == @0x0`, that epoch's entire commission (`commission_active` + `commission_pending_inactive`) is converted into unredeemable shares inside the stake pool. This is a supply/custody accounting corruption: value formally exists in the pool's internal ledger but is permanently orphaned, satisfying the "Permanent lock or non-recoverable loss of ... resource-account-held value" custody-impact category. Because `synchronize_delegation_pool` is a `public entry fun` callable by anyone (not gated to the operator), this loss compounds automatically over time even without operator involvement once the zero beneficiary is set once.

### Likelihood Explanation
Likelihood is moderate: the action is self-inflicted by the operator (calling `set_beneficiary_for_operator(operator, @0x0)`), so it does not directly steal from delegators, but it can happen accidentally (e.g., front-end bug, copy-paste zero address, or clearing a delegated payout address by passing `@0x0` instead of a dedicated "reset" call) since there is no dedicated `reset_beneficiary_for_operator` function and no argument validation, unlike `vesting::set_beneficiary`, which explicitly calls `assert_account_is_registered_for_apt(new_beneficiary)` before accepting a new beneficiary.

### Recommendation
Add an explicit check in `set_beneficiary_for_operator` (and its equivalents in `staking_contract.move`) rejecting `new_beneficiary == @0x0`, mirroring the Celo fix: disallow setting a zero beneficiary while commission accrual is active, and/or introduce a dedicated `reset_beneficiary_for_operator` function so "no beneficiary" is represented by removing the `BeneficiaryForOperator` resource rather than by an unchecked zero address.

### Proof of Concept
1. Operator calls `initialize_delegation_pool` and later `set_beneficiary_for_operator(operator, @0x0)` — succeeds with no validation.
2. Any account calls `synchronize_delegation_pool(pool_address)`. `calculate_stake_pool_drift` computes non-zero `commission_active`/`commission_pending_inactive`.
3. `buy_in_active_shares(pool, beneficiary_for_operator(operator) /* == @0x0 */, commission_active)` mints shares to shareholder `@0x0` in `pool.active_shares`.
4. No entry function in `delegation_pool.move` allows producing a `&signer` for `@0x0`; therefore these shares (and the APT backing them held by the stake-pool resource account) can never be unlocked or withdrawn — value is permanently lost from circulation despite the transaction succeeding without any error.

<br>

Note: I was unable to fully confirm within available context whether `account::create_account`/`aptos_account::deposit_coins` explicitly reverts on `@0x0` (this would corroborate the parallel, coin-based DoS in `staking_contract::distribute_internal`); that portion of the analysis is presented as a secondary, lower-confidence observation and the primary finding above (delegation_pool share-based permanent lock) does not depend on it.

    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
