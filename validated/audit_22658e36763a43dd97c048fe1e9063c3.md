### Title
Webhook shop-domain identity spoofing via HMAC binding gap - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from an unauthenticated HTTP header, while the HMAC that `ShopifyAPI::Webhooks::Registry.process` validates covers only the raw request body. This breaks the intended binding `hmac-verified bytes == bytes that determine the tenant`, allowing any holder of one valid `(raw_body, hmac)` pair to relabel the event as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. only the body bytes: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic coverage: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (along with `topic`, `webhook_id`, `api_version`) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity equality the code needs to preserve is: *the shop attributed to the event == the shop whose bytes were HMAC-authenticated*. Because the signature only binds `raw_body`, an unprivileged actor who can obtain (or generate, e.g. as a merchant/developer running the app on their own store) one legitimate `(raw_body, valid hmac)` pair can replay that exact body with the `x-shopify-shop-domain` (and `topic`/`webhook-id`/`api-version`) headers rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects those headers, and `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "<victim-shop>", ...)`, `topic`, and `webhook_id` all forged. Per the documented usage pattern (`docs/usage/webhooks.md`), apps use `data.shop` to look up/act on that shop's session and data, so an attacker who controls or has captured a valid webhook payload for their own shop can cause the app to attribute and act on that event under a different shop's identity.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the gem's own webhook-processing API hands the host application attacker-controlled `shop`, `topic`, and `webhook_id` values that were never covered by the cryptographic proof, while advertising (via `Registry.process`) that the request "did indeed come from Shopify" for that shop. Any app that follows the documented pattern of keying business logic (session lookup, per-shop state updates, deduplication via `webhook_id`) off `data.shop`/`data.topic`/`data.webhook_id` can be made to cross tenant boundaries or process spoofed topics, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
An attacker needs one legitimately signed `(raw_body, hmac)` pair — trivially obtainable by any merchant/developer who has installed the app on their own store (an unprivileged actor relative to other tenants) and captured one of their own webhook deliveries. No access to `api_secret_key`, tokens, or other tenants' secrets is required; only header rewriting on replay.

### Recommendation
Include `topic`, `shop`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. by validating the raw body's own `shop_domain`/`id` fields against the headers before trusting them), so `HmacValidator.validate` fails whenever any attacker-controlled header used to build `WebhookMetadata` diverges from what was actually signed.

### Proof of Concept
1. Register a webhook handler that trusts `data.shop` to act on a specific tenant (as documented in `docs/usage/webhooks.md`).
2. As the operator of Shop A (unprivileged w.r.t. Shop B), install the app and capture one legitimate webhook delivery: `raw_body`, and header `x-shopify-hmac-sha256`.
3. Replay the exact same `raw_body`/`hmac` to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com` (and optionally alter `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` (only `raw_body` is hashed), then invokes the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", topic: <attacker-chosen>, webhook_id: <attacker-chosen>, body: <Shop A's body>)`, causing the host app to process/attribute the event under Shop B's identity.
