### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing an attacker to forge which shop a valid webhook is attributed to - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop` (tenant) that the webhook is attributed to is read from an HTTP header that is never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose HMAC matches the body and then routes/labels the event using this unauthenticated `shop` field, breaking the binding `HMAC-covered-bytes == bytes-acted-on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic`/`webhook_id`/`api_version` are all read from HTTP headers, which are attacker-controlled input to the app's webhook endpoint and are never mixed into `to_signable_string`: [2](#0-1) 

`Registry.process` validates the HMAC purely against the body/secret, and, once that passes, dispatches the handler using `request.shop` taken straight from the unauthenticated header: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever operate on `verifiable_query.to_signable_string` (the body, for webhooks) and the app secret — they have no knowledge of, and cannot bind, the `shop` header: [4](#0-3) 

The identity binding that should hold is:
`HMAC-signed bytes == bytes used to attribute/act on the event (topic, shop, webhook id)`

Here, `HMAC-signed bytes = raw_body` while `bytes acted on = raw_body + shop-domain header (+ topic, webhook-id, api-version headers)`. Since the `shop` header falls outside the signed material, an attacker who possesses **any** one genuinely-signed webhook payload/HMAC pair (trivially obtainable by installing the app on their own store and receiving a legitimate webhook for it, since HMAC is only over the body and does not depend on the sender's identity) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value — e.g. a victim's shop domain. The HMAC check in `Registry.process` still succeeds (it never looked at the header), and the handler executes with `WebhookMetadata#shop` set to the forged/victim domain.

### Impact Explanation
This crosses the tenant boundary that this gem is supposed to enforce for webhook processing: an attacker-controlled request is accepted as authentic and is attributed to an arbitrary shop of the attacker's choosing, purely because the header that carries tenant identity is outside the cryptographic envelope. Any host application that relies on `WebhookMetadata#shop` (as documented/intended usage of `Registry.process`) to select the tenant's session, data store, or access token for the associated processing will act on/associate data under the wrong tenant — i.e., cross-tenant access. This matches the "cross-tenant access" Critical impact category defined for this analysis, and is a structurally direct analog of the reported bug class (an operation trusts a field that is not covered by the authentication mechanism).

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who can install the app on a shop they control (a normal, unprivileged path for any merchant): they receive at least one legitimately HMAC-signed webhook body for an arbitrary topic, then simply replay that same body+HMAC with a different `shop`-domain header to the app's public webhook endpoint. No secret material, TLS interception, or privileged access is required — only observing one's own valid webhook and crafting an HTTP request with a spoofed header.

### Recommendation
Include the shop domain (and ideally the webhook id / topic) inside the HMAC-signed material, or otherwise cryptographically bind them to the signature verification, e.g., by validating the header-provided shop against a source that Shopify itself signs, or by having the app perform a follow-up authenticated lookup which does not trust the header for tenant attribution. At minimum, `Utils::HmacValidator.validate` should be extended (or a new check added in `Registry.process`) so that the `shop-domain` header cannot be varied independently of the signed body without invalidating the HMAC.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing:
   - raw body `B`
   - header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `api_secret_key`)
2. Attacker sends a forged HTTP POST to the app's public webhook endpoint with:
   - Body: the same `B`
   - Headers: `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Topic: <same topic>`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` and `H`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the request never actually originated from, nor was authorized by, that shop.
