## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, using the app's single, shop-independent `client_secret`. The `shop` identity that the handler receives, however, is taken directly from an unauthenticated HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) that is never included in the signed content. This breaks the intended binding `authenticated_payload == tenant_identity`: any request whose body+HMAC pair is valid for the app (which is easy to obtain honestly, e.g. by installing the app on an attacker-controlled shop and capturing one of its own real webhook deliveries) can be replayed with an arbitrary `shop-domain` header, and the library will treat it as belonging to a different, victim tenant.

### Finding Description
`Request#hmac` computes the received signature purely from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor pulls the tenant identity straight from an HTTP header with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the webhook using only `Utils::HmacValidator.validate(request)`, i.e. it checks that the body was signed with the app's secret — it performs no check that the `shop` header actually corresponds to the shop that produced that signature: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm only that `computed_signature(raw_body, secret) == received_hmac`, where `secret` is `Context.api_secret_key` — a single value shared across every shop/tenant that has this app installed, not a per-shop secret: [4](#0-3) 

Because the same `client_secret` is used to authenticate webhooks for *every* shop that installs the app, and because `shop` is not part of the signed payload, the HMAC check answers "was this body signed by this app's secret?" — not "did shop X send this body?". The `shop` value handed to the registered handler is therefore an unauthenticated field acted upon as if it were an authenticated tenant identifier: [5](#0-4) 

This is the same class of bug the reference report describes for Liquity's ERC20 contracts: a validity check (`_requireValidRecipient`/HMAC) enforces one invariant (payload integrity/signed-by-this-app), while a different value that downstream code relies on for a security-relevant decision (`_recipient`/`shop`) is not covered by that same guarantee, letting a 3rd party (any shop that installs the app, i.e. an "unprivileged internet user" relative to other tenants) desynchronize the two.

### Impact Explanation
This is cross-tenant confusion: a self-service merchant (attacker) who installs the app on their own store can obtain a legitimately-signed webhook body+HMAC pair for their own shop, then resend that exact body/HMAC combination with a different `shopify-shop-domain` header value. The host application's webhook handler (fed via `WebhookMetadata`/`request.shop`) will process the event as if it originated from the victim shop, because nothing in the library ties the header to the signature. Depending on what the handler does with `shop` (e.g. looking up or mutating per-tenant data, access tokens, or business records keyed by that shop), this can lead to cross-tenant data corruption or disclosure — meeting the "cross-tenant access" bar for a Critical/High finding.

### Likelihood Explanation
Likelihood is high for any app using this gem's webhook registry as documented: the attacker only needs their own legitimate installation (no stolen secret, no TLS interception, no privileged access) to harvest a valid body/HMAC pair, then can freely vary the `shop-domain` header when replaying it to the app's own webhook endpoint.

### Recommendation
Include the shop domain (and ideally the webhook topic/id) inside the HMAC-signed material, or independently re-derive/verify the shop from data that is cryptographically bound to the signature, before trusting `request.shop` for any tenant-scoped operation. Short term, document/enforce that `Registry.process` must cross-check `request.shop` against an out-of-band trusted source (e.g. the session/shop the request was routed to) rather than trusting the header alone.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; attacker triggers a real event (e.g. edits a product) to receive a genuine webhook delivery with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker resends the same `B`/`H` to the app's webhook endpoint but sets `shopify-shop-domain: victim.myshopify.com`.
3. `Request.new` parses headers, `HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and finds it matches `H` (per [6](#0-5) ), so `Registry.process` proceeds.
4. The handler is invoked with `WebhookMetadata` built from `shop: request.shop` = `"victim.myshopify.com"` (per [7](#0-6) ), even though the payload actually came from the attacker's own shop — demonstrating the cross-tenant identity confusion.

          received_signature = verifiable_query.hmac
