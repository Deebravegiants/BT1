This is exactly the vulnerability: `Webhooks::Request#hmac` and `#shop` (and `#topic`, `#webhook_id`) are read from **separate, unauthenticated HTTP headers**, while `to_signable_string` returns only `@raw_body`. [1](#0-0) [2](#0-1) 

The HMAC (`X-Shopify-Hmac-Sha256`) only covers `@raw_body`; it never binds `shop-domain`, `topic`, `webhook-id`, or `api-version`, all of which are attacker-controlled request headers. `Utils::HmacValidator.validate` only checks that `verifiable_query.hmac` (computed over `raw_body`) matches — it says nothing about which shop sent it. [3](#0-2) 

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` IS included inside `to_signable_string` and therefore is bound by the HMAC. [4](#0-3) 

For webhooks, an app that trusts `request.shop` (e.g., to route the webhook payload to a tenant's session/store or to look up which shop's data to update) is trusting a value with no cryptographic binding to the signed bytes. Any attacker who can produce a POST with a valid `hmac-sha256` for a *known* body (e.g., replaying a captured webhook, or since the JSON body for many webhook topics is often predictable/attacker-influenced for their own shop) can freely swap the `shop-domain` header to point to a *different* merchant's shop domain while keeping the same valid HMAC, since the header is not part of the signed content.

### Title
Webhook `shop-domain` header not bound by HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC verification using only the raw request body (`to_signable_string` returns `@raw_body`), but exposes `shop`, `topic`, `webhook_id`, and `api_version` as separately-trusted attributes read straight from HTTP headers. None of these header values are included in the signed bytes, so `Utils::HmacValidator.validate` returning `true` proves only that the body bytes are authentic for *some* HMAC-valid request — it proves nothing about which shop, topic, or webhook the body belongs to.

### Finding Description
`Webhooks::Request#hmac` reads `shopify-hmac-sha256` and `#shop` reads `shopify-shop-domain` from headers independently (lines 10-23), while `#to_signable_string` (the value actually verified against the HMAC in `Utils::HmacValidator.validate_signature`) is exclusively `@raw_body` (lines 35-38). This breaks the binding: `hmac_valid == true` should imply `shop == authenticated_shop`, but the equality that is actually enforced is only `hmac_valid == true` implies `body == signed_body`. Any consumer of this gem that calls `request.shop` to key their session/store lookup (a documented, expected usage pattern for this class) is trusting an attacker-controlled header field after only validating an unrelated field (the body).

This is the direct analog of the referenced report's bug class: a field acted upon (`shop`, used to determine tenant identity) is not covered by the cryptographic check (the HMAC only covers `raw_body`), exactly the "field acted on but not covered by the HMAC" pattern called out in the rules.

### Impact Explanation
If a host application uses `request.shop` from a verified `ShopifyAPI::Webhooks::Request` to decide which merchant's offline session/access token to use for follow-up processing (the standard integration pattern for this gem, matching Shopify's own webhook documentation), an attacker can present a webhook body that produces a valid HMAC (e.g. a previously observed/replayable body for the attacker's own installed shop) together with a forged `shop-domain` header naming a victim shop. Since the gem reports `hmac_valid = true` and `shop = <victim shop>`, the host app is misled into treating attacker-supplied data as authentic for the victim tenant — a cross-tenant confusion at the trust-boundary this gem is supposed to enforce.

### Likelihood Explanation
Exploitation requires only an unauthenticated HTTP POST to the app's webhook endpoint with attacker-controlled headers (`shop-domain`) and a body/HMAC pair the attacker can obtain (their own shop's legitimately signed webhook, replayed with a different `shop-domain` header, or a genuine webhook captured/observed for one merchant and replayed against the app with a different `shop-domain`). No access token, `client_secret`, or privileged access is required — only the ability to send an HTTP request to the app's public webhook endpoint, which satisfies the "unprivileged internet user" constraint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified representation, or otherwise cryptographically or contractually bind them to the verified body — e.g., have `to_signable_string` incorporate these header values (matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signable string), or document/enforce that `shop` must be independently confirmed against a known/registered shop record before being trusted, never taken solely from the unauthenticated header.

### Proof of Concept
```ruby
# Attacker captures (or generates via their own installed shop) a valid
# raw_body + X-Shopify-Hmac-Sha256 pair.
raw_body = '{"id":123}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
valid_hmac_b64 = Base64.strict_encode64(valid_hmac)

# Attacker sends this body with a forged shop-domain header naming the victim shop.
headers = {
  "X-Shopify-Topic" => "orders/create",
  "X-Shopify-Hmac-Sha256" => valid_hmac_b64,
  "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com",  # attacker-controlled, unsigned
  "X-Shopify-Webhook-Id" => "forged-id",
  "X-Shopify-Api-Version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true
request.shop # => "victim-shop.myshopify.com"  -- attacker-controlled, yet reported as verified
```
`Utils::HmacValidator.validate` returns `true` because the HMAC only ever checked `raw_body`; `request.shop` is nonetheless returned to the caller as if it were an authenticated attribute of the same verified request.
