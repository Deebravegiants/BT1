### Title
Creator can permanently lose accrued FeeVault USDC rewards if blacklisted from USDC - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` pays out a creator's entire pooled USDC balance to `msg.sender` with no ability to specify an alternate recipient. If the creator address is later blacklisted by USDC (e.g. via Circle's freeze list), every call to `claim()` reverts inside `SafeERC20.safeTransfer`, and the already-accrued `creatorBalance[creator]` becomes permanently unclaimable — with no on-chain recovery path.

### Finding Description
Fees are accrued per-creator address in `FeeVault.accrue()`: [1](#0-0) 

`claim()` reads `creatorBalance[msg.sender]`, zeroes it, and transfers it unconditionally to `msg.sender`: [2](#0-1) 

There is no `claimTo(address recipient)` variant and no admin/permissionless function that can redirect or re-key an existing `creatorBalance[creator]` entry to a different address.

The only related recovery mechanism is `Bonding.transferCreator(tokenAddress, newCreator)`, callable solely by the current creator: [3](#0-2) 

Per the project's own documentation, this only redirects **future** fee attribution — it does not touch the FeeVault balance already accrued under the old creator address: [4](#0-3) 

So once USDC fees have accrued into `creatorBalance[oldCreator]` (which happens automatically on every buy/sell of the creator's token via `Zap._accrueFee` → `FeeVault.accrue`), transferring the creator role forward does nothing to unlock that balance. If `oldCreator` is blacklisted by USDC before calling `claim()`, that balance is stuck forever: `claim()` can only be called by `msg.sender == oldCreator` (it reads `creatorBalance[msg.sender]`), and the outbound `safeTransfer(msg.sender, amount)` will always revert for a blacklisted address.

This mirrors the referenced report exactly: a legitimate earner of USDC rewards (there, a round winner; here, a token creator) is permanently denied a payout solely because their address is blacklisted by USDC, and the protocol offers no per-token/alternate-recipient claim path.

### Impact Explanation
Any creator whose address gets blacklisted by USDC (directly, or preemptively before even claiming) permanently loses their entire accrued `creatorBalance` in `FeeVault` — funds that were already pulled from `Zap` and are sitting, fully backed, in the vault (per `accrue`'s underfund invariant). This is a permanent freeze of legitimate creator funds with no owner or permissionless recovery mechanism, satisfying the Medium-severity bar of the original report.

### Likelihood Explanation
The path is fully unprivileged and organic: a creator launches a token via `Zap.createToken`, earns fees automatically as any trader buys/sells through `Zap.buy`/`Zap.sell` (0.25% creator share accrued each trade), and later calls `FeeVault.claim()`. No attacker action is required — only that the creator's own address ends up on USDC's blacklist (a real-world occurrence USDC explicitly supports), which is entirely plausible over a token's lifetime given fees accrue continuously and claims can be deferred indefinitely.

### Recommendation
- Add a `claimTo(address recipient)` function (or allow `claim()` to accept a caller-specified recipient) so a creator can redirect payout to a non-blacklisted address.
- Alternatively/additionally, allow `Bonding.transferCreator` (or a dedicated `FeeVault` function, gated to the affected creator) to migrate the *existing* `creatorBalance[oldCreator]` to `newCreator`, not just future attribution.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`; `Bonding.tokenInfo(token).creator = creator`.
2. Traders buy/sell the token through `Zap.buy`/`Zap.sell`; each trade calls `_accrueFee` → `FeeVault.accrue(token, creator, creatorShare, protocolShare, isBuy)`, incrementing `creatorBalance[creator]`.
3. USDC's issuer blacklists `creator`'s address (a real, supported USDC operation).
4. `creator` calls `Bonding.transferCreator(token, newAddress)` to try to fix future attribution — this only updates `Bonding.tokenInfo(token).creator`, leaving `FeeVault.creatorBalance[creator]` unchanged.
5. `creator` (or anyone) calls `FeeVault.claim()` from `creator`'s address — `$.usdc.safeTransfer(msg.sender, amount)` reverts because `creator` is blacklisted; `newAddress` cannot claim it either because `creatorBalance[newAddress]` is unaffected.
6. The `amount` in `creatorBalance[creator]` is now permanently unclaimable — stuck in the vault forever.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```

```text
    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

```markdown
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
```
