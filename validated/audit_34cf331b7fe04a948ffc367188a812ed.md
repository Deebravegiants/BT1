### Title
Webhook `shop`/`topic` headers unsigned — dispatch and downstream data trust a value never covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves the body is untampered [2](#0-1) . `Registry.process` validates the HMAC and then dispatches on `request.topic` and later hands `request.shop` straight to the handler, both of which come from headers outside the signed string [3](#0-2) . The specific base64-padding angle in the question is not itself exploitable, but the underlying SIGNATURE COVERAGE invariant is genuinely broken for `shop`, `topic`, `api_version`, and `webhook_id`.

### Finding Description
The claimed invariant to test is: `to_signable_string == everything HmacValidator/Registry act on`. Tracing the code:

- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it (via `OpenSSL.secure_compare`) against `verifiable_query.hmac` [2](#0-1) .
- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) . It does **not** include `topic`, `shop`, `api_version`, or `webhook_id`, all of which are read straight from attacker-controlled HTTP headers via `shopify_header` [4](#0-3) [5](#0-4) .
- `Registry.process` first validates HMAC, then uses `request.topic` (unsigned) to select the handler, and finally passes `request.shop` (unsigned) into `WebhookMetadata` given to the handler [3](#0-2) .

So the equality the invariant demands — "every value acted on downstream is inside the string handed to `HmacValidator` via `to_signable_string`" — is false for `shop`, `topic`, `webhook_id`, and `api_version`. Concretely: an attacker who can get one validly-signed webhook body delivered to their own installed app (e.g., trigger a `shop/update` event on their own dev shop, capturing the raw body and its correct `x-shopify-hmac-sha256` value) can replay that exact body+HMAC pair to the shared app webhook endpoint with a different `x-shopify-shop-domain` header (a victim shop's domain) and/or a different `x-shopify-topic` header (any topic registered with a handler). Because `to_signable_string` never includes these headers, the HMAC still validates, `Registry.process` still succeeds, and the handler executes believing the event legitimately originated from the spoofed shop/topic.

Regarding the specific mechanism named in the question — `Base64.decode64` tolerating malformed padding/whitespace on the hmac header itself — this does **not** independently defeat the comparison: `compute_signature` still computes the correct HMAC bytes with the real secret, and `OpenSSL.secure_compare` still requires the decoded header bytes to exactly equal those correct bytes. Lenient base64 decoding does not let an attacker forge signatures without the secret; it only tolerates cosmetic encoding variance in an otherwise-correct signature. So that specific claim (forging via base64 padding tricks) does not hold on its own.

The genuine break is the unsigned-header issue: `Registry.process` trusts `request.shop`/`request.topic` for dispatch and for data handed to the handler, and these are outside SIGNATURE COVERAGE.

### Impact Explanation
An attacker who owns an installed test app can generate a validly-signed webhook body for their own shop, then replay it with a forged `x-shopify-shop-domain` header pointing at any victim shop, and/or a forged `x-shopify-topic` selecting a different registered handler. If the host application trusts `WebhookMetadata#shop` to look up/act on merchant data (a common pattern — using the webhook's shop to fetch a session/access token or update per-shop records), this is a cross-tenant data-injection primitive: the app performs shop-scoped actions attributing attacker-supplied event data to a shop the attacker does not own. This matches the "cross-tenant access" / authentication-bypass-adjacent category, though it requires the host app to use `request.shop` for authorization decisions (this gem provides the metadata; the exact blast radius depends on how the consuming app uses `WebhookMetadata#shop`).

### Likelihood Explanation
Preconditions: attacker needs a dev shop with the target app installed and at least one webhook subscription, so they can obtain one genuinely-signed `(body, hmac)` pair. Sending the forged replay to the app's public webhook endpoint costs nothing further — no secret is required, only observation of one legitimate delivery to their own shop. This is a realistic and repeatable path within the stated attacker model.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` headers in the signable string (or otherwise independently bind the verified body to those header values, e.g., recomputing/checking a canonicalized header+body string), so that `HmacValidator.validate` covers everything `Registry.process` and the handler act on. Alternatively, require the consuming app to independently verify `shop` against session state it controls rather than trusting `WebhookMetadata#shop` from a header not covered by the signature.

### Proof of Concept
```ruby
# test/webhooks/registry_unsigned_headers_test.rb
require "test_helper"

class RegistryUnsignedHeadersTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "shop/update", delivery_method: :http, path: "/webhooks",
      handler: FakeWebhookHandler.new,
    )
  end

  def test_same_signed_body_dispatches_for_different_shops
    body = '{"id":1}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", "secret", body)
    )

    request_a = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "shop/update",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      },
    )
    request_b = ShopifyAPI::Webhooks::Request.new(
      raw_body: body,
      headers: {
        "x-shopify-topic" => "shop/update",
        "x-shopify-hmac-sha256" => hmac,
        "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      },
    )

    assert ShopifyAPI::Utils::HmacValidator.validate(request_a)
    assert ShopifyAPI::Utils::HmacValidator.validate(request_b)
    # Same signature validates for two different declared shops -> shop not covered by signature
    assert_equal "victim-shop.myshopify.com", request_a.shop
    assert_equal "attacker-shop.myshopify.com", request_b.shop
    refute_equal request_a.shop, request_b.shop
  end
end
```
Both requests pass `HmacValidator.validate` with the identical signature, yet `Registry.process` would hand different `shop` values to the handler for the same signed body — proving `shop` is acted upon downstream despite being outside `to_signable_string`.
