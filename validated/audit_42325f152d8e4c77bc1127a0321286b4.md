## Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as verified once the raw body's HMAC checks out, then forwards the `shop` value taken from the `X-Shopify-Shop-Domain` header — a value that is **not** covered by that HMAC — to the app's handler as the trusted tenant identity.

## Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`shop` is a completely separate header, read independently and never mixed into the signed string: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it against the received signature — it never touches `shop`: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authenticity gate, then immediately hands `request.shop` to the handler as the trusted tenant/shop identity for the webhook: [4](#0-3) 

The gem's own documentation reinforces that host apps are expected to rely on this "verified" status and on `data.shop` as the shop identity without any additional check: [5](#0-4) [6](#0-5) 

**Broken identity binding (as an equality):**
`shop_attributed_to_handler (request.shop, from an unsigned header)` should equal `shop_that_actually_produced_the_HMAC-covered_body`, but nothing in `HmacValidator`/`Registry`/`Request` enforces this. The gem authenticates the *bytes of the body*, not the *(body, shop) pair*.

## Impact Explanation
An attacker who legitimately installs the app on their own store receives genuine, correctly-HMAC'd webhook deliveries from Shopify for that store. Because `shop` is outside the signed content, the attacker can replay the same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (the body/HMAC pair is untouched), so `Registry.process` calls the handler with `WebhookMetadata` claiming the data belongs to the victim shop. Any host-app logic that is scoped/keyed by `data.shop` (the documented, expected usage pattern) can be made to write, delete, or act on attacker-controlled payloads under another merchant's tenant context — a cross-tenant integrity/confidentiality violation reachable from an unprivileged internet user without any credentials belonging to the victim or the app.

## Likelihood Explanation
The attacker only needs their own (unprivileged) shop with the app installed to obtain a valid `(body, hmac)` pair; no access to `api_secret_key`, tokens, or the victim's credentials is required. Replaying the POST to the app's public webhook URL with a modified header is trivial and matches exactly the documented integration pattern (`Registry.process` + `data.shop`), so any app following the gem's own docs is exposed.

## Recommendation
Bind `shop` into the authenticated material, e.g. include the shop domain (and/or webhook id/topic) in the value that is HMAC-verified, or require callers to independently confirm that `request.shop` corresponds to a shop with a currently valid, previously-stored session/access token before trusting it as the tenant identity. At minimum, update `Registry.process` to cross-check `request.shop` against known installed shops rather than exposing it as an implicitly-trusted field once `HmacValidator.validate` passes.

## Proof of Concept
1. Install the app on attacker-controlled shop `evil.myshopify.com`; Shopify sends a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` with the app's secret), `X-Shopify-Shop-Domain: evil.myshopify.com`.
2. Attacker replays the identical `B`/`H` pair to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers; `Utils::HmacValidator.validate` recomputes HMAC over `B` only (per `lib/shopify_api/webhooks/request.rb` `to_signable_string` and `lib/shopify_api/utils/hmac_validator.rb`), which still matches `H` — validation succeeds.
4. `Registry.process` invokes the app handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's payload>, ...)`, causing the host app to process attacker-supplied data as if it originated from `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
