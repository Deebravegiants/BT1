### Title
Backend Duplicate-Signup Check Bypassed For User-Centric Signups - (File: `src/plans/mod.rs`)

### Summary
In `MasterPlan::do_signup`, the Orb only calls `enroll_user()` — which is the sole code path that submits iris codes to the backend and polls for the backend's duplicate/uniqueness detection — when `user_centric_signup` is `false`. When `user_centric_signup` is `true` (and `ignore_user_centric_signups` is not overridden), the signup is marked successful purely from the *local* `signup_reason`, without ever notifying the backend or requesting a uniqueness check. This mirrors the reported bug class: a mandatory check ("round must be active" / here, "backend uniqueness enrollment must occur") is applied only on one branch of a boolean-gated code path and is entirely skipped on the other, letting the skipped branch bypass validation that is otherwise required for every signup.

### Finding Description
`do_signup` in [1](#0-0)  branches on `user_centric_signup`:

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
        .await
        .is_success()
};
```

`enroll_user()` [2](#0-1)  is the function that actually submits the captured iris codes to the backend (`signup_post::request`) and then polls (`signup_poll::request`) until the backend confirms uniqueness. The poll's own comments make clear this is where backend-side duplicate detection happens: [3](#0-2)  lists "Backend duplicates", "Backend inflight matches", "Backend detected fraud" as reasons a signup can fail at this step.

When `user_centric_signup` is `true`, this entire submission/uniqueness step is skipped: `success` is derived only from `signup_reason`, which itself comes from the local `detect_fraud()` call. In the current build, `detect_fraud()` is a stub that always returns `false` — "FOSS: WE HAVE DELETED ALL FRAUD CHECKS" [4](#0-3) . As a result, for the `user_centric_signup` branch there is no local fraud/liveness enforcement and no backend-side duplicate/uniqueness enforcement — the signup is unconditionally marked `Normal`/success as long as the biometric pipeline produced a `Some(pipeline)`.

This is structurally identical to the reported donation bug: the code correctly gates a critical check (round-active / project-id requirement, here backend duplicate enrollment) behind an `if !special_case` block, but omits any equivalent check for the `special_case` branch, allowing that branch to bypass validation that every other signup must pass through.

### Impact Explanation
Any signup routed through the `user_centric_signup` branch is accepted as a verified, unique-human signup without the backend ever being asked to check for duplicate iris codes, and without any local fraud detection (since `detect_fraud` is stubbed to `false`). This allows the same biometric identity to be enrolled multiple times ("cross-signup state bleed" / unauthorized or misattributed signup), directly undermining the uniqueness guarantee the whole signup/enrollment pipeline exists to provide. Given the enroll_user path is also what forwards the signup outcome for fraud/duplicate bookkeeping, entirely skipping it for this branch means fraudulent or duplicate signups can be silently and repeatedly marked as `Success`.

### Likelihood Explanation
The `user_centric_signup` flag is not attacker-forged in the direct sense — it originates from `backend::user_status::UserData` returned by the backend during QR-code verification — but it is a normal, reachable value for any unprivileged end user whose account/app is provisioned in "user-centric" mode [5](#0-4) . No special privilege, feature flag, or CLI access is required to hit this branch; it is part of the standard `do_signup` flow exercised on every normal signup attempt for such accounts. Combined with `detect_fraud()` currently always returning `false`, the likelihood of complete bypass of duplicate-signup enforcement for this code path is high whenever an unprivileged user's account is in user-centric mode.

### Recommendation
Do not allow the `user_centric_signup` branch to bypass backend enrollment/uniqueness submission entirely. At minimum, still submit the captured biometric data to the backend (`enroll_user`/`signup_post`) for uniqueness/duplicate checking even when `user_centric_signup` is true, and only skip the app-centric credential-issuance parts of the flow that are legitimately owned by the app. Alternatively, require the backend to independently confirm uniqueness before this branch can report `success = true`, rather than trusting purely local, unauthenticated state (`signup_reason`).

### Proof of Concept
1. Provision (or have the backend mark) an account such that `user_status::UserData.user_centric_signup == true` (standard app-centric account, no special access needed).
2. Perform a signup on the Orb with this account; ensure the biometric pipeline produces `Some(pipeline)` (a normal successful capture).
3. Observe in `do_signup` [1](#0-0)  that `enroll_user()` (and therefore `signup_post`/`signup_poll` backend duplicate checking) is never invoked; `success` is set to `true` solely because `signup_reason == SignupReason::Normal`, which itself is only affected by the always-`false` `detect_fraud()` stub.
4. Repeat steps 1–3 with the same underlying biometric identity across multiple accounts/signups — each completes as a "successful," unique signup because the backend's duplicate-detection step is never reached.
