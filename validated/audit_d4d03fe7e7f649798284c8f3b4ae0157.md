### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop` (and `topic`/`webhook_id`) values extracted from HTTP headers that are excluded from that signature. This breaks the intended binding: `hmac-verified bytes == raw_body` while `shop identity used by host app == unauthenticated header`, allowing replay of a legitimately-signed webhook body with a forged shop-domain header to impersonate a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by defining: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from HTTP headers that are never part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which computes the signature over `request.to_signable_string` (i.e., `raw_body` only) — and then, once that check passes, blindly forwards `request.shop` (sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) into `WebhookMetadata`, which is handed to the app's registered handler: [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC only from `to_signable_string` and the app's `api_secret_key`, and compares it to the `hmac` header value — it never binds the shop/topic/webhook-id headers into the signed material: [4](#0-3) 

Because the identity field acted on (`shop`, used by the host app to key sessions/data via `WebhookMetadata.shop`) is not part of the HMAC-covered bytes, any party who has ever obtained one valid `(raw_body, hmac)` pair — e.g., a merchant who installed the app and received a legitimate webhook to their own shop — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true` because only the body is checked, yet `Registry.process` will hand the attacker-chosen `shop` value to the app's handler as if it were verified.

### Impact Explanation
This is a cross-tenant integrity failure: an unprivileged actor (a legitimate merchant of one shop, acting maliciously, or anyone who has captured one webhook delivery) can cause the host application to process/attribute webhook data under an arbitrary victim shop domain, since the gem itself asserts (via a passing `HmacValidator.validate` check) that the request — including its `shop` field — is authentic. Any app relying on the gem's HMAC validation to trust `request.shop`/`WebhookMetadata.shop` (which is the documented purpose of `Registry.process`) is exposed to cross-tenant data confusion/injection, satisfying the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker who can obtain at least one legitimate webhook body+HMAC for a shop they control (trivial — install the app, trigger any subscribed event) and can also send an HTTP POST to the app's webhook endpoint with custom headers (also trivial, since these endpoints are public by design). No secrets, tokens, or privileged access are required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity into the HMAC-covered material, or otherwise cryptographically tie the header-derived shop to the verified body (e.g., include shop domain in the canonical signable string, or cross-check the header shop against a shop already known/authorized for the raw body's content) before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document that `request.shop` is not authenticated by `HmacValidator.validate` so consuming apps do not rely on it as a tenant-authorization boundary.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic, capturing the raw POST body and the legitimate `x-shopify-hmac-sha256` value Shopify sent for that delivery.
2. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds normally; `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only and succeeds (matches step 1's untouched body/HMAC).
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))`, causing the host app to process the payload as if it belonged to `victim-shop.myshopify.com`.
