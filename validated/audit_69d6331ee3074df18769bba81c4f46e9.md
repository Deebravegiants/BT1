### Title
Tokens transferred directly to the pool are permanently locked — `cash` bookkeeping ignores stray balances and no recovery path exists - (File: contracts/pool/src/lib.rs)

### Summary
The original report describes reward tokens stuck in `LiquidationRow` because no route converts them and no function redistributes them. The XOXNO Lending analog is stronger: any token amount transferred directly to the `pool` contract (or left in the `controller`) is untracked by the pool's `cash` ledger and there is no entrypoint — permissionless or otherwise — that can release it. Every outbound transfer is driven by the bookkeeping layer (`withdraw`, `borrow`, `claim_revenue`, `recapitalize` refunds, `flash_loan`), which only moves amounts the ledger itself credited. Stray balances are therefore frozen permanently.

### Finding Description
The pool README states that `cash` "is a bookkeeping number" and the pool takes "the controller's word, without verifying the transfer" — the only reconciliation against real `token.balance()` is inside `flash_loan`, which checks strict equality. [1](#0-0)  The full outbound surface is `borrow`, `withdraw`, `repay` (overpayment refund), `recapitalize` (excess refund), `claim_revenue`, `flash_loan`, and `create_strategy` — each debits `cash` or burns shares before transferring. [2](#0-1)  `claim_revenue` pays at most `min(cash, floor(revenue_value))`, so it cannot touch donated balances either. [3](#0-2) 

On the controller side, `claim_revenue_for_asset` measures `balance_delta_since` around the pool call and forwards whatever arrived to the accumulator; anything already sitting in the controller is swept along, but nothing lets an unprivileged caller route tokens *out* of the controller to themselves or to a deserving user — everything goes to the configured accumulator. [4](#0-3) 

So the concrete stuck-fund paths reachable by a single unprivileged address:

1. `token.transfer(user → pool, X)` on any market asset: `cash` is unchanged, `supplied` shares are unchanged, and no entrypoint maps that balance to a claim. The tokens are visible in `token.balance(pool)` but unreachable — `withdraw`/`borrow`/`claim_revenue` only move ledger-backed amounts.
2. `token.transfer(user → controller, X)`: the controller has no sweep-to-user function; the next `claim_revenue` call sweeps the balance into the accumulator as if it were protocol revenue. The sender's funds are permanently absorbed.
3. Seized-share revenue in gated assets (the LQV test shows the pool→controller→accumulator hop): if the token issuer never allowlists the accumulator, the revenue claim reverts and the shares stay in the pool as unclaimable revenue — an exact mirror of "rewards that cannot be liquidated remain in the contract," with no fallback redistribution to suppliers. [5](#0-4) 

### Impact Explanation
Permanent freezing of funds. Tokens donated or mistakenly sent to the pool/controller are locked forever — every outbound leg is gated on ledger state that never recorded the inbound amount. For gated collateral assets, seized-collateral revenue (path 3) can remain permanently unclaimable inside the pool, mirroring the original finding's "rewards locked in `LiquidationRow`" — the value exists on-chain but no reachable entrypoint can distribute it to anyone.

### Likelihood Explanation
Medium-low for accidental transfers (users do send tokens to contract addresses by mistake, and multi-leg liquidation code paths leave transient balances in the controller). Path 3 requires a gated-asset market whose issuer withholds allowlisting — plausible for RWA/permissioned tokens but conditional on issuer behavior. No attacker profit motive is needed; this is a loss-of-funds / stuck-value class, not an exploitable theft.

### Recommendation
- Add an owner/controller-gated `sweep(asset, to)` entrypoint on the pool that transfers `token.balance(pool) − cash` (the untracked surplus) to a specified address, keeping `cash` bookkeeping untouched.
- Alternatively, have `claim_revenue` credit the measured surplus (`balance − cash`) as revenue shares so stray balances become claimable through the existing path.
- For the controller, either document that idle balances are swept to the accumulator on the next claim (current behavior, arguably acceptable) or add a governed recovery function.
- For gated-asset revenue stuck in the pool (path 3), add a fallback that re-routes claim proceeds to an allowlisted fallback address when the accumulator is not admitted, so seized collateral cannot be permanently stranded.

### Proof of Concept
```rust
// Soroban test sketch
let pool = /* deployed pool with a USDC market */;
let user = Address::generate(&env);
let usdc = token::Client::new(&env, &usdc_addr);

// 1. Supply normally so the market has bookkeeping state
controller.supply(&supplier, &entries);           // cash = S, balance = S

// 2. Stray donation
usdc.transfer(&user, &pool_addr, &1_000_000);

// 3. No recovery path
let cash = pool.get_reserves(&key);               // still S; donation invisible
// claim_revenue pays min(cash, revenue) -> never touches the donation
// withdraw/borrow only move ledger-backed amounts
// flash_loan's strict balance == cash check now *reverts* (side effect: DoS)
```
Expected result: `usdc.balance(pool)` permanently exceeds `cash` by the donation, no entrypoint recovers it, and `flash_loan` — which reconciles `token.balance()` with strict equality — fails while the surplus persists. (I did not read `ops/flash.rs` in full to confirm whether the equality check is `>=` or `==`; if it is `>=`, the DoS side-effect disappears but the funds remain locked — the core finding stands either way.)
