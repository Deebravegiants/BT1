### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2` (Tron) can silently fail while escrow accounting still marks funds as paid - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2`, several token payout paths use a raw low-level `.call()` with `IERC20.transfer.selector` and only check that the call itself did not revert (`success`), without decoding and validating the returned boolean. ERC20 tokens that return `false` on failure instead of reverting will cause the contract to treat the transfer as successful, decrement escrow/dust accounting, and emit success events — while the beneficiary never actually receives the tokens.

### Finding Description
The `withdraw` function, which releases escrowed order funds to solvers/users on `RedeemEscrow`/`RefundEscrow` message delivery, performs: [1](#0-0) 

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and similarly for transaction fee payout: [2](#0-1) 

and for dust sweeping: [3](#0-2) 

In every case only the outer call-success (i.e., that the target contract did not revert) is checked; the ABI-encoded `bool` return value from `transfer` is never decoded or asserted. This is exactly the unhandled-return-value class described in the referenced report: for ERC20 implementations that return `false` on failure rather than reverting, `success` will be `true` even though no tokens moved, so the check `if (!success) revert TransferFailed();` never fires.

Notably, the file already imports `SafeERC20`/`IERC20` and uses `using SafeERC20 for IERC20;` and does use `safeTransferFrom` for pulling funds in during `placeOrder`/`fillOrder`, but the payout side (`withdraw` and `SweepDust` handling) reverts to raw, unchecked `.call` usage instead of `safeTransfer`, making the inconsistency clearly a bug rather than an intentional design choice. [4](#0-3) 

### Impact Explanation
Because escrow bookkeeping (`_orders[body.commitment][token] -= amount`, deletion of `TRANSACTION_FEES`, or dust accounting) is updated unconditionally after the `.call`, a non-reverting-`false`-returning ERC20 token used as an order's input/output/fee asset causes the contract to believe funds were paid out while the beneficiary received nothing. The tokens remain locked in the `IntentGatewayV2` contract, and the corresponding order/escrow slot is already zeroed out or marked filled/refunded, so the beneficiary has no path to reclaim them — a permanent loss of user/solver funds. Since `RedeemEscrow`/`RefundEscrow` withdrawals and dust sweeps are the primary fund-exit paths of the intents system, this results in concrete freezing/loss of escrowed value.

### Likelihood Explanation
Any ERC20 token that returns `false` on failed transfers instead of reverting (a common non-standard-but-widely-used pattern, e.g. Tron's TRC20 ecosystem has multiple such deployed tokens) can trigger this when used as an order's input/output/fee token, or when a target address is a contract that rejects the transfer via a boolean return. Given `IntentGatewayV2` is generically designed to support arbitrary caller-specified ERC20 tokens as order assets and fee tokens, and Tron is precisely the ecosystem with elevated exposure to non-compliant token implementations, the likelihood of encountering such a token in production is meaningful, not merely theoretical.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` payout patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw`, fee payout, and `SweepDust` handling) with `IERC20(token).safeTransfer(...)` (the library is already imported and used elsewhere in the same file), which reverts on both call failure and a `false` return value, ensuring escrow accounting can never be updated ahead of an actually successful transfer.

### Proof of Concept
1. Deploy (or use) a TRC20/ERC20 token whose `transfer` implementation returns `false` on failure instead of reverting (e.g., insufficient balance edge case, blacklist check, or a paused-token style implementation).
2. A user places a cross-chain order using this token as an input asset via `placeOrder` (escrowed via `safeTransferFrom`, which works fine since balances are sufficient at deposit time).
3. A solver fills the order on the destination chain; Hyperbridge relays a `RedeemEscrow` message back to the source-chain `IntentGatewayV2`.
4. `onAccept` invokes `withdraw(body, false)`; the token's `transfer` call returns `false` (e.g., because the beneficiary is momentarily blacklisted or a similar non-reverting failure condition specific to that token), yet `success` from the low-level `.call` is `true`.
5. `if (!success) revert TransferFailed();` does not trigger; `_orders[body.commitment][token] -= amount` still executes, and `EscrowReleased` is emitted — the beneficiary's tokens remain stuck in the `IntentGatewayV2` contract with no accounting entry left to reclaim them.
