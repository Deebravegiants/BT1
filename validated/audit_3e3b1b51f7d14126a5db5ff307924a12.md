### Title
Unsafe low-level ERC20 `transfer` in Tron `IntentGatewayV2.withdraw`/`onAccept` accepts non-reverting-`false` tokens as success, permanently freezing escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) releases escrowed order funds and sweeps protocol dust by making a raw low-level `.call` encoded with `IERC20.transfer.selector` and only checking the outer `success` boolean of the call, never decoding/verifying the ABI-encoded `bool` return value that ERC20 `transfer` is supposed to return.

### Finding Description
In `withdraw()`, escrowed collateral/output tokens and accumulated transaction fees are paid out via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

The identical unsafe pattern is used in `onAccept`'s `SweepDust` handler:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

For a low-level `.call`, `success` only reflects whether the callee reverted; it does not validate the boolean payload the ERC20 `transfer` function returns. Non-standard tokens (e.g., USDT-style tokens, and any token that returns `false` on failure instead of reverting) will make the call itself succeed (`success == true`) even though the token transfer failed to move any balance. Because the check only inspects `success`, the code proceeds as if the transfer succeeded: it decrements `_orders[body.commitment][token]` by `amount`, marks the order `_filled`, deletes the fee escrow, and emits `EscrowReleased`/`EscrowRefunded`/`DustSwept` — all while the beneficiary received nothing.

This directly mirrors the referenced Teller `CollateralEscrowV1.withdrawCollateral` report: an unsafe ERC20 transfer whose return value is ignored, applied here to Hyperbridge's cross-chain intents escrow release path. Notably, the same file imports and uses `SafeERC20`/`safeTransferFrom` elsewhere (e.g. lines 405, 459) [3](#0-2)  showing the safe pattern was known but not applied consistently to the payout/sweep paths.

### Impact Explanation
`withdraw()` is reached from `onAccept` when a `RedeemEscrow`/`RefundEscrow` request is delivered by any relayer relaying an authenticated Hyperbridge message from the peer chain, or via `onGetResponse` after a cancellation proof [4](#0-3) . Since the internal escrow accounting (`_orders[...] -= amount`) and order-finalization state are updated unconditionally once the outer call doesn't revert, a token that returns `false` on failed transfer (rather than reverting) causes:
- The beneficiary to receive zero tokens.
- The escrow being marked spent/finalized, so the tokens can never be re-claimed (`UnknownOrder` will revert on any retry since escrow was already zeroed).

This is a permanent loss/freezing of user/solver funds for any ERC20 that follows the widely-deployed non-reverting-return convention.

### Likelihood Explanation
Likelihood is High for any deployment where a listed input/output token doesn't strictly revert on transfer failure (a common real-world token behavior, e.g. USDT-style tokens on EVM-compatible/Tron-style chains). No privileged role is required to trigger it — it fires on the ordinary intents fulfillment/redemption/refund/dust-sweep flow whenever the underlying token transfer silently fails (e.g., due to token-specific restrictions, blacklist, paused state, or insufficient balance edge cases where the token chooses to return `false`).

### Recommendation
Replace the raw `.call` + `success`-only checks in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` usage already present elsewhere in this contract, so that both call-reversion and a `false` boolean return are treated as failures before mutating escrow state.

### Proof of Concept
1. An order is placed and filled cross-chain with an ERC20 input token that returns `false` on failed `transfer` (non-reverting) instead of reverting, e.g., paused/blacklisted for the beneficiary at redemption time.
2. Hyperbridge relayer delivers a `RedeemEscrow` request; `onAccept` routes to `withdraw(body, false)` [4](#0-3) .
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (no revert) but the encoded return data is `false`, meaning zero tokens were moved to `beneficiary` [5](#0-4) .
4. `_orders[body.commitment][token] -= amount` still executes, and `_filled[body.commitment]` is set, `EscrowReleased` is emitted — the order is now permanently considered settled even though the beneficiary got nothing, and the tokens remain stuck in the contract with no accounting path to reclaim them.
