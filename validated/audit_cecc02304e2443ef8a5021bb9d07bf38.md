### Title
Webhook HMAC Verification Signs Only the Raw Body, Letting an Attacker Forge the `shop`/`topic` Headers Used for Tenant Identity - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` covers exclusively the JSON body — never the `shop-domain` or `topic` headers. Those two headers are exactly the fields the registry hands to the app's handler as the trusted tenant identity (`WebhookMetadata.shop`, `WebhookMetadata.topic`). An attacker who can obtain any one valid `(body, hmac)` pair for the app's secret (e.g., by installing the app on their own free/development store and capturing a webhook the app itself sent them) can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value, and the signature check still passes.

### Finding Description
The identity binding that should hold is:

`shop field trusted by the handler (WebhookMetadata.shop) == shop field cryptographically bound by the HMAC`

That equality does not hold in this gem:

- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop` is read straight from the unauthenticated `shop-domain` header: [2](#0-1) 
- `HmacValidator.validate_signature` computes the signature only from `verifiable_query.to_signable_string` (the body) and compares it against the received `hmac`, never mixing in `shop` or `topic`: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 
- `WebhookMetadata.shop` is a plain, unauthenticated `String` field that downstream app code is documented to key business logic on: [5](#0-4) 

Because the signature is computed over the body alone, any header (`shop-domain`, `topic`, `webhook-id`, `api-version`) can be swapped for a different value without invalidating the HMAC, as long as the body/hmac pair being replayed is unchanged.

### Impact Explanation
This breaks the tenant boundary the webhook system is meant to enforce. An unprivileged attacker who is themselves a legitimate merchant of the target app (a free, self-service install — no special privilege required) will receive real webhooks with valid `(body, hmac)` pairs for their own store. By replaying that pair to the app's public webhook callback URL with `x-shopify-shop-domain` rewritten to a victim shop and/or an arbitrary `x-shopify-topic`, the gem reports the event as authentic and passes it to the host application's handler tagged with the attacker-chosen shop/topic. Any host app that uses `data.shop`/`data.topic` (as the gem's own documentation instructs) to select the tenant record to update, e.g. to write order/product/customer data or to trigger shop-specific business logic, can be tricked into applying attacker-controlled webhook content to a victim shop's data — a cross-tenant integrity break. This falls under the High severity class of "scope or expiry/identity check bypass" via a field acted on but not covered by the HMAC.

### Likelihood Explanation
Likelihood is high for any attacker willing to install the target app once on a shop they control (typical free-trial/dev-store friction only): they can generate an arbitrary number of legitimately-signed `(body, hmac)` pairs on demand (e.g., by triggering `orders/create` on their own store) and then POST them directly to the app's public webhook route with forged headers — no TLS interception, no leaked secrets, and no access to `api_secret_key` are required.

### Recommendation
Bind the header values that are used for tenant identity into the signed material, or otherwise verify them out-of-band against session/tenant records before trusting `request.shop`/`request.topic`. Concretely, `HmacValidator`/`Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` into the HMAC input (matching how Shopify's own webhook signing actually authenticates the full delivery, not just the body), and `Registry.process` should reject requests whose `shop` is not a known/authorized shop for the app before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (self-service, no privilege needed) and registers/receives any webhook, e.g. `orders/create`, capturing the raw POST: `raw_body = B`, `x-shopify-hmac-sha256 = H` (valid HMAC of `B` under the app's secret, computed via `compute_signature` logic in `lib/shopify_api/utils/hmac_validator.rb:34-40`).
2. Attacker crafts a new POST to the same public webhook endpoint with:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or a different registered topic)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` builds a `Request`, calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `request.to_signable_string` (`= B`) and compares to `H` — it matches because the check never inspects `shop-domain`/`topic` [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: B, ...)` [7](#0-6) , causing the host application to process attacker-supplied data as if it originated from the victim shop.
