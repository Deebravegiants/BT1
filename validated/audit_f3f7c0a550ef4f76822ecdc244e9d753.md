Audit Report

## Title
Outbound HTTP action response cache is keyed only by owner, not by workflow, allowing cross-workflow cache-result confusion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's `responseCache` deduplicates and serves cached HTTP responses using `OutboundHTTPRequest.Hash()` as the sole cache key, and that hash (defined in the `chainlink-common` dependency but consumed here) excludes `WorkflowID` and `CacheSettings`. This contradicts the component's own documented invariant that "Cache entries are scoped by workflow ID to prevent cross-workflow data leakage," letting a cached response produced for one workflow be served to a different workflow of the same owner when method/URL/headers/body match.

## Finding Description
`gatewayHandler.makeOutgoingRequest` calls `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)` when `req.CacheSettings.MaxAgeMs > 0`, and `responseCache.Fetch`/`Set` key the internal `cache` map purely by `req.Hash()`: [1](#0-0) [2](#0-1) 

The package's own comment documents that the key is composed of "method, URL, headers, body, workflowOwner" — `WorkflowID` and `CacheSettings` are deliberately excluded: [3](#0-2) 

This is directly confirmed by the test suite (`TestRequestHash`), which explicitly asserts two requests differing only in `WorkflowID` produce the **same** hash, and two requests differing only in `CacheSettings` also produce the same hash, while only `WorkflowOwner` differences change the hash: [4](#0-3) [5](#0-4) 

Meanwhile, the module's README explicitly states the opposite guarantee — that the cache key is generated "from workflow ID and request hash" and that cache entries are "scoped by workflow ID to prevent cross-workflow data leakage": [6](#0-5) 

No other code path in `response_cache.go` or `http_handler.go`'s `makeOutgoingRequest` adds `WorkflowID` scoping to the cache key before calling `Fetch`/`Set`, so the documented isolation guarantee is not actually enforced.

## Impact Explanation
Two workflows sharing the same `WorkflowOwner` that issue HTTP Action requests with identical method/URL/headers/body (plausible for common/shared external APIs) will read and write the same cache entry regardless of `WorkflowID`, and regardless of differing `CacheSettings.Store` values. This is a form of cross-user/cross-workflow response corruption — a workflow can receive HTTP action results that were actually fetched on behalf of a different workflow, or pollute another workflow's cache entry, breaking the documented per-workflow isolation boundary. Impact is bounded to workflows under the same owner (owner is included in the hash), so no cross-tenant leak occurs, but the isolation guarantee documented by the component itself is broken.

## Likelihood Explanation
This is deterministic, not race-dependent: any workflow belonging to an owner can trigger it by issuing a normal HTTP Action request with `CacheSettings.MaxAgeMs > 0` whose method/URL/headers/body coincide with another workflow's request under the same owner. No special privileges, timing, or edge conditions beyond ordinary HTTP Action usage are required.

## Recommendation
Include `WorkflowID` in the cache key computation (either in `OutboundHTTPRequest.Hash()` in `chainlink-common`, or by combining `req.WorkflowID` with `req.Hash()` before using it as the map key in `responseCache.Fetch`/`Set`/`isExpiredOrNotCached`), so entries are genuinely scoped per workflow as documented. Alternatively, if owner-level sharing is intentionally desired, update the README to remove the workflow-isolation claim and document the actual owner-scoped sharing behavior, including handling of divergent `CacheSettings` between colliding requests.

## Proof of Concept
1. Workflow A (owner `O`, `WorkflowID:"wf-A"`) issues `GET https://api.example.com/data` with `CacheSettings{Store:true, MaxAgeMs:600000}`. The gateway fetches externally and calls `responseCache.Set`, storing under `req.Hash()` (owner+method+url+headers+body only, per `response_cache.go` lines 15-16 and 111-120).
2. Workflow B (same owner `O`, `WorkflowID:"wf-B"`) issues the identical `GET https://api.example.com/data` with `CacheSettings.MaxAgeMs > 0`.
3. Per `TestRequestHash`'s "having different workflowID results in same Hash" assertion (`response_cache_test.go` lines 139-149), `req.Hash()` for Workflow B equals Workflow A's; `responseCache.Fetch` (lines 66-77) returns Workflow A's cached response to Workflow B without contacting the external endpoint or checking `WorkflowID`. A Go unit test extending `TestRequestHash`/`response_cache_test.go` with two `OutboundHTTPRequest`s differing only by `WorkflowID`, followed by `Set`+`Fetch` calls asserting the second request receives the first's cached response, would concretely demonstrate this.

```go
func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}
```

```go
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}
```
