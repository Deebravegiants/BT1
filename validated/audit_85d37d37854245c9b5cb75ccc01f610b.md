Confirmed: `to_signable_string` in `lib/shopify_api/webhooks/request.rb` returns only `@raw_body`, while `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the HMAC-verified bytes.### Title
Webhook `shop` attribution is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the tenant identity (`shop`) that the framework hands to the app's `WebhookHandler` is read from an HTTP header that is never included in the signed bytes. This breaks the equality that should hold: `bytes verified by HMAC == bytes that determine which shop the event is attributed to`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the value from the `hmac`/`hmac-sha256` field [1](#0-0) . For webhooks, `Request#to_signable_string` returns **only** `@raw_body`, while `Request#shop` is parsed independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional binding check between the header and the signed body [3](#0-2) . `WebhookMetadata.shop` is the sole tenant identifier surfaced to the app's `WebhookHandler#handle` [4](#0-3) .

Because Shopify computes the HMAC purely as `HMAC-SHA256(client_secret, raw_body)` (this is mirrored exactly in this gem's own test helpers, which sign only the body: `OpenSSL::HMAC.hexdigest(Digest.new("sha256"), api_secret_key, "{}")` [5](#0-4) ), any actor who is a legitimate customer/merchant of the host application (i.e., an "unprivileged internet user" who signs up their own shop) will receive genuinely, validly-signed webhooks for their **own** shop. Since the shop attribution header is disjoint from the signed payload, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to point at a victim shop. `Registry.process`'s HMAC check still passes (it only checks the body/hmac pair), and the forged `shop` value is delivered straight into the handler as if Shopify itself reported the event for the victim tenant.

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately controls Shop A can cause the host application to process a webhook "as if" it originated from Shop B, with attacker-chosen (but validly-signed-for-Shop-A) body content. Any app logic keyed off `WebhookMetadata.shop` (e.g., updating billing state, toggling feature flags, processing `shop/redact` or `customers/data_request` compliance topics, marking uninstalls, or writing to a per-shop record identified by `data.shop`) can be manipulated cross-tenant without any credential belonging to the victim shop. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only becoming a legitimate installer/customer of the app (an unprivileged, self-service action — same threat model called out for the analog report), plus the ability to send an arbitrary HTTP request to the app's public webhook endpoint with a spoofed header. No access token, `client_secret`, or privileged account of the victim is needed, and no interception of TLS traffic is required, since the attacker's own genuinely-received webhook payload/HMAC pair is reused.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the HMAC-signed material, or otherwise cryptographically tie the shop attribution to the verified body — e.g., require the host application to independently confirm the derived `shop` against a value obtained from a trusted, previously-established session/install record before acting on `WebhookMetadata.shop`. At minimum, document prominently that `request.shop` is unauthenticated header data and must not be trusted for tenant-sensitive actions unless independently corroborated (e.g., cross-checked against the shop stored for the matching installed app record).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (self-service, unprivileged).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid HMAC over raw_body>`, and some `raw_body`.
3. Attacker captures `raw_body` and the valid `hmac` value (both are delivered to their own server/endpoint they control, or observable via any debug logging they set up).
4. Attacker crafts a new HTTP request to the same webhook endpoint with the identical `raw_body` and `shopify-hmac-sha256` value, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds (it only checks `raw_body`/`hmac`) [6](#0-5) , and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on the victim tenant using attacker-controlled body content.

          received_signature = verifiable_query.hmac
