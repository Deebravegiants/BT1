## Analysis

The reported bug class — an unprivileged user's pending transaction executing against parameters that silently changed between when the trade was decided and when it lands on-chain, with no protection value to bound the divergence — has a direct analog in `BandwidthManager.purchase()`.

### Root cause

`BandwidthManager.purchase()` reads the live `tierPrice[tier]` mapping at execution time and pulls exactly that computed amount from the buyer via `safeTransferFrom`, with no caller-supplied ceiling on cost: [1](#0-0) 

`tierPrice` is fully governance-mutable at any time via the `SetTiers` action in `onAccept`, applied unconditionally and immediately with no timelock or pending-purchase awareness: [2](#0-1) 

A buyer quotes the cost off-chain (as documented), approves the ERC-20 for that amount (or, commonly, a larger/infinite allowance to avoid repeated approvals for future top-ups), and submits `purchase(app, tier, months, chain)`. If a governance `SetTiers` update lands first (block reordering, gas-price congestion, or simply concurrent governance activity — no malicious actor required, just as the original SetToken-manager scenario needed no malicious actor), `tierPrice[tier]` can be higher by the time `purchase()` executes. Because `purchase()` has no `maxAmount`/`maxPrice` parameter, the buyer either:

- overpays silently (if their approval was for more than the quoted amount, e.g. a standing allowance), or
- reverts on `safeTransferFrom` due to insufficient allowance (if approval was exact) — a availability, but the overpay case is the fund-loss case.

This mirrors the report's core defect precisely: `BasicIssuanceModule.issue()`/`redeem()` read mutable `SetToken` state (components, `positionMultiplier`, `positionUnit`) live at execution with no caller-supplied bound, so a state change between submission and execution changes the economics of the trade without the user's consent. `BandwidthManager.purchase()` has the same shape: `tierPrice` is the mutable state, and there is no `maxAmount` guard.

### Title
Missing max-price guard in `BandwidthManager.purchase()` lets a mid-flight tier-price change overcharge the buyer - (File: `evm/src/apps/BandwidthManager.sol`)

### Summary
`BandwidthManager.purchase()` computes the fee-token cost from the live `tierPrice[tier]` value and pulls it via `safeTransferFrom`. There is no parameter allowing the caller to cap the amount they are willing to pay. Because `tierPrice` can be updated by governance's `SetTiers` message at any time with no delay, a purchase transaction signed/submitted against one quoted price can execute against a higher price if the `SetTiers` update lands first, silently overcharging the buyer whenever their ERC-20 approval exceeds the originally quoted amount.

### Finding Description
`purchase()` reads `tierPrice[tier]` at execution time (`evm/src/apps/BandwidthManager.sol:160`), scales it to the fee token's decimals, and transfers that amount from `msg.sender` (`evm/src/apps/BandwidthManager.sol:170`) — there is no upper bound supplied by the caller. `tierPrice` is set purely by inbound governance messages via `onAccept`'s `SetTiers` branch (`evm/src/apps/BandwidthManager.sol:213-219`), which overwrites the mapping unconditionally, with no cooldown, no pending-request check, and no interaction with in-flight `purchase()` calls. The documentation's own recommended purchase flow has the caller quote the price off-chain, then `approve()` the manager, then call `purchase()` — a two-step, non-atomic flow inherently exposed to a price change landing between the two steps [3](#0-2) . Any buyer who keeps a standing/looser approval (common to avoid re-approving before every top-up) pays whatever `tierPrice` happens to be at execution time, not the price they quoted.

### Impact Explanation
An unprivileged bandwidth purchaser can lose funds (overpay in the fee token) purely from ordinary governance price updates racing their transaction — no malicious actor is required, only the ordinary possibility of two independent transactions landing in an order the buyer did not anticipate. This is the same "no execution guard on mutable, externally-changeable state" defect class as the referenced report; the fix (a `maxAmount`/`maxPrice` parameter, analogous to `minSetTokens`/`maxComponentAmounts` in the report's remediation) is directly transferable.

### Likelihood Explanation
Requires only: (1) governance issuing a routine `SetTiers` price update (an expected, non-malicious operational event, since tier prices are explicitly designed to be adjustable), and (2) a buyer's `purchase()` transaction being pending in the same window with an approval large enough to cover the new, higher price. Given `purchase()` is documented as a standalone call intended to be reusable across top-ups (implying non-minimal approvals in practice), and price changes are a normal governance operation, the timing collision is plausible without any adversarial coordination.

### Recommendation
Add a caller-supplied `maxAmount` (or `maxPrice18d`) parameter to `purchase()` and revert if the computed cost from the live `tierPrice` exceeds it, mirroring standard slippage-protection patterns:
```solidity
function purchase(
    bytes calldata app,
    uint256 tier,
    uint256 months,
    bytes calldata chain,
    uint256 maxAmount
) external returns (bytes32 commitment) {
    ...
    uint256 amount = total18d / scale;
    if (amount > maxAmount) revert PriceExceedsMax();
    ...
}
```

### Proof of Concept
1. Governance configures `tierPrice[TIER1] = 1e18` (1 token, 18-decimal).
2. Buyer quotes cost off-chain via `tierPrice(TIER1)`, approves the manager for that amount plus buffer for future top-ups (or an unlimited approval, as is common), and submits `purchase(APP, TIER1, 1, CHAIN)`.
3. Before the buyer's transaction is mined, a `SetTiers` governance message updates `tierPrice[TIER1]` to, e.g., `5e18` via `onAccept` (`evm/src/apps/BandwidthManager.sol:213-219`).
4. The buyer's `purchase()` transaction executes against the new price: `total18d = 5e18 * 1`, and `safeTransferFrom` pulls 5x the amount the buyer intended to pay, succeeding silently because the approval covers it. No revert, no user consent for the new price — `evm/src/apps/BandwidthManager.sol:153-171`.
