### Title
Zap's LT mint/redeem calls pass `minOut = 0` and `minBase = 0`, deferring slippage protection to a mismatched downstream check - (File: packages/contracts/src/Zap.sol)

### Summary
`Zap._executeBuy` and `Zap._sellInternal` call the external BounceTech `IBounceLeveragedToken.mint`/`redeem` functions with the slippage-protection argument hardcoded to `0`, exactly the anti-pattern described in the report (`min_dy`/`but_expected` always `0`). Downstream checks exist, but they validate the *net* trade output (`tokensOut`, `usdcOut`), not the mint/redeem leg itself, and use a stale on-chain `exchangeRate()` rather than the actual realized amount for the buy-side pre-check.

### Finding Description
In `_executeBuy`, both branches call BounceTech's `mint` with `minOut = 0`: [1](#0-0) [2](#0-1) 

In `_sellInternal`, `redeem` is likewise called with `minBase = 0`: [3](#0-2) 

The `IBounceLeveragedToken` interface explicitly defines these as slippage-protection parameters (`minOut` for `mint`, `minBase` for `redeem`): [4](#0-3) 

The only protections that exist afterward are:
- Buy side: a check that the *estimated* mint result (`ltIfFull`, computed from `baseToLtAmount`, a view function reflecting `exchangeRate()` at call time) matches expectations only implicitly through the final `tokensOut < minTokensOut` check in `_buyInternal`. There is no direct comparison against the actual `ltMinted` return value from `mint`.
- Sell side: after `redeem` returns, the code computes `grossUsdcEstimate` from `ltReceived * exchangeRate()` *before* calling redeem for the `BelowMinAmount` check, then separately checks `usdcOut < minUsdcOut` against the actual `grossUsdc` returned by `redeem`. This final check does bound the ultimate USDC handed to the user, so a pure sandwich against `redeem`'s internal exchange rate is bounded by the user's own `minUsdcOut`.

The buy path is weaker: on the curve-buy branch (`isGraduated == false`), `ltMinted` from BounceTech's `mint(..., 0)` is used to size the subsequent `Bonding.buy` call, and any `mint`-side price manipulation (e.g., BounceTech LT's `exchangeRate` being manipulable by a third party interacting with the LT contract directly, if such a path exists) would only be caught indirectly through the final `tokensOut < minTokensOut` on the curve output, not through a direct check on how much LT was actually minted for the USDC paid.

### Impact Explanation
If BounceTech's LT `mint`/`redeem` pricing can be manipulated within the same block by an unrelated third party (e.g., another BounceTech LT depositor/withdrawer, or the LT's own streaming-fee checkpoint logic), a user's `Zap.buy`/`sell` could mint less LT per USDC or redeem less USDC per LT than expected, with the `minOut`/`minBase` guard on the BounceTech call itself providing no defense — the loss can only be caught by the outer `minTokensOut`/`minUsdcOut` checks, which most callers set loosely to avoid reverts. This could allow value extraction from Zap users on the LT mint/redeem leg specifically, distinct from the AMM curve swap (which is protected by `Bonding.buy/sell`'s own `amountOutMin`).

### Likelihood Explanation
This requires the externally-controlled BounceTech LT contract's `mint`/`redeem` pricing to be atomically manipulable by a third party within the same transaction/block as the Zap call — a property of the LT contract, not of code in scope here. I could not verify from the in-scope contracts whether BounceTech's `exchangeRate()`/`mint`/`redeem` is vulnerable to such manipulation (its source is external, referenced only via interface and mocks). The `packages/contracts/AGENTS.md` documentation notes BounceTech's mint-pause and redemption-fee behavior but not any transient-price-manipulation risk, and the mock (`MockLeveragedToken.sol`) is not proof of the real contract's behavior.

### Recommendation
Pass a real `minOut`/`minBase` to `IBounceLeveragedToken.mint`/`redeem` derived from the on-chain `exchangeRate()` (or the caller-supplied `minTokensOut`/`minUsdcOut`, converted through the mint/redeem legs) instead of `0`, so the BounceTech call itself reverts on adverse pricing rather than relying solely on the end-to-end `SlippageExceeded` check in `_buyInternal`/`_sellInternal`.

### Proof of Concept
Not constructible from in-scope code alone: exploiting this requires demonstrating that BounceTech's `LeveragedToken.mint`/`redeem` exchange rate can be moved atomically by a third party between quote and execution inside `Zap._executeBuy`/`_sellInternal`. That contract is out of scope (`packages/contracts/src/interfaces/IBounceLeveragedToken.sol` only declares the interface; the real implementation lives in BounceTech's own repository), so I cannot confirm or rule out real-world exploitability with the tools available here — this should be validated against BounceTech's actual `LeveragedToken.sol` before treating it as a confirmed, actionable finding.
