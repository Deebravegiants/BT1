### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are taken directly from unauthenticated HTTP headers and handed to the app's handler as the identity of the tenant/event — are never included in the signed material. An attacker who can obtain any one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` (e.g., by triggering a webhook delivery from their own, legitimately installed shop) can replay that exact body/HMAC pair to the app's webhook endpoint while forging the `shopify-shop-domain` and `shopify-topic` headers to name an arbitrary victim shop and topic. The HMAC check passes because it only verifies the body, and the app's handler is invoked believing the event genuinely originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` define what is authenticated for a webhook request: [1](#0-0) [1](#0-0) 

`to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from request headers with no cryptographic binding to the body.

`ShopifyAPI::Webhooks::Registry.process` uses this to authenticate and then dispatch the event: [2](#0-1) 

`Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the `hmac` field using constant-time comparison: [3](#0-2) 

Because only the body is hashed, the equality the code actually enforces is:
`HMAC(api_secret_key, raw_body)` == `header["hmac-sha256"]`

but the code *acts* on a different, unauthenticated equality:
`request.shop` (from `shopify-shop-domain` header) == "the shop this event is attributed to"

These two are never tied together. Any attacker who can generate one legitimately-signed `(raw_body, hmac)` pair — trivial for any merchant who installs the app on their own store and triggers a webhook (e.g., updates an order, product, etc., with attacker-chosen field values) — can capture that pair and resend it to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a different, victim shop's domain, and/or with a different `shopify-topic` header. `HmacValidator.validate` still returns `true`, and `Registry.process` calls the topic handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` — i.e., attacker-controlled tenant identity and attacker-crafted body, passed off as an authentic event from the victim shop.

This is directly analogous to the OpenVM finding: just as the recursive verifier trusted public values from an AIR without confirming there was exactly one authoritative instance bound to those values, this gem trusts the `shop`/`topic` identity fields without binding them into the value that was actually cryptographically verified (the body).

### Impact Explanation
Any app that keys business logic (e.g., "update the order for shop X", "revoke subscription for shop Y", "sync inventory for shop Z") off `WebhookMetadata#shop` is exposed to cross-tenant forgery: an attacker who controls one shop can forge events purportedly from any other shop, using body content they crafted in their own store. Depending on the handler, this can lead to unauthorized cross-tenant data mutation, cache/state poisoning, or triggering privileged internal workflows (e.g., `app/uninstalled`, `shop/redact`, plan-change webhooks) for a victim shop the attacker does not control — a cross-tenant access issue.

### Likelihood Explanation
High for any app using this gem's webhook `Registry`/`Request` implementation as documented. The only prerequisite is the ability to generate one valid signed webhook from any shop that has installed the app — something any unprivileged internet user can do by installing a public app on their own development/trial store and performing an action that fires a webhook. No access to the app's `client_secret`, access tokens, or privileged accounts is required.

### Recommendation
Bind the identity fields into the authenticated value. At minimum, `Webhooks::Request#to_signable_string` (or the validation step in `Registry.process`) should incorporate `shop`, `topic`, and `webhook_id` into the HMAC-verified material (Shopify already signs webhook delivery via headers separate from body, so the gem should authenticate the full header set it relies on, not just the raw body), or the registry should independently authenticate/attest the shop domain (e.g., cross-check it against a known/registered shop for that webhook subscription) before invoking the handler with that shop identity.
