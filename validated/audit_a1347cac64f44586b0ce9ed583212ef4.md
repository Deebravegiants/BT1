## Analysis

The reported bug class is about an attacker breaking an identity-binding invariant: a field that is *acted on* by the code but not *covered* by the HMAC that is supposed to authenticate the request. Searching the analogous surface of this gem (`lib/shopify_api/webhooks/**` and `lib/shopify_api/utils/hmac_validator.rb`), I found this exact pattern in webhook processing.

`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

But `shop` (the tenant identifier) is read straight from an HTTP header and is never part of the signed material:

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`HmacValidator.validate` only checks the HMAC over `to_signable_string` (i.e., the body) against `Context.api_secret_key`:

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

`Registry.process` validates only that HMAC, then forwards the **unauthenticated** `request.shop` value straight into the tenant-scoped handler payload:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

### Why this matches the identity-binding break

The equality that should hold is: `shop_the_HMAC_was_issued_for == shop_passed_to_the_handler`. In this gem, the left side doesn't exist at all — the HMAC secret (`Context.api_secret_key`) is the **app's own client secret**, shared across every shop that has installed the app, and the signed bytes are only the JSON body. `shop` is carried in a plain, unsigned header.

Because Shopify's webhook HMAC secret is per-app (not per-shop), any unprivileged user who installs the app on their own store legitimately receives genuinely-signed webhooks from Shopify. They can then replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` hands the handler a `WebhookMetadata` claiming to be from the victim shop with attacker-chosen body content.

This is a genuine, reachable analog of the reported bug class ("a field acted on but not covered by the HMAC") and crosses a tenant boundary, matching the required Critical impact category (cross-tenant access) without needing any credential the app owner controls.

### Title
Webhook `shop` identity is not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop` value used by `ShopifyAPI::Webhooks::Registry.process` to build `WebhookMetadata` is read from an unsigned header. Because Shopify signs webhooks with the app's single shared `api_secret_key` (not a per-shop key), any unprivileged user who installs the app on their own shop can obtain a validly-signed `(body, hmac)` pair and replay it to the app's webhook endpoint with the `shop` header rewritten to a victim shop's domain, producing a `WebhookMetadata` object that falsely claims to originate from the victim tenant.

### Finding Description
- `Request#hmac`/`#to_signable_string` bind the signature exclusively to `@raw_body` [5](#0-4) .
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all taken from headers that are never included in the signed string [6](#0-5) .
- `HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely from `to_signable_string`, i.e. the body [7](#0-6) .
- `Registry.process` treats a passing `HmacValidator.validate(request)` as proof of authenticity for the whole request, then trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` delivered to the app's handler [4](#0-3) .

Because Shopify apps use one `api_secret_key` for all installations, any store owner (an unprivileged internet user relative to other merchants) who installs the app receives real, validly-HMAC'd webhooks for their own body content. They can then send that exact `(body, hmac)` to the same endpoint but with the `shop-domain` header changed to any other shop the app serves. The `shop` value has no cryptographic tie to the signature, so the forged request passes `HmacValidator.validate` and is delivered to the handler as if it truly originated from the victim shop.

### Impact Explanation
This breaks the equality `authenticated_shop == shop_delivered_to_handler`, letting a low-privilege attacker (any merchant who installs the app) inject webhook events attributed to an arbitrary victim shop into the host application's per-tenant business logic (e.g., order/customer/app-uninstalled processing keyed by `data.shop`). Depending on what the host app does with `WebhookMetadata#shop` (data writes, cache keys, triggering per-shop side effects), this is a cross-tenant integrity/confidentiality issue — satisfying the "cross-tenant access" Critical criterion, since the tenant identity binding the gem is supposed to guarantee via HMAC verification does not actually cover the `shop` field.

### Likelihood Explanation
Likelihood is high for any app that keys business logic off `WebhookMetadata#shop`: the only prerequisite is installing the target app on a store the attacker controls (free, requires no special access, social engineering, or leaked secrets), capturing one legitimate webhook, and replaying it with a modified header — all doable with a simple HTTP client.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed material, or otherwise cryptographically bind the `shop` header to the HMAC-validated payload before constructing `WebhookMetadata`. Where that isn't possible (Shopify signs only the body by design), the gem should document/require that consuming apps independently verify `WebhookMetadata#shop` corresponds to a shop with an active, previously-established session/installation record before acting on the payload, and `Registry.process` should surface this as an explicit contract rather than implicitly trusting the header once HMAC validation of the body succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, registering for a webhook topic the app is subscribed to.
2. Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid_hmac_of_body>`, and some JSON body.
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker sends a new HTTP request to the same webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the shared `api_secret_key` — it passes [8](#0-7) .
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-chosen JSON>, ...)`, and the host app processes it as a genuine event from the victim shop [9](#0-8) .
