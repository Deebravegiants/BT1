### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing HMAC-valid webhook replay to be attributed to an arbitrary shop - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signable content from the raw request body only, while the `shop` (and `topic`) values that the app treats as the authenticated tenant identity are read from separate HTTP headers that are not part of the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then blindly forwards `request.shop` to the app's `WebhookHandler` as trusted tenant metadata, without that value ever having been bound to the signature.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` and `Request#topic` are populated from the `x-shopify-shop-domain` / `shopify-shop-domain` headers, which are never included in `to_signable_string`: [2](#0-1) 

`Registry.process` only validates the HMAC of the body via `Utils::HmacValidator.validate(request)` and then constructs `WebhookMetadata` using `request.shop` and `request.topic` directly, treating them as verified: [3](#0-2) 

`WebhookMetadata` carries `shop` as a plain, trusted `String` field consumed by the host app's `WebhookHandler#handle`: [4](#0-3) 

The `HmacValidator.validate` call only recomputes and compares the HMAC over `to_signable_string` (i.e., the raw body) against the secret key — it says nothing about which shop or topic header accompanied that body: [5](#0-4) 

**Identity binding broken (as an equality):**
`shop_header_used_by_handler == shop_bound_by_hmac_signature` is **not enforced** — the gem only proves `raw_body` is authentic; it never proves that the accompanying `shop-domain` header is the one Shopify actually signed for. Since the HMAC scheme signs only the body, any legitimate webhook body+HMAC pair captured for shop A (e.g., a merchant installed on the app receiving their own genuine webhooks) remains HMAC-valid when replayed to the same app endpoint with the `shop-domain` header rewritten to shop B. `HmacValidator.validate` returns `true` in both cases because the signature never covered the shop header, so `Registry.process` hands the handler `WebhookMetadata(shop: "B", body: <A's data>)` as if it were an authenticated event for shop B — a cross-tenant binding failure.

### Impact Explanation
This breaks the tenant boundary that `WebhookHandler` implementations rely on: the gem asserts (via passing HMAC-verified `WebhookMetadata`) that `data.shop` is the authenticated origin of `data.body`, but that assertion is false. An attacker with access to their own valid, HMAC-signed webhook (which is easy to obtain by installing the app to their own store) can replay the identical raw body to the app's webhook endpoint while substituting the `shop-domain` header of a victim store. Any host application logic that trusts `data.shop` for tenant-scoped writes (e.g., "update order status for shop X" or "process customer redact/data for shop X") will act on the victim tenant using attacker-controlled body content, i.e., cross-tenant access/data corruption through this gem's own webhook processing API.

### Likelihood Explanation
Likelihood is Low: it requires the attacker to already have a valid app installation (thus their own genuine HMAC-signed webhook) and the ability to send a forged HTTP request directly to the app's public webhook endpoint with a modified header, which the gem's `Request`/`Registry` layer does nothing to prevent since headers are never authenticated. No credentials of the target shop or the app's `client_secret` are needed by the attacker — only a legitimate webhook they themselves received.

### Recommendation
Bind the `shop` (and `topic`) values into the signed payload used for HMAC verification, or otherwise cryptographically tie the header-derived tenant identity to the signature before it is passed to `WebhookHandler#handle`. Short term, `Utils::HmacValidator.validate` (or a new check in `Registry.process`) should verify that the `shop-domain`/`topic` headers match values independently confirmed for the request (e.g., cross-check against the registered webhook subscription / shop that is expected to receive this topic) rather than trusting the raw header. Document clearly in `docs/usage/webhooks.md` that `data.shop` is not itself HMAC-protected so host apps do not assume it is authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a real webhook: raw body `B` with header `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over `B` with the app's `client_secret`.
2. Attacker resends the exact same raw body `B` and the exact same `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: <unchanged>...})` is constructed successfully.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only — passes, since `B` and the HMAC are unmodified. [6](#0-5) 
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` is invoked — the host app's handler now processes attacker-controlled data `B` under the identity of `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
