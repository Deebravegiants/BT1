## Analysis

The OXID bug (CVE-2015-6926) is a classic CWE-287 case: an authentication token carried an identity claim (the email) that the verifier trusted without cryptographically binding it to the specific session/context it was issued for, letting an attacker replay/craft a token to impersonate any user.

The closest reachable analog in this codebase is the calldata-authorization scheme in the `hyper-fungible-token` pallet's ISMP module handler, which lets an unprivileged relayer/dispatcher deliver a cross-chain token message that executes an arbitrary runtime call "as" the token recipient, based on a signature that is not bound to the specific message/chain context it is used in. [1](#0-0) 

### Title
Unbound signature domain in `hyper-fungible-token::on_accept` allows cross-message/cross-instance replay of a beneficiary's authorization, letting an attacker dispatch runtime calls under the victim's identity - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` (the `IsmpModule` handler invoked by `pallet-ismp` on any inbound POST request from a registered token bridge contract) optionally dispatches an arbitrary `T::RuntimeCall` under `RawOrigin::Signed(beneficiary)` if the message's calldata carries a signature. That signature only covers `(nonce, runtime_call)` — it omits the destination chain/state-machine, the source, the local asset id, or any pallet/instance identifier. [2](#0-1) 

Because the signed payload has no domain separator tying it to a particular incoming message, asset, or pallet instance, any relayer/dispatcher who obtains a validly-signed `(nonce, call)` pair from a user — e.g. observed off-chain, or intended for a different bridging instance/asset/message — can embed it into an entirely different, attacker-controlled incoming token transfer (attacker picks `source`, `amount`, timing) that reaches `on_accept` and have it dispatch that call under the user's identity, as long as the user's current on-chain nonce still matches. This mirrors the OXID flaw: the "identity assertion" (signature) is accepted without being scoped to the transaction/session it was actually meant to authorize.

Contrast this with the sibling `pallet-ismp-relayer` code, which explicitly includes `state_machine` in every signed payload precisely to prevent this class of cross-chain replay: [3](#0-2) [4](#0-3) 

### Finding Description
`on_accept` decodes the ABI-encoded `Message` from an inbound `PostRequest` after checking `ContractToAsset::<T>::get(source, &from)` — this only authenticates that the *token contract* is a registered peer for that chain, not anything about the `data` payload's runtime call or its authorization. [5](#0-4) 

If `message.data` is non-empty and carries a `SubstrateCalldata` with a `signature`, the pallet:
1. Reads `beneficiary`'s current `frame_system` nonce.
2. Builds `msg = keccak256(scale_encode(nonce, runtime_call))`.
3. Verifies the signature against `beneficiary`'s public key using this bare `msg`.
4. On success, dispatches `runtime_call` with `RawOrigin::Signed(beneficiary)`. [6](#0-5) 

No part of the signed payload binds it to: the specific state machine/source chain the request came from, the specific `local_asset_id`/contract instance, the request commitment, or any pallet-specific domain tag. `frame_system::account_nonce` is a chain-wide counter shared with the account's ordinary extrinsics and with any other pallet instance of this token bridge that might exist on the same runtime, so a signature the beneficiary produced for one bridging context (one asset, one incoming transfer, potentially one destination parachain) remains valid for replay through *any other* incoming message that reaches this same `on_accept` handler while the nonce still matches — and delivery, `source`, and `amount` in that other message are entirely attacker/relayer controlled, since anyone can dispatch a bridging POST request from a registered peer contract by burning even a trivial amount of tokens.

### Impact Explanation
An attacker (any unprivileged bridge user/relayer able to submit a burn-and-send transaction from a registered `HyperFungibleToken` peer contract) who obtains a user's signature over `(nonce, runtime_call)` — intended for a specific, legitimate transfer — can front-run or repackage it into their own incoming message and have the pallet dispatch that call under `RawOrigin::Signed(victim)` in a context the victim did not intend (different asset/source/amount/timing). This is an "unauthorized app action": arbitrary dispatchable execution as another account without a properly scoped authorization, directly matching the impersonation pattern (identity accepted without binding to session/context) called out in the reference vulnerability.

### Likelihood Explanation
Exploitation requires the attacker to observe or otherwise obtain a validly-signed `(nonce, call)` tuple from the target — which is plausible since such signatures must be transmitted through relayers/calldata to be delivered at all, making them observable in the message-preparation flow before final on-chain inclusion. Given the wide reach of `on_accept` (any registered peer contract, any relayer) and low cost of dispatching a qualifying incoming message, likelihood is moderate.

### Recommendation
Include a domain separator in the signed payload: at minimum the local pallet/asset identifier (`local_asset_id`), the `source` state machine, and ideally the ISMP request commitment/hash, e.g. `keccak256(scale_encode(nonce, local_asset_id, source, runtime_call))`. This scopes each authorization to the exact incoming message it was created for, matching the pattern already used in `pallet-ismp-relayer`'s `beneficiary_message`/withdrawal signing.

### Proof of Concept
1. Victim signs `(nonce=N, call=C)` off-chain intending it to authorize `runtime_call C` via a specific legitimate `HyperFungibleToken` transfer (asset A, source chain S1), and hands the signature to a relayer/dApp to embed in `message.data`.
2. Attacker observes this signed payload (it must be transmitted in cleartext to be delivered) before it lands on-chain.
3. Attacker independently burns a trivial amount of a *different* registered `HyperFungibleToken` peer contract (asset B, or same asset from a different source chain S2) with `to = victim`, embedding the *same* `(runtime_call=C, signature)` in `message.data`.
4. If this message is delivered to `on_accept` first (attacker can race/front-run), the victim's nonce still equals N; the ECDSA/Ed25519/Sr25519 check in `module.rs` passes and `runtime_call C` is dispatched as `RawOrigin::Signed(victim)` — in a context (asset/source/amount) the victim never authorized.
