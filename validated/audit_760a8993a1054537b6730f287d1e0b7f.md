### Title
Unconditional Uniswap V2 swap in `EvmHost.dispatch()` DoSes all native-fee-paying message dispatches - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` unconditionally calls out to a third-party AMM (`IUniswapV2Router02.swapETHForExactTokens`) whenever a caller pays the relayer fee with native token. If that external market cannot service the swap — depleted/removed liquidity, a router that reverts, or a pair that no longer exists for the configured `feeToken()` — the entire `dispatch()` call reverts, bricking every app's native-fee dispatch path on that host. This mirrors the `StakedEXA::harvest()` pattern: a critical, otherwise-independent operation (dispatching a message) is made to depend on the live state of an external market with no pre-check or fallback, so a change in that external market's state DoSes users who have nothing to do with it.

### Finding Description
`dispatch()` is the single dispatch entrypoint used by every app built on `EvmHost` — `HyperFungibleToken.send()`, `WrappedHyperFungibleToken.send()`, `IntentGatewayV2`, `BandwidthManager.purchase()`, `HyperbridgeLzEndpoint.send()`, etc. — whenever they forward `msg.value` for fee payment instead of pulling `feeToken()` directly: [1](#0-0) 

The `msg.value > 0` branch performs an unconditional external call:
```
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)
```
There is no precondition check (e.g., verifying the pair exists, has sufficient reserves, or that the router is not paused/deprecated) before making this call, and no fallback to the `feeToken()`-pull path if the swap is unavailable. `notFrozen` only guards the host's *own* freeze flag; it does nothing about the health of the external Uniswap V2 pool the host depends on for this code path.

Every app-level `send()`/`purchase()` function that optionally accepts native payment forwards straight into this same unconditional call, e.g.: [2](#0-1) [3](#0-2) 

This is structurally the same bug class as the `StakedEXA::harvest()` report: a core, frequently-invoked function (`dispatch`, analogous to `deposit`) unconditionally reaches into an independent external market (Uniswap V2, analogous to the `Market` contract) whose availability it does not control, with no guard, so a change external to Hyperbridge's own admin/governance (thin liquidity, a compromised/paused router, a removed pair, or even just the pair's owner draining liquidity) reverts the dispatch and blocks users who have no relation to that liquidity pool.

### Impact Explanation
Any unprivileged caller of `dispatch()` (directly or via any `HyperApp`-based application) who pays the relayer fee with native `msg.value` is unconditionally routed through the WETH/feeToken Uniswap V2 pair. If that pair's liquidity is drained, the pair does not exist, or the router reverts for any external reason, `swapETHForExactTokens` reverts and the *entire* dispatch reverts — the message is never emitted/committed, no commitment is stored, and the relayer fee funds are not consumed. This freezes the native-fee dispatch path for every app on that `EvmHost` instance until the pool/router is restored or the host owner reconfigures `_hostParams.uniswapV2`/`feeToken`, causing message-delivery failure (a "route unable to deliver messages") for anyone using native payment, and loss of intended cross-chain functionality (bandwidth purchases, HFT sends, intent-gateway dispatches, LZ endpoint messages) during the outage.

### Likelihood Explanation
Liquidity for a specific WETH/feeToken Uniswap V2 pair thinning out, being fully withdrawn by LPs, or the pair simply not existing at some chain deployment is a realistic, externally-triggerable condition that Hyperbridge does not control — exactly the "external market frozen/paused" precondition from the source report. Any dispatcher opting to pay with native value (a common, documented payment mode per `IDispatcher`/`dispatch` docs) can trigger the failure without any special privilege; no attacker action against Hyperbridge itself is required, only ordinary AMM liquidity dynamics on the configured router.

### Recommendation
Before attempting the swap, validate that the swap is feasible (e.g., quote via `getAmountsIn`/`getReserves` and confirm sufficient output/liquidity, or wrap the swap call in `try/catch`) and provide a defined fallback (e.g., revert with a clear, specific error distinguishing "swap unavailable" from generic failure, or allow the caller to fall back to paying with `feeToken()` directly) rather than letting an opaque low-level revert from a third-party AMM propagate and block the entire dispatch path.

### Proof of Concept
1. Deploy `EvmHost` with `_hostParams.uniswapV2` pointed at a real (or mock) Uniswap V2 router/pair for `WETH -> feeToken()`.
2. Drain the pair's liquidity (or deploy a router that always reverts on `swapETHForExactTokens`, simulating an external market outage).
3. Call any app's native-fee send path, e.g. `HyperFungibleToken.send{value: fee}(params)` (which calls `IDispatcher(_host).dispatch{value: msg.value}(request)`), or call `EvmHost.dispatch{value: fee}(post)` directly.
4. Observe the transaction reverts inside `swapETHForExactTokens`, and no `PostRequestEvent` is emitted and no commitment is recorded — the message is never dispatched, even though the caller and the destination app are fully unrelated to the drained liquidity pool.

        if (msg.value > 0) {

            path[0] = IUniswapV2Router02(uniswapV2).WETH();

            );

        }
