### Title
Unchecked `U128 -> u64` truncation via `.as_u64()` in `swap_token_amount_base_out` fee scaling allows draining pool reserves for near-zero input - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_swap_base_out` / `process_swap_base_out_v2` compute the required input amount for a `SwapBaseOut`/`SwapBaseOutV2` trade using 128-bit arithmetic, then narrow the final result to `u64` with a raw `.as_u64()` call instead of the codebase's own checked conversion helper `Calculator::to_u64`. Because `U128::as_u64()` (from the `uint` crate) silently returns only the low 64 bits with no overflow check, an attacker can choose `amount_out` such that the true required input exceeds `u64::MAX`, causing the computed `swap_in_after_add_fee` to wrap to an attacker-controlled, arbitrarily small value. All downstream slippage/balance checks and the actual SPL token transfer then use this wrapped value, letting the attacker pay a tiny amount of tokens while withdrawing almost the entire opposite-side reserve.

### Finding Description
`Calculator::swap_token_amount_base_out` (the constant-product "solve for input" formula) is computed entirely in `U128`: [1](#0-0) 

For the `Coin2PC` direction, `amount_in = total_coin * amount_out / (total_pc - amount_out)`. By choosing `amount_out` close to `total_pc_without_take_pnl` (e.g. `total_pc - 1`), the denominator shrinks to `1`, and `amount_in` becomes `total_coin * amount_out`, a product that easily exceeds `u64::MAX` (~1.8e19) even for pools with modest reserves, while still fitting comfortably inside `U128`.

Back in the processor, this large `U128` value is fed through fee scaling and then truncated with an unchecked `.as_u64()`: [2](#0-1) [3](#0-2) 

Unlike this raw `.as_u64()`, the same file defines a checked conversion helper that is used elsewhere in the math module: [4](#0-3) 

`.as_u64()` on the `uint` crate's `U128` simply returns the low 64 bits of the value (equivalent to `value % 2^64`), with no panic or error — this is the exact "unsafe narrowing cast" bug class described in the report (unchecked `uint256 -> uint128`), just materialized here as an unchecked `U128 -> u64` truncation.

The wrapped, attacker-shrunk `swap_in_after_add_fee` is then used both for the slippage/balance checks and for the actual token transfer amount: [5](#0-4) [6](#0-5) 

Note the asymmetry: the source-side transfer moves only the truncated `swap_in_after_add_fee`, while the destination-side transfer moves the full, attacker-chosen `swap.amount_out`: [7](#0-6) 

The only earlier guard is `if swap.amount_out >= total_pc_without_take_pnl { return Err(InsufficientFunds) }`, which merely enforces `amount_out < total_pc`, allowing the attacker to set `amount_out = total_pc - 1` and drive the denominator to `1`. No check anywhere verifies that the "true" (unwrapped) `amount_in` fits within `u64` before it is truncated.

### Impact Explanation
An unprivileged swapper submitting a single `SwapBaseOut` or `SwapBaseOutV2` transaction with a crafted `amount_out` can make the program believe only a negligible/attacker-chosen amount of the input token is required, while still withdrawing close to the full reserve of the output token. This is a direct theft of LP/pool funds and results in insolvent pool accounting, since the pool's `k`-invariant based accounting (and `total_*_without_take_pnl` bookkeeping) is bypassed by the wrapped value. This meets the "concrete theft of user or LP funds" bar for a valid finding.

### Likelihood Explanation
Reachable by any unprivileged account in one transaction: the caller only needs to control the `SwapInstructionBaseOut`/`SwapBaseOutV2` instruction data (`max_amount_in`, `amount_out`) and hold a small balance of the source token (the truncated value can be engineered to be small, even near-zero, by choosing `amount_out` appropriately, since the attacker can compute the exact `U128` result offline and pick an `amount_out` whose wrapped remainder is minimal and nonzero). No special privileges, non-default configuration, or off-chain assumptions are required — only that the pool's `total_coin_without_take_pnl * amount_out` product exceeds `2^64`, which is realistic for most active pools.

### Recommendation
Replace the raw `.as_u64()` calls used for `swap_in_after_add_fee` (and any other `U128` value derived from `swap_token_amount_base_out`) with the existing checked helper `Calculator::to_u64`, which uses `try_into` and returns an error on overflow instead of silently truncating: [8](#0-7) 
This ensures the swap fails safely (`AmmError::ConversionFailure`) instead of wrapping to an attacker-controlled small value whenever the computed input amount cannot be represented in `u64`.

### Proof of Concept
1. Identify or create a pool where `total_coin_without_take_pnl` and `total_pc_without_take_pnl` are large enough that `total_coin_without_take_pnl * (total_pc_without_take_pnl - 1) > 2^64` (true for essentially any pool with non-trivial reserves given typical token decimals).
2. Attacker computes, off-chain, the exact `U128` result of `Calculator::swap_token_amount_base_out(amount_out, total_pc, total_coin, Coin2PC)` for `amount_out = total_pc_without_take_pnl - 1`, then applies the same fee-scaling formula used in `process_swap_base_out_v2` (`* swap_fee_denominator / (swap_fee_denominator - swap_fee_numerator)`, ceiling), and reduces mod `2^64` to know the exact truncated `swap_in_after_add_fee` value that will result.
3. Attacker submits `SwapBaseOutV2` with:
   - `amount_out = total_pc_without_take_pnl - 1`
   - `max_amount_in` set to (or above) the pre-computed truncated value
   - source token account funded with only that small truncated amount
4. `process_swap_base_out_v2` computes `swap_in_after_add_fee` via the vulnerable `.as_u64()` truncation at [9](#0-8) , passes the `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` checks at [5](#0-4) , then transfers only the tiny truncated amount from the attacker while sending almost the entire `total_pc_without_take_pnl` reserve to the attacker's destination account at [7](#0-6) , draining the pool.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
```
