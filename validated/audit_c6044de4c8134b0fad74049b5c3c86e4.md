### Title
Webhook HMAC signature covers only the raw body, not the `shop-domain`/`topic` headers, allowing shop-identity forgery in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) directly from unauthenticated HTTP headers, while the HMAC that `ShopifyAPI::Webhooks::Registry.process` validates is computed only over the raw request body. The equality the code relies on — "HMAC-verified bytes == bytes acted upon" — is broken: the verified bytes are `raw_body` only, but the bytes acted upon (and handed to the host app's handler as the tenant key) include the `shop-domain` header, which is never covered by the signature.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the `VerifiableQuery` implementation: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `#hmac` and `#shop` are both pulled from separate, unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) as the tenant identifier passed to the app's handler: [3](#0-2) 

By contrast, the OAuth callback's `AuthQuery` (also a `VerifiableQuery`) includes `shop` inside the signed payload itself, so the shop cannot be swapped without invalidating the HMAC: [4](#0-3) 

Because the webhook `shop` header sits outside the HMAC's coverage, anyone who can obtain one genuine `(raw_body, hmac)` pair signed with the app's shared secret — for example a merchant who has installed the app on their own store and receives a legitimately signed webhook delivery — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Utils::HmacValidator.validate` still returns `true` (it only checks `raw_body` against the secret), yet `Registry.process` reports the forged `shop` value to the handler as the authoritative tenant for that payload.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to the host application: HMAC-verified webhook == webhook genuinely originating for the reported shop. A host app that uses `WebhookMetadata#shop` to route/store data per-tenant (the documented and intended usage) can be made to associate one shop's data/events with a different shop's identifier, i.e. cross-tenant data injection/corruption, purely by an actor who controls webhook traffic for any single shop using the same app instance.

### Likelihood Explanation
Any merchant/developer able to install the target app on a shop they control can trivially capture a legitimately HMAC-signed webhook body for that shop (webhooks are delivered over plain HTTP(S) to the app's public endpoint, and the shared secret is not required to observe body+HMAC pairs of one's own traffic). Replaying that pair with a different `shop-domain` header against the same public endpoint requires no credentials beyond internet access to the app's webhook URL, making this a low-effort, standing vulnerability class for any multi-tenant deployment of this gem.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind the header values to the signed body (e.g., by validating that the shop domain in the header matches a shop already known to have installed the app for the delivered `webhook_id`/topic combination, and/or by having `to_signable_string` incorporate the header values the same way `AuthQuery` incorporates `shop` into its signable string).

### Proof of Concept
1. App developer installs the app on `attacker-shop.myshopify.com`; a webhook (e.g. `orders/create`) fires with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC only over `B` (per `Webhooks::Request#to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`) — it passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now returns `"victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop`, demonstrating the identity-binding break.
