### Title
Decimal-mismatch scaling bug in `pallet-hyper-fungible-token`'s `convert_to_balance`/`convert_to_erc20` mints/credits the wrong amount when local decimals exceed the registered ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` scales cross-chain token amounts between the local substrate asset's decimals and the remote EVM contract's decimals using `convert_to_balance`/`convert_to_erc20`. Both helpers assume `erc_decimals >= local_decimals` and compute the scaling exponent with `erc_decimals.saturating_sub(local_decimals)`, which silently clamps to `0` (i.e. no scaling at all) whenever that assumption does not hold, instead of scaling in the opposite direction or rejecting the conversion. The invariant is only checked once, at `register_token`/`update_token` time, against the *current* value of `local_decimals`; it is never re-validated when the pallet later reads live decimals from `T::Assets` on every `send`, `on_accept`, and `on_timeout` call.

### Finding Description
The scaling helpers are: [1](#0-0) 

`convert_to_balance` divides the incoming ERC20 `U256` value by `10^(erc_decimals - local_decimals)`, and `convert_to_erc20` multiplies the local balance by the same exponent — both using `saturating_sub`, which returns `0` if `local_decimals > erc_decimals`. A `saturating_sub` result of `0` means the exponent silently becomes `10^0 = 1`, i.e. the value is passed through completely unscaled, even though the correct operation in that regime is the *opposite* direction (multiply on receive, divide on send).

The only place this direction is enforced is in `register_token`/`update_token`, which validate `config.decimals (erc) >= local_decimals` at configuration time: [2](#0-1) 

However, `local_decimals` used later in `send`, `on_accept`, and `on_timeout` is read live from `T::Assets::decimals()` (fungible-asset metadata), not the value pinned at registration time: [3](#0-2) [4](#0-3) 

Nothing in the pallet freezes or re-validates the registered asset's decimals after `register_token`. `pallet-assets` metadata (including `decimals`) is mutable after asset creation via `set_metadata`, callable by the asset's owner — an entity distinct from `T::CreateOrigin` (the bridge governance that approved the token listing). If the local asset's decimals are increased above the registered `erc_decimals` for any configured chain after registration (a state the pallet itself never guards against once created), the once-valid invariant silently breaks, and every subsequent `send`/`on_accept`/`on_timeout` computation is mis-scaled by a full power-of-ten factor instead of erroring out.

This is a direct structural analog of the reported `UniV2LPOracle` bug: an unvalidated, silently-assumed decimals relationship (`decimals == 18` in the original report, `erc_decimals >= local_decimals` here) feeds directly into an arithmetic scaling step, and when the assumption breaks the result is wrong by orders of magnitude rather than raising an error — exactly matching the `ErcDecimalsBelowLocal` error variant that exists in the pallet but is only checked once, not continuously enforced.

### Impact Explanation
When the invariant breaks, `convert_to_erc20` on the `send` path stops dividing down and passes the local (finer-precision) amount through unscaled to the EVM side, minting the counterpart contract an amount inflated by `10^(local_decimals - erc_decimals)` relative to what was actually escrowed/burned locally. This is an unbacked-mint / fund-inflation vector on the destination chain purely from a decimal bookkeeping error, not a deliberate governance/admin abuse — matching the "unbacked mint" acceptance criterion. Conversely, on `on_accept`/`on_timeout` the same bug causes the wrong (deflated) amount to be minted/released locally, which is a fund-loss/freezing outcome for legitimate senders.

### Likelihood Explanation
Triggering requires the local (non-native) asset's decimals metadata to increase past the registered `erc_decimals` for at least one configured destination chain after `register_token` has already approved that chain. This is not something `T::CreateOrigin` (bridge governance) does — it is a property of `pallet-assets`, where a token's own `Owner`/`Issuer`, not the bridge admin, can call `set_metadata` to change decimals at any time the metadata is not frozen. Since the pallet re-reads decimals live on every operation rather than pinning them at registration, this is a genuine unprivileged path from the bridge's perspective, reachable by whoever controls the underlying asset class, not by the bridge's trusted admin.

### Recommendation
Pin (store) the local asset's decimals in the `Precisions`/registration storage at `register_token` time rather than re-reading live metadata on every `send`/`on_accept`/`on_timeout`, and reject (rather than `saturating_sub`-clamp) any conversion where `erc_decimals < local_decimals`, either by re-enforcing the `ErcDecimalsBelowLocal` check at every conversion site or by supporting bidirectional scaling (multiply/divide) explicitly instead of relying on `saturating_sub` clamping to zero.

### Proof of Concept
1. Governance (`CreateOrigin`) registers asset `X` (owned by user `U`, currently `decimals = 6`) for chain `Evm(1)` with `erc_decimals = 18` via `register_token`; passes the `config.decimals >= local_decimals` check (18 ≥ 6). [5](#0-4) 
2. `U`, as the owner of asset `X` in `pallet-assets`, later calls `set_metadata` to raise `X`'s decimals to `19` (no re-check occurs in the HFT pallet).
3. `U` calls `send` with a small `amount` of `X`. `send` reads `decimals` live as `19`, computes `erc20_amount = convert_to_erc20(amount, erc_decimals=18, decimals=19)`. Since `18u8.saturating_sub(19) == 0`, `erc20_amount = amount * 10^0 = amount` — unscaled, i.e. 10x larger than the correct `amount / 10`. [6](#0-5) 
4. The dispatched `Message` credits the EVM-side contract with an ERC20 amount 10x larger than what was actually burned/escrowed on the substrate side, minting unbacked value on the destination chain.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
