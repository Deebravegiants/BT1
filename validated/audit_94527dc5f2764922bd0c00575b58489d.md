**Analysis:**

`ecdsa_raw_public_key_to_bytes` in `secp256r1.move` is a trivial accessor that returns the raw bytes stored in an `ECDSARawPublicKey` struct with no cryptographic validation performed [1](#0-0) . However, this function is irrelevant to the `rotate_authentication_key` custody path being questioned: `secp256r1`/`single_key` schemes are not even accepted by `rotate_authentication_key`, which only supports `ED25519_SCHEME` and `MULTI_ED25519_SCHEME` for `from_scheme`, aborting with `EINVALID_SCHEME` for anything else [2](#0-1) .

More importantly, the premise that "equality on raw bytes" is the only guard is incorrect. The `from_public_key_bytes == authentication_key` check merely confirms the supplied bytes hash to the account's current auth key — it is explicitly documented as unverified ownership at this stage. The actual custody boundary is enforced afterward by `assert_valid_rotation_proof_signature_and_get_auth_key(from_scheme, from_public_key_bytes, cap_rotate_key, &challenge)`, which requires a valid Ed25519/MultiEd25519 signature over a `RotationProofChallenge` (containing the current sequence number and address) produced by the *private* key corresponding to those bytes [3](#0-2) . An attacker who supplies correct `from_public_key_bytes` without the private key cannot produce a valid `cap_rotate_key` signature, so the transaction aborts with `EWRONG_CURRENT_PUBLIC_KEY`/signature verification failure before any state is mutated [4](#0-3) .

This is the intended, documented design (the function's own doc comment explains why both `cap_rotate_key` and `cap_update_table` signatures are required to prevent exactly this class of spoofing) [5](#0-4) . The formal spec also encodes this signature-verification requirement as an abort condition [6](#0-5) . Since a real authority check (signature verification, not just byte equality) already closes this path, and `secp256r1.move`'s accessor function has no bearing on this flow, this does not meet the custody-impact bar.
