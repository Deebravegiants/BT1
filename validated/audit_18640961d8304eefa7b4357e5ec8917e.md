### Title
Webhook shop-domain not covered by HMAC signature allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (and `topic`, `webhook_id`, `api_version`) from unauthenticated HTTP headers, but the HMAC signature it validates only covers the raw request body via `to_signable_string` [1](#0-0) . `Registry.process` trusts `request.shop` after only checking `Utils::HmacValidator.validate(request)`, and hands it directly to the app's handler as the merchant identity for the event [2](#0-1) .

### Finding Description
The binding that should hold is: `shop-that-signed-the-body == shop-domain-header-used-by-the-handler`. The gem breaks this equality: `HmacValidator.validate_signature` computes and compares the HMAC only against `verifiable_query.to_signable_string`, which for `Request` returns solely `@raw_body` [3](#0-2) [4](#0-3) . The `shop` field returned by `Request#shop` comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed content [5](#0-4) .

Because a valid HMAC only proves "this body was genuinely produced by Shopify for *some* shop that owns the app's secret-signed payload," it proves nothing about which `shop-domain` header accompanies it. An attacker who controls their own Shopify store (an unprivileged internet user relative to other tenants of the same app) can trigger a real webhook delivery to their own endpoint, capture the genuinely-signed body and its valid HMAC, then replay that exact body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` passes the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler [2](#0-1) .

### Impact Explanation
This is a cross-tenant identity-confusion vector: an app's webhook handler that keys off `data.shop` (e.g., to look up the merchant session, update per-shop state, or perform data-deletion/GDPR actions for `shop/redact`, `customers/redact`, `customers/data_request` — all of which are mandatory topics registered through this exact `Registry.process` path) can be made to act on behalf of, or attribute attacker-controlled body content to, a shop the attacker does not control. Depending on the handler's use of `shop`, this can lead to cross-tenant data corruption or spoofed events being recorded against an arbitrary victim shop.

### Likelihood Explanation
Requires only that an attacker operate their own Shopify store (able to trigger genuine webhook deliveries) and be able to POST to the target app's public webhook endpoint with custom headers — no access token, `api_secret_key`, or privileged account is needed. This matches the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered content, or otherwise cryptographically bind the `shop` header to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that consumers must independently verify `shop` against a known/registered shop for the app before using it, since `to_signable_string` does not cover it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), causing Shopify to POST a body `B` with header `X-Shopify-Shop-Domain: attacker.myshopify.com` and a valid `X-Shopify-Hmac-Sha256` computed over `B` with the app's `client_secret`.
2. Attacker captures this request (body `B` + hmac header) via their own reverse proxy logging (no secret needed, they already legitimately receive it).
3. Attacker replays the request to the app's webhook endpoint, keeping body `B` and the HMAC header identical, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only hashes `@raw_body` [4](#0-3) .
5. `request.shop` returns `"victim.myshopify.com"` and this value is passed into the handler as the acting shop [6](#0-5) , causing the handler to process attacker-controlled data as if it belonged to the victim shop.
