### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate`, which computes the HMAC over `Request#to_signable_string`. That method returns only `@raw_body`, not the `shop`, `topic`, or `webhook_id` header values [1](#0-0) . Yet `request.shop`, `request.topic`, and `request.webhook_id` — all read straight from HTTP headers with no cryptographic binding — are forwarded verbatim into `WebhookMetadata` and handed to the app's handler as the authenticated identity of the webhook [2](#0-1) . This is the same class of defect as the report's `ethValueInWithdrawal` bug: a value that flows into a security-relevant computation/decision without being covered by the check that is supposed to guarantee its integrity (there, a missing division after the trust boundary; here, header fields excluded from the HMAC that is supposed to prove Shopify origin).

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header using `OpenSSL.secure_compare` [3](#0-2) . For webhooks, `to_signable_string` is defined as just the raw request body [4](#0-3) . The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no comparison to anything the HMAC covers [5](#0-4) .

The equality that should hold is: `shop asserted in header == shop bound by the HMAC-signed payload`. In this implementation, only `raw_body == HMAC(raw_body, client_secret)` is checked; `shop(header) == shop(signed content)` is never checked, so the two sides diverge — the header-derived `shop` is not what the HMAC authenticates.

This library's own webhook payloads *do* include `shop_domain` inside the JSON body (a well-known Shopify convention) but this gem never cross-checks `request.shop` (header) against any body-derived shop value; it simply trusts whichever `shop` header value arrives, as documented in `docs/usage/webhooks.md`, which explicitly tells developers `data.shop` is "The shop domain of the webhook" without describing that it is unauthenticated [6](#0-5) .

### Impact Explanation
An app installed on an attacker-controlled shop legitimately receives real webhooks, each HMAC-signed over the body with the app's shared `client_secret` [7](#0-6) . Because the signature is computed over the body alone, the attacker can replay that exact body to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers to name a victim shop. `HmacValidator.validate` still succeeds (the body and signature are unchanged and valid), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain [8](#0-7) . Any host application that uses `data.shop` to look up a merchant's session/tenant record and perform state-changing or data-returning operations "on behalf of" that shop — the exact usage pattern shown in this gem's own docs (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [9](#0-8)  — can be tricked into acting under a victim tenant's identity using data actually sourced from the attacker's own shop. This is a cross-tenant identity-binding break reachable without any credential beyond installing the app on one's own (attacker) shop.

### Likelihood Explanation
Requires only that the attacker's business installs the target app (a normal, unprivileged action any merchant can take) and can send arbitrary HTTP requests with attacker-chosen headers to the app's public webhook callback URL — no access token, `client_secret`, or other Shopify-side secret is needed. The header/body split is entirely internal to this gem's `Request`/`HmacValidator`/`Registry` code path, not something the host app can be blamed for ignoring, since the gem transparently trusts and exposes `request.shop` as verified data.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or explicitly document and enforce that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host app against the shop under which the webhook was registered/session-known before being trusted for any privileged operation. At minimum, `to_signable_string` should incorporate the header fields it later exposes as "verified" webhook metadata, mirroring how `AuthQuery#to_signable_string` correctly includes `shop`, `host`, `code`, `state`, and `timestamp` in its signable string [10](#0-9) .

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate `orders/create` webhook: body `B`, headers include `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: H = HMAC_SHA256(B, client_secret)`.
2. Attacker resends to the app's webhook endpoint the identical raw body `B` and identical `shopify-hmac-sha256: H`, but with header `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(B, client_secret)` (body unchanged) and matches `H` via `OpenSSL.secure_compare` [11](#0-10)  — validation passes.
4. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though all signed content originated from the attacker's own shop [12](#0-11) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
