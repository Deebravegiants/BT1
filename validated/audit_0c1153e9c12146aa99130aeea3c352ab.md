### Title
`onPostRequestTimeout` refund path gated by the same pause flag as normal transfers — burned tokens cannot be recovered while paused - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.send()` burns the user's tokens and dispatches a cross-chain POST request [1](#0-0) . If that request times out, the *only* way to recover the burned tokens is `onPostRequestTimeout`, which re-mints them to the original sender [2](#0-1) . Both `send()`'s underlying transfer/mint path and `onPostRequestTimeout` are gated by the same `whenNotPaused` modifier [3](#0-2) ; the identical pattern exists in `HyperFungibleTokenUpgradeable.sol` [4](#0-3)  and in `WrappedHyperFungibleToken.sol`'s lock/unlock refund path [5](#0-4) .

### Finding Description
This mirrors the reported `LibUbiquityPool` bug class exactly: a single pause flag controls both the *initiating* action (new transfers/mints/redemptions) and the *completion/recovery* action for state that was already committed by a user (burned tokens awaiting refund on timeout). A user who calls `send()` (burning their tokens) before the owner pauses the contract has no way to reclaim those tokens via `onPostRequestTimeout` for as long as the pause is active, because that function reverts under `whenNotPaused` just like the initiating functions [2](#0-1) . The project's own design notes acknowledge this coupling was a deliberate choice, but do not address the fund-recovery implication for outstanding burns [6](#0-5) .

The dispatch path for timeouts (`HandlerV2.handlePostRequestTimeouts` → `host.dispatchTimeOut`) verifies non-membership proofs and then calls into the module's `onPostRequestTimeout` [7](#0-6) ; if the module call reverts because the token is paused, the relayer's whole timeout-handling transaction reverts as well, so the request cannot be settled at all while the pause remains — freezing user funds in limbo exactly as in the analog report, tied to an owner-controlled but user-uncontrollable condition, with no separate "refunds-only" flag to let already-burned tokens be recovered independently of new-transfer suspension.

### Impact Explanation
Users who legitimately burned tokens via `send()` and whose cross-chain message subsequently times out are unable to recover their funds via the sanctioned refund path (`onPostRequestTimeout`) whenever the owner has the contract paused, exactly mirroring the "burn succeeds, recovery blocked" pattern in the source report. This affects any HFT/WrappedHFT deployment where a pause coincides with an in-flight, later-timed-out transfer — a realistic operational scenario (e.g., pausing during an incident while messages are already in flight).

### Likelihood Explanation
Likelihood is moderate: it requires (1) a user to have an outstanding `send()` whose message eventually times out, and (2) the owner to pause the contract during that window. Given that pausing is a normal incident-response action and cross-chain timeouts are an expected occurrence (relayer failure, congestion, etc.), the overlap is plausible without any malicious actor — consistent with the "Medium" severity of the original analog.

### Recommendation
Split the single `Pausable` flag used by `HyperFungibleToken`/`HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken` into two independent controls: one gating new transfers/mints (`send`, `onAccept`, ERC20 `transfer`/`transferFrom`), and a separate flag (or no gate at all) for `onPostRequestTimeout`, so that users can always recover already-burned/locked funds once a timeout is proven, regardless of whether new transfers are currently paused.

### Proof of Concept
1. User calls `HyperFungibleToken.send()`, burning `amount` tokens and dispatching a POST request with a timeout [1](#0-0) .
2. Before the message is delivered, the owner calls `pause()`.
3. The message times out; a relayer submits the timeout proof through `HandlerV2.handlePostRequestTimeouts` → `host.dispatchTimeOut` → `HyperFungibleToken.onPostRequestTimeout` [7](#0-6) .
4. `onPostRequestTimeout` reverts due to `whenNotPaused` [2](#0-1) , so the user's burned tokens cannot be re-minted until the owner unpauses — an unbacked-for-user freeze of funds tied purely to the pause state, with no independent path to recovery.

**Note on uncertainty:** I was unable to inspect `EvmHost.dispatchTimeOut`'s exact revert-handling/commitment-deletion order (whether a reverted module call also prevents the request-commitment from being deleted, allowing retry after unpause). If commitment deletion happens regardless of the module call's success (e.g., via try/catch), this would be a *permanent* loss rather than a temporary freeze; this could not be confirmed within the available tool calls.

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));

            from: message.from,
            to: beneficiary,

            amount: message.amount
        });

    function handlePostRequestTimeouts(IHost host, PostRequestTimeoutMessage calldata message)
        external
        notFrozen(host)
    {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            PostRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            // known request? also serves as source check
            bytes32 requestCommitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(requestCommitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(REQUEST_RECEIPTS_STORAGE_PREFIX, requestCommitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(PostRequestTimeout(request, _msgSender()), meta, requestCommitment);
        }
    }
