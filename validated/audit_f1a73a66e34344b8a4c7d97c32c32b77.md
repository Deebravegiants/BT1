### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook request's HMAC before dispatching it to the registered handler, but the HMAC only covers the raw request body — never the `shop-domain` header. The handler is then invoked with a `WebhookMetadata` whose `shop` field is taken straight from that unauthenticated header. Any party who can obtain one valid `(raw_body, hmac)` pair for the shared app `client_secret` (e.g. by installing the app on their own free/dev store and capturing one of their own inbound webhook deliveries) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header, and the library will accept it as an authentic webhook "from" the victim shop.

### Finding Description
The HMAC verification path is:
- `ShopifyAPI::Utils::HmacValidator.validate(verifiable_query)` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`. [1](#0-0) 

- For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` — it never includes the shop domain (or topic/webhook-id) header. [2](#0-1) 

- `#hmac` and `#shop` are both derived from independent, unrelated HTTP headers, with `shop` coming from `shopify-shop-domain`/`x-shopify-shop-domain`, a header that is not part of the signed material at all. [3](#0-2) 

- `Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop` to build the `WebhookMetadata` that is handed to the app's webhook handler: [4](#0-3) 

The identity binding the app relies on is: *`shop` authenticated by the HMAC == `shop` used to key the tenant-scoped action in the handler*. In reality the HMAC only proves "this body was produced with the app's `client_secret`" — it says nothing about which shop the request is for. Since the same `client_secret` is shared across every shop that installs the app, any unprivileged party who can install the app on a shop they control (a free Shopify partner/dev store, no privileged credentials required) can capture one legitimately-signed `(body, hmac)` pair from their own store's webhook delivery, then send that identical body+HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim's `*.myshopify.com` domain. `HmacValidator.validate` still succeeds (body unchanged), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the shop/tenant identity binding entirely inside the gem: verified bytes (the body) are decoupled from the field the handler acts on (`shop`). Any host application that follows the documented pattern of using `WebhookMetadata#shop` to determine which merchant's data/session/record to look up or mutate (e.g. `customers/redact`, `shop/redact`, `app/uninstalled`, or any data-syncing handler) can be tricked into performing that tenant-scoped action against a victim shop chosen entirely by the attacker, using a payload the attacker fully controls (since it's the body from their own store's webhook). This is a cross-tenant access primitive achievable by any unprivileged internet user who can install the app once on their own store — no access token, no leaked credentials, and no privileged account required.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair requires nothing more than installing the target app on any Shopify development/partner store (free, self-service) and capturing one webhook delivery to a controlled endpoint (a trivial network capture, not a credential theft). Replaying that request against the app's public webhook endpoint with a modified header requires no special access. The vulnerability is entirely within this gem's `Registry.process`/`Utils::HmacValidator`/`Webhooks::Request` code path, independent of how carefully a host app writes its own handler logic, because the gem itself hands the handler an unauthenticated `shop` value alongside a body it merely proved was HMAC-valid for *some* store.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header value into the material that is verified, or otherwise cryptographically tie the header-derived shop to the request that was actually signed — e.g. require host apps to cross-check `WebhookMetadata#shop` against a shop they already have a stored offline session/access token for before trusting it, and document in `docs/usage/webhooks.md` that `shop` is not itself authenticated by `HmacValidator.validate`. At minimum, `Registry.process` should not silently hand an unauthenticated tenant identifier to the handler without a clear contract that the caller must independently verify it belongs to a shop with an existing installation.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (attacker-controlled) development store `attacker.myshopify.com`.
2. Attacker triggers a webhook delivery for a subscribed topic (e.g. `products/update`) to a URL they control, capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify computed with the app's shared `client_secret`.
3. Attacker sends this identical `raw_body` + `X-Shopify-Hmac-Sha256` to the target app's real webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. In the app, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `to_signable_string` (`@raw_body`), unchanged from step 2. [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, so the attacker's payload is processed as if it originated from the victim shop.
