### Title
BSC verifier: no length check before `aggregate_public_keys` allows quorum bypass when `current_validators` is empty - (File: `modules/consensus/bsc/verifier/src/lib.rs`)

### Summary
`verify_bsc_header` in the BSC consensus client computes a required supermajority threshold as `(2 * current_validators.len()) / 3` and rejects the update only `if participant_count < threshold`. When `current_validators.len() == 0` (an empty validator set, e.g. the initial/default `ConsensusState`), the threshold evaluates to `0`, so `participant_count < 0` is always false and the check trivially passes with zero participants. The empty `participants` vector is then passed to `bls_utils::aggregate_public_keys`, which — like the disclosed Prysm `AggregatePublicKeys` bug — performs no length/emptiness check and returns the BLS identity point without error instead of failing.

### Finding Description
`verify_bsc_header` builds `participants` by filtering `current_validators` against the bitset of signers: [1](#0-0) [2](#0-1) 

`aggregate_public_keys` iterates over the input slice and folds points via elliptic-curve addition, with no check that the slice is non-empty: [3](#0-2) 

This mirrors CL-2021-32 exactly: "there is no length check in `AggregatePublicKeys`. If `pubs` is nil or `[][]byte{}` the function returns a public key without error." Here, if `keys` is empty, `aggregate` stays as `G1ProjectivePoint::default()` (the identity element) and is returned as a valid public key with `Ok(...)`.

The reachable path is `current_validators.len() == 0`. `ConsensusState` for the BSC light client derives `Default` and starts with `current_validators: Vec::new()`: [4](#0-3) 

When `current_validators` is empty, the supermajority gate in `verify_bsc_header` becomes vacuous: [1](#0-0) 

and the aggregate public key ends up being the BLS identity element, with the verifier then calling `bls::verify` against an attacker-supplied signature and message derived from attacker-controlled `vote_data`: [5](#0-4) 

An identity/empty aggregate public key allows an adversary to construct signatures the pairing check accepts without needing any real validator's secret key — the pairing equation `e(g1, σ) = e(apk, H(m))` degenerates when `apk` is the identity, and a corresponding well-formed "identity" signature or a chosen forged signature can be produced by an attacker who fully controls the input (no restriction from any genuine key). This lets an unprivileged relayer submit a bogus consensus update that finalizes an arbitrary `source_header`/state root, forging state commitments for the BSC light client.

### Impact Explanation
If the consensus client ever reaches (or is initialized in) a state with an empty `current_validators` set — the default/starting state before any genesis validator set is populated, or any code path that clears the set without populating a new one — an attacker (a relayer submitting a consensus proof, which is an unprivileged, permissionless action) can submit a forged `BscClientUpdate` that trivially satisfies the quorum check and produces an accepted BLS verification against the identity public key. This results in a forged state commitment being accepted by the ISMP host for the `Evm(BSC chain)` state machine, i.e., unsound state commitment / forged message delivery — a Critical-severity vulnerability class if the empty-validator state is reachable, since it can lead to fabricated cross-chain state proofs and consequently unauthorized token mint/withdraw actions relying on that state.

### Likelihood Explanation
Likelihood depends on whether `current_validators` can actually be empty when `verify_consensus` is invoked in production. The pallet's genesis/initialization flow for populating `current_validators` was not found in the indexed code (the initial value comes from `ConsensusState::default()`), so it is uncertain whether governance-set genesis state always populates a non-empty validator set before the client accepts proofs, or whether an all-zero/emptied state is reachable through some update path (e.g., a malformed `next_validators` promotion emptying `current_validators`). Assuming standard operational setup always initializes with a full validator set, exploitability is limited to a misconfiguration/edge case; however the underlying code defect — missing an explicit non-empty check before aggregation, unlike the sibling Pharos verifier which does check (`if participants.is_empty() { return Err(Error::NoParticipants) }`) — is a genuine, unconditional root-cause bug matching the disclosed report.

### Recommendation
Add an explicit non-emptiness/length check in `verify_bsc_header` before computing `participants`/calling `aggregate_public_keys` — reject when `current_validators.is_empty()` or `participants.is_empty()`, mirroring the Pharos verifier's `Error::NoParticipants` guard: [6](#0-5) 
Additionally, harden `bls_utils::aggregate_public_keys` itself to return an error on an empty input slice, defense-in-depth against any future caller omitting the check: [3](#0-2) 

### Proof of Concept
1. Reach (or initialize) a BSC `ConsensusState` where `current_validators == vec![]` (e.g. default/uninitialized genesis state prior to any validator-set population, or any bug that clears the set).
2. Craft a `BscClientUpdate` with an arbitrary `attested_header`/`extra_data.vote_data` (non-zero source/target hashes) and any `validators_bit_set` value — since `current_validators.len() == 0`, all bits are "beyond validator count" only if set; leave bits unset so `participant_count == 0`.
3. `participant_count (0) < (2*0)/3 (0)` evaluates to `false`, so the supermajority check passes.
4. `participants` is empty; `aggregate_public_keys(&[])` returns `Ok` with the identity public key instead of erroring.
5. Submit a signature crafted against the identity public key/attacker-chosen message; `bls::verify` may accept it, causing `verify_bsc_header` to return success and accept the forged `source_header` as a legitimate finalized BSC header/state root.

pub fn aggregate_public_keys(keys: &[BlsPublicKey]) -> Result<Vec<u8>, BLSError> {
	let mut aggregate = G1ProjectivePoint::default();
	for key in keys {
		aggregate = aggregate + pubkey_to_projective(key)?;
	}
	Ok(bls::point_to_pubkey(aggregate.into()))
}
