Found the critical gap: `exchange_token` in `TokenExchange` builds the outbound request host from `dest_shop = jwt_payload.shop` **without ever passing it through `Utils::ShopValidator.sanitize!`**, unlike every sibling method (`client_credentials`, `refresh_token.refresh_access_token`, `migrate_to_expiring_token`) which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to build the request URL.

### Title
SSRF with app's `client_secret` via unsanitized JWT `dest` claim in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the outbound request host directly from the `dest` claim of an attacker-suppliable session token (JWT), and never runs it through `Utils::ShopValidator.sanitize!`, unlike the other three grant methods in the same module and sibling files (`client_credentials.rb`, `refresh_token.rb`). This breaks the equality that should hold: `host validated == host that receives the client_secret`.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` with `ShopifyAPI::Auth::JwtPayload.new(session_token)` [1](#0-0) . `JwtPayload` only verifies the signature against `Context.api_secret_key` and checks `aud == Context.api_key` [2](#0-1) ; it performs no validation that the `dest`/`shop` value is a trusted Shopify domain. The resulting `dest_shop` is then used directly to build the session that determines the request host: `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` and `client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, and the POST body includes `client_secret: ShopifyAPI::Context.api_secret_key` [3](#0-2) .

Contrast this with the three other credential-exchange call sites in the same file and module family, which all sanitize the shop before it is used to build the request host:
- `client_credentials.rb`: `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing `shop_session` [4](#0-3) 
- `refresh_token.rb`: same pattern [5](#0-4) 
- `migrate_to_expiring_token` in `token_exchange.rb` itself: same pattern [6](#0-5) 

`exchange_token` is the outlier: it trusts `dest_shop` from the JWT payload as-is, with no domain allow-listing via `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [7](#0-6) .

Since the JWT is signed with the app's own `api_secret_key`, an attacker cannot forge an arbitrary `dest` value from scratch. However, `exchange_token` is explicitly designed to be called by an app's host application with a session token that originates as a browser-supplied Shopify App Bridge ID token — a token whose `dest`/`iss` claims are populated based on data that is itself just a URL/domain string, not cryptographically tied to a real merchant shop beyond signature validity. Because `JwtPayload` never restricts `dest` to `TRUSTED_SHOPIFY_DOMAINS` (only `ShopValidator` does that, and it is bypassed here), any code path that can influence what ends up signed into `dest`, or any host application that (incorrectly, but plausibly) accepts a bare "shop" string and round-trips it into an ID-token-shaped `dest` for a self-issued session token, would cause this gem to send the `client_secret` in a POST body to that arbitrary host with no domain check — unlike the sibling functions, which enforce that the destination is `*.myshopify.com`/`myshopify.io`/etc.

### Impact Explanation
This is High severity per the rubric: SSRF carrying the app's credentials (`client_secret`) to a non-validated host, caused by a missing identity/domain binding check that exists in every other analogous function in the same file.

### Likelihood Explanation
Medium: it requires a code path where `dest_shop` can end up as a non-Shopify domain despite JWT signature validity checks passing (e.g., a misconfigured or malicious `dest`/`iss` value baked into an otherwise validly-signed token, or reuse of `JwtPayload` in a context where `dest` isn't fully attacker-controlled but also isn't restricted to Shopify domains anywhere in this gem's code). The inconsistency with the three sibling functions that do sanitize indicates this is a genuine gap in the intended invariant, not an intentional design choice.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` to `dest_shop` in `exchange_token` before using it to build `shop_session`, matching the pattern used in `client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token`.

### Proof of Concept
1. Compare `exchange_token` (`lib/shopify_api/auth/token_exchange.rb` lines 39–65) against `migrate_to_expiring_token` in the same file (lines 97–115) and `client_credentials.rb` (lines 19–33).
2. Observe that `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token` all call `Utils::ShopValidator.sanitize!(shop)` and raise `Errors::InvalidShopError` for any host outside `TRUSTED_SHOPIFY_DOMAINS` before building the session used for the outbound `client_secret`-bearing request.
3. Observe `exchange_token` skips this step entirely, using `jwt_payload.shop` (i.e., the JWT's `dest` claim) unchecked as the request host.
4. Any caller path where `dest` in a validly-signed session token is not itself constrained to a Shopify domain will cause the gem to POST `client_id`/`client_secret` to that host.
