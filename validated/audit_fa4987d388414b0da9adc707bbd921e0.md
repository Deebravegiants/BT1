## Title
Webhook `shop` domain is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable signature from the raw body only, while the `shop` value that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler is read from the unauthenticated `x-shopify-shop-domain` header. The HMAC therefore does not bind the tenant identity to the payload it protects.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` — the value used to identify which merchant/tenant the webhook belongs to — is pulled straight from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is never part of the signed content: [2](#0-1) 

`Registry.process` verifies the HMAC over the body and, on success, forwards `request.shop` directly to the app's handler as the authenticated tenant identity: [3](#0-2) 

The gem's `HmacValidator.validate` computes `HMAC(Context.api_secret_key, verifiable_query.to_signable_string)` and compares it to the received signature: [4](#0-3) 

Because `Context.api_secret_key` is a single app-wide secret shared across every shop that installs the app (it is not shop-specific), any legitimately installed shop can generate a `(raw_body, valid_hmac)` pair for arbitrary body content it controls (e.g. by creating an order with attacker-chosen field values in its own store to trigger a real Shopify webhook). Because the shop-domain header is not covered by that HMAC, the attacker can replace `x-shopify-shop-domain` with any other shop's domain and POST the forged request directly to the app's public webhook endpoint. `Registry.process` will accept it as valid (`Utils::HmacValidator.validate(request)` only checks the body signature) and invoke the app's handler with `shop: request.shop` set to the victim shop, and `body: request.parsed_body` containing attacker-controlled data.

This breaks the identity binding that the gem's own documentation implies is guaranteed: "`ShopifyAPI::Webhooks::Registry.process` ... will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook": [5](#0-4) [6](#0-5) 

The equality that should hold but doesn't: `bytes_covered_by_hmac(shop) == shop_value_delivered_to_handler`. In fact `shop` is entirely outside the signed bytes, so `process` cryptographically proves only "this body was signed by the app's secret" — not "this body originated from shop X."

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as documented) to scope tenant data — e.g., to select which merchant's DB row to update, which merchant's cache to invalidate, or which customer/order record to write — can be made to apply data for shop A while attributing/writing it under shop B's tenant context, since `process` provides no cryptographic guarantee binding the delivered `shop` to the signed payload. This is a cross-tenant data integrity/confusion vector reachable by any unprivileged actor able to install the app in their own store and control the public webhook endpoint address (which apps expose to receive webhooks from Shopify).

### Likelihood Explanation
Exploitation requires only: (1) an attacker installs the target app in a shop they control (standard app installation, no special privilege), (2) they trigger events that generate real signed webhooks with attacker-influenced body fields, (3) they replay the captured `(body, hmac)` pair to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secrets, tokens, or Shopify-side compromise are needed — only the ability to install the app and send an HTTP POST to its public webhook URL.

### Recommendation
Bind the shop domain (and other routing-critical headers such as `webhook_id`/topic if relied upon by the handler for authorization decisions) into the HMAC computation, or independently verify that the shop asserted in the header matches a shop the app has an active, previously-established session/webhook subscription for (e.g., cross-check `request.shop` + `request.webhook_id` against the app's own registered webhook records before invoking the handler), rather than trusting the header value as-is once only the body's HMAC has been validated.

### Proof of Concept
1. App developer registers a webhook handler that uses `data.shop` to select the tenant record to update, per the documented usage in `docs/usage/webhooks.md`.
2. Attacker installs the app in `attacker-shop.myshopify.com` and triggers an event (e.g. `orders/create`) with attacker-chosen field values, receiving from real Shopify a POST with headers `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a JSON body they crafted the content of.
3. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only verifies `HMAC(api_secret_key, raw_body)` — unaffected by the header swap — as shown in `HmacValidator#validate_signature` [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to process attacker-controlled data under the victim shop's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
