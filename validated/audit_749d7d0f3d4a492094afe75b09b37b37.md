The `Registry.process` method validates only the HMAC over the raw body via `Utils::HmacValidator.validate(request)`, but the `shop`, `topic`, `api_version`, and `webhook_id` fields—read directly from HTTP headers via `shopify_header`—are never included in the signed data (`to_signable_string` returns only `@raw_body`). ### Title
Webhook Shop Identity Spoofing via HMAC Scope Gap - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook delivery solely by validating an HMAC computed over the raw request body [1](#0-0) , while the `shop`, `topic`, `api_version`, and `webhook_id` values used to build `WebhookMetadata` are taken unauthenticated from HTTP headers [2](#0-1) . `to_signable_string` returns only `@raw_body`, so none of the header-derived fields — most importantly `shop` — are covered by the HMAC [3](#0-2) .

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against the `hmac` field using `OpenSSL.secure_compare` [4](#0-3) . For webhook requests, `to_signable_string` is defined to be just the raw request body, so the HMAC signature is a function of the body alone [3](#0-2) .

The equality this HMAC is meant to enforce is:
`hmac(secret, body) == hmac ⇒ (shop, topic, body) genuinely originated from Shopify for this shop`

But the actual binding only covers `body`, not `shop`/`topic`/`webhook_id`/`api_version`, which are read straight from attacker-controllable HTTP headers via `shopify_header` [5](#0-4) . Because every shop that installs a given Shopify app shares the same `api_secret_key` (the app's `client_secret`, not a per-shop secret), any merchant who installs the app — an unprivileged party from the perspective of any *other* tenant — legitimately receives real webhook deliveries for their own shop, each with a valid `(body, hmac)` pair signed with that shared secret.

That attacker can then replay the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header with a victim shop's domain. `Registry.process` will call `Utils::HmacValidator.validate(request)`, which still succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — it never re-derives or checks `shop` [6](#0-5) . The resulting `WebhookMetadata` is built with `shop: request.shop` set to the victim's domain, and is handed to the host application's registered handler as if Shopify had genuinely sent that payload for that shop [7](#0-6) .

### Impact Explanation
This breaks the tenant isolation boundary the gem is supposed to provide: an authenticated body from shop A is deliverable as, and processed as, a webhook attributed to a different shop B, without possessing shop B's credentials. Any host application logic keyed off `WebhookMetadata#shop` (e.g., updating shop-scoped records, triggering shop-scoped side effects, deletion/uninstall handling such as `app/uninstalled` or `shop/redact`) can be triggered against an arbitrary victim shop merely by an attacker who has installed the app on any shop. This is a cross-tenant data integrity / spoofing issue rooted directly in this gem's webhook verification implementation, matching the report's "field acted upon but not covered by the signature" bug class.

### Likelihood Explanation
Requires only that the attacker install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint (which the app owner necessarily exposes to receive Shopify webhooks). No access to `api_secret_key`, tokens, or the victim's credentials is needed — only replaying an already-valid body/HMAC pair with a swapped `shop-domain` header.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-covered signable string (or otherwise cryptographically bind them to the body), or independently verify that `request.shop` corresponds to a shop for which this exact `(topic, webhook_id, hmac)` triple is expected, before constructing `WebhookMetadata` and invoking handlers.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`, and app registers a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and some `raw_body`.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Attacker (or anyone who can reach the app's public webhook endpoint) resends the same body and HMAC header, but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only ever depended on `raw_body` [1](#0-0) .
6. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the attacker-supplied body as if it were a genuine webhook for the victim shop [7](#0-6) .
