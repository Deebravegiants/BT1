## Title
Webhook HMAC only covers the raw body, letting an attacker who controls one shop spoof the `shop-domain` identity of a webhook request - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The M-3 report describes a class of bug where a security-relevant identifier is used by application logic without being bound to the data that was actually authenticated. In `LienToken.sol`, the loop index used to act on the lien stack diverged from the index actually validated by the deletion logic. The same class of bug — "acted on, but not covered by the authentication check" — exists in this gem's webhook request handling: the `shop` identifier used downstream by the app's webhook handler is never included in the bytes that `Utils::HmacValidator` actually verifies.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery#to_signable_string` by returning only the raw HTTP body: [1](#0-0) 

But `request.shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on that HMAC check and then hands the *unverified* `request.shop` straight to the app's handler as the tenant identity for the event: [4](#0-3) 

The identity binding broken here is an equality that is never enforced:
`hmac_verified(shop-domain header)` == `shop-domain header trusted by handler`

Before the attack: for a legitimately-delivered webhook, `request.shop` happens to equal the shop that Shopify actually sent the event for, but only because Shopify itself sets both the header and the signature consistently — the gem does nothing to force this equality.

After the attack: an attacker who owns any shop with the app installed (an ordinary, unprivileged action — installing a free/dev store) can trigger a real event in their own store, which Shopify signs and delivers with a valid `hmac-sha256` over the body and a `shop-domain` header equal to the attacker's own shop. The attacker then replays that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but substitutes the `shop-domain` (and `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still passes, because it only checks the body bytes, which are untouched. `request.shop` now returns the attacker-chosen victim domain, and `Registry.process` dispatches the event to the handler tagged with that victim shop's identity, even though the payload content (order data, customer data, etc.) actually belongs to the attacker's own store.

### Impact Explanation
Any consuming app that trusts `WebhookMetadata#shop` (as documented and demonstrated in this gem's own tests, e.g. `data.shop`) to select which tenant's session/access token/database row to act on will process attacker-controlled payload content under a victim shop's identity. This is a cross-tenant confusion / cross-tenant access vector: the attacker can inject fabricated event data (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request`) attributed to a shop they do not control, without ever needing that victim's credentials, access token, or the app's `client_secret`.

### Likelihood Explanation
The prerequisite is only that the attacker has (or creates) their own shop where the app is installed — a normal, unprivileged action — and can capture/replay HTTP requests, which requires no interception of TLS traffic between Shopify and the app (the attacker is the legitimate origin of their own webhook and simply re-sends it with a modified header to the app's public endpoint). No secrets are needed. This makes the analog realistically reachable through the gem's own verification code path (`Webhooks::Request` + `Utils::HmacValidator` + `Registry.process`).

### Recommendation
Bind the `shop-domain` header into the signed payload check, or otherwise cryptographically bind the shop identity to the verified bytes — e.g., have `Request#to_signable_string` incorporate the `shop-domain` header (mirroring how Shopify's OAuth `AuthQuery#to_signable_string` already includes `shop` in the signed string, see `lib/shopify_api/auth/oauth/auth_query.rb` lines 34-43), or require consuming apps to independently correlate `request.shop` against the shop's stored webhook secret/session before trusting it as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Attacker triggers a real event (e.g. updates an order) so Shopify delivers a legitimately-signed webhook: body `B`, header `x-shopify-hmac-sha256: H`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body `B` and `hmac` header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation succeeds (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and dispatches to the handler (`lib/shopify_api/webhooks/registry.rb` lines 188-200), even though the payload `B` actually describes the attacker's own shop's data.
