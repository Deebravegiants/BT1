Audit Report

## Title
Value-transferring EVM `CALL`s always classify as `AllowReentry` regardless of stipend gas, defeating the `AllowNext` reentrancy mitigation - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

## Summary
`run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` selects the reentrancy protection level via a `match` on `(value.is_zero(), gas_limit == CALL_STIPEND)`, and the `(false, _)` arm is checked first, so any call with `value != 0` is unconditionally classified `ReentrancyProtection::AllowReentry` while still being granted `add_stipend = true` weight — never reaching the `AllowNext` arm that exists specifically to close this gap. [1](#0-0)  The `AllowNext` doc comment explicitly states this variant exists because "due to gas scale differences that guarantee does not automatically hold in revive," yet the code never applies it when `value != 0`. [2](#0-1) 

## Finding Description
The Solidity `.transfer()`/`.send()` reentrancy mitigation on real Ethereum works because the low-level `CALL` is issued with an explicit low/zero gas amount, and the protocol then adds a fixed 2300-gas stipend automatically — an amount provably insufficient for a further state-changing call (e.g., `SSTORE`). `pallet-revive`'s prdoc for this feature confirms the actual encoding: solc-compiled `.transfer(amount)`/`.send(amount)` with `value > 0` pass gas `0` (relying on the automatic addition), while only the zero-value special case (`transfer(0)`/`send(0)`) has solc inject the literal `2300` gas parameter. [3](#0-2) 

The `run_call` match, however, routes on `value.is_zero()` first: any `value != 0` (which is the actual real-world `.transfer(amount)`/`.send(amount)` case, where solc passes `gas_limit = 0`) falls into `(false, _) => (true, ReentrancyProtection::AllowReentry)`, never reaching the `gas_limit == CALL_STIPEND` check at all, regardless of what gas value was actually passed. [1](#0-0)  Meanwhile `add_stipend = true` is still granted, so `determine_call_stipend::<T>()`'s real, non-trivial weight (CALL_STIPEND + `DepositEvent` weight) is added to the callee's budget. [4](#0-3)  The very PR that introduced this stipend weight explicitly documents that this weight is calibrated to be enough for "emitting a LOG event on top of the base 2300 gas operations," and adds reentrancy tests only for the injected-2300, but that protective path is only reachable through `AllowNext`. [5](#0-4) 

Because `AllowReentry` is granted, `Stack::call` never sets `top_frame_mut().allows_reentry = false`, so the callee is not blocked from calling back into the caller's frame while it is still active on the stack. [6](#0-5)  This defeats the checks-effects-interactions mitigation that `.transfer()`/`.send()` are conventionally relied upon to provide, and the repo's own fixture (`Stipends.sol`) demonstrates that this reentrancy-blocking property is explicitly expected to hold for real `.transfer(amount)`/`.send(amount)` calls with `value > 0` (see `testTransferReentrancy`/`testSendReentrancy`, which assert that a reentrant callback via the stipend must fail). [7](#0-6) 

The reentrancy-blocking behavior demonstrated by the fixture (`ComplexReceiver`'s `SSTORE` failing under `.transfer()`/`.send()`) currently relies on the callee running out of gas/weight during the stipend-limited nested execution — not on the `AllowNext` reentrancy guard being active, since that guard is unreachable whenever `value != 0` due to the match-arm ordering. This means the reentrancy protection for the overwhelmingly common `.transfer(amount)`/`.send(amount)` pattern (`value > 0`) currently depends entirely on whether the stipend weight happens to be exhausted before a reentrant `CALL` can be issued, rather than on the explicit `allows_reentry = false` mechanism that `AllowNext` provides. Any contract path or future weight/fee recalibration that leaves enough of the stipend weight for a reentrant `CALL` opcode (but not enough for a full state-changing operation) would let a malicious receiver re-enter the caller before its own post-call accounting completes — exactly the scenario the `AllowNext` comment says must be "enforce[d]... explicitly."

## Impact Explanation
If the stipend-equivalent weight budget is ever sufficient to issue a further `CALL` (which the `AllowNext` design comment acknowledges can happen "due to gas scale differences"), a value-transferring call using the canonical `.transfer()`/`.send()` pattern (`value != 0`) provides no explicit reentrancy guard, unlike the narrower `value == 0` stipend case which does get `AllowNext`. This could allow a malicious receiving contract to re-enter the caller mid-execution before the caller finalizes its own state, matching a checks-effects-interactions violation. However, the currently observed protective outcome (per the `Stipends.sol` fixture tests) is that the stipend weight is calibrated to be too small for a further call in the tested scenarios, so exploitation depends on weight/fee parameters that were not fully verifiable within this review.

## Likelihood Explanation
Reachability of the `(false, _)` code path is trivial and unprivileged — every value-transferring `CALL`/`STATICCALL`/`DELEGATECALL` in EVM contracts hits it. Whether this translates into an exploitable reentrancy window depends on whether the stipend weight budget granted (`determine_call_stipend::<T>()`) is ever sufficient to perform a further `CALL`; the repository's own tests assert it currently is not for a simple `SSTORE`-performing receiver, and no test or code path in this review demonstrated a concrete bypass producing double-spend or corrupted accounting.

## Recommendation
Reorder or redesign the heuristic so that the `AllowNext` reentrancy guard is applied whenever `add_stipend` is granted, independent of `value.is_zero()`, e.g., by keying off the actual condition intended to detect a stipend-limited call (explicit `gas_limit == 0` or `gas_limit == CALL_STIPEND`) before checking value, and by re-verifying that `determine_call_stipend::<T>()` remains provably insufficient for a nested `CALL` under all fee/weight configurations rather than relying solely on gas exhaustion as an implicit reentrancy guard.

## Proof of Concept
No test in the repository currently demonstrates a successful reentrant call breaking through the stipend weight budget; the existing `Stipends.sol` fixture tests (`testTransferReentrancy`, `testSendReentrancy`) show the opposite — reentry attempts currently fail due to weight exhaustion, not due to `AllowNext`. Constructing a concrete PoC would require: (1) crafting or configuring a scenario where `determine_call_stipend::<T>()`'s granted weight is enough to execute a further `CALL` opcode but insufficient to complete other bookkeeping, and (2) showing that a nested reentrant call into the caller succeeds and observes/mutates the caller's pre-finalization state. This was not verified in this review, and the currently observed test behavior in `Stipends.sol` does not confirm exploitability with the existing stipend weight calibration.

    // Test that the transfer stipend prevents reentrancy. The attacker's receive()
    // tries to call back into attemptTransfer() to drain more ETH, but the 2300
    // gas stipend is not enough for an external call.
    function testTransferReentrancy() public payable {
        uint256 amount = msg.value / 4;
        uint256 balanceBefore = address(reentrancyAttacker).balance;

        // The attacker's receive() attempts an external call which exhausts
        // the stipend, causing receive() to revert with out-of-gas.
        bool failed = false;
        try this.attemptTransfer(payable(address(reentrancyAttacker)), amount) {
            failed = false;
        } catch {
            failed = true;
        }
        require(failed, "Transfer to reentrancy attacker should have failed");
        require(address(reentrancyAttacker).balance == balanceBefore, "Attacker balance should not change");
    }

    // Test that the send stipend prevents reentrancy.
    function testSendReentrancy() public payable {
        uint256 amount = msg.value / 4;
        uint256 balanceBefore = address(reentrancyAttacker).balance;

        bool success = payable(address(reentrancyAttacker)).send(amount);
        require(!success, "Send to reentrancy attacker should have failed");
        require(address(reentrancyAttacker).balance == balanceBefore, "Attacker balance should not change");
    }
