### Title
OIDC login trusts unverified `email` claim for session/role binding, enabling account takeover - (File: core/sessions/oidcauth/oidc.go)

### Summary
`oidcAuthenticator.handleTokenExchange` (the `/oidc-exchange` endpoint) authenticates a user by verifying the ID token signature/audience only, then reads the `email` claim straight out of the token claims and uses it, unmodified and without checking `email_verified`, to create a local session bound to that email and to the RBAC role derived from group claims.

### Finding Description
After the OIDC provider redirect and code exchange, the handler does: [1](#0-0) 
It verifies the ID token cryptographically and extracts group claims via `ExtractIDClaimValues`, but the `email` field is taken directly from `claims["email"].(string)` with no verification that the identity provider considers this email confirmed/owned by the authenticating principal: [2](#0-1) 
That raw `email` value is then lowercased and persisted as the session identity in `oidc_sessions`, alongside the role mapped from group claims: [3](#0-2) 
This session lookup path (`AuthorizedUserWithSession`) simply trusts `user_email`/`user_role` stored at exchange time — there is no secondary check tying the OIDC subject identifier (`sub`) to a specific Chainlink user record: [4](#0-3) 

The `github.com/coreos/go-oidc` library and this code perform no `email_verified` claim check anywhere in the file (confirmed via search — no occurrences of `email_verified`/`EmailVerified`). Many IdPs (and misconfigured OIDC apps, similar to the referenced Microsoft multi-tenant CVE) will populate `email` from a self-service or unverified attribute for certain account types (e.g., personal/consumer accounts, guest/B2B invited accounts, or accounts where email is user-editable prior to verification). If the Chainlink operator's IdP tenant allows any such account type — mirroring exactly the vulnerable configuration class in CVE-2023-46241 ("Accounts in this organizational directory only" not enforced) — an attacker who registers or edits an IdP account to claim a victim's email can complete the OIDC flow and receive a Chainlink session for that email/role.

### Impact Explanation
Because role is derived purely from IdP group claims and email is taken from the unverified claim, an attacker can potentially impersonate any Chainlink node user (up to Admin, if they can also satisfy or spoof the configured `AdminClaim` group) by controlling an IdP identity with a matching unverified email. This grants full node control: managing jobs/bridges, viewing/managing keys via the authenticated API surface, matching the CVSS 9.0 "account takeover" class of the referenced advisory.

### Likelihood Explanation
Exploitability depends entirely on the operator's IdP tenant configuration — if the configured OIDC provider allows self-registration or unverified/editable email on any account type reachable by outside users (not restricted to a single verified-email-only tenant), this is directly exploitable by an unprivileged external actor with no special access, exactly the precondition called out in the source CVE. Chainlink's own code provides no compensating control (no `email_verified` check, no binding to IdP `sub`), so the entire mitigation burden rests on IdP-side configuration that is easy to get wrong.

### Recommendation
- Check `email_verified` (or provider-equivalent) in the ID token claims in `handleTokenExchange` and reject/require re-verification if false or absent.
- Bind the local session/user identity to the immutable OIDC `sub` claim (per issuer) rather than (or in addition to) the mutable/unverified `email` claim, storing a `sub`→user mapping.
- Document/enforce in `NewOIDCAuthenticator` startup validation that the configured IdP application/tenant only allows verified-email account types, or add a config flag to require `email_verified`.

### Proof of Concept
1. Configure Chainlink's OIDC provider against a real-world IdP tenant that permits account types with unverified/self-set email (e.g., a multi-tenant/consumer-allowed Azure AD app or a similar OIDC IdP without enforced email verification for guest/self-service accounts).
2. Attacker registers or edits an IdP account so its `email` claim equals a target victim node-user's email, while their account also happens to fall in a claim group mapped to `AdminClaim`/`EditClaim`.
3. Attacker completes `/oidc-login` → provider consent → `/oidc-exchange`; `handleTokenExchange` verifies the token signature (valid) and extracts `claims["email"]` (the victim's email) without checking `email_verified`.
4. `oidc_sessions` row is created with `user_email = victim@example.com` and the attacker-controlled role; the response sets the session cookie, granting the attacker a valid Chainlink session under the victim's identity/role.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired
func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
