## Title
Fee‑on‑transfer tokens break collateral accounting in `WrappedHyperFungibleTokenUpgradeable.send()`, under‑collateralizing the bridge and permanently freezing later unlocks — ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`WrappedHyperFungibleTokenUpgradeable.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain `Message` that declares `amount: params.amount` as the value to be unlocked on the destination chain. If `_underlying` is a fee‑on‑transfer token, the contract actually receives less than `params.amount`, but the full `params.amount` is still promised to the destination chain's `onAccept`, which unconditionally transfers `message.amount` out of its own locked reserve. This mirrors exactly the Teller `CollateralEscrowV1.depositAsset` bug: accounting is done on the "intended" transfer amount instead of the amount actually received.

### Finding Description
In `send()`: [1](#0-0) 

the non-WETH branch calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` with no balance-before/after check, then builds the `DispatchPost` body using the unmodified `params.amount`: [2](#0-1) 

On the destination chain, `onAccept` trusts `message.amount` verbatim and releases that full amount from its own escrow of the underlying token: [3](#0-2) 

Because the source-side contract only actually locked `params.amount - fee`, every send of a fee-on-transfer underlying creates a shortfall between what is locked on the source chain and what is promised/unlockable on the destination chain. This is the same root cause the Teller report identifies: accounting on the pre-transfer amount rather than the post-transfer balance delta.

Notably, the sibling `IntentGatewayV2.sol` (main EVM app) was hardened against exactly this class of bug — it snapshots balances before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actual received delta: [4](#0-3) 

and has dedicated fee-on-transfer regression tests confirming this fix: [5](#0-4) 

However, `WrappedHyperFungibleTokenUpgradeable.send()` has no equivalent balance check, and neither does the Tron port of `IntentGatewayV2`, whose non-predispatch escrow path also stores `reducedInputs[i].amount` (the intended, fee-adjusted amount) rather than the actual transferred delta: [6](#0-5) 

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying token silently under-funds the wrapper's on-chain reserve relative to the liabilities it has promised across the bridge (the sum of `message.amount` values dispatched to all destination deployments). As more transfers accumulate, the contract's actual underlying balance falls increasingly short of what legitimate `onAccept`/`onPostRequestTimeout` calls are entitled to unlock. Eventually, a `safeTransfer` in `onAccept` (or a timeout refund in `onPostRequestTimeout`) will revert due to insufficient balance, permanently freezing funds for legitimate later senders/recipients — a durable insolvency of the escrow backing the wrapped token. This satisfies the "unbacked mint" / "permanent freezing of funds" acceptance criteria: the destination side effectively becomes able to promise more value than the source side custodies.

### Likelihood Explanation
Any unprivileged token bridger can trigger this in a single transaction simply by calling `send()` with a fee-on-transfer (or deflationary/rebasing-on-transfer) ERC20 configured as `_underlying`. No governance or admin action is required beyond the initial (routine) `configure()` call that sets `_underlying` — which per the original Teller report's scope statement ("FEE-ON-TRANSFER: any") is an explicitly supported token class. The bug reproduces on every single send with such a token, not just an edge case.

### Recommendation
Mirror the fix already applied in `IntentGatewayV2.sol`: snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, compute the actual received delta, and use that delta (not `params.amount`) both for the dispatched `Message.amount` and for the `Sent` event. Apply the same fix to the Tron `IntentGatewayV2.sol` non-predispatch escrow branch, storing the actually-received (post-fee) balance delta in `_orders[commitment][token]` instead of `reducedInputs[i].amount`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleTokenUpgradeable` with `_underlying` set to a 1%-fee-on-transfer ERC20, `_isWeth = false`.
2. Alice calls `send({amount: 1000e18, dest: ..., to: bob, ...})`. `safeTransferFrom` pulls 1000e18 from Alice but the contract only receives 990e18 (see `WrappedHyperFungibleTokenUpgradeable.sol` lines 294-301).
3. The dispatched `Message.amount` is still 1000e18 (lines 264-271, 303).
4. On the destination chain, `onAccept` unlocks 1000e18 of the underlying to Bob's counterpart contract from its own reserve (lines 327-360), even though only 990e18 worth of collateral was ever locked on the source side.
5. Repeating this creates a growing deficit; eventually a subsequent `onAccept`/`onPostRequestTimeout` `safeTransfer` reverts for insufficient underlying balance, freezing that transfer's funds permanently.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {

        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);

            deadline: block.number + 100,

            session: address(0),

            output: output
        });
