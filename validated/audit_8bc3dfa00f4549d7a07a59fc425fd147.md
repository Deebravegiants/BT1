Pupil-contraction liveness extension accepts static/artifact-derived frames because acceptance is gated only on IR-Net sharpness/score, never on measured pupil contraction - (File: src/plans/biometric_capture/pupil_contraction.rs)

### Summary
`pupil_contraction::Plan::handle_ir_net` drives an LED brightness ramp and delegates frame acceptance entirely to `biometric_capture::Plan::handle_ir_net`/`poll_extra`, whose only accept criteria are `estimate.score >= IRIS_SCORE_MIN` and brightness range, with no comparison of `pupil_to_iris_ratio` before vs. after the ramp. Consequently the extension never verifies that a pupil actually contracted in response to the light stimulus, so a high-fidelity static printed/displayed iris image with matching IR reflectance and correct sharpness/score can satisfy every gate the code checks.

### Finding Description
`State::NoSharpIris` in `pupil_contraction.rs` waits for `biometric_capture.handle_ir_net` to return `BrokerFlow::Break` [1](#0-0) . That underlying acceptance is computed in `biometric_capture/mod.rs` purely from `estimate.score >= IRIS_SCORE_MIN` and, if auto-exposure is enabled, `IRIS_BRIGHTNESS_RANGE.contains(&frame.mean())` [2](#0-1) . Once a sharp/high-score frame is captured, the state machine moves through `RampingUp` (which only computes an LED brightness ramp value and pushes MCU commands) and `Waiting` (which only waits for `WAIT_TIME` to elapse) before calling `BrokerFlow::Break` to complete the extension [3](#0-2) . `poll_extra` itself performs no additional check at all — it is a pure passthrough to `biometric_capture.poll_extra` [4](#0-3) .

Critically, `ir_net::EstimateOutput` carries a `pupil_to_iris_ratio` field [5](#0-4) , but nowhere in `biometric_capture::Plan` (fields listed at [6](#0-5) ) or in `pupil_contraction.rs` is this ratio stored, compared, or delta-checked between the pre-ramp and post-ramp frames. The extension's name and stated purpose ("force the pupil ... to contract" [7](#0-6) ) is not enforced by any code — it only modulates the LED and captures additional frames at `FPS` for later upload; it never gates signup success on an observed contraction.

Compounding this, the downstream fraud-detection pipeline that could otherwise catch spoofing is a no-op in this codebase: `FraudChecks::run` always returns an empty `Report {}` [8](#0-7)  with `N_FRAUD_CHECKS = 0` [9](#0-8) , and `detect_fraud` in `src/plans/mod.rs` explicitly states "FOSS: WE HAVE DELETED ALL FRAUD CHECKS" and unconditionally returns `Ok(false)` [10](#0-9) . So there is no secondary check (contact lens, liveness, etc.) that would compensate for the missing contraction check.

Given this, an attacker presenting a static high-resolution iris/face artifact with IR reflectance tuned to pass sharpness/brightness thresholds satisfies every check the code performs: `IRIS_SCORE_MIN`, `IRIS_BRIGHTNESS_RANGE`, sharp-frame detection, and the fixed-duration ramp/wait timers, none of which measure whether the pupil size actually changed.

### Impact Explanation
This maps to a liveness/anti-spoofing bypass leading to enrollment or verification of a non-live subject (identity spoofing), a recognized Orb bounty impact category. Because `detect_fraud` and `FraudChecks::run` are hard-coded no-ops in this build, the pupil-contraction extension is effectively the only liveness signal in the biometric capture path, and it is not actually checked/enforced.

### Likelihood Explanation
Feasible for any unprivileged party who can physically present an artifact to the Orb: no operator, hardware tampering, or credential access is required. The attacker only needs to reproduce IR reflectance/sharpness/brightness in the artifact — properties reproducible with printed/displayed materials under controlled illumination — since the code never inspects `pupil_to_iris_ratio` change over time. The attack is repeatable across signup attempts since the check logic is deterministic and stateless per-signup.

### Recommendation
In `pupil_contraction.rs`, record `pupil_to_iris_ratio` (or an equivalent pupil-size metric) from the IR-Net estimate captured in `State::NoSharpIris` before the ramp, and again during/after `RampingUp`/`Waiting`; require a statistically significant, monotonic decrease correlated with the LED brightness increase before allowing `BrokerFlow::Break`/enrollment to proceed. Reject captures where the ratio change is absent, inconsistent with the light stimulus timing, or below a defined minimum contraction threshold. This check should be wired into `poll_extra`/`handle_ir_net` here rather than silently delegating to the unrelated `biometric_capture` sharpness gate, and should feed into `enroll_user`/fraud reporting so a failed liveness check blocks enrollment.

### Proof of Concept
Add a unit/integration test in `src/plans/biometric_capture/pupil_contraction.rs` (or a new test module) that:
1. Constructs `pupil_contraction::Plan` with a mocked `biometric_capture::Plan`.
2. Feeds a sequence of `ir_net::EstimateOutput` frames simulating a static artifact: identical (or near-identical) `pupil_to_iris_ratio` across the entire `RampingUp`/`Waiting` sequence, but `score >= IRIS_SCORE_MIN` and mean brightness within `IRIS_BRIGHTNESS_RANGE` throughout.
3. Calls `handle_ir_net` repeatedly through `NoSharpIris -> RampingUp -> Waiting` and asserts that today's code returns `BrokerFlow::Break` (i.e., "accepts" the artifact) despite zero pupil-size change — demonstrating the vulnerability.
4. After applying the fix, assert the same input sequence causes `handle_ir_net`/`poll_extra` to reject (never reach `BrokerFlow::Break`, or set a rejection/fraud flag) because no measurable contraction was observed, while a synthetic sequence with a genuine ratio decrease over time is accepted.
