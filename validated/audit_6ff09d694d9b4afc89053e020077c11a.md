### Title
Excess native-token refund on `EvmHost.dispatch()` fee swaps is trapped in the host contract instead of being returned to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
The reported bug class is about a fee-related address field/parameter that is declared in the interface but never honored, causing fees/refunds to be misdirected. The closest reachable analog in this codebase is in `EvmHost.dispatch(DispatchPost)` / `dispatch(DispatchGet)`: when a caller overpays native ETH to cover the relayer fee, the Uniswap V2 swap's leftover ETH refund is sent to `address(this)` (the `EvmHost` contract) rather than to the original caller (`_msgSender()`), because `EvmHost` itself is the direct caller of `swapETHForExactTokens`.

### Finding Description
`EvmHost.dispatch(DispatchPost memory post)` performs the fee payment like this: [1](#0-0) 

When `msg.value > 0`, it calls the configured `uniswapV2` router's `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` directly from the `EvmHost` contract. In the standard `UniswapV2Router02` implementation (and the project's own wrapper implementations, e.g. `UniV3UniswapV2Wrapper.swapETHForExactTokens`), any unspent ETH is refunded to `msg.sender` of the swap call: [2](#0-1) 

Because `EvmHost` is the direct caller of the router (not a low-level call that preserves the original tx sender), the refund recipient resolved by the router is `address(this)` (`EvmHost`), not the account that called `EvmHost.dispatch()` and supplied the excess `msg.value`. There is no code path in `dispatch()` that forwards any leftover native balance back to `_msgSender()`. The same pattern repeats in `dispatch(DispatchGet memory get)`.

By contrast, the `HostParams.feeToken`/`FeeMetadata` design elsewhere in the protocol treats the payer/refund target as an explicit, honored field (e.g., `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})`, and the timeout paths correctly `safeTransfer` the fee back to `meta.sender`): [3](#0-2) [4](#0-3) 

But no equivalent honoring exists for the *native-token overpayment* refund path in `dispatch()` — the excess ETH silently accrues on the host contract's own balance instead of returning to the payer, which is directly analogous to the audited bug: a fee-related destination is never correctly routed to the party the caller/spec expects, and value ends up parked in an unintended location.

### Impact Explanation
Any unprivileged caller of `IDispatcher(host).dispatch{value: msg.value}(post)` who supplies `msg.value` greater than what the Uniswap swap actually consumes for `post.fee` loses the difference — it becomes stuck in the `EvmHost` contract's native balance rather than being returned to them. This is a direct, unbacked loss of user funds reachable from a single transaction to a permissionless entry point (`dispatch`), which any application, integrator, or the `HyperbridgeLzEndpoint` (which calls `dispatch{value: msg.value}(request)` on behalf of end users) can trigger. Funds are only recoverable later via governance's `withdraw()`, and even then go to whatever beneficiary governance selects — not back to the original overpaying sender. This matches the required impact bar: concrete freezing/misdirection of user funds.

### Likelihood Explanation
Likelihood is high in practice: every non-EVM-native dApp or SDK caller estimating gas conservatively (or any caller that doesn't compute the exact router-quoted amount) will send `msg.value` with slack to avoid reverts. The `HyperbridgeLzEndpoint.quote()` function explicitly applies a 2x buffer on the native fee quote specifically to "absorb" fee model differences, guaranteeing routine overpayment on every native-fee dispatch through that adapter: [5](#0-4) 

This means the buffer built into the standard SDK path (2x) is the exact overpayment that gets trapped on every dispatch that pays with native token, not just an edge case.

### Recommendation
In `EvmHost.dispatch()` (both `DispatchPost` and `DispatchGet` overloads), capture the contract's native balance before/after the `swapETHForExactTokens` call (or read the router's returned `amounts[0]`) and forward any unspent ETH back to `_msgSender()` (or to `post.payer`) instead of letting it sit as `address(this)` balance. Alternatively, route the swap through a wrapper contract that forwards refunds to the original caller (as `UniV4UniswapV2Wrapper` correctly demonstrates by refunding to `msg.sender` who in that design equals the true caller) rather than calling the router directly from `EvmHost`.

### Proof of Concept
1. Deploy `EvmHost` with a configured `uniswapV2` router and `feeToken`.
2. Any user calls `dispatch{value: 5 ether}(DispatchPost{... fee: 0.1e18 (feeToken units) ...})` intending to pay a small relayer fee in native token.
3. `EvmHost` executes `swapETHForExactTokens{value: 5 ether}(0.1e18, [WETH, feeToken], address(this), block.timestamp)`.
4. The router spends only the ETH needed for `0.1e18` fee tokens and refunds the remainder (~4.9 ether) to `msg.sender` of the swap call — which is `EvmHost` itself.
5. `EvmHost`'s native balance increases by ~4.9 ether; the user who sent the transaction receives nothing back and has no on-chain path to reclaim it. Only cross-chain governance via `HostManager.withdraw()` can move that ETH, and only to a beneficiary of governance's choosing, not the original user.
