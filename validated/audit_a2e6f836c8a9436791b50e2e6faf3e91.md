Found it: the webhook HMAC in `Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`) only signs `@raw_body` (`to_signable_string` returns `@raw_body`), while `topic`, `shop`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers (`shopify_header`). None of these header fields are covered by the HMAC computation, yet `Registry.process` uses `request.topic` to select the handler and passes `request.shop` straight into the `WebhookMetadata` delivered to the app's handler.

### Title
Webhook `shop` and `topic` identity fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)` [1](#0-0) , which computes the HMAC exclusively over `request.to_signable_string`, itself just the raw body bytes [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled from HTTP headers via `shopify_header`, which are never part of the signed payload [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop == the tenant whose data the raw_body actually belongs to`. Because the HMAC only proves that the caller possesses the app's shared secret and that the given `@raw_body` bytes are unmodified, it proves nothing about which shop the headers claim to represent. Any party who can produce a valid HMAC over a body (e.g. Shopify delivering a genuine webhook for Shop A, or replaying/relaying a previously captured payload) can pair that same signed body with arbitrary `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` header values, and `HmacValidator.validate` will still return `true` because those fields are outside `to_signable_string`. `Registry.process` then trusts `request.topic` to route to a handler and forwards the attacker-controlled `request.shop` into `WebhookMetadata` [1](#0-0) , so an app's handler that keys off `data.shop` to select which tenant's records to update can be made to act on the wrong tenant.

### Impact Explanation
This breaks the shop-identity binding that webhook consumers rely on for tenant isolation: a handler receives `WebhookMetadata#shop` believing it was authenticated by the same HMAC that authenticated the body, but it wasn't. This is a cross-tenant integrity issue — an attacker who obtains one validly-signed webhook delivery (which reaches any endpoint that logs or exposes body/headers, or via a compromised/duplicated request) can relabel it to a different `shop`, causing the host app to process/store data under the wrong tenant record.

### Likelihood Explanation
Exploitability depends on an attacker being able to submit a request with a valid raw-body HMAC but attacker-chosen headers to the app's webhook endpoint. Since the header values are never authenticated by this gem, the exploit surface is entirely determined by whether the host application's transport (not this gem) prevents header tampering; if it does not, likelihood is high given how straightforward reordering the signed/unsigned fields would be. This is a real design gap in `Webhooks::Request`, independent of the specific transport used.

### Recommendation
Extend `to_signable_string` (or the `HmacValidator` contract for webhook requests) to bind `shop`, `topic`, `webhook_id`, and `api_version` together with the raw body, or otherwise require the consuming application to independently verify the shop header against a known/enrolled shop list before trusting `WebhookMetadata#shop`.

### Proof of Concept [4](#0-3) 
1. Capture a valid webhook delivery for `shop-a.myshopify.com` with raw body `B` and its correct `shopify-hmac-sha256` value `H` (valid because `H = HMAC(secret, B)`).
2. Replay the same `B` and `H` to the app's webhook endpoint, but substitute the header `shopify-shop-domain: shop-b.myshopify.com` (and/or a different `shopify-topic`).
3. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` which still equals `H`, so validation passes [5](#0-4) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, delivering `shop-b.myshopify.com` as the shop even though the payload actually belonged to `shop-a` [6](#0-5) .

        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
