### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that the body hashes correctly against the app's shared secret via `HmacValidator.validate(request)` [3](#0-2) , then forwards `request.shop` straight into the `WebhookMetadata` struct that is handed to the app's handler [4](#0-3) , with no independent check binding that shop value to the signed body. This breaks the equality `shop_asserted_by_header == shop_bound_by_hmac`, since the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across *every* shop that has the app installed [5](#0-4) .

### Finding Description
Because the same app-wide secret is used to compute the HMAC for every tenant's webhooks, any shop that has legitimately installed the app can capture a genuinely-signed `(raw_body, hmac)` pair from its own webhook deliveries. Since the `x-shopify-shop-domain` header is not part of the signed content, that captured pair can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a different (victim) shop's domain. `HmacValidator.validate` will still succeed, because `validate_signature` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the received `hmac` [6](#0-5) ; it never checks that `shop` is consistent with anything cryptographically bound to the request. `Registry.process` then dispatches the handler with `WebhookMetadata` carrying the forged `shop` value [7](#0-6) , and the app-level handler (which trusts `data.shop` per the library's documented contract in `WebhookHandler#handle`) will act on the victim tenant's identity using attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker who legitimately controls one tenant (shop A) of a multi-tenant app can make the app process webhook events "as if" they came from a different tenant (shop B), because the shop identity is asserted by an unauthenticated header rather than bound into the signed payload. Depending on how the host app's `WebhookHandler` implementations use `data.shop` (e.g., `app/uninstalled` triggering session/token deletion, `shop/redact` triggering data deletion, or `orders/create` writing data under a shop record), this enables cross-tenant data corruption, unauthorized state changes, or forced data deletion against a shop the attacker does not control — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker operate an app installation on at least one shop (the normal, unprivileged state for any merchant installing the app) and be able to send a crafted HTTP POST directly to the app's public webhook receiver endpoint with a captured body/HMAC pair and a modified `shop-domain` header — no access token, `client_secret`, or privileged credential is needed. The only constraint is that the forged webhook's usable "payload" is limited to content the attacker's own shop legitimately received (since they cannot forge new content without the secret), but topic type and timing can be controlled by triggering the attacker's own store events.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC computation, or otherwise cryptographically tie them to the signed body, so that `to_signable_string` cannot be satisfied by an HMAC computed for a different shop/topic combination. At minimum, `Registry.process` should reject requests where header-derived identity fields are not verifiable against the signed payload, rather than trusting `request.shop` outright.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` (both tenants of the same app, sharing one `client_secret`).
2. Attacker triggers an event on their own shop (e.g., updates a product) to receive a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` where `H = HMAC-SHA256(client_secret, B)`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker POSTs directly to the app's webhook endpoint with the same `raw_body = B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` [3](#0-2)  — validation succeeds.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [4](#0-3)  and performs its shop-scoped action against the victim tenant using attacker-supplied data.
