### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but its `to_signable_string` only returns the raw request body. `Utils::HmacValidator.validate` therefore only proves that the *body bytes* were signed with `Context.api_secret_key` — it proves nothing about which shop, topic, or webhook id the request claims to be for. `Webhooks::Registry.process` nonetheless trusts these unauthenticated header values to route the event to a handler and to populate `WebhookMetadata#shop`/`#topic` that the host application uses to identify the tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body is included in the signable string, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from request headers with no cryptographic binding to that body: [2](#0-1) 

`Webhooks::Registry.process` validates only the HMAC over the body, then immediately uses the unauthenticated `topic` to select the handler and the unauthenticated `shop` to build the metadata passed to that handler: [3](#0-2) 

The `HmacValidator.validate` implementation confirms the check is purely `HMAC(secret, verifiable_query.to_signable_string) == received_hmac`, with no reference to shop/topic: [4](#0-3) 

The binding that is broken (as an equality the gem should enforce but doesn't):
`shop-domain header used for tenant attribution == shop that Shopify actually signed the payload for`
and
`topic header used for handler dispatch == topic Shopify actually signed the payload for`

Neither holds, because the HMAC only commits to the raw body bytes, not to the headers. Any entity that possesses one legitimately Shopify-signed `(raw_body, hmac)` pair for *any* shop/topic (e.g., the operator of their own store with the app installed, who can trivially trigger and capture a webhook delivery) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop and/or the `X-Shopify-Topic` header for a different registered topic. `HmacValidator.validate` will still pass (it never looked at those headers), `Registry.process` will route to whatever handler matches the forged `topic`, and the handler will receive `WebhookMetadata` claiming the event is `shop: <victim-shop>`.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem hands the host application data that is misattributed to an arbitrary victim shop, or dispatched to a handler for a topic the payload was never signed for, while presenting it as validated ("HMAC ok"). Applications built on this gem typically use `WebhookMetadata#shop` to look up per-shop sessions/state and act on the shop's behalf, and use `#topic` to decide what privileged action to take (e.g., `customers/redact`, `shop/redact`, order/fulfillment processing). Forged shop attribution combined with forged topic routing can cause the app to perform actions against the wrong tenant's data or invoke a handler with a body it never expected, which fits the "cross-tenant access" high/critical impact bucket.

### Likelihood Explanation
Moderate-to-low: the attacker needs at least one valid `(raw_body, hmac)` pair signed by the target app's `api_secret_key`. The easiest way to obtain one is to install the app on the attacker's own shop and capture any real webhook delivery, then replay it with modified `shop-domain`/`topic` headers pointed at another (victim) shop that also has the app installed. This does not require knowledge of `api_secret_key`, an access token, or any privileged credential — only participation as an ordinary merchant/installer of the app, matching the "unprivileged internet user" threat model.

### Recommendation
Include the `shop`, `topic`, and `webhook_id`/`api_version` values in the HMAC-signable content (or otherwise cryptographically bind them to the verified payload), so that `to_signable_string` commits to everything the gem subsequently trusts and acts on — not just the raw body. At minimum, document/enforce that `Registry.process` must not trust header-derived `shop`/`topic` for tenant or handler-dispatch decisions unless the app independently confirms the shop against its own stored session for that shop, since the gem currently offers no such guarantee.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g. `app/uninstalled`), capturing the raw request body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and (if desired) `X-Shopify-Topic: customers/redact`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers un-authenticated: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body`, then dispatches using the forged `topic` and constructs `WebhookMetadata` with the forged `shop`: [3](#0-2) 
5. The host application's handler receives data it believes is a validated event for `victim-shop.myshopify.com` under topic `customers/redact`, even though it was never signed for that shop or topic.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
