### Title
Unsigned cross-chain calldata in `pallet-hyper-fungible-token` dispatches arbitrary runtime calls as the beneficiary account without authentication - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
This is the closest structural analog to the OpenOLAT SSTI bug class: untrusted, attacker-controlled payload data is deserialized and then *executed* server-side with meaningful privilege, rather than merely stored or displayed. In OpenOLAT, an Author-controlled Velocity template string gets evaluated by the server as code. In `pallet-hyper-fungible-token::on_accept`, an attacker-controlled `message.data` field carried inside a cross-chain token-transfer message is decoded into a `RuntimeCall` and *dispatched* (`runtime_call.dispatch(...)`) with `RawOrigin::Signed(origin)` — and when no signature is attached, `origin` is derived directly from the untrusted `message.from` bytes.

### Finding Description
`on_accept` in [1](#0-0)  processes the optional `data` field of an incoming `Message` as a `SubstrateCalldata { signature: Option<...>, runtime_call: Vec<u8> }`. If `signature` is `None`, the origin used for dispatch is computed purely from `message.from`: [2](#0-1) 

`message.from` is not authenticated against anything — it is simply a field of the ABI-encoded `Message` struct that originates from the sending contract on the source chain, and its content is entirely controlled by whoever calls the source-chain HFT/WrappedHFT contract's `send()` (an unprivileged, permissionless external function, see `IHyperFungibleToken.send`, e.g. `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`). The Solidity side does not attempt to constrain `from` to `msg.sender`; the field is documented purely as "original sender (for timeout refunds)" (see `docs/content/developers/evm/hyper-fungible-token/overview.mdx`, `Message.from`). The pallet's `on_accept` handler only checks that the request comes from a *registered peer contract address* on the source chain via `ContractToAsset`, not that `from` matches any expected caller.

Consequently, any account able to invoke the source-chain HFT `send()` function (any unprivileged EVM user) can set `message.from` to an arbitrary 20-byte (or 32-byte, for substrate sources) value, and set `data` to an ABI/SCALE-encoded `SubstrateCalldata` with `signature = None` and any `runtime_call`. When relayed and accepted on the Polkadot side, `T::EvmToSubstrate::convert(H160::from(from_bytes))` maps that attacker-chosen address to a *substrate account*, and the pallet dispatches the attacker-supplied `RuntimeCall` **as that account**, via `RawOrigin::Signed`.

This is functionally equivalent to the SSTI pattern: attacker-controlled data that should be inert (a bridging message) is decoded into an executable construct (`RuntimeCall`) and evaluated (dispatched) with real signing authority, without any actual cryptographic proof that the account authorized the call. The only gate is `BaseCallFilter::contains(&runtime_call)` [3](#0-2) , which filters *which* calls are permitted runtime-wide, but does not verify *who* actually authorized this specific call.

### Impact Explanation
Any `RuntimeCall` not blocked by the runtime's `BaseCallFilter` can be dispatched with `Signed` origin of an arbitrary, attacker-chosen substrate account (derived from an arbitrary EVM address the attacker supplies as `from`). Concretely this allows:
- Transferring away the balance of any account whose derived address the attacker names as `from` (e.g. `Balances::transfer_all` from that account to the attacker), constituting theft of funds.
- Calling other pallets' dispatchables (subject only to the base call filter) as an account the attacker does not control the private key of — this can be used to drain assets, manipulate other pallet state (e.g. asset transfers, staking operations), or perform unauthorized app actions signed by a victim identity.
- Because `EvmToSubstrate::convert` maps *any* EVM address to *some* substrate account deterministically, an attacker can target any account whose EVM-mapped substrate identity holds funds, without needing that account's private key at all.

This meets the "concrete theft of funds" / "unauthorized app action" bar in the validation criteria, and is reachable from a single unprivileged, permissionless transaction (calling `send()` on the source-chain HFT contract), matching the reachability constraint ("token bridger" path explicitly listed as in-scope).

### Likelihood Explanation
High. `send()` on `HyperFungibleToken`/`WrappedHyperFungibleToken` is a public, unprivileged function callable by anyone; `data`/`call_data` is an arbitrary user-supplied field with no validation against `msg.sender`, and reaches `on_accept` unauthenticated aside from checking that the message came from a registered peer *contract address* (not that `from` matches the caller). No relayer collusion or governance/admin compromise is required — a single crafted cross-chain message, delivered by any relayer (a role that is itself intended to be trustless/permissionless in ISMP), triggers the dispatch.

### Recommendation
- Require `substrate_data.signature` to always be present and valid before dispatching any `RuntimeCall`; never fall back to deriving a signing origin purely from the unauthenticated `message.from` field.
- Alternatively, if the "no signature" path is intended to represent "act as the token sender," derive `origin` only from a value that is provably tied to `msg.sender` on the source chain (e.g. have the source contract set `from = msg.sender` and be unable to override it), and document/enforce that invariant on both the Solidity and pallet sides.
- Add integration tests asserting that a `data` payload with `signature = None` cannot cause the pallet to dispatch privileged operations (e.g. balance transfers) as an account the caller does not control.

### Proof of Concept
1. Deploy/target an EVM chain's `HyperFungibleToken`/`WrappedHyperFungibleToken` contract registered as a peer of `pallet-hyper-fungible-token` on the Polkadot side.
2. As an unprivileged attacker EOA, call `send()` with:
   - `to` = attacker-controlled recipient address (for the token transfer itself, incidental).
   - `data` = ABI-encoded `Call[]` is not used here; instead craft `message.data` (per `Message.data` field documented in `docs/content/developers/evm/hyper-fungible-token/overview.mdx`) to be a SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded Balances::transfer_all(dest: attacker, keep_alive: false)> }`.
   - Set the EVM `from` field of the outgoing ISMP request (source-chain contract's `from`, propagated into `Message.from`) to the 20-byte representation of the victim's EVM-mapped address (i.e., an address the attacker knows maps via `EvmToSubstrate` to a funded substrate account).
3. Relay the request to Hyperbridge/Polkadot; `pallet-hyper-fungible-token::on_accept` decodes the message, sees `signature.is_none()`, computes `origin = EvmToSubstrate::convert(H160::from(from_bytes))`, decodes `runtime_call`, checks only `BaseCallFilter`, then calls `runtime_call.dispatch(RawOrigin::Signed(origin))`.
4. If `Balances::transfer_all` (or another call moving funds) is not blocked by the runtime's `BaseCallFilter`, the victim's substrate-mapped account funds are transferred to the attacker without any signature ever being verified from that account.

Note: exact exploitability depends on the specific runtime's `BaseCallFilter` configuration (e.g. `IsmpCallFilter` seen in `parachain/runtimes/gargantua/src/lib.rs` / `parachain/runtimes/nexus/src/lib.rs` only filters ISMP-specific calls, not general dispatchables like `Balances`), which I was not able to fully audit within the available context — a Devin session with full repo access should confirm which runtime(s) configure `hyper-fungible-token::Config` and what their concrete `BaseCallFilter` allows through.

					},
					MultiSignature::Eth(_) => Err(HftError::EthSignatureUnsupported)?,

				if source.is_evm() {
