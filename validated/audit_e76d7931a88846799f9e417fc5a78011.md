I have enough evidence to identify the vulnerability. The core finding is in the webhook processing flow: `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `Webhooks::Registry.process` trusts `request.shop` and `request.topic` (parsed from unauthenticated headers) to route/attribute the webhook, without those fields being covered by the HMAC signature.### Title
Webhook tenant identity (`shop`) and routing (`topic`) are trusted from unauthenticated headers while HMAC validation only covers the raw body - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body [1](#0-0) , but then uses `request.shop` and `request.topic` — values parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` and `shopify-topic` / `x-shopify-topic` HTTP headers — to select the handler and to populate `WebhookMetadata` used by the host application for tenant attribution [2](#0-1) . Those header values are never included in the HMAC-signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`shop` and `topic` are read directly from headers with no cross-check against the signed payload: [4](#0-3) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and the app's `api_secret_key`: [5](#0-4) 

This breaks the intended identity binding: `shop authenticated (i.e., cryptographically bound by the HMAC) == shop used to attribute/process the webhook`. In this implementation, the right-hand side (`request.shop` passed into `WebhookMetadata`) is populated from a header that is completely outside the HMAC's scope, so the equality does not hold — only the body bytes are bound to the secret, not the shop or topic that determine how those bytes are processed.

Any party capable of obtaining one genuine webhook (valid raw body + valid HMAC) for a topic your app subscribes to — e.g., an unprivileged merchant who installs the app on their own store and triggers a webhook-generating event — can capture that `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. Because `Utils::HmacValidator.validate` never inspects the `shop` header, the forged request passes validation, and the gem hands the host application a `WebhookMetadata` claiming the payload belongs to whatever shop the attacker specified in the header, while the request handler was still selected using the equally unauthenticated `topic` header.

### Impact Explanation
This is a High severity cross-tenant integrity issue: an attacker with a legitimate, otherwise-unprivileged relationship to the app (their own shop) can cause the gem to report webhook data as originating from a different, targeted shop domain of their choosing. Because host applications built on this gem (per its documented API in `docs/usage/webhooks.md`) rely on `WebhookMetadata#shop` as the trusted tenant key to look up sessions, update records, or take shop-scoped actions, this can lead to cross-tenant data corruption or the app performing sensitive actions (e.g. mandatory GDPR topics like `customers/redact`, `shop/redact`) attributed to the wrong merchant, without needing the target's access token or credentials.

### Likelihood Explanation
Exploitation requires only the ability to trigger one genuine webhook delivery from any Shopify store (trivial for a developer/dev-store account, which is essentially free and unprivileged relative to any specific target shop) and the ability to POST arbitrary headers to the app's public webhook endpoint. No access to the target's credentials, session, or `client_secret` is required. The `topic`/`shop` headers being excluded from the signable string is the direct, structural root cause, matching exactly the reported bug class of "a field acted on but not covered by the HMAC."

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values in the HMAC-signed content that `to_signable_string` produces, or otherwise cryptographically bind them to the raw body before trusting them for routing/attribution — mirroring the OAuth `AuthQuery#to_signable_string`, which does include `shop` in its signed parameters [6](#0-5) . At minimum, the gem should document that `request.shop`/`request.topic` are unauthenticated and must not be used as tenant keys without independent verification (e.g., matching against a known/installed shop list).

### Proof of Concept
1. App developer creates/controls their own Shopify store `attacker-shop.myshopify.com`, installs the target app, and subscribes to a webhook topic the app registers (e.g., `orders/create`).
2. Trigger the webhook naturally; capture the resulting `raw_body` and the genuine `x-shopify-hmac-sha256` header value — both are valid because they are computed by Shopify using the real `api_secret_key`.
3. Replay this exact `raw_body` + `hmac` header to the app's public webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — it matches, so validation succeeds [1](#0-0) .
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop` [7](#0-6) . The host app's handler now processes attacker-controlled data under the victim shop's identity.
