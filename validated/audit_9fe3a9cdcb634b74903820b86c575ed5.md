### Title
Webhook `shop` identity is taken from an HMAC-unauthenticated header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity using `Utils::HmacValidator.validate(request)`, but the HMAC signature only covers the raw request body. The `shop` identity that gets handed to the app's webhook handler is read from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed bytes. This is the same class of bug as the EVMC_DELEGATED report: a security-relevant field (there, the delegation flag on the call frame; here, the shop/tenant identity on the webhook) is *acted upon* by downstream logic without being *bound* to the value that was actually authenticated (there, the CREATE/CREATE2 sender check; here, the HMAC digest).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the body’s HMAC and then trusts `request.shop` when constructing the metadata passed to the app’s handler: [4](#0-3) 

So the equality the gem implicitly claims to enforce is:
`shop_the_HMAC_authenticated == shop_passed_to_handler`

but what it actually enforces is only:
`hmac(secret, raw_body) == received_hmac`, while `shop_passed_to_handler` comes from an independent, unauthenticated header.

### Impact Explanation
Any party who can obtain one genuine, correctly-signed webhook delivery for a shop they control (e.g., a merchant who installs the app on their own store and triggers a webhook topic) possesses a `(raw_body, hmac)` pair that is valid for that body regardless of headers. Because the `shop-domain` header sits outside the signed bytes, that same body/HMAC pair can be replayed with the `shop-domain` header rewritten to any other shop's domain, and `HmacValidator.validate` will still pass since it only checks the body against the HMAC. The `Registry.process` handler then receives `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) 
If the host application’s webhook handler uses `data.shop` to look up per-tenant session/access-token data or to perform tenant-scoped writes (the documented, expected usage pattern), this becomes a cross-tenant identity confusion: attacker-controlled data is processed under a victim shop's identity.

### Likelihood Explanation
Exploitability requires only an unprivileged attacker who can install the app on any shop (including a free/test store) to legitimately trigger one webhook for a topic the app has registered, then replay that request against the app’s webhook endpoint with a forged `shop-domain` header. No `api_secret_key`, access token, or privileged account for the *victim* is needed — only a normal merchant relationship for the *attacker's own* shop, which satisfies the "unprivileged internet user" bar since the harm lands on a different tenant than the one that authenticated the request.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value verified by the HMAC, or otherwise cryptographically bind the header values to the signed body (e.g., include them in the signable string, or require the webhook consumer to cross-check the header-derived shop against a shop recorded when the specific `webhook_id` was registered/delivered). At minimum, document clearly that `request.shop` is not covered by HMAC verification and must not be trusted for tenant-scoping without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets it register a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app: body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and replays a POST to the app's webhook endpoint with the same body `B` and same `H`, but with header `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `HMAC(secret, B)`: [6](#0-5) 
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the app’s handler, which processes attacker-supplied body content under the victim shop’s identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
