### Title
Webhook shop/topic/id headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` binds *only* the body bytes. The `shop`, `topic`, `webhook_id` and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` reads from HTTP headers and forwards to the app's webhook handler are never covered by that signature, so any request with a body/HMAC pair that is valid for the app's secret (e.g. one the attacker legitimately received for their own shop) can be replayed with a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header and will still pass validation.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are used by `HmacValidator.validate` to verify the signature: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` only — none of `shop`, `topic`, `webhook_id`, or `api_version` are part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature purely against `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts the header-derived `shop`, `topic`, and `webhook_id` fields when dispatching to the handler: [4](#0-3) 

Because the HMAC never covers `shop`, an unprivileged merchant who has the app installed on their own store (and therefore legitimately receives real webhooks with valid `body` + `hmac-sha256` for the shared `client_secret`) can capture one such request and resend it to the app's webhook endpoint after swapping only the `X-Shopify-Shop-Domain` header to a victim shop's domain. The signature check still passes because it only re-hashes the untouched body, yet `WebhookMetadata.shop` is populated with the attacker-chosen victim domain, so the host app's handler processes/attributes the webhook as if it originated from the victim tenant. This breaks the identity binding `shop authenticated == shop the handler is told to act on`.

### Impact Explanation
This allows cross-tenant confusion: a handler that uses `WebhookMetadata#shop` to look up or mutate per-shop data (a documented, expected usage pattern of this gem) can be tricked into acting on/for a shop the attacker does not own, using only body content the attacker legitimately possesses. This matches the "cross-tenant access" Critical impact category, since the attacker never needs the app's `client_secret`, access tokens, or any credential belonging to the victim shop.

### Likelihood Explanation
Likelihood is Medium: the attacker must be a genuine merchant with the target app installed on their own shop (to obtain a valid body+HMAC pair from a real webhook delivery), and the effect depends on the webhook body being reusable/meaningful for a different shop context (e.g., topics whose body doesn't itself embed a shop identifier that the handler cross-checks). No cryptographic secret or privileged access is required — only observation of one's own legitimate webhook traffic and the ability to send an HTTP POST with modified headers.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable content, or otherwise independently authenticate the shop domain (e.g., compare it against a value derived from the app's own webhook registration/session store) before dispatching to handlers. At minimum, document prominently that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be trusted for tenant identification without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with body `{"id":1}`.
2. Attacker captures the legitimate `X-Shopify-Hmac-Sha256` header value computed over that body with the app's shared `client_secret`.
3. Attacker resends the same body/HMAC to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <captured-valid-hmac>
X-Shopify-Shop-Domain: victim.myshopify.com

{"id":1}
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature only covers the unmodified body: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the request never had valid authorization tied to `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
