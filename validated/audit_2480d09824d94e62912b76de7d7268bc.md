### Title
Webhook HMAC signs only the request body, not the `shop`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts any webhook whose HMAC matches the raw request body, but the identity fields (`shop`, `topic`, `webhook_id`, `api_version`) that are handed to the app's webhook handler come from unauthenticated HTTP headers that are never included in the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely over that signable string: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` uses this validation result as the sole authenticity check, and then builds `WebhookMetadata` directly from the request's `shop`, `topic`, `webhook_id`, and `api_version` accessors: [3](#0-2) 

Those accessors read straight from HTTP headers with no cryptographic binding to the HMAC: [4](#0-3) 

The equality that the bug class targets is: **bytes verified by the HMAC (`@raw_body`) ≠ bytes parsed and trusted as tenant identity (`shop`, `topic`, `webhook_id` headers)**. Since only the body is authenticated, an attacker who possesses any single valid `(body, hmac)` pair — trivially obtainable by installing the app on their own store and receiving one legitimate webhook to a server they control — can replay that exact body/HMAC pair while freely rewriting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers to any other value. `Registry.process` will still consider the request authentic (the HMAC over the untouched body still matches) and will invoke the registered handler with attacker-chosen `shop`/`topic`/`webhook_id` metadata.

### Impact Explanation
Apps commonly key their handler logic (and any data lookups, session retrieval, or state mutation) off `WebhookMetadata#shop`, trusting that Shopify — not an arbitrary caller — authenticated that value. Because `shop` is outside the HMAC's scope, this gem allows the identity binding "authenticated request == originating shop" to be broken, enabling one merchant/tenant to make the host application believe an event (with attacker-controlled body content matching a topic the attacker can obtain, e.g. `app/uninstalled`, `shop/update`, etc.) originated from a **different** shop. This is a cross-tenant confusion vector: the host app processes data for shop B while believing it came from (validated) shop A's webhook channel, potentially triggering account state changes, cache/session invalidation, or business logic tied to the impersonated shop.

### Likelihood Explanation
Any developer/merchant who can install the app on a shop they control receives legitimate webhooks with valid HMACs for known bodies. No secret material, access token, or privileged account is needed to then replay that body with rewritten identity headers to the app's public webhook endpoint — only network access to the endpoint, which is exposed publicly by design. Likelihood is high wherever a handler branches or persists data based on `WebhookMetadata#shop`/`#topic` without independently confirming the shop is one that actually has this topic subscribed/expected.

### Recommendation
Bind the identity headers into the signable payload (e.g., include `shop`, `topic`, and `webhook_id` in the HMAC-verified string, or require the caller to separately verify `shop` against the set of shops known to be currently installed/subscribed before trusting `WebhookMetadata#shop`). At minimum, document prominently that `shop`/`topic`/`webhook_id` are NOT covered by the HMAC and must not be trusted for tenant-identification without additional verification (e.g., cross-checking against an actively registered webhook ID for that specific shop/topic pair).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures a webhook subscription (e.g., `products/update`) pointing to a server the attacker controls, capturing one legitimate delivery: headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: products/update`, body `B`.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the exact same body `B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the signature over `B` only — matches `H` — so `Registry.process` accepts the request as authentic.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)`, causing the host app to act as if `victim.myshopify.com` sent this event, despite it never having done so.
