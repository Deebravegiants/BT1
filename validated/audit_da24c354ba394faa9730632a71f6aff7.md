## Finding: Bonding-curve AMM ignores caller-supplied FA `decimals`, letting the token creator mis-price the pool and drain real APT held by the liquidity-pair object

### Title
Unvalidated custom FA decimals let the pair creator mis-price `liquidity_pairs::get_amount_out`, draining APT custody held by the liquidity-pair object - (File: `aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move`)

### Summary
`bonding_curve_launchpad::create_fa_pair` accepts an arbitrary, caller-controlled `decimals: u8` parameter with no validation against the constant assumed elsewhere in the module [1](#0-0) . `liquidity_pairs.move` even declares a fixed `FA_DECIMALS: u8 = 8` constant, showing the pricing math was designed for a single fixed decimal precision [2](#0-1) , yet that constant is never referenced or enforced anywhere in the file. The AMM's constant-product pricing function `get_amount_out` operates purely on raw `u64` reserve amounts with no decimal normalization between the FA and APT (8 decimals, i.e. octas) [3](#0-2) . This mirrors the root cause of the external report: a value derived from token amounts is computed as if decimals were fixed/normalized, but the actual token can have a different decimal precision, corrupting the resulting allocation/exchange rate.

### Finding Description
`create_fa` mints the FA supply and creates the liquidity pair using the caller-supplied `decimals`, with the only bound being the generic `MAX_DECIMALS = 32` check inside `fungible_asset::add_fungibility` [4](#0-3) . Nothing in `bonding_curve_launchpad.move` or `liquidity_pairs.move` restricts `decimals` to the value (`8`) the AMM math implicitly assumes, and `INITIAL_VIRTUAL_APT_LIQUIDITY`/`APT_LIQUIDITY_THRESHOLD` are hardcoded octas-denominated constants [5](#0-4) .

`register_liquidity_pair` seeds the pool's `fa_reserves` with the raw (un-normalized) FA unit count and pairs it against `INITIAL_VIRTUAL_APT_LIQUIDITY` octas [6](#0-5) . Every subsequent swap (`swap_apt_to_fa`/`swap_fa_to_apt`) prices trades using the constant-product formula over these two raw counters with no decimal conversion [7](#0-6) .

Because a creator fully controls `decimals` at FA-creation time, they can pick an extremely low value (e.g. `0`) so that each raw FA unit represents a "whole token" rather than a tiny fraction. This directly changes the effective FA/APT exchange rate encoded into the constant-product curve, without changing the code's treatment of `fa_reserves` (still just a raw `u64`). The creator can then use the optional initial swap (`apt_amount_in` in `create_fa_pair`, executed inside `register_liquidity_pair`) or a follow-up transaction to extract a disproportionate amount of real APT relative to what unaware later swappers deposit, since the pool's real APT balance accrues under the liquidity-pair object's custody via `aptos_account::transfer` [8](#0-7) .

### Impact Explanation
Real APT deposited by subsequent swappers is held under the liquidity-pair object's address (an Aptos custody construct) and is paid out according to the mis-priced constant-product curve [9](#0-8) . A creator who selects an unvalidated `decimals` value can bias this curve in their favor, allowing them to drain a disproportionate share of the pooled APT from other participants — a theft of object-held value, matching the "Custody Impact Gate" criterion for theft of APT/fungible-asset value held by an object.

### Likelihood Explanation
`decimals` is a fully attacker/creator-controlled entry-function parameter with no cross-check against the AMM's implicit fixed-decimals assumption, and creating a new FA/pair is permissionless (`create_fa_pair` is a public entry function open to any signer) [1](#0-0) . No privileged access or race condition is required — any user launching a token chooses the decimals themselves, making exploitation straightforward and repeatable for every new pair they create.

### Recommendation
Enforce a single fixed decimals value (matching `FA_DECIMALS` already declared but unused, or APT's 8 decimals) for all FAs launched through the bonding curve, rejecting `create_fa_pair` calls with a different `decimals`. Alternatively, normalize `fa_reserves` and `apt_reserves` in `get_amount_out` to a common base-unit scale using the FA's actual decimals before applying the constant-product formula, analogous to correcting `tokenAllocated` to `wavaxReserve * 1e18 / floorPrice` in the original report.

### Proof of Concept
1. Call `create_fa_pair` with `decimals = 0` and `max_supply = 1_000_000` (raw units == whole tokens) plus a non-zero `apt_amount_in`.
2. `create_fa` mints `fa_minted = fungible_asset::mint(&mint_ref, (max_supply as u64))` = 1,000,000 raw FA units [10](#0-9) .
3. `register_liquidity_pair` seeds `fa_reserves = fa_initial_liquidity` (raw units, unscaled by decimals) against `apt_reserves = INITIAL_VIRTUAL_APT_LIQUIDITY = 50_000_000_000` octas, then immediately executes the creator's `apt_amount_in` swap via `get_amount_out` using this raw-unit ratio [11](#0-10) .
4. Because 1 raw FA unit at `decimals=0` is a full token (vs. `1e-8` of a token at `decimals=8`), the same integer ratio math yields a drastically different real-world exchange rate than the developers intended (as evidenced by the dead `FA_DECIMALS = 8` constant), letting the creator's initial/early swaps capture more real APT per FA than later swappers receive for equivalent FA, draining the object-held APT balance disproportionately as more users trade against the pool.

Note: I could not find any explicit validation elsewhere in the repo (outside `fungible_asset::MAX_DECIMALS`) constraining `decimals` for bonding-curve FAs, and I was unable to execute this scenario end-to-end (no test/terminal access here) to observe on-chain numeric drain magnitude — a Devin session with repo execution access would be needed to quantify exact extractable APT for a given `decimals`/`max_supply` choice.

    public fun get_amount_out(
        fa_reserves: u128,
        apt_reserves: u128,
        swap_to_apt: bool,
        amount_in: u64
    ): (u64, u64, u128, u128) {
        if (swap_to_apt) {
            let divisor = fa_reserves + (amount_in as u128);
            let apt_gained = (math128::mul_div(apt_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves + (amount_in as u128);
            let apt_updated_reserves = apt_reserves - (apt_gained as u128);
            assert!(apt_gained > 0, ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT);
            (amount_in, apt_gained, fa_updated_reserves, apt_updated_reserves)
        } else {
            let divisor = apt_reserves + (amount_in as u128);
            let fa_gained = (math128::mul_div(fa_reserves, (amount_in as u128), divisor) as u64);
            let fa_updated_reserves = fa_reserves - (fa_gained as u128);
            let apt_updated_reserves = apt_reserves + (amount_in as u128);
            assert!(fa_gained > 0, ELIQUIDITY_PAIR_SWAP_AMOUNTOUT_INSIGNIFICANT);
            (fa_gained, amount_in, fa_updated_reserves, apt_updated_reserves)
        }
    }
