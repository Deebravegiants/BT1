Audit Report

## Title
Plaintext Bridge/External-Initiator Outgoing Secrets Exposed to Read-Only `view`-Role Users via `GET /v2/bridge_types` and `GET /v2/external_initiators` - (File: core/web/router.go)

## Summary
`GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` are registered under `authv2` with no `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper, only the generic `auth.Authenticate` (session or API token) check. [1](#0-0)  This means any user provisioned with the lowest privilege `UserRoleView` role can call these routes, since role gating is only enforced inside `RequiresRunRole`/`RequiresEditRole`, which explicitly reject `UserRoleView`. [2](#0-1)  The handlers unconditionally serialize `OutgoingToken` (bridges) and `AccessKey`/`OutgoingToken` (external initiators) into the JSON response with no redaction for read paths. [3](#0-2) 

## Finding Description
`BridgeResource.OutgoingToken` is tagged `json:"outgoingToken"` (no `omitempty`), unlike `IncomingToken`, which is explicitly commented as "only provided when creating a Bridge" and tagged `omitempty`. [4](#0-3)  `NewBridgeResource` always populates `OutgoingToken` from the stored `bridges.BridgeType.OutgoingToken` field, which is persisted in plaintext. [5](#0-4)  The `Index`/`Show` handlers call `NewBridgeResource` directly with no additional filtering, and the route wiring shows these GETs have no role wrapper at all, in contrast to the `POST`/`PATCH`/`DELETE` routes on the same resource, which are explicitly wrapped with `auth.RequiresEditRole`. [6](#0-5)  The same pattern applies to `GET /v2/external_initiators`. [7](#0-6) 

This is a genuine, code-verifiable root cause: `RequiresRunRole` and `RequiresEditRole` are the only mechanisms that block `UserRoleView`, and they are simply absent from these three GET routes. [8](#0-7) 

## Impact Explanation
This does map to a real, in-scope impact category (secret/key exfiltration via node API): a `view`-role authenticated user — a role intended for read-only dashboard/monitoring access — can retrieve plaintext `OutgoingToken` (bridges) and `AccessKey`/`OutgoingToken` (external initiators), credentials that authenticate the node's outgoing calls to bridge adapters/external initiators. Possession of these lets a low-privilege user impersonate the node's outgoing calls to those third-party endpoints. This is a real permission-boundary violation, not a false positive: the code explicitly distinguishes `IncomingToken` (creation-only, `omitempty`) from `OutgoingToken` (always returned), and explicitly wraps mutating bridge/EI endpoints with `RequiresEditRole` while leaving the GET endpoints unwrapped — showing an inconsistency between the documented privilege model (`view` = read-only, no secrets) and the actual behavior.

## Likelihood Explanation
Exploitability requires only that the node deployment provisions at least one `view`-role user (a supported, documented role, created via the admin-only `POST /v2/users` endpoint) and has at least one bridge or external initiator configured. Given a valid `view` session or API token, the exploit is a single unauthenticated-role HTTP GET — fully deterministic and repeatable. No admin/host/database access is needed beyond having been granted the lowest-tier credential, which is a normal, supported operational scenario (e.g., third-party auditors, monitoring dashboards).

## Recommendation
- Redact `OutgoingToken` (and `AccessKey`/`OutgoingSecret`) from `BridgeResource`/`ExternalInitiatorResource` on read paths (`Index`/`Show`), consistent with how `IncomingToken` is already creation-only/`omitempty`.
- Alternatively, wrap `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` with at least `auth.RequiresRunRole` or `RequiresEditRole`.
- Consider hashing/rotating `OutgoingToken` similarly to `IncomingTokenHash` if outgoing-token verification can be redesigned away from plaintext comparison.

## Proof of Concept
1. As an admin, create a user with role `view` via `POST /v2/users`.
2. Authenticate as that user (session cookie or API token via `X-API-KEY`/`X-API-SECRET`).
3. Call `GET /v2/bridge_types` — response includes `attributes.outgoingToken` in plaintext for every configured bridge, per `presenters.NewBridgeResource` (core/web/presenters/bridges.go:29-41).
4. Call `GET /v2/external_initiators` — response includes `attributes.accessKey`/`attributes.outgoingToken` for every configured external initiator, per `presenters.NewExternalInitiatorResource`.
5. Confirm no `401 Unauthorized` occurs (unlike calling `POST /v2/bridge_types` with the same `view` credential, which is blocked by `RequiresEditRole`), demonstrating the GET routes bypass the role gate entirely.
6. Use the retrieved `OutgoingToken`/`AccessKey` to authenticate to the corresponding external adapter/initiator endpoint as the node.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
