### Title
Genesis state-machine commitments are silently dropped in `HandlerV2.handleConsensus`, permanently blocking message delivery for newly-onboarded state machines - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handleConsensus` stores an intermediate state's commitment only when `latestHeight != 0 && intermediate.height > latestHeight`. For any state machine that has never had a commitment recorded before (i.e. `latestStateMachineHeight == 0`), this condition is false, so the very first commitment for that chain is never written to storage — mirroring the CVE-2022-33745 pattern of a wrong flush/skip condition that omits a state update where one is actually necessary.

### Finding Description
In `handleConsensus`:
```solidity
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    StateMachineHeight memory stateMachineHeight =
        StateMachineHeight({stateMachineId: intermediate.stateMachineId, height: intermediate.height});
    host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
``` [1](#0-0) 

`latestStateMachineHeight` defaults to `0` for any `stateMachineId` this host has never recorded a commitment for. The guard `latestHeight != 0` is meant to be a monotonicity check ("only accept a strictly higher height"), but because Solidity's default `uint256` value is `0`, it also happens to gate the *initial* record for a brand-new state machine — the one case where storing unconditionally (there is nothing to be "behind") is exactly what should happen. As written, the condition can never be satisfied for a never-before-seen `stateMachineId`, so `host.storeStateMachineCommitment` is never invoked for it, regardless of how many valid consensus proofs are delivered afterward with a nonzero height.

`EvmHost.setConsensusState` can pre-seed one `(stateMachineId, height)` pair, but it is a one-shot admin function gated by `_canReinitConsensus` (`_consensusState` must be empty) [2](#0-1) , so it cannot be used to onboard every new counterparty chain added after initial deployment. Any state machine added later via governance, whose first-ever height update arrives only through `handleConsensus`, has its genesis commitment permanently dropped.

This matches the CVE-2022-33745 bug class: a condition guarding a critical state update (there: TLB flush; here: state-commitment store) uses a variable/condition that is correct in the common case but wrong in a specific edge case (variable at its default/zero value), causing the update to be silently skipped rather than performed.

### Impact Explanation
Because `EvmHost.stateMachineCommitment` returns a zero commitment when nothing was ever stored for that height, `handlePostRequests` / `handleGetResponses` / timeout handlers all check `if (root == bytes32(0)) revert StateCommitmentNotFound();` [3](#0-2) [4](#0-3) . If the genesis height for a newly added state machine is never stored, every message proof anchored at (or below) that height fails verification with `StateCommitmentNotFound`, and no relayer can ever produce a proof against a height that was skipped. This is a "route unable to deliver messages" condition — a hard, permanent denial of service for that state machine's inbound message path, satisfying the accepted-impact criteria.

### Likelihood Explanation
This triggers deterministically, with no attacker action required, the first time consensus proofs are relayed for any state machine whose `latestStateMachineHeight` is still `0` on this host (e.g., a chain onboarded after deployment, or any host that wasn't seeded via `setConsensusState` for that particular remote chain). Any permissionless relayer submitting the first consensus proof for that state machine reproduces it.

### Recommendation
Change the guard to only require monotonic progress, without conflating "never initialized" with "must not update": e.g. `if (intermediate.height > latestHeight)` (since `latestHeight == 0` is already `<=` any valid nonzero height), or explicitly special-case `latestHeight == 0` to always store. Add a regression test that delivers a consensus proof for a `stateMachineId` never seen before and asserts the resulting commitment is retrievable via `host.stateMachineCommitment`.

### Proof of Concept
1. Deploy `EvmHost`/`HandlerV2` normally; do not call `setConsensusState` for state machine `X` (so `latestStateMachineHeight(X) == 0`).
2. Have the trusted consensus client return, via `handleConsensus`, an `IntermediateState` for `stateMachineId = X` at some height `H > 0` with a valid `StateCommitment`.
3. Observe that `host.storeStateMachineCommitment` is never called because `latestHeight (0) != 0` evaluates false, so the `if` branch is skipped entirely.
4. Call `host.stateMachineCommitment(StateMachineHeight({stateMachineId: X, height: H}))` — it returns the zero-valued default commitment.
5. Any subsequent `handlePostRequests`/`handleGetResponses` call referencing height `H` for state machine `X` reverts with `StateCommitmentNotFound`, confirming messages to/from `X` can never be delivered through this height, and no later proof can fix it retroactively since the height check only compares against the (still-zero) `latestHeight`.

**Caveat on confidence:** I was not able to retrieve git-blame history for this exact line (the `get_blame` tool call failed due to a missing `ref` parameter, and no further tool calls were available), so I cannot confirm whether this `latestHeight != 0` condition was introduced by a specific code-movement/refactor (as in the literal CVE) versus being an original design choice with an unintended edge case. The functional bug — genesis commitments for new state machines being unstorable — is confirmed directly from the current source, independent of its history.
