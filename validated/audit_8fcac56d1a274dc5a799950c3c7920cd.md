## Title
Sell-then-buy sequencing can permanently brick graduation via an unguarded underflow in `canGraduate`'s USD-trigger reserve subtraction - ([File: packages/contracts/src/Bonding.sol])

## Summary
The Trezor commit fixes a `wait` value that underflowed to `4294967 seconds` because a subtraction between two unsynchronized time sources wasn't guarded. The alt.fun analog is the analogous unguarded subtraction `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` in `canGraduate` (and the sibling `reserveAsset - virtualLt` pattern reused in `previewLtUntilGraduation` and `_prepareGraduationLiquidity`), where `assetReserve` is a live/stored pair reserve and `virtualLtReserve` is a value *recovered* from `Pair.k() / Token.TOTAL_SUPPLY()` rather than tracked directly. [1](#0-0) 

## Finding Description
`canGraduate` computes the USD-trigger leg as:
```
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [2](#0-1) 

`_launchTimeVirtualLtReserve` is not a stored constant per token — it is recovered on-the-fly from `Pair.k() / Token.TOTAL_SUPPLY()` per the documented design (`AGENTS.md`/`docs/contracts-scope.md`), and `k` is fixed at mint time and never changes on `Pair.swap`. In Solidity 0.8.24 this subtraction is checked arithmetic (no `unchecked` block was found anywhere in `packages/contracts/src`), so if `assetReserve < virtualLtReserve` at the moment `canGraduate`/`previewLtUntilGraduation`/`_prepareGraduationLiquidity` execute, the call reverts with a `Panic(0x11)` instead of returning a graceful `false`/`0`.

Because a normal `sell` reduces the pair's stored asset reserve (LT) via `Router._computeSell`/`Pair.swap` while `k` (hence the recovered virtual reserve) stays fixed, any sequence of sells that drives `assetReserve` below the recovered `virtualLtReserve` would make this subtraction underflow. This is directly reachable by an unprivileged trader calling `Bonding.sell` / `Zap.sell` repeatedly, and the same expression is reused inside the phase-1 entry path (`_enterGraduating` → `_prepareGraduationLiquidity`) and in the permissionless `triggerGraduation`. A revert here on a call sequence that is otherwise supposed to succeed would either:
- brick `triggerGraduation`/the inline post-buy graduation check for that token permanently (since `canGraduate` is called unconditionally on every buy inside `_executeBuy`), freezing the curve in an unresolvable state, or
- brick view calls (`previewLtUntilGraduation`) that Zap depends on to size buys, DoS-ing further buys on that token.

I was not able to fully verify within the available context whether `Pair.swap`'s own K-invariant enforcement (the `+1` K slack noted in the scope docs) mathematically forecloses `assetReserve` from ever dropping below the recovered virtual reserve during ordinary sells — the invariant tests in `GraduationInvariants.t.sol` assert `tokenBalance() < tokenReserve()` (the *token*-side invariant), not the asset-side one that `canGraduate`'s subtraction depends on. Confirming whether a sell (or sequence of sells) can push `assetReserve` below `virtualLtReserve` requires stepping through `Pair.sol`'s reserve bookkeeping and `Router._computeSell`'s K-preservation math directly, which I could not complete in the remaining budget.

## Impact Explanation
If reachable, this is a Medium/High-severity permanent freezing bug: it would deadlock any curve token's graduation path (funds already raised on the curve, including creator/protocol fee accrual tied to trading, and the eventual LP seeding) with no admin recovery function visible in `Bonding.sol` for this specific state, and no upgrade path was indicated as available in the accessible code for an unprivileged remediation.

## Likelihood Explanation
Likelihood is **uncertain** given the depth of context I could gather in the time available. The `Router`/`Pair` K-invariant design (documented "no changes to Pair, asset-agnostic" and the `+1` K slack) may already prevent `assetReserve` from crossing below the recovered virtual reserve during normal sells, which would make this unreachable in practice. Without reading `Pair.sol`'s `swap`/`getReserves` implementation directly (not retrieved in my search results), I cannot confirm the trigger condition is reachable by an unprivileged trader.

## Recommendation
Given the uncertainty above, the concrete, low-risk fix mirroring the Trezor patch is to replace the unguarded subtraction with a saturating one (as already used elsewhere in this exact codebase, e.g. `finalizeGraduation`'s `ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0` pattern) in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`:
```
uint256 virtualLt = _launchTimeVirtualLtReserve(token_, pair);
uint256 realLtRaised = assetReserve > virtualLt ? assetReserve - virtualLt : 0;
```
This is a defensive, zero-behavior-change guard on the happy path (per the codebase's own established idiom) and removes any Panic-revert DoS/freeze surface regardless of whether the underlying invariant currently holds.

## Proof of Concept
Not confirmed — I was unable to construct or verify a concrete sell sequence that drives `assetReserve` below the recovered `virtualLtReserve` without reading `Pair.sol`'s reserve-update logic, which was not available in my retrieved context. This finding should be treated as a **hypothesis requiring verification against `Pair.sol`** (specifically `getReserves()`, `swap()`, and how `reserve1`/`assetReserve` is updated on sells) before being escalated; if `Pair.swap`'s K-invariant provably keeps `assetReserve ≥ virtualLtReserve` at all times, this analog does not hold and should be discarded.
