Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant routing while excluded from HMAC verification, enabling cross-shop webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which signs/verifies only the raw body [1](#0-0) . The `shop` value used for tenant identification and dispatched to the merchant's handler comes from the `shopify-shop-domain` HTTP header, which is never covered by that HMAC [2](#0-1) . This breaks the identity binding: `hmac_verified_bytes == raw_body`, but `tenant_acted_on == header["shop-domain"]`, and these two are never proven to correspond to the same request.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns only `@raw_body` [3](#0-2) . `HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) and compares it to the received HMAC using `Context.api_secret_key` [4](#0-3) . `Registry.process` gates entirely on this HMAC check and then immediately reads `request.shop`, `request.topic`, and `request.webhook_id` straight from headers to build `WebhookMetadata` passed to the app's handler [5](#0-4) . The constructor for `Request` only checks that the headers are *present*, not that they are authentic or bound to the signed body [6](#0-5) .

Critically, the `api_secret_key` used for HMAC verification is the **app-level** `client_secret`, shared across every shop that has installed the app — it is not a per-shop secret. Any user (including an attacker) can install the app on their own shop and legitimately trigger a real, correctly HMAC-signed webhook delivery for that shop (e.g. by creating an order). Because the shop-domain header is outside the signed content, the attacker can capture that valid `(raw_body, hmac)` pair and replay it directly to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it never inspects headers), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: `shop_authenticated_by_hmac == nil` while `shop_acted_on_by_handler == header_value`. Depending on how the app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up/update the merchant's DB record, sync inventory, issue credits, or trigger fulfillment for "that shop"), an attacker can inject attacker-controlled body content that the app processes and attributes to an arbitrary victim shop. This matches the "Impact: Critical — cross-tenant access" criterion, since it lets one tenant's data cross into another tenant's processing context purely by controlling unauthenticated header bytes.

### Likelihood Explanation
The attack requires only: (1) the ability to install the app on one's own (attacker-owned) shop — a normal, unprivileged action any merchant can take, and (2) network access to POST to the app's webhook endpoint with a captured valid body+HMAC pair and a forged shop header. No leaked credentials, TLS interception, or privileged account access is required; the `api_secret_key` never needs to be known to the attacker, since they simply replay a genuine signed delivery. This is straightforwardly reachable through the gem's own documented `Request`/`Registry.process` API.

### Recommendation
Bind the tenant identity into the verified signature material, or otherwise cryptographically tie the `shop-domain` header to the signed body. Concrete options:
- Extend `to_signable_string` in `Webhooks::Request` to include the `shop`, `topic`, and `webhook_id` headers (canonicalized) in the HMAC-signed string, matching how `Auth::Oauth::AuthQuery` includes all relevant fields in its signable string.
- Alternatively, require callers of `Registry.process` to independently verify that `request.shop` corresponds to a shop with an active session/installation known to the app before dispatching to the handler, rather than trusting the header value unconditionally.
- Document prominently that `request.shop` is unauthenticated and must not be trusted for authorization decisions without additional binding.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker.myshopify.com`, completing OAuth normally (no leaked secrets needed).
2. Attacker triggers a real webhook event (e.g., `orders/create`) on their shop, causing Shopify to deliver a legitimately HMAC-signed webhook to the app's endpoint: headers `X-Shopify-Hmac-Sha256: <valid>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, body `B`.
3. Attacker intercepts/replays this exact request but rewrites the `X-Shopify-Shop-Domain` header to `victim.myshopify.com`, keeping body `B` and the HMAC header unchanged.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only [1](#0-0)  — unaffected by the header change — so it passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed_body, ...)` [7](#0-6)  and invokes the app's handler, which now processes attacker-supplied content under the victim's tenant identity.
