## Title
Malicious order creator can permanently freeze escrowed native-token input by setting `order.user` to a contract that rejects ETH, causing `RefundEscrow` delivery to always revert - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`IntentGatewayV2`'s escrow-release path pushes native tokens directly to `order.user` via a low-level call in `_withdraw`/`_sendValue`. When an order's native-token escrow is refunded across chains via the `RefundEscrow` message, the payout beneficiary is `order.user`, a value the order creator fully controls at placement time. If that address is a contract without a payable `receive`/`fallback`, the refund can never be delivered, and because the destination side has already locked the order against future fills, the escrowed funds and the message itself become permanently stuck — an on-chain analog of the GoGoPool `cancelMinipoolByMultisig` push-payment DoS (M-07).

### Finding Description
`IntentsBase._sendValue` performs an unconditional low-level call and reverts the entire transaction if the recipient can't accept ETH: [1](#0-0) 

`_withdraw` uses `_sendValue` to pay out native-token (`token == address(0)`) escrow to `beneficiary`, and — critically — this is the *same* internal function used both for a successful fill/cancel refund and for finalizing the order (`_filled[body.commitment] = beneficiary`) in one atomic call: [2](#0-1) 

For a destination-initiated cancellation, `_cancelFromDest` immediately locks the order on the destination chain (`_filled[commitment] = order.user`), preventing any future fill, and then dispatches a `RefundEscrow` POST message back to the source chain naming `order.user` as the beneficiary — a value the canceller cannot change: [3](#0-2) 

On the source chain, `onAccept` handles `RefundEscrow`/`RedeemEscrow` by calling `_withdraw(body, ..., true)` directly, with no way to fall back to a pull-based claim if the native push fails: [4](#0-3) 

If `order.user` is a contract that reverts on receiving ETH (deliberately, by omitting `receive()`/payable `fallback()`), `_sendValue` reverts, which reverts the *whole* `onAccept` call — including the `_filled[body.commitment] = beneficiary` finalization. Because `RefundEscrow` requests are dispatched with `timeout: 0` (no timeout, per `_cancelFromSource`/`_cancelFromDest` construction), the message can never time out and be abandoned either — it is submitted, resubmitted, and always reverts, exactly mirroring the GoGoPool `cancelMinipoolByMultisig` pattern where a malicious operator's non-payable contract permanently blocks a privileged state transition that pushes funds.

The same push-without-fallback pattern also exists in the Tron variant's `withdraw()`: [5](#0-4) 

By contrast, the `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` apps in this same codebase already anticipate this exact class of bug and implement a fallback (re-wrap to ERC-20 on failed native push) precisely to avoid permanently locking funds: [6](#0-5) 
No equivalent fallback exists in `IntentsBase._sendValue`/`_withdraw`, showing the intents-escrow path was not hardened against this known bug class.

### Impact Explanation
Once destination-side cancellation locks `_filled[commitment]`, the order can never be filled again. If the native-token refund to `order.user` on the source chain always reverts, the order can also never be finalized/refunded on the source chain: the escrowed native tokens are permanently frozen in the `IntentGatewayV2` contract, and the corresponding ISMP `RefundEscrow` request becomes a permanently undeliverable message (relayers can indefinitely attempt and fail delivery, wasting gas, since `timeout: 0` prevents it from ever being abandoned via timeout). This satisfies "permanent freezing of funds" and "a route unable to deliver messages."

### Likelihood Explanation
`order.user` is fully attacker-controlled at order placement (`placeOrder`). No special privileges are required: any user can place a native-ETH-input cross-chain order naming a deliberately non-payable contract as `order.user`, then trigger `cancelOrder` from the destination chain. The bug is deterministically triggered on the very first relayed `RefundEscrow` delivery attempt, requiring no race condition or unusual timing.

### Recommendation
Adopt the pull-over-push pattern already used elsewhere in the app suite (as in `WrappedHyperFungibleToken.onAccept`): on a failed native transfer in `_withdraw`/`withdraw`, fall back to crediting an internal claimable balance for `beneficiary` (or wrap to WETH/fee-token equivalent) rather than reverting the entire finalize/refund transaction. This ensures `_filled` finalization and message delivery always succeed, decoupling escrow accounting from the beneficiary's ability to receive native value.

### Proof of Concept
1. Attacker deploys `NoReceive` — a contract with no `receive()`/payable `fallback()`.
2. Attacker calls `placeOrder` on the source chain with a native-ETH (`token == address(0)`) input and `order.user = address(NoReceive)`.
3. Before the deadline, attacker (as `order.user`, or anyone after expiry) calls `cancelOrder(order, options)` on the destination chain, which routes to `_cancelFromDest`: destination sets `_filled[commitment] = order.user` and dispatches a `RefundEscrow` POST with `timeout: 0`.
4. A relayer delivers the `RefundEscrow` POST to the source chain's `onAccept`, which calls `_withdraw(body, true, true)`.
5. `_withdraw` reaches the native-token branch and calls `_sendValue(address(NoReceive), amount)`, which reverts because `NoReceive` has no payable fallback; the entire `onAccept` transaction reverts.
6. The order is permanently stuck: destination already marked filled/cancelled (no future fill possible), and the source chain can never successfully process the refund — escrowed native ETH is frozen indefinitely, and the `RefundEscrow` message can never be delivered nor time out.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
