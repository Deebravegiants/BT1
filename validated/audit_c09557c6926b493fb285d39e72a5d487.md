## Title
Webhook `shop` (and `topic`) identity fields are not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the **raw body**, but the `shop` (and `topic`) values that are handed to the application's handler as the trusted tenant identifier come from unauthenticated HTTP headers that are never covered by that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop`, `topic`, `api_version` and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) .

`Registry.process` validates only that HMAC against the body, then forwards the header-derived `shop`/`topic` to the registered handler as if they were verified facts: [3](#0-2) .

Because the webhook signing secret is `Context.api_secret_key` (the app-wide client secret, identical for every merchant shop that has installed the app), any two shops running the same app share the same signing key, as demonstrated in `HmacValidator`: [4](#0-3) . This means the equality the library implicitly relies on — "`hmac` valid for `raw_body`" implies "`shop` header is truthfully the origin shop" — does not hold. The HMAC only proves *some* shop running this app produced that exact body; it says nothing about which shop's domain header accompanies it.

### Impact Explanation
An attacker who controls any shop that has installed the target app (e.g., a free/dev store) can:
1. Trigger a webhook event with attacker-chosen body content on their own store (a value they fully control, e.g. an `orders/create` payload with arbitrary fields).
2. Capture the resulting valid `(raw_body, x-shopify-hmac-sha256)` pair — valid because it is signed with the shared `api_secret_key`.
3. Replay that exact body/HMAC pair to the app's webhook endpoint, substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim merchant's domain.

`Utils::HmacValidator.validate` passes (the body signature is genuine), and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the victim's domain and attacker-controlled `body`. Any host application that uses `data.shop` to key writes/updates to per-tenant storage (the documented/expected usage pattern shown in `docs/usage/webhooks.md`) will attribute attacker-controlled data to a different merchant's tenant — a cross-tenant data-integrity break rooted in this gem's authentication contract, not merely a downstream app mistake.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (commonly permitted for public/dev apps) and be able to POST to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. This is a realistic, low-barrier scenario for any externally-installable Shopify app.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the signed material, or otherwise require the host app to cross-check `request.shop` against a shop that is known/authorized for this installation before trusting `WebhookMetadata.shop`. At minimum, document explicitly in `Registry.process`/`docs/usage/webhooks.md` that the HMAC check only authenticates the body and does **not** authenticate the shop-domain header, and provide a helper to verify `shop` against the app's known-installed-shops list before invoking handlers.

### Proof of Concept
1. Install the target Shopify app on an attacker-owned shop `attacker.myshopify.com`.
2. Configure a webhook (e.g. `orders/create`) and trigger it with attacker-chosen JSON body `B`.
3. Capture the resulting `X-Shopify-Hmac-Sha256` header value `H` sent by Shopify (valid because `H = HMAC-SHA256(api_secret_key, B)`).
4. Send a forged POST directly to the victim-hosted app's webhook route:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com

B
```
5. `ShopifyAPI::Webhooks::Registry.process` accepts the request (`HmacValidator.validate` succeeds because `H` is valid for `B`), and calls the app's handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body: B`, even though the request never originated from that shop.
