### Title
Webhook `shop` (and topic/webhook-id) Are Not Covered by the HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain` header (exposed via `Request#shop`) to attribute the delivered payload to a tenant. Because the `shop`, `topic`, `webhook-id` and `api-version` headers are never part of the HMAC-signed content, an attacker who can obtain one validly-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own shop and receiving a legitimate webhook) can replay that same body/HMAC while swapping the `shop-domain` header to any other merchant's domain, and the gem will accept it as authentic.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from headers that are entirely outside of the signed content: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only checks `to_signable_string` (the body) against the shared `api_secret_key`, and then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to the handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm only that the body was signed with the app's `api_secret_key` — this secret is shared across every shop that has installed the app, so a valid `(body, hmac)` pair merely proves "some install of this app produced this body," not "this body is about shop X": [4](#0-3) 

The broken identity binding, stated as an equality that the code implicitly assumes but never enforces:
`shop authenticated by HMAC == shop attributed to the processed payload`
In reality, the HMAC only certifies the *body bytes*; the `shop-domain` header travels unauthenticated alongside it, so the equality does not hold.

### Impact Explanation
An unprivileged internet user who installs the target app on their own (attacker-controlled) development shop will legitimately receive HMAC-signed webhook deliveries from Shopify for that shop. Because the HMAC secret (`api_secret_key`) is identical for every installation of the app, the attacker can capture one such `(raw_body, hmac-sha256)` pair and replay it to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a victim merchant's domain (and, independently, the `topic`/`webhook-id` headers rewritten as well, since these are also unsigned). `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata`-equivalent payload claiming to originate from the victim shop. If the host app's handler trusts `data.shop` to look up/act on tenant records (a pattern the library itself encourages, since `shop` is the only tenant identifier surfaced), this enables cross-tenant data injection/corruption attributed to a shop the attacker does not control — e.g., forging mandatory compliance webhooks (`customers/data_request`, `customers/redact`, `shop/redact`) or `app/uninstalled` against a victim tenant, or injecting attacker-chosen order/customer data into the victim's tenant records. This is a cross-tenant access/spoofing primitive.

### Likelihood Explanation
Requires only: (1) attacker installs the target app on their own shop, which is the normal, unprivileged path any Shopify merchant/developer can take, and (2) attacker crafts an HTTP POST to the app's public webhook receiver with a captured `(raw_body, hmac)` pair and forged Shopify headers. No access token, `client_secret`, or privileged account is required — the gem's own webhook-authentication design is the root cause, not host misuse of a documented safeguard, since the library exposes no mechanism or documented requirement to independently bind `shop` to the HMAC.

### Recommendation
Bind the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`) into the HMAC-signed material, or otherwise reject/flag payloads where the header-derived shop cannot be cryptographically tied to the signed body. At minimum, `Registry.process` should cross-check `request.shop` against the shop associated with the session/install that the app expects for that HMAC secret before invoking the handler, and the library should document explicitly that `Request#shop` is unauthenticated so host apps do not conflate HMAC validity with shop authenticity.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives (or self-triggers) a legitimate webhook delivery, capturing:
raw_body = '{"id":1,"note":"hi"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)

# Attacker replays the exact same signed body but swaps the shop header:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "shopify-webhook-id" => "attacker-chosen-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation succeeds (it only checks raw_body), and the handler
#    is invoked believing this payload came from "victim-shop.myshopify.com".
```

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
