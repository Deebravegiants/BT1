### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant impersonation of replayed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant identity) is read from a separate, unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then passes this unauthenticated `shop` value straight to the app's webhook handler, so the value the HMAC actually verifies (the body) is not bound to the value the handler trusts as the tenant identity (the shop).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no part in signature computation: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (i.e., the body) and compares it against the received `hmac`, with no reference to `shop`: [4](#0-3) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header value) directly to the tenant's handler as the trusted tenant identifier: [5](#0-4) 

Equality that is broken: the identity the HMAC binds is `HMAC(secret, raw_body)`, which is independent of `shop`; but the identity the handler trusts is `data.shop == request.shop` (header-derived). Because `shop` is never part of the signable string, `HMAC(secret, raw_body)` is identical regardless of which shop's domain header accompanies that body. An unprivileged holder of one valid `(raw_body, hmac)` pair — obtainable from a legitimate webhook delivered to their own shop installation — can resend the same body/hmac pair with the `shopify-shop-domain` header changed to any other shop the app is installed on. `Registry.process` will accept the HMAC as valid (it only checks the body) and hand the handler a `WebhookMetadata` claiming to be from the victim shop, with attacker-controlled body content.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on `WebhookMetadata#shop` to enforce (data isolation, per-shop record updates, etc.), enabling cross-tenant data injection/impersonation without any credentials beyond having received one legitimately signed webhook for any shop. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on more than one shop and uses this gem's `Webhooks::Registry.process`/`Request` as documented: an attacker only needs to install the app on their own shop (or otherwise trigger one webhook delivery) to obtain a valid `(body, hmac)` pair, then replay it with a forged `shop-domain` header against the app's public webhook endpoint. No secret material, access token, or elevated privilege is required — only network access to the app's webhook receiver.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string used for webhook HMAC verification, or otherwise cryptographically bind `shop` to the HMAC before it is trusted by `Registry.process`. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should compute the signature over a canonical string that incorporates `shop-domain`, not the raw body alone, and `Registry.process` should reject any request whose header-derived shop cannot be tied to the verified signature.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)`.
3. Attacker resends a POST to the same webhook endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (per `Request#to_signable_string`, which ignores the shop header) and finds it equal to `H` — validation passes.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied content under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
