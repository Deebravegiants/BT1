### Title
Webhook shop/topic identity spoofing via HMAC that only covers the body, not the headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that the host application relies on for tenant identification and business logic are taken from HTTP headers that are never included in the HMAC computation. Any party who has captured one valid `(body, hmac)` pair — for example a legitimate webhook delivered to their own shop, which is trivial for any merchant/unprivileged installer of the app to obtain since all shops share the same `api_secret_key` for a given app — can resend that exact body with the HMAC unchanged but with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a different shop or topic. The gem's `HmacValidator` will report the request as valid, and the forged `shop`/`topic` values are passed unmodified to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read from headers with no relation to the signed content: [4](#0-3) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it against the received `hmac`: [5](#0-4) 

`Registry.process` performs exactly this HMAC check and then immediately trusts `request.topic` and `request.shop` to build `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e., the authenticated bytes should equal the bytes the application acts upon. Instead, the equality actually enforced is only `hmac == HMAC(secret, body)`, while `shop` and `topic` — the fields the handler acts on — are unauthenticated headers. This is precisely the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" class of identity-binding break: the header claiming a specific merchant is never bound to the cryptographic proof.

### Impact Explanation
Because the HMAC signature is shared per-app (all shops using the same app share `api_secret_key`), any unprivileged holder of one legitimate webhook delivery (e.g., a merchant installing the app who receives their own webhooks, or anyone who has observed a delivery in transit/logs) can replay that same `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The `HmacValidator` still validates successfully because it never inspects the header. This lets an attacker who controls no more than their own shop's webhook traffic make the host application process business-logic events (order/customer/app-uninstall data, mandatory GDPR topics, etc.) attributed to a shop they do not own — a cross-tenant identity spoof achieved purely through this gem's verification logic, with no access token, secret, or privileged account required beyond normal use of the app by any merchant.

### Likelihood Explanation
The attack requires no special access: the attacker only needs to have received (or otherwise observed) one legitimate webhook body+HMAC for the shared app secret, which is guaranteed for any merchant who installs the app (since webhooks are regularly delivered to them). Forging headers on an HTTP POST to a public webhook endpoint is trivial. The library provides no compensating control (e.g., binding shop/topic into the signed string, or requiring the caller to independently confirm the shop belongs to a known session) — `Registry.process` performs no such check.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body before trusting them in `Registry.process`. At minimum, document and enforce that `request.shop` must be cross-checked by the caller against a known/expected shop before use, and consider validating that the `shop` header is consistent with any session/store the app already trusts for that webhook subscription.

### Proof of Concept
```ruby
# Attacker owns shop "attacker-shop.myshopify.com" and legitimately receives a webhook:
body = '{"id":123,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SHARED_SECRET, body)
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
# Attacker resends the identical body+hmac but claims to be "victim-shop.myshopify.com":
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

req = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# HmacValidator.validate(req) returns true because it only checks HMAC(secret, body).
# The registered handler receives WebhookMetadata with shop == "victim-shop.myshopify.com",
# even though the request never originated from Shopify on behalf of that shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
