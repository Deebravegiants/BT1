### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature verified by `ShopifyAPI::Webhooks::Registry.process` only covers the raw request body, not this header. As a result, the `shop` value that is handed to the app's webhook handler is not cryptographically bound to the signature that authenticates the request.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely separate from the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over `@raw_body` only, per `to_signable_string`) and, once that check passes, immediately trusts `request.shop` to build the `WebhookMetadata` that is dispatched to the app's handler: [3](#0-2) 

The HMAC validator itself simply recomputes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac` value — it has no knowledge of, and does not cover, the `shop` header: [4](#0-3) 

This breaks the following identity binding as an equality that should hold but does not:

```
shop_authenticated_by_hmac == shop_used_for_tenant_routing (request.shop)
```

Concretely: `HMAC(secret, raw_body)` authenticates only `raw_body`; it says nothing about the `shopify-shop-domain` header value that is later trusted as the multi-tenant key (`request.shop`, passed into `WebhookMetadata.shop`). Any actor capable of obtaining one valid `(raw_body, hmac)` pair — e.g., an attacker who owns their own Shopify store and receives genuine webhooks for it from Shopify — can replay that exact body/HMAC pair to a victim app's webhook endpoint while substituting the `shopify-shop-domain` header with a different (victim) shop's domain. Because `to_signable_string` never incorporates the shop header, the HMAC check in `Registry.process` still succeeds, and the handler receives `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
Any app built on this gem that uses `Registry.process` and trusts `WebhookMetadata#shop` (or `Request#shop`) to select which merchant's data to mutate is exposed to cross-tenant data confusion: an attacker-controlled webhook body, correctly HMAC-authenticated for the attacker's own shop, can be attributed to an arbitrary victim shop domain of the attacker's choosing. Depending on how the app's webhook handler uses `shop` (e.g., to look up a merchant record and write incoming data, uninstall/cancel state, or update order/inventory data), this can result in cross-tenant data being created, corrupted, or associated with the wrong merchant — i.e., cross-tenant access driven entirely by unauthenticated header content that survives HMAC verification.

### Likelihood Explanation
Exploitation requires network access to the app's webhook endpoint and possession of one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` for the attacker's own shop — obtainable by simply installing the target app on an attacker-owned/free development store and capturing a real webhook delivery. No possession of the app's `client_secret`/`api_secret_key` is needed, and no privileged account on the victim shop is required. The header substitution step is a trivial HTTP replay.

### Recommendation
Bind the tenant identity into the signed material, or otherwise cryptographically verify that the `shopify-shop-domain` header corresponds to the shop that legitimately produced the HMAC. Concretely:
- Include the `shopify-shop-domain` (and ideally `shopify-webhook-id`/`shopify-topic`) header value in `to_signable_string`, or
- After HMAC validation, independently verify that the claimed `shop` is one the app actually has an active session/installation for before dispatching to the handler, and
- Document clearly (and enforce where feasible) that consumers of `Registry.process`/`WebhookMetadata` must not treat `shop` as authenticated by the HMAC alone.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery:
   - Headers: `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body>`
   - Body: `raw_body` (arbitrary attacker-controlled payload content, since it's their own shop's webhook)
2. Attacker replays the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object where `hmac` and `to_signable_string` are unchanged (both derived from body/hmac header only) — see `lib/shopify_api/webhooks/request.rb` lines 11-38.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)` — see `lib/shopify_api/utils/hmac_validator.rb` lines 12-31.
5. `Registry.process` then builds `WebhookMetadata.new(topic: ..., shop: request.shop, body: ..., ...)` with `shop == "victim.myshopify.com"` and dispatches it to the app's handler — see `lib/shopify_api/webhooks/registry.rb` lines 188-199 — even though the payload was never actually sent by Shopify for `victim.myshopify.com`.
