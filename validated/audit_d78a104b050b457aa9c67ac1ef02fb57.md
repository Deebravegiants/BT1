## Title
Outbound request delivery reward is read at claim time, not snapshotted at dispatch time, so a relayer can be underpaid or unpaid for delivery work already performed - (File: `modules/pallets/relayer/src/outbound_request.rs`)

## Summary
`pallet-relayer`'s outbound-request incentive pays relayers for delivering hyperbridge-originated system messages (host-executive, intents-coprocessor, token-governor, etc.). The reward amount is looked up **at claim time** from `OutboundRequestDeliveryReward[module_id]` rather than being fixed/snapshotted when the request was originally dispatched. Governance can change (or zero out) this value at any point between dispatch and the relayer's proof-of-delivery claim, so a relayer who already paid destination-chain gas to deliver the message can be paid a different — or zero — amount than what was configured when they committed to the work. This mirrors the SecondSwap "outdated penalty fee" bug class: an economically committing action (delivery/unlisting) is priced against a governance parameter that is re-read at settlement time instead of being cached at commitment time.

## Finding Description
The claim handler `process_outbound_request_delivery_claim` derives the payout entirely from live storage: [1](#0-0) 

```rust
let module_id: BoundedVec<u8, ModuleIdBound> = request.from.clone().try_into()...;
let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);
ensure!(reward > BalanceOf::<T>::default(), Error::<T>::OutboundRequestNoRewardConfigured);
```

`reward` is fetched fresh from `OutboundRequestDeliveryReward` when the claim is processed — potentially long after the request was dispatched, delivered on the destination chain, and its state commitment finalized on Hyperbridge. Governance can update this value at any time via `set_outbound_request_delivery_reward`, which unconditionally overwrites the map entry with no linkage to any specific pending/in-flight commitment: [2](#0-1) 

There is no mechanism that records the reward that was in effect when the request was dispatched (`RequestCommitments` only stores the commitment, not the reward that applied at that time), and no protection preventing a governance update from retroactively affecting requests that are already "in flight" — dispatched, delivered, and awaiting a claim. The delivery flow itself is entirely decoupled from the dispatch flow (by design, per the feature's own docs): [3](#0-2) 

The off-chain relayer (tesseract) commits real resources — it delivers the message to the destination chain (paying destination gas) before it ever files the claim, and only later builds a state proof and submits `claim_outbound_request_delivery_reward`: [4](#0-3) 

If governance reduces or zeroes `OutboundRequestDeliveryReward[module_id]` after the relayer has delivered but before it claims, the relayer either receives a smaller reward than the one it relied on when deciding to spend gas on the delivery, or the claim reverts entirely with `OutboundRequestNoRewardConfigured` (a total loss, since the destination-chain delivery gas was already spent and cannot be recovered).

## Impact Explanation
This is a relayer fee/reward-accounting flaw reachable from a normal, unprivileged relayer action (submitting an unsigned `claim_outbound_request_delivery_reward` extrinsic after performing legitimate delivery work). Because the reward is not locked in at dispatch time:
- A relayer can perform costly destination-chain delivery work expecting a specific reward, and later find governance has reduced or removed the reward, resulting in an economic loss with no way to recover already-spent gas.
- In the worst case (`reward` set to zero after delivery, before claim), the relayer's claim reverts outright and the module effectively "steals" free delivery work with zero payout, undermining the entire incentive model this feature exists to provide.

This directly matches the judged severity rationale in the reference report: the actor (here, the relayer) should be protected from a rug of the parameter it relied on at commitment time; instead the responsibility for guarding against governance changing the reward mid-flight falls entirely and silently on the relayer.

## Likelihood Explanation
Governance is expected to actively tune `OutboundRequestDeliveryReward` per module (raising/lowering rewards, or removing modules from the allowlist by zeroing the value) as normal, routine operation — this is explicitly the intended governance lever described in the design doc, not an edge case. Given the delay inherent in the claim pipeline (waiting for BEEFY finalization on the destination, then for Hyperbridge's own state commitment to the destination, then building/submitting a state proof), there is a realistic window between "relayer commits to delivering" and "relayer claims" during which a routine reward update collides with in-flight relayer work.

## Recommendation
Snapshot the reward that applies to a given request at dispatch time (e.g., store `(commitment → reward_at_dispatch)` alongside `RequestCommitments`, or have the dispatching pallet lock in the reward when it calls `dispatch_request`) and use that cached value at claim time instead of re-reading the live `OutboundRequestDeliveryReward` map. Alternatively, apply reward changes only to requests dispatched after the update (e.g., versioned/queued reward table), so relayers can rely on the reward that was configured when they committed to delivering a specific message.

## Proof of Concept
1. Governance calls `set_outbound_request_delivery_reward(module_id, 100)` for `host-executive`'s module id.
2. `pallet-host-executive::update_host_params` dispatches a hyperbridge-originated `PostRequest` from that module (`modules/pallets/host-executive/src/lib.rs:225-231`), creating an entry in `RequestCommitments`.
3. A relayer observes the reward is 100, spends destination-chain gas delivering the request (`onAccept` on the destination `HostManager`), and begins assembling `OutboundRequestDeliveryClaim` (waiting on Hyperbridge's state commitment for the destination, per `tesseract/messaging/messaging/src/outbound_request_claim.rs:245-260`).
4. Before the relayer submits the claim, governance calls `set_outbound_request_delivery_reward(module_id, 0)` (e.g., to remove the module from the allowlist for unrelated reasons, or simply to lower operating costs).
5. The relayer submits `claim_outbound_request_delivery_reward` with a valid proof of delivery; `process_outbound_request_delivery_claim` reads `reward = OutboundRequestDeliveryReward::get(module_id) == 0` and reverts with `OutboundRequestNoRewardConfigured` (`modules/pallets/relayer/src/outbound_request.rs:148-149`), even though the relayer already paid gas to deliver the message under the prior 100-unit reward regime.

```rust
		/// Governance-set per-`module_id` reward for delivering a
		/// hyperbridge-originated request from that module. Setting
		/// `amount = 0` removes the module from the allowlist.
		#[pallet::call_index(6)]
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().reads_writes(0, 1))]
		pub fn set_outbound_request_delivery_reward(
			origin: OriginFor<T>,
			module_id: BoundedVec<u8, ModuleIdBound>,
			amount: BalanceOf<T>,
		) -> DispatchResult {
			T::RelayerOrigin::ensure_origin(origin)?;
			OutboundRequestDeliveryReward::<T>::insert(&module_id, amount);
			Self::deposit_event(Event::OutboundRequestDeliveryRewardUpdated {
				module_id,
				new_reward: amount,
			});
			Ok(())
		}
```
