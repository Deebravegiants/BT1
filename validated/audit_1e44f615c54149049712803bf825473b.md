### Title
UID-only indexing in `newBlockingOwnerDeletionRefs` allows attacker to bypass `blockOwnerDeletion` authorization by reusing an old ownerReference UID for a different owner - ([File: plugin/pkg/admission/gc/gc_admission.go])

### Summary
`indexByUID` builds a map of old owner references keyed solely by `ref.UID`, and `newBlockingOwnerDeletionRefs` uses this map to decide whether a `blockOwnerDeletion:true` reference is "new" (requires authorization) or "pre-existing" (skipped). Because `metav1.OwnerReference.UID` is a client-supplied, unvalidated string (not cross-checked against `Kind`/`Name`/`APIVersion` by `validateOwnerReference`), an attacker can update an object's owner references, keep the previously-used UID value but swap in a different `Kind`/`Name`/`APIVersion`, and have the admission plugin treat the new, unauthorized blocking reference as already-existing, skipping the delete-permission check entirely.

### Finding Description
`newBlockingOwnerDeletionRefs` compares new blocking owner references against old ones purely by UID: [1](#0-0) [2](#0-1) 

If `ref.UID` matches an entry in `indexedOldRefs`, the code only checks `oldRef.BlockOwnerDeletion` to determine `wasNotBlocking`; it never verifies that `oldRef.Kind`/`Name`/`APIVersion` actually match the new ref's `Kind`/`Name`/`APIVersion`. A UID match is treated as proof the reference is unchanged.

Crucially, `metav1.OwnerReference.UID` is not validated against the real UID of any actual object at the referenced `Kind`/`Name`. `validateOwnerReference` only requires it to be non-empty: [3](#0-2) 

Exploit flow:
1. Attacker creates a dependent object `O` in their own namespace with `ownerReferences: [{Kind: ConfigMap, Name: cm-i-own, UID: "X", BlockOwnerDeletion: true}]`, where `cm-i-own` is a ConfigMap the attacker can genuinely delete. On create, `oldObj == nil`, so `newBlockingOwnerDeletionRefs` returns all blocking refs and the plugin's authorization check in `Validate` runs `ownerRefToDeleteAttributeRecords`, which the attacker legitimately passes (real ConfigMap they can delete).
2. Attacker later updates `O`, changing the ownerReference to `{Kind: Secret, Name: secretA, UID: "X", BlockOwnerDeletion: true}` — same UID string `"X"`, but a completely different `Kind`/`Name` pointing at a Secret the attacker cannot delete.
3. `isChangingOwnerReference` returns `true` (Kind/Name differ), so the plugin proceeds.
4. In `newBlockingOwnerDeletionRefs`, `indexByUID(oldMeta.GetOwnerReferences())` maps `"X"` → the old ConfigMap ref. The lookup `indexedOldRefs[ref.UID]` for the new Secret ref finds this old ref by UID alone, sees `BlockOwnerDeletion == true`, sets `wasNotBlocking = false`, and **excludes** the new Secret reference from `newBlockingRefs` — even though it refers to an entirely different object.
5. Back in `Validate`, `newBlockingRefs` ends up empty, so `if len(newBlockingRefs) == 0 { return nil }` short-circuits and the entire authorization loop (`ownerRefToDeleteAttributeRecords` + `Authorize`) is skipped.

The result: the attacker persists `blockOwnerDeletion: true` against `secretA` without ever having `update`/`finalizers` permission checked on it, because the admission plugin was tricked into believing this blocking reference already existed.

### Impact Explanation
This grants an unprivileged attacker the ability to set `ownerReference.blockOwnerDeletion: true` pointing at an arbitrary object they don't have delete rights on, bypassing the `OwnerReferencesPermissionEnforcement` admission plugin's core security guarantee (the plugin exists specifically to prevent exactly this — see the delete-permission and blockOwnerDeletion checks in `Validate`). This maps to a Kubernetes bounty "admission bypass" / authorization-bypass class impact: it undermines garbage-collection finalizer semantics and can be used to block deletion of objects the attacker does not control, a form of unauthorized cross-tenant interference (denial-of-deletion / resource-lock griefing) that the admission control was designed to prevent.

### Likelihood Explanation
Preconditions are minimal and within an ordinary unprivileged user's RBAC:
- Create/update rights on some namespaced dependent resource type not in the plugin's whitelist (only `pods/status` is whitelisted).
- Delete rights on some resource of any kind at least once, to seed a legitimate blocking owner reference with an attacker-chosen UID string.
- No special privilege is required to choose the `UID` field value in `ownerReferences`, since it is a free-form string not cross-validated against a real object's UID.

The attack is fully reproducible via a two-step API sequence (create then update) and requires no race conditions, no admin/node/kubelet access, and no elevated capability, making it a moderate to high likelihood issue for anyone using this admission plugin in a multi-tenant cluster.

### Recommendation
Change `indexByUID` / `newBlockingOwnerDeletionRefs` to index and compare old and new owner references by the full owner identity (`APIVersion`, `Kind`, `Name`, and `UID` together, e.g. using `ownerReferenceCoordinates`/`ownerReferenceMatchesCoordinates`-style comparison as already used in `pkg/controller/garbagecollector/graph.go`), not by `UID` alone. A reference should only be considered "pre-existing" if all coordinate fields match the old reference, not just the UID.

### Proof of Concept
Add a table-driven unit test alongside the existing tests in `plugin/pkg/admission/gc/gc_admission_test.go` for `newBlockingOwnerDeletionRefs`:
- `oldObj` owner references: `[{APIVersion: "v1", Kind: "ConfigMap", Name: "cm-i-own", UID: "X", BlockOwnerDeletion: true}]`.
- `newObj` owner references: `[{APIVersion: "v1", Kind: "Secret", Name: "secretA", UID: "X", BlockOwnerDeletion: true}]`.
- Call `newBlockingOwnerDeletionRefs(newObj, oldObj)`.
- Current (buggy) behavior: returns an empty slice, incorrectly treating the Secret reference as pre-existing/non-blocking-new.
- Expected (fixed) behavior: the function should return the Secret reference as a genuinely new blocking ref (since its Kind/Name differ from anything in `oldObj`), triggering the `ownerRefToDeleteAttributeRecords`/`Authorize` check in `Validate` for the Secret.

A higher-level integration test can also drive `gcPermissionsEnforcement.Validate` twice (simulating create then update as described in the exploit flow) with a fake authorizer that denies delete on `secretA`, asserting that the second call currently incorrectly returns `nil` (allowed) instead of `admission.NewForbidden`.

func indexByUID(refs []metav1.OwnerReference) map[types.UID]metav1.OwnerReference {
	ret := make(map[types.UID]metav1.OwnerReference)
	for _, ref := range refs {
		ret[ref.UID] = ref
	}
	return ret
}

func validateOwnerReference(ownerReference metav1.OwnerReference, fldPath *field.Path) field.ErrorList {
	allErrs := field.ErrorList{}
	gv, err := schema.ParseGroupVersion(ownerReference.APIVersion)
	// gvk.Group is empty for the legacy group.
	if len(ownerReference.APIVersion) == 0 {
		allErrs = append(allErrs, field.Required(fldPath.Child("apiVersion"), "must not be empty").MarkCoveredByDeclarative())
	} else if err != nil || len(gv.Version) == 0 {
		allErrs = append(allErrs, field.Invalid(fldPath.Child("apiVersion"), ownerReference.APIVersion, "must be <group>/<version> or <version>"))
	}
	if len(ownerReference.Kind) == 0 {
		allErrs = append(allErrs, field.Required(fldPath.Child("kind"), "must not be empty").MarkCoveredByDeclarative())
	}
	if len(ownerReference.Name) == 0 {
		allErrs = append(allErrs, field.Required(fldPath.Child("name"), "must not be empty").MarkCoveredByDeclarative())
	}
	if len(ownerReference.UID) == 0 {
		allErrs = append(allErrs, field.Required(fldPath.Child("uid"), "must not be empty").MarkCoveredByDeclarative())
	}
	gvk := gv.WithKind(ownerReference.Kind)
	if _, ok := BannedOwners[gvk]; ok {
		allErrs = append(allErrs, field.Invalid(fldPath, ownerReference, fmt.Sprintf("%s is disallowed from being an owner", gvk)))
	}
	return allErrs
}
