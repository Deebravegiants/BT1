### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking that the HMAC computed over the raw request body matches the `X-Shopify-Hmac-Sha256` header. It then trusts the `shop-domain` header — which is *not* part of the signed content — as the tenant identity that is handed to the app's `WebhookHandler`.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` using the shared `Context.api_secret_key`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body — none of the `topic`, `shop-domain`, `webhook-id`, or `api-version` headers are included in the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (read straight from the unauthenticated header) as the tenant identity passed to the handler: [3](#0-2) 

Because `Context.api_secret_key` is the single shared secret for the app across **all** installed shops, any merchant who installs the app on their own store receives webhook deliveries with a *valid* HMAC computed over a body they control/observe. That attacker-controlled (body, hmac) pair remains valid regardless of which `shop-domain` header value accompanies it, because the header is never part of the signed content. The attacker can therefore resend the exact same body/HMAC pair to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header (e.g., a victim's shop), and `Registry.process` will accept it and dispatch `WebhookMetadata.new(topic: ..., shop: request.shop, ...)` with the attacker-chosen shop.

This breaks the identity binding: `shop authenticated (any shop whose install produced a validly-HMAC'd body under the shared secret) != shop trusted for tenant routing (request.shop header, attacker-controlled)`.

### Impact Explanation
A host application built on this gem typically keys its persisted data, session lookups, or business logic off `WebhookMetadata#shop`. Since that value is unauthenticated, an attacker with their own install of the target app can forge webhook events (e.g. `app/uninstalled`, `shop/redact`, `orders/create`) that appear to originate from a victim shop of the same app, causing the host application to act on/write to the wrong tenant's records — a cross-tenant access/data-integrity violation without ever obtaining the target shop's access token or the app's `client_secret`.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (even free-tier) installer of the target Shopify app — an unprivileged internet user relative to other merchants using the same app — and to know or guess the shop domain of a victim tenant (shop domains are public, discoverable strings). No secrets, tokens, or elevated privileges are required, making this readily reachable by any user who can install the app once.

### Recommendation
Bind the trusted headers into the HMAC-verified payload (or otherwise cryptographically authenticate `shop-domain`, `topic`, and `webhook-id`) rather than validating body content alone, e.g., include the shop domain in the signable string, or cross-check `request.shop` against a shop the app has verifiably installed (a stored offline session) before dispatching to handlers. At minimum, document to consumers that `WebhookMetadata#shop` must be revalidated against known installed shops before being trusted for tenant-scoped logic.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `POST /webhooks` with body `{"id":1}` and header `X-Shopify-Hmac-Sha256: <valid_hmac_of_body>` — valid because it's computed with the app's shared `client_secret`.
2. Attacker replays the identical request to the app's webhook endpoint, keeping the body and HMAC header unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because `Request#to_signable_string` only checks the raw body [4](#0-3) .
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the app's handler [5](#0-4) , causing the host app to process a forged event attributed to a shop the attacker does not control.
