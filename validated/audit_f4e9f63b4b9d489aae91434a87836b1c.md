### Title
Webhook `shop` (and `topic`) identifiers are excluded from the HMAC signature, breaking the shop-authenticated-vs-shop-processed binding - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and are never part of the HMAC-verified payload. `Registry.process` forwards these header-derived values, unauthenticated, straight to the app's `WebhookHandler` as the tenant identifier (`data.shop`).

### Finding Description
`HmacValidator.validate` verifies only `verifiable_query.to_signable_string`, which for `Request` equals `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that carry no cryptographic binding at all: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (and `request.topic`) as the tenant/routing identity passed to the handler: [3](#0-2) 

The identity binding the app relies on is: `shop authenticated by HMAC == shop the app processes as tenant`. In this gem that equality never holds — the HMAC secret (`api_secret_key`/`client_secret`) is shared by the app across **every** shop that installs it, and the signature covers none of the header fields. Any entity that can obtain one validly-signed webhook payload for the app (e.g., by installing the app on their own development/free store, which requires no privileged credential, or by intercepting one over an insecure channel) can replay that exact body with the `x-shopify-shop-domain` (and `x-shopify-topic`) headers swapped to a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the (attacker-controlled) body to the handler tagged with the victim's shop domain. Because `WebhookMetadata.shop` (the value the app's own handler code keys tenant lookups on, per the documented handler contract) is fully attacker-controlled, this allows cross-tenant confusion: data ostensibly "from shop A" gets attributed to shop B in the receiving application, using the app's own legitimate signing secret. [4](#0-3) 

### Impact Explanation
This is a cross-tenant boundary break enabled purely by this gem's webhook-verification code: the party that legitimately possesses no more than "install the app on any shop" access can forge the shop identity attached to a signed webhook body for any other tenant of the same app, because the shop header is outside the HMAC's protected surface. That matches the Critical "cross-tenant access" category, since the app never has any means, using this gem's API, to detect that the `shop` field was not part of what was actually authenticated.

### Likelihood Explanation
High: obtaining one authentic app webhook only requires installing the app as a normal, unprivileged merchant (or any means of observing one webhook delivery), no `api_secret_key` or access token theft is needed. Re-sending the same body with a modified `shop-domain`/`topic` header is a mechanical HTTP replay, and the gem provides no protection against it because verification is defined at `to_signable_string` returning `@raw_body` only.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` cryptographically to the verified payload, or otherwise refuse to trust header-derived identity fields that aren't part of the HMAC input. Concretely, extend `Request#to_signable_string` (or add a parallel check in `Registry.process`) to incorporate the shop/topic headers into what is verified — e.g., cross-check `request.shop` against a shop already known to be authorized for this app installation (from stored session data) before dispatching to the handler, rather than trusting the header value as an authenticated fact.

### Proof of Concept
1. Attacker installs the victim app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving a request with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint but replaces `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body`; it succeeds unchanged. [5](#0-4) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` and handed to the app's handler, which (per the gem's documented contract) uses `data.shop` to select the tenant/session to act on, causing attacker-supplied data to be processed under the victim shop's identity. [6](#0-5)
