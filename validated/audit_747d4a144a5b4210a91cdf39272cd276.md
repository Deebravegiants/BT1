## Findings

I found a concrete analog: the Tron deployment of `IntentGatewayV2.onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) omits the relayer-allowlist validation (`_checkRelayer`) that the canonical EVM implementation (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) enforces before processing any incoming request kind, including `NewDeployment`, `UpdateParams`, and `SweepDust` — governance-only actions.

### Title
Missing relayer authorization check in Tron `IntentGatewayV2.onAccept` allows unauthorized governance actions and fund sweeps - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical `ExtrinsicIntents.onAccept` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:330-350`) calls `_checkRelayer(incoming.relayer)` as the very first statement, before any `RequestKind` byte is even read — this restricts every delivery (RedeemEscrow, RefundEscrow, NewDeployment, UpdateParams, SweepDust, Execute) to the configured `_relayer` address once armed [1](#0-0) . The Tron port's `onAccept` (`evm/tron/contracts/apps/IntentGatewayV2.sol:629-683`) contains no such call at all — it reads `RequestKind` directly and dispatches to `authenticate()` (source-module check only) or the Hyperbridge-source check, with no relayer gate anywhere in the function [2](#0-1) .

### Finding Description
`authenticate()` in the Tron contract only checks that `request.from` matches the registered peer gateway for `request.source` [3](#0-2) , and the Hyperbridge-source check only validates `request.source == hyperbridge()` for `NewDeployment`/`UpdateParams`/`SweepDust`. Neither check constrains *who delivered* the message (`incoming.relayer`, i.e., `msg.sender` at `HandlerV2.handlePostRequests`, which is fully attacker-controlled per `HandlerV2.sol:181-209` and the documented flow) [4](#0-3) . On the canonical EVM contract, this relayer gate is the deliberate second layer of defense noted in its own comments (`_checkRelayer`, "Once a relayer is set, rejects deliveries from anyone else before the body is read") [5](#0-4) , and the test suite treats bypassing it as the exact attack this gate exists to prevent (`testOnAcceptGovernanceRejectsUnlistedRelayer`, `testFreshProxyIsOpenUntilGovernanceArmsIt`) [6](#0-5) .

### Impact Explanation
On the Tron deployment, any relayer (permissionless by ISMP design) can deliver `SweepDust`, `NewDeployment`, or `UpdateParams` requests as soon as they are legitimately dispatched from Hyperbridge/hyperbridge-source and included in a valid proof/consensus update, without needing to be the gateway's designated relayer. `SweepDust` directly transfers protocol-accumulated dust funds to an attacker-controlled `beneficiary` via raw `.call` [7](#0-6) ; `NewDeployment`/`UpdateParams` let an unauthorized relayer be the first to register a malicious "peer gateway" address or rewrite protocol fee parameters, undermining `authenticate()` for future escrow releases and enabling forged cross-chain withdrawal authentication once a rogue peer address is registered. This is a permanent loss/misdirection of protocol funds and an unauthorized app-state/governance action, matching the "unauthorized app action" / "theft of funds" impact bar.

### Likelihood Explanation
High — this requires no privileged access; any address capable of relaying a legitimately-dispatched Hyperbridge governance message (which is by design permissionless for delivery) can front-run the intended relayer and land the state-changing call first, since the only defense the canonical contract relies on (`_checkRelayer`) is entirely absent in this file.

### Recommendation
Add the identical `_checkRelayer(incoming.relayer)` gate (or equivalent) at the top of `IntentGatewayV2.onAccept` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring `ExtrinsicIntents.sol:330-331`, before any `RequestKind` byte is read, and audit any other Tron-specific app contracts for the same divergence from the canonical EVM implementation.

### Proof of Concept
1. Deploy/observe the Tron `IntentGatewayV2` with `_relayer` armed to a specific governance relayer address (as intended).
2. Hyperbridge dispatches a legitimate `SweepDust` (or `NewDeployment`) `PostRequest` addressed to the gateway.
3. Any third-party account (not the configured relayer) submits this proven message through `HandlerV2.handlePostRequests`, becoming `incoming.relayer`.
4. `onAccept` processes the request with no relayer check, executing `SweepDust`'s fund transfer or `NewDeployment`'s peer registration — actions the canonical contract would have reverted with `Unauthorized` for the same unauthorized relayer.

**Note on limitations:** I was not able to fully verify whether Tron's underlying `HandlerV2`/host equivalent also forwards `msg.sender` as `incoming.relayer` identically to the EVM `HandlerV2.sol`, since the Tron host/handler source wasn't retrieved in this session — this should be confirmed by a follow-up session with full file access before treating this as certain, though the contract-level omission itself is directly verified from the two file diffs above.

    /**
     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The
     * host records the revert as undelivered, so the authorised relayer can resubmit. While unset,
     * every delivery passes: a proxy from before the gate stays open until `migrate` arms it.
     * @param relayer The account that submitted the message to the handler.
     */
    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
    }

   rest of the batch proceeds and the message stays deliverable.
