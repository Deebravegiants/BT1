### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant shop confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header for tenant identification passed to the app's handler. This breaks the identity binding: `hmac == HMAC(raw_body)` while `shop` used downstream comes from a header that is not part of the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

The HMAC signable string used to authenticate the request is only the raw body, not the shop header: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the app's webhook handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare`: [4](#0-3) 

Because the same `client_secret` is shared across every shop that installs the app, and the HMAC is computed only over the body, a valid `(body, hmac)` pair generated for one shop remains valid for **any** `shop-domain` header value. The identity binding the gem should provide is:

`hmac_verified(bytes) == bytes_that_determine_the_tenant`

but instead:

`hmac_verified(raw_body) != shop_header_used_for_tenant_attribution`

An unprivileged internet user who can obtain one legitimately signed webhook for *any* shop (e.g., their own free/dev store with the target app installed — a normal, unprivileged action) can capture a valid `(raw_body, x-shopify-hmac-sha256)` pair and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop's domain. `Registry.process` will pass HMAC validation (the body/HMAC pair is untouched) and invoke the handler with `WebhookMetadata.shop == victim_shop`, `body == attacker's own captured body`. This lets the attacker inject arbitrary, replay-able webhook payloads attributed to a shop they don't operate — a cross-tenant data/identity confusion.

### Impact Explanation
This is a cross-tenant boundary violation: an attacker can make a Shopify app (via this gem) process attacker-controlled data as though it originated from a different, unrelated merchant's shop, without ever needing that merchant's credentials or the app's `client_secret`. Depending on what the host application's webhook handler does with `data.shop` (e.g. looking up the merchant record, writing to that merchant's data store, triggering merchant-scoped side effects), this can lead to cross-tenant data corruption or forged events being attributed to a victim shop — matching the "cross-tenant access" high/critical impact category.

### Likelihood Explanation
Medium-to-High. The attacker only needs the ability to trigger one webhook to be delivered for *any* shop where the app is installed (trivially achievable by installing the app on the attacker's own free/development store and generating an event), then replay that exact request body/HMAC to the public webhook endpoint with a forged `shop-domain` header. No secret material, tokens, or privileged access is required — only capturing and replaying a valid, previously-observed HTTP request to a public endpoint.

### Recommendation
Bind the shop identity into the verified bytes, or otherwise verify that the request truly originates from the shop it claims:
- Include the `shop-domain` (and `topic`, `webhook-id`) values in the signable string that is HMAC-verified, not just the raw body, OR
- After verifying the body HMAC, independently confirm the `shop-domain` header matches a shop for which this specific webhook subscription is registered/expected before dispatching to a handler, and reject mismatches.
- Document (and enforce in the handler contract) that `WebhookMetadata.shop` must not be trusted for tenant-sensitive actions unless independently corroborated (e.g., cross-checked against the webhook_id belonging to that shop's active subscription record).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (unprivileged, standard installation flow) and configures a webhook (e.g., `orders/create`).
2. Attacker triggers the event in their own store; Shopify delivers a POST to the app's public webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H = HMAC(client_secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and immediately re-sends the same POST to the same endpoint, keeping body `B` and header `H`, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares to `H` — this still matches because `to_signable_string` never included the shop header: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and processes it as if it were a legitimate event from the victim shop.
