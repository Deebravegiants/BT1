### Title
Fee-On-Transfer Token Internal Accounting Mismatch in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-chain variant of `IntentGatewayV2.placeOrder` credits escrow (`_orders[commitment][token]`) with the user-declared input amount (minus protocol fee) instead of the amount actually received by the contract via `safeTransferFrom`. For fee-on-transfer or rebasing ERC20 tokens, the actual token balance received by the gateway will be less than the amount recorded in escrow, creating an internal accounting mismatch (unbacked escrow liability).

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract transfers tokens with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits escrow with `reducedInputs[i].amount` — which is derived from `order.inputs[i].amount` (the pre-transfer, user-declared amount) reduced only by the protocol fee — without ever measuring the contract's actual token balance before/after the transfer: [1](#0-0) 

This is the exact bug class described in the external report: shares/escrow are credited based on the nominal transfer amount rather than the actual balance change, so fee-on-transfer or rebasing tokens cause the internal ledger (`_orders`) to overstate the tokens actually held by the contract.

Notably, the primary EVM implementation of the same contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against exactly this issue: it snapshots `balanceOf(address(this))` before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received delta before computing the commitment and escrow amount: [2](#0-1) 

This fix is also explicitly covered by dedicated fee-on-transfer regression tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) in the Solidity/EVM test suite: [3](#0-2) 

The Tron variant, however, was not updated with this fix — it still records escrow based on the nominal `order.inputs[i].amount` (protocol-fee-adjusted only), not the actual balance delta: [4](#0-3) [1](#0-0) 

Since escrow accounting (`_orders[commitment][token]`) is the source of truth used later to release funds to solvers on `RedeemEscrow` or to refund users on `RefundEscrow`/`cancelOrder`, an overstated escrow entry means the contract believes it holds more of a given token than it actually does.

### Impact Explanation
If a fee-on-transfer or rebasing (negative-rebase) token is used as an order input on the Tron gateway, the escrow ledger will record more tokens than the contract actually received/holds. When the order is later filled and the corresponding withdrawal (`RedeemEscrow`) is processed, the contract will attempt to pay out the full escrowed (overstated) amount to the solver/beneficiary. This either:
- causes the payout transaction to revert once the shortfall is discovered (permanently freezing the escrowed funds for that order, since `_filled`/order state may already be locked in), or
- if other tokens/orders share the same token's pooled balance, drains balance intended for unrelated orders, causing insolvency and stuck/failed withdrawals for other users.

This matches the required impact bar: permanent freezing of funds / unsound internal accounting reachable directly by any unprivileged user placing an order with such a token via `placeOrder`, a function reachable by "an unprivileged... token bridger, intent solver."

### Likelihood Explanation
Likelihood is contingent on the protocol supporting or a user managing to register/use a fee-on-transfer or rebasing token as an order input on the Tron deployment. The comment history and dedicated fix/tests in the primary EVM contract show the team is aware of and actively mitigating this exact bug class, confirming that fee-on-transfer/rebasing token support is a live concern for this codebase — but the mitigation was not carried over to the Tron variant, leaving it exploitable there if/when such tokens are used or listed.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: snapshot `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom` call in the non-predispatch branch of `placeOrder`, use the actual delta as `order.inputs[i].amount` before computing `reducedInputs`/the commitment, and credit `_orders[commitment][token]` with the fee-adjusted actual-received amount rather than the nominal input amount.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC20 token (e.g., 1% fee, analogous to the `FeeOnTransferToken` test helper in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2690-2735) as an input asset.
2. User calls `placeOrder` with `order.inputs[0].amount = 1000e18` of the FOT token, with no predispatch. `safeTransferFrom` moves 1000e18 nominally but the gateway's actual balance only increases by 990e18 (1% fee burned/redirected) — see the non-predispatch transfer at `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 458-463.
3. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[0].amount` ≈ 1000e18 (minus only protocol fee, if any), overstating the escrow versus the actual 990e18 held.
4. When the order is filled and `RedeemEscrow`/withdrawal logic pays out based on `_orders[commitment][token]`, the contract attempts to transfer more tokens than it actually holds for that commitment, reverting the withdrawal (freezing funds) or depleting balance backing other orders.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
