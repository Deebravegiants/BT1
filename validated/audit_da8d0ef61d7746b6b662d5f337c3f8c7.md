Audit Report

## Title
Missing para lifecycle validation in `on_demand::do_place_order` allows on-demand orders for non-onboarded (`Onboarding`) paras, letting them seize scheduler core-assignment slots - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)

## Summary
`do_place_order` never checks the target `para_id`'s `ParaLifecycle` state before accepting payment and enqueuing the order; it only checks price and queue length. `OrderQueue::pop_assignment_for_cores` and the coretime assigner's dispatch of pool cores likewise apply no lifecycle/registration filter, so an order for a para still in `Onboarding` can occupy a pool core-assignment slot that no valid candidate can fill.

## Finding Description
`do_place_order` validates only `spot_price.le(&max_amount)` and `order_status.queue.len() < on_demand_queue_max_size` before charging the sender and calling `order_status.queue.try_push(now, para_id)`. There is no call to `paras::Pallet::<T>::is_valid_para`, `lifecycle`, or any registration check anywhere in this function or in `OrderQueue::pop_assignment_for_cores`, which only gates on timing (`ready_at <= now`) and per-call de-duplication via a `BTreeSet`. This is propagated unfiltered through `pop_assignment_for_ondemand_cores` in the coretime assigner and `advance_assignments_single_impl`, which pushes every `Pool`-assigned core index into `pool_cores` and pops assignments for exactly that count with no validity check. [3](#0-2) 

This matches the documented error list (`InsufficientBalance`, `QueueFull`, `SpotPriceHigherThanMaxAmount`), which conspicuously omits any para-validity error, confirming the check was never intended/added.

## Impact Explanation
A para in `ParaLifecycle::Onboarding` has no live genesis head/code materialized until the next session boundary's `apply_actions_queue` (`initialize_para_now`), so no collator can produce a valid backed candidate for it in the interim. If such a para's order is popped by `pop_assignment_for_cores`, that pool core-assignment slot for the round is effectively wasted, since no valid candidate exists to fill it — a resource-seizure effect against the shared on-demand queue. This is a real, if narrow, griefing vector: it can starve legitimate parathreads of on-demand core time for a round, though it does not cause fund loss beyond the attacker's own order payment.

## Likelihood Explanation
Reserving and registering a `para_id` is a normal permissionless registrar flow, and calling `place_order_allow_death` / `place_order_with_credits` for an `Onboarding` para requires only normal signed extrinsics and sufficient balance/credits to cover the current spot price. The attack is repeatable every order cycle for as long as the para remains `Onboarding` (i.e., until the next session rotation completes onboarding), making it feasible at modest, self-funded cost.

## Recommendation
Add a lifecycle validity check in `do_place_order` (e.g., `ensure!(<paras::Pallet<T>>::is_valid_para(para_id), Error::<T>::InvalidParaId)` or an equivalent check for `Parathread`/`Parachain` lifecycle) before accepting payment and enqueuing the order, mirroring the lifecycle check already used in `paras_registrar::make_parachain`. As defense in depth, also filter out non-live paras in `pop_assignment_for_cores`/`advance_assignments` so any order that slips through (e.g., due to a lifecycle transition happening after the order was placed) is dropped rather than consuming a core slot.

## Proof of Concept
1. Register a `para_id` via `Paras::schedule_para_initialize` (or the registrar) without advancing to the session where `apply_actions_queue` promotes it; confirm `Paras::lifecycle(para_id) == Some(ParaLifecycle::Onboarding)`.
2. Fund `alice` and call `OnDemand::place_order_allow_death(RuntimeOrigin::signed(alice), amt, para_id)`; observe it returns `Ok(())` with no lifecycle-related error.
3. Advance blocks for asynchronous-backing readiness and call `OnDemand::pop_assignment_for_cores(block_num, 1)`; observe it yields `Some(para_id)` even though the para is still `Onboarding`, demonstrating a non-live para consuming a pool core-assignment slot.

impl<N> OrderQueue<N> {
	/// Pop `num_cores` from the queue, assuming `now` as the current block number.
	pub fn pop_assignment_for_cores<T: Config>(
		&mut self,
		now: N,
		mut num_cores: u32,
	) -> impl Iterator<Item = ParaId>
	where
		N: Saturating + Ord + One + Copy,
	{
		let mut popped = BTreeSet::new();
		let mut remaining_orders = Vec::with_capacity(self.queue.len());
		for order in mem::take(&mut self.queue) {
			// Order is ready 2 blocks later (asynchronous backing):
			let ready_at = order.ordered_at.saturating_plus_one().saturating_plus_one();
			let is_ready = ready_at <= now;

			if num_cores > 0 && is_ready && popped.insert(order.para_id) {
				num_cores -= 1;
			} else {
				remaining_orders.push(order);
			}
		}
		self.queue = BoundedVec::truncate_from(remaining_orders);
		popped.into_iter()
	}
