### Title
Global `surplusShareBps` and `solverSelection` parameters are mutable mid-order and read at fill time, letting a governance parameter update change settlement terms for already-placed IntentGateway orders - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` orders are explicitly described as "auctioned" to competing solvers [1](#0-0) : a user escrows tokens with `placeOrder`, solvers compete/bid off-chain, and a solver later calls `fillOrder` — an arbitrarily long window during which the order sits "in flight," exactly like an ongoing Nouns-style auction. Two protocol-wide parameters that materially affect the economics and security of that in-flight order — `surplusShareBps` and `solverSelection` — are **not captured into the order at placement time**. They live in the mutable `_params` struct and are read live at fill time via `IntentsBase._updateParams` / `_splitSurplus`, so a parameter update dispatched between `placeOrder` and `fillOrder` changes the terms of an order that a user and solver have already agreed to, exactly the bug class described in the reference report (Auction.sol parameters changing mid-auction with no snapshot/timelock).

### Finding Description
`_updateParams` overwrites the entire `_params` struct (including `surplusShareBps` and `solverSelection`) immediately and unconditionally, with no check for in-flight orders and no delay: [2](#0-1) 

`surplusShareBps` is only consulted when a solver actually fills the order, via `_splitSurplus`, which reads `_params.surplusShareBps` directly rather than a value pinned to the order at `placeOrder` time: [3](#0-2) 

This function is invoked from both the same-chain and cross-chain fill paths at the moment of fill, long after the order (and any off-chain bid/quote based on the surplus split at placement time) was created: [4](#0-3) 

Contrast this with `protocolFeeBps`, which the contract *does* snapshot correctly: it is deducted from `order.inputs` and baked into the commitment hash at `placeOrder` time, so it cannot silently change for an order that already exists: [5](#0-4) 

No equivalent snapshot exists for `surplusShareBps` (or for `solverSelection`, which gates whether an order requires an authorized solver via a signed session key — also read live from `_params` rather than fixed at placement). Because `Order` itself carries only `user, source, destination, deadline, nonce, fees, session, predispatch, inputs, output` and no economic-parameter fields, any governance-dispatched `UpdateParams` message applied between `placeOrder` and `fillOrder` changes:
- how much of a solver's overpayment (surplus) goes to the beneficiary vs. the protocol for orders that were already placed and are awaiting a fill, and
- whether solver-selection protection is active/inactive for orders whose users chose a `session` key expecting it to be enforced (or expecting it not to matter).

This mirrors the referenced finding precisely: mutable, globally-scoped parameters take effect immediately on all outstanding state (here, open orders/auctions) rather than being fixed at the time the affected state was created, and there is no timelock or grandfathering mechanism.

### Impact Explanation
- A user or a solver who priced/bid an order assuming a particular `surplusShareBps` split can have that split change before the fill lands, altering the actual payout distribution without their consent — a direct, unexpected shift of value between the beneficiary, the protocol treasury, and (indirectly) solver profitability that can make a previously profitable/agreed bid unprofitable or change realized proceeds for the user.
- More severely, if `solverSelection` is toggled off after an order was placed with an authorization-bearing `session` key (user expected only an authorized solver could fill), any solver can now fill it before the user notices, undermining the confidentiality/exclusivity guarantee the user relied on when placing the order. Conversely, toggling it on after placement can unexpectedly block a solver who had already prepared an authorized fill under the old rules.
- This is reachable purely through the normal, unprivileged transaction flow of intent solving (`placeOrder` → wait → `fillOrder`), combined with a routine (non-malicious) governance parameter update landing in between — the same "social accident" risk the original judge flagged as Medium severity for Auction.sol.

### Likelihood Explanation
Parameter updates (`UpdateParams`) are a normal, expected governance operation (fee tuning, surplus-split tuning, feature toggles) rather than a rare emergency action, so the window in which an order can be placed, sit unfilled, and then have its governing parameters change before `fillOrder` is realistically hit whenever governance adjusts `surplusShareBps` or `solverSelection` while any orders are outstanding — which, given orders can remain open until `order.deadline` (a block number with no protocol-imposed ceiling, as noted in the SDK docs), can be an arbitrarily large window.

### Recommendation
- Snapshot `surplusShareBps` (and `solverSelection`, if it must vary per-order) into the `Order` struct or into per-commitment storage at `placeOrder` time, and use the snapshotted value in `_splitSurplus` / solver-authorization checks at fill time, the same way `protocolFeeBps` is already baked into the reduced `order.inputs` and commitment.
- Alternatively, apply `_updateParams` changes only to orders placed after the update (versioned params keyed by a monotonically increasing params-epoch, with each order recording the epoch it was placed under), or add a timelock so outstanding orders can be filled/cancelled under the old terms before new terms take effect.

### Proof of Concept
1. Governance calls `initialize`/`_updateParams` with `surplusShareBps = 5000` (50% to protocol / 50% to beneficiary).
2. User calls `placeOrder(...)`, escrowing input tokens; solver observes the order and any off-chain quote assumes a 50/50 surplus split (as demonstrated in `evm/tests/foundry/IntentGatewayV2Test.sol` lines 931-990, which shows the split is computed at fill time from live `_params`).
3. Before the solver's `fillOrder` transaction lands, governance dispatches another `UpdateParams` request via `onAccept` (as exercised in `evm/tests/foundry/IntentGatewayV2Test.sol` lines 2851-2906) setting `surplusShareBps = 10000` (100% to protocol).
4. Solver calls `fillOrder` with the same overpayment amount planned under the old split; `_splitSurplus` now reads the new `_params.surplusShareBps`, and the beneficiary receives 0% of the surplus instead of the 50% assumed when the order was placed and the bid was prepared — exactly reproducing `evm/tests/foundry/IntentGatewayV2Test.sol` lines 1073-1110 ("100% to protocol, 0% to beneficiary") applied retroactively to an order created under different terms.

    /// @dev Splits overpayment between protocol and beneficiary. An order with output calldata
    /// gives the beneficiary nothing, since the surplus is not the caller's to give.
    function _splitSurplus(uint256 dust, bool hasOutputCall)
        internal
        view
        returns (uint256 protocolShare, uint256 beneficiaryShare)
    {
        if (hasOutputCall) return (dust, 0);
        protocolShare = (dust * _params.surplusShareBps) / 10_000;
        beneficiaryShare = dust - protocolShare;
    }

     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,

     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to

     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }

        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }
