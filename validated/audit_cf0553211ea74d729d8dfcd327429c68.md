I identified a concrete, exploitable analog. In the webhook handling path, `ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, but the `shop` (and `topic`/`webhook_id`) fields used by the app's webhook handler come from unauthenticated HTTP headers that are never covered by the signature.### Title
Webhook `shop`/`topic`/`webhook-id` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC only ever covers the raw request body. The `shop`, `topic`, and `webhook_id` values that the handler receives (and that a host app uses to attribute the webhook to a tenant) come straight from HTTP headers that are completely outside the signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are all read from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) via `shopify_header`, none of which participate in `to_signable_string`: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` trusts the request as soon as this body-only HMAC check passes, then hands `request.shop` and `request.topic` directly to the app's handler as the tenant/topic identity for the webhook, with no additional binding check: [5](#0-4) 

The identity binding that should hold is: `HMAC(secret, signed_bytes)` proves authenticity of **exactly** `{shop, topic, webhook_id, body}` as a unit. What is actually proven is `HMAC(secret, body)` == valid, while `shop`, `topic`, and `webhook_id` are taken from bytes that were never authenticated. Because the app's `client_secret`/`api_secret_key` is shared across every shop that has the app installed, any shop that has installed the app can obtain a validly-signed webhook body (e.g., from its own `app/uninstalled`, `shop/redact`, or other topic with a small/fixed body shape) and then resend that exact body to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because the body is unchanged, yet `Registry.process` reports the victim's shop as the webhook's origin to the handler.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is supposed to provide: an app relying on `WebhookMetadata#shop` (constructed from `request.shop`) to decide which merchant's session/store record to modify is exposed to cross-tenant webhook injection by any other merchant who has the app installed. Depending on how the host app implements handlers (e.g., GDPR `shop/redact`, `customers/redact`, `app/uninstalled` cleanup, inventory/order sync), this can be used to trigger destructive or state-changing actions against a shop the attacker does not own, which is a cross-tenant access violation as defined by the task's Critical impact category (cross-tenant access without holding that tenant's credentials).

### Likelihood Explanation
Likelihood is Medium: the attacker must (a) have the app installed on a shop they control (not privileged access to the app's secret), (b) discover a topic whose signed body is generic enough to be replayed against a different shop's context (many topics such as `app/uninstalled` carry no shop-specific fields in the body at all), and (c) be able to reach the app's public webhook endpoint directly with forged headers, which is standard for any internet-facing webhook receiver built on this gem, since the gem does no origin-IP or additional binding check beyond the body HMAC.

### Recommendation
Include the identity fields (`shop`, `topic`, and ideally `webhook_id`) in the signed material verified by `HmacValidator`, or perform a secondary, cryptographically-bound comparison (e.g., require the `dest`/shop the app expects for that installation to match `request.shop`, sourced from a value the app already trusts, such as a stored per-shop token) before dispatching to a handler. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be used as the sole tenant-selection key without additional verification (e.g., checking the shop is a known/installed shop and cross-referencing against application-level authorization), and consider extending `Webhooks::Request#to_signable_string` to canonically include the header-derived shop/topic if Shopify's HMAC scheme is ever extended to support this (currently Shopify only signs the body, so this may require an app-level compensating control rather than a gem-only fix).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining a legitimately signed webhook for a low-content topic, e.g. `app/uninstalled`, with headers:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid HMAC of the empty/minimal body using the app's shared secret>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: <id>
   ```
2. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the same endpoint, but changes only:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over `@raw_body` (unchanged) and succeeds, since `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31` never look at the `shop` header.
4. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` per `lib/shopify_api/webhooks/registry.rb:198-199`, causing the app to run its uninstall/cleanup logic against the victim shop even though the victim never uninstalled the app and the attacker holds no credentials for that shop.
