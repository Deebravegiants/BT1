### Title
Reserve fee (treasury yield) can be permanently rounded away to zero on frequent `accrue()` calls - ([File: mainnet/contracts/vault/v0-vault-usdc.clar], and identically in `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
The vault `accrue` function splits newly-accrued borrower interest into a treasury reserve share and a supplier share using integer division. Because the reserve share (`reserve-inc`) is computed from a *delta* since the last accrual and each accrual immediately advances the stored index, any interest delta small enough that `reserve-inc` rounds down to `u0` is never recovered on a later call — it is permanently lost rather than deferred. An unprivileged caller can force this every block by repeatedly invoking the public `accrue()` function, keeping the reserve-factor's cut of interest at zero indefinitely while suppliers still get full economic benefit of the (already-applied) index update.

### Finding Description
In every vault contract, `accrue` recomputes the borrow index and the treasury cut in one shot: [1](#0-0) 

The key lines:
```clarity
(old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
(new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
(debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```
`mul-div-down` truncates: [2](#0-1) 

`idx` is unconditionally advanced to `next` regardless of whether `reserve-inc` was nonzero:
```clarity
(if (not (is-eq idx next)) (var-set index next) false)
```
This mirrors exactly the reward-rounding bug class from the report: a proportional split (`balance/supply` there, `fee-reserve/BPS` here) computed once per period via floor-division, where the numerator that should have been the "reward" (here, the DAO treasury's reserve fee) is dropped to zero when the per-call delta is small relative to the divisor, and — critically — is **never revisited** because the underlying state (`index`) that the delta is measured against has already moved forward. This breaks the identity:

`Σ(reserve-inc over all accrue calls) == fee-reserve/BPS × Σ(total interest actually accrued)`

If a caller forces many small `debt-delta`s (by calling `accrue()` every block instead of allowing interest to compound over a longer interval), the LHS trends toward 0 while the RHS remains the full intended protocol fee — i.e., the DAO treasury's unclaimed yield is permanently destroyed rather than merely delayed.

### Impact Explanation
This is a "theft/permanent loss of unclaimed yield" scenario for the DAO treasury (the reserve-factor cut), matching the accepted High-impact category ("theft of unclaimed yield ... or permanent freezing of unclaimed yield"). Suppliers are not harmed (they still receive the full liquidity-index benefit), but the protocol's designated revenue stream is siphoned away from the treasury and effectively redistributed to suppliers, with no way to reclaim it after the fact because the `old-debt`/`new-debt` comparison window resets with every `accrue()` call.

### Likelihood Explanation
`accrue()` is a public function reachable by anyone (it is invoked automatically before other public entrypoints, and can also be called directly as a standalone transaction). No privileged role, oracle manipulation, or flashloan is required — a griefer/attacker only needs to submit `accrue()` transactions frequently (e.g., every block) to keep `debt-delta` small enough that `reserve-inc` floors to zero. The likelihood that `debt-delta * fee-reserve / BPS` rounds to zero depends on `INDEX-PRECISION`, `fee-reserve` (in BPS), and `scaled-principal`; for vaults with modest debt and a typical reserve factor (e.g., 1000 BPS = 10%), sub-block deltas realistically fall under this threshold, especially in periods of low utilization or lower-decimal assets.

### Recommendation
Track un-realized reserve fee as a running remainder (or accumulate `debt-delta` across calls until `reserve-inc` clears the rounding threshold) instead of discarding the truncated fraction each time the index is advanced. Alternatively, round `reserve-inc` up (`mul-div-up`) at the expense of suppliers rather than the treasury, or accrue reserve fee based on the cumulative index delta since the last time reserve was actually minted (not since the last `accrue()` call), so partial fees carry forward instead of being reset when `index` is bumped.

### Proof of Concept
1. Vault has `fee-reserve` = e.g. `u1000` (10%) and `BPS` = `u10000`, with a nonzero `scaled-principal` (outstanding debt).
2. Attacker calls `accrue()` in block N: `old-debt` computed at `idx`, `new-debt` computed at `next` (interest accrued during a short time-delta, e.g. 1 block ≈ 10s). Because the time-delta is tiny, `debt-delta` is a small integer (or even can be `u0`/`u1`).
3. `reserve-inc = debt-delta * 1000 / 10000` truncates to `u0` whenever `debt-delta < 10`.
4. `index` is nonetheless updated to `next` (`(var-set index next)`), so this same interest delta will never be seen again by the reserve calculation — the next call's `old-debt` starts from the now-current `idx`.
5. Attacker repeats step 2 every block indefinitely. Over time, the vault's suppliers receive the full compounded interest (because `lindex`/liquidity index still advances each call), but `treasury-lp` is minted as `u0` in call after call, so the DAO treasury permanently receives none (or a negligible fraction) of its intended 10% reserve cut, compared to calling `accrue()` only once after a long interval where `debt-delta` would be large enough to produce a nonzero, correctly-rounded `reserve-inc`.

Note: I was unable to independently verify from the index the exact numeric value of `INDEX-PRECISION` and the reachability/gas cost of calling `accrue()` every single block across all vault contracts due to index size limits — starting a full Devin session against the repository would allow confirming exact constants and simulating the attack end-to-end with real numbers.
