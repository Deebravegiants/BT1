### Title
Webhook `shop` (and `topic`/`api-version`/`webhook-id`) headers are not covered by the HMAC signature, allowing tenant impersonation in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `ShopifyAPI::Webhooks::Registry.process` validates never covers the `shop-domain` header. Any party able to obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — which is the same secret for every shop that installs the app, not per-tenant — can replay that body with an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. The HMAC check still passes, and the forged shop value is handed unchecked to the app's webhook handler as `WebhookMetadata#shop`, breaking the binding between "HMAC-authenticated bytes" and "the shop the app believes sent them."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

It returns only `@raw_body`. `Registry.process` validates the HMAC exclusively against this signable string: [2](#0-1) 

`request.shop`, however, is read directly from an unauthenticated header: [3](#0-2) 

and is passed straight through to the handler as the tenant identifier in `WebhookMetadata`: [4](#0-3) 

Because `api_secret_key` (the app's client secret) is shared across every shop installation — it is not per-tenant — any shop that has legitimately installed the app can receive a real, validly-signed webhook (valid `(body, hmac)` pair) from Shopify for its own store, then resend that identical body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different (victim) shop's domain. `HmacValidator.validate` still succeeds because it only recomputes the HMAC over `@raw_body`: [5](#0-4) 

The identity binding that should hold is: `shop-domain header == shop that produced the HMAC-signed body`. This gem breaks that binding because the shop header is acted upon (`request.shop` is trusted and forwarded to app logic) but is not included in the HMAC-covered bytes.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is merely a normal (unprivileged) installer of the vulnerable app can make the app process webhook data while believing it originated from a shop the attacker does not control. Depending on how the host application keys data/actions off `WebhookMetadata#shop` (e.g. updating billing state, order data, or triggering shop-specific side effects), this can lead to cross-tenant data corruption or unauthorized actions attributed to another merchant — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires no leaked secrets, tokens, or privileged access: the attacker only needs to be able to install the target app on their own store (available to any internet user with a Shopify dev/partner account) to obtain one legitimately-signed `(body, hmac)` pair, then replay it against the app's public webhook endpoint with a modified shop header. No cryptographic secret is guessed or broken — the header simply falls outside the signed payload.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the HMAC-covered signable string, or otherwise cryptographically bind the `shop-domain` header to the signed body (e.g., verify it against a shop known to be associated with the specific HMAC/secret being used, or require the host application to independently verify `request.shop` is one it has previously seen with a token before trusting it in `WebhookMetadata`).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends the app a real webhook: body `{"id":1}`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed with the app's `api_secret_key`.
2. Attacker captures this `(body, hmac)` pair (e.g., by running their own receiving endpoint or intercepting the callback they control).
3. Attacker POSTs the same body and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only covers `@raw_body`, unchanged from step 1. [6](#0-5) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload was never generated by Shopify for that shop.
