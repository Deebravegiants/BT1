### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the shop domain, topic, and webhook id used for tenant/topic routing are taken from unauthenticated HTTP headers. This breaks the identity binding `HMAC-verified bytes == bytes acted upon`, allowing a request with a genuine, previously-observed `(raw_body, hmac)` pair to be replayed with a forged `shop-domain`/`topic` header and still pass validation.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the received `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

However, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, which are *not* part of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches purely on the (unauthenticated) `request.topic`, forwarding the (unauthenticated) `request.shop` to the app's handler as the tenant identifier: [4](#0-3) 

The documented usage pattern explicitly instructs apps to key their tenant-scoped processing (e.g. job queue routing, DB writes) off `data.shop` and `data.topic`: [5](#0-4) 

This is the same bug class as the referenced report: fees (there) / the tenant-identity fields (here) are acted upon by downstream logic, but excluded from the value that is cryptographically authenticated. The equality that should hold is:

`shop used for tenant routing == shop authenticated by the HMAC`

but the code instead guarantees only:

`raw_body authenticated by the HMAC` ⊄ `{shop, topic, webhook_id} used for routing`

### Impact Explanation
Because the `api_secret_key` used to compute the webhook HMAC is a single shared secret for the whole app (not per-shop), any merchant who installs the app on their own store can trigger a real webhook delivery and capture a valid `(raw_body, hmac)` pair signed by Shopify. That attacker can then replay the exact same body/HMAC directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) with an arbitrary value. `HmacValidator.validate` will accept it because it never inspects those headers, and `Registry.process` will hand the forged `shop`/`topic` straight to the app's handler as authenticated fact. In an app that uses `data.shop` to scope database writes, background jobs, or cache invalidation (exactly as the gem's own documentation recommends), this enables cross-tenant data confusion/injection — the attacker can make the app believe arbitrary attacker-controlled content originated from a victim shop or a different webhook topic than what Shopify actually sent.

### Likelihood Explanation
Any developer/merchant can install the target app on a store they control and receive a legitimately-signed webhook, satisfying the only precondition (capturing one valid `(body, hmac)` pair for the shared app secret). No access to `api_secret_key`, access tokens, or victim credentials is required. This is a low-effort, always-reachable path through the gem's core `Webhooks::Request`/`Registry` classes as documented.

### Recommendation
Include the identity fields in the signed content, or otherwise cryptographically bind them to the authenticated body:
- Extend `Request#to_signable_string` (or add a secondary verification step in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` so that tampering with these headers invalidates the HMAC.
- At minimum, document and/or enforce in `Registry.process` that the `shop` header must match a shop with a currently registered/expected webhook subscription for that specific topic before invoking the handler, rather than trusting the header value outright.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`, subscribe to a topic (e.g. `orders/create`).
2. Trigger the event in the attacker's own store; Shopify sends a real webhook: headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`, plus `raw_body`.
3. Replay the identical `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) succeeds because it only checks `raw_body`.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) invokes the app handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, causing the host app to treat attacker-controlled data as authenticated content from `victim-shop.myshopify.com`.
