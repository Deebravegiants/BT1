### Title
Atomic multi-token escrow withdrawal in IntentGatewayV2 permanently freezes an order's funds if any single token transfer becomes non-executable - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentsBase._withdraw` releases every escrowed token of an order in a single atomic loop. If a transfer for any one token in that loop permanently reverts (e.g. the beneficiary is later blacklisted by a token issuer, or the token is paused), the entire withdrawal transaction reverts, and because `_filled[commitment]` is only set inside that same reverted call, the failure state is never persisted. Every subsequent attempt to redeem or refund the order hits the identical revert, permanently freezing *all* of the order's escrowed assets — including the ones that remain perfectly transferable — exactly mirroring the reported bug class where an external, unprivileged action after commitment makes a settlement path irrecoverably impossible to complete.

### Finding Description
`_withdraw` iterates over `body.tokens`, decrements the per-token escrow accounting, and performs `IERC20(token).safeTransfer(beneficiary, amount)` for each token before finalizing the order: [1](#0-0) 

Finalization (`_filled[commitment] = beneficiary`) and fee release both happen only if the whole loop, including every `safeTransfer`, completes without reverting: [2](#0-1) 

This function is the single settlement path reached from three unprivileged entry points:
- `_cancelSameChain`, reachable by the order's own user calling `cancelOrder()`, which builds a `WithdrawalRequest` covering *all* remaining input tokens and calls `_withdraw(body, true, true)` in one shot: [3](#0-2) 
- `onAccept` for `RedeemEscrow`/`RefundEscrow`, reachable by anyone relaying a Hyperbridge message after a cross-chain fill or a destination-side cancellation, which also calls the same all-or-nothing `_withdraw`: [4](#0-3) 
- `onGetResponse`, reachable by anyone submitting a relayed storage proof after a source-side cancellation, which likewise finishes with `_withdraw`.

The tron fork of the app contains the identical pattern in its own `withdraw()`, looping over tokens with a low-level `.call` that reverts the whole function (`TransferFailed`) on the first failing transfer: [5](#0-4) 

In every one of these paths there is no mechanism to skip, quarantine, or separately re-attempt an individual token that cannot be transferred to the beneficiary. Just as the audited lending protocol assumed the LP position NFT it depended on would always remain retrievable — and broke irrecoverably once it was burned by its owner — `IntentGatewayV2`/`IntentsBase` assumes every input token in an order will always accept a transfer to the (immutable) beneficiary address recorded at order placement. Any post-placement event that makes one of those transfers permanently revert (issuer blacklist, token pause, token contract self-destruct/upgrade breaking `transfer`) removes the *only* code path capable of releasing escrow for that commitment, since `_filled` is never marked and the commitment can be replayed forever with the same result.

### Impact Explanation
Once a single token in an order's input set becomes untransferable to its beneficiary, none of the order's escrowed tokens — not just the affected one — can ever be released: same-chain cancellation, cross-chain refund delivery, and cross-chain redeem delivery all route through the same atomic `_withdraw`/`withdraw`. This is a permanent freezing-of-funds condition with no governance or user-level recovery path in the reviewed code, matching the "permanent freezing of funds" acceptance criterion. The severity is amplified because `order.inputs` can be an arbitrary token list chosen by the user at placement time, and many widely used stablecoins (e.g., USDC, USDT) support issuer-level blacklisting of arbitrary addresses at any time after escrow — a realistic, foreseeable event rather than a contrived "malicious token" scenario.

### Likelihood Explanation
Likelihood is moderate: it requires an external event (blacklist/pause) to hit the specific beneficiary/token pair used by an already-placed order. This is outside the direct control of the order's user or any Hyperbridge/gateway operator, similar to the original report where the lender's decision to burn a position was outside the borrower's/protocol's control. Given the widespread use of blacklist-capable tokens in real DeFi flows, this is a plausible, non-privileged trigger rather than a purely theoretical one.

### Recommendation
Do not perform per-token transfers in one atomic all-or-nothing loop when finalizing a withdrawal. Options:
- Persist `_filled`/escrow decrements per-token immediately as each transfer succeeds (not gated behind the full loop), so a stuck token doesn't block release of the others.
- Wrap each token transfer in a try/catch and, on failure, move the stuck amount into a separate per-token "pending" balance that the beneficiary (or anyone) can retry or redirect later, rather than reverting the entire finalize step.
- Alternatively, mark the order `_filled` unconditionally once the withdrawal request is authenticated, and treat individual token transfer failures as a separate claimable/retryable ledger entry keyed by `(commitment, token)`.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder` with two input tokens: a normal ERC20 and a blacklist-capable stablecoin (e.g., a mock USDC with a `blacklist(address)` admin function), beneficiary = `order.user`.
2. After escrow, the stablecoin issuer blacklists `order.user`'s address (an event entirely outside the protocol's or the order placer's control).
3. `order.user` calls `cancelOrder()` (same-chain) or the cross-chain cancel/redeem flow completes and Hyperbridge delivers the `RefundEscrow`/`RedeemEscrow` message to `onAccept`.
4. `_withdraw` reaches the blacklisted-token `safeTransfer` call inside the loop over `body.tokens`, which reverts (`ERC20: transfer to blacklisted account` style revert bubbling through `SafeERC20`), reverting the whole transaction: [1](#0-0) 
5. Because the revert happens before `_filled[commitment]` is set, every future retry of `onAccept`/`cancelOrder`/`onGetResponse` for this commitment hits the same revert. The other (non-blacklisted) input token, plus any accumulated `TRANSACTION_FEES`, remain permanently locked in the gateway with no code path able to release them.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }

        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }
