### Title
Excess ETH from Uniswap swaps in `EvmHost.dispatch()`/`fundRequest()` is permanently trapped in the contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are all `payable` and, when `msg.value > 0`, forward the *entire* `msg.value` to `swapETHForExactTokens` on the configured Uniswap V2 router to buy an exact amount of `feeToken`. None of these functions capture or refund the leftover ETH that the router returns after the swap.

### Finding Description
In each of these functions the pattern is identical: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } ...
```

The same pattern recurs in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

The standard `UniswapV2Router02.swapETHForExactTokens` implementation only spends the exact ETH amount required to obtain `post.fee`/`amount`/`get.fee` tokens, and refunds any unused ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amountIn)`. Because `EvmHost` itself is the caller of the router (not the original end user), that refund lands back on the `EvmHost` contract's own balance rather than being returned to the user who originally sent the extra ETH. `EvmHost` has no `receive()`/`fallback()` designed to route or track this incoming ETH, and — critically — none of `dispatch`, `dispatch(DispatchGet)`, or `fundRequest` forward the leftover amount back to `_msgSender()`. There is also no admin/owner "sweep ETH" function visible in `EvmHost.sol` to recover it. This is a direct analog of the `createAndInitializePool` finding: a `payable` entrypoint that performs a swap with the full `msg.value` but never calls an equivalent of `refundETH()` for the unused portion.

### Impact Explanation
Any user or integrating contract (e.g. `HyperFungibleToken.send`, `IntentGatewayV2`/`ExtrinsicIntents` cross-chain dispatch paths, or any `HyperApp` calling `dispatchWithFeeToken`/native dispatch) that slightly overestimates the native fee and calls `dispatch{value: msg.value}(...)` or `fundRequest{value: msg.value}(...)` on `EvmHost` will have the ETH dust permanently locked in the `EvmHost` contract with no path to reclaim it. Over many transactions across a widely used relayer/dispatch entrypoint, this can accumulate into a material amount of permanently frozen user funds — a medium-severity freezing-of-funds issue reachable by any unprivileged caller dispatching a POST/GET request or funding a request with native token payment.

### Likelihood Explanation
Likelihood is high: every native-token payment path documented for `dispatch()`/`fundRequest()` explicitly instructs callers to send `msg.value` covering the fee, and any imprecision in the client-side fee estimate (gas price/slippage between quote time and execution) results in dust that cannot be recovered. This is a routine, frequently-triggered path rather than an edge case, since native-token payment is one of the two officially documented payment methods for POST/GET dispatch.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the actual amount spent (`amounts[0]` returned by the swap) and refund `msg.value - amounts[0]` back to `_msgSender()` via a low-level ETH transfer, mirroring the `refundETH()` pattern referenced in the original report.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires 0.3 ether worth of ETH to obtain via the Uniswap swap.
2. `swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)` executes, spending ~0.3 ether and refunding ~0.7 ether back to `msg.sender` of the swap call, which is `EvmHost` itself.
3. `EvmHost.dispatch` returns without forwarding any of that 0.7 ether back to the user.
4. The 0.7 ether now sits in `EvmHost`'s balance with no function in `EvmHost.sol` (as observed in this scan) to withdraw or credit it back to the user, resulting in permanent loss of the overpaid ETH. [1](#0-0) [2](#0-1) [3](#0-2)
