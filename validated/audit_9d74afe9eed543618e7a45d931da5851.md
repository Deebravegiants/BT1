### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by computing an HMAC only over the raw request body, then trusts the `shop-domain` header verbatim to build the `WebhookMetadata` passed to the host app's handler. The header identifying *which tenant* the payload belongs to is never bound into the HMAC, so it can be swapped without invalidating the signature.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field of the `VerifiableQuery` implementation: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`, while `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no part in the signed string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (an unauthenticated header value) to the handler as the tenant identity, alongside the (HMAC‑authenticated) body: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`

Because the HMAC only covers `@raw_body`, this equality is never enforced. Any actor who can capture one legitimate signed webhook payload for their own shop (any merchant with the app installed can trivially do this, e.g. by observing their own webhook deliveries) can resend the exact same `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` (the body and signature are still a valid pair), and `Registry.process` calls the handler with `shop: <attacker-chosen value>` and `body: <victim's/attacker's own valid payload>`.

The documentation for this exact call explicitly promises full authentication of the request: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," which is not true for the `shop` field of the resulting `WebhookMetadata`. [5](#0-4) 

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (as the API is documented and intended to be used) to select which merchant's session, storage row, or tenant context to update will process attacker-controlled body content while attributing it to an attacker-chosen shop. Because the API's own trust boundary (`process` = "verified request from Shopify") silently omits binding the tenant field, this crosses the cross-tenant boundary the gem is supposed to enforce for host applications relying on its guarantees.

### Likelihood Explanation
Exploitability only requires: (1) attacker has any shop with the target app installed (installing a free/dev app is trivial and requires no privilege beyond being a normal merchant), (2) they capture one webhook delivery (their own endpoint receives it, or they can trigger one via a normal store action), and (3) they replay the captured `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint with a modified `shop-domain` header. No knowledge of `api_secret_key` or any credential belonging to the victim shop is required, making this reachable by an ordinary unprivileged actor.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signable string bound to the HMAC, or independently verify `request.shop` against a value derived from an authenticated source (e.g., cross-check against the known session/shop for the delivery, and enforce webhook-id uniqueness/replay protection per shop). At minimum, update `Request#to_signable_string` so the HMAC comparison also incorporates the shop-domain header, and document that `WebhookMetadata#shop` is not currently HMAC-bound so host applications know they must not trust it as an authenticated tenant identifier on its own.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; attacker controls that shop and observes/captures one legitimate webhook delivery: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (a valid HMAC of `B` under the app's secret, as computed by Shopify).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same `raw_body = B` and same `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop) and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature over `raw_body = B` only and finds it matches `H` — validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: <parsed B>, ...)`, i.e., data legitimately produced for/by `shop-a` is now attributed to `shop-b` in the host application: [7](#0-6)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
