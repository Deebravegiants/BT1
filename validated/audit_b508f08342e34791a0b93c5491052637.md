### Title
Webhook tenant identity (`shop`) is read from an unauthenticated header while only the raw body is HMAC-verified, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the `X-Shopify-Hmac-Sha256` header against the raw request body [1](#0-0) . The `shop` (and `topic`, `webhook_id`) values that are handed to the app's `WebhookHandler` are pulled straight from HTTP headers, which are never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `HmacValidator.validate` computes/compares the HMAC over exactly that string using `Context.api_secret_key` [3](#0-2) . Meanwhile `Request#shop`, `#topic`, and `#webhook_id` are derived from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers [4](#0-3)  — fields that are never included in `to_signable_string` and therefore never covered by the HMAC.

`Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` unconditionally when building `WebhookMetadata` for the handler: [5](#0-4) 

This breaks the intended equality `shop_bound_by_hmac == shop_used_by_handler`. In reality: `bytes_verified (raw_body) != bytes_that_determine_tenant (shop-domain header)`.

Because Shopify's webhook body payload does not itself repeat/bind the delivering shop's domain into content that is covered by the signature in a way this code checks, any actor who can obtain one legitimately-HMAC-signed webhook body for topic `T` (trivially available — install the app on any store the attacker controls, or on a free/dev store, and receive a normal webhook delivery with a valid `X-Shopify-Hmac-Sha256` header for that body) can replay that same `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` still succeeds (it only checks the body bytes against the secret, which the attacker did not need to know), and `Registry.process` will dispatch the handler with `shop:` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the app's webhook handler acts on `data.shop`/`data.topic`/`data.body` believing they are authenticated as originating from that shop, but the gem has not actually bound the shop identity to the signed bytes. Any handler that uses `request.shop` to select which tenant's database row/session/access token to update (which is exactly the documented purpose of `WebhookMetadata#shop`) can be made to write/act against an arbitrary victim shop's tenant record using data an attacker fully controls (their own webhook payload content), or can be used to trigger mandatory-compliance actions (`shop/redact`, `customers/redact`, etc.) against a victim shop chosen by the attacker. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires no privileged credential — only the ability to install the app on an attacker-controlled/dev store to legitimately receive one signed webhook body, and the ability to POST to the app's public webhook endpoint with attacker-chosen headers, both of which are available to any unprivileged internet user.

### Recommendation
Bind the tenant/topic/webhook-id identity into the signed material, or verify header-derived fields against a source of truth: e.g., include `shop`, `topic`, and `webhook_id` in the string that `to_signable_string` returns (matching Shopify's actual webhook signing scheme only if Shopify itself signs those fields), or, since Shopify's HMAC only covers the raw body, require the app to independently confirm `request.shop` corresponds to a shop with an active session/installation for this app before trusting it, and treat the `shop-domain` header as untrusted metadata rather than an authenticated identity claim inside `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it register a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's real `api_secret_key`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays it directly to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` then `Registry.process(request)`.
5. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `B` [2](#0-1) .
6. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...))` executes with the attacker-controlled body attributed to `victim.myshopify.com` [6](#0-5) .
