### Title
Stale secondary oracle leg remains valid and skews blended collateral prices - (File: contracts/price-aggregator/src/engine.rs)

### Summary
A secondary price source can be hours old yet still pass freshness checks whenever its configured `max_stale_seconds` allows it. The aggregator then averages that stale quote with the fresh primary quote if the prices remain inside tolerance, allowing collateral to be valued above its current market price and enabling under-collateralized borrows. [1](#0-0) [2](#0-1) 

### Finding Description
Each feed is marked stale only when `now - timestamp` exceeds that feed's configured `feed.max_stale_seconds`. [1](#0-0) 

The source-level flag is then combined with the asset-level `oracle.max_price_stale_seconds`, but no separate freshness bound is applied relative to the other leg. [3](#0-2) 

For a two-source oracle, `blend` marks the result stale only when either leg is individually stale or when both legs are market-nature feeds whose timestamps differ by more than `MAX_LEG_AGE_SPREAD_SECONDS`. [4](#0-3) 

If both prices are within the configured tolerance, the accepted price is their midpoint. [5](#0-4) 

Configuration validation permits staleness budgets as large as 93,600 seconds and only requires each source's bound not to exceed the asset's bound. [6](#0-5) [7](#0-6) 

The included regression test configures a RedStone secondary leg with an 86,400-second staleness allowance, leaves its 23-hour-old `$1.00` observation unchanged while the primary updates to `$0.91`, and obtains a valid blended price of approximately `$0.955`. [8](#0-7) 

### Impact Explanation
An unprivileged borrower can use collateral whose accepted price is skewed upward by a stale secondary leg. In the in-repository proof, supplying 100,000 XLM and borrowing 70,000 USDC succeeds under the stale-anchor midpoint even though the same borrow fails with `INSUFFICIENT_COLLATERAL` when the secondary leg is fresh. [9](#0-8) [10](#0-9) 

This creates an under-collateralized debt position. If the borrower does not repay before the oracle recovers, the shortfall becomes protocol bad debt and can make the lending market insolvent. [11](#0-10) 

### Likelihood Explanation
The attacker only needs an ordinary `borrow` call after a secondary oracle stops updating or remains within a permissive heartbeat. No privileged call, oracle-key compromise, malformed configuration, or transaction manipulation is required. [9](#0-8) 

The deployed XOXNO oracle configuration includes a 86,400-second aggregate staleness budget, demonstrating that day-scale freshness windows are part of the supported configuration surface. [12](#0-11) 

The condition requires a dual-source market where one leg lags while its stale price remains inside the configured deviation tolerance. That scenario can occur during a normal heartbeat delay or provider outage, so exploitation does not depend on the oracle reporting a maliciously false value. [13](#0-12) 

### Recommendation
For two-source prices, apply the timestamp-divergence bound to every pair of legs rather than only when both legs have `FeedNature::Market`. A mixed Reflector/RedStone oracle should be marked stale when the leg timestamps differ by more than `MAX_LEG_AGE_SPREAD_SECONDS`. [4](#0-3) [14](#0-13) 

Alternatively, derive the effective freshness budget for secondary legs from the tighter of the feed's configured `max_stale_seconds` and a protocol-level maximum dual-source leg-age gap. The stale-leg case should fail closed before midpoint blending. [15](#0-14) 

### Proof of Concept
The repository already contains an executable proof in `tests/test-harness/tests/controller/audit_borrow_withdraw_liquidate_stale_anchor_blend.rs`.

1. Configure XLM with a fresh Reflector primary and a RedStone secondary whose `max_stale_seconds` is 86,400 and whose tolerance is 1,000 bps. [16](#0-15) 
2. Initialize both sources at `$1.00`, then update the primary to `$0.91`. [17](#0-16) 
3. Leave the secondary timestamp 82,800 seconds in the past while retaining its `$1.00` price. [18](#0-17) 
4. Fund the pool by supplying 500,000 USDC, then have the borrower supply 100,000 XLM. [19](#0-18) 
5. Call controller `borrow` for the borrower's account on the USDC market with a 70,000 USDC amount. The stale-anchor run succeeds and values collateral over 4% higher than the fresh-anchor control, while the control borrow fails with `INSUFFICIENT_COLLATERAL`. [20](#0-19)
