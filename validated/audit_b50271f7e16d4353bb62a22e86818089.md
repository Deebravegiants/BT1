### Title
Webhook shop/topic/id headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never included in that signed content. `Registry.process` accepts any request whose body/HMAC pair validates and then forwards the *unauthenticated* `shop` value to the app's handler as the trusted tenant identifier, breaking the binding `shop covered by HMAC == shop delivered to handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic tie to the signature: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively over `to_signable_string` (i.e., the raw body) using the app's shared `client_secret`: [3](#0-2) 

`Registry.process` checks only this body/HMAC signature, then immediately trusts `request.shop` and hands it to the registered handler as the tenant identity for the event: [4](#0-3) 

Because a Shopify app's `client_secret` is shared across *all* merchant shops that install the app (it is not per-shop), any actor who installs the app on their own shop can capture a genuine `(raw_body, hmac)` pair generated for their own store. Since `shop-domain` (and `topic`/`webhook_id`) are excluded from the signed content, that same valid `(raw_body, hmac)` pair remains cryptographically valid no matter what `shop-domain` header accompanies it. The attacker can therefore POST directly to the app's public webhook endpoint with the captured body+HMAC but a forged `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will accept it and dispatch it to the handler labeled as an event for the victim shop — a genuine identity-binding break: "shop whose secret authenticated the payload" ≠ "shop attributed to the payload."

### Impact Explanation
This lets an attacker who merely installs the app on a shop they control forge webhook events (e.g., `orders/create`, `app/uninstalled`, GDPR topics) attributed to any other merchant shop using this gem's own trusted-field surface (`WebhookMetadata#shop`), causing the host application to process attacker-supplied data under a victim tenant's identity — cross-tenant data injection/corruption. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled shop (a normal, unprivileged action any merchant can take), (2) capturing one legitimate webhook body+HMAC delivered for that shop, and (3) POSTing it directly to the app's public webhook endpoint with a forged shop-domain header. No access to the `client_secret`, access tokens, or any victim credentials is required, since the shop field sits entirely outside the HMAC-covered content.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable content verified against the HMAC, or independently cross-check the `shop` header against session/tenant records associated with the specific delivery (e.g., validate that the shop is one the app has an active installation/session for and correlate delivery metadata) before trusting `WebhookMetadata#shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw JSON body `B` and header `x-shopify-hmac-sha256: H` (valid, since it's HMAC(`B`, shared `client_secret`)).
2. Attacker sends a direct HTTP POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but header `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(B, secret) == H`: [5](#0-4) 
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload/HMAC actually originated from the attacker's own shop: [6](#0-5)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
