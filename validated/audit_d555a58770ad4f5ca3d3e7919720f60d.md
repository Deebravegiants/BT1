### Title
Webhook `shop` (tenant) identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the shop identity used to route the webhook to the host application's handler is taken from an unauthenticated header. Any actor who can obtain one legitimately-signed `(body, hmac)` pair — e.g., by installing the app on their own store and triggering a webhook — can replay that exact pair against the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, causing the gem to hand the host application data attributed to a victim shop.

### Finding Description
`Request#to_signable_string` only returns the raw request body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signature: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the body) against the HMAC: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then dispatches to the host application's handler using `request.shop` unmodified and unverified: [4](#0-3) 

The binding that should hold is: `shop header == shop bound by HMAC`. In this gem it instead holds: `shop header == unauthenticated attacker-supplied value`, while only `body == HMAC(body, secret)` is actually checked. Because the app's `api_secret_key` is shared across all shops that install the app (it is not shop-specific), any user who can install the app on their own shop (an ordinary, unprivileged action — creating a free/dev store and installing the app) can trigger a real webhook delivery, capture the resulting `(raw_body, hmac)` pair, and then directly POST that same body/hmac to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will pass because the body/hmac pair is genuinely valid, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the (forged) victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an attacker with no special privileges (just their own shop's ability to install the app and receive webhooks) can inject data or trigger domain logic (e.g., order/customer/app-uninstall webhooks) attributed to another tenant's shop. Any host application that trusts `WebhookMetadata#shop` for tenant-scoped data writes, cache invalidation, or access-token lookups is exposed to cross-tenant data confusion/injection, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that: (1) has multiple shop installs (the norm for public apps), and (2) exposes a single shared webhook endpoint per topic (the standard registration pattern via `Registry`). The attacker only needs their own installation to harvest a valid `(body, hmac)` pair for a topic/body shape they control (e.g. by placing a test order in their own dev store), then replay it with a different `shop-domain` header — no access to `api_secret_key` or any victim credential is required.

### Recommendation
Bind the shop identity to the signature verification: include the `shop-domain` (and ideally `topic`/`webhook_id`/`api_version`) header values in the string that is HMAC-verified, or otherwise cryptographically tie the claimed shop to the request before it is handed to `WebhookMetadata`/the host handler in `lib/shopify_api/webhooks/registry.rb#process`.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker.myshopify.com`), a standard, unprivileged action.
2. Attacker performs an action that triggers a webhook (e.g., creates an order), and captures the raw `POST` body `B` and the `x-shopify-hmac-sha256` header `H` that Shopify sent to the app's webhook endpoint (observable if the attacker controls any intermediary, logging proxy, or simply operates their own receiving endpoint temporarily pointed at by a controllable redirect/mirror, or via the app's own visible webhook logs if exposed).
3. Attacker sends a new HTTP request directly to the app's public webhook URL:
   - Headers: `x-shopify-topic: <same topic>`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: victim-shop.myshopify.com`
   - Body: `B` (unchanged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (identical to step 2), per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` per `lib/shopify_api/webhooks/registry.rb:198-199`, causing the host application to process attacker-controlled data as belonging to the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
