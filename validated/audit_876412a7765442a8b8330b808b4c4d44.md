## Analysis

The GHSA-hhx9-4vw2-x54r bug class is "authenticated-but-unprivileged user obtains API keys/secrets via a normal read endpoint" (RhodeCode's `get_repo` leaked API keys to any authenticated user). Chainlink has a directly analogous pattern: two GET endpoints return live authentication credentials (`AccessKey` / `OutgoingToken`) to users holding only the lowest ("view") role, even though creation/rotation of those credentials is gated behind the "edit" role.

### Title
Bridge and External Initiator authentication tokens (`OutgoingToken`, `AccessKey`) are disclosed to unprivileged "view"-role authenticated users - (File: core/web/router.go)

### Summary
`GET /v2/external_initiators` and `GET /v2/bridge_types` (and `GET /v2/bridge_types/:BridgeName`) are registered without any role-gating middleware, so any authenticated user — including the lowest-privilege `view` role, which is documented and tested as read-only/non-sensitive — can retrieve the `AccessKey` for every configured External Initiator and the `OutgoingToken` for every configured Bridge.

### Finding Description
In `v2Routes`, the index/show handlers for both resources are wired without `auth.RequiresEditRole`/`RequiresAdminRole`, unlike their mutating counterparts: [1](#0-0) 

The handlers serialize sensitive fields directly into the response:
- `ExternalInitiatorResource` includes `AccessKey` (the credential identifier used together with a corresponding secret to authenticate as an External Initiator and trigger job runs): [2](#0-1) 
- `BridgeResource` includes `OutgoingToken` unconditionally (only `IncomingToken` is create-only/`omitempty`): [3](#0-2) 

These tokens are generated as high-entropy secrets specifically for bridge/initiator authentication: [4](#0-3) [5](#0-4) 

The node's own RBAC test suite confirms these two GET routes are intentionally reachable by the `view` role (`viewOnlyAllowed: true`), the same role that is blocked from every mutating/administrative operation: [6](#0-5) 

By contrast, the RBAC middleware itself demonstrates the intended privilege boundary — `view` and `run` roles are explicitly excluded from "edit" operations: [7](#0-6) 

This is the same bug class as the RhodeCode/Kallithea `get_repo` disclosure: a read endpoint intended for basic authenticated visibility (viewing which bridges/initiators exist) also leaks the authentication secrets attached to those objects, collapsing the privilege boundary between "can view configuration" and "can act as/impersonate the bridge or external initiator."

### Impact Explanation
A user provisioned with only the `view` role (e.g., a monitoring/dashboard account, explicitly meant to have no ability to create, edit, or trigger jobs) can enumerate `AccessKey`/`OutgoingToken` values for every configured Bridge and External Initiator on the node. Depending on how `OutgoingToken` is consumed downstream (I was not able to fully trace its verification call site within the available tool budget — this should be confirmed by a follow-up code review of the pipeline bridge/webhook resume path), possession of it may allow an unprivileged internal account to impersonate a bridge/external initiator or forge responses attributed to it, which is a request-impersonation / secret-disclosure impact matching CWE-200/CVSS vector `AV:L/AC:L/PR:L/UI:N/C:H` in the source advisory.

### Likelihood Explanation
High for the disclosure itself: no special conditions are needed beyond having any valid authenticated session with the lowest role, which is explicitly supported by the product's role model and is tested/expected traffic (`view` role test in `auth_test.go`). The endpoints require no additional parameters or race conditions.

### Recommendation
Wrap `GET /v2/external_initiators` and `GET /v2/bridge_types` / `GET /v2/bridge_types/:BridgeName` with `auth.RequiresEditRole` (matching the role required to create/rotate these credentials), or strip `AccessKey`/`OutgoingToken` from the index/show presenters and only return them once, at creation time (as `IncomingToken` already does via `omitempty`).

### Proof of Concept
1. Create a node user with role `view` (`chainlink admin users create --role=view`).
2. Log in as that user and issue: `GET /v2/external_initiators` — response includes `accessKey` for every External Initiator, per `ExternalInitiatorResource`.
3. Issue: `GET /v2/bridge_types` — response includes `outgoingToken` for every Bridge, per `BridgeResource`.
4. Confirm via `core/web/auth/auth_test.go` RBAC matrix that both routes are `viewOnlyAllowed: true`, i.e., intentionally reachable by the lowest role, while `POST`/`PATCH`/`DELETE` on the same resources require `edit`.

**Note on completeness:** I was unable, within the tool-call budget, to trace the exact downstream verification logic for `OutgoingToken` (e.g., whether it authenticates callback/resume requests) to fully confirm the impersonation impact chain. This should be validated with a full read of the pipeline bridge/webhook handling code before treating the impact severity as final.

func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error,
) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)

// NewExternalInitiator generates an ExternalInitiator from an
// auth.Token, hashing the password for storage
func NewExternalInitiator(
	eia *auth.Token,
	eir *ExternalInitiatorRequest,
) (*ExternalInitiator, error) {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(eia, salt)
	if err != nil {
		return nil, pkgerrors.Wrap(err, "error hashing secret for external initiator")
	}

	return &ExternalInitiator{
		Name:           strings.ToLower(eir.Name),
		URL:            eir.URL,
		AccessKey:      eia.AccessKey,
		HashedSecret:   hashedSecret,
		Salt:           salt,
		OutgoingToken:  utils.NewSecret(utils.DefaultSecretSize),
		OutgoingSecret: utils.NewSecret(utils.DefaultSecretSize),
	}, nil
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
