### Title
Stale `Account.owner` field lets a prior NFT holder retain full spending authority after transferring the position NFT - (File: contracts/controller/src/account.rs)

### Summary
CVE-2016-7075 is an authentication bypass caused by trusting an unvalidated identity field (the X.509 hostname) instead of the verified identity. The analog here: several controller entrypoints authorize `caller` against `account.owner` — a value stored in the `Account` struct at mint time — rather than against the live NFT owner (`storage::account_owner`, which reads `Base::owner_of`). Position NFTs are freely transferable (`NonFungibleToken`/`NonFungibleEnumerable` on `PositionNft` is the stock OZ interface with no transfer hook into the controller), so a seller can transfer the NFT yet keep owner-equivalent authority over the account's collateral and debt capacity.

### Finding Description
In `contracts/controller/src/account.rs`, `load_or_create_account` calls `require_owner_or_delegate(env, account_id, caller, &account.owner)` (account.rs:101-108), where `account` comes from `storage::get_account` and `account.owner` was written once in `create_account_with` (`Account { owner: owner.clone(), .. }`, account.rs:64-70). In contrast, `require_account_owner` (used by `renew_account`, `add_delegate`, `remove_delegate`) deliberately re-reads ownership via `storage::account_owner(env, account_id)` — the comment at account.rs:142 states it verifies "`caller` currently owns the account NFT," confirming the struct field is not the live source of truth.

The NFT contract exposes the stock OZ `transfer`, `transfer_from`, `approve`, and `approve_for_all` (contract.rs:131-173) with no controller callback to rewrite `account.owner`. Therefore after `position_nft.transfer(alice → bob, id)`:

- `account.owner` still equals `alice`;
- `is_owner_or_delegate` returns `true` for `alice` (account.rs:121);
- `require_owner_or_delegate` admits `alice` on every guarded entrypoint (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`), which all resolve the account through `load_or_create_account`/`require_owner_or_delegate` per scripts/permissionless_entrypoints.txt:49-56.

Additionally, `get_delegates(env, account_id, owner)` is keyed by the stored `owner`, so delegates granted by the *old* owner continue to pass `is_owner_or_delegate` after transfer — a second stale-identity path.

### Impact Explanation
Theft of user funds. Bob buys/receives the position NFT believing he owns the account's collateral. Alice (the previous owner) calls `controller::withdraw(account_id, collateral_hub_asset, amount, to: alice)` or `borrow(...)` — `require_owner_or_delegate` passes because `account.owner == alice` — and drains the collateral Bob just paid for, up to the account's full supply balance and LTV debt capacity. Any still-active delegate of the old owner can do the same. This meets the "theft of user funds" acceptance criterion.

### Likelihood Explanation
High. The trigger is a routine, unprivileged NFT `transfer` on the position-nft contract — explicitly in scope ("position-nft transfer/approve"). No privileged role, oracle manipulation, or flash path is needed. The window is permanent: `account.owner` is only written at mint, and the struct is loaded fresh on each call with the stale value. The only mitigating factor is whether `storage::get_account`/`account_owner` re-syncs the field on load; nothing in `account.rs` does so, and the deliberate use of `storage::account_owner` in `require_account_owner` implies the struct field is known to be unreliable for exactly this reason.

### Recommendation
Derive authority from the live NFT owner on every path: in `load_or_create_account` (or inside `require_owner_or_delegate`), replace `&account.owner` with `storage::account_owner(env, account_id)`, and key `get_delegates` by that live owner. Alternatively, make `storage::get_account` restamp `account.owner` from `owner_of` at load time, and clear the delegate set on ownership change so grants cannot survive a transfer.

### Proof of Concept
```rust
// Setup: alice supplies USDC collateral via controller::supply -> account_id = N.
// position_nft contract minted token N to alice; Account.owner == alice in storage.

// 1. Alice sells the position to bob.
position_nft.transfer(&alice, &bob, &N);
assert_eq!(position_nft.owner_of(N), bob);

// 2. Bob (real owner) tries to withdraw — reverts: account.owner != bob.
//    (require_owner_or_delegate compares against stale Account.owner == alice.)

// 3. Alice retains authority and drains the collateral she sold.
controller.withdraw(&alice, &N, &usdc_hub_asset, &full_amount, &alice);
// Passes require_owner_or_delegate (account.rs:136 -> is_owner_or_delegate:121
// matches stored owner == alice), post-pool solvency still clears since
// withdrawal is her own collateral in storage. USDC lands with alice.

// Bob holds a worthless NFT over an empty account.
```

Note: I could not read `storage::account_owner`/`get_account` in `contracts/controller/src/storage/account.rs` within the available iterations to confirm whether the stored `Account.owner` is re-synced on load. If `get_account` already restamps `owner` from `owner_of`, this finding reduces to the delegate-list staleness (delegates keyed under the old owner persisting post-transfer), which still lets an old owner's active delegate act on the account — still Medium.
