## Finding

Sablier's bug class — "a value is trusted for identity/authorization purposes but was never covered by the cryptographic proof that supposedly authenticates the message" — has a direct analog in the webhook verification path of this gem.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns **only the raw HTTP body**, not any header: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers, not from the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the HMAC against `to_signable_string` (the raw body) and the app's `api_secret_key`: [3](#0-2) 

Once that check passes, `Registry.process` trusts `request.shop` (the header value) as the tenant identity and forwards it straight to the app's handler: [4](#0-3) 

### The broken equality

The code implicitly assumes:
`bytes verified by HMAC == identity (shop) acted upon`

but in fact:
`bytes verified by HMAC (body only) != shop header value (unauthenticated)`

Since the app's `api_secret_key` is the same for every shop that installs the app (it's a per-app secret, not per-shop), any merchant who has a legitimately installed instance of the app can capture one valid `(raw_body, x-shopify-hmac-sha256)` pair sent to their own store, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, letting the attacker inject a forged webhook event attributed to another tenant.

This is not a hypothetical gap in the host app's logic — it originates purely in this gem: `Webhooks::Request` deliberately excludes headers from the signed string, and `Registry.process`/`HmacValidator.validate` provide no separate binding between the verified body and the `shop` header that is handed to the app as the authenticated tenant identifier.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are trusted as tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body. The `shop`, `topic`, and `webhook_id` values consumed by `Registry.process` and forwarded to the app's webhook handler come from HTTP headers that are entirely excluded from the HMAC computation, so `Utils::HmacValidator.validate` cannot detect tampering with these fields.

### Finding Description
`Request#hmac` and `#to_signable_string` are computed solely from `@raw_body` (`lib/shopify_api/webhooks/request.rb:11-13,35-38`). `Request#shop`, `#topic`, and `#webhook_id` are read directly from HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`) that play no role in signature verification. `Registry.process` validates the HMAC and, on success, passes `request.shop` unchanged into `WebhookMetadata` given to the application's handler (`lib/shopify_api/webhooks/registry.rb:188-199`). Because the app's `api_secret_key` (used in `HmacValidator.validate`, `lib/shopify_api/utils/hmac_validator.rb:12-31`) is shared across all shops that install the app, a valid `(body, hmac)` pair obtained from one shop's genuine webhook delivery remains valid when replayed with a forged `shop-domain` header pointing at a different shop.

### Impact Explanation
This allows cross-tenant webhook forgery: an attacker who controls one shop installation of the app can generate an authenticated-looking webhook event attributed to a victim shop, since the "shop" identity is never bound to the signed bytes. Depending on what the host app does with webhook data (e.g., updating per-shop state, billing, or order records keyed by `shop`), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's tenant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only a legitimate (even free/trial) installation of the target app by the attacker to obtain one genuine `(body, hmac)` pair from Shopify, then a single crafted HTTP POST to the app's public webhook endpoint with a substituted `x-shopify-shop-domain` header. No access to another merchant's credentials or the app's `client_secret` is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed payload verification — e.g., include them in the HMAC-computed digest, or independently verify the `shop` header corresponds to a shop for which the app holds an active session/installation matching this specific event, rather than trusting the header verbatim once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggers a real webhook (e.g., `orders/create`), and captures the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` per `lib/shopify_api/utils/hmac_validator.rb:33-40`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header (`lib/shopify_api/webhooks/request.rb:20-23`); `HmacValidator.validate` recomputes the HMAC over `B` only and succeeds because the app's secret and body are unchanged (`lib/shopify_api/utils/hmac_validator.rb:12-22`).
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", topic: ..., body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act as if `victim.myshopify.com` sent this webhook event.

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
