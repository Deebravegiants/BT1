## Analysis

The CVE-2020-8118 bug class — an **authenticated, non-privileged user registering a URL "subscription" that the server later blindly requests, enabling SSRF against internal/local services** — has a direct structural analog in the chainlink node's bridge subsystem.

### Title
Authenticated Edit-role user can register a Bridge/External-Initiator URL that bypasses the node's SSRF protections, enabling internal service discovery - (File: core/services/pipeline/runner.go)

### Summary
Chainlink nodes expose `POST /v2/bridge_types` and `POST /v2/external_initiators`, both gated only by `auth.RequiresEditRole` (a role strictly below Admin), which let an authenticated user register an arbitrary `URL` for later use. [1](#0-0) [2](#0-1)  When a job later runs a `bridge` pipeline task referencing that name, the node resolves the URL from its own database and issues the HTTP request using the **unrestricted** HTTP client — explicitly bypassing the local/private-network SSRF guard that is applied to the ordinary `http` task type.

### Finding Description
`ValidateBridgeType` only checks that the `URL` field is non-empty; it performs no allowlist/blocklist check against localhost, link-local, or private-network addresses. [3](#0-2) 

When the pipeline runner initializes a job, it deliberately wires bridge tasks to the unrestricted HTTP client, with a comment acknowledging the URL is only "safe" because it is taken from the node's own DB — not because any actual host validation happened: [4](#0-3) 

`BridgeTask.Run` then looks up the bridge by name and performs the outbound request to that stored, unrestricted URL: [5](#0-4) [6](#0-5) 

By contrast, the `HTTPTask` (a different pipeline task type intended for arbitrary URLs) applies restricted-network protections by default and only allows bypass via an explicit, per-task `allowUnrestrictedNetworkAccess` flag: [7](#0-6) . This is the exact protection that bridge tasks are architecturally excluded from, since the runner unconditionally assigns them `unrestrictedHTTPClient`.

### Impact Explanation
An Edit-role user (a role explicitly distinct from, and less privileged than, Admin per the RBAC route table) [8](#0-7)  can register a Bridge (or External Initiator) whose URL points at internal-only addresses (e.g. cloud metadata endpoints, internal admin panels, other services on the private network/localhost). Any job that references that bridge by name — which only requires Run role to trigger — will cause the node to make the outbound request and return the raw response body as the job run result via the `/v2/jobs/.../runs` and pipeline_runs APIs. This lets a limited-privilege actor probe and read from internal/local network services that should not be reachable from the node's public-facing job pipeline, exactly matching the "detect local and remote services" impact described in CVE-2020-8118.

### Likelihood Explanation
Likelihood is high in any deployment where Edit-role accounts are not implicitly as trusted as Admin (a common RBAC assumption, since the tiers are modeled and enforced separately throughout `core/web/router.go`). No code path validates or restricts the bridge/EI URL against private, loopback, or link-local ranges at creation or at request time — the protection that exists for the generic `http` task is architecturally absent for `bridge` tasks.

### Recommendation
Apply the same SSRF allowlist/blocklist checks used by the restricted HTTP client (`clhttp.NewRestrictedClient` / `ErrDisallowedIP`) to Bridge and External Initiator URLs, either at creation time (`ValidateBridgeType`, `ValidateExternalInitiator`) or by making bridge tasks default to the restricted HTTP client unless an explicit, audited opt-in (mirroring `AllowUnrestrictedNetworkAccess` on `HTTPTask`) is set — rather than unconditionally granting them unrestricted network access in `runner.go`.

### Proof of Concept
1. As a user with only Edit role, call `POST /v2/bridge_types` with `{"name":"metadata","url":"http://169.254.169.254/latest/meta-data/iam/security-credentials/"}` (or any internal/localhost address, e.g. the node's own admin API). [9](#0-8) 
2. Create/trigger a job with a `bridge` task referencing `name="metadata"`.
3. The pipeline runner assigns `bt.httpClient = r.unrestrictedHTTPClient` [10](#0-9)  and `BridgeTask.Run` sends the request to the internal URL and returns the body as the task's `Result.Value`. [6](#0-5) [11](#0-10) 
4. Retrieve the response contents via the job run results API, confirming SSRF/internal-service disclosure — while the same request through a generic `http` task with an interpolated URL would have been blocked with "Connections to local/private and multicast networks are disabled" as seen in `TestHTTPTask_OverrideURLSafe`. [12](#0-11)

func ValidateBridgeType(bt *bridges.BridgeTypeRequest) error {
	fe := models.NewJSONAPIErrors()
	if len(bt.Name.String()) < 1 {
		fe.Add("No name specified")
	}
	if _, err := bridges.ParseBridgeName(bt.Name.String()); err != nil {
		fe.Merge(err)
	}
	u := bt.URL.String()
	if len(strings.TrimSpace(u)) == 0 {
		fe.Add("URL must be present")
	}
	if bt.MinimumContractPayment != nil &&
		bt.MinimumContractPayment.Cmp(assets.NewLinkFromJuels(0)) < 0 {
		fe.Add("MinimumContractPayment must be positive")
	}
	return fe.CoerceEmptyToNil()
}
