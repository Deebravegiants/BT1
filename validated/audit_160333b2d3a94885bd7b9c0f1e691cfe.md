Since the app's `api_secret_key` (`Context.api_secret_key`) is a single per-app secret shared by every shop that installs the app, any shop that receives a genuine webhook already possesses a `(raw_body, valid HMAC)` pair. Nothing in this gem's verification stops that same `(raw_body, HMAC)` pair from being replayed to the app's webhook endpoint with the `shopify-shop-domain` header changed to a different, victim shop — `HmacValidator` never inspects the shop header, so validation still succeeds, and the handler is invoked with `data.shop` set to whatever the attacker supplied.

### Title
Webhook shop identity is trusted from an unauthenticated header while HMAC only covers the body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` (used by `Utils::HmacValidator` to verify inbound webhooks) returns only the raw request body. The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed material. `Registry.process` validates the HMAC and then forwards `request.shop` unchanged into `WebhookMetadata`, so the shop identity handed to app code is not bound by the HMAC that "authenticates" the request.

### Finding Description
The identity equality that should hold is: `shop asserted to the handler == shop that the signed bytes actually originated from`. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac-sha256` header [5](#0-4)  — `to_signable_string` for `Request` is just `@raw_body` [6](#0-5) . The `shop` field [7](#0-6)  is read from an HTTP header that is completely outside that signed string. Because `Context.api_secret_key` is one static secret per app (not per shop), an attacker who legitimately installs the app on shop A and receives one real webhook can capture `(raw_body, hmac header)`, then replay it to the app's webhook endpoint with `shopify-shop-domain` swapped to shop B (or any arbitrary value). `Registry.process` passes this check and calls the handler with `WebhookMetadata#shop` equal to the attacker-controlled value [2](#0-1) .

### Impact Explanation
Per `docs/usage/webhooks.md`, `data.shop` is the field host applications are told to rely on to know which tenant a webhook belongs to (e.g. to look up that shop's session/store data, enqueue per-shop jobs, etc.) [4](#0-3) . Since this value is unauthenticated relative to the HMAC, an app built on top of this gem's documented API can be made to process real webhook payloads under a false shop identity — a cross-tenant identity-binding break that can lead to incorrect data being written to, or fetched for, the wrong shop, satisfying the "cross-tenant access" impact category.

### Likelihood Explanation
The only prerequisite is that the attacker be an ordinary merchant/user who has installed the target app on at least one shop (unprivileged internet user), which lets them obtain one valid `(body, HMAC)` pair to replay with a forged shop header — no access to `api_secret_key` or any privileged credential is required.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signable material for `Webhooks::Request`, or otherwise cryptographically bind the asserted shop to the request before constructing `WebhookMetadata`, so `Registry.process` cannot be fooled into attributing verified bytes to an attacker-chosen shop.

### Proof of Concept
1. App installs on `shop-a.myshopify.com`; attacker (merchant of shop A) receives a real webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker POSTs to the app's webhook endpoint with the same raw body `B`, the same `H`, but header `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this passes [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "shop-b.myshopify.com", body: parsed(B), ...)` [9](#0-8) , even though `B` never originated from shop B.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook.   extend ShopifyAPI::Webhooks::WebhookHandler
