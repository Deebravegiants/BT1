## Title
Pool Creator Can Register a Coin/PC Mint With a Freeze Authority, Enabling Permanent Freezing of Pool Vaults - (File: `program/src/processor.rs`)

## Summary
`process_initialize2` validates that the newly-minted LP token has no freeze authority, but it never checks whether the pool's `coin_mint`/`pc_mint` (the actual assets deposited into the AMM vaults) have a freeze authority. Any unprivileged user calling `Initialize2` can supply a mint they control that has an active freeze authority. Once the pool is created and other LPs deposit into the shared vaults, the mint's freeze authority can freeze the `amm_coin_vault`/`amm_pc_vault` SPL token account at will, permanently locking swap and withdrawal for that pool — mirroring the external report's core failure mode of an irreversible, unvetted asset registration leading to permanently unbridgeable/unusable funds.

## Finding Description
In `process_initialize2`, the code unpacks `coin_mint` and `pc_mint` and later validates several properties of the created vault accounts and LP mint: [1](#0-0) 

The checks performed against the vaults only cover `delegate`, `close_authority`, and matching mint address — never the mint's own freeze authority: [2](#0-1) 

Only the freshly-created `lp_mint` is checked for the absence of a freeze authority: [3](#0-2) 

Because `coin_mint`/`pc_mint` are entirely attacker-supplied accounts (any unprivileged user picks them when calling `Initialize2`), a user can register a pool using a mint they control that still has a freeze authority set. `Self::unpack_mint` only checks the account is owned by the SPL Token program and is a valid `Mint` layout — it performs no freeze-authority validation: [4](#0-3) 

Once the pool is live and other unprivileged LPs deposit funds via `Deposit` (which transfers real user coin/pc tokens into `amm_coin_vault`/`amm_pc_vault`), the original mint freeze authority can call the standard SPL Token `FreezeAccount` instruction against the vault token account at any moment. This is entirely outside the Raydium program's control since the AMM only owns the vault account, not the mint's freeze authority.

Once frozen, all functions moving tokens out of that vault fail at the SPL Token CPI layer, since `token_transfer`/`token_transfer_with_authority` used in `process_swap_base_in/out`, `process_swap_base_in_v2/out_v2`, and withdraw processing all rely on the vault account being unfrozen: [5](#0-4) [6](#0-5) 

There is no admin instruction in the program to migrate a pool's coin/pc vault or mint to a new account once `Initialize2` succeeds — the `AmmInfo.coin_vault_mint`/`pc_vault_mint` bindings set at line 969-970 are permanent for the life of the pool.

## Impact Explanation
Once liquidity providers deposit into a pool whose underlying coin/pc mint retains a freeze authority, that authority (controlled by the malicious pool creator or a colluding party) can freeze the vault token account at any time, permanently trapping all coin/pc tokens deposited by every LP in that pool — mirroring the external report's "permanently unbridgeable, users lose their tokens, no way to pause/fix a specific pair" outcome. This is a direct, permanent freezing of user/LP funds with no on-chain remediation path in the reachable instruction set (Initialize2/Deposit/Withdraw/Swap).

## Likelihood Explanation
Any unprivileged user can create an SPL mint with a freeze authority (a completely standard, unprivileged token operation) and then call `Initialize2` themselves to register it as a coin or pc mint — no elevated permission or special account is required, and the check gap exists on every path through `process_initialize2`. An attacker only needs one successful `Initialize2` transaction with attacker-chosen mint accounts, followed by waiting for/attracting LP deposits, to set up the freeze.

## Recommendation
In `process_initialize2`, explicitly reject `coin_mint`/`pc_mint` accounts whose `freeze_authority` is `Some(_)`, the same way it is already done for the LP mint at lines 904-906. If certain projects require a freeze authority for compliance reasons, gate that exception behind an explicit admin-approved allowlist rather than allowing any unprivileged pool creator to introduce such mints.

## Proof of Concept
1. Attacker creates SPL Token mint `M` (as coin_mint) with `freeze_authority = attacker_key`, using standard `initialize_mint`.
2. Attacker calls `Initialize2` on the Raydium AMM program, supplying `M` as `amm_coin_mint` and a normal token as `amm_pc_mint`, funding minimal initial liquidity themselves.
3. `process_initialize2` passes all checks (lines 742-906) because none of them inspect `coin_mint.freeze_authority`.
4. Other users add liquidity via `Deposit`, transferring real value into `amm_coin_vault`.
5. Attacker (freeze authority of `M`) submits a standard `spl_token::instruction::freeze_account` against `amm_coin_vault`.
6. All subsequent `SwapBaseIn/Out`, `SwapBaseIn/OutV2`, and withdraw calls referencing this vault fail permanently at the SPL Token CPI layer, permanently freezing all LP funds in the pool with no recovery instruction available.
