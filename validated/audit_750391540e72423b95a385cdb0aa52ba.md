### Title
Missing `return` after failed email-claim extraction lets the OIDC login flow continue and issue a valid authenticated session - (File: `core/sessions/oidcauth/oidc.go`)

### Summary
The reported CVE describes an Apache CloudStack SAML plugin flaw where an error/edge-case in the external‑IdP assertion handling path was not correctly enforced, letting requests continue and bypass the intended authentication gate. Chainlink's OIDC identity-provider integration contains a directly analogous logic defect in `oidcAuthenticator.handleTokenExchange`, the HTTP handler that completes the browser-facing OIDC login flow (`core/sessions/oidcauth/oidc.go`).

### Finding Description
`handleTokenExchange` validates the CSRF `state`, exchanges the authorization code, and verifies the signed `id_token`. It then extracts the `email` claim: [1](#0-0) 

If the `email` claim is missing or not a string, the code logs the error and writes an HTTP 500 response via `c.String(...)`, but **does not `return`**. Execution falls through to role mapping, session insertion, cookie assignment, and a final `200 OK` JSON response: [2](#0-1) 

Because there is no early return, a request whose verified `id_token` lacks (or has a non-string) `email` claim still proceeds to:
1. Map the token's group/role claims to a Chainlink RBAC role via `IDClaimsToUserRole` (unaffected by the missing email).
2. `INSERT INTO oidc_sessions (id, user_email, user_role, created_at)` with an empty/whatever `email` value.
3. Emit `audit.AuthLoginSuccessNo2FA`.
4. Set the session cookie (`ginSession.Set(webauth.SessionIDKey, clSession.ID)`, `ginSession.Save()`).
5. Return `http.StatusOK` with `Success: true` — even though an internal error path was already triggered.

This is exactly the CVE-2016-3085 bug class: an error/edge-case branch in the external identity-provider callback is logged but not enforced, so the authentication flow silently continues and still grants a usable, cookie-backed session.

### Impact Explanation
Any client completing the OIDC/OAuth2 callback whose ID token omits (or malforms) the `email` claim — for example due to scope misconfiguration, an IdP not returning `email` for certain accounts, or claim manipulation on IdPs that allow it — still gets a fully functional Chainlink session with a role derived from group claims (up to `UserRoleAdmin`). The resulting `oidc_sessions` row stores an essentially uncontrolled `user_email` value, and `AuthorizedUserWithSession` trusts this row directly: [3](#0-2) 

This breaks the intended fail-closed behavior of the authentication gate and can grant privileged (Admin/Edit/Run) node-API access via a session created through an incompletely validated identity assertion, undermining the WebServer.OIDC authentication method entirely.

### Likelihood Explanation
Reaching this code only requires completing the standard OIDC redirect/callback flow against whatever `WebServer.OIDC.ProviderURL` is configured — no privileged access to the node is needed beforehand. The trigger condition (an `id_token` lacking a string `email` claim) is plausible in real deployments (misconfigured scopes, service/machine accounts, IdPs that omit `email` for non-verified addresses), making this a realistic, not merely theoretical, edge case, though it does still require control over or interaction with the actual configured IdP's issued token contents.

### Recommendation
Add an explicit `return` immediately after the failed `email` claim extraction in `handleTokenExchange`, ensuring the HTTP 500 response terminates the handler and no session/cookie is created:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, audit other branches of the OIDC/LDAP authenticators for similar "log-error-without-return" patterns, since this class of bug is easy to reintroduce.

### Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'oidc'` with a valid OIDC provider.
2. Obtain (or have the IdP issue) a validly signed `id_token` that includes the configured role-mapping group claim (e.g. `AdminClaim`) but does **not** include an `email` claim (or where `email` is a non-string type).
3. Complete the standard redirect flow (`/oidc-login` → provider → callback) and POST the resulting `code`/`state` to the token-exchange endpoint (`handleTokenExchange`, mounted via `oi.provider`/router in the OIDC package).
4. Observe that despite the handler writing an HTTP 500 for the missing email, the response also completes with `Success: true`, `Set-Cookie` is issued, and a corresponding row is inserted into `oidc_sessions` with the mapped role — the session cookie is fully valid for subsequent authenticated node API calls.

Note: I could not locate the exact router-registration line that mounts `handleTokenExchange` to a path within the indexed context (searches for "ExtendRouter"/route registration in `oidc.go` did not surface the route-setup snippet), so the exact HTTP path is unconfirmed from the available index; this does not affect the validity of the logic flaw itself, which is unambiguous from the handler code shown above.

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
