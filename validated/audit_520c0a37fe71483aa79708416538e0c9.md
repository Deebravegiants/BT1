### No vulnerability found for this question.

**Reasoning:**

The claimed divergence — that `hotSdk.buildGaslessWithdrawIntent` encodes `receiver` differently than what `validateEthAddress` validated — is not supported by the code. `createWithdrawalIntents` passes `args.withdrawalParams.destinationAddress` straight through, unmodified, as the `receiver` field to `this.hotSdk.buildGaslessWithdrawIntent`, and the resulting `receiver_id` in the emitted `mt_withdraw` intent is the same literal string, as confirmed by the test fixtures (e.g., `zeroAddress` in → `receiver_id: zeroAddress` out). [1](#0-0) [2](#0-1) 

`validateEthAddress` is explicitly documented as a **format-only** check, and the module-level docstring states plainly that "A valid format does not guarantee a bridge will accept the address" — this is intentional, disclosed behavior, not a hidden divergence. [3](#0-2) [4](#0-3) 

The scenario described — a native-asset withdrawal to an EVM address that happens to be a non-payable contract, causing an on-chain revert — is a case of funds being sent by the user/integrator to a correctly-validated, format-valid address that later fails execution on-chain. This is explicitly listed as out-of-scope: "funds sent by mistake to a correctly validated address." No code in this repo re-encodes, swaps, or misroutes the address; the same string that passed `validateEthAddress` is the same string encoded in the intent's `receiver_id`, so the invariant "validated address == paid address" is not actually broken — it is preserved byte-for-byte.

There is no reachable bug in `estimateWithdrawalFee`, `validateWithdrawal`, or `createWithdrawalIntents` that causes divergence between the validated address and the address ultimately encoded in the intent sent to the HOT Omni bridge relayer.

function validateEthAddress(address: string) {
	if (
		address === "0x0000000000000000000000000000000000000000" ||
		address.toLowerCase() === "0x000000000000000000000000000000000000dead"
	) {
		return false;
	}
	return isAddress(address, { strict: true });
}
