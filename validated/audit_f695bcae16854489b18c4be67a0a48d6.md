This timeout window does not pause or extend when the host is frozen.### Title
Requests dispatched or in-flight during a host freeze are immediately timed out on unfreeze because the timeout window is not paused - ([File: evm/src/core/HandlerV2.sol])

### Summary
`EvmHost` supports a `FrozenStatus` (`None`, `Incoming`, `Outgoing`, `All`) that an admin/handler can toggle via `setFrozenState()` to halt protocol operations, e.g. during a security incident or upgrade [1](#0-0) . While the destination host is frozen for `Incoming` messages, `HandlerV2.handlePostRequests` cannot be called because of the `notFrozen(host)` modifier [2](#0-1) [3](#0-2) . However, the `timeoutTimestamp` attached to each `PostRequest` is an absolute, real-world Unix timestamp computed at dispatch time on the source chain (`block.timestamp + post.timeout`) [4](#0-3) , and the destination-side timeout check compares this absolute value directly against the *live* `block.timestamp` with no accounting for any freeze period: `if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();` [5](#0-4) .

### Finding Description
Because delivery is blocked while `Incoming` (or `All`) is frozen but the timeout clock keeps advancing with real wall-clock time, any in-flight `PostRequest` whose `timeoutTimestamp` falls inside (or shortly after) the freeze window is rendered permanently undeliverable the moment the freeze is lifted. As soon as `setFrozenState(FrozenStatus.None)` is called, `handlePostRequests` immediately reverts with `MessageTimedOut` for such requests, and a relayer can instead call `handlePostRequestTimeouts`, whose only condition is `if (request.timeout() > state.timestamp) revert MessageNotTimedOut();` [6](#0-5) , allowing the request to be force-timed-out and the relayer fee refunded via `dispatchTimeOut` [7](#0-6) , without the application ever getting a fair chance to have the message delivered. This mirrors the reported analog: a pause (freeze) silently consumes the "grace" window that the protocol otherwise guarantees applications for message delivery, and resuming normal operation immediately penalizes the application/user (irreversible timeout / cancelled cross-chain call) through no fault of their own, purely due to the pause's duration overlapping the request's deadline.

### Impact Explanation
Applications relying on ISMP `PostRequest` semantics assume that once dispatched, a request either gets delivered or safely times out based on real elapsed processing time, not based on unrelated admin-controlled freeze windows. If a freeze (used for legitimate incident response, e.g., a compromised consensus client) lasts longer than some in-flight requests' remaining timeout budget, those requests are irreversibly timed out upon unfreeze, causing cross-chain calls (e.g., fund transfers, governance actions, escrowed transactions) to be cancelled/reverted on the source side even though the destination chain was fully capable of processing them — the delay was solely due to the protocol-level freeze. This can cause loss of intended cross-chain effects and unfair fee refunds at the expense of applications/users, which given the potential value moved via arbitrary cross-chain messages, is a Medium-severity funds/logic impact.

### Likelihood Explanation
Freezing the host is an expected, documented operational action (`setFrozenState`, `FrozenHost` error, `HostFrozen` event) [8](#0-7) [9](#0-8) , so any freeze event that lasts anywhere close to a request's configured timeout duration (which applications choose, sometimes short for UX reasons) will trigger this. No attacker action beyond a normal permissionless call to `handlePostRequestTimeouts` is required once the freeze ends and the deadline has passed, making exploitation straightforward and likely to occur in practice during any real incident-response freeze.

### Recommendation
Exclude frozen time from the timeout calculation — e.g., track the cumulative duration the host spent frozen (`Incoming`/`All`) and add it to `leaf.request.timeout()` before comparing against `block.timestamp` in `handlePostRequests`, or equivalently require `handlePostRequestTimeouts`/`handleGetRequestTimeouts` to subtract elapsed freeze time from `state.timestamp`/`block.timestamp` before the timeout comparison. This effectively grants a grace period equal to the freeze duration, consistent with the reported recommendation of excluding paused time from time-based penalties.

### Proof of Concept
1. Application on chain A dispatches `PostRequest` to chain B with `post.timeout = 300` (5 minutes); `timeoutTimestamp = block.timestamp + 300` is stored via `EvmHost.dispatch` [10](#0-9) .
2. Before the relayer can submit the `PostRequestMessage` proof to chain B, the admin calls `setFrozenState(FrozenStatus.Incoming)` on chain B's `EvmHost` (e.g., in response to an unrelated incident) [1](#0-0) .
3. `HandlerV2.handlePostRequests` cannot be called during this window due to `notFrozen(host)` [2](#0-1) .
4. The freeze remains active for 6 minutes (> the 5-minute timeout), then the admin calls `setFrozenState(FrozenStatus.None)`.
5. A relayer attempts `handlePostRequests` — it reverts with `MessageTimedOut` since `block.timestamp >= leaf.request.timeout()` [11](#0-10) .
6. The same or another relayer instead calls `handlePostRequestTimeouts` with a valid non-membership proof; the check `request.timeout() > state.timestamp` passes (i.e., is false), so the request is timed out and the relayer fee refunded via `EvmHost.dispatchTimeOut` [12](#0-11) [7](#0-6)  — the application's cross-chain call is permanently cancelled although the delay was entirely caused by the protocol-level freeze rather than any actual processing delay.
