This confirms the pattern. Every other credential-exchange flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) calls `Utils::ShopValidator.sanitize!(shop)` before building the `Session`/`HttpClient` that the request (including `client_secret`) is sent to. `Auth::Oauth.begin_auth` and `Auth::Oauth.validate_auth_callback`, however, never call `ShopValidator` on `shop`/`auth_query.shop` — the `shop` value flows directly into `auth_base_uri(shop)`, which becomes both the OAuth-authorize redirect target and, critically, the host that receives the POST containing `client_id`/`client_secret` during code exchange.

### Title
Missing `shop` domain validation in `Oauth.begin_auth`/`validate_auth_callback` allows forced-OAuth redirection to attacker-controlled host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth-authorize redirect from a caller-supplied `shop` string with no format validation, and `ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` (checked only for HMAC-signature membership, not for being a genuine `*.myshopify.com`/trusted domain) to compute `auth_base_uri(shop)`, the host that the code-exchange POST — containing `client_id` and `client_secret` — is sent to. Every sibling credential flow in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) calls `Utils::ShopValidator.sanitize!(shop)` before doing this; `Oauth` does not.

### Finding Description
`begin_auth` takes `shop:` directly from the caller (in practice, the unauthenticated `shop` query parameter of the app's "install"/"login" route) and passes it unmodified into `auth_base_uri(shop)`: [1](#0-0) [2](#0-1) 

There is no call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` anywhere in this file, unlike the equivalent code paths in other modules: [3](#0-2) [4](#0-3) [5](#0-4) 

`validate_auth_callback` does invoke `Utils::HmacValidator.validate(auth_query)`, but that only proves that `shop`, `code`, `state`, `host`, and `timestamp` together match a signature computed with the app's own `api_secret_key` — it does not constrain `shop` to a trusted Shopify domain: [6](#0-5) 

The `shop` value is then used, unsanitized, to build `null_session` and the `HttpClient` base path via `auth_base_uri(shop)`, which is the destination that receives the POST body containing `client_id` and `Context.api_secret_key`: [7](#0-6) 

This breaks the identity binding: **the host that is validated as belonging to the OAuth transaction (`auth_query.shop`, only checked for HMAC self-consistency) ≠ the host that must be a genuine, trusted Shopify domain before the app's `client_secret` is transmitted to it.** `Utils::ShopValidator` exists precisely to enforce this binding and is used everywhere else in the gem's auth code, but not in `oauth.rb`.

### Impact Explanation
This matches the High-impact category "SSRF with the app's credentials": if the host application passes an unauthenticated, attacker-influenced `shop` value straight into `begin_auth` (as the documented flow in `docs/usage/oauth.md` implies — `shop` originates from the pre-auth request), an attacker can steer the redirect to an attacker-controlled `auth_route` host and can also make `validate_auth_callback` build a code-exchange request whose destination host is attacker-controlled if `shop` is not otherwise constrained by the host app. Because `shop` is embedded in `auth_base_uri(shop)` for the `/oauth/authorize` redirect and again for the `access_token` POST that carries `client_id`/`client_secret`, a non-`myshopify.com` `shop` value results in the app's OAuth credentials being sent to a host outside Shopify. This is a direct violation of the tenant/host binding the gem is otherwise careful to enforce via `ShopValidator` in every other credential-issuing code path.

### Likelihood Explanation
The likelihood is high for any integrator following the gem's own documented pattern (`shop` comes in via an unauthenticated pre-install request and is forwarded to `begin_auth`) without independently re-implementing the same `ShopValidator` check the gem already provides and uses internally elsewhere. Since `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token` all defensively sanitize `shop` before constructing the request host, the omission in `Oauth` is an inconsistency rather than an intentional design choice, making it plausible this is an unpatched instance of the same class of bug the analog report describes (mismatched validation performed on one field vs. the field actually used to determine a security-critical destination).

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) on `shop` in `Oauth.begin_auth` before constructing `auth_route`, and on `auth_query.shop` in `Oauth.validate_auth_callback` before constructing `null_session`/`auth_base_uri`, mirroring the pattern already used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
1. Host app implements the documented `login` route by reading `shop` from the query string and calling `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`.
2. Attacker sends a victim merchant admin a link to the app's `login` route with `shop=attacker-controlled.example`.
3. `begin_auth` computes `auth_route = auth_base_uri("attacker-controlled.example") + "/oauth/authorize?..."` = `https://attacker-controlled.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=<app callback>&state=...`, with no rejection, since `auth_base_uri` in [8](#0-7)  only special-cases `.my.shop.dev` and otherwise blindly interpolates `shop` into an `https://` URL.
4. The victim's browser is redirected to the attacker's server, which can host a script mimicking the Shopify OAuth flow, or — if the attacker also controls a way to trigger `validate_auth_callback` with a matching `state` — the code-exchange step similarly sends `client_id`/`client_secret` to `auth_base_uri(auth_query.shop)` without the `shop` value ever being checked to be a genuine `*.myshopify.com`/trusted domain, unlike `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which reject non-trusted shops via `Utils::ShopValidator.sanitize!` before performing the equivalent request.
