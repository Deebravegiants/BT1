### Title
Reentrant `borrow()` calls transfer funds before writing the debt ledger, allowing the health check to be bypassed and vault funds to be drained beyond recorded debt - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`borrow()` in `v0-4-market.clar` transfers the borrowed asset to the receiver via `vault-system-borrow` *before* it writes the corresponding debt into the ledger via `.v0-market-vault debt-add-scaled`. If the borrowed asset's `ft-trait` implementation can trigger a callback during its `transfer` call (the same conditional assumption the ConvexMasterChef report relies on — "if [the] token allows for control of transfer call flow"), an attacker can reenter `borrow()` before the first call's debt is recorded, causing the health check to evaluate against stale (pre-borrow) debt and permitting a second payout without a matching increase in tracked debt.

### Finding Description
`borrow()` computes `collateral-value` / `debt-value` from `get-position`/`accrue-user-debts` at the top of the function, asserts health, then calls: [1](#0-0) 

`vault-system-borrow` performs the outbound token transfer to `funds-receiver`, and only *after* that external call returns does the function call `.v0-market-vault debt-add-scaled` to persist the scaled debt for `account`. This is the exact ordering flagged in the ConvexMasterChef finding: **external transfer happens before the internal accounting (debt ledger) update**.

If the receiving/borrowed token contract can execute code during `transfer` (post-transfer hook, upgradeable token, or any `ft-trait` implementation with callable logic) and re-enter `borrow()` for the same `account` before the outer call's `debt-add-scaled` executes, the nested call's `get-position`/`accrue-user-debts` will read the **pre-borrow** debt value (since the outer call hasn't written it yet). The nested call's health check (`is-healthy-with-mask`) is therefore evaluated against understated debt, letting a second `vault-system-borrow` payout go through. The result: two (or more) payouts leave the vault while the debt ledger in `v0-market-vault` (via `debt-add-scaled`, appended cumulatively) may not reflect the true amount that left the vault relative to what collateral could support at each step, because health was checked against stale state at each nested level.

This breaks the identity: `sum(vault-system-borrow payouts to account) <= debt recorded for account in v0-market-vault, consistent with collateral at each step`. Reentrancy allows payouts to outrun the debt ledger's ability to gate them.

### Impact Explanation
This directly parallels the "per-user debt ledger versus the vault aggregate" value identity called out as in-scope. If exploited, an attacker extracts vault liquidity (theft of principal / protocol insolvency) beyond what their collateral supports and beyond what the debt ledger will ever reflect as owed, since each nested health check is evaluated against understated debt. This is a Critical-class impact (protocol insolvency / theft of funds at rest) if a reentrant path exists.

### Likelihood Explanation
Likelihood is conditional — like the original finding — on whether any asset listed via `get-asset`/registered `ft-trait` in the market can trigger a callback during `transfer` (e.g., a token with hooks, or one that is upgraded post-listing to add such hooks). No explicit reentrancy guard (e.g., an `in-borrow` flag analogous to `in-flashloan` used elsewhere in the vault contracts) was found protecting `borrow()` in `v0-4-market.clar`. Given assets are DAO-vetted before listing, likelihood is lower than a fully unprivileged bug, but the code path itself contains the same ordering flaw the original report flags as the root cause, so it remains a code-level defect independent of whether a malicious token is present today.

### Recommendation
- Write the debt ledger update (`debt-add-scaled`) before performing the external token transfer (`vault-system-borrow`), or
- Add an explicit reentrancy guard around `borrow()` (and symmetric `repay()`/`liquidate()` paths) similar to the `in-flashloan` pattern already used in the vault contracts, ensuring no nested call to `borrow()` can execute while an outer call's state updates are still pending.

### Proof of Concept
1. Asset `X` is listed on the market with an `ft-trait` implementation that can execute code during `transfer` (e.g., is upgraded, or has a callback hook) and calls back into `market.borrow()`.
2. Attacker calls `borrow(X, amount, none, feeds)` with collateral just sufficient for `amount`.
3. Execution reaches `(try! (vault-system-borrow asset-id amount funds-receiver))` [2](#0-1) , which transfers `amount` of `X` to the attacker before `debt-add-scaled` executes.
4. During this transfer, `X`'s contract re-enters `borrow(X, amount, none, feeds)` for the same account. `get-position`/`accrue-user-debts` at the top of the nested call still reflect **zero** added debt from step 2/3 (since `debt-add-scaled` hasn't run yet), so `is-healthy`/`is-healthy-with-mask` pass again [3](#0-2) .
5. The nested call also transfers `amount` of `X` to the attacker and then writes its own `debt-add-scaled`.
6. Outer call resumes and writes its own `debt-add-scaled`.
7. Net effect: attacker received `2 * amount` of `X` from the vault while collateral only supported one health-checked `amount`, and the debt ledger's growth does not correspond to the risk actually taken on by the protocol at each step.
