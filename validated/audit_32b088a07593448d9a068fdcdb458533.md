### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` (or `shopify-shop-domain`) header as the identity of the shop the webhook belongs to when constructing `WebhookMetadata` for the host app's handler. Because the signed bytes and the "shop identity" field are decoupled, the shop attribute an app relies on to select tenant context is not bound by the same authentication check that verifies the payload came from Shopify.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against that signable string, using the app-wide `Context.api_secret_key` (the same secret is used for every shop installed on this app, not a per-shop secret): [2](#0-1) 

`Registry.process` performs exactly this body-only HMAC check, then immediately reads `request.shop` — sourced straight from the unauthenticated `shop-domain` header — and hands it to the app's handler as trusted tenant identity: [3](#0-2) 

`Request#shop` itself is a plain header read with no cryptographic binding to the body or the HMAC: [4](#0-3) 

The binding that should hold is: `hmac_valid(raw_body, secret) == true` should imply `shop_header == shop_that_secret/body_actually_belongs_to`. In this design that equality does not hold — `shop` is a field "acted on but not covered by the HMAC". Any request whose `raw_body` and `hmac-sha256` header pair is valid for the app's shared secret will pass validation regardless of what `shop-domain` header accompanies it, because the shop is never part of `to_signable_string`.

### Impact Explanation
An attacker who controls one shop installed on a multi-tenant app can obtain a legitimate, correctly-HMAC-signed webhook body for their own shop (e.g., by triggering an `orders/create` event in their own store) and then replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will validate the HMAC successfully (it never looked at the shop header) and will invoke the app's registered handler with `WebhookMetadata.shop` set to the victim's shop domain alongside the attacker's own body content. Any host application that uses `data.shop` to look up the tenant/session for processing that webhook body (the documented and expected usage pattern, per `docs/usage/webhooks.md`) will process attacker-controlled data under a different tenant's identity — a cross-tenant confusion/injection primitive reachable purely from spoofed HTTP headers, with no credentials required beyond having any account able to generate one legitimate webhook.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint by design and headers are fully attacker-controlled in the request the app receives; only the body and `hmac-sha256` header are cryptographically checked. Any existing shop (including one the attacker controls) can generate legitimately-signed webhook traffic and then replay it with a modified `shop-domain` header, which is a low-effort, repeatable action.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) in the HMAC-signed material, or otherwise verify that the `shop-domain` header used to route the callback matches metadata that Shopify cryptographically vouches for (e.g., cross-check against the API version/topic-specific webhook subscription created for that exact shop, or use per-shop shared secrets where available). At minimum, document explicitly that `request.shop` is unauthenticated and must not be trusted for tenant selection without additional verification (e.g., confirming it matches an installed/active session for that shop).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both webhook subscriptions registered to the same handler/endpoint.
2. Attacker triggers an event (e.g. updates an order) on `attacker-shop.myshopify.com`, capturing the resulting webhook POST: `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>`.
3. Attacker resends this exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC only from `raw_body`, matches the forwarded `hmac-sha256`, and returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds and calls `handler.handle(data: WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...))`, delivering attacker-controlled body content tagged as belonging to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
