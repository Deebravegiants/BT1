### Title
Webhook `shop` Domain Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` domain used to identify the tenant for a webhook event is read from an unauthenticated header. Any party that can obtain one validly-signed webhook body (e.g. by installing the app on their own store) can replay that exact body to the app's webhook endpoint with a forged `x-shopify-shop-domain`/`shopify-shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as valid and pass the attacker-chosen `shop` value straight to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` simply reads the `shop-domain` header without any cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string` (i.e., the raw body), never incorporating the `shop` header: [3](#0-2) 

`Registry.process` performs only this body-bound HMAC check, then immediately trusts `request.shop` and forwards it, unauthenticated, to the registered handler as the tenant identifier: [4](#0-3) 

The documented handler contract explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and is safe to use for shop-scoped processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing that this field is treated as authenticated tenant context even though it is never covered by the HMAC: [5](#0-4) 

Because the same `api_secret_key` is shared across all shops that install a given app, and the signature covers only the body, an attacker who legitimately installs the app on a shop they control receives genuinely-signed webhook bodies for events they can trigger (e.g. creating an order with attacker-chosen line items/customer data in their own store). They can then replay that exact `raw_body` (with its still-valid HMAC) to the app's webhook callback URL while substituting the `shop-domain` header for a victim shop's domain. `Registry.process` will validate the HMAC successfully (it never checked the header) and hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
This breaks the identity binding `authenticated_shop == shop_used_for_tenant_scoping`: the HMAC only proves "this body was produced by Shopify (or someone who received a signed webhook)", not "this body pertains to this shop." Any app that uses `data.shop` (as documented) to select which merchant's records to create/update/enqueue work for is exposed to cross-tenant data injection/corruption — an attacker-controlled shop can inject fabricated webhook events attributed to any other shop.

### Likelihood Explanation
Exploitability requires only that the attacker (or accomplice) be able to install the target app on a shop they control (trivial for a public app) and be able to send arbitrary HTTP requests to the app's public webhook endpoint (which is inherently internet-reachable). No access token, `client_secret`, or privileged account is required — only the ability to replay an HTTP request with a modified header, which is well within an "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unauthenticated header for tenant scoping:
- Cross-check the `shop` header against the recipient/registration record for the specific webhook subscription (Shopify's webhook IDs are shop-specific) rather than trusting the header value verbatim, or
- Document loudly and enforce in the gem that `data.shop` must never be used as the sole tenant-scoping key without correlating it against a known, previously-registered shop/session record, and
- Where feasible, validate that the `topic`/`webhook_id` combination is one that was actually registered for the claimed `shop`.

### Proof of Concept
1. Attacker registers/installs the vulnerable app on their own store `attacker.myshopify.com` and subscribes to `orders/create`.
2. Attacker creates an order in their store, causing Shopify to POST a genuinely HMAC-signed webhook body `B` (signed with the app's shared `api_secret_key`) to the app's callback URL, with header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same callback URL, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (body `B` and its HMAC header are left untouched).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes the HMAC over `B` and it still matches, since the header was never part of the signed content (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data under the victim's tenant identity.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
