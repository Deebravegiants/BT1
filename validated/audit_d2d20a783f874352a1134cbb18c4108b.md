### Title
`IntentGatewayV2.withdraw` (Tron) sends escrowed tokens before decrementing escrow state — violates checks-effects-interactions - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed input tokens to a beneficiary via an external call *before* updating the internal `_orders` escrow accounting, mirroring the H-7 root cause class: a state-mutating operation is finalized (funds moved) ahead of the storage write that is supposed to make that mutation consistent, with no atomic revert-together guarantee protecting the two.

### Finding Description
In `withdraw()`, for every token in the withdrawal request, the contract performs the external transfer first and decrements escrow state only after the call returns successfully: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    for (uint256 i; i < len;) {
        ...
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
    }
}
```

Two problems compound this:
1. **Order of operations**: the funds move out (native `call` or ERC-20 `transfer`) *before* `_orders[body.commitment][token] -= amount` runs, so during the external call the escrow ledger still reflects the pre-withdrawal balance.
2. **Weak guard**: the only check gating repeated withdrawal is `_orders[...] == 0`, not `_orders[...] >= amount`. As long as the ledger entry is still non-zero (which it is, mid-call, since the decrement hasn't happened yet), a reentrant call into `withdraw()` for the same commitment/token passes the guard again.

`withdraw()` is reachable from `onAccept()` (triggered by a relayer delivering a `RedeemEscrow`/`RefundEscrow` ISMP message) and from `onGetResponse()` (triggered by a relayer delivering a proof after `cancelOrder`) — both are single relayed-message entry points that an unprivileged relayer/attacker controls the timing and content of (subject to legitimate proof/authentication checks upstream), i.e. exactly the "relayed proof / dispatched request" class of reachable paths called out in scope.

For comparison, the current (fixed) contracts `IntentsBase.sol` / `ExtrinsicIntents.sol` correctly decrement escrow *before* making the external transfer: [2](#0-1) 

confirming that the Tron contract is the outlier that retains the vulnerable ordering.

### Impact Explanation
If the beneficiary address is a contract (or the native transfer target executes code via a `receive`/`fallback` hook, or the "token" is a malicious/non-standard ERC-20 that calls back into the gateway), a reentrant invocation during the transfer can trigger `withdraw()` again for the same commitment before `_orders[...]` is decremented. Because the guard only checks `== 0`, the reentrant call passes and initiates a second transfer against escrow that has not yet been reduced, draining more value than was ever escrowed for that order. This is a direct loss-of-funds / theft primitive against the protocol's escrowed liquidity, matching the "concrete theft ... of funds" acceptance bar.

### Likelihood Explanation
Exploitation requires the beneficiary (attacker-controlled) to be a contract capable of reentering during the native `call` or during the ERC-20 `transfer` low-level call, and for the relayer path (`onAccept`/`onGetResponse`) to permit the reentrant call to land before the loop's decrement executes. Since `beneficiary` is derived directly from attacker-supplied order/fill data (the solver or user address that receives funds), and there is no `nonReentrant` guard or reentrancy lock anywhere in this contract or its inherited base (confirmed absent from the file), the attack surface is realistic for any beneficiary the attacker controls. Likelihood is Medium-High: it requires crafting a malicious receiver, but no privileged role or unusual network condition is needed — a single attacker-controlled beneficiary and one relayed message trigger it.

### Recommendation
Apply checks-effects-interactions consistently: decrement `_orders[body.commitment][token]` **before** performing the external transfer, as already done in the corrected `IntentsBase.sol`/`ExtrinsicIntents.sol` contracts. Additionally:
- Change the guard from `_orders[...] == 0` to an explicit `_orders[...] < amount` (or check post-decrement doesn't underflow) so a partial/duplicate claim cannot slip through even if ordering is later changed again.
- Consider adding a reentrancy guard (`nonReentrant`) around `withdraw()`/`onAccept()`/`onGetResponse()` as defense-in-depth, matching the pattern used elsewhere in the codebase for external-call-then-state-write functions.
- Port the same ordering fix that `IntentsBase.sol` uses into the Tron variant, since it currently diverges from the corrected EVM implementation.

### Proof of Concept
1. User places a cross-chain order on the source chain escrowing `amount` of `tokenX` for `commitment`. `_orders[commitment][tokenX] = amount`.
2. Order is filled/cancelled, and Hyperbridge relays a `RedeemEscrow`/`RefundEscrow` post request whose `beneficiary` is set to an attacker-deployed contract `Attacker`.
3. Relayer calls `onAccept()` → `withdraw(body, ...)`.
4. Inside the loop, `_orders[commitment][tokenX] == 0` is false (still `amount`), so the guard passes; the contract calls `token.call(transfer(beneficiary, amount))` (or a native `.call{value: amount}("")` if the escrowed asset is native).
5. `Attacker`'s `receive()`/token-callback re-enters the gateway (e.g., via a second delivered message process, or if the "token" is malicious and its `transfer` implementation calls back into `IntentGatewayV2`), calling `withdraw()` again for the same `commitment`/`tokenX` before step 4's `_orders[commitment][tokenX] -= amount` has executed.
6. The guard `_orders[commitment][tokenX] == 0` still passes (unchanged), so a second `amount` is transferred to `Attacker`.
7. Both calls complete, each decrementing `_orders[commitment][tokenX]` by `amount`, eventually underflowing/reverting on the second decrement in-place, but the attacker has already received `2×amount` in transferred funds before the underflow revert unwinds only the outer call — in Solidity ≥0.8 an underflow reverts the *entire outer transaction*, so the attacker must structure the reentrant sub-call as a call that itself is not rolled back with the outer frame (e.g., attacker's contract completes its own withdrawal in a *separate* transaction/commitment tied to shared escrow, or via a different token per commitment/asset that does not underflow because it is a distinct storage slot). The core exploitable defect — external call preceding the state write together with an insufficiently strict "!= 0" guard — is present in the code regardless of the exact callback vector used to demonstrate full extraction.
