### Title
Attacker-controlled route payload can invoke a rogue pool that spends unrelated caller wallet assets - (File: contracts/swap-aggregator/src/program.rs)

### Summary

A swap route's `assets` registry supplies the destination `pool` address for every instruction, and the router invokes that address without an allowlist. A malicious pool can therefore execute arbitrary contract calls during a caller-authorized `execute_strategy` or controller strategy call. Because Soroban records those calls beneath the caller's authorization tree, a wallet token transfer initiated by the rogue pool executes when the caller signs the simulated tree. This can steal assets entirely unrelated to the tokens being swapped.

### Finding Description

`execute_strategy` decodes the caller-provided `swap_xdr` into a `StrategyPayload` and passes it to `execute::run`. [1](#0-0)  The program format defines each swap instruction's `idx_a` field as the pool address index, while validation only checks that the index is within `assets`; it does not bind the address to a known venue deployment. [2](#0-1) [3](#0-2) 

At execution, the router resolves `hop.pool` directly from `assets[op.idx_a]` and dispatches the venue adapter. [4](#0-3)  For example, the Soroswap adapter invokes `get_reserves` and `swap` on that attacker-selected address. [5](#0-4) [6](#0-5)  `dispatch_hop` measures token balances, but it places no restriction on what other contract calls the selected pool performs. [7](#0-6) 

The controller exposes the same route to users through `swap_collateral`, which authorizes the account owner or delegate and forwards the route to the configured router. [8](#0-7) [9](#0-8)  The harness demonstrates that a rogue hop pool called during `swap_collateral` can invoke `token.transfer(alice, attacker, amount)` for an unrelated wallet token; simulation records that transfer as a child of Alice's `swap_collateral` authorization, and signing that tree makes it execute. [10](#0-9) [11](#0-10) 

### Impact Explanation

A malicious route can steal arbitrary spendable tokens from the caller's wallet, not merely the swap input or the caller's lending collateral. The rogue pool can return a valid measured swap output, allowing the router's output checks and the controller's final risk checks to succeed while an unrelated token transfer is hidden inside the route execution.

This satisfies theft of user funds. In the harness, Alice retains a fair `ETH` supply result while her unrelated wallet-token balance moves to the attacker. [12](#0-11) 

### Likelihood Explanation

The attack is reachable by an unprivileged route author because every hop's pool address is caller-controlled and the venue adapters accept it by address alone. The victim must submit the poisoned route and sign an authorization tree containing the rogue child invocation. That is plausible when a quote service, SDK consumer, or wallet presents the transaction as an ordinary swap without clearly exposing nested authorization children. Enforcing authorization rejects the malicious transfer if the signed tree omits it, but accepts it when simulation-generated authorization includes it. [13](#0-12) [11](#0-10) 

### Recommendation

Bind each route hop to an authenticated venue deployment rather than accepting an arbitrary pool address. Maintain an owner-controlled venue/pool registry, derive the pool from a validated venue identifier, or include a cryptographic/registration check that the invoked contract is the expected implementation. At minimum, prevent route-selected code from inheriting caller authorization for unrelated token transfers; if Soroban cannot scope that safely, execute external pool calls only from addresses registered as trusted venue contracts and make client tooling reject any unexpected authorization child before signing.

### Proof of Concept

1. Deploy a malicious contract with the expected pool methods, such as `get_reserves` and `swap` for a Soroswap hop.
2. Configure the malicious contract with:
   - victim = Alice's address;
   - `wallet_token` = an unrelated token contract;
   - `to` = attacker;
   - `amount` = Alice's wallet-token balance.
3. In its `swap` function, return a plausible output to the router and also call `token::Client::new(env, wallet_token).transfer(alice, attacker, amount)`. The harness implements this rogue pool at `RogueHopPool::swap`. [14](#0-13) 
4. Construct a valid route whose `assets` registry contains the malicious contract as the hop pool, `USDC` as input, and `ETH` as output, then have Alice call:
   - `Controller::swap_collateral(alice, account_id, usdc_hub_asset, 50_000_000_000, eth_hub_asset, route)`, or equivalently `Router::execute_strategy(alice, total_in, route)`.
5. During simulation, Soroban records the unrelated `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's controller authorization. [15](#0-14) 
6. When Alice signs the recorded tree, the malicious transfer executes. The harness ends with Alice's unrelated wallet balance at `0`, the attacker holding `WALLET_BALANCE`, and Alice still receiving the expected swap output. [12](#0-11)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
