### Title
CatFee bandwidth-purchaser client logs its API key and HMAC secret in cleartext at INFO level - ([File: tesseract/messaging/tron/src/lib.rs])

### Summary
`TronClient::new` builds a `CatFeeConfig` containing the plaintext CatFee `api_key` and `api_secret` and immediately logs the whole struct with `{:#?}` at `log::info!` level, because `CatFeeConfig` derives `Debug` and neither field is redacted.

### Finding Description
`CatFeeConfig` is defined with both credential fields exposed to the default `Debug` derive: [1](#0-0) 

When the TRON relayer client initializes its optional CatFee integration (a client used to purchase TRON "bandwidth"/energy before broadcasting transactions), it builds this config from the operator-supplied credentials and logs the entire struct via its `Debug` implementation: [2](#0-1) 

Because `catfee_config` derives `Debug` and `api_key`/`api_secret` are plain `String` fields with no masking, `format!("{:#?}", catfee_config)` renders the raw key and secret into the log line. This is written at `log::info!`, the relayer's default operating log level, so — unlike the RUSTSEC-2026-0275 analog which required `debug`/`trace` logging to be enabled — this leak fires unconditionally on every startup where CatFee credentials are configured, with no elevated log level required. Anyone with read access to the tesseract relayer's stdout/log aggregation (operators' log shipping, monitoring stacks, crash dumps, support bundles) obtains live, replayable CatFee credentials.

By contrast, the codebase's other HTTP integrations (`tesseract/messaging/tron/src/catfee.rs` request/response tracing, `tesseract/messaging/tron/src/tx.rs::post_json`, `tesseract/messaging/tron/src/api.rs::TronApi`) are careful to log only non-secret fields (URLs, order IDs, statuses) and never the `CF-ACCESS-SIGN`/`CF-ACCESS-KEY` header values or the TRON-PRO-API-KEY — confirming the `lib.rs` config dump is the one path where secret material leaks.

### Impact Explanation
The leaked `api_key`/`api_secret` pair lets anyone reading relayer logs forge valid `CF-ACCESS-SIGN` HMAC signatures and impersonate the relayer's CatFee account for the lifetime of that credential (until manually rotated). An attacker can drain the relayer operator's CatFee balance by placing energy/bandwidth purchase orders under the operator's account, or disrupt the relayer's ability to purchase TRON energy needed to submit `handlePostRequests`/`handleGetResponses` transactions on TRON, degrading message delivery on that route. This is a real (not hypothetical) credential-exposure impact classed Medium under the same CWE-532 rationale as the reported advisory, scoped to funds/availability of the TRON relayer's bandwidth-purchasing operations rather than protocol-level fund theft.

### Likelihood Explanation
High likelihood of exposure in practice: this log line fires every time the relayer starts with CatFee credentials configured (a supported, documented feature), at the relayer's default `info` log level — no special debug flag needs to be enabled, unlike the original advisory. Any standard log-collection pipeline, crash report, or support ticket that includes relayer startup logs will contain the plaintext secret.

### Recommendation
Remove the `#[derive(Debug)]` exposure of `api_key`/`api_secret` on `CatFeeConfig` (implement a custom `Debug` that redacts both fields, e.g. `"***"`), and change the startup log line in `tesseract/messaging/tron/src/lib.rs` to log only non-sensitive fields (e.g. `api_base`, `timeout`) instead of the full config struct.

### Proof of Concept
1. Configure a TRON relayer instance with `catfee_api_key` / `catfee_api_secret` set in `TronConfig`.
2. Start the relayer; `TronClient::new` runs and executes `log::info!(target: LOG_TARGET, "CatFee integration enabled: {:#?}", catfee_config);` at `tesseract/messaging/tron/src/lib.rs:257`.
3. Observe the relayer's stdout/log file: the line contains `CatFeeConfig { api_key: "<real key>", api_secret: "<real secret>", ... }` in cleartext.
4. Anyone with read access to that log can now compute valid `CF-ACCESS-SIGN` HMACs (per the documented scheme in `tesseract/messaging/tron/src/catfee.rs:21-29`) and call the CatFee API as the relayer operator. [3](#0-2) [1](#0-0)
