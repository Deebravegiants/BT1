### Title
Webhook `shop` and `topic` are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the HMAC-signed material. `Registry.process` trusts these header-derived fields for dispatch and for the `WebhookMetadata` handed to the app's business logic, even though only the body was cryptographically verified.

### Finding Description
`Request#to_signable_string` is defined as `@raw_body` only [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over that signable string [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight out of caller-controlled headers with no cryptographic binding to the body or to each other [3](#0-2) .

`Registry.process` gates entirely on `Utils::HmacValidator.validate(request)` and, once that passes, constructs `WebhookMetadata` from the unauthenticated `request.topic` and `request.shop` values, dispatching to the host app's handler as if these were verified: [4](#0-3) .

The identity binding that should hold is: `hmac(raw_body, secret) == received_hmac` should imply `(shop, topic, webhook_id)` in the metadata match the values Shopify actually associated with that signed body. In this implementation that binding does not exist — the HMAC only certifies the bytes of the body, not the header-derived attribution fields that the handler uses to decide "which shop/topic this event belongs to."

An unprivileged actor (any developer/merchant who installs the app on their own free development store) legitimately receives real webhook deliveries — valid `(body, hmac)` pairs signed with the app's shared `api_secret_key` — for their own shop's events. Since the same `api_secret_key` is used for every shop/topic combination, and the headers carrying `shop`/`topic` are outside the signed data, that attacker can replay the identical `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` and/or `x-shopify-topic` headers with an arbitrary victim shop domain or a different topic. `HmacValidator.validate` still returns `true` because it only checks the body bytes against the signature, and `Registry.process` will hand the host app a `WebhookMetadata` claiming the forged shop/topic, with `hmac_validated == true` from the host app's perspective.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: a signature that only proves "Shopify signed this body for some shop" is treated by callers as "Shopify signed this body for `request.shop`/`request.topic`." Any host application logic that trusts `WebhookMetadata#shop`/`#topic` after `HmacValidator.validate` succeeds (e.g., to look up a session, write data, or dispatch a topic-specific handler) can be tricked into attributing an attacker-controlled event to a different, victim shop — a cross-tenant confusion enabled purely by an unprivileged internet user who installed the app once on their own store.

### Likelihood Explanation
Likelihood is realistic: installing the target Shopify app on a free development store is unprivileged and requires no special access; capturing one's own legitimately delivered webhook `(body, hmac)` pair is trivial (it's simply logging one's own webhook endpoint traffic), and replaying it with modified headers requires no cryptographic secret at all, since the vulnerable bytes-verified-vs-bytes-parsed gap is structural to `Request`/`HmacValidator`.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string, or otherwise cryptographically bind them to the verified body (e.g., verify them against the response of an authenticated lookup, or require them to be echoed inside the signed payload) before constructing `WebhookMetadata`. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must not be used for authorization decisions without an independent verification step (e.g., cross-checking against a known/allow-listed shop associated with an existing session).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a legitimate webhook, capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays the exact same request to the app's webhook endpoint, keeping `body=B` and `x-shopify-hmac-sha256=H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: <different-topic>`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers successfully (they satisfy only presence checks) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, returning `true` [6](#0-5) .
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with the forged `shop`/`topic`, and the host app processes attacker-supplied data as if it originated from `victim-shop.myshopify.com` [7](#0-6) .

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
