### Title
Webhook tenant (`shop`) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shop`, `topic`, `webhook_id`, and `api_version` values that are read from HTTP headers. `Registry.process` validates the HMAC over that signable string only, then builds `WebhookMetadata` — including `shop` — directly from the same unauthenticated headers and hands it to the app's handler. Because Shopify signs webhooks per-app (a single `client_secret`/`api_secret_key` is shared across every shop that installs the app), any shop that legitimately receives one signed webhook can capture the `(raw_body, hmac)` pair and replay it to the app's endpoint with an altered `x-shopify-shop-domain` header, producing a request that passes `Utils::HmacValidator.validate` while being attributed to an arbitrary victim shop.

### Finding Description
The binding that should hold is: `shop authenticated == shop the HMAC computation is bound to`. In this gem it does not:

- `Request#to_signable_string` returns `@raw_body` only: [4](#0-3) 
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all parsed straight from headers, none of which participate in the HMAC: [5](#0-4) 
- `HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, i.e. the body: [6](#0-5) 
- `Registry.process` trusts `request.shop` (header-derived) once the body-only HMAC passes, and forwards it as the `shop` field of `WebhookMetadata` given to the app's handler: [2](#0-1) 
- The gem's own documentation instructs handlers to key subsequent business logic (job enqueueing, session lookup, tenant-scoped work) directly off `data.shop`: [7](#0-6) 

Since the same `api_secret_key` signs webhooks for every shop that has the app installed, an attacker who controls (or briefly installs the app on) their own shop can generate a legitimately-signed webhook body of their choosing (e.g. by triggering `customers/update` with attacker-controlled fields), capture the resulting `(body, x-shopify-hmac-sha256)` pair, and then send a new POST to the app's webhook endpoint with that same body/HMAC but with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` passes the forged `shop` to the handler as if it were an authentic event for the victim tenant.

### Impact Explanation
This breaks the tenant boundary that webhook processing is supposed to enforce: an app relying on this gem's documented `data.shop` value to select the merchant's session, access token, or database row will act on attacker-controlled body data under the wrong tenant's identity — a cross-tenant access/data-injection primitive. This meets the Critical bar of "cross-tenant access" defined in scope, since the attack requires only participation as any shop-app user, not possession of the app's `client_secret` or a stolen access token.

### Likelihood Explanation
Requires only that the attacker have (or briefly obtain) a shop that installs/uses the target app and can trigger at least one webhook delivery whose body they control (many topics allow attacker-influenced content, e.g. customer or order fields). No access to `api_secret_key`, access tokens, or the host app's source is needed — the replay is a pure HTTP-header substitution against the app's public webhook endpoint.

### Recommendation
Include the tenant-identifying and routing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before exposing them via `WebhookMetadata`, so that `HmacValidator.validate` fails if any of these header values are altered relative to what Shopify actually signed for that delivery.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook topic whose body they influence (e.g. updates a customer field mapped into the webhook payload).
2. Shopify delivers the webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, and the attacker-controlled `raw_body`.
3. Attacker records `raw_body` and the HMAC value, then sends a forged POST to the same endpoint, keeping `raw_body`/`x-shopify-hmac-sha256` identical but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which only checks `raw_body` against the HMAC — validation succeeds.
5. The handler receives `WebhookMetadata#shop == "victim-shop.myshopify.com"` together with the attacker's chosen body, and any app logic keyed on `data.shop` (as documented) processes attacker-controlled content under the victim's tenant identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
