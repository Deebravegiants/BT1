### Title
Missing duplicate-authority-index check in BEEFY consensus signature verification allows supermajority threshold bypass - (File: `modules/consensus/beefy/verifier/src/lib.rs`, `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
The Keycloak SAML flaw stems from a verifier that determines what a signature attests to (a full document vs. a sub-element) by inference (position) rather than by cryptographically binding each signature to a distinct, referenced item — letting an attacker satisfy the check without the signature actually covering what the verifier assumes. The BEEFY consensus verifier in Hyperbridge has an analogous binding gap: it counts the number of *signature entries submitted* toward the 2/3+1 supermajority threshold, and separately checks that each submitted `(index, recovered-address)` pair is a member of the authority set — but never checks that the submitted `authority_indices` are distinct. A relayer can submit the same valid authority signature (and its accompanying merkle-index) multiple times to inflate the participation count without there being that many distinct signers.

### Finding Description
In `verify_mmr_update_proof` [1](#0-0) , `signatures_length` is simply `mmr.signed_commitment.signatures.len()` — the raw count of entries in the attacker-supplied `signatures` vector — and this count alone is passed to `check_participation_threshold` against `authority_set.len`. The loop that follows recovers an address per signature entry and pushes `(authority_leaves, authority_indices)` pairs [2](#0-1) , then calls a single merkle multi-proof `verify` over the full `authority_indices` list [3](#0-2) . There is no assertion anywhere in this path that `authority_indices` contains no duplicates. The same pattern exists identically in the Solidity `EcdsaBeefy.verifyMmrUpdateProof`, where `sigLen` (the raw votes-array length) gates `checkParticipationThreshold`, and each `vote.authorityIndex` is pushed into the `MerkleMultiProof.Leaf[]` array without a uniqueness check [4](#0-3) .

Both the Rust light-client verifier (used by `pallet-ismp` consensus clients) and the on-chain EVM `EcdsaBeefy` verifier treat "number of signature entries in the proof" as equivalent to "number of distinct authorities who actually signed," which is the same class of error as Keycloak's XMLSignatureUtil inferring "what is signed" from structural position rather than validating a proper 1:1 binding between each claimed attestation and a unique entity.

### Impact Explanation
If duplicate indices are accepted by the underlying merkle multi-proof verification routine (`rs_merkle`'s `MerkleProof::verify` for the Rust path, `MerkleMultiProof.VerifyProof` for the Solidity path), an attacker controlling fewer than 2/3+1 of the real BEEFY authority set's private keys — e.g. controlling exactly one authority key, or colluding with a minority — could replay that one authority's valid signature/index pair enough times in the `signatures`/`votes` array to make `signatures_length`/`sigLen` cross the supermajority threshold, while the actual number of independent signers remains below quorum. This would let a minority (or single) validator forge acceptance of an arbitrary BEEFY commitment, and thus an arbitrary MMR root / parachain header set, letting the attacker inject forged state commitments into Hyperbridge's trusted consensus state. Any dependent action — request/response delivery via `verify_membership`, non-membership timeouts, or fee/reward claims gated by these state commitments — could then be forged, meeting the "forged message delivery / unsound state commitment" bar.

### Likelihood Explanation
This path is reachable by any relayer submitting a BEEFY consensus update, which is an unprivileged, permissionless action (`submit_proof`/`verify_consensus` entry points accept proofs from any caller). The only barrier to exploitation is whether the underlying merkle multi-proof `verify` implementations (`rs_merkle` in Rust, `MerkleMultiProof.sol` in Solidity) happen to reject duplicate `(index, leaf)` pairs as a side effect of their algorithm (e.g., by requiring sorted, unique k-indices during layer pairing). I was not able to inspect the `rs_merkle` crate source or `MerkleMultiProof.sol` source directly in this codebase to confirm whether duplicate indices are structurally rejected or silently tolerated; this determines whether the gap is merely a missing defense-in-depth check or a directly exploitable bypass.

### Recommendation
Add an explicit uniqueness check on `authority_indices` (Rust) / `vote.authorityIndex` values (Solidity) before computing the participation count and before invoking the merkle multi-proof verification, e.g. deduplicate and use the deduplicated count for `check_participation_threshold`/`checkParticipationThreshold`, and reject the proof outright if duplicates are found. This mirrors the general principle from the Keycloak fix: bind each verification unit to a unique, explicit reference rather than trusting an inferred/aggregate count.

### Proof of Concept
Not executable in this ask-only review — verifying exploitability requires reading the `rs_merkle::MerkleProof::verify` and `MerkleMultiProof.sol` implementations to confirm whether they tolerate duplicate `(index, leaf)` entries in the multi-proof set. I recommend a Devin session construct a unit test that: (1) builds a trusted authority set of N validators, (2) crafts a `MmrProof`/`RelayChainProof` where only 1 real authority signs, but that authority's `(index, signature)` is duplicated ⌈2N/3⌉+1 times in the `signatures`/`votes` array with the same merkle index repeated, and (3) asserts whether `verify_mmr_update_proof`/`verifyMmrUpdateProof` incorrectly returns `Ok`/succeeds.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}
