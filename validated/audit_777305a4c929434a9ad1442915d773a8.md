### Title
Fire-and-forget `passphraseCache.set()` in `Application#unlock`/`changePassphrase` can race with `Application#lock`'s awaited `passphraseCache.clear()`, leaving passphrase persisted after a "locked" state - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`Application#unlock` calls `void this.#passphraseCache.set(opts.passphrase)` without awaiting it, so the write to the passphrase storage continues asynchronously after `unlock()` resolves. If `Application#lock` is invoked immediately afterward, its `await this.#passphraseCache.clear()` can complete and the `locked` state can be emitted before the pending `set()` write lands, causing the passphrase to be re-written into storage after the wallet has reported itself locked.

### Finding Description
`Application#unlock` at [1](#0-0)  fires `this.#passphraseCache.set(opts.passphrase)` with `void`, i.e., fire-and-forget, after already setting `lockedAtom` to `false` and firing the `Unlock` hook. `PassphraseCache#set` itself has an `await` point (`await this.#getTtl()`) before the actual `storage.batchSet(...)` write completes, as seen in [2](#0-1) , meaning the write is not synchronous and can be delayed relative to the caller.

`Application#lock`, in contrast, awaits `this.#wallet.lock()`, sets `lockedAtom` to `true`, and then awaits `this.#passphraseCache.clear()` (`storage.clear()`) before firing the `Lock` hook: [3](#0-2) . There is no mutex, queue, or ordering guarantee between the fire-and-forget `set()` triggered by a prior `unlock()`/`changePassphrase()` call and a subsequently awaited `clear()` triggered by `lock()`. Both `unlock` and `lock` are exposed directly on the SDK's `application` API surface (`applicationApiDefinition`) and reachable over RPC by any caller with access to that RPC surface: [4](#0-3) . `changePassphrase` has the identical fire-and-forget-adjacent risk pattern removed (it awaits `set`), but `unlock` does not: [5](#0-4) .

Concretely: call `unlock({ passphrase })` → `lockedAtom` set to `false`, hooks fired, function returns while `passphraseCache.set(passphrase)` is still pending → immediately call `lock()` → `lockedAtom` set to `true` and `Lock` hook/event emitted, `passphraseCache.clear()` (i.e., `storage.clear()`) executes → the pending `set()`'s `storage.batchSet({ [PASSPHRASE_KEY]: passphrase, ... })` resolves afterward, re-writing `PASSPHRASE_KEY` into storage. Any observer of the `lock` event/`lockedAtom` (UI, downstream consumers) at that point believes the wallet is locked and the passphrase is not cached, but the passphrase is in fact present in storage.

There is no code in either `PassphraseCache` or `Application` that serializes or cancels in-flight cache writes when a lock is requested — `clear()` is just `await this.#storage.clear()`, and nothing tracks/awaits the in-flight promise from the earlier fire-and-forget `set()`.

### Impact Explanation
If the passphrase remains in storage after a reported "locked" state, any code path that reads `passphraseCache.get()` afterward (e.g., `#autoUnlock` on app restart, `restoreFromCurrentPhrase`) will retrieve a live passphrase and silently unlock/decrypt the wallet or expose it for signing, even though the application state and UI show the wallet as locked. This breaks the "locked means locked" invariant and enables unauthorized unlock/signing after what appears to be a user-initiated or environment-triggered lock, i.e., cached-secret persistence beyond the intended lock boundary — matching an "auth bypass / secret persists after lock" class of impact.

### Likelihood Explanation
Exploitation requires the ability to invoke `application.unlock({ passphrase })` immediately followed by `application.lock()` in rapid succession on the same running application instance, both of which are exposed application/SDK API methods. This is a genuine, reachable race in ordinary usage patterns (e.g., an auto-lock triggered by an event handler firing right after an unlock RPC, or a compromised/malicious script that has access to the SDK's exposed application API attempting to unlock-then-immediately-lock to leave the passphrase cached while reporting locked). The precondition is timing-sensitive but deterministic and reproducible under mocked/deferred storage in tests, since the race window is defined purely by pending microtask/promise resolution order, not by external timing jitter (no `setTimeout`/network involved) — making it consistently reproducible in a controlled test harness and plausible, though timing-dependent, in production.

### Recommendation
Await `this.#passphraseCache.set(opts.passphrase)` in `Application#unlock` instead of using `void`, so `unlock()` does not resolve until the passphrase write completes. Additionally, serialize `PassphraseCache` operations (e.g., a simple internal promise chain/mutex around `set`/`clear`/`changeTtl`/`scheduleClear`) so that a `clear()` call issued after a `set()` call always applies after that `set()`'s storage write has completed, guaranteeing "locked" truly clears any passphrase written by a preceding unlock.

### Proof of Concept
Unit/integration test using a deferred mock storage to control resolution order:
1. Create a mock `Storage` where `batchSet` returns a promise that resolves only after an explicit `resolveSet()` is called (simulate a slow write), while `clear` resolves immediately.
2. Instantiate `PassphraseCache` with this mock storage, and `Application` with this `passphraseCache`.
3. Call `await application.unlock({ passphrase: 'secret' })` — since `set()` is fire-and-forget, `unlock()` resolves immediately while the mock `batchSet` promise is still pending.
4. Immediately call `await application.lock()` — this awaits `storage.clear()`, which resolves immediately (before the pending `batchSet`).
5. After `lock()` resolves, call `resolveSet()` to let the deferred `batchSet` promise resolve, then flush microtasks (`await Promise.resolve()` a few times or `await new Promise(setImmediate)`).
6. Assert: `await storage.get(PASSPHRASE_KEY)` is falsy (expected to fail on unpatched code, since `PASSPHRASE_KEY` will be present after the delayed `batchSet` writes it post-`clear()`), demonstrating that `lock()`'s invariant "no passphrase left in storage" is violated by the race with the earlier fire-and-forget `set()`.
