## Title
LDAP Authentication Bypass via Unauthenticated Bind with Empty Password - ([File: core/sessions/ldapauth/ldap.go])

## Summary
`ldapAuthenticator.CreateSession` and `ldapAuthenticator.TestPassword` in `core/sessions/ldapauth/ldap.go` forward the client-supplied password directly into `conn.Bind(searchBaseDN, sr.Password)` / `conn.Bind(searchBaseDN, password)` with no application-level check rejecting an empty password before delegating trust entirely to the upstream LDAP server's response. If the configured LDAP server implements RFC 4513 §5.1.2 unauthenticated-bind semantics (returning success for a non-empty DN with a zero-length password), this code path will treat that success as a valid login and mint a full node session for the target user, including admin accounts.

## Finding Description
`CreateSession` builds `searchBaseDN` from client-controlled, lower-cased, escaped email, then calls `conn.Bind(searchBaseDN, sr.Password)` without checking that `sr.Password` is non-empty: [1](#0-0) 

If the Bind succeeds (`err == nil`), the code proceeds to call `FindUser`, and on success builds a session and inserts it into `ldap_sessions` with the resolved role, without any further password verification: [2](#0-1) 

The identical unguarded pattern exists in `TestPassword`, reachable via the authenticated password-change/API-token flows: [3](#0-2) 

`TestPassword` is invoked from `UserController.NewAPIToken` and `UserController.DeleteAPIToken` in `core/web/user_controller.go`: [4](#0-3) [5](#0-4) 

There is no code anywhere in `ldap.go` (confirmed via full-repo grep for `sr.Password`, `password ==`, and length checks) that rejects an empty password before it reaches `conn.Bind`. This matches the claim precisely.

However, the actual exploitability of this issue is **entirely contingent on the behavior of a third-party component the node operator configures and controls**: the upstream LDAP server. I was unable to verify, from within this repository, whether the vendored `go-ldap/ldap/v3` client's `Bind` function performs any client-side normalization (e.g., some LDAP client libraries special-case an empty password as an error before ever forming a request), and I could not inspect the vendored library source in this environment. Regardless, the deciding factor is the LDAP server's own bind policy: RFC 4513 defines unauthenticated bind as the standards-compliant behavior for empty-password simple binds, but many production directory deployments (Active Directory by default, and modern OpenLDAP with `disallow bind_anon` set) reject or restrict this. This is a server-side configuration/hardening matter, not a purely code-level vulnerability in the Chainlink node.

## Impact Explanation
If realized against a misconfigured or non-hardened LDAP directory, this would be a severe authentication bypass — full session issuance for any known user email, including admins, via `POST` to the sessions endpoint with an empty password. This maps to the in-scope "node API authentication or role bypass" impact category.

## Likelihood Explanation
The likelihood is fundamentally gated by an external dependency the node operator controls: whether the configured LDAP directory permits RFC 4513 unauthenticated binds. This is a **server-side/operator misconfiguration precondition**, not a flaw purely within Chainlink's code. Modern default LDAP deployments (Active Directory, hardened OpenLDAP) commonly reject or restrict unauthenticated binds. The report itself acknowledges this dependency ("Likelihood depends on the deployed LDAP server's configuration"), which weakens the claim as a definitive, node-code-only vulnerability, since defense against server misconfiguration falls into "operator/misconfiguration" territory that is typically excluded from scope. That said, the missing defense-in-depth check (rejecting empty passwords before ever contacting LDAP) is a legitimate, low-cost hardening gap that the code should close regardless of server behavior, since it currently provides zero protection against this class of server misconfiguration.

## Recommendation
Add an explicit rejection of empty/zero-length passwords before calling `conn.Bind` in both `CreateSession` and `TestPassword`:
```go
if sr.Password == "" {
    return "", errors.New("password cannot be empty")
}
```
and similarly in `TestPassword`. This removes any reliance on the upstream LDAP server's own unauthenticated-bind policy.

## Proof of Concept
1. Configure a Chainlink node with LDAP auth pointed at an LDAP server that permits RFC 4513 unauthenticated binds (e.g., default OpenLDAP without `disallow bind_anon`).
2. `POST` to the sessions endpoint with `{"email": "admin@example.com", "password": ""}`.
3. `ldapAuthenticator.CreateSession` calls `conn.Bind(searchBaseDN, "")`; if the LDAP server treats this as an unauthenticated bind and returns success, `FindUser` resolves the role and a session cookie is issued without a valid credential.
4. Confirm via `ldap_sessions` table insertion and successful authenticated API calls with the resulting cookie.

This PoC requires a specific, non-default, and increasingly uncommon server-side misconfiguration to succeed; it is not demonstrable as an unconditional bypass purely from the Chainlink node's code.
