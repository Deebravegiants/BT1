## Analysis

Note: this task description embeds a "scan prompt" instructing me to produce a vulnerability report based only on an unrelated Flatmoney fee-skew bug. I'll treat this as a legitimate request to look for an analogous "check computed against a stale/incomplete state, then used later without re-validation" pattern in `orb-core`, restricted to the allowed categories (signup authorization / identity binding).

The closest structural analog to the Flatmoney bug (a safety check evaluated against a snapshot of state that ignores further changes that occur before the guarded action is actually finalized) is the operator QR-code expiration check in `src/plans/mod.rs`.

### Title
Operator QR-code authorization is validated against a stale timestamp snapshot and never re-checked before signup completion - (File: `src/plans/mod.rs`)

### Summary
`scan_remaining_qr_codes` decides whether a previously-scanned operator QR code is still authorized by comparing `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time` **once**, at the moment `do_signup` begins [1](#0-0) . After that single point-in-time check passes, the `operator_data` (and the authorization/location binding it represents) is carried through the rest of the multi-step signup flow — QR handling, a 3-second UX sleep, biometric capture, the biometric pipeline, and enrollment — without ever re-evaluating the expiration [2](#0-1) . Just like the Flatmoney check that ignored the fee that would still be applied after the skew check, this check ignores all elapsed time that will pass *after* the check but *before* the authorization is actually consumed to bind/enroll the signup.

### Finding Description
`scan_remaining_qr_codes` is called at the very start of `do_signup` [3](#0-2) . If `QrCodes::Both`/`QrCodes::Operator` already carries a prior `operator_data`, the branch tests only `operator_data.timestamp.elapsed() < operator_qr_expiration_time` [4](#0-3) . Once this boolean gate passes, `operator_data` is treated as valid for the remainder of `do_signup`: it's used to build the `DebugReport`, gates `orb_relay_app_id` checks, and ultimately flows into `enroll_user::Plan` for backend enrollment [5](#0-4) .

Between the expiration check and the point where the operator authorization is actually consumed (enrollment), the code performs a fixed 3-second sleep, then `biometric_capture`, `biometric_pipeline`, and fraud-check phases — each of which can take a non-trivial, variable amount of wall-clock time [6](#0-5) . None of these steps re-validate `operator_data.timestamp` against `operator_qr_expiration_time`. Exactly as in the referenced bug class — where `checkSkewMax` used a snapshot of collateral state that didn't account for a fee still to be applied — this code uses a snapshot of elapsed time that doesn't account for the additional time that elapses before the authorization is actually used to bind the signup to the backend/operator.

### Impact Explanation
`operator_qr_expiration_time` exists specifically to bound how long an operator's authorization/location binding remains valid for starting a signup [7](#0-6) . Because the check is performed once and not re-verified before the authorization is actually consumed by enrollment, a signup that legitimately started just under the expiration boundary can complete enrollment meaningfully later than the configured expiration window, binding the completed signup to operator/location data that the system's own policy considers stale. This is a signup-authorization/identity-binding correctness issue: the enrollment call proceeds using operator authorization data whose freshness guarantee no longer holds by the time it's actually used.

### Likelihood Explanation
This requires no attacker action beyond normal signup timing variance — biometric capture and the AI pipeline naturally take a variable, sometimes lengthy amount of time, so the gap between the expiration check and actual enrollment is a normal occurrence rather than an edge case. This mirrors the "Medium" characterization in the source report: the individual overrun may be small in typical cases, but it is systematic (every signup is affected the same way) and the impact is deterministic once a slow capture/pipeline run occurs.

### Recommendation
Re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` immediately before the authorization is consumed (i.e., right before calling `enroll_user::Plan::run`, or at minimum right before backend `signup_post`/`enroll_user` submission), rather than only at entry to `do_signup`. If the check fails at that later point, fail the signup with a distinct reason (e.g. `OperatorAuthorizationExpired`) instead of proceeding with enrollment.

### Proof of Concept
1. Operator QR code is scanned and validated; `operator_data.timestamp` is set to `Instant::now()`.
2. `do_signup` starts; `scan_remaining_qr_codes` checks `operator_data.timestamp.elapsed() < operator_qr_expiration_time` and passes because little time has elapsed [8](#0-7) .
3. Signup proceeds through the 3-second sleep, biometric capture, and biometric pipeline stages, which together can exceed `operator_qr_expiration_time` in slow-capture conditions.
4. `enroll_user::Plan` still runs and submits the enrollment tied to the now-expired `operator_data`, because no expiration check occurs again after step 2 [5](#0-4) .
