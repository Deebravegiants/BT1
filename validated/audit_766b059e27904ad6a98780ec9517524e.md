### Title
`describeWithdrawal` misattributes withdrawal status/txHash across multiple same-token withdrawals in one batch - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves each `WithdrawalIdentifier` by matching the POA API's `withdrawals` array solely on `assetId` (via `nep141:${w.data.near_token_id}`), never consulting `args.index` or the amount/destination address. When a single intent batches two withdrawals of the same PoA token, both `index:0` and `index:1` calls resolve to the same `.find()`-first matching record, so one withdrawal's real status/txHash gets reported for both.

### Finding Description
The broken equality: `(status, txHash)` returned for withdrawal *i* should equal the on-chain outcome of withdrawal *i*, i.e. `describeWithdrawal({index:i}).txHash == onChainOutcome(withdrawalParams[i])`.

`describeWithdrawal` (poa-bridge.ts:313-343) calls `findMatchingWithdrawal` (poa-bridge.ts:418-427), which does:
```
return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
```
This is an `Array.prototype.find`, which always returns the *first* array element satisfying the predicate — irrespective of `args.index`, `args.withdrawalParams.amount`, or `args.withdrawalParams.destinationAddress`. The code even documents this exact limitation in a comment directly above the function (poa-bridge.ts:409-416): "multiple withdrawals of the same token in a single transaction are not supported."

Attacker/triggering input: an ordinary user or integrator submits (or a solver constructs) a single intent whose `createWithdrawalIntents` batches two `nep141:btc.omft.near` withdrawals to two different `destinationAddress`es. `createWithdrawalIdentifiers` (withdrawal-watcher.ts:80-107) assigns `index:0` and `index:1` per bridge route as expected — the index bookkeeping itself is correct. The bug is purely in the POA API response-matching step.

Exploit flow:
1. Two same-token POA withdrawals are batched in one NEAR intent tx.
2. The POA bridge API returns an unsorted `withdrawals` array with two entries for `near_token_id = btc`, one `COMPLETED` (withdrawal 0's real outcome) and one `PENDING` (withdrawal 1, not yet done).
3. `describeWithdrawal({index:0, ...})` calls `findMatchingWithdrawal`, gets the first array element matching `assetId` — which may or may not be entry 0's actual record, since ordering is unspecified/unsorted.
4. `describeWithdrawal({index:1, ...})` calls the same function with the same `assetId`, and — because `.find()` ignores index — returns the exact same matched record as call for index 0.
5. If that shared record is `COMPLETED`, both `describeWithdrawal(0)` and `describeWithdrawal(1)` report the same `status:"completed", txHash` even though withdrawal 1 is still `PENDING` on-chain.

None of the existing guards prevent this: `validateAddress`, `compareAddresses`, `validateWithdrawal`, and `supports()` all operate on withdrawal creation/validation, not on status reporting; `assert` sanity checks in this file only validate fee sign and asset support, not response matching. There is no cross-check between `args.index`/`amount`/`destinationAddress` and the matched withdrawal record.

### Impact Explanation
An integrator using `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises`/`watchWithdrawal` (which all call `bridge.describeWithdrawal` per index, see withdrawal-watcher.ts:20-77) will receive the same `txHash` for two logically distinct withdrawals. This causes the integrator to credit/refund the second destination based on the first destination's completed transfer — a status/hash misreport that leads to double-crediting one destination while the other withdrawal's real completion (and possibly its real, different txHash) is silently dropped or delayed indefinitely. This matches the "High" impact category: a status or hash misreport making an integrator credit or refund twice. It is repeatable on every batch containing ≥2 same-asset PoA withdrawals, for as long as they remain outstanding/pending together in the API response.

### Likelihood Explanation
Preconditions: a single intent batching two (or more) withdrawals of the *same* PoA-bridge asset with different destinations — no special privilege needed, any user or solver constructing a batched intent can trigger this; it requires no misuse of a documented escape hatch. The condition is fully attacker/integrator-reachable through the standard SDK batch withdrawal flow (`sdk.processWithdrawal`/`createWithdrawalIdentifiers` support batching by design, per `docs/design/rfc-batch-withdrawal-granular-control.md`). Feasibility is high: it's a natural usage pattern (e.g., "USDC to Solana + BTC refund" batching two same-chain-token entries), not a contrived edge case.

### Recommendation
`findMatchingWithdrawal` needs to disambiguate same-asset withdrawals within a batch. Per the code's own comment, sort the API's `withdrawals` array and the local withdrawal params by `amount` (since PoA relayer fees are equal for the same token, relative amount ordering should be preserved) and match candidates by `(assetId, sorted-position)` instead of returning the first `assetId` match. Until the POA API supports disambiguation server-side, `describeWithdrawal` should track and exclude already-claimed records per `(tx.hash, assetId)` so distinct indices cannot resolve to the same withdrawal record twice.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
