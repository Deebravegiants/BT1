### Title
Webhook `shop` field is not covered by the HMAC signature, allowing shop-spoofed replay of a legitimately signed webhook - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop identity (`shop-domain` header) is read separately and forwarded, unauthenticated, to the app's webhook handler. This breaks the binding "bytes verified == bytes acted on": the HMAC proves the *body* came from Shopify, but not that the accompanying `shop` value is genuine, so an attacker who can obtain one validly-signed webhook (e.g., by installing the app on their own shop and triggering a webhook) can replay the identical body with a different `shop-domain` header and have it accepted as valid for an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` value used for dispatch, however, comes straight from an HTTP header that is never included in that signable string: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` (which only checks `to_signable_string`, i.e., the body) and then immediately hands `request.shop` to the handler without any further binding check: [4](#0-3) 

`HmacValidator.validate` confirms only that the *signable string* (body) matches the signature — it has no knowledge of, and does not cover, the `shop` header: [5](#0-4) 

The broken identity equality is:
`HMAC-verified-bytes (raw_body) != bytes-acted-on (shop-domain header used to attribute the payload to a tenant)`.

Because `shop` is not part of the signed payload, any attacker who has captured a single valid signed webhook body/HMAC pair (trivially obtainable — an attacker can install the app on their own shop, a normal unprivileged action, and trigger a webhook to get a valid body+HMAC) can resend the exact same body and HMAC while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header value with any victim shop domain. `Registry.process` will still consider the HMAC valid (it never looked at the header) and will call the handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, ...)`.

### Impact Explanation
Any host application relying on this gem's webhook processing to attribute payload data to the correct tenant (`data.shop` in the handler) can be made to process attacker-controlled data as if it originated from a different shop. Depending on how the host stores/looks up per-shop state from that `shop` value (a normal, encouraged use of `WebhookMetadata#shop` per this gem's own webhook handling contract), this enables cross-tenant data confusion/injection using a replayed, otherwise-legitimate payload — meeting the "cross-tenant access" bar, since the tenant boundary (which shop a webhook is attributed to) is broken by an unprivileged user who only needs the ability to install the app on their own store to obtain one signed sample.

### Likelihood Explanation
High feasibility: no secrets are required. An attacker only needs (a) to be able to install/receive one webhook themselves (any developer can install a public/dev app, or trigger a mandatory GDPR webhook), and (b) network access to POST to the app's webhook endpoint with a forged `shop-domain` header and the previously captured body+HMAC. The gem performs no additional binding between the verified bytes and the `shop` header, so the attack surface is exactly at the boundary this gem is responsible for (`Webhooks::Request` / `Webhooks::Registry.process`).

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signable content, or otherwise cryptographically bind them to the verified body (e.g., verify Shopify's HMAC is computed over `shop + raw_body` if Shopify signs that combination, or independently authenticate the `shop-domain` header against a known/expected value per registered webhook subscription before dispatch). At minimum, document/enforce that host applications must not trust `WebhookMetadata#shop` without corroborating it against session/shop records established via OAuth, and consider rejecting webhooks whose `shop` cannot be independently corroborated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it register mandatory/webhooks; the app's endpoint receives a webhook payload `{"id": 1}` with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker captures this raw body + HMAC.
3. Attacker resends the same body/HMAC to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the HMAC: [6](#0-5) 
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...))`, causing the host app to process/attribute the payload to `victim-shop.myshopify.com` even though the request never touched Shopify's systems for that shop.
