### Title
Accrual overflows before the borrow-index cap and permanently freezes a large debt market - (File: common/src/rates/simulate.rs)

### Summary

Medium. The pool accrues debt by first unscaling `borrowed` with the current `borrow_index`, but that multiplication is not bounded before the configured index ceiling is applied. Once a sufficiently large borrowed-share balance and index product exceed the `i128` range, every path that synchronizes the market panics with `MathOverflow`, leaving suppliers unable to withdraw and borrowers or liquidators unable to reduce the debt.

### Finding Description

`accrue_step` computes `borrowed_original` and `supplied_original` through `scaled_to_original`, which is a `Ray::mul` operation, before it calculates utilization or updates the capped borrow index. [1](#0-0)  The conversion delegates directly to fixed-point multiplication, so an overflowing product aborts accrual instead of being clamped or skipped. [2](#0-1) [3](#0-2)  Although `update_borrow_index` later caps the index at `MAX_BORROW_INDEX_RAY`, that cap cannot prevent the earlier unscaled debt-value overflow. [4](#0-3) 

Every pool mutation loads the market through `synced_market`, which invokes `interest::global_sync` before the requested operation. [5](#0-4)  The permissionless controller `update_indexes` path reaches the same accrual logic through `pool_update_indexes_call`, while the pool commits state only after `global_sync` returns. [6](#0-5) [7](#0-6)  Therefore the first panicking accrual leaves `last_timestamp` unchanged, and all subsequent repayment, withdrawal, liquidation, revenue, or synchronization calls hit the same overflow.

### Impact Explanation

The result is permanent freezing of user funds in the affected `(hub_id, asset)` market. Suppliers cannot recover deposited tokens through `withdraw`; borrowers cannot restore solvency through `repay`; and liquidators cannot de-risk or clean up the position because their pool legs synchronize first. The market is not merely temporarily unavailable or fail-closed on a malicious input: its existing cash and claims become unreachable once the stale timestamp advances far enough to make the accrual calculation overflow.

The repository’s deterministic regression test demonstrates the condition with a valid 18-decimal market, one billion supplied whole units, and 98% utilization; after yearly accrual attempts, `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW` while `borrow_index` remains below its cap. [8](#0-7) 

### Likelihood Explanation

An unprivileged caller can invoke `supply` with a large positive amount, invoke `borrow` from a sufficiently collateralized account, and later call `update_indexes` with the target `HubAssetKey`. [9](#0-8) [10](#0-9)  The attacker does not need an admin role, oracle manipulation, malformed input, or a leaked key; ordinary large market balances and elapsed ledger time are sufficient when the configured caps and rate model admit them.

Likelihood is bounded by the very large asset amount and sustained high-utilization accrual needed to cross the `i128` product boundary before the index ceiling. That lowers the likelihood, but the consequence is permanent for all users of the affected market.

### Recommendation

Make accrual saturation total rather than transactional. In particular, compute debt and supply values with a widening or saturating representation before the utilization step, or pre-clamp the index/step when the representable value bound would be crossed. If the intended terminal state is `MAX_BORROW_INDEX_RAY`, detect the overflow and commit that capped index instead of panicking, then continue with zero additional borrower interest where the documented cap semantics require it. Add a regression test proving that `update_indexes`, `repay`, `withdraw`, liquidation, and bad-debt cleanup remain callable after crossing the value ceiling.

### Proof of Concept

The repository already contains the reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`:

1. Create an 18-decimal `BIG18` market using `xlm_curve()` and a collateral market using `col()`. [11](#0-10) [12](#0-11) 
2. Call controller `supply` as Bob with `account_id = 0`, the configured `spoke_id`, and one `[(BIG18, 1_000_000_000 * 10^18)]` entry. [13](#0-12) 
3. Supply sufficient `COL` collateral and call controller `borrow` for `98%` of the `BIG18` principal. [14](#0-13) 
4. Advance ledger time in yearly increments and call `update_indexes(caller, [(hub_id, BIG18)])` until it returns `MathOverflow`. [15](#0-14) 
5. Observe that `borrow_index` is still below `MAX_BORROW_INDEX_RAY`, while both `withdraw` and `repay` subsequently return the same overflow error. [16](#0-15)

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
