### Title
Permissionless theft of any third party's residual ERC20 allowance to Emporium via unrestricted CASE 2 stateless calls - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation.callData` against an attacker-chosen `endpoint` with `msg.sender == Emporium` (CASE 2, the "stateless" branch), blocking only two specific selectors (`callHinkalWallet`, `doSendToRelay`). Nothing constrains the `from` address encoded inside that arbitrary `callData`, so any attacker can make Emporium call `token.transferFrom(victim, emporium, amount)` and sweep any standing ERC20 allowance a third party (or their `HinkalWallet`) previously granted to the Emporium contract, converting it into the attacker's own shielded UTXO.

### Finding Description
The broken equality is **AUTHORITY**: the entity that signs an `EmporiumSignature` (`stack.signerAddress`) should be the same entity whose funds are moved by the operations it authorizes. In practice, `verifyWallet` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:302-349`) only checks that `stack.signerAddress` produced a valid ECDSA signature over the `ops` array — it never checks *whose* assets the `callData` inside those ops actually moves.

In `runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-118`):
```
if (op.invokeWallet && stack.signerAddress != address(0)) {
    (success, err) = IHinkalWallet(stack.signerAddress).callHinkalWallet(...);
} else {
    bytes4 selector = bytes4(op.callData);
    if (selector == callHinkalWallet.selector || selector == doSendToRelay.selector) revert UnauthorizedWalletCall();
    (success, err) = op.endpoint.call{value: op.value}(op.callData);
}
```
CASE 2 (the `else` branch) performs a raw low-level call directly from Emporium's own context, so `msg.sender` seen by `op.endpoint` is `address(Emporium)`. An attacker who is themselves the signer (any EOA can sign its own valid `EmporiumSignature`; note the literal "attacker deploys an IHinkalWallet-compatible contract and gets it validated as `stack.signerAddress`" path in CASE 1 is cryptographically infeasible, since `verifyWallet` requires ECDSA-recovering the signature to exactly `stack.signerAddress`, and an attacker cannot forge a signature that recovers to an arbitrary contract address they deploy) can set `op.invokeWallet = false` and craft `op.endpoint = <ERC20>`, `op.callData = abi.encodeWithSelector(IERC20.transferFrom.selector, victim, address(emporium), amount)`.

If `victim` (or a `HinkalWallet` acting for them) previously granted Emporium a standing/residual ERC20 allowance (a normal, common pattern — e.g., "approve once, reuse many times" for gas efficiency during a prior legitimate Emporium session), the call succeeds because `allowance[victim][emporium] >= amount` and `msg.sender == emporium`. No code path checks that `victim` authorized *this* specific `EmporiumSignature`/`emporiumMessage` — only the attacker's own signature over their own arbitrary bytes is checked.

After the loop, `runAction` computes `balanceChange = balancesAfter[i] - balancesBefore[i]` (`EmporiumUpgradeable.sol:132-144`), which is positive by `amount` since Emporium's balance of that token increased. With the attacker setting `circomData.amountChanges[i] = 0` (they aren't depositing/withdrawing their own funds for this token), the `deltaAmountChanges[i] < 0` adjustment does not fire, so `balanceChange` remains `amount`, and `handleOut` (`EmporiumUpgradeable.sol:162-184`) transfers it to `msg.sender` (Hinkal.sol) and mints a `UTXO` of `amount` for whatever `stealthAddressStructure` the attacker chose. Hinkal.sol's outer balance/utxo equality (`balanceDif == amountChanges[i] + utxoAmount`, `contracts/Hinkal.sol:134-146`) is satisfied trivially since `amountChanges[i] = 0` and `utxoAmount = amount` exactly matches Hinkal.sol's own balance increase. None of `performHinkalChecks`, `verifyProof`, `insertNullifiers`, or the circuit's `inTotal + amountChanges === outTotal` constraint touch the victim's allowance or the semantics of arbitrary `op.callData` — they only prove self-consistency of the attacker's own UTXO set, not authorization over the `from` field of an arbitrary external call.

### Impact Explanation
Critical — direct theft of a third party's funds (any ERC20 allowance standing against the Emporium contract) executed via a call the fund owner never authorized for this specific transaction, converted into the attacker's own shielded balance. This is repeatable against every account/allowance pair with a nonzero residual allowance to Emporium, and against every ERC20 the attacker can find such an allowance for, at the cost of only gas and one attacker-signed proof/signature per sweep.

### Likelihood Explanation
Preconditions: some account (typically a `HinkalWallet` used in a prior legitimate Emporium session, or any EOA) must have a nonzero, unrevoked `allowance[victim][emporium]`, which is publicly readable on-chain via `allowance()`. This is a realistic and common state given approve-once/reuse patterns. The attacker needs no privileged role: they generate their own valid ZK proof for their own UTXOs and sign their own `EmporiumSignature`; the exploit requires no cooperation from the victim, no relay, and no admin role.

### Recommendation
Restrict CASE 2 stateless calls so that any ERC20 `transferFrom`/`transfer`-style call cannot reference an arbitrary `from` address unrelated to the transaction's actual participants (e.g., disallow `transferFrom` entirely in CASE 2, or require that the `from` argument equal `stack.signerAddress`/a value bound into the proof's public inputs and originating strictly from deposits the current prover controls). More generally, do not allow Emporium to make arbitrary calls on behalf of unauthenticated "ops" whose targets/parameters are not cryptographically bound to funds the signer/prover actually owns.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, `HinkalHelper`, a mock ERC20, and a `HinkalWallet` for a `victim` address.
2. As `victim`, execute a normal legitimate Emporium `transact()` (e.g., a swap) whose `EmporiumOperation` includes `token.approve(emporium, type(uint256).max)` via CASE 1 through the victim's real `HinkalWallet`, consuming less than the full allowance, leaving `token.allowance(victim, emporium) > 0`.
3. As `attacker`, build a `CircomData`/proof for the attacker's own (possibly zero-value) UTXO set with `erc20TokenAddresses = [token]`, `amountChanges = [0]`, `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = attackerEOA` (self-signed `EmporiumSignature`, valid deadline/maxFee) and one `EmporiumOperation{ endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transferFrom.selector, victim, emporium, residualAllowance) }`.
4. Call `Hinkal.transact(...)` with the attacker's proof.
5. Assert: `token.allowance(victim, emporium)` decreases by `residualAllowance`, `token.balanceOf(victim)` decreases by `residualAllowance`, and a new commitment/UTXO of `residualAllowance` is inserted into Hinkal's tree under the attacker's `stealthAddressStructure` — proving funds moved from `victim` to `attacker`'s shielded balance without `victim` ever signing or being referenced in the attacker's `EmporiumSignature`/`emporiumMessage`.     function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
