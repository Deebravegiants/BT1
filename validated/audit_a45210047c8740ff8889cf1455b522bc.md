### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant identity despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which signs/verifies only the raw request body [1](#0-0) . The `shop` value that is handed to the app's `WebhookHandler` as the tenant identity is read directly from the `X-Shopify-Shop-Domain` HTTP header and is never included in the signed material [2](#0-1) .

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` using `OpenSSL.secure_compare` [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , and the HMAC itself is taken from the `hmac-sha256` header [4](#0-3) .

This means the cryptographic guarantee only proves "this body was signed by an entity holding `api_secret_key`" — it says nothing about which shop the header claims to be from. `Registry.process` nonetheless trusts `request.shop` (from the header) as the tenant identity and forwards it unmodified into `WebhookMetadata`, which is delivered to the app's handler as authoritative: [5](#0-4) .

Because `api_secret_key` is a single app-wide secret shared by every shop that installs the app, any merchant that installs the app (an unprivileged, low-friction action requiring no special access) can capture a legitimately HMAC-signed webhook body for their *own* store. Since the signature covers only the body, that same `(body, hmac)` pair remains valid if replayed with the `shop-domain` header rewritten to name a different, victim tenant. The equality the gem should be enforcing — `shop-domain header == the shop bound by the HMAC` — is never checked; the header is accepted at face value.

### Impact Explanation
This breaks the tenant-identity binding the gem is responsible for. An app relying on this library's webhook processing to route data/updates per-shop (uninstall handling, order/customer webhooks, data-erasure requests, subscription state, etc.) can be made to attribute attacker-supplied webhook content to an arbitrary victim shop, i.e. cross-tenant access/injection via credential-and-signature reuse across tenants. This matches the "Critical - cross-tenant access" impact category, since the vulnerable check is entirely inside this gem's `Registry.process`/`Request` implementation and does not depend on the host app misusing an documented API — the gem's own webhook verification is incomplete.

### Likelihood Explanation
Likelihood is high for any public multi-tenant app: the attacker only needs to install the app on a store they control (no privileged credentials, no access token, no leaked secret) to obtain a validly signed webhook body/HMAC pair for that body, then can replay the raw HTTP request with a forged `X-Shopify-Shop-Domain` header value to the app's webhook endpoint. No interaction with Shopify's real infrastructure is required after that.

### Recommendation
Bind the shop identity to the signed payload instead of trusting an unsigned header:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signable string used by `Request#to_signable_string`, matching what Shopify actually signs, or
- If Shopify's HMAC scheme covers only the body by design, cross-check the header-derived `shop` against the shop associated with the `Auth::Session`/subscription that this webhook topic was registered for, rejecting the webhook if they don't match.
- At minimum, document and enforce that `Registry.process` callers must independently verify `request.shop` is one of their known/installed shops before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate, unprivileged install action).
2. Shopify sends a real webhook to the app, e.g. `orders/create`, with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over body>`, and a JSON body.
3. Attacker captures this exact `(body, hmac)` pair (it's delivered to their own endpoint/logs since they installed the app).
4. Attacker replays the identical raw body and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` succeeds (body/hmac unchanged) [6](#0-5) ; `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [7](#0-6)  and dispatches it to the app's handler, which processes attacker-supplied webhook content as if it originated from the victim tenant.
