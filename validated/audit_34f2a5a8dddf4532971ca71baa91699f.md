Audit Report

## Title
CORS wildcard origin allowlist bypass via missing subdomain boundary check in `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin` in the Gateway HTTP server strips the `*.` prefix from a wildcard `CORSAllowedOrigins` entry and then checks `strings.HasSuffix(originHost, allowedHost)` with no `.` boundary check. This allows an attacker-controlled domain like `evilethereum.org` to satisfy a `*.ethereum.org` allowlist entry, since `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true` despite `evilethereum.org` not being a subdomain of `ethereum.org`.

## Finding Description
`isAllowedOrigin` parses the incoming `Origin` header and each `CORSAllowedOrigins` entry into scheme/host/port via `splitURL`, matches scheme and port exactly, and for wildcard entries strips the `*.` prefix before calling `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) . This is a pure string suffix comparison with no verification that the character immediately preceding `allowedHost` within `originHost` is a `.`, so any origin host string that merely ends with the allowed suffix (e.g. `evilethereum.org`, `notarealethereum.org`) is incorrectly treated as a valid subdomain match.

`handleRequest` calls `isAllowedOrigin` and, if true, reflects the raw `Origin` header value back as `Access-Control-Allow-Origin`, with no additional validation: [2](#0-1) . The exact-match branch (`originHost == allowedHost`) is correct and unaffected, but it does not mitigate the flawed wildcard branch. The existing test suite covers the case of a host that doesn't end with the allowed suffix at all (`ethereum.remix.org` vs `ethereum.org`) but does not test the boundary-bypass case where the origin host ends with the allowed suffix without a preceding dot.

## Impact Explanation
When an operator enables `CORSEnabled` and configures a wildcard entry such as `*.ethereum.org` intending to trust only genuine subdomains, a page hosted on an unrelated, similarly-suffixed domain (which the attacker can freely register, e.g. `evilethereum.org`) can have its `Origin` reflected into `Access-Control-Allow-Origin`. This lets an untrusted origin make credentialed/cross-origin browser requests to the Gateway HTTP endpoint and read the JSON-RPC-style response, which is a concrete allowlist bypass leading to cross-origin response disclosure — an in-scope impact category (allowlist bypass / cross-user response corruption).

## Likelihood Explanation
The vulnerable code path is directly reachable by any unprivileged remote client via a normal cross-origin browser request against the internet-facing Gateway; the only precondition is that the operator has `CORSEnabled = true` with a wildcard entry in `CORSAllowedOrigins` (a supported, documented configuration, not a misconfiguration outside the feature's intended use), and that the attacker registers/hosts a domain ending in the allowed suffix — a cheap and realistic action requiring no credentials or special network position.

## Recommendation
Require a boundary check when matching wildcard hosts, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
This preserves matches like `remix.ethereum.org` against `*.ethereum.org` while rejecting `evilethereum.org`.

## Proof of Concept
1. Start the Gateway HTTP server with `CORSEnabled = true` and `CORSAllowedOrigins = []string{"https://*.ethereum.org"}`.
2. Send an HTTP request to the Gateway's configured path with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the bypass. This can be added as a unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting the origin `https://evilethereum.org` against `["https://*.ethereum.org"]` incorrectly passes and returns a non-empty `Access-Control-Allow-Origin` header.
