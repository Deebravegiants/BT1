### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let `Hinkal.transact` credit the same `msg.value` to multiple accounting slots, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` computes a per-index balance-difference for every entry in `circomData.erc20TokenAddresses`, adding `msg.value` back into the ETH (`address(0)`) branch of that computation to compensate for the fact that ETH already landed in `address(this).balance` before the function body runs. Neither `Hinkal.sol` nor `HinkalHelper.dimensionsCheck`/`performHinkalChecks` enforces that `erc20TokenAddresses` entries are unique, so an attacker can list `address(0)` twice and have the single `msg.value` counted as backing for two independent `amountChanges` legs, each of which mints its own shielded UTXO.

### Finding Description
The broken equality is: **for a fixed `msg.value`, the sum of ETH-denominated `amountChanges[i]` values validated by the balance equation must not exceed `msg.value` once.** The code lets it happen twice.

In `Hinkal.transact` (contracts/Hinkal.sol): [1](#0-0) 
`oldBalances`/`newBalances` are snapshotted via `getBalancesForArray`, which simply reads `address(this).balance` (or ERC20 balance) once per array index: [2](#0-1) 

For every index `i` where `erc20TokenAddresses[i] == address(0)`: [3](#0-2) 
`balanceDif = newBalances[i] + msg.value - oldBalances[i]`. Because ETH sent with the call is already reflected in `address(this).balance` at the time `oldBalances` is captured (msg.value arrived atomically with the call), and an ETH "deposit" leg in `_internalTransact` does not move any further ETH (it only calls `transferERC20TokenFromOrCheckETH` with `_to == address(this)`, which merely asserts `msg.value == _value` and performs no transfer): [4](#0-3) 
`newBalances[i] == oldBalances[i]`, so `balanceDif == msg.value` for **every** index tagged `address(0)`, regardless of how many such indices exist.

The final per-index check is: [5](#0-4) 
`balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount`. If the attacker sets `erc20TokenAddresses = [address(0), address(0), ...]` (all other legs zero/consistent) with `onChainCreation[i] = false` for both slots (required for internal transactions per `checkOnchainCreation`): [6](#0-5) 
and `amountChanges[i] = amountChanges[k] = msg.value` for both duplicate indices, then:
- `transferERC20TokenFromOrCheckETH` passes for both legs (each independently checks `msg.value == amountChanges[idx]`, and both idx claim the same msg.value).
- The outer balance-equation check passes for both indices, since `balanceDif == msg.value == amountChanges[idx]` holds for each slot independently.

Root cause: (1) no uniqueness constraint on `erc20TokenAddresses` anywhere in `dimensionsCheck`/`performHinkalChecks`/`transact`, and (2) the address(0) `+= msg.value` compensation term in the balance equation is applied once per matching array index rather than once per transaction. `getHashedCalldata`/`formBasicInput` in `CircomDataBuilder.sol` treat `erc20TokenAddresses[i]` as an independent per-slot public input tag with no cross-slot distinctness constraint fed to the verifier, so `verifyProof` does not reject duplicates either — the circuit's `inTotal + amountChanges === outTotal` constraint is evaluated per token slot, and a duplicated token address simply produces two valid slots each individually consistent with the (identical) claimed `amountChanges`.

The attacker's call: `Hinkal.transact(a, b, c, dimensions, circomData)` directly (no relay, no privileged role needed; `HinkalWrapper.prooflessDeposit` is a separate, unrelated code path that is not affected — see below), with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [msg.value, msg.value]`, `onChainCreation = [false, false]`, `externalActionData.externalActionId == 0` (internal transfer), and a locally-generated valid proof for these public inputs (since nothing in the circuit's usage prevents duplicate token slots at the Solidity level, the proof is buildable for any self-consistent set of public signals).

Existing guards checked and why they don't stop this:
- `dimensionsCheck` only checks array lengths against `dimensions.tokenNumber`, never element uniqueness.
- `checkOnchainCreation` only forbids `onChainCreation` for internal transactions; it doesn't touch address uniqueness.
- `performHinkalChecks`/`verifyProof`/`buildVerifierId` validate proof structure and calldata-hash integrity, not token-address distinctness.
- `rootHashExists`, `insertNullifiers`, `nonReentrant` are orthogonal to this issue.
- The slippage `require(balanceDif >= slippageValues[i])` doesn't prevent duplication since both duplicated legs still satisfy their own slippage bound with `balanceDif == msg.value`.

Note that `HinkalWrapper.prooflessDeposit` (contracts/HinkalWrapper.sol) and `Hinkal.prooflessDeposit`'s internal `_calcTokenChangesForProoflessDeposit` correctly **merge** duplicate token entries (summing amounts into a single unique-token bucket) before doing a single balance-before/after check: [7](#0-6) [8](#0-7) 
so the proofless-deposit path is **not** vulnerable to this double-count; the real vulnerability is isolated to `Hinkal.transact`.

### Impact Explanation
An attacker can mint shielded ETH UTXOs whose total claimed value is a multiple of the ETH actually sent with the transaction (2x per duplicate `address(0)` slot, and more with additional duplicates, bounded only by array-length/gas limits), directly minting unbacked shielded value and causing protocol insolvency once withdrawn. This matches the "Critical: minting shielded value without backing (protocol insolvency)" category, is fully repeatable by any unprivileged depositor, and requires no relayer, admin, or victim cooperation.

### Likelihood Explanation
The attacker needs only: (1) the ability to call `Hinkal.transact` directly with `externalActionData.externalActionId == 0` (an internal transaction, allowed for any EOA), (2) the ability to generate a valid Groth16 proof for their own chosen public inputs/circuit dimensions (explicitly listed as within attacker capability in the rules), and (3) ETH to cover `msg.value` once. No special tree state, no privileged role, and no dependency on other users' funds is required. This is a low-cost, deterministic, and repeatable exploit limited only by the attacker's own capital efficiency (each execution mints roughly double the sent ETH in shielded value, redeemable later via ordinary withdrawal flows).

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries in `dimensionsCheck` (or `performHinkalChecks`) so no token address, including `address(0)`, may appear more than once per `transact` call. Alternatively/additionally, compute the `msg.value` compensation term exactly once per transaction (e.g., accumulate it outside the per-index loop and subtract it after use, or track a boolean "ETH slot consumed" flag) rather than adding `msg.value` unconditionally to every index that matches `address(0)`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with a test verifier that accepts arbitrary public inputs matching locally-generated Groth16 proofs (or use the real circuit and generate two proofs/witnesses for `tokenNumber = 2` with `erc20TokenAddresses = [address(0), address(0)]`).
2. Craft `CircomData` with `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `inputNullifiers`/`outCommitments` sized per `dimensions`, `slippageValues = [0, 0]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`.
3. Call `hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
4. Assert (equality check before/after):
   - Before: `address(hinkal).balance` increases by exactly `X` (the `msg.value` sent).
   - After: two on-chain/off-chain UTXO creations are recorded each with `amount == X` for `erc20Address == address(0)` (verify via emitted commitment events / `insertCommitments` state), i.e. total minted shielded ETH value == `2*X` while `address(hinkal).balance` delta == `X`.
   - Assert `2*X > X` (minted value exceeds actual backing), confirming the broken invariant `msg.value backing == exactly one accounting term`.

        address[] calldata erc20Addresses,
        uint256[] calldata amounts

        private
        pure

    {
        uniqueTokens = new TokenWithAmount[](erc20Addresses.length);

            for (uint256 j = 0; j < uniqueCount; j++) {

                    uniqueTokens[j].amount += amounts[i];
                    found = true;
                    break;

                uniqueTokens[uniqueCount] = TokenWithAmount({
                    erc20Address: erc20Addresses[i],
                    amount: amounts[i]
                });
                uniqueCount++;
            }
        }
    }
