### Title
Webhook Shop-Domain / Topic Headers Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw HTTP body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values that are trusted and forwarded to the app's handler come from unsigned HTTP headers. This mirrors the `IpNFT.sol` royalty-vault bug class: a value that the application *acts on* (the shop identity used to route/attribute the webhook) is not part of the data actually covered by the cryptographic check (the HMAC), so the two can disagree.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (i.e., only the body) against the received `hmac` header, then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. the body — never the shop-domain or topic headers: [4](#0-3) 

The equality the application implicitly relies on is:
`shop header used to attribute/route the webhook == shop that produced the HMAC-signed body`

But the HMAC only proves: `HMAC(secret, raw_body) == received_hmac`. It proves nothing about which shop or topic header accompanied that body. Since `api_secret_key` is the same for every shop that has installed a given app (it is the app's secret, not a per-shop secret), any legitimate installation can obtain a body+HMAC pair that is valid under the shared secret, then resend that exact body with a different `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `Request.new` and `Registry.process` accept this combination as fully valid and pass the attacker-chosen `shop`/`topic` value straight to the app's webhook handler.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to attribute webhook events to the correct tenant. An attacker who controls (or has installed the app on) any shop can:
1. Trigger/observe a legitimate webhook delivery for their own shop (a valid `raw_body` + `hmac` pair, signed with the app's shared `api_secret_key`).
2. Replay that same body to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or a different `x-shopify-topic`).
3. `Registry.process` will validate successfully (HMAC only checks the body) and invoke the handler with `shop: <victim shop>`, causing the host application to process/attribute data as belonging to the victim tenant.

Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the victim's stored access token/session, updating victim-scoped records, triggering victim-scoped side effects), this enables cross-tenant data confusion/access — satisfying the Critical "cross-tenant access" impact bar, since the header that determines which tenant's session/credentials get used downstream is unauthenticated relative to the cryptographic check that gates processing.

### Likelihood Explanation
Requires only an app installation the attacker controls (unprivileged internet user relative to other tenants) to harvest one valid signed body, and then a single crafted HTTP POST with a spoofed header to the app's public webhook endpoint — no access to `api_secret_key`, access tokens, or other privileged material is needed. This is a realistic, low-effort exploit path purely through this gem's own webhook-verification logic (`Request`/`Registry`/`HmacValidator`), not merely a host-application misuse.

### Recommendation
Bind the shop (and ideally the topic) into the value that is actually verified, rather than only the raw body:
- Have `Registry.process` cross-check `request.shop` against the shop encoded/derivable from the payload body itself where Shopify includes it (many webhook payloads include shop-level identifiers), or
- Require host applications to independently verify that `request.shop` matches an actively installed/known shop with a valid session before trusting `WebhookMetadata#shop`, and document this requirement prominently, or
- At minimum, expose a stricter validation path that binds header-level shop/topic metadata to a per-request signature (e.g., HMAC over `shop|topic|body` instead of `body` alone) so replay-with-different-headers cannot pass validation.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
raw_body = '{"id": 1, "order_number": 123}'

# Step 1: Attacker's own shop legitimately receives this webhook,
# so they capture a genuinely valid HMAC for this exact body.
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)

# Step 2: Attacker replays the SAME body+hmac but swaps the shop-domain header
# to a victim shop the attacker never installed on.
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # <-- attacker-controlled
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes: HMAC only covers raw_body, not the shop-domain header.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...))
```
`Registry.process` will accept this request and invoke the app's registered handler with `shop == "victim-shop.myshopify.com"`, even though the HMAC only ever certified the body, not the shop attribution. [3](#0-2) [5](#0-4)

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
