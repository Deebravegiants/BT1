### Title
Unbounded `borrowed × borrow_index` i128 overflow in accrual permanently freezes a market before the index cap can engage — (File: common/src/rates/simulate.rs)

### Summary
The OpenLDAP report's bug class is a remote, unauthenticated availability failure: a single input triggers an assertion that kills the service. The lending analog is a permanent, unprivileged-triggerable `MathOverflow` panic inside the accrual step (`accrue_step` → `scaled_to_original` → `Ray::mul` → `fp_core::mul_div_half_up`). Every mutating entrypoint runs `interest::global_sync` first, so once `borrowed * borrow_index / RAY` exceeds `i128::MAX`, the market is bricked: `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `update_indexes`, `claim_revenue`, and `recapitalize` all panic on the same multiply — forever, because accrual recomputes the overflowing product on every call and no code path can shrink `borrowed` or `borrow_index` without first running accrual.

### Finding Description
`accrue_step` unscales the market's scaled debt before computing utilization:

```text
// common/src/rates/simulate.rs:60-64
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
```

`scaled_to_original` is `scaled.mul(env, index)` (common/src/rates/scaling.rs:14-16), which is `mul_div_half_up(self, other, RAY)` over raw `i128` (common/src/math/fp.rs:50-52) and panics with `GenericError::MathOverflow` when `borrowed * borrow_index` overflows `i128`.

The borrow index is clamped at `MAX_BORROW_INDEX_RAY` only *after* `old_index.mul(interest_factor)` succeeds (common/src/rates/index.rs:13-18), and `update_supply_index` similarly multiplies `supplied.mul(old_index)` before clamping (common/src/rates/index.rs:34). So the value-domain overflow (`borrowed × index` leaving `i128`) is reached strictly before the index cap becomes protective: at `borrow_index ≈ 1.7e29` (170×), scaled debt only needs to be `≈ i128::MAX / 170 ≈ 1e36` raw — i.e. ~`1e9` tokens of an 18-decimal asset — for the multiply to trap.

The panic is stateful, not transactional: `global_sync` (contracts/pool/src/interest.rs:20-33) runs at the head of every market mutation, so the same `MathOverflow` recurs on every subsequent call. `repay` — the only operation that could shrink `borrowed` — accrues first and dies in the same place. `MAX_COMPOUND_DELTA_MS` chunking doesn't help because the failure is in the step's unscaling of the *existing* debt, not in factor computation. The in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: `update_indexes`, `withdraw`, and `repay` all fail with `MATH_OVERFLOW` and `borrow_index < MAX_BORROW_INDEX_RAY` at the freeze point (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-360).

### Impact Explanation
Permanent freezing of funds. All supplier deposits and outstanding debt on the market become unreachable: no withdraw, no repay, no liquidate, no `clean_bad_debt`, no `recapitalize` (which itself runs the pool's accrue-first flow for the market it touches). Controller-side verbs that load the market (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `flash_position`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `claim_revenue`) inherit the freeze because the pool accrues on entry. Unlike a fail-closed DoS, this is an arithmetic trap on a value the attacker influenced (`borrowed`), not a parameter or permission gate.

### Likelihood Explanation
Requires a high-decimals market (the cliff is `~1e9` whole tokens at 18 decimals, more at lower decimals), caps lifted enough for a single whale to supply and borrow at near-max utilization, and sustained high borrow rate long enough for the index to reach ~170× (the test's XLM steep curve reaches it in a few years; ~40-year bound). An attacker can accelerate it by holding the borrow themselves at high utilization — they don't need honest borrower demand. Once triggered it is irreversible. Capital cost is very high, so likelihood is moderate-low, but the impact class (permanent freeze of all funds in a market) is the worst availability outcome and there is no admin escape hatch (`update_params` also accrues under the old curve first).

### Recommendation
Saturate rather than panic in the accrual unscaling path. In `accrue_step` (common/src/rates/simulate.rs:60-61) and in `update_supply_index` (common/src/rates/index.rs:34), replace `scaled.mul(index)` with a saturating `mul_div` (the `mul_div_floor_saturating`/`mul_div_ceil` family already used elsewhere), so that `borrowed_original`/`total_supplied_value` clamp to `i128::MAX` instead of trapping. Equivalently, enforce the borrow-index cap *before* the pre-clamp multiply in `update_borrow_index`, and gate `supplied × index` the same way. Additionally consider an explicit max-scaled-value bound at mint time (`calculate_scaled_borrow`/`calculate_scaled_supply`) so `scaled × MAX_INDEX` can never leave `i128`, making the freeze structurally unreachable rather than rate-dependent.

### Proof of Concept
The repository already contains an executable PoC: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360).

1. Create a market on an 18-decimal asset with the steep XLM rate curve and caps lifted.
2. Attacker supplies `1e9 × 10^18` base units, supplies collateral on a second market, and borrows `0.98` of the debt market at 98% utilization — all via unprivileged `supply`/`borrow`.
3. Advance ledger time; each `update_indexes` call compounds the index. Within the test horizon the index reaches ~170× before `MAX_BORROW_INDEX_RAY` engages.
4. The next `update_indexes` (or any mutation) panics with `MathOverflow` inside `scaled_to_original`. Thereafter `withdraw` and `repay` — including the attacker's own — permanently fail with the same error. All funds in the market are frozen. pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
```rust
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
