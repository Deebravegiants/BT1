### Title
Sequential `checked_sub` of independently-rounded PnL quantities in `process_withdraw`/`process_withdrawpnl` can underflow and permanently brick withdrawal/PnL accounting - ([File: program/src/processor.rs])

### Summary
`process_withdraw` and `process_withdrawpnl` update `target_orders.calc_pnl_x` / `calc_pnl_y` by chaining two separate `checked_sub(...).unwrap()` calls on values that come from two independently-rounded computations: the amount actually withdrawn/removed from the pool (rounded via `normalize_decimal_v2`/floor division) and `delta_x`/`delta_y` (rounded inside `calc_take_pnl` via a *different* rounding path — floor of `diff_x * pnl_numerator / pnl_denominator` computed directly in normalized-decimal space, versus the native-unit `pc_pnl_amount` that is actually subtracted from `total_pc_without_take_pnl` via a round-trip through `restore_decimal`). This is the exact bug class described in the Tokemak `LMPVault.updateDebtReporting` report: subtracting two values derived from different, independently-rounded computations before validating that the subtrahends don't exceed the minuend, causing an arithmetic underflow.

### Finding Description
In `Processor::process_withdraw` (`program/src/processor.rs:1719-1839`), the flow is:
1. `x1`/`y1` = `normalize_decimal_v2(total_pc_without_take_pnl, ...)` computed **before** any PnL is taken. [1](#0-0) 
2. `calc_take_pnl` is called, which reduces `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (native units) by `pc_pnl_amount`/`coin_pnl_amount`, and separately returns `delta_x`/`delta_y` (normalized-decimal units) computed via an *independent* rounding path. [2](#0-1)  Inside `calc_take_pnl`, `delta_x` is `diff_x * pnl_numerator / pnl_denominator` (floor, normalized units), while the amount actually deducted from the pool, `pc_pnl_amount`, is computed by first restoring `diff_x` to native decimals (`restore_decimal`, itself a floor division) and then applying the same fraction again — a second, independent rounding step. [3](#0-2) 
3. `coin_amount`/`pc_amount` (the tokens actually paid out to the withdrawing LP) are computed from the *already-PnL-reduced* `total_pc_without_take_pnl` using `RoundDirection::Floor`. [4](#0-3) 
4. Finally, `target_orders.calc_pnl_x`/`calc_pnl_y` are updated by subtracting from the **original** `x1`/`y1` first the normalized `pc_amount`/`coin_amount`, and then `delta_x`/`delta_y` — via two chained `checked_sub(...).unwrap()` calls: [5](#0-4) 

```
target_orders.calc_pnl_x = x1
    .checked_sub(Calculator::normalize_decimal_v2(pc_amount, ...))
    .unwrap()
    .checked_sub(U128::from(delta_x))
    .unwrap()
    .as_u128();
```

Because `delta_x` (subtrahend #2) is computed via a decimal round-trip through `restore_decimal`/re-derivation distinct from the direct normalized-space computation used to bound `x1`, and because `pc_amount` (subtrahend #1) is derived from a post-PnL, floor-rounded pool balance rather than directly from `x1`, the two subtrahends are not guaranteed to sum to at most `x1`. Repeated small withdrawals against a pool whose native/sys decimal ratio introduces truncation (e.g., `pc_decimals` or `coin_decimals` not matching `sys_decimal_value`'s precision) can cause `normalize_decimal_v2(pc_amount) + delta_x > x1`, triggering an underflow panic in the `checked_sub(...).unwrap()` chain. The identical pattern also appears in `process_deposit`'s `calc_pnl_x`/`calc_pnl_y` update, which chains an add then a subtract. [6](#0-5) 

This mirrors the root cause in the referenced Tokemak report: `debt = totalDebt - prevNTotalDebt + afterNTotalDebt` underflowing because the two operands are each independently rounded (one rounds up on burn, the other rounds down on the "previous" tracked value), and subtraction is performed before any bound-check or reordering that would prevent it.

### Impact Explanation
An `.unwrap()` panic on `checked_sub` aborts the transaction, so no direct fund theft occurs from this specific panic in isolation. However, because `target_orders.calc_pnl_x`/`calc_pnl_y` are **persistent on-chain state** that every subsequent `deposit`/`withdraw`/`withdrawpnl` call depends on (via `calc_take_pnl`'s invariant checks against `target.calc_pnl_x`/`calc_pnl_y`), if the pool state ever reaches a combination where this underflow is unavoidable (i.e., any valid withdrawal amount against the current pool/PnL state triggers the underflow), withdrawals for that AMM become permanently unable to succeed — a freezing of LP funds, analogous to the described impact "the whole vault asset is locked and withdrawals won't be successful."

### Likelihood Explanation
Reaching a state where truncation error accumulates enough to cause `normalize_decimal_v2(pc_amount) + delta_x > x1` requires specific decimal-precision/rounding conditions between `pc_decimals`/`coin_decimals` and `sys_decimal_value`, combined with a particular sequence of swaps/deposits/withdrawals that drift `target_orders.calc_pnl_x/y` away from the true pool ratio (similar to how the original PoC needed two rounding-up redemptions to diverge from the rounded-down reference value). This is a real, unprivileged-reachable path (any user can call `withdraw`/`deposit`/swap with attacker-chosen amounts), but I was not able to fully construct a concrete numeric trace within the available exploration to prove the underflow is reachable with realistic decimal configurations (e.g., typical 6/9-decimal SPL tokens) — this would require running the actual rounding arithmetic (`restore_decimal`/`normalize_decimal_v2` with real `pnl_numerator`/`pnl_denominator`, which I could not fully confirm from the indexed code) to find a concrete triggering sequence, similar to how the original report needed specific numeric examples (`100_001`/`1_000_010`/`1_000_011`) to demonstrate feasibility.

### Recommendation
- Avoid chaining independently-rounded subtractions against a value (`x1`/`y1`) that was snapshotted before any of those roundings occurred. Instead, compute the *new* `total_pc_without_take_pnl`/`total_coin_without_take_pnl` directly (already tracked and updated consistently inside `calc_take_pnl` and after the withdrawal debit) and re-derive `calc_pnl_x`/`calc_pnl_y` from the final consistent totals rather than subtracting two separately-rounded deltas from a stale snapshot.
- Where subtraction order matters, reorder computations to add before subtracting (as recommended in the referenced report) or use saturating/checked arithmetic with explicit clamping and a documented invariant proof rather than raw `.unwrap()`.
- Add an explicit invariant check/test asserting `normalize_decimal_v2(pc_amount) + delta_x <= x1` (and the coin/y equivalent) is unconditionally provable given the two independent rounding paths in `calc_take_pnl` (`restore_decimal` round-trip for `pc_pnl_amount` vs. direct fraction for `delta_x`), across the supported decimal ranges.

### Proof of Concept
A full numeric PoC could not be finalized within the available investigation because it requires concretely tracing `restore_decimal`/`normalize_decimal_v2` rounding with real `pnl_numerator`/`pnl_denominator` and `pc_decimals`/`coin_decimals`/`sys_decimal_value` values from `state.rs`, which I was unable to fully retrieve before the tool budget was exhausted. The reachable path is: unprivileged user calls `deposit`/`swap` to establish a PnL-divergent state (`target_orders.calc_pnl_x/y` diverges from actual pool ratio due to floor/ceil rounding in `calc_take_pnl`), then calls `withdraw` with an amount chosen such that `pc_amount`'s normalized value plus `delta_x` exceeds the stale `x1` snapshot, triggering the `checked_sub(...).unwrap()` panic in [7](#0-6) . Constructing exact attacker-chosen amounts to realize this concretely would require a Devin session with terminal access to run the Rust arithmetic against the actual `calc_take_pnl`/`Calculator` implementations and brute-force/fuzz for a triggering decimal combination.
