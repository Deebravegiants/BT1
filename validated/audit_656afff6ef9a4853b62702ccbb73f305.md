### Title
Same-asset batch withdrawals via POA Bridge report the wrong destination tx hash for a given withdrawal index - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`, `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`)

### Summary
When a caller submits a batch of withdrawals that includes two or more entries for the same NEP-141 asset (e.g. two USDC withdrawals to different destination addresses in one intent), `PoaBridge.describeWithdrawal()` and the standalone `waitForWithdrawalCompletion()` helper both resolve the status/tx-hash for a specific withdrawal by matching **only on `assetId`** (`near_token_id`), not by index, amount, or destination address. If the POA API returns multiple withdrawal records for that asset in the same NEAR tx, `findMatchingWithdrawal()` deterministically returns the **first** array entry that matches the asset, regardless of which logical withdrawal (by index/destination) it actually corresponds to.

### Finding Description

and [2](#0-1) 

use `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)`. This is explicitly called out as a known limitation in the comment on both functions: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."

`PoaBridge.describeWithdrawal()` is invoked once per withdrawal index by the SDK's polling orchestration: [3](#0-2) 

The SDK's batch APIs (`sdk.waitForWithdrawalCompletion`, `sdk.createWithdrawalCompletionPromises`, `sdk.processWithdrawal`) explicitly support and document batching multiple `withdrawalParams` entries with guaranteed index correspondence between `withdrawalParams[i]` and the returned/resolved transaction for index `i`: [4](#0-3) [5](#0-4) 

The README's own batch example shows two different withdrawals (`nep141:usdt...` and a different asset) being tracked by index and each promise being routed to a distinct downstream action (`saveUsdc`, `saveBtc`): [6](#0-5) 

Nothing in `WithdrawalParams` prevents a caller from submitting two withdrawals of the **same** `assetId` to two **different** `destinationAddress` values in one batch (e.g. splitting a single NEP-141 balance to two recipients). When this happens, both `describeWithdrawal()` calls (index 0 and index 1) query the same POA `getWithdrawalStatus` response and each independently calls `findMatchingWithdrawal()` with the same `assetId`, which will return the **same first matching record** for both indices, or in the completion-promise polling loop, index 0 could resolve using the transfer hash that actually belongs to index 1's withdrawal (or vice versa), while the correct entry is skipped or misreported as still pending.

This breaks the equality that the caller (an integrator credit/refund system) depends on: `status/txHash reported for withdrawalParams[i]` == `actual on-chain outcome for withdrawalParams[i]`. Instead, the reported destination transaction hash can belong to a different destination address/amount than the one being polled.

### Impact Explanation
This matches the accepted impact category "a status or hash misreport making an integrator credit or refund twice." A concrete consequence: an integrator polling `promises[0]` (destined for address A) can receive the destination tx hash that actually corresponds to the withdrawal to address B (`promises[1]`), and vice versa. If the integrator uses the returned tx hash to mark a specific customer's withdrawal record as completed (a very common pattern shown in the SDK's own README and RFC docs: `promises[0].then(tx => saveUsdc(tx))`), this can cause it to credit/confirm the wrong customer's off-chain record as "delivered," or to falsely conclude a withdrawal is still pending when it actually completed (or the reverse) — because two logically distinct withdrawals are conflated into one status query result. There is no on-chain fund loss, but there is a concrete integrator-facing state-consistency (misreport) impact matching "High."

### Likelihood Explanation
Batching multiple withdrawals of the same asset to different destinations in a single intent is a normal, supported usage pattern of the batch withdrawal API (no validation rejects duplicate `assetId` entries with differing destinations). Any integrator using `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` with such a batch on POA-Bridge-routed assets (nep141 tokens bridged via POA, e.g. BTC/ETH/other POA-supported assets) will hit this deterministically once the underlying withdrawals appear together in the POA API response, and the bug is explicitly acknowledged as an unhandled limitation in the code's own comments, confirming it is reachable and unaddressed rather than purely theoretical.

### Recommendation
Disambiguate `findMatchingWithdrawal()` beyond `assetId` when multiple withdrawals of the same asset exist in one transaction: as the code comment suggests, sort both the withdrawal params list and the POA API's returned `withdrawals` list deterministically (e.g., by amount, since relayer fees are identical per asset) and match by position among same-asset entries, or track a per-asset occurrence counter across the batch so index i's Nth same-asset withdrawal maps only to the API response's Nth same-asset entry. Until POA API provides a native identifier (e.g., a client-supplied withdrawal correlation ID) that can be echoed back and matched exactly, reject/flag batches containing duplicate `assetId` values routed to POA Bridge, or surface an explicit warning/error from `describeWithdrawal`/`waitForWithdrawalCompletion` rather than silently returning a possibly-mismatched result.

### Proof of Concept
1. Caller submits `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdc.token.near", amount: 100n, destinationAddress: "addrA"}, {assetId: "nep141:usdc.token.near", amount: 200n, destinationAddress: "addrB"} ] })`, both routed via `PoaBridge`.
2. NEAR intent settles; POA relayer processes both withdrawals and, at some point, `getWithdrawalStatus` returns two entries with `near_token_id: "usdc.token.near"` — one `COMPLETED` (destined for addrB, `transfer_tx_hash: "0xB"`), one still `PENDING` (destined for addrA).
3. SDK internally calls `describeWithdrawal` for index 0 (addrA) and index 1 (addrB) separately; both invoke `findMatchingWithdrawal(withdrawals, "nep141:usdc.token.near")`, which returns the **same first array element** (say, the `COMPLETED` addrB entry) for both calls.
4. Index 0's promise (which should represent addrA's withdrawal) resolves as `{ hash: "0xB" }` — the transaction hash for addrB's withdrawal — while index 1 may also resolve with the same value or be marked pending depending on ordering, in either case mismatching a specific withdrawal identity to the wrong on-chain outcome.
5. An integrator handling `promises[0].then(tx => markCustomerADelivered(tx))` incorrectly marks customer A's withdrawal as delivered using a transaction hash that actually paid customer B.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
