### Title
Meta-transaction (`DelegateAction`) bundles can be forced to fail by front-running the delegate nonce, wasting relayer gas — (File: `runtime/runtime/src/actions.rs`)

### Summary
NEAR's meta-transaction feature (NEP-366) lets a user sign a `SignedDelegateAction` off-chain and hand it to a relayer, who wraps it in an ordinary transaction and pays gas on the user's behalf. Because the signed payload is public once it leaves the user's hands (sent to the relayer, gossiped, or visible once the relayer's transaction hits the mempool) and any account can act as the "wrapper," anyone can copy the exact same `SignedDelegateAction` bytes into their own transaction and submit it first. This consumes the delegate nonce on the user's access key, so when the legitimate relayer's transaction is later applied, `validate_delegate_action_key` rejects it with `DelegateActionInvalidNonce`, and the relayer's gas is burned for nothing — the same "front-run a one-time-use authorization to force the real submitter's operation to fail" pattern described in the Angstrom `PermitSubmitterHook` report.

### Finding Description
A `SignedDelegateAction` is validated purely by signature and nonce, not by who submits the wrapping transaction: [1](#0-0) 

`apply_delegate_action` only checks the inner signature (`signed_delegate_action.verify()`) and expiry; it never checks the identity of the outer transaction's signer/predecessor beyond requiring `delegate_action.sender_id() == receiver of the wrapping tx`. This means **any** account can wrap and submit a copy of a `SignedDelegateAction` it has observed, as long as it sends it to the correct `sender_id` account.

Nonce validation and consumption happens in `validate_delegate_action_key`: [2](#0-1) 

The nonce is strictly monotonic per `(sender_id, public_key)`: whichever transaction lands first advances it, and any later transaction carrying the *same* `SignedDelegateAction` (same nonce) is rejected with `DelegateActionInvalidNonce`. Because the delegate action is not consumed atomically with submission — anyone can extract the exact same signed bytes off the network and race the honest relayer — an unprivileged actor can front-run to burn the specific nonce before the legitimate relayer's transaction is applied.

The design docs explicitly acknowledge that meta-transaction nonce sharing/relaying creates trust and invalidation issues between relayer and user, but this is framed as an accepted MVP limitation, not defended against maliciously: [3](#0-2) 

This mirrors the reported bug class: an unprivileged third party observes a signed, single-use authorization (an ERC-20 `permit` signature / here, a `SignedDelegateAction`) destined for inclusion in someone else's bundle/transaction, and front-runs it to consume the one-time nonce/signature, forcing the legitimate submitter's transaction to revert/fail after they already paid for inclusion.

### Impact Explanation
The relayer's outer transaction still gets included and gas-charged up to the point of failure (nonce check happens during action application, after the relayer has already paid `SEND` costs and gas purchase), so the relayer suffers real, uncompensated financial loss (wasted NEAR spent on gas) with zero benefit to the user. This is a griefing/DoS vector against relayers offering meta-transaction services, and it can be repeated indefinitely and cheaply by anyone who can observe the pending `SignedDelegateAction` (e.g., in the public mempool, from a public relayer API, or via network gossip), without needing any special privileges or knowledge of any private key.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only observing/copying a publicly-visible `SignedDelegateAction` before the legitimate relayer's transaction is finalized and resubmitting it with a higher gas price or via faster propagation — no cryptographic secrets, validator/node privileges, or special access are needed. Any general-purpose relayer service that accepts `SignedDelegateAction`s from the public (the very use case NEP-366 targets) is exposed once the delegate action becomes visible before inclusion.

### Recommendation
- Bind the acceptance of a `SignedDelegateAction` to a specific authorized relayer (e.g., include an intended-relayer/receiver commitment in the signed payload, or require the relayer's own signature to co-sign it) so a third party cannot resubmit the same payload as their own transaction.
- Alternatively, allow the relayer to detect and skip/replace already-invalidated delegate nonces before submission, and/or make the failure cheap (fail fast pre-charge) rather than burning full send/gas costs when `DelegateActionInvalidNonce` is hit, to reduce the cost of griefing.

### Proof of Concept
1. User `Alice` signs a `DelegateAction` (nonce `N`, `sender_id = alice`) intended for relayer `R`, per the flow in `docs/architecture/how/meta-tx.md`.
2. `R` broadcasts its outer transaction containing `Action::Delegate(signed_delegate_action)` to the network; the transaction (including the embedded `SignedDelegateAction`) is visible in the mempool/gossip before inclusion.
3. Attacker `M` (any unprivileged account) copies the exact `SignedDelegateAction` bytes and constructs its own transaction: `signer_id = M`, `receiver_id = alice`, `actions = [Action::Delegate(signed_delegate_action)]`, and submits it with higher priority so it lands first.
4. On `alice`'s shard, `apply_delegate_action` → `validate_delegate_action_key` accepts `M`'s copy since it only checks signature/nonce (`runtime/runtime/src/actions.rs:437-461`, `558-639`), advancing the access key nonce past `N`.
5. `R`'s original transaction is later applied; `validate_delegate_action_key` now finds `delegate_nonce.nonce() <= current_nonce` and returns `ActionErrorKind::DelegateActionInvalidNonce` (`runtime/runtime/src/actions.rs:632-639`), failing `R`'s meta-transaction after `R` already paid send/purchase gas costs.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
