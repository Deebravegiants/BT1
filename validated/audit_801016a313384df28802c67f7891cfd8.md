I found the relevant analog in `decode_public_key` at [1](#0-0)  — this function decodes a base64-encoded 32-byte string into a `sodiumoxide::box_::PublicKey`, but only validates the byte length, never checking that the key isn't a degenerate value (e.g. all-zero bytes, a known low-order/identity point, or an attacker-controlled weak key). This key is then used unconditionally to encrypt the user's biometric data.

### Title
Missing validation of backend/self-custody public keys allows biometric data encryption with a degenerate key - ([File: src/backend/user_status.rs])

### Summary
`decode_public_key` in `src/backend/user_status.rs` only checks that the decoded payload is exactly 32 bytes; it performs no validation that the value is a well-formed, non-degenerate Curve25519 public key (no all-zero check, no low-order-point check). The resulting `PublicKey` values (`backend_iris_public_key`, `backend_normalized_iris_public_key`, `backend_face_public_key`, `backend_tier2_public_key`, `self_custody_user_public_key`) are attacker/backend-controlled response fields that flow directly into `Credentials` and are used to encrypt iris, face, and normalized-iris biometric tiers in the Personal Custody Package.

### Finding Description
The backend's `/api/v1/user/{id}/status` (or `/api/v2/session/{id}/status`) response supplies `backend_keys.iris.public_key`, `backend_keys.normalized_iris.public_key`, `backend_keys.face.public_key`, `backend_keys.tier2.public_key`, and `authenticated_app_data.self_custody_public_key` as base64 strings [2](#0-1) . Each is passed through `decode_public_key`, which only enforces a 32-byte length [1](#0-0) . This is directly analogous to the reported bug class: incoming arguments (here, cryptographic key material instead of an Ethereum address) are accepted without validating that they are non-degenerate/non-zero values before being trusted as a destination for sensitive operations (here, biometric-data encryption instead of a rewards-receiver address).

These unvalidated keys populate `UserData`/`Credentials` at [3](#0-2)  and are subsequently used in `Package::build` to encrypt the iris, normalized-iris, and face tarballs, as well as tier1/tier2 packages, via the `encrypt(...)` calls: [4](#0-3) . If a public key resolves to the identity element / a known low-order point (a "zero-address" analog for Curve25519 `box_seal` encryption), the resulting ciphertext can be trivially decrypted or is otherwise not confidentiality-protected, without any error being raised anywhere in this path.

### Impact Explanation
If this degenerate-key condition occurs (whether from a compromised/misbehaving backend response, a MITM on the status endpoint, or a backend bug), the orb encrypts sensitive iris/face/normalized-iris biometric tiers with a key that provides no real confidentiality guarantee, resulting in concrete biometric data disclosure risk for the tier0/tier1/tier2 Personal Custody Package uploaded to the backend/S3 [5](#0-4) . This matches the "biometric data disclosure" impact category explicitly accepted by the validation rules.

### Likelihood Explanation
Likelihood is Low-to-Medium: the request is authenticated with `basic_auth(&*ORB_ID, ...)` [6](#0-5) , so a purely external/unprivileged attacker cannot directly supply this response; exploitation requires backend compromise, a bug in backend key generation, or an on-path attacker able to forge the TLS-protected response. This is weaker than the original Aave report's direct-deployment-argument scenario, but it remains an unprivileged-outcome analog (the affected party is the user whose biometrics are being protected) rather than a malicious-operator/hardware-access scenario excluded by the rules.

### Recommendation
Add explicit validation in `decode_public_key` (and/or immediately after decoding) rejecting all-zero keys and other known degenerate/low-order Curve25519 points before they are accepted into `UserData`/`Credentials`, aborting the signup (returning `Ok(None)` or an error) rather than silently proceeding to encrypt biometric data with an unvalidated key.

### Proof of Concept
1. Have the signup-backend status response return a `backend_keys.iris.public_key` (or `self_custody_public_key`) that base64-decodes to 32 zero bytes.
2. `decode_public_key` accepts it because it only checks length [1](#0-0) .
3. This key flows into `Credentials.backend_iris_public_key` and is used in `encrypt(iris_tar, backend_iris_public_key)` in `Package::build` [7](#0-6) , producing ciphertext with no effective confidentiality guarantee, which is then uploaded as part of the signup's tier0/tier1 package.

fn decode_public_key(payload: &str) -> Result<PublicKey> {
    let bytes = BASE64.decode(payload.as_bytes())?;
    let bytes = <[u8; 32]>::try_from(bytes)
        .map_err(|x| eyre!("incompatible public key length: {}", x.len()))?;
    Ok(PublicKey(bytes))
}
