### Title
Webhook HMAC signs only the raw body, not the `shop-domain` header, allowing shop-identity spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all pulled straight from HTTP headers that are never part of the signed content [2](#0-1) . `Registry#process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `request.shop` value [3](#0-2) .

### Finding Description
This is the same class of bug as the referenced report: a value that downstream logic *acts on* (here, `shop`) is not covered by the integrity check that is supposed to bind the whole request together (here, the webhook HMAC). `Utils::HmacValidator.validate` only proves that `@raw_body` bytes were signed with the app's `client_secret`; it says nothing about which shop sent it [4](#0-3) .

Because every shop installing the same app shares the app's single `client_secret`, a valid `(raw_body, hmac)` pair produced by *any* shop's genuine webhook delivery is a valid pair for *every* shop as far as `Utils::HmacValidator.validate` is concerned — the signature check has no shop binding. An attacker who controls one legitimate installation of the app (an "unprivileged internet user" relative to *other* merchants' tenants) can capture a real webhook `raw_body`+`hmac-sha256` header pair generated for their own shop, then replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still passes (it only checked the body bytes), and `Registry#process` builds `WebhookMetadata` using the attacker-supplied `shop` header, so the app's handler processes/stores this data as if it belonged to the victim shop [3](#0-2) .

The breakable identity binding, stated as an equality that the gem fails to enforce:
`shop_that_produced_valid_hmac(raw_body) == shop_header_used_for_dispatch(request)`
This equality is never checked because `shop` is excluded from `to_signable_string`.

### Impact Explanation
This breaks tenant isolation: a caller who is a legitimate (but malicious) merchant of the app can forge webhook deliveries that the host application will attribute to another merchant/tenant, since `shop` is the only tenant identifier passed to the handler and it carries no cryptographic binding to the signed payload. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/write per-shop records), this enables cross-tenant data injection or corruption — matching the "cross-tenant access" Critical impact class.

### Likelihood Explanation
Exploitation requires only: (1) install the app on an attacker-controlled shop (something any developer/merchant can do without special privileges or access to the app's `client_secret`), (2) trigger any webhook topic delivery to capture a legitimate `raw_body` + `X-Shopify-Hmac-Sha256` pair, and (3) resend that exact body/HMAC to the same endpoint with a forged `X-Shopify-Shop-Domain` header. No secrets, tokens, or TLS interception are needed — only the ability to send arbitrary HTTP requests to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified material, or otherwise cryptographically bind the shop domain to the request before trusting it (e.g., cross-check against the shop stored for that webhook subscription server-side, or verify the shop is one for which the app holds a valid session/access token) rather than relying solely on a body-only HMAC plus an unauthenticated header for tenant dispatch.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed; Shopify delivers a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid signature of `B` with the app's shared `client_secret`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays this exact request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#to_signable_string` returns the unchanged `raw_body` `B` [1](#0-0) ; `HmacValidator.validate` recomputes the HMAC over `B` with the shared secret and it matches `H` [5](#0-4) .
4. `Registry#process` passes validation and calls the handler with `shop: request.shop` == `"victim.myshopify.com"` [6](#0-5) , even though the payload actually originated from and describes `attacker.myshopify.com`'s data.
