## Finding: `validate_state_machine` omits the `is_expired` check that `update_client` enforces

### Title
Request/Response/Timeout handling accepts proofs from expired consensus clients because `validate_state_machine` never calls `is_expired` - (File: modules/ismp/core/src/handlers.rs)

### Summary
The ISMP core defines two "liveness" checks for a consensus client: frozen (`is_consensus_client_frozen`) and expired (`is_expired`, based on the unbonding period). `update_client` enforces both before accepting a new consensus proof, but `validate_state_machine` — the shared pre-check used by the request, response, and timeout handlers — only enforces the frozen check and never calls `is_expired`. This is the same class of inconsistency as the reported Hats Protocol issue: two code paths that are supposed to gate the same underlying trust property behave differently, one being strict and the other silently permissive.

### Finding Description
`update_client` explicitly checks both frozen and expired status before processing a new consensus proof: [1](#0-0) 

The `is_expired` default implementation on `IsmpHost` returns `Error::UnbondingPeriodElapsed` once `host_timestamp - last_update >= unbonding_period`: [2](#0-1) 

However, `validate_state_machine`, which is the sole preliminary-check function shared by `request::handle`, `response::handle`, and `timeout::handle` for verifying state membership/non-membership proofs, only checks `is_consensus_client_frozen` and the challenge-period delay — it never calls `is_expired`: [3](#0-2) 

All three unprivileged, relayer-reachable message handlers rely exclusively on `validate_state_machine` for this liveness gating: [4](#0-3) [5](#0-4) [6](#0-5) 

The docs even describe expiry as a distinct, security-critical mitigation ("mitigates any potential long fork attacks that may arise due to a loss of liveness of consensus clients"), but this mitigation is only wired into `update_client`, not into the request/response/timeout paths: [7](#0-6) 

### Impact Explanation
Once a consensus client's unbonding period has elapsed without an update, the protocol's own model treats the underlying validator set's stake as no longer economically secured (unbonded), so fraud-proof/slashing guarantees for previously verified state commitments are no longer credible. `update_client` correctly refuses further updates in this state (`UnbondingPeriodElapsed`), but because `validate_state_machine` never checks expiry, a relayer can continue to submit `Request`, `Response`, and `Timeout` messages that verify membership/non-membership proofs against already-stored `StateCommitment`s tied to that same (now expired) consensus client — indefinitely, with no way for governance/fishermen to shut this down short of manually freezing the client. This undermines the security assumption that expired clients stop being trusted, and can lead to acceptance of requests/responses relying on stale, no-longer-economically-secured state, i.e., unauthorized app actions/forged message delivery through an already-untrusted trust root.

### Likelihood Explanation
This requires no privileged access: any relayer can call the standard `Message::Request`/`Message::Response`/`Message::Timeout` handlers with proofs referencing a `StateMachineHeight` whose owning consensus client has since expired but was never explicitly frozen by a fraud proof. Since expiry is a normal, expected occurrence when a consensus client stops being updated, this condition is easy to reach without any malicious actor and the code path is hit on every single request/response/timeout message.

### Recommendation
Add an `host.is_expired(proof_height.id.consensus_state_id)?` check inside `validate_state_machine` (mirroring `update_client`), so that all message handlers consistently reject proofs from consensus clients whose unbonding period has elapsed, matching the guarantee already documented and enforced for consensus updates.

### Proof of Concept
1. Register/create a consensus client and let it accumulate a valid `state_machine_commitment` at height `H` (via a normal `update_client` call).
2. Let time pass until `host_timestamp - last_update >= unbonding_period` (client is now "expired" per `is_expired`, but not frozen).
3. Any relayer submits a `Message::Request` (or `Response`/`Timeout`) referencing proof height `H`. `request::handle` → `validate_state_machine` only checks `is_consensus_client_frozen` (false) and the challenge-period delay (elapsed) — `is_expired` is never invoked — so the message is processed and dispatched to the destination module despite the consensus client being expired, in contrast to `update_client`, which would reject any further proof against this same client with `UnbondingPeriodElapsed`.

	/// Check if the client has expired since the last update
	fn is_expired(&self, consensus_state_id: ConsensusStateId) -> Result<(), Error> {
		let host_timestamp = self.timestamp();
		let unbonding_period = self
			.unbonding_period(consensus_state_id)
			.ok_or(Error::UnnbondingPeriodNotConfigured { consensus_state_id })?;
		let last_update = self.consensus_update_time(consensus_state_id)?;
		if host_timestamp.saturating_sub(last_update) >= unbonding_period {
			Err(Error::UnbondingPeriodElapsed { consensus_state_id })?
		}

		Ok(())
	}

/// This function does the preliminary checks for a request or response message
/// - It ensures the consensus client is not frozen
/// - Checks for frozen state machine is deprecated and malicious state machine commitment will be
///   deleted instead
/// - Checks that the delay period configured for the state machine has elapsed.
pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}
