### Title
Batch withdrawals of the same token are not de-duplicated/disambiguated, causing `describeWithdrawal` to report the same destination hash for two distinct withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`IntentsSDK.processWithdrawal`/`signAndSendWithdrawalIntent` allow a caller to submit a batch of `WithdrawalParams` with no check that entries are unique. When two withdrawals in the same batch share the same `assetId` (e.g. withdrawing the same NEP-141 token to two different destination addresses in one intent), `PoaBridge.describeWithdrawal` cannot tell them apart and reports the completion status/txHash of one physical withdrawal for both logical withdrawal requests.

### Finding Description
`PoaBridge.createWithdrawalIdentifier` builds a `WithdrawalIdentifier` keyed by `index` and `withdrawalParams`, but `describeWithdrawal` never uses `index` to select the matching record. Instead it calls `findMatchingWithdrawal`, which matches purely by `assetId`: [1](#0-0) 

The code comment explicitly acknowledges the underlying equality being broken: two different logical withdrawals (different index, potentially different destination address/amount) resolve to the same on-chain withdrawal record because the match key (`assetId`) is not unique within a batch: [2](#0-1) 

The SDK itself does not prevent constructing such a batch. `processWithdrawal` accepts `WithdrawalParams[]` and fans out fee estimation, intent signing, and completion waiting without any uniqueness constraint on `assetId`: [3](#0-2) 

This is the same equality violation as the referenced report ("operator adds the same validator twice" → funds intended for distinct destinations end up attributed to one address): here, two distinct withdrawal requests (distinct destination/amount) end up attributed to a single withdrawal record/txHash, because the "assetId" key used to look up the on-chain result is not the caller-supplied unique identity of the request (index + destination + amount).

### Impact Explanation
If an integrator batches two POA-bridge withdrawals of the same token (e.g., paying out two different users the same token in one intent, a very plausible product feature), `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` will resolve both withdrawal identifiers to the **same** `txHash`/status once the first matching withdrawal record appears. An integrator that credits/marks-as-paid based on this status can end up crediting or confirming two separate withdrawal legs against a single actual on-chain transfer, effectively causing the integrator to believe funds were delivered twice when they were delivered once, or, worse, to reconcile the wrong destination address against a given completion event. This fits the "status or hash misreport making an integrator credit or refund twice" High-impact category, since resolution of withdrawal completion is what integrators use to release custody, mark ledgers complete, or trigger downstream payouts.

### Likelihood Explanation
No malicious actor or privileged role is required — any regular SDK consumer batching two or more withdrawals of the same asset in a single `processWithdrawal`/`signAndSendWithdrawalIntent` call triggers this. This is a normal, foreseeable usage pattern (e.g., paying multiple users the same token in one intent to save on relayer/storage fees) and the code path is unconditionally reached whenever `describeWithdrawal` is called for such a batch on the PoA route.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` beyond `assetId` alone: either (a) reject/validate batches containing more than one withdrawal with the same `assetId` on the PoA route at construction time, or (b) implement the amount-based ordering the code comment already proposes — sort both the API's withdrawal list and the local `withdrawalParams` (filtered by `assetId`) by amount and match by relative position/index, since PoA relayer fees are equal for the same token and thus preserve amount ordering.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ { assetId: "nep141:usdt.tether-token.near", amount: 100n, destinationAddress: "0xAAA...", feeInclusive: false }, { assetId: "nep141:usdt.tether-token.near", amount: 200n, destinationAddress: "0xBBB...", feeInclusive: false } ] })` — a single intent with two USDT withdrawals to two different EVM addresses.
2. Both `WithdrawalIdentifier`s (`index: 0` and `index: 1`) are passed to `PoaBridge.describeWithdrawal`.
3. Once the PoA bridge processes the first payout and the withdrawal-status API returns one `withdrawals[]` entry for `near_token_id: usdt.tether-token.near`, `findMatchingWithdrawal` returns that same entry for **both** identifiers (matched only on `assetId`).
4. Both `waitForWithdrawalCompletion` promises resolve with the identical `{ status: "completed", txHash }`, even though only one of the two on-chain transfers (to `0xAAA` or `0xBBB`) has actually completed — see the deliberate assetId-only matching logic at [4](#0-3) .

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	async processWithdrawal(
		args: ProcessWithdrawalArgs<WithdrawalParams | WithdrawalParams[]>,
	): Promise<WithdrawalResult | BatchWithdrawalResult> {
		const withdrawalParams = Array.isArray(args.withdrawalParams)
			? args.withdrawalParams
			: [args.withdrawalParams];

		// Step 1: Estimate fee
		const feeEstimation = await (() => {
			if (args.feeEstimation != null) {
				return Array.isArray(args.feeEstimation)
					? args.feeEstimation
					: [args.feeEstimation];
			}

			return this.estimateWithdrawalFee({
				withdrawalParams,
				logger: args.logger,
			});
		})();

		// Step 2: Sign and send intent
		const { intentHash } = await this.signAndSendWithdrawalIntent({
			withdrawalParams,
			feeEstimation,
			referral: args.referral,
			intent: args.intent,
			logger: args.logger,
		});

		args.logger?.info("Intent published", { intentHash });

		// Step 3: Wait for intent settlement
		const intentTx = await this.waitForIntentSettlement({
			intentHash: intentHash,
			logger: args.logger,
		});

		args.logger?.info("Intent settled", { txHash: intentTx.hash });

		// Step 4: Wait for withdrawal completion
		const destinationTx = await this.waitForWithdrawalCompletion({
			withdrawalParams,
			intentTx,
			logger: args.logger,
		});
