This confirms the vulnerability. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers [2](#0-1)  that are never included in the HMAC-signed content. `Registry.process` validates only the raw-body HMAC via `Utils::HmacValidator.validate(request)` and then hands the unauthenticated `request.shop` value straight to the handler as the tenant identifier [3](#0-2) .

### Title
Webhook shop/topic/metadata headers are not covered by HMAC verification, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw HTTP body via HMAC-SHA256, but the `shop-domain`, `topic`, `api-version`, and `webhook-id` values used by the handler dispatch logic come from unauthenticated HTTP headers that are excluded from the signable string.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from request headers [2](#0-1)  and are never mixed into the signed payload.

`Registry.process` trusts these header-derived values once the body HMAC checks out: it dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` to the registered handler without any binding between `shop`/`topic` and the signed bytes [3](#0-2) .

The identity binding that should hold is: `shop authenticated by HMAC == shop acted on by the handler`. Because the header-derived `shop` is outside the HMAC's scope, an attacker who possesses one valid `(raw_body, hmac)` pair — e.g. a merchant who legitimately receives a genuine Shopify webhook for their own shop A — can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for shop B. `HmacValidator.validate` still succeeds because it only checks the untouched raw body, but `Registry.process` will attribute the payload to the attacker-chosen shop/topic, causing the host application to process/store shop-A's data under shop B's tenant context or misroute it to an unintended handler.

### Impact Explanation
This breaks the authenticated-shop-equals-acted-on-shop binding and produces cross-tenant data attribution: a webhook payload's content is verified as coming from the app's Shopify configuration, but the tenant (`shop`) and event classification (`topic`) it gets recorded under are attacker-controlled. Depending on how the host app persists `WebhookMetadata#shop`/`#topic` (e.g., keyed lookups, per-tenant records), this can lead to cross-tenant data leakage or corruption, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires possession of at least one genuine `(raw_body, x-shopify-hmac-sha256)` pair for the target app, which any merchant with the app installed receives passively as part of normal webhook delivery — no `api_secret_key`, access token, or privileged account is required. The webhook endpoint is by design a public, unauthenticated HTTP endpoint that accepts POSTed bytes plus headers, so replaying with modified headers requires only a basic HTTP client.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them to the body, e.g. by validating that the `shop` header matches a shop already tied to a stored session/subscription before dispatch), so any header value acted on by `Registry.process` is covered by the same signature validated in `HmacValidator.validate`.

### Proof of Concept
1. As a merchant with the app installed on `shop-a.myshopify.com`, capture a legitimate webhook request the app receives: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's configured `api_secret_key`), along with `x-shopify-shop-domain: shop-a.myshopify.com` and `x-shopify-topic: orders/create`.
2. Resend an HTTP POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: shop-b.myshopify.com` (a different tenant not controlled by the attacker).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks body `B` against `H` [1](#0-0) .
4. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the signed content actually originated for `shop-a.myshopify.com`, demonstrating the cross-tenant attribution bypass [3](#0-2) .
