### Title
`HandlerV2.handlePostRequests` / `handleGetResponses` revert the entire batch on a single already-delivered leaf, enabling front-run griefing of relayers - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` verify a Merkle Mountain Range membership proof for an entire batch of leaves and only *afterwards* loop back over every leaf to check for duplicates, reverting the **whole transaction** with `DuplicateMessage()` if even one leaf in the batch was already delivered. This is the same bug class as the referenced PoolTogether finding: a malicious actor can front-run a relayer's large multi-item batch by cheaply delivering just one of its constituent requests/responses first, causing the victim's expensive batch transaction (which already paid the gas for proof verification over the full leaf set) to revert entirely and deliver nothing.

### Finding Description
Both permissionless handler entrypoints follow the same two-phase pattern:

1. Build `leaves[]` for every item in the batch and verify a single MMR multiproof against the stored `overlayRoot`.
2. Loop a second time and, for each leaf, check `host.requestReceipts(...)` / `host.responseReceipts(...)`; if any single one is non-zero (already delivered), `revert DuplicateMessage()` aborts the entire call. [1](#0-0) [2](#0-1) 

Both functions are explicitly permissionless — "Access: Permissionless (can be called by anyone)" — and are also composable via `batchCall`, which delegatecalls sequential handler calls and reverts the whole batch if any inner call fails. [3](#0-2) [4](#0-3) 

Note that the underlying `EvmHost.dispatchIncoming` calls were deliberately designed to *not* abort the surrounding batch on a per-item failure (early `return` instead of `revert`) — the code even comments "instead of reverting the entire batch, early return here" — showing the protocol authors intended to protect batches from single-item failures. However, the `DuplicateMessage()` check inside `HandlerV2` itself was not given the same treatment, leaving exactly the gap the referenced report is about. [5](#0-4) 

Relayer tooling explicitly relies on batching many messages into one `handlePostRequests`/`handleGetResponses`/`batchCall` transaction for gas efficiency: [6](#0-5) 

### Impact Explanation
A malicious actor observing a pending relayer transaction in the mempool (containing N post-requests or get-responses) can front-run it with a minimal, cheap transaction delivering just one of the same leaves (reusing/deriving a valid sub-proof for that single leaf, since the leaf commitments and MMR data are all public in the observed calldata). Once that single leaf's `requestReceipts`/`responseReceipts` entry is set, the victim's larger batch transaction will revert entirely at the `DuplicateMessage()` check — *after* it has already paid the full gas cost of `MerkleMountainRange.VerifyProof` over the complete leaf set. This:
- Wastes the honest relayer's gas on every batched transaction that overlaps with a griefed leaf.
- Prevents legitimate delivery of all N-1 other, still-undelivered requests/responses in that batch, effectively blocking a route from making progress until the relayer retries with a filtered batch.
- Can be used repeatedly and cheaply (attacker only pays for single-item deliveries, which they can execute themselves, potentially capturing any fee/incentive associated with each attacked message) to systematically grief a competing or slow relayer.

This matches the "route unable to deliver messages" and denial-of-relayer-economics impact categories.

### Likelihood Explanation
Both handler functions are fully permissionless and take proofs that are visible/derivable directly from the target transaction's calldata once it is broadcast to the mempool, making front-running straightforward for any observer with basic mempool-monitoring and MEV tooling. No special privileges, admin access, or governance control are required — only an unprivileged actor submitting a transaction ahead of the victim's.

### Recommendation
Mirror the mitigation already applied in `EvmHost.dispatchIncoming` at the `HandlerV2` batch level: instead of reverting the whole call when a leaf's receipt already exists, skip (early-continue) that individual leaf and emit an event/no-op for it, while still processing and dispatching the remaining un-delivered leaves in the batch. This preserves proof-verification cost recovery for the relayer and prevents a single griefed leaf from blocking delivery of the rest of the batch.

### Proof of Concept
1. Relayer A builds and broadcasts `handlePostRequests(host, {proof, requests: [r1, r2, ..., r50]})` containing 50 leaves, paying gas to verify the MMR multiproof for all 50.
2. Attacker observes this pending transaction, extracts `r1` and a corresponding single-leaf sub-proof (or independently queries/derives one), and submits `handlePostRequests(host, {proof', requests: [r1]})` with higher gas price so it lands first.
3. Attacker's transaction sets `_requestReceipts[hash(r1)] = attacker`.
4. Relayer A's transaction executes: the MMR proof for all 50 leaves is verified successfully (gas fully spent), but the post-verification duplicate-check loop hits `r1`, whose receipt is now non-zero, and the entire call reverts via `DuplicateMessage()` — none of `r2..r50` are delivered despite the relayer having paid for the verification of the whole batch.     /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});

/// Submit a full batch of ISMP messages as a single `IHandlerV2.batchCall` transaction.
///
/// One tx replaces what would otherwise be N separate txs (one per message),
/// cutting gas overhead and nonce management complexity. Atomic: if any
/// inner call reverts, the whole transaction reverts.
pub async fn submit_batch_messages(
	client: &EvmClient,
	messages: Vec<Message>,
) -> anyhow::Result<SubmitOutcome> {
	if messages.is_empty() {
		return Ok((BTreeSet::new(), Vec::new(), Vec::new()));
	}

	let handler_addr = Address::from_slice(&client.handler().await?.0);
	let from = Address::from_slice(&client.address);
	let gas_price = fetch_gas_price(client, false).await?;
	let chain_gas_limit = get_chain_gas_limit(client.state_machine);

	let inner_calls = build_batch_inner_calls(client, &messages).await?;
	let handler_v2 = HandlerV2Instance::new(handler_addr, client.signer.clone());
	let call = handler_v2.batchCall(inner_calls);
	let gas = call.estimate_gas().await.unwrap_or_else(|_| (chain_gas_limit * 8) / 10);
	let calldata = call.calldata().clone();
	let calldata_len = calldata.len();
	let tx_request =
		build_tx_request(from, handler_addr, calldata, gas_price, gas_with_buffer(gas));
