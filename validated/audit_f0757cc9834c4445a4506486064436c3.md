## Analysis

The bug class in the report is a broken identity binding: an action (`borrowTokenFromGt`) trusts an identifier (`gtId`) supplied by the caller without checking that the caller actually owns it, and the check that *is* performed (approval to the router) does not bind the recipient/caller to the resource. The strongest analog in this gem is in webhook signature verification, where the `shop` value used to route/process a webhook is **not** part of the HMAC-signed payload.

### Root cause

`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery`, and its `to_signable_string` returns **only the raw body**: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` are all read from HTTP headers that are **not covered by the HMAC**: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against the received `hmac`: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop`, which was never covered by that HMAC: [4](#0-3) 

### Why this is exploitable by an unprivileged attacker

Any merchant who has installed the app (an "unprivileged internet user" with respect to other tenants) legitimately receives real, validly-HMAC'd webhook deliveries for their own shop. Because the signature covers only the raw body and not the `shopify-shop-domain` header, that same attacker can replay the identical body + identical valid HMAC to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `Utils::HmacValidator.validate` will report success because it never inspected the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled body content.

This exactly matches the excluded bullet in scope: *"a field acted on but not covered by the HMAC"* — here the identity-binding field is `shop`, verified-bytes vs. acted-upon-bytes diverge, just as the gtId in the original report was used to act on a resource without checking ownership.

### Impact

Depending on the host application's webhook handler (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, order/product sync handlers), an attacker can inject or corrupt data attributed to a victim tenant, or trigger tenant-scoped side effects (data deletion, session revocation, resynchronization) against a shop they do not control — a cross-tenant access/write, satisfying the "Critical - cross-tenant access" bar, without needing `api_secret_key`, an access token, or any privileged account.

### Title
Webhook HMAC Does Not Bind the Shop-Domain Header, Enabling Cross-Tenant Webhook Spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body. The `shop`, `topic`, and `webhook_id` fields, which `Webhooks::Registry.process` uses to route and label the webhook payload delivered to the app's handler, are read from HTTP headers that are excluded from the HMAC computation.

### Finding Description
`HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) checks the HMAC only against `verifiable_query.to_signable_string`. For webhooks, that string is `@raw_body` only (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, and `webhook_id` are pulled from headers (`lib/shopify_api/webhooks/request.rb:15-33`) with no cryptographic tie to the body or to each other. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC and then trusts `request.shop`/`request.topic` for dispatch and for populating `WebhookMetadata` passed to the app's handler. Since the `shop` header is never part of what's authenticated, a party who legitimately receives a validly-signed webhook body (for their own shop) can resend that same body with a spoofed `shop` header, and the gem will report a valid signature while attributing the payload to an arbitrary victim tenant — an identity binding break equivalent to trusting a `gtId` without verifying ownership.

### Impact Explanation
An attacker who is a legitimate (but unprivileged relative to other tenants) app user can forge webhook deliveries the app believes originate from a different, victim shop, while still passing HMAC validation. Any handler logic keyed off `shop` (uninstall cleanup, GDPR redaction, data sync, per-shop state changes) can be triggered or poisoned for a shop the attacker does not own — a cross-tenant access/write.

### Likelihood Explanation
Requires only: (1) the attacker's own app installation (to obtain one authentic, HMAC-valid webhook body), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with custom headers — both are available to any unprivileged internet user who is an app merchant. No `api_secret_key`, access token, or privileged account is required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the authenticated payload (e.g., require the consuming application to cross-check `request.shop` against a shop it independently expects for that endpoint/session) before trusting it for dispatch.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed; Shopify sends a real webhook with a valid `shopify-hmac-sha256` computed over the JSON body.
2. Attacker captures this request (body + valid HMAC).
3. Attacker replays the exact same body and HMAC to the app's webhook endpoint, but changes the `shopify-shop-domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
5. The registered handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` and processes it as though it were an authentic event for the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
