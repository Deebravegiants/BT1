Confirmed: the docs at `docs/usage/webhooks.md` explicitly document that `Registry.process` "will verify the request did indeed come from Shopify" — meaning the shop identity is presented to the app as authenticated, when in fact only the raw body is HMAC-verified.

### Title
Webhook `shop` header is trusted as authenticated but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC (`hmac`) that is verified by `ShopifyAPI::Utils::HmacValidator.validate` before a webhook is processed, giving the appearance that the entire webhook request — including which shop it is "from" — has been authenticated. In reality, the HMAC is computed only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` value used to identify the tenant is read directly from the unauthenticated `X-Shopify-Shop-Domain` / `shopify-shop-domain` header and passed straight into the handler as the tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from a header with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then forwards `request.shop` unmodified to the app's handler as the trusted tenant identity: [3](#0-2) 

This is the equality the gem implicitly claims to guarantee for the caller:
`shop authenticated (bound to the signature) == shop acted upon by the handler`

That equality does not hold: `HMAC = HMAC_secret(raw_body)` binds only the body bytes; `shop`, `topic`, `webhook_id`, and `api_version` are all read from headers that are completely outside the signed material. Docs explicitly tell app authors that `Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md), reinforcing the false assumption that `data.shop` is authenticated.

Concretely: any merchant who installs the app (an "unprivileged internet user" relative to other tenants) legitimately receives real webhooks from Shopify — i.e., genuine `(raw_body, hmac)` pairs signed with the app's own `api_secret_key`, since HMAC-SHA256 is deterministic and depends only on body + secret, not on any per-shop nonce embedded in the signature. That attacker can replay the exact same `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain. `HmacValidator.validate` will still pass (it never looks at the shop header), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain, `body` set to attacker-chosen content, for whatever topic the attacker chooses (also unauthenticated) among any topic the app has registered.

### Impact Explanation
This crosses a tenant boundary using data that appears authenticated but isn't. Depending on how the app's registered handler uses `data.shop` (session lookup key, cache key, per-shop record update), this enables cross-tenant effects: forging events (e.g. `app/uninstalled`) against a victim shop to trigger deletion of the victim's stored session/access token, or injecting attacker-controlled `body` content that the app associates with and processes under a victim shop's identity. This matches the Critical criterion "cross-tenant access" for this class of finding, since the app is misled into acting on a different tenant's identity using data supplied by an unrelated, unprivileged actor.

### Likelihood Explanation
Requires only that the attacker be able to install the app on their own store (any merchant can do this for public apps) to obtain a valid `(body, hmac)` pair, and be able to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no access to `api_secret_key`, access tokens, or any privileged credential is required. This is a design consequence of the gem only signing the body and offering no mechanism/documentation warning developers that `data.shop` (and `data.topic`/`data.webhook_id`) are unauthenticated.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the material that is verified, or explicitly document and enforce that the app must independently verify `data.shop` against a known/installed shop list before trusting it. At minimum, the gem should not imply (in code or docs) that `process`/`validate` authenticates anything beyond the raw body, and should provide a supported way to cross-check the `shop` header against session storage before invoking handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, causing Shopify to send a real webhook (e.g. `app/uninstalled`) to the app's endpoint with a genuine `raw_body` and `x-shopify-hmac-sha256` computed with the app's real `api_secret_key`.
2. Attacker captures this exact `(raw_body, hmac)` pair.
3. Attacker sends a new HTTP POST to the same webhook endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and any desired `x-shopify-topic`).
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks the body against the HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to process an attacker-controlled event as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
