### Title
Unauthenticated `RequestState` replay lets any relay peer read the last signup-session message meant for the paired counterpart - (File: `orb-relay-client/src/client.rs`)

### Summary
The `renounceOwnership()`/`_pendingOwner` bug in the report is a "two-step state machine where the guard is only enforced on one path, letting stale/unscoped state leak to the wrong actor." The same bug class is reachable in orb-core's Orb-Relay client: incoming `RequestState` messages are answered with the cached `last_message` **before** the sender-identity check (`src.id != self.config.dst_id`) that is applied to every other message type, so the reply-with-cached-state path bypasses the peer-binding check that is supposed to scope the session.

### Finding Description
`PollerAgent::main_loop` processes incoming `RelayConnectResponse` payloads in a single match arm. For a normal payload it validates that the sender is the expected paired peer before dispatching it: [1](#0-0) 

Concretely:
```rust
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source...");
} else {
    self.handle_message(...).await?;
}
```
The `src.id != self.config.dst_id` guard — which is the only mechanism ensuring a message is scoped to the currently paired counterpart (Orb↔App session) — is only evaluated in the `else if` branch. The `RequestState` branch is checked first and, if it matches, immediately replies with `self.last_message` regardless of who `src` is. `last_message` is the most recently sent session-relevant payload (e.g. `AnnounceOrbId`, `SignupEnded`), stored per `PollerAgent` instance and updated on every outgoing send: [2](#0-1) 

Because the relay routes by `dst_id`/`session_id` at the transport layer but the orb-relay-client itself does not additionally verify `src.id` before honoring a `RequestState`, any entity able to open a relay connection scoped to that session (e.g. a stale/duplicated app connection, or a race during reconnect/session hand-off) is answered with the cached session state without the same authorization check applied to all other message types.

### Impact Explanation
`last_message` can carry signup lifecycle information such as `AnnounceOrbId` (which orb/app is paired for the in-progress signup) or `self_serve::orb::v1::SignupEnded` (success/failure of a signup). An unauthenticated/unbound `RequestState` request bypassing the peer-identity check can cause the Orb to leak this signup-session state to a party other than the legitimate paired app, mirroring the original bug's core defect: a stale/incompletely-guarded piece of session state (`_pendingOwner` / `last_message`) that skips the authorization check enforced on the "normal" path and can be read back out by an unintended party, causing cross-session/cross-signup state disclosure.

### Likelihood Explanation
This code path executes on every reconnect or whenever a `RequestState` message arrives, which is a normal part of the self-serve app protocol (used to recover the current state after a disconnect, as seen in `orb-relay-client/src/bin/manual-test.rs` `orb_to_app_with_state_request`). The check that is skipped (`src.id != self.config.dst_id`) is explicitly present for the other branch, showing the developers intended per-session isolation but did not apply it uniformly, making this a straightforward, easily triggerable inconsistency rather than a deep architectural issue.

### Recommendation
Apply the same `src.id != self.config.dst_id` validation before the `RequestState` short-circuit, so `last_message` is only replayed to the verified paired peer:
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```

### Proof of Concept
1. Orb sends `AnnounceOrbId`/`SignupEnded` to its paired app; `PollerAgent::last_message` is updated to this payload. [3](#0-2) 
2. A second relay connection (any `src`) scoped to the same relay session sends `self_serve::app::v1::RequestState {}`.
3. Because the `RequestState` branch is evaluated before the `src.id != self.config.dst_id` check, the Orb immediately replies with `last_message` to this connection, regardless of whether `src.id` matches the expected `dst_id`. [4](#0-3)
