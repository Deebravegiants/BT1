The reported "nonce vs salt" bug describes a class of vulnerability where a field is *used* downstream but is not actually *bound* to the cryptographic proof that authorizes its use. The strongest analog in `shopify-api-ruby` is in the webhook verification path.### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `x-shopify-shop-domain` header to determine which tenant a webhook belongs to. The HMAC therefore proves the body is genuine for *some* shop using the same app credentials, but does not bind that body to the specific shop identity that the library hands to the host app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the presented signature [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`; the shop identity is never part of the signed material [2](#0-1) . `shop` is instead read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header, with no cryptographic linkage to the HMAC [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the host application's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

This breaks the intended binding `shop authenticated == shop that receives the webhook effects`. Because every shop installing the same app shares the same `api_secret_key`, the HMAC over the body is valid for *any* shop, not just the one named in the header. An attacker who controls (or has previously received, e.g. by installing the app on their own store) a genuine webhook body+HMAC pair can resend that exact body/HMAC to the app's webhook endpoint while substituting a victim's `shop-domain` header. `HmacValidator.validate` still passes because it never inspects the shop header, and `Registry.process` will hand the forged shop identity straight to the app's handler as if it originated from the victim shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged attacker (any merchant who can install the app, or anyone able to capture a webhook delivery for one shop) can make the host application process attacker-controlled body content under a victim shop's identity. Depending on how the host app's webhook handler uses `WebhookMetadata#shop` (e.g., looking up the corresponding session/access token, updating billing state, processing `app/uninstalled`, `customers/redact`, or order data), this can lead to state corruption, unauthorized actions performed against the victim's store context, or triggering privileged flows (like session/token lookups) keyed by an attacker-forged shop value — a cross-tenant access primitive.

### Likelihood Explanation
Exploitability only requires network access to the app's public webhook endpoint plus one legitimate raw_body/HMAC pair for any shop using the app (trivial to obtain by installing the app on an attacker-controlled store, since HMACs are shared per app, not per shop). No secrets, tokens, or elevated privileges are needed — matching the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically verify that the shop domain in the header is consistent with the shop that legitimately owns the delivered webhook. At minimum, `to_signable_string` should incorporate the `shop-domain` (and ideally `webhook-id`/`topic`) so any header substitution invalidates the HMAC, mirroring how `AuthQuery#to_signable_string` includes `shop` in its signed payload [5](#0-4) . Alternatively, document that host applications must independently verify `request.shop` against a known, previously-authorized shop for that specific webhook subscription/session before trusting it.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com`, receiving a legitimate webhook delivery with body `B` and valid header `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker replays the same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` — it matches `H`, since the shop header is not part of the signed string [7](#0-6) .
5. `Registry.process` invokes the host handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data as if it came from the victim's shop [8](#0-7) .
