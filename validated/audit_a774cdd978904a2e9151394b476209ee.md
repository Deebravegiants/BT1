### Title
Webhook `shop-domain` header is trusted as the tenant identifier without being covered by the HMAC signature, enabling cross-tenant webhook attribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used to attribute an incoming webhook to a specific tenant from the `X-Shopify-Shop-Domain` header, but the HMAC signature computed by this gem only covers the raw request body, not this header. An attacker who legitimately receives a validly-signed webhook for one shop (e.g. their own store) can replay the identical body/HMAC pair while substituting a different shop's domain in the header, and the gem's own verification will accept it, handing the host application an unauthenticated `shop` value for a tenant-critical decision.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC (which, per above, only proves the body was signed by someone holding the app's `client_secret` — it says nothing about which shop sent it) and then immediately forwards `request.shop` — taken from the unverified header — into `WebhookMetadata`, which the host application's `WebhookHandler#handle` uses as the tenant identifier for the event: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`shop asserted inside the HMAC-covered bytes == shop the host application attributes the event to`

but the actual binding implemented is:
`shop-domain header (uncovered by HMAC) == shop the host application attributes the event to`

Because the header is not part of `to_signable_string`, two different header values produce the *same* valid HMAC for the same body. This mirrors the report's bug class of "a field acted on but not covered by the HMAC" — here the field is the shop-domain attribution rather than a balance amount, but the structural flaw (verifying one thing, acting on another, unbound value) is identical.

### Impact Explanation
Any actor who can obtain one legitimately-signed webhook payload (trivial — install the app on any shop they control, which requires no special privilege) can replay that exact `raw_body` + `hmac` pair against the app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to name a different, victim shop. `Registry.process` will treat the HMAC as valid (it only checks body integrity) and dispatch the event with `shop:` set to the attacker-chosen victim domain. Any host application that uses `WebhookMetadata#shop` to select which tenant's session/data store to update (the intended and documented usage) will apply attacker-controlled payload content under a different tenant's identity — a cross-tenant data-integrity/access violation, satisfying the "cross-tenant access" Critical impact bucket, achieved without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Medium-to-High: the attacker only needs a single valid webhook delivery from any shop they control (ordinary, unprivileged use of the platform), the header manipulation itself is standard HTTP header injection at the transport layer that this gem does nothing to prevent, and `Registry.process` is the sanctioned, documented mechanism host apps use to consume webhooks, so no misuse of undocumented APIs is required.

### Recommendation
Bind the shop identity into the material that is actually verified: either include the shop domain in the HMAC-signed payload check (compare it against a shop value obtained from an authenticated source — e.g., the webhook subscription/registration record keyed by `webhook_id`, not the raw header), or explicitly document and enforce that `Request#shop` must not be used as a trust boundary and require callers to re-validate the shop against their own session store before acting on webhook data. At minimum, `Registry.process`/`Request` should not present `shop` as if it were verified alongside the HMAC check when it is not.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (no special privilege required) and triggers/receives a legitimate webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header — both validly signed by Shopify with the app's `client_secret`.
2. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `to_signable_string` (`@raw_body`) against the HMAC — the shop header is never part of that computation: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host application to process attacker-supplied webhook content under `victim-shop`'s tenant context.
