## Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant identity) is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed content. `Registry.process` passes this unauthenticated header value straight to the app's webhook handler as the tenant identifier. Because the app's `client_secret` is shared across every shop that installs the app, an attacker who legitimately installs the app on their own store can capture a genuinely-signed webhook (valid body + HMAC) and simply resend it with a different `X-Shopify-Shop-Domain` header, causing the app to process the payload as if it originated from a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from a header that is completely outside that signable string: [2](#0-1) 

`HmacValidator.validate` only ever verifies `to_signable_string` against the secret — it never binds the shop-domain header into the signature: [3](#0-2) 

`Registry.process` verifies the HMAC and then unconditionally forwards `request.shop` (the unauthenticated header) to the app's handler as the tenant identity for the event: [4](#0-3) 

The binding that should hold is:
`shop used by the handler == shop cryptographically bound inside the HMAC-covered payload`

but the actual code enforces only:
`HMAC(raw_body, client_secret) == received_hmac`, independent of `shop`.

Since the `client_secret` is the same for the app across all merchant installations (it is the app's own secret, not a per-shop secret), any merchant who installs the app — an unprivileged party from Shopify's perspective — can trigger genuine webhook deliveries to their own endpoint, capture a `(raw_body, hmac)` pair that validates correctly, and then replay that exact body/HMAC pair to the endpoint while substituting the `X-Shopify-Shop-Domain` header of a different (victim) shop. `Utils::HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` will call the handler with `WebhookMetadata` claiming the victim shop's identity.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is supposed to guarantee to consuming applications: a webhook handler that uses `WebhookMetadata#shop` to scope data access, storage keys, or side effects per merchant can be made to act on/for a shop it was never actually notified about by Shopify. This is a cross-tenant access primitive (Critical), since the entire trust model of multi-tenant Shopify apps depends on `request.shop` being an authenticated value.

### Likelihood Explanation
Any user can register as a Shopify partner/merchant, install the target app on a free development store at no privilege cost, and receive real webhooks signed with the app's real `client_secret` (shared across tenants). Capturing and replaying an HTTP POST with a modified header is trivial. No access token, session, or leaked secret is required — only normal use of the app as any other merchant.

### Recommendation
Bind the tenant identity into the signed payload verification path instead of trusting a bare header:
- Cross-check `request.shop` against the shop identity embedded in the webhook body payload (most Shopify webhook payloads contain shop-scoped resource data) before dispatching to handlers, or
- Require callers of `Registry.process`/`Request.new` to supply the expected shop (e.g., from the URL path or a known per-install token) and reject requests whose header shop does not match, or
- At minimum, document/enforce that `WebhookMetadata#shop` must never be treated as authenticated by itself and require host applications to independently verify shop provenance (e.g., via a shop-specific webhook secret or a stored mapping of expected shops) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker signs up as a normal merchant and installs the target Shopify app on their own store (`attacker-shop.myshopify.com`).
2. Shopify delivers a legitimate webhook to the app, e.g. body `{"id":123}` with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of the body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker captures this raw body and HMAC.
4. Attacker resends the identical body and HMAC directly to the app's webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
5. `Utils::HmacValidator.validate` succeeds (it only checks the body against the secret), `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: ...)`, and the app performs whatever tenant-scoped action the handler implements (e.g., updates data keyed by shop) attributed to the victim shop.
