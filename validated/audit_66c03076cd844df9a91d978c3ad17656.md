Confirmed: the HMAC in `Webhooks::Request` is computed only over the raw request body, while the `shop` (and `topic`) attributes come from separate, unsigned headers.### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable payload from the raw body only, while the tenant-identifying `shop` attribute is read from a separate, unsigned HTTP header. `Registry.process` verifies the HMAC over the body and then dispatches to the app's handler using this unauthenticated `shop` value, breaking the binding `HMAC-authenticated body == shop the handler believes it is for`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `#shop` (as well as `#topic` and `#webhook_id`) is pulled straight from a header that is never part of the signed material: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` against the HMAC, i.e. the body: [3](#0-2) 

`Registry.process` uses this same, unauthenticated `request.shop` to construct the metadata handed to the app's webhook handler, immediately after the body-only HMAC check succeeds: [4](#0-3) 

This is the exact bug class described in the report analog: a field that is acted upon (`shop`, used by the host app to determine which tenant's data the webhook belongs to) is not covered by the integrity check (`HMAC` over `@raw_body`). The `api_secret_key` used for HMAC is shared across all shops installing the same app, so proving knowledge of it (i.e. a valid signature over some body) says nothing about which shop that body is meant for.

### Impact Explanation
Because `shop` is unauthenticated, any party who can produce one valid `(body, hmac)` pair for the app's shared secret — trivially available to an attacker who has installed the app on their own shop, since they can trigger real webhooks to themselves — can submit a request to the app's public webhook endpoint with the original valid body+HMAC but an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header. `Registry.process` will pass HMAC validation and invoke the app's handler with `shop` set to any victim shop the attacker chooses, while the `body` content is attacker-controlled data from their own shop. Any handler logic that keys off `WebhookMetadata#shop` to select which tenant's records to read/write is exposed to cross-tenant data corruption or exfiltration. This is a cross-tenant access boundary break, matching the Critical impact bucket in scope.

### Likelihood Explanation
No leaked secrets, TLS interception, or privileged access are required. An attacker only needs: (1) their own shop with the target app installed (to obtain one legitimately-signed webhook body+HMAC pair), and (2) the ability to POST directly to the app's public webhook receiver URL with a modified `shop-domain` header. Both are within reach of an ordinary unprivileged internet user / app installer.

### Recommendation
Include the tenant-identifying attributes (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., recompute/verify shop against a value independently obtained via the registered webhook subscription rather than trusting the header), so that a valid signature can only be replayed for the exact shop/topic it was generated for.

### Proof of Concept
1. App installed on attacker-controlled shop `attacker.myshopify.com`; attacker triggers a real webhook (e.g. `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(api_secret_key, B)`).
2. Attacker sends a new POST directly to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate(request)` — this only compares `H` against `HMAC(api_secret_key, B)`, which still matches (see [1](#0-0)  and [3](#0-2) ).
4. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim.myshopify.com"` and attacker-chosen body content ( [5](#0-4) ), causing the app to process attacker data under the victim's tenant.
