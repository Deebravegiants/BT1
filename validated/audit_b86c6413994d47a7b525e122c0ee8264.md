## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` (and `topic`) values used to build `WebhookMetadata` come from separate, unauthenticated HTTP headers. The HMAC therefore only proves body integrity — it never binds the `shop-domain` header to the signature. Any party capable of producing a valid HMAC for a given body (e.g., the legitimate installer of the app on Shop A, who legitimately receives webhooks with a valid HMAC for that body) can resend the same body/HMAC pair while substituting an arbitrary `shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it and hand the attacker-chosen `shop` value to the app's webhook handler as if it were authenticated.

### Finding Description
`Request#hmac` is computed from the `hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks that the computed HMAC over `to_signable_string` (the body) matches the received HMAC — it never touches `shop`: [4](#0-3) 

`Registry.process` then trusts `request.shop` (read straight from the `shop-domain` header) as the tenant identity handed to the app's handler, with no additional binding check: [5](#0-4) 

This is a genuine identity-binding gap, not an inherent Shopify design limitation being misused: the gem's own OAuth callback path (`Auth::Oauth::AuthQuery`) demonstrates the correct pattern by explicitly folding `shop` into `to_signable_string` so the HMAC binds shop identity to the callback: [6](#0-5) 

The webhook path does not follow this pattern — `shop` is "acted on" (used to construct `WebhookMetadata.shop`, which apps use for tenant-scoped business logic such as looking up records or the shop's access token) but is not covered by the HMAC. The equality that should hold — `shop authenticated by HMAC == shop delivered to handler` — is broken: the gem authenticates only the body, while the handler receives an unauthenticated `shop` value.

### Impact Explanation
An attacker who is a legitimate merchant/installer of the target app on "Shop A" (and therefore able to trigger and capture a genuine webhook delivery with a valid HMAC for a chosen body/topic) can replay that exact body and HMAC while spoofing the `shop-domain` (and `topic`, `webhook-id`, `api-version`) headers to name "Shop B". `Registry.process` will pass HMAC validation and invoke the app's `WebhookHandler#handle` with `data.shop == "Shop B"`, even though the payload never originated from Shop B. Since apps commonly use `data.shop` to select which tenant's records to create/update/delete or to fetch that shop's stored access token for follow-up API calls, this can lead to cross-tenant data corruption or the handler acting with Shop B's credentials/context using attacker-supplied data — a cross-tenant access issue as defined in scope.

### Likelihood Explanation
Exploitation requires the attacker to be able to install/be a merchant of at least one shop using the target app (to obtain a body+HMAC pair) and knowledge/guessing of a target shop's domain — both realistic for a public Shopify app. No `client_secret` or access token theft is required; only a normal webhook HTTP POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include `shop` (and ideally `topic`/`webhook-id`) in the signed material the HMAC is checked against, or otherwise cryptographically bind the shop identity delivered in `WebhookMetadata` to the HMAC-verified payload, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker (merchant of Shop A) captures a real webhook POST: body `{}`, header `x-shopify-hmac-sha256: <valid HMAC for "{}">`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only re-derives the HMAC over the unchanged body (`lib/shopify_api/utils/hmac_validator.rb:27-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the app's handler processes attacker-controlled data under Shop B's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
