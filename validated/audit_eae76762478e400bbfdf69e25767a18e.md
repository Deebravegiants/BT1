### Title
Zero-token Emporium "min" path lets an attacker drain the Emporium contract's own ETH/token balance with an unsigned, unauthenticated `EmporiumStack` — (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`formInputForCircom` routes to `formInputEmporiumMin` whenever the attacker sets `circomData.erc20TokenAddresses.length == 0` [1](#0-0) . In this branch only `emporiumMessage`, `timeStamp`, `calldataHash` become public inputs, and neither `rootHashHinkal` nor `erc20TokenAddresses`/`amountChanges` are folded into `getSignedMessageHash` (which is only computed inside `formBasicInput`, never called from `formInputEmporiumMin`) [2](#0-1) [3](#0-2) . Because `dimensionsCheck` forces every per-token array (`amountChanges`, `inputNullifiers`, `outCommitments`, `onChainCreation`, `encryptedOutputs`, `slippageValues`) to length 0 in lock-step with `erc20TokenAddresses.length` [4](#0-3) , the attacker cannot smuggle a nonzero token amount through the omitted fields — that specific claimed divergence does not hold. However, the same zero-token condition also makes `EmporiumUpgradeable.runAction`'s balance-diff loop and `payRelayFees` loop no-ops, since both iterate over `circomData.erc20TokenAddresses` (length 0) [5](#0-4) [6](#0-5) , while the `ops` loop that actually executes external calls with `op.value` runs unconditionally over `stack.ops`, which comes straight from attacker-supplied, ABI-decoded `externalActionMetadata` [7](#0-6) .

### Finding Description
Equality that should hold: *every real value movement authorized by `runAction` (via `op.value` sent from the Emporium contract's own balance) must be reconciled against a `balanceChange` check gated on the corresponding `erc20TokenAddresses` entry, and that entry/operation set must be bound into the proof's public inputs or a valid EIP-712 signature.* This equality breaks in the zero-token branch:

- `verifyWallet` only checks the ECDSA signature over `stack.ops`/`maxFee`/`deadline` when `stack.signerAddress != address(0)`; if the attacker sets `signerAddress = address(0)`, the function returns immediately after marking `emporiumMessage` used — no signature, no authorization at all is required for the `ops` array [8](#0-7) .
- With `signerAddress == address(0)`, `runAction`'s Case 2 branch executes `op.endpoint.call{value: op.value}(op.callData)` directly for every op in the attacker-controlled `stack.ops` [9](#0-8) , e.g. `ETH_RECIPIENT.call{value: X}(...)`.
- Because the attacker chose `erc20TokenAddresses = []` (which is required to reach `formInputEmporiumMin`), `balancesBefore`/`balancesAfter` are empty arrays, `deltaAmountChanges` is empty, and the balance-reconciliation loop (`for (i = 0; i < circomData.erc20TokenAddresses.length; ...)`) never runs — so any ETH actually withdrawn via `op.value` is never checked against `deltaAmountChanges`/`balanceChange >= 0`, and no UTXO is ever minted to account for what left the contract [10](#0-9) .
- `dimensionsCheck`/`checkOnchainCreation` in `HinkalHelper.sol` only enforce internal array-length consistency (all forced to 0) and `getHashedCalldata` does not cover `erc20TokenAddresses`, `amountChanges`, `rootHashHinkal`, `inputNullifiers`, `outCommitments`, or `stealthAddressStructure` at all [11](#0-10) . Since these are also absent from the circuit's public-input vector in the min path, the ZK proof constrains nothing about them, and `rootHashHinkal` is never checked against the Merkle tree state for this call — trivially satisfiable with a proof over zero UTXOs.
- The net effect: an unprivileged attacker can call the wallet's execute entrypoint with a proof containing zero nullifiers/zero output commitments (cheap/trivial to generate — it proves nothing about ownership of funds), `erc20TokenAddresses = []`, and an `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: ETH_RECIPIENT, invokeWallet: false, value: <Emporium's ETH balance>, callData: ""}]`. `runAction` executes the call, draining whatever ETH balance the `EmporiumUpgradeable` contract is holding (pooled there from other users' prior stateful "invokeWallet" interactions or from Emporium's `receive()` function) to `ETH_RECIPIENT`, with zero balance check and zero authorization.

### Impact Explanation
This is direct theft of in-flight/pooled user funds held by the `EmporiumUpgradeable` contract: any ETH sitting in the contract (from other users' multi-step swap/interaction flows) can be sent to an attacker-chosen address with no signature, no proof-of-ownership over any UTXO, and no balance reconciliation. This matches the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable for as long as the Emporium contract holds any residual ETH balance and costs only gas plus generation of a trivial zero-UTXO proof.

### Likelihood Explanation
Preconditions: the Emporium contract must hold a nonzero ETH balance at the time of attack (this happens whenever any legitimate Emporium "Stateful Interaction" leaves funds temporarily in the contract, or via its unguarded `receive()` function). The attacker needs no special role — they only need to be able to submit their own `circomData` with `erc20TokenAddresses=[]`, a self-generated zero-UTXO proof, and a crafted `EmporiumStack`. This is fully within the stated attacker capabilities (deposit own funds, generate own proofs, craft every field of `CircomData`). Feasibility is high because the "min" path's design intentionally skips checks that would otherwise apply for real token transfers.

### Recommendation
Do not allow `runAction`'s `ops` loop to execute stateless calls carrying `op.value` unless (a) `stack.signerAddress != address(0)` and its EIP-712 signature is verified, or (b) the corresponding token/ETH amount is explicitly included in `erc20TokenAddresses`/`amountChanges` and reconciled by the balance-diff loop. Bind `rootHashHinkal`, `erc20TokenAddresses`, and `stealthAddressStructure` into a hash that is always included as a public input (even in the "min" path) so the proof cannot be trivially satisfied with meaningless/zero dimensions when `ops` still perform real value transfers. Alternatively, disallow `signerAddress == address(0)` combined with any `op.value > 0`.

### Proof of Concept
Foundry/Hardhat test plan:
1. Deploy `EmporiumUpgradeable`, `HinkalHelper`, and the Hinkal wallet entrypoint; fund `EmporiumUpgradeable` with ETH (simulate residual balance from a prior legitimate stateful interaction, or via its `receive()`).
2. As the attacker (unprivileged EOA), construct `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, and `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`; ABI-encode an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: attackerRecipient, invokeWallet: false, value: emporiumBalance, callData: ""}]}` as `externalActionMetadata`.
3. Generate a valid zero-UTXO proof for these dimensions (locally, using the project's snarkjs/circom setup) and call the wallet's execute function with it.
4. Assert: `performHinkalChecks` and `verifyProof` succeed; `EmporiumUpgradeable.runAction` executes; `attackerRecipient.balance` increases by `emporiumBalance`; `EmporiumUpgradeable`'s ETH balance goes to 0; no UTXO is minted to account for the ETH that left (`utxoSetLength == 0`); and `deltaAmountChanges` (all-empty) never triggered `BalanceChangeShouldBePositive`.
5. Assert the equality break explicitly: before the call, `emporiumBalance_before == V`; after, `emporiumBalance_after == 0` and `attacker_balance_after - attacker_balance_before == V`, while `sum(deltaAmountChanges) == 0` and no `UTXO` was created recording `V` — showing value left the protocol with zero accounting.
