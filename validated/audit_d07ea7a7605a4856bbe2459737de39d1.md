### Title
Permissionless, shared `CallDispatcher` allows dangling ERC20 approvals to be exploited for unauthorized `transferFrom` drains - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a fully public, access-control-free function that executes attacker-supplied `Call[]` batches (arbitrary `to`/`value`/`data`) in the dispatcher's own context. This single `CallDispatcher` contract is deployed once per chain and shared by every Hyperbridge app that supports calldata execution — `IntentGatewayV2` (predispatch/postdispatch), `HyperFungibleToken`/`WrappedHyperFungibleToken` (`onAccept`), and `BridgeToken`. Because any user or solver can embed an `approve(...)` call in their own order/transfer's `Call[]` that grants an attacker-controlled address an unlimited allowance on a given ERC20 from the dispatcher, and because that allowance is never reset by the protocol, an attacker can leave a permanent dangling approval on the shared dispatcher and later drain any balance of that token the dispatcher subsequently holds — via a plain, out-of-band `token.transferFrom(dispatcher, attacker, amount)` call that requires no further interaction with Hyperbridge contracts. This mirrors the SwapNet root cause: insufficient validation of user-controlled call parameters enabling abuse of existing token approvals to execute unauthorized `transferFrom`s against a shared custodial contract.

### Finding Description
`CallDispatcher.dispatch()` decodes and executes an attacker-supplied `Call[]` with no restriction on `to`, `value`, or `data` beyond requiring the target to have code: [1](#0-0) 

This contract is not per-order or per-user — it is a single deployed singleton reused across chains and across every app: `IntentGatewayV2` predispatch/postdispatch execution, `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-on-receive, and `BridgeToken`, all wired to the same `CALL_DISPATCHER` address: [2](#0-1) [3](#0-2) [4](#0-3) 

`IntentGatewayV2.placeOrder` (and the fill/`_execute` path) forwards a user- or solver-supplied `Call[]` directly to this shared dispatcher without any validation of individual call targets or calldata selectors: [5](#0-4) [6](#0-5) 

The project's own documentation acknowledges the danger of leaving unlimited allowances on the dispatcher but treats it purely as caller guidance, not an enforced invariant: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." [7](#0-6) 

The project's own tests even demonstrate the exact pattern — approving a router for `type(uint256).max` from the shared dispatcher inside a `Call[]`: [8](#0-7) 

Because `dispatch()` has no `onlyOwner`/`onlyHost`/per-caller isolation and the dispatcher is shared across all users, orders, and apps, nothing prevents an attacker from placing a single order whose `predispatch.call` or `output.call` grants an unlimited `approve()` to an attacker-controlled address for a widely-used token (e.g., USDC/USDT/DAI) from the dispatcher. This approval is a normal, permanent ERC20 allowance recorded on-chain against the dispatcher address; it is never revoked by the protocol. Once granted, the attacker does not need to interact with any Hyperbridge contract again — they simply monitor the dispatcher's balance of that token (populated by any subsequent, unrelated legitimate order/transfer that routes through predispatch/postdispatch/on-receive swap flows, or by unswept dust) and call `token.transferFrom(dispatcher, attacker, amount)` directly to steal it.

### Impact Explanation
This allows outright theft of funds transiting the shared `CallDispatcher` from any user or solver who is not the attacker. Since the same dispatcher instance backs `IntentGatewayV2` (used by many concurrent orders/solvers), `HyperFungibleToken`/`WrappedHyperFungibleToken`, and `BridgeToken` on every chain, a single malicious order is sufficient to plant a persistent backdoor allowance that can later be exercised against value belonging to unrelated users whenever it transiently or residually sits in the dispatcher. This is a Critical-severity theft-of-funds vector reachable from a single unprivileged, submitted order/transfer — directly analogous to the SwapNet arbitrary-call/approval-abuse root cause.

### Likelihood Explanation
Likelihood is high: placing an order with a crafted `predispatch.call`/`output.call`, or triggering an HFT/WrappedHFT `send()` with malicious `data`, is a normal unprivileged user action requiring no special permissions, front-running, or governance compromise. The `Call[]` structure is fully attacker-controlled and `CallDispatcher.dispatch()` performs no selector/allowance whitelisting, so the only requirement is that the dispatcher later holds a balance of the targeted token — a routine occurrence given predispatch/postdispatch swap-then-escrow and swap-and-forward flows are core, documented features of the protocol.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to be callable only by a whitelisted set of registered app contracts (`onlyAuthorizedCaller`), and/or deploy a fresh, ephemeral dispatcher instance per call/order rather than sharing one persistent contract across all users.
- Disallow or specially handle `approve`-selector calldata inside `Call[]` batches (e.g., require any approval set within a batch to be reset to zero by the end of the same batch), or enforce that the dispatcher's allowance to any spender is zero both before and after each `dispatch()` invocation.
- Ensure the dispatcher never carries a token balance across transactions (assert zero balance for touched tokens at the end of dispatch, reverting otherwise) so that a dangling approval cannot later be exploited against a balance belonging to a different order.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.predispatch.assets = []`-like minimal escrow and `order.predispatch.call` (or `order.output.call` on a self-fillable order) encoding a single `Call{ to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attackerAddress, type(uint256).max) }`.
2. `IntentGatewayV2` forwards this to the shared `CallDispatcher` via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [9](#0-8) , which executes `USDC.approve(attackerAddress, type(uint256).max)` from the dispatcher — a permanent on-chain allowance.
3. Later, any unrelated user places a legitimate order whose predispatch/postdispatch flow (e.g., "swap-then-escrow" or "fill-then-act") routes USDC through the same dispatcher, or a solver's postdispatch calldata deposits/refunds USDC into the dispatcher before the final sweep (as shown in `testPostdispatchTokenSweep` [10](#0-9) ).
4. The attacker directly calls `USDC.transferFrom(dispatcherAddress, attackerAddress, amount)` using the standing allowance from step 2 — no interaction with any Hyperbridge contract is required — draining the victim's funds from the shared dispatcher.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
