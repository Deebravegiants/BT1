### Title
Unfunded repay overpayment refund drains pool custody — a declared `amount` above the debt is paid out of real token custody without any inbound transfer or reserve check - (File: contracts/pool/src/ops/repay.rs)

### Summary
`Pool::repay` resolves the caller-declared `amount` into a net repay plus an `overpayment`, and `apply` transfers the overpayment back to `payer` via `Cache::transfer_out`. The excess is computed purely from the declared `action.amount` and the position's outstanding debt — never from a measured inbound balance and never debited against the `cash` book. When a market carries no debt, `resolve_repay` takes the full-close branch: `net_repay` is zero, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the entire declared amount is refunded out of real custody with the book untouched. The codebase's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` pins this behavior: a repay of `custody_before` against zero debt pays the full pool balance to a random `payer` with `credited == 0` and cash unchanged. The same "refund from declared amount, not from custody delta" gap is documented for `ops::recapitalize::apply` (the excess over the shortfall) in the same test file.

### Finding Description
In `contracts/pool/src/ops/repay.rs`, `accounting` calls `cache.resolve_repay(amount, position)`, where `amount` is the attacker-controlled `action.amount`. `apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)` — an unconditional token transfer of the overpayment to `payer`. Neither the refund nor `credit_cash(net_repay)` passes through `require_reserves`, and the refund does not debit `cash`. The controller-side flow prefunds the pool before calling repay (`apply_repay_batch` in `contracts/controller/src/positions/debt.rs`), so the design assumes the declared amount is already in custody — but the pool leg itself trusts the declaration. An unprivileged caller invoking `Pool::repay` directly (as the pool's own unit tests do, e.g. `t.client().repay(&payer, &t.ract(0, custody_before))` at `contracts/pool/tests/flows.rs:3604-3608`) can declare an arbitrary amount on a market with no (or small) debt and receive `amount - debt` refunded from supplier funds it never deposited. This mirrors the report's class exactly: the refund leg computes `excess = paid - owed` from a declared `paid` rather than from what actually arrived, so the "refund" is not bounded by any real inflow.

### Impact Explanation
Theft of user funds / protocol insolvency. A single transaction declaring `amount` equal to the pool's full token balance on a debt-free (or lightly borrowed) market receives the whole balance as an "overpayment refund," while `cash` and supplier share accounting are untouched — suppliers retain book claims against an empty contract. The drained amount is capped only by the token's actual balance at the pool.

### Likelihood Explanation
The attack requires no privileged role, no timing, no race, and no oracle manipulation: one call to `Pool::repay` with `payer = attacker` and a large `PoolAction.amount` on a market where `current_debt_ceil` is zero (any supplied-but-unborrowed market, or after the pool's debt is repaid). If `Pool::repay` gates on an authorized payer bound to the declared debt position, the equivalent path via the controller is still prefund-trusting: the controller pulls `amount` to the pool, so the declared-amount refund is safe there — but nothing in `ops::repay` or `Cache::transfer_out` enforces that invariant at the pool layer, and the sibling leg `ops::recapitalize::apply` has the same declared-amount refund shape. One caveat: whether the deployed pool enforces a controller-only caller check on `repay` could not be fully confirmed in this pass; the pool's own tests invoke it with a generated payer and no mocked controller auth, indicating no such gate exists.

### Recommendation
Make the refund self-funding or measured: either (a) gate `Pool::repay`/`recapitalize` to the controller contract and assert it, and/or (b) compute `overpayment` from the measured pool balance delta since entry rather than from `action.amount`, and/or (c) skip the refund when `net_repay == 0` and no debt shares were burned, or debit the refund against `cash`/`require_reserves` so an unfunded refund cannot exceed what was actually received.

### Proof of Concept
1. Deploy pool + controller, register a market for token T, and have a supplier `supply` so the pool holds `B` units of T with zero borrowed.
2. As an unprivileged address `A` holding no T, call `Pool::repay(A, [(hub_asset, B)])` — declaring `amount = B` without any inbound transfer.
3. `resolve_repay` sees `current_debt_ceil == 0`, returns `overpayment = B`, `burned = 0`; `net_repay = 0` passes the `RepayRoundsToZeroShares` disjunct; `cache.credit_cash(0)` leaves the book unchanged.
4. `apply` executes `transfer_out(A, B)`: the pool's entire T balance moves to `A` while `cash` still reads `B`.

This is exactly what `contracts/pool/tests/flows.rs:3590-3610` (`test_unfunded_repay_overpayment_refund_also_pays_out_of_custody`) demonstrates: `repay(&payer, &ract(0, custody_before))` yields `actual_amount == 0` and `assert_unfunded_refund_drained_custody` confirms custody moved to `payer` with the book untouched.
