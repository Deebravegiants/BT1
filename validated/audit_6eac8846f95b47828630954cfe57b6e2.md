### Title
Zcash `validateAddress` accepts Orchard-only Unified Addresses that the Omni Bridge cannot deliver to, allowing funds to be withdrawn to an undeliverable destination - (File: `packages/intents-sdk/src/lib/validateAddress.ts`, `packages/intents-sdk/src/lib/zcash-unified-address.ts`)

### Summary
`validateZcashUnifiedAddress` explicitly permits a Unified Address whose only receiver is Orchard (shielded), since the function's success condition `hasOrchardOrTransparent` is satisfied by an Orchard receiver alone with no transparent (P2PKH/P2SH) receiver present. This format-only address is then passed unmodified through `deriveOmniWithdrawIntentParams` into the signed `ft_withdraw` intent sent to `omni.bridge.near`.

### Finding Description
The claimed equality is: `validateAddress(s, Chains.Zcash) === true` implies "the Omni Bridge connector can deliver to `s`". This is broken for Orchard-only Unified Addresses.

- `validateZcashAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` (lines 344-371) routes any `u1...` string to `validateZcashUnifiedAddress`.
- `validateZcashUnifiedAddress` in `packages/intents-sdk/src/lib/zcash-unified-address.ts` (lines 92-147) parses receivers and only requires `hasOrchardOrTransparent` to be true, which is set by a P2PKH, P2SH, **or** Orchard receiver [1](#0-0) . A UA containing solely an Orchard receiver therefore validates as `true`, even though it has no transparent receiver at all.
- The function's own docstring states the intent was to require "at least one Orchard, P2PKH, or P2SH receiver," but conflates Orchard (shielded) with the transparent types for acceptance purposes [2](#0-1) .
- `validateAddress` itself documents that it is format-only and "does not guarantee a bridge will accept the address" [3](#0-2) .
- In `omni-bridge.ts`, `validateWithdrawal` calls this same `validateAddress` as its only address-format gate before signing [4](#0-3) .
- Zcash is classified as a UTXO chain (`UTXO_CHAINS = [ChainKind.Btc, ChainKind.Zcash]`) [5](#0-4) , and for UTXO chains `validateWithdrawal` calls `this.omniBridgeAPI.getFee(...)` with the raw destination address before allowing the withdrawal to proceed [6](#0-5) . Whether this live bridge-indexer call actually rejects an Orchard-only UA is an external dependency not visible in this repo (the indexer's behavior for UTXO-chain address validation is not implemented here), so the SDK's own code contains no explicit capability check for Zcash receiver types.
- `deriveOmniWithdrawIntentParams` takes `destinationAddress` as-is and builds `recipient = omniAddress(omniChainKind, destinationAddress)` without any receiver-type-specific handling for Zcash (unlike the lower-case normalization it does for Bitcoin bech32) [7](#0-6) . This value flows into `createWithdrawalIntents`, which packs it into the signed `ft_withdraw` intent sent to `omni.bridge.near` [8](#0-7) .
- `describeWithdrawal` only reports `pending`/`completed` based on whether the Omni Bridge API returns a `finalised` transaction hash for the transfer index [9](#0-8) ; there is no explicit "address unsupported / delivery impossible" status, so a stuck transfer surfaces only as an indefinitely `pending` state.

### Impact Explanation
If the live Omni Bridge Zcash connector genuinely cannot construct or broadcast a transaction to a shielded-only receiver (a well-known limitation of connectors that operate on Zcash's transparent pool, since a smart-contract-driven bridge cannot spend into or interact with the shielded pool without viewing/spending keys), then the user's intent debits their intents.near balance irrevocably once signed and settled, while the connector cannot deliver the withdrawal. `describeWithdrawal` has no code path to report this specific failure mode distinctly from ordinary pending state, so an integrator/user has no deterministic signal that the withdrawal is unrecoverable via the SDK. This matches "withdrawal stuck until manual intervention" (High).

### Likelihood Explanation
This requires only an ordinary user (or integrator forwarding a counterparty-supplied `destinationAddress`) to submit a syntactically valid Orchard-only Zcash UA and a Zcash-routed OmniBridge withdrawal with any `feeInclusive` setting; no bridge/relayer/RPC compromise is needed to trigger the format-validation gap itself — the gap is entirely in this repo's `validateZcashUnifiedAddress`. The precondition that *actual delivery failure* occurs depends on the live Omni Bridge connector's real support matrix for Zcash receiver types, which cannot be confirmed purely from this repository's code (this is the untestable, externally-dependent part of the claim).

### Recommendation
In `validateZcashUnifiedAddress`, require a transparent receiver (P2PKH or P2SH) to be present specifically when validating addresses for bridge withdrawal purposes, rather than accepting Orchard-only UAs as satisfying `hasOrchardOrTransparent`. At minimum, `OmniBridge.validateWithdrawal` should perform (or `validateAddress` should expose) a Zcash-specific check that rejects Orchard-only Unified Addresses before signing, since the Omni Bridge connector's actual receiver-type support should be encoded and enforced pre-sign rather than left to a downstream fee-quote call whose failure semantics are not verified in this codebase.

				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
