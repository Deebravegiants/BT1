### Title
BCH legacy address validation skips base58Check checksum, allowing corrupted addresses to pass `validateWithdrawal` - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateBchAddress`'s legacy-address branch matches Bitcoin-style base58 addresses using only a length/charset regex, with no checksum verification, unlike `validateBtcAddress`/`validateBtcBase58Address` which fully decodes and verifies the base58Check checksum. This means a BCH withdrawal to a legacy address with a corrupted checksum (structurally valid base58, wrong hash160) passes validation and gets encoded verbatim into the signed intent.

### Finding Description
The broken equality: "a `destinationAddress` that passes `validateAddress(_, Chains.BitcoinCash)`" should equal "a base58Check address whose checksum matches its payload" — but it doesn't for the legacy branch.

In `packages/intents-sdk/src/lib/validateAddress.ts`, `validateBtcAddress` (used for `Chains.Bitcoin`) calls `validateBtcBase58Address`, which decodes with `base58.decode`, checks length is exactly 25 bytes, and verifies the double-SHA256 checksum byte-by-byte: [1](#0-0) 

In contrast, `validateBchAddress`'s legacy branch only checks the regex `/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/` or `/^3[...]{25,34}$/` and returns `true` immediately — no base58 decode, no length-in-bytes check, no checksum verification at all: [2](#0-1) 

`validateAddress` dispatches `Chains.BitcoinCash` to `validateBchAddress`: [3](#0-2) 

The existing test suite for `validateBchAddress` (`validateAddress.spec.ts`) only tests one bad-checksum legacy case — a wrong version-prefix digit ("1BpEi6DfDAUFd7GtittLSdBeYJvcoaVgg0") — which happens to be rejected only because of the trailing invalid base58 character `0` matching the regex's excluded-character set, not because of checksum logic. There is no test exercising a same-length, same-charset, valid-regex-matching string with a flipped internal byte (bad checksum, e.g. changing one of the middle characters while keeping length and charset valid), so the gap is not caught.

Once `validateWithdrawal` accepts the address, `OmniBridge`'s withdrawal-creation path (`createWithdrawalIntents` → `deriveOmniWithdrawIntentParams`) takes the unmodified `destinationAddress` string and passes it straight to `omniAddress(params.omniChainKind, destinationAddress)` to build the `recipient` field of the intent that is ultimately signed: [4](#0-3) 

No downstream code re-verifies the checksum; `omniAddress` merely wraps the string with a chain-kind prefix for the on-chain contract, it does not decode/validate the base58 payload.

### Impact Explanation
A checksum-corrupted "BCH legacy" address is a string that does not correspond to any real hash160 (it decodes to a payload whose checksum bytes don't match, meaning it isn't a valid Bitcoin/BCH address at all — no wallet or exchange would recognize it as controllable). If a caller (integrator forwarding user-supplied `destinationAddress`, or a solver/counterparty providing one) supplies such a string for a BCH withdrawal, `validateWithdrawal` accepts it, and the SDK proceeds to sign and submit a withdrawal intent whose `recipient` field contains this unusable address. The withdrawn funds are irrecoverably lost — funds delivered to an address that cannot be redeemed on the destination chain, matching the Critical impact category ("funds delivered to a wrong address/chain/contract with no recovery").

### Likelihood Explanation
Preconditions: the withdrawal route must resolve to BitcoinCash (`Chains.BitcoinCash`), and the destination address must use the legacy (`1...`/`3...`) format rather than CashAddr. The attacker/caller cost is trivial — any base58 string of the right length matching the regex charset works; no special privilege is needed, since `validateWithdrawal`/`validateAddress` is reachable by any caller supplying a `destinationAddress`. It's fully repeatable per call. The regex accepts a wide range of invalid strings (25–34 chars of valid base58 charset starting with `1` or `3`), most of which will have an invalid checksum, making an accidental or malicious mistyped/corrupted address highly likely to slip through undetected.

### Recommendation
Make `validateBchAddress`'s legacy branch perform the same decode-and-checksum verification as `validateBtcBase58Address` (decode with `base58.decode`, require exactly 25 bytes, verify version byte is 0x00 or 0x05, and verify the trailing 4-byte double-SHA256 checksum) instead of relying on a bare regex.

### Proof of Concept
```ts
import { describe, expect, it } from "vitest";
import { validateAddress, validateBchAddress } from "./validateAddress";
import { Chains } from "./caip2";

describe("validateBchAddress legacy checksum gap", () => {
  it("accepts a legacy-format address with a corrupted checksum", () => {
    // Valid BTC/BCH legacy address that PASSES full base58Check validation for Bitcoin:
    const validBtc = "1BvBMSEYstWetqTFn5Au4m4GFg7xJaNVN2";
    expect(validateAddress(validBtc, Chains.Bitcoin)).toBe(true);

    // Same length/charset, but a middle character flipped -> breaks the base58Check checksum,
    // while still matching /^1[1-9A-HJ-NP-Za-km-z]{25,34}$/
    const corruptedChecksum = "1BvBMSEYstWetqTFn5Au4m4GFg7xJbNVN2";

    // Confirmed broken as a Bitcoin address (checksum mismatch caught):
    expect(validateAddress(corruptedChecksum, Chains.Bitcoin)).toBe(false);

    // BUG: BCH validation has no checksum check, so it wrongly accepts the same corrupted string
    expect(validateBchAddress(corruptedChecksum)).toBe(true); // should be false
    expect(validateAddress(corruptedChecksum, Chains.BitcoinCash)).toBe(true); // should be false
  });
});
```
This demonstrates the equality violation directly: the identical string is rejected as an invalid Bitcoin address (checksum verified) but accepted as a valid BitcoinCash address (checksum unverified) — confirming `validateBchAddress` legacy branch lacks the checksum guard that `validateBtcAddress` has, and that this unverified string would flow unmodified into `deriveOmniWithdrawIntentParams`'s `omniAddress(...)` call as the signed `recipient`.

```typescript
function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
```

```typescript
export function validateBchAddress(address: string): boolean {
	// Legacy address format (same as Bitcoin)
	if (
		/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address) ||
		/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address)
	) {
		return true;
	}

	// CashAddr format
	return validateBchCashAddr(address);
}
```
