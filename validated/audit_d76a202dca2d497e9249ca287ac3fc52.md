## Analysis

The Tron variant of the Intent Gateway contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, imports and enables OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`) [1](#0-0)  yet the escrow-release path deliberately bypasses it, matching the exact "use `safeTransfer()`" bug class from the report.

### Title
Escrow withdrawal in `IntentGatewayV2.withdraw()` uses raw low-level `IERC20.transfer` call and only checks call success, not the ERC20 return value, allowing silent-failure tokens to permanently lock escrowed/fee funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` (invoked from `onAccept` on `RedeemEscrow`/`RefundEscrow`) and the `SweepDust` branch of `onAccept` both release funds via a raw low-level call to `IERC20.transfer`, checking only the boolean `success` of the call rather than decoding and validating the ERC20 return data.

### Finding Description
In `withdraw()`, for every non-native input token:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same pattern is repeated for the fee-token payout [3](#0-2)  and in the `SweepDust` handler [4](#0-3) .

This only reverts if the external call itself reverts (e.g., no contract code, or the token explicitly reverts). Many real-world ERC20 tokens (older/non-compliant implementations, or tokens with pausing/blacklisting logic) return `false` from `transfer()` instead of reverting when a transfer cannot be completed. In that case `success == true` (the call executed without reverting) even though no tokens moved, so the check passes silently.

Crucially, after this unchecked "transfer," the contract unconditionally advances its internal accounting as if the transfer succeeded:
- `_orders[body.commitment][token] -= amount;` decrements escrow regardless of whether tokens actually reached the beneficiary [5](#0-4) 
- `_filled[body.commitment] = beneficiary;` marks the order as finalized before the loop even runs [6](#0-5) 

This is the same root cause as the referenced Sentiment `Account.sol::sweepTo` finding: relying on a non-reverting `transfer()` call without validating its actual boolean return value. The contract already uses `SafeERC20.safeTransferFrom` elsewhere in the same file for pulling tokens in [7](#0-6) , showing the safe pattern was known and available but not applied consistently to the payout path.

### Impact Explanation
Because `onAccept` is called by the trusted `IsmpHost` after a cross-chain (or `authenticate`d same-instance) settlement message, this path is reachable for every order fill/refund settlement and every dust sweep. If the escrowed/fee token is one that returns `false` on failure instead of reverting (or is later paused/blacklists the beneficiary), the order/escrow state is finalized (`_filled` set, `_orders` decremented) while the tokens never leave the contract. This results in:
- Permanent loss of funds for the intended beneficiary (solver or user), since the order is marked filled/refunded and cannot be retried.
- Tokens becoming permanently stuck/unaccounted for in the `IntentGatewayV2` contract, since the internal escrow ledger no longer reflects their presence.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: the Intent Gateway is designed to be token-agnostic (arbitrary ERC20 `TokenInfo.token` addresses supplied by users/solvers in orders), and non-reverting-on-failure ERC20 semantics are common among deployed tokens (e.g., older non-compliant tokens, or tokens with transfer restrictions such as blacklists/pausability). No privileged action is required — a normal order fill/refund settlement through the standard `RedeemEscrow`/`RefundEscrow`/`SweepDust` flow triggers the vulnerable code.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept` with `IERC20(token).safeTransfer(beneficiary, amount)` (already imported and used elsewhere in the contract via `SafeERC20`), which reverts on both call failure and a `false` return value, ensuring escrow/`_filled` state is only updated when tokens are confirmed to have moved.

### Proof of Concept
1. A user places an order in `IntentGatewayV2` escrowing a non-standard ERC20 token `T` that returns `false` on transfer failure instead of reverting (e.g., `T` implements a blacklist and the intended beneficiary address later gets blacklisted, or `T` is a legacy token like some older USDT-style contracts under certain failure modes).
2. A solver fills the order cross-chain; the `RedeemEscrow` request settles back to the source chain and `onAccept` invokes `withdraw()`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` executes without reverting but the underlying `transfer` call returns `false` (transfer did not occur).
4. `success` is `true`, so the code does not revert; `_orders[commitment][token] -= amount` and `_filled[commitment] = beneficiary` are set as if the payout succeeded.
5. The beneficiary never receives `T`, and the tokens remain irretrievably locked in the `IntentGatewayV2` contract, since the escrow accounting has already been zeroed and the order is marked filled.
