### Title
Unsound escrow accounting for fee-on-transfer tokens in Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the escrow mapping `_orders[commitment][token]` with the user-declared `order.inputs[i].amount` (minus protocol fee), but never verifies that the contract actually received that amount via `safeTransferFrom`. If the input token charges a fee on transfer, the escrow will record more tokens than the contract actually holds, exactly mirroring the "Collateral removal not possible" fee-on-transfer accounting bug from the referenced report.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the requested `order.inputs[i].amount`, not from any measured post-transfer balance delta.

Contrast this with the sibling EVM implementation (`evm/src/apps/IntentGatewayV2.sol`), which snapshots `balanceOf` before and after the transfer and mutates `order.inputs[i].amount` to the actual received amount before computing the commitment and crediting escrow: [2](#0-1) 
That version was specifically patched (and tested, see `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`) to be safe against fee-on-transfer tokens: [3](#0-2) 

The Tron contract's predispatch branch does perform a balance check for dust detection against the call-dispatcher sweep, but even there it stores `reducedInputs[i].amount` (the pre-computed, non-measured value) into escrow rather than the actually swept `balance`: [4](#0-3) 

For the simple (non-predispatch) path, there is no balance measurement at all — the code trusts the nominal transfer amount: [1](#0-0) 

This is directly analogous to the Polynomial `_addCollateral` bug: the protocol adjusts internal accounting (there: position collateral amount; here: escrow balance) using the pre-fee amount instead of the amount actually received by the contract.

### Impact Explanation
If any input token later becomes (or is deployed as) a fee-on-transfer token, every `placeOrder` call using that token will over-credit the escrow ledger relative to the token balance actually held by the `IntentGatewayV2` contract. Because `_orders[commitment][token]` is the value later used to redeem escrow to solvers (via `withdraw`/`RedeemEscrow`) or refund to users (via `RefundEscrow`/`cancelOrder`), the sum of all escrow credits for that token can exceed the contract's actual token balance. This creates an insolvent escrow: some legitimate solver fills or user cancellations will be unable to be paid in full, and whichever withdrawal is processed last will fail or be shorted — a permanent freezing/loss of funds for whoever is left unpaid. This is a fund-safety defect reachable by any unprivileged user simply calling `placeOrder` with a fee-on-transfer ERC20 as input.

### Likelihood Explanation
Likelihood depends on whether a currently-approved input token on the Tron deployment introduces (or already has) a transfer fee — the same precondition as the original report. Since IntentGatewayV2 accepts an open set of ERC20 tokens as `order.inputs` (no protocol-level allow/deny list enforcing "no fee-on-transfer" was found in this excerpt), and the sibling EVM contract was explicitly hardened against this exact scenario, the Tron contract not receiving the same fix is a genuine oversight rather than a deliberately accepted risk. Likelihood is Medium: it requires a token with non-zero transfer fee among supported inputs, which is plausible for stablecoins like USDT-style tokens with governance-controlled fees.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`, use the actual delta as the amount used both to compute `reducedInputs`/commitment and to credit `_orders[commitment][token]`, and do the same for the predispatch sweep path (crediting escrow with the actually-swept `balance` rather than `reducedInputs[i].amount` computed from the nominal amount).

### Proof of Concept
1. Admin/governance approves a fee-on-transfer ERC20 `X` as a valid input token for `IntentGatewayV2` on Tron (or an existing token later turns on a transfer fee, e.g. USDT-style tokens with a fee switch).
2. User calls `placeOrder` with `order.inputs[0] = {token: X, amount: 1000}`.
3. `IERC20(X).safeTransferFrom(msg.sender, address(this), 1000)` transfers 1000 nominal but the contract receives only 990 (1% fee) due to `evm/tron/contracts/apps/IntentGatewayV2.sol:459`.
4. Escrow is nonetheless credited `_orders[commitment][X] += reducedInputs[0].amount` based on the full 1000 (minus protocol fee, if any) at `evm/tron/contracts/apps/IntentGatewayV2.sol:463`, not the 990 actually held.
5. Repeat with multiple orders: the aggregate `_orders[...][X]` values across all commitments exceed `IERC20(X).balanceOf(address(this))`.
6. When solvers fill orders and redeem escrow, or users cancel and request refunds, the last withdrawal(s) for token `X` will revert or be unable to receive the recorded escrow amount because the contract lacks sufficient token balance — freezing/losing funds for those users/solvers.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
