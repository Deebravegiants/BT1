### Title
Backend enrollment/fraud checkpoint bypassed for `user_centric_signup` signups in `do_signup` - (File: src/plans/mod.rs)

### Summary
The Sherlock report describes `emergency_withdraw` skipping `_checkpoint_gauge()` — a protective call made by the normal `deposit`/`withdraw` paths — allowing an alternate code path to bypass a fraud/flash-loan protection. The analogous pattern in `orb-core` is in `MasterPlan::do_signup`: when the QR-provided `user_data.user_centric_signup` flag is `true`, the code takes an alternate branch that computes `success` purely from the locally-derived `signup_reason` and **never calls `self.enroll_user(...)`**, which is the function that performs the actual backend enrollment/dedup/verification checkpoint via `signup_post::request` and `signup_poll` in `src/plans/enroll_user.rs`.

### Finding Description
In `do_signup`, after biometric capture and pipeline processing, the normal signup path calls `enroll_user`, which posts the signup (with `signup_reason`, iris code signature, etc.) to the backend and polls until the backend confirms/denies (dedup, backend-side fraud, legacy checks) via `signup_post::request`/`signup_poll` [1](#0-0) . That backend round-trip is the real "checkpoint" that determines whether a signup is legitimate, non-duplicate, and not backend-flagged as fraud [2](#0-1) .

However, when `user_centric_signup` is `true` (and the orb config does not set `ignore_user_centric_signups`), `do_signup` takes a branch that skips this entire backend enrollment checkpoint and instead derives `success` solely from the local `signup_reason` (which itself depends on locally-computed `detect_fraud`, and in this build `detect_fraud` always returns `false` — "FOSS: WE HAVE DELETED ALL FRAUD CHECKS"): [3](#0-2) 

`detect_fraud` in this codebase is a no-op stub: [4](#0-3) 

The `user_centric_signup` flag itself originates from `orb_qr_link::UserData` returned by the backend/app and is only checked with `user_data.verify(user_data_hash)` (a hash comparison against a QR-embedded hash) rather than being validated through the same server-round-trip checkpoint used in the non-user-centric path: [5](#0-4) 

This mirrors the M-3 root cause exactly: an alternate/"special" execution path (`emergency_withdraw` / `user_centric_signup` branch) legitimately reaches a state-transition point but omits the protective checkpoint call (`_checkpoint_gauge` / `enroll_user`→backend enrollment verification) that all "normal" paths (`deposit`/`withdraw` / the non-user-centric `do_signup` branch) perform.

### Impact Explanation
Skipping `enroll_user` means the backend's own signup verification/dedup/fraud pipeline (`signup_post::request` + `signup_poll`, which the comments explicitly note covers "Backend duplicates," "Backend inflight matches," and "Backend detected fraud") is never consulted for `user_centric_signup` signups [6](#0-5) . Combined with `detect_fraud` being a stub that always returns `false` in this build, a `user_centric_signup` signup can be marked `success = true` and proceed to PCP upload/enrollment-status reporting without any actual backend-side enrollment confirmation or duplicate/fraud check — a misattributed/unauthorized signup outcome analogous to the reward-checkpoint bypass in the report.

### Likelihood Explanation
Reachability depends on whether `user_centric_signup` and the associated `user_data_hash` verification in `src/backend/user_status.rs` can be influenced by an unprivileged party (e.g., a malicious/modified companion app supplying its own `authenticated_app_data`). I could not fully verify the cryptographic strength of `user_data.verify(user_data_hash)` (the `verify` implementation lives in the external `orb_qr_link` crate, not in this repo, so I could not confirm whether it is a signature check tied to a backend-held secret or a simpler hash check an app author could reproduce). This is a material open question that determines whether this is attacker-reachable or purely a backend-trusted, intended code path (in which case it is by design rather than a vulnerability).

### Recommendation
- Confirm in `orb_qr_link::UserData::verify` whether `user_centric_signup` and its associated data are protected by a backend-held signing key inaccessible to app authors; if not, treat this as attacker-reachable.
- Regardless, route the `user_centric_signup` branch through the same backend enrollment checkpoint (`enroll_user` / `signup_post::request`) used by the normal path, or add an equivalent backend confirmation call before setting `result.success = true`, so dedup/fraud verification is never bypassed for any signup path.

### Proof of Concept
Not directly reproducible from the indexed code alone: verification requires exercising `do_signup` with a QR-derived `UserData` where `user_centric_signup == true` and confirming that `enroll_user`/`signup_post::request` is never invoked, while `result.success` is still set to `true` purely from `signup_reason == SignupReason::Normal` [7](#0-6) .
