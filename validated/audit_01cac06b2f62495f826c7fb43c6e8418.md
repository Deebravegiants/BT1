### Title
Uncapped LI.FI router output credited to attacker's UTXO via unlimited approval and unchecked input consumption - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction.callRouter` grants the LI.FI `router` a persistent `type(uint256).max` allowance on `inputToken` via `approveUnlimited`, then forwards fully attacker-controlled `externalActionMetadata` to `router.call(...)` without ever verifying that the router actually consumed exactly `inputAmount` of `inputToken`. `ExternalActionSwap.swap` only measures the *output*-side balance delta (`swappedAmount`) and enforces a floor via `circomData.slippageValues[1]`, but never a ceiling tied to the proof-authorized `inputAmount`. Any residual `inputToken` balance sitting in `ExternalActionSwap` (e.g. left over from an earlier "exact-out"/partial-fill LI.FI route that refunded unused input back to `msg.sender == ExternalActionSwap`) can be pulled by an attacker's own crafted calldata via the still-unlimited approval, inflating `swappedAmount`, which is credited wholesale into the attacker's own new UTXO.

### Finding Description
Equality that must hold: tokens debited from `ExternalActionSwap`'s `inputToken` balance during the `router.call` in `LifiExternalAction.callRouter` must equal `inputAmount` (derived from `-deltaAmounts[0]` proven by the attacker's own proof) [1](#0-0) . Nothing in the code enforces this. `callRouter` only compares `outputToken` balance before/after to derive `swappedAmount`, with no check on how much `inputToken` was actually pulled by the router calldata [2](#0-1) .

Path: `Hinkal.transact -> _externalTransact` transfers `inputAmount` (i.e. `-deltaAmountChanges[0]`) into `ExternalActionSwap` before calling `runAction` [3](#0-2) , then `ExternalActionSwap.swap -> callRouter` re-approves `router` for `type(uint256).max` if the existing allowance is low (persists across calls, never reset to the actual amount) and forwards attacker-controlled `externalActionMetadata` [4](#0-3) . Because the router address is fixed but the calldata is fully attacker-supplied, the attacker can encode a `fromAmount` in the calldata larger than the `inputAmount` that was proof-authorized for this transaction, letting the router's internal `transferFrom` pull additional `inputToken` residing in `ExternalActionSwap`'s balance (e.g. dust from an earlier swap that left unspent input un-swept back to depositors, since `swap()` has no sweep-back/consumption check for `inputToken`).

The resulting inflated `swappedAmount` is used, unchecked against any proof-side cap, to compute `amountToSendToHinkal`, which becomes the new UTXO amount attributed to `circomData.stealthAddressStructure` — fully controlled by the attacker [5](#0-4) . Back in `Hinkal.transact`, the balance-consistency check for the output token only verifies internal self-consistency (`balanceDif == amountChanges[i] + utxoAmount`), where `utxoAmount` is derived from the same runtime-computed, unbounded `utxoSet[j].amount` — it is not tied to any proof-committed expected output, so it always passes regardless of how inflated `swappedAmount` is [6](#0-5) . The only enforced bound is the slippage floor `circomData.slippageValues[1] != 0`/`>=` check, which caps the *minimum*, not the *maximum* output — so the missing ceiling is never caught by existing guards.

### Impact Explanation
An attacker credits themselves shielded value backed by tokens that were never debited from their own proven UTXO input — this is minting shielded value without backing / theft of funds (input-token residue) stranded in `ExternalActionSwap`, which belongs to the protocol/other depositors whose earlier swaps left the leftover behind. This matches the Critical category: direct theft of shielded funds / minting shielded value without backing.

### Likelihood Explanation
Exploitability strictly depends on `ExternalActionSwap` holding a non-zero residual balance of the targeted `inputToken` beyond the current transaction's `inputAmount` at the moment `callRouter` executes. This residual is plausible under normal operation (LI.FI "exact-out"/partial-fill routes commonly refund unspent input to `msg.sender`, i.e. `ExternalActionSwap`, and the contract never sweeps or accounts for that residue), but its existence is not something the current transaction's attacker directly controls — it must already be present from a prior swap. The attack itself costs only gas plus crafting one legitimate-looking deposit/swap proof and router calldata; it is repeatable every time residual balance accumulates.

### Recommendation
- After `router.call(externalActionMetadata)` in `LifiExternalAction.callRouter`, assert that the `inputToken` balance of `ExternalActionSwap` decreased by exactly `inputAmount` (not more, not less), reverting otherwise.
- Replace `approveUnlimited` with a per-call bounded `approveERC20Token(inputToken, router, inputAmount)` that is reset to zero after the call, so router-controlled calldata can never pull more than what was explicitly authorized for that transaction.
- Add an upper bound check on `swappedAmount`/`amountToSendToHinkal` tied to an expected/maximum value passed through `circomData` (in addition to the existing slippage floor).

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a `MockRouter` that supports both a normal "exact swap" path and a "partial-fill" path that only pulls part of the approved input and leaves the rest in the caller (`ExternalActionSwap`).
2. Perform a first legitimate `Hinkal.transact` swap (token A -> token B) whose calldata triggers the partial-fill path on `MockRouter`, leaving `X` tokens of A stranded in `ExternalActionSwap`, and confirm `IERC20(A).allowance(ExternalActionSwap, router) == type(uint256).max` persists.
3. As a second, unrelated attacker, deposit a small real amount of token A, generate a valid proof for `inputAmount = Y`, but craft `externalActionMetadata` for `MockRouter` specifying `fromAmount = Y + X`.
4. Assert `MockRouter` pulls `Y + X` from `ExternalActionSwap` (i.e., `IERC20(A).balanceOf(ExternalActionSwap)` decreases by `Y + X`, not `Y`), and assert the attacker's new UTXO (`utxoSet[0].amount`) reflects the swap of `Y + X`, not `Y` — i.e., `swappedAmount` (and the credited UTXO) is strictly greater than what `-deltaAmounts[0]` authorized, proving the equality `tokens pulled by router == inputAmount authorized by proof` is broken and value is stolen without being counted against the attacker's proof.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
