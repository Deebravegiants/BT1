### Title
GetResponse delivery on gargantua bypasses the bandwidth gate despite the code documenting it as enforced - (File: parachain/runtimes/gargantua/src/ismp.rs)

### Summary
`ProxyModule::on_accept` meters every non-purchase `PostRequest` through `BandwidthGate::try_consume` before crediting bytes against the `(source, app)` subscription ledger [1](#0-0) . `ProxyModule::on_response`, which handles inbound `GetResponse` delivery, carries a comment stating it "mirrors the request path in `on_accept`" for the bandwidth gate, but the function body never calls `try_consume` — it only checks destination and dispatches to the callback module [2](#0-1) . This is structurally the same bug class as CVE-2019-9849: one message/resource type (`GetResponse`) is silently exempted from a metering/protection control that the documentation and analogous code path assert applies uniformly.

### Finding Description
The bandwidth model is designed so that "every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`" [3](#0-2) , and the runtime's `on_accept` implements exactly that, computing `bytes = encode_post_request(&request).len()` and deducting from the app's subscription before allowing the request through [4](#0-3) . The `on_response` handler for `GetResponse` messages contains a comment explicitly claiming equivalent enforcement ("Bandwidth gate. Mirrors the request path in `on_accept`... the chain and module that produced the response pay for the bytes they deliver"), yet the actual code performs no `try_consume` call at all — it only gates on `response.dest_chain()` and then dispatches to `pallet_ismp_demo`'s `on_response` callback [2](#0-1) . Every `GetResponse` reaching this host is therefore delivered for free, regardless of the size of the storage-value payload, with no subscription check, no allowlist requirement, and no accounting event (`BandwidthConsumed` is never emitted for responses).

### Impact Explanation
This breaks the intended economic/DoS-resistance invariant of the bandwidth subsystem: GET response delivery — which can carry arbitrarily large batches of `StorageValue`s across many keys — completely bypasses the per-app byte metering that the rest of the protocol relies on to price and rate-limit inbound traffic. An app (or any unprivileged actor who can get a relayer to submit `GetRequest`/`GetResponse` pairs bound for this module) can drive unlimited free response-delivery bandwidth through this host with no subscription purchase, undermining the sponsorship/quota model documented for the pallet and creating an unmetered resource-consumption/griefing vector.

### Likelihood Explanation
`GetRequest`/`GetResponse` are ordinary ISMP primitives dispatchable by any unprivileged application; no privileged role is needed. The gap is triggered automatically on delivery of any `GetResponse` addressed to the `pallet_ismp_demo` module (or any module wired into this match arm going forward) — there is no special crafting required beyond dispatching a normal GET request and having its response delivered, which is the standard, expected flow.

### Recommendation
Add the same `is_purchase_message`-style bandwidth-gate check to `ProxyModule::on_response`, computing the encoded response size and calling `BandwidthGate::try_consume(&response.source_chain(), &response.get.from, bytes)` before dispatching to the destination callback, mirroring the `on_accept` implementation, and gated the same way behind the `no-bandwidth` feature flag.

### Proof of Concept
1. Register a `BandwidthManager` and configure a tier as in the normal flow; do **not** purchase any subscription for the target app.
2. From a source chain, dispatch a `DispatchGet` request targeting a large number of storage keys, addressed (via `from`) to a module id matching `pallet_ismp_demo::PALLET_ID` on the gargantua-based host.
3. Have a relayer deliver the `GetRequest` and subsequently the `GetResponse` (via `ResponseMessage`/`handle` in `modules/ismp/core/src/handlers/response.rs`) to the runtime.
4. Observe that `ProxyModule::on_response` processes and dispatches the response successfully with no `BandwidthConsumed` event and no `GateError::NoAllowance`/`Insufficient` rejection, even though `Allowance` for `(source, app)` is empty — demonstrating the gate is never consulted for this message type, in contrast to the identical scenario using `on_accept` for a `PostRequest`, which correctly reverts with `bandwidth gate: no bandwidth allowance`.

```text
## The Gate

Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.
```
