### Title
Missing decompression size limit in `unzipIcon` allows a zip-bomb DoS via unvalidated `getIcon`/`#fetchIcon` token-registry path - ([File: adapters/storage-icons-mobile/src/icons-storage.js])

### Summary
`unzipIcon` in both the mobile and browser icon-storage adapters calls `pako.ungzip`/`zlib.gunzip` on attacker-influenced base64 data with no upper bound on the decompressed output size, and `cleanup()`/`validate()` in `@exodus/svg-safe` only run *after* decompression has already completed. Critically, the `AssetsModule#fetchIcon` path calls `iconsStorage.unzipIcon(token.icon)` directly on a token fetched from the remote custom-token registry (CTR) **without** running it through `validateCustomToken`/`isValidCustomToken` first, bypassing the icon `maxLength` schema check that protects the other call sites (`addRemoteTokens`, `fetchToken`, `#fetchTokens`, `#fetchUpdates`).

### Finding Description
`unzipIcon` is implemented identically in intent across adapters: [1](#0-0) 
and [2](#0-1) 

Neither implementation caps the decompressed size before handing the result to `cleanup()`/`validate()`: [3](#0-2) 
`validate()` itself only performs structural tokenization/regex checks and does not reject based on length; it will happily iterate a multi-hundred-MB string once it's already been allocated by `ungzip`.

The normal write paths to `storeIcons` (`addRemoteTokens`, `fetchToken`, `#fetchTokens`, `#fetchUpdates`) all pass fetched tokens through `validateCustomToken`/`isValidCustomToken` (from `@exodus/asset-schema-validation`) before calling `#storeIcons`: [4](#0-3) [5](#0-4) 
Per the package changelog, this schema includes an `icon` field length cap (`increase maxLength validation for CT icons`, #15748), which bounds the *compressed/base64 input size* reaching `unzipIcon` on these paths.

However, `#fetchIcon` (used by `getIcon()` when an asset has not yet been added/cached) fetches a token from the CTR `tokens` endpoint and calls `unzipIcon` directly on `token.icon`, with **no call to `validateCustomToken`/`isValidCustomToken`** in between: [6](#0-5) 
This is exercised by the existing test `getIcon when asset is not added`, which shows the exact call chain `getIcon -> #fetchIcon -> iconsStorage.unzipIcon(token.icon)` with a raw token straight from the mocked registry response: [7](#0-6) 

Because this path skips the icon `maxLength` schema gate, a malicious/compromised CTR response (or any registry the wallet queries for token metadata search/lookup) can supply an arbitrarily large base64 gzip blob as `icon`, which `pako.ungzip(arr, { to: 'string' })` will decompress fully into memory before any size or validity check occurs.

### Impact Explanation
A single malicious token response returned from the custom-token registry search/lookup flow can cause `unzipIcon` to allocate an unbounded decompressed string in the wallet process. Gzip/deflate can achieve compression ratios well over 1000:1, so even a moderately sized malicious payload can balloon into hundreds of megabytes to gigabytes in memory, causing memory exhaustion, severe slowdown, or a crash of the wallet application/process (mobile OOM kill, browser extension background page crash). This is a device-level availability impact rather than key/secret compromise, matching a memory-exhaustion DoS bounty category.

### Likelihood Explanation
Reaching this path requires the wallet to call `getIcon()` for a token name that is not already a locally-known asset (triggering the memoized `#fetchIcon` fallback which fetches directly from the CTR `tokens` endpoint), which is a normal flow when searching/browsing/looking up unregistered custom tokens by name. No privileged wallet state, unlock, or user interaction beyond a token search/lookup is required. This assumes the registry response (or a MITM/compromised CDN in front of it) can be attacker-influenced with the malicious `icon` payload; this is the same "remote/API response" trust boundary explicitly called out as in-scope by the audit preconditions.

### Recommendation
- Enforce a hard cap on decompressed size directly inside `unzipIcon` (both mobile and browser adapters), e.g., pass an output size limit to `pako.ungzip`/stream-based `gunzip` and abort/throw if exceeded, independent of any upstream schema check.
- Route the `#fetchIcon` result through the same `validateCustomToken`/`isValidCustomToken` (or at minimum an icon-length-only) check used by `addRemoteTokens`/`fetchToken`/`#fetchTokens`/`#fetchUpdates` before calling `iconsStorage.unzipIcon`.
- Add a maximum SVG string length assertion in `cleanup()`/`validate()` in `@exodus/svg-safe` as defense in depth, so any future caller that forgets pre-validation is still protected.

### Proof of Concept
Unit test plan for `features/assets-feature/module/assets-module.js` `#fetchIcon`/`getIcon`:
1. Mock `fetch` to return a token for `searchedtoken` whose `icon` is a base64-encoded gzip blob crafted to decompress to e.g. 500MB (a zip bomb, e.g. gzip of a repeated character string).
2. Call `assetsModule.getIcon('searchedtoken')`.
3. Assert that `iconsStorage.unzipIcon`/`pako.ungzip` is invoked with no length guard and that decompression proceeds to completion (in a sandboxed test, mock `ungzip` to report the requested output length and assert it exceeds a safe threshold, e.g. > 10MB, without being rejected).
4. Contrast with `addRemoteTokens`/`fetchToken`, where the same crafted token is rejected/logged as `Invalid Custom Token schema` due to `validateCustomToken`'s icon `maxLength` check, demonstrating the `#fetchIcon` path uniquely bypasses this protection.
Expected assertion for the fix: `unzipIcon` (or `#fetchIcon`) throws/rejects once the base64-decoded buffer or decompressed size exceeds a defined maximum, before `cleanupSVG`/`validateSVG` are invoked.

```javascript
export const unzipIcon = async (base64) => {
  const buff = Buffer.from(base64, 'base64')
  const unzip = await new Promise((resolve, reject) => {
    gunzip(buff, (err, res) => {
      if (err) {
        reject(err)
        return
      }

      resolve(res)
    })
  })
  return cleanup(unzip.toString('utf8'))
}
```
