This confirms the analog: `ShopifyAPI::Webhooks::Registry.process` at [1](#0-0)  validates HMAC integrity of the raw body only, then forwards `request.shop` — sourced directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — as the tenant identity to the app's webhook handler via `WebhookMetadata`. The HMAC's signable string is defined as just the raw body [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled independently from headers that are never part of the signature computation [3](#0-2) .

### Title
Webhook tenant identity (`shop` header) is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , so the HMAC computed by `Utils::HmacValidator.validate` in `Registry.process` [4](#0-3)  only proves the body bytes were signed by Shopify with the app's secret — it says nothing about which shop the signature was issued for. The `shop` value handed to the host app's handler is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header [5](#0-4)  and passed unchecked into `WebhookMetadata` [6](#0-5) .

### Finding Description
The gem verifies "bytes signed" (`raw_body` + HMAC) but the host application acts on "bytes parsed as tenant" (`shop` header field), and these two are not bound together. Because Shopify computes the HMAC exclusively over the body using the app's `client_secret`, and body content for a given topic can be identical or attacker-influenced (e.g., an attacker installs the app on their own shop, and Shopify sends a validly-HMAC-signed webhook for a resource with attacker-controlled body content, e.g. product title/note fields), an attacker who controls where they can relay a raw HTTP request (e.g., a malicious proxy, a misconfigured shared webhook endpoint across shops, or an app that reuses the same secret/handler across multiple installations) can present a validly-signed `raw_body` while substituting a different `shopify-shop-domain` header. `Registry.process` performs no cross-check that the `shop` header matches any identity actually embedded in the signed payload, and the equality "shop used for tenant routing == shop the HMAC signature was computed for" is never enforced.

### Impact Explanation
If the host app trusts `WebhookMetadata#shop` as the tenant boundary for storing/retrieving data (as recommended in the gem's own documentation example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [7](#0-6) ), a spoofed `shop` header combined with a validly-HMAC'd body causes the app to attribute and process webhook data under the wrong tenant — a cross-tenant data integrity/confusion issue, since the identity binding (shop claimed vs. shop actually authenticated by the signature) is broken.

### Likelihood Explanation
Exploitability depends on an attacker's ability to control or replay the raw HTTP request reaching the app's webhook endpoint with an arbitrary `shop` header while keeping a validly-signed body (e.g., via a proxy/CDN that doesn't lock headers, a shared webhook URL misconfiguration, or an attacker's own shop installation generating a legitimately-signed payload that is then replayed with a different shop header). This requires some ability to manipulate request headers en route to the app, which is a plausible unprivileged-adjacent scenario for apps handling raw webhook headers without a reverse proxy that strips/re-sets them from a trusted source.

### Recommendation
Bind the `shop` (and `topic`/`webhook_id`) into the signable string the HMAC is computed over, or otherwise verify the `shop` header against Shopify's known origin/IP allowlist, and document that host apps must not trust the `shop` header without further protections. At minimum, the gem should compute the HMAC over a canonical representation that includes the `shop-domain` header alongside the raw body, matching Shopify's actual signing behavior server-side, or the gem should explicitly document this limitation to callers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `products/update`) with attacker-chosen body content, receiving a validly-signed request: `raw_body=B`, `hmac=HMAC(secret, B)`, header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker relays/forwards this exact request to the app's webhook endpoint but rewrites the `shopify-shop-domain` header to `victim-shop.myshopify.com` (the HMAC is unaffected since it only covers `raw_body`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3) , which succeeds because it only checks `raw_body` against the HMAC, per `to_signable_string` [2](#0-1) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, despite the signature never having attested to `victim-shop.myshopify.com`.
