### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `#shop` (and `#topic`, `#webhook_id`, `#api_version`) come from HTTP headers that are never included in the HMAC computation. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler, breaking the equality "shop whose bytes were HMAC-verified" == "shop attributed to the event."

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [3](#0-2) . For webhooks, `to_signable_string` is defined as just `@raw_body`: [4](#0-3) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are not part of the signed bytes: [5](#0-4) .

`Registry.process` raises only if the HMAC over the body fails, then immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, etc., and dispatches it to the app-supplied handler as verified data: [6](#0-5) .

Because `Context.api_secret_key` is a single per-app secret shared across every installed shop (the same secret Shopify uses to sign webhooks for *any* store that has the app installed), any user who installs the app on a store they control receives legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pairs signed with that shared secret. Since the shop-domain header is outside the signed bytes, that same valid `(raw_body, hmac)` pair can be resent to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to an arbitrary victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes against the secret; `Registry.process` then calls the handler with `WebhookMetadata.shop` set to the forged victim domain: [7](#0-6) .

The docs instruct app authors that `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "the shop domain of the webhook," to be used directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [8](#0-7) [9](#0-8) . So this is the gem's documented API contract being broken by its own implementation, not host-app misuse.

### Impact Explanation
An unprivileged attacker who is merely a legitimate installer of the app on their own shop can forge webhook events attributed to any other shop domain string of their choosing, with a body of their own construction (as long as they control the body/signature pairing they captured from their own store's real webhooks, or any body for which they can obtain a validly-signed pair). Any app logic keyed off `data.shop` — e.g., updating per-shop billing/plan state, marking a shop's subscription/webhooks status, triggering shop-scoped background jobs, or writing to a shop-keyed data store — can be manipulated to act against a victim tenant's identity. This is a cross-tenant identity confusion primitive at Critical severity per the rules (cross-tenant access via broken shop-identity binding).

### Likelihood Explanation
Requires no access to `api_secret_key`, access tokens, or credentials beyond what any unprivileged user gets by installing the app on their own store — installing an app is a normal, unprivileged action. Capturing one's own legitimately-delivered webhook `(raw_body, hmac)` and replaying it with a modified `X-Shopify-Shop-Domain` header is trivial and requires no special access.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id/api-version) into the signed payload used for HMAC verification, or independently verify the shop domain against a known-installed-shop list/session store before trusting `request.shop`. At minimum, `to_signable_string` should not be the sole basis for trusting header-derived identity fields that `Registry.process` forwards as verified `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged action) and receives a real webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid per `HmacValidator.validate` since `H = HMAC(client_secret, B)`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint, replacing the shop header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B` against `H` [10](#0-9) [4](#0-3) .
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop = "victim-shop.myshopify.com"` and dispatches it to the app's handler as an authenticated event for the victim shop [11](#0-10) .

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```

```ruby
        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
```
