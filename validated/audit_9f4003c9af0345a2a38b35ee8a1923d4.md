### Title
Unlimited router approval + attacker-controlled calldata lets any residual/parked action balance be redirected off-accounting - (File: contracts/external-actions/swaps/ExternalActionSwap.sol / LifiExternalAction.sol)

### Finding Description
The invariant the protocol relies on is: *tokens leaving the action contract in a transaction == `-deltaAmountChanges` Hinkal sent it that transaction*. `ExternalActionSwap.swap` only measures this via a balance delta on the **output** token: [1](#0-0) 

`swappedAmount = balanceAfter(outputToken) - balanceBefore(outputToken)`, taken immediately around the `router.call(externalActionMetadata)`. There is **no check anywhere that the router only consumed `inputAmount` of `inputToken`**. Before the call, the contract grants the router unlimited (not amount-scoped) allowance: [2](#0-1) 

`approveUnlimited(inputToken, router)` sets the router's allowance on the action's *entire* balance of `inputToken`, not just `inputAmount`. `externalActionMetadata` is fully attacker-controlled calldata forwarded verbatim to `router.call`, and it is not validated by `performHinkalChecks`, `dimensionsCheck`, or any circuit constraint — the circuit only constrains `-deltaAmounts[0]` (declared spend) and the on-chain slippage floor on `swappedAmount`, never the amount the router actually pulls from the action's balance, nor the destination the router sends output to.

Because LI.FI/aggregator swap calldata typically lets the caller specify (a) the amount to pull via `transferFrom`/generic-swap facets and (b) an arbitrary output `receiver`, an attacker who knows (or can seed in the same block) that the action contract holds a residual/parked balance of a token — e.g. surplus output tokens left behind by an earlier partial swap/refund, or leftover input-token dust — can craft `externalActionMetadata` so the router:
1. pulls more than `inputAmount` of `inputToken` from the action (using the unlimited allowance, consuming the stranded balance too), and/or
2. sends the swap output directly to an attacker-chosen address instead of back to the action contract.

In case (1), `swappedAmount` (and thus the attacker's own UTXO built from `amountToSendToHinkal`) includes value derived from stranded funds that were never accounted for by `-deltaAmounts[0]`. In case (2), value leaves the action/router flow entirely outside the `swappedAmount`/UTXO accounting, so it is not reflected as `-deltaAmountChanges` at all, and no invariant check catches it because `swap()` never verifies input-token balance drawn down, nor that all router output landed back at `address(this)` before being redistributed.

Existing guards do not prevent this: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the circuit's `inTotal + amountChanges === outTotal` constrain only the shielded-side bookkeeping supplied by the attacker's own proof — they never constrain what the router does with the *actual* token balance sitting in the shared, stateful action contract, nor do they scope the router's ERC20 allowance to `inputAmount`.

### Impact Explanation
An unprivileged attacker can drain any token balance parked/stranded in the `ExternalActionSwap`/`LifiExternalAction` contract (from a prior partial refund, rounding dust, or any other user's in-flight state left in the same block) by crafting `externalActionMetadata` that instructs the router to consume more than the attacker's declared `inputAmount` and/or reroute output to themselves. This is direct theft of protocol/relay- or other users'-in-flight funds parked in the action contract, matching the Critical category "direct theft of shielded or in-flight user funds." It is repeatable any time residual balance exists in the action contract.

### Likelihood Explanation
Preconditions: the action contract must hold a nonzero residual balance of some ERC20/ETH from a prior transaction (partial refund, dust, or leftover in-flight state within the same block). Attacker cost is a single normal `Hinkal.transact` call with self-crafted `externalActionMetadata`; no special privilege is required, and the attacker fully controls the router calldata field. The feasibility hinges on the router (LI.FI diamond/aggregator) accepting calldata that pulls more than the intended `inputAmount` or redirects output — a realistic property of generic-swap/aggregator facets that take amount/receiver from calldata. Given the unlimited (not scoped) approval and total absence of an input-side balance check in `swap()`, this is a code-level gap in this repo, not merely a router defect.

### Recommendation
- Scope the router approval to exactly `inputAmount` (approve-and-reset, not `approveUnlimited`), and reset it to zero after the call.
- Record `inputToken` balance before/after the router call and require the balance decrease equals exactly `inputAmount` (revert otherwise), so any consumption of pre-existing/residual balance is detected and rejected.
- Ensure swap output is only ever measured/used if it lands at `address(this)`; do not trust attacker-chosen receiver fields in aggregator calldata — if the router/aggregator API permits an arbitrary receiver, enforce/overwrite it to `address(this)` where possible or restrict which router selectors are callable.
- Sweep/track any pre-existing balance explicitly (e.g., only ever operate on balances attributable to the current transaction) rather than relying solely on the output-token delta.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router that mimics a generic-swap facet: it accepts calldata specifying `(tokenIn, amountIn, tokenOut, amountOut, receiver)` and performs `transferFrom(action, router, amountIn)` then sends `amountOut` of `tokenOut` to `receiver`.
2. Seed residual state: directly transfer extra `inputToken` (or `outputToken`, using `inputToken == outputToken`) into the action contract to simulate a stranded/parked balance left from a prior transaction in the same block.
3. Have the attacker call `Hinkal.transact` (or directly `runAction`, using the allowed-recipient path) with `deltaAmounts[0] = -inputAmount` (their genuine declared spend) but with `externalActionMetadata` crafted to make the mock router pull `inputAmount + residualAmount` (permitted by `approveUnlimited`) and either (a) return more output into the action and let it flow into `utxoSet[0].amount`, or (b) set `receiver = attackerEOA` directly.
4. Assert: `tokens actually leaving action-contract balance != -deltaAmountChanges` (i.e., attacker's `utxoSet[0].amount` or `attackerEOA` balance increase exceeds what corresponds strictly to `inputAmount`), proving the invariant `tokens leaving == -deltaAmountChanges` is broken and the residual/stranded balance was captured by the attacker.
