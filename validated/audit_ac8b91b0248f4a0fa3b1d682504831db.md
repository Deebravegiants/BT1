Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC only to the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers and passed to the app's webhook handler as trusted tenant/context identity. Because a single app-wide `client_secret` (`Context.api_secret_key`) is used to compute the HMAC for every shop that has the app installed, an entity that controls one legitimate installation can capture a genuine `(body, hmac)` pair and replay it with a forged `shopify-shop-domain` header to impersonate a different shop, since that header is never part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` using `Context.api_secret_key`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unsigned HTTP headers: [3](#0-2) 

`Registry.process` only checks the body HMAC and then forwards the unverified `request.shop` value to the app's handler as the authoritative tenant identity: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop acted upon by the handler`. In this implementation that equality is broken — `shop` (and `topic`/`webhook_id`) are acted upon (routed to handlers, used as tenant key in `WebhookMetadata`) but are not part of the HMAC-covered bytes. Since `Context.api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop key), a valid HMAC on a given body proves only "this body was signed by Shopify for some install of this app," not "this body belongs to shop X."

### Impact Explanation
An attacker who controls one legitimate installation of the app (a normal unprivileged action — installing a public/embedded app requires no special credential) can capture a real webhook delivery `(raw_body, hmac)` issued for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header to name a victim shop. `Utils::HmacValidator.validate` will accept it because it only checks the body, and `Registry.process` will dispatch the forged data to the handler tagged with the victim shop's identity via `WebhookMetadata`. Depending on how the host application uses `WebhookMetadata#shop`/`#topic` (e.g., to look up per-shop records, trigger data writes, or invalidate/update tenant state), this allows cross-tenant data confusion/corruption — the handler processes attacker-supplied content while believing it originated from, and applies it to, a different merchant's tenant. This matches the Critical "cross-tenant access" impact category, since the tenant binding (shop) that the rest of the library and downstream app code relies on is forgeable.

### Likelihood Explanation
Likelihood is meaningful but not universal: it requires (1) an attacker to have (or create) a legitimate installation of the target app to obtain a genuine `(body, hmac)` sample, and (2) the host application to key sensitive per-tenant behavior off `WebhookMetadata#shop`/`#topic` without independent verification (e.g., checking the shop against an existing session/tenant record before trusting the payload). Both preconditions are common in typical Shopify app architectures, since the library's own documented contract (`Utils::HmacValidator.validate(request)` + `WebhookMetadata`) presents `shop`/`topic` as already-authenticated fields to the handler, encouraging trust.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable material for webhook requests (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp`), or otherwise document/enforce that consumers of `WebhookMetadata` must independently verify `shop` against a known/authorized tenant before acting on it. At minimum, the library should not present these header-derived fields as verified once `HmacValidator.validate` succeeds.

### Proof of Concept
1. App has two shops installed, `attacker.myshopify.com` (attacker-controlled) and `victim.myshopify.com`.
2. Shopify sends a genuine webhook for `attacker.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over body>`.
   - Body: `{"id": 123, ...}`.
3. Attacker captures `raw_body` and the valid `hmac` value (both attacker-visible, since it's their own shop's webhook).
4. Attacker replays the identical `raw_body` and `hmac` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (i.e., `raw_body` only) using the app's single `Context.api_secret_key` — this succeeds because the body is unchanged: [5](#0-4) 
6. The registered handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {...}, ...)` — attacker-controlled content is now processed under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
