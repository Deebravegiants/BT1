This confirms the core mechanics: the docs explicitly state the app's handler is meant to trust `data.shop` from the webhook (`docs/usage/webhooks.md` lines 12-14, 25) as "the shop domain of the webhook," while `ShopifyAPI::Webhooks::Registry.process` claims that calling `Utils::HmacValidator.validate(request)` "will verify the request did indeed come from Shopify" (line 125) — but the HMAC only covers the raw body, not the shop header.

### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a specific shop once `Utils::HmacValidator.validate(request)` succeeds, and hands `request.shop` straight to the app's handler as the trusted tenant identity. However, the HMAC signature only ever covers the raw request body — the `shop-domain` header is read out-of-band and is never part of the signed material. Any HTTP request bearing a valid `(body, hmac)` pair accepted for one shop can be replayed with an arbitrary `x-shopify-shop-domain` header, and the library will report it to the app as coming from that arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is instead read directly from an unauthenticated header, independent of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `to_signable_string` (i.e., the body) against the secret — it never mixes in `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` uses HMAC success as the sole authentication gate, then forwards the unauthenticated `request.shop` (and `topic`/`webhook_id`/`api_version`) to the app's handler as if it were verified: [4](#0-3) 

The documentation for both the `Registry.process` call and the handler contract makes explicit that `data.shop` is expected to be the authenticated tenant identity that hosting applications should trust and key their per-shop data on:
- "This will verify the request did indeed come from Shopify..." (`docs/usage/webhooks.md` line 125)
- "`shop`, `String` - The shop domain of the webhook" (`docs/usage/webhooks.md` line 14)

Since the shop identity is never part of the signed payload, the equality the library implicitly claims — `shop authenticated == shop stored/reported to the app` — does not hold. `api_secret_key` is shared across every shop that has installed a given app; **any** shop that installs the app can obtain a validly HMAC-signed `(body, hmac)` pair for its own webhooks (e.g. by triggering `orders/create` on its own store). Because the header carrying the shop identity is excluded from the signed bytes, that same `(body, hmac)` pair remains valid when replayed with a different `x-shopify-shop-domain` header pointing at any other shop using the same app, letting an unprivileged app-installing user forge webhook events that the host application will attribute to a victim tenant.

### Impact Explanation
This breaks the binding "bytes verified versus bytes parsed" / "shop authenticated versus the shop stored as a session key": the bytes cryptographically verified (raw body) do not include the shop identity that is subsequently parsed and trusted (`request.shop`). Any app-based logic that uses `data.shop` to select which tenant's data to create/update/delete based on webhook content (the documented and recommended usage pattern) can be manipulated by one tenant to inject or corrupt data attributed to another tenant — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Exploitation only requires installing the target app on an attacker-controlled shop (or in some app models, being any user who can trigger webhook-eligible events on a shop that has the app installed), capturing one legitimately signed webhook body+hmac, and replaying it against the app's webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header. No access to `api_secret_key`, access tokens, or any privileged account is required beyond ordinary installation of the (typically publicly installable) app.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the material that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the signed body (e.g., include the shop domain in the signable string, or cross-check the shop against a value obtained from a channel that is itself authenticated, such as an existing active session for that exact webhook path). At minimum, document prominently that `request.shop`/`data.shop` is **not** cryptographically authenticated and must not be trusted as a tenant-scoping key without additional verification (e.g., confirming the shop has a currently active, previously-established session/installation record) — but note this weakens the security guarantee applications currently rely on based on the library's own documentation and current API surface.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (apps are typically installable by any Shopify merchant).
2. Attacker triggers a webhook event they control (e.g. updates a product to fire `products/update`), and captures the raw POST body and the `X-Shopify-Hmac-SHA256` header Shopify sends to the app's webhook endpoint — this HMAC is valid because it's computed with the app's single, shared `api_secret_key`: [5](#0-4) 
3. Attacker replays that exact `(raw_body, hmac header)` pair directly to the app's public webhook route, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the forged header: [2](#0-1) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the secret — it never inspects `shop`: [6](#0-5) 
6. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, and the host application — following the library's documented contract — processes/persists this attacker-controlled data as if it were an authentic event from `victim.myshopify.com`.
