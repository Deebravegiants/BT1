### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields used downstream by the app's handler are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands the handler a `WebhookMetadata` struct whose `shop` value was never covered by that HMAC, breaking the binding `HMAC-authenticated payload == shop attributed to that payload`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, which are not part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header using the app's single, shop-agnostic `api_secret_key`: [3](#0-2) 

`Registry.process` validates only that HMAC, then dispatches to the handler using `request.shop` as the trusted shop identity for that payload: [4](#0-3) 

Because the `api_secret_key` used to sign webhooks is the same for every shop that installed the app (it is not per-shop), any party that can obtain one valid `(raw_body, hmac)` pair for their own store's webhook delivery — for example a merchant/dev who installed the app on a store they control — can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds, because it only checks the body against the secret; the header is never fed into the signature. The handler consequently receives a `WebhookMetadata.shop` value that is completely attacker-controlled while believing the payload came from Shopify authenticated for that shop.

This is the same root-cause shape as the `LamboFactory` report: a check (`HMAC valid` / `pair doesn't exist yet`) is performed on one thing while a security-relevant, causally-linked field (`shop` / `pool identity`) is allowed to be attacker-controlled and unbound from that check.

### Impact Explanation
If a host application uses `WebhookMetadata.shop` (as documented and demonstrated in the gem's own usage docs and tests) to route data to the correct tenant/shop record — e.g., to invalidate a session, update billing state, process `app/uninstalled`, or write order/customer data — an attacker can force the app to process an HMAC-"verified" webhook under an arbitrary victim shop's identity. This is a cross-tenant identity confusion: the app is misled into believing data originated from, or should be applied to, a shop it did not actually originate from, despite passing the gem's own cryptographic check.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimate `(raw_body, hmac)` pair, which is trivial for anyone who can install the app on a store they control (a very low bar for public/free apps) or who can otherwise capture one delivered webhook. No access to `api_secret_key` or any access token is required — only replay of an intercepted or self-generated webhook delivery with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC verification, not just the raw body — e.g., by including the shop domain in `to_signable_string`, or by cross-checking `request.shop` against an independently known/expected shop for the webhook subscription (such as the shop that registered that specific webhook ID) before invoking the handler, and by treating webhook headers as untrusted until corroborated by data already scoped to the resolved session/shop.

### Proof of Concept
1. App installs `ExampleApp` on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery for topic `orders/create` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays this exact request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — this succeeds because the header value never entered the signature.
4. The registered handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., data from the attacker's own shop is now processed under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
