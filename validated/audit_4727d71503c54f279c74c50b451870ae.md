### Title
`AuroraEngineBridge.validateWithdrawal` never checks the destination address against the token's own address, unlike every other bridge — ([File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts])

### Summary
Every bridge implementation in the SDK (`DirectBridge`, `HotBridge`, `OmniBridge`, `PoaBridge`) enforces the equality check `compareAddresses(tokenAddress, destinationAddress)` inside `validateWithdrawal()` and rejects the withdrawal with `DestinationAddressMatchesTokenAddressError` when the two match. `AuroraEngineBridge.validateWithdrawal` only validates the address *format* and omits this check entirely, so a caller can build a withdrawal whose `destinationAddress` equals the bridged token's own contract/proxy address.

### Finding Description
`AuroraEngineBridge.validateWithdrawal` at [1](#0-0)  only checks address format:
```
async validateWithdrawal(args: {...}): Promise<void> {
    if (validateAddress(args.destinationAddress, Chains.Ethereum) === false) {
        throw new InvalidDestinationAddressForWithdrawalError(...);
    }
    return;
}
```
It never compares `destinationAddress` against the token's own address, unlike its sibling bridges:
- `DirectBridge.validateWithdrawal` [2](#0-1) 
- `HotBridge.validateWithdrawal` [3](#0-2) 
- `OmniBridge.validateWithdrawal` [4](#0-3) 
- `PoaBridge.validateWithdrawal` [5](#0-4) 

All four use `compareAddresses()` [6](#0-5)  to break the equality "destination == token contract" and reject it via `DestinationAddressMatchesTokenAddressError`, and each has dedicated tests confirming this ("blocks withdrawals of token to it's address"), e.g. [7](#0-6) . The Aurora Engine bridge has no such test and no such guard, and its `createWithdrawIntentPrimitive()` [8](#0-7)  will happily encode a `ft_withdraw` intent whose `msg` deposit target (`makeAuroraEngineDepositMsg`) is the proxy/base token's own address on the virtual chain.

This mirrors the reported bug class: an equality that is enforced on other code paths ("recipient must not be blacklisted" enforced, but "sender must not be blacklisted" silently skipped) is missing here — "destination != token address" is enforced by every bridge except this one.

### Impact Explanation
Depositing an ERC-20 (or native) token to its own contract address on the destination virtual chain, via the Aurora Engine deposit mechanism, typically has no valid receiver logic to credit the balance — the funds land in the token contract itself with no `transfer`/`mint` credit to any account. This is the exact "stuck funds until manual intervention" scenario the sibling bridges guard against (as evidenced by their `DestinationAddressMatchesTokenAddressError` checks and tests). Because `AuroraEngineBridge` skips this validation, funds routed through `RouteEnum.VirtualChain` can become irrecoverably stuck at the token's own address on the Aurora Engine-powered chain.

### Likelihood Explanation
This can be triggered by any caller of `IntentsSDK.createWithdrawalIntents` / `processWithdrawal` who selects `RouteEnum.VirtualChain` and sets `destinationAddress` equal to the underlying token's contract address (a plausible user/integrator mistake, or something a malicious front-end could set on a user's behalf), since no validation blocks it — whereas the identical mistake is caught and rejected on every other route.

### Recommendation
Add the same equality check used by the other bridges to `AuroraEngineBridge.validateWithdrawal`: resolve the token/proxy-token address for the route (`args.withdrawalParams.routeConfig.proxyTokenContractId` or the parsed asset's underlying address) and compare it against `args.destinationAddress` with `compareAddresses()`, throwing `DestinationAddressMatchesTokenAddressError` on a match, consistent with `DirectBridge`, `HotBridge`, `OmniBridge`, and `PoaBridge`.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents({ withdrawalParams: { assetId: "nep141:<token>.near", amount, destinationAddress: "<the ERC-20/base token's own address on the virtual chain>", routeConfig: createVirtualChainRoute(...) }, feeEstimation })`.
2. `AuroraEngineBridge.validateWithdrawal` only checks `validateAddress(destinationAddress, Chains.Ethereum)`, which passes because the token's own address is a syntactically valid Ethereum address [9](#0-8) .
3. Compare with the equivalent call on `OmniBridge`/`HotBridge`/`PoaBridge`/`DirectBridge` with `destinationAddress` set to the token's own address: those calls reject with `DestinationAddressMatchesTokenAddressError` (see their respective `*.test.ts` "blocks withdrawals of token to it's address" cases), while `AuroraEngineBridge` proceeds to build and submit the `ft_withdraw` intent, sending funds to the token's own address with no recovery path.

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	auroraEngineContractId: string;
	proxyTokenContractId: string | null;
	destinationAddress: string;
	amount: bigint;
	storageDeposit: bigint;
}): IntentFtWithdraw {
	const { contractId: tokenAccountId, standard } = utils.parseDefuseAssetId(
		params.assetId,
	);
	assert(standard === "nep141", "Only NEP-141 is supported");

	// Most cases
	if (params.proxyTokenContractId == null) {
		return {
			intent: "ft_withdraw",
			token: tokenAccountId,
			receiver_id: params.auroraEngineContractId,
			amount: params.amount.toString(),
			msg: makeAuroraEngineDepositMsg(params.destinationAddress),
			storage_deposit:
				params.storageDeposit > 0n
					? params.storageDeposit.toString()
					: undefined,
			min_gas: MIN_GAS_AMOUNT,
		};
	}

	//  Flow for transferring a base token to a virtual chain with a non-standard (non-ETH) base token
	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: params.proxyTokenContractId,
		amount: params.amount.toString(),
		msg: `${params.auroraEngineContractId}:${makeAuroraEngineDepositMsg(params.destinationAddress)}`,
		storage_deposit:
			params.storageDeposit > 0n ? params.storageDeposit.toString() : undefined,
		min_gas: MIN_GAS_AMOUNT_NON_STANDARD_DECIMALS,
	};
}
