This confirms the vulnerability. The `WebhookMetadata` struct passed to the host app's `handle(data:)` callback includes `shop`, `topic`, `webhook_id`, and `api_version` — all sourced from HTTP headers [1](#0-0) . `Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and then, without any further binding, builds `WebhookMetadata` directly from the same `request.shop`, `request.topic`, `request.webhook_id` header accessors [2](#0-1) . But the HMAC signature only ever covers the raw JSON body — `Webhooks::Request#to_signable_string` returns `@raw_body` alone [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated headers [4](#0-3) .

### Title
Webhook `shop` identity is not bound by the HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values used to build the `WebhookMetadata` dispatched to the host application's handler are taken from HTTP headers that are never part of the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` checks `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is derived solely from `verifiable_query.to_signable_string` [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body`, i.e. only the JSON body bytes [3](#0-2) .

`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [2](#0-1) 

`request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are read from the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` headers (or their `x-shopify-` equivalents) [4](#0-3) [6](#0-5) . None of these header values are included in `to_signable_string`, so the HMAC only proves that the *body* came from Shopify — it proves nothing about which shop, topic, or webhook the body is attributed to.

This breaks the equality that the host application relies on: `shop-domain header value == shop that produced/owns this signed body`. Because only the body is bound by the signature, an attacker who can replay or forward a validly-signed request (e.g. one previously delivered to their own shop, or a body they otherwise obtain) can freely swap the `shopify-shop-domain` header to an arbitrary victim shop domain, and `Registry.process` will still pass HMAC validation and dispatch a `WebhookMetadata` claiming to be from the victim shop. Any host application logic that uses `data.shop` from the handler callback to select the tenant record, look up per-shop state, or gate access, is fed an attacker-controlled, unauthenticated value that is presented as if it were verified.

### Impact Explanation
This is a cross-tenant identity-binding break: the field host applications are expected to trust as an authenticated tenant identifier (`WebhookMetadata#shop`) is not covered by the same signature that is checked before dispatch. Since the gem explicitly performs "the" verification step (`Utils::HmacValidator.validate(request)`) and then hands the caller a `shop` value implied to be verified alongside the body, downstream apps that don't independently re-verify `shop` against their own webhook subscription/shop registry can be tricked into processing webhook data under the wrong tenant identity — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires the attacker to have at least one validly HMAC-signed raw body (trivial for topics like their own shop's webhooks, since any Shopify merchant/app owner receives correctly-signed webhooks for their own shop) and the ability to submit an HTTP request to the app's webhook endpoint with a modified `shopify-shop-domain` header — both are available to an unprivileged internet user/merchant without any Shopify credentials, access tokens, or `client_secret`. This does not require breaking the HMAC itself, only exploiting that the signature doesn't cover the header used for tenant attribution.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the value that is HMAC-verified (or otherwise cryptographically bind them to the raw body before signature computation), so that `to_signable_string` cannot be satisfied by mixing a validly-signed body with attacker-chosen header values. At minimum, document/require that host applications must independently verify the `shop-domain` header against a known/authorized shop record before trusting `WebhookMetadata#shop`, since the gem itself does not bind it.

### Proof of Concept
1. Attacker installs/owns their own shop `attacker-shop.myshopify.com` and receives a legitimately-signed webhook, e.g. for `orders/create`, with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid HMAC of {"id":1}>`.
2. Attacker resends the exact same raw body to the victim host app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` while leaving the HMAC header untouched.
3. `Webhooks::Request.new` accepts the request (only checks for header presence, not header content) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC purely from `@raw_body` and succeeds, since the body was unmodified [8](#0-7) .
5. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {"id"=>1}, ...))` to the host app, which believes this data is authenticated as belonging to `victim-shop.myshopify.com` [9](#0-8) .
