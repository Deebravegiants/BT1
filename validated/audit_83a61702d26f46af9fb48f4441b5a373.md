### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the raw `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `Registry.process` only covers the raw request body, never the `shop` header. This breaks the identity binding `hmac_signed_bytes == bytes_the_app_acts_on`: the bytes that are cryptographically verified (body only) are not the bytes used to identify which shop/tenant the webhook belongs to (the header).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads directly from an attacker-controllable header, with no cryptographic binding to the body or its HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then passes `request.shop` straight into the `WebhookMetadata` handed to the host app's handler, treating it as an authenticated tenant identifier: [4](#0-3) 

`Utils::HmacValidator.validate` only compares an HMAC computed over `verifiable_query.to_signable_string` (i.e., the raw body for webhooks) against the header-supplied `hmac` value; it never incorporates the `shop` header into the signed material: [5](#0-4) 

Because the HMAC is computed solely from `secret + body`, any two webhook deliveries with byte-identical bodies produce byte-identical valid HMACs regardless of which shop they originate from. An attacker who legitimately installs the app on their own shop (or otherwise obtains one genuine `(body, hmac)` pair, e.g. via a topic with attacker-controlled/predictable body content) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the host app's handler with `shop: <victim-shop>`, `topic`, and `body: <attacker-controlled-or-replayed-content>` — data the app will treat as an authenticated event coming from the victim tenant.

### Impact Explanation
This is a cross-tenant confusion vulnerability: the gem hands the host application data purportedly from the victim shop, without any cryptographic assurance that the body actually originated for that shop. Any host application that uses `WebhookMetadata#shop` (as documented/intended) to key persistence, trigger tenant-scoped side effects (e.g., updating a customer record, redacting data for `customers/redact`, uninstall handling, order create side effects) is exposed to cross-tenant data corruption or disclosure, since the gem provides no guarantee binding `shop` to the verified bytes. This matches the Critical class "cross-tenant access."

### Likelihood Explanation
Requires only an internet-reachable app that has webhooks enabled and at least one attacker-controlled or replayable webhook body from any tenant (including the attacker's own shop, which is unprivileged relative to any other merchant's tenant). No access token, `client_secret`, or victim credentials are needed — the header is simply a plaintext, application-supplied string the gem never authenticates.

### Recommendation
Bind the tenant identity into the verified material: include the `shop-domain` header (and other identifying headers such as `topic`/`api-version`) in the string that is HMAC-verified, or validate that Shopify's actual delivery-signing scheme (which Shopify computes over the raw body only, by design) is paired with a secondary sender/tenant authentication mechanism before handing `shop` to the handler — e.g., document/verify that the raw body itself always carries a shop identifier that is cross-checked against the header before use, or reject processing when the two disagree. At minimum, the gem should not present `request.shop` to consumers as if it were a value covered by `Utils::HmacValidator.validate`.

### Proof of Concept
1. App installs the webhook handler for `orders/create` (or any topic with static/attacker-influenced JSON body).
2. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and triggers a webhook, capturing the genuine `raw_body` and its `x-shopify-hmac-sha256` value (both delivered to the attacker's own endpoint, hence not requiring any victim secret).
3. Attacker POSTs to the app's public webhook endpoint with the *same* `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request object [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the secret [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: ..., ...)` [8](#0-7) , causing the host app to process attacker-supplied data as if it belongs to the victim tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
