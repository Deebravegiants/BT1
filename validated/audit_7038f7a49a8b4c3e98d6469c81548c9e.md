## Finding

Shopify webhook signature verification in this gem covers only the raw HTTP body — the `shop-domain` header used to attribute a webhook to a specific merchant is never part of the signed content. Since a single app's `api_secret_key` is shared across *every* store that installs the app, any user who installs the app on their own store can capture a genuinely-signed `(raw_body, hmac)` pair and replay it against the same webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop. `Registry.process` will accept the HMAC as valid and hand the attacker-chosen body to the app's handler, tagged with the victim's shop.

### Root cause

`HmacValidator.validate` only verifies the HMAC over `to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body — it does not include the shop, topic, or webhook-id headers: [2](#0-1) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read directly from unauthenticated headers: [3](#0-2) 

`Registry.process` checks only the HMAC, then unconditionally forwards `request.shop` (an unverified header) to the app's handler as the attributed tenant: [4](#0-3) 

The identity binding that should hold is:
`shop covered by verified HMAC == shop attributed to the processed webhook`

but in reality:
`shop covered by verified HMAC (none) != shop attributed to the processed webhook (request.shop header)`

### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, excluding the `shop-domain` header. `HmacValidator.validate` therefore only proves the body was signed with the app's `api_secret_key` — it proves nothing about which shop the body belongs to. `Registry.process` nonetheless treats `request.shop` as trustworthy and passes it straight through to the application's webhook handler.

### Finding Description
Shopify signs webhooks with the app's `client_secret`, which is identical for every shop that has the app installed. Because the shop identifier lives only in the `x-shopify-shop-domain` header and that header is excluded from the HMAC input (`@raw_body` only, see `to_signable_string`), a valid `(body, hmac)` pair generated by *any* installation of the app can be replayed with a different `shop-domain` header value, and `HmacValidator.validate` will still return `true`. `Registry.process` performs no additional check that `request.shop` corresponds to the shop that actually produced the signed payload, so the handler receives attacker-controlled `shop` + `body` under a fully "verified" HMAC.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce: an app relying on `WebhookMetadata#shop` to decide which merchant's data to update, delete, or sync will act on the wrong tenant using attacker-supplied body content. This is a cross-tenant access issue reachable from any user who can install the target app on their own store (a standard, unprivileged action) and then hits the merchant's public webhook endpoint directly.

### Likelihood Explanation
Any unprivileged user can create a Shopify dev/partner store, install the target public app to receive real signed webhooks, capture a `(raw_body, hmac)` pair from a webhook topic whose body they can influence (e.g., a webhook fired as a result of their own store actions), and then POST it to the app's public webhook endpoint with the victim's `x-shopify-shop-domain` header substituted in. No secrets, tokens, or privileged access are required.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable content used for HMAC verification, or otherwise cryptographically bind the verified body to the `shop-domain` header before it is handed to registered handlers — e.g., only trust `request.shop` when it can independently be tied to the specific webhook subscription/shop that was registered for that topic, rather than relying solely on a body-only HMAC that is valid across all installs of the app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com`.
2. Attacker triggers a webhook topic they control content for (e.g. `orders/create` with attacker-authored order data), and captures the raw request Shopify sends to the app's webhook endpoint, including `x-shopify-hmac-sha256` and body.
3. Attacker resends this exact body and HMAC header to the same app endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the shared `api_secret_key`: [5](#0-4) 
5. The app's handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and processes it as if it legitimately originated from the victim shop.
