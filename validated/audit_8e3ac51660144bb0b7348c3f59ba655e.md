### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field the HMAC signature never covers — and hands it to the app's handler as the authoritative tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read directly from the `shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes [2](#0-1) . `Registry.process` validates only that HMAC-over-body [3](#0-2) , and then builds `WebhookMetadata` directly from the unverified header value and passes it to the app-supplied handler [4](#0-3) .

This is the same bug class as the report's `unit`/curve mismatch: a value that is *acted upon* (here, the tenant identity `shop`) is decoupled from the value that was *actually verified* (the HMAC, which binds only the raw body). The equality that should hold — `shop authenticated by HMAC == shop the app acts on` — is broken because the HMAC binds nothing about `shop` at all.

Because a single app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant who legitimately installs the app can capture a genuinely-signed `(raw_body, hmac)` pair from their own store's webhook traffic. That HMAC remains valid for `Utils::HmacValidator.validate` regardless of which shop-domain header accompanies it, since `validate_signature` only recomputes over `to_signable_string` (the body) [5](#0-4) . Replaying that exact body with an arbitrary `X-Shopify-Shop-Domain` header value (e.g. a victim shop) passes verification and delivers attacker-controlled data labeled as belonging to another tenant.

The gem's own documentation instructs developers to treat `data.shop` as ground truth and pass it straight into downstream processing/queuing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) , so this is not a case of the host app ignoring documented API — it is following it exactly as written.

### Impact Explanation
This enables cross-tenant confusion: an attacker with a legitimate install of the app on their own shop can produce a request that the gem authenticates as "valid Shopify webhook" while spoofing the `shop` field to any other myshopify domain. Any downstream logic that keys tenant-scoped operations (data updates, cache invalidation, notifications, provisioning, deprovisioning triggers, etc.) off `data.shop` operates on the wrong tenant's record, using attacker-supplied body content. This matches the "Critical - cross-tenant access" category since it lets one tenant inject verified-looking events attributed to another tenant.

### Likelihood Explanation
Requires only that the attacker be a legitimate merchant/user of the target app (a normal, unprivileged app install) — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. Capturing one's own valid `(body, hmac)` pair and replaying it with a modified header is straightforward given the gem never binds `shop` into the signed payload.

### Recommendation
Do not trust the `shop-domain` header as an implicit identity claim. At minimum, extend `Utils::HmacValidator`/`Request#to_signable_string` design (or the `process` flow) to cross-check the header-derived shop against an app-side registry of shops the handler currently expects, or document/require handlers to independently verify `data.shop` against their own installed-shop store before treating the payload as authoritative — mirroring how `dest`/`aud` are bound and checked inside the signed JWT payload elsewhere in this gem (`lib/shopify_api/auth/jwt_payload.rb`).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and legitimately receives a webhook, capturing `raw_body` and the valid `X-Shopify-Hmac-Sha256` value computed by Shopify with the app's shared `client_secret`.
2. Attacker POSTs the identical `raw_body`/HMAC pair to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the signature only over `raw_body` and succeeds [3](#0-2) .
4. `WebhookMetadata.new(shop: request.shop, ...)` sets `shop` to `victim-shop.myshopify.com` from the unverified header [4](#0-3) .
5. The app's handler, following the documented pattern, processes attacker-controlled `data.body` as if it were an authentic event for `victim-shop.myshopify.com`.
