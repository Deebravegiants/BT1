### Title
Webhook shop identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's webhook handler with the shop identity taken from the request. In reality, the HMAC signature computed by `Utils::HmacValidator.validate` only covers the raw request body, not the `shop`, `topic`, `webhook_id`, or `api_version` fields that are read from unauthenticated headers and handed directly to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then builds `WebhookMetadata` directly from unauthenticated header values, including `request.shop`: [3](#0-2) 

`request.shop` is read straight from the `shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC: [4](#0-3) 

The identity binding the gem's own documentation promises is:
`HMAC-verified request == (body, shop, topic, webhook_id, api_version)` used by the handler

but the actual binding enforced is only:
`HMAC-verified bytes == raw_body`

Because `shop` (and `topic`/`webhook_id`/`api_version`) sit outside the signed bytes, any party who can produce one valid `(raw_body, hmac)` pair — trivially available to an attacker who is a legitimate merchant/installer of the app and therefore legitimately receives real webhook deliveries for their own shop — can replay that exact `raw_body` + `x-shopify-hmac-sha256` value to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it never inspects the shop header, and `Registry.process` will call the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain while the body content is the attacker's own shop's data.

### Impact Explanation
This breaks the identity binding between the cryptographically verified payload and the shop the host application will apply that payload to, letting an attacker who controls one legitimately-signed webhook cause the application to process/store data under an arbitrary victim shop identity — a cross-tenant confusion inside the receiving app driven purely by this gem's verification contract. This maps to the Critical "cross-tenant access" impact category, since the gem is the layer solely responsible for asserting "this webhook is authenticated for shop X," and that assertion is false as implemented.

### Likelihood Explanation
Any app built with this gem exposes a public HTTP endpoint per the documented `docs/usage/webhooks.md` pattern, and the exploit only requires: (1) install the target app on an attacker-owned shop to receive one genuine `(body, hmac)` pair, and (2) POST it directly to the app's webhook route with a forged `x-shopify-shop-domain` header — no access token, `client_secret`, or privileged credential is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the bytes that are HMAC-verified, or otherwise cryptographically bind the header-derived `shop` value to the verified request (e.g., verify shop against an independently maintained list of shops with active app installations before trusting `WebhookMetadata.shop`), rather than trusting the unauthenticated header value.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for secret known only to Shopify/the app).
2. POST to the app's webhook route (per `docs/usage/webhooks.md` example) with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-shop-domain: victim.myshopify.com`
   and body `B` unchanged.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, returns `true` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the app handler with `WebhookMetadata` where `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the app to associate the attacker-supplied body with the victim tenant.
