### Title
Cross-account secret key material access via unscoped `seedId` parameter in `cachedSodiumEncryptor` RPC surface - ([File: features/cached-sodium-encryptor/module/cached-sodium-encryptor.ts])

### Summary
The `cachedSodiumEncryptor` RPC feature exposes `encryptSecretBox`, `decryptSecretBox`, `encryptBox`, and `decryptBox` directly to any SDK caller with no origin, active-account, or consent binding. Any caller can supply an arbitrary `seedId` string (for any unlocked seed present in the keychain, not just the currently active/connected account) and obtain ciphertext/plaintext derived from that other seed's `WALLET_INFO`/`FUSION` key material.

### Finding Description
The RPC surface is created via `createRpcFeature('cachedSodiumEncryptor', api)` [1](#0-0)  which registers the module methods verbatim as the public API with no wrapping authorization layer [2](#0-1) . The API definition simply forwards `cachedSodiumEncryptor.encryptSecretBox/decryptSecretBox/encryptBox/decryptBox` unchanged [3](#0-2) .

The underlying methods accept a `params` object validated only by a zod schema requiring `keyId` and `seedId: z.string()` with no relation to caller identity, active wallet, or origin [4](#0-3) . Inside `CachedSodiumEncryptor`, `#getPrivateKey` only checks that `keyId` is in `ALLOWED_KEY_IDS` (`WALLET_INFO`, `FUSION`) via `#checkIfAllowed`, but performs no check on `seedId` against the currently unlocked/active account [5](#0-4) . It then calls `this.#keychain.exportKey({ keyId, seedId, exportPrivate: true })` directly with the attacker-supplied `seedId` [6](#0-5) , caches the resulting private key keyed only by `(keyId, seedId)` cache key, and uses it to encrypt/decrypt/box arbitrary attacker-supplied data [7](#0-6) .

Nowhere in this call chain (RPC feature → API → module) is there a check binding `seedId` to the requesting origin, the currently active/connected wallet account, or any consent/approval step. As long as the target `seedId` corresponds to a seed already present/unlocked in the keychain (e.g., an "extra seed" added alongside the primary), an unprivileged caller of the exposed RPC method can derive/use its `WALLET_INFO` or `FUSION` key material.

### Impact Explanation
This allows encrypting or decrypting data (and box operations) using the secret key material of a seed/account that is not the one the caller/dapp is scoped or connected to, violating "consent is explicit and scoped." Since `WALLET_INFO` protects secure-storage data (tx-history, address cache, NFTs, etc.) and is described in comments as unlocked once for the app's lifetime and never re-locked, this enables cross-account secret material use without any account-selection or consent gate at the RPC layer, matching a wrong-account access impact class. The exposure is scoped to keys allowed by `ALLOWED_KEY_IDS` (`WALLET_INFO`, `FUSION`) rather than raw seed/signing keys, since `#checkIfAllowed` restricts `keyId`.

### Likelihood Explanation
Exploitability requires only: (1) the RPC surface being reachable by an unprivileged caller (dapp bridge or headless SDK caller), and (2) multiple seeds already existing/unlocked in the keychain (e.g., primary + an added extra seed) — both plausible preconditions per the question. No additional privilege, key leak, or social engineering is required; the call is a single direct RPC invocation with attacker-controlled `seedId`.

### Recommendation
Bind `seedId` resolution to the caller's authorized/active account context at the RPC boundary (or inside `CachedSodiumEncryptor`), rejecting requests where the supplied `seedId` does not match the currently active/connected account for the requesting origin, or require an explicit consent/approval step before honoring a `seedId` targeting a non-active account.

### Proof of Concept
Unit test plan (extending `features/cached-sodium-encryptor/module/cached-sodium-encryptor.test.ts`):
1. Construct a keychain mock with two seeds unlocked: `activeSeedId` (currently connected/active) and `otherSeedId` (an unrelated "extra seed").
2. Instantiate `CachedSodiumEncryptor` with this keychain, without wiring in any active-account/origin context.
3. Call `cachedSodiumEncryptor.encryptSecretBox({ seedId: otherSeedId, keyId: EXODUS_KEY_IDS.WALLET_INFO, data })`.
4. Assert the call succeeds and that `keychain.exportKey` was invoked with `seedId: otherSeedId`, `exportPrivate: true`, with no prior check comparing `otherSeedId` to an "active account" value — confirming absence of account-scoping/consent enforcement before `exportKey` is reached.
