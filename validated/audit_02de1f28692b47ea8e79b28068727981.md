The webhook HMAC in this gem is computed only over the raw request body (`request.to_signable_string` returns `@raw_body`), while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from HTTP headers that are never included in the HMAC-signed material. `Registry.process` treats a valid body-HMAC as authentication for the *entire* `WebhookMetadata` (including `shop`), and hands that unauthenticated `shop` value to the app's handler.

### Title
Webhook `shop` (and topic/api_version/webhook_id) identity is not bound by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` in `Registry.process` verifies solely the JSON body's integrity/authenticity. The `shop`, `topic`, `api_version`, and `webhook_id` fields come from HTTP headers (`shopify-shop-domain`, etc.) that are outside the HMAC computation, yet `Registry.process` forwards them, unauthenticated, as trusted identity inside `WebhookMetadata` to the app's `WebhookHandler#handle`.

### Finding Description [1](#0-0) 
`shop`, `topic`, `api_version`, `webhook_id` are all derived from headers via `shopify_header`, while `to_signable_string` (used as the HMAC message) returns only `@raw_body`. [2](#0-1) 
`Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`, which hashes only `@raw_body`) and, on success, immediately trusts `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` to build `WebhookMetadata` passed to the handler — i.e., the equality the code implicitly assumes is `HMAC-verified-body == HMAC-verified-(body+shop+topic+...)`, which does not hold. [3](#0-2) 
`WebhookMetadata.shop` is what app code (e.g. `shopify_app`-based handlers) uses to select the tenant/session to act on, so this field must be identity-bound, but it isn't.

Because the HMAC secret (`Context.api_secret_key`) is shared by Shopify across all shops that installed the app, a party who legitimately controls one shop with the app installed can capture a genuine webhook delivery (valid body + valid HMAC) sent to their own endpoint, then replay the identical body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with another shop's domain. The signature check still passes because the signature never covered those headers, so the app processes attacker-chosen data under a victim shop's identity.

### Impact Explanation
This breaks the tenant identity binding — HMAC-authenticated bytes (body only) versus the identity actually acted upon (`shop` header) — leading to cross-tenant data confusion: a handler that persists/acts on `data.body` keyed by `data.shop` will apply another merchant's shop's install "trusted" payload to the attacker-chosen victim shop, since the gem asserts the webhook is valid before handing over an unauthenticated `shop`. This matches the Critical "cross-tenant access" impact category since app logic keyed on `WebhookMetadata.shop` after a passed HMAC check would treat forged/replayed cross-tenant data as authentic.

### Likelihood Explanation
Requires only that the attacker operate their own shop/installation of the target app (an unprivileged, ordinary merchant action — no `api_secret_key`, token theft, or privileged access needed) and be able to capture and replay HTTP requests to the app's public webhook endpoint with modified headers, which is standard HTTP tooling. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → `WebhookMetadata.new(shop: request.shop, ...)`) is always exercised for every registered HTTP webhook handler.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material verification path (Shopify's actual webhook signature only covers the body per their spec, so instead the header-derived `shop` should be cross-checked against out-of-band trusted state, e.g., require the app to independently verify that the delivered `shop` corresponds to a session/install the app expects for that specific webhook subscription, or document/enforce that consumers must not treat `WebhookMetadata.shop`/`topic`/`webhook_id` as authenticated by `Registry.process` alone). At minimum, update `Utils::HmacValidator`/`Request#to_signable_string` documentation and `Registry.process` to make explicit that only the body is authenticated, and provide a way to bind the delivery to the specific webhook subscription (e.g., correlate `webhook_id` against a server-side registry per shop) before acting on `shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets it receive a legitimate webhook, e.g. `orders/create`, capturing the raw POST: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`), and other headers.
2. Attacker resends the exact same body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds because the shop header was never part of the signed content [4](#0-3) .
4. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)` is passed to the app's handler, which now processes attacker-controlled body content as though it were an authentic delivery from `victim-shop.myshopify.com` [5](#0-4) .
