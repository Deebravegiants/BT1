### Title
Missing invalidation of `_requestCommitments[commitment].fee` in `EvmHost.dispatchIncoming(GetResponse)` allows repeated relayer-fee payout for the same GET response - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse memory response, address relayer)` pays out the relayer fee escrowed in `_requestCommitments[commitment]` on every successful delivery of a GET response, but never deletes or zeroes that entry afterward. Every other "consume once" delivery path in the same contract (`dispatchTimeOut(GetRequestTimeout,...)` and `dispatchTimeOut(PostRequestTimeout,...)`) explicitly `delete`s `_requestCommitments[commitment]` as its replay-protection step before paying anything out. The GetResponse delivery path is the one place that skips this, leaving stale fee-escrow state that a repeated delivery of the exact same response can read and pay again — the analog of a use-after-free primitive: state that should have been "freed" (invalidated) after first consumption is instead reused on a subsequent call.

### Finding Description
In `dispatchIncoming(GetResponse memory response, address relayer)`: [1](#0-0) 

only `_responseReceipts[commitment]` is written (unconditionally overwritten, with no revert-on-existing check) before the external call to the destination module; on success the function then reads `_requestCommitments[commitment].fee` and transfers it to `relayer` via `IERC20(feeToken()).safeTransfer`, but `_requestCommitments[commitment]` is never deleted.

Compare this with the sibling timeout paths in the same contract, which treat the same mapping as consumed exactly once: [2](#0-1) [3](#0-2) 

Both timeout handlers `delete _requestCommitments[commitment]` up front specifically for "replay protection", and only restore the entry if the module callback fails (so it can be retried). `dispatchIncoming(GetResponse,...)` has no equivalent invalidation step for the fee it is about to spend.

The Rust core, by contrast, treats this exact bug class as a first-class concern: `handlers/response.rs` and `handlers/timeout.rs` contain explicit "re-check right before dispatch" and "delete to prevent reentrancy" guards precisely because a prior request/response in the same batch (or a reentrant call) can otherwise cause double-processing: [4](#0-3) [5](#0-4) 

`EvmHost.dispatchIncoming(GetResponse,...)` has no equivalent protection for the value it pays out: the only replay-relevant field written before the call, `_responseReceipts[commitment]`, does not gate the fee transfer at all — it only records who last delivered — and it is overwritten unconditionally rather than checked and reverted-on-conflict.

### Impact Explanation
Whenever `dispatchIncoming(GetResponse,...)` is invoked more than once for the same commitment with a still-valid membership proof (e.g., a relayer resubmits a GET response whose proof verifies against a state commitment/height that Hyperbridge still stores, or the destination module's `onGetResponse` implementation does not itself defend against being invoked twice for the same request), the `_requestCommitments[commitment].fee` is read and paid out again because it was never cleared. This directly drains fee-token funds held by `EvmHost` to the relayer, i.e., concrete theft of escrowed protocol/user funds, which is one of the accepted impact classes (concrete theft of funds).

### Likelihood Explanation
The function is `restrict(_hostParams.handler)`, so it can only be reached through `HandlerV2`'s GET-response delivery path, and I was unable to fully confirm within the available search budget whether `HandlerV2` itself deduplicates against `_responseReceipts` before calling `dispatchIncoming` for a given commitment. What is confirmed directly from `EvmHost.sol` is that the host-level defense that exists everywhere else in this contract for "consume-once" state (`delete _requestCommitments[commitment]` before payout) is absent specifically in this function, so `EvmHost` itself provides no guarantee against double payout if it is ever called twice for the same commitment (via handler-level replay, a lenient/duplicate proof submission, or a reentrant `onGetResponse` callback in an app that fails to guard reentrancy). Given the deliberate, documented reentrancy hardening applied to the analogous Rust paths, and the explicit "replay protection" comments on the sibling Solidity timeout functions, the omission here looks like an inconsistency in an area the codebase otherwise treats as security-critical.

### Recommendation
Delete (or zero) `_requestCommitments[commitment]` before making the external `onGetResponse` call in `dispatchIncoming(GetResponse,...)`, mirroring the pattern already used in `dispatchTimeOut(GetRequestTimeout,...)` and `dispatchTimeOut(PostRequestTimeout,...)`: consume the fee-escrow entry up front, and only restore it if the callback fails, so a second delivery of the same commitment can never re-read a stale fee. Additionally, check `_responseReceipts[commitment]` for a prior delivery and revert (rather than silently overwrite) if one exists, so `HandlerV2` cannot cause a double payout even if it does not itself dedupe.

### Proof of Concept
1. A relayer submits a valid `GetResponse` for request `R` (commitment `C`) through `HandlerV2` → `EvmHost.dispatchIncoming(response, relayer)`. `_requestCommitments[C].fee = F` is read and `F` is transferred to `relayer`; `_requestCommitments[C]` is left unchanged (not deleted).
2. The relayer (or any actor able to trigger the same code path again for `C`, e.g., a duplicate proof/message referencing the same still-valid state commitment, or via `onGetResponse` reentering the handler) causes `EvmHost.dispatchIncoming` to be invoked again for commitment `C`.
3. Because `_requestCommitments[C].fee` still equals `F`, the fee-transfer branch fires again, paying `F` a second time out of the host's fee-token balance, at direct expense of other users' escrowed fees. [1](#0-0)

    /**
     * @dev Dispatch an incoming GET response to source module
     * @param response - get response
     */
    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
