### Title
LP share/withdrawal ratio can be driven to a near-zero `lp_amount` floor and then inflated via direct vault donation, enabling a share-price manipulation attack against later depositors - (File: `program/src/processor.rs`)

### Summary
`process_withdraw` guarantees `amm.lp_amount` can never reach zero, but it *can* be driven down to `1` (the minimum non-zero value). Once at that floor, an attacker can inflate the accounting ratio used for `Deposit`/`Withdraw` by transferring tokens directly into the AMM's coin/pc vaults (a plain SPL transfer, not routed through the program's `Deposit` instruction), because `total_pc_without_take_pnl`/`total_coin_without_take_pnl` are computed straight from the vaults' live token-account balances. This is the same root-cause class as the referenced report: an accounting ratio (assets ÷ "supply") becomes attacker-controllable and severely distorted when the "supply" side (`amm.lp_amount`) is pushed to a minimal value.

### Finding Description
`process_withdraw` explicitly forbids fully draining LP supply, but not down to the smallest non-zero unit: [1](#0-0) 
This means an attacker who owns (or accumulates) nearly all LP tokens can withdraw everything except `1` unit, leaving `amm.lp_amount == 1`.

The `Deposit` and `Withdraw` instructions convert between LP units and underlying tokens using `InvariantPool`, keyed off `amm.lp_amount` as the "supply" and `total_coin_without_take_pnl`/`total_pc_without_take_pnl` as the "assets": [2](#0-1) [3](#0-2) 

Crucially, `total_coin_without_take_pnl`/`total_pc_without_take_pnl` are derived from the *actual* SPL token account balances of the coin/pc vaults (`amm_coin_vault.amount`, `amm_pc_vault.amount`), which are read directly from on-chain token account state: [4](#0-3) 
Because the vaults are ordinary SPL token accounts owned by the AMM's PDA authority, anyone can increase their balance with a plain `spl_token::transfer` instruction that never touches the AMM program's deposit accounting/lp minting path. This lets an attacker inflate `total_coin_without_take_pnl`/`total_pc_without_take_pnl` while `amm.lp_amount` stays at `1`.

With `amm.lp_amount = 1` and vault balances inflated by direct donation, the ratio `assets / lp_amount` becomes extreme, mirroring the "inflated ratio when totalSupply() is very low" bug class in the reference report — except here the analog impact is not "denial of fees" but a share-price/first-depositor style manipulation: a subsequent legitimate depositor's `mint_lp_amount` computed via `exchange_token_to_pool(amm.lp_amount, RoundDirection::Floor)` rounds toward zero unless their deposit exceeds the inflated total, and if it does, the attacker's single remaining LP unit now represents a large, disproportionate claim on the pool relative to what the attacker actually contributed, which can then be redeemed through `process_withdraw`'s proportional payout logic.

### Impact Explanation
If exploitable, this allows an attacker to either (a) grief/DoS deposits into a low-supply pool by making `mint_lp_amount` round to zero (deposit instruction rejects `mint_lp_amount == 0` at `program/src/processor.rs:1323`), or (b) extract a disproportionate share of a subsequent depositor's contributed assets by owning the dust `lp_amount == 1` position against an artificially inflated vault balance, then withdrawing proportionally once new liquidity dilutes/re-balances the LP count. This is a fund-safety issue for LPs, not merely a fee-accounting inconvenience.

### Likelihood Explanation
I was not able to fully verify one mitigating factor within the available search budget: `calc_take_pnl` (invoked in both `Deposit` and `Withdraw`) subtracts a "pnl" component from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` before the LP-ratio math runs, and it is derived from `target_orders.calc_pnl_x`/`calc_pnl_y`. I could not confirm from the snippets retrieved whether this mechanism fully absorbs/neutralizes any donated balance as "pnl" owed to the admin sink (via `process_withdrawpnl`) before it can affect the LP conversion ratio, which would reduce or eliminate the practical exploitability of the donation vector described above. This is a genuine gap in my verification, and confirming/refuting it requires reading the full body of `calc_take_pnl` and `Calculator::calc_total_without_take_pnl_no_orderbook` in `program/src/math.rs`/`program/src/processor.rs`, which I was unable to retrieve before running out of tool calls.

### Recommendation
- Enforce a minimum `amm.lp_amount` floor well above `1` (e.g., require `amm.lp_amount` to stay above some fixed minimum-liquidity threshold, similar to the permanently-locked minimum liquidity pattern used in `process_initialize2`'s `InitLpAmountTooLess` check) so a single actor can never hold the entire remaining LP supply as a single dust unit.
- Verify (this needs confirmation, see caveat above) whether `calc_take_pnl` fully diverts any vault-balance increase not accompanied by a corresponding `Deposit` call into the pnl/sink accounting, and if not, consider basing the deposit/withdraw ratio on internally tracked contributed balances rather than raw vault token-account balances, to remove the direct-donation vector entirely.

### Proof of Concept
Conceptual sequence (mirrors the original report's multi-step methodology):
1. Attacker acquires effectively all LP tokens of a pool (or is the sole depositor).
2. Attacker calls `Withdraw` repeatedly/with `withdraw.amount = amm.lp_amount - 1`, which is allowed since the check is `withdraw.amount >= amm.lp_amount` (strict), leaving `amm.lp_amount == 1` — [5](#0-4) .
3. Attacker sends a plain SPL `Transfer` of a large amount of coin and pc tokens directly to `amm_coin_vault`/`amm_pc_vault` (owned by the AMM PDA authority), bypassing the `Deposit` instruction entirely.
4. `total_coin_without_take_pnl`/`total_pc_without_take_pnl`, computed from live vault balances at `program/src/processor.rs:1148-1153`, are now hugely inflated relative to `amm.lp_amount == 1`.
5. A victim calls `Deposit`; `mint_lp_amount` is computed via `exchange_token_to_pool(amm.lp_amount, Floor)` at `program/src/processor.rs:1244-1250`, which rounds to a very small number of new LP units relative to the value the victim contributed.
6. Attacker calls `Withdraw` with their `1` retained LP unit; the payout at `program/src/processor.rs:1751-1761` is proportional to `amm.lp_amount`, letting the attacker redeem a disproportionately large fraction of the pool (including the victim's freshly deposited assets) relative to the negligible amount the attacker actually contributed via the initial LP-token positions.

Note: full confirmation of step 4's magnitude (i.e., whether `calc_take_pnl` neutralizes the donated balance before it reaches the LP-ratio math) requires reading the complete `calc_take_pnl`/`calc_total_without_take_pnl_no_orderbook` implementations, which I could not retrieve in full before this session ended.
