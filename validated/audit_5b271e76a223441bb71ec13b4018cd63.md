The key vulnerability lives in `market-vault.clar`'s collateral accounting, which trusts a SIP-010 token's `transfer` response without validating its boolean payload.

### Title
Collateral ledger can be credited without real token custody via non-reverting SIP-010 `transfer` calls - (File: `local-testing/contracts/market/market-vault.clar` / `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`collateral-add` records a user's collateral in the internal ledger based solely on `try!`-wrapping the SIP-010 `transfer` call, without checking that the call actually returned `(ok true)`. Any registered collateral asset whose `transfer` implementation can return `(ok false)` (the direct Clarity analog of an ERC20 that returns `false` instead of reverting on failure, as flagged in the referenced report) lets an attacker record collateral in the ledger while zero tokens are actually moved into the vault's custody.

### Finding Description
`receive-tokens` simply forwards the trait call without inspecting its result: [1](#0-0) 

It is invoked from `collateral-add` wrapped only in `try!`: [2](#0-1) 

In Clarity, `try!` on a `response` type only short-circuits on `(err ...)`; if the callee's `transfer` returns `(ok false)` — a value that is technically SIP-010-response-shaped but signals "did not transfer" — `try!` unwraps it to `false` and execution continues normally. The subsequent `(insert updated-entry)` and `add-user-collateral` calls (invoked in the `let` bindings before the auth/pause checks) commit the recorded collateral amount to the ledger regardless of whether any value was actually received into the contract's custody. This breaks the identity:

```
sum(collateral map entries for asset) == actual token balance held in market-vault custody
```

The equivalent path for withdrawals, `send-tokens`, has the same defect in reverse — it wraps the outgoing `transfer` in `try!` inside `as-contract?`, but the ledger is already decremented via `insert updated-entry` before the transfer is attempted: [3](#0-2) 

If the outgoing `transfer` returns `(ok false)` without reverting, the user's collateral is silently erased from the ledger without the funds actually leaving the vault to reach the intended recipient, permanently freezing that value from the user's perspective while it remains stuck in the vault.

Both `collateral-add` and `collateral-remove` accept an attacker/DAO-supplied `<ft-trait>` implementation (any principal implementing the `ft-trait`), matching the report's core concern: the ability to interact with a registered asset whose `transfer` semantics don't strictly guarantee atomic revert-on-failure, unlike Stacks' native `ft-transfer?` for the protocol's own fungible tokens.

### Impact Explanation
On the `collateral-add` side, phantom collateral can be recorded without real backing assets entering custody. Since `market.clar`'s borrow/health logic reads the collateral ledger via `market-vault.clar` to size how much real debt a position can carry, an attacker can inflate their recorded collateral for zero real cost and then borrow real, fully-backed assets (STX/sBTC/USDC/etc.) out of the vaults — a direct theft of protocol funds and a break of solvency (ledger vs. custody identity). On the `collateral-remove` side, a non-reverting failed payout permanently strands the user's already-debited collateral in the contract, a permanent freezing of funds.

### Likelihood Explanation
Exploitability depends on a collateral asset being registered whose `transfer` can return `(ok false)` instead of aborting on failure — this is exactly the scenario the original report calls out as a realistic, non-malicious quirk of "compliant but imperfect" tokens (the report's ZRX-style example), not a requirement for the DAO to deliberately whitelist a malicious token. Any asset onboarded by the DAO in good faith that has this transfer semantic (or is later upgraded/proxied to have it) silently exposes this path, so it is a code-level unchecked-return-value bug rather than a DAO-trust or oracle issue.

### Recommendation
After every `contract-call? asset transfer ...)` in `receive-tokens` and `send-tokens`, explicitly assert the boolean payload of the response (e.g., `(asserts! (unwrap! response ERR-TRANSFER-FAILED) ERR-TRANSFER-FAILED)`) rather than relying on `try!` alone, so any `(ok false)` result reverts the whole transaction. Additionally, for `collateral-add`, verify the contract's asset balance increased by the expected `amount` before crediting the ledger, and reorder `collateral-remove` to perform the outbound transfer before committing the ledger decrement (or roll back the ledger update if the transfer does not succeed).

### Proof of Concept
1. DAO (or protocol operators) registers a collateral asset `X` implementing `ft-trait` whose `transfer` function, on certain conditions (e.g., insufficient balance, paused state, or any internal guard), returns `(ok false)` instead of `(err ...)`.
2. Attacker calls `market.clar`'s `collateral-add` (or directly `market-vault.clar`'s `collateral-add`) with asset `X` and an `amount` that triggers the `(ok false)` path (e.g., attacker holds zero balance of `X`).
3. `receive-tokens` executes `(contract-call? asset transfer amount account current-contract none)`, which returns `(ok false)`; the wrapping `try!` in `collateral-add` unwraps this to `false` without erroring.
4. `add-user-collateral` and `insert updated-entry` still execute, crediting the attacker's ledger with `amount` of asset `X` even though the vault's real balance of `X` did not increase.
5. Attacker then calls `borrow` against this phantom collateral to withdraw real backing assets from other vaults, realizing a direct theft of protocol funds.

```text
(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))
    
    (insert updated-entry)
```

```text
(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))
        (updated-entry (merge entry (refresh updated-mask))))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
    (try! (send-tokens ft amount recipient))
```
