## Title
Shared `Emporium` identity in CASE-2 stateless ops lets any Hinkal user steal another user's principal+rewards staked via `EmporiumStack` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

## Summary
When a victim's `transact()` performs a CASE 2 "stateless" `EmporiumOperation` (e.g. `staking.stake(amount)`), the call is executed directly by the shared `EmporiumUpgradeable` contract, so any external protocol that tracks state by `msg.sender` (like a staking pool) attributes the deposit to the single shared `Emporium` address rather than to the victim. Because `runAction` mints a UTXO to whoever's transaction merely observes a positive balance delta on the `Emporium` contract, any subsequent unprivileged caller can withdraw the victim's staked principal and rewards into their own UTXO.

## Finding Description
The claimed equality "principal staked by victim + rewards accrued to victim's stake == amount later claimable exclusively by the victim's stealth address" does **not** hold. There is no on-chain or circuit binding tying a specific external-protocol state (e.g., a staking contract's internal `balances[msg.sender]`) to the depositor's private UTXO/stealth address; the only tie is the ephemeral, per-call `balancesBefore`/`balancesAfter` comparison inside `EmporiumUpgradeable.runAction`.

Trace:
1. Victim calls `Hinkal.transact` → `_externalTransact` → `IExternalActionV2(Emporium).runAction(circomData, deltaAmountChanges)` as a plain external call (not `delegatecall`), so inside `runAction`, `msg.sender == address(Hinkal)`, but crucially the CASE 2 branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the `Emporium` contract itself: [1](#0-0) . Thus the staking contract sees `msg.sender = address(Emporium)` for the `stake()` call — identical for every Hinkal user who routes through CASE 2.
2. `EmporiumUpgradeable.runAction` only gates entry via `onlyAllowedRecipient`, which checks that `msg.sender` (the `Hinkal` contract) is an allowed recipient — it enforces nothing about caller identity or ownership of prior staked funds: [2](#0-1) .
3. Later, the attacker crafts their own `transact()` with an `EmporiumStack` containing `staking.unstake(amount)` + `staking.claimRewards()` as CASE 2 ops, and lists the staking token in their own `circomData.erc20TokenAddresses`. Since the staking contract's bookkeeping is keyed to `address(Emporium)` (not to the victim), it happily pays out the victim's principal+rewards to `address(Emporium)`.
4. `runAction` measures `balanceChange = balancesAfter[i] - balancesBefore[i]` purely as a delta on `Emporium`'s own token balance around the attacker's own ops, with no knowledge that this balance originated from the victim's earlier deposit: [3](#0-2) .
5. `handleOut` unconditionally mints a UTXO of `balanceChange` to `circomData.stealthAddressStructure` — the attacker's own stealth address — and physically transfers the tokens to `msg.sender` (`Hinkal`), which the attacker's own proof/commitment structure then claims: [4](#0-3) .
6. `Hinkal._verifyAndProcessTransaction`'s balance-equation check (`balanceDif == amountChanges[i] + utxoAmount`) is self-consistent per-transaction — it validates that the attacker's own `Hinkal` contract balance change matches what the attacker claims and mints, but it has zero knowledge of who the funds "should" belong to: [5](#0-4) . None of `performHinkalChecks`, `verifyProof`, `insertNullifiers`, or the circuit's `inTotal + amountChanges === outTotal` constraint reference the external staking contract's internal ledger at all — they only constrain Hinkal's own private UTXO tree, which is completely decoupled from state left inside third-party contracts under the shared `Emporium` identity.

Root cause: CASE 2 stateless `EmporiumOperation`s execute with the caller identity of the shared, singleton `Emporium` contract rather than a per-user identity (contrast with CASE 1, which routes through a per-user `HinkalWallet` via `stack.signerAddress`, giving isolated identity). Any external protocol that tracks ownership/balances by `msg.sender` therefore pools all CASE-2 users' state under one address, and whoever next calls that protocol through `Emporium` can drain it.

## Impact Explanation
Critical — direct theft of another user's principal and accrued yield. The victim's staked funds, once staked via a stateless CASE 2 op, become claimable by any unprivileged attacker who simply calls the staking contract's withdraw/claim functions through their own `transact()` before the victim does. This is repeatable against every victim who uses CASE 2 with any msg.sender-keyed external protocol (staking, lending, vault shares, etc.), and race-prone (whoever unstakes first wins, including the true victim if they act fast, but any attacker can front-run).

## Likelihood Explanation
Preconditions: victim must perform a stateless (CASE 2, `invokeWallet=false` or `signerAddress=address(0)`) `EmporiumOperation` against an external protocol that attributes deposits/balances to `msg.sender`. This is a natural, unprivileged usage pattern explicitly supported by `EmporiumStack`/`EmporiumUpgradeable.runAction` CASE 2 branch. The attacker needs no special role — just the ability to call `transact()` with their own `CircomData` referencing the same staking contract and token, which is fully within the stated attacker capabilities. Cost is just gas plus proof generation for their own valid UTXO transaction; the attack is highly feasible and repeatable against any qualifying staking/lending integration.

## Recommendation
For CASE 2 stateless ops, do not allow direct calls where the external protocol's own bookkeeping is keyed by `msg.sender`; either (a) force all stateful/balance-accruing interactions through per-user `HinkalWallet` instances (CASE 1) so external state is isolated per depositor, or (b) require CASE 2 ops to be atomic (deposit-and-immediately-settle within the same `transact()`, never leaving state resident in the external contract under the shared `Emporium` address across multiple transactions), or (c) maintain an internal Hinkal-side ledger mapping which staking positions belong to which committed UTXO/stealth address and enforce it before minting an output UTXO from `handleOut`.
