### Title
Creator fee stream can be permanently orphaned by reassigning `creator` to an unreachable address, freezing funds in `FeeVault` - ([File: packages/contracts/src/FeeVault.sol])

### Summary
NFTR-11 describes a "coveted asset" (a reserved name) that becomes permanently unclaimable once the identity it is bound to (an NFT owner) can no longer act, because the protocol provides no way to release or reassign the asset. The alt.fun analog is the per-token `creator` role: `FeeVault` accrues every trader's buy/sell fee into `creatorBalance[creator]`, and the only way to withdraw it is `claim()`, which pays out to `msg.sender` directly with no separate recipient parameter [1](#0-0) . If the `creator` address tied to a token is ever set — via `Bonding.transferCreator` (the creator-role transfer entrypoint named in this contest's own scope rules) — to an address that can never itself originate a transaction calling `claim()` (e.g. the `Token` contract, the `Pair` contract, `Bonding`/`Zap`/`FeeVault` itself, or any other non-EOA/non-proxying contract), every already-accrued and all future creator fees for that token become permanently unclaimable, exactly mirroring the "name is lost forever" outcome in NFTR-11.

### Finding Description
`FeeVault.accrue` only guards against the zero address when crediting a creator (`if (creator == address(0)) revert ZeroAddress();`), and then simply increments `creatorBalance[creator]` [2](#0-1) . Withdrawal is strictly self-service: `claim()` reads `creatorBalance[msg.sender]`, zeroes it, and pushes USDC to `msg.sender` [1](#0-0) . There is no admin-recovery path, no alternate beneficiary parameter, and no restriction that the `creator` address must be an EOA or a contract capable of calling `claim()` on its own behalf.

Because the creator role for a launched token is itself transferable (`Bonding.transferCreator`, listed as an unprivileged, permissionless-caller-reachable function in this protocol's own attack surface), a token creator can reassign the role to any non-zero address without alt.fun validating that the destination can ever call `FeeVault.claim()`. Any address that is a plain contract with no logic to forward such a call (the `Token` ERC20 itself, the bonding-curve `Pair`, or any immutable/finalized contract) can still receive `accrue()` credits — USDC transfers succeed to any address, contract or not — but can never execute `claim()` to withdraw them, since `claim()`'s only authorization path is `msg.sender` matching the stored `creator` key. USDC does not require a receive hook, so the transfer into `creatorBalance` silently succeeds and looks fully backed in `FeeVault`'s O(1) underfund accounting [3](#0-2) , yet the balance is permanently orphaned — indistinguishable in outcome from NFTR-11's burned-NFT name loss.

### Impact Explanation
Once `creator` for a token is pointed at an address incapable of calling `claim()`, all of that token's past and future creator-side trading fees are permanently frozen inside `FeeVault`. This is a permanent freezing of creator funds, matching the required impact bar (concrete permanent freezing of creator funds), and — unlike the NFTR resolution — is not merely a self-inflicted loss of a name but a loss of an ongoing revenue stream that continues to accrue and lock up USDC with every subsequent trade on the token's bonding curve, since `accrue()` has no way to detect or reject an unreachable `creator`.

### Likelihood Explanation
Any token creator (or anyone the creator role is transferred to) can trigger this by calling `Bonding.transferCreator` with a contract address that has no `claim()`-forwarding logic — including addresses that are readily available and predictable, such as the token's own `Token` contract address, the `Pair` address, or any other protocol contract, none of which alt.fun validates against. No privileged role or unusual preconditions are required; it is reachable purely through normal permissionless creator-role management.

### Recommendation
Validate the `creator` recipient in `Bonding.transferCreator` (and/or in `FeeVault.accrue`) to reject known protocol contract addresses, and/or add an owner- or creator-initiated recovery/redirect mechanism in `FeeVault` so that `creatorBalance` for an address proven incapable of calling `claim()` can be reassigned, mirroring the recommendation NFTR received (a "dereserve"/reassignment path) rather than leaving funds permanently stranded.

### Proof of Concept
1. Creator launches a token through `Zap.createToken`, becoming the `creator` of record in `Bonding`.
2. Traders buy/sell against the bonding curve; `Bonding` calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)` repeatedly, growing `creatorBalance[creator]` [2](#0-1) .
3. Creator (or an attacker who obtains the creator role) calls `Bonding.transferCreator(token, tokenContractAddress)`, setting `creator` to the token's own `Token` contract address (or `Pair`/`Bonding`/`Zap` address) — an address with no code path to call `FeeVault.claim()`.
4. Trading continues; `accrue()` keeps crediting `creatorBalance[tokenContractAddress]` with real USDC backing it.
5. `claim()` can never be called as that address (no EOA controls it, and the contract has no function that calls `FeeVault.claim()` on its own behalf), so `creatorBalance[tokenContractAddress]` — and all USDC behind it — is permanently frozen in `FeeVault`.

**Note on verification limits:** I was unable to load the full implementation of `Bonding.transferCreator` within the available tool budget (only `FeeVault.sol` was fully retrieved; `Bonding.sol`'s creator-transfer logic was referenced only via the contest's own scope rules, which explicitly name `transferCreator` as an in-scope, unprivileged-reachable function). If `transferCreator` already restricts the destination address (e.g., to EOAs only, or blocks known protocol contract addresses), this finding's likelihood would be reduced accordingly — a full review of `Bonding.sol`'s `transferCreator` function is recommended to confirm whether such a guard exists.

```text
    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

```text
    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }
```
