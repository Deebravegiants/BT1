Found a genuine, verifiable off-by-one analog: `ValidateGetSecretsRequest` in `core/capabilities/vault/validator.go` rejects a batch that is exactly at the documented `MaxBatchSize`, effectively allowing only `MaxBatchSize-1` items — the same class of error described in the Astaria report (`length > MAX` used instead of `length >= MAX`, here inverted as `>=` instead of `>`).

### Title
Off-by-one in vault `GetSecrets` batch-size check silently caps requests below the documented `MaxBatchSize` - (File: `core/capabilities/vault/validator.go`)

### Summary
`vaulttypes.MaxBatchSize` is documented as "the maximum number of secrets that can be created/updated/deleted **in a single request**" and is set to `10` [1](#0-0) . For `CreateSecrets`, `UpdateSecrets`, and `DeleteSecrets`, the validator correctly uses `MaxRequestBatchSizeLimiter.Check(ctx, len(...))`, whose `UpperBoundLimiter` semantics reject only when `n > bound`, so a batch of exactly `MaxBatchSize` items is accepted [2](#0-1) . However, `ValidateGetSecretsRequest` uses a hand-rolled comparison `if len(request.Requests) >= vaulttypes.MaxBatchSize` which rejects a batch that is exactly at the limit, only allowing `MaxBatchSize-1` (9) items through [3](#0-2) .

### Finding Description
The root cause is the wrong comparison operator (`>=` instead of `>`) for `ValidateGetSecretsRequest`, which is inconsistent with the sibling validators (`ValidateCreateSecretsRequest`/`ValidateUpdateSecretsRequest`/`ValidateDeleteSecretsRequest`) that all delegate to `MaxRequestBatchSizeLimiter.Check`, whose bound semantics is strictly `n > bound` [4](#0-3) . This is confirmed by the test suite itself, which explicitly documents the asymmetry: for `Create`/`Update`/`Delete` requests, a batch of exactly `MaxBatchSize` items is accepted ("AcceptsBatchAtLimit" tests use `vaulttypes.MaxBatchSize` items and expect no error) [5](#0-4) , while `ValidateGetSecretsRequest`'s own test explicitly states "batch size equals MaxBatchSize is rejected" using exactly `10` items, and "batch size at limit is accepted" only for `9` items (`MaxBatchSize-1`) [6](#0-5) .

`ValidateGetSecretsRequest` is invoked from the unprivileged client-facing gateway path for the `vault.secrets.get` RPC method that any authenticated workflow owner can call through `GatewayHandler.HandleGatewayMessage` / the vault request-processing pipeline, so this off-by-one is directly reachable by ordinary users making valid requests [7](#0-6) .

### Impact Explanation
This is functionally similar to the Astaria finding: a documented capacity/limit (`MaxBatchSize = 10`) is not actually honored for the `GetSecrets` operation — legitimate requests carrying exactly the maximum allowed number of secret identifiers are incorrectly rejected with "request batch size exceeds maximum of 10", even though the constant and comment promise that 10 is the max, and other sibling operations (`Create`/`Update`/`Delete`) do allow exactly 10. This causes availability/usability degradation for legitimate batch `GetSecrets` calls (denial of valid requests), and creates inconsistent, confusing limit enforcement across the vault's write vs. read APIs. It does not itself allow bypassing a limit (no over-limit acceptance), so impact is bounded to erroneous rejection of valid within-spec requests rather than a security bypass.

### Likelihood Explanation
High likelihood of being triggered in normal operation: any workflow or client that legitimately batches exactly `MaxBatchSize` (10) `GetSecrets` lookups in one request — which is exactly the documented supported maximum — will hit this bug deterministically, every time, with no special conditions required.

### Recommendation
Change the comparison in `ValidateGetSecretsRequest` from `if len(request.Requests) >= vaulttypes.MaxBatchSize` to `if len(request.Requests) > vaulttypes.MaxBatchSize`, or better, refactor it to delegate to `r.MaxRequestBatchSizeLimiter.Check(ctx, len(request.Requests))` as the other three validators do, for consistent semantics [3](#0-2) .

### Proof of Concept
1. Build a `vaultcommon.GetSecretsRequest` with exactly `vaulttypes.MaxBatchSize` (10) valid, unique `SecretRequest` entries.
2. Call `RequestValidator.ValidateGetSecretsRequest(ctx, request)`.
3. Observe the call returns an error `"request batch size exceeds maximum of 10"` even though the batch size equals, and does not exceed, the documented maximum [8](#0-7) .
4. Contrast with `CreateSecrets`/`UpdateSecrets`/`DeleteSecrets` using the same size (10) items, which succeed without error, confirming the inconsistency [5](#0-4) .

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}
