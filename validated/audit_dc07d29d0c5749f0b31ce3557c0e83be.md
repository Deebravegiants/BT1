### Title
`recapitalize` pays out pool custody without debiting the cash book, leaving suppliers permanently unable to withdraw - (File: contracts/pool/src/ops/mod.rs)

### Summary
The kernel bug class is *failure/cleanup path leaves an enabled resource inconsistent* (mount aborts but quotas stay on). The analog in XOXNO Lending is stronger: `recapitalize` — a permissionless pool entrypoint — completes a token transfer out of the pool while the market's `cash` book is not debited to match. The book keeps claiming custody the pool no longer holds. This is the same shape as the ext4 bug: a state transition (paying tokens / enabling quotas) is performed without the corresponding bookkeeping unwinding, so every later consumer that trusts the accounting fails inside the actual resource operation.

### Finding Description
`Pool::recapitalize` is callable by any address (it is listed among the unprivileged controller/pool surfaces). Per the regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`, calling `recapitalize` with `amount` equal to the pool's entire token balance sends all custody to `payer` and returns success, while `state.cash` remains `>=` the outstanding supplier deposit. On withdrawal, the pool's liquidity guard `require_reserves` reads the `cash` book, admits the exit, and the subsequent SAC `transfer` reverts with `BalanceError (10)` because custody is gone. No pool-side guard (`InsufficientLiquidity`, `PoolInsolvent`) fires, so the book-vs-custody divergence is never corrected and cannot self-heal. The same host-rollback that protects atomic multi-leg ops does nothing here because `recapitalize` itself succeeds — the inconsistency is committed, exactly as the leaked quotas were committed before the mount error path ran.

### Impact Explanation
Permanent freezing of funds and protocol insolvency bookkeeping. Suppliers' exits always pass the solvency/liquidity pre-checks and then revert inside the token transfer, so their deposits are unwithdrawable while the market reports itself solvent. Because `cash` still counts the phantom balance, subsequent suppliers may also deposit into a market whose book overstates its ability to pay, worsening the shortfall. An attacker pays nothing — `recapitalize` itself moves the tokens.

### Likelihood Explanation
Fully reachable by a single unprivileged address with one call: `pool.recapitalize(hub_asset, payer, pool_balance)`. No authorization, timing, or oracle precondition is required; the only prerequisite is that the pool holds custody, which is the normal state of an active market. The scenario is already reproduced deterministically in `contracts/pool/tests/flows.rs:3407-3483`.

### Recommendation
Make `recapitalize` measured like other settlement paths: snapshot the pool's SAC balance, perform the payout, then debit `cash` by the measured delta (or require the payer to fund the write-down by pulling tokens in rather than paying custody out). Additionally, reconcile `cash` against actual custody — or fail with the pool's own `PoolInsolvent`/`InsufficientLiquidity` instead of deferring to the SAC balance error — so the book can never overstate custody after a committed operation.

### Proof of Concept
```rust
// contracts/pool/tests/flows.rs:3407-3483 (existing regression)
#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // Legitimate supplier deposits; book == custody.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t.client().supply(&t.sup(0, deposit))
        .get_unchecked(0).position.scaled_amount;
    assert_eq!(t.state_snapshot().cash, token.balance(&t.pool));

    // Unprivileged recapitalize drains ALL custody; the cash book is untouched.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0);
    assert!(t.state_snapshot().cash >= deposit); // book still claims solvency

    // Withdrawal clears the book-based liquidity guard, then dies in the SAC.
    let outcome = t.client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    // Error is SAC BalanceError(10), NOT InsufficientLiquidity / PoolInsolvent.
    assert_eq!(token.balance(&receiver), 0); // supplier gets nothing, forever
}
```
