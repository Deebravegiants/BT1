### Title
Graduation LP-rebalance swap budget is capped by Bonding's own inventory, not by what's needed to correct an attacker-sized HyperSwap V2 pre-seed, letting a pre-seeded pool graduate at a price far from curve-close - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` seeds the post-graduation HyperSwap V2 pool via `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`, which is meant to arb away any hostile pre-seed of the TOKEN/LT pair before depositing the curve-close-priced liquidity. The rebalance swap, however, is capped at 99% of `Bonding`'s own graduation inventory (`tokensForLP` / `ltFromPair`), not at the size actually required to bring an attacker-sized pre-seed back to the curve-close ratio. An attacker who pre-creates the HyperSwap V2 pair and mints LP against a sufficiently large, skewed reserve (funded with externally-sourced LT and a modest curve-bought TOKEN balance) can make the required corrective swap exceed that budget by construction. The rebalance then only partially corrects the ratio, and `_routerDepositAndDispose` deposits the remaining protocol-owned liquidity at that still-skewed, post-swap ratio - i.e., the locked LP (`LPLock.recordLock`) is seeded away from the curve-close price the design explicitly claims to preserve.

### Finding Description
`_seedRebalancing` decides direction and calls `_pairRebalance` with `maxSwap` computed from `_swapBudget`, which is simply `(budget * 99) / 100` where `budget` is `Bonding`'s own held LT (`_ltSwapInventory`) or TOKEN balance — i.e. `ltFromPair`/`tokensForLP`, the fixed, small amounts drained from the curve at graduation: [1](#0-0) 

`_swapBudget` and `_ltSwapInventory` derive that cap purely from Bonding's own balance, with no relation to the size of the pre-existing pool reserves that must be overcome: [2](#0-1) 

`_noFeeSwapInput` computes the theoretically-needed swap `s` to hit the target ratio and then silently truncates it to `maxSwap` when the pre-seed is large enough to demand more: [3](#0-2) 

Because `VIRTUAL_LIQUIDITY_USD` is fixed at `3000 ether` and the (immutable, per-deployment) `graduationThresholdUsd` bounds the LT ever raised on the curve, `ltFromPair` and `tokensForLP` are small, fixed-size quantities: [4](#0-3) 

An attacker can pre-create the HyperSwap V2 pair for a not-yet-graduated token, buy a modest amount of the launched TOKEN off the curve via `Zap.buy` (an ordinary unprivileged trade), acquire a much larger LT balance independently (LT is an external, freely tradable BounceTech asset), transfer both into the pre-created pair, and call `pair.mint(attacker)` — all before `finalizeGraduation` runs. This produces reserves whose ratio is arbitrarily far from the curve-close ratio and whose *size* dwarfs `tokensForLP`/`ltFromPair`. When `finalizeGraduation` eventually runs: [5](#0-4) 

the rebalance swap is capped at 99% of Bonding's own (small) inventory, so it cannot move a large pre-seed all the way to the target ratio. `_routerDepositAndDispose` then deposits the remaining protocol liquidity at the router's `quote()`-optimal split of the *post-swap* (still-skewed) ratio, using `addLiquidity(min0=1, min1=1)` so it can never fail on the mismatch: [6](#0-5) 

The resulting LP is minted to `LPLock` and permanently locked with no rescue path: [7](#0-6) [8](#0-7) 

The contract's own natspec states the design goal is that the graduated pool "opens at the exact curve-close price" and that the rebalance exists specifically to "arb the pre-seed away," but the swap-budget derivation only accounts for Bonding's own inventory, not the attacker-controlled reserve size, so that policy is not actually enforced against a sufficiently large pre-seed.

### Impact Explanation
The freshly-seeded, permanently-locked LP (the entirety of the curve's raised LT plus up to 250M tokens, per `LP_RESERVE`) is deposited at a ratio diverging from the true curve-close price whenever a pre-seed exceeds the rebalance budget. Because the attacker holds the majority of LP in the pool from their own pre-seed mint, the mispricing lets them immediately arbitrage the pool back to fair value, extracting value from the newly-deposited (and now-locked) reserves — this is a direct value transfer out of the protocol-owned, permanently-locked liquidity to the attacker, i.e. theft of LP funds via an LP seeded away from the curve close price, one of the impact categories the scope explicitly recognizes as valid on its own.

### Likelihood Explanation
Every step is reachable by a single unprivileged address using ordinary permissionless actions already enumerated as in-scope: pre-creating/pre-seeding the HyperSwap V2 TOKEN/LT pair before graduation, and buying TOKEN via `Zap.buy`/curve `buy`. No privileged role, upgrade, or off-chain component is required. The only cost to the attacker is capital to fund the oversized pre-seed, which is recoverable (plus profit) via the post-finalize arbitrage, making this economically self-financing rather than merely griefing.

### Recommendation
Size the rebalance swap budget (and/or reject/limit the graduation) relative to the *actual* pre-existing pool reserves rather than only Bonding's own graduation inventory — e.g., compute the swap required to fully correct the ratio and refuse to proceed with a partial-correction deposit if the required swap exceeds what the available inventory can achieve, or cap the pre-seed's influence by requiring the deposited liquidity's implied price to stay within a bounded tolerance of `tokensForLP/ltFromPair`, reverting `finalizeGraduation` (rather than silently depositing at a skewed price) when that tolerance cannot be met with the available budget.

### Proof of Concept
1. Creator launches a token via `Zap.createToken`; curve trades normally under `Bonding`.
2. Before the token graduates, attacker calls `uniswapV2Factory.createPair(token, lt)` directly (permissionless) to pre-create the future graduation pair.
3. Attacker buys a modest amount of `token` from the curve via `Zap.buy` (ordinary trade) and separately acquires a much larger quantity of `lt` (external BounceTech LT market).
4. Attacker transfers both into the pre-created V2 pair and calls `pair.mint(attacker)`, creating large reserves at an extreme, attacker-chosen ratio.
5. The token eventually crosses `canGraduate` (via further buys or LT appreciation) and enters `Lifecycle.Graduating`; `_prepareGraduationLiquidity` caches `(tokensForLP, ltFromPair)` at the curve-close ratio (`Bonding.sol:1073-1096`).
6. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedRebalancing` detects the non-empty pool and attempts `_pairRebalance`, but `maxSwap = _swapBudget(bonding's small inventory)` (`Bonding.sol:1374-1378`) is far smaller than what `_noFeeSwapInput` (`Bonding.sol:1507-1522`) computes is needed to reach the target ratio against the attacker's large reserves, so the swap only partially corrects the ratio.
7. `_routerDepositAndDispose` deposits Bonding's remaining `tokensForLP`/`ltFromPair` at the still-skewed post-swap ratio via `addLiquidity(min=1,min=1)` (`Bonding.sol:1449-1473`), minting LP to `LPLock` (`Bonding.sol:1022-1033`, `LPLock.sol:69-85`), permanently locking a mispriced position.
8. Attacker (holding the majority pre-existing LP share) immediately swaps against the pool to arbitrage it back toward the pre-seed's price, extracting value contributed by the freshly-deposited, now-locked liquidity.

    function _seedUniswapV2Direct(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }

    /// @notice Record an LP lock. LP tokens must already sit at this address.
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
