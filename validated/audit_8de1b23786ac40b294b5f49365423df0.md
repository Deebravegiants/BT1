### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant spoofing of `WebhookMetadata#shop` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw JSON body. The `shop` (and `topic`/`webhook_id`/`api_version`) values are read directly from unauthenticated HTTP headers that are never included in the signed payload. This breaks the intended binding: shop identity acted upon (`request.shop` handed to the app's handler) ≠ shop identity actually covered by the HMAC (only `raw_body`).

### Finding Description
`Utils::HmacValidator.validate` checks `request.hmac` against a signature computed over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are excluded entirely: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop` (parsed straight from the `x-shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because `api_secret_key` is shared by every shop that installs the app, any unprivileged user who installs the app on their own store (a normal, unprivileged action requiring no special access) legitimately receives real webhooks for that store, complete with a valid `X-Shopify-Hmac-Sha256` header computed by Shopify itself over that specific body. Since the signature covers only the body, the attacker can replay that exact `(raw_body, hmac)` pair to the victim app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `topic`/`webhook-id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), but `WebhookMetadata#shop` now reports the victim's shop rather than the tenant the body actually belongs to.

This is the exact bug class described in the report: a field that is *acted on* (`shop`, used by the app to route the payload's data to a tenant, e.g. to look up that shop's session/access token and perform actions on its behalf, per the documented handler contract) is not covered by the authentication mechanism (`HMAC`) that is supposed to bind the request to that tenant.

### Impact Explanation
Downstream apps are documented to key their business logic off `data.shop` (`docs/usage/webhooks.md` explicitly shows `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), and the whole purpose of webhook shop-domain is to let the app determine which merchant's session/access token to load and act on. An attacker who legitimately installs the app on their own shop can forge the `shop` field of a validly-HMAC'd webhook to point at any other installed shop, causing the app to process attacker-supplied body content under a victim shop's identity — a cross-tenant confusion/injection primitive reachable purely through this gem's documented `Webhooks::Request` / `Webhooks::Registry.process` API, with no need for `api_secret_key`, access tokens, or any privileged access.

### Likelihood Explanation
High reachability: the only prerequisite is that the attacker has (or can obtain, e.g. via a free/dev store) a legitimate install of the target app so they receive one real webhook with a valid HMAC, which they can then replay with a modified shop header at the app's public webhook endpoint. No secrets or credentials belonging to the victim are needed.

### Recommendation
Bind the shop identity to the signature verification step instead of trusting an unauthenticated header:
- Have the app's handler/registry cross-check `request.shop` against the shop associated with the webhook subscription/session that the app expects for the given `webhook_id`/topic before acting, or
- Document (and, ideally, enforce in the gem) that `shop` must be independently verified against the app's own list of installed shops before being used to select which session/access token to act with, since the HMAC does not bind the header values.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":123}` with header `X-Shopify-Hmac-Sha256: <valid signature computed by Shopify using the app's api_secret_key over that body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as shown in [4](#0-3) ; `Utils::HmacValidator.validate` succeeds because it only checks the body against the signature ( [5](#0-4) ).
4. `Registry.process` calls the app handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id":123}, ...)` ( [6](#0-5) ), causing the app to act on attacker-controlled data under the victim shop's identity.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
