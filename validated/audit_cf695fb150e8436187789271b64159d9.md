### Title
Delegator rewards deposited into a vote account before any stake is delegated to it become permanently unclaimable - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`DepositDelegatorRewards` (SIMD-0123) lets anyone push lamports into a vote account's `pending_delegator_rewards` balance at any time, with no requirement that the vote account already have delegated stake. [1](#0-0)  These pending rewards are only ever paid out at the end of an epoch, pro-rated by each stake account's share of `total_active_stake` for that vote account in `calculate_block_reward`. [2](#0-1)  If `total_active_stake == 0` (i.e. no stake delegation exists yet for that vote account in the reward epoch), the function simply returns `0` — the loop is not even entered for that voter because it iterates over existing `stake_delegations`, so `pending_delegator_rewards` is never decremented and never handed to anyone. [3](#0-2)  This mirrors the reported Beedle `Staking.update()` bug: value (WETH fees vs. lamports) accrues in a shared pool before any depositor/staker exists, and the payout formula's implicit "divide by current total stake/supply" logic means that pre-existing value is silently absorbed with no attribution once staking begins, or remains forever stuck if staking never begins.

### Finding Description
`deposit_delegator_rewards` unconditionally accepts a lamport transfer into any V4 vote account and increments `pending_delegator_rewards`, without checking whether the vote account currently has any active stake delegated to it. [1](#0-0) 

At epoch-reward time, `calculate_block_reward` is the only code path that consumes `pending_delegator_rewards`. It is called once per existing stake delegation, using `reward_epoch_delegated_stakes.delegated_stakes` (per-vote-account total active stake at the rewarded epoch) as the denominator: [4](#0-3) 

Because the function is only invoked from within the per-delegation loop in `calculate_stake_rewards_and_commissions` (`stake_delegations.par_iter()...calculate_block_reward(...)`), a vote account with **zero** delegations in the rewarded epoch is never visited at all — there is no "zero-supply catch-up" mechanism analogous to correctly re-basing an index. The `pending_delegator_rewards` field is left completely untouched, forever, until stake eventually gets delegated to that voter. [5](#0-4) 

Once a delegation finally does exist, the payout is `pending_delegator_rewards * stake / total_active_stake`, clamped to `pending_delegator_rewards`. [6](#0-5)  This is structurally identical to the reported `Staking.update()` bug: a reward pool computed from a live/global quantity (here, `pending_delegator_rewards` funded independent of stake existing; there, `WETH.balanceOf` funded independent of `TKN` deposits) that is only divided among participants once the "supply" (here, delegated stake to that voter; there, `TKN.balanceOf`) becomes non-zero. Anyone who deposits before that point gets no attribution and the funds sit idle with no accounting variable tracking "how much has accrued while stakeless."

The `withdraw` instruction does protect the deposited lamports from being swept away by the withdrawer (it blocks closing the account or withdrawing below `pending_delegator_rewards`), [7](#0-6)  so the lamports are not stolen — but they remain economically inert (non-distributable, non-withdrawable by delegators) for as long as no stake is delegated to that voter.

### Impact Explanation
Lamports deposited via `DepositDelegatorRewards` into a vote account with no active delegated stake are permanently locked in a limbo state: not withdrawable to any delegator (no delegation exists to claim a share) and not returnable to the depositor (the withdraw path enforces `pending_delegator_rewards` stays inside the vote account balance). This is a concrete value-loss/lock condition rather than a purely cosmetic issue, though it requires a validator/vote-account operator to use `DepositDelegatorRewards` (a feature-gated, opt-in SIMD-0123 mechanism) before any stake delegation exists — this is a narrower trigger than the original DeFi report (which affected the default flow of a live protocol), so actual value at risk depends on the block-revenue-sharing deployment pattern.

### Likelihood Explanation
Requires `block_revenue_sharing`/SIMD-0123 features active and someone calling `DepositDelegatorRewards` on a vote account that currently has zero delegated stake for the relevant reward epoch (e.g., a freshly created validator identity depositing revenue before delegators join, or any vote account that temporarily loses all delegated stake). This is a plausible, unprivileged, no-collusion-required scenario since `DepositDelegatorRewards` has no delegation-existence precondition.

### Recommendation
Add a check in `deposit_delegator_rewards` (or in `calculate_block_reward`) analogous to tracking "supply" explicitly rather than implicitly deriving it from `balanceOf`: either (a) reject deposits when the target vote account has zero currently-delegated stake, or (b) when `total_active_stake == 0` in `calculate_block_reward`, route the un-attributable `pending_delegator_rewards` back to the depositor/collector rather than leaving it silently un-decremented, or (c) let the deposited amount roll forward transparently and document/guarantee it will correctly accrue to the first delegator(s) once stake exists (currently it is simply dropped from consideration since the per-delegation loop never runs for that voter).

### Proof of Concept
1. Enable `block_revenue_sharing`/related SIMD-0123 features and create a new vote account with a V4 vote state, `pending_delegator_rewards = 0`.
2. Call `DepositDelegatorRewards` to transfer, e.g., 1,000,000 lamports into the vote account with no delegated stake anywhere pointing to it. `pending_delegator_rewards` becomes 1,000,000 (see test asserting this behavior). [8](#0-7) 
3. Let an epoch boundary pass with block-reward calculation running. Because `reward_epoch_delegated_stakes.delegated_stakes.get(&vote_pubkey)` returns `None`/0 (no delegations), `calculate_block_reward` is never invoked for this voter (no entries in `stake_delegations` reference it), confirmed by unit test `get_block_reward_for_test(0, 0, pending_delegator_rewards, 0) == 0`. [9](#0-8) 
4. `pending_delegator_rewards` remains 1,000,000 indefinitely. Any attempt to withdraw down to zero or close the account is blocked by the `pending_delegator_rewards > 0` check in `withdraw`, confirming the funds are stuck rather than merely undistributed. [10](#0-9)

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
