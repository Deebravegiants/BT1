### Title
Fee-on-transfer tokens cause escrow over-crediting and locked/insolvent funds in Tron `IntentGatewayV2.placeOrder`/`withdraw` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2.sol` escrows the nominal, pre-transfer order amount rather than the amount actually received by the contract when a fee-on-transfer (or otherwise deflationary) ERC20 is used as an order input, unlike the canonical EVM `IntentGatewayV2.sol`, which explicitly measures actual received balances to defend against exactly this bug class.

### Finding Description
In the direct-escrow branch of `placeOrder` (no `predispatch`), the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — i.e., the nominal amount reduced only by the protocol fee, with no comparison to the token balance actually gained by the contract: [1](#0-0) 

The predispatch branch is only partially better: it computes `dust = balance - requiredAmount` using the dispatcher's/gateway's balance snapshot, but still credits `_orders[commitment][token] += reducedInputs[i].amount` (the nominal reduced amount) instead of the measured `balance`: [3](#0-2) 

If `token` charges a transfer fee (deducts a percentage on `transferFrom`), the gateway contract receives less than `order.inputs[i].amount`, yet the internal accounting (`_orders[commitment][token]`) records the full nominal (fee-adjusted-only-by-protocol-fee) amount as escrowed. This directly breaks the invariant that `sum(_orders[*][token])` should not exceed `IERC20(token).balanceOf(address(this))`.

This is precisely the vulnerability class flagged in the reference report (assuming transferred amount == received amount for fee-on-transfer tokens), and the project's own EVM mainline contract shows the maintainers are aware of and have fixed this exact issue there — using `balanceOf` snapshots before/after `safeTransferFrom` and mutating `order.inputs[i].amount` to the actual received amount before crediting escrow and computing the commitment hash: [4](#0-3) 

The Tron variant (`evm/tron/contracts/apps/IntentGatewayV2.sol`) was not updated with this fix, despite implementing the same `placeOrder`/escrow/`withdraw` flow.

### Impact Explanation
Once escrow accounting is inflated relative to actual token balance, `withdraw()` — invoked either from `onAccept` (cross-chain `RedeemEscrow`/`RefundEscrow`) or `cancelOrder` (same-chain refund) — will attempt to `transfer` the over-recorded `amount` to the beneficiary: [2](#0-1) 

For a single affected order, this causes the withdrawal for that order (fill payout or refund) to revert (`TransferFailed`) if it's the last such transfer draining the shortfall, permanently freezing the user's or solver's escrowed principal since `_filled`/`_orders` state is difficult to reset via a reverted call. Alternatively, if the shortfall is silently absorbed by tokens from other unrelated orders sitting in the same contract's shared token balance, it causes insolvency across the pool: later, unrelated users' or solvers' withdrawals for other orders using the same token will fail due to insufficient balance, since the contract's real holdings of that token no longer back the sum of all outstanding `_orders` entries for it. This is a direct freezing-of-funds / accounting-insolvency bug affecting any unprivileged user or solver who places or fills an order with a fee-on-transfer token on the Tron deployment.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with a fee-on-transfer ERC20 as an input token — no special privileges required. Tron's ecosystem includes fee-on-transfer / deflationary TRC20 tokens, and the `IntentGatewayV2` contract does not restrict which ERC20 addresses may be used as `order.inputs[i].token`, so nothing prevents such a token from being escrowed. Likelihood scales with adoption of the Tron deployment and demand to bridge/swap non-standard tokens through it.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `IERC20(token).balanceOf(address(this))` immediately before and after `safeTransferFrom` (and after the predispatch sweep), use the actual delta as the amount used both for computing `reducedInputs`/the commitment hash and for crediting `_orders[commitment][token]`, rather than crediting the nominal `order.inputs[i].amount` minus only the protocol fee.

### Proof of Concept
1. Deploy a fee-on-transfer TRC20 token (e.g., 1% fee burned/retained on `transferFrom`) and mint balance to `user`.
2. `user` calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no `predispatch`.
3. `IERC20(FOT).safeTransferFrom(user, gateway, 1000e18)` executes; gateway actually receives only `990e18` (contract's real `balanceOf` increases by 990e18).
4. Contract sets `_orders[commitment][FOT] += reducedInputs[0].amount` where `reducedInputs[0].amount` is `1000e18` minus only the protocol fee (e.g., `997e18` at 30bps), not `990e18`.
5. When the order is filled/settled and `withdraw()` attempts to `token.call(transfer(beneficiary, 997e18))`, the gateway's real FOT balance (990e18, minus whatever other orders in the same token also hold) is insufficient, causing the transfer to fail and the settlement to revert — locking the escrowed funds — or succeeding by draining balance backing other orders, causing a later, unrelated order's withdrawal in the same token to fail.
