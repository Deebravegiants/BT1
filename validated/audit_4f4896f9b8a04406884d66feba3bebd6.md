This confirms the finding. The `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` only checks that signable string against the HMAC header [2](#0-1) . Meanwhile `Registry.process` extracts `request.shop`, `request.topic`, `request.api_version`, `request.webhook_id` straight from unauthenticated headers and hands them to the app's handler as trusted tenant-identifying metadata [3](#0-2) , and the documented usage pattern explicitly relies on `data.shop` to key work per-tenant [4](#0-3) .

### Title
Webhook `shop` (and topic/api_version/webhook_id) headers are trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, never incorporating the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. `ShopifyAPI::Webhooks::Registry.process` nonetheless treats `request.shop` as the authenticated tenant identifier and forwards it unchanged to the host application's webhook handler. Because the app's `api_secret_key` is shared across every shop that installs the app, any user who has legitimately installed the app on their own store can capture one of their own valid signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header (and/or `topic`/`api-version`/`webhook-id`) rewritten to point at a different, victim shop. The HMAC still validates because it only covers the untouched body, so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop while the signature only proves the body came from Shopify for *some* installation of the app.

### Finding Description
The identity binding that should hold is:
```
HMAC-verified bytes == bytes the handler treats as authenticated (shop, topic, api_version, webhook_id)
```
Instead, `to_signable_string` returns `@raw_body` exclusively [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never mixed into the signed payload [5](#0-4) . `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and does a constant-time comparison against the `hmac-sha256` header value [2](#0-1)  — so validation success only proves the *body* was signed by Shopify (using the app's `api_secret_key`), not that the accompanying `shop-domain` header matches the shop the body was actually generated for.

`Registry.process` then does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [3](#0-2) 

This means `request.shop` — an unsigned header — is passed to the handler with the same level of trust as the HMAC-verified body. The gem's own documentation instructs apps to key tenant-scoped work directly off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [4](#0-3) , so this is the intended, documented consumption pattern for host apps built on this gem, not a misuse of an undocumented API.

Because `api_secret_key` is the app's single client secret shared by all merchants who install the app (not a per-shop secret), any merchant/attacker who installs the app on their own shop receives genuinely HMAC-valid webhook deliveries for that shop. They can capture the raw body + `hmac-sha256` header from one of their own deliveries and re-POST it to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` since it only checks the untouched body, so `Registry.process` will invoke the handler believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is a legitimate but unprivileged user of the app (installed on their own store) can make the app process fabricated events under the identity of an arbitrary other shop, without ever obtaining that shop's credentials. Any handler logic that uses `data.shop` to select which merchant's data/session/state to update (the exact pattern shown in this gem's own docs) can be tricked into acting on behalf of, or attributing attacker-controlled data to, a different tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop (typically self-serve/free), (2) capturing one legitimate webhook delivery (trivial — logs, browser devtools proxy, or a test webhook triggered by the attacker's own store actions), and (3) replaying it with a modified `shop-domain` header to the app's public webhook URL. No access to the victim's credentials, the app's `api_secret_key`, or TLS interception is needed.

### Recommendation
Bind the tenant-identifying headers into the HMAC-signed payload (or otherwise cryptographically bind them, e.g. via a resolved webhook-id-to-shop lookup against Shopify), rather than trusting `shop-domain`/`topic`/`api-version`/`webhook-id` headers purely because the raw body's HMAC validated. At minimum, `to_signable_string` should incorporate these header values so that tampering with them invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`.
2. Attacker's server receives the request with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and the raw body.
3. Attacker resends the identical raw body and `hmac-sha256` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the HMAC [6](#0-5) .
5. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` [7](#0-6) , causing the app to process attacker-controlled data under the victim's tenant identity.
