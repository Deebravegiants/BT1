### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise-valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the HMAC-signed payload [2](#0-1) . `Registry.process` validates the HMAC over the request (i.e., over `raw_body` only) and then dispatches the handler using `request.shop` taken from the unverified header [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes-that-include-shop)`. Instead the gem only verifies `hmac == HMAC(secret, raw_body)` [1](#0-0)  and separately trusts `shop-domain` header without binding it into the signed bytes. `HmacValidator.validate` simply calls `verifiable_query.to_signable_string` and `verifiable_query.hmac` and does a `secure_compare` [4](#0-3) ; for `Webhooks::Request` this only covers `raw_body`, never `shop`. This is the exact same "bytes verified vs bytes parsed" pattern as the reported issue — a value the code acts on (`shop`, used to attribute the webhook to a tenant) is not covered by the integrity check applied (HMAC over `raw_body`).

An unprivileged internet user who can produce (or capture/replay) a body+HMAC pair that Shopify itself signed for their own store (`shop-domain: attacker-shop.myshopify.com`) can replay that exact `raw_body`/`hmac` pair while substituting an arbitrary `shopify-shop-domain` header value, because the header is never mixed into the signed bytes. The HMAC check still passes (it only checks `raw_body`), and `Registry.process` will construct `WebhookMetadata` with the attacker-chosen `shop` value and hand it to the app's registered handler [5](#0-4) . If the host application uses `data.shop` (as the gem's own documentation/tests demonstrate handlers do — see `assert_equal(@shop, data.shop)` [6](#0-5) ) to look up which merchant's session/record to update, this breaks the `shop`-as-tenant-key binding and can misattribute a legitimately-signed payload to a different, victim tenant.

### Impact Explanation
This maps to "cross-tenant access": an attacker who owns one Shopify store (or has captured one legitimately-delivered, correctly-signed webhook) can cause the host app to process that payload under a different shop's identity, because the gem does not bind `shop` into the verified bytes. Any host code that trusts `WebhookMetadata#shop` for tenant lookup/authorization (the pattern the gem's own tests encourage) is exposed to cross-tenant data confusion.

### Likelihood Explanation
Medium: the attacker needs at least one validly-HMAC-signed webhook body (trivially available since they can install the app on their own store, or capture any delivered webhook), and then only needs to change one header field — no cryptographic secret, access token, or `client_secret` is required. The header value is not covered by the signature so no cryptographic material needs to be broken.

### Recommendation
Bind `shop` (and other identity-relevant metadata such as `topic`/`api_version`/`webhook_id`) into the HMAC-signed material, or otherwise authenticate the shop domain header against a channel that Shopify itself signs (e.g., verify it matches a value in the signed body/topic mapping, or require the caller to independently authenticate the shop before trusting the header). At minimum, document clearly that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-identity source, and provide a signed alternative.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimately Shopify-signed webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = base64(HMAC(secret, B))`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker resends this same body+HMAC to the app's webhook endpoint but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `HMAC(secret, raw_body)` [1](#0-0)  — validation passes because `raw_body` is unchanged.
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop = "victim-shop.myshopify.com"` [5](#0-4) , even though the payload was never signed for that shop.
