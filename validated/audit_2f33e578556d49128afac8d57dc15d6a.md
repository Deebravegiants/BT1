### Title
Webhook shop-domain spoofing due to `shop` field not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value handed to the app's webhook handler is therefore never cryptographically bound to the signature that authenticates the request.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the request body: [1](#0-0) [2](#0-1) 

The HMAC is validated with `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`, and for `Webhooks::Request` that method returns only the raw body bytes: [3](#0-2) 

Meanwhile `shop` is read from a separate header that is completely outside that signed string: [4](#0-3) [5](#0-4) 

Once the HMAC passes, `Registry.process` builds `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and hands it to the app's registered handler: [6](#0-5) 

The documented usage pattern explicitly tells integrators to trust `data.shop` for tenant-scoped actions (e.g., enqueuing background jobs keyed by shop): [7](#0-6) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`HMAC-verified bytes (raw body) == bytes that determine tenant identity (shop-domain header)`.
Because the api_secret_key used to compute the HMAC is a single per-app secret shared across every merchant installation (not shop-specific), any attacker who controls one legitimate shop can obtain a validly-signed `(raw_body, hmac)` pair for a real webhook delivered to their own store (e.g., by installing the app on a shop they control and triggering `orders/create` or any subscribed topic). Because the signature never depends on the `shop-domain` header, the attacker can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value (e.g., a victim merchant's domain). `Utils::HmacValidator.validate` will still return `true` because it only recomputes the HMAC over the untouched body, and `Registry.process` will dispatch to the handler with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant/shop identity binding for all HTTP webhook processing built on this gem. Any host application that uses `data.shop` from `WebhookMetadata` to select or act on merchant-specific state (look up the shop's session/access token, write to a shop-scoped record, enqueue shop-scoped background jobs, or trigger any app-side business logic keyed by shop) can be made to attribute forged webhook data to any victim shop of the attacker's choosing. This is a cross-tenant identity-spoofing primitive: an attacker who legitimately installs the app on their own store can forge inbound events for a merchant they do not control, with no ability of the host app to detect the impersonation using this gem's provided verification. Depending on what the host app does with `data.shop` (e.g., re-triggering paid operations, corrupting another tenant's cached state, or triggering data writes under the victim's identity), this constitutes cross-tenant access as defined in scope.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on a Shopify store they control (a normal, permission-free action for any Shopify merchant/developer) and be able to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-controlled headers — both are unprivileged-internet-user capabilities requiring no access token, no `client_secret`, and no interaction with Shopify's own delivery infrastructure integrity, since the endpoint is a normal internet-reachable route. The only "cost" is triggering one legitimate webhook delivery on the attacker's own shop to capture a valid `(body, hmac)` pair, which is trivial and requires no special access.

### Recommendation
Bind the shop identity into the authenticated data before trusting it:
- Do not treat the `shop-domain` header as authenticated on its own. Either include the shop identifier as part of the HMAC-signed material, or cross-check the header value against an independently trusted source (e.g., verify it matches a shop associated with a resource ID embedded in the signed body, such as looking up the webhook subscription/shop pairing server-side via the Admin API using `webhook_id`) before dispatching to the handler.
- At minimum, document prominently that `data.shop` from `WebhookMetadata` is **not** cryptographically authenticated by `HmacValidator.validate` and must not be used by integrators to select shop-scoped credentials or trigger privileged, shop-scoped actions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they legitimately control) and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimately signed webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(app_secret, B)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker captures this exact `(B, HMAC)` pair.
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with body `B` and header `x-shopify-hmac-sha256` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(app_secret, B)` and matches the supplied HMAC — validation succeeds.
6. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled webhook content as if it originated from `victim-shop.myshopify.com`. [1](#0-0) [8](#0-7)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
