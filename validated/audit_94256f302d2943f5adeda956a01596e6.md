### Title
Pausing HyperFungibleToken blocks timeout refunds of already-burned funds - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken` (and its variants `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, `WrappedHyperFungibleTokenUpgradeable`) gate `onPostRequestTimeout`, the refund path that returns already-burned/locked funds to the sender when an outgoing message times out, with the same `whenNotPaused` modifier used for `send`/`onAccept`. This mirrors the Cap M-4 pattern: a "repay/return-funds" style operation that should always be permitted is incorrectly blocked by the same pause guard meant only for new outgoing/incoming value flows.

### Finding Description
`send()` burns the caller's tokens and dispatches a POST request to the destination chain: [1](#0-0) 

If that POST request times out without delivery, `EvmHost` calls back into the app via `onPostRequestTimeout` to re-mint the burned tokens to the original sender as a refund: [2](#0-1) 

This refund function is decorated with `whenNotPaused`, the exact same modifier used to gate `send` (new outgoing burns) and `onAccept` (new incoming mints): [3](#0-2) [4](#0-3) 

`pause()` is owner-controlled and documented as pausing "all cross-chain operations (send and receive)": [5](#0-4) 

Just as in the Cap `BorrowLogic.realizeRestakerInterest` bug — where an unrelated pause check on `Vault.borrow` blocked the legitimate `repay`/liquidation path even when zero interest needed to be borrowed — here the same `whenNotPaused` gate meant for stopping *new* value creation (mint on `onAccept`) or *new* value destruction (burn on `send`) is reused, unmodified, on the refund/return-of-funds path (`onPostRequestTimeout`). Users who already burned tokens via `send()` before the pause have no way to recover them via the timeout path while the contract is paused.

The delivery mechanism in `EvmHost.dispatchTimeOut` performs a raw low-level `.call()` to the app and, on failure, simply re-stores the commitment for a later retry rather than reverting the whole transaction: [6](#0-5) 

So while the failure is retryable once unpaused, in the interim any user whose message has legitimately timed out cannot reclaim their previously burned tokens — funds they are unconditionally owed are frozen by a guard that was only intended to stop new sends/receives, not to withhold already-committed refunds.

### Impact Explanation
Any user who calls `send()` and whose message subsequently times out (e.g. due to relayer downtime, congestion, or being timed out deliberately) cannot retrieve their locked tokens for as long as the token contract remains paused. Since `pause()` is a normal operational lever (e.g. for a security incident or during an upgrade) rather than a permanent shutdown, this can freeze user funds for an indefinite duration tied entirely to the owner's discretion, contrary to the timeout-refund guarantee that the design otherwise provides (compare to `BridgeToken`, which layers a relayer check on top of `onPostRequestTimeout` but does not add any pause gate of its own beyond the inherited one). This affects `HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable` identically.

### Likelihood Explanation
The trigger only requires the contract owner to invoke `pause()` (already part of normal contract operation, not a compromise) while any user has an in-flight `send()` that later times out — a routine and expected occurrence in cross-chain messaging. No malicious actor or governance compromise is required; the bug manifests during ordinary pause usage.

### Recommendation
Do not gate `onPostRequestTimeout` (the refund of already-committed/burned funds) behind `whenNotPaused`. Following the same fix pattern as the Cap remediation (only guard the code path that actually performs the disallowed action), remove the `whenNotPaused` modifier from `onPostRequestTimeout` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol`, so refunds remain available regardless of pause state, while `send` and `onAccept` retain their pause protection.

### Proof of Concept
1. Owner deploys `HyperFungibleToken`, configures a supported destination chain and host.
2. User A calls `send()` with a valid `SendParams`, burning `amount` tokens and dispatching a POST request with commitment `C`.
3. Owner calls `pause()` before the request is delivered on the destination.
4. The request times out (destination never delivers within `timeout`).
5. A relayer submits the timeout proof; `EvmHost.dispatchTimeOut` calls `onPostRequestTimeout` on the token contract.
6. Call reverts due to `whenNotPaused`; `EvmHost` catches the failure and re-stores the commitment for retry, but User A's tokens remain unmintable/frozen as long as the contract stays paused — confirming the refund path is blocked exactly as `BorrowLogic.realizeRestakerInterest`'s unnecessary paused `Vault.borrow()` call blocked `repay` in the referenced Cap finding.

        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
