### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) header is trusted for cross-tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by HMAC-validating the raw request body, then hands the caller's declared `shop` (and `topic`/`api_version`/`webhook_id`), taken straight from unauthenticated HTTP headers, to the app's webhook handler as if it were verified. The binding "shop that produced the signed bytes" == "shop attributed to the request" is never enforced.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns **only `@raw_body`**. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read directly from HTTP headers (`shopify_header`) and are never included in the signable string: [3](#0-2) 

`Registry.process` validates the request with `Utils::HmacValidator.validate(request)`, which only compares an HMAC of `to_signable_string` (i.e. the raw body) against the `hmac-sha256` header: [4](#0-3) 

After that check passes, `Registry.process` immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` and forwards them to the app-registered handler as verified metadata: [5](#0-4) 

Because the app's `client_secret`/API secret is shared across **every shop** that has installed the app, the HMAC over the body is identical for identical body content regardless of which shop produced it. Since the `shop` header is outside the signed material, the binding the gem implicitly claims to provide (`hmac_valid(body) == shop_header_is_authentic`) does not hold: any party that can obtain one genuine `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own shop and receiving a real webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value. `Registry.process` will pass HMAC validation and dispatch the handler with `shop:` set to the attacker-chosen value, `topic`/`api_version`/`webhook_id` likewise forgeable.

### Impact Explanation
This breaks the identity binding the library is expected to guarantee for consumers who key their persistence/authorization logic off `WebhookMetadata#shop` — the whole reason this gem exposes a "verified" webhook object with a `shop` attribute instead of raw headers. A malicious app user can attribute forged/fabricated webhook events to any other shop that has installed the same app, causing the host application to write, delete, or act on data under a victim tenant's identity (cross-tenant data corruption/access), meeting the Critical "cross-tenant access" bar. The severity depends on what the downstream handler does with `shop`, but the gem provides no way for the handler to distinguish a legitimately-shop-scoped webhook from a replayed one, since only the body is authenticated.

### Likelihood Explanation
Requires the attacker to have (or obtain) one legitimate signed webhook body for the shared app secret — trivially achievable by installing the target app on the attacker's own store and triggering any subscribed webhook topic (e.g. `app/uninstalled`, `orders/create` with attacker-controlled order data). No access to `api_secret_key`, access tokens, or TLS interception is required; only a normal HTTP POST to the app's public webhook endpoint with modified headers.

### Recommendation
- Bind the `shop` (and ideally `topic`/`api_version`) to the signed payload, or independently verify `request.shop` against the shop associated with the currently-installed/authorized session/subscription for that specific topic/webhook id before invoking handlers.
- At minimum, document/require that `WebhookHandler` implementations cross-check `data.shop` against their own store of installed shops (offline session existence) rather than treating it as authenticated purely because `Registry.process` didn't raise.
- Consider incorporating the shop domain into the HMAC verification step (e.g., verify webhook subscription ownership via the GraphQL Admin API using the shop from the header) rather than trusting the header outright once body HMAC passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook subscription (e.g. `orders/create`) and captures the raw POST from Shopify: the raw JSON body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (valid because it's `HMAC_SHA256(app_secret, B)`).
3. Attacker crafts a new HTTP request to the app's webhook endpoint containing the *same* body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(app_secret, B)` and compares to `H` — this matches, since the body wasn't changed.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...))`.
6. The registered `WebhookHandler` executes its business logic believing the event is legitimately from `victim-shop.myshopify.com`, even though the shop header was never covered by the signature and no session/authorization check tied it to the actual originating shop.
