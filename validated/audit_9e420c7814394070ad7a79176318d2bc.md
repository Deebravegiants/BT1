### Title
Empty `erc20TokenAddresses` (Emporium-min circuit path) lets `EmporiumUpgradeable.runAction` execute arbitrary token-draining ops with zero balance accounting - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `circomData.erc20TokenAddresses` is empty, `CircomDataBuilder.formInputForCircom` routes the proof through `formInputEmporiumMin`/`MainEVMCircuitMin`, which never constrains any ERC20 accounting [1](#0-0) . In that case `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` loops and the `deltaAmountChanges` conservation check iterate zero times, while the `stack.ops` execution loop (lines 91-118) still runs unconditionally and unauthenticated when `stack.signerAddress == address(0)`, letting an attacker drain any ERC20 balance already sitting on the Emporium contract.

### Finding Description
The broken equality: value leaving Emporium via `op.endpoint.call(...)` (an ERC20 `transfer` to the attacker) should equal `-deltaAmountChanges[i]` for that token, enforced by the loop at [2](#0-1) . When `circomData.erc20TokenAddresses.length == 0`, this loop body never executes for any token, so the equality is never evaluated at all — the drained USDC is simply unaccounted.

Path: `Hinkal.transact` → `hinkalHelper.performHinkalChecks` builds `inputForCircom` via `formInputForCircom`, which detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` and switches to `formInputEmporiumMin`, whose only public signals are `emporiumMessage`, `timeStamp`, `calldataHash` [3](#0-2) . The corresponding circuit `MainEVMCircuitMin` only computes a Poseidon hash of a private `messageSeed` and constrains nothing about token addresses, amounts, or ops content [4](#0-3) . Since the attacker fully controls `messageSeed` and every other private input for their own self-authored transaction, they can trivially produce a valid proof for any `circomData`/`EmporiumStack` payload they want.

`Hinkal._externalTransact` builds `deltaAmountChanges` sized to `erc20TokenAddresses.length` (i.e., empty array) and calls `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` [5](#0-4) . Inside `runAction`, `stack.ops` is decoded straight from `circomData.externalActionData.externalActionMetadata` — a field entirely outside the min circuit's public signals — and executed regardless of `erc20TokenAddresses`: [6](#0-5) 
`verifyWallet` only checks/marks `usedMessages[emporiumMessage]`; it validates the EIP-712 signature over `stack.ops` **only if `stack.signerAddress != address(0)`** [7](#0-6) . So with `signerAddress = address(0)` there is no authentication at all on the ops content — the attacker (an unprivileged, `onlyAllowedRecipient`-gated caller acting as `msg.sender == Hinkal`) can supply `ops = [{endpoint: USDC, invokeWallet:false, value:0, callData: transfer(attacker, X)}]`, and it executes via `op.endpoint.call{value: 0}(op.callData)` as `msg.sender == Emporium`.

Back in `Hinkal.transact`, the outer balance-diff/slippage/conservation loop (lines 97-147) is also bounded by `circomData.erc20TokenAddresses.length == 0` [8](#0-7) , so it likewise never inspects USDC. No guard anywhere else (proof verification, `rootHashExists`, `insertNullifiers`) constrains `stack.ops` content when the min-circuit path is used, because the min circuit's public-input vector simply doesn't include a hash or commitment to the ops/callData.

### Impact Explanation
Any ERC20 balance resting on the `EmporiumUpgradeable` contract — whether from rounding/dust of a prior legitimate action that left an undeclared token behind, or any other residual balance — can be stolen outright by an unprivileged attacker with a single `transact()` call, with zero UTXOs minted or burned to compensate. This is direct theft of protocol/user-custodied ERC20 funds, matching the **Critical** severity bucket (direct theft of shielded or in-flight user funds / bypass of the value-conservation constraint that the proof system is supposed to enforce). The attack is repeatable for every ERC20 token balance that accumulates on Emporium.

### Likelihood Explanation
Preconditions: Emporium must hold a nonzero balance of some ERC20 token that is not currently the subject of the attacker's `erc20TokenAddresses` array. This is plausible whenever any prior Emporium action's `op` set produces or receives a token not declared in that call's `erc20TokenAddresses` (e.g., swap remainder, reward token, fee-on-transfer excess) — such dust is not reclaimed by any other mechanism. The attacker only needs to be able to call `transact()` (any `onlyAllowedRecipient` caller — this is a permission on the recipient/relay list managed by `ExternalActionBaseUpgradeable`, not a privileged Hinkal role) and generate a proof for their own self-chosen `messageSeed`, which is trivial since `MainEVMCircuitMin` imposes no meaningful constraint. Cost is one transaction; the exploit is fully repeatable against any Emporium dust balance.

### Recommendation
Do not let `stack.ops` execute (or at minimum, do not let it move ERC20/ETH balances) when `circomData.erc20TokenAddresses.length == 0` / when `MainEVMCircuitMin` is used. Concretely:
- Bind the min-circuit public inputs to a commitment/hash of `externalActionData.externalActionMetadata` (the ops) so the circuit actually constrains what is executed, and/or
- In `EmporiumUpgradeable.runAction`, always compute `balancesBefore`/`balancesAfter` over the full set of tokens touched by `stack.ops` (not just `circomData.erc20TokenAddresses`), and always enforce `balanceChange >= 0`/full conservation regardless of whether the min-circuit path was used.
- Require signature verification over `stack.ops` unconditionally (never skip it just because `signerAddress == address(0)`), or disallow `invokeWallet=false` stateless calls entirely when `signerAddress == address(0)`.

### Proof of Concept
1. Deploy Hinkal + `EmporiumUpgradeable`, register a token `USDC`.
2. Seed Emporium with `X` USDC via any legitimate flow that leaves USDC undeclared in that call's `erc20TokenAddresses` (or simply `deal(USDC, address(emporium), X)` to model accumulated dust, since the question's premise stipulates this precondition).
3. Attacker calls `Hinkal.transact(a,b,c,dimensions,circomData)` where:
   - `circomData.erc20TokenAddresses = []`
   - `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `circomData.externalActionData.externalActionMetadata` encodes `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: USDC, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker, X))}] }`
   - proof generated locally by attacker for `MainEVMCircuitMin` with attacker-chosen `messageSeed`.
4. Assert: `USDC.balanceOf(emporium)` decreases by `X`, `USDC.balanceOf(attacker)` increases by `X`.
5. Assert: no `outCommitments`/UTXO was inserted compensating for `X`, and `deltaAmountChanges` array passed into `runAction` had length 0 (confirm via trace) — i.e., the value-conservation equality (`balanceChange == -deltaAmountChanges[i]` summed over declared tokens) was never evaluated for USDC.
