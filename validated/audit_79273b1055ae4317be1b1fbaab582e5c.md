### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are read directly from unauthenticated HTTP headers. Any party that can obtain one validly-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a genuine webhook) can replay that same body/HMAC combination while substituting an arbitrary `X-Shopify-Shop-Domain` header. The signature check still passes because the header is not part of the signed material, so the registered handler executes believing the webhook belongs to a different shop.

### Finding Description
`to_signable_string` in `ShopifyAPI::Webhooks::Request` returns only `@raw_body`: [1](#0-0) 

while `shop` is read from the `shopify-shop-domain` header without any cryptographic binding to the signature: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e., the raw body) against the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` trusts `request.shop` after only checking the HMAC, and forwards it unverified into the handler's metadata: [4](#0-3) 

The `api_secret_key` used to sign webhooks is a single, app-wide secret shared across every shop that installs the app — it is not per-shop. Consequently, a valid `(body, hmac)` pair generated for one shop's webhook remains cryptographically valid for that same body regardless of which shop's domain is asserted in the (unsigned) header. This is the same class of defect as the referenced advisory: the signature does not cover the identity field (`PeerId` there, `shop` here) that the code subsequently trusts to determine "whose data is this."

Binding broken (equality that should hold but doesn't):
`shop_header_used_by_handler == shop_that_actually_produced_the_signed(body, hmac)`
The check only verifies `hmac == HMAC(secret, body)`; it never verifies that `shop_header` is bound to that specific `(body, hmac)` pair.

### Impact Explanation
An attacker who can obtain any one legitimately-signed webhook payload for the app (trivial to obtain by installing the app on their own store, or by any store that receives webhooks from the app) can replay that exact body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop. Any handler logic keyed off `WebhookMetadata#shop` — e.g., updating that shop's local database record, revoking access, redacting shop data (`shop/redact`), processing `customers/redact` or `customers/data_request`, or reacting to `app/uninstalled` — would be executed against the wrong tenant. This is a cross-tenant integrity issue: data or actions intended for one merchant can be misattributed to another merchant purely by header manipulation, which qualifies as "cross-tenant access" under the High/Critical impact bar.

### Likelihood Explanation
Likelihood is moderate-to-high for an app that keys any per-shop side effects off `WebhookMetadata#shop`: the attacker only needs (a) their own shop's install of the target app to receive one legitimate webhook of any topic, and (b) network access to the app's public webhook endpoint to replay the captured request with a different shop header — no access token, secret, or privileged account is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the HMAC-signable string so the signature cryptographically binds the shop identity to the payload, mirroring how `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed parameters (`lib/shopify_api/auth/oauth/auth_query.rb`). At minimum, document/enforce that consumers must independently verify `data.shop` against a known/registered shop list before acting, since the gem currently offers no cryptographic guarantee that the header is authentic.

### Proof of Concept
1. Register the app as a normal merchant on shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) so Shopify sends a legitimately HMAC-signed request to the app's webhook endpoint. Capture `raw_body` and the `X-Shopify-Hmac-Sha256` header value.
2. Replay the identical HTTP request to the same endpoint, keeping `raw_body` and the HMAC header unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only hashes `raw_body`: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload/HMAC actually originated from `attacker.myshopify.com`, causing the app to act on the wrong tenant.
