### Title
Stale `deadline: block.timestamp` in `EvmHost` native-fee swaps provides no MEV/staleness protection - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all convert user-supplied native token (`msg.value`) into `feeToken` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`, using `block.timestamp` as the swap `deadline`, exactly the pattern flagged in the referenced Beedle `Fees::sellProfits()` report. `IntentGatewayV2.placeOrder()` contains the identical pattern for its fee-swap leg.

### Finding Description
Uniswap's `deadline` parameter is meant to bound how long a signed/submitted transaction may sit in the mempool before it can be executed, protecting the sender from a miner/validator or searcher holding the transaction until the price becomes maximally unfavorable. Passing `block.timestamp` as the deadline is a well known anti-pattern: `block.timestamp` is evaluated in the context of the block that finally mines the transaction, not the block in which the caller signed/submitted it. As a result the check `deadline >= block.timestamp` inside the router is always true regardless of how long the transaction was withheld — it provides zero real protection against a delayed/held execution.

This exact anti-pattern appears in the reachable, unprivileged dispatch surface of `EvmHost`: [1](#0-0) 

and again in the GET-request and fee-top-up paths: [2](#0-1) [3](#0-2) 

and in `IntentGatewayV2.placeOrder()`'s fee-token conversion: [4](#0-3) 

All four call sites are reachable from a single, unauthenticated `dispatch()`/`fundRequest()`/`placeOrder()` transaction sent with `msg.value > 0` — i.e. any user paying protocol/relayer fees in native token, which is the documented, recommended UX path (`docs/content/developers/evm/messaging/post-requests.mdx`, `get-requests.mdx`).

### Impact Explanation
Because `swapETHForExactTokens` requests a **fixed output amount** (`post.fee` / `get.fee` / `order.fees`) with `amountInMax = msg.value`, a searcher/validator holding the transaction cannot make the caller pay *more than msg.value*, and unused ETH is generally refunded by the router/gateway. This bounds the worst case compared to the original Beedle report (which used `exactInputSingle` with `amountOutMinimum: 0`, i.e., unlimited downside on price). Consequently the severity here is materially lower than a "lose a lot of funds" scenario: the primary residual risk is that a held transaction can be executed at a stale/manipulated price, consuming a larger portion of the user's supplied ETH than intended before any refund, and enabling a validator/searcher to selectively delay execution until conditions favor them (classic MEV timing exploitation), but it does not expose the protocol/user to unbounded slippage loss the way the original report describes, since the input is capped by `msg.value` and (in `IntentGatewayV2`) unspent value is explicitly refunded (`_sendValue(msg.sender, msgValue)` at `evm/src/apps/IntentGatewayV2.sol:394-397`).

### Likelihood Explanation
Any unprivileged actor calling `dispatch()`, `fundRequest()` on `EvmHost`, or `placeOrder()` on `IntentGatewayV2` with native-token payment triggers this code path. A block builder/validator (or a searcher paying for priority) can trivially hold or reorder the transaction to a block they control the price context for, since no real expiration is enforced.

### Recommendation
Replace `deadline: block.timestamp` with a caller-supplied, bounded deadline parameter (e.g., `block.timestamp + maxDelay`) computed at transaction-construction time and passed through `DispatchPost`/`DispatchGet`/`fundRequest`/`Order`, so the deadline check is meaningful against the time the transaction was authored rather than the time it is mined.

### Proof of Concept
1. Attacker (validator/searcher) observes a pending `EvmHost.dispatch(DispatchPost)` (or `fundRequest`/`IntentGatewayV2.placeOrder`) transaction carrying `msg.value > 0`.
2. Because `deadline` is computed as `block.timestamp` at execution time, the attacker can withhold the transaction across multiple blocks without it ever reverting for staleness.
3. The attacker times inclusion of the transaction to a block where the WETH/feeToken pool price is most unfavorable to the sender (e.g., after sandwiching the pool), maximizing the ETH consumed by `swapETHForExactTokens` before any refund is issued, at no cost of reverted execution due to deadline enforcement.
