### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Webhooks::Registry.process` uses `HmacValidator.validate(request)` to authenticate the request and then trusts `request.shop` (derived from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header) when invoking the app's webhook handler. Because the shop identifier is not part of the signed payload, its value can be swapped for any string while a *validly-signed* body/HMAC pair is replayed, breaking the binding between "shop whose secret signed this request" and "shop the handler is told the data belongs to."

### Finding Description
The HMAC that authenticates a webhook is computed only over `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from client-controlled HTTP headers and are never included in `to_signable_string`: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, and then forwards `request.shop` unchanged (and un-rebound to the signed content) to the app-supplied handler: [3](#0-2) 

Since the app's `client_secret`/`api_secret_key` is the *same* value used to sign webhooks for every shop that has the app installed, any actor who can obtain one validly-signed `(raw_body, hmac)` pair for their own shop (e.g., by installing the app themselves and receiving a real webhook, or intercepting/replaying one) can resend that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `HmacValidator.validate` only recomputes the HMAC over the body and compares it — it never re-derives or binds the `shop` field — so the forged request passes validation and the handler is invoked with `data.shop` equal to the attacker-chosen victim shop domain rather than the shop that actually produced the signed body.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the gem should enforce is `shop_that_signed_body == shop_delivered_to_handler`, but the gem only enforces `hmac(body) == received_hmac`.

### Impact Explanation
Any application built on this gem that keys per-shop authorization, data isolation, or side effects (e.g., "look up webhook_id/shop in our DB", "attribute this order/payload to shop X") off `WebhookMetadata#shop` is exposed to cross-tenant data confusion: an attacker-controlled shop domain string is delivered as if it were authenticated, letting one tenant's legitimately-signed traffic be relabeled and attributed to a different, victim tenant. This matches the Critical "cross-tenant access" impact category, since the shop identity is the tenant boundary for this gem's session/authorization model.

### Likelihood Explanation
Exploitation requires no possession of `api_secret_key`, access tokens, or privileged accounts — only a self-service app installation (or any other means of obtaining one legitimately-signed webhook body/HMAC pair) plus the ability to POST an HTTP request with attacker-chosen headers to the app's public webhook endpoint. The header/body split of the HMAC computation is inherent to how `Request#to_signable_string` and `Registry.process` are implemented in this gem.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is verified, e.g., verify the `x-shopify-shop-domain` header against the destination context that established the webhook (or include shop/topic in `to_signable_string`) before trusting `request.shop`, or require callers of `Registry.process` to independently confirm the shop is one they registered for prior to acting on `data.shop`. At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated and must not be trusted for tenant-isolation decisions without an independent cross-check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (or otherwise obtains one legitimate webhook delivery) and receives a real webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker resends `POST /webhook` to the victim app with the same body `B` and same `hmac-sha256` header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and compares it to `H` — it matches because `B` is unchanged.
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the signed payload was never produced for that shop. [4](#0-3)
