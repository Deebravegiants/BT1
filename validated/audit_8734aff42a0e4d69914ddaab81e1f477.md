[1](#0-0)  is the closest structural analog found. No other in-scope, unprivileged-account-reachable "nonreentrant-guard" pattern exists elsewhere in the runtime — everything else in the transaction/receipt/action pipeline (`process_action_receipt`, `PromiseYield`/`PromiseResume` handling) is explicitly designed to be idempotent and safely discards duplicate/late resumes rather than reverting [2](#0-1) , so those are not valid analogs. The wallet-contract's boolean guard, however, mirrors the report's "nonreentrant flag that can get stuck and permanently block forward progress" bug class, and it is reachable simply by calling `rlp_execute` as an ordinary unprivileged account.

### Title
`WalletContract.has_in_flight_tx` guard can be permanently stuck `true`, permanently DoSing the eth-wallet-contract account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` uses a boolean reentrancy-style guard, `has_in_flight_tx`, to enforce that only one Ethereum-emulated transaction is "in flight" at a time [3](#0-2) . The flag is set to `true` right before a promise chain is dispatched, and is only ever reset to `false` at the very start of the corresponding `#[private]` callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) [4](#0-3) [5](#0-4) [6](#0-5) . Because NEAR receipt execution is atomic — a `FunctionCall` action that fails (e.g., runs out of the small fixed gas budgeted for the callback, such as `RLP_EXECUTE_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`, all only 5–15 Tgas [7](#0-6) ) — discards **all** state writes made during that receipt, the `self.has_in_flight_tx = false` write is rolled back along with everything else if the callback itself later fails for any reason (e.g. `GasExceeded`/`GasLimitExceeded` from `runtime/near-vm-runner`). There is no other code path, timeout, or admin/reset function that can clear `has_in_flight_tx` once this happens.

### Finding Description
This is directly analogous to the reported bug class: a boolean/"locked" reentrancy guard is flipped to a blocking state before an external/cross-contract call, and is only cleared by a callback that is expected — but not truly guaranteed — to run to completion and commit its state change. In the Sherlock report, Chainlink VRF's own `nonReentrant` lock caused a second call within the same call stack to revert, permanently stalling the "drawn" state. In `WalletContract`, the analog is subtler but structurally the same: `has_in_flight_tx` is committed as `true` in one receipt and is supposed to be committed back to `false` in a follow-up receipt's callback, but that follow-up receipt is itself gas-budgeted by a small fixed constant computed by the contract author, not by the actual dynamic cost of the downstream call and callback logic. If that budget is exceeded (out-of-gas), or if any host error/panic occurs partway through the callback for any other unforeseen reason, the entire receipt — including the `has_in_flight_tx = false` state mutation — is discarded, per the runtime's guarantee that failed `FunctionCall` execution reverts all state changes for that receipt. Once `has_in_flight_tx` remains stuck at `true`, `rlp_execute` unconditionally short-circuits every future call with `"transaction already in progress, please try again later"` [8](#0-7) , with "later" never actually arriving.

### Impact Explanation
This breaks core contract functionality for the affected eth-wallet-contract account: the account becomes permanently unable to process any further Ethereum-emulated transaction via `rlp_execute`, with no funds directly stolen but the wallet's usability fully bricked (matching the Medium-severity "breaks core contract functionality, rendering the contract useless" bar cited in the report's resolution). Unlike the LooksRare case, there is no governance/cancel path built into `WalletContract` to reset `has_in_flight_tx`; the invariant comment on the struct [9](#0-8)  asserts the guard is always correctly paired with a promise, but that invariant depends on the downstream/callback gas budget always being sufficient, which is not enforced by the protocol.

### Likelihood Explanation
Likelihood is a function of whether the fixed gas constants (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`) are ever insufficient for the actual work done in the callback (JSON parsing of arbitrary-sized cross-contract responses, `format!`, building further promises). Because these are small, hard-coded budgets rather than dynamically computed, any unusually large or adversarial payload from a called contract (e.g., an oversized `storage_balance_of`/registrar response) — reachable simply by having the wallet owner or a relayer target a malicious/unexpected `target`/token contract — could push the callback over its gas budget and trigger the stuck state.

### Recommendation
Do not rely solely on a leading `self.has_in_flight_tx = false` write inside a callback that can still fail later in the same receipt. Either (a) split "clear the guard" into its own minimal, gas-cheap operation that is executed and committed before any additional work that could fail, e.g. via a preceding trivial callback/receipt dedicated only to clearing the flag, or (b) add a use of `promise_batch_action_function_call_weight`/generous static gas plus explicit gas-based fallbacks so the reset is guaranteed to commit even under out-of-gas, and/or (c) add a permissionless recovery/timeout mechanism (e.g., allow the flag to be cleared if no callback has landed after N blocks) so the wallet is never permanently unusable.

### Proof of Concept
1. Deploy `WalletContract` for an eth-implicit account and call `rlp_execute` with a `target` pointing at a NEP-141 token contract (or the address registrar) that is made to return an unusually large/complex JSON payload from `storage_balance_of` (or `lookup`).
2. The resulting `nep_141_storage_balance_callback` (or `address_check_callback`) is executed with only `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS` of static gas [10](#0-9) ; craft the payload so that parsing/processing it exceeds that budget, causing the callback receipt to fail with an out-of-gas host error after `self.has_in_flight_tx = false` was written but before the receipt commits.
3. Because the receipt fails, the entire state diff (including the flag reset) is discarded; `has_in_flight_tx` remains `true` in the persisted contract state.
4. Any subsequent call to `rlp_execute` by the legitimate wallet owner now immediately returns `ExecuteResponse { success: false, error: Some("Error: transaction already in progress, please try again later.") }` [8](#0-7)  forever, since no code path exists to clear the flag outside of a callback that itself never gets a chance to commit.
