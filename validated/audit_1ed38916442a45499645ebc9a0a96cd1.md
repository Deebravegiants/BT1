### Title
Unbounded array allocation from attacker-controlled SCALE compact length in `Codec.DecodeHeader` allows gas-exhaustion DoS on BEEFY parachain header verification - (File: `evm/src/consensus/Codec.sol`)

### Summary
`Codec.DecodeHeader` reads a SCALE compact-encoded digest count directly from the untrusted `para.header` bytes and immediately allocates a memory array of that size, before any bound check against the remaining bytes in the slice or any cap on the maximum number of digests. Because the mode-2/mode-3 branches of `decodeUintCompact` can return values up to `4503599627370496` (mode 3, `uint256` decoded from up to 8 bytes), an attacker can force `new Digest[](length)` to attempt an enormous memory allocation, triggering the classic "memory allocation with excessive size value" pattern from the reported GitLab issue, applied here to the header-decoding step of Hyperbridge's BEEFY consensus client.

### Finding Description
`Codec.DecodeHeader` in [1](#0-0)  decodes:

```
uint256 length = ScaleCodec.decodeUintCompact(slice);
Digest[] memory digests = new Digest[](length);
```

`length` comes straight from `decodeUintCompact`, which for a `mode == 3` prefix returns `ScaleCodec.decodeUint256(read(data, l))` with `l` up to 8 bytes [2](#0-1) , i.e. a value up to `2^56`-ish is fully attacker-controlled and not checked against the actual remaining length of `encoded`. The subsequent `new Digest[](length)` allocation happens unconditionally, before the loop that would eventually revert on `readByte`/`read` bounds checks [3](#0-2) . Solidity memory arrays of struct type are zero-initialized on allocation, so the EVM must pay (and execute) memory-expansion cost proportional to `length * sizeof(Digest)` before a single bounds-check revert can fire in the loop body.

This function is called from `EcdsaBeefy.verifyParachainHeaderProof` on `para.header`, which is part of the caller-supplied `ParachainProof` and is decoded via `Codec.DecodeHeader(para.header)` *before* the corresponding merkle multi-proof against `headsRoot` is checked (that check only happens after the loop) [4](#0-3) . The same `Codec.DecodeHeader`/digest-decoding path is shared by `SP1Beefy.sol`.

### Impact Explanation
`EcdsaBeefy.verify` (and the SP1 variant) is the `IConsensusV2` entry point invoked whenever a relayer submits a new consensus proof to update the trusted state and deliver intermediate parachain state commitments. Because `para.header` bytes are not validated against `headsRoot` until *after* `DecodeHeader` runs, any caller who can produce a `RelayChainProof` that passes the (legitimate, signature-gated) MMR update step — which is public, observable, and can be paired with an arbitrary, unrelated `ParachainProof.parachains[i].header` — can force the header-decoding path to attempt a massive memory allocation. This causes the consensus-update transaction to consume gas quadratically in the fabricated compact length, forcing an out-of-gas revert (or making the call prohibitively expensive to include), effectively denying the ability to deliver new intermediate states/finalize parachain headers through this consensus client — a route made unable to deliver messages, which is one of the explicitly accepted impact classes.

### Likelihood Explanation
Medium. The attacker does not need to forge relay-chain authority signatures — they only need a validly-signed `RelayChainProof` (which is publicly derivable from real relay chain data, since BEEFY commitments and signatures are public) and can then freely substitute the `ParachainProof.parachains[i].header` bytes, since that content is unchecked until after decoding. Constructing the malicious compact-length prefix requires only a few crafted bytes at the start of `para.header`. The main constraint is that a fresh, unconsumed relay commitment (with `blockNumber` greater than the currently trusted height) is required for each attempt, but these become available continuously as the relay chain finalizes new blocks/commitments.

### Recommendation
- Bound the decoded digest `length` against the remaining bytes in `slice` (e.g. require `length <= (encoded.length - slice.offset)`) and/or enforce an explicit maximum digest count before calling `new Digest[](length)`.
- More generally, apply the same "reject unreasonable declared length before allocating" pattern used elsewhere in the codebase (e.g. `MAX_VALIDATORS`/`MAX_PROOF_DEPTH` checks in `modules/consensus/pharos/...`) to all SCALE/compact-length-driven allocations in `Codec.sol`.
- Consider moving the header-inclusion merkle-proof check (`MerkleMultiProof.VerifyProof(headsRoot, ...)`) in `EcdsaBeefy.verifyParachainHeaderProof` before/interleaved with `Codec.DecodeHeader`, so unauthenticated header bytes are never decoded before being proven to belong to the finalized `headsRoot`.

### Proof of Concept
1. Attacker observes a legitimate, currently-valid `RelayChainProof` (public BEEFY commitment + authority signatures + valid MMR proof) whose `commitment.blockNumber` exceeds the light client's `latestHeight`.
2. Attacker crafts a `ParachainProof` where `parachains[0].header` begins with a SCALE compact prefix selecting `mode == 3` with `l == 8`, encoding `length ≈ 2^56` digests, followed by arbitrary/garbage bytes (this need not correspond to any real chain data since it isn't checked until later).
3. Attacker calls `EcdsaBeefy.verify(previousState, abi.encode(relay, parachain))`.
4. Execution passes `verifyMmrUpdateProof` (using the legitimate relay proof), then enters `verifyParachainHeaderProof`, which calls `Codec.DecodeHeader(para.header)`.
5. `DecodeHeader` executes `Digest[] memory digests = new Digest[](length)` with the attacker-chosen huge `length`, causing the EVM to attempt massive memory expansion and consume/exhaust the transaction's gas before the inner loop's bounds check (`Bytes.readByte`) can revert, denying processing of the legitimate parachain header update in that transaction.

    // @dev Deserializes a substrate header
    function DecodeHeader(bytes memory encoded) internal pure returns (Header memory) {
        ByteSlice memory slice = ByteSlice(encoded, 0);
        bytes32 parentHash = Bytes.toBytes32(Bytes.read(slice, 32));
        uint256 blockNumber = ScaleCodec.decodeUintCompact(slice);
        bytes32 stateRoot = Bytes.toBytes32(Bytes.read(slice, 32));
        bytes32 extrinsicsRoot = Bytes.toBytes32(Bytes.read(slice, 32));

        uint256 length = ScaleCodec.decodeUintCompact(slice);
        Digest[] memory digests = new Digest[](length);

        for (uint256 i = 0; i < length; i++) {
            uint8 kind = Bytes.readByte(slice);
            Digest memory digest;
            if (kind == DIGEST_ITEM_OTHER) {
                digest.isOther = true;
            } else if (kind == DIGEST_ITEM_CONSENSUS) {
                digest.isConsensus = true;
                digest.consensus = decodeDigestItem(slice);
            } else if (kind == DIGEST_ITEM_SEAL) {
                digest.isSeal = true;
                digest.seal = decodeDigestItem(slice);
            } else if (kind == DIGEST_ITEM_PRERUNTIME) {
                digest.isPreRuntime = true;
                digest.preruntime = decodeDigestItem(slice);
            } else if (kind == DIGEST_ITEM_RUNTIME_ENVIRONMENT_UPDATED) {
                digest.isRuntimeEnvironmentUpdated = true;
            }
            digests[i] = digest;
        }

        return Header(parentHash, blockNumber, stateRoot, extrinsicsRoot, digests);
    }
