## Finding: Duplicate `erc20TokenAddresses` entries let one real balance delta satisfy the balance equation multiple times, minting unbacked shielded UTXOs

### Root cause
`Hinkal.transact` checks a "balance equation" **per index `i`** of `circomData.erc20TokenAddresses`, comparing a real-token balance delta to the circuit-declared `amountChanges[i]` plus the newly created UTXO amount for that index: [1](#0-0) [2](#0-1) 

`oldBalances`/`newBalances` are fetched once via `getBalancesForArray(circomData.erc20TokenAddresses)` before and after the action, indexed positionally by the array — there is no dedup, so two indices that reference the **same real ERC20 address** read the exact same `balanceOf()` value at both snapshot points, meaning `balanceDif[i]` is identical for every index carrying that address.

Nothing enforces that `erc20TokenAddresses` entries are distinct: `dimensionsCheck` only checks array lengths against `Dimensions`, never uniqueness of addresses [3](#0-2) . On the circuit side, `MainEVMCircuit` enforces UTXO conservation (`inTotal`/`outTotal` vs `amountChanges[i]`) and commitment/nullifier correctness **independently per token index `i`**, using `erc20TokenAddresses[i]` only as a field baked into each commitment/nullifier hash — there is no cross-index constraint tying two indices with the same address together [4](#0-3) . `CircomDataBuilder.formBasicInput` likewise just lists each index's address/amountChange into the public input vector with no uniqueness pinning [5](#0-4) .

### Break in the equality
The intended invariant is: *for each distinct real token, its balance change equals the sum of on/off-chain shielded value created/destroyed for that token.* Because the check runs per array-index rather than per distinct address, a prover can list the **same** token address at two (or more) indices `i` and `k`. A single real deposit of `D` tokens produces `balanceDif[i] == balanceDif[k] == D`. The prover can then independently satisfy:
- index `i`: `D == amountChanges[i] + utxoAmount_i` (e.g. mint a shielded UTXO worth `D`)
- index `k`: `D == amountChanges[k] + utxoAmount_k` (mint a second shielded UTXO worth `D` for the same real token)

Both checks pass against the *same* underlying `D`, so the contract will accept a proof that inserts two valid, independently spendable commitments worth `D` each into the Merkle tree, backed by only one real deposit of `D` — i.e., shielded value is minted without matching on-chain backing.

### Impact
This maps to the "Critical" category explicitly listed as in-scope: *minting shielded value without backing*. It is unprivileged (any EOA constructing a valid Groth16 proof with a duplicated `erc20TokenAddresses` entry can attempt it), and does not rely on relayer/admin trust, oracle assumptions, or generated-verifier code — the break is purely in `Hinkal.sol`'s balance-equation loop and the absence of a uniqueness constraint in `HinkalHelper.dimensionsCheck`/the circuit.

### What I could not fully verify
- The exact semantics of `Transferer.getBalancesForArray`/`getERC20OrETHBalance` (I could not read `Transferer.sol` before the tool budget ran out) — confirming it does a plain positional `balanceOf` lookup per array entry (with no internal dedup) would close the loop definitively.
- Whether the actual circuit's private-input generation tooling (off-chain prover code, not in `circuits/**`) enforces distinctness of `erc20TokenAddresses` as a matter of practice — but on-chain/circuit code alone does not enforce it, so a malicious prover bypassing the official client is not prevented.

### Recommendation (conceptual, not a plan since this is Ask mode)
Add a uniqueness check on `circomData.erc20TokenAddresses` in `dimensionsCheck` (or in `Hinkal.transact` before the balance-equation loop), and/or aggregate `balanceDif` per distinct address instead of per raw index, so that a duplicated address cannot double-count a single real balance delta across multiple `amountChanges`/UTXO-creation slots.
