## Title
Webhook shop and topic identity are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but binds the HMAC signature to the raw request body only. The `shop` and `topic` values that `ShopifyAPI::Webhooks::Registry.process` trusts and hands to the host application's handler are read from unauthenticated HTTP headers that are never part of the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are read straight from HTTP headers, with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac` header value — it never incorporates `shop` or `topic`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to dispatch to the app's handler, treating the shop identity as authenticated even though it never entered the signature computation: [4](#0-3) 

Because the app's `api_secret_key` is a single shared secret used for every shop that installs the app (it is not per-shop), `HMAC(secret, body)` is identical for any two tenants that happen to receive/produce a byte-identical `body`. This is entirely plausible for templated or minimal webhook payloads (e.g. `app/uninstalled`, or any topic whose payload the app itself controls the shape of). The equality the code should enforce is:

`authenticated(shop) == shop_dispatched_to_handler`

but what is actually enforced is only:

`authenticated(raw_body) == raw_body`, with `shop` (and `topic`) taken on faith from an attacker-writable header.

### Impact Explanation
An attacker who can obtain (or predict) any one valid `(raw_body, hmac)` pair signed with the app's shared secret (for example, by being a legitimate/malicious merchant who installs the app and triggers a webhook with a predictable/templated body on their own store, or by any other means of observing one such pair) can replay that exact body and HMAC directly against the app's public webhook endpoint while setting the `shopify-shop-domain` (and `shopify-topic`) header to an arbitrary victim shop and topic. `Registry.process` will treat this as an authenticated webhook for the victim tenant and invoke the host application's webhook handler with attacker-chosen `shop`/`topic`/`body` combination, since only the body is actually verified. Depending on how the host app's webhook handler keys off `shop` (e.g., looking up or mutating tenant-specific state, session data, or triggering shop-scoped side effects), this breaks the tenant isolation boundary — a cross-tenant access primitive.

### Likelihood Explanation
Medium. It requires the attacker to have or produce at least one valid `(body, hmac)` pair for the shared app secret. This is realistic for apps that receive webhooks with fixed/templated bodies (common for lifecycle topics like `app/uninstalled`, `shop/redact`, or any topic whose payload the attacker's own shop can trigger and whose body content the attacker fully controls or can predict), since the secret is shared across all installs of the app, not scoped per shop.

### Recommendation
Bind the shop (and ideally topic) into the value being authenticated, or otherwise re-derive the shop identity from a source that itself is authenticated (e.g., cross-check `request.shop` against a shop the app already has an active, verified session/access token for, rather than trusting the header value as-is once the body HMAC passes). At minimum, document that `request.shop`/`request.topic` are not covered by the HMAC and must not be used as the sole tenant-identifying value for dispatch without additional verification against a known/authenticated session.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` with the app's shared `api_secret_key`.
2. Attacker triggers (or otherwise obtains) a webhook delivery whose body is predictable/fixed, e.g. raw body `{}`, computing/observing `hmac = HMAC-SHA256(api_secret_key, "{}")`.
3. Attacker sends a forged HTTP POST directly to the app's public webhook endpoint with:
   - `shopify-hmac-sha256: Base64(hmac)` (the valid, previously obtained value)
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: <any registered topic>`
   - body: `{}`
4. `ShopifyAPI::Webhooks::Request.new` is constructed from these headers/body; `HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, "{}")` against the supplied hmac — matching regardless of the `shop-domain` header value.
5. `Registry.process` dispatches to the registered handler with `shop: "victim-shop.myshopify.com"`, `topic: <attacker-chosen>`, even though this request never actually originated from Shopify for that shop. [4](#0-3) [5](#0-4)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
