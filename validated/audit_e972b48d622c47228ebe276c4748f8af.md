### Title
Infinite loop in GRANDPA `AncestryChain::ancestry` via a crafted two-header cycle in `votes_ancestries` - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry`, used while validating a GRANDPA justification's precommit ancestry, walks `parent_hash` pointers in a loop that only terminates when it reaches the trusted `base` hash or fails to find an entry. Because the header list it walks (`votes_ancestries`) is attacker-supplied, unvalidated data decoded straight out of the submitted consensus proof, an attacker can construct two headers whose `parent_hash` fields point at each other, forming a cycle that never reaches `base`. The loop then runs forever, exactly the "malicious size/structure in untrusted data causes unbounded loop" bug class described in CVE-2017-14934 (there: a corrupted CU size field in DWARF debug info drove `process_debug_info` into an infinite loop; here: forged parent-hash pointers drive `ancestry()` into an infinite loop).

### Finding Description
`AncestryChain` is built directly from `votes_ancestries: Vec<H>`, a field of `GrandpaJustification` that is SCALE-decoded from the raw proof bytes with no structural validation of the parent/child relationships between headers: [1](#0-0) 

The traversal function walks from `block` back toward `base` purely by following `parent_hash()`: [2](#0-1) 

`GrandpaJustification::verify` builds this `AncestryChain` from the fully attacker-controlled `votes_ancestries` list and then calls `.ancestry(base_hash, target_hash)` once per precommit, before any check exists that the header set is acyclic or bounded: [3](#0-2) 

Since headers are keyed by their own hash in a `BTreeMap`, an attacker can freely fabricate two headers `A` and `B` where `A.parent_hash == hash(B)` and `B.parent_hash == hash(A)`. Neither header's hash needs to equal `base` or the real chain's headers — this list is not yet checked against any trusted state at the point `ancestry()` is called. If the queried `block` (a precommit's `target_hash`) resolves into this two-cycle instead of into `base`, the `while current_hash != base` loop cycles `A -> B -> A -> B -> ...` forever without ever hitting a `None` entry that would return `Err(NotDescendent)`.

This is reachable from a single relayed consensus proof: `verify_consensus` in the ISMP GRANDPA client decodes the submitted proof into a `ConsensusMessage`, then calls `verify_grandpa_finality_proof` / `verify_parachain_headers_with_grandpa_finality_proof`, which in turn calls `GrandpaJustification::verify`: [4](#0-3) 

That consensus-update path is invoked by an unprivileged relayer submitting a consensus proof (pallet-ismp's unsigned consensus-update dispatch), so no special privilege is required to trigger it.

### Impact Explanation
The infinite loop occurs inside on-chain STF logic invoked from an unsigned/relayed extrinsic path with no per-iteration bound or weight metering tied to loop count. A single malicious consensus proof can hang the executing node/runtime call indefinitely, blocking further GRANDPA consensus updates for that state machine and, by extension, blocking delivery of any ISMP messages gated behind that consensus client's finality proofs — i.e., "a route unable to deliver messages," matching the accepted impact classes for this scan.

### Likelihood Explanation
Constructing two headers with mutually-referencing `parent_hash` fields is trivial — headers here are just SCALE-encoded structures under attacker control before any hash-chain validation against the trusted relay chain occurs. No cryptographic break is needed; only a self-consistent pair of fabricated header structs is required. Any relayer or user able to submit a GRANDPA consensus proof (an unprivileged action) can trigger this.

### Recommendation
Bound the `ancestry()` walk by the size of the `votes_ancestries`/`unknown_headers` map (e.g., cap iterations at `self.ancestry.len()` and return `Err(NotDescendent)` if exceeded), and/or track visited hashes in a set to detect and reject cycles before they cause unbounded looping.

### Proof of Concept
1. Craft header `A` with `parent_hash = hash(B)` and header `B` with `parent_hash = hash(A)` (arbitrary otherwise-valid header fields).
2. Include both in `votes_ancestries` of a `GrandpaJustification`, with a `commit.precommits` entry whose `target_hash == hash(A)` (or `hash(B)`), and a `base_hash` computed from the lowest-numbered precommit that is neither `hash(A)` nor `hash(B)`.
3. Submit this justification as the GRANDPA consensus proof via the ISMP consensus-update path (`GrandpaConsensusClient::verify_consensus`).
4. `GrandpaJustification::verify` calls `ancestry_chain.ancestry(base_hash, hash(A))`, which cycles `A -> B -> A -> ...` forever, hanging the call.

pub struct AncestryChain<H: HeaderT> {
	ancestry: BTreeMap<H::Hash, H>,
}

impl<H: HeaderT> AncestryChain<H> {
	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
