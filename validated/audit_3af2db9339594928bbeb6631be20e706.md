### Title
Unrestricted route venues can attach wallet-draining transfers to a caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept caller-supplied swap payloads and invoke the configured router while the account owner’s authorization is active. Although the controller narrowly authorizes only `token_in.transfer(controller, router, amount_in)`, the route can name an arbitrary venue contract that runs below the caller’s authorization tree. That venue can require authorization for an unrelated `token.transfer(caller, attacker, amount)`. Simulation records the malicious transfer as a child of the strategy call, and execution succeeds if the caller signs that simulated tree. The controller’s balance-delta checks cover only the strategy’s input and output tokens, so they do not detect or bound the unrelated wallet transfer. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`swap_collateral` authenticates the account owner or delegate, withdraws the requested collateral to the controller, and passes the caller-provided `swap` bytes into `swap_tokens`. [4](#0-3)  `swap_tokens` authorizes one exact controller-to-router input transfer and then calls `router.execute_strategy(controller, amount_in, swap)` inside the flash guard. [5](#0-4) 

The router decodes the payload and dispatches each swap hop to the pool address selected by the payload. [2](#0-1)  There is no venue/pool allowlist at that dispatch boundary; the router treats the payload-selected address as executable venue code and checks only that exactly `amount_in` was spent and positive output was received. [6](#0-5) 

Because the malicious venue executes under the user-authorized controller call stack, it can request the caller’s token authorization for an unrelated transfer. An honest simulation exposes that transfer as a child authorization, but if the caller signs the resulting tree, the token transfer succeeds even though it is unrelated to the swap. The test fixture demonstrates this behavior through `swap_collateral`: the rogue pool drains Alice’s entire unlisted wallet token while still returning a fair ETH output and completing the collateral swap. [7](#0-6) [8](#0-7) 

### Impact Explanation
This permits theft of user funds outside the routed collateral amount. The attacker can drain any token balance held by the signer if the signed authorization tree contains the malicious child transfer, while the strategy itself can remain economically valid and pass the controller’s output and final account-risk checks. The affected surface includes the swap-routed controller strategies such as `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply`, because they all route caller-provided swap payloads through the same settlement path. The direct router `execute_strategy` path has the same exposure. [3](#0-2) 

This is a High-severity analogue: exploitation requires user interaction/signing of the poisoned authorization tree, but the consequence can be complete loss of unrelated wallet assets rather than merely poor swap execution.

### Likelihood Explanation
An unprivileged route producer can construct swap bytes naming an attacker-controlled venue address. The venue does not need to be a real DEX pool; it only has to satisfy the router’s measured input/output expectations, which can be done by returning an acceptable output token amount while separately requesting a transfer from the caller. The transaction’s simulation records the malicious child authorization, so exploitation depends on a wallet, frontend, or user approving that tree without rejecting the unrelated transfer. The protocol documentation explicitly states that a route can place third-party code below the caller’s authorization and that the caller’s wallet loss is not bounded by the route minimum or final risk gate. [3](#0-2) 

### Recommendation
Do not invoke arbitrary payload-selected pool addresses while a user authorization is active. Enforce an on-chain allowlist of venue contracts or fixed venue adapters in the router, and have the controller reject opaque routes unless they resolve to admitted venues. Clients should additionally simulate and display the complete authorization tree and refuse any strategy transaction containing token transfers outside the expected input movement. [9](#0-8) [10](#0-9) 

### Proof of Concept
A minimal path is:

1. Alice owns a lending account with USDC collateral and also holds an unrelated wallet token.
2. The attacker deploys a contract with a `swap` method that calls `token.transfer(Alice, attacker, wallet_balance)`.
3. The attacker provides Alice a `swap_collateral` transaction whose route names that contract as a hop pool.
4. `swap_collateral` authenticates Alice, withdraws USDC to the controller, and invokes the router with the malicious `swap` bytes. [11](#0-10) 
5. The router invokes the attacker contract during hop dispatch. [12](#0-11) 
6. Simulation records `wallet_token.transfer(Alice, attacker, balance)` as a child of Alice’s `swap_collateral` authorization. [13](#0-12) 
7. If Alice signs that tree, the rogue transfer executes: Alice’s unrelated token balance becomes zero, the attacker receives it, and the strategy still deposits fair swap output into her account. [8](#0-7)

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
