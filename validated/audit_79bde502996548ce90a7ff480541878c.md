I found a concrete privilege-boundary bug matching the CVE's "non-admin users having access to read and modify configuration or other components that should only be accessible by admin users" pattern.

### Title
Any authenticated user (including View-only role) can read External Initiator outgoing credentials via `GET /v2/external_initiators` - (File: core/web/router.go)

### Summary
The `/v2/external_initiators` listing endpoint is registered without any role-gating middleware, so any authenticated API user regardless of role (including the lowest-privilege `view` role) can enumerate all configured External Initiators and their `AccessKey`/`OutgoingToken` credentials, which are secret-equivalent values used to authenticate outbound webhook calls from the node.

### Finding Description
In `core/web/router.go`, the route group is:
```go
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))
authv2.DELETE("/external_initiators/:Name", auth.RequiresEditRole(eia.Destroy))
``` [1](#0-0) 

Only `Create` and `Destroy` are wrapped by `auth.RequiresEditRole`; `Index` (the `GET` list handler) has no role check at all, so it is reachable by any user who passes only the base `auth.Authenticate` middleware — i.e. a `view` role user. The `ExternalInitiatorsController.Index` handler returns the full `ExternalInitiatorResource` (including `AccessKey` and `OutgoingToken`) for every initiator with no redaction:
```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}
	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
``` [2](#0-1) 

`ExternalInitiatorResource` explicitly serializes `AccessKey` and `OutgoingToken`:
```go
type ExternalInitiatorResource struct {
	JAID
	Name          string         `json:"name"`
	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`
	UpdatedAt     time.Time      `json:"updatedAt"`
}
``` [3](#0-2) 

This is confirmed by the test asserting the response body carries `AccessKey` and `OutgoingToken` for every listed initiator: [4](#0-3) 

This directly matches the RBAC test map, which explicitly documents `/v2/external_initiators` GET as `viewOnlyAllowed: true`:
```go
{"GET", "/v2/external_initiators", true, true, true},
{"POST", "/v2/external_initiators", false, false, true},
{"DELETE", "/v2/external_initiators/MOCK", false, false, true},
``` [5](#0-4) 

By contrast, comparable credential-bearing surfaces (`AccessKey`/private key export endpoints) are gated at `RequiresAdminRole` (e.g. `keys/csa/export`, `keys/eth/export`), and the overall auth model in `core/web/auth/auth.go` defines a 4-tier role hierarchy (`view` < `run` < `edit` < `admin`) intended to segregate exactly this kind of access [6](#0-5) . The External Initiator listing endpoint breaks that segregation model since `AccessKey`/`OutgoingToken` are effectively bearer credentials (used for `AuthenticateExternalInitiator` and outbound requests) but are exposed to the lowest-privilege role instead of at minimum `edit` (which is required to `Create`/`Destroy` them).

### Impact Explanation
A `view`-role API user or token holder — intended only to observe non-sensitive state — can retrieve the `AccessKey` and `OutgoingToken` for every External Initiator configured on the node. `AccessKey`+`Secret` pairs are the credential used by external initiators to call back into the node's job-run endpoints (`AuthenticateExternalInitiator`), and `OutgoingToken`/`OutgoingSecret` are used by the node to authenticate to the initiator's webhook. Leaking `AccessKey`/`OutgoingToken` to an unprivileged, low-trust user allows that user to impersonate the external initiator relationship or replay/forge calls that should only be available to `edit`/`admin` operators, matching the CVE's class of unauthorized read access to privileged configuration/component data by a non-admin user.

### Likelihood Explanation
Any legitimately provisioned `view`-role user (the lowest tier explicitly supported by the RBAC system, intended for read-only dashboards/monitoring) can trigger this with a single authenticated `GET /v2/external_initiators` request — no special conditions, race, or additional access are required.

### Recommendation
Wrap the `Index` route with at least `auth.RequiresEditRole` (matching `Create`/`Destroy`), or better, strip `AccessKey`/`OutgoingToken` from the list resource returned to non-privileged roles (similar to how private-key material export endpoints are separated from list endpoints elsewhere).

### Proof of Concept
1. Create an API user with role `view` (`chainlink admin users create --role view`).
2. Have an `edit`/`admin` user create at least one External Initiator: `POST /v2/external_initiators {"name":"bitcoin","url":"https://example.com"}` (returns `AccessKey`/`Secret`/`OutgoingToken`/`OutgoingSecret` at creation time, but not needed for the exploit).
3. Log in as the `view` user and call `GET /v2/external_initiators`.
4. Observe the JSON response contains `accessKey` and `outgoingToken` fields for the initiator created in step 2, as validated by `TestExternalInitiatorsController_Index` [7](#0-6) , confirming a `view`-role user obtained credential material intended to be restricted to `edit`/`admin` roles.

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
