This confirms the vulnerability. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC over the request via `Utils::HmacValidator.validate(request)`, but the signable content for `Webhooks::Request` is defined in `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) as `@raw_body` only — it does not include the `X-Shopify-Shop-Domain` header. Yet `request.shop` (read straight from that unsigned header at `lib/shopify_api/webhooks/request.rb:20-23`) is passed on to the app's handler as the tenant identifier (`WebhookMetadata.new(..., shop: request.shop, ...)` at `registry.rb:198`), and the gem's own documentation (`docs/usage/webhooks.md:12-16`) tells integrators to trust `data.shop` as "The shop domain of the webhook."

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw body, excluding the `shop-domain` header that `Registry.process` forwards to the app's webhook handler as the authenticated tenant identifier.

### Finding Description
`Registry.process` gates webhook handling on `Utils::HmacValidator.validate(request)` returning true, treating that as proof the whole request came from Shopify for the shop it claims. However `HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes the HMAC exclusively over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop` value read via `shopify_header("shop-domain")` (`request.rb:20-23`) sits entirely outside the signed content.

The breaking identity binding is:
`shop authenticated by HMAC` ≠ `shop used to route/attribute the webhook` (`request.shop` passed into `WebhookMetadata` at `registry.rb:198`).

Because the app's secret (`api_secret_key`) is shared across all shops installed on that app, any body+HMAC pair the app validly receives for one shop is a valid HMAC for that same body regardless of which shop-domain header accompanies it — the signature never binds body to shop. An attacker who can get one legitimate webhook delivered (e.g., by installing the app on their own shop and triggering an event) obtains a genuinely-signed `(raw_body, hmac)` pair, then replays that exact body and hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` proceeds to call the handler with `shop: <victim shop>`. ### Impact Explanation
This is a cross-tenant integrity/spoofing issue: an attacker-controlled shop can forge webhook events that are processed as if they came from an arbitrary victim shop, since the gem itself certifies the forged request as HMAC-valid. Any downstream logic keyed on `data.shop` (the gem's documented contract, `docs/usage/webhooks.md:12-16`) — e.g. updating per-shop records, marking uninstall/redact for `shop/redact` mandatory topics, feeding order/customer data into the wrong tenant's records — can be corrupted for a shop the attacker doesn't own. This meets the "cross-tenant access" Critical impact bar since the gem's verification primitive is what the host app is told to rely on to establish tenant identity.

### Likelihood Explanation
Likelihood is high for any app that has at least one other legitimate, attacker-accessible installation (trivial for public/free-plan apps): the attacker needs no secrets, only the ability to receive one real webhook to their own store and replay its body/HMAC with a modified shop-domain header against the shared webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed content used to validate webhooks, or independently cross-check `request.shop` against the shop tied to the session/installation that this specific `hmac` was previously observed for. At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant attribution without additional verification (e.g., comparing against a known/installed shop list) — but the safer fix is to make `HmacValidator`/`Registry.process` bind the shop header into the verified signature space, e.g. by extending `to_signable_string` to include the shop-domain header, or by having `Registry.process` reject requests whose shop is not a shop with an active installation for this app.

### Proof of Concept
1. App is installed on `attacker.myshopify.com` (attacker's own store) and on `victim.myshopify.com`.
2. Attacker triggers a real event (e.g. `products/update`) on their own store; Shopify sends a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` (e.g., via a proxy they control, or simply by being the recipient in a test harness they run).
4. Attacker (or any actor who can reach the app's public webhook endpoint) resends an HTTP request to the same endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully (all required headers present); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares to `H` — it matches, since the shop header was never part of the signed input.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on the victim shop's tenant data using attacker-controlled body content.
