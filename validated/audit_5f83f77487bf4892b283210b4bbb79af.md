### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but the shop identity that the gem hands to the application's handler is read from an HTTP header that is never included in that signature. This breaks the binding `HMAC-authenticated bytes == identity trusted by the handler`, analogous to the reported fyDAI flaw where `flashMint` (an operation without an internal invariant check) let an attacker reach `redeem`, a function whose safety depended on an assumption (maturity/ownership) that wasn't actually enforced against the calling context.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) 

The HMAC is verified only over `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from unauthenticated HTTP headers, with no cryptographic tie to the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches the handler using the unauthenticated `request.shop`: [4](#0-3) 

This is exactly the pattern the rules flag: "a field acted on but not covered by the HMAC." `Utils::HmacValidator.validate` proves only that the body bytes were signed with the app's secret; it says nothing about which shop the signer intended, yet `WebhookMetadata#shop` is treated by the handler as the authenticated tenant identity.

### Impact Explanation
Because `shop` is outside the signed data, any actor who can obtain one valid `(body, hmac)` pair — trivially possible by installing the app on their own (even free/dev) store and receiving one legitimate webhook for it — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. The gem will report `HmacValidator.validate` as `true` and hand the handler a `WebhookMetadata` claiming the payload belongs to the victim tenant. Any host application that uses `WebhookMetadata#shop` to select which merchant's records to update (the documented and expected usage) can be made to apply attacker-controlled webhook data to another tenant, i.e., cross-tenant access/data corruption — a Critical-severity outcome under the defined impact list.

### Likelihood Explanation
The attacker only needs to control any shop where the app is installed (no elevated privileges, no access to `api_secret_key`, no TLS interception) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint, which is by definition internet-reachable. This is a realistic, unprivileged-attacker scenario as required by scope.

### Recommendation
- **Short term:** Include the shop domain (and ideally topic/webhook id/api version) as part of the HMAC signable string, or otherwise cryptographically bind them to the signed payload, so header values cannot be substituted independently of the verified body. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host app against its own session store before use.
- **Long term:** Avoid exposing any identity field to consumers of `Registry.process`/`WebhookMetadata` that is not itself covered by the same integrity check used to accept the request, mirroring the general principle from the report of not letting an operation manipulate data whose provenance isn't fully constrained by the same trust boundary.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook event (e.g., `orders/create`). Shopify POSTs body `B` with `X-Shopify-Hmac-Sha256: H = HMAC-SHA256(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com` to the app's webhook URL.
2. Attacker captures `(B, H)` from their own server/logs (this is their own data, no interception of a third party needed).
3. Attacker sends a new POST to the same webhook endpoint using the same raw body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `#hmac` and `#to_signable_string` are unchanged from step 1 (both derive only from `B`/`H`), so `Utils::HmacValidator.validate` returns `true` [5](#0-4) .
5. `Registry.process` proceeds and calls the app's handler with `shop: request.shop == "victim.myshopify.com"` [6](#0-5) , causing the host application to attribute attacker-controlled event data to the victim tenant.
