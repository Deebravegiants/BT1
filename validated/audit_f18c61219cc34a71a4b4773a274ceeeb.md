### Title
Session hijacking via predictable, unsigned offline session cookie value - (File: lib/shopify_api/auth/oauth/session_cookie.rb)

### Summary
For non-embedded apps, the gem issues a session cookie whose entire value is the internal `Session#id`. For offline (store-level) sessions this ID is deterministically derived as `"offline_#{shop}"` where `shop` is public information. The `SessionCookie` struct carries no signature or MAC binding the value to the browser/user it was issued to, and `SessionUtils.cookie_session_id` trusts whatever value is present in the cookie as the session lookup key. An attacker who knows (or guesses) a target shop's domain can forge this cookie value client-side and cause the host application to resolve and use that shop's stored offline session (including its access token), without ever completing OAuth.

### Finding Description
`Auth::Oauth.validate_auth_callback` builds the browser cookie directly from `session.id` for non-embedded apps: [1](#0-0) 

`Auth::Session.from` computes the offline session ID purely from the `shop` argument, with no secret or randomness involved: [2](#0-1) [3](#0-2) 

`SessionCookie` itself is a plain, unsigned struct — `name`, `value`, `expires` — with no HMAC or integrity field: [4](#0-3) 

`SessionUtils.current_session_id` (and `cookie_session_id`) then trust the raw cookie value as the session identifier used by the host app to look up the corresponding stored `Session` (containing the access token): [5](#0-4) [6](#0-5) 

The binding that should hold is: `cookie_value == session_id issued by this gem to this specific browser for this specific OAuth completion`. Instead, the actual equality enforced by the code is only: `cookie_value == whatever bytes are currently present in the `shopify_app_session` cookie`, with no cryptographic proof that those bytes originated from a legitimate OAuth flow for that browser. Because the offline session ID is `"offline_#{shop}"` — a pure function of public data — any unprivileged internet user can compute the exact session ID for any shop that installed the app and set it as their own `shopify_app_session` cookie value.

### Impact Explanation
This breaks the tenant boundary between shops using the same app: an attacker sets `shopify_app_session=offline_target-shop.myshopify.com` in their own browser, calls into any endpoint that uses `SessionUtils.current_session_id`/`cookie_session_id`, and the host application will resolve and act using the target shop's stored offline session — including making authenticated Admin API calls with that shop's access token. This is a cross-tenant session hijack that yields de facto theft/use of another merchant's access token, matching the Critical impact category (cross-tenant access, theft of a merchant access token) without requiring the app's `client_secret`, TLS interception, or any privileged access — only knowledge of the target's `myshopify.com` domain, which is not secret.

### Likelihood Explanation
High for any app built with the documented non-embedded, cookie-based session flow (`docs/getting_started.md`'s "Cookie" section explicitly instructs passing raw cookies into `SessionUtils.current_session_id`). The attack requires no secrets — only the victim shop's domain — and the vulnerable code path (`cookie_session_id`) performs no validation whatsoever on the retrieved value before it is treated as an authoritative session key.

### Recommendation
Never let an externally-suppliable cookie value double as the trusted session-lookup key without cryptographic binding. Sign the cookie value (e.g., HMAC it with `Context.api_secret_key`, verified in `cookie_session_id`) or use a random, unguessable session identifier that is unrelated to the deterministic `offline_#{shop}` scheme, and reject cookie values that fail verification.

### Proof of Concept
1. App developer builds a non-embedded Shopify app using this gem's documented cookie-based session helper (`docs/getting_started.md`).
2. Shop `victim-shop.myshopify.com` installs the app and completes OAuth; the gem creates an offline session with `id = "offline_victim-shop.myshopify.com"` per `Session.from` (`lib/shopify_api/auth/session.rb:116`), and this ID becomes the raw, unsigned `shopify_app_session` cookie value (`lib/shopify_api/auth/oauth.rb:106-109`).
3. Attacker, in their own browser, sets `shopify_app_session=offline_victim-shop.myshopify.com` (no login/session with the app required).
4. Attacker hits any app route that calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` — the gem returns `"offline_victim-shop.myshopify.com"` verbatim (`lib/shopify_api/utils/session_utils.rb:19-37`) with no verification.
5. The host app looks up its session store with that ID (per the gem's documented integration pattern) and retrieves `victim-shop`'s stored `Session`, including its Admin API `access_token`, letting the attacker act as `victim-shop`.
