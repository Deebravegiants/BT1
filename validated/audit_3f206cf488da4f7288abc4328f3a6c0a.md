### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated headers while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string from the raw HTTP body only, but the `shop`, `topic`, `webhook_id`, and `api_version` values are read from HTTP headers that are never included in that signature. `Registry.process` accepts any request whose body/HMAC pair is valid and then hands the caller-supplied `shop` header straight to the app's webhook handler as if it were an authenticated tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` verifies integrity by recomputing `HMAC(secret, to_signable_string)` and comparing it to the `hmac` field [1](#0-0) . For webhook requests, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic binding to the HMAC at all [3](#0-2) .

`Registry.process` validates only the HMAC of the body and then trusts `request.shop`/`request.topic`/`request.webhook_id` unconditionally when building the `WebhookMetadata` passed to the app-registered handler: [4](#0-3) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` should imply `shop == the shop that produced (body, hmac)`, but the gem never establishes that equality — it only proves `hmac == HMAC(secret, body)`, and `shop` is an independent, attacker-controllable header.

An unprivileged internet user who legitimately owns any Shopify store using the same app (or who otherwise obtains one genuine `(raw_body, hmac)` pair signed by the app's real secret — a normal occurrence since webhooks are delivered to a shared HTTP endpoint) can:
1. Capture a real webhook delivery for their own shop (body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, valid `hmac = HMAC(secret, B)`).
2. Replay the same `(B, hmac)` to the app's public webhook endpoint, but with the `shopify-shop-domain` header rewritten to a victim shop domain (and/or a different `shopify-webhook-id`/`shopify-topic` if the body happens to be topic-agnostic, e.g. certain generic payloads).
3. `HmacValidator.validate` still passes (it only checks the body), and the handler is invoked believing the event originated from the victim shop.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select which merchant's data/session to act on (a documented, expected usage pattern for this gem) can be tricked into applying a legitimately-signed payload to the wrong tenant — a cross-tenant data confusion/write. This satisfies the "cross-tenant access" criterion for Critical severity, since the boundary broken is exactly a tenant (shop) identity check that the gem is responsible for establishing before invoking the handler.

### Likelihood Explanation
Likelihood is High/practical for any unprivileged user who is themselves a legitimate merchant on the target app (a normal, unprivileged relationship — no leaked secret, no TLS interception, no social engineering needed): they can generate genuine `(body, hmac)` pairs for their own shop at will by triggering an event, then freely manipulate the shop header on replay since it's outside the signed scope.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically/independently verify that the `shop` header matches the shop the webhook subscription was registered for) before invoking the handler in `Registry.process`. At minimum, cross-check the `shop` header against a known/registered shop for the given `topic`/`webhook_id` rather than passing it through unauthenticated.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and receives a real webhook:
raw_body = '{"id":123,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body) # computed by Shopify

# Attacker replays it to the same endpoint, forging the shop header:
headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (body/hmac match),
# handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)) is invoked
# even though victim-shop never sent this webhook.
``` [4](#0-3) [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
