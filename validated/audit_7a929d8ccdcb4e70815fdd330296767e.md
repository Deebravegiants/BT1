Confirmed: the fee-on-transfer/actual-received-amount protection exists only in `evm/src/apps/IntentGatewayV2.sol` (mainline EVM) but is absent from the Tron port at `evm/tron/contracts/apps/IntentGatewayV2.sol`, and there are no fee-on-transfer tests for the Tron contract. This is a real, reachable analog to the "wrong return value used" bug class: escrow accounting trusts a nominal/requested amount instead of the actually-received token balance.

### Title
`placeOrder` escrows the requested amount instead of the tokens actually received, allowing fee-on-transfer/deflationary TRC20 tokens to under-collateralize escrow - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In `IntentGatewayV2.placeOrder` on the Tron port, when a user supplies inputs without a predispatch call, the contract pulls tokens with `safeTransferFrom` but records the escrow credit using the pre-transfer, user-declared `order.inputs[i].amount` (via `reducedInputs[i].amount`, itself derived from `originalAmount = order.inputs[i].amount`) rather than the amount the gateway actually received. [1](#0-0)  For any token that delivers less than the requested amount on transfer (fee-on-transfer, deflationary, or rebasing tokens), the gateway will credit `_orders[commitment][token]` with more than it actually holds.

### Finding Description
The mainline EVM contract fixes exactly this issue by snapshotting the gateway's balance before and after `safeTransferFrom` and overwriting `order.inputs[i].amount` with the real delta before computing fees/commitment: [2](#0-1)  This logic (and the analogous predispatch-sweep path that also measures actual balance deltas) is the intended, audited defense, as confirmed by dedicated fee-on-transfer regression tests [3](#0-2) .

The Tron contract's non-predispatch branch never re-measures the balance; it computes `reducedInputs` purely from the caller-supplied `order.inputs[i].amount` before any transfer happens [4](#0-3) , then transfers with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and immediately escrows `reducedInputs[i].amount` without verifying receipt [1](#0-0) . This is the same root-cause class as the referenced report: the code trusts a nominal/expected value rather than the value actually confirmed by the token/protocol interaction (there, `depositAndFix`'s wrong return value; here, the un-verified `safeTransferFrom` amount).

TRC20/BEP20-style tokens on Tron/BSC ecosystems commonly implement optional fee-on-transfer mechanisms (e.g., historical USDT fee-switch precedent), and any ERC20-compatible deflationary or rebasing token used as an order input would trigger this gap. No test in the Tron contract's test suite exercises fee-on-transfer tokens, unlike the mainline EVM suite which explicitly does [5](#0-4) .

### Impact Explanation
When escrow accounting is inflated beyond the gateway's real token balance, later `RedeemEscrow`/withdrawal flows that pay out based on `_orders[commitment][token]` can attempt to pay more than the contract holds for that token, either reverting (freezing legitimate withdrawals/griefing the whole order) or, if the gateway holds a surplus balance from other orders in the same token, draining funds that belong to other users' escrows to cover the shortfall. This is a concrete fund-safety issue: token/intent bridgers using any imperfect-transfer TRC20 token can create escrow entries that are not fully backed by real collateral, an unbacked-liability condition analogous to unbacked minting.

### Likelihood Explanation
Reachable directly and permissionlessly by any user calling `placeOrder` with a non-predispatch order using a fee-on-transfer/deflationary token as input — no privileged role, governance, or special conditions required, only the choice of ERC20/TRC20 token used as collateral for an intent.

### Recommendation
Mirror the mainline EVM fix in the Tron contract's `placeOrder`: for each non-native input in the no-predispatch branch, snapshot `IERC20(token).balanceOf(address(this))` before `safeTransferFrom`, and set `order.inputs[i].amount` to the post-transfer balance delta before computing `protocolFee`/`reducedInputs` and before writing to `_orders[commitment][token]`, consistent with the pattern already applied in `evm/src/apps/IntentGatewayV2.sol` [2](#0-1) .

### Proof of Concept
1. Deploy a fee-on-transfer TRC20 token (e.g. 1% fee on transfer) and use it as `order.inputs[0].token` with `amount = 1000e18`, no `predispatch`.
2. User calls `placeOrder`; `reducedInputs[0].amount` is computed from the full `1000e18` (minus protocol fee if any) at [4](#0-3) .
3. `safeTransferFrom` at [6](#0-5)  only delivers `990e18` to the gateway due to the token's transfer fee.
4. `_orders[commitment][token] += reducedInputs[0].amount` at line 463 still credits based on the undiscounted `~1000e18` figure, exceeding the `990e18` actually held — creating an escrow entry not fully backed by the gateway's real balance of that token.

    function testPlaceOrder_FeeOnTransferToken_WithProtocolFee() public {
        IntentGatewayV2 gatewayWithFees = _deployGatewayProxy();
        Params memory intentParams = Params({
            host: address(host),
            dispatcher: address(dispatcher),
            solverSelection: false,
            surplusShareBps: SURPLUS_SHARE_BPS,
            protocolFeeBps: PROTOCOL_FEE_BPS, // 30 bps
            priceOracle: address(0)
        });
        gatewayWithFees.initialize(intentParams, new bytes[](0), address(0));

        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 receivedAfterTransferFee = inputAmount - (inputAmount * 100) / 10000; // 990
        uint256 protocolFee = (receivedAfterTransferFee * PROTOCOL_FEE_BPS) / 10000;
        uint256 expectedEscrow = receivedAfterTransferFee - protocolFee;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(gatewayWithFees), inputAmount);
        gatewayWithFees.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Reconstruct commitment: inputs mutated to received, then reduced by protocol fee
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedEscrow; // commitment is hashed with reduced amount
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            gatewayWithFees._orders(commitment, address(fot)),
            expectedEscrow,
            "Escrow should equal received minus protocol fee"
        );
    }
