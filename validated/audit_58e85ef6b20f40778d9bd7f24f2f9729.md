### Title
Stale `TombStone.original_owner` lets a former owner reclaim an object after later, unrelated owners send it to `BURN_ADDRESS` - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
The reported bug reduces to one custody invariant: any privileged action gated on "the owner" must be evaluated against the *current* owner, not an identity captured before the object was transferred. In `aptos_framework::object`, the soft-burn/`TombStone` mechanism records `original_owner` at the time `burn()` is called, but ordinary ungated transfers never update or clear this record. If the object later ends up back at `BURN_ADDRESS` through any subsequent, unrelated transfer, `unburn()` will hand the object back to the stale, long-departed `original_owner` instead of whoever most recently sent it to the burn address.

### Finding Description
`burn()` marks an object as (soft) burnt without moving it to `BURN_ADDRESS`; it just records the caller as `original_owner` in a `TombStone` resource: [1](#0-0) 

That `TombStone` is only cleared in two places: (1) inside `unburn()` when the "new owner" branch matches, and (2) inside the privileged `transfer_with_ref()` path used by `TransferRef`/`LinearTransferRef` holders: [2](#0-1) 

Ordinary, unprivileged transfers (`transfer`, `transfer_call`, `transfer_raw`, `transfer_to_object`, all routed through `transfer_raw_inner`) do **not** touch `TombStone` at all: [3](#0-2) 

`unburn()`'s authorization logic branches purely on the *current* `object_core.owner` field, and specifically re-enables the very old `original_owner` whenever the object's current owner happens to equal `BURN_ADDRESS`: [4](#0-3) 

Exploit sequence:
1. Owner `A` calls `object::burn(A, obj)`. This creates `TombStone{ original_owner: A }`; `obj`'s `ObjectCore.owner` is still `A` (new-style soft burn does not move ownership).
2. `A` sells/transfers `obj` normally to `B` via `object::transfer` (or several hops, `B -> C -> ...`). None of these calls touch `TombStone`, so it still says `original_owner: A`.
3. At some later point, whoever is the *current* legitimate owner (say `C`) performs an ordinary `object::transfer(C, obj, BURN_ADDRESS)` — for any reason of their own (e.g., using the well-known convention of "send to `0xfff...fff` to destroy"), which is a fully permitted, ungated transfer since `BURN_ADDRESS` is just an address and `allow_ungated_transfer` is unaffected by the earlier soft-burn.
4. `object_core.owner` is now `BURN_ADDRESS`. The stale `TombStone.original_owner` is still `A`, an address that has had no relation to the object since step 2.
5. `A` calls `object::unburn(A, obj)`. Since `object_core.owner == BURN_ADDRESS` and `original_owner_addr == signer::address_of(A)`, the second branch fires and `transfer_raw_inner(object_addr, A)` executes, handing full ownership of the object back to `A` — a party with zero legitimate claim at the time `C` actually sent it to the burn address.

This is the exact custody analog of the reported bug: an authorization decision (`unburn`) is keyed off an identity (`original_owner`) captured at an earlier point in the object's ownership history, and that identity is never invalidated by intervening, unprivileged ownership transfers.

### Impact Explanation
This breaks the object-ownership custody invariant: whoever legitimately controls an object right before it is sent to the canonical "burn"/destroy address should be the only party who can ever recover it (or it should be permanently irrecoverable, per the module's own "burn" semantics). Instead, any address that ever called `burn()` on the object earlier in its history retains a standing, unprivileged reclaim right that resurfaces whenever a later, unrelated owner moves the object to `BURN_ADDRESS`. For token objects, fungible-asset-holding objects, or other object-held value, this allows an unauthorized former holder to seize the object/asset away from its current or intended-to-be-destroyed state, which is a direct theft / owner-reassignment vector on mainnet-relevant custody flows. Severity is high because it applies to any object type using the framework's own soft-burn feature and requires no special privileges beyond having burned the object at some point in its past.

### Likelihood Explanation
Likelihood is moderate to high in practice: `burn()`/`unburn()` and transfers to `BURN_ADDRESS` are both public, permissionless, ordinary entry functions available on every object; no special capability is required to trigger the flow, and the "send to `0xfff...` to destroy" pattern is a widely used convention independent of this specific `TombStone` feature. The attacker only needs to have been a past owner who called `burn()`, then sold/transferred the object onward — a natural marketplace flow (list "burnt/hidden" collectible, sell it, buyer later disposes of it by sending to the burn address).

### Recommendation
Clear (or otherwise invalidate) any existing `TombStone` on an object whenever `transfer_raw_inner` changes its owner via an unprivileged/ungated transfer, exactly as `transfer_with_ref` already does for the privileged path. Alternatively, `unburn()`'s `BURN_ADDRESS` branch should additionally verify that the address that most recently transferred the object to `BURN_ADDRESS` is the same as `TombStone.original_owner`, or simply disallow re-arming reclaim rights once the object has changed hands since the `TombStone` was recorded (e.g., store the owner-at-time-of-send-to-burn instead of relying on a value that can be stale across arbitrary numbers of intervening transfers).

### Proof of Concept
```
// A owns object O
object::burn(&A, O);                       // TombStone{original_owner: A} created, O still owned by A

// normal marketplace transfer(s), TombStone untouched
object::transfer(&A, O, B_addr);           // owner(O) = B
object::transfer(&B, O, C_addr);           // owner(O) = C

// C, unaware of any special semantics, "destroys" O the conventional way
object::transfer(&C, O, BURN_ADDRESS);     // owner(O) = BURN_ADDRESS

// A reclaims an object it has had no relation to for two transfers
object::unburn<T>(&A, O);
// -> object_core.owner == BURN_ADDRESS branch fires,
//    original_owner_addr (A) == signer::address_of(A) passes,
//    transfer_raw_inner(O, A) executes: owner(O) becomes A again.
```
This directly parallels the referenced report's root cause: an authorization decision tied to a stored (stale) address rather than the object's live, current owner.

    inline fun transfer_raw_inner(object: address, to: address) {
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
