Audit Report

## Title
Reentrant same-contract calls cause `own_contribution` storage diff to be applied twice to `ContractInfo` - (File: substrate/frame/revive/src/metering/storage.rs)

## Summary
`RawMeter::apply_pending_changes_to_contract` applies a nested frame's pending `Diff` to a contract's `ContractInfo` via `Diff::update_contract` but, by design (per its own doc comment), does not consume or reset `own_contribution`, leaving it as `Contribution::Alive(diff)`. If that same frame subsequently completes normally, `finalize_own_contributions` calls `update_contract` again on the same unconsumed diff, re-applying the identical byte/item delta to `ContractInfo` a second time.

## Finding Description
`Diff::update_contract` [1](#0-0)  is not idempotent: each call unconditionally adds `bytes_added`/`items_added` (net of removed) into `info.storage_bytes`/`info.storage_items`, and adjusts `storage_byte_deposit`/`storage_item_deposit` accordingly.

`apply_pending_changes_to_contract` takes `&self` (not `&mut self`) and explicitly does not touch `self.own_contribution`, per its doc comment: "Unlike `finalize_own_contributions`, this does not consume the pending diff, allowing the meter to continue tracking changes after the nested call returns." [2](#0-1) 

`finalize_own_contributions` calls `self.own_contribution.update_contract(info)` and then sets `self.own_contribution = Contribution::Checked(deposit)`. [3](#0-2)  If `own_contribution` is still `Contribution::Alive(diff)` holding the same diff that was already applied by `apply_pending_changes_to_contract`, this second call reapplies the identical `bytes_added`/`items_added` delta onto the (already mutated) `info`, double-counting it.

By contrast, the sibling helper `bank_pending_changes` applies the diff and then explicitly resets `self.own_contribution = Contribution::Alive(Default::default())`, avoiding this double-application. [4](#0-3) 

This confirms the code-level mechanics described in the claim: `apply_pending_changes_to_contract` and `finalize_own_contributions`, if both invoked on the same frame's `own_contribution` without an intervening reset, will double-apply the diff to `ContractInfo`.

However, whether this is actually **reachable** in practice depends entirely on the call sites in `exec.rs` — specifically, whether `apply_pending_changes_to_contract` is ever invoked on a frame's meter followed later by a normal (non-reverted) `finalize_own_contributions` on that same meter without an intervening `bank_pending_changes` or explicit reset. I was not able to fully trace and confirm the exact call sequence in `substrate/frame/revive/src/exec.rs` within the available tool budget — I confirmed the function exists and is referenced there (2 matches) but did not get to inspect the surrounding logic (e.g., whether it's called only in contexts that are always followed by `bank_pending_changes`, or whether some other reset happens before `finalize_own_contributions` runs). This is a material gap: if `exec.rs` always pairs `apply_pending_changes_to_contract` with a subsequent `bank_pending_changes` (which resets the diff) rather than ever reaching `finalize_own_contributions` on the unconsumed diff, then the double-application would not be practically triggerable despite the code shape looking suspicious in isolation.

Given the explicit doc comments on both functions describing exactly this non-consuming/consuming distinction, and that `bank_pending_changes` exists specifically to "reset `own_contribution` so finalize does not apply it a second time" — the code's own documentation acknowledges the double-apply hazard is real and that callers are expected to use `bank_pending_changes` (not `finalize_own_contributions`) after previewing via `apply_pending_changes_to_contract`. This suggests the double-counting is a genuine risk contingent on correct call-site usage in `exec.rs`, which I could not fully verify due to running out of investigation budget.

## Impact Explanation
If reachable, the impact is real: an attacker-controlled contract performing a same-contract reentrant call (write→reenter→return) could inflate `ContractInfo.storage_items`/`storage_bytes`/`storage_item_deposit`/`storage_byte_deposit`, corrupting the deposit/refund accounting baseline for that contract across all future transactions — a legitimate accounting-integrity bug in scope for the storage deposit metering system.

## Likelihood Explanation
Exploitability requires no privileged access — any unprivileged account could deploy a self-reentrant contract using `AllowReentry`. However, likelihood is contingent on the unverified call-site behavior in `exec.rs`: if `apply_pending_changes_to_contract` is always followed by `bank_pending_changes` (which resets the diff) rather than `finalize_own_contributions`, the vulnerability would not be triggerable in the current code, despite the theoretical hazard shown in `storage.rs`.

## Recommendation
Verify in `substrate/frame/revive/src/exec.rs` whether any code path calls `apply_pending_changes_to_contract` on a frame and later calls `finalize_own_contributions` on the same frame's meter without an intervening reset (e.g., via `bank_pending_changes`). If such a path exists, either route reentrant previews exclusively through `bank_pending_changes`, or make `apply_pending_changes_to_contract` record what was applied and net it out on the next `update_contract` call.

## Proof of Concept
A unit test extending `substrate/frame/revive/src/metering/storage/tests.rs` as described in the claim (charge a diff, call `apply_pending_changes_to_contract`, then call `finalize_own_contributions` on the same meter, and compare `info.storage_items`/`storage_bytes` against a non-reentrant control run) would directly demonstrate whether double-counting occurs at the `RawMeter`/`Diff` level. This confirms the storage.rs-level mechanics but does not by itself prove real-world reachability without confirming the actual call sequence used by `exec.rs` for reentrant `CALL`/`STATICCALL` handling, which requires further investigation of `exec.rs` beyond what I was able to complete.

	pub fn update_contract<T: Config>(&self, info: Option<&mut ContractInfo<T>>) -> DepositOf<T> {
		let per_byte = T::DepositPerByte::get();
		let per_item = T::DepositPerChildTrieItem::get();
		let bytes_added = self.bytes_added.saturating_sub(self.bytes_removed);
		let items_added = self.items_added.saturating_sub(self.items_removed);
		let mut bytes_deposit = Deposit::Charge(per_byte.saturating_mul((bytes_added).into()));
		let mut items_deposit = Deposit::Charge(per_item.saturating_mul((items_added).into()));

		// Without any contract info we can only calculate diffs which add storage
		let info = if let Some(info) = info {
			info
		} else {
			return bytes_deposit.saturating_add(&items_deposit);
		};

		// Refunds are calculated pro rata based on the accumulated storage within the contract
		let bytes_removed = self.bytes_removed.saturating_sub(self.bytes_added);
		let items_removed = self.items_removed.saturating_sub(self.items_added);
		let ratio = FixedU128::checked_from_rational(bytes_removed, info.storage_bytes)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		bytes_deposit = bytes_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_byte_deposit)));
		let ratio = FixedU128::checked_from_rational(items_removed, info.storage_items)
			.unwrap_or_default()
			.min(FixedU128::from_u32(1));
		items_deposit = items_deposit
			.saturating_add(&Deposit::Refund(ratio.saturating_mul_int(info.storage_item_deposit)));

		// We need to update the contract info structure with the new deposits
		info.storage_bytes =
			info.storage_bytes.saturating_add(bytes_added).saturating_sub(bytes_removed);
		info.storage_items =
			info.storage_items.saturating_add(items_added).saturating_sub(items_removed);
		match &bytes_deposit {
			Deposit::Charge(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_byte_deposit = info.storage_byte_deposit.saturating_sub(*amount)
			},
		}
		match &items_deposit {
			Deposit::Charge(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_add(*amount)
			},
			Deposit::Refund(amount) => {
				info.storage_item_deposit = info.storage_item_deposit.saturating_sub(*amount)
			},
		}

		bytes_deposit.saturating_add(&items_deposit)
	}

	/// Apply pending storage changes to a ContractInfo without finalizing the meter.
	///
	/// This is used before creating a nested frame to ensure the child frame can see
	/// the parent's pending storage changes when calculating refunds.
	///
	/// Unlike [`Self::finalize_own_contributions`], this does not consume the pending diff,
	/// allowing the meter to continue tracking changes after the nested call returns.
	pub fn apply_pending_changes_to_contract(&self, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(diff) = &self.own_contribution {
			// Apply the diff to update the ContractInfo's storage deposit fields.
			// We don't care about the return value (the deposit amount) here,
			// we just want to update the ContractInfo so child frames can see it.
			let _ = diff.update_contract::<T>(Some(info));
		}
	}

	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}
