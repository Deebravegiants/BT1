### Title
Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identifier passed to the handler, even though `shop` is not part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`hmac` is derived from the `hmac-sha256`/`x-shopify-hmac-sha256` header, and `to_signable_string` returns `@raw_body` only — it does **not** incorporate `shop`, `topic`, or `webhook_id`, all of which come straight from attacker-controllable HTTP headers via `shopify_header`: [2](#0-1) 

`Utils::HmacValidator.validate` only checks that the HMAC over `to_signable_string` (the body) matches: [3](#0-2) 

`Registry.process` gates on this validation and then forwards `request.shop` — sourced from the unsigned header — as the tenant identity to the app's handler: [4](#0-3) 

The equality that should hold is: *the shop the HMAC authenticates == the shop the handler acts on*. Because `shop` is excluded from `to_signable_string`, this equality is broken: the HMAC only authenticates "this body came from someone who knows the api_secret_key," not "this body is for shop X." An unprivileged actor who legitimately receives one authentic `(raw_body, hmac)` pair — for example, from their own store's webhook deliveries, which they are entitled to receive as an app installer — can replay that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value naming a different (victim) shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the spoofed shop.

### Impact Explanation
This breaks the tenant/identity binding between the cryptographically-verified sender and the shop the host application acts on behalf of, letting an unprivileged party who controls one legitimate webhook payload attribute/replay that payload under an arbitrary victim shop domain. Depending on how a host app uses `WebhookMetadata#shop` (e.g., to select which merchant record to update, delete, or which session/data store to touch), this enables cross-tenant data confusion or corruption without ever needing the target's or the app's `client_secret`/access token.

### Likelihood Explanation
Medium: the attacker needs at least one authentic `(body, hmac)` pair, which any installed-merchant/unprivileged app user can obtain simply by receiving their own store's webhooks (e.g., an `app/uninstalled` or `orders/create` webhook with attacker-controlled or predictable body content). No secrets, tokens, or privileged access are required to then replay it against the app's public webhook endpoint with a forged shop header.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material used for verification, or otherwise cross-check the header-derived `shop` against an independently trusted source (e.g., verify the shop is one the app has an active session/token for) before acting on `request.shop`. At minimum, document that `HmacValidator.validate(request)` only proves body integrity and that callers must independently authenticate the `shop-domain` header (e.g. against known installed shops) before trusting it for tenant routing.

### Proof of Concept
1. App merchant A (attacker, unprivileged relative to victim shop B) installs the app and captures one legitimate webhook delivery: `raw_body`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker POSTs to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (victim).
3. `ShopifyAPI::Webhooks::Request.new` parses headers normally; `Utils::HmacValidator.validate(request)` recomputes HMAC over `raw_body` only and it matches `H`, so validation succeeds.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, i.e., the host application processes attacker-supplied data as though it originated from shop B, despite no cryptographic binding between the HMAC and the `shop` value.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
