### Title
Cross-chain refund path gated by `whenNotPaused` permanently blocks recovery of burned tokens when timeout coincides with a pause - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and dispatches an ISMP POST request; the only way to recover those tokens if the message never arrives is `onPostRequestTimeout()`, which re-mints the burned amount to the original sender. Both `send()` and `onPostRequestTimeout()` are gated by the `whenNotPaused` modifier [1](#0-0) , [2](#0-1) . If the contract owner pauses the token (for maintenance or in response to a security incident) while a previously-sent message is timing out, the relayer's timeout-refund transaction reverts, and the user's already-burned tokens cannot be recovered until the contract is unpaused — mirroring the reported issue where `lockForAnOrder`'s `whenNotPaused` modifier blocked debt repayment and exposed a user to unavoidable liquidation.

### Finding Description
In `send()`, tokens are unconditionally burned from the caller before the ISMP request is dispatched [3](#0-2) . The compensating action, `onPostRequestTimeout()`, is the sole mechanism that re-mints the burned amount back to the sender once the ISMP host confirms the request has timed out [4](#0-3) . Both functions share the `Pausable` state via the `whenNotPaused` modifier, so pausing the contract disables the recovery path exactly as it disables normal sends. Because the pause is entirely at the discretion of `onlyOwner` [5](#0-4) , any owner-initiated pause (routine maintenance, or reacting to an unrelated incident) that overlaps with the timeout window of an in-flight message leaves the user's already-burned funds unredeemable for the duration of the pause, with no alternate recovery function. The same pattern is repeated in the upgradeable variant `HyperFungibleTokenUpgradeable.onPostRequestTimeout` [6](#0-5)  and in the wrapped variants `WrappedHyperFungibleToken.sol` / `WrappedHyperFungibleTokenUpgradeable.sol`, where the timeout handler additionally unwraps WETH before refunding, and is likewise `whenNotPaused` [7](#0-6) .

### Impact Explanation
The user's tokens are burned at send-time regardless of pause state; the only path back to wholeness after a failed cross-chain delivery is the timeout refund. Coupling that refund to `whenNotPaused` means a legitimate protocol pause — which the user cannot control or predict — can freeze the user's funds for the pause's entire duration, with no fallback mint/refund function available. This is a fund-availability/freezing issue directly analogous to the original medium-severity finding: a critical, user-initiated recovery action is blocked by the same circuit breaker meant to protect against unrelated risks, exposing users to loss of access to funds they are otherwise entitled to.

### Likelihood Explanation
Pausing is a normal operational tool used for maintenance or security incidents and can happen at any time, including while there are outstanding in-flight cross-chain sends whose timeout window elapses during the pause. Any user who calls `send()` is exposed the moment the owner exercises this ordinary admin capability, making the scenario realistic and not reliant on any privileged or malicious actor performing an unusual action — merely on normal pause usage overlapping with normal user activity.

### Recommendation
Remove the `whenNotPaused` modifier from `onPostRequestTimeout()` (and its wrapped/upgradeable counterparts) so that refunds of already-burned/locked tokens remain available regardless of pause state, consistent with the original report's recommendation to exempt debt-repayment/recovery paths from the pause guard. If pausing `onAccept` and `send` is still desired to stop new transfers, ensure the timeout-refund and equivalent recovery functions are excluded from that guard.

### Proof of Concept
1. Alice calls `HyperFungibleToken.send()`, burning `amount` tokens and dispatching a POST request with a `timeout` [8](#0-7) .
2. The destination chain never delivers the message before `timeout` elapses (e.g., relayer inactivity or destination congestion).
3. Before a relayer submits the timeout proof, the token owner calls `pause()` for an unrelated maintenance/security reason [9](#0-8) .
4. The relayer (or anyone) submits the timeout proof through the host, which calls `onPostRequestTimeout()`; the call reverts because the contract is paused [4](#0-3) .
5. Alice's burned tokens remain unrecoverable until the owner unpauses the contract — during which she holds neither the original tokens nor a destination-side balance.

        bytes32 commitment;
        if (msg.value > 0) {
            commitment = IDispatcher(_host).dispatch{value: msg.value}(request);

        }

            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
