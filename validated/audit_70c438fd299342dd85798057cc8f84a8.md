### Title
Cross-tenant webhook confusion via `shop-domain`/`topic` headers not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic based solely on an HMAC computed over the raw request body, then trusts the `shop-domain` and `topic` HTTP headers — which are never included in that HMAC — to decide which tenant ("shop") and which handler logic the payload is attributed to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` and `topic` accessors read straight from unauthenticated headers: [2](#0-1) . `HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) . `Registry.process` performs this single check and then forwards `request.topic` and `request.shop` — unvalidated against the signed content — directly to the app's handler as trusted tenant/topic identity: [4](#0-3) .

The binding the gem is supposed to enforce is: `shop header == shop that produced this exact (body, hmac) pair`. Because `shop` (and `topic`) are outside the signed bytes, that equality does not hold — any `(body, hmac)` pair valid for *some* shop is also "valid" for *any* `shop-domain` header value, since the signature only proves the body wasn't tampered with, not who it's from or for whom it's intended. This is the direct analog of the audit finding: the report's bug is that a signature validated for one context (`prepareForMigration`) can be replayed into a different context (`addPeerByPeer`/`removePeerByPeer`) because the signed payload doesn't include enough distinguishing/contextual data. Here, similarly, the signed bytes (raw body) don't bind the `shop` or `topic` that the code acts on, enabling context/tenant confusion via replay.

### Impact Explanation
An attacker who can obtain any one legitimate `(raw_body, hmac)` pair — for example by installing the target app on their own development store and receiving a genuine webhook, since the app's `client_secret`/`api_secret_key` is shared across all shops using the app — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic` header) with a victim shop's domain or a different topic. `HmacValidator.validate` still passes because it only checks the body bytes, and `Registry.process` will dispatch the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain. Any host application that trusts `data.shop` to select/act upon per-tenant records (e.g., app/uninstalled cleanup, order/customer updates, GDPR data requests) can be made to act on behalf of the wrong tenant, i.e., cross-tenant access/confusion.

### Likelihood Explanation
Requires the attacker to have legitimate access to at least one valid (body, hmac) pair from the shared app secret (e.g., by installing the app on their own store) — this does not require possession of `api_secret_key` itself, only reuse of a signature it produced. The webhook receiving endpoint is a public HTTP endpoint by design (Shopify posts to it over the internet), so no network position or credential theft is needed beyond that. Likelihood is moderate: it depends entirely on how the host application uses `data.shop`/`data.topic`, which is outside this gem, but the gem provides no mechanism (e.g., signing shop/topic, or requiring correlation against a known installed shop) to prevent it.

### Recommendation
Include the `shop-domain` and `topic` header values as part of the HMAC-verified content (or independently verify that `request.shop` corresponds to a shop the app has an active session/webhook registration for) before dispatching to handlers. At minimum, document prominently that `data.shop`/`data.topic` are not covered by the HMAC and must be cross-checked by the host app against known installed shops before being used for any authorization or data-selection decision.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and triggers a webhook (e.g. `orders/create`), capturing the exact `raw_body` and the `shopify-hmac-sha256` header Shopify sent.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and same `hmac` header, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only presence of shopify-topic/hmac/shop-domain headers is checked): [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `raw_body` — the modified `shop-domain` header is never part of the signed content: [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, even though the payload actually originated for `attacker.myshopify.com`, resulting in cross-tenant data confusion in the host application's handler logic.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```
