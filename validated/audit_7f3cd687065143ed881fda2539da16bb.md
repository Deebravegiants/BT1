### Title
Same-chain fill indexes `order.inputs[i]` by the output-array loop counter with no length equivalence check, permanently freezing escrow when inputs and outputs differ in length - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`_fillSameChain` iterates `for (uint256 i; i < outputsLen; i++)` where `outputsLen = order.output.assets.length`, but inside that loop it repeatedly indexes the unrelated `order.inputs[i]` array (lines 113, 115, 117) to look up escrow amounts and build the `escrowedInputs` release array. Nothing in `placeOrder` or anywhere else in the intent-gateway code enforces `order.inputs.length == order.output.assets.length`, so the two arrays are only "index-aligned" by convention, matching the report's bug class of inconsistent parallel-array lengths used for index-based access.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` only requires `order.inputs.length != 0` and rejects duplicate output tokens; it never checks that `order.inputs.length == order.output.assets.length`. [1](#0-0) 

`_fillSameChain` then assumes a 1:1 index correspondence between the escrowed `order.inputs` array and the `order.output.assets` array it is filling: [2](#0-1) [3](#0-2) 

Two failure modes follow directly from the length mismatch:

1. `order.inputs.length < order.output.assets.length`: once `i` reaches `order.inputs.length`, `order.inputs[i]` is an out-of-bounds access on a `calldata` array, causing the entire fill transaction (and any legitimate fill of that order) to revert unconditionally — a permanent denial of service on the order, since the user's escrowed tokens can never be released to a filler and the order can only be cancelled by its own creator via `_cancelSameChain`.
2. `order.inputs.length > order.output.assets.length`: the loop only ever touches `order.inputs[0..outputsLen-1]`. Any escrowed input token at index `>= outputsLen` is never included in `escrowedInputs`, is never passed to `_withdraw`, and its entry in the `_orders[commitment][token]` escrow mapping is never zeroed or released to the solver on a full fill. Those tokens remain permanently locked in the gateway's escrow: `_filled[commitment]` is set and `isFullyFilled` can become true, so the order is considered filled/closed, and `_cancelSameChain` — the only other path that reads `_orders[commitment][token]` — is restricted to `order.user` and requires the order not already be filled elsewhere; even where reachable, it does not fix the design flaw of index-based misalignment for orders with more inputs than outputs.

Since a user fully controls the `Order` struct passed to `placeOrder` (both `inputs` and `output.assets` arrays are of arbitrary attacker-chosen length, memory-typed, no cross-length validation), any user can create an order that is either un-fillable (griefing the solver market / trapping their own escrow, or worse, a filler's expected settlement) or that traps a subset of their own or a counterparty's escrowed funds — this is directly reachable from a single `placeOrder` transaction dispatched by any unprivileged user, matching an intents-escrow bid/fill path explicitly in scope.

### Impact Explanation
- Escrowed input tokens whose index exceeds `outputsLen` are never released and never refunded through the fill path — this is a permanent freezing of user funds (Medium/High per Sherlock's classification of frozen funds).
- Orders with `inputs.length < outputs.length` become permanently unfillable via `_fillSameChain` due to guaranteed out-of-bounds revert, denying legitimate settlement of an otherwise valid order and locking its escrow.
- The root cause is architectural: two independently-sized, user-supplied arrays are coupled by loop index with no consistency check, exactly the failure class described in the referenced report (`poolInfo`/`userInfo` index mismatch in Multipool.sol).

### Likelihood Explanation
High likelihood: any user calling `placeOrder` can construct an `Order` with `inputs.length != output.assets.length` (both are plain memory arrays with no relative-length validation in `placeOrder`), and any solver attempting `_fillSameChain` against such an order deterministically triggers one of the two failure modes described above. No special privileges or off-chain conditions are required — a single crafted transaction suffices.

### Recommendation
Enforce `order.inputs.length == order.output.assets.length` in `placeOrder` (and in the cross-chain equivalent path, if `ExtrinsicIntents` shares the same index-correlation assumption — this could not be fully verified within the available tool budget and should be checked explicitly). Alternatively, redesign `_fillSameChain` to look up each input's escrowed amount by token identity (as `_cancelSameChain` already does via `_orders[commitment][token]`) rather than by reusing the output loop's index `i`, removing the implicit array-length coupling entirely.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs = [TokenA(100), TokenB(50)]` (length 2) and `order.output.assets = [TokenC(10)]` (length 1). This is accepted because `placeOrder` never compares the two lengths.
2. A solver calls `fillOrder`/`_fillSameChain` with `options.outputs = [TokenC(10)]`. The loop runs once (`i = 0`), fully filling the single output and releasing only `order.inputs[0]` (TokenA) to the solver via `escrowedInputs`. `isFullyFilled` becomes true and `_filled[commitment]` is set.
3. `order.inputs[1]` (TokenB, 50 tokens) is never referenced, never included in `escrowedInputs`/`_withdraw`, and its entry remains in `_orders[commitment][TokenB]` with no code path left to release it — the 50 TokenB are permanently stuck in the gateway contract.
4. Conversely, an order with `order.inputs.length = 1` and `order.output.assets.length = 2` causes `order.inputs[1]` to be accessed at `i = 1` in the loop, reverting the entire fill transaction and permanently blocking settlement of that order.
