### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which `Registry.process` treats as the authoritative tenant/topic identity and hands straight to the app's webhook handler — are never included in the signed material, so they are not bound to the signature that is validated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies the HMAC strictly against that signable string (the body) using the app's `api_secret_key`: [2](#0-1) 

`Registry.process` only checks this body HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — none of which were part of the signed content — and forwards them as the tenant identity to the app-provided handler: [3](#0-2) 

The identity binding the report's bug class hints at is broken here as an equality: `shop_verified_by_HMAC == shop_delivered_to_handler` does not hold, because the HMAC only authenticates the body bytes, not the `shop-domain` header that `WebhookMetadata` uses to attribute the event to a tenant.

Because the same `api_secret_key` is shared by the app across every installed shop, an unprivileged attacker who has (or creates) any one legitimate, low-privilege installation of the app can capture a genuine webhook delivery to their own store (a real body + valid HMAC pair, signed with the app's shared secret). They can then replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain (and/or the `topic` header for any registered topic). `HmacValidator.validate` will still succeed, since it never inspects the headers, and `Registry.process` will dispatch to the handler with `WebhookMetadata.shop` set to the victim's domain.

### Impact Explanation
This crosses the tenant boundary the gem is responsible for maintaining when processing multi-tenant webhook traffic: an attacker with only their own legitimate (or trial) shop installation can make the host application believe an arbitrary Shopify event (e.g., `app/uninstalled`, `customers/data_request`, `shop/update`) originated from a different merchant's shop. Depending on how the host app's handler uses `WebhookMetadata#shop` (commonly to look up/act on that shop's stored access token or data), this enables cross-tenant data manipulation or state corruption using the app's own credential material — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability only requires the attacker to control one legitimate app installation (freely obtainable via a Shopify dev/trial store) to capture one valid `(raw_body, hmac)` pair, plus the ability to send an HTTP POST to the app's public webhook endpoint with modified headers — no access to `api_secret_key`, access tokens, or any privileged account is needed. The gem provides no server-side mechanism to bind the headers to the signature, so the weakness is systemic wherever `Registry.process` is used as documented.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind them to the request (e.g., derive shop identity solely from a value included in the signed payload, or require a separate authenticated channel to correlate topic/shop with body). At minimum, document that consuming code must not treat `WebhookMetadata#shop`/`#topic` as authenticated beyond what Shopify's own header contract implies, since this gem does not verify them itself.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify store, a normal unprivileged action.
2. Shopify sends a legitimate webhook to the app for the attacker's own shop: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B` under the shared `api_secret_key`), `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker replays a POST to the same webhook endpoint with body `B` and header `x-shopify-hmac-sha256 = H` unchanged, but sets `x-shopify-shop-domain = victim-shop.myshopify.com` (and/or `x-shopify-topic` to a different registered topic).
4. `Utils::HmacValidator.validate` in `Registry.process` succeeds because it only checks `H` against `B`: [4](#0-3) 
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes it as if it were a genuine event for the victim, despite the HMAC never having authenticated that shop value.
