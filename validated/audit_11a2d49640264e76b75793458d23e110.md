## Title
Meta-transaction (`DelegateAction`/NEP-366-461) signature digest lacks a chain/network domain separator, enabling cross-chain signature replay - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
`DelegateAction` (and `DelegateActionV2`) signatures are computed over a `SignableMessage` that only commits to a small `MessageDiscriminant` (NEP number tag) plus the action's own fields (`sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`). Nothing in the signed payload binds the signature to a specific chain/genesis, mirroring the reported Uniswap/PancakeSwap KEM-hook issue where a swap-authorization digest omitted a domain separator (chain ID, contract identity), permitting cross-chain signature replay.

### Finding Description
`SignableMessage::sign`/`verify` hashes `discriminant || borsh(msg)`: [1](#0-0) 

The discriminant only encodes the NEP number (366 for V1, 611 for V2 gas keys), not a chain identifier: [2](#0-1) 

`DelegateAction::get_nep461_hash` / `VersionedDelegateActionPayload::get_nep461_hash` build the actual signed hash purely from the action struct fields — `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key` — with no `genesis_hash`/`chain_id`/network identifier included: [3](#0-2) [4](#0-3) 

Compare this with ordinary `SignedTransaction`s, which include a `block_hash` tied to a specific chain's recent blocks for replay protection. `DelegateAction` intentionally has no `block_hash` field at all — only `max_block_height` and a per-access-key `nonce`, both of which are meaningful only relative to a particular chain's own block-height counter and access-key nonce state: [5](#0-4) 

When the receiver shard applies the delegate action, verification only checks the borsh-encoded signature, `max_block_height` against the local `apply_state.block_height`, and the account's local access-key nonce — none of which reference chain identity: [6](#0-5) [7](#0-6) 

Because NEAR account IDs, public keys, and access-key nonce sequences can be reproduced identically on any other chain running the same nearcore-based protocol (e.g., a user who registers the same full-access key on the same-named account on two independent networks — mainnet/testnet, or any forked/derived chain), a `SignedDelegateAction` produced with intent for chain A remains fully valid and will be accepted verbatim by chain B, as long as `max_block_height` and the access-key nonce state happen to line up (which an attacking relayer can arrange, since block height and nonce simply need to be "not yet exceeded"). The signature itself carries no chain-specific commitment to reject this.

### Impact Explanation
An attacker who obtains a validly-signed `DelegateAction`/`SignedDelegateAction` intended for one NEAR-protocol chain can relay it as-is to any other chain sharing the same account name/public-key/nonce state (e.g., a user's mainnet and testnet accounts using the same access key, or a chain fork). This causes the relayer's meta-transaction to execute the delegated actions (transfers, function calls, key management, etc.) on a network the signer never authorized, resulting in unauthorized state/balance changes on that chain — the same "signed intent replay across environments" failure mode described in the source report, adapted to NEAR's meta-transaction signing scheme rather than an EVM hook digest.

### Likelihood Explanation
Exploitation requires that the same account id + public key + compatible nonce/height state exist on two chains running the nearcore protocol (a realistic pattern for users who reuse keys across mainnet/testnet or private/forked networks and relayers who process meta-transactions off-chain before submission), and does not require any validator, node compromise, or network-layer manipulation — only a normal user-submitted transaction/relayer on the target chain. This keeps it within the unprivileged, transaction-driven exploitation model.

### Recommendation
Fold a chain-specific domain separator into the `SignableMessage`/`DelegateAction` hash — e.g., include the genesis hash or a `chain_id` field in the discriminant or in the hashed struct — so that a signature produced for one network's `DelegateAction` cannot be verified as valid on any other network.

### Proof of Concept
1. User `alice.near` maintains a full-access key on account `alice.near` on both Network A and Network B (e.g. by registering the same `PublicKey` on both), a scenario `validate_delegate_action_key` does not distinguish since verification is purely local to whichever chain's state trie is queried: [8](#0-7) 
2. Alice signs a `DelegateAction` (nonce N, max_block_height H) via `VersionedSignedDelegateAction::sign` intending it only for Network A: [9](#0-8) 
3. An attacker/relayer submits the identical `SignedDelegateAction` bytes to Network B. Because `signed.verify()` only recomputes `hash(discriminant || borsh(delegate_action))` — with no chain identifier — the signature check passes on Network B as well: [10](#0-9) 
4. If Alice's access-key nonce on Network B has not yet reached N and the local block height on Network B is below H, `apply_delegate_action` executes the delegated actions on Network B exactly as it would on Network A, causing unintended state changes on a network Alice never signed for: [6](#0-5)

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

fn validate_delegate_action_key(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,

                    account_id: sender_id.clone(),
                    public_key: public_key.clone().into(),
                },
            )
            .into());
            return Ok(());
        }
    };
