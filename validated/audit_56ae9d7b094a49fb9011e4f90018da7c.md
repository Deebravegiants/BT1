### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is compared against a signature computed only over `@raw_body` (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the signable string.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, request.to_signable_string)` and compares it to `request.hmac`. For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [2](#0-1) . `request.shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body [1](#0-0) . After HMAC succeeds, `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and forwards it, unmodified, to the app-supplied handler [4](#0-3) . The gem's own documentation instructs integrators to trust `data.shop` as "The shop domain of the webhook" for routing/attribution [5](#0-4) .

Because the app-wide `api_secret_key` is identical across every shop that installs the app, any merchant who is a legitimate installer (an "unprivileged internet user" relative to other tenants) can capture one authentic, validly-HMAC-signed webhook delivered for their own store, then replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` will still pass because it only checks `raw_body` integrity, not header-to-body binding. The equality the gem enforces is `HMAC(secret, raw_body) == received_hmac`; the equality the app actually needs — `shop_header == shop_that_produced(raw_body)` — is never checked anywhere in the gem.

### Impact Explanation
This breaks the tenant identity binding between the webhook payload and the shop it is attributed to, meeting the Critical "cross-tenant access" bar: a host application that persists or acts on webhook data keyed by `data.shop` (exactly as the gem's own documented usage example does) can have attacker-controlled data attributed to, or trigger business logic for, a different merchant's tenant, without needing that merchant's access token or credentials.

### Likelihood Explanation
Likelihood is realistic: any user who can legitimately install the target app on their own development/test store obtains a genuine `raw_body` + HMAC pair for arbitrary topics they can trigger (e.g. `products/update`), and only needs to replay that HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no secrets, tokens, or privileged access required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or independently verify that the `shop-domain` header corresponds to a shop actually registered for that webhook/session before trusting `WebhookMetadata#shop`. At minimum, document prominently that `data.shop` is unauthenticated header data and must be cross-checked by the integrator against known/installed shops before using it as a tenant key.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `products/update`) to capture a real request with headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker.myshopify.com`, and raw body `B`.
2. Replay an HTTP POST to the app's webhook endpoint with the same body `B` and `x-shopify-hmac-sha256: <H>`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only re-derives the HMAC over `B` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the app handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's data>, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host application to attribute attacker-controlled webhook data to the victim tenant.
