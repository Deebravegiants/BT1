### Title
Native ETH forwarded to CallDispatcher during cross-chain calldata execution can become permanently stuck due to missing withdraw/sweep function - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` accepts native ETH via its `receive()` function and only exposes a single external entrypoint, `dispatch(bytes memory encoded)`, which forwards ETH to caller-controlled targets based on a decoded `Call[]` array. There is no owner, no access control, and critically no `withdraw`/`sweep`/`rescue` function anywhere in the contract, unlike other core protocol contracts (`EvmHost`, `IntentGatewayV2`, `IntentsBase`) which all implement dust-collection and sweep mechanisms for stray native/ERC20 balances.

### Finding Description
`WrappedHyperFungibleToken.onAccept` (and the analogous `WrappedHyperFungibleTokenUpgradeable`) unwraps bridged WETH into native ETH and, when the incoming message carries optional calldata, forwards execution to `ICallDispatcher(_dispatcher).dispatch(message.data)` where `message.data` is an ABI-encoded `Call[]` originating from the cross-chain message body set by the original sender on the source chain [4](#0-3) . `CallDispatcher.dispatch` iterates the calls and forwards `call.value` native ETH per call via a low-level `.call` [5](#0-4) . The documentation confirms this exact flow is an intended, supported feature: unwrapped native ETH is held by `CallDispatcher` and forwarded to a router as `Call.value` [6](#0-5) .

Nothing in `CallDispatcher.sol` enforces that the sum of `call.value` across the decoded `Call[]` equals the ETH balance actually delivered to the contract for that dispatch. If the calldata payload (constructed off-chain by an application/user on the source chain) under-specifies `value` fields relative to the amount of ETH unwrapped and sent to the dispatcher — whether from a bug in the calling app's encoding, dust left over from rounding during WETH unwrap, or a malformed/short `Call[]` — the excess native ETH remains in `CallDispatcher`'s balance permanently. Because `receive()` is the only other function besides `dispatch()`, and `dispatch()` has no owner-only rescue path, that ETH can never be retrieved.

### Impact Explanation
This is a shared, protocol-level utility contract referenced by both `HyperFungibleToken`/`WrappedHyperFungibleToken` deployments across chains (it's not app-specific state, but a singleton per chain used by every configured HFT deployment). Stuck ETH here represents a permanent freezing of user funds with no recovery mechanism, meeting the "permanent freezing of funds" bar. Given that dispatch payloads are attacker/user-supplied bytes decoded from cross-chain messages, this is reachable by any unprivileged actor who sends a cross-chain HFT transfer with calldata that doesn't perfectly account for 100% of the forwarded native value.

### Likelihood Explanation
Likelihood is moderate: it requires the calldata `Call[]` to under-allocate value relative to what's unwrapped/forwarded (e.g., partial execution, a call that reverts is caught... actually note `dispatch` reverts entirely `CallFailed` on any failed call, so a full revert would just fail the whole `onAccept`, not leave stuck funds — but a *successful* run where a Call entry's `value` is simply less than the ETH sent to the dispatcher, or leftover dust from WETH withdraw rounding, or a message with `data.length > 0` whose calls only spend part of the forwarded balance) is entirely plausible in real integrations since the correctness of `Call.value` accounting is left entirely to the calling application/user, with no on-chain safety net.

### Recommendation
Add a permissioned (or otherwise safe) rescue/sweep function to `CallDispatcher` allowing any residual ETH (and possibly ERC-20 dust) balance to be recovered — for example, forwarding leftover balance to a specified beneficiary after the `Call[]` executes, or exposing an owner-gated `sweep(address token, address to)` function analogous to the dust-sweeping mechanisms already present in `EvmHost` and `IntentGatewayV2`.

### Proof of Concept
1. A user on chain A calls `WrappedHyperFungibleToken.send()` with `data` encoding a `Call[]` intended to swap the bridged ETH for USDC via a UniswapV2 router, but the encoded `Call.value` for the swap step is set to slightly less than the full bridged `amount` (e.g., off-by-rounding, or the app author simply forgets to account for all of it).
2. On chain B, `onAccept` unwraps the full `message.amount` of WETH to native ETH and sends it to `_dispatcher`, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)` [7](#0-6) .
3. `CallDispatcher.dispatch` executes the single `Call` with `call.value` less than its full ETH balance; the call succeeds, and execution returns normally [5](#0-4) .
4. The leftover ETH difference remains in `CallDispatcher`'s balance. Because the contract exposes no withdraw, sweep, or owner, this ETH is permanently unrecoverable — it accumulates indefinitely across every less-than-perfectly-encoded cross-chain calldata execution routed through this dispatcher.

contract CallDispatcher is ICallDispatcher {
    /**
     * @dev error thrown when the target is not a contract.
     */
    error NotContract(address target);

    /**
     * @dev error thrown when a call fails.
     */
    error CallFailed(address target, bytes result);

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
}
