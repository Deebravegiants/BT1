### Title
POA Bridge Withdrawal Status Misreport for Concurrent Same-Asset Withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal by matching POA bridge API results using only the token's `assetId`, ignoring the withdrawal's index, amount, and destination address. When a caller batches two or more POA-bridge withdrawals of the same asset to different destinations in a single `signAndSendWithdrawalIntent` call, `findMatchingWithdrawal` returns the same (first) matching record for every withdrawal in the batch, causing the SDK to report the same `status`/`txHash` for withdrawals that actually settled independently (or not at all) on-chain.

### Finding Description
`findMatchingWithdrawal` in [1](#0-0)  matches a POA API withdrawal record purely by `` `nep141:${w.data.near_token_id}` === assetId ``. It is invoked from `describeWithdrawal` at [2](#0-1) , where the comment explicitly states: "Response list is unsorted, so we match by assetId instead of index." The docstring on `findMatchingWithdrawal` itself acknowledges: "Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported."

The SDK, however, does support submitting multiple withdrawals of the same asset in one call. `IntentsSDK.signAndSendWithdrawalIntent` accepts `withdrawalParams: WithdrawalParams[]` in batch mode ( [3](#0-2) ), and `createWithdrawalCompletionPromises`/`createWithdrawalIdentifiers` builds a separate `WithdrawalIdentifier` per entry, tracking indexes per bridge route without any assetId-level disambiguation ( [4](#0-3) ). For the PoA route, `createWithdrawalIdentifier` does not encode index into the identifier's matching key, so at polling time (`watchWithdrawal` → `describeWithdrawal`), two independent withdrawals sharing the same `assetId` but different `destinationAddress`/`amount` collapse onto the same `.find()` match, always returning the first record in the (unsorted) API response.

This breaks the intended equality: *the status/txHash reported for withdrawal N should reflect withdrawal N's own on-chain settlement*, not an arbitrary sibling withdrawal of the same token. The exact same weakness is mirrored in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`'s `findMatchingWithdrawal` ( [5](#0-4) ), used by `waitForWithdrawalCompletion` ( [6](#0-5) ), which only disambiguates by `assetId`.

### Impact Explanation
An integrator that batches two POA-bridge withdrawals of the same token (e.g., paying out two different users, or splitting one user's balance to two different destination addresses) will receive identical `{status: "completed", txHash: ...}` results for both withdrawal identifiers once any one of them settles. If the integrator uses this SDK-reported status to release funds, mark invoices paid, or reconcile off-chain balances, it can credit two distinct payees/records against a single actual on-chain transfer — a double-credit condition driven purely by a status/hash misreport rather than an on-chain fact. This matches the "status or hash misreport making an integrator credit or refund twice" impact category (High).

### Likelihood Explanation
This requires the integrator to submit more than one POA-bridge withdrawal of the same `assetId` in a single batched call (or otherwise poll multiple in-flight withdrawals of the same token concurrently) — a use case the SDK explicitly supports via batch `signAndSendWithdrawalIntent`/`createWithdrawalCompletionPromises`, and one the codebase's own comments acknowledge is unhandled. No malicious counterparty action is needed; the ambiguity manifests purely from normal batched usage combined with the POA API returning an unsorted list.

### Recommendation
Disambiguate `findMatchingWithdrawal` beyond `assetId` — e.g., match by `destinationAddress` and `amount` (and `destinationMemo` where applicable) in addition to `near_token_id`, or track per-asset ordering/consumption so each withdrawal identifier consumes a distinct API record instead of always matching the first. Apply the fix consistently in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`.

await sdk.signAndSendWithdrawalIntent({
  withdrawalParams: [
    { assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: "addrA", feeInclusive: false },
    { assetId: "nep141:btc.omft.near", amount: 200000n, destinationAddress: "addrB", feeInclusive: false },
  ],
  feeEstimation: [feeA, feeB],

// Both wids share route = PoaBridge, index 0 and 1, but PoaBridge.describeWithdrawal
// ignores index and matches only by assetId:
//   findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")
// -> always returns withdrawals[0] regardless of which wid (index 0 or 1) is queried.

// Once addrA's transfer completes, BOTH watchWithdrawal(wid0) and watchWithdrawal(wid1)

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

async function findBridgeForWithdrawal(
	bridges: Bridge[],
	params: WithdrawalParams,
): Promise<Bridge | undefined> {
	for (const bridge of bridges) {
		if (await bridge.supports(params)) {
			return bridge;
		}
	}
	return undefined;
}

	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
