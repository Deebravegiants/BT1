### Title
Webhook shop identity (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from an HTTP header that is entirely excluded from the HMAC signature computation, while `ShopifyAPI::Webhooks::Registry.process` trusts that header value as the tenant binding once the HMAC check passes. This breaks the equality `shop authenticated == shop bound by HMAC`, letting an attacker who legitimately receives one signed webhook for their own shop relabel it as belonging to a different shop and have it accepted as valid.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which plays no part in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC over `to_signable_string` only (body bytes), never the headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity that is forwarded to the app's handler, with no further binding check: [4](#0-3) 

`WebhookMetadata#shop` is a plain, unauthenticated `String` field consumed by the handler interface as the tenant key: [5](#0-4) 

This is directly analogous to the `H-03` root cause pattern: a value acted upon by the security-critical path (`shop`, used as the tenant binding, analogous to `debtDiff`/collateral used to mint DUSD) is derived from data that is not covered by the integrity check (`hmac`, analogous to the collateral check that used the wrong CR/price). Concretely:
- Before request: attacker's own shop `evil-shop.myshopify.com` legitimately installs the app and receives a real webhook, with body `B` and a genuine `hmac = HMAC(client_secret, B)` computed by Shopify, plus header `shopify-shop-domain: evil-shop.myshopify.com`.
- Attacker replays the same body `B` (and therefore the same valid `hmac`) to the app's webhook endpoint, but substitutes the header to `shopify-shop-domain: victim-shop.myshopify.com`.
- `HmacValidator.validate` recomputes `HMAC(client_secret, B)` — identical to the original — and returns `true`, because the shop header was never part of the signed content.
- `Registry.process` then calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...))`, presenting attacker-controlled body content as if it originated from `victim-shop.myshopify.com`.

Any host application that follows this gem's documented pattern — trusting `WebhookMetadata#shop` to select which tenant's records to create/update/delete based on the webhook payload — will act on attacker-supplied data under a victim tenant's identity, i.e. cross-tenant data injection/corruption without ever needing the victim's credentials.

### Impact Explanation
Meets the Critical bar: cross-tenant access. The `client_secret`/HMAC never needs to be leaked — only its correctness is required for the body the attacker already legitimately possesses (from their own shop's webhook deliveries). By swapping the identity header, the attacker forges the appearance of a message from another merchant's shop, causing the app to process attacker-chosen payload content under a different tenant's identity. This directly breaks the tenant isolation the HMAC verification is supposed to guarantee.

### Likelihood Explanation
Requires only an unprivileged, ordinary use of the app: install the app on one's own store (or capture any webhook delivery visible to a merchant), then replay it to the public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or elevated access are needed, and the webhook endpoint is by design internet-reachable.

### Recommendation
Include the shop domain (and other identity-bearing headers, e.g. `topic`, `webhook-id`) in the signed content used by `to_signable_string`, or otherwise cryptographically bind the shop domain to the payload (e.g., verify the shop from an authenticated session/store lookup rather than trusting the raw header) before constructing `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated header data and must never be used alone to select tenant scope; cross-check it against Shopify's registered/expected domain for the installation before acting on webhook content.

### Proof of Concept
1. Install the app on `evil-shop.myshopify.com`; capture a legitimate webhook delivery: raw body `B`, header `shopify-hmac-sha256: <base64 HMAC(client_secret, B)>`, header `shopify-shop-domain: evil-shop.myshopify.com`.
2. Build a new HTTP POST to the app's webhook endpoint using the exact same body `B` and same `shopify-hmac-sha256` header, but set `shopify-shop-domain: victim-shop.myshopify.com` (and matching `shopify-topic`/`shopify-webhook-id` if required by the handler routing).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the host app framework and passed to `Registry.process`.
4. `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` == `B` is unchanged, per `lib/shopify_api/webhooks/request.rb#L35-L38` and `lib/shopify_api/utils/hmac_validator.rb#L26-L31`.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb#L198-L199) invokes the app handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body: B`, despite the request never having been signed by Shopify for that shop.
