### Title
`rootHashHinkalIndex` is used for Merkle-root validation but is excluded from `calldataHash`, `signedMessageHash`, and the circuit's public-input vector - (File: `contracts/Hinkal.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
`CircomData.rootHashHinkalIndex` [1](#0-0)  is passed to `rootHashExists(circomData.rootHashHinkal, circomData.rootHashHinkalIndex)` in `Hinkal.transact` [2](#0-1) , but this field is never included in the value hashed into `circomData.calldataHash` (`getHashedCalldata1`/`getHashedCalldata2`) [3](#0-2) , never included in `getSignedMessageHash` [4](#0-3) , and never included in the circuit public-input vector built by `formBasicInput`/`formInputEmporiumMin` [5](#0-4) . Only `rootHashHinkal` (the root value itself) is bound into these equalities — the index that selects *which* historical root slot to check it against is unauthenticated relative to the proof and the prover's/relayer's signed intent.

### Finding Description
`performHinkalChecks` in `HinkalHelper.sol` enforces `CircomDataBuilder.getHashedCalldata(circomData) == circomData.calldataHash` [6](#0-5) , and the circuit's `calldataHash` signal and `signedMessageHash` signal are meant to bind the entirety of the transaction's `CircomData` to both the zk-proof and the relay's/user's EdDSA/EIP712 signature. However, `rootHashHinkalIndex` is absent from every one of these binding mechanisms:
- `getHashedCalldata1`/`getHashedCalldata2` hash `publicSignalCount, relay, emporiumMessage, externalActionData, slippageValues, hookData, encryptedOutputs, onChainEncryptedOutput, feeStructure, onChainCreation, originalSender, extraData` — no `rootHashHinkalIndex`.
- `getSignedMessageHash` hashes `rootHashHinkal` (the root value) plus token/amount/nullifier/commitment/calldataHash data and stealth-address fields — again no `rootHashHinkalIndex`.
- `formBasicInput` places `rootHashHinkal` into the public input array (index used by the verifier) but never places `rootHashHinkalIndex`.

Because `circomData.rootHashHinkalIndex` is a plain calldata field on the public `transact` function, any unprivileged EOA calling `transact` can supply an arbitrary `rootHashHinkalIndex` alongside a `rootHashHinkal`/proof/signature combination that was generated for a *different* index, as long as `rootHashExists(root, index)` in `MerkleBase.sol` accepts that (root, index) pair. I could not fully confirm the internal behavior of `rootHashExists`/`MerkleBase.sol` (history depth, whether index is even used to select a slot or is just informational) since I ran out of tool iterations before reading that file's body — this is the one open verification gap.

### Impact Explanation
If `rootHashExists` treats `rootHashHinkalIndex` as a genuine selector into a bounded history of historical roots (rather than merely re-deriving/ignoring it), an attacker could pair a root value that is valid at one historical index with an index pointing to a stale or different slot, potentially reusing an old root that was already advanced past (i.e., a root whose corresponding nullifiers might already be different), because the index itself carries no cryptographic binding to the proof, the calldata hash, or the signed message. This falls into the class described by the report's rule: "a `CircomData` field acted on but outside `calldataHash`/`signedMessageHash`/the public-input vector." If exploitable, the effect maps to "a (leaf, root) pair the circuit accepts that the tree never produced [at that index]" or stale-root reuse, which can enable double-spend/nullifier-bypass conditions — a Critical-class impact per the rules, but this requires confirming `MerkleBase.sol`'s exact validation logic.

### Likelihood Explanation
Likelihood cannot be confirmed as concretely exploitable without inspecting `contracts/MerkleBase.sol`'s `rootHashExists` implementation, since if that function only checks "does this root value exist among stored historical roots" and uses the index purely as an O(1) lookup hint with a fallback/verification against the stored value (not as an unchecked trust anchor), the missing binding would be harmless. I was unable to complete this verification in the available iterations.

### Recommendation
Include `rootHashHinkalIndex` in `getHashedCalldata1`/`getHashedCalldata2` (or in `getSignedMessageHash`) in `contracts/CircomDataBuilder.sol`, and/or add it to the circuit's public-input vector, so that the index is cryptographically bound to the same proof and signature that bind `rootHashHinkal`. Additionally, verify in `contracts/MerkleBase.sol` that `rootHashExists` cannot be satisfied by an index/root pair that the on-chain Merkle tree never actually produced together.

### Proof of Concept
I could not construct a concrete PoC transaction because I did not have time to read `contracts/MerkleBase.sol`'s `rootHashExists` logic to confirm whether the index is exploitable in isolation (i.e., whether supplying a mismatched but "existing" root/index pair is actually accepted). This is flagged as an open item requiring further investigation of `contracts/MerkleBase.sol` and `contracts/Merkle.sol` before this can be confirmed as a valid, exploitable finding rather than a benign discrepancy.

    function formBasicInput(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData,
        uint256[] memory input,
        uint256 index,
        uint256 emporiumMessage
    ) internal pure returns (uint256[] memory) {
        // 1) First we list public inputs as in the body of the main template (not the one with exact dimensions)
        input[index++] = circomData.stealthAddressStructure.H1x;
        input[index++] = circomData.stealthAddressStructure.H1y;
        input[index++] = circomData.stealthAddressStructure.stealthAddress;
        input[index++] = emporiumMessage; // this is for Emporium message signature verification

        // 2) Then we list the private inputs as in the body of the main template
        input[index++] = circomData.rootHashHinkal;
        input[index++] = getSignedMessageHash(
            chainId,
            verifyingContract,
            circomData,
            emporiumMessage
        );

        for (uint16 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            input[index++] = uint256(
                uint160(circomData.erc20TokenAddresses[i])
            );
        }

        for (uint16 i = 0; i < circomData.amountChanges.length; i++) {
            require(
                circomData.amountChanges[i] < MAX_AMOUNT &&
                    circomData.amountChanges[i] > -1 * MAX_AMOUNT,
                "amount changed is too large"
            );

            input[index++] = circomData.amountChanges[i] >= 0
                ? uint256(circomData.amountChanges[i])
                : CIRCOM_P - uint256(-circomData.amountChanges[i]);
        }

        for (uint16 i = 0; i < circomData.inputNullifiers.length; i++) {
            for (uint16 j = 0; j < circomData.inputNullifiers[i].length; j++) {
                input[index++] = circomData.inputNullifiers[i][j];
            }

        input[index++] = circomData.timeStamp;

        for (uint16 i = 0; i < circomData.outCommitments.length; i++) {

        input[index++] = circomData.calldataHash;
