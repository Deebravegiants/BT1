Audit Report

## Title
Unprivileged `view`-role users can list Bridge and External Initiator secrets (`OutgoingToken`/`AccessKey`) via unauthenticated-role-gated endpoints - (File: core/web/router.go)

## Summary
`GET /v2/bridge_types` and `GET /v2/external_initiators` are registered in `core/web/router.go` with only the generic `paginatedRequest` wrapper and no `auth.RequiresEditRole`/`auth.RequiresAdminRole` gate, while the `POST`/`PATCH`/`DELETE` routes for the same resources are explicitly role-gated. This allows any authenticated user, including the lowest-privilege `view` role, to retrieve `OutgoingToken` and `AccessKey` secrets for all bridges and external initiators.

## Finding Description
The route registrations confirm the asymmetry: `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` and `authv2.GET("/bridge_types", paginatedRequest(bt.Index))` have no role check, whereas `authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))` and the corresponding bridge write routes do. [1](#0-0) 

`RequiresEditRole` explicitly blocks `UserRoleView` and `UserRoleRun` from proceeding, confirming that `view` is meant to be a read-limited role for sensitive write actions, but this check is simply absent on the two Index routes. [2](#0-1) 

`ExternalInitiatorsController.Index` builds `presenters.ExternalInitiatorResource` for every stored initiator and serializes it in the paginated response, and that resource type includes both `AccessKey` and `OutgoingToken` fields populated directly from the DB-stored initiator. [3](#0-2) [4](#0-3) 

Similarly, `BridgeTypesController.Index` builds `presenters.BridgeResource` for every bridge and returns it, and that resource includes `OutgoingToken`. [5](#0-4) [6](#0-5) 

The project's own RBAC regression test table in `core/web/auth/auth_test.go` codifies this behavior: `{"GET", "/v2/external_initiators", true, true, true}` and `{"GET", "/v2/bridge_types", true, true, true}` show `viewOnlyAllowed: true` for these GET routes, in contrast to `false` for the corresponding write routes on the same resources. [7](#0-6) 

## Impact Explanation
`OutgoingToken` and `AccessKey` are credentials used to authenticate outbound calls to external adapters/initiators. A node user provisioned with only the `view` role — a legitimate, documented low-privilege role intended for read-only/monitoring access — can retrieve these secrets via a normal authenticated GET request and use them to impersonate the bridge/external-initiator relationship outside the node, or interact with the external adapter/initiator endpoint directly. This is a concrete secret/credential exfiltration via a role-bypass in the node API, matching the "key/secret exfiltration" and "node API authentication or role bypass" impact categories.

## Likelihood Explanation
Exploitation requires only a standard authenticated `view`-role session/token and a single unauthenticated-role-gated GET request — no additional exploitation steps, no admin/host access, no database access. Any deployment that issues `view`-role API users (a supported, intended feature) is directly exposed, and the existing test `TestExternalInitiatorsController_Index` confirms the response body includes `AccessKey` and `OutgoingToken` for every listed initiator. [8](#0-7) 

## Recommendation
Gate `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` with at least `auth.RequiresEditRole`, matching the write endpoints for the same resources in `core/web/router.go`. Alternatively, strip `OutgoingToken`/`AccessKey` from the `Index`/`Show` presenter output (`presenters.BridgeResource`, `presenters.ExternalInitiatorResource`) so secrets are only exposed at creation time, consistent with how `IncomingToken`/`Secret` are already handled.

## Proof of Concept
1. Create a `view`-role API user: `chainlink admin users create --email=viewer@test.com --role=view`.
2. Authenticate as that user and issue `GET /v2/external_initiators` (or `GET /v2/bridge_types`) with a valid session/token.
3. Observe the JSON response body includes `accessKey` and `outgoingToken` fields for every configured resource, per `presenters.NewExternalInitiatorResource` / `presenters.NewBridgeResource`, even though the same user receives `401 Unauthorized` when attempting `POST`/`PATCH`/`DELETE` on the identical resource via `auth.RequiresEditRole`.
4. This can be verified as a unit test extension of the existing `routesRolesMap` table in `core/web/auth/auth_test.go` by asserting the response body contents (not just status code) for the `view` role on `GET /v2/external_initiators` and `GET /v2/bridge_types`.

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
