### Title
Cross-tenant webhook forgery via unsigned `X-Shopify-Shop-Domain` header trusted as authenticated shop identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` proves only that the body was signed with the app's shared `api_secret_key`, never that the accompanying shop-domain header is authentic. `Registry.process` calls `HmacValidator.validate(request)` and then, on success, passes the independently-read, unsigned `request.shop` straight into `WebhookMetadata` for the handler to act on, so shop-signed == shop-acted-on does not hold.

### Finding Description
Binding claimed: `HMAC(raw_body, api_secret_key) valid` should imply `request.shop is the authentic origin shop for that body`. Tracing the code shows this does not hold:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header independently of the signature and with no cross-check against the signed body [2](#0-1) .
- `HmacValidator.validate` computes `HMAC(verifiable_query.to_signable_string, Context.api_secret_key)` and compares it to the received `hmac` header — the shop-domain header is never part of the signable string [3](#0-2) .
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) .

Because `api_secret_key` is a single per-app secret shared across every shop that installs the app (not a per-shop secret), any webhook body legitimately delivered to the attacker's own shop's registered endpoint is HMAC-valid under the exact same secret used for every other shop of that app. An attacker who operates their own development shop with the app installed, registers their own callback URL, and receives a real webhook (e.g., `orders/create`) obtains a `(raw_body, hmac)` pair that is valid for that `api_secret_key` regardless of which shop's name is attached. The attacker then sends an HTTP POST directly to the victim host app's public webhook endpoint (a normal internet-reachable URL, not something only Shopify can reach) with the identical `raw_body` and `X-Shopify-Hmac-Sha256` value, but with `X-Shopify-Shop-Domain: victim.myshopify.com`. `HmacValidator.validate` returns `true` because it only checks body+secret, and `Registry.process` forwards `shop: "victim.myshopify.com"` to the handler as if it were an authentic webhook for that shop.

None of the existing guards close this gap: `ShopValidator.sanitize!` is not invoked anywhere in the webhook `Request`/`Registry` path (it's used in OAuth/token exchange flows) [4](#0-3) ; Sorbet typing only enforces that `shop` is a `String`, not that it matches the signed origin [2](#0-1) ; and no per-shop verification (e.g., checking the shop is a session the app has on record) occurs in `Registry.process`.

### Impact Explanation
This is a Critical cross-tenant authentication-bypass: a host app that relies on `WebhookMetadata#shop` (as the gem's own documentation instructs, `docs/usage/webhooks.md` shows handlers using `data.shop` to route/attribute work) after `Registry.process` succeeds will process an attacker-supplied payload as if it originated from an arbitrary victim shop. Repeated for every `(topic, body)` pair the attacker can legitimately trigger for their own shop, this lets the attacker inject fabricated events (e.g., fake order data, fake app/uninstall events) attributed to any victim shop domain known to the attacker (shop domains are often guessable/public), with no way for the host app to distinguish forged webhooks from genuine ones using the mechanisms this gem provides.

### Likelihood Explanation
Preconditions are low-cost and fully attacker-controlled: create a free development/trial shop, install the target app, register a webhook endpoint under the attacker's control, capture one legitimate signed webhook, then replay it with a rewritten `X-Shopify-Shop-Domain` header to the victim's exposed webhook URL (the endpoint path is typically predictable/documented, e.g. `callback/orders/create`). No credentials, secrets, or privileged access are required — this matches the stated unprivileged attacker model exactly. It is trivially repeatable against any number of victim shops using the same app.

### Recommendation
Do not trust `Request#shop` as authenticated shop identity based solely on `HmacValidator.validate`. Either (a) include the shop-domain header in the signable string used for HMAC computation so tampering invalidates the signature, or (b) require the host app / `Registry.process` to cross-check `request.shop` against a known/installed shop (e.g., an existing session) before invoking the handler, and document this requirement prominently since the gem's own current documentation implies `data.shop` can be trusted after `Registry.process` succeeds.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_trusts_unsigned_shop_domain_header_cross_tenant
  attacker_body = '{"id":1}'
  hmac = OpenSSL::HMAC.digest(
    OpenSSL::Digest.new("sha256"),
    ShopifyAPI::Context.api_secret_key,
    attacker_body,
  )
  headers = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac), # valid for attacker's own shop's webhook
    "x-shopify-shop-domain" => "victim.myshopify.com", # forged, attacker-controlled header
  }
  request = ShopifyAPI::Webhooks::Request.new(raw_body: attacker_body, headers: headers)

  # Binding under test: HMAC validity should not imply the shop header is authentic
  assert(ShopifyAPI::Utils::HmacValidator.validate(request)) # passes: body/secret only
  assert_equal("victim.myshopify.com", request.shop)         # unsigned, attacker-chosen

  received_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(->(data) { received_shop = data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
  )

  ShopifyAPI::Webhooks::Registry.process(request)

  # Demonstrates cross-tenant forgery: handler receives victim's shop for attacker-supplied body
  assert_equal("victim.myshopify.com", received_shop)
end
```
