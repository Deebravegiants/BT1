### Title
Deposit into a zero-`total-assets` pool mints zero shares while still crediting `assets`, letting existing shareholders steal the depositor's principal - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`convert-to-shares-preview` returns `u0` whenever `total-assets-preview()` is `0` and `total-supply-preview()` is non-zero, but `deposit` has no guard against minting `0` shares (unlike `redeem`, which explicitly rejects `inkind = 0` via `ERR-OUTPUT-ZERO`). If `assets` is ever driven to `0` while `zft` supply remains positive (e.g. via `socialize-debt`), the next depositor's underlying is silently added to `assets` with zero shares minted, and every existing shareholder's price-per-share jumps from `0` to a positive value funded entirely by that depositor's donated principal.

### Finding Description
The broken identity: for depositor `d` depositing `amount` when `ta = total-assets-preview() = 0` and `ts = total-supply-preview() > 0`:

```
shares_minted(d) = convert-to-shares-preview(amount) = 0     (v0-vault-ststx.clar:311-315)
assets_after      = assets_before(0) + amount                (v0-vault-ststx.clar:781)
```

So depositor `d` contributes `amount` to `assets` but owns `0` shares of it. For attacker `a` who already holds shares `s_a` (with `ts` total supply, unaffected by the zero mint):

```
convert-to-assets-preview(s_a)_before = mul-div-down(s_a, 0, ts) = 0
convert-to-assets-preview(s_a)_after  = mul-div-down(s_a, amount, ts) > 0
```

The attacker's redeemable value strictly increases by `s_a * amount / ts`, funded 100% by `d`'s deposit, with `d` receiving `0` shares and thus `0` claim on `amount` — the vault's fundamental invariant "every unit of `assets` backing shares came from a share-minting deposit of an equal proportional amount" is violated.

Code path:
- `convert-to-shares-preview` (v0-vault-ststx.clar:308-315) returns `amount` when `ts=0`, else `u0` when `ta=0`, else `mul-div-down(amount, ts, ta)`. The `ta=0 && ts>0` branch is mathematically undefined (price-per-share is 0) but the code silently maps it to `0` shares instead of reverting.
- `deposit` (v0-vault-ststx.clar:763-795) computes `inkind` from this preview, checks only `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` — which is satisfied by `inkind=0` as long as `min-out=0` (the default a naive/bot caller would pass) — then unconditionally does `(try! (ft-mint? zft inkind recipient))` (mint of `0`, a no-op) and `(var-set assets (+ current-assets amount))`, crediting the full `amount` to `assets` regardless of shares minted.
- Contrast with `redeem` (v0-vault-ststx.clar:797-831), which explicitly has `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` — the symmetric guard is simply missing from `deposit`.

How `ta` reaches `0` while `ts>0`: `MINIMUM-LIQUIDITY` (u1000) shares are permanently minted to `NULL-ADDRESS` at `initialize` (v0-vault-ststx.clar:494-509), so `total-supply` never returns to `0` again. `redeem`'s own `ERR-OUTPUT-ZERO` and rounding-down guard mathematically prevent any single caller from redeeming assets down to exactly `0` while other shares (including the immutable `NULL-ADDRESS` 1000) remain outstanding — `inkind = floor(X*ta/ts) < ta` strictly whenever `X < ts`. However, `socialize-debt` (v0-vault-ststx.clar:944-984) can set `(var-set assets ...)` to exactly `0` directly (bad-debt write-down), independent of `ts`, which is the realistic trigger for the `ta=0, ts>0` state that this bug then exploits.

### Impact Explanation
Once `ta=0, ts>0` occurs (from a bad-debt socialize event), every subsequent depositor who deposits before anyone notices/fixes the pool loses their entire deposited `amount` to existing shareholders pro-rata — this is direct theft of principal, matching Critical severity ("direct theft of user funds at rest"). The divergence per deposit call equals the full deposited `amount` (100% loss to the depositor, 100% transferred to remaining shareholders' claim). The bug is repeatable across every distinct occurrence of the `ta=0` state (each future bad-debt event that zeroes `assets` while `zft` supply survives re-opens the same exploitable window), so it is not a single one-shot bug but a structural flaw triggered any time the precondition recurs. The party absorbing the loss is the zero-share depositor; the beneficiaries are all pre-existing shareholders (including any attacker who deliberately positions shares before/during the `ta=0` window).

### Likelihood Explanation
Preconditions: (1) `total-assets-preview()` must be exactly `0` while `zft` total supply is `>0` — reachable via `socialize-debt`, which is only callable by an authorized contract (`check-caller-auth`, v0-vault-ststx.clar:960) representing the lending system's bad-debt write-off, not directly by an unprivileged attacker; (2) a deposit must land while the pool is still in that state — the attacker needs to race a deposit transaction (their own, or an unsuspecting victim's) into that window. Capital cost to the attacker is just their existing share balance (no flashloan required for the theft step itself). Because `convert-to-shares` (read-only) also returns `0` in this state, a careful UI/integrator checking the preview before depositing would see "0 shares" and could avoid the trap, which lowers likelihood for sophisticated depositors but not for naive/automated ones or attacker-controlled deposits used to bait others.

### Recommendation
Add a symmetric zero-output guard to `deposit`, mirroring `redeem`'s `ERR-OUTPUT-ZERO`: `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` immediately after computing `inkind` in `deposit` (v0-vault-ststx.clar:763-795). Additionally, treat `ta=0 && ts>0` as an unrecoverable/degenerate vault state that should require an explicit re-initialization path (e.g., burn remaining dust shares and reset `ts` to `0`, or mint 1:1 shares for the first re-depositor) rather than silently accepting deposits that produce `0` shares.

### Proof of Concept
Clarinet/vitest simnet test plan:
1. Deploy and `initialize` the vault (mints `MINIMUM-LIQUIDITY`=1000 shares to `NULL-ADDRESS`).
2. Have attacker deposit a large amount, e.g. `1_000_000_000` underlying, receiving proportional shares `s_a` (assets=`1_000_000_000`, ts≈`1_000_000_000+1000`).
3. Simulate a full bad-debt write-off via the authorized-contract-only `socialize-debt` call with a `scaled-amount` sized so that `old_total_assets - debt_reduction*principal_ratio == 0`, driving `(get-assets)` to exactly `u0` while `(get-total-supply)` remains `≈ s_a + 1000`.
4. Assert `(contract-call? .v0-vault-ststx get-total-assets)` returns `u0` and `(get-total-supply)` returns `> u0`.
5. Have victim `d` call `deposit(amount=500_000_000, min-out=0, recipient=d)`. Assert the returned `shares-minted` (`inkind`) is `u0` and assert `(get-balance d)` is `u0` after the call, while `(get-assets)` is now `500_000_000`.
6. Have attacker call `redeem(s_a, min-out=0, recipient=attacker)`. Assert `amount-received = convert-to-assets-preview(s_a)` is `> 0` (specifically `≈ s_a * 500_000_000 / ts`), proving the attacker extracted value that came entirely from `d`'s zero-share deposit rather than from the attacker's own pre-existing pro-rata claim (which was mathematically `0` immediately after step 3).
7. Assert `d`'s final redeemable value (`convert-to-assets-preview(0)` since `d` holds `0` shares) is `u0`, confirming `d`'s full contribution was transferred to attacker/remaining shareholders — violating the share-backing identity. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  (let (
    (states (var-get pause-states))
    (u (try! (accrue)))
    (account contract-caller)
    (current-assets (var-get assets))
    (balance (get-balance-internal account))
    (balance-check (asserts! (>= balance amount) ERR-INSUFFICIENT-BALANCE))
    (available-assets (get-available-assets))
    (inkind (convert-to-assets-preview amount)))

  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
  (asserts! (>= available-assets inkind) ERR-INSUFFICIENT-LIQUIDITY)

  (try! (ft-burn? zft amount account))

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

    (print {
      action: "socialize-debt",
      caller: contract-caller,
      data: {
        scaled-amount: scaled-amount,
        debt-reduction: debt-reduction,
        principal-reduction: principal-reduction,
        old-lindex: current-lindex,
        new-lindex: new-lindex,
        old-total-assets: old-total-assets,
        principal-scaled: (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0),
        total-borrowed: (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0),
        index: idx
      }
    })

    (ok true)))
