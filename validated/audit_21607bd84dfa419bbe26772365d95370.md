### Title
Consensus-incentives reward calculation applies the current cost-per-block over the entire unpaid block span, ignoring in-flight rate changes - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives::calculate_reward` computes a relayer's consensus-delivery reward as `(latest_height - baseline) * block_cost`, where `block_cost` is whatever `StateMachinesCostPerBlock` holds *at the moment the reward is computed*. It never accounts for the fact that `update_cost_per_block` may have changed the rate partway through the unpaid span (between `LastRewardedHeight` and the new `latest_height`). This is the same root-cause pattern as the referenced LoopFi finding: a flat "current rate × elapsed period" formula is used instead of splitting the period at the rate-change boundary.

### Finding Description
`calculate_reward` in [1](#0-0)  reads the persisted watermark (`LastRewardedHeight`, or `previous_commitment_height` as fallback) as the baseline, computes `blocks = latest_height - baseline`, and multiplies the *entire* span by the single `block_cost` value passed in from `process_message`, which is simply `StateMachinesCostPerBlock::<T>::get(state_machine_id)` read at call time: [2](#0-1) .

`update_cost_per_block` is a normal, expected governance operation that can be called at any time to retune the per-block reward rate: [3](#0-2) . There is no snapshot of "rate in effect per block" or per-height rate history — only a single current value in `StateMachinesCostPerBlock`. Consequently, if the rate changes while blocks are pending reward (i.e., between the last relayed consensus update and the next one), the entire accumulated span — including all the blocks that elapsed under the old rate — gets paid out at whatever rate is current when the next `StateMachineUpdated` event is processed via `FeeHandler::on_executed` → `process_message` → `calculate_reward`.

Because relayers permissionlessly and asynchronously decide when to submit the next consensus proof (an unsigned/self-selected extrinsic path reachable by any relayer delivering BEEFY/consensus updates), a rational relayer can strategically delay submitting a pending consensus update until after governance raises `cost_per_block`, then submit it to collect the entire backlog of blocks — including all blocks that accrued under the old, lower rate — at the new, higher rate. This drains more from `T::TreasuryAccount` than the emission schedule intended.

### Impact Explanation
Every block span that straddles a `cost_per_block` update is paid entirely at the new rate rather than a blended old/new-rate calculation. Because relayers control the timing of their consensus-update submissions, this allows an unprivileged relayer to intentionally hold back updates until a rate increase lands, then claim an inflated reward for the whole backlog, directly overpaying from the protocol `TreasuryAccount` via `T::Currency::transfer` at [4](#0-3) . This is a concrete, repeatable drain of treasury funds — a Medium-severity emission/reward-accounting bug, matching the reported bug class.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a `cost_per_block` change for a given state machine (an expected, routine governance action, not malicious), and (2) at least one relayer with a pending, undelivered consensus update at that time. Relayers are economically motivated and already control delivery timing, so the incentive to hold back a submission around a known/observable rate change is realistic and requires no special privilege — only observation of on-chain governance events.

### Recommendation
Track rate history (or accrue rewards incrementally on every relevant height/rate change) so that `calculate_reward` splits the `[baseline, latest_height]` span at each rate-change boundary and sums `Σ rate_i * blocks_in_segment_i`, mirroring the LoopFi mitigation of computing `oldRate * (changeHeight - baseline) + newRate * (latest_height - changeHeight)`. Alternatively, force `calculate_reward`/`process_message` to run (checkpoint reward accrual) on every `update_cost_per_block` call, snapshotting the reward owed up to the current height under the old rate before the new rate takes effect.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[X] = 10` via `update_cost_per_block`.
2. A relayer sees the consensus proof advance `latest_commitment_height` for chain `X` by 100 blocks but does not submit the corresponding consensus message yet (`LastRewardedHeight[X]` stays at the old watermark).
3. Governance raises the rate: `update_cost_per_block(X, 1000)`.
4. The relayer now submits the consensus update. `on_executed` → `process_message` → `calculate_reward` computes `blocks = 100`, reads the *current* `block_cost = 1000`, and pays `100 * 1000` instead of the intended `100 * 10` (or a correctly blended amount), overpaying the relayer 100x from `TreasuryAccount`. 	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)

		/// Update cost per block for a state machine
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]
		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {

			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
