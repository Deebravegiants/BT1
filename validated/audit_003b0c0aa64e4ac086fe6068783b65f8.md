Webhook `shop-domain` header is not covered by HMAC verification, allowing shop-identity spoofing on legitimate webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" via HMAC before dispatching to app handlers [1](#0-0) . However, the HMAC signature only ever covers the raw request body, never the `shop-domain` header that the gem hands to the handler as the authoritative tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` reads the `hmac-sha256` header value: [2](#0-1) [3](#0-2) 

`Registry.process` validates only this body-derived HMAC, then immediately trusts `request.shop` — sourced from the unauthenticated `shop-domain` header — to build `WebhookMetadata` passed to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding the gem's own documentation implies is: `HMAC-verified request == request whose shop/topic/body are all authentic`. The actual binding enforced is only: `HMAC(secret, raw_body) == received_hmac`. Since `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are excluded from the signed content, the equality that should hold — `verified_shop == actual_originating_shop` — does not, because `verified_bytes (body) ≠ bytes_the_handler_trusts_for_tenant_identity (shop header)`.

An unprivileged internet user who can install the app on their own (attacker-controlled) development shop will legitimately receive real, validly-HMAC-signed webhooks from Shopify for that shop. Because the signature is computed only from the body, the attacker can capture such a genuine `(body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` (and `topic`/`webhook-id`) header rewritten to a different value — e.g., a victim shop's domain, or a mandatory-compliance topic name (`shop/redact`, `customers/redact`, `customers/data_request`) — while the HMAC still validates successfully, since it only checks the untouched body bytes.

### Impact Explanation
This crosses a tenant boundary inside the gem's own trust contract: the gem asserts (per `docs/usage/webhooks.md`) that a successful `Registry.process` call means the webhook is authentic and safe to act on for the shop the handler is told about via `WebhookMetadata#shop`. Any host application that uses `data.shop` from the handler to key persistence, authorization, or job dispatch (exactly as the gem's own example handler in `docs/usage/webhooks.md#L26` demonstrates: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-supplied header content under the assumption it was verified, enabling cross-tenant data confusion/injection using only a signature that was legitimately obtained for the attacker's own shop. This matches the Critical "cross-tenant access" category, since it lets one authenticated tenant (a shop the attacker legitimately controls) inject content that is trusted as belonging to a different tenant.

### Likelihood Explanation
Requires only that the attacker install the app (or otherwise cause a webhook to be sent) on a shop they control, capture the resulting webhook body and its valid `X-Shopify-Hmac-Sha256` value, then send a forged HTTP request to the app's public webhook endpoint with the same body/HMAC but altered `shop-domain`/`topic` headers. No secret, access token, or privileged account is needed — Shopify supplies the valid signature for free as part of normal app installation.

### Recommendation
Do not rely solely on the body-only HMAC as proof of the associated `shop-domain`/`topic`/`webhook-id` header values. Either:
1. Include the relevant headers (shop domain, topic, webhook id, api version) in the signable content that is HMAC-verified, or
2. After HMAC verification, cross-check `request.shop` against a shop the app has an active session/webhook registration for (i.e., only accept metadata for a shop this specific handler/topic is registered against), rejecting mismatches, rather than passing raw header values straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`. Shopify sends a real webhook, e.g. for `customers/data_request`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker captures `B` and `H`.
3. Attacker POSTs to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it only covers `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: customers/data_request` (unchanged or altered)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` even though that shop never sent this webhook, letting the host application act on attacker-controlled data believing it was authenticated for the victim tenant.

*Note: I could not fully verify how downstream host applications (outside this gem) use `WebhookMetadata#shop` in practice, since that logic lives outside `lib/shopify_api/**`; the analysis above is scoped strictly to what this gem's own code and documented contract guarantee.*
