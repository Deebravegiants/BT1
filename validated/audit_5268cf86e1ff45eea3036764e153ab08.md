### Title
Webhook shop-domain identity is not covered by HMAC, allowing cross-tenant spoofing via header manipulation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the `shop-domain` header (which becomes the trusted tenant identifier `WebhookMetadata#shop` passed to the app's handler) is read directly from an unauthenticated header and is never included in the signed data.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that value [2](#0-1) . `Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it against the `hmac` field [3](#0-2) . `Registry.process` accepts the request once that body-only HMAC check passes, then constructs `WebhookMetadata` using `request.shop` verbatim as the authoritative tenant identity delivered to the app's handler [4](#0-3) , and `WebhookMetadata.shop` is a plain `String` field with no further validation [5](#0-4) .

This breaks the identity binding: `shop authenticated (by HMAC) == shop acted upon (WebhookMetadata#shop)`. The HMAC only proves "this body was signed by our `client_secret`," not "this body belongs to this shop." Since the body's HMAC is independent of the shop header, an attacker who possesses one valid `(raw_body, hmac)` pair (e.g., their own tenant's own genuine webhook, which any merchant using the app legitimately receives/can capture) can resend the same raw body to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value corresponding to another tenant. `HmacValidator.validate` still passes because it only checks the body against the signature, and `Registry.process` dispatches the handler with the attacker-chosen `shop` value, causing the host application (which trusts this gem's documented `WebhookMetadata#shop` as the tenant key, per this gem's own API contract) to apply attacker-controlled webhook data under a different shop's identity.

### Impact Explanation
This is a cross-tenant identity-binding bypass: a request cryptographically valid for tenant A's data can be attributed to tenant B purely by manipulating an unauthenticated header, letting one merchant inject or mutate data (e.g., order/customer state, GDPR redact events) into another store's account inside the host app, which relies on this gem's `Request`/`WebhookMetadata` shop attribution as authoritative.

### Likelihood Explanation
Any account holder of the app (a merchant with legitimate webhook traffic for their own shop) can capture one legitimate webhook body+HMAC pair from Shopify and replay it to the endpoint with a forged `shop-domain` header — no `api_secret_key`, access token, or privileged access is required, only the ability to send an HTTP POST to the app's public webhook endpoint. This makes it a low-effort, internet-reachable exploit.

### Recommendation
Bind the shop identity into the verified signable data, or otherwise independently authenticate the shop header (e.g., validate `shop-domain` against the shop registered for the app/session that the webhook subscription belongs to) rather than trusting the header value once only the body HMAC is checked. At minimum, document/require host apps to cross-check `webhook_id`/`shop` against their own webhook subscription registry rather than trusting `WebhookMetadata#shop` directly.

### Proof of Concept
1. App is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both subscribed to `orders/create`.
2. Attacker's own store legitimately receives a webhook: raw body `B` with header `shopify-hmac-sha256: HMAC(secret, B)` and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends `POST` to the app's webhook endpoint with the same body `B` and same HMAC header, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully [6](#0-5) ; `HmacValidator.validate` succeeds because it only checks body `B` against the HMAC, which still matches [7](#0-6) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's order data>, ...)` [4](#0-3) , causing the host app to process attacker-controlled data under the victim's tenant identity.

      def initialize(raw_body:, headers:)

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
