### Title
Missing lower-bound check on `virtualLtReserve` lets an appreciated LT's `exchangeRate` round the launch-time virtual LT reserve to zero, zeroing `Pair.k()` and letting the first buyer drain the entire curve for free - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._deployAndSeed` computes the launch-time virtual LT reserve as an integer division of a fixed USD constant by the paired LT's live `exchangeRate()`, and only guards the *upper* bound of the result (`ExchangeRateTooLow`) and the *zero exchangeRate* case (`ZeroExchangeRate`). It never checks that the computed `virtualLtReserve` itself is non-zero. Because BounceTech LTs are externally-controlled, appreciating, rebasing-priced assets with no upper bound on `exchangeRate()`, a creator can simply pick — or wait for — an LT whose `exchangeRate()` is large enough that `(VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate` truncates to `0`. That zero is passed straight into `Pair.mint`, permanently zeroing the pair's `k` invariant, which collapses `Router._computeBuy`'s overflow-cap math to hand out the *entire* 750M real curve-token balance for `amountInUsed == 0`.

### Finding Description
`Bonding._deployAndSeed` (`packages/contracts/src/Bonding.sol:477-494`): [1](#0-0) 
computes:
```
uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();
if (exchangeRate == 0) revert ZeroExchangeRate();
uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();
...
$.router.addInitialLiquidity(tokenAddr, totalSupply, curveSupply, virtualLtReserve);
```
The two guards only reject: (a) `exchangeRate == 0`, and (b) `virtualLtReserve` too *large*. There is no check that `virtualLtReserve > 0`. Since `VIRTUAL_LIQUIDITY_USD * 1e18` is a fixed numerator and `exchangeRate` is a live, unbounded, appreciating LT price (`totalAssets/totalSupply` scaled to 1e18, per `docs/contracts-scope.md`/`AGENTS.md`'s description of the LT reserve asset), any `exchangeRate` above the numerator makes the division truncate to `0` — this is ordinary Solidity integer-division rounding, not a revert.

`virtualLtReserve = 0` then flows into `Router.addInitialLiquidity` → `Pair.mint(totalSupply, 0)`: [2](#0-1) 
`_pool.k = tokenReserve * assetReserve = totalSupply * 0 = 0`.

With `k == 0`, the very next buy on the curve (the mandatory seed buy in `Zap.createToken`, or any subsequent unprivileged trader's `Zap.buy`) hits `Router._computeBuy`: [3](#0-2) 
- `tokensOut = reserveToken - (k / newReserveAsset) = reserveToken - 0 = reserveToken` (the full 1B virtual reserve), which always exceeds `realBalance` (750M, the actual transferred `curveSupply`), so the overflow-cap branch fires.
- `cappedReserveToken = reserveToken - realBalance = 250,000,000e18` (the `LP_RESERVE`), which is non-zero, so the `OverflowCapDegenerate` guard does not trip.
- `cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken = (0 + cappedReserveToken - 1) / cappedReserveToken`, which is `0` under integer division because the numerator is strictly less than the denominator.
- `amountInUsed = cappedReserveAsset - reserveAsset = 0 - 0 = 0`.

The buyer therefore receives the entire 750M real token balance of the curve (`tokensOut == realBalance`) while paying `amountInUsed == 0` LT. This also immediately satisfies the supply-side graduation trigger (`IPair.tokenBalance() == 0`, per `Bonding`'s dual-trigger logic), so the token graduates instantly with zero LT raised, and `_prepareGraduationLiquidity`'s `ltFromPair = assetReserve - virtualLtReserve = 0` seeds/burns the LP with nothing behind it.

This mirrors the CVE-2021-29593 bug class conceptually: an unvalidated divisor/derived-value degenerates to zero and corrupts all downstream arithmetic that assumes it is non-zero, silently producing an incorrect (here, catastrophically favorable-to-attacker) result instead of a safe revert.

### Impact Explanation
This is a direct, complete theft of the entire real curve token balance (750M of the 1B token supply) for zero payment, executable by any unprivileged creator (via `Zap.createToken`) who selects a sufficiently appreciated LT, or by any trader who buys into such a curve. It is a concrete "unbacked token payout" and effectively drains value intended for legitimate buyers/LP, and forces an immediate, worthless graduation (zero LT backing the seeded LP). This satisfies the report's bar for Critical/High impact (unbacked token payouts, permanent value loss to the curve/LP).

### Likelihood Explanation
Reachability requires only that some BounceTech LT's `exchangeRate()` exceed `VIRTUAL_LIQUIDITY_USD * 1e18` at the moment `Bonding.launch`/`Zap.createToken` is called — fully within reach of an unprivileged actor, since `exchangeRate` is a live, unbounded, monotonically-drifting external price and `Bonding.launch` only rejects retired LTs (`ltExists` gate), not high-priced ones. Because leveraged tokens are designed to appreciate over long horizons, this condition becomes increasingly likely to be met by long-lived/highly-leveraged LTs, and a creator can also choose which LT to pair against, making this trivially triggerable on demand once such an LT exists.

### Recommendation
Add an explicit lower-bound revert in `Bonding._deployAndSeed` immediately after computing `virtualLtReserve`, e.g. `if (virtualLtReserve == 0) revert ExchangeRateTooHigh();`, mirroring the existing upper-bound `ExchangeRateTooLow` check. Additionally, consider hardening `Router._computeBuy`'s overflow-cap branch to explicitly revert (rather than silently compute `amountInUsed = 0`) whenever `k == 0` or the computed `cappedReserveAsset` would be less than or equal to the current `reserveAsset`, as defense-in-depth against any other path that could zero `k`.

### Proof of Concept
1. Deploy/identify a BounceTech LT whose `exchangeRate()` (18-decimals) is `> VIRTUAL_LIQUIDITY_USD * 1e18` (i.e., an appreciated/high-priced LT — trivially simulated in tests via `MockLeveragedToken.setExchangeRate(largeValue)`, and realistically reachable on a long-lived leveraged token).
2. Call `Zap.createToken({..., ltAddress: <that LT>, ...}, seedUsdcAmount >= MIN_SEED_USDC)` as any unprivileged creator. `Bonding.launch` → `_deployAndSeed` computes `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate == 0` and calls `Router.addInitialLiquidity(token, totalSupply, curveSupply, 0)`, setting `Pair.k() == 0`.
3. The seed buy (or any subsequent `Zap.buy`) executes `Bonding.buy` → `Router.buy` → `_computeBuy`, which with `k == 0` returns `tokensOut = realBalance (750M)` and `amountInUsed = 0`.
4. Verify: the buyer's token balance increases by 750,000,000e18 tokens, while the LT actually pulled from the buyer (`amountInUsed`) is `0`; `Bonding.isGraduating(token)` becomes true with `ltFromPair == 0` cached for phase-2 LP seeding.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
