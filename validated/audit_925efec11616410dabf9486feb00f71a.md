### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant impersonation in webhook handlers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is taken from an HTTP header that is never covered by that signature. This breaks the intended binding `HMAC-verified bytes == identity used by the handler`, allowing an attacker who can obtain any validly-signed webhook body (e.g. by installing the app on their own store and triggering an event) to relabel that payload as belonging to an arbitrary victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a value completely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the *body* bytes were signed by Shopify with the app's secret) and then immediately trusts `request.shop` as the tenant identity passed to the handler, without any cross-check that this shop is the one the signature was actually issued for: [3](#0-2) 

The identity binding that should hold is:
`bytes verified by HmacValidator == bytes that determine tenant (shop)`
but here the verified bytes are `raw_body` only, while the tenant-determining bytes are the unauthenticated `shop-domain` header — an equality that does not hold.

### Impact Explanation
Any party who can obtain one validly HMAC-signed webhook body/signature pair for the app’s shared secret (trivially available to any merchant who installs the app on their own store and triggers a webhook event) can replay that exact `(raw_body, hmac)` pair to the app’s webhook endpoint while substituting the `shop-domain` header for a different, victim shop. Because `HmacValidator.validate` never binds the shop to the signature, the request passes validation and the handler receives `WebhookMetadata` claiming to be from the victim shop with attacker-controlled body content. If the host application uses `data.shop` (as documented) to key look-ups (e.g., load the victim's stored access token/session, write to the victim's local records, or trigger a merchant-scoped action), this results in cross-tenant data injection/confusion — the impersonation of one merchant's webhook traffic as another's.

### Likelihood Explanation
The gem's own documented pattern is for the handler to trust `WebhookMetadata#shop` as the tenant identifier once `Registry.process` has "validated" the webhook (that is exactly what `process` promises by raising `InvalidWebhookError` only on bad HMAC). No additional binding step exists anywhere in `lib/shopify_api/webhooks/**`. Obtaining a legitimately-signed body is low effort for anyone able to install the app (a normal, unprivileged action for any Shopify merchant), so likelihood of exploitation is high once such an app relies on this attribute for tenant scoping.

### Recommendation
Include the shop domain (and ideally the webhook id / topic) inside the HMAC-signed material used for verification, or otherwise cryptographically bind the declared `shop` value in `Webhooks::Request` to the request that was actually signed by Shopify — for example, by having `HmacValidator`/`Registry.process` reject any webhook whose `shop` cannot be confirmed to correspond to a shop actually associated with the given signature/topic pairing, or by requiring hosts to independently verify `webhook_id` uniqueness together with the calling shop before trusting `WebhookMetadata#shop`. At minimum, the gem should document explicitly that `shop` on `WebhookMetadata` is unauthenticated and must not be used as the sole tenant-selection key without additional server-side verification (e.g. matching against previously registered/installed shops).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a real webhook delivery with a body `B` and a valid `hmac = HMAC_SHA256(secret, B)` signed by Shopify.
2. Attacker sends a POST to the app’s webhook endpoint with the same raw body `B` and the same `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts the forged headers (no header is authenticated except by comparing to `raw_body`): [4](#0-3) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature matches `raw_body` — the header substitution does not affect the check: [5](#0-4) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, believing this data originated from the victim's store.
