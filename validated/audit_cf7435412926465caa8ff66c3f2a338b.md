### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `Utils::HmacValidator.validate` proves nothing about the `shopify-shop-domain` header. `Webhooks::Registry.process` nonetheless trusts this unauthenticated header as the tenant identity passed to the app's handler. An attacker who legitimately owns one shop (any unprivileged merchant who has installed the app) can capture a real, validly-signed webhook body from their own store and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to point at a victim shop, producing a signature that still validates.

### Finding Description
The identity binding that should hold is:

`shop authenticated by HMAC == shop used to route/attribute the webhook payload`

In this gem it does not:

- `Request#to_signable_string` only returns `@raw_body`: `lib/shopify_api/webhooks/request.rb:35-38`. [1](#0-0) 
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body: `lib/shopify_api/webhooks/request.rb:20-23`. [2](#0-1) 
- `Registry.process` validates the HMAC (which only covers the body) and then forwards `request.shop` unchanged into `WebhookMetadata`, which is handed to the app's handler as the authoritative tenant identifier: `lib/shopify_api/webhooks/registry.rb:188-199`. [3](#0-2) 
- `Utils::HmacValidator.validate_signature` recomputes HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares to the received `hmac`: `lib/shopify_api/utils/hmac_validator.rb:26-31`. [4](#0-3) 

Because the shop header sits entirely outside the signed content, "HMAC valid" only proves "this exact body was produced by Shopify for *some* shop that shares the app's secret," not "this body belongs to the shop named in the header." Any merchant who installs the app has their own valid `api_secret_key`-signed webhook traffic and can freely substitute the shop header before delivering the request to the app's endpoint (webhooks are delivered over plain HTTPS POST to a URL the app owns/exposes, not over a channel that itself authenticates the source shop).

### Impact Explanation
This breaks the cross-tenant isolation boundary: an unprivileged merchant of the app can cause the app to process attacker-controlled webhook data while it is attributed to a different tenant (`WebhookMetadata#shop`), because the shop identity used downstream is never covered by the same HMAC that gatekeeps the request. Any handler that uses `metadata.shop` to select which tenant's records to create/update/delete (the documented and intended purpose of that field, per `docs/usage/webhooks.md`) can be made to write attacker-controlled data into another tenant's context — cross-tenant access/data injection — without possessing that tenant's access token, `client_secret`, or any credential.

### Likelihood Explanation
Requires nothing but an ordinary installation of the app on an attacker-controlled development/test store to obtain genuine signed webhook traffic, plus the ability to POST to the app's own publicly-reachable webhook URL with a modified header — no secret key, no token theft, no TLS interception, no social engineering. This is squarely within "unprivileged internet user" capability.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the verified body before it's handed to `WebhookMetadata`/handlers — e.g., require the host application to independently verify that `request.shop` corresponds to a shop it has an active session for, and document this as a hard requirement rather than leaving `shop` fully trusted from an unauthenticated header.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook event (e.g., updates a product), receiving from Shopify:
   - Body: `{"id": 1, ...}` 
   - Header `shopify-hmac-sha256: <valid HMAC of body with app's api_secret_key>`
   - Header `shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker replays the exact same body and `shopify-hmac-sha256` value directly to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler receives `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled body>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and acts on victim-shop's tenant data using attacker-supplied content.
