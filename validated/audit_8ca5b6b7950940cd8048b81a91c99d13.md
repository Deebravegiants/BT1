### Title
Reentrant escrow drain via CEI violation in `IntentGatewayV2.withdraw` (Tron variant) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron build of `IntentGatewayV2` implements escrow release with a low-level external token call executed **before** the escrow accounting is decremented and with **no reentrancy guard** anywhere in the contract, unlike the hardened EVM/`IntentsBase.sol` implementation which explicitly decrements state before transferring.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the internal function invoked from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` messages) and from `onGetResponse()` (for source-initiated cancellations): [1](#0-0) 

The critical ordering bug: for each escrowed token it checks `_orders[commitment][token] == 0`, then performs the external transfer (`.call(...)` for both native value and ERC20 `transfer`), and only *afterwards* does `_orders[body.commitment][token] -= amount;`. This is a Checks-Effects-Interactions violation — the state that gates repeat withdrawal is updated after the external call that could trigger reentrant execution.

Compare this to the fixed, canonical `_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol`, which decrements `_orders` **before** calling `_sendValue`/`safeTransfer`: [2](#0-1) 

Neither `withdraw()`, `onAccept()`, nor `onGetResponse()` in the Tron contract carries a `nonReentrant` modifier (grep for `nonReentrant`/`ReentrancyGuard` across the file returned no matches), and the token transfer uses a raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` rather than `SafeERC20.safeTransfer`, so any token address supplied in `order.inputs` — which is attacker-controlled at order-creation time — can execute arbitrary code during the "transfer" leg of `withdraw`.

Because `_filled[body.commitment]` is also written unconditionally at withdraw-entry without checking a prior state, and because the per-token check only guards against a *fully zeroed* balance (not against a mid-loop reentrant partial-drain), a token with a transfer hook can re-enter the withdrawal path before `_orders[commitment][token]` is decremented, allowing the same escrow slot to be paid out more than once — the "double payout of an already-consumed resource" analog to the double-free primitive in CVE-2017-12925, applied to escrowed funds instead of memory.

### Impact Explanation
A successful reentrant call before the balance decrement lands allows draining the same escrowed token balance for a commitment more than once, resulting in direct theft of escrowed user/solver funds from the IntentGateway — a concrete "theft of funds" outcome, which the validation rules classify as Medium/High severity depending on exploitability of a chosen malicious token as an order input.

### Likelihood Explanation
This path is reachable by an ordinary flow: any user can create an order specifying an arbitrary ERC20 as an input token (subject to whatever allowlisting exists at order-creation, which was not confirmed in this pass), and a relayer or the order originator can then trigger `onAccept`/`onGetResponse` to invoke `withdraw()`. The exploitability hinges on (a) whether the deployed configuration permits an arbitrary/attacker-controlled token as an escrowed input, and (b) whether `onAccept`/`onGetResponse`'s `onlyHost` restriction and the ISMP replay-protection at the host layer (which sets request receipts before invoking `onAccept`) can be bypassed to achieve genuine re-entry into `withdraw` mid-loop for the *same* commitment via a different entry point (e.g., a second token in the same withdrawal request, or a chained call back into the gateway through another public function that reaches `withdraw`/`_orders`). I was not able to fully verify token-allowlisting or a second reachable call path into `withdraw` for the same commitment within this pass, so likelihood is assessed as plausible but not conclusively proven exploitable end-to-end.

### Recommendation
Apply the same Checks-Effects-Interactions ordering already used in `IntentsBase.sol` to the Tron `IntentGatewayV2.withdraw`: decrement `_orders[body.commitment][token]` before performing the native/ERC20 transfer, replace raw `.call` for ERC20 transfer with `SafeERC20.safeTransfer`, and add a `nonReentrant` guard to `onAccept`/`onGetResponse` (or `withdraw` itself) as defense in depth.

### Proof of Concept
Concrete PoC could not be fully constructed within this pass because the order-creation/deposit function (which determines whether attacker-controlled ERC20 tokens are permitted as escrow inputs) was not located and inspected. The exploit sketch is:
1. Attacker creates a cross-chain order whose `order.inputs` includes a malicious ERC20 token with a `transfer()` hook.
2. A `RedeemEscrow`/`RefundEscrow` message (or `onGetResponse` cancellation) triggers `withdraw()` for that commitment with multiple tokens, including the malicious one.
3. During the malicious token's `transfer()` callback (before `_orders[commitment][token] -= amount` executes), the attacker re-enters a code path that calls `withdraw()` again for the same commitment/token before the balance is zeroed, receiving a second payout of the same escrow. [1](#0-0)
