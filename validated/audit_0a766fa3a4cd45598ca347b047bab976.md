### Title
Destination-side order cancellation permanently locks escrowed input tokens if the `RefundEscrow` message times out — ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`IntentGatewayV2._cancelFromDest` immediately and irreversibly marks an order as settled on the destination chain before the cross-chain `RefundEscrow` message that actually releases the escrowed tokens on the source chain has been delivered. If that message times out, `IntentGatewayV2` has no `onPostRequestTimeout` override to reverse the local "filled" mark, so the order can never be re-cancelled from either chain and the escrowed tokens are permanently stuck — the same class of bug as the referenced JOJO report, where an off-chain state change is triggered irrevocably by an on-chain action with no way to "undo" it if the downstream step fails.

### Finding Description
When a user (or, after expiry, anyone) calls `cancelOrder` from the destination chain, `_cancelFromDest` sets the finality flag before the cross-chain confirmation exists: [1](#0-0) 

This dispatches a `RefundEscrow` POST request from the destination chain back to the order's source chain. The escrowed input tokens live in `_orders[commitment][token]` on the *source* chain and can only be released when that source-chain gateway receives the `RefundEscrow` message via `onAccept`, per the documented flow: [2](#0-1) 

If this POST request times out (e.g. relayer unavailability, congestion, or any liveness failure on the destination-of-message chain), ISMP invokes `onPostRequestTimeout` on the app that dispatched it — i.e. `IntentGatewayV2`/`ExtrinsicIntents` on the order's destination chain. Neither `IntentsBase.sol`, `ExtrinsicIntents.sol`, nor `IntentGatewayV2.sol` override this callback. They inherit `HyperApp`'s default, which unconditionally reverts: [3](#0-2) 

On the EVM host, a reverting timeout callback does not clean up or notify the application — it simply restores the request commitment "so it can be retried," but never actually invokes any cleanup logic, and there's no other path in `IntentGatewayV2` that unmarks `_filled[commitment]`: [4](#0-3) 

The documentation itself confirms the timeout callback must succeed for the flow to make progress, and by default this app's callback can never succeed: [5](#0-4) 

Because `_filled[commitment]` is already non-zero on the destination chain, the alternate recovery route — cancelling from the source chain via a storage-proof GET request — is also permanently blocked, since that path explicitly reverts once the destination's `_filled` slot is non-empty: [6](#0-5) 

So once a `RefundEscrow` message times out, there is no contract-level path (destination-side retry, or source-side proof-of-unfilled) that can ever release the input tokens still held in `_orders[commitment][token]` on the source chain.

### Impact Explanation
This results in a permanent freezing of user funds: the order's escrowed input tokens on the source chain become unrecoverable once the refund message times out, because (1) the destination-side "filled/cancelled" flag can never be reset (the timeout callback always reverts) and (2) the source-side cancellation route is blocked by that same flag. This is a direct, contract-enforced loss of collateral analogous to the original JOJO finding — an irreversible state transition triggered without any way to roll it back if the dependent cross-chain step fails.

### Likelihood Explanation
POST request timeouts are a normal, expected part of Hyperbridge's design (used for relayer incentive/liveness failures) and are explicitly documented as a first-class occurrence, not an edge case requiring an adversary. Any user- or relayer-triggered destination-side cancellation (`cancelOrder` called before deadline by the user, or after deadline by anyone) whose `RefundEscrow` dispatch subsequently exceeds its timeout window (e.g., due to relayer unavailability, high fees, or congestion on the source chain) will trigger this permanent lock — no malicious actor is required.

### Recommendation
Implement an `onPostRequestTimeout` override in `IntentGatewayV2`/`ExtrinsicIntents` that, upon a timed-out `RefundEscrow` dispatch, reverts the destination-side `_filled[commitment]` mark (or otherwise re-enables the order for cancellation/retry), so that the withdrawal/refund action can be resubmitted or the funds otherwise recovered. Alternatively, defer setting `_filled[commitment]` until the corresponding source-chain refund is confirmed, or add a dedicated recovery/retry function usable after a proven timeout.

### Proof of Concept
1. User places a cross-chain order; input tokens are escrowed on the source chain (`_orders[commitment][token]`).
2. Before the order is filled, the destination gateway is called: `cancelOrder(order, options)` → `_cancelFromDest` sets `_filled[commitment] = user` and dispatches a `RefundEscrow` POST request to the source chain (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:297-307`).
3. Suppose no relayer delivers this POST request within `timeout` (a realistic, non-malicious liveness failure). The message times out.
4. `EvmHost.dispatchTimeOut(PostRequestTimeout, ...)` calls `IntentGatewayV2.onPostRequestTimeout`, which is unimplemented and inherits `HyperApp`'s reverting default (`sdk/packages/core/contracts/apps/HyperApp.sol:138-140`). The call reverts, so `EvmHost` merely restores the commitment for a future retry without any actual state cleanup (`evm/src/core/EvmHost.sol:885-899`).
5. The destination order remains permanently marked `_filled[commitment] != address(0)`.
6. Any attempt to cancel from the source chain fails: the GET-response verification observes a non-empty `_filled[commitment]` on destination and reverts with `Filled()` (per `docs/content/developers/evm/intent-gateway/overview.mdx:65`).
7. Result: `_orders[commitment][token]` on the source chain is never decremented and the escrowed tokens are permanently unreachable — no function in `IntentGatewayV2` can release them.

```text
    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
```

```text
**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.
```

```text
    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
```

```text
<Callout type="warning" title="Handler Must Succeed for Refund">
The timeout handler `onPostRequestTimeout` is called **before** refunding fees. If your handler reverts, the fees are **not refunded** and the timeout message can be resubmitted. This means `onPostRequestTimeout` can be called multiple times until it succeeds. Ensure your handler is idempotent and handles repeated calls gracefully.
</Callout>

Use the `@hyperbridge/sdk` to monitor request status and detect timeouts. The SDK generates the necessary proof and submits it to the source chain, which calls your contract's `onPostRequestTimeout` handler first. Only if the handler succeeds are relayer fees refunded to the `payer` address.

For complete timeout handling with code examples, see [Tracking POST Request Timeouts](/developers/sdk/tracking/timeouts).
```
