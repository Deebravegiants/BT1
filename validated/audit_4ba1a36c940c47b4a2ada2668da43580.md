## Title
Unauthenticated infinite loop in GRANDPA ancestry-chain traversal causes a permanent node hang (DoS) — ([File: modules/consensus/grandpa/verifier/src/lib.rs])

## Summary
`verify_grandpa_finality_proof` walks the attacker-supplied header ancestry chain from the claimed target header back to the trusted latest hash **before** any cryptographic verification of the GRANDPA justification takes place. Because the ancestry map is built entirely from attacker-controlled `unknown_headers` (with attacker-chosen `parent_hash` fields), a submitter can construct a cycle of headers that never reaches the trusted base hash. `AncestryChain::ancestry`'s traversal loop then spins forever, hanging the thread executing the ISMP consensus update — reachable by anyone through the permissionless `handle_unsigned` extrinsic (and even earlier, through `validate_unsigned`/transaction-pool validation), with no signature or stake required.

## Finding Description
The vulnerable traversal is in `AncestryChain::ancestry`: [1](#0-0) 

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

The map `self.ancestry` is built directly from the caller-supplied `finality_proof.unknown_headers` with no cycle detection: [2](#0-1) 

`verify_grandpa_finality_proof` calls this traversal at line 88, **before** the justification is cryptographically verified at line 92: [3](#0-2) 

```rust
let from = consensus_state.latest_hash;

let base = finality_proof.unknown_headers.iter().min_by_key(|h| *h.number())
    .ok_or(Error::UnknownHeadersEmpty)?;

if base.number() < &consensus_state.latest_height {
    headers.ancestry(base.hash(), consensus_state.latest_hash).map_err(|_| Error::InvalidAncestry)?;
}

let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;

// 2. verify justification.
justification.verify(consensus_state.current_set_id, &consensus_state.current_authorities)
    .map_err(|e| Error::JustificationVerify(e.to_string()))?;
```

Everything preceding the `ancestry(from, target.hash())` call is unauthenticated: `unknown_headers` are just SCALE-decoded structures, and the only checks so far are that `target.hash() == finality_proof.block` and `justification.commit.target_hash == finality_proof.block` (plain equality checks on attacker-chosen fields, not signatures). An attacker can therefore submit two crafted headers `H1`, `H2` where `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()`, set `target = H1` (highest block number in the set), and never include the trusted `from` hash reachable in that cycle. The `while current_hash != base` loop then alternates between `H1.hash()` and `H2.hash()` forever, since both are present in the map and lookups never fail.

This function is reached from the ISMP consensus-update path for GRANDPA-based state machines (Polkadot/Kusama parachains and standalone Substrate chains): [4](#0-3) [5](#0-4) 

which is itself invoked by `update_client`, the ISMP consensus handler called from `pallet_ismp::Call::handle_unsigned`, an unsigned/permissionless call, and — critically — also from `ValidateUnsigned::validate_unsigned`, which runs during transaction-pool validation for every submitted extrinsic before it is even included in a block: [6](#0-5) [7](#0-6) 

Because `validate_unsigned` calls `Self::execute(messages.clone())` (which reaches the same consensus verification), the hang can be triggered simply by broadcasting the malicious extrinsic to the network — it does not even need to be mined into a block to hang the node's transaction-pool validation logic.

## Impact Explanation
This is a route unable to deliver messages / a complete denial of service, matching the CVE-2025-30685 bug class (an easily exploitable "hang or frequently repeatable crash" affecting availability). Any node running the GRANDPA consensus client (validating relay-chain/parachain-based state machines) can be hung indefinitely by a single crafted, unsigned message. Since messages are validated in the transaction pool of every full node before block inclusion, the attack can degrade or halt block production/relaying across the network without spending any funds or requiring privileged access — a classic availability-only impact (no confidentiality/integrity loss), consistent with a Medium severity finding.

## Likelihood Explanation
Trivial to construct: the attacker only needs to craft two headers with reciprocal `parent_hash` fields (headers are just SCALE-encoded data structures the caller fully controls) and package them as `unknown_headers` in a `ConsensusMessage`. No signatures, stake, or special permissions are required — the message is dispatched as `handle_unsigned`/`validate_unsigned`, which is explicitly designed to accept "free" unsigned messages from anyone with a syntactically valid proof shape.

## Recommendation
Add cycle detection / a bound on traversal length in `AncestryChain::ancestry` (e.g. track visited hashes and return `Err` if a hash repeats, or cap iterations at `unknown_headers.len()` since a valid ancestry chain can visit each header at most once). Alternatively, verify the justification's cryptographic signature over the authority set *before* performing any ancestry traversal over unauthenticated header data, so a bogus/cyclic header set is rejected cheaply without ever reaching the traversal.

## Proof of Concept
1. Construct `H1` and `H2` (arbitrary contents) such that `H1.parent_hash = H2.hash()` and `H2.parent_hash = H1.hash()` (fully attacker-controlled, e.g. via `frame_system`-style headers with mismatched digests/extrinsics roots — validity of the header content is irrelevant since no state-root check happens yet).
2. Set `finality_proof.unknown_headers = vec![H1, H2]`, `finality_proof.block = H1.hash()` (so `target = H1` clears the `target.hash() != finality_proof.block` check).
3. Craft any `justification` bytes whose `commit.target_hash == H1.hash()` (decoding must succeed and the target-hash equality check must pass; actual signature content is irrelevant because verification never runs).
4. Wrap this into a `ConsensusMessage::Polkadot`/`StandaloneChain` and submit via `pallet_ismp::Call::handle_unsigned` (or simply broadcast it, triggering `validate_unsigned`).
5. `verify_grandpa_finality_proof` reaches `headers.ancestry(from, target.hash())` and loops forever between `H1` and `H2`, hanging the calling thread (transaction-pool validation or block execution).
