### Title
Webhook shop/topic/webhook-id identity spoofing via HMAC that only covers the raw body, not the headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify," but the HMAC signature it checks only covers the raw JSON body. The `shop`, `topic`, `webhook-id`, and `api_version` values — which are read straight from unauthenticated HTTP headers — are never included in the signed material, yet they are handed to the app's webhook handler as if they were verified. This breaks the intended binding `authenticated(payload) == claimed(shop, topic, webhook_id)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `to_signable_string` to return only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers with no cryptographic binding to the body or its signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` then trusts this validation as proof of Shopify origin, and forwards the *unauthenticated* `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler: [4](#0-3) 

Because the app's `api_secret_key` is a single shared secret used for **every** shop that installs the app (not per-shop), any user who installs the app on their own store can capture a legitimately-signed webhook delivery (valid `raw_body` + valid `hmac-sha256`) that Shopify sent them. They can then replay that exact `body`+`hmac` pair directly to the app's public webhook endpoint while forging the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers to name a different, victim shop/topic. Since none of those headers are covered by the signature, `HmacValidator.validate` still returns `true`, and `Registry.process` calls `handler.handle` with `shop:` set to the attacker-chosen victim shop and `topic:` set to whatever topic the attacker wants processed (e.g., an `app/uninstalled` or `shop/redact`/`customers/redact` handler that deletes or mutates data keyed by `shop`).

This is exactly the "field acted on but not covered by the HMAC" identity-binding failure: the gem authenticates *that some valid body was sent by Shopify for the app*, but the app-facing API (and its documentation) presents this as proof that the *specific shop/topic/webhook-id* combination was verified, which it is not.

### Impact Explanation
This allows cross-tenant impersonation: an attacker with access to only their own store's webhook traffic (unprivileged relative to other merchants) can trigger the app's webhook handler as if the event came from an arbitrary other shop and/or topic, causing data belonging to another tenant to be created, mutated, or deleted, or triggering privileged app-lifecycle logic (e.g., faking `app/uninstalled`, GDPR redact topics, or `shop/update`) against a shop the attacker doesn't control. This is a cross-tenant access impact.

### Likelihood Explanation
The attacker only needs: (1) their own free/dev store with the app installed to obtain one legitimately signed webhook body+HMAC pair, and (2) the ability to POST directly to the app's public webhook callback URL with forged headers — both are trivially available to any unprivileged party who can install the app once. No access token, `api_secret_key`, or privileged account is required.

### Recommendation
Bind the header-derived identity fields into the signed material that `HmacValidator` verifies (or otherwise cryptographically authenticate `shop`, `topic`, and `webhook_id` against the verified payload), and update `to_signable_string`/the HMAC validation contract so that spoofing any of these header values invalidates the signature. At minimum, the documentation for `Registry.process` should not claim to verify "the request did indeed come from Shopify" for fields that are not included in the HMAC.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker.myshopify.com`) and configure a webhook subscription for topic `orders/create`.
2. Capture the resulting legitimate delivery: `raw_body` and the `x-shopify-hmac-sha256` header — both valid under the app's shared `api_secret_key`.
3. Replay this exact `raw_body`/`hmac` pair to the app's webhook endpoint, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any registered topic/handler the attacker wants to trigger)
   - `x-shopify-webhook-id: <arbitrary>`
4. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged; `Registry.process` calls `Utils::HmacValidator.validate`, which passes because it only checks `raw_body` against the shared secret [5](#0-4) .
5. `handler.handle` is invoked with `shop: "victim-shop.myshopify.com"` and `topic: "app/uninstalled"`, causing the app to perform victim-shop-scoped actions (e.g., deleting victim shop's stored session/data) despite Shopify never having sent this event for that shop.
