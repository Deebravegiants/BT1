### Title
Stale cached operator authorization allows continued signup approval after a block decision - (File: src/plans/mod.rs)

### Summary
`orb-core`'s `MasterPlan` caches the result of the operator QR-code validation (`verify_operator_qr_code`) for the duration of `operator_qr_expiration_time` (default 23 hours). Once an operator is validated, subsequent signups reuse this cached authorization without re-querying the backend, so a backend-side decision to block/deauthorize that operator does not take effect on the Orb until the local cache expires. This is the same root-cause pattern as the reported bug: an authorization/blocking decision is made asynchronously against a party while a stale local state continues to permit action, letting the party "front-run" the block for the remainder of the cache window.

### Finding Description
The operator QR-code is validated once via `verify_operator_qr_code`, which calls `backend::operator_status::request` and returns `valid: true/false` based on the operator's current status [1](#0-0) . The result is stored as `OperatorData` with a `timestamp` [2](#0-1) .

In `scan_remaining_qr_codes`, if the cached `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, the Orb skips re-verification entirely and proceeds directly to scanning the user QR code, reusing the previously-approved operator authorization: [3](#0-2) 

The same pattern appears in `idle_wait_for_signup_request`/`scan_initial_qr_codes`, which only re-scans/re-verifies the operator QR when the cached timestamp has expired [4](#0-3) , and in `idle_scan_user_qr_code`, which is driven purely by the remaining time until `operator_qr_expiration_time` [5](#0-4) .

`operator_qr_expiration_time` defaults to 23 hours [6](#0-5) , meaning that once an operator is authorized, the Orb will not re-check that operator's status with the backend for up to 23 hours, regardless of any block/deauthorization action taken by the backend/manager in the interim.

### Impact Explanation
If a manager or backend operation blocks/deauthorizes an operator (e.g., due to detected abuse, fraud, or compromised credentials) while that operator's QR is already cached as valid on an Orb, the Orb will continue to accept that operator's authorization and run signups under their identity for up to the remaining cache window (up to 23 hours by default). This is a misattributed/unauthorized-signup-authorization impact: signups performed during this window are attributed to and enabled by an operator identity that the backend has already decided to block, undermining the intended real-time enforcement of the block.

### Likelihood Explanation
This requires no attacker skill beyond timing/awareness: an operator (or someone in possession of a soon-to-be-blocked operator QR code) simply needs to have already scanned the operator QR before the block is applied, or to continue operating within the 23-hour cache window after the block decision is made on the backend. Because the check-then-cache-then-reuse pattern is unconditional in the normal (non-self-serve gated) flow, likelihood is moderate-to-high in any deployment where blocking of operators is used as an incident-response mechanism.

### Recommendation
- Short term: Re-verify the operator QR-code / operator status against the backend before allowing continued use of a cached authorization for a new signup, or reduce `operator_qr_expiration_time`, or add a backend push/pull mechanism to invalidate cached operator sessions immediately when a block occurs.
- Long term: Treat all locally cached authorization decisions (operator, and potentially user) as revocable, and add periodic/inline revalidation for any authorization state whose validity is time-bounded, so that backend-side blocking decisions propagate to Orbs without waiting for the full expiration window.

### Proof of Concept
1. Operator scans their operator QR code; `verify_operator_qr_code` succeeds and `OperatorData.timestamp` is set to `Instant::now()` [7](#0-6) .
2. Backend/manager blocks the operator's account (e.g., via the management backend) immediately afterward.
3. Within `operator_qr_expiration_time` (up to 23 hours), the Orb performs further signups: `scan_remaining_qr_codes` sees `operator_data.timestamp.elapsed() < operator_qr_expiration_time` and reuses the cached `OperatorData` without calling `backend::operator_status::request` again [8](#0-7) .
4. Signups proceed and are attributed to/enabled by the now-blocked operator until the cache naturally expires.

                    continue;

                    continue;

                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
