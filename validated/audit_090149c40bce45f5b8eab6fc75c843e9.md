### Title
`validateStellarAddress()` accepts CRC16-checksum-invalid StrKey strings, letting `createWithdrawalIntents()` build a withdrawal to an unpayable Stellar receiver - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateStellarAddress` only checks the shape `/^G[A-Z0-9]{55}$/` and never decodes the base32 payload or verifies the CRC16 checksum that real Stellar StrKey addresses carry. Every other checksummed address type in the same file (Bitcoin, Litecoin, Dash, Tron, BCH) explicitly decodes and verifies its checksum, making this an outlier and a genuine gap rather than a deliberate simplification.

### Finding Description
The claimed equality is: `(chain=Stellar, address) validated by validateAddress == true` should imply `(chain=Stellar, address)` decodes to a valid StrKey `G...` account id with a correct CRC16 checksum. This does not hold: `validateStellarAddress` at [1](#0-0)  is a pure regex test with no base32 decode and no checksum verification, unlike the sibling checksummed validators in the same file, e.g. Bitcoin/Litecoin/Dash which decode and compare a computed checksum against the trailing bytes ( [2](#0-1) ). Any 56-character string starting with `G` and consisting of uppercase letters/digits — including one with a random, invalid final CRC16 — passes.

In `HotBridge.validateWithdrawal()`, this fake-but-regex-valid address is accepted at the `validateAddress` gate: [3](#0-2) . Separately and more importantly, `HotBridge.createWithdrawalIntents()` never calls `validateAddress` at all — it takes `args.withdrawalParams.destinationAddress` and passes it straight through as `receiver` to `this.hotSdk.buildGaslessWithdrawIntent(...)`: [4](#0-3) . The only sanity checks after that call are on `intent.amounts`, not on `receiver_id`/address correctness: [5](#0-4) .

The one place that performs a real network round-trip capable of catching a malformed Stellar address is the trustline check, gated on `assetInfo.blockchain === Chains.Stellar` and calling `this.hotSdk.stellar.isTrustlineExists(...)`: [6](#0-5) . That call lives in the third-party `hotSdk` (`@hot-labs/omni-sdk`) and talks to Horizon/Soroban RPCs — its correctness/behavior for a checksum-invalid address is an external-RPC/third-party-SDK trust assumption, which is explicitly out of scope for this audit. Within this repo's own code, there is no CRC16 verification anywhere in the reachable path.

### Impact Explanation
`createWithdrawalIntents()` is the function that actually builds the `mt_withdraw` intent (`receiver_id` in the built primitive) that gets signed and submitted to move HOT-bridged funds off NEAR intents. If a checksum-invalid but regex-matching Stellar address reaches it — either because `validateWithdrawal` was skipped/bypassed by an integrator, or because the trustline-check path in the third-party SDK does not itself perform a StrKey checksum validation before doing its lookup — the built intent will target an address that cannot receive funds on the Stellar network. This matches the Critical category: funds already signed and routed with no recovery path once the mt_withdraw intent executes, since intents-sdk's own address-format guard is the only in-repo control and it accepts the invalid checksum.

### Likelihood Explanation
Constructing a 56-character `G`-prefixed base32 string with an intentionally wrong last few bytes (breaking CRC16) is trivial and free for any caller supplying `destinationAddress` (an ordinary NEAR Intents user or an integrator forwarding a counterparty-supplied string). The regex-only check in `validateAddress` makes this pass with 100% reliability for `Chains.Stellar`, and `createWithdrawalIntents` itself performs no independent validation. Whether the exploit fully reaches an executed, funds-losing withdrawal depends on the external `hotSdk.stellar.isTrustlineExists` behavior for such malformed addresses (out of scope to verify here), but the in-repo function that is explicitly named as the "destination truth" guard (`validateAddress`) is confirmed broken for Stellar.

### Recommendation
Implement full StrKey decoding for Stellar addresses in `validateStellarAddress`: base32-decode the string, verify the version byte corresponds to an `ed25519 public key` (`G...`), and recompute/verify the CRC16-XModem checksum over the version+payload bytes, matching the pattern already used for Bitcoin/Litecoin/Dash/Tron in the same file. Additionally, consider having `createWithdrawalIntents` re-validate `destinationAddress` via `validateAddress`/`compareAddresses` as a defense-in-depth measure rather than relying solely on the caller having invoked `validateWithdrawal` first.

```ts
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

it("rejects a 56-char G-address with invalid CRC16 checksum", () => {
  // Real StrKey: base32(version_byte + 32-byte payload + 2-byte CRC16), 56 chars total incl. 'G'.
  // Take a real valid address and flip trailing checksum characters.
  const validLike = "GAEQ3MB7PSTGWKH2GK7O3HK5AKGH2RHVS4X7GDXV7BMX2GK4VL7GDHKD"; // 56 chars
  const brokenChecksum = `${validLike.slice(0, -2)}ZZ`; // corrupt last 2 chars (checksum bytes)

  // Current behavior (bug): regex-only check returns true even though CRC16 is wrong.
  expect(validateAddress(brokenChecksum, Chains.Stellar)).toBe(true); // should be false after fix
});
```

```typescript
function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
```
