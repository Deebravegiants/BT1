### Title
Read-modify-write race in `ConnectedOrigins` module allows concurrent `add()`/`untrust()` calls to lose the user's revoke, silently re-trusting an origin - ([File: features/connected-origins/module/connections.js])

### Summary
`isSoleWriter: true` on `connectedOriginsAtom` (and `connectedAccountsAtom`) only guarantees that the low-level storage `set()` calls are serialized against each other by the atom factory; it does **not** make the higher-level "read current array → compute new array → write array" sequences in `ConnectedOrigins` atomic. Concurrent invocations of `add`, `untrust`, `setAttributes`-based methods (`setFavorite`, `setAutoApprove`, `connect`, `disconnect`) all read a private snapshot with `#getData()`/`#getOrigin()` and later write it back with `#setData()`, with no version check or lock between the read and the write, so a slower `add()` in flight can overwrite a faster `untrust()`'s result.

### Finding Description
`connectedOriginsAtom` is created with `isSoleWriter: true` in [1](#0-0) . Looking at the underlying storage atom factory, `isSoleWriter`/the storage atom's `set()` only serializes the actual `storage.set(key, value)` write and cache update [2](#0-1) ; it operates purely on whatever final array value it is given — it has no knowledge of, or protection against, application-level compare-and-swap races that happen *before* `set()` is called.

The actual mutation logic lives in `features/connected-origins/module/connections.js`, and every mutating method follows the same unguarded pattern: read the whole array via `#getData()`, compute a new array in JS, then call `#setData()`: [3](#0-2) [4](#0-3) [5](#0-4) 

`add()` and `untrust()` each independently call `#getOrigin`/`#getData` (an `await`), then perform further async work (`#setData` computes connected accounts via `#getAccounts`, which awaits `addressProvider.getDefaultAddress` for each asset) before finally writing with `Promise.all([...atom.set(data)...])`. Because there are multiple `await` points between the read and the final write, two concurrent calls (e.g. a dApp's in-flight `add()`/`connect()` racing with a user-initiated `untrust()`) can both read the same pre-revoke snapshot; whichever call's `#setData` resolves last "wins" and overwrites the other's result — including reintroducing the origin that the user just revoked with `trusted: true` intact.

`dedupe()` does not fix this either — it only wraps the *final* value with an `isEqual` check against the atom's `previous`, it does not serialize or version the module's read step: [6](#0-5) .

Because the module never uses the atom's own functional-setter form (`atom.set(prev => ...)`) for these compound operations — it always computes the new array in the outer scope from a stale `#getData()` snapshot and calls `#setData(newData)` with a plain value — the `isSoleWriter` guarantee at the atom layer is bypassed at the module layer.

### Impact Explanation
An attacker-controlled dApp can keep an origin trusted (auto-approving future signing requests) even after a user explicitly revokes it via `connectedOrigins.untrust`. Since `isTrusted`/`isAutoApprove` gate signing/connection approval flows, this is a privilege-persistence / origin-trust-bypass: the wallet continues to treat a revoked malicious origin as trusted, enabling silent auto-approved connections/signing without user re-consent.

### Likelihood Explanation
The race requires the attacker's `add()`/`connect()` call to be in flight (already reached its async `#getAccounts`/address-lookup step) at the moment the user calls `untrust`, and for the attacker call's writes to resolve after the revoke's writes. This is timing-dependent but readily triggerable by a malicious dApp that repeatedly/eagerly calls its RPC connect/add endpoint (a normal, attacker-reachable RPC surface) so that some in-flight call overlaps with the user's revoke action — no privileged state or additional exploitation primitive is needed.

### Recommendation
Make the read-modify-write sequences in `ConnectedOrigins` atomic by using the atom's functional setter form (`connectedOriginsAtom.set(prev => ...)`), so that all mutations are queued/serialized against the atom's own current value instead of a value computed from an early, possibly stale, snapshot. Apply this to `#setAttributes`, `add`, `untrust`, `clearConnections`, `connect`, and `disconnect`.

### Proof of Concept
Integration test plan (Jest, similar to existing `features/connected-origins/module/__tests__/connections.test.js`):
1. Set up `connectedOriginsAtom`/`connectedAccountsAtom` with an already-trusted origin `exodus.com`.
2. Stub `addressProvider.getDefaultAddress` to introduce an artificial delay (e.g. `await delay(20)`) only on the first invocation, so `add()`'s internal `#getAccounts` await point is elongated.
3. Fire concurrently (do not await between them):
   - `connectedOrigins.add({ origin: 'exodus.com', trusted: true, connectedAssetName: 'solana' })` (delayed path)
   - `connectedOrigins.untrust({ origin: 'exodus.com' })` (fast path)
4. `await Promise.all([...])` both calls.
5. Assert `connectedOriginsAtom.get()` — expected (secure) result: origin absent (untrust wins, matches "last authorized intent"). Actual (vulnerable) result: origin still present with `trusted: true`, showing the delayed `add()` overwrote the `untrust()`.

const dedupe = <T>(atom: Atom<T>): Atom<T> => {
  const set = (value: T | Setter<T>) => {
    // avoid triggering a get() when we're resetting the atom
    if (value === undefined) return atom.reset()

    return atom.set(async (previous) => {
      const newValue = isSetter(value) ? await value(previous) : value
      return isEqual(previous, newValue) ? previous : newValue
    })
  }
