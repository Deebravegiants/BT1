### Title
Emporium's `runAction` Balance-Diff Check Is Scoped Only To `circomData.erc20TokenAddresses`, Allowing Arbitrary Unsigned Calls To Drain Any Other Token Balance Held By The Contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
The external report's bug class ("approval/whitelist logic that only validates a hardcoded set of parameters while a raw payload lets an attacker invoke an arbitrary function/target") maps onto Hinkal's `EmporiumUpgradeable.runAction`. In the "stateless" execution branch, when `stack.signerAddress == address(0)`, no EIP-712 signature check is performed at all, and the resulting arbitrary `endpoint.call(callData)` is only bounded by a balance-difference equality that is computed **exclusively over `circomData.erc20TokenAddresses`**. Any token balance the Emporium contract happens to hold outside that caller-supplied array is invisible to the check and can be moved by an unprivileged caller.

### Finding Description
`Hinkal._externalTransact` transfers the withdrawn amount to the external action address (Emporium) before invoking `runAction`: [1](#0-0) 

Inside `EmporiumUpgradeable.runAction`, `verifyWallet` is the only gate on the operations to be executed, and it explicitly skips signature verification when no wallet is used: [2](#0-1) 

When `stack.signerAddress == address(0)`, every operation falls into the "Stateless Interaction" branch, which performs a raw low-level call to an attacker-chosen `endpoint` with attacker-chosen `callData`, with the only restriction being that the selector isn't `callHinkalWallet`/`doSendToRelay` (a wallet-only protection, irrelevant here): [3](#0-2) 

The only safety net against this arbitrary call is the post-execution balance-difference check, but that loop iterates only over `circomData.erc20TokenAddresses` — an array fully controlled by the same unprivileged caller who also supplies the ops: [4](#0-3) 

Because `circomData` (including `externalActionData.externalActionMetadata`, which encodes the `EmporiumStack`/ops, and `erc20TokenAddresses`) is entirely attacker-supplied and only checked for internal hash-consistency via `getHashedCalldata`/`calldataHash` (not for completeness of which tokens must be covered): [5](#0-4) 

an attacker can simply omit any token they intend to steal from `circomData.erc20TokenAddresses`. The equality the protocol relies on ("balance moved by an external action == amount accounted for in the tracked token array") is broken: value can be moved out of the Emporium contract for tokens that are never part of the tracked array, so it is never validated by either `EmporiumUpgradeable.runAction`'s internal check or by `Hinkal.transact`'s outer balance-diff/slippage checks (which likewise only loop over `circomData.erc20TokenAddresses`): [6](#0-5) 

### Impact Explanation
Any ERC20/ETH balance that persists on the Emporium contract outside of a single atomic `runAction` execution (e.g., dust left over from imperfect swaps/deposits, fee remnants, or funds belonging to another in-flight/undelivered operation) can be moved by an unrelated, unprivileged caller by crafting a stateless op targeting that token/contract and simply excluding it from `erc20TokenAddresses`. This is theft of protocol/relay-adjacent funds sitting in a shared contract without requiring any admin, relay, wallet-owner signature, or another user's key — matching the High/Critical bar of "theft or permanent freezing of protocol/relay fees" or "executing calls... a wallet owner or prover never authorised," since the call is made from the Emporium contract's own context (`msg.sender == Emporium`), not the attacker's.

### Likelihood Explanation
Reachable by any unprivileged EOA: `Hinkal.transact()` is a public entrypoint, and the signer-less (`signerAddress == address(0)`) Emporium path is the standard flow for direct (non-wallet) users, requiring only a valid ZK proof over the attacker's own genuine shielded funds — no compromise of a Governor, admin, or relay is needed, unlike the original report's scenario. The only prerequisite is that the Emporium contract be holding some balance of a token not declared in the attacker's `erc20TokenAddresses`, which is plausible given normal operational dust/residuals.

### Recommendation
Bind the set of tokens whose balances must be checked to the full universe touched by the ops (e.g., require `erc20TokenAddresses` to include every token referenced by `op.endpoint`/decoded transfer targets, or enforce a global "no net balance decrease for any token not explicitly declared" invariant), and/or restrict stateless-call `endpoint`s to a pre-approved allowlist of router/token contracts rather than allowing arbitrary `call` targets when `signerAddress == address(0)`.

### Proof of Concept
1. Assume the Emporium contract holds a nonzero balance of `TokenX` (e.g., dust left from a prior imperfect swap or another user's not-fully-swept output).
2. An attacker who owns their own valid shielded UTXOs (no special privileges needed) calls `Hinkal.transact()` with `externalActionData.externalAddress = Emporium`, `erc20TokenAddresses` containing only tokens they legitimately control (e.g., a small `TokenY` withdrawal), and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one op: `{ endpoint: TokenX, invokeWallet: false, value: 0, callData: TokenX.transfer(attacker, TokenX.balanceOf(Emporium)) }`.
3. `verifyWallet` returns immediately without any signature check since `signerAddress == address(0)`.
4. The stateless branch executes `TokenX.transfer(attacker, ...)` directly from Emporium's context, succeeding since `msg.sender == Emporium`.
5. Both `EmporiumUpgradeable.runAction`'s balance loop and `Hinkal.transact`'s outer balance-diff loop only iterate over `circomData.erc20TokenAddresses` (which contains only `TokenY`), so the `TokenX` outflow is never checked, and the transaction succeeds, leaving the attacker with the stolen `TokenX`.
