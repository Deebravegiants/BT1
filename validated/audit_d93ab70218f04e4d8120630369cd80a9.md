### Title
Webhook `shop` identity is not bound to the HMAC-verified payload, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` only authenticates the body bytes against the app's shared `client_secret`. The `shop` field, which the gem exposes to the host application's webhook handler and which apps use as the tenant key (per the gem's own docs), comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never covered by the HMAC. This is exactly the "field acted on but not covered by the HMAC" class of bug: the binding `verified(bytes) == used(shop)` does not hold — HMAC verifies `raw_body`, but the shop tenant identity used downstream is an unauthenticated header.

### Finding Description
`Request#hmac`, `#topic`, and `#shop` are all read from HTTP headers via `shopify_header`, but `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, i.e. against `request.to_signable_string` (the body), then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed to the app's handler: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature purely from `to_signable_string`: [3](#0-2) 

Shopify webhook HMAC signatures are computed with the app's single `client_secret` (`Context.api_secret_key`), which is the same secret for every shop that installs the app — it is not shop-specific. Since the shop-domain header is excluded from the signed content, any party who can obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on a shop they control and receiving a legitimate webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never inspects the shop header, and the host app's handler will process the payload under the attacker-chosen shop identity — exactly as the docs illustrate handlers keying off `data.shop`: [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the identity binding `authenticated_bytes == shop_used_for_tenant_action`. An attacker with any single legitimate installation of the target app can forge webhooks that the gem reports as HMAC-valid for a victim shop of their choosing, letting them inject attacker-controlled webhook bodies (order data, product data, GDPR events, etc.) into another tenant's data pipeline. This is a cross-tenant access/injection vulnerability — Critical impact per the given classification.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs their own legitimate app installation (a normal merchant capability) to capture a valid `(body, hmac)` pair signed with the app's shared secret, then replay it to the app's public webhook endpoint with a spoofed shop-domain header. No secrets, tokens, or privileged access to the victim are required.

### Recommendation
Bind the shop identity into the HMAC-verified content, or otherwise cryptographically/contextually tie the shop header to the authenticated request:
- Include the `shop` (and ideally `topic`/`webhook_id`) in `to_signable_string`'s signed material, or
- Cross-check `request.shop` against a shop the app has an active/known webhook registration or session for before dispatching to the handler, rejecting shops that are not recognized/expected for that registered webhook, and
- Document clearly that `data.shop` from `WebhookMetadata` is not itself HMAC-protected today, so host apps must not treat it as authenticated without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and registers for a webhook topic (e.g. `orders/create`) via the app.
2. Shopify sends a legitimate webhook to the app's endpoint for `attacker.myshopify.com`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — `client_secret` is the same for all shops using this app.
3. Attacker captures `(B, H)`.
4. Attacker sends a raw HTTP POST directly to the app's webhook route with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), and header `X-Shopify-Shop-Domain: victim.myshopify.com` (spoofed).
5. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers))`.
6. `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` returns `B`, and `H` matches `B` (per line 190 of `registry.rb` and lines 12-31 of `hmac_validator.rb`).
7. `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)` is passed to the app's handler, which processes/persists data as if it legitimately originated from `victim.myshopify.com`, despite the attacker fully controlling the payload and shop claim.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
