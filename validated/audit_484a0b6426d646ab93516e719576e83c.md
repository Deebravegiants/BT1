## Confirmed: `compute_all_storage_keys` runs before proof verification

`verify_validator_set_proof` calls `compute_all_storage_keys` on the **raw, unverified** `proof.storage_values` *before* `verify_all_storage_proofs` checks them against `state_root`: [1](#0-0) 

This means `bls_data_slots_from_header`, called from `compute_all_storage_keys`, operates on attacker-controlled bytes carried inside a relayed consensus/state-proof message, submitted by any unprivileged relayer.

### Title
Unbounded/overflowing BLS-string length derived from unverified Pharos storage header causes panic in `compute_all_storage_keys` - (File: modules/consensus/pharos/verifier/src/state_proof.rs)

### Summary
`bls_data_slots_from_header` derives a slot count (`data_slots`) from a raw, **not-yet-verified** storage value (`storage_values[idx]`), analogous to the ALSA bug where a size value derived by scaling an untrusted field is used before being clamped against a hardware/allocation limit. Like `snd_usb_handle_sync_urb()`, the derived value is propagated downstream (into index arithmetic and a `Vec` builder) without being capped to any sane maximum.

### Finding Description
`bls_data_slots_from_header` computes:
```
let length = (header_val - 1) / 2;
let str_len = length.low_u64() as usize;
Ok((str_len + 31) / 32)
``` [2](#0-1) 

`header_val` comes straight from `storage_values[idx]`, a field inside `ValidatorSetProof` supplied by the relayer and **not yet checked against any Merkle/state proof** at the point it is used in `compute_all_storage_keys`: [3](#0-2) 

`str_len` can be as large as `(2^256-1)/2` truncated into `u64::MAX` via `low_u64()`. The subsequent `(str_len + 31) / 32` on a `usize` is a **plain, non-saturating addition**. On a 32-bit target (or after `low_u64()` truncation edge cases) this addition can overflow and panic in debug builds, and even in release (wrapping) it can produce a wrong, unbounded `data_slots` that is only checked afterward via `idx.saturating_add(data_slots).saturating_add(2)` against `storage_values.len()` — but that check happens *after* the value has already been computed and is only used to bound the *keys* generation, not to validate the header itself. There is no explicit maximum bound (`MAX_VALIDATORS`-style cap) applied directly to `data_slots`/`str_len`, unlike `MAX_VALIDATORS` which *is* enforced on `count` immediately after decoding it.

The USB-audio analog: `snd_usb_handle_sync_urb()` scaled an untrusted sender-supplied packet size by a stride and stored it without clamping to `ep->maxframesize`, letting the oversized value propagate into a hardware queue. Here, an untrusted relayer-supplied header value is scaled/divided into `data_slots` without a similar clamp before it propagates into key-generation and index arithmetic (`get_validator_keys`, `idx.saturating_add(data_slots)`).

### Impact Explanation
A malicious or malfunctioning relayer submitting a Pharos consensus proof can craft `storage_values` with a header field that decodes to a pathological length, triggering an arithmetic overflow panic inside `compute_all_storage_keys` before any cryptographic proof check has run. Since this runs inside the runtime's consensus-client message handling path (`pallet-ismp` / consensus client update via `handle_unsigned`), a panic here can abort or repeatedly fail block execution for the Pharos light client update path, denying consensus updates and freezing the route (messages for Pharos can no longer be delivered) — a "route unable to deliver messages" condition.

### Likelihood Explanation
Reachable from a single unsigned/relayed consensus update message; no signature or state-root check gates the header value before it is used. Exploitability depends on target word size (`usize`) and exact truncation behavior of `low_u64()`/arithmetic — on 64-bit targets a full overflow requires `str_len` near `usize::MAX`, achievable because `header_val` is fully attacker-controlled (up to `U256::MAX`).

### Recommendation
Clamp `str_len`/`data_slots` in `bls_data_slots_from_header` (and its prover-side twin `bls_data_slots_from_hex`) to a fixed maximum (e.g., a small constant like 4, matching the known 96/98-char BLS key encoding) before doing any further arithmetic, mirroring the existing `MAX_VALIDATORS` guard pattern. Use `saturating_add`/`checked_add` throughout instead of plain `+` when deriving slot counts from untrusted header bytes, and reject any header claiming an implausible string length prior to using it in `compute_all_storage_keys`.

### Proof of Concept
Construct a `ValidatorSetProof.storage_values[idx]` (the BLS header slot) equal to a big-endian 32-byte encoding of `U256::MAX` (odd, so it hits the "long string" branch). This yields `length = (U256::MAX - 1)/2` and `str_len = length.low_u64() as usize` ≈ `u64::MAX`/2 range; the subsequent `(str_len + 31) / 32` addition overflows `usize` on affected targets, panicking inside `compute_all_storage_keys`, which is invoked directly on unverified relayer input by `verify_validator_set_proof` at [4](#0-3)  before `verify_all_storage_proofs` runs.

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}
