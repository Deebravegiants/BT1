### Title
Unguarded underflow in `Bonding.canGraduate`'s USD leg permanently DoSes buys once a sell drains real-raised LT below the launch-time virtual reserve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` computes `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no underflow guard, unlike the sibling supply-leg computation in `previewLtUntilGraduation`, which was already patched against an analogous underflow (the "donation attack regression" documented in `test/Zap.t.sol`). `canGraduate` is invoked unconditionally at the end of every `Bonding.buy` via `_executeBuy`, so if `assetReserve` can ever legitimately read below the immutable `virtualLtReserve` recovered from `Pair.k() / TOTAL_SUPPLY()`, the subtraction panics and every subsequent buy for that token permanently reverts. [1](#0-0) 

### Finding Description
`canGraduate` reads the pair's live reserves and subtracts the launch-time virtual LT reserve without any `>=` check:

```
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
``` [2](#0-1) 

The same expression is reused, also unguarded, in `_prepareGraduationLiquidity`:
```
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
``` [3](#0-2) 

By contrast, `previewLtUntilGraduation`'s supply-leg calculation was explicitly hardened against an analogous underflow after a "donation attack" (a direct ERC20 token donation to the pair inflating `tokenBalance()` above the stored `reserveToken`), with a dedicated regression comment and guard:
```
// Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
if (realBalance >= reserveToken) return ltUntilThreshold;
``` [4](#0-3) 

That fix, and its regression tests, target only the **supply leg** (`realBalance` vs `reserveToken`) — the parallel underflow risk on the **USD leg** (`assetReserve` vs `virtualLtReserve`) in both `canGraduate` and `_prepareGraduationLiquidity` was not similarly hardened. The test suite documents the underflow's downstream effect explicitly:
```
// A TOKEN donation that drives `realBalance > reserveToken` previously
// underflowed `Bonding.previewLtUntilGraduation`'s supply leg,
// cascading into a `Zap.buy` DoS. Guard added; tests pin the fix.
``` [5](#0-4) 

`canGraduate` is on the hot path of every buy — the documentation states it is "checked at the end of every buy inside `_executeBuy`" — so any state that pushes `assetReserve` below `virtualLtReserve` bricks the token's curve permanently (every future `Bonding.buy` call reverts with an arithmetic Panic), which is a **freeze of trader funds on the curve and of the creator's fee stream**, matching the CVE-2019-9031 bug class of an unchecked dereference/operation on a value that can be degenerate, crashing the calling code path.

I was not able to conclusively construct, within this investigation, a concrete unprivileged sequence of `Bonding.sell`/`Router.sell` calls that drives `assetReserve` below `virtualLtReserve` given the K-invariant symmetry between `_computeBuy`/`_computeSell` — the normal buy/sell round-trip appears bounded so that `assetReserve` returns to exactly `virtualLtReserve` in the worst case, not below it. Confirming whether this is exploitable (e.g., via rounding drift across many small sell operations, or interaction with `Router.sell`'s `+1` K slack in `Pair.swap`) requires deeper numerical analysis of `Pair.swap`'s `(newTokenReserve+1)*(newAssetReserve+1) < k` check combined with repeated buy/sell cycling, which is beyond what the available code excerpts can settle with certainty.

### Impact Explanation
If reachable, this permanently freezes the bonding curve for the affected token: `Bonding.buy` (and therefore all `Zap.buy`/`Zap.buyWithPermit` calls) reverts unconditionally because `canGraduate` is called unconditionally at the end of every buy. Traders lose the ability to buy on the curve, the creator loses future fee accrual on buys, and the token can never reach graduation via the buy path (only `sell`-triggered `triggerGraduation`, itself gated on `canGraduate` succeeding, would also revert). This is a concrete, permanent freezing of trader and creator funds/flow, matching the severity bar (medium/high) requested.

### Likelihood Explanation
Likelihood is uncertain pending confirmation of an exploitable sell sequence; the K-invariant appears designed to prevent `assetReserve` from dropping below `virtualLtReserve` under normal buy/sell rounding. However, the asymmetry between the hardened supply-leg guard and the unguarded USD-leg subtraction in the same function family is a real code-quality/defense-in-depth gap that mirrors the exact CVE-2019-9031 bug class (an operation performed on a value assumed non-degenerate without checking), and the protocol's own test comments show this bug class has already bitten this exact codebase once (the supply-leg donation-attack DoS).

### Recommendation
Add the same defensive `>=` guard to the USD leg that was added to the supply leg: in both `canGraduate` and `_prepareGraduationLiquidity`, check `assetReserve >= virtualLtReserve` before subtracting, and treat `realLtRaised`/`ltFromPair` as `0` (or otherwise safely handle it) when the check fails, exactly mirroring the existing `if (realBalance >= reserveToken) return ltUntilThreshold;` pattern. Add a targeted regression test analogous to `test_donation_realBalanceExceedsReserveToken` / `test_donation_previewLtUntilGraduation_returnsThresholdLeg` that attempts to drive `assetReserve` below `virtualLtReserve` via repeated buy/sell cycles and asserts `canGraduate`/`buy` never Panics.

### Proof of Concept
A definitive PoC requires resolving the open question above (whether `assetReserve` can actually be driven below `virtualLtReserve` through legitimate `Bonding.sell` calls, given the K-invariant's `+1` slack in `Pair.swap`). I could not confirm or rule this out with certainty from the available excerpts of `Router.sol`/`Pair.sol`; a background engineer with fuzzing/foundry access should attempt a repeated buy→sell round-trip fuzz test asserting `IPair(pair).getReserves()`'s asset reserve never drops below `IPair(pair).k() / Token.TOTAL_SUPPLY()` to settle reachability before treating this as a confirmed, not just theoretical, freeze.
