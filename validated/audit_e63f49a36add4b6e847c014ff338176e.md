### Title
Pools can be created with coin/pc mints that retain a freeze authority, allowing permanent freezing of vault token accounts and locking of all pool/LP funds - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` only rejects a freeze authority on the AMM's own newly-created LP mint, but performs no check on the `freeze_authority` of the user-supplied `amm_coin_mint_info` / `amm_pc_mint_info`. Any unprivileged caller can permissionlessly create a pool (`Initialize2`) using a coin or pc mint that keeps a live freeze authority. The mint's freeze authority (which is external to and unrelated to the Raydium program) can later freeze the `amm_coin_vault` / `amm_pc_vault` SPL token accounts that hold pool liquidity, permanently blocking every `token_transfer` / `token_transfer_with_authority` CPI used by `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn(V2)` and `SwapBaseOut(V2)`.

### Finding Description
In `process_initialize2`, the program unpacks and validates the coin/pc vault token accounts and the newly created LP mint: [1](#0-0) 
It checks `lp_mint.freeze_authority.is_some()` and rejects it via `AmmError::InvalidFreezeAuthority`, but there is no equivalent check on `coin_mint` / `pc_mint` (obtained via `Self::unpack_mint`): [2](#0-1) 

Because the coin/pc mints are entirely user-supplied and unvalidated for freeze authority, a pool creator (or anyone colluding with/being the mint's freeze authority) can set up a pool where the vault token accounts are subject to an external freeze authority. Since the vault accounts (`amm_coin_vault`, `amm_pc_vault`) are SPL token accounts owned by the pool's PDA authority but whose *mint's* freeze authority is independent, the freeze authority can call `spl_token::instruction::freeze_account` on the vault at any time.

Once a vault token account is frozen, every subsequent CPI through `Invokers::token_transfer` / `Invokers::token_transfer_with_authority` (used throughout `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn`, `SwapBaseOut`, and their V2 variants) will fail at the SPL Token Program level, because SPL Token enforces `AccountState::Frozen` checks on both source and destination in `Transfer`/`Burn`/`MintTo` instructions. See the shared transfer helper: [3](#0-2) 
and its usage across swap paths: [4](#0-3) 

This is directly analogous to the referenced report: instead of an ERC20-style pausable/blacklistable token blocking `safeTransfer`/`safeTransferFrom`, here an SPL mint's freeze authority blocks the vault token account, which the Raydium program never guards against for the pool's underlying assets (only for its self-minted LP token).

### Impact Explanation
If the freeze authority of the coin or pc mint freezes the pool's vault account, all LPs' deposited liquidity in that vault becomes permanently frozen/inaccessible: `Withdraw`, `WithdrawPnl`, and both swap directions revert indefinitely, and no admin instruction exists to recover or migrate vault balances once frozen. This is a full, protocol-wide, permanent freezing of user/LP funds in the affected pool, satisfying the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
`Initialize2` is fully permissionless — any account can create a pool for any coin/pc mint pair, and the program does not require or verify that a token has no freeze authority (unlike its LP mint, which it explicitly checks). Malicious or compromised token issuers with freeze authorities are common on Solana (e.g., stablecoins, centralized tokens), and an attacker only needs to create a pool with such a token, wait for liquidity/LP funds to accumulate, then invoke `freeze_account` on the vault to lock funds — a low-cost, single-transaction attack requiring no privileged access to the AMM program itself.

### Recommendation
In `process_initialize2`, after unpacking `coin_mint` and `pc_mint`, reject mints whose `freeze_authority` is `Some(..)`, mirroring the existing check already applied to `lp_mint`:
```rust
if coin_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
if pc_mint.freeze_authority.is_some() {
    return Err(AmmError::InvalidFreezeAuthority.into());
}
```
Alternatively/additionally, maintain a mint allow/deny-list gated by config, or require that the freeze authority be renounced (set to `None`) before a pool can be created for a given mint.

### Proof of Concept
1. Attacker creates an SPL mint `M` and mints tokens to themselves, while keeping a freeze authority key under their control (default `spl-token create-token` behavior retains a mint authority; freeze authority can also be explicitly set with `--enable-freeze`).
2. Attacker calls `Initialize2` (`program/src/processor.rs::process_initialize2`) to create a Raydium pool pairing `M` with a legitimate token (e.g. USDC), depositing some initial liquidity. The program's checks in lines 742-906 do not reject `M` for having a freeze authority.
3. Other users deposit liquidity into the pool via `Deposit`, growing `amm_coin_vault`/`amm_pc_vault` balances.
4. Attacker (holding `M`'s freeze authority) submits `spl_token::instruction::freeze_account` against the pool's vault token account for `M`.
5. From this point, every `Invokers::token_transfer`/`token_transfer_with_authority` call touching that vault in `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn(V2)`, `SwapBaseOut(V2)` fails at the SPL Token Program level (frozen account), permanently locking all LP funds in the pool.
