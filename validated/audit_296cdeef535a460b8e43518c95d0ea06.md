### Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` and `topic` — the fields used to attribute a webhook event to a specific merchant tenant — come from separate, unauthenticated HTTP headers that are never included in the HMAC-signed material. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop`/`request.topic` for dispatch and tenant attribution, breaking the equality that should hold between "bytes verified by HMAC" and "bytes used to identify the tenant."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

Meanwhile `shop` and `topic` are pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic` or their `x-shopify-` variants) with no relation to the signed payload: [2](#0-1) 

`Registry.process` gates on `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

Once that check passes, `Registry.process` dispatches using `request.topic` and constructs `WebhookMetadata` using `request.shop`, both taken from the unauthenticated headers, not from anything cryptographically bound to the verified body: [4](#0-3) 

The identity binding that should hold is:
`shop-attributed-to-verified-body == shop-that-Shopify-actually-signed-the-payload-for`

Because Shopify signs webhooks with the app's single `api_secret_key`/`client_secret`, which is shared across *all* shops that installed the app (there is no per-shop key), any merchant who has installed the app can receive genuinely-signed webhook deliveries (`body` + valid `hmac-sha256`) for their own shop from Shopify. That attacker-controlled merchant can then replay the exact same `body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header for a victim shop that also installed the app. `HmacValidator.validate` still succeeds (it only checks the body against the shared secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop, while the body content actually originated from — and was only ever signed for — the attacker's own shop.

This is precisely the "bytes verified versus bytes parsed" / "a field acted on but not covered by the HMAC" analog described in the report: the swap-quantity bug swapped a fixed, unbounded field with no per-token validation; here the `shop` tenant-identity field is swapped/asserted with no coverage by the integrity check that is supposed to authenticate the whole message.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as returned by `Registry.process`/`handler.handle`) to key per-tenant data operations — e.g., updating order/customer/inventory records "for shop X" — can be made to apply attacker-controlled webhook content under a victim shop's identity. This is a cross-tenant data-confusion/corruption primitive reachable by any unprivileged party who has installed the app on at least one shop of their own (no access token, `client_secret`, or privileged account required), satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled shop to receive a genuinely-signed webhook, and (2) sending an HTTP POST to the app's public webhook endpoint with the captured body/HMAC but a forged `shop-domain` header pointing at a victim shop that also has the app installed. No secrets need to be recovered or guessed — the attacker simply reuses a signature they already legitimately possess. The webhook endpoint is, by design, a public unauthenticated endpoint that expects requests originating from Shopify's infrastructure, and the gem does nothing to bind the `shop`/`topic` claims to the signed body.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them to the body, e.g., by requiring Shopify's per-request signed headers to be covered), so `to_signable_string` used for verification covers every field that `Registry.process` subsequently trusts for tenant/topic attribution. Alternatively, cross-check the `shop` header value against an app-side webhook subscription record for the specific `webhook_id` before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`.
2. Attacker triggers an event so Shopify sends a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared `client_secret`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop that also installed the app).
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb#process` succeeds because it only checks `B` against `H` via `to_signable_string` (the raw body), which is unchanged.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` with `shop == "victim.myshopify.com"`, and the app's handler processes attacker-supplied content under the victim tenant's identity.
