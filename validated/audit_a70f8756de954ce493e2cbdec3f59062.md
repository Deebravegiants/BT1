### Title
Unbounded In-Memory Bid Cache Growth in `pallet-intents-coprocessor` RPC Enables Node DoS via Mempool Spam - (File: `modules/pallets/intents-coprocessor/rpc/src/lib.rs`)

### Summary
The `BidCache` used by the intents-coprocessor's RPC bid-watcher stores every `place_bid` extrinsic seen in the transaction pool in an unbounded `HashMap<H256, OrderBids>`, with each `OrderBids` holding an unbounded `Vec<BidEntry>`. Entries are only evicted by a time-based sweep (`remove_expired`), never by a size cap. This mirrors the `@fastify/accepts-serializer` bug class: a cache keyed by attacker-controlled input with no bound or LRU eviction, growable purely by submitting many distinct requests.

### Finding Description
`BidCache::insert` inserts a new `OrderBids` entry for every distinct `commitment` (`H256`) seen, and pushes a new `BidEntry` for every distinct `filler` under that commitment, with no maximum count enforced anywhere in the structure: [1](#0-0) 

The only cleanup mechanism is a periodic, duration-based sweep triggered on a timer tick, which removes commitments whose `first_seen` exceeds a TTL — there is no size limit, LRU, or per-source rate limit: [2](#0-1) 

The cache is populated by `run_bid_watcher`, which subscribes to the node's transaction pool `import_notification_stream()` and inserts a cache entry for every `place_bid` extrinsic that becomes "ready" in the pool — this happens *before* block inclusion, purely on entry into the mempool: [3](#0-2) 

Because the trigger is pool-readiness rather than finalized/executed state, any account able to get a signed `place_bid` extrinsic accepted into the ready queue (which only requires a validly signed extrinsic paying the base transaction fee, not funds actually escrowed on-chain) can grow the cache. An attacker can:
1. Submit many `place_bid` extrinsics with distinct random `commitment` values, each creating a new `HashMap` entry, unboundedly, between cleanup ticks.
2. Submit many `place_bid` extrinsics for the same `commitment` with distinct `filler` accounts, growing the `entries: Vec<BidEntry>` for a single `OrderBids` without bound.

Both paths let an unprivileged intent solver / bandwidth purchaser (anyone able to broadcast transactions to the node's pool) inflate the node's heap between cleanup intervals, and because the pool itself has its own capacity/eviction independent of this cache, the volume of `place_bid` transactions that can transiently occupy "ready" status before being dropped/replaced can still be large enough to be replayed into this cache repeatedly.

### Impact Explanation
This is a memory-exhaustion Denial of Service against the collator/validator node process hosting the intents-coprocessor RPC (equivalent to `CWE-770: Allocation of Resources Without Limits`, matching the reported bug class). A crashed node stops relaying and processing intents/bids, which is a route unable to deliver messages / process intents — a valid "route unable to deliver" impact per the validation criteria. The severity is bounded by needing valid signed transactions (transaction fees apply), but no economic bound scales with the number of distinct HashMap keys created, and there is no per-account or global cap on cache entries.

### Likelihood Explanation
Medium-High. No special privilege is required — any account able to submit signed `place_bid` extrinsics (a normal intent solver action) can trigger cache growth just by having transactions enter the pool's ready queue; on-chain inclusion is not required. The only cost is the transaction fee for building many superficially valid extrinsics, and the cleanup timer's interval (`cleanup_interval`, configured in `parachain/node/src/service.rs`) determines the exploitable window during which cache growth is unbounded.

### Recommendation
Bound `BidCache` explicitly:
- Cap the total number of distinct commitments tracked (e.g. LRU eviction like the upstream fastify fix, defaulting to a fixed size such as 100–1000).
- Cap the number of `BidEntry` items per `OrderBids` (e.g. reject/replace the oldest bid once a per-order limit is hit).
- Consider validating economic cost/eligibility (e.g. requiring the filler to have an on-chain escrow deposit) before admitting a bid into the in-memory cache, rather than accepting on pool-readiness alone.
- Optionally rate-limit `insert` calls per source account within the cleanup interval.

### Proof of Concept
1. Configure a node running the intents-coprocessor RPC bid watcher (`run_bid_watcher`) with its default `cleanup_interval`.
2. From an account with a minimal balance, script continuous submission of signed `place_bid(commitment, user_op)` extrinsics where `commitment` is a fresh random `H256` for each submission (never reused), at a rate the tx pool accepts into `ready`.
3. Observe `BidCache::insert` being called via `run_bid_watcher`'s `import_notification_stream()` handling for every submitted extrinsic [4](#0-3) , growing the `bids: RwLock<HashMap<H256, OrderBids>>` [5](#0-4)  without any size cap, until `remove_expired` next fires — sustained submission faster than the TTL/cleanup cadence causes continuous, unbounded RSS growth on the node.

*Note: I was unable to verify within the available index whether `place_bid`'s runtime call validation (in `modules/pallets/intents-coprocessor/src/lib.rs`) requires pre-locked escrow funds before a transaction can enter the pool as "ready," which would affect the exact economic cost per spammed entry; a Devin session with full repo access would be needed to confirm this detail precisely.*

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}
}
