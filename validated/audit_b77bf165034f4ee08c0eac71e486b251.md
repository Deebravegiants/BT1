## Title
Webhook `shop` identity is not bound by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook's `X-Shopify-Shop-Domain` header as an authenticated tenant identifier once `Utils::HmacValidator.validate` passes, but the HMAC only ever covers the raw request body — never the shop header. This breaks the equality that the gem's own documentation implies: `hmac_valid(raw_body) == true` is treated as proof that `request.shop == "the shop that actually sent this payload"`, when in fact those are two independent, unbound values.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` derive the signable content solely from `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers and are **not** part of `to_signable_string`: [3](#0-2) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC, then returns a boolean with no binding to the shop header: [4](#0-3) 

`Registry.process` uses exactly this boolean check as the sole gate before dispatching `request.shop` to the app's handler as trusted tenant data: [5](#0-4) 

The gem's own documentation instructs developers to trust `data.shop` — described as "The shop domain of the webhook" — as soon as `Registry.process` has run, explicitly stating this method "will verify the request did indeed come from Shopify": [6](#0-5) [7](#0-6) 

So the equality the gem promises is: `HMAC-valid(raw_body) ⇒ shop-domain-header is genuine`. The actual guarantee is only `HMAC-valid(raw_body) ⇒ body bytes are genuine (for *some* shop)`. Any request whose raw body and HMAC pair were legitimately produced by Shopify for one tenant will pass `HmacValidator.validate` unchanged if replayed to the same multi-tenant endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header swapped to a different tenant's domain — `Registry.process` will accept it and hand the attacker-chosen `shop` value straight to the handler.

### Impact Explanation
In a typical multi-tenant Shopify app, all installed shops' webhooks are delivered to the same registered endpoint/route, differentiated only by these headers. A handler that keys any subsequent action (data attribution, session/token lookup, cache invalidation, billing events, etc.) on `data.shop` as returned by `WebhookMetadata` can be made to act on behalf of, or attribute attacker-supplied data to, a completely different tenant — a cross-tenant access/confusion condition, since the shop identity was never actually authenticated by the HMAC that gated the request.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair that Shopify produced for the shared endpoint (e.g. from webhook delivery details/logs that Shopify's own admin surfaces to any shop owner for their legacy notification webhooks, or from any tooling/log surface that echoes raw webhook deliveries). Given such a pair — which does not require the app's `client_secret`, an access token, or TLS interception — the replay with a modified shop header is trivial and deterministic, since nothing in this gem binds shop identity to the signed bytes.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the signable content that `HmacValidator` verifies, or independently authenticate `request.shop` against a shop the app has an active session/registration for before trusting it in `WebhookMetadata`. At minimum, document that `data.shop` is not itself HMAC-protected and must be cross-checked against known installed shops before use as a tenant key.

### Proof of Concept
1. App registers webhook handler `WebhookHandler` for topic `orders/create`, using the single shared route from `docs/usage/webhooks.md` (`ShopifyAPI::Webhooks::Registry.process`).
2. Attacker obtains one legitimate `(raw_body, hmac)` pair delivered by Shopify for their own shop (e.g., via Shopify's webhook delivery/response viewer for their own store, or any log surface exposing raw deliveries).
3. Attacker POSTs the same `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's shared webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC and returns `true`.
5. `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.
