### Title
Sensitive vault request/response data exposed via INFO-level gateway message logging - (File: core/capabilities/vault/gw_handler.go)

### Summary
`GatewayHandler.HandleGatewayMessage` in the Chainlink node's Vault gateway integration logs the full inbound request and full outbound response for every vault-related message. The request is logged at `Debug` level, but the response is logged at `Info` level via `reqLggr.Infow("Sent message to gateway", "resp", response)`. This mirrors the reported Valtimo `InboxHandlingService#handle` bug class (CWE-532): an internet-facing message-handling entrypoint logs the entire message envelope at a log level that is enabled by default in production, exposing data that should not be persisted to general application logs.

### Finding Description
`HandleGatewayMessage` is the callback the Vault `GatewayHandler` registers with the gateway connector to process every JSON-RPC message routed from the public-facing Gateway HTTP endpoint (`vaulttypes.Methods`: `secrets.create`, `secrets.update`, `secrets.delete`, `secrets.list`, `publicKey.get`). [1](#0-0) 

After dispatching to the method-specific handler and sending the response back to the gateway, the full `response` object (a `*jsonrpc.Response[json.RawMessage]`, i.e. the raw wire result for the request) is logged unconditionally at `Info` level: [2](#0-1) 

The default node log level is `info`, as documented in the core config docs, meaning this line is active in production deployments without any special debug configuration. [3](#0-2) 

For `secrets.list`, the result payload is the identifiers/metadata of a user's stored secrets (owner, namespace, secret IDs) built by `handleSecretsList`, which is exactly the kind of per-user confidential inventory data that should not be dumped into general logs. [4](#0-3) 
For `secrets.create`/`secrets.update`, the response is derived from `vaultCapResponse.ToJSONRPCResult()`, and the corresponding request handlers already separately log `vaultCapRequest.String()`/`r.String()` at `Debug` — showing the codebase treats these payloads as sensitive enough to require caution, yet the aggregate response is still logged unconditionally at `Info`. [5](#0-4) 

Notably, the project has an established, security-conscious pattern of stripping such payloads from logs elsewhere in the same gateway subsystem — e.g. the Vault JSON-RPC handler explicitly excludes raw request `params` from error logs with a dedicated regression test (`TestVaultHandler_InvalidParamsDoesNotLogRawParams`) verifying no log line contains raw request content. [6](#0-5) 
`gw_handler.go`'s `Infow("Sent message to gateway", "resp", response)` does not follow this pattern and is the analog of the reported `logger.info("Received message: {}", message)` bug: an entrypoint reachable end-to-end from an unprivileged client request, logging the full message body at a log level enabled by default.

### Impact Explanation
Any operator or process with read access to node logs (log files, log aggregation systems, or any admin-facing log viewer in the node's UI/monitoring stack) can observe the full content of every vault response sent back through the gateway — including which secret identifiers/namespaces/owners exist for `secrets.list` responses — without needing the workflow-owner-scoped Vault credentials that are otherwise required to query the Vault capability directly. This is a confidentiality/data-exposure issue (CWE-532), matching the CVSS vector of the reported issue: no privileges required for the exposure's downstream reach (an unprivileged client's request content ends up logged), high confidentiality impact, no integrity/availability impact.

### Likelihood Explanation
The log statement executes on every successful vault gateway request/response cycle (`secrets.create`, `secrets.update`, `secrets.delete`, `secrets.list`, `publicKey.get`), and does so at `Info`, the node's default log level, so no special configuration is needed to trigger the exposure — it happens continuously in normal production operation whenever an unprivileged client interacts with the Vault gateway endpoint.

### Recommendation
- Downgrade `reqLggr.Infow("Sent message to gateway", "resp", response)` to `Debug` (matching the request-side log line at line 182) so it is not emitted by default in production.
- Avoid logging the full `response`/`req` objects; instead log only non-sensitive correlation fields already available via `requestLogger` (`requestID`, `method`, `gatewayID`) plus a boolean success indicator or error code.
- Add a regression test analogous to `TestVaultHandler_InvalidParamsDoesNotLogRawParams` asserting that no `Info`-level (or higher) log line from `HandleGatewayMessage` contains secret identifiers, owners, or raw result payloads.

### Proof of Concept
1. Configure a node with default log level (`info`, the documented default).
2. As an unprivileged (but allow-listed) workflow client, send a `secrets.list` JSON-RPC request through the public Gateway HTTP endpoint that reaches `GatewayHandler.HandleGatewayMessage`.
3. Observe the node's application logs: the line `"Sent message to gateway"` is emitted at `Info` level with a `resp` field containing the full JSON-RPC response, including the secret identifiers/owner/namespace metadata returned by `handleSecretsList`.
4. Anyone with read access to these logs (log files, centralized logging, or a log-viewing admin panel) can harvest this data without needing direct Vault access.

func (h *GatewayHandler) handleSecretsCreate(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) *jsonrpc.Response[json.RawMessage] {
	vaultCapRequest := vaultcommon.CreateSecretsRequest{}
	if err := json.Unmarshal(*req.Params, &vaultCapRequest); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}

	h.lggr.Debugw("Processing authorized create secrets request", "request", vaultCapRequest.String())
	vaultCapResponse, err := h.secretsService.CreateSecrets(ctx, &vaultCapRequest)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.FatalError, err)
	}

	jsonResponse, err := toJSONResponse(vaultCapResponse, req.Method)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}
	return jsonResponse
}

func (h *GatewayHandler) handleSecretsList(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage], authResult *AuthResult) *jsonrpc.Response[json.RawMessage] {
	r := &vaultcommon.ListSecretIdentifiersRequest{}
	if err := json.Unmarshal(*req.Params, r); err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, err)
	}
	r.Owner = authResult.AuthorizedOwner()

	h.lggr.Debugw("Processing authorized list secrets request", "request", r.String())
	resp, err := h.secretsService.ListSecretIdentifiers(ctx, r)
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.HandlerError, fmt.Errorf("failed to list secret identifiers: %w", err))
	}

	resultBytes, err := resp.ToJSONRPCResult()
	if err != nil {
		return h.errorResponse(ctx, gatewayID, req, api.NodeReponseEncodingError, err)
	}

	return &jsonrpc.Response[json.RawMessage]{
		Version: jsonrpc.JsonRpcVersion,
		ID:      req.ID,
		Method:  req.Method,
		Result:  (*json.RawMessage)(&resultBytes),
	}
}

func TestVaultHandler_InvalidParamsDoesNotLogRawParams(t *testing.T) {
	t.Parallel()

	// Observed at Info level so the pre-existing whole-request Debug log is excluded.
	lggr, logs := logger.TestObserved(t, zapcore.InfoLevel)
	h, callback, don, _ := setupHandlerWithLogger(t, lggr, limits.Factory{Settings: cresettings.DefaultGetter})
	// Don't expect SendToNode to be called for invalid params
	don.AssertNotCalled(t, "SendToNode")

	const marker = "SENSITIVE_MARKER_123"
	invalidParams := json.RawMessage(`{"request_id":"req-1","injected":"` + marker + `"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "invalid-params-logs",
		Method: vaulttypes.MethodSecretsCreate,
		Params: &invalidParams,
	}

	// The invalid-params response is sent synchronously, so no goroutine is needed.
	err := h.HandleJSONRPCUserMessage(t.Context(), req, callback)
	require.NoError(t, err)

	resp, err := callback.Wait(t.Context())
	require.NoError(t, err)
	var secretsResponse jsonrpc.Response[vaultcommon.CreateSecretsResponse]
	require.NoError(t, json.Unmarshal(resp.RawResponse, &secretsResponse))
	assert.Equal(t, req.ID, secretsResponse.ID, "Request ID should match")
	assert.Equal(t, api.ToJSONRPCErrorCode(api.InvalidParamsError), secretsResponse.Error.Code, "Error code should match")

	invalidParamsLogs := logs.FilterMessage("invalid params")
	entries := invalidParamsLogs.All()
	require.Len(t, entries, 1, "expected exactly one 'invalid params' log entry")
	assert.Equal(t, zapcore.ErrorLevel, entries[0].Level)
	assert.Equal(t, req.ID, entries[0].ContextMap()["requestID"])
	assert.NotContains(t, entries[0].ContextMap(), "params", "raw params must not be logged")

	for _, e := range logs.All() {
		assert.NotContains(t, e.Message, marker)
		for k, v := range e.ContextMap() {
			if s, ok := v.(string); ok {
				assert.NotContains(t, s, marker, "log field %q must not contain raw request params", k)
			}
		}
	}
}
