This confirms the vulnerability. `HmacValidator.validate` computes the HMAC solely over `to_signable_string`, which for `Webhooks::Request` returns only `@raw_body` [1](#0-0) . The `shop` accessor reads the unsigned `x-shopify-shop-domain`/`shopify-shop-domain` header independently of the HMAC computation [2](#0-1) . `Registry.process` validates HMAC over the body only, then passes `request.shop` straight into the handler for tenant routing without re-verifying it's bound to the signed content [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#shop` reads `x-shopify-shop-domain` directly from headers, which are entirely excluded from the HMAC signature computed over `to_signable_string` (i.e., `@raw_body` only). An attacker who owns/controls shop A can capture a validly-signed webhook body+HMAC delivered to their own endpoint and replay it to the host app's webhook endpoint with the shop-domain header rewritten to victim shop B, causing `ShopifyAPI::Webhooks::Registry.process` to pass a validly-verified HMAC alongside an attacker-controlled, unverified shop value to the handler.

### Finding Description
The binding the code implicitly relies on is: `shop bytes verified by HMAC == shop value delivered to handler`. In reality: HMAC verifies `hmac == HMAC(secret, raw_body)` via `HmacValidator.validate_signature` calling `compute_signature(verifiable_query.to_signable_string, secret)` [4](#0-3) , and `to_signable_string` returns only `@raw_body`, never any header [5](#0-4) . Meanwhile `shop` is read straight from the `x-shopify-shop-domain` header with no cryptographic binding to the body or HMAC [2](#0-1) . `Registry.process` checks `HmacValidator.validate(request)` and then constructs `WebhookMetadata` using `request.shop` for the handler, trusting it for tenant routing [3](#0-2) .

Exploit flow: attacker owns shop A, installs the app, receives a real webhook (body B, valid HMAC H for body B signed with the app's real `api_secret_key`). Attacker replays a POST to the host app's webhook route with `raw_body = B`, `x-shopify-hmac-sha256 = H` (unchanged, still valid because it only covers the body), and `x-shopify-shop-domain` rewritten to `shop-b.myshopify.com`. `HmacValidator.validate` returns `true` because the body and HMAC are unchanged and still match. `Registry.process` finds a handler and calls it with `shop: "shop-b.myshopify.com"`, `topic`, and `parsed_body` — all attributed to victim shop B even though nothing about the request was ever signed by or for shop B.

None of the existing guards catch this: `HmacValidator.validate` only checks the body/HMAC pair (which is unaffected by header tampering), and there is no `ShopValidator.sanitize!` or comparison between `shop` and any signed value anywhere in `Registry.process` or `Request`. Sorbet's `sig` only enforces the header value is a `String`, not that it's cryptographically bound.

### Impact Explanation
The host app's webhook handler(s) will process attacker-supplied body content while believing it originates from — and is scoped to — victim shop B. Depending on the handler's use (e.g. updating shop-specific database rows, triggering data sync, calling GDPR mandatory webhooks like `customers/redact`/`shop/redact` with attacker-chosen `shop` values), this leads to cross-tenant data corruption/processing under a victim's identity. This matches the Critical category: cross-tenant access via a forged/replayed webhook accepted as authentic for the wrong tenant. The attack is trivially repeatable against any known/guessable victim shop domain, since Shopify shop domains (`*.myshopify.com`) are often predictable or discoverable.

### Likelihood Explanation
Preconditions: the attacker only needs their own development/trial shop with the app installed (a standard, permission-free action any internet user can perform), and knowledge of the victim's `.myshopify.com` domain (publicly discoverable via the storefront). No app secret, access token, or elevated privilege is required. The cost is a single webhook receipt plus a replayed HTTP POST with one header changed — no cryptographic work needed, since the HMAC remains valid because the header isn't covered by it. This is fully repeatable against arbitrary victim shops using the same or freshly triggered webhook bodies (e.g., re-triggering benign events like `orders/create` in the attacker's own store to get new valid signed bodies), as long as the host app's handler logic doesn't independently re-verify shop identity against something else (which the base gem gives it no tool to do, since `shop` is the only shop signal exposed).

### Recommendation
Bind the shop domain to the signed payload before trusting it, e.g., by validating that `request.shop` matches an expected/known shop (such as one with an active session or an installed webhook subscription for that specific topic+shop) before invoking the handler, or by including relevant headers into `to_signable_string`/a separate signed digest so header tampering breaks the HMAC. At minimum, `Registry.process` should not simply trust `request.shop` as authenticated tenant context — the gem should document/enforce that host apps must independently verify shop-topic webhook registration existence before acting, since the raw HMAC only proves body integrity, not header integrity.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (illustrative addition)
def test_process_trusts_unsigned_shop_domain_header_cross_tenant
  body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

  # Attacker captures a valid signature for shop A's webhook body
  headers_shop_a = {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),
    "x-shopify-shop-domain" => "shop-a.myshopify.com",
  }
  request_a = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_shop_a)
  assert(ShopifyAPI::Utils::HmacValidator.validate(request_a))
  assert_equal("shop-a.myshopify.com", request_a.shop)

  # Attacker replays same body+hmac but rewrites shop-domain header to victim shop B
  headers_shop_b = headers_shop_a.merge("x-shopify-shop-domain" => "shop-b.myshopify.com")
  request_b = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers_shop_b)

  # HMAC still validates because it only covers raw_body, never the shop header
  assert(ShopifyAPI::Utils::HmacValidator.validate(request_b))
  # But shop resolves to the victim, unverified
  assert_equal("shop-b.myshopify.com", request_b.shop)

  handled_shop = nil
  handler = TestHelpers::FakeWebhookHandler.new(->(data) { handled_shop = data.shop })
  ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", path: "path", delivery_method: :http, handler: handler)

  ShopifyAPI::Webhooks::Registry.process(request_b)
  assert_equal("shop-b.myshopify.com", handled_shop) # handler acted on victim's identity from an unsigned header
end
```
