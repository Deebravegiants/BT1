## Title
Webhook Shop Identity Not Covered by HMAC — Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by validating an HMAC computed **only over the raw request body**, yet the `shop` (tenant) identity handed to the application's webhook handler is read from an **unauthenticated HTTP header** (`x-shopify-shop-domain`/`shopify-shop-domain`) that is never included in the signed material. This is the same class of bug as the reported finding: a security-critical identity value (the delegatee token in Golom, here the "shop" tenant) is trusted from a source disjoint from what was actually integrity-checked (the delegator's checkpoint array vs. the token itself, here the raw body vs. the shop header).

### Finding Description
`HmacValidator.validate` computes the HMAC solely from `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `Request#shop` — the value that identifies *which merchant/tenant* the webhook is for — is pulled straight from the `shopify-shop-domain` header, which is completely outside the HMAC's signed scope: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards `request.shop` (the unauthenticated header) directly to the application handler as the tenant identity, with no additional binding check: [4](#0-3) 

The equality the code implicitly assumes is:

`shop_used_by_handler (WebhookMetadata#shop, from header)` == `shop_that_the_HMAC_actually_authenticates (none — HMAC only covers @raw_body)`

Since a single `api_secret_key` is shared by the app across **all shops that installed it**, any shop that has the app installed can receive a legitimately-signed webhook from Shopify (valid raw body + valid HMAC for that body). An attacker who controls such a shop can capture one authentic `(raw_body, hmac)` pair delivered to their own endpoint, then replay that exact pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspected the shop header, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the attacker-chosen (victim) domain, alongside the attacker-controlled body content.

### Impact Explanation
This breaks the tenant identity binding: an app's webhook handler will act on data under a shop identity that was never verified. Depending on how the handler uses `WebhookMetadata#shop` (e.g., looking up/activating a session for that shop, writing data keyed by shop, or triggering shop-specific side effects), an attacker with a legitimate install of the app on their own store can inject webhook events attributed to an arbitrary victim shop — a cross-tenant access/data-integrity issue. This maps to the "Critical - cross-tenant access" category in scope.

### Likelihood Explanation
Requires only an unprivileged attacker who can install the target app on a shop they control (a normal, non-privileged action for any Shopify merchant/developer) and can send raw HTTP requests to the app's public webhook endpoint. No access token, `api_secret_key`, or privileged credential is needed — only observation of one legitimately delivered webhook to their own shop and the ability to replay it with a modified header, both trivially available to any internet user who owns a shop.

### Recommendation
Bind the `shop` value into the signed material, or otherwise cryptographically tie it to the verified payload, e.g.:
- Include the `shop` (and ideally `topic`/`webhook-id`) in `to_signable_string` so the HMAC covers them, or
- After HMAC validation, independently confirm `request.shop` against a value already trusted for a matching, currently-active session/installation before dispatching to the handler, rather than trusting the header verbatim.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app's endpoint:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   body: {"id":1,...}
   ```
3. Attacker replays the identical `body` and `x-shopify-hmac-sha256` value to the same endpoint, but changes:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks the raw body against the HMAC — see `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the webhook was never actually authenticated as belonging to `victim-shop.myshopify.com`.
