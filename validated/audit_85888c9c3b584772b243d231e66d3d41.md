The claim is confirmed by direct code inspection: `record_native_deposit` creates a distinct `NativeDepositOf[to][from]` row per unique payer with no cap on the number of distinct payers <cite repo="AYontt/polkadot-sdk--030" path="substrate/frame/revive/src/deposit_payment.rs" start="556="562" /> [1](#0-0) , and `process_deletion_queue_batch`'s Phase 1 `break` on `result.maybe_cursor.is_some()` exits the entire outer `loop` rather than skipping to the next queue entry [2](#0-1) . Since `queue.next()` always returns the same un-advanced head entry until `entry.remove()` is called (which only happens after Phase 2 fully succeeds) [3](#0-2) [4](#0-3) , an attacker-inflated `NativeDepositOf` backlog on the head-of-queue contract does stall processing of every subsequent queued entry, exactly as described.

Audit Report

## Title
Head-of-queue contract with inflated `NativeDepositOf` row count can indefinitely stall the entire lazy `DeletionQueue`, blocking trie reclamation for itself and every other queued contract - ([File: substrate/frame/revive/src/storage.rs])

## Summary
`ContractInfo::process_deletion_queue_batch` processes the `DeletionQueue` strictly FIFO via `DeletionQueueManager::next()`, which always returns the same head entry until it is fully removed. An attacker can cheaply and unboundedly inflate a single contract's distinct-payer count in `NativeDepositOf` by having many distinct accounts trigger native-fallback storage-deposit charges against it, then queue that contract for deletion. Because Phase 1's `clear_prefix` incompletion triggers an unconditional `break` out of the entire outer loop (not just a `continue` to the next entry), this head-of-queue entry stalls reclamation of its own trie and of every other contract queued behind it, for as many blocks as needed to drain the attacker-inflated backlog.

## Finding Description
`process_deletion_queue_batch` fetches the head of the queue via `queue.next()`, which reads the entry at `delete_counter` without advancing it [3](#0-2) . The counter only advances in `DeletionQueueEntry::remove()` [5](#0-4) , which is only called after Phase 2's `child::kill_storage` reports `AllRemoved` [4](#0-3) , which is itself only attempted after Phase 1's `NativeDepositOf::clear_prefix` reports no remaining cursor [6](#0-5) .

Critically, when Phase 1 does not finish within the block's weight budget (`result.maybe_cursor.is_some()`), the code executes `break`, which exits the entire outer `loop { ... }` meant to iterate over multiple queue entries per call [2](#0-1) . This means no other queue entries are processed in that call at all once the head entry's Phase 1 can't finish.

`NativeDepositOf[to][from]` rows are created via `record_native_deposit`, invoked whenever a storage-deposit charge falls back to the native currency because the payer lacks sufficient PGAS [1](#0-0) [7](#0-6) . There is no cap on the number of distinct payers per contract in this path. An attacker can fund many distinct accounts (each without PGAS), have each make one contract call triggering a native-fallback charge, then terminate the contract via `queue_for_deletion`, which appends a `DeletionQueueItem` to the tail of the FIFO queue [8](#0-7) .

The benchmark `deletion_queue_per_native_deposit_key` confirms the row-count scaling assumption up to `k=1024`, and shows the mechanism is measured/understood but not bounded against an unbounded attacker-controlled backlog beyond a single block's budget [9](#0-8) .

## Impact Explanation
This is a genuine denial-of-service against the lazy trie-reclamation pipeline for pallet-revive. As long as the attacker's inflated head-of-queue entry hasn't finished draining `NativeDepositOf` rows, no other terminated contract's child trie behind it in the FIFO queue is touched, regardless of how small or otherwise ready those entries are. This causes state/PoV bloat to persist chain-wide for a duration proportional to the attacker's chosen backlog size, which they can grow arbitrarily across multiple blocks before triggering termination.

## Likelihood Explanation
The exploit path requires only ordinary signed extrinsics — funding sybil accounts and having them make contract calls, then triggering contract self-destruct. No privileged origin or special conditions are needed. Cost scales roughly linearly with the number of distinct payer rows the attacker wants to create, which is entirely attacker-controlled and can be grown far beyond what benchmarks assume for a single block, directly translating to a proportionally longer chain-wide stall.

## Recommendation
Change `process_deletion_queue_batch` so that an entry whose Phase 1 or Phase 2 cannot fully finish within the current block's budget does not block subsequent, independent queue entries in the same or later calls — e.g., `continue` to the next entry instead of `break`-ing the whole loop, or otherwise decouple per-entry phase completion from the outer loop's control flow while still bounding total per-block weight consumption.

## Proof of Concept
1. Instantiate contract A with a small trie and terminate it, queuing it as `DeletionQueueItem` #0.
2. Instantiate contract B; have 200+ distinct signed accounts each perform one native-fallback storage-growing call to B, populating 200+ `NativeDepositOf[B][*]` rows via `record_native_deposit`; terminate B, queuing it as `DeletionQueueItem` #1.
3. Reorder queuing so B (bloated `NativeDepositOf`, small trie) is queued *before* A. Repeatedly call `ContractInfo::process_deletion_queue_batch` with a fixed small `WeightMeter` limit across multiple simulated blocks.
4. Observe that A's `DeletionQueueItem` remains in `DeletionQueue::<Test>` and A's trie keys remain readable via `child::get`, with A's reclamation blocked, for a number of blocks proportional to B's `NativeDepositOf` row count — despite A's own trie being trivially small and unrelated to B's backlog.
