### Title
Fraud detection is unconditionally disabled, forcing every signup to bypass fraud checks - (File: src/plans/mod.rs)

### Summary
`detect_fraud` in `src/plans/mod.rs` is stubbed to always return `Ok(false)` whenever a biometric pipeline is present, regardless of any fraud signals (face identifier fraud checks, occlusion errors, iris/liveness anomalies) contained in that pipeline. This means the fraud-verdict invariant is fail-open rather than fail-closed: any signup that reaches the pipeline stage is unconditionally treated as non-fraudulent.

### Finding Description
`detect_fraud` takes an `Option<&biometric_pipeline::Pipeline>` and, after confirming `pipeline.is_some()`, drops the reference (`let Some(_pipeline) = pipeline else { return Ok(false) }`) and never inspects any field of the pipeline (`face_identifier_fraud_checks`, `occlusion`, iris code data, etc.) before returning `Ok(false)` [1](#0-0) . The comment `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` confirms this is intentional removal rather than a bug in gating logic [2](#0-1) .

Upstream, the pipeline is built from the attacker-controlled capture (biometric_pipeline stage) and already carries fraud-relevant signals such as `face_identifier_fraud_checks` and `occlusion`, which are recorded into the debug report but not consulted by `detect_fraud` [3](#0-2) . Because `detect_fraud`'s boolean return is the sole in-orb decision point feeding into `SignupReason` used by `enroll_user` (`enroll_user::Plan { ..., signup_reason }`), any pipeline output — including one with adversarial/duplicate/poor-liveness signals — is deterministically classified as non-fraud [4](#0-3) .

### Impact Explanation
Because the on-device fraud gate always reports "not fraud," full-quality biometric packages (iris codes/shares, mask codes, face identifier bundle/thumbnail, normalized iris images) proceed through enrollment and are packaged/uploaded via `enroll_user::Plan` for every signup, including signups that should have been blocked for spoofing, poor liveness, or duplicate-identity fraud signals. This causes biometric data that should never leave the device to be exfiltrated to the backend-designated upload key, and it also means any local, on-orb fraud-based blocking is defeated for an otherwise unprivileged attacker who simply completes a normal signup flow with adversarial input. This matches a biometric-data-disclosure / fraud-bypass impact class.

### Likelihood Explanation
Preconditions are minimal and match normal attacker capability: an unprivileged participant runs an ordinary signup session, `pipeline.is_some()` after any successful biometric pipeline run (which happens whenever biometric capture and pipeline computation complete, independent of the quality/fraud content of the biometric input). No operator privileges, key leakage, or MCU tampering are required — the vulnerable code path is reached on every completed pipeline in the current build, making this fully deterministic and repeatable on every signup attempt.

### Recommendation
Restore real fraud-check evaluation in `detect_fraud`: inspect `pipeline.face_identifier_fraud_checks`, `pipeline.occlusion`, and other pipeline-level fraud/liveness signals, and return `true` (fraud) when any of them indicate a fraud condition rather than unconditionally returning `Ok(false)`. Ensure the function fails closed (treats unknown/error states as fraud) rather than defaulting to "not fraud."

### Proof of Concept
Unit test plan in `src/plans/mod.rs` test module:
1. Construct a `biometric_pipeline::Pipeline` (or minimal mock via existing test helpers) with `face_identifier_fraud_checks` set to `Err(...)` or an adversarial/duplicate-identity result, and/or `occlusion` set to an error indicating spoofing/poor liveness.
2. Call `Plan::detect_fraud(&mut plan, &mut orb, &mut debug_report, Some(&pipeline))`.
3. Assert the function returns `Ok(true)` (fraud detected).
4. Current code returns `Ok(false)` unconditionally, so this assertion fails, proving the fail-open behavior — confirming that no adversarial pipeline content can ever trigger a fraud classification in the current build.
