## Custody Analog Found: Frozen-CoinStore Bidder Bricks Marketplace Auction Escrow

### Title
Auction bid refund to a frozen `CoinStore` permanently locks the NFT/token object in escrow - ([File: aptos-move/move-examples/marketplace/sources/coin_listing.move])

### Summary
`coin_listing::bid<CoinType>` [1](#0-0)  refunds the previous highest bidder via `aptos_account::deposit_coins(bidder, coins)` before accepting a new bid. `aptos_framework::coin` supports a `FreezeCapability` that lets a coin issuer freeze an individual account's `CoinStore`, after which deposits into that store abort. If the current highest bidder's `CoinStore` for `CoinType` is frozen after placing a bid (analogous to a blacklisted USDC holder in the external report), every subsequent call to `bid` reverts while trying to refund that frozen bidder, permanently DoS-ing the auction. Because the listed token object is held in escrow by the `Listing`/`AuctionListing` resources until `complete_auction` or a fresh bid succeeds, and `complete_auction` itself is unaffected only when the frozen party isn't the final `current_bid` holder, the escrowed asset and the frozen bidder's locked coins can become permanently stuck if the frozen bidder remains the top bidder at auction end or if no one can out-bid them going forward.

### Finding Description
The generic `CoinType` marketplace auction in `coin_listing.move` is explicitly designed to support arbitrary Aptos `Coin` types [2](#0-1) . `aptos_framework::coin` provides `FreezeCapability` and store-freezing so an unprivileged bidder's account can be frozen by the coin issuer (e.g., a compliance/blacklist-capable stablecoin), independent of the marketplace module's own authorization.

In `bid<CoinType>`, when a new bid is placed, the previous bid is unconditionally refunded:
```
let Bid { bidder, coins } = option::extract(&mut auction_listing.current_bid);
let current_bid = coin::value(&coins);
aptos_account::deposit_coins(bidder, coins);
``` [3](#0-2) 

`aptos_account::deposit_coins` unconditionally attempts a deposit into the recipient's `CoinStore` [4](#0-3) , and `coin::deposit`/`merge_coin` will abort if that store is frozen. There is no try-catch or fallback escrow path — the same pattern flagged as the root cause in the external BendDAO finding (unconditional outbound transfer to a potentially blacklisted/frozen party blocking all further state transitions on a shared auction).

This break propagates: since the previous bid's coins live inside the `AuctionListing<CoinType>` object's `Bid` struct [5](#0-4) , and the listed token itself is custody-held by the `Listing` object until purchase/auction completion, a revert in `bid()` blocks:
1. Any new bidder from placing a bid (transaction always reverts at the refund step).
2. Effectively freezing the auction state — the underlying token object remains escrowed and non-transferable via this flow, and the frozen bidder's locked coin balance inside `Bid` is also stuck (no `try-catch`/rescue path exists in this module).

### Impact Explanation
This satisfies the custody impact gate as a "permanent lock of object-held value": the NFT/token object held in escrow by `Listing`, and the coins locked inside `AuctionListing.current_bid`, become non-recoverable through the normal auction lifecycle once the current bidder's `CoinType` store is frozen by the coin issuer. Neither `bid` nor `complete_auction` provides any way to eject or write off a stuck refund — `complete_auction` only pays the seller/fee/royalty out of the *winning* bid, it does not rescue a stuck escrowed refund from a still-open auction that can no longer accept new bids. This is a genuine, high-impact custody/DoS issue for any marketplace instance built on `CoinType`s that support freezing (this is an example/reference module, but it is part of the framework's `move-examples` and demonstrates the pattern that would recur in any production deployment following it).

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any `Coin<T>` with a `FreezeCapability` in circulation (a standard, supported Aptos coin feature, not a hypothetical) can be used as the auction `CoinType`. The attack requires only that the coin issuer (or a compromised/malicious freeze-capability holder) freezes the current top bidder's store — no cooperation or special privilege within the marketplace module is needed by the bidder or attacker beyond normal bidding.

### Recommendation
- Do not perform outbound refund transfers synchronously inside `bid()`. Instead, credit the outbid party's refund to a per-auction pull-based claim/escrow balance that they withdraw later, decoupling bid acceptance from refund transfer success.
- Alternatively, wrap the refund transfer so failure does not abort the whole transaction (Move lacks native try/catch for aborts across the VM boundary the way EVM does, so this generally means restructuring to a claimable-balance pattern rather than a push transfer, since the recommended EVM try-catch mitigation is not directly available in Move).
- Ensure `complete_auction` and any auction-cancellation path can independently release the underlying token object to the seller/winner even if a legacy bid’s coin refund cannot be completed, so the escrowed object is never contingent on a successful arbitrary-party payout.

### Proof of Concept
1. Deploy or use an existing `Coin<T>` with `FreezeCapability` (standard Aptos coin feature).
2. Seller lists a token via `coin_listing::init_auction<T>`.
3. Bidder A calls `bid<T>(A, listing, 100)` — succeeds, `A`'s coins now held in `AuctionListing.current_bid`.
4. Coin issuer freezes `A`'s `CoinStore<T>` (e.g., compliance action) via the coin's freeze capability.
5. Bidder B calls `bid<T>(B, listing, 150)`. Execution reaches `aptos_account::deposit_coins(A, coins)` at [6](#0-5) , which aborts because `A`'s store is frozen.
6. The entire `bid` transaction reverts; no further bids can be placed on this auction, and the listed token object plus `A`'s locked coins remain stuck in escrow indefinitely.

Note: I was not able to fully verify within the available context whether `coin::deposit`'s abort behavior on a frozen store is unconditional in all code paths (e.g., whether `merge_coin`/direct-deposit variants check frozen status identically); confirming this exact abort condition in `coin.move`'s `deposit`/`merge_coin` functions would require reading that file directly (a Devin session with full file access is recommended to confirm the precise abort code and any exceptions).
