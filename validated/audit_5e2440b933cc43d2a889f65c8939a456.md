Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are trusted for tenant/topic identity but are not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` and forwarded to the app's `WebhookHandler` are read directly from unauthenticated HTTP headers. This breaks the intended binding `hmac-verified bytes == bytes the app trusts for tenant identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: ` [1](#0-0) `. The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from the (attacker-controlled, unauthenticated) HTTP headers via `shopify_header`: ` [2](#0-1) ` and ` [3](#0-2) `.

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `verifiable_query.to_signable_string` (i.e., the raw body) against the computed HMAC: ` [4](#0-3) `. It then looks up the handler by `request.topic` and constructs `WebhookMetadata` using `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` — none of which were part of the signed material — and passes this trusted-looking metadata to the app's handler code, which typically uses `shop` to select the tenant record to mutate (per this gem's documented usage in `docs/usage/webhooks.md`, and mirrored in the tests at `test/webhooks/registry_test.rb:270-302`).

Because the signature only binds `@raw_body`, any request whose body+HMAC pair is valid for the app's secret (which happens on every legitimate Shopify webhook delivery) can have its `shop-domain`, `topic`, `webhook-id`, and `api-version` headers swapped by an attacker sitting in front of the app (e.g., a malicious/compromised intermediate proxy, a merchant-controlled forwarding endpoint, or any actor capable of replaying a captured webhook body with modified headers to the app's public webhook endpoint) without invalidating `Utils::HmacValidator.validate(request)`. The gem provides no mechanism to bind the header claims to the signed payload, so `hmac-verified bytes` (`raw_body` only) ≠ `bytes the app treats as authoritative for tenant/topic`.

### Impact Explanation
This qualifies as cross-tenant access: an attacker who can deliver an HTTP POST to the app's public webhook endpoint (no credentials required — this is exactly the unprivileged shape of a webhook endpoint) can present a body/HMAC pair valid under the app's `api_secret_key` (for example, a body that was legitimately signed for their own shop, or any body an attacker manages to obtain with a valid signature) together with a forged `shop-domain` header naming a different shop, or a forged `topic` header selecting a different handler/topic than the one the body was actually generated for. Since `WebhookMetadata.shop`/`topic` are trusted downstream without cross-checking them against the signed content, the app can be tricked into processing data for the wrong shop (cross-tenant data confusion) or into invoking a handler for a topic the payload was never intended for.

### Likelihood Explanation
Medium/High: exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair signed by the target app's secret — which is trivial for any merchant that has installed the app (they legitimately receive their own signed webhooks) — and then to POST that body with substituted `shopify-shop-domain`/`shopify-topic`/`shopify-webhook-id`/`shopify-api-version` headers to the app's public webhook endpoint. No access token, no `client_secret`, and no privileged account is needed beyond being a normal installed merchant or an intermediary capable of delivering HTTP requests to the endpoint.

### Recommendation
Include `shop-domain`, `topic`, `webhook-id`, and `api-version` in the HMAC-signed material (or otherwise cryptographically bind them to the body), and have `Utils::HmacValidator.validate` verify the full bound string rather than only `@raw_body`. At minimum, `Registry.process` should refuse to trust `request.shop`/`request.topic` unless they are proven to originate from the same signed request context as the body.

### Proof of Concept
1. App receives a legitimate webhook for shop `attacker-shop.myshopify.com` with topic `orders/create`, headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker (who owns `attacker-shop.myshopify.com` and can legitimately trigger this webhook, e.g., by creating an order) captures `raw_body` and its valid `hmac`.
3. Attacker replays the same `raw_body` and `hmac` to the app's public webhook endpoint, but with `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: customers/redact`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) still returns `true` because it only checks the unchanged `raw_body` against the unchanged `hmac`.
5. `Registry.process` dispatches to the handler registered for the (forged) topic and passes `WebhookMetadata` with the forged `shop`, letting the app process/act on data as if it came from `victim-shop.myshopify.com` or from a different (e.g. mandatory GDPR) topic, at the app developer's trust boundary.
