### Title
Swap Output Slippage Floor Committed in the Proof Is Never Enforced, Allowing Unauthorised Value Loss on Swaps - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap()` requires that a slippage floor (`circomData.slippageValues[1]`) be non-zero, but the actual output amount returned from the router call (`swappedAmount`) is never compared against that floor before being distributed to the relay and the user's shielded balance.

### Finding Description
`swap()` pulls `circomData.slippageValues[1]` from the proof-committed `CircomData` and only checks that it is non-zero: [1](#0-0) 

It then calls `callRouter()` with attacker/relayer-supplied `externalActionMetadata` bytes, which are forwarded verbatim to an external `router` after granting the router an (effectively permanent, since `approveUnlimited` only re-approves when the allowance drops below half of `type(uint256).max`) unlimited allowance on `inputToken`: [2](#0-1) [3](#0-2) 

The resulting `swappedAmount` (computed purely from the pre/post balance diff of `outputToken`) is used directly to compute fees and the amount credited to the user's new shielded UTXO, with no assertion that `swappedAmount >= circomData.slippageValues[1]`: [4](#0-3) 

Because the circuit/public-input side only commits to the floor value being non-zero (via the `calldataHash`/public-input vector presumably including `slippageValues`), while the on-chain code never enforces `swappedAmount` against it, the slippage-floor field is effectively acted upon (it gates progress) but not used to bound the actual value moved — breaking the equality between the amount the user authorised as their minimum acceptable output and the amount actually credited to their shielded balance.

### Impact Explanation
A malicious or compromised relayer/guardian-equivalent party who controls the `externalActionMetadata` calldata forwarded to `router` (e.g., through route selection, minimal-output routing, or coordinating a sandwich around the swap) can cause the swap to execute far below the user's intended minimum output, and the contract will still accept and credit whatever `swappedAmount` results — silently reducing the user's shielded balance below what they authorised. This is a theft/loss-of-user-funds scenario (temporary or permanent freezing/loss of value the user never authorised), matching the report's underlying bug class (an approval/authorisation gap that lets a privileged-but-adversarial actor divert value that should be protected by an on-chain check).

### Likelihood Explanation
Exploitability depends on who controls `externalActionMetadata` at submission time (typically the relay/off-chain infra assembling the transaction) — since this content is not required to be validated against a real minimum by the contract, any relayer able to submit non-optimal router calldata (or one that colludes with/executes a sandwich) can realize this gap without needing owner/admin/relay-key compromise beyond the roles already trusted to assemble the swap transaction.

### Recommendation
Add an explicit `require(swappedAmount >= circomData.slippageValues[1], "swap output below floor")` after computing `swappedAmount` in `ExternalActionSwap.swap()`, so the on-chain execution actually enforces the floor committed to in the circuit's public inputs rather than merely checking it is non-zero.

### Proof of Concept
1. User submits a shielded swap with `circomData.slippageValues[1] = X` (their true minimum acceptable output).
2. The relayer/guardian-equivalent constructs `externalActionMetadata` that routes the swap through a low-liquidity/adversarial path (or sandwiches it), yielding `swappedAmount < X`.
3. `swap()` in `ExternalActionSwap.sol` only checks `slippageValues[1] != 0` (line 53-56) and never compares it to `swappedAmount` (lines 63-93), so the transaction proceeds and the user's shielded UTXO is credited with `amountToSendToHinkal` derived from the deflated `swappedAmount`, resulting in silent value loss below the user-committed floor.
