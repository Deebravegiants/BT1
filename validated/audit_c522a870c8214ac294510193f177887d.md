Audit Report

## Title
JWT replay-guard check-then-act race allows a single-use HTTP trigger token to authorize concurrent duplicate workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `h.jwtCache.isReplay(claims.ID)` and only records usage via `h.jwtCache.recordUsage(claims.ID)` at the end of the function, after signature verification, workflow lookup, and authorized-key checks. `isReplay` and `recordUsage` acquire the cache's mutex independently (`RLock`/`Lock` on `jwtReplayCache.mu`) rather than as a single atomic check-and-set, so two concurrent `Authorize` calls carrying the same valid JWT can both observe `isReplay == false` before either calls `recordUsage`, letting a single-use token authorize more than one execution.

## Finding Description
The verified code shows the exact sequence claimed: [1](#0-0) 

`isReplay` and `recordUsage` are implemented as two separate lock acquisitions on the same `jwtReplayCache`, with no combined check-and-set: [2](#0-1) 

This is confirmed to be a genuine TOCTOU gap: between the `isReplay` read (releasing `RLock` immediately after) and the later `recordUsage` write, there is no lock held across the whole `Authorize` call, and nothing else in the call path serializes concurrent invocations with the same `jti`. Tracing the caller path, `httpTriggerHandler.HandleUserTriggerRequest` calls `authorizeRequest` → `workflowMetadataHandler.Authorize` directly: [3](#0-2) [4](#0-3) 

The only other uniqueness check in the request path is `setupCallback`'s check on `req.ID` (the JSON-RPC request ID), not the JWT `jti`: [5](#0-4) 

Since `req.ID` is chosen by the caller and is independent of the JWT `jti`, an attacker can submit two (or more) concurrent requests with distinct `req.ID`s but the identical signed JWT, and nothing rejects the duplicate `req.ID`s, so the race window in `Authorize` is fully reachable and exploitable by an unprivileged holder of one valid, signed, single-use JWT.

The codebase does contain a correctly-implemented atomic check-and-record primitive elsewhere (`RequestReplayGuard.CheckAndRecord`, which holds one mutex across both the existence check and the insert): [6](#0-5) 

This confirms the fix pattern is known and used elsewhere in the codebase, but `WorkflowMetadataHandler`'s `jwtReplayCache` does not use an equivalent atomic primitive.

## Impact Explanation
A winning race lets one single-use JWT authorize more than one concurrent workflow execution. This is a quota/one-time-token bypass on the gateway's HTTP trigger authorization path, mapping to the in-scope "unauthorized job run" impact category — a workflow that is supposed to be triggerable exactly once per issued token can instead be triggered multiple times, which is significant when the triggered workflow performs fund-moving or other state-changing side effects. The impact is bounded to duplicate execution of a workflow the attacker is already authorized to trigger (they must already hold a valid signed JWT for that specific workflow/signer), not to arbitrary privilege escalation or authentication bypass against workflows they aren't authorized for.

## Likelihood Explanation
Exploitation only requires possession of one legitimately issued (or intercepted) signed JWT for an HTTP-triggered workflow, and sending it via multiple concurrent HTTP requests with distinct JSON-RPC `id`s (a normal, unprivileged client capability) to win the goroutine-scheduling race inside `Authorize`. No operator/admin access, host access, or malicious-node capability is required, and the race is a standard concurrent-request race that is straightforward to attempt (win probability depends on scheduling, so it may require several attempts to reliably win, but is repeatable).

## Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic check-and-set primitive (analogous to `RequestReplayGuard.CheckAndRecord` in `core/capabilities/vault/request_replay_guard.go`) that holds one lock across both the existence check and the insert, and call that combined primitive from `WorkflowMetadataHandler.Authorize` immediately after JWT signature verification, before performing the authorized-key checks, so that only one of two concurrent requests with the same `jti` can pass.

## Proof of Concept
1. Register a workflow with an authorized signer key in `WorkflowMetadataHandler.authorizedKeys`.
2. Generate one valid signed JWT (`jti = X`) for an HTTP trigger request to that workflow.
3. Construct two `jsonrpc.Request` objects with distinct `ID` fields but the same JWT token in `req.Auth`.
4. Spawn two goroutines that concurrently call `WorkflowMetadataHandler.Authorize(workflowID, token, req1)` and `Authorize(workflowID, token, req2)`.
5. Assert: under race conditions, both calls can return a non-nil `*gateway.AuthorizedKey` with no error, proving the single-use JWT authorized two executions. This can be implemented as a Go test using `sync.WaitGroup` with both goroutines started simultaneously and repeated iterations (or `go test -race -count=100`) to demonstrate the race is winnable, since `isReplay`'s `RLock`/`RUnlock` completes before `recordUsage`'s `Lock` is acquired at the end of `Authorize`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
