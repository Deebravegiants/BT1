### Title
Webhook Shop-Domain Header Is Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` in `Registry.process` proves only that the *body bytes* were signed by Shopify with `Context.api_secret_key` — it proves nothing about which shop sent the request. However, `Registry.process` uses `request.shop` (sourced from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) directly as the tenant identifier passed to the host app's handler.

### Finding Description
`process` validates the webhook with: [3](#0-2) 

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the received `hmac`: [4](#0-3) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to the HMAC: [5](#0-4) 

Because there is only **one shared `api_secret_key` for the whole app** (not a per-shop secret), any tenant that has ever received a legitimate webhook from Shopify (e.g. by triggering `orders/create` in their own store, which they fully control) possesses a `(raw_body, hmac)` pair that is valid under the app's secret. That tenant can then replay this exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim's shop domain. `HmacValidator.validate` only checks that `hmac` matches `sha256_hmac(secret, raw_body)` — it never checks that `shop` (or `topic`) is consistent with what Shopify actually signed, so the forged request passes validation and is dispatched to the handler as if it came from the victim shop: [6](#0-5) 

This is exactly the "field acted on but not covered by the HMAC" pattern — `shop` is trusted/acted upon (it determines which tenant's session/data the host app operates on, per the documented handler contract) but is not part of the signed payload.

### Impact Explanation
This breaks the identity binding `shop_authenticated == shop_acted_upon`: the shop domain used by the host application to select a tenant session, look up stored merchant data, or route background jobs is not the shop Shopify actually authenticated. A malicious merchant/attacker with any working app installation can spoof `shopify-shop-domain` (or a stale `topic`) on a replayed, self-obtained body+HMAC pair to make the app process data as belonging to a different (victim) shop. Depending on how the host app implements its handler (as literally shown in this gem's own documentation, `shop_domain: data.shop` is used to enqueue tenant-scoped work), this can lead to cross-tenant data confusion/access — a Critical-impact class per the given criteria.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must be a legitimate (even if low-privilege) merchant/installer of the vulnerable app to obtain a valid `(raw_body, hmac)` pair in the first place (e.g., via their own store's webhook deliveries), and the payload content is fixed to whatever body Shopify actually sent for that event on the attacker's own shop. Still, no secret material, TLS interception, or social engineering is required — only observing one's own legitimate webhook traffic and replaying it with a different header value to a publicly reachable webhook endpoint, which is exactly the "unprivileged internet user" threat model in scope here.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-covered payload before validation, or otherwise cryptographically tie the `shop` header to the request. Concretely, `to_signable_string` should not be the raw body alone — e.g., verify the `shopify-shop-domain` header against a shop the app has an active session/webhook registration for the specific `webhook_id`, and/or require callers to additionally validate `request.shop` against `webhook_id`-to-shop state recorded at registration time, rather than trusting the header outright once the body HMAC passes.

### Proof of Concept
1. App developer installs their own app on `attacker-shop.myshopify.com` and triggers `orders/create`. Shopify sends a webhook with headers `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker captures `raw_body` and `shopify-hmac-sha256` (both are things any merchant naturally receives/can log from their own installed webhook endpoint).
3. Attacker resends a POST to the app's webhook endpoint with the same `raw_body` and `shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the shared secret — validation succeeds: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, i.e., the host app processes attacker-supplied content under the victim's tenant identity: [8](#0-7)
