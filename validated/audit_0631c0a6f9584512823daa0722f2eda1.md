### Title
Unrestricted `superApprove` in `HyperFungibleTokenImpl` lets any address grant itself unlimited allowance over any holder's fee-token balance - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl.superApprove(address owner, address spender)` calls the internal ERC20 `_approve(owner, spender, type(uint256).max)` directly, without any access control, without checking `msg.sender == owner`, and without any role gate. [1](#0-0) 

### Finding Description
`HyperFungibleTokenImpl` is the fee token deployed by the protocol's own deploy script for non-mainnet/testnet deployments, becoming the `feeToken` configured on `EvmHost`, used by every dispatcher/relayer to pay for ISMP dispatch and relayer rewards. [2](#0-1) 

Unlike `mint`/`burn`, which are properly gated behind `MINTER_ROLE`/`BURNER_ROLE`, `superApprove` is `public` with no modifier at all: [3](#0-2) [1](#0-0) 

Because `_approve(owner, spender, type(uint256).max)` sets the ERC20 allowance mapping directly, any unprivileged address can call `superApprove(victim, attacker)` to grant the attacker unlimited spending allowance over the victim's balance, then call `transferFrom(victim, attacker, victim.balanceOf())` on the standard ERC20 interface to drain the victim's fee-token balance completely. No signature, consent, or role from the victim is required. This is the same bug class as the DEI incident referenced in the report: a state-mutating function that should be privileged (an approval/consent action normally reserved for the token owner) is left publicly callable, letting an attacker manipulate balances/allowances of arbitrary accounts and steal funds.

### Impact Explanation
Any holder of this fee token — which is used to pay for dispatch and relayer fees across the ISMP host, and can be funded by users, relayers, or the `TokenFaucet` — can have their entire balance drained by any third party in a single transaction, with no cooperation or private key exposure required from the victim. This is a direct, permanent theft of funds primitive reachable from a single unprivileged transaction, satisfying the "concrete theft of funds" validation bar.

### Likelihood Explanation
Trivial to exploit: the function is `public`, requires no role, no proof, no special preconditions beyond the victim holding a nonzero balance of the token. Any address (an unprivileged relayer, a bandwidth purchaser paying fees, a faucet recipient, etc.) holding this token is a potential victim the moment the contract is deployed and in use as `feeToken`.

### Recommendation
Remove `superApprove` from production code entirely, or restrict it to `msg.sender == owner` (self-approval only) equivalent to standard ERC20 `approve`, or gate it behind `onlyRole(DEFAULT_ADMIN_ROLE)` if it must exist as a test utility, and ensure it is never included in a contract that is deployed as a live fee token via `DeployIsmp.s.sol`.

### Proof of Concept
1. Deploy/observe `HyperFungibleTokenImpl` deployed as `feeToken` per `evm/script/DeployIsmp.s.sol:102-105`.
2. Victim `V` acquires balance of the fee token (e.g., via `TokenFaucet.mint` or by paying ISMP dispatch fees).
3. Attacker `A` calls `feeTokenInstance.superApprove(V, A)` — no access control blocks this call. [4](#0-3) 
4. Attacker `A` calls standard ERC20 `transferFrom(V, A, feeTokenInstance.balanceOf(V))`, draining `V`'s entire balance to `A`.
