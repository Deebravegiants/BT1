### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) header is trusted but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, and `ShopifyAPI::Utils::HmacValidator.validate` only ever checks that HMAC against the body. None of the Shopify headers — `shop-domain`, `topic`, `api-version`, `webhook-id` — are part of the signed material, yet `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the authenticated tenant identity once HMAC validation of the body succeeds.

### Finding Description
The webhook signature binding this gem implements is:

```
HMAC_valid  ==  (api_secret_key, raw_body)
```

but the value that is *acted on* as the tenant identity is `request.shop`, which is read straight from an unauthenticated header: [1](#0-0) 

`to_signable_string` — the only input to the HMAC check — is just the raw body, never the headers: [2](#0-1) 

`HmacValidator.validate` computes/compares the HMAC purely over that signable string: [3](#0-2) 

`Registry.process` performs exactly one check (`Utils::HmacValidator.validate(request)`) and then dispatches to the handler using `request.shop` taken from the header, with no cross-check against the signed body: [4](#0-3) 

Because the same `api_secret_key` is shared by *every* shop that installs the app, any shop that has the app installed can legitimately trigger Shopify to sign an arbitrary attacker-influenced webhook body (e.g. an `orders/create` or `products/update` event containing attacker-chosen field values) with a real, valid HMAC. Since the signature never binds the body to a particular shop, that exact `(raw_body, hmac)` pair remains valid when replayed to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a different, victim shop. `Registry.process` will accept it (HMAC check passes because it only validates the body) and hand the handler a `WebhookMetadata` claiming to be from the victim shop but containing attacker-controlled body content.

This is the same bug class as the Tendermint report: a signature verification path that validates a payload but leaves a field that downstream logic treats as an authenticated identity binding (`shop`) outside the coverage of that signature.

### Impact Explanation
This breaks the tenant-isolation boundary this gem is supposed to provide to host applications: `data.shop` in the handler is presented as verified/authenticated, but it is fully attacker-controlled. Any host application that keys per-tenant side effects (order/inventory sync, GDPR compliance actions, billing state, customer data updates, etc.) off `WebhookMetadata#shop` can be made to apply attacker-supplied data to another merchant's tenant records — a cross-tenant access/data-injection primitive, without needing the app's `client_secret`, an access token, or any privileged account. It only requires installing the app on a shop the attacker controls (an ordinary, unprivileged action available to any internet user with a free Shopify dev store) and the ability to POST to the app's public webhook endpoint.

### Likelihood Explanation
Requires no leaked secrets, tokens, or elevated access — only that the app is publicly installable (the normal Shopify App Store distribution model) and that its webhook endpoint accepts requests without additional shop-binding checks, which is exactly what `Registry.process` does. The severity does depend on how the host application uses `WebhookMetadata#shop`, but the gem provides no primitive to detect or reject the spoofing, and its own webhook usage docs instruct consumers to trust `data.shop` directly.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the material that is cryptographically verified, or otherwise cryptographically tie the header claims to the signed body/delivery — e.g., require the host application to independently confirm `request.shop` against a known/installed-shop store keyed by webhook subscription id rather than trusting the header outright. At minimum, document prominently (and ideally enforce via `ShopValidator`) that `request.shop` from `Webhooks::Request` is unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Attacker installs the target app on their own (free) Shopify development store, obtaining a legitimate webhook subscription that POSTs to the app's shared public webhook endpoint.
2. Attacker triggers a webhook event (e.g. edits a product title to attacker-controlled content) so Shopify computes and sends `raw_body` + a valid `X-Shopify-Hmac-Sha256` signed with the app's shared `api_secret_key`.
3. Attacker captures this `(raw_body, hmac)` pair (e.g., by pointing their own store's webhook delivery at attacker-controlled infrastructure first).
4. Attacker replays an HTTP POST to the app's public webhook endpoint with the exact same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC — it never inspects the `shop-domain` header. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-controlled body data, believing it is legitimate data from the victim's tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
