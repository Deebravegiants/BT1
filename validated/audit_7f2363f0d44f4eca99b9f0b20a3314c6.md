### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
The webhook HMAC verification in this gem only authenticates the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read directly from HTTP headers and are never included in the signed material, so an attacker who legitimately owns a Shopify development store can capture one validly-signed webhook and replay it against the same app endpoint with a forged `shop-domain` header pointing to a victim shop, and the signature check will still pass.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-visible HTTP headers, none of which participate in `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it with the received `hmac`, which is exactly the body-only string above: [3](#0-2) 

`Registry.process` treats `Utils::HmacValidator.validate(request)` as the sole authenticity gate before dispatching to the app's handler with `shop: request.shop` taken from the unauthenticated header: [4](#0-3) 

Because `shop` (and `topic`/`webhook_id`) is not bound into the HMAC, the identity equality the gem is supposed to enforce — "the shop attributed to this webhook == the shop the HMAC actually authenticates" — does not hold. Any user with a legitimate installation on their own store can obtain a validly-signed body/HMAC pair (Shopify signs webhooks for the attacker's own store using the app's real secret) and reuse that exact signature while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header for a different, victim tenant. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

This is the direct analog of the reported bug class: a field acted upon by the verifier (`shop`, used downstream to establish tenant identity) is not covered by the cryptographic check (the HMAC), just as the report's public inputs were used in `Pi` computation without being range-checked against the value the proof actually commits to.

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to select the tenant/session context for writing data, deduplicating, or triggering GDPR/mandatory actions can be made to process attacker-supplied webhook content under a victim shop's identity — a cross-tenant data-integrity/confusion issue reachable by any user who can install the app on their own store and replay HTTP requests, without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
High likelihood for any consumer of this library: the header-vs-signature mismatch is unconditional, requires no secret knowledge beyond normal, legitimate webhook receipt on the attacker's own installation, and works against the documented, canonical `Registry.process` entry point.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material verified by `HmacValidator`, or otherwise cryptographically bind them (e.g., derive/verify `shop` from a source Shopify actually signs, such as re-deriving expected values from a per-shop secret/session rather than trusting the raw header). At minimum, document and enforce that `request.shop` must never be used as a tenant key without an out-of-band verification that it matches an already-established, authenticated session for that shop.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and legitimately receives a webhook, capturing `raw_body` and the valid `X-Shopify-Hmac-Sha256` header Shopify computed over that body with the app's real secret.
2. Attacker POSTs the same `raw_body` and the same `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the (unchanged) signature: [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: request.shop` == `"victim-shop.myshopify.com"`, even though the payload/signature pair was never issued for that shop.

            result
          else

          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
