## Title
Webhook HMAC signature does not cover the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which merchant/tenant the webhook belongs to. Because the `shop` value is never included in the signable string, an attacker who legitimately owns any one shop that has a registered webhook (and can therefore obtain a genuine, validly-signed body/HMAC pair from Shopify) can replay that exact body with a forged `shop-domain` header pointing at a victim shop, and the library will accept it as authentic.

### Finding Description
The webhook `Request` object implements `VerifiableQuery` and defines the signable material as only the raw body: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers without being part of the HMAC input: [2](#0-1) 

`Registry.process` validates the HMAC and, if it matches, immediately trusts `request.shop` (and `request.topic`) to construct `WebhookMetadata` that is handed to the host application's handler: [3](#0-2) 

`HmacValidator.validate` only performs a `secure_compare` on the computed vs. received signature over `to_signable_string` (the raw body) — it never checks that the `shop` header is consistent with anything cryptographically bound to it: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality the code implicitly assumes is `shop-domain header == shop that produced/authorized this body+signature`, but the actual guarantee provided by the signature check is only `hmac == HMAC(secret, body)`, with `shop` completely unconstrained.

### Impact Explanation
Because a merchant's shop domain drives which tenant record the host application updates (order data, uninstall, inventory changes, GDPR data-erasure requests, etc.), and the gem hands `request.shop` straight through to the handler as authenticated, an attacker who is also a legitimate Shopify merchant (or otherwise obtains one genuine signed webhook body from their own store) can forge the `shop-domain` header to impersonate a different, victim shop while keeping the same body and (still-valid) HMAC. Any host application that uses `WebhookMetadata#shop` to key its per-tenant handling — the documented and expected pattern — will act on data attributed to the wrong tenant. This is a cross-tenant identity-spoofing vector reachable by any unprivileged internet user who can register one shop and receive one legitimate webhook.

### Likelihood Explanation
Likelihood is moderate-to-high: no special privileges beyond installing/owning any Shopify development store are required, webhook endpoints are public HTTP endpoints, and headers are trivially forgeable by any client (the HMAC only protects the body, not headers, which is documented Shopify webhook behavior but is not compensated for anywhere in this library). The main constraint is that the attacker needs a body whose *content* happens to be attributable/useful when replayed under a different shop, which is often the case for topics whose bodies are shop-agnostic or attacker-controllable (e.g., some app-lifecycle or product/order test payloads), or via topics where the attacker's own store data can plausibly overlap with data the victim app expects.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the authenticated material, e.g., by including the `shop-domain` header value in the string being HMAC-verified, or by requiring the host application to separately confirm that `request.shop` corresponds to a shop with a currently valid, stored session/install record before processing the webhook. At minimum, document prominently that `WebhookMetadata#shop` is not itself authenticated and must be cross-checked against known installed shops before being trusted for tenant-scoping decisions.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook for a registered topic (e.g. `app/uninstalled`), with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw body B>`
   - body `B`
2. Attacker replays the exact same body `B` and HMAC to the host application's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged header, and `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)` against the unchanged body: [5](#0-4) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`: [6](#0-5) 
5. The host application, trusting `shop` as the tenant identifier, performs the topic's action (e.g., uninstall cleanup, data deletion) against the victim's records instead of the attacker's own.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
