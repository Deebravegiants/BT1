## Finding

### Title
Router._computeBuy underflow-panics on oversized buys once a token donation inflates the pair's real balance above the virtual reserve, permanently blocking the curve's supply-trigger graduation - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap back-calculation assumes `realBalance <= reserveToken` always holds. A plain ERC20 `transfer` of the launched `Token` directly into its `Pair` — reachable by any unprivileged holder — breaks that assumption, and any subsequent buy that needs the overflow cap (in particular the buy that would otherwise exhaust the curve and fire the supply-trigger graduation) reverts with an arithmetic-underflow panic instead of executing.

### Finding Description
`Router._computeBuy` caps `tokensOut` at the pair's real token balance and back-calculates `amountInUsed` from the capped state: [1](#0-0) 

```solidity
tokensOut = reserveToken - (k / newReserveAsset);
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;     // <-- reserveToken - realBalance
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

`cappedReserveToken = reserveToken - tokensOut` is only safe when `realBalance <= reserveToken` (the documented and tested "virtual reserve always exceeds real balance" invariant). That invariant is explicitly a *no-donation* property — the codebase itself acknowledges it breaks under donation, e.g. in `previewLtUntilGraduation`'s explicit early-out for "donation-inflated `realBalance`": [2](#0-1) 

and it is directly demonstrated by the test suite's own donation-attack regression, which proves `realBalance > reserveToken` is achievable by any address holding curve tokens and simply transferring them to the `Pair`: [3](#0-2) 

Unlike `Bonding.previewLtUntilGraduation`, which was patched with an explicit `if (realBalance >= reserveToken) return ...` guard for exactly this donation case, `Router._computeBuy` has no equivalent guard. Once `realBalance > reserveToken`, any buy whose uncapped `tokensOut` still exceeds the (now inflated) `realBalance` — which is guaranteed for the buy that attempts to consume the entirety of the remaining real supply, i.e. the buy that would normally fire the curve's supply-trigger graduation — hits the capping branch, sets `tokensOut = realBalance`, and computes `reserveToken - tokensOut` where `tokensOut (=realBalance) > reserveToken`. In Solidity 0.8, this subtraction reverts with a `Panic(0x11)` (arithmetic underflow) *before* the `if (cappedReserveToken == 0) revert OverflowCapDegenerate()` check is ever reached — the intended defensive revert never fires; a raw panic does instead.

The existing regression coverage (`test_donation_zapBuyStillSucceeds`, `test_donation_sellsStillWork`) only exercises small buys/sells post-donation, never a buy sized to hit the overflow-cap branch after the invariant is broken, so this path is untested.

### Impact Explanation
Once an unprivileged holder (who legitimately bought tokens via `Zap.buy`) donates enough of the launched `Token` directly to its `Pair` to push `tokenBalance() (realBalance)` above the pair's stored `reserveToken`, the specific buy that would drain the curve's remaining real supply and trip the supply-trigger graduation (`IPair.tokenBalance() == 0`) reverts with an underflow panic instead of executing. Because the donation is irreversible from the buyer's side (the donated tokens are stuck in the pair and are only ever burned inside `_prepareGraduationLiquidity`, which itself is only reached *after* graduation triggers — a chicken-and-egg lock), the curve's ability to reach the supply trigger is permanently disabled for that token unless/until the USD trigger independently fires via LT exchange-rate appreciation. This is a permanent-freeze / denial-of-service condition on the bonding curve's core buy/graduation flow, directly reachable by a single unprivileged wallet with direct ERC20 transfers into the `Pair`.

### Likelihood Explanation
High feasibility: any address that has bought tokens off the curve (a normal, unprivileged action) can trivially `transfer` those tokens directly to the `Pair` address — no special role or permission is required, and `Pair.swap`/`Pair.transferToken` are the only gated functions; a plain ERC20 transfer is not gated. The `_stageDonationAttack` helper already in the test suite shows the exact mechanics needed to inflate `realBalance` past `reserveToken` with a single drain-then-donate sequence, confirming this is not a contrived edge case but a state reachable in a couple of ordinary transactions.

### Recommendation
Guard `Router._computeBuy`'s overflow-cap branch the same way `Bonding.previewLtUntilGraduation` already guards its supply leg: detect `realBalance >= reserveToken` before computing `cappedReserveToken` and handle it explicitly (e.g., treat the supply-cap leg as unreachable/skip capping, or explicitly revert with a named error) rather than letting the subtraction underflow into a Solidity panic. Add a dedicated regression test that donates tokens into the pair to break the invariant and then submits a buy sized to hit the overflow-cap branch, asserting it degrades gracefully instead of panicking.

### Proof of Concept
1. Launch a token via `Zap.createToken`.
2. As `drainer` (any unprivileged wallet), buy a large chunk of the curve (e.g. via `Zap.buy`/`Bonding.buy`) to acquire > `LP_RESERVE` (250M) tokens, exactly as `_stageDonationAttack` does.
3. `Token.transfer(pairAddr, donatedTokens)` — a plain ERC20 transfer, no role required. This makes `IPair(pairAddr).tokenBalance() > reserveToken` (confirmed by `test_donation_realBalanceExceedsReserveToken`).
4. Have any buyer submit a buy sized so that the uncapped `tokensOut` computed by `Router._computeBuy` still exceeds the now-inflated `realBalance` (e.g., attempt to buy out the entire remaining real supply, which is exactly the transaction that would normally trip the supply-trigger graduation).
5. The call reverts with a Solidity `Panic(0x11)` from `cappedReserveToken = reserveToken - tokensOut` underflowing, instead of executing or hitting `OverflowCapDegenerate()`. The curve can no longer complete that buy, and the supply-trigger graduation path is permanently blocked for this token.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
