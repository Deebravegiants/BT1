### Title
Stale Mega Agent model configuration (`iris_model_configs`, `ir_net_model_configs`, `fraud_check_engine_config`) used across signups after backend config update - ([File: src/brokers/observer.rs])

### Summary
The reported bug describes a config-update function that mutates stored config without triggering the recomputation step (`execute_epoch_operations`) that consumes it, so subsequent operations act on stale data. In `orb-core`, the analogous pattern is `DefaultPlan::config_update` in `src/brokers/observer.rs`, which periodically replaces the shared `Config` object with a freshly downloaded one, but the already-spawned `mega_agent_one`/`mega_agent_two` process agents — which were initialized once from a snapshot of `Config` at spawn time — are never told to re-derive their internal model state from the new config unless they happen to be explicitly killed and respawned.

### Finding Description
The shared configuration lives in `Arc<Mutex<Config>>` and is refreshed by a background task in `DefaultPlan::config_update`: [1](#0-0) 

This performs a full atomic replace of the `Config` object (`*config.lock().await = new_config`). However, `mega_agent_one` and `mega_agent_two` — the process agents that host the Iris, IR-Net, Occlusion, RGB-Net and Face-Identifier models — are constructed once from a `Config` snapshot at spawn time: [2](#0-1) [3](#0-2) 

The `enable_mega_agent_one`/`enable_mega_agent_two` methods generated by the broker macro only construct a fresh agent (and thus fresh config) when the corresponding `Cell` is `Vacant`. If the cell is already `Enabled` or `Disabled` from a previous signup, the *existing* agent instance is reused as-is, with no re-initialization from the current config: [4](#0-3) 

This means that config fields baked into `MegaAgentOne`/`MegaAgentTwo` at spawn time — such as `iris_model_configs`, `ir_net_model_configs`, `child_threshold`, and `fraud_check_engine_config` (used to build `iris::Model`/`ir_net::Model` via `impl From<&Config>`) — keep using whatever values were current when the agent process was first spawned, even after the backend pushes an updated `Config` via `config_update`. Only `face_identifier_model_configs` is explicitly re-pushed on every biometric pipeline run via `run_update_all_configs`: [5](#0-4) 

Developers were clearly aware that mega-agent config could go stale: `warmup::Plan::run` explicitly kills both mega agents before re-enabling them "to ensure latest config updates are loaded properly": [6](#0-5) 

But this kill/respawn only happens during the dedicated warm-up phase, not on every signup cycle in the main loop (`MasterPlan::run`), nor is it triggered by the `config_update` background task itself. As a result, once mega agents are spawned, they can process many subsequent signups using outdated iris/IR-Net model configs and fraud-check engine configuration, exactly mirroring the reported bug class where `update_config` mutates stored config but never invokes the recomputation step that would apply it.

### Impact Explanation
If the backend operator updates `iris_model_configs`, `ir_net_model_configs`, `child_threshold`, or `fraud_check_engine_config` to tighten fraud/liveness/underage detection (e.g., in response to a discovered bypass or newly identified fraud pattern), signups processed by an already-running `mega_agent_one`/`mega_agent_two` will continue to use the old, potentially weaker model/threshold configuration until the process is killed (crash-triggered restart) or the orb goes through `warmup::Plan`. This can lead to fraud/liveness checks and underage-detection logic operating on stale (and potentially less strict) parameters, contributing to unauthorized or misattributed signups.

### Likelihood Explanation
Likelihood is limited by the fact that Orb devices are usually rebooted/restarted relatively often (each boot re-runs `warmup::Plan`, which does kill and respawn the mega agents with fresh config), which bounds the staleness window. However, whenever the orb runs multiple signups continuously without a reboot or warm-up, or the config is pushed mid-session, the stale-config window is real and unbounded by any explicit refresh mechanism in the main signup loop.

### Recommendation
Ensure that whenever `Config` is replaced by `config_update` (or at minimum before each signup / biometric pipeline run), the relevant fields consumed by `mega_agent_one` and `mega_agent_two` (`iris_model_configs`, `ir_net_model_configs`, `child_threshold`, `fraud_check_engine_config`) are either: (1) explicitly pushed to the running agents via an `UpdateConfig`-style message analogous to what already exists for `face_identifier_model_configs` in `run_update_all_configs`, or (2) the mega agents are killed and respawned (as already done in `warmup::Plan`) whenever the shared config changes, so that security-relevant model configuration is never used stale across a config update boundary.

### Proof of Concept
1. Orb boots, `warmup::Plan::run` spawns `mega_agent_one`/`mega_agent_two` from `Config` (with `iris_model_configs`/`child_threshold`/`fraud_check_engine_config` = V1) — see `src/plans/warmup.rs:72-79` and `src/brokers/orb.rs:999-1005`.
2. Backend pushes an updated config with tightened fraud/liveness parameters (V2). The observer's `config_update` background task replaces the shared `Config` object: `src/brokers/observer.rs:187-205`.
3. A new signup starts; `MasterPlan::run`/`do_signup` calls `orb.enable_mega_agent_one()`/`enable_mega_agent_two()` (via `biometric_pipeline::Plan::run`, `src/plans/biometric_pipeline/mod.rs:274`). Because the `Cell` is not `Vacant` (agent already spawned and just disabled, not killed), the macro-generated `enable_*` reuses the existing agent instance without re-deriving it from the new `Config` — `agentwire/macros/src/broker.rs:275-290`.
4. `run_update_all_configs` only refreshes `face_identifier_model_configs`; iris/IR-Net model configs and fraud-check engine config remain at V1 — `src/plans/biometric_pipeline/mod.rs:580-591`.
5. The signup's fraud/liveness/underage checks are evaluated using the stale V1 parameters instead of the newly pushed, stricter V2 parameters — analogous to the reported `execute_epoch_operations` not being invoked after `update_config`.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
