The code confirms the claim exactly as described in the report. `Authorize` calls `h.jwtCache.isReplay(claims.ID)` under a separate `RLock`, performs unrelated authorization checks in between, and only calls `h.jwtCache.recordUsage(claims.ID)` afterward under a separate `Lock` [1](#0-0) . The `jwtReplayCache` type uses a `sync.RWMutex` with `isReplay` and `recordUsage` as two independent critical sections rather than one atomic check-and-set [2](#0-1) . There is no test covering concurrent/replay behavior for this handler, and no evidence in `SECURITY.md` or elsewhere that this is an accepted/out-of-scope or already-fixed issue [3](#0-2) .

This is a genuine TOCTOU race: two concurrent requests bearing the identical single-use JWT can both pass `isReplay` before either commits via `recordUsage`, since there is a window between the read-lock release and the write-lock acquisition. This is triggerable purely by an unprivileged client sending two simultaneous HTTP requests with the same captured/leaked JWT to the gateway's trigger endpoint — no operator, admin, or host access required — and the impact (bypassing single-use enforcement to trigger a workflow more than once) maps to an in-scope authentication/quota bypass on the gateway.

Audit Report

## Title
JWT replay-cache check-then-act race allows a single-use HTTP-trigger JWT to be reused by concurrent requests - (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay status via `jwtCache.isReplay(claims.ID)` and only marks the JWT as used via `jwtCache.recordUsage(claims.ID)` several steps later, with each operation acquiring the cache's `sync.RWMutex` independently rather than atomically. Two requests using the same JWT `jti` sent concurrently can both pass the `isReplay` check before either calls `recordUsage`, allowing the same single-use JWT to authorize multiple concurrent trigger invocations.

## Finding Description
`Authorize` verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)` (`RLock`/`RUnlock`) [4](#0-3) , performs unrelated workflow/key lookups [5](#0-4) , and finally calls `h.jwtCache.recordUsage(claims.ID)` (`Lock`/`Unlock`) only at the end [6](#0-5) . Because `isReplay` and `recordUsage` are separate, non-atomic critical sections of `jwtReplayCache` [2](#0-1) , no lock is held across the whole `Authorize` call, leaving a race window in which two goroutines processing the same JWT concurrently can both observe `isReplay == false` before either commits the usage record. No other authentication or synchronization mechanism in `Authorize` closes this window.

## Impact Explanation
JWTs used for HTTP-trigger authentication are intended to be single-use via the `jti` claim and replay cache. Winning the race lets an attacker (or a client that resends in parallel) get one JWT accepted more than once concurrently, each acceptance yielding an `*gateway.AuthorizedKey` used downstream to authorize a distinct workflow trigger invocation. This defeats the single-use invariant of the token, enabling an authentication/quota bypass on the gateway's trigger endpoint — an in-scope impact class (gateway request impersonation / authorization bypass).

## Likelihood Explanation
The race only requires an attacker to send two (or more) requests carrying the same captured/leaked JWT at the same time; this is fully within an unprivileged HTTP client's control and needs no node, DON, or host compromise. The window is narrow but deterministically reproducible under concurrency (e.g., via a Go test spawning two goroutines calling `Authorize` with the same token), matching the described LooksRare-style TOCTOU pattern.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-set method on `jwtReplayCache` (e.g., `checkAndRecord(jti string) bool`) that acquires the write lock once, checks for existence, inserts if absent, and returns whether the token was already used — all under one lock acquisition. Call this atomic method in `Authorize` immediately after JWT signature verification, before performing any other authorization logic, so only one of the racing requests can proceed.

## Proof of Concept
Go unit test plan: construct a `WorkflowMetadataHandler` with a valid signed JWT and workflow/authorized-key setup; spawn two goroutines that both call `Authorize(workflowID, sameToken, req)` concurrently; assert (over repeated runs / with `-race` and forced scheduling delay between `isReplay` and `recordUsage`, e.g. via a test hook or `time.Sleep` injected in a modified `isReplay`) that both goroutines can return a non-nil `*gateway.AuthorizedKey` for the same `jti`, demonstrating that the single-use enforcement is bypassed.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

}

	defer cache.mu.Unlock()
