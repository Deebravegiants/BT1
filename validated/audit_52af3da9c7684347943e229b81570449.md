### Title
Attacker-selected route venue can inject a wallet-draining transfer into the caller’s authorization tree - (File: contracts/swap-aggregator/src/venues/soroswap.rs)

### Summary
The swap router executes pool addresses supplied through the decoded route payload, and the Soroswap adapter directly calls `get_reserves` and `swap` on `ctx.hop.pool`. [1](#0-0) [2](#0-1) 
Because venue addresses are not constrained to known protocol pools, an attacker can provide a contract that implements the expected adapter ABI but also calls `token.transfer(victim, attacker, amount)` inside `swap`. [3](#0-2) 
Soroban simulation records that unrelated transfer as a child of the victim’s original controller authorization, and execution succeeds if the victim signs that poisoned authorization tree. [4](#0-3) 

### Finding Description
`execute_strategy` decodes attacker-controlled route data, pulls the input under `sender.require_auth()`, and executes every decoded instruction. [5](#0-4) [6](#0-5) 
For a Soroswap hop, the router first transfers input to the payload-selected `pool`, then invokes that same address’s `swap` function. [7](#0-6) 
Neither the router settlement checks nor the controller’s exact input-transfer authorization prevent this venue from invoking another token transfer naming the original caller as `from`; host authorization merely records that invocation as an additional child that the caller must sign. [8](#0-7) [9](#0-8) 
The malicious venue can preserve route validity by returning sufficient output, so the measured output, minimum-output check, controller input-bound check, and final account risk checks do not bound the unrelated wallet transfer. [10](#0-9) [11](#0-10) 

### Impact Explanation
A victim who submits an attacker-supplied route and signs the simulated authorization tree can lose unrelated wallet tokens in addition to completing an apparently valid `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` operation. [12](#0-11) [13](#0-12) 
The harness demonstrates a route whose venue transfers the victim’s entire unrelated token balance to the attacker while returning fair swap output and preserving the expected collateral result. [14](#0-13) 
This is theft of user funds rather than merely poor route quality because the stolen asset is outside the swap’s declared input, output, and routed amount. [15](#0-14) 

### Likelihood Explanation
Exploitation requires the victim to use a malicious route and sign the authorization tree containing the extra transfer, so it is not a purely passive protocol compromise. [16](#0-15) 
However, route bytes are opaque to ordinary users, venue addresses are payload-selected, and the recorded extra authorization is still executable once signed. [17](#0-16) [7](#0-6) 
The attack works for both direct `execute_strategy` use and controller-mediated strategies because the rogue invocation can be attached beneath the caller’s signed root invocation. [5](#0-4) [18](#0-17) 

### Recommendation
Maintain an on-chain venue allowlist and reject route pool addresses that are not verified deployments for the selected adapter. [2](#0-1) 
As a defense-in-depth measure, expose signed route metadata to clients, reject simulations containing unexpected authorization children, and warn whenever a swap authorization tree includes any token transfer other than the exact declared input pull. [8](#0-7) [19](#0-18) 

### Proof of Concept
1. Deploy `FakePool`, which implements `get_reserves` and `swap`; have `swap` call `victim_token.transfer(victim, attacker, victim_balance)` and then pay sufficient output to the router. [7](#0-6) 
2. Give the victim supplied USDC collateral and construct a USDC-to-ETH route whose Soroswap instruction selects `FakePool` as `ctx.hop.pool`. [20](#0-19) 
3. Have the victim invoke `swap_collateral` with that route; the controller authorizes only the exact USDC transfer to the configured router, but the router subsequently enters `FakePool.swap`. [21](#0-20) [3](#0-2) 
4. Simulation records `victim_token.transfer(victim, attacker, victim_balance)` as a child authorization below the victim’s `swap_collateral` invocation. [22](#0-21) 
5. If the victim signs that simulation-produced tree, the swap completes, the attacker receives the victim’s unrelated wallet tokens, and the victim still receives the expected ETH collateral. [9](#0-8)

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {

    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])

        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));

    /// Decodes `swap_xdr` as a `StrategyPayload` and runs it for `sender`.
    ///
    /// Requires `sender` authorization. Pulls `total_in` of the input token, runs the
    /// instruction stream, applies fees, checks the minimum output, and returns the amount
    /// delivered to `sender`. Panics with `Error::InvalidRouteXdr` if the XDR does not decode.
    fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        renew_instance(&env);
        let payload = StrategyPayload::from_xdr(&env, &swap_xdr)
            .unwrap_or_else(|_| panic_with_error!(&env, Error::InvalidRouteXdr));
        execute::run(env, sender, total_in, payload)
    }
