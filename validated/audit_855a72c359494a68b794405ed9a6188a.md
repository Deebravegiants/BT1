### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) are trusted from unauthenticated headers while the HMAC only signs the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC that covers only the raw request body, then unconditionally trusts the `shop-domain`, `topic`, and `webhook-id` values taken from HTTP headers — none of which are covered by that signature — and hands them to the app's handler as the verified tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, immediately forwards the header-derived `shop`, `topic`, and `webhook_id` to the app's handler as trusted metadata identifying which tenant/topic the payload belongs to: [3](#0-2) 

The equality the gem implicitly claims to enforce is:
`bytes verified by HMAC == bytes acted upon as the tenant/topic identity`

In reality the HMAC only proves `raw_body` was signed with `api_secret_key`; it says nothing about which shop or topic that body was intended for. Any request whose body carries a signature that validates (e.g., a `raw_body` + `hmac-sha256` pair previously captured from one genuine, legitimately-signed webhook delivery) can be replayed with arbitrary `shop-domain`/`topic`/`webhook-id` headers, and `Registry.process` will accept it and dispatch it to the handler labeled with the attacker-chosen shop and topic.

### Impact Explanation
This breaks the tenant identity binding at the core of multi-tenant webhook processing: the gem asserts `data.shop` is authoritative (it is documented and used by consuming apps, e.g. `shopify_app`, purely to select which merchant's state to mutate), but that value is never covered by the signature that is supposed to authenticate the request. An attacker who can obtain even one legitimately signed webhook body (for instance, from their own store, or from a public/observable webhook) can replay it while asserting it belongs to a victim shop or a different topic, causing the app to process attacker-supplied data under another tenant's identity — a cross-tenant access condition, since typical downstream logic looks up sessions/records keyed by `data.shop`.

### Likelihood Explanation
Moderate-to-high: no possession of `api_secret_key` is required to mount the replay — the attacker only needs to have observed one valid `(raw_body, hmac)` pair generated by Shopify for any shop (including their own store, which any unprivileged internet user can set up as a merchant/dev store and receive real webhooks for). The header spoofing itself (setting `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id` to arbitrary values) requires nothing beyond making an HTTP POST to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them to the HMAC verification), or independently verify that the `shop-domain` header corresponds to a shop with an active, known session/installation before trusting it as the tenant identity in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store (or otherwise obtains one genuine webhook delivery), capturing a valid `raw_body` and its corresponding `X-Shopify-Hmac-Sha256` value signed by the app's real `api_secret_key`.
2. Attacker POSTs that exact `raw_body` + `hmac-sha256` header to the victim app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` with a different topic than what was originally signed).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC. [4](#0-3) 
4. The handler registered for that topic receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, causing the app to act as if the payload genuinely originated from and pertains to the victim shop. [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
