### Title
Missing FeeExceedsAmountError guard in `IntentsSDK.createWithdrawalIntents` allows negative `actualAmount` in signed `ft_withdraw`/`native_withdraw` intents - (File: packages/intents-sdk/src/sdk.ts)

### Summary
`createWithdrawalIntents` recomputes `actualAmount = amount - feeEstimation.amount` for fee-inclusive withdrawals but, unlike its sibling `_estimateWithdrawalFee`, never checks `amount <= feeEstimation.amount` before doing so. If a caller supplies a `feeEstimation` (from a prior estimate, a stale cached value, or one they constructed/forwarded) whose `amount` exceeds `withdrawalParams.amount`, `actualAmount` becomes a negative bigint that flows unchecked into `DirectBridge.createWithdrawIntentPrimitive`, which stringifies it directly into the `ft_withdraw`/`native_withdraw` intent's `amount` field.

### Finding Description
The claimed broken equality is: `amount debited == amount + fee` should always hold with `amount debited >= 0`. In `_estimateWithdrawalFee`, this is enforced: `if (args.withdrawalParams.feeInclusive) { if (args.withdrawalParams.amount <= fee.amount) throw new FeeExceedsAmountError(...) }` before computing `actualAmount`. [5](#0-4)  In `createWithdrawalIntents`, the same subtraction is performed with no equivalent guard: `const actualAmount = args.withdrawalParams.feeInclusive ? args.withdrawalParams.amount - args.feeEstimation.amount : args.withdrawalParams.amount;` [6](#0-5) 

This `actualAmount` is passed straight to `bridge.validateWithdrawal` and `bridge.createWithdrawalIntents`. For the `DirectBridge` route, `validateWithdrawal` only checks destination address validity, token/destination collision, and NEAR account existence — no amount-sign or amount-vs-fee check exists. [3](#0-2)  `createWithdrawalIntents` then calls `createWithdrawIntentPrimitive({ ..., amount: args.withdrawalParams.amount, ... })`, which does `amount: params.amount.toString()` with no sign check, so a negative bigint becomes a negative-looking string embedded in the signed intent. [4](#0-3) 

Attacker's exact input: call `IntentsSDK.createWithdrawalIntents` (or `signAndSendWithdrawalIntent`, which internally uses this path) directly with `withdrawalParams.feeInclusive = true`, `withdrawalParams.amount = 100n`, and `feeEstimation.amount = 200n` (a `feeEstimation` object the integrator obtained separately, is stale, or constructs itself — this is a normal, documented parameter, not a private/internal field). Because `createWithdrawalIntents` is a public documented entrypoint (also reachable via `signAndSendWithdrawalIntent`) and does not force callers to route through `_estimateWithdrawalFee` for every call, this divergence is reachable by any unprivileged caller who controls the `feeEstimation` argument passed to withdrawal signing.

Existing guards fail to catch this because `FeeExceedsAmountError` is only thrown inside `_estimateWithdrawalFee`'s code path, and `validateAddress`/`compareAddresses`/`DirectBridge.validateWithdrawal` do not perform any amount sanity check. The `assert` sanity checks in `omni-bridge.ts`/`poa-bridge-utils.ts` check fee/relayer amounts, not the sign of the final withdrawal amount.

### Impact Explanation
A negative `actualAmount` gets embedded in the `ft_withdraw`/`native_withdraw` intent, is signed by the user's key with their nonce, and submitted for settlement. This wastes a nonce and produces a malformed, signed payload; on-chain the intents contract or the NEP-141 token contract would very likely reject a negative-looking amount string, so no direct fund loss to the debit itself is demonstrated, but a valid user signature is produced for a payload that does not correspond to any amount the user intended, and if the string is interpreted differently downstream (e.g., unsigned/overflowed) it could result in an unintended debit. This matches at most a High-level concern (a withdrawal effectively stuck/rejected, wasted nonce, confusing status) rather than a demonstrated fund-draining Critical, since actual fund movement depends on the intents contract's own numeric parsing/validation, which is outside this repo's control.

### Likelihood Explanation
Preconditions: the caller must supply a `feeEstimation.amount` greater than `withdrawalParams.amount` while `feeInclusive: true`. This requires either forwarding a stale/mismatched fee estimate or deliberately constructing one — both are within an unprivileged caller's control since `feeEstimation` is a plain public-API parameter, not something cryptographically bound to the current amount before this call. It's repeatable per call. Feasibility is high (no special access needed) but the resulting payload's rejection is likely at the intents contract or token contract level once submitted.

### Recommendation
Add the same `FeeExceedsAmountError` guard in `IntentsSDK.createWithdrawalIntents` before computing `actualAmount`: 
```ts
if (args.withdrawalParams.feeInclusive && args.withdrawalParams.amount <= args.feeEstimation.amount) {
  throw new FeeExceedsAmountError(args.feeEstimation, args.withdrawalParams.amount);
}
```
Additionally, add a defensive `assert(actualAmount >= 0n, ...)` in `createWithdrawIntentPrimitive` (and equivalents for other bridges) as a last line of defense against negative amounts reaching the signed intent.

### Proof of Concept
```ts
// vitest, mocks only HTTP where applicable (none needed here since DirectBridge path doesn't hit network for this specific call)
it("createWithdrawalIntents allows negative actualAmount without FeeExceedsAmountError", async () => {
  const sdk = new IntentsSDK({ referral: "", intentSigner });
  const withdrawalParams = {
    assetId: "nep141:usdc.near", // or any DirectBridge-supported asset
    amount: 100n,
    destinationAddress: "alice.near",
    feeInclusive: true,
  };
  const feeEstimation = {
    amount: 200n, // > withdrawalParams.amount
    quote: null,
    underlyingFees: { [RouteEnum.NearWithdrawal]: { storageDepositFee: 0n } },
  };

  const call = sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation });

  // Assert 1: no FeeExceedsAmountError is thrown (demonstrating the missing guard)
  await expect(call).resolves.not.toThrow();

  const intents = await call;
  const ftWithdraw = intents.find((i) => i.intent === "ft_withdraw");
  // Assert 2: actualAmount = amount - feeEstimation.amount = 100n - 200n = -100n
  expect(ftWithdraw.amount).toBe((-100n).toString());
});
```
Equality checked: `withdrawalParams.amount (100n) > feeEstimation.amount (200n)` is FALSE both before and after — i.e., the required invariant `amount debited >= 0` is violated, while `_estimateWithdrawalFee` calling the same subtraction would have thrown `FeeExceedsAmountError` under identical inputs.

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	destinationAddress: string;
	amount: bigint;
	storageDeposit: bigint;
	msg: string | undefined;
	logger?: ILogger;
}): IntentFtWithdraw | IntentNativeWithdraw {
	if (
		params.assetId === NEAR_NATIVE_ASSET_ID &&
		// Ensure `msg` is not passed, because `native_withdraw` intent doesn't support `msg`
		params.msg === undefined
	) {
		return {
			intent: "native_withdraw",
			receiver_id: params.destinationAddress,
			amount: params.amount.toString(),
		};
	}

	const { contractId: tokenAccountId, standard } = utils.parseDefuseAssetId(
		params.assetId,
	);
	assert(standard === "nep141", "Only NEP-141 is supported");
	if (params.msg !== undefined) {
		params.logger?.warn(
			"min_gas is not set for direct-bridge withdrawal with msg, gas consumption is unpredictable",
		);
	}

	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: params.destinationAddress,
		amount: params.amount.toString(),
		storage_deposit:
			params.storageDeposit > 0n ? params.storageDeposit.toString() : undefined,
		msg: params.msg,
		// Only set min_gas when msg is not provided (simple ft_transfer).
		// When msg is present, ft_transfer_call is used and gas consumption is unpredictable.
		min_gas: params.msg == null ? MIN_GAS_AMOUNT : undefined,
	};
}
