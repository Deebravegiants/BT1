Confirmed: the HMAC on webhook requests covers only `@raw_body` via `to_signable_string` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers and are never included in the signed content [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body HMAC) and then forwards `request.shop` unchanged to the app's handler as the tenant identifier [3](#0-2) .

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies solely that the body bytes were signed by Shopify with the app's secret. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are taken straight from unauthenticated HTTP headers and are never part of the signed material. `Registry.process` trusts `request.shop` as the tenant identity forwarded to the app's `WebhookHandler` without any binding to the HMAC-verified body.

### Finding Description
The equality that should hold is: `shop value cryptographically bound by HMAC == shop value passed to the app's webhook handler`. In this gem, the HMAC only binds the body bytes (`to_signable_string` → `@raw_body`), not the header-derived `shop`, `topic`, or `webhook_id` [4](#0-3) . `Registry.process` raises only if the body HMAC fails; it then reads `request.topic`, `request.shop`, `request.webhook_id`, `request.api_version` from headers and passes them straight into `WebhookMetadata` handed to the app-registered handler [3](#0-2) .

Since Shopify computes the HMAC as `HMAC-SHA256(secret, raw_body)` and the gem's validator recomputes the exact same digest over the same `raw_body` (see `HmacValidator.validate_signature`/`compute_signature` [5](#0-4) ), any request with a body/HMAC pair that was legitimately produced by Shopify for the attacker's own store will pass verification unchanged even if the `X-Shopify-Shop-Domain` header is swapped to a victim shop domain, because that header plays no role in `to_signable_string`.

### Impact Explanation
An unprivileged internet user who owns/installs the app on their own development or trial store receives legitimately HMAC-signed webhook deliveries for events they can trigger for their own shop (e.g., `app/uninstalled`, `shop/update`, `customers/data_request`, or any topic whose payload content they can influence). By capturing one such `(raw_body, hmac-sha256)` pair and replaying it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain, the request still passes `HmacValidator.validate` because that check is body-only. `Registry.process` then invokes the app's handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain and `body` equal to attacker-influenced content, breaking the equality between the tenant the HMAC actually authenticates (the attacker's shop, since it's their secret-bearing installation delivering the payload) and the tenant identity the app trusts to key its per-shop data/actions. If the host application uses `WebhookMetadata#shop` to select which shop's records to update/delete (a documented, expected usage per the webhook processing flow), this yields cross-tenant data mutation/spoofing under the app's own trusted webhook channel.

### Likelihood Explanation
Requires the attacker to install/operate the app on any shop they control (a normal capability for merchants/attackers of a public app) and to control or predict body content for at least one webhook topic — no `api_secret_key`, access token, or other Shopify credential is needed, and no interaction with the app's OAuth flow is required. The `shop-domain` header value is fully attacker-controlled at the HTTP layer since it is never covered by the signature.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed material verified against the body, or independently verify that `request.shop` corresponds to an already-known/authorized shop for that specific `webhook_id`/subscription before invoking handlers. At minimum, document/require that `WebhookMetadata#shop` must not be trusted as an authenticated tenant identifier unless the header is bound into the signature.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `customers/data_request`) so Shopify sends a real request with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture `B` and `H` from the attacker's own server logs (fully accessible, since it is the attacker's own installation).
3. Replay to the victim app's webhook endpoint with headers `X-Shopify-Topic: customers/data_request`, `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, and body `B`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `B` against `H`, both of which are unchanged and valid [1](#0-0) .
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "customers/data_request", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` [6](#0-5) , causing the app to act on `victim-shop.myshopify.com`'s tenant data using attacker-supplied body content, despite the HMAC never having authenticated that shop identity.
