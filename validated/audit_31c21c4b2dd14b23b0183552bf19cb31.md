### Title
Division-by-zero panic (unwrap on `checked_div`) in `calc_take_pnl` reachable from Deposit/Withdraw/WithdrawPnl/Swap - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` performs an unchecked `checked_div` on the pool's normalized pc reserve (`x1`) inside `.unwrap()` calls, without first proving `x1 != 0`. This function is invoked from every liquidity/pnl/swap-adjacent code path (`process_deposit`, `process_withdraw`, `process_withdrawpnl`, and the swap handlers that update pnl accounting), meaning any account state that drives the normalized pc reserve to zero causes a runtime panic instead of a clean error, aborting the transaction unconditionally for as long as that state persists.

### Finding Description
`calc_take_pnl` computes `y2` as: [1](#0-0) 
```
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
```
`x1` is the normalized total pc amount (`total_pc_without_take_pnl` scaled by `sys_decimal_value`), passed in by every caller: [2](#0-1) 

If `x1` is `0` (i.e., the pool's pc-side reserve, net of pnl already taken, is zero) and the branch condition `pool_pc_amount.checked_mul(pool_coin_amount) >= calc_pc_amount.checked_mul(calc_coin_amount)` is satisfied (trivially true when both sides evaluate to `0`), execution reaches `checked_div(x1)` with a zero divisor. `checked_div` returns `None` in that case, and the subsequent `.unwrap()` panics, which aborts the Solana transaction with a runtime panic rather than a controlled `ProgramError`.

Because `calc_take_pnl` is invoked unconditionally at the top of `process_deposit`, `process_withdraw`, `process_withdrawpnl`, and the pnl-accounting portion of the swap instructions (all four swap variants update `state_data`/pnl bookkeping through the same accounting path), once a specific `AmmInfo`/`TargetOrders` pair reaches a state where the normalized pc reserve is `0`, **every subsequent instruction touching that pool** (deposit, withdraw, withdrawpnl, and swaps) will panic and revert. This can permanently strand LP and user funds already deposited in the pool's vaults, because no instruction that could recover the pool (all of which route through `calc_take_pnl`) can execute again.

This is conceptually the same bug class as CVE-2021-3443: a decoder/processor dereferences/operates on a component (here, the normalized reserve `x1`) without validating that the reference is non-null/non-zero before use, causing an application crash on a specially/naturally reachable state, rather than a graceful error.

### Impact Explanation
If reserves can reach the zero-`x1` state through legitimate pool activity (e.g., proportional withdrawal draining the pc side to zero while coin side and `TargetOrders.calc_pnl_x/y` are also zero, satisfying the `>=` branch), any subsequent call into `calc_take_pnl` panics. Since deposit, withdraw, and withdrawpnl are the *only* instructions capable of moving funds back out of or into the pool, and they all panic in that state, this results in permanent freezing of user/LP funds trapped in the amm coin/pc vaults — a Medium/High-severity outcome per the rules (permanent freezing of funds), reached via ordinary transactions from an unprivileged swapper/LP with attacker-controllable trade sizing to drive reserves toward the zero-reserve edge case.

### Likelihood Explanation
Reaching exactly `x1 == 0` requires draining the normalized pc reserve to zero while the `checked_mul` comparison also holds — a specific, narrow, adversarially-achievable edge case (e.g., a user submitting withdraw/swap instructions sized to exhaust the pc vault). This is plausible for a determined low-privilege attacker who can choose amounts freely in `Withdraw`/`SwapBaseIn`/`SwapBaseOut` instructions, but requires precise state manipulation, so likelihood is assessed as low-to-moderate rather than trivial.

### Recommendation
Replace the unchecked `.unwrap()` calls in `calc_take_pnl` (particularly the `checked_div(x1)` on line 208, and the other paired `checked_mul`/`checked_div`/`checked_sub` unwraps in the same function) with explicit zero/`None` checks that return a defined `ProgramError`/`AmmError` (e.g., `AmmError::CalculationExRateFailure` or similar) instead of panicking. Additionally, guard the pnl-taking branch with an explicit `x1 != 0` (and `y1 != 0`) check before entering the sqrt/division logic.

### Proof of Concept
Conceptual PoC (state-dependent, not code-verified against a live cluster):
1. Attacker (or any LP) submits `Withdraw` instructions sized to drive `total_pc_without_take_pnl` (and thus `x1` after normalization) to `0`, while `TargetOrders.calc_pnl_x` is also `0` (e.g., freshly initialized pool or pool where prior pnl was fully withdrawn).
2. Once the pool state satisfies `x1 == 0` and the `pool_pc_amount.checked_mul(pool_coin_amount) >= calc_pc_amount.checked_mul(calc_coin_amount)` condition (true since both sides are `0`), any subsequent `Deposit`, `Withdraw`, `WithdrawPnl`, or swap instruction against this `AmmInfo`/`TargetOrders` pair calls `Processor::calc_take_pnl`, which executes `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` with `x1 == 0`.
3. `checked_div` returns `None`; `.unwrap()` panics, aborting the transaction and leaving the pool permanently unusable for any instruction that reaches this code path, freezing any remaining LP/vault balances.

Note: I was not able to fully trace every guard along `process_deposit`/`process_withdraw` to conclusively confirm that no earlier check prevents `x1` from reaching exactly `0` in practice (e.g., minimum-liquidity constraints elsewhere in `math.rs`); this would need to be confirmed with a live/simulated transaction trace, which is beyond what static code reading can fully verify here.
