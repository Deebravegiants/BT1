### Title

Malicious swap routes can append unauthorized wallet-token transfers to a signed swap authorization - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary

`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept attacker-selected swap bytes and forward them to the configured router while the account owner’s authorization is active. [1](#0-0)  A route-selected third-party venue can add a `token.transfer(victim, attacker, amount)` beneath the victim’s `swap_collateral` authorization; simulation records it as an authorization child, and it executes if the victim signs the displayed tree. [2](#0-1) [3](#0-2) 

### Finding Description

The controller authenticates `caller.require_auth()` and verifies ownership or delegation, but does not constrain the callee graph reachable through opaque `swap` bytes. [4](#0-3) [5](#0-4)  `swap_tokens` snapshots only the controller’s input/output balances, authorizes exactly the controller-to-router input transfer, invokes `execute_strategy`, and later checks only controller-side overspend and positive output. [6](#0-5)  Neither measurement nor the final account-risk gate inspects child calls that route-selected code causes the caller to authorize outside the routed amount. [7](#0-6)  The repository’s live authorization-tree test records the rogue wallet transfer as a child of `swap_collateral`, drains all `WALLET_BALANCE` units from Alice to the attacker, and still deposits the fair swap output. [3](#0-2) 

### Impact Explanation

A user can lose arbitrary wallet-token balances unrelated to the supplied lending collateral if their wallet signs the simulation-produced authorization tree without decoding every child invocation. [2](#0-1)  The loss is not bounded by `amount_in`, router minimum output, collateral value, or account solvency because the stolen transfer references the victim as `from` and the attacker as `to`. [8](#0-7) 

### Likelihood Explanation

An unprivileged attacker can supply a malicious route to a victim through a quote or trading interface; the victim need only execute the reachable `swap_collateral` path and approve the poisoned authorization tree. [9](#0-8) [10](#0-9)  Honest enforcement prevents an unsigned rogue transfer, so exploitation depends on wallet UX or user failure to reject the unexpected child authorization rather than a leaked private key. [11](#0-10)  This matches the report’s malicious-transaction/signing class rather than private-key compromise: the contract exposes a path by which unrelated wallet authority can be included in the signed operation. [12](#0-11) 

### Recommendation

Constrain every venue/pool callable through strategy routes to a protocol-maintained allowlist and reject opaque or dynamically supplied route destinations. [13](#0-12)  Wallets and integrations should also hard-fail any `multiply`, `swap_debt`, `swap_collateral`, or `repay_debt_with_collateral` simulation whose caller authorization contains children other than the expected token pull, while route generation should prove that venue calldata cannot request unrelated token transfers. [2](#0-1) 

### Proof of Concept

1. Create a debt-free Alice account with USDC collateral and an unrelated wallet-token balance. [14](#0-13) 
2. Point the configured swap aggregator at a router double whose route decodes an attacker-controlled `hop_pool`, `token_in`, `token_out`, and `min_out`. [15](#0-14) 
3. Give the attacker’s `RogueHopPool` a plan containing `(victim, wallet_token, attacker, amount)` and make its `swap` function call `token.transfer(victim, attacker, amount)`. [16](#0-15) 
4. Build `swap_collateral(caller=alice, account_id, current=USDC, amount=50_000_000_000, new=ETH, swap=route_through_rogue_pool)` from the route fields. [17](#0-16) 
5. In recording mode, the simulated authorization tree contains a `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` child beneath Alice’s `swap_collateral` root; Alice’s wallet balance becomes zero and the attacker receives `WALLET_BALANCE`. [18](#0-17) 
6. In enforcing mode, signing the same poisoned child makes the transfer succeed; omitting it makes the host reject the operation before any wallet token moves. [19](#0-18)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
