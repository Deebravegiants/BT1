### Title
Double-entry (balance-aliased) token lets `balanceDif` be satisfied twice for one real transfer, minting unbacked shielded UTXOs — (File: `contracts/Hinkal.sol` :: `transact`)

### Summary
`Hinkal.transact` measures value movement per `erc20TokenAddresses[i]` purely via `getBalancesForArray`/`balanceOf` snapshots taken before and after the external action, and separately checks, per index, that `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount`. Neither Solidity nor the circuit verifies that distinct entries of `erc20TokenAddresses` correspond to economically independent token balances — the circuit's `distinctErc20AddressChecks` only forces the numeric addresses to differ, not that their `balanceOf(Hinkal)` values are independent. An attacker who deploys a "double-entry" token pair (two distinct contract addresses that read/write the same underlying balance storage) can make one real transfer satisfy the per-index equality twice, minting a second, unbacked shielded UTXO.

### Finding Description
The claimed equality is:
`sum(amountChanges) + sum(on-chain UTXO amounts minted) == net real tokens entering Hinkal`

Trace in `contracts/Hinkal.sol`:
- `oldBalances`/`newBalances` are snapshotted via `getBalancesForArray(circomData.erc20TokenAddresses)`, which calls `getERC20OrETHBalance` → `IERC20(addr).balanceOf(address(this))` for each listed address [1](#0-0) .
- For each index `i`, `balanceDif` is computed from these snapshots and checked against `(onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount`, where `utxoAmount` sums entries of the `utxoSet` returned by the external action whose `erc20Address` equals `erc20TokenAddresses[i]` [2](#0-1) .
- The only uniqueness constraint on `erc20TokenAddresses` is enforced inside the circuit as a raw field-element inequality (`distinctErc20AddressChecks`), not an economic/storage independence check [3](#0-2) .

Attack: the attacker deploys two distinct ERC20 contract addresses, `tokenA` and `tokenB`, that alias the same underlying balance storage (any transfer/mint affecting one address is simultaneously visible via `balanceOf` on the other — a "double-entry" token). The attacker builds `circomData.erc20TokenAddresses = [inputToken, tokenA, tokenB]` for a LiFi swap external action:

- Index 0/1 run the normal swap in `ExternalActionSwap.swap`: the router swaps into `outputToken = tokenA`, and `amountToSendToHinkal` of `tokenA` is transferred to Hinkal, then returned as a single `UTXO{erc20Address: tokenA, amount: amountToSendToHinkal}` [4](#0-3) . This satisfies the index-1 (`tokenA`) equality legitimately: `balanceDif == 0 (amountChanges) + utxoAmount`.
- Index 2 (`tokenB`) is an extra slot the attacker adds purely to exploit the aliasing. Because `tokenA` and `tokenB` share the same real balance, the same swap-transfer also raises `balanceOf(Hinkal, tokenB)` by `amountToSendToHinkal`, even though the external action's `utxoSet` contains no entry with `erc20Address == tokenB` (`utxoAmount == 0` for this index — this is exactly the "external action returns an empty UTXO set for that token" case the question describes).
- The attacker sets `circomData.amountChanges[2] = amountToSendToHinkal` and `onChainCreation[2] = false`. The circuit only requires `inTotal[2] + amountChanges[2] === outTotal[2]` [5](#0-4) ; with `inTotal[2] = 0`, the attacker's own proof trivially creates an off-chain output UTXO worth `amountToSendToHinkal` of `tokenB`, fully self-authorized (no need for anyone else's nullifiers).
- On-chain, the index-2 check `balanceDif(tokenB) == amountChanges[2] + 0` now holds automatically because of the aliasing, with no additional real transfer.

Net effect: one real transfer of `amountToSendToHinkal` backs two minted claims — the genuine on-chain UTXO for `tokenA` and a brand-new off-chain shielded UTXO for `tokenB` — doubling the shielded value minted relative to value actually received by the vault. The existing guards (`performHinkalChecks`, `verifyProof`, slippage checks, `distinctErc20AddressChecks`) do not catch this because they all operate on the raw address values and per-index balance deltas, none of which assume or verify that two different addresses cannot represent one real balance.

### Impact Explanation
This mints shielded value without backing, directly matching the Critical category ("minting shielded value without backing / protocol insolvency"). Each execution mints an extra unbacked UTXO equal to the real value moved in that transaction; the attacker can later withdraw or spend this UTXO, extracting real value from other users' deposits in the vault. The attack is repeatable each time the attacker triggers a swap with a freshly (or the same) deployed double-entry token pair included as an extra `erc20TokenAddresses` slot.

### Likelihood Explanation
Preconditions are fully within the stated unprivileged-attacker capabilities: deploying arbitrary token contracts, crafting `CircomData`/`Dimensions`, choosing `erc20TokenAddresses` ordering/length, and generating a valid proof for one's own UTXOs. No relayer privilege, oracle assumption, or victim funds are required to trigger it (though the ultimate cash-out requires the unbacked UTXO to later drain real assets from the shared pool). The only engineering cost is deploying a token pair with shared/aliased balance storage (e.g., a lightweight proxy/facade contract that forwards `balanceOf`/transfer effects to a shared storage contract), which is feasible with basic Solidity.

### Recommendation
Do not trust `erc20TokenAddresses` uniqueness/independence purely from field-element inequality. Either (a) require all balance snapshots and transfers to be resolved through a single canonical registry/allowlist of tokens vetted for standard, independent ERC20 balance semantics, or (b) restructure the accounting so that the vault's solvency check aggregates a single global `balanceOf` per unique underlying asset (not per listed address) and cross-checks total minted UTXO value against total tokens actually received in that transaction, rather than per index with independent snapshots that can be aliased.

### Proof of Concept
Foundry test plan:
1. Deploy `DoubleEntryToken` — a pair of contract addresses `tokenA`/`tokenB` (or a proxy `tokenB` delegating storage reads/writes to `tokenA`) sharing one balance mapping.
2. Deploy `Hinkal`, `HinkalHelper`, `LifiExternalAction`, and a mock LI.FI router that transfers `amountToSendToHinkal` of `tokenA` back to the caller on `callRouter`.
3. Craft `circomData` with `erc20TokenAddresses = [inputToken, tokenA, tokenB]`, `onChainCreation = [true,true,false]`, `amountChanges[2] = amountToSendToHinkal`, and locally generate a valid proof satisfying `inTotal[2] + amountChanges[2] === outTotal[2]` with `inTotal[2]=0`.
4. Call `Hinkal.transact(...)`.
5. Assert: (a) `balanceDif` for index 1 (`tokenA`) and index 2 (`tokenB`) are both `amountToSendToHinkal`, though only one real transfer occurred; (b) total value minted (on-chain UTXO for `tokenA` + off-chain UTXO for `tokenB`) equals `2 * amountToSendToHinkal`; (c) net real ERC20 units received by Hinkal (via the underlying shared storage) equals only `amountToSendToHinkal` — i.e. `sum(minted UTXO value) > net tokens entering Hinkal`, confirming the equality violation.
