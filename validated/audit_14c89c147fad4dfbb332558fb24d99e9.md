### Title
Webhook shop-domain identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used to dispatch webhook payloads from an HTTP header that is never included in the HMAC-verified byte range, breaking the intended binding `HMAC-verified bytes == bytes acted on for tenant attribution`.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identifier passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`, i.e., only the body for webhooks: [4](#0-3) 

Equality that should hold but does not: `bytes verified by HMAC == bytes used to attribute the webhook to a shop`. In this implementation: `HMAC covers {raw_body}` while `tenant attribution uses {shop-domain header}`, which are disjoint. Because HMAC validation only proves the *body* originated from a request signed with the app's secret, and the app's own legitimately-received webhook body/HMAC pair (from its own installed shop) can be replayed with an arbitrary `shop-domain` header value, `Registry.process` will pass HMAC validation and dispatch to the handler with a forged `shop` value, while the body content still matches the originally signed shop.

### Impact Explanation
Any application built on this gem that trusts `WebhookMetadata#shop` (the documented, public attribute returned to the handler) to select the tenant record/session/database row to act on — a very common pattern for merchant webhook processing — can be made to apply another shop's legitimate webhook body under an attacker-chosen shop identity, or vice versa: attribute a request to a victim shop using a payload the attacker fully controls the surrounding transport of. This is a cross-tenant identity-binding break: the HMAC guarantees the *payload* is authentic for *some* shop, but the gem lets an unauthenticated header decide *which* shop that payload is credited to, which is exactly the class of bug in the report (validation/binding computed over the wrong set of bytes/fields allowing a party without the shared secret to control an unverified but security-relevant field).

### Likelihood Explanation
Exploitation requires only capturing or otherwise obtaining one legitimately-signed webhook body+HMAC pair (webhooks are delivered over plain HTTP(S) to the app's public endpoint controlled by the attacker/app operator, not secret in transit to any third party who can see request logs, proxies, or a malicious/compromised endpoint owner in a multi-tenant deployment) and then re-submitting it with a different `shop-domain` header value — no access to `api_secret_key` is needed to forge the header, since the header is never covered by the HMAC. Given this gem explicitly documents `shop` as the trusted tenant identifier surfaced to the handler, most integrators will rely on it directly.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) values into the HMAC-verified signable string, or otherwise require the caller/host framework to independently corroborate the shop header against a value obtained through an authenticated channel (e.g. the registered webhook endpoint per shop) before trusting it for tenant dispatch. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be used as the sole tenant-selection key without additional verification.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (who can observe/replay this exact request, e.g. via a logging proxy, shared infra, or because they operate the receiving endpoint in a multi-tenant SaaS) resends the identical body `B` and identical HMAC header, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches — validation passes because the shop header is not part of the signed string: [3](#0-2) [1](#0-0) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, causing the host app to act on `B`'s contents under `shop-b`'s tenant context despite the payload never having been signed for `shop-b`.
