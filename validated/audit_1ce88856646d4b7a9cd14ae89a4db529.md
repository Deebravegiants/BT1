### Title
Unallowlisted route venues let attacker-supplied pool/token contracts execute under the caller's auth tree and drain the caller's wallet - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
CVE-2025-55911's class is "server fetches/invokes an attacker-controlled resource locator." The XOXNO Lending analog is the strategy-route payload: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position` all forward a caller-supplied `StrategySwap`/`swap_xdr` to the configured router, and the router (and the test double for it) invokes whatever `pool`/`token` addresses the payload names with no venue/pool allowlist. Arbitrary third-party code therefore runs inside the call stack beneath the caller's `require_auth` root, and a token `transfer` it issues from the caller is recorded as a child of the caller's authorization entry — it executes if the caller signs that (simulator-produced) tree.

### Finding Description
`swap_tokens` authorizes only one exact `token_in.transfer(controller, router, amount_in)` via `authorize_transfer_as_current` and then calls `router.execute_strategy(controller, amount_in, swap)` with the raw caller payload [1](#0-0) . The controller validates only measured input spend and positive output [2](#0-1)  — it never inspects which contracts the route touches. Inside the router, `execute_op` resolves `hop.pool`, `hop.token_in`, `hop.token_out` purely from the payload's `assets` table and dispatches the venue call [3](#0-2) . The threat model states it plainly: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." [4](#0-3)  The regression test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` proves the mechanics end-to-end: a rogue "pool" named by the route calls `token.transfer(alice, attacker, WALLET_BALANCE)`, the simulation records that transfer as a sub-invocation of Alice's `swap_collateral` auth entry, and Alice's wallet is emptied while her position still receives the fair swap output [5](#0-4) .

### Impact Explanation
Theft of user funds. A victim who signs a simulator-produced authorization tree for `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply`/`flash_position` (or direct `execute_strategy`) can lose every token balance their address holds — not just the routed input — because the malicious pool/token contract's `transfer(from=victim)` rides inside the signed tree. The payload `min_out` and the controller's measured-output/final-risk gates give zero protection since they only bound routed funds.

### Likelihood Explanation
Medium. Exploitation needs the victim to sign a poisoned auth tree rather than an honest one — Soroban enforcing mode requires the exact tree — but standard client flows sign whatever `simulateTransaction` returns, and simulation faithfully records the injected child entry, so a malicious or compromised route-quoting front-end can deliver a fully valid-looking transaction. The attack requires no privilege, no leaked key, and no router compromise: the attacker only supplies XDR that names attacker-deployed contracts, which the unprivileged strategy entrypoints accept by design.

### Recommendation
Maintain an on-chain allowlist of venue pool contracts (governance-managed, like the Blend pool approval list) and reject hops whose `pool` is not listed; alternatively or additionally, pin each venue adapter to a router-validated pool factory and verify `token_in`/`token_out` are real Stellar Asset Contracts the controller already custodies. At minimum, clients must decode the route they sign and refuse any authorization tree whose children exceed the single expected input transfer, as the threat model already instructs.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the full chain: `UnlistedPoolRouter::execute_strategy` invokes `env.invoke_contract(&route.hop_pool, "swap")` on the attacker-named pool [6](#0-5) , `RogueHopPool::swap` executes `transfer(alice → attacker, WALLET_BALANCE)` [7](#0-6) , and the recorded auth tree contains the theft as a sub-invocation of Alice's `swap_collateral` root, draining her wallet while she still receives the fair ETH output [8](#0-7) . The real router reproduces the shape via payload-controlled `assets` indexes in `execute_op` and venue `invoke_contract` calls such as `aquarius/pool.rs::invoke_pool_swap` [9](#0-8) .

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
```
