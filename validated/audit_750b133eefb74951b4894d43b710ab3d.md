## Finding

The webhook HMAC verification path in this gem authenticates only the raw request body — it never binds the `shop` (tenant identifier) that the HMAC-validated request is subsequently routed under. This is the concrete "field acted on but not covered by the HMAC" pattern from the rules.

### Title
Webhook `shop` tenant identifier is not bound to the HMAC, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that HMAC-over-body relationship, then dispatches the handler using the unauthenticated `request.shop` value as the tenant identifier [3](#0-2) .

### Finding Description
The equality the code should enforce is: `hmac == HMAC(secret, body ‖ shop)` (or otherwise bind the tenant), so that the `shop` a host application acts on is the same `shop` that was cryptographically authenticated. Instead the code enforces only `hmac == HMAC(secret, body)` [4](#0-3) , and `shop` is taken verbatim from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no signature coverage [5](#0-4) .

Critically, `Context.api_secret_key` — the value used to compute/verify this HMAC — is a single, app-wide secret shared across every shop that has the app installed [6](#0-5) . It is not shop-specific. Contrast this with `Auth::Oauth::AuthQuery`, where the same `HmacValidator` is used but `shop` **is** included in `to_signable_string` and thus bound to the signature [7](#0-6) . The webhook path lacks this equivalent binding.

Before the attacker's request: `hmac` authenticates `(body)` only; `shop` is an unauthenticated header value.
After the attacker's request sequence: `Registry.process` still returns `hmac` valid (body unchanged) and passes an attacker-chosen `shop` value straight into `WebhookMetadata` handed to the host application's handler [8](#0-7) .

### Impact Explanation
Because the app secret is shared across all shops, any unprivileged internet user who can get the app installed on a shop they control (which is the normal, unprivileged onboarding flow for any public/multi-tenant Shopify app) can capture a legitimate webhook delivery (`body` + valid `hmac`) for their own shop, then replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (it never looked at the shop header), and the host application's webhook handler receives `WebhookMetadata` claiming the payload belongs to the victim shop. Any host application that trusts `data.shop` (as the gem's own documentation instructs: "shop, String - The shop domain of the webhook" [9](#0-8) ) to select which tenant's session/record to update will apply attacker-controlled data to the wrong tenant — a cross-tenant confusion/injection.

### Likelihood Explanation
Getting the app installed on an attacker-controlled shop is normal, unprivileged behaviour for public Shopify apps (no credentials, tokens, or social engineering required). Capturing one's own webhook deliveries and replaying them with a modified header is straightforward for anyone who can send HTTP requests to the app's webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`) into the HMAC-covered signable string for webhook requests, or otherwise re-derive the shop identity from a value that Shopify signs (Shopify does not sign the shop header, so the correct fix is for the gem to require app developers cross-check `request.shop` against an independently-verified session before trusting the payload, and to document this gap explicitly). At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to make clear that `shop` is unauthenticated and must not be used as the sole tenant key.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed.
# They capture a legitimate webhook delivery Shopify sent them:
captured_body = '{"id":123,"note":"hi"}'
captured_hmac = "shopify_computed_hmac_over_captured_body"  # valid, shared api_secret_key

# Attacker replays it against the same app's webhook endpoint, but
# swaps the shop-domain header to point at a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,       # still valid! body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only body+secret checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: captured_body, ...))
# Host app now applies attacker-controlled body to victim-shop's tenant record.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
