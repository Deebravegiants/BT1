# No vulnerability found for this question.

**Rationale:**

The `Plugin` struct in `plugin/pkg/admission/serviceaccount/admission.go` has no authorizer dependency at all — it only holds a `client`, a `serviceAccountLister`, and mutation/validation flags [1](#0-0) . `Validate` only checks that the referenced ServiceAccount object exists via `getServiceAccount` and, if `enforceMountableSecrets` is set, that referenced secrets are allowed by that SA [2](#0-1) . `Admit` mounts the SA token whenever `MountServiceAccountToken` is true and automount isn't disabled, again with no identity/authorization check on who is allowed to "use" that SA [3](#0-2) .

This is not a bug introduced in this code — it reflects the documented Kubernetes design: **RBAC does not restrict which `serviceAccountName` a pod may reference**; any principal permitted to `create` pods in a namespace can specify (and thereby obtain a mounted token for) any ServiceAccount that exists in that same namespace. The actual privilege boundary is the namespace-scoped `create pods` RBAC permission, which is enforced by the kube-apiserver's authorizer *before* admission runs, not by this plugin. There is no "authority to use a specific SA" concept enforced anywhere in core Kubernetes admission (that model — restricting SA usage per-identity — was only ever implemented via the deprecated PodSecurityPolicy `use` verb or external admission webhooks/policies like Kyverno/OPA, neither of which is in scope here).

Since:
1. The attacker is scoped to a single namespace with minimal RBAC (per the rules, "ordinary authenticated user... with minimal namespace-scoped RBAC"), and
2. Using an SA that already exists in that same namespace via `serviceAccountName` is expected, by-design behavior, not a broken invariant, and
3. There is no authorization check being bypassed here — none exists in this plugin because none is expected to exist —

this does not meet the bar of "protected field/identity set by a requester lacking authority" as a genuine control-plane compromise. It is standard, well-known Kubernetes behavior rather than an admission bypass.
