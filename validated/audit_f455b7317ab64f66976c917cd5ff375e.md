### Title
Same-asset batched withdrawals to different destinations are misattributed by `findMatchingWithdrawal` (assetId-only matching) - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
When a caller batches two `WithdrawalParams` with the same `assetId` but different `destinationAddress` values in a single `signAndSendWithdrawalIntent`/`processWithdrawal` call, `PoaBridge.describeWithdrawal` (via `findMatchingWithdrawal`) matches the PoA withdrawal-status entry purely by `nep141:${near_token_id} === assetId`, ignoring `index`/`destinationAddress`/amount. Both batch indices therefore resolve to the identical status entry and `txHash`, even though the two withdrawals paid different recipients.

### Finding Description
The broken equality: `describeWithdrawal({index: 0, withdrawalParams: {assetId: X, destinationAddress: A}}).txHash` should equal the destination-chain outcome for the withdrawal that paid address `A`, and must differ from the outcome for index `1` that paid address `B`. Instead, both calls resolve to whichever single withdrawal-status entry in the POA API response has `near_token_id` matching `assetId`, because `findMatchingWithdrawal` only compares `nep141:${w.data.near_token_id} === assetId` [1](#0-0) , with no differentiation on `index`, `destinationAddress`, or `amount`. The function's own doc comment acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported" [2](#0-1) .

Reachable path: `IntentsSDK.signAndSendWithdrawalIntent` accepts `WithdrawalParams[]` in batch mode with no de-duplication or same-asset restriction [3](#0-2) , and `PoaBridge.validateWithdrawal` only validates a single withdrawal's address/amount/min-amount in isolation — it never checks for collisions with sibling withdrawals in the same batch [4](#0-3) . After settlement, `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` builds one `WithdrawalIdentifier` per index via `createWithdrawalIdentifiers` and calls `bridge.describeWithdrawal` per index independently [5](#0-4) , each hitting the same flawed `findMatchingWithdrawal`. A parallel copy of the same bug exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` [6](#0-5) .

Existing guards do not prevent this: `validateAddress`/`compareAddresses` only check a single destination against the token's own on-chain address [7](#0-6) ; none of them compare sibling withdrawals in a batch against each other. There is no assertion anywhere blocking two same-`assetId` entries in one `WithdrawalParams[]`.

### Impact Explanation
Both withdrawal indices report the same `status`/`txHash` to the integrator despite crediting two different destination addresses on-chain. An integrator that credits/refunds a user based on the SDK-reported `txHash` per index will attribute the same completion (and the same destination tx hash) to both recipients, i.e., it can double-credit one recipient's completion status/hash to both indices while leaving the other index's true outcome unreported. This is a status/hash misreport that can cause an integrator to credit or refund twice — matching the High severity category ("a status or hash misreport making an integrator credit or refund twice"). It does not itself move funds or forge a signature, so it does not meet the Critical bar (no fund misrouting, no replay, no fee drain caused by this code path).

### Likelihood Explanation
Preconditions: an unprivileged caller (or an integrator forwarding attacker-controlled batch parameters) simply needs to submit a batch with two (or more) `WithdrawalParams` sharing the same `assetId` (a PoA-bridge-routed token) but different `destinationAddress`. No special permissions, no contract admin, no relayer collusion needed — this is fully reachable via the public `signAndSendWithdrawalIntent`/`processWithdrawal` batch API. It is deterministic and repeatable on every such batch, not a one-off race condition.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate among multiple candidates for the same `assetId`, e.g. by matching amount (accounting for the relayer fee) and/or tracking already-consumed matches per call so the same status entry cannot be returned twice, or by rejecting/serializing batches containing duplicate `assetId`s destined for the PoA bridge until the POA API supports per-withdrawal correlation.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
