### Title
Swap output is only checked for a non-zero slippage floor, never enforced against actual `swappedAmount` - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`ExternalActionSwap.swap()` requires that a caller-supplied slippage floor (`circomData.slippageValues[1]`) be non-zero, but never compares it to the amount actually returned by the external router (`swappedAmount`). This means the user-signed slippage protection committed into the ZK proof's public inputs is never validated on-chain, letting the actual value the user receives diverge arbitrarily from what they authorized — precisely the class of loss described in the external report ("price moves between request and fulfillment, no partial refund/enforcement").

### Finding Description
`circomData.slippageValues` is included in `getHashedCalldata1`, which feeds `calldataHash`, which in turn is bound into `getSignedMessageHash` and ultimately into the public input vector verified by the Groth16 proof [1](#0-0) [2](#0-1) . This makes it look like the user has cryptographically committed to (and the prover/signer has authorized) a real slippage floor for the swap.

However, in `ExternalActionSwap.swap()` the only use of that value is a non-zero check: [3](#0-2) 
after which the router is called and `swappedAmount` is used directly to compute fees and the output UTXO amount, with no comparison such as `require(swappedAmount >= circomData.slippageValues[1])`: [4](#0-3) 

The balance equation the circuit enforces is over `amountChanges`/`inAmounts`/`outAmounts` inside the shielded pool, but the actual token amount produced by the external router call (`swappedAmount`) is an off-chain/on-chain-router-determined value that is passed back into the shielded UTXO (`amountToSendToHinkal`) without ever being checked against the value the user authorized (`slippageValues[1]`). The equality "amount user authorized as minimum ≥ amount actually re-shielded" is never enforced, even though the user's signature/circuit believes it is, because the field exists in the signed/hashed calldata purely as a presence flag.

### Impact Explanation
This is a "value moved by an external action but not properly constrained by the balance equation the prover/signer believes is enforced" bug. A relay/router path returning a substantially reduced output (through price movement, a malicious/compromised router integration, or MEV sandwiching around the swap call) results in the shielded UTXO created for the user containing far less value than the user's signed slippage floor demanded, with no on-chain protection. This is a direct value loss to the user's shielded/in-flight funds during a protocol-mediated swap, meeting the High/Critical bar of "temporary or permanent freezing/theft of user funds" and "executing calls or moving assets ... never authorised" (since the user authorized a floor that is silently ignored).

### Likelihood Explanation
Any transaction that triggers `ExternalActionSwap.swap()` (LI.FI or other swap external actions) with a non-zero-but-unenforced slippage value hits this path; no privileged role is required — the vulnerable check is exercised on every ordinary shielded-swap call, and any adverse output from the router (whether via honest slippage, sandwich attacks, or by controlling `externalActionMetadata`) triggers the loss.

### Recommendation
In `ExternalActionSwap.swap()`, add an explicit check enforcing the floor after the router call, e.g. `require(swappedAmount >= uint256(circomData.slippageValues[1]), "swap output below slippage floor");`, rather than merely checking that the value is non-zero.

### Proof of Concept
1. User submits a shielded swap with `circomData.slippageValues[1] = X` (their expected minimum acceptable output), which gets hashed into `calldataHash`/`signedMessageHash` and proven valid by their ZK proof.
2. `performHinkalChecks` verifies the hash matches and the proof is valid — this only proves the *value X was included in the signed payload*, not that it will be respected.
3. `ExternalActionSwap.swap()` calls `require(circomData.slippageValues[1] != 0, ...)` — passes since `X != 0`.
4. The router call (`callRouter`) returns `swappedAmount << X` (e.g. due to price movement or a sandwich attack around the router trade).
5. No check compares `swappedAmount` to `X`; `amountToSendToHinkal` is computed from the depressed `swappedAmount` and re-shielded as the user's new UTXO.
6. The user ends up with a shielded balance far below their authorized floor, with the loss realized by whoever controlled/benefited from the router execution — matching the report's "user overpays/loses value with no partial refund" scenario, but here fully unenforced on-chain despite an apparent slippage-protection field.
