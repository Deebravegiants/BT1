## Finding: Webhook shop identity not bound by HMAC — cross-tenant webhook spoofing

### Title
Webhook Origin Shop Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The reported EntryPoint.sol bug is about a value (paymaster return data) being *acted upon* by the contract without being *validated* through the same trust mechanism (the try/catch). The same class of bug — a security-relevant field that is used by the application but not bound by the cryptographic check meant to authenticate the message — exists in this gem's webhook processing path: the shop identity attached to an incoming webhook is never covered by the HMAC signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

and `HmacValidator` computes/verifies the signature strictly over that signable string, using the single, app-wide `Context.api_secret_key` (the same secret is shared across *every* shop that installs the app, it is not per-tenant): [2](#0-1) 

`Registry.process` validates only that HMAC-over-body check, then immediately trusts `request.shop` — which is read straight from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are all pulled from headers with no relation to the signed content: [4](#0-3) 

Because `api_secret_key` is identical for all shops that install a given app, and the shop-domain header is excluded from the signed bytes, `verified bytes (body)` ≠ `bytes acted on (shop identity used to attribute the webhook)`. This is the same "field acted on but not covered by the authentication mechanism" class as the reported EntryPoint issue.

### Impact Explanation
Any merchant who has installed the app on their own store is a legitimate holder of valid `(body, hmac)` pairs signed with the app's shared `api_secret_key` (they simply have to trigger any of their own store's webhook deliveries). By replaying that same body/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header, the request still passes `Utils::HmacValidator.validate`, and the handler will process the payload as if it originated from the victim shop. This is a cross-tenant identity confusion: data intended to be scoped to the attacker's own tenant is attributed to another tenant, satisfying the Critical "cross-tenant access" impact category, since the vulnerability lives entirely inside this gem's own webhook-processing logic (`Webhooks::Request` / `Webhooks::Registry`), not in host-application misuse.

### Likelihood Explanation
Likelihood is high for any app that (a) allows self-serve installs (so an attacker can be a legitimate tenant), and (b) whose webhook handlers key off `WebhookMetadata#shop` to select which tenant's records to create/update/delete — a standard pattern this gem exposes to consumers (see `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`). No secret material beyond a legitimately-received webhook is required, and the header is trivially editable by anyone who can POST to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified content, or otherwise cryptographically tie the header-derived shop to the specific installation the webhook was issued for (e.g., cross-check `request.shop` against a shop that is independently known to have an active, matching webhook subscription/session before trusting it), rather than trusting the shop header purely because a body-only HMAC validated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) to capture a valid `(raw_body, x-shopify-hmac-sha256)` pair — this HMAC is valid because it's computed with the same `api_secret_key` used for all shops.
2. Attacker POSTs the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the raw body against the shared secret.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker's forged order data, ...)` and processes it as belonging to the victim tenant.
