### Title
Cross-chain amount truncation in `pallet-hyper-fungible-token`'s `convert_to_balance` permanently burns dust on every inbound HFT transfer - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` divides an incoming ERC20 `U256` amount by `10^(erc_decimals - local_decimals)` with plain integer division, discarding the remainder. When an EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract burns/escrows an exact ERC20 amount and dispatches it to this pallet, any amount that isn't an exact multiple of the decimals scale factor is credited to the beneficiary rounded down, and the truncated remainder is permanently lost — never minted, never refunded, never recoverable by anyone.

### Finding Description
`convert_to_balance` is used in the pallet's `on_accept` inbound handler to convert the ERC20 `Message.amount` (sourced from a remote `HyperFungibleToken.send()` call) into the local asset's balance type: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```

Because Rust/`U256` division truncates toward zero, any inbound amount that is not an exact multiple of `10^(erc_decimals - local_decimals)` is silently floored. On the EVM side, the sender's `HyperFungibleToken.send()` burns/escrows the caller's *exact* requested amount (there is no rounding on burn), and the dispatched `Message.amount` carries that exact value: [2](#0-1) 

So the pallet's `on_accept` credits `beneficiary` strictly less than what was burned on the source chain whenever the low-order digits (below the local chain's precision) are non-zero — e.g. a token bridged from an 18-decimal EVM contract to a 10-decimal local asset truncates any amount whose last 8 decimal digits aren't all zero. This is the exact "interest_ gets rounded down" bug class from the referenced report: a division-by-scale-factor truncation on the *credit* leg of a value-transfer, applied per-transaction and fully attacker/user-controllable (any amount can be chosen to maximize dust loss up to `10^(erc_decimals-local_decimals) - 1` local-precision units, i.e., up to just under one full unit of the finer-grained token, per transfer).

Compare this with the reverse (outbound) direction, `convert_to_erc20`, which *multiplies* up and is therefore lossless: [3](#0-2) 

The asymmetry (multiply-up on send, floor-divide on receive) means value is conserved leaving this chain but not conserved arriving on it — the system is not invariant under a round trip, and repeated dust loss compounds over time with no path to reclaim it. Nothing in `on_accept` checks for a non-zero remainder or reverts/queues it; the loss is silent, matching the audit report's "no revert, straightforward loss to the receiving party."

### Impact Explanation
This is a permanent, protocol-level loss of user funds on the token-bridge mint/burn path (in-scope per the grading rules: "token bridge mint/burn"). Every inbound HFT transfer whose amount isn't a clean multiple of the decimals-scale factor burns the full amount on the source chain but mints/releases a strictly smaller amount on the destination chain. Because `HyperFungibleToken.send()` never rounds down the amount pulled/burned to match what `convert_to_balance` will later reconstruct, a bridging user (or an attacker deliberately choosing dust-maximizing amounts, e.g. `local_unit - 1` in ERC20 terms repeatedly) systematically destroys value with no beneficiary — the pallet's `Assets`/`NativeCurrency` total issuance is reduced across the pair relative to what should be backed, and no accounting entry exists to recover it. Over many transfers this is an unbounded drain, satisfying "concrete theft or permanent freezing of funds" at High severity for any HFT pair where `erc_decimals > local_decimals` (the documented, expected configuration, e.g. BRIDGE token 18-decimal EVM vs 12-decimal nexus).

### Likelihood Explanation
High likelihood: this path executes on every single inbound HFT transfer for any decimals-mismatched pair (the pallet's own docs and the `BridgeToken` contract state this is the standard configuration — "BRIDGE is 12 decimals on nexus... the pallet scales by 10^6"). No special privilege is required; any user calling `send()` on the peer EVM contract with an amount not aligned to the scale factor triggers the truncation, and a malicious actor can trivially choose amounts to always land on the maximum-dust boundary to grief/drain value over repeated transfers.

### Recommendation
Round `convert_to_balance`'s ERC20→local conversion consistently with the burn/escrow side: either (a) require callers to only transfer amounts that are exact multiples of the scale factor (reject the message / hold the remainder in an explicit escrow credited back to the original sender or to a claimable dust pool) instead of silently flooring, or (b) mirror the amount actually credited back into what is burned on the EVM side by having the EVM contract round the input amount down to the destination's precision *before* burning, so the burned and minted amounts always match exactly. At minimum, track the discarded remainder per-transfer and expose a mechanism (e.g., a `DustAccumulated` event and a redemption path) so it isn't permanently and silently destroyed.
