### Title
Operator QR-code authorization bypass via self-declared `signup_extension` flag - ([File: src/plans/mod.rs])

### Summary
`MasterPlan::verify_operator_qr_code` (`src/plans/mod.rs:1543-1578`) short-circuits the backend authorization call whenever `qr_code.signup_extension()` is true, returning a synthetic `LocationData { team_operating_country: "DEV", .. }` as if the backend had validated it. Because `signup_extension()` is derived purely from the content of the QR code the attacker presents to the camera (parsed in `src/plans/qr_scan/user.rs` / `src/plans/qr_scan/operator.rs`), an attacker can craft a QR code that sets this flag and obtain a "valid" operator authorization without any backend call ever succeeding.

### Finding Description
`verify_operator_qr_code` is supposed to authorize an operator QR code "through the backend" per its doc comment (`src/plans/mod.rs:1543`). Its actual logic is:

```rust
if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
    return Ok(Some((0, backend::operator_status::LocationData {
        team_operating_country: "DEV".to_string(),
        ...
    })));
}
``` [1](#0-0) 

`qr_code` is the `qr_scan::user::Data` produced from parsing the raw string scanned from the camera, and `Data::try_parse` in `src/plans/qr_scan/operator.rs` only checks that, when `signup_extension()` is true, a `signup_extension_config` is also present in the same self-reported QR payload: [2](#0-1) 

There is no cryptographic signature, backend round-trip, or any operator-privileged secret involved in setting `signup_extension()` — it is a plain parse of attacker-controlled bytes shown to the camera. The `else` branch — the actual backend call `backend::operator_status::request(qr_code).await` — is completely skipped when the flag is set, meaning the "valid" result is never confirmed by the backend.

### Impact Explanation
This breaks the intended authorization boundary: the function's entire purpose is to gate operator/session start on a backend decision, but a purely local, attacker-suppliable QR-code flag causes it to fabricate an approval (`valid`-equivalent `LocationData`) with zero backend involvement. Depending on how the returned `LocationData`/operator authorization is subsequently used to gate signup start, this could let an unprivileged person start or authorize an Orb signup session without any backend-side permission check — a signup-authorization bypass.

### Likelihood Explanation
Feasibility hinges entirely on whether `signup_extension()` and the "DEV"-mode override path are reachable in the production/shipped build. I could not fully confirm in this session whether this branch is compiled out or additionally gated by a build-time feature flag (e.g. a "data acquisition" build mode) that is unavailable to the class of unprivileged attacker described in this audit's rules. Multiple other files (`src/consts.rs`, `src/bin/orb-core.rs`, `src/plans/idle.rs`, `src/agents/image_uploader.rs`) reference `data_acquisition`/`signup_extension` concepts extensively, suggesting this is an intentional test/data-acquisition mode rather than a code path enabled in normal production signup flows. Given the prompt's explicit exclusion of "test-only cfg paths" and "build/runtime feature flags" requiring more than unprivileged QR presentation, and given I was unable to verify that this branch is reachable in a normal, non-data-acquisition production build purely by presenting a QR code (the question itself frames this as conditional on "build/runtime feature flags OR simply presenting a signup-extension QR code," and the second disjunct's actual gating is unverified), I cannot confirm this is exploitable by a strictly unprivileged attacker without a specific build configuration.

### Recommendation
Restrict `signup_extension()`-based bypass and `operator_qr_code_override` strictly to compile-time-gated non-production builds, and ensure `verify_operator_qr_code` never returns `Some(...)` in production/data-acquisition-disabled builds without a real backend call whose `valid == true` response is used.

### Proof of Concept
Not confirmable as a concrete PoC given available evidence: I was unable to verify from the indexed code whether the `signup_extension`/override bypass path in `verify_operator_qr_code` is actually compiled into and reachable in the standard production build (versus being restricted to a data-acquisition/test build feature), which is required to establish that an unprivileged attacker can trigger it merely by presenting a QR code. A definitive PoC/unit test would need to assert, in a production feature-flag configuration, that `MasterPlan::verify_operator_qr_code` given a QR string satisfying `signup_extension()` (with `try_parse` success per `src/plans/qr_scan/operator.rs:40-45`) never returns `Some(...)` unless `backend::operator_status::request` was actually invoked and returned `valid: true` — this requires further investigation of `src/consts.rs` and build feature definitions (e.g., via `orb-core` binary/cli flags) to confirm reachability, which was not completed in this session.
