### Title
`AuroraEngineBridge.describeWithdrawal` unconditionally reports "completed" without checking the Aurora Engine sub-call outcome - ([File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts])

### Summary
`AuroraEngineBridge.describeWithdrawal` is hard-coded to return `{ status: "completed", txHash: null }` with no arguments and no on-chain check whatsoever. It never inspects the NEAR transaction outcome, let alone the nested Aurora Engine receipt that actually credits the destination virtual-chain account, so the reported status can never reflect reality — it is always "completed" regardless of whether the underlying credit succeeded.

### Finding Description
The claimed equality is: `describeWithdrawal(wid).status == outcome of the Aurora Engine credit for withdrawal wid`. Tracing the code:

- `createWithdrawalIdentifiers`/`watchWithdrawal` in [1](#0-0)  polls `bridge.describeWithdrawal(...)` and treats a `"completed"` result as final success, resolving the watcher with the (possibly null) `txHash`.
- `AuroraEngineBridge.describeWithdrawal` takes **no parameters at all** and unconditionally returns `{ status: "completed", txHash: null }`: [2](#0-1) .
- The withdrawal intent that is actually submitted is `ft_withdraw` with `receiver_id: auroraEngineContractId` and `msg: makeAuroraEngineDepositMsg(destinationAddress)` [3](#0-2) . Execution of this intent on `intents.near` triggers a cross-contract `ft_transfer_call` to the token contract, which in turn invokes Aurora Engine's `ft_on_transfer`, which performs the actual internal EVM-account credit — a receipt nested *inside* the outer NEAR transaction. Under the NEP-141 `ft_transfer_call` protocol, if the receiving contract's callback fails or refuses part/all of the amount, the tokens are refunded and the *outer* transaction can still finish with `SuccessValue`, i.e. the outer NEAR tx hash succeeding does not imply the nested Aurora Engine credit succeeded.
- `describeWithdrawal` never fetches the transaction result, never inspects receipt outcomes, and never distinguishes a successful nested credit from a failed/refunded one — it doesn't even use the `tx.hash` that other bridges' `describeWithdrawal` implementations receive and rely on (compare `DirectBridge.describeWithdrawal`, which at least echoes `args.tx.hash`) [4](#0-3) .

No existing guard (`validateWithdrawal`, `supports()`, `withdrawalParamsInvariant`, etc.) checks the nested Aurora Engine receipt outcome either — `validateWithdrawal` only validates the destination address format via `validateAddress(..., Chains.Ethereum)` before submission [5](#0-4) , which does nothing to detect a runtime failure of the Aurora Engine credit after submission. Hence the equality is broken by construction: the SDK-reported status is a constant, independent of the actual on-chain outcome.

### Impact Explanation
Any integrator using `waitForWithdrawalCompletion`/`watchWithdrawal` for a `RouteEnum.VirtualChain` withdrawal will be told the withdrawal is `"completed"` the moment the outer NEAR transaction is queried, even if the nested Aurora Engine `ft_on_transfer` call actually failed and refunded the tokens. This is a status misreport that can cause an integrator to credit a user's balance (e.g., mark an off-chain ledger entry, release a corresponding asset, or allow further withdrawals) for funds that were never actually delivered to the destination virtual-chain account — matching the "status or hash misreport making an integrator credit or refund twice" Critical/High impact category. The failure mode is repeatable for every withdrawal through this route since the check is entirely absent, not merely mishandled in an edge case.

### Likelihood Explanation
No special privilege is needed — any ordinary user withdrawing through `RouteEnum.VirtualChain` is affected. Triggering the underlying divergence requires only that the nested Aurora Engine credit fail/be refunded for any reason (e.g., transient issues on the virtual chain, gas/limits inside the Aurora Engine call, or any other cause on the receiving side) while the outer NEAR transaction still finalizes successfully — a scenario NEAR's cross-contract call semantics for NEP-141 `ft_transfer_call` make entirely possible. Because `describeWithdrawal` performs zero verification, this class of failure is always misreported, with no dependency on attacker sophistication beyond causing (or waiting for) one failed nested call.

### Recommendation
`AuroraEngineBridge.describeWithdrawal` must fetch the NEAR transaction result (via `tx.hash`/`tx.accountId`) and inspect the actual receipt outcomes for the nested `ft_transfer_call` → Aurora Engine `ft_on_transfer` chain, returning `"completed"` only when the nested credit succeeded (e.g., by checking the returned unused-amount value from `ft_on_transfer`/refund events), `"failed"` when the token was refunded, and `"pending"` while the transaction/receipts have not yet finalized — following the same pattern already used in `HotBridge.describeWithdrawal` and `PoaBridge.describeWithdrawal`, which do inspect actual withdrawal state before declaring completion.

### Proof of Concept
```ts
// aurora-engine-bridge.describeWithdrawal.test.ts
import { describe, it, expect } from "vitest";
import { AuroraEngineBridge } from "./aurora-engine-bridge";

describe("AuroraEngineBridge.describeWithdrawal", () => {
  it("reports completed even when nested Aurora Engine ft_on_transfer receipt failed", async () => {
    const bridge = new AuroraEngineBridge({
      envConfig: /* ...mocked... */,
      nearProvider: /* mocked provider whose tx result shows
                        outer SuccessValue but a FAILED nested receipt
                        for the Aurora Engine ft_on_transfer call */,
    });

    const wid = bridge.createWithdrawalIdentifier({
      withdrawalParams: { assetId: "nep141:token.near", amount: 100n,
        destinationAddress: "0x0000000000000000000000000000000000dEaD",
        routeConfig: { route: "virtual_chain", auroraEngineContractId: "aurora", proxyTokenContractId: null } },
      index: 0,
      tx: { hash: "outer-success-but-inner-failed-tx", accountId: "user.near" },
    });

    // Left side: SDK-reported status
    const result = await bridge.describeWithdrawal(); // no params consumed at all
    expect(result.status).toBe("completed"); // BUG: always true

    // Right side: actual on-chain outcome (mocked receipt tree) shows the
    // Aurora Engine credit sub-receipt failed / tokens were refunded.
    // A correct implementation should have returned status "failed" here,
    // demonstrating the two sides of the equality diverge.
  });
});
```
