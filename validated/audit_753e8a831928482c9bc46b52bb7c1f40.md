### Title
Unprotected `initialize` on `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` allows front-running of ownership - (File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol / WrappedHyperFungibleTokenUpgradeable.sol)

### Summary
`HyperFungibleTokenUpgradeable.initialize` and `WrappedHyperFungibleTokenUpgradeable.initialize` are `public` functions gated only by OpenZeppelin's `initializer` modifier (one-shot-only), with no caller restriction analogous to `onlyFresh`/CREATE2-atomic binding used elsewhere in the same codebase.

### Finding Description
`HyperFungibleTokenUpgradeable.initialize(string,string,address)` and `WrappedHyperFungibleTokenUpgradeable.initialize(address)` are declared `public virtual initializer` with no access control beyond the standard `Initializable` guard that only prevents a *second* call: [1](#0-0) [2](#0-1) 

The `initialize` call sets the `OwnableUpgradeable` owner from the caller-supplied `initialOwner` argument: [3](#0-2) 

Compare this to the codebase's own established, documented pattern for this exact bug class in `IntentGatewayV2.initialize` and `SimplexPaymaster.initialize`, both of which add an explicit `onlyFresh` modifier (reverting unless `_getInitializedVersion() == 0`) precisely because "`initialize` has no caller restriction" would otherwise let "anyone... initialize it with their own host" if the proxy is ever left in a bare, uninitialized state between deployment and the `initialize` call: [4](#0-3) [5](#0-4) [6](#0-5) 

`IntentGatewayV2` and `SimplexPaymaster` deployment scripts additionally bind `initialize` calldata atomically into the `ERC1967Proxy` constructor via CREATE2, closing the window entirely: [7](#0-6) [8](#0-7) 

`HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable`, however, have neither the `onlyFresh` guard nor any deploy script in this repository that binds `initialize` atomically to proxy construction; a `grep` across the repo found zero references to these contracts outside their own source file, and no `ERC1967Proxy` deployment wiring for them.

### Impact Explanation
If a deployer (developer/protocol integrating the SDK) deploys the implementation and a proxy in separate transactions — the standard, commonly-used upgradeable-proxy pattern (deploy implementation, deploy `ERC1967Proxy` pointing at it, then separately call `initialize`) — the proxy sits in an uninitialized state after proxy creation and before the `initialize` transaction confirms. Any unprivileged actor watching the chain can front-run that transaction and call `initialize` first, becoming the `Ownable` owner of the bridge token contract.

Owning the contract grants full control of `configure` (sets the ISMP `_host` and `_dispatcher`), `addChain`/`removeChain` (sets the trusted peer `moduleId` per chain, which is the sole authorization check in `onAccept`/`send` for minting/burning across chains), and `pause`/`unpause`: [9](#0-8) 

By setting `_host`/`_dispatcher` and `_supportedChains` to attacker-controlled values, the attacker can register itself as a "peer" and forge incoming cross-chain messages that pass the `_supportedChains` check in `onAccept`, resulting in unbacked mints, or otherwise permanently break/freeze the bridge app (wrong host address bricks all `send`/receive flows). This is a full loss-of-control / unauthorized-mint primitive for that token deployment, matching the reported bug class (missing AC on `initialize` → mint to arbitrary caller).

### Likelihood Explanation
This requires a deployer to use a non-atomic deploy flow (deploy proxy, then separately call `initialize`), which is a common but avoidable proxy deployment pattern. The codebase's own decision log shows the maintainers are aware of and actively defend against exactly this class of risk for other upgradeable apps (`IntentGatewayV2`, `SimplexPaymaster`) but did not carry the same fix to `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable`, indicating an inconsistency/oversight rather than a deliberate, documented acceptance of risk for these two contracts.

### Recommendation
Add an `onlyFresh`-style guard (checking `_getInitializedVersion() == 0` or equivalent) to `HyperFungibleTokenUpgradeable.initialize` and `WrappedHyperFungibleTokenUpgradeable.initialize`, consistent with `IntentGatewayV2` and `SimplexPaymaster`, or ensure/document that deployment must always bind `initialize` calldata atomically into the proxy constructor (as done for `IntentGatewayV2`/`SimplexPaymaster` in their deploy scripts) and enforce this via a `_disableInitializers()`-guarded factory helper rather than leaving it to caller discretion.

### Proof of Concept
1. Deployer deploys implementation: `HyperFungibleTokenUpgradeable impl = new HyperFungibleTokenUpgradeable();` (constructor calls `_disableInitializers()` on the implementation only, per [10](#0-9) ).
2. Deployer deploys a bare `ERC1967Proxy(address(impl), "")` (no init data) — this is a valid, commonly used pattern the deploy scripts for other apps deliberately avoid via atomic init data, but nothing in this file prevents it.
3. Attacker observes the proxy deployment transaction/mempool and, before the deployer's follow-up `initialize` call is mined, submits `proxy.initialize("Evil", "EVIL", attacker)`.
4. `attacker` becomes the `Ownable` owner (`__Ownable_init(initialOwner)`), and the deployer's subsequent `initialize` call reverts (`InvalidInitialization` from the `initializer` modifier), permanently locking out the legitimate owner.
5. Attacker calls `configure` and `addChain` with attacker-controlled `host`/`dispatcher`/peer `moduleId` values, then can trigger `onAccept` (if attacker also controls or spoofs the configured host) to mint arbitrary balances to itself, or simply `pause()` to permanently freeze the token for legitimate cross-chain use.

```text
    /// @param params_  Initial pricing and treasury parameters
    /// @param tokens_  Initially supported ERC-20 tokens

    /// @param relayer_ The only relayer whose governance deliveries are accepted; zero leaves

        address host_,
        Params memory params_,
        address[] memory tokens_,
        AggregatorV3Interface[] memory oracles_,
```

```markdown
# 2026-09-05 — `initialize` only on a bare proxy, rather than a version check in the upgrade path

Chosen: `initialize` is refused unless the proxy is at version 0. `migrate` is the only entry to
`VERSION` for a proxy that already has one, and it is host-only.

The hole both options close: `initialize` has no caller restriction, because a bare proxy is
initialized atomically in its constructor. An `UpgradeContract` that installs this implementation
on a version-1 proxy without `migrate` calldata would leave the proxy below `VERSION` with
`initialize` callable by anyone, who could then set the params and the relayer.

Alternative rejected — require the version to have risen after `upgradeToAndCall`. It forces
every upgrade to carry a migration, so a same-implementation upgrade carrying only `setRelayer`,
the rotation path, would be refused; scoping the check to implementation changes fixes that but
adds a branch and an implementation-slot read to every upgrade. And it cannot protect the first
upgrade off the live pre-gate implementation, whose `onAccept` has no such check. The `initialize`
guard covers that case too, since it is the new implementation's code that runs `initialize`.
```
