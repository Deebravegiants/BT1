### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop misattribution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate a webhook by validating the HMAC over the raw request body only. The `shop` value that the gem hands to the host application's webhook handler is read from the `x-shopify-shop-domain` header, which is never included in the signed material. This breaks the identity binding: `shop` used by the handler ≠ `shop` covered by the HMAC.

### Finding Description
`HmacValidator.validate` computes/verifies the signature using `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop` is pulled straight from the `shopify-shop-domain` HTTP header, which is not part of the signed string at all: [3](#0-2) 

`Registry.process` validates only the HMAC of the request, then forwards `request.shop` (the unauthenticated header) to the handler as trusted metadata: [4](#0-3) 

Because the HMAC is computed purely from `secret + raw_body` (`OpenSSL::HMAC.hexdigest(... secret, signable_string)`), any request with a body/HMAC pair that is valid for shop A (e.g., obtained by an attacker who owns a legitimate installed instance of the app on their own store) remains **HMAC-valid** even if the `x-shopify-shop-domain` header is changed to shop B. `Registry.process` has no mechanism to detect this because the header is never part of the signable string: [5](#0-4) 

The equality that should hold is: `shop authenticated by HMAC == shop delivered to the handler as WebhookMetadata#shop`. In fact `shop authenticated by HMAC` is undefined (HMAC binds nothing to shop), while `shop delivered to handler` is attacker-controlled via a header, so the equality is broken.

### Impact Explanation
Any app merchant (an "unprivileged" tenant relative to other tenants) who has a legitimate installation can capture one of their own genuine webhook deliveries (valid body + HMAC pair, e.g. via a proxy or replay) and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to another merchant's shop domain. Because `Registry.process` only checks `Utils::HmacValidator.validate(request)` (body-only) and then trusts `request.shop` when building `WebhookMetadata`, the host application will process/store this data as if it originated from the victim shop. Any app that uses the `shop` field from `WebhookMetadata` as a tenant key (which is the intended and documented usage) can have its per-tenant data poisoned or cross-contaminated by an unrelated, unprivileged merchant — a cross-tenant integrity breach reachable without any of the app's credentials.

### Likelihood Explanation
High/plausible: exploitation requires only (a) being a legitimate installed merchant able to observe one authentic webhook delivery for their own shop, and (b) the ability to POST an HTTP request to the app's public webhook endpoint with a modified header — both are trivially available to any unprivileged internet user who has installed the app once. No secrets, tokens, or privileged access are required; the gem's own `Registry.process`/`Request` design is what fails to bind the header to the signature.

### Recommendation
Include the shop domain (and ideally the topic/api-version) inside the HMAC-signed material for webhooks, or otherwise cryptographically bind the header value used for tenant attribution to the signed payload before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should refuse to trust `request.shop` for any purpose that affects tenant-scoped storage unless the shop is independently corroborated (e.g., cross-checked against the shop of the session/subscription that registered the webhook).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives a real webhook, capturing the raw body `B` and the header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`), along with `x-shopify-topic: T`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B`, same `x-shopify-hmac-sha256: H`, same `x-shopify-topic: T`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present): [6](#0-5) 
4. `Registry.process` validates the HMAC — which succeeds because it is computed over `B` only, unaffected by the spoofed shop header — then builds `WebhookMetadata` using the spoofed `shop`: [4](#0-3) 
5. The host application's handler receives `shop: "victim-shop.myshopify.com"` with attacker-supplied `body`, processing/storing it against the wrong tenant.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
