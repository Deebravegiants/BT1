## Title
Simplex FXFiller's Uniswap V4 venue price is trusted for order sizing and fills with no default guard and no execution-cost check, letting an order placer manipulate the pool to extract solver funds - ([File: sdk/packages/simplex/src/strategies/fx.ts])

## Summary
The External Report describes a class of bug where a keeper/attacker manipulates a DEX spot price (e.g., via flash loan) and gets an order executed against that manipulated price because the protocol relies solely on the DEX execution price rather than an independent oracle bound. The closest reachable analog in this codebase is Simplex's `FXFiller` cross-asset pricing for "venue-priced" (curveless) pairs, which reads the live Uniswap V4 pool mid-price as the *sole* pricing source for sizing and filling orders, with the only defense (`checkPriceGuard`) being optional, comparing only to a static reference (not execution cost/impact), and doing nothing when unconfigured.

## Finding Description
When a pair has no configured bid/ask curves and `token0` is a USD stablecoin, `FXFiller.resolveLegRates` prices the leg entirely from the live Uniswap V4 pool state instead of a curve: [1](#0-0) 

The price is fetched via `UniswapV4FundingPlanner.getExoticTokenPrice`, which selects the most-liquid qualifying pool and returns `computeDirectPoolPriceUsd`, the **raw pool mid** derived straight from `sqrtPriceX96` with no depth/impact adjustment: [2](#0-1) [3](#0-2) 

The only defense against a manipulated/stale/thin pool is `checkPriceGuard`, documented as comparing "deviation from a static reference, not execution cost": [4](#0-3) 

This guard is explicitly **optional** per-position config (`referencePrice`/`maxDeviationBps`); operators can "leave the chain unguarded": [5](#0-4) 

Both `referenceRate` (used to size the order's token0 notional and cap budgets) and `resolveLegRates` (used to compute the actual fill amount/output) rely on this single spot-pool read: [6](#0-5) 

An order is a message an **unprivileged user submits** via `IntentGatewayV2.placeOrder`, which any address can call: [7](#0-6) 

This is structurally the same defect class flagged in the PrimeX report: the protocol/filler's price-tolerance protection is bound only to a live DEX read (and only when a static-reference guard is even configured), with no execution-cost/oracle-independent check, allowing an attacker who controls the pool at bid time (flash-loan or JIT liquidity manipulation) to shift `computeDirectPoolPriceUsd` favorably, in turn shifting `referenceRate`/`resolveLegRates`, sizing an order so the solver is induced to deliver more of the exotic token (or accept less USD notional) than the true market price warrants.

## Impact Explanation
If the price guard is not configured for the manipulated position/chain (an explicitly supported, documented configuration - "omit both to leave the chain unguarded"), there is no independent bound at all, and the solver's on-chain inventory (Uniswap V4 LP positions and wallet balances) is priced and paid out entirely off the attacker-manipulated pool mid. Even when a guard is configured, it only bounds *deviation from a static reference*, not the price impact/execution cost of the withdrawal itself - the same gap the PrimeX report calls out (comparing to "amountOutMin"/oracle tolerance rather than validating actual DEX execution slippage). The result is a same-transaction or same-block funds-extraction vector: an attacker manipulates the V4 pool price within (or without) the guard's tolerance, places an order sized against that manipulated rate, and the solver fills it, permanently transferring value out of the solver's LP position/wallet to the attacker - a concrete theft of solver funds triggered entirely by an unprivileged `placeOrder` call.

## Likelihood Explanation
Likelihood is Medium: exploitation requires (1) a Simplex operator configuring a curveless (venue-priced) pair backed by Uniswap V4 LP positions, and (2) either no price guard configured, or a guard tolerance wide enough / a pool manipulation cheap enough to stay within `maxDeviationBps` while still moving the effective fill price. Flash-loan-based AMM manipulation is a well-understood, cheap, and repeatable attack primitive, and placing an order is a fully permissionless action reachable by any address. The main mitigating factor is that this only affects operators who opt into pool-based (curveless) pricing rather than static curves, and operators are documented to be able to add a guard - meaning the vulnerability's blast radius depends on the guard being absent or loosely configured, which the docs actively describe as a legitimate operating mode.

## Recommendation
1. Make the price guard (`referencePrice`/`maxDeviationBps`) mandatory for any curveless, Uniswap-V4-priced pair rather than optional, so no chain/position can run fully unguarded.
2. Extend `checkPriceGuard` beyond a static-reference deviation check to also bound execution cost/impact - e.g., simulate or bound the price impact of the actual liquidity withdrawal size against the pool's real depth (TWAP or multi-block price averaging) rather than trusting a single-block `sqrtPriceX96` read.
3. Consider requiring a secondary, harder-to-manipulate price source (a Chainlink-style oracle or TWAP over a manipulation-resistant window) as an independent tolerance check on top of the live pool mid, analogous to PrimeX's `needOracleTolerableLimitCheck` / `maximumOracleTolerableLimit` pattern - i.e., reject a fill/order sizing if the venue price and the independent oracle price diverge beyond a fixed tolerance, regardless of whether an operator configured a guard.
4. Apply the fee-tier/impact adjustment already noted as missing (`computeLegPolicyOutput extends the mid linearly across the whole priced quantity`) so pricing accounts for the true cost of sourcing inventory from the pool itself.

## Proof of Concept
1. Operator configures a curveless pair (e.g., `USDC/CNGN`) priced from a Uniswap V4 position, with either no `referencePrice`/`maxDeviationBps` guard, or a guard wide enough to tolerate the intended manipulation.
2. Attacker takes a flash loan and swaps heavily in the configured V4 pool to move `sqrtPriceX96` so that `computeDirectPoolPriceUsd` returns a USD price of the exotic token that is more favorable to the attacker than the true market price (e.g., understating CNGN's USD value, or overstating it depending on direction).
3. Within the same block (or before the pool reverts to true price), attacker calls `IntentGatewayV2.placeOrder` with input/output amounts that, when priced by `FXFiller.resolveLegRates`/`referenceRate` against the manipulated pool, look profitable to the solver but are actually mispriced against the manipulated rate.
4. `FXFiller` sizes and bids/fills the order using the manipulated venue price (guard either absent or still within `maxDeviationBps` tolerance despite the manipulation), delivering the exotic token (sourced via `UniswapV4FundingPlanner.planWithdrawalForToken`, which decreases the solver's LP liquidity) to the attacker at the manipulated rate.
5. Attacker repays the flash loan and/or reverses the pool manipulation, keeping the extracted value; the solver's LP position/wallet balance is permanently reduced by the mispriced fill.

Note: I could not directly execute or trace a live transaction (no runtime/terminal access), so this PoC is a structural walkthrough based on the code paths cited above (`resolveLegRates` → `getVenueUsdPrice` → `computeDirectPoolPriceUsd` → `checkPriceGuard` → `planWithdrawalForToken`) rather than an empirically reproduced exploit.

	 * Minimum-size reference rate (token1 per token0) for a leg's pair: the
	 * bid curve at 0 (the side token1-input legs trade at), falling back to the
	 * ask curve, then the live venue quote for venue-priced pairs.
	 */
	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {

				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

			return {

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
