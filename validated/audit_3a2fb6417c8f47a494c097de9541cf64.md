### Title
Webhook `shop-domain`, `topic`, `webhook-id` and `api-version` headers are not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification computed in `Utils::HmacValidator.validate` only proves that the request *body* was signed by the app's `client_secret`. It proves nothing about the identity headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) that `Webhooks::Registry.process` subsequently trusts and hands to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body is included in the signed payload, while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from attacker-influenced HTTP headers, unauthenticated: [2](#0-1) 

`Registry.process` verifies only the HMAC over the body, then trusts `request.topic` (to select the handler) and forwards `request.shop`, `request.api_version`, and `request.webhook_id` directly into the metadata passed to the app-defined handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that the *body bytes* were HMAC-signed with the app's (single, shared) `client_secret` — the same secret is used for every shop that installs the app, so a valid `(body, hmac)` pair generated for one tenant remains a valid pair for any other tenant: [4](#0-3) 

This is the same class of bug as the report's root cause: an identity-binding value (there, `block.chainid`; here, the `shop`/`topic` headers) is not included under the same cryptographic guarantee as the data it accompanies, so a signature/message pair valid in one context (chain, or tenant) can be replayed in a different context (another chain, or another shop) while still passing verification. The equality that should hold — `hmac_verified_bytes == bytes_the_handler_acts_on` — is broken: the HMAC binds only the body, but the handler acts on `(shop, topic, webhook_id, api_version, body)`.

### Impact Explanation
An unprivileged internet user who can obtain any one legitimate `(raw_body, x-shopify-hmac-sha256)` pair for the target app (e.g., from their own store's webhook delivery, a public webhook log, or a low-value/empty-body topic where the body is predictable/constant such as `{}`) can POST that same body+HMAC to the app's public webhook endpoint while forging the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers to claim it belongs to a different (victim) shop and topic. `Registry.process` will pass HMAC validation (the body's signature is genuinely valid — it was computed with the app's real `client_secret`) and will invoke the registered handler with `shop: <victim-shop>` and attacker-chosen `topic`/`webhook_id`. Any handler that trusts `WebhookMetadata#shop` to select which tenant's data to update (a common pattern, e.g. `orders/*`, `app/uninstalled`, `shop/redact`) can be tricked into performing actions against, or leaking behavior/state for, a shop the attacker does not control — this is a cross-tenant boundary violation reachable without any credential.

### Likelihood Explanation
Likelihood is moderate: the attacker needs at least one valid `(body, hmac)` pair for the app (easy for their own installed shop, since installing an app and receiving webhooks requires no special privilege), and needs the webhook endpoint to be reachable on the internet (true by design — webhook endpoints are public HTTP callbacks). No access to `client_secret`, access tokens, or TLS interception is required.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the signed payload used for HMAC verification (or otherwise cryptographically bind them to the body/signature), so that a signature is only valid for the specific shop/topic/delivery it was generated for. At minimum, `Registry.process` should independently verify that `request.shop` matches an expected/known shop for the active session context before dispatching to a handler, rather than trusting an unauthenticated header.

### Proof of Concept
1. Attacker's own store (or any store on which they can trigger a webhook, e.g. `app/uninstalled`) generates a legitimate webhook delivery to the app: `raw_body = "{}"`, `x-shopify-hmac-sha256 = HMAC(client_secret, "{}")`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this `(raw_body, hmac)` pair (they own the shop, so they can freely trigger and observe deliveries, or use any topic whose body is constant/predictable).
3. Attacker sends a new POST to the app's public webhook endpoint with the *same* `raw_body` and `hmac`, but headers rewritten to:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: shop/redact` (or any registered topic)
   - `x-shopify-webhook-id: <anything>`
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(client_secret, raw_body)`, matching regardless of the headers [5](#0-4) .
5. `Registry.process` looks up the handler for the forged topic and calls `handler.handle` with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to act as though the victim shop sent this webhook — a cross-tenant identity-binding bypass equivalent to the reported cross-chain replay issue.

          received_signature = verifiable_query.hmac
