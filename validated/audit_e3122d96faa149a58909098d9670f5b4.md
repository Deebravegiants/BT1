### Title
Stale `DelegateGrant` silently re-arms when the position NFT returns to the granting owner, restoring a revoked-looking delegate's full spending authority - (File: contracts/controller/src/storage/account.rs)

### Summary
The controller invalidates delegate grants on NFT transfer only *virtually*: `get_delegates` filters the stored `DelegateGrant` by `granted_by == current_owner` instead of deleting it. The stale grant remains in persistent storage and becomes live again if the position NFT ever returns to `granted_by`. A position manager (delegate) that was granted once can therefore regain unrestricted `borrow`/`withdraw`/`multiply`/strategy authority over the account without any new authorization from the owner — the direct analog of an access key that survives (and is re-armed by) an ownership change.

### Finding Description
`ControllerKey::Delegates(account_id)` stores a single `DelegateGrant { granted_by, delegates }`. Reads go through `get_delegates`, which returns the delegate list only when `grant.granted_by == current_owner`; a transfer makes it read as empty but leaves the entry untouched:

- `contracts/controller/src/storage/account.rs:176-181` — `get_delegates` filters on `granted_by` rather than clearing state.
- `contracts/controller/src/storage/account.rs:203-221` — `add_delegate` overwrites the stale entry only when the *current* owner writes.
- `contracts/controller/src/storage/account.rs:226-247` — `remove_delegate` deletes a foreign `granted_by` entry only if the new owner happens to call it.
- `contracts/controller/src/account.rs:115-127` — `is_owner_or_delegate` treats any `delegates.contains(caller)` match on an active `PositionManagerConfig` as full account authority.
- `contracts/position-nft/README.md:174-179` and `common/src/types/controller.rs:63-67` explicitly document: "The stale grant stays in storage and re-arms if the token returns to `granted_by`."

Attack sequence (all steps reachable by unprivileged addresses):

1. Alice owns `account_id` = NFT `token_id`, calls `add_delegate(caller=alice, account_id, delegate=Manager)` where Manager is an active registered position manager.
2. Alice transfers the NFT to Bob (`position_nft::transfer`). The grant reads empty; Alice reasonably treats the delegation as revoked. Bob never calls `add_delegate`/`remove_delegate`, so the `granted_by = alice` entry persists.
3. The token returns to Alice — e.g., Bob sells the position back, transfers it as part of a trade, or Manager itself acquires the token legitimately and later sends it to Alice (or to any account controlled by Alice) as part of a settlement. No controller write to `Delegates` occurred in between.
4. `is_owner_or_delegate` now resolves `owner = alice`, `grant.granted_by == alice` — Manager's delegation is live again with no fresh `require_auth` from Alice.
5. Manager calls `borrow(caller=manager, account_id, borrows=[...], to=manager)` up to the LTV limit and `withdraw(caller=manager, account_id, withdrawals=[...], to=manager)` for any collateral above the solvency floor, or `multiply`/`swap_collateral`/`repay_debt_with_collateral` to reposition value — all gated solely by `require_owner_or_delegate`, which the resurrected grant passes.

### Impact Explanation
Theft of user funds. A re-armed delegate can draw the account's maximum borrowable debt to itself and withdraw all collateral consistent with post-action solvency, plus operate every strategy entrypoint pinned by `require_owner_or_delegate` (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend` on the account). The victim owner never signed a new authorization; the protocol's own invariant INV-AUTH-02 ("account spending authority is explicit") is violated because the authority was conferred by a grant the owner had every reason to believe died on transfer.

### Likelihood Explanation
Medium. It needs three conditions: a prior `add_delegate` (delegates are governance-registered position managers, so grants are a designed feature, not exotic), an NFT transfer out and back to the same owner without an intervening delegate write by the interim holder, and a delegate willing to abuse the re-armed grant. Position NFTs are transferable and can change hands repeatedly (sales, settlements, `transfer_from` by operators), and nothing in the transfer path clears the `Delegates` key — each round trip through the original owner re-arms the grant automatically. The attacker (the delegate) cannot force the token back to `granted_by` alone, which caps the likelihood, but the grant holder has indefinite persistence: the stale entry survives in storage indefinitely and is renewed by `renew_user_account`.

### Recommendation
Delete the `Delegates` entry on ownership change rather than shadowing it. Concretely: have the NFT transfer path (or the controller on first owner resolution after a change) remove `ControllerKey::Delegates(account_id)`, or version the grant with a transfer counter/epoch stored in `AccountMeta` and compare epochs in `get_delegates` instead of comparing `granted_by`. At minimum, make re-arming impossible by keying `Delegates` on `(account_id, granted_by)` so a returned owner sees only a list they currently control, or require `add_delegate` to re-stamp grants on every owner change and delete mismatched entries on read.

### Proof of Concept
Extension of the existing test `transfer_revokes_prior_owner_and_delegates` (`contracts/controller/tests/helpers/account.rs:387-434`) and `transfer_revokes_old_owners_delegates` (`tests/test-harness/tests/controller/position_nft.rs:81-93`):

```rust
// After the existing assertions that ALICE's grant is dead under BOB:
// BOB never touches add_delegate/remove_delegate, so the stale
// DelegateGrant { granted_by: alice, delegates: [manager] } persists.

// Return the token to ALICE.
position_nft::PositionNftClient::new(&env, &nft).transfer(
    &bob, &alice, &u32::try_from(account_id).unwrap(),
);

env.as_contract(&contract_id, || {
    let owner = crate::storage::account_owner(&env, account_id);
    assert_eq!(owner, alice);
    // VULN: grant re-arms with no new authorization from alice.
    assert!(is_owner_or_delegate(&env, account_id, &manager, &owner));
});
```

In the harness (`t.nft_transfer(BOB, ALICE, account_id)` after `t.nft_transfer(ALICE, BOB, account_id)` with no delegate write by BOB), `t.borrow_as_to("MANAGER", account_id, "USDC", 10.0, "MANAGER")` succeeds again and `MANAGER` receives borrowed funds — demonstrating the re-armed delegate can extract account value with zero fresh consent from the owner.
