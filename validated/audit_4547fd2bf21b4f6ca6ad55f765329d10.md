### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant routing but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and are never included in the HMAC computation, yet `Registry.process` forwards `request.shop` directly to the app's webhook handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.): [1](#0-0) 

However `to_signable_string`, which is what `HmacValidator` signs/verifies against, only covers the raw body: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac-sha256` header, so it only proves the *body* bytes are authentic - it says nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers: [3](#0-2) 

Despite this, `Registry.process` validates the HMAC and then passes the **header-derived, unauthenticated** `request.shop` and `request.topic` straight to the host app's handler as the trusted tenant/topic identity: [4](#0-3) 

The documented processing flow explicitly tells integrators that `data.shop` is "the shop domain of the webhook" and is safe to use for tenant dispatch (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) 

The binding that is broken is: `HMAC_valid(raw_body) == true` is treated as implying `shop_header == actual_originating_shop`, when in fact the HMAC only certifies `raw_body`, not `shop_header`. Any party who can obtain one genuine `(raw_body, hmac)` pair signed with the app's secret (trivially available to any merchant who installs the app on their own store and triggers a webhook, e.g. `orders/create`) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never looks at the header, and `Registry.process` will call the handler with `shop:` set to the attacker-chosen value while `body:` contains data the attacker fully controls from their own store.

### Impact Explanation
This breaks the cross-tenant isolation the gem is expected to provide: an unprivileged internet user who merely has (or creates) their own Shopify store can forge webhook deliveries that the host app will attribute to a victim shop of the attacker's choosing, using body content the attacker controls. If the host application (as the docs recommend) uses `data.shop` to select the tenant record/database row/queue partition to act on, this is a cross-tenant data-injection primitive — attacker-controlled webhook payloads being processed and persisted under a victim shop's identity. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker with a Shopify development/partner account: capturing a legitimate `(raw_body, x-shopify-hmac-sha256)` pair only requires triggering a webhook on their own store and observing the delivery (or intercepting the app's own webhook endpoint traffic, which is not TLS-protected credential access — it's simply their own webhook). No access to the app's `client_secret`, access tokens, or the victim's data is required; only a normal HTTP POST to the app's public webhook endpoint with a substituted header is needed.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`api-version`/`webhook-id`) headers into the value that is HMAC-verified, or otherwise validate `request.shop` against an independent trust anchor before dispatch — e.g., include the header values in `to_signable_string`, or require the host app to cross-check `request.shop` against the shop embedded in the webhook body/known installed-shops list before acting on it, and document this requirement clearly since `Registry.process` currently implies the header is already authenticated.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and receives a genuine webhook delivery for it:
raw_body = '{"id":1,"note":"attacker controlled payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
# (This hmac is genuinely computed by Shopify for the attacker's own store event.)

# Attacker replays it against the app's public webhook endpoint, substituting the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim.myshopify.com" # spoofed, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) returns true (only raw_body is checked),
# handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...))
# is invoked, attributing attacker-controlled data to "victim.myshopify.com".
```

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
