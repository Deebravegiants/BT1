## Title
Native-token overpayment during `EvmHost.dispatch()`/`fundRequest()` swaps is refunded to the Host contract, not the caller, permanently misappropriating the payer's excess funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
The Tomb Finance incident stemmed from a fee-collection mechanism whose behavior under normal user interaction (a third-party "Gatekeeper" fee gate) produced unintended value loss for users. The structurally analogous bug class here is a **fee-collection swap mechanism that silently misdirects user funds** rather than returning them. `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all let a caller pay the relayer fee in native token by invoking Uniswap V2's `swapETHForExactTokens`, but none of these paths refund unused `msg.value` to the original caller.

### Finding Description
When a user or app dispatches a message with `msg.value > 0`, `EvmHost` performs an exact-output swap for the fee token: [1](#0-0) 

`IUniswapV2Router02.swapETHForExactTokens(amountOut, path, to, deadline)` is a payable function: it computes the minimal ETH input required (`amounts[0]`) to produce `amountOut` fee tokens, and if `msg.value > amounts[0]`, the Uniswap router refunds the difference to **its own caller** (`msg.sender` of the swap call), which is `EvmHost` itself — not the end user who originally sent the transaction. The same pattern recurs in `dispatch(DispatchGet)` and in `fundRequest()`: [2](#0-1) 

Because `EvmHost` never reads back the router's refund and never forwards it to `_msgSender()`, any ETH sent in excess of the exact quote is absorbed into the Host contract's balance. There is no code path in these functions that returns unspent value to the payer.

### Impact Explanation
Any unprivileged caller (an app, an `IHyperFungibleToken` sender paying with native token, or a direct integrator) who supplies `msg.value` slightly above the exact quote — which is easy to do, since `quote()` in `HyperApp.sol` is a separate, potentially stale read subject to slippage between quoting and execution — permanently loses the difference. This is not a griefing/DoS issue: it is an unrecoverable transfer of user-owned native currency into protocol-controlled contract balance without the user's consent, satisfying "concrete theft or permanent freezing of funds" for the affected caller on every over-quoted dispatch. Given `dispatch()` is the primary entrypoint reachable by any single transaction from an unprivileged message dispatcher/token bridger, and the swap-based fee-collection path is used broadly across `HyperFungibleToken.send()` and any custom `IApp` dispatching with native value, the blast radius is broad, but limited to whatever amount of overpayment is sent.

### Likelihood Explanation
High likelihood of accidental triggering: exact quotes drift due to normal block-to-block price/slippage in the Uniswap V2 pool between calling `quote()` and submitting the transaction, and typical integrator patterns add a slippage buffer to `msg.value` to avoid reverts — which is precisely what causes leftover ETH to be trapped rather than reverted or refunded.

### Recommendation
After calling `swapETHForExactTokens`, capture the returned `amounts[0]` (actual ETH spent) and refund `msg.value - amounts[0]` to `_msgSender()` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. Caller queries `quote(post)` via `HyperApp.quote()`, gets `nativeFee`.
2. Attacker/user sends `dispatch{value: nativeFee + slippageBuffer}(post)` (a common integration pattern to survive quote staleness).
3. Inside `dispatch()`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; Uniswap refunds `slippageBuffer` ETH to `address(this)` (the Host), not to the caller.
4. `dispatch()` returns normally with no error and no refund event; the `slippageBuffer` amount is now stuck in `EvmHost`'s balance, unreachable by the original payer. [1](#0-0) [2](#0-1) 

Note: I was unable to fully confirm within the available index whether `EvmHost.sol` exposes a `receive()`/admin sweep function that later disburses this trapped ETH (a partial grep match suggested related keywords exist elsewhere in the file, but I could not inspect those exact lines before running out of tool calls). Even if such a sweep exists, it would route the funds to governance/host-manager rather than back to the original payer, which does not remedy the user-level fund loss described above.
