## Finding

### Title
IntentGatewayV2 (Tron) escrow withdrawal ignores ERC20 `transfer()` boolean return, allowing silent-fail tokens to be marked settled without paying out - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` settles escrowed intent funds using a raw low-level `.call()` to the token's `transfer()` function and only checks that the *call itself* did not revert (`success`). It never inspects/decodes the returned boolean payload. Any ERC20 that returns `false` on failure instead of reverting (a common non-standard/defensive pattern, and the exact class of token called out in the referenced report) will cause the withdrawal to be accepted as successful even though no tokens moved, while the protocol simultaneously deletes the escrow accounting and marks the order filled/refunded.

### Finding Description
`withdraw()` is the internal settlement routine invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` POST request is delivered by any relayer for the destination-chain solver fill or user cancellation. It releases escrowed input tokens and any accumulated transaction fees: [1](#0-0) 

Specifically:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and
```
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
```
`success` here only reflects whether the external call reverted — it says nothing about the ABI-decoded boolean payload that `IERC20.transfer` is supposed to return. Standard OpenZeppelin `SafeERC20.safeTransfer` correctly decodes and checks this return value (and also tolerates tokens that return no data at all, like Ethereum-mainnet-style USDT). This Tron-specific IntentGatewayV2 rewrote the transfer sites with unchecked low-level calls instead of `SafeERC20`, even though `SafeERC20`/`IERC20` are already imported and used (`using SafeERC20 for IERC20;`) and are used correctly for the *inbound* escrow leg (`safeTransferFrom`) elsewhere in the same file: [2](#0-1) 

The same pattern also appears in `onAccept`'s `SweepDust` handling and in the predispatch sweep of `placeOrder`: [3](#0-2) [4](#0-3) 

By contrast, the canonical EVM `IntentsBase._withdraw()` used by the non-Tron `IntentGatewayV2` uses `SafeERC20.safeTransfer`, which correctly reverts on a token returning `false`: [5](#0-4) 

### Impact Explanation
For any input token, output token, or the protocol fee token that returns `false` on a failed `transfer()` (rather than reverting) — for example, due to a blacklist check, pause state, insufficient balance edge case in a non-conforming token, or an intentionally crafted malicious/rebasing/permissioned token registered by a user or solver as an order input — the withdrawal path will:
1. Treat the call as successful (`success == true`).
2. Decrement/zero the escrow accounting (`_orders[body.commitment][token] -= amount`) and delete transaction fee escrow.
3. Mark the order as filled/refunded (`_filled[body.commitment] = beneficiary`) and emit `EscrowReleased`/`EscrowRefunded`.

No tokens are actually transferred to the beneficiary. Because this happens in the same transaction as the accounting update, the escrowed value is permanently unrecoverable — a direct loss of user/solver funds locked in the IntentGateway escrow, and this exact settlement path (`RedeemEscrow`/`RefundEscrow` via `onAccept`) is reachable purely by a relayer delivering a legitimate cross-chain proof, i.e. no privileged/admin action is required.

### Likelihood Explanation
Reachability requires only a normal order lifecycle (place → fill/cancel → cross-chain settlement delivered by any relayer) using a token whose `transfer()` can return `false` instead of reverting. This is a realistic and common token-integration hazard (deflationary/blacklist/pausable tokens), and it directly parallels the non-standard-ERC20 class flagged in the referenced report, except inverted: instead of missing return data causing reverts, unchecked return data causes silent failures to be accepted as success. Given IntentGatewayV2 is permissionless with respect to which ERC20s can be used as order inputs/outputs, this is readily triggerable.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` sites in `evm/tron/contracts/apps/IntentGatewayV2.sol` (the `withdraw()` function, the `SweepDust` handling in `onAccept()`, and the predispatch sweep in `placeOrder()`) with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase._withdraw`, `WrappedHyperFungibleToken`, `EvmHost`), so that both non-standard "no return value" tokens and tokens that explicitly return `false` are handled safely.

### Proof of Concept
1. Deploy a minimal ERC20 whose `transfer()` returns `false` on failure conditions instead of reverting (e.g., a blacklist/pause-gated token, mirroring known non-standard token behavior on Tron/Ethereum).
2. Register it as an order input token and place/fill an order such that it becomes eligible for `RedeemEscrow`/`RefundEscrow` settlement.
3. Put the token into a state where `transfer(beneficiary, amount)` returns `false` (e.g., beneficiary blacklisted, or token paused) without reverting.
4. Deliver the `RedeemEscrow`/`RefundEscrow` POST request via `onAccept()`; observe that `withdraw()` completes without reverting, `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — while `beneficiary`'s token balance is unchanged, permanently freezing the escrowed funds.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
