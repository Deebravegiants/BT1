### Title
Intent-order predispatch swaps default `amountOutMinimum` to the unslipped quoted amount, providing zero slippage protection when `slippageBps` is unset - (File: sdk/packages/sdk/src/utils/uniswapQuote.ts)

### Summary
`quoteExactInputForProtocol` in `sdk/packages/sdk/src/utils/uniswapQuote.ts` only rewrites the generated swap transaction with a slippage-adjusted `minAmountOut` when the caller passes a positive `slippageBps`. If `slippageBps` is omitted (default `0`), the transactions returned by `findBestProtocolWithAmountIn` in `sdk/packages/sdk/src/utils/swap.ts` are used as-is, and those transactions set `amountOutMinimum`/`amountOutMin` equal to the just-fetched quoted `amountOut` — a value obtained from an on-chain quoter call in the same flow, not validated against the pool state at execution time. Between quoting and broadcasting the intent order's predispatch call, the pool price can move (front-running, sandwich attacks, or natural volatility), and since there is no minimum floor below the "expected" amount, the swap can execute at a materially worse rate while still satisfying the router's `amountOutMinimum` check, because that value is stale/attacker-influenceable rather than a true user-configured tolerance.

### Finding Description
The predispatch/output swap calldata built by the intents SDK (`createV2SwapCalldataExactIn`, `createV3SwapCalldataExactIn`, `createV4SwapCalldataExactIn`) is executed atomically as part of an `IntentGatewayV2` order's `predispatch.call` or `output.call` on-chain (see `evm/tests/foundry/IntentGatewayV2Test.sol`, which demonstrates this exact "swap ETH -> token via predispatch" pattern used in production order flows). The `amountOutMinimum` passed into these calldata builders comes from `quoteExactInputForProtocol`: [2](#0-1) 

When `params.slippageBps` is not supplied by the caller (defaults to `0`), the code path that would compute `minAmountOut = applySlippageToAmountOut(...)` and rebuild the transactions with a genuine minimum never executes. Instead, the SDK falls back to `result.transactions`, which were generated inside `findBestProtocolWithAmountIn` using the raw quoted `amountOut`/`amountOutV2`/`amountOutV3`/`amountOutV4` directly as the swap's minimum-out parameter: [1](#0-0) 

Using the just-quoted output as the minimum provides no real slippage buffer: by the time the transaction is signed and broadcast (or bundled into a `UserOperation`/predispatch call for cross-chain settlement), the AMM pool state can shift due to normal trading or an adversary sandwiching the transaction. Because the "minimum" is not a caller-configured tolerance below the expected value but the expected value itself (subject to floating-point/timing skew), the protection is effectively nominal, analogous to the reported `BuyBackBurnerBalancer._performSwap` hard-coding `amountOutMinimum = 1`. In both cases, the party building the swap calldata does not enforce a meaningful floor tied to real slippage tolerance, allowing extraction of value through price manipulation or front-running.

### Impact Explanation
Any consumer of the intents SDK (or the filler/solver path, or a user constructing a predispatch swap for their order's input assets) who does not explicitly pass `slippageBps` will unknowingly place trades with no effective slippage protection. An attacker able to observe pending transactions (mempool visibility) or manipulate short-lived AMM pool prices can sandwich these swaps, causing the user's escrowed input tokens (for `predispatch`) or the solver's escrowed proceeds (for `output.call`) to be received at a degraded rate — a direct loss of funds for the order's economic beneficiary. Given this is a widely reachable code path for constructing on-chain-executed swap calldata within the core intents flow, the impact is a concrete loss-of-funds vector, warranting Medium severity consistent with the referenced report.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the caller to omit `slippageBps` (a plausible default/oversight since it's optional and not enforced) and requires an attacker with mempool visibility or DEX price-manipulation capability to front-run/sandwich the specific swap transaction. This does not require any privileged access — any observer of the predispatch/output swap transaction can attempt to profit, matching the same "front-run or manipulate pool prices" root cause identified in the original report.

### Recommendation
Do not use the raw quoted `amountOut` as the on-chain `amountOutMinimum`/`amountOutMin` for any generated swap calldata. Require slippage protection to be either (a) mandatory (non-optional, with no zero/undefined default) whenever `generateCalldata` is true, or (b) always applied with a safe non-zero default (e.g., a conservative default like 50–100 bps) inside `findBestProtocolWithAmountIn`'s calldata generation itself, rather than deferring the min-out adjustment to an opt-in post-processing step in `quoteExactInputForProtocol`. Additionally, enforce a reasonable maximum staleness/deadline on quotes used to build predispatch/output swap calldata so pool-state drift between quoting and execution is bounded.

### Proof of Concept
1. Call `quoteUniswap({ tokenIn, tokenOut, amountIn, recipient, tradeType: "exactInput" /* no slippageBps */ })`, which routes to `quoteExactInputForProtocol`.
2. Because `slippageBps` is undefined, `params.slippageBps ?? 0` evaluates to `0`, so the `if (generateCalldata && slippageBps > 0)` branch in `uniswapQuote.ts` is skipped.
3. The returned `transactions` are exactly `result.transactions` from `findBestProtocolWithAmountIn`, whose V2/V3/V4 calldata builders were invoked with `amountOutMinimum = amountOutV2/amountOutV3/amountOutV4` (the raw quote), as shown in `swap.ts` lines 1257–1263, 1281–1288, 1305–1313.
4. These transactions are embedded as an order's `predispatch.call`/`output.call` (per the pattern in `evm/tests/foundry/IntentGatewayV2Test.sol`) and executed atomically on-chain by the Dispatcher/IntentGatewayV2.
5. An attacker monitoring the mempool sandwiches the swap transaction, moving the pool price between quote-time and execution so the actual output is materially lower than the quoted value, yet still equal to or greater than the "minimum" (which was set to the pre-attack quoted amount, offering no real floor) — resulting in fewer tokens delivered than the user/solver expected, at the attacker's profit.
