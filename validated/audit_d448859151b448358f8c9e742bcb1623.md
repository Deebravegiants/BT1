Audit Report

## Title
Missing fuel deduction in `EngineMeter::charge_ref_time` lets a contract run more wasm bytecode than `gas_limit` allows - (File: substrate/frame/contracts/src/gas.rs)

## Summary
`EngineMeter::charge_ref_time` computes the fuel-equivalent cost of a host-function call but never subtracts it from `self.fuel`, returning the stale (unchanged) fuel value which is written straight back into wasmi's engine fuel counter via `store.set_fuel(fuel.into())`. This means every host-function call fails to shrink wasmi's independent instruction-fuel budget, letting a contract that interleaves cheap host calls with wasm bytecode loops execute more wasm instructions per segment than its `gas_limit` should permit, with the discrepancy only caught retroactively on the next host call.

## Finding Description
In `substrate/frame/contracts/src/gas.rs` lines 69-76, `charge_ref_time` calls `self.fuel.checked_sub(amount)` solely to detect underflow (mapping it to `OutOfGas` on error) but discards the resulting decremented value and never reassigns `self.fuel`. The function returns `Syncable(self.fuel)`, the original unmodified fuel amount, as if the host call cost zero fuel.

This return value flows through `GasMeter::sync_to_executor` (lines 255-258), which is invoked by the proc-macro-generated `sync_gas_after` block on every host function exit (`substrate/frame/contracts/proc-macro/src/lib.rs` lines 734-748), and its result is passed directly to `__caller__.set_fuel(fuel.into())`, writing the unchanged fuel value back into wasmi's engine.

Meanwhile, the true and correctly-implemented accounting mechanism is `gas_left`, which `GasMeter::charge` (lines 207-220) properly decrements via `checked_sub`. This creates a real discrepancy: wasmi's internal fuel counter (used to bound bytecode execution) is never reduced for host-call weight cost, while `gas_left` is. The mismatch is only reconciled the next time a host function is entered, via `sync_from_executor`'s `checked_reduce` against `gas_left` (lines 239-245) — by which point excess wasm bytecode may have already executed using the inflated wasmi fuel budget.

This is a genuine logic bug: an assignment that should occur (`self.fuel = self.fuel.checked_sub(...)`) is missing, breaking the accounting invariant that wasmi's engine fuel tracks the same budget as `gas_left`.

## Impact Explanation
An unprivileged contract caller can craft a contract that interleaves many cheap host calls (e.g., `seal_gas_left`, `seal_caller`) with wasm-only compute loops. Because wasmi's fuel counter is never reduced for host-call cost, each interleaved wasm loop segment can execute more bytecode than the weight-metered `gas_limit` should allow, before the shortfall is retroactively detected and `OutOfGas` raised on the next host call. This allows real, unmetered excess computation/block-time consumption beyond what `gas_limit` is meant to bound — a legitimate weight/gas-limit accounting bypass in the contracts pallet's fuel-metering integration with wasmi.

## Likelihood Explanation
The bug is unconditionally reachable: it fires on every host-function call made through the `sync_gas_after` path with no special preconditions, privileges, or origin requirements — any user can deploy and invoke an attacker-controlled contract that triggers it. It is deterministic and reproducible.

## Recommendation
Fix `EngineMeter::charge_ref_time` to actually apply the computed decrement:
```rust
self.fuel = self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;
Ok(Syncable(self.fuel))
```
This mirrors the correct pattern in `substrate/frame/revive/src/metering/weight.rs`'s `sync_remaining_ref_time`, which recomputes and assigns `self.fuel` rather than discarding the computed value.
