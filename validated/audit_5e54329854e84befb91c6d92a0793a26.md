### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor (and `topic`, `api_version`, `webhook_id`) that are all read straight from HTTP headers, but `to_signable_string` — the value that `Utils::HmacValidator` actually verifies against `hmac-sha256` — is defined as `@raw_body` only. `Registry.process` accepts any request whose HMAC matches the app's `client_secret` over the raw body, then trusts `request.shop` (taken from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header) to build the `WebhookMetadata` handed to the host app's handler.

### Finding Description
The equality that should hold is: `shop that produced the HMAC-verified bytes == shop attributed to the webhook event`. In this implementation that equality is never enforced:

- `Request#hmac` decodes the `hmac-sha256` header [1](#0-0) .
- `Request#to_signable_string` returns only `@raw_body`, excluding every header, including `shop-domain` [2](#0-1) .
- `Request#shop` is read verbatim from the `shop-domain` header with no relation to the signed bytes [3](#0-2) .
- `HmacValidator.validate` only recomputes and compares the HMAC of `to_signable_string` (i.e., the body) [4](#0-3) .
- `Registry.process` gates only on this body HMAC, then forwards `request.shop` — the unauthenticated header — into `WebhookMetadata` passed to the app's handler [5](#0-4) .
- `WebhookMetadata#shop` is a plain `String` field with no further validation, documented as "the shop domain of the webhook" that handler implementations are expected to trust for tenant identification [6](#0-5) , and the shipped docs example uses `data.shop` directly as `shop_domain` when enqueuing tenant-scoped work [7](#0-6) .

Because a single `api_secret_key` is shared by the app across every installed shop, any unprivileged internet user who can install the app on their own (attacker-controlled) shop can capture a legitimately-signed webhook body/HMAC pair for that shop, then replay the identical raw body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still succeed because it never inspects the shop header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This breaks the tenant-identity boundary the gem is documented to provide ("`shop`, `String` - The shop domain of the webhook"). Any host application that uses `data.shop` from `WebhookMetadata` to route, attribute, or authorize webhook-driven side effects (as the gem's own usage docs recommend) can be made to process attacker-crafted, attacker-signed-looking data under a victim shop's identity — a cross-tenant data-integrity/confusion issue reachable by any unprivileged actor who installs the app once.

### Likelihood Explanation
Likelihood is high: installing a Shopify app on a free/dev store is trivial for any external actor, no privileged credentials of the target are needed, and the only work required is capturing one webhook delivery (or synthesizing a body of choice, since the attacker owns the shop that produced the signature) and replaying it with a modified header — an operation fully within reach of `curl`/basic HTTP tooling.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the signed payload to the shop domain (e.g., include the shop domain in `to_signable_string`, or independently confirm the shop against a shop-specific webhook registration/secret) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining a valid webhook delivery: body `B` and header `x-shopify-hmac-sha256: H` (a correct HMAC-SHA256 of `B` under the app's shared `client_secret`).
2. Attacker replays this exact request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only [4](#0-3)  and it matches `H`, so `Registry.process` proceeds [8](#0-7) .
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [9](#0-8)  and performs tenant-scoped work as if the victim shop sent it.
