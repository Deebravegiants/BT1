### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/checks the HMAC exclusively over that body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers and are never part of the signed material, yet `Registry.process` forwards `request.shop` directly into `WebhookMetadata` and hands it to the app's handler as the authenticated tenant identifier.

### Finding Description
`Request#hmac` and `Request#to_signable_string` establish the binding checked by `HmacValidator.validate`: [1](#0-0) [1](#0-0) 

`to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers (`shopify_header("shop-domain")`, etc.) and are excluded from the signed string entirely: [2](#0-1) 

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC — again, only the body is covered: [3](#0-2) 

`Registry.process` then treats a valid body HMAC as proof that the entire request — including `request.shop` — is authentic, and passes that unauthenticated `shop` value straight into the handler-facing `WebhookMetadata`: [4](#0-3) 

The equality the gem implicitly claims to enforce is: `shop that the app's handler acts on == shop that produced the HMAC-signed body`. In reality, `hmac(raw_body, secret) == valid` is the only fact proven; `request.shop` is uncorrelated header data. This is the same defect class as the reported issue — a value ("shop", analogous to the protocol fee) that is used by downstream logic (`WebhookMetadata`/handler, analogous to the pool reserves) is never bound to/removed from the verified quantity (the HMAC, analogous to the reserve accounting), so it can be substituted freely as long as the signed body itself matches something the attacker legitimately obtained.

### Impact Explanation
An unprivileged internet user who can install the app on their own (e.g., free trial) shop can trigger any real webhook event for that shop (place an order, edit a customer, etc.), capture the raw POST body and its valid `X-Shopify-Hmac-Sha256` value, and then replay that exact body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a different, victim shop. Because the HMAC only covers the body, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` dispatches `WebhookMetadata.new(shop: <victim-shop>, body: <attacker's own legitimate payload>, ...)` to the host application's handler. Any host app that uses `data.shop` (as the gem's own documentation and generated `WebhookMetadata` instruct) to select which tenant's session/record to mutate will act on the victim shop using attacker-supplied data — a cross-tenant data/state confusion crossing the shop-identity boundary that the app relies on this gem to enforce.

### Likelihood Explanation
Any internet user can obtain a Shopify development/trial store for free, install the target app there, and generate a legitimately signed webhook body for an arbitrary topic already registered by the app (this includes the mandatory topics `shop/redact`, `customers/redact`, `customers/data_request` that every app must support). Forging the header swap requires no cryptographic secret — only a normal HTTP client — since headers are not part of the signed material. This makes the likelihood high once an attacker chooses to exploit it.

### Recommendation
- Short term: include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the string that is HMAC-verified (or otherwise cryptographically bind them to the body), so that `Registry.process` cannot trust `request.shop` unless it was part of the signed material.
- Long term: require callers to supply and validate an expected/whitelisted shop (e.g., pass the expected shop or session into `Registry.process`, and raise if `request.shop` does not match), and add tests asserting that mismatched header/body combinations are rejected even when the body-only HMAC is valid.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets a registered webhook topic fire (e.g., `orders/create`), capturing:
   - Raw body `B`
   - Valid header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`
2. Attacker sends a new HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Headers: `X-Shopify-Hmac-Sha256: H` (unchanged), `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (changed)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)`, which equals `H`, so validation passes.
4. `Registry.process` dispatches `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` to the app's handler, which acts on `victim-shop.myshopify.com` using data that actually originated from the attacker's own store — demonstrating the shop identity was never authenticated by the HMAC.
