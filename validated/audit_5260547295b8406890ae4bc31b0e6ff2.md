### Title
Webhook `shop` Identity Is Not Covered By The HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw body for HMAC validation, but exposes `shop` (the merchant identity used downstream) from an HTTP header that is never included in that signed content. Any party capable of obtaining one valid `(raw_body, hmac)` pair for a webhook delivered to their own shop can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic for the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is read straight from an unauthenticated header, independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, with no additional check binding `shop` to the signed payload: [3](#0-2) 

This is the same bug class as the referenced report: a field the application relies on for identity (`shop`, analogous to the mis-indexed swap output) is consumed without being part of the value that was actually cryptographically verified (analogous to trusting an unverified array index instead of the verified one). Here, the equality the gem implicitly assumes but does not enforce is:

`shop used for HMAC verification == shop attributed to the processed webhook`

but in reality only the body is bound by the HMAC, so this equality can be broken.

Concretely: `HmacValidator.validate` (used by `Registry.process`) computes the signature purely from `verifiable_query.to_signable_string`, which for `Request` is `@raw_body` — `shop` is not an input to the signature at all: [4](#0-3) 

### Impact Explanation
Because the `api_secret_key` is shared across all shops that install a given app, an attacker who installs the app on their own (even free/dev) store receives legitimate webhooks whose body content they largely control (e.g., `products/create`, `orders/create` payloads they trigger themselves) signed with a valid HMAC using the app's secret. They can then send an HTTP request directly to the app's webhook endpoint with that same `raw_body` + `hmac-sha256` header, but an `x-shopify-shop-domain` header set to a victim shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and dispatch the handler with `shop` set to the victim's domain. Any downstream logic in the host application that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete will act on the victim's tenant using attacker-controlled data — a cross-tenant data integrity/confidentiality breach reachable without credentials belonging to the victim, the app's `client_secret`, or any TLS interception.

### Likelihood Explanation
The attacker only needs the ability to install the target (public) app on any shop they control and to send a direct HTTP POST to the app's public webhook endpoint — both are unprivileged-internet-user capabilities. No access token, secret, or MITM is required; the only requirement is knowing the app's webhook endpoint URL, which is typically public/discoverable for embedded apps.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed content, or otherwise verify it out-of-band (e.g., cross-check `shop` against the shop associated with the webhook subscription/topic via a server-side lookup before trusting it), rather than trusting an unauthenticated header field once the body-only HMAC check passes.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and triggers, e.g., a products/create webhook with attacker-controlled body.
# Shopify computes:
#   hmac = HMAC-SHA256(api_secret_key, raw_body)
# and delivers headers including:
#   x-shopify-shop-domain: attacker.myshopify.com
#   x-shopify-hmac-sha256: <valid hmac for raw_body>

# Attacker replays directly to the app's webhook endpoint, keeping raw_body
# and the hmac header identical, but forging the shop header:
POST /webhooks HTTP/1.1
x-shopify-topic: products/create
x-shopify-hmac-sha256: <same valid hmac, unchanged>
x-shopify-shop-domain: victim-shop.myshopify.com   # forged
Content-Type: application/json

<same raw_body used to compute the hmac above>

# ShopifyAPI::Webhooks::Registry.process(request) validates only the body's HMAC
# (lib/shopify_api/webhooks/registry.rb:190, lib/shopify_api/webhooks/request.rb:35-38)
# and then hands the handler WebhookMetadata with shop: "victim-shop.myshopify.com",
# even though that domain was never authenticated.
```
