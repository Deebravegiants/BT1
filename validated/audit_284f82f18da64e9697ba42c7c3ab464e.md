### Title
Webhook shop identity is not bound to the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` identity used by `Registry.process` to route the webhook to the merchant's handler comes from an unsigned header. This breaks the binding "shop authenticated by HMAC == shop acted upon by the handler."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the body) against the secret — it never checks that the asserted `shop` is the shop that produced that body: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, and then forwards the **unauthenticated** `request.shop` value straight to the handler as the tenant identity: [4](#0-3) 

Because a single app-level `api_secret_key` is shared across every merchant that installs the app (there is no per-shop signing secret), any actor who legitimately installs the app on a shop they control can trigger a webhook for that shop, capture the valid `(body, hmac)` pair, and replay it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. The signature will still validate (it only attests to the body, not the shop), but `WebhookMetadata.shop` handed to the app's handler will be the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged app installer can make the gem report webhook events as belonging to an arbitrary victim shop. Any downstream logic that trusts `WebhookMetadata#shop` for tenant-scoped actions (e.g. uninstall cleanup, data sync, entitlement changes keyed by shop) can be tricked into acting on the wrong tenant's data, i.e. cross-tenant access — this satisfies the Critical impact bar for cross-tenant access.

### Likelihood Explanation
Likelihood is high for any app that allows self-serve installs (the normal Shopify app flow): an attacker only needs to install the app on their own (or a throwaway) store to legitimately receive a validly-HMAC'd webhook, then can freely resend it with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or any other party's credentials is required.

### Recommendation
Bind the shop identity into the verified material instead of trusting an unauthenticated header:
- Include the shop domain in the signable content used for HMAC verification (if Shopify's webhook signature scheme doesn't cover it), or
- Cross-check `request.shop` against the shop associated with the specific webhook subscription/session the payload should have come from, rejecting the request if they don't match, before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a legitimate webhook installation and thus valid HMAC signatures for that shop.
2. Attacker triggers (or waits for) any webhook event on `attacker-shop.myshopify.com`, capturing `raw_body` and its valid `x-shopify-hmac-sha256` value.
3. Attacker POSTs that exact `raw_body`/HMAC pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload never originated from that shop.
