Audit Report

## Title
Unbounded JWT Replay Cache Growth Enables Memory Exhaustion in Gateway HTTP Trigger Authorization - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
The gateway's HTTP-trigger JWT replay-protection cache (`jwtReplayCache`) is a plain `map[string]time.Time` keyed by the attacker-supplied JWT `jti` claim, with no maximum-size bound and only a fixed periodic time-based cleanup. Because `Authorize` (which calls `recordUsage`, inserting into this map) runs before `checkRateLimit` in `HandleUserTriggerRequest`, any workflow signer can flood the cache with unique `jti` values faster than cleanup can reclaim them, consuming gateway memory without being throttled by the per-workflow-owner rate limiter.

## Finding Description
`jwtReplayCache` is defined as an unbounded map [1](#0-0) . In `Authorize`, after JWT signature verification and workflow-signer authorization succeed, `h.jwtCache.recordUsage(claims.ID)` inserts the JWT's `jti` into the cache [2](#0-1) , and `recordUsage` performs an unconditional insert with no capacity check [3](#0-2) . Cleanup only happens on a fixed periodic ticker keyed to `JWTReplayPeriodMs`, not bounded by cache size [4](#0-3) [5](#0-4) .

Critically, in `HandleUserTriggerRequest`, `authorizeRequest` (which triggers `Authorize` → `recordUsage`) executes before `checkRateLimit` [6](#0-5) . This confirms the ordering claim: the per-workflow-owner rate limiter (`h.userRateLimiter.AllowErr`) in `checkRateLimit` [7](#0-6)  cannot prevent JWT-cache writes from occurring, since the cache insertion has already happened by the time the rate limiter is consulted.

I reviewed the surrounding request pipeline for any other mitigating control. At the HTTP server layer, only a total request-body size limit (`MaxRequestBytesLimiter`) is enforced [8](#0-7) ; there is no per-request-count or per-IP rate limiting applied before `ProcessRequest` dispatches into `HandleJSONRPCUserMessage` → `HandleUserTriggerRequest`. The `gatewayHandler` does construct several rate limiters (`globalNodeRateLimiter`, `perNodeRateLimiters`, `mtlsRequestRateLimiter`, `userRateLimiter`) [9](#0-8) , but the node-facing ones (`globalNodeRateLimiter`, `perNodeRateLimiters`) only gate node-to-gateway messages via `HandleNodeMessage` [10](#0-9) , not user-facing trigger requests, and the only user-facing limiter (`userRateLimiter`) is applied in `checkRateLimit`, which runs after authorization as shown above. This confirms no existing control bounds JWT-cache growth ahead of, or independent from, the per-owner rate limiter.

## Impact Explanation
This maps to a service-availability / memory-exhaustion impact on the gateway's internet-facing HTTP trigger path. An attacker who is an authorized signer for at least one registered workflow can submit a high volume of uniquely-`jti`'d, validly-signed JWTs within a single `JWTReplayPeriodMs` cleanup window, each adding an entry to `jwtCache.cache` before the per-workflow-owner rate limiter is even consulted. Since workflow registration is described as a low-barrier self-service action, this is reachable by an attacker with minimal privilege (their own registered workflow), not requiring operator/admin access. Sustained abuse could degrade or crash the gateway process for all users sharing that DON/shard, which is an in-scope "gateway request impersonation/availability" class of impact given the internet-facing gateway cache is explicitly in scope.

## Likelihood Explanation
Likelihood is moderate. The attacker must possess a private key registered as an authorized signer for a workflow ID present in `authorizedKeys` — an unprivileged but non-anonymous precondition, satisfiable by self-registering a workflow through the normal, low-barrier registration flow described in the report. Generating new signed JWTs with a fresh `jti` per request is computationally cheap (no proof-of-work requirement), and nothing in `Authorize`, `recordUsage`, or the cleanup ticker imposes any hard cap on the total number of entries, so the attack is straightforward and repeatable.

## Recommendation
- Add a hard maximum-size bound to `jwtReplayCache` (e.g., reject or evict-oldest once a configurable `MaxJWTCacheEntries` is reached), replacing the unbounded `map[string]time.Time` with an LRU or capacity-bounded TTL cache.
- Reorder `HandleUserTriggerRequest` so `checkRateLimit` runs before `authorizeRequest`/`Authorize`, ensuring JWT-cache writes are also bounded by the per-workflow-owner rate limiter.
- Consider adding a per-workflow-owner cap on outstanding/cached `jti` entries independent of the global cleanup ticker.

## Proof of Concept
1. Register a workflow and obtain a signer key authorized in `WorkflowMetadataHandler.authorizedKeys` (standard self-service registration flow).
2. Using `utils.CreateRequestJWT`, generate a large number of distinct, validly-signed JWTs (unique `jti` per request) for `gateway_common.MethodWorkflowExecute` HTTP trigger requests.
3. Submit these requests to the gateway faster than `JWTReplayPeriodMs` elapses; each call flows through `HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize` → `jwtCache.recordUsage(claims.ID)` (`workflow_metadata_handler.go:105`), inserting into `jwtCache.cache` (`workflow_metadata_handler.go:411`) before `checkRateLimit` is reached (`http_trigger_handler.go:111`).
4. Observe `jwtCache.cache` size (exposed via `RecordJwtCacheSize` metric) and gateway process memory grow proportionally to the number of submitted requests, unbounded by any capacity limit, until the next scheduled cleanup tick.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

// cleanupOldEntries removes expired entries from the cache
func (cache *jwtReplayCache) cleanupOldEntries(cutoff time.Time) int {
	cache.mu.Lock()
	defer cache.mu.Unlock()
	var expiredCount int
	for jti, createdAt := range cache.cache {
		if createdAt.Before(cutoff) {
			delete(cache.cache, jti)
			expiredCount++
		}
	}
	return expiredCount
}

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	orgID := h.resolveOrgID(ctx, workflowRef.workflowOwner)
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Org: orgID, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}
