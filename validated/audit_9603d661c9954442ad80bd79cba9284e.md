### Title
Cross-fork transaction replay due to reliance on ancestor block hash without a persistent chain identifier - (File: `chain/chain/src/store/utils.rs`)

### Summary
NEAR's replay-protection for `SignedTransaction` relies solely on the transaction's `block_hash` field being validated as an ancestor of the block that includes it, within a bounded `transaction_validity_period`. There is no persistent, chain-specific value (analogous to Ethereum's EIP-155 `chain_id`) embedded in the signed `Transaction` payload. In the event of a protocol hard fork that produces two independently-continuing chains sharing identical pre-fork history, a transaction signed and referencing a common pre-fork `block_hash` remains a valid ancestor on *both* resulting chains for the duration of `transaction_validity_period`, allowing the identical signed transaction to be replayed and independently executed on both forks.

### Finding Description
A NEAR `Transaction` contains `signer_id`, `public_key`, `nonce`, `receiver_id`, `block_hash`, and `actions` — no field ties the signature to a specific, permanently unique chain instance [1](#0-0) . Replay protection instead depends entirely on `check_transaction_validity_period`, which confirms that `base_block_hash` (the tx's `block_hash`) is an ancestor of the current chain head within `transaction_validity_period` blocks [2](#0-1) .

The ancestor determination in `validity_period_validate_is_ancestor` walks the local node's own canonical chain (`get_block_hash_by_height`, `get_block_header_on_chain_by_height`) to confirm the base block is on that chain [3](#0-2) . This check is purely local and history-based — it has no notion of a globally unique "chain instance" identifier. If a hard fork produces two chains, A and B, that share identical history up to the fork height, then any block hash before the fork height is a valid ancestor on *both* A's and B's canonical chains. A transaction signed against such a shared pre-fork `block_hash` will pass `check_transaction_validity_period` identically on both A and B during the whole `transaction_validity_period` window (up to 86400 blocks / ~1 day on mainnet) [4](#0-3) .

This mirrors the reported bug class: the "SOURCE_IDENTIFIER" in the external report is a static value that does not change across a fork, allowing replay; here, nearcore's replay defense is anchored to shared pre-fork chain history rather than to a value that becomes unique per fork, and there is no equivalent to Wormhole's `chainId()`-based binding. This differs from Ethereum's EIP-155 chain_id design specifically introduced after the ETH/ETC fork to prevent exactly this class of replay.

Access-key nonces are advanced independently by each fork's own state, so consuming the transaction on chain A does not prevent it from later being (re-)submitted and separately applied on chain B, since B has not yet seen/applied that transaction (nonce for the signer/key on B is still unadvanced) [5](#0-4) .

### Impact Explanation
If a hard fork produces two viable, independently operated NEAR networks sharing pre-fork history (the scenario explicitly called out in the source report), any transaction submitted on one fork within the `transaction_validity_period` window can be independently rebroadcast and applied on the other fork by any observer (transactions and their signatures are public). This results in unauthorized duplicate execution of the same signed action (e.g., duplicate transfers, duplicate function calls, double-spending of the signer's intent) across the two chains — a concrete unauthorized state/balance change analogous to the "double signature acceptance" impact in the source report.

### Likelihood Explanation
Requires an actual nearcore hard fork/chain split producing two independently continuing chains that share pre-fork history — an infrequent, high-impact event, matching the "Medium" severity/likelihood framing used in the source report. Given `transaction_validity_period` is roughly a day on mainnet, there is a meaningful window post-fork during which in-flight or newly rebroadcast transactions can be replayed cross-fork.

### Recommendation
Bind transaction signatures to a persistent, fork-specific identifier in addition to the block-hash-based freshness check — e.g., include the genesis config's `chain_id`/genesis hash (already used as `GenesisId` in the network handshake protocol, see `chain/network/src/network_protocol/network.proto`) or an explicit protocol/hardfork epoch identifier as part of the signed `Transaction` payload, analogous to EIP-155. This ensures that after a hard fork, transactions signed on the old chain, or specifically for a different network instance, cannot validate on the newly diverged chain, even if the referenced block hash exists in both chains' shared history.

### Proof of Concept
1. Chain forks at height `H`, producing chain A and chain B that share identical block history and account/access-key state for heights `<= H`.
2. User signs a `SignedTransaction` with `block_hash` set to a block at height `H-1` (shared ancestor), spending funds from account `X` using access key nonce `N`.
3. Submit the transaction to chain A: `check_transaction_validity_period` passes (`H-1` is an ancestor of A's head within `transaction_validity_period`) as shown in `chain/chain/src/store/utils.rs` lines 56-75; the transaction executes, advancing `X`'s nonce to `N+1` on chain A only.
4. Rebroadcast the identical signed bytes to chain B within `transaction_validity_period`: `check_transaction_validity_period` passes independently on B (same shared ancestor block, same local-chain ancestor walk logic), and nonce `N` is still unused on B, so the transaction executes there as well — resulting in the same signed action being applied twice across two independent chains from a single signature.

pub fn check_transaction_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_header.height().saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_header.height() > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is an ancestor of `prev`)
    validity_period_validate_is_ancestor(&base_header, prev_block_header, chain_store)
}

/// Check if base_header is an ancestor of prev_block_header.
/// Used in check_transaction_validity_period.
fn validity_period_validate_is_ancestor(
    base_header: &BlockHeader,
    prev_block_header: &BlockHeader,
    chain_store: &ChainStoreAdapter,
) -> Result<(), InvalidTxError> {
    let base_height = base_header.height();
    let prev_height = prev_block_header.height();
    let base_block_hash = base_header.hash();

    // Base can't be an ancestor of prev if its height is bigger
    if base_height > prev_height {
        return Err(InvalidTxError::InvalidChain);
    }

    // if both are on the canonical chain, comparing height is sufficient
    // we special case this because it is expected that this scenario will happen in most cases.
    if let Ok(base_block_hash_by_height) = chain_store.get_block_hash_by_height(base_height) {
        if &base_block_hash_by_height == base_block_hash {
            if let Ok(prev_hash) = chain_store.get_block_hash_by_height(prev_height) {
                if &prev_hash == prev_block_header.hash() {
                    return Ok(());
                }
            }
        }
    }

    // if the base block height is smaller than `last_final_height` we only need to check
    // whether the base block is the same as the one with that height on the canonical fork.
    // Otherwise we walk back the chain to check whether base block is on the same chain.
    let last_final_height = chain_store
        .get_block_height(prev_block_header.last_final_block())
        .map_err(|_| InvalidTxError::InvalidChain)?;

    if last_final_height >= base_height {
        let base_block_hash_by_height = chain_store
            .get_block_hash_by_height(base_height)
            .map_err(|_| InvalidTxError::InvalidChain)?;
        if &base_block_hash_by_height == base_block_hash {
            Ok(())
        } else {
            Err(InvalidTxError::InvalidChain)
        }
    } else {
        let header =
            get_block_header_on_chain_by_height(chain_store, prev_block_header.hash(), base_height)
                .map_err(|_| InvalidTxError::InvalidChain)?;
        if header.hash() == base_block_hash { Ok(()) } else { Err(InvalidTxError::InvalidChain) }
    }
