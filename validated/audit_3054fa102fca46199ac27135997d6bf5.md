### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook using an HMAC that is computed only over the raw request body, while the `shop` value handed to the application's webhook handler is taken from an HTTP header that is never included in that HMAC computation. Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app can obtain a validly-signed webhook body and then present that same body with a different `x-shopify-shop-domain` / `shopify-shop-domain` header, causing the gem to accept it as an authentic webhook "from" an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC using `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac-sha256` header, using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity and forwards it, unchecked, into the data structure passed to the app's handler: [4](#0-3) 

The `api_secret_key` used for this HMAC is a single value configured once for the whole app via `Context.setup`, not a per-shop secret: [5](#0-4) 

The identity binding that should hold is: `hmac-signed bytes == bytes that determine which shop the webhook is attributed to`. In this implementation that equality does not hold — `to_signable_string` (the signed bytes) excludes the `shop` header (the bytes that determine tenant attribution). Since the signing secret is shared across all shops on the same app, a webhook body signed for shop A validates successfully when replayed with the `shop-domain` header changed to shop B.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), which the rules classify as Critical. An attacker who has installed the app on their own store (a normal, unprivileged action) can capture one legitimately signed webhook payload and immediately reuse it against the same endpoint with an arbitrary victim shop's domain in the header. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen value, with body content the attacker also controls (by triggering whichever webhook topic produces the payload they want on their own store, e.g. an `app/uninstalled` or `orders/create` event body). Any downstream logic keyed off `data.shop` (e.g. looking up per-shop settings, revoking access, updating order state per tenant) can be tricked into acting as though the event came from a different shop.

### Likelihood Explanation
Likelihood is high for any app author who trusts `WebhookMetadata#shop` from this gem as an authenticated tenant identifier — which is the documented/intended usage of the `process` API. No credentials beyond the ability to install the app on one's own store (or observe/replay one's own webhook traffic) are required; the `api_secret_key` and any merchant access token are never needed by the attacker.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the HMAC-signed content, or otherwise cryptographically bind the header-derived shop to the signed body (e.g. include the shop domain in the canonical string that is HMAC'd, mirroring how `AuthQuery#to_signable_string` includes `shop` as part of the signed OAuth callback query). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be independently verified by the host application (e.g. by cross-checking against a known/installed shop list) before being trusted as a tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with an attacker-chosen JSON body.
2. Attacker's endpoint (or a network capture) records the valid request, including the `x-shopify-hmac-sha256` header, which was computed over the raw body using the app's single, app-wide `api_secret_key`:
```ruby
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
```
3. Attacker resends the identical `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb` / `lib/shopify_api/webhooks/request.rb#to_signable_string`).
5. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, as shown in `lib/shopify_api/webhooks/registry.rb:198-199`, causing the app to process attacker-controlled data attributed to the victim shop.
