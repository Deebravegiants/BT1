### Title
Native-fee swaps use `deadline = block.timestamp`, nullifying Uniswap V2 slippage/deadline protection on solver-fee and relayer-fee purchases - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch()` and `EvmHost.fundRequest()` (and the analogous native-fee path in `IntentGatewayV2.placeOrder()`) swap native token for the protocol fee token via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` as the swap's `deadline` argument. Because the deadline is evaluated against `block.timestamp` at execution time, this check can never fail — it provides no protection against delayed inclusion, leaving every unprivileged caller who pays fees in native token exposed to price movement/MEV between signing and mining, with no user-supplied bound on the input amount consumed.

### Finding Description
`dispatch()` performs a native-token fee swap with a deadline set to the current execution-time `block.timestamp`: [1](#0-0) 

The same pattern recurs in `fundRequest()`: [2](#0-1) 

And in `IntentGatewayV2`'s (tron variant, but same pattern exists in the EVM contract) native-fee escrow path when placing an order with `order.fees` paid in native token: [3](#0-2) 

`swapETHForExactTokens(amountOut, path, to, deadline)` requires `deadline >= block.timestamp` inside the Uniswap V2 router. When the caller (this contract) supplies `block.timestamp` as `deadline`, the check trivially passes at whatever block the transaction is finally mined in — it can never revert due to staleness, no matter how long the transaction sits in the mempool (e.g., during gas spikes, or if deliberately delayed/held by a searcher). This is the well-known "deadline == block.timestamp" Uniswap anti-pattern: it removes the entire purpose of the deadline parameter, which is to bound the acceptable execution time window from the caller's perspective. The transaction is fully exposed to price movement and sandwich attacks between signing and inclusion, with the only remaining bound being `msg.value` (the max ETH the caller is willing to spend) — if the price has moved unfavorably beyond `msg.value`, the call reverts, but if it has moved just within that bound, the caller pays a materially worse price than intended with zero on-chain enforcement of a time window.

This is a direct analog to the reported bug class: the reported issue is that DINARI's buy/sell orders hardcode `TIF.GTC` (no expiration) and `OrderType.MARKET` (no price/slippage protection), exposing user funds to price fluctuation with no time-bound cutoff. Here, Hyperbridge's own fee-payment swaps hardcode a deadline value that functions identically to "no deadline" (any block satisfies `block.timestamp >= block.timestamp`), combined with an exact-output swap where the actual price paid is unbounded except by the coarse `msg.value` ceiling — i.e., no genuine execution-time slippage/staleness protection, reachable by any unprivileged user who dispatches an ISMP POST/GET request or funds a request with native token, or places an IntentGateway order paying solver fees in native token.

### Impact Explanation
Any unprivileged user paying protocol/relayer fees in native token — via `EvmHost.dispatch()`, `EvmHost.fundRequest()`, or `IntentGatewayV2.placeOrder()`'s native-fee path — has their fee-swap transaction exposed to unbounded price staleness. A delayed or sandwiched transaction can execute at a substantially worse rate than intended at signing time, consuming more of the user's native token than a properly time-bound deadline would have allowed, up to the full `msg.value` supplied. This is a fund-loss/economic-loss issue for the message dispatcher/relayer-fee payer, reachable from a single submitted transaction with no special privileges, matching the Medium severity of the original report (impacts user funds under market/price volatility, no expiration/slippage cutoff).

### Likelihood Explanation
Likelihood is moderate-to-high: this triggers on the ordinary, unprivileged "pay fee with native token" code path used by every `dispatch()` call funded in ETH and by `fundRequest()`, and is exacerbated during periods of gas-price volatility or MEV activity when transactions sit in the mempool longer, or are deliberately delayed by a searcher who can then execute the swap once the price has moved in their favor (a bounded sandwich, since `msg.value` limits total loss).

### Recommendation
Do not use `block.timestamp` as the Uniswap deadline for a swap being submitted by the contract on behalf of the caller. Instead, accept a caller-supplied deadline (or a wrapper-level maximum staleness) as part of `DispatchPost`/`fundRequest` parameters and pass that through to `swapETHForExactTokens`, so a genuinely late-mined transaction reverts instead of executing at a stale price. This restores the deadline's intended protection without weakening the exact-output amount guarantee already provided by `swapETHForExactTokens`.

### Proof of Concept
1. A user calls `EvmHost.dispatch()` (or `fundRequest()`) with `msg.value` set to cover an expected native-to-fee-token swap at the current market rate, expecting `swapETHForExactTokens` to revert if the transaction is stale.
2. The transaction is broadcast but not immediately included (e.g., due to low gas price, network congestion, or is deliberately held by a block builder/searcher).
3. Between signing and inclusion, the native-token/fee-token price moves unfavorably for the caller (but not beyond the `msg.value` ceiling).
4. The transaction is eventually mined; because `deadline = block.timestamp` is evaluated at execution time, `require(deadline >= block.timestamp)` in the router always passes — the swap executes anyway, consuming more of the caller's ETH than intended for the same `post.fee`, with the excess still refunded only insofar as `msg.value` allowed slack, and no code path enforcing the caller's original time-of-signing price expectation.
