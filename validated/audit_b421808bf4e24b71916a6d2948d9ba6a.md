### Title
Unbounded in-memory mempool bid cache in the intents-coprocessor RPC service enables node-memory exhaustion DoS - (File: modules/pallets/intents-coprocessor/rpc/src/lib.rs)

### Summary
The `intents-coprocessor` RPC service maintains an in-memory `BidCache` (`HashMap<H256, OrderBids>`) that is populated purely from transactions observed in the node's transaction pool, before they are ever included in a block. There is no cap on the number of distinct order commitments or bids tracked, and the only eviction mechanism is a time-based sweep (`remove_expired`) run on a fixed interval. An unprivileged party can flood the mempool with `place_bid` extrinsics carrying unique commitments to grow this map without bound, similar to the xgrammar unbounded compiled-grammar cache (CVE-2025-32381).

### Finding Description
`BidCache::insert` is invoked from `run_bid_watcher`, which subscribes to `pool.import_notification_stream()` and caches every `place_bid` extrinsic that becomes "ready" in the transaction pool — well before block inclusion or finalization: [1](#0-0) 

The cache itself has no capacity bound; each unique `commitment` (`H256`) creates a new `OrderBids` entry, and eviction only happens on a wall-clock TTL sweep, not a size limit: [2](#0-1) 

Because entries are keyed by attacker-controlled `commitment` values and each entry stores a `Vec<BidEntry>` (with `filler` and `user_op` byte vectors of attacker-supplied size), an attacker who can get transactions accepted into the ready transaction pool — which only requires passing the node's normal extrinsic validity checks (signature, nonce, fee payment), not block inclusion or finality — can insert an effectively unbounded number of entries into node memory. Any node running this RPC handler shares this exposure. Unlike the on-chain `Bids` storage map (which is subject to blockchain state-growth economics and can be capped/pruned by governance), this cache lives purely in the collator/full-node's RAM and is not constrained by any of the protocol's on-chain bounded types (`BoundedVec`, `BoundedBTreeSet`, etc.) used elsewhere in the pallet.

### Impact Explanation
An attacker can cause unbounded memory growth on any node running the intents RPC service by submitting many low-cost `place_bid` transactions with unique commitments and maximally sized `user_op` payloads into the transaction pool (transactions do not need to be included in a block or even remain valid after the tx-pool's usual eviction — they only need to reach "ready" state once to be captured by `import_notification_stream`). Sustained pressure faster than the cleanup interval, or simply a large number of distinct never-expiring-fast-enough entries, can exhaust node memory, causing the RPC/collator process to crash or become unresponsive — a denial of service against bid discovery for the intents/solver market and any node running this component.

### Likelihood Explanation
Likelihood is high for any deployment exposing this RPC handler: submitting `place_bid` extrinsics is available to any unprivileged account with modest transaction fees, and the tx-pool "ready" notification stream fires for many transactions that will never be included in a final block (e.g., transactions bumped out of the pool, replaced, or simply not yet included), meaning an attacker does not need the transaction to succeed on-chain to poison this cache — only to be briefly valid/ready. Repeating this at a rate exceeding `cleanup_interval` (configurable, but bounded by practical trade-offs against RPC responsiveness) sustains unbounded growth.

### Recommendation
Bound the `BidCache`:
- Impose a maximum total number of tracked commitments and/or a maximum number of bids per commitment (mirroring `MAX_ON_CHAIN_BIDS` already used for the on-chain read path), evicting oldest entries (e.g., via an LRU or a bounded ring keyed by insertion order) when the cap is exceeded.
- Impose a maximum size on cached `filler`/`user_op` byte vectors before insertion, rejecting or truncating anything from the tx pool exceeding the on-chain `place_bid` weight/length limits.
- Consider evicting/ignoring cache entries for transactions that are later removed from the pool (dropped/invalid), rather than relying solely on TTL.

### Proof of Concept
1. Start a node running `IntentsRpcHandler`/`run_bid_watcher` with the intents-coprocessor pallet.
2. From an unprivileged account (or many funded accounts), submit a large number of `place_bid(commitment, user_op)` extrinsics to the node's transaction pool, each with a freshly-random `commitment` and a maximally-sized `user_op` payload, at a rate exceeding `cleanup_interval`.
3. Observe `BidCache::bids` (`HashMap<H256, OrderBids>`) grow unbounded in the node's memory as `run_bid_watcher`'s `import_notification_stream` handler calls `bid_cache.insert` for every observed transaction: [3](#0-2) 
4. Continue submission faster than the TTL sweep interval to prevent `remove_expired` from reclaiming memory, eventually exhausting the node's available RAM.

/// In-memory bid cache.
pub struct BidCache {
	bids: RwLock<HashMap<H256, OrderBids>>,
	ttl: Duration,
}

impl BidCache {
	pub fn new(ttl: Duration) -> Self {
		Self { bids: RwLock::new(HashMap::new()), ttl }
	}

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn get_bids(&self, commitment: &H256) -> Result<BTreeSet<RpcBidInfo>, String> {
		let bids = self.bids.read().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		Ok(bids
			.get(commitment)
			.map(|order| {
				order
					.entries
					.iter()
					.map(|e| RpcBidInfo {
						commitment: *commitment,
						filler: e.filler.clone(),
						user_op: e.user_op.clone(),
					})
					.collect()
			})
			.unwrap_or_default())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}
