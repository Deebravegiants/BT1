### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the webhook dispatcher come from unsigned HTTP headers. Any party who can obtain one validly-signed webhook body (e.g., because they installed the app on their own store) can replay that body with a forged `shop-domain`/`topic` header pair to make the receiving app process the payload as if it belonged to a different tenant or a different event type.

### Finding Description
`Utils::HmacValidator.validate` verifies a signature computed from `verifiable_query.to_signable_string` against the `hmac` header/value: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never included in the signed content: [3](#0-2) 

`Registry.process` only checks the body HMAC before dispatching to the handler with the header-derived `shop`, `topic`, and `webhook_id`: [4](#0-3) 

This breaks the intended identity binding: `hmac_verified(raw_body) == true` is treated as equivalent to `hmac_verified(raw_body, shop, topic, webhook_id) == true`, but the gem only proves the former. Since `api_secret_key` is shared across all shops that install a given public app, any unprivileged user who installs the app on their own store will receive genuine, validly-HMAC'd webhook deliveries for their own shop/topic. Because `shop`, `topic`, and `webhook_id` are not part of the signed content, that same attacker can replay the untouched `body` + `hmac` pair while swapping the `x-shopify-shop-domain` and/or `x-shopify-topic` headers to point at a different tenant or a different (and more impactful) event type, and the library will accept it as fully authenticated.

### Impact Explanation
This allows cross-tenant impersonation: an app receiving webhooks keyed on `data.shop`/`data.topic` (as constructed in `Registry.process` via `WebhookMetadata.new(topic:, shop:, body:, ...)`) can be tricked into applying another merchant's data mutation logic to a victim shop's tenant record, or into firing a handler for a topic (e.g., mandatory compliance topics like `customers/redact`, `shop/redact`, or business-critical topics like `app/uninstalled`) that was never actually sent for that shop. This satisfies the "Critical – cross-tenant access" criterion, since the trust boundary between tenants is broken using only a body+HMAC pair the attacker legitimately possesses for their own store.

### Likelihood Explanation
Likelihood is moderate-to-high for any public app: obtaining a valid signed webhook is trivial (install the app on any store you control), and forging headers on an HTTP request to the app's own publicly reachable webhook endpoint requires no special access. The only constraint is that the attacker doesn't fully control the body content (it must be an existing signed body), which limits — but does not eliminate — the practical damage (e.g., replaying `orders/create` payloads to inject fake orders attributed to a victim shop, or replaying `app/uninstalled` to falsely deprovision a victim's app record).

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed content (or otherwise cryptographically bind them to the raw body) so that `HmacValidator.validate` fails whenever any header used for dispatch differs from what Shopify actually signed. At minimum, cross-check the `shop` header against a known/expected tenant (e.g., a shop for which the app has an active session) before invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id": 1, "...": "..."}`
2. Attacker captures `body` and `x-shopify-hmac-sha256` (both untouched, still valid since only body is signed).
3. Attacker sends a new POST to the app's public webhook endpoint with the same `body` and `x-shopify-hmac-sha256`, but headers changed to:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create` (or another topic)
4. `Utils::HmacValidator.validate` succeeds (body unchanged), `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to act on data intended for the attacker's own shop as though it originated from the victim tenant. [5](#0-4) [4](#0-3)

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
