Confirmed: `SignedCommitment.signatures: Vec<SignatureWithAuthorityIndex>` and `MmrProof.authority_proof: Vec<[u8; 32]>` are unbounded (`Vec`, not `BoundedVec`) ` [1](#0-0) `. There's no per-signature or per-authority-proof cap enforced before the expensive cryptographic loop runs.

### Title
Denial of Service via Unbounded BEEFY Signature/Authority-Proof Arrays Verified for Free During Unsigned Extrinsic Validation - (File: `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic lets anyone submit ISMP messages, including a `Message::Consensus` carrying a raw naive BEEFY proof, for free ` [2](#0-1) `. Both `validate_unsigned` (run by every node for every transaction entering the pool, including gossip) and dispatch itself call `Self::execute(messages.clone())`, which eventually reaches `BeefyConsensusClient::verify_consensus` → `beefy_verifier::verify_consensus` → `verify_mmr_update_proof` ` [3](#0-2) ` ` [4](#0-3) `.

### Finding Description
`verify_mmr_update_proof` iterates over `mmr.signed_commitment.signatures` performing one `secp256k1_recover` and two `keccak256` hashes per element, then builds a merkle multi-proof over all of them:
```
for sig in mmr.signed_commitment.signatures.iter() {
    let uncompressed = H::secp256k1_recover(&commitment_hash.0, &sig.signature)...
    ...
}
let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());
let valid = merkle_proof.verify(..., &authority_indices, &authority_leaves, authority_set.len as usize);
```
` [5](#0-4) `

Neither `SignedCommitment.signatures` nor `MmrProof.authority_proof` is a `BoundedVec` — they SCALE-decode an attacker-controlled `Vec<T>` whose length is limited only by the outer extrinsic's byte size, not by any protocol-level cap tied to the actual authority-set size ` [1](#0-0) `. `check_participation_threshold` only checks that `signatures_length >= 2/3 * authority_set.len + 1` — it never checks an *upper* bound, so an attacker can pad the array with tens of thousands of garbage 65-byte signatures (each ~65 bytes; a multi-MB extrinsic can carry >10⁴–10⁵ entries) ` [6](#0-5) `. Each entry forces a full `secp256k1_recover` + double `keccak256` before the (cheap) merkle-proof check that would ultimately reject the padded set. Crucially, this expensive loop runs during **`validate_unsigned`**, i.e. during transaction-pool validation on every full node that receives the gossiped extrinsic — before any fee is charged and before the transaction is even included in a block ` [7](#0-6) `. This is structurally identical to the Next.js SVG bug: a cheap, unauthenticated request (image URL / unsigned extrinsic) triggers unbounded expensive processing (image parsing / ECDSA recovery loops) on the server/node before any authorization or cost check completes.

### Impact Explanation
An unprivileged attacker (no fee, no signature required, since `handle_unsigned` is `ensure_none`) can submit or gossip a single crafted BEEFY consensus message with an oversized `signatures`/`authority_proof` array. Every node in the network that validates this transaction in its pool (which happens repeatedly — on receipt, on re-validation, on block-building attempts) pays the full CPU cost of thousands of `secp256k1_recover` operations, which is orders of magnitude more expensive than ordinary transaction validation. Submitted repeatedly (and for free, since it's unsigned) this can degrade or stall the transaction pool and consensus liveness of every parachain relying on `pallet-ismp` + `ismp-beefy`, i.e. a network-wide denial of service — a High/Medium severity CWE-407 (uncontrolled resource consumption) issue reachable directly from a single relayed/dispatched extrinsic.

### Likelihood Explanation
High. The path is directly reachable by any unprivileged party: `handle_unsigned` is explicitly designed to accept unsigned/unauthenticated ISMP messages for free ` [8](#0-7) `, and nothing in the type definitions or the verifier bounds the size of `signatures`/`authority_proof` before the expensive cryptographic loop executes. The only mitigating factor is the substrate extrinsic/block size limit, which caps the maximum array length but still permits a large multiple of the actual required signature count.

### Recommendation
- Bound `SignedCommitment.signatures` and `MmrProof.authority_proof` with an explicit maximum length tied to a sane multiple of the known/maximum authority-set size (e.g. via `BoundedVec` or an explicit `ensure!(signatures.len() <= MAX_SIGNATURES)` check performed *before* any `secp256k1_recover` call).
- Reject proofs whose `signatures.len()` exceeds `authority_set.len` (a valid supermajority proof never needs more signatures than there are authorities) before entering the recovery loop.
- Apply the same anti-padding checks to `ParachainProof.parachains`/`proof` and any other unsigned, pre-fee-gated array inputs reachable through `handle_unsigned`'s `validate_unsigned` path, mirroring the size-gating pattern already used in `pallet-call-decompressor`'s `decompress` fix ` [9](#0-8) `.

### Proof of Concept
1. Construct a `Message::Consensus` whose `consensus_proof` is a naive BEEFY `ConsensusMessage` (`PROOF_TYPE_NAIVE` prefix) targeting a live BEEFY consensus state.
2. Set `signed_commitment.signatures` to contain the minimum valid supermajority of real signatures **plus** tens of thousands of additional garbage `SignatureWithAuthorityIndex` entries (random 65-byte blobs) to pad the array up to the maximum extrinsic size allowed by the runtime.
3. Submit this as an unsigned `handle_unsigned([Message::Consensus(...)])` extrinsic to the network.
4. Observe that every full node calls `ValidateUnsigned::validate_unsigned` → `Self::execute` → `verify_mmr_update_proof`, which performs one `secp256k1_recover` per padded signature (tens of thousands of expensive elliptic-curve recoveries) before rejecting the proof — for free, and repeatable, causing sustained CPU load across the network's transaction-pool validators.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}
