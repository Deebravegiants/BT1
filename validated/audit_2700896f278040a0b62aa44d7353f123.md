### Title
`validateLitecoinAddress` accepts version-0x05 legacy P2SH addresses that are format-identical to Bitcoin addresses, letting a BTC address pass as a Litecoin destination - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateLitecoinAddress` treats any base58check string starting with `3` and decoding to version byte `0x05` as a valid Litecoin address, but this is the exact same encoding Bitcoin uses for legacy P2SH addresses. The function itself contains a comment admitting this ambiguity cannot be resolved by format/checksum alone.

### Finding Description
The broken equality: **(chain = Litecoin, address)** validated by `validateAddress` must equal the **(chain, address)** pair that the LTC-denominated bridge payout actually targets.

In `packages/intents-sdk/src/lib/validateAddress.ts`, `validateLitecoinAddress` dispatches on the address's first character: [1](#0-0) 

For addresses starting with `3`, it calls `validateLitecoinBase58Address(address, 0x05)` — the same version byte (`0x05`) used by Bitcoin's legacy P2SH addresses (`validateBtcBase58Address` at lines 140-158 also accepts `0x05`). The function's own comment states: `[Inference] This also matches Bitcoin P2SH; cannot distinguish by prefix+version alone.` (line 522). `validateLitecoinBase58Address` (lines 537-567) only checks: base58 decode succeeds, length is 25 bytes, version byte matches `expectedVersion`, and the double-SHA256 checksum matches — none of these differ between BTC and LTC legacy P2SH encodings, because both networks reuse the identical version byte for this address type.

As a result, `validateAddress('3EktnHQD7RiAE6uzMj2ZifT9YgRrkSgzQX', Chains.Litecoin)` returns `true` even though this string is a genuine, real-world Bitcoin P2SH address, because the underlying base58check payload (version `0x05` + hash160 + checksum) is byte-for-byte identical to what a Litecoin legacy P2SH address would decode to. Nothing downstream in the format validator, and (per my search) nothing found in `poa-bridge.ts`/`omni-bridge.ts` that layers additional chain-specific discrimination on top of `validateAddress`, distinguishes these two cases — the ambiguity is intrinsic to the shared base58check version byte and is not resolvable from the string alone.

### Impact Explanation
If `PoaBridge.validateWithdrawal`/`OmniBridge.validateWithdrawal` resolves `assetInfo.blockchain === Chains.Litecoin` and calls `validateAddress(destinationAddress, Chains.Litecoin)`, a caller-supplied Bitcoin-style legacy P2SH address (`3...`) will pass validation and be embedded into the signed withdrawal intent's payout memo. The bridge will then broadcast an LTC-network payment to the hash160 encoded in that address. Whether the recipient can actually access those LTC funds depends entirely on whether the corresponding redeem script/private key infrastructure has also been set up on the Litecoin network — something the SDK has no way to verify. In the general case (address not controlled the same way on both chains), this results in fund loss with no recovery path, matching the Critical category ("funds delivered to a wrong address/chain with no recovery").

### Likelihood Explanation
This requires: (1) a Litecoin-denominated NEP-141 asset route resolving through PoaBridge/OmniBridge, and (2) the attacker/withdrawing user supplying a `3...`-prefixed address that decodes to version `0x05` — trivially satisfiable since any real Bitcoin P2SH address qualifies, no special crafting needed. The cost to the attacker (or an integrator accidentally forwarding a BTC address for an LTC withdrawal) is zero; the flaw is deterministic and repeatable on every call with such an address. Note this affects only the legacy `3...`/`0x05` P2SH form — the `L.../M...` (0x30/0x32) and `ltc1...` bech32 forms are LTC-specific and not affected.

### Recommendation
Reject legacy `3...`/version `0x05` addresses for Litecoin format validation (or require an explicit LTC-specific address type such as `M.../0x32` or bech32 `ltc1...`), since this legacy form cannot be distinguished from Bitcoin P2SH by format alone. Alternatively, surface this ambiguity to callers/integrators so that bridges refuse `3...`-style destinations for LTC-denominated withdrawals, forcing users to use unambiguous LTC address formats.

### Proof of Concept
```ts
import { describe, expect, it } from "vitest";
import { validateAddress, validateLitecoinAddress } from "./validateAddress";
import { Chains } from "./caip2";

describe("validateLitecoinAddress cross-chain ambiguity", () => {
  it("accepts a real Bitcoin P2SH address as a valid Litecoin address", () => {
    const btcP2SH = "3EktnHQD7RiAE6uzMj2ZifT9YgRrkSgzQX";

    // Same string validates as Bitcoin...
    expect(validateAddress(btcP2SH, Chains.Bitcoin)).toBe(true);

    // ...and ALSO validates as Litecoin, despite never being an LTC address.
    expect(validateAddress(btcP2SH, Chains.Litecoin)).toBe(true);
    expect(validateLitecoinAddress(btcP2SH)).toBe(true);
  });
});
```
This demonstrates the equality break: the same raw string is accepted as valid for two different chains (`Chains.Bitcoin` and `Chains.Litecoin`), confirming that `validateAddress`'s Litecoin branch cannot distinguish a Litecoin-only destination from a Bitcoin-only one for the `3.../0x05` address family.

```typescript
export function validateLitecoinAddress(address: string): boolean {
	const first = address[0];

	// ---- Base58 (mainnet) ----

	// P2PKH: L... (0x30)
	if (first === "L") {
		return validateLitecoinBase58Address(address, 0x30);
	}

	// P2SH (new): M... (0x32)
	if (first === "M") {
		return validateLitecoinBase58Address(address, 0x32);
	}

	// P2SH (legacy): 3... (0x05)
	// [Inference] This also matches Bitcoin P2SH; cannot distinguish by prefix+version alone.
	if (first === "3") {
		return validateLitecoinBase58Address(address, 0x05);
	}
```
