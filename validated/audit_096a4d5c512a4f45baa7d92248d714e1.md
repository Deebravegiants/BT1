### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the shop-tenant identity (`shop-domain` header) that the handler uses to attribute the webhook to a specific merchant is never included in the signed material. This breaks the intended binding `hmac_verified(raw_body) == shop_domain_trusted`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, so the HMAC computed by Shopify (and verified via `HmacValidator.validate`) authenticates *only the JSON body bytes*. The `shop` accessor, however, is read straight from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the app's handler as the trusted tenant identifier, with no cross-check that this header is consistent with anything cryptographically bound to the signature: [3](#0-2) 

`WebhookMetadata#shop` is a plain `String` field populated directly from that header, and the gem's own documentation instructs apps to key business logic off `data.shop`: [4](#0-3) [5](#0-4) 

Because the same app's `api_secret_key`/`client_secret` is shared across every shop that installs the app, and only `raw_body` is HMAC-bound, a merchant who has legitimately installed the app (Shop A) can:
1. Capture a real, validly-signed webhook payload sent to their own endpoint (valid `hmac` for that `raw_body`, using the shared app secret).
2. Replay the identical `raw_body` (and thus identical, still-valid `hmac`) to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header for a different, victim shop (Shop B) that also uses the app.
3. `HmacValidator.validate` still succeeds, because it only checks `raw_body` against the shared secret — it never checks that the claimed `shop` was actually the one Shopify signed for.
4. The app's handler receives `WebhookMetadata` claiming `shop: "shop-b.myshopify.com"` with attacker-chosen body content, and applies tenant-scoped actions (e.g., looking up Shop B's stored access token/session, writing orders/customer data attributed to Shop B, mandatory GDPR topics like `customers/redact`) under a forged tenant identity.

This satisfies the required binding-break pattern: "a shop authenticated versus the shop stored/acted upon" — here, the HMAC authenticates the body while the shop identity used for all downstream tenant-scoped effects is taken from unauthenticated header bytes.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical bucket): any single-tenant attacker who has installed the app (a normal, low-privilege condition — no `api_secret_key`, no access token theft, no TLS interception required) can forge webhook events that a host application will process as though they originated from an arbitrary other shop that shares the same app. This can be used to poison another merchant's data pipeline, trigger tenant-scoped side effects (order creation handling, GDPR redact flows, inventory/product update handling) with attacker-controlled body content, under a victim's `shop` identity — a violation of tenant isolation guaranteed by the gem's webhook authentication contract.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on their own store (a normal onboarding flow for any app listed publicly, or any multi-tenant SaaS built on this gem) and can send arbitrary HTTP requests to the app's public webhook endpoint. No secrets beyond a body/HMAC pair the attacker can legitimately obtain for their own tenant are required.

### Recommendation
Bind the shop domain (and other webhook-identifying headers Shopify sends, e.g. `webhook-id`, `topic`, `api-version`) into the HMAC-verified signable material, or independently verify that the claimed `shop-domain` header corresponds to a shop with an actual known installation/session before trusting it. At minimum, `Request#to_signable_string` should not silently drop header-derived identity fields that `Registry.process` subsequently treats as authenticated; document/enforce that host applications must independently corroborate `data.shop` against their own installed-shop registry rather than trusting it as authenticated purely by virtue of `HmacValidator.validate` succeeding.

### Proof of Concept
```ruby
# Attacker installs the target app on their own store "attacker-shop.myshopify.com"
# and receives a real webhook, e.g. orders/create, with body B and valid hmac H
# computed by Shopify using the app's shared api_secret_key.

forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => H,                                # unchanged, still valid for body B
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",       # forged: not covered by H
  "x-shopify-webhook-id"  => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)

# Passes: HmacValidator.validate only checks B against H, and never touches "shop-domain"
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...))
# Host app now processes attacker-supplied body B as if it were a legitimate
# event from victim-shop.myshopify.com.
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```
