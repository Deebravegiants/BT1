### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant dispatch but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator` binds solely to `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` values used to dispatch and attribute the webhook to a tenant come from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` for the signable payload: [1](#0-0) 

`Request#to_signable_string` returns `@raw_body` exclusively, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers with no cryptographic linkage to that body: [2](#0-1) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`bytes_verified_by_hmac (raw_body)` != `bytes_used_for_tenant_dispatch (shop-domain header, topic header, webhook_id header)`

Because the app's `client_secret` is shared across every shop that installs the app, any merchant/attacker who installs the app receives genuine, validly-HMAC-signed webhook deliveries for their own shop. Since the signature covers only the body, that same attacker can capture one legitimate `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header altered to name a different shop that also uses the app. `Utils::HmacValidator.validate` will still return `true` because it only recomputes the HMAC over the unchanged body, and `Registry.process` will hand the forged `shop`/`topic` values straight to the handler via `WebhookMetadata`: [3](#0-2) 

The handler, and by extension the host application, has no way to detect that the `shop` attribute was never authenticated - it is bound only by the attacker's chosen header value, not by the signature.

### Impact Explanation
Any host application that keys webhook side effects (order sync, data updates, fulfillment triggers, etc.) off `WebhookMetadata#shop`/`topic` can be made to attribute another merchant's forged or replayed event to itself, or a merchant's own captured payload to a different tenant's context - a cross-tenant integrity/confusion issue. This matches the Critical "cross-tenant access" impact category since it lets one authenticated party (an app-installing merchant) inject or mis-tag data for another tenant sharing the same app installation, bypassing the very check (`process`) that is supposed to guarantee the request "did indeed come from Shopify" for that specific shop and topic, per the gem's own documentation: [4](#0-3) 

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate installer of the target app on at least one shop (a normal, unprivileged onboarding action, not a privileged operation) and the ability to replay an HTTP request with modified headers to the app's public webhook endpoint - no access to `client_secret`, tokens, or TLS interception is needed. This is straightforward for any developer/tester of a public or unlisted Shopify app.

### Recommendation
Bind the tenant-identifying fields into the signed material, or independently verify them against data derived from the signed body/registered subscription instead of trusting raw headers:
- Do not use `request.shop`/`request.topic`/`request.webhook_id` from headers as the sole source of tenant attribution for side effects; where possible, cross-check the shop against the `access_token`/session used to have registered that specific webhook subscription, or use Shopify's webhook `id` uniqueness plus stored subscription-to-shop mapping to detect and reject header/body mismatches.
- At minimum, document prominently that `Registry.process`'s `Utils::HmacValidator.validate` only proves the body was signed by an app owning `client_secret`, and does **not** prove the `shop`, `topic`, or `webhook_id` headers are authentic or bound to that body, so consuming applications must not treat these header-derived fields as trusted tenant identifiers without additional verification.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` (or any shop the attacker controls) and let it also be installed on a `victim-shop.myshopify.com`.
2. Capture a legitimate incoming webhook delivery for `attacker-shop.myshopify.com`, e.g.:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <valid-hmac-for-raw_body>
   shopify-shop-domain: attacker-shop.myshopify.com
   shopify-webhook-id: <id>
   Body: {...attacker's order payload...}
   ```
3. Replay the identical body and `shopify-hmac-sha256` value, but change the header:
   ```
   shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` and `to_signable_string` (== `raw_body`) are unchanged, so:
   ```ruby
   Utils::HmacValidator.validate(request) # => true, because only raw_body is checked
   ```
5. `Registry.process(request)` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the payload was never generated for `victim-shop`. [1](#0-0) [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
