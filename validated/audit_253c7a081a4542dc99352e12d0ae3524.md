### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` headers are trusted despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, yet the gem's documented API exposes `shop`, `topic`, `webhook_id`, and `api_version` — all derived from unauthenticated HTTP headers — as trusted, verified fields once `Registry.process` passes HMAC validation. This breaks the intended binding: `HMAC-verified == trustworthy(shop)`. In reality, `HMAC-verified` only proves the *body* bytes are unmodified; the shop/topic/webhook-id/api-version headers can be freely set by anyone submitting a request with a previously-observed valid `(body, hmac)` pair.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers, independent of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) and then immediately trusts `request.shop`/`request.topic` to route and label the event, without any check that the claimed shop domain matches a shop that legitimately owns this delivery: [3](#0-2) 

The gem's own documentation instructs app authors to treat `data.shop` as an authenticated identifier once `Registry.process` succeeds, e.g. using it directly as a tenant/store key: [4](#0-3) 

Because Shopify webhook HMACs are computed with the app's `client_secret`, which is shared across **every merchant that installs the app** (not per-shop), any user who installs the app on their own store legitimately receives valid `(raw_body, hmac)` pairs for their own webhooks. That same user can then replay that exact raw body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with an arbitrary victim shop domain. `Utils::HmacValidator.validate` will report the HMAC as valid (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop: [5](#0-4) 

This is the exact bug-class analog requested: a field (`shop`) acted on by the application but not covered by the HMAC that is supposed to authenticate the request.

### Impact Explanation
An unprivileged, low-cost attacker (any user who can install the app, e.g. via a free development store) can forge webhook deliveries that the host application attributes to an arbitrary victim shop of their choosing. Because the library's documented pattern is to key store/tenant data directly off `data.shop` (as shown in `docs/usage/webhooks.md`), a downstream app built per this library's guidance would process attacker-controlled data as belonging to another merchant's tenant — a cross-tenant data-integrity/impersonation issue reachable purely by an internet-accessible, credential-less request replay.

### Likelihood Explanation
Likelihood is high for any app that follows the documented usage pattern verbatim: the attacker only needs (1) the ability to install the app once on any shop (very low barrier, often free/self-serve), (2) capture one legitimate webhook delivery, and (3) resend it with a modified `shop-domain`/`topic` header to the app's public webhook URL. No secrets, tokens, or privileged access are required beyond standard app installation.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` values in the signable string (or otherwise cryptographically bind them to the HMAC), or require the consuming application to independently verify the received `shop` header against a known/installed shop for that HMAC-secret before trusting it. At minimum, the library's HMAC validation for webhooks should not silently ignore fields the documentation instructs callers to treat as authenticated (`shop`, `topic`).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers including `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, and a valid `X-Shopify-Hmac-Sha256` computed over the raw JSON body using the app's shared `client_secret`.
3. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new POST request to the same public webhook endpoint, reusing the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only hashes `@raw_body`.
6. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker body>, ...)`, causing the application to process attacker-supplied data as belonging to `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```
