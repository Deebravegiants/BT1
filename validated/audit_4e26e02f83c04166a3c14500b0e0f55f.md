Audit Report

## Title
CORS wildcard allowlist bypass via unanchored suffix match in Gateway HTTP server - (File: `core/services/gateway/network/httpserver.go`)

## Summary
`isAllowedOrigin` implements wildcard-domain matching for `CORSAllowedOrigins` by stripping the `*.` prefix and then calling `strings.HasSuffix(originHost, allowedHost)` with no domain-label-boundary check. [1](#0-0)  This allows an attacker-controlled origin such as `evil-ethereum.org` to satisfy a `*.ethereum.org` allowlist entry, since raw suffix matching does not require a `.` separator between the wildcard portion and the fixed suffix.

## Finding Description
`isAllowedOrigin` parses the scheme/host/port of the `Origin` header and compares against each configured `CORSAllowedOrigins` entry. [2](#0-1)  For entries prefixed with `*.`, the code strips the prefix and performs an unanchored `strings.HasSuffix` check: [1](#0-0)  This means `originHost = "evil-ethereum.org"` against `allowedHost = "ethereum.org"` (after stripping `*.`) returns `true` from `HasSuffix`, even though `evil-ethereum.org` is not a subdomain of `ethereum.org`.

This function directly gates `handleRequest`, the unauthenticated entry point for all Gateway HTTP traffic. When `isAllowedOrigin` returns true, the server reflects the attacker's exact `Origin` value into `Access-Control-Allow-Origin`: [3](#0-2)  This permits a browser page hosted on the attacker's look-alike domain to make cross-origin requests to the Gateway and read the JSON-RPC responses, defeating the intended origin restriction. The existing test suite exercises only correctly-anchored subdomains (e.g., `remix.ethereum.org` against `*.ethereum.org`) and does not cover the boundary-bypass case, so this defect is untested and unmitigated by any other check in the code path. [4](#0-3) 

## Impact Explanation
This is a concrete CORS allowlist bypass reachable by any unprivileged actor who can host a webpage on a domain string sharing the wildcard's suffix — no subdomain relationship, credentials, or special privileges are required, only domain registration. It undermines the operator's origin-restriction configuration for the Gateway's public-facing HTTP API, enabling cross-origin browser-based reads of Gateway responses meant to be limited to trusted subdomains. This maps to the in-scope "allowlist bypass" impact category for the Gateway.

## Likelihood Explanation
Likelihood is moderate-to-high in any deployment using wildcard `CORSAllowedOrigins` entries (a documented, supported pattern demonstrated in the test suite itself). Exploitation requires no authentication, no race conditions, and no interaction beyond a victim visiting the attacker's page while the attacker's script issues a cross-origin request.

## Recommendation
Anchor the suffix match to a domain-label boundary: after stripping `*.`, require `originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost)` so that `evil-ethereum.org` no longer matches `*.ethereum.org`.

## Proof of Concept
1. Configure Gateway with `CORSAllowedOrigins = ["https://*.ethereum.org"]` and `CORSEnabled = true`.
2. Send an HTTP request to the Gateway's configured path with header `Origin: https://evil-ethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` (via `strings.HasSuffix("evil-ethereum.org", "ethereum.org")`), and the response includes `Access-Control-Allow-Origin: https://evil-ethereum.org`.
4. Add a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` [5](#0-4)  asserting that origin `https://evil-ethereum.org` against allowlist `https://*.ethereum.org` is rejected (currently it is incorrectly accepted).
