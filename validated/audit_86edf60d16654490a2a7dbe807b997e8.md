### Title
Emporium `runAction` only reconciles tokens declared in `circomData.erc20TokenAddresses`, letting an EOA drain any other token held by the Emporium contract via an unaccounted-for op call - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` lets a prover attach an arbitrary sequence of low-level calls (`stack.ops`) that execute with the Emporium contract itself as `msg.sender` (the "Stateless Interaction" branch). After the ops run, the contract only computes `balancesBefore`/`balancesAfter` and enforces a non-negative balance-change invariant for the token list the *same prover declares* in `circomData.erc20TokenAddresses`. Any token moved out of the Emporium contract that is not included in that self-chosen list is never measured, so an attacker can omit the target token from the array and use an op to `transfer`/`call` it away for free, exactly analogous to the Wise-Lending bug where the health check iterated only a caller-chosen subset of collateral and skipped the condition check for anything outside it.

### Finding Description
`Hinkal.transact()` delegates the per-token accounting entirely to the arrays the prover supplies in `CircomData` (`circomData.erc20TokenAddresses`), and `HinkalHelper.dimensionsCheck` only verifies internal consistency of the arrays' lengths against each other and `Dimensions` — it never restricts which/how many tokens the prover may list [1](#0-0) .

Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are snapshotted only for `circomData.erc20TokenAddresses`, and the sole safety check (`balanceChange < 0 → revert BalanceChangeShouldBePositive()`) is likewise scoped to that same array: [2](#0-1) 

The ops themselves are unrestricted low-level calls executed with the Emporium contract as `msg.sender` when `invokeWallet` is false: [3](#0-2) 

Because `calldataHash`/`signedMessageHash` bind every `CircomData` field including `erc20TokenAddresses` and `externalActionMetadata` (the encoded `EmporiumStack`) [4](#0-3) , the proof/hash checks only guarantee the *declared* array and ops are internally consistent — they do nothing to prevent the declared array from omitting a token that the ops nonetheless act on. The circuit itself has no knowledge of `externalActionMetadata` or the Emporium op list at all (it is not a circuit input), so it cannot constrain which tokens are moved by the ops either.

This breaks the balance equality the protocol relies on: "every token balance change at the external-action contract must equal the sum of shielded-UTXO/on-chain-commitment changes for that token." Any token whose balance moves due to an op, but that is absent from `erc20TokenAddresses`, is invisible to both the Emporium-level check and the outer `Hinkal.transact()` balance-diff loop (which also only iterates `circomData.erc20TokenAddresses`) [5](#0-4) .

### Impact Explanation
Any ERC20/ETH balance the Emporium contract happens to hold (protocol/relay fee remnants left mid-flight by `payRelayFees`, dust from prior swaps, tokens accidentally sent to the contract) can be swept by an unprivileged EOA: they submit a `transact()` with a valid proof for a declared token set that excludes the target token, and attach an Emporium op whose `callData` calls `transfer`/`transferFrom` on the target token contract, moving it to an address they control. No require statement anywhere sees this movement because it's outside the declared array on both `EmporiumUpgradeable.runAction` and `Hinkal.transact()`. This is theft of protocol/relay fee funds (assets Emporium holds transiently), matching the "High – theft ... of protocol/relay fees" impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only a normal (unprivileged) call to `transact()` with the Emporium external action and a self-crafted `EmporiumStack.ops` entry; no admin, relay, or victim key is needed. It does require the Emporium contract to actually be holding a spare balance of the target token at call time (e.g., transient fee balances from `payRelayFees`/`sendToRelayFromWallet`, or funds left over from a preceding transaction in the same block), which is realistic given the multi-step relay-fee flow in `EmporiumUpgradeable`.

### Recommendation
Enumerate and check the balance delta of *every* token an Emporium op could plausibly touch, not just the prover-declared `erc20TokenAddresses` — e.g., require ops' target contracts/selectors be restricted to a pre-approved allowlist, or snapshot/verify balances for all tokens referenced anywhere in `stack.ops` (decoded token addresses) in addition to `circomData.erc20TokenAddresses`, and revert if any balance decreases outside the declared/accounted set.

### Proof of Concept
1. Assume the Emporium singleton currently holds a stray balance of token `X` (e.g., leftover from `payRelayFees` rounding, or accidentally transferred in).
2. Attacker calls `Hinkal.transact()` with `externalActionData.externalActionId` set to the Emporium action, and `circomData.erc20TokenAddresses` containing only token `Y` (not `X`), producing a valid proof/hash for that declared set only.
3. `externalActionMetadata` encodes an `EmporiumStack` with one `EmporiumOperation`: `endpoint = X`, `invokeWallet = false`, `callData = abi.encodeCall(IERC20.transfer, (attacker, allOfX))`.
4. `EmporiumUpgradeable.runAction` executes the op as `msg.sender = Emporium`, transferring all of token `X` to the attacker (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:112`).
5. `balancesBefore`/`balancesAfter` and the `balanceChange < 0` guard only inspect token `Y`, so the loss of `X` is never checked, and `Hinkal.transact()`'s outer balance-diff loop also only iterates `circomData.erc20TokenAddresses` (`Y`), so the transaction completes successfully.
