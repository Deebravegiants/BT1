## Title
Webhook `shop` field is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read directly from the unauthenticated `X-Shopify-Shop-Domain` header, but the HMAC verification performed by `HmacValidator` only covers the raw request body. This breaks the identity binding `hmac_verified_bytes == shop_bound_bytes`: an attacker can present a genuinely Shopify-signed webhook body/HMAC pair (obtained from their own shop, which they legitimately control as an app installer) together with a forged `X-Shopify-Shop-Domain` header naming an arbitrary victim shop, and the library will accept it as authentic and hand the forged shop identity to the host app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shop-domain` header, entirely outside the signed content: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC using only `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` uses this validation result as the sole authenticity gate, then forwards the **unverified** `request.shop` straight to the app's handler as the tenant identifier: [4](#0-3) 

Crucially, the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — it is not shop-specific. This means a valid `(body, hmac)` pair from *any* shop the attacker controls (e.g. their own free/dev store where they installed the same app) will pass `validate_signature` regardless of which shop domain is asserted in the header, because the header is never part of the signed bytes.

The library's own documented usage pattern instructs host apps to trust `data.shop` for tenant routing (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is not a case of the host app "ignoring documented API" — it is following it exactly as documented while the gem itself fails to bind `shop` to the cryptographic proof of authenticity.

### Impact Explanation
This is a cross-tenant identity-binding break: authentication of "this request came from Shopify using our secret" is conflated with authentication of "this request is about shop X." An attacker with a legitimate installation on their own shop can:
1. Trigger any webhook topic on their own shop (e.g. `app/uninstalled`, `shop/update`, `customers/data_request`, `orders/create`) with body content they control (product titles, customer fields, shop settings, etc., all editable on their own store).
2. Capture the genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends to their webhook endpoint.
3. Replay that exact body/HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain.
4. `HmacValidator.validate` succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim's domain.

Any host application that uses `data.shop` to select which tenant's records to mutate, mark app-uninstalled, wipe data (GDPR topics), or otherwise take shop-scoped action will act on behalf of/against the victim shop using attacker-supplied trigger data — a cross-tenant access/action vulnerability.

### Likelihood Explanation
Exploitation requires only that the attacker be an ordinary, unprivileged app installer with their own Shopify store (no special credentials, tokens, or `client_secret` needed) and knowledge of the app's public webhook endpoint, both trivially obtainable for any public app. This is squarely reachable by "an unprivileged internet user."

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header in the bytes that are HMAC-verified, or otherwise cryptographically bind the shop domain to the signed payload before `Registry.process` passes it to handlers. At minimum, document and/or enforce that `data.shop` in `WebhookMetadata` must be cross-checked by the host application against a shop it has an existing, independently-established session/relationship with before taking any shop-scoped action, since the shop domain itself carries no cryptographic guarantee.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they own).
2. Attacker performs an action that triggers a subscribed webhook topic (e.g. edits a product to trigger `products/update`), causing Shopify to POST a genuinely-signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Hmac-Sha256: <valid HMAC over raw body using app's client_secret>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: products/update`.
   - Body: JSON attacker fully controls the field values of (their own product data).
3. Attacker captures this raw body and its valid HMAC.
4. Attacker sends a new POST request directly to the app's public webhook endpoint with the same raw body and same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `HmacValidator.validate` returns `true` because it only hashes `@raw_body`; `Registry.process` calls the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-controlled body — despite the request having nothing genuinely to do with the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
