### Title
Webhook shop-domain (and topic/webhook-id/api-version) headers are not covered by the HMAC, allowing cross-tenant shop-attribution forgery on replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`, `webhook-id`, `api-version`) HTTP headers verbatim to build the `WebhookMetadata` object handed to the app's handler. Because those headers are outside the signed material, a party who legitimately receives one valid `(body, hmac)` pair for their own shop can replay it to the same endpoint with a forged `shop-domain` header, and the gem will report it as a validly-authenticated webhook for the victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) calls `validate_signature`, which compares the received HMAC against `compute_signature(verifiable_query.to_signable_string, secret)`. [1](#0-0) 

For webhook requests, `to_signable_string` is defined to return only the raw HTTP body: [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers and are never included in the signed string: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then immediately trusts these unauthenticated header-derived fields to construct the metadata object dispatched to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `bytes verified == bytes parsed` should hold for the shop that a webhook is attributed to, but here `bytes verified (raw body only)` != `bytes parsed (raw body + shop/topic/webhook-id/api-version headers)`. A verified HMAC over a body says nothing about which shop, topic, or webhook-id the request actually pertains to.

### Impact Explanation
An unprivileged internet user who can install the vulnerable app on any shop they control (a normal, unprivileged action any developer can perform via a free Shopify dev store) will receive genuine webhook deliveries with valid `(body, hmac)` pairs computed by Shopify using the app's `client_secret` — a secret the attacker never needs to know or steal. Because the app's public webhook endpoint is reachable over the internet and the gem's validation only checks the body/HMAC pair, the attacker can replay that exact valid body+HMAC to the same endpoint while altering the `shop-domain` (and/or `topic`/`webhook-id`) header to name a different, victim shop. `Webhooks::Registry.process` will accept it as authentic and hand the handler a `WebhookMetadata` claiming the data originates from the victim shop. If the host application uses `data.shop` to select per-tenant state (e.g., to look up the tenant's stored access token, update tenant records, or key a cache), this yields cross-tenant data confusion/injection — attacker-controlled webhook content being processed and attributed to a shop the attacker does not control. This maps to the Critical "cross-tenant access" impact category, since the boundary broken is the authentication of *which tenant* a signed message belongs to.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker must (a) be able to install the target app on a shop they control (a routine, unprivileged action for any developer using a free dev store), (b) capture one legitimate `(body, hmac)` pair delivered to the app's own webhook endpoint, and (c) know or guess the victim shop's `myshopify.com` domain (typically public/discoverable). No secrets, tokens, or privileged access to the victim's shop are required. The exploit is a straightforward HTTP replay with one header changed — well within reach of an unprivileged internet user.

### Recommendation
Bind the identity fields into the signed material rather than trusting unauthenticated headers:
- Extend `Webhooks::Request#to_signable_string` (or the HMAC validation path) to incorporate `shop`, `topic`, and `webhook_id` alongside the raw body, or otherwise cryptographically bind the header values to the signature (this may require coordinating with Shopify's webhook delivery format since Shopify does not currently include headers in the signed payload).
- At minimum, since the underlying webhook signature scheme cannot be changed unilaterally by this gem, document prominently and/or provide a helper that requires handlers to independently verify that `shop` matches an expected/registered tenant (e.g., cross-check against the app's own list of installed shops) before trusting `WebhookMetadata#shop`/`#topic` for tenant-sensitive operations, and consider rejecting requests whose header-derived `shop`/`topic` do not correspond to an actually registered webhook subscription for that shop.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (free dev store) and triggers a webhook event, capturing the raw POST body `B` and the resulting `x-shopify-hmac-sha256: H` header sent by Shopify (computed as `HMAC-SHA256(client_secret, B)`).
2. Attacker sends a new POST to the app's public webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally forges `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (`lib/shopify_api/webhooks/request.rb:45-63`) since only presence of the header names is checked, not their correctness.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B` (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker-controlled webhook content under the victim shop's tenant identity.
