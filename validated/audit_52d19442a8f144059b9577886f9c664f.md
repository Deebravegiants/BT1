### Title
Webhook Tenant Identity (`shop`) Not Covered by HMAC Verification Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, then dispatches the webhook to the host application's handler using a `shop` value taken from an HTTP header that is never included in the HMAC computation. This breaks the identity binding `shop_used_by_handler == shop_that_the_HMAC_was_computed_for`, allowing an attacker who possesses one validly-signed webhook body (e.g., a webhook generated for their own store) to relabel it for any other tenant simply by changing the `x-shopify-shop-domain` header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read directly from the unauthenticated header dictionary with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature exclusively against `verifiable_query.to_signable_string`, i.e. the raw body — the `shop` header plays no role in signature computation or verification: [3](#0-2) 

`Registry.process` validates the HMAC (over body only) and then immediately trusts `request.shop` as the tenant identity passed to the host application's webhook handler, with no secondary check tying the shop value to the signed payload: [4](#0-3) 

Because `hmac(raw_body, secret)` is independent of the `shop` header value, any request with a given `raw_body` and its correctly-computed HMAC will pass `Utils::HmacValidator.validate` regardless of what `x-shopify-shop-domain` / `shopify-shop-domain` header accompanies it. An attacker who can obtain one genuinely-signed webhook body (for example, by installing the merchant app on their own store and triggering a webhook event, which yields a valid `hmac` for that specific body under the app's shared `client_secret`) can resend that exact body with an arbitrary `shop` header value to the app's public webhook endpoint. `HmacValidator.validate` will report success because it never inspects the header, and `Registry.process` will hand the (correct-signature, wrong-tenant) data to the handler labeled as belonging to a different, victim shop.

### Impact Explanation
This is a High-severity, cross-tenant identity confusion. Host applications built on this gem are expected to trust `WebhookMetadata#shop` (constructed from `request.shop`) as the authenticated tenant identifier once `Registry.process` returns without raising `InvalidWebhookError`. Since the shop is not part of the signed content, an attacker who owns any valid signed payload can inject data attributed to a shop they do not control, potentially triggering the host app's business logic (e.g. data writes, redaction workflows, or entitlement changes) against another merchant's tenant record — a cross-tenant access vector.

### Likelihood Explanation
The prerequisite (obtaining one valid signed webhook body) is trivial: any user can install the merchant's app on their own development or trial store, trigger a subscribed webhook topic, and capture the resulting `body` + `x-shopify-hmac-sha256` pair. Replaying it with a modified `shop` header requires only unauthenticated HTTP access to the app's public webhook endpoint — the same access an attacker needs to deliver the spoofed request in the first place.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed content that `Utils::HmacValidator` verifies, or require host applications to cross-check the delivered `shop` against a shop-specific registered webhook secret/endpoint before trusting it. At minimum, `Registry.process` should not treat a body-only HMAC pass as sufficient authentication for the `shop` field used to route/attribute webhook data.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a subscribed webhook (e.g. `orders/create`), capturing the raw JSON `body` and the resulting `x-shopify-hmac-sha256` header — both valid under the app's real `client_secret`.
2. Attacker sends a POST to the app's public webhook endpoint reusing the exact `body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers/body successfully.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches — validation passes.
5. `handler.handle` is invoked with `WebhookMetadata` where `shop == "victim.myshopify.com"`, even though the payload and signature originated entirely from the attacker's own store, demonstrating the identity-binding break: verified bytes (`raw_body`) ≠ bytes that determine tenant identity (`shop` header).
