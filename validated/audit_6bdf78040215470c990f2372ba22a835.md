### Title
`process_deposit` never checks `AmmStatus::deposit_permission`, so deposits succeed while the pool is `Disabled` - (File: `program/src/processor.rs`)

### Summary
The Goldfinch report describes a lending-pool status check that fails to account for one specific pool state ("paused"), causing a paused pool to be treated as `Active`. Raydium's AMM has an analogous state-machine gate, `AmmStatus`, with dedicated permission predicates for each operation (`deposit_permission`, `withdraw_permission`, `swap_permission`). While `process_withdraw` and all four swap handlers correctly call `AmmStatus::from_u64(amm.status).withdraw_permission()`/`.swap_permission()` before proceeding, `process_deposit` never calls `deposit_permission()` at all, so it silently treats every reachable status (including `Disabled`) as if deposits were allowed.

### Finding Description
`AmmStatus` defines an explicit `deposit_permission()` method that should gate the deposit instruction the same way `withdraw_permission()`/`swap_permission()` gate withdraw and swap: [1](#0-0) 

Every other state-changing entry point enforces its corresponding permission check immediately after loading `AmmInfo`:
- `process_withdraw` checks `withdraw_permission()`: [2](#0-1) 
- `process_swap_base_in` / `process_swap_base_out` / `process_swap_base_in_v2` / `process_swap_base_out_v2` all check `swap_permission()`: [3](#0-2) [4](#0-3) 

However, `process_deposit` loads `AmmInfo` and immediately moves on to validating deposit amounts and signer checks — there is no call to `AmmStatus::from_u64(amm.status).deposit_permission()` anywhere in the function or in `processor.rs`: [5](#0-4) 

A repo-wide search confirms `deposit_permission` is defined in `state.rs` but is never referenced from `processor.rs`, whereas `withdraw_permission` is referenced and enforced. This means `AmmStatus::Uninitialized` and `AmmStatus::Disabled` (both of which `deposit_permission()` returns `false` for) are not actually blocked at the deposit instruction — the pool owner's intent to freeze the pool via `SetParams(AmmParams::Status, Disabled)` is bypassed for deposits, exactly as the Goldfinch pool's "paused" intent was bypassed by `_getLendingPoolStatus`.

The `SetParams` admin instruction is the only way to set `amm.status = AmmStatus::Disabled`, and this is meant to be an emergency stop for the whole pool (e.g., in response to a discovered exploit or bad pricing data), consistent with `withdraw_permission()` and `swap_permission()` both returning `false` for `Disabled`: [6](#0-5) 

### Impact Explanation
Any unprivileged user can still submit `Deposit` instructions against a pool the admin has explicitly disabled via `SetParams`. This undermines the intended emergency-pause mechanism: LPs and depositors interacting with a pool that the pool admin flagged `Disabled` (e.g., due to a detected exploit, oracle/market issue, or other critical condition) can still deposit assets and mint LP tokens, potentially depositing into a pool whose accounting or vault state is already compromised, or continuing to add liquidity that the admin intended to freeze. This is a violation of the pool's access-control invariant and can result in fund loss/mismanagement for depositors who rely on the `Disabled` status meaning "no further pool interaction."

### Likelihood Explanation
High reachability: `Deposit` is a standard, permissionless instruction reachable in a single transaction with attacker/user-chosen accounts and amounts; no privileged signer is required beyond the normal LP depositor signature. The only precondition is that the pool's admin has set `status = Disabled` (or the pool is otherwise in a status where `deposit_permission()` should be `false`), which is a supported and expected admin action via `process_set_params`.

### Recommendation
Add the missing status gate at the top of `process_deposit`, mirroring the pattern used in `process_withdraw` and the swap handlers:
```rust
if !AmmStatus::from_u64(amm.status).deposit_permission() {
    return Err(AmmError::InvalidStatus.into());
}
```
This should be inserted immediately after `AmmInfo::load_mut_checked` in `process_deposit`, consistent with `program/src/processor.rs:1648-1654` and `program/src/processor.rs:1927-1938`.

### Proof of Concept
1. Pool admin calls `SetParams` with `AmmParams::Status` and `value = AmmStatus::Disabled` (2u64), which succeeds and sets `amm.status = 2`: [7](#0-6) 
2. An arbitrary user then submits a `Deposit` instruction against the same `amm_info` account with valid vault/mint/owner accounts.
3. `process_deposit` loads `AmmInfo`, checks `pc_vault_mint != coin_vault_mint`, validates `max_coin_amount`/`max_pc_amount != 0`, and checks the signer — but never checks `AmmStatus::from_u64(amm.status).deposit_permission()`: [5](#0-4) 
4. Since `deposit_permission()` is never invoked, the deposit proceeds and mints LP tokens even though the pool is `Disabled`, in direct contradiction to the admin's intended pause and to the behavior enforced for withdraw/swap.
