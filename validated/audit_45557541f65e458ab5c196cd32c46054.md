Investigating the reported "poor slippage management" bug class against the reachable dispatch paths, the closest and most concrete analog is in `EvmHost.dispatch()`'s native-fee-payment swap path, not the intent-gateway/solver code (which already enforces `solverAmount >= totalRequired` via `InvalidInput()` at [1](#0-0) , and the Simplex paymaster's DEX swap already carries an oracle-derived `amountOutMin` bound and is treasury-gated [2](#0-1) , making it a privileged-only path excluded by the rules).

### Title
Native-fee dispatch swap sends excess ETH refund to `EvmHost` instead of the caller, permanently trapping overpaid fees - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` let any unprivileged message dispatcher pay the Hyperbridge dispatch fee in native tokens. Both functions perform an on-chain "exact-output" Uniswap V2 swap (`swapETHForExactTokens`) funded by `msg.value`, with no mechanism to return unused ETH to the actual caller.

### Finding Description
Both dispatch entry points execute: [3](#0-2) [4](#0-3) 

`IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` is an exact-output swap: the router computes `amountIn` needed to produce exactly `post.fee` fee tokens and, per the standard UniswapV2Router02 implementation, refunds `msg.value - amountIn` in ETH to `msg.sender` of that call. Because `EvmHost` itself is the caller of the router (not the original dispatcher, `_msgSender()`), any unused ETH is refunded back into `EvmHost`'s own balance rather than to the application/user that supplied `msg.value`. There is no code path visible in `dispatch()` that forwards this refund back to `_msgSender()`.

This is compounded by the SDK's own fee-estimation logic, which deliberately overpays to build in safety margin — e.g. `TokenGateway.quoteNative()` adds a 1% buffer to both the relayer fee and protocol fee before dispatch [5](#0-4) . Since every buffered/overestimated native payment routes through the same `swapETHForExactTokens` call, the deliberate buffer — meant to protect against price movement/slippage — is itself the amount silently lost on every dispatch, rather than being refunded to the payer.

### Impact Explanation
Any unprivileged application or user dispatching a POST/GET request and paying the relayer/protocol fee in native currency loses any amount sent above the exact swap requirement. This is systemic rather than incidental: the SDK's own fee-quoting flow always pads the native payment by ~1%, meaning routine cross-chain dispatches (token bridging via `TokenGateway`, `HyperFungibleToken.send`, GET requests, etc.) continuously bleed value into `EvmHost`'s balance with no attribution or recovery path back to the payer — a concrete, permanent loss of funds for the dispatching party, framed exactly as "poor slippage/price management in trade execution" from the reference report (paying more than needed and never getting the difference back).

### Likelihood Explanation
High. This does not require any adversarial timing or market manipulation — it triggers on ordinary usage any time a caller pays in native token and doesn't send the exact minimal `amountIn` (which is effectively guaranteed, since callers must estimate `amountIn` off-chain against a router price that can move between estimation and execution, and the SDK intentionally overpays by design).

### Recommendation
After the swap in both `dispatch(DispatchPost)` and `dispatch(DispatchGet)`, forward any leftover native balance received from the swap back to `_msgSender()` (e.g., track balance before/after the swap call, or use `swapETHForExactTokens` refund awareness and manually forward it), mirroring the refund pattern already used elsewhere in the codebase, e.g., in `IntentGatewayV2`/`ExtrinsicIntents.sol` where solver overpayment is explicitly refunded: [6](#0-5) .

### Proof of Concept
1. A dispatcher (e.g., via `TokenGateway.quoteNative`) computes `totalNativeCost` with a 1% buffer over the raw quoted protocol fee, per [7](#0-6) .
2. The dispatcher calls `IDispatcher.dispatch{value: totalNativeCost}(post)` where `post.fee` is the exact fee-token amount required.
3. Inside `EvmHost.dispatch`, `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes; the router computes the true `amountIn` (typically less than the 1%-buffered `msg.value`) and refunds the difference to `msg.sender`, which is `EvmHost`, not the dispatcher [8](#0-7) .
4. The dispatcher's transaction succeeds, the request is dispatched, but the ~1% (or more, if the on-chain price differs from the SDK's off-chain quote) buffer is stranded inside `EvmHost` and is unrecoverable by the dispatcher.

**Note on completeness:** I could not fully confirm within the available search whether `EvmHost` exposes any admin/governance sweep function that could later distribute this stranded ETH (which would reduce this to a value-misallocation rather than fully-unrecoverable loss for the specific payer), nor whether a later code path re-forwards the router's refund. If a Devin session with full repo access is available, this should be verified directly against the complete `EvmHost.sol` and its inheritance chain before treating the funds as unrecoverable versus merely misdirected.
