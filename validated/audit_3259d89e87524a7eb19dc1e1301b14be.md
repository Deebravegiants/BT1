### Title
Unguarded reserve subtraction in `canGraduate`/`previewLtUntilGraduation` USD leg can underflow and permanently brick curve trading and graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` and `Bonding.previewLtUntilGraduation` both compute the real (non-virtual) LT raised on a curve as `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no floor check. This is the same bug class as GHSL-2024-243's `atom_length - 8`: an unchecked subtraction whose minuend can be driven below the subtrahend by attacker-reachable state, producing either a revert (Solidity 0.8 checked-math) that DoS's every path that calls it, or (if ever ported to an `unchecked` block) a huge wrapped value analogous to the C `cclen` overflow. The developers already recognized and patched exactly this hazard on the sibling "supply leg" of `previewLtUntilGraduation` (`realBalance >= reserveToken` guard, `packages/contracts/test/Zap.t.sol:939-989`, comment: "A TOKEN donation ... previously underflowed `Bonding.previewLtUntilGraduation`'s supply leg... Guard added") but left the USD leg's `assetReserve - virtualLtReserve` subtraction, used in both `canGraduate` (called on every buy and every sell) and `previewLtUntilGraduation`, unguarded.

### Finding Description
`canGraduate` recovers the launch-time virtual LT reserve and subtracts it from the pair's live stored `reserveAsset`: [1](#0-0) 

The same pattern repeats in `previewLtUntilGraduation`: [2](#0-1) 

Both sites assume `assetReserve >= _launchTimeVirtualLtReserve(token_, pair)` always holds, i.e. that the pair's stored LT reserve never drops below the reserve it was seeded with at launch. That invariant is only guaranteed if the AMM math (`Router._computeSell` / `Pair.swap`'s K-invariant check with its documented `+1` K slack) never lets `reserveAsset` decrease by more than what was ever added on the buy side. The K slack that exists specifically to tolerate rounding on `Pair.swap` (mentioned throughout `packages/contracts/AGENTS.md` and the scope rules as "Pair.swap's `+1` K slack") is precisely the kind of per-trade rounding tolerance that, compounded over many buy/sell round-trips by a single unprivileged trader, can erode `reserveAsset` by a few wei below `virtualLtReserve` — the same way a rounding-off-by-one in `atom_length - 8` erodes `atom_length` below 8 in the GHSL report. Once that happens, `assetReserve - _launchTimeVirtualLtReserve(...)` underflows.

This is directly analogous to the fixed sibling bug: `test_donation_realBalanceExceedsReserveToken` proves the team already observed a live scenario where a stored-reserve invariant assumed by the code broke under attacker-crafted trade sequences (there, a token donation drove `realBalance > reserveToken`), underflowing the supply-leg subtraction in `previewLtUntilGraduation` and cascading into a `Zap.buy` DoS: [3](#0-2) 

The fix applied only guards `reserveToken - realBalance` (the supply leg): [4](#0-3) 

No equivalent guard was added to the USD leg's `assetReserve - _launchTimeVirtualLtReserve(...)` subtraction in either `canGraduate` (line 692) or `previewLtUntilGraduation` (line 722), even though `canGraduate` is invoked on the hot path of **every** buy and **every** sell: [5](#0-4) [6](#0-5) 

Because Solidity 0.8.24 uses checked arithmetic by default, the underflow does not silently wrap into a huge value (as in the C `g_memdup2` OOB-read case) — it reverts. But given `canGraduate` gates `_executeBuy` (post-buy inline graduation check) and `sell` (pre-sell graduation re-check), a revert there permanently DoS's **every** buy and sell on that curve: trader funds already committed to the curve (tokens bought, LT deposited) become unable to be sold or to trigger graduation, since both `Bonding.buy` → `_executeBuy` → `canGraduate` and `Bonding.sell` → `canGraduate` (via `if (canGraduate(tokenAddress)) revert TokenIsGraduating();`) hit the same reverting subtraction. This is a permanent freezing of trader funds on that token's curve, satisfying the "Validate" bar.

### Impact Explanation
If `reserveAsset` can ever be driven (even by 1 wei) below the recovered `_launchTimeVirtualLtReserve` through legitimate, permissionless buy/sell round-trips (enabled by the documented K-invariant rounding slack in `Pair.swap`), `canGraduate` reverts on every subsequent call. Since `canGraduate` is called inline after every buy (`_executeBuy`) and before every sell (`Bonding.sell`), the entire curve for that token becomes permanently untradeable — buyers can no longer buy, holders can no longer sell, and the token can never reach graduation via the normal path either, since `triggerGraduation` also calls `canGraduate`. This is a full freeze of every trader's and creator's funds locked in that curve, with no recovery path in the current code (no floor guard, no alternate accessor).

### Likelihood Explanation
The precondition — `reserveAsset` dipping below the launch-time virtual reserve — requires only unprivileged, permissionless buy/sell calls through `Zap.buy` / `Zap.sell` (or direct `Bonding.buy`/`sell` via an allow-listed router), repeated enough times to accumulate the rounding slack that `Pair.swap`'s "+1 K slack" is documented to tolerate on every single trade. No privileged role, upgrade, or off-chain component is needed. The team's own test suite (`Zap.t.sol`'s donation-attack regression) demonstrates that this exact class of "one AMM leg is guarded, the sibling leg using the same pattern is not" bug has already manifested once in this codebase, making it a credible, previously-proven bug class here rather than a purely theoretical one.

### Recommendation
Mirror the guard already applied to the supply leg onto the USD leg: before computing `assetReserve - _launchTimeVirtualLtReserve(token_, pair)` in both `canGraduate` and `previewLtUntilGraduation`, check `assetReserve >= _launchTimeVirtualLtReserve(...)` and treat the shortfall case as `realLtRaised = 0` (not yet graduatable) rather than letting the subtraction underflow and revert. Additionally, audit `Pair.swap`'s K-slack tolerance to confirm it can never let cumulative sells pull `reserveAsset` below the pair's initial virtual reserve, and add an invariant test (paralleling `test_donation_realBalanceExceedsReserveToken`) that repeatedly buys/sells to try to drive `reserveAsset` under `_launchTimeVirtualLtReserve` and asserts `canGraduate` never reverts.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a minimal seed, establishing `pair.reserveAsset() == virtualLtReserve` at `_launchTimeVirtualLtReserve`.
2. As an unprivileged trader, repeatedly call `Zap.buy` followed immediately by `Zap.sell` for the same token, each round-trip sized to interact with `Pair.swap`'s K-invariant rounding slack on the sell leg (per `AGENTS.md`'s documented "+1 K slack").
3. After enough round-trips, `pair.getReserves()`'s `reserveAsset` slot drifts to a value strictly less than `_launchTimeVirtualLtReserve(token, pair)` (`Pair.k() / TOTAL_SUPPLY`).
4. The next call to `Bonding.canGraduate(token)` — triggered inline by any further `Zap.buy`/`Zap.sell` — executes `assetReserve - _launchTimeVirtualLtReserve(...)` at `packages/contracts/src/Bonding.sol:692`, underflows, and reverts, permanently bricking all further buys and sells on that token's curve.

*(Note: reproducing the exact number of round-trips and slack magnitude requires running `Pair.sol`'s swap/K-check code directly, which I could not fetch in this pass due to tool/output limits — the mechanism is inferred from `Router.sol`'s `_computeBuy`/`_computeSell` cap logic already reviewed and from the K-slack description in `packages/contracts/AGENTS.md`. A background engineer should instrument `test/GraduationInvariants.t.sol` or `test/Bonding.t.sol` with a fuzzed buy/sell round-trip loop asserting `canGraduate` never reverts, to concretely confirm reachability.)*
