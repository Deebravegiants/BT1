### Title
Unchecked `String::from_utf8_unchecked` on Untrusted Cross-Chain Message Body Produces Invalid UTF-8 Strings (Undefined Behavior) - (File: modules/pallets/demo/src/lib.rs)

### Summary
`IsmpModuleCallback::on_accept` in `pallet-ismp-demo` converts the raw `request.body` of an incoming `PostRequest` from an EVM source chain directly into a `String` using `unsafe { String::from_utf8_unchecked(request.body) }`, without any UTF-8 validity check [3](#0-2) . This pallet is wired into the production Gargantua/Nexus runtime's ISMP `ProxyModule` router and is reachable by any relayer that delivers a proven `PostRequest` message targeting `pallet_ismp_demo::PALLET_ID` [4](#0-3) .

### Finding Description
`request.body` is attacker-controlled bytes carried in a cross-chain `PostRequest`, whose contents are opaque application payload set by the source-chain sender and only checked for structural membership-proof validity by `pallet-ismp`, not for UTF-8 well-formedness [5](#0-4) . When `source_chain` is `StateMachine::Evm(_)`, the code calls `String::from_utf8_unchecked(request.body)` and immediately uses the resulting `String` as event data [2](#0-1) . `from_utf8_unchecked` is documented by the Rust standard library as `unsafe` precisely because passing non-UTF-8 bytes is undefined behavior — the safety invariant of `str`/`String` (that its bytes are valid UTF-8) is violated. Any relayer submitting a `PostRequest` from an EVM chain to `pallet-ismp-demo`'s module ID with a body that is not valid UTF-8 breaks this invariant. This is directly analogous to CVE-2021-24028's bug class: deserialization of attacker-controlled, unvalidated wire data is fed into a low-level unsafe operation whose correctness depends on invariants the deserialization path never checks, corrupting an in-memory representation and yielding undefined behavior (which downstream, depending on optimizations/inlining, LLVM is free to miscompile around, since it assumes `String` invariants hold — potentially causing crashes or exploitable memory-safety issues, not merely a logic bug).

### Impact Explanation
Undefined behavior triggered by unprivileged relayer/message-dispatcher input on a live parachain collator is a memory-safety/availability issue: it can crash the node's block-execution / STF logic (denial of service for the whole ISMP subsystem, since panics or memory corruption in `on_accept` occur inside consensus-critical extrinsic execution), and in principle undefined behavior gives the compiler license to produce unexpected code paths beyond a simple panic. Because `pallet-ismp-demo` is compiled into the production runtime and reachable through the standard cross-chain request-delivery path (no special privilege needed beyond relaying a validly-proven request), this qualifies as a High severity issue under the reachable-path criteria (a route unable to deliver messages / node crash via a single relayed message).

### Likelihood Explanation
High. Any account or relayer able to dispatch a `PostRequest` from an EVM-classified source chain (`StateMachine::Evm(_)`) to `pallet_ismp_demo::PALLET_ID` on Gargantua/Nexus can trigger this by simply choosing a non-UTF-8 body (e.g., a single `0xFF` byte). No consensus fraud or governance compromise is needed — the ISMP membership/consensus proof only attests to inclusion of the request, not to the semantic content of `body`.

### Recommendation
Replace `String::from_utf8_unchecked(request.body)` with `String::from_utf8(request.body)` and handle the `Err` case by rejecting the request (returning an `IsmpError`) or by using `String::from_utf8_lossy` if display-only semantics are acceptable, so malformed bytes can never violate the `String` UTF-8 invariant.

### Proof of Concept
1. On an EVM-classified source chain, construct and relay a `PostRequest` with `to = pallet_ismp_demo::PALLET_ID` bytes and `body = vec![0xFF]` (invalid UTF-8).
2. Submit the corresponding `RequestMessage` with a valid membership proof via `pallet_ismp::Call::handle_unsigned` so the request passes proof verification [5](#0-4) .
3. `pallet-ismp` routes to `ProxyModule::on_accept`, which forwards to `pallet_ismp_demo::IsmpModuleCallback::on_accept` [1](#0-0) .
4. `String::from_utf8_unchecked(request.body)` executes on the invalid bytes, producing a `String` that violates UTF-8 invariants — undefined behavior [6](#0-5) .
