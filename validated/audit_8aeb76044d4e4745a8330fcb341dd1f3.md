### Title
Infinite loop / unbounded memory growth in `AncestryChain::ancestry` reachable via unsigned GRANDPA consensus messages - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`AncestryChain::ancestry` (used by GRANDPA justification verification and by `verify_grandpa_finality_proof`) walks a parent-hash chain supplied entirely by the untrusted proof, with no cycle detection and no bound on the number of steps. An attacker can craft two synthetic headers whose `parent_hash` fields point at each other, creating a 2-node cycle. When the target of this walk is not on the cycle, the `while current_hash != base` loop never terminates, spinning forever and growing the `route` vector without bound — this is directly analogous to the reported `ChmParser` infinite-loop DoS (CWE-835) triggered by crafted/fuzzed input.

### Finding Description
`AncestryChain::ancestry` in [1](#0-0)  is:

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
```

`self.ancestry` is built directly from the untrusted `votes_ancestries`/`unknown_headers` field of the submitted proof, via `AncestryChain::new` [2](#0-1) . Because a Substrate `Header` is a plain SCALE struct, an attacker fully controls every field including `parent_hash` — there is no cryptographic constraint linking a header's `parent_hash` to any other header's actual content beyond what the attacker chooses to encode. This lets an attacker construct headers `H1`, `H2` with `H1.parent_hash == hash(H2)` and `H2.parent_hash == hash(H1)`, i.e., a self-referential 2-cycle, entirely offline before submission.

This function is reachable from two attacker-controlled call sites:
- `GrandpaJustification::verify_with_voter_set` calls `ancestry_chain.ancestry(base_hash, signed.precommit.target_hash)` for each precommit [3](#0-2) .
- `verify_grandpa_finality_proof` calls `headers.ancestry(base.hash(), consensus_state.latest_hash)` and `headers.ancestry(from, target.hash())` [4](#0-3) .

Both are exercised end-to-end by `pallet_ismp::Call::handle_unsigned`, a fully permissionless unsigned extrinsic (`ensure_none(origin)`), whose messages include `Message::Consensus(ConsensusMessage)` [5](#0-4) . Critically, `ValidateUnsigned::validate_unsigned` for this pallet actually *executes* the messages (`Self::execute(messages.clone())`) during transaction-pool validation itself [6](#0-5) , i.e., before any block inclusion and with no weight metering. This means merely gossiping the malicious unsigned transaction to a node is enough to hang that node's transaction-pool validation logic indefinitely, for free.

### Impact Explanation
An unprivileged attacker can submit (or merely gossip) a single unsigned `handle_unsigned` extrinsic carrying a crafted GRANDPA `ConsensusMessage`. Every node that receives and validates this transaction — in `validate_unsigned`, prior to any weight-limited dispatch — enters the infinite loop inside `AncestryChain::ancestry`, permanently hanging that thread and growing memory without bound. This can be repeated against every relayer/collator/full node on any chain that registers the GRANDPA consensus client, producing a network-wide denial of service against the relayer/consensus-update path — matching the "route unable to deliver messages" acceptance criterion via halted consensus-state validation.

### Likelihood Explanation
High. No signature, stake, or special permission is required; the extrinsic is unsigned and free. Constructing the two colliding headers requires no cryptographic breaks — the attacker simply chooses arbitrary field values (including `parent_hash`) for two `Header` structs and computes their hashes, then cross-wires the `parent_hash` fields. Any state machine wired to the `ismp-grandpa` client is affected.

### Recommendation
Add cycle detection (e.g., track visited hashes in a `BTreeSet`, returning `NotDescendent` on revisit) and/or an explicit maximum step bound (e.g., bounded by `self.ancestry.len() + 1`) inside `AncestryChain::ancestry`, so a chain that cannot possibly reach `base` within `ancestry.len()` steps is rejected in O(n) rather than looping forever. Apply the same fix to any duplicated `AncestryChain` implementation used by the ismp-grandpa client. Additionally, consider not fully executing/verifying consensus messages inside `validate_unsigned` without a hard step/weight budget, so a pathological proof cannot stall transaction-pool validation itself.

### Proof of Concept
1. Construct two `SubstrateHeader` values `H1`, `H2` (arbitrary `number`/`state_root`/`extrinsics_root`/`digest`), setting `H1.parent_hash = hash(H2)` and `H2.parent_hash = hash(H1)` (choose `H2`'s content first, compute its hash, embed it as `H1.parent_hash`; then compute `H1`'s hash and embed it as `H2.parent_hash`).
2. Build a `GrandpaJustification`/`FinalityProof` whose `unknown_headers`/`votes_ancestries` contains `[H1, H2]`, with a `commit.target_hash` (or `base`) pointing to a hash NOT equal to `hash(H1)` or `hash(H2)` so the walk never reaches `base`.
3. Wrap this in a SCALE-encoded `ConsensusMessage` targeting a registered GRANDPA `consensus_state_id`, and submit it via `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(msg)] }` as an unsigned transaction.
4. Observe that `validate_unsigned` calls `Self::execute`, which reaches `AncestryChain::ancestry`, which loops forever toggling between `hash(H1)` and `hash(H2)`, hanging the validating node's transaction-pool worker and growing `route` without bound.
