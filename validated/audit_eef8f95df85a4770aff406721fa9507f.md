### Title
Webhook Shop Identity Spoofing via HMAC Signature That Only Covers the Request Body, Not the `Shop-Domain` Header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable string from the raw request body only, while the shop identity (`shop`, along with `topic` and `webhook_id`) is read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` from the header to build `WebhookMetadata` passed to the app's handler. Since the HMAC signature never binds the `shop-domain` header, any party in possession of one validly-signed webhook body/HMAC pair (e.g., from their own shop's legitimate webhook delivery) can replay that exact body+signature to the app's public webhook endpoint while substituting a different `shop-domain` header value, and the app will process the payload as if it originated from that other (victim) shop.

### Finding Description
The HMAC binding is defined in: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors are parsed straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` checks only that the HMAC is valid, then immediately trusts `request.shop` (from the unauthenticated header) to construct `WebhookMetadata` handed to the application's business logic: [4](#0-3) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used to attribute the webhook data`. In this code, the HMAC authenticates only body bytes; the shop claim used downstream for tenant attribution is taken from a header outside the signed material. Anyone with a legitimately-signed webhook (from their own shop, which requires no secret — Shopify sends it to any subscribed shop) can capture the `(raw_body, hmac)` pair and POST it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header. `HmacValidator.validate` still returns `true` because the body/signature pair is untouched, but `WebhookMetadata.shop` now reflects the attacker-supplied victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an unprivileged actor (any merchant who has installed the app on their own store, or anyone who intercepts a publicly-observable webhook delivery) can inject data attributed to a different, victim shop into the host application's per-shop data pipeline — e.g., triggering handlers that write order/product/customer data keyed by `data.shop` for a shop they don't control. This is a cross-tenant data-integrity/confusion vulnerability reachable without the app's `client_secret` or any access token, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is high for any app that exposes a webhook receiver at a public URL (a documented and required deployment pattern) and uses `Registry.process`/`WebhookMetadata.shop` to key data by shop. The attacker only needs one legitimately delivered webhook to their own store — no secret material, no elevated privilege — and standard HTTP tooling to replay it with a modified header.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-verified signable content, or otherwise separately authenticate the shop claim before trusting it — e.g., verify that `request.shop` corresponds to a shop for which the app holds a valid, previously-stored session/access token, and reject/log mismatches instead of unconditionally trusting the header. At minimum, document that `WebhookMetadata.shop` is unauthenticated and must not be used as the sole tenant key without cross-checking against known installed shops.

### Proof of Concept
1. App shop A (attacker-controlled) installs the app and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac for raw body B>`, and body `B`.
3. Attacker captures `B` and the valid HMAC value (trivial — it's their own webhook).
4. Attacker sends a new POST request directly to the app's public webhook endpoint with the identical body `B` and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only validates `B` against the HMAC — it never inspects the shop header.
6. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-controlled data as though it came from `victim-shop.myshopify.com`.
