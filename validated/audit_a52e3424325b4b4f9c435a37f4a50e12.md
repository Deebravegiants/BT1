### Title
Panic in `receipt_filter_fn()` on stale `GlobalContractDistribution` delayed receipts after double resharding causes permanent chain stall - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`DelayedReceiptQueueWrapper::pop()` unconditionally pops every entry from the persistent `DelayedReceiptQueue` and calls `receipt_filter_fn()` on it to decide whether it belongs to the current shard after a resharding event. `receipt_filter_fn()` calls `.unwrap()` on `receiver_shard_id(&shard_layout)`, which can fail for a `GlobalContractDistribution` receipt whose `target_shard` no longer maps into the shard layout after two sequential resharding events. This is directly analogous to the LiquidityPool `QueuedWithdraw` bug: a single problematic entry stuck in a persistent queue causes every future attempt to drain the queue to abort, and because the queue is only mutated via the same non-committing code path, the failure recurs deterministically on every re-application of the chunk, permanently blocking progress.

### Finding Description
The delayed receipt queue is a persistent FIFO stored in the trie (`core/store/src/trie/receipts_column_helper.rs`), analogous to Polynomial's `withdrawalQueue`. Instead of simple removal, `DelayedReceiptQueueWrapper::pop()` (`runtime/runtime/src/congestion_control.rs:880-910`) loops, popping entries and filtering out ones that no longer belong to the current shard (needed for `ReshardingV3`, where stale delayed receipts may transiently belong to a sibling shard). The filtering itself is done in `receipt_filter_fn()`: [1](#0-0) 

Both `self.epoch_info_provider.shard_layout(&self.epoch_id).unwrap()` and `receipt.get_receipt().receiver_shard_id(&shard_layout).unwrap()` can panic. As documented in the repository's own regression test, after two sequential resharding events a stale `GlobalContractDistribution` receipt's recorded `target_shard` can no longer be remapped into the current shard layout, causing `receiver_shard_id()` to fail and the `.unwrap()` to panic: [2](#0-1) 

This is called from `process_delayed_receipts()`, which is on the mandatory chunk-apply path for every block: [3](#0-2) 

Because the queue entry is only removed from the trie as part of an in-memory `TrieUpdate` that is committed atomically along with the rest of `Runtime::apply`, a panic aborts the entire chunk application before any state change (including the queue-index advancement) is persisted. On the next attempt to apply the same chunk (e.g., on node restart or catch-up), the same stale receipt is at the head of the queue again, and the same panic recurs — exactly mirroring the report's core defect: "if the processing of a queued entry reverts, the head pointer never advances and all further processing is blocked."

### Impact Explanation
Unlike Solidity's revert model where only the affected pool function reverts, a Rust panic inside `Runtime::apply()` on the hot chunk-processing path crashes the node process (or is caught as an unrecoverable "unexpected panic" depending on `catch_unwind` boundaries used by the client). Because the stale receipt can never be filtered out or skipped, and its removal is never durably committed, every validator/node that attempts to apply this chunk will panic identically and deterministically, causing a persistent shard-wide chain stall — an unrepairable liveness failure requiring a protocol fix/hotfix, not just a retry. This is a stronger analog of the original DoS: instead of a single user losing funds, it can halt block production/execution entirely for the affected shard.

### Likelihood Explanation
Triggering the bug requires: (1) creating a `GlobalContractDistribution` receipt whose `target_shard` points at a shard, (2) that shard undergoing resharding once so the receipt becomes "stale" relative to the new layout, while the receipt remains queued (e.g., via chunk compute saturation to keep it in the delayed queue), and (3) a second resharding event before the receipt is drained, so `receiver_shard_id()` cannot remap it into the current layout. This requires dynamic resharding to be enabled and an attacker or unlucky sequence of events to keep the receipt delayed across two reshardings — a non-trivial, but protocol-triggerable and reproducible condition (the repository ships a deterministic regression test reproducing exactly this scenario), not a purely theoretical concern.

### Recommendation
`receipt_filter_fn()` (and its callers in `pop()`/`peek_iter()`) should not use `.unwrap()` on `receiver_shard_id()`/`shard_layout()`. Instead, treat receipts whose `target_shard` can no longer be resolved as a recoverable condition: either fall back to forwarding/dropping them via a well-defined migration path, or return a `Result` so the caller can handle unresolvable stale receipts gracefully (e.g., route through a fallback shard or emit a protocol-versioned migration) rather than panicking and repeatedly failing chunk application.

### Proof of Concept
The repository already contains a targeted regression test that reproduces this exact scenario end-to-end (deploy global contract → saturate compute to keep its `GlobalContractDistribution` receipt in the delayed queue → force two sequential shard splits → drain the queue and assert the chain does not stall): [4](#0-3) 
The assertion `head_height >= drain_end` with the failure message "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)" confirms the intended failure mode is exactly a chain stall from the panic described above.

fn test_stale_global_contract_distribution_after_double_resharding() {
    init_test_logger();

    // The fix only works with V3 shard layouts (dynamic resharding).
    // With static resharding, the shard layout doesn't maintain a full split history.
    if !ProtocolFeature::DynamicResharding.enabled(PROTOCOL_VERSION) {
        return;
    }

    let epoch_length: BlockHeightDelta = 10;
    let base_boundary_accounts = create_account_ids(["user2", "user3"]).to_vec();
    let base_shard_layout = ShardLayout::multi_shard_custom(base_boundary_accounts, 3);
    let deploy_user: AccountId = create_account_id("user0");
    let users = create_account_ids(["user0", "user1", "user2", "user3", "user4", "user5"]).to_vec();
    let validators_spec = create_validators_spec(1, 0);
    let clients = validators_spec_clients(&validators_spec);
    let chunk_producer = clients[0].clone();
    let gas_limit = Gas::from_teragas(300);
    let base_pv = PROTOCOL_VERSION - 1;

    // Configure dynamic resharding to force-split two shards sequentially.
    // The first split targets the shard containing deploy_user (user0), so the
    // GlobalContractDistribution receipt becomes stale after two layout transitions.
    let first_split_shard = base_shard_layout.account_id_to_shard_id(&deploy_user);
    let second_split_shard = base_shard_layout.account_id_to_shard_id(&create_account_id("user4"));
    assert_ne!(first_split_shard, second_split_shard);

    let dynamic_config = DynamicReshardingConfig {
        memory_usage_threshold: u64::MAX,
        min_child_memory_usage: u64::MAX,
        max_number_of_shards: 100,
        min_epochs_between_resharding: 1.try_into().unwrap(),
        force_split_shards: vec![first_split_shard, second_split_shard],
        block_split_shards: vec![],
    };

    let genesis = TestLoopBuilder::new_genesis_builder()
        .protocol_version(base_pv)
        .validators_spec(validators_spec)
        .shard_layout(base_shard_layout.clone())
        .epoch_length(epoch_length)
        .gas_limit(gas_limit)
        .add_user_accounts_simple(&users, Balance::from_near(1_000_000))
        .build();
    let base_epoch_config = TestEpochConfigBuilder::from_genesis(&genesis).build();

    let mut dynamic_epoch_config = base_epoch_config.clone();
    dynamic_epoch_config.shard_layout_config =
        ShardLayoutConfig::Dynamic { dynamic_resharding_config: dynamic_config };

    let epoch_config_store = EpochConfigStore::test(BTreeMap::from([
        (base_pv, Arc::new(base_epoch_config)),
        (base_pv + 1, Arc::new(dynamic_epoch_config)),
    ]));

    let mut env = TestLoopBuilder::new()
        .genesis(genesis)
        .clients(clients)
        .epoch_config_store(epoch_config_store)
        .gc_num_epochs_to_keep(5)
        .build();

    // Step 1: Deploy the test contract on user0's account so we can call burn_gas_raw.
    {
        let node = env.node_for_account(&chunk_producer);
        let tx = node.tx_deploy_test_contract(&deploy_user);
        node.submit_tx(tx);
    }
    env.runner_for_account(&chunk_producer).run_for_number_of_blocks(2);

    // Step 2: Deploy a global contract from user0. This creates a
    // GlobalContractDistribution receipt with target_shard = user0's shard (S_A),
    // which is the shard that will be split in the first resharding.
    {
        let node = env.node_for_account(&chunk_producer);
        let code = ContractCode::new(near_test_contracts::rs_contract().to_vec(), None);
        let tx = node.tx_deploy_global_contract(
            &deploy_user,
            code.code().to_vec(),
            GlobalContractDeployMode::CodeHash,
        );
        node.submit_tx(tx);
    }

    // Step 3: Saturate compute on user0's shard every block so that the
    // GlobalContractDistribution receipt (arriving as incoming) gets pushed to
    // the delayed queue and stays there through both resharding events.
    //
    // Each burn_gas_raw call burns slightly more than half the gas limit, so
    // two local receipts exhaust the chunk's compute budget. We submit 3 per
    // block to ensure at least 2 are processed as local receipts.
    let gas_to_burn = gas_limit.checked_div(2).unwrap().checked_add(Gas::from_gas(1)).unwrap();
    let initial_num_shards = base_shard_layout.num_shards();
    let target_num_shards = initial_num_shards + 2; // after two splits

    let start_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };

    // Keep saturating until both resharding events complete. Dynamic resharding has a
    // 2-epoch proposal-to-activation pipeline, so we need enough epochs for both splits.
    let max_saturation_height = start_height + epoch_length * 12;
    let mut both_splits_done = false;
    for target_height in (start_height + 1)..=max_saturation_height {
        // Submit 3 heavy transactions to saturate this block's compute budget.
        {
            let node = env.node_for_account(&chunk_producer);
            for _ in 0..3 {
                let tx = node.tx_call(
                    &deploy_user,
                    &deploy_user,
                    "burn_gas_raw",
                    gas_to_burn.as_gas().to_le_bytes().to_vec(),
                    Balance::ZERO,
                    gas_limit,
                );
                node.submit_tx(tx);
            }
        }
        env.runner_for_account(&chunk_producer).run_until_head_height(target_height);

        // Check if both resharding events have completed.
        let node = env.node_for_account(&chunk_producer);
        let epoch_id = node.client().chain.chain_store().head().unwrap().epoch_id;
        let current_layout = node.client().epoch_manager.get_shard_layout(&epoch_id).unwrap();
        if current_layout.num_shards() >= target_num_shards {
            both_splits_done = true;
            break;
        }
    }
    assert!(both_splits_done, "both shard splits did not complete within the allotted blocks");

    // Step 4: Stop saturating. Let the delayed queue drain.
    // If the vulnerability exists, processing the stale GlobalContractDistribution
    // receipt will panic in receipt_filter_fn() when receiver_shard_id() fails
    // to remap the old target_shard after two resharding generations.
    let current_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    let drain_end = current_height + epoch_length * 2;
    env.runner_for_account(&chunk_producer).run_until_head_height(drain_end);

    let head_height = {
        let node = env.node_for_account(&chunk_producer);
        node.client().chain.chain_store().head().unwrap().height
    };
    assert!(
        head_height >= drain_end,
        "chain stalled at height {}; expected >= {} (likely panicked processing stale receipt)",
        head_height,
        drain_end
    );
}
