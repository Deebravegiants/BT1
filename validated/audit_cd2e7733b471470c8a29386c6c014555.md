### Title
Deposits minted zero shares when vault total-assets is zero but total-supply is non-zero, causing silent loss of deposited principal - (File: mainnet/contracts/vault/v0-vault-usdc.clar and equivalent v0-vault-*.clar / vault-*.clar files)

### Summary
Zest's per-underlying vault contracts guard the exchange-rate division-by-zero case highlighted in the external report by short-circuiting `convert-to-shares-preview` to return `u0` instead of reverting when `total-assets-preview` is `u0`. However, `deposit` has no `> 0` check on the resulting `inkind` (shares to mint), unlike `redeem`, which explicitly asserts `(> inkind u0) ERR-OUTPUT-ZERO`. This asymmetry converts the "protocol freeze" bug class from the report into a "silent value loss" bug: instead of reverting, a depositor can transfer real underlying assets into the vault and receive zero shares in return.

### Finding Description
The conversion helper mirrors the report's identified division-by-zero hazard but resolves it by returning zero instead of reverting: [1](#0-0) 

`deposit` computes `inkind` from this helper and only checks it against `min-out` (a caller-supplied slippage bound), not against zero: [2](#0-1) 

If a caller (or the default UI) passes `min-out = 0` (a very common default/no-slippage-protection case), the `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` check trivially passes even when `inkind` is `0`. The transaction then proceeds to pull in the depositor's `amount` via `receive-underlying`, mint `0` shares via `ft-mint?`, and increase `assets` by the full deposited `amount`. The depositor's principal is added to the vault's backing with no corresponding share issued to them — it is silently redistributed to all existing s-token holders.

By contrast, `redeem` in the same contract explicitly guards against this exact zero-output scenario: [3](#0-2) 

This is the analog of the reported identity break: `totalAssets == 0` while `totalSupply > 0` (reachable when the vault's liquid `assets` balance is fully lent out, i.e. `current-assets = 0` and `total-debt <= total-borrowed`, so `total-assets-preview` returns `0`). In the original Sherlock report this state made the protocol *revert* (freeze). In this codebase the same state does not freeze — but it opens a path for principal to be minted at a zero share-price without depositor protection, breaking the equation:
`shares_minted (0) != value_added / exchangeRate` for any nonzero deposit, i.e. `assets_after - assets_before = amount > 0` while `shares_minted = 0`.

This same pattern (`convert-to-shares-preview` short-circuit + missing zero-check in `deposit`) is repeated identically across all vault contracts (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, and their `local-testing` counterparts).

### Impact Explanation
This is a permanent, unrecoverable loss of the depositor's principal for any deposit made while `total-assets == 0` and `total-supply > 0`, with the value transferred to existing shareholders rather than reflected in the depositor's balance. It qualifies as theft of principal / permanent freezing of the depositor's funds (they cannot get back what they deposited, since they received no claim on it), satisfying the required impact bar.

### Likelihood Explanation
Reaching `total-assets-preview == 0` requires the vault's `assets` variable to hit zero (all liquidity lent out via `borrow`) while accrued interest has not yet exceeded `total-borrowed`. This is a state achievable through normal, unprivileged utilization of the lending market (no DAO action, no oracle manipulation, no flashloan reliance) at very high utilization, which is plausible over the vault's lifetime, especially right after `initialize` mints only `MINIMUM-LIQUIDITY` shares to a null address and organic usage drives utilization toward 100%. The trigger additionally requires a depositor (or front-end) to submit `min-out = 0`, which is a common/default value when slippage protection isn't explicitly configured.

### Recommendation
Add an explicit zero-output check to `deposit`, symmetric with the one already present in `redeem`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `deposit` assertions in each vault contract (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, and their `local-testing` equivalents). Additionally, consider maintaining a protocol-enforced minimum backing (as recommended in the original report) so that `total-assets` cannot reach exactly zero while `total-supply` is non-zero.

### Proof of Concept
1. Vault is initialized normally; `MINIMUM-LIQUIDITY` shares are minted to `NULL-ADDRESS` at initialization [4](#0-3) .
2. Borrowers borrow against the vault until `var-get assets` (current liquid assets) reaches `0`, while `total-debt <= total-borrowed` (no net interest accrued yet), making `total-assets-preview` return `0`.
3. `total-supply` remains non-zero (existing s-token holders still hold shares).
4. A user calls `deposit(amount, 0, recipient)` with a nonzero `amount` and `min-out = 0`.
5. `convert-to-shares-preview` computes `ta = 0`, hits the `(is-eq ta u0)` branch, and returns `u0` for `inkind`.
6. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` → `(>= u0 u0)` passes.
7. `receive-underlying` transfers `amount` of the underlying token from the depositor into the vault; `ft-mint?` mints `0` shares to `recipient`; `assets` is incremented by `amount`.
8. The depositor has permanently lost `amount` of principal with zero shares to show for it; the vault's backing (and thus the exchange rate for existing holders) increased at the depositor's expense.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
