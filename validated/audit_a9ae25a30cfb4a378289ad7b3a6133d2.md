### Title
Deterministic, unsigned offline session-id cookie lets an attacker impersonate any known shop and exfiltrate its access token - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps the gem sets the `shopify_app_session` cookie's value directly to `session.id`, and for offline sessions that id is generated by `SessionUtils.offline_session_id` as `"offline_#{shop}"` — a fully deterministic string derived only from the public `.myshopify.com` domain, with no secret or per-request binding [1](#0-0) . `SessionUtils.cookie_session_id`/`current_session_id` then trust that raw cookie value as-is with no cryptographic signature or verification tying it to an authenticated browser session [2](#0-1) . Following the documented pattern of `session_storage.load_session(session_id)` + `Context.active_session = session`, an attacker who merely knows a victim's shop domain can forge the cookie header on a raw HTTP request and have the host app hand back the victim's real access token.

### Finding Description
The binding that should hold is: `Context.active_session.access_token` must equal the access token that belongs to the shop cryptographically authenticated in *this* request — i.e. `session.shop == authenticated_requester.shop`. Tracing the code shows this binding is never enforced for the non-embedded cookie path:

1. During OAuth completion, `Oauth.validate_auth_callback` sets the browser cookie's value to the plain, unsigned `session.id` [3](#0-2) . For an offline session this id is computed by `offline_session_id(shop)` as `"offline_#{shop}"` [1](#0-0)  — no random nonce, no HMAC, nothing that requires possession of `api_secret_key` or any secret to reproduce.
2. On every subsequent request, `SessionUtils.current_session_id` for a non-embedded app (or an embedded app falling back to cookies) reads the cookie hash supplied by the host and returns `cookies[SESSION_COOKIE_NAME]` verbatim via `cookie_session_id` — there is no signature check, no comparison against any value that was itself verified via HMAC or JWT in this request [4](#0-3) .
3. Per the README/docs' documented flow, the host app then does `session = session_storage.load_session(session_id)` and `Context.active_session = session`, which loads the actual persisted `Session` object (including the real `access_token`) that was created by legitimate OAuth for that shop.

Because the cookie's content is fully attacker-computable from public information (the shop's `myshopify.com` subdomain) and is never validated cryptographically by this gem, an attacker does not need to steal the victim's browser cookie via XSS or network interception — they can simply construct the `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` header on their own raw HTTP request to the app server. None of the existing guards intercept this: `HmacValidator.validate` and the OAuth `state` comparison only run during the OAuth callback, not on ordinary authenticated app requests; `JwtPayload`'s `aud`/signature checks only apply to the embedded id_token path, which this cookie-fallback path bypasses entirely; `Context.setup?`/`private?`/`embedded?` only gate configuration, not per-request cookie authenticity.

### Impact Explanation
Any unprivileged internet user who knows (or enumerates) a target merchant's `.myshopify.com` domain — public information visible in storefront URLs, app-store listings, etc. — can obtain that merchant's persisted offline access token bound into their own request's `Context.active_session`, and then issue REST/GraphQL calls through `Clients::HttpClient` using the victim's credentials. This is a full cross-tenant access-token exfiltration, repeatable against any shop whose domain the attacker knows, with no per-victim secret required. This matches the Critical category: "theft or exfiltration of a merchant access token" and "cross-tenant access."

### Likelihood Explanation
Preconditions: the host app must be a non-embedded app (or an embedded app that falls back to cookie-based sessions, which the docs explicitly support), use offline sessions, and follow the documented `current_session_id` → `session_storage.load_session` → `Context.active_session=` pattern exactly, as the question stipulates. Attacker cost is trivial: no secret, no XSS, no TLS interception — just knowledge of the target's shop domain and the ability to set an arbitrary `Cookie` header on an HTTP request, which is explicitly within the attacker's granted capabilities. This makes the attack cheap, deterministic, and repeatable against arbitrary victim shops.

### Recommendation
Do not trust raw cookie content as a bare, unauthenticated session identifier. At minimum: (1) sign/HMAC the session cookie value with `Context.api_secret_key` when it is issued in `Oauth.validate_auth_callback`, and verify that signature in `SessionUtils.cookie_session_id` before returning it; (2) avoid deriving session ids purely from public shop domain data with no secret component (make `offline_session_id` incorporate an unguessable per-installation secret, or rely on a signed/opaque token instead of a predictable string); (3) document clearly that hosts must use a signed/encrypted cookie jar (e.g., Rails' signed cookies) rather than raw Rack cookies with this API, and/or add an explicit warning/guard in `session_utils.rb`.

### Proof of Concept
```ruby
# test/utils/session_utils_forgery_test.rb
require_relative "../test_helper"

class SessionCookieForgeryTest < Test::Unit::TestCase
  def test_attacker_can_construct_victim_offline_session_id_without_secret
    victim_shop = "victim-shop.myshopify.com"

    # Attacker only knows the public shop domain, nothing else.
    forged_session_id = ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop)
    forged_cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

    ShopifyAPI::Context.stubs(:embedded?).returns(false)

    # current_session_id trusts the forged cookie with zero cryptographic check.
    session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, forged_cookies, false)
    assert_equal(forged_session_id, session_id)

    # Simulate the documented host-app pattern:
    victim_session = ShopifyAPI::Auth::Session.new(
      id: forged_session_id,
      shop: victim_shop,
      access_token: "shpat_super_secret_victim_token",
    )
    session_storage = mock
    session_storage.stubs(:load_session).with(session_id).returns(victim_session)

    ShopifyAPI::Context.active_session = session_storage.load_session(session_id)

    # Attacker's subsequent request now carries the victim's real access token.
    assert_equal("shpat_super_secret_victim_token", ShopifyAPI::Context.active_session.access_token)
    assert_equal(victim_shop, ShopifyAPI::Context.active_session.shop)
  end
end
```
This demonstrates both sides of the broken binding: before the forged request, the attacker holds no credential for `victim_shop`; after `current_session_id` → `load_session` → `Context.active_session=`, the attacker's request context holds `access_token == "shpat_super_secret_victim_token"`, i.e. the victim's real token, obtained purely from public shop-domain knowledge with no cryptographic verification anywhere in the gem's code path.
