### Title
Arbitrary, unauthenticated external calls in `EmporiumUpgradeable.runAction` enable ERC777-hook interception and theft of victims' deposited tokens - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `(endpoint, callData, value)` operations directly from the Emporium contract's own address whenever `EmporiumStack.signerAddress == address(0)` (the "Stateless Interaction" branch). No signature, no allow-list of endpoints, and no allow-list of selectors (beyond two hardcoded ones) constrain this call. This mirrors the reported `Executor`/`GenericCrossChainFacet` bug class: an attacker can use these unrestricted calls to register ERC777 hooks and pre-authorize their own contract, then intercept a later, unrelated victim's deposit into Emporium and drain it.

### Finding Description
`runAction` decodes attacker-controlled `circomData.externalActionData.externalActionMetadata` into an `EmporiumStack` and iterates its `ops`: [1](#0-0) 

When `stack.signerAddress == address(0)`, `verifyWallet` returns immediately without checking any signature over the ops: [2](#0-1) 

In that unauthenticated case, every op takes the "Stateless Interaction" branch and is executed directly by Emporium itself, `op.endpoint.call{value: op.value}(op.callData)`, with only two selectors blocked: [3](#0-2) 

Because `runAction` is reachable by any unprivileged EOA that supplies a valid ZK proof for its own UTXOs/deposit (via `Hinkal.transact` -> `Hinkal._externalTransact` -> `IExternalActionV2.runAction`), the attacker fully controls `endpoint` and `callData` for these calls with no allow-list of destinations: [4](#0-3) 

This lets the attacker, in one or more of their own transactions:
1. Make Emporium call `token.approve(attackerContract, MAX)` for an ERC777 token (a stateless op; balance unchanged, so it passes Emporium's post-op `balanceChange >= 0` check).
2. Make Emporium call `ERC1820Registry.setInterfaceImplementer(Emporium, TOKENS_RECIPIENT_INTERFACE_HASH, attackerImplementer)` — this succeeds because `msg.sender == account` (`Emporium` itself is the caller and the account being registered), which is exactly what ERC1820 permits without any special privilege.

Once this state is set, when *any other user* later deposits that ERC777 token into Emporium as part of a normal Hinkal transaction, the token transfer into Emporium (executed in `Hinkal._externalTransact` before `runAction` is even invoked) triggers the ERC777 `tokensReceived` hook, running attacker code in Emporium's transaction context. The attacker's hook then calls `token.transferFrom(Emporium, attacker, allowance)`, draining the just-arrived victim funds using the previously granted approval.

Critically, Emporium's own internal accounting cannot detect this: `balancesBefore` inside `runAction` is snapshotted *after* the deposit transfer (and thus after the hook-triggered theft) has already occurred: [5](#0-4) 
and Hinkal's own outer balance check only tracks Hinkal's own balance (which correctly decreased when it sent funds to Emporium as intended), not what happened to those funds once they reached Emporium: [6](#0-5) 

The equality broken is the "value moved by Hinkal accounted for in the balance equation" invariant: value that left the victim's shielded balance and was transferred to Emporium is diverted to the attacker via a hook triggered inside the same call stack, before Emporium's own before/after accounting or Hinkal's slippage check can observe it — none of these guards were designed to account for reentrant token movement caused by attacker-installed hooks.

### Impact Explanation
This is a direct theft of a victim's in-flight/deposited funds, executed without any authorization from the victim or the prover of the victim's own proof — the attacker's earlier, unrelated transactions permanently poison the shared `Emporium` contract for all future users of that token. This matches the Critical impact category: direct theft of in-flight user funds via calls a wallet owner/prover never authorized.

### Likelihood Explanation
The attacker needs only two ordinary, permissionless Emporium calls (an `approve` and an ERC1820 `setInterfaceImplementer`) executed via their own legitimate-looking transaction with `signerAddress == address(0)`, which requires no special privilege — any user of the Emporium "stateless" call feature can trigger this path. The only precondition is that some ERC777-compliant token is usable through the protocol; there is no evidence of a token allow-list in the reviewed code restricting `erc20TokenAddresses` to non-hook-bearing tokens.

### Recommendation
- Restrict the "Stateless Interaction" call path (`op.endpoint.call(op.callData)`) to an allow-list of trusted endpoints/selectors, analogous to `allowedRecipients` used elsewhere in the codebase, instead of only blacklisting two specific selectors.
- Alternatively, require every `EmporiumOperation` to be authenticated by `signerAddress`'s signature (remove the `signerAddress == address(0)` bypass in `verifyWallet`), so arbitrary calls can never execute purely from unauthenticated `runAction` invocations.
- Disallow tokens with transfer hooks (ERC777/ERC1363-style) from being registered as `erc20TokenAddresses`, or snapshot/verify balances immediately around each token transfer to close the reentrancy window created by transfer hooks.

### Proof of Concept
1. Attacker calls `Hinkal.transact` with `externalActionData.externalActionId` pointing to Emporium and an `EmporiumStack` with `signerAddress = address(0)` and one op: `{endpoint: ERC777Token, callData: approve(attackerContract, type(uint256).max), invokeWallet: false}`. `verifyWallet` passes trivially (no signature required), and `op.endpoint.call(...)` executes `Emporium.approve(...)` successfully.
2. Attacker sends a second such transaction with an op calling `ERC1820Registry.setInterfaceImplementer(Emporium, keccak256("ERC777TokensRecipient"), attackerImplementer)`; this succeeds since `msg.sender == account == Emporium`.
3. Victim later performs an ordinary Hinkal transaction that deposits the ERC777 token into Emporium. During the token transfer (inside `Hinkal._externalTransact`, before `Emporium.runAction`'s own balance snapshot), the ERC777 hook fires and invokes `attackerImplementer.tokensReceived(...)`, which calls `token.transferFrom(Emporium, attackerContract, allowance)`, draining the victim's just-deposited tokens.
4. Neither Emporium's `balancesBefore`/`balancesAfter` check (captured after the theft) nor Hinkal's outer slippage check (which only tracks Hinkal's own balance) detects the loss; the victim's transaction either proceeds with the funds already gone or the resulting shielded UTXO is minted for an amount no longer backed by real tokens in Emporium.
