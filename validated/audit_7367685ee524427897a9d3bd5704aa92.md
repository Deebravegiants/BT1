### Title
Webhook `shop-domain`, `topic` and `webhook-id` headers are trusted for tenant/handler identity but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry` verify a webhook's HMAC over the raw request body only, then pass the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values — none of which are covered by that signature — as trusted identity data to the app's registered handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator` computes and compares the signature exclusively against that signable string: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, and `#webhook_id` are all read straight from HTTP headers, which are never part of the HMAC-signed material: [3](#0-2) 

`Registry.process` validates the HMAC (body-only) and then dispatches to the registered handler using the *header-derived* (unsigned) `topic` and passes the *header-derived* (unsigned) `shop` straight into `WebhookMetadata`: [4](#0-3) 

The equality this breaks: the gem's contract implies `hmac_verified(body) == identity_bound(shop, topic)`, i.e. that a valid signature vouches for the tuple `(shop, topic, body)`. In reality the gem only proves `hmac_verified(body)`; `shop` and `topic` are unauthenticated header values that travel independently of the signature. An attacker who is an ordinary (unprivileged) merchant/app-installer can obtain a validly-signed `(body, hmac)` pair for their **own** shop by triggering a real webhook event (e.g. `products/create`), then replay that exact HTTP request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with an arbitrary target value. `HmacValidator.validate` still succeeds because it only re-derives the HMAC from `@raw_body`, and `Registry.process` will happily route the attacker-authored body to the handler under a spoofed `shop`/`topic` identity.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (the value returned by `Registry.process`'s dispatch) as the tenant key — e.g., to look up which merchant's access token/session to use, or to attribute the webhook body's data to a specific shop record — can be tricked into applying an attacker-controlled body to a different, victim tenant's record. This is a cross-tenant identity-binding break: the gem asserts "this HMAC-valid body belongs to shop X" when it has in fact only proven "this body's bytes are unmodified," not that they originated for shop X. This matches the Critical "cross-tenant access" impact category, since the confused-deputy effect is a direct consequence of how this gem structures and delivers the `WebhookMetadata` object to app handlers.

### Likelihood Explanation
The prerequisite — being able to trigger at least one genuine webhook for one's own shop and capture the resulting `(raw_body, hmac)` — is available to any unprivileged Shopify merchant/app installer; no access to `api_secret_key` or any other privileged credential is needed. Sending the modified replay to the app's public webhook endpoint requires no authentication either, since webhook endpoints are unauthenticated HTTP endpoints by design (verified only via HMAC). The only precondition is that the target application's webhook handler trusts the `shop` field on `WebhookMetadata` for tenant scoping without independently deriving the shop from the signed portion — a very common pattern, since the gem provides no other authenticated channel for this.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook-id` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them, e.g. by having the gem require the caller to supply the expected shop for the delivery and comparing it against the header before trusting it), so a valid signature vouches for the full `(shop, topic, webhook_id, body)` tuple rather than the body alone. At minimum, document that `WebhookMetadata#shop`/`#topic` are NOT covered by HMAC verification and must not be used by consuming applications as an authoritative tenant identifier without additional binding (e.g., cross-checking against the target of an already-registered webhook ID per shop).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and subscribes to a webhook topic the app registers for (e.g. `products/create`).
2. Attacker creates a product in their own store, causing Shopify to deliver a webhook to the app's endpoint with a legitimate body and a correctly computed `x-shopify-hmac-sha256` header (computed by Shopify over that body using the app's real secret — the attacker never needs to know the secret, they just capture the delivered request).
3. Attacker replays the captured HTTP request to the same endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `raw_body` — validation succeeds because the body is untouched: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` equals the attacker-supplied `victim.myshopify.com`, despite the body content originating from the attacker's own shop — a fully spoofed cross-tenant webhook delivery that passes HMAC verification.
