### Title
Unrestricted API-token brute-force via loose "Authenticated" rate limit applied before credential validation on `/v2/*` endpoints - ([File: core/web/router.go])

### Summary
Chainlink's node API applies a global per-IP rate limiter for the entire authenticated route group that is ~200x looser than the dedicated login rate limiter, and this loose limiter is evaluated before/regardless of whether `AuthenticateByToken` credential validation succeeds. This mirrors the Tandoor Recipes bug class (CVE-2026-33152): a credential-guessing surface (there: `BasicAuthentication` on arbitrary API endpoints; here: `X-API-KEY`/`X-API-SECRET` header validation on `/v2/*` endpoints) that bypasses the strict rate limiting intended for the login flow.

### Finding Description
The gin engine sets up two different rate limiters:
- The dedicated login endpoint `/sessions` is protected by the strict `Unauthenticated` limiter (`5` requests / `20s`) via `sessionRoutes`: [1](#0-0) 
- Every other route registered under the top-level `api` group — including all of `v2Routes`, which exposes dozens of endpoints protected only by `auth.AuthenticateByToken` (API key/secret header check) — is instead covered by the much looser `Authenticated` limiter (`1000` requests / `1m`), applied once at router construction: [2](#0-1) 

`AuthenticateByToken` reads `X-API-KEY`/`X-API-SECRET` headers directly from the request and performs credential comparison (`FindUserByAPIToken` + `AuthenticateUserByToken`) on every request that hits any `/v2/*` endpoint, before returning 401 on failure: [3](#0-2) 

These `/v2/*` endpoints (e.g. `/v2/config`, `/v2/keys/eth`, `/v2/bridge_types`, etc.) are registered under `authv2 := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession))`, which only inherits the parent group's loose `Authenticated` rate limiter — there is no dedicated per-endpoint stricter limiter for token-guessing attempts, analogous to how Tandoor's `ACCOUNT_RATE_LIMITS` only covered `/accounts/login/` and not `BasicAuthentication`-protected API routes: [4](#0-3) 

The config confirms the disparity in limits: `Authenticated = 1000` per `1m` vs `Unauthenticated = 5` per `20s`: [5](#0-4) 

### Impact Explanation
An attacker who knows or guesses a valid node user email/API-key access key can attempt up to 1000 `X-API-SECRET` guesses per minute per source IP against any `/v2/*` endpoint (e.g. `GET /v2/config`), roughly 200x the throughput permitted against `/sessions`. There is no account lockout tracking failed token attempts (unlike the local session ORM's password path which at least logs failed attempts via `audit.AuthLoginFailedPassword`). Successful brute force yields full session-equivalent authentication and role-scoped access (Admin/Edit/Run), enabling unauthorized access to sensitive endpoints such as `/v2/keys/eth/export`, `/v2/user/token`, `/v2/transfers`, etc. This matches the CVE's core impact class: authentication bypass via unrestricted brute force on a credential-guessing surface that a login-focused rate limit was not designed to protect.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to already know a valid `AccessKey` (the "username" analog) for a node user's API token, since `FindUserByAPIToken` first looks up by access key before comparing the secret. Access keys are generated randomly and not simply the user's email, which raises the bar compared to Tandoor's plain email/username brute force. However, once an access key is known or leaked (e.g. through logs, shared configs, or CI secrets), the secret can be brute-forced at high throughput due to the loose `Authenticated` rate limit governing the entire `/v2/*` surface.

### Recommendation
Apply a strict, dedicated rate limiter (comparable to `Unauthenticated`) specifically around the `AuthenticateByToken` credential-check path — not the general `Authenticated` group limiter — so that failed token/secret validation attempts are throttled per access-key or per-IP independently of the high authenticated-traffic allowance. Consider adding failed-attempt lockout/backoff tracking for API token authentication similar to what could be added for local password login, and audit-log failed token authentication attempts.

### Proof of Concept
1. Obtain (or guess) a valid API `AccessKey` for a chainlink node (e.g., leaked from logs/CI).
2. Send up to 1000 requests/minute to any `/v2/*` endpoint (e.g. `GET /v2/config`) with header `X-API-KEY: <known-access-key>` and varying `X-API-SECRET` guesses.
3. Because these requests fall under the `api` group's `Authenticated` rate limiter (1000/min) rather than the `Unauthenticated` limiter (5/20s) enforced only on `/sessions`, the attacker can iterate through secret guesses at roughly 200x the throughput permitted against the login form, until `AuthenticateUserByToken` succeeds and grants a session-equivalent authenticated context. func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}

// AuthenticateByToken authenticates a User by their API token.
//
// Implements authMethod
func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
