## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates a webhook's authenticity by checking an HMAC computed over the raw request body only. The `shop` (from the `x-shopify-shop-domain` / `shopify-shop-domain` header) is never included in the signed payload, yet it is passed straight through to the registered webhook handler as the tenant identifier. Because the HMAC secret (`api_secret_key`) is shared across all shops that install the same app, any body+HMAC pair that is valid for one shop remains valid after the shop-domain header is swapped for a different shop, letting an unprivileged holder of one valid webhook delivery impersonate any other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the (unauthenticated) header: [2](#0-1) 

`Registry.process` validates the request purely against `Utils::HmacValidator.validate(request)`, which in turn calls `validate_signature`, computing the HMAC over `verifiable_query.to_signable_string` (the raw body) and comparing it with `OpenSSL.secure_compare`: [3](#0-2) 

After that check passes, `Registry.process` forwards the caller-supplied `request.shop` value, unverified, directly to the app's handler as the tenant identity: [4](#0-3) 

The equality this breaks: `shop asserted by the "shopify-shop-domain" header == shop that actually produced/authenticated the signed bytes`. The HMAC only proves "this body was signed with the app's secret at some point by some shop that installs this app"; it proves nothing about which shop. Since `api_secret_key` is the same for every shop instance of a given app, an attacker who operates (or compromises) their own shop installation can capture one legitimately-signed webhook delivery (body + `x-shopify-hmac-sha256`) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. The HMAC check still passes because it never covered the header, and the handler receives `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This crosses a tenant boundary using only a shared per-app secret, not a per-shop secret: an attacker who runs their own app installation (unprivileged relative to the victim shop) can make the host application process a webhook it believes originates from a completely different, victim shop, with attacker-controlled body content that was validly signed for the attacker's own shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up the victim's stored session/access token to react to the "event", writing data associated with the victim tenant, or triggering business logic scoped to the victim's shop), this enables cross-tenant data manipulation. This matches the "cross-tenant access" criteria for a Critical/High-severity impact class.

### Likelihood Explanation
Any developer/merchant with a store that installs the app can trivially capture one webhook delivery (their own request body + its valid HMAC, since they receive their own webhooks) and replay it against the app's public webhook endpoint with a modified `shop-domain` header — no access token, `api_secret_key`, or privileged account is required. The only requirement is that the app process at least one webhook topic whose body the attacker can influence or whose replay has tenant-scoped side effects.

### Recommendation
Do not trust the `shop`/`shop-domain` header as an authenticated value. Either include the shop domain in the signed payload/comparison used for verification, or independently corroborate the header value against the shop that is the subject of the specific installed webhook subscription (e.g., match against the webhook id's known registered shop) before passing it to handlers as a trusted tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook subscription (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with body `B` and a valid `x-shopify-hmac-sha256` computed with the app's `api_secret_key` (shared across shops), plus header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` using only the raw body (`request.rb` `to_signable_string`), which is unchanged and still matches — validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...))` is invoked; the host application processes attacker-controlled webhook content as if it came from `victim.myshopify.com`.
