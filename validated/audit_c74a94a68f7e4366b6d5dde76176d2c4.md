### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) header is trusted for tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values used as the tenant/dispatch identity are taken from HTTP headers that are never part of the signed bytes. This breaks the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string`: [2](#0-1) 

But `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id` are all sourced from HTTP headers, not from the signed body: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body bytes) and then unconditionally trusts `request.shop`/`request.topic` to build the `WebhookMetadata` that is handed to the app's registered handler as the identity of the webhook sender: [4](#0-3) 

Because the signature check verifies the request body but the code acts on the `shop-domain` header, an attacker who possesses any one validly-signed webhook body/HMAC pair (e.g. one delivered to their own shop, which they fully control and can read) can replay it while substituting a different `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true`, since it only recomputes the HMAC over the untouched raw body, and `Registry.process` will dispatch to the app's handler with `WebhookMetadata.shop` set to the attacker-chosen shop domain and the attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the app's webhook handler receives data whose "sender shop" attribute is fully attacker-controlled while the payload's authenticity (HMAC) says nothing about which shop it came from. Any host application logic that uses `WebhookMetadata#shop` to look up a merchant session, write to shop-scoped storage, or make authorization decisions can be tricked into associating attacker-supplied webhook content with an arbitrary victim shop, i.e., cross-tenant access/data injection across shop boundaries.

### Likelihood Explanation
The attacker only needs to control (or observe) one legitimately signed webhook for any shop (including one they install the app on themselves) and be able to send HTTP requests to the app's webhook endpoint with modified headers — no `api_secret_key`, access token, or other privileged credential is required. This is easily reachable by any unprivileged internet user/merchant who can install the target app.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the payload (as Shopify's own webhook signing already binds body content to the secret; the gem should not additionally trust unauthenticated headers for tenant identity). At minimum, `Registry.process`/`HmacValidator` should not let handlers key off of `request.shop` unless that value is itself covered by the verified signature.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery with body `B` and valid header `x-shopify-hmac-sha256: H` (H is HMAC(secret, B)).
2. Attacker replays the same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) and matches `H` → validation succeeds.
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
