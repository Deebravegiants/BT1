### Title
Webhook `shop` tenant identity is trusted from an unauthenticated header while the HMAC only binds to the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Finding Description
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) that is handed to the app's webhook handler directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header: [1](#0-0) 

However, the HMAC signature that `HmacValidator.validate` checks is computed only over the raw request body, never the shop header: [2](#0-1) 

`HmacValidator` confirms only that `to_signable_string` (i.e. `@raw_body`) was signed by the app's shared `client_secret`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, and then trusts `request.shop` (from the unsigned header) as the tenant for the handler call: [4](#0-3) 

Because the HMAC key (`Context.api_secret_key`, the app's single `client_secret`) is identical across every shop that installs the app, any valid `(raw_body, hmac)` pair produced for one tenant remains cryptographically valid for a request that swaps in a different `shop-domain` header while reusing the same body. The equality the code should enforce is:

`hmac == HMAC(secret, raw_body ++ shop)` (or equivalent binding of `shop` into the signed material)

but what is actually enforced is only:

`hmac == HMAC(secret, raw_body)`, with `shop` accepted unauthenticated.

### Impact Explanation
A merchant who has installed the app on their own store (an "unprivileged" tenant relative to other merchants) legitimately receives real webhooks with valid HMACs computed using the app's shared secret. By capturing such a webhook body and replaying it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, the attacker produces a request that passes `HmacValidator.validate` (body/HMAC pair untouched) while `WebhookMetadata.shop` now falsely claims to be the victim tenant. Any handler logic that keys off `data.shop` to select/update per-tenant records, sessions, or state can be tricked into acting on/for the wrong tenant — a cross-tenant data confusion/injection primitive that maps to the report's flagged impact category (Critical - cross-tenant access), since the tenant boundary the app relies on is not actually cryptographically enforced by this gem.

### Likelihood Explanation
Exploitation requires only: (1) being a legitimate app installer on at least one shop (no special privilege, any merchant can install a public app), and (2) capturing one webhook delivery to replay with an altered header. No access to `api_secret_key` or any victim credentials is needed, satisfying the "unprivileged internet user" analog criteria. The main constraint is that the replayed body's content must be plausible/useful for the target handler logic (e.g., generic-shaped payloads or replay of the attacker's own data against a shop-keyed handler), which is feasible for many webhook topics.

### Recommendation
Bind the tenant identity into the material that is actually verified: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in `to_signable_string`, or otherwise cryptographically bind the header set to the HMAC before trusting `request.shop` in `Registry.process` / `WebhookMetadata`. Alternatively, require host applications to independently verify that `request.shop` corresponds to a shop with a currently valid, stored session for that specific webhook body/id before acting on it, rather than trusting the header value outright once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook (e.g. `orders/create`) with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`.
2. Attacker resends the exact same raw body `B` and the exact same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` calls `compute_signature(verifiable_query.to_signable_string, secret)`, which only hashes `@raw_body` — identical to step 1 — so `OpenSSL.secure_compare` succeeds.
4. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop. [5](#0-4)
