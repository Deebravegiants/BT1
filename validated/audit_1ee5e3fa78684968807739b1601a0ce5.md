### Title
`shop` and `topic` identity fields on incoming webhooks are not covered by the HMAC signature, allowing header spoofing to misattribute webhook payloads to a different tenant - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate an inbound webhook by validating only the HMAC over the raw request body, then trust the `shop-domain` (and `topic`) HTTP headers verbatim to identify which tenant the payload belongs to. Because those identity headers are never included in the HMAC-signed content, the binding "HMAC-verified sender == the shop the payload is attributed to" does not actually hold.

### Finding Description
`Utils::VerifiableQuery#to_signable_string`, as implemented by `Webhooks::Request`, returns only `@raw_body`: [1](#0-0) 

The HMAC is computed and verified purely over that raw body string: [2](#0-1) 

`Request#shop`, `Request#topic`, `Request#webhook_id`, and `Request#api_version` are all read directly from HTTP headers, which are not part of the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` and `request.topic` taken straight from those unauthenticated headers: [4](#0-3) 

Root cause as an equality that should hold but doesn't: "the shop that produced the HMAC-valid body" == "the shop attributed by `WebhookMetadata#shop`". The gem only proves the former's *body* was untampered by Shopify; it never binds the `shop-domain`/`topic` header values to that signature. Any party capable of sending an HTTP request to the app's webhook endpoint — including a merchant who has legitimately installed the app and thus can observe genuine `(raw_body, hmac)` pairs sent to their own endpoint, or anyone who intercepts/replays such a pair — can attach an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) header while keeping the same valid body+hmac, and the gem will still report `Errors::InvalidWebhookError` as not raised and hand the handler a `WebhookMetadata` claiming the payload is for a different shop/topic than the one that actually produced it.

### Impact Explanation
This breaks the shop-identity binding for webhook processing inside the gem itself (not a host-app misuse of the API): `Registry.process` is the gem's own dispatch entry point and it never validates `shop`/`topic` against anything cryptographically bound to the request. Any downstream application that relies on `WebhookMetadata#shop`/`#topic` (the values the gem itself exposes as the "authenticated" identity of the webhook) to select the tenant record, apply the payload, or route mandatory-webhook redaction data (`shop/redact`, `customers/redact`, `customers/data_request`) can be made to associate attacker-supplied `shop`/`topic` labels with a body whose HMAC only proves the *body*, not those labels — a cross-tenant data misattribution scenario. This matches the High-severity "scope or expiry check bypass"/binding-break category, since the affected field (shop identity) governs which tenant's data a webhook is trusted to belong to.

### Likelihood Explanation
Exploitation requires obtaining at least one legitimately Shopify-signed `(raw_body, hmac)` pair — which any merchant with the app installed will routinely receive for their own shop, since webhook signatures never rotate with header content. No access token, `client_secret`, or TLS interception is needed; only the ability to POST to the app's public webhook endpoint with modified headers and the previously-observed valid body/hmac pair. This is realistically reachable by any unprivileged party that can see one webhook delivery.

### Recommendation
Include the shop domain (and ideally topic) in the value that is HMAC-verified, or independently authenticate `request.shop` against session/tenant state (e.g., verify the shop is a known, currently-installed shop with a stored access token, and reject if the topic in the header does not match a topic-specific check) before dispatch in `Registry.process`. At minimum, document/require that consuming apps not trust `WebhookMetadata#shop`/`#topic` without separate verification, or bind these fields cryptographically the way `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signable string.

### Proof of Concept
1. App has installed webhooks; attacker owns/operates Shop A with the app installed and thus can observe one legitimate delivery: headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid-for-body>`, body `{"secret_customer_data":"..."}`.
2. Attacker resends the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `shop-b.myshopify.com` (a victim shop) and/or `x-shopify-topic` to a different registered topic.
3. `Utils::HmacValidator.validate` in `HmacValidator#validate_signature` only recomputes the signature over `@raw_body`, which is unchanged, so validation succeeds: [5](#0-4) 
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` using the attacker-controlled `shop`/`topic` values: [6](#0-5) 
5. Any app logic that trusts `data.shop`/`data.topic` from this callback to select which tenant's records to update now applies Shop A's payload to Shop B's tenant context, or misroutes a `customers/redact` payload to the wrong shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
