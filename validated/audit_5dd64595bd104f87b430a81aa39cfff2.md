### Title
Webhook shop domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `X-Shopify-Shop-Domain` header, yet `ShopifyAPI::Webhooks::Registry.process` trusts that same unauthenticated header to identify the tenant the webhook belongs to when invoking the app's handler.

### Finding Description
The HMAC validation for webhooks is performed by `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile, the `shop` accessor used to identify which tenant the webhook is "from" is read straight from the `shopify-shop-domain` HTTP header, which is never included in the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, and — with no cross-check that the `shop` header matches the shop the body's HMAC was actually issued for — hands the header-derived shop straight to the app's handler via `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is: `hmac_covers(shop_used_by_handler) == true`. In reality: `hmac_covers(raw_body) == true` but `shop` (the field the handler acts on to select/scope tenant data) is not part of the signed material, i.e. `hmac_covers(shop) == false`. Because the webhook secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret), any entity that can install the app on a store it controls — an ordinary, unprivileged action available to any internet user for public apps — will receive genuine, validly-signed `(raw_body, hmac)` pairs from Shopify for its own shop. That attacker can then replay the exact same body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` will still succeed, because the header is not part of the signed string, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to guarantee: an app author normally relies on `ShopifyAPI::Webhooks::Registry.process`/`Request#shop` to know unambiguously which merchant's data a webhook payload pertains to, since the library only exposes an HMAC-validated `Request` object to the handler and documents it as verified. Since the `shop` field is not authenticated, an attacker with access to only their own (attacker-controlled) shop's webhooks can forge webhooks that are processed as if they belong to a different, victim shop, resulting in cross-tenant data confusion/injection (e.g. attacker-controlled order/product/customer payloads or mandatory GDPR `customers/redact`, `shop/redact`, `customers/data_request` topics being applied against a victim shop record) purely through this gem's own `Registry.process`/`Request` verification logic.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on any shop they control (a normal, unprivileged path for any public Shopify app) to obtain a validly-HMAC-signed webhook body, then replay that request to the app's registered webhook endpoint with a modified shop-domain header. No access to `api_secret_key`, access tokens, or the victim's credentials is required, and the vulnerable code path (`HmacValidator.validate` + `Registry.process` + `Request#shop`/`#to_signable_string`) is entirely within this gem's in-scope library code.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material used for `to_signable_string`, or otherwise cryptographically bind the `shop` header to the payload before trusting it (e.g., require callers to independently confirm the shop is a known, currently-installed tenant before dispatching to handlers), so that `HmacValidator.validate` fails whenever the shop header has been tampered with relative to the originally-issued webhook.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action for public apps) and lets a webhook (e.g. `orders/create`) fire to the app's endpoint, capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header — both are valid because they're signed with the app-wide `api_secret_key`, not a per-shop secret.
2. Attacker resends this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. On the server, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged header, and `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — passing successfully — because `to_signable_string` never includes the `shop-domain` header. The app's handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing it to process attacker-controlled webhook data as if it originated from the victim shop.
