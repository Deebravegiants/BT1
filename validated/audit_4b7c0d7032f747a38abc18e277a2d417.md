### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` identity used downstream to process the webhook is taken from an HTTP header that is never included in that signed content. Any actor able to obtain one genuinely-signed webhook (e.g., a merchant on their own, attacker-controlled shop using the app) can replay that valid HMAC with the `shop-domain` header rewritten to a victim shop, and `Webhooks::Registry.process` will accept it and pass the forged shop identity to the app's handler.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read from the `shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the body) and a single, app-wide `Context.api_secret_key`, and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` validates only that HMAC, then immediately trusts `request.shop` as the tenant identity delivered to the handler, with no additional binding check between the verified bytes (body) and the unverified header (shop): [4](#0-3) 

The broken identity equality is:
`HMAC-verified(body, secret) == valid` should imply `shop-header == shop-that-produced-that-body`, but the gem never enforces this — the `shop-domain` header is fully decoupled from the cryptographic check.

Because `Context.api_secret_key` (the app's `client_secret`) is shared across every shop that installs the app, any merchant who installs the app on their own store can trigger a webhook with attacker-influenced body content (e.g., editing an order note before an `orders/updated` webhook fires) and thereby obtain a body + valid HMAC pair signed with the app-wide secret. That attacker can then send this raw body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as the source: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity confusion: a low-privilege, self-installed merchant can make the host application believe arbitrary attacker-chosen webhook content originated from a different, victim merchant's shop. Any application logic that keys off `WebhookMetadata#shop` (e.g., updating per-shop records, deprovisioning, billing state, or triggering emails/actions scoped to "the shop that the webhook says it's from") can be manipulated cross-tenant without ever compromising the victim's credentials, satisfying the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-controlled or trial shop (a normal, unprivileged action), (2) triggering any webhook topic whose body includes attacker-controllable content, and (3) replaying that HTTP POST to the app's public webhook endpoint with a modified shop header — no secrets, tokens, or elevated privileges are needed. This is straightforward for anyone who can install the app.

### Recommendation
Bind the shop identity into the verified content instead of trusting an unauthenticated header:
- Include the shop-domain header (and ideally topic/webhook-id) in the HMAC-signable string used by `Request#to_signable_string`, or
- If Shopify's webhook HMAC spec truly only covers the body (as it currently does upstream), the gem should not expose `request.shop` as trusted tenant identity without documenting this loudly, and/or should require callers to cross-check the shop header against a known/expected shop for the topic before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`.
2. Trigger a webhook topic whose payload contains attacker-influenced text (e.g., set an order note to arbitrary JSON-safe content, then let `orders/updated` fire). Capture the raw POST body and its legitimate `X-Shopify-Hmac-Sha256` header — both signed with the app's single `client_secret`.
3. Replay this exact body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the secret. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though the payload never touched `victim.myshopify.com`.
