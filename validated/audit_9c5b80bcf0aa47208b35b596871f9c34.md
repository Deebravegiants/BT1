### Title
Native-to-fee-token swap in `EvmHost.dispatch`/`fundRequest` lacks slippage protection, exposing dispatchers to sandwich-attack value extraction - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` each perform an on-chain, exact-output UniswapV2 swap (`swapETHForExactTokens`) to convert a caller's native token payment into `feeToken` for message dispatch, with no minimum-output/maximum-slippage bound beyond the caller's own `msg.value` and a deadline of `block.timestamp` (i.e., no real time-bound protection). This mirrors the reported class of bug: an unprotected AMM swap executed on behalf of a user/victim inside a single, MEV-sandwichable transaction.

The same unprotected pattern is duplicated in `IntentGatewayV2.placeOrder` and its Tron fork for fee-token acquisition: [4](#0-3) [5](#0-4) 

In all of these, `amountInMaximum` is set to the caller's entire `msg.value`, and `deadline` is `block.timestamp` (a no-op deadline, since it always passes in the same block). There is no oracle-derived or otherwise off-chain-informed minimum acceptable price, unlike the analogous pattern correctly implemented in `SimplexPaymaster.swapAndDeposit`, which derives `amountOutMin` from Chainlink oracle prices minus a slippage tolerance before calling the router: [6](#0-5) 

Because `dispatch()` is the core, permissionless entry point any application or user calls to send a cross-chain message and pay in native token, an attacker can:
1. Observe a pending `dispatch()`/`fundRequest()`/`placeOrder()` transaction that pays with native token (mempool visibility).
2. Front-run it with a trade that skews the WETH→feeToken UniswapV2 pool reserves.
3. Let the victim's `swapETHForExactTokens` execute at the manipulated price, consuming close to the caller's full `msg.value` to acquire the fixed `post.fee`/`get.fee`/`order.fees` amount of `feeToken` (since `amountInMaximum == msg.value` is the only bound).
4. Back-run with a reverse trade to restore the pool and capture the value that would otherwise have been the caller's unspent ETH/refund.

This is functionally the same root cause as the reported `Voting.sol` bug: an exact-output/exact-input swap with no independent slippage bound, executed automatically inside a contract on behalf of a third party, whose execution price is entirely controllable by an attacker within the same block.

### Impact Explanation
Any unprivileged caller dispatching a cross-chain POST/GET request, funding a pending request, or placing a cross-chain intent order while paying fees in native token is exposed to value extraction via sandwich attack — the attacker can force the swap to consume near-maximal ETH from the caller's `msg.value`, capturing the difference as arbitrage profit. In `EvmHost.dispatch`/`fundRequest` specifically, unlike `IntentGatewayV2.placeOrder` (which explicitly forwards any unspent `msgValue` back to `msg.sender` after the swap), there is no subsequent handling of excess ETH the router refunds to the `EvmHost` contract itself, meaning the "spent" amount (post-sandwich) is directly borne by the caller with no path to recovery. This is a concrete loss of user funds on the core dispatch path used throughout the protocol (message dispatch is the base primitive for every Hyperbridge application).

### Likelihood Explanation
Likelihood is high wherever the WETH/feeToken UniswapV2 pool has thin liquidity relative to the swap size, since MEV searchers routinely monitor mempools for AMM swaps lacking slippage protection. Every call to `dispatch()`/`fundRequest()` that pays with native token is a candidate target, and no special privilege or race condition beyond normal mempool visibility is required to execute the attack.

### Recommendation
Introduce an explicit, caller-supplied (or oracle-derived) minimum-acceptable-price / maximum-slippage parameter for these swaps rather than relying on the raw `msg.value` as `amountInMaximum`, and use a genuine future deadline rather than `block.timestamp`. Where excess native token remains after the swap, explicitly refund it to the original payer (as `IntentGatewayV2.placeOrder` already does), and consider routing native-fee payments through a wrapper (such as `SimplexPaymaster`'s oracle-bounded swap pattern) that bounds execution price independently of the user-supplied value.

### Proof of Concept
1. Attacker monitors mempool for a `dispatch(DispatchPost)` call with `msg.value > 0` (or `fundRequest`/`placeOrder` equivalents).
2. Attacker front-runs with a large WETH→feeToken (or feeToken→WETH) trade on the configured UniswapV2 pool referenced by `_hostParams.uniswapV2`, skewing the price against the victim's `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` call.
3. The router executes at the worse price, consuming ETH up to (but bounded only by) `msg.value` to still deliver exactly `post.fee` in `feeToken`.
4. Attacker back-runs to reverse the price skew and realize profit, while the victim's transaction succeeds (assuming their `msg.value` was large enough to cover the manipulated price) but at a materially worse rate than fair market price, with any residual ETH left stranded in the `EvmHost` contract instead of returned to the caller.
