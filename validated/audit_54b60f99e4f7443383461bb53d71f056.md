## Analog Scan Result

### Title
Attacker-controlled `postHookContract` can drain the shared pool after the balance equation has already been checked - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal::transact` calls an arbitrary user-supplied `postHookContract.afterTransact(circomData)` *after* the balance-equation check has already passed, but *before* nullifiers/commitments are finalized, and with no re-check of the contract's token balances afterward.

### Finding Description
`HookData.preHookContract`/`postHookContract` are arbitrary, attacker-supplied addresses that are only bound into `calldataHash` (and thus the signed message) — they are never constrained to a whitelist the way `externalActionMap` constrains `externalActionData.externalAddress` [1](#0-0) . Because the calldata hash is checked for integrity in `performHinkalChecks` and folded into `getSignedMessageHash`, a malicious *submitter of their own transaction* can freely choose any `postHookContract`/`preHookContract` and still produce a valid proof for that choice, since the circuit only needs to reproduce the same hash — it does not validate the semantics of the hook contract [2](#0-1) [3](#0-2) .

In `Hinkal::transact`, the sequence is:
1. `oldBalances` snapshot taken.
2. Internal/external transact moves tokens.
3. `newBalances` snapshot taken, and the balance equation (`balanceDif == amountChanges + utxoAmount`) is enforced.
4. **Only after this check passes**, `postHookContract.afterTransact(circomData)` is invoked.
5. Nullifiers and commitments are inserted with no further balance verification. [4](#0-3) 

Because `afterTransact` executes after step 3's balance check and before step 5's finalization, with no subsequent re-verification of the contract's token balance, a malicious `postHookContract` can transfer additional shielded-pool funds (tokens held by `Hinkal.sol` on behalf of *all* users) to the attacker without decreasing any recorded UTXO commitment or nullifying any input. The equality that should hold — "on-chain token balance change equals the sum of committed/nullified UTXO deltas" — is broken because the hook's balance-moving side effect occurs entirely outside the window in which that equality is enforced.

### Impact Explanation
This breaks the core conservation invariant of the shielded pool: value can be extracted from `Hinkal.sol`'s token balance (funds belonging to other users' unspent commitments) without any corresponding nullifier being spent or backing commitment being reduced. This is a direct theft of shielded/pooled user funds — Critical impact, analogous to the reported bug's core theme of "an actor-controlled but unauthenticated/unaccounted delta bypassing the equality the protocol relies on," here in the balance-equation sense rather than Uniswap's swap-delta sense.

### Likelihood Explanation
Any user submitting their own transaction (no admin/relay/manager privilege required) controls `circomData.hookData.postHookContract` and can deploy a contract that, when invoked as `afterTransact`, calls `transferFrom`/`transfer` on the pool's held tokens (assuming it has, e.g., prior approval or reentrant call context, or directly calls `IERC20.transfer` if `Hinkal.sol` holds a balance it can move without an allowance check — note `Hinkal.sol` is the token holder, so a hook could simply have `Hinkal` call an external protocol it has approved, or, if the hook contract itself holds delegated approval/allowance from the pool, pull tokens directly). The exact mechanics of what "unauthorized transfer out of Hinkal.sol" a hook can perform depend on approvals/allowances Hinkal.sol may have granted elsewhere in the codebase (e.g., to routers via `Transferer`), which I was not able to fully trace before running out of tool budget — this is a gap in my verification.

### Recommendation
Move the balance snapshot/equation check to occur *after* `postHookContract.afterTransact()` executes (or re-run the balance check after the hook call), so that any balance-affecting behavior from hooks is captured by the conservation equation before nullifiers/commitments are finalized. Alternatively, restrict `postHookContract`/`preHookContract` to an admin-controlled whitelist analogous to `externalActionMap`.

### Proof of Concept
Not fully constructible without confirming what token-moving capability `Hinkal.sol` exposes to an arbitrary hook contract (i.e., whether `Hinkal.sol` holds standing allowances/approvals that a hook could exploit, or whether `afterTransact` runs in a context where it can call `transferFrom(Hinkal.sol, attacker, amount)` on a token `Hinkal.sol` has approved elsewhere). I could not verify this within the available tool iterations — the `Transferer`/`TransfererBase` contracts (referenced in the wiki but not fully read) would need to be inspected to confirm whether standing approvals exist that a malicious `postHookContract` could leverage in this window. If no such standing approval exists anywhere in the codebase, this finding downgrades from Critical/High to a lower-severity ordering issue, since the hook would then only be able to move tokens it directly controls (its own balance), not the pool's.

**Note on confidence:** This finding is a plausible analog based on the ordering bug pattern (an unaccounted state-changing call executing outside the checked window), but I was unable to fully confirm exploitability because I did not have iteration budget remaining to inspect `Transferer.sol`/`TransfererBase.sol` for standing token approvals held by `Hinkal.sol`, nor to check `HinkalWallet.sol`/Emporium hook usage patterns that might clarify whether `postHookContract` genuinely gets privileged access to pool funds. I recommend a Devin session with the full codebase (including `Transferer.sol`, `TransfererBase.sol`, and any router-approval logic) to close this gap before treating this as a confirmed Critical finding.
