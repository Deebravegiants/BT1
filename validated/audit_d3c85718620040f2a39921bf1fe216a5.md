### Title
Webhook `shop-domain` header is trusted by the SDK without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` value taken directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that the SDK validates via `HmacValidator.validate` is computed only over the raw request body. `Registry.process` treats a successful HMAC check as proof the whole request (including the shop identity) is authentic, and forwards the unauthenticated `shop` value straight to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `Request#shop` is read straight from an HTTP header that is not part of that signable string: [2](#0-1) 

`Registry.process` calls `Utils::HmacValidator.validate(request)`, and once it passes, immediately constructs `WebhookMetadata` using `request.shop` and hands it to the app-registered handler with no further binding check between the signed body and the shop header: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field - it never incorporates the shop header: [4](#0-3) 

The identity-binding equality that should hold is:
`HMAC_valid(body, hmac) == true` should imply `shop == the tenant that produced this exact (body, hmac) pair`.

In this implementation, `HMAC_valid(body, hmac) == true` says nothing about `shop`, because `shop` is never an input to the signature. Since the app's `api_secret_key` is shared across every merchant that has the app installed, any two shops that use the same app share the same HMAC key. Consequently, a merchant who legitimately receives real webhook deliveries for their own store (and therefore possesses valid `(body, hmac)` pairs signed with the shared app secret) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a different, victim shop domain. `Registry.process` will validate the HMAC successfully (since it only checks the body) and will pass `shop: <victim-shop>` to the handler, even though the body/HMAC pair was never actually associated with that shop.

### Impact Explanation
This breaks the tenant-authentication boundary the SDK is supposed to provide to hosting applications: the `shop` field delivered to the app's webhook handler is presented as validated (because `HmacValidator.validate` succeeded) but is in fact attacker-controlled. Any application that uses `WebhookMetadata#shop` to select which merchant's data/session/access-token to operate on (the documented and expected usage pattern) can be made to act on behalf of, or write data into, a different tenant than the one that actually sent the request - i.e., cross-tenant access, which is explicitly listed as a Critical-severity impact category (cross-tenant access via a scope/binding check that answers permissively).

### Likelihood Explanation
The attacker only needs: (1) their own store to have the target app installed so they receive genuine webhook deliveries for their own shop (no privileged credentials, access tokens, or `client_secret` needed - this is available to any unprivileged merchant/user of the app), and (2) the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header, which any internet user can do. No cryptographic secret needs to be obtained or brute-forced since the same signed body/HMAC pair the merchant already legitimately possesses is reused unchanged. The gem itself provides no defense against this because the shop identity is structurally outside the HMAC's scope.

### Recommendation
Bind the shop identity into the signature check that `Registry.process` performs, e.g., by requiring the caller to supply the expected/authenticated shop domain (from the session/tenant context the request was routed to) and comparing it against `request.shop`, or by having `HmacValidator`/`Request#to_signable_string` incorporate the `shop-domain` header into the signed payload comparison so a body/HMAC pair from shop A cannot be replayed with shop B's domain.

### Proof of Concept
1. App `X` is installed on both `shop-a.myshopify.com` (attacker-controlled) and `shop-b.myshopify.com` (victim), sharing one `api_secret_key`.
2. Shopify sends a legitimate webhook to shop A's endpoint: headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, body `B`.
3. Attacker (who controls shop A's server/infra receiving that webhook) captures `(B, hmac)`.
4. Attacker POSTs the same `body: B` and `x-shopify-hmac-sha256: hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `body` against `hmac` using `Request#to_signable_string` (`@raw_body` only) - this passes.
6. `WebhookMetadata` is built with `shop: "shop-b.myshopify.com"` and delivered to the app's handler as if it were an authentic webhook for shop B, even though the request never touched Shopify's systems for shop B. [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
