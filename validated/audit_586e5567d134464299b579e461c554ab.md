### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook signature verification in this gem authenticates only the raw HTTP body, not the `shop-domain` header used to attribute the webhook to a specific merchant. This breaks the equality: `shop authenticated by HMAC` ≠ `shop the registry hands to the application handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `#shop` is read straight from the untrusted `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` only: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once this body-only HMAC check passes, then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata` handed to the app's handler: [4](#0-3) 

This is in sharp contrast to the OAuth `AuthQuery` verifiable query, where `shop` (and `host`) are explicitly included in `to_signable_string` and thus bound by the HMAC: [5](#0-4) 

Because the webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that installs the app, any tenant that legitimately receives a webhook for its own store (a valid `body` + valid `hmac`) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature still validates (it never covered the header), so the registry dispatches the attacker-chosen body to the handler *labeled as coming from a different, victim shop*.

### Impact Explanation
This crosses a tenant boundary: an attacker who controls one installation of the app can inject webhook events that the app attributes to another merchant's shop, corrupting per-shop state, triggering shop-scoped side effects (e.g., data writes, notifications, order/inventory changes) under a victim's identity. This matches the Critical "cross-tenant access" impact category, since the identity binding (shop) that the app relies on for tenant isolation is not authenticated.

### Likelihood Explanation
Exploitation requires only an unprivileged account that can install the app on an attacker-controlled development/trial store to obtain a valid `(body, hmac)` pair signed with the shared `client_secret`, and the ability to POST directly to the app's public webhook endpoint with a forged `shop-domain` header — both are within reach of any internet user who can install the app, no leaked secrets or privileged access required.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is cryptographically verified, or otherwise bind the verified body to the specific shop before dispatch — e.g., extend `VerifiableQuery`/`to_signable_string` for webhooks to incorporate the `shop-domain` header (mirroring what `AuthQuery` already does for `shop`/`host`), and reject/re-validate if the header used for dispatch differs from any shop encoded in the verified payload. At minimum, document that consumers must independently verify `request.shop` against their own known/registered shop list before trusting it, since the gem's HMAC check does not cover it.

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com`, obtaining the app's real `client_secret`-signed webhook for a triggered event: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(client_secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same `raw_body = B` and the same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers without validating `shop` against the signature: [6](#0-5)  .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC over `B` (see `to_signable_string`), then invokes the handler with `shop: "victim.myshopify.com"` and attacker-controlled body content: [4](#0-3) .
5. The application's webhook handler processes attacker-supplied data as if it originated from `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
