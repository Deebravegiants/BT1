### Title
Session identity is resolved from an unauthenticated, predictable cookie value with no cryptographic binding - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` is the gem's documented mechanism for a host application to determine which stored session to load for a request. For the non-embedded flow (and as a fallback for embedded apps without an id token), it derives the session id **directly from the raw browser cookie value**, with no signature, HMAC, or any cryptographic check binding that value to the shop or user it claims to represent — unlike every other identity-bearing artifact in this gem (`AuthQuery`, `JwtPayload`, webhook `Request`), which are all HMAC/JWT-signature verified before their claims are trusted.

### Finding Description
`current_session_id` (`lib/shopify_api/utils/session_utils.rb:19-37`) branches on whether the app is embedded and whether a `shopify_id_token` is present:

- If an id token is present, `session_id_from_shopify_id_token` is used, which decodes and cryptographically verifies a JWT (`Auth::JwtPayload.new`) before deriving the id — this path is safe.
- Otherwise (non-embedded apps, or embedded apps without an id token), it falls back to `cookie_session_id`:

```ruby
sig { params(cookies: T::Hash[String, String]).returns(T.nilable(String)) }
def cookie_session_id(cookies)
  cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]
end
``` [1](#0-0) 

This method returns the raw `shopify_app_session` cookie value **verbatim**, with zero verification that the value was actually issued by this gem's OAuth flow. The `SessionCookie` struct that produces this value has no signature or MAC field at all:

```ruby
class SessionCookie < T::Struct
  const :name, String, default: SESSION_COOKIE_NAME
  const :value, String
  const :expires, T.nilable(Time)
``` [2](#0-1) 

Critically, the session id values the gem itself generates and stores in this cookie are **deterministic and guessable from public information**:

```ruby
def jwt_session_id(shop, user_id)
  "#{shop}_#{user_id}"
end

def offline_session_id(shop)
  "offline_#{shop}"
end
``` [3](#0-2) 

and for the non-embedded auth-code-grant flow, the cookie is populated with exactly this id:

```ruby
cookie = SessionCookie.new(value: session.id, expires: session.expires ? session.expires : nil)
``` [4](#0-3) 

The identity binding that should hold is:
`session_id (trusted by SessionRepository.retrieve)` == `session_id cryptographically proven to belong to the requesting browser's authenticated session`

What the code actually checks is:
`session_id (trusted by SessionRepository.retrieve)` == `raw bytes of a cookie the client presented`

Because a shop's `myshopify.com` domain is public and offline session ids are simply `"offline_{shop}"`, an attacker who controls any means of writing an arbitrary cookie value for the app's origin (e.g. a cookie-injection bug in the host framework, a shared parent-domain cookie, response-splitting, or simply because the docs' example (`docs/usage/oauth.md`) stores the cookie as a plain, non-`httponly`-enforced-by-the-gem browser value with no server-side integrity check) can set `shopify_app_session=offline_victim-shop.myshopify.com` and have `SessionUtils.current_session_id` return that exact string. If the host app's `SessionRepository.retrieve(id)` (the pattern this gem's own docs recommend, e.g. `MyApp::SessionRepository.retrieve_session_for_shop`) simply looks up a stored session by that id, as shown in the gem's own documented usage pattern (`docs/usage/oauth.md:441-448`), the attacker is served another tenant's stored `access_token`.

This is the same class of bug as the audited report: a downstream trust decision (which principal a request acts as) is made using a field/byte-string that was never bound to an authenticated proof (HMAC/JWT signature), only "the caller and the intended target are treated the same," analogous to `accrueRewards` being called on `caller`/`receiver` but never on the actually-affected `owner`.

### Impact Explanation
This qualifies as **Critical — cross-tenant access / theft of a merchant access token**, since the resolved session id is used by the host app to look up and use another shop's stored offline (or online) access token, per the gem's own documented session-retrieval pattern. No credential, TLS interception, or privileged access is required — only the ability to influence one cookie value and knowledge of a target shop's public `.myshopify.com` domain.

### Likelihood Explanation
Moderate-to-high: exploitability depends on the host application's cookie-writing surface (the gem does not sign/encrypt the cookie itself, so the trust boundary is delegated to a plain HTTP cookie). Given that the gem explicitly ships this as the documented, first-class API (`SessionUtils.current_session_id`, referenced in `docs/getting_started.md`) for retrieving the active session, and offline session ids are 100% predictable (`"offline_#{shop}"`), any host that stores this cookie as an ordinary (non-cryptographically-bound) value inherits the vulnerability by following the gem's own documented pattern — this is not "the host app ignoring the API," it's the API's documented contract lacking an integrity binding.

### Recommendation
`SessionCookie`/`cookie_session_id` should not be trusted as a bare identity claim. Options: (1) HMAC-sign the cookie value with `Context.api_secret_key` and verify the signature in `cookie_session_id` before returning the id (mirroring `HmacValidator`/`JwtPayload`), or (2) deprecate the raw-cookie fallback path entirely in favor of only the JWT-verified path, consistent with Shopify's recommendation to use token exchange/session tokens instead of unsigned session cookies.

### Proof of Concept
1. Attacker learns (or brute-forces) a victim's shop domain, e.g. `victim-shop.myshopify.com` (public, discoverable).
2. Attacker sets/injects a browser cookie for the target app's origin: `shopify_app_session=offline_victim-shop.myshopify.com`.
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged, since `cookie_session_id` performs no verification:
```ruby
def cookie_session_id(cookies)
  cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]
end
``` [1](#0-0) 
4. Host app (per the gem's documented pattern) retrieves the stored session/access token for that id and uses it to make Admin API calls on behalf of `victim-shop`, exfiltrating the victim's data/access token.
