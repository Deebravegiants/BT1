### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant/topic dispatch despite being excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch and attribute the webhook are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands these header-derived, unverified values straight to the app's `WebhookHandler#handle`, breaking the binding "HMAC-verified bytes == bytes acted upon."

### Finding Description
`Utils::HmacValidator.validate` computes the signature from `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`, and the `hmac` accessor reads the `hmac-sha256` header — but `shop`, `topic`, `webhook_id`, and `api_version` are pulled from separate, unauthenticated headers that are never part of the signed material: [2](#0-1) 

`Registry.process` validates only the body HMAC, then dispatches using `request.topic` for handler lookup and constructs `WebhookMetadata` directly from these unauthenticated header values, including `shop: request.shop`: [3](#0-2) 

The identity binding that should hold is: **shop attribution used by the handler == shop cryptographically bound to the signed payload**. Because the HMAC secret (`api_secret_key`) is shared across every shop that has installed the same app, any unprivileged user who legitimately installs the app on their own store can obtain a genuinely valid `(raw_body, hmac)` pair from their own webhook deliveries. That exact `(body, hmac)` pair remains valid under `HmacValidator.validate` regardless of what `shop-domain`, `topic`, or `webhook-id` headers accompany it, since those fields are never covered by the signature. The attacker can therefore replay that valid body+HMAC to the app's public webhook endpoint with `shopify-shop-domain` swapped to a victim shop, and/or `shopify-topic`/`shopify-webhook-id` swapped to route the payload to a different handler than the one Shopify actually intended.

### Impact Explanation
This breaks the shop/tenant identity binding at the point where the library hands verified data to app code: the app's `WebhookHandler#handle` receives a `WebhookMetadata#shop` value that has no cryptographic tie to the HMAC-approved body. Any app that uses `data.shop` to decide which tenant's records to update, or that relies on `topic` to select business logic without independently re-checking the shop against its own installed-shop list, can be made to attribute (and act on) a legitimately signed payload as if it came from an arbitrary victim shop domain — a cross-tenant data/action confusion that only requires the attacker to be a legitimate (if minimal) installer of the same app on their own store, not to possess the app's `client_secret`. This matches the "Critical — cross-tenant access" impact bucket.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker needs to (1) install the target app on a shop they control (a normal, unprivileged action any merchant/developer can take), (2) capture one genuine webhook delivery (body + `hmac-sha256` header) sent to their own endpoint, and (3) replay that exact body with the `hmac-sha256` header unchanged but other Shopify headers rewritten to the victim's shop domain / desired topic, directly to the app's public webhook URL. No secret material, TLS interception, or privileged account is required — only network access to the target app's webhook endpoint and a webhook subscription the attacker can trigger on their own store.

### Recommendation
- Do not treat `shop-domain`, `topic`, or `webhook-id` headers as authenticated identifiers. After HMAC validation, cross-check `request.shop` against the caller's own record of installed shops (and their corresponding sessions/tokens) before performing any tenant-scoped action, and document this requirement clearly for consumers of `ShopifyAPI::Webhooks::Registry.process`/`WebhookHandler`.
- Where feasible, additionally bind delivery-specific identifiers (e.g. `webhook-id`) via idempotency/replay tracking, so a captured `(body, hmac)` pair cannot be reused indefinitely with arbitrary header values.
- Consider extending `to_signable_string` (or adding a secondary check) to include the shop domain in a validated way if the underlying webhook delivery format supports doing so without breaking backward compatibility, or make it very explicit in `docs/usage/webhooks.md` that handler-supplied `shop` must be independently re-authenticated against locally stored sessions.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on a shop they own, `attacker-shop.myshopify.com`, and subscribes to a webhook topic (e.g. `orders/create`).
2. Attacker triggers that event on their own shop and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header value sent by Shopify to the app's webhook endpoint. This pair is valid because it was computed with the app's real `api_secret_key` over that exact body:
   `HMAC = OpenSSL::HMAC.hexdigest("sha256", api_secret_key, raw_body)` — reproducing `Utils::HmacValidator.compute_signature`. [4](#0-3) 
3. Attacker resends the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses these headers without any cryptographic check on them. [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged, still-valid) body/HMAC pair, then dispatches the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`. [6](#0-5) 
6. Any app logic keyed off `data.shop` (e.g., "update victim-shop's local order cache/state") now executes as if the event genuinely originated from the victim shop, despite the victim never having sent that webhook.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
