### Title
Webhook topic used for handler dispatch is not covered by the HMAC signature, allowing topic-swap attacks - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the JSON body but never the `X-Shopify-Topic` (or `X-Shopify-Shop-Domain`) header. `Registry.process` nevertheless uses the unauthenticated `request.topic` header value to select which registered handler to invoke and to populate `WebhookMetadata`. An attacker who legitimately receives a validly-signed webhook body for one topic can resend that unmodified body to the app's single documented webhook endpoint with the topic header rewritten to a different registered topic, and the wrong (potentially destructive) handler will run against a body it was never designed to receive.

### Finding Description
The binding the design implicitly assumes is:

`topic authenticated by HMAC == topic dispatched to handler`

i.e. `HMAC(secret, raw_body)` should attest to the tuple `(topic, raw_body)` that the handler receives. Tracing the code shows this binding does not hold:

- `Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Webhooks::Request#topic` and `#shop` are read straight from attacker-suppliable HTTP headers with no cross-check against the signed body: [2](#0-1) [3](#0-2) 
- `Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [4](#0-3) 
- `Registry.process` uses this unauthenticated `request.topic` both to look up the handler in `@registry` and to build the `WebhookMetadata` passed to `handler.handle`: [5](#0-4) 

The library's own documented integration pattern funnels *all* topics through a single controller action that builds one `Request` from `request.headers.to_h` and calls `Registry.process` — dispatch is entirely header-driven: [6](#0-5) 

Exploit flow: attacker owns a development shop with the app installed and has registered for `customers/data_request`. Shopify delivers a validly-signed body `B` for that topic to the app's webhook URL. The attacker (who controls their own network client, not Shopify's delivery infrastructure) replays `B` unchanged directly to the same webhook URL, but sets `X-Shopify-Topic: customers/redact`. `HmacValidator.validate` recomputes the HMAC over `B` only, which still matches, so validation passes. `Registry.process` then resolves `@registry["customers/redact"]` and invokes that handler with `WebhookMetadata.new(topic: "customers/redact", ..., body: JSON.parse(B))`, running redact/deletion logic on a body shaped for a read-only data-request.

None of the gem's existing guards catch this: `HmacValidator.validate` never inspects `topic`; `Request#initialize` only checks header *presence*, not their relationship to the body; there is no comparison anywhere between an authenticated topic claim and the header-derived `request.topic`.

### Impact Explanation
Any topic/handler pair reachable through the same shared webhook endpoint can be confused: a body legitimately signed for a benign/read-only topic can be redirected to a destructive handler (e.g., `customers/redact`, `shop/redact`) for the attacker's own shop, since `request.shop` is likewise taken from an unauthenticated header and not cross-checked against the body. This is repeatable at will by the attacker against their own tenant, and depending on how the host app derives the acted-upon shop/customer from `WebhookMetadata` vs. from the body content, could affect data belonging to other shops if the app trusts `data.shop` for authorization decisions. This matches the "cross-tenant / authentication bypass" severity category because the topic driving a destructive/administrative action is effectively unauthenticated even though the request otherwise carries a valid Shopify HMAC.

### Likelihood Explanation
Preconditions: the host app (a) uses the documented single-endpoint pattern where multiple topics are dispatched from one route based on `Registry.process`/`request.topic`, and (b) registers at least two topics with meaningfully different handler semantics (e.g., a read/export handler and a delete handler). The attacker needs no secret — only their own shop with the app installed (to obtain one validly-signed body) and the ability to send an arbitrary HTTP POST to the app's known webhook URL, both of which fall within the defined "unprivileged attacker" capabilities. Cost is a single replayed HTTP request; the attack is fully repeatable.

### Recommendation
Do not use the `X-Shopify-Topic` (or shop-domain) header alone to select/authorize handler dispatch. Either include the topic (and shop) as part of the signed payload the app validates (e.g., require the handler to independently verify `topic`/`shop` fields embedded in the parsed body against the header before acting), or have `Registry.process` bind the header-derived topic to the handler registration only after confirming the body's own declared topic/resource type matches, and document that host apps must not conflate header-derived metadata with HMAC-authenticated content when performing destructive actions.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_swap_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class TopicSwapTest < Test::Unit::TestCase
      def test_topic_header_swap_invokes_wrong_handler
        raw_body = '{"shop_id":1,"shop_domain":"attacker.myshopify.com"}'
        hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          raw_body,
        )
        encoded_hmac = Base64.encode64(hmac)

        data_request_handler = mock("data_request_handler")
        redact_handler = mock("redact_handler")
        # data_request handler is NEVER called...
        data_request_handler.expects(:handle).never
        # ...but the destructive redact handler IS called with the swapped-topic metadata
        redact_handler.expects(:handle).with(
          data: has_attributes(topic: "customers/redact"),
        )

        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "customers/data_request", path: "webhooks", delivery_method: :http,
          handler: data_request_handler,
        )
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "customers/redact", path: "webhooks", delivery_method: :http,
          handler: redact_handler,
        )

        # Attacker replays the SAME originally-signed body B, only rewriting the topic header
        forged_headers = {
          "x-shopify-topic" => "customers/redact", # swapped, unsigned
          "x-shopify-hmac-sha256" => encoded_hmac, # still valid for raw_body
          "x-shopify-shop-domain" => "attacker.myshopify.com",
        }

        request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

        # HMAC validation succeeds even though the topic was never signed
        assert(ShopifyAPI::Utils::HmacValidator.validate(request))

        ShopifyAPI::Webhooks::Registry.process(request)
      end
    end
  end
end
```

This demonstrates the broken binding directly: `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` for a body signed under `customers/data_request` even after the topic header is rewritten to `customers/redact`, and `Registry.process` dispatches to the redact handler instead of the data-request handler.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
