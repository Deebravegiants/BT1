<title>Attacker can escrow orders against a fake "token" address, forcing solvers to lose real output assets for phantom input tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)</title>

### Summary
`IntentGatewayV2.placeOrder` lets any caller (unprivileged) specify arbitrary `order.inputs[i].token` addresses that are escrowed and later transferred out via low-level `.call()` in `withdraw`, without validating that the address is a real, functioning ERC-20. A malicious order creator can set an input token to an address with no contract code (or a token whose `transfer`/`safeTransferFrom` behaves inconsistently), so the escrow accounting records a balance that is never backed by real value, while a solver who fills the order on the destination chain irrevocably sends real output assets before discovering the "input" they are owed can never be redeemed for real funds.

### Finding Description
`placeOrder` accepts a user-supplied `Order` with `inputs[i].token` chosen entirely by `msg.sender`: [1](#0-0) 
For non-native tokens, the code calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally increments `_orders[commitment][token]` by the (fee-adjusted) input amount, treating the transfer as successful.

Later, when the escrow is redeemed (`RedeemEscrow`/`RefundEscrow`), the same `token` address is used to release funds via raw low-level `.call()`: [2](#0-1) 
The `withdraw` code checks `success` from the low-level call but does not verify that `token` has code or that any tokens were actually moved. A call to an address without code trivially returns `success = true` with empty `returndata`, so `withdraw` "succeeds" without any value changing hands.

The chain of trust here is: solver observes `OrderPlaced` (emitted with `order.inputs`), decides the escrowed input is a real, redeemable asset, and fills the order by sending real output assets on the destination chain. Only after fill/dispatch does the solver attempt to redeem the escrowed input on the source chain — at which point `token` being a non-contract or otherwise non-functional address means the "transfer" silently no-ops, and the solver receives nothing for the value they already paid out.

This is the same root-cause pattern flagged in the reference report — an externally reachable function performs `transfer`-style calls against a caller-supplied `token` address with no validation that the address is a genuine, well-behaved ERC-20 — except here the impact is amplified because it is reachable by any unprivileged user placing an intent order, and the consequence is loss of real solver funds rather than a generic "unexpected behavior."

### Impact Explanation
A malicious order placer can grief/steal from solvers: solvers fill the order and irrevocably transfer their own output assets on the destination chain, then find the "escrowed" input token on the source chain is not a real, transferable asset when they attempt `RedeemEscrow`. This is a direct loss-of-funds vector for any unprivileged solver interacting with the intents system, satisfying the "concrete theft" bar for Medium severity.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged entry point; no special permissions are required to supply an arbitrary `token` address for `order.inputs`. The only friction is that a solver must be willing to fill an order with a token they haven't verified — but nothing in the on-chain flow (event emission, commitment hash, or escrow bookkeeping) prevents or flags a non-contract/malformed token address, so this can be executed opportunistically against any solver that doesn't perform full off-chain due diligence on every input token.

### Recommendation
Before crediting `_orders[commitment][token]` in `placeOrder`, verify `token.code.length > 0` (or otherwise validate it is a genuine ERC-20, e.g. by checking balance deltas before/after the transfer rather than trusting the boolean return of a low-level `call`). In `withdraw`/`SweepDust`, likewise confirm the target has code and that balances actually decreased by `amount` before treating the release as successful, or migrate off raw `.call()` + selector encoding to OpenZeppelin's `SafeERC20`, which already reverts on non-contract targets in recent versions.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs = [{token: <address with no deployed code>, amount: X}]` and attractive `order.output` assets/beneficiary on a destination chain. [1](#0-0) 
2. `safeTransferFrom` against the no-code address trivially "succeeds" (empty returndata), and `_orders[commitment][token] += reducedInputs[i].amount` records a bogus escrow balance without any real tokens ever entering the contract.
3. A solver observes `OrderPlaced`, fills the order on the destination chain, sending real output assets to the beneficiary.
4. Solver triggers `RedeemEscrow` to claim the source-chain escrow; `withdraw` performs `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` against the no-code address, which again returns `success = true` without transferring anything. [3](#0-2) 
5. Solver's redemption "succeeds" on-chain but they receive zero real value, while having already given up genuine output assets — net loss for the solver, net (indirect) gain for the attacker who paid nothing real for the fill.
