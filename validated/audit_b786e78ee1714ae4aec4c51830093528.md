### Title
Webhook `shop-domain` Header Is Not Covered by the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing via Replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from only the raw request body [1](#0-0) , while the `shop` value that is later trusted and forwarded to the app's handler is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates only that the HMAC of the body is correct, then passes `request.shop` straight through as the tenant identifier to the registered handler without any check that the shop is cryptographically bound to that HMAC [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(api_secret_key, body || shop)`. In this gem, the binding actually enforced is `hmac == HMAC(api_secret_key, body)` only [4](#0-3) [1](#0-0) , and the `shop` field is a completely independent, attacker-controllable HTTP header [2](#0-1) .

Any actor capable of triggering a legitimately signed webhook for their own store (e.g., an attacker who has installed the app on a store they control, which is an ordinary unprivileged action) can capture the resulting `(raw_body, hmac)` pair — this HMAC is valid because it is computed only over the body — and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value for a victim shop. `HmacValidator.validate` in `Registry.process` will still succeed, because the signature never depended on the shop header [5](#0-4) . The handler then receives a `WebhookMetadata` struct asserting `shop: <victim-shop>` [6](#0-5) , even though the payload actually originated from the attacker's own store.

### Impact Explanation
Host applications built on this gem are expected to trust `WebhookMetadata#shop` as the source-of-truth tenant identifier for looking up sessions, updating per-shop state, or acting on mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) [7](#0-6) , because the gem's documented contract is that a webhook passing `HmacValidator.validate` is an authenticated event for the stated shop. Since the shop is not bound to the HMAC, an attacker can make the app process (attacker-controlled) event data under a victim shop's identity — a cross-tenant confusion that can corrupt per-shop state, trigger unwarranted redaction/data-request handling for a shop the attacker doesn't control, or otherwise pollute one tenant's data path with another tenant's content. This satisfies the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Exploitation requires only that the attacker be able to obtain one valid `(body, hmac)` pair — trivially available to anyone who can install the app on their own shop (an ordinary unprivileged action, not requiring `api_secret_key` or a victim's credentials) — and the ability to send an HTTP request to the app's public webhook endpoint with a forged header. No secret material, session, or victim interaction is needed, making this practically exploitable by any internet user who can install the target app once.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signed payload that is verified, or otherwise cryptographically bind the shop identity to the HMAC-verified body (e.g., require host applications to independently re-verify that the shop in the header corresponds to a shop with an active, previously stored session/installation before trusting `WebhookMetadata#shop`, and document this requirement prominently). At minimum, update `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` so verification covers the full set of trust-relevant fields, not just the raw body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify sends a legitimately HMAC-signed webhook to the app's endpoint:
   - `raw_body = '{"id":123,...}'`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker captures this exact request, then resends it to the same endpoint, only replacing the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - keeping `raw_body` and `X-Shopify-Hmac-Sha256` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds [8](#0-7) [9](#0-8) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [10](#0-9) , causing the app to process attacker-controlled data under the victim shop's tenant identity.
