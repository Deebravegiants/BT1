### Title
`findMatchingWithdrawal` misreports withdrawal status/txHash when multiple same-asset withdrawals share a NEAR tx - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches PoA bridge withdrawal status entries by `assetId` alone via `findMatchingWithdrawal` [1](#0-0) , ignoring `args.index` and `args.withdrawalParams.destinationAddress`/`amount`. When a single NEAR intents tx contains two `ft_withdraw` intents for the same PoA `assetId` to different destinations, `Array.prototype.find` deterministically returns the same first-matching entry for both `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` calls, so both watchers converge on the same `(status, txHash)`.

### Finding Description
The broken equality: `describeWithdrawal({index: i}).txHash` should correspond to withdrawal `i`'s actual on-chain outcome, but with two same-`assetId` withdrawals in one NEAR tx (same `args.tx.hash`), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` invoke `getWithdrawalStatusWithRetry` with the identical `withdrawal_hash` [2](#0-1)  and receive the identical `response.withdrawals` array. `findMatchingWithdrawal` then filters only by `` `nep141:${w.data.near_token_id}` === assetId `` [1](#0-0) , and since `.find()` is deterministic and stateless with respect to caller, **both index-0 and index-1 calls resolve to the same array element** — not a random/swapped mismatch as the question posits, but a consistent duplicate: whichever withdrawal appears first in the API response is reported for *both* logical withdrawals. The code comment itself acknowledges this limitation explicitly [3](#0-2) , stating "multiple withdrawals of the same token in a single transaction are not supported" and that "POA API doesn't currently support this case either." The response schema (`WithdrawalStatusResponseOk`) does include `data.address` and `data.amount` fields per entry [4](#0-3) , meaning a fix using `destinationAddress`/`amount` correlation (as the comment itself suggests: sort by amount) is feasible but not implemented.

Existing guards don't prevent this: `validateAddress`, `compareAddresses`, and `validateWithdrawal` operate on withdrawal creation/input validation, not on status reconciliation; `createWithdrawalIdentifier` correctly carries `index` and full `withdrawalParams` per withdrawal [5](#0-4) , but that context is thrown away in `findMatchingWithdrawal`.

### Impact Explanation
An integrator polling `watchWithdrawal` for both legs will get an identical `txHash` and `status` for two withdrawals that are meant to go to two different destination addresses/amounts. If withdrawal 1 (to destination B) completes first and its entry happens to be the one `.find()` locates, an integrator watching withdrawal 0 (destination A) may prematurely mark A's payout as `completed` with B's `transfer_tx_hash`, crediting/reconciling A's off-chain ledger against a transaction that never paid A. This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice" — it is a real misreport of on-chain settlement outcome to the wrong logical withdrawal, repeatable any time an attacker crafts a multi-ft_withdraw-same-asset batch.

### Likelihood Explanation
Preconditions: attacker (an ordinary NEAR Intents user) submits one signed tx with two `ft_withdraw` intents to the same PoA `assetId` but different `destinationAddress`/`amount`, and both are routed through the SDK's batch withdrawal flow (`createWithdrawalIdentifiers` → `watchWithdrawal`). This requires no privilege beyond normal SDK usage and is fully attacker-controlled/reproducible at will, limited only by needing PoA-bridge-supported assets and multiple withdrawal legs in one call.

### Recommendation
Extend `findMatchingWithdrawal` (or `describeWithdrawal`) to disambiguate beyond `assetId` using additional available signals — e.g., match/sort by `data.address` against `withdrawalParams.destinationAddress`, and secondarily by `data.amount` relative ordering as the existing code comment suggests, consuming each matched entry once so it cannot be reused for a second `index`.

### Proof of Concept
Vitest plan (mock only `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `getWithdrawalStatus` to return two `COMPLETED` entries with identical `near_token_id` but different `data.address` ("addrA" vs "addrB") and different `data.transfer_tx_hash` ("hashA" vs "hashB").
2. Call `poaBridge.describeWithdrawal({ index: 0, withdrawalParams: { assetId, destinationAddress: "addrA", ... }, tx })` and `poaBridge.describeWithdrawal({ index: 1, withdrawalParams: { assetId, destinationAddress: "addrB", ... }, tx })`.
3. Assert `result0.txHash === "hashA"` and `result1.txHash === "hashB"` — current implementation fails this because both calls return the same first-matched entry (e.g., both return `"hashA"`), proving withdrawal 1's reported outcome does not correspond to its own destination.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
