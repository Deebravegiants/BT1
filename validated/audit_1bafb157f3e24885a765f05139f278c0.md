### Title
Webhook HMAC signs only the request body, not the `shop-domain` header — cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable "signable string" using only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` are taken directly from unauthenticated HTTP headers. This breaks the identity binding `hmac == HMAC(secret, shop || body)` that the gem implicitly presents to consumers of `WebhookMetadata.shop`: any request whose body+HMAC pair is valid for shop A will also validate for a forged request claiming to be shop B, because the header carrying the tenant identity is outside the signed data — the same "signature not bound to the identity it's supposed to protect" flaw described in the ERC1271 report (where `signedHash` wasn't bound to `address(this)`, allowing replay across accounts sharing an owner).

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts these header-derived values to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality that should hold is: `hmac_valid(request) == (body_authentic AND shop_authentic)`. In reality it is only `hmac_valid(request) == body_authentic`; `shop` (and `topic`/`webhook_id`/`api_version`) are unauthenticated and can be swapped freely by anyone who can reach the app's public webhook endpoint, as long as they can supply *some* body+HMAC pair that is valid for the app's secret. That pair is easy to obtain: any merchant who installs the app (an "unprivileged internet user" from the app's perspective) receives genuine webhook deliveries with a valid `x-shopify-hmac-sha256` for their own shop. They can capture one such delivery and replay the identical body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-webhook-id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still returns true because it only checks the body: [5](#0-4) 

The host application's handler then receives `WebhookMetadata` claiming the event belongs to the victim shop, even though nothing about the request was ever tied to that shop.

### Impact Explanation
This lets an attacker who is a legitimate (but unprivileged relative to other tenants) installer of the app forge webhook events attributed to a different, victim shop. Depending on how the host app's handler acts on `data.shop` (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or any topic that triggers session/data deletion, resyncing, or privileged side effects keyed by `shop`), this is a cross-tenant integrity/availability issue: one merchant can inject fabricated, "HMAC-valid" events into another merchant's tenant data pipeline without ever possessing that merchant's credentials or the app's `client_secret`.

### Likelihood Explanation
Requires only: (1) being able to install the target app on some shop (or otherwise obtain one valid webhook body+HMAC pair, which Shopify sends automatically on normal app events), and (2) the ability to send an arbitrary HTTP POST to the app's public webhook receiving endpoint with attacker-chosen headers — both are available to any internet user interacting with the app normally, no leaked secrets or privileged access required.

### Recommendation
Include the tenant-identifying header(s) (`shop`, and ideally `topic`/`webhook_id`) in the HMAC-signable material, or otherwise cryptographically bind `shop` to the signed payload before trusting it in `WebhookMetadata`. At minimum, document that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must not be treated as verified identity, or have `Registry.process` derive the effective shop only from data that is inside the HMAC-covered body when available.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker sends a POST to the app's public webhook endpoint with the exact same body `B` and HMAC header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (via `HmacValidator.compute_signature` over `request.to_signable_string`, i.e. `B`) succeeds because the body/HMAC pair is unchanged (`lib/shopify_api/utils/hmac_validator.rb:12-22`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` from the forged header (`lib/shopify_api/webhooks/registry.rb:188-200`, `lib/shopify_api/webhooks/request.rb:20-23`) and invokes the app's handler as if the event genuinely originated from the victim shop.
