### Title
Predictable, unsigned session identifiers enable session fixation and cross-tenant session hijacking - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps, the gem issues session cookies whose value is exactly the session lookup key (`session.id`), and that key is a fully deterministic string derived only from public/guessable data — the shop domain (and, for online sessions, the associated user id) — with no HMAC, signature, or random binding bytes tying the cookie to the specific OAuth transaction that created it. `SessionUtils.cookie_session_id` then trusts whatever value the caller passes back as the session key, with zero cryptographic verification.

### Finding Description
The identity binding that should hold is:

`cookie bytes received == a value that could only originate from this app's own successful OAuth completion for this browser`

Instead what is enforced is:

`cookie bytes received == deterministic_string(shop, user_id)`

`Session.from` builds the session `id` purely as a deterministic function of `shop` (and `associated_user.id` for online sessions): [1](#0-0) 

For non-embedded apps, `Oauth.validate_auth_callback` sets the browser's session cookie value to exactly this deterministic `session.id`: [2](#0-1) 

Later, when resolving "the current session," `SessionUtils.cookie_session_id` simply echoes back whatever the cookie hash contains under `SESSION_COOKIE_NAME` — there is no signature, no nonce, and no check that this value was ever actually issued by this gem's OAuth flow to this particular browser: [3](#0-2) [4](#0-3) 

Because offline session ids are literally `"offline_#{shop}"` and shop domains are not secrets (they are typically visible in the app's own URLs, install links, or are simply the merchant's `*.myshopify.com` subdomain), any unprivileged party who knows or guesses the shop domain can construct the exact valid session-cookie value in advance, without ever completing OAuth themselves. Online session ids (`"#{shop}_#{associated_user.id}"`) are similarly derived only from data that is frequently enumerable or observable by an unprivileged actor (Shopify user/staff ids are small sequential integers).

This is directly the bug class in the report generalized: the report's core issue is a hardcoded parameter that isn't bound/adjustable to the actual security-relevant context (token decimals/value), causing a control to fail its intended purpose. Here, the analogous failure is that the "session identity" control is satisfied by a value with no cryptographic binding to the actual authenticated transaction — it can be computed by anyone from public inputs, so the check that's supposed to gate authenticated access degenerates into a no-op for an attacker who can predict/plant the cookie value.

### Impact Explanation
This is a session fixation / forced-session vulnerability: an attacker can pre-set the `shopify_app_session` cookie in a victim's browser (or in their own browser after guessing) to the deterministic value for a target shop before or independent of any real OAuth completion. Once the app's session-storage layer (per the gem's own documented pattern, `SessionRepository.store_session(auth_result[:session])`, keyed by `session.id`) contains a real session for that shop — created either by the legitimate merchant's OAuth flow or by the attacker driving their own OAuth completion for that shop under this predictable id — any party presenting the same predictable cookie value is treated by the host app as that authenticated session. This crosses a tenant boundary: an unprivileged actor gains access to another shop's session (and thus, indirectly, to actions gated behind that shop's access token) without ever possessing that shop's credentials. This matches the "session fixation or forced OAuth completion" High-impact category.

### Likelihood Explanation
Likelihood is high for offline sessions specifically, since the id depends solely on the shop domain, which is not treated as a secret anywhere else in the flow (it appears in URLs, redirect params, and is often the app's own tenant identifier). No access token, `client_secret`, or privileged access is required to compute the value — only knowledge of the target shop domain, which is the normal, expected piece of public information an attacker interacting with any given install would have.

### Recommendation
Do not use a deterministic, attacker-predictable string as both the session lookup key and the literal browser cookie value. Bind the cookie to the session cryptographically (e.g., sign or HMAC the cookie payload with `Context.api_secret_key`, or store an unguessable random token in the cookie that maps server-side to the deterministic session id) so that `SessionUtils.cookie_session_id` can verify the cookie's authenticity before trusting it as a session key, mirroring the HMAC-verified pattern already used for `AuthQuery`.

### Proof of Concept
1. Attacker knows/observes the target shop domain `victim-shop.myshopify.com` (public information, e.g., from the merchant's storefront or app listing).
2. Attacker computes the offline session id exactly as the gem does: `"offline_victim-shop.myshopify.com"` (per `Session.from`, `lib/shopify_api/auth/session.rb:116`).
3. Attacker sets a browser cookie `shopify_app_session=offline_victim-shop.myshopify.com` in their own browser (or fixates it into a victim's browser before the victim completes login, depending on host-app cookie scoping).
4. Once the shop's real offline session is created via legitimate OAuth (`Oauth.validate_auth_callback`, `lib/shopify_api/auth/oauth.rb:100-110`) and stored by the host app keyed on `session.id` (per documented `SessionRepository.store_session`), any request presenting the same predictable cookie causes `SessionUtils.current_session_id` → `cookie_session_id` (`lib/shopify_api/utils/session_utils.rb:68-71`) to resolve to that same session id, with no verification the requester ever went through OAuth for that shop.
5. The host app looks up and activates the victim shop's session for the attacker's request, granting cross-tenant access to functionality gated on that shop's authenticated session/access token.
