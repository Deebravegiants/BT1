This confirms the discrepancy: in the OAuth flow, `AuthQuery#to_signable_string` explicitly includes `shop` in the HMAC-signed payload, but in the webhook flow, `Webhooks::Request#to_signable_string` only returns the raw body, excluding the `shop-domain` header from the HMAC computation entirely.

### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the `shop` (and `topic`) values used by `Registry.process` to route and attribute the webhook are taken from unsigned HTTP headers. Anyone who can produce one genuine, HMAC-valid webhook body/signature pair for the shared app secret (e.g. the owner of any shop that installs the app) can replay that exact body with the `x-shopify-shop-domain` header changed to a victim shop, and the gem's HMAC check will still pass.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and computes `HMAC-SHA256(secret, signable_string)`, comparing it to the `hmac` field via `OpenSSL.secure_compare`. [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body` — the shop domain, topic, webhook id and api version headers are entirely excluded from what is signed: [2](#0-1) 

Contrast this with the OAuth `AuthQuery#to_signable_string`, which deliberately includes `shop` (along with `code`, `host`, `state`, `timestamp`) inside the signed payload, so that the shop identity itself is bound by the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches the handler using `request.shop` and `request.topic`, both sourced purely from headers that were never part of the signed bytes: [4](#0-3) 

Because the app-level `api_secret_key` is shared across all shops installing the app (it is not shop-specific), any shop's genuine webhook body+HMAC pair remains valid HMAC input regardless of which `x-shopify-shop-domain` header accompanies it. This is the same class of bug as the Guard contract checking `data.length` while not covering the field (`value`) that determines the actual effect of the transaction — here the gem validates the body's authenticity but never binds that authenticity to the shop/topic fields that determine how the payload is processed and attributed.

Equality that should hold but doesn't:
`shop authenticated by HMAC` == `shop used by Registry.process to attribute the event`

In this gem, the left side is empty (no shop binding at all) while the right side is the raw `x-shopify-shop-domain` header.

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce. An attacker who operates their own store (or otherwise obtains one legitimate webhook body/signature pair for the app) can craft a forged request to the app's webhook endpoint with an unmodified, HMAC-valid body but an arbitrary `x-shopify-shop-domain` header pointing at a victim merchant. `HmacValidator.validate` returns `true` because the signed bytes are untouched, and `Registry.process` will hand `WebhookMetadata.new(topic: ..., shop: <attacker-chosen shop>, body: ..., ...)` to the host application's handler. Any app that trusts `request.shop`/`data.shop` to select which merchant's records to update, decrement inventory for, mark orders fulfilled/paid for, or otherwise treat as the acting tenant, can be made to cross-write data between tenants — a cross-tenant integrity violation.

### Likelihood Explanation
Likelihood is limited to attackers who can obtain at least one valid webhook body/HMAC pair from Shopify (trivial for anyone who installs the app on their own store and triggers a webhook, e.g. `orders/create`), and requires the target app to make trust decisions based on `request.shop`/`WebhookMetadata#shop` without independently confirming shop identity (e.g. matching against a session/subscription record keyed by shop). This is a realistic usage pattern since the gem's own documentation and `WebhookMetadata` expose `shop` specifically for that purpose.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise bind them cryptographically — following the pattern already used by `AuthQuery#to_signable_string`. At minimum, `Webhooks::Request#to_signable_string` should not present `shop`/`topic` as verified fields to consumers unless they are covered by the signature; alternatively, document clearly that `shop`/`topic` are NOT authenticated by `HmacValidator.validate` and must be revalidated by the host app against a known session record before being trusted.

### Proof of Concept
1. App has `api_secret_key = S` shared by all installed shops.
2. Attacker installs the app on their own shop `attacker.myshopify.com` and captures a legitimate `orders/create` webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(S, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical body `B` and identical HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(S, B)` from `Request#to_signable_string` (which is just `B`) — this still matches, so validation passes: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's own shop, letting the attacker inject data attributed to (or affecting) the victim tenant if the host app trusts `data.shop`.
