### Title
Pool creation does not reject freeze-authority-enabled coin/pc mints, allowing a malicious pool creator to permanently freeze all swaps/withdrawals - (File: program/src/processor.rs)

### Summary
`process_initialize2` is a fully permissionless instruction: any signer can call `Initialize2` with attacker-chosen `amm_coin_mint_info` / `amm_pc_mint_info` accounts to spin up a new AMM pool [1](#0-0) . During validation it checks that the vault token accounts have no `delegate` and no `close_authority`, and it explicitly rejects an LP mint with a `freeze_authority` set, but it never checks the `freeze_authority` of the `coin_mint`/`pc_mint` themselves [2](#0-1) [3](#0-2) . This mirrors the report's bug class ("a malicious/unvalidated token can be inserted into a push-based system and later brick outbound transfers"), except here the "whitelist gap" is the missing freeze-authority check for the two tokens that make up a pool.

### Finding Description
`Processor::unpack_mint` only unpacks the mint and checks the owning program id, performing no field-level validation [4](#0-3) . In `process_initialize2` the coin/pc mints are unpacked with this function and never inspected further for `freeze_authority` [1](#0-0) ; only the resulting vault token accounts are checked for `delegate` and `close_authority` [5](#0-4) [6](#0-5) , and only the LP mint's `freeze_authority` is rejected [7](#0-6) .

An attacker can:
1. Create an SPL mint `M` where they hold the `freeze_authority`.
2. Call `Initialize2` to create a new Raydium pool pairing `M` with any legitimate token (e.g. USDC), seeding it with a small amount of initial liquidity [8](#0-7) . Nothing in `Initialize2` prevents this because freeze authority on the coin/pc mint is never checked.
3. Wait for other unprivileged LPs/swappers to deposit into this pool via `Deposit` (which pushes user tokens into the same coin/pc vaults) [8](#0-7)  or swap against it via `SwapBaseIn`/`SwapBaseOut`.
4. Once meaningful third-party funds are in the vault, the attacker calls the SPL token program's `FreezeAccount` instruction (using the freeze authority they control) on the `amm_coin_vault` or `amm_pc_vault` token account — an account the attacker knows deterministically because it is derived from a fixed PDA seed at pool creation [9](#0-8) .
5. Every subsequent `SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2`, `Withdraw`, and `WithdrawPnl` call performs a direct SPL `Transfer` CPI out of (or into) that frozen vault via `Invokers::token_transfer_with_authority` / `Invokers::token_transfer` [10](#0-9) [11](#0-10) [12](#0-11) . The SPL Token program rejects transfers on a frozen account, so every one of these calls will revert, permanently.

There is no pull-based fallback and no per-token exclusion mechanism — the AMM always pushes both legs of the trade/withdrawal in a single push-style CPI, exactly as described in the source report.

### Impact Explanation
Once the vault is frozen, all LP funds deposited into that pool (both the attacker's initial deposit and any subsequent depositors' funds) become permanently unwithdrawable, and the pool becomes permanently unusable for swaps. This is a direct, permanent freeze of third-party user/LP funds triggered entirely by the malicious pool creator's own signer-controlled action (freezing their own mint) after the pool has attracted external liquidity — no cooperation from Raydium admins or validators is required. This satisfies "permanent freezing of user or LP funds."

### Likelihood Explanation
Likelihood is high: `Initialize2` is completely permissionless and reachable from a single transaction with attacker-chosen mint accounts [1](#0-0) ; creating a mint with a freeze authority is a standard, one-instruction SPL token operation available to anyone; and freezing a known vault address afterward is a normal token-program call the attacker can issue at any time of their choosing (e.g., once liquidity/volume looks attractive). No off-chain, privileged, or non-default-build conditions are needed.

### Recommendation
In `process_initialize2`, reject pools whose `coin_mint` or `pc_mint` has `freeze_authority.is_some()`, mirroring the existing check already applied to the LP mint [7](#0-6) . If certain freeze-authority tokens must be supported, consider gating this behind an admin-curated allow-list rather than fully permissionless `Initialize2`, or add a pull-based/escrow withdrawal path that cannot be starved by a single frozen vault.

### Proof of Concept
1. Attacker mints token `M` with `freeze_authority = attacker`.
2. Attacker calls `initialize2` (program/src/instruction.rs `initialize2`) pairing `M` as `amm_pc_mint` with e.g. USDC as `amm_coin_mint`, seeding the pool with a small amount [13](#0-12) .
3. `process_initialize2` completes successfully since no freeze-authority check exists for `pc_mint` [1](#0-0) [14](#0-13) .
4. Victim LPs call `Deposit`, transferring USDC/`M` into the pool's vaults.
5. Attacker calls SPL Token's `FreezeAccount` on `amm_pc_vault` (the deterministic PDA-derived vault address from step 2) using their `freeze_authority`.
6. Any subsequent `Withdraw`, `WithdrawPnl`, `SwapBaseIn`, or `SwapBaseOut` call reverts inside `Invokers::token_transfer_with_authority`/`token_transfer` because the frozen `amm_pc_vault` cannot be debited or credited, permanently freezing all coin/pc funds in that pool [10](#0-9) [12](#0-11) .
