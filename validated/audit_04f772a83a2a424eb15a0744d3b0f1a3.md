### Title
Hardcoded zero-pad EVM→AccountId conversion in `pallet-hyper-fungible-token::on_accept` bypasses the configured `EvmToSubstrate` mapping, permanently stranding bridged funds - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token` bridges ERC20 tokens between EVM chains and a substrate chain via `HyperFungibleToken`/`WrappedHyperFungibleToken`. When a message arrives from the EVM side, `on_accept` must decide which local `AccountId` receives the minted/unlocked tokens. Instead of using the pallet's own configurable `EvmToSubstrate::convert` trait (which the pallet already uses elsewhere in the very same function for authenticating calldata execution), the beneficiary used for the actual token transfer is derived by simply zero-padding the raw 20-byte `to` address into a 32-byte `AccountId`.

### Finding Description
In `on_accept`, the recipient of bridged funds is computed at [1](#0-0) , using a raw zero-pad of the EVM address bytes with no consultation of `T::EvmToSubstrate`.

Later in the same function, when executing optional cross-chain calldata, the pallet uses the *configured* `T::EvmToSubstrate::convert` to derive the actual signer/origin account for an EVM sender, and even asserts that the derived account must equal the `beneficiary` [2](#0-1) . This shows the pallet is aware that the "correct" EVM→Substrate identity mapping is `T::EvmToSubstrate::convert`, not raw zero-padding — yet the token-moving logic at lines 61-72 hardcodes the zero-pad instead of calling `T::EvmToSubstrate::convert`.

The trait itself is defined and documented as the source of truth for "Converts an EVM address to a substrate account, used for authenticating incoming cross-chain runtime calls" [3](#0-2) . Its only shipped default (`impl EvmToSubstrate<T> for ()`) coincidentally also zero-pads, but the trait exists specifically so that production runtimes can supply a non-trivial converter (e.g., a Keccak-derived or claim/mapping-based scheme, analogous to Moonbeam-style `AccountId20`↔`AccountId32` unification) so that the EVM-address holder can actually control the resulting substrate account. If a production runtime configures a real `EvmToSubstrate` (as the pallet's design clearly anticipates, and as the calldata-execution branch depends on for authorization), then any inbound HFT transfer whose `to` field is a bare 20-byte EVM address will have its tokens minted/unlocked to a *different* `AccountId` than the one the sender's EVM key (or contract) actually controls via that runtime's converter. The zero-padded `AccountId32` is, in general, not a valid public key with a known private key (or a controllable derived account) under the runtime's real conversion scheme, so the funds land in an account nobody can sign for.

This mirrors the reported bug class precisely: an address representation valid and controlled on the source chain (an EVM address, EOA or contract) is translated to the destination chain via a naive/incorrect scheme instead of the canonical chain-specific address-derivation/aliasing mechanism, producing a destination account that the original controller cannot actually operate — resulting in permanently stranded funds. The register/update paths that configure this bridge only store raw 20-byte EVM contract addresses per chain [4](#0-3)  and give no indication that recipients are expected to be treated specially; nothing in `send`/`register_token` warns integrators that the destination beneficiary bypasses `EvmToSubstrate`.

### Impact Explanation
This is a High-severity fund-freezing bug: any unprivileged EVM user (or protocol) sending ERC20/native value cross-chain into this substrate pallet, when the runtime configures a non-trivial `EvmToSubstrate`, will have funds minted to an account address that does not correspond to any private key the sender controls under that scheme. Because token custody (native escrow release or non-native mint) happens directly to this miscomputed `beneficiary` [5](#0-4) , the loss is immediate and irreversible once the request is delivered — there is no timeout/refund path for this class of error since delivery succeeds (only failed dispatch triggers `on_timeout` refunds). This is a systemic, permanent freezing/loss of user funds, not merely edge-case griefing.

### Likelihood Explanation
Likelihood is high wherever a runtime deploys this pallet with a non-identity `EvmToSubstrate` converter (the entire reason the trait exists beyond the toy `()` default) — every ordinary cross-chain transfer from an EVM chain into that runtime hits this path with no attacker action required; it's a normal, expected user/protocol interaction (`send()` → `onAccept`/`on_accept`) that silently misroutes funds.

### Recommendation
In `on_accept` (and in the mirrored `on_timeout` refund path, which has the analogous issue for the `from`/refund beneficiary), replace the raw zero-pad conversion with `T::EvmToSubstrate::convert(H160::from_slice(&to_bytes))` when the recipient bytes are 20 bytes (EVM-address form), consistent with how the calldata-execution branch already derives origins. Reserve the raw 32-byte pass-through only for native substrate `AccountId32` recipients. Add regression tests asserting that, with a non-identity `EvmToSubstrate` configured, the minted/unlocked balance lands on the account returned by that converter rather than on the zero-padded bytes.

### Proof of Concept
1. Configure a runtime with `pallet_hyper_fungible_token::Config::EvmToSubstrate` set to a non-identity converter, e.g. one that maps `H160` to a distinct claim account `C(addr)` different from `zero_pad(addr)` (as intended by the trait's design, mirroring the same override used at [6](#0-5)  for signature verification).
2. On the EVM chain, call `HyperFungibleToken.send()` with `to = abi.encodePacked(evmAddress)` targeting this substrate chain.
3. The relayer delivers the `PostRequest`; `on_accept` runs, computing `beneficiary = zero_pad(evmAddress)` at [7](#0-6)  and minting/transferring the bridged amount to it.
4. The true owner of `evmAddress`, who can only sign for `C(evmAddress)` (the account produced by `T::EvmToSubstrate::convert`), cannot produce a valid `MultiSignature` for `zero_pad(evmAddress)` and therefore can never move the received balance — funds are permanently stuck, verifiable by comparing `beneficiary` (line 72) against `T::EvmToSubstrate::convert(evmAddress)` and observing they differ whenever the runtime's converter isn't the trivial zero-pad.

/// Converts an EVM address to a substrate AccountId
pub trait EvmToSubstrate<T: frame_system::Config> {
	fn convert(addr: H160) -> T::AccountId;
}

/// Default implementation: zero-pads the 20-byte address into a 32-byte AccountId
impl<T: frame_system::Config> EvmToSubstrate<T> for ()
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn convert(addr: H160) -> <T as frame_system::Config>::AccountId {
		let mut account = [0u8; 32];
		account[12..].copy_from_slice(&addr.0);
		account.into()
	}
