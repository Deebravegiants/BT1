This confirms the important behavior: per the documented `handle` invariant (docs/content/protocol/ismp/requests.mdx:113-115), if `IsmpModule::on_accept` doesn't return `Ok`, "the receipt of this request will not be persisted, allowing the request to be replayed" [1](#0-0) , and `handle_incoming_message`/`Pallet::<T>::execute` propagates any `on_accept` error as a hard failure for the whole message batch, reverting all storage changes from that extrinsic (including receipt persistence) [2](#0-1) . That means a failed `on_accept` for the withdrawal module is retryable on the delivery side. However, the `Fees::<T>::insert(...,U256::zero())` zeroing on the **Hyperbridge/source side** happens in a separate, already-committed transaction (the `withdraw()` extrinsic) that only dispatches the request — it does not wait for, or roll back on, the destination's execution result.

### Title
Relayer fee accounting is zeroed optimistically before delivery confirmation, permanently losing rewards on destination-side transfer failure - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in `modules/pallets/relayer/src/withdrawal.rs` reads the relayer's full `available_amount` from `Fees`, dispatches an ISMP POST request to the destination chain instructing it to pay that amount, and **unconditionally zeroes** the `Fees` entry in the same extrinsic, before the destination-side payout is confirmed [3](#0-2) . On the destination chain, `HyperbridgeWithdrawalModule::on_accept` performs `T::Currency::transfer(&RELAYER_FEE_ACCOUNT, &account, amount, Preservation::Expendable)`, which reverts with a currency error if `RELAYER_FEE_ACCOUNT`'s balance is insufficient to cover `amount` (or leaves it below the Existential Deposit) [4](#0-3) .

### Finding Description
This is the analog of the Ajna bug: an exact, hard-capped withdrawal amount (`transferAmount_`/`minAmount_` in Ajna, `available_amount`/`amount` here) is compared against an on-chain balance that can legitimately be lower than the amount owed, and the transfer reverts instead of partially settling. In Ajna this only wasted the user's transaction (the storage was untouched by the revert). Here it is strictly worse: the accounting update (`Fees::<T>::insert(...,U256::zero())`) is performed on the **source (Hyperbridge)** chain within the `withdraw()` extrinsic itself, independent of whether the destination-chain payout succeeds. `dispatch_request` merely queues the outbound message — it does not block on execution — so the zeroing of `Fees` is not gated on delivery success at all.

If `RELAYER_FEE_ACCOUNT`'s balance on the destination chain is below `amount` (a very plausible situation: `RELAYER_FEE_ACCOUNT` is only credited incrementally as new fee-bearing requests are dispatched via `dispatch_request` in `modules/pallets/ismp/src/dispatcher.rs:99-105`, and is drained by both relayer withdrawals and refunds on timeouts), the destination-side `on_accept` fails. Per the documented ISMP invariant, a failing `on_accept` leaves no receipt and can be retried on the delivery side — but the relayer's `Fees` balance on Hyperbridge has already been irreversibly zeroed by the `withdraw()` call, and there is no mechanism to restore it. The relayer has no way to reclaim the accrued fee: they cannot resubmit `withdraw()` (their `Fees` entry is zero), and the destination-side retry of the same POST request will keep failing for the same reason until/unless `RELAYER_FEE_ACCOUNT` happens to be topped up, at which point the funds would go to whichever address is passed by the retryer, not necessarily correlate with fixing accounting, since the source-side ledger is already gone.

### Impact Explanation
This is a permanent freezing/loss of relayer reward funds: a relayer who has legitimately earned fees for delivering messages loses the accrued balance if the shared `RELAYER_FEE_ACCOUNT` cannot cover the exact claimed amount at the time the destination executes the withdrawal message. Given `RELAYER_FEE_ACCOUNT` is a shared pot funded by ordinary fee-paying dispatches and drained by all relayers' withdrawals concurrently, transient insufficiency is a realistic, not merely theoretical, scenario — analogous to the Ajna case where the reward pool balance briefly trails the amount owed.

### Likelihood Explanation
Medium-to-High. `RELAYER_FEE_ACCOUNT` balance sufficiency is never checked or reserved at `withdraw()` time on the source chain; the check only happens implicitly via the `Currency::transfer` on the destination chain, well after the source-side `Fees` accounting has already been zeroed out. Any timing where accumulated relayer claims exceed the currently-escrowed relayer-fee pool on a given destination chain (e.g., bursty withdrawals, or if fees are also drawn down by timeout refunds) triggers permanent loss for the relayer whose withdrawal executes after the pool is exhausted.

### Recommendation
Do not zero `Fees::<T>` optimistically at dispatch time. Either:
1. Zero (or debit) `Fees` only after receiving confirmation that the destination-side transfer succeeded (e.g., via a response/ack message back to Hyperbridge), or
2. Escrow/reserve the funds atomically on the source side before dispatch so the destination-side transfer is guaranteed to have backing, or
3. On destination-side `on_accept` failure, ensure the request remains retryable indefinitely and expose a way to top-up/reconcile `RELAYER_FEE_ACCOUNT` before it can be drained below outstanding relayer claims, with the source-side ledger only cleared upon confirmed delivery.

### Proof of Concept
1. Multiple relayers accumulate `Fees` on Hyperbridge for message deliveries to the same `dest_chain`; `RELAYER_FEE_ACCOUNT` on `dest_chain` holds only enough BRIDGE/fee-token balance to cover roughly the sum of expected claims, assuming none time out or double-claim concurrently.
2. Relayer A calls `withdraw()`; `available_amount` is read, an ISMP POST `WithdrawRelayerFees` is dispatched to `dest_chain`, and `Fees::<T>::insert(dest_chain, A, U256::zero())` executes immediately (`modules/pallets/relayer/src/withdrawal.rs:116-184`).
3. Before A's request is delivered, Relayer B's earlier withdrawal (or a timeout refund routed through the same `dispatcher.rs::dispatch_request` fee-escrow path) drains `RELAYER_FEE_ACCOUNT` below A's `amount`.
4. When A's message executes on `dest_chain`, `HyperbridgeWithdrawalModule::on_accept`'s `T::Currency::transfer` fails (insufficient balance/ED), and the whole `Message::Request` handling errors out (`modules/pallets/ismp/src/impls.rs:37-51`), so no receipt is persisted and the request can technically be replayed.
5. Relayer A has no `Fees` balance left on Hyperbridge to re-derive or re-dispatch the withdrawal from — their reward is unrecoverable through the protocol.

impl<T: Config> Pallet<T> {
	/// Execute the provided ISMP datagrams, this will short circuit if any messages are invalid.
	/// This also charges fee on valid message delivery
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		let messages_with_weights = message_results
			.iter()
			.zip(messages)
			.map(|(result, message)| MessageWithWeight { message, weight: result.weight() })
			.collect::<Vec<_>>();

		let events = message_results
			.into_iter()
			// check that requests will be successfully dispatched
			// so we can not be spammed with failing txs
			.map(|result| match result {
				MessageResult::Request { events, .. } |
				MessageResult::Response { events, .. } |
				MessageResult::Timeout { events, .. } => events,
				MessageResult::ConsensusMessage(events) => events.into_iter().map(Ok).collect(),
				MessageResult::FrozenClient(_) => vec![],
			})
			.flatten()
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;

		T::FeeHandler::on_executed(messages_with_weights, events.clone())
			.map_err(|_| Error::<T>::ErrorChargingFee)?;

		for event in events.clone() {
			// deposit any relevant events
			Pallet::<T>::deposit_event(event.into());
		}

		Ok(events)
	}
