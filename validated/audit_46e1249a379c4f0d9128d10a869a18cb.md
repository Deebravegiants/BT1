### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) exclusively from the `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. Since Shopify webhook HMACs are computed with the app's single `client_secret` shared across every shop that installs the app, an attacker who legitimately installs the app on their own (attacker-controlled) shop can obtain genuinely-signed webhook payloads, then replay them to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop. Because the header is not part of the signed payload, the forged shop identity passes `HmacValidator.validate` unchanged, and the handler receives `WebhookMetadata` attributing the (attacker-supplied) body to the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: `to_signable_string` [1](#0-0)  yet `Request#shop` is read straight from the unauthenticated header: `shopify_header("shop-domain")` [2](#0-1) .

`Registry.process` validates only the HMAC over the body and then dispatches the handler using `request.shop`, `request.topic`, etc., all taken from headers that were never part of the signed content: [3](#0-2) .

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field: [4](#0-3) . For webhook requests this string is only the raw body, so the `shop` (and `topic`/`webhook_id`) headers can be freely modified by anyone who can produce (or capture) one validly-signed body — most simply, an attacker who installs the app on their own store.

This breaks the identity binding: **shop authenticated (bytes actually covered by HMAC) ≠ shop stored/used as the tenant key (`request.shop` header value)**. Compare this to the OAuth callback path, where `AuthQuery#to_signable_string` explicitly folds `shop`, `host`, `code`, `state`, and `timestamp` into the signed string [5](#0-4)  — the webhook path has no equivalent binding of `shop` into the signature.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as populated by `Registry.process`) to select which tenant's data to update, invalidate, or key by shop domain is vulnerable to cross-tenant data confusion: an unprivileged actor who has legitimate install access to their own store (an "unprivileged internet user" from the app's perspective, since anyone can install a public/test app) can forge which merchant a webhook body applies to. This meets the Critical bar of cross-tenant access, since the gem's own webhook processing API hands the host application an attacker-controllable tenant identifier despite claiming HMAC-verified integrity.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint and the ability to obtain one genuinely-signed webhook body (trivial via installing the app on any store, including a free/dev store) plus knowledge of a target shop's `myshopify.com` domain (public information). No access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed content in `to_signable_string`, e.g. `"#{shop}|#{topic}|#{@raw_body}"`, or otherwise cross-check the header-derived `shop` against a value obtained independently (e.g., resolve the shop via a stored session/webhook subscription lookup) before dispatching to handlers, rather than trusting the raw header value verified only against body bytes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, receives an `orders/create` webhook with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's shared `client_secret`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Webhooks::Request.new` accepts the request (all required headers present) [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `@raw_body` [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim.myshopify.com`, even though the payload actually originated from the attacker's own shop [8](#0-7) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
