### Title
Unchecked ERC20 `transfer()` return value in Tron `IntentGatewayV2.withdraw()` and `SweepDust` handler can silently drop token payouts while escrow accounting is finalized - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` uses a raw low-level `.call()` with `IERC20.transfer.selector` and only checks whether the *call* succeeded (`success`), never inspecting the returned boolean payload. Non-compliant ERC20/TRC20 tokens that return `false` on failed transfers instead of reverting will make `success == true` even though no tokens moved, while the contract proceeds to zero out escrow accounting as if the payout succeeded.

### Finding Description
In `withdraw()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

and for fee redemption:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [2](#0-1) 

and in the `SweepDust` branch of `onAccept()`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

`success` here only reflects whether the external call reverted/executed, not whether the token itself reports the transfer as successful. Many ERC20/TRC20 tokens do not revert on failure — they return `false`. With this pattern, `success` will be `true` (no revert occurred) even though the token contract signaled failure, so `TransferFailed()` is never triggered.

Immediately after this check, `withdraw()` decrements escrow state:
```solidity
_orders[body.commitment][token] -= amount;
``` [4](#0-3) 

and for the fee slice:
```solidity
delete _orders[body.commitment][TRANSACTION_FEES];
``` [5](#0-4) 

This is reachable from an unprivileged path: `withdraw()` is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` request is delivered by any relayer (permissionless message delivery) [6](#0-5) , and also from `onGetResponse()` following a permissionless GET-response proof delivery [7](#0-6) . The `SweepDust` branch is reachable the same way through `onAccept()` [8](#0-7) .

Note that the parallel non-Tron implementation, `evm/src/apps/intentsv2/IntentsBase.sol`, and other paths in the codebase correctly use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (e.g. `IntentGatewayV2.sol` predispatch/input transfers use `safeTransferFrom` [9](#0-8) , and `WrappedHyperFungibleToken.sol` uses `safeTransfer` throughout [10](#0-9) ). Only the Tron variant's `withdraw()`/`SweepDust` paths regressed to the unchecked raw-call pattern despite importing `SafeERC20` at the top of the file (it is used elsewhere for `safeTransferFrom` on input assets, but not for these payout paths).

### Impact Explanation
If the escrowed input token or fee token is a non-standard ERC20/TRC20 that returns `false` instead of reverting on failure (e.g. due to blacklisting, paused state, or insufficient balance from a rug-adjacent implementation), the escrow record is deleted / decremented as though the beneficiary was paid, but the beneficiary receives nothing. The tokens remain stuck in the `IntentGatewayV2` contract with no accounting path to reclaim them (the commitment is marked filled/refunded, so `withdraw` cannot be re-triggered for that commitment). This is a permanent loss of user/solver funds — the exact class of impact described in the reported bug ("tokens are transferred when they are not supposed to be because return value is not checked for success," here manifesting as funds becoming permanently unrecoverable when transfer fails silently).

### Likelihood Explanation
Likelihood depends on which tokens are configured as intent input/fee tokens on the Tron deployment. TRC20 implementations are not uniformly OpenZeppelin-compliant, and some historically return `false` rather than reverting on failure (similar to legacy ERC20 patterns like older USDT forks). Because `withdraw()` and the `SweepDust` handler are reachable by any relayer delivering a valid cross-chain proof/message (no privileged caller required), exploitation only requires selecting or waiting for a token whose transfer legitimately fails once (e.g., temporarily paused, blacklisted beneficiary, or insufficient contract balance due to another bug) — at that point funds are permanently stuck rather than the transaction reverting for retry.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`using SafeERC20 for IERC20;` is already imported in this file). This ensures both call-success and returned-boolean truthiness are validated, causing a proper revert instead of silently finalizing escrow state on failed transfers.

### Proof of Concept
1. Configure (or have selected via order input) an ERC20/TRC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (non-standard but common on Tron-style tokens).
2. A relayer delivers a `RedeemEscrow` (or `RefundEscrow`) POST request for a commitment whose escrowed token is this non-compliant token, calling `onAccept()` → `withdraw()`.
3. At execution time the token's `transfer()` call returns without reverting but returns `false` (e.g., balance drained by a race, blacklist applied, or pause enabled) — `success` from the low-level `.call` is `true` since only the call's revert status is checked. [11](#0-10) 
4. `withdraw()` proceeds past the check, decrements `_orders[body.commitment][token]`, and emits `EscrowReleased`/`EscrowRefunded` even though the beneficiary received zero tokens.
5. Because the commitment's escrow entry is now zeroed/marked filled, there is no remaining code path to retry or reclaim the stuck tokens — they are permanently locked in the `IntentGatewayV2` contract.
