### Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and handed to the webhook handler as trusted identity data. This breaks the binding `hmac_authenticated_bytes == bytes_the_handler_acts_on`, allowing a party who possesses one validly-signed `(raw_body, hmac)` pair to relabel it as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight out of request headers with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, then immediately dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

`HmacValidator.validate` only ever hashes `verifiable_query.to_signable_string`, i.e., the raw body: [4](#0-3) 

The identity binding the gem's API implicitly promises to the host application is:
`shop header trusted by handler == shop bound to the HMAC-authenticated bytes`

In reality the equality is:
`shop header trusted by handler != any field covered by hmac(raw_body, client_secret)`

Because the app's public webhook endpoint accepts arbitrary POST requests (it is not restricted to Shopify's IP ranges by this gem), any unprivileged party who has previously observed one legitimately-signed `(raw_body, hmac)` pair — for example by triggering a webhook on their own installed store, which they are fully entitled to receive — can resend that exact `(raw_body, hmac)` pair to the same endpoint while substituting the `x-shopify-shop-domain` (and/or `topic`/`webhook-id`) header for a different, victim shop. `Utils::HmacValidator.validate` will still pass, because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` is the attacker-forged value.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: the webhook handler processes attacker-controlled/replayed data while believing (via the "verified" `shop` field) that it originated from a different shop. In host applications that use `data.shop` to select the tenant record/session to update (a common and expected use of `WebhookMetadata#shop` per this library's own design), an unprivileged actor with access to only their own store's webhooks can cause cross-tenant data writes/side effects attributed to a victim shop's account.

### Likelihood Explanation
Likelihood is constrained by the need to first capture one legitimately-signed `(raw_body, hmac)` pair, which any store owner with the app installed can trivially obtain from their own genuine webhook traffic, and by the target application actually keying tenant-scoped behavior off `WebhookMetadata#shop` (an intended and documented use of the API). No secrets, tokens, or privileged access are required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-signed content, or otherwise cryptographically tie the trusted header values to the signature verification, e.g. by including them in `to_signable_string`, or by requiring the host application to cross-check the header-derived `shop` against a shop value embedded in the verified JSON body before dispatching to a handler.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and triggers/observes a legitimate webhook delivery, capturing `raw_body` and the `x-shopify-hmac-sha256` header (both fully attacker-visible, no secret needed).
2. Attacker sends a POST request directly to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — this passes because the body/HMAC pair is unmodified. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the attacker's replayed body as if it belonged to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
