### Title
Webhook `shop` identity not bound to HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `x-shopify-shop-domain` header as-is to identify which shop the event belongs to. The HMAC signature never covers the `shop` (or `topic`/`webhook-id`) header, so the identity binding `hmac(body) == hmac(body, shop)` does not hold — verified bytes and acted-upon identity diverge.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`shop` is read from an HTTP header, not from any cryptographically authenticated field: [4](#0-3) 

`Registry.process` validates only the HMAC of the body and then forwards `request.shop` unchanged to the app's handler as `WebhookMetadata.shop`: [1](#0-0) 

The HMAC key (`Context.api_secret_key`) is the app's single client secret, shared across every shop that installs the app — it is not shop-specific. Consequently, a valid `(raw_body, hmac)` pair generated from one shop's own genuine webhook delivery is a valid pair for *any* `shop-domain` header value, because the header plays no role in the signature computation. An unprivileged user who installs the app on their own store can capture a legitimate webhook (body + HMAC), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim's shop). `HmacValidator.validate` will still succeed because it only checks `verifiable_query.to_signable_string` (the body) against the same shared secret, and the forged event will be delivered to the handler labeled as coming from the victim shop.

This breaks the identity equality the app relies on: `shop authenticated (by HMAC) == shop acted upon (by handler)`. The equality fails because the header is unauthenticated while the handler-visible identity is taken directly from that same header.

### Impact Explanation
Any app built on this gem that uses `data.shop` from `WebhookMetadata` to look up a stored session/access token, update per-shop state, or otherwise scope work to a tenant is exposed to cross-tenant data injection: an attacker-controlled event (with attacker-chosen JSON body content, subject to whatever fields the topic includes) can be attributed to a victim shop. This matches the Critical "cross-tenant access" impact bucket — the boundary between shop A's and shop B's webhook data collapses because the shop identity carried in the header is never verified against the payload's origin.

### Likelihood Explanation
Exploitation only requires an unprivileged internet user to install the app on their own store (or otherwise obtain one valid `(body, hmac)` pair, which is straightforward for any topic they can trigger themselves, e.g. `orders/create`) and then send a crafted HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No access token, `client_secret`, or privileged credential is needed — only capturing one legitimate webhook body/HMAC from their own tenant.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) into the value that is HMAC-verified, or otherwise cross-check the header-provided `shop` against an independently authenticated source (e.g., verify the header shop matches a shop actually associated with the specific webhook subscription/HMAC via a lookup keyed by a value that is part of the signed payload) before trusting `request.shop` in `WebhookMetadata`. At minimum, document/require that host apps derive shop identity only from data actually covered by the signature.

### Proof of Concept
1. Attacker registers app on `attacker.myshopify.com` and receives a genuine webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (computed as `HMAC-SHA256(api_secret_key, B)`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same raw body `B` and header `x-shopify-hmac-sha256: H` to the app's webhook callback endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and matches `H` — validation succeeds because the header is not part of the signed input (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The handler is invoked with `WebhookMetadata.shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the event body actually originated from `attacker.myshopify.com`, demonstrating the broken shop/HMAC binding.
