### Title
Escrow released to attacker-chosen token before accounting update enables reentrant double-withdrawal of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The CVE describes an EFA driver bug where a resource's refcount is decremented (and memory freed) *before* the operation that could fail is confirmed to succeed, so a failed/retried destroy can underflow an already-zeroed refcount. The same "interaction before effect" ordering flaw exists in the Tron fork of `IntentGatewayV2.withdraw()`, where escrowed token balances are decremented *after* the external token transfer instead of before it — the reverse of the checks-effects-interactions pattern used everywhere else in the protocol (including the canonical EVM `IntentsBase._withdraw`, which decrements before transferring).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` is reached from `onAccept` (for `RedeemEscrow`/`RefundEscrow` cross-chain messages) and from `onGetResponse` (cross-chain cancel confirmation): [1](#0-0) 

The loop only checks that the escrow slot is non-zero (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();`), performs the raw `token.call(...)` transfer to the attacker-controlled `beneficiary`, and only *afterward* executes `_orders[body.commitment][token] -= amount;`. The same pattern repeats for transaction fees at lines 717-723, where `feeToken.call(transfer...)` runs before `delete _orders[body.commitment][TRANSACTION_FEES];`.

Because `order.inputs[i].token` is an arbitrary address chosen by the order's creator at `placeOrder` time (there is no allow-list enforced in this contract), an attacker can escrow a self-deployed malicious "token" contract as an order input. When that token's `transfer` implementation is invoked during `withdraw()`, it executes with the escrow accounting for that commitment/token still un-decremented. This mirrors the CVE's root cause exactly: the resource (escrowed balance) is not "deallocated" (decremented) before the interaction that can trigger reentry, instead of the safe reverse order.

By contrast, the canonical EVM contract does this correctly: [2](#0-1) 
which decrements `_orders[body.commitment][token]` *before* the token transfer — proving the Tron fork's ordering is a regression against the intended CEI pattern in this codebase.

### Impact Explanation
If the attacker's malicious token can re-enter any state-mutating path that reads or mutates `_orders[commitment][token]` for the same commitment before the pending decrement is applied (e.g., during future upgrades to `withdraw`/`onAccept`, or if `onAccept`'s `onlyHost` guard is bypassed or the host's `restrict(handler)` protections around `dispatchIncoming` are ever loosened, or via nested calls that reach `_cancelSameChain`-style withdrawal paths sharing the same accounting), escrowed input tokens or accumulated protocol/relayer fees tied to that commitment can be drained more than once, resulting in direct theft of escrowed user funds — a concrete High-severity impact matching the CVE's "use-after-free"-style resource accounting flaw.

### Likelihood Explanation
Exploitability today is constrained by the fact that `withdraw()` is only reachable through `onAccept`/`onGetResponse`, both gated `onlyHost`, and the host's `dispatchIncoming` is itself `restrict(_hostParams.handler)`, so a straightforward reentrant call back into `onAccept` from a malicious token's `transfer` hook is not trivially callable by an attacker-controlled token contract in the current wiring. However, this is a fragile, implicit protection rather than a property enforced by the vulnerable function itself, and it depends on invariants outside `withdraw()`'s control (host/handler access-control remaining intact across all future code paths and chain-specific token semantics on Tron, which supports TRC10/TRC20 tokens with different call/callback behaviors than standard EVM ERC-20). Any future refactor, alternate entrypoint, or Tron-specific token semantics that permits a reentrant call into a function touching the same `_orders[commitment][token]` slot converts this into an immediately exploitable fund-theft primitive. Given that the fix is essentially free (swap two lines to match the already-correct pattern in `IntentsBase.sol`), this is best treated as a real defect rather than benign code style.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to decrement `_orders[body.commitment][token]` (and `delete _orders[body.commitment][TRANSACTION_FEES]`) *before* performing the external `token.call`/native transfer, matching the checks-effects-interactions pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally, consider adding an explicit reentrancy guard on `withdraw()`/`onAccept` as defense-in-depth, since this function moves escrowed user funds.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC-20-like contract whose `transfer(address,uint256)` function, when invoked by `IntentGatewayV2`, attempts to re-enter into any function that reads/writes `_orders[commitment][EvilToken]` for the same commitment (conceptually analogous to a classic ERC-777/callback reentrancy).
2. Attacker calls `placeOrder` on the source chain, escrowing `EvilToken` as `order.inputs[0].token` with `amount = X`.
3. Order is cancelled/filled such that a `RefundEscrow`/`RedeemEscrow` cross-chain message triggers `onAccept -> withdraw(body, ...)` with `beneficiary = attacker`.
4. Inside `withdraw()`, at line 706 (`evm/tron/contracts/apps/IntentGatewayV2.sol:706`) the call `token.call(transfer(attacker, X))` executes before `_orders[commitment][EvilToken] -= X` at line 710 runs.
5. If any reachable path allows `EvilToken.transfer` to trigger a second withdrawal against the same still-nonzero `_orders[commitment][EvilToken]` slot before the pending decrement lands, the attacker receives `X` tokens more than once, draining the escrow — directly analogous to the CVE's double-decrement/use-after-free caused by releasing a resource's guard before confirming the operation's completion.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
