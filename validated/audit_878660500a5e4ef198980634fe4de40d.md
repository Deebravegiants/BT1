### Title
Two-phase graduation caches a phase-1 LT/token snapshot with no re-validation against the live external LT config, permanently freezing curve-raised funds - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The TLS analog is: a security-relevant setting (cert-validation config) is checked once, cached, and later reused for a session without re-checking it against the live config that may have changed. `Bonding.sol`'s two-phase graduation does the structural equivalent: `triggerGraduation` snapshots amounts into `PendingGraduation` (`tokensForLP`, `ltFromPair`, `lpBurned`, `unsoldBurned`) computed against the *current* state of the external, live-configurable leveraged token (LT), and `finalizeGraduation` later consumes that frozen snapshot with **no freshness check and no re-derivation** against the LT's live config (`exchangeRate()`, `minTransactionSize()`), by explicit design.

### Finding Description
`PendingGraduation` is documented as a snapshot "cached at end of phase 1, consumed by `finalizeGraduation`, deleted on success," with an explicit design note that there is intentionally "No `pendingSince` / freshness timestamp... see the exchange-rate drift between phase 1 and phase 2 note on `finalizeGraduation`": [1](#0-0) 

The LT is an externally-controlled, rebasing-priced asset whose `exchangeRate()` and `minTransactionSize()` are read live rather than validated once: [2](#0-1) 

`canGraduate` and `previewLtUntilGraduation` both re-read `IBounceLeveragedToken(info.ltAddress).exchangeRate()` live to decide whether phase-1 (`triggerGraduation`) should fire: [3](#0-2) 

Once phase 1 fires, the lifecycle moves to `Graduating`, all curve-raised real LT and the LP-reserved token allocation are parked on `Bonding` as a fixed-amount snapshot (`PendingGraduation`), and both `buy`/`sell` are blocked for that token while in this state: [4](#0-3) 

The root problem: the snapshot amounts (`ltFromPair`, `tokensForLP`, etc.) are fixed at phase-1 time, but `finalizeGraduation` is a **separate, permissionless transaction** that can be called at an arbitrary later block. In the interim, the LT — an entity the Bonding contract does not control — can change its own live-read configuration (e.g., raise `minTransactionSize()` above `ltFromPair`, or otherwise alter behavior tied to `exchangeRate()`/`baseToLtAmount`/`ltToBaseAmount`). Because the phase-1 snapshot is never re-validated or re-derived in phase 2, and there is no timestamp/staleness guard by the code's own admission, any operation in `finalizeGraduation` that re-touches the LT with the stale snapshot amount (mint/redeem/transfer sized off `ltFromPair`) can revert against the LT's *current* config even though it was valid at snapshot time. Since `PendingGraduation` is "deleted on success" only, a failing `finalizeGraduation` leaves the token stuck indefinitely in `Lifecycle.Graduating` — a state where trading is blocked (`TokenIsGraduating`) and graduation cannot complete, permanently freezing the parked curve-raised LT and the 250M-token LP allocation with no rescue path.

**Uncertainty**: I was not able to read the full body of `finalizeGraduation` (the exact LT calls it makes with the cached `ltFromPair`) before running out of tool iterations, so I cannot cite the precise line where the stale amount is reused against a live LT call. The struct's own doc comment is the strongest available evidence that this drift is a known, accepted design gap rather than a re-validated path. This would need direct inspection of `finalizeGraduation`'s body (and `_seedRebalancing`/`_pairRebalance`/`_seedDirectMint` fallbacks referenced in the rules) to confirm which specific LT call can revert on the stale snapshot.

### Impact Explanation
If confirmed, this permanently freezes: (1) all real LT raised from curve traders during phase 1 (parked on `Bonding`, never returned to traders or delivered to the pair/LP), and (2) the creator's/curve's 250M-token LP allocation, since the token can neither resume curve trading nor complete graduation. This matches the freezing-of-funds impact class explicitly in scope.

### Likelihood Explanation
Graduation is permissionless in both phases — any address can call `triggerGraduation` and, separately, any address can call `finalizeGraduation` at a later block, so the phase-1/phase-2 gap is attacker-controllable in timing. The LT's `exchangeRate`/`minTransactionSize` are explicitly documented in this codebase as externally, live-controlled values that the Bonding contract only reads, not pins. The likelihood of the gap being *reachable* is high; the likelihood of it being *exploitable to revert finalize* depends on the unverified body of `finalizeGraduation`, which is why this should be confirmed before treating it as fully proven.

### Recommendation
Add a freshness/staleness safeguard (e.g., re-derive amounts against current LT state in `finalizeGraduation`, or bound the LT's minimum-transaction check against the snapshot at trigger time with a guaranteed execution path), and/or provide an explicit recovery/retry path for `PendingGraduation` so that a transient LT-side config change cannot permanently strand curve-raised funds.

### Proof of Concept
Not fully constructible without the `finalizeGraduation` source; conceptually:
1. Trader buys push a token to `canGraduate() == true`; any address calls `triggerGraduation`, snapshotting `PendingGraduation.ltFromPair` and pulling curve-raised LT/tokens onto `Bonding`.
2. Before anyone calls `finalizeGraduation`, the LT's live-read config changes (e.g., `minTransactionSize()` rises) via `MockLeveragedToken.setMinTransactionSize` / real LT equivalent — this is an external, permissionless-to-the-LT-owner action per the "LT read live" contract design. [5](#0-4) 
3. `finalizeGraduation` is called, reuses the stale `ltFromPair` snapshot against the now-changed LT config, and (per the hypothesized unverified path) reverts.
4. The token is permanently stuck in `Lifecycle.Graduating`: `buy`/`sell` revert with `TokenIsGraduating`, and every subsequent `finalizeGraduation` retry reverts the same way, freezing the parked LT and tokens.

    ///
    ///         `exchangeRate()` is a view that doesn't settle the LT's
    ///         accrued streaming fee (only mint / redeem / agent checkpoints
    ///         do), so the USD leg can read marginally high and trip the
    ///         threshold a touch early. Bounded by the pending fee,
    ///         one-directional, and the same accepted drift class as the
    ///         launch snapshot (`_deployAndSeed`); the inline post-buy path
    ///         is unaffected (`Zap.buy`'s `mint` checkpoints in the same tx)
    ///         and LP seeding never reads the rate, so the pool still opens
    ///         at the exact curve-close price.
    ///
    ///         Supply trigger: uses live `IPair.tokenBalance()`. This IS an
    ///         `IERC20.balanceOf` read but is donation-resistant in the
    ///         opposite direction — token donations can only INCREASE the
    ///         balance, never satisfy "== 0", and the only path that drains
    ///         tokens out of the pair is the curve buy flow. Donated tokens
    ///         are unconditionally burned by `_prepareGraduationLiquidity`.
    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }

    function previewLtUntilGraduation(
        address token_
    ) external view returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return 0;
        if (info.lifecycle != Lifecycle.Curve) return 0;

        address pair = info.pair;
        uint256 realBalance = IPair(pair).tokenBalance();
        if (realBalance == 0) return 0;

        (uint256 reserveToken, uint256 reserveAsset) = IPair(pair).getReserves();

        uint256 ltUntilThreshold = type(uint256).max;
        uint256 exchangeRate = IBounceLeveragedToken(info.ltAddress).exchangeRate();
        if (exchangeRate > 0) {
            uint256 realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(token_, pair);
            uint256 thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate;
            if (realLtRaised >= thresholdRealLt) return 0;
            ltUntilThreshold = thresholdRealLt - realLtRaised;
        }

        // Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
        if (realBalance >= reserveToken) return ltUntilThreshold;

        uint256 cappedReserveToken = reserveToken - realBalance;
        uint256 cappedReserveAsset = (IPair(pair).k() + cappedReserveToken - 1) / cappedReserveToken;
        uint256 ltUntilSupply = cappedReserveAsset - reserveAsset;

        return ltUntilSupply < ltUntilThreshold ? ltUntilSupply : ltUntilThreshold;
    }
