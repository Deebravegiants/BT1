## Custody Analog Found: Missing chain-id domain separation in `SignerCapabilityOfferProofChallengeV2` (signer-capability grant is replayable across networks)

### Title
`offer_signer_capability`'s challenge struct omits `chain_id`, enabling signer-capability signature replay across Aptos networks/forks - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The external Hermez finding is a single custody invariant: an authorization signature that binds a key to a privileged capability must be scoped to the exact deployment/chain it was signed for, or it can be replayed elsewhere to hijack that capability. Aptos's `account.move` already recognizes and fixed this exact class of bug for rotation-capability delegation by adding `chain_id` to `RotationCapabilityOfferProofChallengeV2` <cite repo="AYontt/aptos-core--024" path="aptos-move/framework/aptos-framework/sources/account/account.move" start="145="153" /> [1](#0-0) , with the code comment explicitly stating "This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message." However, the sibling struct `SignerCapabilityOfferProofChallengeV2`, used to authorize `offer_signer_capability` (which grants a full `signer` for the offerer's account), was never given the same `chain_id` field [2](#0-1) .

### Finding Description
`offer_signer_capability` builds a proof challenge and verifies it purely off `sequence_number`, `source_address`, and `recipient_address`: [3](#0-2) 

The verification (`verify_signed_message`) wraps the message in `ed25519::signature_verify_strict_t`, which domain-separates only by Move `TypeInfo` (module address/name/struct name) via the `SignedMessage<MessageType>` wrapper [4](#0-3) , not by chain or network identity. This means the exact same signature bytes over `SignerCapabilityOfferProofChallengeV2{sequence_number, source_address, recipient_address}` are valid on any Aptos-compatible chain/fork/testnet that shares the same module address (`0x1::account`), the same account address, and the same sequence number — which is trivially true for freshly created accounts (`sequence_number == 0`) on two different networks.

This directly parallels the Hermez `_checkSig` bug: the signature has no chain/deployment-specific binding, so a signature intended for use on one instance (e.g., a testnet or forked chain) can be replayed on another (e.g., mainnet).

### Impact Explanation
`create_authorized_signer`, gated by this capability offer, returns a full `signer` for the offerer's account [5](#0-4) . A `signer` handle is complete custodial control: it can withdraw/transfer coins, fungible assets, and objects owned by that account, rotate keys via other capabilities, etc. If a user is convinced to sign a `SignerCapabilityOfferProofChallengeV2` "for testing" on a fork/testnet (believing it's low-stakes), the identical signature can be replayed against the same address on mainnet (or any other Aptos-derived network sharing the address/sequence-number state) to silently grant the attacker's `recipient_address` a live signer capability over the victim's real, asset-holding mainnet account — a full custody takeover, matching the exploit scenario described in the original report almost verbatim.

### Likelihood Explanation
The likelihood is nontrivial because:
- Accounts are commonly created identically (same key, `sequence_number = 0`) across mainnet/testnet/devnet or private forks, since Aptos address derivation is chain-agnostic.
- Social-engineering vectors (e.g., "sign this to test the app on our testnet fork") are the exact type the original report calls out and are a known Web3 attack pattern.
- The framework authors were clearly aware of this class of issue and patched it for `RotationCapabilityOfferProofChallengeV2`, but the fix was not applied consistently to `SignerCapabilityOfferProofChallengeV2`, indicating this is a genuine oversight rather than an intentional trust assumption.

### Recommendation
Add a `chain_id: u8` field to `SignerCapabilityOfferProofChallengeV2` (mirroring `RotationCapabilityOfferProofChallengeV2`) and populate/verify it against `chain_id::get()` in `offer_signer_capability`, exactly as already done in `offer_rotation_capability`. This closes the domain-separation gap and prevents cross-network signature replay for signer-capability grants.

### Proof of Concept
1. Alice creates account `A` on Chain X (e.g., a testnet/fork) with `sequence_number = 0`.
2. Alice is asked to sign a `SignerCapabilityOfferProofChallengeV2{sequence_number: 0, source_address: A, recipient_address: Attacker}` and calls `offer_signer_capability` on Chain X, believing it only affects the test deployment.
3. Alice's real mainnet account, derived from the same key, also has address `A` and `sequence_number = 0` (freshly funded).
4. Attacker resubmits the identical `signer_capability_sig_bytes`, `account_public_key_bytes`, and `recipient_address` to `offer_signer_capability` on mainnet — verification succeeds because the challenge bytes are chain-agnostic.
5. Attacker calls `create_authorized_signer(&attacker_signer, A)` on mainnet to obtain a full `signer` for Alice's mainnet account and drains its assets.

```text
    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
```

```text
    public fun create_authorized_signer(account: &signer, offerer_address: address): signer acquires Account {
        assert_account_resource_with_error(offerer_address, ENO_SUCH_SIGNER_CAPABILITY);
        // Check if there's an existing signer capability offer from the offerer.

    }
```
