### Title
`pending_delegator_rewards` is never decremented after being paid out as block rewards - (File: `programs/vote/src/vote_state/handler.rs`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`VoteStateV4::pending_delegator_rewards` (SIMD-0123) is incremented every time lamports are deposited via `DepositDelegatorRewards`, but across the entire codebase there is no corresponding code path that decrements it when those lamports are actually paid out to stakers as block rewards during epoch-reward distribution. This mirrors the reported bug class of an accounting accumulator being incremented on deposit but not adjusted on withdrawal/payout.

### Finding Description
`add_pending_delegator_rewards` is the only mutator for the field, and it is strictly additive: [1](#0-0) 

It is invoked from `deposit_delegator_rewards`, which transfers lamports from a source account into the vote account and then bumps the counter: [2](#0-1) 

During epoch reward calculation, `calculate_block_reward` reads `pending_delegator_rewards` to compute each stake account's proportional share of the vote account's accrued delegator rewards for that epoch, clamping the result to the current `pending_delegator_rewards` value: [3](#0-2) 

That computed `block_reward` is later credited to the stake account's lamport balance during distribution: [4](#0-3) 

I was unable to locate any code (in `handler.rs`, `vote_state/mod.rs`, `vote_processor.rs`, or the reward calculation/distribution modules) that subtracts the amount actually paid out from `pending_delegator_rewards` after distribution. Every reference to the field outside of `add_pending_delegator_rewards` is a getter, view/serialization accessor, or CLI/RPC display code — none perform a subtraction.

### Impact Explanation
If `pending_delegator_rewards` is used as the denominator/pool-size input for `calculate_block_reward` in subsequent epochs without ever being reduced by amounts already paid out, then stake accounts would continue to be paid a share of rewards that were already distributed in prior epochs, effectively re-distributing the same deposited amount multiple times. This is analogous to the reported `vaultRewardsPerWeight` bug: the "amount available to distribute" bookkeeping value is only ever incremented on deposit and never decremented on payout, causing over/duplicate payouts and understating how much of the pool has already been consumed. Because this occurs inside the bank's partitioned epoch-reward distribution path, a discrepancy here directly affects lamport accounting/capitalization consistency across the validator's reward path.

### Likelihood Explanation
This would trigger any time a `DepositDelegatorRewards` deposit is followed by more than one epoch-reward distribution cycle drawing against the same vote account — a normal, expected operational flow for SIMD-0123 rather than an edge case, so likelihood is high if the missing decrement is genuine. However, I was not able to fully trace the entire commission/collector settlement code (`load_and_reward_commission_accounts`, referenced in comments in `calculation.rs`, was not retrieved) to rule out the possibility that `pending_delegator_rewards` is reset or overwritten elsewhere as part of that flow. This gap in verification should be closed before treating the finding as fully confirmed.

### Recommendation
Decrement `VoteStateV4::pending_delegator_rewards` by the actual amount distributed as `block_reward` for a given epoch immediately after (or as part of) the distribution phase in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`, mirroring the pattern used for `vaultRewardsPerWeight` in the reported bug (update the accumulator inside the payout function, not just the deposit function). This requires also updating `handler.rs`/`vote_state/mod.rs` to expose a checked-subtract mutator analogous to `add_pending_delegator_rewards`.

### Proof of Concept
Not independently reproduced; based on static code-path analysis: `add_pending_delegator_rewards` (`programs/vote/src/vote_state/handler.rs:196-209`) is the sole mutator found via repository-wide search for `pending_delegator_rewards`, and `calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-231`) reads/clamps against it without any accompanying decrement call being located in the distribution path examined (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:239-325`). A concrete PoC (deposit rewards, run two epoch cycles, and assert total block rewards paid exceed the deposit) could not be constructed within the available exploration budget and would require running the reward-calculation test harness (e.g., extending `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`).
