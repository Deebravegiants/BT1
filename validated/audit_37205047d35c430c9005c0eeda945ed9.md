### Title
Webhook topic/shop dispatch is unauthenticated relative to the HMAC-signed body, enabling handler relabeling/cross-tenant dispatch - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Request#to_signable_string` only returns `@raw_body`, so `HmacValidator.validate` cryptographically authenticates the request body alone. `Request#topic` and `Request#shop` are read from HTTP headers that are never part of the signed content, and `Registry.process` uses these unauthenticated header values to select the handler and populate `WebhookMetadata`.

### Finding Description
The intended binding should be: `topic_authenticated_by_hmac == topic_dispatched_on`. Tracing the code: `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) returns only `@raw_body`; `Request#topic`, `Request#shop` (`lib/shopify_api/webhooks/request.rb:16-23`) come from `shopify_header`, i.e., the `X-Shopify-Topic`/`X-Shopify-Shop-Domain` HTTP headers, which are excluded from the signable string entirely. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) computes `HMAC(secret, verifiable_query.to_signable_string)` and compares to the received HMAC header — this only proves the body bytes were signed by someone holding `api_secret_key`; it says nothing about which topic or shop that signature was intended for. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) then does `@registry[request.topic]&.handler` and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`, trusting the unauthenticated header values for routing and for the `WebhookMetadata` passed to the handler. Since `api_secret_key` is shared across all shops installing the same app (not per-shop), an attacker who legitimately installs the app on their own development shop can receive a genuinely-signed webhook (any topic, e.g. `orders/create`) directly from Shopify, capturing a valid `(raw_body, hmac)` pair. They can then POST that exact body+HMAC directly to the app's public webhook receiver endpoint while substituting `X-Shopify-Topic: shop/redact` (and optionally a different `X-Shopify-Shop-Domain`). `HmacValidator.validate` still passes since `@raw_body` is unchanged. `Registry.process` looks up the `shop/redact` handler and invokes it with the attacker's chosen shop/body pairing that was never actually signed for that topic or shop. `mandatory_webhook_topic?` in `lib/shopify_api/webhooks/registry.rb` only gates `register`/`unregister`, never `process`, so it provides no protection here.

### Impact Explanation
An unprivileged attacker can cause a mandatory-compliance handler (e.g. `shop/redact`, `customers/redact`, `customers/data_request`) or any other registered handler to fire with attacker-chosen `topic`/`shop`/`body` combinations that were never actually signed together, because the HMAC only vouches for body bytes, not the header-derived routing metadata. Depending on what the host app's handler does with `WebhookMetadata#shop` and `#body` (e.g., triggering redaction/deletion routines keyed by the `shop` field from the header), this can lead to a handler being invoked for a shop/topic pairing it wasn't intended for — a cross-tenant/authentication-binding bypass at the gem's dispatch layer. Repeatable per request; the attacker only needs one genuinely-signed body from their own shop and can replay it indefinitely with arbitrary topic/shop headers.

### Likelihood Explanation
Requires the host app to expose an HTTP webhook receiver route reachable by arbitrary internet clients (the normal, documented deployment for Shopify webhooks) and to have registered a handler for the targeted topic via `Registry.add_registration`. The attacker needs no secrets — only a real shop where they can install the app to receive at least one legitimately-signed webhook body/HMAC pair, which is achievable by any developer via a free development store. Constructing and sending the forged request costs nothing beyond a normal HTTP client.

### Recommendation
Bind `topic` (and ideally `shop`) into the material that is HMAC-verified, or otherwise ensure the gem cryptographically ties the dispatched topic to the verified payload before handing off to `Registry.process`'s handler lookup — e.g., require the caller to pass the expected topic and shop separately from trusted transport data instead of trusting header values reflected back from `Request`, or document/enforce that `topic`/`shop` headers must be independently validated against the authenticated session/shop registration before dispatch.

### Proof of Concept
minitest with WebMock/Mocha under `test/webhooks/`:
1. Register a `FakeWebhookHandler` for topic `shop/redact` via `ShopifyAPI::Webhooks::Registry.add_registration(topic: "shop/redact", delivery_method: :http, path: "path", handler: handler)`.
2. Build a real HMAC over an arbitrary body: `hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)` matching `HmacValidator`'s computation, base64-encode it as `X-Shopify-Hmac-Sha256`.
3. Construct `ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: { "x-shopify-topic" => "shop/redact", "x-shopify-hmac-sha256" => hmac, "x-shopify-shop-domain" => "attacker-or-victim.myshopify.com" })` where `body` is unrelated JSON (e.g. an `orders/create`-shaped payload, not a `shop/redact` payload).
4. Call `ShopifyAPI::Webhooks::Registry.process(request)`.
5. Assert both sides of the binding: `Utils::HmacValidator.validate(request)` returns `true` (body-only authentication succeeds) while `handler_called` becomes `true` with `data.topic == "shop/redact"` and `data.body` equal to the unrelated `orders/create` payload — demonstrating the handler fires for a topic/body pairing that was never jointly signed.
