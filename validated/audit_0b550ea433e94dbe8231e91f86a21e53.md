### Title
Webhook `shop` (and `topic`) header not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The report describes a race condition where an untrusted party can substitute values that a downstream consumer treats as authenticated. Mapping this bug class onto this gem's own code, the closest reachable analog is in the webhook verification path: `ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`) values used by the handler dispatch are taken from HTTP headers that are never included in the signed bytes. This breaks the equality `bytes verified == bytes acted on`.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against `to_signable_string` using the app's `client_secret` (`api_secret_key`): [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw body: [2](#0-1) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read from HTTP headers that are entirely outside the signed payload: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC over the body, then constructs `WebhookMetadata` using the *unauthenticated* `request.shop` and `request.topic` values and hands it to the app-registered handler: [4](#0-3) 

Because the app's `client_secret` is a single shared secret used to validate webhooks for *every* shop that installs the app (not a per-shop secret), any merchant that installs the app can:
1. Trigger a legitimate webhook delivery to their own store (or otherwise obtain a body + valid HMAC pair, since they control what data exists in their own shop and can trigger events on it), giving them a `(body, hmac)` pair that is valid under the app's secret.
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain, and/or the topic header.
3. `HmacValidator.validate` still succeeds, because it only checks the body bytes, which were not altered — the equality the gem enforces is `hmac == HMAC(body)`, not `hmac == HMAC(body || shop || topic)`.
4. The handler receives `WebhookMetadata` claiming the event belongs to the victim shop, even though the body/HMAC only prove authenticity for the attacker's own shop's data.

This is exactly the pattern called out in the rules: "a field acted on but not covered by the HMAC" — `shop` and `topic` are consumed by `Registry.process`/handler dispatch (tenant routing) but never enter `to_signable_string`.

### Impact Explanation
Host applications built on this gem are expected to trust `WebhookMetadata#shop` as the tenant identifier once `HmacValidator.validate` passes (this is the documented contract — the gem returns "verified" webhook data including `shop`). Since `shop` is not bound to the signature, an attacker who is a legitimate (but low-privilege) installer of the app can forge a webhook payload that appears to originate from — and be verified for — a different merchant's shop. Depending on how the host app's handler consumes `WebhookMetadata.shop` (e.g., to look up which merchant record to update, uninstall, or process billing/order data for), this can lead to cross-tenant data corruption or cross-tenant action execution. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be an app installer able to generate a valid `(body, hmac)` pair — trivial for any shop that installs a public/multi-tenant app, since Shopify signs every real webhook it sends to that shop with the app's shared secret. No access to the app's `client_secret`, no TLS interception, and no privileged account beyond "installed the app once" is required. The gem's own verification code path (`HmacValidator.validate` + `Request#shop`/`#topic`) is the root cause, independent of any host-application misuse, because the gem exposes `shop`/`topic` as trusted fields of a "validated" `Request`/`WebhookMetadata` without binding them into the signature it checks.

### Recommendation
Include the `shop` (and ideally `topic`) values in the signable payload verified against the HMAC, or otherwise cryptographically bind them to the raw body (e.g., verify shop against a known/stored value the app already authenticated during OAuth, or require Shopify to include shop/topic in the signed body). At minimum, document that `Request#shop`/`#topic` are unauthenticated header values and must not be used as an identity/tenant boundary until independently corroborated.

### Proof of Concept
1. App with `client_secret = S` is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Shopify sends the attacker a legitimate webhook: body `B`, header `shop-domain: attacker-shop.myshopify.com`, `hmac-sha256: HMAC(S, B)`.
3. Attacker resends `POST /webhooks` with the same body `B` and `hmac-sha256` header unchanged, but sets `shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body; `HmacValidator.validate(request)` computes `HMAC(S, B)` (body unchanged) and it matches the supplied hmac — validation passes: [5](#0-4) 
5. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"`, `body: <attacker-controlled B>` — a forged, "verified" webhook for a tenant the attacker does not own.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
