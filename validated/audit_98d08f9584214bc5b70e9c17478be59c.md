## Analysis

The reported bug class is "a value that participates in a security-critical computation but is not covered by the integrity check," causing the system to trust unverified data. The strongest analog in this gem is in the webhook processing path, where the shop identity is trusted from an unauthenticated header while only the body is HMAC-covered.

### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies the *body* integrity but never binds the `shop-domain`, `topic`, or `webhook-id` headers to that signature. `Registry.process` then trusts `request.shop` (taken straight from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler, breaking the binding "HMAC-authenticated payload == shop identity acted upon."

### Finding Description
`Request#hmac`/`#to_signable_string` sign/verify only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and other header-derived fields) to construct the metadata delivered to the app's business logic: [3](#0-2) 

The `HmacValidator` itself only ever signs/verifies whatever `to_signable_string` returns — for webhooks that is exclusively the body: [4](#0-3) 

Because a single app-level `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant who legitimately installs the app (an unprivileged, credential-less action for an internet user) receives real webhook deliveries with a valid HMAC computed only over the body. That attacker-controlled shop can capture a `(raw_body, hmac)` pair from a webhook sent to their own store, then replay it against the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to point at a victim shop that also has the app installed. `HmacValidator.validate` still returns true (it never looked at the header), and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` is the victim's domain but whose `body` is attacker-controlled.

### Impact Explanation
This breaks the identity binding `shop authenticated == shop the webhook body is attributed to`. Any host application that uses `WebhookMetadata#shop` to key writes, cache invalidation, order/inventory sync, or other tenant-scoped storage (the documented and intended use of this field) can be made to apply attacker-chosen webhook payloads to another tenant's data — a cross-tenant access/data-integrity issue, which maps to the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on a store they control (a normal, unprivileged action any Shopify merchant can take) and capture one legitimate webhook body+HMAC pair, then replay it with a forged shop header. No access token, `client_secret`, or privileged account is needed — the attacker never needs the app's secret because the HMAC they replay is legitimately issued for their own installation.

### Recommendation
Bind the shop identity to the HMAC-covered payload: either include `shop-domain`/`topic`/`webhook-id` in the signable string used by `HmacValidator`, or have `Registry.process`/consuming applications independently verify that the `shop` header corresponds to a shop with an active, known session/installation before trusting `WebhookMetadata#shop` for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free/unprivileged action).
2. Shopify delivers a real webhook to the app's endpoint: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and resends an HTTP POST to the same webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` passes because it only checks `HMAC(client_secret, B) == H`, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`.
5. `handler.handle` receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to process attacker-controlled data under the victim tenant's identity.
