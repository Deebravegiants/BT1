This confirms the claim: `Transfer::transfer` in both `pallet_nfts` and `pallet_uniques` (`Self::do_transfer(...)`) performs the storage change but any owner-check is delegated entirely to the closure argument, which `NonFungiblesTransferAdapter::transfer_asset` passes as nothing at all — the adapter never converts `from` and never enforces ownership before calling `Assets::transfer`. This matches exactly what the report claims: the `withdraw_asset` path is safe (passes `Some(&who)` into `Assets::burn`, which is checked against `d.owner` in `do_burn`'s closure), but the `transfer_asset` path has no analogous check because the `nonfungibles::Transfer::transfer` trait signature has no owner parameter at all, and the adapter code never independently verifies `from` against `Assets::owner(&class, &instance)`. The `Matcher::matches_nonfungibles` call only validates asset-id encoding, not ownership, so this doesn't block the exploit. The XCM executor's `TransactAsset::transfer_asset` default implementation dispatches straight to `internal_transfer_asset`/the transactor's overridden `transfer_asset`, with no fallback to withdraw+deposit unless `AssetNotFound`/`Unimplemented` is returned, confirming the report's description of how `TransferAsset`/`internal_transfer_asset` reach this vulnerable code path.

Audit Report

## Title
NFT theft via missing owner check in `NonFungiblesTransferAdapter::transfer_asset` (used by `NonFungiblesAdapter::transfer_asset`/`internal_transfer_asset`) - ([File: polkadot/xcm/xcm-builder/src/nonfungibles_adapter.rs])

## Summary
`NonFungiblesTransferAdapter::transfer_asset` never validates that the `from` location is the current owner of the `(class, instance)` NFT before calling `Assets::transfer`, because neither the adapter nor the underlying `nonfungibles::Transfer::transfer` trait method accepts or checks an owner/`from` parameter. This is inconsistent with `withdraw_asset`, which correctly threads `Some(&who)` into `Assets::burn` and lets the pallet enforce the check.

## Finding Description
`NonFungiblesTransferAdapter::transfer_asset` at [1](#0-0)  matches `what` to `(class, instance)`, converts only the `to` location to a destination account, and calls `Assets::transfer(&class, &instance, &destination)` — the `from` parameter is never converted or compared to the item's current owner. This contrasts with `withdraw_asset`, which converts `who` and passes `Some(&who)` into `Assets::burn` at [2](#0-1) , letting the pallet enforce ownership in its `burn` implementation.

The trait `nonfungibles::Transfer::transfer` itself has no owner-check parameter, confirmed in both concrete pallet implementations: `pallet_uniques`'s `Transfer::transfer` calls `Self::do_transfer(collection.clone(), *item, destination.clone(), |_, _| Ok(()))` with a no-op authorization closure [3](#0-2) , and `pallet_nfts`'s `Transfer::transfer` similarly calls `Self::do_transfer(*collection, *item, destination.clone(), |_, _| Ok(()))` [4](#0-3) . By contrast, both pallets' `Mutate::burn` implementations explicitly check `d.owner != check_owner` inside the closure passed to `do_burn` [5](#0-4) [6](#0-5) . This proves the ownership-check asymmetry is real: `burn` enforces it, `transfer` does not — at either the adapter layer or the pallet layer.

`NonFungiblesAdapter`'s `TransactAsset::transfer_asset` forwards directly to `NonFungiblesTransferAdapter::transfer_asset` [7](#0-6) . The generic `TransactAsset::transfer_asset` default implementation in the executor traits calls `internal_transfer_asset` first and only falls back to withdraw+deposit on `AssetNotFound`/`Unimplemented` [8](#0-7) ; since `NonFungiblesAdapter` overrides `transfer_asset` directly (not merely `internal_transfer_asset`), any caller invoking `transfer_asset` on this transactor bypasses the safe withdraw-path ownership check entirely.

## Impact Explanation
Any account able to trigger the XCM `TransferAsset` instruction (or any other executor code path calling `TransactAsset::transfer_asset` on a configuration using `NonFungiblesAdapter`/`NonFungiblesTransferAdapter`) can move an NFT owned by a different account to an arbitrary destination, without ever owning or being authorized for that item — a direct, unauthorized reassignment of a non-fungible asset's ownership. This is a genuine broken invariant (ownership must be checked on transfer) in in-scope XCM asset-transactor code.

## Likelihood Explanation
Exploitability requires only that a runtime configures `NonFungiblesAdapter` (or the bare `NonFungiblesTransferAdapter`) as its `AssetTransactor`, that `Matcher::matches_nonfungibles` accepts attacker-chosen `(class, instance)` ids (a normal asset-id matcher, not an ownership check), and that the attacker can get a `TransferAsset` (or equivalent) XCM instruction executed, e.g. via `pallet_xcm::execute`. No privileged extrinsic, signature forgery, or governance action is required — a normal user-originated XCM program naming someone else's NFT suffices. The vulnerability is present in the SDK's reusable adapter code itself, not merely a misconfiguration mistake by a downstream chain, though it does require the affected chain to actually route NFTs through `NonFungiblesAdapter`.

## Recommendation
In `NonFungiblesTransferAdapter::transfer_asset`, convert `from` via `AccountIdConverter::convert_location` and verify it equals `Assets::owner(&class, &instance)` before calling `Assets::transfer`, returning `XcmError::NoPermission` otherwise. Better yet, extend `nonfungibles::Transfer::transfer` to accept a `maybe_check_owner: Option<&AccountId>` parameter (mirroring `Mutate::burn`), and update `do_transfer` in both `pallet_nfts` and `pallet_uniques` to enforce the check via the closure, so ownership is verified at the pallet level regardless of caller.

## Proof of Concept
1. Mint an NFT `(class=1, instance=42)` to `owner_account` via `Assets::mint_into`.
2. Construct an `attacker_location` (distinct from `owner_account`'s location) and a `beneficiary_location`.
3. Call `<NonFungiblesAdapter<...> as TransactAsset>::transfer_asset(&nft_asset, &attacker_location, &beneficiary_location, &XcmContext::with_message_id([0; 32]))`.
4. Observe the call returns `Ok(...)` and `Assets::owner(&1, &42)` now equals the beneficiary account — proving the item was moved away from `owner_account` without any ownership check ever firing, since `from` (`attacker_location`) is unused throughout `transfer_asset`.
