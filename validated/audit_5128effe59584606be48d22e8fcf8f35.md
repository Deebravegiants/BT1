### Title
`exportPrivate` truthy coercion bypasses default private-key nondisclosure in `keychain.sodium.getKeysFromSeed` - (File: features/keychain/module/crypto/sodium.js)

### Summary
`getKeysFromSeed` and its internal helper `cloneKeypair` gate private-key/secret disclosure with a loose truthiness check (`exportPrivate ? ... : null`) instead of a strict `exportPrivate === true` check. Any attacker-controlled value that is JS-truthy but not the literal boolean `true` (e.g. the string `'false'`, a non-empty object, or a non-zero `BigInt`) will cause `sign.privateKey`, `box.privateKey`, and `secret` to be returned instead of `null`.

### Finding Description
`getKeysFromSeed` in [1](#0-0)  derives `box`, `sign`, and `secret` from the unlocked seed via `getSodiumKeysFromIdentifier`, then decides whether to include private material solely based on the truthiness of `exportPrivate`:
```
return {
  box: cloneKeypair({ keys: box, exportPrivate }),
  sign: cloneKeypair({ keys: sign, exportPrivate }),
  secret: exportPrivate ? cloneBuffer(secret) : null,
}
```
`cloneKeypair` repeats the same pattern [2](#0-1) :
```
const cloneKeypair = ({ keys, exportPrivate }) => {
  return {
    publicKey: cloneBuffer(keys.publicKey),
    privateKey: exportPrivate ? cloneBuffer(keys.privateKey) : null,
  }
}
```
Because JS truthy coercion treats any non-empty string, non-zero number/BigInt, or object/array as truthy, a caller that supplies `exportPrivate: 'false'`, `exportPrivate: {}`, or `exportPrivate: 1n` (rather than a strict boolean `false`) will get private key/secret material back, even though the intent of the caller (and the API contract implied by tests such as `features/keychain/module/__tests__/lock-private-keys.test.js`) is that private material should only be exported when `exportPrivate: true` is explicitly and deliberately passed. This function/API is exposed as `keychain.sodium.getKeysFromSeed` / `getSodiumKeysFromSeed` and reachable from `createInstance()`/`createEncryptor()` in the same file [3](#0-2) , and from `keychain.sodium` on the `Keychain` class [4](#0-3) .

The only guard on this path is the seed lock check performed inside `getPrivateHDKey`/`#assertPrivateKeysUnlocked` [5](#0-4) , which only enforces that the seed is *unlocked* — it does not perform any type validation or strict-boolean enforcement on `exportPrivate`. There is no schema/type coercion guard in `sodium.js` or `keychain.js` that normalizes `exportPrivate` to a strict boolean before the truthy check is applied.

### Impact Explanation
If an intermediate layer (RPC/dapp-bridge argument marshalling, JSON round-tripping through structured clone, or a caller that forwards a non-boolean flag) ever passes a non-boolean-but-truthy `exportPrivate` value to `getKeysFromSeed`/`getSodiumKeysFromSeed`, the function will silently disclose `sign.privateKey`, `box.privateKey`, and the seed-derived `secret` — private key material — instead of respecting the intended "export only public data" default. This is a private key/secret material disclosure bug matching Hydra's high-severity "private key disclosure" impact category, since the exported keys/secret can be used for signing, box decryption, or secret-box decryption on behalf of the wallet.

### Likelihood Explanation
Exploitability strictly requires (a) the seed already unlocked (a stated precondition of the question, not something the attacker needs to bypass), and (b) a code path that forwards an unsanitized non-boolean truthy value for `exportPrivate` into this function. The vulnerable comparison (`exportPrivate ? ... : null` instead of `exportPrivate === true`) is present and reachable in the current code exactly as described, so any caller (internal or external) that fails to coerce this argument to a strict boolean will trigger the unintended disclosure. I was not able to fully trace whether the RPC/dapp-bridge layer that exposes `keychain.sodium.getKeysFromSeed` to external callers performs its own strict-boolean validation/coercion before invoking this function (that layer's code was not found within the indexed portion of the repo I could inspect); this is the main remaining uncertainty affecting real-world reachability from an external, unprivileged RPC caller.

### Recommendation
Change both truthy checks to strict boolean comparisons, e.g. `exportPrivate === true`, in `cloneKeypair` and `getKeysFromSeed` in `features/keychain/module/crypto/sodium.js`, and add an explicit `assert(typeof exportPrivate === 'boolean', ...)` (or default/normalize non-boolean input to `false`) at the entry point of `getKeysFromSeed` to prevent any type-coercion bypass regardless of what upstream callers pass.

### Proof of Concept
Unit test to add to `features/keychain/module/__tests__/sodium.test.js`:
```js
it('should NOT export private key/secret for truthy-but-non-boolean exportPrivate', async () => {
  const keychain = await createKeychain({ seed })
  const keyId = createKeyIdentifierForExodus({ exoType: 'FUSION' })

  for (const value of ['false', 0n === 0n ? 1n : 1n, {}, [], 'no']) {
    const result = await keychain.sodium.getKeysFromSeed({ seedId, keyId, exportPrivate: value })
    expect(result.sign.privateKey).toBeNull()
    expect(result.box.privateKey).toBeNull()
    expect(result.secret).toBeNull()
  }

  // sanity: explicit boolean true still exports
  const exported = await keychain.sodium.getKeysFromSeed({ seedId, keyId, exportPrivate: true })
  expect(exported.sign.privateKey).not.toBeNull()
})
```
Expected (current buggy) behavior: the loop assertions fail because `sign.privateKey`/`box.privateKey`/`secret` are non-null for truthy-but-non-boolean inputs, demonstrating the disclosure. After applying the recommended `=== true` fix, the test passes.
