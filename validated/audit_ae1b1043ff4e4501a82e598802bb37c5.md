Audit Report

## Title
Unvalidated hex-prefix length assumption in `normalizeHex` causes crash via crafted `workflowID` - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

## Summary
`validateHexInput` (used by `validateWorkflowID`) only checks that `len(workflowID) <= 66` and that the string (after stripping an optional `"0x"` prefix) is valid hex; it does not require the `"0x"` prefix to be present. If a client submits a 66-character lowercase hex string with no `"0x"` prefix, it passes validation. `normalizeHex`, called later from `resolveWorkflowID`, computes `expectedHexLength := length - 2` (64) and pads with `strings.Repeat("0", expectedHexLength-len(hexStr))`. Since the string had no `"0x"` to strip, `len(hexStr)` remains 66, producing a negative repeat count (`64-66=-2`), which panics Go's `strings.Repeat`.

## Finding Description
The code path is exactly as described: `HandleUserTriggerRequest` → `validatedTriggerRequest` → `validateTriggerParams` → `validateWorkflowFields` → `validateWorkflowID`/`validateHexInput` for validation, then `resolveWorkflowID` → `normalizeHex` for usage. [1](#0-0) [2](#0-1) [3](#0-2) 

A 66-character lowercase-hex `workflowID` without `"0x"` prefix passes `validateHexInput` (`len(input) > expectedLength` is false since 66 is not `>` 66; `hex.DecodeString` succeeds on the even-length hex string), then reaches `normalizeHex`, where `strings.TrimPrefix` is a no-op, `expectedHexLength-len(hexStr)` evaluates to `-2`, and `strings.Repeat("0", -2)` panics with `"strings: negative Repeat count"`. This is a genuine, reachable, unauthenticated (pre-`authorizeRequest`) code defect confirmed by direct code reading.

However, the impact claim in the submission (full daemon/process crash, DoS of the entire gateway) is not substantiated. `HandleJSONRPCUserMessage` in `http_handler.go` calls `h.triggerHandler.HandleUserTriggerRequest` synchronously within the gateway's per-request message-handling path [4](#0-3) . Go's standard `net/http` server (and typical websocket/JSON-RPC dispatch loops built on top of it) recovers panics per request/connection rather than crashing the whole process; I was unable to conclusively verify from the indexed code whether a panic here propagates only to the requesting connection/goroutine (causing a single failed request or dropped connection) or whether it would take down the entire gateway process. No explicit `recover()` was found guarding this specific call path in the reachable source, but this alone doesn't prove a full-process crash — it depends on the goroutine/dispatch structure around message handling (e.g., `multihandler.go`, `wsserver.go`), which I could not fully trace within the available tool budget.

## Impact Explanation
At minimum, this is a real logic bug that can cause a panic reachable by an unauthenticated HTTP-trigger client, mapping to a denial-of-service class impact if the panic is not recovered at a higher level and crashes the node process. The severity is bounded by significant uncertainty on the blast radius (single request failure vs. full process crash), which the original report itself flags as needing verification and does not resolve.

## Likelihood Explanation
The crafted input (66 lowercase hex characters without `0x` prefix) is trivial to construct and requires no privileges — only the ability to send a `workflows.execute` JSON-RPC request to the gateway. Reachability of the vulnerable code without authentication (since `authorizeRequest` runs after `resolveWorkflowID`) is confirmed by direct reading of `HandleUserTriggerRequest`.

## Recommendation
In `normalizeHex`, guard against `len(hexStr) > expectedHexLength` before calling `strings.Repeat`, returning an error/user error instead of panicking. Additionally, tighten `validateHexInput` to require a `"0x"` prefix explicitly (or normalize consistently) so validation and later padding logic share the same assumptions.

## Proof of Concept
Send a `workflows.execute` JSON-RPC request to the gateway with:
```json
{
  "jsonrpc": "2.0",
  "id": "poc-1",
  "method": "workflows.execute",
  "params": {
    "workflow": { "workflowID": "00000000000000000000000000000000000000000000000000000000000001" },
    "input": {}
  }
}
```
This is 66 lowercase hex characters with no `"0x"` prefix. It passes `validateHexInput` and then panics in `normalizeHex` via `strings.Repeat("0", -2)`. A Go unit test directly calling `normalizeHex("00000000000000000000000000000000000000000000000000000000000001", 66)` reproduces the panic deterministically and is the most reliable way to confirm the bug without needing to determine whether the surrounding server infrastructure recovers it.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

func (h *httpTriggerHandler) validateWorkflowID(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	if err := validateHexInput(workflowID, workflowIDLength); err != nil {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflowID "+err.Error(), callback)
		return errors.New("workflowID " + err.Error())
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
