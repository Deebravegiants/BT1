### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop that a webhook belongs to purely from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw body only. The tenant-identifying field (`shop`) is therefore never bound by the cryptographic check that gates whether the webhook is trusted.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines its signable content as the raw JSON body alone: [1](#0-0) [2](#0-1) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` header without any relation to the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` header value — it never touches `shop`: [4](#0-3) 

`Registry.process` checks this HMAC and then immediately trusts `request.shop` as the tenant identifier passed to the app's webhook handler: [5](#0-4) 

The identity binding this breaks is: `shop attributed to the HMAC-verified payload == shop header value`, when the actual HMAC only proves `body == body used to compute hmac`. Anyone able to produce a body+hmac pair that is valid for the app's secret (e.g., a genuine webhook delivery captured off their own store) can pair it with an arbitrary `shopify-shop-domain` header value, and `Registry.process` will still consider the HMAC check passed and hand the handler a `WebhookMetadata` claiming the payload is for a different shop.

### Impact Explanation
This breaks the shop/tenant boundary of the gem's webhook processing: an attacker who can replay/re-post a genuinely-signed webhook body (for instance one captured in transit, from logs, or forwarded by a proxy/CDN in front of the app's webhook endpoint) can relabel it as belonging to any other shop simply by changing an unauthenticated header. Downstream app logic that trusts `WebhookMetadata#shop` for tenant-scoped writes (e.g., `customers/redact`, `shop/redact`, order/product updates) can be tricked into applying another merchant's webhook payload to the wrong shop's records — a cross-tenant data integrity issue.

### Likelihood Explanation
Exploitation requires the attacker to already possess a validly-HMAC'd body for the target app (not the app's `client_secret` itself), which is a meaningfully lower bar than credential theft, and the header value is trivially attacker-controlled since headers are outside the signed payload by construction. This aligns with the report's underlying bug class (a security-relevant field checked out-of-band from the value that is actually integrity-protected).

### Recommendation
Bind the shop identity to the signature: include `shop` (and ideally `topic`/`webhook_id`) inside `to_signable_string`, or require the caller-supplied `shop` to be cross-checked against a shop known to have installed the app (e.g., matched against an existing session) rather than trusted solely from the header before invoking the handler.

### Proof of Concept
1. Capture a legitimately Shopify-signed webhook `raw_body` + `hmac` header pair delivered to the app (e.g., via a MITM-capable proxy positioned in front of the webhook endpoint, or a webhook forwarding/logging tool).
2. Re-send the same `raw_body` and `hmac` header to the app's webhook endpoint, but replace `shopify-shop-domain` with a different (victim) shop's domain.
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:12-31` succeeds because it only checks `raw_body` against `hmac`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds to invoke the handler with `WebhookMetadata.new(shop: request.shop, ...)`, attributing the payload to the attacker-chosen `shop` value.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
