## Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only checks that the body's HMAC matches, so any attacker who possesses one valid `(raw_body, hmac)` pair can replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a different, victim shop, and the signature check will still pass.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` field [1](#0-0) . For webhook requests, `to_signable_string` is defined to return only `@raw_body`, never the headers [2](#0-1) . Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers with no cryptographic binding to the HMAC [3](#0-2) .

`Registry.process` relies on `Utils::HmacValidator.validate(request)` to authenticate the request, then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` dispatched to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e. the shop attributed to the event must be part of what the HMAC authenticates. Instead the gem only enforces `hmac == HMAC(secret, body)`, leaving `shop` (and `topic`/`webhook_id`) completely unauthenticated. An attacker who can obtain any single valid `(body, hmac)` pair — for example by triggering a webhook on their own installed shop, which Shopify will deliver with a correctly computed HMAC over that body — can POST that exact body/HMAC combination to the app's public webhook endpoint while supplying an arbitrary `X-Shopify-Shop-Domain` header naming a different, victim shop. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: webhook events processed by the app can be misattributed to any shop the attacker names, without the attacker ever needing the app's `client_secret`. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up/update per-shop records, sync inventory, or trigger side effects keyed by shop), this enables cross-tenant data corruption or state confusion — an attacker can inject arbitrary webhook payloads that are processed as if they originated from a shop they do not own or operate.

### Likelihood Explanation
Webhook receiver endpoints are, by design, public HTTP endpoints with no other authentication besides the HMAC (that's the entire point of `HmacValidator`). Any user with a free/trial Shopify store can install the target app, trigger a webhook event on their own store, capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair (e.g., via their own logging/proxy since it's their own request), and replay it to the same public endpoint with a modified shop header. No secrets, tokens, or privileged access are required — only the ability to generate one legitimate webhook for any shop and to send arbitrary HTTP requests to the app's known webhook URL.

### Recommendation
Bind `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop domain to the payload before trusting it. Since Shopify's webhook HMAC scheme only signs the raw body, the header fields cannot retroactively be made part of that signature; instead, the app-facing API should either:
- Require the caller to independently correlate `webhook_id`/`shop` against a shop that has an active, verified session/install record before acting on the payload, and document this requirement clearly, and/or
- Cross-check the `shop` header against the `body`'s own embedded shop identifiers where the topic payload includes one (many Shopify webhook payloads include shop-identifying fields), rejecting mismatches.

At minimum, the library should document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be trusted for authorization decisions without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `orders/create`).
2. Shopify delivers the webhook to the app's public endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and a JSON body.
3. Attacker captures the exact `raw_body` and `X-Shopify-Hmac-Sha256` value (trivial, since it is their own webhook to their own server/logging proxy).
4. Attacker sends a new HTTP POST to the same app endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` returns the unchanged `raw_body` [2](#0-1) ; `Utils::HmacValidator.validate` recomputes the same HMAC and returns `true` [5](#0-4) .
6. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [4](#0-3) , causing the app to process the attacker's forged payload as if it belonged to the victim shop.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
