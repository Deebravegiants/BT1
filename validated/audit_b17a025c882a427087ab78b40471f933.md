### Title
BSC consensus verifier accepts finality proofs one vote short of true 2/3 supermajority - ([File: modules/consensus/bsc/verifier/src/lib.rs])

### Summary
The BSC light-client header verifier's participation check rejects only when `participant_count < (2 * validator_count) / 3`, i.e. it *accepts* any `participant_count >= floor(2N/3)`. Every other consensus client in this codebase (BEEFY, sync-committee, Pharos) enforces the stricter `>= floor(2N/3) + 1` bound. This is the same class of bug as the reported off-by-one/boundary miscalculation in `SimplePriceFeedStrategy` — a boundary condition that is one unit weaker than intended, silently accepting an input set that should have been rejected.

### Finding Description
`verify_bsc_header` in `modules/consensus/bsc/verifier/src/lib.rs` computes participation as:

```rust
let participant_count = validators_bit_set
    .iter()
    .take(current_validators.len())
    .filter(|bit| **bit)
    .count();
if participant_count < ((2 * current_validators.len()) / 3) {
    Err(Error::NotEnoughParticipants)?
}
``` [1](#0-0) 

This accepts `participant_count == floor(2N/3)` exactly, which is **not** a supermajority (`> 2/3 * N`), whereas the codebase's other three consensus clients all require the stricter `>= floor(2N/3) + 1` bound:

- BEEFY: `len >= ((2 * total) / 3) + 1` [2](#0-1) 
- Sync-committee: rejects when `< ((2 * committee_size) / 3) + 1` [3](#0-2) 
- Pharos: `required = (self.total_stake * 2 / 3) + 1` [4](#0-3) 

For example, with 21 validators (as used in this file's own unit tests), `floor(2*21/3) = 14`. The BSC check accepts `participant_count == 14`, but the strict BFT supermajority bound (`>2/3`) requires 15. The existing test `rejects_too_few_in_range_participants` only exercises 10-of-21 (below even the weaker 14 threshold), so it does not catch this boundary gap; there is no test asserting rejection at exactly 14-of-21.

### Impact Explanation
A missing "+1" in the quorum threshold means a validator/attacker coalition controlling only exactly `floor(2N/3)` of BSC's validator set (one less signer than a true supermajority) can produce a header update, `target_header`/`source_header` finality pair, and vote-address bitset that `verify_bsc_header` will accept as valid. Since this consensus client feeds `IntermediateState`/state commitments into ISMP's cross-chain state verification pipeline, a forged/insufficiently-attested BSC header could let an attacker supply unsound state commitments, enabling forged message delivery, unauthorized state proofs, or double-spend-style token bridge mint/relay actions sourced from BSC — a concrete path to fund loss or a route delivering forged messages, matching the acceptance criteria for unsound state commitment / forged message delivery.

### Likelihood Explanation
Exploitability requires colluding validators (or a compromised subset) controlling exactly one vote below the standard `2N/3+1` bound to construct a header/vote-set meeting `>= floor(2N/3)` but `< floor(2N/3)+1`. This is a much smaller bar than acquiring an actual `2N/3+1` supermajority, and any relayer submitting the resulting `BscClientUpdate` (an untrusted, permissionless action) would have it accepted by the on-chain/off-chain verifier. The comment in the code claims this matches BSC's own Parlia consensus threshold (`2/3`), but Parlia's actual finality rule requires a **strict majority greater than** 2/3 of validators (`> 2N/3`), not `>= floor(2N/3)`; as written the Rust implementation is weaker by exactly one required signer versus the intended BFT bound and versus the codebase's other consensus clients.

### Recommendation
Change the participation check to require strict supermajority consistent with the rest of the codebase:
```rust
if participant_count < ((2 * current_validators.len()) / 3) + 1 {
    Err(Error::NotEnoughParticipants)?
}
```
Add a unit test asserting rejection at exactly `floor(2N/3)` participants (e.g., 14-of-21) and acceptance only at `floor(2N/3)+1` (15-of-21), mirroring the sync-committee test pattern (`rejects_under_threshold_participants` / `accepts_exactly_threshold_participants`).

### Proof of Concept
1. Configure a BSC light client instance tracking a validator set of `N = 21`.
2. Construct (or have a colluding subset of) exactly 14 validators sign a `BscClientUpdate` header pair satisfying the adjacency/vote-data checks.
3. Set the corresponding 14 bits in the `vote_address_set` bitvector, leaving the rest unset.
4. Submit the update via `verify_bsc_header`. Because `participant_count (14) < floor(2*21/3) (14)` is `false`, the participation check passes, and (assuming the other checks — vote-data hash match, non-consecutive finalization check — are also satisfiable by the colluding set) the update is accepted despite only 14/21 (66.6%, not a true 2/3+1 supermajority of 15/21) validators having signed.
