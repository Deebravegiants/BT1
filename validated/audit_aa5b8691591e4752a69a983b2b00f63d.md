### Title
Webhook `shop-domain` and `topic` headers are trusted for dispatch but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (invoked from `Registry.process`) verifies **only the request body bytes**. The `shop-domain`, `topic`, and `webhook-id` values are read straight from HTTP headers via `shopify_header`, are never included in the signed material, and are then trusted by `Registry.process` to route the request and to populate `WebhookMetadata` (`shop:`, `topic:`, `webhook_id:`) that is handed to the app's handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` define the bytes that `HmacValidator.validate_signature` recomputes and constant-time-compares against the `X-Shopify-Hmac-Sha256` header: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` only - it does not fold in `shop-domain`, `topic`, or `webhook-id`: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.topic` (to pick the handler) and `request.shop` (passed into the handler's metadata) - both of which come from headers outside the signed scope: [4](#0-3) 

The binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_(shop, topic, webhook_id)_used_for_dispatch`

but the actual implementation only enforces:
`hmac_signed_bytes == raw_body`

so `shop` and `topic` (and `webhook_id`) are free variables an attacker can set independently of the signature.

### Impact Explanation
Any entity capable of installing the app on a shop (an ordinary, unprivileged merchant/attacker - no `api_secret_key` needed) legitimately receives real webhook deliveries for their own shop, each with a valid HMAC over the body. Because the signature covers only the body, that attacker can replay the exact same raw body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers. The gem will still report the HMAC as valid (`Utils::HmacValidator.validate(request)` passes), and `Registry.process` will call the registered handler for the *attacker-chosen* topic with `shop: request.shop` set to the *attacker-chosen* shop domain, while the JSON body content is unrelated to that identity. This causes the host application (which trusts `WebhookMetadata#shop`/`#topic` for tenant-scoped persistence, GDPR redaction routing, etc.) to attribute or apply data belonging to one merchant under another merchant's identity - a cross-tenant integrity breach reachable purely by an unprivileged app-installing party with no credential leakage or privileged access required.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on an attacker-controlled shop to legitimately receive a webhook (any topic delivered to that shop) with its valid signature, and (2) POSTing that same body/HMAC to the app's public webhook endpoint with modified `shop-domain`/`topic` headers. No secret material is needed since the attacker reuses a signature Shopify already produced for them; they never need to compute a new HMAC. This is straightforward for anyone who can install the app, making likelihood high wherever a host app relies on this gem's `WebhookMetadata#shop`/`#topic` without independently re-deriving those values from validated data.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the signed material verified against the HMAC, or otherwise cryptographically bind them to the raw body (e.g., recompute/verify against `Digest.hexencode` over a canonical string containing all of `topic`, `shop`, `webhook_id`, and `raw_body`) before they are used for dispatch in `Registry.process`. At minimum, document loudly that `Request#shop`/`#topic`/`#webhook_id` are **not** authenticated by the HMAC check and must not be trusted for tenant-identification without additional verification (e.g., cross-checking against the shop's known session/access token).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid signature over `B` computed with the app's shared secret) plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays an HTTP POST to the app's webhook controller with:
   - Body: the same bytes `B`
   - Header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it only signs `B`)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic: shop/redact` (forged, or any topic with a registered handler)
3. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) and matches `H` → validation succeeds.
4. `Registry.process` dispatches to the handler registered for the forged topic and constructs `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to act on `victim-shop.myshopify.com` using attacker-supplied body content it never authorized.         def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
