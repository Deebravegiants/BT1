This confirms `pallet-assets` does not override the default `fungibles::Mutate::transfer` from `substrate/frame/support/src/traits/tokens/fungibles/regular.rs`, and its `decrease_balance`/`increase_balance` (`substrate/frame/assets/src/impl_fungibles.rs:195-217`) are called by that default implementation with `BestEffort` precision on debit — meaning the default `transfer` trait method used by `Pallet::mint`/`Pallet::redeem` genuinely reports the nominal requested `amount` rather than the amount actually moved, exactly as the claim describes.

Audit Report

## Title
PSM pallet mints internal-asset debt based on nominal transfer amount without verifying actual reserve credit, enabling insolvency for non-exact-transfer external assets - (File: `substrate/frame/psm/src/lib.rs`)

## Summary
`Pallet::mint` and `Pallet::redeem` in the custom `pallet-psm` discard the `Balance` returned by `T::Fungibles::transfer(...)` and instead update `PsmDebt`/mint/burn amounts using the pre-computed nominal `effective_external`/`internal_net` values. Because `T::Fungibles` is a generic `fungibles::Mutate` bound and the crate's own default `transfer` implementation performs debits with `BestEffort` precision while still returning the *requested* amount, any external-asset backend that can legitimately deliver less than the requested amount (fee-on-transfer, deflationary, dust-shaving, or foreign/bridged adapters) can desynchronize `PsmDebt` bookkeeping from the real reserve balance in `psm_account`.

## Finding Description
In `mint` (`substrate/frame/psm/src/lib.rs:743-756`), the pallet transfers `effective_external` from the user to `psm_account`, then unconditionally mints `internal_to_user` and records `PsmDebt` increase by `internal_equivalent`, all derived from the pre-transfer computed amount, not from the actual value moved into the reserve: [1](#0-0) . The symmetric pattern exists in `redeem`, where `external_out` is transferred out of `psm_account` and debt/burn accounting is finalized independently of transfer's actual effect: [2](#0-1) .

`T::Fungibles` in this pallet's `Config` is bound only by the generic `fungibles::Mutate` trait, `FungiblesMetadataInspect`, and `FungiblesRolesInspect` — it is not bound to any specific pallet implementation: [3](#0-2) . The crate's default `Mutate::transfer` implementation debits the source with `BestEffort` precision and unconditionally returns the *requested* `amount` rather than what was actually credited: [4](#0-3) .

Critically, I confirmed that `pallet-assets` — the concrete implementation most likely used for `T::Fungibles` in a real runtime — does **not** override this default `transfer` method with its own exact-transfer implementation; its `impl_fungibles.rs` only implements `Unbalanced::decrease_balance`/`increase_balance` (both called by the generic default `transfer`), `Mutate` hooks (`done_mint_into`, `done_burn_from`, `done_transfer`), `Balanced`, `Create`, `Destroy`, metadata, approvals, and roles traits — no bespoke `transfer` is present: [5](#0-4) . This means `pallet-assets`'s own `decrease_balance` is invoked with `precision == BestEffort` whenever the generic default `transfer` is used, and the caller (PSM) has no way to detect a shortfall from the `Result<Balance, DispatchError>` return value, since it is discarded via `?`.

## Impact Explanation
If `psm_account` receives less than `effective_external` (via a `T::Fungibles` implementation — pallet-assets-based or otherwise — that permits partial/best-effort debits, dust rounding, or fee-on-transfer semantics), `PsmDebt` will overstate the actual reserve backing that external asset. Since `internal_to_user` is minted in full regardless of the shortfall, the internal asset's aggregate claim against the PSM instance can exceed real backing. `redeem`'s defensive check (`reserve < external_out` → `Error::Unexpected`, `substrate/frame/psm/src/lib.rs:851-855`) only prevents any single over-draw once the deficit already exists; it does not prevent the deficit from accumulating, and ultimately blocks the last redeemers from redeeming their full claim — an insolvency for that PSM instance's external-asset reserve. This matches an in-scope Polkadot SDK pallet-level accounting/solvency defect, not a purely theoretical concern, given the pattern is directly reachable via the pallet's own generic trait bound and default trait method behavior.

## Likelihood Explanation
`mint`/`redeem` are permissionless, signed extrinsics reachable by any unprivileged user on every call — no governance or privileged action is needed to trigger the vulnerable code path itself: [6](#0-5) . The only precondition is that a PSM instance's `T::Fungibles` binding (chosen by the runtime integrator, or an external asset approved via `add_external_asset`) does not guarantee exact-amount transfers. This is a realistic risk for a pallet explicitly designed to be asset-agnostic over `T::Fungibles`, and is exacerbated by the fact that even the "standard" `pallet-assets` implementation relies on the generic default `transfer` (BestEffort debit, exact-amount return), so the guarantee the PSM pallet implicitly relies on is not actually enforced by the trait system or by `pallet-assets` itself.

## Recommendation
1. In `mint`, capture and use the actual `Balance` returned by `T::Fungibles::transfer(...)` (converted back through `external_to_internal`) to compute `internal_equivalent`/`internal_to_user`/`PsmDebt` increments, instead of relying on the pre-computed `effective_external`.
2. Symmetrically in `redeem`, verify the amount actually delivered by the outgoing transfer matches `external_out` before finalizing debt/burn accounting, or reconcile any shortfall against the caller instead of silently mutating pool-wide debt.
3. Add an explicit "exact-transfer" invariant/documentation requirement for any `T::Fungibles` implementation used with PSM (or add a runtime-level assertion/reject path in `add_external_asset`) so integrators cannot unknowingly wire in a non-exact fungibles backend.

## Proof of Concept
1. Configure a PSM instance's `T::Fungibles`/external asset such that `transfer(who, psm_account, X, Preservation::Expendable)` returns `Ok(X)` per the default trait contract (`substrate/frame/support/src/traits/tokens/fungibles/regular.rs:366-386`) but only actually credits `psm_account` with `X - δ` due to `BestEffort` debit/dust handling (achievable with any `decrease_balance`/`increase_balance` pair that isn't perfectly symmetric, e.g. a foreign-asset or fee-bearing adapter).
2. Call `Psm::mint(origin, internal_asset, external_asset, X, max_fee)`; the pallet computes `effective_external = X` and mints `internal_to_user` and increases `PsmDebt` by the full `internal_equivalent`, while `psm_account`'s real balance only grew by `X - δ` (`substrate/frame/psm/src/lib.rs:743-756`).
3. Repeat across multiple mints so `PsmDebt` compounds ahead of the real reserve.
4. Attempt full redemption of accumulated `PsmDebt` via `Psm::redeem`; later redeemers hit `reserve < external_out` → `Error::Unexpected` (`substrate/frame/psm/src/lib.rs:851-855`), demonstrating the PSM instance is insolvent relative to its own recorded debt for that external asset. A unit test using a mock `Fungibles` implementation whose `decrease_balance` deliberately debits `X - δ` while the default `transfer` still returns `X` would concretely reproduce this in the pallet's own test harness (`substrate/frame/psm/src/mock.rs`, `substrate/frame/psm/src/tests.rs`).
