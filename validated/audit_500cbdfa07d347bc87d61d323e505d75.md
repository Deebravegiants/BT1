Based on my investigation, I found a real analog in `EcdsaBeefy.sol`, in the same bug-class family as the CAPTCHA report: an unprivileged input (`sigLen`/`votes`) is used to satisfy a supermajority/security threshold check without the de-duplication guard that every *other* consensus verifier in this codebase applies to the same kind of participant list.

### Title
Missing Duplicate-Authority-Index Check in `EcdsaBeefy` Allows Supermajority Threshold Bypass with Fewer Real Signers - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` counts `relayProof.signedCommitment.votes.length` (`sigLen`, fully attacker/relayer-controlled) against the 2/3+1 supermajority threshold, then builds `MerkleMultiProof.Leaf[]` entries keyed by each vote's `authorityIndex` and verifies them as a merkle multi-proof. Unlike the BSC, sync-committee, and Pharos verifiers in this same codebase — which explicitly reject duplicate/out-of-range participant indices before counting them toward the threshold — `EcdsaBeefy` never checks that `authorityIndex` values are distinct.

### Finding Description
`checkParticipationThreshold(sigLen, authoritySet.len)` is evaluated purely against `votes.length` [1](#0-0) . The votes are then converted into merkle leaves keyed by `vote.authorityIndex` and passed to `MerkleMultiProof.VerifyProof` [2](#0-1) . Analogous BFT-participation checks elsewhere in the repo explicitly defend against exactly this shape of attack: the BSC verifier rejects "bits set beyond validator count" [3](#0-2) , the sync-committee verifier does the same for bitfield positions past committee size [4](#0-3) , and the Pharos verifier explicitly de-duplicates participant keys with a `BTreeSet` check before counting stake [5](#0-4) . `EcdsaBeefy.sol` and its Rust BEEFY counterpart (`modules/consensus/beefy/verifier/src/lib.rs`) have no equivalent de-duplication of `authorityIndex`/`sig.index` before the threshold check [6](#0-5) .

If `MerkleMultiProof.VerifyProof` (an external library, `@polytope-labs/solidity-merkle-trees`) tolerates repeated leaf indices in its input list without rejecting the proof, an attacker who holds signatures from fewer than 2/3+1 of the current BEEFY authority set could resubmit the same authority's valid signature/vote multiple times under the same `authorityIndex`, inflating `sigLen` past the supermajority threshold while the actual number of unique signing authorities remains below it.

### Impact Explanation
If exploitable, this would let a minority (or even a single) subset of BEEFY authorities forge a consensus update accepted as if it had 2/3+1 supermajority backing, which forges MMR-root/state-machine-commitment updates. Downstream, this enables forged message delivery and unbacked minting/relaying of cross-chain messages/assets that depend on the trusted BEEFY consensus state, which is a critical unsound-state-commitment class of bug per the maintained rules.

### Likelihood Explanation
This is **not confirmed as exploitable** without access to `MerkleMultiProof.VerifyProof`'s source (it lives in an external dependency, `@polytope-labs/solidity-merkle-trees`, whose implementation was not indexed/available to me). Standard merkle multi-proof implementations typically process leaves as a set keyed by position and would likely reject a duplicate index either implicitly (index collision corrupts the proof reconstruction) or by construction. I could not verify this either way from the available code. The absence of an explicit duplicate check in `EcdsaBeefy.sol`/`beefy/verifier` — in contrast to the deliberate, commented de-duplication guards present in every sibling consensus verifier in this codebase (BSC, sync-committee, Pharos) — is the concrete, provable root-cause finding; whether the external merkle library independently closes the gap is unknown.

### Recommendation
Add an explicit uniqueness check on `vote.authorityIndex` (Solidity) / `sig.index` (Rust) before counting `sigLen`/`signatures_length` toward `checkParticipationThreshold`/`check_participation_threshold`, mirroring the `BTreeSet`-based de-duplication already used in `modules/consensus/pharos/verifier/src/lib.rs::verify_validator_membership` [7](#0-6) . This closes the gap regardless of whether the underlying merkle-proof library independently rejects duplicates, consistent with the defense-in-depth pattern already applied to the BSC and sync-committee verifiers.

### Proof of Concept
Not independently reproducible from the indexed code alone: reproducing this would require exercising `MerkleMultiProof.VerifyProof` from `@polytope-labs/solidity-merkle-trees` with a `Leaf[]` array containing repeated `index` values (same `authorityIndex`, same recovered signer) to confirm whether the external library accepts or rejects it. I recommend a Devin session build a Foundry test against `EcdsaBeefy.verify` with an authority set of size N, fewer than `2N/3+1` unique signing authorities, and `votes` padded with repeated `(signature, authorityIndex)` pairs from those same authorities to hit the `sigLen` threshold, to confirm or rule out exploitability before treating this as confirmed rather than a candidate finding.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
