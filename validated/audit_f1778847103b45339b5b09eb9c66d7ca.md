### Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied `shop-domain` header to the app's handler as the trusted tenant identifier, without that header ever being part of the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the signature purely over that signable string against the app's single, shop-independent `Context.api_secret_key` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers and are never mixed into the signed bytes [3](#0-2) .

`Registry.process` only calls `Utils::HmacValidator.validate(request)` to authenticate the request, then immediately trusts `request.shop` as the tenant identity when constructing the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because the same `api_secret_key` is used to sign webhooks for every shop that has installed the app (the secret is per-app, not per-shop, per `Context.api_secret_key`), a valid `(raw_body, hmac)` pair obtained from any one legitimately-registered installation (e.g., an attacker installing the app on their own store, which is a normal unprivileged action) remains a cryptographically valid pair for any other shop's webhook endpoint. An attacker can replay that exact body and HMAC to the app's public webhook URL while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will pass (it never looks at the shop header), and the app's `WebhookHandler#handle` will receive `data.shop == "victim-shop.myshopify.com"` bound to attacker-controlled body content, breaking the intended binding `authenticated_secret_owner == claimed_shop`.

### Impact Explanation
This crosses the tenant boundary the gem is meant to enforce: a merchant/attacker who is unprivileged with respect to any other tenant can cause the host application to process an attacker-forged event as if it originated from a different, victim shop. Depending on how the host app's handler uses `data.shop` (common patterns include looking up/loading the victim's session or triggering shop-scoped side effects such as data deletion, resource redaction, or state changes keyed by `shop`), this enables cross-tenant data manipulation or spoofed mandatory-compliance webhooks (e.g. `shop/redact`, `customers/redact`, `customers/data_request`), all of which are explicitly registered and dispatched with the unauthenticated `shop` field. This matches the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high for any app that exposes a public webhook endpoint (which is the norm) and that is installed by more than one shop (any third-party app). No access token, `api_secret_key`, or privileged account is required — only the ability to install the app on an attacker-owned store to harvest one valid `(body, hmac)` pair, and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a modified shop header, both of which are unprivileged-internet-user actions.

### Recommendation
Bind the shop identity into the authenticated material, e.g., verify that the `shop-domain` header value corresponds to a shop with a currently active/known session/installation before trusting it, and/or additionally validate against Shopify's IP allowlist/mTLS if available, or include the shop domain in the signed payload check by cross-referencing it with data already contained/verifiable inside the signed body (many webhook payloads include shop-scoped resource IDs) rather than trusting the header in isolation.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, receiving a legitimate webhook POST with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body `B`.
2. Attacker resends this exact request to the app's public webhook endpoint, keeping body `B` and the `x-shopify-hmac-sha256` header unchanged, but replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` using the app's single `api_secret_key` and matches the (unchanged) provided HMAC → passes [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...)`, i.e., the app processes attacker-controlled body content under the victim shop's identity [6](#0-5) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
