## Title
Wallet account `compatibilityMode` is mutable at any time via `update()`/`updateMany()` and directly controls key-derivation/signing paths - (File: `features/wallet-accounts/src/module/wallet-accounts.ts`)

### Summary
`compatibilityMode` on a `WalletAccount` is only pinned at creation time (inherited from the default account), but it is not protected from later modification through `WalletAccounts.update`/`updateMany`. This mirrors the reported "genes are overrideable" bug class: a value that should be immutable once set (because downstream code treats it as identity-defining for key derivation) can instead be changed at any time, making the initial "inheritance" meaningless.

### Finding Description
On account creation, `compatibilityMode` is copied from the default account: [1](#0-0) 

The generic update path, `updateWalletAccount`, only guards against changing `source`, `id`, `index`, and `seedId` (once set) — `compatibilityMode` is not in that immutable set: [2](#0-1) 

`update`/`updateMany` call this helper directly with attacker-influenced `data`, with no additional restriction on `compatibilityMode`: [3](#0-2) 

`compatibilityMode` is then consumed downstream to compute the derivation path/purpose used for both address generation and transaction/message signing: [4](#0-3) [5](#0-4) [6](#0-5) 

This is structurally the same bug class as the reported issue: a setting that is supposed to be fixed/inherited for an account (analogous to `gene()` in `KinoAccountMinter`) can instead be freely overwritten post-creation with no immutability enforcement, so "leaving it unset/inherited" and "setting a new value before each operation" are equivalent.

### Impact Explanation
Because `compatibilityMode` directly feeds `getKeyIdentifier`/derivation-path computation used both for computing receive/change addresses and for producing the signer used in `signTransaction`/`signMessage`, being able to freely mutate it after account creation could cause an account to sign with, or derive addresses from, a different derivation path than the one the user/UI believes is associated with that account (e.g., silently switching between "exodus" and "metamask" derivation semantics for Ethereum, as seen in the test fixture at `sdks/headless/__tests__/adapters/asset-plugins.js:81-102`). If `update`/`updateMany` is reachable by a less-privileged caller (e.g., through an exposed API surface), this could lead to address/key confusion for the affected wallet account.

### Likelihood Explanation
I was not able to confirm, within the available indexed files, whether `walletAccounts.update`/`updateMany` is exposed to an untrusted/lower-privileged caller (e.g. a dApp via RPC bridge) versus being callable only from trusted background/application code. The API/module wiring for `wallet-accounts` (e.g. `features/wallet-accounts` API slice or exposed namespace) was not fully retrievable via search, so likelihood of an actual cross-privilege exploitation path could not be conclusively established from the indexed content.

### Recommendation
Treat `compatibilityMode` as immutable once set (add it to the guarded/forbidden-to-change key list in `updateWalletAccount`, alongside `source`, `id`, and `index`), consistent with the recommendation in the reported issue to make "genes" (identity/behavior-defining fields) immutable after initial assignment.

### Proof of Concept
Not fully constructible from the indexed codebase alone — while `updateWalletAccount` and `update()` clearly permit changing `compatibilityMode` after creation (see code cited above), confirming a concrete unauthorized-caller path (i.e., whether an untrusted context such as a dApp/RPC bridge can invoke `walletAccounts.update`) requires inspecting the full API/index wiring for `features/wallet-accounts`, which was not available within the indexed content. A Devin session with full repository access would be needed to trace the exposed API surface and build a runnable PoC test (analogous to the reporter's `testGeneInheritance`) that calls `walletAccounts.update(name, { compatibilityMode })` from an untrusted context and observes altered signing/derivation behavior.

const updateWalletAccount = (
  walletAccounts: Record<string, WalletAccount> = Object.create(null),
  walletAccount: string,
  newData: Record<string, unknown>
) => {
  const before = walletAccounts[walletAccount]

  if (!before) throw new Error(`${walletAccount} is not a known wallet account`)

  if (walletAccount === DEFAULT_WALLET_ACCOUNT.toString() && newData.enabled === false) {
    throw new Error("Can't disable default walletAccount")
  }

  const after = new WalletAccount({
    ...before,
    ...newData,
  })

  for (const key of ['source', 'id', 'index']) {
    assert(
      (before as unknown as Record<string, unknown>)[key] ===
        (after as unknown as Record<string, unknown>)[key],
      `cannot change account ${key}`
    )
  }

  assert(
    !before.seedId || before.seedId === after.seedId,
    'seedId can only be set if previously undefined'
  )

  return after
}

    await this.updateMany({ [name]: data })

  updateMany = async (dataByName: Record<string, Record<string, unknown>>) => {
    const currentWalletAccounts = await this.#getInternalWalletAccountsWithFallback()
    const updated = Object.entries(dataByName).map(([name, data]) => {
      const walletAccount = updateWalletAccount(currentWalletAccounts, name, data)
      return [walletAccount.toString(), walletAccount]
    })

    await this.#persistWalletAccounts(Object.fromEntries(updated))
  }
