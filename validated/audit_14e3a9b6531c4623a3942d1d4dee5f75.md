### Title
Unbounded pre-auth ECDSA JWT signature verification on HTTP trigger gateway path enables CPU-exhaustion DoS - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The gateway's HTTP Trigger request path (`MethodWorkflowExecute`) performs full ECDSA signature recovery for every incoming, unauthenticated request that references a known (non-secret) `workflowID`, with no concurrency or rate-limit budget applied before that CPU-bound verification step. This mirrors the reported bug class in GHSA-qcc3-jqwp-5vh2: a public-facing webhook/message-handler entry point that performs expensive signature verification work without a shared pre-auth concurrency budget, allowing an unprivileged remote caller to exhaust server resources.

### Finding Description
`httpTriggerHandler.HandleUserTriggerRequest` processes every inbound trigger request in this fixed order: request validation, workflow ID resolution, then authorization (JWT verification), and only *after* successful authorization does it apply the per-workflow rate limiter: [1](#0-0) 

`authorizeRequest` delegates to `WorkflowMetadataHandler.Authorize`, which calls `utils.VerifyRequestJWT`: [2](#0-1) [3](#0-2) 

`VerifyRequestJWT` performs `GetSignersEthAddress`, an ECDSA public-key-recovery over secp256k1 on every request before any claim/signature match against the workflow's registered keys is even checked: [4](#0-3) 

The only rate limiting on this path, `checkRateLimit`, runs strictly *after* `authorizeRequest` succeeds and is scoped per-workflow-owner — it does nothing to bound the CPU work already spent recovering the signer's public key for an arbitrary/forged token: [5](#0-4) 

Unlike the node-to-gateway path (`HandleNodeMessage`), which is gated by both a per-node and a `globalNodeRateLimiter` before any processing: [6](#0-5) 

there is no equivalent global rate limiter or concurrency budget constructed for, or applied to, the user-facing HTTP trigger path before the CPU-intensive JWT/ECDSA verification step. `NewGatewayHandler` only wires `globalNodeRateLimiter`/`perNodeRateLimiters` for node responses and `mtlsRequestRateLimiter`/`mtlsConcurrencyLimiter` for outbound mTLS actions — none of these apply to inbound `MethodWorkflowExecute` requests prior to signature verification: [7](#0-6) 

Since `resolveWorkflowID` only requires knowledge of a `workflowID` (which is not a secret — it is derivable from owner/name/tag or otherwise discoverable) to reach `authorizeRequest`, any unauthenticated internet caller can trigger the expensive signature-recovery path repeatedly and concurrently with garbage/forged JWTs, with no shared budget bounding how many such verifications run in parallel.

### Impact Explanation
This is directly analogous to the reported bug class: a public gateway endpoint performs non-trivial pre-auth cryptographic work (ECDSA public key recovery) per request, and no shared concurrency/rate budget exists to cap that work before authentication succeeds or fails. A flood of forged requests can consume gateway CPU/goroutines, degrading or denying service for legitimate workflow trigger requests — a bounded availability impact (CWE-770/CWE-799), matching the "low/medium," `A:L` CVSS profile of the source advisory. No confidentiality or integrity impact is created; this is purely a resource-exhaustion/availability concern.

### Likelihood Explanation
The `MethodWorkflowExecute` endpoint is explicitly internet-facing and designed to accept requests from external, unauthenticated callers (it is the entry point for triggering workflows via HTTP). No signature/authentication is required to reach the point where signature verification work occurs — only a `workflowID`, which is not treated as a secret by design. This makes exploitation straightforward for any unprivileged actor capable of sending JSON-RPC requests to the gateway.

### Recommendation
Introduce a shared, cheap pre-auth admission control (e.g., a global concurrency limiter/semaphore or lightweight global rate limiter, similar to `globalNodeRateLimiter`) that gates access to `HandleUserTriggerRequest`/`authorizeRequest` before the ECDSA/JWT verification work is performed, independent of and prior to the per-workflow-owner `checkRateLimit`. This bounds the number of concurrent expensive signature verifications that can be triggered by unauthenticated/unauthorized callers.

### Proof of Concept
An attacker can send a burst of concurrent `MethodWorkflowExecute` requests, each specifying a valid, known `workflowID` (workflow IDs are not secret) paired with a syntactically valid but forged/garbage JWT (`req.Auth`). Each such request reaches `authorizeRequest` → `Authorize` → `VerifyRequestJWT` → `GetSignersEthAddress`, performing full ECDSA signature recovery, before being rejected. Because no shared concurrency budget or global rate limiter gates this step, an attacker can drive an arbitrarily high number of concurrent CPU-bound verifications purely by sending unauthenticated traffic, as demonstrated conceptually by the JWT-authorization failure test path that reaches this verification step without any prior throttling: [8](#0-7)

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	orgID := h.resolveOrgID(ctx, workflowRef.workflowOwner)
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Org: orgID, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}

func (h *gatewayHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	if resp.ID == "" {
		return fmt.Errorf("received response with empty request ID from node %s", nodeAddr)
	}
	h.lggr.Debugw("handling incoming node message", "requestID", resp.ID, "nodeAddr", nodeAddr)
	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementCapabilityNodeThrottled(ctx, nodeAddr, h.lggr)
		return fmt.Errorf("rate limit exceeded for node %s", nodeAddr)
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		h.metrics.IncrementGlobalThrottled(ctx, h.lggr)
		return errors.New("global rate limit exceeded")
	}
