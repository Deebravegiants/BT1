### Title
Webhook `shop`/`topic` identity spoofing via HMAC that only covers the request body, not headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by computing an HMAC over the raw request body only, then dispatches to a handler using `topic` and `shop` values pulled from HTTP headers that are never included in that signature. This breaks the intended binding of `shop == the tenant the signature was computed for`, letting anyone in possession of one valid (body, HMAC) pair — for example a merchant who has the app installed on their own store — replay that pair while rewriting the `shop-domain` and `topic` headers to point at any other shop or handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from attacker-controllable HTTP headers, with no involvement in the signature: [2](#0-1) 

`HmacValidator.validate` recomputes the HMAC using `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never touches `shop` or `topic`: [3](#0-2) 

`Registry.process` uses the *unauthenticated* `request.topic` to select which handler runs, and forwards the *unauthenticated* `request.shop` straight into `WebhookMetadata`, which is the tenant-identifying value the host application's handler relies on: [4](#0-3) 

The equality the code is supposed to enforce is: `shop bound by the HMAC signature == shop acted upon by the handler`. In reality the signature only binds the body bytes; `shop` (and `topic`) are parsed from headers that sit entirely outside the signed material. Any party that can obtain one legitimately-signed `(raw_body, hmac)` pair — trivially available to any merchant who installs the app on their own store and receives their own webhooks — can resubmit that exact body/HMAC to the app's webhook endpoint while substituting a different `shop-domain` and/or `topic` header. `HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` happily invokes the handler registered for the attacker-chosen topic with `WebhookMetadata#shop` set to an arbitrary target shop's domain and attacker-controlled body content.

### Impact Explanation
This is a cross-tenant identity confusion at the SDK layer: the host application is led to believe a webhook authentically originated for shop B (and/or for topic X) when it was really assembled by an attacker from data legitimately signed for shop A (and/or topic Y). Any handler that uses `data.shop` to select a tenant's session, database record, or credential — the documented, intended usage pattern shown in the gem's own docs (`ShopifyAPI::Webhooks::Registry.process` example) — will act on behalf of the wrong tenant using attacker-supplied body content. Depending on the handler, this can mean cross-tenant data injection, spoofed mandatory-compliance callbacks (`shop/redact`, `customers/redact`, `customers/data_request`), or triggering privileged app-side logic for a shop the attacker does not control. This satisfies the "cross-tenant access" Critical bucket, since the attacker crosses a tenant boundary using only data from their own, unprivileged install.

### Likelihood Explanation
The prerequisite is low: any unprivileged internet user can install a public app on a free development/trial shop, receive one legitimate webhook (body + valid `hmac-sha256`), and replay it against the app's public webhook endpoint with modified `shop-domain`/`topic` headers. No access token, `client_secret`, or privileged account is required — only the ability to receive one webhook for a store the attacker owns, which is a normal, expected capability of any merchant.

### Recommendation
Bind `shop` (and ideally `topic`) into the value that is actually authenticated. Options:
- Have `Request#to_signable_string` incorporate the shop domain (and topic) alongside the body, and require the app to configure per-shop webhook secrets or otherwise verify shop identity through a channel not controlled by the caller (e.g., only trust `shop` after checking it against a shop that is known to have an active install, not solely from the header).
- At minimum, document/enforce that `WebhookMetadata#shop` and `#topic` are unauthenticated header values, and add a library-level check that cross-references the delivered `shop` against Shopify's known registered webhook endpoint/shop mapping before dispatch, or reject processing unless the shop domain format and known session store combination are validated server-side.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets it register an HTTP webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)` — attacker captures this `(B, H)` pair from their own traffic (e.g., via browser devtools/proxy on their own server, or by having their own receiving code log it).
3. Attacker sends a new HTTP request to the same app webhook endpoint with:
   - body = `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - header `x-shopify-topic: shop/redact` (changed, if desired)
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns `true`. [5](#0-4) 
5. `Registry.process` looks up the handler for `shop/redact`/`orders/create` and calls it with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`. [6](#0-5) 
6. The app's handler executes tenant-scoped or compliance logic against `victim-shop.myshopify.com` using attacker-supplied body content, even though the attacker has no relationship with that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
