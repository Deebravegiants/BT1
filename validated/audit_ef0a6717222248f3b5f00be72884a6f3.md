The route-registration in `core/web/router.go` confirms the core claim of the report: `GET /v2/bridge_types` and `GET /v2/external_initiators` are registered with only base authentication (`auth.Authenticate` requiring a valid session/API token) and **no role-based middleware** — unlike the `POST`/`PATCH`/`DELETE` variants which are wrapped in `auth.RequiresEditRole` or `auth.RequiresAdminRole` [1](#0-0) . This means even a user with the lowest privilege role, `UserRoleView`, can call these list endpoints and receive the plaintext `OutgoingToken`/`OutgoingSecret` values, since `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` checks are entirely absent from the `Index`/`Show` handlers [2](#0-1) . This directly confirms the report's claim and actually strengthens it: the finding isn't just about "any authenticated user" but specifically that even the read-only `view` role — which is intended to have no mutation or run capability — can exfiltrate these secrets.

Audit Report

## Title
Bridge and External Initiator outgoing tokens are stored and returned in plaintext to any authenticated node user, including the lowest-privilege "view" role - ([File: core/web/presenters/external_initiators.go], [File: core/web/presenters/bridges.go], [File: core/web/router.go])

## Summary
Bridge `OutgoingToken` and External Initiator `OutgoingToken`/`OutgoingSecret` values are generated as plaintext secrets, persisted unhashed in the database, and returned in full on every subsequent list/get call, including via GraphQL. Critically, `GET /v2/bridge_types` and `GET /v2/external_initiators` are registered in `core/web/router.go` with no role-gating middleware at all, so any authenticated user — even one with the lowest `UserRoleView` role, which is otherwise restricted from running jobs or editing anything — can retrieve these secrets.

## Finding Description
`NewBridgeType` generates an `OutgoingToken` in plaintext and stores it unhashed in `bridge_types.outgoing_token`, unlike `IncomingToken`, which is salted/hashed [3](#0-2) . `BridgeResource`, used by both `bt.Index`/`bt.Show` handlers and by the GraphQL `Bridge` resolver, always includes `OutgoingToken` in its JSON output, with no `omitempty` restricting it to creation time [4](#0-3) [5](#0-4) .

The same pattern applies to `NewExternalInitiator`, which generates plaintext `OutgoingToken`/`OutgoingSecret` [6](#0-5) , persisted and returned via `ExternalInitiatorsController.Index` → `NewExternalInitiatorResource`, which includes `OutgoingToken` in the response [7](#0-6) [8](#0-7) .

Crucially, in `core/web/router.go`, the routes for these endpoints are:
```go
authv2.GET("/external_initiators", paginatedRequest(eia.Index))
...
authv2.GET("/bridge_types", paginatedRequest(bt.Index))
authv2.GET("/bridge_types/:BridgeName", bt.Show)
```
These are wrapped only by the base `authv2` group's `auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession)` — there is no `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole` wrapper, in contrast to the `POST`/`PATCH`/`DELETE` routes on the same lines which do use `auth.RequiresEditRole` [1](#0-0) . The role-check helpers `RequiresRunRole`, `RequiresEditRole`, and `RequiresAdminRole` in `core/web/auth/auth.go` demonstrate that the codebase does have a role hierarchy (`view` < `run` < `edit` < `admin`) that is enforced elsewhere but simply omitted for these GET endpoints [2](#0-1) . This confirms that a `UserRoleView` user — the lowest privilege level in the system, intended to be read-only and unable to run jobs or edit configuration — can call these endpoints and receive the plaintext outgoing secrets.

This contrasts with the node's own user API tokens, which are hashed and never re-served after creation via `SetAuthToken` [9](#0-8) , showing the bridge/EI outgoing token handling is an inconsistent, weaker design choice rather than an intended behavior.

## Impact Explanation
Any authenticated node user — even one restricted to `view` role with no edit/run/admin permissions — can retrieve the outgoing token/secret used to authenticate the node to a bridge's external adapter or an external initiator's callback. This token can be replayed by that low-privileged user to impersonate the chainlink node when calling the adapter/initiator endpoint, potentially triggering unauthorized job runs or serving fabricated responses trusted by the node. This maps to the in-scope "secret exfiltration enabling request impersonation" impact class, and represents privilege escalation since a `view`-role user gains a capability equivalent to (or beyond) what `run`/`edit` roles are meant to gate.

## Likelihood Explanation
Exploitation requires only a valid, low-privilege authenticated session (the lowest role, `view`) and a simple `GET` request to a standard, always-available endpoint (`/v2/bridge_types`, `/v2/external_initiators`, or the GraphQL equivalents) — no special role, admin access, or host/database access is needed. This makes exploitation straightforward and repeatable in any node with bridges or external initiators configured, which is a common, standard node configuration.

## Recommendation
Restrict outgoing-token visibility on `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, `GET /v2/external_initiators`, and the GraphQL `bridge`/`bridges` resolvers to admin-role callers only, or omit the field entirely after creation (mirroring the `IncomingToken` `omitempty`-at-creation pattern). Additionally, consider hashing/salting the outgoing token analogous to `IncomingTokenHash`, requiring re-generation/rotation flows instead of persistent plaintext storage.

## Proof of Concept
1. As an admin, create a user with `UserRoleView` and a bridge via `POST /v2/bridge_types` (admin/edit role) — response includes `outgoingToken`.
2. Authenticate as the `view`-role user (session or API token) and call `GET /v2/bridge_types` — the same plaintext `outgoingToken` is returned, despite `view` role having no edit/run privileges.
3. Repeat with `POST /v2/external_initiators` (edit role) then `GET /v2/external_initiators` as the `view`-role user to retrieve the persisted `outgoingToken`.
4. Confirm in `core/web/router.go` that these two `GET` routes lack any `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` wrapper, unlike their corresponding write routes.
5. Use the disclosed token to authenticate as the node against the external adapter/initiator endpoint, demonstrating impersonation capability.
