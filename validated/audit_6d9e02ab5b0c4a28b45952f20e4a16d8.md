### Title
Bystander biometric capture via unauthenticated primary-face selection - (File: rgb-net/src/lib.rs, src/agents/python/rgb_net.rs)

### Summary
`RgbNet::estimate` in `rgb-net/src/lib.rs` is a thin PyO3 wrapper that forwards raw frames to the Python RGB-Net model and returns whatever `predictions` list it produces, with no Rust-side subject identity or consent binding. [1](#0-0)  The downstream Rust code (`EstimateOutput::primary`, used throughout capture/distance/eye-tracking/pipeline logic) blindly trusts a single boolean flag, `is_primary`, computed entirely inside the opaque Python model to decide which detected face in the frame is "the user." [2](#0-1) 

### Finding Description
`RgbNet::estimate` in `rgb-net/src/lib.rs` simply calls the Python agent's `estimate` method and returns the raw dict-like `PyAny` result — it performs no filtering, ranking, or identity/consent check on which face in frame is processed. [1](#0-0)  The results are parsed in `extract()` into a `Vec<EstimatePredictionOutput>`, each with an `is_primary: bool` field and a `score: f64` supplied directly by the Python model. [3](#0-2)  The Rust code selects "the" subject via `EstimateOutput::primary()`, which just finds the first prediction with `is_primary == true` — a value entirely determined by the underlying (out-of-scope, model-internal) selection heuristic (e.g., largest bbox / highest confidence), not by any tracked identity or session-bound consent gate. [2](#0-1) 

This `primary()` result is then used unconditionally to: populate eye-tracker mirror targeting, [4](#0-3)  gate distance/focus-range computation used to decide when to trigger IR capture, [5](#0-4)  and — critically — select which RGB frame/bbox/landmarks get stored into the `left_rgb`/`right_rgb` capture slots in `biometric_capture::Plan::handle_rgb_net`, which are later fed into the biometric pipeline (iris/face embeddings) and uploaded. [6](#0-5) [7](#0-6) 

There is no session-bound tracking ID, face-embedding continuity check, or "same person across the whole capture" invariant anywhere in this pipeline. Each new RGB-Net estimate independently re-derives `is_primary` from the current frame's face population, so if a bystander presents a face that the model scores as more prominent (e.g., closer, larger, more centered, or a face better matching whatever the underlying heuristic favors) than the enrolling user's face, the "primary" designation can shift frame-to-frame. The `distance` agent (`src/agents/distance.rs`) only checks that the primary subject's estimated distance is in focus range — it doesn't verify it's the *same* subject as prior frames. [5](#0-4)  Likewise, `biometric_capture::Plan::handle_rgb_net` will happily overwrite `left_rgb`/`right_rgb` with whichever face is currently flagged primary and passes the bbox sanity check, with no cross-frame identity consistency enforcement. [6](#0-5) 

### Impact Explanation
If exploitable, this would let an unprivileged bystander who positions themselves prominently in the camera's field of view get their face/eye landmarks captured, stored in `left_rgb`/`right_rgb`/`face_self_custody_candidate`, and processed through the face-identifier/iris pipeline under someone else's signup session — i.e., non-consenting biometric data capture and processing under another user's `signup_id`. This matches an Immunefi-style "biometric data disclosure / wrong-identity binding" impact.

### Likelihood Explanation
This is plausible in principle from the Rust-side code alone (no identity continuity or consent check exists in the reachable Rust path), but exploitability depends heavily on factors this audit cannot verify from the Rust codebase: (1) the actual Python RGB-Net model's `is_primary` heuristic (largest bbox vs. centered vs. confidence-weighted vs. distance-based) is not present in this repo and could not be inspected; (2) the physical/optical setup of the Orb (narrow FOV, mirror-steered close-range IR/RGB capture) may make it physically very hard for a bystander's face to appear prominently alongside or instead of the enrolling user's face within the short capture window; (3) `distance.rs`'s in-range gating (`IR_FOCUS_RANGE`/`IR_FOCUS_RANGE_SMALL`) requires the primary face to be within a tight focus distance, which constrains how "swappable" the primary subject practically is mid-capture. Given the reliance on an unverified Python-side heuristic and physical capture constraints outside this repo's scope, likelihood cannot be confirmed as high without hardware-in-the-loop testing.

### Recommendation
Add a Rust-side identity-continuity guard for the duration of a capture session: bind the first accepted `primary` face's embedding/landmarks/bbox center at capture start, and reject subsequent RGB-Net estimates in `biometric_capture::Plan::handle_rgb_net` / `distance::Agent` whose "primary" prediction diverges beyond a tolerance (position/size/embedding) from the originally bound subject, rather than trusting Python's per-frame `is_primary` flag in isolation.

### Proof of Concept
Integration test plan (requires access to `biometric_capture::Plan` and a fake/mock RGB-Net port since the real Python model isn't available in this repo):
1. Construct a sequence of `rgb_net::Output::Estimate` outputs simulating two subjects: frame 1-5 with `is_primary=true` on subject A (bbox centered, small, at valid distance), frame 6+ with `is_primary=true` switching to subject B (bystander, e.g., larger bbox / different landmarks).
2. Feed frames through `biometric_capture::Plan::handle_rgb_net` and assert that `left_rgb`/`right_rgb` slots, once populated with subject A's estimate, are never overwritten by subject B's estimate for the remainder of the session.
3. Expected (current, vulnerable) behavior: the slot is overwritten unconditionally as long as `prediction.bbox.coordinates.is_correct()` holds, regardless of subject identity — [8](#0-7)  — demonstrating the missing identity-continuity check.

```rust
    fn handle_rgb_net(
        &mut self,
        _orb: &mut Orb,
        output: port::Output<rgb_net::Model>,
        frame: Option<camera::rgb::Frame>,
    ) -> Result<BrokerFlow> {
        if let rgb_net::Output::Estimate(estimate) = output.value {
            if let Some(prediction) = estimate.primary() {
                if prediction.bbox.coordinates.is_correct() {
                    let frame = frame.expect("frame must be set for an estimate output");
                    let slot =
                        if self.target_left_eye { &mut self.left_rgb } else { &mut self.right_rgb };
                    *slot = Some(FrameInfoRgb::new(estimate, frame));
                }
            }
        }
        Ok(BrokerFlow::Continue)
    }
```
