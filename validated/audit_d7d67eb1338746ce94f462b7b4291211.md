### Title
`Oauth.begin_auth` builds the OAuth authorization redirect from an unvalidated `shop` parameter, unlike every other OAuth entry point in the gem - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` constructs the merchant-facing OAuth authorization URL using the caller-supplied `shop:` argument with **no domain validation**, whereas every sibling credential-issuing flow (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the value to build a request host. `begin_auth` is the one OAuth entry point that is normally invoked directly from an unauthenticated, attacker-influenced HTTP request (the app's `/login?shop=...` route), so the missing binding here is the most reachable one in the gem.

### Finding Description
`Utils::ShopValidator.sanitize!` exists specifically to enforce the identity binding "the `shop` value used to build a request host == a value verified to be a real `TRUSTED_SHOPIFY_DOMAINS` (or configured myshopify) domain": [1](#0-0) . This is consistently applied before any code path builds a URL host from a `shop` string that is not otherwise cryptographically bound:

- `ClientCredentials.client_credentials` — `validated_shop = Utils::ShopValidator.sanitize!(shop)` before creating the session/host [2](#0-1) .
- `RefreshToken.refresh_access_token` — same pattern [3](#0-2) .
- `TokenExchange.migrate_to_expiring_token` — same pattern [4](#0-3) .

In contrast, `Oauth.begin_auth` takes the `shop:` keyword argument as-is and feeds it straight into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` and appends the authorization query string containing `client_id`, `scope`, `redirect_uri` and `state`: [5](#0-4) , [6](#0-5) . No call to `Utils::ShopValidator` occurs anywhere in `begin_auth`, and this is confirmed by `grep_search` showing `ShopValidator` referenced only in `client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`, and `graphql/storefront.rb` — never in `oauth.rb`.

`begin_auth` is, by design, the entry point invoked before any authentication has occurred — a merchant simply loads `https://your-app.com/install?shop=<value>` and the host application (per Shopify's documented integration pattern) passes that raw query parameter straight into `begin_auth(shop: ...)`. Unlike `validate_auth_callback`'s `auth_query.shop`, this `shop` value carries **no HMAC or other binding at all** at this point in the flow — it is pure attacker-supplied input. The equality that should hold is:
`shop used to build auth_base_uri == shop verified by ShopValidator against TRUSTED_SHOPIFY_DOMAINS`
but the actual code enforces:
`shop used to build auth_base_uri == shop as received from the unauthenticated caller`.

### Impact Explanation
Because `auth_base_uri` is unchecked, `begin_auth(shop: "attacker.example")` returns `auth_route: "https://attacker.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://legit-app.com/redirect&state=...&grant_options[]=..."`. If a host application relies on this gem to build the redirect (as intended/documented) without independently validating `shop`, an attacker can:
1. Send a victim merchant a crafted install link with `shop=attacker.example`.
2. The app calls `begin_auth`, sets the anti-CSRF `state` nonce cookie in the victim's browser, and redirects the victim's browser to the attacker's server instead of Shopify.
3. The attacker's server, now in possession of the app's `client_id`, requested `scope`, and the genuine `redirect_uri`/`state`, can complete a forced-OAuth-completion style attack: it can redirect the victim onward to the real Shopify authorize endpoint for a shop of the attacker's choosing, or otherwise manipulate the flow so the victim's session cookie (`state`) is completed against a shop the attacker controls, letting the attacker's shop obtain a valid callback into the app under the victim's already-primed session cookie.

This matches the "session fixation or forced OAuth completion" High-severity category called out in the rules, because the state-fixation cookie is issued to the victim's browser before the shop is validated, and the redirect destination is fully attacker-controlled.

### Likelihood Explanation
`shop` is documented and expected to come straight from an unauthenticated query parameter on the app's install route — this is the standard OAuth-initiation pattern for every Shopify app, so the exploit requires no privileged access, tokens, or secrets, only the ability to send the victim a link. The only mitigating factor is that a careful host application might independently validate `shop` before calling `begin_auth`, but the gem itself provides no such protection at this specific call site even though it does so at every other OAuth/credential call site, so a host application following the gem's own inconsistent example is exposed.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth`, raising `Errors::InvalidShopError` for any `shop` value that does not resolve to a `TRUSTED_SHOPIFY_DOMAINS` domain, mirroring the validation already performed in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, and use the sanitized value in `auth_base_uri`.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host_name: "legit-app.com",
  scope: ["read_products"], is_private: false, is_embedded: false)

result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example", redirect_path: "/auth/callback")
puts result[:auth_route]
# => "https://attacker.example/admin/oauth/authorize?client_id=key&scope=read_products&
#     redirect_uri=https://legit-app.com/auth/callback&state=<nonce>&grant_options%5B%5D="
```
No `ShopifyAPI::Errors::InvalidShopError` is raised, and the victim's browser (with the `state` cookie already set) is redirected to the attacker-controlled host, contrasted with:
```ruby
ShopifyAPI::Auth::ClientCredentials.client_credentials(shop: "attacker.example")
# raises ShopifyAPI::Errors::InvalidShopError
```
confirming the validation is present elsewhere but missing specifically in `begin_auth`. [6](#0-5) [7](#0-6) [8](#0-7)

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
