## Analysis

Looking for the closest analog to the Poseidon2 bug — an `enabled`/flag signal that gates critical side effects (execution-bus emission) without being properly bound to the data it is supposed to gate — the strongest match in this repo is the `onChainCreation` bool array in `CircomData`, which is used by `Hinkal.transact()` to skip nullifier insertion and commitment insertion, but is **not** part of the ZK proof's public inputs nor part of the signed message hash that binds the rest of `circomData` to the user's EdDSA signature.

`CircomDataBuilder.getSignedMessageHash` binds `rootHashHinkal`, token addresses, `amountChanges`, `timeStamp`, `inputNullifiers`, `outCommitments`, and `calldataHash` into the hash the user signs [1](#0-0) , and `buildVerifierId`/public-input builder likewise never includes `onChainCreation` in the values checked by `verifyProof` [2](#0-1) . Yet `onChainCreation[i]` directly controls, per-token, whether the balance equation uses `amountChanges[i]` or forces it to zero [3](#0-2) [4](#0-3) , and whether `insertNullifiers`/`insertCommitments` process that token's off-chain nullifiers/commitments at all:

`insertNullifiers` breaks out of the inner loop for token `i` entirely once `onChainCreation[i]==true`, so any real `inputNullifiers[i][j]` for that token are never marked spent [5](#0-4) . `insertCommitments` similarly breaks for token `i` in all three loops, so real `offChainCommitments[i][j]` for that token are never counted, inserted into the tree, or emitted [6](#0-5) .

Since `onChainCreation` is arbitrary calldata not tied to the proof or signature, an unprivileged party who can observe a valid `(a,b,c)` proof + `circomData` (e.g. any relayer, or anyone front-running a mempool transaction — `transact()` has no caller restriction) can resubmit it with `onChainCreation[i]` flipped to `true` for a token index while keeping every other field (including `amountChanges[i]`, `inputNullifiers[i]`, `outCommitments[i]`, `rootHashHinkal`, `calldataHash`) identical to what was proven and signed.

### Title
Unbound `onChainCreation` flag lets any submitter skip nullifier/commitment insertion for a proven transaction - (File: contracts/Hinkal.sol, contracts/HinkalBase.sol)

### Summary
`circomData.onChainCreation` is never included in the ZK proof's public inputs or in the EIP-712-style `signedMessageHash` that binds the rest of `CircomData` to the user's signature, yet it gates whether `insertNullifiers`/`insertCommitments` process a given token's real off-chain nullifiers and commitments, and whether the balance equation enforces `amountChanges[i]`. Any caller of `transact()` who has (or intercepts) a valid proof can flip this flag for a token index without invalidating the proof or signature.

### Finding Description
`Hinkal.transact()` verifies the proof against `inputForCircom` built from `circomData` fields, and separately validates `rootHashHinkal` [7](#0-6) . None of these checks constrain `circomData.onChainCreation`. Later, the per-token balance equation branches on `onChainCreation[i]` [3](#0-2) , and `_calculateDeltaAmount` (used for actual token transfers in `_internalTransact`) does the same [4](#0-3) . Finally `insertNullifiers` and `insertCommitments` are called with `circomData.onChainCreation` [8](#0-7)  and, per token, `break` out of processing that token's real nullifiers/commitments whenever `onChainCreation[i]==true` [9](#0-8) [10](#0-9) .

Because `onChainCreation` is excluded from `getSignedMessageHash` [1](#0-0)  and from the public-input array checked by `verifyProof` [2](#0-1) , it is fully malleable by whoever submits the transaction on-chain, independent of the user's authorization. This is directly analogous to the Poseidon2 `enabled`/`end_top_level` bug: a flag that gates critical downstream effects (there, execution-bus emission; here, nullifier/commitment bookkeeping and the balance equation) is not constrained to match the data it is supposed to describe.

### Impact Explanation
Setting `onChainCreation[i]=true` for a token index whose off-chain proof actually spends real input UTXOs and creates real output UTXOs causes:
- The real output commitment(s) for that token in `outCommitments[i]` to never be inserted into the merkle tree (`insertCommitments` breaks before counting/inserting/emitting them), permanently freezing the value the circuit proved was created for that output UTXO — the owner can never construct a valid membership proof for a leaf that was never inserted.
- The real input nullifier(s) for that token in `inputNullifiers[i]` to never be recorded in the `nullifiers` mapping (`insertNullifiers` breaks before marking them spent), so the underlying input commitment is never actually invalidated on-chain and can be replayed in a later transaction with a fresh proof — a nullifier-reuse / double-spend of the original UTXO's value.
- The balance-diff equation and `_internalTransact`/`_externalTransact` transfer logic to use `0` instead of `amountChanges[i]`, decoupling actual on-chain token movement from what the proof and user signature committed to.

This matches the Critical bar in-scope: "permanent freezing of user funds" (frozen output commitment) and "proof or nullifier verification bypass" (nullifier never recorded, enabling double spend), achieved purely by an unprivileged transaction submitter/front-runner manipulating a field outside the signed/proven data.

### Likelihood Explanation
`transact()` has no access control restricting who can call it with a given valid proof, and nothing revalidates that `onChainCreation` is consistent with the actual non-zero entries in `inputNullifiers`/`outCommitments` for each token. Any relayer, MEV bot, or the user's own subsequently-malicious relay can alter this single calldata array while replaying an otherwise-untouched, still-valid proof/signature bundle from the mempool or via legitimate relay access.

### Recommendation
Bind `onChainCreation` into both the ZK proof's public inputs (or at minimum into `signedMessageHash`) and add on-chain checks that `onChainCreation[i]==true` implies `inputNullifiers[i]` and `outCommitments[i]` are all zero (i.e. that token had no off-chain UTXOs in this transaction), so the flag cannot silently suppress bookkeeping for real off-chain value.

### Proof of Concept
1. User (or relay on user's behalf) generates a valid proof for `transact()` where token index `i` spends real input UTXO `U_in` (nonzero `inputNullifiers[i][0]`) and creates real output UTXO `U_out` (nonzero `outCommitments[i][0]`), with `amountChanges[i] = 0` (pure internal shielded transfer, so `_calculateDeltaAmount` originally would be `0` regardless — chosen to keep the balance equation satisfiable under manipulation).
2. Before/while this transaction is included, an unprivileged third party (or the same relay) resubmits identical `(a,b,c)`, `dimensions`, and `circomData` except `circomData.onChainCreation[i]` is flipped to `true`.
3. Proof verification and root-hash check pass unchanged (`onChainCreation` not part of the public inputs) [7](#0-6) .
4. Balance-diff check passes because `amountChanges[i]` was `0` for this transfer, so the `onChainCreation[i]` branch is a no-op there [3](#0-2) .
5. `insertNullifiers` skips marking `inputNullifiers[i][0]` (nullifier of `U_in`) as spent [9](#0-8) ; `insertCommitments` skips inserting `outCommitments[i][0]` (`U_out`) into the tree [10](#0-9) .
6. Result: `U_out`'s value is permanently unspendable (never in the tree), while `U_in`'s nullifier was never recorded — `U_in` can later be re-spent in a separate valid proof, double-spending its value.

    function insertCommitments(
        uint256[][] memory offChainCommitments,
        bytes[][] memory offChainEncryptedOutputs,
        OnChainCommitment[] memory onChainCommitments,
        bool[] memory onChainCreation
    ) internal {
        // 1) Total Length of Commitments
        uint256 length = 0;
        for (uint256 i = 0; i < offChainCommitments.length; i++) {
            for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                if (onChainCreation[i]) break;
                length += offChainCommitments[i][j] != 0 ? 1 : 0;
            }
        }
        length += onChainCommitments.length;

        if (length > 0) {
            // 2) Flattening leaves array
            uint256[] memory leaves = new uint256[](length);
            uint256 index = 0;
            for (uint256 i = 0; i < offChainCommitments.length; i++) {
                for (uint256 j = 0; j < offChainCommitments[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        leaves[index++] = offChainCommitments[i][j];
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                leaves[index++] = onChainCommitments[i].commitment;
            }

            // 3) Inserting Leaves
            uint256[] memory insertedIndexes = insertMany(leaves);

            // 4) Emitting Commitments/EncryptedOutputs
            index = 0;
            for (uint256 i = 0; i < offChainEncryptedOutputs.length; i++) {
                for (uint256 j = 0; j < offChainEncryptedOutputs[i].length; j++) {
                    if (onChainCreation[i] == true) break;
                    if (offChainCommitments[i][j] != 0) {
                        emit NewCommitment(
                            leaves[index],
                            int256(insertedIndexes[index]),
                            offChainEncryptedOutputs[i][j]
                        );
                        index++;
                    }
                }
            }
            for (uint256 i = 0; i < onChainCommitments.length; i++) {
                emit NewCommitment(
                    leaves[index],
                    -1 * int256(insertedIndexes[index++]),
                    abi.encode(
                        onChainCommitments[i].utxo,
                        onChainCommitments[i].onChainEncryptedOutput
                    )
                );
            }
        }
    }

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }
