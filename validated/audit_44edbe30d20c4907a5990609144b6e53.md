### Title
Tron IntentGatewayV2.placeOrder credits escrow from the pre-transfer requested amount instead of the tokens actually received, silently under-collateralizing escrow for fee-on-transfer tokens - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The mainline EVM `IntentGatewayV2.sol` was patched to compute protocol fees and the order commitment from the *actual balance received* by the gateway (an explicit fix for fee-on-transfer tokens, see "Phase 1"/"Phase 2" comments). The Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` was never given this fix: it still computes `reducedInputs` (and thus what gets credited into the escrow ledger `_orders[commitment][token]`) from the caller-supplied `order.inputs[i].amount` *before* the token transfer happens, and in the direct-transfer path never checks how much the gateway actually received.

### Finding Description
In the patched, canonical contract, `placeOrder` explicitly measures the actual tokens received before computing fees/commitment: [1](#0-0) 
This is described directly in the code comments as a deliberate fix: "For fee-on-transfer tokens, the gateway receives less than the requested amount. We mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds." [2](#0-1) 

The Tron copy of the same contract computes `reducedInputs`/the commitment from `order.inputs[i].amount` up front, before any transfer occurs: [3](#0-2) 

Then in the direct (non-predispatch) escrow path it calls `safeTransferFrom` for the nominal amount but never checks the resulting balance delta before crediting the ledger: [4](#0-3) 

If the input token deducts any amount on transfer (a fee-on-transfer / deflationary token, common among TRC-20 tokens), the gateway physically receives `order.inputs[i].amount - transferFee`, but `_orders[commitment][token]` is credited with `reducedInputs[i].amount`, which was derived from the full pre-transfer `order.inputs[i].amount`. The escrow ledger therefore overstates the gateway's actual token holdings for that order by the transfer-fee amount.

Because `_orders` is a shared, per-token accounting structure across all orders in the same contract, this discrepancy is not merely a loss confined to the placing user — it creates a shortfall that is paid out of the pooled balance belonging to other users' escrowed funds when this (and subsequent) orders are filled or redeemed via `RedeemEscrow`/`fillOrder`, which pay out exactly the ledger-recorded (`reducedInputs`) amount. Repeating this with a fee-on-transfer token — or one where a fee can be turned on by its owner (many tokens include a toggleable fee mechanism) — lets an attacker/solver systematically siphon real token balance out of the gateway that was deposited by other, unrelated orders, while the ledger never reflects the true shortfall until the contract runs out of tokens for a legitimate order to be redeemed.

### Impact Explanation
This is a direct accounting/solvency bug in the escrow ledger of a live token-custody contract reachable by any user with a single `placeOrder` transaction — no privileged role required. The result is understated collateral for the gateway pool, which materializes as either (a) later legitimate order fills/redemptions failing due to insufficient real balance (permanent freezing/DoS of funds), or (b) an attacker deliberately using fee-on-transfer tokens across many orders to accumulate ledger credit disproportionate to actual deposits, then draining that credit through fills/`RedeemEscrow`, stealing from the pooled balance of other users. This satisfies the "concrete theft or permanent freezing of funds" bar for High severity.

### Likelihood Explanation
Likelihood is Medium-High: it requires the deployment to accept at least one ERC/TRC-20 input token that charges a transfer fee (either at launch or via an owner-toggleable fee), which is common in the Tron/TRC-20 ecosystem, and it requires no special privilege — only a normal `placeOrder` call by any user. The bug is a straightforward oversight relative to the already-fixed mainline contract, showing the fix was not propagated to this deployment target.

### Recommendation
Port the "measure actual balance received" fix from `evm/src/apps/IntentGatewayV2.sol` (Phase 1) into `evm/tron/contracts/apps/IntentGatewayV2.sol`: transfer input tokens first, measure `balanceOf(address(this))` before/after each transfer, mutate `order.inputs[i].amount` to the actually-received amount, and only then compute `protocolFeeBps`, `reducedInputs`, and the commitment hash from that real amount before crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy/target a Tron `IntentGatewayV2` instance configured with `protocolFeeBps > 0` and whitelist a TRC-20 token `FOT` that charges e.g. a 2% transfer fee (or use a token whose owner enables such a fee post-listing).
2. Attacker calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
   - `reducedInputs[0].amount` is computed as `1000e18 - protocolFee` based on the nominal `1000e18` (see `evm/tron/contracts/apps/IntentGatewayV2.sol:359-385`).
   - `safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but the gateway actually only receives `980e18` (2% fee).
   - `_orders[commitment][FOT] += reducedInputs[0].amount` credits the ledger with the amount based on the un-taxed `1000e18`, i.e., more than the `980e18` actually held for this order (`evm/tron/contracts/apps/IntentGatewayV2.sol:462-463`).
3. A solver fills the order (or the order is redeemed via `RedeemEscrow`), and the gateway pays out the full ledger-recorded `reducedInputs[0].amount`, which exceeds what was physically deposited for this order — the excess is drawn from other users' pooled `FOT` escrow balance in the same contract.
4. Repeating step 2–3 across multiple orders accumulates a growing shortfall between the ledger and the real token balance, eventually causing either theft of other users' funds or an inability to honor legitimate withdrawals/fills (frozen funds).

Note: I could not directly execute this PoC in a sandbox (no code execution tool available in this session); the analysis is based on static comparison of the patched mainline contract's Phase 1 fee-on-transfer fix against the unmodified logic still present in the Tron variant, both cited above.
