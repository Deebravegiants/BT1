## Title
Deterministic AMM associated-account PDAs allow front-running to permanently block pool creation for a target market - (File: `program/src/processor.rs`)

### Summary
The Raydium AMM `Initialize2` instruction derives the `target_orders`, `lp_mint`, `coin_vault`, `pc_vault`, and `amm` accounts as PDAs whose seeds are `[program_id, market_account.key, associated_seed]` [1](#0-0) . The `market_info` account is explicitly documented as "just a seed for AMM account... can be any account" and is never validated to be a real, checked OpenBook market at the time these deterministic addresses are derived and populated [2](#0-1) . Because the resulting addresses are 100% deterministic and publicly computable from the market pubkey alone, any unprivileged user can pre-empt a legitimate pool creator by calling `Initialize2` first for that market pubkey (with arbitrary/garbage coin and pc mints), permanently occupying the associated PDAs before the intended pool for that market can ever be created.

### Finding Description
`process_initialize2` computes each associated account address via `get_associated_address_and_bump_seed`, whose seeds are simply the program id, the caller-supplied `market_account.key`, and a fixed associated-seed suffix [1](#0-0) . These addresses are then created and permanently assigned to `program_id` via `invoke_signed` in `generate_amm_associated_account`, `generate_amm_associated_spl_mint`, and `generate_amm_associated_spl_token`, all of which check only `associated_token_account.owner == system_program_account.key` before creation and return `AmmError::RepeatCreateAmm` if the account is already owned by anything else [3](#0-2) [4](#0-3) .

Critically, at no point during `process_initialize2` is `market_info` validated against real OpenBook market state (e.g., verifying its base/quote mint matches `amm_coin_mint_info`/`amm_pc_mint_info`, or that it is owned by the actual market program) — comments in the code explicitly state the market account "won't be used" / is "just a seed" [5](#0-4) . This means the deterministic ID space for `(target_orders, lp_mint, coin_vault, pc_vault, amm)` is keyed purely on a market pubkey that any user can predict in advance (e.g., the well-known OpenBook market address for a popular token pair that a legitimate market maker intends to use for a Raydium pool).

This directly mirrors the reported bug class: object/account identifiers are deterministically derived off-chain-predictable inputs, and because objects (here, on-chain accounts owned by the program) cannot be "removed" or reset back to `Uninitialized`/system-owned once created, an attacker can front-run the legitimate creation with a bogus pool using the same market seed, permanently squatting the ID space tied to that market.

### Impact Explanation
Once an attacker's `Initialize2` call succeeds using a target market pubkey, all five derived PDAs (`amm`, `target_orders`, `lp_mint`, `coin_vault`, `pc_vault`) become permanently owned by the Raydium AMM program at those exact deterministic addresses [6](#0-5) . Any subsequent, legitimate attempt to create the real pool for that same market will fail with `AmmError::RepeatCreateAmm` because the owner check no longer matches the system program [7](#0-6) . There is no instruction in the program to reclaim, reset, or reassign these accounts, so this results in a **permanent denial of service** — a specific, high-value token/market pair can never be onboarded to Raydium's canonical AMM pool for that market, which is a permanent, non-recoverable griefing/freezing effect on the protocol's ability to list that market.

### Likelihood Explanation
The attack requires only a single, unprivileged transaction: the attacker needs the target market's public key (which is public, e.g., discoverable ahead of a project's planned pool launch) and minimal token amounts to satisfy `init_pc_amount`/`init_coin_amount` non-zero checks [8](#0-7) . No special role or signer beyond a funded wallet is needed since `Initialize2` is permissionless and only requires `user_wallet_info.is_signer` [9](#0-8) . This makes the attack cheap, fully front-runnable, and highly likely for any anticipated high-profile market/pool launch.

### Recommendation
Bind the account-derivation seeds to values that cannot be squatted independently of real pool intent, and validate `market_info` before using it as a seed. Options:
- Verify `market_info` is genuinely owned by the expected market program and that its packed base/quote mint fields match `amm_coin_mint_info`/`amm_pc_mint_info` before deriving/creating any associated accounts.
- Incorporate the coin/pc mint pubkeys (not just the market key) into the PDA seeds, and/or require the pool creator to provide a fresh, program-verified nonce/salt, so that an attacker cannot cheaply occupy the ID space for an as-yet-uncreated legitimate pool.
- Provide an administrative recovery path (e.g., allow `sysAdmin`-gated reclaiming or reallocation) for squatted accounts that were initialized with invalid/mismatched market data.

### Proof of Concept
1. Attacker observes a well-known OpenBook `market` pubkey `M` intended for a legitimate token pair (e.g. TOKEN/USDC) that has not yet had a Raydium pool created.
2. Attacker computes the deterministic PDAs `target_orders`, `lp_mint`, `coin_vault`, `pc_vault`, `amm` using seeds `[program_id, M.to_bytes(), <ASSOCIATED_SEED>]` via `get_associated_address_and_bump_seed` [1](#0-0) .
3. Attacker submits `Initialize2` passing `market_info = M` along with two arbitrary throwaway SPL mints as `amm_coin_mint`/`amm_pc_mint` and minimal non-zero `init_coin_amount`/`init_pc_amount`.
4. `process_initialize2` succeeds: it creates and permanently assigns all five PDAs to `program_id` at the addresses derived from `M` [6](#0-5) , with no check tying `M` to the attacker's chosen mints.
5. When the legitimate team later attempts `Initialize2` for market `M` with the real TOKEN/USDC mints, every `generate_amm_associated_*` call finds the PDA already owned by `program_id` (not system program) and returns `AmmError::RepeatCreateAmm`, permanently blocking creation of the genuine pool for market `M` [7](#0-6) .
