### Title
Escrow credit in `placeOrder`'s predispatch path is derived from the shared `CallDispatcher`'s ambient balance instead of a per-call delta, letting an attacker back an order with donated/residual funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder` (Tron variant) escrows `reducedInputs[i].amount` for an order whenever `IERC20(token).balanceOf(dispatcher)` (or `address(dispatcher).balance` for native) is merely `>= requiredAmount`. This mirrors the Loop `PrelaunchPoints` bug of computing a deposit/claim amount from `address(this).balance` rather than a verified, order-specific transfer delta — allowing anyone who can put tokens into the shared, publicly known `dispatcher` address (by direct donation, by a leftover/stuck balance from another order, or via their own attacker-controlled `predispatch.call`) to satisfy the check and have the gateway credit escrow for an order without that value being uniquely, verifiably contributed by the caller for that specific order.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder`'s predispatch branch: [1](#0-0) 

reads `balance = IERC20(token).balanceOf(dispatcher)` / `address(dispatcher).balance`, checks only `balance < requiredAmount`, sweeps the *entire* raw `balance` out of the shared `dispatcher` contract, and unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount` — a value computed purely from the caller-supplied `order.inputs[i].amount`, with **no verification that this specific transaction's predispatch flow actually produced that balance**.

This differs materially from the mainline EVM implementation, which snapshots `address(this).balance`/token balance *before* the sweep and computes `received = balance_after - balance_before`, capping `order.inputs[i].amount` to the measured delta and shunting any excess strictly to `DustCollected` (never to escrow): [2](#0-1) 

The Tron version has none of this delta accounting — it trusts the dispatcher's ambient balance. Additionally:
- `order.predispatch.assets[i].amount == 0` is never rejected in the Tron path (the EVM sibling explicitly reverts `InvalidInput` on a zero amount), so an attacker can skip contributing real predispatch assets entirely.
- `placeOrder` in the Tron contract carries no `nonReentrant`/`ReentrancyGuardTransient` protection, unlike the EVM version (`function placeOrder(...) public payable nonReentrant`), so the shared `dispatcher`'s balance is not isolated against concurrent/nested calls within the same or reentered execution.
- `dispatcher` is a single, persistent, protocol-wide address (`_params.dispatcher`), not a per-order ephemeral contract, so its balance can carry over between unrelated orders (e.g., dust left over from another user's predispatch, or a token sent directly via a plain `transfer`).

This is the same root cause pattern as the Loop finding: an "invariant" (escrow only reflects tokens the caller actually contributed for *this* order) is broken because the amount is read from a balance that any third party can inflate before the check runs, rather than from a value strictly attributable to the current transaction's transfer.

### Impact Explanation
Because the credited escrow (`_orders[commitment][token]`) backs a real cross-chain/same-chain settlement promise — a solver on the destination chain fills the order and later redeems this exact escrow via `RedeemEscrow`/`withdraw()` — crediting escrow that isn't genuinely backed by the order's own funds is equivalent to an unbacked mint of claimable value in the intents system. An attacker can:
1. Send tokens/ETH directly to the well-known `dispatcher` address (or exploit dust left behind by another user's predispatch flow), and
2. Call `placeOrder` with `predispatch.assets[i].amount = 0` (or trivial) and a no-op `predispatch.call`, setting `order.inputs[i].amount` up to the ambient `dispatcher` balance.

The gateway will sweep that ambient balance into itself and credit the attacker's order with escrow they never contributed, which a colluding/attacker-controlled solver can then redeem for real output tokens cross-chain — a direct theft of protocol/gateway funds or of another user's stuck/donated tokens, and a violation of the "deposit only reflects escrowed funds" invariant analogous to the H-01 report.

### Likelihood Explanation
Reachable by any unprivileged caller through a single `placeOrder` transaction with a crafted `predispatch` section — no special privileges, governance, or multi-block timing required beyond being able to transfer tokens to a public contract address. The missing zero-amount check and missing reentrancy guard in the Tron variant materially lower the bar versus the hardened EVM implementation, which already anticipates and defends against exactly this class of donation/balance-inflation attack via delta accounting.

### Recommendation
Align the Tron `IntentGatewayV2.placeOrder` predispatch flow with the EVM implementation:
1. Snapshot `address(this)`/token balance immediately before executing the sweep `Call`s and compute `received = balanceAfter - balanceBefore`; cap `order.inputs[i].amount`/escrow credit to `received`, routing only genuine excess to `DustCollected`.
2. Reject `order.predispatch.assets[i].amount == 0` as `InvalidInput`, matching the EVM sibling.
3. Add `nonReentrant` (or transient-storage reentrancy guard) to `placeOrder`.
4. Consider isolating or zeroing the dispatcher's balance per call (e.g., a per-order ephemeral proxy, or sweeping any pre-existing balance to a dust sink before the predispatch assets are transferred in) so ambient/residual balance can never be attributed to an unrelated order.

### Proof of Concept
1. Read the shared dispatcher address: `address dispatcher = IntentGatewayV2(gateway).params().dispatcher;` (public via `params()`).
2. Attacker transfers `X` tokens directly to `dispatcher` (a plain `IERC20.transfer(dispatcher, X)`, requiring no allowance from the gateway).
3. Attacker calls `placeOrder` with:
   - `order.predispatch.assets = [{token, amount: 0}]` (bypassed since the Tron code has no zero-amount check),
   - `order.predispatch.call` = a no-op `Call[]` (or any dispatcher-executable call),
   - `order.inputs = [{token, amount: X}]` (or any amount `<= X`).
4. In `placeOrder`: `balance = IERC20(token).balanceOf(dispatcher)` equals `X` (from step 2, contributed by attacker with no real transferFrom against `msg.sender` inside this call), passes `balance < requiredAmount` check, and the full `X` is swept from `dispatcher` to the gateway.
5. `_orders[commitment][token] += reducedInputs[i].amount` credits escrow for `X` (minus protocol fee) attributed to this order, even though the tokens were pre-positioned by the attacker outside of any per-order transfer accounting (and could equally have originated from a prior, unrelated user's stuck predispatch balance rather than the attacker's own funds, which the attacker did not need to permanently spend to trigger the credit if `order.predispatch.call` also reclaims them).
6. A colluding solver fills the order and redeems the resulting escrow cross-chain via `RedeemEscrow`, monetizing the fraudulently credited escrow. [1](#0-0)
