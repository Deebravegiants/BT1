### Title
Webhook `shop` (and `topic`) Identity Not Bound to HMAC Signature Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`) and event `topic` that get dispatched to app handlers directly from unauthenticated HTTP headers, while the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. An attacker who can obtain any validly-signed webhook body/HMAC pair (e.g. by installing the target app on a shop they control and triggering a webhook themselves) can replay that exact body+HMAC to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to a victim shop, and the signature check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic`, however, are read straight from headers with no cryptographic binding to that body: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it to the `hmac` header value — it never incorporates `shop` or `topic`: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` trusts the (unauthenticated) `request.shop` and `request.topic` and forwards them directly to the app's handler as the tenant/event identity: [4](#0-3) 

This breaks the intended identity binding: `shop_authenticated_by_hmac == shop_delivered_to_handler`. In reality, `hmac` only authenticates the body bytes; `shop` (and `topic`) are attacker-controllable header values that the gem never verifies against the signature.

### Impact Explanation
An unprivileged internet user who can install the target app on their own shop (a normal, unprivileged action for any public Shopify app) can:
1. Trigger a real webhook event in their own shop, capturing a genuinely Shopify-signed `(raw_body, hmac)` pair for a topic the app handles.
2. Replay that exact body and `hmac` header to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain (and optionally the `x-shopify-topic` header).
3. `HmacValidator.validate` still succeeds because it only checks the body signature.
4. The app's handler receives `WebhookMetadata` with `shop` set to the victim's domain, potentially causing the host application to write/update data under the wrong tenant, trigger tenant-scoped side effects, or otherwise process attacker-supplied body content as if it originated from the victim shop — a cross-tenant integrity issue.

This maps to the "Critical - cross-tenant access" impact category since the binding between the cryptographically-verified content and the claimed tenant (`shop`) is absent.

### Likelihood Explanation
Likelihood is constrained by the need for the attacker to first obtain a validly HMAC-signed body for a topic supported by the target app, which requires the app to be installable by the attacker's own shop (a normal step for public/embeddable apps) and for the handler logic to trust `data.shop`/`data.topic` from `WebhookMetadata` without additional out-of-band verification. Given many host apps use webhook `shop` directly as a tenant key (as illustrated in this gem's own docs example), the likelihood of exploitable impact is meaningful, though it depends on host-app trust assumptions and reachability of the webhook endpoint.

### Recommendation
Do not treat `shop`/`topic` header values as authenticated. Either:
- Cross-check `request.shop` against the `Auth::Session`/tenant record the app already has on file for the expected event before dispatching, or
- Where possible, corroborate `shop`/`topic` against fields embedded in the (HMAC-covered) JSON body rather than relying solely on headers, and document clearly that `WebhookMetadata#shop`/`#topic` are not HMAC-bound so consuming apps must not use them as the sole tenant-authorization signal.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app there.
# Shopify sends a real, validly-signed webhook to the attacker for their own shop:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)

# Attacker replays the SAME body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => Base64.encode64(hmac),   # still valid – only body is signed
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # attacker-controlled, unverified
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (body signature matches)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The app's handler now processes attacker-controlled body content attributed to the victim shop.
```

          received_signature = verifiable_query.hmac
