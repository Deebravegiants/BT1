This confirms the finding: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#shop` is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)` and then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight to the app-supplied handler, binding the (unauthenticated) `shop` value to the (authenticated) body without any cross-check [3](#0-2) . Since the HMAC secret (`Context.api_secret_key`, the app's client secret) is shared across every shop that has the app installed, a valid HMAC over a given body does not bind that body to any particular shop.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs/verifies only the raw body via HMAC, but the `shop` (tenant identity) is taken from an unauthenticated header and passed straight through to the host application's webhook handler as if it were verified.

### Finding Description
`HmacValidator.validate` computes `HMAC-SHA256(secret, signable_string)` and compares it to the `hmac-sha256` header [4](#0-3) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , so the signature proves only "this app's secret produced a MAC over this exact body." It says nothing about which shop the body belongs to. The `shop` accessor is pulled unchecked from the `shopify-shop-domain` header [2](#0-1) .

`Registry.process` treats a passing `HmacValidator.validate(request)` as authorization to trust the entire `request`, including `request.shop`, and forwards it unchanged into `WebhookMetadata` for the app's handler [3](#0-2) . The equality the gem implicitly claims to guarantee is: `shop-header == shop that produced/owns this HMAC-signed body`. In reality the HMAC only certifies `secret == app's shared secret`, since the same `api_secret_key` is used for every shop's webhook deliveries for a given app [5](#0-4) . Because the secret is not shop-specific and the header isn't part of the signed content, anyone who can obtain one genuine `(body, hmac)` pair delivered for their own shop (e.g., by triggering a webhook in their own store and capturing the raw request before it reaches the app, since they control network access to their own app installation's endpoint/proxy) can resubmit that same body+signature to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header value. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` claiming the data belongs to a different, victim shop [6](#0-5) . This is documented in the library's own guidance as the trusted mechanism host apps should rely on to attribute data to a tenant, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [7](#0-6) .

### Impact Explanation
This breaks the tenant-identity binding the gem is expected to provide to host applications: `Registry.process` presents `shop` as an authenticated field once HMAC validation passes, but it is not actually bound to the signed payload. A multi-tenant host application that keys any state (records, queues, background jobs, cache invalidation, permission checks) off `WebhookMetadata#shop` can be made to attribute attacker-controlled webhook data to an arbitrary victim shop domain, i.e. cross-tenant data injection/spoofing.

### Likelihood Explanation
Exploitation requires the attacker to be able to obtain one valid `(raw_body, hmac)` pair originally destined for the app (e.g., control of their own shop's install and the network path to the app's endpoint) and then resend it with a forged shop header directly to the app's public webhook URL. No possession of the app's `client_secret`, an access token, or any other shop's credentials is required — only a legitimately-issued webhook for the attacker's own tenant.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `topic`/`webhook-id`) in the HMAC-signed content, or otherwise cryptographically bind the shop identity to the body (e.g., cross-check `shop` against a `shop_domain`/`shop_id` field already present inside the verified JSON body for topics that include it, or require host apps to reconcile `WebhookMetadata#shop` against the shop associated with the specific webhook subscription rather than trusting the header value as-is). At minimum, update the library documentation to explicitly warn that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) for a resource they control.
2. Attacker captures the raw POST that Shopify sends to the app's webhook endpoint: `raw_body` and the `x-shopify-hmac-sha256` header value (both are delivered to a URL the attacker's own shop configuration determines, so the attacker can position a logging proxy in front of their own endpoint).
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `raw_body` using the app's single shared `api_secret_key` [4](#0-3)  — it matches, since the secret is not shop-specific.
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled>, ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim tenant's identity.
