### Title
Webhook `shop` (tenant) field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC over the raw request body only, while the `shop` (and `topic`, `webhook_id`) values used to route and attribute the webhook are taken from unauthenticated HTTP headers. This is structurally the same class of bug as the reported "double wrapping" issue: an identity-relevant value (the tenant/shop) is *used* by the code path but is not *covered* by the integrity check that is supposed to authenticate the whole request, breaking the binding `authenticated_bytes == acted_on_bytes`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `Request#hmac` is read from the `hmac-sha256` header: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `computed_signature(verifiable_query.to_signable_string, secret)` against the received HMAC: [3](#0-2) 

So the cryptographic check only proves "this exact body was signed with the app's shared secret." It says nothing about the `shop`, `topic`, or `webhook_id` headers. Yet `Registry.process` uses those unauthenticated header values as the tenant/routing identity for dispatch: [4](#0-3) 

`request.shop` and `request.topic` are both parsed straight from headers with no signature coverage: [5](#0-4) 

The binding that should hold is: `shop_covered_by_hmac == shop_used_for_tenant_dispatch`. It does not — `shop_covered_by_hmac` is the empty set (only body bytes are signed), while `shop_used_for_tenant_dispatch` is an attacker-controllable header.

Critically, the HMAC secret (`Context.api_secret_key`) is the app-wide `client_secret`, shared across every merchant/shop that has installed the app — it is not shop-specific. Any unprivileged person who installs the app on their own shop legitimately receives real Shopify webhooks: valid `(body, HMAC)` pairs signed with that same shared secret. Because the signature never touches the `shop` header, that same `(body, HMAC)` pair remains valid if replayed to the app's own webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a different, victim shop's domain.

### Impact Explanation
This is a cross-tenant identity binding break (Critical, per the provided impact list: "cross-tenant access"). A host application that follows the gem's own webhook API and trusts `WebhookMetadata#shop` (as returned by `Registry.process`) to select which merchant's records to update will process an attacker-supplied, replayed webhook body under a different shop's identity. This can lead to writing/deleting a victim shop's data, or triggering business logic (e.g., `app/uninstalled`, `orders/create`) attributed to a shop the attacker does not control — a genuine tenant-isolation failure caused entirely by this gem's `Request`/`Registry` design, not by host misuse.

### Likelihood Explanation
Exploitation only requires:
1. The attacker installs the target app on their own (attacker-controlled) shop — an ordinary, unprivileged action any merchant can take.
2. The attacker captures one legitimate webhook delivery (body + valid `hmac-sha256` header) sent by Shopify to the app.
3. The attacker replays that exact body/HMAC pair to the app's public webhook endpoint, substituting the `shop-domain` header with the victim shop's domain.

No access to `api_secret_key`, no privileged account, and no TLS interception is needed — the attacker only needs the credentials of their own, legitimately-installed shop instance, which is not a privileged capability. This is realistic and low-effort.

### Recommendation
Include the tenant-identifying and routing fields (`shop`, `topic`, and ideally `webhook_id`) in the signed/verified material, or otherwise cryptographically bind them to the request the way Shopify's newer webhook verification schemes do. At minimum, `Request#to_signable_string` should not be limited to the raw body if downstream code (`Registry.process`, `WebhookMetadata`) treats header-derived `shop`/`topic` as trusted, authenticated identity for dispatch — either the HMAC coverage must be expanded, or the library must explicitly document that `shop`/`topic` are unauthenticated and must not be used for tenant-scoping decisions without additional verification (e.g., cross-checking against a known/authorized shop list per HMAC-validated body content).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify delivers a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint with headers:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B, using the app's shared client_secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   ```
   and raw body `B`.
3. Attacker captures `(B, valid_hmac)` (e.g., via their own logging/proxy of traffic to their own server, or their own app instance if self-hosted).
4. Attacker POSTs the same raw body `B` and the same `x-shopify-hmac-sha256` value to the app's webhook endpoint again, but sets:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the secret — per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`'s `to_signable_string`.
6. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed(B), ...)`, causing the host app to act on victim-shop data using attacker-supplied order body `B`. [4](#0-3) [6](#0-5)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
