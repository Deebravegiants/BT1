### Title
First LP depositor can bypass the MINIMUM_LIQUIDITY lock via a zero-decimal coin mint and steal value from later depositors via vault donation - (File: program/src/processor.rs)

### Summary
`process_initialize2` derives the LP mint's decimals directly from the attacker-supplied `coin_mint`, and uses that value as the size of the "minimum liquidity" burn subtracted from the pool creator's initial LP mint. Because the attacker chooses the `coin_mint` (any SPL mint they create), they can make this decimals value `0`, reducing the anti-inflation buffer from a meaningful amount (e.g. `10^6`/`10^9`) to just `1` unit — effectively nullifying the Uniswap V2-style minimum-liquidity protection. Combined with the fact that `deposit`'s LP-mint math is computed off live vault balances (which anyone can inflate via a direct SPL token transfer/"donation"), a pool creator can create a near-zero-liquidity pool, front-run a victim's `deposit` with a large donation, and then withdraw a disproportionate share of the victim's contributed tokens.

### Finding Description
In `process_initialize2`, the LP mint is created with `lp_decimals = coin_mint.decimals` [2](#0-1) , where `coin_mint` is unpacked from the caller-supplied `amm_coin_mint_info` account with no validation that it matches any specific decimals or that it corresponds to the market's base/quote mint decimals [3](#0-2) .

The initial LP supply math is:
```
liquidity = sqrt(pc_amount * coin_amount)
user_lp_amount = liquidity - 10^lp_mint.decimals   // "MINIMUM_LIQUIDITY" burn
amm.lp_amount = liquidity                          // full liquidity used as total-supply denominator
``` [4](#0-3) 

The subtracted `10^lp_mint.decimals` amount is never minted to any account, it is only "phantom" supply baked into `amm.lp_amount` — analogous to Uniswap V2's practice of permanently locking `MINIMUM_LIQUIDITY` shares to raise the cost of a first-depositor price-manipulation attack. If `lp_mint.decimals == 0` (attacker's choice, since `coin_mint` decimals are unconstrained), this buffer collapses to `1`, i.e. essentially no protection.

Subsequent `deposit` calls compute LP mint amount using **live SPL token account balances** of the vaults, not an internally-tracked running total:
```
(total_pc_without_take_pnl, total_coin_without_take_pnl) =
    calc_total_without_take_pnl_no_orderbook(amm_pc_vault.amount, amm_coin_vault.amount, &amm)
``` [5](#0-4) 
and mints LP tokens proportionally to `amm.lp_amount` using floor rounding:
```
mint_lp_amount = invariant_coin.exchange_token_to_pool(amm.lp_amount, RoundDirection::Floor)
``` [6](#0-5) 

Because `amm_coin_vault`/`amm_pc_vault` are ordinary SPL token accounts owned by the AMM authority PDA, anyone can transfer ("donate") tokens directly into them without going through `deposit`, instantly inflating `total_pc_without_take_pnl`/`total_coin_without_take_pnl` without minting any LP tokens. This directly changes the LP-share/value ratio seen by the next depositor.

### Impact Explanation
With `lp_decimals = 0`, the pool creator/attacker can:
1. Create a pool with a self-issued 0-decimal `coin_mint` and trivial `init_coin_amount`/`init_pc_amount` (e.g. 2/2), receiving nearly all of `liquidity` as `user_lp_amount` (only 1 unit permanently un-minted).
2. Front-run a victim's `deposit` transaction with a large direct SPL transfer ("donation") into `amm_coin_vault`/`amm_pc_vault`.
3. The victim's `deposit` then computes `mint_lp_amount` against the inflated `total_coin_without_take_pnl`/`total_pc_without_take_pnl`, receiving LP shares representing only a tiny fraction of the value they contributed (bounded from exact-zero by the `mint_lp_amount == 0` revert check [7](#0-6) , but not from severe underpricing above zero).
4. The attacker then calls `withdraw`, redeeming their near-total share of `amm.lp_amount` and receiving a proportional cut of the full vault balance — including the value the victim just deposited — resulting in a direct transfer of funds from the victim to the attacker.

This is a High-severity issue: it permits theft of user-deposited LP funds and unbacked/disproportionate value extraction, reachable entirely by an unprivileged pool creator/LP using ordinary `Initialize2`, `Deposit`, and `Withdraw` instructions plus a plain SPL token transfer.

### Likelihood Explanation
Likelihood is high in practice for any newly created pool with low initial liquidity (a common real-world pattern for new token listings), since:
- Pool creation (`Initialize2`) is fully permissionless and the creator freely chooses the `coin_mint`/`pc_mint` accounts and their decimals.
- No check ties `coin_mint`/`pc_mint` decimals to the OpenBook `market_info`, which is explicitly documented as "can be any account" / just a PDA seed.
- Donating tokens directly to an SPL token account (the vault) requires no special privilege, just a standard `spl_token::transfer`.
- The only defense already in the code (`mint_lp_amount == 0` revert) blocks the degenerate all-or-nothing case but does not prevent severe underpricing of a nonzero deposit.

### Recommendation
- Enforce a fixed, protocol-defined minimum-liquidity constant (e.g. always subtract a fixed large value such as `1_000_000`, independent of `lp_mint.decimals`), rather than deriving it from the attacker-controlled `coin_mint.decimals`.
- Alternatively, mint the `MINIMUM_LIQUIDITY` amount to a burn address at a fixed absolute size regardless of decimals, and additionally validate that `coin_mint`/`pc_mint` correspond to the OpenBook market's actual base/quote mints (rejecting mismatched or attacker-crafted mints).
- Consider tracking total pooled amounts internally (updated only through `deposit`/`withdraw`/`swap` state transitions) instead of trusting live vault token balances for LP-mint ratio math, to remove the donation-based manipulation vector entirely.

### Proof of Concept
1. Attacker creates a new SPL mint `M` with `decimals = 0` and mints itself some units; uses `M` as `coin_mint` in `Initialize2` alongside a normal `pc_mint`, with `init_coin_amount = 2`, `init_pc_amount = 2`.
   - `liquidity = sqrt(2*2) = 2`
   - `lp_mint.decimals = coin_mint.decimals = 0` ⇒ `10^0 = 1`
   - `user_lp_amount = 2 - 1 = 1` minted to attacker; `amm.lp_amount = 2` (this matches lines 908-929 [4](#0-3) ).
2. Attacker observes victim's pending `deposit(max_coin_amount, max_pc_amount)` transaction in the mempool and front-runs it by directly transferring, say, `1_000_000` units of `pc_mint`/`coin_mint` straight into `amm_pc_vault`/`amm_coin_vault` (bypassing `Deposit`).
3. Victim's `deposit` executes: `calc_total_without_take_pnl_no_orderbook` now returns the inflated vault balances [5](#0-4) , so `mint_lp_amount = floor(deduct_coin_amount * amm.lp_amount / total_coin_without_take_pnl)` yields a minuscule LP amount relative to the value the victim contributed.
4. Attacker calls `withdraw` for their `1` LP unit (essentially 50% of the now-diluted `amm.lp_amount = 2 + mint_lp_amount`), redeeming a large proportional share of the pool's real token balance — including funds the victim just deposited — extracting value that should belong to the victim.
