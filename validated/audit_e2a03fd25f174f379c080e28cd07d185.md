### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop domain, topic, and webhook id are read directly from unauthenticated HTTP headers. `Utils::HmacValidator` and `Webhooks::Registry.process` treat a valid HMAC on the body as sufficient proof of the entire request's authenticity, then hand the unauthenticated `shop` header straight to the host application as the tenant identifier.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the `@raw_body` is fed into the HMAC computation. The `shop`, `topic`, and `webhook_id` accessors instead read straight from caller-supplied headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` and secure-compares it to the supplied `hmac` value: [3](#0-2) 

`Webhooks::Registry.process` performs exactly one authenticity check — this HMAC — and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, which the host application's handler uses as the tenant/shop identifier for the payload: [4](#0-3) 

The binding the library implicitly claims to provide is:
`hmac_valid(body) == true` implies `(shop, topic, body)` are all authentic and bound together.

In reality the equality that actually holds is only:
`hmac_valid(body)` proves `body` was produced with the app's real `api_secret_key` — it says nothing about which shop or topic that body was intended for.

Because installing the app is open to any merchant (including an attacker's own test store), an attacker can:
1. Install the target app on their own store and receive one or more genuine, correctly-signed webhooks (any topic/body, signed with the real `api_secret_key`).
2. Replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint, but with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header changed to point at a different (victim) shop.
3. `HmacValidator.validate` still succeeds (it only re-hashes the unmodified body), so `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain, together with attacker-controlled body content that was never actually intended for or seen by that shop.

Any host application that uses the gem as documented — trusting `WebhookMetadata.shop`/`.body` coming out of a "validated" webhook — will process attacker data under another tenant's identity, exactly the kind of trust-boundary confusion described in the report's bug class (an action taken based on a field that the cryptographic check does not actually cover).

### Impact Explanation
This breaks the shop-identity binding that `Registry.process` implicitly guarantees to callers, allowing an authenticated-but-unprivileged merchant/attacker to inject data attributed to an arbitrary victim shop into the host application's webhook processing pipeline — a cross-tenant access/data-integrity violation reachable without possessing the victim's credentials or access token.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on any shop they control (a normal, unprivileged action for any Shopify merchant) and can freely choose HTTP headers on the replayed POST to the app's public webhook endpoint. No secret material, token, or elevated privilege is needed beyond normal app installation.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or otherwise cryptographically bind `shop` to the signature — e.g., verify that `X-Shopify-Shop-Domain` matches a shop-scoped webhook secret/session, or require the HMAC to cover a canonicalized string containing shop+topic+body rather than the body alone.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers/receives a legitimate webhook, capturing:
   - `raw_body` (e.g. `{"id":1,...}`)
   - `x-shopify-hmac-sha256` (valid signature over that body, computed by Shopify with the real `api_secret_key`)
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this successfully; `Utils::HmacValidator.validate` returns `true` because it only checks the (unmodified) body.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker body>, ...)`, causing the host app to apply attacker-controlled data under the victim shop's tenant context.
