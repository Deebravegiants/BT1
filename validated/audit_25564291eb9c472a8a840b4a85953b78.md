Based on my analysis, this confirms the vulnerability: `Registry.process` at [1](#0-0)  uses `Utils::HmacValidator.validate(request)` to authenticate the request, but the HMAC only covers `request.to_signable_string` which returns `@raw_body` [2](#0-1) . The `shop`, `topic`, and `webhook_id` fields are all read straight from HTTP headers and are never included in the signed bytes [3](#0-2) . After the HMAC check passes, `request.shop` (attacker-controllable header, unauthenticated) is forwarded directly into `WebhookMetadata` and handed to the app's handler as the tenant identifier [4](#0-3) .

### Title
Webhook `shop` (and `topic`/`webhook_id`) header fields are not covered by the HMAC, allowing a valid signature from one shop to be replayed while spoofing the tenant identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Registry.process` treats a webhook request as authenticated for a given `shop` once `Utils::HmacValidator.validate(request)` succeeds. However, the HMAC is computed only over the raw body; the `shop-domain`, `topic`, and `webhook-id` headers are excluded from the signed content and are trusted as-is.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header [5](#0-4) . The `shop` attribute is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or the HMAC [6](#0-5) .

Because a legitimate app (or any merchant who installs the app, including an unprivileged/free-tier installer) receives real webhook deliveries with a valid `(raw_body, hmac)` pair for their own shop, that same body/HMAC pair remains cryptographically valid regardless of which `shop-domain` header value accompanies it — the gem's `HmacValidator.validate` only checks the body against the secret, never binding it to the shop that generated it. An attacker who has captured or generated one valid `(body, hmac)` pair (e.g., from their own store's webhook, or any topic whose payload content is generic/predictable) can POST it to the app's webhook endpoint with a different `shop-domain` header value. `Registry.process` will accept it as authentic (`HmacValidator.validate(request)` passes) and dispatch `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the app's handler using the attacker-chosen `shop` [7](#0-6) . The identity binding broken is: `shop authenticated by HmacValidator == shop stored/acted-upon in WebhookMetadata`, which does not hold because `shop` is never part of the HMAC-signed bytes.

### Impact Explanation
Any app logic built on `WebhookMetadata#shop` (data resync, redaction, order/customer processing, cache invalidation, uninstall cleanup, etc.) inherits an unauthenticated tenant identifier despite the gem exposing HMAC verification as its security guarantee. This can produce cross-tenant effects — e.g., triggering `customers/redact` or `shop/redact`-style processing, or injecting/refreshing data, against a victim shop's identifier using a signature that was only ever valid for the attacker's own (or any known) payload/HMAC pair.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine `(raw_body, hmac)` pair, which is straightforward for topics with static or attacker-influenced payload content, or simply by installing the app on a shop they control and capturing their own webhook deliveries. No access to `api_secret_key` or any privileged credential is required — only the ability to POST to the publicly reachable webhook endpoint, which is the gem's documented use case (`Registry.process`).

### Recommendation
Bind the shop (and topic/webhook id, if used for routing/authorization decisions) into the signed content, or independently verify that `request.shop` corresponds to a shop with an active, previously-established session/install record before trusting it, rather than deriving trust for the shop solely from the fact that the raw body's HMAC validated. At minimum, document/enforce that `WebhookMetadata#shop` must be cross-checked against a known installed-shop registry before being used for any tenant-scoped action.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com` (or otherwise obtain one legitimate webhook delivery for a topic whose body content the attacker knows/controls).
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this pair is valid because `HmacValidator` only signs the body [2](#0-1) .
3. Replay this exact `(body, hmac)` pair to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body against the secret [8](#0-7) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` despite the request never being authenticated for that shop [4](#0-3) .
