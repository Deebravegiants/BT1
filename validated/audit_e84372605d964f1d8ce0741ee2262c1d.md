### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is taken from unauthenticated headers, not bound by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via HMAC over the raw request body only, but the `shop`, `topic`, `api_version`, and `webhook_id` fields used by the host app to identify which tenant/shop the webhook belongs to are read straight from HTTP headers that are never included in the HMAC-signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate`/`validate_signature` computes and compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile, `Webhooks::Request#shop` simply returns the `shopify-shop-domain` (or `x-shopify-shop-domain`) header verbatim [3](#0-2) , and the constructor only checks for header *presence*, not that they are bound to the signed content [4](#0-3) .

The equality that should hold is: `shop` used to authorize/route the webhook == `shop` bound inside the HMAC-covered signable string. In this gem it instead holds: `shop (used for identification)` == `shop-domain header (attacker-controlled, unauthenticated)`, which is disjoint from `shop (covered by HMAC)` == `raw_body only`. This is analogous to the reported bug class: a value acted upon (the mint/burn recipient's effective check) is not actually covered by the guard that is supposed to protect it — here, the `shop` identity field is not covered by the cryptographic integrity check at all, even though the API's implicit design intent is that `HmacValidator.validate(request)` authenticates the whole request including which shop it claims to be from.

### Impact Explanation
If a host application uses `Webhooks::Request#shop` (as the library's own public API surface exposes it) to determine which tenant/session a webhook payload belongs to — e.g., to look up the shop's stored access token, mark uninstall, or otherwise act per-tenant — after calling `HmacValidator.validate` on the same `Request` object, it will get a false sense of authenticity for the `shop` field. An attacker who intercepts or replays any *validly-signed* webhook body from Shop A (HMAC only covers the body, and request bodies for a given topic can be structurally generic) could resubmit it with a forged `X-Shopify-Shop-Domain` header pointing at Shop B, and `HmacValidator.validate` would still return `true` because the signature check never inspects the shop header. This enables cross-tenant confusion: the host app would treat cryptographically-valid webhook content as if it originated from and applies to an arbitrary shop of the attacker's choosing.

### Likelihood Explanation
Exploitability depends on the attacker having captured at least one legitimately-signed webhook body (same `api_secret_key`-derived HMAC, but HMAC is over body only — no per-shop secret binding is enforced within the gem for the header). Since `to_signable_string` is body-only, and the gem's documented pattern (`HmacValidator.validate(request)` then `request.shop`) is exactly what's exposed via `Webhooks::Request`, this is a realistic misuse-inducing API shape rather than a purely theoretical gap.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified, or otherwise document/require that callers must independently authenticate the shop header before trusting `Webhooks::Request#shop`. Preferably, extend `to_signable_string` (or add a secondary check) so that the shop-domain header is cryptographically bound to the request, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed payload [5](#0-4) .

### Proof of Concept
1. Attacker captures a legitimately Shopify-signed webhook: headers `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: orders/create`, and body `B`.
2. Attacker resubmits the same body `B` with the same valid `X-Shopify-Hmac-Sha256` header unchanged, but replaces `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. Host app builds `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `ShopifyAPI::Utils::HmacValidator.validate(request)` [6](#0-5)  — this returns `true` because validation only hashes `B`.
4. Host app then trusts `request.shop` (`"shop-b.myshopify.com"`) [3](#0-2)  to process the webhook payload `B` (which actually belongs to shop-a) as if it were shop-b's data — a cross-tenant data/authorization confusion enabled purely by this gem's verification not covering the `shop` field.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```
