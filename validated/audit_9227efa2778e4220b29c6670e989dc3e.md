### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via header substitution - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC only over the raw request body, while the `shop` value that gets attached to the dispatched `WebhookMetadata` (and used by host applications to key tenant/session data) is read directly from an unauthenticated HTTP header. The HMAC never binds the header value to the signature, so the `shop` used downstream is not the shop that the signature actually vouches for.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight out of the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (i.e., only the body) — the header-derived `shop` plays no role in the signature check — and then immediately trusts `request.shop` to build the metadata handed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop-domain header == shop that the HMAC vouches for`. Because the HMAC is computed exclusively over the body, this equality is never enforced — the signature `HMAC(secret, raw_body)` is valid for that body regardless of which `shop-domain` header accompanies it. A merchant who has a legitimate, currently-installed copy of the app can capture one of their own genuinely-signed webhook deliveries (valid HMAC, computed by Shopify with the real `api_secret_key`, which the attacker never needs to know) and resend the identical body with the `X-Shopify-Shop-Domain` header changed to a different shop. `HmacValidator.validate` still returns `true` because the body and its HMAC are unmodified, and `Registry.process` will pass `WebhookMetadata` claiming the victim's `shop` to the app's handler, even though the payload never belonged to that shop.

This mirrors the reported bug class precisely: a value that's semantically part of the trust decision (the voting key / here, the shop identity used for tenant binding) is accepted and acted upon without being covered by the cryptographic proof (proof-of-knowledge / here, the body HMAC), letting an attacker present a fully-valid signature paired with an unverified identity claim.

### Impact Explanation
Host applications built on this gem key their per-shop session lookup, data writes, and business logic off `WebhookMetadata#shop`. If a host app trusts this value (as the gem's own contract implies it should, since it is the thing the gem exposes after "verifying" the webhook), an attacker who legitimately installed the app on their own store can forge webhook events that are attributed to an arbitrary victim shop, using a signature that is genuinely valid. This is a cross-tenant identity confusion: the gem itself resolves and returns a shop for the caller with no assurance the returned shop matches what was actually signed, satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Exploitability is straightforward for anyone who can install the app on a shop they control (a normal unprivileged flow — no `api_secret_key`, no access token, and no elevated privilege is required). The attacker only needs to capture one of their own legitimately delivered webhooks (trivial, since they control the receiving endpoint) and replay the same body with a different shop-domain header value.

### Recommendation
Bind the `shop` identity into the value that is verified: include the `shop-domain` (and ideally `webhook-id`/`topic`) header in the signable payload used by `HmacValidator`, or require the host application to independently correlate `request.shop` against a shop known to be currently installed/authorized before trusting it, and document that the header is not currently covered by the signature so integrators do not treat it as pre-verified.

### Proof of Concept
1. Install the app normally on `attacker-shop.myshopify.com`; capture a genuine webhook delivery, e.g. body `{"id":123}` with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of the body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
2. Resend the exact same body and HMAC header, but change the domain header to `victim-shop.myshopify.com`.
3. Call `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: tampered_headers))`.
4. `Utils::HmacValidator.validate` returns `true` (body/HMAC pair unchanged, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-22`), and the registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though nothing signed by Shopify ever asserted that shop for this payload.
