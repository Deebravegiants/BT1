### Title
Non-embedded session lookup trusts an unauthenticated, deterministic cookie value as the session identifier - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` is the gem's documented helper for resolving "which stored session should this request use." For non-embedded apps (and for embedded apps falling back to cookies), it returns the raw `shopify_app_session` cookie value verbatim as the session id, with no cryptographic binding to the request's shop/host and no comparison against any authenticated claim.

### Finding Description
The identity binding that should hold is:

`session_id_returned_to_caller == session_id_that_was_cryptographically_established_for_this_specific_actor`

Two things break this equality:

1. Session ids are deterministic, guessable strings computed purely from the shop domain (public information):
   - `offline_session_id(shop)` → `"offline_#{shop}"` [1](#0-0) 
   - `jwt_session_id(shop, user_id)` → `"#{shop}_#{user_id}"` [2](#0-1) 
   - Same formulas are used when a `Session` is created after OAuth: `id = "offline_#{shop}"` / `id = "#{shop}_#{associated_user.id}"` [3](#0-2) 

2. For the cookie fallback path, the gem does **no verification at all** of the cookie's authenticity or provenance — it simply returns `cookies[SESSION_COOKIE_NAME]` unmodified:
   ```ruby
   def cookie_session_id(cookies)
     cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]
   end
   ``` [4](#0-3) 

   This is reached both for non-embedded apps unconditionally, and for embedded apps when no `shopify_id_token` is supplied: [5](#0-4) 

The `SessionCookie` object itself carries no signature or MAC over its `value` — it is a plain struct (`name`, `value`, `expires`) with no HMAC field: [6](#0-5) . Contrast this with every other identity-sensitive value in the gem (OAuth callback params, webhook body) which *is* HMAC-protected via `Utils::HmacValidator` [7](#0-6) . The session cookie is the one identity-carrying value in the library with no equivalent protection baked in, and `SessionUtils` — the gem's own documented API for resolving the current session id — hands that unauthenticated string straight back to the caller as a trusted lookup key.

Because the resulting id is what the host application then uses to fetch a `Session` (containing the merchant's live access token) from its session storage, an attacker who merely knows (or guesses) a target shop's `myshopify.com` domain can compute the exact deterministic id `"offline_target-shop.myshopify.com"`, set it themselves as their own `shopify_app_session` cookie, and have `current_session_id` return it as if it had been legitimately established for their own session — with no secret, token, or credential of any kind required.

### Impact Explanation
This breaks the tenant boundary: an unprivileged internet user who merely knows a target shop's domain can cause the host application (following the gem's documented `current_session_id` API) to resolve to, and act using, the victim shop's stored `Session`/access token. This is a cross-tenant access primitive squarely within the "Critical" impact bucket (cross-tenant access via a session/identity binding never verified by this gem).

### Likelihood Explanation
High for any non-embedded integration, or any embedded integration that falls back to cookies (e.g., when the client omits an `Authorization: Bearer <session token>` header). No `client_secret`, access token, or privileged account is needed — only knowledge of the target `shop` value, which is not secret (it's the store's public `.myshopify.com` domain). The only mitigating factor — session-cookie scoping (`HttpOnly`, domain/path, `SameSite`) and comparing the resolved session's `shop` against the request's actual shop — is left entirely to the host application; the gem's own `SessionUtils` performs no such check, and this is exactly the class of gap the audit prompt calls out ("a session id derived from unauthenticated bytes").

### Recommendation
- Bind the cookie value to the request's actual shop: after resolving `cookie_session_id`, require the caller to supply (or the gem to independently derive) the expected shop for the request and assert `resolved_session.shop == expected_shop` before returning/using the id.
- Alternatively, do not use a directly guessable/deterministic string as the cookie payload; instead store a random, unpredictable session token in the cookie (mapped server-side to the deterministic id), so knowledge of the shop domain alone cannot produce a valid cookie value.
- At minimum, document prominently (and enforce via an assertion in `current_session_id`) that the returned id must be revalidated by the caller against the shop implied by the current request before being used to load a session/access token.

### Proof of Concept
1. Attacker knows (public) target shop domain `victim-shop.myshopify.com`.
2. Attacker computes the offline session id per the gem's own formula: `offline_session_id("victim-shop.myshopify.com") #=> "offline_victim-shop.myshopify.com"` [1](#0-0) .
3. Attacker sends a request to the host application with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` and no `shopify_id_token`.
4. Host application calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which — with no shop/authenticity check — returns `"offline_victim-shop.myshopify.com"` verbatim [8](#0-7) .
5. Host application looks up that id in its session store and retrieves the victim shop's `Session` (containing the real Shopify access token), then performs Admin API calls on the attacker's behalf using the victim's credentials.

          end
        end

          if is_online

          end

            shop: shop,
            access_token: access_token_response.access_token,
            scope: access_token_response.scope,
