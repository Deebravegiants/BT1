### Title
Unbounded-length `Vote.signature` panics on fixed-size buffer copy during BEEFY naive-proof decoding - (File: evm/rust/src/conversions.rs)

### Summary
`pallet-beefy-consensus-proofs::submit_proof` accepts unsigned, attacker-supplied proof bytes and, for `PROOF_TYPE_NAIVE`, ABI-decodes them into a `BeefyConsensusProof` and converts it into the internal `ConsensusMessage` type before handing it to `handlers::handle_incoming_message`. Part of that conversion chain (`From<Vote> for SignatureWithAuthorityIndex`) copies an attacker-controlled, variable-length `bytes` field straight into a fixed `[u8; 65]` array with `copy_from_slice`, without first checking the length. A `Vote.signature` of any length other than 65 bytes causes an immediate Rust panic during proof decoding, which is analogous to CVE-2025-27832's "compression buffer overflow": an untrusted, attacker-shaped input is written into a fixed-size buffer without a size check, corrupting/crashing the process that is decoding it.

### Finding Description
The dispatch path is:
`pallet_beefy_consensus_proofs::Pallet::submit_proof` (`modules/pallets/beefy-consensus-proofs/src/lib.rs:448`) → `Self::verify_and_apply(&proof)` (`modules/pallets/beefy-consensus-proofs/src/lib.rs:805`) → for `types::PROOF_TYPE_NAIVE`, ABI-decodes `ismp_abi::ecdsa_beefy::BeefyConsensusProof` and converts it `.into(): beefy_verifier_primitives::ConsensusMessage` (`modules/pallets/beefy-consensus-proofs/src/lib.rs:828-836`) → `handlers::handle_incoming_message` → BEEFY consensus client verification. [1](#0-0) 

The `Into` conversion chain bottoms out at: [2](#0-1) 

`value.signature` originates from an ABI-decoded Solidity `bytes` field inside `Vote`, which is populated from `BeefyConsensusProof.relay.signedCommitment.votes` submitted by the caller (see the `RelayChainProof -> MmrProof` conversion at `evm/rust/src/conversions.rs:368-389`, which maps `value.signedCommitment.votes.into_iter().map(Into::into).collect()` into `signatures`). Since Solidity `bytes` is a dynamic type, nothing in the ABI schema constrains its length to exactly 65 bytes. `copy_from_slice` panics whenever `sig_bytes.len() != 65`, so a single malformed `Vote.signature` (e.g. 0, 64, or 66 bytes) anywhere in the votes list triggers an unrecoverable Rust panic mid-decode.

This is the same bug class the codebase has already identified and fixed once before in a different location — `modules/utils/serde/src/lib.rs:118-136` explicitly documents that an unchecked `copy_from_slice` into a fixed `[u8;4]` from untrusted RPC input "panics on any length mismatch... and took the process down," and adds a regression test (`modules/utils/serde/src/lib.rs:529-533`) to prevent recurrence. The same defect pattern is still present, unguarded, in `From<Vote> for SignatureWithAuthorityIndex`.

I could not locate/verify the exact generated `ismp_abi::ecdsa_beefy::BeefyConsensusProof` / `Vote` Solidity type definitions in the index (the `ismp-abi` sol-bindings module was not found by search), so I cannot 100% confirm the field is an unbounded `bytes` rather than a fixed `bytes65`; this should be verified directly in the repo before treating this as fully confirmed.

### Impact Explanation
`submit_proof` is dispatchable by any unsigned account (see `ensure_none(origin)` semantics implied by the pallet's unsigned/naive proof path and `parachain/simtests/src/pallet_beefy_consensus_proofs.rs:355-387`, which shows the pallet accepting arbitrary "naive" proof bytes from any signer for malformed-payload testing). A panic during extrinsic execution inside the WASM runtime is not a normal `DispatchError` — it manifests as an unreachable trap, which every node executing/importing that block hits identically. Because BEEFY consensus updates are the mechanism by which Hyperbridge advances its trusted relay-chain/parachain state and therefore its ability to deliver ISMP messages, a reliably-triggerable panic in the consensus-proof decode path is a route-availability issue: state root advancement (and hence all message delivery gated on it) can be blocked by a single crafted proof.

### Likelihood Explanation
The trigger requires only constructing one ABI-encoded `BeefyConsensusProof` with a `PROOF_TYPE_NAIVE` prefix byte and a `Vote.signature` of a length other than 65, then submitting it as an unsigned extrinsic — no privileged role, key, or state precondition is needed. `types::PROOF_TYPE_NAIVE` accepts any properly ABI-shaped payload up to the `BoundedVec<u8, MaxProofSize>` limit (see `modules/pallets/beefy-consensus-proofs/src/lib.rs:449-455` and `parachain/simtests/src/pallet_beefy_consensus_proofs.rs:378-387`, which already exercises malformed naive-proof rejection paths, but the malformed cases tested there are ABI-decode failures, not the deeper signature-length panic described here).

### Recommendation
In `evm/rust/src/conversions.rs`, change `From<Vote> for SignatureWithAuthorityIndex` to a fallible conversion (`TryFrom`) that validates `sig_bytes.len() == 65` and returns an error instead of panicking, mirroring the fix already applied in `modules/utils/serde/src/lib.rs` for the analogous `consensus_state_id` bug. Propagate that error up through `From<RelayChainProof> for MmrProof` / `From<BeefyConsensusProof> for ConsensusMessage` (which currently assume infallible `Into`) so malformed naive BEEFY proofs are rejected with a typed `DispatchError` in `verify_and_apply` rather than panicking. Add a regression test analogous to `as_utf8_string_rejects_non_four_byte_input` that submits a `PROOF_TYPE_NAIVE` proof with a non-65-byte vote signature and asserts a graceful error.

### Proof of Concept
1. Construct a `BeefyConsensusProof` (per `ismp_abi::ecdsa_beefy::BeefyConsensusProof`) whose `relay.signedCommitment.votes` contains at least one `Vote` with `signature` set to a `bytes` value of length ≠ 65 (e.g., empty or 64 bytes).
2. ABI-encode it, prefix with `types::PROOF_TYPE_NAIVE`, and submit via `BeefyConsensusProofs::submit_proof(proof)` as an unsigned extrinsic (as exercised in `parachain/simtests/src/pallet_beefy_consensus_proofs.rs:378-387` for other malformed-naive cases).
3. Execution reaches `Self::verify_and_apply` → `BeefyConsensusProof::into::<ConsensusMessage>()` → `RelayChainProof::into::<MmrProof>()` → `Vote::into::<SignatureWithAuthorityIndex>()` at `evm/rust/src/conversions.rs:356-366`, where `signature.copy_from_slice(&sig_bytes)` panics because `sig_bytes.len() != 65`.

Note: I was unable to locate the generated `ismp_abi::ecdsa_beefy` Solidity type bindings in the index to confirm `Vote.signature`'s exact ABI type (dynamic `bytes` vs. fixed `bytes65`); this should be checked directly in the repository to fully confirm exploitability before remediation is scoped.
