### Title
Zero shares minted on deposit after bad-debt socialization drains vault backing to zero, causing depositor's principal to be donated to existing zTokens holders - (File: mainnet/contracts/vault/v0-vault-usdc.clar)

### Summary
The lending vault's share-price formula falls back to `u0` shares whenever `total-assets` (the vault's backing) is zero but `total-supply` (outstanding zTokens) is non-zero. This exact state — supply alive, backing zero — is reachable through the protocol's own normal, permissionless-triggering liquidation/bad-debt-socialization flow, not through any oracle manipulation. Because `deposit` never asserts that the computed shares (`inkind`) are non-zero (only `redeem` does), a depositor who calls `deposit` while the vault is in this state transfers real underlying tokens into the vault's `assets` variable but receives **zero** zTokens in return. Their principal is effectively donated to existing zToken holders, whose shares' backing increases at no cost to them.

### Finding Description
`convert-to-shares-preview` in every vault contract (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) computes minted shares as: [1](#0-0) 

```
(if (is-eq ts u0)
    amount
    (if (is-eq ta u0)
        u0
        (mul-div-down amount ts ta)))
```

The `ts == u0` branch (first depositor) is safe — this is the exact scenario the external report calls "doesn't really matter," since the first minter is the sole owner of supply. The dangerous branch is `ta == u0` (vault has zero backing while shares still exist) — this is exactly the scenario the report identifies as unsafe, requiring the "restrict mint / use fixed ratio" fix. In Zest's vaults, this branch is not defended: it silently returns `u0` shares.

`total-assets` is driven to (or toward) zero legitimately by `socialize-debt`, which is called by `market.clar` when a liquidated borrower has no collateral left to cover outstanding debt in a given vault: [2](#0-1) 

```
(var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
```

and is invoked from the bad-debt-socialization path in the market: [3](#0-2) 

This is a normal, expected code path (not a DAO misconfiguration or oracle-publisher issue) — it fires whenever a liquidation leaves a borrower's debt uncollateralized in a given asset vault.

Critically, `deposit` has no `(> inkind u0)` guard — only a slippage check that a zero `min-out` (the natural default) trivially satisfies: [4](#0-3) 

```
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
...
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
```

Compare with `redeem`, which explicitly guards against a zero-output edge case: [5](#0-4) 

```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```

The asymmetry (guard exists on `redeem` but not `deposit`) shows the "output must be non-zero" invariant was known to the developers but was not applied to the mint path — the same defensive gap the external report flags for `mintTokens`/`_deposit`.

**Broken identity**: shares minted vs. backing added should satisfy `sharesMinted / totalSupply == amountDeposited / totalAssets` (value-per-share conservation). Instead, when `totalAssets == 0`:
- Before: `totalAssets = 0`, `totalSupply = ts0 > 0`.
- After deposit of `amount`: `totalAssets = amount`, `totalSupply = ts0` (unchanged, since `sharesMinted = 0`).
- The depositor's `amount` of real principal is fully absorbed into the vault's assets, backing the pre-existing `ts0` zTokens, while the depositor holds 0 zTokens — a direct transfer of value from the depositor to existing zToken holders.

### Impact Explanation
This is theft of the depositor's principal (Critical/High): the underlying tokens transferred in via `receive-underlying` are irrevocably added to the vault and increase the backing/value of other users' zTokens, while the depositing account receives nothing they can redeem. It also affects the depositor's ability to ever recover the deposited funds — a permanent freezing/loss of principal for that specific transaction, satisfying the "theft of principal or unclaimed yield" / "permanent freezing of funds" bar.

### Likelihood Explanation
The zero-backing / non-zero-supply state is reached through the protocol's own designed liquidation-bad-debt-socialization mechanism (not through any oracle manipulation, flashloan trick, or DAO compromise), so it can occur under normal adverse-market conditions (e.g., a sharp price crash leaving an under-collateralized borrower with no collateral in a specific vault asset). Once that state exists, any subsequent, unaware depositor using default UI parameters (`min-out = 0`) — including a fresh, uninvolved user, not just an attacker — will lose their principal. An attacker could also intentionally front-run/trigger this to donate their own tiny amount deliberately or trick other users, but even without malicious intent the bug is triggerable by ordinary protocol operation.

### Recommendation
Add an explicit check in `deposit` (mirroring `redeem`'s `ERR-OUTPUT-ZERO` guard) requiring `(> inkind u0)`, and additionally handle the `total-assets == 0 && total-supply > 0` branch of `convert-to-shares-preview` the same way the external report's fix recommends: do not silently return `u0`; either revert the deposit, or use a fixed/bounded ratio with a capped maximum deposit amount until real backing is restored, so a "reset" mint cannot be exploited or accidentally drop a legitimate depositor's principal.

### Proof of Concept
1. A borrower opens a position collateralized only in vault X (e.g. USDC vault) and borrows against it.
2. A price move causes the position to become severely under-collateralized; a liquidator calls the liquidation entrypoint in `market.clar`, fully removing the collateral and leaving remaining debt with `no-collateral-left` true.
3. `market.clar`'s bad-debt-socialization path calls `socialize-debt` on vault X with a `scaled-amount` large enough that `principal-reduction >= current-assets`, driving `(var-get assets)` to `u0` and `lindex` to `u0` per [6](#0-5) . `total-assets-preview` for vault X is now `0`, while `total-supply` (existing zUSDC balances) remains non-zero.
4. Any user (or attacker) calls `deposit(amount, min-out=0, recipient)` on vault X. `convert-to-shares-preview` returns `u0` shares because `ta == 0` and `ts != 0`. The `(>= inkind min-out)` check (`0 >= 0`) passes.
5. `receive-underlying` pulls the depositor's `amount` of USDC into the vault; `ft-mint? zft u0 recipient` mints them nothing; `(var-set assets (+ 0 amount))` credits the vault with the deposit.
6. The depositor now holds `0` zUSDC while their `amount` of USDC now backs the existing zUSDC holders' shares, permanently increasing those other users' redeemable value at the depositor's total expense.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
