### Title
`BandwidthManager.purchase()` reverts (permanent DoS) for fee tokens with more than 18 decimals - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` scales an 18-decimal tier price down to the fee token's native decimals using `10 ** (18 - dec)`. Because Solidity 0.8 checked math reverts on underflow, any fee token configured with more than 18 decimals makes this subtraction underflow and every call to `purchase()` revert unconditionally, permanently blocking the bandwidth-purchase message route for that chain.

### Finding Description
`purchase()` computes the amount to pull from the caller as: [1](#0-0) 

```solidity
uint256 total18d = price18d * months;
address feeToken = IDispatcher(_host).feeToken();
uint8 dec = IERC20Metadata(feeToken).decimals();
uint256 scale = 10 ** (18 - dec);
if (total18d % scale != 0) revert PriceNotRepresentable();
uint256 amount = total18d / scale;
```

`dec` is read directly from the fee token configured on the host (`IDispatcher(_host).feeToken()` returns the address used across the protocol), with no upper bound check before the subtraction `18 - dec`. This is exactly the bug class from the C4 `changeFeeQuote` report: an unchecked assumption about token decimals feeding a subtraction, causing every call to underflow-revert once the assumption is violated — except mirrored to the high-decimals side instead of the low-decimals side. Tokens with more than 18 decimals do exist (documented internally as a known limitation), so `dec > 18` is a real, reachable state.

The project's own documentation for this function explicitly acknowledges the underflow but dismisses it as "not a concern in practice": [2](#0-1) 

```
1. **Fee tokens with `decimals > 18` would underflow `(18 - dec)`.** This is not a concern in practice — the supported fee tokens are all `≤ 18` decimals.
```

Once such a fee token is configured on `EvmHost`/`IDispatcher`, every `purchase()` call from any unprivileged caller reverts, and the `BandwidthPurchaseMsg` dispatch to `pallet-bandwidth` never happens — the route becomes unable to deliver bandwidth-credit messages entirely, with no way to purchase or top up bandwidth on that chain until the fee token is changed.

### Impact Explanation
This is a functional denial-of-service on the entire bandwidth-purchase path for the affected chain: no user can call `purchase()` to buy or extend bandwidth for any app, since the transaction always reverts before the `safeTransferFrom`/`dispatch` calls execute. This matches the "route unable to deliver messages" impact class. No funds are lost (the transfer never happens because of the revert), but the feature is completely inoperable for that fee-token configuration, mirroring the Medium severity and rationale given in the original finding (contingent on an edge-case token decimals value, acknowledged with no fix required since the affected class of tokens is uncommon).

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the host's `feeToken()` to be configured to an ERC-20 with more than 18 decimals (e.g., some tokens like YAM use 24 decimals). This is a governance/configuration choice rather than something an attacker can force directly, similar to how the original GUSD case depended on which base token a pool owner selected. Once such a token is configured, the DoS is deterministic and affects every unprivileged caller of `purchase()`.

### Recommendation
Guard the scaling logic to handle `dec > 18` symmetrically with `dec < 18`, e.g.:
```solidity
uint256 amount;
if (dec == 18) {
    amount = total18d;
} else if (dec < 18) {
    uint256 scale = 10 ** (18 - dec);
    if (total18d % scale != 0) revert PriceNotRepresentable();
    amount = total18d / scale;
} else {
    amount = total18d * (10 ** (dec - 18));
}
```
This avoids the underflow entirely and lets `purchase()` function correctly regardless of the configured fee token's decimals, consistent with how `VWAPOracle._normalizeAmount` already handles both directions of the decimals comparison.

### Proof of Concept
1. Deploy `BandwidthManager` and configure `IDispatcher(_host).feeToken()` to point to a mock ERC-20 with `decimals() == 24` (representing a real high-decimal token such as YAM).
2. Governance calls `SetTiers` via `onAccept` to configure a non-zero `tierPrice[tier]`.
3. Any user calls `purchase(app, tier, 1, chain)`.
4. Execution reaches `uint256 scale = 10 ** (18 - dec);` with `dec = 24`, so `18 - dec` underflows in Solidity 0.8 checked arithmetic and the entire transaction reverts with a panic, before any transfer or dispatch occurs — reproducing the same underflow-revert pattern described for `PrivatePool.changeFeeQuote` in the original report, but on the opposite (high-decimals) side of the subtraction.
