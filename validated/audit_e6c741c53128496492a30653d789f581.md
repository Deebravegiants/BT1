## Title
EvmHost relies on the live Uniswap V2 spot price (no TWAP, no slippage bound beyond `msg.value`) to price native-fee dispatches, exposing every `dispatch()`/`fundRequest()` call on L2s to atomic sandwich manipulation - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)` and `fundRequest()` convert native ETH sent with the call into `feeToken` by calling `IUniswapV2Router02.swapETHForExactTokens` directly against the configured `uniswapV2` pool [1](#0-0) . The exchange rate used is the pool's instantaneous reserve ratio at execution time - there is no TWAP, no reference-price deviation check, and no minimum-liquidity guard. This is the same bug class flagged in the external report: using a Uniswap pool as a live price oracle is unsafe on L2s, where atomic manipulation (flash-swap the pool immediately before the victim's dispatch transaction, then reverse it) is cheap and, unlike a TWAP, cannot be smoothed out because the whole quote-and-swap happens in one block.

### Finding Description
`EvmHost.dispatch()` for both POST and GET requests, and `fundRequest()`, each perform:
```solidity
address[] memory path = new address[](2);
address uniswapV2 = _hostParams.uniswapV2;
path[0] = IUniswapV2Router02(uniswapV2).WETH();
path[1] = feeToken();
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` computes the ETH required to obtain exactly `post.fee`/`get.fee`/`amount` of `feeToken` using the pool's current reserves (constant-product spot price) at the moment the transaction executes - functionally identical to reading a Uniswap price at a single block, the exact pattern the referenced Sherlock report warns against on L2s. `HyperApp.quote()`, used off-chain/on-chain by callers to size `msg.value`, reads the same unprotected spot price via `getAmountsIn` [4](#0-3) , so both the quote and the execution price come from the same manipulable source with no bound other than the caller's own `msg.value`.

Any unprivileged address can call `dispatch()`/`fundRequest()` directly - these are the primary user-facing entry points for message dispatch and are payable with native token specifically to route through this Uniswap V2 swap [5](#0-4) . Hyperbridge is deployed across many EVM chains including L2 rollups (Arbitrum orbit chains and OP-stack chains are explicitly handled elsewhere in the codebase, confirming L2 deployment) [6](#0-5) , which is exactly the environment the external report warns is unsuitable for spot Uniswap pricing due to cheap, fast atomic manipulation.

### Impact Explanation
Because the swap price is read and consumed within the dispatcher's own transaction with no TWAP/staleness/deviation protection, an attacker can sandwich a victim's `dispatch()`/`fundRequest()` call: swap heavily against the WETH/feeToken pool immediately before the victim's transaction to skew reserves, let the victim's `swapETHForExactTokens` execute at the manipulated price, then reverse the manipulation. Depending on direction, this either forces the victim to consume more ETH than the fair rate would require for the `feeToken` amount needed to cover their protocol fee (direct value extraction from users dispatching cross-chain messages), or lets an attacker acquire `feeToken` cheaply and drain pool liquidity that legitimate users depend on for correctly priced dispatches. This is a repeatable, per-transaction value-extraction vector against every native-fee payer on every chain where Hyperbridge is deployed, concentrated on L2s where such manipulation is cheapest and fastest to execute atomically.

### Likelihood Explanation
High on L2s: block production is fast/cheap, MEV searchers routinely watch for pending swaps against thin pools, and `dispatch()`/`fundRequest()` are unauthenticated, permissionless, and called by ordinary users/relayers/bandwidth purchasers with no rate limiting or price-sanity check on the Host side. The only defense is the caller bounding `msg.value` themselves (acting as `amountInMax`), which does not prevent a sandwich that still executes within that bound while draining value from the user or the pool.

### Recommendation
Do not use the raw Uniswap V2 spot price as the exchange rate for a single atomic swap. Either (a) require callers to supply an explicit `amountInMax`/minimum-output slippage bound validated against an external reference price (e.g., a TWAP oracle or Chainlink feed, as already used elsewhere in the codebase, e.g. `SimplexPaymaster._getOraclePrice`) [7](#0-6) , or (b) replace the direct spot swap with a router/wrapper that checks price deviation against a trusted reference before executing, similar to the `referencePrice`/`maxDeviationBps` guard already implemented for Simplex's Uniswap V4 pool pricing [8](#0-7) .

### Proof of Concept
1. Attacker observes a pending `EvmHost.dispatch{value: v}(DispatchPost{fee: F, ...})` transaction in the L2 mempool/sequencer queue.
2. Attacker front-runs with a large swap against the same `uniswapV2` WETH/`feeToken` pool, shifting reserves so that `swapETHForExactTokens(F, [WETH, feeToken], ...)` now requires either more or less ETH than the fair-market rate.
3. Victim's `dispatch()` executes `swapETHForExactTokens{value: v}(F, path, address(this), block.timestamp)` at the manipulated reserve ratio [1](#0-0) ; the victim overpays in ETH (excess ETH refunded per the router is sent back to `address(this)`/the Host, not the original caller) or the pool suffers a mispriced trade.
4. Attacker back-runs to reverse their initial swap, capturing the price differential, all within the same block - impossible to defend against with a TWAP-free spot price regardless of chain, but cheapest and most reliable to execute on L2s.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
