### Title
Unrefunded native-token overpayment in `IntentGatewayV2.placeOrder()` (Tron variant) permanently locks user funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder()` is `payable` and computes a running `msgValue` counter that is decremented as native-token order inputs are escrowed and as the solver fee is optionally swapped for the fee token via Uniswap, but unlike the canonical EVM `IntentGatewayV2.sol`, it never refunds any leftover `msgValue` to the caller before returning.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder()`, the function accepts `msg.value` and tracks it in a local `msgValue` variable that is reduced whenever a native (`address(0)`) input or predispatch asset is escrowed [1](#0-0) , and again when `order.fees > 0` is paid via a Uniswap swap from native token to the fee token [2](#0-1) . After that fee block, the function goes directly to emitting `OrderPlaced` and returns [3](#0-2)  — there is no "refund any unspent native tokens to the user" step.

This is a direct structural regression versus the reference EVM contract `evm/src/apps/IntentGatewayV2.sol`, whose `placeOrder()` explicitly refunds leftover `msgValue` with `_sendValue(msg.sender, msgValue)` right before emitting the same `OrderPlaced` event [4](#0-3) . The Tron file is missing this equivalent block, so any native token sent above what is strictly consumed by native inputs and the fee-token swap remains trapped in the contract balance with no bookkeeping entry (it is not credited to `_orders[commitment][address(0)]`, since only the required `order.inputs[i].amount` is escrowed, and predispatch/native-input consumption is capped at the exact `amount` fields — see lines 398-411 and 454-457).

This mirrors the reported analog exactly: a payable entrypoint that accepts `msg.value` for token movement without validating/consuming or refunding the full amount, causing a caller mistake (or intentional overpayment, e.g., when quoting a slightly larger native fee for slippage) to permanently lock native tokens in the contract, since:
- The escrow accounting (`_orders[commitment][token]`) only reflects the exact required amounts, never the excess.
- `cancelOrder`/`withdraw` paths only release amounts tracked in `_orders`, so the excess is unreachable by the user.
- There is no admin "sweep"/`DustSwept` path visible for native token surplus from `placeOrder` in the reviewed portion of the contract (only `DustCollected`/`DustSwept` events are defined for protocol-fee dust captured during escrow, not for uncredited native overpayment).

### Impact Explanation
Native token sent in excess of the exact requirement (native input amounts + native-to-fee-token swap consumption) is permanently locked in the `IntentGatewayV2` (Tron) contract balance, with no on-chain path for the depositor or an admin to recover it. This is a direct, permanent loss of user funds triggered by a single `placeOrder` transaction — satisfies "permanent freezing of funds" criteria. It is reachable by any unprivileged user placing an order and slightly overestimating the native value needed (a very common client-side quoting pattern, as shown by the SDK's own overpayment-refund expectations for the canonical EVM contract, e.g. `docs/content/developers/evm/intent-gateway/placing-orders.mdx` and the corresponding refund tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`).

### Likelihood Explanation
High likelihood of accidental triggering: SDKs/clients commonly pad `msg.value` for slippage/fee-swap buffer (as documented for the mainline contract's refund behavior), and the Tron contract silently drops this safety net. Any user or integrator who reuses the mainline SDK's value-computation logic against the Tron deployment (assuming parity with `evm/src/apps/IntentGatewayV2.sol`) will lose the overpaid amount every time they overpay, with no revert to alert them.

### Recommendation
Add the same refund step present in the canonical EVM contract: after the `order.fees` handling block and before emitting `OrderPlaced`, check `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` (or equivalent low-level call with success check) to return unspent native tokens to `msg.sender`, mirroring `evm/src/apps/IntentGatewayV2.sol` lines 394-397. Apply the same audit to `fillOrder` and any other payable entrypoints in the Tron variant to ensure consistent overpayment refunds across both same-chain and cross-chain code paths.

### Proof of Concept
1. On the Tron-deployed `IntentGatewayV2`, a user calls `placeOrder(order, graffiti)` with `order.inputs` containing one ERC20 input (e.g., USDC) and `order.fees = 0`, but attaches `msg.value = 1 ether` (e.g., due to a client bug or defensive overestimation).
2. In `placeOrder`, since the only input is an ERC20 token, the native-token branch (`token == address(0)`) is never taken, so `msgValue` remains `1 ether` throughout escrow processing (lines 451-469 branch of the else-clause without predispatch, or lines 389-449 with predispatch — neither touches `msgValue` for the ERC20 leg).
3. `order.fees == 0`, so the fee-payment block (lines 471-488) is skipped entirely; `msgValue` is never spent.
4. The function proceeds directly to `emit OrderPlaced(...)` and returns without refunding `msgValue`.
5. The `1 ether` sent by the user is now part of the contract's Tron-native balance but is not credited to any `_orders[commitment][address(0)]` entry, is not recoverable via `cancelOrder`/`withdraw` (which only releases tracked escrow amounts), and there is no sweep function shown in the reviewed contract that lets an admin or user reclaim it — the funds are permanently locked.
