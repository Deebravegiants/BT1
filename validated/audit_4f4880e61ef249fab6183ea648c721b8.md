### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's HMAC over the raw request body only, then blindly trusts the unauthenticated `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header when reporting the `shop` identity to the app's webhook handler. Because that header is not part of the signed material, an attacker who can obtain one validly-signed webhook payload (e.g., by installing the app on their own shop, which is possible for any public app) can replay that exact `raw_body`+`hmac` pair while substituting the shop-domain header for a victim shop, and the gem will report it as authentic data for the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. the body) and then immediately forwards `request.shop` — sourced from the unauthenticated header — into the handler as trusted tenant identity: [3](#0-2) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`, so it never covers the shop header: [4](#0-3) 

The identity binding that should hold is: `shop reported to handler == shop that the HMAC-secret owner (Shopify) actually signed the payload for`. In reality the gem only proves `hmac == HMAC(raw_body, api_secret_key)`; it never proves the shop header is the one Shopify associated with that body. This is exactly the "field acted on but not covered by the HMAC" class of bug: the gem authenticates bytes (the body) but parses/trusts a different, unauthenticated field (the shop-domain header) as if it had been verified together with those bytes.

Because a single app has one `api_secret_key` shared across every shop that installs it, any attacker who installs the app on their own (or any) shop can capture a legitimately-signed webhook (raw body + valid `hmac-sha256`) for that shop, and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. The HMAC check still passes (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the shop/tenant identity guarantee that host applications rely on when consuming this gem's documented webhook processing API (`docs/usage/webhooks.md` explicitly tells integrators to trust `data.shop`). An application that persists or acts on webhook data keyed by `data.shop` (a documented, intended usage pattern) can be made to attribute another shop's data to itself, or vice versa — a cross-tenant integrity issue rooted entirely in this gem's own verification logic, not misuse of the API by the host app.

### Likelihood Explanation
Any developer/attacker can obtain a public app's `client_id`/install flow on a shop they control, legitimately receive real Shopify webhooks (valid body + valid HMAC) for that shop, and then replay the captured body/HMAC pair to the target app's webhook endpoint with a forged shop-domain header, without needing the app's `api_secret_key`, an access token, or any privileged access.

### Recommendation
Include the shop-domain (and ideally topic/api-version/webhook-id) in the signable material, or otherwise cryptographically bind the shop identity to the payload before trusting it — e.g., only accept `request.shop` if it matches a shop for which the caller can independently prove ownership (such as cross-checking against a known/expected shop for the endpoint, or requiring Shopify's newer per-webhook verification metadata that ties the domain to the signature).

### Proof of Concept
1. Install the target public app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — both are valid.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which only hashes `raw_body` and succeeds [5](#0-4) ; the handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` reporting `victim.myshopify.com` even though the payload never originated from or was signed for that shop [6](#0-5) .
