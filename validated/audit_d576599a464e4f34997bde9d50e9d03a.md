## Title
Stale operator authorization reused across many signups without re-validation - ([File: src/plans/mod.rs])

### Summary
This is a valid analog to the reported bug class: a value that gates a user-facing action (fee amount / authorization) is fetched once and then reused later without being re-checked against the backend's current, potentially-changed state. In `orb-core`, the operator QR-code authorization (`OperatorData`) obtained from `verify_operator_qr_code` is cached with only a time-based expiration check, and is reused to authorize an unbounded number of subsequent user signups until that timer expires, rather than being re-validated against the backend before each signup it authorizes.

### Finding Description
When an operator QR-code is scanned, `verify_operator_qr_code` performs a single backend call to confirm the operator is `valid` and returns `location_data`, which is cached in `OperatorData { qr_code, location_data, timestamp }` [1](#0-0) .

That cached `OperatorData` is reused for subsequent signups as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, both in the main loop (`scan_initial_qr_codes`) and in the self-serve idle loop (`idle_scan_user_qr_code`), rather than re-querying the backend for the operator's current status: [2](#0-1) [3](#0-2) 

The default expiration window is 23 hours: [4](#0-3) 

`scan_remaining_qr_codes` similarly accepts the cached `operator_data` for a fresh user QR-code scan as long as it isn't expired, without a fresh backend call to `operator_status::request`: [5](#0-4) 

Each subsequent user's validation (`verify_user_qr_code` → `backend::user_status::request`) is performed against this same, potentially stale, `operator_data`, and, depending on config, the user-validation backend call may rely solely on the operator's cached location (`user_qr_validation_use_only_operator_location`) instead of any fresh operator-specific check: [6](#0-5) 

This mirrors the report's root cause exactly: a decision-relevant value (`handleOpeningFees`'s open-interest inputs / here, "operator authorization validity") is captured once, then used repeatedly for actions (fee charge / here, signup authorization) whose correctness depends on state that can change out-of-band (other traders opening positions / here, the backend revoking or updating the operator's status) between the check and its reuse.

### Impact Explanation
If the backend invalidates an operator mid-window (e.g., due to a fraud finding, distributor suspension, or location/policy change), `orb-core` will continue to accept and process user signups attributed to that operator, including the previously-fetched (now possibly incorrect) `location_data`, for up to the full `operator_qr_expiration_time` (23 hours by default). This is a misattributed-signup risk: signups get processed and recorded under an operator's authorization/location that the backend no longer considers valid, without the orb re-confirming the operator's authorization before allowing further user enrollments.

### Likelihood Explanation
Likelihood is medium: it requires either normal backend-side revocation timing to fall within an active operator caching window, or a self-serve idle loop that keeps reusing one operator authorization across many separate users over hours. Both are ordinary, non-privileged operational occurrences rather than a crafted attack, matching the "medium/medium" severity/likelihood profile of the analog report.

### Recommendation
Re-validate the operator's status against the backend (or at least re-check a shorter freshness bound) before authorizing each new user signup, rather than relying purely on the client-side `operator_qr_expiration_time` timer. Consider reducing reliance on cached `location_data`/validity across many separate user signups, and invalidate the cached `OperatorData` immediately if any backend call (e.g., during `verify_user_qr_code`) indicates the operator's authorization is no longer valid.

### Proof of Concept
1. Operator scans their QR-code; `verify_operator_qr_code` succeeds and `OperatorData` is cached with `timestamp = now`.
2. Backend subsequently marks this operator as invalid/suspended (out of band, e.g., fraud investigation).
3. Within `operator_qr_expiration_time` (up to 23h by default), `scan_remaining_qr_codes`/`idle_scan_user_qr_code` continue to accept the stale `OperatorData` (since only `elapsed() < operator_qr_expiration_time` is checked) and process further user signups under that operator's authorization/location without re-querying `backend::operator_status::request`.
