### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then hands the caller-supplied `request.shop` (from the `X-Shopify-Shop-Domain` header) to the app's handler as the authenticated tenant identifier. The HMAC, however, is computed only over the raw request body, never over the shop-domain header, so the header can be swapped to any value without invalidating the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop` is read from a separate, unsigned header: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`: [3](#0-2) 

`Registry.process` treats a successful `HmacValidator.validate` call as full authentication of the webhook, then forwards the unsigned `request.shop` straight to the handler as the tenant identifier: [4](#0-3) 

The identity binding the library claims to establish is:
`HMAC_valid(body, secret) == true` ⟺ `(body, shop) originated from shop`

But what is actually proven is only:
`HMAC(secret, body) == received_hmac`

`shop` is never part of the signed material, so the equality the app relies on does not hold. Since `secret` (the app's `client_secret`) is shared across every shop that has the app installed, any shop that installs the app receives genuinely-signed webhook deliveries `(body, hmac)` for its own store activity. The installer of that shop — an otherwise unprivileged party with respect to any other merchant using the same app — can capture a legitimately-signed `(body, hmac)` pair and re-POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to an arbitrary victim shop domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` passes the attacker-chosen `shop` value into `WebhookMetadata`, which the host application will treat as authenticated tenant data.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to guarantee: cross-tenant data injection/spoofing. A party that can obtain any one valid `(body, hmac)` pair for the shared app secret (e.g., by installing the app on a shop they control, which is the normal, unprivileged onboarding flow for any Shopify app) can make the library accept and process forged webhook events attributed to a shop domain of their choosing, without ever needing the `api_secret_key`, an access token, or any privileged credential belonging to the victim. Depending on the topic (e.g., `app/uninstalled`, `customers/data_request`, `shop/update`) this can trigger destructive or data-exfiltrating actions against a shop the attacker never had access to — a cross-tenant access impact.

### Likelihood Explanation
Exploitability only requires the attacker to be able to install the target app on any shop (a free/dev store is sufficient) and observe one legitimate webhook delivery to their own endpoint — no secret material or leaked credentials are needed. This is a realistic and low-effort path for anyone integrating with the app.

### Recommendation
Bind the shop identity into the authenticated material before trusting it: e.g., verify that `request.shop` corresponds to a shop for which the host app already has an active/authorized session before acting on the payload, and document that consumers of `Registry.process`/`WebhookMetadata` must not treat `shop` as authenticated by the HMAC alone. Alternatively, extend `to_signable_string` (or add an explicit secondary check within `HmacValidator`/`Registry.process`) to fail closed unless the shop header matches a shop known to have installed the app with the same credentials that produced the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (normal install flow, no credential theft).
2. Shopify delivers a genuine webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac over body>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes `HMAC(secret, raw_body)` and finds it matches the replayed `hmac`, returning `true` — the shop header was never part of that computation.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the host app processes/merges the forged payload as if it legitimately came from `victim-shop`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
