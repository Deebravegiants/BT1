### Title
Webhook Shop-Domain Header Not Bound by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook request signature only covers the raw JSON body. The `shop-domain` header — which the registry uses to attribute the webhook to a specific merchant/tenant — is never part of the signed data, so any attacker who can generate one *valid* signed webhook (e.g., by installing the app on their own store) can replay that exact body+HMAC pair while swapping the `shop-domain` header to point at a different, victim tenant. The HMAC check still passes because it never verified which shop the payload belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as only the raw request body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` trusts this HMAC check as proof of authenticity for the *entire* webhook, then dispatches the handler using the unauthenticated `request.shop` header value to attribute the payload to a tenant: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop attributed to webhook data (request.shop, used in WebhookMetadata) == shop actually covered by the HMAC signature (none — HMAC covers raw_body only)`.

Because an app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), an unprivileged user can:
1. Install the target app on their own (attacker-controlled) shop.
2. Trigger any webhook event and capture the resulting `raw_body` + `x-shopify-hmac-sha256` value — both perfectly valid, signed with the app's real secret.
3. Replay that identical `raw_body`/HMAC pair to the app's public webhook endpoint, but set `x-shopify-shop-domain` to a victim shop that also has the app installed.

`HmacValidator.validate` will accept the request because the body and HMAC still match each other. `Registry.process` then hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop, when it actually originated from — and was authored/controlled by — the attacker's own shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce. An app relying on this gem's webhook signature verification to safely route/attribute per-shop data (e.g., updating a shop's local order records, gating side effects on `shop`) can be made to process attacker-authored webhook content under a victim merchant's identity — a cross-tenant data injection / confusion vulnerability, without requiring any credential theft. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app author using the documented `Registry.process` + `Request` flow as-is: any user able to install the app on a shop they control (the normal, unprivileged path to using a Shopify app) can produce a validly-signed payload and then simply change one header when replaying it to the webhook endpoint, which is internet-reachable by design.

### Recommendation
Include the tenant-identifying header (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed/verified content, or otherwise cryptographically bind the shop identity to the HMAC computation rather than trusting a plain unauthenticated header. At minimum, document/require that consuming apps independently verify that the `shop` in `WebhookMetadata` matches an app-installation record they control, since this gem's `HmacValidator` alone does not guarantee that binding.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# receives (or triggers) a legitimate webhook, capturing:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
valid_hmac_b64 = Base64.encode64(valid_hmac)

# Attacker replays the exact same body/hmac to the app's webhook endpoint,
# but spoofs the shop-domain header to target a victim shop that also
# installed the same app:
headers = {
  "x-shopify-topic" => "orders/updated",
  "x-shopify-hmac-sha256" => valid_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Passes: HMAC only ever checked raw_body against the shared app secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The attacker-authored payload is now processed as belonging to the victim shop.
