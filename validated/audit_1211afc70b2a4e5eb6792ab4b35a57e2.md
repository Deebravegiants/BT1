### Title
Hardcoded `MinWithdrawal` default (18-decimal-denominated) permanently locks relayer fees on destination chains with low-decimal fee tokens - (File: modules/pallets/relayer/src/lib.rs)

### Summary
The relayer fee-withdrawal pallet defaults to a `MinWithdrawal` threshold of `10 * 10^18` (i.e., "$10" assuming an 18-decimal fee token) for any destination `StateMachine` that governance has not explicitly configured via `set_minimum_withdrawal`. This is the same bug class as the referenced Sherlock finding: a hardcoded minimum-amount constant that assumes 18 decimals, applied indiscriminately to tokens of arbitrary decimals, including 6-decimal stablecoins such as USDC/USDT.

### Finding Description
`MinWithdrawal` is a hardcoded `Get<U256>` implementation: [1](#0-0) 

It is used as the fallback minimum whenever no per-destination override exists in `MinimumWithdrawalAmount`: [2](#0-1) 

The check is performed in the unprivileged, relayer-callable `withdraw` function, which any relayer with accumulated fees on a given `dest_chain` can invoke via the `withdraw_fees` extrinsic: [3](#0-2) [4](#0-3) 

`available_amount` (the `Fees` balance) is denominated in the destination chain's configured fee token, whose decimals vary per chain/deployment (the codebase elsewhere explicitly tracks per-chain fee-token decimals distinctly — e.g. 6 for most EVM chains' USDC/USDT vs 18 on BSC pegged versions, and Substrate chains defaulting fee-token decimals to 6): [5](#0-4) [6](#0-5) 

Because `MinWithdrawal::get()` is a flat `10 * 10^18` regardless of the destination fee token's actual decimals, any destination whose fee token has fewer than 18 decimals (e.g. 6-decimal USDC/USDT) requires an amount that is decimally inflated by up to `10^12` relative to the intended "$10" threshold — i.e., `10 * 10^18` raw units of a 6-decimal token is `10^13` whole tokens, an amount that can never realistically accumulate from protocol fees. Governance can override this per-`state_machine` via `set_minimum_withdrawal`, but until that governance action happens (e.g. immediately after a new destination chain with a low-decimal fee token is onboarded via `pallet-ismp-host-executive`), the default silently applies and blocks every relayer withdrawal on that chain.

### Impact Explanation
This is a permanent freezing-of-funds bug for relayers: fees legitimately accumulated in `Fees::<T>` for a destination chain with a low-decimal fee token become practically unwithdrawable, since `available_amount < MinWithdrawal::get()` will essentially always hold. Unlike ordinary governance parameter risk, this triggers automatically as the pallet's default behavior on any newly-configured, non-18-decimal destination before an explicit `set_minimum_withdrawal` call is made — a gap during which unprivileged relayers who accumulate and try to withdraw fees are unconditionally blocked with `Error::NotEnoughBalance`, with no attacker action required. This matches the "permanent freezing of funds" acceptance criterion via a reachable path (a relayer's own `withdraw_fees` extrinsic).

### Likelihood Explanation
Medium likelihood: it materializes whenever a new destination `StateMachine` with a fee token of fewer than 18 decimals is onboarded and governance has not yet (or forgets to) call `set_minimum_withdrawal` for that specific chain — a realistic and easy-to-miss operational gap given the constant is silently used as a fallback rather than failing loudly or scaling by decimals.

### Recommendation
Do not hardcode `MinWithdrawal` in raw 18-decimal units. Instead:
- Require an explicit, decimals-aware minimum to be configured per destination chain before any fee token becomes withdrawable (fail closed rather than silently applying a wrong-decimals default), or
- Store `MinWithdrawal` in USD-equivalent terms and scale it dynamically by the destination fee token's actual decimals (as is already done elsewhere in the codebase, e.g. `tesseract/messaging/relayer/src/fees.rs`'s `10u128.pow(fee_token_decimals.into())` pattern) rather than assuming 18 decimals universally.

### Proof of Concept
1. Governance (via `pallet-ismp-host-executive`) configures a new destination `StateMachine` whose fee token has 6 decimals (e.g., a USDC-pegged token), without yet calling `set_minimum_withdrawal` for that chain.
2. A relayer accumulates fees for that destination via `accumulate_fees`, e.g. `Fees::<T>` reaches 1,000 whole tokens (`1_000 * 10^6` raw units) — an economically large, realistic balance.
3. The relayer calls `withdraw_fees`. `Self::min_withdrawal_amount(dest_chain)` returns `None`, so `MinWithdrawal::get()` (`10 * 10^18`) is used: [3](#0-2) 
4. `1_000 * 10^6 < 10 * 10^18` is true, so the call reverts with `Error::<T>::NotEnoughBalance`, and no amount of realistically-accrued 6-decimal fee tokens can ever clear this threshold. The relayer's accumulated fees remain permanently stuck until governance manually intervenes with `set_minimum_withdrawal` for that chain.
