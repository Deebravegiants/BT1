### Title
Webhook shop/topic/version identity is trusted without being covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the underlying HMAC check only authenticates the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read from unauthenticated HTTP headers and passed straight to the app's handler as the trusted tenant identity, breaking the binding between "bytes verified" and "identity acted upon."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never included in the signable string: [2](#0-1) 

`HmacValidator.validate` only compares the HMAC of `to_signable_string` (i.e., the body) against the `hmac` header value; it never touches any other header: [3](#0-2) 

`Registry.process` performs exactly that body-only check, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, handing it to the app's handler as if it were verified data: [4](#0-3) 

The documentation explicitly promises stronger guarantees than the code provides: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and the handler doc lists `shop` as one of the trusted fields available on `data`: [5](#0-4) [6](#0-5) 

The binding that should hold is: `bytes verified by HMAC == identity (shop) the app attributes the event to`. In this implementation that equality does not hold — only the JSON body is signed, while the shop-domain header used to route/attribute the event to a tenant is fully attacker-controlled once an attacker possesses any one valid `(body, hmac)` pair.

### Impact Explanation
Any unprivileged internet user who can obtain one legitimate `(raw_body, hmac)` pair — trivially available to them by installing the app on their own store (a normal, unprivileged onboarding flow) and triggering any webhook event — can replay that exact body with the same valid `hmac` header while substituting the `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers to point at a victim shop. `Registry.process` will accept it as authentic, and the handler will process attacker-controlled body content tagged as originating from the victim shop. Depending on the app's business logic (common in multi-tenant Shopify apps), this can corrupt or exfiltrate another merchant's data, trigger actions performed using the victim's stored session/access token, or otherwise achieve cross-tenant access — this maps to the Critical "cross-tenant access" impact category, since no secret credential is required, only possession of the app's own legitimate webhook traffic.

### Likelihood Explanation
High for any developer who follows the gem's documented `Registry.process` contract at face value: the doc states the method "will verify the request did indeed come from Shopify," so app authors reasonably treat `data.shop` as trustworthy tenant identity without adding their own cross-checks (e.g., verifying `data.shop` against a shop derived from an authenticated session/webhook_id lookup). No secret key, TLS interception, or privileged account is required — only the ability to install the app on an attacker-owned store, which is the normal unprivileged installation flow for any public Shopify app.

### Recommendation
Extend the webhook signature verification to bind the tenant-identifying headers to the authenticated payload, e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them), or explicitly document — in a way that cannot be missed — that `shop`/`topic`/`webhook_id`/`api_version` are NOT covered by the HMAC and must be independently validated by the host application (e.g., by cross-referencing against the shop derived from the app's own stored sessions before trusting webhook attribution). At minimum, update `docs/usage/webhooks.md` to stop asserting that `process` verifies the request "did indeed come from Shopify" for headers as a whole, since today only the body is verified.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (normal, unprivileged flow) and registers/receives any webhook, e.g. `orders/create`. Shopify sends:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-webhook-id: <id>`
   - Body: `{"id": 1, "note": "attacker-controlled content"}`
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but swaps the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses this fine (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes HMAC over the (unchanged) body and secret — validation succeeds because the body was never altered.
4. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...}, ...)` and invokes the app's handler as though this event legitimately originated from `victim-shop.myshopify.com`, even though it was fully attacker-controlled data originally generated for `attacker-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
