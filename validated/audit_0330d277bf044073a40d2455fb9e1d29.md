Based on my investigation, I found a genuine identity-binding gap in the webhook processing path.

### Title
Webhook shop/topic identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the **body bytes** were signed by the holder of `api_secret_key` [2](#0-1) . The `shop`, `topic`, and `webhook_id` values consumed downstream come straight from HTTP headers that are never part of the signed payload [3](#0-2) .

### Finding Description
`Registry.process` validates only the HMAC-over-body, then dispatches to the handler for `request.topic` using `request.shop` taken from the (unauthenticated) header value: [4](#0-3) 

The equality the HMAC is supposed to enforce is:
`bytes_verified_by_hmac == bytes_the_app_acts_on`

Here that equality is broken: `bytes_verified_by_hmac = raw_body` only, while `bytes_the_app_acts_on = (raw_body, shop-domain header, topic header, webhook-id header)`. Because `api_secret_key` is the app's single shared secret across every merchant that installs the app (it is not shop-specific), any shop that has the app installed receives legitimately-signed `(raw_body, hmac)` pairs. Since the headers are excluded from the signature, an attacker who controls one installed shop can capture a valid `(raw_body, hmac)` pair from their own webhook traffic and resend it to the app's public webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header. `HmacValidator.validate` still returns `true` (the body signature checks out), and `Registry.process` will happily route the payload to the handler registered for the attacker-chosen topic while stamping it with the attacker-chosen `shop` in `WebhookMetadata` [5](#0-4) .

Any host application that trusts `WebhookMetadata#shop` (returned by the gem) as an authenticated tenant identifier — which is the documented/expected usage pattern, since the gem provides no other shop-authentication primitive for webhooks — will process/store attacker-supplied data under another merchant's identity, i.e., a cross-tenant data-injection/confusion primitive.

### Impact Explanation
This crosses a tenant boundary: the `shop` value that the host application uses to key data (session lookup, per-shop storage, mandatory GDPR topics like `customers/redact`, `shop/redact`) is attacker-controlled despite HMAC verification succeeding. This matches the Critical "cross-tenant access" impact category, since it lets one merchant's/attacker's traffic be attributed to and processed as belonging to a different, arbitrary shop.

### Likelihood Explanation
Exploitation requires the attacker to operate any shop that has the target app installed (a normal, unprivileged merchant/developer relationship, not a privileged account) so they can capture one legitimate `(body, hmac)` webhook pair, then replay it toward the app's public webhook endpoint with modified `shop-domain`/`topic` headers. No access to `api_secret_key`, tokens, or TLS interception is required — only observing traffic to one's own installed test/dev store, which is trivially available to any developer.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api-version`) in the HMAC-signed payload construction, or otherwise cryptographically bind the shop/topic to the signed body before they are used to route/tag webhook data in `WebhookMetadata`. At minimum, document that consuming applications must independently verify the `shop` header against their own list of shops with an active/expected webhook subscription before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and observes a legitimate webhook delivery, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header value (a valid signature over `raw_body` using the app's shared `api_secret_key`).
2. Attacker POSTs to the app's public webhook endpoint reusing the exact same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: customers/redact` (or any registered topic of choice)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers [6](#0-5) , and `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `raw_body`, which is unchanged [7](#0-6) .
4. `Registry.process` dispatches the handler for `customers/redact` with `WebhookMetadata#shop == "victim-shop.myshopify.com"` [4](#0-3) , even though `victim-shop` never sent this webhook — demonstrating the host app will process attacker-controlled data under another shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
