### Title
Webhook `shop-domain`/`topic` identity is not covered by the HMAC signature, allowing tenant-attribution confusion in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and event `topic` exclusively from HTTP headers, while the HMAC signature that `Utils::HmacValidator` checks only covers the raw request body. This breaks the intended identity binding: `HMAC-authenticated bytes == request.shop`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop`/`#topic` are read straight from the `shopify-shop-domain`/`shopify-topic` headers with no cryptographic tie to the signed payload [2](#0-1) .

`Utils::HmacValidator.validate` computes the expected signature purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` header via `OpenSSL.secure_compare` [3](#0-2) . Nothing in this computation includes `shop-domain` or `topic`.

`Registry.process` trusts this validation and then forwards the unauthenticated `request.shop` and `request.topic` straight to the registered handler as the tenant/event identity: `raise ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

Because the same body bytes and HMAC digest are valid for *any* combination of `shop-domain`/`topic` headers (they are not part of the signed content), an attacker who can trigger a captured/legitimate webhook delivery for one topic/shop (e.g., a webhook fired for their own store, or any request whose exact raw body they can reproduce/observe) can resend that identical body+hmac pair to the app's public webhook endpoint with a different `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it only re-derives the signature from the body, and `Registry.process` will attribute the payload to the attacker-chosen shop.

Equality that should hold but doesn't: `authenticated_shop (bound by HMAC) == request.shop (header used by handler)`. In this gem's implementation, the left side does not exist — no shop identity is signed at all.

### Impact Explanation
This maps to the "cross-tenant access" impact category: a handler that trusts `WebhookMetadata#shop`/`#topic` to key its persistence layer, cache, or authorization decisions (a normal integration pattern encouraged by this gem's docs, e.g. `usage/webhooks.md`) can be made to process or store data under the wrong tenant record, or dispatch to the wrong topic-specific handler logic, purely by manipulating headers on an otherwise-valid signed request. The HMAC check gives developers a false sense that `request.shop`/`request.topic` are authenticated, when only the body bytes are.

### Likelihood Explanation
Exploitability is bounded by the attacker's ability to obtain one valid `(raw_body, hmac)` pair for the target app's secret — which happens naturally any time the attacker's own shop has the app installed and a webhook fires (this requires no privileged credentials, `api_secret_key`, or access tokens; it is simply capturing/replaying an HTTP POST the attacker's own store legitimately received/triggered). The endpoint accepting the POST is public, unauthenticated at the transport level (only HMAC-checked), and the header manipulation requires nothing beyond standard HTTP client control by any internet-reachable actor sending requests to the app's webhook path.

### Recommendation
Include the tenant/event identity headers in the signed material, or otherwise cryptographically bind them:
- Extend `Request#to_signable_string` (or add a separate verification step) to incorporate `shop-domain` and `topic` alongside the raw body before computing/verifying the HMAC, or
- Have `Registry.process`/`HmacValidator` explicitly validate that `shop-domain` matches an expected/registered shop for the given HMAC context (e.g., cross-check against a known-shop allowlist or session lookup) rather than trusting the header verbatim, and document to consumers that `WebhookMetadata#shop` is header-derived and must be independently corroborated before being used as a tenant key.

### Proof of Concept
```ruby
# Attacker controls their own shop "attacker.myshopify.com" which has the target app installed.
# Shopify sends a legitimate signed webhook to the app's endpoint:
body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)

# Attacker captures this exact (body, hmac) pair (e.g. via a proxy on their own store's webhook flow)
# and replays it directly to the app's public webhook endpoint, but swaps the shop-domain header:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # arbitrary, attacker-chosen
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) passes because it only checks `body` against `hmac`;
# the handler receives WebhookMetadata with shop == "victim-shop.myshopify.com",
# even though Shopify never sent this data for that shop.
```
