### Title
Webhook `shop` (tenant) field is not covered by the HMAC signature, allowing cross-tenant shop-domain spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, but its `to_signable_string` only returns the raw request body, while the `shop` (tenant identity) is read from an unauthenticated HTTP header. `Registry.process` validates only the HMAC-over-body and then forwards the header-derived `shop` value to the app's handler as if it were an authenticated tenant identifier.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is read directly from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, which is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and, once that check passes, immediately trusts the header-derived `shop` and forwards it to the app-supplied handler as the tenant identity, with no binding between the verified bytes (body) and the claimed tenant (header): [3](#0-2) [4](#0-3) 

Because the HMAC only proves "this body was produced with the app's `client_secret`" and says nothing about which shop it came from, an attacker who can obtain one legitimately-signed webhook delivery (e.g., from their own trial/dev store subscribed to the multi-tenant app) can replay the identical `body`+`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still succeed because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim's `shop`, breaking the equality "shop authenticated by the HMAC" == "shop used as the tenant/session key" for any application that trusts `WebhookMetadata#shop` to select or scope tenant data/session records.

### Impact Explanation
This is a cross-tenant identity confusion vector: the gem allows the header-derived `shop` to reach application code as if it were bound to the cryptographically verified body, enabling an attacker-controlled tenant claim on an otherwise "verified" webhook. Applications built on this gem's documented API (using `WebhookMetadata#shop` post-`Registry.process`) are exposed to cross-tenant processing of attacker-replayed events (e.g., writing/mutating data keyed by the spoofed shop, or acting on behalf of a shop the attacker does not own) without needing the app's `client_secret`, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires an attacker to (a) control a store that can trigger a real webhook delivery from Shopify (trivial — any developer/trial store can install the app and produce arbitrary webhook events), and (b) intercept/relay that raw body + signature to the target app's webhook endpoint with a modified shop header, which any external actor able to reach the app's public webhook URL can do. No credentials, tokens, or the app's secret are needed to mount the attack, only the ability to capture one's own legitimately-issued webhook once.

### Recommendation
Bind the tenant identity into the verified material: either include the `shop` (and `topic`/`webhook-id`) in the signable string used for HMAC comparison, or have `Registry`/`Request` cross-check the header-derived `shop` against an independently-authenticated source (e.g., a value looked up from a session store keyed only by data proven inside the signed body, or require the host app to separately authenticate the delivery, such as comparing against known/registered shop domains and webhook IDs) before constructing `WebhookMetadata`. At minimum, the gem's documentation and `WebhookMetadata` should clearly flag that `shop`, `topic`, `api_version`, and `webhook_id` are **not** cryptographically bound to the HMAC and must not be treated as trusted tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target multi-tenant app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify computed with the app's shared `client_secret`.
2. Attacker replays this exact `body` to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, spoofed `webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== raw body only) — this succeeds because the body and secret are unchanged. [5](#0-4) 
4. Processing continues, and the handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, i.e., attacker-controlled tenant identity presented as verified. [6](#0-5)
