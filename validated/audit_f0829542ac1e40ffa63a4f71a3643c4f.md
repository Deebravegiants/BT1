### Title
Webhook cross-tenant spoofing — `shop` and `topic` fields are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated for a given shop/topic once `Utils::HmacValidator.validate(request)` passes, but the HMAC only ever covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken directly from unauthenticated HTTP headers — are trusted and handed to the app's handler as if Shopify had vouched for them.

### Finding Description
The gem's own documentation states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and that `data.shop` in the handler is "The shop domain of the webhook" [2](#0-1) .

In `ShopifyAPI::Webhooks::Request`, `hmac` and `shop` (along with `topic`, `api_version`, `webhook_id`) are all parsed straight out of request headers: [3](#0-2) 

Critically, `to_signable_string` — the value that is actually HMAC-verified — returns only the raw body, never the headers: [4](#0-3) 

`Utils::HmacValidator.validate_signature` computes the expected signature purely from `to_signable_string` (the body) and compares it to the `hmac` header: [5](#0-4) 

`Registry.process` then raises only if this body-only HMAC check fails, and immediately builds `WebhookMetadata` using `request.shop` and `request.topic` — values that were never part of the signed material: [6](#0-5) 

The identity binding that should hold is:
`shop authenticated by Shopify (bound into the signature)` == `shop used by the app (request.shop header)`

In this implementation that equality does not hold — the left side is empty (no shop-binding at all in the HMAC), while the right side is a bare, attacker-controlled header.

**Attack path (no privileged credentials required):** Any unprivileged internet user who is a merchant with the app installed on their own store (Shop A) receives genuine, correctly-HMAC-signed webhook deliveries from Shopify for Shop A. Since the signature covers only the JSON body (which for many topics contains no shop identifier at all, e.g. `orders/create`, `products/update`), the attacker can capture one such legitimate `(body, hmac)` pair and replay it directly to the app's public webhook endpoint while substituting `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant) and/or a different `x-shopify-topic`. `HmacValidator.validate` still succeeds because it only checks the body against the real secret-derived HMAC, which is unchanged. The app's handler then processes data it believes originates from Shop B, using Shop B's identity.

### Impact Explanation
This breaks the shop/tenant identity boundary that the entire webhook subsystem is documented to enforce: “verify the request did indeed come from Shopify” for the shop in question. Downstream host applications (per the gem's documented contract) rely on `data.shop` to route work, invalidate caches, write records, or trigger merchant-specific side effects (e.g. enqueuing jobs keyed by `shop_domain`, as shown in the gem's own webhook example). An attacker can inject falsified events attributed to a shop they do not own/operate, forge `shop/redact` or `customers/data_request` compliance events for arbitrary shops, or trigger business logic under another tenant's identity — a cross-tenant integrity/authenticity violation reachable by any unprivileged holder of the app on any single shop, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for topics whose JSON bodies do not embed the shop domain (most resource webhooks describe only the resource, not the originating shop) — an attacker only needs to be a legitimate merchant on the app (trivially obtainable, unprivileged) to harvest one valid `(body, hmac)` pair, and the webhook receiver endpoint is by design a public, unauthenticated internet endpoint that accepts POSTs from anyone, not just Shopify's IP ranges (nothing in this gem enforces source restriction).

### Recommendation
Bind the identity fields into the authenticated material. Since Shopify's own HMAC spec does not include headers, the header-derived `shop`/`topic`/`webhook_id` must not be treated as authenticated for cross-shop-sensitive decisions unless independently corroborated — e.g., cross-check `request.shop` against the shop associated with a `webhook_id`/subscription previously registered via `register_all`/`register` for that shop, or require the host app to validate `shop` against its own session store before trusting it, and document explicitly (more strongly than currently) that `shop`/`topic`/`webhook_id` headers are *not* covered by the HMAC and must be independently validated by the consuming application before being used to look up or mutate tenant data.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate `orders/create` webhook, capturing:
   - body: `{"id":123,...}` (no shop field)
   - header `x-shopify-hmac-sha256: <valid signature over body>`
2. Attacker POSTs to the app's public webhook endpoint with:
   - same body and same `x-shopify-hmac-sha256`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds (body unchanged), `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the host app to act as if the event originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
