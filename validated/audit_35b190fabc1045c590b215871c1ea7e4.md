Confirmed: `evm/tron/contracts/apps/IntentGatewayV2.sol` has **no `nonReentrant` modifier anywhere** in the contract, unlike the mainline `evm/src/apps/IntentGatewayV2.sol` (`cancelOrder` there is `nonReentrant`). This confirms the Tron port lacks the reentrancy guard present in the audited mainline implementation.

### Title
Reentrant escrow drain via checks-effects-interactions violation in `withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
CVE-2022-3046 is a Chrome use-after-free where a freed object is still reachable and reused before its state is properly torn down. The structural analog here is `withdraw()` in the Tron `IntentGatewayV2`, which performs the external token/native transfer for each escrowed asset *before* decrementing the corresponding `_orders[commitment][token]` balance — i.e. the "resource" (escrow slot) is used/handed out via an external call while the bookkeeping that should have "freed" it has not yet executed, and the contract additionally lacks any reentrancy guard (`nonReentrant`) on the public entry points that reach this state.

### Finding Description
In `withdraw()`: [1](#0-0) 

the loop reads `_orders[body.commitment][token]`, performs the external call (`beneficiary.call{value:amount}("")` for native tokens, or `token.call(...transfer...)` for ERC20s), and only *afterwards* executes `_orders[body.commitment][token] -= amount;`. This is a classic checks-effects-interactions violation: the balance that should be consumed ("freed") is still non-zero/stale at the moment external code runs.

Contrast with the mainline EVM implementation, `IntentsBase.sol::_withdraw`, which decrements storage *before* the external transfer: [2](#0-1) 

and whose `cancelOrder` entry point is explicitly `nonReentrant`: [3](#0-2) 

The Tron variant's `cancelOrder` has the identical `_filled[commitment]` check-then-branch structure but is declared without `nonReentrant`: [4](#0-3) 

`withdraw()` is reached from `onGetResponse` (cancel-from-source path, `onlyHost`) and from the `onAccept` handler for `RedeemEscrow`/`RefundEscrow` post requests — the beneficiary in the `RedeemEscrow` path is the solver, who is an unprivileged, attacker-controllable address (it can be a malicious contract), and for native-token escrow the transfer target is `beneficiary.call{value: amount}("")`, which forwards all gas and permits arbitrary reentrant execution in the receive/fallback function before `_orders[commitment][token]` is decremented.

### Impact Explanation
Because `_filled[body.commitment]` is set once at the top of `withdraw()` before the loop, straightforward re-entry into `cancelOrder`/`fillOrder` for the *same* commitment is blocked by the `Filled()` check — this limits, but does not eliminate, exploitability. However, any order whose `inputs`/`tokens` array contains more than one asset lets the attacker-controlled beneficiary reenter during the transfer of asset #1 (native ETH/TRX via low-level `call`) and call back into `withdraw`-reachable public paths for *other, independent* order commitments that also hold escrow, or interact with any other contract state that depends on the not-yet-updated `_orders` mapping, since none of the public functions in this file are reentrancy-guarded. At minimum, the missing decrement-before-interaction ordering combined with a completely absent `nonReentrant` guard is a materially weaker security posture than the mainline contract it mirrors, and any future code path (or an ERC-20 with transfer hooks, e.g. ERC-777-style tokens) that reads `_orders[commitment][token]` between the transfer and the decrement, or that permits a second concurrent `withdraw` call for the same commitment via a different message path, will result in double-payout of escrowed funds — permanent loss of protocol/user funds.

### Likelihood Explanation
Reachable from a single relayed cross-chain message (`RedeemEscrow`) whose beneficiary is chosen by an unprivileged solver, requiring no admin/governance privilege — only that the solver deploys a malicious beneficiary contract and multi-asset orders are used (a normal, permitted order shape). The absence of `nonReentrant` throughout this file, unlike its sibling mainline implementation, indicates this hardening was dropped/never ported, raising confidence that this divergence is a genuine regression rather than an intentional simplification specific to Tron's semantics (Tron's TVM still supports reentrant low-level calls the same way EVM does).

### Recommendation
Port the mainline `IntentsBase.sol` pattern to `evm/tron/contracts/apps/IntentGatewayV2.sol`: decrement `_orders[body.commitment][token]` before performing the native/ERC20 transfer in `withdraw()`, and add a `nonReentrant` modifier (or equivalent reentrancy guard) to `cancelOrder`, `fillOrder`, and any other public entry point that can trigger `withdraw()`.

### Proof of Concept
1. Place a cross-chain order with two input assets: native TRX and an ERC20 token, both escrowed under the same `commitment`.
2. As the solver, fill the order on the destination chain with `beneficiary` set to an attacker-controlled contract.
3. When the settlement `RedeemEscrow` message is delivered to `onAccept` → `withdraw()` on the source chain, the loop processes the native-TRX leg first: `beneficiary.call{value: amount}("")` invokes the attacker contract's fallback *before* `_orders[commitment][nativeToken] -= amount` executes.
4. In the fallback, the attacker calls any other public function on the gateway (e.g., initiates a fill/cancel for a different order, or — if the ERC20 leg uses a hook-capable token — reenters mid-loop) while `_orders[commitment][...]` for the not-yet-processed ERC20 leg is still fully populated and the contract holds no reentrancy lock, enabling drainage of escrow that should not yet be spendable.

Note: I could not fully verify a complete, self-contained double-spend transaction trace within the current investigation due to the complexity of cross-contract call graphs and time budget; the `_filled` guard does block the most direct same-commitment double-`withdraw` scenario. The core, concretely provable defect is the checks-effects-interactions violation and complete absence of `nonReentrant` in this file relative to the audited mainline contract, which is a real regression warranting a fix regardless of whether a fully chained PoC across multiple orders is constructed.
