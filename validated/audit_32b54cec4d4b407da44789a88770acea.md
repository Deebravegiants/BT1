### Title
Webhook shop identity spoofing — `Registry.process()`/`Request#shop` trust a header not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the handler a `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed payload. Anyone who can obtain one validly-signed webhook body (e.g. by installing the app on their own store, since the HMAC secret is the app's shared `api_secret_key`, not shop-specific) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop` header, and the request will still pass verification.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string` against the received `hmac`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only `@raw_body`, and `Request#hmac`/`Request#shop` are both derived from unauthenticated HTTP headers: [2](#0-1) [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof of authenticity for the whole request and then forwards `request.shop` (the header value) to the handler as the trusted tenant identity: [4](#0-3) 

The identity binding that should hold is: `shop asserted in X-Shopify-Shop-Domain == shop whose secret produced the HMAC`. Because the HMAC covers only the body bytes and is computed with the app-wide `api_secret_key` (shared across every shop that installs the app, not a per-shop secret), that binding is never checked. Before the attacker's request: a legitimate webhook for shop A has body `B`, and `HMAC(secret, B)` valid, `shop header = A`. After the attacker's replay: the same body `B` and same valid `HMAC(secret, B)` are sent with `shop header = victim`, and `Registry.process` accepts it as an authentic webhook "from" `victim`, since the shop header is checked nowhere against the signature or against any known-installed-shop list.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications are documented to rely on (`WebhookMetadata.shop` is passed straight to the handler as the source of truth): see the webhook processing example in the docs where the handler is invoked with the request's `shop` value implicitly trusted as authenticated. An attacker who has installed the app on any shop (a normal, unprivileged action requiring no special credentials) can generate one legitimate signed payload, then replay it against the app's public webhook endpoint with a forged `shop` header pointing at a victim's shop domain, achieving cross-tenant data injection (e.g., orders/customer/redact data attributed to a shop the attacker never controls) without possessing that shop's access token or secret.

### Likelihood Explanation
Likelihood is Medium-to-High for apps that trust `WebhookMetadata.shop` as the tenant key (as the gem's own documentation encourages): the webhook HTTP endpoint is public, the attacker only needs a normal app install to obtain one valid signed body, and header spoofing on an unauthenticated POST is trivial. No secret, token, or privileged access is required — only that the attacker be able to install the app once on any store.

### Recommendation
Bind the asserted `shop` (and ideally `topic`/`webhook_id`) into the value that is cryptographically verified, not just the raw body — e.g., include the shop domain in the signable string, or require the caller to independently confirm that `request.shop` corresponds to a shop with an active app installation/session before trusting the value in `WebhookMetadata`. At minimum, document prominently that `Request#shop` is unauthenticated and must be cross-checked by the host application against known installed shops before use.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` that Shopify sent (`H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B`, the same header `H`, but with `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...spoofed shop...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` — it succeeds because `H` was genuinely produced from `B` and the same shared `api_secret_key`. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)`, and the app processes attacker-controlled data as if it originated from `victim.myshopify.com`.
