### Title
Hardcoded `eth_wallet_global_contract_hash` constant can desynchronize ETH-implicit accounts from the real wallet contract - ([File: runtime/near-wallet-contract/src/lib.rs])

### Summary
The reported Solidity bug is a class of "hardcoded/derived-address constant mismatch": `POOL_INIT_CODE_HASH` is a compile-time hash constant that must exactly match the runtime hash of deployed contract bytecode, and any mismatch makes address computation diverge from the real deployed contract, breaking every downstream operation that depends on it. Nearcore has a structurally identical construct: `eth_wallet_global_contract_hash()` in `runtime/near-wallet-contract/src/lib.rs` returns hardcoded, per-chain `CryptoHash` byte-array constants for `MAINNET`/`TESTNET`/`MOCKNET` that are supposed to equal the hash of the actual deployed global wallet contract on that chain. [1](#0-0) 

### Finding Description
When an ETH-implicit account is created via a `Transfer` action (`action_implicit_account_creation_transfer`), and the `EthImplicitGlobalContract` protocol feature is enabled, the runtime sets the new account's contract to `AccountContract::Global(global_contract_hash)`, where `global_contract_hash` comes directly from the hardcoded constant returned by `eth_wallet_global_contract_hash(chain_id)`: [2](#0-1) 

This hash is never derived at runtime from the actually-deployed global contract's bytecode — it is baked into the binary as literal bytes per chain ID: [1](#0-0) 

If this hardcoded constant does not match the hash of the wallet contract that was actually deployed as a global contract on that chain (e.g., due to a WASM build/version mismatch, wrong bytes copied at release time, or an update to the wallet contract without updating this constant), every account created via `AccountContract::Global(hash)` would reference a code hash for which no matching global contract exists in state. This is directly analogous to the reported bug: an incorrect hardcoded hash used to locate/identify a deployed contract, causing the dependent operation (minting positions in the Solidity case; executing wallet-contract calls for ETH-implicit accounts here) to fail.

### Impact Explanation
If the constant is wrong for a live network, every ETH-implicit account (`0x...` accounts) created after the `EthImplicitGlobalContract` feature activates would be permanently bound to a non-existent (or wrong) global contract. Function calls against these accounts (the `rlp_execute` wallet-contract flow used to relay Ethereum-style transactions) would fail at execution (analogous to `GlobalContractDoesNotExist`), effectively bricking every such account: users could receive funds (the account is created by `Transfer`) but could never execute a transaction from it, since ETH-implicit accounts cannot have a `CreateAccount`/`AddKey` full-access key added and are usable only through the wallet contract. This would be a chain-wide denial of service on a whole account-type/class rather than affecting a single user, and would require a protocol upgrade to fix, matching the "critical" severity of the analog report (mint function reverts for all users).

### Likelihood Explanation
This is not an externally-triggerable attack — it is a build/release integrity risk: the hash is a hardcoded literal that must be kept in lockstep with the WASM binary the network operator actually deploys as the global contract, similar to how `POOL_INIT_CODE_HASH` in the report had to be kept in lockstep with the compiled pool bytecode. There is a unit test (`test_eth_wallet_global_contract_hash_values`) asserting the mainnet/testnet constants against expected values, which reduces (but does not eliminate) the chance of this drifting silently, since the test would need to be updated in lockstep with any change to the deployed contract without correspondingly verifying against the actually-deployed on-chain global contract. [3](#0-2) 

### Recommendation
Rather than relying purely on a hardcoded, hand-maintained hash constant per chain, cross-check `eth_wallet_global_contract_hash(chain_id)` against the hash of the wallet contract binary embedded in the same crate (`MAINNET`/`TESTNET`/`LOCALNET` `WalletContract` statics) at compile time or via a stronger integration/release test that queries a live/genesis state for the actual on-chain global contract hash and asserts equality, so any future update to the wallet contract WASM without updating this constant is caught before release rather than causing production account bricking.

### Proof of Concept
Not directly reproducible as a transaction-triggerable exploit within this codebase snapshot; this is a build-time/release-integrity issue rather than a runtime-exploitable bug in the currently indexed source (the current hardcoded values pass the existing unit test at `runtime/near-wallet-contract/src/lib.rs:193-202`, and I could not verify against live mainnet/testnet state whether the constant currently matches the deployed global contract, since that is outside the scope of the indexed repository). The reachable path once a mismatch is (re-)introduced is: `Transfer` to `0x...` address → `action_implicit_account_creation_transfer` → `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` → any subsequent function call to that account fails to resolve the global contract code.
