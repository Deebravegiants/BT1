### Title
`prepareSwapSignedData` (STELLAR_SEP53) derives `public_key` from `userInfo.userAddress` without verifying it matches the ed25519 key that produced `signatureData` - ([File: packages/internal-utils/src/utils/prepareBroadcastRequest.ts])

### Summary
In the `STELLAR_SEP53` branch of `prepareSwapSignedData`, the outgoing `public_key` field is built exclusively from `userInfo.userAddress` (converted via `stellarAddressToBytes` + base58), while the `signature` field is built from `signature.signatureData` independently. The only check performed is `assert(userInfo.userChainType === "stellar", ...)`, which never ties `userAddress` to the actual key that signed the payload.

### Finding Description
The equality that must hold for the relayed intent to be valid is:

`public_key (sent to relay) == key-that-produced(signature.signatureData)`

Code path, `packages/internal-utils/src/utils/prepareBroadcastRequest.ts` lines 69-83:
```
case "STELLAR_SEP53": {
	assert(
		userInfo.userChainType === "stellar",
		"User chain and signature chain must match",
	);
	return {
		standard: "sep53",
		payload: signature.signedData.message,
		public_key: `ed25519:${base58.encode(
			stellarAddressToBytes(userInfo.userAddress),
		)}`,
		signature: transformED25519Signature(signature.signatureData),
	};
}
```
`public_key` is derived solely from `userInfo.userAddress` (attacker/caller-supplied string), `stellarAddressToBytes` (`packages/internal-utils/src/utils/stellarAddressToBytes.ts`) just decodes the Stellar strkey to raw ed25519 bytes - it does not derive anything from `signature.signatureData`. `signature` is derived solely from `signature.signatureData` (the raw ed25519 signature bytes), independent of `userAddress`. There is no code anywhere in this function, in `publishIntent` (`packages/internal-utils/src/solverRelay/publishIntent.ts`), or in `publishIntents` that cross-verifies `userAddress` against the signature (e.g., by verifying the ed25519 signature against the derived public key locally before sending). The only guard, `assert(userInfo.userChainType === "stellar", ...)`, checks a chain-type tag, not key ownership.

The identical structural weakness exists in the `SOLANA` branch (lines 40-51), where `public_key` is likewise taken straight from `userInfo.userAddress` with no signature binding — confirming this is a systemic pattern in this function, not an isolated typo.

Exploit flow: an attacker who controls the calling flow (e.g., a malicious/compromised wallet-adapter layer, or any caller of `publishIntent`/`prepareSwapSignedData` that lets these two arguments be supplied independently) signs the intent payload with their own keypair A, but passes `userInfo.userAddress` set to victim B's Stellar address. `prepareSwapSignedData` will happily emit `signer_id`/`public_key` = B's address, and `signature` = a valid SEP-53 signature — but produced by A, not B. The resulting `signed_data` claims B authorized the payload while only A actually signed anything.

### Impact Explanation
This breaks the fundamental invariant that the `public_key` field forwarded to the solver relay/intents contract must be the key that actually produced the signature. If the downstream relay/contract trusts the `public_key` field as-is (matching the described threat model: "the intents contract's own signature and nonce verification" is what the audit says should be checked, but from this file's perspective, the SDK is producing a `signed_data` object where the stated signer and the actual signer of the bytes can diverge before it ever reaches the contract). Whether this is fully exploitable end-to-end depends on whether `intents.near`'s own SEP-53 verification recomputes the address from the signature (out of scope per the rules — "defects inside intents.near ... with no path through this repo" is excluded), but the SDK-side function itself is the root of the divergence and is squarely in scope as a repo-level bug: it manufactures a `signed_data` payload with an unverified binding between `public_key` and `signature`.

### Likelihood Explanation
Preconditions: the attacker/caller must be able to invoke `prepareSwapSignedData`/`publishIntent` with `signatureData` and `userInfo` supplied from different, uncorrelated sources (e.g., a caller that lets `userAddress` be attacker-controlled input string while the signature comes from the attacker's own wallet). This is plausible for any integrator or wallet flow built on top of this SDK function since the function signature explicitly takes `signature` and `userInfo` as two separate, independently-suppliable parameters with no internal cross-check.

### Recommendation
Derive `public_key` from the same source used to produce/verify `signatureData` (i.e., have the caller supply the ed25519 public key used for signing, or verify the SEP-53 signature locally against the public key derived from `userInfo.userAddress` before constructing the payload), and assert that verification succeeds rather than only asserting chain-type equality. Apply the same fix to the `SOLANA` branch, which has the identical pattern.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import * as ed25519 from "@noble/ed25519"; // or equivalent used in repo
import { prepareSwapSignedData } from "../prepareBroadcastRequest";
import { stellarAddressToBytes } from "../stellarAddressToBytes";
import { base58 } from "@scure/base";

describe("STELLAR_SEP53 public_key/signature binding", () => {
  it("allows attacker keypair A signature to be bound to victim B's address", () => {
    // keypair A (attacker) actually signs
    const privA = ed25519.utils.randomPrivateKey();
    const pubA = ed25519.getPublicKey(privA);
    const message = "intent-payload";
    const sigBytesA = ed25519.sign(new TextEncoder().encode(message), privA);

    // victim B's Stellar address (unrelated to keypair A)
    const stellarAddressB = "G..."; // valid strkey for a different ed25519 key

    const result = prepareSwapSignedData(
      {
        type: "STELLAR_SEP53",
        signedData: { message },
        signatureData: sigBytesA,
      } as any,
      { userAddress: stellarAddressB, userChainType: "stellar" },
    );

    // LHS: public_key claimed in payload (from userAddress B)
    const claimedPubKey = result.public_key; // ed25519:<base58 of B's bytes>
    // RHS: key that actually produced the signature (A)
    const actualSignerPubKey = `ed25519:${base58.encode(pubA)}`;

    expect(claimedPubKey).not.toEqual(actualSignerPubKey); // equality is broken
    // and yet the signature verifies for A's key against the payload:
    expect(
      ed25519.verify(sigBytesA, new TextEncoder().encode(message), pubA),
    ).toBe(true);
  });
});
```
This demonstrates `public_key` (built from `userInfo.userAddress`) ≠ the ed25519 key that actually produced `signature.signatureData`, with no assertion in `prepareSwapSignedData` catching the mismatch.
