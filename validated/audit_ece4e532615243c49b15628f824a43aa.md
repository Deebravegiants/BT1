### Title
Withdrawal status matched only by `assetId`, not by withdrawal identity, misattributing completion status/hash across batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal (identified by `index`/`tx`) by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, matching purely on `assetId`, explicitly bypassing `index` correlation.

### Finding Description
`describeWithdrawal` fetches all withdrawals batched under a single NEAR transaction hash and must map each logical withdrawal (identified by its `index` in the batch) to its corresponding entry in the (unsorted) response list. The code comment states the intentional design: "Response list is unsorted, so we match by assetId instead of index" [1](#0-0) . This assumes each `assetId` appears at most once per batch. When a caller submits multiple withdrawals of the *same* `assetId` in one batch (e.g., two USDT withdrawals to different destination addresses in the same `ft_withdraw` transaction, which `WithdrawalParams` as an array supports per the SDK's `createWithdrawalCompletionPromises` API), `findMatchingWithdrawal` has no way to distinguish which entry belongs to which `index` — it can only key off `assetId`.

### Impact Explanation
If the matching logic (not fully visible in my search, defined in the same file) returns the same or an unintended entry for two different indices sharing an `assetId`, `watchWithdrawal`/`createWithdrawalCompletionPromises` [2](#0-1)  would report a `completed` status with a `txHash` belonging to a *different* withdrawal than the one an integrator is polling. This is exactly the "status or hash misreport" class called out as High impact: an integrator could credit or confirm a withdrawal as settled based on another withdrawal's transaction hash, potentially double-crediting a user or confirming an unrelated destination's payout as their own.

### Likelihood Explanation
This requires no malicious actor — a legitimate SDK consumer batching two same-asset withdrawals (a normal, documented use case per `createWithdrawalCompletionPromises`) would trigger the ambiguity purely through ordinary usage, satisfying the "unprivileged" requirement.

### Recommendation
Disambiguate by destination address and amount (or another unique withdrawal identifier returned by the POA API) in addition to `assetId` inside `findMatchingWithdrawal`, or require the POA API to expose a stable per-index identifier for batched withdrawals.
