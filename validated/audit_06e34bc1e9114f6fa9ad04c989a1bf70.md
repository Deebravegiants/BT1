### Title
Solver fund loss via Uniswap V4 pool price manipulation in venue-priced fills - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
Simplex's `FXFiller` prices curveless, venue-priced trading pairs directly off the live `sqrtPriceX96` of a Uniswap V4 pool [1](#0-0) , and the only defense against a manipulated quote is a static, optional `checkPriceGuard` band around a fixed `referencePrice` [2](#0-1) . Like the Carson incident — where an attacker repeatedly swapped through a thin, unaudited pair contract to inflate the token's price before extracting value — an attacker can move this pool's mid-price with ordinary (optionally flash-loaned) swaps immediately before an order is filled, causing the solver to price and fund the entire fill off the manipulated mid.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` reads the current pool state and derives `priceUsd` straight from `sdkPool.token0Price`/`token1Price` — the instantaneous pool mid computed from `sqrtPriceX96` — with no TWAP, no depth check, and no size/impact term [3](#0-2) . This is documented explicitly as untrusted: "the pool acts as the price oracle" and "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote" [4](#0-3) .

`FXFiller.resolveLegRates` consumes this venue quote for any curveless pair whose `token0` is a USD stable, converts it to a rate, and — after `checkPriceGuard` — extends that single mid **linearly across the entire order notional**, with no size/impact term applied [5](#0-4) . The internal flow documentation states this outright: "there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost" [6](#0-5) .

The guard itself only bounds deviation from a fixed operator-supplied `referencePrice`; it is optional (guard-by-chain map is empty unless configured) and, even when configured, it does nothing to detect that the *current* quote was just pushed to the edge of the band by the same actor about to submit the order [2](#0-1) . The state is refreshed immediately before each planning/pricing call (`await state.refresh()`), so the manipulated price is picked up fresh, not from any historical/aggregated source [7](#0-6) .

Compounding this, when the solver must fund the fill from the same LP position, `planWithdrawalForToken` withdraws liquidity from that very pool, paying the fee tier and price impact of the withdrawal that was never quoted against [8](#0-7) .

This mirrors the Carson bug class precisely: the reported attack repeatedly called a swap function to inflate a token's on-pool price before extracting value against that inflated price. Here, an unprivileged actor can (1) swap in the V4 pool (optionally via flash loan) to move `sqrtPriceX96` to a price still inside (or, if unconfigured, entirely outside) the guard band, (2) place an `IntentGatewayV2.placeOrder` order sized to exploit that skewed mid, and (3) have the automated solver fill it at the bad linear price, funding the payout by draining the very position it just perturbed.

### Impact Explanation
An attacker can extract funds from the solver's wallet/vault by forcing a fill at an off-market rate derived from a self-manipulated pool tick, with no execution-cost or size-impact check in the pricing path. Because the guard band is static and optional, this ranges from bounded skimming (when a guard is configured) up to unbounded loss (when no `referencePrice`/`maxDeviationBps` guard is set for the chain, which the config explicitly allows — "omit both to leave the chain unguarded" [9](#0-8) ). This is concrete theft of solver-held/vault funds, satisfying the Medium-to-High bar.

### Likelihood Explanation
This requires only ordinary permissionless actions reachable from a single flow: swapping against a public Uniswap V4 pool (a standard, unprivileged action, easily flash-loan-financed for thin pools — the exact scenario the docs call out as risky) and placing an intent order via `IntentGatewayV2.placeOrder`, which any user can call [10](#0-9) . No privileged role, governance, or malicious-operator assumption is needed — it is exploitable by any external user against an under-guarded or thin exotic-token pool, which is a realistic and currently supported production configuration (venue pricing is a documented, opt-in but fully supported feature).

### Recommendation
- Do not price fills directly off an instantaneous pool mid; use a manipulation-resistant reference (TWAP over a sufficiently long window, or a liquidity/size-weighted price) before applying `checkPriceGuard`.
- Apply a real price-impact/size term when extending the venue rate across the order notional instead of linear extrapolation of the raw mid.
- Make the price guard mandatory (not optional) whenever venue pricing is enabled, and consider comparing against a rolling on-chain reference rather than a static, operator-set constant.
- When funding a fill by withdrawing from the same pool used for pricing, re-derive/re-check the effective execution price (including the withdrawal's own price impact and fee tier) against the guard before committing to the fill.

### Proof of Concept
1. Operator configures a Simplex filler with a curveless, venue-priced pair (e.g., USDC/cNGN) sourced from a Uniswap V4 position with either no price guard, or a guard with a workable `maxDeviationBps` (e.g., 200 bps) [11](#0-10) .
2. Attacker takes a flash loan and executes `swapExactTokensForTokens`-style trades against the V4 pool to push `sqrtPriceX96` to the edge of (or beyond, if unguarded) the allowed band.
3. In the same block/transaction window, attacker calls `IntentGatewayV2.placeOrder` for a large USDC→cNGN (or reverse) order sized to exploit the skewed rate.
4. The solver's `resolveLegRates` reads the just-manipulated pool mid via `getExoticTokenPrice`/`computeDirectPoolPriceUsd`, passes `checkPriceGuard` (in-band by construction), and linearly extends that mid across the full order notional [12](#0-11) .
5. `UniswapV4FundingPlanner.planWithdrawalForToken` funds the fill by withdrawing LP liquidity from the same manipulated pool [8](#0-7) .
6. Attacker reverses the initial swap / repays the flash loan, netting the difference between the manipulated fill price and the pool's true price — funds extracted from the solver's vault/LP position, analogous to Carson's price-inflation-then-extraction pattern.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.
