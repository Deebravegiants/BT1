### Title
Accrual overflow in `scaled_to_original` permanently freezes a high-utilization market — (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` computes `borrowed`/`supplied` in original units via `scaled_to_original` (`Ray::mul`), which panics on `i128` overflow. A single unprivileged address can place a market in the state that reaches this overflow: supply a near-cap amount and borrow it to sustained high utilization (`supply`/`borrow`/`update_indexes` are permissionless). Once `borrowed_scaled × borrow_index` crosses the RAY-value ceiling, every subsequent accrual panics — and since `interest::global_sync` runs before every mutation, withdraw, repay, liquidate, and even `recapitalize` all revert permanently on that market.

### Finding Description
In `common/src/rates/simulate.rs:60-61`, `accrue_step` unscales both books each chunk:
```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```
`scaled_to_original` (`common/src/rates/scaling.rs:14-16`) is `scaled.mul(env, index)`, which panics on `i128` overflow — there is no clamp. The `MAX_BORROW_INDEX_RAY` index cap exists but engages only on the index itself, not on the product `borrowed_scaled × borrow_index`; with a whale-scale scaled book (caps allow up to ~`i128::MAX`-adjacent raw amounts per `max_cap_for_decimals`), the product overflows while the index is still far below its cap.

The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) proves the freeze end-to-end: `update_indexes` fails with `MathOverflow`, and then `withdraw` and `repay` also revert with `MathOverflow` because every pool verb runs `Cache::load` → `interest::global_sync` → `accrue_step` first (`contracts/pool/README.md` flow). `clean_bad_debt`/`seize_positions`/`repay`/`withdraw`/`flash_loan`/`create_strategy` all accrue first, so there is no in-protocol escape. `recapitalize` cannot help — it accrues too.

Entrypoints (all unprivileged): `Controller::update_indexes(caller, assets)` (`contracts/controller/src/lib.rs:370`), plus `supply`, `borrow` to set up the state. The pool's `update_indexes` is `#[only_owner]` but the controller is the owner and forwards any caller's request (`contracts/controller/src/markets.rs:119-125`).

### Impact Explanation
Permanent freezing of funds and a contract unable to operate: once the overflow state is reached, all supplier principal and accrued yield in that market are locked forever — no withdrawal, no repayment, no liquidation, no bad-debt cleanup, no governance-mediated fix short of a code upgrade (and `upgrade` itself cannot retroactively shrink the index). This matches "permanent freezing of funds" and "contract unable to operate" impact classes.

### Likelihood Explanation
Medium. An unprivileged attacker needs to (a) supply a very large position in an 18-decimal or high-decimal market (caps lifted to `max_cap_for_decimals`), (b) borrow ~98% of it to pin utilization on the steep curve segment, and (c) let accrual run until the index multiplies the scaled book past `i128::MAX`. The capital requirement is large but the attack needs no privilege, no oracle manipulation, and no cooperation — the attacker can be the sole supplier/borrower. The harness test demonstrates the cliff is reached within ≤40 years of ledger time on the XLM-style curve and could arrive sooner on steeper configured curves; critically, once the state is set up, no one — including honest users calling `update_indexes` — can prevent the freeze, and the attacker can also just wait for organic accrual.

### Recommendation
Apply the index cap semantics before unscaling, or make the unscale saturating:
- In `accrue_step`, clamp `borrow_index`/`supply_index` to `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` *before* computing `borrowed_original`/`supplied_original`, so the cap actually bounds the product.
- Alternatively, enforce a market-level bound `borrowed_scaled ≤ i128::MAX / MAX_BORROW_INDEX_RAY` (and same for supply) at `supply`/`borrow` time via `calculate_scaled_cap`, so the product can never overflow regardless of index growth.
- Ensure at least one recovery verb (e.g., `recapitalize` or a debt write-down path) skips or tolerates accrual overflow so a frozen market can be unwound.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`, which exercises exactly this path:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance ledger years, calling permissionless update_indexes each year
// → MathOverflow inside scaled_to_original while borrow_index < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

Attack sequence in production terms: call `controller.supply` with the whale leg, `controller.borrow` to ~98% utilization, then `controller.update_indexes` periodically; after the index grows sufficiently, every accrual-first verb on that `(hub, token)` market reverts permanently, freezing all supplier funds.
