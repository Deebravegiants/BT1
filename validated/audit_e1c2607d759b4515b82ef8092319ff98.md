### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted by the handler but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers and passed on to the app's webhook handler. The HMAC that Shopify sends only signs the body bytes, so these header-derived fields are unauthenticated. This breaks the identity binding `shop_used_by_handler == shop_bound_by_signature`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers, entirely outside the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header — it never incorporates the shop/topic/webhook-id headers into the signed material: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then immediately forwards `request.shop` (an unauthenticated header value) to the app's handler via `WebhookMetadata`, with no check that the header-derived shop is consistent with anything cryptographically bound to the body: [4](#0-3) 

So the equality that should hold — "the shop the handler acts on" == "the shop bound by the HMAC-signed bytes" — does not hold. The HMAC only proves body integrity/authenticity; it says nothing about which shop/topic the body belongs to.

### Impact Explanation
Because `shop-domain` is not part of the signed material, any webhook payload whose HMAC validates for its own body can have its `x-shopify-shop-domain` header swapped, and `Registry.process` will still accept it (`HmacValidator.validate` only checks the body against the secret) and hand the forged shop to the handler. Any host application that uses `WebhookMetadata#shop` (i.e., `request.shop`) as the tenant identifier for looking up sessions, writing data, or authorizing an operation — the documented and expected use of this field per this gem's own webhook API — will attribute the webhook body to the wrong merchant. This is a cross-tenant confusion issue: data or events legitimately signed for shop A can be delivered to the application logic as if they belonged to shop B, without ever needing the app's `client_secret` or a valid access token, satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
An attacker only needs to control (or install the app on) one shop to receive a legitimately HMAC-signed webhook body for that shop's own events. They can then replay the identical body and `hmac` header to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and, if useful, `x-shopify-topic`) with a different shop's domain. No secret key, access token, or privileged access is required — only network access to the app's public webhook endpoint and control of one's own store's webhook events, which is realistic for any merchant/attacker who can install the target app.

### Recommendation
Bind the shop (and topic) identity into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the payload before trusting it — for example, by validating that the shop-domain header matches an `X-Shopify-Shop-Domain`-independent claim inside the body/registration context, or by documenting/enforcing that consumers must cross-check `request.shop` against a shop already known to be associated with the specific `webhook_id`/subscription (fetched via a signed, session-authenticated API call) rather than trusting the header verbatim. At minimum, the gem should surface that `shop`, `topic`, `api_version`, and `webhook_id` are unauthenticated header values distinct from the HMAC-verified body, so host applications don't implicitly treat `WebhookMetadata#shop` as a verified tenant identifier.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) with body `B`.
2. Shopify sends `POST /webhooks` with header `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: HMAC(secret, B)`, body `B`.
3. Attacker replays this exact request to the app's webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and the original `hmac` value unchanged.
4. `ShopifyAPI::Webhooks::Request.new` parses the headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to the untouched `hmac` header — it matches, since `B` and the HMAC are both unmodified. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, even though `B` was never actually sent by or authorized for `victim-shop`, demonstrating the forged cross-tenant shop binding.
