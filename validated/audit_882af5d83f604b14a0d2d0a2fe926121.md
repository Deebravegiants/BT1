### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The shop identity that the handler receives and acts on (`request.shop`, taken from the `X-Shopify-Shop-Domain` header) is never included in the signed material, so the binding "HMAC-verified bytes == data the handler trusts as the tenant identity" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines the signable string as only the raw HTTP body: [1](#0-0) 

```
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

`topic`, `shop`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers and are excluded from `to_signable_string`. `Registry.process` validates only the body-derived HMAC and then forwards the unsigned `shop` header straight into the data the app's handler acts on: [2](#0-1) 

```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The equality this design implicitly assumes is:
`HMAC-verified bytes (raw_body) == tenant identity trusted by the handler (shop header)`

That equality is false: the HMAC only proves the *body* was produced with `Context.api_secret_key`; it says nothing about which shop the body belongs to. For webhook topics whose body is small/fixed or otherwise shop-agnostic (confirmed by the test suite itself, which signs a literal `"{}"` body: `HmacValidator` test and registry test both compute `HMAC(secret, "{}")`), the resulting valid `(body, hmac)` pair is identical for every shop that installs the app. [3](#0-2) 

### Impact Explanation
This is a cross-tenant identity-binding break, matching the "field acted on but not covered by the HMAC" analog. A merchant (an unprivileged actor relative to other tenants of the same multi-tenant app) can:
1. Install the app on their own shop, legitimately triggering Shopify to deliver a real webhook (e.g. `app/uninstalled` or any topic with a small/constant JSON body) to the app's public endpoint, obtaining a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's shared `api_secret_key`.
2. Replay that exact body and HMAC to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to a victim shop's domain.
3. `Utils::HmacValidator.validate(request)` still succeeds because it only checks the (unmodified) body against the (unmodified) HMAC.
4. The handler receives `WebhookMetadata` claiming the event is `shop: <victim-shop>`, causing the host application to act on/attribute data to a shop the attacker does not control — i.e., cross-tenant access/data-integrity compromise, without possessing any credential belonging to the victim.

This satisfies the Critical impact bar (cross-tenant access) because no access token, `client_secret`, or victim credential is required — only a body/HMAC pair the attacker legitimately obtained for their own tenant.

### Likelihood Explanation
Likelihood is high for any host app whose webhook handlers key store/session lookups off `WebhookMetadata#shop` (this is exactly how the library's own docs and `ShopifyApp` gem recommend using webhook data) and for any webhook topic whose payload is small or shop-independent (uninstall, redact-style, or any topic that can otherwise be forced to a known/fixed body). No secret, token, or privileged account is needed — only the ability to install the app on any one shop.

### Recommendation
Bind the tenant identity into the material that is HMAC-verified, or otherwise cryptographically tie the `shop` (and `topic`/`webhook_id`) header to the verified body, e.g.:
- Include the `shop-domain`, `topic`, and `webhook-id` headers in `to_signable_string` for `ShopifyAPI::Webhooks::Request`, so the HMAC recomputation covers them.
- If that's not possible without breaking Shopify's own signature contract, at minimum require host apps to independently corroborate `shop` against a durable app-side association (e.g., look up an existing installed-shop record and reject if the shop was never granted access, or cross-check with an offline session store) rather than trusting the raw header as-is.
- Document explicitly in `docs/usage/webhooks.md` that `WebhookMetadata#shop`/`topic`/`webhook_id` are NOT covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional binding.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and installs the victim's app.
# Shopify delivers a legitimate webhook, e.g. topic "app/uninstalled", with body "{}"
# and a valid X-Shopify-Hmac-Sha256 computed by Shopify using the app's api_secret_key.

captured_body = "{}"
captured_hmac = "<value from the legitimate request the attacker received for their own shop>"

# Attacker now POSTs to the app's public webhook endpoint, reusing the untouched
# body/hmac but forging the shop header to a victim shop they do not control:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => captured_hmac,      # unchanged, still valid for captured_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only "{}" body is checked),
#    handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com",
#    causing the host app to process/act on data attributed to the victim shop.
```
