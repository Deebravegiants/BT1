### Title
Tron `IntentGatewayV2.onAccept` lacks the relayer allowlist gate present in the EVM gateway, permitting escrow redemption via any relayer that can pass consensus/state proof verification - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements `onAccept` with only an `onlyHost` check plus per-source `authenticate()`, but never defines or enforces a `_relayer` allowlist / `_checkRelayer` gate the way the canonical EVM contract (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) does. [1](#0-0) [2](#0-1) 

### Finding Description
On the canonical EVM path, `IApp.onAccept` receives an `IncomingPostRequest` whose `relayer` field is the `msg.sender` that called `HandlerV2.handlePostRequests`, forwarded verbatim by `EvmHost.dispatchIncoming`. Because the handler is a permissionless entity (any address can submit a proof to the handler once it verifies), Hyperbridge's threat model relies on individual apps optionally restricting which relayer address is allowed to actually execute privileged callback logic — this is exactly what `ExtrinsicIntents._checkRelayer` (called before decoding any body) and `BridgeToken._checkRelayer` implement, and what an internal decision doc explicitly documents as closing a forged-consensus attack route. [3](#0-2) 

The Tron `IntentGatewayV2.onAccept` grep for `_relayer`/`setRelayer`/`relayer()` returns no matches anywhere in that file, and it never calls anything resembling `_checkRelayer`. `onAccept` is gated only by `onlyHost` and, for `RedeemEscrow`/`RefundEscrow`, by `authenticate(incoming.request)`, which merely checks that `request.from` matches a registered gateway instance address for the claimed source chain — it does not check who relayed the message: [4](#0-3) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
        authenticate(incoming.request);
        WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
        return withdraw(body, kind == RequestKind.RefundEscrow);
    }
    ...
```

`authenticate` only checks `request.from` against `instance(request.source)`, i.e. that the message claims to originate from a peer gateway — it says nothing about which relayer physically delivered it: [5](#0-4) 

Compare this to the EVM `ExtrinsicIntents.onAccept`, which runs `_checkRelayer(incoming.relayer)` unconditionally before even reading the request kind: [6](#0-5) 

The documented rationale for the relayer gate is that a forged consensus proof could otherwise let an attacker deliver a message through a compromised/malicious handler that reports an arbitrary relayer, and the app-level gate is the only backstop once the handler itself is compromised or a consensus proof is somehow forged: [7](#0-6)  The Tron `IntentGatewayV2` has no equivalent second line of defense: any address that can get a `PostRequest` accepted by `EvmHost`/`HandlerV2` on Tron (i.e., any relayer whose proof verifies, or, under a forged/compromised consensus path, any attacker) can trigger `withdraw()` to redeem or refund escrowed order inputs.

### Impact Explanation
`withdraw()` transfers escrowed input tokens (and accumulated transaction fees) out of the gateway to the beneficiary named in the `WithdrawalRequest` body, which is decoded directly from the incoming request body without any relayer-specific restriction: [8](#0-7)  Since Tron's `authenticate()` only checks the claimed `request.from`/`request.source` pairing, if the consensus layer or handler that feeds Tron's `EvmHost`/equivalent can be tricked (forged proof, compromised handler swap, or any bug that lets an unauthorized relayer's delivery through) into reporting a legitimate source/from pairing, `withdraw()` executes with no additional relayer-identity check — unlike every other Intent Gateway deployment in this codebase, which treats the relayer gate as the last line of defense against exactly this scenario. This maps to concrete theft of escrowed order funds (RedeemEscrow diverts to an attacker-chosen beneficiary) or forged unbacked refunds (RefundEscrow draining escrow to an attacker-controlled beneficiary), analogous to the SIL.Finance incident where a smart-contract permission gap let an automated actor submit transactions that drained/exploited escrowed funds ahead of the legitimate flow.

### Likelihood Explanation
Exploitation requires the attacker to get a `PostRequest` with a spoofed but plausible `from`/`source` accepted by the local host/handler stack on Tron — this is the same "forged consensus" precondition documented elsewhere in the repo as the reason the relayer gate exists on every other app (`ExtrinsicIntents`, `BridgeToken`). The likelihood is therefore tied to the strength of Tron's specific consensus/handler verification, which was not available to inspect in this pass. Given that this repo's own security documentation treats "forged consensus swapping in a permissive handler" as a credible, previously-mitigated threat model for the EVM side, the absence of the equivalent mitigation on Tron is a genuine regression/gap rather than a theoretical concern, though it is contingent on that same class of consensus-layer weakness being reachable on Tron specifically.

### Recommendation
Add a `_relayer` allowlist (mirroring `ExtrinsicIntents.sol` / `HyperFungibleToken.sol`) to `evm/tron/contracts/apps/IntentGatewayV2.sol`, with a `setRelayer`/governance-gated setter, and call `_checkRelayer(incoming.relayer)` unconditionally at the top of `onAccept` (and `onGetResponse`) before any request-kind branching or body decoding, exactly as done in the EVM `ExtrinsicIntents.onAccept`.

### Proof of Concept
Not independently verifiable in this pass: reproducing the exploit requires demonstrating a concrete way to get an unauthorized relayer's `PostRequest` accepted by Tron's host/handler with a spoofed `from`/`source`, which depends on Tron-specific consensus/handler code not covered by the available index. This is flagged as a structural permission gap (missing relayer gate) confirmed by direct comparison of `onAccept` implementations across the codebase, but full proof-of-concept requires access to the Tron host/handler/consensus verification code, which the current index does not surface. A Devin session with full repository access would be needed to confirm the exact upstream reachability and build an executable PoC.

```text
     * @notice Withdraws the escrowed tokens for a request body.
     * @dev This function is marked as internal.
     * @param body The request body containing commitment, tokens, and beneficiary.
     * @param isRefund Whether this is a refund (true) or a successful fill (false).
     */
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
```

```markdown
# How a cross-chain delivery reaches the gateway, and where the relayer gate sits

Verified against `evm/src/core/HandlerV2.sol`, `evm/src/core/EvmHost.sol` and
`evm/src/apps/intentsv2/ExtrinsicIntents.sol`, and exercised by
`testRejectedDeliveryStaysRetryableThroughHost` in `evm/tests/foundry/IntentGatewayV2Test.sol`.

1. A relayer calls `HandlerV2.handlePostRequests` (or `handleGetResponses`). After proof
   verification the handler calls `host.dispatchIncoming(request, _msgSender())`. `_msgSender()` is
   plain `msg.sender`; the handler has no trusted forwarder.
2. `EvmHost.dispatchIncoming` (restricted to the handler) writes a receipt for the request
   commitment, then low-level calls the module with `IApp.onAccept(IncomingPostRequest(request,
   relayer))`. If that call fails the host deletes the receipt and returns without reverting, so the
   rest of the batch proceeds and the message stays deliverable.
3. `ExtrinsicIntents.onAccept` runs `onlyHost`, then `_checkRelayer(incoming.relayer)`, which reverts
   with `Unauthorized` when a relayer is set and the delivery is from anyone else. Only then is the
   first body byte read as a `RequestKind`. `onGetResponse` has the same two steps before touching
   the response.

So a delivery from anyone but the authorised relayer never decodes the body, never runs
`_authenticate`, and leaves no receipt. The authorised relayer submitting the same message later
takes the normal path. A gateway whose `_relayer` is zero accepts every relayer: that is the state
a fresh proxy is in until governance arms it, below.
```

```markdown
# 2026-09-03 — `HostManager` deliveries are gated too, and that does not touch permissionless relaying

Chosen: `HostManager.onAccept` refuses any relayer but the one the host admin set, zero included.

The app gates check an address the host reports, and the host takes it from its handler. The
handler is a host parameter that a `SetHostParam` governance message can replace, and until now
any relayer could deliver that message once its consensus proof verified. Under a forged consensus
an attacker would swap in a handler that reports the whitelisted relayer on every message, and the
app gates would pass. Gating the HostManager closes that route.
```
