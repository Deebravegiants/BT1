Based on my review of the OAuth, JWT, and webhook verification code, the analog that clearly fits the required pattern (a field acted upon but not covered by the HMAC) is in the webhook request/verification flow.

### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant identifier) is read from an unauthenticated HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then passes the untrusted `shop` value straight through to the app's webhook handler, breaking the intended binding `authenticated_body == acted_upon_tenant`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Registry.process` verifies the HMAC over `to_signable_string` (i.e., body only) and, on success, forwards `request.shop` — the unauthenticated header value — to the registered handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC solely from `verifiable_query.to_signable_string` and the app's shared `api_secret_key`: [4](#0-3) 

Because the `api_secret_key` is a single shared secret used for **every** shop that has this app installed (not a per-shop secret), any unprivileged internet user who runs their own store, installs the target app on it, and configures a webhook endpoint they control receives a legitimately HMAC-signed `(body, hmac)` pair from Shopify. That pair authenticates only the body content — it says nothing about which shop it came from. The attacker can then submit that same `(body, hmac)` pair directly to the victim app's public webhook endpoint while setting the `X-Shopify-Shop-Domain` header to a *different*, victim shop domain. `HmacValidator.validate` returns `true` (the body/HMAC pair is valid), and `Registry.process` calls the handler with `shop: <attacker-chosen victim domain>`.

The broken identity binding is:
`hmac_verified(body) == true` is treated as proving `shop == <header value>`, when in fact the header is never covered by the signature.

### Impact Explanation
Any app that uses `ShopifyAPI::Webhooks::WebhookMetadata#shop` (as returned by this gem) to key persistence, cache invalidation, GDPR redaction (`customers/redact`, `shop/redact`), or any per-tenant business logic is exposed to cross-tenant data injection/corruption: an attacker-controlled shop can inject fabricated webhook events that the app will process and store as if they originated from a victim merchant's shop. This crosses the tenant boundary the gem is expected to enforce for webhook consumers, matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target app on a shop the attacker controls (any merchant/developer can do this for public or even custom apps they have access to), and (2) capturing one legitimately delivered `(raw_body, hmac)` pair, which is trivial by pointing the webhook endpoint at a server the attacker controls. No access to the app's `client_secret`, session tokens, or victim credentials is required — only the ability to receive a webhook as any legitimate tenant, which is inherent to normal app usage.

### Recommendation
Bind the shop identity to the signed payload before trusting it as a tenant key: either include the `shop-domain` header value as part of the HMAC-signed content (e.g., verify `HMAC(shop + raw_body)` or a canonicalized string incorporating the header), or require callers to cross-check `request.shop` against the shop associated with the specific webhook/session/installation record already known to the app (rather than trusting the header value directly) before acting on it. At minimum, the library's documentation and `WebhookMetadata` should explicitly flag that `shop` is unauthenticated and must be independently verified by the host application against its own installed-shop registry.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and points its webhook registration (or manually crafts a request in the same shape Shopify would send) at a server they control, or intercepts a real delivery.
2. Attacker obtains a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair — this is valid because it was generated by Shopify using the shared `api_secret_key` for the raw body only.
3. Attacker sends that same `raw_body` and `X-Shopify-Hmac-Sha256` header to the victim app's webhook endpoint, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and `X-Shopify-Topic` set to any topic the app has registered (e.g. `app/uninstalled`, `customers/data_request`, or a topic whose handler writes data keyed by shop).
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` and `ShopifyAPI::Webhooks::Registry.process(request)` validate the HMAC successfully (per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/registry.rb:188-190`) and invoke the handler with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though this data never actually originated from the victim shop.
