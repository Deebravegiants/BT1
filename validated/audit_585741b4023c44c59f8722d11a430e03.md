### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable payload solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly and unauthenticated from HTTP headers. `ShopifyAPI::Webhooks::Registry.process` only checks that the *body* was signed with the app's `api_secret_key`, then hands the attacker-controlled `shop` header straight to the host application's handler as if it were verified. This breaks the identity binding `hmac_signed_bytes == shop_identity_used_by_handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic tie to the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and `request.topic`) to build the metadata passed to the app's handler: [3](#0-2) 

The `HmacValidator` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body: [4](#0-3) 

Compare this to the OAuth callback flow, where every field that matters (`code`, `host`, `shop`, `state`, `timestamp`) is explicitly included in `to_signable_string` and therefore bound by the HMAC: [5](#0-4) 

The webhook processing flow does not follow this pattern for `shop`. As a result, an unprivileged attacker who has installed the target app on their own store (a legitimate, low-privilege tenant) will receive real webhook deliveries with a valid `X-Shopify-Hmac-Sha256` signature computed over the JSON body using the app's shared `api_secret_key`. Because the signature never covers `X-Shopify-Shop-Domain`, the attacker can replay the exact same `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim shop, or a shop they don't control at all). `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` forwards the forged `shop` value into `WebhookMetadata`, which the app's documented handler contract treats as trustworthy: [6](#0-5) 

This is exactly the "verified bytes vs. parsed/acted-upon identity" mismatch class of bug: the equality that should hold is `hmac_covers(shop) == true`, but in fact `hmac_covers(shop) == false`.

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," which is a stronger guarantee than what is actually implemented (only the body content is verified, not the claimed shop): [7](#0-6) 

### Impact Explanation
This enables cross-tenant data confusion: an attacker's legitimately-received webhook (for their own store) can be replayed with a forged `shop` value, causing the host application to process/store webhook data under a different tenant's identity. Depending on how the host app uses `data.shop` (e.g., looking up the tenant's session/access token, writing to per-shop records, or triggering per-shop side effects), this can lead to cross-tenant data injection or corruption — since the shop identifier that gates per-tenant processing was never included in the cryptographic proof of authenticity.

### Likelihood Explanation
Requires the attacker to have their own valid installation of the target app (or intercept/obtain a single valid `(body, hmac)` pair for any topic), plus network access to the app's public webhook endpoint. Both prerequisites are realistic for a public, unprivileged internet user, since the webhook endpoint is by design internet-reachable and unauthenticated (protected only by HMAC).

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that is verified by the HMAC, or at minimum, require the host application to independently verify that `request.shop` matches an expected/known shop from a separately authenticated context before trusting it. Update `Request#to_signable_string` and `HmacValidator` usage so verification is tied to shop identity, not just body bytes, and correct the documentation to accurately describe what `process` verifies.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body.
3. Attacker captures this `(raw_body, hmac)` pair and replays it directly to the same public endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only and returns `true`, since `to_signable_string` never included the shop header.
5. `Registry.process` calls the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker's data> ...)`, and the host app processes attacker-supplied data as if it originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
