Found: pallet-ismp's `handle_unsigned` extrinsic runs a full, unbounded batch execution during `validate_unsigned` — before any fee, weight, or block-inclusion gate applies.

### Title
Unbounded free computation in `pallet_ismp::validate_unsigned` allows excessive-loop DoS on mempool/block-authoring nodes - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is explicitly designed to let anyone execute ISMP messages "for free" [1](#0-0) . Its `ValidateUnsigned::validate_unsigned` implementation runs `Self::execute(messages.clone())` — the *entire* message batch (proof verification, MMR/state-proof checks, request dispatch loops) — synchronously inside transaction-pool validation, with no cap on `messages.len()` or on the size of nested `requests`/`timeouts` vectors [2](#0-1) . This is the same bug class as CVE-2016-9372: unbounded iteration over an attacker-supplied collection of "objects" (there, Profinet I/O objects in a dissector; here, ISMP messages/requests in mempool validation) performed before any resource accounting rejects the input.

### Finding Description
`Self::execute` iterates over every message in the batch, calling `handle_incoming_message` per message [3](#0-2) , and each request/response/timeout handler (`request::handle`, `response::handle`, `timeout::handle`) itself loops over `Vec<PostRequest>` / `Vec<GetRequest>` performing per-item validation and, in the case of the response handler, calling `verify_state_proof` for every entry [4](#0-3) . None of `RequestMessage`, `ResponseMessage`, or the outer `Vec<Message>` passed to `handle_unsigned` are `BoundedVec`s or otherwise capped in size at the codec/extrinsic-length level before `validate_unsigned` runs this work.

`validate_unsigned` is invoked by every node's transaction pool for every unsigned transaction it receives from the network — this happens *before* `pre_dispatch`/block inclusion and *before* any weight-based fee is charged (the whole point of `handle_unsigned` is to be feeless) [5](#0-4) . An attacker can therefore submit a single unsigned extrinsic containing a very large `Vec<Message>` (or a `RequestMessage`/`ResponseMessage` with a huge inner `requests` vector) with syntactically well-formed (but ultimately failing) proofs, forcing every peer's mempool to perform substantial cryptographic verification work (potentially many MMR/state-proof checks) purely to reject it, with no fee paid and only the extrinsic's byte size as a cost.

This mirrors the Wireshark case: an unbounded count of "objects" drives unbounded looped work in a low-trust intake path (a packet dissector there, unsigned mempool validation here) before any bound is enforced.

### Impact Explanation
This is a network/consensus-node availability risk: repeated submission of oversized `handle_unsigned` payloads can consume mempool validation CPU across every full node/collator running pallet-ismp, degrading transaction pool throughput and potentially delaying legitimate message delivery (a form of "route unable to deliver messages" per the validation criteria) at negligible attacker cost, since the extrinsic is unsigned and free by design. It does not directly cause fund loss, but it directly weakens the liveness of the message-dispatch path that relayers rely on.

### Likelihood Explanation
High reachability: `handle_unsigned` is permissionless by design (`ensure_none(origin)`) [6](#0-5) , and `validate_unsigned` runs on every node for every submitted unsigned extrinsic before longevity/priority gating can drop it, so a single crafted, large batch is sufficient to trigger the cost on every propagating peer.

### Recommendation
Bound the size of the message batch and nested request/response/timeout vectors accepted by `handle_unsigned` (e.g., via `BoundedVec` with a runtime-configured max, or an explicit length check at the top of `validate_unsigned` before calling `Self::execute`), and/or perform a cheap structural/size pre-check (proof length, request count) ahead of running full cryptographic verification, similar to the existing `MAX_PROOF_DEPTH`/`MaxCallSize` guards already used elsewhere in the codebase (e.g. `modules/consensus/pharos/primitives/src/spv.rs`, `modules/pallets/call-decompressor/src/lib.rs`).

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned` unsigned extrinsic whose `messages: Vec<Message>` contains, e.g., `Message::Response(ResponseMessage { requests: <N very large or many GetRequest entries>, .. })` with syntactically valid but bogus proof bytes.
2. Submit this extrinsic repeatedly to network peers via the standard unsigned-transaction gossip path.
3. Each peer's `validate_unsigned` calls `Self::execute(messages.clone())`, which iterates the full `requests` vector and invokes state-proof verification per entry before ultimately failing and returning `InvalidTransaction::BadProof` [2](#0-1)  — the CPU cost of verification is paid by the network before the transaction is discarded, at no cost to the sender since `handle_unsigned` requires no fee/signature.

*Note: I could not directly confirm the exact maximum extrinsic-size limit configured for this specific runtime or measure actual CPU cost per verification call from the indexed code, so the precise severity of achievable amplification is not fully quantified here — a Devin session with full repository/runtime access would be needed to measure this concretely.*
