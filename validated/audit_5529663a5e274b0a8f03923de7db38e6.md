### Title
Cross-tenant session hijacking via unauthenticated, predictable session-cookie value used as storage lookup key - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` (and its helper `cookie_session_id`) returns the raw value of the `shopify_app_session` cookie verbatim, with no cryptographic signature or binding to the browser/OAuth flow that created it. Because the gem itself documents and generates this cookie value as a deterministic, guessable string (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`), any unprivileged user can set this cookie in their own browser to point at a different, arbitrary shop's session id and have the host application (following this gem's documented API exactly) load and use that other tenant's stored session — including its Shopify access token — on the attacker's behalf.

### Finding Description
For non-embedded apps (and as a fallback for embedded apps), the gem's documented session-retrieval flow is: [1](#0-0) 

`current_session_id` simply reads whatever value is present in the `shopify_app_session` cookie via `cookie_session_id`: [2](#0-1) 

That cookie's value is exactly the session `id`, which the gem itself computes deterministically from public information — the shop domain and, for online sessions, the numeric associated-user id — with no secret or signature involved: [3](#0-2) 

The cookie container is a plain unsigned struct with no MAC/HMAC over its `value`: [4](#0-3) 

The documented usage pattern instructs the host app to feed this raw cookie-derived id directly into its session storage lookup and then use the resulting `Session` (containing the merchant's access token) for authenticated API calls: [5](#0-4) [6](#0-5) 

The broken identity binding is: **`session_id_looked_up_in_storage` (derived from attacker-controlled, unauthenticated cookie bytes) == `session_id_of_the_legitimately_authenticated_tenant`**. Because the id format (`offline_{shop}` / `{shop}_{user_id}`) is public and predictable, and the value carries no cryptographic proof of having been issued by this gem's OAuth flow to the requesting browser, an attacker can forge that equality for any shop domain they know (shop domains are not secret — they're visible in storefront URLs, app listings, etc.) or for any online user id they can enumerate/guess.

### Impact Explanation
This breaks the tenant boundary at the core of the library's session model: the gem hands the host application a "verified enough" session id to fetch and activate another merchant's `ShopifyAPI::Auth::Session`, exposing that merchant's `access_token` to the attacker's requests. This is a cross-tenant access vulnerability with no dependency on the app's `client_secret`, API keys, or any leaked credential — it only requires knowledge of a target shop's domain (or a user id), which is not secret.

### Likelihood Explanation
Likelihood is high for offline sessions: the offline session id is entirely derived from the public shop domain (`offline_{shop}.myshopify.com`), so no guessing/brute force of secrets is needed — only knowledge of the target's store domain, which is typically public. For online sessions, the attacker additionally needs a user id, which is a small enumerable integer.

### Recommendation
Do not use a raw, unsigned, predictable string as the authoritative session lookup key. The session cookie value should be a cryptographically signed/opaque token (e.g., HMAC-signed with the app's secret, or a random unguessable identifier bound at cookie-issuance time) so that `cookie_session_id`/`current_session_id` cannot be spoofed by simply setting a cookie to a computed string. At minimum, document and enforce that host applications must independently verify that the shop/user encoded in the resolved session id matches an authenticated context (e.g., cross-check against an authenticated JWT `dest`/`sub` claim) before trusting the cookie-derived id for storage lookups.

### Proof of Concept
1. Attacker identifies a target merchant's shop domain, e.g. `victim-shop.myshopify.com` (public information — visible in the storefront URL).
2. Attacker visits the vulnerable app in their own browser and sets the cookie:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. The host app, following the gem's documented pattern, calls:
   ```ruby
   session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)
   # => "offline_victim-shop.myshopify.com"
   session = MyApp::SessionRepository.retrieve_session(session_id)
   ```
4. `MyApp::SessionRepository.retrieve_session` returns the victim shop's stored `ShopifyAPI::Auth::Session`, including its `access_token`.
5. The host app now makes Admin API calls (`ShopifyAPI::Clients::Graphql::Admin.new(session: session)`) using the victim's access token on behalf of the attacker's request, granting the attacker full API access to the victim's store data.

```markdown
### Sessions

Sessions are required to make requests with the REST or GraphQL clients. This Library provides helpers for creating sessions via OAuth. Helpers are provided to retrieve session ID from a HTTP request from an embedded Shopify app or cookies from non-embedded apps.

Session persistence is handled by the [ShopifyApp](https://github.com/Shopify/shopify_app) gem and is recommended for use in the Rails context. See that gem for documentation on how to use it.

#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
