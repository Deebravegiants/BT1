### Title
Missing duplicate/overwrite checks in `register_token` allow one EVM contract address to be bound to two different assets, enabling cross-asset unbacked minting - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`)

### Summary
`register_token` inserts into `TokenContracts` and `ContractToAsset` without verifying that the target `(chain, contract_address)` pair isn't already bound to a different asset, and without cleaning up the reverse mapping when an asset's contract for a chain is changed. This mirrors the yAxis `Manager.addToken` bug class: the same "slot" (here, an EVM contract address on a given chain) can end up mapped to two different logical assets, or a stale asset→contract binding can persist after re-registration, corrupting the reverse lookup that `on_accept` trusts to authenticate and route incoming cross-chain messages.

### Finding Description
`register_token` writes both storage maps unconditionally: [1](#0-0) 

There is no `ensure!` that `ContractToAsset::<T>::get(chain, &token_contract)` is empty (or already equals `registration.local_id`) before overwriting it, and no check that `TokenContracts::<T>::get(chain, registration.local_id)` is empty before re-pointing an existing asset's contract. Contrast this with `update_token`, which explicitly removes the stale reverse-mapping entry before writing a new one: [2](#0-1) 

Because `register_token` skips this cleanup/guard step entirely, two failure modes are reachable through `CreateOrigin` (a privileged but ordinary governance/root call, analogous to the yAxis DAO calling `addToken`):

1. **Cross-asset contract collision**: registering asset `B` with the same `(chain, token_contract)` previously bound to asset `A` silently overwrites `ContractToAsset[chain][contract] = B`, while `TokenContracts[chain][A]` still points outgoing sends for `A` at that same contract address.
2. **Stale trusted source on re-registration**: calling `register_token` again for the same `local_id` with a new `token_contract` on the same chain leaves the *old* contract's `ContractToAsset` entry intact (only `update_token` removes it), so the decommissioned contract remains a trusted source for that asset indefinitely.

`on_accept` in the ISMP module implementation relies entirely on `ContractToAsset` to authenticate the source of an incoming message and decide which local asset to credit: [3](#0-2) 

If `ContractToAsset[source][from]` has been repointed to the wrong asset (case 1) or still contains a stale/decommissioned contract (case 2), `on_accept` will mint/transfer the wrong asset, or accept messages from a contract that should no longer be trusted for that asset.

### Impact Explanation
This breaks the ISMP message-authentication invariant that one EVM contract address on one chain corresponds to exactly one local asset. A misconfiguration (accidental double-registration, or intentional reassignment without following the two-step `update_token` cleanup path) causes:
- Unbacked minting: incoming lock/burn messages meant for asset A get credited as asset B (or vice versa), minting tokens with no corresponding lock/burn accounting on the EVM side.
- Permanent freezing/misrouting of funds for the asset whose reverse mapping was clobbered or left stale, since its legitimate incoming messages are now misattributed or its `TokenContracts` entry points at a contract the pallet no longer authenticates correctly.
This matches the "unbacked mint" / "forged message delivery" / "unauthorized app action" criteria for Medium/High severity.

### Likelihood Explanation
`register_token` is gated by `CreateOrigin`, so it requires a privileged call, same threat model as the original yAxis finding, where the DAO (not the attacker) is the one who can trigger duplicate/colliding registration. The report explicitly frames this as a real operational risk ("as the protocol develops, there's likely that one token is supported in two vaults... the DAO may mistakenly add the same token twice"). Here, the same operational mistake — reusing a contract address across two asset registrations, or re-registering an asset with a new contract without going through `update_token`'s cleanup — is just as plausible given the pallet exposes two separate calls (`register_token` for creation, `update_token` for updates) with inconsistent safety guarantees.

### Recommendation
In `register_token`, before inserting into `ContractToAsset`, `ensure!` that no existing entry exists for `(chain, token_contract)` (or that it already equals `registration.local_id`), returning an error such as `Error::<T>::ContractAlreadyRegistered` otherwise. Additionally, when a chain entry already exists for `registration.local_id` (i.e., this is effectively a re-registration), remove the old reverse mapping the same way `update_token` does before inserting the new one — or reject the call and require callers to use `update_token` for existing chain configs.

### Proof of Concept
1. `CreateOrigin` calls `register_token` for `asset_id = A` with `chains = { Evm(1): { token_contract: 0xAAA, decimals: 18 } }`. This sets `TokenContracts[Evm(1)][A] = 0xAAA` and `ContractToAsset[Evm(1)][0xAAA] = A`.
2. `CreateOrigin` later calls `register_token` for a different `asset_id = B` with `chains = { Evm(1): { token_contract: 0xAAA, decimals: 18 } }` (e.g. a copy-paste governance mistake, or reusing an address before the first registration is audited). No check rejects this: `TokenContracts[Evm(1)][B] = 0xAAA` and `ContractToAsset[Evm(1)][0xAAA]` is overwritten to `B`.
3. A subsequent legitimate incoming ISMP `PostRequest` from `source = Evm(1)`, `from = 0xAAA` (a real lock/burn event for asset A) is processed by `on_accept`, which resolves `local_asset_id = ContractToAsset::get(Evm(1), 0xAAA) = B` and mints/transfers asset **B** to the beneficiary instead of asset A — an unbacked mint of asset B and silent loss of the correct crediting for asset A.
