### Title
Webhook tenant identity (`shop`) is taken from an HMAC-unverified header while only the raw body is signature-checked - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is read from the `x-shopify-shop-domain` / `shopify-shop-domain` header — a value that is never part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [1](#0-0) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `hmac` is decoded from the `hmac-sha256` header: [2](#0-1) [3](#0-2) 

Crucially, `shop` is read independently from the `shop-domain` header and is **not** included in the signed bytes: [4](#0-3) 

`Registry.process` validates the HMAC (i.e., the body integrity) and then, on success, treats `request.shop` as an authenticated tenant identifier, passing it straight into `WebhookMetadata` for the developer's handler: [5](#0-4) 

This is the exact identity-binding break described in the rules: *bytes verified (raw body) versus bytes/fields acted on (the `shop` header used as the tenant key)*. Nothing in the signed payload ties the HMAC to the `shop-domain` header, so the gem's own API exposes an unauthenticated field as if it were verified once `HmacValidator.validate` returns `true`.

### Impact Explanation
Any previously-delivered, genuinely-signed webhook payload+HMAC pair (e.g., one the attacker legitimately received for their own store, or intercepted at any point before reaching the app, e.g. logs, proxies, previous storage) can be replayed to the app's webhook endpoint with a forged `shop-domain` header value pointing at a **different, victim** shop. `Registry.process` will still validate (the body and HMAC are untouched and genuinely valid), and the handler will be invoked with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. If the host application's webhook handler uses this `shop` field to look up the victim's stored session/access token or to write/mutate victim-tenant data (which is exactly the documented purpose of `WebhookMetadata#shop`, per `docs/usage/webhooks.md` and the `WebhookHandler` interface), this results in cross-tenant data corruption or unauthorized actions being attributed to/executed against a shop that never triggered the event.

This satisfies the "Critical - cross-tenant access" impact bar: the identity used to select the tenant scope is not covered by the same authentication check (HMAC) that gates request acceptance.

### Likelihood Explanation
Medium-to-High. No possession of `api_secret_key` or an access token is required — the attacker only needs one valid `(raw_body, hmac)` pair, which they can obtain legitimately (e.g., by installing the app on their own store and capturing the webhook their own store received) and then replay with a spoofed `shop-domain` header. Because `Request.new` and `Registry.process` never cross-check the header-derived `shop` against any signed value, this reproduces reliably for every webhook topic the app has registered.

### Recommendation
Do not treat the `shop-domain` header as authenticated purely because the body HMAC matches. Either:
- Include the shop/tenant identity in the signed payload (most Shopify webhook bodies already embed `shop_id`/similar in JSON) and cross-validate `request.shop` against that signed value before dispatching to the handler, or
- Document explicitly (and enforce in the gem) that `WebhookMetadata#shop` must be re-validated by the consuming application against known, previously-provisioned shop records before being used as a tenant/session lookup key, and add a corresponding validation helper in `Registry.process` that fails closed if the header shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the app on their own dev store `attacker.myshopify.com` and lets a webhook (e.g., `orders/create`) fire, capturing the raw HTTP request: body `B` and header `x-shopify-hmac-sha256: H` (valid, since Shopify signed `B` with the app's shared secret).
2. Attacker replays the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com` (and, if used, `x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (now attacker-controlled) header: [4](#0-3) 
4. `Utils::HmacValidator.validate` re-computes the HMAC over `@raw_body` (`B`, unchanged) — validation succeeds because the header change never enters `to_signable_string`. [3](#0-2) 
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`: [5](#0-4) 
6. Any handler logic keyed on `data.shop` (e.g., "look up victim's session and apply this order update") now operates against the victim tenant using attacker-supplied event content.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
