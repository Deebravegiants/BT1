This confirms the contrast clearly: in OAuth, `AuthQuery#to_signable_string` explicitly includes `shop` in the HMAC-covered payload [1](#0-0) , whereas in the webhook flow `Request#to_signable_string` returns only the raw body, excluding the `shop-domain` header entirely from the signed content [2](#0-1) .

### Title
Webhook shop-tenant confusion: `shop` field used for tenant attribution is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`/`webhook_id`/`api_version`) attributes purely from HTTP headers, while `Utils::HmacValidator` only authenticates the raw request body against `Context.api_secret_key`. The `shop` value that downstream handler logic uses to attribute the webhook to a tenant is never part of the signed material, breaking the equality "shop authenticated == shop attributed to the event."

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)` [3](#0-2) . That validator computes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header value [4](#0-3) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [5](#0-4) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated request headers [6](#0-5) . Once HMAC validation passes (which only proves the *body* bytes were signed by the app's secret), `Registry.process` passes `request.shop` — an unverified header — straight into `WebhookMetadata` for the handler to act on [7](#0-6) .

This differs sharply from the OAuth flow, where `AuthQuery#to_signable_string` includes `shop` explicitly in the signed parameter set, so the shop value cannot be altered without invalidating the HMAC [1](#0-0) . Webhooks have no equivalent binding: identical (body, hmac) pairs remain valid for any `shop-domain` header value. A holder of one valid (body, hmac) pair for their own shop — which they legitimately receive from Shopify since they are a real merchant using the app — can replay it with a modified `x-shopify-shop-domain` header pointing to a victim shop, and `HmacValidator.validate` will still return true because it never looks at the shop header.

### Impact Explanation
This is a cross-tenant confusion vector: the webhook handler receives `shop` values that are not cryptographically bound to the authenticated payload. If host application code (following this gem's documented API of trusting `WebhookMetadata#shop` post-validation) uses this value to key session/data lookups, an attacker-controlled tenant can inject events that get attributed to a different, victim shop, without needing that shop's credentials.

### Likelihood Explanation
Exploitation requires the attacker to control an app installation that legitimately receives real signed webhooks (i.e., they must be an existing merchant of the app) — an unprivileged-but-authenticated-to-their-own-tenant position, not a fully anonymous internet user. This is a meaningful boundary crossing (their own tenant → arbitrary other tenant) rather than needing any of the excluded privileged credentials (`api_secret_key`, access token, etc.).

### Recommendation
Include the `shop` (and `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed material for webhook requests, or otherwise cryptographically bind them to the body/signature (e.g., via a signed metadata envelope) so tampering with headers invalidates the HMAC. At minimum, document that `request.shop` must be independently cross-checked against session/tenant records before use.

### Proof of Concept
1. Attacker owns Shop A, which has this app installed and receives real webhooks; a real webhook delivery arrives with `raw_body = B` and `x-shopify-hmac-sha256 = HMAC(B, secret)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `shop-victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `@raw_body` only [5](#0-4)  — signature matches, validation succeeds.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "shop-victim.myshopify.com" ...)` [7](#0-6) , causing the host app to process the event as if it originated from the victim shop.
