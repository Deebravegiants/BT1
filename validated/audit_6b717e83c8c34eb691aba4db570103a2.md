### Title
Unrestricted `CallDispatcher.dispatch()` lets any address drain funds routed through `IntentGatewayV2`'s predispatch flow - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`IntentGatewayV2.placeOrder` routes user-deposited "predispatch" assets through a single, shared `CallDispatcher` contract to execute an arbitrary, order-supplied call (e.g., unwrapping/swapping) before sweeping the resulting balance back into escrow. The sweep only recovers the tokens listed in `order.inputs`, not the tokens listed in `order.predispatch.assets`. `CallDispatcher.dispatch()` itself has no access control - it is a bare `external` function callable by anyone, executing `to.call{value}(data)` against any address with nonzero code. This mirrors the Euler pattern of an unchecked, shared "reserve" address whose balance is not fully reconciled against the intended per-order accounting: any token left in the dispatcher (predispatch tokens not equal to input tokens, partial swaps, slippage, fee-on-transfer leftovers, or a direct donation) is freely sweepable by any third party at any time.

### Finding Description
`placeOrder`'s predispatch branch:
1. Transfers each `order.predispatch.assets[i]` (native or ERC20) into `_params.dispatcher`. [1](#0-0) 
2. Executes the user-supplied `order.predispatch.call` through the dispatcher. [2](#0-1) 
3. Sweeps the dispatcher's balance back to the gateway, but **only for the tokens named in `order.inputs`** - `order.predispatch.assets` tokens are never swept if they differ from `order.inputs` tokens, and any un-consumed remainder of the predispatch asset (or dust from the arbitrary call) stays in the dispatcher. [3](#0-2) 

`CallDispatcher` is a single, permanent, shared contract instance (`_params.dispatcher`) used by every `placeOrder` call, and it accepts ETH via a public `receive()` and executes arbitrary calls with **no caller restriction**: [4](#0-3) 

Because `dispatch()` is callable by anyone (not restricted to the `IntentGatewayV2` contract), any balance the dispatcher accumulates - from mismatched predispatch/input tokens, partial predispatch-call execution, fee-on-transfer residue, or a plain direct token/ETH donation to the dispatcher's address - can be swept out by an unrelated third party simply by calling `CallDispatcher.dispatch()` with a `Call` that transfers the token/ETH to themselves. The only gate is `extcodesize(to) > 0`, which any ERC20 token trivially satisfies.

This is structurally the same root cause as the Euler incident: funds sitting at a shared/reserve address are not protected by an ownership or liquidity check tying them to the entity that deposited them, so anyone who can reach that address's balance can extract it.

### Impact Explanation
Any value left behind in the shared `CallDispatcher` - which is reachable by every user of `IntentGatewayV2` through `predispatch` - is permanently exposed to theft by any address. This includes:
- Residual `order.predispatch.assets` tokens that differ from `order.inputs` tokens (never swept back by `placeOrder`).
- Slippage/dust left over from the arbitrary `predispatch.call` (e.g., a swap that doesn't consume 100% of the input).
- Native ETH sent to `dispatcher` (the contract has an unconditional `receive()`), which is not covered by the token sweep logic unless the specific order also lists `address(0)` as an input.

Since `CallDispatcher` is a singleton shared across the entire deployment (all users, all orders), this is a critical, unbounded theft vector, not a self-inflicted loss: an attacker monitoring the dispatcher's balance can drain any accumulated funds left by other users' orders.

### Likelihood Explanation
High. Any user constructing a `predispatch` order whose asset set doesn't exactly match `order.inputs` (a legitimate and expected use case per the code comment "e.g., unwrapping LP tokens"), or any `predispatch.call` that doesn't fully consume its input (normal for swaps with slippage), leaves exploitable residue. No privileged role, governance action, or malicious insider is required - a single unprivileged actor can call `CallDispatcher.dispatch()` directly at any time after residue accumulates.

### Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by the configured `IntentGatewayV2` (or a registered set of gateways), e.g. via an `onlyGateway`/`restrict` modifier, so third parties cannot invoke it directly.
- In `placeOrder`, sweep back the full set of tokens touched by `order.predispatch` (union of `predispatch.assets` and `order.inputs` tokens, plus native ETH) rather than only `order.inputs` tokens, so no balance is left behind in the shared dispatcher.
- Consider making the dispatcher ephemeral (deployed per-order via `CREATE2` and self-destructed/cleared after use) instead of a single persistent shared contract, eliminating cross-order residue entirely.

### Proof of Concept
1. User A places an order with `predispatch.assets = [TokenX: 1000]` and `predispatch.call` that swaps `TokenX` for `TokenY`, but `order.inputs = [TokenY: amount]`. Suppose the swap leaves 5 `TokenX` unconsumed in `dispatcher` due to rounding/slippage (or a partially-filled predispatch call).
2. `placeOrder`'s sweep loop only iterates `order.inputs` (TokenY), so the 5 `TokenX` remain in `CallDispatcher`. [5](#0-4) 
3. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: TokenX, value: 0, data: transfer(attacker, 5)})]))` directly - this succeeds because `dispatch()` has no access control and `TokenX` has nonzero code. [6](#0-5) 
4. Attacker has stolen User A's residual funds with no interaction with `IntentGatewayV2` at all. Repeating this across many orders/predispatch flows accumulates ongoing losses for any user relying on predispatch with non-matching asset/input tokens.

    /**
     * @dev Receive function to accept ETH transfers
     */
    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
