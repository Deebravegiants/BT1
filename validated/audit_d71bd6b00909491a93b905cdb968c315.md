### Title
Webhook processing trusts the unauthenticated `shop-domain` header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then forwards the value of the `shop-domain` header — which is *not* part of the signed material — straight to the application's handler as the identity of the shop the event belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read directly from an HTTP header with no cryptographic binding to that body: [2](#0-1) 

`Registry.process` validates the request using only this HMAC-over-body check, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature purely from `to_signable_string` (the raw body) and `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop)` (or equivalent inclusion of shop in the signed payload). What is actually checked is `hmac == HMAC(secret, body)`, with `shop` taken from an out-of-band, unsigned header. Because `Context.api_secret_key` is the **app's** single client secret — identical for every merchant shop that has installed the app — any shop that has installed the app can capture one of its own legitimate webhook deliveries (valid body + valid HMAC, since the secret is shared across all installs of that app) and replay it to the app's webhook endpoint with the `shopify-shop-domain` / `x-shopify-shop-domain` header rewritten to name a *different* shop that also has the app installed. The HMAC check still passes because it never looked at the shop header, so `Registry.process` calls the application's webhook handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop while `body`/`topic` are the attacker's own genuine (and attacker-controlled, since they own that shop's data) content.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem is supposed to provide to consuming applications: `Registry.process` is the gem's designated authentication boundary for webhooks (`raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)`), and callers reasonably treat a passing check as proof that both the payload and the shop attribution came from Shopify for that specific shop. Any host application that keys per-tenant side effects off `WebhookMetadata#shop` (installation/uninstallation bookkeeping, billing, data deletion via `customers/redact` or `shop/redact`, cache invalidation, webhook-driven authorization decisions, etc.) can be tricked into applying another merchant's data or triggering shop-scoped operations against a victim tenant it does not control. This is a cross-tenant access vulnerability entirely within this gem's own webhook-authentication code path, not a defect of the host app ignoring documented behavior — the gem's own `process` method is what discards the shop binding.

### Likelihood Explanation
Exploitation requires only an unprivileged attacker who has installed the app on their own store (a routine, low-privilege action any Shopify merchant can take) and the ability to send an HTTP request to the app's public webhook endpoint with a captured body/HMAC pair and a modified `shop-domain` header — no access token, `client_secret`, or victim credentials are needed. The only prerequisite is that the target app share one `client_secret` across all installs (the normal/default configuration for Shopify apps), which is true for the vast majority of consumers of this gem.

### Recommendation
Bind the shop identity to the verified material before trusting it:
- Include the shop domain (and/or topic) inside the HMAC-signed payload used for verification, or
- Cross-check `request.shop` against an independently trusted source (e.g., require the caller to supply the shop the webhook was registered for, or validate the header against a list of shops that have valid installations before dispatch), or
- At minimum, document/emit the unauthenticated header for host apps and require them to independently verify shop ownership before using `WebhookMetadata#shop` for any privileged/tenant-scoped action, and add a check in `Registry.process` (or `Request`) so it does not present `shop` as trusted if it isn't cryptographically bound to the signed body.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` (attacker-controlled) and `shop-b.myshopify.com` (victim), sharing the same app `client_secret`.
2. Attacker triggers a webhook delivery for `shop-a` (e.g., `orders/create`) and captures the raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — see `lib/shopify_api/utils/hmac_validator.rb:33-40`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: shop-b.myshopify.com` and `x-shopify-topic` of choice.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (`lib/shopify_api/webhooks/request.rb:45-63`), `Utils::HmacValidator.validate` succeeds because it only re-derives `H` from `B` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), and `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "shop-b.myshopify.com"` and attacker-controlled body content (`lib/shopify_api/webhooks/registry.rb:188-200`), successfully impersonating `shop-b` despite lacking any credential for it.
