Audit Report

## Title
CORS wildcard-origin bypass via boundary-unaware suffix match in gateway HTTP server allows any domain sharing a suffix to be treated as an allowed origin - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway HTTP server's `isAllowedOrigin` function implements wildcard CORS origin matching (e.g., `https://*.remix.ethereum.org`) using a bare `strings.HasSuffix(originHost, allowedHost)` check after stripping the `*.` prefix, with no requirement that the match be preceded by a `.` label boundary. As a result, any attacker-controlled domain whose name merely ends with the same character sequence as the configured allowed host (e.g., `evilremix.ethereum.org` for `*.remix.ethereum.org`, or `notethereum.org` for `*.ethereum.org`) is incorrectly treated as an allowed origin.

## Finding Description
`isAllowedOrigin` at [1](#0-0)  strips the `*.` prefix from the configured wildcard host and then checks only `strings.HasSuffix(originHost, allowedHost)`. This is a string-suffix comparison, not a hierarchical/hostname-label comparison: it does not verify that the character immediately preceding the matched suffix in `originHost` is a `.`. Consequently `evilremix.ethereum.org` (attacker-registered domain) satisfies `HasSuffix("evilremix.ethereum.org", "remix.ethereum.org")` even though it shares no actual subdomain relationship with `remix.ethereum.org`.

`handleRequest` then reflects the raw attacker `Origin` header into `Access-Control-Allow-Origin` once `isAllowedOrigin` returns true, at [2](#0-1) , without any further boundary re-validation.

The existing test suite in `httpserver_test.go` exercises only legitimate subdomain matches (`TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards`) and non-suffix-matching negatives such as `https://ethereum.remix.org` (reordered labels, not a suffix collision) — it does not test the suffix-collision case (e.g., `evilethereum.org` against `*.ethereum.org`), so this gap is unmitigated and untested. [3](#0-2) 

## Impact Explanation
An operator who configures a wildcard CORS entry to allow their own subdomains (e.g., `https://*.chain.link`) unintentionally also allows any domain an attacker registers that merely ends with the same label sequence (e.g., `evilchain.link` is not a suffix collision, but `notchain.link` — where "chain.link" is the exact suffix — would collide) to receive `Access-Control-Allow-Origin` reflecting their origin, letting a malicious webpage read the gateway's JSON-RPC responses cross-origin. This bypasses the intended origin allowlist boundary for the gateway's internet-facing HTTP endpoint.

## Likelihood Explanation
Exploitation requires no privileges against the gateway itself: an attacker needs only to register a domain string ending in the same characters as a configured wildcard suffix and issue a cross-origin request (or lure a victim browser to do so). This does, however, depend entirely on an operator having opted into a wildcard `CORSAllowedOrigins` configuration — a supported but non-default configuration choice — and depends on the attacker being able to register a domain with the specific suffix collision, which is a real but non-trivial precondition (domain availability/naming).

## Recommendation
Replace the bare suffix check with a boundary-aware comparison:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
Add regression tests using suffix-collision hostnames (e.g., `evilethereum.org` vs. `*.ethereum.org`) that must be rejected, alongside the existing legitimate-subdomain acceptance tests.

## Proof of Concept
Given gateway config `CORSAllowedOrigins = ["https://*.ethereum.org"]`:
1. Attacker controls `https://notethereum.org` (ends in literal suffix `ethereum.org` but is not a subdomain).
2. Attacker's page issues `fetch()` to the gateway HTTP endpoint with `Origin: https://notethereum.org`.
3. In `isAllowedOrigin`, `allowedHost` becomes `ethereum.org` after stripping `*.`; `strings.HasSuffix("notethereum.org", "ethereum.org")` returns `true`, so the origin is wrongly allowed.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://notethereum.org`, letting the attacker page read the JSON-RPC response cross-origin.

This can be reproduced as a Go unit test in `httpserver_test.go` analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, but asserting that `https://notethereum.org` against `["https://*.ethereum.org"]` currently returns a non-empty `Access-Control-Allow-Origin` header (should be empty after the fix).
