### Title
EmporiumSignature EIP-712 digest omits `feeStructure.feeToken`, letting an unprivileged caller drain a wallet-authorized fee cap in an arbitrarily more valuable token - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`verifyWallet()` in `EmporiumUpgradeable.sol` recovers a wallet owner's EIP‑712 signature over `EMPORIUM_SIGNATURE_TYPEHASH`, which binds only `emporiumMessage`, the hashed `ops`, `maxFee` and `deadline` — it never binds `circomData.feeStructure.feeToken` (or any other token identity used to pay the fee). [1](#0-0)  The only on-chain guard that ties `maxFee` to reality is a bare numeric comparison, `circomData.feeStructure.flatFee > stack.maxFee`, with no unit/token check. [2](#0-1)  This is the same bug class as the reported COLLATERAL-not-in-digest issue: a value-bearing token address is excluded from the signed digest, so a signature intended for one token can be reused/reinterpreted against a different, more valuable token.

### Finding Description
`EmporiumStack.signerAddress` designates a `HinkalWallet` whose owner off-chain signs an authorization permitting a caller (any address in `$._isAllowedRecipient`, reached indirectly by any unprivileged EOA driving a Hinkal transaction through `runAction`) to execute `stack.ops` and pay up to `stack.maxFee` in relay fees. [3](#0-2)  The signed struct is:

```
EmporiumSignature(uint256 message, EmporiumOperation[] ops, uint256 maxFee, uint256 deadline)
``` [4](#0-3) 

`maxFee` is a bare `uint256` with no token field, so the signer cannot bind it to a specific asset. The actual fee token, `circomData.feeStructure.feeToken`, and the flat fee amount, `circomData.feeStructure.flatFee`, are supplied by the same untrusted `circomData` calldata that the caller of `runAction` constructs. [5](#0-4)  Nothing in `performHinkalChecks` or the ZK circuit constrains `feeStructure` beyond a keccak256 self-consistency check (`getHashedCalldata` == `calldataHash`) that the same untrusted caller who builds `circomData` also controls — the SNARK never validates the fee structure's semantic meaning. [6](#0-5) [7](#0-6) 

When `payRelayFees` runs, `relayFee = flatFee` for the signer-authorized path, and this fee is pulled directly from the user's `HinkalWallet` via `sendToRelayFromWallet` → `IHinkalWallet.doSendToRelay` → `sendToRelay` → `transferERC20TokenOrETH`. [8](#0-7) [9](#0-8) 

Because `feeStructure.feeToken` is not part of the signed digest, an unprivileged caller can take a signature the wallet owner produced expecting `maxFee` to denominate a low-value token (e.g. a stablecoin with 18 decimals) and instead submit `circomData` with `feeStructure.feeToken` set to a high-value/low-decimal token (e.g. WBTC) while keeping the same numeric `flatFee <= maxFee`. The `FeeExceedsSignedMax` check still passes because it only compares raw numbers, not token-denominated value, so the wallet is drained of far more value than the signer authorized — exactly analogous to the reported bug where an unincluded token field lets a signature for 1e9 USDC be replayed for 1e9 WBTC.

### Impact Explanation
This breaks the "unauthorised asset movement" invariant: value is transferred out of a user's `HinkalWallet` to a relay in an amount/asset the wallet owner never actually signed off on, because the token identity that gives `maxFee` its meaning is outside the signed digest. This is theft of user (wallet) funds by an unprivileged actor holding (or intercepting) a valid signed authorization, mapping to the Critical impact class ("direct theft of ... user funds").

### Likelihood Explanation
Likelihood is limited by the fact that `emporiumMessage` is single-use (`$.usedMessages`) and the attack requires possession of a not-yet-consumed valid `EmporiumStack` signature (typically produced for a legitimate relay flow) before submitting it with a substituted `feeStructure.feeToken`. [10](#0-9)  Since signed messages are transmitted off-chain to be relayed, any party who observes or front-runs one signed authorization (not necessarily the assigned relay) can exploit it, and no additional privileged role is required beyond calling the reachable `runAction` entrypoint through the standard Hinkal transaction flow.

### Recommendation
Include `feeStructure.feeToken` (and ideally the full `feeStructure`, or at minimum every token address used to compute/deny the transferred fee) inside `EMPORIUM_SIGNATURE_TYPEHASH` so the signer explicitly authorizes both the fee amount and its denomination, closing the same class of gap described in the COLLATERAL/digest report.

### Proof of Concept
Conceptual sequence (no code execution possible in this environment):
1. Wallet owner signs an `EmporiumStack` with `maxFee = 1_000_000` intending it to apply to a fee token such as a stablecoin.
2. An unprivileged actor intercepts this valid, unused signature and builds `circomData` for `runAction` with `feeStructure.feeToken` set to a high-value token (e.g., WBTC) and `feeStructure.flatFee = 1_000_000` (same raw number, now denominated in WBTC's 8 decimals).
3. `verifyWallet` recomputes the EIP‑712 digest from `emporiumMessage`, `ops`, `maxFee`, `deadline` only — recovers the same signer, passes. [11](#0-10) 
4. `flatFee (1_000_000) > maxFee (1_000_000)` is false, so `FeeExceedsSignedMax` does not revert. [2](#0-1) 
5. `payRelayFees` pulls `1_000_000` units of WBTC (worth vastly more than the intended stablecoin fee) from the victim's `HinkalWallet` to the relay. [8](#0-7) 

Note: I could not fully trace how `EmporiumStack` signatures are generated/distributed off-chain (e.g., SDK code) since that logic is outside `contracts/**`/`circuits/**` in-scope paths; this PoC reflects the on-chain verification logic only.

        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
