### Title
Unprivileged Balance-Griefing of Gas-Key/Account Deletion via Strict Threshold Check - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`TransferToGasKeyAction` lets *any* account fund an existing gas key belonging to a *different* account, exactly like a plain `Transfer`. The gas-key deletion path (and, by extension, account deletion) rejects the operation with `GasKeyBalanceTooHigh` whenever the gas key's balance exceeds a fixed constant (`GasKeyInfo::MAX_BALANCE_TO_BURN`). Because the check is a strict, unconditional threshold comparison that doesn't distinguish who funded the balance, an unprivileged third party can push a victim's gas-key balance over the threshold with a trivial deposit, causing the victim's own `DeleteKey`/`DeleteAccount` action to revert — the same "attacker inflates a balance the victim doesn't control, breaking a strict check the victim relies on" bug class described in the GMX report (execution-fee equality griefed by a stray WETH transfer).

### Finding Description
`action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`) increments `gas_key_info.balance` on the target `account_id`'s gas key by `action.deposit`, without any check that the caller (predecessor) is the same account that owns the key: [1](#0-0) 

An attacker can sign a `SignedTransaction` from their own full-access key with `receiver_id = victim` and action `TransferToGasKey { public_key: <victim's gas key>, deposit: 1 yoctoNEAR }`. The victim's gas keys (and their current balances) are publicly queryable on-chain, so the attacker can precisely target a gas key sitting just under the burn threshold.

`delete_gas_key` then enforces a strict, unconditional cap: [2](#0-1) 

Once `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`, `DeleteKey` on that gas key always fails with `ActionErrorKind::GasKeyBalanceTooHigh`, confirmed by the test at `runtime/runtime/src/access_keys.rs:1218-1256`: [3](#0-2) 

Account deletion sums *all* gas-key balances against the same `MAX_BALANCE_TO_BURN` threshold (documented and tested at `runtime/runtime/src/access_keys.rs:1334-1368`): [4](#0-3) [5](#0-4) 

So topping up any one of an account's gas keys with a trivial amount can also block `DeleteAccount` if the sum of all gas-key balances crosses the 1 NEAR cap.

### Impact Explanation
This is a griefing/DoS on unprivileged account operations, analogous to the reported class: the victim's `DeleteKey`/`DeleteAccount` transaction — which they fully control the inputs to — reverts because an unrelated, unprivileged party altered a balance that feeds into a strict threshold check. This can be used to:
- Block a specific gas key from being deleted (forcing the owner to first issue a `WithdrawFromGasKeyAction` to bring the balance back under threshold before they can delete it).
- Block `DeleteAccount` entirely for as long as the attacker keeps re-funding gas keys faster than the owner can withdraw/delete, since `TransferToGasKey` costs the attacker only the gas fee plus the tiny deposit each time.

There is no token theft or inflation, and the impact is bounded to an extra remediation step or transient inconvenience (the owner can always call `WithdrawFromGasKey` on their own key to drop the balance back under `MAX_BALANCE_TO_BURN` before retrying deletion), which matches the "Acknowledged / no direct fund loss" severity of the original GMX report.

### Likelihood Explanation
High: the attack only requires a `TransferToGasKeyAction` in a single signed transaction from an attacker's own account, costs the attacker essentially nothing (gas fee + 1 yoctoNEAR), and the target gas key's public key/balance is discoverable via a standard account query. No special privileges, validator status, or race conditions are required.

### Recommendation
- Restrict `TransferToGasKeyAction` so that only the account itself (`predecessor_id == account_id`, i.e. self-funding via `signer_id == receiver_id`, or a receipt originated by the account's own promise) can top up its gas keys, consistent with how gas keys are meant to be funded by their owner. 
- Alternatively, decouple the deletion path from a hard balance cap: allow deletion to burn any residual balance (with appropriate accounting/limits) rather than reverting outright when the balance exceeds `MAX_BALANCE_TO_BURN`, so a third party cannot lock out deletion by inflating the balance.

### Proof of Concept
1. Victim `V` has a gas key `pk` with balance `B` close to (but under) `GasKeyInfo::MAX_BALANCE_TO_BURN` (verifiable via `runtime/runtime/src/access_keys.rs:1218-1256`, threshold ≈ 1 NEAR).
2. Attacker `A` queries `V`'s access keys via RPC to learn `pk` and `B`.
3. `A` signs and submits `SignedTransaction { signer_id: A, receiver_id: V, actions: [TransferToGasKey { public_key: pk, deposit: MAX_BALANCE_TO_BURN - B + 1 }] }` using `A`'s own full-access key.
4. `action_transfer_to_gas_key` (`access_keys.rs:257-288`) increases `V`'s gas key balance above `MAX_BALANCE_TO_BURN`.
5. `V` submits `DeleteKey { public_key: pk }` (or `DeleteAccount`); `delete_gas_key` (`access_keys.rs:93-111`) now returns `ActionErrorKind::GasKeyBalanceTooHigh`, reverting `V`'s intended action, until `V` first issues `WithdrawFromGasKeyAction` to reduce the balance.

Note: I did not have access to the exact numeric value/definition site of `GasKeyInfo::MAX_BALANCE_TO_BURN` (only inferred ≈1 NEAR from test fixtures); confirming the exact constant would require reading `core/primitives-core/src/account.rs` directly, which was not fully retrievable in this session.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}

    #[test]
    fn test_delete_account_gas_key_balance_at_threshold() {
        let (account_id, public_key, access_key) = test_account_keys();
        let public_keys: Vec<PublicKey> = (0..3)
            .map(|i| PublicKey::from_seed(KeyType::ED25519, &format!("gas_key_{i}")))
            .collect();
        let mut state_update = setup_account(&account_id, &public_key, &access_key);
        let mut account = get_account(&state_update, &account_id).unwrap().unwrap();
        for public_key in &public_keys {
            add_gas_key_to_account(&mut state_update, &mut account, &account_id, public_key);
        }

        // Fund gas keys so total is exactly 1 NEAR
        let deposit_amounts = [
            Balance::from_millinear(400),
            Balance::from_millinear(400),
            Balance::from_millinear(200),
        ];
        for (pk, amount) in public_keys.iter().zip(deposit_amounts.iter()) {
            transfer_to_gas_key(&mut state_update, &account_id, pk, *amount);
        }
        state_update.commit(StateChangeCause::InitialState);

        let action_result = test_delete_account(
            &account_id,
            AccountContract::from_local_code_hash(CryptoHash::default()),
            100,
            PROTOCOL_VERSION,
            &mut state_update,
        );
        assert!(action_result.result.is_ok());
        let expected_burnt =
            deposit_amounts.iter().fold(Balance::ZERO, |acc, x| acc.checked_add(*x).unwrap());
        assert_eq!(action_result.tokens_burnt, expected_burnt);
    }
