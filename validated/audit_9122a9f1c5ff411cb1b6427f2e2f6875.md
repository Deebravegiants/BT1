### Title
Cookie-based session lookup returns attacker-guessable, non-secret `shop_userId` / `offline_shop` identifiers as session credentials - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`Session#id` (used as the value stored in the `shopify_app_session` cookie) is deterministically derived from public/guessable data — `"#{shop}_#{associated_user.id}"` for online sessions and `"offline_#{shop}"` for offline sessions — rather than a random opaque token. `SessionUtils.cookie_session_id` blindly trusts whatever value is present in the `shopify_app_session` cookie of an incoming request, with no signature or freshness check, so it is used as-is to key into the host app's session store.

### Finding Description
The claimed binding is: `cookie_session_id(cookies) == "the caller's own previously-issued session identifier"`. In practice this only holds because `Session#id` (`lib/shopify_api/auth/session.rb:114-116`) is `"#{shop}_#{associated_user.id}"` or `"offline_#{shop}"` — both fully reconstructable by anyone who knows the shop's `.myshopify.com` domain (public) and a staff `associated_user.id` (a small/sequential integer that can be enumerated). `SessionUtils.cookie_session_id` (`lib/shopify_api/utils/session_utils.rb:68-71`) does `cookies[SESSION_COOKIE_NAME]` with no HMAC/signature check, and `current_session_id` (`lib/shopify_api/utils/session_utils.rb:19-37`) returns that raw value directly as the "session id" to the caller for storage lookup, with no reference back to any request-bound secret (unlike the JWT branch, which validates the token's signature via `Auth::JwtPayload`). None of the gem's other guards apply here: `HmacValidator.validate` only protects the OAuth callback query string, `ShopValidator.sanitize!` only validates shop domain format, and `JwtPayload`'s `aud` check only applies to the JWT branch, which is bypassed entirely when `shopify_id_token` is omitted.

Attacker request: send any HTTP request to the host app with `Cookie: shopify_app_session=<guessed-shop>_<guessed-staff-id>` and no `Authorization`/`id_token`. If `Context.embedded?` is true and the fallback cookie branch is reached (lines 20-30) — or the app is non-embedded (lines 31-36), which is the officially documented use case for this cookie ("Cookie based authentication is not supported for embedded apps... Non-embedded apps are able to use cookies") — `current_session_id` returns the guessed string verbatim, which the host app then uses to fetch a `Session` (and its `access_token`) from its session store.

### Impact Explanation
If the guess matches a real, previously stored session key, the host app will retrieve and use another merchant's/staff member's stored session (including their access token) for the guesser's request — a cross-tenant authentication bypass. This is repeatable against any victim shop/staff-id pair; the attacker does not need to intercept or steal a cookie, only guess it, since the "session id" carries no entropy of its own.

### Likelihood Explanation
This requires: (1) a non-embedded app, or an embedded app relying on the documented cookie fallback when no `shopify_id_token` is sent, and (2) the victim's session already stored under the predictable key. Shop domains are public/discoverable and staff IDs are typically small sequential integers, so guessing cost is low and the attack is fully remote and repeatable — but it depends entirely on how the host application implements session cookie issuance/scoping (e.g., whether the cookie is also `HttpOnly`/`Secure`, scoped per-browser session, and whether the host adds its own signing). This gem provides only the identifier derivation and lookup helper; it does not sign or bind the cookie to anything request-specific.

### Recommendation
Do not use `Session#id` (or any value derived purely from `shop`/`user id`) as the cookie value. Generate a separate random, high-entropy, unguessable identifier for the `shopify_app_session` cookie (e.g., `SecureRandom.uuid`/`SecureRandom.hex(32)`), store it as a pointer to the actual session server-side, and never let `SessionUtils.cookie_session_id` accept a client-supplied value that is also a deterministic session-storage key discoverable from public shop/staff data.

### Proof of Concept
Not producible as a self-contained minitest/WebMock proof strictly inside `lib/`: the divergence (identifier predictability) is real, but the actual exploitable harm (attacker successfully retrieves another tenant's `access_token`) only manifests in the host application's session-storage layer, which lives outside this gem and outside `test/`. A minitest for `SessionUtils.current_session_id` can only show that `cookie_session_id({SESSION_COOKIE_NAME => "myshop.myshopify.com_12345"})` returns that exact string unchanged and unauthenticated — it cannot demonstrate cross-tenant token theft without a stubbed host-side session store, which is out of this gem's scope.
