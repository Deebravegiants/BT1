### Title
Duplicate `address(0)` (ETH) entries in `erc20TokenAddresses` let an internal transact double-count a single `msg.value` deposit across two token slots, minting 2x shielded ETH value for 1x real ETH received - (File: `contracts/Hinkal.sol`)

### Summary
`Hinkal.transact` reconstructs a per-token `balanceDif` for every entry in `circomData.erc20TokenAddresses` and, for any entry equal to `address(0)`, adds `msg.value` into that entry's balance-diff calculation. Neither `Hinkal.sol` nor `HinkalHelper.dimensionsCheck`/`checkOnchainCreation` enforce that `erc20TokenAddresses` contains unique addresses, so an attacker can list `address(0)` at two (or more) indices in the same call. Because the `+msg.value` correction and the "unchanged real balance" observation are applied independently per index, a single ETH payment satisfies the `balanceDif == amountChanges[i]` equality at every duplicated index simultaneously, letting the attacker credit shielded ETH value once per duplicated slot for only one real ETH transfer.

### Finding Description
The equality the code is supposed to enforce per token `i` is:
`realValueReceivedForToken(i) == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount(i)`

In `Hinkal.transact`, real value received is approximated via balance snapshots: [1](#0-0) 

and the `address(0)` correction plus the equality check: [2](#0-1) 

For a pure ETH deposit through `_internalTransact` (`externalActionId == 0`), the deposit path is a no-op transfer that only asserts `msg.value == amountChanges[i]`; it does not move any ETH (since `_to == address(this)`): [3](#0-2) [4](#0-3) 

Because the ETH backing the deposit is already reflected in `address(this).balance` before `oldBalances` is even snapshotted (EVM credits `msg.value` to the callee before the function body executes), `oldBalances[i] == newBalances[i]` for every `address(0)` entry when no other transfer touches ETH during the call. The `balanceDif` formula therefore evaluates to `msg.value` (added once) for **every** index `i` where `erc20TokenAddresses[i] == address(0)` — not just once for the whole transaction.

Neither `dimensionsCheck` nor `checkOnchainCreation` in `HinkalHelper.sol` verify uniqueness of `erc20TokenAddresses`: [5](#0-4) [6](#0-5) 

Exploit flow:
1. Attacker calls `Hinkal.transact` with `dimensions.tokenNumber = 2` (or more), `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [msg.value, msg.value]`, `onChainCreation = [false, false]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`, and sends exactly `msg.value` ETH.
2. Attacker generates a valid proof for two independent token "slots" both bound to `address(0)` in the public input vector, each slot creating its own output UTXO/commitment of value `msg.value` (slot inputs can be zero/dummy nullifiers, which the circuit's `inTotal + amountChanges === outTotal` constraint permits for a fresh deposit).
3. In `_internalTransact`, both loop iterations execute `transferERC20TokenFromOrCheckETH(address(0), attacker, address(this), msg.value)`, which is a no-op transfer (since `_to == address(this)`) and only re-checks `msg.value == amountChanges[i]` — this passes for both `i=0` and `i=1` because both hold the same value.
4. Back in `transact`, both `balanceDif` computations independently equal `msg.value` (per the reasoning above) and both satisfy `balanceDif == amountChanges[i]`, so both `require` checks pass.
5. `insertCommitments` mints two independent sets of shielded UTXOs, each carrying `msg.value` worth of ETH, i.e., `2 * msg.value` total shielded ETH credited to the attacker's UTXO set, while only `msg.value` real ETH was ever transferred into the contract.

This works because the balance-diff/`msg.value` reconciliation logic assumes each real token appears **at most once** in `erc20TokenAddresses`; that assumption is never validated on-chain, and the `+msg.value` term is re-applied per matching index rather than once per unique token.

### Impact Explanation
The attacker mints shielded UTXO value with no matching backing asset in the vault — a direct case of "minting shielded value without backing," matching the Critical impact category (protocol insolvency). The attacker can repeat this for any multiple of duplicate `address(0)` slots (N slots → N× the deposited ETH credited as shielded value) up to whatever `dimensions.tokenNumber`/circuit slot limits allow, and can repeat the attack across transactions to continually drain backing reserves relative to outstanding shielded liabilities.

### Likelihood Explanation
No privileged role is required: the attacker only needs to craft `CircomData`/`Dimensions` with duplicate `address(0)` entries and generate a self-consistent proof for two independent slots bound to the same token index, both permitted by `checkOnchainCreation` (which only forbids `onChainCreation` for internal transactions, not duplicate token addresses) and `dimensionsCheck` (which only checks array-length consistency, not address uniqueness). This requires access to proof generation for the circuit's public inputs, which the attacker fully controls per the stated threat model. I was not able to fully inspect `circuits/MainEVMCircuit.circom` before running out of tool calls to confirm the circuit does not itself impose a global "erc20 addresses must be pairwise distinct" constraint across slots; if such a constraint exists in the circuit, this exact vector would be blocked at the proof level even though the Solidity-side check is missing. This should be verified directly against `MainEVMCircuit.circom` before final triage.

### Recommendation
In `HinkalHelper.dimensionsCheck` (or a new check called from `performHinkalChecks`), enforce that all entries of `circomData.erc20TokenAddresses` are pairwise distinct. Additionally, in `Hinkal.transact`, apply the `msg.value` correction exactly once (e.g., track a `bool ethAccountedFor` flag, or aggregate all `address(0)` amountChanges into a single required equality before adding `msg.value` once) rather than per-matching-index, so duplicate ETH entries cannot each independently claim credit for the same real ETH transfer.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, verifier, and merkle infra per repo test harness.
2. Generate a valid proof (via snarkjs/circom test fixtures) for a `CircomData` with `dimensions.tokenNumber = 2`, `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, zero/dummy `inputNullifiers` for both slots, two independent output commitment sets each worth `X`, `externalActionData.externalActionId = 0`.
3. Call `Hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
4. Assert: `address(hinkal).balance` increased by exactly `X` (real value in), but the sum of newly inserted shielded UTXO amounts for `address(0)` equals `2*X` (credited shielded value) — i.e., assert `vaultBalanceDelta (X) < totalCreditedUTXOValue (2*X)`, demonstrating the equality `net tokens entering Hinkal == sum(amountChanges)+sum(onchain UTXO amounts)` is violated at the aggregate/protocol-solvency level even though each individual `require` in the loop passes.
