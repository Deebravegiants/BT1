### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by checking that the HMAC over the raw request body matches the app's `api_secret_key`, but the `shop` value passed to the app's handler is read from an HTTP header that is never included in that signature. Because the `api_secret_key` is shared across every shop that installs the app, any shop owner can obtain a validly-signed body/HMAC pair for their own store and then replay it with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header pointing at a different, victim shop, causing the app to process attacker-controlled data under another tenant's identity.

### Finding Description
`Registry.process` verifies authenticity with: [1](#0-0) 

The check calls `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — nothing else: [3](#0-2) 

However, `shop` (and `topic`, `webhook_id`, `api_version`) are pulled directly from unauthenticated headers: [4](#0-3) 

`process` then forwards this unauthenticated `shop` value straight into the `WebhookMetadata` struct passed to the app's handler: [5](#0-4) [6](#0-5) 

This is a broken identity binding of exactly the class described in the report: an equality that should hold — `hmac_signed(shop) == shop_used_by_handler` — does not, because the signature only binds `hmac_signed(body)`, while `shop_used_by_handler` is taken from a completely separate, unauthenticated header. The library's own documentation confirms that host apps are expected to key tenant-scoped work (e.g. enqueuing jobs, looking up records) directly off `data.shop`: [7](#0-6) 

**Attack path:**
1. Attacker installs the target app on their own shop (unprivileged; no special credentials of the victim or the app needed) and triggers a webhook topic that includes attacker-controlled data in the body (e.g. `products/update` with an attacker-editable title/note field, or any topic with a body the attacker can influence).
2. Attacker captures the raw body and the valid `X-Shopify-Hmac-Sha256` value that Shopify computed with the app's shared `api_secret_key`.
3. Attacker POSTs that same raw body + HMAC to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with the victim shop's domain.
4. `HmacValidator.validate` succeeds (body+HMAC pair is valid for the app's secret), and `Registry.process` invokes the handler with `shop` set to the victim's domain and `body` set to the attacker's chosen content.
5. The host application processes attacker data as if it originated from the victim tenant — e.g. writing to the victim's stored records, triggering victim-scoped side effects, or (for topics like `app/uninstalled` or `shop/redact`) forcing tenant-destructive actions against a shop the attacker doesn't control.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-used-as-tenant-key binding and enables cross-tenant access/interference: an unprivileged user who has only installed the app on their own store can cause the app to process forged data attributed to an arbitrary other merchant, without needing that merchant's access token, session, or `client_secret`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High/likely reachable: any merchant that installs the app can generate at least one genuinely-signed webhook body for their own store (webhooks fire automatically on ordinary events), and replaying it with a modified header requires nothing beyond basic HTTP tooling — no secret material or privileged access is needed. The vulnerable code path (`Registry.process` / `Webhooks::Request`) is the gem's standard, documented mechanism for webhook verification, so any app that uses it as directed is exposed.

### Recommendation
Bind the shop (and other trust-relevant metadata such as topic/webhook id) into the value that is actually verified, e.g.:
- Compute/verify webhook authenticity using a signature that covers `shop-domain` (and topic) alongside the body, or
- Independently validate that `request.shop` matches an expected/registered shop domain (e.g. one already known to have an active session/webhook subscription) before invoking the handler, rejecting the webhook if it doesn't, or
- At minimum, document explicitly and enforce in `Registry.process` that host apps must not trust `data.shop` for tenant lookups unless it is cross-checked against the app's own installed-shop records.

### Proof of Concept
Conceptual reproduction using the test harness pattern already present in the codebase:
```ruby
raw_body = '{"note":"attacker payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker obtains this valid (raw_body, hmac) pair from a webhook fired on their own shop.
forged_headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"note"=>"attacker payload"}, ...))
```
`Registry.process` accepts this because `HmacValidator.validate` only checks the body signature (`lib/shopify_api/webhooks/request.rb` `to_signable_string`), never the `shop-domain` header value that is subsequently trusted as the tenant identity.

          received_signature = verifiable_query.hmac
