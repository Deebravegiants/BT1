### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity used by the host application (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw request body only. Any party who can obtain one validly-signed webhook (e.g., by installing the app on their own shop) can replay that exact body/HMAC pair while substituting a different `shop-domain` header, and the library will report the request as authentic for the attacker-chosen shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an unauthenticated header with no cross-check against the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only confirms that `hmac` matches `compute_signature(to_signable_string, secret)`, i.e. it authenticates the body bytes, never the `shop`/`topic`/`webhook_id` headers: [3](#0-2) 

`Request#initialize` only checks that the required headers are *present*, not that they are bound to the signed payload: [4](#0-3) 

The identity binding the host application relies on is effectively:
`verified(hmac) == true` is meant to imply `shop == "the shop that legitimately sent this payload"`.
In reality the equality that actually holds is only:
`HMAC(raw_body, client_secret) == received_hmac`,
which is independent of the `shop-domain` header value. Because the same app `client_secret` signs webhooks for *every* shop that installs the app, any shop owner who legitimately installs the app receives real webhooks with a valid HMAC over a body they fully control the shape of (for topics they can trigger, e.g. `orders/create`, `app/uninstalled`, etc.). That legitimate (body, hmac) pair can be resent to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop, and this library will validate it as authentic because the header is outside the signed scope.

### Impact Explanation
This breaks tenant isolation: an attacker who merely installs the target app on their own store (no `api_secret_key`, no access token, no privileged account needed) can forge webhook events that the host application will attribute to any other shop that uses the app. Depending on what the host app does with webhook data (e.g. updating billing state, order records, product data, or triggering `app/uninstalled` cleanup) keyed by `shop`, this enables cross-tenant data corruption/spoofing — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high: the only prerequisite is installing the app on any shop (available to any internet user with a Shopify account) and capturing one legitimate webhook delivery, which is standard developer capability for any app installer. No credential theft, TLS interception, or social engineering is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived tenant identity to the signed payload before trusting it — e.g., include the shop domain header in `to_signable_string`, or require host applications to look up the shop by the accompanying access-token/session rather than trusting the unauthenticated header outright.

### Proof of Concept
1. Attacker signs up for a Shopify dev store `attacker-shop.myshopify.com` and installs the vulnerable app (legitimate installation, no elevated privileges).
2. Attacker triggers a webhook topic they control the payload shape for (e.g. modifies an order) and captures the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because Shopify signed it with the app's shared `client_secret`.
3. Attacker resends this exact body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Utils::HmacValidator.validate` returns `true` because it only checks the raw body against the shared secret — never the `shop-domain` header. [5](#0-4) 
5. The host application processes the forged webhook as if it originated from `victim-shop.myshopify.com`.

module ShopifyAPI

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
