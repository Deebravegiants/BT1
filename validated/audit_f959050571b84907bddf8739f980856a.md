### Title
Unused native ETH from `dispatch()`/`fundRequest()` swap is trapped in `EvmHost` instead of being refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and swap it for the exact `feeToken` amount needed using `IUniswapV2Router02.swapETHForExactTokens`. Any leftover ETH from that swap is refunded by the router to its immediate caller — which is `EvmHost` itself, not the original transaction sender (`_msgSender()`). The excess ETH is thus stranded in the `EvmHost` contract balance rather than being swept back to the user who overpaid, exactly the bug class described in the referenced Napier report.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

Each of these functions is `payable` and forwards the entire `msg.value` to `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The canonical `UniswapV2Router02.swapETHForExactTokens` implementation computes the exact input required (`amounts[0]`) and, when `msg.value > amounts[0]`, refunds the dust via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Because `EvmHost` is the caller of the router (not the original user), that dust refund lands on `address(EvmHost)`, not on `_msgSender()` (the account that actually funded the transaction and is entitled to the leftover ETH).

None of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` contain any subsequent logic to forward the refunded dust back to `_msgSender()`. No sweep-back call, no `_sendValue`-style refund pattern exists here, unlike the pattern deliberately implemented and tested elsewhere in this same codebase for native-ETH overpayment (e.g. `IntentGatewayV2`/`ExtrinsicIntents`/`IntrinsicIntents`, which explicitly do `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }`).

Docs corroborate that `msg.value` is expected to cover the fee via a swap with no user-facing refund path described: [4](#0-3) 

Because `feeToken()` price and Uniswap slippage are subject to change between quote time and execution time, any caller who sends a safety buffer above the minimum required ETH (a common practice to avoid `EXCESSIVE_INPUT_AMOUNT`-style reverts) will permanently lose that buffer — it accumulates as ETH balance inside `EvmHost` with no code path that returns it to them.

### Impact Explanation
This directly causes loss of user/relayer/app funds on every native-ETH-funded dispatch (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`) or fee top-up (`fundRequest`) where the sender does not send the *exact* minimal ETH amount. Since `EvmHost.dispatch` is the core, unprivileged, permissionless message-dispatch entry point used by every app on Hyperbridge (including `HyperFungibleToken.send`, `HyperbridgeLzEndpoint.send`, and any third-party `IApp` integrator that pays with native token), this is reachable from a single ordinary user transaction with no special privileges required. The stranded ETH is not merely temporarily locked — with no owner/admin withdraw path identified for arbitrary native-ETH dust in `EvmHost.sol` within the code reviewed, the funds are effectively permanently unrecoverable by the paying party, meeting the "permanent freezing/loss of funds" bar.

### Likelihood Explanation
High likelihood: this triggers on ordinary usage whenever a caller supplies `msg.value` larger than the exact quote (which is a normal defensive practice against price movement/slippage between off-chain quoting and on-chain execution, especially since no `quote()` view helper exists on `EvmHost` for `DispatchGet`/`fundRequest` to compute the precise amount beforehand). No attacker action or malicious actor is required — it is a systemic side effect of the fee-swap design on every native-ETH funded dispatch.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, check `address(this).balance` (or track the ETH balance delta) and if any residual amount remains beyond what the function held before the swap, refund it to `_msgSender()` via a low-level call, mirroring the pattern already used in `IntentGatewayV2`/`intentsv2` contracts (`_sendValue(msg.sender, remainder)`).

### Proof of Concept
1. Governance configures `feeToken()` and `_hostParams.uniswapV2` on `EvmHost`.
2. A user calls `EvmHost.dispatch{value: 10 ether}(DispatchPost{... fee: X ...})` where the actual ETH needed to acquire `X` feeToken via `swapETHForExactTokens` is only 9 ether (buffer sent to cover slippage/price movement).
3. Uniswap's `swapETHForExactTokens` spends 9 ether and refunds 1 ether dust to `msg.sender`, which is `EvmHost`, incrementing `address(EvmHost).balance` by 1 ether.
4. `dispatch()` returns normally; the user has permanently lost the 1 ether — it is not tracked as owed to them and no function in `EvmHost.sol` returns arbitrary native ETH balance to callers.
5. Repeat across many callers: `EvmHost`'s native balance from unrefunded dust accumulates indefinitely, unclaimed by the users who paid it, with no observed path (in the code inspected) to recover it back to those specific payers.
