### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `topic`, `shop`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the HMAC computation. `Registry.process` trusts these header-derived values to dispatch the payload to app handlers, so an attacker who can obtain one genuinely HMAC-signed webhook body (by installing the target app on their own, attacker-owned development store) can replay that exact body to the app's webhook endpoint with forged `shop-domain`/`topic`/`webhook-id` headers and have it pass validation.

### Finding Description
The HMAC binding this gem is supposed to enforce is:
`HMAC(body, client_secret) == received_hmac` should imply `(topic, shop, body)` is authentic and untampered.

In reality:
- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `topic`, `shop`, `webhook_id`, and `api_version` are parsed straight from headers with no cryptographic binding to the signed body: [2](#0-1) 
- `HmacValidator.validate` only checks the `hmac` field against `to_signable_string` (i.e., the body), and `Registry.process` uses the header-derived `topic`/`shop` to route and construct `WebhookMetadata` passed to the app's handler: [3](#0-2) 
- `HmacValidator.validate_signature` computes the signature purely over `verifiable_query.to_signable_string` (the body, in the webhook case) and secure-compares it to the received HMAC — it never incorporates the headers: [4](#0-3) 

So the equality the gem actually verifies is `HMAC(body) == received_hmac`, but the identity fields the application acts on (`shop`, `topic`, `webhook_id`) are unauthenticated. Because Shopify signs webhooks for every shop that installs the app using the same per-app `client_secret`, any attacker who installs the target app on a store they control (an "unprivileged internet user" action — no special access needed) will receive genuinely-signed webhook deliveries for that store. The attacker can then capture one such `(raw_body, hmac)` pair and POST it directly to the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop and/or a forged `shopify-topic` header, and `Registry.process` will accept it as valid and dispatch it to the handler as if it originated from the victim shop/topic.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC signature is meant to provide (Critical - cross-tenant access). A host application that relies on `WebhookMetadata#shop`/`#topic` (as intended and documented by this gem) to determine which merchant/tenant an event pertains to can be made to process attacker-controlled events "as" another tenant — e.g. spoofing `app/uninstalled`, `customers/redact`, order or fulfillment events, etc., attributed to a shop the attacker does not control. This can lead to unauthorized data mutation, denial of legitimate shop functionality, or leakage/misattribution of tenant data depending on how the host app's handlers use the `shop` value.

### Likelihood Explanation
Reasonably likely: it requires only that the attacker be able to install the target app once on a store they control (a normal, unprivileged Shopify merchant action for any public/installable app) to obtain a validly-signed `(body, hmac)` pair, then replay it with rewritten headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them (e.g., verify them against a value independently looked up via a trusted API call, not solely from the request headers) so that a signature computed for one shop/topic/body combination cannot be replayed for another.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook with a real body `B` and header `shopify-hmac-sha256: HMAC(B, client_secret)`.
3. Attacker resends the same raw body `B` and HMAC value to the app's webhook endpoint, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: app/uninstalled` (or any other registered topic)
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `HMAC(B, secret)`, which is unchanged: [5](#0-4) 
5. `Registry.process` dispatches to the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen `topic`, even though the request never actually originated from Shopify regarding that shop or topic.
