### Title
Webhook `shop` identity header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-verifying the raw request body, then hands the caller a `shop` identity value that is read from an unsigned HTTP header. Because Shopify apps use one shared `api_secret_key` across every shop that installs them, any shop that has installed the app can capture a legitimate, validly-signed webhook body from its own store and replay it to the app's webhook endpoint with a forged `shop-domain` header, causing the app to process attacker-controlled data under a victim shop's identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` verifies only that the HMAC over the body matches, then forwards the header-derived `shop` value to the app's handler as trusted tenant context: [3](#0-2) 

`Utils::HmacValidator.validate`/`validate_signature` confirm this: the signature is computed only over `verifiable_query.to_signable_string` (the body), never over any header: [4](#0-3) 

The equality this breaks is: `hmac == HMAC(api_secret_key, raw_body)` is verified, but the tenant claim actually consumed downstream is `request.shop` (an unsigned header) — i.e., `signed(raw_body) != signed(shop)`. Because the `api_secret_key` used for HMAC is the app's single client secret shared across all shop installations (not a per-shop key), any shop that has installed the app already possesses a data source of validly-signed `(body, hmac)` pairs. Such an attacker can:
1. Trigger a real webhook from their own shop to capture a body + valid `X-Shopify-Hmac-Sha256` value.
2. Replay that exact body/HMAC to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim shop's domain.
3. `HmacValidator.validate` passes because the body is unchanged and the secret is the same for every shop.
4. `Registry.process` invokes the handler with `shop: <victim-shop>`, `body: <attacker-controlled>`, tricking the host application into acting on attacker data as if it came from the victim tenant.

### Impact Explanation
This breaks the cross-tenant isolation the HMAC is meant to guarantee: it lets an unprivileged installer of the app forge webhook events that appear to originate from any other shop that uses the app, since the identity field consumed by application logic (`shop`) is outside the authenticated payload. Depending on what the host app does with `WebhookMetadata#shop` (e.g., looking up/mutating that shop's stored session, order data, or triggering shop-scoped side effects), this constitutes cross-tenant access/data confusion — rated Critical per the given impact classes.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own (attacker-controlled) shop — a normal, unprivileged action available to any Shopify merchant/developer — and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed; the attacker only reuses HMAC values the app itself legitimately produced for their own shop's webhooks.

### Recommendation
Bind the tenant identity to the authenticated payload instead of trusting unsigned headers:
- Include `shop`, `topic`, and `webhook_id` in the signable string used for HMAC verification (mirroring `AuthQuery#to_signable_string`), or
- Cross-check the header-derived `shop` against Shopify's own webhook `X-Shopify-*` claims through a channel Shopify signs (e.g. verify the header set is consistent and reject requests where the signed payload doesn't reference the same shop), or at minimum document/require host apps to independently verify that the `shop` header corresponds to a shop actually subscribed to that specific webhook (e.g., by tracking webhook IDs per shop) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Install the target app (any Shopify plan permits a free/dev install) on `attacker-shop.myshopify.com`.
2. Trigger any webhook (e.g. `orders/create`) from `attacker-shop` and capture the raw request: headers `X-Shopify-Hmac-Sha256: <H>`, `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and raw JSON body `B`.
3. Replay the exact same body `B` and `X-Shopify-Hmac-Sha256: <H>` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds (HMAC over `B` matches, same shared `api_secret_key`), and `Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though the request never originated from `victim-shop`.

          received_signature = verifiable_query.hmac
