### Title
User QR-code parser accepts truncated (non-canonical) UUIDs as `user_id`, enabling collision-based signup misattribution - ([File: src/plans/qr_scan/user.rs])

### Summary
The `QR_CODE_V2` regex used to parse the user identifier from a scanned QR code accepts a truncated, 18-character partial UUID in addition to the full 36-character UUIDv4, and the parser stores whichever value was scanned verbatim into `Data::user_id`, which is subsequently used as the canonical user identity throughout the entire signup flow (backend validation, PCP upload, signup creation).

### Finding Description
`Data::user_id` is documented as "User ID in format of 128-bit UUIDv4" [1](#0-0)  but the `QR_CODE_V2` regex that parses it makes the last two UUID groups (`-XXXX-XXXXXXXXXXXX`, 72 of the 128 bits) entirely optional: [2](#0-1) 

This is confirmed by the repository's own test, which demonstrates that a QR code containing only the first three UUID groups (`3bcf883d-ce22-4a03`, an 18-character truncated identifier) is accepted and parsed into `user_id` unchanged, with no truncation warning, error, or fallback to reject/pad the value: [3](#0-2) 

There is no post-parse validation anywhere in `Data::from_v2`/`try_parse` that rejects a shortened `user_id` or enforces the full 128-bit UUID format before the value is used [4](#0-3) .

This same `user_id` field is then propagated, unvalidated, into every downstream identity-bearing operation of the signup pipeline:
- User/session validation against the backend, where `qr_code.user_id` is embedded directly into the request URL: [5](#0-4) 
- The signup-creation request, where it is submitted as the authoritative `userId` form field alongside biometric iris codes: [6](#0-5) 
- The personal-custody-package (biometric data) upload path, where the same truncated string is used as the `user_id`/`session_id` tag for the uploaded encrypted iris package: [7](#0-6)  and [8](#0-7) 

Because a full UUIDv4 has 122 random bits while the truncated form retains only roughly the first 60 bits (8+4+4 hex groups), many distinct full UUIDs share the same truncated prefix. Since the parser never distinguishes "truncated" vs "full" `user_id`s and never re-validates length before use, a truncated identifier can be accepted end-to-end as if it were a unique, canonical user identity for validation, iris-code submission, and encrypted biometric-package upload.

### Impact Explanation
This mirrors the wallet bug class described in the report: a system accepts a variable/reduced-length identifier and treats it as fully authoritative downstream, causing the difference between the "confirmed" length and the "actually required" length to become a source of real-world data loss or misattribution. Here, the consequence is a truncated `user_id` (only a prefix of the full UUID) being used as the durable identity key for backend session validation, signup creation, and personal-custody-package biometric uploads. Because many possible full UUIDs collapse to the same truncated prefix, this allows signup state (and associated encrypted biometric packages) to be uploaded, validated, or referenced under an identifier that does not uniquely and durably map back to a single user — a cross-signup identity/state confusion class issue in the same family as the reported bug.

### Likelihood Explanation
Any generation of a v2-format user QR code with fewer than the full five UUID groups (whether from a compromised/buggy client, a modified partner integration, or a malformed operator/user tool) will be silently accepted by `try_parse`/`QR_CODE_V2` without any warning or rejection, since the shortened form is explicitly supported by the regex and exercised by the codebase's own passing test (`test_v2_shortened`). No special privileges are required — this is reachable purely from the content of a scanned user QR code during the normal, unprivileged signup flow.

### Recommendation
Short term: reject any `user_id` that does not match the full canonical 36-character UUIDv4 format at parse time in `Data::try_parse`/`Data::from_v2` (i.e., make the optional group in `QR_CODE_V2` mandatory, or add an explicit length/format check after regex capture) rather than accepting the shortened alternate form. Long term, if a shortened identifier format is intentionally supported for legacy/compat reasons, ensure it's mapped to a fully-resolved canonical UUID by the backend before it is used as an identity key in `signup_post::request`, `user_status`, or `upload_personal_custody_package::request`, so that no truncated value is ever propagated as the authoritative user identity for biometric data handling.

### Proof of Concept
1. Construct a user QR code string `userid:3bcf883d-ce22-4a03:1` (a truncated 18-character UUID prefix instead of the full 36-character UUIDv4).
2. Call `qr_scan::user::Data::try_parse` on this string; per `QR_CODE_V2` and the existing `test_v2_shortened` unit test, this succeeds and yields `Data { user_id: "3bcf883d-ce22-4a03", .. }` [3](#0-2) .
3. This `Data` instance flows unmodified into `verify_user_qr_code` → `backend::user_status::request`/`do_request`, `signup_post::request`, and eventually `upload_pcp_tier_0` → `backend::upload_personal_custody_package::request`, each of which embeds the truncated `user_id` directly into backend requests and biometric package metadata [9](#0-8) [10](#0-9) .

    fn try_parse(code: &str) -> Option<Self> {
        if let Ok((user_id, user_data_hash)) = decode_qr(code) {
            return Some(Self {
                user_id: user_id.hyphenated().to_string(),
                signup_extension: false,
                signup_extension_config: None,
                user_data_hash: Some(user_data_hash),
            });
        }
        if let Some(captures) = QR_CODE_V2.captures(code) {
            return Some(Data::from_v2(&captures));
        }
        #[cfg(feature = "internal-data-acquisition")]
        if let Some(captures) = QR_CODE_SIGNUP_EXTENSION.captures(code) {
            return Some(Data::from_signup_extension(&captures));
        }
        None
    }
}
