Found it: `Webhooks::Request#shop` reads the value straight from the `x-shopify-shop-domain` HTTP header, but the HMAC verification (`to_signable_string`) only signs the **raw body**, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. The gem's own `Registry.process` uses this unauthenticated `shop` value to build the `WebhookMetadata` handed to the app's handler.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are trusted without HMAC coverage, allowing cross-tenant data injection into webhook handlers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` only proves that the *body bytes* were signed with the app's secret [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from HTTP headers that are never part of the signed payload [3](#0-2) . `Registry.process` validates only the body-based HMAC and then trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's registered handler [4](#0-3) .

### Finding Description
The identity binding that should hold is: `shop header verified == shop header the handler acts on`. In reality, HMAC verification only binds `body == HMAC(body, secret)`; it says nothing about which shop, topic, or webhook id the body is attributed to. Since Shopify computes the HMAC only over the raw JSON body (a documented, low-entropy/predictable structure for many topics, e.g. `{"id":123}`), and the header values are copied verbatim into the trusted `WebhookMetadata` without any cryptographic tie to the body, an unprivileged internet user who can reach the app's webhook endpoint (which by design is a public, unauthenticated HTTP endpoint) can request the app's public webhook signature validate a body they crafted for shop A, then replay that exact body+HMAC pair while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers to point at shop B (or a topic the attacker doesn't own). Because `hmac == HMAC(body)` alone is checked, and the body can be reproduced for common resource states, the gem cannot distinguish "shop A's webhook" from "attacker replaying shop A's known body claiming to be shop B."

This is the closest in-scope analog to the reported bug class: a field (`shop-domain`/`topic`/`webhook_id`) is acted upon by application logic (`Registry.process`, `WebhookMetadata`) but is not covered by the same integrity check (`HmacValidator`) that is presented as the authorization gate for the whole request.

### Impact Explanation
If a host app's webhook handler uses `data.shop` to decide which merchant record to update (the documented and intended usage per `WebhookMetadata`), an attacker who obtains any valid `(body, hmac)` pair for one shop (e.g., their own installed test shop) can forge requests attributing that body to a different `shop` domain string, since `shop-domain` is not part of the signed content. This lets an unprivileged caller inject data cross-tenant into another merchant's records inside the host application without needing any of the app's credentials — matching the "cross-tenant access" Critical impact category, contingent on the host app's handler trusting `data.shop`/`data.topic` as Shopify has cryptographically guaranteed (which the gem's public docs and structure both encourage).

### Likelihood Explanation
The webhook endpoint is by necessity internet-reachable and unauthenticated (that's the entire point of `Registry.process`/HMAC validation existing). No secrets, tokens or elevated access are required — only the ability to send an HTTP POST with attacker-chosen headers and a body that matches a `(body, hmac)` pair previously observed (trivial for topics with small/predictable bodies, or trivially available if the attacker installs the app themselves and captures a real webhook for their own shop, then reuses the exact bytes against a spoofed `shop-domain` header).

### Recommendation
Include `shop-domain`, `topic`, and `webhook_id` (and `api_version`) in the signed material checked by `HmacValidator`, or otherwise cryptographically bind them to the body before trusting them in `WebhookMetadata`. At minimum, `to_signable_string` should incorporate the shop domain so that `Utils::HmacValidator.validate` fails if the body was signed for one shop but the header claims another.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and lets it receive a legitimate webhook for a topic with a small, guessable body, e.g. `orders/create` with body `{"id":1}`; they capture the header `x-shopify-hmac-sha256: <H>` that Shopify computed over that exact body with the app's real secret (attacker doesn't need the secret itself — Shopify sends it to them because it's their own installed shop).
2. Attacker crafts a new POST to the app's public webhook endpoint reusing the same raw body `{"id":1}` and the same `x-shopify-hmac-sha256: <H>` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-webhook-id`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) ; this only recomputes `HMAC(raw_body, secret)` and compares to `<H>`, which still matches because the body is unchanged.
4. `Registry.process` proceeds to call the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [6](#0-5) , where `shop` is now `victim-shop.myshopify.com` even though the HMAC never certified that association — the handler processes attacker-controlled data as if it originated from the victim shop.
