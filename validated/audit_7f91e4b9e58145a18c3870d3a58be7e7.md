### Title
Oversized cross-chain amount causes `on_accept` mint to fail in `pallet-hyper-fungible-token`, permanently stranding tokens already burned on the EVM side - (File: `modules/pallets/hyper-fungible-token/src/module.rs`, `modules/pallets/hyper-fungible-token/src/impls.rs`, `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` on the EVM side unconditionally burns the caller's tokens **before** dispatching the ISMP message [1](#0-0) . On the Substrate destination, `pallet-hyper-fungible-token::on_accept` converts the raw `uint256` ERC-20 amount into the local `Balance` type via `convert_to_balance`, which divides the `U256` and then parses the resulting decimal string with `FromStr` [2](#0-1) . If the scaled value exceeds what the target `Balance` type (`u128`) can represent, `.parse::<B>()` returns an `Err`, and `on_accept` propagates that as `HftError::InvalidAmountConversion`, aborting the mint [3](#0-2) . This mirrors the H-10 pattern: a user-controlled `uint256` amount is downcast/converted into a narrower fixed-width type on the critical path, and the conversion failure permanently blocks the operation that would otherwise release/credit the corresponding value — except here the asset side that already gave up value (the EVM burn) has no guaranteed recovery path tied to this specific failure.

### Finding Description
- The EVM `HyperFungibleToken.send()` burns `params.amount` (a full `uint256`) from the sender immediately, then builds and dispatches the ISMP `DispatchPost` [4](#0-3) .
- On the Substrate side, `Pallet::on_accept` decodes the ABI `Message`, looks up decimals, and calls `convert_to_balance::<Balance>(U256, erc_decimals, decimals)` to scale and cast the amount down to the local `Balance` (`u128`) type [5](#0-4) .
- `convert_to_balance` divides the `U256` by the decimal-scaling factor and then does a string-based `parse::<B>()` [6](#0-5) . Any scaled value greater than `u128::MAX` (~3.4×10^38) fails to parse and returns `Err`, which is mapped to an application error and returned from `on_accept`.
- Unlike Astaria's `LienToken`, where the same value simply can't ever succeed once cast too large (permanently locking the specific position's collateral), here the burn on the EVM side has already occurred as an independent, irreversible action prior to the destination-side conversion failing. Whether the burned funds can ever be recovered depends entirely on whether a `timeout` was set and whether ISMP's handling of an `on_accept` error is later exposed to a timeout-driven refund path (`onPostRequestTimeout`, which re-mints the sender's tokens [7](#0-6) ). If `params.timeout` is `0` (as is explicitly done elsewhere in this codebase for "non-timeouting" dispatches, e.g. `BandwidthManager.purchase()` [8](#0-7) ), or if the message is treated by `pallet-ismp` as "delivered" despite the module-level conversion error, there is no path back to the sender, and the burned tokens are permanently lost.

### Impact Explanation
If reachable, this would result in permanent loss of user funds on the source chain with no compensating mint on the destination chain — a direct freezing-of-funds condition, matching the "permanent freezing of funds" acceptance criterion. The severity depends on whether the specific overflow amount is realistically reachable (very large token supplies/amounts, or decimal-scaling configurations that shrink the effective headroom below `u128::MAX`), and on ISMP's exact semantics for module-level `on_accept` errors (retry vs. permanent-delivered-but-failed), which I was not able to fully verify with the remaining budget.

### Likelihood Explanation
Low-to-moderate. Reaching a scaled amount that overflows `u128` requires either an extremely large `uint256` transfer amount or unusual decimal configurations (`Precisions` storage) that reduce the effective scale-down factor. This is far less likely than the original Astaria case, where a strategist directly and cheaply sets `liquidationInitialAsk` above `2**88`. Here it requires either a misconfigured `Precisions` entry or an attacker/large-supply token pushing amounts near `u128::MAX` scaled equivalents.

### Recommendation
- Validate `message.amount` against a safe upper bound on the EVM side (`HyperFungibleToken.send()`/`onAccept`) before dispatch, rejecting amounts that cannot be represented in the destination chain's local `Balance` type.
- On the Substrate side, avoid string-based `FromStr` conversion for balance scaling; use checked arithmetic (`TryFrom<U256>` with explicit bounds checks) and reject the message with a clear, documented failure mode.
- Confirm and, if necessary, harden the ISMP failure/timeout semantics so that any module-level `on_accept` error is guaranteed to eventually be recoverable by the sender (e.g., only allow non-zero timeouts for `HyperFungibleToken.send()`, or ensure `on_accept` failures are treated identically to non-delivery for timeout purposes).

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to tool-budget constraints):
1. Register a `HyperFungibleToken` pair with `erc_decimals` and local `decimals` configured such that `erc_decimals - decimals` is small (e.g., both 18), so scaling barely reduces magnitude.
2. Call `send()` on the EVM side with `amount` close to `type(uint256).max`, or with a token whose supply legitimately approaches `u128::MAX` scaled equivalent. EVM tokens are burned immediately.
3. The relayer delivers the message to the Substrate destination; `on_accept` calls `convert_to_balance`, which fails to `parse::<u128>()` the oversized value, returning `HftError::InvalidAmountConversion` and aborting the mint [9](#0-8) .
4. If `params.timeout` was `0` or the delivery is otherwise recorded as processed despite the module error, the sender's burned tokens are unrecoverable.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
