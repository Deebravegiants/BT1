### Title
Unrestricted arbitrary call in Emporium ops lets any caller drain untracked token balances stranded in the shared action contract - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only reconciles balances for the tokens the *caller themselves* lists in `circomData.erc20TokenAddresses`. Because the "stateless" operation branch allows an arbitrary `op.endpoint.call(op.callData)` with only two forbidden selectors, any unprivileged user can craft an `EmporiumOperation` that directly calls `transfer()` on any ERC20 the singleton `EmporiumUpgradeable` contract happens to hold (e.g. leftover from a router refund in a prior, unrelated transaction) and simply omit that token from `erc20TokenAddresses`, so neither the Emporium loop nor `Hinkal.transact`'s balance-diff check ever inspects it.

### Finding Description
The claimed invariant is: *tokens leaving an action in a tx == `-deltaAmountChanges` Hinkal sent it that tx*. This is enforced only per-index over `circomData.erc20TokenAddresses`: [1](#0-0) 

and mirrored at the top level in `Hinkal.transact`, again only over `circomData.erc20TokenAddresses`: [2](#0-1) 

Both loops are entirely blind to any token address that the attacker does not choose to include in `erc20TokenAddresses` — a field the attacker fully controls and which only has to match `dimensions.tokenNumber` in length via `dimensionsCheck` (no constraint on *which* addresses are listed): [3](#0-2) 

Meanwhile, the stateless operation branch executes a fully attacker-controlled arbitrary call from the Emporium contract itself, blocking only the two `IHinkalWallet` selectors: [4](#0-3) 

Since `EmporiumUpgradeable` is a single persistent, upgradeable proxy shared by all users (not an ephemeral per-tx contract), any ERC20 balance it happens to hold between transactions — for example a router refund of an intermediate/unswept token from a prior legitimate swap that wasn't anticipated in that transaction's `erc20TokenAddresses` — remains sitting on the contract. An attacker's transaction can then:
1. Submit `erc20TokenAddresses` that omits the stranded token entirely (it only needs to include whatever tokens the attacker's own genuine deposit/output uses to satisfy `dimensionsCheck` and the Hinkal balance-diff equation).
2. Include one `EmporiumOperation` with `invokeWallet=false`, `endpoint = strandedToken`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount)`.
3. Since `strandedToken` is not in `erc20TokenAddresses`, neither `EmporiumUpgradeable.runAction`'s balance loop nor `Hinkal.transact`'s balance-diff loop ever computes a `balanceChange`/`balanceDif` for it, so `BalanceChangeShouldBePositive()` never triggers and the slippage/balance-equality `require`s in `Hinkal.transact` are never evaluated for that token.
4. The `calldataHash`/proof only bind the transaction to whatever ops the attacker itself chose when generating their own proof (`getHashedCalldata` / `getSignedMessageHash`), which does not restrict the semantic content of `op.endpoint`/`op.callData` — the attacker is the prover, so they can freely encode this malicious op: [5](#0-4) 

Consequently, funds parked in the action outside the current transaction's declared token set can be pulled straight to the attacker's EOA with zero on-chain accounting, breaking the stated equality between funds leaving the action and `-deltaAmountChanges` sent to it.

### Impact Explanation
Any ERC20 balance resting in the shared `EmporiumUpgradeable` contract that is not part of a given transaction's `erc20TokenAddresses` — including router refunds/dust from earlier legitimate user swaps, or any token accidentally/temporarily held by the contract — can be stolen outright by any unprivileged caller who notices it, with no corresponding debit anywhere in the protocol's balance/UTXO accounting. This is a direct theft of protocol/in-flight user funds (Critical), and is repeatable every time residual balance accumulates on the contract.

### Likelihood Explanation
No special privileges are required — only the ability to submit a normal `Hinkal.transact` call with a self-generated valid proof over the attacker's own nullifiers/UTXOs and an `EmporiumStack` with a crafted stateless `op`. The only precondition is that `EmporiumUpgradeable` currently holds a non-declared token balance (a realistic and recurring situation given arbitrary router calls that can refund unswept amounts). Cost is a single transaction; the exploit is trivially repeatable whenever residual balance reappears.

### Recommendation
Do not allow arbitrary `op.endpoint`/`op.callData` combinations to move tokens off the Emporium contract without those tokens being captured by the balance-reconciliation loop. Either (a) restrict allowed endpoints/selectors to a vetted allowlist (e.g., approved routers only, and disallow direct token `transfer`/`transferFrom` calls to arbitrary recipients), or (b) require that every token address touched/approved during `ops` execution be included in `circomData.erc20TokenAddresses` and reconciled by the existing balance-diff/slippage checks, or (c) sweep/zero out the contract's balance for any token not listed before returning, reverting if a nonzero untracked balance is detected.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as allowed recipient), a mock ERC20 `TokenA`.
2. Simulate a "stranded" state: directly `TokenA.transfer(address(emporium), residualAmount)` (representing an unswept router refund left after a prior legitimate transaction) — do not register `TokenA` in any subsequent transaction's `erc20TokenAddresses`.
3. As attacker, build a `CircomData` for a legitimate small deposit/swap using an unrelated `TokenB` (real deposit, generated proof over attacker's own nullifiers), with `EmporiumStack.ops` containing one stateless op: `endpoint = address(TokenA)`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualAmount)`.
4. Call `Hinkal.transact(...)`.
5. Assert: `TokenA.balanceOf(attacker)` increased by `residualAmount`, `TokenA.balanceOf(emporium)` decreased by `residualAmount`, while every `require` in `EmporiumUpgradeable.runAction` and `Hinkal.transact` passed (transaction did not revert) — demonstrating tokens left the action with no corresponding `-deltaAmountChanges` entry for `TokenA`, breaking the claimed equality.
