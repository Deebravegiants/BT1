### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed in `Registry.process` authenticates the request body but not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that are used to construct the `WebhookMetadata` passed to the app's handler. [3](#0-2)  These header values are trusted verbatim without being part of the signed payload. [4](#0-3) 

### Finding Description
Shopify computes a single shared HMAC using the app's `api_secret_key` over the raw JSON body only; this same secret is used for every shop installed on the app, so any body+HMAC pair that is valid for one shop (e.g., the attacker's own store, on which they can install their own app instance/webhook and legitimately receive a genuinely-signed webhook) is *also* a cryptographically valid body+HMAC pair regardless of which shop header accompanies it. `Utils::HmacValidator.validate` checks:

```
computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
OpenSSL.secure_compare(computed_signature, received_signature)
```

and `to_signable_string` for a webhook `Request` returns only `@raw_body`. [5](#0-4) [6](#0-5) 

The binding that should hold is:
`HMAC(secret, raw_body) valid` ⇒ `(raw_body, shop, topic, webhook_id)` all originated together from Shopify for that specific shop.

What the code actually verifies is only `HMAC(secret, raw_body) valid`, and `shop`, `topic`, and `webhook_id` are read independently from headers with no cryptographic tie to the body. `Registry.process` then forwards `request.shop` directly into `WebhookMetadata` handed to the app's business logic. [4](#0-3) 

An attacker who is an unprivileged internet user with respect to any *other* tenant, but who legitimately controls their own Shopify store on the same app installation, can capture one genuine `(raw_body, hmac)` pair emitted by Shopify for their own shop, then POST it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `Utils::HmacValidator.validate` still passes because it only checks the body signature, and the handler executes believing the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant identity binding between an authenticated payload and the shop it is attributed to, i.e., cross-tenant access/confusion: application logic keyed off `WebhookMetadata#shop` (e.g., updating shop-scoped state, triggering shop-scoped side effects, writing to a per-shop data store, or de-duplicating/authorizing by shop) can be made to run under an arbitrary victim shop's identity using data whose HMAC was never actually validated for that shop. This matches the report's core pattern: an identity/authorization check that answers based on data disjoint from what was actually cryptographically verified.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a legitimate merchant with a store using the same app (unprivileged relative to other tenants, no special credentials needed), (2) the ability to receive one genuine webhook for their own store (trivial — triggering any registered event), and (3) sending a raw HTTP POST with modified headers to the public webhook endpoint, since headers are attacker-controlled while the body/HMAC pair is simply replayed. No access token, `api_secret_key`, or TLS interception is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed material verified against the HMAC (mirroring how `AuthQuery#to_signable_string` binds `shop`/`host`/`state` into the OAuth HMAC check), or otherwise cryptographically bind these header values to the body before trusting them in `Registry.process`, so that `to_signable_string` cannot be satisfied by replaying a body/HMAC pair captured for a different shop.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Attacker triggers the event and captures the genuine request Shopify sends: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid since `HMAC(secret, B) == H`), along with `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker sends a new POST to the app's public webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a different `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` in `Registry.process` succeeds because `to_signable_string` only checks `B` against `H`. [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, causing the app to process attacker-supplied data as if it belonged to the victim shop. [8](#0-7)
