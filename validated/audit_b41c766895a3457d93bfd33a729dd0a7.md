Based on my review of the in-scope auth and webhooks code, I found a genuine identity-binding gap matching the reported bug class (a field that is *acted upon* but not *covered* by the cryptographic check).### Title
Webhook shop-tenant identity spoofing via HMAC that only covers the raw body, not the shop-domain header - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook using only `Utils::HmacValidator.validate(request)`, and that validator signs/verifies exclusively `Request#to_signable_string`, which returns the raw HTTP body. The `shop` value that is subsequently trusted and handed to the app's `WebhookHandler` is read from the `X-Shopify-Shop-Domain` header, a field that is never included in the signed content. This mirrors the report's bug class: a field that is acted upon (used to identify the tenant) is not bound by the same integrity check that gates the action.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 
- `hmac` is read from the `hmac-sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop` (`shop-domain` header), `topic`, `webhook_id`, and `api_version` are all parsed from headers but are **not** part of `to_signable_string`.

`HmacValidator.validate` computes `HMAC-SHA256(client_secret, to_signable_string)` and compares it to the `hmac` value with `OpenSSL.secure_compare`: [2](#0-1) 

`Registry.process` uses only this check as its authentication gate, then forwards `request.shop` (an unauthenticated header) straight into `WebhookMetadata`, which the host app's handler is documented to use as the tenant identifier for routing/updating shop data: [3](#0-2) [4](#0-3) 

The documented usage pattern confirms `data.shop` is meant to identify which merchant the payload belongs to (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) 

Because the shop identity is not cryptographically bound to the body, `hmac_valid(body, shop=A) == hmac_valid(body, shop=B)` for the same body — the equality the check should enforce (`shop_header == shop_that_produced_body`) is never verified.

### Impact Explanation
An unprivileged internet user who legitimately owns any shop that has installed the app (or otherwise obtains one genuine `raw_body` + `hmac-sha256` pair produced by Shopify for the app's `client_secret`, e.g. from their own store's webhook traffic) can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header value pointing at a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop. If the host app (as documented) uses `data.shop` to select which tenant's database row to update, this results in cross-tenant data corruption/injection — attacker-controlled data being attributed to and applied against a shop the attacker does not control, without ever needing the app's `client_secret` or an access token. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (1) the attacker controls or has visibility into one shop that installed the target app (an ordinary merchant-level capability, not a privileged one), and (2) the app's webhook endpoint is reachable, which by design it is. No secret material, TLS interception, or social engineering is needed — only manipulation of an HTTP header on a replayed request, which is trivial for any unprivileged actor sending requests to the app's public webhook route.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed content check, or otherwise revalidate that the header-provided `shop` matches a shop known to have `webhook_id` this exact combination registered/expected, before trusting `request.shop`. At minimum, `Registry.process`/`WebhookMetadata` should not treat the `shop-domain` header as authenticated data derived from HMAC verification alone; the gem should document (or enforce) that host apps must cross-check `data.shop` against their own webhook registration records, or the gem should incorporate the shop/topic/webhook_id headers into the HMAC-covered signable string used for verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers an HTTP webhook (e.g. `orders/create`).
2. Shopify sends a legitimately signed webhook to the app for that shop:
```
POST /callback/orders/create
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid HMAC of raw_body with app's client_secret>
X-Shopify-Shop-Domain: attacker-shop.myshopify.com
X-Shopify-Webhook-Id: ...
{"id": 1, "note": "malicious content"}
```
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value (they can observe/log it themselves since it targets their own shop/endpoint).
4. Attacker resends the identical body and HMAC header to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation succeeds unchanged.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...attacker content...})` and, per the gem's documented usage pattern, performs actions (e.g., `perform_later(shop_domain: data.shop, ...)`) against the victim tenant using attacker-supplied data.
