### Title
Caller-chosen `side` tag reinterprets one untyped scaled amount as either market debt or market supply, letting any caller burn debt shares it does not own - ([File: contracts/pool/src/ops/seize.rs])

### Summary
`Pool::seize_positions` consumes `PoolSeizeEntry { hub_asset, side, position }`. The `position` field is an untyped `ScaledPositionRaw`; the caller-supplied `side: AccountPositionType` is the only thing that decides whether that number is treated as *debt shares to burn* (`Borrow`) or *supply shares to convert into protocol revenue* (`Deposit`). The pool keeps only market-level totals — it has no per-caller book — so it cannot verify that the caller actually holds the shares described by the entry. This is the same defect class as CVE-2026-29079: one untyped payload field reinterpreted through a confused constructor/tag, with the corrupted interpretation later driving value-bearing writes.

### Finding Description [1](#0-0) 
`apply()` syncs the market, then branches purely on `entry.side`:

- `Borrow`: `unscale_borrow_ceil_ray(position)` → `apply_bad_debt_to_supply_index` (socializes the amount onto all suppliers by writing down the supply index) → `cache.burn_debt(position)` (decrements the market's `borrowed` shares).
- `Deposit`: `cache.absorb_supply_as_revenue(position)` (moves scaled supply shares into `revenue`).

The only input validation is `require_nonneg_amount` on `scaled_amount`. Per INV-ACCT-10, "the pool stores market totals only ... the pool trusts it: it has no per-account book to check the value against" [2](#0-1) . In legitimate flows the controller constructs `PoolSeizeEntry` internally with the correct tag (`AccountPositionType::Deposit` for fee shares) [3](#0-2) , but the pool entrypoint itself accepts the tag from whoever calls it. The fuzz target exercises `try_seize_positions` with an arbitrary caller-chosen `side` and arbitrary `scaled_amount`, confirming the endpoint accepts both variants with externally supplied payloads [4](#0-3) .

A caller can therefore submit `PoolSeizeEntry { side: Borrow, position: ScaledPositionRaw { scaled_amount: X } }` where `X` is any value up to the market's `borrowed` total — including debt the caller never took out. The pool burns `X` debt shares and socializes the ceiled token value onto `supply_index`.

### Impact Explanation
Passing `side: Borrow` with a large `scaled_amount` erases market debt the attacker does not owe and writes the loss into the supply index: every supplier's shares are devalued pro rata (`apply_bad_debt_to_supply_index`), i.e. a direct, unprivileged theft/insolvency primitive against all suppliers of that `(hub, asset)` book. No deposit, collateral, or outstanding borrow of the attacker's is required — the pool never checks that the entry corresponds to a position the caller holds.

### Likelihood Explanation
Reachability depends on pool-level caller gating, which is the part I could not fully verify within the indexed code: no `require_auth` / operator check appears in `contracts/pool/src`, and the pool's own tests call `seize_positions` and `borrow` with generated addresses, suggesting callers act as independent spokes bearing their own books. If the pool relies on the caller honestly describing its own position, the confusion is directly exploitable: the `side` tag plus an untyped `scaled_amount` is precisely the "wrong constructor reinterpretation" of the reference bug, and both variants are reachable from a single externally supplied argument. If deployment instead restricts pool entrypoints to the controller contract, this collapses to a trust-boundary assumption rather than an exploitable path — that gate could not be confirmed or refuted from the indexed sources.

### Recommendation
Make the pool derive the interpretation from provable state rather than a caller tag: split `seize_positions` into two entrypoints (`seize_debt`, `seize_supply`) or bind the side to the key (e.g., `PoolKey::DebtSeize`/`SupplySeize`), and — more fundamentally — have the pool maintain per-spoke scaled share balances so a seize can be checked against the caller's own recorded position before mutating market totals. Absent per-caller books, restrict `seize_positions` to the registered controller/spoke address and document the trust boundary.

### Proof of Concept
1. Attacker (any unprivileged address) calls `Pool::seize_positions` on market `(hub_id, asset)` with:
   `PoolSeizeEntry { hub_asset, side: AccountPositionType::Borrow, position: ScaledPositionRaw { scaled_amount: D } }`, where `D` ≈ the market's `borrowed` total.
2. `apply()` takes the `Borrow` branch: `apply_bad_debt_to_supply_index` writes `D * borrow_index` (ceil) down onto `supply_index`, then `burn_debt(D)` reduces `borrowed`.
3. Result: all debt in the market is extinguished and supplier shares are devalued by the same amount — borrower obligations are erased at suppliers' expense, with no attacker position involved.

```rust
pub(crate) fn apply(env: &Env, entry: &PoolSeizeEntry) -> MarketStateSnapshot {
    require_nonneg_amount(env, entry.position.scaled_amount);
    let mut cache = ops::synced_market(env, &entry.hub_asset);
    let position = Ray::from(entry.position.scaled_amount);

    match entry.side {
        AccountPositionType::Borrow => {
            let bad_debt = cache.unscale_borrow_ceil_ray(position);
            interest::apply_bad_debt_to_supply_index(&mut cache, bad_debt);
            cache.burn_debt(position);
        }
        AccountPositionType::Deposit => {
            cache.absorb_supply_as_revenue(position);
        }
    }

    cache.commit()
}
```

```markdown
The pool stores market totals only. Every pool position call carries the
account's scaled position, and the pool trusts it: it has no per-account book to
check the value against. For each market, the sum of account supply shares
equals the pool's supplied shares minus its revenue shares, and the sum of
account debt shares equals the pool's borrowed shares.

The controller holds this by construction, not by a runtime assertion. It takes
each new scaled position from the pool's returned mutation, merges duplicate
legs by hub asset before it reads a position, and moves shares between two
accounts only in credit-mode liquidation, where the debit, the credit and the
fee are asserted to sum exactly. A controller path that writes a position from
any other source, or that sends a stale position to the pool, breaks this
invariant without a revert.
```
