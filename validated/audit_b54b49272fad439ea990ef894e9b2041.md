### Title
Integer-division truncation in relay-fee calculation lets a withdrawer's entire payout be captured as the relay fee - (File: contracts/Hinkal.sol)

### Summary
The relay-fee split used on every non-deposit (withdrawal) leg of `_internalTransact` divides by `10000` using Solidity integer division. For withdrawal amounts (`sumAbs`) that are small relative to the configured `variableRate`, `recipientAmount` truncates to `0`, so the withdrawer receives nothing while the relay receives the entire withdrawn amount. This mirrors the referenced Fractional `Migration.sol` bug class where a low denominator causes rounding to zero and total loss of the user's expected share, except here the "share" is the user's shielded withdrawal payout.

### Finding Description
In `Hinkal.sol`, when a token's `deltaAmountChange` is negative (a withdrawal) and a relay is present, the recipient's share is computed as: [1](#0-0) 

```
uint256 recipientAmount = ((10000 - variableRate) * (sumAbs - flatFee)) / 10000;
relayFee = sumAbs - recipientAmount;
```

Because this is a floored integer division, whenever `(10000 - variableRate) * (sumAbs - flatFee) < 10000`, `recipientAmount` rounds down to `0`. Consequently `relayFee = sumAbs`, and the subsequent transfer to the withdrawer: [2](#0-1) 

sends `sumAbs - relayFee == 0` to the intended recipient. The full withdrawn amount instead goes to `circomData.relay`. The same rounding pattern is duplicated in `RelayStore.calculateRelayFee` (used identically by `HinkalHelper`/Emporium/swap paths): [3](#0-2) 

The `require(sumAbs >= flatFee, ...)` check only guards against the flat fee exceeding the withdrawal; it does not protect against the variable-rate truncation zeroing out the recipient's share for small `sumAbs - flatFee` values. Because `variableRate` and `flatFee` are part of `circomData.feeStructure`, which is attacker/relay-supplied data authenticated only insofar as it is part of `signedMessageHash`/`calldataHash` (not bounded to a "safe" minimum withdrawal size), any withdrawal whose post-flat-fee remainder is small enough relative to `variableRate` triggers full-value capture by the relay, with no code path returning value to the user.

### Impact Explanation
This is a High-severity value-loss bug: an unprivileged user withdrawing a small amount (or a relay purposefully accepting/relaying dust-value withdrawals with a nonzero `variableRate`) causes the entire withdrawn amount to be redirected to `circomData.relay` instead of the withdrawer, with `hasPaidToRelay` set to `true` and the transaction succeeding normally. The value is not "burned" (it is fully accounted for in the on-chain balance transfer, `relayFee + recipientAmount == sumAbs`), so it is not a case of unbacked minting or a broken shielded-balance invariant, but it constitutes an unauthorized/unintended transfer of the user's withdrawal principal to a third party (the relay) purely due to rounding, matching "theft of protocol/relay-adjacent value" and "unauthorized asset movement" categories.

### Likelihood Explanation
The trigger condition depends only on the ratio of `variableRate` to `sumAbs - flatFee`, both of which are attacker/relay-influenced parameters within a normal (non-privileged) transaction flow. No admin/owner access, no proof forgery, and no compromise of cryptographic primitives is required — only choosing (or being routed through) a fee structure/withdrawal-size combination where `(10000 - variableRate) * (sumAbs - flatFee) < 10000`. This is realistically reachable whenever small withdrawals are combined with nonzero variable rates, which is a standard configuration, not an edge case requiring privileged setup.

### Recommendation
Enforce a minimum-viable withdrawal amount (or a minimum `sumAbs - flatFee`) before allowing the variable-rate split, e.g. `require(recipientAmount > 0, "withdrawal too small for fee structure")`, or switch to a rounding scheme that allocates the truncation remainder to the recipient rather than the relay (e.g., compute `relayFee = (variableRate * (sumAbs - flatFee)) / 10000` and derive `recipientAmount = sumAbs - flatFee - relayFee`, so any rounding dust stays with the user, not the relay). Apply the same fix in `RelayStore.calculateRelayFee` used across `HinkalHelper`, `ExternalActionSwap`, and `EmporiumUpgradeable`.

### Proof of Concept
1. A user submits a valid, proven withdrawal transaction through `Hinkal.transact` with `deltaAmountChange = -3` for a token (i.e., `sumAbs = 3`), `circomData.relay` set to a valid relay address, `feeStructure.flatFee = 0`, and `feeStructure.variableRate = 5000` (50 beeps... actually 5000/10000 = 50%, but any rate where `(10000-variableRate)*3 < 10000` works, e.g. `variableRate = 6700`).
2. In `_internalTransact` (`contracts/Hinkal.sol:188-223`): `flatFee = 0`; `recipientAmount = ((10000-6700) * 3) / 10000 = 9900/10000 = 0`; `relayFee = 3 - 0 = 3`.
3. `transferERC20TokenOrETH(token, relay, 3)` executes (all 3 units go to the relay).
4. `sumAbs - relayFee = 0`, so the branch that pays the intended recipient (`circomData.externalActionData.externalAddress`) is skipped entirely — the user receives nothing for their withdrawn shielded balance.
5. The transaction completes successfully (`hasPaidToRelay = true`), the nullifiers are consumed, and there is no path to recover the lost `3` units.
