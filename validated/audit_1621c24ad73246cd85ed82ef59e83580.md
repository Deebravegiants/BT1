### Title
Griefing attack permanently denies protocol PnL fee accrual via baseline reset on every Deposit/Withdraw - ([File: program/src/processor.rs])

### Summary
The pnl accounting baseline stored in `TargetOrders.calc_pnl_x`/`calc_pnl_y` is unconditionally rewritten on every `Deposit` and `Withdraw` call to reflect the *current* pool state, even when the corresponding `pc_pnl_amount`/`coin_pnl_amount` computed in `Processor::calc_take_pnl` rounds down to zero. Because `Deposit`/`Withdraw` are fully permissionless and can be invoked with minimal amounts, any unprivileged actor can repeatedly call them to keep resetting the baseline before the price drift accumulates enough to survive integer-division truncation, permanently preventing the protocol's owed pnl fees from ever being credited to `need_take_pnl_pc`/`need_take_pnl_coin`.

### Finding Description
`Processor::calc_take_pnl` computes the pnl split for the protocol using the current pool reserves (`x1`, `y1`) versus the previous baseline (`target.calc_pnl_x`, `target.calc_pnl_y`): [1](#0-0) 

The `diff_x`/`diff_y` (price drift since the last checkpoint) is converted through `pnl_numerator`/`pnl_denominator` with integer division, and if the resulting `pc_pnl_amount` or `coin_pnl_amount` is `0`, `delta_x`/`delta_y` are simply reset to `0` — no pnl is credited to `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin`, and `total_pc_without_take_pnl`/`total_coin_without_take_pnl` are left untouched [2](#0-1) .

Critically, regardless of whether `delta_x`/`delta_y` ended up zero, the caller of `calc_take_pnl` (both `process_deposit` and `process_withdraw`) unconditionally rewrites the baseline `target_orders.calc_pnl_x`/`calc_pnl_y` to the post-transaction pool state: [3](#0-2) 

The same pattern (baseline reset from `x1`/`y1` minus `delta_x`/`delta_y`) recurs on withdraw at [4](#0-3) .

`Deposit` and `Withdraw` are permissionless instructions reachable by any signer with the minimum token amounts needed to mint/burn at least `1` lp unit [5](#0-4) . Because the baseline is reset to the *current* pool state on every call (`x1`/`y1` at call time), any residual price drift below the rounding threshold that would otherwise accumulate across multiple swaps is discarded rather than carried forward. An attacker can front-run or interleave minimal deposit/withdraw transactions after every swap (or periodically) to repeatedly re-baseline `calc_pnl_x`/`calc_pnl_y` to the current reserves before the accumulated drift crosses the threshold needed to produce a non-zero `pc_pnl_amount`/`coin_pnl_amount`. This is structurally identical to the Resolv `ResolvStakingCheckpoints.checkpoint()` griefing pattern: a permissionless caller repeatedly forces a checkpoint/baseline update that truncates the claimable delta to zero while advancing the stored baseline, permanently forfeiting the accrued amount.

### Impact Explanation
The protocol's swap-fee-derived pnl (owed to `AmmConfig.pnl_owner`, collectible via `WithdrawPnl`) never accrues into `need_take_pnl_pc`/`need_take_pnl_coin`, because the baseline is perpetually kept in sync with the live pool state by trivial, cheap, permissionless calls. This is a permanent freezing/denial of the protocol's rightful fee revenue with no way to recover the lost increments once the baseline has been overwritten — the drift is not stored anywhere else and is discarded each time `calc_take_pnl` computes a zero delta. This matches the "permanent freezing of funds" / "unauthorized privileged effect" (denial of the protocol's designated pnl-collection right) category.

### Likelihood Explanation
Likelihood is low-to-medium: it requires an attacker to actively and repeatedly submit minimal `Deposit`/`Withdraw` transactions (each requiring at least enough balance to mint/burn 1 lp unit) at a cadence tight enough to outrun the natural accumulation of price drift from swaps. This is economically cheap (no funds are lost by the attacker, only transaction fees) and does not require any privileged role, matching the Resolv report's "Low likelihood, High impact" profile for this bug class.

### Recommendation
Do not reset `calc_pnl_x`/`calc_pnl_y` unconditionally to the post-transaction pool state when `calc_take_pnl` yields a zero `delta_x`/`delta_y`. Instead, preserve the un-truncated drift across calls (e.g., by tracking pnl in higher precision, or only advancing the baseline component-wise by the actually-realized delta, not by resetting it to the full current reserves) so that repeated permissionless `Deposit`/`Withdraw` calls cannot be used to discard pending pnl before it can accumulate to a non-zero collectible amount.

### Proof of Concept
1. Deploy a pool with `pnl_numerator`/`pnl_denominator` fee split via `process_create_config`/pool initialization.
2. Let normal swap activity create a price drift such that `x1 - x2` (as computed in `calc_take_pnl`) is small enough that `pc_pnl_amount`/`coin_pnl_amount` (after `restore_decimal` and fee-ratio division) rounds to `0`, but would eventually become non-zero if left to accumulate over several swaps.
3. As an attacker, submit a minimal `Deposit` (e.g., depositing the smallest amount that mints `1` lp token) immediately after each swap.
4. Observe that each `Deposit` call invokes `Processor::calc_take_pnl`, computes `delta_x = delta_y = 0` (rounded down), yet still resets `target_orders.calc_pnl_x`/`calc_pnl_y` to the new `x1 + deduct_pc_amount` / `y1 + deduct_coin_amount` baseline (`program/src/processor.rs:1352-1371`).
5. Repeat over many swap/deposit cycles: `amm.state_data.need_take_pnl_pc`/`need_take_pnl_coin` never increase, and `WithdrawPnl` (`program/src/processor.rs:1495-1536`) never has anything meaningful to collect — the protocol's fee share is permanently forfeited despite continuous swap volume and fee-generating trades occurring in the pool.
