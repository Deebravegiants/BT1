### Title
`surplusShareBps` is read live from governance-updatable `_params` at fill time instead of being checkpointed when the order was placed - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2` orders commit `protocolFeeBps` economics at placement time (inputs are reduced and hashed into the commitment), but the surplus split percentage `_params.surplusShareBps` used in `_splitSurplus` is read from live governance-mutable storage at fill time, not from a value fixed when the order was created or signed by the user.

### Finding Description
`_splitSurplus` computes how solver overpayment ("dust") is divided between the protocol and the order's beneficiary using the *current* value of `_params.surplusShareBps`: [1](#0-0) 

`_params.surplusShareBps` is a governance-controlled parameter that can be changed at any time via `_updateParams`, which is invoked from a cross-chain `UpdateParams` message delivered through `onAccept` (dispatched by Hyperbridge governance, e.g. `pallet-intents-coprocessor`'s `ParamsUpdate`): [2](#0-1) 

Unlike `protocolFeeBps`, which is applied and baked into the order commitment at `placeOrder` time (the reduced input amounts are hashed into the commitment so the fee percentage is effectively locked in for that order): [3](#0-2) 

`surplusShareBps` is never snapshotted per-order. An order can be placed while `surplusShareBps` is, say, 0 (100% of surplus to beneficiary), and by the time a solver fills it — potentially many blocks later, especially for orders with long `deadline` windows — governance can update `surplusShareBps` to 10,000 (100% to protocol), silently redirecting the entire solver overpayment away from the beneficiary the user expected to benefit, or vice versa (protocol expecting a cut, but getting none). This mirrors the reported bug class exactly: a per-round/per-order economic parameter that participants rely on at commitment time is not checkpointed, and is instead resolved using whatever value is live at settlement/fill time, which is controlled by a different, later-acting party (governance) than the one who committed funds (the user placing the order, and the solver preparing to fill it).

### Impact Explanation
This affects real economic outcomes on every fill that involves solver overpayment (surplus), which is a normal and expected code path (`fillOrder` calls `_splitSurplus` whenever `received > order.inputs[i].amount`/output overage). A governance parameter change between order placement and fill can:
- Divert 100% of a beneficiary's expected surplus to the protocol, effectively confiscating funds the beneficiary reasonably expected based on the parameter active at order placement.
- Or divert protocol-expected surplus entirely to solvers/beneficiaries, undermining protocol revenue assumptions.

Because the surplus can be a meaningful fraction of order value in volatile markets, and orders can remain open for a `deadline` window measured in destination-chain blocks, this is a real, exploitable timing gap rather than a purely theoretical one. It qualifies as Medium/High severity: it is a fund-misdirection bug reachable by any user placing an order and any solver filling it, contingent on a benign governance-driven parameter update landing within an order's lifetime (no malicious governance assumption required — this is simply routine parameter tuning colliding with in-flight orders).

### Likelihood Explanation
Likelihood is moderate: it requires only that `_updateParams` (a normal governance maintenance action, not an attack) executes while at least one order with potential surplus is pending. Given that `surplusShareBps` is explicitly exposed as a tunable operational parameter (per the `Params`/`ParamsUpdate` structs and dedicated update path), and orders can be open for up to `order.deadline` blocks, routine fee tuning naturally creates windows where this occurs. No adversarial coordination is needed beyond ordinary parameter updates.

### Recommendation
Checkpoint `surplusShareBps` (and any other per-order economics such as `protocolFeeBps`, which is already handled correctly for input-side fees) at `placeOrder` time by storing it alongside the order commitment (e.g., in a small per-commitment struct or extra mapping), and have `_splitSurplus` read the checkpointed value for that specific commitment during `fillOrder`/settlement rather than the live `_params.surplusShareBps`. This mirrors the pattern already used for `protocolFeeBps`, where the fee-reduced amounts are committed into the order hash at placement.

### Proof of Concept
1. Governance sets `_params.surplusShareBps = 0` (100% of surplus to beneficiary) via `_updateParams`.
2. User calls `placeOrder`, expecting any solver overpayment/surplus to fully accrue to the `output.beneficiary`.
3. Before the order is filled (within its `deadline` window), governance updates params again, setting `surplusShareBps = 10_000` via a new `UpdateParams` cross-chain message processed by `onAccept` → `_updateParams` (evm/src/apps/intentsv2/IntentsBase.sol:611-628).
4. A solver fills the order and overpays (provides more output tokens than required), triggering `_splitSurplus` (evm/src/apps/intentsv2/IntentsBase.sol:426-434) with the now-current `surplusShareBps = 10_000`.
5. 100% of the surplus is diverted to the protocol instead of the beneficiary, contradicting the economic terms in effect when the order was placed and signed — exactly the "variables not checkpointed at start" bug class from the reference report.

```text
    /// @dev Splits overpayment between protocol and beneficiary. An order with output calldata
    /// gives the beneficiary nothing, since the surplus is not the caller's to give.
    function _splitSurplus(uint256 dust, bool hasOutputCall)
        internal
        view
        returns (uint256 protocolShare, uint256 beneficiaryShare)
    {
        if (hasOutputCall) return (dust, 0);
        protocolShare = (dust * _params.surplusShareBps) / 10_000;
        beneficiaryShare = dust - protocolShare;
    }
```

```text
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
```
