### Title
Webhook `shop` identity is unauthenticated (not covered by HMAC), enabling cross-tenant data attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook using `Utils::HmacValidator.validate(request)`, which authenticates only the raw request body via `Request#to_signable_string`. The `shop` value that the gem hands to the app's handler as the authoritative tenant identifier is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never included in the signed material, so it is fully attacker-controlled while the HMAC still validates successfully.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [2](#0-1) 
`hmac` is derived from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`: [3](#0-2) 

`shop` is read from a separate, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`): [4](#0-3) 

`Registry.process` validates only the HMAC (which covers the body) and then forwards `request.shop` unchanged into `WebhookMetadata`, which is documented and used by host apps as the authoritative tenant identifier for the webhook: [5](#0-4) [6](#0-5) 

The identity binding broken is: `shop authenticated (bytes covered by HMAC) != shop stored/used as tenant key (header value passed to the handler)`. An unprivileged internet user who can send arbitrary HTTP requests to the app's public webhook endpoint can take any previously-observed, validly-signed webhook body (bodies are frequently generic or predictable, e.g. `app/uninstalled`, `shop/redact`, or webhooks with attacker-influenced content on a shop the attacker controls) and resubmit it with a different `shopify-shop-domain` header. Because that header is not part of the signed bytes, `Utils::HmacValidator.validate` still returns `true`, and `Registry.process` will call the handler with `data.shop` set to the attacker-chosen shop while `data.body` is the replayed payload — causing the host app (which trusts this gem's stated guarantee that the request "did indeed come from Shopify") to attribute Shopify-signed webhook content to the wrong merchant/tenant.

### Impact Explanation
This breaks the tenant boundary the gem advertises: the docs explicitly claim `Registry.process` "will verify the request did indeed come from Shopify," implying the whole `WebhookMetadata` (including `shop`) is trustworthy. Host apps that key persistence, billing, GDPR redaction, or session/webhook-id deduplication logic off `data.shop` can have webhook data or actions cross-attributed to a different merchant's tenant, i.e., cross-tenant data confusion, without needing the app's `client_secret` or any privileged credential — only network access to the app's public webhook endpoint and one legitimately observed signed body.

### Likelihood Explanation
An attacker only needs to observe (or trigger, if they control a test/dev shop with the same app installed) one validly signed webhook body and can then freely resubmit it with any `shop-domain` header value; no secret material is required and the endpoint is by design internet-reachable and unauthenticated apart from the HMAC. This is a low-effort, no-credential attack once a single valid signed payload has been observed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified material, or at minimum have `Registry.process`/`HmacValidator` bind the header-derived `shop` to the signature context so a body cannot be replayed under a different shop identity. Alternatively, document prominently that `shop`, `topic`, and other headers are NOT authenticated by the HMAC and must not be trusted by host applications for tenant-sensitive decisions without additional verification (e.g., cross-checking against a known/registered shop for that webhook subscription).

### Proof of Concept
1. Attacker's own shop `attacker-shop.myshopify.com` has the app installed and receives a legitimately Shopify-signed webhook, e.g. body `{"id":123}` with header `shopify-hmac-sha256: <valid-hmac-of-body>` and `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body and HMAC header to the app's public webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) and `Utils::HmacValidator.validate(request)` returns `true` because validation only checks `raw_body` against the HMAC: [7](#0-6) 
4. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`: [8](#0-7) 
5. The host application, trusting `data.shop` as the verified tenant per the gem's documentation, processes/stores/enqueues the attacker's body as if it originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
