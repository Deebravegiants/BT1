## Analysis

The Shopify webhook HMAC verification in this gem binds *only* the request body, not the tenant-identifying headers (`shop`, `topic`, `webhook-id`, `api-version`) that the rest of the pipeline treats as authoritative. This is the same identity-binding defect class as the reported bug (a field is *acted on* — used to attribute/route the event — while a different, narrower set of bytes is what's actually *covered by the signature*).

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers, which are excluded from that signable string: [2](#0-1) 

`HmacValidator.validate` verifies the signature over `verifiable_query.to_signable_string` (the body only) using the app's single, shop-wide `api_secret_key`: [3](#0-2) 

`Registry.process` performs exactly that check and then forwards the header-derived `shop` (and `topic`) straight to the handler with no further binding check: [4](#0-3) 

Because the HMAC key (`Context.api_secret_key`) is the same for every shop that installs a given app, and the signature covers only the body, any request whose body+HMAC pair was legitimately produced for shop A will also pass validation when replayed with the `shop`/`topic` headers rewritten to shop B. The identity binding that should hold — `shop header == shop bound by signature` — does not hold, because the signature binds nothing about the shop at all.

### Title
Webhook HMAC does not bind the shop/topic headers, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content as the raw body only, excluding the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers. `Utils::HmacValidator` and `Webhooks::Registry.process` treat a valid body-HMAC as sufficient proof of authenticity for the whole request, then hand the unauthenticated `shop`/`topic` header values to the application's webhook handler as trusted tenant-identifying data.

### Finding Description
The equality that should hold is: `shop value trusted by the handler == shop value cryptographically bound by the signature`. Instead:
- `hmac` is computed over `@raw_body` only (`to_signable_string`), per `lib/shopify_api/webhooks/request.rb` lines 35-38.
- `shop`, `topic`, `webhook_id`, `api_version` come from headers, never mixed into the signed content (lines 15-33).
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) validates the HMAC and then constructs `WebhookMetadata` using `request.shop` and `request.topic` directly from headers, with no cross-check against the body or any per-shop secret.
- The signing secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop that has installed the app — it is not shop-specific.

Because the signature never covers the shop/topic headers, a body+HMAC pair valid for shop A's webhook is also valid for a request claiming to be from shop B, as long as the body content is unchanged. An entity that can obtain one legitimately-signed webhook payload for their own installation (e.g., a merchant who installed the app and can trigger/observe an outgoing webhook, or anyone who can capture such a payload in transit to a non-TLS-enforced endpoint) can replay it against the app's webhook endpoint with the `shop-domain`/`topic` headers rewritten to a different tenant, and it will pass `Utils::HmacValidator.validate` unchanged.

### Impact Explanation
This breaks the tenant boundary the webhook system is supposed to enforce: an application handler that trusts `WebhookMetadata#shop` to decide which merchant's data to update, create, or delete can be tricked into performing an action attributed to, or targeting, a different tenant than the one that actually produced the signed payload. This matches "cross-tenant access" (Critical) under the accepted impact categories, since it lets one tenant's authenticated event data cross into another tenant's processing context purely by header manipulation with no `client_secret` compromise needed.

### Likelihood Explanation
Exploitation requires possession of at least one valid signed body/HMAC pair, which any shop that has the app installed will legitimately receive from Shopify. No access to `api_secret_key` or any merchant's access token is required — only the ability to capture or trigger one webhook delivery and resend it to the app's public webhook endpoint with different headers. This is a realistic, credential-free replay against a public, internet-reachable endpoint.

### Recommendation
Bind the tenant-identifying headers into the signed content, or otherwise verify them out-of-band: at minimum, the app-level handler should not treat `shop`/`topic` from `WebhookMetadata` as authoritative for authorization decisions without corroborating against session/shop record state (e.g., verifying the shop is a known installed shop and, where possible, requiring a per-shop shared secret or including a nonce/shop binding in the verified payload). Within the gem, consider incorporating the `shop-domain` and `topic` headers into `to_signable_string`, or documenting explicitly that these headers are unauthenticated and must not be trusted for tenant attribution without additional application-level checks.

### Proof of Concept
1. Install the app on Shop A and Shop B (both use the same `api_secret_key`/`client_secret`).
2. Trigger or capture a legitimate webhook delivery to Shop A's app endpoint, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body B1>
   X-Shopify-Shop-Domain: shop-a.myshopify.com
   Body: B1
   ```
3. Replay the identical body `B1` and identical HMAC header, but change only the shop header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same HMAC of body B1>
   X-Shopify-Shop-Domain: shop-b.myshopify.com
   Body: B1
   ```
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31) succeeds because it only checks the HMAC over `B1`, which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) calls the handler with `shop: "shop-b.myshopify.com"`, even though the payload was never signed for, nor genuinely originated from, Shop B.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
