Audit Report

## Title
Non-atomic check-then-act JWT replay guard allows concurrent request authorization bypass in `WorkflowMetadataHandler.Authorize` - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks for JWT replay via `jwtCache.isReplay(claims.ID)` under an `RLock`, then performs workflow/signer lookups, and only marks the JWT as used via `jwtCache.recordUsage(claims.ID)` under a separate `Lock` at the end. Because these are two independent critical sections rather than one atomic check-and-set, concurrent requests using the same JWT can both pass the replay check before either records usage, resulting in multiple successful authorizations from a single-use token.

## Finding Description
`Authorize` verifies the JWT, calls `h.jwtCache.isReplay(claims.ID)`, then does workflow ID and signer lookups (map reads), and finally calls `h.jwtCache.recordUsage(claims.ID)` right before returning success. [1](#0-0)  `isReplay` and `recordUsage` are implemented as separate lock-guarded methods on `jwtReplayCache`, with `isReplay` using `RLock`/`RUnlock` and `recordUsage` using `Lock`/`Unlock` independently. [2](#0-1)  No lock spans the full check-then-act sequence in `Authorize`, so two goroutines can both observe `isReplay == false` for the same `jti` before either calls `recordUsage`, both proceeding through workflow/signer validation and both returning a valid `*gateway.AuthorizedKey`. This is reachable from the gateway's HTTP trigger request-handling path. [3](#0-2)  The codebase's own Vault `RequestReplayGuard.CheckAndRecord` shows the correct atomic pattern (single `Lock` for check-and-insert), which `jwtReplayCache` lacks. [4](#0-3)  The existing test only demonstrates sequential (non-concurrent) replay rejection, which does not cover this race. [5](#0-4) 

## Impact Explanation
An attacker holding one valid signed JWT for a workflow-execute request can send concurrent requests to the gateway and, if the race is won, obtain more than one successful authorization/execution from a single-use token. This breaks the single-use guarantee of signed workflow-execute requests, potentially enabling duplicate workflow triggers — a gateway request-impersonation/authorization-integrity issue affecting single-use token semantics.

## Likelihood Explanation
Exploitability requires only an unprivileged client capable of obtaining/crafting a valid JWT and sending it via a small number of parallelized requests; the window between `isReplay` and `recordUsage` includes real map-lookup work, giving an appreciable race window. This is realistically exploitable with moderate effort (parallel request flooding), making likelihood Medium.

## Recommendation
Introduce an atomic `CheckAndRecord`-style method on `jwtReplayCache` that performs the existence check and insertion under a single `Lock`/`Unlock` critical section (mirroring `RequestReplayGuard.CheckAndRecord`), and invoke it as the first step of `Authorize` before any workflow/signer lookups, ensuring no two concurrent calls with the same `jti` can both pass.

## Proof of Concept
1. Sign a single JWT for a valid workflow-execute request as done in the existing `TestWorkflowMetadataHandler_Authorize` "JWT replay protection" subtest.
2. Launch two goroutines calling `handler.Authorize(workflowID, tokenString, req)` concurrently with the identical token, synchronized to start together (e.g., via a barrier/waitgroup).
3. Because `isReplay` and `recordUsage` are non-atomic, assert that occasionally (or with sufficient repetition/`-race` stress runs) both goroutines return `err == nil` and a non-nil `*gateway.AuthorizedKey`, instead of the expected single success and one "JWT token has already been used" error.

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
