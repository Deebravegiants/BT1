### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted as tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` (and `topic`, `webhook_id`, `api_version`) purely from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies is computed over the raw body only. `Webhooks::Registry.process` then hands `request.shop` straight to the app's webhook handler as the authoritative tenant identifier. This breaks the identity binding `shop_used_by_handler == shop_that_produced_the_signed_bytes`, allowing a valid HMAC produced for one shop's webhook payload to be replayed with a different `shop-domain` header, causing cross-tenant data confusion in any app built on this gem.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac` value (itself also read from a header): [3](#0-2) [4](#0-3) 

`Webhooks::Registry.process` then checks only that the body-HMAC is valid, and forwards the header-derived, unauthenticated `request.shop`/`request.topic` values to the app-supplied handler as the trusted tenant/topic identifiers: [5](#0-4) 

Because none of `shop-domain`, `topic`, or `webhook-id` are part of the signed bytes, the equality the library implicitly promises — "the `shop` passed to the handler is the shop for which Shopify computed this HMAC" — does not hold. Any bytes (body) that produce a valid HMAC for *some* shop under the app's `api_secret_key` remain valid for *any* `shop-domain` header value, because the header is never mixed into the signed material.

### Impact Explanation
This is a cross-tenant identity-binding break at the core of the gem's webhook-authentication primitive. Any Ruby app that follows the documented pattern (`Registry.process(request)` → trust `WebhookMetadata#shop`) inherits the flaw: a payload legitimately generated for shop A (with a valid HMAC over that body, computed by Shopify using the app's real `api_secret_key`) can be relabeled as coming from victim shop B simply by changing the `shopify-shop-domain` / `x-shopify-shop-domain` header before it reaches the endpoint. The handler will then create/update/associate data (orders, customers, sessions, etc.) under the wrong merchant's tenant — a cross-tenant access/data-confusion vulnerability, which the assessment classifies as Critical impact.

### Likelihood Explanation
Exploitation requires no possession of the app's `api_secret_key`, no TLS interception, and no privileged account. Any actor can (a) install the target app on their own, freely-created Shopify development/trial store to obtain a body+HMAC pair that is valid under the target app's real secret, and (b) submit an HTTP POST directly to the app's public webhook endpoint with that same body/HMAC pair but an altered `shop-domain` (and/or `topic`) header, since the endpoint is a normal internet-reachable HTTP route and the gem performs no header-binding check. This is straightforward for any unprivileged internet user familiar with the target app's webhook URL.

### Recommendation
Bind the identity headers into the signed material actually verified, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in `to_signable_string` (or perform a secondary derivation/check), so a body+HMAC pair is only valid for the exact shop/topic Shopify signed it for.
- Alternatively, require host applications to cross-check `request.shop` against a shop already known/authorized for that install (e.g., an existing session record) before trusting the payload, and document this requirement prominently since the gem currently offers no such protection itself.
- Add regression tests asserting that replaying a valid HMAC body with a different `shop-domain` header is rejected.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker-shop.myshopify.com"
# and captures a legitimately delivered webhook (body + valid HMAC), e.g. orders/create:
raw_body = '{"id":1,"note":"attacker-controlled content"}'
valid_hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  app_api_secret_key, # not known to attacker; obtained legitimately from a real Shopify-signed callback
  raw_body,
)

# Attacker replays the SAME body/hmac but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation because only raw_body is checked:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process hands attacker-controlled body to the handler
# labeled as belonging to "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
```
`request.shop` returned to the handler is `"victim-shop.myshopify.com"` despite the HMAC only proving the body originated from an app-signed payload — not from that specific shop — demonstrating the broken binding.
