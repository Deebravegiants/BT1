## Title
Arithmetic-underflow panic in `Processor::calc_take_pnl` can permanently brick `Deposit`/`Withdraw`/`WithdrawPnl` for a pool - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes the “after take-pnl” invariant point `(x2, y2)` and then does `x1.checked_sub(x2).unwrap()` / `y1.checked_sub(y2).unwrap()` under the assumption that `x2 <= x1` and `y2 <= y1`. That assumption is protected only by a coarse guard computed in *raw, un-normalized token amounts*, while `x2`/`y2` are derived in *sys-decimal normalized* units. Because both `normalize_decimal_v2` and `restore_decimal` are lossy floor divisions, the raw-unit guard and the normalized-unit invariant it is supposed to protect are not equivalent — rounding drift can make the guard pass while `x2 > x1` (or `y2 > y1`) in the normalized domain, causing the subtraction to underflow and the whole transaction to panic/revert. This mirrors the reported `MPROMasterDistributor.getAllTokenDistribution()` bug class: an internal helper used by several user-facing entry points underflows because the loop/guard condition doesn't precisely match the units used in the arithmetic that follows it.

### Finding Description
`calc_take_pnl` is the shared PnL-rebasing routine invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`: [1](#0-0) [2](#0-1) 

Inside it, the branch guard is evaluated on raw token amounts: [3](#0-2) 

but the quantity that is actually subtracted (`x1 - x2`, `y1 - y2`) is computed from `x1`/`y1` in sys-decimal-normalized units derived via `Calculator::calc_x_power`/`integer_sqrt`, then subtracted with `.unwrap()` (a panic on underflow, not a recoverable `Result`): [4](#0-3) 

`normalize_decimal_v2` and `restore_decimal` are both floor-divisions: [5](#0-4) 

so the round-trip `raw -> normalized -> raw` used to build the guard (`calc_pc_amount`, `calc_coin_amount` via `restore_decimal`) is lossy relative to the direct `raw -> normalized` path used to build `x1`, `y1`. Algebraically the intended invariant is `x1*y1 >= calc_pnl_x*calc_pnl_y` (normalized units), but the code instead checks `pool_pc_amount*pool_coin_amount >= calc_pc_amount*calc_coin_amount` (raw units, with `calc_pc_amount`/`calc_coin_amount` floor-restored from `calc_pnl_x`/`calc_pnl_y`). These two checks are only approximately equivalent; floor-rounding on the restore side systematically lowers the RHS of the raw-unit check, which can let the guard pass even when the true normalized invariant `x1*y1 >= calc_pnl_x*calc_pnl_y` no longer holds (e.g., after many small swaps/deposits/withdraws that keep nudging `total_pc_without_take_pnl`/`total_coin_without_take_pnl` and `target_orders.calc_pnl_x/calc_pnl_y` by rounding amounts). Once that inequality is violated in the normalized domain while the raw-unit guard still passes, `x2 = sqrt(calc_pnl_x*calc_pnl_y*x1/y1)` can exceed `x1`, and/or the derived `y2` can exceed `y1`, making `x1.checked_sub(x2).unwrap()` or `y1.checked_sub(y2).unwrap()` panic.

### Impact Explanation
Once the pool’s accumulated state (`amm.state_data.need_take_pnl_pc/coin`, `target_orders.calc_pnl_x/calc_pnl_y`, current vault balances) drifts into this edge condition, **every** subsequent call to `calc_take_pnl` panics deterministically for that pool, because the inputs (`x1`, `y1`, `target_orders.calc_pnl_x/y`) only change incrementally with each operation and the underflow condition, once triggered, is not self-correcting. Since `calc_take_pnl` is invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`, this means LPs can be permanently unable to deposit or withdraw liquidity from the affected pool — i.e., a **permanent freeze of LP/user funds** in that pool, satisfying the "Medium" DoS severity of the analog report (and worse here, since it can affect fund withdrawal, not just a distribution helper).

### Likelihood Explanation
No privileged signer or malicious validator is required. The underflow depends only on organically accumulated rounding drift from ordinary pool activity (swaps/deposits/withdrawals performed by any unprivileged user over time) interacting with the two non-equivalent unit checks in `calc_take_pnl`. An attacker can accelerate reaching the edge condition by repeatedly performing small deposit/withdraw cycles designed to maximize floor-rounding loss in `restore_decimal`/`normalize_decimal_v2`, then trigger the panic with one final deposit/withdraw call using ordinary account inputs — no special permissions or account substitution needed.

### Recommendation
- Perform the guard comparison in the same units used for the subsequent `checked_sub` (i.e., compare `x1.checked_mul(y1)` against `target.calc_pnl_x.checked_mul(target.calc_pnl_y)` directly in normalized/sys-decimal units, not round-tripped through `restore_decimal`).
- Replace the panicking `.unwrap()` calls around `x1.checked_sub(x2)` / `y1.checked_sub(y2)` (and the related subtractions in `process_deposit`/`process_withdraw`/`process_withdrawpnl`) with `checked_sub(...).ok_or(AmmError::CalcPnlError)?` (or clamp `x2`/`y2` to `min(x2, x1)`/`min(y2, y1)`) so that a rounding edge case returns a graceful program error instead of an unrecoverable panic.
- Add regression tests that intentionally construct near-boundary `calc_pnl_x`/`calc_pnl_y` vs. vault-balance states (as already partially exercised by `test_calc_pnl_precision`) to confirm the function never underflows regardless of decimal configuration.

### Proof of Concept
1. Create a pool with asymmetric decimals (e.g., `pc_decimals = 6`, `coin_decimals = 9`, as used in `test_calc_pnl_precision`) and a non-trivial `sys_decimal_value`.
2. Repeatedly perform small `Deposit`/`Withdraw` operations (attacker-controlled amounts, no special accounts needed) so that `target_orders.calc_pnl_x`/`calc_pnl_y` and the vault balances drift via the floor-rounding in `normalize_decimal_v2`/`restore_decimal` shown at `program/src/math.rs:80-116`.
3. Once `pool_pc_amount*pool_coin_amount >= calc_pc_amount*calc_coin_amount` (raw-unit guard, `program/src/processor.rs:190-192`) holds while `x1*y1 < calc_pnl_x*calc_pnl_y` (true normalized invariant) no longer holds, the subsequent call to `Processor::calc_take_pnl` from any `Deposit`/`Withdraw`/`WithdrawPnl` instruction computes `x2 > x1` (or `y2 > y1`) and panics at `program/src/processor.rs:213-214`, aborting the transaction and leaving the pool’s LPs unable to deposit or withdraw funds thereafter.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
