## Title
Flash-swap manipulation of the AMM's own spot reserves to inflate LP-token minting via `calc_take_pnl` during `Deposit`/`Withdraw` - (File: `program/src/processor.rs`)

### Summary
Raydium's `Deposit` and `Withdraw` instructions derive the "true" (fee/PNL-adjusted) pool reserves from the AMM's *instantaneous* vault balances read in the same instruction, then compare them against a previously stored baseline (`TargetOrders.calc_pnl_x/y`) to decide how much of the pool's balance is "profit" that must be walled off (`need_take_pnl_pc/coin`) before computing LP mint/redemption ratios. Because this spot price can be freely moved by an attacker-controlled swap earlier in the same transaction, and there is no TWAP, oracle, or minimum lock/period protecting this computation, an attacker can distort the reserves right before calling `Deposit`, causing an inflated amount to be walled off as "PNL" and shrinking the reserve figure used as the denominator for LP-share minting math — resulting in the attacker receiving more LP shares than a fair deposit would produce.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` computes the reserves that back existing LP supply purely from the current vault token balances minus the recorded `need_take_pnl_*` counters: [1](#0-0) 

`calc_take_pnl` is invoked unconditionally on every `Deposit` (and on `Withdraw` unless status is `WithdrawOnly`) using this same-instruction spot state (`x1`, `y1` derived directly from `amm_pc_vault.amount` / `amm_coin_vault.amount`) and compares it to the last stored baseline `target.calc_pnl_x` / `target.calc_pnl_y`: [2](#0-1) 

The pnl amounts it derives are immediately subtracted from `total_pc_without_take_pnl` / `total_coin_without_take_pnl` and added to `amm.state_data.need_take_pnl_pc/coin`: [3](#0-2) 

In `process_deposit`, this call happens before the mint calculation, and its adjusted (shrunken) totals are then used as the denominator to compute `mint_lp_amount`: [4](#0-3) [5](#0-4) 

Because `mint_lp_amount = deduct_coin_amount / total_coin_without_take_pnl * amm.lp_amount`, artificially shrinking `total_coin_without_take_pnl` (via an inflated, price-manipulated "PNL" deduction) directly inflates the LP tokens minted for the same deposited amount. The same distorted spot reserves are also used symmetrically in `process_withdraw`, reusing `calc_take_pnl` before computing `coin_amount`/`pc_amount` payouts: [6](#0-5) 

Both `Deposit` and `Withdraw` are permissionless instructions reachable by any signer with attacker-chosen token accounts and amounts, and both can be freely combined with the four swap instructions in the same transaction (Solana composability plays the role of the "flash loan" in the referenced report — no external loan is even needed since it's all one atomic transaction). This is the direct analog of the reported bug class: a protocol using its own manipulable spot price/reserves (rather than a time-weighted or external price) to make consequential accounting decisions (PNL skimming that affects LP-share issuance) within a single attacker-controlled transaction, with no lock period or anti-manipulation guard.

### Impact Explanation
An attacker can, within one transaction: (1) swap to skew the AMM's coin/pc ratio away from the stored `calc_pnl_x/y` baseline, (2) call `Deposit`, causing an inflated "PNL" figure to be walled into `need_take_pnl_pc/coin` and the LP-backing reserve denominator to shrink, thereby minting the attacker more LP tokens than a fair deposit at the true price would produce, (3) reverse the swap, and (4) `Withdraw` the inflated LP position to redeem more underlying value than deposited. This dilutes existing LP holders' claims on the pool and/or diverts pool value that should back LP shares, constituting theft of LP funds / insolvent LP accounting — a direct value transfer from existing liquidity providers to the attacker.

### Likelihood Explanation
All required instructions (`SwapBaseIn`/`SwapBaseOut`, `Deposit`, `Withdraw`) are unprivileged, take attacker-supplied accounts and amounts, and are composable in a single transaction, which is the normal way Solana clients build multi-instruction operations. No minimum time lock, TWAP, or oracle is used to bound the reserve state that `calc_take_pnl` relies on, so the cost of the attack is only swap fees plus any temporary capital needed to move the pool's ratio — which is directly proportional to pool depth and thus most exploitable on shallower pools, similar to the referenced report's dependence on pool liquidity depth.

### Recommendation
- Do not derive the PNL/reserve baseline comparison from the same-instruction, attacker-influenced spot vault balances; instead use a time-weighted or otherwise manipulation-resistant reference (e.g., require `calc_take_pnl` inputs to be sourced from a price recorded prior to the current transaction/slot).
- Consider disallowing `Swap` and `Deposit`/`Withdraw` against the same pool within a single transaction, or add a minimum holding/lock period for freshly minted LP tokens before they can be redeemed, mirroring the `_minLockPeriod > 0` mitigation from the referenced report.
- Bound the maximum PNL that can be skimmed per call relative to a longer-horizon average price rather than the instantaneous ratio.

### Proof of Concept
1. Attacker observes `TargetOrders.calc_pnl_x` / `calc_pnl_y` (the stored reserve baseline) for a target pool.
2. In one transaction: call `SwapBaseIn`/`SwapBaseOut` with a large `amount_in` to shift `amm_pc_vault.amount` / `amm_coin_vault.amount` far from the baseline ratio (see swap math using raw vault balances) [7](#0-6) .
3. Immediately call `Deposit`; `calc_take_pnl` computes an inflated `pc_pnl_amount`/`coin_pnl_amount` from the distorted `x1`,`y1` versus the stale baseline, shrinking `total_pc_without_take_pnl`/`total_coin_without_take_pnl` [8](#0-7) , causing `mint_lp_amount` to be computed against an artificially small pool denominator [5](#0-4) .
4. Reverse the initial swap in the same transaction to restore the price.
5. Call `Withdraw` to redeem the inflated LP position for underlying coin/pc at (now normal) pricing, extracting more value than was deposited, at the expense of existing LP holders whose backing reserves were permanently reduced by the phantom PNL deduction.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
