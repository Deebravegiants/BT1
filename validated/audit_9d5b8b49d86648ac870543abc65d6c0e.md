### Title
Unfunded `recapitalize` refunds the declared amount from pool custody, draining supplier funds - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
`recapitalize` is documented as "the controller transfers `amount` into the pool before this call," but the pool never measures or verifies that it actually received `amount` before paying the refund. `accounting` credits `min(amount, backing_shortfall)` to cash and computes `refund = amount - applied`; `apply` then unconditionally executes `cache.transfer_out(&payer, refund)` [1](#0-0) . When there is no backing shortfall (the normal case), `applied = 0` and `refund = amount`, so the pool pays the full declared `amount` out of its own token custody — funds that belong to suppliers — without anyone having deposited a single unit. This is the same bug class as the reference finding: a refund is computed from a caller-declared/stored amount rather than from funds actually received, so unbacked claims are paid out of protocol custody.

### Finding Description
In `contracts/pool/src/ops/recapitalize.rs`, `apply` calls `accounting`, which loads the market via `ops::renewed_market`, computes `applied = amount.min(guards::backing_shortfall(&cache))`, credits only `applied` to the cash book, and commits [2](#0-1) . It then calls `outcome.cache.transfer_out(&payer, outcome.refund)` for the full `amount - applied` [3](#0-2) . Unlike the repay path, which also refunds an overpayment with `transfer_out` [4](#0-3) , no prior balance snapshot or measured receipt ties the outbound refund to an inbound transfer — the controller-side `repay_debt_from_controller` pattern snapshots `balance_before` and refunds only the measured delta [5](#0-4) , but `recapitalize` trusts the declared `amount` verbatim.

The in-repo test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` proves this end-to-end: after minting a 10_000_000_000 deposit into the pool, calling `client().recapitalize(&hub, &payer, &custody)` with a payer that transferred nothing drives `token.balance(&t.pool)` to 0 while `state_snapshot().cash` still reports the deposit, and a subsequent supplier `withdraw` passes the pool's own `require_reserves`/`PoolInsolvent` guards (which read the cash book) and fails only inside the SAC transfer with balance error 10 [6](#0-5) .

### Impact Explanation
An unprivileged caller invokes `recapitalize(hub_asset, attacker_payer, amount)` with `amount` equal to the market's full token custody. With no (or a small) backing shortfall, the pool transfers the entire declared amount to `attacker_payer` directly from custody — a straight theft of supplier funds. Even partial calls work: each call takes `min(amount, shortfall)` as applied and pays the rest to the payer, so draining is bounded only by custody. After the drain, the `cash` book still reports the stolen funds as present, so the market appears solvent while every real withdrawal/liquidation payout fails in the token transfer — permanent loss for suppliers plus a market that cannot pay, matching both "theft of user funds" and "contract unable to operate from lack of token funds" acceptance criteria.

### Likelihood Explanation
The attack is a single public entrypoint call with caller-chosen `payer` and `amount` arguments; no timing, oracle state, position setup, or privileged role is required — the only precondition is that the market holds token custody (i.e., has suppliers). Any healthy market has `backing_shortfall = 0` by construction, so the happy path itself is the exploit path. The existing unit test already demonstrates the drain deterministically.

### Recommendation
- Measure the receipt: snapshot `token.balance(pool)` before crediting and require the balance delta to be ≥ `applied` (use the `transfer_amount_measured`/`balance_delta_since` pattern already used for controller repayments [7](#0-6) ), or revert unless `shortfall >= amount` so the refund is always 0.
- Never call `transfer_out` for a refund derived from an unverified declared `amount`; derive `refund = received - applied` from the measured delta instead.
- Optionally restrict `recapitalize` to the controller and have the controller perform the funding transfer atomically before the pool call, as with `repay`.

### Proof of Concept
```
// Attacker, unprivileged. Market is healthy: no backing shortfall.
let custody = token.balance(&pool);           // e.g. suppliers' 10_000 USDC
pool.recapitalize(&hub_asset, &attacker, &custody);
// accounting(): applied = min(custody, 0) = 0; refund = custody
// apply():      cache.transfer_out(attacker, custody)
assert_eq!(token.balance(&attacker), custody);
assert_eq!(token.balance(&pool), 0);
// cash book still reports `custody`; next supplier withdraw reverts
// inside the token transfer (SAC balance error 10), not in pool guards.
```
This mirrors `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3407`, which already executes this exact sequence and asserts custody drained to zero while the book still overstates it.

Caveat: I could not fully verify `recapitalize`'s authorization layer in `contracts/pool/src/lib.rs` within the available iterations; the endpoint is listed among unprivileged-reachable paths in scope and the test invokes it with an arbitrary generated `payer`, but if a caller-auth check on `payer` exists, the attacker simply authorizes their own address — the payout still goes to them and no funding check exists regardless.

pub(crate) fn refund_controller_balance_delta(
    env: &Env,
    asset: &Address,
    balance_before: i128,
    refund_to: &Address,
) {
    let controller = env.current_contract_address();
    let excess = balance_delta_since(env, asset, &controller, balance_before);
    if excess > 0 {
        token::Client::new(env, asset).transfer(&controller, refund_to, &excess);
    }
}
