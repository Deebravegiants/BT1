## Title
Webhook Shop/Topic Identity Spoofing via Unauthenticated Headers Not Covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook HMAC verification in this gem only binds the raw request body to the signature. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values — which are the fields the host application actually acts upon to determine tenant identity and dispatch — are read directly from unauthenticated HTTP headers and are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` by exposing `hmac` (parsed from the `X-Shopify-Hmac-Sha256` header) and `to_signable_string`, which returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC strictly over `verifiable_query.to_signable_string` (the body) and compares it to the received signature — it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` (all header-derived, unauthenticated) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding broken here is: `hmac_valid(body) == true` is treated as equivalent to `shop_header == originating_shop`, when in fact the HMAC secret (`Context.api_secret_key`) is a single app-wide secret shared across every shop that installs the app — it is not shop-specific. Consequently, any party who can obtain one validly-signed webhook body (e.g., by triggering a webhook-eligible event on their own store, which they legitimately control as an app installer) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will dispatch the handler with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
Applications built on this gem commonly use the webhook's `shop` field to select which merchant's data/session to update (e.g., write order data, update fulfillment status, revoke access on `app/uninstalled`, etc.) keyed by that field. Because `shop` is not cryptographically bound to the signed body, an attacker who legitimately controls one shop installation can forge events attributed to a different merchant's shop, causing cross-tenant data injection/corruption — matching the "cross-tenant access" Critical impact category, since the tenant boundary (shop identity) is exactly what the HMAC binding fails to enforce.

### Likelihood Explanation
Any developer or attacker who installs the app on their own store (which requires no special privilege beyond being a Shopify merchant/dev-store owner) has legitimate access to real, correctly-signed webhook deliveries for their own shop. Replaying such a request against the app's public webhook endpoint with a modified `shop-domain` header requires only basic HTTP tooling — no access to `api_secret_key`, tokens, or the target's credentials.

### Recommendation
Bind tenant/event identity into the verified material: either derive `shop` (and `topic`/`webhook_id`) from the signed payload itself, or use a per-shop verification path (e.g., look up the expected shop for that HMAC/webhook subscription rather than trusting the header) so that `shop_header == originating_shop` is enforced as part of `HmacValidator.validate`, mirroring how `checked_mul` was introduced to close the analogous "value used vs. value guarded" gap in the referenced report.

### Proof of Concept
1. Install the target app on an attacker-owned shop; trigger any subscribed webhook topic (e.g., `orders/create`) to receive a request with a valid `X-Shopify-Hmac-Sha256` for that exact raw body, computed with the app's single shared `api_secret_key`.
2. Capture the raw body and its valid HMAC header.
3. Resend the identical body + HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with the victim's `*.myshopify.com` domain.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks the (unchanged) body.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `data.shop` equal to the victim's domain, causing the host application to process attacker-controlled content as if it originated from the victim shop.
