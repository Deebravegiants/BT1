### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC of an incoming webhook using only the raw request body as the signable string, while the `shop` (and `topic`/`webhook_id`) values are taken from unauthenticated HTTP headers that are never included in the signed payload. Because a single `api_secret_key` is shared across every shop that has installed the app, any shop that legitimately receives a validly-signed webhook can replay that exact body+signature while substituting a different `shop-domain` header, and the signature will still validate. This breaks the intended binding: `hmac_is_valid(body) == data_belongs_to(shop_header)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the (attacker-controllable, in the sense of a malicious/rogue merchant sending a raw HTTP request) header, with no cryptographic tie to the signature: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`; it never inspects or incorporates `shop`: [3](#0-2) 

`Registry.process` gatekeeps solely on this HMAC check, then immediately trusts `request.shop` when dispatching to the app-supplied handler: [4](#0-3) 

Since `Context.api_secret_key` is one value for the whole app (not per-installation), every shop that installs the app can produce a validly-HMAC-signed webhook body (Shopify signs it for them using the shared secret). A malicious merchant can capture a webhook Shopify sent to their own endpoint (valid signature over that body), then POST the identical `raw_body` + `hmac-sha256` header to the app's webhook endpoint again, but with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` (it only checks the body/secret pair), so `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with the forged shop value. Any handler logic that trusts `data.shop` to select which tenant's records to read/write/associate now operates cross-tenant.

This is the same root-cause class as the report's `_updateLastClaimTime` bug: a field that is *acted upon* (`shop`) is not covered by the same integrity mechanism (HMAC) that protects the field the code assumes is authoritative (`raw_body`), so verifying one does not verify the other, breaking `verified_bytes == acted_upon_identity`.

### Impact Explanation
This falls under "cross-tenant access" (Critical), since it allows a merchant/attacker who has valid webhook traffic for their own shop to make the consuming application process/attribute data as belonging to an arbitrary other shop, without ever needing that other shop's credentials or the app's `client_secret`.

### Likelihood Explanation
Any app built on this gem that (a) processes webhooks from more than one shop with a single shared `api_secret_key` (the standard multi-tenant public-app model) and (b) uses `WebhookMetadata#shop` to route/attribute data is exposed. The only prerequisite is that the attacker has legitimately received at least one real webhook for their own shop — a normal, unprivileged capability of any merchant who installs the app.

### Recommendation
- Require the caller to supply the expected shop (e.g., looked up via `webhook_id`/topic registration or session context) and reject the webhook if `request.shop` doesn't match, or
- Bind `shop` (and `topic`, `webhook_id`) into the HMAC-verified signable string / verification step, rather than trusting raw headers, and
- Document clearly that `WebhookMetadata#shop` is not currently authenticated by the HMAC check, so downstream apps understand they must independently validate the shop.

### Proof of Concept
1. App has installations for `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, both under the same app `client_secret`.
2. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. Attacker captures `B` and `H` (e.g., via their own reverse proxy/logging).
3. Attacker crafts a new HTTP POST to the same webhook endpoint with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` runs `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` — validation succeeds. [5](#0-4) 
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and performs whatever tenant-scoped action it implements (e.g., update order/customer data) against `victim-shop.myshopify.com`'s records, even though the payload actually originated from the attacker's own shop.
