### Title
Cross-chain amount conversion can round down to zero, silently dropping bridged transfers - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` in the `hyper-fungible-token` pallet converts an incoming ERC20-denominated amount into the local asset's balance via `convert_to_balance`, then unconditionally mints/transfers that converted amount to the beneficiary, without ever checking whether the conversion produced zero. This mirrors the Sherlock finding in Rio's `RioLRTCoordinator::deposit`, where a decimals/price conversion could floor `amountOut` to zero and the deposit still proceeded, silently losing the user's value.

### Finding Description
`on_accept` decodes the cross-chain `Message`, resolves the local asset/decimals, and then computes: [1](#0-0) 

```
let amount = convert_to_balance::<...>(
    U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
    erc_decimals,
    decimals,
).map_err(...)?;
```

`convert_to_balance` performs a decimals-rescale between the source ERC20's decimals (`erc_decimals`) and the local asset's decimals (`decimals`). When the local asset has fewer decimals than the source token (e.g., an 18-decimal EVM ERC20 bridged to a 6-decimal Substrate asset, or any similarly lossy downscale), a small enough `message.amount` rescales to `0` via integer division, yet the function only errors on conversion failure, not on a successful-but-zero result.

That zero `amount` then flows straight into the mint/transfer branch with no zero-amount guard: [2](#0-1) 

The pallet mints or transfers `amount` (which can legitimately be `0`) to `beneficiary` and returns `Ok(Weight)` (success) either way — there is no `ensure!(amount > 0, ...)` check anywhere on this path, unlike the Rio report's recommended `if(amountOut == 0) revert`.

### Impact Explanation
Because this pallet is the receiving side of a cross-chain token bridge (`IsmpModule::on_accept` for `PostRequest`), a message that carries a non-zero amount on the source chain that rescales to zero locally results in the request being accepted/processed successfully with `amount = 0`. If the source-side contract already burned/locked the user's tokens before dispatching the ISMP message (the standard bridge burn-then-mint pattern), the user's funds are permanently lost: nothing is minted on the destination, but the request is marked handled/accepted, so there is no automatic retry or refund path. This is a permanent freezing/loss-of-funds bug reachable by any user who dispatches a bridge transfer with a small enough amount relative to the decimals delta between the two chains' asset representations.

### Likelihood Explanation
Likelihood is asset/decimals-dependent but fully attacker/user-controllable: any unprivileged user bridging a token pair where the destination asset has materially fewer decimals than the source ERC20 (a completely normal, admin-configured but not fault-prevented scenario via `Precisions`/asset metadata) can trigger this simply by sending a small amount — no special privileges or races are required, matching the "small deposit" trigger condition in the original report.

### Recommendation
Add an explicit zero-amount check on the converted `amount` in `on_accept` before minting/transferring, and reject (revert/error) the request rather than silently succeeding with a zero-value mint:
```rust
let amount = convert_to_balance::<...>(...)?;
ensure!(!amount.is_zero(), HftError::AmountRoundsToZero);
```
This causes such tiny cross-chain transfers to fail explicitly (and be retried/handled as a failed request per ISMP's normal error path) instead of being marked as successfully processed while delivering nothing to the beneficiary.

### Proof of Concept
1. Configure a bridge pair where the source ERC20 has 18 decimals and the destination local asset has, e.g., 6 decimals (via `Precisions::<T>` / asset metadata), consistent with normal deployment configuration.
2. From the source EVM chain, dispatch a `PostRequest` with `message.amount` representing a token quantity small enough that, after the decimals rescale in `convert_to_balance`, the result truncates to `0` (e.g., an amount smaller than `10^(erc_decimals - decimals)`).
3. `on_accept` decodes the message, computes `amount = 0` via `convert_to_balance`, and proceeds to `mint_into`/`transfer` with `amount = 0`, returning success.
4. The request is recorded as handled; the beneficiary receives nothing, while the user's tokens were already consumed/locked on the source chain — resulting in an unrecoverable loss of the deposited value. [3](#0-2)

impl<T: Config> IsmpModule for Pallet<T>
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
	<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance: core::str::FromStr,
	<<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance as core::str::FromStr>::Err:
		core::error::Error + Send + Sync + 'static,
	<<T as Config>::Assets as fungibles::Inspect<T::AccountId>>::Balance:
		From<<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance>,
{
	fn on_accept(
		&self,
		PostRequest { body, from, source, .. }: PostRequest,
	) -> Result<Weight, anyhow::Error> {
		// Authenticate: look up which local asset this contract address maps to
		let local_asset_id = ContractToAsset::<T>::get(source, &from)
			.ok_or(HftError::UnknownSourceContract(source))?;

		// Decode the Message
		let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

		// Convert recipient bytes to substrate AccountId
		// If 32 bytes: use directly. If 20 bytes: left-pad with zeros.
		let mut beneficiary_bytes = [0u8; 32];
		let to_bytes = message.to.as_ref();
		if to_bytes.len() == 32 {
			beneficiary_bytes.copy_from_slice(to_bytes);
		} else if to_bytes.len() == 20 {
			beneficiary_bytes[12..].copy_from_slice(to_bytes);
		} else {
			Err(HftError::InvalidRecipientLength(to_bytes.len()))?;
		}
		let beneficiary: T::AccountId = beneficiary_bytes.into();

		// Convert amount from ERC20 denomination to local
		let decimals = if local_asset_id == T::NativeAssetId::get() {
			T::Decimals::get()
		} else {
			<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
				local_asset_id.clone(),
			)
		};
		let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), source)
			.ok_or(HftError::DecimalsNotConfigured(source))?;
		let amount = convert_to_balance::<
			<<T as Config>::NativeCurrency as Currency<T::AccountId>>::Balance,
		>(
			U256::from_big_endian(&message.amount.to_be_bytes::<32>()),
			erc_decimals,
			decimals,
		)
		.map_err(|e| HftError::InvalidAmountConversion(format!("{e:?}")))?;

		// Mint or transfer to beneficiary
		if local_asset_id == T::NativeAssetId::get() {
			<T as Config>::NativeCurrency::transfer(
				&Pallet::<T>::pallet_account(),
				&beneficiary,
				amount,
				ExistenceRequirement::AllowDeath,
			)
			.map_err(|e| HftError::TransferFailed(e.into()))?;
		} else {
			let is_native = NativeAssets::<T>::get(local_asset_id.clone());
			if is_native {
				<T as Config>::Assets::transfer(
					local_asset_id,
					&Pallet::<T>::pallet_account(),
					&beneficiary,
					amount.into(),
					Preservation::Expendable,
				)
				.map_err(|e| HftError::TransferFailed(e.into()))?;
			} else {
				<T as Config>::Assets::mint_into(local_asset_id, &beneficiary, amount.into())
					.map_err(|e| HftError::MintFailed(e.into()))?;
			}
		}
