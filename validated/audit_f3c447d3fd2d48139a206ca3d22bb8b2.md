Based on my research, I found a strong Aptos-native analog to this bug class in the `swap::liquidity_pool` example module, where LP token fee accounting depends on a custom transfer wrapper that is not enforced by the underlying fungible-asset primitives.

### Title
Unenforced LP-token transfer wrapper allows bypass of fee-accounting hook, corrupting fee custody between LPs - (File: `aptos-move/move-examples/swap/sources/liquidity_pool.move`)

### Summary
The `liquidity_pool` module tracks swap-fee entitlement per LP based on their LP-token balance, using a "last known total fees" checkpoint (`total_fees_at_last_claim_1/2`) that must be updated via `update_claimable_fees` whenever an LP's balance changes [1](#0-0) . The only balance-changing entry points that call this update are `mint`, `burn`, and the module's own `transfer` function [2](#0-1) . The module's own doc comment admits this is a soft convention, not an enforced invariant: "fungible_asset::transfer and primary_fungible_store::transfer are not supported" for LP tokens [3](#0-2) . This is the exact bug class from the report: value (LP-token ownership) can change hands through a path that does not trigger the reward/fee "claim-on-transfer" hook.

### Finding Description
`update_claimable_fees` computes each holder's claimable share as `(current_total_fees - total_fees_at_last_claim) * lp_balance / lp_token_total_supply` [4](#0-3) . This calculation is only correct if it is called immediately before every balance change for both the sender and receiver, which is exactly what the module's `transfer` function does [5](#0-4) .

However, LP tokens are ordinary fungible assets held in a `FungibleStore` created via `fungible_asset`/`object` primitives [6](#0-5) , and nothing in the constructor registers dispatchable withdraw/deposit hooks (`dispatchable_fungible_asset::register_dispatch_functions`) for the LP token metadata, unlike other examples in the codebase such as `fa_coin` and `usdk` which explicitly override `deposit`/`withdraw` to enforce policy on every transfer [7](#0-6) . Without such hooks, or without the LP store being frozen so only `transfer_ref`-gated paths work, an LP-token owner (or anyone controlling the store) can call the generic `fungible_asset::transfer` / `primary_fungible_store::transfer` directly on the LP token store, changing balances without ever invoking `update_claimable_fees`.

This breaks the custody invariant that "fee entitlement must be checkpointed at the moment of ownership change." A stale checkpoint means a subsequent call to `update_claimable_fees` (triggered later by the *new* holder calling `mint`/`burn`/the wrapper `transfer`) will attribute the entire fee delta since the *old* holder's last checkpoint to the new holder's *current* balance — effectively minting claimable-fee credit for value the new holder never held, while the old holder's rightful fee accrual up to the transfer point is permanently lost (since their `claimable` snapshot was never flushed and their balance is now zero, freezing their entitlement).

### Impact Explanation
This corrupts the fee-custody accounting for a liquidity pool: fees rightfully accrued to one LP can be silently reassigned to another address that did not hold the LP tokens during the accrual period, and the original holder's unclaimed fee entitlement becomes permanently unrecoverable once their balance moves to zero. Since `claimable_1`/`claimable_2` amounts are ultimately backed 1:1 by real fungible-asset reserves in `fees_store_1`/`fees_store_2` and are withdrawn via `claim_fees` using the module's own signer authority [8](#0-7) , this is a direct misdirection of custodied value between users — not merely a display/event bug.

### Likelihood Explanation
This requires no privileged access; it is a naturally reachable path for any LP holder who uses the standard, generic fungible-asset transfer functions instead of the module-specific wrapper — behavior a typical user or an unaware integrator (wallet, DEX aggregator, or another dApp autocompleting fungible-asset transfers generically) would exhibit by default. I was unable to fully verify within the available context whether the LP token store is frozen via `TransferRef`-only gating (which would force all transfers through `deposit_with_ref`/`withdraw_with_ref` and effectively block the generic path) — I could not locate a `set_frozen` call or dispatch-function registration for the LP token metadata in this file. If the store is left unfrozen and undispatched, as the evidence suggests, the bypass is trivially reachable by any holder.

### Recommendation
Enforce, rather than merely document, that LP token transfers cannot bypass the fee-accounting checkpoint:
- Freeze the underlying LP `FungibleStore` (mark all created LP stores as frozen at creation using the pool's `TransferRef`), forcing every balance change to go through `deposit_with_ref`/`withdraw_with_ref`, which are only reachable via this module's `transfer`/`mint`/`burn`.
- Alternatively, register `dispatchable_fungible_asset::register_dispatch_functions` on the LP token metadata with custom `withdraw`/`deposit` functions that call `update_claimable_fees` for both parties before adjusting balances, mirroring the pattern in `fa_coin`/`usdk`.

### Proof of Concept
1. Pool has accrued `total_fees_1 = 1000` since inception; LP Alice holds the entire LP-token supply and has never claimed, so her `total_fees_at_last_claim_1 = 0`.
2. Alice calls generic `fungible_asset::transfer` (or `primary_fungible_store::transfer`) to send all her LP tokens to Bob, bypassing `liquidity_pool::transfer` and thus never calling `update_claimable_fees`.
3. Bob (now holding 100% of LP supply) calls `liquidity_pool::mint` (adding a small amount of liquidity), which invokes `update_claimable_fees(bob, pool)` [9](#0-8) .
4. Since Bob has no prior checkpoint (`total_fees_at_last_claim_1` defaults via `smart_table::borrow`, or is seeded at 0 on first touch), the calculation attributes the full `delta_1 = 1000 - 0 = 1000` to Bob's current (100%) balance, crediting Bob with `claimable_1 = 1000`, fees Alice actually earned.
5. Alice's own `claimable_1`/checkpoint was never flushed before her balance went to zero, so she has no path to reclaim the 1000 units — they are custodied to the wrong holder, with no separate compensating loss anywhere else in the pool (the fee reserve is depleted paying Bob).

```text
    /// Calculate and update the latest amount of fees claimable by the given LP.
    public entry fun update_claimable_fees(lp: address, pool: Object<LiquidityPool>) acquires FeesAccounting {
        let fees_accounting = unchecked_mut_fees_accounting(&pool);
        let current_total_fees_1 = fees_accounting.total_fees_1;
        let current_total_fees_2 = fees_accounting.total_fees_2;
        let lp_balance = (primary_fungible_store::balance(lp, pool) as u128);
        let lp_token_total_supply = lp_token_supply(pool);
        // Calculate and update the amount of fees this LP token store is entitled to, taking into account the last
        // time they claimed.
        if (lp_balance > 0) {
            let last_total_fees_1 = *smart_table::borrow(&fees_accounting.total_fees_at_last_claim_1, lp);
            let last_total_fees_2 = *smart_table::borrow(&fees_accounting.total_fees_at_last_claim_2, lp);
            let delta_1 = current_total_fees_1 - last_total_fees_1;
            let delta_2 = current_total_fees_2 - last_total_fees_2;
            let claimable_1 = math128::mul_div(delta_1, lp_balance, lp_token_total_supply);
            let claimable_2 = math128::mul_div(delta_2, lp_balance, lp_token_total_supply);
            if (claimable_1 > 0) {
                let old_claimable_1 = smart_table::borrow_mut_with_default(&mut fees_accounting.claimable_1, lp, 0);
                *old_claimable_1 = *old_claimable_1 + claimable_1;
            };
            if (claimable_2 > 0) {
                let old_claimable_2 = smart_table::borrow_mut_with_default(&mut fees_accounting.claimable_2, lp, 0);
                *old_claimable_2 = *old_claimable_2 + claimable_2;
            };
        };

        smart_table::upsert(&mut fees_accounting.total_fees_at_last_claim_1, lp, current_total_fees_1);
        smart_table::upsert(&mut fees_accounting.total_fees_at_last_claim_2, lp, current_total_fees_2);
```

```text
    public(friend) fun claim_fees(
        lp: &signer,
        pool: Object<LiquidityPool>,
    ): (FungibleAsset, FungibleAsset) acquires FeesAccounting, LiquidityPool {
        let lp_address = signer::address_of(lp);
        update_claimable_fees(lp_address, pool);

        let pool_data = liquidity_pool_data(&pool);
        let fees_accounting = unchecked_mut_fees_accounting(&pool);
        let claimable_1 = if (smart_table::contains(&fees_accounting.claimable_1, lp_address)) {
            smart_table::remove(&mut fees_accounting.claimable_1, lp_address)
        } else {
            0
        };
        let claimable_2 = if (smart_table::contains(&fees_accounting.claimable_2, lp_address)) {
            smart_table::remove(&mut fees_accounting.claimable_2, lp_address)
        } else {
            0
        };
        let swap_signer = &package_manager::get_signer();
        let fees_1 = if (claimable_1 > 0) {
            fungible_asset::withdraw(swap_signer, pool_data.fees_store_1, (claimable_1 as u64))
        } else {
            fungible_asset::zero(fungible_asset::store_metadata(pool_data.fees_store_1))
        };
        let fees_2 = if (claimable_2 > 0) {
            fungible_asset::withdraw(swap_signer, pool_data.fees_store_2, (claimable_2 as u64))
        } else {
            fungible_asset::zero(fungible_asset::store_metadata(pool_data.fees_store_2))
        };
        (fees_1, fees_2)
    }
```
