## Analysis

This is a strong analog to the "DoS for Start" bug class: an invariant check that gates a **legitimate, permissionless state-advancing action** can be permanently blocked by an economically-exhaustible precondition (treasury balance), causing the route that delivers cross-chain messages to seize up.

### Title
Unpayable prover reward permanently halts new outbound message proofs (route DoS) - (`modules/pallets/beefy-consensus-proofs/src/lib.rs`)

### Summary
`pallet-beefy-consensus-proofs::settle_first_proof` pays a `$BRIDGE` reward from the treasury to the prover who submits the first valid proof advancing Hyperbridge's proven parachain height. For **messaging proofs** (proofs that advance state due to new cross-chain message dispatches, not an authority-set rotation), the code deliberately propagates `RewardTransferFailed` as a hard error, which reverts the entire extrinsic — including the state-machine-commitment advance that lets `pallet-ismp` (and downstream relayers) see the new messages exist. Once the treasury balance drops below `ProofReward`, **every** subsequent messaging proof submission reverts identically, and the parachain height used to prove outbound messages can never advance again until governance intervenes.

### Finding Description
`pay_position_reward` transfers `ProofReward` from the treasury `PalletId` account to the submitter and returns `Err(Error::<T>::RewardTransferFailed)` on failure: [1](#0-0) 

`settle_first_proof` explicitly treats rotation-proof reward failures as recoverable (logs and continues, preserving the already-applied authority-set rotation), but keeps the hard error for the non-rotation (messaging) case: [2](#0-1) 

The pallet's own test documents this exact asymmetry and its consequence — a messaging proof "must still fail hard when the reward cannot be paid": [3](#0-2) 

Because FRAME dispatchables are wrapped in an implicit storage transaction, an `Err` return unwinds *all* storage mutations performed by `do_submit_proof`/`verify_and_apply` for that call, including the `pallet_ismp` state-machine-commitment update that represents "new messages are now provable." `submit_proof` is a permissionless, signed extrinsic reachable by anyone: [4](#0-3) 

Reward payouts are entirely a function of ordinary protocol operation — every accepted first-proof (rotation or messaging) drains `ProofReward` (and uncle-curve fractions) from the treasury with no automatic refill mechanism visible in this module: [5](#0-4) 

This mirrors the reported bug class precisely: an unprivileged/permissionless flow (prover proof submission, analogous to deposits/withdrawals before `start()`) steadily consumes a shared resource (treasury balance, analogous to tranche ratios) that a later, otherwise-valid operation (advancing the messaging proof height, analogous to `StructuredPortfolio.start()`) depends on passing a check against. Once the resource is exhausted, the dependent operation reverts every time it is attempted.

### Impact Explanation
Once the treasury balance falls below the configured `ProofReward`, no new messaging proof can be accepted. Since `MessagingProofs`/`ProofContext`/`AcceptedProvers` and the underlying `pallet_ismp` state-machine-commitment for Hyperbridge's own height only advance via a successful `settle_first_proof`, this permanently freezes the discovery/provability of any newly dispatched outbound ISMP requests — i.e., "a route unable to deliver messages," until an `AdminOrigin` either tops up the treasury or lowers `ProofReward` via `set_proof_reward`. Rotation (authority-set) proofs remain unaffected because that path explicitly swallows the payment failure, so the asymmetry itself confirms the messaging path was a deliberate, but exploitable/fragile, design choice.

### Likelihood Explanation
No attacker action is even required — normal, expected operation (rewarding provers for every accepted proof) monotonically drains the treasury. Any prover (permissionless) can also accelerate the drain by chasing uncle-reward slots on every height. Once the balance dips below `ProofReward`, the condition self-perpetuates: every messaging-proof submitter observes the same revert, and there is no way to "pay less" or skip the reward from an unprivileged transaction — only governance can recover it. This makes the likelihood of eventually triggering the DoS effectively certain absent active treasury monitoring/replenishment, and trivially acceleratable by a motivated party.

### Recommendation
Apply the same non-blocking treatment used for rotation proofs to the messaging-proof path: on `RewardTransferFailed`, log and continue (skip the reward, mark `reward_paid = 0`) rather than propagating a hard error that rolls back the state-commitment advance. Alternatively, decouple reward payment from proof acceptance entirely (e.g., accrue an IOU/claimable balance rather than an inline transfer), so treasury insolvency can never block the liveness-critical act of advancing the proven height.

### Proof of Concept
1. Deploy/observe `pallet-beefy-consensus-proofs` with `ProofReward` set to a non-zero value and a treasury balance that is nonzero but insufficient to cover `ProofReward` (this state is reachable simply by draining the treasury via ordinary prior reward payouts, or by governance lowering the treasury without lowering `ProofReward` in lockstep).
2. Dispatch cross-chain messages so that `pallet-ismp`'s child-trie `RequestCommitments` root advances (`has_new_messages = true`).
3. A prover submits a valid `submit_proof` extrinsic whose outcome is `!outcome.rotated` (a pure messaging advance, no authority-set rotation).
4. `settle_first_proof` calls `pay_position_reward`, which fails with `RewardTransferFailed` because the treasury cannot cover `ProofReward`; this error is propagated (not swallowed), reverting the whole extrinsic per the test `an_unpayable_reward_cannot_block_a_rotation`'s explicit assertion (`"a messaging proof must still fail hard when the reward cannot be paid"`).
5. Every subsequent honest prover hits the identical revert until governance intervenes — the height for provable outbound messages never advances, freezing the route. [6](#0-5)

/// Same hazard, different source: an unpayable reward. `pay_position_reward` runs after the
/// caller has applied the rotation, so propagating `RewardTransferFailed` rolls it back — and
/// since the mandatory justification is the only one obtainable for that session, every retry
/// fails identically until the treasury is topped up, leaving consensus on the old set. The
/// reward is the cheaper thing to drop. Messaging proofs deliberately keep the hard error.
#[test]
fn an_unpayable_reward_cannot_block_a_rotation() {
	let mut ext = new_test_ext();
	let height = 800u64;

	ext.execute_with(|| {
		// The BEEFY proofs treasury holds nothing in genesis, so any non-zero reward makes the
		// transfer fail with `RewardTransferFailed`.
		ProofReward::<Test>::put(1_000_000u128);

		pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
			submitter(11),
			vec![PROOF_TYPE_SP1, 0xab],
			Some(H256::repeat_byte(11)),
			PROOF_TYPE_SP1,
			Vec::new(),
			rotation_outcome(height, 30),
		)
		.expect("an unpayable reward must not reject the rotation");

		assert_eq!(
			RotationProofs::<Test>::get().get(&30).copied(),
			Some(height),
			"the rotation must be recorded even though the reward could not be paid",
		);

		// The asymmetry is deliberate: reverting a messaging proof is recoverable, because the
		// next proof re-attempts the same work once the treasury can pay.
		assert!(
			pallet_beefy_consensus_proofs::Pallet::<Test>::settle_first_proof(
				submitter(12),
				vec![PROOF_TYPE_SP1, 0xac],
				Some(H256::repeat_byte(12)),
				PROOF_TYPE_SP1,
				Vec::new(),
				messaging_outcome(height + 1, 30),
			)
			.is_err(),
			"a messaging proof must still fail hard when the reward cannot be paid",
		);
