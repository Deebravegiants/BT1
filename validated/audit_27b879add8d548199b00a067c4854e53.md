### Title
Unhedged fee-on-transfer accounting in `IntentGatewayV2.placeOrder` (Tron build) causes escrow insolvency - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal `_orders` escrow ledger using the user-declared, protocol-fee-reduced input amount rather than the amount the contract actually receives via `safeTransferFrom`. For any input token that charges a fee on transfer, the contract's real token balance will be lower than the amount recorded in escrow, exactly the bug class described in the referenced report.

### Finding Description
In `placeOrder` (no-predispatch path), the contract calls: [1](#0-0) 
which does `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally increments `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from the caller-supplied `order.inputs[i].amount` minus the protocol fee, computed *before* any transfer occurs: [2](#0-1) 

No balance-before/after check is performed on the receiving contract (`address(this)`) for this branch. If the input token deducts a transfer fee (e.g., a USDT-style fee toggle), the gateway will hold strictly less of that token than what `_orders[commitment][token]` claims is escrowed.

The predispatch branch is only partially better: it checks `IERC20(token).balanceOf(dispatcher)` before sweeping from the intermediate `dispatcher` to the gateway, but still credits escrow with `reducedInputs[i].amount` (again based on the caller's original declared amount) rather than what `address(this)` actually receives from the dispatcher-to-gateway leg: [3](#0-2) 
This second leg is itself a `transfer` call that can be taxed again by a fee-on-transfer token, so the final gateway balance can be lower still than what is credited.

This is precisely the report's bug class: `safeTransferFrom`/`transfer` are relied upon to deliver the full nominal amount, with no post-transfer balance verification, so any calculation depending on the "amount received" (here, the escrow ledger `_orders`) can diverge from the contract's actual custodied balance.

Notably, the mainline EVM contract (`evm/src/apps/IntentGatewayV2.sol`) was hardened against exactly this scenario — it snapshots balances before/after each transfer and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment and crediting escrow: [4](#0-3) [5](#0-4) 
The Tron fork of the contract does not carry this fix.

### Impact Explanation
Because `_orders[commitment][token]` overstates the gateway's real token balance, downstream fulfillment/refund/cancellation logic that pays out based on this ledger can attempt to transfer more tokens than the contract holds for that token. Depending on how the escrow ledger is drawn down across multiple concurrent orders (shared per-token accounting), this can starve later legitimate claimants of their rightful escrow — a "last one out gets nothing" insolvency — or allow a specific claimant to be paid using tokens that are actually still owed to a different user's order, i.e. socialized loss / fund freezing for other order participants. This satisfies the "permanent freezing of funds" / unsound accounting bar from the validation criteria.

### Likelihood Explanation
This is directly reachable by any unprivileged user in a single transaction: simply calling `placeOrder` with a fee-on-transfer ERC20 as an input asset. No special privileges, governance, or malicious relayer/collator involvement is required — it only requires that the deployment accepts an input token that charges a transfer fee (a property of the token itself, not of any privileged actor), matching the exact precondition in the original report (e.g., USDT's dormant fee switch).

### Recommendation
Apply the same fix already implemented in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: measure `balanceOf(address(this))` before and after each `safeTransferFrom`/sweep `transfer`, use the actual delta as the amount credited to `_orders` and as the basis for the protocol-fee deduction and commitment hash, for both the direct-transfer and predispatch code paths.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and register a fee-on-transfer ERC20 (e.g., 1% fee) as a valid input token.
2. User calls `placeOrder` with `inputs[0].amount = 1000e18` of the fee-on-transfer token; the contract's `safeTransferFrom` only delivers `990e18` to the contract (`evm/tron/contracts/apps/IntentGatewayV2.sol:459`), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` computed from the full `1000e18` (minus only the protocol fee), e.g. `997e18` at 0.3% protocol fee (`evm/tron/contracts/apps/IntentGatewayV2.sol:463`).
3. The gateway's actual token balance (`990e18`) is now less than the sum of what is recorded as escrowed for outstanding orders (`997e18`+ across orders), so a later solver fill/withdrawal/cancellation against this or another order's escrow entry for the same token will fail or drain the escrow at another order's expense once balances are compared/depleted — an accounting mismatch consistent with the referenced bug class, mirrored by the fee-on-transfer regression tests already present for the (fixed) mainline contract at `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2440-2494`, which the Tron contract has no equivalent protection for.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
