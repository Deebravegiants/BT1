## #Vulnerability found for this question.

### Title
Non-embedded session identifier is a predictable, unsigned value derived directly from the shop domain, enabling cross-tenant session hijacking - (File: `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps (and as a fallback for embedded apps without a JWT), `ShopifyAPI::Utils::SessionUtils.current_session_id` treats the raw, unsigned `shopify_app_session` cookie value as the trusted session identifier used to retrieve a previously-stored, already-authorized merchant `Session` (including its access token) from the host app's `SessionRepository` — exactly as documented in `docs/usage/oauth.md`. The cookie's value is set by `ShopifyAPI::Auth::Oauth.validate_auth_callback` to `session.id`, which for offline sessions is the fully deterministic string `"offline_#{shop}"`, and for online sessions `"#{shop}_#{associated_user.id}"`. Because this value carries no cryptographic binding (no HMAC/signature) to the browser that completed OAuth, any unprivileged internet user who knows or guesses a target shop's `myshopify.com` domain (public information) can present the same value as their own cookie/session identifier and, per the gem's own documented session-lookup pattern, be treated as that merchant's authenticated session.

### Finding Description
The identity binding that should hold is: `cookie bearer == entity that legitimately owns the session with this id`. Instead the code checks: `cookie bytes == session.id string`, with `session.id` fully derivable from public data.

- `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser cookie to the bare `session.id` for non-embedded flows: [1](#0-0) 

- `Session.from` computes `id` deterministically from public inputs — the shop domain and (for online sessions) the associated user id returned by Shopify: [2](#0-1) 

- `SessionUtils.current_session_id` and `cookie_session_id` take the cookie header value verbatim as the session key, without any signature or MAC check: [3](#0-2) [4](#0-3) 

- `offline_session_id`/`jwt_session_id` show the exact deterministic format an attacker needs to reproduce: [5](#0-4) 

- The gem's own documentation instructs host apps to store the returned `Session` and to use the cookie value to key that storage — meaning any app following the documented pattern is exposed: [6](#0-5) 

Unlike the embedded/JWT path — where `JwtPayload` cryptographically verifies `dest`/`aud` via `JWT.decode` with the app's secret before deriving a session id (see `lib/shopify_api/auth/jwt_payload.rb:24-45`) — the cookie-based path derives the trusted session key straight from unauthenticated bytes supplied in the request, with no signature over `shop` (or `shop_user-id`) tying it to the browser that actually completed OAuth for that shop.

### Impact Explanation
This breaks the "session id derived from unauthenticated bytes" binding explicitly in scope. Any unprivileged user who knows a target's `.myshopify.com` domain can construct the cookie value `offline_{shop}` (or `{shop}_{user_id}` if a user id is known/guessed) and submit it to the host app's backend. If the host app implements session persistence exactly as documented by this gem (i.e., keys its `SessionRepository` by this session id), the attacker is handed the merchant's previously stored `Session`, including its `access_token`, `refresh_token`, and scopes — resulting in cross-tenant access and theft of a merchant access token, which meets the Critical impact bar.

### Likelihood Explanation
Exploitation requires only knowledge of the target's Shopify domain, which is typically public (visible in storefront URLs, app listings, etc.), and no possession of `api_secret_key`, tokens, or other privileged material. It requires the host app to have adopted the documented cookie/session-id storage pattern from `docs/usage/oauth.md`, which is the officially recommended usage for non-embedded (authorization code grant) apps, making this a realistic and directly reachable path through the gem's own designed API.

### Recommendation
Do not use the bare, deterministic `session.id` as the browser-facing cookie value. Instead, issue an unguessable, cryptographically random session token (unrelated to shop/user id) that the host app maps internally to the real session id, or sign/HMAC the cookie value (binding it to shop, expiry, and a server-side secret) so it cannot be forged or replayed by a party who only knows the shop domain.

### Proof of Concept
1. Note that shop domains are public (e.g., `victim-shop.myshopify.com`).
2. As an unauthenticated attacker, send a request to the target app's authenticated endpoint with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. A host app implementing the gem's documented pattern (`SessionUtils.current_session_id` → `SessionRepository.load_session(id)`) resolves this to the merchant's previously persisted `Session`, exposing its `access_token` for use in subsequent authenticated API calls made on the attacker's behalf.
