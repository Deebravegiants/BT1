### Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `Registry.process` uses the separate, HMAC-unauthenticated `shop` header to populate `WebhookMetadata#shop`, which is the value the gem's own documentation instructs host apps to trust as the webhook's tenant identity.

### Finding Description
`Utils::HmacValidator.validate` verifies that `HMAC(secret, signable_string) == received_hmac` [1](#0-0) . For webhooks, `signable_string` is defined as just `@raw_body` [2](#0-1) , so the `shop` accessor — sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header — is never part of the signed bytes [3](#0-2) .

`Registry.process` validates the HMAC over the body only, then forwards the unauthenticated `request.shop` straight into `WebhookMetadata` for the app's handler [4](#0-3) . The identity binding that should hold is: `hmac-verified bytes == bytes that determine tenant (shop)`. In reality, `hmac-verified bytes = raw_body` while `tenant-determining bytes = shop header`, which are disjoint — breaking that equality.

The gem's own docs instruct handlers to treat `data.shop` as authoritative shop identity and use it directly for shop-scoped actions (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) , and `WebhookMetadata#shop` is documented as "The shop domain of the webhook" [6](#0-5) .

### Impact Explanation
Because the same `api_secret_key` (the app's `client_secret`) is shared across every shop that installs the app, any unprivileged user who installs the app on their own shop can trigger a legitimate webhook to themselves and obtain a validly HMAC-signed `(raw_body, hmac)` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still passes (it only checks the body), and the handler receives `data.shop` equal to the forged victim domain. Any host app following the documented pattern will process, store, or act on data (e.g., enqueue jobs, update per-shop records, invalidate caches) under the wrong tenant's identity — a cross-tenant confusion/data-integrity issue reachable without any access token, `client_secret` knowledge, or privileged account, satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is moderate-to-high: no secret material is required beyond what any shop owner can obtain by installing the app and receiving their own webhook; only header manipulation on replay is needed, which is trivial for any user capable of sending raw HTTP requests.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload, so that the HMAC check fails if any of these header values are altered independently of the body.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` sent by Shopify to the app's webhook endpoint.
2. Replay a new HTTP request to the same webhook endpoint with the identical body `B` and identical `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds [7](#0-6) .
4. The handler receives `WebhookMetadata#shop == "victim.myshopify.com"` even though the body content is the attacker's own shop data, causing the host app to associate/process the attacker's webhook payload under the victim shop's tenant context.
