Audit Report

## Title
View-role users can read External Initiator `OutgoingToken` secrets via unrestricted `GET /v2/external_initiators` - (File: core/web/router.go)

## Summary
The `GET /v2/external_initiators` route is registered without any role-based middleware, while the sibling `Create`/`Destroy` routes on the same resource require `auth.RequiresEditRole`. As a result, any authenticated user — even one with the lowest-privilege `view` role — can call the endpoint and receive the `OutgoingToken` secret for every configured External Initiator in the response body.

## Finding Description
`authv2.GET("/external_initiators", paginatedRequest(eia.Index))` is registered with only base session authentication, unlike `POST`/`DELETE` on the same path which are wrapped in `auth.RequiresEditRole` [1](#0-0) . The `Index` handler queries all external initiators and converts each into a `presenters.ExternalInitiatorResource` [2](#0-1) , which includes the `OutgoingToken` field copied verbatim from the stored entity `ei.OutgoingToken` [3](#0-2) . `OutgoingToken` is a secret the node uses to authenticate itself to the external initiator's webhook, stored alongside `outgoing_secret`/`outgoing_token` columns in the DB schema. The `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` middleware exists and is correctly applied elsewhere (e.g. `Create`/`Destroy`), but is simply absent from the `Index` route, so the general session-auth check is the only gate — insufficient to protect this secret-bearing response.

## Impact Explanation
This is a credential/secret exfiltration vulnerability: a `view`-role user, whose role is intended for read-only/non-sensitive dashboard access, can extract `OutgoingToken` for every configured external initiator. This token can be used to forge/replay traffic that impersonates the node when calling the external initiator, an authentication/secret-disclosure impact squarely in scope for the Chainlink bounty's "key/secret exfiltration" and "node API authentication/role bypass" categories.

## Likelihood Explanation
High likelihood and trivial to exploit: it requires only a valid low-privilege (`view`-role) authenticated API session, with no additional preconditions, admin action, or unusual configuration. This is corroborated by the RBAC test matrix, which explicitly documents and asserts that this route is reachable with `view` role (`viewOnlyAllowed: true`) [4](#0-3) , and by the functional test confirming `OutgoingToken` is present in `Index` responses [5](#0-4) .

## Recommendation
Gate the `Index` route with at least `auth.RequiresEditRole` (or `RequiresRunRole`) to match the sensitivity of the data it returns, consistent with `Create`/`Destroy` on the same resource:
```go
authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```
Alternatively/additionally, strip `OutgoingToken` (and any other secret) from `ExternalInitiatorResource` for listing purposes, exposing it only once at creation time via `ExternalInitiatorAuthentication`, mirroring how the incoming `Secret` is never re-exposed after creation.

## Proof of Concept
1. As an admin, create an External Initiator: `POST /v2/external_initiators {"name":"foo","url":"http://example.com"}`; note the one-time `outgoingToken` in the response.
2. Create a low-privilege API user with role `view`.
3. As the `view` user, call `GET /v2/external_initiators`.
4. Observe the JSON response includes `outgoingToken` for `foo` and all other configured initiators, confirming secret disclosure to a role that should have no access to it. This can also be directly validated by adding an assertion in `core/web/external_initiators_controller_test.go` performing the `Index` request with a `view`-role session and asserting `OutgoingToken` is present (mirroring the existing non-role-scoped assertions at lines 105-126).
