**Analysis:**

The premise that `StructTag::try_from` could be "more permissive than on-chain struct registration" for unicode-normalized or case-variant names does not hold in this codebase.

Move identifiers (module and struct names) are validated through `move_core_types::identifier::Identifier::is_valid`, which restricts characters to ASCII `a-z`, `A-Z`, `0-9`, `_`, `$` only [1](#0-0) [2](#0-1) . There is no Unicode normalization step anywhere — non-ASCII bytes are rejected outright, so homoglyph/Unicode-lookalike attacks are impossible by construction. The doc comments explicitly note that "Allowed identifiers are currently restricted to ASCII due to unresolved issues with Unicode normalization" [3](#0-2) .

This exact same `Identifier::new`/`is_valid` validation is used both for on-chain module/struct registration in the Move VM and for parsing the API's `resource_type` path parameter (`MoveStructTag::verify` calls `verify_module_identifier`/`verify_identifier`, which wrap the same `is_valid` check) [4](#0-3) [5](#0-4) . There is no separate, more permissive validation path for the API — `verify` and on-chain registration share the identical character set and are case-sensitive with no folding.

Furthermore, `StateApi::resource` converts the `MoveStructTag` into a `StructTag` via `TryFrom<&MoveStructTag> for StructTag`, which copies the address, module, and name fields byte-for-byte with no normalization [6](#0-5) , and then calls `find_resource` with that exact tag [7](#0-6) . The on-chain storage key (`access_vector`) is the BCS-serialized bytes of the full `StructTag` (address + module identifier + name identifier + type args) [8](#0-7) , so lookups require an exact byte-for-byte match — two structs differing by even a single case-varied character produce entirely different `Identifier` byte sequences and thus entirely different storage keys with zero possibility of collision or conflation.

Since (1) identifiers are ASCII-only with no normalization, (2) the same strict validation applies at both API input and on-chain registration, and (3) resource lookup keys are exact BCS byte matches, there is no mechanism by which an attacker-controlled `resource_type` string could cause the API to return a lookalike struct's data under a different struct's identity. This finding does not cross a custody boundary and is rejected per the decision standard.

pub const fn is_valid(s: &str) -> bool {
    // Rust const fn's don't currently support slicing or indexing &str's, so we
    // have to operate on the underlying byte slice. This is not a problem as
    // valid identifiers are (currently) ASCII-only.
    let b = s.as_bytes();
    match b {
        b"<SELF>" => true,
        [b'<', b'S', b'E', b'L', b'F', b'>', b'_', ..] if b.len() > 7 => all_bytes_numeric(b, 7),
        [b'a'..=b'z', ..] | [b'A'..=b'Z', ..] => all_bytes_valid(b, 1),
        [b'_', ..] | [b'$', ..] if b.len() > 1 => all_bytes_valid(b, 1),
        _ => false,
    }
}
