[1](#0-0) ### Title
Untrusted swap routes can poison the caller’s authorization tree and steal unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
High. `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept caller-supplied opaque route bytes and forward them to the configured router without inspecting which contracts the route invokes. [2](#0-1)  A crafted route can place a malicious venue below the controller call and add an unrelated token transfer as a child of the victim’s signed authorization tree. [3](#0-2) 

### Finding Description
`swap_collateral` exposes a `swap: Bytes` argument supplied by the caller. [4](#0-3)  After `caller.require_auth()` and account-owner/delegate validation, the route is forwarded into the collateral withdrawal-and-swap path. [5](#0-4) [6](#0-5) 

At the router boundary, `swap_tokens` checks only that the encoded route is non-empty, authorizes one exact input-token transfer from the controller to the configured router, and executes the supplied payload. [7](#0-6)  The post-call checks measure only the controller’s input spend and output receipt; they do not constrain contracts deeper in the route or unrelated transfers added to the caller’s authorization tree. [8](#0-7) 

The helper’s “no further sub-invocations” bound applies only to the controller’s invoker-contract authorization for `token_in.transfer(controller, router, amount_in)`. [9](#0-8)  It does not prevent malicious route-selected code below the router from requesting the victim account’s authorization for a different token transfer, which transaction simulation can materialize as another child beneath the victim’s controller invocation. [3](#0-2) 

### Impact Explanation
A victim who submits a malicious route and signs the simulated authorization tree can lose arbitrary unrelated wallet tokens to the attacker while still receiving a valid-looking swap output. [8](#0-7)  The subsequent deposit and final risk checks can still pass because they validate the account’s resulting collateral position, not unrelated transfers embedded in the authorization tree. [10](#0-9) [11](#0-10)  This is direct theft of user funds beyond the routed collateral amount.

### Likelihood Explanation
An unprivileged attacker can deploy a contract implementing the expected venue interface, fund it sufficiently to produce the expected output token, and encode a route that selects it. [3](#0-2)  Exploitation requires the victim to use that route and sign the poisoned simulated authorization tree, so it is not fully autonomous; however, opaque route bytes make unexpected venue contracts and extra child authorizations difficult for ordinary clients to detect. [12](#0-11) 

### Recommendation
Constrain routes to governance-approved venue, pool, and token contracts before execution rather than allowing arbitrary route-selected contracts under the user’s signed invocation. [7](#0-6)  If arbitrary routing is retained, clients must decode the full route and reject any authorization tree containing calls other than the expected strategy invocation and intended token movement. [9](#0-8) 

### Proof of Concept
1. The attacker deploys a malicious venue contract implementing the expected pool calls. During its swap call, it also invokes `token.transfer(victim, attacker, victim_balance)` for an unrelated wallet token. [3](#0-2) 
2. The attacker funds the venue with enough `token_out` to satisfy the expected swap output and constructs a `swap: Bytes` route that selects the malicious venue. [12](#0-11) 
3. The victim invokes `swap_collateral(caller=victim, account_id, current=USDC_key, amount, new=ETH_key, swap=malicious_route)`. [4](#0-3) 
4. The controller authenticates the victim, withdraws the requested collateral, grants only the intended controller-to-router input transfer, and invokes the configured router with the attacker’s route. [6](#0-5) [13](#0-12) 
5. During the malicious venue call, the unrelated token transfer requests victim authorization; simulation adds that transfer as a child of the victim’s `swap_collateral` authorization. [3](#0-2) 
6. If the victim signs the simulated tree, the attacker receives the unrelated wallet tokens while the venue can still return enough output for the controller’s balance checks and final risk validation to succeed. [8](#0-7) [10](#0-9)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```
