### Title
Cross-tenant webhook spoofing via unauthenticated `shop-domain` header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` binds only the raw request body, not the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, or `X-Shopify-Api-Version` headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (and `request.topic`) as authenticated tenant identity and passes them straight to the app's `WebhookHandler`, which the gem's own documentation instructs developers to use for shop-scoped processing.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over that signable string [5](#0-4) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight out of request headers with no cryptographic binding to the body or the HMAC at all [2](#0-1) .

`Registry.process` raises only if the HMAC over the body fails; once that check passes it builds `WebhookMetadata` directly from the request's `shop`/`topic`/`webhook_id`/`api_version` accessors and dispatches to the handler [3](#0-2) .

Because Shopify's `client_secret`/`api_secret_key` is shared across every merchant install of a given app, any merchant who has installed the app can obtain a **genuinely, correctly-signed** webhook for their own store (any topic they can trigger, e.g. `orders/create`). Since only the body bytes are covered by the HMAC, that attacker-controlled merchant can resend the exact same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain, and optionally altering `X-Shopify-Topic`/`X-Shopify-Webhook-Id`/`X-Shopify-Api-Version` (none of which the library verifies). `Utils::HmacValidator.validate` still returns `true` because the body/HMAC pair is authentic, but `request.shop` is now attacker-chosen. This breaks the identity binding: `shop authenticated by HMAC == shop used by the handler for tenant-scoped side effects`.

### Impact Explanation
This is a cross-tenant identity confusion: the gem hands the app attacker-controlled tenant identity (`shop`) alongside cryptographically-verified but attacker-controlled body content, letting a low-privileged merchant (any app installer) inject fabricated "verified" webhook events attributed to a victim shop they don't control. Any app that trusts `data.shop` from a processed webhook — exactly as the gem's own documentation instructs (`docs/usage/webhooks.md`) — to look up sessions, update per-shop records, or trigger per-shop business logic can have data written/actioned against the wrong tenant, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any Shopify merchant who has ever installed the app (an "unprivileged internet user" relative to other tenants) can trivially trigger a real webhook to obtain a validly-signed `(body, hmac)` pair, then replay it with a forged `shop-domain`/`topic` header set to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or victim credentials is required — only the attacker's own legitimate webhook traffic and header rewriting.

### Recommendation
Include the header values that identity/routing decisions depend on (`shop-domain`, `topic`, at minimum) in the HMAC-signed material, or independently verify that the `shop-domain` header corresponds to a shop for which the app holds a valid, previously-established session/webhook registration before dispatching to handlers. At minimum, document prominently (and enforce in the gem) that `WebhookMetadata#shop`/`#topic` are unauthenticated and must be cross-checked by the app against known installed shops before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a real webhook event (e.g., updates an order), causing Shopify to POST a correctly HMAC-signed webhook to the app's callback URL with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker intercepts/replays this exact request to the same endpoint but replaces `X-Shopify-Shop-Domain: attacker.myshopify.com` with `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and header `H` unchanged.
3. Server calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers))`.
4. `Utils::HmacValidator.validate` succeeds because `to_signable_string` only hashes `B`, which is unmodified [6](#0-5) .
5. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, and — following the gem's documented pattern — performs shop-scoped processing (e.g., `perform_later(shop_domain: data.shop, webhook: data.body)`) against the victim tenant using attacker-supplied data [7](#0-6) .
