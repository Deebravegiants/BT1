### Title
Unsanitized `shop` parameter builds the initial OAuth `auth_route` in `Oauth.begin_auth`, allowing redirection of the merchant's browser to an attacker-controlled host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorize-redirect URL by concatenating the raw `shop:` argument directly into `auth_base_uri`, without ever calling `Utils::ShopValidator.sanitize!` on it. Every other OAuth entry point in this gem that accepts a caller-supplied `shop` (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`) does call `ShopValidator.sanitize!` before using the value, making the omission in `begin_auth` an inconsistency and a real defect.

### Finding Description
The binding that should hold is: `auth_base_uri(shop).host ∈ ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (i.e., every character of the host used to build the redirect target must come from a domain sanitized by `ShopValidator.sanitize!`). In `begin_auth`, this equality is never enforced. [1](#0-0) 
constructs `query` (containing `client_id`, `scope`, `redirect_uri`, `state`) and then calls: [2](#0-1) 
`auth_base_uri(shop)` returns `"https://#{shop}/admin"` verbatim — there is no call to `ShopValidator.sanitize!` anywhere in `begin_auth` or `auth_base_uri`.

By contrast, sibling methods that accept `shop:` from the host app do sanitize it, e.g. `TokenExchange.migrate_to_expiring_token`: [3](#0-2) 

Per the documented usage in `docs/usage/oauth.md`, host apps are expected to source `shop` from an inbound request (e.g., a query string or header) and pass it straight into `begin_auth`: [4](#0-3) 

Exploit flow: attacker sends the victim a link to the app's login route with `shop=attacker.com` (or the app reads the header/query value as documented). `begin_auth` builds `auth_route = "https://attacker.com/admin/oauth/authorize?client_id=<api_key>&scope=...&redirect_uri=https://legit-app.com/auth/callback&state=<nonce>&grant_options[]=..."`, sets the `state` cookie in the victim's browser for the legitimate app domain, and the host app performs a 307 redirect to that URL. The victim's browser now sends the app's public `client_id`, requested `scope`, the app's own `redirect_uri`, and the CSRF `state` nonce to `attacker.com` instead of Shopify — none of these values are secret individually, but disclosing `state` to a third party (and the fact the redirect target is attacker-controlled rather than validated) violates the intended invariant that the initial authorize request only ever goes to a Shopify domain.

Existing guards do not prevent this specific step: `HmacValidator.validate` and the `state == auth_query.state` check in `validate_auth_callback` only run later, at callback time, and still require knowledge of `Context.api_secret_key` to forge a passing HMAC — so this bug by itself does not directly hand the attacker a completed, validated session. But it does confirm the exact code-level claim in the question: `auth_base_uri` performs zero validation of `shop`, unlike every other sanitize!-gated method in the gem, which is the concrete, in-scope bug.

### Impact Explanation
The victim's browser is redirected (open-redirect style) to an arbitrary attacker-chosen host with the app's `client_id`, `scope`, `redirect_uri`, and CSRF `state` nonce appended as query parameters, all visible to that host (server logs, `Referer` headers of subsequent navigation from the attacker's page). This breaks the SHOP_BINDING invariant before any HMAC exists, matching the "High: forced-OAuth-completion / session fixation" category referenced in the question, since it is a genuine host-confusion/open-redirect defect in `begin_auth`. It does not by itself yield a fully forged, HMAC-validated callback (that still requires `api_secret_key`), but it is a concrete, reachable bug distinct from and inconsistent with the sanitize-then-build pattern used elsewhere in the gem.

### Likelihood Explanation
Requires only that the host app pass an attacker-influenced `shop` value into `begin_auth` — which is exactly the documented usage pattern shown in `docs/usage/oauth.md` (`shop = request.headers["Shop"]`). No special app configuration, secrets, or privileged access is needed; any unprivileged internet user who can reach the app's login route with a controllable `shop` parameter can trigger it, and it is repeatable against any victim who clicks the crafted link.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the top of `begin_auth` (before constructing `query` or calling `auth_base_uri`), mirroring `TokenExchange.migrate_to_expiring_token`, `ClientCredentials`, and `RefreshToken`, and use the sanitized/returned trusted host for `auth_base_uri` instead of the raw input.

### Proof of Concept
minitest + WebMock/Mocha plan under `test/auth/oauth_test.rb`:
```ruby
def test_begin_auth_rejects_untrusted_shop_host
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", host: "https://my-app.com",
    api_version: "2024-01", is_embedded: false, is_private: false, scope: "read_products")

  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.com", redirect_path: "/callback")
  end
end
```
Assert on both sides of the binding: before the fix, `result[:auth_route]` starts with `"https://attacker.com/admin/oauth/authorize"` (host equality attacker.com == attacker.com, i.e., never checked against `TRUSTED_SHOPIFY_DOMAINS`); after adding `sanitize!`, the same call raises `Errors::InvalidShopError` instead of returning a route pointed at a non-Shopify host.

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
