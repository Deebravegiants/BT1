### Title
Webhook HMAC signature does not bind the shop domain, allowing cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that the handler subsequently acts on are taken from unauthenticated HTTP headers that are never included in the signed content, breaking the binding `verified_bytes == acted_upon_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are populated purely from HTTP headers with no cryptographic linkage to the HMAC: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per `HmacValidator#validate_signature` — computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and never covers headers such as `shop-domain`: [3](#0-2) [4](#0-3) 

Because the signature only binds the body bytes, an attacker who has legitimately observed a valid `(raw_body, hmac)` pair for one shop (e.g., by operating a trial/dev install of the app themselves) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different, victim shop. `HmacValidator.validate` will still succeed because it only checks the body against the signature, and `Registry.process` then dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` populated from the attacker-controlled header: [5](#0-4) 

This is the same class of defect as the reported bug: a value that downstream code treats as authenticated/trusted (`shop`) is not actually covered by the integrity check (`HMAC` over the body only), so `verified(bytes) != acted_upon(shop)`.

### Impact Explanation
Any consumer of `ShopifyAPI::Webhooks::Registry.process` that uses `WebhookMetadata#shop` to select which tenant's data to update, persist, or key by (a standard usage pattern, per this gem's own docs) can be tricked into applying data intended for shop A to shop B's tenant context — a cross-tenant data-integrity breach with no need for the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Exploitation only requires the attacker to possess one legitimately signed `(body, hmac)` pair — trivially obtainable by installing/registering the app on any shop they control (including a free development store) and capturing the webhook the app receives — plus the ability to send an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header. No secret material or privileged access is required, making this reachable by an unprivileged internet user.

### Recommendation
- **Short term:** Include `shop`, `topic`, and `webhook_id` in the signed content validated against the HMAC (or otherwise cryptographically bind the header values used for dispatch to the signature), so that `Registry.process` cannot be fed a genuine signature paired with a spoofed shop/topic.
- **Long term:** Whenever a value is used for authorization or tenant-routing decisions (like `shop`), ensure it is part of the verified payload rather than sourced from an out-of-band, unauthenticated header.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` that Shopify sent.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, exposing `shop == "victim.myshopify.com"`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process/store the attacker's order data under the victim shop's tenant context.
