### Title
Unbounded, unvalidated user-supplied calldata in `CallDispatcher.dispatch()` lets a sender make cross-chain token deliveries permanently unable to complete - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`HyperFungibleToken`/`WrappedHyperFungibleToken` (`onAccept`) and `IntentGatewayV2`/`ExtrinsicIntents` (`_execute`, predispatch) all forward user-controlled, arbitrary `Call[]` payloads to `CallDispatcher.dispatch()` for execution on the destination chain, with no size limit, no gas cap, and no fee/gas-cost adjustment tied to the payload's actual execution cost. This is the direct analog of the TOKI report's "unvalidated external payload / no dynamic gas adjustment" bug class, mapped onto Hyperbridge's own arbitrary-calldata-execution feature.

### Finding Description
`CallDispatcher.dispatch()` decodes an attacker/sender-supplied `bytes` blob into a `Call[]` array and executes each call sequentially with no gas limit and no bound on the number/size of calls: [1](#0-0) 

This is invoked directly from `IApp.onAccept` in the token-bridging apps: [2](#0-1) 

and from the intents settlement path: [3](#0-2) 

The `data`/`call` field is fully attacker-controlled at dispatch time on the source chain (`SendParams.data`, `Order.output.call`, `Order.predispatch.call`) and is never size- or gas-bounded before being relayed and executed on the destination chain: [4](#0-3) 

Because `EvmHost.dispatchIncoming` forwards the message via a raw, unbounded `.call()` to the module's `onAccept` (which in turn unboundedly calls into `CallDispatcher`), and because a failed `onAccept` (including a revert triggered by a failing/expensive nested call) simply deletes the request receipt and returns without reverting the whole handler batch: [5](#0-4) 

a sender can craft `data`/`call` payloads (e.g., deeply nested/loop-heavy calls, or calls into contracts engineered to consume gas up to the effective block-gas ceiling) whose successful execution requires more gas than any economically rational relayer would ever attach. Every relayer attempt then reverts (or the module deliberately reverts, per the documented "if any call reverts the entire `onAccept` reverts" behavior): [6](#0-5) 

Relayer-fee/gas quoting for these flows is either a flat estimate (`HyperFungibleToken.quote()`, `IntentGatewayV2` `RELAYER_MESSAGE_GAS` budget) or a live `eth_estimateGas`/`eth_estimateUserOperationGas` call that has no way to bound or price the true cost of an adversarially-crafted `Call[]` payload chosen by the order/transfer originator: [7](#0-6) 

Since neither `CallDispatcher`, `HyperFungibleToken.onAccept`, nor `IntentsBase._execute` impose a maximum payload size or a gas ceiling/`gasleft()` reservation before invoking the dispatcher, a message whose calldata is engineered to be undeliverable within any realistic gas budget will never succeed, and — per the documented retry semantics — will either time out (funds refunded, no fund loss, but service denial for that message) or, worse, remain permanently stuck if `timeout == 0` was chosen (no timeout set), since no relayer will ever be able to profitably or successfully deliver it.

### Impact Explanation
This matches the "route unable to deliver messages" category explicitly called out as acceptable impact. Concretely:
- A user/solver can dispatch a `HyperFungibleToken.send()` or an `IntentGatewayV2` order whose `data`/`output.call` is deliberately gas-expensive (e.g., recursive/self-referential calls or a target contract designed to burn gas up to the block limit) such that `CallDispatcher.dispatch()` can never complete within any gas budget a relayer is willing to spend.
- With `timeout == 0` (a supported, valid value meaning "never times out"), the message becomes permanently undeliverable — the mint/unlock to the beneficiary never happens and no refund path exists, since timeout-based refund logic never triggers.
- Even when a timeout is set, this is a reliable, cost-asymmetric griefing vector: the attacker pays once to escrow/lock funds, while causing relayers to repeatedly waste gas on reverting delivery attempts, degrading the general "message must be deliverable" guarantee of the protocol without any privileged actor involved — reachable by any ordinary bridging user or a solver filling any order (unprivileged single transaction).

### Likelihood Explanation
High likelihood: the `data`/`call` fields are always attacker/sender-controlled and pass through no size, complexity, or gas-cost validation anywhere in the call path (`HyperFungibleToken.onAccept` → `CallDispatcher.dispatch`; `IntentsBase._execute`/predispatch → `CallDispatcher.dispatch`). No contract in the reachable path enforces a maximum `data.length`, a maximum number of `Call` entries, or forwards a bounded `gas:` value to the inner `.call{value: ...}(...)`. Crafting a gas-exhausting payload requires no special privileges — just funds to pay for the bridge/order fee — and can be done in a single transaction by any unprivileged user.

### Recommendation
- Enforce a hard limit on `data`/`call` payload size (and/or number of `Call` entries) at dispatch time on the source chain, analogous to TOKI's fix of adding a hard limit on user-input bytes.
- In `CallDispatcher.dispatch()`, forward an explicit bounded gas stipend per call (e.g., `to.call{gas: MAX_CALL_GAS, value: call.value}(call.data)`) and enforce a cumulative gas ceiling across the batch, reserving enough `gasleft()` headroom so a revert/failure can always be caught and reported (never leaving the tx starved of gas mid-execution).
- Incorporate the payload length/complexity into the relayer fee/gas estimate (as already partially done in `GasEstimator`/`HyperFungibleToken.quote`) and reject dispatch on the source chain if the computed gas requirement exceeds a configured maximum per-message gas budget, so an undeliverable message can never be created in the first place.
- Document/require a nonzero timeout for any `send()`/order carrying non-empty `data`/`call`, so a permanently-undeliverable message always has a refund path.

### Proof of Concept
Conceptual (execution not verified in this environment — flagged as uncertain pending live testing):
1. Attacker calls `HyperFungibleToken.send()` with `SendParams.timeout = 0` and `SendParams.data = abi.encode(calls)` where `calls` targets a helper contract that performs a gas-consuming loop (e.g., repeated storage writes) sized to consume close to the destination chain's block gas limit.
2. The message dispatches normally on the source chain (no size/gas validation exists in `HyperFungibleToken.sol` or `IDispatcher`).
3. On the destination chain, any relayer calling `HandlerV2.handlePostRequests` → `EvmHost.dispatchIncoming` → `HyperFungibleToken.onAccept` → `CallDispatcher.dispatch()` will find that completing the call sequence requires more gas than is economically/practically supplied; the low-level `.call()` in `dispatchIncoming` returns `success == false`, the request receipt is deleted (retryable), and delivery never succeeds.
4. Because `timeout == 0`, the message never expires and the beneficiary never receives the minted/unlocked tokens — the message is permanently stuck. (This exact sequence was not executed against a live/forked deployment in this analysis; verifying the precise gas thresholds and confirming no unseen safeguard exists would require a Foundry PoC against `evm/tests/foundry/HyperFungibleTokenTest.sol`.)

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;

            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
