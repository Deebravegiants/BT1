Based on my review of `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`, I found a genuine identity-binding gap: the webhook HMAC only covers the raw body, not the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers that are subsequently trusted and dispatched to the handler.

### Title
Webhook `shop-domain` (and other identifying headers) are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers. `Registry.process` validates the HMAC over that signable string and, if it passes, unconditionally trusts `request.shop`, `request.topic`, etc. to build `WebhookMetadata` and invoke the app's handler. Since the HMAC never binds these headers to the signed payload, they can be freely rewritten by anyone able to submit an HTTP request with a validly-signed body (e.g., a captured/replayed genuine webhook from their own store), producing spoofed metadata that still passes verification.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, raw_body || shop || topic || ...)`, i.e. the authenticated bytes should equal the bytes that determine which tenant/topic the webhook is attributed to. Instead:
- `to_signable_string` signs only `@raw_body` [1](#0-0)  .
- `shop`, `topic`, `api_version`, and `webhook_id` are read straight from HTTP headers with no cryptographic tie to the body or to each other [2](#0-1)  .
- `Registry.process` validates only the HMAC of the (headers-independent) signable string, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to route to a handler and construct `WebhookMetadata` [3](#0-2)  .
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` against the app's single shared `api_secret_key` [4](#0-3)  — this secret is the same across all shops that installed the app, so a valid `(raw_body, hmac)` pair from any one shop remains valid for any other shop's spoofed headers.

Because the same `api_secret_key` is used for every merchant of the app, any external party who can obtain one genuine `(body, hmac)` pair (e.g., their own store's webhook delivery, which they can trivially trigger by performing an action in their own installed app) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` will accept it as an authentic webhook for the *victim* shop because the header is never part of the signed material.

### Impact Explanation
This breaks the cross-tenant boundary the gem is supposed to enforce for webhook authenticity: the host application receives `WebhookMetadata` claiming an arbitrary victim `shop` domain, `topic`, and `webhook_id`, all backed by a signature that only proves "some real Shopify webhook body was signed by this app's secret at some point" — not that it belongs to that shop or topic. Any host app that uses `WebhookMetadata#shop`/`#topic` as the trusted tenant/action key (which is the documented intended use, per `docs/usage/webhooks.md`) can be tricked into applying attacker-chosen body data under a different, victim shop's identity — a cross-tenant data-integrity/impersonation issue.

### Likelihood Explanation
Exploitability only requires the attacker to install the target app in their own shop (or otherwise legitimately receive one webhook), capture the raw body + `X-Shopify-Hmac-Sha256` header, and replay the POST to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. No `api_secret_key`, access token, or other privileged credential is needed beyond what any legitimate merchant already has by installing the app once.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify `shop` against a shop the app actually installed/expects, independent of headers) before trusting them in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a legitimate webhook (e.g., `orders/create`), capturing the exact `raw_body` and `X-Shopify-Hmac-Sha256` value Shopify sends.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [5](#0-4)  ; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared secret [3](#0-2)  .
4. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, believing it is an authentic webhook for the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
