### Title
Unvalidated fixed-size signature copy in BEEFY `Vote`→native conversion causes a panic on malformed consensus proof - ([File: evm/rust/src/conversions.rs])

### Summary
`impl From<Vote> for SignatureWithAuthorityIndex` in the "substrate"-feature conversion module blindly copies an attacker/relayer-supplied, variable-length `signature` byte vector into a fixed `[u8; 65]` buffer with `copy_from_slice`, without checking the length first. This mirrors the root cause of CVE-2024-50256 (a fixed-size destination written from a size that was never validated against it, panicking/crashing instead of performing a safe conditional path), just in Rust's panic-safety idiom rather than a C buffer overrun.

### Finding Description
The conversion routine reads the Solidity ABI `Vote.signature` (`bytes`, dynamic length — Solidity's static `bytes` type only goes up to `bytes32`, so a 65-byte ECDSA signature can only be represented as dynamic `bytes`) and copies it directly into a fixed 65-byte array: [1](#0-0) 

`copy_from_slice` panics unconditionally whenever `sig_bytes.len() != 65`. Every other length-sensitive conversion in the same file guards the length with `try_into()...expect(...)` on numeric fields (block number, validator-set id, mmr leaf index, authority index), but the one place that copies raw bytes into a fixed array has no such guard.

This conversion feeds `MmrProof`/`BvpSignedCommitment` used by `ConsensusMessage`, i.e., the BEEFY consensus-verification path that reconstructs a `SignedCommitment` from an externally supplied `RelayChainProof`/`BeefyConsensusProof`: [2](#0-1) 

The codebase shows a clear, deliberate pattern of hardening exactly this bug class elsewhere — e.g. the regression tests explicitly documenting that `copy_from_slice` on a fixed `[u8; N]` from untrusted-length input is a crash vector that must be rejected as an error instead of panicking: [3](#0-2) [4](#0-3) [5](#0-4) 

The `Vote → SignatureWithAuthorityIndex` conversion was not brought in line with this hardening.

### Impact Explanation
A panic here aborts whatever process is decoding/verifying the submitted BEEFY consensus proof at the moment it processes a vote whose signature is not exactly 65 bytes. Depending on the exact call site (native runtime call vs. relayer/tesseract binary), this can crash a worker thread or process involved in BEEFY consensus verification, which is the mechanism Hyperbridge relies on to authenticate cross-chain state commitments and enable message delivery — i.e., a route unable to deliver/verify messages until the crashing input is filtered out.

### Likelihood Explanation
The trigger condition is trivial to construct — any relayed/submitted BEEFY proof containing a `Vote` with a signature length other than 65 bytes. I was not able to fully trace, within the available tool budget, the exact binary/extrinsic entry point that ultimately calls this `From<Vote>` conversion with attacker-controlled bytes (it sits behind the `substrate` feature of the EVM Rust bindings crate, used for converting Solidity-ABI-shaped BEEFY proof data into native Substrate types). This uncertainty about the precise unauthenticated-reachability boundary should be verified before treating this as confirmed-exploitable versus a robustness bug in an internal/trusted conversion path.

### Recommendation
Validate `sig_bytes.len() == 65` before the `copy_from_slice` and return a `TryFrom`-style error (propagated up through `MmrProof`/`ConsensusMessage` construction) instead of panicking, matching the pattern already used for the numeric fields in the same `impl` blocks and the hardening already applied in `host.rs`, `serde/lib.rs`, and `fisherman/lib.rs`.

### Proof of Concept
1. Craft a `BeefyConsensusProof`/`RelayChainProof` whose `signedCommitment.votes[i].signature` is any length other than 65 bytes (e.g. 64 or 66 bytes).
2. Submit/relay it through whichever path invokes `MmrProof::from(RelayChainProof)` (which calls `SignatureWithAuthorityIndex::from(Vote)` for every vote).
3. `signature.copy_from_slice(&sig_bytes)` panics because the destination `[u8; 65]` and source lengths differ, aborting the calling context instead of returning a decode error.

	/// Deserialize a string into utf8 bytes
	///
	/// The string must be exactly 4 bytes long (bytes, not chars — a 4-char string of
	/// multi-byte codepoints is rejected). Anything else is a deserialization error; this
	/// runs on untrusted RPC input, so it must never panic.
	pub fn deserialize<'de, D, T>(deserializer: D) -> Result<T, D::Error>
	where
		D: serde::Deserializer<'de>,
		T: From<[u8; 4]>,
	{
		let s = <String>::deserialize(deserializer)?;

		// `s.len()` is the utf-8 byte length, which is what the `[u8; 4]` needs to match.
		let bytes: [u8; 4] = s
			.as_bytes()
			.try_into()
			.map_err(|_| serde::de::Error::invalid_length(s.len(), &"a 4-byte utf-8 string"))?;
		Ok(bytes.into())
	}
