### Title
Double-entry (alias) ERC20 in `erc20TokenAddresses` lets `Hinkal.transact`/`EmporiumUpgradeable.runAction` mint an extra on-chain UTXO backed by an already-counted real transfer, causing insolvency - (File: contracts/Hinkal.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`Hinkal.transact` trusts `balanceOf()` reads on attacker-chosen `erc20TokenAddresses` entries to prove that real value backs each minted UTXO, and only guards against literal address duplicates via the circuit's `distinctErc20AddressChecks`. An attacker can deploy a token address `B` that is a pure "read-through" facade of a real, widely-used token `A` (`B.balanceOf(x) == A.balanceOf(x)`) while implementing its own no-op `transfer`/`transferFrom`. Because `EmporiumUpgradeable.runAction` snapshots `balancesBefore`/`balancesAfter` once for the whole batch of token indices rather than incrementally as each `handleOut` payout executes, one single real deposit of `A` gets counted twice — once for index `A` (normal off-chain UTXO) and once for index `B` (on-chain UTXO, which bypasses circuit amount-conservation entirely) — minting shielded value with no additional backing.

### Finding Description
The invariant that should hold is:
`real tokens that entered Hinkal == Σ amountChanges[i] (non on-chain) + Σ utxoAmount[i] (minted UTXOs)`

The check enforcing this is in `Hinkal.transact`: [1](#0-0) 

It compares `oldBalances`/`newBalances` (Hinkal's own `balanceOf`, snapshotted around the whole external action call) per `erc20TokenAddresses[i]`: [2](#0-1) 

The only anti-duplication safeguard is the circuit's pairwise address-inequality check, which only rejects *literally identical* addresses, not economically-aliased ones: [3](#0-2) 

Inside `EmporiumUpgradeable.runAction`, the balances used to compute each token's `balanceChange` (and thus the UTXO amount handed back to Hinkal) are snapshotted **once**, before the per-index loop that also performs the actual `transferERC20TokenOrETH` payouts (`handleOut`): [4](#0-3) [5](#0-4) 

**Attacker's exact call:** `Hinkal.transact` with `externalActionData.externalActionId` = Emporium's id, `erc20TokenAddresses = [A, B]` where `A` is a real token other users also hold shielded balances of, and `B` is an attacker-deployed contract satisfying `IERC20` whose `balanceOf(holder)` simply calls `A.balanceOf(holder)` (pure alias/pass-through) but whose `transfer`/`transferFrom` are independent no-ops (no real value moves). `amountChanges = [0, 0]`, `onChainCreation = [false, true]` (legal per `checkOnchainCreation`, since it only requires `amountChanges[i]==0` and `inputNullifiers[i]==0` when `onChainCreation[i]` is true — it says nothing about aliasing): [6](#0-5) 

The `externalActionMetadata` encodes a single `EmporiumOperation` calling `A.transferFrom(attacker, Emporium, 100)` (a real 100-unit deposit the attacker approved from their own wallet).

**Exploit flow:**
1. `balancesBefore = [A.balanceOf(Emporium)=0, B.balanceOf(Emporium)=0]` (B mirrors A).
2. The op executes: real 100 `A` tokens move attacker → Emporium.
3. `balancesAfter = [100, 100]` — snapshotted once, **before** any `handleOut` payouts run, so both indices still see the same 100.
4. Loop `i=0` (`A`): `balanceChange = 100`; `handleOut` really transfers 100 `A` from Emporium to Hinkal (`msg.sender`), producing `UTXO(100, A)`.
5. Loop `i=1` (`B`): `balanceChange` is computed from the **stale** pre-loop snapshot, still `100`, even though the real 100 `A` tokens were already drained from Emporium in step 4. `handleOut` calls `B.transfer(Hinkal, 100)` — a no-op that returns `true` without moving any real value — producing a second `UTXO(100, B)`.
6. Back in `Hinkal.transact`, Hinkal's own `A`-balance increased by exactly 100 (only real movement). Because `B.balanceOf(Hinkal)` mirrors `A.balanceOf(Hinkal)`, `balanceDif` for **both** index 0 (`A`) and index 1 (`B`) equals 100.
7. Checks: index 0: `100 == amountChanges[0](0) + utxoAmount[0](100)` ✓. Index 1 (`onChainCreation=true`): `100 == 0 + utxoAmount[1](100)` ✓. Both pass.

Because index 1 uses `onChainCreation=true`, its "100 B" UTXO is inserted directly via `onChainCommitments`, **entirely bypassing** the circuit's `inTotal + amountChanges[i] === outTotal` conservation constraint for that token — the ZK proof never constrains this amount at all; only the (broken) Solidity `balanceDif` check does.

The attacker now holds two independently spendable/withdrawable shielded notes worth "100" each (200 total), backed by a single real 100-token deposit. When the "B" note is later redeemed via a normal withdrawal (`_internalTransact`/`transferERC20TokenOrETH(B, ..., 100)`), the pass-through `B.transfer` in a genuine token pairing would need to move real `A` value — since `B` was only ever a facade with no actual reserve, redemption either (a) forces `B`'s logic to pull from Hinkal's shared real `A` reserve (the pool that legitimately backs *other* depositors' `A` UTXOs), directly stealing their funds, or (b) is itself a no-op withdrawal that nonetheless burns the nullifier and lets the attacker walk away having obtained double credit for one deposit. Either way, shielded value was minted without matching backing.

None of the existing guards catch this: `performHinkalChecks`/`checkOnchainCreation` only check flag/field consistency, not economic aliasing; `distinctErc20AddressChecks` only checks address inequality; `verifyProof` never constrains on-chain-created amounts; and the balance snapshots at both the Hinkal and Emporium layers are `balanceOf()` reads on attacker-deployed, attacker-controlled contract code.

### Impact Explanation
This mints shielded value with no matching on-chain backing (Critical: "minting shielded value without backing (protocol insolvency)"). The unbacked "B" UTXO, once withdrawn, either directly drains real tokens belonging to other users of the genuine token `A` from Hinkal's shared reserve, or otherwise represents free/unbacked shielded credit created from a single real deposit — fully repeatable for any amount and any number of times, as the attacker controls the token deployment, the Emporium op list, and all `CircomData` fields.

### Likelihood Explanation
Preconditions are entirely attacker-controlled: deploy a facade/alias ERC20 contract, obtain some real tokens of an existing widely-used asset `A` (even a small amount, since the attack scales with whatever is deposited), and call `Hinkal.transact` once through the Emporium external action with a self-crafted operation list and a locally-generated valid proof (the proof only needs to be valid for the *declared* amounts, all of which are internally consistent). No privileged role, no relay, and no special timing/ordering across blocks is required — the exploit completes within a single transaction. Cost is only gas plus the deposited `A` tokens (fully recoverable).

### Recommendation
- Snapshot and apply balance changes for each `erc20TokenAddresses[i]` incrementally/atomically per index inside `EmporiumUpgradeable.runAction` (i.e., re-read balances immediately before and after each index's own operations/payout) rather than once for the whole batch, so a later index cannot "reuse" a balance delta already paid out to an earlier index.
- Require a protocol-level allowlist for `erc20TokenAddresses` (or at minimum enforce that all balance/token-code interactions for `onChainCreation` indices go through vetted, non-attacker-deployable token contracts), since correctness currently depends entirely on `balanceOf`/`transfer` semantics of attacker-supplied code.
- For `onChainCreation` entries, do not rely solely on a Solidity-side balance-delta check; require the circuit to constrain the minted amount as well (eliminate the "trust `balanceOf` blindly" bypass), or cryptographically bind the on-chain UTXO amount to a value the circuit has already verified conservation for.

### Proof of Concept
Foundry test plan:
1. Deploy real ERC20 `A` (e.g., mintable mock) and mint 100 `A` to `attacker`.
2. Deploy `AliasToken B` where `balanceOf(x) = IERC20(A).balanceOf(x)` and `transfer`/`transferFrom` are no-ops returning `true`.
3. Deploy/whitelist `EmporiumUpgradeable` as an allowed external action on `Hinkal`.
4. `attacker` approves `Emporium` for 100 `A`.
5. Build `CircomData` with `erc20TokenAddresses=[A,B]`, `amountChanges=[0,0]`, `onChainCreation=[false,true]`, `externalActionData.externalActionId` = Emporium id, `externalActionMetadata` encoding one `EmporiumOperation` calling `A.transferFrom(attacker, Emporium, 100)`.
6. Generate a locally valid proof for these public inputs (zero input/output amounts on the circuit side for token index `B`, satisfying `inTotal+amountChanges[1]===outTotal` with all zeros) and call `Hinkal.transact`.
