### Title
Paymaster's oracle staleness bound is decoupled from the underlying feed's deviation threshold, letting gas payments be priced off a stale ETH/USD or token/USD price for up to `maxOracleAge` - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` prices ERC-20 gas payments for ERC-4337 `UserOperation`s using Chainlink `nativeOracle`/`tokenOracle` feeds. The only staleness protection is a single time-window check (`maxOracleAge`), with no check on how far the price could have drifted within that window. This is the same root cause as the reported stETH/ETH issue: a governance-configured "acceptable" staleness bound that is decoupled from the real-world deviation the underlying feed can accumulate before it updates, letting the contract act on a materially stale price and mis-price the transaction against the user or the protocol.

### Finding Description
`_getOraclePrice` only rejects a price when it is older than `maxOracleAge`; it performs no comparison against a secondary source and no bound on the magnitude of price movement that could have occurred during that window: [1](#0-0) 

`maxOracleAge` is a single governance-settable parameter, capped only by `MAX_ORACLE_AGE = 7 days`, and is explicitly sized to be *larger* than the underlying Chainlink stablecoin heartbeats to avoid transient reverts: [2](#0-1) 

The deploy script documents this directly — the age is deliberately padded above the 24h stablecoin heartbeat (`MAX_ORACLE_AGE` default `90_000` seconds ≈ 25h), i.e. the contract is configured to accept prices that are stale for longer than the feed's own update cadence, with no compensating deviation check: [3](#0-2) 

This stale `nativeUsd`/`tokenUsd` pair directly drives the price charged to any unprivileged `UserOperation` sender: [4](#0-3) 

and that price is used both to size the actual token pull from the user in `_prefund`/`_erc20Cost` and to determine the minimum swap output when recycling fees: [5](#0-4) 

Any UserOp sender using paymaster modes `0x00` (permit) or `0x02` (Permit2) reaches this pricing path with no privilege required — this is exactly analogous to the original report's `getTknOhmPrice`, where a wide heartbeat/deviation window on the price feed caused the on-chain price to diverge materially from the true asset price and directly determined how much of a user's asset was taken.

### Impact Explanation
If the native asset (e.g., ETH/BNB) or a registered token's USD price moves materially within the `maxOracleAge` window — routine during normal volatility, let alone a market shock — `_tokenPrice` computes an incorrect `tokenPrice`:
- If `nativeUsd` is stale-high relative to the real price, users are overcharged in the ERC-20 gas token for the same amount of native gas actually consumed, directly losing funds.
- If `nativeUsd` is stale-low, the paymaster undercharges, draining value from the EntryPoint deposit/treasury over many operations, since the ERC-20 collected no longer covers the real native cost that was refunded via `entryPoint().depositTo`.

Because `maxOracleAge` is deliberately configured above real-world heartbeats (per the deploy script), this isn't a theoretical edge case — it is baked into how the contract is meant to run in production.

### Likelihood Explanation
No attacker action or malicious oracle/admin is required: ordinary price volatility of the native asset or of a "stable" token within the governance-configured staleness window (up to 7 days maximum, ~25h in the reference deployment) is sufficient to trigger mispricing on every UserOp settled during that window. This mirrors the exact discussion in the original report, which was ultimately assessed as Medium severity.

### Recommendation
Add a deviation/soundness check independent of pure staleness — e.g., cross-check against a second oracle, or reject if `answer` differs from a bounded reference by more than an acceptable percentage — instead of relying solely on `updatedAt` age. Alternatively, tighten `maxOracleAge` to be strictly bounded by (not padded above) the true heartbeat of the specific feed used, and document/enforce per-feed deviation thresholds when registering a token oracle in `_registerToken`/`_setParams`.

### Proof of Concept
1. Governance calls `UpdateParams` (or deploys) with `maxOracleAge` set to the documented default (~25h), matching `DeploySimplexPaymaster.s.sol`'s guidance. [6](#0-5) 
2. The `nativeOracle` (e.g., ETH/USD) last updates at price P0 at time T0.
3. Within the following ~25 hours, the real ETH/USD price moves by, e.g., 5–10% (a routine intraday move) without a new Chainlink round because the deviation threshold wasn't crossed on this particular feed/round, or the round is simply within `maxOracleAge`.
4. A user submits a `UserOperation` with `paymasterData` mode `0x00`/`0x02` for a registered stablecoin. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the stale `nativeUsd` because `block.timestamp - updatedAt <= maxOracleAge`, per: [7](#0-6) 
5. `_erc20Cost` charges the user based on this stale `tokenPrice`, overcharging (or undercharging) them relative to the true native gas cost by the amount the price drifted — a direct loss of funds to the user (or ongoing protocol insolvency risk) with no attacker interaction required.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
