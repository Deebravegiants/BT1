## Analysis Result

### Title
Checks-Effects-Interactions violation in `withdraw()` — external token/native transfers execute before escrow ledger is decremented - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` contains the exact bug class described in the H-07 report: the internal `withdraw()` function performs external calls (native ETH transfer or ERC20 `transfer`) to an attacker-influenced `beneficiary`/`token` address *before* updating the internal escrow accounting (`_orders[...]`) and before clearing the accumulated transaction fee slot, violating Checks-Effects-Interactions.

### Finding Description
In `withdraw()`, for each token in the withdrawal request, the external transfer happens first and the escrow ledger is decremented only afterward: [1](#0-0) 

The same ordering issue repeats for the accumulated transaction-fee payout, where the external `feeToken.call(transfer(...))` executes before `delete _orders[body.commitment][TRANSACTION_FEES];`: [2](#0-1) 

This contrasts with the hardened mainline implementation in `IntentsBase.sol`, which correctly updates the escrow slot *before* transferring funds out (`_orders[body.commitment][token] = escrowed - amount;` precedes `_sendValue`/`safeTransfer`): [3](#0-2) 

The codebase has clearly already recognized and remediated this exact bug class for other intent-fill code paths — `_fillSameChain`/`_fillCrossChain` now set `_filled[commitment] = msg.sender` at the very top before any external transfer, specifically to block cross-function reentrancy, with a dedicated regression test suite documenting the prior vulnerable ordering and the fix: [4](#0-3) [5](#0-4) 

The Tron `withdraw()` sets `_filled[body.commitment] = beneficiary` before its token loop, which does block reentry into `fillOrder`/`cancelOrder` for the *same* commitment, but the per-token escrow decrement and the fee-slot deletion inside the same function still occur strictly after their respective external calls — the same raw ordering flaw the report describes, just with the primary attack vector partially (not fully) mitigated by the early `_filled` write.

`token` is fully attacker-controllable: any address may be listed as an order's input token at `placeOrder` time (an unprivileged, single-transaction call), so an order placer can escrow a custom ERC20 whose `transfer()` implementation executes arbitrary attacker logic mid-call, exactly the kind of external call the CEI pattern is meant to isolate from subsequent bookkeeping.

### Impact Explanation
A malicious token (or a beneficiary contract for the native-ETH branch) that hijacks control during the `token.call(...)`/`.call{value}(...)` executed inside `withdraw()` runs with `_orders[body.commitment][token]` still un-decremented and, for the fee branch, with `_orders[body.commitment][TRANSACTION_FEES]` still un-deleted. Any reachable state-reading/state-mutating path in this contract that is not itself protected against re-entry during this window (unlike `fillOrder`/`cancelOrder`, which are shielded via the early `_filled` write) is exposed to acting on stale, not-yet-updated escrow figures, which is the structural precondition for double-spend of escrowed funds or incorrect accounting of protocol fee dust. This maps to the "concrete theft of funds" / "unauthorized app action" impact classes.

### Likelihood Explanation
Medium: exploitation requires the attacker to control an escrowed token contract or the beneficiary address (both are attacker-reachable in the intents flow — a user freely chooses input tokens at `placeOrder`, and a solver freely becomes the RedeemEscrow beneficiary), so the precondition is trivially satisfiable by a single unprivileged transaction. The primary same-commitment re-entry path is already closed by the early `_filled` write, which reduces likelihood relative to the original C4 report, but the ordering flaw itself is unambiguously present and inconsistent with the CEI pattern the team has otherwise standardized on elsewhere in the same protocol.

### Recommendation
Apply the same fix already used in `IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` slot) before performing the external transfer, for every branch in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw()`. Consider adding an explicit reentrancy guard to `withdraw()`/`onAccept()`/`onGetResponse()` in this contract for defense in depth, and add a Tron-specific regression test mirroring `IntrinsicIntentsReentrancyTest.sol` to lock in the corrected ordering.

### Proof of Concept
1. An order placer calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs` containing a custom ERC20 token whose `transfer()` function contains attacker logic (e.g., calls back into the gateway).
2. A solver fills the order (same-chain or cross-chain), and the settlement path eventually invokes `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 691-730.
3. Inside the loop, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` (line 706) executes the attacker's token code before `_orders[body.commitment][token] -= amount;` (line 710) runs.
4. During this window, the attacker's token contract can attempt any reachable action against the gateway that depends on the not-yet-updated `_orders`/`TRANSACTION_FEES` state, or against unrelated escrow entries sharing the same token address, to extract value beyond what the CEI-safe implementation in `IntentsBase.sol` would allow.
