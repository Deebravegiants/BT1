### Title
Webhook HMAC signs only the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant/topic forgery of `WebhookMetadata` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, excluding the `shop-domain`, `topic`, and `webhook-id` headers [3](#0-2) . `HmacValidator.validate` only checks that the HMAC matches this signable string against the shared app secret [4](#0-3) , so a signature that is valid for one shop/topic/body combination remains valid if the header values are swapped, and those unsigned header values flow unchecked into `WebhookMetadata#shop` and `#topic` handed to the host app's handler [5](#0-4) .

### Finding Description
The broken binding: the invariant "every value the app trusts as authenticated is inside the HMAC-signed string" should mean `to_signable_string ⊇ {shop, topic, webhook_id, api_version}`, but in fact `to_signable_string == @raw_body` only [3](#0-2) . `request.shop`, `request.topic`, and `request.webhook_id` are read straight from HTTP headers with no cryptographic binding to the body [6](#0-5) .

Exploit flow:
1. Attacker registers their own webhook endpoint on their own development shop, installs the app, and receives a legitimately-signed webhook (any topic, e.g. `orders/create`), obtaining a raw body `B` and a valid HMAC `H` computed with the app's shared `api_secret_key`.
2. Attacker replays a forged HTTP request to the app's public webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but arbitrary `X-Shopify-Shop-Domain` (victim shop) and/or `X-Shopify-Topic` headers.
3. `HmacValidator.validate` recomputes the HMAC over `B` only, matches `H`, and returns `true` — the forged headers were never part of the check [7](#0-6) .
4. `Registry.process` looks up the handler by the forged `topic` and builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` from the unsigned headers, then calls `handler.handle(data: ...)` [5](#0-4) .
5. The host app, trusting `WebhookMetadata#shop`/`#topic` because "the HMAC validated," acts on the wrong tenant's records or under the wrong topic's business logic.

Existing guards do not catch this: `HmacValidator.validate` checks body integrity/authenticity only, not header authenticity; there is no `ShopValidator.sanitize!` or any format/ownership check on `request.shop` anywhere in `Registry.process` or `WebhookMetadata`; `WebhookMetadata` is a plain `T::Struct` with `const :shop, String` — Sorbet only enforces type, not provenance [8](#0-7) .

Note: this mirrors the real Shopify webhook verification design (HMAC over raw body only, using the app's shared secret across all installed shops) — this is Shopify's own documented/intended verification mechanism, not something this gem alone introduced. However, within the scope of "does `Webhooks::Registry.register`'s downstream consumer (`process`/`WebhookMetadata`) preserve signature coverage over the shop identity," the answer is no: `request.shop` and `request.topic` are unauthenticated relative to the signature check performed by this gem.

### Impact Explanation
An attacker who is a legitimate (if unprivileged) merchant/installer of the target app can forge the shop identity and/or topic on webhook deliveries accepted by the app, because the shared app secret used for signing is not shop-specific and the signature covers only the body. This can cause the host app to act on/write to a different merchant's tenant data (cross-tenant access) or invoke a handler for a topic whose body schema doesn't match, corrupting state. This matches "cross-tenant access" under the Critical category. Blast radius: any shop using the target app is a potential impersonation target for any other attacker-controlled shop that has ever received a signed webhook.

### Likelihood Explanation
Preconditions: attacker needs a development/trial shop with the app installed (freely obtainable), and the app must derive per-shop trust decisions from `WebhookMetadata#shop`/`#topic` without independently re-verifying shop ownership (typical/documented usage pattern per `docs/usage/webhooks.md`). Attacker cost is low — capture one legitimate webhook body+HMAC, then replay with modified headers directly to the app's public webhook URL. Repeatable per captured body/topic pair; limited to shops/topics for which the attacker can obtain at least one legitimately-signed payload.

### Recommendation
Either (a) document explicitly that `WebhookMetadata#shop`/`#topic` are not cryptographically authenticated and host apps must independently validate the shop against the session/install record before acting, or (b) if feasible, extend the HMAC coverage/verification to cross-check that the resolved shop for a topic corresponds to an app installation your app expects, and avoid trusting `shop-domain`/`topic` headers as the sole authorization basis downstream.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_forged_shop_and_topic_headers_pass_hmac_validation
  body = '{"id":1,"note":"hi"}'
  secret = "secret"
  ShopifyAPI::Context.setup(api_secret_key: secret, ...)
  valid_hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", secret, body))

  # Legit request from attacker's own shop
  legit_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: body,
    headers: {
      "X-Shopify-Topic" => "orders/create",
      "X-Shopify-Hmac-Sha256" => valid_hmac,
      "X-Shopify-Shop-Domain" => "attacker-shop.myshopify.com",
      "X-Shopify-Webhook-Id" => "1",
      "X-Shopify-Api-Version" => "2023-10",
    },
  )
  assert ShopifyAPI::Utils::HmacValidator.validate(legit_request)

  # Forged request: same body/hmac, victim shop-domain + different topic
  forged_request = ShopifyAPI::Webhooks::Request.new(
    raw_body: body,
    headers: {
      "X-Shopify-Topic" => "customers/update", # forged topic
      "X-Shopify-Hmac-Sha256" => valid_hmac,   # same signature
      "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com", # forged shop
      "X-Shopify-Webhook-Id" => "1",
      "X-Shopify-Api-Version" => "2023-10",
    },
  )
  # Assert both sides of the "signature coverage" binding diverge:
  assert ShopifyAPI::Utils::HmacValidator.validate(forged_request) # still true!
  assert_equal "victim-shop.myshopify.com", forged_request.shop     # unauthenticated value trusted
  assert_equal "customers/update", forged_request.topic             # unauthenticated value trusted
end
```
This demonstrates that identical body/HMAC pairs validate successfully regardless of `shop-domain`/`topic` header content, proving the signature does not cover the values that `WebhookMetadata` exposes to the host app.
