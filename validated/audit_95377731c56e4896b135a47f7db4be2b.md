## Title
Direct SPL-Token `Burn` on the LP mint (bypassing `process_withdraw`) desynchronizes `AmmInfo.lp_amount` from the real LP supply and permanently freezes the corresponding pool assets — (File: `program/src/processor.rs`)

### Summary
The reported bug class is that a token with a mint/burn ledger backed by a locked balance elsewhere (L1 lock vs L2 mint/burn) can be burned through an unrestricted, non-canonical path (`L2ECO.burn()` called directly instead of via the bridge), permanently desynchronizing the two ledgers and freezing the corresponding locked value. Raydium's AMM has the same structural pattern: `AmmInfo.lp_amount` is an internally tracked "shadow ledger" that is supposed to always equal the LP SPL-mint's real `supply`, but nothing in the SPL Token Program or the AMM program prevents an LP holder from calling `spl_token::burn` directly on their own LP token account, bypassing the AMM's canonical `Withdraw` instruction entirely.

### Finding Description
In `process_deposit`, the AMM mints LP tokens to the user and increments the internal counter together in lockstep: [1](#0-0) 

In `process_withdraw`, LP tokens are burned and the internal counter is decremented together in lockstep, and pool tokens are paid out proportionally to `withdraw.amount / amm.lp_amount`: [2](#0-1) 

`amm.lp_amount` (not the LP mint's actual `supply`) is the sole denominator used everywhere pro‑rata pool shares are computed, e.g. via `InvariantPool` in both deposit and withdraw: [3](#0-2) [4](#0-3) 

The LP mint is a standard SPL token whose mint authority is the AMM `$authority` PDA, but **burn authority is simply the LP token account owner** — the SPL Token Program's `Burn` instruction only requires the token account owner's signature, not the mint authority's. This means any LP holder can invoke `spl_token::burn` on their own LP token account directly (completely outside the raydium-amm program, using no privileged signer), reducing the LP mint's real `supply` while leaving `amm.lp_amount` untouched, exactly mirroring how `L2ECO.burn()` let a holder reduce L2 supply without touching the L1-locked balance.

### Impact Explanation
Once `lp_mint.supply` drops below `amm.lp_amount` via an out-of-band burn, the AMM's proportional-share math (`InvariantPool::exchange_pool_to_token`, used in `process_withdraw`) continues to use the stale, now-inflated `amm.lp_amount` as the total-supply denominator. The coin/pc value that would have belonged to the burned LP tokens can never be reclaimed by anyone through `process_withdraw`, because `amm.lp_amount` never accounts for that reduction — the corresponding vault assets become permanently stuck/unclaimable in `amm_coin_vault`/`amm_pc_vault`, i.e. a permanent freezing of pool funds and a lasting accounting mismatch between the AMM's internal state and the real, verifiable circulating LP supply.

### Likelihood Explanation
This requires no privileged role, no malicious validator, and no special build — any regular liquidity provider can trigger it with a single, ordinary SPL Token Program `Burn` instruction on their own LP token account, entirely independent of the raydium-amm program's instruction set (`Initialize2`, `Deposit`, `Withdraw`, swaps). The action is indistinguishable from a normal wallet operation, so it can happen accidentally (e.g., a wallet or aggregator UI offering "burn LP" as a shortcut) or be used deliberately to grief the pool's accounting.

### Recommendation
Since the AMM program cannot prevent third-party SPL Token `Burn` calls on the LP mint, consider reconciling `amm.lp_amount` against `lp_mint.supply` at the start of `process_deposit`/`process_withdraw` (e.g., asserting `amm.lp_amount == lp_mint.supply`, or actively resyncing to the smaller value) so that stranded value is detected and/or handled rather than silently and permanently locked.

### Proof of Concept
1. Attacker/LP deposits into a pool via `Deposit`, receiving `N` LP tokens; `amm.lp_amount` and `lp_mint.supply` are both incremented by `N` (`processor.rs:1341-1350`).
2. Instead of calling the AMM's `Withdraw` instruction, the LP holder submits a standalone `spl_token::burn` instruction (signed only by themselves as the LP token account owner) burning `N` LP tokens directly.
3. `lp_mint.supply` decreases by `N`, but `amm.lp_amount` is untouched (no code path in `processor.rs` reacts to external burns).
4. Subsequent `Withdraw` calls by remaining LP holders keep dividing by the stale, larger `amm.lp_amount` (`processor.rs:1751-1761`), so the coin/pc value corresponding to the burned `N` LP tokens can never be withdrawn by anyone and remains permanently locked in `amm_coin_vault`/`amm_pc_vault`.

impl InvariantPool {
    /// Exchange rate
    pub fn exchange_pool_to_token(
        &self,
        token_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(token_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
