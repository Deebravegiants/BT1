## Finding

The core bug class in the report — a fixed, non-updatable recipient address that can be forced onto an external blacklist (e.g. by a bad actor dusting it with tainted/OFAC-sanctioned funds) while funds are already locked/committed, with no path to redirect or recover them — maps directly onto `FeeVault`'s creator fee accounting.

`FeeVault.accrue` credits fees to a fixed `creator` address in `$.creatorBalance[creator]` [1](#0-0) , and `claim()` can only ever pay out to `msg.sender` — there is no way for anyone (owner or creator) to redirect an already-accrued balance to a different address [2](#0-1) . `Bonding.transferCreator` only changes `info.creator` in `Bonding`'s own storage for *future* accruals; it never touches `FeeVault.creatorBalance` for the old address [3](#0-2) .

### Title
Permanent freezing of creator fees in FeeVault when the creator address is externally blacklisted on USDC - (File: packages/contracts/src/FeeVault.sol)

### Summary
`FeeVault` accrues creator fees against a fixed `creator` address and only allows that exact address (`msg.sender == creator`) to withdraw them via `claim()`. If that address is ever added to the USDC blacklist — which any unrelated third party can trigger by sending tainted/sanctioned funds to it — the creator's entire accrued balance becomes permanently unclaimable, with no admin or self-service path to redirect it to a clean address.

### Finding Description
`accrue()` stores creator fee balances keyed by `creator` [4](#0-3) . The only withdrawal path, `claim()`, transfers USDC to `msg.sender` and requires `msg.sender` to be exactly the address the balance is keyed under [2](#0-1) . There is no `claimTo(address)` variant, no owner-assisted migration function, and `Bonding.transferCreator` — the only function that changes a creator's identity — writes solely to `Bonding`'s `info.creator` field for future accrual attribution; it never migrates or reassigns the existing `FeeVault.creatorBalance[oldCreator]` [3](#0-2) .

USDC is a centrally-blacklistable stablecoin. Any unrelated wallet can send a creator's address a dusting amount of USDC obtained from a recent exploit or an OFAC-sanctioned source, prompting Circle to add that creator's address to its blacklist — exactly the attack vector described in the external report. Once blacklisted, `IERC20($.usdc).safeTransfer(msg.sender, amount)` inside `claim()` will revert unconditionally for that address, because USDC's own `transfer` reverts when the recipient is blacklisted.

Because `creatorBalance` is permanently keyed to that one address with no reassignment mechanism, the accrued fees are stuck in `FeeVault` forever — the creator cannot claim them (their address is blacklisted), and calling `transferCreator` on `Bonding` does nothing to move the already-accrued `FeeVault` balance to the new creator address.

### Impact Explanation
This results in permanent freezing of creator funds held in `FeeVault`. Any creator whose curve is actively earning meaningful trading fees is a viable target: an attacker only needs to dust the creator's wallet with tainted USDC to trigger blacklisting, after which all past and future accrued `creatorBalance` for that address becomes permanently unclaimable, with no recovery path in the current contract.

### Likelihood Explanation
The attack requires only an unprivileged wallet capable of sending USDC to the target creator address (a plain ERC20 transfer, reachable by anyone) plus reliance on Circle's blacklisting policy actually being triggered on the dusted address — the same precondition the external report relies on. No privileged access, upgrade, or off-chain compromise is needed; the trigger is entirely on-chain and permissionless.

### Recommendation
Add an owner-gated (or creator-signed, e.g. via signature) `reassignCreatorBalance(address oldCreator, address newCreator)` function in `FeeVault` that migrates `creatorBalance[oldCreator]` to `newCreator`, mirroring/complementing `Bonding.transferCreator`. Alternatively, add a `claimTo(address recipient)` function that lets `msg.sender` (still gated to the actual creator, e.g. via a signed message or `msg.sender == creator` check) direct the payout to an arbitrary clean address instead of hardcoding `msg.sender` as both the authorization and the payout target.

### Proof of Concept
1. Creator C launches a token via `Bonding.launch`/`Zap.createToken` and accrues creator fees in `FeeVault.creatorBalance[C]` through normal `buy`/`sell` activity (via `accrue`) [1](#0-0) .
2. An unrelated attacker sends C's address USDC previously obtained from a known exploit or an OFAC-sanctioned source via a plain ERC20 `transfer`.
3. Circle blacklists address C on USDC.
4. C calls `FeeVault.claim()`; the internal `$.usdc.safeTransfer(msg.sender, amount)` reverts because C is blacklisted [2](#0-1) .
5. C calls `Bonding.transferCreator(tokenAddress, newAddress)` to designate a clean address for future accruals [3](#0-2) ; this does not move the existing `FeeVault.creatorBalance[C]`, which remains permanently stuck since no function can reassign it.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
