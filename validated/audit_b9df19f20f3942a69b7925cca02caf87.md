### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let the same `msg.value` back two independent output-amount checks, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
In `Hinkal.transact`, the balance-verification loop (lines 97-147) evaluates `balanceDif` per index of `circomData.erc20TokenAddresses` using a snapshot of `oldBalances`/`newBalances` taken once before and once after the internal transfer logic runs. When `address(0)` appears more than once in this array, each duplicate index independently recomputes the identical `balanceDif = newBalance + msg.value - oldBalance` and checks it against that index's own `amountChanges[i]`, allowing the same real ETH payment to satisfy two separate output-amount obligations.

### Finding Description
The invariant that should hold is: **total ETH actually received by the contract == sum of `amountChanges[i]` (plus `utxoAmount[i]`) over all `i` where `erc20TokenAddresses[i] == address(0)`**. Instead, the code checks each index *independently* against the *same* snapshot delta.

Path:
- `Hinkal.transact` snapshots `oldBalances = getBalancesForArray(circomData.erc20TokenAddresses)` [1](#0-0)  and, for `externalActionId == 0`, calls `_internalTransact(circomData)` [2](#0-1) .
- `_internalTransact` iterates the same `erc20TokenAddresses` array; for a positive `amountChanges[i]` it calls `transferERC20TokenFromOrCheckETH(...)`, which for `address(0)` only asserts `msg.value == _value` and performs **no actual transfer** when `_to == address(this)` [3](#0-2) . This check is index-local, so if two entries both carry `address(0)` with a positive `amountChanges`, both checks independently pass by being forced equal to the single `msg.value`.
- Back in `transact`, `newBalances` is snapshotted once after `_internalTransact` [4](#0-3) , then the loop computes, for every duplicate `address(0)` index, the identical `balanceDif = int256(newBalances[i]) + int256(msg.value) - int256(oldBalances[i])` [5](#0-4)  and separately requires it to equal `amountChanges[i] + utxoAmount` [6](#0-5) .

Because both duplicate indices are checked against the *same* `balanceDif` value (derived from one real `msg.value` payment), the prover can set `amountChanges[i1] = amountChanges[i2] = msg.value`, satisfying both requires with a single real ETH payment. The circuit constrains `inTotal + amountChanges === outTotal` per output slot, so the circuit will happily mint two independent shielded ETH output notes, each valued at `msg.value`, while the contract only ever received `msg.value` once. No code in `transact`/`_internalTransact` deduplicates `erc20TokenAddresses` or aggregates `amountChanges`/`balanceDif` across repeated token addresses; `performHinkalChecks`/`dimensionsCheck` were not found to enforce uniqueness of `erc20TokenAddresses` entries in the reachable Solidity path.

### Impact Explanation
An attacker who deposits `msg.value = D` once can cause the protocol to record `2D` (or more, with more duplicate entries) worth of shielded ETH value across two output UTXOs, while the vault's real ETH balance increased by only `D`. This directly mints shielded value without backing, i.e., protocol insolvency — a Critical impact matching "minting shielded value without backing." The attack is repeatable per transaction and scales with the number of duplicate `address(0)` entries used.

### Likelihood Explanation
The attacker needs only: (1) an unprivileged EOA able to call `transact` with `externalActionId == 0`, (2) the ability to construct a valid zk-proof for their own chosen public inputs (crafting `amountChanges`, `erc20TokenAddresses` with a duplicated `address(0)`, and matching output commitments), which is within the stated attacker capability ("craft every field of `CircomData` ... and deposit arrays, and choose ordering"). No admin/relay privilege is required, and the cost is simply `msg.value = D` plus gas. This is fully repeatable.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` (reject duplicates, e.g. in `performHinkalChecks`/`dimensionsCheck`), or alternatively aggregate `balanceDif`/`amountChanges` per distinct token address before doing the per-index balance-equality checks, and only add `msg.value` once total (not once per matching index) when computing the ETH balance delta.

### Proof of Concept
Foundry/Hardhat plan:
1. Deploy `Hinkal` with test verifier/merkle setup allowing locally generated proofs (per repo's existing proof-generation tooling).
2. Construct `circomData.erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [D, D]`, `onChainCreation = [false, false]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`.
3. Generate valid proof/public inputs so the circuit produces two output commitments each of value `D` for `address(0)`, with zero input notes (`inTotal = 0`), satisfying `inTotal + amountChanges === outTotal` per slot.
4. Call `hinkal.transact{value: D}(a, b, c, dimensions, circomData)`.
5. Assert:
   - `address(hinkal).balance - balanceBefore == D` (only one real deposit received).
   - The two newly inserted output commitments correspond to shielded ETH UTXOs totaling `2 * D` (i.e., minted shielded value exceeds the real balance increase by `D`), confirming `balanceDif` was double-counted per the broken equality `sum(amountChanges for address(0) entries) != actual ETH received`.
