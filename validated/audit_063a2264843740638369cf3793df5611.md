### Title
`Oauth.begin_auth` builds the OAuth authorization redirect from an unvalidated `shop` parameter, breaking the shop/host identity binding - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop:` string and uses it directly, with no validation, to build the URL the merchant's browser is redirected to for OAuth authorization. Unlike other credential-issuing entry points in this gem, it never runs the value through `Utils::ShopValidator`.

### Finding Description
`begin_auth` takes the raw `shop:` argument and passes it straight into `auth_base_uri(shop)`, which interpolates it into `"https://#{shop}/admin"` with no domain check: [1](#0-0) 

That result is then concatenated with the OAuth query string (containing `client_id`, `redirect_uri`, `state`) to produce `auth_route`, and a `state` nonce cookie is issued unconditionally: [2](#0-1) 

This is inconsistent with the rest of the library: other flows that also handle the app's `shop` identity route their input through `Utils::ShopValidator` before trusting it (e.g. `client_credentials.rb`, `refresh_token.rb`, storefront client, and `TokenExchange`, which explicitly derives `shop` only from the signed JWT `dest` claim). `ShopValidator.sanitize!`/`sanitize_shop_domain` exists specifically to enforce that a `shop` value resolves to a domain under `TRUSTED_SHOPIFY_DOMAINS`: [3](#0-2) [4](#0-3) 

`begin_auth` never calls into `ShopValidator` at all, so the identity binding "host that receives the app's `client_id`/authorization request" == "a genuine `*.myshopify.com` (or configured trusted) domain" is not enforced by the gem for this entry point, even though the documented API states `shop` "MUST" be `{exampleshop}.myshopify.com` — a contract the gem does not itself verify.

Note: this differs from `validate_auth_callback`, where `auth_query.shop` is bound by a Shopify-computed HMAC over the whole query (including `shop`) via `Utils::HmacValidator.validate`, so that path cannot be forged without the `client_secret`: [5](#0-4) [6](#0-5) 
`begin_auth` has no such signature to rely on, since it runs before any Shopify-issued proof exists — which is exactly why validating the shape/domain of `shop` at this step matters.

### Impact Explanation
If a host application passes an unsanitized, user/URL-controlled `shop` value straight to `begin_auth` (a pattern the docs' own example encourages — `shop = request.headers["Shop"]`), an attacker who can influence that value can force a victim's browser to be redirected to an attacker-controlled origin, carrying the app's `client_id`, the requested `redirect_uri`, and a freshly-minted `state` nonce that the app has already bound to a cookie on the victim's browser. This matches the "session fixation / forced OAuth completion" class of issue: the attacker fully controls the destination of the OAuth "begin" step and can leverage the pre-issued state cookie to attempt to manipulate or fixate the session before the real OAuth handshake with Shopify occurs.

The `client_secret` itself is not exposed here (it's only sent inside `validate_auth_callback`, which is HMAC-gated), so this does not directly yield secret exfiltration, but it does demonstrate that the gem's shop/host binding is only enforced on the callback side, not on the side that first commits the app's `client_id` and a session-controlling nonce to an attacker-influenceable destination.

### Likelihood Explanation
Exploitability depends entirely on whether the host application forwards an untrusted `shop` value into `begin_auth` without first calling `ShopValidator.sanitize!` itself — which the gem's own docs neither show nor require, and even show a raw `request.headers["Shop"]` example. Because the sanitization utility exists in this same library but simply isn't wired into `begin_auth`, this is a gap in the library's own defense-in-depth rather than a pure host-app misuse, but likelihood of real-world exploitation still hinges on host-app integration choices.

### Recommendation
Have `Oauth.begin_auth` call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: Context.custom_shop_domains)` (or equivalent) internally before using the value to build `auth_base_uri`, raising `Errors::InvalidShopError` for any value that doesn't resolve to a trusted Shopify domain — mirroring the protection already applied in `client_credentials.rb`, `refresh_token.rb`, and the storefront client.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "APIKEY123", api_secret_key: "secret", host_name: "app.example.com", scope: "read_products")

# Attacker-influenced shop value (e.g. taken unsanitized from a query/header param)
result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example", redirect_path: "/auth/callback")

result[:auth_route]
# => "https://attacker.example/admin/oauth/authorize?client_id=APIKEY123&scope=read_products&redirect_uri=..." 
# The app's client_id, redirect_uri, and freshly generated `state` nonce are sent to an
# attacker-controlled host, with no validation performed by ShopifyAPI::Auth::Oauth.begin_auth.
```

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
