### Title
Replayable off-chain approval in `usdk::transfer_from` due to non-consuming nonce (`account::get_sequence_number`) - (File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move)

### Summary
`usdk::transfer_from` implements an ERC20-`permit`-style delegated-transfer scheme where `spender` submits a signature from `from` authorizing a transfer. The signed `Approval` message's replay-protection field (`nonce`) is set to `account::get_sequence_number(from)` [1](#0-0) . This is the exact bug class from the external report: a signed authorization message whose "nonce" is not tied to (and not consumed by) the verification/transfer flow itself, enabling replay of the same signature.

### Finding Description
`transfer_from` is called by `spender` (not by `from`), so the Move VM transaction prologue only increments the sequence number of the transaction's sender (`spender`), never `from`'s sequence number [2](#0-1) . Since `from`'s account sequence number changes only when `from` submits its own transactions, and this custody flow never touches or increments it, a single signed `Approval{owner: from, to, nonce, chain_id, spender, amount}` message remains valid and unconsumed after use. The same `proof` can be replayed by the `spender` (or anyone relaying it) as many times as `from`'s sequence number stays unchanged, executing `primary_fungible_store::transfer_with_ref` repeatedly for `amount` each time [3](#0-2) . There is no on-chain used-nonce set, no burn/increment of the nonce, and no linkage to the on-chain transaction's actual sequence-number consumption — mirroring the reported bug where a nonce is generated but never invalidated after use.

### Impact Explanation
This breaks the custody invariant that a signed transfer authorization must be single-use. An attacker who obtains one valid `proof` (e.g., a spender contract, a relayer, or anyone who observes the transaction calldata/mempool) can call `transfer_from` repeatedly to drain the full remaining balance of `from`'s USDK primary fungible store, well beyond the single `amount` the owner intended to authorize — a direct theft of fungible-asset value, satisfying the custody-grade "theft of ... fungible assets" impact criterion.

### Likelihood Explanation
High. `proof`/signature material passed to a public function is inherently observable on-chain (it's a transaction argument) and callers of `transfer_from` are not restricted (it is a `public fun`, not `entry`, but any module or off-chain relayer with the signature bytes can call it repeatedly). No privileged assumption is required — only that the account signs one approval and the sequence number of `from` does not change in the interim (a very common condition, since PFS transfers via `transfer_from` don't affect `from`'s own sequence number at all).

### Recommendation
- Short term: Add an explicit, monotonic, on-chain "used nonce" resource per `from` account, incremented/marked-used inside `transfer_from` itself (not derived from `account::get_sequence_number`), and require the caller-provided nonce to exactly match and then be consumed.
- Long term: Deprecate use of `account::get_sequence_number` as an authorization nonce anywhere in example/framework code; document that account sequence numbers are not appropriate replay-protection nonces for functions not executed as the owning account's own transaction.

### Proof of Concept
1. `from` (owner) signs one `Approval { owner: from, to, nonce: account::get_sequence_number(from), chain_id, spender, amount: N }` off-chain and gives `proof` to `spender` for a single intended payment of `N` USDK.
2. `spender` calls `usdk::transfer_from(spender, proof, from, scheme, pubkey, to, N)`. `assert_not_paused`/`assert_not_denylisted` pass, `account::verify_signed_message` succeeds because `nonce` still equals `from`'s (unchanged) sequence number, and `N` tokens move from `from` to `to` [4](#0-3) .
3. `spender` calls `usdk::transfer_from` again with the identical `proof`/arguments. Because `from` never submitted any transaction in between, `account::get_sequence_number(from)` is unchanged, so the recomputed `expected_message` still matches the signature, and the transfer succeeds again, moving another `N` tokens.
4. Step 3 repeats until `from`'s USDK balance is exhausted, at which point `primary_fungible_store::transfer_with_ref`/underlying withdraw fails — but by then far more than the intended `N` tokens have been stolen.

Note: This module is example/reference code (`aptos-move/move-examples/fungible_asset/stablecoin`), not production framework code deployed at a privileged address; its mainnet relevance depends on whether/how it (or code copied from it) is actually deployed as a custody-bearing stablecoin contract. I was not able to verify from the available index whether this exact contract is deployed on mainnet — this should be confirmed with a Devin session before treating it as a live mainnet finding.

    public fun transfer_from(
        spender: &signer,
        proof: vector<u8>,
        from: address,
        from_account_scheme: u8,
        from_public_key: vector<u8>,
        to: address,
        amount: u64,
    ) acquires Management, State {
        assert_not_paused();
        assert_not_denylisted(from);
        assert_not_denylisted(to);

        let expected_message = Approval {
            owner: from,
            to: to,
            nonce: account::get_sequence_number(from),
            chain_id: chain_id::get(),
            spender: signer::address_of(spender),
            amount,
        };
        account::verify_signed_message(from, from_account_scheme, from_public_key, proof, expected_message);

        let transfer_ref = &borrow_global<Management>(usdk_address()).transfer_ref;
        // Only use with_ref API for primary_fungible_store (PFS) transfers in this module.
        primary_fungible_store::transfer_with_ref(transfer_ref, from, to, amount);
    }
