### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that authenticates the webhook only covers the raw request body. The `shop` field that downstream handlers use to attribute the webhook to a specific merchant is therefore unauthenticated, letting any holder of a validly-signed webhook (i.e., any merchant/dev store that has installed the app) relabel it as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only the raw body, and `Request#shop` is read straight from a header that plays no part in that signable string: [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC-SHA256(client_secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For webhooks, `to_signable_string == @raw_body`, so the signature proves only "this body was HMAC'd with the app's client secret" — it says nothing about which shop the header claims to be from. `Registry.process` nonetheless trusts `request.shop` unconditionally once the HMAC check passes and forwards it straight into the handler's tenant-scoped data: [3](#0-2) 

This is the exact bug class from the reference report: a field that participates in the trust/routing decision (`historicalSummaryIndex` there, `shop-domain` header here) is not bound by the cryptographic check that is assumed to cover it (bit-size check there, HMAC coverage here). The equality that should hold — `shop authenticated by HMAC == shop used to key per-tenant processing` — is broken because the HMAC never binds `shop` at all.

Because Shopify webhooks for a given app are all signed with the same `client_secret` regardless of which shop triggered them, any shop that installs the app (an unprivileged action available to any merchant, including the attacker's own free/dev store) can receive a legitimately-signed webhook whose body and signature stay valid for any shop identity, and simply replay it with a different `x-shopify-shop-domain` header.

### Impact Explanation
Any host application built on this gem that keys per-tenant behaviour off `WebhookMetadata#shop` (e.g., `shop/redact`, `customers/data_request`, `app/uninstalled`, order/customer webhooks used to update per-shop records) can be made to process a forged event "as" a shop the attacker does not own, since the gem provides no authenticated binding between the HMAC and the shop header. This is a cross-tenant integrity issue: an attacker-controlled shop can inject webhook events attributed to a victim shop into the app's tenant-scoped processing pipeline, which the rules classify as Critical (cross-tenant access).

### Likelihood Explanation
Likelihood is high for any app that trusts `WebhookMetadata#shop` from this gem: the attacker only needs their own (unprivileged) shop to install the app to obtain a validly-signed webhook body/HMAC pair, then can freely swap the shop header on replay since the gem's own HMAC validation never inspects it.

### Recommendation
Bind the shop identity into the authenticated data used for webhook verification — e.g., require the host app to independently confirm `request.shop` corresponds to a shop with an active app installation/session before trusting it, and/or extend `VerifiableQuery`/`to_signable_string` for webhooks to include the shop domain in the value that is HMAC-verified (mirroring how `AuthQuery#to_signable_string` includes `shop` in its signed parameters at [4](#0-3) ). At minimum, clearly document in `Registry.process` that `request.shop` is not authenticated and must be cross-checked against a known/installed shop before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook, e.g. body `{"id":123}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body using app's client_secret>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
3. Attacker captures this request and re-sends it to the app's webhook endpoint unchanged except:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Utils::HmacValidator.validate` in `Registry.process` ( [5](#0-4) ) recomputes the HMAC over `raw_body` only — unaffected by the header change — and passes.
5. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` with `shop == "victim.myshopify.com"` and dispatches it to the handler, which the host app will treat as an authentic event from the victim shop.
