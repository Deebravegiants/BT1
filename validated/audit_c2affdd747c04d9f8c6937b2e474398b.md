Based on my investigation, I found a genuine identity-binding gap in `TokenExchange.exchange_token`.

### Title
Token Exchange sends `client_secret` to a shop host taken from an unvalidated JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange request (which carries the app's `client_id`/`client_secret`) directly from the `dest` claim of the caller-supplied session token, without ever passing it through `Utils::ShopValidator.sanitize!`. Every sibling method that builds a request host from a `shop` string (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` first; `exchange_token` is the only credential-carrying code path that skips this check.

### Finding Description
In `exchange_token`, the shop used to build the request session is taken straight from the decoded JWT: [1](#0-0) 

Compare this to `migrate_to_expiring_token` in the same file, and `client_credentials`/`refresh_access_token`, which all call `Utils::ShopValidator.sanitize!(shop)`: [2](#0-1) [3](#0-2) 

`dest_shop` (`jwt_payload.shop`) is simply `@dest.gsub("https://", "")` with no domain allow-list check applied: [4](#0-3) 

That unsanitized value is then used to build the `Session`, and `HttpClient` turns `session.shop` directly into the request host that receives `client_id`/`client_secret` in the POST body: [5](#0-4) 

The critical question is whether `dest` can be attacker-influenced while still passing `JwtPayload`'s validation. `JwtPayload` verifies the JWT signature against `Context.api_secret_key` and checks `aud == Context.api_key`, but it does **not** verify that `dest` is a trusted Shopify/myshopify domain, nor that `dest` matches `iss`: [6](#0-5) 

Session tokens (App Bridge `authenticatedFetch` tokens / checkout UI extension tokens) are signed with the app's own `api_secret_key` — the same secret the host application already possesses — and Shopify controls what `dest` is set to when it issues these tokens. Because the token's HMAC is verified with the app's own secret, this is the standard, intended trust boundary for session tokens (unlike the OAuth callback `AuthQuery`, whose `hmac` is a Shopify-computed value proving authenticity of `shop`). In `exchange_token`, however, unlike every other place that builds a request host from a shop string, there is no defense-in-depth domain allow-list check on the value that ends up receiving the `client_secret`. This breaks the equality that should hold everywhere else in the library: `host receiving client_secret == validated Shopify/myshopify domain`.

### Impact Explanation
If the `dest` claim were ever able to diverge from a legitimate Shopify domain (e.g., a compromised/older HS256 key, a downstream bug in claim parsing, or a future code path that constructs a `JwtPayload`-like object from less trusted input), the missing `ShopValidator.sanitize!` call means `TokenExchange.exchange_token` would POST the app's `client_id` and `client_secret` to an arbitrary host — an SSRF-with-credentials condition carrying the app's `client_secret`. This is inconsistent with the defense-in-depth pattern the rest of the library enforces on every other shop-to-host code path.

### Likelihood Explanation
Low under current conditions, because JWT signature + `aud` verification does bind `dest` to a token that Shopify (or an attacker controlling `api_secret_key`, which is out of scope) must have issued. The exploitability is contingent on some other JWT/claim-trust weakness or code path that isn't validated by the current tests. It's best characterized as a missing defense-in-depth control that deviates from the pattern used everywhere else, rather than a demonstrated, immediately triggerable exploit from an unprivileged internet user with no additional assumptions.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` in `exchange_token` before constructing `shop_session`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of how `dest` was derived.

### Proof of Concept
Not independently reproducible as a live exploit from this analysis alone — it requires demonstrating a way to obtain a JWT that passes `JwtPayload`'s signature/`aud` checks with an attacker-chosen `dest` value, which was not found in the reachable code paths reviewed (`JwtPayload`, `Auth::Oauth`, `Utils::SessionUtils`). This is flagged as a code-consistency/defense-in-depth gap rather than a confirmed exploit chain; a background Devin session with test-execution access would be needed to confirm whether any reachable path allows `dest` to carry attacker-controlled content while still passing signature verification.
