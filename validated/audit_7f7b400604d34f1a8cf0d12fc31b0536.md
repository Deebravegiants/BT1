### Title
Excess native-token refund from `dispatch()`'s Uniswap V2 swap is misdirected to `EvmHost` instead of the payer, and the swap carries no slippage/max-input protection — ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap `msg.value` native token for the exact `feeToken` amount needed via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. This is the same bug class as the reported `LendingPool.deposit()` issue: a user-submitted transaction executes against a spot AMM price with no independent slippage bound the caller controls, and — worse than the original report — any unused ETH from that swap is refunded by the router to `address(this)` (the `EvmHost`), not to the original transaction sender, with no on-chain mechanism visible in the reviewed code to return that ETH to the payer. [1](#0-0) [2](#0-1) 

### Finding Description
`dispatch()` is reachable by any unprivileged caller (an `IApp`/`HyperApp` integrator or an EOA) that dispatches an ISMP POST or GET request and chooses to pay the relayer fee in native token via `msg.value` instead of the fee token. The function calls:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
``` [3](#0-2) 

Two distinct but related problems exist here, both stemming from the missing-slippage-protection bug class described in the external report:

1. **No caller-supplied `amountInMax`/slippage bound.** The implicit "max input" is `msg.value` itself, and the "deadline" is `block.timestamp` — i.e., no real deadline protection, since it's always satisfied in the same block. An attacker who front-runs the transaction (e.g., by trading on the WETH/feeToken Uniswap V2 pool) can move the price so that `getAmountsIn(post.fee, path)` increases right before the victim's swap executes. If the manipulated price now requires more ETH than the amounts the victim priced off-chain when computing `msg.value` (typically via `HyperApp.quote()`, which reads the same AMM state moments earlier — [4](#0-3) ), the victim either overpays (up to the full `msg.value` they sent) for the same `post.fee` output, or the call reverts and their transaction fails, exactly mirroring the `LendingPool.deposit()` liquidityIndex front-running scenario — the price the user is charged is no longer the price they computed off-chain, and there is no minimum/maximum output check the user can enforce on-chain.

2. **Misdirected refund (the more severe consequence).** `swapETHForExactTokens`'s `to` recipient for the *output tokens* is `address(this)` (correct — `EvmHost` needs the fee tokens), but the Uniswap V2 router refunds any **unspent ETH** to `msg.sender` of the router call, which is `EvmHost`, not the original transaction sender (`_msgSender()`/`post.payer`). Since the amount of ETH actually needed (`amounts[0]` from `getAmountsIn`) is normally less than a caller's supplied `msg.value` (callers must overpay somewhat to tolerate normal price movement), on every native-fee dispatch some ETH is silently retained by `EvmHost` rather than returned to the payer. Combined with point (1), an attacker can amplify this by manipulating the pool immediately before the victim's transaction to widen the gap between quoted and actual cost, then trade back afterward, extracting value while the victim's leftover ETH is trapped in the host contract rather than refunded.

The `dispatch(DispatchGet)` function has the identical pattern. [2](#0-1) 

### Impact Explanation
This directly matches the required impact categories: **concrete theft/permanent freezing of funds**. Every native-token-funded dispatch call permanently locks the payer's unspent ETH inside `EvmHost` with no visible path in the reviewed code for the original payer to reclaim it, and the lack of slippage protection lets an attacker manipulate the AMM price via front-running to worsen the effective rate a payer receives for their fee payment (mirroring the LendingPool `liquidityIndex` manipulation exactly: front-run, shift the priced rate, victim's transaction executes against the worse rate with no protection). Any user calling `IApp.dispatch{value}()`-style flows in the SDK (`HyperApp.dispatchWithFeeToken`, `TokenGateway.quoteNative`, `IntentGatewayV2.placeOrder` fee-swap path, `HyperbridgeLzEndpoint`) is exposed, since msg.value dispatch is a documented, first-class payment path.

### Likelihood Explanation
High — this is triggered by an ordinary, unprivileged, single transaction (any `dispatch()` call funded with native token), requires no special permissions, and Uniswap V2 pools are permissionlessly manipulable by any actor with capital, especially for pairs with modest liquidity (feeToken/WETH pools configured per-deployment). The refund misdirection triggers on essentially every native-fee dispatch call where the quoted `msg.value` exceeds the exact amount consumed by the swap, which is the normal case.

### Recommendation
1. Refund unspent native token to the original payer: capture ETH balance before/after the swap (or use `swapETHForExactTokens`'s return value `amounts[0]`) and forward `msg.value - amounts[0]` back to `_msgSender()`/`post.payer` via a safe ETH transfer.
2. Add caller-controlled slippage/price protection: expose a maximum acceptable native input (or a minimum acceptable exchange rate) as part of `DispatchPost`/`DispatchGet`, and have `dispatch()` revert if the actual `getAmountsIn` value exceeds it, rather than silently consuming up to the full `msg.value`.
3. Replace `block.timestamp` as the swap deadline with an actual caller-supplied deadline so the transaction cannot be executed arbitrarily far from when the exchange rate was quoted.

### Proof of Concept
Conceptual PoC (cannot be executed without a fork/testnet, but is directly supported by the cited code paths):
1. Attacker observes a pending `dispatch(DispatchPost)` (or `dispatch(DispatchGet)`) transaction from a victim paying with native token, with `msg.value = X` computed off-chain via `HyperApp.quote()` against the current WETH/feeToken pool price.
2. Attacker front-runs with a large WETH→feeToken (or feeToken→WETH) trade on the same Uniswap V2 pool the host uses (`_hostParams.uniswapV2`), shifting the price so `getAmountsIn(post.fee, path)` increases.
3. Victim's `dispatch()` call executes `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`. If the new required input is still ≤ `X`, the call succeeds but consumes more ETH than the victim priced for; the leftover `X - amounts[0]` (smaller than the victim expected, or in the base case just any leftover at all) is refunded by the router to `msg.sender` of the router call — `EvmHost` — not to the victim.
4. Attacker reverses their trade after the victim's transaction lands, profiting from the price impact, while the victim's leftover ETH remains stuck in `EvmHost` with no observed withdrawal path back to them in the reviewed contract code. [1](#0-0)
