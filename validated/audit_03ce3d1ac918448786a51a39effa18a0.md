### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook delivery solely by HMAC-signing the raw request body, while the `shop` identifier that downstream handlers use to key tenant data is read from an HTTP header that is excluded from that signature. Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that has installed the app, any shop that legitimately receives one authentic webhook can replay that exact body/HMAC pair while swapping the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to name a different, victim shop, and the signature check still passes.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from an HTTP header that is never included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) using the app's shared secret: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and other unauthenticated headers) to build the `WebhookMetadata` handed to the app's handler, which is the value host applications use to look up/act on shop-specific session/state: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop used as the tenant key`. Here, the HMAC only certifies "this body was produced with the app's secret"; it does not certify "this body belongs to shop X". Since the secret is identical for every shop that has the app installed, the binding between the signed bytes and the claimed tenant is broken — the `shop` header can be swapped without invalidating the signature.

### Impact Explanation
An unprivileged actor who is merely an installer of the target app on their own store (Shop A) can capture one genuine webhook delivery (body + valid HMAC signed with the app's shared secret) and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to Shop B's domain. `Registry.process` still calls `Utils::HmacValidator.validate` successfully (body unchanged) and dispatches `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` to the handler. Any host application logic that uses `data.shop` to select which tenant's stored session/access token to act on (a documented, expected usage pattern for webhook handlers in this ecosystem) will act on Shop B's context using data that Shop A fabricated — a cross-tenant confusion/spoofing vector, since no shop-specific secret or credential is required, only participation as a normal merchant/installer of the app.

### Likelihood Explanation
Likely for any app that has more than one installed shop, since: (1) webhook payloads and headers are visible to the shop's own endpoint operator / can be observed by anyone with network visibility to a delivery; (2) the shared secret used for all shops means a valid HMAC obtained for one shop's payload remains valid unmodified for a replay with a different shop header; (3) no elevated privileges, tokens, or the app's `client_secret` are ever required by the attacker — only ordinary installation of the target app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signable string used for HMAC verification, or otherwise cryptographically tie the claimed shop domain to the signed payload, so that `Utils::HmacValidator.validate` fails if the shop header is altered after signing. At minimum, document that host applications must not treat `WebhookMetadata#shop` as a trusted tenant key on its own and must cross-check it against other authenticated context (e.g., the webhook's resource ownership) before acting.

### Proof of Concept
1. App is installed on Shop A and Shop B; both share the same `api_secret_key`.
2. Attacker (merchant of Shop A) triggers a webhook event on Shop A's store, capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's endpoint.
3. Attacker resends the identical body and HMAC header to the same endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the shared secret — validation succeeds.
5. The handler receives `WebhookMetadata` with `shop == "shop-b.myshopify.com"` even though the payload actually originated from Shop A, letting the attacker inject spoofed events under Shop B's identity.
