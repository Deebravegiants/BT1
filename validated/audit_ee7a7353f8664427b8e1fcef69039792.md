Webhook tenant identity (`shop`) is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` value that identifies *which tenant* the webhook belongs to is read straight from an unauthenticated HTTP header and handed to the application's handler unchecked. The bytes that are cryptographically verified (`@raw_body`) are not the same bytes that are parsed and trusted for tenant identity (`shopify-shop-domain` / `x-shopify-shop-domain` header), breaking the equality `shop_verified_by_hmac == shop_used_by_handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body, and `#shop` is read directly from the incoming headers with no cryptographic binding to the signature: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` only ever calls `verifiable_query.to_signable_string`, which for `Request` is `@raw_body` — the shop header is never part of the signed material: [3](#0-2) 

`Registry.process` performs the HMAC check and then, without any further verification of `request.shop`, constructs `WebhookMetadata` using that unauthenticated value and passes it straight to the app's handler: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no relation to the HMAC: [5](#0-4) 

Because the signature only covers `@raw_body`, any request whose body is byte-for-byte identical to a body that was legitimately signed by Shopify (for example, a webhook the attacker legitimately receives for their own shop after installing the app) will pass `Utils::HmacValidator.validate` regardless of the `shopify-shop-domain` header value. An attacker can replay that exact `(body, hmac)` pair while substituting an arbitrary `shopify-shop-domain` header naming a victim shop. The equality broken is:

`shop authenticated by HMAC` (nothing — the header is outside the signed scope) vs. `shop stored/used as the tenant key` (`request.shop`, passed into `WebhookMetadata.shop` and delivered to the handler).

### Impact Explanation
This satisfies the Critical bar of "cross-tenant access": a handler that keys any state, side effect, or authorization decision off `WebhookMetadata#shop` (e.g., updating order/customer data, revoking access, writing audit logs, or triggering GDPR redaction flows keyed by shop) can be made to act on behalf of a shop the attacker does not control, using only a body/HMAC pair the attacker legitimately obtained for a different (their own) shop. No `api_secret_key`, access token, or privileged account is required — only the ability to receive one genuine webhook (e.g., by installing the app on any shop) and replay it with a forged header.

### Likelihood Explanation
Exploitation requires only HTTP-level control over headers on a replayed request, which is trivial for any actor who can install the app (a normal, unprivileged flow for public apps) and capture one webhook delivery. The gem provides no additional binding of the shop identity to the cryptographic proof, so likelihood is high wherever a consuming application relies on `WebhookMetadata#shop` for tenant-scoped logic without independent verification (e.g., comparing against a shop already known/registered for that specific webhook).

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the claimed shop to the verified body (e.g., derive/validate the shop from a value that is itself covered by the signature, or require the caller to supply the expected shop and assert equality before dispatch). At minimum, `Registry.process` should verify that `request.shop` matches an expected/registered shop for the topic before invoking the handler, rather than passing the raw header value through unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's shared secret), `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (headers required, but not cross-checked): [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and succeeds (since `B` and `H` are unchanged) — the forged shop header is never checked: [4](#0-3) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the (attacker-supplied-context) payload as if it originated from the victim shop.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
