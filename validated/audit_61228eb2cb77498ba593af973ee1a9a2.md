### Title
Reachable panic via unchecked `.unwrap()` on `checked_sub()` in `process_withdraw` PNL accounting can permanently DoS LP withdrawals - (File: program/src/processor.rs)

### Summary
The direwolf CVE is a reachable-assertion crash: a crafted, boundary-condition input (empty MIC-E comment) reaches an `assert!` that the developer believed could never fail, and the resulting unhandled panic terminates the process. The Raydium AMM program contains an analogous pattern in `process_withdraw`: the post-withdrawal PNL bookkeeping calls `.unwrap()` on the results of `checked_sub()`, which is Rust's idiomatic "this subtraction must never underflow" assertion. If pool state (accumulated via legitimate deposit/withdraw/swap flows and rounding in `Calculator::normalize_decimal_v2` / `calc_take_pnl`) ever drives the operand smaller than the subtrahend, the `unwrap()` panics instead of returning a graceful `ProgramError`, aborting the transaction unconditionally for every future `Withdraw` call against that pool.

### Finding Description
In `process_withdraw`, after computing `coin_amount`/`pc_amount` to disburse and invoking the SPL token transfers/burn, the code updates the pool's PNL tracking fields using chained `checked_sub(...).unwrap()` calls instead of propagating an error: [1](#0-0) 

Specifically:
- `amm.lp_amount = amm.lp_amount.checked_sub(withdraw.amount).unwrap();`
- `target_orders.calc_pnl_x = x1.checked_sub(normalize_decimal_v2(pc_amount,...)).unwrap().checked_sub(U128::from(delta_x)).unwrap().as_u128();`
- `target_orders.calc_pnl_y = y1.checked_sub(normalize_decimal_v2(coin_amount,...)).unwrap().checked_sub(U128::from(delta_y)).unwrap().as_u128();`

`x1`/`y1` are derived from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` after `Self::calc_take_pnl` mutates `delta_x`/`delta_y` and the totals in-place: [2](#0-1) 

Unlike every other error path in this same function (e.g. `.ok_or(AmmError::CalculationExRateFailure)?` for `exchange_pool_to_token`), these four subtractions have no error-handling path — a legitimate withdrawal by any unprivileged LP, once decimal-normalization rounding or PNL delta accumulation drives the minuend below the subtrahend, causes an unconditional panic instead of returning `AmmError`. This mirrors the direwolf bug class precisely: a reachable, unhandled internal-invariant assertion (`assert!`/`unwrap()`) triggered by ordinary (not necessarily "malicious") boundary-value input causes the handling code to abort rather than fail gracefully.

### Impact Explanation
On Solana, a panic inside an instruction handler aborts and reverts the enclosing transaction (no cross-transaction memory corruption), so this is not a validator crash like the direwolf process. However, because `process_withdraw` is the only unprivileged code path (reachable by any LP with attacker-chosen `withdraw.amount` and accounts, no privileged signer required) that lets liquidity providers redeem their LP tokens for underlying coin/pc, if a pool's accumulated PNL/rounding state ever produces the underflow, **every subsequent Withdraw instruction against that pool will unconditionally panic**, permanently freezing all LPs' funds in that pool (no upgrade or admin instruction resets `target_orders.calc_pnl_x/y` or `amm.lp_amount` outside this code path). This satisfies the "permanent freezing of LP funds" impact bar.

### Likelihood Explanation
Likelihood is speculative without deeper analysis of `Self::calc_take_pnl` and `Calculator::normalize_decimal_v2` (whose full underflow-safety proofs were not fully inspected in this pass). The structural absence of `checked_sub` error propagation — where the rest of the same function scrupulously converts calculation failures to `AmmError::CalculationExRateFailure` — indicates the underflow-freedom of these subtractions is an *assumed* invariant, not a *verified* one, which is exactly the failure mode described in the reference CVE. Given rounding in `normalize_decimal_v2` (integer division for decimal scaling) and independent evolution of `delta_x`/`delta_y` via swaps/pnl withdrawals between deposits and withdrawals, an edge case reaching this underflow cannot be ruled out from the code inspected.

### Recommendation
Replace all four `.unwrap()` calls in `process_withdraw`'s PNL-update block (`program/src/processor.rs:1812-1838`) with proper error propagation (e.g. `.ok_or(AmmError::CalculationExRateFailure)?` or a dedicated `AmmError::Underflow` variant), consistent with the error handling already used elsewhere in the same function for `exchange_pool_to_token`. This ensures any invariant violation returns a normal transaction failure instead of an unrecoverable panic path, and should be paired with an audit of `Self::calc_take_pnl` and `Calculator::normalize_decimal_v2` to confirm (or restore) the non-negativity invariants these subtractions rely on.

### Proof of Concept
Exact numeric inputs that trigger the underflow could not be derived without full visibility into `Self::calc_take_pnl`'s delta computation and `normalize_decimal_v2`'s rounding behavior (not fully retrieved in this investigation). Conceptually: an unprivileged LP calls `Withdraw` with `withdraw.amount` sized so that `coin_amount`/`pc_amount` (computed via `InvariantPool::exchange_pool_to_token`, floor-rounded) combined with a `delta_x`/`delta_y` from `calc_take_pnl` (driven by prior swap activity altering `total_pc_without_take_pnl`/`total_coin_without_take_pnl` relative to `target_orders.calc_pnl_x/y`) makes `x1 - normalize_decimal_v2(pc_amount,...) - delta_x < 0` in `U128` arithmetic, causing `checked_sub` to return `None` and the subsequent `.unwrap()` to panic, aborting the withdraw transaction. If this condition becomes persistent for the pool's committed on-chain state, all further `Withdraw` calls repeat the same panic, permanently freezing LP funds.

**Uncertainty note:** I was unable to fully trace `Self::calc_take_pnl`'s implementation and `Calculator::normalize_decimal_v2`'s rounding guarantees within the available tool budget, so I cannot provide concrete numeric account/amount values that deterministically trigger the underflow. This should be verified by inspecting `program/src/processor.rs` (the `calc_take_pnl` function body) and `program/src/math.rs` (`normalize_decimal_v2`) directly, or via a Devin session with full repository access, to confirm exploitability.
