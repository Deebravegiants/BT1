### Title
Webhook `shop-domain` header is trusted for tenant routing but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, then hands the handler a `shop` value taken from an HTTP header that is never included in that signature. An attacker who possesses one validly-signed webhook body (e.g. from their own store where the same app is installed) can replay it to the app's public webhook endpoint with an arbitrary `shop-domain` header and have it accepted as belonging to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines `to_signable_string` to return **only** the raw HTTP body: [1](#0-0) 

The `shop` accessor, however, is read straight from an HTTP header supplied by the caller, with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` and constant-time-compares it to the `hmac` value, which itself comes from another header (`hmac-sha256`): [3](#0-2) [4](#0-3) 

`Registry.process` uses exactly this check as its sole authenticity gate, then immediately forwards `request.shop` to the app's handler as the tenant identifier for the webhook: [5](#0-4) 

The documented handler contract explicitly treats `data.shop` as the trusted shop domain for the webhook, e.g. used to key background jobs (`shop_domain: data.shop`): [6](#0-5) 

Because `api_secret_key` (used to compute the HMAC) is fixed per-app rather than per-shop, the same secret signs webhook bodies for **every** shop that has the app installed. This breaks the intended identity binding:

`shop authenticated by HMAC` == `shop acted upon by the handler`

is false: the shop trusted by the handler (`request.shop`, header-derived) is never covered by `request.hmac` (body-derived only). This is structurally the same class of defect as the C4 SecondSwap finding cited in the prompt — a value that is supposed to be constrained/verified together with another is instead validated independently, letting the check be satisfied while the unguarded field is manipulated at will.

### Impact Explanation
An attacker who can obtain any single valid `(raw_body, hmac)` pair for the target app — trivially achievable by installing the app on their own development/trial store and capturing one real webhook delivery — can replay that exact body+HMAC to the app's public webhook callback URL while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` calls the handler with `shop: "<victim>.myshopify.com"` and attacker-controlled body content. Any host application that keys persistence, background jobs, or business logic off `data.shop` (as the gem's own documentation instructs) will process forged data under the wrong tenant — this is a cross-tenant data injection/corruption vector, satisfying the "cross-tenant access" Critical impact criterion. No access token, `client_secret`, or privileged account is required from the attacker beyond controllable HTTP requests to a public endpoint and one legitimately-signed body they can obtain via their own installation.

### Likelihood Explanation
Likelihood is high for any deployment that follows the gem's documented pattern of trusting `WebhookMetadata#shop` for tenant routing without independently re-validating the shop against session/subscription records. Obtaining a valid `(body, hmac)` pair requires nothing more than installing the target app on an attacker-controlled shop (typical development-store flow) and capturing one webhook delivery, or reusing mandatory webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) which fire for every merchant. The webhook endpoint itself is, by design, a public unauthenticated HTTP endpoint reachable by any internet user.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the signable material verified by the HMAC, or have `Registry.process`/consumers independently verify that `request.shop` corresponds to a shop with an active, previously-established app installation/session before trusting it — never rely on the header value alone once HMAC only covers the body. At minimum, document loudly that `data.shop` from `WebhookMetadata` is unauthenticated and must be cross-checked against known installed shops before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers/receives any webhook, capturing `raw_body` and the `X-Shopify-Hmac-Sha256` header value (valid because it's computed over `raw_body` with the app's `client_secret`, shared across all shops).
2. Attacker sends a POST to the app's public webhook endpoint with:
   - Body: the captured `raw_body` (optionally a body they fully control if the app accepts flexible JSON, since only body bytes—not schema—are signed)
   - Header `X-Shopify-Hmac-Sha256`: the captured, still-valid HMAC
   - Header `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (attacker-chosen, arbitrary)
   - Header `X-Shopify-Topic`: any registered topic
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC.
4. `handler.handle` is invoked with `data.shop == "victim-shop.myshopify.com"` and the attacker's body, even though that body/HMAC pair was never issued by Shopify for that shop. [7](#0-6)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
