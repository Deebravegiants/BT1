### Title
Signup extension mode bypasses biometric pipeline, fraud detection, and enrollment while still reachable via a scanned QR-code combination - (File: `src/plans/mod.rs`)

### Summary
The Sherlock finding describes a resolution function (`triggerEndEpoch`) that reaches a terminal "success/finalize" state without first checking whether a different, more specific precondition (the "null epoch" case) applies — causing funds to be moved down the wrong path. The analogous pattern in `orb-core` is `MasterPlan::do_signup` in `src/plans/mod.rs`, where the signup state machine short-circuits directly to a "success" terminal state whenever `signup_extension_config` is set, without ever routing through the biometric pipeline, fraud detection, or enrollment status checks that a normal signup must pass through.

### Finding Description
In `do_signup`, after biometric capture completes, the code checks: [1](#0-0) 

```rust
if self.skip_pipeline() || debug_report.signup_extension_config.is_some() {
    result.success = true;
    return Ok(result);
}
```

If `debug_report.signup_extension_config` is `Some(..)`, the function returns immediately with `result.success = true`, bypassing:
- `biometric_pipeline` (iris/face code generation),
- `detect_fraud`,
- `build_pcp` / credential issuance,
- `enroll_user` (the actual backend enrollment call that sets `enrollment_status`/`signup_status`).

The `signup_extension_config` is populated from the **scanned QR codes** themselves (both operator and user QR codes must declare a signup-extension mode) in `handle_user_qr_code`: [2](#0-1) 

and is parsed straight from the QR-code payload in `qr_scan::user::Data::from_signup_extension`: [3](#0-2) 

This is structurally identical to the Sherlock bug: a state-resolution function (`do_signup`) checks one condition (`skip_pipeline` or `signup_extension_config.is_some()`) and takes an early "success" branch, without verifying that the precondition for *that* branch (this really is an internal data-acquisition/testing signup, not a real identity enrollment) still holds in the way the rest of the pipeline expects. Just like `triggerEndEpoch` assumed `triggerNullEpoch` would have already been called, `do_signup` assumes that any QR code carrying a `signup_extension_config` must be a legitimate internal-testing flow, and short-circuits state resolution instead of validating the precondition through the normal enrollment path.

The mitigating factor: reaching this branch (parsing `signup_extension_config` from a QR code at all) requires the `internal-data-acquisition` cargo feature to be compiled in (`#[cfg(feature = "internal-data-acquisition")]` gates `from_signup_extension`), and the operator QR scanning path additionally rejects `signup_extension` QR codes unless `self.data_acquisition` is set. This materially limits it to an internal/QA build configuration rather than a standard production build.

### Impact Explanation
If this code path is reachable in a production-configured orb (i.e., built with `internal-data-acquisition` and with `data_acquisition` mode enabled), an attacker presenting a crafted operator+user QR-code pair with a signup-extension mode could cause the orb to report `result.success = true` for the local signup-flow state (used for phase transitions, oneshot exit, and UI feedback) without ever running iris/face fraud checks or committing an actual enrollment record on the backend — a "resolution taken without validating the precondition" bug matching the reported bug class. However, this branch does not call `debug_report.signup_successful()` or set `enrollment_status`, so `after_signup`'s `ui_complete_signup` is not invoked (since `signup_status` remains `None`), and no credentials/PCP packages are uploaded. The primary consequence is therefore state/telemetry misattribution (a `SignupResult { success: true, .. }` for a session that never underwent fraud/liveness checks or enrollment) rather than a full unauthorized identity issuance.

### Likelihood Explanation
Likelihood is low in a real production deployment because: (1) the vulnerable branch requires the `internal-data-acquisition` feature to be compiled into the binary, and (2) an additional `data_acquisition` runtime flag gates whether signup-extension QR codes are even accepted during the operator-QR scan (`src/plans/mod.rs:906-916`). In a build/configuration where these are enabled (e.g., a test/QA fleet accidentally left in this mode, or misconfigured), the path is trivially reachable by anyone able to present two crafted QR codes to the orb.

### Recommendation
- Restrict the `signup_extension_config.is_some()` short-circuit so it can only be reached when `data_acquisition` mode is both compiled in and explicitly enabled at runtime, and never allow it to set `result.success = true` in a way that is later treated as a genuine enrollment success signal.
- Add an explicit assertion/guard in `do_signup` verifying that reaching the early-return branch is only possible when the orb is running in internal data-acquisition mode, mirroring the recommended fix in the report (add a check for the "should not resolve this way" precondition before taking the shortcut, rather than relying on implicit assumptions from earlier QR-code validation).
- Ensure any early-return/short-circuit success paths in the signup state machine are audited to confirm they cannot be conflated with `debug_report.signup_successful()`/`enrollment_status` semantics used elsewhere.

### Proof of Concept
1. Build/run the orb with feature `internal-data-acquisition` enabled and `data_acquisition` runtime flag set to true (as used for internal testing).
2. Present an operator QR code and user QR code that both encode a valid `signup_extension` mode (matching the regex in `QR_CODE_SIGNUP_EXTENSION`, e.g. `userid:<uuid>:1::multi_wavelength::`).
3. `handle_user_qr_code` accepts the pair and populates `signup_extension_config` (`src/plans/mod.rs:1060-1074`).
4. Biometric capture proceeds normally (`biometric_capture`), but afterwards `do_signup` hits the check at `src/plans/mod.rs:558` and immediately returns `SignupResult { success: true, .. }` without running `biometric_pipeline`, `detect_fraud`, or `enroll_user`.
5. Observe that the signup is marked `success: true` at the `MasterPlan::run` level (`src/plans/mod.rs:369`) despite no fraud checks, iris pipeline, or backend enrollment having executed — directly analogous to `triggerEndEpoch` resolving an epoch without checking the null-epoch precondition first.
