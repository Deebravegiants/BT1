### Title
Missing Chainlink L2 sequencer-uptime check in `SimplexPaymaster._getOraclePrice` allows mispriced gas payments during Arbitrum/Base sequencer outages - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster._getOraclePrice` prices every stablecoin gas payment purely from Chainlink `latestRoundData()` staleness (`updatedAt`) and a positivity check, with no check of the L2 sequencer uptime feed. `SimplexPaymaster` is deployed on Arbitrum and Base (per `sdk/packages/sdk/src/configs/chain.ts` addresses and the deploy tooling), both optimistic rollups where Chainlink explicitly requires a `SequencerUptimeFeed` check per its L2 data-feeds guidance, exactly the bug class in the referenced report.

### Finding Description
`_getOraclePrice` is the sole pricing primitive used to convert between the native asset and each registered stablecoin for gas sponsorship: [1](#0-0) 

It only validates `answer > 0` and `block.timestamp - updatedAt <= maxOracleAge`; there is no `AggregatorV3Interface` reference to an L2 `SequencerUptimeFeed`, nor any `isSequencerUp`/`startedAt` grace-period check as recommended by Chainlink for L2 deployments. This mirrors the exact vulnerability class from the reported `JOJOOracleAdaptor.getAssetPrice()` issue: on Arbitrum/Base, when the sequencer goes down, the L2-side Chainlink aggregator can no longer receive fresh updates relayed from L1, yet the last pushed `answer`/`updatedAt` can still sit inside the configured `maxOracleAge` window (up to 24h for stablecoin feeds per the deploy script comment), so `_getOraclePrice` returns a price that is falsely perceived as fresh.

`_tokenPrice` combines `nativeOracle` and the per-token oracle price to compute `prefundAmount` in `_prefund`/`_validatePaymasterUserOp`, and the same price feeds size the AMM `swapAndDeposit` minimum-out guard: [2](#0-1) 

`SimplexPaymaster` is confirmed deployed at `0x7281Bccb4f0BCE44F3B8542d1fC5e51c2F5fC08C` on Arbitrum mainnet: [3](#0-2) 

and the deploy script and decisions log confirm Base and Arbitrum are release targets for this contract: [4](#0-3) 

### Impact Explanation
Any account abstraction user (an unprivileged "bandwidth purchaser" of gas, including intent solvers using this paymaster to sponsor bids per `paymaster-selection-for-a-sponsored-userop.md`) submits UserOps priced through this stale-but-"fresh" oracle during a sequencer outage on Arbitrum or Base. A frozen or lagging price lets a submitter prefund far less stablecoin than the true native-asset cost of gas (or, symmetrically, overpay), draining paymaster surplus/EntryPoint deposit value or letting solvers extract value at the treasury's expense. Because pricing directly gates `_prefund`'s `transferFrom`/`Permit2.permitTransferFrom` amount and the AMM swap slippage guard in `_swapAndDeposit`, a mispriced feed compromises both the sponsorship accounting and the treasury-controlled fee-recycling swap.

### Likelihood Explanation
This requires only a real-world Arbitrum/Base sequencer downtime event (which has occurred historically on these networks) coincident with any user/solver submitting a sponsored UserOp — no privileged role, governance action, or malicious relayer is needed; the flaw is purely in the pricing dependency reachable by ordinary paymaster usage.

### Recommendation
Add a Chainlink `SequencerUptimeFeed` check to `_getOraclePrice` (or a wrapper called before pricing), following Chainlink's documented pattern: read `latestRoundData()` on the sequencer uptime feed, require `answer == 0` (up) and enforce a grace period since `startedAt` before trusting price data, reverting (e.g. with a new `SequencerDown` error) otherwise. Configure the sequencer feed address per-chain alongside `nativeOracle`/token oracles in `Params`/`TokenConfig`, and skip/no-op the check on chains without a sequencer (Ethereum, BSC, Polygon).

### Proof of Concept
1. Deploy/observe `SimplexPaymaster` on Arbitrum (`0x7281Bccb4f0BCE44F3B8542d1fC5e51c2F5fC08C`) or Base.
2. Simulate an Arbitrum/Base sequencer outage (L2 Chainlink aggregator stops receiving relayed L1 updates while its last `updatedAt` remains within `maxOracleAge`, e.g. within the 24h stablecoin heartbeat window per `DeploySimplexPaymaster.s.sol` comment).
3. During the outage, the true market price of the native asset or the stablecoin moves materially away from the frozen `answer`.
4. Submit a sponsored UserOp; `_validatePaymasterUserOp` → `_tokenPrice` → `_getOraclePrice` returns the stale-but-timestamp-valid price (passes both `answer > 0` and the `maxOracleAge` check), so `_prefund` pulls an incorrect stablecoin amount relative to the real gas cost, extracting value from the paymaster/treasury or overcharging the sender.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
