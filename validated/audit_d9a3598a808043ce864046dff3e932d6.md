Based on my investigation, I found a genuine analog in the `evm/tron/contracts/apps/IntentGatewayV2.sol` (Tron variant of the Intent Gateway) that mirrors the Vaadin bug class: validation is performed against a *declared* metadata value, but the actual state that later executes is computed from that same unvalidated, attacker-influenced declared value rather than the *actually observed* result — allowing the check to be bypassed by a mismatch between declared and real values.

### Title
Escrow accounting in Tron `IntentGatewayV2.placeOrder` uses caller-declared `order.inputs[i].amount` instead of actually-received balance for fee-on-transfer/deflationary tokens, permitting escrow-value forgery - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The EVM mainline `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`) was hardened to measure the *actual* tokens received by the gateway (via before/after balance snapshots) and mutate `order.inputs[i].amount` to that measured value before computing the commitment hash and crediting escrow [1](#0-0) . The Tron variant of the same contract (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not perform this measurement: it computes `reducedInputs`/`commitment` and credits `_orders[commitment][token] += reducedInputs[i].amount` directly from the caller-supplied `order.inputs[i].amount`, then calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` without checking what the gateway actually received [2](#0-1) .

### Finding Description
This is the same bug class as the Vaadin advisory: a validation/accounting decision (in Vaadin's case, upload metadata used to accept/reject a file; here, the escrow amount credited and committed to the cross-chain order) is derived from **declared** input rather than from **what was actually observed to occur**. In Vaadin, the start listener validated declared metadata while the real uploaded bytes could diverge. Here, the escrow ledger (`_orders[commitment][token]`) and the `commitment` hash used to authorize solver fills and cross-chain settlement are derived from the user-declared `order.inputs[i].amount`, while the actual tokens transferred into the gateway (`IERC20.safeTransferFrom`) can differ from that declared amount for any fee-on-transfer, rebasing, or otherwise non-standard ERC20/TRC20 token.

The predispatch code path in the same Tron file *does* correctly measure `balance = IERC20(token).balanceOf(dispatcher)` before crediting escrow with `reducedInputs[i].amount` [3](#0-2) , but even there the credited escrow value is still `reducedInputs[i].amount` (the declared/requested amount), not the measured `balance`, so the "dust" delta is only used for the emitted event and the escrow bookkeeping remains keyed to a value the gateway may not actually hold. The direct (non-predispatch) path is worse still: it performs no balance measurement at all before crediting escrow.

Contrast this with the corrected EVM mainline implementation, which snapshots `balBefore`/`balAfter` and overwrites `order.inputs[i].amount` with the true delta before it ever reaches fee computation, commitment hashing, or escrow crediting [4](#0-3) , and the accompanying fee-on-transfer regression tests that pin this behavior [5](#0-4) .

### Impact Explanation
An order placed with a deflationary/fee-on-transfer token on the Tron deployment records an escrow amount (and a `commitment` used to authorize solver fills / cross-chain output delivery) that is **higher** than the tokens the gateway actually holds. When a solver fills the order, `IntentGatewayV2.fillOrder`/cross-chain settlement will attempt to release the over-stated amount, either reverting later (denial of order fulfillment / griefing solvers and users) or, if the token or downstream accounting does not re-check the true balance, allowing the gateway to become insolvent for that token — a permanent freezing/loss-of-funds condition once other users' escrowed balances are drawn down to cover the shortfall. This is reachable by any unprivileged user calling `placeOrder` with an arbitrary fee-on-transfer token, with no special privileges required.

### Likelihood Explanation
Likelihood is high for any deployment of this Tron contract that accepts arbitrary (non-allowlisted) TRC20/ERC20-style tokens, since fee-on-transfer and rebasing tokens are common and the caller fully controls which token is used in `order.inputs`. The EVM mainline contract was already patched for exactly this class of token behavior, indicating the team is aware the bug class is realistic and reachable, but the Tron copy was not updated to match.

### Recommendation
Mirror the mainline `evm/src/apps/IntentGatewayV2.sol` fix in `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot the gateway's (or dispatcher's, for the predispatch path) token balance before each transfer, compute the actually-received amount as `balanceAfter - balanceBefore`, and use that measured value (not the caller-declared `order.inputs[i].amount`) for fee computation, commitment hashing, and escrow crediting in both the direct-transfer and predispatch code paths.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) and a TRC20 token that deducts a 1% fee on every `transfer`/`transferFrom`.
2. Call `placeOrder` with `order.inputs[0] = {token: feeToken, amount: 1000}`, no predispatch.
3. `safeTransferFrom(msg.sender, address(this), 1000)` actually delivers only 990 tokens to the gateway (`balanceOf(gateway)` increases by 990), but `_orders[commitment][token]` is credited with `reducedInputs[0].amount` derived from the declared `1000` (minus protocol fee, still based on 1000, not 990).
4. A solver later fills the order; settlement/refund logic that trusts `_orders[commitment][token]` attempts to move 1000 (or the fee-reduced value from 1000) worth of tokens that the gateway never actually received, causing a shortfall against the escrow ledger.

    /// @notice Fee-on-transfer through the predispatch path: escrow reflects actual received.
    function testPlaceOrder_FeeOnTransferToken_Predispatch() public {
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% transfer fee
        fot.mint(user, 10000 * 1e18);

        uint256 predispatchAmount = 1000 * 1e18;
        // After transferring to dispatcher: 1% fee = dispatcher receives 990
        uint256 dispatcherReceived = predispatchAmount - (predispatchAmount * 100) / 10000;
        // After dispatcher transfers to gateway: another 1% fee = gateway receives ~980.1
        uint256 gatewayReceived = dispatcherReceived - (dispatcherReceived * 100) / 10000;

        // Predispatch: send FOT to dispatcher, the "call" is a no-op (empty calls array)
        TokenInfo[] memory predispatchAssets = new TokenInfo[](1);
        predispatchAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: predispatchAmount});

        // The predispatch call is an empty Call[] dispatch (no-op, tokens just sit on dispatcher)
        Call[] memory emptyCalls = new Call[](0);
        bytes memory predispatchCall = abi.encode(emptyCalls);

        // Inputs: expect the FOT that lands on dispatcher after predispatch
        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: dispatcherReceived});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 500 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: predispatchAssets, call: predispatchCall}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), predispatchAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received (double fee-on-transfer)
        assertEq(fot.balanceOf(address(intentGateway)), gatewayReceived, "Gateway should hold double-taxed amount");

        // Reconstruct commitment
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = gatewayReceived; // mutated to actual received
        bytes32 commitment = keccak256(abi.encode(order));

        assertEq(
            intentGateway._orders(commitment, address(fot)),
            gatewayReceived,
            "Escrow should match actual received after double transfer fee"
        );
    }
