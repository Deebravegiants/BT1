Audit Report

## Title
Node crash via nil-params `vault_publicKeyGet` request bypassing params validation - (File: core/capabilities/vault/gw_handler.go)

## Summary
The Vault gateway's `HandleJSONRPCUserMessage` explicitly fast-paths `vault_publicKeyGet` requests without authorization or params validation, and the corresponding DON-side handler, `GatewayHandler.HandleGatewayMessage`, routes `MethodPublicKeyGet` directly to `handlePublicKeyGet` — bypassing `GatewayVaultRequestProcessor.ProcessRequest`, the only code path that checks `req.Params == nil` for other vault methods. `handlePublicKeyGet` then unconditionally does `json.Unmarshal(*req.Params, r)`, which panics on a nil `Params` pointer.

## Finding Description
Verified in `core/services/gateway/handlers/vault/handler.go` `HandleJSONRPCUserMessage` (lines 404-420): for `vaulttypes.MethodPublicKeyGet`, the handler explicitly skips the authorization/`ProcessRequest` pipeline ("Public key requests don't require authorization... Let's process this request right away") and forwards the raw request to `h.handlePublicKeyGet(ctx, ar)` when no cached key exists, ultimately dispatching to DON nodes.

On the node side, confirmed in `core/capabilities/vault/gw_handler.go`, `HandleGatewayMessage` (lines 180-236) explicitly switches on `req.Method`:
- `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` all go through `h.requestProcessor.ProcessRequest(...)`, which internally validates `req.Params == nil` for `processCreateSecretsRequest`/`processDeleteSecretsRequest`, etc.
- `MethodPublicKeyGet` (line 207-208) instead calls `h.handlePublicKeyGet(ctx, gatewayID, req)` directly, with **no** call into `requestProcessor` and **no** nil check.

`handlePublicKeyGet` (lines 364-368) unconditionally executes `json.Unmarshal(*req.Params, r)`. If `req.Params` is `nil` (JSON `"params": null` or omitted), dereferencing `*req.Params` is a nil-pointer dereference panic. This is a genuine, confirmed gap — the pattern used for the other four methods (nil check before dereference/unmarshal, e.g. in `processCreateSecretsRequest`/`processDeleteSecretsRequest`) is absent for the public-key-get path.

This is reached from `connector.go`'s `readLoop` (lines 268-297), which calls `handler.HandleGatewayMessage` directly from the connector's read goroutine with no local `recover()`. I was unable to fully verify whether the goroutine that launches `readLoop` is wrapped by a top-level panic-recovery mechanism (e.g., `recovery.WrapRecover`, which exists in `core/recovery/recover.go` and is used elsewhere in the codebase). If the goroutine is unrecovered, the panic crashes the whole node process (Go panics in a goroutine terminate the program unless recovered anywhere in that goroutine's call stack); if wrapped by `WrapRecover`, it would still permanently kill the connector's read loop for that gateway connection (since the loop does not restart after a panic), causing a persistent DoS against Vault requests from that node. Either outcome is a legitimate crash/DoS impact triggered by unauthenticated, unprivileged input.

Existing tests (`handler_test.go` lines 1289-1297, `TestVaultHandler_PublicKeyGet`) only exercise `Params: nil` through the gateway-side `handler.handlePublicKeyGet`, which is a *different* method on the gateway-side `handler` struct in `core/services/gateway/handlers/vault/handler.go`, not the DON node-side `GatewayHandler.handlePublicKeyGet` in `gw_handler.go`. That gateway-side method does not dereference `*req.Params` the same way (it operates on `activeRequest`, not raw params), so this specific node-side nil-dereference path is genuinely untested.

## Impact Explanation
This is a legitimate unauthenticated Denial-of-Service against the DON node's Vault capability, triggered purely by a malformed/missing `params` field, matching the class of "crash on missing/unexpected field" bugs like CVE-2017-9217. The affected code path is explicitly exempted from authorization by design, so no credentials, JWT, or allowlist membership are required — any client able to reach the gateway's vault endpoint (and cause a cache miss on the public key) can trigger it. Depending on goroutine panic-recovery wrapping (unconfirmed), this either crashes the entire node process or permanently disables that connector's ability to process further gateway messages — both are concrete, in-scope DoS impacts.

## Likelihood Explanation
High. The vulnerable code path requires no special preconditions beyond a public-key cache miss (e.g., right after startup/cache-expiry), which is a normal, attacker-influenceable/waitable condition. The bug is deterministic given the input and reachable by an unauthenticated actor via the standard gateway HTTP endpoint. No existing validation, authorization check, or nil-guard intercepts this specific request shape on the node-side handler.

## Recommendation
Add an explicit `req.Params == nil` check in `GatewayHandler.handlePublicKeyGet` (`core/capabilities/vault/gw_handler.go`) before dereferencing/unmarshalling, returning a JSON-RPC error response (e.g., `api.UserMessageParseError`) instead of panicking. Apply the same defensive check to any other handler branch reached from `HandleGatewayMessage` that bypasses `GatewayVaultRequestProcessor.ProcessRequest`. Additionally, verify and, if missing, add `recover()`/`recovery.WrapRecover` protection around the goroutine that runs `connector.go`'s `readLoop`, so a single malformed message cannot take down the read loop or the node process.

## Proof of Concept
1. As an unauthenticated client, send to the gateway's vault HTTP endpoint:
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault_publicKeyGet","params":null}
```
2. `handler.HandleJSONRPCUserMessage` (gateway) skips authorization for `MethodPublicKeyGet`; on a public-key cache miss it forwards the raw request via `fanOutToVaultNodes` to DON nodes.
3. On the DON node, `connector.go`'s `readLoop` unmarshals the request (`Params` remains `nil`) and calls `GatewayHandler.HandleGatewayMessage`, which routes to `handlePublicKeyGet`.
4. `json.Unmarshal(*req.Params, r)` in `core/capabilities/vault/gw_handler.go` line 366 dereferences the nil `*json.RawMessage`, causing a panic.
5. Add a Go unit test calling `GatewayHandler.HandleGatewayMessage` (or `handlePublicKeyGet` directly) with `req.Params == nil` and assert it returns an error response instead of panicking — this test does not currently exist and would fail against current code.
