Audit Report

## Title
Unhandled panic (DoS) via crafted `workflowID`/`workflowOwner` in HTTP trigger gateway handler - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

## Summary
`validateHexInput` only enforces a maximum length and hex-decodability, without requiring the `"0x"` prefix to be present, so a 66-character (or 42-character) lowercase hex string without the `"0x"` prefix passes validation for `workflowID` (or `workflowOwner`). This value is later passed unconditionally to `normalizeHex`, which computes `strings.Repeat("0", expectedHexLength-len(hexStr))`; because `hexStr` retains its full un-stripped length, the repeat count goes negative and `strings.Repeat` panics.

## Finding Description
`validateHexInput` [1](#0-0)  only checks that `len(input) > expectedLength` is false, that the string is lowercase, and that `hex.DecodeString` succeeds on the string after trimming a literal `"0x"` prefix if present — it never requires the prefix to actually exist. A 66-character all-lowercase-hex string (e.g., 66 `a` characters) with no `"0x"` prefix satisfies all three checks: its length equals `workflowIDLength` (66, not greater), it is lowercase, and `hex.DecodeString` on the full 66-character string succeeds since 66 is even.

This "validated" value flows into `resolveWorkflowID` [2](#0-1) , which calls `normalizeHex(workflowID, workflowIDLength)` [3](#0-2) . Since the input lacks the `"0x"` prefix, `strings.TrimPrefix` is a no-op, leaving `hexStr` at 66 characters while `expectedHexLength` is computed as `66-2=64`. The repeat count `64-66=-2` is negative, and `strings.Repeat` panics with "strings: negative Repeat count." The same defect applies to `workflowOwner` at length 42.

The call sequence in `HandleUserTriggerRequest` [4](#0-3)  confirms `resolveWorkflowID` runs before `authorizeRequest`, meaning the panic is triggerable pre-authorization. I confirmed this by reading the full source of the file — the code matches the claim precisely. I also examined the existing test suite: `http_trigger_handler_test.go` includes a "missing 0x prefix" test case, but it uses a 64-character hex string (the exact expected trimmed length), which computes a repeat count of `0` and does not panic — this is a materially different input from the exploit's 66-character string, so the existing tests do not cover or catch this bug. [5](#0-4) 

Regarding blast radius: I traced the call path from the HTTP server down. `handleRequest` in `httpserver.go` calls `s.handler.ProcessRequest(...)` synchronously within the `http.HandlerFunc` invoked by Go's `net/http` server [6](#0-5) . `ProcessRequest` in `gateway.go` synchronously calls `h.HandleJSONRPCUserMessage(...)` [7](#0-6) , which synchronously calls `h.triggerHandler.HandleUserTriggerRequest(...)` [8](#0-7) . Because this entire chain executes synchronously within the goroutine that Go's standard `net/http` server spawns per incoming connection/request, and Go's `net/http` server has a built-in `recover()` in `conn.serve()` that catches panics from `ServeHTTP` (logs the panic and closes that connection, without crashing the process), a panic reaching this depth would very likely be contained to the single request/connection rather than crashing the entire node process — a materially different and much lower impact than the "DoS crashes node" claim asserts. I did not find any additional goroutine spawned specifically for this request path that would escape `net/http`'s panic recovery.

## Impact Explanation
This is a real, reachable panic bug, but its practical impact is a single dropped/failed HTTP request (with an ungraceful connection close and an error logged), not a full node-process crash. Go's standard library `net/http` server recovers panics per-request in `conn.serve()`, so unless the gateway is served through some non-standard transport that bypasses this behavior (not found in the reviewed code), an attacker can repeatedly cause failed/reset connections for the HTTP trigger endpoint but cannot bring down the entire gateway process with this vector alone. This does not clearly rise to the level of "node API authentication/role bypass," "key/secret exfiltration," "unauthorized fund movement," or "gateway request impersonation" — it is, at most, a minor availability nuisance (malformed-input handling bug) affecting individual requests, which is a much weaker impact than claimed.

## Likelihood Explanation
Triggering the panic itself is trivial and requires no authentication — any client can send a `workflows.execute` request with a 66/42-character lowercase hex `workflowID`/`workflowOwner` without the `"0x"` prefix. However, given that `net/http`'s built-in recovery isolates the panic to that single request/connection, repeated exploitation only causes repeated single-request failures, not a sustained node-wide outage.

## Recommendation
In `validateHexInput`, require the literal `"0x"` prefix to be present before applying length/hex checks, and/or make `normalizeHex` defensive by clamping the repeat count to `max(0, expectedHexLength-len(hexStr))`, returning an error instead of panicking when the trimmed hex exceeds the expected length. Add a regression test using a 66/42-character lowercase hex string without the `0x` prefix (distinct from the existing 64-character "missing 0x prefix" test).

## Proof of Concept
Send a `workflows.execute` HTTP trigger request with:
```json
{
  "workflow": { "workflowID": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa" },
  "input": {}
}
```
(66 lowercase `a` characters, no `0x` prefix). This passes `validateHexInput` (length == 66, lowercase, valid hex) and panics inside `normalizeHex` via `resolveWorkflowID`. A Go unit test analogous to the existing "missing 0x prefix" test, but using a 66-character (not 64-character) hex string, would reproduce the panic and can be used to verify a fix. Full confirmation of whether this panic escapes per-request isolation (e.g., due to a non-standard server wrapper) would require running the gateway locally and observing whether the panic crashes the whole process or only resets the single connection.

func validateHexInput(input string, expectedLength int) error {
	if input != strings.ToLower(input) {
		return errors.New("must be lowercase")
	}

	if len(input) > expectedLength {
		return fmt.Errorf("hex string too long: expected at most %d characters, got %d", expectedLength, len(input))
	}

	hexStr := strings.TrimPrefix(input, "0x")
	_, err := hex.DecodeString(hexStr)
	if err != nil {
		return errors.New("must be a valid hex string")
	}

	return nil
}

// normalizeHex normalizes a hex string by stripping 0x prefix, padding with leading zeros, and adding 0x prefix back
func normalizeHex(input string, length int) string {
	hexStr := strings.TrimPrefix(input, "0x")
	// length-2 because we'll add "0x" prefix
	expectedHexLength := length - 2
	paddedHex := strings.Repeat("0", expectedHexLength-len(hexStr)) + hexStr
	return "0x" + paddedHex
}

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}

	maxRequestBytes, err := s.config.MaxRequestBytesLimiter.Limit(r.Context())
	if err != nil {
		msg := "Failed to get request size limit"
		s.lggr.Errorw(msg, "err", err)
		http.Error(w, msg, http.StatusInternalServerError)
		return
	}
	source := http.MaxBytesReader(nil, r.Body, int64(maxRequestBytes))
	rawMessage, err := io.ReadAll(source)
	if err != nil {
		s.lggr.Error("error reading request", err)
		w.WriteHeader(http.StatusBadRequest)
		return
	}

	// Optionally extract jwt token from authorization header
	authHeader := r.Header.Get("Authorization")
	jwtToken := ""
	if authHeader != "" {
		jwtToken = strings.TrimPrefix(authHeader, "Bearer ")
	}

	startTime := time.Now()
	rawResponse, httpStatusCode := s.handler.ProcessRequest(r.Context(), rawMessage, jwtToken)
	duration := time.Since(startTime)
	s.hMetrics.RecordRequestDuration(r.Context(), httpStatusCode, duration)
	s.hMetrics.RecordRequestCount(r.Context(), httpStatusCode)

	w.Header().Set("Content-Type", s.config.ContentTypeHeader)
	w.WriteHeader(httpStatusCode)
	_, err = w.Write(rawResponse) //nolint:gosec // G705: response body is written with an explicit Content-Type, not rendered as HTML
	if err != nil {
		s.lggr.Error("error when writing response", err)
	}
}
