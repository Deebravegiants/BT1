## Title
Predictable, unsigned session cookie value enables cross-tenant session hijacking - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/session.rb`)

### Summary
For the non-embedded Authorization Code Grant flow, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser session cookie's value directly to the internal `Session#id`, which is a fully deterministic string derived only from public information (the shop domain, and for online sessions the numeric associated-user id). This value is later read back verbatim by `SessionUtils.cookie_session_id` and used as the lookup key to activate a stored `Session` (and its access token) — with no HMAC, signature, or any proof that the browser presenting the cookie ever completed OAuth for that shop.

### Finding Description
When `Context.embedded?` is false, `validate_auth_callback` builds the response cookie as: [1](#0-0) 

`session.id` is computed deterministically in `Session.from`: [2](#0-1) 

So a non-embedded offline session's cookie value is always `"offline_#{shop}"`, and an online session's is `"#{shop}_#{associated_user.id}"` — both computable by anyone who knows (or guesses) the shop domain and, for online sessions, a small/sequential Shopify user id.

On subsequent requests, the gem trusts this raw cookie value as the session identifier with no cryptographic check: [3](#0-2) [4](#0-3) 

The documented integration pattern instructs host apps to simply store the returned `Session` by this ID and set the cookie as `secure`/`httpOnly` — no mention of also signing/encrypting the cookie value: [5](#0-4) [6](#0-5) 

The broken identity binding is: `cookie value presented by browser == proof of a completed OAuth flow for shop X`. In fact the cookie value is just unauthenticated, attacker-derivable bytes (`session id`) that double as both storage key and bearer credential, with no signature tying them to the server-issued session.

### Impact Explanation
Any unprivileged internet user who knows a target merchant's `myshopify.com` domain (public information) can set the `shopify_app_session` cookie to `offline_<target-shop>.myshopify.com` in their own browser. If the host app's session storage returns the previously persisted `Session` for that ID (which it will, once the target shop has installed the app and stored an offline session as instructed by this gem's own docs), the attacker's browser is treated by the host app as an authenticated session for that shop, and subsequent API calls are signed using the target shop's stored offline access token. This is cross-tenant access to another merchant's data/API access token without ever performing OAuth, credentials, or interception — a critical authentication-bypass class impact.

### Likelihood Explanation
High for offline sessions: the ID `"offline_#{shop}"` requires zero secret knowledge — only the shop domain, which is public. For online sessions the associated-user id may need to be guessed/enumerated, but Shopify staff/user ids are often small sequential integers, making brute force practical. The only precondition is that the host app follows this gem's own documented, unmodified example (plain cookie with the session id as value, no additional signing) — which is exactly what the docs show.

### Recommendation
Do not use the raw, predictable `Session#id` as the browser-facing cookie value. Instead:
- Generate a cryptographically random, unguessable session token distinct from the storage key, and store a mapping (token → session id) server-side, or
- Sign/encrypt the cookie value (e.g., via Rails' `cookies.signed`/`cookies.encrypted`) so it cannot be forged or predicted by outside parties, and update `docs/usage/oauth.md` to explicitly require this.
- At minimum, update `SessionUtils.cookie_session_id`/`current_session_id` and the docs to make clear that the raw cookie value must never be trusted as an authenticated identity without an accompanying signature.

### Proof of Concept
1. Victim shop `victim-shop.myshopify.com` installs an app built with this gem in non-embedded mode; the app persists an offline `Session` keyed by `session.id == "offline_victim-shop.myshopify.com"` per `Session.from` (`lib/shopify_api/auth/session.rb:107-118`) and `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:100-110`).
2. Attacker, with no relationship to the app or shop, opens the app's domain in their browser and manually sets:
   `document.cookie = "shopify_app_session=offline_victim-shop.myshopify.com"`.
3. Attacker issues any authenticated request to the host app. The host calls `SessionUtils.current_session_id(nil, cookies, false)` → `cookie_session_id(cookies)` (`lib/shopify_api/utils/session_utils.rb:19-37,68-71`), which returns `"offline_victim-shop.myshopify.com"` verbatim.
4. Host app's `SessionRepository.load_session("offline_victim-shop.myshopify.com")` (per documented pattern) returns the victim shop's real `Session`, including its live access token.
5. Attacker's request is now served using the victim shop's access token — cross-tenant access achieved with zero credentials.
