Based on my review of the in-scope webhook verification code, I found a valid analog to the double-accounting bug class: an identity-binding field that is trusted by the application but not covered by the cryptographic signature.

### Title
Webhook shop-domain/topic identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` (and `topic`) headers — which are never included in the signed content — as the tenant identity handed to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the signature [3](#0-2) .

`Registry.process` validates only the HMAC and then immediately constructs `WebhookMetadata` from these unsigned header values, handing `shop: request.shop` and `topic: request.topic` to the app's handler as trusted tenant identity: [4](#0-3) .

The identity binding that should hold is: `hmac_valid(body) == true` should imply `(body, shop, topic)` were jointly produced/authorized by Shopify for that specific shop. In reality only `hmac_valid(body)` is checked, so `shop` and `topic` are unauthenticated relative to the signature — exactly the "field acted on but not covered by the HMAC" pattern.

### Impact Explanation
Because the app's own `client_secret`/API secret key is shared across every shop that installs the app, Shopify computes webhook HMACs using that same per-app secret for all its merchants' shops. An attacker who controls their own (attacker-owned) installed shop can legitimately receive a Shopify-signed webhook whose body+HMAC pair is valid for the app's secret. Since the `shop-domain` header carrying the tenant identity is not covered by that signature, the attacker can replay the same body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or topic) header to name an arbitrary victim shop. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `shop: <victim-shop>` to the handler [5](#0-4) . Any host application that uses the resulting `WebhookMetadata#shop` to select which tenant's data/session to act on will process attacker-supplied data under a victim shop's identity — a cross-tenant confusion/data-injection vector.

### Likelihood Explanation
Any internet user who can install the target app on a shop they control (a normal, unprivileged self-serve action) can obtain a validly-signed webhook body for that app. The webhook endpoint is by design a public, unauthenticated HTTP endpoint, so replaying the captured body with a forged `shop-domain` header requires no special access, secret, or privileged account.

### Recommendation
Bind the header-derived `shop` (and `topic`) values into the signed content that `HmacValidator` verifies (e.g., include them in `to_signable_string`, or separately verify the `shop` against a per-installation secret/session before dispatching to the handler), so that a value produced for one shop cannot be replayed and attributed to another.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining a legitimate webhook delivery with raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret).
2. Attacker sends `POST /webhooks` to the victim app with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because only `B` is checked [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the host app to treat attacker-controlled data as originating from the victim shop.
