### Title
Stale operator-QR authorization window used to gate signup after its expiration has effectively elapsed - (File: src/plans/mod.rs)

### Summary
The reported Arcade bug is a boundary/synchronization flaw: a single point-in-time comparison (`block.timestamp` vs `dueDate`) is used to gate a privileged action (`claim`), with no grace period to account for the time it takes for the counter-action (`repay`) to land. `orb-core` has a structurally analogous pattern: the operator QR-code's authorization validity is checked once against `operator_qr_expiration_time` via `Instant::elapsed()`, but the subsequent, potentially lengthy signup flow (user QR scan, biometric capture, backend enrollment) is then carried out using that same already-captured `operator_data` without any re-validation at the moment the authorization is actually consumed.

### Finding Description
In `scan_remaining_qr_codes`, the freshness of the operator's authorization is decided by a single boundary check: [1](#0-0) 

If `operator_data.timestamp.elapsed() < operator_qr_expiration_time` holds at the moment of the match, the orb proceeds to call `self.scan_user_qr_code(orb, &operator_data)` (which can take up to `self.qr_scan_timeout`, default `QR_SCAN_TIMEOUT` = 70s) and then hands the *same, unrevalidated* `operator_data` into `do_signup`: [2](#0-1) 

`do_signup` itself re-derives `operator_qr_expiration_time` from config and calls `scan_remaining_qr_codes` again, but by that time the QR-code, once matched as "not yet expired," is consumed for the rest of the signup — including a 3-second sleep, biometric capture, and backend enrollment — all of which can add tens of seconds beyond the original boundary check, with no re-check of `operator_data.timestamp` immediately before backend calls that rely on the operator's session location/authorization (`verify_user_qr_code`, `backend::user_status::request`): [3](#0-2) [4](#0-3) 

This is the same root-cause pattern as the Arcade report: a single, non-buffered timestamp comparison determines whether a security-relevant window is "still open," and everything that happens afterward assumes that decision remains valid, even though real elapsed wall-clock time during the subsequent multi-step, network-bound process can push the actual usage well past the intended validity boundary. The config field itself documents this as an authorization boundary, not a soft UX timeout: [5](#0-4) 

The equivalent check is also present when initially deciding whether to keep or re-scan the operator code: [6](#0-5) 

### Impact Explanation
The `operator_qr_expiration_time` boundary exists to bound how long an operator's location/identity data (used by the backend to validate user QR codes and enforce operating-location/fraud constraints, see `LocationData` in `src/backend/operator_status.rs`) may be trusted for authorizing a signup. Because the freshness check is performed once and not re-verified at the point where that operator context is actually used to validate the user and drive enrollment, a signup can be authorized and carried through to completion using operator location/authorization data that is, in effect, stale relative to the configured trust window by the time biometric capture and backend validation occur. This can result in a signup being processed under operator authorization/location constraints that no longer strictly hold, i.e., a form of misattributed signup context — the class of impact the validation rules require (unauthorized/misattributed signup state).

### Likelihood Explanation
This is reachable in the normal, unprivileged flow of every signup (no operator/hardware compromise needed): it only requires the natural delay between operator QR scan and the subsequent user QR scan / biometric capture / backend validation approaching or exceeding `operator_qr_expiration_time` (default `Duration::from_secs(60 * 60 * 23)`, i.e., ~23 hours, per `src/config.rs`). While the default window is large, it is backend-configurable (`operator_qr_expiration_time` in `src/backend/config.rs`), and the check-then-use gap exists regardless of the configured value — the boundary is enforced only at entry, not at the point of actual use, so any deployment tuning this value down (e.g., for tighter operator-session security) inherits the same TOCTOU-style gap the Arcade report describes.

### Recommendation
Re-validate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` immediately before it is used to authorize security-relevant actions (i.e., right before `verify_user_qr_code`/`backend::user_status::request`, and again before final enrollment), rather than only at the top of `scan_remaining_qr_codes`. Alternatively, thread a hard deadline (`Instant` cutoff) through `do_signup` and `scan_user_qr_code`/`verify_user_qr_code` so that any elapsed time consumed by scanning or capture is deducted from the trust window, and abort/re-scan the operator code if the deadline is breached before the user-authorization backend call is made — mirroring the "grace-period"-style fix but applied as a strict re-check rather than a leniency extension, since here the risk runs the opposite direction (stale authorization being used, not premature invalidation).

### Proof of Concept
1. Configure (or accept default) `operator_qr_expiration_time`.
2. Scan operator QR code; `operator_data.timestamp` is set to `Instant::now()` (`src/plans/mod.rs:849-853`).
3. Immediately after, `scan_remaining_qr_codes` evaluates `operator_data.timestamp.elapsed() < operator_qr_expiration_time` → true, and enters the `QrCodes::Operator { .. }` branch (`src/plans/mod.rs:806-820`).
4. `scan_user_qr_code` runs, which can take up to `qr_scan_timeout` (default 70s) to complete; further processing in `do_signup` (3s sleep + biometric capture + enrollment) adds more elapsed time.
5. No point after step 3 re-checks `operator_data.timestamp.elapsed()` against `operator_qr_expiration_time` before this operator context is used in `verify_user_qr_code` → `backend::user_status::request` (`src/backend/user_status.rs:112-144`) to authorize and validate the signup.
6. If `operator_qr_expiration_time` is configured tightly (e.g., minutes) to bound operator-session risk, a signup that starts just inside the window can complete using an operator authorization context that has, in real elapsed time, already exceeded the configured trust boundary — with no re-validation ever performed.
