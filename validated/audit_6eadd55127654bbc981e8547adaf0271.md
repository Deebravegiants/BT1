Confirmed: `placeOrder` does not validate that `order.output.assets[i].amount` is nonzero — only `order.inputs[i].amount == 0` is checked (`revert InvalidInput()`), and output tokens are only checked for duplicates, not zero amounts. This means a user can legitimately create an order with a zero-amount output leg (e.g. a multi-leg order where one leg is a placeholder/declined leg, as the SDK's `zipFillLegs` comment even documents: "A missing or null amount ... becomes a zero quote").

### Title
Cross-chain `fillOrder` permanently reverts and freezes escrow when a solver fills a zero-amount output leg with a token that reverts on zero-value transfers - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`_fillCrossChain` unconditionally calls `IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare)` for every output leg without checking whether the resulting amount is zero. Because `placeOrder` never rejects a zero-amount output asset, and cross-chain fills are strictly all-or-nothing (no partial fill support), a legitimately zero-valued leg paired with a "revert on zero transfer" ERC-20 token permanently blocks fill of the whole order, freezing all escrowed input tokens.

### Finding Description
`_fillCrossChain` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` (lines 164-220) loops over `order.output.assets` and, for each ERC-20 output leg, executes: [1](#0-0) 

`totalRequired` comes directly from `order.output.assets[i].amount`, which is never validated to be nonzero in `placeOrder` (`evm/src/apps/IntentGatewayV2.sol` lines 194-211 only check `order.inputs.length == 0` and reject duplicate output tokens, never a per-asset zero amount): [2](#0-1) 

If `totalRequired == 0` and the solver quotes `solverAmount == 0` for that leg (a legitimate "declined leg" pattern, matching the SDK's own documented convention for multi-leg orders), `beneficiaryShare` is also `0`, so the code executes `IERC20(token).safeTransferFrom(msg.sender, beneficiary, 0)`. ERC-20 tokens that revert on zero-value transfers (per the weird-erc20 catalogue referenced in the original report) will cause this call — and therefore the entire `fillOrder` transaction — to revert unconditionally, every single time, for every solver.

Unlike the same-chain path (`IntrinsicIntents.sol`), which explicitly special-cases `remaining == 0 || solverAmount == 0` with a `continue` to skip the transfer: [3](#0-2) 

`_fillCrossChain` has no equivalent skip. Because cross-chain orders are all-or-nothing (no partial fill), there is no way to route around the reverting leg — the order can never be filled by any solver.

### Impact Explanation
Cross-chain orders are permanently unfillable once they contain a zero-amount output leg denominated in a zero-value-reverting token. Since cross-chain fills are strictly all-or-nothing, no solver can ever complete the fill, and the full escrowed input tokens (`order.inputs`, held by `IntentGatewayV2` on the source chain) remain locked forever — the order can also never legitimately reach `RedeemEscrow`, and cancellation flows depend on separate cross-chain GET/timeout logic (subject to the order's `deadline`), so if these are misconfigured or the deadline is far out, funds are frozen indefinitely. This is a permanent freezing-of-funds condition matching Sherlock's Medium severity bar for the analogous Kairos issue.

### Likelihood Explanation
Reachable by any ordinary user submitting a normal `placeOrder` transaction with a multi-leg output list containing a zero-amount leg (a pattern the codebase's own SDK anticipates and encodes, `zipFillLegs`), combined with any token in that leg's slot that reverts on zero-value transfers (a documented, common weird-ERC20 behavior, e.g. certain compliance/vault or older tokens). No privileged role or malicious actor is required — this is a straightforward account of an underspecified input, so likelihood is Medium.

### Recommendation
In `_fillCrossChain`, skip the ERC-20/native transfer when the leg's total transfer amount (`totalRequired + beneficiaryShare`, and separately `protocolShare`) is zero, mirroring the guard already present in `_fillSameChain`/`IntrinsicIntents.sol`. Alternatively, reject zero-amount output assets in `placeOrder` validation to eliminate the zero-value leg case entirely.

### Proof of Concept
1. User calls `placeOrder` with a cross-chain order whose `output.assets` includes one leg `{token: WEIRD_ERC20, amount: 0}` alongside a normal nonzero leg. `placeOrder` accepts this (no zero-amount check on outputs), escrowing the input tokens.
2. Any solver calls `fillOrder` with `options.outputs` supplying `amount: 0` for that leg (satisfying `solverAmount < totalRequired` check since `0 < 0` is false) and the correct amount for the other leg.
3. Inside `_fillCrossChain`, for the weird-token leg, `totalRequired + beneficiaryShare == 0`, so `IERC20(WEIRD_ERC20).safeTransferFrom(solver, beneficiary, 0)` is executed and reverts (per weird-erc20 "revert on zero-value transfers" behavior).
4. The entire `fillOrder` transaction reverts. This is deterministic and repeats for every solver attempt — the escrowed input tokens can never be released via fill, only (if at all) via the separate cancel/timeout GET-proof path.
