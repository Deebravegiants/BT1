Found the identity-binding break: the webhook HMAC covers only the raw body, but the `shop` and `topic` fields the app trusts for tenant routing are taken from unauthenticated headers.

### Title
Webhook `shop`/`topic` identity fields are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop` and `topic` values from the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` HTTP headers, but `to_signable_string` only returns `@raw_body`, meaning the HMAC signature validated by `HmacValidator.validate` never covers those headers. The gem verifies "bytes signed" (raw body) but the application-facing API surfaces and trusts "bytes parsed" (headers) for tenant identity, breaking the equality `signed_bytes == trusted_identity_bytes` required for a correct HMAC binding.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` value using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` — the fields a consuming app is expected to use to route processing to the correct tenant/handler — are read straight from HTTP headers with no cryptographic binding to the signed body: [3](#0-2) [4](#0-3) 

Because Shopify's actual webhook HMAC (`X-Shopify-Hmac-Sha256`) is computed over the raw body only (this matches real Shopify behavior), an attacker who has ever seen one legitimately-signed webhook body/HMAC pair for *any* shop (e.g. via a public test store, a leaked webhook payload, or a shared webhook body used across multiple shops with identical payload structure) can replay that exact `(raw_body, hmac)` pair while substituting arbitrary `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers. `Request#hmac` and `#to_signable_string` will still validate successfully because neither header is part of the signed material, so `Request.new` and `HmacValidator.validate` both accept the forged request as authentic for the attacker-chosen shop.

This is the closest analog to the `compensate()` CR-check bug class: a security check ("is this HMAC valid") is evaluated using different — narrower — content than the identity fields ("which shop/topic does this app act on") that the rest of the code trusts as if they had been covered by that check.

### Impact Explanation
If a host application does what the gem's own `Request` object encourages (read `request.shop` and `request.topic` after `HmacValidator.validate` succeeds, and dispatch/process the webhook payload for that shop), an attacker can cause the app to process a forged webhook body under an arbitrary tenant identity of their choosing, as long as they can obtain one valid `(raw_body, hmac)` pair (e.g., from their own store's legitimate webhook, or from any publicly observable webhook traffic). Depending on how the host app uses the shop identity (e.g., to look up/attach access tokens, update tenant-scoped state, or trigger tenant-scoped side effects), this enables cross-tenant data corruption or state confusion. This lands in High severity under "credential leakage / cross-tenant access," since the gem's verification primitive is what's advertised as the authenticity guarantee for `shop`/`topic`, yet those fields sit entirely outside the signed boundary.

### Likelihood Explanation
Exploitation requires the attacker to already possess one legitimately-signed webhook body and its HMAC — trivially obtainable from the attacker's own development/test store (attackers can always subscribe their own shop to webhooks and receive valid signed payloads) since the check is purely: does this body+hmac pair verify against `api_secret_key`, with no shop-specific binding in the signable string. It does not require any elevated credential (no access token or leaked `api_secret_key` needed), matching the in-scope unprivileged-internet-user threat model. Likelihood is Medium-High: no cryptographic secret needs to be broken, only the (well-documented) fact that Shopify's raw-body HMAC does not bind headers, combined with the gem exposing headers as trusted post-verification fields.

### Recommendation
Include `shop`, `topic`, and any other header-derived identity fields consumed by the host application in the value returned by `to_signable_string`, or otherwise cryptographically bind them (e.g., HMAC over a canonical string incorporating headers + body) before exposing `shop`/`topic` as "verified." At minimum, update documentation to explicitly warn that `Request#shop` and `Request#topic` are NOT covered by HMAC verification and must not be trusted for tenant routing without additional out-of-band binding (e.g., cross-checking against the shop associated with the offline session/access token used to register the webhook).

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and subscribes a webhook, legitimately receiving a request with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker replays this exact request to the victim app's webhook endpoint but changes `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or `X-Shopify-Topic`), keeping body `B` and header `H` unchanged.
3. The host app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `HmacValidator.validate(request)`:
   - `to_signable_string` returns `B` (unchanged) [2](#0-1) 
   - `validate_signature` recomputes `HMAC-SHA256(secret, B)` and compares it to `H` via `OpenSSL.secure_compare`, which succeeds because `B` and `H` are identical to the legitimately-signed pair [5](#0-4) 
4. The app, trusting `request.shop == "victim-shop.myshopify.com"` (from the forged header) because `HmacValidator.validate` returned `true`, processes the webhook as if it legitimately originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
