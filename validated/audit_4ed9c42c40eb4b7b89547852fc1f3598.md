### Title
Webhook `shop` (and `topic`/`webhook-id`) header not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking that the HMAC over the raw request body matches, then trusts the `shop` value taken from an unauthenticated HTTP header to route the payload to the merchant's handler as the tenant identifier.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`shop` is read directly from an unsigned header with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., body integrity) before dispatching the handler with `shop: request.shop`, which is exactly the unauthenticated header value: [4](#0-3) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (the raw body) using the app's single, shop-independent `api_secret_key`: [5](#0-4) 

The identity binding the code implicitly assumes is: `shop header == shop that the HMAC/body was generated for`. But the HMAC secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop that has installed the app — it is not a per-shop secret. Because the `shop-domain` header is excluded from the signable string, any party holding one valid `(raw_body, hmac)` pair for their own installation (which they legitimately receive from Shopify when a webhook fires for their own shop) can resend the identical body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a different, victim shop. `HmacValidator.validate` still passes because it only checks the body against the shared secret; `request.shop` then returns the attacker-supplied victim shop domain.

### Impact Explanation
Downstream application code (via `WebhookMetadata.new(... shop: request.shop ...)`) uses this `shop` value as the tenant key for handling/state changes (e.g., persisting the webhook payload against a shop record, deleting data for `shop/redact` or `customers/redact` mandatory topics, updating per-shop state). Since the field consumed for tenant identity is not part of the authenticated (HMAC-covered) data, an attacker who has legitimate access to any one merchant's webhook stream for the app (trivial: install/own an app-installed store) can forge webhook deliveries that the library will accept as authentic for a **different tenant** (victim shop domain), breaking the `shop` binding entirely. This is a cross-tenant identity confusion at the trust boundary the gem is responsible for enforcing.

### Likelihood Explanation
Any user who has installed the app on their own shop legitimately receives a body+HMAC-valid webhook from Shopify. Since the same `api_secret_key` verifies webhooks for all installs of the app, replaying the captured `(raw_body, hmac)` with a modified `shop-domain` header directly to the app's public webhook endpoint requires no secret knowledge beyond what a normal, unprivileged app user already possesses.

### Recommendation
Do not treat `request.shop` as authenticated data derived independently of the HMAC. At minimum, bind the shop domain into the signed payload validation path (e.g., look up the expected shop via an authenticated session/webhook subscription record keyed by `webhook_id`, or require that the topic/shop pair be corroborated against Shopify's GraphQL API before trusting it), rather than passing the raw unauthenticated header straight into `WebhookMetadata`.

### Proof of Concept
1. App is installed on attacker-owned store `attacker.myshopify.com`; Shopify fires a webhook to the app: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request and resends it to the same webhook endpoint, keeping `B` and the HMAC header unchanged but rewriting `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — still valid, since `shop` is excluded from `to_signable_string`.
4. `handler.handle(data: WebhookMetadata.new(shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"`, even though the payload actually originated from the attacker's own store. [4](#0-3)

          received_signature = verifiable_query.hmac
