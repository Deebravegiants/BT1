### Title
Shared `CallDispatcher` balance is swept whole-cloth by `IntentGatewayV2.placeOrder`, letting a composed transaction steal another party's residual tokens - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`CallDispatcher` is a single, permanently-deployed, address-pinned contract shared by every `IntentGatewayV2` order and every `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain delivery on a chain. When `placeOrder` executes predispatch calldata, it credits the order's escrowed input by reading the dispatcher's *entire* current token balance rather than the amount actually produced by that order's own predispatch transfer/call. This is structurally identical to the ParaSpace bug: a shared pool contract's `balanceOf(address(this))` is swept wholesale to whichever unrelated caller next triggers the sweep, letting that caller collect value that belongs to someone else.

### Finding Description
`CallDispatcher.dispatch` executes attacker/sender-supplied `Call[]` in its own context and holds a `receive() payable` fallback, and it is reused across unrelated flows (`IntentGatewayV2` predispatch/postdispatch, `HyperFungibleToken`/`WrappedHyperFungibleToken` incoming-message calldata execution): [1](#0-0) 

In `IntentGatewayV2.placeOrder`, after the predispatch call runs, the sweep-back loop reads the dispatcher's *full* balance for each token/native asset and transfers all of it to the gateway: [2](#0-1) 

It then measures `received` as the gateway's balance delta and only treats the excess as protocol dust when `received > order.inputs[i].amount`; when `received == order.inputs[i].amount` the entire swept amount is silently accepted as this order's legitimate escrow with no dust event at all: [3](#0-2) 

The same "sweep whatever balance the dispatcher currently holds" pattern also exists in the post-fill calldata path: [4](#0-3) 

Because the dispatcher is a single shared, well-known deployment (its address is published on the contract-addresses page and reused by `HyperFungibleToken`/`WrappedHyperFungibleToken`), an attacker can compose, in one atomic transaction they construct themselves:
1. A relayed cross-chain delivery (`onAccept`) to `HyperFungibleToken`/`WrappedHyperFungibleToken` whose `data` calldata is crafted (e.g., a DEX swap with unfavorable slippage bounds) so that it deliberately leaves residual token balance sitting in the shared `CallDispatcher` after execution: [5](#0-4) 

2. Immediately, in the same transaction, a call to `IntentGatewayV2.placeOrder` with a no-op predispatch call and `order.inputs[i].amount` set to exactly "the attacker's own contribution + the residual balance left behind in step 1." The sweep-back code in `placeOrder` reads `IERC20(token).balanceOf(dispatcher)` (which now includes the victim's leftover tokens) and transfers all of it to the gateway, crediting it in full as the attacker's own order input since `received == order.inputs[i].amount` avoids the dust branch entirely.

The attacker's order (which they fully control as `order.user`) can then be cancelled via `_cancelSameChain`, refunding the entire escrowed amount — including the misappropriated third-party residue — directly to the attacker: [6](#0-5) 

### Impact Explanation
Any tokens left transiently in the shared `CallDispatcher` by an unrelated cross-chain delivery, swap-with-slippage, or any other calldata execution routed through it can be misappropriated by an attacker who times their own `placeOrder` call (or bundles it atomically with the triggering delivery) to land immediately afterward, since the escrow-crediting logic trusts the dispatcher's raw balance rather than tracking amounts attributable to the current call. This is a direct theft of user funds analogous to the ParaSpace `NTokenBAYC` reserve-pool sweep, mediated by a shared, permanently-deployed pool contract instead of a shared NFT-collateral reserve.

### Likelihood Explanation
Exploitation requires only an attacker-authored transaction that composes (a) triggering or waiting for a delivery/predispatch call that leaves residual balance on the well-known `CallDispatcher` address, and (b) a `placeOrder` call with matching input amounts and a trivial no-op predispatch call — both are permissionless, unprivileged operations reachable by any relayer/user, making this practically exploitable whenever any calldata routed through `CallDispatcher` (swap slippage, partial consumption, direct transfers to its public address) leaves it non-empty even momentarily.

### Recommendation
Scope the sweep to the amount actually produced by the current call instead of the dispatcher's raw `balanceOf`/`.balance` — e.g., snapshot the dispatcher's balance immediately before transferring this order's own predispatch assets in, and only sweep `balanceAfter - balanceBeforeThisOrder`, reverting (or diverting strictly to protocol dust with no path back to any single user) any remainder. Alternatively, deploy a dedicated, single-use `CallDispatcher` instance per order/message rather than one shared globally-addressable contract, eliminating cross-order/cross-app balance bleed entirely.

### Proof of Concept
1. Attacker relays (or waits for) a cross-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` delivery whose attached `data` (a DEX swap or similar) executes through the shared `CallDispatcher` and leaves `D` tokens of a given ERC-20 behind due to slippage/rounding, as in `WrappedHyperFungibleToken.onAccept` at `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:326-328`.
2. In the same transaction, attacker calls `IntentGatewayV2.placeOrder` with `predispatch.assets[i].amount = A` (their own funds) and a no-op `predispatch.call`, but sets `order.inputs[i].amount = A + D`.
3. `placeOrder`'s sweep-back loop (`evm/src/apps/IntentGatewayV2.sol:274-311`) reads `balance = IERC20(token).balanceOf(dispatcher) = A + D`, transfers it all to the gateway, and since `received (A+D) == order.inputs[i].amount (A+D)`, credits the full amount as the attacker's escrow with no `DustCollected` event.
4. Attacker calls `cancelOrder` → `_cancelSameChain` (`evm/src/apps/intentsv2/IntrinsicIntents.sol:159-180`), refunding `A + D` directly to themselves, netting `D` tokens that belonged to the unrelated bridging transaction from step 1.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
