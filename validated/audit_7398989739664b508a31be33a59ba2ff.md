### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while `topic`, `shop`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the signed material. `Registry.process` validates the HMAC and then dispatches the handler using these unsigned header-derived values, breaking the binding between "bytes verified" and "bytes acted on."

### Finding Description
`Utils::HmacValidator.validate` verifies a signature computed over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body: [2](#0-1) 

But `topic`, `shop`, and `webhook_id` are pulled straight from request headers, which are not covered by the HMAC at all: [3](#0-2) 

`Registry.process` validates the HMAC and then trusts these unsigned fields to build the dispatched metadata and select the handler: [4](#0-3) 

The identity-binding equality that should hold is:
`bytes_covered_by_hmac == bytes_the_handler_acts_on`

but in this implementation:
`bytes_covered_by_hmac (raw_body) != bytes_the_handler_acts_on (raw_body + shop-domain + topic + webhook-id headers)`

Because `shop` and `topic` are outside the signed scope, anyone who has ever legitimately received one valid `(body, hmac)` pair from Shopify (e.g., by installing the app on their own shop, which requires no special access token or `client_secret`) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` and/or `x-shopify-topic` header. The HMAC still validates (it only checks the body), and `Registry.process` will invoke the handler believing the webhook came from a different shop or represents a different topic than it actually does.

### Impact Explanation
This breaks the shop/topic identity binding relied upon by webhook handlers, allowing an unprivileged actor who can obtain even one valid signed payload (from their own installation) to impersonate a different tenant (`shop`) or a different event (`topic`) to the app's webhook processing logic. Since apps commonly use `WebhookMetadata#shop` to select the tenant record to modify (e.g., mark uninstalled, purge data, update entitlements), this is a cross-tenant integrity issue reachable purely by manipulating HTTP headers of a replayed, previously-legitimate request — no `api_secret_key`, access token, or other credential is required beyond having received one webhook.

### Likelihood Explanation
Any developer/attacker can self-install a public app on their own shop (no special privilege), capture one real webhook `(body, hmac)` pair, and then POST it back to the app's webhook endpoint with modified `shop-domain`/`topic` headers. No cryptographic material is required to forge this — only header manipulation, which is trivial for any HTTP client hitting an internet-facing endpoint.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signable material for webhook requests (or otherwise cryptographically bind them, e.g., verify body content matches expected shop), so that `Utils::HmacValidator.validate` fails if any of these header values are altered relative to what Shopify actually signed.

### Proof of Concept
1. Install the target app (self-service, no elevated privilege) on `attacker-shop.myshopify.com`.
2. Trigger any webhook (e.g., `products/update`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
3. Replay the exact same request to the app's webhook endpoint, but set:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any other registered topic)
   - keep body `B` and header `H` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes.
5. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act as though `victim-shop` sent this webhook, even though it never did.
