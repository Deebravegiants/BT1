Audit Report

## Title
JWT replay protection race condition allows a single one-time trigger token to authorize multiple concurrent workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks JWT replay via `h.jwtCache.isReplay(claims.ID)` and only marks it used via `h.jwtCache.recordUsage(claims.ID)` several lines later, after other checks. Since these are two independent, non-atomic lock acquisitions (`RLock` for the check, `Lock` for the write) with no lock held across `Authorize`'s entire body, two concurrent requests carrying the identical signed JWT can both pass `isReplay` before either calls `recordUsage`, allowing the same one-time token to authorize multiple concurrent workflow trigger executions.

## Finding Description
`Authorize` verifies the JWT, then checks replay status, then (after unrelated authorized-key lookups) records usage: [1](#0-0) 

The cache's check and write are implemented as two separate critical sections with different lock types (`RLock` for read, `Lock` for write), meaning the read-then-write sequence spanning lines 87 and 105 is not atomic: [2](#0-1) 

`Authorize` is invoked directly by `authorizeRequest`, itself called from `HandleUserTriggerRequest`, with no mutex or serialization wrapping the call: [3](#0-2) [4](#0-3)  The only mutex in `httpTriggerHandler` (`callbacksMu`) guards the unrelated `callbacks` map, not the authorization path, and `WorkflowMetadataHandler.mu` guards `authorizedKeys`/workflow metadata, not the `jwtCache`. Thus nothing prevents two goroutines processing two concurrent HTTP requests with the same `req.Auth` JWT from both executing `isReplay` and getting `false` before either executes `recordUsage`.

Existing tests only validate strictly sequential replay attempts, not concurrent ones: [5](#0-4) , [6](#0-5) . The correct atomic pattern is already used elsewhere in the codebase in `RequestReplayGuard.CheckAndRecord`, which performs the existence check and the map write under a single `mu.Lock()`: [7](#0-6) 

## Impact Explanation
This allows a client already holding a valid signer key for a workflow — the same access level required to trigger the workflow legitimately once — to trigger duplicate concurrent executions of the same workflow from a single signed one-time JWT, bypassing the intended one-time-use guarantee. This is an in-scope "unauthorized job run" / quota-bypass class impact: duplicate execution can cause duplicate downstream side effects and resource amplification.

## Likelihood Explanation
Exploitation only requires the caller to send two (or more) HTTP trigger requests carrying the identical signed JWT at effectively the same time — something entirely within a normal client's control, requiring no special privilege beyond already holding a valid workflow signer key. HTTP requests are naturally concurrent, so hitting the race window is straightforward and repeatable.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic `checkAndRecord(jti)` method that holds a single `Lock()` across both the existence check and the map insertion, following the same pattern already implemented correctly in `RequestReplayGuard.CheckAndRecord`. Call this atomic method from `Authorize` instead of the separate `isReplay`/`recordUsage` calls.

## Proof of Concept
1. Register a workflow and an authorized signer key as in `TestWorkflowMetadataHandler_Authorize`.
2. Create a single signed JWT (`tokenString`) for a given request.
3. Spawn two goroutines synchronized with a start barrier (e.g., a channel closed to release both simultaneously) that both call `handler.Authorize(workflowID, tokenString, req)` concurrently.
4. Under `go test -race` with enough repetitions, observe that both goroutines can return `nil` error (both succeed) instead of the second returning "JWT token has already been used" — demonstrating the one-time-use guarantee is bypassable by concurrent replay.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
