### Title
Unprivileged users can hijack another user's WebAPI trigger response via `MessageID` collision in the gateway's legacy handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `webapi/capabilities` gateway handler's `HandleLegacyUserMessage` stores the pending user callback in a shared, handler-wide map keyed solely by the attacker-controllable `msg.Body.MessageID`, with no per-request/per-sender namespacing and no collision check before insertion. When the corresponding node response later arrives, `handleWebAPITriggerMessage` looks the callback up by that same `MessageID` and forwards whatever the node returns to whichever callback is currently stored under that key. An unprivileged external user who submits a request with a `MessageID` equal to (or that overwrites) another concurrently in-flight user's `MessageID` can capture that other user's node response, or cause that user's response to be delivered to the attacker — a cross-user response confusion equivalent in effect to the OpenClaw bug class of "lifecycle event accepted without provenance binding it to the originating request."

### Finding Description
`HandleLegacyUserMessage` unconditionally overwrites the `savedCallbacks` map entry for a given `MessageID`: [1](#0-0) 

There is no check that an entry for that `MessageID` doesn't already exist (unlike the sibling `confidentialrelay` handler, which explicitly rejects a duplicate/in-flight request ID: [2](#0-1) , and unlike `httpTriggerHandler.setupCallback`, which also rejects duplicate request IDs: [3](#0-2) ).

Later, when a DON node responds, `handleWebAPITriggerMessage` matches purely on `msg.Body.MessageID` and delivers the payload to whatever callback is currently registered under that key — it does not verify that the response's `MessageID` still belongs to the original requester, nor cross-check requester identity/session: [4](#0-3) 

The dispatch path in `HandleNodeMessage` only checks that `nodeAddr` matches the message's claimed sender, not that the response is provenance-bound to the specific user request that originated it beyond the raw `MessageID` string: [5](#0-4) 

Because `MessageID` is part of the user-submitted `api.Message` body and is used as the sole map key across all concurrent users hitting this DON's handler, an attacker who submits a request with a `MessageID` value colliding with a currently in-flight legitimate request effectively overwrites the pending entry. Whichever request's node response returns first is delivered to whichever callback (attacker's or victim's) currently occupies that map slot — a direct analog to the "node event accepted without enough provenance tying it to an authorized request" root cause in the OpenClaw advisory, except here reachable by an ordinary unprivileged HTTP client, not requiring node compromise.

### Impact Explanation
An attacker with no special privileges (just standard access to submit gateway legacy WebAPI trigger requests) can:
- Intercept another user's trigger response payload (potential confidentiality impact, e.g., leaking legitimate trigger/webhook result content to the attacker).
- Cause their own crafted response to be silently swapped for a victim's expected response, or cause a victim's callback to be lost/dropped (integrity/availability impact on that request).

This matches the "cross-user response confusion" acceptance criterion.

### Likelihood Explanation
Exploitability requires only that the attacker guess or choose a `MessageID` that coincides with another concurrently in-flight request's `MessageID` within the `CallbackMaxAgeSec` window (default 120s, see `defaultCallbackMaxAgeSec`) — [6](#0-5) . If `MessageID`s are caller-supplied/predictable (rather than being a validated, per-session-bound value), collision is straightforward to trigger deliberately. I was not able to fully confirm from the indexed code how strictly `MessageID` is validated/generated on submission (the `api/message.go` `Validate()` contents were not retrieved before the tool budget ran out), so the exact precondition — whether `MessageID` must be unique/random by protocol convention or can be freely chosen by the caller — remains unverified and should be checked directly in `core/services/gateway/api/message.go`.

### Recommendation
- Reject a `HandleLegacyUserMessage` request if a `savedCallbacks` entry already exists for the given `MessageID`, mirroring the duplicate-ID rejection already used in `confidentialrelay` handler's `newActiveRequest` and `httpTriggerHandler.setupCallback`.
- Bind the saved callback entry to additional request provenance (e.g., requester/session identity or a server-generated nonce) rather than relying solely on the caller-supplied `MessageID` as the map key.
- Consider mandating that `MessageID` be a gateway-generated value, not attacker-supplied, to eliminate the collision vector entirely.

### Proof of Concept
1. Attacker sends a legacy WebAPI trigger request (`HandleLegacyUserMessage`) with `MessageID = "X"` shortly after a victim's own request that also happens to use (or is made to use) `MessageID = "X"` is in flight — both requests dispatched to the same DON.
2. The second request to arrive at the handler overwrites `h.savedCallbacks["X"]` with the attacker's callback (`core/services/gateway/handlers/capabilities/handler.go:411-420`).
3. When a node's response for `MessageID = "X"` is processed by `handleWebAPITriggerMessage` (`core/services/gateway/handlers/capabilities/handler.go:148-162`), it is delivered to whichever callback is currently stored — potentially the attacker's — regardless of which user's original request the node was actually answering.

*Note: full confirmation of `MessageID` generation/validation constraints in `core/services/gateway/api/message.go` was not completed due to tool-call limits; this should be verified in a follow-up session with full repository access.*

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	msg, err := common.ValidatedMessageFromResp(resp)
	if err != nil {
		return err
	}
	if msg.Body.Sender != nodeAddr {
		return errors.New("message sender mismatch when reading from node ")
	}
	start := time.Now()
	switch msg.Body.Method {
	case MethodWebAPITrigger:
		err = h.handleWebAPITriggerMessage(ctx, msg, nodeAddr)
	case MethodWebAPITarget, MethodComputeAction, MethodWorkflowSyncer:
		err = h.handleWebAPIOutgoingMessage(ctx, msg, nodeAddr)
	default:
		err = fmt.Errorf("unsupported method: %s", msg.Body.Method)
	}
	h.metrics.recordHandleDuration(ctx, time.Since(start), msg.Body.Method, err == nil)
	return err
}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	labels := h.extractRequestLabels(req)
	l := h.requestLogger(req, labels)
	l.Debugw("handling confidential relay request", "nodes", len(h.donConfig.Members), "f", h.donConfig.F)

	ar, err := h.newActiveRequest(req, labels, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
