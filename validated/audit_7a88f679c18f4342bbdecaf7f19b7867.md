### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by validating an HMAC over the raw HTTP body only, but reports the webhook's tenant identity (`shop`) from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` passes that unauthenticated `shop` value straight to the app's `WebhookHandler`, so the value the app uses to decide "which merchant does this event belong to" is not the value that was cryptographically verified.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely separate from `@raw_body` and therefore excluded from the signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC using only `verifiable_query.to_signable_string` (i.e., the raw body) and `Context.api_secret_key`, and never touches the `shop` header: [3](#0-2) 

`Registry.process` checks only this body-HMAC and, once it passes, immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identity handed to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`HMAC-authenticated-content.shop == header.shop`

but the actual binding enforced by the code is only:
`HMAC-authenticated-content.body == header's claimed raw_body`

with `shop` entirely outside the signed value. All Shopify apps share the same `api_secret_key`/HMAC secret across every merchant that installs them — the secret is not per-shop. This means any attacker who is a legitimate merchant installer of the target app receives genuinely-signed webhook deliveries (body + valid HMAC) for their own shop. That attacker can capture one such genuine `(raw_body, hmac)` pair and replay it directly to the app's webhook endpoint while substituting an arbitrary value in the `shopify-shop-domain` header (e.g., a victim tenant's domain). `HmacValidator.validate` still succeeds, because it only re-derives the HMAC from `raw_body` and never binds it to the shop header, and `Registry.process` forwards the forged `shop` value unchanged to `WebhookHandler#handle`.

### Impact Explanation
This is a cross-tenant identity confusion: an app that keys any persisted state, side effects, or authorization decisions in its `WebhookHandler#handle` implementation off `WebhookMetadata#shop` (as the documented usage pattern shows/recommends) can be tricked into attributing an attacker-controlled event body to a victim shop. Depending on the topic and how the host app uses the data (e.g., `shop/redact`, `customers/data_request`, order/customer webhooks used to sync or mutate per-tenant records), this can lead to writing, deleting, or disclosing data under the wrong tenant — i.e., cross-tenant access, which matches the Critical impact bucket in scope (cross-tenant access via a broken authentication binding).

### Likelihood Explanation
The attacker only needs to be a legitimate merchant/installer of the target Shopify app (a normal, unprivileged capability, not requiring `api_secret_key`, TLS interception, or social engineering) to obtain one genuinely HMAC-signed webhook body from Shopify. Because the HMAC secret is shared across all shops for a given app, that same `(body, hmac)` pair remains valid when replayed with a forged `shop-domain` header. No credentials belonging to the victim or the app owner are needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or independently verify that the `shop` header corresponds to a shop with a currently valid installation/session before trusting it for tenant attribution. Concretely, `Request#to_signable_string` should incorporate the shop-domain header (or the library should cross-check `request.shop` against an independently stored/authenticated shop record) rather than relying solely on raw-body integrity while treating the shop header as authenticated.

### Proof of Concept
1. App `X` is installed on attacker's own shop `attacker.myshopify.com` and on victim shop `victim.myshopify.com`.
2. Shopify delivers a genuine webhook to `attacker.myshopify.com`'s configured endpoint with headers `shopify-shop-domain: attacker.myshopify.com`, `shopify-hmac-sha256: <valid HMAC of raw_body under app X's shared client_secret>`, and some `raw_body`.
3. Attacker captures `raw_body` and `shopify-hmac-sha256` and replays them to the same app endpoint, replacing only the header value: `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only (`lib/shopify_api/utils/hmac_validator.rb:26-31`) and succeeds, because `raw_body` and the secret are unchanged.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, body:, ...))` with `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the event content actually originated from and describes the attacker's own shop.
6. Any app logic that trusts `WebhookMetadata#shop` for tenant-scoped operations now processes attacker-controlled data as if it belongs to the victim tenant.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
