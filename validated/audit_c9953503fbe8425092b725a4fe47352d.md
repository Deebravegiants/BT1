### Title
Flash-position callback can make risk checks use a stale oracle snapshot after a governance oracle update - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` prefetches oracle prices before invoking an attacker-controlled receiver. That receiver can execute a ready governance operation that changes price-aggregator configuration, after which the controller still evaluates the resulting debt and collateral using the pre-callback prices cached in `Context`.

### Finding Description
`process_flash_position` calls `prefetch_strategy_prices` before entering the flash callback. `Context::fetch_prices` stores the returned feeds in `token_prices`, and `cached_price` retains those values for the remainder of the invocation.

The callback then invokes arbitrary Wasm code through `execute_flash_position`. The controller flash guard prevents reentry into controller monetary entrypoints, but it does not prevent the receiver from calling the governance contract or the governance contract from calling the price aggregator. Therefore, inside the same transaction, the receiver can execute a ready oracle-configuration operation that changes the post-callback price used by the aggregator.

After the callback returns:

1. `collect_collateral_deposits` measures the transferred collateral.
2. `process_deposit` credits it.
3. `strategy_finalize` performs solvency, health-factor, LTV, and collateral-floor checks.
4. Those checks continue reading the prices prefetched before the governance mutation.

The root cause is the check/use gap in `contracts/controller/src/strategies/flash_position.rs`: external state is sampled before an untrusted callback and reused afterward without validating that the oracle configuration or price epoch remained unchanged.

### Impact Explanation
An attacker can open or extend a `Multiply`, `Long`, or `Short` account whose true post-transaction health factor is below one. For example:

- a governance operation lowers the collateral asset’s oracle price while the controller uses the old higher price; or
- a governance operation raises the debt asset’s oracle price while the controller uses the old lower price.

The attacker keeps the borrowed assets while leaving collateral that is insufficient under the oracle state committed by the same transaction. This can produce protocol insolvency and loss of supplier funds.

### Likelihood Explanation
The attacker only needs an unprivileged account, a Wasm `FlashPositionReceiver`, and a governance operation that is already ready to execute. Ready-operation execution is reachable without ownership of the target lending account. The attack is timing-dependent because a suitable oracle-changing governance operation must be executable, but no privileged access, leaked key, malformed parameter, or malicious oracle report is required.

### Recommendation
Do not let prefetched prices cross an untrusted callback without validation. In particular:

- refetch all risk-relevant prices after `invoke_receiver` and before `strategy_finalize`;
- preferably have the price aggregator expose a configuration/price epoch, snapshot it before the callback, and assert it is unchanged afterward;
- apply the same post-callback validation to every externally mutable input consumed by final risk checks;
- alternatively delay all oracle-dependent validation until after the callback.

Refreshing prices after the callback is the safer default because the transaction’s final oracle state is the state under which the resulting position will exist.

### Proof of Concept
Transaction trace:

1. Governance has a ready operation that changes the oracle for collateral token `C` from price `P_old` to lower price `P_new`, or for debt token `D` from `P_old` to higher `P_new`.
2. Attacker deploys a Wasm receiver implementing `execute_flash_position`.
3. Attacker calls:

   `controller::flash_position(caller, account_id = 0, spoke_id, mode = Multiply, debt = D, amount, receiver, data, collaterals = [(C, min_c)], refund_assets = [])`

4. The controller caches the old oracle prices through `prefetch_strategy_prices`.
5. `mint_and_forward` mints debt and sends the measured debt-token receipt to the attacker’s receiver.
6. Inside `execute_flash_position`, the receiver calls the governance ready-operation execution path and commits the oracle change.
7. The receiver transfers at least `min_c` of `C` to the controller and returns normally.
8. `collect_collateral_deposits` measures and deposits `C`.
9. `strategy_finalize` still uses `P_old` because `Context::cached_price` returns the prefetched value.
10. The position passes the controller’s final health-factor check even though it is undercollateralized under `P_new`.
11. The transaction commits both the new oracle configuration and the unsafe debt position. The attacker retains the borrowed proceeds and can abandon or partially liquidate the unhealthy account, leaving the shortfall to suppliers.
