## Finding

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version` and `webhook_id` entirely from HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. `Registry.process` accepts the request once the body-only HMAC checks out, and then hands the *unauthenticated* `shop` header straight to the app's webhook handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers that are never included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the HMAC over whatever `to_signable_string` returns: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC, then forwards the unauthenticated `request.shop` (plus `topic`/`webhook_id`/`api_version`) to the registered handler as trusted metadata identifying which tenant the event belongs to: [4](#0-3) 

The identity binding that should hold is: `hmac(secret, signable_string)` should authenticate **all** fields the handler acts on (`shop`, `topic`, `webhook_id`), i.e. `verified(body) == verified(shop, topic, webhook_id, body)`. In this implementation that equality fails — the signature authenticates only `body`, not `shop`/`topic`/`webhook_id`. Any request that carries a body+HMAC pair that is valid for the app's secret (e.g. a genuine webhook delivery the attacker legitimately received for their own installed shop) can have its `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers rewritten to arbitrary values, and `HmacValidator.validate` will still return `true` because it never inspects the headers.

### Impact Explanation
Because host applications built on this gem are expected to use `WebhookMetadata#shop` (sourced from `Request#shop`) as the tenant key to route/process webhook data (e.g. update records for "that shop"), an attacker who controls a shop that has installed the app can capture one of their own genuine webhook deliveries (valid body + valid HMAC) and replay it against the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. The HMAC check still passes (it only verifies the body), and the app processes attacker-controlled data under a different tenant's identity — i.e., cross-tenant data confusion/write, which maps to the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires no secret material beyond what an ordinary merchant/attacker already possesses by installing the app on their own store and receiving a real webhook (topic, HMAC, and body are all things Shopify sends to any installed shop). Forging arbitrary headers on an HTTP POST while keeping a previously-observed valid body+HMAC pair is trivial and needs no knowledge of `api_secret_key`. The main precondition is that the host application actually trusts `WebhookMetadata#shop`/`#topic` as an authorization/tenant-routing signal, which is exactly the intended and documented usage pattern of `Registry.process` / `WebhookMetadata`.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g. verify the HMAC and then re-check the `shop` against an independently-trusted source such as the session/store the app has itself registered the webhook for) before dispatching to handlers.

### Proof of Concept
1. App has two installed shops: `attacker-shop.myshopify.com` (attacker-controlled) and `victim-shop.myshopify.com`.
2. Shopify sends the attacker a genuine webhook for `attacker-shop.myshopify.com`: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid signature of `B` under the app's secret), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker POSTs the same body `B` and the same `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only — matches `H` — and returns `true`.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from, and was only ever authenticated for, `attacker-shop.myshopify.com`, corrupting the victim's tenant data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
