## Custody Analog Found: Stale `override_threshold` in `multisig_account` Timelock After Owner/Threshold Changes

### Title
Multisig timelock bypass via stale `override_threshold` not re-validated after `num_signatures_required` changes - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The external report's core invariant is: **a protective value is computed once from a snapshot of a live, mutable quantity, and is never re-validated when that quantity changes** — leaving the protection either unenforceable or fully bypassable. The Aptos-native analog is the `MultisigAccountTimeLock` feature in `multisig_account.move`. Its `override_threshold` field is defined to be strictly greater than `num_signatures_required` at the time the timelock is configured [1](#0-0) , but `num_signatures_required` is a separately-stored, independently-mutable field on `MultisigAccount` [2](#0-1)  that can be lowered later (e.g. via `update_signatures_required`, or implicitly via `remove_owners` reducing the owner set). Nothing in the timelock-check path re-validates that `override_threshold > num_signatures_required` still holds.

### Finding Description
`can_execute_with_timelock` allows a transaction to execute immediately, bypassing the configured `timelock_period`, if `num_approvals >= override_threshold`: [3](#0-2) 

`validate_multisig_transaction` (called from the VM prologue) already independently requires `num_approvals >= num_signatures_required` before ever consulting the timelock override path: [4](#0-3) 

The `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` error and its doc comment ("Timelock override threshold must be greater than num_signatures_required and at most the number of owners") [5](#0-4)  show this ordering is an intended, security-critical invariant: the override quorum must always demand *more* signatures than the normal execution quorum, so that the timelock delay provides real protection unless an unusually large supermajority agrees to skip it.

However, `override_threshold` is stored once inside the separate `MultisigAccountTimeLock` resource at configuration time [6](#0-5) , while `num_signatures_required` lives in the `MultisigAccount` resource and can be changed independently by an owner-approved `update_signatures_required` transaction, or the effective quorum can shrink when owners are removed via `remove_owners`. Because the timelock resource is not touched by those operations, the invariant "`override_threshold > num_signatures_required`" enforced only at initial setup silently decays out of validity — exactly like the veCRV balance decaying below the value baked into `votesDifference` at Pledge-creation time in the original report.

If `num_signatures_required` is later reduced to be `<= override_threshold`, then any transaction that clears the *normal* quorum check (`num_approvals >= num_signatures_required`, already mandatory) will also automatically satisfy `num_approvals >= override_threshold`, causing `can_execute_with_timelock` to return `true` unconditionally. The timelock delay — the entire security feature — becomes a no-op for every future transaction on that multisig account, with no re-check, no event, and no way for other owners to detect the silent downgrade except by manually diffing configuration state.

### Impact Explanation
This directly breaks a custody invariant for multisig-controlled assets and authority: the timelock is meant to give owners a delay window to react to (and collectively reject) a malicious or compromised-signer-initiated transaction unless an unusually large supermajority explicitly agrees to override it. Once `num_signatures_required` decays below `override_threshold` (via a legitimate, in-scope `update_signatures_required` or `remove_owners` call), the override condition becomes trivially satisfied by the same signer set that would pass anyway — silently eliminating the intended time-delay protection for all subsequent transactions, including transfers of APT/fungible assets, resource-account/code-object control changes, or auth-key rotations executed as the multisig account. This is a High-severity custody-control weakness: it removes a designed safeguard against fast malicious execution without any explicit re-authorization or warning.

### Likelihood Explanation
Likelihood is Medium-High: `update_signatures_required` and `remove_owners` are both standard, already-exposed multisig operations reachable by the account's own owners through the normal multisig transaction flow (no external attacker or privileged-admin assumption is required — it's a self-service governance action available to the multisig's ordinary participants). No special condition beyond "owners later lower the threshold or remove owners after configuring a timelock" is needed to trigger the decay.

### Recommendation
Re-validate (or automatically clamp/re-derive) `override_threshold` against the current `num_signatures_required` every time either value changes: reject `update_signatures_required` / `remove_owners` calls that would violate `override_threshold > num_signatures_required` for an active `MultisigAccountTimeLock`, or force an explicit timelock re-configuration transaction whenever the owner/threshold configuration changes.

### Proof of Concept
1. Owner set configures `MultisigAccountTimeLock` with `num_signatures_required = 2`, `override_threshold = Some(4)`, satisfying the invariant at setup (`EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` check passes).
2. Owners later approve a normal transaction calling `update_signatures_required` to lower `num_signatures_required` to `4` (or remove owners so the effective threshold recalculates) — this is a standard multisig-approved operation on `MultisigAccount`, and does not touch `MultisigAccountTimeLock`.
3. Now `override_threshold (4) <= num_signatures_required (4)`.
4. Any future transaction that gathers `4` approvals (already mandatory to pass `validate_multisig_transaction`'s quorum assert at line 1353) automatically also satisfies `can_execute_with_timelock`'s override branch (`num_approvals >= override_threshold`), executing immediately with **zero timelock delay**, defeating the configured protection without any additional owner action or warning.

Note: I was not able to fully view the bodies of `update_signatures_required` and `remove_owners` in this session (only test call-sites and struct/constant definitions were retrieved) to confirm textually that they omit any timelock re-check; this should be explicitly re-verified against the full function implementations before treating this as fully confirmed.

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
