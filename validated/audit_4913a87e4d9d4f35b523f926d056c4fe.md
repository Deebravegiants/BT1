### Title
Webhooks::Request#to_signable_string omits the `shop-domain` header from the HMAC, letting an attacker relabel a validly-signed webhook to an arbitrary victim shop - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp` into the signed message, so any change to `shop` after the HMAC is computed invalidates the signature. `Webhooks::Request#to_signable_string` returns only `@raw_body`, so `topic`, `shop`, `webhook_id`, and `api_version` (all `shopify-*` headers) are outside the signed message. Because the app's `api_secret_key` is shared across every shop that installs the app, an attacker who runs their own development shop can take a genuinely Shopify-signed webhook delivered to their own endpoint and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop; `Utils::HmacValidator.validate` still returns `true` and `Registry.process` hands the handler `WebhookMetadata` labeled with the forged victim shop.

### Finding Description
Binding claimed: `HmacValidator.validate(x)` is safe against relabeling iff `x.shop` is part of `x.to_signable_string`.

- `AuthQuery#to_signable_string` includes `shop`: [1](#0-0) 
So in `Oauth.validate_auth_callback`, `Utils::HmacValidator.validate(auth_query)` fails as soon as `auth_query.shop` is changed after the HMAC was computed, because `compute_signature(verifiable_query.to_signable_string, secret)` now produces a different digest: [2](#0-1) [3](#0-2) 

- `Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, but `to_signable_string` only returns `@raw_body`: [4](#0-3) 
`shop`, `topic`, `webhook_id`, and `api_version` are never part of the signed message, so `Utils::HmacValidator.validate(request)` in `Registry.process` depends only on `@raw_body` matching the received HMAC — it is invariant to the value of the `shop-domain` header: [5](#0-4) 

Attacker flow: the attacker installs the app on their own development shop (a legitimate action available to any unprivileged developer) and registers their own webhook endpoint. Shopify delivers a genuine webhook to that endpoint with a valid `raw_body`, `X-Shopify-Hmac-Sha256`, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. The attacker captures this triple, then POSTs the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the target app's real webhook route, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Webhook-Id`/`X-Shopify-Api-Version`) rewritten to the victim shop's domain. Since the app's `api_secret_key` is the same for every installed shop, `Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — unaffected by the header rewrite — and passes. `Registry.process` then invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with the forged victim shop, `at lib/shopify_api/webhooks/registry.rb:198-199`, causing the app's webhook handler to process attacker-controlled body content under the victim tenant's identity.

None of the existing guards catch this: `HmacValidator.validate` only checks body integrity, not header authenticity; there is no `ShopValidator.sanitize!` or state check on the webhook path; `Context.setup?`/`private?`/`embedded?` are irrelevant to webhook processing; Sorbet's runtime typing only enforces `String` types, not header/body binding.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` (as delivered by `Registry.process`) to scope data writes, cache keys, session/token lookups, or downstream API calls per merchant will process attacker-supplied body content under an arbitrary victim shop's identity — this is cross-tenant access/data corruption, matching the Critical category ("one tenant's request touching another tenant's data"). It is fully repeatable: the same captured (body, hmac) pair can be replayed against any number of distinct victim shop domains registered with the same app, since the signature check never varies with the shop header.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's reach: create a free development shop, install the target app, receive one legitimate webhook to their own endpoint, then replay it to the app's public webhook URL with a rewritten `Shop-Domain` header. No secrets, tokens, or victim cooperation are required. The only constraint is that the replayed webhook's `topic`/body must be one the attacker can trigger on their own shop (e.g., `orders/create`), which is trivial for any test order. This makes the attack cheap, deterministic, and repeatable against arbitrary victims of the same app installation.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into `Webhooks::Request#to_signable_string` (or otherwise authenticate them, e.g. by deriving the shop from a signed session/registration lookup rather than trusting the raw header), so any header tampering invalidates the HMAC the same way `AuthQuery` invalidates on `shop` tampering.

### Proof of Concept
```ruby
# test/webhooks/shop_relabeling_test.rb
require_relative "../test_helper"

class ShopRelabelingTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "host",
      scope: "scope", is_embedded: true, api_version: "unstable",
      is_private: false,
    )
  end

  def test_auth_query_shop_mutation_invalidates_hmac
    params = { code: "c", shop: "attacker-shop.myshopify.com", timestamp: "1", state: "s", host: "h" }
    query_string = URI.encode_www_form(params)
    hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, query_string)

    auth_query = ShopifyAPI::Auth::Oauth::AuthQuery.new(**params, hmac: hmac)
    assert ShopifyAPI::Utils::HmacValidator.validate(auth_query)

    # Attacker relabels shop AFTER the hmac was computed
    tampered = ShopifyAPI::Auth::Oauth::AuthQuery.new(**params.merge(shop: "victim-shop.myshopify.com"), hmac: hmac)
    refute ShopifyAPI::Utils::HmacValidator.validate(tampered) # binding holds
  end

  def test_webhook_shop_header_mutation_does_not_invalidate_hmac
    raw_body = '{"id":1,"note":"attacker order"}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", ShopifyAPI::Context.api_secret_key, raw_body),
    )

    original_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
      "x-shopify-api-version" => "unstable",
      "x-shopify-webhook-id" => "wh-1",
    }
    request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: original_headers)
    assert ShopifyAPI::Utils::HmacValidator.validate(request)

    # Attacker relabels the shop header AFTER the hmac was computed, body+hmac unchanged
    tampered_headers = original_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
    tampered_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: tampered_headers)

    assert ShopifyAPI::Utils::HmacValidator.validate(tampered_request) # binding fails: still valid, shop not covered
    assert_equal "victim-shop.myshopify.com", tampered_request.shop
  end
end
```
This mirrors the two required assertions: mutating `auth_query.shop` post-HMAC turns `validate()` false (`AuthQuery` binding holds), while mutating `request.shop` post-HMAC leaves `validate()` true (`Webhooks::Request` binding fails), proving `Registry.process` would accept the relabeled webhook and hand `handler.handle` a `WebhookMetadata` tagged with the attacker-chosen victim shop.
