### Title
Unsigned, deterministic session-cookie value enables session fixation / cross-tenant session hijack in `SessionUtils.cookie_session_id` - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, the gem's session lookup trusts the raw value of the `shopify_app_session` cookie as the session identifier with no signature, HMAC, or other binding proving it was produced by a completed OAuth flow for that browser. Because the session id format is fully deterministic and guessable from public information (the shop domain), an attacker who can set/overwrite this cookie in the victim's browser can force the app to activate another tenant's persisted session (which holds that tenant's real access token).

### Finding Description
`ShopifyAPI::Auth::Session.from` computes session ids purely from public, guessable values: [1](#0-0) 
- offline: `"offline_#{shop}"`
- online: `"#{shop}_#{associated_user.id}"`

After OAuth completes, `Oauth.validate_auth_callback` sets this deterministic id directly as the cookie value for non-embedded apps: [2](#0-1) 

`SessionCookie` is a plain struct with no signature/MAC over its `value`: [3](#0-2) 

And on every subsequent request, `SessionUtils.cookie_session_id` reads back and trusts that raw cookie byte string as the authenticated session id with zero verification: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`session_id_returned_to_caller == session_id_that_this_browser_actually_completed_OAuth_for`

Instead the gem enforces only:
`session_id_returned_to_caller == bytes_present_in_cookie_header`

Because the right-hand side is never authenticated (no HMAC, no server-side nonce, no binding to the OAuth `state`/callback that created it) and the left-hand side format is fully predictable (`offline_{shop}.myshopify.com` or `{shop}_{user_id}`), any mechanism that lets an attacker set a cookie named `shopify_app_session` in the victim's browser (e.g. a cookie fixation vector, a sibling subdomain under a shared parent domain, or a response that reflects/sets cookies) lets the attacker choose exactly which tenant's persisted session gets activated. The host app's session repository (e.g. `ShopifyApp::SessionRepository` per the docs) will look up that id and return the real, stored `access_token` for that shop, which the gem then uses transparently for API calls made in that browser context.

### Impact Explanation
This breaks the tenant/session identity binding without needing `api_secret_key`, an access token, or any credential — the attacker only needs to be able to set a cookie value in the victim's browser and know (or guess) a target shop's `.myshopify.com` domain, which is public. The result is that the victim's browser session gets bound to another merchant's stored access token, i.e., cross-tenant access to that merchant's Shopify Admin API via the app, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitability depends on the attacker's ability to write the `shopify_app_session` cookie into the victim's browser (classic session-fixation precondition — e.g. cookie not scoped tightly enough, shared registrable domain with attacker-controlled subdomain, or any endpoint that sets cookies from request data). This is a real-world common precondition for session-fixation-class bugs, and the docs' own recommendation ("secure, httpOnly cookies") only protects confidentiality/XSS-read, not fixation/overwrite from a sibling origin. Given the deterministic, guessable id format, once cookie-write is achieved the attack is trivial and 100% reliable.

### Recommendation
Do not use a bare, deterministic session id as the cookie's trust anchor. Either:
1. Sign/HMAC the cookie value (e.g., `HMAC(secret, session_id)`) and verify it in `cookie_session_id` before returning the id, or
2. Store a high-entropy, unguessable token in the cookie that maps to the session id server-side (session-store indirection) instead of embedding the shop/user-derived id directly, and
3. Bind the cookie to the OAuth transaction (e.g., via the same nonce/state mechanism already used in `begin_auth`) so a cookie value cannot be replayed/guessed independently of a completed OAuth handshake.

### Proof of Concept
1. Attacker learns/guesses a victim merchant's shop domain, `victim-shop.myshopify.com` (public/enumerable).
2. Attacker computes the deterministic offline session id: `offline_victim-shop.myshopify.com` (per `Session.from`/`SessionUtils.offline_session_id`).
3. Attacker sets the victim's browser cookie `shopify_app_session=offline_victim-shop.myshopify.com` (via any cookie-fixation vector against the host domain/subdomain).
4. Victim (or attacker, using victim's browser context) visits the app; the app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns the attacker-chosen id straight from the cookie: [6](#0-5) 
5. The host app's session repository loads the persisted `Session` for `offline_victim-shop.myshopify.com`, containing the real access token for that shop, and the gem uses it for all subsequent Admin API calls — granting the requester access to the victim shop's data/API.
