### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, then passes the `shop` field — taken verbatim from an unauthenticated HTTP header — to the host application's webhook handler as the trusted tenant identifier. Because the HMAC never binds the `shop` value, a party who can obtain one validly-signed webhook body (e.g., from their own shop, which is legitimate and attacker-controlled) can replay it with an arbitrary `shop-domain` header and still pass HMAC validation, causing the handler to process data under a spoofed/victim shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

The class's `to_signable_string`, which is what actually gets HMAC-verified, returns only the raw request body — it does not include the shop domain, topic, or any other header: [2](#0-1) 

`Registry.process` validates the webhook using exactly that signable string via `Utils::HmacValidator.validate(request)`, and — once the HMAC check passes — forwards `request.shop` unmodified into the `WebhookMetadata` handed to the application's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute and compare the signature strictly against `verifiable_query.to_signable_string`, i.e. the body only: [4](#0-3) 

The `WebhookMetadata` struct treats `shop` as a first-class, trusted identity field consumed by the handler: [5](#0-4) 

The identity binding the gem's API implicitly promises to the host application is: `HMAC-valid webhook request` ⇒ `request.shop is the shop that Shopify signed this payload for`. In reality the binding enforced is only: `HMAC(secret, raw_body) == received_hmac`, with no cryptographic tie to `shop`. This is exactly the pattern called out in scope: *"a field acted on but not covered by the HMAC."* Since `WebhookHandler#handle` is expected to key merchant data (loading/storing/deleting per-shop records) off `data.shop`, and this gem is the one performing the "authentication" step (`Registry.process` → `HmacValidator.validate`) before invoking that handler, the trust boundary is crossed inside this gem's own code, not merely by host misuse.

### Impact Explanation
An unprivileged internet user who operates their own legitimate merchant shop (a normal, unprivileged tenant of the app) can obtain a body+HMAC pair that Shopify validly signed for one of the app's mandatory/registered webhook topics (e.g., `shop/redact`, `customers/data_request`, or any topic with a fixed/predictable body such as `{}`). They can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a different, victim shop domain. `Registry.process` will accept the request as valid (HMAC matches the body) and invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any host application that trusts `data.shop` from this gem to select/act on per-tenant records (which is the documented and intended usage of `WebhookMetadata`) can be tricked into performing actions against, or associating attacker-supplied data with, a different tenant — a cross-tenant integrity violation rooted entirely in this gem's HMAC-validation logic.

### Likelihood Explanation
Exploitability depends on the attacker being able to produce or capture at least one valid `(raw_body, hmac)` pair, which is trivial for topics with static/empty bodies or for any webhook fired from the attacker's own installed shop instance (a completely unprivileged, self-service action). No secrets, tokens, or elevated access are required — only a normal Shopify merchant account and the ability to POST to the app's public webhook endpoint with a modified header.

### Recommendation
Bind `shop` (and ideally `topic`, `api_version`, `webhook_id`) into the HMAC-verified material, or otherwise cryptographically tie the shop domain to the signed payload before it is trusted, e.g., extend `Request#to_signable_string` to include the shop/topic headers in a canonical form that Shopify also signs, or require the caller to independently corroborate `shop` against a value obtained through an already-authenticated channel (such as the session that registered the webhook) rather than trusting the raw header value returned from `Request#shop`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` (unprivileged, self-service).
2. Attacker triggers/receives a webhook for a topic with a fixed body, e.g. mandatory `customers/data_request` with body `{}`, capturing the valid `x-shopify-hmac-sha256` value Shopify computed as `HMAC(secret, "{}")`.
3. Attacker POSTs to the app's webhook endpoint with:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-hmac-sha256: <captured valid hmac for body "{}">`
   - body: `{}`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, "{}")` and finds it matches — validation passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though Shopify never signed anything binding this payload to `victim.myshopify.com`. [3](#0-2) [6](#0-5)
