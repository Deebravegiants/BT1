This confirms the vulnerability. The docs explicitly recommend using `data.shop` as the tenant identifier (`shop_domain: data.shop`) for actions like enqueuing background jobs, and `ShopifyAPI::Webhooks::Registry.process` documentation claims it "will verify the request did indeed come from Shopify" — but the HMAC verification does not actually bind the `shop` field to the signed content.

### Title
Webhook shop/topic/webhook-id are unauthenticated headers not covered by the HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body only, then passes the header-derived `shop` straight through to the host app's handler as `WebhookMetadata#shop`, which the docs explicitly recommend using as the tenant identifier. This breaks the intended binding `HMAC-verified shop == tenant shop acted upon`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC using `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` alone: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from the `shopify-*` / `x-shopify-*` HTTP headers with no cryptographic tie to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then forwards the *header-derived* `shop`/`topic`/`webhook_id` values unchecked to the handler: [3](#0-2) 

This is analogous to the reported bug class: the same cryptographic proof (a valid HMAC computed with the app's shared `api_secret_key`) is accepted for materially different "actions" — here, different tenants/topics — because the identity-critical fields (`shop`, `topic`) are never included in what gets signed.

Since `api_secret_key` is shared across every shop that installs a given app, any merchant (an unprivileged internet user who installs the app on their own store) can legitimately receive genuine webhook deliveries with a valid HMAC over some body content they fully control (e.g. by editing their own store's order note/products to shape the JSON body, or simply replaying any webhook body they received). They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `x-shopify-topic`, `x-shopify-webhook-id`) headers to target a victim shop. `Utils::HmacValidator.validate` will pass because it only checks the body's HMAC, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop/topic, with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant integrity issue: an app built on this gem's documented API (`docs/usage/webhooks.md` explicitly instructs using `data.shop` as the tenant key, e.g. `shop_domain: data.shop`) will process attacker-supplied webhook bodies as if they belong to a shop the attacker does not control. Depending on what the handler does with the data (e.g. updating shop-scoped billing/subscription state, order records, or inventory), this can lead to cross-tenant data corruption or unauthorized state changes attributed to a victim shop — meeting the Critical "cross-tenant access" bar, since the gem's own webhook-processing primitives (`Request`, `HmacValidator`, `Registry.process`) are what create this false trust, not misuse of an undocumented API.

### Likelihood Explanation
Medium-to-High: exploitation requires only that the attacker be able to install the target app on their own (or a trial) shop — a normal, unprivileged action for any Shopify merchant/developer — and be able to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or victim credentials is required.

### Recommendation
Include the identity-critical fields in the signed material, or otherwise cryptographically bind them to the signature, e.g. change `Webhooks::Request#to_signable_string` to incorporate `shop`, `topic`, and `webhook_id` (Shopify's own webhook HMAC only covers the raw body per its API contract, so this would require the gem to independently verify these headers, e.g. by re-deriving/confirming `shop` from the session/API client used to receive the webhook, or documenting loudly that `data.shop`/`data.topic` are unauthenticated and must not be trusted as tenant identifiers without additional verification such as checking the shop against an active, previously-established session/installation record before performing any state-changing action).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) that Shopify delivers with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts `B` to contain whatever payload they want (their own store's order data is fully attacker-controlled).
3. Attacker sends a new POST to the app's webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` and (optionally) any `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H` — validation succeeds since `shop` is never part of the signed string: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, and the host app (following the gem's documented pattern) acts on `victim.myshopify.com` using attacker-supplied data.
