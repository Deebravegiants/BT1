### Title
Prototype pollution via unvalidated key in `SecoKeyval.batch`/`set` allows attacker-controlled data to shadow real keyval values - ([File: libraries/seco-keyval/src/index.js])

### Finding Description
`SecoKeyval.batch(ops)` executes `this._data[key] = value` for each `set` op without any key allowlisting or sanitization [1](#0-0) , and `set(key, value)` simply forwards to `batch` [2](#0-1) . Since `this._data` starts life as a plain object literal (`this._data = {}` in the constructor, or `JSON.parse(...)`/`initialData` in `open()`) [3](#0-2) , assigning to the special key `__proto__` with an object value reassigns the object's actual prototype rather than creating an own `"__proto__"` property. After such a call, `get(key)` — which does a plain `this._data[key]` lookup [4](#0-3)  — will resolve any key that is not an own property of `_data` through the attacker-installed prototype object instead of returning `undefined`.

However, whether this is exploitable in the actual wallet depends entirely on whether `key` in `set()`/`batch()` calls is ever attacker-controlled. I searched the only concrete consumer in this repo, `features/wallet/module/wallet.js`, which uses `walletStorage.set(...)`/`walletStorage.batch(...)`. All keys I could find there (e.g. `SEED_KEY`, `EXTRA_SEEDS_KEY`, `GENERATED_PASSPHRASE_KEY`, `HAS_USER_SET_PASSPHRASE_KEY`) are hardcoded module-level constants, not values derived from dapp/RPC/import input — I was not able to locate any call site in this codebase where an unprivileged/external input (RPC parameter, deeplink, QR/backup payload, remote config) is passed through as the `key` argument to `SecoKeyval.set`/`batch`. The library itself (`libraries/seco-keyval`) has no callers outside its own test suite and `secure-container`'s tests.

### Impact Explanation
If a reachable code path did pass an attacker-controlled string as the `key` in `set()`/`batch()` (e.g., a backup-import routine that replays arbitrary `{key, value}` pairs from an imported file), an attacker could pollute `_data`'s prototype and make `get()` calls for legitimate keys (e.g. a seed key) return attacker-chosen data, potentially causing the wallet to sign with or trust attacker-supplied "seed" material. That would match Hydra's "unauthorized signing / seed disclosure" impact category. But this scoped impact requires such a reachable, unvalidated key-passthrough call site, which I could not confirm exists in this repository.

### Likelihood Explanation
Low/unconfirmed. The vulnerable code pattern in `SecoKeyval.batch`/`set` is real (no key allowlisting), but exploitability requires a caller that forwards attacker-controlled keys into `set()`/`batch()`. All identified call sites in `features/wallet/module/wallet.js` use fixed, hardcoded key constants, not external input. No import/backup-replay code path was found that maps untrusted key names into `SecoKeyval` operations.

### Recommendation
Regardless of current reachability, defensively harden `SecoKeyval.batch`/`set` (and `delete`) by rejecting or ignoring dangerous keys (`__proto__`, `constructor`, `prototype`), e.g. via `Object.prototype.hasOwnProperty.call` checks or by using a `Map`/`Object.create(null)` for `_data` instead of a plain object literal, and by using `Object.defineProperty` for assignment instead of bracket-notation `this._data[key] = value`.

### Proof of Concept
```js
// libraries/seco-keyval/src/seco-keyval.test.js (hypothetical addition)
test('batch() with __proto__ key does not pollute prototype', async (t) => {
  const kv = new SecoKeyval(tempFile(), { appName: 'test', appVersion: '1.0.0' })
  await kv.open(Buffer.from('pw'))

  t.equal(kv.get('seed'), undefined, 'seed unset before pollution attempt')

  await kv.batch([{ type: 'set', key: '__proto__', value: { seed: 'attacker-value' } }])

  t.equal(Object.getPrototypeOf(kv.getAllData()), Object.prototype, 'prototype must remain Object.prototype')
  t.equal(kv.get('seed'), undefined, 'seed must remain unset, not resolved through polluted prototype')
  t.end()
})
```
Expected (current code): `Object.getPrototypeOf(kv.getAllData())` becomes `{ seed: 'attacker-value' }` and `kv.get('seed')` returns `'attacker-value'`, failing the assertions — confirming the prototype-pollution primitive exists in the library itself, even though a concrete reachable attacker path into this sink was not found in this repository's current call sites.
