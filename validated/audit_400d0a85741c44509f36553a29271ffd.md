Based on my investigation, I found a strong analog in `MemoizedKeychain`, which caches exported public keys keyed only by `keyId`, completely omitting `seedId` from the cache key — directly paralleling the report's root cause (a cache that isn't scoped to the "underlying" value that can change).

### Title
Public-key cache in `MemoizedKeychain` is not scoped by `seedId`, causing stale cross-seed key/address disclosure - (File: `features/keychain/module/memoized-keychain.js`)

### Summary
`MemoizedKeychain.exportKey()` short-circuits public-key lookups through an in-memory/persisted cache keyed solely by `keyIdToCacheKey(keyId)` (a stable stringification of the `keyId` shape), never incorporating `seedId` into the cache key, even though `seedId` is a required, independent input to every keychain export operation.

### Finding Description
`exportKey` is defined as: [1](#0-0) [2](#0-1) 

`#getCachedKey`/`#setCachedKey` compute the cache slot exclusively from `keyIdToCacheKey(keyId)` (i.e., `stableStringify(keyId)`), which encodes only `keyType`, `derivationAlgorithm`, `derivationPath`, and `assetName` — it never includes the `seedId` that is passed alongside `keyId` into `exportKey(keyId, opts)`'s underlying call. Because `KeyIdentifier` shapes (e.g. default derivation path for account index 0 of a given asset) are commonly identical across different seeds/wallet accounts, two different seeds can produce the exact same cache key.

This is the direct analog of the pool bug: in the reported issue, prices/fees were cached without accounting for the fact the "underlying asset" could change, so stale values persisted and were served after the change. Here, the underlying "asset" is the `seedId` (the cryptographic root the key is derived from); the cache is populated on first `exportKey` call for a given `keyId` shape and is never invalidated or re-keyed when a *different* `seedId` requests the same `keyId` shape — the cached xpub/publicKey from the first seed is returned instead of deriving fresh key material for the new seed.

The base `Keychain` class correctly requires and uses `seedId` for every operation (`#getPrivateHDKey`, `exportKey`, `getPublicKey`, `signBuffer` all key off `this.#masters[seedId]`): [3](#0-2) [4](#0-3) 

But `MemoizedKeychain`, which wraps and is registered as the actual `keychain` module (`id: MODULE_ID`), strips this scoping when serving from cache: [5](#0-4) 

`clear()` wipes the entire cache, but is only invoked on explicit resets; ordinary flows such as `addSeed()`/`removeSeeds()` on the underlying `Keychain` do not go through `MemoizedKeychain.clear()`, and the cache persists indefinitely (it is even written to durable `storage` under a single `CACHE_KEY`): [6](#0-5) 

### Impact Explanation
If a user adds/imports a second wallet seed (multi-wallet support, restoring a different seed, hardware+software mixed accounts, or any flow that produces a `KeyIdentifier` with the same `derivationPath`/`keyType`/`derivationAlgorithm`/`assetName` as one already cached from a prior seed), `exportKey()` will silently return the xpub/publicKey belonging to the *previous* seed instead of deriving it from the newly requested `seedId`. Any consumer relying on `keychain.exportKey({ seedId, keyId })` for public key/xpub (e.g. `PublicKeyProvider`, address derivation, connected-origin address exposure) can receive a public key/address that does not correspond to the intended seed/account. This is a direct account-isolation bleed: funds could be directed to (or addresses exposed for) the wrong wallet's key material, and any downstream trust decisions based on that address (e.g. dApp connections, receive addresses) would be built on the wrong account's public key.

### Likelihood Explanation
Medium: triggering requires two different seeds to share an identical `KeyIdentifier` shape, which is common for default account paths (index 0) across separately-imported seeds, or scenarios where a wallet's seed is replaced/rotated while keeping the same derivation-path conventions. This does not require attacker privilege — it can occur from ordinary user flows (adding a wallet, importing a seed, or wallet-reset/restore sequences) without any malicious actor, similar to how the reported bug is triggered by a routine admin action (`changeAsset()`).

### Recommendation
Include `seedId` in the cache key computation used by `MemoizedKeychain` (e.g., combine `seedId` and `keyId` via `keyIdToCacheKey`), and invalidate/clear cache entries whenever the underlying seed set changes (on `addSeed`, `removeSeeds`, `removeAllSeeds`) so cached public keys can never be served for a mismatched `seedId`.

### Proof of Concept
1. Instantiate `MemoizedKeychain` and call `exportKey(keyId, { exportPrivate: false })` with `seedId: 'seedA'` for a given `keyId` (e.g., default BIP44 path index 0) — this populates the cache keyed only by `stableStringify(keyId)` with seedA's `xpub`/`publicKey`.
2. Without calling `clear()`, call `exportKey(keyId, { exportPrivate: false })` again with a different `seedId: 'seedB'` but the identical `keyId` shape.
3. Observe that `#getCachedKey` returns the cached entry from step 1 (seedA's public key/xpub) instead of deriving fresh key material for `seedB`, because the cache lookup in `memoized-keychain.js:28-31` never inspects `seedId`.
