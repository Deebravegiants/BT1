## Analog Found

### Title
Single malicious/reverting input token permanently freezes an entire multi-token escrow, blocking both solver redemption and user refund - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2` orders can escrow multiple arbitrary ERC-20 tokens as `order.inputs` with no token allow-list check at `placeOrder`. Both escrow-release paths — solver redemption (`RedeemEscrow`) and user refund/cancellation (`RefundEscrow`) — funnel through the single internal `_withdraw` function, which iterates over *all* escrowed tokens in one atomic loop and calls `safeTransfer` on each. If any single token in that list is malicious or reverts (e.g. a blacklist token, a token that reverts for a specific recipient, or one whose transfer behavior changes after escrow), the whole loop reverts, and none of the other — otherwise perfectly good — escrowed tokens can ever be released, by either path. This mirrors the reported combination of "malicious token blocks claiming" and "funds frozen with no refund/claim possible," except here it does not even require a griefing DOS on iteration count — a single bad token in a multi-asset order is sufficient, and it poisons both the fill and the refund/cancel paths identically because they share the same withdrawal code.

### Finding Description
`_withdraw` in `IntentsBase.sol` is the sole function that ever moves escrowed tokens out of the gateway: [1](#0-0) 

It loops over `body.tokens` and calls `IERC20(token).safeTransfer(beneficiary, amount)` for each one; a revert on any single index reverts the entire call, including the release of every other already-verified, legitimate token in the same order.

Both the success path (a solver's fill being settled) and the recovery path (a refund after cancellation, or a source-chain cancel after proving the order was never filled) call this exact same function: [2](#0-1) [3](#0-2) 

The Tron variant of the contract has the identical structural pattern — one `withdraw` function used by both `RedeemEscrow` and `RefundEscrow`, iterating with a low-level `.call` per token and reverting the whole batch on any single failure: [4](#0-3) [5](#0-4) 

There is no restriction on which ERC-20 addresses can be used as `order.inputs` at `placeOrder` time — any token address supplied by the order creator is accepted and escrowed (`IERC20(token).safeTransferFrom(...)` is called unconditionally for each input), as seen in the input-transfer loop of `IntentGatewayV2.sol`: [6](#0-5) 

Because the user who creates the order fully controls the set of input tokens, an order can combine one legitimate, valuable token (e.g. USDC) with one malicious/adversarial token (e.g. a token the creator can later blacklist a specific address on, or one that unconditionally reverts for certain recipients) in the same `inputs` array. A solver who fills the order delivers the requested output assets on the destination chain and dispatches `RedeemEscrow` back to the source chain. When `onAccept` calls `_withdraw`, the loop hits the poisoned token and reverts — the solver's rightful claim on the legitimate token in the same escrow is blocked along with the malicious one. The same order's escrow cannot be recovered by cancellation either, since `_cancelFromSource`/`_cancelFromDest` and their corresponding `onGetResponse`/`onAccept` handlers for `RefundEscrow` reduce to the identical `_withdraw` call, so the same poisoned token blocks the refund path too.

### Impact Explanation
This permanently and irrecoverably freezes every token escrowed under the affected commitment, not just the malicious one. Concretely:
- A solver who has already delivered output tokens on the destination chain to fill the order can never redeem the escrowed input on the source chain — solver funds are effectively stolen with no on-chain remedy.
- The order's original user (or anyone) cannot recover the legitimate portion of the escrow via cancellation either, since cancellation resolves to the same reverting loop.
- There is no partial-withdrawal or per-token skip mechanism in `_withdraw`; the failure is all-or-nothing across the entire `WithdrawalRequest.tokens` array.

This satisfies the "concrete theft or permanent freezing of funds" bar: it is a single-transaction-reachable path (placing one order with a mixed token set) that leads to funds locked forever with no possibility of refund or claim, exactly mirroring the referenced report's combined H-1/H-2 scenario, but requiring only one adversarial token rather than a griefing volume attack.

### Likelihood Explanation
Likelihood is high: any order creator (an unprivileged, permissionless actor) can compose an order's `inputs` array with an arbitrary ERC-20 token address, since `placeOrder` performs no allow-list or safety check on input token addresses. Deploying or selecting an ERC-20 with conditional-revert/blacklist semantics is trivial and well precedented (USDT-style blacklist tokens, deny-list stablecoins, or a purpose-built malicious token). The attacker does not need any special timing beyond placing the order and, for cross-chain orders, optionally activating the malicious condition (e.g., blacklisting the solver/relayer address) after a solver has already committed output funds, maximizing the damage.

### Recommendation
Change `_withdraw` (and its Tron equivalent `withdraw`) so a revert on transferring one token does not block the release of the others in the same request — e.g., wrap each per-token transfer in a try/catch (or a low-level call whose failure is recorded rather than propagated) and let a failed token remain claimable separately/later, or track partial-success state per token so unaffected tokens are always released. Alternatively/additionally, restrict `order.inputs` to a curated token allow-list at `placeOrder` time so users cannot escrow arbitrary, unvetted ERC-20s that could later behave adversarially against specific counterparties.

### Proof of Concept
1. Deploy a malicious ERC-20 `EvilToken` whose `transfer`/`transferFrom` behaves normally at `placeOrder` time but is configured (e.g., via an owner-controlled blacklist, or unconditionally) to revert when called with the eventual solver/relayer address as recipient.
2. User calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1000e6}, {token: EvilToken, amount: 1} ]`, escrowing both tokens in the gateway (`IntentGatewayV2.sol` input-transfer loop, no allow-list check).
3. A solver fills the order on the destination chain, delivering the requested output assets to the beneficiary, and the gateway dispatches a `RedeemEscrow` message back to the source chain (`onAccept` → `_withdraw(body, false, true)` in `ExtrinsicIntents.sol`).
4. When the relayer delivers the `RedeemEscrow` post to the source-chain gateway, `_withdraw`'s loop reaches `EvilToken` and `safeTransfer` reverts, reverting the entire transaction — the solver never receives the 1000 USDC despite having delivered the output.
5. The user (or anyone) attempts to cancel and refund the order instead; `_cancelFromSource`/`_cancelFromDest` and the resulting `onGetResponse`/`onAccept` handling for `RefundEscrow` again resolve to the same `_withdraw` call, which reverts on `EvilToken` in the same way — the 1000 USDC can never be refunded either.
6. Both the USDC and EvilToken remain permanently locked in the gateway contract, with the solver's already-delivered output funds effectively stolen and no function in the contract able to release only the good token.
