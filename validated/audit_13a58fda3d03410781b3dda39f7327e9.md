### Title
PoA bridge withdrawal status is matched by `assetId` only, causing cross-reported completion hashes for batched same-asset withdrawals - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` resolves the completion status/txHash of a specific withdrawal by calling `findMatchingWithdrawal()`, which selects a record from the POA API response using `Array.prototype.find()` matched **solely on `assetId`** (`nep141:${w.data.near_token_id} === assetId`), ignoring the withdrawal's `index`, `destinationAddress`, and `amount`.

### Finding Description
When multiple withdrawals in the same batch/intent share the same `assetId` (e.g., two BTC withdrawals to two different destination addresses submitted together via `IntentsSDK.createWithdrawalCompletionPromises()` / `processWithdrawal()`), `createWithdrawalIdentifiers()` assigns each of them a distinct `index` [1](#0-0) , but `PoaBridge.describeWithdrawal()` never consults that `index` (or the destination address) when resolving which POA-side withdrawal record corresponds to which SDK-side withdrawal identifier [2](#0-1) .

The matching function itself:
```
function findMatchingWithdrawal(withdrawals, assetId) {
  return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [3](#0-2) 

The code comment explicitly acknowledges the gap: "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." [4](#0-3) . The same limitation is duplicated in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`'s own `findMatchingWithdrawal()` [5](#0-4) .

Because `.find()` returns only the **first** array element that matches `assetId`, any second (or further) withdrawal instance for the same asset in the batch is reported with the **same** `transfer_tx_hash`/status as the first one — even though the underlying POA response array actually contains two distinct records with two distinct `transfer_tx_hash` values, `address` fields, and amounts (as demonstrated by the repository's own test `"matches withdrawal by assetId, not by index"`, which only tests differing chains, not the same-asset-multiple-destination collision case) [6](#0-5) .

This breaks the equality: *"the destination transaction hash reported for withdrawal #i" == "the actual on-chain outcome of withdrawal #i"*. Instead, withdrawal #2's reported `txHash` may actually be withdrawal #1's `txHash`.

### Impact Explanation
An integrator using `sdk.createWithdrawalCompletionPromises()` / `waitForWithdrawalCompletion()` to track multiple same-asset withdrawals in one batch will receive a `completed` status with a `destinationTx` hash for withdrawal #2 that is actually the transaction hash belonging to withdrawal #1 (or vice versa). If the integrator marks withdrawal #2 as paid/settled based on this misreported hash — e.g., crediting a user's off-chain ledger, releasing an escrow, or closing an order — this constitutes exactly the "status or hash misreport making an integrator credit or refund twice" scenario the rubric classifies as High severity, since the two withdrawals were destined for different addresses/amounts but are conflated into one status report.

### Likelihood Explanation
This requires no privileged or malicious actor — it is triggered purely by an ordinary user/integrator submitting a batch withdrawal containing two or more entries with the identical `assetId` (a supported, unprivileged usage pattern the SDK explicitly exposes via `WithdrawalParams[]` arrays and `createWithdrawalCompletionPromises`). No `routeConfig`, address, or amount deduplication check exists to prevent or flag this input combination, and the resulting matching bug is deterministic (`Array.find` always returns the first match), not merely a rare race.

### Recommendation
Update `findMatchingWithdrawal` (in both `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate matches using additional withdrawal-specific fields (destination `address`, `amount`) rather than `assetId` alone, and/or reject/queue same-asset batch withdrawals until the POA API supports per-withdrawal correlation IDs. At minimum, throw an explicit error when more than one candidate match exists for a given `assetId` within a batch, instead of silently returning the first result.

### Proof of Concept
1. Submit a batch withdrawal with two entries, both `assetId: "nep141:btc.omft.near"`, destined for addresses A and B respectively, via `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [wA, wB], intentTx })`.
2. The POA bridge processes both and its `getWithdrawalStatus` API eventually returns two records: `{address: A, transfer_tx_hash: X}` and `{address: B, transfer_tx_hash: Y}`.
3. `PoaBridge.describeWithdrawal()` is invoked once for each SDK-side identifier (index 0 for wA, index 1 for wB), but both calls only pass `assetId = "nep141:btc.omft.near"` into `findMatchingWithdrawal`.
4. `.find()` returns the same first-matching record (say `{address: A, transfer_tx_hash: X}`) for **both** calls, so the promise for wB (destined to address B) resolves with `txHash: X`, which actually belongs to wA's withdrawal to address A.
5. An integrator awaiting `promises[1]` (for wB) incorrectly believes wB completed with hash X, potentially crediting/closing wB using a transaction that never paid address B.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(

			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };

			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {

				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
