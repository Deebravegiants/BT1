The claim is technically accurate: `AuthorizedUserWithSession` (ldap.go L342-373) and `FindUserByAPIToken` (L204-236) only check row age against local `ldap_sessions`/`ldap_user_api_tokens` tables and never call `validateUsersActive` or otherwise re-query the upstream LDAP server on a per-request basis. ## Title
Deactivated/revoked LDAP users retain valid session and API token access until natural expiry — ([File: core/sessions/ldapauth/ldap.go])

## Summary
`AuthorizedUserWithSession` and `FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` validate sessions and API tokens purely by checking local record age against `SessionTimeout`/`UserAPITokenDuration`, without ever re-querying the upstream LDAP directory's active/membership status on the request path. Revocation only propagates through `LDAPServerStateSyncer.Work()` in `core/sessions/ldapauth/sync.go`, which — under the documented default `UpstreamSyncInterval = '0s'` — runs exactly once at node startup (`Start()`) and is never re-triggered afterward, since it is not called from `CreateSession`, logout, or any other per-request code path in `ldap.go`.

## Finding Description
`AuthorizedUserWithSession` (`core/sessions/ldapauth/ldap.go` L342-373) executes:
```
SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1
``` [1](#0-0) 
and `FindUserByAPIToken` (L204-236) performs the analogous check against `ldap_user_api_tokens`. [2](#0-1) 
Neither function calls `validateUsersActive` or contacts the upstream LDAP server; validity is determined solely by `created_at + duration >= now()`.

The package-level doc comment claims "This sync happens for every auth endpoint hit," but no code in `ldap.go` invokes `LDAPServerStateSyncer.Work()` from `CreateSession`, `AuthorizedUserWithSession`, `FindUserByAPIToken`, or any logout path — `Work()` is only referenced from `sync.go` itself (its `Start()`/`run()` methods) and wired into the application via `core/services/chainlink/application.go`, confirming the doc comment is misleading/stale relative to actual behavior. [3](#0-2) 

`Start()` only schedules a recurring ticker when `UpstreamSyncInterval().IsInstant()` is false; otherwise `Work(ctx)` runs exactly once at startup: [4](#0-3) 
and the documented default is `'0s'`, explicitly described as disabling the interval-based background sync. [5](#0-4) 

`Work()` is the only code path that calls `validateUsersActive` against the upstream directory and purges `ldap_sessions`/`ldap_user_api_tokens` for users no longer active/present upstream. [6](#0-5) 

Because no per-request revalidation exists and the default configuration only syncs once at startup, a session or API token created before an upstream deactivation event remains fully valid and authorized for its entire local timeout window (`SessionTimeout` default `15m`, `UserAPITokenDuration` default `240h0m0s`), independent of the user's actual state in the LDAP directory. [7](#0-6) 

## Impact Explanation
This is a genuine authorization-bypass / stale-credential class issue: an LDAP-integrated node continues to honor API/GUI requests from a user whose access was revoked upstream (offboarding, compromise response, role demotion) for up to 15 minutes (session) or up to 10 days (API token) by default, with `UserAPITokenEnabled` granting the same authorization as the underlying role, up to Admin. This maps to the in-scope "node API authentication or role bypass" impact category since the node's own session/token validation logic — not an external actor's exploit against a specific request — is the direct cause of continued unauthorized access.

## Likelihood Explanation
The affected behavior is the out-of-box default (`UpstreamSyncInterval = '0s'`) and requires no special misconfiguration to trigger — only that a node operator has enabled LDAP authentication, which is a supported, documented `AuthenticationMethod`. Any operator relying on the default config is exposed without additional action, and the exposure window is deterministic and reproducible (bounded exactly by `SessionTimeout`/`UserAPITokenDuration`).

## Recommendation
Re-validate upstream active status (or force a lightweight `validateUsersActive` check) inside `AuthorizedUserWithSession` and `FindUserByAPIToken` rather than relying solely on local record age, or enforce a bounded maximum default for `UpstreamSyncInterval`. Additionally, correct the misleading doc comment in `ldap.go` (L12-17) claiming sync happens "for every auth endpoint hit," and emit a startup warning when `UpstreamSyncInterval` is `0s` while `ActiveAttribute` is configured, since this combination silently disables continuous revocation enforcement.

## Proof of Concept
1. Configure `WebServer.AuthenticationMethod = 'ldap'` with `ActiveAttribute` set and `UpstreamSyncInterval` left at default `'0s'`.
2. Log in as an LDAP user (creates a row in `ldap_sessions` via `CreateSession`) and/or generate an API token via `SetAuthToken` (creates a row in `ldap_user_api_tokens`).
3. Deactivate the user's account upstream in LDAP (flip the `ActiveAttribute` value).
4. Because `LDAPServerStateSyncer.Work()` only ran once at node startup and is not re-triggered, the local `ldap_sessions`/`ldap_user_api_tokens` rows are not purged.
5. Call an authenticated endpoint using the existing session cookie or API token; `AuthorizedUserWithSession`/`FindUserByAPIToken` return the cached role, granting continued access until `SessionTimeout`/`UserAPITokenDuration` naturally elapses — verifiable via a Go unit test asserting these functions never invoke `validateUsersActive` or the LDAP client.

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}
```
