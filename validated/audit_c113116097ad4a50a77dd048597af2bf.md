### Title
Webhook shop-domain identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for a webhook purely from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator.validate` checks is computed only over the raw request body (`to_signable_string` returns `@raw_body`). The shop header is never included in the signed bytes, so the identity binding `shop_header == shop_that_produced_this_HMAC` is never enforced.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
`Request#shop` is read straight from an attacker-controlled header with no cryptographic binding to the body/HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` as the tenant identity when dispatching to the app's handler: [3](#0-2) 

This is the same bug class as the external report: a value that is *acted upon* (the packet ID / here, the shop identity) is not the value that was actually *verified* (the zeroed array / here, the HMAC-covered bytes). The equality that should hold is:
`shop_identity_used_by_handler == shop_identity_that_the_HMAC_secret_owner_intended`
but the code instead enforces only:
`HMAC(raw_body, api_secret_key) == received_hmac`
with `shop` sourced from an entirely separate, unauthenticated channel (the HTTP header). The test fixture itself demonstrates that the HMAC is computed from body content alone, independent of the shop header: [4](#0-3) 

### Impact Explanation
Any party capable of obtaining one legitimate `(raw_body, hmac)` pair for a topic whose payload is static or predictable across tenants (e.g., an app developer's own shop receiving a webhook with body `{}` or another deterministic payload) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. Because `Registry.process` only checks the HMAC of the body and never ties the header to the signature, the handler will execute business logic (e.g., mandatory-compliance handlers like `shop/redact`, `customers/redact`, `customers/data_request`, or any custom handler) attributing the event to a victim shop chosen by the attacker. This crosses a tenant boundary using only the attacker's own legitimately-received webhook material, without needing the `api_secret_key`, an access token, or any privileged credential — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Likelihood is High for topics with static or attacker-influenceable bodies (compliance webhooks, or any webhook whose payload the attacker can trigger for their own shop and predict). The attacker only needs: (1) their own app installation to receive one real webhook (any merchant can install a public app), and (2) the ability to send a raw HTTP POST to the app's webhook route with a modified shop header — both are unprivileged-internet-user actions requiring no secret material.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the verified request:
- Include the shop domain (and/or other identity headers) in `to_signable_string`, matching how Shopify actually computes the webhook HMAC if it covers more than the raw body, or
- After verifying HMAC over the body, independently validate that `request.shop` corresponds to a shop that legitimately owns an app installation/session on this app instance before dispatching to `handler.handle`, rather than trusting the header as ambient truth.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a real webhook delivery with topic `shop/redact` and body `{}` (or any deterministic body), including a valid `shopify-hmac-sha256` header computed by Shopify using the app's `client_secret`.
2. Attacker replays the exact same raw body and `shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` and `shopify-topic: shop/redact`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the raw body only) and it matches, since the body is unchanged: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to execute redaction/business logic against the victim tenant using data/timing chosen by the attacker. [6](#0-5)
