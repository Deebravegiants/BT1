### Title
Division-by-zero / underflow panic in `calc-treasury-lp-preview` can permanently DoS vault deposits and withdrawals - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent per-asset vault contracts)

### Summary
The `calc-treasury-lp-preview` helper computes the treasury's LP share of newly accrued interest by dividing `reserve-inc` by `(- ta-preview reserve-inc)`. The guard only checks that `reserve-inc > u0`; it never checks whether the denominator `(- ta-preview reserve-inc)` is zero or would underflow. Clarity aborts the entire transaction on both division-by-zero and unsigned-integer underflow, so this function's result feeds directly into `total-supply-preview`, which is used by `convert-to-shares-preview` / `convert-to-assets-preview`, which in turn back every deposit, withdraw, mint, and redeem call.

### Finding Description
```clarity
// mainnet/contracts/vault/v0-vault-stx.clar
(define-private (calc-treasury-lp-preview)
  (let ((scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (next (next-index))
        (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
        (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
        (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
        (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
        (ta-preview (total-assets-preview)))
    (if (> reserve-inc u0)
        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
``` [1](#0-0) 

`mul-div-down` itself is a raw division with no zero-denominator check:
```clarity
(define-private (mul-div-down (x uint) (y uint) (z uint))
  (/ (* x y) z))
``` [2](#0-1) 

Unlike the sibling conversion helpers `convert-to-shares-preview` and `convert-to-assets-preview`, which explicitly check `(is-eq ts u0)` / `(is-eq ta u0)` before dividing, `calc-treasury-lp-preview` only guards against `reserve-inc == u0`; it never verifies `ta-preview > reserve-inc`. [3](#0-2) 

If accrued interest owed to the reserve (`reserve-inc`) equals or exceeds `ta-preview` (total previewed assets), the subtraction `(- ta-preview reserve-inc)` either produces `u0` (triggering division by zero) or underflows a `uint` (Clarity aborts the transaction). Both cases cause every call into `calc-treasury-lp-preview` — and therefore `total-supply-preview`, `convert-to-shares-preview`, `convert-to-assets-preview`, and consequently `deposit`/`withdraw`/`mint`/`redeem` — to revert.

The identity being broken is the share-supply-vs-backing invariant: `total-supply-preview = total-supply + treasury-lp`, which is supposed to always resolve to a valid share count reflecting the vault's real asset backing, but instead can become mathematically undefined (division by a non-positive quantity) whenever the reserve's claim on freshly accrued interest is not strictly smaller than the previewed total assets.

### Impact Explanation
Once triggered, every subsequent transaction that touches `total-supply-preview` (all deposit, withdraw, mint, redeem paths) will revert, since `ta-preview`, `reserve-inc`, and the underlying state variables (`principal-scaled`, `index`, `fee-reserve`) do not change from read-only preview calls — the vault becomes permanently unusable until an admin/DAO action (e.g., changing `fee-reserve`) resolves the condition, if one is even available. This is a permanent freezing of user funds (deposited principal and unclaimed yield) in the affected vault, matching the "permanent freezing of funds" impact category.

### Likelihood Explanation
This requires `reserve-inc` (fee-reserve's share of newly accrued interest since last index update) to be greater than or equal to `ta-preview` (previewed total vault assets). This is an extreme edge case — it would generally require either a very high `fee-reserve` BPS setting combined with a long period of accrued interest, or a vault with very low total assets relative to accumulated debt. It is not trivially attacker-triggerable under normal parameterization, so likelihood is Low, but it is a reachable state through normal protocol usage (time passing without index updates plus interest accrual) rather than through a DAO misconfiguration alone.

### Recommendation
Add an explicit guard in `calc-treasury-lp-preview` to skip the division (return `u0`, or clamp) whenever `ta-preview <= reserve-inc`, mirroring the zero-checks already used in `convert-to-shares-preview` / `convert-to-assets-preview`:
```clarity
(if (and (> reserve-inc u0) (> ta-preview reserve-inc))
    (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
    u0)
```

### Proof of Concept
1. Vault is deployed with a nonzero `fee-reserve` BPS value.
2. Time elapses with no calls that update `index`/`last-update` (accrual is lazy, computed only in `-preview` functions), so `debt-delta` (and thus `reserve-inc`) grows relative to `ta-preview` because `total-assets-preview` grows only by interest already reflected in `total-borrowed` vs. `debt`, while `reserve-inc` scales directly with `debt-delta * fee-reserve`.
3. When a sufficiently high `fee-reserve` is combined with sufficient elapsed time/interest accrual, `reserve-inc` reaches or exceeds `ta-preview`.
4. The next call to `deposit`, `withdraw`, `mint`, or `redeem` invokes `total-supply-preview` → `calc-treasury-lp-preview`, hitting `(- ta-preview reserve-inc)` which is `u0` or underflows, causing the entire transaction to abort with a runtime error.
5. All subsequent user-facing vault operations continue to revert since the underlying state is unchanged by a failed call, permanently freezing deposits and withdrawals in the vault. [4](#0-3)
