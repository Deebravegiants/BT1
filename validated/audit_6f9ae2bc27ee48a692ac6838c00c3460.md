### Title
Webhook `shop` identity is trusted from an unauthenticated header not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` field is therefore an unbound identity claim: it is delivered to the app's `WebhookHandler#handle` as trusted tenant identity, without being cryptographically tied to the HMAC that "authenticates" the request.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via: [1](#0-0) 
which calls `Utils::HmacValidator.validate(request)`. That validator computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 
and `Webhooks::Request#to_signable_string` returns only the raw JSON body, not any headers: [3](#0-2) 

Meanwhile `Webhooks::Request#shop` is parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the signed payload: [4](#0-3) 

This unauthenticated `shop` value is then forwarded as the tenant identity to the app's handler: [5](#0-4) [6](#0-5) 

The binding that should hold is: `shop authenticated by HMAC == shop acted upon by the handler`. Because only the body is signed, an attacker can take any legitimate `(raw_body, hmac)` pair - which they can obtain for their own shop, since the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is identical across all shops that install the same app - and resend it with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body bytes, so `Registry.process` accepts the forged request and hands the handler a `WebhookMetadata` claiming to originate from the victim shop.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (or `Request#shop`) to select which merchant's session/tenant record to update, delete, or otherwise mutate is exposed to cross-tenant data confusion: a merchant who has installed the app (and therefore holds valid HMAC'd webhook payloads for their own shop) can forge webhook deliveries "from" any other shop the app serves, since the shop identity is never bound to the HMAC. This crosses the tenant boundary this gem is documented to enforce via webhook HMAC verification, matching the report's "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app as any merchant (unprivileged, ordinary onboarding, no special credentials), (2) capturing one legitimate webhook (any topic) delivered to that merchant, and (3) resending it to the app's webhook endpoint with a rewritten `X-Shopify-Shop-Domain` header. No access to the app's `client_secret`, access tokens, or TLS interception is needed - the attacker already legitimately possesses a valid `(body, hmac)` pair for their own tenant. The gem provides no mechanism to bind `shop` into the signature, so every app that only calls `HmacValidator.validate` (as the built-in `Registry.process` does) inherits this gap.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed payload, or independently verify that the `shop` header matches a shop the caller is authorized to act as (e.g., cross-check against a known/registered shop list or a per-shop signing context) before trusting `request.shop` / `WebhookMetadata#shop`. Short term, document prominently that `Request#shop` is unauthenticated and must not be trusted for tenant selection without additional verification; longer term, extend `to_signable_string` in `Webhooks::Request` to bind the shop domain into the signable material so `HmacValidator` implicitly authenticates it.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed over `B` with the app's shared `client_secret`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the same request to the app's webhook endpoint, keeping `B` and `H` unchanged but rewriting the header to `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`B`) only, matches `H`, and returns `true`. [7](#0-6) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., data forged to appear as though it came from `victim.myshopify.com`, even though `victim` never sent it and the attacker never obtained any victim credential. [5](#0-4)
