### Title
Reentrant escrow withdrawal via unpatched checks-effects-interactions violation in `withdraw()` — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The CVE describes a bug class where a cleanup/settlement effect (`rpm put()`) fires twice because the code performs a side-effecting external action before the internal accounting state that gates it is finalized, letting an error/callback path re-trigger the same effect. `IntentGatewayV2.withdraw()` in the Tron variant of the intent gateway has the analogous structural flaw: it performs the token transfer (an external call) *before* decrementing the escrow accounting (`_orders[...]`), unlike the already-hardened EVM version of the same logic.

### Finding Description
`withdraw()` is reached from `onAccept` (processing `RedeemEscrow`/`RefundEscrow` requests relayed permissionlessly through Hyperbridge) and from `onGetResponse` (processing a GET response for cross-chain cancellation) [1](#0-0) [2](#0-1) .

Inside `withdraw()`, for each output token, the escrow balance is only checked for non-zero, then the raw external transfer (`.call`, including a native-value `.call{value: amount}("")` to an attacker-controlled `beneficiary`) is executed, and only *afterwards* is `_orders[body.commitment][token]` decremented: [3](#0-2) 

This is a checks-effects-interactions violation: the native-token branch calls `beneficiary.call{value: amount}("")` while `_orders[body.commitment][token]` still reflects the pre-withdrawal (undecremented) balance, so a malicious `beneficiary` contract can re-enter during that call and pass the same `_orders[...][token] == 0` check again, draining the same escrow slot multiple times before the balance is ever reduced.

This is precisely the same bug class that the project's own EVM `IntentsBase.sol` version of this logic was previously vulnerable to and has since fixed: the escrow decrement (`_orders[body.commitment][token] = escrowed - amount;`) is now placed *before* the external transfer [4](#0-3) , and the repository's own reentrancy regression tests document that this exact reordering was the fix for a prior escrow-theft vulnerability [5](#0-4) [6](#0-5) . The Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` never received this CEI fix, leaving the same class of vulnerability live in that deployment target — analogous to the CVE's pattern of an effect (fee/token release) being allowed to fire more than once because the guarding state update happens after, not before, the externally observable action.

### Impact Explanation
A solver/beneficiary that fills or cancels an order routed through the Tron `IntentGatewayV2` can supply a malicious contract as `beneficiary` for a native-token (`token == address(0)`) output. On receiving the `.call{value: amount}("")`, the malicious beneficiary re-enters (directly or via a nested cross-chain/message path) and withdraws the same escrowed balance again before `_orders[body.commitment][token]` is decremented, draining escrowed user/protocol funds beyond what was legitimately owed — concrete theft of funds from the intent escrow.

### Likelihood Explanation
Reachable by any solver/user who can become the `beneficiary` of a `RedeemEscrow` or `RefundEscrow` withdrawal and can therefore control a contract address that receives the native-token payout — no privileged or admin access required, only a normal fill/cancel flow followed by relaying (permissionless) of the resulting message. The project's own test suite proves the identical reordering was already exploited and had to be patched in the EVM contracts, confirming the flaw is realistic and exploitable, not theoretical.

### Recommendation
Apply the same checks-effects-interactions fix used in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` (and `_filled`/fee accounting) before performing any external `.call`/token transfer, and add a reentrancy guard consistent with the rest of the gateway.

### Proof of Concept
1. Attacker places/fills a cross-chain order on the Tron `IntentGatewayV2` with a native-token (`token == address(0)`) output, setting `beneficiary` to an attacker-controlled contract.
2. Once the corresponding `RedeemEscrow`/`RefundEscrow` message is relayed and `onAccept` calls `withdraw(body, ...)` [7](#0-6) , the loop reaches `beneficiary.call{value: amount}("")` while `_orders[body.commitment][token]` is still non-zero.
3. The attacker's beneficiary contract's fallback re-enters (e.g., re-triggers processing of the same/duplicated message or another code path that calls `withdraw`/reads `_orders`), passing the `_orders[...][token] == 0` check again and receiving another payout for the same commitment before the original call returns and decrements the balance.
4. Escrowed funds are withdrawn more than once for the same order, permanently draining protocol/user funds.

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
