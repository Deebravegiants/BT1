### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant spoofing of webhook payloads - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the shop/tenant identity delivered to the app's handler is read from an HTTP header that is never included in the signed bytes. This breaks the intended binding: `hmac_valid(body) == true` should imply `shop == the shop the body actually originated from`, but the gem lets an attacker keep a validly-signed body while substituting an arbitrary `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and the `shop` accessor is derived independently from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of the signable string at all [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `validate_signature`, computing `HMAC(secret, request.to_signable_string)` and comparing it to the `hmac` header using `OpenSSL.secure_compare` [3](#0-2) . Because `to_signable_string` is just the raw body, this check proves only that the *body* bytes were signed by Shopify with the app's secret at some point — it says nothing about which shop the body belongs to.

Once that check passes, `Registry.process` immediately trusts `request.shop` (from the header) and hands it to the app's handler as the tenant identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . `WebhookMetadata#shop` is exactly the field host apps use to look up per-tenant sessions/access tokens and to decide which merchant's data to mutate [5](#0-4) .

The `VerifiableQuery` interface only requires `hmac` and `to_signable_string` [6](#0-5) ; there is no mechanism anywhere in `HmacValidator`, `Registry`, or `Request` that ties the externally supplied `shop` header to the HMAC-covered bytes.

Equality that should hold: `hmac_verified(body) == true` → `shop_header == origin_shop_of(body)`.
Equality that actually holds: `hmac_verified(body)` only proves `body` was HMAC-signed by *some* legitimate Shopify webhook for *some* shop using this app's secret; `shop_header` is taken verbatim from unauthenticated header bytes.

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged internet user who can capture (or replay through their own installed instance of the app on a shop they control) one legitimately HMAC-signed webhook body/HMAC pair can resend it with a forged `x-shopify-shop-domain` header naming a victim shop. Because `Registry.process` never checks that the signed body actually originated for that shop, the app's webhook handler will process attacker-controlled webhook data as if it belongs to the victim tenant — e.g. triggering per-shop side effects (order/customer/redact processing, data updates, cache invalidation, session/token lookups keyed by `shop`) under the wrong tenant. This is a cross-tenant access vector purely through this gem's own verification logic, not dependent on the host app ignoring documented behavior — the gem's own `process` method performs the trust decision.

### Likelihood Explanation
The prerequisite is only the ability to send an HTTP POST to the app's registered webhook endpoint plus possession of one validly-signed body+HMAC pair from any shop that has the app installed (an attacker can trivially obtain this by installing/using the app on their own store, since webhooks for one's own shop are freely receivable). No access token, `api_secret_key`, or privileged account is required to mount the header-substitution attack itself — only the ordinary ability to install the app on any shop and to send a spoofed request to the endpoint the app exposes.

### Recommendation
Include the tenant/shop identity in the HMAC-covered material, or independently bind it: e.g., have `to_signable_string` incorporate the `shop-domain` header (consistent with how `Auth::Oauth::AuthQuery#to_signable_string` already includes `shop` in its signed params, see `lib/shopify_api/auth/oauth/auth_query.rb`), or require callers of `Registry.process` to supply the expected shop for the session being acted on and assert `request.shop == expected_shop` before invoking the handler, rejecting on mismatch.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (or otherwise has an app installation) and triggers a webhook event, capturing a legitimate `(raw_body, x-shopify-hmac-sha256, x-shopify-topic, x-shopify-webhook-id, x-shopify-api-version)` set signed by Shopify for that shop's secret.
2. Attacker replays the exact same body/HMAC to the app's webhook endpoint but replaces the `x-shopify-shop-domain` header with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the unchanged raw body) and matches the unchanged `hmac` header, so validation succeeds [7](#0-6) .
4. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled parsed body>, ...)` [8](#0-7)  — the app processes attacker data attributed to the victim tenant.
