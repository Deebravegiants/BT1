## Title
Solver relies on unguarded Uniswap V4 spot price to fill intent orders, letting a single-transaction pool manipulation extract funds from the intent solver — (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
Simplex (the reference intent solver / filler for Hyperbridge's Intent Gateway) can price a "curveless" trading pair directly off the current tick of a Uniswap V4 pool instead of a static curve. This is the same bug class as the Hegic/Sharwa exploit: a value that should be economically bound is read as an instantaneous spot quote from an AMM pool that any address can move within one transaction, and that unguarded (or weakly guarded) read directly determines how much the solver pays out when filling a cross-chain/same-chain intent order.

### Finding Description
When a pair has no `bidPriceCurve`/`askPriceCurve` configured and `token0` is a USD stablecoin, `FXFiller.resolveLegRates` prices the leg from the configured Uniswap V4 position's pool instead of a curve: [1](#0-0) 

That price comes from `UniswapV4FundingPlanner.getExoticTokenPrice`, which for every position matching the exotic token calls `computeDirectPoolPriceUsd`, deriving the USD price straight from `sdkPool.token0Price`/`token1Price` — i.e., the pool's current `sqrtPriceX96` tick, with no TWAP, no size/impact adjustment, and the pool's own fee tier never applied to the number: [2](#0-1) [3](#0-2) 

The only defense is an *optional* price guard (`referencePrice` + `maxDeviationBps`), and the documentation explicitly states both fields are optional together — "omit both to leave the chain unguarded": [4](#0-3) 

Even when configured, `checkPriceGuard` only rejects a quote that deviates more than `maxDeviationBps` from a static reference — it does not detect or resist manipulation that stays inside the configured band, and it is a deviation check against a stale reference the operator set, not a manipulation-resistance mechanism (e.g., no TWAP window, no minimum liquidity check, no same-block detection): [5](#0-4) 

The project's own internal documentation confirms this is a known, understood gap rather than a hypothetical: "Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote," and separately: "`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost." [6](#0-5) 

This price then flows straight into `calculateProfitability`/`computeLegPolicyOutput`, which decides how much of the exotic token the solver actually hands to the order placer when filling the intent, and into `referenceRate`, which also sizes confirmation-depth requirements from the same unguarded number: [7](#0-6) 

### Impact Explanation
An attacker who can move the configured Uniswap V4 pool's tick within the same transaction/block (a swap, optionally flash-loan-funded, exactly like the Hegic PoC's callback-triggered swap into the thin USDC/USDC.e pool) can submit or trigger a Simplex-priced intent order at that moment. If no price guard is configured (which is the norm — the docs describe it as opt-in and describe leaving it unguarded as a supported configuration) or if the manipulation is crafted to stay within the configured `maxDeviationBps` band, Simplex will fill the order using the manipulated spot price rather than the fair price, handing over more of the exotic token (or accepting less input) than it should, and the attacker profits from the difference once the pool reverts to its true price. This is a direct value-extraction path against the solver's own liquidity/vault, matching "concrete theft ... of funds" and "unauthorized app action" (the solver executing a fill it would never authorize at the true price).

### Likelihood Explanation
Any unprivileged actor can move an AMM pool's spot price within a single transaction and then place/trigger the order that gets priced against it — this requires no special access to Hyperbridge, the Intent Gateway, or Simplex's configuration, exactly mirroring the reachable, single-transaction attack pattern in the external report. Likelihood is higher for thinly-liquid exotic-token pools (the exact class of pool this feature targets — non-stablecoin "exotic" tokens like cNGN), where manipulation cost is lowest.

### Recommendation
- Do not use raw current-tick pool price (`sqrtPriceX96`) as a solver's fill price. Use a time-weighted average price (TWAP) over a manipulation-resistant window, or require corroboration from an independent oracle/multiple pools before pricing a fill.
- Make the price guard mandatory (not opt-in) whenever venue/pool pricing is enabled, and widen it to include liquidity-depth and same-block/same-transaction manipulation checks, not just a static deviation band.
- Apply the pool's own fee tier and a price-impact term proportional to trade size (`computeDirectPoolPriceUsd`/`computeLegPolicyOutput` currently apply neither), so a manipulated tick cannot be scaled arbitrarily across the whole order size.

### Proof of Concept
Conceptually mirrors the referenced Sharwa/Hegic exploit:
1. Configure/observe a Simplex deployment with a curveless pair priced from `[vault.uniswapV4]` with no `referencePrice`/`maxDeviationBps` set (a documented, supported configuration).
2. Attacker swaps a large amount through the underlying Uniswap V4 pool in one transaction to push the tick so `computeDirectPoolPriceUsd` returns a favorable USD price for the exotic token.
3. In the same block, submit/trigger the intent order that Simplex prices via `resolveLegRates` → `getVenueUsdPrice` → `getExoticTokenPrice`, causing the solver to fill at the manipulated price.
4. Reverse the initial swap, restoring the pool, and keep the excess exotic tokens/input-token difference obtained from the mispriced fill.

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

	private async referenceRate(
		leg: ResolvedLeg,
		venueUsdPrice: (chain: string, token1Address: string) => Promise<Decimal | null>,
	): Promise<Decimal | null> {
		const policy = leg.pair.bidPricePolicy ?? leg.pair.askPricePolicy
		if (policy) {
			const rate = policy.getPrice(new Decimal(0))
			return rate.gt(0) ? rate : null
		}
		// Venue-priced pair: token0 is USD-stable (constructor invariant), so the
		// venue's USD-per-token1 quote inverts straight into token1-per-token0.
		const venueUsd = await venueUsdPrice(leg.token1Chain, leg.token1Address)
		if (!venueUsd) return null
		const venueRate = new Decimal(1).div(venueUsd)
		// Same guard as trade pricing: this rate sizes the order's USD notional
		// for confirmation depth, and a manipulated pool understating the value
		// would shrink the reorg protection — the exact attack the guard exists
		// to stop. Refusing to size skips the order, consistent with pricing.
		if (!this.checkPriceGuard(undefined, leg.token1Chain, venueRate)) return null
		return venueRate
	}

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
