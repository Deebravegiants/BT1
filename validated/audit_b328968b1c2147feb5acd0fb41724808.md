### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant impersonation of webhook origin - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` passes, and then forwards `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by that HMAC — to the app's handler as if they were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The HMAC is computed and checked exclusively over the raw body bytes with the app's shared `api_secret_key`: [2](#0-1) . The `shop`, `topic`, and `webhook_id` accessors read straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) .

`Registry.process` validates only this HMAC-over-body, then immediately trusts `request.shop` and `request.topic` to select the handler and build `WebhookMetadata` that is handed to the app: [4](#0-3) .

The `api_secret_key` (the app's `client_secret`) is identical for every shop that installs the app — it is not shop-specific. Any unprivileged attacker can:
1. Install the target app on their own shop (a normal, unprivileged, unauthenticated-to-others action).
2. Trigger any webhook topic on their own shop, capturing the resulting `raw_body` and its valid `X-Shopify-Hmac-Sha256` value — this HMAC is valid app-wide, not shop-scoped, since it is only a function of `(body, api_secret_key)`.
3. Replay that exact `raw_body` + `hmac` to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with an arbitrary victim shop's domain.
4. `HmacValidator.validate` still returns `true` (it only checks the body bytes), so `Registry.process` dispatches the forged request to the handler with `shop: <victim-shop>` and the attacker's captured body content.

This breaks the identity binding the gem implicitly promises: **shop header value == shop that produced the HMAC-signed bytes**. In reality the equality only holds for **body bytes == HMAC-verified bytes**; the shop/topic/webhook-id headers are unauthenticated metadata that the app is led to believe are equally trustworthy because they arrive alongside a "validated" request.

### Impact Explanation
Any app that uses `WebhookMetadata#shop` (as returned by `Registry.process`) to key persistence, deduplication, tenant-scoped side effects, or audit logging is exposed to cross-tenant data confusion/injection: an attacker-controlled shop's webhook payload can be attributed to a different, victim shop, without ever needing that victim's access token, credentials, or any privileged access — only their own unprivileged app installation. This matches the "cross-tenant access" class of Critical/High impact called out in scope, since it lets one tenant's traffic be attributed to another tenant purely by manipulating unauthenticated headers alongside a validly-signed body.

### Likelihood Explanation
Likelihood is moderate-to-high for any first-party attacker: installing an app on one's own shop is trivial and requires no special privilege, and capturing/replaying an HTTP webhook request with modified headers requires no cryptographic secret at all — the attacker only needs raw network/HTTP tooling. No `api_secret_key`, access token, or victim credential is required, satisfying the "unprivileged internet user" bar.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g., by having `HmacValidator`/`Request` verify a canonical string composed of body + these header values) so that `Registry.process` cannot be fed a validly-signed body annotated with an attacker-chosen shop/topic. At minimum, document prominently that `request.shop`/`request.topic` are **not** covered by the HMAC and must not be trusted as tenant identifiers without an independent verification step (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# 1. Attacker triggers a webhook (e.g. orders/create) on their own shop and
#    captures the raw body + valid HMAC Shopify sent to the app's endpoint:
raw_body = '{"id": 1, "note": "malicious content attributed to victim"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)
hmac_b64 = Base64.encode64(valid_hmac)

# 2. Attacker replays the same body/hmac but swaps the shop-domain header:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, unsigned
  "shopify-webhook-id" => "forged-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation succeeds because it only checks raw_body bytes:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the handler believing this data came
#    from "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
