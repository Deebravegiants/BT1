Confirmed: `timeout: 0` on a `DispatchPost` means the message never expires, per `EvmHost.dispatch` and the ISMP spec docs.### Title
Missing `address(0)` validation on `HyperFungibleToken.send`'s recipient permanently burns tokens with no way to recover them - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and dispatches a cross-chain message carrying an arbitrary `params.to` recipient with no validation. On the destination chain, `onAccept` decodes this into an address via `_toAddr` (which only checks byte length, not zero-ness) and mints to it. If the recipient decodes to `address(0)` — whether from a caller mistake, a client-side encoding bug, or a malicious `data`/`to` payload construction — the destination-chain `_mint(address(0), ...)` reverts (OpenZeppelin `ERC20` disallows minting to the zero address). Combined with a `timeout: 0` (the documented "never expires" value), the message can never resolve: it cannot be delivered (mint always reverts) and it can never time out (no expiry) to trigger the refund path in `onPostRequestTimeout`. The burned tokens are then permanently unrecoverable.

### Finding Description
`send()` in `HyperFungibleToken` burns `msg.sender`'s balance up front and builds a `DispatchPost` whose body embeds `params.to` verbatim: [1](#0-0) 

The destination-side handler decodes the message and mints to whatever address `_toAddr` extracts, with `_toAddr` validating only that the byte-slice length is 20 — it performs no non-zero check: [2](#0-1) 

If `message.to` decodes to `address(0)`, `_mint(address(0), amount)` reverts per OpenZeppelin's `ERC20InvalidReceiver` check, so `onAccept` reverts every time it's attempted — the message can never be successfully delivered.

Whether the burned funds can ever be recovered depends entirely on the `timeout` field of `SendParams`, which is threaded straight into `EvmHost.dispatch`: [3](#0-2) 

A `timeout` of `0` is documented, and implemented, as "never expires": [4](#0-3) [5](#0-4) 

With `timeout: 0` set (which the SDK/docs present as a normal, supported option, and which the project's own tests use for cross-chain sends, e.g. `BridgeTokenTest.t.sol`), a request that can never be delivered (because the mint always reverts) also can never be timed out and refunded via `onPostRequestTimeout`. The tokens burned on the source chain are gone forever with no compensating mint or refund path.

This mirrors the reported `UToken.borrow` class of bug — an unvalidated, attacker/user-reachable `address(0)` destination causing loss of funds — but is more severe here because the loss is not just "sent to an address nobody controls," it can become a stuck, permanently undeliverable ISMP message when paired with a zero timeout, i.e., a genuine "route unable to deliver messages" / permanent freezing-of-funds condition reachable by any ordinary token holder calling `send()`.

### Impact Explanation
Any holder of a `HyperFungibleToken` (or the analogous `WrappedHyperFungibleToken`) can lose their entire bridged balance permanently: the source-chain burn is unconditional and immediate, while the destination-side mint is gated by an unchecked `address(0)` recipient that always reverts. When combined with `timeout: 0`, there is no recovery mechanism (no timeout refund, no way to redeliver with a corrected recipient since the request commitment/body is fixed). This is a direct, permanent loss of user funds reachable from a single ordinary transaction with no privileged role required.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `to` is attacker/user supplied raw bytes with no SDK-side or contract-side zero-check, `timeout: 0` is a documented and commonly used value (used in the project's own reference tests for cross-chain sends), and a wrong/zero recipient can arise from integration bugs, encoding mistakes, or malicious construction of calldata by front-ends/relaying tooling built on top of `send()`. No special privileges or race conditions are needed — it is a single dispatch call.

### Recommendation
Add an explicit check in `HyperFungibleToken.send()` (and its upgradeable/wrapped counterparts) that `params.to` decodes to a non-zero, 20-byte address before burning and dispatching, e.g. revert with `InvalidAddress` if `_toAddr(params.to) == address(0)`. As defense in depth, also validate the same in `onAccept`/`onPostRequestTimeout` before minting, and consider disallowing `timeout: 0` for value-bearing sends so that failed deliveries always have a bounded refund path.

### Proof of Concept
1. User calls `HyperFungibleToken.send(SendParams({dest: <chain>, to: abi.encodePacked(address(0)), amount: X, timeout: 0, relayerFee: 0, data: ""}))`.
2. `_burn(msg.sender, X)` executes immediately — tokens are gone on the source chain: [6](#0-5) 
3. The POST request is dispatched with `timeoutTimestamp = 0` (never expires) per `EvmHost.dispatch`: [3](#0-2) 
4. A relayer delivers the message to the destination `HyperFungibleToken.onAccept`, which decodes `to` via `_toAddr` to `address(0)` and calls `_mint(address(0), X)`, which reverts every time it's attempted: [7](#0-6) 
5. Because `timeoutTimestamp == 0`, the request never becomes eligible for `onPostRequestTimeout`'s refund mint, so the burned `X` tokens are permanently lost.

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }

    /// @notice Extracts an address from the first 20 bytes of a bytes memory value
    function _toAddr(bytes memory b) internal pure returns (address addr) {
        if (b.length != 20) revert InvalidAddress(b.length);
        // casting to 'bytes20' is safe because we already checked length
        // forge-lint: disable-next-line(unsafe-typecast)
        return address(bytes20(b));
    }
