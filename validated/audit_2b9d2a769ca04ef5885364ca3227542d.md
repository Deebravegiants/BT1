### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw()`/`onAccept` (Tron) permanently locks escrowed funds for non-compliant tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent funds and protocol dust using a raw low-level `.call()` to the token's `transfer` function, and only checks the boolean `success` of the *call itself*, never decoding/validating the ERC20 `bool` return value the call produced. Non-compliant ERC20 tokens that signal failure by returning `false` (instead of reverting) will make `withdraw()` and the `SweepDust` handler believe the transfer succeeded, permanently finalizing the order and wiping the escrow accounting while the beneficiary never receives the tokens.

### Finding Description
`withdraw()` is the internal function invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` requests. For each escrowed token it does: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    _orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the low-level call reverted, not whether the token's `transfer` function returned `true`. Standard-compliant tokens revert on failure, but many real-world ERC20 tokens (and any non-standard/custom token a solver or user might escrow) return `false` on failure instead of reverting (e.g. insufficient balance edge cases, paused/blacklisted transfers on certain token implementations). In that case `success == true` even though no tokens moved, so the code proceeds to finalize the order (`_filled[commitment] = beneficiary`) and decrement escrow accounting, all before verifying the transfer actually delivered funds.

The identical pattern recurs in the `SweepDust` branch of `onAccept`: [2](#0-1) 

and for fee redemption within `withdraw`: [3](#0-2) 

For comparison, the canonical EVM implementation used elsewhere in the repo (`evm/src/apps/intentsv2/IntentsBase.sol`) correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which decodes and validates the boolean return (or the absence of one) before considering the transfer successful: [4](#0-3) 

The Tron variant deviates from this safe pattern and only guards against the call reverting outright, not against a `false` return.

### Impact Explanation
`withdraw()` is reached whenever Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` cross-chain message — the exact settlement path that pays a solver for filling an intent or refunds a user after cancellation. If the escrowed token silently returns `false` on transfer failure:
- `_orders[commitment][token]` is decremented and `_filled[commitment]` is set to the beneficiary as if the transfer succeeded.
- No tokens are actually delivered to the beneficiary.
- Because the order is now marked filled/refunded, there is no retry path — the escrowed value is permanently stuck in the contract and unrecoverable by the intended party, meeting the "permanent freezing of funds" bar.

The `SweepDust` governance path has a similar but less severe effect (protocol dust falsely marked as swept).

### Likelihood Explanation
This requires the escrowed/fee token to be a non-standard ERC20 that returns `false` rather than reverting on failure — a known and common class of real-world tokens. Since `IntentGatewayV2` accepts arbitrary ERC20 tokens supplied by users/solvers as order inputs/outputs (`order.inputs[i].token`, `TokenInfo.token`), there is no on-chain restriction preventing such a token from being escrowed, making this reachable by any user submitting an order or governance sweeping dust with such a token, without any privileged access needed to trigger the vulnerable code path.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (as already done correctly in `evm/src/apps/intentsv2/IntentsBase.sol`), which validates both call success and, when return data is present, that it decodes to `true`. Apply this fix to `withdraw()`, the `SweepDust` branch of `onAccept`, and the fee-transfer block in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Governance/relayer registers an order whose input token is a non-standard ERC20 that returns `false` (does not revert) when a `transfer` call fails (e.g., due to an internal check like a transfer cap or paused state that the contract doesn't want to hard-revert on).
2. User escrows funds; solver fills the order; Hyperbridge relays a `RedeemEscrow` request to `onAccept`, invoking `withdraw()`.
3. Inside the token's `transfer`, the internal condition causing failure is met, and the token returns `abi.encode(false)` without reverting.
4. `token.call(...)` returns `(success=true, data=abi.encode(false))`; the code only checks `success`, so `_orders[commitment][token] -= amount` executes and `_filled[commitment] = beneficiary` is set.
5. The beneficiary never receives the tokens, yet the order is now finalized — the escrowed amount is permanently stuck with no further code path to release it.
