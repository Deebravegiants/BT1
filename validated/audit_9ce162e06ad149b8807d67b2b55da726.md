### Title
Webhook `shop` field is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain` header — which is *not* included in that HMAC computation — to route the payload to the handler as the tenant identity. This breaks the equality that should hold: `shop-the-signature-was-computed-for == shop-trusted-for-tenant-scoped-processing`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is completely separate data that never enters the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — again, only the body is signed: [3](#0-2) 

`Registry.process` performs exactly this check and then, once it passes, hands `request.shop` straight into the handler as the trusted tenant identifier, with no further binding of `shop` to the signed content: [4](#0-3) 

Because the app's `client_secret` (used as the HMAC key) is shared across **all** shops that install the app, any `(raw_body, hmac)` pair that is valid for one shop is *also a valid HMAC for every other shop* — the signature carries no shop binding at all. An attacker who legitimately installs the app on their own store (an ordinary, unprivileged action available to any internet user via a Shopify dev/trial store) will receive authentic webhook deliveries with a valid body+HMAC pair addressed to their own shop domain. They can then replay that exact `raw_body` and `hmac` to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim shop they want to target). `HmacValidator.validate` will still succeed (it never looks at the header), and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop — a case of stale/unbound-value use exactly analogous to the reported `_isExternalLendingUnhealthy()` bug class, where a value used for a critical decision (`targetAmount` factors) was not the one actually validated/refreshed (`shop` domain not the one actually HMAC-verified).

### Impact Explanation
This crosses a tenant boundary: the host application built on this gem typically uses the webhook's `shop` to look up that shop's stored access token/session and perform shop-scoped side effects (e.g., process an "orders/create" payload, sync inventory, trigger app logic) under the impression the data genuinely originated from that shop. Since the `shop` claim is unauthenticated relative to the signed payload, an attacker can inject arbitrary attacker-crafted webhook bodies "as" any victim shop that has the same app installed, causing cross-tenant data confusion/injection in the merchant's app state. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled/free dev store to obtain one legitimate `(raw_body, hmac)` pair (no special privileges, no leaked credentials, no `client_secret`), and (2) sending a normal HTTP POST to the app's own publicly reachable webhook endpoint with a forged `shop-domain` header. No interaction with Shopify's own webhook delivery infrastructure is required, and the gem's `Registry.process` API — used exactly as documented — performs no additional binding check.

### Recommendation
Do not treat the `shop-domain` (or `webhook-id`/`topic`) header as trusted tenant identity based solely on body-HMAC validation. Either:
- Include the shop domain (and other routing headers) in the signable string so the signature binds to them, if protocol changes are feasible, or
- Require the consuming application to independently verify that the `shop` in the webhook matches a shop for which this specific app installation is registered/expected (e.g., cross-check against a known/authorized shop list or existing stored session) before trusting the tenant-scoped identity, and document this requirement prominently since `Registry.process` on its own does not perform this check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`.
2. Shopify delivers a legitimate webhook: body `B`, headers `x-shopify-hmac-sha256: H` (valid for `B` with the app's `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the same `B` and `H` to the app's webhook endpoint, replacing the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only hashes `B`.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim.myshopify.com"`, and the host app processes attacker-controlled data as if it came from the victim's shop.
