### Title
Webhook `shop` identity taken from an unauthenticated header while HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#hmac` and `#to_signable_string` bind the HMAC signature only to the raw request body, while `Registry.process` trusts `request.shop` (read from the `X-Shopify-Shop-Domain` header) as the tenant identity passed on to the host application's webhook handler, without that header ever being covered by the signature check.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is decoded from the `hmac-sha256` header [2](#0-1) . `HmacValidator.validate` computes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header [3](#0-2) . This proves that only the body bytes are authenticated — the `shop-domain` header is never part of the signed material.

`Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using `request.shop`, which is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header [4](#0-3) [5](#0-4) [6](#0-5) . This is the identity-binding equality that is broken:

`shop authenticated by HMAC` ≠ `shop delivered to the handler (from header)`

Because the shop domain is not part of the HMAC-signed bytes, an unprivileged internet user who can forward or replay a legitimately-signed webhook body (the HMAC only depends on the body, not on the recipient or the shop) can pair that valid signature with an arbitrary `X-Shopify-Shop-Domain` header. `Registry.process` will pass the validated request to the handler tagged with the attacker-chosen shop, even though the signed body may have originated from (or be replayable against) a different tenant.

### Impact Explanation
If a host application uses the `shop` field from `WebhookMetadata` to select which merchant's data to update (a common pattern, e.g., "delete data for shop X" for GDPR webhooks, or crediting an event to a shop's session/store), an attacker who obtains one validly-signed webhook body (bodies are not shop-specific secrets and HMAC verification succeeds for any recipient using the correct `client_secret`-derived key comparison) can relabel it to a different shop domain and have it processed as though it came from that shop. This is a cross-tenant data integrity/isolation break — the same class of "field acted on but not covered by the HMAC" issue described in the report, mapped onto the gem's own webhook verification code.

### Likelihood Explanation
Exploitability depends on the host application trusting `metadata.shop` from the gem without independently cross-checking it against an out-of-band trusted mapping (e.g., matching against the endpoint the webhook was delivered to). Since the gem's own documented contract is "HMAC validates the request," and the `shop` accessor is exposed directly from `WebhookMetadata` as if it were verified, this is a real risk for any consumer following the gem's intended API rather than an application-level misuse of undocumented behavior.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the shop header to the payload before exposing `request.shop`/`WebhookMetadata#shop` as trusted output of `HmacValidator.validate`.

### Proof of Concept
1. Attacker obtains one HMAC-valid webhook body/signature pair sent to the app's endpoint (e.g., by triggering a benign webhook on their own trial store, since the HMAC only signs the body, not the shop).
2. Attacker crafts a POST to the same webhook endpoint with the same body and `hmac-sha256` header, but sets `X-Shopify-Shop-Domain` to a victim shop's domain.
3. `Utils::HmacValidator.validate` returns `true` because it only checks the body against the signature [7](#0-6) .
4. `Registry.process` builds `WebhookMetadata` with `shop: request.shop` set to the victim's domain and dispatches it to the handler [8](#0-7) , causing the host app to act on the victim shop using attacker-controlled body content.
