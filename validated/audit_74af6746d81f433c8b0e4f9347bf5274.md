### Title
Webhook `shop`/`topic` identity is not bound to the HMAC-verified payload, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`) HTTP headers — which are never covered by that HMAC — to identify the tenant the payload belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The tenant identifier consumed by the handler, however, comes from an unauthenticated header, independent of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body and then dispatches using the unverified `request.shop` (and `request.topic`) to attribute the payload to a tenant: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the raw body) and compares it, via `secure_compare`, to the caller-supplied `hmac` header — it never incorporates `shop-domain` or `topic`: [4](#0-3) 

This is exactly the bug class in the source report: a field that is *acted on* (`shop`, used as the tenant identity for the handler) is *not covered by* the cryptographic authentication check (the HMAC only binds the body bytes). The equality that should hold — `shop authenticated == shop the signed bytes actually originated from` — is broken: the gem only proves "these bytes were HMAC-signed by client_secret for *some* legitimate webhook delivery," not "these bytes were signed *for the shop named in this header*."

### Impact Explanation
Any actor who operates their own Shopify store with the target app installed can legitimately receive a validly-signed webhook (real body + real `X-Shopify-Hmac-Sha256` computed by Shopify with the app's `client_secret`) addressed to their own shop. Because the header carrying the shop identity is not part of the signed material, that same valid `(raw_body, hmac)` pair can be replayed to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/hmac pair is genuinely valid), and `Registry.process` calls `handler.handle` with `shop: request.shop` set to the victim's domain while the actual payload content is the attacker's own data. Any host application that uses `WebhookMetadata#shop` (as the gem's own documented API surface returns it) to key per-tenant data, without independently re-deriving the shop from an authenticated source, will attribute attacker-controlled data to the victim tenant — a cross-tenant data-integrity/confusion vulnerability requiring no access to `client_secret`, no privileged account, and no credential theft.

### Likelihood Explanation
The prerequisite (attacker installs the app on their own low-cost/free development or trial store, which is trivial and does not require any special privilege or Shopify partner status) is easily met by an unprivileged internet user. Capturing their own webhook deliveries (raw body + hmac header) requires only controlling the webhook receiving endpoint temporarily, or reading their own delivery logs from the Partner dashboard. No secret material, TLS interception, or social engineering is required.

### Recommendation
Bind the tenant/topic identity into the authenticated material, e.g. include `shop-domain` and `topic` in the signable string (or require the caller to separately validate that `request.shop` matches the shop the session/tenant record expects) before dispatching to `handler.handle`. At minimum, document and enforce that `Registry.process` callers must cross-check `request.shop` against an independently-authenticated session before trusting it, since the current HMAC check gives no such guarantee.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g., `products/create`), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's `client_secret`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` to the app's webhook endpoint.
2. Attacker captures `(B, H)`.
3. Attacker sends a new POST to the same endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` accepts the request (all required headers present); `HmacValidator.validate(request)` recomputes HMAC over `@raw_body == B` and finds it matches `H` — validation succeeds.
5. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))`, causing the host application to process attacker-controlled data under the victim shop's identity.
