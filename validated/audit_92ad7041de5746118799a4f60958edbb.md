### Title
Webhook `shop`/`topic`/`webhook_id` fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching to the app's handler, but the HMAC signature only ever covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are passed straight through to the handler as if they had been verified, breaking the binding `verified(payload) == verified(shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read directly from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string`: [3](#0-2) 

`Registry.process` gates handler dispatch solely on this body-only HMAC check, then forwards the unauthenticated header values (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`) into `WebhookMetadata` for the app's handler to act on: [4](#0-3) 

Critically, the gem's own documentation asserts that this process fully authenticates the request and explicitly instructs developers to key business logic off `data.shop`: [5](#0-4) [6](#0-5) 

Because `shop` (and `topic`/`webhook_id`) are excluded from the signed content, an attacker who legitimately installs the target app on any shop they control (a free/trial store, no special privilege needed) can capture one genuine `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to the app's known webhook endpoint for their own shop, then replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a different, victim tenant's shop domain. `HmacValidator.validate` still succeeds because it never inspected the header, and the handler receives `WebhookMetadata` attributing the (attacker-supplied) payload to the victim shop.

### Impact Explanation
This breaks the tenant identity binding `shop_asserted_by_headers == shop_verified_by_HMAC`, which does not hold in this implementation. A host app following the gem's own documented pattern (using `data.shop` to route/attribute webhook effects, as shown in the docs example) can be made to apply another merchant's webhook data/state changes under an attacker-chosen shop identity — a cross-tenant access issue, matching the Critical impact category (cross-tenant access) defined in scope.

### Likelihood Explanation
The attacker only needs to install the target app once on any store they control (no elevated privileges, no `api_secret_key`, no access token, no TLS interception) and be able to send an HTTP POST to the app's publicly documented webhook path. Constructing the spoofed request requires only header modification, well within reach of an unprivileged internet user.

### Recommendation
Include the relevant Shopify-supplied headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the verified payload (e.g., by requiring the shop domain embedded within the JSON body, where present, to match the header value) before constructing `WebhookMetadata`. Update the documentation to clarify precisely what the HMAC check does and does not guarantee.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker-shop.myshopify.com`; trigger any subscribed webhook (e.g., `orders/create`) so Shopify POSTs a legitimately-signed request to the app's registered endpoint, containing `raw_body` and header `X-Shopify-Hmac-Sha256: <valid_hmac>` plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Capture that `(raw_body, hmac)` pair (e.g., via the attacker's own reverse proxy/logging in front of their own app instance, or any tooling they control since it's their own shop's delivery).
3. Replay an HTTP POST to the same app endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body`: [7](#0-6) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's payload, exactly as the documented handler pattern consumes it, causing the host app to attribute attacker-controlled data to the victim tenant.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
