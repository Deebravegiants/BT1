Confirmed: `TokenExchange.exchange_token` (used for the primary embedded-app "token exchange" flow) is the one OAuth code path in this library that sends the app's `client_secret` to a shop host **without** passing it through `Utils::ShopValidator.sanitize!`, unlike every sibling method (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) which all call `Utils::ShopValidator.sanitize!(shop)` before building the outbound request.

### Title
Unvalidated JWT `dest` claim used as request host in Token Exchange leaks `client_secret` to attacker-controlled host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the shop host it sends the app's `client_secret` to directly from the `dest` claim of the caller-supplied session token, with no domain allow-list check, breaking the binding "host that is authenticated == host that receives the `client_secret`" that is otherwise enforced everywhere else in the auth code.

### Finding Description
`JwtPayload#shop` returns `@dest.gsub("https://", "")` verbatim from the JWT `dest` claim [1](#0-0) . `JwtPayload.new` only verifies the token's HS256 signature against `Context.api_secret_key`/`old_api_secret_key` and checks `aud == Context.api_key` [2](#0-1) ; it never validates that `dest`/`iss` is a trusted `*.myshopify.com`/`myshopify.io`/etc. domain the way `Utils::ShopValidator` does for the OAuth-adjacent flows.

`TokenExchange.exchange_token` takes that unchecked `dest_shop` and builds a session/request directly from it: [3](#0-2) 

That session is passed to `Clients::HttpClient.new`, whose base URI is `"https://#{api_host || session.shop}"` — i.e., the destination host for the outbound HTTP POST carrying `client_id`/`client_secret` is exactly `session.shop` [4](#0-3) .

Every other credential-issuing method in the same module sanitizes the shop first: `ClientCredentials.client_credentials` [5](#0-4) , `RefreshToken.refresh_access_token` [6](#0-5) , and even `TokenExchange.migrate_to_expiring_token` in the very same file [7](#0-6) . Only `exchange_token` skips this step, relying solely on the JWT signature to vouch for `dest` being a real Shopify host — but the signature only proves the token was minted with the app's own secret; it does not constrain what string was placed into the `dest` field when the token was created/relayed to your app.

### Impact Explanation
If any code path in the app (or an intermediary) allows a JWT with an app-controlled/attacker-influenced `dest` value to reach `exchange_token` (e.g., a malformed/relayed token, non-Shopify issuer that nonetheless can produce or replay a same-secret-signed token, or a testing/staging bridge that trusts token content over transport), `client_id` and `client_secret` — the app's `client_secret` — are sent in the POST body to whatever host `dest` names, since `HttpClient` builds the URL straight from `session.shop` with no allow-list. This matches the report's "Critical: theft or exfiltration of the app's client_secret" impact category, and is the same class of "host validated vs. host receiving the credential" binding break called out in the rules.

### Likelihood Explanation
Reachability depends on how `dest` can be populated in a token that still passes signature verification with the app's own `api_secret_key`/`old_api_secret_key`. This is a real gap relative to the rest of the codebase (which treats `shop` strings as untrusted and always calls `ShopValidator.sanitize!` before using them as a request host) but it is currently the only inconsistency of its kind found; I could not fully verify from this index alone whether any external actor without knowledge of the api_secret_key can control `dest` in a token that still validates. Given the difficulty confirming an unprivileged attacker can supply such a token without the secret, likelihood is uncertain, but the missing symmetric check is a clear defense-in-depth gap.

### Recommendation
In `TokenExchange.exchange_token`, sanitize `dest_shop` with `Utils::ShopValidator.sanitize!` (as done in `client_credentials.rb`, `refresh_token.rb`, and `migrate_to_expiring_token`) before constructing `shop_session`/making the outbound request, so the destination host is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what the JWT `dest` claim contains.

### Proof of Concept
Not independently reproducible from static review alone since it requires producing a session token whose `dest` claim is attacker-controlled while still passing `JwtPayload`'s HS256 signature check — a scenario I could not confirm is reachable purely from the indexed library code. The structural gap (missing `ShopValidator.sanitize!` call that is present in every sibling method) is directly verifiable in the cited lines.
