### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body, not headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the HMAC computation. `Webhooks::Registry.process` validates the HMAC and then unconditionally trusts these unauthenticated header values when dispatching the webhook to the handler, breaking the binding `shop-domain header == shop the signed body actually belongs to`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only `@raw_body`; the `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from the (unauthenticated) HTTP headers and are not part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC (over the body only) and then passes the header-derived, unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight into the handler as trusted identity data: [3](#0-2) 

Because the signature never binds to these header fields, an attacker who legitimately receives one valid webhook for a shop they control (e.g., "attacker-shop.myshopify.com") can capture that exact `(raw_body, hmac)` pair — which stays cryptographically valid forever for that body — and replay it to the app's webhook endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook-id`) header for an arbitrary victim shop. `Utils::HmacValidator.validate` still returns `true` because it only re-hashes the untouched body, and `Registry.process` will invoke the handler believing the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism is supposed to enforce: an app built on this gem, following its documented `Registry.process` / handler pattern, cannot distinguish "this body was really produced for this shop" from "this body was signed for some shop, and the shop header was swapped." Downstream, most apps use `WebhookMetadata#shop` to select the tenant record to update, so an attacker-controlled shop can inject or associate arbitrary attacker-authored data into another merchant's tenant context — a cross-tenant access/data-injection primitive, without needing the app's `api_secret_key`, an access token, or any privileged account (only that the attacker be an ordinary merchant who has the app installed on their own store, which is the normal unprivileged-internet-user starting point).

### Likelihood Explanation
Moderate-to-high: any merchant who installs the app can trigger webhooks for their own store (e.g., by creating an order), capture the raw POST body and its valid `X-Shopify-Hmac-Sha256` value, and replay it with a modified `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header to the same public webhook endpoint. No secret material or privileged access is required — only observing one's own legitimately delivered webhook and crafting a replay request.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie the `shop`, `topic`, and `webhook_id` to the signature — e.g., include them (already delivered by Shopify) in an app-level, out-of-band verified channel (mTLS/allowlisted webhook source IPs), or have `Registry.process`/`WebhookMetadata` cross-check the header-derived shop against a shop the app actually has an active session/installation for before trusting it, and document to consumers that `request.shop`/`request.topic` are NOT covered by the HMAC and must not be trusted as tenant-authenticated on their own.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw body `B` and the resulting valid header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the *same* body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object whose `hmac` is still `H` and whose `to_signable_string` is still `B`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(secret, B)` and gets `H` — validation succeeds.
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), topic: ..., webhook_id: ...)`, causing the app to process attacker-authored data under the victim shop's tenant identity. [3](#0-2)
