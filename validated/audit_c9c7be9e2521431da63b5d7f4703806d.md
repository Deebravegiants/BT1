### Title
Webhook shop/topic identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id` and `api_version` are read from unauthenticated HTTP headers and passed straight to the host application's handler as trusted, per-tenant identity data. The HMAC signature that `ShopifyAPI::Utils::HmacValidator` checks therefore proves only that the *body bytes* were signed by Shopify with the app's secret — it proves nothing about which shop the body belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` is the only integrity gate applied to an inbound webhook: [1](#0-0) 

It calls `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to compute the expected signature: [2](#0-1) 

`Request#to_signable_string` is defined to return `@raw_body` only: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from raw, attacker-controllable HTTP headers with no cross-check against the HMAC: [4](#0-3) 

`Registry.process` then hands these unauthenticated header values straight to the app's handler as the tenant identity of the event: [5](#0-4) 

The gem's own documentation confirms `shop` is meant to be trusted tenant-identifying data handed to the app: `data.shop` — "The shop domain of the webhook" — used directly to route/attribute the payload (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 

**Broken identity binding (as an equality):** the gem implicitly asserts `hmac_valid(raw_body) == shop_header_trustworthy`, but the actual relationship is `hmac_valid(raw_body) ⇏ shop_header_authentic`. The bytes that are cryptographically verified (`raw_body`) are disjoint from the bytes that are used to decide *whose* tenant this event belongs to (`shopify-shop-domain` / `x-shopify-shop-domain` header).

### Impact Explanation
Any unprivileged internet user who can capture one legitimately-signed webhook delivery for their own shop (they control a shop that is a merchant of the host app and can observe webhooks sent to their own registered endpoint, since HTTP webhook endpoints are typically public) can replay that exact body with only the `x-shopify-shop-domain` header changed to point at a victim shop. `HmacValidator.validate` will still return `true` because the signature only ever covered `@raw_body`, and `Registry.process` will invoke the host handler with `data.shop` set to the attacker-chosen victim shop domain. In a multi-tenant host application that uses `data.shop` to select which tenant's records to create/update/delete (the exact usage pattern shown in this gem's own documentation), this enables cross-tenant data injection/corruption — an attacker-controlled shop can make forged, believable webhook events appear to originate from a different, victim shop.

### Likelihood Explanation
Likelihood is moderate-to-high: webhook HTTP endpoints are public by necessity, an attacker only needs their own (or any) merchant shop connected to the target app to obtain one genuinely-signed sample payload, and no special credentials, tokens, or `api_secret_key` knowledge are required — only header manipulation on a replayed request, which is trivial for any user capable of sending HTTP requests to the app's webhook route.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC computation, or otherwise cryptographically bind them to the payload before dispatching to the handler, so that a forged/replayed header combination invalidates the signature. At minimum, document prominently that `data.shop` in `WebhookMetadata` is **not** authenticated by the HMAC check and that host applications must independently verify the shop domain against an existing, known session/installation before trusting it for tenant routing.

### Proof of Concept
1. Attacker controls (or is) a merchant with shop `attacker-shop.myshopify.com`, which has the app installed and receives real webhooks at the app's public webhook endpoint.
2. Shopify delivers a legitimately HMAC-signed webhook (e.g., `orders/create`) with body `B` and header `x-shopify-shop-domain: attacker-shop.myshopify.com`; the attacker records the full request including the valid `x-shopify-hmac-sha256` value.
3. Attacker resends the identical body `B` and HMAC header to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` computes `HmacValidator.validate` using only `@raw_body` (`request.rb#to_signable_string`), which is unchanged — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)`, causing the host app to process attacker-supplied order data as if it belonged to `victim-shop.myshopify.com`.
