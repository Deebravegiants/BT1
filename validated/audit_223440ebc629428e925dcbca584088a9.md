### Title
Cross-tenant webhook shop spoofing due to `shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` identity that is handed to the app's handler is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never part of the signed payload. An attacker who can obtain one validly-signed webhook body (e.g. because the app is installed on their own store, so Shopify legitimately sends them HMAC-signed webhooks) can replay that same body to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates because the signature only covers the body, so the handler executes with attacker-chosen `shop` metadata, breaking the binding "shop authenticated == shop the data belongs to."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from attacker-controllable HTTP headers, independent of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (which is computed exclusively from `to_signable_string`, i.e. the body) and then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the metadata passed to the host app's handler: [3](#0-2) 

`HmacValidator.validate` confirms the signature is computed purely over `to_signable_string`, with no shop binding: [4](#0-3) 

`VerifiableQuery` interface only requires `hmac` and `to_signable_string`, formalizing that headers such as `shop-domain` are excluded from what gets authenticated: [5](#0-4) 

`WebhookMetadata.shop` is a plain, unauthenticated string field that the handler is required to trust: [6](#0-5) 

**Root cause equality that is broken:** the gem implicitly assumes `shop header == shop that produced/authorized the signed body`, but the signature computation never includes the shop, so nothing in the gem enforces this equality. Any tenant who legitimately receives a real, HMAC-signed webhook for their own store (a normal, unprivileged use of the app — not requiring `api_secret_key` or any elevated access) can replay that exact body with a forged `shop-domain` header value pointing at a victim shop, and `Registry.process` will pass the forged shop through to the handler with a still-valid HMAC.

### Impact Explanation
This is a cross-tenant identity-binding failure: an app that keys any per-request behavior (data storage, lookups, redaction actions such as the mandatory `shop/redact` and `customers/redact` topics, billing, audit logging) off `WebhookMetadata#shop` as returned by this gem's `Registry.process` API can be made to attribute a legitimate-body webhook to the wrong shop. Because `MANDATORY_TOPICS` includes GDPR/redaction webhooks, a forged `shop` value could cause redaction, or data processing meant for the attacker's own store, to be misapplied under the identity of another merchant — a cross-tenant impact, which meets the Critical bar.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one validly-signed webhook body to replay (i.e., they need the app installed on some shop they control, which is the normal, low-privilege path for any merchant installing a public Shopify app). No `api_secret_key`, access token, or privileged account is required — only ordinary use of the app as an installing merchant plus the ability to intercept/observe one of their own webhook deliveries and resend a modified HTTP request to the app's public webhook endpoint with a different `shop-domain` header. This is a realistic, low-effort exploitation path once the gem's own `process` API is used as documented.

### Recommendation
- Bind the `shop` (and other trust-sensitive fields such as `topic`) into the signed content, or otherwise cryptographically tie the HMAC to the shop that legitimately owns it (e.g., use a shop-specific verification key/lookup rather than the single app-wide secret, or include the shop domain in the value that is HMAC-verified).
- At minimum, document/require that host applications cross-check `WebhookMetadata#shop` against a shop that is known to be registered/installed and expected to send that topic, rather than trusting it as authenticated purely because the HMAC check passed.
- Consider exposing a method that returns whether the `shop` header was part of the authenticated data, and reject or clearly flag processing when it is not.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary merchant onboarding — no special privilege).
2. Shopify sends the app a legitimately HMAC-signed webhook for `attacker-shop.myshopify.com`, e.g.:
```
POST /webhooks
x-shopify-topic: customers/redact
x-shopify-hmac-sha256: <valid-signature-for-body>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {"customer": {...attacker-controlled redact payload...}}
```
3. Attacker captures this raw body and its valid `x-shopify-hmac-sha256` value (both attacker-visible, since it was addressed to them).
4. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but changes only the shop header:
```
POST /webhooks
x-shopify-topic: customers/redact
x-shopify-hmac-sha256: <same-valid-signature, unchanged>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: <identical body>
```
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only hashes `@raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
6. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` per `lib/shopify_api/webhooks/registry.rb:198-199` and invokes the host app's handler as if the (attacker-supplied) payload legitimately came from `victim-shop.myshopify.com`.
