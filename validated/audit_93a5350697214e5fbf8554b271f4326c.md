Based on the investigation, there is a directory-traversal analog in the workflow artifact fetcher.

### Title
Directory Traversal in HTTP artifact fetcher allows escaping the configured base path - (File: core/services/workflows/syncer/v2/fetcher.go)

### Summary
`newHTTPFetcher`, one of the `FetcherFunc` implementations returned by `NewFetcherFunc`, builds the outbound fetch URL by joining an attacker/workflow-controlled `req.URL` value onto a configured base URL without properly containing it inside that base path, unlike its sibling `newFileFetcher` which explicitly validates the joined path stays under `basePath`.

### Finding Description
`newHTTPFetcher` attempts to prevent traversal only by calling `filepath.Clean` and trimming a single leading `/`: [1](#0-0) 

`filepath.Clean` does **not** remove leading `..` segments — it only normalizes redundant separators/`.`; it strips leading `..` only when the path is already rooted. Because `cleanPath` may still contain leading `../../..` segments, the subsequent `u.Path = filepath.Join(u.Path, cleanPath)` call (which internally also calls `Clean`) can resolve the traversal and escape the intended base path within the configured host, e.g. turning `basePath/artifacts` + `../../../admin/secret` into `/admin/secret` on the same host.

This is the same root cause class as CVE-2025-57682 (Papermark): a path/URL supplied by an authenticated caller is joined onto a trusted base without validating that the final resolved path is still confined to the intended prefix, allowing retrieval of resources outside the intended scope.

Contrast this with the file-based fetcher in the same file, which correctly re-validates the resolved path after `filepath.Join`: [2](#0-1) 

The unit tests only exercise this traversal guard against the **file** fetcher (`../../../etc/passwd` rejected with "is not within the basePath"): [3](#0-2) 

No equivalent traversal-rejection test exists for `newHTTPFetcher`, and the code has no analogous prefix check.

`req.URL` for the HTTP fetcher path originates from workflow artifact locations (`binaryURL`/`configURL`) supplied through the workflow artifact fetch flow in `FetchWorkflowArtifacts`: [4](#0-3) [5](#0-4) 

These URLs are ultimately populated from workflow-registration data (`BinaryURL`/`ConfigURL`), which an authenticated workflow owner controls when registering a workflow. I was not able to fully trace, within the remaining tool budget, whether `newHTTPFetcher` (as opposed to the DON-gateway-mediated `FetcherService.Fetch`) is the fetch function actually wired into `Store` in the production node configuration — this wiring (in `core/services/cre/cre.go` and related startup code) could not be confirmed before running out of iterations.

### Impact Explanation
If an attacker-controlled path segment reaches `newHTTPFetcher`, they can cause the node to request arbitrary paths on the configured artifact-storage HTTP host rather than the intended base directory/prefix, potentially retrieving other tenants' or internal artifacts served from the same host (cross-user response confusion / allowlist bypass), mirroring the impact of the Papermark CVE (arbitrary file retrieval via a proxy that fails to constrain the resolved path).

### Likelihood Explanation
Likelihood depends on whether `newHTTPFetcher` is actually used as the artifact-fetching function in a deployment where `req.URL` is influenced by workflow-registration data supplied by workflow owners (an authenticated, non-operator role) and where the artifact storage host serves multiple workflows/tenants under path-based isolation. This reachability could not be fully confirmed in this pass.

### Recommendation
Mirror the `newFileFetcher` containment check in `newHTTPFetcher`: after joining `cleanPath` onto the base URL's path, verify the resulting `u.Path` still has the original base path as a strict prefix (or lexically resolve and reject any path containing unresolved `..` before the join), returning an error otherwise instead of silently constructing a URL outside the intended scope.

### Proof of Concept
1. Configure `NewFetcherFunc` with `baseURL = "https://artifacts.example.com/tenantA/"`.
2. Trigger an artifact fetch with `req.URL = "../tenantB/secret-config.json"` (e.g., via a workflow's `ConfigURL`/`BinaryURL`).
3. `filepath.Clean("../tenantB/secret-config.json")` leaves the leading `..` intact; `filepath.Join("/tenantA/", "../tenantB/secret-config.json")` resolves to `/tenantB/secret-config.json`.
4. The node issues an HTTP GET to `https://artifacts.example.com/tenantB/secret-config.json`, retrieving another tenant's artifact instead of one under `tenantA`.
