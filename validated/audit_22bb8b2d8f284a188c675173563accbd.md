### Title
Wallet Contract loses caller's attached deposit when calls to the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` fail - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (NEP-518, used for ETH-implicit accounts) hardcodes the account ID of its Address Registrar dependency at compile time via `include_str!`, exactly mirroring the reported bug class of a hardcoded external-contract address that is never validated against the actual deployment. When the cross-contract call to this hardcoded registrar fails, the failure-handling branch of `address_check_callback` (unlike its sibling `rlp_execute_callback`) does not refund the caller's attached deposit, permanently stranding those funds in the contract.

### Finding Description
The registrar account ID is baked into the compiled wasm binary as a constant: [1](#0-0) 

This constant is used, unconditionally, whenever an `EOABaseTokenTransfer` requires an address check (i.e. the relayer-supplied `target` looks like it could collide with a registered named account): [2](#0-1) 

Because this value is compiled once into the shared Wallet Contract wasm that is deployed identically to every ETH-implicit account across the network, any drift between the hardcoded account ID and the actual, live Address Registrar contract (wrong account name, registrar not yet deployed/initialized, or a differently-versioned registrar without a `lookup` method) causes the cross-contract call to fail outright — the same failure mode described in the source report, where a hardcoded dependency address does not match the real deployed contract.

When that cross-contract call fails, `address_check_callback` handles it as follows: [3](#0-2) 

Note this branch simply returns an error `ExecuteResponse` — it does **not** use the `caller_deposit` parameter it was given to refund the caller. This is inconsistent with the contract's own documented invariant that `CallerDeposit` exists specifically "to refund the caller's deposit if the cross-contract call fails": [4](#0-3) 

and inconsistent with how `rlp_execute_callback` correctly performs this refund on failure: [5](#0-4) 

Because `rlp_execute` (and `address_check_callback`) return a `Value`/`PromiseOrValue::Value` rather than panicking, NEAR's protocol-level automatic deposit refund (which only triggers when a receipt/action actually fails) does not apply — the attached deposit is treated as successfully consumed by the contract. The same missing-refund pattern also exists in `nep_141_storage_balance_callback`'s `PromiseResult::Failed` arm: [6](#0-5) 

### Impact Explanation
Any external caller (typically a relayer) that attaches a NEAR deposit to `rlp_execute` for a base-token transfer requiring an address check will have that deposit irretrievably absorbed by the Wallet Contract if the hardcoded Address Registrar call fails for any reason (misconfigured/mismatched account ID, registrar not deployed on that network/environment, or the registrar's interface changing). This is an unauthorized/unrecoverable balance change against the caller, directly analogous to the reported issue where a hardcoded external contract address guarantees loss of expected value (there, COMP rewards; here, the relayer's attached NEAR deposit) whenever that address is not exactly correct.

### Likelihood Explanation
The `ADDRESS_REGISTRAR_ACCOUNT_ID` is a single hardcoded value shared by every ETH-implicit-account deployment of this contract; any mismatch (e.g., deploying/testing on a different network, upgrading the registrar contract's interface, or a registrar account not yet created at genesis) reliably triggers `PromiseResult::Failed` on every affected transaction, not just an edge case. This is directly reachable by any relayer or user submitting an `rlp_execute` transaction with a nonzero attached deposit for a base-token transfer to a candidate eth-implicit target.

### Recommendation
In `address_check_callback` (and `nep_141_storage_balance_callback`), refund `caller_deposit` in the `PromiseResult::Failed` arm exactly as `rlp_execute_callback` does, so a failed lookup against the Address Registrar cannot strand user/relayer funds. Additionally, consider making the registrar account configurable/verifiable at runtime (e.g., via a settable field or genesis-config value) rather than baked into the wasm via `include_str!`, so that deployment mismatches fail safely instead of silently losing deposits.

### Proof of Concept
1. Deploy the Wallet Contract to an ETH-implicit account on a network/environment where the account named in `ADDRESS_REGISTRAR_ACCOUNT_ID` (`address-map.near`) either does not exist or does not implement the expected `lookup(address) -> Option<AccountId>` method.
2. A relayer submits `rlp_execute` with a signed Ethereum-style transaction representing a base-token transfer whose `target` triggers the `address_check` path, attaching a NEAR deposit (`caller_deposit`).
3. `inner_rlp_execute` issues a cross-contract call to the hardcoded, non-functional registrar account, which fails.
4. `address_check_callback` receives `PromiseResult::Failed` and returns `ExecuteResponse { success: false, ... }` without invoking any refund logic for `caller_deposit`.
5. Since the call to `rlp_execute` completed with a `Value` (not a panic), NEAR does not auto-refund the attached deposit, and the relayer's deposit remains permanently held by the Wallet Contract with no code path to recover it.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
