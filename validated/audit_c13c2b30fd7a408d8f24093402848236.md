### Title
Missing upper-bound validation on `destinationFeeBps` in Tron `IntentGatewayV2.onAccept` can permanently revert `placeOrder` for a destination chain - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron deployment of `IntentGatewayV2` applies a governance-supplied `destinationFeeBps` override directly to `_destinationProtocolFees` without validating it stays below `10_000` (100%). The EVM mainline contract enforces this bound, but the Tron fork's `UpdateParams` handler does not. A `destinationFeeBps` value at or above `10_000` makes `protocolFee > originalAmount` in `placeOrder`, causing an unconditional underflow revert that permanently bricks order placement to that destination chain, unbacked by any recovery other than a second, correct governance update.

### Finding Description
`placeOrder` computes, per input token, using whichever `destinationFeeBps` is set for the order's destination: [1](#0-0) 

```
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
```

`reducedAmount = originalAmount - protocolFee` underflows and reverts whenever `protocolFeeBps >= 10_000`, since `protocolFee` would equal or exceed `originalAmount`.

On the mainline EVM contract, this is prevented by `IntentsBase._updateParams`, which explicitly rejects any `destinationFeeBps >= 10_000` before writing it into storage: [2](#0-1) 

The Tron variant, however, implements its own inline `UpdateParams` handling inside `onAccept` and skips this validation entirely — it writes `feeBps` straight into `_destinationProtocolFees` with no bound check: [3](#0-2) 

This mirrors the referenced Sherlock finding's root cause: an admin-configurable fee parameter with no enforced upper bound flows into a subtraction later performed on user funds, and the lack of a bound turns an otherwise valid configuration update into a permanent DoS for the affected code path.

### Impact Explanation
Once a `destinationFeeBps >= 10_000` is set for a given destination chain (through a normal, non-malicious `UpdateParams` cross-chain governance message that simply omits validation the mainline contract has), every subsequent `placeOrder` call targeting that destination reverts due to arithmetic underflow. This is a route unable to deliver messages/orders: users can no longer open orders to that destination on Tron until a further corrective governance update is dispatched and delivered cross-chain, which itself requires waiting for the full IBC/consensus-proof cycle. This satisfies the "route unable to deliver messages" acceptance criterion for Medium severity — the freeze is only fixed by another privileged action, not user recourse.

### Likelihood Explanation
The trigger does not require a malicious actor: it only requires a `destinationFeeBps` value of `10_000` or higher to be set for a destination — an operational/config mistake identical in nature to the original `referrerTierStep`-without-upper-bound bug. Because the mainline EVM version of the exact same contract already codifies the fix (validate `< 10_000`), it demonstrates the developers recognize the need for this bound but failed to port it to the Tron fork, making an eventual occurrence plausible via ordinary parameter tuning across many destination chains.

### Recommendation
Add the same bound check used in `IntentsBase._updateParams` to the Tron `onAccept`'s `UpdateParams` branch: reject (revert) any `destinationFeeBps >= 10_000` before writing to `_destinationProtocolFees`, and likewise validate `protocolFeeBps`/`surplusShareBps` bounds for `_params` updates, keeping the Tron contract's governance-update path consistent with the validated mainline implementation.

### Proof of Concept
1. Hyperbridge governance dispatches an `UpdateParams` request to the Tron `IntentGatewayV2` setting `destinationFees = [{ chain: "SOME_CHAIN", destinationFeeBps: 10_000 }]` (or any value ≥ 10,000) — no error occurs because the Tron `onAccept` performs no bound check, unlike the mainline contract's `_updateParams`. [3](#0-2) 
2. Any user calls `placeOrder` with `order.destination = "SOME_CHAIN"` and a nonzero input amount.
3. Inside `placeOrder`, `protocolFeeBps` resolves to `10_000`, so `protocolFee = originalAmount`, and `reducedAmount = originalAmount - protocolFee` underflows, reverting the transaction. [1](#0-0) 
4. Every subsequent `placeOrder` call to `"SOME_CHAIN"` reverts identically until governance dispatches a corrective `UpdateParams` message and it clears the cross-chain delivery pipeline.

    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
