### Title
Partial unlock() failure leaves primary seed unlocked in Keychain while Wallet.isLocked() reports true - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet.unlock()` adds the primary seed to the keychain and sets `#primarySeedIdAtom` *before* processing extra seeds; if extra-seed retrieval/decryption or `keychain.addSeed` for an extra seed throws, the outer `catch` swallows the error, throws a generic `'Wrong password. Try again.'`, and never rolls back the already-successful primary-seed unlock. `Wallet.#isLocked` remains `true`, but `Keychain` internally has the primary seed unlocked and fully usable for signing/exporting.

### Finding Description
In `unlock()`: [1](#0-0) 
the sequence is:
1. `#getSeed({ passphrase })` decrypts the primary seed.
2. `#keychain.addSeed(seed)` is called — this immediately sets `this.#seedLockStatus[seedId] = false` inside `Keychain`, independent of any wallet-level flag: [2](#0-1) 
3. `this.#primarySeedIdAtom.set(primarySeedId)` persists the now-active primary seed id.
4. `#getExtraSeeds()` (which itself calls `#getExtraSeedsPassphrase()` → `keychain.exportKey` on the just-unlocked primary seed) decrypts `EXTRA_SEEDS_KEY`, and each extra seed is fed to `#keychain.addSeed`.
5. Only after all of that succeeds is `this.#isLocked = false` set.

If step 4 throws (corrupted/incompatible `EXTRA_SEEDS_KEY` entry, or a rejected `addSeed` call for an extra seed), execution jumps to the `catch` block, which unconditionally rethrows `'Wrong password. Try again.'` and never resets `#isLocked` nor calls `this.#keychain.removeAllSeeds()` to undo the already-completed primary-seed unlock: [3](#0-2) .

Because `Keychain.exportKey`/`signBuffer` gate solely on their own internal `#seedLockStatus` map (`#assertPrivateKeysUnlocked`) and have no dependency on `Wallet.#isLocked`, [4](#0-3) , any caller with a reference to the keychain module (or any wallet method that doesn't route through `Wallet.#assertWalletIsUnlocked`) can successfully sign or export the primary seed's private key even though `Wallet.isLocked()` reports `true`.

### Impact Explanation
This breaks the "locked means locked" invariant: `Wallet.isLocked()` is the source of truth surfaced to UI/RPC callers to gate signing/export, yet the keychain module — the actual key-material holder — remains unlocked for the primary seed. Any code path that reaches the keychain directly (bypassing `Wallet.#assertWalletIsUnlocked`) can sign transactions or export the primary private key from a wallet the UI/RPC surface believes is locked, i.e., an auth-bypass / privilege-persistence condition on the primary seed's key material.

### Likelihood Explanation
Requires `usePassword` enabled and an extra-seed entry that is corrupt or otherwise fails to decrypt/decode after being added through a normal import/backup restore flow (e.g. `addSeed()` persists `EXTRA_SEEDS_KEY` via `#setExtraSeeds` before calling `#keychain.addSeed(data.seed)`, so a keychain-side rejection there leaves a stored extra-seed entry whose future unlock will always fail at the `keychain.addSeed` step) — see `addSeed()`: [5](#0-4) . Once such an entry exists, every subsequent `unlock()` call deterministically reproduces the partial state, making this a repeatable bug, not a race condition.

### Recommendation
On any failure inside `unlock()` after `#keychain.addSeed(seed)` has succeeded, roll back the keychain state (e.g. call `this.#keychain.removeAllSeeds()`) before rethrowing, and only persist `primarySeedIdAtom` after the entire unlock sequence (including extra seeds) has succeeded. Ensure `Wallet.#isLocked` and `Keychain`'s internal lock status can never diverge — either by having the wallet's lock check consult keychain state directly, or by guaranteeing atomic all-or-nothing unlock semantics.

### Proof of Concept
Unit test (Jest-style) forcing `#getExtraSeeds` to reject after a real `#keychain.addSeed` call for the primary seed:
```js
test('unlock() leaves primary seed unlocked in keychain despite isLocked() === true', async () => {
  const keychain = createRealKeychainInstance() // real Keychain, not mocked
  const wallet = createWallet({ keychain, /* usePassword: true, maxExtraSeeds: 1, ... */ })

  await wallet.create({ passphrase: 'pw' })
  // Simulate a corrupted EXTRA_SEEDS_KEY entry, e.g. by writing malformed bytes
  // directly into walletStorage under EXTRA_SEEDS_KEY after a legit addSeed() flow,
  // or stub walletStorage.get for EXTRA_SEEDS_KEY to throw once decrypted.

  await expect(wallet.unlock({ passphrase: 'pw' })).rejects.toThrow('Wrong password. Try again.')

  expect(await wallet.isLocked()).toBe(true) // wallet believes it's locked

  const primarySeedId = await wallet.getPrimarySeedId()
  // Yet keychain still allows exporting/signing with the primary seed:
  const { privateKey } = await keychain.exportKey({
    seedId: primarySeedId,
    keyId: /* some valid keyId */,
    exportPrivate: true,
  })
  expect(privateKey).toBeTruthy() // proves key material is usable despite isLocked() === true
})
```
Expected assertions: `wallet.isLocked()` returns `true`, while `keychain.exportKey`/`signBuffer` for `primarySeedId` succeed without throwing `'private keys are locked'`.

  unlock = async ({ passphrase } = {}) => {
    try {
      const { seed } = await this.#getSeed({ passphrase })
      const primarySeedId = await this.#keychain.addSeed(seed)
      this.#primarySeedIdAtom.set(primarySeedId)

      const extraSeeds = await this.#getExtraSeeds()
      await Promise.all(extraSeeds.map(({ seed }) => this.#keychain.addSeed(seed)))

      this.#isLocked = false

      return { primarySeedId }
    } catch (err) {
      this.#logger.debug('unlock() failed: wrong password', err)
      throw new Error('Wrong password. Try again.')
    }
  }
