### Title
Protocol fee on `IntentGatewayV2.placeOrder` rounds down to zero for small-enough inputs, letting a caller escape the fee entirely - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` computes the protocol fee taken from each order input with `protocolFee = (originalAmount * protocolFeeBps) / 10_000` before dividing, without ever checking that a non-zero `protocolFeeBps` actually yields a non-zero fee. Integer division floors the result to `0` whenever `originalAmount * protocolFeeBps < 10_000`, letting an unprivileged order-placer dodge the fee by keeping each escrowed input below that threshold — the exact same rounding-to-zero fee-evasion pattern described in the external Perennial `positionFee` report.

### Finding Description
`placeOrder` is reachable by any address (an "unprivileged" intent creator) and, when `protocolFeeBps > 0`, deducts a protocol fee from each input token before escrowing and hashing the order commitment: [1](#0-0) 

```solidity
if (protocolFeeBps > 0) {
    reducedInputs = new TokenInfo[](inputsLen);
    for (uint256 i; i < inputsLen;) {
        uint256 originalAmount = order.inputs[i].amount;
        if (originalAmount == 0) revert InvalidInput();
        uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
        uint256 reducedAmount = originalAmount - protocolFee;
        ...
        if (protocolFee > 0) emit DustCollected(token, protocolFee);
        reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
        ...
    }
}
```

The division `(originalAmount * protocolFeeBps) / 10_000` truncates towards zero. If `originalAmount * protocolFeeBps < 10_000`, `protocolFee` evaluates to `0` and the entire input amount is escrowed fee-free, even though `protocolFeeBps` (or a per-destination override) is configured to be non-zero. This mirrors exactly the root cause in the cited Perennial report — a multiply-then-divide fee formula with no floor/non-zero sanity check, letting a caller who controls the input size choose amounts small enough to always round the fee to `0`.

The docs even describe the fee model (`protocolFee = input.amount × protocolFeeBps / 10_000`) without mentioning any zero-fee guard: [2](#0-1)  and the SDK's mirrored helper reproduces the same unguarded floor: [3](#0-2) . The same vulnerable pattern is duplicated verbatim in the Tron and SDK-vendored copies of the contract: [4](#0-3) .

### Impact Explanation
Every order whose per-token input amount is small enough (below `10_000 / protocolFeeBps` raw token units) escrows and settles with **zero** protocol fee collected, while the protocol still incurs escrow/settlement overhead for that order. A user who wants to move a large amount fee-free can split it into many sub-threshold orders (e.g. for the deployed 5 bps fee, any single input below `2,000` raw units of a token pays no fee at all — trivially reachable for any token with meaningful decimals, e.g. an 18-decimal token where `2,000` wei is economically negligible per order but the *aggregate* moved value can still be large). This causes systemic under-collection of protocol revenue (a fee-evasion / unbacked-fee shortfall across the intents escrow surface), which the rules classify as a form of fund loss/permanent fee-revenue leakage from an unprivileged, directly reachable dispatch path (`placeOrder`).

### Likelihood Explanation
High reachability: `placeOrder` is a public, unauthenticated entry point that any address can call with arbitrary `TokenInfo.amount` values, requiring no special permissions, proofs, or relayer cooperation. The only "cost" to the attacker/user is the marginal gas of issuing more orders, which is far outweighed by the value of the aggregate transferred principal when the per-fill fee threshold is a small fraction of typical order sizes (especially on low-gas-cost L2/EVM destinations where the protocol is deployed). No existing check in `placeOrder` (or its Tron/SDK counterparts) enforces `protocolFee > 0` when `protocolFeeBps > 0`.

### Recommendation
After computing `protocolFee`, add a sanity check mirroring the Perennial-report remediation: if `protocolFeeBps != 0` and the computed `protocolFee == 0`, either revert the order (rejecting inputs too small to fee) or round the fee up (ceiling division) so a configured non-zero fee can never be silently bypassed:

```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
if (protocolFeeBps != 0 && protocolFee == 0) revert InputTooSmallForFee();
```
or use a ceiling-division helper (`(originalAmount * protocolFeeBps + 9_999) / 10_000`) consistently in both the contract and the SDK's `deductProtocolFee`/`grossUpForProtocolFee` mirrors so the on-chain and off-chain fee math stay in sync.

### Proof of Concept
1. Governance sets `protocolFeeBps = 5` (0.05%, the documented default) globally or for a destination.
2. A user calls `placeOrder` with `order.inputs[0].amount = 1999` (any value `< 2000`).
3. In `placeOrder`: `protocolFee = (1999 * 5) / 10_000 = 9995 / 10_000 = 0` (integer division truncates).
4. `reducedAmount = 1999 - 0 = 1999` — the full amount is escrowed, `DustCollected` is not emitted (`protocolFee > 0` check fails), and the commitment/escrow reflect zero fee taken.
5. Repeating this with many sub-2000-unit orders lets a user move an arbitrary aggregate amount through the gateway while never paying the configured protocol fee, exactly as described for `openTakeFor`/`_closeTake` in the cited Perennial report.

/** Mirrors the gateway's floored fee deduction. */
export function deductProtocolFee(amount: bigint, protocolFeeBps: bigint): bigint {
	if (protocolFeeBps <= 0n) return amount
	const fee = (amount * protocolFeeBps) / BPS_DENOMINATOR
	return amount - fee
}
