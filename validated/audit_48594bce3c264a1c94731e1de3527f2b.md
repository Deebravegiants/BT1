### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the request, then dispatches to the app's handler using `request.shop`, `request.topic`, `request.api_version`, and `request.webhook_id`. However, `Webhooks::Request#to_signable_string` returns only `@raw_body`, so none of those identity/routing fields are covered by the HMAC. Any caller who can obtain one genuine `(body, hmac)` pair for a webhook topic (e.g., by installing the app on their own shop) can replay that exact body/HMAC to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a victim shop, and the signature check still passes.

The `shop`, `topic`, `api_version`, and `webhook_id` values used by the rest of the class are pulled straight from HTTP headers, not from the signed body: [2](#0-1) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against an HMAC computed over `to_signable_string` (the raw body): [3](#0-2) 

`Registry.process` treats a passing HMAC check as authenticating the whole request, including the header-derived `shop`, and forwards it to the app's handler: [4](#0-3) 

The equality this breaks is: **shop claimed via the `X-Shopify-Shop-Domain` header == shop that actually authored the signed body**. The HMAC only proves "this body byte string was produced with our shared secret"; it proves nothing about which shop's header should accompany it, because the header is never part of the signable string.

### Impact Explanation
An attacker who can install the target app on their own Shopify store (an ordinary, unprivileged action any internet user can take) legitimately receives real webhook deliveries — genuine `(raw_body, X-Shopify-Hmac-Sha256)` pairs signed with the app's shared secret. Because the header block (topic/shop/webhook-id/api-version) is not part of the signed material, the attacker can replay that captured, validly-signed body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (body is byte-identical, HMAC untouched), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: <forged victim shop>, body:, ...)`. Any app logic that keys off `data.shop` (e.g., looking up the victim's session/access token, writing/merging data under the victim's tenant record, or triggering shop-scoped side effects) will act as though the victim shop sent that payload — a cross-tenant data-confusion/injection primitive achieved without ever needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Likelihood is realistic: obtaining a legitimately signed webhook body only requires installing the (typically public) app once on an attacker-owned store — no secret material, TLS interception, or social engineering needed. Forging arbitrary HTTP headers on a request to the app's own public webhook endpoint is trivial. The only constraint is that the replayed body's *content* is whatever the attacker's own store produced (they don't get to choose the victim's real data), but for topics whose body content is attacker-influenced (e.g., `app/uninstalled`, `shop/update`, `customers/data_request`, or any custom fields the attacker controls within their own shop's webhook payload) this is enough to inject falsely-attributed events for a shop the attacker does not own.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the HMAC before trusting them:
- Include the relevant Shopify headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in `to_signable_string`, matching whatever canonicalization Shopify uses to compute the HMAC over combined header+body context, **or**
- If Shopify's HMAC scheme genuinely only covers the body (as it does for standard webhook delivery), have `Registry.process` treat `request.shop` as merely informational/routing data and require the consuming app to independently verify that the shop asserted by the webhook actually has an active, matching session/install record before trusting it for any tenant-scoped action — document this requirement prominently so host apps don't implicitly trust `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `shop/update`).
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: shop/update`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and some JSON body.
3. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value.
4. Attacker sends this exact body and HMAC header to the app's public webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. In the gem: `Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` matches (`Digest.hexencode(Base64.decode64(...))`) and whose `to_signable_string` returns the unchanged `raw_body` [5](#0-4) .
6. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body-derived signature [6](#0-5) .
7. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: "shop/update", shop: "victim.myshopify.com", body: <attacker's JSON>, ...)` [4](#0-3) , and the app processes attacker-controlled data as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
