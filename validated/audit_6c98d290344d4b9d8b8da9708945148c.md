Webhook `shop` tenant identifier is not covered by the HMAC signature, enabling cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable representation from the raw body only, while the `shop` value handed to webhook handlers as the tenant identity comes from an HTTP header that the signature never covers. Since a single app's `api_secret_key` is shared across every merchant shop that installs it, a valid `(body, hmac)` pair captured from one shop's own genuine webhook can be re-sent with a different `shop-domain` header and will still pass HMAC validation, letting an attacker cause the registry/handler to attribute the payload to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` unchanged into `WebhookMetadata`, which the handler treats as the identity of the tenant the event belongs to: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares only against `verifiable_query.hmac` — it has no knowledge of, and does not bind, the `shop` field at all: [5](#0-4) 

The broken binding, stated as an equality that should hold but does not:
`HMAC-authenticated bytes == bytes actually used to select the tenant (shop)`.
Before the attack: legitimate webhook `(body_A, hmac_A, shop=A)` is valid and processed as belonging to shop A. After the attacker's request sequence: the attacker (who is a legitimate merchant of the app, and thus receives real webhooks addressed to their own installation on shop A) replays `(body_A, hmac_A)` unchanged but sets the `shop-domain` header to `shop=B` (a victim shop that also installed the app, sharing the same `api_secret_key`). `HmacValidator.validate` still succeeds because it only checks `body_A` against `hmac_A`; `Registry.process` then dispatches `WebhookMetadata.new(..., shop: "B", body: body_A, ...)` to the handler, which believes the event genuinely originated from shop B.

This is a concrete instance of "a field acted on but not covered by the HMAC" from the prompt's list of allowed analog classes, directly reachable through this gem's own `Webhooks::Request`/`Registry` code, not dependent on the host application ignoring documented behavior — the gem's own `to_signable_string` implementation is what excludes `shop` from the signed payload.

### Impact Explanation
This breaks the tenant-authentication boundary between shops that use the same app installation: an attacker-controlled shop can force the app to process webhook data (and take the corresponding actions — e.g., inventory updates, order fulfillment triggers, GDPR/redact-topic handling, or any custom handler logic keyed on `data.shop`) under the identity of a different, victim shop. Depending on what the host application's `WebhookHandler#handle` implementations do with `data.shop` (e.g., look up per-shop credentials/records and mutate them), this can lead to cross-tenant data corruption or cross-tenant action injection — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to operate their own legitimate installation of the target app on some shop (to obtain a genuinely-signed `(body, hmac)` pair from real Shopify webhook traffic to their own endpoint), then replay that pair to the same app's public webhook endpoint with a forged `shop-domain` header. No possession of `api_secret_key`, access tokens, or other privileged material is required — only the ability to receive webhooks as a normal merchant and re-POST an HTTP request, which is within reach of an "unprivileged internet user" who can install the app on a shop they control. This does not require intercepting or tampering with the victim's traffic.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values as part of the signed material considered during validation, or otherwise independently verify that the shop domain in the header belongs to a shop this app instance expects/has installed, before dispatching to handlers. At minimum, `Request#to_signable_string`/`HmacValidator` should bind the shop identity to the signature check so that a payload signed for one shop cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: `raw_body = '{"id":1}'`, header `x-shopify-hmac-sha256 = HMAC(raw_body, api_secret_key)` (base64), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` still matches `raw_body` (per `to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-31`) since only body bytes are checked.
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` and calls the app's handler, which now performs its logic believing the event is authentically for `victim-shop.myshopify.com`.
