### Title
Cached wallet passphrase absolute-expiration cap (`maxTtl`) can be bypassed indefinitely via repeated `restartAutoLockTimer` calls - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache` caches the wallet's decryption passphrase in `sessionStorage` so the wallet can auto-unlock [1](#0-0) . It is configured with a `maxTtl` intended to bound the maximum lifetime of the cached secret [2](#0-1) . However, the expiration check in `get()` only enforces `addedAt + maxTtl` when `inactiveAt` has never been recorded; once any call updates `inactiveAt` (via `scheduleClear()`/`restartAutoLockTimer()`), the check switches permanently to a sliding `inactiveAt + ttl` window and the absolute `maxTtl` cap is never re-applied [3](#0-2) .

### Finding Description
This is structurally identical to the reported Union bug class: a security-relevant time boundary (here, the absolute passphrase-cache TTL cap `maxTtl`) is only checked against a *staker/user-controlled, resettable* "last activity" timestamp, so repeatedly invoking the reset action before the sliding window elapses keeps the record "fresh" forever and the hard cap is never reached.

- `set(passphrase)` records `ADDED_AT_KEY = Date.now()` once, when the passphrase is first cached [4](#0-3) .
- `scheduleClear()` (invoked from `Application#restartAutoLockTimer`, exposed publicly as `exodus.application.restartAutoLockTimer()` [5](#0-4)  and in the SDK API surface [6](#0-5) ) sets `INACTIVE_AT_KEY = Date.now()` every time it is called, and (re)schedules a `clear-passphrase` alarm for `ttl` minutes later [7](#0-6) .
- `get()`'s expiry logic:
  ```
  if (inactiveAt) {
    if (inactiveAt + ttl > Date.now()) return passphrase   // sliding window
  } else if (addedAt + maxTtl > Date.now()) {
    return passphrase                                       // absolute cap, only used pre-activity
  }
  ``` [8](#0-7) 

Once `inactiveAt` is non-null (which happens the very first time `restartAutoLockTimer` is called), `addedAt`/`maxTtl` are never consulted again for the rest of that cached passphrase's lifetime. As long as `restartAutoLockTimer()` is invoked at least once every `ttl` interval, `inactiveAt + ttl > Date.now()` remains true indefinitely, and the plaintext passphrase stays resident in `sessionStorage` far beyond the configured `passphraseCacheMaxTtl` — with no re-imposed hard limit, mirroring how `withdrawRewards()` calls before `overdueBlocks` elapses keep `repayDiff` under the threshold and permanently suppress the `frozenCoinAge` penalty in the Union report.

`changeTtl()` only clamps the *value* of `ttl` to `maxTtl` (`Math.min(this.#maxTtl, ttl)`) [9](#0-8) ; it does not limit how long the cache entry as a whole can be kept alive by repeated resets of `inactiveAt`.

### Impact Explanation
The passphrase is the secret used to decrypt the wallet's seed/keychain (`wallet.unlock({ passphrase })` [10](#0-9) ). `maxTtl` is the operator/product-configured hard ceiling meant to force periodic passphrase re-entry as defense-in-depth for a compromised or long-lived session/process (e.g. `passphraseCacheMaxTtl` config [11](#0-10) ). Because that ceiling is silently disabled after the first activity-based reset, an attacker who can trigger `restartAutoLockTimer` calls (e.g. via a malicious/compromised page or extension surface that calls the exposed `application.restartAutoLockTimer` API, or via routine background "keep-alive" polling in the host app) can keep the decrypting secret cached in storage indefinitely, well past its intended absolute expiry, increasing the exposure window for secret disclosure/auto-unlock if that storage is later read by another process or extracted from disk/session state.

### Likelihood Explanation
`restartAutoLockTimer` is a first-class, documented public API (`exodus.application.restartAutoLockTimer()` [12](#0-11) , `ApplicationWalletApi.restartAutoLockTimer` [13](#0-12) ), callable by any UI/consumer code without additional authorization beyond having access to the SDK surface (same trust level as the "any staker" precondition in the source report). No special privileges, timing races, or edge conditions are required — merely calling it more frequently than the configured `ttl` (e.g. driven by normal UI activity events or a scripted loop) keeps the cache alive forever, so the bypass is trivially and reliably reproducible.

### Recommendation
Track and enforce a true lifetime cap independent of activity resets: retain `addedAt` as the anchor for an absolute deadline (`addedAt + maxTtl`) and always require `Date.now() < addedAt + maxTtl` in `get()` **in addition to** the sliding `inactiveAt + ttl` check, rather than only falling back to it when `inactiveAt` is unset. Equivalently, clear/re-prompt for the passphrase once `Date.now() - addedAt > maxTtl`, regardless of how recently `scheduleClear()`/`restartAutoLockTimer()` was called, mirroring the report's recommendation to use lifetime/inception-based accumulators instead of resettable "last action" checkpoints for security-critical thresholds.

### Proof of Concept
1. Configure the SDK with `cachePassphrase: true` and a `passphraseCacheMaxTtl` (e.g. 60 minutes) [14](#0-13) .
2. Unlock the wallet with a passphrase, which caches it via `passphraseCache.set(passphrase)` (`addedAt = t0`) [4](#0-3) .
3. Every interval shorter than the current `ttl` (default `autoLockTimerAtom` value, e.g. 60m, or whatever the app sets via `changeLockTimer`), call `exodus.application.restartAutoLockTimer()`, which sets `inactiveAt = Date.now()` each time [7](#0-6) .
4. After `t0 + maxTtl` has long passed, call `passphraseCache.get()` (indirectly via app auto-unlock flow `#autoUnlock` [10](#0-9) ). Because `inactiveAt` is set and `inactiveAt + ttl > Date.now()` continues to hold, the passphrase is returned and the wallet auto-unlocks — the `maxTtl` cap configured at step 1 is never enforced.
