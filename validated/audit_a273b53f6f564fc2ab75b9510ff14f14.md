Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing subdomain boundary check - ([File: core/services/gateway/network/httpserver.go])

## Summary
The Gateway's HTTP server CORS origin check (`isAllowedOrigin`) supports wildcard entries like `*.example.com`, but after stripping the `*.` prefix it performs a plain `strings.HasSuffix` comparison instead of verifying a `.` label boundary. As a result, any origin host that merely ends with the configured suffix (e.g. `evilexample.com`) is treated as an allowed subdomain of `example.com`, even though it is not.

## Finding Description
In `isAllowedOrigin`, the wildcard branch does:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [1](#0-0) 
`allowedHost[2:]` strips only the two characters `"*."`, leaving the bare domain without a leading dot. `strings.HasSuffix(originHost, allowedHost)` then matches any string suffix, not a hostname label boundary, so `evilexample.com` satisfies `HasSuffix("evilexample.com", "example.com")`. No other check (exact match, scheme, port) prevents this false-positive suffix match. This result gates `Access-Control-Allow-Origin` reflection in `handleRequest`:
```go
if s.isAllowedOrigin(origin) {
    w.Header().Set("Access-Control-Allow-Origin", origin)
    ...
}
``` [2](#0-1) 

## Impact Explanation
The Gateway HTTP server is the internet-facing entry point that forwards raw requests (including `Authorization: Bearer` tokens) to `ProcessRequest`. If an operator configures a wildcard CORS entry (e.g. `*.mycompany.com`) intending to trust genuine subdomains only, an attacker controlling a domain such as `evilmycompany.com` can have cross-origin browser requests to the Gateway accepted with `Access-Control-Allow-Origin` reflecting their origin — enabling credentialed cross-origin requests from an unintended domain against the Gateway API. This maps to the in-scope "gateway request impersonation / allowlist bypass" impact category.

## Likelihood Explanation
Exploitation requires only that the operator has configured a wildcard `CORSAllowedOrigins` entry, a documented supported feature — no privileged access or credential leakage is needed. An unprivileged remote attacker can register a domain sharing the configured suffix and issue requests with a spoofed `Origin` header directly to the Gateway, making this low-complexity and reachable from the internet-facing path.

## Recommendation
Fix the suffix comparison to require a proper subdomain boundary, e.g., reconstruct the comparison as `strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost` after stripping `*.`, or split `originHost` into labels and compare trailing labels exactly against `allowedHost`'s labels. Add a regression test asserting `evilexample.com` does NOT match `*.example.com`.

## Proof of Concept
1. Configure `CORSAllowedOrigins: ["https://*.example.com"]`.
2. Send a request to the Gateway HTTP endpoint with header `Origin: https://evilexample.com`.
3. `isAllowedOrigin` strips `"*."` leaving `"example.com"`, then evaluates `strings.HasSuffix("evilexample.com", "example.com")` → `true`.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evilexample.com`, incorrectly granting CORS trust to a non-subdomain origin.

This can be verified with a Go unit test calling `httpServer.isAllowedOrigin("https://evilexample.com")` against config `CORSAllowedOrigins: []string{"https://*.example.com"}` and asserting it currently (incorrectly) returns `true`.
