### Title
Webhook shop attribution is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](), [File: lib/shopify_api/webhooks/registry.rb]())

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching the webhook to the app's handler, but the only thing it actually authenticates is the raw request body via HMAC. The `shop` identity that the handler receives and acts on is read from an unauthenticated header and is never bound into the HMAC computation, so any holder of one valid (body, hmac) pair can relabel it as belonging to a different tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the request, then immediately trusts `request.shop` (and `request.topic`) as the tenant identity forwarded to the app's handler: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has installed the app — it is not per-shop. This is confirmed by the registry test setup, which computes the HMAC purely from the body and a shared secret: [4](#0-3) 

The library's own documentation reinforces the misleading trust boundary, stating that `Registry.process` "will verify the request did indeed come from Shopify," without qualifying that shop attribution itself is unauthenticated: [5](#0-4) 

**Identity binding broken (as an equality):** the gem implicitly assumes `hmac_valid(raw_body) == shop_header_is_authentic`, but the header carrying `shop` is disjoint from the bytes covered by the HMAC. An unprivileged internet user who is simply a merchant installing the app (no `api_secret_key`, no access token, no privileged account) legitimately receives real webhooks for their own shop, each with a valid `(raw_body, hmac)` pair computed under the shared app secret. That user can resend the identical `raw_body`/`hmac` pair to the app's shared webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `WebhookMetadata.new(shop: <victim-domain>, body: <attacker's own real payload>, ...)` to the app's handler as if the victim shop's store had produced that event.

### Impact Explanation
This constitutes cross-tenant access: an unprivileged installer of the app can make the host application attribute attacker-controlled webhook data to an arbitrary other tenant (shop) it does not control, without needing the app secret, an access token, or a privileged account — only their own genuine, previously-received webhook traffic. Depending on what the host app's webhook handler does with `data.shop` (e.g., writing state, provisioning, updating billing/inventory, revoking access, or driving business logic keyed by shop), this can corrupt or forge data belonging to another merchant's tenant, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app using this gem's `Webhooks::Registry`/`Webhooks::Request` as documented with a single shared HTTP endpoint (the common pattern shown in `docs/usage/webhooks.md`). No exotic capability is required: any user who can install the app (a normal, low-privilege action) automatically becomes able to receive one authentic `(raw_body, hmac)` pair and replay it with a modified `shop` header. The exploit requires no cryptographic secret knowledge, no MITM, and no leaked credentials — it purely exploits the gap between what the HMAC covers and what the code trusts.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise re-derive/confirm shop identity from data that is inside the signed payload. Concretely:
- Include the `shop` (and ideally `topic`/`webhook_id`) in the signable string used for verification, or cross-check `request.shop` against a shop value embedded in the verified JSON body when available.
- At minimum, document explicitly (and enforce in `Registry.process`) that `shop`/`topic` headers are unauthenticated metadata and that host apps must independently verify the `shop` belongs to a session/tenant they expect (e.g., by checking it against a known/installed-shop list) before trusting `WebhookMetadata#shop`.
- Consider per-shop webhook endpoints/secrets rather than a single shared app secret validating a shared endpoint, to remove the ability for one tenant's valid traffic to be replayed as another's.

### Proof of Concept
1. App uses the documented pattern: a single controller action processes all shops' webhooks:
```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
  end
end
```
2. Attacker installs the app for their own shop `attacker.myshopify.com` and subscribes to a topic (e.g., `orders/create`). Shopify delivers a legitimate webhook to the app's endpoint with:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw_body, using the app's shared client_secret>`
   - `raw_body: {"id": ..., "note": "attacker-controlled content"}`
3. Attacker captures this exact `raw_body` + `x-shopify-hmac-sha256` value.
4. Attacker (or a script under their control) sends a new HTTP request directly to the app's public webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds because it only hashes `raw_body` — verified via `HmacValidator.validate_signature` at `lib/shopify_api/utils/hmac_validator.rb:26-31`.
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's content>, ...)`, causing the host app to act as though the victim's store produced this webhook event.
