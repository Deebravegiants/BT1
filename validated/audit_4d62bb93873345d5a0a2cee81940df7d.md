### Title
POA Bridge `describeWithdrawal` reports the wrong withdrawal's status/txHash for batched withdrawals of the same asset - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` matches an on-chain withdrawal record to the caller's `withdrawalParams` using only `assetId`, ignoring the per-withdrawal `index`, `destinationAddress`, and `amount`. When a single NEAR transaction batches two or more withdrawals of the same token (fully supported by the SDK's batch withdrawal API), every index resolves to the *same* first-matching record from the POA API, so an integrator polling withdrawal completion per-index receives an identical status/txHash for withdrawals that are actually distinct, independent transfers.

### Finding Description
`findMatchingWithdrawal` explicitly matches by `assetId` only: [1](#0-0) 

and `describeWithdrawal` uses this matcher on the unsorted API response list, keyed only by `args.withdrawalParams.assetId`: [2](#0-1) 

The code comment on `findMatchingWithdrawal` acknowledges the limitation ("multiple withdrawals of the same token in a single transaction are not supported") but this is not enforced anywhere — the SDK's batch withdrawal path (`signAndSendWithdrawalIntent` / `processWithdrawal` accepting `WithdrawalParams[]`, and `createWithdrawalIdentifier` assigning a distinct `index` per withdrawal item) does not reject or deduplicate multiple withdrawals of the same `assetId` within one batch: [3](#0-2) 

Because `Array.prototype.find` returns the first array element satisfying the predicate, calling `describeWithdrawal` for withdrawal index 0 and withdrawal index 1 (same `assetId`, different `destinationAddress`/`amount`) both resolve to the *same* underlying POA API withdrawal record. The equality that should hold — "status/txHash reported for withdrawal identifier N equals the actual on-chain outcome of the transfer originated at index N" — is broken: both indices report the same `status`/`transfer_tx_hash`, regardless of which of the two transfers it actually belongs to.

### Impact Explanation
An integrator building on this SDK typically calls `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` per withdrawal index to decide when to mark each user's withdrawal as settled (e.g., to release custody, mark an order complete, or send a receipt/credit confirmation). If two withdrawals of the same token are batched:
- Both indices can be reported "completed" with the same `txHash`, even though only one transfer actually completed on-chain (the other may still be pending or may have failed).
- This is exactly the "status or hash misreport making an integrator credit or refund twice" pattern: an integrator could treat both withdrawals as finalized based on the first one's completion, potentially crediting/confirming a withdrawal that never actually landed on-chain, or reusing one destination's txHash as "proof" for an unrelated destination.

This qualifies as **High** severity per the rules ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires no privileged actor — any normal SDK user/integrator who batches two withdrawals of the same `assetId` via the POA bridge route (a supported, unprivileged usage pattern) triggers the bug. The likelihood is proportional to how often integrators batch same-asset withdrawals to multiple destinations in one transaction, which is a realistic use case (e.g., paying out multiple users the same token in one intent).

### Recommendation
Update `findMatchingWithdrawal` to disambiguate withdrawals sharing the same `assetId` by also matching on `destinationAddress` and `amount` (and consuming matched entries so they cannot be reused for a different index), or reject/queue-serialize batches containing duplicate `assetId` withdrawals until the POA bridge API supports returning enough data (e.g., a client-supplied correlation id) to uniquely bind each on-chain transfer back to its originating withdrawal index.

### Proof of Concept
1. Call `sdk.signAndSendWithdrawalIntent` with a batch of two `WithdrawalParams` for the same `assetId` (e.g., `nep141:usdc.omft.near`) but different `destinationAddress` values (e.g., Alice and Bob), routed through the POA bridge.
2. The resulting NEAR transaction produces two POA bridge withdrawal records for the same token.
3. Call `bridge.describeWithdrawal` for `index: 0` and `index: 1` using the two different `WithdrawalIdentifier`s.
4. `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) filters the POA API's `withdrawals` array using only `nep141:${w.data.near_token_id} === assetId`; since both identifiers share the same `assetId`, both calls return the identical first array entry — same `status` and same `transfer_tx_hash` — even though Alice's and Bob's transfers are distinct on-chain events with potentially different completion times/outcomes.

*Note: I was not able to fully trace whether `signAndSendWithdrawalIntent`/`processWithdrawal` performs any validation that would reject duplicate-`assetId` batches before reaching this code path (batch-mode validation logic in `sdk.ts` was only partially visible in the indexed context), so this should be verified directly in the repository before treating the PoC as fully confirmed.*

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
