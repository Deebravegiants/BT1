## Title
Webhook Signature Verification Does Not Cover the `shop`, `topic`, `webhook_id`, or `api_version` Headers, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `Registry.process` trusts the `shop`, `topic`, `webhook_id`, and `api_version` values that are parsed from unauthenticated HTTP headers. Because the HMAC only binds the body, an attacker who can obtain any one validly-signed webhook (e.g. by installing the app on a store they control) can replay that exact body with a forged `x-shopify-shop-domain` header pointing at a victim shop, and the gem will accept it as authentic.

### Finding Description
The equality that should hold is:

`bytes verified by HMAC == bytes the application acts on when tagging the event to a tenant`

`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

But `Registry.process` verifies that signable string and then uses `request.shop` and `request.topic` — which come straight from the `shopify-shop-domain`/`x-shopify-shop-domain` and `shopify-topic`/`x-shopify-topic` headers, never included in the signed bytes — to route and tag the event: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes the HMAC solely over `to_signable_string` (the body) and compares it to the `hmac-sha256` header value; it never incorporates `shop-domain`, `topic`, `webhook-id`, or `api-version`: [4](#0-3) 

Since the webhook HMAC secret is the app's single `client_secret`/`api_secret_key`, shared across every shop that installs the app, any shop that installs the app can trigger the delivery of a validly-signed webhook whose body is (to varying degrees) attacker-influenced (e.g. `orders/create`, `customers/data_request`, etc.). Because the signature never covers the `shop-domain` header, that header can be swapped for a different shop's domain after capture, and `Utils::HmacValidator.validate(request)` at `lib/shopify_api/webhooks/registry.rb:190` will still pass, since it only re-verifies the body.

### Impact Explanation
This breaks the tenant-isolation invariant that a webhook accepted by `Registry.process` truly originated from the shop it claims to be from. A host application's webhook handler (which receives `WebhookMetadata.new(topic:, shop:, body:, ...)`) will process attacker-supplied/attacker-timed data under a victim shop's identity — for example, triggering `customers/data_request` or `shop/redact` mandatory-compliance handlers, or injecting fabricated `orders/create`/`app/uninstalled` events, tagged as coming from a shop the attacker does not control. This is a cross-tenant confusion of exactly the kind called out as Critical/High in scope (cross-tenant access), achieved purely by an unprivileged installer of the same app replaying a header-modified but still-"validly-signed" webhook request.

### Likelihood Explanation
Exploitation requires only: (1) the attacker being able to install the target app on any shop they control (a normal, unprivileged action for any Shopify merchant/developer), (2) capturing one webhook delivery with a body they find useful, and (3) sending a crafted HTTP request to the app's webhook endpoint with the original body/HMAC but a forged `shop-domain` (and optionally `topic`) header. No access token, `client_secret`, or victim-shop credential is required. Likelihood is High relative to the guardrails in scope.

### Recommendation
Include `shop`, `topic`, and other trust-relevant headers in the signable bytes verified by the HMAC (or otherwise cryptographically bind them to the body, e.g. by requiring the application to independently look up/validate the shop against a known installed-shop list before trusting `request.shop`). At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated header values and must not be used to select tenant context without an additional binding check.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the shared `api_secret_key`), plus `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Capture this raw request.
3. Replay it to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` → `lib/shopify_api/utils/hmac_validator.rb:12-31` re-hashes only `@raw_body` (`B`) and compares to `H` — validation succeeds.
5. `Registry.process` then dispatches `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-influenced data as though it belongs to `victim-shop.myshopify.com`.
