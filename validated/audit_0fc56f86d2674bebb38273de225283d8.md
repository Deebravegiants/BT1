## Title
Fee-on-transfer tokens allow draining pool reserves during swaps and corrupting LP/PNL accounting — ([File: program/src/processor.rs])

### Summary
The AMM program supports pools created with arbitrary SPL token mints (`process_initialize2`) and performs no check that the coin/pc mint is a standard, non-fee-charging SPL token. All accounting for swaps, deposits, and PNL is computed using the *nominal* instruction-specified amount (`swap.amount_in`, `deposit.max_coin_amount`, etc.) rather than the amount actually received by the AMM vault after the SPL transfer completes. If a fee-on-transfer token is used as coin or pc mint, an attacker can drain real vault reserves.

### Finding Description
In `process_swap_base_in` (and the analogous `_v2`/`process_swap_base_out(_v2)` variants), the swap output is computed from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (read from the vaults' actual balances before the transfer) and the nominal `swap.amount_in` supplied in the instruction: [1](#0-0) 

After computing `swap_amount_out`, the program transfers the *nominal* `swap.amount_in` (or `swap_in_after_add_fee` for base-out) from the user to the AMM vault via `Invokers::token_transfer`, and then unconditionally pays out `swap_amount_out` from the opposite vault via `Invokers::token_transfer_with_authority`: [2](#0-1) 

If the coin/pc mint is a fee-on-transfer token, the vault actually receives less than `swap.amount_in` (the difference is burned/redirected by the token's transfer-fee logic), but the program still pays out the full `swap_amount_out` computed as if the entire nominal amount arrived. There is no post-transfer balance check (no `balance_before`/`balance_after` pattern), so the shortfall is never detected — it silently reduces the vault's real reserves relative to what the invariant assumes.

The same nominal-vs-actual mismatch exists in `process_deposit`: `deduct_coin_amount`/`deduct_pc_amount` are computed from the pre-transfer vault balances and used both to mint LP tokens and to update `target_orders.calc_pnl_x`/`calc_pnl_y` (the PNL/invariant tracking state), but the actual coin/pc credited to the vault after the fee-on-transfer deduction will be smaller: [3](#0-2) 

Because the AMM's `process_initialize2` does not restrict the coin/pc mint to standard non-fee tokens, any user can create a pool with a fee-on-transfer mint and then repeatedly swap into it, each time causing the pool to pay out full amounts against a vault that received less than expected.

### Impact Explanation
Repeated exploitation systematically drains real token reserves from the AMM vault while the program's internal accounting (`total_coin_without_take_pnl`/`total_pc_without_take_pnl`, `target_orders.calc_pnl_x/y`, `amm.lp_amount`) does not reflect the shortfall until the next vault-balance read, at which point the pool is already insolvent relative to LP claims. This is a concrete theft-of-funds vector against other LPs/swappers in the pool and can create unbacked LP value (deposits mint LP based on nominal, not actual, contributed amounts). This qualifies as Medium/High severity per the rules (concrete theft/insolvent pool accounting).

### Likelihood Explanation
Reachable by any unprivileged user via a single `Initialize2` (pool creation with attacker-chosen mint) followed by ordinary `SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2` or `Deposit` instructions — all of which are part of the four/five in-scope instructions and require no special privileges, just a pool using a fee-on-transfer mint.

### Recommendation
Compare the vault's SPL token balance before and after each `token_transfer` into an AMM vault and use the actual received delta (rather than the nominal instruction amount) for all downstream calculations: `swap_amount_out`, `deduct_coin_amount`/`deduct_pc_amount`, and PNL/invariant updates (`target_orders.calc_pnl_x/y`, `amm.lp_amount`). Alternatively, explicitly reject the initialization or reject transfers for mints with a transfer-fee extension (e.g., detect Token-2022 `TransferFeeConfig`) at `process_initialize2`.

### Proof of Concept
1. Attacker creates a new AMM pool via `Initialize2` using a fee-on-transfer SPL token as the coin (or pc) mint — nothing in `process_initialize2` checks for or rejects transfer-fee-bearing mints.
2. Attacker (or any user) calls `SwapBaseIn` supplying `amount_in = X` of the fee-on-transfer coin token.
3. The program computes `swap_amount_out` from `total_coin_without_take_pnl`/`total_pc_without_take_pnl` and the full nominal `X` [1](#0-0) .
4. `Invokers::token_transfer` sends `X` from the user, but the vault only receives `X - fee` due to the token's built-in transfer fee.
5. The program still transfers the full `swap_amount_out` (computed for full `X`) out of the pc vault to the user [4](#0-3) .
6. Repeating this swap drains the vault's real reserves faster than the program's internal invariant accounts for, eventually making LP withdrawals unable to be satisfied at the recorded ratio (insolvent pool).
