### Title
Missing Validation of `orb_relay_app_id` Before Use as Orb-Relay Destination Identity - (File: src/plans/mod.rs)

### Summary
The Linea `TokenBridge.initialize` bug stemmed from accepting `sourceChainId`/`targetChainId` without checking they are non-zero and distinct, allowing bridge messages to be mis-routed. `orb-core` has an analogous pattern in `orb_relay_announce_orb_id`: the orb-relay `Client` is constructed with `ORB_ID` as the source identity and the attacker/user-influenced `orb_relay_app_id` as the destination identity, with no check that `orb_relay_app_id` is non-empty or distinct from `ORB_ID` (or from other in-flight session identities) before it is used to route signup-session messages.

### Finding Description
`orb_relay_app_id` is taken from `UserData::orb_relay_app_id`, which is populated from the backend's `authenticated_app_data.orb_relay_app_id` [1](#0-0)  and is only checked against a self-consistent hash supplied via the user's own QR code, not against any orb-side allowlist or uniqueness constraint [2](#0-1) .

This value flows unvalidated into `orb_relay_announce_orb_id`, which is invoked directly from the signup flow when `self_serve` is enabled [3](#0-2) . Inside that function, the relay `Client` is constructed with the orb's own fixed `ORB_ID` as source and the untrusted `orb_relay_app_id` as destination, with no validation that it is non-empty, well-formed, or different from `ORB_ID`: [4](#0-3) 

The `Client`/relay layer itself uses these two identities purely as routing labels for the `RelayPayload` `Entity` `src`/`dst` fields, with no defense against them colliding or being degenerate: [5](#0-4) .

This mirrors the TokenBridge issue structurally: two identifiers that are supposed to represent two distinct endpoints of a message-routing channel (source chain / destination chain, or here source orb / destination app-session) are accepted and used without any check that they are non-empty and mutually distinct.

### Impact Explanation
If `orb_relay_app_id` is empty, malformed, or intentionally set to collide with the orb's own `ORB_ID` or with another active/legitimate app session identifier, the relay routing built on `src_id`/`dst_id` can be corrupted for that signup session. Because this identity governs which app session receives `AnnounceOrbId`, `SignupEnded`, `CaptureStarted`/`CaptureTriggerTimeout`, and biometric-capture-trigger messages during a self-serve signup [6](#0-5) , an unvalidated/colliding identity could let signup-session control/state messages be delivered to, or accepted from, the wrong app session, i.e., cross-signup state bleed for a self-serve signup flow.

### Likelihood Explanation
`orb_relay_app_id` originates from data the enrolling user's own app supplies as part of the "authenticated" user QR-code payload, and the only check performed orb-side is that the QR-code-embedded hash matches the app-supplied data — not that the `orb_relay_app_id` value itself is sane or unique [2](#0-1) . This makes the value effectively user-influenced input at signup time, reachable through the ordinary self-serve signup path without needing operator or hardware access.

### Recommendation
Validate `orb_relay_app_id` in `orb_relay_announce_orb_id` (or earlier, right after it is retrieved from `UserData`) to ensure it is non-empty and not equal to `ORB_ID`, and reject the signup/relay connection with an error (as is already done for the missing-ID case at `src/plans/mod.rs:527-531`) if validation fails, mirroring the recommended fix of checking non-zero and distinct source/destination identifiers before use.

### Proof of Concept
1. Complete the self-serve signup flow with a user QR-code whose `authenticated_app_data.orb_relay_app_id` is set to the orb's own `ORB_ID` value (attacker controls the app-side payload and its self-consistent hash, so the `verify()` check at `src/backend/user_status.rs:175` passes).
2. `do_signup` reaches `orb_relay_announce_orb_id` with this value and constructs `Client::new_as_orb(..., ORB_ID.to_string(), orb_relay_app_id)` where `orb_relay_app_id == ORB_ID` [7](#0-6) .
3. Because `src_id == dst_id`, the resulting `RelayPayload` `src`/`dst` `Entity` values are indistinguishable for this session, breaking the routing invariant the relay protocol relies on to keep signup sessions isolated.

async fn proceed_with_biometric_capture(orb: &mut Orb) -> Result<bool> {
    let Config {
        self_serve,
        self_serve_app_skip_capture_trigger,
        self_serve_app_capture_trigger_timeout,
        ..
    } = *orb.config.lock().await;
    if !self_serve || self_serve_app_skip_capture_trigger {
        // Biometric capture not gated by a user action. Continue.
        orb.ui.signup_start();
        return Ok(true);
    }

    let orb_relay = orb.orb_relay.as_mut().expect("orb_relay to exist");

    tracing::info!("Waiting for self-serve biometric-capture trigger...");
    if let Err(e) = orb_relay
        .wait_for_msg::<self_serve::app::v1::StartCapture>(self_serve_app_capture_trigger_timeout)
        .await
    {
        if let Err(e) = orb_relay.send(self_serve::orb::v1::CaptureTriggerTimeout {}).await {
            tracing::warn!("failed to send CaptureTriggerTimeout: {e}");
        };
        orb.ui.signup_fail(SignupFailReason::Timeout);
        tracing::warn!("Self-serve biometric-capture start was not triggered: {e}");
        return Ok(false);
    };

    tracing::info!("Self-serve biometric-capture start triggered");
    orb.ui.signup_start();

    tracing::info!("Self-serve: Informing orb-relay that biometric_capture has started");
    orb_relay
        .send(self_serve::orb::v1::CaptureStarted {})
        .await
        .inspect_err(|e| tracing::error!("Relay: Failed to CaptureStarted: {e}"))?;

    Ok(true)
}
