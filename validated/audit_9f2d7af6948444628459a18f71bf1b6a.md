### Title
Vetoing the latest EVM state-machine commitment resets the height pointer to a hardcoded `1` instead of the true previous height, allowing stale/lower-height consensus updates to bypass the monotonic ordering check - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` resets `_latestStateMachineHeight[stateMachineId]` to the magic constant `1` whenever the vetoed height was the latest one, rather than restoring it to the actual last-known-good height. This is the EVM-side analog of the "lack of sanity checks on record update" bug: a state mutation (fisherman veto) corrupts the persisted "latest height" record without validating it against the chain's real history, later allowing new/incoming records (consensus updates) to be accepted even though they are inconsistent with previously verified state.

### Finding Description
`storeStateMachineCommitment` blindly persists whatever height/commitment it's given and unconditionally sets `_latestStateMachineHeight` to that height: [2](#0-1) .

The only guard against accepting out-of-order or stale heights lives in the caller, `HandlerV2.handleConsensus`, which requires the new height to be strictly greater than the currently recorded `_latestStateMachineHeight` (and skips the check entirely when it is `0`): [3](#0-2) .

When a fisherman vetoes a commitment via `deleteStateMachineCommitment` → `deleteStateMachineCommitmentInternal`, and the vetoed height happens to be the currently recorded latest height, the code resets the pointer to the literal constant `1`: [4](#0-3) .

This is unlike the equivalent Substrate `pallet-ismp` logic, which tracks a real `PreviousStateMachineHeight` value and restores the pointer to that actual prior height on delete: [5](#0-4) , backed by dedicated storage [6](#0-5) .

On the EVM host there is no analogous "previous height" storage at all — `_latestStateMachineHeight` is the only height-tracking mapping in `EvmHost.sol` [7](#0-6) . So after a veto of the latest height (e.g. height 500, when the chain had previously and legitimately advanced from height 1 through 490 with many valid, still-stored commitments in between), the pointer collapses to `1`. Any subsequent consensus update whose intermediate height is merely `> 1` — for example height 2, or any stale/earlier height the consensus client is still willing to attest to (an old but cryptographically valid BEEFY/GRANDPA/SP1/BSC/Tendermint proof, replayed or resubmitted within the unstaking/challenge window) — now satisfies `HandlerV2`'s ordering check and gets written as a fresh "latest" `StateMachineUpdated` record, even though it is far behind the real chain history the host had already verified.

### Impact Explanation
This breaks the monotonicity guarantee that downstream relayers, fishermen and applications rely on. The `StateMachineUpdated` event (and the `latestStateMachineHeight` getter used by SDKs/relayers/monitors) can advance the "latest" pointer backward/inconsistently after a single veto, letting an attacker-controlled or merely lagging relayer insert an out-of-order state commitment as if it were current. Since request/response delivery in `HandlerV2.handlePostRequests` only gates on the challenge period elapsed for the specific proof height supplied (not on "latest height" consistency) [8](#0-7) , a stale commitment accepted through this hole can be used to satisfy MMR membership proofs against an overlay root that the protocol had effectively moved past, enabling forged/duplicate message delivery windows or reopening timing assumptions (challenge periods, timeouts) that later legitimate updates and fishermen no longer expect to be reachable. Because only the admin/handler can subsequently re-freeze or fix host state, and vetoes are a normal fisherman action (not requiring privileged access to trigger the harmful sequence — any relayer submitting the next consensus proof after a veto benefits), this matches the reported bug class's HIGH severity: an incorrect "last record" (the latest-height pointer) silently corrupts subsequent sanity checks.

### Likelihood Explanation
Triggering the corrupted state requires only: (1) the vetoed height to be the current latest (a routine, expected veto scenario for fishermen contesting a bad/forged commitment — this is the intended, permissionless veto path), and (2) a subsequent relayer to submit any consensus proof whose intermediate height is `>1`, which is trivially satisfied by almost any valid or stale proof still accepted by the underlying consensus client (BEEFY/SP1/BSC/Tendermint/GRANDPA verifiers do their own height checks against the opaque `_consensusState`, not against this per-state-machine pointer). No special privilege beyond "submit a consensus proof" (an unprivileged relayer action) is needed to exploit the corrupted pointer once it exists.

### Recommendation
Track the true previous verified height on the EVM host, mirroring the Substrate implementation: add a `_previousStateMachineHeight` mapping, populate it every time `storeStateMachineCommitment` advances `_latestStateMachineHeight`, and in `deleteStateMachineCommitmentInternal` restore `_latestStateMachineHeight` to that recorded previous value instead of the hardcoded `1`:
```solidity
if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
    _latestStateMachineHeight[height.stateMachineId] = _previousStateMachineHeight[height.stateMachineId];
}
```
Additionally, consider having `storeStateMachineCommitment` itself enforce the "new height > latest" invariant (rather than relying solely on the caller in `HandlerV2`), so any future or alternate caller path cannot re-introduce the same class of bug.

### Proof of Concept
1. Consensus proof #1 advances the state machine's `_latestStateMachineHeight` from `0` to `490` through many `storeStateMachineCommitment` calls (heights 1..490), each legitimately verified.
2. A subsequent (malicious or erroneous) consensus proof advances the pointer to `500`.
3. A fisherman correctly detects height `500`'s commitment is wrong and calls `deleteStateMachineCommitment` (`fisherman` path) → `deleteStateMachineCommitmentInternal`: since `500 == _latestStateMachineHeight`, the pointer resets to `1`, discarding the legitimately verified `490`.
4. Any relayer now submits a consensus proof (potentially a stale/old-but-still-verifiable proof, or a normal one) whose intermediate state includes height `5` (or any height `> 1`, `< 490`). `HandlerV2.handleConsensus`'s check `latestHeight != 0 && intermediate.height > latestHeight` passes (`1 != 0 && 5 > 1`), so `storeStateMachineCommitment` writes height `5` as the new "latest," emitting `StateMachineUpdated` for height `5` — moving the protocol's recorded latest height backward from where it legitimately stood before the attack, and reopening acceptance of out-of-order/stale state for that counterparty chain.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
