### Title
Withdrawal status misreported to the wrong destination when a NEAR transaction contains multiple withdrawals of the same asset - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`findMatchingWithdrawal` matches a POA Bridge withdrawal status entry using only `assetId`, ignoring the caller-supplied `index`, `destinationAddress`, and `amount` that are actually part of the `WithdrawalIdentifier`. When a single NEAR transaction produces two or more `ft_withdraw` intents for the same token (e.g., a batch withdrawal to two different addresses), `describeWithdrawal` for every index resolves to the same first-matching API entry, breaking the equality "the withdrawal reported as completed for identifier X is the withdrawal that was actually authorised for X."

### Finding Description
`describeWithdrawal` calls `getWithdrawalStatusWithRetry` to fetch all withdrawals tied to the NEAR tx hash, then calls: [1](#0-0) 

The matcher only compares `near_token_id`: [2](#0-1) 

The comment explicitly acknowledges: "multiple withdrawals of the same token in a single transaction are not supported" — but `createWithdrawalIdentifier` and the SDK's batch flow (`createWithdrawalIdentifiers` in `withdrawal-watcher.ts`) do not prevent or reject this scenario; they happily assign distinct `index` values per bridge/route while `describeWithdrawal` silently drops that `index` when resolving status: [3](#0-2) [4](#0-3) 

Since `Array.prototype.find` always returns the first match, when the same token is withdrawn twice to two different `destinationAddress`es in one NEAR transaction, both `describeWithdrawal` calls (one per withdrawal identifier/index) return the identical entry — same `status`, same `transfer_tx_hash` — even though only one of the two withdrawals has actually completed to its correct destination.

### Impact Explanation
This breaks the equality between "reported withdrawal status/hash" and "the actual on-chain outcome for that specific withdrawal." An integrator or the SDK's `watchWithdrawal`/`waitForWithdrawalCompletion` consumer polling both identifiers would see index 1 reported `"completed"` with a `txHash` that in reality belongs to the destination of index 0. This can cause an integrator to credit/settle the second withdrawal as fulfilled (double credit / incorrect reconciliation) or to have surface a wrong hash to a user awaiting confirmation for their own recipient address — matching the "High" impact bucket ("a status or hash misreport making an integrator credit or refund twice").

### Likelihood Explanation
This requires the SDK caller (or an integrator building on it) to submit a NEAR transaction with two `ft_withdraw` withdrawals of the same asset routed via the POA bridge in one call — no malicious relayer/bridge/RPC behavior needed, just an unprivileged multi-withdrawal batch that the SDK's own APIs (`createWithdrawalIntents`, `waitForWithdrawalCompletion` accepting arrays of `WithdrawalParams`) permit constructing. The bug is deterministic once such a batch is submitted (not a race condition), so likelihood is moderate: it depends on whether the caller batches identical-asset withdrawals, which the code does not prevent or warn against at call time (only documented in an internal comment).

### Recommendation
Reject or explicitly detect (and fail closed to `"pending"`/error) batches containing multiple withdrawals of the same `assetId` in a single NEAR transaction until the POA API and `findMatchingWithdrawal` can disambiguate by `destinationAddress`/amount ordering (as the code comment suggests), or refuse to call `describeWithdrawal` per-index when duplicate assetIds are detected in `createWithdrawalIdentifiers`.

### Proof of Concept
1. Build a NEAR tx with two `ft_withdraw` intents for `nep141:usdc.omft.near`: one to address A, one to address B, both routed through POA bridge (`createWithdrawalIntents` called twice or a multi-withdrawal batch).
2. Submit the tx; POA API indexes two withdrawal records for that `tx_hash`, differing only in `address`/`transfer_tx_hash`.
3. Call `describeWithdrawal` for index 0 (destination A) and index 1 (destination B).
4. Both calls invoke `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")`, which returns the same first array entry (e.g., the one for destination A) for both index 0 and index 1.
5. If destination A's withdrawal completes first, index 1 (destined for B) is reported `"completed"` with A's `transfer_tx_hash`, even though B's withdrawal may still be pending or use a different hash. [1](#0-0) [5](#0-4)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

async function findBridgeForWithdrawal(
	bridges: Bridge[],
	params: WithdrawalParams,
): Promise<Bridge | undefined> {
	for (const bridge of bridges) {
		if (await bridge.supports(params)) {
			return bridge;
		}
	}
	return undefined;
}
