### Title
Index accrual can permanently freeze an oversized market when RAY-scaled debt exceeds `i128` - ([File: common/src/rates/scaling.rs])

### Summary
A market with sufficiently large scaled debt can reach a borrow index where `borrowed * borrow_index / RAY` no longer fits in `i128`. The next accrual panics before updating `last_timestamp`, after which every repayment, withdrawal, liquidation, and index update repeats the same panic and the market is permanently unusable. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` first converts the stored scaled debt into a RAY-denominated value by calling `scaled_to_original`. [3](#0-2) 

`scaled_to_original` delegates to `Ray::mul`, which computes `scaled * index / RAY` through `mul_div_half_up`. [4](#0-3) [5](#0-4) 

Although `mul_div_half_up` uses an exact `I256` intermediate, it still returns `None` when the final quotient cannot fit in `i128`, and the public wrapper converts that condition into `GenericError::MathOverflow`. [6](#0-5) 

Consequently, the global `MAX_BORROW_INDEX_RAY` does not protect the market: the actual ceiling is the smaller value for which the current scaled debt's RAY valuation remains representable. [7](#0-6) 

Every pool operation loads the market through `synced_market`, which invokes `global_sync` before applying the requested mutation. [8](#0-7) 

`global_sync` only stamps the market as accrued after all chunks complete, so a panic in the first valuation leaves `last_timestamp` unchanged and makes every later operation attempt the same overflowing calculation. [9](#0-8) 

The protocol's own integration test reproduces this condition with a billion-token, 18-decimal market at 98% utilization and confirms that withdrawal and repayment subsequently fail with `MathOverflow`. [10](#0-9) 

### Impact Explanation
This is a permanent freezing-of-funds condition rather than an ordinary failed transaction: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot liquidate positions because all those routes accrue the affected market first. [8](#0-7) 

The public `repay`, `withdraw`, and `liquidate` entrypoints all route through pool mutations that use the same synchronized-market path. [11](#0-10) 

The rate model also cannot be repaired through `update_params`, because `replace_rate_model` performs a synced accrual under the old model before writing the new parameters. [12](#0-11) 

### Likelihood Explanation
Triggering the condition requires an extremely large market, sufficient collateral to establish approximately 98% utilization, permissive configured caps, and enough elapsed time for the borrow index to reach the debt-specific RAY-value ceiling. [13](#0-12) 

Once those prerequisites exist, any unprivileged account can trigger the freeze by submitting `update_indexes` with the affected `HubAssetKey`; the controller calls the pool's `update_indexes`, which executes `global_sync` for the supplied market. [14](#0-13) [15](#0-14) 

### Recommendation
Derive a market-specific maximum index from the outstanding scaled balances so `scaled * index / RAY` always remains representable, and clamp index growth to that bound before accrual can cross it. 

Alternatively, add an explicit winding-down or accrual-freezing state that can be entered without first performing the overflowing accrual, while still allowing repayments, withdrawals, and liquidations to settle using the last committed indexes. 

Cap validation should account for future index growth and scaled debt valuation rather than only the representability of the initial token-to-RAY conversion. [16](#0-15) 

### Proof of Concept
The existing regression test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the sequence end to end:

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }

    assert_contract_error(failed, errors::MATH_OVERFLOW);

        "the index cap did not engage before the value overflow"

/// Returns the largest cap, in asset base units, whose ray-scaled form still
/// fits in `i128`.
///
/// Returns 0 when `asset_decimals > RAY_DECIMALS`, since the ray form is not
/// representable in that case. Enforced by
/// [`require_cap_within_asset_domain`], so stored caps can never overflow the
/// asset→ray rescale.
pub fn max_cap_for_decimals(asset_decimals: u32) -> i128 {
    let Some(exp) = RAY_DECIMALS.checked_sub(asset_decimals) else {
        return 0;
    };
    let upscale = 10i128
        .checked_pow(exp)
        .expect("10^(RAY_DECIMALS - asset_decimals) fits i128 for asset_decimals <= RAY_DECIMALS");
    i128::MAX / upscale
}

/// Panics with `CollateralError::AssetDecimalsTooHigh` if `asset_decimals`
/// exceeds `RAY_DECIMALS`, or with `CollateralError::InvalidBorrowParams` if
/// `cap` exceeds the value returned by `max_cap_for_decimals`.
pub fn require_cap_within_asset_domain(env: &Env, cap: i128, asset_decimals: u32) {
    if RAY_DECIMALS.checked_sub(asset_decimals).is_none() {
        panic_with_error!(env, CollateralError::AssetDecimalsTooHigh);
    }
    assert_with_error!(
        env,
        cap <= max_cap_for_decimals(asset_decimals),
        CollateralError::InvalidBorrowParams
    );
