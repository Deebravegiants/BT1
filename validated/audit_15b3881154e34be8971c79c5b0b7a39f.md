Audit Report

## Title
Unauthenticated exposure of LOOP-plugin debug/pprof and metrics endpoints, bypassing authentication enforced on equivalent node debug routes - (File: core/web/router.go, core/web/loop_registry.go)

## Summary
`loopRoutes` in `core/web/router.go` registers `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` on the top-level `api` router group, which carries only rate-limiting and session-cookie middleware and no `auth.Authenticate` call. This is inconsistent with the node's own equivalent debug routes (`/debug/vars` and `/v2/debug/pprof/*`), which are correctly gated behind session/token authentication.

## Finding Description
`NewRouter` builds an `api` group with only rate limiting and session-cookie middleware [8](#0-7) , then passes it unmodified into `debugRoutes`, `v2Routes`, and `loopRoutes` [1](#0-0) . `debugRoutes` wraps its own sub-group with `auth.Authenticate(..., auth.AuthenticateBySession)` before exposing `/debug/vars` [2](#0-1) , and `v2Routes` creates an `authv2` sub-group requiring token or session auth before exposing `/v2/debug/pprof/*` (via `metricRoutes`, though `metricRoutes` itself is defined but its call site inside the file was not located during review) [4](#0-3) . In contrast, `loopRoutes` registers its handlers directly on the passed-in `r` group with no additional `auth.Authenticate` wrapper [3](#0-2) . The handlers (`discoveryHandler`, `pluginMetricHandler`, `pluginPPROFHandler`, `pluginPPROFPOSTSymbolHandler`) proxy requests directly to the internal LOOP plugin's Prometheus and pprof HTTP endpoints and stream the response body back to the caller unfiltered [5](#0-4) [9](#0-8) , forwarding attacker-supplied `debug`/`gc`/`seconds` query parameters that also control request timeout [10](#0-9) . No existing middleware (rate limiter, session-cookie store) performs authentication, so this bypass is real and not mitigated elsewhere.

## Impact Explanation
An unauthenticated network client reaching the node's HTTP API port can: enumerate registered LOOP plugins and internal Prometheus scrape targets via `/discovery`; pull raw internal Prometheus metrics via `/plugins/:name/metrics`; and trigger heap/goroutine/cpu-profile/trace collection against the internal plugin process via `/plugins/:name/debug/pprof/*`, potentially leaking process memory/stack-trace contents and causing resource exhaustion through attacker-controlled profile durations. This is an in-scope confidentiality/availability impact stemming from a node API authentication inconsistency, directly comparable to the correctly-gated `/v2/debug/pprof/*` and `/debug/vars` routes.

## Likelihood Explanation
High. The routes are registered unconditionally with no auth middleware, feature flag, or role check, so any client capable of making HTTP requests to the node's web server port (default configuration, no privileged access needed) can reach them directly and repeatably.

## Recommendation
Wrap `loopRoutes` registrations in the same authentication requirement applied to the node's own debug/pprof routes, e.g. `r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession))`, ideally combined with `auth.RequiresAdminRole`, so `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` are not reachable without valid credentials.

## Proof of Concept
Against a running node with LOOP plugins registered:
```
GET http://<node>:<port>/discovery
→ 200, plugin names and internal scrape targets, no auth header/cookie required

GET http://<node>:<port>/plugins/<plugin-name>/metrics
→ 200, raw Prometheus metrics, no auth required

GET http://<node>:<port>/plugins/<plugin-name>/debug/pprof/heap
→ 200, pprof heap profile of internal plugin process, no auth required
```
Compare with the equivalent node-level route requiring auth:
```
GET http://<node>:<port>/v2/debug/pprof/heap
→ 401 Unauthorized
```
A Go integration test can be added to `core/web/router_test.go` (or equivalent) asserting that requests to `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` without an `Authorization` header or session cookie return 401/403 after the fix, confirming the current absence of such enforcement.

func pprofURLVals(gc *gin.Context) (urlVals url.Values, timeout time.Duration) {
	urlVals = make(url.Values)
	if db, ok := gc.GetQuery("debug"); ok {
		urlVals.Set("debug", db)
	}
	if gc, ok := gc.GetQuery("gc"); ok {
		urlVals.Set("gc", gc)
	}
	timeout = PPROFOverheadSeconds * time.Second
	if sec, ok := gc.GetQuery("seconds"); ok {
		urlVals.Set("seconds", sec)
		if i, err := strconv.Atoi(sec); err == nil {
			timeout = time.Duration(i+PPROFOverheadSeconds) * time.Second
		}
	}
	return urlVals, timeout
}

func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}
