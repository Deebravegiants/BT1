### Title
Deposit into a vault with `total-assets-preview() == u0` and `total-supply() > u0` mints zero shares while crediting full deposit to `assets`, transferring the depositor's principal to existing zft holders - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`socialize-debt` can drive `(var-get assets)` and `(var-get total-borrowed)` to exactly `u0` in the same call that zeroes `principal-scaled`, whenever the write-off covers the entire outstanding scaled principal and the vault has no idle reserves beyond what is borrowed. Because `socialize-debt` never touches the `zft` token supply, `total-supply-preview()` stays strictly positive for any surviving holders. In that state `convert-to-shares-preview` returns `u0` for any subsequent deposit, and `deposit` has no floor check rejecting a zero-share mint, so the depositor's real underlying tokens are added to `assets` and effectively donated pro-rata to existing `zft` holders.

### Finding Description
The broken identity: for `deposit` to fairly price shares, `convert-to-shares-preview(amount) = amount * ts / ta` must hold with `ta = total-assets-preview() > 0` whenever `ts = total-supply-preview() > 0`. The code instead special-cases `ta == u0` to return `u0`: [1](#0-0) 

`total-assets-preview` combines `(var-get assets)` with any unaccrued interest above `total-borrowed`: [2](#0-1) 

`socialize-debt` writes down `principal-scaled`, `total-borrowed`, and `assets` together, floored at `u0` independently, with no invariant tying them to the surviving `zft` supply: [3](#0-2) 

When `scaled-amount` equals the full `scaled-principal` (write off all debt) and `current-assets == borrowed` (fully utilized vault, no idle reserve), `principal-reduction` computes exactly to `borrowed`, so `total-borrowed` and `assets` are both set to `u0` while `principal-scaled` also goes to `u0`. `zft` balances of surviving holders are never burned, so `total-supply()` (and thus `total-supply-preview()`) remains `> u0`.

Root cause: `deposit` computes `inkind` via `convert-to-shares-preview` and only checks `(>= inkind min-out)`, never asserting `inkind > u0`: [4](#0-3) 

Note that `redeem`, by contrast, does enforce `(> inkind u0)` via `ERR-OUTPUT-ZERO`, but `deposit` has no equivalent guard: [5](#0-4) 

Exploit flow: an unprivileged caller (or naive user) calls `deposit(amount, u0, recipient)` after a legitimate `socialize-debt` writeoff has left `assets = 0`, `total-borrowed = 0`, `principal-scaled = 0`, while `total-supply() > 0` from surviving holders. `convert-to-shares-preview(amount)` returns `u0`. The `min-out` slippage check (`0 >= 0`) passes trivially because the caller supplied `min-out = u0`. `receive-underlying` pulls `amount` real underlying tokens from the caller into the vault, `ft-mint?` mints `u0` shares to `recipient`, and `assets` is set to `amount`. Every existing `zft` holder's `convert-to-assets-preview(balance)` claim increases from `0` to `(balance/ts)*amount` with no corresponding shares issued to the depositor - a direct, uncompensated transfer of the depositor's principal to existing holders.

### Impact Explanation
Per call, the depositor loses 100% of `amount` with zero shares received; the loss is fully absorbed by existing `zft` holders proportional to their balance. The bug is repeatable for every deposit made while the vault remains in the `ta == 0, ts > 0` state (until enough deposits/repay restore `ta > 0`). This is a direct loss of principal for whoever calls `deposit` unaware of the state (or is directed to do so), matching the Critical category ("direct theft of user funds at rest or in motion").

### Likelihood Explanation
Preconditions require a prior `socialize-debt` writeoff that fully clears `principal-scaled`/`total-borrowed` while the vault held no idle underlying beyond what was borrowed (100% utilization) - a plausible operational state for a lending vault absorbing bad debt, reachable via the DAO/authorized-caller `socialize-debt` path which is a normal (not attacker-privileged) protocol operation. Once that state occurs, exploitation costs nothing beyond calling a public function with `min-out = u0`, which is the default naive usage pattern; no special capital or timing is required, and it is trivially repeatable by any caller until the state is resolved.

### Recommendation
In `deposit`, explicitly reject zero-share mints, e.g. `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`, mirroring the guard already present in `redeem`. Additionally, consider preventing `total-assets-preview()` from reaching `u0` while `total-supply-preview()` remains positive (e.g., pause deposits or require a re-seeding mechanism when `ta == 0 && ts > 0`).

### Proof of Concept
Clarinet/vitest simnet plan:
1. Initialize vault, deposit from two real users A and B so `total-supply() = S_A + S_B + MINIMUM_LIQUIDITY`.
2. Borrow the full idle liquidity so `assets == total-borrowed` (100% utilization).
3. Call `socialize-debt` with `scaled-amount` equal to the full `principal-scaled`, driving `assets`, `total-borrowed`, `principal-scaled` all to `u0`; assert `(get-total-assets)` returns `u0` and `(get-total-supply)` still returns `S_A + S_B + MINIMUM_LIQUIDITY > u0`.
4. Record `convert-to-assets-preview(balance-of A)` (expect `u0` from the writeoff).
5. Call `deposit(amount, u0, attacker)` from a fresh principal; assert the return value (`inkind`) `== u0`.
6. Assert `(get-assets)` increased by exactly `amount`.
7. Assert `convert-to-assets-preview(balance-of A)` increased from `u0` to `(balance-of A / total-supply) * amount`, proving A's (and B's) claim grew by the attacker's/depositor's donated `amount` with no shares issued to the depositor.
