### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from raw HTTP headers, but its `to_signable_string` — used for HMAC verification — only covers the raw request body. `Registry.process` trusts `request.shop` after validating only the body's HMAC, so the shop-tenant binding is not authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` gates on this HMAC check, then immediately dispatches the handler using `request.shop`, `request.topic`, etc., taken from the unauthenticated headers: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" bug class: the equality the code needs to guarantee is `hmac == HMAC(secret, body || shop || topic)`, but the gem instead only proves `hmac == HMAC(secret, body)` while treating the accompanying `shop` header as trusted. An attacker who can capture or replay one legitimately-signed webhook delivery (e.g., via a request that transits shared infrastructure, logging, browser devtools on a merchant-controlled shop, or any MITM-adjacent vantage point that doesn't require TLS interception of Shopify's own delivery — simply resending the exact same body+HMAC to the app's own webhook endpoint with a modified `X-Shopify-Shop-Domain` header) can make the identical body+HMAC pair appear to originate from a different shop.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to determine which merchant's session/store to update (the intended and documented use, since `Registry.process` passes `shop: request.shop` into the handler), a forged `shop-domain` header lets an attacker apply another shop's legitimately-signed webhook payload against an arbitrary tenant context recognized by the app. This is a cross-tenant identity-binding break consistent with the Critical impact class (cross-tenant access) called out in the rules, since the shop field — the multi-tenant boundary for this library — is verified independently of the payload it is coupled with.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(raw_body, hmac)` pair for some shop (a normal, expected artifact of operating a merchant-facing endpoint — e.g. captured from their own store's webhook traffic, which any merchant using the app can generate for themselves) and the ability to POST to the app's public webhook endpoint with a different `shop-domain` header value. No `api_secret_key`, access token, or privileged credentials are needed, only unprivileged access to a merchant's own webhook deliveries plus network access to the app's public endpoint.

### Recommendation
Bind the `shop` (and `topic`/`api_version`/`webhook_id` if they influence handler dispatch) into the signed material, or independently verify the shop-domain header against a value already bound to the authenticated body (e.g., embed shop/topic inside the JSON body and compare it to the header before trusting the header), so that `HmacValidator.validate` cannot pass while the shop identity is forged.

### Proof of Concept
1. Attacker owns/operates `attacker-shop.myshopify.com` and receives a legitimate webhook delivery to the app's endpoint: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(secret, B)`), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `B` and `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H})` builds successfully.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — matches `H` regardless of the shop header — and passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, so the host application processes attacker-controlled data under the victim shop's tenant context.

          received_signature = verifiable_query.hmac
