### Title
Relayer fee withdrawal permits an unvalidated zero-address beneficiary, permanently burning accrued fees - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`Pallet::withdraw` in `pallet-ismp-relayer` never validates that the caller-supplied `beneficiary` is non-zero before zeroing the relayer's accrued `Fees` balance and dispatching the payout request to the destination chain. This is the same bug class as Celo's `setPaymentDelegation`: an actor can point a payment at the zero address, the destination-side transfer/mint reverts, and the funds are lost because the source-side accounting was already finalized optimistically.

### Finding Description
`WithdrawalInputData::beneficiary` is an arbitrary `Option<Vec<u8>>` chosen by the withdrawing relayer and is only checked for a valid *signature*, never for being a non-zero address: [1](#0-0) 

In `withdraw`, this value is used directly as `beneficiary_address` with no zero-check, and is embedded into the substrate `WithdrawalRequest` account or the EVM `WithdrawalParams.beneficiary_address`: [2](#0-1) 

Critically, the pallet dispatches the cross-chain payout request and **immediately zeroes `Fees`** and bumps `Nonce`, before any confirmation that the destination chain actually settled the payout: [3](#0-2) 

If `beneficiary_address` resolves to the zero address (`0x00...00` for EVM, or the all-zero `AccountId32` for substrate), the destination-side settlement — an ERC20-style mint/transfer to the zero address on the EVM `HostManager`, or an account credit on the substrate `HYPERBRIDGE_MODULE_ID` handler — will either revert (mint-to-zero reverts under standard token semantics) or silently vanish into an unspendable account. Either way, the relayer's fee is unrecoverable: the source-side `Fees` entry was already zeroed and the nonce already incremented, so there is no retry path and no fallback to the original relayer address. This mirrors the Celo `Accounts.setPaymentDelegation` flaw precisely: a validator-set (here, a relayer-set) zero beneficiary combined with a non-zero payment amount causes the payout to be irrecoverably lost when the mint/transfer step reverts or is swallowed. The same unvalidated-beneficiary pattern also exists in the beneficiary redirect path used during fee accumulation, where `beneficiary_address` from `withdrawal_proof.beneficiary_details` is credited into `Fees` with no zero-address check: [4](#0-3) 

### Impact Explanation
Any relayer who withdraws with a zero (or malformed-to-zero) beneficiary — whether by client bug, malicious front-end, or an adversary who can influence the beneficiary field of another relayer's flow — causes deterministic, permanent loss of the relayer's entire accrued fee balance for that chain. This is a direct loss-of-funds bug reachable by any permissionless relayer through a single signed withdrawal call, satisfying the "concrete... permanent freezing of funds" criterion.

### Likelihood Explanation
Likelihood is Medium: the beneficiary field is fully attacker/user-controlled with only a signature check, no address-format or non-zero validation exists on either the withdrawal or beneficiary-redirect path, and the accounting (`Fees` zeroing, `Nonce` increment) is committed unconditionally before dispatch, so a single malformed withdrawal transaction is sufficient to trigger the loss — no special privilege or race condition required.

### Recommendation
Add an explicit non-zero-address check on `withdrawal_data.beneficiary` (and on `beneficiary_details.0` in `accumulate`) before any state mutation, rejecting with a dedicated `Error::<T>::InvalidBeneficiary` (or `ZeroAddress`) prior to zeroing `Fees` or incrementing `Nonce`, analogous to disallowing a zero beneficiary in `setPaymentDelegation`/`deletePaymentDelegation`. Additionally, consider not finalizing (zeroing `Fees`/bumping `Nonce`) until destination-side delivery success is confirmed, or providing a recovery/refund mechanism for failed dispatches.

### Proof of Concept
1. Relayer accrues a non-zero balance in `Fees::<T>` for `StateMachine::Evm(dest)`.
2. Relayer calls `withdraw` with `WithdrawalInputData { beneficiary: Some(vec![0u8; 20]), .. }` and a valid signature over the corresponding `message(nonce, dest_chain, beneficiary)`. [5](#0-4) 
3. `Pallet::withdraw` accepts the zero beneficiary, builds `WithdrawalParams { beneficiary_address: [0u8;20], .. }`, dispatches the POST request, zeroes `Fees`, and increments `Nonce`. [6](#0-5) 
4. On the EVM destination, the `HostManager`'s fee-token mint/transfer to the zero-address beneficiary reverts (or is burned), so the relayer never receives the funds — and `Fees` on Hyperbridge is already zero, with no retry path.

Note: I was unable to fully inspect `evm/src/core/HostManager.sol`'s withdrawal-handling function within the available iterations to confirm whether it explicitly reverts or silently accepts a zero-address transfer; this should be verified directly in that file to confirm the exact failure mode (revert vs. silent loss) on the destination side.

	pub fn withdraw(withdrawal_data: WithdrawalInputData) -> DispatchResult {
		let address = match &withdrawal_data.signature {
			Signature::Evm { address, .. } => address.clone(),
			Signature::Sr25519 { public_key, .. } => public_key.clone(),
			Signature::Ed25519 { public_key, .. } => public_key.clone(),
		};

		let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
		let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());

		match &withdrawal_data.signature {
			Signature::Evm { address, .. } => {
				let eth_address = withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
				if &eth_address != address {
					Err(Error::<T>::InvalidPublicKey)?
				}
			},
			Signature::Sr25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
			Signature::Ed25519 { .. } => {
				// Verify signature with public key provided in signature enum
				withdrawal_data
					.signature
					.verify(&msg, None)
					.map_err(|_| Error::<T>::InvalidSignature)?;
			},
		};
		let available_amount = Fees::<T>::get(withdrawal_data.dest_chain, address.clone());

		if available_amount <
			Self::min_withdrawal_amount(withdrawal_data.dest_chain)
				.unwrap_or(MinWithdrawal::get())
		{
			Err(Error::<T>::NotEnoughBalance)?
		}

		let dispatcher = <T as Config>::IsmpHost::default();

		Nonce::<T>::try_mutate(address.clone(), withdrawal_data.dest_chain, |value| {
			*value += 1;
			Ok::<(), ()>(())
		})
		.map_err(|_| Error::<T>::ErrorCompletingCall)?;

		let beneficiary_address = withdrawal_data.beneficiary.clone().unwrap_or(address.clone());
		let (to, body) = match withdrawal_data.dest_chain {
			s if s.is_substrate() => (
				HYPERBRIDGE_MODULE_ID.to_vec(),
				Message::WithdrawRelayerFees(WithdrawalRequest {
					amount: available_amount.low_u128(),
					account: AccountId32::try_from(&beneficiary_address[..])
						.map_err(|_| Error::<T>::InvalidPublicKey)?,
				})
				.encode(),
			),
			_ => {
				let HostParam::EvmHostParam(params) =
					HostParams::<T>::get(withdrawal_data.dest_chain)
						.ok_or_else(|| Error::<T>::MissingMangerAddress)?;

				let body = WithdrawalParams {
					beneficiary_address: beneficiary_address.clone(),
					amount: available_amount.into(),
					token: params.fee_token,
				}
				.abi_encode()
				.map_err(|_| Error::<T>::InvalidPublicKey)?;

				(params.host_manager.0.to_vec(), body)
			},
		};

		let post = DispatchPost {
			dest: withdrawal_data.dest_chain,
			from: MODULE_ID.to_vec(),
			to,
			body,
			timeout: 0,
		};

		// Account is not useful in this case
		dispatcher
			.dispatch_request(
				DispatchRequest::Post(post),
				FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
			)
			.map_err(|_| Error::<T>::DispatchFailed)?;

		Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero());
