### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `Registry.process` verifies only the body's HMAC and then forwards the header-derived `shop` value to the app's webhook handler unchanged. This breaks the identity binding `hmac-covers(shop) == shop-used-for-tenant-routing`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e., the body — it never incorporates the `shop`, `topic`, or `webhook_id` fields into the signature check: [3](#0-2) 

`Registry.process` validates the HMAC and then hands the *header-derived* `request.shop` (never re-checked) straight to the app-provided handler as trusted tenant identity: [4](#0-3) 

Because the HMAC only signs the raw body, any request whose body+HMAC pair is valid (e.g., a genuine webhook the attacker legitimately received for their **own** shop, since anyone can install a public app on a shop they control and trigger webhooks like `orders/create` or `app/uninstalled` for it) can be replayed to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. The signature check still passes (same secret, same body, same HMAC), but `WebhookMetadata#shop` now reports the attacker-chosen shop while the body content is whatever the attacker generated on their own shop.

The equality that should hold — `shop value verified by HMAC == shop value delivered to the handler` — does not hold: the HMAC verifies the byte-identity of the body, while the code trusts a separate, unauthenticated header for the tenant identity used by every consuming app's `WebhookHandler#handle`.

### Impact Explanation
This is a cross-tenant identity confusion vector: an unprivileged internet user who can install the app on any shop (their own) can forge webhook deliveries that appear (per `WebhookMetadata#shop`) to originate from a different, victim shop, while fully controlling the body content of a legitimately-signed payload. Any app that keys per-tenant data mutation (order sync, product updates, GDPR redaction handling, uninstall cleanup, etc.) off `WebhookMetadata#shop` without independently re-validating that the shop is one it has an active session/installation for is exposed to cross-tenant data corruption — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) installing the target public app on an attacker-controlled shop to legitimately receive HMAC-signed webhooks, and (2) POSTing that captured body+HMAC to the app's public webhook endpoint with a rewritten `shop-domain` header. No access to `api_secret_key`, access tokens, or TLS interception is needed — the exploit is a direct, unauthenticated HTTP request to the app's own webhook route using gem-provided verification logic exactly as designed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is actually authenticated, or independently corroborate the header-derived `shop` against server-side state (e.g., confirm an active installation/session exists for that shop) before handing it to `WebhookHandler#handle`, rather than trusting it solely because the body's HMAC checked out.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Attacker POSTs to the app's public webhook route with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - body `B` (unchanged)
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` proceeds: [5](#0-4) 
4. The registered `WebhookHandler#handle` receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, even though `B` and `H` were both produced for `attacker-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
