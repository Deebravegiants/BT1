## Title
Webhook `shop`, `topic`, and `webhook_id` metadata is trusted from unauthenticated headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds only the raw request body into the HMAC-verified payload, while `shop`, `topic`, `webhook_id`, and `api_version` — all of which are acted on by the application (tenant routing, handler dispatch) — are read straight from HTTP headers and are never covered by the HMAC. This is the same bug class as the report: metadata that controls trust/behavior is appended alongside a signature but never cryptographically bound to it, so it can be altered without invalidating the signature.

### Finding Description
`Request#to_signable_string` (which `Utils::HmacValidator.validate` uses to recompute and compare the HMAC) returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from separate, unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then trusts `request.shop`, `request.topic`, and `request.webhook_id` (none of which were part of the verified bytes) to dispatch to a handler and build `WebhookMetadata`: [3](#0-2) 

The intended binding should be: `HMAC_verify(shop, topic, webhook_id, body) == (shop, topic, webhook_id, body)` used by the handler. The actual binding is `HMAC_verify(body) ≠ (shop, topic, webhook_id, body)` used by the handler — the shop/topic/webhook_id are unauthenticated metadata riding alongside a signature that only covers the body, exactly mirroring the `validUntil`/`validAfter` issue where validity metadata rode alongside a signature that didn't cover it.

### Impact Explanation
A holder of any one legitimately-signed webhook payload (e.g., an app-installing merchant, who is an "unprivileged" tenant relative to other merchants, legitimately receives real webhooks addressed to their own shop with a valid HMAC computed from the shared `api_secret_key`) can replay that same `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will pass the attacker-chosen `shop` value into the handler as `WebhookMetadata#shop`. Any host application that uses `WebhookMetadata#shop` to look up a tenant record, credentials, or trigger tenant-scoped side effects will act on the wrong shop's identity — a cross-tenant confusion driven entirely by unauthenticated header data that this gem hands to the handler as if it were verified.

### Likelihood Explanation
Reachable by any actor who can obtain one valid `(body, hmac)` pair for their own shop (trivial for any merchant with the app installed, since Shopify sends them real webhooks) and can POST to the app's public webhook endpoint — no `api_secret_key`, access token, or privileged account is required.

### Recommendation
Bind the trust-bearing metadata into the verified payload. Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically verify them against the delivery, e.g. by confirming `shop` against a known/allow-listed installed shop before dispatch), so that tampering with these headers invalidates the HMAC.

### Proof of Concept
1. Attacker (a merchant with the app installed on `attacker-shop.myshopify.com`) receives a legitimate webhook: body `{"id":1}` with header `x-shopify-hmac-sha256` computed by Shopify over that body using the app's `api_secret_key`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the identical body and HMAC header to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) recomputes the HMAC over `request.to_signable_string` (`= @raw_body`) and it matches — validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though that shop never sent this webhook and the HMAC never certified this shop value.
