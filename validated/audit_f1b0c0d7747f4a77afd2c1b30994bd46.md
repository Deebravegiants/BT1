### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` identity used by `Registry.process` to attribute the webhook to a tenant is read straight from an unauthenticated HTTP header. Any actor able to obtain one genuinely signed webhook for *any* shop on the app (e.g., their own store) can replay that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the signature check will still pass.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely outside that signed string: [2](#0-1) 

`Registry.process` validates the request via `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (i.e., `raw_body`) using the app's shared `api_secret_key`, and — once that passes — immediately forwards `request.shop` as the tenant identity into `WebhookMetadata`, handed to the app's handler: [3](#0-2) [4](#0-3) 

`api_secret_key` is a single, app-wide secret shared across every shop that has installed the app — it is not scoped per shop. Consequently, the HMAC only proves "this body/signature pair was produced by Shopify (or someone with the app secret) for this app," not "this body belongs to this particular shop." The binding that should hold is:
```
shop_bound_by_HMAC == shop_used_by_handler(request.shop)
```
but in reality `shop_used_by_handler` is taken from an attacker-controllable header that plays no part in `to_signable_string`, so the equality does not hold.

### Impact Explanation
Any party who can install the app on a shop they control (a normal, unprivileged trial/dev store) will receive genuinely-signed webhooks for that shop. By capturing one `(raw_body, hmac)` pair and replaying it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim's `*.myshopify.com` domain, the attacker gets `Registry.process` to construct a `WebhookMetadata` object that claims to be from the victim shop while the HMAC check still succeeds. Any handler logic keyed off `data.shop` (e.g., updating per-shop state, marking installation/uninstallation, processing mandatory `shop/redact`/`customers/redact` compliance topics, writing merchant-scoped records) will then act on the attacker's payload under the victim's tenant identity — a cross-tenant data-confusion / spoofing primitive.

### Likelihood Explanation
Exploitation only requires: (1) being able to install the target app on an attacker-owned store (typically free/self-serve), (2) capturing one legitimate webhook delivery for that store, and (3) replaying it with a modified header to the app's public webhook endpoint. No access to the app's `client_secret`, access tokens, or any victim credentials is required, making this reachable by any unprivileged internet user who can install the app.

### Recommendation
Do not trust the `shop` value taken from the webhook headers as an authenticated tenant identifier on its own. Either bind the shop domain into the signed payload comparison (e.g., cross-check `request.shop` against a shop the app has a known, previously-established session/installation for) or otherwise validate that the reported shop domain matches the shop context in which the webhook subscription was registered before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (self-serve, unprivileged).
2. Shopify sends a real webhook to the app's endpoint:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: shop/redact`
   - Body: `{"shop_id":..., "shop_domain":"attacker-shop.myshopify.com", ...}`
3. Attacker captures this exact raw body and `hmac` header value.
4. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only (`to_signable_string`) — it matches, since the body/hmac pair is unchanged.
6. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and calls the app's handler, which now processes attacker-supplied data believing it originates from `victim-shop.myshopify.com`. [3](#0-2)
