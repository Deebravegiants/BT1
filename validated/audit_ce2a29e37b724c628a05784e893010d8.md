## Finding

### Title
Unchecked ERC20 boolean return value in `IntentGatewayV2.withdraw` and dust-sweep handler leads to fund loss for non-reverting tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.sol` (Tron deployment) settles escrowed order funds and sweeps dust using a low-level `.call()` to the ERC20 `transfer` selector, but only checks the boolean `success` of the *call itself* — it never decodes and validates the token's returned boolean success flag.

### Finding Description
In `withdraw()` and in the `SweepDust` branch of `handle()`, token payouts are performed like this: [1](#0-0) 

and [2](#0-1) 

Both sites do `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount)); if (!success) revert TransferFailed();` without decoding `returndata` to confirm the token actually returned `true`. For ERC20 tokens that signal failure by returning `false` instead of reverting (e.g. 0x's ZRX token, or many older/non-compliant tokens), the low-level `call` succeeds (`success == true`) even though no tokens were moved. Despite this, `withdraw()` unconditionally decrements the internal escrow accounting `_orders[body.commitment][token] -= amount` (see line 710) and emits `EscrowReleased`/`EscrowRefunded`, marking the order as settled.

This differs from the rest of the contract, which correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom` for pulling funds into escrow (e.g. lines 405 and 459), but the payout path (`withdraw`) and the `SweepDust` handler bypass `SafeERC20` and use raw low-level calls that don't validate the return value.

### Impact Explanation
For any ERC20 asset traded through `IntentGatewayV2` that returns `false` on failed transfers rather than reverting, a beneficiary can be permanently denied their escrowed funds: the contract's internal accounting is decremented as if payment succeeded, while the token balance is never actually moved to the beneficiary. Depending on the failure condition (e.g. blacklist, paused token, insufficient dispatcher/contract balance edge cases), escrowed tokens become permanently stuck/unaccounted while the protocol believes the order was filled/refunded. This constitutes a permanent freezing/loss of user funds, satisfying a Medium/High severity impact for this analog since it is a fund-settlement path reachable by any relayer submitting a valid `RedeemEscrow`/`RefundEscrow`/`SweepDust` cross-chain message.

### Likelihood Explanation
The path is reached by any order withdrawal or dust sweep — a routine, permissionless-in-effect flow triggered whenever escrow is released/refunded via `handle()` (called by the ISMP host after a relayed cross-chain message) or via a `GET` response in `onGetResponse`. Any token integrated with the gateway that follows the "return false, don't revert" convention (a known category of real-world ERC20 tokens) will trigger this silently. No attacker action is even required — normal use of a non-reverting-on-failure token is enough.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` consistently (as already done elsewhere in the same contract, e.g. `safeTransferFrom` on lines 405/459) instead of raw `.call()` + `success`-only checks in `withdraw()` and the `SweepDust` handler. If a raw call must be kept for gas/ABI reasons, decode `returndata` and require it either empty or `abi.decode(returndata, (bool)) == true`, and additionally verify `token.code.length > 0` before trusting an empty-returndata success.

### Proof of Concept
1. Configure an order whose input/output token is an ERC20 implementation that returns `bool` `false` on transfer failure instead of reverting (ZRX-style token behavior).
2. Have the order escrow funds normally via `placeOrder` (uses `safeTransferFrom`, functions correctly).
3. Trigger a condition under which the token's `transfer` would fail post-escrow (e.g. token pausing, blacklist added to beneficiary, or any state causing the token's internal `transfer` logic to return `false`).
4. Relay a `RedeemEscrow`/`RefundEscrow` message to `handle()`, which calls `withdraw()`.
5. `token.call(...)` returns `success = true` (the call didn't revert, it just executed the token's internal logic that returns `false`), so `TransferFailed` is never raised.
6. `_orders[body.commitment][token] -= amount` executes, marking the escrow as released even though the beneficiary never received the tokens — the tokens are now stuck in the gateway with no accounting path to recover them.
