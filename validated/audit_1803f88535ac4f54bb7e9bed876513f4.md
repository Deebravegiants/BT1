Found the analog. In `EcdsaBeefy.verifyMmrUpdateProof` (and the equivalent Rust verifier `verify_mmr_update_proof`), the supermajority "participation threshold" check only enforces a **lower bound** (`sigLen >= 2/3*total + 1`) on the number of signatures — it never enforces an **upper bound** (`sigLen <= authoritySet.len`). The subsequent `ecrecover` loop iterates `sigLen` times, a value fully controlled by the caller through `relay.signedCommitment.votes`.

### Title
Unbounded attacker-controlled signature count in BEEFY commitment verification causes CPU/gas exhaustion - ([File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
`checkParticipationThreshold` in `EcdsaBeefy.sol` and `check_participation_threshold` in `modules/consensus/beefy/verifier/src/lib.rs` only check `len >= (2*total)/3 + 1`, with no upper bound tied to the actual authority-set size. [1](#0-0) [2](#0-1) 

### Finding Description
`verifyMmrUpdateProof` derives `sigLen` directly from the caller-supplied `relayProof.signedCommitment.votes.length`, checks only the lower-bound threshold, and then recovers a signer address via `ECDSA.recover` for every one of those `sigLen` entries before any membership/merkle check runs: [3](#0-2) 

The equivalent Rust verifier follows the same pattern — `signatures_length` is the attacker-supplied `mmr.signed_commitment.signatures.len()`, checked only against the lower-bound threshold, then every signature is `secp256k1_recover`-ed in a loop before the merkle membership proof is checked: [4](#0-3) 

Because `authoritySet.len` (the real authority-set size) is never compared against `sigLen` as an upper bound, an attacker can submit an arbitrarily large `votes`/`signatures` array (e.g. thousands of garbage or duplicated signatures for a small live authority set) that trivially satisfies the lower-bound participation check yet forces the verifier to perform `ecrecover`/`secp256k1_recover` on every entry — exactly the "cheap request forces expensive crypto work" pattern that CVE-2024-1975 describes for BIND's SIG(0)/KEY handling, where a single cheap message forces disproportionate CPU-bound cryptographic verification. This function is reachable by anyone submitting a consensus proof (e.g. via `pallet-beefy-consensus-proofs::submit_proof` or the equivalent `EvmHost`/`HandlerV2` consensus-update path calling into `IConsensusV2.verify`) — no privilege is required to submit a BEEFY consensus update.

Notably, sibling verifiers in this same codebase (sync-committee, BSC/Parlia, Pharos) explicitly cap participant bit counts at the real committee/validator-set size before counting them (`i >= committee_size`/`current_validators.len()` guards), and other paths in the repo are deliberately engineered to reject cheaply before doing expensive work (duplicate-key rejection before EVM storage-proof verification, allowlist rejection before state-proof verification, `StaleHeight` rejection before any crypto). The BEEFY ECDSA/Rust verifiers are the outlier that omit the analogous upper-bound/cap check. [5](#0-4) [6](#0-5) 

### Impact Explanation
Every BEEFY consensus-proof submission (EVM `EcdsaBeefy.verify` or the substrate `verify_consensus`) is a single unprivileged transaction/extrinsic. By padding the `votes`/`signatures` array with a large number of entries (bounded only by calldata/extrinsic size limits, which are typically megabytes, i.e. many thousands of 65-byte signatures), an attacker forces the EVM contract or the runtime's BEEFY consensus client to perform a proportionally large number of `ecrecover`/`secp256k1_recover` operations on every submitted proof. On EVM this inflates gas cost dramatically (potentially hitting block gas limits and reverting, denying legitimate consensus updates from landing), and in the substrate pallet path (which is unsigned/spam-protected but still executes this verification logic during dispatch or benchmarking-bounded weight) it can consume disproportionate CPU relative to the honestly-computed weight, since weight is normally benchmarked against the expected authority-set size, not an attacker-inflated one. This can degrade or freeze the relay chain's ability to deliver new consensus updates (a "route unable to deliver messages" condition) to Hyperbridge.

### Likelihood Explanation
High. No special conditions or privileges are needed — an attacker only needs to construct a signed-commitment payload whose signature count is large; the lower-bound supermajority check is trivially satisfiable by any live authority set, and nothing stops piling on far more entries than the set actually contains.

### Recommendation
Add an explicit upper-bound check `sigLen <= authoritySet.len` (and reject duplicate `authorityIndex`/`index` values) immediately after resolving the applicable authority set, both in `EcdsaBeefy.checkParticipationThreshold`/`verifyMmrUpdateProof` and in `check_participation_threshold`/`verify_mmr_update_proof`, mirroring the bound already enforced in the sync-committee and BSC/Parlia verifiers (`i >= committee_size` guards) before running the `ecrecover`/`secp256k1_recover` loops.

### Proof of Concept
1. Take a live BEEFY authority set of size `N` (e.g. `N = 100`).
2. Construct a `SignedCommitment` whose `votes`/`signatures` array contains `M >> N` entries (e.g. `M = 5000`), reusing arbitrary signature bytes and repeated/garbage `authorityIndex` values — as long as `M >= (2*N)/3 + 1`, which is trivially true for any `M > N`.
3. Submit this as a BEEFY consensus proof via `EcdsaBeefy.verify` (EVM) or `verify_consensus` (substrate `pallet-beefy-consensus-proofs`).
4. `checkParticipationThreshold(M, N)` / `check_participation_threshold(M, N)` passes because it only checks the lower bound.
5. The loop `for (uint256 i = 0; i < sigLen; i++) { ECDSA.recover(...) }` (or its Rust equivalent) executes `M` `ecrecover` operations before the merkle membership check (which would ultimately reject the bogus authorities) is ever reached — consuming gas/CPU proportional to `M`, not `N`.
