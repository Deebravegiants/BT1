### Title

Unrestricted route code can inject an unauthorized-looking token transfer into the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary

Controller strategy entrypoints accept opaque `swap` bytes and forward them to the configured router without validating the contracts that the route invokes. [1](#0-0)  Because router pool addresses are supplied through the payload rather than restricted to trusted venues, route-selected code can request authorization from the caller for an unrelated token transfer. [2](#0-1) [3](#0-2) 

### Finding Description

`swap_collateral(caller, account_id, current, amount, new, swap)` is reachable by an account owner or delegate and passes the caller-controlled `swap` bytes into `withdraw_and_swap_from_supply`. [4](#0-3) [5](#0-4) 

The swap helper snapshots the controller’s input and output balances, authorizes one exact controller-to-router input transfer, and invokes `SwapAggregatorClient::execute_strategy(&controller, &amount_in, swap)`. [6](#0-5)  This authorization is narrowly scoped for the controller’s own funds, but it does not restrict code reached by the route under the caller’s top-level authorization. [7](#0-6) 

A strategy payload contains an address registry and packed instructions whose swap instructions select a pool by registry index. [8](#0-7) [9](#0-8)  During execution, each swap resolves `pool`, `token_in`, and `token_out` from that registry and dispatches to the selected venue adapter. [2](#0-1)  The adapter boundary measures router balance deltas but does not isolate route-selected code from host authorization recording. [10](#0-9) 

An attacker can therefore provide a route whose venue contract implements the expected venue-facing behavior while also calling `token.transfer(victim, attacker, amount)` on any token held by the victim. [11](#0-10)  During simulation, that nested transfer is recorded as a child invocation of the victim’s `swap_collateral` authorization, and signing the simulated tree makes the transfer valid. [12](#0-11) 

The repository’s threat model explicitly confirms that there is no venue allowlist and that such a transfer executes when the caller signs the poisoned authorization tree. [13](#0-12) 

### Impact Explanation

This allows theft of user funds outside the lending position and outside the declared swap input. [14](#0-13) 

A malicious route can still return enough output to satisfy the router’s measured-output and minimum-output checks while the injected pool call steals an unrelated wallet asset. [15](#0-14)  Consequently, the controller’s `RouterOverspend`, `NoSwapOutput`, and final account-risk checks do not bound the victim’s wallet loss. [16](#0-15) [17](#0-16) 

The same route-processing helper is also reached by `multiply`, `swap_debt`, and `repay_debt_with_collateral`, so the exposure is not limited to `swap_collateral`. [18](#0-17) [19](#0-18) [20](#0-19) 

### Likelihood Explanation

Exploitation requires the victim to submit or sign a transaction containing a malicious route and a poisoned authorization tree, so this is not a purely self-contained attacker invocation. [21](#0-20)  However, no protocol privilege, leaked key, compromised router, or parameter-control role is needed: an unprivileged attacker can deploy the route-selected contract and distribute the crafted `swap` bytes. [22](#0-21) [2](#0-1) 

The injected authorization is mechanically generated by normal transaction simulation, which makes the attack practical where users sign route bytes or nested authorization trees they do not independently decode. [12](#0-11) 

### Recommendation

Restrict pool and venue addresses reachable through strategy payloads to governance-registered immutable venue contracts, rather than trusting arbitrary registry addresses. [23](#0-22) 

At the controller boundary, document or enforce a trusted route schema instead of treating all non-empty `swap` bytes as opaque router input. [24](#0-23)  In addition, wallets and SDK transaction builders should fail signing when the simulated authorization tree contains any invocation beyond the expected controller operation and its documented token pulls. [13](#0-12) 

### Proof of Concept

The test harness defines a router-compatible route whose pool address selects an attacker-controlled contract. [15](#0-14) 

The malicious pool stores a victim, unrelated wallet token, attacker recipient, and amount, then performs `token.transfer(victim, attacker, amount)` when invoked. [11](#0-10) 

The test constructs a `swap_collateral` call using 5,000 USDC collateral and a route through that rogue pool. [25](#0-24) 

In authorization-recording mode, the wallet-token transfer appears as a child invocation beneath the victim’s `swap_collateral` authorization. [12](#0-11) 

With an honest authorization tree the transfer is rejected and the swap rolls back, while signing the simulated poisoned tree transfers the victim’s entire 77,770-token wallet balance to the attacker. [26](#0-25)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
