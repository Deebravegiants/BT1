Found the analog vulnerability. The Tron variant of `IntentGatewayV2` uses raw low-level `.call()` with `IERC20.transfer.selector` and only checks the boolean `success` returned by `.call()` (i.e., whether the call didn't revert), but never decodes/validates the ABI-encoded `bool` return value that ERC20 `transfer` is supposed to return. This is the exact same bug class as the reported issue: an ERC20 token that returns `false` instead of reverting will make `token.call(...)` return `success = true` (the call executed, it just returned encoded `false`), so the `if (!success) revert TransferFailed();` guard never triggers, and the contract proceeds to decrement escrow and emit `EscrowReleased` as if funds were delivered, even though the beneficiary received nothing.

### Title
Unsafe raw `.call()` ERC20 transfers in `IntentGatewayV2.withdraw` skip return-value validation, allowing silent transfer failures with fund loss - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` imports and even declares `using SafeERC20 for IERC20;` [1](#0-0) , but the escrow-release path in `withdraw()` bypasses `SafeERC20` entirely and instead performs raw low-level calls to the `transfer` selector, checking only that the external call itself did not revert.

### Finding Description
In `withdraw()`, escrowed input tokens and transaction fees are released to the beneficiary/solver via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

This checks only whether the low-level `call` reverted, not the ABI-encoded boolean payload that a compliant ERC20 `transfer()` returns. Per the ERC20 standard, a token is permitted to return `false` on failure instead of reverting. In that case `token.call(...)` succeeds (`success == true`) with return data encoding `false`, so the `if (!success)` check never fires. The function then unconditionally decrements the escrow accounting (`_orders[body.commitment][token] -= amount;`) and, for finalizing withdrawals, marks the order `_filled[body.commitment] = beneficiary` and emits `EscrowReleased`, even though the beneficiary never actually received the tokens.

The identical unsafe pattern is repeated for:
- Escrowed input token release [3](#0-2) 
- Transaction-fee release to the beneficiary [4](#0-3) 
- Dust sweeping to the protocol beneficiary in `onAccept`'s `SweepDust` handling [5](#0-4) 

By contrast, the canonical EVM `IntentGatewayV2`/`IntentsBase` on the main `evm/src` tree correctly uses `IERC20(token).safeTransfer(beneficiary, amount);` which reverts on both a false return and a non-reverting no-op token [6](#0-5) , and even the same `placeOrder`/`withdraw` flow in the Tron file elsewhere correctly uses `safeTransferFrom` for inbound transfers [7](#0-6) . The `withdraw()` outbound path is the one place this safety property was dropped, despite the contract already importing `SafeERC20`.

### Impact Explanation
This is a real path reachable by any unprivileged relayer/solver flow: `withdraw()` is invoked either from `onAccept()` when a cross-chain `RedeemEscrow`/refund message is delivered, or from `onGetResponse()` on a GET-response driven refund. If the escrowed input token or the fee token behaves like a "return false on failure" ERC20 (e.g., due to a paused/blacklisted state, insufficient balance edge case, or a non-standard implementation), the beneficiary/solver receives no tokens, yet:
- Escrow accounting (`_orders[commitment][token]`) is decremented as if the transfer succeeded, permanently orphaning the tokens still held by the contract (funds effectively frozen — no code path re-attempts or refunds them once the order is marked filled).
- The order is marked filled/refunded and `EscrowReleased`/`EscrowRefunded` is emitted, misleading downstream integrations (indexers, solvers, users) into believing settlement occurred.

This causes concrete, permanent loss/freezing of escrowed user or solver funds without any admin/attacker action required — a standard token quirk under normal operating conditions is enough to trigger it.

### Likelihood Explanation
Likelihood is moderate-to-high for any deployment where the escrowed input token or the configured fee token is a non-standard ERC20 that can return `false` (rather than revert) on transfer failure — a documented and common real-world ERC20 pattern. Since `IntentGatewayV2` is designed to be generic and accept arbitrary tokens as `order.inputs`/`order.output.assets`, and Tron's own TRC20 ecosystem has a well-known history of non-standard token implementations, this condition is plausible in normal operation, not merely under an adversarial token.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee-token release) and in the `SweepDust` handler with `IERC20(token).safeTransfer(beneficiary, amount)`, using the `SafeERC20` library already imported and declared via `using SafeERC20 for IERC20;` in this contract. This ensures both a reverting failure and a `false`-returning failure abort the transaction atomically, before any escrow accounting or `EscrowReleased`/`EscrowRefunded` state is committed.

### Proof of Concept
1. Deploy (or use) an ERC20 token contract as `order.inputs[0].token` whose `transfer()` returns `false` on failure instead of reverting (a standard-compliant behavior; e.g., transfer to an address with insufficient allowance/balance edge cases handled internally, or a token intentionally emulating this well-known non-standard pattern).
2. A user calls `placeOrder()` escrowing this token; the contract holds the tokens (`_orders[commitment][token] = amount`).
3. Trigger the condition under which the token's `transfer()` returns `false` (e.g., the token is paused for the beneficiary, or a blacklist check fails silently) when `withdraw()` is later invoked via `onAccept()`'s `RedeemEscrow` handling.
4. Observe: `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` with encoded `false` payload; `if (!success)` does not revert; `_orders[body.commitment][token] -= amount` executes; `_filled[body.commitment] = beneficiary` is set; `EscrowReleased` is emitted.
5. Beneficiary's token balance is unchanged (transfer silently failed), while the contract's internal accounting and emitted events indicate the escrow was fully released — the tokens remain stuck in the contract with no remaining code path to reclaim them for that commitment.
