### Title
Unchecked ERC20 `transfer` return value in Tron `IntentGatewayV2.withdraw`/`SweepDust` causes silent-failure permanent freezing of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` uses a raw low-level `.call()` to move ERC20 tokens out of escrow in `withdraw()` and in the `SweepDust` branch of `onAccept`, and only checks that the call did not *revert* (`success`), never decoding/validating the boolean the ERC20 `transfer()` function is expected to return. This is the mirror-image of the reported bug class ("token approve/transfer required to return `true`, so non-boolean-returning tokens revert and get stuck"): here the code fails to enforce the boolean check at all, so any ERC20 whose `transfer()` returns `false` on failure instead of reverting will report `success = true` even though no tokens moved, while the contract has already permanently deleted/decremented the escrow accounting and marked the order filled/refunded.

### Finding Description
In `withdraw()`, escrowed tokens are released with: [1](#0-0) 
```
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```
and the fee redemption path does the same: [2](#0-1) 

The `SweepDust` handler in `onAccept` follows the identical unsafe pattern: [3](#0-2) 

`success` from a low-level `.call` only reflects whether the callee reverted; it does not reflect the ABI-encoded `bool` many ERC20 implementations return to signal transfer failure. Contracts that return `false` (rather than reverting) on a failed `transfer` — e.g. tokens with owner-blacklists, pausable transfer hooks that return `false`, or defensively-coded custom tokens — will make this call return `success = true` with `returndata` decoding to `false`. The check `if (!success) revert TransferFailed()` never fires, so execution proceeds as if the transfer succeeded.

Crucially, immediately after the unchecked transfer, the function mutates state assuming the transfer succeeded: it decrements `_orders[body.commitment][token]` in `withdraw()` and had already set `_filled[body.commitment] = beneficiary` before the loop, and `SweepDust` emits `DustSwept` unconditionally. Since these are the only code paths that release escrowed tokens for a given commitment (`RedeemEscrow`/`RefundEscrow` requests processed once via `onAccept`), once the accounting is updated the tokens can never be withdrawn again for that commitment — they remain permanently stuck in the `IntentGatewayV2` contract while the intended beneficiary receives nothing.

This is reachable by an ordinary, unprivileged flow: any user creating an intent order on the Tron gateway can choose an arbitrary ERC20 as the input token; once a solver fills the order and the cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered, this vulnerable code path executes non-interactively, driven purely by the relayed ISMP request — no admin or governance action is required to trigger the loss.

By contrast, the EVM-mainline `IntentGatewayV2.sol` (and other apps such as `WrappedHyperFungibleToken.sol`, `EvmHost.sol`) consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which correctly handles both "no return value" tokens (like USDT) and "returns false" tokens (reverting in the latter case), as shown for example at [4](#0-3)  and [5](#0-4) . The Tron fork diverges from this safe pattern specifically in `withdraw()`/`SweepDust`.

### Impact Explanation
This results in a concrete, permanent loss/freezing of user escrowed funds: the token balance stays locked in the `IntentGatewayV2` contract forever (no retry path exists once `_orders[...]` is decremented and `_filled` is set), while the intended beneficiary (the order's user on refund, or the filler on redemption) receives nothing. This meets the "permanent freezing of funds" bar required by the validation criteria.

### Likelihood Explanation
Likelihood depends on whether any ERC20 that can be configured as an intent input token on the Tron deployment returns `false` on failed transfers rather than reverting. This is a known real-world pattern for several deployed tokens (some blacklist-based stablecoin forks, some custom tokens with pausable/whitelisted transfer hooks). Because token selection for orders is user-controlled (any ERC20 address can be used as `order.inputs[i].token`), and the vulnerable code executes automatically on relayed `RedeemEscrow`/`RefundEscrow`/`SweepDust` messages with no privileged gating, the likelihood is non-trivial for any token with this failure mode, though it does not affect fully-standard ERC20s (e.g. plain OpenZeppelin tokens) that revert on failure.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust` branch of `onAccept` with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (the contract already imports and uses `SafeERC20` via `using SafeERC20 for IERC20;`). This correctly reverts on both non-reverting `false`-returning transfers and non-boolean-returning tokens, preventing state from being finalized when the underlying transfer did not actually happen.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer` function returns `false` (without reverting) when a transfer would fail, e.g. due to an internal blacklist flag set for the recipient — mirroring the pattern already used in this repo's own test mocks such as the fee-on-transfer mock at [6](#0-5)  (adapt `_transfer` to `return false` on a blacklist condition instead of always succeeding).
2. Create an intent order on the Tron `IntentGatewayV2` using this token as `order.inputs[0].token`, and have a solver fill it cross-chain, causing escrow of the token in the gateway.
3. Set the beneficiary address (or trigger the condition) so the mock token's `transfer` to the beneficiary returns `false`.
4. Relay the `RedeemEscrow` (or `RefundEscrow`) ISMP request to `onAccept`, which calls `withdraw()`.
5. Observe: `token.call(...)` returns `success = true` (no revert), `TransferFailed` is never raised, `_orders[commitment][token]` is decremented, `_filled[commitment]` is set — yet the beneficiary's token balance is unchanged and the gateway contract still holds the tokens with no remaining code path to release them.
