### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC against that body alone. The `shop` (from the `x-shopify-shop-domain` header) that `Registry.process` hands to the app's webhook handler is never part of the signed material, breaking the intended binding `hmac == HMAC(shared_secret, body + shop)`.

### Finding Description
`Registry.process` treats a request as authentic for a given shop purely because `Utils::HmacValidator.validate(request)` returns true: [1](#0-0) 

`HmacValidator.validate` recomputes the signature only over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is defined as just the raw body, while `shop` is read from a separate, unauthenticated header: [3](#0-2) 

Because the app-wide `Context.api_secret_key` (the app's single `client_secret`) is shared across *every* shop that has the app installed, any merchant who installs the app can legitimately receive a webhook whose `hmac-sha256` header validly signs a given body. That merchant can then replay the identical body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspects the shop header), and `Registry.process` forwards `request.shop` (now the victim's domain) straight into the handler via `WebhookMetadata`, so the equality `shop_header == shop_that_produced_this_HMAC` no longer holds.

### Impact Explanation
This breaks the tenant-isolation guarantee that the gem's webhook verification is supposed to provide: the library asserts a request is "verified for shop X" when it has only verified the body was HMAC'd by the app's shared secret, not that shop X actually sent it. A host application that (reasonably, per the gem's documented API) trusts `WebhookMetadata#shop` to select/attribute the tenant record to update will process attacker-supplied webhook data (e.g., `orders/create`, `customers/data_request`, `app/uninstalled`, inventory/product changes) under a victim shop's identity — a cross-tenant data-integrity/authentication issue, since data attributed to shop X was never generated by shop X's install.

### Likelihood Explanation
The attacker only needs their own legitimate app installation (any merchant/test store) — no leaked credentials, no TLS interception, no access to `api_secret_key`. They can trigger real webhook events on their own store to obtain valid (body, hmac) pairs, then replay them with a forged `x-shopify-shop-domain` header value against the app's public webhook endpoint. This is a low-effort, purely network-level replay requiring only unprivileged internet access to the app's webhook receiver.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) as part of the signed/verified material, or otherwise cryptographically bind them to the signed payload, before trusting `request.shop`/`WebhookMetadata#shop`. At minimum, document/require host applications to independently correlate the shop domain against a per-shop secret/session lookup rather than relying on the header value validated only by the app-wide HMAC.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's shared `client_secret`).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (all required headers present).
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(secret, B)` and compares to `H` — this matches, so validation passes.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled data attributed to the victim shop, despite `victim.myshopify.com` never having sent this webhook.
