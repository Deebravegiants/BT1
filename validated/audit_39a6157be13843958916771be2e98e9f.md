### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing tenant-mismatched processing of a replayed webhook - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook purely by validating an HMAC over the raw request body, then hands the `shop` value straight out of an HTTP header — which is never included in the signed bytes — to the app's handler as the tenant identifier. This breaks the equality that should hold: `shop verified by HMAC == shop acted upon by the handler`.

### Finding Description
`Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` and, once it passes, immediately builds `WebhookMetadata` using `request.shop`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body (`@raw_body`) — it does **not** include the `shop` value: [3](#0-2) 

Meanwhile `Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, with no cryptographic binding to the HMAC that guards the payload: [4](#0-3) 

By contrast, the OAuth callback path (`AuthQuery`) does the correct thing: `shop` is one of the fields folded into `to_signable_string` before HMAC verification, so it is cryptographically bound to the signature: [5](#0-4) 

The webhook path lacks this binding. This is the direct analog of the reported `directionMask` bug: the field the code *acts on* (`shop`, used to route/attribute the webhook) is not the field the HMAC *actually verifies* (only the body bytes). Since a single app's `client_secret` is shared across every shop that installs the app, HMAC validity does not imply the header's shop value is correct — it only proves the body bytes were signed by *some* legitimate webhook delivery to *some* shop/topic using that app's secret.

### Impact Explanation
An attacker who controls a shop that has this app installed can capture a genuine webhook delivery (body + valid HMAC) sent to their own endpoint, then replay it with a forged `x-shopify-shop-domain` header identifying a different, victim shop. `Utils::HmacValidator.validate` will still pass because the HMAC only covers `@raw_body`, and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` is the attacker-chosen victim domain while `body` is the attacker's own (crafted-content) webhook payload. Any app logic that trusts `data.shop` to select the tenant record to update (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request`, or app-specific state changes keyed by shop) can be made to act on the wrong tenant's data — a cross-tenant integrity violation using data the app believes came from a verified source.

### Likelihood Explanation
Requires only an attacker who runs (or briefly installs) the target app on their own store to receive one legitimate signed webhook, then replays it to the app's public webhook endpoint with a modified `Shop-Domain` header. No access to `api_secret_key`, tokens, or victim credentials is needed — this satisfies the "unprivileged internet user" bar and does not depend on the host application ignoring documented behavior; it is a direct consequence of `Webhooks::Request#to_signable_string` only covering the body in this gem's own verification helper.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified surface, or otherwise explicitly re-derive/validate the shop identity from a source that is cryptographically covered before it is passed to `WebhookMetadata`/handlers. At minimum, document and enforce that `Registry.process` must not trust `request.shop` as an authenticated tenant identifier since it is outside the signed payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a real webhook (e.g., `orders/create`) to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and a JSON body.
2. Attacker captures the raw body and HMAC value from this delivery.
3. Attacker crafts a new HTTP POST to the same webhook endpoint, reusing the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new(raw_body:, headers:)` parses this into a request whose `shop` returns `"victim-shop.myshopify.com"`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) and matches the header HMAC — validation succeeds.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...))` is invoked, and the application processes attacker-supplied data under the victim shop's identity. [1](#0-0) [3](#0-2)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
