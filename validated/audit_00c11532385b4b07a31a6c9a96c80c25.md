### Title
Unbounded token array in escrow withdrawal loop can permanently freeze funds via out-of-gas - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` iterates over `body.tokens`, an array whose length is derived directly from the order's declared input/output token list, with no visible cap enforced at order placement or at withdrawal time. This mirrors the reported `totalValueLocked` bug class: a loop bound entirely by attacker/user-supplied array length, executed inside a critical, atomic fund-release path.

### Finding Description
The `withdraw` internal function loops over every token entry in the `WithdrawalRequest.tokens` array to transfer escrowed funds to the `beneficiary`: [1](#0-0) 

This function is reachable from `onGetResponse` (handling refund/cancel flows) and, per the module's `RequestKind` enum, from `RedeemEscrow`/`RefundEscrow` incoming requests dispatched by the Hyperbridge host — i.e. it is invoked as part of standard settlement of an order that any unprivileged user can place: [2](#0-1) 

The `len` value comes from `body.tokens.length`, which is populated from the order's own input/output token specification at order-placement time. I could not confirm within the available index whether `placeOrder` enforces a maximum number of input/output tokens per order; the withdraw loop itself contains no bound check, unlike the reported `OperationalStaking.totalValueLocked` case, where the loop scaled with the number of validators/unstakings a delegator interacted with, similarly without a hard cap.

### Impact Explanation
If an order can be created with an arbitrarily large number of distinct input/output tokens, the resulting `withdraw()` call (whether releasing funds to a solver on success or refunding the depositor on cancellation/timeout) must process every token entry in a single transaction. Once the required gas for that loop exceeds the block gas limit, the withdrawal can never succeed — regardless of how much gas the caller supplies — permanently freezing the escrowed principal and any transaction fees for that order. This is the "permanent freezing of funds" impact class this deployment is graded against.

### Likelihood Explanation
Likelihood depends on whether order-placement code caps the number of tokens per order (input assets + output assets). I was not able to locate that check within the indexed portion of the contract in the time available. If no such cap exists, any user placing an order is the "attacker" — they need only construct an order with enough distinct output tokens (each may hold a trivially small amount) to push the eventual `withdraw()` loop over the block gas limit, then have the request routed back through `onGetResponse`/redeem/refund. This requires no privileged access and no cooperation from other actors.

### Recommendation
- Confirm and, if absent, add an explicit maximum on the number of distinct tokens allowed in `Order.output.assets` (and any other array feeding `WithdrawalRequest.tokens`) at order-placement time, sized so the worst-case `withdraw()` loop comfortably fits within a conservative block gas limit across all supported destination chains.
- Alternatively, refactor `withdraw()` to process tokens in bounded batches (a claimable-per-token pattern) rather than requiring one atomic loop over the full set, so a large but valid order cannot deadlock its own settlement.

### Proof of Concept
Not independently reproduced against a live/forked deployment; this analysis is based on static review of `withdraw()`'s unbounded loop over `body.tokens.length`: [3](#0-2) 

To confirm exploitability, a PoC would need to: (1) verify `placeOrder` has no token-count cap, (2) construct an order with N output tokens where N is large enough that the per-token transfer loop (external call + storage read/write per iteration) exceeds the target chain's block gas limit, and (3) show the resulting `RefundEscrow`/`RedeemEscrow` callback into `withdraw()` reverts unconditionally due to out-of-gas. This step could not be completed with the tools available in this session.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
