### Title
Permanently locked `pending_delegator_rewards` in vote accounts when a validator's delegated stake is zero at the reward epoch boundary - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
Under SIMD-0123 block-revenue-sharing, delegator rewards are deposited as real lamports into a vote account's balance and tracked in the `pending_delegator_rewards` field via `deposit_delegator_rewards` [1](#0-0) . These funds are meant to be paid out to individual stake accounts pro-rata to their share of the vote account's total delegated stake through `calculate_block_reward`. If the vote account's total delegated stake for the rewarded epoch (`total_active_stake`) is zero, the function unconditionally returns `0` and no distribution happens, exactly mirroring the Wenwin `Staking.rewardPerToken()` pattern of `if (_totalSupply == 0) return rewardPerTokenStored;`.

### Finding Description
`calculate_block_reward` looks up the validator's stake denominator from `RewardEpochDelegatedStakes::delegated_stakes` (a snapshot computed once per epoch in `Stakes::calculate_activated_stake`) and short-circuits to `0` whenever that denominator is `0` or missing: [2](#0-1) 

`pending_delegator_rewards` is only ever decremented as part of the `block_reward` computed here (via `redeem_delegation_rewards`/`build_updated_stake_reward` later in the distribution pipeline). There is no fallback path that sweeps or burns `pending_delegator_rewards` when the denominator is zero — the value simply stays parked in the vote account state and its lamports stay in the vote account's balance, since `total_active_stake == 0` causes the calculation to skip payout entirely rather than treating it as a special/degenerate case.

This is structurally identical to the reported bug class: the "supply" (here, `total_active_stake`, the per-validator sum of currently effective delegations for the rewarded epoch) can be zero even though a deposit already happened, because:
1. The deposit (`DepositDelegatorRewards`) can occur at any point while the validator is producing blocks with revenue sharing enabled, based on the *current* delegation state.
2. `total_active_stake` used at reward-calculation time is a *snapshot for the rewarded epoch* computed by `Stakes::calculate_activated_stake` [3](#0-2) , which reflects whichever stake accounts happen to be delegated (and activation-adjusted) to this vote account at that specific epoch boundary.
3. If all stake previously delegated to a validator deactivates (fully unstakes) before/at that epoch boundary — the "Flow 2" scenario from the Wenwin report — `delegated_stakes.get(&vote_pubkey)` returns `0` or `None`, and any `pending_delegator_rewards` already sitting in the vote account become permanently stranded: no stake accounts exist in that epoch to claim a proportional share, and nothing ever forces `pending_delegator_rewards` back to `0`.

Compounding this, the vote-account `withdraw` instruction explicitly refuses to release these funds to the authorized withdrawer while `pending_delegator_rewards > 0`: [4](#0-3) 

So once stuck, the lamports are unreachable by both the (non-existent) delegators and the vote account's own withdraw authority — a stricter lock than the analog contract, which at least allows a future staker to accidentally receive it upon staking.

### Impact Explanation
Real, already-minted lamports (transferred into the vote account by `DepositDelegatorRewards`) become permanently unspendable: they cannot be claimed by stakers (no active delegation exists to compute a payout against) and cannot be withdrawn by the vote account's authorized withdrawer (`withdraw` blocks any amount that would dip into `pending_delegator_rewards`, and blocks full account closure while it is nonzero). This is a concrete, permanent loss of usable value with no recovery path in the current code, matching the "value loss" bar for this scan (funds effectively burned/frozen).

### Likelihood Explanation
This requires: (a) `block_revenue_sharing`/SIMD-0123 features active, (b) a validator that had delegator rewards deposited via `DepositDelegatorRewards`, and (c) all stake delegated to that validator's vote account fully deactivating by the reward-epoch stake snapshot used for `RewardEpochDelegatedStakes`. Small/low-stake validators, or validators experiencing a full stake exodus (e.g., after misbehavior, commission changes, or a validator temporarily losing all delegators), can realistically hit `total_active_stake == 0` while retaining nonzero `pending_delegator_rewards` accumulated from prior blocks. This is a plausible, unprivileged-triggerable edge case rather than a purely theoretical one, though it does require specific timing (deposit before stake fully unwinds) so it is not a routine occurrence.

### Recommendation
When `total_active_stake == 0` for a vote account with nonzero `pending_delegator_rewards`, either: (1) redirect the stranded pending rewards to a recoverable destination (e.g., allow the withdraw authority to reclaim them once no delegated stake exists for the relevant reward epoch), or (2) carry the balance forward and re-attempt distribution once new stake delegates to that vote account, explicitly tracking "orphaned" pending rewards separately from the withdraw-lock check so they don't become permanently frozen.

### Proof of Concept
Conceptual reproduction (cannot be run without a test harness edit, but derivable directly from the code paths cited above):
1. Enable `block_revenue_sharing`, `custom_commission_collector`, `commission_rate_in_basis_points` features and delegate stake `S` to vote account `V`.
2. While `V` is a leader and earning block rewards, call `DepositDelegatorRewards` on `V`, incrementing `pending_delegator_rewards` to `X > 0` [5](#0-4) .
3. Deactivate/withdraw all stake delegated to `V` so that, at the next epoch boundary, `Stakes::calculate_activated_stake` produces `effective_delegated_stakes` with `V`'s entry equal to `0` (or absent) in `RewardEpochDelegatedStakes` [6](#0-5) .
4. At the reward-epoch boundary, `calculate_block_reward` is invoked for any remaining/new delegations to `V`; since `total_active_stake == 0`, it returns `0` for all of them, so `pending_delegator_rewards` is never decremented [2](#0-1) .
5. Attempt to withdraw lamports from `V`'s vote account beyond `lamports - pending_delegator_rewards - rent_exempt_minimum`, or attempt to fully close the account: both fail with `InstructionError::InsufficientFunds` [4](#0-3) , confirming the `X` lamports are now permanently stuck.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

    pub(crate) fn calculate_activated_stake(
        &self,
        next_epoch: Epoch,
        thread_pool: &ThreadPool,
        new_rate_activation_epoch: Option<Epoch>,
        stake_delegations: &[(&Pubkey, &StakeAccount)],
        use_fixed_point_stake_math: bool,
    ) -> (
        StakeHistory,
        VoteAccounts,
        DelegatedStakes,
        RewardEpochDelegatedStakes,
    ) {
        // Wrap up the prev epoch by adding new stake history entry for the
        // prev epoch.
        let (stake_history_entry, effective_delegated_stakes) = thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .fold(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(acc, mut delegated_stakes), (_stake_pubkey, stake_account)| {
                        let delegation = stake_account.delegation();
                        let activation_status = delegation_activation_status(
                            delegation,
                            self.epoch,
                            &self.stake_history,
                            new_rate_activation_epoch,
                            use_fixed_point_stake_math,
                        );
                        *delegated_stakes.entry(delegation.voter_pubkey).or_default() +=
                            activation_status.effective;
                        (acc + activation_status, delegated_stakes)
                    },
                )
                .reduce(
                    || (StakeActivationStatus::default(), HashMap::default()),
                    |(activation_status_a, delegated_stakes_a),
                     (activation_status_b, delegated_stakes_b)| {
                        (
                            activation_status_a + activation_status_b,
                            merge_delegated_stakes(delegated_stakes_a, delegated_stakes_b),
                        )
                    },
                )
        });
        let mut stake_history = self.stake_history.clone();
        stake_history.add(self.epoch, stake_history_entry);
        // Refresh the stake distribution of vote accounts for the next epoch,
        // using new stake history.
        let (vote_accounts, delegated_stakes) = refresh_vote_accounts(
            thread_pool,
            next_epoch,
            &self.vote_accounts,
            stake_delegations,
            &stake_history,
            new_rate_activation_epoch,
            use_fixed_point_stake_math,
        );
        let reward_epoch_delegated_stakes = RewardEpochDelegatedStakes {
            epoch: self.epoch,
            delegated_stakes: effective_delegated_stakes,
        };
        (
            stake_history,
            vote_accounts,
            delegated_stakes,
            reward_epoch_delegated_stakes,
        )
    }
