### Title
Unvalidated caller-supplied swap route executes arbitrary attacker contracts under the signer's authorization tree, enabling wallet-token theft — (File: `contracts/controller/src/strategies/swap.rs`, `contracts/swap-aggregator/src/venues/aquarius/pool.rs`)

### Summary
The controller's strategy entrypoints (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) accept opaque, caller-supplied route bytes and forward them verbatim to the swap aggregator via `router.execute_strategy(&controller, &amount_in, swap)`. The aggregator decodes the route into pool and token addresses and calls them with `env.invoke_contract` — it "keeps no allowlist of them" (`docs/explanation/threat-model.md`). A route can therefore name an attacker-deployed contract. Any `token.transfer(victim, attacker, ...)` issued by that rogue code is recorded by simulation as a child of the caller's `require_auth` tree, and executes if the caller signs the simulated tree — draining wallet tokens unrelated to the swap, unbounded by the input amount, min-out, or the final health-factor gate.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` authorizes only one exact transfer (`authorize_transfer_as_current(token_in, controller → router, amount_in)`) and then calls the router inside the flash guard. Neither it nor the router validates the route's hop `pool`/`token_in`/`token_out` addresses. In `contracts/swap-aggregator/src/venues/aquarius/pool.rs::invoke_pool_swap`, `dispatch_hop` invokes `pool.swap(...)` at whatever address the payload names. The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the chain end-to-end: an `UnlistedPoolRouter`-style route through a `RogueHopPool` whose `swap` calls `token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount)` — when the signed auth tree includes that stolen transfer as a sub-invocation (which is exactly what simulation returns), the call succeeds and the victim's wallet is emptied (`enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` asserts `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE`).

This is the direct analog of the `safe_eval` injection class: attacker-influenced input (route bytes, typically sourced from a quote service or a malicious UI/payload) is interpreted as executable contract invocations, and the authorization mechanism designed to constrain it (per-entry invoker auth) silently folds the attacker's unauthorized code into the victim's signed tree.

### Impact Explanation
Theft of user funds: every token in the signer's wallet (not just the swap input) can be transferred out by route-named code, provided the user signs the simulated auth tree — which wallets produce automatically and users rarely decode. The controller's measured-delta checks (`RouterOverspend`, `NoSwapOutput`) and post-swap health-factor gate do not bound the rogue transfer, since it targets the caller's wallet rather than controller or router custody. The same exposure exists on the standalone `execute_strategy` path for every swap user, as documented in `threat-model.md:154-165`.

### Likelihood Explanation
Exploitation requires the victim to submit (and sign for) an attacker-crafted route — e.g., via a compromised/malicious quote source or a pasted `routeXdr` — so it is not fully self-triggered. However, the contracts provide no mitigation: no venue/token allowlist, no structural restriction on which contracts the payload may name, and the benign-looking swap still settles correctly (`swap` returns fair output and `verify_router_output` passes), so nothing on-chain distinguishes the poisoned route. The harness test demonstrates the theft succeeds under normal simulation-produced signatures. Rated High rather than Critical because it requires the victim to sign a poisoned auth tree.

### Recommendation
- Maintain a venue/pool registry in the swap aggregator (admin-allowlisted pool addresses per opcode, or venue-contract allowlisting plus per-pool `get_tokens`/`share_id` verification already partly done for Aquarius) and reject routes naming unregistered pools.
- In the controller, reject routes that reference token or pool addresses not previously registered, and document that `swap_collateral`/`swap_debt`/`repay_debt_with_collateral`/`multiply` callers must simulate and decode the auth tree, refusing any `transfer`/`transfer_from`/`approve` child entries beyond the single expected input pull.

### Proof of Concept
1. Victim Alice holds `WALLET_BALANCE` of an unrelated token and has a healthy position.
2. Attacker deploys `RogueHopPool` (test file above): its `swap` does `token::Client::new(&env, &wallet_token).transfer(&alice, &attacker, &WALLET_BALANCE)`.
3. Attacker supplies a route whose hop `pool` is `RogueHopPool`; route's `token_in`/`token_out` and `min_out` are set so the router still pays a fair output, so `verify_router_output` passes.
4. Alice calls `swap_collateral(alice, account_id, USDC_market, amount, ETH_market, route)`; simulation embeds the rogue `transfer` as a child of her auth entry; she signs the simulated tree.
5. `RogueHopPool.swap` executes under that authorization, moving Alice's full wallet balance to the attacker; the swap itself completes normally, so all post-checks pass. Confirmed by `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:229-269`.
