### Title
Webhook `shop-domain` header is not bound by the HMAC signature, allowing shop identity spoofing on webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are all taken from HTTP headers that are excluded from the signed content. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the authenticated shop identity for the handler after HMAC validation succeeds, even though that field was never covered by the HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived purely from the `x-shopify-shop-domain` / `shopify-shop-domain` header, independent of the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the signature strictly against `to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` gates on that HMAC check and then forwards `request.shop` straight to the handler as the shop identity, with no additional binding to the signed content: [4](#0-3) 

Because the shop-domain header sits outside the HMAC-covered bytes, `verified(hmac, body) == true` does not imply `shop-domain == shop that generated body`. Any party that can influence the `x-shopify-shop-domain` header of a request carrying an otherwise-valid `(body, hmac)` pair (e.g., a genuine webhook delivery for the attacker's own installed shop, replayed/relayed with the header rewritten) produces a request that passes `HmacValidator.validate` unchanged while claiming to originate from an arbitrary victim shop. This breaks the identity equality: **shop authenticated by HMAC (none) vs. shop consumed by the handler (unauthenticated header)**.

### Impact Explanation
Multi-tenant apps built on this gem key their per-tenant business logic (data writes, session/access-token lookups, entitlement checks) off `WebhookMetadata#shop`, believing it was validated alongside the HMAC check that immediately precedes its use in `Registry.process`. An attacker who controls delivery of a validly-signed webhook for their own shop can rewrite the shop-domain header and get the host application to process/attribute the payload to a different tenant — a cross-tenant access impact.

### Likelihood Explanation
The only prerequisite is control over a request that carries a legitimately-signed body for some shop (a shop the attacker owns/controls can generate this by triggering any webhook-eligible action, since Shopify itself signs the delivery with the app's shared `client_secret` for every installed shop) and the ability to alter the shop-domain header before it reaches the app's webhook endpoint logic. No access token, `client_secret`, or victim credentials are needed — only the attacker's own legitimate installation.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the shop identity to the signature, so `HmacValidator.validate` fails whenever the claimed `shop` does not match the shop that produced the signed body. At minimum, document that `request.shop` is unauthenticated and must be cross-checked against a shop the app has independently verified (e.g., an installed-shop record) before being trusted.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook-eligible event, causing Shopify to POST a body `B` with header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com` to the app's webhook endpoint.
2. Attacker intercepts/relays this delivery (e.g., via a proxy in front of the endpoint they control) and rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, leaving `B` and the HMAC header untouched.
3. The endpoint constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: rewritten_headers)` and calls `ShopifyAPI::Webhooks::Registry.process(request)`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against the unchanged HMAC header. [5](#0-4) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the signed body actually originated from `attacker-shop.myshopify.com` — the host application processes attacker-controlled data under the victim tenant's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
