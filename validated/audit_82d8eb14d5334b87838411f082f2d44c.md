## Title
Webhook `shop-domain` identity is not covered by the HMAC, allowing cross-tenant shop-identity spoofing of otherwise-valid webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used by webhook handlers from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body. The shop identity is therefore never bound to the signature that authenticates the request, mirroring the report's core defect: "the identity is not part of the hash."

### Finding Description
`Request#to_signable_string` returns only the raw body, and `Request#shop` is read straight from an attacker-suppliable header: [1](#0-0) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac-sha256` header, i.e. it only authenticates the body bytes, never the shop header: [2](#0-1) 

`Registry.process` accepts any request that passes this body-only HMAC check and forwards the attacker-controlled `request.shop` straight to the app's handler as the trusted tenant identity: [3](#0-2) 

Because a single app-wide `Context.api_secret_key` is used to validate webhooks for *every* installed shop (not a per-shop secret), any unprivileged user who installs the app on their own store legitimately receives correctly-HMAC-signed webhook deliveries. Since the shop identity is carried out-of-band in a header that is not part of the signed content, the attacker can replay the exact same `(raw_body, hmac)` pair while substituting the `shop-domain` header for a victim shop. The HMAC still validates (it only checks the untouched body), and `WebhookMetadata.shop` is populated with the attacker-chosen victim shop domain, exactly like the report's "identity not bound to signature" replay across two different identities sharing one credential domain (here, one shared app secret across all shops).

The binding that is broken:
`hmac_valid(body) == true` should imply `shop == the tenant that Shopify actually generated this HMAC for`, but instead `hmac_valid(body) == true` only implies `body` is unmodified — `shop` is attacker-controlled and unauthenticated.

### Impact Explanation
Apps built on this gem commonly key per-tenant state (offline session/access-token records, uninstall bookkeeping, GDPR data lifecycle, plan/feature flags) by `WebhookMetadata#shop`. Because `shop` is unauthenticated, an attacker with only their own (unprivileged) shop installation can forge webhook deliveries that the host application will process as belonging to a different, victim shop — e.g., replaying an `app/uninstalled` body against a victim's shop-domain to trigger deletion/revocation of the victim's stored offline access token, or replaying a data body to have it processed under a victim shop's identity. This is a cross-tenant identity-confusion primitive rooted entirely in this gem's `Webhooks::Request`/`HmacValidator` design, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any developer/merchant can install the app on their own store (no special privilege required) to obtain a batch of validly-HMAC-signed webhook bodies signed with the app's single, shop-agnostic `api_secret_key`. Swapping the `shop-domain` header on a replayed request is trivial and entirely within reach of an "unprivileged internet user" as scoped by the rules — it requires no access token, no leaked credentials, and no privileged account.

### Recommendation
Bind the shop identity into the authenticated signal before it is trusted: either include `shop-domain`/`topic`/`webhook-id` in the HMAC signable content (matching what Shopify actually intends to authenticate) or, at minimum, document and enforce that `Registry.process` callers must independently verify `request.shop` against a shop that is expected to exist/be installed (e.g., cross-check against a known, previously-established offline session for that shop before trusting the payload), rather than treating `shop-domain` as authenticated purely because the body's HMAC passed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, completing OAuth normally (no elevated privilege).
2. Shopify delivers a legitimate webhook to the attacker's endpoint, e.g. `app/uninstalled` with body `{}`, header `x-shopify-shop-domain: attacker.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed over that body with the app's shared `api_secret_key`.
3. Attacker replays the identical raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, "{}")`, which still matches (body unchanged) — validation passes.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` and invokes the app's handler, which now performs uninstall cleanup (e.g., deleting the stored offline access token) for `victim.myshopify.com` — a shop the attacker never controls or has installed the app on.
