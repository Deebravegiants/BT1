This confirms the vulnerability. `Auth::Oauth::AuthQuery#to_signable_string` deliberately includes `shop` in the HMAC-signed payload (matching Shopify's design), but `Webhooks::Request#to_signable_string` signs only `@raw_body`, excluding `shop-domain`, `topic`, and `webhook-id` headers from the HMAC-verified data entirely.

### Title
Webhook shop/topic/webhook-id identity fields are unauthenticated (not covered by HMAC), enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying fields (`shop`, `topic`, `webhook_id`) from raw HTTP headers, but the HMAC signature validated by `Utils::HmacValidator.validate` only covers the raw request body. Any actor who can obtain one legitimately-signed webhook body (e.g., by installing the app on their own store and receiving a real webhook) can replay that body+HMAC pair while forging the `shop-domain` header to any other shop, and it will pass validation.

### Finding Description
`Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` value: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include the `shop`, `topic`, or `webhook_id` values, all of which are read directly from unauthenticated headers: [3](#0-2) 

By contrast, the OAuth callback's `AuthQuery#to_signable_string` explicitly binds `shop` (along with `code`, `host`, `state`, `timestamp`) into the signed payload, which is the correct pattern: [4](#0-3) 

Because the webhook HMAC never binds `shop-domain`/`topic`/`webhook-id` to the body, `HmacValidator.validate` returns `true` for any request that pairs a genuinely-signed body with a forged `shop-domain`, `topic`, or `webhook-id` header. The identity binding broken is: `shop authenticated by HMAC` ≠ `shop used as the tenant key passed to the handler`. `Registry.process` passes this unauthenticated `request.shop` straight into `WebhookMetadata`, which the host application's handler trusts as the tenant identity: [5](#0-4) 

### Impact Explanation
This enables cross-tenant confusion/spoofing: an attacker who has legitimately installed the app on their own shop (an unprivileged, arbitrary merchant) receives real webhooks signed with the app's shared secret for their own body content. They can replay that valid `(body, hmac)` pair while swapping only the `shop-domain` header to any target shop domain the app is also installed on. `Registry.process` will accept it as authentic and hand `WebhookMetadata` with the forged `shop` (and the attacker's own body content, or a body they control if the topic also allows attacker-influenced content) to the host app's handler, which will act on it as if it came from the victim tenant. This crosses a tenant boundary using data not actually authorized by Shopify for that tenant, meeting the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is realistic: any actor with a Shopify Partner/dev account can install the app on their own store (no privileged access, tokens, or credentials required), trigger a webhook naturally, capture the `(raw_body, hmac)` pair, and replay it against the app's webhook endpoint with a modified `shop-domain`/`topic`/`webhook-id` header. No knowledge of `api_secret_key` or any merchant's access token is needed — the whole point is that Shopify itself signs the body on the attacker's behalf.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-verified payload for webhooks, or otherwise cryptographically bind these header values to the signed body content (e.g., include them in `to_signable_string`, mirroring the `AuthQuery` pattern), so `HmacValidator.validate` fails whenever any tenant-identifying header has been altered relative to what Shopify actually signed.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to.
2. Capture the resulting HTTP request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (a valid signature of `B` under the app's secret).
3. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `B` against `H`. [6](#0-5) 
5. `Registry.process` invokes the host app's handler with `shop: "victim.myshopify.com"` and the attacker-supplied body, despite Shopify never having signed a webhook claiming to be from `victim.myshopify.com`. [7](#0-6)
