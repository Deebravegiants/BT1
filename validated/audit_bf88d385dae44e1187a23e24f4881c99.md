This confirms the vulnerability: the webhook HMAC signature in `Utils::HmacValidator` only covers `Request#to_signable_string`, which returns `@raw_body` alone [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` fields are all read directly from HTTP headers and are never included in the signed payload [2](#0-1) . `Registry.process` validates only the HMAC of the raw body, then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` values [3](#0-2) .

### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string as only the raw request body [1](#0-0) , while the `shop` (tenant identifier), `topic`, and `webhook_id` used to route and process the webhook are taken from unauthenticated HTTP headers [2](#0-1) . `Utils::HmacValidator.validate` computes and compares the HMAC purely over `to_signable_string`, i.e., the body [4](#0-3) . `Registry#process` trusts `request.shop` for the `WebhookMetadata` passed to the app's handler as soon as the body HMAC checks out [3](#0-2) .

### Finding Description
This is the same bug class as the `BaseV2Minter` report: a value that is acted upon (the DAO `share`, here the webhook's tenant/`shop` binding) is computed/validated relative to the wrong scope — the intention is that HMAC validity should imply "this exact `(shop, topic, body)` tuple is authentic," but the implementation only proves "this exact `body` was signed by *some* install of this app." Because Shopify apps share one `client_secret`/`api_secret_key` across every shop that installs them, the HMAC does not bind the message to a specific shop. Formally, the binding the gem needs is:

`hmac_valid(body, secret) == true` should imply `authenticated_shop == claimed_shop`

but what is actually implemented is:

`hmac_valid(body, secret) == true` implies only `body was produced by *an* install of this app` — the header-derived `shop` is asserted, not proven.

An unprivileged internet user who has installed the target app on their own store (a legitimate, low-privilege tenant) receives genuine webhook deliveries from Shopify to their configured endpoint, each with a valid `X-Shopify-Hmac-Sha256` signature over the body, computed with the app's shared `client_secret`. Because the signature never covers the `X-Shopify-Shop-Domain` header, the attacker can capture one of these bodies (with its valid signature) and replay it to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointing at a victim shop. `HmacValidator.validate` will accept it because the body+signature pair is legitimate, and `Registry#process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop [5](#0-4) .

### Impact Explanation
Any app built on this gem that keys business logic, storage, or side effects off `WebhookMetadata#shop` (e.g., `app/uninstalled`, `shop/update`, `customers/data_request`) can be tricked into applying attacker-controlled data to, or triggering privileged actions against, a different tenant's record — a cross-tenant confusion/injection primitive, since the shop identity used to select the tenant's session/data is not covered by the authentication check.

### Likelihood Explanation
Requires only that the attacker be an app-installing merchant (no special access, no leaked secrets), and control of the headers sent to the app's public webhook endpoint (trivial, since headers are attacker-controlled in a replayed/forged HTTP request) — well within the "unprivileged internet user" threat model.

### Recommendation
Include the routing-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material, or otherwise cryptographically bind them to the body (e.g., HMAC over a canonical string of `shop|topic|webhook_id|body`) instead of validating only the raw body in `Request#to_signable_string` [1](#0-0) .

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook (e.g. `orders/create`) to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, and a valid `X-Shopify-Hmac-Sha256` computed over the body.
3. Attacker captures this raw body + hmac header.
4. Attacker sends a new HTTP POST to the same app endpoint with the identical body and hmac header, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` returns `true` because it only checks `body` against `hmac` [6](#0-5) ; `Registry#process` dispatches the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body [3](#0-2) .
