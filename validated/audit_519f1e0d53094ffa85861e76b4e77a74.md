### Title
Unrefunded native token overpayment permanently locked in `EvmHost` on POST dispatch - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)` allows callers to pay the relayer fee in native ETH by swapping it for the exact fee-token amount through `swapETHForExactTokens`. Any ETH sent above what the swap actually consumes is refunded by the router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender — and the function contains no logic to forward that residual balance back to the caller. This is the same root cause as the reported Pyth issue: value is transferred to an external "pay-what-you-owe" call without first validating/capping the exact amount, and any surplus is not returned to the payer.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

when `msg.value > 0`, the entire `msg.value` is forwarded to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. This call only spends as much ETH as is required to obtain exactly `post.fee` fee tokens; the router refunds the unspent ETH to `msg.sender`, which in this call context is `EvmHost` itself (the contract executing the swap), not the externally-owned account or contract that originally called `dispatch()`. There is no subsequent step in `dispatch()` that measures the leftover native balance and returns it to `_msgSender()`.

This mirrors the exact bug pattern from the external report: a function accepts a `msg.value` amount, forwards it wholesale into a downstream "charge only what's needed" call, and the excess is not refunded to the actual payer — except here the surplus is captured by the protocol's own dispatcher contract rather than a third-party oracle, so the funds are lost inside `EvmHost` unless a privileged admin/withdrawal path exists to recover them.

Note: this analysis is based on the `dispatch(DispatchPost)` implementation directly read from `EvmHost.sol`; due to tool-call limits I was not able to fully re-verify every other dispatch entrypoint (`DispatchGet`, `dispatchPostResponse`) line-by-line, though grep results show `swapETHForExactTokens` is used multiple times in the same file with the same `address(this)`-recipient pattern, suggesting the same issue is present across all native-fee dispatch paths.

### Impact Explanation
Any user or integrating application (e.g. `IDispatcher(_host).dispatch{value: msg.value}(post)`) that supplies `msg.value` greater than the swap's actual ETH cost — for example due to price movement between quoting and execution, or simply sending a safety margin — permanently loses the difference, because it accrues to the `EvmHost` contract's own balance instead of being returned. Given `dispatch` is the primary entrypoint used by every application built on Hyperbridge (as shown in the SDK/docs examples that always forward `msg.value`), this can affect a large volume of routine cross-chain message dispatches, not just an edge case.

### Likelihood Explanation
Likelihood is Medium: users/integrators frequently send extra ETH as slippage buffer when quoting fee amounts (as explicitly done in `HyperbridgeLzEndpoint.quote`, which applies "a generous 2x buffer" and relies on the assumption that "Excess native is refunded by the uniswap router"): [2](#0-1) 
That comment itself demonstrates the flawed assumption — the router does refund, but to `EvmHost`, not to the end caller — so overpayment is an expected, common occurrence rather than a rare edge case.

### Recommendation
After the `swapETHForExactTokens` call in `EvmHost.dispatch` (and any other dispatch function following the same pattern), compute the actual ETH spent (or measure `address(this).balance` delta) and refund any leftover native value to `_msgSender()`:
```solidity
if (msg.value > 0) {
    uint256 balanceBefore = address(this).balance - msg.value;
    address[] memory path = new address[](2);
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
    uint256 leftover = address(this).balance - balanceBefore;
    if (leftover > 0) {
        (bool ok, ) = _msgSender().call{value: leftover}("");
        require(ok);
    }
}
```

### Proof of Concept
1. Caller calls `dispatch(DispatchPost)` with `msg.value = 2 ETH` while `post.fee` only requires `0.1 ETH` worth of WETH swapped for the fee token.
2. `swapETHForExactTokens{value: 2 ether}(post.fee, path, address(this), block.timestamp)` executes, spending only the ETH needed for `post.fee` tokens and refunding the remaining ~1.9 ETH to `msg.sender` — `EvmHost`.
3. `dispatch()` returns normally with a valid commitment; the caller's 1.9 ETH is now held by `EvmHost` with no accounting entry and no code path to withdraw it back to the caller, resulting in a permanent loss of funds for the caller and an unaccounted-for balance in `EvmHost`.
