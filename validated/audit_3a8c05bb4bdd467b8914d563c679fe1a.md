### Title
Panic-inducing fixed-size buffer write from unvalidated cross-chain message field in `HftModule::on_accept` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`on_accept` in the hyper-fungible-token pallet's `IsmpModule` implementation decodes an incoming ISMP `PostRequest` and, in the substrate-recipient branch of the calldata dispatch path, copies `message.from` (an ABI-decoded `bytes` field controlled entirely by the source-chain sender) into a fixed `[u8; 32]` buffer via `copy_from_slice` without first checking its length.

### Finding Description
In `on_accept`, after decoding `message` from the request body: [1](#0-0) 
the substrate (non-EVM-source) branch executes:
```rust
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
```
`from_bytes` is `message.from.as_ref()`, taken directly from the ABI-decoded, attacker/counterparty-supplied message body — there is no length check comparable to the `message.to` handling a few lines earlier (which explicitly validates 32-byte or 20-byte lengths and returns `HftError::InvalidRecipientLength` otherwise, see lines 63-71). `copy_from_slice` panics immediately when source and destination slice lengths differ, matching the CVE's root cause: "writes... with guest controlled data of guest controllable size... bounding of the writes was missing."

This branch is only reached when `message.data` is non-empty and no `signature` is present in the decoded `SubstrateCalldata` (i.e., the sender relies on the derived-from-source-address path rather than a verified signature) and the request source is not EVM. Since `message.from` is fully attacker-controlled ABI-decoded bytes (arbitrary length), a malicious or misconfigured source-chain contract can craft `from` with any length other than 32 bytes, causing this dispatch to panic mid-message-handling.

### Impact Explanation
`on_accept` is invoked by `HandlerV2`/`pallet-ismp`'s dispatch machinery when delivering an inbound `PostRequest` from a registered source contract — i.e., directly reachable by any relayer delivering a validly-proven message from a source chain whose contract is mapped via `ContractToAsset`. A panic here aborts extrinsic execution non-gracefully within message dispatch, which can disrupt the pallet's ability to process further requests in the same block/queue and is a denial-of-service condition on the token-bridge message-delivery path, potentially freezing token mint/transfer processing for that route until the message is skipped or handled out of band.

### Likelihood Explanation
High for any deployment where a source-chain contract is registered in `ContractToAsset` and can be induced (or is malicious/compromised) to emit a message with a non-32-byte `from` value alongside non-empty `data` and no `signature` — no special privilege is required beyond delivering a validly-proven relayed message, matching the "unprivileged message dispatcher/relayer" reachability criterion.

### Recommendation
Validate `from_bytes.len() == 32` before `copy_from_slice`, mirroring the existing pattern used for `message.to` a few lines above (returning a typed error such as `HftError::InvalidSenderLength(from_bytes.len())` instead of panicking).

### Proof of Concept
1. Register a source contract address in `ContractToAsset` for a non-EVM `source` `StateMachine`.
2. Construct a `PostRequest` whose ABI-encoded body decodes to a `Message` with:
   - `data` non-empty and containing a `SubstrateCalldata` with `signature: None`.
   - `from` set to any byte length other than 32 (e.g., 31 or 33 bytes).
3. Deliver this request through the normal proof-verified dispatch path to `on_accept`.
4. Execution reaches `account.copy_from_slice(from_bytes)` with mismatched lengths and panics, aborting the call. [2](#0-1) [1](#0-0)
