### Title
Consensus-incentive reward can be front-run: signer field embedded in the unsigned `ConsensusMessage` is decoupled from whoever actually produced the consensus proof - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives` rewards "consensus relayers" for advancing a remote chain's state via `pallet_ismp::handle_unsigned` submissions of `Message::Consensus`. The relayer entitled to the `$BRIDGE` reward is not derived from the transaction's origin (the extrinsic is unsigned) or from any property intrinsic to the proof itself, but purely from an arbitrary `Signature` byte-blob (`consensus_msg.signer`) that is embedded inside the message and self-supplied by whoever crafts the extrinsic. This mirrors the "Front-Run Keeper Rewards" bug class: an attacker can watch the public mempool for a valid `Message::Consensus` payload, strip out only the `signer` field, substitute their own signature over the same `consensus_proof` bytes, and resubmit with higher priority — capturing the reward for consensus verification work someone else actually performed, exactly as described in the report ("sending a transaction with a few input mutations... to fraudulently claim the reward without fulfilling the keeper effort").

### Finding Description
`Pallet::on_executed` in `modules/pallets/consensus-incentives/src/impls.rs` (lines 104-163) is the `FeeHandler::on_executed` hook invoked after `pallet-ismp` successfully processes a batch of ISMP messages, including `Message::Consensus`. [1](#0-0) 

The reward recipient is derived exclusively from:
```rust
let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
Signature::decode(&mut &consensus_msg.signer[..])
    .ok()
    .and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
    .map(|pub_key| pub_key.into())
```
i.e. any sr25519 keypair the *submitter of the extrinsic* controls can produce a valid `signer` over `keccak256(consensus_proof)`, because the signature only needs to verify against a hash of public data (the proof bytes), not against anything tying it to the entity that generated the proof or to the transaction's actual origin (the extrinsic call itself is unsigned, `ensure_none(origin)`). [2](#0-1) 

The reward is then paid from the treasury and reputation is minted to whatever account decoded from `signer`: [3](#0-2) 

Critically, `consensus::update_client` (the actual proof-verification logic invoked by `handle_incoming_message`) never inspects or constrains `msg.signer` at all — it only uses `msg.consensus_proof` and `msg.consensus_state_id`: [4](#0-3) 

So the `signer` attribution is entirely out-of-band from proof verification. Because the underlying `handle_unsigned` extrinsic that carries the `Message::Consensus` (with its `consensus_proof` and `signer`) is itself unsigned and broadcast through the public mempool/tx-pool, any observer can:
1. See a pending `Message::Consensus{ consensus_proof, consensus_state_id, signer }` in the mempool.
2. Recompute `keccak256(consensus_proof)` (public data — no re-derivation of the underlying BEEFY/GRANDPA proof is needed).
3. Sign that same hash with their own throwaway sr25519 key to produce a new `signer`.
4. Resubmit the message with the swapped `signer` and higher priority/tip, landing before the original.

The proof itself still verifies (it is unchanged and does real work advancing state), so the message is accepted by `pallet_ismp`, but the treasury payout and reputation mint now go to the front-runner's self-chosen key rather than the account that actually ran the consensus client and produced the proof.

### Impact Explanation
This directly steals treasury funds (`$BRIDGE`) and soulbound reputation (used for collator-selection weighting per the relayer docs) from honest consensus relayers who perform the real, resource-intensive work of tracking source-chain finality and constructing valid BEEFY/consensus proofs. Because reputation feeds into collator selection, this also lets a zero-effort front-runner unfairly accumulate collator-selection weight. Repeated over many state updates, this is a systemic drain of the treasury towards addresses that never ran relayer infrastructure — a concrete unbacked-value transfer / fund-theft impact meeting the "Medium/High" bar (funds are diverted from legitimate participants to attackers, and protocol incentive alignment is broken).

### Likelihood Explanation
High likelihood: unsigned extrinsics carrying `Message::Consensus` are visible pre-inclusion in the mempool (this is explicit protocol design — the docs describe relaying as "competitive... first-to-submit wins"), and the mutation required (swap a signature field for a self-generated one over already-public hash data) is trivial and requires no special privileges, staking, or the ability to re-derive the underlying consensus proof. This is materially easier than ordinary "first submitter wins" front-running because the attacker does not even need to independently construct a valid proof — they parasitize someone else's already-broadcast, already-verifying proof and merely relabel the payee.

### Recommendation
Bind the reward recipient to something that cannot be swapped without redoing the actual verification work, e.g.:
- Derive the rewarded account from the transaction's actual signer/origin (require a signed extrinsic, or use `ValidateUnsigned`/`pre_dispatch` to bind a specific relayer identity that the runtime tracks), rather than trusting an arbitrary self-supplied `signer` byte blob inside the payload.
- If the unsigned-extrinsic design must be kept, have the signature commit to something an attacker cannot cheaply reproduce standing outside of the honest relayer's private inputs (e.g., require the signature over data that includes a value only the original proof producer would know, or move to a proof-of-work/staked-identity scheme), or move to the keeper-consensus/slot-allocation design the team has already floated for the analogous EVM keeper reward issue.
- At minimum, tie the `signer` recovery to the account that actually authored/broadcast the extrinsic (e.g., require the extrinsic to be signed and match the recovered pubkey), closing the gap between "who submitted the winning transaction" and "who is credited with the reward."

### Proof of Concept
1. Honest relayer R constructs a valid `beefy_verifier` proof for a new finalized height and builds `Message::Consensus { consensus_proof: P, consensus_state_id: S, signer: Sig_R(keccak256(P)) }`, then calls `pallet_ismp::handle_unsigned(origin=None, vec![msg])`.
2. Attacker A observes this unsigned extrinsic in the public mempool before it is included in a block, extracting `P` and `S` (both are plaintext in the extrinsic).
3. A computes `h = keccak256(P)`, signs it with A's own sr25519 keypair to get `Sig_A(h)`, and constructs `Message::Consensus { consensus_proof: P, consensus_state_id: S, signer: Sig_A(h) }`.
4. A submits this message via `pallet_ismp::handle_unsigned` with a higher priority/tip so it lands in an earlier block position than R's original transaction.
5. `consensus::update_client` verifies `P` successfully (it is unmodified, valid proof data) and advances state; `pallet-consensus-incentives::on_executed` recovers A's pubkey from `Sig_A`, and transfers the `$BRIDGE` reward plus mints reputation to A's account instead of R's.
6. R's original transaction, submitted later, either fails (stale height / `NoNewWork`-style rejection) or, if it still lands, pays nothing new since the state advance was already consumed — R receives no compensation for the work performed.

		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,

		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

				reward,
				Preservation::Expendable,

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

pub fn update_client<H>(host: &H, msg: ConsensusMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host.consensus_client_id(msg.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized { consensus_state_id: msg.consensus_state_id },
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;
	host.is_consensus_client_frozen(msg.consensus_state_id)?;
	host.is_expired(msg.consensus_state_id)?;

	let (new_state, intermediate_states) = consensus_client.verify_consensus(
		host,
		msg.consensus_state_id,
		trusted_state,
		msg.consensus_proof,
	)?;
