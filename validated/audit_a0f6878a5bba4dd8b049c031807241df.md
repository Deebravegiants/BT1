### Title
`calc_take_pnl()`'s invariant check can permanently revert `Deposit`, `Withdraw`, and `WithdrawPnl`, locking pool funds - (File: `program/src/processor.rs`)

### Summary
`Calculator`-derived `calc_take_pnl()` gates every `Deposit`, `WithdrawPnl`, and non-`WithdrawOnly` `Withdraw` instruction on a comparison between the pool's live reserves and a separately-tracked "last k" snapshot (`target_orders.calc_pnl_x` / `calc_pnl_y`). If the live value ever falls below the snapshot, the instruction returns `AmmError::CalcPnlError` and — because the snapshot is only ever advanced inside the success branch — there is no unprivileged instruction that can resynchronize the two values. This mirrors the reported Hats-Zodiac bug class: a threshold/invariant check compares two independently maintained state values, one of which is never corrected on the failure path, so once they diverge the guarded function reverts forever.

### Finding Description
`calc_take_pnl()` requires `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount`, else it unconditionally errors: [1](#0-0) [2](#0-1) 

`calc_pc_amount`/`calc_coin_amount` are restored from `target.calc_pnl_x` / `target.calc_pnl_y`, which are only updated on the success path of this same function and of the callers (`Deposit`, `Withdraw`, `WithdrawPnl`) after a successful call: [3](#0-2) [4](#0-3) 

This function is invoked unconditionally by `process_deposit`: [5](#0-4) 

by `process_withdrawpnl`: [6](#0-5) 

and by `process_withdraw` for every status except `WithdrawOnly`: [7](#0-6) 

The pool's "live" reserve values used for the comparison are computed via `normalize_decimal_v2`, an integer-division (floor) decimal-normalization routine, while the stored snapshot advances through the same lossy floor/`restore_decimal` round trips on every deposit/withdraw: [8](#0-7) 

Because every branch that legitimately updates `calc_pnl_x`/`calc_pnl_y` performs `checked_sub`/`checked_add` combined with truncating decimal conversions (see the post-deposit and post-withdraw updates), repeated legitimate deposit/withdraw activity accumulates rounding error between the tracked snapshot and the true reserve product: [9](#0-8) [10](#0-9) 

Once the true (normalized) `x*y` value dips below the stored `calc_pnl_x*calc_pnl_y`, `calc_take_pnl` starts returning `AmmError::CalcPnlError` on every subsequent call. Since neither `Deposit`, `Withdraw` (outside `WithdrawOnly` status), nor `WithdrawPnl` can succeed without first passing this check, and none of them can write a corrected/reconciled snapshot except via this same guarded success path, the pool becomes permanently unable to process deposits or ordinary withdrawals — exactly analogous to the referenced report where `checkAfterExecution()`'s threshold comparison, once desynced, can never converge again through the paths available to unprivileged callers.

### Impact Explanation
If triggered, LPs cannot withdraw liquidity through the normal `Withdraw` path (only escapable if the privileged pool status is switched to `WithdrawOnly`, bypassing `calc_take_pnl` entirely), no new `Deposit` can occur, and `WithdrawPnl` (pnl owner sweep) is also permanently blocked. This is a freezing-of-funds condition reachable purely through normal, permissionless pool usage (deposits/withdraws/swaps altering vault balances relative to the tracked snapshot), with no unprivileged recovery instruction to resynchronize `target_orders.calc_pnl_x/y` to the true reserves.

### Likelihood Explanation
The condition depends on rounding/precision drift accumulating between the floor-based `normalize_decimal_v2`/`restore_decimal` conversions and the true reserve values across many deposit/withdraw cycles, or on any sequence of operations where the live invariant is decremented (e.g., via `need_take_pnl_*` growth without an intervening `WithdrawPnl`) faster than the tracked snapshot. It is not a single-transaction, attacker-fully-controlled trigger like the original report, but it is reachable purely by normal unprivileged pool activity over time and requires no privileged signer, making it a plausible medium-to-high likelihood latent DoS/freeze bug given enough usage or an adversarial sequence of small deposits/withdraws designed to maximize rounding loss.

### Recommendation
Do not hard-fail the guarded instructions when the invariant check fails; instead, treat it as "no pnl to take" (skip pnl extraction, proceed with the deposit/withdraw using the live reserves) rather than reverting the whole instruction, and/or clamp/re-derive `target_orders.calc_pnl_x/y` from live reserves whenever the computed values are inconsistent, so a rounding-induced dip below the last snapshot cannot brick core liquidity operations. Additionally, consider carrying remainder/precision instead of truncating in `normalize_decimal_v2`/`restore_decimal`, or use consistently rounding directions (ceiling vs floor) so the tracked snapshot cannot outpace true reserves.

### Proof of Concept
1. Initialize a pool via `Initialize2`; `target_orders.calc_pnl_x/y` is seeded from `normalize_decimal_v2` of the initial reserves.
2. Repeatedly call `Deposit` and `Withdraw` with small, decimal-misaligned amounts (e.g., pc_decimals/coin_decimals differing from `sys_decimal_value`) such that each `normalize_decimal_v2`/`restore_decimal` round trip truncates a small remainder in the direction that inflates `target_orders.calc_pnl_x * calc_pnl_y` relative to the true, live `total_pc_without_take_pnl * total_coin_without_take_pnl`.
3. Once `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount` in `calc_take_pnl` (`program/src/processor.rs:190-192`), every subsequent `Deposit`, `Withdraw` (non-`WithdrawOnly`), and `WithdrawPnl` call reverts with `AmmError::CalcPnlError`, and there is no unprivileged instruction path that updates `target_orders.calc_pnl_x/y` outside of these same reverting calls, permanently freezing normal deposit/withdraw functionality for the pool.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
