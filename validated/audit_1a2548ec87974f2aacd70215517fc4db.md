### Title
Webhook HMAC only signs the request body, allowing `shop` and `topic` header spoofing that bypasses tenant/topic binding - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively against that string. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never included in the signed content, yet `Registry.process` passes them unmodified into the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
which returns only the raw request body, ignoring the `shop`, `topic`, `webhook_id`, and `api_version` accessors that read from headers: [2](#0-1) 

`Registry.process` validates the HMAC over this signable string, then constructs `WebhookMetadata` directly from the unauthenticated header-derived `topic` and `shop` values: [3](#0-2) 

The `HmacValidator` only checks `hmac(secret, signable_string) == received_hmac`: [4](#0-3) 

The binding that should hold is: `HMAC valid ⟺ (body, shop, topic, webhook_id, api_version) is authentic and unmodified`. In reality it is only: `HMAC valid ⟺ body is authentic`. An unprivileged internet user who can obtain any single legitimately-signed `(body, hmac)` pair — trivially available since anyone can install the app on their own development/trial store and receive real Shopify-signed webhooks for their own shop — can replay that exact body/hmac pair to the app's public webhook endpoint while freely substituting the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` (or new `shopify-*`) headers to any value. `HmacValidator.validate` still succeeds because it never inspects those headers, and the app's registered `WebhookHandler#handle` receives a `WebhookMetadata` claiming an arbitrary victim shop and/or an arbitrary topic, even though Shopify never sent a webhook for that shop or topic.

This is exactly the "field acted on but not covered by the HMAC" pattern: `shop`/`topic` are acted upon (used for tenant identification and dispatch) but excluded from the signed bytes.

### Impact Explanation
This is a cross-tenant integrity break: the app cannot distinguish a webhook that genuinely originated for shop A from an attacker-forged request claiming to be for shop B, as long as the attacker can produce any real signed body (from their own shop or a previously observed webhook). Depending on the handler implementation (which the gem's own documentation encourages to trust `data.shop` and `data.topic` directly, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this enables injecting fabricated events attributed to another merchant's shop, or invoking a different topic's handler logic than what was actually delivered — a cross-tenant access/data-integrity violation.

### Likelihood Explanation
High. No credentials, TLS interception, or leaked secrets are required. Any developer/attacker who installs the app on a shop they control (a completely normal, unprivileged flow) can capture one legitimate `(body, X-Shopify-Hmac-Sha256)` pair from Shopify and then POST it directly to the app's public webhook callback URL with attacker-chosen `shop-domain`/`topic` headers.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the signed/verified content (or verify them independently against a trusted source, e.g. a known list of shops with active installations, and reject header/body mismatches), rather than relying solely on the raw body for HMAC verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers for topic `orders/create`, receiving a real Shopify webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B`), `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker replays the exact request to the app's public webhook endpoint, keeping body `B` and header `H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this succeeds because the signed string is only `B` (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...))` is invoked as if Shopify had genuinely sent this webhook for `victim-shop.myshopify.com`, even though it never did.
