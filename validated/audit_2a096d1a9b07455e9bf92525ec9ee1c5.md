### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and other identifying fields taken from HTTP headers that are never included in that HMAC computation. Because the HMAC does not bind the tenant identity (`shop-domain`) to the signed bytes, a party who can obtain one genuinely HMAC-valid webhook payload (e.g. by installing the app on their own store) can replay that exact body/HMAC pair while substituting the `shop-domain` header to make the library attribute the payload to a different (victim) shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all of which are read straight from unsigned headers — to build the `WebhookMetadata` that is handed to the app's business logic: [3](#0-2) [4](#0-3) 

The equality being broken is: `shop authenticated by HMAC` ≠ `shop used as the tenant key for the handler`. The HMAC only proves "this body was signed with the app's `api_secret_key`" — it says nothing about which shop the payload is for, since `api_secret_key` is shared across every shop that has installed the app, not per-tenant.

### Impact Explanation
Any user who can install the app on their own store (a normal, unprivileged action) will receive webhooks whose HMAC is valid for the app's shared secret. That same person can then resend the identical raw body + HMAC to the app's webhook endpoint with a forged `shopify-shop-domain` (or `x-shopify-shop-domain`) header naming a victim shop. `Registry.process` will accept the HMAC (since it only checks the untouched body) and invoke the app's webhook handler believing the data belongs to the victim tenant. Depending on what the host app's handler does with `WebhookMetadata#shop` (e.g., writing to shop-scoped storage, triggering side effects keyed by shop), this enables cross-tenant data injection/corruption — a boundary meant to isolate one merchant's data from another's is broken purely through this gem's verification logic.

### Likelihood Explanation
The attacker only needs the ability to install the app on a shop they control (or otherwise obtain one legitimately-signed webhook body) and network access to POST to the app's public webhook endpoint — no access token, `client_secret`, or `api_secret_key` is required. This is achievable by any ordinary Shopify merchant/developer able to install the target app.

### Recommendation
Bind the tenant identity into the authenticated material before trusting it, e.g. by cryptographically associating the `shop-domain` header (and/or `webhook_id`) with the body signature, or by requiring the app to independently verify that the `shop` value on an inbound webhook matches a shop for which the app has an active, previously-established installation/session (not merely "HMAC of body validates"). At minimum, document explicitly that `Registry.process`/`Utils::HmacValidator` only authenticate the body and that consuming apps must not treat the `shop` header as trusted tenant context without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint:
   ```
   POST /webhooks
   shopify-topic: orders/create
   shopify-hmac-sha256: <valid HMAC of raw_body computed with api_secret_key>
   shopify-shop-domain: attacker-shop.myshopify.com
   raw_body: {"id": 1, ...}
   ```
3. Attacker captures this exact request and resends it to the same endpoint, only changing the header:
   ```
   shopify-shop-domain: victim-shop.myshopify.com
   ```
   (`raw_body` and `shopify-hmac-sha256` left untouched.)
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes HMAC over `raw_body` only — it still matches, so validation passes: [5](#0-4) 
5. `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`, letting the attacker inject/attribute arbitrary (but replayed) webhook content to another tenant.
