### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` accepts the request whenever `Utils::HmacValidator.validate(request)` succeeds against that body-only signature. The `shop` (from `x-shopify-shop-domain` / `shopify-shop-domain`), `topic`, and `webhook_id` headers are read directly off the unauthenticated HTTP headers and forwarded to the app's handler as trusted, authenticated data — none of them are covered by the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns `@raw_body` only — the `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's `api_secret_key`, then does a constant-time compare against the `hmac` header: [3](#0-2) 

`Registry.process` trusts the request once this body-only HMAC check passes, and immediately hands the **unauthenticated** `request.shop` value to the app's handler as `WebhookMetadata#shop`: [4](#0-3) 

Because a single Shopify app's `client_secret` is shared across every shop that has installed it, any merchant that installs the app can, from their own store, trigger a legitimate webhook delivery and obtain a valid `(raw_body, hmac)` pair signed with the app's secret. Since the signature never covers the `shop-domain` header, that same attacker can replay the identical body+hmac pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and the gem forwards `data.shop = <victim-shop>` to the app's handler as if it were an authentic webhook for the victim tenant — even though the body content originated from the attacker's own store.

The binding that is broken, expressed as an equality that should hold but doesn't:
`shop_covered_by_hmac == shop_delivered_to_handler` — the gem asserts this equality is true (by only exposing a "verified" `Request` object after HMAC validation) but in fact `shop_covered_by_hmac` is undefined (not part of the signed bytes) while `shop_delivered_to_handler` is attacker-controlled header data.

### Impact Explanation
This is a cross-tenant data/identity confusion: the app's webhook handler is expected to treat `data.shop` as the authenticated identity of the shop the event pertains to (per the library's own documentation, "the shop domain of the webhook"). Any app that uses `data.shop` to select which tenant's records to update, look up a stored session/access token for, or otherwise scope side effects, can be made to act on the wrong tenant using attacker-supplied body content, purely because the merchant is capable of registering the app on their own store and thus obtaining a validly-signed webhook. This matches the "field acted on but not covered by the HMAC" bug class from the reference report and results in cross-tenant access/effects without any credential compromise.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who can install the target app on a shop they control (a normal, permission-less action for any Shopify Partner/merchant). No access token, `api_secret_key`, or privileged account is required — only the ability to install the app once to receive one legitimate webhook delivery, after which the (body, hmac) pair can be replayed indefinitely against the same endpoint with arbitrary shop headers.

### Recommendation
Bind the shop identity into the verified signature material, or otherwise re-authenticate the shop header:
- Extend `to_signable_string` (or add a separate check in `Registry.process`) to incorporate the `shop-domain` header (and ideally `topic`/`webhook_id`) into the HMAC computation, if Shopify's delivery signing scheme is updated to support this, or
- Have `Registry.process` cross-check `request.shop` against the set of shops that are known to have valid, stored sessions/webhook registrations for that specific `webhook_id`/topic combination before invoking the handler, and
- Document prominently that `data.shop` from `WebhookMetadata` is not cryptographically bound by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., cross-referencing against the app's own session store).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, so the app's webhook endpoint receives a legitimate webhook, e.g. for `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)` — see `lib/shopify_api/utils/hmac_validator.rb` `compute_signature`.
2. Attacker replays an HTTP POST to the same app webhook route with the identical raw body `B` and identical `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` parses `shop` from the (attacker-controlled) header, per `lib/shopify_api/webhooks/request.rb` lines 20-23.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `B` and matches `H` — validation succeeds (`lib/shopify_api/webhooks/registry.rb` line 190; `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the app to process attacker-supplied body content under the victim shop's identity.
