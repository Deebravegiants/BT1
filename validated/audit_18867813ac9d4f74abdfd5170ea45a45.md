### Title
Potential underflow panic in `calc_take_pnl` due to decimal-precision mismatch between guard check and subtraction operands - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` guards a subsequent subtraction with an inequality check performed on decimal-*restored* values, but then performs the actual subtraction on decimal-*normalized* values. Because the two decimal-conversion helpers (`normalize_decimal_v2` / `restore_decimal`) are not exact inverses (they use floor integer division), the guard does not strictly guarantee that the subtrahend is smaller than the minuend in the domain where the subtraction actually happens. This can lead to an unchecked `.unwrap()` panic on `checked_sub`, analogous to the reported "potential underflow" bug class in the external report.

### Finding Description
In `Processor::calc_take_pnl`: [1](#0-0) 
the code computes `calc_pc_amount`/`calc_coin_amount` by *restoring* `target.calc_pnl_x`/`target.calc_pnl_y` from the pool's internal "system decimal" representation back to native decimals via `Calculator::restore_decimal`, and compares `pool_pc_amount * pool_coin_amount` (raw vault amounts) against `calc_pc_amount * calc_coin_amount` (restored amounts) to decide whether pnl can be taken.

If the check passes, the function proceeds to compute `x2`/`y2` and subtract them from `x1`/`y1`, but `x1`/`y1` here are the *normalized* (system-decimal) representations of the same vault amounts, not the native ones used in the guard: [2](#0-1) 
```
let x2_power = Calculator::calc_x_power(target.calc_pnl_x.into(), target.calc_pnl_y.into(), x1, y1);
let x2 = x2_power.integer_sqrt();
let y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap();
let diff_x = U128::from(x1.checked_sub(x2).unwrap().as_u128());
let diff_y = U128::from(y1.checked_sub(y2).unwrap().as_u128());
```

`normalize_decimal_v2` and `restore_decimal` both use floor integer division: [3](#0-2) 
so converting native→normalized→native (or vice versa) is lossy and not a perfect round-trip whenever `sys_decimal_value` is not an exact power-of-ten multiple/divisor of `10^native_decimal`. As a result, the inequality validated in the *restored/native* domain (line 190-192) does not mathematically guarantee `x1 >= x2` in the *normalized* domain used for the actual subtraction. When rounding pushes `x2` (or `y2`) marginally above `x1` (or `y1`), the `checked_sub(...).unwrap()` calls at lines 213-214 will panic instead of returning a handled `AmmError`.

`calc_take_pnl` is invoked from the unprivileged, user-reachable `Deposit` and `Withdraw` code paths: [4](#0-3) [5](#0-4) 
as well as the same-pattern re-derivation used again inside `process_deposit`/`process_withdraw` when updating `target_orders.calc_pnl_x`/`calc_pnl_y` with further unguarded `checked_sub(...).unwrap()` calls: [6](#0-5) [7](#0-6) 

### Impact Explanation
If a pool's rounding state reaches a point where the normalized-domain comparison diverges from the native-domain guard, any `Deposit` or `Withdraw` instruction that triggers `calc_take_pnl` will panic (program abort) instead of failing gracefully with an `AmmError`. Because this is a deterministic function of the current on-chain state (vault balances vs. `target_orders.calc_pnl_x/y`), once the pool enters such a state, every subsequent `Deposit`/`Withdraw` call reaching this code path would revert, effectively freezing user/LP funds in the pool (unable to deposit or withdraw) until/unless the state changes in a way that resolves the discrepancy. This matches the "permanent freezing of user or LP funds" impact class.

### Likelihood Explanation
The guard check and the subtraction operate on values converted through two independent, non-invertible integer-division decimal conversions (`normalize_decimal_v2` and `restore_decimal`). Any pool configured with `sys_decimal_value`/`pc_decimals`/`coin_decimals` combinations that are not exact powers of ten of each other (which is common, since `sys_decimal_value` is configurable per-pool) is susceptible to rounding divergence over repeated deposit/withdraw/swap cycles that alter vault balances and `calc_pnl_x/y` incrementally. This does not require a privileged signer, malicious validator, or off-chain component — it can be reached purely through normal `Deposit`/`Withdraw` transactions by any user, though it depends on the pool's accumulated rounding state reaching the specific edge condition, so it is not guaranteed on every call.

### Recommendation
Perform the guard comparison and the actual subtraction in the same numeric domain (either both in native decimals or both in normalized/system decimals), and replace all `checked_sub(...).unwrap()` calls in `calc_take_pnl` (and the analogous ones in `process_deposit`/`process_withdraw`) with `checked_sub(...).ok_or(AmmError::CheckedSubOverflow)?` so that a residual rounding mismatch results in a clean instruction failure rather than a program panic.

### Proof of Concept
A full PoC requires simulating `AmmInfo`/`TargetOrders` state with specific `sys_decimal_value`/`pc_decimals`/`coin_decimals` values and a sequence of deposits/withdraws that drift `calc_pnl_x`/`calc_pnl_y` relative to vault balances until the native-domain check at [8](#0-7)  passes while the normalized-domain subtraction at [9](#0-8)  underflows. I was not able to execute/fuzz this in the current environment (no filesystem/terminal access) to produce concrete input values that trigger the panic; a Devin session with repository and terminal access would be needed to run the existing test harness (e.g., extending `test_calc_pnl_precision`/`test_calc_take_pnl` in `program/src/processor.rs`) to search for such a divergent state and confirm the panic empirically.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
