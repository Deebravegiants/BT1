### Title
SimplexPaymaster prices ERC-20 gas tokens with a single Chainlink feed and no depeg/deviation check, letting a depegged fee token drain the paymaster's EntryPoint deposit - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` computes the ERC-20 amount an ERC-4337 UserOp must pay for gas from two Chainlink feeds — `nativeOracle` (native/USD) and the registered token's `tokenOracle` (token/USD) — combined in `_tokenPrice`. Like the JOJOOracleAdaptor case where BTC/USD is used to price WBTC with no accounting for WBTC/BTC depeg, this contract trusts the token/USD feed's answer as the true market value of the registered ERC-20, with only a staleness/positivity check (`_getOraclePrice`) and no sanity bound against the token's actual peg or a secondary source.

### Finding Description
`_tokenPrice` (evm/src/utils/SimplexPaymaster.sol:653-658) computes:
```
tokenPrice = (nativeUsd * 10^tokenDecimals * (10000+markupBps)) / (tokenUsd * 10000)
```
`_getOraclePrice` (lines 662-676) validates only that the answer is positive and not stale (`maxOracleAge`); it performs no comparison against a reference/spot price and no deviation/circuit-breaker check. `_fetchDetails` (524-556) uses this `tokenPrice` directly to size the ERC-20 prefund pulled from the UserOp sender/solver via `transferFrom` or `Permit2.permitTransferFrom` (`_prefund`, 563-610), and `PaymasterERC20._postOp` uses the same price to compute the final charge, funded out of the paymaster's real native `EntryPoint` deposit.

If a registered fee token depegs from the price implied by its configured Chainlink feed (e.g., a wrapped/bridged stablecoin or wrapped asset whose designated oracle continues reporting the peg price after a bridge/custodian compromise, exactly the WBTC/BTC-feed scenario in the source report), `tokenUsd` stays inflated relative to the token's real market value. Because `tokenPrice` is inversely proportional to `tokenUsd`, an inflated `tokenUsd` produces an artificially *low* `tokenPrice`, meaning the contract charges fewer real-value ERC-20 units than the gas actually costs. The user pays with a now-worthless (or reduced-value) token while the paymaster sponsors full-value native gas from its `EntryPoint` deposit.

### Impact Explanation
This is a fund-drain path reachable by any unprivileged UserOp sender who can supply a registered token in `paymasterData` (mode `0x00`/`0x02`). No governance action or admin misbehavior is required at exploitation time — the contract's own price derivation, once a registered token's peg breaks (bridge hack, depeg event, stale feed floor), directly lets attackers pay negligible real value for real ETH-denominated gas sponsorship, draining the paymaster's `EntryPoint` stake/deposit funded by the treasury. This matches "concrete theft ... unbacked mint" class impact and is Medium severity, consistent with the original finding's rating, since it requires an external depeg precondition but the contract has no mitigating control (deviation check, secondary oracle, or pause) once that precondition occurs.

### Likelihood Explanation
Likelihood is moderate: it requires a depeg event for a token that governance registered with a Chainlink feed (per the contract's own doc comment, "any token with a Chainlink feed"). Whenever a wrapped/bridged asset is registered rather than a canonical stablecoin, this becomes directly analogous to the WBTC/BTC scenario in the source report. The docstring acknowledges "a malicious oracle" only in the context of bounding permit sizes (a few dollars) — this does not prevent the loss, only slows accumulation; an attacker can repeat the underpriced-gas cheat across many UserOps to drain the deposit over time.

### Recommendation
- Cross-check the token/USD Chainlink answer against a secondary source (e.g., a Uniswap TWAP or a second oracle) and revert or clamp the price when the two diverge beyond a configured threshold, mirroring the recommendation in the source report.
- Alternatively, cap `tokenPrice` deviation per update and add a circuit breaker (kill-switch already exists via `_deactivateToken`, but there is no automatic trigger) that a permissionless watcher/relayer can invoke when a registered token's oracle price deviates materially from spot/TWAP.
- Document and enforce that only tokens whose Chainlink feed directly tracks *that specific token's* market price (not a proxy/underlying asset's feed) may be registered, and add an on-chain check when possible (e.g., verifying feed description matches token symbol) as a defense-in-depth measure.

### Proof of Concept
1. Governance registers a wrapped/bridged token `WTOKEN` via `RegisterToken`, pairing it with a Chainlink feed that tracks the underlying reference asset's USD price (`_registerToken`, evm/src/utils/SimplexPaymaster.sol:387-404).
2. The `WTOKEN` bridge/custodian is compromised and `WTOKEN` depegs to a fraction of the referenced asset's value on the open market, while the registered Chainlink feed keeps reporting the pre-depeg (reference-asset) price because it was never designed to track `WTOKEN` specifically.
3. An attacker acquires cheap depegged `WTOKEN` and submits UserOps using mode `0x00`/`0x02` paymasterData naming `WTOKEN`. `_fetchDetails`/`_tokenPrice` (lines 524-556, 653-658) computes a `tokenPrice` based on the stale/incorrect feed, understating the true cost of gas in `WTOKEN` terms.
4. `_prefund`/base `PaymasterERC20` logic pulls the computed (deflated) `WTOKEN` amount from the attacker while the `EntryPoint` deposit pays out full native-value gas on the attacker's behalf (`_postOp`, inherited).
5. Repeating this across many UserOps drains the paymaster's `EntryPoint` deposit/stake for a fraction of its real cost, at the expense of the treasury that funded it.
