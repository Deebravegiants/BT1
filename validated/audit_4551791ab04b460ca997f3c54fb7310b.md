### Title
Permissionless phantom-bid weighted-median price manipulation lets a low-capital actor skew IntentGateway swap quotes (`quotePhantomFill` → `weightedMedian` → `PhantomOrderPriceSnapshotV2`) — ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
Hyperbridge's `PhantomSnapshotIntentQuoteStrategy` prices real USDC↔cNGN swaps off a `medianPrice` that is derived exclusively from *phantom* order bids — quotes that solvers post but never actually execute. Any account that can EIP-7702-delegate to a `SolverAccount` and hold a comparatively small amount of the leg's output token can dominate the liquidity-weighted median and force the published price to an arbitrary value, exactly mirroring the H-3 "manipulating funding rates" attack vector from the Hubble audit, where a privileged matcher skewed a price-TWAP by placing extreme-priced orders. Here no privilege is required at all, and — unlike Hubble's validator, who had to pay the spread on a real matched trade — the manipulator pays nothing, because phantom bids are quotes, not executions.

### Finding Description
Each pricing interval, `pallet-intents-coprocessor` opens a phantom order per configured chain and lets any delegated `SolverAccount` submit a `place_bid` quote for it (`modules/pallets/intents-coprocessor/src/lib.rs`, `place_bid` extrinsic). Because a phantom order is never filled (`sdk/packages/simplex/src/strategies/fx.ts`, `quotePhantomFill`: *"Phantom orders are probes that never execute; we only need the price signal"*), quoting one costs nothing beyond holding balance: [1](#0-0) 

The indexer aggregates every bid for the commitment with `aggregatePhantomBids` and picks the price with `weightedMedian`, which is a **selection**, not a blend — it returns one bidder's exact quoted integer: [2](#0-1) 

The weight backing a quote is only the solver's balance of that leg's output token on the destination chain — inventory that is read but never spent, never escrowed, and reusable bid after bid: [3](#0-2) 

The project's own flow doc states the consequence explicitly: *"a solver holding over half the leg's weight sets the published price verbatim"*: [4](#0-3) 

That `medianPrice` is then consumed directly to price real, capital-committing orders: `PhantomSnapshotIntentQuoteStrategy.quoteSnapshot` computes `amountOut = netAmountIn * snapshot.medianPrice / snapshot.standardAmount` for a real USDC↔cNGN swap request: [5](#0-4) 

Users are told to use these exact amounts as `order.inputs`/`output.assets` when calling `placeOrder`, i.e., the manipulated rate becomes the escrowed, on-chain committed terms of a real intent: [6](#0-5) 

Bid verification (`isVerifiedSolverBid`) only checks that the bid's signature is valid over the phantom order's `userOpHash` and that the sender is EIP-7702-delegated to a configured `SolverAccount` address — both of which are permissionless, self-servable properties (anyone can delegate their own EOA to the public `SolverAccount` implementation): [7](#0-6) 

There is no check that the quoting party is an economically meaningful market maker, no cost to repeatedly requoting each interval, and no bound preventing one well-capitalized (but not necessarily liquid-at-scale) delegated account from being the single dominant bidder on a thin leg.

### Impact Explanation
This is the direct analog of the Sherlock H-3 finding's "manipulation of funding rate" vector: an actor with no special protocol privilege other than possessing the right token balance and delegating to `SolverAccount` can dictate the published exchange rate that real users' swap orders are priced and escrowed against. A user calling `quoteIntent({strategy: "phantom_snapshot", ...})` and then `placeOrder` with the returned `amountIn`/`amountOut` locks in a rate that the manipulator chose, not a market rate. Any solver (including the manipulator or a colluding party) can then fill the resulting order at the manipulated rate for a guaranteed profit at the user's expense — concrete theft of funds via mispriced escrow, the same mechanism the original report flagged (validator front-running a liquidation match at an off-market price). Unlike the original Hubble scenario — where the Sherlock judge downgraded the funding-manipulation vector to Medium specifically because "it will also be costly to do so" — here the manipulation is essentially free per round (only inventory, never capital consumed), which argues for at least the same, if not higher, severity.

### Likelihood Explanation
No privileged role is required: any EOA can be EIP-7702-delegated to the public `SolverAccount` and submit `place_bid` extrinsics. On thin legs (the same "low liquidity" precondition the Hubble sponsor and judges accepted as sufficient to make the funding-manipulation vector valid, albeit Medium), a single account with a comparatively modest balance of the leg's output token can already exceed "over half the leg's weight" and set the price outright. Because phantom bids never execute and never lock capital, the same balance can be reused indefinitely across bidding windows, making sustained manipulation cheap relative to a scheme requiring real matched trades.

### Recommendation
- Do not let `PhantomOrderPriceSnapshotV2`/`medianPrice` be consumed as an executable, capital-committing rate for real swaps without an independent sanity bound (e.g., deviation cap against `IndexedRateIntentQuoteStrategy`/DEX-quoted rates, or a minimum bidder-count/diversity requirement instead of a single-bidder-can-dominate weighted-median selection).
- Require the weight backing a phantom quote to reflect actual committed/locked capital (e.g., a bonded quote or a small mandatory real fill) rather than a freely re-readable, unspent balance snapshot, so repeated cost-free requoting cannot dominate the median every interval.
- Consider widening the weighting beyond a single dominant bidder (e.g., cap any one solver's contribution to some fraction of total weight) so no single delegated account can set the price verbatim regardless of how thin the leg's liquidity is.

### Proof of Concept
1. Deploy or reuse the public `SolverAccount` implementation on the destination chain (e.g., Base) and EIP-7702-delegate an EOA to it — this is unprivileged and available to anyone per the documented Solver-Selection flow.
2. Acquire a modest balance of the leg's output token (e.g., cNGN) on the destination chain — enough to exceed half the total weight of legitimate bidders on that leg, which is realistic on a thinly-traded pair such as USDC/cNGN.
3. When `pallet-intents-coprocessor` opens the interval's phantom order (`PhantomOrderV2`), submit a `place_bid` extrinsic (`IntentsCoprocessor::placeBid`) with a `PackedUserOperation` whose `fillOrder` calldata quotes an extreme `outputs[i].amount` (e.g., far below fair value) for that leg, signed as required by `isVerifiedSolverBid`.
3. When `PhantomBidWindowExhausted` fires, `aggregatePhantomBids`/`weightedMedian` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:709-724`) selects this bid's price verbatim because the attacker's weight (its output-token balance) exceeds half the leg's total weight, and `handlePhantomOrderPrices.handler.ts` persists it into `PhantomOrderPriceSnapshotV2.medianPrice`.
4. Any user calling `IntentGateway.quoteIntent({ strategy: "phantom_snapshot", tokenIn: USDC, tokenOut: cNGN, amountIn })` receives `amountOut` computed from the manipulated `medianPrice` (`phantomSnapshot.ts:88-94`) and places a real order with that mispriced `output.assets` amount.
5. The attacker (or a colluding solver) fills the resulting order via `fillOrder`, capturing the difference between the manipulated rate and the fair-market rate as risk-free profit, extracted directly from the user's escrowed input tokens.

```typescript
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
```

```text
### Protocol fees

Before escrowing, the contract deducts a protocol fee from each input amount:

```
protocolFee = input.amount × protocolFeeBps / 10_000
reducedAmount = input.amount − protocolFee
```

The fee is retained in the gateway as dust (emitting `DustCollected`), and per-destination overrides take precedence over the global `protocolFeeBps` when set. Current deployments charge **5 bps (0.05%)**. For a 100 USDC input:

| Item | Amount |
| --- | ---: |
| USDC transferred from your wallet | 100.000000 USDC |
| Protocol fee: `100 × 5 / 10,000` | 0.050000 USDC |
| Amount actually escrowed and offered to solvers | 99.950000 USDC |

The commitment hash is computed over the **fee-reduced inputs** — solvers read the reduced amounts from the `OrderPlaced` event and only need to match those. The fee is deducted at placement and is **not refunded** if the order expires, receives no bids, or is cancelled; a cancellation returns the remaining escrow and `order.fees`, but not the protocol fee.

<Callout type="warn">
Do not build an order by reducing the input yourself to account for the protocol fee. Send the gross input amount and use the amounts returned by `quoteIntent()`. The quote prices the fee-reduced escrow amount; reducing it again would make the order smaller than intended.
</Callout>
```
