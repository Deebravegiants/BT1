### Title
Webhook `shop-domain` and `topic` identifiers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop` (tenant identifier) and `topic` fields used to route and process the webhook are taken from unauthenticated HTTP headers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop`, `#topic`, `#webhook_id`, `#api_version` are all read straight from headers with no cryptographic binding to that body: [1](#0-0) 

`Registry.process` validates only the HMAC of the body, then immediately trusts the header-derived `shop` to construct `WebhookMetadata` and dispatch it to the handler: [2](#0-1) 

`HmacValidator.validate_signature` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)`, which for webhooks is `HMAC(api_secret_key, raw_body)` — `shop`, `topic`, and `webhook_id` are never part of the signed material: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop used to route/process the webhook`. Because `api_secret_key` is shared by the app across all shops that install it (it is not shop-specific), a single valid `(raw_body, hmac)` pair is valid for *any* `shop-domain` header value. An attacker who controls a shop that has the app installed can capture a legitimate `(body, hmac)` pair from their own store's webhook delivery, then replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header of a victim shop. `HmacValidator.validate` returns `true` (the body's signature is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data came from the victim's shop.

### Impact Explanation
This breaks the tenant-isolation boundary the gem is expected to provide for webhook processing: an app's webhook handler (and by extension the host application, which typically uses `WebhookMetadata#shop` to select which merchant record/session to act on) can be made to process attacker-controlled data under a victim shop's identity — a cross-tenant confusion/attribution issue reachable without any privileged credential, only knowledge of the app's public webhook endpoint and control of one's own (attacker) shop's webhook traffic.

### Likelihood Explanation
The attacker only needs to run their own shop with the target app installed (a normal unprivileged, un-trusted actor from Shopify's perspective) to obtain a valid `(raw_body, hmac)` pair, and a generic HTTP client to replay it with a modified header. No secrets, tokens, or elevated access are required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material used for verification, or otherwise cross-check the header-derived `shop` against an out-of-band trusted source (e.g., verify the shop is one that has an active install/session for this app) before dispatching to handlers. At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated header values that must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify delivers `raw_body` B with header `x-shopify-hmac-sha256: H = HMAC(api_secret_key, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only recomputes `HMAC(api_secret_key, B)` per [3](#0-2) , ignoring the `shop` header.
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed B, ...)` to the app's handler per [4](#0-3) , causing the host app to process attacker-supplied content attributed to the victim tenant.
