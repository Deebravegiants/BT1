### Title
`ShopifyAPI::Webhooks::Request#shop` is read from an unauthenticated header not covered by the HMAC signature - (File: `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that host applications use to identify which tenant a webhook belongs to, but this value is read from the `X-Shopify-Shop-Domain` header, which is **not** included in the HMAC signature computation. The signature only covers the raw request body.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `hmac` and `to_signable_string`. The signable string is defined as only the raw body: [1](#0-0) 

But the `shop` accessor used for tenant identification is pulled straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) HTTP header, which plays no part in the signature at all: [2](#0-1) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it only against the `hmac` field returned by the object — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

This breaks the intended binding: **shop header value == shop the HMAC was computed for**. Because `shop` is not bound by the HMAC, an attacker who can produce (or replay) a request with a *valid* `hmac-sha256` header for a given body (e.g., by replaying a legitimate webhook delivery captured for shop A, or by controlling both body and header value in an environment where the header isn't independently verified downstream) can set an arbitrary `shop-domain` header value while keeping the body/HMAC pairing valid. Any host application that trusts `Webhooks::Request#shop` (as the gem's own API surface implies is safe once `hmac_valid?`/`HmacValidator.validate` passes) to select which merchant's session/data to act on will process the webhook under the wrong tenant.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem's documented verification primitive (`HmacValidator.validate`) gives host applications false assurance that *all* attributes of the `Request` object, including `shop`, are authenticated, when in fact only the raw body is covered. A host application acting on `request.shop` post-validation (the natural and only path the gem exposes for determining the webhook's tenant) can be tricked into cross-tenant data access/processing.

### Likelihood Explanation
Exploitation requires the attacker to obtain a body/HMAC pair that validates (e.g. a previously observed legitimate webhook payload for shop A is technically forgeable in body-and-hmac terms only if secret is known, but the header spoof itself does not require secret knowledge at all — the HMAC only ever validates `@raw_body`, so **any** valid captured webhook (body+hmac) from *any* shop can be replayed with a rewritten `shop-domain` header pointed at a victim shop, and it will still pass `HmacValidator.validate`). No `api_secret_key`, access token, or privileged access is needed by the attacker beyond capturing one legitimate webhook delivery for their own shop.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them to the payload) so that `HmacValidator.validate` fails if any of these header-derived attributes are altered independently of the body and its original HMAC.

### Proof of Concept
```ruby
# Attacker owns a legitimate Shopify shop "attacker.myshopify.com" and
# receives a real webhook there, capturing raw_body + valid hmac-sha256 header.
captured_body = '{"id":123,"note":"legit payload"}'
captured_hmac_header = "<valid base64 hmac for captured_body computed with the merchant app's secret>"

# Attacker replays the exact same body/hmac pair to the app's webhook endpoint,
# but rewrites the shop-domain header to point to a victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not part of HMAC input
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because only @raw_body is checked
request.shop # => "victim-shop.myshopify.com" — trusted by host app, but never authenticated
```
