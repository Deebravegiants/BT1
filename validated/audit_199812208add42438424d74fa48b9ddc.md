### Title
Untrusted swap route can expose unrelated caller wallet tokens - (`File: contracts/controller/src/strategies/swap.rs`)

### Summary
`swap_collateral` and `swap_debt` accept caller-supplied opaque `StrategySwap` bytes and forward them to the configured router. [1](#0-0) [2](#0-1)  The controller bounds only its own input-token transfer, while route-selected third-party code can invoke additional operations under the caller's authorization tree. [3](#0-2)  This is analogous to processing a malicious qcow image: opaque attacker-controlled data causes the host to expose resources outside the intended virtual disk boundary.

### Finding Description
`StrategySwap` is defined as raw `Bytes`, with no controller-visible structure, destination validation, or venue allowlist. [4](#0-3)  `swap_collateral` authenticates the caller, verifies account ownership or delegation, withdraws collateral, and passes the caller-supplied payload into the swap helper. [5](#0-4) [6](#0-5)  `swap_debt` follows the same pattern after borrowing the replacement debt asset. [7](#0-6) 

`swap_tokens` forwards the unmodified bytes to `SwapAggregatorInterface::execute_strategy`. [8](#0-7)  The controller snapshots and validates only the selected `token_in` and `token_out` balances. [9](#0-8) [10](#0-9)  It does not constrain which pool or token contracts the route invokes, and those checks do not observe transfers of unrelated caller-held tokens.

The controller's invoker-contract authorization covers exactly one transfer from the controller to the router, but it does not limit authorization invocations that route code associates with the user's `require_auth` tree. [11](#0-10)  Consequently, a malicious route venue can call `wallet_token.transfer(victim, attacker, amount)`; transaction simulation can record that transfer as a child of the victim's `swap_collateral` authorization, and signing the poisoned tree authorizes it. [12](#0-11) 

### Impact Explanation
A crafted route can steal arbitrary tokens held by the victim's wallet, including assets never supplied to or listed by the lending protocol. [12](#0-11)  The intended collateral swap can still return positive measured output and pass the account's final risk checks, so the protocol-level swap succeeds while the unrelated wallet transfer also executes. [10](#0-9)  The loss is not bounded by `amount_in`, router output checks, or the lending position's collateral value.

### Likelihood Explanation
Exploitation requires the victim to invoke a malicious route and sign an authorization tree containing the extra token transfer. [13](#0-12)  A malicious quoting interface, copied route payload, or compromised route source can construct such a payload without privileged access, while relying on the victim not decoding every nested authorization. [12](#0-11)  Because an honest route normally produces no caller-side child transfer, explicit authorization-tree validation can detect the attack, but the contract does not prevent the poisoned signature from being used.

### Recommendation
Do not allow opaque routes to execute arbitrary venue contracts during an invocation that carries the user's authorization. Prefer venue allowlisting and route decoding in a trusted boundary, or split the withdrawal and external route execution into separate transactions so no user authorization is available while unallowlisted code runs. Until contract-side isolation exists, clients must decode every signed authorization subtree and reject a strategy whose caller entry contains anything other than the expected controller invocation.

### Proof of Concept
1. Deploy an attacker-controlled contract exposing a route-compatible `swap` function that executes:
   ```rust
   token::Client::new(&env, &victim_wallet_token)
       .transfer(&victim, &attacker, &victim_wallet_balance);
   ```
2. Encode a `StrategySwap` route that calls that contract while still returning enough `new.asset` to satisfy the controller's positive-output check. [4](#0-3) [14](#0-13) 
3. Have the victim invoke:
   ```text
   controller.swap_collateral(
       caller = victim,
       account_id = victim_account,
       current = USDC_market,
       amount = supplied_usdc_amount,
       new = ETH_market,
       swap = malicious_route,
   )
   ```
   The entrypoint forwards the bytes unchanged. [15](#0-14) 
4. During execution, the route venue calls `victim_wallet_token.transfer(victim, attacker, victim_wallet_balance)`, which simulation records under the victim's `swap_collateral` authorization. [12](#0-11) 
5. If the victim signs the poisoned tree, the unrelated wallet token moves to the attacker while the collateral conversion completes normally. [16](#0-15)

```rust
/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
```

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
