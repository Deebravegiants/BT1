### Title
Outgoing ISMP dispatch reverts entirely when the configured UniswapV2 fee-swap router is paused/broken, permanently blocking native-fee message delivery - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch` (for both `DispatchPost` and `DispatchGet`) unconditionally routes any native-token (`msg.value`) fee payment through an external `IUniswapV2Router02.swapETHForExactTokens` call with no try/catch or fallback path. If that external router/pool (or a wrapper contract standing in for UniV3/UniV4, per `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol` and `UniV4UniswapV2Wrapper.sol`) is paused, drained of liquidity, or otherwise reverts, every user who tries to dispatch a message by paying with native currency has their transaction revert, with no way to complete the dispatch except falling back to the fee-token path (which requires holding and approving that ERC20 separately). The same unguarded external dependency exists in `IntentGatewayV2` order placement fee payment.

### Finding Description
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` both contain: [1](#0-0) [2](#0-1) 

When `msg.value > 0`, the function directly calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(...)` with no try/catch. The router address (`_hostParams.uniswapV2`) can be the real Uniswap V2 router, or a project-owned wrapper adapting UniV3/UniV4 pools, as shown by `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol` and `UniV4UniswapV2Wrapper.sol`, both of which forward to third-party routers (`IV3SwapRouter`/`IUniversalRouter`) that can independently be paused, have insufficient liquidity, or otherwise revert.

Because there is no fallback or error handling around this external call, any transient failure of the swap dependency — the underlying DEX pool being paused, drained, migrated, or reverting due to price/slippage checks — causes the entire `dispatch` call to revert. This blocks every attempt to submit an outgoing POST/GET request paid for in native currency, which is the primary "quote and pay" flow documented and tested throughout the SDK (`quote()` + `dispatch{value: ...}`).

The identical pattern (an unguarded external `swapETHForExactTokens` call feeding fee collection) also appears in `IntentGatewayV2.placeOrder`: [3](#0-2) 

This is directly analogous to the reported Aave issue: a core, unprivileged-user-reachable function (`deposit`/`withdraw` there, `dispatch`/`placeOrder` here) depends on an external DeFi protocol call that has no failure isolation, so any pause or malfunction of that external dependency makes the core function permanently revert for all callers using that payment path.

### Impact Explanation
This falls under the "a route unable to deliver messages" acceptance criterion: whenever the configured swap dependency for a given chain is paused/broken/illiquid, every relayer, application, or user attempting to dispatch a native-fee-paying POST/GET request on that `EvmHost` deployment is denied service — there is no other way for `dispatch` to succeed with `msg.value > 0`. Given that `quote()` + native `dispatch` is a first-class, widely-documented payment path (see `docs/content/developers/evm/api/idispatcher.mdx`), this can halt outgoing cross-chain messaging entirely from an affected chain for as long as the external swap venue remains impaired, which is a protocol-level denial of service on message delivery, not merely a minor inconvenience.

### Likelihood Explanation
Likelihood is moderate to high over the life of the protocol: the swap dependency is a third-party (or project-controlled wrapper around a third-party) AMM/router that can be paused by its own admin, drained via a large swap/exploit, migrated, or run out of the specific WETH/feeToken pool liquidity — none of which are under Hyperbridge's control. No malicious actor is required; it is triggered purely by depending on external infrastructure without a safety fallback, matching exactly the "audit-issue" class cited in the report (Aave `LendingPool.paused()` blocking `deposit`/`withdraw`).

### Recommendation
Wrap the `IUniswapV2Router02(...).swapETHForExactTokens(...)` calls in `EvmHost.dispatch` (both overloads) and in `IntentGatewayV2.placeOrder` in a try/catch (or a low-level `call` with success check), and on failure either: (a) revert with a clear, specific error rather than bubbling up an opaque router revert, and/or (b) provide a documented fallback allowing the caller to retry with the fee token directly instead of native value. At minimum, ensure a router failure cannot be silently conflated with user error, and consider allowing `HostManager`/governance to hot-swap `_hostParams.uniswapV2` to a working router without needing a full host upgrade, to recover availability quickly.

### Proof of Concept
1. Configure `EvmHost` (or `IntentGatewayV2`) with `_hostParams.uniswapV2` pointing at a Uniswap V2 router/pool for `WETH -> feeToken`.
2. Pause or drain liquidity from that pool (e.g., simulate via a malicious/paused router in a forge test, or fork-test against a real pool and remove liquidity/pause it, mirroring `evm/tests/foundry/ConfiguredWrapperForkTest.t.sol`'s `_assertSwapWorks` but forcing the swap call to revert).
3. Call `host.dispatch{value: fee}(DispatchPost{...})` as any unprivileged user.
4. Observe the entire transaction reverts due to the unguarded `swapETHForExactTokens` call, with no alternative path to complete the dispatch using native value — demonstrating the message cannot be sent through this payment route while the dependency is impaired.
