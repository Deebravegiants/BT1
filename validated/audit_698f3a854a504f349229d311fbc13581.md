### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The reported contract bug is a class of "field acted on but not covered by the binding check" — the withdraw preview used a formula that didn't match the value actually protected/enforced elsewhere. The analogous pattern in this gem is `ShopifyAPI::Webhooks::Request`: the HMAC signature only covers the raw request body, while the `shop` identity that the registry hands to the app's webhook handler is read from an unauthenticated header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that header at all: [2](#0-1) [3](#0-2) .

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately passes `request.shop` — the unauthenticated header value — into `WebhookMetadata` and on to the app's handler: [4](#0-3) .

`HmacValidator.validate_signature` compares `verifiable_query.hmac` against a signature computed only from `to_signable_string` (i.e., the body), never touching `shop`, `topic`, `webhook_id`, or `api_version`: [5](#0-4) .

The equality this design is supposed to guarantee is: *"shop that owns the webhook" == "shop the handler is told about."* Because only the body bytes are authenticated, that equality can be broken: any two requests carrying identical bodies (e.g., two different merchant shops both firing the same low/no-payload topic such as `app/uninstalled`, `shop/redact`, or any webhook whose body content is attacker-influenced/predictable) produce identical valid HMACs regardless of which shop the `shop-domain` header claims. The app's `client_secret`/`api_secret_key` is the same across every installed shop, so a legitimate webhook payload+HMAC pair captured for shop A remains a *valid* signature when replayed with the `shop-domain` header rewritten to shop B.

### Impact Explanation
If the host application (as documented, `WebhookMetadata.shop` is the field apps are expected to use to key their per-tenant data/session storage) trusts `data.shop` to determine which merchant's records to update, this allows cross-tenant data confusion/write: an attacker who can capture or predict one shop's HMAC-body pair can attribute that processed webhook event to a different shop identifier, since the gem's HMAC check never binds `shop` to the signature. This falls into the "cross-tenant access" impact category defined by the scope.

### Likelihood Explanation
Exploitability depends on the attacker being able to submit an HTTP request to the app's webhook endpoint with a header of their choosing and a body+HMAC pair that is valid for *some* shop — feasible when body content is static/predictable per topic (compliance webhooks, uninstall notifications, or any topic with minimal/fixed payload), or when an attacker who has legitimately received a webhook for their own shop (as an app-installing merchant) replays it against the endpoint with the `shop-domain` header altered. No `api_secret_key` or access token possession is required by the attacker; only a captured or guessed valid (body, hmac) pair for any tenant.

### Recommendation
Include the shop-domain (and ideally topic and webhook id) in the value that is HMAC-verified — mirroring how `AuthQuery#to_signable_string` binds `shop`, `host`, and other fields into the signed string: [6](#0-5) . At minimum, document/enforce that `WebhookMetadata.shop` must never be used as a trust boundary without independently confirming the shop has an active, matching session/installation record, since the gem itself does not bind that field cryptographically.

### Proof of Concept
1. App has two installed shops, `shop-a.myshopify.com` and `shop-b.myshopify.com`, sharing the same app `client_secret`.
2. Shopify sends a webhook for topic `X` to shop A with a fixed/predictable body `B` (e.g., an empty-body or well-known-body topic) and header `shopify-shop-domain: shop-a.myshopify.com`, HMAC `H = HMAC(secret, B)`.
3. Attacker (who is the operator of shop A, or who intercepts/observes this traffic) resends `{body: B, headers: {shopify-hmac-sha256: H, shopify-shop-domain: shop-b.myshopify.com, shopify-topic: X, ...}}` directly to the app's public webhook endpoint.
4. `Request#hmac` == `H`; `HmacValidator.validate` computes the same `H` from body `B` and accepts it (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` builds `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` from the spoofed header and invokes the handler as if the event came from shop B (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the event body actually belonged to shop A.
