### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing shop-identity spoofing across tenants - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant the payload belongs to. Because the shop identifier is never part of the signed material, any actor who can legitimately obtain one valid `(body, hmac)` pair for the app (e.g. by installing the app on their own store and triggering a webhook event) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. The signature still validates, and the host application's handler receives data attributed to the spoofed shop instead of the shop that actually produced it.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read directly from the (unsigned) header, independent of the signature computation: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the handler as the tenant identity, with no cross-check that the shop matches anything bound by the signature: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (the raw body in this case) and compares it to the supplied `hmac`, so it can never detect a tampered `shop-domain` header: [4](#0-3) 

The identity binding the gem should enforce is `shop_bound_by_signature == shop_acted_on`. Because the signature only covers the body, this equality never actually holds — the "shop acted on" is fully attacker-controlled bytes taken from a header, while the only thing cryptographically authenticated is that *some* installation of this app produced this body with the shared `api_secret_key`. Any merchant who installs the app (an unprivileged action available to anyone with a Shopify store) can capture one legitimate `(body, hmac)` pair from their own shop and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to any other shop that has installed the app. `Registry.process` will accept it as authentic and dispatch it to the handler as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook system is supposed to enforce: an attacker-controlled payload can be attributed to an arbitrary other tenant (cross-tenant access/confusion), which is exactly the class of impact called out as in-scope ("cross-tenant access"). Depending on what the host application's webhook handler does with `WebhookMetadata#shop` (e.g. updating billing state, GDPR data-erasure flows, order/customer records, or session bookkeeping keyed by shop), this can let one merchant inject or forge events attributed to a different merchant's shop.

### Likelihood Explanation
The prerequisite — installing the app on one's own store and receiving at least one real webhook — is trivial for any unprivileged Shopify merchant/developer to obtain, since this gem's `api_secret_key` is a single shared app-level secret used to sign webhooks for every installation, not a per-shop secret. No access token, `client_secret`, or privileged access is required; only a normal app installation and the ability to POST a crafted HTTP request with modified headers to the app's public webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed material, or independently verify that the `shop` header value corresponds to a shop the app has an active, previously-established session/installation for before trusting it in `WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated and must be cross-checked by the host application against known installed shops before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `products/update`), capturing the resulting request body `B` and its valid `x-shopify-hmac-sha256` value `H` (computed by Shopify using the app's shared `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (only checks header presence), and `Utils::HmacValidator.validate` succeeds because it only hashes `B`: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-supplied data as if it came from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
