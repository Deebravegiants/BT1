### Title
`DirectBridge.getCachedStorageDepositValue()` builds its LRU cache key by unseparated string concatenation, allowing collisions that make an unregistered destination look storage-registered - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`DirectBridge.getCachedStorageDepositValue()` derives its cache key as `` `${contractId}${accountId}` `` with no delimiter between the two fields. Because NEAR account IDs can contain dots and arbitrary alphanumeric segments, two different `(contractId, accountId)` pairs can concatenate to the identical string. This breaks the equality the cache is supposed to preserve: "the cached `[minStorageBalance, userStorageBalance]` pair belongs to *this* token contract and *this* destination account." A collision lets a request for one `(token, destination)` pair be served the cached, "storage sufficient" result computed for a completely different `(token, destination)` pair.

### Finding Description
`estimateWithdrawalFee()` calls:
```
const [minStorageBalance, userStorageBalance] =
    await this.getCachedStorageDepositValue(
        tokenAccountId,
        args.withdrawalParams.destinationAddress,
    );

    const cached = this.storageDepositCache.get(key);
    if (cached !== undefined) {

    }
    ...
    if (result[1] >= result[0]) {
        this.storageDepositCache.set(key, result);

    return result;

``` [2](#0-1) 

Note that entries are only ever cached when `userStorageBalance >= minStorageBalance`, i.e. the cache only ever stores "storage is already sufficient, no deposit required" outcomes. `contractId` and `accountId` are simply concatenated with no separator (e.g. `":"`), so a pair `(contractId="a", accountId="b.near")` and a pair `(contractId="a.near"... wait it collides at the string level `"ab.near"`)` produce the exact same cache key as any other `(contractId', accountId')` whose concatenation is also `"ab.near"`. Since `destinationAddress` is fully attacker-controlled and `contractId` is chosen by picking which supported NEP-141 token to withdraw, an attacker can pick both fields to make the concatenation match a previously-cached (and "sufficient") entry belonging to a different token/account pair.

Once the collision hits, `estimateWithdrawalFee()` treats `minStorageBalance <= userStorageBalance` as true and returns `storageDepositFee: 0n`:
```
if (minStorageBalance <= userStorageBalance) {
    return { amount: 0n, quote: null, underlyingFees: { [RouteEnum.NearWithdrawal]: { storageDepositFee: 0n } } };
}
``` [3](#0-2) 

That fee then flows into `createWithdrawalIntents()`, which attaches `storageDeposit: 0` to the built `ft_withdraw`/`ft_transfer_call` intent:
```
const intent = createWithdrawIntentPrimitive({
    assetId: args.withdrawalParams.assetId,
    destinationAddress: args.withdrawalParams.destinationAddress,
    amount: args.withdrawalParams.amount,
    storageDeposit: getUnderlyingFee(args.feeEstimation, RouteEnum.NearWithdrawal, "storageDepositFee"),
    ...
});
``` [4](#0-3) 

The equality that is broken: "the storage-deposit sufficiency fact reported for `(token, destination)` was actually computed for `(token, destination)`" — not for some other pair whose concatenation happens to collide.

### Impact Explanation
If the withdrawal proceeds with `storageDeposit: 0` for a destination account that is not actually registered on the real token's NEP-141 contract, the on-chain `ft_transfer_call`/withdraw will typically fail (most NEP-141 implementations panic on transfer to an unregistered account), causing the whole withdrawal transaction to fail. That leaves the withdrawal in a failed/stuck state requiring the user or integrator to retry with a corrected estimate — matching the "withdrawal stuck until manual intervention" bucket. In environments where the token contract instead silently accepts (or where storage is later paid by someone else), this could also translate into an under-collected fee (the user/protocol effectively subsidizes storage registration that should have been billed), which falls into "fee error" territory. Either way it's a violation of the fee/status computed by the SDK vs. the real on-chain requirement for the destination actually being withdrawn to.

### Likelihood Explanation
Exploitability requires an attacker to know or predict a previously-cached `(contractId, accountId)` key from another request (their own prior request or another user's), and then choose their own `(token, destinationAddress)` such that the concatenated strings coincide exactly. Since `contractId` is limited to the small set of supported NEP-141 tokens and `destinationAddress` is fully attacker-chosen (any syntactically valid NEAR account id, up to 64 chars), constructing a colliding suffix is straightforward once a target cached pair is known — an attacker can even self-seed the cache first with a cheap "sufficient" pair, then immediately issue a second request in a colliding shape. The cache has a 1-hour TTL and process-lifetime scope, giving a wide window. This requires no privileged access, only calling the public SDK APIs (`estimateWithdrawalFee`), so likelihood is Medium-to-High for a determined actor, though it depends on precise string crafting.

### Recommendation
Use a delimiter that cannot appear in valid NEAR account IDs' concatenation ambiguity, or better, use a structured/hashed key or a `Map`/`LRUCache` keyed by a tuple/hash, e.g.:
```ts
const key = `${contractId}:${accountId}`; // still needs a bijective separator scheme, or
const key = `${contractId.length}:${contractId}:${accountId}`;
```
The safest fix is length-prefixing or hashing both components (e.g., `sha256(contractId + "\0" + accountId)` or a JSON-encoded tuple) so no two distinct `(contractId, accountId)` pairs can ever map to the same key.

### Proof of Concept
1. Attacker calls `estimateWithdrawalFee` for `tokenA = "ab.near"`, `destinationAddress = "cd.near"` (or any pair) where the destination genuinely has sufficient storage balance on `ab.near`. This populates the cache with key `"ab.nearcd.near"` → `[min, balance]` where `balance >= min`.
2. Attacker then calls `estimateWithdrawalFee` for `tokenB = "ab.nearc"`... constrained to real deployed token contracts, so in practice the attacker picks any two supported tokens `tokenX`, `tokenY` and crafts `destinationAddress` values `accX`, `accY` such that `tokenX + accX === tokenY + accY` as strings, with the first pair genuinely storage-sufficient (cheap to arrange, e.g. use their own already-registered account) and the second pair `(tokenY, accY)` NOT actually registered on `tokenY`'s contract.
3. The second call to `estimateWithdrawalFee(tokenY, accY)` hits the cache from step 1 and returns `storageDepositFee: 0`, causing `createWithdrawalIntents` to attach zero storage deposit for a withdrawal to an unregistered account on `tokenY`.
4. Executing that intent on-chain fails (or, depending on the token contract implementation, silently proceeds without the required storage payment), producing a stuck/failed withdrawal that required no privileged access to trigger — only crafting matching-length NEAR account ID strings.

Note: I was not able to execute this against a live NEAR RPC/contract to observe the exact on-chain failure mode (panic vs. silent success) for arbitrary NEP-141 implementations; the described PoC is based on static analysis of the cache-key construction and its call sites within the indexed sources.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;

		const result = await Promise.all([

			}),
