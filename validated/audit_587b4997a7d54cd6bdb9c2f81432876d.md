### Title
Domain-less ERC-1271 signature validation in `SolverAccount` enables cross-protocol signature replay - (File: `evm/src/apps/intentsv2/SolverAccount.sol`)

### Summary
`SolverAccount.isValidSignature` implements the ERC-1271 interface for EIP-7702-delegated solver accounts by doing a bare `ECDSA.recover(hash, signature) == address(this)` check with no domain separation, purpose tag, or ERC-7739-style nested rehashing binding the approval to the calling verifier's identity, chain, or intended action. [1](#0-0)  This mirrors exactly the bug class described in the external report about `ERC1271Handler.isValidSignature`: for 65-byte EOA-style signatures there is no restriction on how the signed hash is constructed, so any valid `(hash, signature)` pair produced by the solver key for one context can satisfy `isValidSignature` for an unrelated verifier that happens to compute the same hash.

### Finding Description
`_rawSignatureValidation` — used both internally by `validateUserOp` and externally via `isValidSignature` — only checks that the recovered signer equals `address(this)`, without incorporating `block.chainid`, the calling/verifying contract's address, or any account-scoped domain separator into the check itself. [2](#0-1)  The contract's own documentation states this `isValidSignature` entrypoint is intended to be called by arbitrary third-party protocols using OpenZeppelin's `SignatureChecker` "e.g. USDC's EIP-2612 permit" against a solver's EIP-7702-delegated EOA. [3](#0-2)  Solver bids also embed a plain 65-byte ECDSA signature over the raw `userOpHash`, which the code comments acknowledge is public and reusable within the intended bid flow (already partially mitigated for the `fillOrder` griefing case). [4](#0-3)  Because `isValidSignature` accepts any externally supplied 32-byte `hash` and does not rehash/tag it as being requested by a specific verifying contract (the ERC-7739 "nested EIP-712" defense referenced by the original report), a signature legitimately produced by the solver's key for one purpose (a `userOpHash` under one EntryPoint/chain context, or a typed-data digest for one verifier) can be replayed against any other protocol that independently arrives at the identical 32-byte digest when calling `isValidSignature` on the same delegated address — exactly the "insufficient checks... reuse a historical transaction hash and signature" pattern flagged in the external report.

### Impact Explanation
If exploited, this allows unauthorized app actions to be authorized against a solver's delegated account without the actual EOA holder consenting to that specific action/context, since the account offers no cryptographic separation between the different consumers of its `isValidSignature` (ERC-4337 EntryPoint, IntentGatewayV2 session-key selection, and arbitrary ERC-2612/`SignatureChecker`-based external protocols). This falls under "unauthorized app action" impact and specifically threatens solver funds and approvals held by the delegated `SolverAccount`, which participates directly in the intents fill/bid path reachable by any intent solver.

### Likelihood Explanation
Exploitation requires an attacker to find or engineer a hash collision between two different verifying-contract domains that both call `isValidSignature` on the same solver account (e.g., a `userOpHash` value equal to an EIP-2612 permit digest). This is not as trivial as the original zkSync SSO report's cross-account/cross-chain scenario (which didn't require any hash collision, since removing `_hashTypedDataV4` meant no domain binding existed at all in the message construction), but the underlying root cause — an ERC-1271 implementation with zero domain separation on the *validation* side — is identical, and the contract explicitly advertises this entrypoint for use by multiple, independent third-party protocols, increasing the realistic surface for such coincidental or attacker-influenced digest reuse over the account's lifetime.

### Recommendation
Adopt the same fix path the original report and its resolution reference: wrap `isValidSignature` with an ERC-7739-style defensive rehashing scheme (e.g., Solady's `ERC1271.sol`) so that every hash presented to the account is first bound to `address(this)`, `block.chainid`, and the calling verifier's context before ECDSA recovery, preventing a signature produced for one context from validating in another. At minimum, incorporate a domain separator into `_rawSignatureValidation`/`isValidSignature` so the account cannot be fooled into approving a digest it did not knowingly construct for that verifier.

### Proof of Concept
1. A solver's EOA is EIP-7702-delegated to `SolverAccount`, code deployed per the constructor/test harness pattern. [5](#0-4) 
2. The solver signs a plain ECDSA signature over some digest `H` for one purpose (e.g., a bid's `userOpHash`, which the code says is public). [6](#0-5) 
3. A separate protocol (e.g., an EIP-2612-permitted token or any `SignatureChecker`-based verifier) independently computes the identical 32-byte digest `H` for an unrelated action it wants the solver account to authorize, and calls `SolverAccount.isValidSignature(H, sig)`.
4. Since `_rawSignatureValidation` performs no domain/purpose binding beyond `ECDSA.recover(H, sig) == address(this)`, the call returns the ERC-1271 magic value `0x1626ba7e`, authorizing the unrelated action without the solver ever intending to approve it in that context. [7](#0-6)

    /**
     * @notice Validates a raw signature against a hash
     * @dev Internal function used by the Account base contract for signature validation.
     *      Recovers the signer from the ECDSA signature and verifies it matches address(this).
     *      In EIP-7702 delegation, the EOA's address becomes this contract's address.
     *      Used for both standard ERC-4337 operations and intent solver selection validation.
     * @param hash The hash that was signed (typically userOpHash or Ethereum signed message hash)
     * @param signature The ECDSA signature to validate (65 bytes: r, s, v)
     * @return bool True if the recovered signer matches this contract's address, false otherwise
     */
    function _rawSignatureValidation(bytes32 hash, bytes calldata signature) internal view override returns (bool) {
        return ECDSA.recover(hash, signature) == address(this);
    }

    /**
     * @notice ERC-1271 signature validation for EIP-7702 delegated accounts.
     * @dev Required so that protocols using OpenZeppelin's SignatureChecker (e.g. USDC's
     *      EIP-2612 permit) can verify signatures from this account. Under EIP-7702 the
     *      account has code, so SignatureChecker takes the ERC-1271 path instead of
     *      ecrecover. Delegates to {_rawSignatureValidation} which performs ECDSA recovery
     *      and checks that the recovered address equals address(this) (the delegating EOA).
     */
    function isValidSignature(bytes32 hash, bytes calldata signature) external view override returns (bytes4) {
        return _rawSignatureValidation(hash, signature) ? bytes4(0x1626ba7e) : bytes4(0xffffffff);
    }
