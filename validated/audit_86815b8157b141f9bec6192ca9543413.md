## Title
`compareAddresses` fails to canonicalize case-insensitive Bech32/CashAddr encodings, allowing bypass of the "destination equals token address" check - (File: `packages/intents-sdk/src/lib/compareAddresses.ts`)

### Summary
`compareAddresses` is the equality primitive used across every bridge (`direct-bridge.ts`, `hot-bridge.ts`, `omni-bridge.ts`, `poa-bridge.ts`) to block a withdrawal whose `destinationAddress` resolves to the token's own on-chain address (`DestinationAddressMatchesTokenAddressError`). For Bitcoin, Bitcoin Cash, Litecoin, Dogecoin, Dash, Zcash and Cardano it falls through to a raw `a === b` string comparison: [1](#0-0) 

This is the same class of bug as the axios `shouldBypassProxy` advisory: an equality/allow-list check that compares raw strings instead of the canonical value, so an alternate-but-equivalent textual encoding of the exact same address is not recognized as equal.

### Finding Description
`validateAddress` explicitly accepts Bitcoin Bech32/Bech32m addresses in either all-lowercase or all-uppercase form — both are valid per BIP-173 and decode to the identical witness program: [2](#0-1) 

This is confirmed by the test fixtures, which assert that the uppercase form is a valid Bitcoin address: [3](#0-2) 

Bitcoin Cash CashAddr addresses have the same property (case-insensitive, and optionally prefixed with `bitcoincash:`) — `validateBchAddress`/`validateBchCashAddr` normalize case and prefix before validating: [4](#0-3) 

However, `compareAddresses` never performs this canonicalization for these chains — it just does `a === b`: [1](#0-0) 

`compareAddresses` is the sole mechanism used by every bridge to prevent a user from withdrawing a token to the token's own on-chain address (e.g. sending the BTC-backed token withdrawal to the BTC bridge's own origin address, which would render the funds unrecoverable): [5](#0-4) [6](#0-5) [7](#0-6) 

Because `validateAddress` accepts the uppercase/alternate-cased Bech32 (or unprefixed/mixed-case CashAddr) form as a valid destination, but `compareAddresses` compares it byte-for-byte against the stored canonical (typically lowercase) `origin_chain_address`, a destination address that is byte-identical on-chain to the token's own address — merely re-encoded in uppercase Bech32/CashAddr — passes format validation yet is *not* detected as "matches token address". The safety check silently fails open.

### Impact Explanation
This breaks the same equality the guard exists to enforce: "the address paid is not the token's own address that was validated". A withdrawal can be routed to the token's own bridge/contract address (an address whose funds cannot be recovered by the sender), because the collision-detection comparison missed a valid alternate encoding of that exact address. This matches the Critical bucket: "funds delivered to a wrong address/chain/contract with no recovery."

### Likelihood Explanation
Any caller (SDK consumer or a slightly malformed/attacker-influenced destination address field) that supplies the uppercase Bech32 (Bitcoin/Litecoin/Dogecoin/Dash if Bech32-capable) or an alternately-cased/prefixed CashAddr (Bitcoin Cash) equal to the bridge's own token address will pass `validateAddress` (format valid) and bypass `compareAddresses`'s self-address check, with no privileged action required — a plain caller can trigger it by choosing the address casing.

### Recommendation
Canonicalize before comparing in `compareAddresses` for the affected chains, mirroring what `validateAddress` already does for format checking:
- For Bitcoin/Litecoin/Dogecoin/Dash Bech32/Bech32m forms, decode to the witness program bytes (or at minimum lowercase) before comparing.
- For Bitcoin Cash, strip/normalize the `bitcoincash:` prefix and lowercase before comparing (reuse the same normalization used in `validateBchCashAddr`).
- Consider deriving `compareAddresses` from the same decode routines used by `validateAddress`, rather than maintaining two independently-diverging notions of "canonical form".

### Proof of Concept
```javascript
import { compareAddresses } from "./compareAddresses";
import { Chains } from "./caip2";

// Same underlying witness program, different valid Bech32 casing.
const lower = "bc1q973xrrgje6etkkn9q9azzsgpxeddats8ckvp5s"; // token's canonical origin_chain_address
const upper = "BC1Q973XRRGJE6ETKKN9Q9AZZSGPXEDDATS8CKVP5S"; // attacker-chosen destinationAddress

// Both pass validateAddress (per validateAddress.spec.ts fixtures) — format check does not block `upper`.
// compareAddresses fails to recognize they are the same on-chain address:
console.log(compareAddresses(lower, upper, Chains.Bitcoin)); // false, should be true

// -> poa-bridge.validateWithdrawal's `DestinationAddressMatchesTokenAddressError` guard is bypassed,
// allowing a withdrawal to the token's own address.
```
