### Title
`SessionUtils.cookie_session_id` trusts an unauthenticated, unsigned cookie value as the session storage key, allowing cross-tenant session/access-token theft - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.cookie_session_id` returns `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` verbatim as the key used to look up a stored `Session` (and its `access_token`), with no signature, MAC, or cross-check against any independently authenticated shop for the current request. Because the offline session id is deterministically derived as `"offline_#{shop}"` [1](#0-0) , and the cookie carries this exact value with no cryptographic binding [2](#0-1) , an attacker who knows or guesses a victim shop's myshopify domain can set the `shopify_app_session` cookie to that shop's session id and have the host app fetch and use the victim's stored `access_token`.

### Finding Description
The claimed binding is: `session.shop == shop_authenticated_by_this_request`. In the non-embedded flow, `current_session_id` unconditionally trusts the raw cookie: [3](#0-2) 

`cookie_session_id` does nothing but echo the cookie value: [4](#0-3) 

The cookie's *value* is set once, at OAuth completion, to `session.id` — for offline sessions this is simply `"offline_#{shop}"`, a value fully determined by the (public) shop domain and containing no HMAC, signature, or nonce that ties it to the browser/session that completed OAuth [5](#0-4) . The `SessionCookie` struct itself carries no signing metadata: `name`, `value`, `expires` only [6](#0-5) .

Contrast this with the JWT-based (embedded) path, where the shop is derived from a cryptographically verified `Auth::JwtPayload` (`payload.shop`, `payload.sub`) before constructing the session id [7](#0-6)  — there the shop identity does come from an authenticated source. The cookie path has no equivalent verification: `cookie_session_id` is reached whenever the `Authorization`/`shopify_id_token` header is absent, and for non-embedded apps it is the *only* path, used unconditionally [3](#0-2) .

Exploit flow: the attacker installs the app on their own development shop to learn the offline session-id naming scheme (`offline_<shop>.myshopify.com`), which requires no privileged secret. They then send a request to the victim merchant's app instance (host app built with this gem) with the cookie `shopify_app_session=offline_<victim-shop>.myshopify.com`. The host app calls `SessionUtils.current_session_id(nil, cookies, false)`, gets back the victim's exact session id, loads the victim's `Session` object (including `access_token`) from its `SessionStorage`, and issues Admin API requests — or otherwise exposes session data — using the victim's credentials on behalf of the attacker's request. No `HmacValidator.validate`, `ShopValidator.sanitize!`, `state` comparison, JWT `aud`/`sub` check, or `HttpRequest#verify` exists on this path, because those all belong to the OAuth-callback and id-token flows, not to `cookie_session_id`.

### Impact Explanation
Critical — theft/use of another merchant's Admin API access token. Any component that stores the session keyed purely by this gem-provided id (as documented for non-embedded apps) inherits the vulnerability, because the gem supplies no mechanism to prevent one client from presenting another client's session id. This is a cross-tenant identity collapse: the "shop" the request is later processed as belongs entirely to whichever id string the attacker chose to send, not to any shop that authenticated this particular request. It is repeatable against any shop whose myshopify domain the attacker can learn (install links, storefront URLs, app-store listings, public webhook headers received when the attacker installs the same app on their own store, etc.), and requires no possession of `api_secret_key` or any token.

### Likelihood Explanation
Preconditions: the host app is a non-embedded app (or falls back to cookie auth per the code path shown) using this gem's `SessionUtils.current_session_id`/`cookie_session_id` and a `SessionStorage` keyed by the returned id, as documented in `docs/getting_started.md`. Attacker cost is trivial — set one cookie header with a guessed/known shop domain; no secrets, no signature forging required, since the id format (`offline_#{shop}`) is public knowledge from this open-source gem's code. Repeatable against every shop whose domain is discoverable.

### Recommendation
Do not treat the raw cookie value as a self-authenticating storage key. Sign/MAC the `SessionCookie` value using `Context.api_secret_key` at issuance in `Oauth.validate_auth_callback`, and verify that signature inside `SessionUtils.cookie_session_id` before returning it as a lookup key; alternatively, store only an opaque random token in the cookie (never the shop-derived session id) and resolve it server-side to the real session id, so the cookie value never predictably encodes `shop`.

### Proof of Concept
```ruby
# test/utils/session_utils_cookie_spoof_test.rb
require "test_helper"

class SessionUtilsCookieSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "app.example.com",
      scope: "read_products", is_embedded: false, is_private: false, api_version: "2023-01",
    )
  end

  def test_attacker_can_present_victim_offline_session_id_via_cookie
    victim_shop = "victim-shop.myshopify.com"
    forged_cookie_value = ShopifyAPI::Utils::SessionUtils.offline_session_id(victim_shop)

    # Attacker never authenticated as victim_shop, yet:
    resolved_id = ShopifyAPI::Utils::SessionUtils.current_session_id(
      nil,
      { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value },
      false,
    )

    # BROKEN BINDING: resolved_id == victim's real storage key,
    # with no check that this request was ever authenticated as victim_shop.
    assert_equal forged_cookie_value, resolved_id
    assert_equal "offline_#{victim_shop}", resolved_id
    # A host app's SessionStorage.load(resolved_id) would now return the
    # victim's Session, including its access_token, to the attacker's request.
  end
end
```
This demonstrates that `cookie_session_id`/`current_session_id` return the attacker-chosen, unauthenticated cookie value verbatim, with no assertion binding it to any shop actually authenticated for the request — confirming the SINGLE IDENTITY invariant is violated.
