### Title
IntentGatewayV2 (Tron) `placeOrder()` escrows the nominal input amount instead of the actual tokens received, causing escrow insolvency for fee-on-transfer or non-standard ERC20 tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder()` in the Tron fork of `IntentGatewayV2.sol` credits the escrow mapping `_orders[commitment][token]` with a `reducedInputs[i].amount` value computed purely from the caller-supplied `order.inputs[i].amount`, while the actual tokens pulled into the contract come from an untrusted `safeTransferFrom` call whose real effect on the gateway's balance is never measured. This is the same root-cause pattern as the C4 finding: a value that is supposed to represent "what was actually received" is instead hard-coded to the value that was requested, so the escrow accounting can silently diverge from the real token balance held by the contract.

### Finding Description
In the non-predispatch branch of `placeOrder()`: [1](#0-0) 

```solidity
} else {

```

`reducedInputs[i].amount` is derived earlier purely from `order.inputs[i].amount` (the user-requested amount) minus the protocol fee percentage — it is never reconciled with what `safeTransferFrom` actually delivered: [2](#0-1) 

For a fee-on-transfer, rebasing, or otherwise non-standard ERC20 token, the gateway's actual balance increase is strictly less than `order.inputs[i].amount`, yet the code still records the full (fee-reduced-only) nominal amount as escrowed for that `commitment`/`token` pair. The commitment hash itself is computed from the *nominal* `order.inputs`, not from a "received" value, before any transfer occurs (unlike the corresponding EVM mainline `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf` before and after the transfer and overwrites `order.inputs[i].amount` with the delta before computing the commitment and crediting escrow): [3](#0-2) 

The Tron fork dropped this balance-based reconciliation, reproducing exactly the `SavingsAccountUtil.savingsAccountTransfer()` bug class: trusting a caller-controlled/nominal amount as the "received" amount used for internal accounting instead of measuring the actual transfer effect.

### Impact Explanation
Because `_orders[commitment][token]` is the authoritative escrow ledger used later for `fillOrder`/`cancelOrder`/`withdraw` redemption, over-crediting escrow relative to the contract's actual token balance means:
- The sum of all outstanding escrow entries can exceed the gateway's real token balance.
- Legitimate solvers filling *other* orders, or users cancelling *other* orders for the same token, can find withdrawals failing or draining balance meant for them — a last-depositor-loses situation identical in spirit to the H-02 report's `cancelPool()`/liquidation failures causing fund loss.
- An attacker can deliberately use a fee-on-transfer token as an input asset to place an order that is escrowed for more than what was actually deposited, extracting value from the shared token pool at the expense of other legitimate order participants.

This is a concrete fund-loss / accounting-insolvency bug in a message dispatcher reachable by any unprivileged caller via a single `placeOrder()` transaction.

### Likelihood Explanation
Any externally supplied ERC20 token address can be used as `order.inputs[i].token`; the gateway does not restrict inputs to a vetted allow-list of "well-behaved" tokens in this code path. Fee-on-transfer and deflationary/rebasing tokens are common in the wild, so triggering the divergence requires no special privileges — just placing an order with such a token, which is a single unprivileged transaction (`placeOrder`).

### Recommendation
Mirror the mainline EVM `IntentGatewayV2.sol` fix: measure the gateway's actual token balance before and after each `safeTransferFrom`, use that delta (not the nominal `order.inputs[i].amount`) to both compute the commitment and to determine the escrowed/reduced amount, e.g.:

```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
uint256 received = IERC20(token).balanceOf(address(this)) - balBefore;
// use `received` (not order.inputs[i].amount) for fee reduction, commitment hashing, and escrow crediting
```

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token (e.g., 1% fee burned/retained on transfer) and mint balance to `user`.
2. `user` calls `placeOrder()` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch.
3. `safeTransferFrom` moves only `990e18` into the gateway (1% fee), but `_orders[commitment][FOT]` is credited with `reducedInputs[0].amount` derived from the full `1000e18` (minus only protocol fee, if any) — i.e., escrow records ~`1000e18` (or `997e18` with a 0.3% protocol fee) while the gateway actually holds only `990e18`.
4. When a solver fills the order and later redeems escrow via `RedeemEscrow`/`withdraw`, or when other orders using the same token attempt withdrawal, the contract's real `FOT` balance is insufficient to cover all outstanding escrow entries, causing reverts for other legitimate participants or allowing the attacker's own order to be over-credited relative to what they deposited.
