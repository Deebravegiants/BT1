Webhook shop-domain and topic identity are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to the raw request body only. The `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are parsed and trusted as tenant/event identity but never included in the signed content, breaking the binding `hmac == HMAC(secret, body ‖ shop ‖ topic)` that the framework implicitly relies on.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and compares it against the received `hmac` using the app's `client_secret`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from unauthenticated HTTP headers via `shopify_header`: [3](#0-2) 

`Registry.process` verifies only the HMAC-over-body, then dispatches the handler keyed by `request.topic` and forwards `request.shop` as the tenant identity into `WebhookMetadata`, without any cryptographic binding between that header value and the signed body: [4](#0-3) 

Because a single app-level `client_secret` signs webhooks for *all* shops that installed the app (there is no per-shop key mixed into the signature), and the `shop-domain` header is excluded from `to_signable_string`, a valid `(body, hmac)` pair generated for one shop remains cryptographically valid when replayed with a different `shop-domain` header. An unprivileged user who installs the app on their own shop can trigger a real webhook delivery (e.g., `orders/create` with attacker-controlled body content), capture the resulting `body` + `hmac-sha256` header (both readable to them since it targets their own endpoint/proxy), and then submit a forged HTTP request to the app's webhook endpoint with `shop-domain` swapped to a victim shop and/or `topic` swapped to a different registered topic. `HmacValidator.validate` will accept it because only the body is checked, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop, causing the host application's handler logic to act as though the victim shop sent that data — a cross-tenant identity binding break.

### Impact Explanation
This matches the Critical impact category: cross-tenant access. The `shop` field acted upon by downstream webhook handlers (used by host apps to look up per-shop state, sessions, or trigger shop-scoped side effects such as data deletion for GDPR topics) is not covered by the HMAC that is meant to authenticate the message, so an attacker can impersonate any other shop that has installed the same app for webhook purposes, independent of any credential belonging to the victim.

### Likelihood Explanation
Likelihood is High for any app author who installs the app themselves (a routine, unprivileged action) — they can legitimately trigger webhooks against their own store, harvest a valid `(raw_body, hmac)` pair, and replay it with a modified `shop-domain`/`topic` header. No access token, `api_secret_key`, or victim credential is required; only control of the HTTP request that reaches the webhook endpoint (which is a normal, internet-reachable route by design), and prior participation as an app-installing shop.

### Recommendation
Include the `shop`, `topic`, and `webhook_id`/`api_version` values in the material verified by the HMAC (or otherwise cryptographically bind them to the request), e.g., by having `to_signable_string` incorporate a canonicalized combination of headers and body, or by requiring the host application to independently confirm that `request.shop` corresponds to a shop with an active session/registration for that specific webhook subscription (mapping the `webhook_id` returned by Shopify's registration APIs to the expected shop) before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a legitimate webhook, e.g. `orders/create`, with body `{"note":"x"}`. Shopify signs it with the app's single `client_secret`:
   `hmac = Base64(HMAC-SHA256(client_secret, raw_body))`.
2. Attacker records `raw_body` and the `shopify-hmac-sha256` header value from this legitimate delivery.
3. Attacker crafts a new POST to the app's webhook endpoint with the **same** `raw_body`/`hmac` but headers:
   `shopify-shop-domain: victim.myshopify.com`, `shopify-topic: orders/create`.
4. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present): [5](#0-4) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` — identical to step 1 — with the same app secret: [6](#0-5) 
6. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: ...)`, causing the host app to process attacker-controlled data as an authentic event from the victim shop — a cross-tenant impersonation the HMAC was supposed to prevent. [7](#0-6)
