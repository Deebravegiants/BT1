### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/event routing but are not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then dispatches the handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken directly from HTTP headers. Those header values are never included in the signed payload, so they can be freely altered without invalidating the HMAC check.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All the identity-bearing fields — `shop` (`shop-domain` header), `topic`, `api_version`, and `webhook_id` — are read straight from unauthenticated headers and are not part of the signed string: [2](#0-1) 

`Registry.process` validates the request using exactly this signable string and then trusts `request.topic` and `request.shop` to route and label the event for the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [4](#0-3) 

Because the signature only binds the raw body bytes, the identity binding that should hold is:

`shop-domain header == shop that the signed body actually originated from`

but the code only verifies:

`HMAC(raw_body, api_secret_key) == received hmac`

with no constraint tying `shop-domain`/`topic`/`webhook_id` to that signature. Anyone who obtains one legitimate `(raw_body, hmac)` pair for the app (e.g., because they are a merchant who installed the app and can observe webhooks delivered to their own endpoint, or the pair leaks via logs/CDN/proxy) can resend that exact body+hmac pair to the app's webhook endpoint while substituting arbitrary `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, and `shopify-api-version` header values. `HmacValidator.validate` still succeeds because it only checks `@raw_body`, and `Registry.process` will happily dispatch the handler believing the event came from a different shop and/or a different topic than the one that actually produced the body.

### Impact Explanation
This breaks tenant isolation for any application built on this gem's webhook processing helper: an attacker can make the host application process a webhook body under a forged `shop-domain`, causing cross-tenant data injection/confusion (e.g., a `customers/data_request` or `orders/create` payload from shop A being attributed to shop B, or a benign topic's body being reinterpreted under a sensitive topic such as `shop/redact`/`customers/redact` if a handler is registered for it). This is a cross-tenant access issue, matching the "Critical - cross-tenant access" impact category, since the identity of the tenant (`shop`) that a webhook is attributed to is not cryptographically bound to the payload the HMAC actually protects.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimate `(raw_body, hmac)` pair, which they can obtain without any credentials by being a merchant who has installed the app themselves (webhooks are delivered to a public app endpoint, and the attacker's own shop's webhook is exactly such a pair) or by observing/replaying it via any request-logging surface. No `api_secret_key`, access token, or privileged account access to a target tenant is needed — only a body+signature pair for *some* shop, which the attacker can self-generate as a legitimate installer of the app. This keeps the analog within the unprivileged-internet-user scope defined by the rules (a field acted on but not covered by the HMAC).

### Recommendation
Bind the tenant/event identity into the signed payload verification, not just the raw body. Concretely:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the string that is HMAC-verified, or verify Shopify's webhook signature semantics require binding topic/shop to the signed bytes.
- At minimum, cross-check the `shop-domain` header against an independently known/authorized shop for the session/handler before dispatching, rather than trusting the header solely because the raw body's HMAC matches.

### Proof of Concept
1. Install the target app as shop `attacker.myshopify.com`; Shopify delivers a legitimate webhook to the app endpoint with body `B` and header `shopify-hmac-sha256: H` (a valid HMAC of `B`), along with `shopify-shop-domain: attacker.myshopify.com` and `shopify-topic: orders/create`.
2. Capture `(B, H)`.
3. Send a forged HTTP request to the same webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but change `shopify-shop-domain: victim.myshopify.com` and/or `shopify-topic: shop/redact`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(B, api_secret_key)` — this equals `H` because the body is unchanged — so validation passes: [5](#0-4) 
5. `Registry.process` dispatches the registered handler with `shop: "victim.myshopify.com"` and/or `topic: "shop/redact"`, even though the payload actually originated from `attacker.myshopify.com`'s `orders/create` event, demonstrating the cross-tenant/topic-confusion identity break.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

          received_signature = verifiable_query.hmac
