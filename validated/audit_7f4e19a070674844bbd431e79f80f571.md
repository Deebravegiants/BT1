This is exactly the fail-open-when-unconfigured bug class described in the dbx CVE, and it exists deliberately in `ExtrinsicIntents._checkRelayer`.

### Title
Unauthenticated arbitrary relayer delivery on IntentGatewayV2 when `_relayer` is unset — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents._checkRelayer` is the sole gate protecting `onAccept`/`onGetResponse` on `IntentGatewayV2`. When `_relayer` is `address(0)` (unset), the check passes for *any* caller who can get a message accepted through `EvmHost.dispatchIncoming`, exactly mirroring the dbx pattern where auth "fails fully open" whenever the credential is unconfigured. A fresh proxy, or a proxy whose relayer has been reset to zero, accepts escrow releases and privileged governance-shaped bodies (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`) from an unauthenticated relayer address.

### Finding Description
`_checkRelayer` only rejects a mismatched relayer *if one is configured*: [1](#0-0) 

`onAccept` calls this before any authentication of the message body: [2](#0-1) 

The delivery path reaching this gate requires only a proof-verified `HandlerV2.handlePostRequests`/`handleGetResponses` call, after which `EvmHost.dispatchIncoming` forwards `IApp.onAccept(IncomingPostRequest(request, msg.sender))` with `relayer = msg.sender` — any address that submitted the proof: [3](#0-2) 

The repo's own documentation confirms this is the exact, currently-live behavior — "unset relayer gates nothing" and "an unset relayer therefore gates nothing": [4](#0-3) 

and the flow doc: "A gateway whose `_relayer` is zero accepts every relayer: that is the state a fresh proxy is in until governance arms it": [5](#0-4) 

Notably, an earlier internal decision explicitly considered the opposite design ("zero relayer fails closed") and it was **superseded** in favor of fail-open: [6](#0-5) 

This is a design decision, not a coding accident, and the codebase carries regression tests (`testFreshProxyIsOpenUntilGovernanceArmsIt`, `testSetRelayerToZeroReopensTheGate`) that assert this exact fail-open behavior is intended: [7](#0-6) [8](#0-7) 

### Impact Explanation
While the gate itself is documented and intentional, the risk class matches the CVE precisely: any state (fresh deployment before governance arms the relayer, or any deliberate/accidental `setRelayer(address(0))`) leaves `IntentGatewayV2.onAccept`/`onGetResponse` reachable by an unauthenticated relayer address. In that window, an attacker who can produce (or has access to a compromised/malicious) message delivery through `HandlerV2` can:
- Trigger `RedeemEscrow`/`RefundEscrow` releasing escrowed funds to an attacker-chosen beneficiary (subject to `_authenticate` still checking the source module address, which limits this to genuine cross-chain messages from the registered peer instance — see caveat below).
- Deliver governance-shaped bodies (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`) if the `source` check for those passes, since Hyperbridge-sourced checks are separate from the relayer gate.

The window is bounded in practice (only exists pre-arming or after an explicit `setRelayer(0)`), and `_authenticate` still requires `request.from` to match the registered peer gateway for user-fund-moving actions, so this is not a full unauthenticated-anyone-can-drain-funds bug like the dbx CVE. It is a genuine authorization gap in a specific operational state, matching "unauthorized app action" in the validation criteria, but its blast radius depends on whether a relayer is left unset in production and on what other checks constrain the message source.

### Likelihood Explanation
Low-to-medium. Exploitation requires either (a) a production deployment where governance has not yet armed the relayer (a known, time-bounded operational window that the team explicitly accepted, per the superseded-decision doc), or (b) some other bug/operator error resetting `_relayer` to zero on a live gateway. Given the explicit design decision and test coverage affirming this behavior, the team appears to have accepted this risk as bounded by deployment procedure rather than by contract-level defense-in-depth.

### Recommendation
Since this is a deliberate design tradeoff (not a coding oversight), the main options for a fix, if desired, are:
- Fail closed on zero relayer (as the superseded 2026-09-03 decision originally chose), accepting that until `migrate`/`setRelayer` is called, no relayer delivery is accepted at all.
- Or, if fail-open must be kept for deployment ergonomics, ensure the arming transaction is atomic with proxy deployment (e.g., always call `initialize`/`migrate` with a non-zero relayer in the same transaction as deployment, never leaving an intermediate unarmed block reachable on a public network) and add an invariant/monitor that alerts if `relayer() == address(0)` on any deployed proxy.

### Proof of Concept
From the repo's own test suite, `testSetRelayerToZeroReopensTheGate` demonstrates the exploit path end-to-end: after `setRelayer(address(0))`, an arbitrary `relayer` (`filler`) is accepted by `onAccept` and released escrowed funds: [7](#0-6) 

Similarly `testFreshProxyIsOpenUntilGovernanceArmsIt` shows a fresh, unarmed proxy accepting a governance-shaped delivery from an arbitrary relayer (`filler`) before `setRelayer` is called: [8](#0-7)

# 2026-09-05 — Gateway `setRelayer` is host-only and the only writer; unset means open

Chosen: `setRelayer` lives in `ExtrinsicIntents` behind `onlyHost`, `initialize` does not touch the
relayer, and `_checkRelayer` passes every delivery while `_relayer` is zero. This supersedes the
2026-09-03 decision below that zero fails closed.

The owner branch existed so a fresh proxy could be armed locally; it also let the owner key
redirect every cross-chain delivery without a governance message. Removing it leaves the host as
the only caller, reachable solely from `UpgradeContract` migration calldata. Carrying the relayer
in the init data was tried and rejected: the relayer is operational state that governance owns,
not part of what fixes a proxy's address. With no local or init-time arming left, the message that
arms a fresh proxy is a governance delivery, so the unarmed proxy has to accept it; an unset
relayer therefore gates nothing, and `setRelayer(address(0))` reopens the gate. The window is the
one between deployment and the `upgrade_gateway` that arms it, and closing it is governance's
first act on a new chain.
