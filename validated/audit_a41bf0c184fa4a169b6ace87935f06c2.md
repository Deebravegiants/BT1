### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
This gem's webhook `HmacValidator` proves only that the raw request *body* was signed with the app's `api_secret_key`; the `shop`, `topic`, `api-version`, and `webhook-id` values are read from unauthenticated HTTP headers and are never included in the bytes that are verified. `ShopifyAPI::Webhooks::Registry.process` nonetheless hands `request.shop` straight to the app's handler as the authoritative merchant/tenant identifier, so the field an app uses to decide "which shop does this data belong to" is not bound to the field the HMAC actually authenticates.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version` and `webhook_id` are all read from headers, entirely outside the signed material: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (i.e. the body) and secure-compares it to the received HMAC — it never touches the shop/topic/webhook-id headers: [3](#0-2) 

`Registry.process` validates only the HMAC, then immediately trusts `request.shop` as the tenant identity for the handler: [4](#0-3) 

The documented contract states that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler, and that `data.shop` is "The shop domain of the webhook" — i.e., apps are told to trust this field as an authenticated attribute of the verified request: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop header used by the handler == shop whose secret produced the verified HMAC`. Because the HMAC covers only the body, this equality is never checked — it is entirely possible to present a body/HMAC pair that is valid for the app's `api_secret_key` (e.g. captured/replayed from any webhook belonging to any shop that has installed the app, including a shop controlled by the attacker) together with an arbitrary, attacker-chosen `shop-domain` header value naming a different (victim) shop. `Registry.process` will accept it as a validly-verified webhook and dispatch it to the handler labeled with the forged shop.

This is structurally the same class of bug as the reported GammaSwap issue: a value that is used pervasively downstream (there, the invariant factor derived from only `decimals[0]`; here, the shop identity derived from an unauthenticated header) is computed/trusted from an incomplete or wrong input, silently corrupting every consumer that assumes it was fully validated.

### Impact Explanation
Any app built on this gem that uses `data.shop` from a processed webhook to key merchant-specific storage, dispatch background jobs "for that shop", or make authorization decisions (as the gem's own documented example does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute one merchant's webhook payload to a different, victim merchant's identity. This is a cross-tenant data/identity confusion: an attacker who controls a shop that has installed the app (or who otherwise obtains one validly-signed webhook body/HMAC pair for the app) can cause the app to process and store that data as though it belongs to an arbitrary victim shop domain, since nothing in the verified bytes ties the payload to a specific shop.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled store (a low bar, most Shopify apps are installable) to obtain a legitimate, freshly-HMAC-signed webhook body, and (2) delivering a forged HTTP request to the app's public webhook endpoint with that body/HMAC pair but an attacker-chosen `shopify-shop-domain` header — something entirely within an unprivileged internet user's control since no TLS interception, leaked secret, or privileged account is needed. The main constraint is that the attacker doesn't control the *content* of the body (Shopify writes it), limiting impact to whichever webhook topics/paths the app has registered, but the shop-attribution confusion itself is fully forgeable.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., verify `request.shop` against a shop known from an existing session lookup keyed by the signed payload, not from the raw header alone) before passing them to the handler as trusted identity.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `api_secret_key`.
2. Attacker captures `raw_body` and its valid `hmac` header from this delivery.
3. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the same `raw_body`/`hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers without validation: [7](#0-6) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the secret: [8](#0-7) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`, and the host app (per the documented pattern) enqueues/stores it under the victim's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
