Found the analog. `TokenExchange.exchange_token` derives `dest_shop` from the JWT payload's `dest` claim and uses it **unsanitized** to build the base URI that receives the app's `client_secret`, unlike every sibling credential-issuing method in the same module.

### Title
Unsanitized JWT `dest` claim used as `client_secret`-receiving host in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` value directly from the JWT session-token's `dest` claim (`jwt_payload.shop`, i.e. `@dest.gsub("https://", "")`) and passes it straight into `Auth::Session.new(shop: dest_shop)`, which `Clients::HttpClient` then uses verbatim as the request host (`@base_uri = "https://#{api_host || session.shop}"`) for the POST that carries `client_id`/`client_secret` to `/admin/oauth/access_token`. No `Utils::ShopValidator.sanitize!` call is applied to `dest_shop`, even though every other credential-issuing method in the same file/module (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host used for the `client_secret` POST.

### Finding Description
`JwtPayload#shop` only strips the `https://` prefix from the raw `dest` claim (`lib/shopify_api/auth/jwt_payload.rb` L47-50) — it performs no domain allow-listing against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`). `JwtPayload.initialize` only verifies the token's signature and that `aud == Context.api_key` (`lib/shopify_api/auth/jwt_payload.rb` L43-45); it never validates the `dest`/`iss` value's host format.

`exchange_token` then does:
```
jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
dest_shop = jwt_payload.shop
...
shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
...
client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
``` [1](#0-0) 

`Clients::HttpClient#initialize` builds the request host directly from `session.shop`: [2](#0-1) 

Because the app's own signing secret (`Context.api_secret_key`) is used to *decode/verify* the JWT (L26 of `jwt_payload.rb`), any embedded-app frontend context (App Bridge, iframe host, or any caller able to obtain/replay a session token whose `dest` value is attacker-influenced) can drive `exchange_token` to treat an out-of-policy `dest` value as the destination host for the token-exchange POST — the equality the library elsewhere enforces (`validated_shop == ShopValidator.sanitize!(shop)` before it becomes the request host) is skipped here. This is the same bug class as the CVE-style host/identity-binding pattern in the report: a value that is *cryptographically verified for integrity* (JWT signature / HMAC) is nonetheless used as an SSRF-style destination host without checking that it is bound to a *trusted* domain, unlike its sibling functions in the very same file.

### Impact Explanation
If `dest_shop` is not constrained to `TRUSTED_SHOPIFY_DOMAINS`, `HttpClient` will POST a JSON body containing `client_id` and `client_secret` (the app's confidential OAuth secret) to `https://{dest_shop}/admin/oauth/access_token`. If `dest_shop` can be steered to an attacker-controlled host, this results in exfiltration of the app's `client_secret` to that host — matching the "High: SSRF with the app's credentials / credential leakage" impact category.

### Likelihood Explanation
Likelihood is **Medium**: the JWT is verified with `Context.api_secret_key`, so a token must be validly signed by the app's own secret. But nothing in this gem's `JwtPayload`/`TokenExchange` code cross-checks that the signed `dest` value is actually a `*.myshopify.com`/allow-listed host before it is trusted as an HTTP destination for secret material — this is exactly the gap that `ShopValidator.sanitize!` was introduced elsewhere in the same module to close (`migrate_to_expiring_token`, `client_credentials`, `refresh_access_token`), making `exchange_token` an inconsistent, unguarded outlier reachable by any caller (e.g., embedded-app frontend/App Bridge flows) that can supply a session token to `exchange_token`.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, sanitize `dest_shop` the same way as the sibling methods before it is used to build `shop_session`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
and raise `Errors::InvalidShopError` (consistent with `ShopValidator.sanitize!`) when the `dest` claim does not resolve to a trusted Shopify domain, preventing the `client_secret`-bearing POST from ever targeting a non-allow-listed host.

### Proof of Concept
Not independently reproducible end-to-end without a valid signed JWT from a party controlling `Context.api_secret_key` (which is out of scope per the rules); the finding is established by static code comparison: [3](#0-2)  (no `ShopValidator.sanitize!` call on `dest_shop`) versus [4](#0-3)  (`migrate_to_expiring_token` calling `Utils::ShopValidator.sanitize!(shop)`), and [5](#0-4) , [6](#0-5)  confirming the intended pattern that `exchange_token` fails to follow, combined with `HttpClient` using `session.shop` unchecked as the request host that carries `client_secret`: [2](#0-1) .
