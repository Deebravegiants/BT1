Confirmed root cause. The `topic`, `shop`, `api_version`, and `webhook_id` fields in `WebhookMetadata` all come from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the HMAC over `request.raw_body` (`to_signable_string` returns `@raw_body`), not the `shop`, `topic`, or other headers.

### Title
Webhook shop/topic identity spoofing via unsigned headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, but the `shop`, `topic`, `api_version`, and `webhook_id` values handed to the app's `WebhookHandler#handle` are read directly from HTTP headers that are never included in the signed payload, breaking the binding between "HMAC-verified sender" and "shop the data is attributed to."

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` to authenticate the webhook [1](#0-0) . That validator computes the HMAC exclusively over `verifiable_query.to_signable_string`, and `Request#to_signable_string` returns only `@raw_body` [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all parsed straight from the `x-shopify-*` / `shopify-*` headers with no cryptographic binding to the HMAC [3](#0-2) . After a successful HMAC check, `process` builds `WebhookMetadata` using these unverified header values and passes it straight to the app-registered handler [4](#0-3) , and `WebhookMetadata.shop`/`.topic` are exactly the fields multi-tenant apps use to route/attribute webhook data to a specific merchant [5](#0-4) .

This is the same identity-binding gap as the reported analog: `vote()` checked "signature/objection window valid" but never checked "was this specific proposal state (rejected) still consistent with the action" — here, the gem checks "is this body's HMAC valid" but never checks "is the `shop`/`topic` header consistent with the entity that produced that HMAC." Formally: `hmac_verified(raw_body, secret) == true` does NOT imply `header['shop-domain'] == shop_that_produced(raw_body)`.

### Impact Explanation
An attacker who controls any shop that has the target app installed (e.g., a free Shopify development/partner store, requiring no privileged access, secrets, or tokens) can capture a legitimately-signed webhook delivery for their own shop and body content, then replay it to the app's webhook endpoint while spoofing the `x-shopify-shop-domain` header to a victim shop's domain. Because the HMAC only covers `raw_body` and never the `shop`/`topic` headers, the tampered request still passes `HmacValidator.validate`. The handler then receives `WebhookMetadata` attributing attacker-chosen body content to an arbitrary victim shop, resulting in cross-tenant data confusion/injection in any host app that trusts `WebhookMetadata.shop` for record attribution, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only an unprivileged attacker with their own Shopify store where the target app is installed (or any means of observing one legitimately-signed webhook delivery and its raw body), plus the ability to POST arbitrary headers/body to the app's public webhook endpoint — no `api_secret_key`, access token, or other privileged credential is needed.

### Recommendation
Include the `shop`, `topic`, `api_version`, and `webhook_id` header values in the HMAC-signable string (or otherwise cryptographically bind them to the verified payload) so that `Utils::HmacValidator.validate` fails if any of these attribution fields are altered independently of the body.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store and triggers a webhook (e.g. `orders/create`), capturing the raw POST: headers including `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and `raw_body`.
2. Attacker resends the identical `raw_body` (and thus identical, still-valid `x-shopify-hmac-sha256`) to the same endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Registry.process` -> `Utils::HmacValidator.validate` still returns `true` because it only checked `raw_body` against the secret [6](#0-5) .
4. `WebhookMetadata.shop` is now `"victim-shop.myshopify.com"` even though the payload never touched that shop, and the registered handler processes it as legitimate victim-shop data [7](#0-6) .
