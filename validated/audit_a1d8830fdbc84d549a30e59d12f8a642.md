### Title
`describeWithdrawal()` matches PoA withdrawal status/txHash by `assetId` only, ignoring `index`, misreporting status for same-asset batch items - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` calls `findMatchingWithdrawal()` which selects an entry from the indexer's unsorted `withdrawals` array purely by comparing `assetId` (`nep141:${w.data.near_token_id}`), ignoring `WithdrawalIdentifier.index`, `destinationAddress`, and `amount`. When a single NEAR transaction contains two withdrawals of the same asset (e.g. same token to two different destination addresses), `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` both resolve against the same matched entry (`Array.prototype.find` returns the first match for both calls), causing the second withdrawal's status/`txHash` to be reported using the first one's outcome (or vice versa).

### Finding Description
The broken equality: for withdrawal `i` in a batch, `describeWithdrawal({index:i,...})` must resolve `(status, txHash)` equal to the indexer record actually corresponding to withdrawal `i`'s own destination/amount — not to any other withdrawal `j` sharing the same `assetId`.

Code path in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`:
- `describeWithdrawal()` fetches `response.withdrawals` via `getWithdrawalStatusWithRetry` keyed only by `args.tx.hash` (line 316), then calls: [1](#0-0) 
- `findMatchingWithdrawal()` matches purely by `assetId`, with the matching limitation explicitly documented in the code comment itself: [2](#0-1) 

The same pattern with the identical caveat exists in the internal-utils polling helper: [3](#0-2) 

Root cause: `WithdrawalIdentifier.index` (defined in `packages/intents-sdk/src/shared-types.ts`) is never consulted for matching: [4](#0-3) 

Attacker's exact input: any unprivileged user who submits a batch withdrawal (`WithdrawalParams[]`) containing two entries with identical `assetId` but different `destinationAddress`/`amount` routed through PoA bridge. Nothing in `validateWithdrawal`, `supports()`, or `createWithdrawalIdentifier` rejects duplicate `assetId` within a batch — `validateWithdrawal` only checks per-item address/amount validity, not batch-level uniqueness, and `createWithdrawalIdentifier` just copies `index` through without using it in matching later: [5](#0-4) 

Exploit flow: batch withdrawal tx hash `H` contains withdrawal 0 (asset X → address A) and withdrawal 1 (asset X → address B). The PoA indexer returns an unsorted `withdrawals` array for `H` containing both records. Calling `describeWithdrawal` for index 0 and index 1 both invoke `findMatchingWithdrawal(withdrawals, "nep141:X")`, which returns the *same* first match (e.g., the record for B) for both calls. An integrator polling per-index would then report index 0 as completed with B's `transfer_tx_hash`, misattributing the destination-chain proof.

Existing guards do not prevent this: `compareAddresses`/`validateAddress` operate on a single item's own destination, not batch-wide de-duplication; `supports()` only routes by asset type; the intents contract's own signature/nonce checks constrain what is submitted on-chain but not the SDK-side status reporting logic post-hoc.

### Impact Explanation
This is a status/txHash misreport for a `nep141` PoA-bridge withdrawal batch item: the SDK, not the chain, reports the wrong `(status, txHash)` pairing for the wrong index. An integrator that credits or marks a specific end-user's withdrawal (identified by `index`) as complete based on `describeWithdrawal`'s returned `txHash` could credit/complete the wrong recipient's record or, in a double-check flow, double-credit. This matches the **High** category: "a status or hash misreport making an integrator credit or refund twice." It is repeatable for every batch that contains ≥2 same-asset withdrawals to different destinations, and the code comments confirm this is a known, unresolved limitation rather than a one-off inconsistency.

### Likelihood Explanation
Preconditions: the attacker (or an integrator processing multiple users in one batched NEAR transaction) simply needs to submit ≥2 withdrawal items with the same `assetId` in one `signAndSendWithdrawalIntent`/`processWithdrawal` batch call to the PoA route — a fully permitted, unprivileged, single-call action requiring no special funds beyond the withdrawal amounts themselves. No bridge-API or relayer misbehavior is required; the PoA indexer's normal (documented as "unsorted") response is sufficient to trigger the divergence. Feasibility is high and the bug is deterministic and repeatable for every such batch.

### Recommendation
Extend `findMatchingWithdrawal` (in both `poa-bridge.ts` and `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate same-`assetId` entries using additional fields returned by the indexer (e.g., destination address, amount, or a stable per-item sequence/withdrawal id from the PoA API) instead of `assetId` alone; if the PoA API cannot currently distinguish same-asset batch items, `describeWithdrawal`/`waitForWithdrawalCompletion` should refuse to disambiguate and instead throw/return an explicit "ambiguous match" error for batches with duplicate `assetId` entries, rather than silently returning a possibly-wrong record.

// packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.same-asset-batch.test.ts
import { describe, it, expect, vi } from "vitest";
import { poaBridge } from "@defuse-protocol/internal-utils";
import { PoaBridge } from "./poa-bridge";

it("misreports txHash for two same-assetId withdrawals in one batch", async () => {
  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "usdt.omft.near", transfer_tx_hash: "TX_FOR_B", chain: "eth", address: "0xB" } },
      { status: "COMPLETED", data: { near_token_id: "usdt.omft.near", transfer_tx_hash: "TX_FOR_A", chain: "eth", address: "0xA" } },
    ],
  });

  const bridge = new PoaBridge({ envConfig: /* ... */, xrplRpcUrls: [] });

  const paramsA = { assetId: "nep141:usdt.omft.near", amount: 1n, destinationAddress: "0xA", feeInclusive: false };
  const paramsB = { assetId: "nep141:usdt.omft.near", amount: 2n, destinationAddress: "0xB", feeInclusive: false };
  const tx = { hash: "H", accountId: "acct" };

  const resultForA = await bridge.describeWithdrawal({ landingChain: "eth", index: 0, withdrawalParams: paramsA, tx });
  const resultForB = await bridge.describeWithdrawal({ landingChain: "eth", index: 1, withdrawalParams: paramsB, tx });

  // BROKEN EQUALITY: withdrawal for A's own outcome should have txHash "TX_FOR_A" ... but it doesn't:
  expect(resultForA).toEqual(resultForB); // both resolve to the SAME (first-matched) entry
  // i.e. resultForA.txHash === "TX_FOR_B" (B's hash), not "TX_FOR_A" — proving index i's report
  // is not equal to withdrawal i's actual outcome.
});

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
