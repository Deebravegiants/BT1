I have enough evidence to confirm the vulnerability. The `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `x-shopify-shop-domain` header without being part of the HMAC-signed content [2](#0-1) . `Registry.process` validates the HMAC and then forwards `request.shop` unchanged to the app's handler [3](#0-2) .

### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature verified by `Utils::HmacValidator` only covers the raw request body, never the `shop` header. `Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the app's `WebhookHandler` as trusted tenant context, breaking the binding: `HMAC-authenticated bytes == body only`, while `shop attributed to the request == unauthenticated header value`.

### Finding Description
`VerifiableQuery#to_signable_string` for `Webhooks::Request` returns just `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC over exactly that signable string using the app's `api_secret_key` [4](#0-3) . The `shop` accessor, however, is read straight from `shopify_header("shop-domain")` [2](#0-1) , a value that is never mixed into the signed payload. `Registry.process` checks `Utils::HmacValidator.validate(request)` and, once that passes, immediately builds `WebhookMetadata` using `request.shop` and dispatches it to the app-supplied handler with no further tenant check [3](#0-2) .

Because the HMAC never binds the shop, any request with a valid `(body, hmac)` pair (e.g. one produced by a genuinely subscribed shop) can have its `X-Shopify-Shop-Domain` header replaced with the domain of a different, victim shop, and the request will still pass validation and be processed as if it came from the victim shop.

### Impact Explanation
Since apps commonly key sessions/tenants by the `shop` field delivered in `WebhookMetadata` (as documented in `docs/usage/webhooks.md`, which instructs handlers to key work off `data.shop`), this allows cross-tenant data confusion in host applications: a webhook whose body and HMAC were legitimately generated for shop A can be replayed with a spoofed `X-Shopify-Shop-Domain` header for shop B, causing the app to attribute/act on that payload — including mandatory compliance topics like `shop/redact` or `customers/data_request` — under shop B's identity, without ever needing shop B's credentials. This crosses a tenant boundary using only a body/HMAC pair obtainable from the attacker's own (or any) subscribed shop.

### Likelihood Explanation
An attacker who controls (or has ever received) any single legitimate webhook delivery for the target app — trivial to obtain by installing the app on their own test shop — has body+HMAC pairs they fully control the timing of, and can freely swap the unsigned `shop-domain` header before replaying the request to the app's public webhook endpoint. No secret material or privileged access is required beyond having a shop where the app is installed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind `shop` to the verified body — e.g., have `to_signable_string` incorporate the `shop-domain`, `topic`, and `webhook-id` headers rather than the body alone, so a mismatch between signed and forwarded identity is impossible. At minimum, document and enforce that `request.shop` must be cross-checked by the host app against its own persisted shop/session records before trusting it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook delivery with a valid `X-Shopify-Hmac-Sha256` header computed over the JSON body.
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the HMAC [5](#0-4) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes/persists the attacker's payload under the victim shop's tenant identity [6](#0-5) .
