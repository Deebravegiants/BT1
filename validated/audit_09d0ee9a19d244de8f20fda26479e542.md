### Title
Multisig transaction execution can run with a mismatched payload when `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` is not enabled - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
`multisig_account::validate_multisig_transaction` only cross-checks the caller-supplied `payload` against the on-chain-stored `transaction.payload` when the feature flag `features::abort_if_multisig_payload_mismatch_enabled()` is true. If that flag is not enabled on a given network/epoch, an owner can execute the pending multisig transaction while supplying an arbitrary `payload` argument different from what was actually approved by the other owners, as long as `payload_hash` is unset. This is structurally identical to the Funding.sol bug: a gating flag exists, but the "safe" state (flag cleared / not enabled) still lets a stale/attacker-controlled value flow into execution instead of the value that was actually validated by governance/co-owners.

### Finding Description
`MultisigTransaction` can store either a full `payload` (set via `create_transaction`) or just a `payload_hash` (via `create_transaction_with_hash`) [1](#0-0) .

At execution time, `validate_multisig_transaction` performs the payload-matching checks:
```
if (transaction.payload_hash.is_some()) { assert!(sha3_256(payload) == *payload_hash, ...) };
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()
) {
    assert!(payload == *stored_payload, error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
}
``` [2](#0-1) 

When `transaction.payload_hash` is `None` (the common case, since `create_transaction` stores the full payload on-chain and leaves `payload_hash` as `option::none`), the *only* place that guarantees the executed payload equals the approved payload is the second branch, and that branch is entirely gated by the `abort_if_multisig_payload_mismatch_enabled` feature flag. If that flag is off, the executing owner can supply any different `payload` bytes to the entry function and the on-chain VM will run that (mismatched) payload as the multisig transaction, while the `transactions` table is cleaned up as if the originally-voted payload were executed.

This is analogous to the Funding.sol issue: the framework has an authoritative stored value (`transaction.payload` = the vetted/approved payload, like the oracle price), and a flag intended to enforce correctness (`abort_if_multisig_payload_mismatch_enabled`, like `citadelPriceFlag`), but the flag's "off"/default state allows execution to proceed using a value that was never validated against the authoritative stored value — silently substituting attacker-controlled input for the value that multisig owners actually approved.

### Impact Explanation
If exploited, an owner (who already has legitimate execute rights due to quorum being met) can cause the multisig account to execute a transaction payload that other owners never approved — e.g., a different recipient address or amount in a coin/fungible-asset transfer, or a different function call entirely (subject to type/argument compatibility) — while consuming the approval slot of the transaction that owners *did* vote for. This breaks the multisig custody invariant that "only the exact payload approved by quorum may execute," directly enabling theft or redirection of APT/fungible-asset value held by the multisig account, which is a custody-grade, mainnet-relevant impact per the report's own scope (multisig control tied to live assets).

### Likelihood Explanation
This is gated by a feature flag rather than by hardcoded logic, so exploitability is entirely conditioned on the on-chain state of `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` at execution time. I could not confirm from the indexed code whether this flag is enabled by default in current mainnet genesis/feature-flag configuration — the `features.move` default-feature list and `vm-genesis`/`aptos-release-builder` feature-flag rollout data were only partially retrievable within the tool's index limits, and the doc comment for the flag ("Whether the multisig v2 fix is enabled... Lifetime: transient") suggests it was introduced specifically as a *fix* for this exact class of bug, meaning it is very likely already enabled on mainnet as a permanent behavior. If it is enabled, this path is not exploitable; if any network/testnet/devnet has not yet enabled it (or governance disables it), the mismatch is live. Given this ambiguity, this should be treated as a **verify-before-report** finding rather than a definitive live vulnerability.

### Recommendation
Given the uncertainty in confirming the feature flag's live/default status from the available index, do not treat the payload/hash check as optional. Concretely: unconditionally enforce `payload == *stored_payload` whenever `transaction.payload.is_some()`, independent of the `abort_if_multisig_payload_mismatch_enabled` flag, and reserve the flag purely for staged rollout/versioning rather than allowing the "off" state to bypass payload verification permanently. This removes the analog of "stale/unvalidated value used when the flag is not set."

### Proof of Concept
Not runnable — this requires confirming the on-chain state of the `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` feature flag, which could not be established from the indexed files (`features.move`'s default feature set and `vm-genesis` rollout configuration were not fully retrievable). Conceptual PoC, assuming the flag is disabled:
1. Owner A creates a multisig transaction via `create_transaction(owner_A, multisig_addr, payload_X)` — `payload` is Some(payload_X), `payload_hash` is None [3](#0-2) .
2. Owners B, C vote to approve, reaching quorum for `payload_X`.
3. Owner A (or any owner with execute rights) submits a transaction whose VM-provided `payload` argument is `payload_Y` (different call/args) to `validate_multisig_transaction`.
4. Because `transaction.payload_hash` is `None`, the hash check is skipped; because the feature flag is disabled, the full-payload equality check is skipped entirely.
5. `payload_Y` executes as the multisig transaction, and `successful_transaction_execution_cleanup` marks sequence number as resolved as if `payload_X` had been executed.

**Note:** Because I could not verify the current activation status of `ABORT_IF_MULTISIG_PAYLOAD_MISMATCH` within the indexing limits of this tool, I recommend confirming via a full repository checkout (e.g., a Devin session) whether this feature is enabled in mainnet genesis/framework release configuration before treating this as a live, exploitable finding rather than an already-patched historical issue.
