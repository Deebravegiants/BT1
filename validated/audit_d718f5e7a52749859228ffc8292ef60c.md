## Finding

### Title
Webhook shop-domain (and topic/webhook-id) headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-covered signable string from the **raw body only**, while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers. `Registry.process` validates only that the body's HMAC matches, then unconditionally trusts `request.shop` and `request.topic` (header-derived) to route and tag webhook data delivered to the host application's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates HMAC over the body, then passes the header-derived `shop`/`topic` straight to the app's handler without any additional check that they correspond to the shop that actually generated the signed body: [3](#0-2) 

The identity binding that should hold is:
`shop_that_produced(hmac-valid raw_body) == request.shop (used by handler as the tenant identity)`

This equality is not enforced anywhere in the gem. HMAC validation only proves "this body's bytes were signed with the app's secret at some point" — it says nothing about which shop's header values accompany that body. Since Shopify signs webhook bodies with the app's shared `client_secret` (the same key for every shop that has the app installed), a merchant who has the app installed on **shop A** can capture one legitimate webhook delivery (raw body + `x-shopify-hmac-sha256`), and then resend the exact same body/HMAC pair with `x-shopify-shop-domain` (and/or `x-shopify-topic`) rewritten to reference **shop B**. Because `to_signable_string` never includes the shop or topic headers, the same valid HMAC passes for a forged tenant. The app then executes the webhook handler believing the event belongs to shop B (e.g., writing/deleting data keyed by `WebhookMetadata#shop`), constituting cross-tenant data confusion/access.

This matches the target bug class exactly: a field acted upon (`shop`, used as the tenant key by the handler) is not covered by the authentication mechanism (`hmac`, computed over body only).

### Impact Explanation
This is a Critical-tier cross-tenant issue: an attacker who legitimately installs/uses the vulnerable app on their own store can forge webhook deliveries that the host application will process as belonging to an arbitrary other shop (as long as that shop's domain string is known/guessable, e.g. `*.myshopify.com` subdomains are often predictable/enumerable). Any handler logic keyed off `WebhookMetadata#shop`/`#topic` (order processing, GDPR data requests, app-uninstalled cleanup, subscription updates, etc.) can be triggered against the wrong tenant, or the same event can be replayed under a different topic than the one the merchant's shop actually fired.

### Likelihood Explanation
Moderate-to-high: exploitation requires the attacker to (a) install/have access to the app on at least one shop to legitimately capture one valid `(raw_body, hmac)` pair, and (b) know/guess the target shop's domain. Both are realistic for public apps with self-serve installation, and Shopify shop domains are frequently discoverable.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string (or otherwise cryptographically bind them, e.g. HMAC over `"#{topic}\n#{shop}\n#{raw_body}"`) rather than trusting them as bare headers. At minimum, `Registry.process` should independently corroborate `request.shop` against session/shop data already known to belong to the tenant that installed the app for the given webhook subscription, rather than trusting the header verbatim once body-HMAC passes.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret)
2. Attacker POSTs to the app's webhook endpoint with:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H          # unchanged, still valid since only B is signed
   x-shopify-shop-domain: victim-shop.myshopify.com   # forged
   ```
   and body `B` unchanged.
3. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B`: [4](#0-3) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host app to act as though this event came from `victim-shop`. [5](#0-4)
