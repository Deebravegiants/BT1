### Title
Solver output-token balance used as bid weight can be flash-inflated to dominate the phantom price median and poison indexed pool rates - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights every phantom bid by the solver's live on-chain balance of the leg's output token, and `weightedMedian` lets a single solver holding over half the total weight set the published leg price verbatim. That price is written into `PhantomOrderPriceSnapshotV2` and merged by `weightedRate` (a depth-weighted mean) into `LiquidityPool.sellRate`/`buyRate`, the exact values `IntentGateway.quoteIntent`'s default `indexed_rates` strategy uses to size real, fund-moving cross-chain intents with no fallback or sanity bound. Any permissionless solver can temporarily inflate its own destination-chain token balance (e.g. via a flash loan) at the moment the balance is read, drown out every other solver's genuine quote for that leg, and push an attacker-chosen exchange rate into the indexed pool rate that other callers of `quoteIntent` then price real orders against. This is the same failure mode as the referenced Vader finding: a manipulable, momentarily-skewable on-chain quantity is trusted as the dominant weight in an aggregate price used elsewhere for real value transfer.

### Finding Description
`runAggregation` weights each bid's quoted leg by the solver's inventory in that leg's output token, read live from the destination chain: [1](#0-0) 

`weightedMedian` then *selects* one bidder's exact quote rather than blending them, and documents explicitly that a solver holding over half the total weight sets the published price verbatim: [2](#0-1) 

The resulting `medianPrice` is written to `PhantomOrderPriceSnapshotV2` and then folded by `updateLiquidityPools`/`weightedRate` — a depth-weighted mean across chains — into the pool's canonical `sellRate`/`buyRate`: [3](#0-2) [4](#0-3) 

`LiquidityPool.sellRate`/`buyRate` are exactly the values the SDK's default, no-fallback pricing path consumes to size real cross-chain orders: [5](#0-4) [6](#0-5) 

Bidding requires only that the sender be EIP-7702 delegated to a known `SolverAccount` implementation and sign the bid with a session key — this is a permissionless "intent solver" role, not a privileged operator: [7](#0-6) 

Because the weight is a live balance read (documented as reflecting a solver's balance "as of" the block tag used, defaulting to chain head unless the caller pins an event-specific block), a solver can borrow the leg's output token (flash loan or any transient funding) immediately before the `PhantomBidWindowExhausted` aggregation runs, inflate its reported weight far above every legitimate bidder's inventory, win the weighted median outright with an arbitrary price, and return/dispose of the borrowed tokens afterward — the same "skew the input the oracle reads, then unwind" pattern as the original Vader flash-loan reserve manipulation. This directly parallels the external report's root cause: a value that dominates a downstream weighted aggregate is derived from an on-chain quantity that is cheaply and momentarily manipulable by whoever is being measured.

### Impact Explanation
`quoteIntent`'s `indexed_rates` strategy is the SDK's default and has no fallback to another price source when the pool rate looks wrong: [8](#0-7) 

If an attacker-controlled solver publishes an extreme `sellRate`/`buyRate` for a pool by winning the weighted median with a flash-inflated balance, every subsequent caller quoting that pair receives a mispriced `amountIn`/`amountOut`. A user who places an order sized from that mispriced quote can be induced to over-fund an order (loss to the user) or under-fund one that a colluding solver later fills favorably (loss to the counter-party/protocol surplus), and the manipulated rate also corrupts `queryAvailableLiquidity`/`queryBuyAndSellRates` consumers. This is a concrete route to loss of funds for anyone pricing real intents off the indexer's rates, consistent with a Medium/High severity, external-requirement-gated (attacker needs transient capital and a delegated solver identity, both permissionless) manipulation.

### Likelihood Explanation
Becoming a "solver" only requires EIP-7702-delegating an EOA to a known `SolverAccount` implementation and signing bids with a session key — no allowlisting beyond that. The balance used as weight is read live (at or near the aggregation's run time) rather than pinned to a block safely prior to the bid, so a flash loan or any transient funding taken immediately before the window closes can dominate the weight. The `weightedMedian` selection rule (a majority-weight bidder sets the price outright, not diluted into an average) makes a single dominant bid sufficient rather than requiring sustained capital, which raises likelihood relative to typical TWAP-style attacks. The main practical constraints are needing enough weight relative to genuine bidders on a specific pair/window and timing the balance-inflating transaction to land before the RPC read — both are within reach of a well-resourced but unprivileged actor, similar to the original report's assumptions.

### Recommendation
- Do not weight bids by an instantaneously-read balance. Require the weighting balance to be pinned to a block safely before the bid window opens (e.g., the block the `PhantomOrderV2` was created, or an average/TWAP of the solver's balance over the bid window) so a same-window flash loan cannot inflate it.
- Cap a single bidder's influence on `weightedMedian`/`weightedRate` (e.g., clamp weight contribution to some fraction of total observed weight across the window) so no single solver can set the published rate outright.
- Treat a `sellRate`/`buyRate` update that moves beyond a sanity bound (vs. the previous accepted rate or an external reference) as suspect and require corroboration (e.g., multiple independent chains/samples) before it is trusted by `quoteIntent`'s default strategy, mirroring the “fair reserves via invariant + external price” mitigation recommended in the original report.
- Consider requiring `quoteIntent` (or its indexed_rates strategy) to cross-check the indexed rate against a secondary source (Uniswap V4 pool price, Chainlink, etc.) before using it to size real fund transfers, rather than trusting the indexer rate unconditionally with "no fallback."

### Proof of Concept
1. Attacker delegates an EOA (`Solver`) via EIP-7702 to a recognized `SolverAccount` implementation on the destination chain — a normal, permissionless act any intent solver performs.
2. Attacker waits for (or triggers, by placing a phantom-priced order matching the target pool) a `PhantomOrderV2` window on the pair to be manipulated.
3. Immediately before/at the block the indexer's `handlePhantomOrderPrices` runs `aggregatePhantomBids` (triggered by `PhantomBidWindowExhausted`), attacker flash-loans a very large amount of the leg's output token onto `Solver`'s address on the destination chain, so `getBalance`/`getTotalSolverBalance` reports an inventory far exceeding all genuine solvers' combined weight — see the live balance read at [9](#0-8) .
4. `Solver` submits a single verified bid quoting an arbitrary (attacker-favorable) output amount for that leg.
5. `weightedMedian` computes cumulative weight and, because `Solver`'s weight exceeds half the total, returns `Solver`'s exact quoted price verbatim — see [10](#0-9) .
6. Attacker repays/unwinds the flash loan; `Solver`'s true balance returns to near zero, but the manipulated `medianPrice` is already persisted to `PhantomOrderPriceSnapshotV2` and merged into `LiquidityPool.sellRate`/`buyRate` by `weightedRate` — see [3](#0-2) .
7. Any subsequent `quoteIntent` call for that pair (default `indexed_rates` strategy, no fallback) prices real orders from the poisoned `LiquidityPool` rate — see [5](#0-4)  — letting the attacker profit from users' or the protocol's mispriced fund transfers.

Note: I could not confirm from the indexed code exactly how many blocks/how tight the window is between `PhantomBidWindowExhausted` firing and the balance read executing (this depends on indexer scheduling/RPC latency not fully covered in the indexed files), so the precise minimum flash-loan window is uncertain; a Devin session with full repo/build access would be needed to verify exact timing bounds and any block-tag pinning added elsewhere that might mitigate this.

// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

// The one rate-merge policy: depth-weighted average, falling back to the unweighted mean when
// the whole sample set carries zero depth (so a price is still reported). Every merge in this
// file — collapsed legs, the cross-chain pool merge, and the divergence alarm's consensus —
// must agree on this, hence the single home.
function weightedRate(samples: { rate: bigint; depth: bigint }[]): bigint {
	const depth = samples.reduce((acc, sample) => acc + sample.depth, 0n)
	return depth > 0n
		? samples.reduce((acc, sample) => acc + sample.rate * sample.depth, 0n) / depth
		: samples.reduce((acc, sample) => acc + sample.rate, 0n) / BigInt(samples.length)
}
