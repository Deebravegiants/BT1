## Analysis

### Title
Unchecked-transfer-amount assumption in `pallet-psm::mint` mints uncollateralized internal asset when `Fungibles` is backed by a fee-on-transfer/deflationary token - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
The Yieldy report describes contracts that transfer `amount` of an ERC20, then mint/credit the *same* `amount` to a user, assuming the receiver got exactly what was sent — which breaks for deflationary/fee-on-transfer tokens. The same pattern exists in the newly added `pallet-psm` pallet's `mint()` extrinsic, which transfers an external asset into the PSM reserve and then mints internal asset based on the *requested* amount rather than the *actually received* amount.

### Finding Description
In `Pallet::mint`, the pallet computes `effective_external` from the caller-desired `external_amount`, transfers it via the generic `T::Fungibles::transfer` call, and then unconditionally mints `internal_to_user` (and the fee) computed from that same pre-transfer amount, without re-checking the PSM reserve's balance delta: [1](#0-0) 

`T::Fungibles` is a fully generic associated type, bounded only by `FungiblesMutate<AccountId, AssetId = Self::AssetId>` etc.: [2](#0-1) 

The default `Mutate::transfer` implementation in `frame_support` simply calls `decrease_balance`/`increase_balance` and returns the requested `amount`, trusting the underlying implementation's bookkeeping rather than measuring an actual balance delta: [3](#0-2) 

For an accounting-based backend such as `pallet-assets`/`pallet-balances`, this is safe because balance changes are exact 1:1 internal ledger operations. However, `pallet-revive` exposes a `fungibles::Mutate`/`Inspect` adapter (`impl_fungibles.rs`) that represents an *arbitrary on-chain ERC20 contract* as a fungible asset identified by its `H160` address, driving real `transfer`/`balanceOf` calls into the contract: [4](#0-3) 

If a runtime configures `pallet-psm::Config::Fungibles` (directly, or transitively via a `fungibles` union/adapter) to route through this revive-backed asset representation, an "external asset" approved for a PSM instance could be a real, arbitrary ERC20 contract — including a deflationary/fee-on-transfer one. In that case `T::Fungibles::transfer(external_asset, &who, &psm_account, effective_external, ...)` would silently return `Ok(effective_external)` even though the PSM reserve account actually received less (the contract's own `transfer` logic burns/redirects part of the value), while `mint_into(internal_asset, &who, internal_to_user)` still mints the full amount based on the *requested* value. This is structurally identical to Yieldy's `Staking::stake()`/`LiquidityReserve::addLiquidity()` bug: transfer-then-mint-same-amount without verifying the real amount received.

The `asset-conversion` pallet's `do_add_liquidity` has the analogous pattern too — reserves are read before the transfer, `amount1`/`amount2` (the *desired*, not observed, amounts) are transferred, and LP tokens are minted from those same pre-transfer values rather than the post-transfer reserve delta: [5](#0-4) 

### Impact Explanation
If a PSM instance (or an asset-conversion pool) is ever backed by an `AssetKind`/`Fungibles` implementation whose `transfer` can deliver less than the nominal amount (fee-on-transfer/deflationary/rebasing token, most plausibly reachable through the `pallet-revive` ERC20 fungibles bridge), every `mint`/`add_liquidity` call under-collateralizes the internal asset or LP-token pool. The PSM's `internal_asset` (or LP token) supply grows unbacked by real reserves, and later redemptions/removals by other, honest users will drain real reserves and fail once they're exhausted — a direct loss of user funds, exactly matching the referenced finding's impact.

### Likelihood Explanation
Likelihood is **conditional, not immediate**, on the concrete configuration: with the standard/expected backends (`pallet-assets`, `pallet-balances`), balances move 1:1 and the issue cannot occur. It only manifests when an external asset routed through `pallet-psm`/`pallet-asset-conversion` is ultimately backed by contract-controlled transfer semantics (e.g., via `pallet-revive`'s `impl_fungibles.rs`), and once such an asset is approved (via `add_external_asset`/`create_pool`, which are privileged/permissioned actions), *any unprivileged user* calling the public `mint`/`add_liquidity` extrinsic triggers the shortfall — no attacker privilege is needed at call time, mirroring the original report where the exploit is triggered by ordinary `stake()`/`addLiquidity()` calls once a deflationary token is already integrated.

### Recommendation
In `Pallet::mint` (and `do_add_liquidity`), measure the PSM reserve's/pool's actual balance before and after the `transfer` call and use the observed delta (not the requested amount) when computing `internal_to_user`/`lp_token_amount`. Alternatively, explicitly document and enforce (e.g., via a metadata check or an allow-list requiring "standard" 1:1 transfer semantics) that `Config::Fungibles`/`Config::Assets` must never be backed by deflationary/fee-on-transfer/rebasing token implementations, consistent with how the referenced protocol chose to explicitly disclaim support rather than patch the code.

### Proof of Concept
Conceptual PoC (cannot be fully executed without a concrete runtime wiring `pallet-psm::Config::Fungibles` to a `pallet-revive`-backed ERC20 asset):
1. Configure a runtime where `pallet-psm::Config::Fungibles` (or a `fungible::UnionOf` adapter feeding it) resolves an `AssetId` to a `pallet-revive` ERC20 contract via `impl_fungibles.rs`.
2. Deploy/approve as `external_asset` an ERC20 contract that charges e.g. a 2% fee on every `transfer` (deflationary/fee-on-transfer token), and register it with `add_external_asset`.
3. A regular user calls `Pallet::mint(internal_asset, external_asset, external_amount, max_fee)`.
4. `T::Fungibles::transfer` invokes the ERC20's `transfer`, which only delivers `external_amount * 0.98` to the PSM reserve account, `impl_fungibles.rs::mint_into`/`burn_from` don't re-verify actual balance-delta against the requested `amount` (see `burn_from` at lines 162-203 which trusts the `did_revert`/`decode` success flag, not an on-chain balance diff check tied back into `mint`'s accounting).
5. `Pallet::mint` still computes and mints `internal_to_user` from the full, pre-fee `internal_equivalent`, crediting the caller with more internal-asset value than was actually deposited into the reserve — extractable at the expense of later PSM redeemers. [6](#0-5)

			external_asset: T::AssetId,

			max_fee: Permill,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let info = Psm::<T>::get(&internal_asset).ok_or(Error::<T>::PsmNotFound)?;

				Self::ensure_decimals_match(&info, &internal_asset, &external_asset, &external)?;

			let internal_equivalent =
				Self::external_to_internal(external_amount, ext_decimals, internal_decimals)?;
			ensure!(!internal_equivalent.is_zero(), Error::<T>::AmountTooSmallAfterConversion);
			ensure!(internal_equivalent >= info.min_swap_amount, Error::<T>::BelowMinimumSwap);

			let effective_external =
				Self::internal_to_external(internal_equivalent, ext_decimals, internal_decimals)?;

			let fee_rate = MintingFee::<T>::get(&internal_asset, &external_asset);
			ensure!(fee_rate <= max_fee, Error::<T>::FeeTooHigh);
			let fee = fee_rate.mul_ceil(internal_equivalent);
			let internal_to_user = internal_equivalent.saturating_sub(fee);

			let current_total_psm_debt = Self::total_psm_debt(&internal_asset);
			ensure!(
				current_total_psm_debt.saturating_add(internal_equivalent) <= info.max_debt,
				Error::<T>::ExceedsMaxPsmDebt
			);

			let current_debt = PsmDebt::<T>::get(&internal_asset, &external_asset);
			let max_debt = Self::max_asset_debt(&internal_asset, &external_asset, &info);
			let new_debt = current_debt.saturating_add(internal_equivalent);
			ensure!(new_debt <= max_debt, Error::<T>::ExceedsMaxPsmDebt);

	fn transfer(
		asset: Self::AssetId,
		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,
		preservation: Preservation,
	) -> Result<Self::Balance, DispatchError> {
		let _extra = Self::can_withdraw(asset.clone(), source, amount)
			.into_result(preservation != Expendable)?;
		Self::can_deposit(asset.clone(), dest, amount, Extant).into_result()?;
		if source == dest {
			return Ok(amount);
		}

		Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
		// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
		// anyway.
		let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
		Self::done_transfer(asset, source, dest, amount);
		Ok(amount)
	}
