### Title
Vault gateway `writeMethodsEnabled` kill switch blocks users from deleting (withdrawing) their own secrets when disabled - (File: `core/services/gateway/handlers/vault/handler.go`)

### Summary
The gateway-side Vault handler gates `vault.secrets.delete` behind the same `writeMethodsEnabled` gate limiter used for `create`/`update`. When this operator-controlled setting is disabled, users lose the ability to delete their own previously-stored secrets, even though `DeleteSecrets` is the user's sole self-service mechanism to remove/retract their own owned data — functionally analogous to a "withdraw" operation in the referenced report. [1](#0-0) 

### Finding Description
`handleSecretsDelete` calls `h.writeMethodsEnabled.AllowErr(ctx)` and, if the limiter denies the request, immediately returns an `UnsupportedMethodError` response without ever forwarding the delete request to the DON: [1](#0-0) 

This is the exact same gate used for `handleSecretsCreate` and `handleSecretsUpdate`: [2](#0-1) 

The gate is constructed from a global settings flag (`cresettings.Default.GatewayVaultManagementEnabled`) at handler construction time: [3](#0-2) 

In contrast, `handleSecretsList` — a read path — is not subject to this gate at all: [4](#0-3) 

The bug-class parallel to the external report is direct: in `RelayerV2.sol`, `withdraw()` is blocked by `whenNotPaused`, denying users access to their own already-deposited assets whenever a privileged party pauses the protocol. Here, `vault.secrets.delete` — the user's mechanism to remove their own already-stored secret — is blocked by the same "write methods disabled" switch used for create/update, with no separate exemption for delete despite delete being a data-removal (self-custody exit) operation rather than a new-write operation.

### Impact Explanation
While disabled, secrets already stored by a user under `MethodSecretsCreate`/`MethodSecretsUpdate` cannot be deleted through the gateway. This matters particularly for secret rotation/incident response: if an owner needs to purge a compromised secret, they cannot do so while the write-methods gate is off, and the value remains retrievable by workflows (`GetSecrets` has no such gate) for as long as the outage persists. This is a moderate-impact, low-likelihood availability/control issue rather than a fund-loss issue, since this is a secrets-management capability, not a token vault — however the structural bug (conflating "read-only pause" with "delete pause") is identical to the reported class.

### Likelihood Explanation
Requires an operator to disable `GatewayVaultManagementEnabled` (e.g., during an incident, maintenance, or as a defensive measure), which is a deliberate/privileged action, so likelihood is low — mirroring the low-likelihood rating of the original finding (guard must intentionally pause).

### Recommendation
Exempt `vault.secrets.delete` from the `writeMethodsEnabled` gate the same way `vault.secrets.list` is exempted, so that users always retain the ability to remove/purge their own secrets, analogous to the report's recommendation to remove `whenNotPaused` from `withdraw()`. If a distinct "delete-disable" control is desired for other operational reasons, it should be a separate, explicitly-named setting rather than reusing the create/update write gate.

### Proof of Concept
1. Deploy the gateway Vault handler with `cresettings.Default.GatewayVaultManagementEnabled` resolved to "disabled" (or trigger the underlying `limits.GateLimiter` to deny).
2. As a normal authorized user, previously create a secret via `vault.secrets.create` while the gate was enabled.
3. With the gate now disabled, send a `vault.secrets.delete` request for that secret through the gateway handler's `HandleJSONRPCUserMessage` → `handleSecretsDelete` path.
4. Observe the handler returns an `UnsupportedMethodError` ("vault write methods(create/update/delete) are disabled…") without ever fanning the request out to the DON, per `core/services/gateway/handlers/vault/handler.go` lines 643-656 — the user cannot delete their own secret despite being fully authorized to do so.

func (h *handler) handleSecretsCreate(ctx context.Context, ar *activeRequest) error {
	l := logger.With(h.lggr, "method", ar.req.Method, "requestID", ar.req.ID)

	err := h.writeMethodsEnabled.AllowErr(ctx)
	if errors.Is(err, limits.ErrorNotAllowed{}) {
		l.Warnw("secrets write method called but write methods are disabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.UnsupportedMethodError, errors.New("vault write methods(create/update/delete) are disabled: "+err.Error()), nil))
	} else if err != nil {
		l.Errorw("error checking if write methods are enabled", "error", err)
		return h.sendResponse(ctx, ar, h.errorResponse(ar.req, api.FatalError, errors.New("error checking if write methods are enabled: "+err.Error()), nil))
	}

	return h.fanOutToVaultNodes(ctx, l, ar)
}
