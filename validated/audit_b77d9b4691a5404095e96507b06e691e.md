### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant identifier) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body, never over the shop-domain header. An attacker who can obtain any body+HMAC pair signed with the app's shared secret (e.g., by installing the app on their own store and capturing a legitimate webhook delivery) can resend that same body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature still validates, and the handler receives attacker-controlled data tagged with a victim shop's domain.

### Finding Description
The HMAC verification path is:
- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Webhooks::Request#shop` reads the `shop-domain` header directly, entirely outside the signed payload: [2](#0-1) 
- `HmacValidator.validate_signature` computes the digest strictly over `verifiable_query.to_signable_string` (i.e., body only) and compares it to the received `hmac`: [3](#0-2) 
- `Webhooks::Registry.process` validates only the HMAC, then immediately trusts `request.shop` to build the metadata passed to the app's handler, with no separate check binding shop to signature or to a known installed session: [4](#0-3) 

The binding that is broken is: `shop conveyed to the handler == shop authenticated by the HMAC`. In fact the HMAC authenticates only the body bytes; the shop field is unauthenticated metadata that the registry treats as trusted tenant identity. This is exactly the class of bug called out for identity-binding analogs: "a field acted on but not covered by the HMAC."

Because the app's `client_secret` (used to sign every webhook for every shop under that app) is shared across all shops that install the app, any unprivileged attacker who installs the app on their own store can:
1. Trigger a real webhook event (e.g., `orders/create`) on their own shop and capture the legitimate `(raw_body, hmac)` pair Shopify sends.
2. Replay that exact body and HMAC to the app's webhook endpoint, but with the `shop-domain` header rewritten to the victim shop's domain.
3. `HmacValidator.validate` still returns `true` because it never inspected the shop header, so `Registry.process` proceeds and calls the handler with `WebhookMetadata` claiming `shop: <victim shop>` while `body` is attacker-controlled.

### Impact Explanation
This crosses a tenant boundary: attacker-controlled webhook payloads are delivered to the host application labeled as belonging to a different (victim) merchant. Any host app that uses `data.shop` from the webhook handler to look up/update per-tenant records (which is the documented intended usage) can have its data model poisoned or actions taken against the wrong tenant using attacker-supplied content, which meets the "cross-tenant access" criterion.

### Likelihood Explanation
Any unprivileged internet user can become "privileged enough" simply by installing the target app on their own development/test store (a normal, unprivileged action for any Shopify app that supports installation), which gives them a legitimately signed `(body, hmac)` pair without needing the app's `client_secret` or any victim credentials. Forging the `shop-domain` header on an HTTP POST requires no special access.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed payload verification, or require the application to cross-check `request.shop` against a set of shops with an active/installed session before trusting it in `WebhookMetadata`. At minimum, document and enforce that `shop` must be validated against known installed shops before being used as a tenant key in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger `orders/create` to receive a real webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's shared secret).
2. Resend an HTTP POST to the app's webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` returns `true` because only `B` is checked against `H` (`lib/shopify_api/webhooks/request.rb:36-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process attacker data under the victim's tenant identity.
