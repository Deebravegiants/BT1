### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing tenant-binding spoofing via header manipulation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, but the shop-identifying header (`x-shopify-shop-domain` / `shopify-shop-domain`) — along with `topic`, `api_version`, and `webhook_id` — are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler as trusted tenant metadata.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator calls `verifiable_query.to_signable_string`, and for `Webhooks::Request` this method returns only `@raw_body` [2](#0-1) . The HMAC computed by `HmacValidator.validate_signature` therefore authenticates the raw body bytes with the shared secret, but nothing else [3](#0-2) .

The `shop` accessor, however, is read straight from the `shop-domain` header, not from the signed body [4](#0-3) . Immediately after HMAC validation succeeds, `Registry.process` builds `WebhookMetadata` using `request.shop` (the unauthenticated header value) as the tenant identifier passed to the app's handler [1](#0-0) . `WebhookMetadata.shop` is a plain `String` field with no cryptographic binding to the payload [5](#0-4) .

This breaks the intended identity binding:
`shop authenticated (bytes covered by HMAC)` ≠ `shop used as tenant key (bytes read from header, unauthenticated)`.

Because the signature is computed only over `@raw_body`, any request carrying a genuine `raw_body` + valid HMAC for that body (e.g., a webhook payload previously delivered to the app for Shop A, which the attacker can observe since they received it as the shop's own webhook endpoint operator or via a webhook relay/proxy they control) remains **HMAC-valid** even if the `x-shopify-shop-domain` header is changed to Shop B. The gem has no mechanism to detect this because the header is never part of the signed content.

### Impact Explanation
An unprivileged actor who can influence or replay the header set of a webhook delivery (for example, an app that fronts webhook delivery through a shared endpoint, a proxy, load balancer, or CDN that re-writes/duplicates headers, or a party that captured one legitimately-signed payload) can cause the receiving application to process a webhook body under the identity of an arbitrary other shop, without needing `api_secret_key` or any other credential — they only need one legitimately-signed body/HMAC pair and control over the HTTP header delivered to the app. Downstream apps that use `WebhookMetadata#shop` as an authorization/tenant key (the documented and expected use, per `Webhooks::Registry.process`) would then attribute webhook data to the wrong tenant — a cross-tenant data-integrity/authorization issue. This matches the Critical category "cross-tenant access" since the HMAC check, the only authenticity control the gem performs, gives a false sense of full-message authenticity while the tenant-selecting field is unauthenticated.

### Likelihood Explanation
Exploitability depends on the attacker having a route to deliver a request to the app's webhook endpoint with attacker-controlled headers but a body+HMAC pair that was genuinely signed by Shopify for a *different* shop's event (e.g., through header-rewriting proxies, misconfigured multi-tenant fronting infrastructure, or webhook forwarders). This is a real deployment pattern for apps using shared webhook ingestion pipelines, but it is not exploitable from a bare unauthenticated HTTP client with no visibility into any valid signed payload. Likelihood is therefore moderate and conditioned on the app's network topology, but the root cause — headers excluded from the signed content — is a hard defect in this gem regardless of deployment.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a separate binding check in `Registry.process`) so the shop domain (and ideally topic/api_version/webhook_id) are cryptographically bound to the verified payload — e.g., by cross-checking the header-derived `shop` against a shop value embedded/expected in the payload where available, or by treating header-derived identity as untrusted and requiring the calling application to independently verify the shop against its own webhook subscription records rather than trusting `WebhookMetadata.shop` implicitly. At minimum, document prominently that `WebhookMetadata.shop` is not authenticated by the HMAC and must not be used as a sole tenant-selection key without additional verification.

### Proof of Concept
1. Attacker (or a component in the delivery path they control, e.g., a shared reverse proxy) obtains a legitimately Shopify-signed webhook: body `B` with header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`, originally delivered with `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body successfully (all required headers present) [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` and compares to `H` — this passes because `B` and `H` are unchanged [7](#0-6) [8](#0-7) .
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` using the spoofed `shop-b.myshopify.com` value, and dispatches it to the handler as if the event genuinely originated for Shop B [9](#0-8) .
6. The app's handler, trusting `data.shop` for tenant scoping, processes Shop A's webhook data under Shop B's tenant context — a cross-tenant identity violation the gem's HMAC check was supposed to prevent but does not, since `shop` was never part of the signed bytes.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
