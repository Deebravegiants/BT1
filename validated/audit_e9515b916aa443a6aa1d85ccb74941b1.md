### Title
Stale delegate grant silently re-arms on NFT return, restoring account control without the owner's renewed consent - (File: contracts/controller/src/storage/account.rs)

### Summary
The controller stamps each account's `DelegateGrant` with the `granted_by` address and treats the grant as live whenever `granted_by` equals the current NFT owner (`get_delegates`, `contracts/controller/src/storage/account.rs:176-181`). Transferring the position NFT deactivates the grant but never deletes it. If the token later returns to the original granter, the old delegate list becomes fully active again with no fresh authorization from the owner. This is the direct analog of CVE-2020-13300's "authorization scope change without user consent in the middle of the flow": the authority an old delegate holds silently expands back over the account, which may by then carry a materially different (larger) collateral and debt profile than what the owner ever consented to delegate.

### Finding Description
- `set_delegates` stores `DelegateGrant { granted_by: owner, delegates }` under `ControllerKey::Delegates(account_id)` (`storage/account.rs:185-199`). There is a single slot per account, keyed by account id, not by ownership epoch.
- `get_delegates` filters purely on `grant.granted_by == *owner` where `owner` is resolved live via `owner_of` on the position NFT (`storage/account.rs:176-181`, `try_account_owner` at :35-38). The comment concedes the semantics: "Ownership changes invalidate a previous owner's grants without deleting them."
- `remove_delegate` explicitly acknowledges the resurrection hazard — it deletes stale grants precisely "preventing those grants from reactivating if the NFT returns to their original owner" (`storage/account.rs:226-238`). But nothing performs that cleanup on transfer itself: only an owner-initiated `remove_delegate` or an intervening owner's `add_delegate` (which overwrites the slot) clears it.
- The position NFT is a plain transferable token; transfer changes nothing in the controller (`contracts/position-nft/README.md:39-41`). The NFT-level `approve`/`approve_for_all` clear or stay owner-scoped correctly, but the controller-side delegate slot survives untouched across any number of transfers.
- Delegates are not passive: per the threat model they "can borrow/withdraw to their chosen recipient within account gates" and "those gates do not constrain them to acting in the owner's economic interest" (`docs/explanation/threat-model.md:81-87`). `is_owner_or_delegate` therefore hands a re-armed delegate full extraction power over the account's net equity.

Attack sequence a single unprivileged delegate can execute:
1. Alice holds account `N` and calls `add_delegate(N, M)` while the position is small. Grant is stamped `granted_by = Alice`.
2. Alice transfers NFT `N` to Bob (sale, collateralized listing, marketplace settlement — all legitimate `transfer` calls). `get_delegates` now returns empty; M is dormant but not deleted.
3. Bob loads the account with collateral (or the account simply accrues value), then the NFT returns to Alice — e.g., Bob transfers it back, Alice repurchases it, or it round-trips through a marketplace. Alice never calls `add_delegate` or `remove_delegate`; she never re-consents to M.
4. The instant `owner_of(N) == Alice` again, `get_delegates(N, Alice)` returns M. M calls `controller::borrow`/`withdraw` with `caller = M`, `account_id = N`, and a recipient M controls, draining the account's withdrawable equity down to the LTV limit.

### Impact Explanation
Theft of user funds. The re-armed delegate can borrow and withdraw to an arbitrary recipient, extracting all collateral above the LTV-weighted debt floor — potentially far more than the position held when the grant was made, since intermediate owners may have grown it. The returning owner receives no prompt, signature request, or on-chain checkpoint; consent from an earlier ownership epoch is silently applied to a new, larger scope, exactly matching the CVE class. Severity: High.

### Likelihood Explanation
Medium. It requires the NFT to return to a former owner who once set delegates and never cleaned them up — plausible via buybacks, marketplace round-trips, OTC re-acquisition, or even deliberate grooming by a counterparty who knows a stale grant exists (the grant is readable on-chain via `get_delegates`, so M or a collaborator can watch for `owner_of` reverting to `granted_by`). No privileged role, oracle manipulation, or timing race is needed; the trigger is an ordinary `transfer`.

### Recommendation
Bind the grant to an ownership epoch, not just an address:
- Stamp `DelegateGrant` with a monotonically increasing per-account transfer epoch (increment a counter in the controller whenever `owner_of` is observed to change, or store `granted_by` together with a transfer nonce/ledger sequence recorded at grant time), and have `get_delegates` require both fields to match the current epoch.
- Alternatively, make the position NFT's `transfer`/`transfer_from` invoke a controller hook (or expose a permissionless `on_transfer(account_id)` cleanup) that deletes `ControllerKey::Delegates(account_id)` on every ownership change, mirroring how the NFT clears its own per-token `Approval` entry on transfer.

### Proof of Concept
1. `supply(caller=Alice, account_id=0, ...)` → creates account `N`, NFT `N` minted to Alice.
2. Alice calls the delegate management entrypoint `add_delegate` (controller) for `N` with delegate `M`. Storage now holds `DelegateGrant{granted_by: Alice, delegates: [M]}` at `ControllerKey::Delegates(N)`.
3. Alice calls `position_nft::transfer(Alice → Bob, N)`. `get_delegates(N, Bob)` → `[]`; M is inactive.
4. Bob calls `supply(caller=Bob, account_id=N, ...)`, topping up the account (permitted for existing supply slots per `INV-ACCT-03`), then transfers NFT `N` back to Alice.
5. `get_delegates(N, Alice)` → `[M]`: the grant re-armed with no transaction signed by Alice.
6. M calls `withdraw(caller=M, account_id=N, withdrawals=[...], to=M)` — `is_owner_or_delegate` passes — and takes the collateral Bob supplied plus Alice's original equity up to the solvency limit.

Supporting code: `get_delegates`/`set_delegates`/`remove_delegate` (`contracts/controller/src/storage/account.rs:176-247`); live owner resolution (`:35-44`); transfer changes nothing controller-side (`contracts/position-nft/README.md:39-41`, `:174-179`); delegate powers (`docs/explanation/threat-model.md:81-87`).

Note: the repository documents the re-arm mechanism in `README.md` and `threat-model.md`, which describes it as a known behavior rather than an explicitly blessed design decision; I have flagged it anyway because the consent-free scope expansion matches the vulnerability class and enables fund theft. If reviewers classify this documentation as an ADR acceptance, this finding should be downgraded/rejected.
