### Title
Phishing risk via user-controlled `to` recipient in `Controller::withdraw` and `Controller::borrow` - ([File: contracts/controller/src/positions/supply.rs])

### Summary
`Controller::withdraw` and `Controller::borrow` accept an optional `to: Option<Address>` parameter that lets the authorized caller redirect the payout to any external address. The only recipient validation is `require_external_recipient`, which rejects the pool and controller contracts but not arbitrary third parties. An attacker can phish an account owner or delegate into submitting a withdrawal/borrow with `to` set to the attacker's address, permanently diverting the user's collateral or borrowed funds.

### Finding Description
In `process_withdraw`, after `require_owner_or_delegate` authorizes the caller, the payout address is taken verbatim from user input: `let recipient = to.unwrap_or_else(|| caller.clone());` and `require_external_recipient(env, &mut cache, &recipient)` is called, then `settle_withdraw` pays the pool's `transfer_out` to `recipient` [1](#0-0) . The identical pattern exists for borrows in `process_borrow` [2](#0-1) . `require_external_recipient` only blocks the pool and controller addresses (per the GH-17 guard and its tests), so any ordinary EOA/contract — including an attacker's — is accepted [3](#0-2) . A test explicitly confirms third-party payout succeeds: `withdraw_to_raw(ALICE, "USDC", ..., &bob)` pays BOB while debiting ALICE's supply [4](#0-3) . Since the account owner signs the transaction, Soroban auth does not protect against a socially engineered `to` value — exactly the `requestWithdraw(receiver)` phishing class from the source report.

### Impact Explanation
Successful phishing results in direct theft of user funds: the victim's supply shares are burned and the underlying tokens are transferred to the attacker (or, for `borrow`, the victim takes on debt while the attacker receives the borrowed assets). No protocol invariant is violated, so the transaction executes cleanly and irreversibly.

### Likelihood Explanation
Requires social engineering — tricking a depositor into signing a `withdraw`/`borrow` call with a hostile `to` argument (malicious frontend, fake "reward claim" dApp, etc.). The attack surface exists solely because the parameter exists; removing it eliminates the vector entirely. Rated Medium, matching the source report.

### Recommendation
Remove the `to` parameter from `withdraw` (and `borrow`) and pay `caller` unconditionally, or restrict `to` to `account.owner`. If third-party payout is an intentional feature (e.g., for strategy adapters), document the phishing exposure and require `to` to equal `caller` or `account.owner` unless the caller is the owner itself.

### Proof of Concept
1. Alice supplies 10,000 USDC; her account is publicly visible on-chain.
2. Attacker presents Alice a malicious interface that calls `Controller::withdraw(caller=alice, account_id=alice_id, withdrawals=[(usdc_hub_asset, 0)], to=Some(attacker))` — amount `0` withdraws the entire position (`ZeroLeg::MeansAll` / `WITHDRAW_ALL_SENTINEL`) [5](#0-4) .
3. Alice signs; `process_withdraw` resolves `recipient = attacker`, `require_external_recipient` passes since attacker is neither pool nor controller.
4. `settle_withdraw` → `apply_withdraw_batch` → pool `transfer_out` sends the full balance to `attacker` while Alice's supply position is zeroed [6](#0-5) . Demonstrated benignly by the existing test where `withdraw_to_raw` pays an unrelated BOB [7](#0-6) .
5. Same flow applies to `borrow`: `to=Some(attacker)` gives the attacker the borrowed tokens while debt accrues on Alice's account [2](#0-1) .

#[test]
fn test_withdraw_to_pays_third_party_recipient() {
    let mut t = LendingTest::new()
        .with_market(usdc_preset())
        .with_dust_disabled_all_markets()
        .build();

    t.supply(ALICE, "USDC", 10_000.0);
    let bob = t.get_or_create_user(test_harness::BOB);

    let alice_wallet_before = t.token_balance_raw(ALICE, "USDC");
    let bob_wallet_before = t.token_balance_raw(test_harness::BOB, "USDC");

    let paid = t.withdraw_to_raw(ALICE, "USDC", 30_000_000_000, &bob);
    let (_, paid_amount) = paid.get(0).unwrap();
    assert_eq!(paid_amount, 30_000_000_000);

    assert_eq!(
        t.token_balance_raw(test_harness::BOB, "USDC") - bob_wallet_before,
        30_000_000_000
    );
    assert_eq!(t.token_balance_raw(ALICE, "USDC"), alice_wallet_before);
    t.assert_supply_near(ALICE, "USDC", 7_000.0, 1.0);
}
