### Title
Webhook shop-tenant identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary

### Finding Description
The external report's root cause is that a value which is *acted on* by the receiver (`to_chain`/`to_handler`) is not covered by the message's authenticity check, allowing the trusted signature to be replayed against an unintended identity binding. The same class of bug exists in this gem's webhook processing pipeline.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) is read completely independently of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate`, which only checks `verifiable_query.to_signable_string` (i.e., the raw body) against `verifiable_query.hmac`: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `process` dispatches to the app's handler with `shop: request.shop` taken straight from the unauthenticated header: [5](#0-4) 

The identity-binding equality that should hold is: `shop_the_signature_was_computed_for == shop_the_handler_believes_the_event_came_from`. Because the same `Context.api_secret_key` is shared across every shop that installs the app, and the signable string never includes the shop, this equality does not hold — the HMAC only proves "this body was signed by our app secret," not "this body pertains to shop X."

### Impact Explanation
Any tenant (shop) that has installed the app can capture a genuine, validly-signed webhook payload/HMAC pair addressed to itself (e.g., by intercepting its own webhook traffic, which it legitimately receives), and then replay the identical `raw_body` + `hmac` to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Registry.process` will pass the HMAC check (since only the body is validated) and invoke the registered handler with `data.shop` equal to the victim shop, `data.topic`, and `data.body` unchanged. Any app that uses `WebhookMetadata#shop` to scope per-tenant state (the intended and documented usage per `docs/usage/webhooks.md`) will process attacker-controlled, falsely-attributed data under another merchant's tenant identity — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Requires only that the attacker be a legitimate (if malicious) merchant who has installed the app — no `api_secret_key`, access token, or TLS interception is needed, since the request is being forged against the developer's own public webhook endpoint, not against Shopify. This satisfies the "unprivileged internet user" bar since installing an app is a self-service action.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`) in the HMAC-signable string used for webhook verification, or otherwise cryptographically bind the shop to the signed payload, so that `Utils::HmacValidator.validate` cannot succeed when the shop identity has been swapped independently of the signed body.

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and `victim.myshopify.com`, both under the same app (`Context.api_secret_key` shared).
2. Shopify sends a legitimate webhook to the app's endpoint for `attacker.myshopify.com`:
   - headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of raw_body>`
   - body: `{"id": 1, ...}`
3. Attacker (who controls/observes this traffic to their own installed app) resends the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only (line 12-22 of `hmac_validator.rb`) — validation succeeds because the body is unchanged.
5. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop == "victim.myshopify.com"`, even though the payload actually originated from `attacker.myshopify.com`'s webhook stream [5](#0-4) .

**Note on uncertainty**: I was not able to fully explore `lib/shopify_api/webhooks/webhook_handler.rb` (the `WebhookMetadata` struct) in this session, so I cannot show its exact field list from source, but its usage as `shop:` is confirmed by the call site above and by `docs/usage/webhooks.md`'s guidance to register/process per-shop webhooks.
