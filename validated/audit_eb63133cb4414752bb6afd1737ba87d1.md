## Title
Webhook `shop-domain` header not covered by HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` authenticate a webhook by verifying the HMAC signature over the **raw request body only**. The `shop` (tenant identity) that the library hands to the app's webhook handler is read from the `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed material. This breaks the identity binding `HMAC-authenticated body == tenant the app believes sent it`, letting anyone who can produce one validly-signed webhook (e.g., from their own shop, since the signing secret is the app's shared `client_secret`, not shop-specific) relabel it as coming from any other shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read straight from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `to_signable_string` and compares it against the `hmac` header — `shop` never enters the computation: [3](#0-2) 

`Registry.process` trusts this unauthenticated `shop` value and forwards it directly to the app's handler as the tenant identifier, with no additional cross-check against the body or any other bound field: [4](#0-3) 

Because the same `client_secret` (app secret) is used to sign webhooks for *every* shop that installs the app, an unprivileged holder of one valid `(raw_body, hmac)` pair from their own shop's install can replay it to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value. `HmacValidator.validate` still returns `true` because it only checks the body's signature, so `Registry.process` calls the handler with `shop: <attacker-chosen victim domain>`, `body: <attacker's own webhook payload>`. This is exactly the identity-binding gap called out by the rules — a field ("field acted on") that the application logic trusts as the authenticated tenant identity, but that is not covered by the cryptographic check that is supposed to authenticate the message.

### Impact Explanation
Any host app that keys persistence, deduplication, or business logic off `WebhookMetadata#shop` (the value this gem hands it) can be made to attribute attacker-controlled webhook content to a victim merchant's tenant — i.e., cross-tenant data injection/corruption using only a signature the attacker legitimately obtained for their own shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Webhook endpoints are typically public HTTP endpoints authenticated solely by the HMAC header the gem validates; no other credential is required. Any merchant who installs the app (an "unprivileged internet user" relative to other tenants) can capture one legitimately signed webhook for their own shop and replay it with a modified `shop-domain` header — no access token, `client_secret`, or privileged account needed.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically/independently authenticate the `shop-domain` header before it is trusted as tenant identity (e.g., cross-verify against a value embedded in the signed payload, or require the caller to look up/validate the shop against a known active session/installation before acting on webhook data keyed by `request.shop`). At minimum, the gem should document that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be used as the sole tenant-selection key by host applications.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimately Shopify-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `client_secret`), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the same `B`/`H` to the app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, client_secret) == H` — succeeds. [4](#0-3) 
4. Handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's data>, ...)` and the host app processes attacker-controlled content under the victim's tenant.
