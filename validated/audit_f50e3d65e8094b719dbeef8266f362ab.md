## Analog Found: Rebasable/negative-rebase tokens break Intent Gateway escrow accounting

### Title
Intent Gateway escrow accounting breaks for rebasable ERC20 input tokens, freezing user/solver funds - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
The `1inch/farming` `FarmAccounting.sol` bug class ("accounting relies on a strict recorded token amount while the underlying balance floats") reproduces in Hyperbridge's `IntentGatewayV2` escrow. Any unprivileged user can `placeOrder` with an arbitrary ERC20 as input — there is no token whitelist. The gateway snapshots the escrowed amount once, into `_orders[commitment][token]`, and later pays out exactly that recorded amount from the contract's pooled, per-token balance. If that token rebases (negatively, e.g. slashing-aware LSTs, algorithmic rebasing tokens, or any token whose `balanceOf` can decrease post-transfer without a corresponding `Transfer` event), the sum of all outstanding `_orders[*][token]` entries across concurrently-escrowed orders can exceed the contract's actual `balanceOf(token)`, since the accounting never re-syncs to the floating balance.

### Finding Description
`placeOrder` measures the *actual* amount received only at deposit time (already hardened for fee-on-transfer tokens via before/after balance diffs), then stores that fixed number in `_orders[commitment][token]`: [1](#0-0) 

Redemption/refund later transfers exactly the recorded amount and decrements the same stored counter, without ever checking it against the contract's current token balance: [2](#0-1) 

Because `_orders` is keyed by `(commitment, token)` but the actual ERC20 balance held by the gateway is a single pooled value shared across *every* order that ever escrowed that token, the design implicitly assumes `sum(_orders[*][token]) == IERC20(token).balanceOf(address(this))` at all times. This invariant is exactly what rebasing breaks: a rebase changes `balanceOf` for every holder (including the gateway contract) without any corresponding `transfer`/`transferFrom` call that the gateway's balance-diff logic could observe. There is no mechanism (unlike `DustCollected` for fee-on-transfer/surplus) that reconciles ambient rebase drift back into the per-commitment accounting.

- Positive rebase: rebase gains accrue to the contract's balance but are never credited to any commitment's `_orders` entry, and are not swept as dust — they are simply orphaned/stuck.
- Negative rebase (the more severe case): the sum of recorded escrow obligations across all outstanding orders for that token can exceed the contract's actual balance. When later orders attempt `_withdraw`/`withdraw` (via `RedeemEscrow`/`RefundEscrow` `onAccept`, or the same-chain cancel path), `IERC20(token).safeTransfer(beneficiary, amount)` reverts with insufficient balance because the contract does not actually hold what its own ledger claims. This is a shared-pool version of the FarmAccounting bug: the "distributed" (recorded) amount no longer matches the floating real balance.

The same pattern exists in the Tron fork of the contract: [3](#0-2) 

### Impact Explanation
For any order whose input token is rebasable and undergoes a negative rebase while escrowed, some legitimate order's `withdraw()` call (redemption to the filling solver, refund to the user on cancel, or cross-chain `RedeemEscrow`/`RefundEscrow` settlement) will permanently revert because the contract's actual balance can no longer satisfy the sum of outstanding per-commitment claims. Because there's no reconciliation or fallback, the affected order's escrow becomes **permanently frozen** — the beneficiary can never claim it since the recorded `_orders[commitment][token]` amount will never again match reality, and every future entry point (`_withdraw`, `onGetResponse`, `onAccept`) reads and pays out the same stale, unreachable amount. This satisfies the "permanent freezing of funds" bar for a valid, in-scope finding, reached via a single unprivileged `placeOrder` transaction with an attacker-chosen (or unknowingly integrated) rebasing token.

### Likelihood Explanation
`placeOrder`'s token parameter is unrestricted — any ERC20 address can be supplied by any caller, with no governance-controlled asset whitelist visible in `IntentGatewayV2.sol`/`IntentsBase.sol`. Solvers and integrators building on the SDK could unknowingly select a rebasing collateral/LST as an input asset (a common DeFi token category), or a malicious user could deliberately place an order in a token they know is scheduled for negative rebase (e.g., an LST post-slashing) to grief the shared escrow pool for that token and lock out other users' legitimate withdrawals. No special privileges are required.

### Recommendation
- Maintain a governance-curated allowlist of input tokens for `IntentGatewayV2`, explicitly excluding rebasable/elastic-supply tokens (mirroring the 1inch farming recommendation to warn against rebasable reward tokens).
- Alternatively/additionally, isolate escrow accounting per-commitment using pull-based redemption verified against `balanceOf` snapshots, or wrap rebasable assets in a non-rebasing share representation before escrowing, so `_orders[commitment][token]` can never diverge from actual holdings.
- Emit and periodically reconcile any drift between `sum(_orders[*][token])` and `IERC20(token).balanceOf(address(this))`, and document rebasable tokens as explicitly unsupported in integrator-facing documentation.

### Proof of Concept
1. Attacker/user A places an order with input token `RBT` (a rebasable ERC20), escrowing amount `X`; `_orders[commitmentA][RBT] = X` is recorded, gateway's `RBT` balance = `X`.
2. User B places a second order with the same `RBT` token, escrowing amount `Y`; `_orders[commitmentB][RBT] = Y`, gateway's `RBT` balance = `X + Y`.
3. `RBT` undergoes a negative rebase (e.g., a protocol-level slashing event), reducing the gateway's actual `RBT` balance to `< X + Y` (say `X + Y - Δ`), while `_orders[commitmentA][RBT]` and `_orders[commitmentB][RBT]` remain unchanged at `X` and `Y`.
4. Order A is filled/cancelled first and successfully withdraws `X` via `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol:451-470`), leaving the gateway holding `Y - Δ` of `RBT`.
5. Order B's beneficiary attempts to redeem via `RedeemEscrow`/`RefundEscrow` (`onAccept`) or cancellation; `_withdraw` calls `IERC20(RBT).safeTransfer(beneficiary, Y)`, which reverts because the gateway only holds `Y - Δ < Y`. Order B's escrow is now permanently unredeemable — there is no code path that adjusts the recorded amount down to match the floating balance.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
