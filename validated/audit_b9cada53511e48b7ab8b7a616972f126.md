### Title
Balance-diffing in `EmporiumUpgradeable.runAction`/`handleOut` lets any caller sweep another user's pending async refund into their own stealth UTXO - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` computes the minted UTXO amount purely as `balancesAfter[i] - balancesBefore[i]`, where both snapshots are taken inside the *current* caller's own `runAction` invocation [3](#0-2) [4](#0-3) . Because Emporium acts as a single shared proxy address for all users' CASE 2 stateless calls, any balance increase that lands on Emporium's address strictly between an attacker's own `balancesBefore` and `balancesAfter` reads gets minted into the attacker's own `stealthAddressStructure` in `handleOut` [5](#0-4) , regardless of whose order/op actually caused it.

### Finding Description
Equality that should hold: `utxoOut.amount minted to caller's stealthAddressStructure == balance change caused solely by that caller's own authorized ops`. The code instead computes `balanceChange = balancesAfter[i] - balancesBefore[i]` (adjusted by the caller's own `deltaAmountChanges[i]`) and unconditionally attributes the whole delta to the caller [6](#0-5) .

Root cause: Emporium is used by all users as the on-chain counterparty for CASE 2 "Stateless Interaction" ops - `(success, err) = op.endpoint.call{value: op.value}(op.callData);` [2](#0-1) . When a victim places a limit order via such an op, the third-party endpoint records `msg.sender` (= Emporium's address, shared by all users) as the order owner/beneficiary. If that endpoint later refunds/settles the order asynchronously (e.g. via a permissionless "claim/settle/cancel" function that anyone can trigger, sending proceeds back to the recorded owner address), the funds land on Emporium's shared balance with no on-chain linkage to the victim's original nullifiers/commitments.

Because `verifyWallet` returns immediately with no signature check when `stack.signerAddress == address(0)` (the CASE 2 branch) [1](#0-0) , an attacker can craft their own `transact()` call whose `stack.ops` array includes an op targeting that same third-party endpoint's permissionless settlement function for the victim's still-open order. Executing this op as part of the attacker's own `runAction` call causes the victim's refund to arrive on Emporium's balance strictly between the attacker's `balancesBefore` and `balancesAfter` snapshots. The resulting `balanceChange` therefore includes the victim's refund, and `handleOut` mints it entirely into the attacker's own `stealthAddressStructure` [7](#0-6) , with `msg.sender` transfer going to the caller (Hinkal.sol on behalf of the attacker) via `transferERC20TokenOrETH` [8](#0-7) .

None of the existing guards prevent this: `onlyAllowedRecipient` only checks that the caller is the main Hinkal contract, not that the balance change is attributable to the current op set [9](#0-8) ; the circuit cannot constrain `handleOut`'s output amount in advance because external-action outputs (swaps, limit-order fills) are inherently variable and determined only by the post-call balance diff - this is precisely why the balance-diffing pattern exists, and it has no notion of which stray inflow belongs to which prior caller's proof/nullifiers.

### Impact Explanation
Direct theft of another user's in-flight (already-deposited-into-Emporium) shielded funds by an unrelated, unprivileged attacker, minted as a shielded UTXO to the attacker's own stealth address with no authorization from the victim. This matches the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable against any victim order that (a) uses a CASE 2 stateless op on an endpoint with a permissionless settlement/refund function, and (b) has not yet been settled at the time the attacker acts.

### Likelihood Explanation
Preconditions: a victim must have an open/pending CASE 2 limit-order-style position on a third-party endpoint whose settlement function is permissionless and sends proceeds to the recorded `msg.sender` (Emporium), and that settlement must not have already occurred (no prior transaction must have already swept it, since any pre-existing Emporium balance nets out in the diff). The attacker's cost is a single `transact()` call with a crafted `stack.ops` entry; no signature, role, or privilege is required for CASE 2 (`stack.signerAddress == address(0)`). Feasibility depends on the specific external endpoints integrated with Emporium exposing such a permissionless settlement path, but the vulnerability itself sits entirely in Hinkal's own accounting logic (`EmporiumUpgradeable.runAction`/`handleOut`) rather than in a third-party defect.

### Recommendation
Do not attribute the full `balancesAfter - balancesBefore` delta to the current caller. Track and reconcile balance changes per order/op (e.g., require endpoints to push funds to a target the runAction can bind to the specific caller/message, or record expected settlement amounts on order placement time and only release the exact amount tied to the caller's own nullifiers/emporiumMessage), and revert or route excess/unexpected balance increases to a recoverable admin-swept pool rather than silently minting them to whichever `stealthAddressStructure` happens to be executing.

### Proof of Concept
Foundry fork test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a mock "LimitOrderBook" endpoint exposing `placeOrder()` (called via CASE 2 op, records `msg.sender`=Emporium as owner) and a permissionless `settle(orderId)` that transfers `refundAmount` of `tokenX` to the stored owner (Emporium).
2. Victim calls `transact()` with a CASE 2 op calling `placeOrder()` on the mock endpoint; assert Emporium's `tokenX` balance unchanged (order pending, no refund yet) and `balancesBefore == balancesAfter` for victim's call.
3. Attacker calls `transact()` for the same `erc20TokenAddresses=[tokenX]`, with `stack.ops` including a CASE 2 op calling `settle(victimOrderId)` on the mock endpoint (no signature required since `signerAddress == address(0)`).
4. Assert: inside this single attacker transaction, `balancesBefore[tokenX]` (read before the op loop) does not yet include `refundAmount`, while `balancesAfter[tokenX]` does; `balanceChange == refundAmount`.
5. Assert `handleOut` returns `utxoOut.amount == refundAmount` bound to the attacker's `circomData.stealthAddressStructure`, and that `refundAmount` is unrelated to any value in the victim's proof/nullifiers - i.e. the victim's nullifiers/circuit never authorized this amount to move to the attacker's stealth address.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,

            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
