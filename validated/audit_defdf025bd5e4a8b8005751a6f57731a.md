### Title
Webhook HMAC covers only the raw body, not the `shop-domain`/`topic` headers, allowing cross-tenant/cross-topic webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only proves that the *body bytes* were signed with `Context.api_secret_key`; it proves nothing about which shop or topic the event belongs to [2](#0-1) . The `shop`, `topic`, `api_version` and `webhook_id` values are all read straight from unauthenticated headers [3](#0-2)  and are handed to the app's handler as trusted identity fields via `WebhookMetadata` [4](#0-3) .

### Finding Description
This is the same bug class as the report's hint "a field acted on but not covered by the HMAC": the identity binding the gem should be enforcing is `shop header == shop that produced the signed bytes`, but the code only checks `HMAC(body, secret) == received_hmac`, never mixing `shop-domain` (or `topic`) into the signable string [1](#0-0) .

Any entity that can obtain one legitimate `(raw_body, hmac)` pair signed by the app's own `api_secret_key` — for example an unprivileged merchant who installs the app on their own shop and receives ordinary webhook deliveries for their own store — can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic` header) for a different value. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` still returns `true` because it only recomputes the signature over `to_signable_string`, i.e. the body [5](#0-4) . `Registry.process` then dispatches to the handler with the attacker-chosen `shop` (and/or `topic`) as if it were authenticated [2](#0-1) .

Equality that should hold but doesn't: `shop_in_signed_bytes == shop_used_for_tenant_dispatch`. Before the request: the real Shopify-issued webhook has `shop-domain = attacker-shop` and a valid HMAC over the body. After the attacker's replay: `shop-domain = victim-shop`, same body, same (still-valid) HMAC — `Registry.process` accepts it and calls the handler with `shop: "victim-shop"`.

### Impact Explanation
This crosses a tenant boundary: any host application that uses `WebhookMetadata#shop` (or `#topic`) to look up/act on a specific merchant's data (a documented, expected usage pattern of this gem's own webhook API, not something the gem tells developers to avoid) can be made to write or process data under an arbitrary victim shop's identity, or to trigger a handler meant for a different topic (e.g., a GDPR data-request/erasure handler) using attacker-supplied body content mislabeled with a legitimate topic/shop pair. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to already have at least one valid `(body, hmac)` pair produced by Shopify for the shared `api_secret_key` (trivially obtainable by any merchant that installs the app, since webhook bodies/HMACs are delivered to the app's public endpoint and are not secret to the receiving shop owner), plus the ability to send an arbitrary HTTP request to the app's webhook endpoint with modified headers — both are unprivileged-internet-user actions with no need for the app's `client_secret`, an access token, or any privileged account.

### Recommendation
Bind the identity headers into the signed content used for verification: include `shop-domain`, `topic`, and `api_version` (in addition to the raw body) in `Request#to_signable_string`, or otherwise cryptographically verify that the header values match the values Shopify actually delivered (e.g., by validating against the `X-Shopify-Webhook-Id` when replay-protection/idempotency storage is available) before handing them to the registered handler as authenticated identity data.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app.
# Shopify legitimately delivers this webhook to the app for the attacker's own shop:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Attacker replays the SAME body+hmac but swaps the shop-domain header to a victim shop:
forged_headers = legit_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => passes HMAC validation (Utils::HmacValidator.validate only checks raw_body)
# => handler.handle is invoked with WebhookMetadata#shop == "victim-shop.myshopify.com",
#    even though Shopify never sent this event for that shop.
