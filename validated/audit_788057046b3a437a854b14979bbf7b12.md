### Title
Storage-deposit hold orphaned when a contract terminates in a call after its own `charge_instantiate` deposit was already recorded — `pallet-contracts` `RawMeter::try_into_deposit` / `ReservingExt::charge` - ([File: substrate/frame/contracts/src/storage/meter.rs])

### Summary
`pallet-contracts`'s storage meter accumulates `Charge` entries per frame into a flat `Vec<Charge<T>>` and never coalesces entries that belong to the same contract account across different call frames. When a sub-contract's base deposit is recorded during instantiation (`charge_instantiate`) in one frame, and the same contract is later self-terminated (`terminate`) in a subsequent, separate frame within the same call stack, `try_into_deposit` processes the `Refund` from termination and the earlier `Charge` from instantiation as two independent, uncoalesced entries. Because refunds are executed before charges, the refund tries to release a hold that was never actually placed yet (no-op, best effort), and the later charge then genuinely `transfer_and_hold`s funds onto the now-deleted contract's account, permanently freezing the origin's balance with no future release path.

### Finding Description
`RawMeter::charge_instantiate` (`substrate/frame/contracts/src/storage/meter.rs:439-463`) only *records* the base-deposit `Charge` via `charge_deposit`, which pushes a `Charge{contract, amount: Deposit::Charge(_), state: Alive}` into `self.charges` [1](#0-0) . The actual `transfer_and_hold` for this charge is deferred until the root meter's `try_into_deposit` runs at the very end of the call stack [2](#0-1) .

Each subsequent cross-contract call gets its *own* nested meter instance (`RawMeter::nested`), and on return that child is merged into the parent via `absorb`, which simply appends the child's charges with `self.charges.extend_from_slice(&absorbed.charges)` — there is no lookup or merge by contract account [3](#0-2) .

When the sub-contract self-terminates in a later, separate call/frame, `RawMeter::terminate` overwrites that frame's own contribution with `Terminated { deposit: Refund(info.total_deposit()), beneficiary }` [4](#0-3) . This refund, once absorbed into the root meter, becomes a second, independent `Charge` entry for the same contract account — it is never matched against or netted with the earlier `Alive` `Charge` entry from `charge_instantiate`.

At `try_into_deposit`, refunds are processed before charges:
```
for charge in self.charges.iter().filter(|c| matches!(c.amount, Deposit::Refund(_))) { E::charge(...)?; }
for charge in self.charges.iter().filter(|c| matches!(c.amount, Deposit::Charge(_))) { E::charge(...)?; }
``` [5](#0-4) 

The `Refund` (termination) entry is processed first via `ReservingExt::charge`'s `Deposit::Refund` branch, calling `transfer_on_hold` with `Precision::BestEffort` [6](#0-5) . Since no hold has actually been placed on the contract's account yet (the corresponding `charge_instantiate` charge is still pending in the second loop), `transferred < amount`, the code just logs an error and continues (no error returned). The `Terminated` branch then runs `dec_consumers` and sweeps the contract's remaining free balance to the beneficiary [7](#0-6) .

Immediately afterward, in the second loop, the earlier `Alive`-state `Charge` (the base deposit from `charge_instantiate`) executes `transfer_and_hold` from `origin` to the now-terminated contract's account (`substrate/frame/contracts/src/storage/meter.rs:548-559`) [8](#0-7) . This actually moves and holds funds on an account whose `ContractInfo` has already been removed (`ContractInfoOf::<T>::remove` happens synchronously inside `Ext::terminate` in `exec.rs`) [9](#0-8) . No further code path will ever release this hold for this dead account, since the sole `Charge` entry for it has already been consumed.

Meanwhile the aggregate `total_deposit` returned by `try_into_deposit` largely cancels out (`Charge(base_deposit)` + `Refund(base_deposit)` ≈ 0), so the value returned to the caller understates the real balance movement: origin's spendable balance actually decreases by `base_deposit`, permanently held under `HoldReason::StorageDepositReserve` on a deleted contract's account.

This confirms the bug's premise: unlike the newer `pallet-revive` implementation, which explicitly sorts and coalesces charges by contract in `execute_postponed_deposits` and special-cases the `Terminated` vs `Alive` merge (using `self.total_deposit = self.total_deposit.saturating_sub(&amount)`, `substrate/frame/revive/src/metering/storage.rs:396-429`) [10](#0-9) , `pallet-contracts`'s `RawMeter` in `storage/meter.rs` performs no such coalescing at all, leaving the sequential-hold ordering bug intact.

### Impact Explanation
Origin funds equal to the terminated sub-contract's base storage deposit get transferred and held (`HoldReason::StorageDepositReserve`) on a contract account whose `ContractInfo` no longer exists. Since the meter's bookkeeping treats the charge and the refund as already netted (returning ~0 net deposit to the caller), there is no remaining code path in the same transaction that will release this hold — it becomes a permanently frozen balance on a dead account, while `try_into_deposit`'s returned value does not reflect this frozen amount. This matches the scoped impact of a storage-deposit accounting asymmetry causing fund freeze.

### Likelihood Explanation
This requires only an ordinary contract-calling account (no privilege) deploying a two-contract setup: a driver contract that (1) instantiates a sub-contract (triggering `charge_instantiate`), (2) calls into the sub-contract causing a storage write, and (3) has the sub-contract self-terminate (`seal_terminate`) within the same top-level call/transaction. This is fully achievable via a normal `bare_call`/signed extrinsic to `pallet_contracts::call` with attacker-authored Wasm, and is deterministically repeatable.

### Recommendation
Add contract-keyed coalescing of `Charge` entries in `RawMeter::try_into_deposit` (or in `absorb`) analogous to the fix already present in `pallet-revive`'s `execute_postponed_deposits`: sort/group charges by `contract`, and when a `Terminated` entry meets a prior `Alive` charge for the same contract, net them out of `total_deposit` and skip performing the stale `transfer_and_hold`/`transfer_on_hold` pair, instead of independently replaying both operations.

### Proof of Concept
Rust integration test in `substrate/frame/contracts/src/tests.rs` (or `storage/meter.rs` unit test style):
1. Deploy `DRIVER` contract with sufficient balance.
2. From `DRIVER`, instantiate `SUB` contract (constructor writes no storage, just relies on base deposit from `charge_instantiate`).
3. In the same call stack, `DRIVER` calls `SUB`, which writes a storage item then calls `seal_terminate(beneficiary)`.
4. Assert after the outer `bare_call` completes:
   - `Balances::balance_on_hold(&HoldReason::StorageDepositReserve.into(), &sub_account) == 0` (expected to pass since account is not tracked, but real bug shows origin's balance dropped by `base_deposit` without a corresponding release),
   - `origin_balance_before - origin_balance_after == try_into_deposit_return_value` (this assertion should FAIL, demonstrating the mismatch: actual balance decrease is larger than the returned net deposit),
   - Attempt to reclaim the held amount from `sub_account` — expect it to be irrecoverable (no future extrinsic or code path clears the hold on a removed `ContractInfo` account).

	pub fn try_into_deposit(self, origin: &Origin<T>) -> Result<DepositOf<T>, DispatchError> {
		// Only refund or charge deposit if the origin is not root.
		let origin = match origin {
			Origin::Root => return Ok(Deposit::Charge(Zero::zero())),
			Origin::Signed(o) => o,
		};
		for charge in self.charges.iter().filter(|c| matches!(c.amount, Deposit::Refund(_))) {
			E::charge(origin, &charge.contract, &charge.amount, &charge.state)?;
		}
		for charge in self.charges.iter().filter(|c| matches!(c.amount, Deposit::Charge(_))) {
			E::charge(origin, &charge.contract, &charge.amount, &charge.state)?;
		}
		Ok(self.total_deposit)
	}

	/// Charges from `origin` a storage deposit for contract instantiation.
	///
	/// This immediately transfers the balance in order to create the account.
	pub fn charge_instantiate(
		&mut self,
		origin: &T::AccountId,
		contract: &T::AccountId,
		contract_info: &mut ContractInfo<T>,
		code_info: &CodeInfo<T>,
	) -> Result<(), DispatchError> {
		debug_assert!(matches!(self.contract_state(), ContractState::Alive));

		// We need to make sure that the contract's account exists.
		let ed = Pallet::<T>::min_balance();
		self.total_deposit = Deposit::Charge(ed);
		T::Currency::transfer(origin, contract, ed, Preservation::Preserve)?;

		// A consumer is added at account creation and removed it on termination, otherwise the
		// runtime could remove the account. As long as a contract exists its account must exist.
		// With the consumer, a correct runtime cannot remove the account.
		System::<T>::inc_consumers(contract)?;

		let deposit = contract_info.update_base_deposit(&code_info);
		let deposit = Deposit::Charge(deposit);

		self.charge_deposit(contract.clone(), deposit);
		Ok(())
	}

	fn terminate(&mut self, beneficiary: &AccountIdOf<Self::T>) -> DispatchResult {
		if self.is_recursive() {
			return Err(Error::<T>::TerminatedWhileReentrant.into());
		}
		let frame = self.top_frame_mut();
		let info = frame.terminate();
		frame.nested_storage.terminate(&info, beneficiary.clone());

		info.queue_trie_for_deletion();
		ContractInfoOf::<T>::remove(&frame.account_id);
		Self::decrement_refcount(info.code_hash);

		for (code_hash, deposit) in info.delegate_dependencies() {
			Self::decrement_refcount(*code_hash);
			frame
				.nested_storage
				.charge_deposit(frame.account_id.clone(), StorageDeposit::Refund(*deposit));
		}

		Contracts::<T>::deposit_event(Event::Terminated {
			contract: frame.account_id.clone(),
			beneficiary: beneficiary.clone(),
		});
		Ok(())
	}
