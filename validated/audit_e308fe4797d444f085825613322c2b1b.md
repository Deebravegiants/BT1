### Title
Webhook `shop-domain` identity field is not covered by the HMAC signature, allowing cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value (taken from the `shopify-shop-domain`/`x-shopify-shop-domain` header) that the gem hands to the app's webhook handler to identify *which merchant* the event belongs to is never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` validates only the body-derived HMAC and then passes the unauthenticated `shop` header straight through to the handler as part of `WebhookMetadata`, without any binding to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from an HTTP header that is completely separate from the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over that same signable string (the body) and, once valid, forwards the header-derived, unauthenticated `request.shop` value directly into `WebhookMetadata` given to the app's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain field with no further verification, and the documented handler pattern uses `data.shop` directly to decide which merchant record to update: [4](#0-3) [5](#0-4) 

This exactly matches the allowed analog class: "a field acted on but not covered by the HMAC." The equality that should hold is:

`shop bound by signature == shop acted upon by the handler`

but the gem actually implements:

`shop header (unauthenticated) == shop acted upon by the handler`

with the HMAC binding only `body == signature`, not `shop == signature`.

**Before attacker action:** a legitimate webhook for the attacker's own installed shop A arrives with `raw_body = B`, `hmac = HMAC(secret, B)`, `shop-domain = A`. Validation: `HmacValidator.validate` recomputes `HMAC(secret, B)` and compares to the supplied HMAC — passes for `shop=A`.

**Attacker action:** the attacker (an unprivileged, merely-installed-app user, no `api_secret_key`, no victim credentials) captures this valid `(B, hmac)` pair from their own shop's traffic and re-POSTs it directly to the app's public webhook endpoint, but rewrites the `shop-domain` header to `B` (the victim's shop).

**After attacker action:** `Utils::HmacValidator.validate` still passes, because it only checks `HMAC(secret, raw_body)` — the shop header plays no part in the signature computation: [6](#0-5) 

The handler then receives `data.shop == "victim-shop.myshopify.com"` with attacker-controlled `data.body`, believing the event legitimately originated from the victim tenant, even though the victim never sent it and the attacker has no access to the victim's data or credentials.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an attacker with only their own low-privilege installed shop can make the app process attacker-chosen body content attributed to any other merchant (whose domain is public knowledge, e.g. `victimshop.myshopify.com`). Depending on how the host app implements its handler (as documented, keyed directly off `data.shop`), this can update, create, or delete records the app believes belong to the victim shop — i.e. cross-tenant access/data corruption, without ever needing the victim's access token or the app's `client_secret`. This matches the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one valid `(raw_body, hmac)` pair, which they can obtain trivially by installing the app on their own store (a normal, unprivileged action any internet user can do) and triggering any webhook topic that is registered, or by inspecting outgoing webhook traffic they control. No secret key, no elevated privilege, and no interaction with the victim is required — only that the vulnerable app trusts `WebhookMetadata#shop` (as the gem's own documentation instructs) to select the target tenant.

### Recommendation
Bind the shop identity to the signed content, e.g. include the `shop-domain` (and `topic`/`webhook_id`) in `to_signable_string`, or independently verify that the `shop-domain` header corresponds to a shop with an actual, currently-registered webhook subscription/session before dispatching to the handler, rather than trusting the header value on its own.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com"
# and receives a real Shopify webhook, capturing:
raw_body = '{"id":1,"note":"hello"}'
hmac     = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body) # only obtainable because it's a legit webhook to attacker's own shop
b64_hmac = Base64.encode64(hmac)

# Attacker replays the same body+hmac to the app's public webhook endpoint,
# but spoofs the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => b64_hmac,
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # not part of the signature
  "x-shopify-webhook-id"   => "attacker-controlled-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC check still passes because signature only covers raw_body
ShopifyAPI::Webhooks::Registry.process(request)
# -> handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...}, ...))
# App now believes attacker-controlled data came from the victim's shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
