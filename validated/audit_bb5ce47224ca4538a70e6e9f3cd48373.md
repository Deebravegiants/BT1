### Title
Vetoing a state commitment resets `latestStateMachineHeight` to a hardcoded `1` instead of the true prior height, permanently lowering the forward-progress bar for future consensus updates - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` handles the veto of a state-machine commitment. When the vetoed height is the chain's currently recorded "latest" height, it resets `_latestStateMachineHeight[stateMachineId]` to the literal constant `1` rather than to the last known-good height, unlike its Substrate/pallet-ismp counterpart which restores the true `PreviousStateMachineHeight`. [1](#0-0) 

### Finding Description
`HandlerV2.setState` (BEEFY/consensus update handling) only accepts a new intermediate state commitment for a state machine if it advances past the currently recorded latest height: [2](#0-1) 

`latestStateMachineHeight` is the single security gate enforcing "only heights greater than the last confirmed height are accepted" — this mirrors the analogous, correctly-implemented check in the Substrate consensus handler, which explicitly skips any height at or below `previous_latest_height`: [3](#0-2) 

In the Substrate `pallet-ismp` implementation, vetoing the currently-latest commitment correctly restores the pointer to the actual last valid height retained in `PreviousStateMachineHeight`, preserving the forward-progress invariant: [4](#0-3) 

The Solidity `EvmHost` implementation of the same operation, however, does not track or restore the real previous height. It simply hardcodes the reset value to `1`: [1](#0-0) 

This is the same bug class as the referenced CVE: a reset/cleanup path that fails to properly restore prior state and instead leaves (or, here, sets) a stale/incorrect low-water-mark value, which is then trusted by a later, security-critical consumer of that value. In the kernel case a stale WQCFG register leaked configuration into the next use of a workqueue; here a stale sentinel (`1`) leaks a permissive "already validated" threshold into all future consensus-update validation for that state machine, for potentially the entire remaining lifetime of the bridge (there is no code path that ever restores the correct prior height once a veto of the latest height occurs).

Once this reset occurs, any subsequent `HandlerV2` consensus-proof submission that includes an intermediate state at any height greater than `1` (i.e. essentially any legitimate-looking height) will pass the `intermediate.height > latestHeight` check and be written to `_stateCommitments`/`_latestStateMachineHeight` via `storeStateMachineCommitment`, even if that height is far below heights that were already legitimately confirmed and relied upon prior to the veto. This breaks the monotonic forward-progress invariant that the challenge-period/veto mechanism is designed to protect, and it does so far more severely than the Substrate implementation's own documented (and bounded/negligible) "one insertion of retention" wart for the same veto operation.

### Impact Explanation
After a fisherman-triggered veto of the current latest height (a normal, expected part of the state-commitment vetoing mechanism reachable via relayed proofs to `HandlerV2`/the ISMP handler that is authorized under `_hostParams.handler`), the security threshold for accepting new state-machine commitments collapses from "greater than the last legitimately confirmed height" to "greater than 1". Any relayer can then submit a consensus proof carrying an intermediate state for a height that is lower than heights already relied upon by `handlePostRequests`/`handleGetResponses` for proof verification (`stateMachineCommitment(request.proof.height)`), re-introducing or overwriting the state root used to verify Merkle proofs for incoming messages. This can enable forged message delivery / unsound state commitments to be accepted, undermining the integrity of all cross-chain message verification for that state machine — a direct path to unauthorized app actions or fund loss through fraudulently "proven" requests/responses.

### Likelihood Explanation
Vetoing the latest commitment is a designed, reachable operational flow (the `StateCommitmentVetoed` event and surrounding comments confirm vetoes of the latest height are an expected, "technically any state commitment can be vetoed" case, not an edge case). No admin or governance privilege is required to trigger the downstream consequence — once a single veto of the latest height has occurred (which itself is meant to be a routine fisherman safety mechanism against bad consensus updates), any subsequent relayer-submitted consensus proof can exploit the collapsed threshold.

### Recommendation
Track the true previous valid `latestStateMachineHeight` per state machine (mirroring `PreviousStateMachineHeight` in `pallet-ismp`) and restore that value in `deleteStateMachineCommitmentInternal`, instead of hardcoding `1`.

### Proof of Concept
1. Consensus updates progress `_latestStateMachineHeight[id]` to height `H` via `storeStateMachineCommitment` (called from `HandlerV2.setState`).
2. A fisherman vetoes height `H` via `deleteStateMachineCommitment`, which is the latest height, so `_latestStateMachineHeight[id]` is reset to `1` (`evm/src/core/EvmHost.sol:719-721`).
3. A relayer submits a new BEEFY/consensus proof through `HandlerV2.setState` containing an intermediate state at height `H' `, where `1 < H' < H` (a height lower than previously legitimately confirmed heights, potentially attacker-influenced).
4. The check `latestHeight != 0 && intermediate.height > latestHeight` (`evm/src/core/HandlerV2.sol:158-159`) passes because `latestHeight == 1`, and the stale/incorrect commitment for `H'` is stored and becomes the new "latest" trusted state, breaking monotonic forward progress and enabling proof verification against an attacker-favorable, non-monotonic state root.
