## Summary

The Aptos analog of the DKIM "under-specified identifier" bug is the `SignerCapabilityOfferProofChallengeV2` struct used by `account::offer_signer_capability`. Unlike its sibling `RotationCapabilityOfferProofChallengeV2`, which was explicitly hardened with a `chain_id` field to stop cross-context replay, the signer-capability variant was never given the same protection — even though it authorizes a strictly more dangerous capability (full `SignerCapability`, not just key rotation).

### Finding Description

`aptos-move/framework/aptos-framework/sources/account/account.move` defines two "delegate a capability via off-chain signature" challenge structs side by side: [1](#0-0) 

```
/// This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message.
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}

struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

The doc-comment on `RotationCapabilityOfferProofChallengeV2` is explicit that `chain_id` was added specifically "to prevent replaying the challenge message" (cross-chain replay). `SignerCapabilityOfferProofChallengeV2` has no such field, yet it is consumed by `offer_signer_capability`, which grants the recipient the ability to fully impersonate the source account via `create_signer_with_capability`: [2](#0-1) 

The only replay-relevant field is `sequence_number`, taken from the account's *current* on-chain sequence number at call time:

```
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
verify_signed_message(source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);
```

`verify_signed_message` only checks that the signature is valid over this struct for the account's current auth key — it performs no chain-specific check: [3](#0-2) 

This is structurally the same defect class as the DKIM bug: the on-chain replay-protection identifier is built from a payload whose fields are insufficient to bind the authorization to a single valid context (there, `canonizedHeaders` was unvalidated; here, `chain_id` is simply absent). An off-chain signed authorization intended for one chain (e.g., testnet/devnet or a pre-mainnet environment) can be replayed verbatim on another chain sharing the same framework, as long as `source_address`, `recipient_address`, and `sequence_number` line up — which is common for freshly provisioned accounts (`sequence_number == 0` on every environment) or accounts whose signing key/mnemonic is reused across networks, a widespread developer/testing pattern.

### Impact Explanation

If exploited, an attacker who is (or controls) the `recipient_address` from a legitimately-obtained signature on one chain/environment can replay that exact signature on another chain to obtain `SignerCapability` over the victim's account there. `SignerCapability` lets the holder mint a `signer` for the victim account at will (`create_signer_with_capability`), enabling full custody takeover: transferring fungible-asset stores, objects, coins, and resource-account-held value out of the account, indistinguishable from the victim acting themselves. This is a full unauthorized takeover of account/resource-account control, not merely a griefing bug.

### Likelihood Explanation

Medium: it requires (a) the same account address/auth key to exist with a matching sequence number on more than one Aptos-framework-based network, and (b) the victim to have signed a `SignerCapabilityOfferProofChallengeV2` at some point (a documented, supported delegation flow used by wallets/automation dApps). Both conditions are realistic — reusing keys across testnet/mainnet or forked chains during development/testing is common, and `sequence_number == 0` collisions are close to guaranteed for newly created accounts.

### Recommendation

Add a `chain_id` (and ideally the same `source_address`-vs-domain hardening already applied to `RotationCapabilityOfferProofChallengeV2`) to `SignerCapabilityOfferProofChallengeV2`, mirroring the fix already made for the rotation-capability variant, and bump to a new versioned struct/entry function so old signatures cannot be replayed under the new scheme.

### Proof of Concept

1. Victim owns address `A` with the same public key/auth key on both `chainX` and `chainY` (e.g., created via the same mnemonic on testnet and later on mainnet), each with `sequence_number == 0`.
2. Victim signs `SignerCapabilityOfferProofChallengeV2{ sequence_number: 0, source_address: A, recipient_address: R }` off-chain to authorize a dApp/automation contract `R` on `chainX`.
3. Attacker (or `R`'s operator) submits the exact same `signer_capability_sig_bytes` to `account::offer_signer_capability` on `chainY` for account `A` before its sequence number advances past 0.
4. `verify_signed_message` succeeds (correct signature, correct current sequence number, correct addresses) even though the victim never intended to authorize `R` on `chainY`.
5. `R` now holds `SignerCapability` for `A` on `chainY` and can call `create_signer_with_capability` to move any assets held by `A` there.

**Uncertainty noted:** I was not able to fully inspect the exact byte-level domain separation performed inside `ed25519::sign_struct` / `signature_verify_strict_t` (in `aptos-move/framework/aptos-stdlib/sources/cryptography/ed25519.move`) within the available iterations, to confirm whether any implicit struct-type-based domain tag also incidentally includes chain-specific data. Based on the explicit doc-comment stating that `chain_id` was added to `RotationCapabilityOfferProofChallengeV2` specifically to solve cross-chain replay, and the absence of that field (or any equivalent) from `SignerCapabilityOfferProofChallengeV2`, the gap appears to be a genuine, unaddressed asymmetry between the two capability-offer flows.

```text
    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
```

```text
    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
```
