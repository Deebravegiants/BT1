## Analysis Result



### Title
Webhook shop-domain identity spoofing via HMAC scope mismatch (body-only signature vs. header-derived tenant) - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain` HTTP header, but the HMAC signature that this gem validates only covers the raw request body. Because the header is completely outside the signed payload, any party who possesses one valid `(body, hmac)` pair — trivially obtainable by installing the target app on their own Shopify store — can replay that same pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `Webhooks::Registry.process` passes this unauthenticated header value straight to the app's business logic as the acting tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read from a header that is never part of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over `verifiable_query.to_signable_string`, i.e., the body — it never touches headers: [3](#0-2) 

`Registry.process` calls this validator, then immediately forwards the *unauthenticated* `request.shop` to the app handler as the tenant identity, with no additional binding check between the verified body and the header-derived shop: [4](#0-3) 

The identity equality the HMAC is supposed to guarantee is: `bytes verified == bytes acted on`. Here, the bytes verified are `raw_body` only, while the bytes acted on for tenant routing are the `shop-domain` header — an entirely different, unsigned input. The app's `api_secret_key` is shared across all shops that install the app, so a signed body from one shop's webhook is cryptographically valid HMAC material for *any* shop domain the attacker chooses to put in the header, since the header plays no role in signature computation.

### Impact Explanation
An unprivileged internet user — anyone who can install the app on their own store (a normal, self-service action) — can capture one legitimately Shopify-signed `(body, hmac)` pair from their own store's webhook deliveries, then POST it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. The gem will report the HMAC as valid (it only checks the body) and hand the attacker-chosen `shop` to the app's webhook handler as if it were an authenticated fact about the request's origin. Any app logic that trusts `WebhookMetadata#shop` to look up/act on a specific tenant's session, data, or settings can be tricked into acting on behalf of, or against, a victim shop it never actually received a webhook about — a cross-tenant access primitive.

### Likelihood Explanation
The attack requires no special privileges beyond being able to install the app on a shop the attacker controls (self-service, free) and being able to send HTTP requests to the app's public webhook endpoint (also assumed reachable, as that's the entire point of the endpoint). No access token, `api_secret_key`, TLS interception, or social engineering is needed. The replay is a pure HTTP-level operation against this gem's own verification logic.

### Recommendation
Bind the header-derived `shop` (and ideally `topic`/`webhook-id`) into the signed material that `HmacValidator` checks, e.g., by including these headers in `to_signable_string`, or by having `Registry.process` cross-validate `request.shop` against a shop value embedded in the verified body (many webhook payloads already carry shop-identifying fields) before dispatching to the handler.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`.
2. Capture any webhook Shopify delivers to the app for that store: raw body `B` and header `x-shopify-hmac-sha256: H` (valid signature over `B` with the app's shared `api_secret_key`).
3. Replay directly to the app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: <same topic as captured>
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com   <-- attacker-controlled, unsigned
   x-shopify-webhook-id: <any>

   B
   ```
4. `Utils::HmacValidator.validate` returns `true` because `H` correctly signs `B` — the swapped `shop-domain` header is never checked.
5. `Registry.process` builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: B, ...)` and invokes the app's handler, which now believes this attacker-supplied body originated from the victim shop.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
