## Title
Webhook Shop Domain Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC signature over the raw request body only, while the `shop` (tenant identity) is taken from an HTTP header that is never included in the signed content. Any actor who can obtain one validly-signed webhook payload (e.g., by installing the app on their own shop and triggering a webhook) can replay that exact body/HMAC pair while swapping the `x-shopify-shop-domain` header to any other shop domain, and the signature check will still pass — breaking the binding between the verified bytes and the shop the data is attributed to.

### Finding Description
The `Request#to_signable_string` method used for HMAC verification returns only the raw body: [1](#0-0) 

But `Request#shop` is read straight from a header that is not part of that signed string: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body), never the shop header: [4](#0-3) 

`Webhooks::Registry.process` validates the HMAC and then unconditionally trusts `request.shop` as the tenant identity passed to the app's handler: [5](#0-4) 

Equality that should hold but doesn't:
`bytes_verified_by_hmac (raw_body)` ≠ `bytes_acted_on_as_tenant_identity (shop header)`.

Because the app's `api_secret_key` is shared across every shop that installs the app, a legitimately obtained `(raw_body, hmac)` pair from any one installation (e.g., the attacker's own shop) remains a valid signature no matter what `x-shopify-shop-domain` value accompanies it. The signature proves the body wasn't tampered with, but it proves nothing about which shop the request is claimed to be from — yet `Registry.process` (and the host application via `WebhookMetadata.shop`) uses that unauthenticated header as the tenant key.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with a legitimate (even free/trial) shop installation can capture one valid webhook delivery and replay it with an arbitrary shop-domain header, causing the receiving application to process/store data (orders, customer info, etc.) under a spoofed shop identity that passed HMAC verification. Applications that key their persistence, authorization, or session lookups by `WebhookMetadata#shop` — exactly as the gem's own test suite demonstrates — inherit this cross-tenant boundary break.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who can install the target app on a shop they control (trivial for most public apps) and capture a single outbound webhook. No access to `api_secret_key` or any privileged credential is required — the attack only needs one legitimately signed body, which is freely obtainable by anyone able to install the app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or otherwise cryptographically bind the shop header to the verified body before it is used as tenant identity in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger any webhook (e.g. `orders/create`); capture the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` (both computed with the shared `api_secret_key`).
2. Send a new HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` even though the payload never originated from that shop, as shown by `Request#shop` being read independently of the HMAC-covered `to_signable_string`.
