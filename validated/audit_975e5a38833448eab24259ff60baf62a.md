### Title
Unsigned Cross-Chain Calldata in `pallet-hyper-fungible-token` Lets an Attacker-Controlled `message.from` Field Authorize Arbitrary Runtime Call Dispatch - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler decodes an attacker-supplied `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` from the body of an incoming `PostRequest` and dispatches `runtime_call` as a fully-privileged `RawOrigin::Signed` extrinsic. When `signature` is `None`, the pallet skips all cryptographic authentication and instead derives the dispatch origin directly from the unauthenticated `message.from` bytes embedded in the same untrusted payload [1](#0-0) . This mirrors the Handlebars `@partial-block` bug class: a value that is nominally inert application data (`message.from`, `runtime_call`) is trusted as an authorization/identity token and then "compiled"/executed (dispatched) without being cryptographically bound to that authority, unlike the properly-verified signed branch which binds `(nonce, runtime_call)` together.

### Finding Description
On `on_accept`, the module authenticates only that the `PostRequest` originated from the registered peer contract at `source` via `ContractToAsset::<T>::get(source, &from)` (the ISMP module-level sender, backed by consensus/state proofs) [2](#0-1) . It then ABI-decodes the request body into an application-level `Message { from, to, amount, data }` struct [3](#0-2) . Nothing in the pallet cryptographically ties `message.from` to the actual caller of `send()` on the source chain — it is simply a `bytes` field inside the payload.

When executing the optional calldata:
- If `substrate_data.signature` is `Some`, the origin is fixed to `beneficiary` (from `message.to`) and the signature must verify over `(account_nonce, runtime_call)`, correctly binding call authority to the signer [4](#0-3) .
- If `signature` is `None`, the origin is derived solely from `message.from` with **no cryptographic check whatsoever** [5](#0-4) , and the arbitrary `T::RuntimeCall` decoded from `runtime_call` is dispatched as that origin [6](#0-5) .

Because `message.from` is just an ABI `bytes` field chosen by whatever code calls `send()` on the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, its authenticity depends entirely on that source-chain contract enforcing `from == msg.sender`. The receiving pallet has no way to verify this invariant — it treats the field as authoritative for origin selection purely because it arrived inside a `PostRequest` from a registered peer. This is structurally identical to the Handlebars flaw: an untyped/unverified data value (`@partial-block` / `message.from`) is promoted to an execution-authorizing role (compiled AST / dispatch origin) without an integrity binding to the actual privileged actor.

### Impact Explanation
If the field is not strictly bound to the transaction's true sender on the source chain (a cross-chain trust assumption this Substrate-side pallet cannot itself verify), any account able to trigger a `send()` with attacker-chosen `from` bytes and `data = SubstrateCalldata{ signature: None, runtime_call: <arbitrary call> }` can have an arbitrary `RuntimeCall` dispatched as `RawOrigin::Signed(<victim account>)` on the destination chain — i.e., unauthorized app action / impersonation of any account reachable via the `EvmToSubstrate` mapping, filtered only by `BaseCallFilter`. This is reachable by an unprivileged token bridger via a single cross-chain token transfer and can result in unauthorized dispatch of privileged calls (e.g., asset transfers, governance-adjacent calls not excluded by the base filter) as an arbitrary victim identity.

### Likelihood Explanation
Exploitability is contingent on the source-chain contract's enforcement of `from == msg.sender` for `Message.from`, which lives in the EVM contracts (`HyperFungibleToken.sol` / `WrappedHyperFungibleToken.sol`) and was not fully verifiable within this review's scope — this is a real limitation of the analysis. Independent of that external enforcement, the receiving pallet's design is itself unsound: it accepts an `Option<signature>` as the sole authorization gate for dispatching arbitrary runtime calls, and the "no signature" branch derives origin from data it cannot independently authenticate, which is a fragile trust boundary that a single misconfigured or compromised peer contract (or a bug in its `from` handling) directly converts into unauthorized cross-chain call execution.

### Recommendation
Require a valid signature (binding `nonce` + `runtime_call` to the target account) unconditionally before dispatching any `runtime_call`, removing the unauthenticated `else` branch entirely; if unsigned execution-as-sender is a required feature, cryptographically derive and pin `message.from` at the protocol/ABI level so it cannot diverge from the true source-chain caller, and treat it with the same suspicion as any other untrusted payload field rather than as an implicit proof of authorization.

### Proof of Concept
Not independently reproducible without also inspecting/controlling the EVM-side `HyperFungibleToken.sol` `send()` implementation (unverified in this review), but the vulnerable code path is directly exercised by: a `PostRequest` from a registered peer contract whose ABI body decodes to `Message{ from: <target victim's 20/32-byte address>, to: <any>, amount: <any>, data: SCALE_ENCODE(SubstrateCalldata{ signature: None, runtime_call: SCALE_ENCODE(<arbitrary RuntimeCall>) }) }`, which on `on_accept` results in `<arbitrary RuntimeCall>.dispatch(RawOrigin::Signed(<victim>))` at [7](#0-6) .
