### Title
Caller-supplied swap route places attacker-controlled code under the caller's authorization tree, letting a rogue venue transfer tokens out of the caller's wallet - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The Transit Swap exploit class is a controllable external call: user-supplied parameters determined which contract was invoked and what it did, so an attacker could make the protocol pull tokens from victims' wallets. XOXNO Lending's controller maps this class onto its router strategies: `swap_tokens` authorizes exactly one input transfer to the configured router and then executes an opaque, caller-supplied `StrategySwap` payload whose venue/pool addresses are never allowlisted or validated in the in-scope code. A malicious venue named in the payload runs on the call stack beneath the caller's `require_auth` entry, so a `transfer` it makes from the caller is recorded by simulation as a child of the caller's authorization and executes if that tree is signed — draining the caller's wallet, not just the routed amount.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:34-37` performs `authorize_transfer_as_current(token_in, controller, router, amount_in)` and immediately calls `router.execute_strategy(&controller, &amount_in, swap)`, where `swap` is the raw `StrategySwap` supplied by the account owner to entrypoints such as `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and `flash_position`. The controller checks only the measured input/output deltas around the router call (`swap.rs:30-54`); it does not inspect which pool/venue addresses the route names. The threat model confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-160`). The dedicated adversarial test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:39-72,195-269` proves it: an `UnlistedPoolRouter` invokes whatever `hop_pool` the payload names, a `RogueHopPool` calls `token::transfer(victim, attacker, amount)`, simulation records that transfer as a child invocation of Alice's `swap_collateral` auth entry, and once Alice signs that tree her entire wallet balance moves to the attacker — while the swap itself still settles "fairly" and passes every controller-side measured-delta and risk check.

### Impact Explanation
Theft of user funds: the whole balance of any token the victim holds can be transferred to the attacker in the same transaction as an otherwise legitimate `swap_collateral`/`swap_debt`/etc. call. The controller's `RouterOverspend`/`NoSwapOutput` guards and the router's own min-out check do not bound the loss, because the stolen transfer is not part of the routed flow — it is a sibling sub-invocation under the victim's signature.

### Likelihood Explanation
Any unprivileged address can craft the malicious route (the payload format is public and venues are unallowlisted). Exploitation requires the victim to sign the authorization tree that simulation returns — which is exactly what standard simulation-and-sign wallet flows produce, since an honest route produces a clean tree and the poisoned child entry is indistinguishable without decoding the route. This mirrors Transit Swap, where a controllable `transferFrom` call drained wallets whose owners had interacted with the protocol; here the drained transfer rides on the auth tree of a routine leveraged-position management call. The hazard is acknowledged in `docs/explanation/threat-model.md` as a client-side decoding responsibility, but no in-scope mitigation exists — the contract happily executes the poisoned tree.

### Recommendation
Constrain the attack surface in-protocol rather than relying on every client to decode routes: maintain an allowlist of venue pool addresses (or venue contract WASMs) that the router/controller will invoke, and/or have the controller reject any `StrategySwap` whose declared venues are not recognized DEX adapters. At minimum, expose a signed-tree lint (e.g., a simulation helper or documented invariant enforced by the SDK) that fails when the auth tree beneath a controller strategy entry contains any token `transfer`/`transfer_from`/`approve` child other than the single expected input transfer.

### Proof of Concept
1. Attacker deploys a router-compatible contract and a `RogueHopPool` whose `swap()` executes `token::Client::transfer(victim, attacker, victim_balance)` on an unrelated wallet token (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:56-71`).
2. Victim calls `controller.swap_collateral` with a `StrategySwap` route whose `hop_pool` is the rogue pool; the controller authorizes only `token_in.transfer(controller, router, amount_in)` (`swap.rs:34`) and delegates the rest to the payload.
3. `simulateTransaction` records the rogue `transfer(victim → attacker, WALLET_BALANCE)` as a sub-invocation under the victim's `swap_collateral` auth entry (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:206-222`).
4. Victim signs the returned tree; the host executes the child transfer, the victim's wallet token balance goes to zero and the attacker's to `WALLET_BALANCE`, while the swap still completes and the position persists (`rogue_hop_pool_transfer_joins_caller_auth_tree.rs:224-227,265-269`).     pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {
        sender.require_auth();
        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();
        token::Client::new(&env, &route.token_in).transfer(&sender, &router, &total_in);
        let _: Val = env.invoke_contract(&route.hop_pool, &symbol_short!("swap"), vec![&env]);
        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }
