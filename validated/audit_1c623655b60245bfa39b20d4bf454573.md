In `_fillSameChain`, the solver's output tokens are sent with `safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal)`, but `outputFills[i]` is recorded using `fillAmount` (the nominal amount), not a measured balance delta, and the corresponding escrowed input is released based on that nominal `fillAmount`/`totalRequired` regardless of what the beneficiary actually received: [2](#0-1)

### Title
Fill-side output transfers don't verify actual amount received by the order beneficiary for fee-on-transfer tokens - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol, evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
Order beneficiaries (users) can receive less than the order's specified output amount if the output token has a fee-on-transfer, while the solver still claims the full escrowed input amount and the order is marked as completely filled.

### Finding Description
`placeOrder` was hardened to measure actual balances received for fee-on-transfer input tokens before recording the escrow amount and computing the commitment [4](#0-3) . No equivalent check exists on the output/fill side. In `_fillSameChain`, the amount released from escrow (`escrowedAmount`) and the `outputFills` recorded in the `OrderFilled`/`PartialFill` events are derived from `fillAmount`/`totalRequired` — the *requested* amount — not the amount actually credited to `beneficiary` after `safeTransferFrom` [5](#0-4) . The same pattern applies to `_fillCrossChain`, which dispatches `RedeemEscrow` carrying the full, unreduced `order.inputs` to the source chain for release to the solver, irrespective of what the beneficiary actually received on the destination chain [6](#0-5) .

### Impact Explanation
If a user's order specifies a fee-on-transfer token as an output asset, a solver only needs to transfer exactly `totalRequired`/`fillAmount` (or the code-mandated minimum) to satisfy the on-chain check; the beneficiary actually receives less due to the transfer fee. Since the fill/escrow-release logic uses the nominal (pre-fee) amount, the order is still marked fully filled and the solver still receives 100% of the proportional/total escrowed input. This directly causes silent value loss to users, a violation of the escrow/settlement invariant that beneficiaries receive what was promised.

### Likelihood Explanation
The path is reachable by any solver calling the permissionless `fillOrder` entry point [7](#0-6) ; no special privileges are required. It is triggered whenever a user's order output asset is a fee-on-transfer (or otherwise balance-deflating) ERC20 token — a scenario the codebase's own tests already treat as a first-class case for the input side [8](#0-7) , showing the developers are aware of and mitigate this pattern for inputs but did not extend the mitigation to outputs.

### Recommendation
Mirror the input-side fee-on-transfer handling on the fill path: measure the beneficiary's actual balance delta after each `safeTransferFrom` in `_fillSameChain` and `_fillCrossChain`, and use that measured amount (not the nominal `fillAmount`/`totalRequired`) when computing `outputFills`, deciding whether the fill is "full" for partial-fill accounting, and when releasing/redeeming the corresponding escrowed input.

### Proof of Concept
1. User places a same-chain order requesting a fee-on-transfer output token (`order.output.assets[0].token = FOT`, `amount = 1000`).
2. Solver calls `fillOrder` with `options.outputs[0].amount = 1000`; `safeTransferFrom(solver, beneficiary, 1000)` executes, but due to a 5% transfer fee the beneficiary only receives 950.
3. `_fillSameChain` still records `fillAmount = 1000`, treats the pair as fully satisfied (`amountFilled == totalRequired`), releases the entire escrowed input to the solver, and emits `OrderFilled` with `outputs` showing 1000 delivered.
4. The user ends up 50 tokens short of the order's requested output while the solver has already claimed the full input escrow.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {

        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received

        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
