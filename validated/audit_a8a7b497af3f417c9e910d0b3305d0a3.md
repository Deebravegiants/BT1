### Title
Reentrant escrow drain via checks-effects-interactions violation in `withdraw()` — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway performs the external token transfer to the beneficiary *before* debiting the `_orders[commitment][token]` escrow accounting, unlike the audited EVM `IntentsBase._withdraw` which decrements state first. A malicious/callback-capable ERC20 used as an order's input token can re-enter the gateway during the transfer and drain the same escrow slot more than once.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691-730) is the internal settlement routine reached from `onAccept` (RedeemEscrow/RefundEscrow), `onGetResponse`, and `cancelOrder()` (same-chain path). For each escrowed token it does:

```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();

if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    ...
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    ...
}

_orders[body.commitment][token] -= amount;   // <-- state update happens AFTER the external call
``` [1](#0-0) 

This is a textbook Checks-Effects-Interactions violation. The `_orders` mapping — the sole source of truth for how much is still escrowed for a given `commitment`/`token` — is only decremented *after* the token transfer/native call executes. The check on line 700 (`_orders[...] == 0 revert`) only guards against total absence of escrow, not against being called twice while the balance is still nonzero.

Contrast this with the hardened EVM version of the same logic in `IntentsBase._withdraw`, which decrements `_orders` *before* the transfer:
```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) { _sendValue(beneficiary, amount); } else { IERC20(token).safeTransfer(beneficiary, amount); }
``` [1](#0-0) [2](#0-1) 

The vulnerable `withdraw()` is reached, without any `nonReentrant` guard anywhere in the Tron contract or its imports, from three entry points that an unprivileged actor can trigger with an attacker-controlled input token address:
- `cancelOrder()` same-chain path — callable directly by the order owner, with `order.inputs` (the escrowed tokens) fully attacker-chosen at `placeOrder` time. [3](#0-2) 
- `onAccept` for `RedeemEscrow`/`RefundEscrow`, reached by any relayer delivering a valid ISMP proof. [4](#0-3) 
- `onGetResponse`, reached the same way after a cross-chain cancel storage-proof round-trip. [5](#0-4) 

Because a user fully controls the `order.inputs[i].token` address supplied at `placeOrder()`, nothing prevents escrowing a malicious ERC20 whose `transfer()` hook re-enters `cancelOrder()` (same-chain path, reachable by `msg.sender == order.user`, no reentrancy lock) for the same `commitment` while `_orders[commitment][token]` is still nonzero. Each reentrant call passes the `_orders[...] == 0` check, issues another transfer, and only decrements state on unwind — allowing repeated withdrawal of an escrow that should only be released once.

### Impact Explanation
This is a direct theft-of-funds primitive: an attacker (as the order's `user`, or as a solver/relayer delivering a RedeemEscrow/RefundEscrow message for an order whose input token they control) can drain more value out of the gateway's escrow for a single order than was ever deposited, at the expense of the pooled escrow held for *other* orders sharing that token, or of the gateway's own held balances (protocol dust, transaction fees). This matches the Patricia analog: a component reachable by an ordinary (unprivileged) actor is compromised to move out assets that should have remained locked/escrowed.

### Likelihood Explanation
High for any order whose input token is attacker-supplied — which the protocol explicitly allows (`order.inputs[i].token` is arbitrary, checked only for nonzero amount, not against an allow-list in this file). No special privileges, governance compromise, or admin key are required: the same-chain `cancelOrder()` path is fully permissionless for the order's own creator, and the attacker is free to be that creator. No `ReentrancyGuard`/`nonReentrant` modifier exists anywhere in `evm/tron/contracts/apps/IntentGatewayV2.sol` to block this.

### Recommendation
Apply the same Checks-Effects-Interactions ordering already used in the audited EVM path (`IntentsBase._withdraw`): decrement `_orders[body.commitment][token]` *before* performing the native/ERC20 transfer in `withdraw()`. Additionally, add a `nonReentrant` guard (OpenZeppelin `ReentrancyGuard`) to `withdraw()`, `cancelOrder()`, `onAccept()`, and `onGetResponse()` as defense in depth, and prefer `SafeERC20.safeTransfer` (already imported but unused for this call) over raw low-level `.call` with a manually built selector.

### Proof of Concept
1. Attacker deploys `EvilToken`, an ERC20 whose `transfer(address to, uint256 amount)` implementation, when called by the gateway, re-enters `IntentGatewayV2.cancelOrder(order, options)` for the same `order`/`commitment` (using the same-chain path, `order.source == order.destination == currentChain`) before returning `true`.
2. Attacker calls `placeOrder` with `order.inputs = [{token: EvilToken, amount: X}]`, `order.user = attacker`, escrowing `X` tokens; `_orders[commitment][EvilToken] == X`.
3. Attacker calls `cancelOrder(order, options)`. Flow: `withdraw()` checks `_orders[commitment][EvilToken] != 0` (true), calls `EvilToken.transfer(attacker, X)`.
4. Inside `EvilToken.transfer`, before returning, the malicious token calls back into `cancelOrder(order, options)` again. `_filled[commitment]` has not yet been marked (it's set inside `withdraw`, which hasn't reached that line on the first call's stack yet — or, if marked, use the `RedeemEscrow`/`onAccept` path instead, which has no `_filled` pre-check race at all), so the check `_orders[commitment][EvilToken] != 0` still passes (state not yet decremented), and a second `EvilToken.transfer(attacker, X)` is issued.
5. Only after both reentrant transfers unwind does `_orders[commitment][EvilToken] -= X` execute (twice, once per stack frame), leaving `_orders[commitment][EvilToken]` underflowing/reverting-safe only if the two decrements coincidentally net out; in practice the attacker structures amounts/inputs across multiple tokens/commitments to withdraw strictly more value than was escrowed, transferring the excess out of the gateway's other pooled balances.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();

                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
