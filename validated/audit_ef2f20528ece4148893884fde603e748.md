## Analysis

The strongest structural analog to the Flayer bug is in `orb-relay-client`'s message-dispatch loop. In the Flayer bug, a generic, normally-legitimate action (`redeem()`/`swap()`) is applied without checking whether the caller is the specific authorized claimant for a privileged item (the airdropped NFT). Here, a generic message-type check (`RequestState`) is applied *before* the source-authorization check (`src.id != self.config.dst_id`) that every other inbound message must pass, letting an unbound/unauthorized peer trigger a privileged action (replay of the last outbound message) without being the paired counterpart for that session.

### Title
Source-identity check bypass on `RequestState` messages allows any relay peer to obtain another session's last message - (File: orb-relay-client/src/client.rs)

### Summary
`PollerAgent::main_loop` validates every inbound relay message against the expected paired peer (`src.id == self.config.dst_id`) before processing it — except for messages matching `self_serve::app::v1::RequestState`, which are handled unconditionally and cause the client to resend `self.last_message` to whichever entity is on the other end of the relay socket. This mirrors the Flayer defect: a general-purpose operation bypasses the authorization check that gates access to session/state data intended for one specific, authorized counterpart.

### Finding Description
In the response-handling branch of `main_loop`, the logic is:

```
if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: ...");
} else {
    self.handle_message(...).await?;
}
``` [1](#0-0) 

The `src.id != self.config.dst_id` guard is the sole authorization mechanism binding a message to "the peer this client is actually paired with for this signup session" (`dst_id` is the counterpart's session/orb id set at construction time via `new_as_orb`/`new_as_app`). [2](#0-1) 

However, the `RequestState` branch is checked first and is not subject to that `src.id` comparison at all — the code replies with `self.last_message` (the last message this client sent, which for the Orb side is `AnnounceOrbId` and can include signup/session identifiers) to whatever connection delivered the payload, regardless of whether `src.id == dst_id`. Because gRPC-level authentication (`ConnectRequest`/`AuthMethod`) only authenticates that a caller possesses a valid orb/app token or ZKP proof — not that it is the specific counterpart bound to this `session_id`/`orb_id` pair — a client authenticated as *some* App or Orb entity, but not the one legitimately paired to this particular session, can still cause `RequestState` to be matched and receive `last_message`.

This is directly analogous to the Sherlock finding: `redeem()`/`swap()` in Flayer are general, "for anyone" operations that unintentionally reach a specific asset (the airdropped NFT) that should only be accessible to a designated authorized party; here, `RequestState` is a general, "for anyone who can dial the relay" message type that unintentionally reaches session state (`last_message`) that should only be replayed to the one authorized session peer.

### Impact Explanation
`last_message` for an Orb client is the most recently sent outbound message in the session — during self-serve signup this is typically `AnnounceOrbId` (carrying `orb_id`) or `SignupEnded`, and for the App side it can be `StartCapture`/`SignupEnded`-adjacent state. An attacker who can establish a relay connection (with a valid but session-unrelated token/ZKP) and send a `RequestState` payload can cause the peer's client to leak its last transmitted message to them instead of the actual paired App/Orb, resulting in cross-signup state disclosure and confusion about which session's Orb/App the receiver is bound to. This falls under "cross-signup state bleed," which is explicitly an accepted impact category for this analysis. It does not directly leak biometric images (those flow through a different pipeline), but it does leak session/orb-identifying state to an unauthorized listener and undermines the src/dst pairing invariant the rest of the loop relies on.

### Likelihood Explanation
Exploitability is gated by the relay's connection-level authentication (token or ZKP) succeeding for the attacker — the finding does not require possessing a legitimate orb operator token itself, only *a* valid credential for the App or Orb role plus knowledge of a `RequestState` payload shape (which is a fixed, publicly-known protobuf message defined in `orb_relay_messages::self_serve::app::v1`). The likelihood of exploitation is moderate to high in any deployment where the relay backend's authentication does not itself enforce that `src`/`dst` pairing matches token claims, since the orb-core client code, as written, provides no independent check for this specific message type. I could not verify from the client-side code whether the relay *server* additionally enforces src/dst pairing server-side (that logic is outside `orb-core`'s scope), which is the main uncertainty in assessing real-world exploitability.

### Recommendation
Move the `src.id != self.config.dst_id` check ahead of the `RequestState` special case so that `RequestState` messages are also validated against the expected paired peer before `last_message` is ever replayed:

```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await...
} else {
    self.handle_message(...).await?;
}
```
This ensures every inbound message type, including `RequestState`, is subject to the same authorization boundary as ordinary payloads, closing the bypass analogous to Flayer's missing claimant check on `redeem()`/`swap()`.

### Proof of Concept
1. An attacker obtains a valid App-role token (or independently valid ZKP credential) for the relay backend, but for a `session_id` different from the legitimate session under attack (or otherwise establishes a connection whose `src.id` does not equal the Orb's configured `dst_id`).
2. The attacker sends a `RelayPayload` whose `payload` matches `self_serve::app::v1::RequestState` to the target Orb's relay connection.
3. In `main_loop`, `self_serve::app::v1::RequestState::matches(&payload).is_some()` evaluates true first, before the `src.id != self.config.dst_id` check is ever reached. [3](#0-2) 
4. The Orb-side client replies with `self.last_message` (e.g., the last `AnnounceOrbId`/`SignupEnded`) directly to the attacker's connection rather than to the legitimate, paired App client, confirming state disclosure to an unauthorized party.

**Uncertainty:** I was not able to inspect the relay server implementation (it appears to live outside this repository, in `orb_relay_messages`/backend service, not indexed here) to confirm whether server-side routing additionally restricts delivery strictly to the `dst_id` originally specified at `ConnectRequest` time, which would mitigate or negate the client-side gap described above. This should be verified against the relay server's routing/authorization logic before treating this as a confirmed, fully exploitable vulnerability end-to-end.
