### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` and `SweepDust` handling allows silent failure with non-standard tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2` on the Tron deployment settles escrowed order funds and swept dust using a raw low-level `.call()` to invoke `IERC20.transfer`, checking only that the external call itself did not revert (`success`), but never inspecting the ABI-decoded boolean return value that `transfer` is supposed to return. This is exactly the "unchecked ERC20 transfer/transferFrom result" bug class from the referenced Cooler.sol report, reachable here by any relayer/unprivileged caller delivering a cross-chain `RedeemEscrow`/`RefundEscrow`/`SweepDust` message into `onAccept`.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function (invoked from `onAccept` for `RedeemEscrow`/`RefundEscrow` messages, and from `onGetResponse`) settles escrowed tokens to the beneficiary with: [1](#0-0) 
and fee-token redemption similarly: [2](#0-1) 

The same pattern is used for dust sweeping triggered by a `SweepDust` admin message processed in `onAccept`: [3](#0-2) 

In all three sites, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only checks the low-level `success` bool (i.e., that the callee didn't revert and has code). It never decodes/validates the ABI-encoded `bool` return value that ERC20 `transfer` returns to signal transfer success/failure. Non-standard ERC20 tokens (e.g., tokens that return `false` on failure instead of reverting) will make `success == true` even though no tokens moved, since a low-level call to a function that returns `false` still succeeds at the EVM call level.

This directly contrasts with the rest of the same contract and its EVM-mainline sibling, which correctly use OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer` (imported and used via `using SafeERC20 for IERC20;`) for escrow intake: [4](#0-3) [5](#0-4) 
but the fund-release/withdrawal path (`withdraw()`/`SweepDust`) was implemented with a manual low-level call instead of `SafeERC20.safeTransfer`, dropping the return-value check.

### Impact Explanation
If a beneficiary-designated output token, escrowed input token, or the protocol's fee token is a non-standard ERC20 that returns `false` on failed transfer (rather than reverting), `withdraw()` will treat the transfer as successful: it decrements `_orders[commitment][token]` and emits `EscrowReleased`/`EscrowRefunded` even though the beneficiary received nothing. This permanently locks the underlying value for that order (the escrow accounting is decremented so it cannot be re-claimed, but the beneficiary never got funds), and for `SweepDust` it could cause dust to be recorded as swept while remaining stuck in the contract. This is a fund-loss / permanent freezing vulnerability for the affected token type, not merely a bookkeeping bug — Medium severity, contingent on non-standard token usage.

### Likelihood Explanation
Trigger requires only that: (1) the intent gateway be configured to support a non-standard/no-revert-on-failure ERC20 as an order input/output or fee token, and (2) a relayer deliver the standard cross-chain `RedeemEscrow`/`RefundEscrow`/`SweepDust` request, which is a routine, unprivileged, expected part of protocol operation (`onAccept` is only gated by `onlyHost`, not by any special caller identity beyond the ISMP relay path). No malicious governance/admin action is needed — a single non-conforming token integration plus normal relay flow is sufficient.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer(IERC20(token), beneficiary, amount)`, consistent with the `using SafeERC20 for IERC20;` directive already declared in the contract and already used for the escrow-intake side (`safeTransferFrom`).

### Proof of Concept
1. Configure/support a token `T` that implements `transfer` to `return false` on failure (or intentionally fails silently) instead of reverting — a valid, if non-standard, ERC20 implementation.
2. A user places an order with token `T` as an input asset via `placeOrder`, which is escrowed via `safeTransferFrom` correctly.
3. Upon fill/settlement, hyperbridge delivers a `RedeemEscrow` (or `RefundEscrow`) message to `onAccept`, invoking `withdraw()`.
4. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is executed against `T`; suppose `T.transfer` returns `false` (e.g., due to an internal pause/blacklist condition on `beneficiary`) without reverting.
5. `success` is `true` (the call itself didn't revert), so `TransferFailed` is not raised; `_orders[body.commitment][token] -= amount;` proceeds and `EscrowReleased`/`EscrowRefunded` is emitted.
6. The beneficiary never receives the tokens, yet the escrow record is zeroed out — the funds are permanently stuck in the `IntentGatewayV2` contract with no accounting path to reclaim them. [6](#0-5)
