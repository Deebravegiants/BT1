### Title
Webhook `shop-domain` header trusted for tenant routing while excluded from HMAC coverage - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that HMAC and forwards `request.shop` straight into the handler's `WebhookMetadata` as the tenant identifier [3](#0-2) .

### Finding Description
The binding that should hold is: `hmac_signed_bytes == bytes_that_determine_tenant_identity`. Here it does not: `to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the signature that is compared against the `hmac-sha256` header [4](#0-3) . The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [5](#0-4) , which is never included in the signed content and is trivially attacker-controllable in the raw HTTP request.

`Registry.process` treats a passing HMAC check as sufficient authorization to dispatch the payload to the topic handler and passes `request.shop` (an unverified header) as the tenant/shop identity for that payload [3](#0-2) . Any downstream handler that uses `data.shop` to select which tenant's records to create/update/delete (the intended and documented usage pattern) is therefore trusting a field that carries no cryptographic binding to the signed body.

### Impact Explanation
An attacker who owns a legitimate (even free/dev) Shopify store and has your app installed on it can receive a genuinely Shopify-signed webhook body+HMAC pair for their own store. Because the HMAC covers only the body, the attacker can replay that exact body/HMAC pair to your webhook endpoint while substituting the `shopify-shop-domain` header for a victim merchant's domain. `Registry.process` will validate the (unchanged, still-valid) HMAC and dispatch the payload with the attacker-chosen `shop` value into the handler [3](#0-2) , causing the application to write/act on data under the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Requires no leaked credentials, no `api_secret_key`, and no privileged Shopify account — only that the attacker control any store with the target app installed (freely obtainable via a Shopify dev/partner store) so they can harvest a validly-signed body/HMAC pair, then replay it with a forged `shop-domain` header at the app's public webhook endpoint. This is an unprivileged-internet-user-reachable path that depends only on this gem's `Request`/`Registry` code, not on the host application ignoring documented behavior — the gem itself exposes `request.shop` from the header as trustworthy metadata post-HMAC-validation.

### Recommendation
Do not rely solely on `Utils::HmacValidator.validate(request)` to authorize the `shop` field. Either:
- Cross-check `request.shop` against the set of shops with active/known sessions/installations before dispatching, or
- Include the shop domain (and topic/webhook id) inside the signable string used for HMAC verification (this deviates from Shopify's own signing scheme, so this must instead be enforced by requiring callers/handlers to independently verify `shop` against their session store before trusting it for tenant-scoped operations), and update `docs/usage/webhooks.md` to explicitly warn that `shop`/`topic`/`webhook_id` are not covered by the HMAC and must be independently validated against known installed shops before being used for tenant-scoped writes.

### Proof of Concept
1. Attacker installs the target app on their own (e.g., free dev) Shopify store `attacker.myshopify.com`.
2. Shopify sends a genuine webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some JSON body `B`.
3. Attacker captures `B` and the valid HMAC, then sends a new HTTP request to the same endpoint with an unchanged body `B` and unchanged `x-shopify-hmac-sha256`, but with `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` reads the (unchanged) HMAC header, `#to_signable_string` returns the (unchanged) body, so `Utils::HmacValidator.validate` succeeds [6](#0-5) .
5. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"` [7](#0-6) , and any handler that uses this value to select the tenant record performs the update against the victim's data.

Note: I was unable to fully verify the exact tenant-lookup implementation the app would use downstream (`WebhookMetadata`/`webhook_handler.rb` consumer code), since that logic lives in the host application, not in this gem, so the concrete data-corruption outcome depends on how a given handler uses `data.shop`.
