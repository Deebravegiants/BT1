### Title
Webhook `shop` (and `topic`/`webhook_id`) attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (tenant identity), `topic`, and `webhook_id` values used to route and attribute that body are taken from unauthenticated HTTP headers that are never included in the signed content, so the binding `HMAC-covered bytes == data used for tenant attribution` does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) that are not part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC of the request (which only covers `@raw_body`) and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata`, which is handed to the app's registered handler: [3](#0-2) 

`WebhookMetadata` carries `shop` as a plain `String` field with no further validation, and app-provided `WebhookHandler#handle` implementations are expected to trust it for tenant-scoped operations (e.g., looking up/saving that shop's session, uninstalling data, updating tenant records): [4](#0-3) 

Because only the body bytes are HMAC-verified, a party who has ever received one legitimate signed webhook for a shop they control (a completely unprivileged action — any merchant that installs the app receives genuine webhooks signed with the app's shared secret over the body) can replay that same body to the public webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to point at a different, victim shop. `Utils::HmacValidator.validate` will still succeed because it only recomputes the HMAC over `to_signable_string` (`@raw_body`), which is unchanged: [5](#0-4) 

This directly matches the bug class in the report: a field acted upon (`shop`) by the downstream handler is not covered by the authentication mechanism (HMAC), while an unrelated field (`raw_body`) is.

### Impact Explanation
This breaks the tenant-identity binding `shop_that_signed_this_payload == shop_attributed_by_the_gem`. Any app that uses `request.shop` from `WebhookMetadata` to key data writes, session lookups, or state transitions (e.g., updating billing state, marking an app as uninstalled, storing customer-data-erasure requests, or writing to per-shop records) can be made to act on an arbitrary victim shop using a payload the attacker legitimately received for their own shop. This is a cross-tenant data integrity/confusion issue — an unprivileged actor (any shop that installs the app) can cause the library to hand the host application data falsely attributed to another tenant.

### Likelihood Explanation
Likelihood is high for any app that relies on `WebhookMetadata#shop` from this library without independently re-verifying shop identity (e.g., against a signed URL parameter or session table keyed differently). The only prerequisite is installing the app on any shop (fully unprivileged, self-service) and capturing one webhook delivery, then replaying it with a forged shop header to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or a canonical serialization of the header fields Shopify signs, if the actual Shopify delivery mechanism supports it) in the HMAC-signed content, or otherwise cryptographically bind the tenant identity to the signed payload before trusting it in `WebhookMetadata`. At minimum, document explicitly in `Registry.process`/`Request` that `shop`/`topic`/`webhook_id` headers are unauthenticated and must not be used for tenant-scoped writes without additional verification (e.g., cross-checking against a previously stored session for that shop).

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook event and capture the raw POST including headers and body — this delivery has a valid `X-Shopify-Hmac-Sha256` computed over the body with the app's shared secret.
2. Replay the exact same HTTP request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id` to a different registered topic/id).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `@raw_body`, and it matches unchanged — signature check passes.
4. `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` is passed to the app's handler, which processes attacker-supplied data as if it originated from `victim.myshopify.com`.
