### Title
Router with unlimited stale approval lets any caller siphon stranded input-token balance out of `ExternalActionSwap` into their own output UTXO - (File: contracts/external-actions/swaps/ExternalActionSwap.sol / contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` grants the LI.FI `router` a persistent, unbounded ERC20 approval on the action contract via `approveUnlimited`, and then forwards attacker-supplied `externalActionMetadata` calldata verbatim to that router. Nothing in `ExternalActionSwap.swap` or `Hinkal.transact` constrains how much of `inputToken` the router actually pulls to the `inputAmount` derived from `-deltaAmounts[0]` (i.e., the amount Hinkal transferred to the action *this* transaction). Any residual/stranded balance of that token already sitting at the action's address (dust from a prior partially-filled swap, rounding, or an unswept balance) can therefore be pulled into the router call and converted into extra output token, which is credited wholesale to the attacker's own freshly-minted UTXO.

### Finding Description
The invariant that should hold is: value leaving the action contract in a transaction should equal `-deltaAmountChanges` that Hinkal sent it in that same transaction (plus whatever it legitimately receives back as swap proceeds proportional to that input). Concretely, `inputAmount` used for the swap should bound the amount of `inputToken` actually consumed from the contract.

`ExternalActionSwap.swap` computes:
```
address inputToken = circomData.erc20TokenAddresses[0];
uint256 inputAmount = uint256(-deltaAmounts[0]);
...
uint256 swappedAmount = callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata);
``` [1](#0-0) 

`inputAmount` is passed to `callRouter` but never enforced there. `LifiExternalAction.callRouter` does:
```
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
...
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [2](#0-1) 

`approveUnlimited` sets `type(uint256).max` approval to `router` for `inputToken` whenever the current allowance is below half of max, and this approval is never revoked or scoped to `inputAmount`:
```
function approveUnlimited(address _erc20TokenAddress, address _to) internal {
    if (IERC20(_erc20TokenAddress).allowance(address(this), _to) < type(uint256).max / 2) {
        IERC20(_erc20TokenAddress).safeApprove(_to, 0);
        IERC20(_erc20TokenAddress).safeApprove(_to, type(uint256).max);
    }
}
``` [3](#0-2) 

`externalActionMetadata` is fully attacker-chosen calldata forwarded verbatim to `router` (the low-level `.call`). Since the router already holds unlimited allowance over the action contract's *entire current* `inputToken` balance — not just the amount transferred to it in this transaction — the attacker can encode a router call whose internal `amountIn` parameter is larger than `inputAmount`, as long as a residual balance of `inputToken` exists at the action address (e.g., dust left by a previous swap that under-consumed the approved/transferred amount, since nothing sweeps or asserts full consumption of `inputToken` after `callRouter` returns). `swappedAmount` is measured purely by before/after balance of `outputToken`, so it faithfully — but blindly — reports whatever the router actually delivered, including proceeds attributable to the stranded balance.

The resulting `amountToSendToHinkal` (== real `swappedAmount` minus fees) is transferred to Hinkal and packaged as `utxoSet[0]` addressed to `circomData.stealthAddressStructure`, which the attacker fully controls in the transaction they submit:
```
transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);
utxoSet[0] = UTXO({ amount: amountToSendToHinkal, erc20Address: outputToken, stealthAddressStructure: circomData.stealthAddressStructure, timeStamp: block.timestamp });
``` [4](#0-3) 

At the `Hinkal.transact` level, the per-token equality only ties the *Hinkal contract's own* balance delta to `amountChanges[i] + utxoAmount`; `utxoAmount` is derived after the fact from `utxoSet`, so it self-satisfies regardless of how much of that value actually originated from the attacker's own declared input versus stranded funds:
```
require(balanceDif == (... ? int256(0) : circomData.amountChanges[i]) + int256(utxoAmount), "...");
``` [5](#0-4) 

The only slippage check (`circomData.slippageValues[1] != 0` and `balanceDif >= circomData.slippageValues[i]`) is a *floor*, not a ceiling — it cannot prevent an inflated output from being accepted. [6](#0-5) [7](#0-6) 

Because the persistent unlimited approval to the fixed `router` address is set once and reused indefinitely (the "prior Emporium op set a persistent approval" precondition in the question corresponds to any earlier legitimate swap already having invoked `approveUnlimited`), any subsequent unprivileged caller who finds (or engineers, e.g., by deliberately crafting a prior swap that leaves dust) a nonzero `inputToken` balance at the action contract can redirect it into their own shielded output by simply widening the amount requested from the router in `externalActionMetadata`.

Because `LifiExternalAction` and its `router` address are typically deployed identically (or with the same integration pattern) on both Base and Arbitrum, the same crafted `externalActionMetadata`/exploit pattern is directly reusable ("replayed") against the analogous stranded balance on each chain's deployment.

### Impact Explanation
An unprivileged attacker can misappropriate token balances that the action contract holds but that are not owed to the attacker for that transaction (residual dust, unswept partial-fill remainders, or any other stray balance parked at the `LifiExternalAction` address). This is captured as a genuine, spendable shielded UTXO under the attacker's control, i.e., direct theft of protocol/other-users' in-flight funds — matching the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable each time a nonzero residual balance accumulates, and is reproducible independently on every chain where the contracts are deployed with the same pattern (Base, Arbitrum).

### Likelihood Explanation
Preconditions: (1) `router` must already hold (or be granted) unlimited approval on `inputToken` for the action contract — guaranteed after any single prior legitimate swap of that token pair via `approveUnlimited`; (2) a nonzero stray/residual balance of `inputToken` must exist at the action address. Such residue is plausible from partial fills, rounding, or dust left by LI.FI multi-hop routes that don't consume 100% of the approved/transferred amount — nothing in `swap()`/`callRouter` asserts full consumption of `inputToken`. The attacker needs only to submit a normal `Hinkal.transact` call with a crafted `externalActionMetadata` payload to the (public, permissionless) router; no privileged role, oracle assumption, or third-party compromise is required. Cost is a single valid proof for the attacker's own (possibly minimal) deposit.

### Recommendation
- Scope router approvals to the exact `inputAmount` of the current call instead of `type(uint256).max`, and reset/revoke the allowance to zero after the router call returns.
- After `callRouter`, assert that the action contract's `inputToken` balance decreased by exactly `inputAmount` (no more, no less), reverting otherwise.
- Alternatively/additionally, snapshot `inputToken` balance before and after the router call and require the delta equals `inputAmount`, so any router pull beyond what Hinkal sent this transaction reverts rather than silently being absorbed into `swappedAmount`.
- Sweep/forbid stray balances from persisting at the action address; if unavoidable, ensure any residual can only be reclaimed by an owner-mediated rescue path, not through the permissionless swap function.

### Proof of Concept
Foundry outline:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock LI.FI `router` whose `swap(address token,address to,uint256 amount)` performs `transferFrom(msg.sender, address(this), amount)` then mints/transfers `amount` (1:1) of `outputToken` back to `msg.sender`), register the action.
2. Transaction A (benign, done by any user via `Hinkal.transact`): swap `inputToken -> outputToken` with `inputAmount = 100`, but craft `externalActionMetadata` so the mock router only consumes `60` of the approved `100` (simulating a partial-fill/dust scenario). Assert `IERC20(inputToken).balanceOf(lifiAction) == 40` after the transaction (residual stranded balance), and that `approveUnlimited` has left `router` with `type(uint256).max` allowance on `lifiAction`.
3. Transaction B (attacker, unrelated EOA, own deposit of `inputAmount = 1` only): craft `externalActionMetadata` so the mock router calls `swap(inputToken, lifiAction, 41)` (1 attacker-contributed + 40 stranded), pulling the full stranded balance via the pre-existing unlimited allowance.
4. Assert: `swappedAmount` reported by `callRouter` (and thus `utxoSet[0].amount` / `amountToSendToHinkal`) equals `41`, not `1` — i.e., `swappedAmount != inputAmount_B` (breaking "tokens leaving the action == -deltaAmountChanges Hinkal sent it that tx"), and that the resulting UTXO commitment is addressed to the attacker's `stealthAddressStructure`, so the attacker's shielded balance increases by value that was never contributed by them in transaction B.
5. Repeat the same deployment/config on a second chain id (simulating Base/Arbitrum) to show the identical `externalActionMetadata` payload reproduces the theft against that chain's independently-stranded residual.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
