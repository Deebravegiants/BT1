This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without being part of the HMAC-signed content [2](#0-1) . `Registry.process` only validates the HMAC over the request (i.e., the raw body) and then forwards the header-derived `shop` value straight to the handler [3](#0-2) .

### Title
Webhook tenant identity (`shop` header) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC signature computed over the raw request body via `Utils::HmacValidator.validate` [4](#0-3) . The `shop` value that identifies which tenant/store the webhook belongs to is read directly from the `x-shopify-shop-domain` HTTP header [2](#0-1) , but `to_signable_string`—the data the HMAC actually signs—only includes the raw body, never the shop-domain header [1](#0-0) . This breaks the identity binding `authenticated_shop == acted_upon_shop`: the HMAC guarantees body integrity for *some* shop registered with the app (Shopify signs all webhooks for an app with the same `client_secret`, regardless of which shop triggered them), but it does not guarantee that the `shop` header used by the handler matches the shop that actually produced the signed body.

### Finding Description
`Registry.process(request)` performs exactly one authentication check—`Utils::HmacValidator.validate(request)`—and then immediately builds `WebhookMetadata` using `request.shop`, which is taken verbatim from the header, and hands it to the app's registered handler [3](#0-2) . Because `to_signable_string` for `Webhooks::Request` is defined as just `@raw_body` [1](#0-0) , the HMAC is computed and verified only over the JSON body — the `shop`, `topic`, `api-version`, and `webhook-id` headers are read but never cryptographically bound to the signature. `HmacValidator.validate_signature` simply recomputes the HMAC of `to_signable_string` and compares it to the received `hmac` value [5](#0-4) , so any request whose body+HMAC pair is valid for the app's shared `api_secret_key` passes, irrespective of the `shop` header content.

Since a single app's `client_secret`/`api_secret_key` is shared across all shops that install the app, and Shopify signs webhooks per-app (not per-shop) with that secret, an attacker who controls or has installed the app on their own store can capture a legitimate, validly-signed webhook payload (e.g., from an `orders/create` or `app/uninstalled` topic on their own shop) and resend it directly to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates because it only covers the unmodified raw body. The `WebhookMetadata` passed to the handler then reports the victim's shop, so any host application that uses `data.shop` from `ShopifyAPI::Webhooks::WebhookMetadata` to key its persistence/lookup logic (the documented and expected usage pattern for this gem) will process forged webhook events under the wrong tenant.

### Impact Explanation
This crosses a tenant boundary using only the app's shared secret capability that legitimate app installers already possess (installing the app on any shop) — no access token, session, or victim credential is required. By replaying a self-obtained, validly-signed payload with a forged shop-domain header, an attacker can make the host application believe events (order data, app/uninstalled, GDPR topics, etc.) originated from a different, victim merchant. Depending on handler logic this enables cross-tenant data injection/corruption (e.g., falsely triggering `app/uninstalled` cleanup or `shop/redact` for a victim shop, or injecting attacker-controlled order/customer data attributed to a victim's store), which matches the "cross-tenant access" criteria.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (a normal, low-privilege action for any Shopify merchant/developer) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with custom headers — both trivially available to any unprivileged internet user/app installer. No secrets, tokens, or insider access are required, only observation of the gem's documented header parsing behavior and the fact that HMAC coverage excludes headers.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id/api-version) header values as part of the signed data verified by `HmacValidator`, or explicitly cross-check `request.shop` against an independently trusted source before dispatch. Since Shopify's actual HMAC signing algorithm for webhooks only signs the raw body by design, the safer mitigation within this gem is to require host applications to independently verify that the shop reported in metadata is one the app has an active session/install record for before trusting webhook-derived tenant identity, and to document this gap explicitly in `Webhooks::Registry.process`/`Request`. At minimum, the library should not present `request.shop`/`WebhookMetadata#shop` as if it were HMAC-authenticated when it is not.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) so Shopify sends a legitimately-signed request to the app's webhook endpoint.
2. Capture the raw body and the `x-shopify-hmac-sha256` value from that request — the signature is valid because it is computed over the body using the app's shared `api_secret_key`.
3. Resend the same raw body and HMAC to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3) , which still succeeds because `to_signable_string` only checks `@raw_body` [1](#0-0) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled data as if it belonged to the victim shop.
