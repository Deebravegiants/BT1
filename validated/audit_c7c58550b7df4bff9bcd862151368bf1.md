### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the request body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then trusts the `shop-domain` header — which is never covered by that HMAC — as the tenant identity passed to the app's handler. The binding the app relies on, `hmac_valid(body) == shop_is_correct`, does not hold: the same shared app secret produces a valid signature for any shop's body, and the `shop` field is excluded from the signed payload, so an attacker who possesses one valid `(body, hmac)` pair (e.g., from their own store's legitimate webhook delivery) can attach an arbitrary `shop-domain` header and have the app process it as if it came from a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are not part of the signed string: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC via `Utils::HmacValidator.validate(request)` and then immediately forwards `request.shop` (an unauthenticated header value) to the handler as the tenant identifier: [4](#0-3) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (the body) with the app's single `Context.api_secret_key`, which is shared across every shop that installs the app — it is not shop-specific: [5](#0-4) 

Because the secret is app-wide and the `shop` header is excluded from the signed material, `HMAC(secret, body)` is valid regardless of which shop the body nominally belongs to. This exactly mirrors the reported bug class: a field (`excess`/here, `shop`) that is acted upon by security-relevant logic is not actually covered/derived from the value that was supposed to bind it (`maxCollateral` init/here, the HMAC digest), breaking the equality `authenticated_body.shop == trusted.shop` that the handler implicitly assumes.

### Impact Explanation
Any actor who can obtain one legitimate `(raw_body, hmac)` pair — trivially available to anyone who installs the app on their own (even free/dev) store and receives one webhook delivery — can replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will pass HMAC validation (since the body/HMAC pair is genuinely valid for the app's secret) and hand the handler a `WebhookMetadata` claiming the event is for the victim's shop, with attacker-chosen `body` content. This is cross-tenant identity confusion delivered through the gem's own webhook-processing API, matching the Critical "cross-tenant access" impact category — a host application built strictly on this gem's documented `Registry.process`/`WebhookMetadata` API has no way to further authenticate the shop, since the gem asserts the webhook (including its shop attribution) is verified once HMAC validation passes.

### Likelihood Explanation
Moderate-to-high: obtaining a valid `(body, hmac)` sample requires nothing more than being an app user (any merchant/dev-store owner can install a public/free app and capture one webhook delivery via a proxy they control), and replaying it with a modified header requires only a basic HTTP client — no access to `api_secret_key`, tokens, or TLS interception is needed. The main constraint is that the replayed body's *content* is fixed to whatever was captured (unless the attacker also controls the body of their own webhook, e.g., by editing their own shop's order details before the webhook fires, which is fully within a merchant's control for many topics).

### Recommendation
Bind the shop identity into the authenticated material before it's trusted by handlers: verify that the `shop` header value matches an app-tracked shop associated with the specific webhook subscription (e.g., via `webhook_id` correlated server-side), or require host applications to independently confirm shop ownership before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated headers not covered by the HMAC, and that consuming applications must not use them as an authorization or tenant-isolation boundary without additional verification (e.g., checking the shop already has a valid, stored session/access token before acting on the payload).

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) development store, subscribing to a webhook topic (e.g. `orders/create`).
2. Attacker captures one legitimate webhook delivery to their endpoint: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(app_secret, B)` — valid because the app secret is shared across all installs, not shop-specific.
3. Attacker sends a forged HTTP request to the same app's webhook endpoint with:
   - body = `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still cryptographically valid)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - `x-shopify-topic`, `x-shopify-webhook-id` set arbitrarily/matching the topic.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process/act on data attributed to `victim-shop.myshopify.com` that never actually originated from that shop.
