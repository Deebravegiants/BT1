### Title
Interest accrual overflow permanently freezes a market — any verb panics before the borrow-index cap can engage - (File: contracts/pool/src/interest.rs)

### Summary
`global_sync` accrues interest before every pool/controller verb. When `scaled_to_original` (i.e., `scaled * borrow_index`) overflows `i128`, `accrue_step` panics with `MathOverflow` inside `accrue_chunk`. Because every mutation — `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, `update_indexes` — calls `Cache::load` → `global_sync` first, the market becomes permanently unoperable: suppliers cannot exit, borrowers cannot repay, liquidators cannot act. The `MAX_BORROW_INDEX_RAY` index cap exists precisely to bound this, but the value ceiling `supplied_scaled * borrow_index < i128::MAX` is reached first when the book is large, so the cap never engages.

### Finding Description
- `interest::global_sync` runs unconditionally ahead of any market mutation and panics propagate out of `accrue_chunk` → `accrue_step` (`common/src/rates`), where index growth multiplies scaled debt by the borrow index.
- `common/src/rates/scaling.rs::scaled_to_original` performs `scaled.mul(env, index)` which traps on `i128` overflow (`GenericError::MathOverflow`, error 33).
- The repository's own adversarial test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the exact freeze: a 1-billion-token 18-decimal market at ~98% utilization on the steep XLM curve hits `MathOverflow` in `try_update_indexes_for`, after which `try_withdraw_raw` and `try_repay` both revert with the same error, and `borrow_index < MAX_BORROW_INDEX_RAY` confirms the cap never fired.
- Root cause: the cap logic bounds `borrow_index` but nothing bounds `borrowed_scaled * borrow_index` (and symmetrically `supplied_scaled * supply_index`) inside accrual; accrual is all-or-nothing, so a single overflowing chunk bricks the market rather than clamping.

### Impact Explanation
Permanent freezing of funds for every participant in the affected market. Once one accrual chunk overflows, `last_timestamp` is never advanced (the panic rolls back `mark_accrued`), so every subsequent call re-executes the same overflowing accrual and reverts forever. Suppliers' principal and unclaimed yield, borrowers' collateral recovery via `repay`/`repay_debt_with_collateral`, and liquidation/`clean_bad_debt`/`recapitalize` are all dead. This matches the report's class (a repeatable crash/complete DoS of the component) but here it is unrecoverable state, not a restartable hang.

### Likelihood Explanation
Requires a large book at sustained near-max utilization on a steep rate curve — the test reaches the cliff in a few years at 98% utilization for a 1e9-token market. An unprivileged attacker cannot jump time, but can push utilization to the steep segment via `borrow` (allowed by caps, e.g. `lift_caps`/high governance caps on a whale-scale asset) and merely needs to prevent `update_indexes`/repayments from ever succeeding once the cliff is crossed — which happens automatically, since accrual itself is what panics. No admin, oracle manipulation, or key compromise is involved; the trigger inputs are ordinary `supply`/`borrow` calls and elapsed ledger time. Medium likelihood, matching the Medium severity of the source report.

### Recommendation
Clamp instead of trap inside accrual: in `accrue_step`/`accrue_chunk`, saturate `borrow_index` at `MAX_BORROW_INDEX_RAY` *before* computing scaled-value products, and compute `scaled * index` with a saturating/checked path that caps the accrued amount rather than panicking. Alternatively, bound accrual so `borrowed_scaled * new_index` cannot exceed `i128::MAX` (e.g., cap the index at `i128::MAX / borrowed_scaled` when nonzero), and advance `last_timestamp` even when the cap binds so the market remains operable at a frozen index. Add a regression test asserting `withdraw`/`repay` still succeed after the cap engages.

### Proof of Concept
Existing test demonstrating the freeze (see `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`):

```rust
// supply 1e9 BIG18 (18 decimals), borrow 98% of it against COL collateral,
// advance time until accrual panics:
if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
// => Error(Contract, MATH_OVERFLOW)
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged
```
