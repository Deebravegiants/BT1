## Analysis

I identified a strong analog in the vote program's block-revenue-sharing (SIMD-0123 / SIMD-0291) reward distribution path.

### Title
`UpdateCommissionBps` with `CommissionKind::BlockRevenue` allows the withdraw authority to retroactively change the commission split applied to already-accrued `pending_delegator_rewards` - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The Solana `V3Vault.setReserveFactor` bug is a class of issue where a rate/commission parameter is mutated instantly and is then applied retroactively over an already-elapsed accrual period instead of only to future accrual. Agave's vote program exhibits the same class of bug for `block_revenue_commission_bps`: block revenue accrues into a pool (`pending_delegator_rewards`) over time, but the commission rate applied to that entire pool at payout time is read live at distribution time and can be changed instantly by the vote account's withdraw authority with no delay rule, unlike the legacy/inflation commission path which is explicitly time-gated.

### Finding Description
`pending_delegator_rewards` is a running balance on the vote account that accumulates block-revenue deposits over an arbitrary span of time via `deposit_delegator_rewards` [1](#0-0) . The withdraw authority can call `UpdateCommissionBps` with `CommissionKind::BlockRevenue` to change `block_revenue_commission_bps` at any time, and the code explicitly documents that there is **no delay/update rule** for this path, unlike the legacy `update_commission` function which enforces `is_commission_update_allowed` (an epoch-midpoint cutoff) and is further protected by the `delay_commission_updates` feature at reward-calculation time: [2](#0-1) 

For comparison, the *inflation* rewards commission path is deliberately protected against retroactive misapplication: `redeem_delegation_rewards` fetches the commission from a snapshot taken 1–2 epochs earlier when `delay_commission_updates` is active, specifically "to attempt to delay the effect of commission updates by at least one full epoch": [3](#0-2) 

However, the block-revenue-sharing distribution path (`calculate_block_reward`, used when `block_revenue_sharing` is enabled) reads `pending_delegator_rewards` from the **live, current** `distribution_epoch_vote_accounts` snapshot and simply splits it proportionally to stake — with no equivalent delay applied to the commission rate that determines how much of that pool the validator vs. delegators receive: [4](#0-3) 

Because `pending_delegator_rewards` is a single scalar balance (not tracked per-accrual-interval), any commission-bps change made via `UpdateCommissionBps(BlockRevenue, ...)` is retroactively applied to the *entire* accumulated pool at whatever value it holds at the next distribution, not just to revenue collected after the change — precisely mirroring the `setReserveFactor` bug where the reserve factor was applied retroactively to interest that had already accrued under the old rate.

### Impact Explanation
An unprivileged vote-account withdraw authority (not a validator/operator-role-privileged action in the SECURITY.md sense — this is a normal vote-account owner instruction, reachable by any user with withdraw authority over their own vote account) can increase `block_revenue_commission_bps` immediately before a distribution event, capturing a larger share of delegator rewards that were already earned under a lower commission rate, or decrease it right before distribution to under-collect on rewards accrued while a higher rate was nominally in effect. This is a concrete value-misallocation/underpriced-distribution bug affecting delegator vs. validator reward splits — the same "math is broken" impact class the C4 judge confirmed for the original finding (mislabeled math causing unfair value shift, not outright theft).

### Likelihood Explanation
This requires no special privilege beyond being the vote account's authorized withdrawer, and `UpdateCommissionBps`/`CommissionKind::BlockRevenue` is a normal, feature-gated (`block_revenue_sharing`/SIMD-0123, `commission_rate_in_basis_points`/SIMD-0291) but otherwise unrestricted instruction path, callable at any slot with a single signed transaction. It is deterministic and reproducible whenever a validator has a nonzero `pending_delegator_rewards` balance and controls the timing of a commission-bps update relative to when distribution/redemption occurs.

### Recommendation
Apply the same delay/snapshotting discipline used for `inflation_rewards_commission_bps` to `block_revenue_commission_bps`: either (a) checkpoint/settle `pending_delegator_rewards` against the commission rate in effect at time of accrual (each deposit should record the commission rate active at deposit time, or immediately split/collect commission on each `deposit_delegator_rewards` call rather than deferring it to a lump-sum distribution), or (b) read `block_revenue_commission_bps` from a prior-epoch snapshot (analogous to `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`) in `calculate_block_reward`, so that commission changes cannot retroactively apply to already-pooled revenue.

### Proof of Concept
Conceptual sequence (not run against the live repo, since this is protocol/program logic rather than an isolated unit that can be exercised without a full bank/test harness):
1. Vote account V has `block_revenue_commission_bps = 0` and accumulates `pending_delegator_rewards = X` lamports over many blocks via repeated `deposit_delegator_rewards` calls (fee revenue sharing).
2. Immediately before the next `calculate_block_reward`/distribution pass reads `distribution_epoch_vote_accounts`, the withdraw authority calls `UpdateCommissionBps { commission_bps: 10000, kind: BlockRevenue }` (100% commission) — allowed instantly per `update_commission_bps`'s "No commission update rule" comment.
3. At distribution, the *entire* pooled `X` is now treated as subject to the new 100% commission rate (the split logic that reduces `pending_delegator_rewards` by the delegator share uses the live `block_revenue_commission_bps`), even though most of `X` accrued while the rate was 0%.
4. Delegators of V who earned rewards under the old 0% rate get retroactively diluted/zeroed out, analogous to lenders in the `V3Vault` PoC receiving an unexpectedly worse `lendExchangeRateX96` because the reserve factor was changed without first settling accrued interest.

I could not locate the exact code path that subtracts the commission share from `pending_delegator_rewards` at distribution time within the indexed portion of the repository (only the `pending_delegator_rewards`-to-stake split in `calculate_block_reward` and the commission-bps setter were found); confirming the precise settlement code (and whether any complementary delay already exists there that I could not find via search) would require a full Devin session with file-system access to trace `RewardCommission`/`reward_commissions` consumption for `BlockRevenue` in `runtime/src/bank/partitioned_epoch_rewards/`.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
