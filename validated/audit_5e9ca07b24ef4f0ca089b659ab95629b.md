### Title
Webhook `shop` identifier is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, but the `shop` value that is handed to the app's handler as the tenant identifier is read from an HTTP header that is never included in the signed payload. Any party that can obtain one genuinely-signed webhook body (e.g. by installing the app on their own store) can replay that body with a forged `X-Shopify-Shop-Domain` header pointing at a different (victim) shop, and the library will report the request as valid and hand the handler a `WebhookMetadata` object claiming the payload came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient to trust the entire `Request`, including `request.shop`, which it forwards unmodified to the app's handler: [4](#0-3) 

The broken identity binding is:
`computed_hmac(raw_body) == received_hmac` is treated as proving `request.shop == "the shop that generated this webhook"`, but `shop` is never an input to the HMAC computation. Because the app's client secret (`api_secret_key`) used to sign webhooks is shared across every shop that installs the app — not shop-specific — any merchant who installs the app can generate a webhook payload with a *genuinely valid* HMAC for their own shop, then replay that exact body/HMAC pair while substituting the `shop-domain` header for an unrelated victim shop. The library will accept it as authentic and hand the consuming application a `WebhookMetadata` record claiming the (attacker-controlled) body originated from the victim's shop, since the shop field is never validated against the signed content.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker who has (or creates) a legitimate installation of the app on one shop can make the library-level webhook validation vouch for arbitrary data as belonging to a different, victim tenant. Any application logic keyed off `WebhookMetadata#shop` (e.g. updating per-shop settings, triggering shop-specific side effects, writing to a shop-scoped record) can be corrupted or hijacked cross-tenant purely by manipulating an unauthenticated header, which the gem never validates against the HMAC.

### Likelihood Explanation
High: the only prerequisite is installing the target app on any (attacker-controlled) shop — a normal, unprivileged action for any Shopify merchant/developer — and being able to POST to the app's public webhook endpoint, which is by definition internet-reachable. No access token, secret leakage, or privileged account is required; header spoofing on an HTTP POST is trivial.

### Recommendation
Bind the `shop` (and other identity-relevant fields such as `topic`/`webhook_id`, if the app trusts them) into the value that is HMAC-verified, or independently authenticate the shop domain (e.g. reconcile it against a value obtained from an authenticated source such as a signed session or a previously stored shop record), rather than trusting an unauthenticated request header. At minimum, `Webhooks::Request` should not expose `shop` as if it were verified data without explicitly documenting to consumers that the HMAC only covers the body, and the library should provide a way to bind shop identity to the signature (Shopify webhook payloads for topics like `shop/redact` etc. often embed the shop’s domain/id in the JSON body itself, which could instead be used and cross-checked against the header).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to (e.g. `products/create`), causing Shopify to POST a body `B` with a valid `x-shopify-hmac-sha256` header `H = HMAC-SHA256(api_secret_key, B)` to the app's webhook endpoint.
2. Attacker captures `B` and `H`.
3. Attacker crafts a new POST to the same endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `H` against `HMAC(api_secret_key, B)` — see [5](#0-4) .
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-supplied data as if it belonged to the victim shop.
