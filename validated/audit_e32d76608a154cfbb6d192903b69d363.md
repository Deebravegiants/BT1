### Title
Shared Emporium identity in CASE 2 stateless ops allows any Hinkal user to hijack another user's external-protocol position - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract itself, so `msg.sender` at the external protocol is always the same shared `EmporiumUpgradeable` address regardless of which Hinkal user's transaction triggered it. Any state an external protocol tracks against that shared identity (e.g. Aave `aToken` balances from a `deposit(..., onBehalfOf=Emporium)`) is therefore controllable by any subsequent unrelated Hinkal user who can submit their own CASE 2 op targeting the same endpoint, since neither `op.endpoint` nor `op.callData` is whitelisted or bound to the originating user.

### Finding Description
The broken equality is: `asset_owner(pre-existing external-protocol position created by victim's CASE 2 op)` should equal `beneficiary_of_subsequent_withdrawal(next CASE 2 op targeting same endpoint)` — but it does not, because both operations share the exact same on-chain identity (`address(EmporiumUpgradeable)`).

Code path: `EmporiumUpgradeable.runAction` [1](#0-0)  takes the CASE 2 branch whenever `op.invokeWallet == false`, and executes the call with `EmporiumUpgradeable` as `msg.sender`, using an attacker-supplied `op.endpoint`/`op.callData` pair with only a narrow selector-based check against re-entering the wallet interface [2](#0-1) . Access to `runAction` itself is gated only by `onlyAllowedRecipient`, which simply checks `msg.sender == Hinkal` [3](#0-2)  — this passes for any Hinkal user's `transact`, not just the one who created the position. There is no whitelist of `op.endpoint` or per-user binding anywhere in `ExternalActionBaseUpgradeable`, `ExternalActionBaseV2`, or `EmporiumUpgradeable` (confirmed by inspection of all three files) [4](#0-3) .

Exploit flow: victim submits a `transact` whose `EmporiumStack.ops[0]` is CASE 2 with `callData = deposit(asset, amount, onBehalfOf=Emporium address)` against a lending pool; the lending pool credits the aToken position to Emporium's address (msg.sender/onBehalfOf), not to any Hinkal-tracked balance, so it never appears in the balance-diff loop over `circomData.erc20TokenAddresses` [5](#0-4)  if that token isn't included by the victim. Attacker then submits their own unrelated `transact` with a CASE 2 op calling `lendingPool.withdraw(asset, amount, attackerRecipient)`; since Aave-style `withdraw` burns aTokens owned by `msg.sender` (Emporium) and sends the underlying directly to the `to` parameter (`attackerRecipient`, an address outside Hinkal entirely), the funds never touch Emporium's own balance and the balance-diff/UTXO minting logic never registers the movement at all. The theft happens via the raw external call side effect, which the balance-based accounting in `runAction` was never designed to police across unrelated transactions.

None of `performHinkalChecks`, `verifyProof`, `insertNullifiers`, `verifyWallet` (which only validates an EIP-712 signature for CASE 1's wallet-invoking path, and is skipped when `signerAddress == address(0)`), or the balance-change guard `BalanceChangeShouldBePositive` constrain which external identity performs CASE 2 calls or whether a position created by one Hinkal user is later drained by another.

### Impact Explanation
A victim's protocol-side position (e.g., aToken balance from a lending-pool deposit routed through Emporium's shared identity) can be directly stolen by any other unprivileged Hinkal user, with funds routed to an attacker-chosen external recipient that never passes through Hinkal's shielded-balance accounting. This is direct theft of a shielded user's protocol-side value created by a stateless op and matches the Critical category ("direct theft of shielded or in-flight user funds" / "executing calls or moving assets a wallet owner or prover never authorised"). The attack is repeatable against any external protocol state accumulated under Emporium's shared address whenever a CASE 2 op is used with an `onBehalfOf`/beneficiary parameter distinct from the immediate caller.

### Likelihood Explanation
Preconditions: Emporium must be registered as an `externalActionId` (already the case for its intended use), the target external protocol must support an operation with a persistent, address-keyed state (deposit/onBehalfOf pattern) reachable via CASE 2, and a victim transaction must have already executed such a CASE 2 op leaving state under Emporium's address. No special role is required by the attacker — only the ability to submit their own valid `transact` with a proof over their own UTXOs and freely crafted `externalActionMetadata`/`CircomData`, which is exactly the attacker capability model in scope. This is straightforward and repeatable for any protocol integrated this way.

### Recommendation
Bind CASE 2 external-protocol state to the originating user rather than to Emporium's shared address: either (a) require CASE 2 stateful positions to always route through per-user `HinkalWallet` instances (CASE 1) instead of the shared Emporium identity whenever the target function creates persistent external state keyed by caller/beneficiary, or (b) maintain an explicit per-user record inside Emporium of which balances/positions belong to which `emporiumMessage`/signer, and require withdrawal ops to reference and be authorized against that record rather than trusting the shared address's balance/protocol identity, or (c) whitelist `op.endpoint` + require that any `onBehalfOf`/beneficiary parameter embedded in `op.callData` match the caller's own `HinkalWallet` address rather than allowing Emporium's own address to be the beneficiary of un-invoked (CASE 2) operations.

### Proof of Concept
Foundry fork test plan:
1. Deploy a mock ERC20 (`asset`) and a mock lending pool with `deposit(address asset, uint256 amount, address onBehalfOf)` minting mock aTokens to `onBehalfOf`, and `withdraw(address asset, uint256 amount, address to)` burning aTokens from `msg.sender` and transferring `asset` to `to`.
2. Register `EmporiumUpgradeable` as `externalActionMap[id]` in `Hinkal`.
3. Victim calls `Hinkal.transact` with a valid proof for their own UTXO input, `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `ops[0] = {endpoint: lendingPool, invokeWallet: false, callData: deposit(asset, amount, onBehalfOf=EmporiumUpgradeable address)}`, and `circomData.erc20TokenAddresses` excluding the aToken. Assert `lendingPool.aTokenBalanceOf(Emporium) == amount`.
4. Attacker (unrelated party, own UTXOs) calls `Hinkal.transact` with a valid proof and `EmporiumStack.ops[0] = {endpoint: lendingPool, invokeWallet: false, callData: withdraw(asset, amount, to=attackerRecipient)}`.
5. Assert `asset.balanceOf(attackerRecipient) == amount` (theft succeeded) and `lendingPool.aTokenBalanceOf(Emporium) == 0`, while the victim's own Hinkal UTXO for the deposited amount was never spent/redeemed — demonstrating `asset_owner(position) != beneficiary_of_withdraw(attacker)`.
