### Title
Webhook shop-identity spoofing via unauthenticated `Shop-Domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` (used by `Utils::HmacValidator.validate` in `Registry.process`) signs only the raw request body. The `shop` value exposed to the app's webhook handler comes from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` HTTP header, which is never included in the HMAC-signed payload. This breaks the intended identity binding `hmac ⟹ (body, shop)`; in reality it only proves `hmac ⟹ body`.

### Finding Description
`Request#hmac` returns the decoded `X-Shopify-Hmac-Sha256` header value, and `Request#to_signable_string` returns just `@raw_body`: [2](#0-1) 

`Request#shop` reads the shop from a header, entirely independent of the signed content: [3](#0-2) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then forwards `request.shop` unchanged to the app's `handler.handle`: [1](#0-0) 

Because Shopify apps use a single `api_secret_key` shared across every installed shop/tenant, `HmacValidator.validate` in [4](#0-3)  only proves "some webhook body was signed by our app's secret for *some* shop" — it does not bind that signature to the specific `shop-domain` header value delivered alongside it. A merchant who legitimately owns Shop A (and therefore receives genuine, validly-signed webhooks addressed to Shop A) can capture one such request and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to Shop B. The HMAC still validates (it only covers the body), but `WebhookMetadata.shop` now reports Shop B to the app's handler.

This breaks the identity equality the app relies on: `shop_authenticated_by_hmac == shop_used_by_handler_to_update_tenant_state`. Any handler that uses `data.shop` from `WebhookMetadata` (built at [5](#0-4)  to look up/mutate per-tenant records (e.g., mark Shop B as uninstalled on a forged `app/uninstalled` replay, or apply Shop A's `orders/*` payload to Shop B's records) is exposed to cross-tenant data corruption/impersonation, driven entirely by an attacker-controlled, unauthenticated header.

### Impact Explanation
Cross-tenant access/impersonation: an attacker who controls one shop's genuine webhook traffic can impersonate a different shop against the app's webhook processing logic, since the shop identity is not bound to the cryptographic signature. This matches the "Critical - cross-tenant access" impact category, as it lets one merchant/tenant inject events that appear to originate from another tenant.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to control (or install) at least one shop that receives real webhooks from the app (trivial — any developer/merchant can install a public app), then replay a captured, validly-HMAC'd payload while altering only the `shop-domain` header — something entirely available to a normal unprivileged HTTP client hitting the app's webhook endpoint, no `api_secret_key` or credential compromise needed.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed payload used for verification, or otherwise cryptographically bind the `shop-domain` header to the HMAC before trusting it — e.g., have `Request#to_signable_string` incorporate the shop domain, or have `Registry.process`/`HmacValidator` additionally verify that the shop asserted in `WebhookMetadata` matches a shop the app expects to receive this specific webhook_id/topic for. At minimum, document to implementers of `WebhookHandler#handle` that `data.shop` is unauthenticated header data and must not be trusted as a sole tenant key without additional verification (e.g., cross-checking against a known installed-shop registry).

### Proof of Concept
1. App shop A (attacker-controlled) receives a legitimate webhook, e.g. `orders/create`, correctly signed with the app's `api_secret_key`: headers include `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, raw body `B`.
2. Attacker replays this exact request to the app's webhook endpoint, changing only the header `X-Shopify-Shop-Domain: shop-b.myshopify.com` (the victim tenant), leaving body `B` and the HMAC header untouched.
3. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`== B`) — validation succeeds because the body and HMAC are unmodified.
4. `WebhookMetadata.new(topic: ..., shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "shop-b.myshopify.com"`, and passed to the app's `WebhookHandler#handle`.
5. Any handler logic keyed off `data.shop` (e.g., updating Shop B's local order/customer records with Shop A's order payload, or marking Shop B uninstalled on a replayed `app/uninstalled`) now executes against the wrong tenant, purely due to attacker-controlled header content that was never covered by the HMAC.
