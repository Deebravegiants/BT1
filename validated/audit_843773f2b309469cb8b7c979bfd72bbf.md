### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header, yet `ShopifyAPI::Webhooks::Registry.process` treats `request.shop` (derived from that unauthenticated header) as the trusted tenant identity passed to the app's webhook handler after HMAC validation succeeds. This breaks the intended binding: `shop_used_by_handler == shop_covered_by_hmac`. In practice the HMAC only proves the body bytes are authentic; it proves nothing about which shop the body belongs to.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop` accessor instead reads directly from the caller-supplied `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC over the `Request` object (i.e., only over `@raw_body`) and then, once that passes, forwards `request.shop` to the registered handler as the authoritative tenant identifier: [3](#0-2) 

Because the `shop` header is never included in `to_signable_string`, `HmacValidator.validate` (which computes the signature purely from `to_signable_string`) cannot detect if the header has been altered: [4](#0-3) 

This mirrors the report's bug class: a field that is acted upon (the destination/tenant identity used by the handler) is not covered by the authenticating mechanism (here, HMAC) — analogous to the Solidity report's "destination address not validated/bound to the transfer."

### Impact Explanation
Any party capable of delivering an HTTP request to the app's webhook endpoint with a body+HMAC pair that was legitimately signed by Shopify for *some* shop that has installed the app (e.g., a merchant who installed the app themselves and captured their own valid webhook deliveries) can resend that exact body/HMAC pair while substituting an arbitrary `shop-domain` header value. `Registry.process` will pass HMAC validation (since only the body is checked) and hand the forged shop identity to the handler via `WebhookMetadata#shop`, confirmed by the registry's own test expectations that `data.shop` is trusted directly: [5](#0-4) 

If the host application uses `data.shop` to select which merchant's records to update/delete/redact (a documented, expected usage pattern for webhook handlers, especially for the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics), an attacker-controlled shop identity can cause the app to act on a victim shop's data using a payload the attacker fully controls — a cross-tenant identity confusion.

### Likelihood Explanation
Requires no possession of `api_secret_key`: it only requires access to legitimately-issued webhook deliveries for at least one shop that has installed the same app (which a merchant naturally receives) and the ability to send an HTTP request to the app's public webhook endpoint with a modified header. No cryptographic secret is broken; the gem's own signable-string construction simply never binds the shop header to the signature.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `webhook_id`/`api_version` if used for authorization decisions) in the HMAC-signable material, or, since Shopify's webhook signature is defined over the raw body only, require host applications to cross-validate `request.shop` against the shop that was expected/registered for that specific webhook subscription (e.g., matching against a known list of installed shops) before trusting it as the tenant key. At minimum, the library should document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier on its own.

### Proof of Concept
1. App-installing merchant A (attacker) receives a legitimate webhook from Shopify: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B` under the app's shared secret), header `x-shopify-shop-domain = "attacker-shop.myshopify.com"`.
2. Attacker resends an HTTP request to the app's webhook endpoint with the same `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain = "victim-shop.myshopify.com"`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `B` (per `to_signable_string`) — validation succeeds.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the body content and signature were never associated with that shop.
