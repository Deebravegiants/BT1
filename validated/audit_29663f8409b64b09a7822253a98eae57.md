## Analog Finding

### Title
Unauthenticated LOOP plugin discovery, metrics, and pprof endpoints - (File: core/web/router.go)

### Summary
Chainlink's node webserver exposes LOOP (Local Out Of Process) plugin discovery, metrics, and pprof profiling endpoints without any authentication middleware, mirroring the CWE-306 (Missing Authentication for Critical Function) pattern described in the Nautobot SSoT advisory, where a Django view lacked authentication and exposed configuration data to any unauthenticated caller.

### Finding Description
`NewRouter` builds the top-level `api` route group with only rate-limiting and session middleware — no authentication: [1](#0-0) 

`loopRoutes` is registered directly on this unauthenticated `api` group: [2](#0-1) 

```go
func loopRoutes(app chainlink.Application, r *gin.RouterGroup) {
	loopRegistry := NewLoopRegistryServer(app)
	r.GET("/discovery", ginHandlerFromHTTP(loopRegistry.discoveryHandler))
	r.GET("/plugins/:name/metrics", loopRegistry.pluginMetricHandler)
	r.GET("/plugins/:name/debug/pprof/*profile", loopRegistry.pluginPPROFHandler)
	r.POST("/plugins/:name/debug/pprof/symbol", loopRegistry.pluginPPROFPOSTSymbolHandler)
}
```

This is in contrast to every sensitive route elsewhere in the router, which is explicitly wrapped in `auth.Authenticate(...)`:
- `/debug/vars` (expvar) is gated behind session auth: [3](#0-2) 
- the core node's own `/debug/pprof/*` handlers (`metricRoutes`) are only mounted inside the authenticated `authv2` group: [4](#0-3) 

By comparison, `loopRoutes`' plugin-specific `/discovery`, `/plugins/:name/metrics`, and `/plugins/:name/debug/pprof/*` are reachable by any unauthenticated network client that can hit the Chainlink node's HTTP port, exactly the same class of bug as the Nautobot advisory (an unauthenticated Django view leaking configuration info): a generic handler with no auth check mounted on a public route.

### Impact Explanation
An unauthenticated attacker who can reach the node's HTTP port (`HTTPPort`, default 6688, `ListenIP = '0.0.0.0'` by default per [5](#0-4) ) can:
- Enumerate registered LOOP plugins and their configuration via `/discovery`.
- Pull Prometheus-style metrics per plugin via `/plugins/:name/metrics`.
- Pull full Go pprof profiles (heap, goroutine, cmdline, trace) for individual LOOP plugin processes via `/plugins/:name/debug/pprof/*profile`.

Unlike the original ServiceNow bug (which discloses only a low-value hostname string), pprof `heap`/`goroutine` dumps can leak in-memory secrets, private keys, and other sensitive runtime state of the plugin process, making this a materially higher-impact analog of the same "unauthenticated config/diagnostic endpoint" bug class (CWE-306).

### Likelihood Explanation
High likelihood: these routes require no credentials, tokens, or session cookies — only network reachability to the node's web server port, which is often exposed for legitimate API/UI use.

### Recommendation
Move `loopRoutes(app, api)` under an authenticated group (e.g., mirror `metricRoutes`/`debugRoutes` and require `auth.Authenticate(...)` with an appropriate role, such as admin) before registering `/discovery`, `/plugins/:name/metrics`, and the pprof/symbol handlers.

### Proof of Concept
Against a running Chainlink node with default `WebServer` config, an unauthenticated `curl`:
```
curl http://<node-ip>:6688/discovery
curl http://<node-ip>:6688/plugins/<plugin-name>/metrics
curl http://<node-ip>:6688/plugins/<plugin-name>/debug/pprof/heap
```
returns plugin discovery data, metrics, and a full heap profile with no `Authorization`/session cookie required, because `loopRoutes` is mounted on the base unauthenticated `api` group as shown in `core/web/router.go` lines 87-91 and 230-236.

**Note on verification limits:** I was unable to fully inspect the contents of `core/web/loop_registry.go` (the implementation of `discoveryHandler`/`pluginMetricHandler`/`pluginPPROFHandler`) due to index size limits, so the exact fields returned by `/discovery` and the precise sensitivity of `pluginMetricHandler`'s output are not fully confirmed from the indexed content — the authentication-bypass finding at the router level, however, is directly supported by the cited code.
