### Title
Webhook `shop` (tenant) identity is taken from an HMAC-unauthenticated header, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC signature verified by `Utils::HmacValidator` only proves the *body* was produced with the app's `api_secret_key`. The `shop-domain` header, which becomes the `shop` value passed to the app's webhook handler as the tenant identifier, is never part of the signed content. A merchant who legitimately has the app installed on their own store (an unprivileged actor with respect to other tenants) can replay a genuinely-signed webhook body/HMAC pair they receive for their own shop, but with the `X-Shopify-Shop-Domain` header rewritten to a victim shop, and the library will accept it as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

Specifically: [2](#0-1) 

`to_signable_string` returns only `@raw_body`, excluding the `shop-domain` header entirely from the signable content. `HmacValidator.validate` computes the HMAC purely over `to_signable_string` and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` trusts the HMAC result as proof of authenticity for the entire request, then forwards `request.shop` (i.e., the unauthenticated header) directly to the app's handler as the tenant identity: [4](#0-3) 

Shopify signs webhooks using the app's `client_secret` (`api_secret_key`), which is identical across every shop that has the app installed — it is not shop-specific. Consequently, a merchant who has legitimately installed the app on their own store can capture a genuine `(raw_body, hmac-sha256)` pair delivered to the app's webhook endpoint (e.g., by triggering an event in their own store and observing/proxying the delivery to the app's public webhook URL), then resend the identical body and HMAC header to the same endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop's domain. Because that header is not covered by the signature, `HmacValidator.validate` still returns `true`, and `Registry.process` invokes the app's handler with `shop: <victim-shop>` and attacker-controlled `body`.

This breaks the identity binding: **shop cryptographically proven by Shopify's signature == shop used to scope the webhook data (`request.shop` / `data.shop`)**. The library only proves "this body was HMAC-signed by an entity holding the app's secret" but silently equates that with "this body pertains to the shop named in this header," which is a distinct, unauthenticated claim.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to identify the tenant record to update (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be induced to apply attacker-supplied webhook payloads (order data, product data, GDPR-topic events, etc.) against a victim shop's tenant record, since the shop attribution is unauthenticated. This is a cross-tenant data-integrity/access issue reachable by any unprivileged actor who merely has the app installed on their own shop — no access token, client secret, or privileged account is required.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop (a normal, unprivileged install any Shopify merchant can perform for public apps), (2) triggering an event to receive one genuinely-signed webhook to the app's known webhook endpoint, and (3) replaying that request with the shop-domain header modified. No secrets, no elevated permissions, and no timing race are needed, making this straightforward for a motivated attacker who has app access.

### Recommendation
Bind the shop identity to the signed content, or otherwise independently authenticate the `shop-domain` header before trusting it as the tenant identifier. Concretely:
- Reconstruct the HMAC input to include the shop domain (and/or webhook id) alongside the body, mirroring the pattern already used for `Auth::Oauth::AuthQuery`, which includes `shop` in its `to_signable_string`.
- Alternatively, require/encourage app authors to cross-check `request.shop` against a shop already known/authorized for this app instance (e.g., a previously stored, OAuth-derived session) before processing the payload, and document this requirement prominently since the header is unauthenticated by design in the current implementation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g., `orders/create`) in their own shop; Shopify delivers to the app's public webhook endpoint a request with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` (captured via a proxy in front of the app's endpoint, or by controlling the reachable network path to it).
3. Attacker resends the exact same body `B` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against the signature and passes.
5. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` and processes it as if Shopify itself reported this event for the victim shop. [4](#0-3) [2](#0-1)
