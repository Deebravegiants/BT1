### Title
Webhook HMAC Validates Only the Body, Not the Shop Header — Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a specific shop once `Utils::HmacValidator.validate(request)` passes, but the HMAC only ever covers the raw request body — never the `shop` value that is subsequently used as the tenant identity passed to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature via `verifiable_query.to_signable_string` and compares it against `verifiable_query.hmac` [3](#0-2) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [1](#0-0) , and `hmac` is decoded from the `hmac-sha256` header [4](#0-3) . The `shop` accessor, however, is read independently from the `shop-domain` header and plays no role in the signature computation [2](#0-1) .

`Registry.process` validates only the HMAC (which covers the body) and then immediately builds `WebhookMetadata` using `request.shop` as the tenant identity passed to the app-supplied handler [5](#0-4) . There is no check anywhere in this path that binds `shop` to the value that was actually signed — the equality the code implicitly relies on, `hmac_valid(body) == shop_is_authentic`, does not hold; the correct equality would need to be `hmac_valid(body || shop)`.

Because the HMAC secret (`api_secret_key`) is shared by the app across every shop that installs it, any unprivileged user who installs the app on their own store (a normal, unprivileged action requiring no special access) can trigger a legitimate webhook and capture a valid `(raw_body, hmac)` pair signed with the app's secret. That pair remains valid for the app's webhook endpoint regardless of which `shop-domain` header accompanies it, since the header is never part of the signed content.

### Impact Explanation
This breaks the tenant/identity binding "shop authenticated ⇔ shop used as session key" called out as one of the analog conditions: the HMAC only proves *some* legitimate shop of the app produced the body, not *which* shop. An attacker can submit that captured `(body, hmac)` to the app's public webhook callback URL with the `shop-domain` header changed to a victim shop. `Registry.process` will pass the HMAC check and hand the handler a `WebhookMetadata` object claiming the (attacker-chosen) victim `shop`, together with attacker-controlled body content. Any host application that uses `data.shop` from `WebhookMetadata` to look up/update per-tenant state (the intended and documented use, see `docs/usage/webhooks.md`) will attribute attacker-controlled data to a shop the attacker does not own — a cross-tenant data integrity/confusion vulnerability reachable purely through this library's own verification logic.

### Likelihood Explanation
No credentials, tokens, or `api_secret_key` knowledge are required. All the attacker needs is: (1) the ability to install the app for free on their own store (or use any store where a webhook already fires) to get one valid `(raw_body, hmac)` pair, and (2) the ability to send an HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — both are unprivileged-internet-user actions available to anyone who can interact with the app's install flow and its public webhook route.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the signed material, or otherwise re-derive/verify the shop identity from a source that is cryptographically bound to the same secret used for the HMAC, before trusting `request.shop`/`WebhookMetadata#shop` as a tenant key. At minimum, document that `shop` from `Webhooks::Request` is unauthenticated and must not be used as a trust boundary, or cross-check it against an authenticated session/shop record before use.

### Proof of Concept
1. Install the target app on an attacker-owned development store; trigger any subscribed webhook topic (e.g. `orders/create`) to receive a legitimate webhook request with headers `x-shopify-hmac-sha256: <hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`.
2. Confirm `HmacValidator.validate` accepts `(B, hmac)` regardless of the `shop-domain` header, since `to_signable_string` returns only `B` [1](#0-0) .
3. Replay the captured request to the app's webhook endpoint, replacing `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` accepts the request (`Utils::HmacValidator.validate(request)` passes because only `B`/`hmac` are checked) [5](#0-4)  and invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker JSON>, ...)`, causing the host app to process attacker data under the victim's tenant identity.
