### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body bytes, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. [1](#0-0)  `Utils::HmacValidator.validate` only verifies the HMAC over that signable string (the body), never over the headers. [2](#0-1)  `Webhooks::Registry.process` then trusts `request.shop` (and `request.topic`) to dispatch the payload to a handler as the tenant identity, after only checking that the body's HMAC is valid. [3](#0-2)  This is the same class of bug as the external report: a field that is *acted on* (here, the shop that owns the webhook data) is not *covered* by the cryptographic binding (the HMAC), so the equality "HMAC-authenticated shop == shop used by the handler" does not actually hold.

### Finding Description
Shopify webhooks are authenticated by computing `HMAC-SHA256(client_secret, raw_body)` and sending it in the `X-Shopify-Hmac-Sha256` header; the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version` headers are plain, unsigned metadata.

In this gem:
- `Request#to_signable_string` returns only `@raw_body`. [4](#0-3) 
- `Request#shop`, `#topic`, `#api_version`, `#webhook_id` are pulled straight from headers with no cryptographic tie to the body or to the HMAC. [5](#0-4) 
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and `Context.api_secret_key`, and never touches shop/topic headers. [6](#0-5) 
- `Registry.process` raises only if the HMAC over the body is invalid, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic`, and hands it to the registered handler. [7](#0-6) 

Because any Shopify shop that installs the app is a valid HMAC source (the HMAC is computed with the single app-wide `client_secret`, not a per-shop key), an unprivileged attacker who controls their own installed shop can:
1. Trigger any webhook topic on their own shop to obtain a body + a **valid** HMAC signature (computed by Shopify with the app's real secret).
2. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) with a victim shop's domain / a different topic.
3. `HmacValidator.validate` still succeeds because it only checks the body against the secret — a check that has nothing to do with which shop or topic is claimed in the headers.
4. The application's webhook handler receives `WebhookMetadata` with `shop:` set to the victim domain and processes the attacker-supplied body as if it came from the victim's store.

This breaks the intended identity binding "the shop and topic that produced this HMAC == the shop and topic acted upon," exactly mirroring the report's pattern of "a field acted on but not covered by the HMAC."

### Impact Explanation
This allows cross-tenant data injection/confusion: an attacker-controlled shop can make the application believe arbitrary webhook data (orders, product updates, GDPR-style mandatory webhooks, app-uninstall notifications, etc.) originated from a different, victim shop, because only the request body is authenticated while the shop attribution is taken from an unauthenticated header. Depending on how the host application persists/keys data by `shop` from `WebhookMetadata`, this can lead to cross-tenant data corruption, false uninstall/GDPR triggers against a victim shop, or planting attacker-controlled content into another tenant's records — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires the attacker to run their own Shopify store/dev shop that installs the target app (no special privileges) and to be able to trigger any webhook topic they want (many are triggered by ordinary shop-owner actions, e.g. `products/update`, `orders/create`). No access token, `client_secret`, or victim credentials are needed — only the ability to replay HTTP requests with modified headers.

### Recommendation
Bind the shop (and ideally topic) identity into the HMAC verification step rather than trusting header data merely because the body's HMAC is valid:
- Extend `VerifiableQuery`/`Request#to_signable_string` (or add a secondary check) so that the shop domain the handler will use is cryptographically tied to the verified request — e.g., cross-check `request.shop` against a shop that the application already has an active, verified session/installation for, before dispatching to the handler.
- At minimum, document/enforce in `Registry.process` that `request.shop` must be validated against known installed shops before being trusted, since the HMAC alone does not authenticate it.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com", which has installed the app.
# Shopify sends a genuine webhook to the app for that shop:
#   body = '{"id":1,"note":"hi"}'
#   X-Shopify-Hmac-Sha256 = HMAC-SHA256(client_secret, body)  <-- valid, computed by Shopify
#   X-Shopify-Shop-Domain = attacker-shop.myshopify.com
#   X-Shopify-Topic       = products/update

# Attacker captures (body, hmac) and replays to the app's webhook endpoint,
# only changing the shop header to a victim shop:
headers = {
  "x-shopify-topic"        => "products/update",
  "x-shopify-hmac-sha256"  => captured_valid_hmac,   # unchanged, still valid for `body`
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # spoofed
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)

# HmacValidator.validate(request) => true, because it only checks `body` against the secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "products/update",
#                                              shop: "victim-shop.myshopify.com",
#                                              body: parsed_body, ...))
# The application now processes attacker-controlled data as belonging to victim-shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
