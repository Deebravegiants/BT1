### Title
Webhook identity fields (`shop-domain`, `topic`) are not covered by the HMAC signature, allowing tenant/topic spoofing on an otherwise "verified" webhook - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from separate, unauthenticated HTTP headers. `Webhooks::Registry.process` treats HMAC validation as proof that the *entire request*, including the shop identity used for tenant attribution, is genuine, when in fact only the body bytes are covered by the signature.

### Finding Description
`Request#to_signable_string` binds the HMAC exclusively to `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to that signature: [2](#0-1) 

`HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity for dispatch, forwarding it unchanged into the handler-visible `WebhookMetadata` after the HMAC check passes: [4](#0-3) 

The equality the code implicitly assumes is:
`bytes verified by HMAC == identity (shop, topic) the handler acts on`

but the actual code only guarantees:
`bytes verified by HMAC == @raw_body`

`shop`/`topic` are parsed from bytes (headers) that were never part of the signable string, so they can diverge from the signed body without failing validation.

### Impact Explanation
Any handler that relies on `WebhookMetadata#shop` (or `#topic`) for tenant attribution — e.g., to decide which merchant's record in the app's own database to update/delete based on webhook data — can be made to act on the wrong tenant's data if the `shopify-shop-domain` (or `shopify-topic`) header is not the one that was actually signed together with the body. This is a cross-tenant identity-binding break inside the gem's own webhook-verification contract: the gem advertises `HmacValidator.validate(request)` as authenticating "the webhook request," but it only authenticates the body, silently leaving the shop/topic headers unauthenticated.

### Likelihood Explanation
Exploitation requires being able to produce or forward a request in which the raw body and its valid HMAC belong to one shop while the `shop-domain`/`topic` headers assert another. Under standard Shopify → app delivery over TLS, this is not trivially forgeable by a network-external attacker with zero position, since it would need either possession of `api_secret_key` to mint a fresh HMAC or the ability to alter in-flight headers. Given the constraints of this review (excluding TLS interception and secret possession), likelihood is best characterized as low without an additional capability, but the root-cause binding defect is real and independent of transport assumptions the gem itself is documented to make no claim about.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api_version`, `webhook_id`) in the signable string, or otherwise explicitly document/enforce that consumers must not treat `request.shop`/`request.topic` as authenticated unless obtained via a channel where header integrity is guaranteed (e.g., re-deriving shop from a separately verified session/token rather than the raw header) before using it as a tenant key.

### Proof of Concept
1. Compute `hmac = HMAC-SHA256(api_secret_key, body)` for a chosen `body` (e.g., `"{}"`).
2. Send a POST to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256: base64(hmac)`
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (any value — not bound to the signature)
   - `x-shopify-topic: shop/redact`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `body` against `hmac`.
4. `Registry.process(request)` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "shop/redact", body: ..., ...)`, i.e., the handler receives a `shop` value that was never covered by the signature check that just "passed". [4](#0-3)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
