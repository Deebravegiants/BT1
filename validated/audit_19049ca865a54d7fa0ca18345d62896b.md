## Title
Tron IntentGatewayV2 lacks the relayer allowlist gate on `onAccept`/`onGetResponse`, allowing a forged/compromised relayer report to authorize escrow withdrawal actions - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The NGFS exploit is a classic bad-access-control bug class: privileged, state-mutating functions (`delegateCallReserves`, `setProxySync`, `reserveMultiSync`) were callable by anyone because the contract failed to gate them to a trusted party, letting the attacker manipulate reserves at will. The strongest reachable analog in this Hyperbridge codebase is the Tron fork of `IntentGatewayV2`, which never received the relayer-allowlist hardening that was deliberately added to the canonical EVM `ExtrinsicIntents`/`IntentGatewayV2` implementations.

### Finding Description
The mainline EVM intent gateway (`evm/src/apps/intentsv2/ExtrinsicIntents.sol`) gates every `onAccept`/`onGetResponse` delivery with `_checkRelayer(incoming.relayer)` immediately after the `onlyHost` modifier, before any request body is even decoded: [1](#0-0) 

This was a deliberate hardening documented across multiple decision/changelog notes, closing the gap where "a delivery from anyone but the authorised relayer never decodes the body ... and leaves no receipt": [2](#0-1) 

The Tron variant of the same contract, however, has no `_checkRelayer`/relayer allowlist at all. Its `onAccept` goes straight from `onlyHost` to decoding the `RequestKind` and calling `authenticate`/`withdraw`: [3](#0-2) 

Per the documented threat model, the relayer gate exists precisely because "the address checked ... is only as trustworthy as the contract [handler/host] that reports it," and the host's handler/manager can in principle be swapped by a forged `SetHostParam` message — the exact scenario the relayer allowlist is meant to catch as a defense-in-depth layer against a compromised delivery path: [4](#0-3) 

Without this gate, the Tron `IntentGatewayV2` has strictly weaker access control than its EVM counterpart on the exact same reachable surface (escrow redemption/refund, governance-style actions such as `UpdateParams`, `SweepDust`, `NewDeployment`), mirroring NGFS's pattern of a privileged state-mutating action left reachable without the intended authorization check.

### Impact Explanation
If the relayer-allowlist protection is bypassed or absent, an attacker who can get a message accepted through a compromised or forged delivery path (e.g. handler swap, as separately guarded elsewhere in the same codebase) gains an unauthenticated route to `withdraw` escrowed funds, `SweepDust` (draining protocol dust to an arbitrary beneficiary), or mutate `_params`/`_instances` — concrete theft or permanent freezing of escrowed intent funds on Tron deployments.

### Likelihood Explanation
Medium: exploitation still requires defeating the `onlyHost` + proof/authentication checks for the underlying message delivery (this is not a standalone unauthenticated entry point like NGFS's raw function calls). However, it removes a layer of defense that the rest of the codebase treats as load-bearing (the relayer gate is documented as covering exactly the compromised-handler/forged-relayer scenario), so any weakness elsewhere in the Tron host/handler chain is one step away from being catastrophic instead of contained.

### Recommendation
Port the `_relayer` / `setRelayer` / `_checkRelayer` allowlist mechanism from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `IntentsBase.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, gating `onAccept` and `onGetResponse` on the authorised relayer before decoding `RequestKind`, matching the canonical implementation.

### Proof of Concept
Not directly executable from the index alone — reaching this requires first compromising or forging the host's handler/relayer delivery path on the Tron deployment (a scenario documented and tested against on the EVM side in `evm/tests/foundry/HostManagerTest.sol::testForgedHandlerSwapIsRefused`); no equivalent test exists for the Tron contract, and I could not confirm from the index whether Tron's `HostManager`/handler carries the same protections. This is a structural code-parity gap, not a demonstrated standalone exploit — flagging it as a genuine but conditional bad-access-control regression relative to the hardened EVM implementation.

     * @notice Executes an incoming post request.
     * @dev This function is called when an incoming post request is accepted.
     * It is only accessible by the host.
     * @param incoming The incoming post request data.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
