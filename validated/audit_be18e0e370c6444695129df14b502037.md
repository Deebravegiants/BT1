Audit Report

## Title
JWT replay-cache check-and-record race allows concurrent replay of a single-use HTTP trigger token - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

## Summary
`WorkflowMetadataHandler.Authorize` enforces single-use JWTs by checking `jwtReplayCache.isReplay` before proceeding and calling `jwtReplayCache.recordUsage` only after signer/authorized-key checks succeed. These are two independent lock sections (`RLock`/`RUnlock` for the check, separate `Lock`/`Unlock` for the record) rather than one atomic check-and-set, so two concurrent requests bearing the same JWT `jti` can both pass `isReplay` before either calls `recordUsage`.

## Finding Description
`Authorize` verifies the JWT signature, then calls `h.jwtCache.isReplay(claims.ID)` [1](#0-0)  and only later, after the authorized-key membership check, calls `h.jwtCache.recordUsage(claims.ID)` [2](#0-1) . The cache implementation confirms these are separate critical sections: `isReplay` takes `RLock`/`RUnlock` and returns, while `recordUsage` independently takes `Lock`/`Unlock` to insert [3](#0-2) . There is no single lock spanning "check membership, then insert," so this is a genuine time-of-check-to-time-of-use (TOCTOU) gap: two goroutines racing through `Authorize` with an identical `jti` can both observe `isReplay == false`, both pass the authorized-key check, and both call `recordUsage`, defeating the single-use guarantee.

## Impact Explanation
This bypasses the intended anti-replay control on the HTTP trigger authorization path, allowing a caller holding one valid signed JWT to potentially cause more than one workflow-execution trigger to be accepted concurrently. This maps to an in-scope impact category (unauthorized job/workflow trigger dispatch via gateway request replay).

## Likelihood Explanation
The race window is real and requires only ordinary concurrent HTTP requests from an unprivileged holder of a valid JWT—no privileged access, credentials leak, or host access needed. The window is bounded (spans JWT verification plus a map lookup), but is fully within attacker control via request timing/parallelism, and is repeatable per token until expiry.

## Recommendation
Merge `isReplay` and `recordUsage` into a single atomic check-and-insert method that holds the cache's write lock (`Lock()`) for the entire check-then-insert sequence, and invoke it immediately after JWT signature verification in `Authorize`, before any downstream authorized-key lookups.

## Proof of Concept
1. Obtain one valid signed JWT (`jti = X`) for a registered workflow's HTTP trigger.
2. Fire two concurrent HTTP requests to the gateway trigger endpoint carrying the identical JWT (e.g., via goroutines with a `sync.WaitGroup`).
3. Both requests reach `WorkflowMetadataHandler.Authorize` concurrently and both call `isReplay(claims.ID)` before either calls `recordUsage(claims.ID)`, since these are non-atomic, separately-locked operations as shown in the cited code.
4. Both requests pass authorization and both trigger workflow executions via `HandleUserTriggerRequest`, from a single JWT intended for one-time use.

A Go unit test that mocks/delays between `isReplay` and `recordUsage` (or directly exercises `jwtReplayCache` with concurrent goroutines) would deterministically demonstrate the race.

	}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
