### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies its HMAC signature over the raw request body only, while the `shop` attribute that the app relies on for tenant identification is read from the `shopify-shop-domain` header, which is never included in the signed content. This breaks the identity binding `shop_authenticated == shop_used_by_handler`, letting an unprivileged holder of one shop's valid webhook signature relabel it as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Request#shop` is read independently from an HTTP header that is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` and, once it passes, forwards `request.shop` directly into `WebhookMetadata` without any further check that the shop matches the content that was actually signed: [3](#0-2) 

`Utils::HmacValidator.validate` / `validate_signature` compute the signature strictly from `to_signable_string`, i.e. the body, using the app's `client_secret`-derived `Context.api_secret_key`: [4](#0-3) 

Because the same app-level secret (`api_secret_key`) is shared across every shop that installs the app, any merchant who installs the app receives their own legitimately-signed webhook deliveries (valid `hmac-sha256` for a body they can influence, e.g. via product/order titles). Nothing in `Request`, `HmacValidator`, or `Registry.process` ties the `hmac` to the `shop` header. An attacker who controls their own shop can therefore take one of their own valid `(body, hmac)` pairs and replay it to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at `shop`), and `WebhookMetadata.shop` passed to the app's handler reports the victim's domain while `body` is attacker-controlled content. [5](#0-4) 

This mirrors the report's bug class directly: a field that is *acted on* (the `shop` used to route/identify the tenant in the handler) is not covered by the cryptographic binding (the HMAC), so the binding `shop_signed == shop_used` silently fails.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select which tenant's data/session to update (as shown in the gem's own documented usage example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into writing or acting on data under a different, unauthorized shop's identity — a cross-tenant access issue, since the "authentication" for the webhook (the HMAC) is not actually bound to the shop that the app believes sent it.

### Likelihood Explanation
Requires only that the attacker themselves install the target app on their own shop (an ordinary, unprivileged action for any merchant/developer), which yields legitimately-signed webhook bodies. No access to `api_secret_key`, tokens, or victim credentials is needed. The header spoof itself is a trivial HTTP header rewrite performed against the app's own public webhook endpoint. Whether this is actually exploitable end-to-end depends on the host application's specific use of `data.shop` (out of this gem's control), but the gem provides no safeguard at all.

### Recommendation
- Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified content, or independently verify that the shop domain in the header corresponds to a shop with an active, registered subscription for that specific webhook/topic before trusting it.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a tenant-identity source without additional verification (e.g., cross-checking against a shop that has confirmed OAuth/session state).
- Longer term, review every place where header- or query-string-derived identity fields are consumed without being part of a signed payload, consistent with the report's general recommendation to audit trust boundaries around values that look authenticated but aren't cryptographically bound.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's `client_secret`.
2. Attacker crafts/updates a resource on their own shop so that the webhook body contains attacker-chosen values (e.g., in `products/update`).
3. Shopify sends a webhook to the app with a valid `x-shopify-hmac-sha256` for that body and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
4. Attacker replays this exact request to the app's webhook endpoint but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks the (unchanged) body against the (unchanged) HMAC: [6](#0-5) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though nothing from `victim-shop` was involved.
