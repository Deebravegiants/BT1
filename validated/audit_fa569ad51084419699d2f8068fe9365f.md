### Title
Webhook `shop-domain` header (and topic/webhook-id/api-version) is not covered by the HMAC signature, enabling cross-tenant shop spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The Unlock Protocol report describes a value derived from an unauthenticated/unbound input (`tx.gasprice`) being trusted for a critical calculation. The analogous flaw here is that `ShopifyAPI::Webhooks::Request` signs only the raw HTTP body with HMAC, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by the handler are taken from HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` verifies the HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `request.to_signable_string` (the body only) — the `shop` header is never part of what's authenticated: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the signature purely over `verifiable_query.to_signable_string`: [4](#0-3) 

Because Shopify apps use a single `api_secret_key` shared across every shop that installs the app (there is no per-shop signing secret), an HMAC computed for a webhook body from Shop A is *also valid* for the exact same body claimed to originate from Shop B. The identity binding that should hold — "the `shop` value the handler trusts equals the `shop` value the HMAC actually authenticates" — does not hold, because `shop` is outside the HMAC's signed content entirely.

An unprivileged user who controls their own shop (any developer can install their own free/dev store and subscribe the target app's webhooks against it) can:
1. Trigger a webhook event on their own shop, capturing a legitimate `(raw_body, hmac)` pair signed with the app's shared secret.
2. Replay that exact `raw_body` and `hmac` directly to the app's public webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header (and optionally `topic`/`webhook-id`) with a victim shop's domain.
3. `HmacValidator.validate` passes because the signature only covers `raw_body`, and `Registry.process` dispatches to the handler with `shop: request.shop` set to the attacker-chosen victim domain: [5](#0-4) 

Handler code that trusts `WebhookMetadata#shop` to look up per-tenant records, credentials, or session data will process the spoofed event as if it came from the victim shop, when in fact the HMAC only proved the *body* was signed with the app's secret — not that it originated for that particular shop.

### Impact Explanation
This breaks the tenant-authentication binding `hmac_authenticated_content == content_the_handler_trusts_as_identifying_the_shop`. A malicious app-installer (any unprivileged internet user who can install the target Shopify app on their own store) can spoof webhook events as belonging to any other shop, leading to cross-tenant data confusion/corruption in the host application (e.g., updating the wrong shop's records, triggering `shop/redact`-adjacent business logic, or poisoning per-shop caches/state) — a cross-tenant access vector.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged credentials are required beyond installing the app on an attacker-controlled shop (a normal, permitted, unprivileged action), and forging the HTTP headers on a direct POST to the app's public webhook endpoint requires no cryptographic secret since `shop` is unauthenticated data.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed content (i.e., have `Request#to_signable_string` compose a canonical string of body + these headers), so that verifying the signature also verifies which shop and topic the payload is bound to, mirroring the OAuth `AuthQuery#to_signable_string` pattern that includes `shop` in its signed fields: [6](#0-5) .

### Proof of Concept
1. Attacker creates a free/dev Shopify store and installs the target app, subscribing to a webhook topic (e.g., `orders/create`).
2. Attacker triggers the event on their own store and captures the raw POST body plus `X-Shopify-Hmac-Sha256` header sent by Shopify (valid because signed with the app's shared `api_secret_key`).
3. Attacker sends a new POST directly to the app's public webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against the shared secret: [7](#0-6) .
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled data as if it came from the victim tenant.
