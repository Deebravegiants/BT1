### Title
Cache-key collision in `getCachedStorageDepositValue` mixes up storage-deposit data across different (token, account) pairs - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating `contractId` and `accountId` with no delimiter [1](#0-0) . Because NEAR account/contract IDs are variable-length strings drawn from the same character set (letters, digits, `.`, `-`, `_`), two different `(contractId, accountId)` pairs can concatenate to the identical string, causing the cache to return the wrong `[minStorageBalance, userStorageBalance]` tuple for an unrelated request.

### Finding Description
`estimateWithdrawalFee` calls `getCachedStorageDepositValue(tokenAccountId, destinationAddress)` to decide whether a withdrawal needs an attached NEAR storage deposit [2](#0-1) . The cache key is `` `${contractId}${accountId}` `` [3](#0-2) . This is the DirectBridge equivalent of the Tomcat bug's "mix-up of responses for requests from different users": a shared, keyed cache silently returns data computed for request A to caller B once two logically distinct requests collide on the same key string.

Example collision: request 1 has `contractId = "usdt.tkn"`, `accountId = "near.alice.near"` → key `"usdt.tknnear.alice.near"`. Request 2 has `contractId = "usdt.tknnear"`, `accountId = "alice.near"` → same key `"usdt.tknnear.alice.near"`. Since a service (integrator backend) typically reuses one `DirectBridge`/`IntentsSDK` instance to serve many concurrent users' withdrawal-fee estimations, an attacker who controls `assetId`/`destinationAddress` for their own withdrawal request can pick strings that collide with a victim's in-flight or previously cached `(contractId, accountId)` key, poisoning what the victim's estimate reads back.

Only "successful" results (`result[1] >= result[0]`, i.e., balance already sufficient) are cached [4](#0-3) , so a colliding cache hit always tells the caller "no additional storage deposit needed" (`minStorageBalance <= userStorageBalance` branch, fee = 0) [5](#0-4) , even though the real target account has insufficient storage balance.

That zero fee flows directly into `createWithdrawIntentPrimitive`, which only sets `storage_deposit` on the `ft_withdraw` intent when `storageDeposit > 0n`; a colliding zero fee omits the attached deposit entirely [6](#0-5) . On-chain, the NEP-141 `ft_transfer`/`ft_withdraw` will then fail for an account lacking registered storage, leaving the withdrawal intent published but the withdrawal stuck/unfulfilled until manual intervention (re-registration and resubmission).

### Impact Explanation
This breaks the equality "the storage-deposit values used for fee calculation belong to the `(token, destination account)` pair actually being withdrawn." A withdrawal that genuinely needs a storage deposit can be miscalculated as needing none, causing the on-chain transfer to revert/fail after intent signing and submission — a withdrawal stuck until manual intervention, matching the High-impact category ("a withdrawal stuck until manual intervention").

### Likelihood Explanation
Exploitability depends on (a) the SDK/bridge instance being shared across concurrent requests from different callers (common in a backend service using one `IntentsSDK`/`DirectBridge` instance), and (b) an attacker being able to choose `assetId` (hence `contractId`) and `destinationAddress` for their own request to craft a string that collides with a legitimate, cached/`in-flight` victim key. Because NEAR IDs share an unrestricted alphabet and no separator is used, constructing a colliding pair is straightforward once a victim's contractId/accountId are known or guessable (e.g., popular token contract IDs), but requires precise knowledge of the victim's exact strings. This makes it a real but moderate-likelihood defect rather than trivially exploitable against an arbitrary unknown victim.

### Recommendation
Use a delimiter that cannot appear ambiguously, or a structured key (e.g., `` `${contractId}\u0000${accountId}` ``, or a `Map<string, Map<string, ...>>` keyed independently), to make the two components unambiguous and eliminate collision potential.

### Proof of Concept
1. Instantiate one `DirectBridge` and call `estimateWithdrawalFee` concurrently for two distinct users:
   - Request A: `assetId` → `contractId = "usdt.tkn"`, `destinationAddress = "near.alice.near"` (account without sufficient storage balance; would normally require a deposit fee).
   - Request B: crafted `assetId` → `contractId = "usdt.tknnear"`, `destinationAddress = "alice.near"` (an account that already has sufficient storage balance, so it caches a "sufficient" result).
2. Both produce the same cache key `"usdt.tknnear.alice.near"` in `getCachedStorageDepositValue` [3](#0-2) .
3. If Request B's result is cached first, Request A's `estimateWithdrawalFee` call reads the cached (wrong) tuple and returns `storageDepositFee: 0n` even though `near.alice.near` truly lacks sufficient storage balance.
4. The resulting `ft_withdraw` intent omits `storage_deposit` [7](#0-6) , and the on-chain transfer to `near.alice.near` fails/stalls after the intent is signed and submitted.
