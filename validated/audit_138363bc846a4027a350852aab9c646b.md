### Title
Webhook `shop` identity is unauthenticated — HMAC covers only the raw body, not the `shopify-shop-domain` header used for tenant routing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity via `Utils::HmacValidator.validate(request)` [1](#0-0) , but the HMAC signature only ever covers `request.to_signable_string`, which is hard-coded to the raw JSON body [2](#0-1) . The `shop` value that is handed to the app's webhook handler and used as the tenant identity is taken from the `shopify-shop-domain` / `x-shopify-shop-domain` header [3](#0-2)  — a field that is never part of the signed bytes.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes-that-determine-shop)`. In reality the gem verifies `hmac == HMAC(secret, raw_body)` while `shop` is parsed from an unauthenticated header [4](#0-3) . `VerifiableQuery` only requires `hmac` and `to_signable_string` [5](#0-4) , and `HmacValidator.validate_signature` recomputes the HMAC purely from `to_signable_string` [6](#0-5) . Because `to_signable_string` for `Request` is just `@raw_body`, any header (including `shopify-shop-domain`) can be swapped for a different value while the HMAC computed over the same body still validates. `Registry.process` then passes this attacker-controllable `shop` straight into `WebhookMetadata` delivered to the handler [7](#0-6) , so the app-level handler (which typically looks up per-shop credentials/state keyed by `shop`) is fed a value that was never bound to the signature.

This is directly analogous to the reported bug class: the report's root cause was a field (`stakeByPlayer`/probability weight) being acted on outside the boundary the game enforces (cooldown gate). Here, the analog is a field (`shop`) being acted on outside the boundary the signature enforces (raw-body HMAC) — the value that authorizes the request (HMAC over `raw_body`) is not the value used to select the tenant (`shop` header).

### Impact Explanation
A webhook delivered for shop A's genuine, correctly-signed payload could be replayed by an attacker to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to shop B (or to an arbitrary attacker-registered dev shop domain), as long as the raw body bytes are unchanged, since only the body is HMAC-verified. If the app's handler trusts `WebhookMetadata#shop` to select which tenant's data to mutate/associate with the delivered payload (a common pattern, since this is the exact purpose the gem exposes `shop` for), an attacker can cause cross-tenant data to be attributed to, or processed under, the wrong shop. This crosses the tenant boundary this gem is supposed to enforce for webhook processing, matching the High "cross-tenant access" impact category.

### Likelihood Explanation
This does not require possession of `api_secret_key` or any privileged credential: an attacker who can reach the app's public webhook endpoint (any unprivileged internet user, since webhook endpoints are unauthenticated HTTP endpoints by design) can capture or infer a legitimately-signed body/HMAC pair (e.g., their own shop's webhook, or a body they construct themselves and get Shopify to sign by triggering a real event on any shop they control) and then re-send it with a different `shop`/`shopify-shop-domain` header value while keeping the same body+hmac pair. The gem performs no header-to-signature binding check anywhere in the webhook path.

### Recommendation
Include the shop domain (and topic/webhook-id) in the bytes that are HMAC-verified, or otherwise cryptographically bind the header value to the signed payload, rather than trusting `shopify-shop-domain` as a bare unauthenticated header. At minimum, `Request#to_signable_string` should incorporate the header value used for tenant routing so `HmacValidator.validate` actually authenticates the shop being acted upon.

### Proof of Concept
1. Attacker controls a Shopify dev/trial shop `attacker.myshopify.com` with the app installed and webhooks configured.
2. Attacker triggers a real webhook event on their own shop, capturing the resulting `raw_body` and the correctly computed `shopify-hmac-sha256` value Shopify sends for that body (any body they can produce with a valid signature works equally, since the signature never covers the shop header).
3. Attacker resends this exact `raw_body` + `hmac` to the app's webhook endpoint, but with the `x-shopify-shop-domain` header changed to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb#process` succeeds because it only checks the HMAC over `raw_body` [2](#0-1) .
5. The app's handler receives `WebhookMetadata(shop: "victim.myshopify.com", ...)` [8](#0-7)  and processes/attributes the attacker's payload under the victim shop's tenant context.
