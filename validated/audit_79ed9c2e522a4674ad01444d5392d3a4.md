### Title
Unvalidated `VestingSchedule` in lockup deployment permanently freezes owner funds - (File: `lockup/src/types.rs`, `lockup/src/lib.rs`, `lockup-factory/src/lib.rs`)

### Summary
The `VestingSchedule::assert_valid()` sanity check (analogous to the missing `vestingStart < vestingEnd` check in the external report) is defined in both `lockup/src/types.rs` and `lockup-factory/src/types.rs` but is never invoked anywhere in the production code path. This means an unprivileged caller of the public `LockupFactory::create` entrypoint can supply a malformed `VestingSchedule` (e.g. `start_timestamp >= end_timestamp`, or `cliff_timestamp > end_timestamp`) for a lockup contract they create on behalf of any `owner_account_id`, permanently breaking every downstream calculation that depends on `end_timestamp - start_timestamp`.

### Finding Description
`VestingSchedule::assert_valid()` checks `start <= cliff <= end` and `start < end`: [1](#0-0) 

However, grepping the entire codebase shows this function is only ever *defined*, never *called*, in either `lockup/src/lib.rs::new` (the lockup contract's `#[init]`) or `lockup-factory/src/lib.rs::create` (the public factory entrypoint): [2](#0-1) [3](#0-2) 

`LockupFactory::create` is a public, payable method callable by any unprivileged account, which fully controls the `vesting_schedule` parameter (`VestingScheduleOrHash::VestingSchedule`) forwarded unchecked into the newly deployed lockup contract for an arbitrary `owner_account_id`: [4](#0-3) 

Because the schedule is never validated, `end_timestamp` can be set less than or equal to `start_timestamp`. This directly breaks `get_unvested_amount`, which computes `vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0` as an unsigned subtraction: [5](#0-4) 

Every function that depends on `get_unvested_amount` — including `get_locked_amount`, `get_liquid_owners_balance` (used by `transfer`), and `terminate_vesting` — will panic on underflow/produce corrupted values once `block_timestamp` enters the range where `end_timestamp <= block_timestamp` doesn't hold but `start > end`. `terminate_vesting` itself calls `get_unvested_amount` before it can transition state: [6](#0-5) 

This mirrors the external report's root cause exactly: a setter/constructor path accepts a `start`/`end` timestamp pair without enforcing `start < end`, and downstream arithmetic (`end - start`) silently assumes the ordering holds.

### Impact Explanation
If the vesting schedule is malformed, every code path that reads `get_unvested_amount`/`get_locked_amount` (owner transfers, `get_liquid_owners_balance`, and the foundation's `terminate_vesting`) either panics or returns nonsensical results. Since NEAR's transaction-level unsigned-subtraction underflow aborts the call, the owner can never transfer any liquid balance and the foundation can never terminate/withdraw the unvested balance — permanently freezing all tokens locked in that lockup contract. This matches the "Critical: Permanent freezing, unrecoverable lock... in lockup release, vesting termination... flows" impact category.

### Likelihood Explanation
The `create` method on `lockup-factory` is a fully public, unprivileged entrypoint — any account can call it, attach the minimum deposit, and specify an arbitrary `owner_account_id` and `vesting_schedule`. Since there is zero validation (`assert_valid` is dead code), constructing a malicious/malformed schedule requires no special access and is trivially reachable, making this a realistic, low-effort griefing vector against any account whose lockup is funded through the factory (or through direct calls to `lockup::new` by any deploying party controlling the vesting schedule parameters, e.g. via a compromised or careless funding workflow).

### Recommendation
Invoke `vesting_schedule.assert_valid()` (for the `VestingScheduleOrHash::VestingSchedule` variant) inside both `lockup/src/lib.rs::new` and `lockup-factory/src/lib.rs::create` before persisting the `VestingInformation`, rejecting the transaction if `start_timestamp < cliff_timestamp <= end_timestamp` does not hold, consistent with the already-written but unused `assert_valid()` check.

### Proof of Concept
1. Unprivileged funding account calls `lockup-factory::create` with `owner_account_id = victim`, attaching `MIN_ATTACHED_BALANCE`, and `vesting_schedule = VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T2, cliff_timestamp: T1, end_timestamp: T1 })` where `T1 < T2` (i.e., `end_timestamp < start_timestamp`).
2. `LockupFactory::create` forwards this schedule unchanged to the newly deployed lockup contract's `new` constructor, which does not call `assert_valid()`. [7](#0-6) 
3. Once deployed, any call to `get_unvested_amount` (directly, or transitively via `get_locked_amount`, `get_liquid_owners_balance`, `transfer`, or `terminate_vesting`) performs `end_timestamp.0 - start_timestamp.0` where `end_timestamp < start_timestamp`, causing an unsigned-integer underflow panic that aborts the call. [8](#0-7) 
4. The victim owner can never withdraw/transfer, and the foundation can never terminate vesting to recover funds, since `terminate_vesting` also depends on `get_unvested_amount`. All tokens locked in the contract are permanently frozen.
