## Analysis

The report describes a duplicate-registration bug class: a value (a token address) accepted into an array/list without a "already present" check, later consumed by code that assumes uniqueness, causing double-counting that leads to over-crediting/insolvency.

This exact bug class was previously found and *fixed* in Hyperbridge's canonical `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`), which explicitly rejects duplicate output tokens via transient storage and duplicate input tokens via an escrow-overwrite guard, with regression tests noting the original bugs ("previously merged into one `_partialFills` bucket", "previously merged into one escrow bucket"): [1](#0-0) [2](#0-1) [3](#0-2) 

The Tron deployment's copy of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, has its own independent `placeOrder` implementation and is **missing both of these duplicate-token guards**: [4](#0-3) 

### Title
Missing duplicate-output-token rejection in `IntentGatewayV2.placeOrder` (Tron) enables over-release of escrowed input funds via merged `_partialFills` buckets - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`evm/src/apps/IntentGatewayV2.sol::placeOrder` (mainline EVM) rejects orders whose `output.assets` array contains the same token more than once, and rejects orders whose `inputs` array contains the same token more than once, precisely because downstream fill logic keys per-token state (`_partialFills[commitment][outputToken]`, `_orders[commitment][token]`) by token address and silently merges repeated legs into one bucket. The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, reimplements `placeOrder` without either guard.

### Finding Description
Mainline `placeOrder` opens with an explicit duplicate-output-token check using transient storage that reverts with `InvalidInput` on any repeated `token` in `order.output.assets`: [5](#0-4) 

It also rejects duplicate input tokens when crediting escrow: [2](#0-1) 

Both checks exist specifically because same-chain/cross-chain fill logic tracks fill progress and released input escrow per *token address*, not per array index — a second leg with the same token silently shares state with the first (`_partialFills[commitment][outputToken]`), exactly analogous to `DSCEngine.s_collateralTokens` being iterated by token address with no de-duplication.

The Tron contract's `placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol:338-386`) performs no such check: it validates only `order.inputs.length == 0`, computes `commitment`, and proceeds straight to fee reduction and escrow crediting, with no scan for repeated `order.output.assets[i].token` or `order.inputs[i].token` values: [4](#0-3) 

Because a user fully controls the `Order` struct passed to `placeOrder`, an unprivileged user can submit an order whose `output.assets` array lists the same output token twice with two different required amounts (e.g., leg A requires 400 DAI, leg B requires 600 DAI). If the fill path shares the mainline `_fillSameChain`/`_fillCrossChain` semantics keyed by `_partialFills[commitment][outputToken]` (as evidenced by the regression test titled "Regression test for: same-chain partial fills prematurely finalize repeated output legs" added to fix this same defect in mainline), a solver filling only the smaller leg's amount would satisfy the shared per-token bucket and be treated as having completed both legs, releasing the full escrowed input to the solver while only delivering a fraction of the promised output — an under-collateralized fill, analogous to the double-spending/insolvency impact in the report.

### Impact Explanation
An attacker (acting as either the order creator colluding with a solver, or a solver exploiting a naively-constructed but user-submitted order) can cause the protocol to release full escrowed input value while receiving only partial output value, or otherwise corrupt per-token fill/escrow accounting. This is a direct fund-theft / accounting-insolvency vector reachable from a single `placeOrder` transaction submitted by any unprivileged user — no admin or governance action required.

### Likelihood Explanation
`placeOrder` is a fully permissionless, unprivileged entry point that any user can call with an arbitrary `Order` struct, and the missing check is a straightforward code-omission relative to the already-fixed mainline contract, making this trivially triggerable once the reachable Tron gateway is deployed and orders route through the shared fill logic.

### Recommendation
Port the exact duplicate-token guards from `evm/src/apps/IntentGatewayV2.sol::placeOrder` (both the transient-storage duplicate-output-token check and the `_orders[commitment][token] != 0` duplicate-input-token check) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, and add the same regression tests (`testRevert_PlaceOrder_DuplicateInputTokens`, `testRevert_PlaceOrder_DuplicateOutputTokens`) against the Tron contract build.

### Proof of Concept
1. User calls `IntentGatewayV2(tron).placeOrder(order, graffiti)` where `order.output.assets = [{token: DAI, amount: 400e18}, {token: DAI, amount: 600e18}]` and `order.inputs = [{token: USDC, amount: 1000e6}]`.
2. `placeOrder` (Tron) performs no duplicate check, computes `commitment`, and escrows the full 1000 USDC.
3. On fill, a solver calls `fillOrder` supplying only 400 DAI (matching the first leg). If the underlying fill logic shares mainline's `_partialFills[commitment][outputToken]` semantics, the shared per-token bucket for DAI is marked filled for the combined leg amounts once the smaller solver-provided amount satisfies the merged accounting path, releasing the full 1000 USDC escrow to the solver despite only 400 of the intended 1000 DAI-equivalent value being delivered.
4. This mirrors the exact scenario the mainline regression test `testRevert_PlaceOrder_DuplicateOutputTokens` was written to prevent: [6](#0-5) 

**Uncertainty note:** I was not able to fully confirm within the indexed content whether the Tron package's fill functions (`fillOrder`/`_fillSameChain`/`_fillCrossChain`) are literally shared with or identical to `evm/src/apps/intentsv2/IntrinsicIntents.sol` / `ExtrinsicIntents.sol`, since the Tron directory may contain its own copies not fully surfaced by the index. The root-cause omission in `placeOrder` itself is confirmed directly from source; a Devin session with full file access should verify the Tron fill-side implementation to confirm the exact exploitation mechanics before remediation.

    function placeOrder(Order memory order, bytes32 graffiti) public payable {
        // Validate that order has inputs
        if (order.inputs.length == 0) revert InvalidInput();

        address hostAddr = host();
        // fill out the order preludes
        order.user = bytes32(uint256(uint160(msg.sender)));
        order.source = IDispatcher(hostAddr).host();
        order.nonce = _nonce++;

        // Calculate reduced inputs (after protocol fees) for commitment and escrow
        uint256 inputsLen = order.inputs.length;
        // Use destination-specific protocol fee, fallback to source chain fee if zero
        bytes32 destinationHash = keccak256(order.destination);
        uint256 protocolFeeBps = _destinationProtocolFees[destinationHash];
        if (protocolFeeBps == 0) {
            protocolFeeBps = _params.protocolFeeBps;
        }
        TokenInfo[] memory reducedInputs;
        bytes32 commitment;

        if (protocolFeeBps > 0) {
            reducedInputs = new TokenInfo[](inputsLen);
            for (uint256 i; i < inputsLen;) {
                uint256 originalAmount = order.inputs[i].amount;
                uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
                uint256 reducedAmount = originalAmount - protocolFee;
                address token = address(uint160(uint256(order.inputs[i].token)));

                // Emit DustCollected for protocol fee if non-zero
                if (protocolFee > 0) emit DustCollected(token, protocolFee);

                reducedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: reducedAmount});
                unchecked {
                    ++i;
                }
            }

            // Temporarily swap inputs to calculate commitment with reduced amounts
            TokenInfo[] memory originalInputs = order.inputs;
            order.inputs = reducedInputs;
            commitment = keccak256(abi.encode(order));
            order.inputs = originalInputs;
        } else {
            // No protocol fees, use order.inputs directly
            reducedInputs = order.inputs;
            commitment = keccak256(abi.encode(order));
        }
