### Title
Webhook `shop-domain`/`topic`/`webhook-id` identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw body, then trusts the `shop-domain`, `topic`, and `webhook-id` headers verbatim to build the `WebhookMetadata` passed to the app's handler. The HMAC signature never covers these identity/routing fields, so a party who can obtain one validly-signed webhook body (e.g., a merchant who has legitimately installed the app on their own store) can reuse that signature on a forged request with a different `shop-domain`/`topic`/`webhook-id`, tricking the app into believing the payload originated from a different tenant or topic.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` uses this body-only check as the sole authentication gate, then forwards the unauthenticated header-derived identity fields directly into `WebhookMetadata`, which is handed to the app's handler as trusted context: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`HMAC(secret, raw_body) valid` ⇒ `(shop, topic, webhook_id)` in the request are the values Shopify actually associated with that signed body.

In this implementation the equality actually enforced is only:
`HMAC(secret, raw_body) valid` ⇒ `raw_body` was produced by Shopify for *some* webhook (unspecified shop/topic/id).

Because `shop`, `topic`, and `webhook_id` are never part of the signed content, any two requests carrying the exact same JSON body will produce the exact same valid HMAC regardless of which shop, topic, or webhook id header accompanies them. All shops using a given app share the same `api_secret_key` for webhook signing, so a malicious but legitimately-installed merchant (an "unprivileged" tenant relative to other merchants using the same app) can:
1. Trigger a real webhook for their own shop with a body they control/predict (many webhook topics have attacker-influenced bodies, e.g. product/order fields the merchant sets themselves).
2. Capture the resulting `X-Shopify-Hmac-Sha256` value, which is valid for that exact body.
3. Replay the same raw body to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (a victim shop) and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`.
4. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the handler using the forged `shop`/`topic`/`webhook_id`.

This breaks the tenant boundary the app relies on: the handler will act as if a different shop (or a different, possibly more consequential, topic such as `app/uninstalled` or `shop/redact`) sent that data, when in fact it was replayed by an unrelated, malicious tenant.

### Impact Explanation
This is a cross-tenant authentication bypass at the identity-binding layer: the app is designed to trust `WebhookMetadata#shop`/`#topic` as authenticated facts once the HMAC passes, but the HMAC does not actually authenticate those fields. An attacker (any merchant who installs the app) can impersonate another merchant's shop domain or spoof a different webhook topic while carrying a validly-signed body, causing the receiving app to execute shop-specific or topic-specific logic (e.g. data deletion for `shop/redact`, install/uninstall handling, order/customer processing) against the wrong tenant. This matches the "Critical - cross-tenant access" impact category, since the identity used for authorization decisions inside the handler is forgeable independently of the cryptographic check.

### Likelihood Explanation
Likelihood is moderate-to-high for apps that key business logic off `WebhookMetadata#shop` or `#topic` without independently cross-checking it against other authenticated context (e.g. an existing session/shop record). Any merchant with a normal app installation can generate at least one validly-signed webhook body under their control and replay it with different routing headers to the shared webhook endpoint; no access to `api_secret_key` or any privileged credential is required, only the ability to install the app as a normal customer and to send an arbitrary HTTP request to the app's public webhook endpoint.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (and `api-version`) in the HMAC-signed material used by `Request#to_signable_string`, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`. Short of that, document clearly that consuming applications must not treat `WebhookMetadata#shop`/`#topic`/`#webhook_id` as authenticated unless they independently verify them (e.g. against Shopify's webhook API using an authenticated GraphQL query keyed by `webhook_id`), since the library's own HMAC check does not cover them.

### Proof of Concept
1. Attacker installs the target app on their own store `evil-shop.myshopify.com` and receives a legitimate webhook, e.g. for `products/update`, with `raw_body = B` and header `X-Shopify-Hmac-Sha256 = H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - `raw_body = B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because `HmacValidator.validate` only checks the body)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic: shop/redact` (forged, or any other topic sharing a compatible body shape)
   - `X-Shopify-Webhook-Id: <arbitrary>` (forged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes the HMAC of `raw_body`.
4. The handler registered for the forged topic receives `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and executes shop-specific/topic-specific logic against `victim-shop.myshopify.com`, even though the signed payload never originated from Shopify for that shop or topic.
