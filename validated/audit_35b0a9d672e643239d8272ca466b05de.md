## Analog Found: Infinite Loop in GRANDPA Ancestry-Chain Walk

### Title
Infinite loop in `AncestryChain::ancestry` allows unauthenticated denial of service via a crafted GRANDPA consensus proof - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks a parent-hash chain built entirely from attacker-supplied, unverified headers (`FinalityProof::unknown_headers`) before any cryptographic signature is checked. Because the walk trusts each header's self-reported `parent_hash()` field without cycle detection or a bound on the number of hops, a relayer can submit a consensus proof containing a cycle of headers that never reaches the expected `base` hash, causing the `while` loop to run forever — the same root-cause pattern as CVE-2017-14229's infinite loop in `jpc_dec_tileinit` (an unbounded decode/traversal loop driven by attacker input).

### Finding Description
The vulnerable loop: [1](#0-0) 

`AncestryChain::new` builds a `BTreeMap<H::Hash, H>` directly from the untrusted `unknown_headers` slice with no validation that the headers actually form a proper decreasing, acyclic ancestry chain: [2](#0-1) 

`ancestry(base, block)` then repeatedly looks up `current_hash` in this map and follows `parent_hash()` until `current_hash == base`. If an attacker supplies two or more headers whose `parent_hash` fields point to each other (forming a cycle) and that cycle never includes `base`, every lookup in the loop succeeds (`Some(current_header)`) and `current_hash` cycles indefinitely — the loop can never hit the error branch (`_ => return Err(...)`) because the map entries always resolve.

This is reached from `verify_grandpa_finality_proof`, which computes `target`/`base` purely from `finality_proof.unknown_headers` (attacker-controlled), decodes the justification, and then calls the vulnerable `ancestry()` **before** the justification's cryptographic signature is verified: [3](#0-2) 

Since the signature check (`justification.verify(...)`) happens only at line 91-93, *after* the vulnerable `headers.ancestry(from, target.hash())` call at line 88, an attacker only needs a proof that SCALE-decodes and satisfies `target.hash() == finality_proof.block` / `justification.commit.target_hash == finality_proof.block` — no valid GRANDPA signatures are required to trigger the infinite loop.

This verifier is invoked directly by the on-chain GRANDPA `ConsensusClient::verify_consensus`, which decodes the proof from raw bytes supplied in an ISMP `Message::Consensus`: [4](#0-3) 

This entry point is reachable via `pallet_ismp`'s unsigned/unsigned-message dispatch path (`handle_unsigned`/`handle_incoming_message`) used by any relayer submitting a consensus update — an unprivileged, single-transaction path.

The same unbounded/untrusted-cycle pattern also affects `verify_with_voter_set`'s per-precommit ancestry walk and the `verify_fraud_proof` path in `modules/ismp/clients/grandpa/src/consensus.rs`, both of which call `AncestryChain::ancestry` on attacker-supplied header sets: [5](#0-4) [6](#0-5) 

### Impact Explanation
A single relayed/dispatched GRANDPA consensus message can hang the runtime's block-execution thread indefinitely inside an unbounded loop, well before any signature is checked. On a Substrate runtime, an unbounded loop in dispatch execution stalls block production/finalization for the chain processing the message — a denial of service against the message dispatcher and, transitively, against every route relying on that GRANDPA consensus client for state-machine updates (this fits the "route unable to deliver messages" acceptance criterion). This is High severity: it is remotely triggerable by any unprivileged relayer with a single crafted proof and requires no signing key or governance access.

### Likelihood Explanation
Likelihood is high: the attack requires only constructing two or more headers with reciprocal/cyclic `parent_hash` fields, packaging them into `unknown_headers`, and having a `commit`/`target_hash` decode successfully (no valid finality signatures required to reach the vulnerable code path). This is well within reach of any address that can submit a consensus-update extrinsic/message.

### Recommendation
Bound the ancestry walk: track visited hashes and abort with `Error::NotDescendent` (or equivalent) if a hash is revisited, and/or cap the number of hops to `unknown_headers.len()` (since a valid ancestry route can never revisit a header). Apply the same fix everywhere `AncestryChain::ancestry` is invoked on unauthenticated header sets (`verify_grandpa_finality_proof`, `verify_with_voter_set`, and the fraud-proof handler in `modules/ismp/clients/grandpa/src/consensus.rs`), and ensure any header-cycle/self-reference is rejected during `AncestryChain::new` or before the walk begins, prior to any signature verification.

### Proof of Concept
1. Craft `unknown_headers = [H1, H2]` where `H1.number = N+1`, `H2.number = N`, `H1.parent_hash = H2.hash()`, and `H2.parent_hash = H1.hash()` (a 2-cycle that never resolves to the trusted `base`/`from` hash held in `consensus_state.latest_hash`).
2. Set `finality_proof.block = H1.hash()` and craft a `GrandpaJustification` with `commit.target_hash = H1.hash()` (signatures can be garbage/invalid — they are not checked yet).
3. Submit this as the `consensus_proof` payload of an ISMP `Message::Consensus` addressed to the GRANDPA consensus state ID, via the standard unsigned message-handling path.
4. Execution reaches `verify_grandpa_finality_proof` → `headers.ancestry(from, target.hash())`; because `from` is never encountered while walking the `H1 <-> H2` cycle, the `while current_hash != base` loop never terminates, hanging block execution.

		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
