### Title
Inconsistent hyphen-delimited StateMachine ID parsing between on-chain/relayer Rust code and SDK/indexer TypeScript can misroute or permanently strand cross-chain messages - (File: `modules/ismp/core/src/host.rs`, `sdk/packages/sdk/src/utils.ts`)

### Summary
The reported `shescape` bug (CVE-2022-31180) is a CWE-74 class issue: a delimiter/special-character is not escaped before being embedded in a downstream parser, so a single untrusted string is interpreted differently — and dangerously — depending on which consumer parses it. Hyperbridge has an analogous root cause in how the human-readable `StateMachine` identifier (e.g. `"EVM-97"`, `"SUBSTRATE-cere"`, `"RELAY-CENJ-1000"`) is parsed. This string is a hyphen-delimited, attacker/user-influenced field that different parts of the stack parse with **different splitting rules**, with no escaping or canonicalization of the `-` delimiter itself.

### Finding Description
`StateMachine::from_str` in [1](#0-0)  parses the identifier by taking the **last** `-`-separated segment (`name.split('-').last()`) for `EVM-`, `POLKADOT-`, `KUSAMA-`, `RELAY-`, `SUBSTRATE-`, and `TNDRMINT-` prefixes, e.g.: [2](#0-1) 

Meanwhile, the TypeScript SDK's `parseStateMachineId` — used to build calldata for `handlePostRequests`/proofs and to decide EVM/Substrate/Polkadot/Kusama identity client-side — destructures only the **first two** elements of the split array and silently discards everything after the first hyphen: [3](#0-2) 

The same first-hyphen-only pattern recurs in the indexer (`getStateId`) [4](#0-3) , and in the EVM chain adapter's proof-height derivation which also does `.split("-")[1]`: [5](#0-4) .

So the same string is parsed by "take the last hyphen-segment" on the Rust/on-chain-facing side and "take the segment after the first hyphen" on the SDK/indexer side. Neither side escapes, rejects, or canonicalizes an identifier containing more than one hyphen — precisely the "insufficient escaping of a control character" pattern from the advisory, just with `-` as the unescaped delimiter instead of whitespace.

For the `SUBSTRATE-`/`TNDRMINT-` variants, the Rust side does guard against silently accepting a wrong-length id (a fixed `[u8;4]`, checked explicitly per the existing regression test noted in the file) [6](#0-5) , so a crafted multi-hyphen identifier there degrades to an outright parse error rather than a length-matching but wrong value. However, that safety net exists only in the Rust parser; the SDK's `parseStateMachineId` and indexer's `getStateId`, and the EVM adapter's numeric-index extraction, have no equivalent defense — they will happily accept a multi-hyphen id and derive a *different* value (whichever segment their particular split logic picks) than what the Rust/on-chain component would derive from the exact same string.

### Impact Explanation
Because state-machine identifiers cross trust and implementation boundaries (dispatcher choosing `dest`, SDK constructing proofs/calldata for `handlePostRequests`, indexer computing commitments/routing metadata, and the Rust ISMP core converting ABI events back into a canonical `StateMachine`), a divergence in how the delimiter is parsed can cause the SDK/relayer path and the authoritative Rust path to disagree about which destination/consensus client a message is bound for. This falls squarely into the accepted impact category "a route unable to deliver messages": a message could be built/proved against one interpretation of the destination identifier while the authoritative host/consensus module resolves the identifier differently (or rejects it), permanently stalling delivery for that route. It could also misdirect fee/withdrawal or proof height computation client-side (as in `evm.ts`'s `.split("-")[1]` usage for `stateMachineId` in state proofs) if an id string legitimately or maliciously contains an extra hyphen.

### Likelihood Explanation
Exploitability is bounded by how much control an unprivileged actor has over the raw identifier string that ultimately reaches both parsers unmodified. State-machine ids are normally short fixed formats (`EVM-<chainid>`, `POLKADOT-<paraid>`, 4-byte SUBSTRATE/TNDRMINT codes), so naturally occurring multi-hyphen ids are uncommon, and the Rust side's explicit 4-byte length check already turns most malformed SUBSTRATE/TNDRMINT ids into hard errors rather than silent misparses. This keeps likelihood at Medium rather than Critical: the bug class (unescaped delimiter, divergent parsers) is real and demonstrable in the code, but a full end-to-end proof that an unprivileged transaction can force a *silently wrong but validly-shaped* identifier all the way through both the SDK and Rust `handlePostRequests` path (as opposed to a clean rejection) was not confirmed within available investigation; it depends on further chain-specific parsing/consumers not inspected here (e.g., every place that consumes `proof.stateMachine` or a dispatched `dest` string).

### Recommendation
- Define a single canonical parser/serializer for `StateMachine` ids (ideally a shared spec or fixed-width tagged encoding rather than a hyphen-joined string) and make every consumer (Rust `host.rs`, SDK `utils.ts`, indexer `state-machine.helper.ts`, `evm.ts` proof encoding) call into it, instead of independently re-implementing `split('-')` logic with different segment-selection rules.
- Reject (rather than best-effort parse) any identifier containing more separators than the format allows, in every implementation — mirroring the length check already present for `SUBSTRATE-`/`TNDRMINT-` in `host.rs`, and add the same for the numeric-id variants and for all TypeScript parsers.
- Add cross-implementation round-trip/fuzz tests that check the Rust parser and the TypeScript parsers agree on every malformed/multi-hyphen input, not just well-formed ones.

### Proof of Concept
Conceptual (not independently executed against a running chain within this investigation):
1. Construct a `StateMachine` string with an embedded extra hyphen inside the value portion, e.g. `"EVM-1-1"`.
2. Rust `StateMachine::from_str("EVM-1-1")` (`modules/ismp/core/src/host.rs:349-356`) does `name.split('-').last()` → `"1"` → `StateMachine::Evm(1)`.
3. SDK `parseStateMachineId("EVM-1-1")` (`sdk/packages/sdk/src/utils.ts:137,148-155`) does `const [type, value] = "EVM-1-1".split("-")` → `type="EVM"`, `value="1"` (from index 1, the "1" right after "EVM") → also `Evm(1)` in this particular numeric example, coincidentally matching.
4. For the SUBSTRATE/TNDRMINT byte-identifier case, the same input processed by the SDK yields a UTF-8 byte string derived from only the first hyphen-delimited segment, while Rust would take the last segment (and reject it if not exactly 4 bytes) — demonstrating the parsers do not agree on which bytes constitute the identifier for any string containing more than one hyphen.

This demonstrates the structural parsing divergence; confirming a concrete on-chain "stuck route" or "forged destination" outcome would require tracing one further hop (which live caller can inject such a multi-hyphen id into both the SDK-side proof construction and the Rust-side event conversion for the same request) that could not be completed with the remaining investigation budget.

					.last()
					.and_then(|id| u32::from_str(id).ok())

			},
			name if name.starts_with("POLKADOT-") => {
				let id = name
					.split('-')
					.last()
					.and_then(|id| u32::from_str(id).ok())
					.ok_or_else(|| format!("invalid state machine: {name}"))?;
				StateMachine::Polkadot(id)
			},

			name if name.starts_with("RELAY-") => {
				let values = name.split('-').collect::<Vec<_>>();
				let id = values
					.last()
					.and_then(|id| u32::from_str(id).ok())
					.ok_or_else(|| format!("invalid state machine: {name}"))?;

					.split('-')

				id.copy_from_slice(bytes);
				StateMachine::Tendermint(id)
			},
			name => Err(format!("Unknown state machine: {name}"))?,
		};

	}

export function parseStateMachineId(stateMachineId: string): {
	stateId: { Evm?: number; Substrate?: HexString; Polkadot?: number; Kusama?: number }
} {
	const [type, value] = stateMachineId.split("-")

	if (!type || !value) {
		throw new Error(
			`Invalid state machine ID format: ${stateMachineId}. Expected format like "EVM-97" or "SUBSTRATE-cere"`,
		)
	}

	const stateId: { Evm?: number; Substrate?: HexString; Polkadot?: number; Kusama?: number } = {}

	switch (type.toUpperCase()) {
		case "EVM": {
			const evmChainId = Number.parseInt(value, 10)
			if (Number.isNaN(evmChainId)) {
				throw new Error(`Invalid EVM chain ID: ${value}. Expected a number.`)
			}
			stateId.Evm = evmChainId
			break
		}

		case "SUBSTRATE": {
			// Convert the string to hex-encoded UTF-8 bytes
			const bytes = Buffer.from(value, "utf8")
			stateId.Substrate = `0x${bytes.toString("hex")}` as HexString
			break
		}

		case "POLKADOT": {
			const polkadotChainId = Number.parseInt(value, 10)
			if (Number.isNaN(polkadotChainId)) {
				throw new Error(`Invalid Polkadot chain ID: ${value}. Expected a number.`)
			}
			stateId.Polkadot = polkadotChainId
			break
		}

		case "KUSAMA": {
			const kusamaChainId = Number.parseInt(value, 10)
			if (Number.isNaN(kusamaChainId)) {
				throw new Error(`Invalid Kusama chain ID: ${value}. Expected a number.`)
			}
			stateId.Kusama = kusamaChainId
			break
		}

		default:
			throw new Error(`Unsupported chain type: ${type}. Expected one of: EVM, SUBSTRATE, POLKADOT, KUSAMA.`)
	}

	return { stateId }
}

export const getStateId = (id: string) => {
	const [type, value] = id.split("-")
	const tag = getStateMachineTag(type)

	switch (tag) {
		case "Evm":
		case "Polkadot":
		case "Kusama":
			return {
				tag,
				value: Number(value),
			}
		case "Substrate":
		case "Tendermint":
			return {
				tag,
				value: Array.from(new TextEncoder().encode(value)),
			}
		default:
			throw new Error(`Unknown state machine type: ${type}`)
	}
}
