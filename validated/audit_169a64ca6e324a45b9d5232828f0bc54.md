This confirms the vulnerability. The `WebhookMetadata.shop` field, which the handler uses to identify which merchant a webhook belongs to, is populated directly from `request.shop` (the `x-shopify-shop-domain` header), while the HMAC only signs `@raw_body` [1](#0-0) . The `shop-domain` header is never included in the signed content.

### Title
Webhook `shop` field is trusted without HMAC binding, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , and `HmacValidator.validate` computes/compares the HMAC solely over that signable string [3](#0-2) . Meanwhile, `Registry.process` uses `request.shop` — sourced from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header — to build the `WebhookMetadata` passed to the app's handler [4](#0-3) [5](#0-4) . The `shop` header is never part of the HMAC-signed material, so it is a field acted on (used as the tenant identifier by consuming apps) but not covered by the HMAC — the exact bug class described in the analog report (an unbound field trusted post-verification).

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler [6](#0-5) . That validation proves the raw body was signed with the app's secret, but it does not bind the body to the specific `shop-domain` header value carried alongside it. Since Shopify signs each shop's outgoing webhook with the same app-level `client_secret`, any legitimate webhook payload (with a valid signature) received by an app — regardless of which install produced it — can be re-submitted to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different (victim) shop. The HMAC check still passes because it only verifies the (unmodified) body/signature pair; the header is parsed independently and trusted as-is: `T.cast(shopify_header("shop-domain"), String)` [5](#0-4) . The `WebhookMetadata.shop` field constructed from this untrusted header [7](#0-6)  is exactly the value applications are expected to use to identify which merchant's tenant record/session/data the event applies to.

### Impact Explanation
This breaks the identity binding `bytes verified == bytes acted upon`: the bytes cryptographically verified (raw body) do not include the bytes used to select the tenant (`shop` header). An attacker who operates their own installed instance of the app (or otherwise obtains one authentic, validly-signed webhook payload) can replay it against the app's public webhook endpoint with an arbitrary `shop-domain` header, causing the receiving application to process/attribute the webhook event to a shop it did not originate from — a cross-tenant data-integrity/confusion issue that can lead to acting on another merchant's behalf (e.g., triggering shop-specific business logic, cache/DB writes) using data forged by an unrelated tenant.

### Likelihood Explanation
Webhook endpoints are unauthenticated public HTTP endpoints by design (Shopify calls them without any session/access token), and the header-vs-signed-body mismatch requires no `api_secret_key`, access token, or privileged access — only capturing/replaying one's own genuine webhook delivery with a modified header, which is fully within reach of any unprivileged internet user who has installed the target app on their own shop.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the payload before trusting `request.shop` for tenant identification, so a valid signature cannot be replayed under a different shop's identity.

### Proof of Concept
1. App installs on attacker-controlled shop `attacker.myshopify.com`; Shopify sends a genuine webhook with body `B`, `x-shopify-hmac-sha256: H` (valid for secret `S`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body `B` and signature `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb` line 190 succeeds because it only checks `B` against `H`.
4. `Registry.process` builds `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B) ...)` and invokes the app's handler, which now processes attacker-forged data under `victim.myshopify.com`'s identity.
