### Title
Missing source-authentication check for `RequestState` messages allows unauthorized replay of the last relay message - (File: `orb-relay-client/src/client.rs`)

### Summary
In `orb-relay-client/src/client.rs`, the relay client's main loop enforces a source check (`src.id != self.config.dst_id`) before processing any inbound `RelayPayload`, dropping messages from unexpected senders [1](#0-0) . However, this enforcement is inconsistently applied: if the inbound payload matches `self_serve::app::v1::RequestState`, the client skips the source check entirely and immediately replays `self.last_message` to the sender [2](#0-1) . This is the same bug class as the reported `_credit` missing `whenNotPaused`: a specific message type bypasses the access-control gate that all other message types must pass through.

### Finding Description
The main polling loop for `PollerAgent` processes incoming `RelayConnectResponse` messages in a `match` branch. For a normal payload, the code path is:
```
if RequestState::matches(&payload) { reply with last_message }     // no src check
else if src.id != self.config.dst_id { drop, log error }           // src check enforced
else { handle_message(...) }                                        // src check enforced
``` [3](#0-2) 

The `dst_id` field represents the expected authenticated counterparty (the Orb for an App-mode client, or the App/session for an Orb-mode client) and is precisely the identity check meant to enforce the orb↔app trust boundary for this IPC-like relay channel [4](#0-3) . That check is applied to every payload type except `RequestState`. Any entity able to send a `RequestState` payload through the relay server (i.e., any sender the relay server itself doesn't restrict per-topic) can trigger a reply containing `self.last_message`, which is the last message this client actually sent to its legitimate counterparty (constructed and cached at send time) [5](#0-4) . This is a state/data disclosure path that sidesteps the identity check that is otherwise consistently enforced in this same loop.

### Impact Explanation
This client is used for orb⟷app relay communication tied to self-serve signup flows (`self_serve::app::v1`, `self_serve::orb::v1` message types are referenced elsewhere in the signup plan, e.g. `CaptureTriggerTimeout`/`CaptureStarted` in `src/plans/mod.rs`). If `last_message` at the time of a spoofed `RequestState` request contains signup-session-relevant state (e.g. capture-trigger/session control messages), an unauthenticated or wrong-identity party on the relay channel could obtain a replay of orb/app session state intended only for the legitimate counterparty — a cross-signup/session state bleed via a trust-boundary bypass, matching the "misattributed/cross-signup state bleed" impact category. Because the source-identity check exists specifically to prevent processing of messages from unexpected sources, and one message type is carved out of that check, the resulting behavior is inconsistent enforcement of the trust boundary, directly analogous to the `_credit` pause bypass in the external report.

### Likelihood Explanation
Likelihood depends on whether the underlying relay server enforces its own strict routing/ACL so that only the intended destination can ever deliver a payload addressed as coming from an arbitrary `src`. Nothing in the client code itself prevents a message tagged with `RequestState` from reaching this branch regardless of who actually sent it; the client-side identity check is bypassed unconditionally for this payload type. This is a concrete, reachable code path (no feature flags gate it) and requires no privileged position — any party capable of publishing to the relay stream this client subscribes to can attempt it.

### Recommendation
Apply the same `src.id != self.config.dst_id` check before honoring `RequestState` requests, so all inbound message types are subject to consistent trust-boundary enforcement:
```rust
if src.id != self.config.dst_id {
    tracing::error!("Skipping received message from unexpected source: {:?}: {payload:?}", src.id);
} else if self_serve::app::v1::RequestState::matches(&payload).is_some() {
    sender_tx.send(self.last_message.clone()).await.wrap_err("Failed to send outgoing message")?;
} else {
    self.handle_message(RelayPayload { src: Some(src), dst, seq, payload: Some(payload) }, message_buffer).await?;
}
```

### Proof of Concept
1. Establish a relay stream connection as any entity able to publish a `RelayConnectResponse`/`RelayPayload` with `payload` matching `self_serve::app::v1::RequestState`, using an arbitrary `src.id` that does not equal the victim client's configured `dst_id`.
2. The client's main loop matches the `RequestState` branch before evaluating the `src.id != self.config.dst_id` condition, and unconditionally sends `self.last_message` back through `sender_tx` [2](#0-1) .
3. The attacker-controlled sender receives a replay of the last message the legitimate client sent, without ever passing the identity check that gates every other message type in the same loop.

Note: I was unable to inspect the relay server implementation (outside this repo/index) to confirm whether server-side routing independently prevents spoofed `src` values from reaching this client; that residual uncertainty affects exploitability but not the fact that the client-side code path itself omits the enforcement present everywhere else in the same function.
