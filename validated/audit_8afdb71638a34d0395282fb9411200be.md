### Title
Missing cleanup of `_requestCommitments` on successful GET-response delivery causes unbounded storage growth in `EvmHost` - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address)` reads and pays out the fee stored in `_requestCommitments[commitment]` when a GET response is successfully delivered to the destination module, but never deletes that mapping entry. This mirrors the QEMU 9p-proxy bug class (CVE-2016-9916): a "missing cleanup operation" on a resource-tracking structure that is reachable by an unprivileged actor (any relayer submitting a GET response), leading to unbounded accumulation of stale state.

### Finding Description
`_requestCommitments` is populated on every outbound `GET`/`POST` dispatch with `FeeMetadata{sender, fee}` [1](#0-0) . For POST and GET timeouts, this metadata is explicitly deleted (`delete _requestCommitments[commitment]`) before the timeout callback runs, and only restored if the app callback fails, guaranteeing eventual cleanup [2](#0-1) [3](#0-2) .

However, in the success path for GET responses — `dispatchIncoming(GetResponse memory response, address relayer)` — the function reads the fee from `_requestCommitments[commitment]`, pays it to the relayer, but performs no `delete _requestCommitments[commitment]` call, leaving the `FeeMetadata` entry permanently in storage even though the request lifecycle has concluded successfully: [4](#0-3) 

Compare this to `dispatchTimeOut(GetRequestTimeout, ...)`, which does perform the delete on the equivalent lifecycle-ending event [2](#0-1) . The success path for GET responses is the outlier: every request that completes normally (the common, expected case) leaves a permanent stale `FeeMetadata` storage slot behind. Because `dispatch(DispatchGet)` is callable by anyone and each dispatched GET request produces a distinct commitment (via a monotonically increasing nonce) [5](#0-4) , an attacker (or ordinary usage at scale) can repeatedly dispatch trivial/cheap GET requests, relay their (self-supplied or third-party) responses to completion, and leave behind unbounded numbers of orphaned storage slots — analogous to the "missing cleanup operation in the proxy backend" causing unbounded host resource consumption in the CVE.

### Impact Explanation
This is a storage-growth/resource-exhaustion issue rather than a fund-theft or consensus-safety issue: it does not enable minting, forged delivery, or unauthorized state mutation. It permanently bloats on-chain storage for `EvmHost`, increasing gas costs for anyone interacting with the contract's storage layout over time and constituting a permanent, uncapped state growth that is reachable from a single unprivileged dispatched GET request/response flow — the class of "resource-only" leak the CVE describes. Per the scoping rules, resource-only leaks are excluded from Medium+ severity unless they cause concrete freezing/theft/unsound state; here the leaked entries do not block subsequent operations, do not freeze funds, and do not corrupt consensus state, so the practical blast radius is limited to storage bloat.

### Likelihood Explanation
Every legitimate GET request/response round trip triggers this omission (not just adversarial ones), and the dispatch path is fully permissionless and cheap to invoke repeatedly, making the leak trivial to trigger at scale.

### Recommendation
Add `delete _requestCommitments[commitment];` in `dispatchIncoming(GetResponse memory response, address relayer)` immediately before or after the relayer fee transfer, mirroring the cleanup performed in `dispatchTimeOut` for `GetRequestTimeout`.

### Proof of Concept
1. Call `dispatch(DispatchGet{...})` on `EvmHost` — this stores `_requestCommitments[commitment] = FeeMetadata{sender, fee}` [1](#0-0) .
2. Have the request delivered normally (via `HandlerV2`/relayer flow) and its `GetResponse` processed via `dispatchIncoming(GetResponse, relayer)` — the fee is paid out but the mapping entry is never deleted [6](#0-5) .
3. Read `_requestCommitments[commitment]` after successful delivery — it still returns the original non-zero `FeeMetadata` instead of being cleared, unlike the analogous timeout path which zeroes it out.
4. Repeat steps 1–3 with new nonces indefinitely to accumulate orphaned storage entries at will.

**Uncertainty note:** I was unable to fully trace whether the `PostResponse` equivalent dispatch path (mentioned in `evm/tests/rust/src/tests/post_response.rs`) has a matching cleanup that the GET path lacks, due to running out of investigation budget; a full review of `evm/src/core/EvmHost.sol` for `dispatchIncoming(PostResponse, ...)` (if it exists) would help confirm whether this omission is unique to the GET-response path.

     * @dev Dispatch an incoming GET response to source module
     * @param response - get response

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatch(DispatchGet memory get) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                get.fee, path, address(this), block.timestamp
            );
        } else if (get.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), get.fee);
        }

        uint64 timeoutTimestamp = get.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(get.timeout);
        GetRequest memory request = GetRequest({
            source: host(),
            dest: get.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            timeoutTimestamp: timeoutTimestamp,
            keys: get.keys,
            height: get.height,
            context: get.context
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: _msgSender(), fee: get.fee});
        emit GetRequestEvent({
            source: string(request.source),
            dest: string(request.dest),
            from: request.from,
            keys: request.keys,
            nonce: request.nonce,
            height: request.height,
            context: request.context,
            timeoutTimestamp: request.timeoutTimestamp,
            fee: get.fee
        });
    }
