### Title
Unallowlisted route venues let a malicious `swap_xdr` execute arbitrary contract code that drains the caller's wallet inside their own auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller forwards caller-supplied `swap` bytes verbatim to the swap router and signs the router's input `transfer` with invoker-contract auth. The router then invokes whatever pool addresses the payload's `assets` registry names — there is no venue allowlist. A hop "pool" can be any contract; nothing constrains its code. Any call it makes that requires the original caller's authorization (e.g. `token.transfer(victim, attacker, amount)`) is recorded as a child of the caller's own auth entry and executes once the caller signs the simulated tree. This is the on-chain analog of remote code injection: an attacker-crafted payload (route XDR) causes the victim's authorization to execute attacker-chosen code, and the routed amounts/min-out do not bound the theft.

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all accept a `swap: StrategySwap` argument built by the caller (or by a quote server the caller trusts). `swap_tokens` at `contracts/controller/src/strategies/swap.rs:34-38` grants exactly one authorization — `transfer(controller → router, amount_in)` — then calls `router.execute_strategy(controller, amount_in, swap)` under the flash guard. The only post-execution checks are `RouterOverspend` / `NoSwapOutput` on the controller's own balances (`swap.rs:41-54`); they say nothing about what the route's venue contracts did under the caller's auth subtree.

The router decodes the payload into an `assets` address registry plus packed ops (`contracts/swap-aggregator/src/program.rs`) and dispatches each hop with `env.invoke_contract(&ctx.hop.pool, "swap"/"swap_exact_amount_in", …)` — see `venues/comet.rs:30-34`, `venues/sushi.rs:48-50`, `venues/phoenix.rs:23-25`. `hop.pool` is an arbitrary `Address` from the payload; no allowlist exists (README: "keeps no allowlist", threat-model.md:154-156). Because the whole transaction executes under the caller's signed invocation tree, a malicious pool's `token.transfer(caller, attacker, wallet_balance)` is recorded as a child of the caller's auth entry and succeeds if the caller signs that tree — which simulation presents as the honest tree for the submitted route.

The test harness proves the primitive end-to-end: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` deploys `RogueHopPool`, whose `swap()` transfers the victim's wallet token to the attacker, and asserts the stolen transfer is recorded under Alice's `swap_collateral` auth entry while the swap still returns a fair `min_out` (lines 194-227).

### Impact Explanation
Theft of user funds beyond the routed amount. The victim's `min_out` and the controller's `RouterOverspend`/`NoSwapOutput` checks bound only the swap's input/output legs; the rogue pool drains an unrelated wallet balance (any token the victim holds and signs for in the auth tree). Severity: Critical-class impact (unbounded wallet theft), gated by the victim signing a poisoned route — typically delivered via a compromised/malicious quote response or phishing route XDR, exactly the "crafted input file" delivery model of the reference advisory.

### Likelihood Explanation
Exploitation requires the victim to sign an authorization tree containing the rogue child. Honest routes never produce such a child (one input-transfer entry only), so wallet-level verification blocks it — but nothing in the contracts enforces it; the defense is purely client-side hygiene (decode `routeXdr`, reject unexpected auth children). Attackers who can influence route construction (malicious frontends, tampered quote relays, or social-engineered XDR) reach this trivially through the permissionless strategy entrypoints.

### Recommendation
- Add a venue allowlist to the router (admin-curated pool/token pairs), or have the controller pin venue addresses per asset.
- At minimum, have the router reject hop pools not registered as known venue contracts for that opcode.
- SDK/API side: enforce and document mandatory verification that the simulated auth tree contains exactly the single input `transfer` child before signing (already partially in `skills/xoxno-swap-aggregator/payload.md`), and ship `verifyRouteBytes`-style checks by default.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
- `RogueHopPool::swap` (lines 62-71) executes `token.transfer(victim, attacker, amount)` against an unrelated wallet token.
- `UnlistedPoolRouter::execute_strategy` (lines 39-47) mirrors the real router: pulls input, invokes the payload-named pool, pays fair `min_out`.
- The test `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` (lines 194-227) shows `swap_collateral(route)` with the attacker's pool as a hop: Alice's wallet goes from `WALLET_BALANCE` to 0, the attacker receives it, the swap still settles `FAIR_OUT_ETH`, and the stolen transfer sits inside Alice's signed `swap_collateral` auth entry. Production reproduction: submit `swap_collateral`/`multiply` with a `swap_xdr` whose `assets` registry maps `idx_a` (the pool) to an attacker contract implementing `swap()` as above.
