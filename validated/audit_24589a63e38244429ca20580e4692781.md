### Title
Emporium CASE 2 stateless ops execute with `msg.sender == Emporium`, letting any unprivileged caller steal assets (e.g. ERC721 LP positions) previously left owned by Emporium — (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` allows a `CircomData.externalActionData.externalActionMetadata` with `EmporiumStack.signerAddress == address(0)` to execute arbitrary `op.endpoint.call(op.callData)` for every "CASE 2" (stateless) operation, with `verifyWallet` performing no signature check whatsoever in that branch. Because `Transferer` (which `EmporiumUpgradeable` inherits) accepts any incoming ERC721/ERC1155 via `onERC721Received`/`onERC1155Received`, any prior stateless op that mints or transfers a non-fungible asset ends up owned by the Emporium contract itself rather than by the originating user. Since the balance/UTXO accounting in `runAction` and in `Hinkal.transact` only tracks the fungible tokens listed in `circomData.erc20TokenAddresses`, a completely unrelated, unprivileged caller can submit their own `transact()` with a crafted CASE 2 op (e.g., `safeTransferFrom(emporium, attacker, tokenId)`) that the target NFT contract accepts because `msg.sender` is Emporium — the current owner — with no accounting or nullifier check ever registering the theft.

### Finding Description
The broken equality is the stated identity: *"every asset or claim created by a user's ops is owned by that user's wallet or stealth address, never by Emporium."* In practice, for CASE 2 (stateless) ops, `EmporiumUpgradeable.runAction` executes:
```
(success, err) = op.endpoint.call{value: op.value}(op.callData);
``` [1](#0-0) 
with `msg.sender` on that call being `address(this)` of `EmporiumUpgradeable`. Any inbound ERC721/ERC1155 transfer during such a call (e.g., a Uniswap-style LP-position mint) is accepted unconditionally because `Transferer` implements permissive receiver hooks: [2](#0-1) 
so that asset becomes owned by Emporium rather than the victim's wallet/stealth address.

`verifyWallet` skips all signature verification when `stack.signerAddress == address(0)`, only marking `emporiumMessage` used: [3](#0-2) 
Nothing constrains the `from`/owner field embedded inside `op.callData` to be the calling user's own address or asset; the only restriction on CASE 2 calldata is a check against `callHinkalWallet`/`doSendToRelay` selectors: [4](#0-3) 

Post-call accounting (`balancesBefore`/`balancesAfter`, `handleOut`) only iterates `circomData.erc20TokenAddresses`: [5](#0-4) 
and `getBalancesForArray` only reads ERC20/ETH balances of listed tokens: [6](#0-5) 
An attacker can submit `circomData.erc20TokenAddresses` with zero relevant entries (or entries unrelated to the NFT), so the theft of the NFT is invisible to both `Hinkal.transact`'s balance/slippage/UTXO-sum checks: [7](#0-6) 
and to `runAction`'s own balance-change tracking. No nullifier tied to the victim's asset is spent by the attacker's proof — the attacker only proves ownership of their own (possibly zero-value) UTXOs and a valid `emporiumMessage`/`calldataHash`, none of which constrain the arbitrary `op.callData` content.

Exploit flow:
1. Victim performs a normal `transact()` with `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and a CASE 2 op that mints or receives an ERC721 (e.g., a Uniswap V3 LP NFT) — the NFT ends up owned by `emporium` because the low-level call in `runAction` runs with `msg.sender == emporium`, and the mint/receive succeeds via `Transferer.onERC721Received`.
2. Attacker (any unprivileged EOA with their own UTXOs, or even trivial dummy inputs) crafts a `CircomData` with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` decoding to an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: victimNFTContract, invokeWallet: false, callData: abi.encodeCall(safeTransferFrom, (emporium, attacker, victimTokenId))}]}`.
3. Attacker calls `Hinkal.transact` with a valid proof for their own inputs; `verifyProof`/`rootHashExists`/`performHinkalChecks` all pass since they only constrain the attacker's own fields, not the semantics of `op.callData`.
4. `runAction` calls `verifyWallet` (no-op check on signature since `signerAddress == 0`), then executes the CASE 2 op: `victimNFTContract.call(safeTransferFrom(emporium, attacker, tokenId))`. Inside the NFT contract, `msg.sender == emporium`, which is the current token owner/approved party, so the transfer succeeds.
5. The victim's nullifiers/UTXOs are untouched; the attacker's own nullifiers are spent for an unrelated no-op. The NFT is now owned by the attacker.

### Impact Explanation
Direct theft of a victim's in-flight, protocol-side asset (LP position/NFT/vault share/permit2 allowance/locked stake) that was left owned by the Emporium contract by any prior user, executed by an unrelated, unprivileged attacker with no signature, no nullifier spend tied to the asset, and no accounting trip-wire, since the stolen asset type is outside the tracked `erc20TokenAddresses`/UTXO balance model. This is Critical: direct theft of in-flight user funds/assets, executing a state-changing transfer that the asset's original creator/owner never authorized.

### Likelihood Explanation
Preconditions: at least one prior CASE 2 op (by any victim, including protocol-encouraged flows like LP-position minting via Emporium) that results in Emporium owning a non-fungible or otherwise untracked asset. Given `Transferer`'s unconditional `onERC721Received`/`onERC1155Received` acceptance and the design of stateless (CASE 2) ops explicitly permitting arbitrary `endpoint.call(callData)`, this precondition is very plausible in normal integrations that use Emporium for external protocols returning NFTs/receipts. The attack itself costs only a valid Hinkal proof over trivial/self-owned inputs and standard gas; it is repeatable against every future asset left in Emporium by any user, and against every un-tracked asset type Emporium ever touches.

### Recommendation
- Disallow anonymous/unsigned (`signerAddress == address(0)`) CASE 2 ops from calling arbitrary endpoints with attacker-chosen calldata; require CASE 2 stateless calls to be scoped (e.g., allow-list of selectors/endpoints, or enforce that any `from`/`owner` argument encoded in `callData` matches `msg.sender`'s stealth address or the current transactor).
- Never let non-fungible/receipt assets be owned by `EmporiumUpgradeable` itself; instead force all "receive" callbacks to route to a per-user `HinkalWallet` (CASE 1, stateful), removing `onERC721Received`/`onERC1155Received` acceptance from the base `Emporium` contract, or immediately forward any received NFTs to the signer's wallet within the same op.
- Extend the balance/UTXO accounting model to also constrain non-fungible transfers so unexpected asset movement out of Emporium reverts the transaction unless properly attributed to a UTXO output.

### Proof of Concept
Foundry fork test plan:
1. Deploy a mock ERC721 "position manager" and register a mock `Emporium`/`EmporiumUpgradeable` proxy as an allowed recipient in `Hinkal`.
2. Victim: build `CircomData` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = `EmporiumStack{signerAddress: address(0), ops: [{endpoint: positionManager, invokeWallet: false, callData: mint(...) -> mints tokenId=1 to emporium}]}`, generate a valid proof for victim's own inputs, call `Hinkal.transact(...)`. Assert `positionManager.ownerOf(1) == address(emporium)`.
3. Attacker: build a separate `CircomData` (own inputs/nullifiers, unrelated `erc20TokenAddresses`), `externalActionMetadata` = `EmporiumStack{signerAddress: address(0), ops: [{endpoint: positionManager, invokeWallet: false, callData: safeTransferFrom(emporium, attacker, 1)}]}`, generate a valid proof for attacker's own inputs, call `Hinkal.transact(...)`.
4. Assert `positionManager.ownerOf(1) == attacker` after the attacker's transaction, and assert the victim's nullifiers (`nullifiers[victimNullifier]`) were never touched by the attacker's transaction — proving the NFT moved with no attribution to any UTXO/nullifier belonging to attacker or victim for this asset.
