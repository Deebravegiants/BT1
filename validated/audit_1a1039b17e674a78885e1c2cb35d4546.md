## Finding

### Title
Predicted multisig-account address becomes permanently unclaimable if the creator's sequence number shifts before creation, permanently locking pre-funded assets - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The Frankencoin bug is rooted in a custody invariant: **an address that a user relies on in advance for depositing funds must remain bound to the exact deployment/creation event the user expects; if a chain reorg or execution-order change lets a different actor/event consume the nonce that determines that address, deposited funds can be stolen or lost.** Aptos's `multisig_account` module exposes `get_next_multisig_account_address` explicitly as a “predicted address … for pre-funding," yet the resource-account address it predicts is derived from the creator's live `sequence_number`, which is not fixed until the actual `create_multisig_account` transaction executes. This is the same nonce-binding hazard as Frankencoin's `create`-based clone deployment, adapted to Aptos's resource-account model, and it produces a permanent-lock custody failure rather than mere unpredictability.

### Finding Description
`get_next_multisig_account_address` is documented as returning "the predicted address for the next multisig account if created from the given creator address": [1](#0-0) 

Internally it uses the creator's **current** sequence number as the nonce fed into resource-address derivation:
```
let owner_nonce = account::get_sequence_number(creator);
create_resource_address(&creator, create_multisig_account_seed(to_bytes(&owner_nonce)))
```

The actual account creation, `create_multisig_account`, computes the same nonce **at execution time**, not at the time the caller queried the prediction: [2](#0-1) 

The resource account itself is created via `account::create_resource_account`, whose address is `sha3_256(source || seed || DERIVE_RESOURCE_ACCOUNT_SCHEME)`: [3](#0-2) 

Because `owner_nonce` equals the creator's sequence number *read at transaction execution time*, any transaction from the same creator account that lands before the intended `create_multisig_account` transaction (a race between two of the user's own transactions, mempool reordering, or a chain reorg that changes which of the user's transactions executes first) increments the sequence number. The address that was previously computed off-chain via `get_next_multisig_account_address` (for nonce `N`) is then never produced by `create_multisig_account` — the module will use nonce `N+1` (or later) instead, since sequence numbers are strictly monotonic and never replayed.

If a depositor (or the multisig owner setting up initial funding — a pattern this API is designed to support) sends APT/FA to the address predicted for nonce `N` *before* the creation transaction confirms, and the nonce shifts, that address is never converted into a resource account. Any address without an `Account` resource that receives a transfer is auto-created via `account::create_account_unchecked`, which sets `authentication_key = bcs::to_bytes(new_address)` — i.e., no one holds a matching private key: [4](#0-3) 

The only way to ever gain a signer over that address is for the *same* creator to call `create_resource_account` with `owner_nonce == N` again — impossible, since Aptos sequence numbers never decrease or repeat: [5](#0-4) 

The framework's own comment on `create_resource_account` acknowledges the "claim ahead of creation" pattern is expected and handled for the *matching* nonce, but provides no protection when the nonce diverges from what was predicted.

### Impact Explanation
Assets sent to the address returned by `get_next_multisig_account_address` become **permanently and non-recoverably locked** if the predicting nonce is consumed by a different transaction from the creator before the intended `create_multisig_account` call executes. This matches the custody-gate criterion "Permanent lock or non-recoverable loss of … resource-account-held value." Unlike the Frankencoin case (theft by a third party), here the corrupted value is destroyed custody: no signer, including the legitimate creator, can ever produce authority over the pre-funded address again.

### Likelihood Explanation
This does not require an adversary at all — any of the following common events cause it:
- The creator submits or has pending any other transaction (fee bump, unrelated transfer, batched operation) before `create_multisig_account` is included.
- Transaction reordering/expiry causes a different transaction from the creator to be sequenced first.
- A validator/mempool reordering or short reorg changes execution order of the creator's own transactions.

Because `get_next_multisig_account_address` is a public, documented "predicted address" API intended for pre-funding workflows, the likelihood of dApps/users relying on it and losing funds to any transaction-ordering perturbation is realistic, not merely theoretical (making it arguably more likely to trigger than the EVM reorg scenario in the original report, which required an actual chain reorg).

### Recommendation
Do not expose or encourage pre-funding of an address derived from a mutable, execution-time-read nonce (`sequence_number`) that can silently advance between prediction and creation. Options:
- Require `create_multisig_account` to take an explicit, caller-committed nonce (verified against the account's sequence number at call time, aborting if it no longer matches the value used off-chain), so pre-funding failures abort loudly instead of silently orphaning funds.
- Or, deterministically reserve/lock the nonce at prediction time via an on-chain commitment, analogous to using `CREATE2` with a caller-chosen salt in the Frankencoin fix, decoupling the derived address from any value that can be advanced by unrelated transactions.
- At minimum, prominently document that `get_next_multisig_account_address` is unsafe for pre-funding and add a guard in `create_resource_account`/`create_multisig_account` to detect and refund/reclaim value stranded at skipped-nonce addresses.

### Proof of Concept
1. Alice's account has `sequence_number = 5`. She calls the view function `get_next_multisig_account_address(alice)`, which computes `owner_nonce = 5` and returns predicted address `A`.
2. A depositor (or Alice herself, following the documented "pre-fund the predicted multisig" pattern) sends APT to address `A`. Since `A` has no `Account` resource, `aptos_account::transfer`/`deposit_coins` auto-creates a bare account there via `create_account_unchecked`, whose `authentication_key` is simply `A`'s own bytes — controlled by no private key.
3. Before Alice's `create_multisig_account` transaction lands, another transaction from Alice's account executes (e.g., a routine transfer, a retried/duplicate submission, or transaction reordering from a reorg), advancing her sequence number to `6`.
4. Alice's `create_multisig_account` transaction now executes with `owner_nonce = 6` (per `multisig_account.move:1489`), producing multisig account address `B ≠ A`.
5. Address `A` never becomes a multisig account and can never be recreated with `owner_nonce = 5` again, since Alice's sequence number is now `≥ 6` and strictly increasing. The APT sent to `A` in step 2 is permanently locked with no recovery path for Alice, the intended owners, or the depositor.

    public fun create_resource_address(source: &address, seed: vector<u8>): address {
        let bytes = bcs::to_bytes(source);
        bytes.append(seed);
        bytes.push_back(DERIVE_RESOURCE_ACCOUNT_SCHEME);
        from_bcs::to_address(hash::sha3_256(bytes))
    }
