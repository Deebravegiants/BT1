### Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong `txHash`/status to be reported for batched same-token withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`describeWithdrawal()` and the analogous `waitForWithdrawalCompletion()` in `internal-utils` determine the completion status of a specific withdrawal by looking up the POA bridge indexer's response list and matching **only** on the token's `assetId` (`nep141:<near_token_id>`), via `findMatchingWithdrawal`. When a caller submits a batch withdrawal (`WithdrawalParams[]`) that includes two or more withdrawals of the same token (e.g., same asset, different destination addresses/amounts), this matching is ambiguous: `Array.prototype.find` returns the *first* array element whose `near_token_id` matches, regardless of which withdrawal in the batch it actually corresponds to.

### Finding Description
`describeWithdrawal` fetches the full list of withdrawals for a NEAR transaction hash and picks the one to report on solely via:

```
function findMatchingWithdrawal(withdrawals, assetId) {
  return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [2](#0-1) 

This is called for each entry of a batch withdrawal via `createWithdrawalCompletionPromises`, which iterates `withdrawalParams` by `index` and independently asks each bridge to `describeWithdrawal`/`watchWithdrawal` for that specific withdrawal's parameters [3](#0-2) . The comment in the code explicitly acknowledges the limitation: "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) . The identical pattern and caveat exist in `internal-utils`'s `waitForWithdrawalCompletion` [5](#0-4) .

The equality that should hold is: *the status/txHash reported for withdrawal index `i` (destination address `A`, amount `X`) must equal the on-chain outcome for that exact withdrawal.* Because matching ignores `destinationAddress`, `amount`, and index/order, when two withdrawals of the same token exist in one batch, `describeWithdrawal` for withdrawal #2 (still pending, destined for address `B`) can return the `COMPLETED` status and `transfer_tx_hash` belonging to withdrawal #1 (destined for address `A`). This is confirmed by the project's own tests, which assert matching happens "by assetId, not by index" [6](#0-5)  — but no test covers the case where the *same* assetId appears twice for two distinct destination addresses in a single batch, which is exactly the ambiguous/incorrect scenario.

### Impact Explanation
An integrator that relies on `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises` to determine when a specific withdrawal in a batch has landed on the destination chain can be told that a still-pending or failed withdrawal is "completed", with a `txHash` that actually belongs to a different withdrawal of the same token in the batch. This is a status/hash misreport that could cause an integrator to prematurely credit a user or a system as though funds had arrived at a specific destination, when in fact that destination never received anything (double-credit / wrong on-chain outcome reported), matching the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
This requires no privileged access and no malicious relayer/RPC — a completely ordinary integrator use of the batch withdrawal API (`processWithdrawal`/`signAndSendWithdrawalIntent` + `createWithdrawalCompletionPromises`) with two withdrawals of the same POA-bridge token in the same NEAR transaction triggers it. The condition (duplicate `assetId` in one batch) is plausible for normal usage (e.g., paying out the same token to two different recipients in one batch) and is not blocked or validated anywhere in `signAndSendWithdrawalIntent` or `createWithdrawalIdentifiers`.

### Recommendation
Disambiguate matching in both `findMatchingWithdrawal` implementations (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) by also matching on `destinationAddress`/`amount` (and `destinationMemo` if applicable), or by consuming matched withdrawals so the same indexer entry cannot be reused for multiple local withdrawal params. At minimum, throw/assert when the match is ambiguous (i.e., more than one candidate withdrawal shares the same `assetId` within the returned list) rather than silently taking the first result.

### Proof of Concept
1. Submit a batch withdrawal via `signAndSendWithdrawalIntent` containing two `WithdrawalParams` for the same `assetId` (e.g., `nep141:btc.omft.near`), one to `destinationAddress: A` and one to `destinationAddress: B`, in a single NEAR transaction.
2. Call `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` for both entries.
3. Suppose the POA bridge indexer processes withdrawal to `A` first and marks it `COMPLETED` with `transfer_tx_hash: "tx-A"`, while the withdrawal to `B` is still `PENDING`.
4. Because `findMatchingWithdrawal` matches only by `assetId`, the call describing withdrawal index `1` (destined for `B`) can also match the first entry in the returned array (destined for `A`) and return `{ status: "completed", txHash: "tx-A" }` — falsely reporting that `B`'s withdrawal completed, using a transaction hash that never paid `B`. 		args: WithdrawalIdentifier & { logger?: ILogger },

		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
