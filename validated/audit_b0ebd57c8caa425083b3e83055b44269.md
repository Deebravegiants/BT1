### Title
`findMatchingWithdrawal` matches only by `assetId`, causing two same-token withdrawals in one batch to report the same status/txHash - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a withdrawal by looking up the POA bridge's status response using `findMatchingWithdrawal`, which matches solely on `nep141:${w.data.near_token_id} === assetId` and disregards `amount`, `destinationAddress`, and the `WithdrawalIdentifier.index`. When a single signed intent contains two withdrawals of the same PoA token (e.g., two `nep141:btc.omft.near` withdrawals to different `destinationAddress`), both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` resolve to the same (first-matching) record, so index 1 can report index 0's `txHash`.

### Finding Description
The equality that must hold is: `(status, txHash)` returned for withdrawal at `index=i` must equal the actual on-chain outcome of the `i`-th signed withdrawal for that user. Instead, `findMatchingWithdrawal` at [1](#0-0) returns `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`, ignoring `w.data.amount`/`destination_address` entirely, and the code comment explicitly acknowledges "multiple withdrawals of the same token in a single transaction are not supported" [2](#0-1) .

`describeWithdrawal` calls this matcher using only `args.withdrawalParams.assetId`, never `args.index` or `args.withdrawalParams.destinationAddress`/`amount`, even though `WithdrawalIdentifier` carries a unique `index` per bridge route and full `withdrawalParams` [3](#0-2) . The `index` field is populated correctly upstream by `createWithdrawalIdentifiers`, which assigns a per-bridge sequence number to each withdrawal in a batch [4](#0-3) , but this index is never consumed to disambiguate which POA API record belongs to which withdrawal — `watchWithdrawal` simply forwards `args.wid` (including `index`) into `describeWithdrawal` and trusts the returned `status`/`txHash` [5](#0-4) .

Attacker input: an ordinary user submits one intent with two withdrawal legs of the same token (`assetId = "nep141:btc.omft.near"`) but different `destinationAddress` (their own two wallets, or a wallet plus an integrator-supplied address). Both legs are valid, signed, and processed by the intents contract. When the integrator later polls status for each `WithdrawalIdentifier` (index 0 and 1), the SDK returns the identical first-matching POA record's `txHash` for both, even though the underlying `transfer_tx_hash` values differ per destination.

No existing guard prevents this: `validateWithdrawal`, `compareAddresses`, and `supports()` all operate per single withdrawal and do not check for duplicate assetIds across a batch; the intents contract's nonce/signature checks are orthogonal to this off-chain status-matching bug.

### Impact Explanation
This causes a status/hash misreport: the integrator watching withdrawal index 1 receives the `txHash` that actually belongs to withdrawal index 0's payout (to a different `destinationAddress`). An integrator that credits or refunds a user's off-chain ledger based on this misreported hash could double-credit the same on-chain payout against two logical withdrawal records, or incorrectly conclude withdrawal 1 has completed when its actual on-chain transfer status/hash is different or still pending. This matches the "High" impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Precondition: a single intent (or batch withdrawal call) must contain ≥2 withdrawals of the same PoA-bridged `assetId` with different `destinationAddress`/`amount`. This is a normal, permitted usage pattern (the SDK's batch withdrawal path explicitly assigns sequential indices per bridge route for exactly this case). Any ordinary user can trigger it at will with no special privilege, and it is fully repeatable on every batch that repeats a token.

### Recommendation
Update `findMatchingWithdrawal` to disambiguate by more than `assetId` — e.g., match by `assetId` + `destinationAddress` + `amount`, and additionally maintain per-assetId ordering/consumption (e.g., track already-consumed indices) so repeated calls for different `index` values of the same token don't collapse to the same record. Since the POA API response is unsorted and doesn't expose a stable per-request correlation ID, the safest fix is to sort candidates matching `assetId` by `amount` (matching the sorted order of `withdrawalParams`, since relayer fees are equal for same token, so relative amount ordering is preserved) and pick the `index`-th one among same-asset withdrawals, rather than always the first `find` result.

```ts
// vitest, mocking only poaBridge.httpClient.getWithdrawalStatus
import { describe, it, expect, vi } from "vitest";
import { PoaBridge } from "./poa-bridge";
import * as poaBridgeModule from "@defuse-protocol/internal-utils";

it("misattributes txHash between two same-token withdrawals", async () => {
  vi.spyOn(poaBridgeModule.poaBridge.httpClient, "getWithdrawalStatus")
    .mockResolvedValue({
      withdrawals: [
        {
          status: "COMPLETED",
          data: {
            near_token_id: "btc.omft.near",
            transfer_tx_hash: "HASH_FOR_WITHDRAWAL_0",
            destination_address: "addrA",
            amount: "100",
          },
        },
        {
          status: "COMPLETED",
          data: {
            near_token_id: "btc.omft.near",
            transfer_tx_hash: "HASH_FOR_WITHDRAWAL_1",
            destination_address: "addrB",
            amount: "200",
          },
        },
      ],
    });

  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const wid0 = { landingChain: "btc", index: 0,
    withdrawalParams: { assetId: "nep141:btc.omft.near", amount: 100n, destinationAddress: "addrA", feeInclusive: true },
    tx: { hash: "txhash", accountId: "acc" } };
  const wid1 = { landingChain: "btc", index: 1,
    withdrawalParams: { assetId: "nep141:btc.omft.near", amount: 200n, destinationAddress: "addrB", feeInclusive: true },
    tx: { hash: "txhash", accountId: "acc" } };

  const status0 = await bridge.describeWithdrawal(wid0);
  const status1 = await bridge.describeWithdrawal(wid1);

  // BUG: both resolve to the SAME record (the first match), despite differing destinationAddress/amount
  expect(status0).toEqual({ status: "completed", txHash: "HASH_FOR_WITHDRAWAL_0" });
  expect(status1).toEqual({ status: "completed", txHash: "HASH_FOR_WITHDRAWAL_0" }); // should be HASH_FOR_WITHDRAWAL_1
});
```

```typescript
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
