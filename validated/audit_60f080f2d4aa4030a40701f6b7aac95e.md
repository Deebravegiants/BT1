### Title
Dangling ERC-20 approvals left by attacker-controlled predispatch/postdispatch calldata let anyone drain future funds routed through the shared `CallDispatcher` - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`IntentGatewayV2.placeOrder` and its fill/settlement paths route arbitrary, order-author-supplied `Call[]` batches through a single, persistent `CallDispatcher` instance to perform swap-then-escrow (predispatch) and fill-then-act (postdispatch) logic [1](#0-0) . The dispatcher executes whatever calldata the order places, including `approve()` calls to arbitrary spender addresses, in its own contract context (not via delegatecall) [2](#0-1) . Because the dispatcher is shared across all orders and all callers, an unprivileged user can place a single order whose predispatch calldata grants an unlimited allowance on some token to an attacker-controlled address, matching the "authorized spending contract" pattern in the external report where a previously-approved spender is later reused to sweep funds routed through the shared contract.

### Finding Description
`placeOrder`'s predispatch phase transfers only the `predispatch.assets` into the dispatcher, executes the attacker-supplied `Call[]`, and then sweeps back **only the tokens that appear in `order.inputs`**, based on the dispatcher's balance at that point [3](#0-2) . If the predispatch calldata approves a spender for a token that is not itself one of `order.inputs` (e.g., an intermediate swap-path token, or a token the attacker deliberately leaves partially unspent by controlling the swap output), that approval and any resulting leftover balance are never revoked or swept — the dust-accounting logic only compares `received` for `order.inputs[i]` tokens, not for arbitrary tokens the predispatch calldata may have interacted with [4](#0-3) .

The docs explicitly acknowledge this design hazard: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution" [5](#0-4)  — but this is only a documentation-level caution; nothing in `CallDispatcher.dispatch` or in `IntentGatewayV2.placeOrder`/`_execute` resets approvals or enforces exact-amount approvals on-chain [2](#0-1) . The postdispatch sweep path (`_execute` in `IntentsBase.sol`) does sweep residual balances of `order.output.assets` tokens and emits `DustCollected` [6](#0-5) , but it never revokes any standing `approve()` grants the attacker's calldata issued to third-party spenders, and it also only iterates over the specific `outputsLen` tokens declared in that order, not any arbitrary token the calldata may have approved.

This mirrors the external report's root cause: a trusted, shared dispatching contract (the report's "Authorized Spending Contract" / `AllowanceTarget`) retains a standing allowance to a helper/spender, and that allowance is later reused — independent of any specific victim transaction — to pull whatever balance subsequently lands in the shared contract. Here, the `CallDispatcher` plays the role of `AllowanceTarget`: any unprivileged order placer can grant a dangling approval to an address they control, and later reclaim any balance of that token that subsequently accumulates in the dispatcher (via `transferFrom`), whether from protocol dust, other orders' predispatch/postdispatch flows, or leftover swap change.

### Impact Explanation
Funds that transiently or permanently reside in the shared `CallDispatcher` (predispatch swap change, un-swept postdispatch dust, or any balance left by an interrupted/partial fill) can be siphoned by any address that was granted a standing approval via a prior malicious order's calldata. Since the dispatcher is a single long-lived contract used by every order across the gateway, this is not confined to the attacker's own funds — it constitutes unauthorized draining of protocol/dust and any token balance the dispatcher subsequently holds, satisfying the "concrete theft" bar for a Medium/High-severity finding.

### Likelihood Explanation
Placing a predispatch order with attacker-chosen `Call[]` calldata (including `approve`) is a single, unprivileged `placeOrder` transaction available to any address — no privileged role, governance, or off-chain compromise is required [7](#0-6) . The attacker only needs to also control (or route the swap through) a pool/protocol call that leaves a nonzero residual balance of the approved token in the dispatcher, which is achievable by controlling the swap path/liquidity or by simply under-spending a deliberately inflated predispatch asset amount.

### Recommendation
- Have `CallDispatcher.dispatch` (or a wrapper) revoke/reset to zero any non-zero allowances the dispatcher granted to third parties before returning, or restrict `approve` calls to only the exact amount actually consumed in the same call batch.
- In `IntentGatewayV2.placeOrder`'s predispatch phase and in `_execute`'s postdispatch sweep, sweep and account for **all** tokens touched by the predispatch/postdispatch calldata (not just `order.inputs`/`order.output.assets`), and emit `DustCollected` for any of them.
- Consider making `CallDispatcher` ephemeral (deployed per-order via `CREATE2`/`CREATE` and self-destructed or made single-use) so no approval or balance state persists across orders.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `predispatch.assets = [{token: TOKEN_A, amount: X}]` and `predispatch.call` encoding two calls executed by the `CallDispatcher`: (a) `TOKEN_A.approve(attackerSpender, type(uint256).max)`, and (b) a swap through an attacker-influenced pool/path that intentionally consumes less than `X` of `TOKEN_A`, so a non-`order.inputs` residual of `TOKEN_A` remains on the dispatcher after the swap.
2. `order.inputs` is declared as `TOKEN_B` (the swap output), so `placeOrder`'s sweep phase only pulls `TOKEN_B` back to the gateway; the `TOKEN_A` residual and its unlimited allowance to `attackerSpender` are left untouched on the `CallDispatcher` [4](#0-3) .
3. At any later time, whenever the `CallDispatcher`'s `TOKEN_A` balance is nonzero again (e.g., protocol dust accrual from later orders, or attacker sends more `TOKEN_A` to the dispatcher directly), `attackerSpender` calls `TOKEN_A.transferFrom(CallDispatcher, attacker, balance)` using the still-valid unlimited approval from step 1, draining it without any further authorization from the dispatcher or its governance.

Note: full exploitation depends on the exact liquidity/pool the attacker can force the predispatch calldata to route through and on the dispatcher subsequently receiving further `TOKEN_A` balance; this was not runnable in this environment, and the described PoC is derived purely from static code review of `IntentGatewayV2.sol`, `IntentsBase.sol`, and `CallDispatcher.sol`.

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
