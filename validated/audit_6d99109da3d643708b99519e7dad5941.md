### Title
`TokenExchange.exchange_token` accepts non-admin-issued session tokens (missing `iss` binding check) - ([File: lib/shopify_api/auth/token_exchange.rb](lib/shopify_api/auth/token_exchange.rb))

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` decodes a JWT session token and, as long as the signature and `aud`/`exp`/`nbf` checks pass, forwards it to Shopify's `/admin/oauth/access_token` token-exchange endpoint together with the app's `client_secret` to obtain a full merchant access token. It never checks the `iss` claim to confirm the token was actually issued for the **admin** embedded-app surface, even though `ShopifyAPI::Auth::JwtPayload` already computes this distinction internally (`admin_session_token?`) but only uses it for an unrelated helper (`shopify_user_id`).

### Finding Description
`JwtPayload#initialize` validates the JWT signature and the `aud` claim against `Context.api_key`: [1](#0-0) 

It also privately determines whether the token's `iss` claim indicates an admin session token: [2](#0-1) 

`admin_session_token?` is only consulted from `shopify_user_id`, never exposed or enforced anywhere else. `TokenExchange.exchange_token` uses the payload solely to extract `shop` (the `dest` claim) and never checks `iss`: [3](#0-2) 

Shopify issues signed session tokens (all HS256-signed with the app's `client_secret`/`api_secret_key`) to multiple non-admin embedded surfaces as well — e.g. Checkout UI Extensions, Customer Account UI Extensions — where `iss` ends in `/checkouts` or another non-`/admin` path (as shown in `test_decode_jwt_payload_coming_from_checkout_ui_extension`, `iss: "https://test-shop.myshopify.io/checkouts"`): [4](#0-3) 

Because these tokens share the same `aud` (the app's client id) and a `dest` matching the shop domain, they pass every check `exchange_token` performs, and the code proceeds to call Shopify's token-exchange endpoint with the app's `client_id`/`client_secret` and the caller-supplied token as `subject_token`: [5](#0-4) 

The intended identity binding is: *"a session token accepted by `exchange_token` == a session token issued for the app's admin embedded surface (`iss` ends with `/admin`)."* That binding is never checked — any Shopify-issued JWT for the same app/shop (regardless of `iss` surface) is treated as equivalent.

### Impact Explanation
Checkout UI Extensions and Customer Account UI Extensions run client-side JavaScript in the buyer's browser and can obtain a Shopify-signed session token for the app via `useSessionToken()`/`useSubscription()` APIs. An unprivileged buyer (or any script on that page) can extract this token and hand it to a host app's backend endpoint that calls `ShopifyAPI::Auth::TokenExchange.exchange_token`. Because the gem does not enforce the admin-surface binding, this buyer-obtainable token can be exchanged for a full offline or online merchant access token — a privilege escalation from buyer-level, unprivileged access to merchant-level API access, i.e. authentication bypass / theft of a merchant access token, which falls into the Critical impact bucket defined in the rules.

### Likelihood Explanation
Exploitation only requires:
1. Access to any Shopify-issued, non-admin session token for the target app/shop (obtainable by any buyer visiting checkout on a shop that installed the app, if the app also renders a checkout/customer-account extension).
2. A host application backend that calls `exchange_token` with attacker-suppliable `session_token` input (a common and documented integration pattern for token exchange).

No access to `api_secret_key`, no privileged account, and no credential leakage is required by the attacker — only the gem's failure to validate `iss`. This is a realistic misuse path given the gem's documented API surface, not a hypothetical one.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, after constructing `jwt_payload`, enforce that the token was issued for the admin surface before proceeding, e.g. expose and check `jwt_payload.admin_session_token?` (or equivalent) and raise `ShopifyAPI::Errors::InvalidJwtTokenError` otherwise. This restores the binding between "token accepted for token-exchange" and "token issued for the admin embedded app surface."

### Proof of Concept
1. As a shop visitor, load a checkout page (or customer-account page) served by an app that also has a Checkout UI Extension / Customer Account UI Extension registered, and obtain the extension's session token (`iss` ending in `/checkouts` or similar), e.g. as constructed in the test fixture:
```ruby
payload = {
  iss: "https://test-shop.myshopify.io/checkouts",
  dest: "https://test-shop.myshopify.io",
  aud: <app_client_id>,
  sub: "gid://shopify/Customer/123456789",
  exp: Time.now.to_i + 10,
  nbf: Time.now.to_i, iat: Time.now.to_i, jti: "x",
}
token = JWT.encode(payload, <app_client_secret>, "HS256")  # produced by Shopify, not the attacker
```
2. Send this `token` to the host app's server endpoint that calls:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
3. `JwtPayload.new(token)` succeeds (valid signature, `aud` matches, not expired) and `exchange_token` forwards `client_id`/`client_secret`/`subject_token` to `/admin/oauth/access_token`, receiving back a merchant offline access token — despite the subject token never having been issued for the admin surface.

**Caveat:** I could not fully verify from the gem alone whether Shopify's token-exchange endpoint server-side also rejects non-admin `iss` tokens (that check happens on Shopify's servers, outside this repo's code), so the exploitability depends partly on server-side behavior I cannot confirm from this codebase; the finding is scoped to the gem's own missing client-side validation of the `iss` binding, which is the control this library is otherwise seen enforcing elsewhere (`aud` check) and documents no other mitigation for.

        def exchange_token(session_token:, requested_token_type:, shop: nil)
          unless ShopifyAPI::Context.setup?
            raise ShopifyAPI::Errors::ContextNotSetupError,
              "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for private apps." if ShopifyAPI::Context.private?
          raise ShopifyAPI::Errors::UnsupportedOauthError,
            "Cannot perform OAuth Token Exchange for non embedded apps." unless ShopifyAPI::Context.embedded?

          # Validate the session token and use the shop from the token's `dest` claim
          jwt_payload = ShopifyAPI::Auth::JwtPayload.new(session_token)
          dest_shop = jwt_payload.shop

          if shop
            ShopifyAPI::Logger.deprecated(
              "The `shop` parameter for `exchange_token` is deprecated and will be removed in v17. " \
                "The shop is now always taken from the session token's `dest` claim.",
              "17.0.0",
            )
          end

          shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)
          body = {
            client_id: ShopifyAPI::Context.api_key,
            client_secret: ShopifyAPI::Context.api_secret_key,
            grant_type: TOKEN_EXCHANGE_GRANT_TYPE,
            subject_token: session_token,
            subject_token_type: ID_TOKEN_TYPE,
            requested_token_type: requested_token_type.serialize,
          }

          if requested_token_type == RequestedTokenType::OFFLINE_ACCESS_TOKEN
            body.merge!({ expiring: ShopifyAPI::Context.expiring_offline_access_tokens ? 1 : 0 })
          end

          client = Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => error
            if error.code == 400 && error.response.body["error"] == "invalid_subject_token"
              raise ShopifyAPI::Errors::InvalidJwtTokenError, "Session token was rejected by token exchange"
            end

            raise error
          end
