Based on my investigation, I found a genuine identity-binding gap analogous to the reported bug class.

### Title
Webhook HMAC signature does not cover the `shop-domain` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (tenant identifier) is read from an unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity passed to the host application's handler, without that value ever being covered by the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) 

`Registry.process` validates the HMAC against the raw body via `Utils::HmacValidator.validate`, and — once that check passes — forwards `request.shop` straight to the handler as the authoritative tenant identity, with no additional binding between the signed body and the claimed shop: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's single shared `api_secret_key`: [4](#0-3) 

Because a single app-level `client_secret`/`api_secret_key` is shared across every shop that installs the app, an HMAC that is valid for one shop's webhook body is also a valid HMAC for the *same body* delivered with a *different* `shop-domain` header — the signature says nothing about which tenant the payload belongs to. This breaks the intended binding: `shop claimed in header == shop the signature actually authenticates`. In the actual Shopify webhook protocol this binding is expected to hold implicitly because only Shopify's servers deliver webhooks with correct headers; but this gem does not independently enforce or re-derive the shop from signed content, so any consumer relying solely on `Registry.process`/`request.shop` for tenant scoping inherits this gap.

This is the same class of defect as the reported Algebra bug: an action (attributing/consuming payload data to a specific tenant) is allowed to proceed using a field (`shop`) that is not actually covered by the integrity/identity check (`hmac`) guarding that action.

### Impact Explanation
If an attacker who controls one tenant (a legitimate shop with the app installed, or any principal who can obtain one genuine `(body, hmac)` pair signed with the app's secret — e.g., by triggering a webhook on their own store) replays that exact body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header, `Utils::HmacValidator.validate` still returns true (it never inspects the header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Any host application that uses `request.shop` (or the `shop` field of `WebhookMetadata`) to select which tenant's records to create/update/delete based solely on this gem's webhook verification is exposed to cross-tenant data injection/corruption — meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation only requires network access to the app's public webhook endpoint (no access token, no `api_secret_key`, no privileged account) plus one legitimate signed body from any tenant using the same app installation — which is realistically obtainable by installing the app on an attacker-controlled dev/trial store and triggering a webhook for a topic whose payload doesn't itself encode the originating shop in a way the host app cross-checks.

### Recommendation
Bind the tenant identity into the signed material or otherwise cross-verify it: e.g., have `Registry.process` (or `HmacValidator`) require and validate the shop against session/registration state known independently for that shop, or document/require that consuming applications independently verify `request.shop` against an authenticated session before trusting it, rather than trusting the header once HMAC-of-body passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook topic (e.g., `orders/create`) and capture the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's shared secret).
2. Send a forged HTTP request to the app's webhook endpoint with `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H`, and body `B`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully [5](#0-4) , `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because it only checks `B` against `H` [6](#0-5) , and the handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
