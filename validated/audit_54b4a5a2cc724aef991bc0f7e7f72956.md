### Title
TOCTOU race in `createMany`/`#persistWalletAccounts` full-snapshot merge allows a concurrent `#replaceAll` (fusion sync) disable/remove of a hardware wallet account to be reverted - ([File: features/wallet-accounts/src/module/wallet-accounts.ts])

### Summary
`createMany` and `#replaceAll` are each wrapped in their own independent `makeConcurrent({ concurrency: 1 })` queue, so they can execute concurrently with respect to each other. `createMany` builds its "walletAccounts" payload as a full snapshot (`{...currentWalletAccounts}` plus the new entry) rather than a delta, and `#persistWalletAccounts` spreads that stale full snapshot on top of a freshly re-read atom state, allowing a concurrent `#replaceAll` write (e.g. disabling/removing a hardware wallet account via a fusion sync event) to be silently overwritten/reverted.

### Finding Description
`createMany` reads `currentWalletAccounts` at [1](#0-0) , then constructs `walletAccounts = {...currentWalletAccounts}` and mutates/adds entries onto this *entire* map, unlike `updateMany`, which only builds a delta object of the specific accounts being updated ( [2](#0-1) ). This full map (stale snapshot + new account) is passed to `#persistWalletAccounts` at [3](#0-2) .

`#persistWalletAccounts` re-reads the atom fresh (`currentWalletAccounts` at line 207), and only skips the write if `containWalletAccounts(currentWalletAccounts, walletAccounts)` is true — i.e. every key in the passed-in map already exactly matches the fresh state [4](#0-3) . `containWalletAccounts` requires strict equality for every key present in the (stale) `walletAccounts` argument, not just the new one [5](#0-4) . If a concurrent `#replaceAll` run has, in the interim, disabled or removed a hardware wallet account (writing at line 323 inside its own separate `makeConcurrent` queue at [6](#0-5) ), that single differing key causes `containWalletAccounts` to return `false`, and the code proceeds to `updatedWalletAccounts = {...currentWalletAccounts, ...walletAccounts}` (line 213). Since `walletAccounts` is the *entire stale snapshot* (not a delta), this spread clobbers every account key present in it — including reverting the hardware account back to its pre-disable/pre-removal state — even though `createMany`'s only intent was to add one new account.

Exploit flow:
1. Attacker triggers rapid fusion sync events during device pairing/unpairing that cause `#replaceAll` to process a disable/remove of a hardware wallet account (`removedHardwareWalletAccounts`/`disabled` in `getChanges`).
2. Concurrently (different `makeConcurrent` queues, so no mutual exclusion), a legitimate `create()`/`createMany()` call is in flight; it already read the pre-disable state at line 353.
3. `#replaceAll` completes and commits the disable/removal to `#walletAccountsInternalAtom` (line 323).
4. `createMany`'s in-flight call then calls `#persistWalletAccounts` with its stale full snapshot; `containWalletAccounts` fails on the one changed key, so the merge overwrites the fresh (disabled) state with the stale (enabled) snapshot, resurrecting the hardware account.

### Impact Explanation
This allows a previously disabled/removed hardware wallet account to be resurrected (re-enabled with its original state) purely due to timing, without any explicit user action to re-enable it. This is a state-integrity/consent-bypass issue: a security-relevant action (disabling/removing a hardware key from the active wallet accounts) can be silently undone, potentially exposing addresses/balances the user believed removed, or causing loss of the disable action state, which could affect what accounts a wallet unexpectedly treats as active/enabled.

### Likelihood Explanation
Requires two conditions: (1) attacker/environment able to trigger a fusion sync event that changes hardware wallet account state (feasible via normal device pairing/unpairing network timing, no special privilege needed since fusion channel processing is part of normal sync flow), and (2) this racing with an in-flight `createMany`/`create()` call. Because `createMany` and `#replaceAll` are independent `makeConcurrent` queues, ordinary async scheduling (not even an actual attacker) can trigger this; it's a legitimate concurrency bug reachable through normal app usage patterns (pairing a hardware wallet while account creation is in progress), making it moderately likely under realistic conditions but not trivially triggerable by a remote unprivileged attacker without some influence over sync timing.

### Recommendation
Make `createMany` pass only the delta (newly created/modified entries) to `#persistWalletAccounts`, mirroring `updateMany`'s pattern, instead of the full stale snapshot. Additionally, `#persistWalletAccounts`'s read-check-write sequence should be placed under a shared concurrency guard (or use atomic compare-and-swap/functional atom update) so that `createMany`, `updateMany`, `disableMany`, `removeMany`, and `#replaceAll` all serialize against the same lock instead of independent `makeConcurrent` queues, preventing lost updates across these code paths.

### Proof of Concept
Integration/invariant test:
1. Seed `#walletAccountsInternalAtom` with a hardware wallet account `HW1` (enabled).
2. Fire two promises without awaiting sequentially:
   - `walletAccounts.createMany([{ name: 'newAccount', ... }])` — start it, but pause it (mock `#wallet.getPrimarySeedId` to `await` a deferred controlled by the test) right after its initial `currentWalletAccounts` read (line 353) but before `#persistWalletAccounts` runs.
   - Trigger `#replaceAll` via the fusion `processOne` callback with fusion data that removes/disables `HW1`; let it complete and commit to the atom.
3. Resume the paused `createMany` promise to let it call `#persistWalletAccounts`.
4. Await both promises.
5. Assert final `#walletAccountsInternalAtom` state: `HW1` should remain disabled/removed (matching `#replaceAll`'s intent) and `newAccount` should be present — i.e., sequential-consistency expectation. The bug manifests as `HW1` being resurrected as enabled in the final atom state, violating the invariant.

export const containWalletAccounts = (
  walletAccounts: Record<string, WalletAccount>,
  otherWalletAccounts: Record<string, WalletAccount>
) => {
  return Object.entries(otherWalletAccounts).every(([key, otherWalletAccount]) => {
    const walletAccount = walletAccounts[key]
    return walletAccount && otherWalletAccount.equals(walletAccount)
  })
}
