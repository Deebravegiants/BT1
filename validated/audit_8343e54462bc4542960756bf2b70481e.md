### Title
Webhook tenant identity (`shop`) is not covered by the HMAC, enabling cross-tenant spoofing of `WebhookMetadata` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but the `shop` (and `topic`) that the handler receives as the tenant identifier come from unauthenticated HTTP headers that are never bound into the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`Registry.process` validates that the HMAC matches the body, but then constructs `WebhookMetadata` using `request.shop` and `request.topic`, both of which are simply read from headers with no cryptographic binding to the signed payload: [2](#0-1) 

`request.shop` and `request.topic` are plain header reads with no relation to `hmac`: [3](#0-2) 

The equality the code relies on is: `hmac == HMAC(secret, body)` implies `shop == "the shop that actually sent this body"`. That implication is false — the HMAC only proves the body was signed by *someone* holding the app's shared secret (any shop with the app installed), not which shop the body belongs to. `shop` and `topic` are attacker-controlled header values that travel outside the signed byte range entirely.

### Impact Explanation
An app that relies on `WebhookMetadata#shop` (as delivered by this gem) to select the tenant/session/database record to act on is vulnerable to cross-tenant data confusion: an attacker who legitimately installs the app on their own shop (an "unprivileged internet user" with respect to any other merchant) receives genuine, correctly-signed webhook deliveries for their own shop. They can capture one such raw body + valid HMAC pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `Utils::HmacValidator.validate` still passes because it only checks `raw_body` against the secret, and the handler is invoked believing the payload belongs to the victim tenant. This is a cross-tenant authentication/identity-binding bypass (the report's "shop authenticated versus the shop stored/acted upon" pattern), which meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop they control (a normal, unprivileged action) and be able to POST arbitrary headers to the app's public webhook endpoint (trivial, since these are plain HTTP callbacks with no mTLS or IP allowlisting enforced by this gem). No access token, `client_secret`, or privileged account is required — only knowledge of one's own legitimately-received webhook body/HMAC pair, which any app-installing merchant automatically has.

### Recommendation
Bind the tenant identity into the verified bytes: include `shop` (and ideally `topic`, `webhook-id`, `api-version`) in the value that is HMAC-verified, or otherwise require the caller to independently authenticate the shop backing the webhook delivery (e.g., cross-check `shop` against a shop that is known to have this specific `webhook_id` registered) rather than trusting the unauthenticated header value verbatim. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used as the sole tenant selector without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook delivery, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of BODY under app secret>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: BODY
   ```
2. Attacker resends the identical `BODY` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `Utils::HmacValidator.validate` (in `lib/shopify_api/webhooks/registry.rb:190`) computes `HMAC(secret, BODY)` — identical to what was received — and passes.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the app's handler as if this data belongs to `victim-shop`, even though the payload actually originated from `attacker-shop`.
