## Analysis: Unrestricted per-chain rate range skews the depth-weighted mean used to price intents

The reported bug class — statistics computed over unrestricted, self-reported values (validator scores) directly driving payout/selection logic without a sanity bound — has a concrete analog in Hyperbridge's intents/liquidity-pool pricing pipeline.

### Title
Unbounded per-chain rate merged into `LiquidityPool.sellRate`/`buyRate` via unrestricted depth-weighted mean, poisoning default intent pricing — (File: `sdk/packages/indexer/src/services/liquidityPool.service.ts`)

### Summary
`weightedRate()` computes a **depth-weighted mean** over per-chain samples with no upper/lower bound check on the individual sample rates, and the one guard that does inspect for outliers (`warnOnDivergentSample`) is explicitly designed to **only log a warning and never exclude or cap** the divergent sample. This merged value becomes `LiquidityPool.sellRate` / `buyRate`, which `IntentGateway.quoteIntent`'s default `indexed_rates` strategy uses, unmodified, to price real cross-chain intent orders [1](#0-0) .

### Finding Description
`weightedRate` merges an array of `{rate, depth}` samples into a single mean, weighted by each sample's `depth`: [1](#0-0) 

This function is used both to build each chain's `PoolChainLiquidity.rate` from a leg's collapsed samples, and — critically — to merge multiple chains' rates into the pool-level `sellRate`/`buyRate` in `mergeChainRowsIntoPool`: [2](#0-1) 

The only outlier detection present, `warnOnDivergentSample`, computes the >5x-divergence consensus check but by design merges the outlier anyway rather than excluding or clamping it: [3](#0-2) 

Per-leg pricing does use `weightedMedian` (a selection, bounded by an actual bid) rather than a mean, which resists a minority bidder setting the price. But once a chain has that median price computed, the cross-chain **pool-level merge** (`mergeChainRowsIntoPool`) is a plain weighted mean of the chains' rates with **no bound on how far one chain's rate may differ from the others**, and the divergence alarm is explicitly non-blocking. A chain where an attacker is the sole/dominant bidder for a leg (a normal, permissionless, single-transaction condition — bids are open to anyone who is a delegated solver) can trivially set that chain's median to an arbitrary price, and that arbitrary price is blended into the pool's global `sellRate`/`buyRate` in proportion to the attacker's own real depth on that chain.

This directly mirrors the reported bug class: an unrestricted input value (there: validator score; here: one chain's median rate) feeds a statistical aggregate (there: mean/stddev; here: depth-weighted mean) that gates a consequential outcome (there: validator reward eligibility; here: the default price used to size real intent fills) without any sanity ceiling on the input's deviation from the rest of the population.

### Impact Explanation
`LiquidityPool.sellRate`/`buyRate` is the rate the SDK's `IntentGateway.quoteIntent` uses **by default** (`indexed_rates` strategy, no fallback) to compute `amountIn`/`amountOut` for real, fund-moving cross-chain intent orders: [4](#0-3) [5](#0-4) 

Because the merge lacks any bound, an attacker who dominates bidding on one destination chain for a leg can skew the cross-chain rate the SDK returns to callers requesting a quote, causing intents built from that quote to over- or under-value the swap. This is a direct pricing-integrity failure in a path reachable by any solver submitting bids on a phantom order — no privileged role is required, matching the "unprivileged … intent solver" reachability the scope calls out.

### Likelihood Explanation
Reaching this requires only becoming a delegated solver and bidding on a chain where other solvers hold little or no output-token inventory for a given leg (a realistic and permissionless condition, especially for newly-listed pairs or thinly-liquid chains) — no governance or admin compromise needed. The existing 5x-divergence check does surface the condition in logs, but the code comment states this is intentional ("the sample still merges") because the design cannot distinguish a bad registry-decimals entry from a genuinely dislocated market — meaning this is a known, accepted design tradeoff, not a code defect that was overlooked. This weakens confidence that it should be treated as an unintended vulnerability versus a documented limitation of a permissionless price-discovery mechanism, and it is also self-limiting in that the attacker's ability to move the mean is proportional to the attacker's own real, verified inventory depth (`bidder.weight` comes from actual ERC-20/vault balances, not a costlessly-submitted number), unlike the original report where scores were entirely free to fabricate.

### Recommendation
If tightening is desired, bound the pool-level merge similarly to the per-leg selection: either exclude/clamp chain samples whose rate diverges beyond a configured threshold from the depth-weighted consensus of the other chains (converting `warnOnDivergentSample` from log-only to exclude-and-log), or require a minimum number/diversity of independent bidders per chain before that chain's sample is allowed to influence the cross-chain mean.

### Proof of Concept
Not independently verified end-to-end (no test harness run); reasoning is based on static code review of `weightedRate`/`mergeChainRowsIntoPool` and the `indexed_rates` quote path. A concrete PoC would: (1) register a phantom order/pair where chain A has an honest bidder pool and chain B has a single attacker-controlled solver; (2) have the attacker bid an extreme price on chain B's leg with real (even small) inventory so `weightedMedian` selects it as chain B's rate; (3) observe `LiquidityPool.sellRate`/`buyRate` shift proportionally to chain B's `depth` weight; (4) call `quoteIntent` and observe the skewed `amountOut`/`amountIn`.

// The one rate-merge policy: depth-weighted average, falling back to the unweighted mean when
// the whole sample set carries zero depth (so a price is still reported). Every merge in this
// file — collapsed legs, the cross-chain pool merge, and the divergence alarm's consensus —
// must agree on this, hence the single home.
function weightedRate(samples: { rate: bigint; depth: bigint }[]): bigint {
	const depth = samples.reduce((acc, sample) => acc + sample.depth, 0n)
	return depth > 0n
		? samples.reduce((acc, sample) => acc + sample.rate * sample.depth, 0n) / depth
		: samples.reduce((acc, sample) => acc + sample.rate, 0n) / BigInt(samples.length)
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

// A pair prices identically across chains, so one sample far off the others' consensus almost
// certainly means a wrong registry decimals entry poisoning that chain's normalization — worth an
// alarm, but the sample still merges: this cannot tell a bad entry from a genuinely dislocated
// market, and silently dropping data would hide the bug the alarm exists to surface.
function warnOnDivergentSample(
	poolId: string,
	direction: string,
	rows: { chain: string; rate: bigint; depth: bigint }[],
): void {
	if (rows.length < 2) return
	for (const row of rows) {
		const consensus = weightedRate(rows.filter((other) => other !== row))
		if (consensus === 0n) continue
		if (row.rate > consensus * 5n || row.rate * 5n < consensus) {
			logger.warn(
				{ poolId, direction, chain: row.chain, rate: row.rate.toString(), consensus: consensus.toString() },
				"Pool chain sample diverges >5x from the other chains — check the token registry decimals",
			)
		}
	}
}
