### Title
Webhook `shop` identity is not covered by the HMAC, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the HMAC verified by `Utils::HmacValidator.validate` binds nothing but the JSON payload. The `shop` (and `topic`/`webhook_id`/`api_version`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's webhook handler are read from unauthenticated headers and are never checked against the signed content.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, while `shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header: [3](#0-2) 

`HmacValidator.validate` computes and compares an HMAC over `to_signable_string` (the body) only, using `Context.api_secret_key`: [4](#0-3) 

`Registry.process` accepts the request once the body HMAC checks out, and then forwards `request.shop` (an unauthenticated header) straight to the handler as the tenant identity, alongside the (HMAC-covered) body: [5](#0-4) 

The security invariant the HMAC is supposed to enforce is:
`shop_used_by_handler == shop_that_actually_sent(body)`

But because only the body bytes are signed, the equality that is actually verified is:
`hmac(body) == hmac(body)` — independent of `shop`, `topic`, `webhook_id`, `api_version`.

Any party that can obtain one legitimately-signed webhook (e.g., by installing the app on their own shop and receiving a real webhook with a valid `x-shopify-hmac-sha256` for that body) can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (the body-derived HMAC is unchanged), so `Registry.process` dispatches the handler with `shop: <attacker-chosen-value>` and `body: <attacker's own, real, signed data>`.

### Impact Explanation
This breaks the tenant binding that host applications rely on to route webhook data to the correct shop record. A handler that trusts `WebhookMetadata#shop` to select which tenant's database row/session to act on (a documented, expected usage pattern for this gem, see `lib/shopify_api/webhooks/webhook_handler.rb`) can be made to apply another shop's real, validly-signed webhook body to a victim shop's tenant context — e.g. forcing an `app/uninstalled`, `shop/redact`, or similar administrative webhook to be attributed to a shop that never sent it. This is a cross-tenant confusion vulnerability stemming directly from the gem's own signature-verification logic, not from host-application misuse, since the gem hands the caller `shop` as if it were HMAC-verified alongside the body.

### Likelihood Explanation
Exploitation only requires the ability to receive one legitimate webhook for any shop (trivially achievable by installing/testing the target app on an attacker-controlled dev/test store) and the ability to POST to the app's public webhook endpoint with a forged `shop-domain` header — no possession of `api_secret_key` is required. This is a realistic, unprivileged-internet-user attack path.

### Recommendation
Bind the identity headers into the signed material, or explicitly document/enforce that `shop`, `topic`, `webhook_id`, and `api_version` must not be trusted independently of the body. Concretely: extend `Request#to_signable_string` (or `Registry.process`) to require the body's own shop/store identifiers to match the `shop-domain` header before dispatch, or cross-check `request.shop` against a shop already known/authorized for the given `webhook_id` via a prior GraphQL lookup, rather than passing the raw header value straight through to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers any webhook topic (e.g. `orders/create`), capturing the raw POST body `B` and its valid `x-shopify-hmac-sha256: H` header.
2. Attacker replays the request to the app's webhook endpoint, keeping `body = B` and header `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)`, causing the host application to process attacker-supplied, validly-signed data under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
