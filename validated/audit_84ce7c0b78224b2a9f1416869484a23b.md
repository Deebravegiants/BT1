### Title
ETH overpayment on `EvmHost.dispatch()`/`fundRequest()` swaps is refunded to the Host contract, not the caller, permanently trapping user dust ETH - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` are all `payable` functions that let a caller pay the relayer fee in native token by forwarding `msg.value` directly to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. The standard Uniswap V2 router only consumes the exact ETH amount needed to buy `post.fee`/`get.fee`/`amount` fee-tokens and refunds any leftover ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amountIn)`. Since `EvmHost` itself is the caller of the router, this refund lands back on `EvmHost`'s own balance — not on the original transaction sender. `EvmHost` has no logic afterward to forward that leftover ETH back to the user, and no `receive()`/sweep function that returns it to the payer.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
the full `msg.value` is forwarded to the router with only `post.fee` as the exact output amount requested. The same pattern is repeated in `dispatch(DispatchGet)`: [2](#0-1) 
and in `fundRequest()`: [3](#0-2) 

None of these three functions capture the router's return value (`amounts[0]`) or compare it to `msg.value` to compute and forward a refund. The canonical `UniswapV2Router02.swapETHForExactTokens` implementation refunds unspent ETH to `msg.sender`, which in this call context is the `EvmHost` contract address itself (since `EvmHost` is the direct caller of the router), not the original EOA/contract that submitted the transaction with `msg.value`. Consequently, any ETH sent beyond the exact amount needed to purchase `fee` worth of `feeToken` is silently absorbed into `EvmHost`'s balance with no code path that returns it to the depositor.

This is the same bug class as the reported "ETH Dust in `createAndInitializePool`" finding: a `payable` function performs a partial-consumption operation (pool init / token swap) without refunding the unused `msg.value`, and the periphery contract lacks a corresponding `refundETH()`-style cleanup after the operation.

Unlike the purpose-built wrapper contracts in the same repo (`UniV3UniswapV2Wrapper.sol`, `UniV4UniswapV2Wrapper.sol`) which explicitly snapshot balances and forward any leftover ETH back to `msg.sender` after the swap: [4](#0-3) [5](#0-4) 
`EvmHost.dispatch`/`fundRequest` call the router directly and have no equivalent refund step.

### Impact Explanation
Any unprivileged user who calls `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with `msg.value` greater than what is needed to purchase the requested fee amount (which is very likely in practice, since exact quoting on-chain is fragile due to slippage/price movement between quote and execution) will have the excess ETH permanently and irrecoverably absorbed by the `EvmHost` contract. There is no user-facing withdrawal path for this stranded ETH; it accumulates in the contract balance. This constitutes a permanent freezing/loss of user funds reachable from a single, ordinary dispatch transaction — no privileged role or malicious actor is required, only normal usage with a safety margin on `msg.value` (a common and expected client pattern, as documented in the SDK/docs where callers are told to send `nativeValue` alongside dispatch calls).

### Likelihood Explanation
High likelihood: overpaying `msg.value` slightly to guard against price slippage in the native-to-feeToken swap is the expected/documented usage pattern (see `docs/content/developers/evm/messaging/post-requests.mdx`, which instructs callers to send `msg.value` for native-token payment without any exact-fee computation guarantee). Every dispatcher, relayer-fee-funder, or app built on `dispatchWithFeeToken`/native dispatch that doesn't compute the exact swap input off-chain will trigger this, making the loss essentially guaranteed on repeated use rather than a rare edge case.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the `amounts` array returned by `swapETHForExactTokens` and refund the difference `msg.value - amounts[0]` back to `_msgSender()` (or the designated `payer`) via a safe ETH transfer, mirroring the refund pattern already implemented correctly in `UniV3UniswapV2Wrapper.swapETHForExactTokens` and `UniV4UniswapV2Wrapper.swapETHForExactTokens`.

### Proof of Concept
1. A user calls `EvmHost.dispatch{value: 2 ether}(post)` where `post.fee` only requires `0.001 ether` worth of ETH to purchase via the router (per current pool price).
2. `dispatch()` forwards the full `2 ether` to `IUniswapV2Router02.swapETHForExactTokens{value: 2 ether}(0.001 ether worth, path, address(this), block.timestamp)`.
3. The router consumes only the ETH needed (e.g., `0.001 ether`) and refunds the remaining `~1.999 ether` to `msg.sender` of the router call, which is `EvmHost`'s address (not the user).
4. `EvmHost.dispatch()` returns normally; the user has permanently lost `~1.999 ether`, which now sits in `EvmHost`'s balance with no function to withdraw it back to them.
5. Repeating steps 1–4 for `dispatch(DispatchGet)` and `fundRequest()` reproduces the identical loss. [1](#0-0) [2](#0-1) [3](#0-2)
