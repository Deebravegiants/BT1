Audit Report

## Title
Missing Role-Based Authorization on External Initiator Listing Endpoint - (File: core/web/router.go)

## Summary
The `GET /v2/external_initiators` route registered in `core/web/router.go` is protected only by the identity-establishing `auth.Authenticate` middleware and lacks any role-based guard, unlike its sibling `POST`/`DELETE` routes on the same resource which require `auth.RequiresEditRole`. As a result, any authenticated user—including one holding only the lowest-privilege `UserRoleView` role—can call this endpoint and retrieve every configured external initiator's `AccessKey` and `OutgoingToken`.

## Finding Description
In `core/web/router.go`, routes under `authv2` are wrapped by `auth.Authenticate(...)`, which verifies identity via token or session but performs no role check [1](#0-0) . Individual routes then explicitly add role guards as needed. For external initiators, the `GET` route omits any role wrapper while `POST`/`DELETE` are wrapped in `auth.RequiresEditRole`: [2](#0-1) 

`ExternalInitiatorsController.Index` fetches all external initiators from the ORM and serializes each via `presenters.NewExternalInitiatorResource`, with no role-based filtering or redaction applied: [3](#0-2) 

`NewExternalInitiatorResource` includes the raw `AccessKey` and `OutgoingToken` fields in the JSON response: [4](#0-3) 

This confirms the structural inconsistency described in the claim: the mutating endpoints (`Create`, `Destroy`) are gated on `edit` role, but the listing endpoint that discloses `AccessKey`/`OutgoingToken` for every configured integration is reachable by any authenticated identity regardless of role, including `UserRoleView`.

## Impact Explanation
This is a genuine authorization-boundary inconsistency: a node user provisioned only with `view`-role credentials (intended for read-only/monitoring use) can enumerate sensitive integration configuration—`AccessKey` and `OutgoingToken`—for every external initiator configured on the node, despite not being entitled to `edit`-level actions on that same resource. `AccessKey`/`OutgoingToken` are credentials used to authenticate outgoing webhook calls back to the initiator, so their disclosure to an unauthorized role constitutes credential/secret exposure via a node API authorization gap, which maps to the in-scope "key/secret exfiltration" / "node API authentication or role bypass" impact categories.

## Likelihood Explanation
Exploitation requires only a `view`-role API credential authenticated through the existing `AuthenticateByToken`/`AuthenticateBySession` middleware — no admin/host/database access, no race conditions, and no reliance on misconfiguration. Any node operator that provisions least-privilege `view` users (a normal, encouraged practice) is directly exposed, making this a straightforward, repeatable disclosure with a minimal-privilege starting point (an authenticated, non-privileged API user), consistent with the eligibility rule requiring an unprivileged-actor trigger.

## Recommendation
Wrap `GET /v2/external_initiators` with a role guard (e.g., `auth.RequiresEditRole` or an equivalent higher-than-view guard) consistent with the sensitivity of the returned fields, or redact `AccessKey`/`OutgoingToken` from `ExternalInitiatorResource` for callers below `edit`/`admin` role, matching the protection level already applied to the sibling `Create`/`Destroy` routes.

## Proof of Concept
1. As an admin, create an API user with `UserRoleView` via `POST /v2/users`.
2. Authenticate as that view-role user (session cookie or API token).
3. Issue `GET /v2/external_initiators` with the view-role credentials — the request passes `auth.Authenticate` (no role check exists on this route) and reaches `ExternalInitiatorsController.Index`, which returns each configured initiator's `Name`, `URL`, `AccessKey`, and `OutgoingToken` in the JSON:API response, despite the same user being rejected (403) if it attempts `POST`/`DELETE /v2/external_initiators`, which are gated by `auth.RequiresEditRole`.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
type ExternalInitiatorResource struct {
	JAID
	Name          string         `json:"name"`
	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`
	UpdatedAt     time.Time      `json:"updatedAt"`
}

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
```
