### Title
Cross-chain token amount truncated to zero on decimal-down-scaling causes fund loss with no credit minted - (File: modules/pallets/hyper-fungible-token/src/impls.rs)

### Summary
The `hyper-fungible-token` pallet's `convert_to_balance` helper scales an incoming ERC20 `U256` amount down to the pallet's local balance precision by integer division. When the incoming amount is smaller than `10^(erc_decimals - local_decimals)`, the division truncates to zero, exactly mirroring the `GlmManager.getGmTokenValueInUSDC()` bug: a legitimate deposit results in a computed value of `0`, while the corresponding tokens have already been locked/burned on the source side.

### Finding Description
`convert_to_balance` performs:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
``` [1](#0-0) 

This is a pure integer division with no floor/minimum check: any `value` less than `10^(erc_decimals - local_decimals)` produces a `dec_str` of `"0"`, so the parsed balance `B` is `0`. This is used by `module.rs` (per grep matches) when processing an inbound ISMP request that credits a user's local balance for tokens bridged from an EVM chain — analogous to `gmTokensDeposit()` in the reported bug, where tokens are already transferred/escrowed on the sending side before the (truncating) value conversion determines what the receiver gets.

### Impact Explanation
If a user (or contract) bridges a small amount of an ERC20 token whose `erc_decimals` exceeds the pallet's `local_decimals` (e.g., an 18-decimal token bridged to a 6-decimal local asset, requiring `10^12` as the truncation threshold), any transfer below that threshold results in the local pallet crediting `0` balance while the corresponding ERC20 amount was already burned/locked on the EVM side. This is a permanent, unrecoverable loss of user funds — the same "GM tokens deposited but no shares minted" pattern from the external report, generalized to any unprivileged token bridger using small amounts.

### Likelihood Explanation
Reachable by any unprivileged user who initiates a cross-chain token transfer via `hyper-fungible-token` for amounts below the decimals-scaling threshold. No special privileges are required — a normal small-value transfer (dust, rounding remainders, or simply a token with large decimal count) triggers this path.

### Recommendation
Add an explicit check in `convert_to_balance` (or at the transfer-initiation site) that rejects/reverts amounts whose scaled-down value would be zero, i.e., require `value >= 10^(erc_decimals - local_decimals)` before allowing the cross-chain transfer to proceed, mirroring the recommended fix in the original report (minimum-deposit floor to avoid truncation-to-zero).

### Proof of Concept
1. Configure a bridged ERC20 token with `erc_decimals = 18` and pallet `local_decimals = 6` (scaling divisor `10^12`).
2. User initiates a cross-chain send of `999_999_999_999` (i.e., `< 10^12`) units of the ERC20 token; the source-side contract locks/burns this amount.
3. On the destination pallet, `convert_to_balance(U256::from(999_999_999_999), 18, 6)` computes `999_999_999_999 / 10^12 = 0`, so the recipient's local balance is credited with `0`.
4. The user's ERC20 tokens are gone from the source chain, and no local balance was minted — a permanent loss of funds, with no revert or safeguard in the code shown. [2](#0-1)
