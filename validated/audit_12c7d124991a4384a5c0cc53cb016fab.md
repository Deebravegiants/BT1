### Title
Webhook `shop` and `topic` identifiers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the `shop`, `topic`, and `webhook_id` values used downstream by `ShopifyAPI::Webhooks::Registry.process` are taken directly from unauthenticated HTTP headers. Because the shop identity is never part of the signed payload, a party that possesses one valid `(body, hmac)` pair for the shared app secret can replay it with an arbitrary `shop-domain` header and have it accepted as an authentic webhook for a different, victim merchant.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the value that gets HMAC'd and compared to the caller-supplied `hmac`: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `hmac` is read straight from the `hmac-sha256` header: [2](#0-1) [3](#0-2) 

The `shop`, `topic`, and `webhook_id` accessors are simple header readers with no relationship to the signed bytes at all: [4](#0-3) 

`Registry.process` validates only the HMAC (i.e., only the body) and then dispatches the handler using `request.shop`, `request.topic`, and `request.webhook_id` taken from the same untrusted headers: [5](#0-4) 

This breaks the intended identity binding: `hmac_valid(body) == true` is treated as `shop_header == authentic_source_shop`, but the equality does not actually hold — the `shop` (and `topic`/`webhook_id`) fields are "acted on but not covered by the HMAC," exactly the class of binding failure called out in the rules.

Because Shopify apps use a single shared `client_secret` (`api_secret_key`) for every merchant that installs the app, any merchant who has installed the app receives real webhooks signed with that same secret. Such a merchant (an unprivileged internet user with respect to *other* tenants of the app) can legitimately obtain a valid `(raw_body, x-shopify-hmac-sha256)` pair from their own shop's webhook deliveries, then replay that exact body/HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`) with a victim shop's domain. `HmacValidator.validate` will succeed because it never looks at the shop header, and `Registry.process` will invoke the app's handler believing the event originated from the victim shop.

### Impact Explanation
This allows cross-tenant data injection/spoofing: an attacker-controlled webhook payload can be attributed to an arbitrary victim shop that also uses the app. Depending on what the host application's webhook handlers do with `WebhookMetadata#shop` (e.g., updating per-shop state, marking uninstalls, disabling billing, invalidating sessions, triggering data sync for "that shop"), this can lead to cross-tenant state corruption entirely from the gem's own signature-verification design, satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker needs only to be a legitimate (even free/trial) installer of the same app to obtain one authentic `(body, hmac)` sample, which is then replayable indefinitely against any shop identifier of the attacker's choosing, since the shop value plays no role in the cryptographic check.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or otherwise cryptographically bind the shop identity to the HMAC-validated payload before it is trusted (e.g., verify/parse the shop from the signed body itself, or require the header value to be corroborated by a separately authenticated channel) inside `ShopifyAPI::Webhooks::Request#to_signable_string` / `HmacValidator`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, becoming an authorized recipient of the app's webhooks (signed with the app's single shared `client_secret`).
2. Shopify sends the attacker's shop a real webhook: headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, plus a JSON body.
3. Attacker replays the identical request to the app's public webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Registry.process` → `HmacValidator.validate` succeeds (body unchanged, HMAC unchanged), and the handler executes with `shop: "victim.myshopify.com"`, `body:` attacker-controlled JSON, even though `victim.myshopify.com` never sent this event.
