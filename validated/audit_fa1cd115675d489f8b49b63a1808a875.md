This confirms the finding. The `VerifiableQuery` interface at [1](#0-0)  only requires `hmac` and `to_signable_string`, and `Request#to_signable_string` returns solely `@raw_body`, never binding the `shop-domain` header into the signable material.

### Title
Webhook `shop` claim is not bound to the HMAC signature, enabling cross-tenant shop-domain spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the `X-Shopify-Shop-Domain` header directly and is exposed unauthenticated via `WebhookMetadata#shop` to host-app handlers, while `HmacValidator.validate` only verifies the raw body against the app's shared secret. Because the app's webhook secret is identical across all shops that install the app, an attacker who can obtain one genuinely-signed `(raw_body, hmac)` pair for their own shop (e.g. by registering their own webhook subscription to a server they control via the Admin API, which they can legitimately do after installing/authorizing the target app) can replay that exact body+HMAC to the app's real webhook endpoint while substituting an arbitrary victim `myshopify.com` domain in the `X-Shopify-Shop-Domain` header, causing `Registry.process` to invoke the host handler with a forged `data.shop`.

### Finding Description
The binding that must hold is: `shop_authenticated_by_signature == shop_used_by_handler_to_select_tenant`. Tracing the code:

- `Request#to_signable_string` returns only `@raw_body` [2](#0-1) .
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed content [3](#0-2) .
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header — the shop-domain header never enters this computation [4](#0-3) .
- `Registry.process` validates only the HMAC, then trusts `request.shop` to build `WebhookMetadata`, which is passed straight to the host app's handler [5](#0-4) .
- The documented usage explicitly tells host apps to key their persistence/tenant logic off `data.shop` [6](#0-5) .

Root cause: the app-level webhook secret (`api_secret_key`) is shared across every shop that installs the app; it is not shop-specific, and the signature covers only the body. Since the attacker legitimately installs/authorizes the target app on their own store, they can use their own valid access token to call the Admin API's `webhookSubscriptionCreate` directly (bypassing the app's own `Registry.register`, which normally fixes the callback path) and point the callback address at a server they control. Shopify will then deliver a genuinely HMAC-signed request — signed with the *same* app secret used for all tenants — to the attacker's server. The attacker now holds a valid `(raw_body, hmac)` pair. They replay this pair verbatim to the target app's real webhook endpoint, only changing `X-Shopify-Shop-Domain` to the victim's domain. `HmacValidator.validate` still succeeds because the signature never covered the shop header, so `Registry.process` calls the handler with `WebhookMetadata#shop` equal to the victim's domain, even though the request was neither sent by Shopify for that shop nor authorized by anything the victim controls.

No existing guard closes this gap: there is no `ShopValidator.sanitize!` call in the webhook path (it's only used in OAuth/token-exchange code), and Sorbet typing only enforces that `shop` is a `String`, not that it matches the signed body or a known-installed shop.

### Impact Explanation
Any host app that follows the gem's documented pattern of trusting `data.shop` to select/create tenant records is exposed to cross-tenant data operations: the attacker can cause records to be written, updated, or associated with a victim shop's tenant using content of the attacker's choosing (whatever body they can get genuinely signed for their own shop). This is repeatable against arbitrary victim `myshopify.com` domains without any interaction from the victim, matching the Critical "cross-tenant access" category. The blast radius is bounded only by what the host app does with the trusted `shop` value in its webhook handler.

### Likelihood Explanation
Preconditions are modest and attacker-achievable without any secret: the attacker installs the target app on their own development store (normal, unprivileged action), obtains their own access token via legitimate OAuth, and uses it to register a webhook subscription pointed at their own server (requires only the `write_webhooks` scope commonly granted). They then capture one genuine `(body, hmac)` pair and replay it with a modified `X-Shopify-Shop-Domain` header. No live victim shop, TLS interception, or leaked credential is needed. It is fully repeatable for any topic the attacker can trigger in their own store and any victim domain string.

### Recommendation
Do not treat `request.shop` as authenticated. At minimum, the gem should require host apps to cross-check `request.shop` against a known/installed shop record (e.g., the shop associated with the webhook `webhook_id`'s registration or with an existing session) before trusting it, or the gem should bind the shop domain into the signable string it exposes for verification (matching the fact that Shopify's own signature does not cover headers) and clearly document that `shop` from `WebhookMetadata` must be re-validated against the app's own tenant/session store, not used as the sole tenant selector.

### Proof of Concept
```ruby
# test/webhooks/shop_spoof_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class ShopSpoofTest < Minitest::Test
      def test_same_body_hmac_valid_for_different_shop_domains
        raw_body = "{}"
        hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          raw_body,
        )
        hmac_header = Base64.encode64(hmac)

        attacker_headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => hmac_header,
          "x-shopify-shop-domain" => "attacker.myshopify.com",
        }
        victim_headers = attacker_headers.merge(
          "x-shopify-shop-domain" => "victim.myshopify.com",
        )

        attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
        victim_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: victim_headers)

        # Same signature validates regardless of the shop-domain header value
        assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))
        assert(ShopifyAPI::Utils::HmacValidator.validate(victim_request))

        # The unauthenticated shop-domain header is trusted verbatim downstream
        assert_equal("attacker.myshopify.com", attacker_request.shop)
        assert_equal("victim.myshopify.com", victim_request.shop)
      end
    end
  end
end
```
This demonstrates that `HmacValidator.validate` returns `true` for both requests despite the different, attacker-chosen `shop` values, proving the signature never binds `request.shop`.
