### Title
Webhook `shop-domain` header is trusted without HMAC coverage, enabling cross-tenant shop-identity spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `api_version`, and `webhook_id` directly from HTTP headers, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` value passed to the app's webhook handler is therefore never bound to the signature that `Registry.process` verifies.

### Finding Description
`Registry.process` validates only that the body's HMAC is correct, then immediately trusts `request.shop` (an unauthenticated header) to build `WebhookMetadata` for the handler: [1](#0-0) 

The `shop` accessor reads straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload: [2](#0-1) 

The HMAC is computed only over `@raw_body`, never over the shop header: [3](#0-2) 

`HmacValidator.validate` verifies the header-supplied `hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. `HMAC(secret, raw_body)`, and never incorporates the shop header into the signed value: [4](#0-3) 

The identity binding the gem should guarantee is: `shop-domain header == shop that produced/signed this raw_body`. Because the header is outside the HMAC-covered bytes, the gem instead only guarantees `HMAC(secret, raw_body) == received_hmac`, with `shop` supplied independently and un-authenticated. Any party capable of obtaining one validly-signed webhook body+HMAC pair for the app (e.g., by installing the app on their own shop, which is a normal unprivileged action any Shopify merchant can take) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header value. `Registry.process` will pass HMAC validation (since only the body is checked) and will hand the handler a `WebhookMetadata` whose `shop` is attacker-controlled, potentially pointing at a victim tenant's domain.

### Impact Explanation
This breaks the tenant-identity binding that host applications rely on: the `shop` field delivered to `handler.handle` (used by virtually every `shopify_app`-style integration to select which merchant's DB row/session to update) is not cryptographically tied to the HMAC-validated bytes. An attacker who has legitimate access to one signed webhook (trivial: install a free/dev store using the target app) can forge deliveries that appear to originate from a different, victim shop, causing the host application to write attacker-supplied webhook data against another tenant's account/session. That is a cross-tenant data integrity/confusion issue reachable by any unprivileged party who can install the app once.

### Likelihood Explanation
Likelihood is High/practical: no secrets beyond the ability to receive one signed webhook are required (an attacker can install the app in their own store to get a validly-signed body/HMAC), and the header-swap requires only rewriting an HTTP header on a replayed POST to the app's registered webhook endpoint — well within reach of an unprivileged internet user, matching the "field acted on but not covered by the HMAC" analog class in this task's rules.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-covered signable string, or independently verify that `request.shop` matches the shop associated with the session/install that the webhook claims to be for, before invoking the handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated and host apps must not trust it without additional binding to a known, previously-registered shop.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`, capturing one legitimate webhook delivery: body `B`, and header `x-shopify-hmac-sha256: HMAC(secret, B)` plus `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay a POST to the app's webhook endpoint with the same body `B` and same HMAC header, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31) recomputes `HMAC(secret, B)`, which still matches the supplied HMAC because the shop header was never part of the signed bytes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) proceeds and calls `handler.handle` with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now reads `"victim-shop.myshopify.com"` — a value the attacker fully controls and that was never verified against the HMAC.
