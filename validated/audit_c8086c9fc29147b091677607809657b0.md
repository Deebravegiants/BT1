This confirms the root cause. The webhook `Registry.process` method passes `request.shop` directly to the handler as the trusted tenant identifier, but that value is never covered by the HMAC signature check.## Finding

The webhook shop identity (`request.shop`, from the `X‑Shopify‑Shop‑Domain` / `shopify-shop-domain` header) is trusted by `ShopifyAPI::Webhooks::Registry.process` as the tenant identifier, but it is never covered by the HMAC signature that this gem validates.

### Title
Webhook `shop` header is not covered by the HMAC signature, breaking the shop-authenticated ≡ shop-acted-upon binding - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable content solely from the raw body, while the shop identifier used by the rest of the pipeline comes from an unsigned HTTP header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate_signature` computes and compares the HMAC exclusively over that signable string: [2](#0-1) . The `shop` accessor, however, is read straight from the `shop-domain` header without any cryptographic binding to the body/HMAC: [3](#0-2) .

`Registry.process` validates the HMAC and then immediately forwards `request.shop` as the trusted tenant value into `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle`: [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field with no further verification: [5](#0-4) .

Broken binding (equality that should hold but does not):
`shop covered by HMAC == shop acted upon by WebhookHandler#handle`

Before the attacker's request: for a genuine Shopify-originated webhook, `hmac(raw_body, api_secret_key)` is valid and `shop-domain` header happens to match the tenant that produced `raw_body`.
After the attacker's request: the attacker (any merchant/tenant who has installed the app, or anyone able to replay a body+HMAC pair they legitimately received from Shopify for their own shop) changes only the `shop-domain` header to a victim shop while leaving `raw_body` and its HMAC untouched. `HmacValidator.validate` still returns `true` because it only checks `raw_body` against the HMAC — the header is outside its scope — yet `Registry.process` now hands the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
Since `request.shop` is not authenticated by the HMAC, an attacker who can produce (or replay) any valid `body`+`HMAC` pair for the app (e.g., via their own installed/legitimate shop's real webhook traffic) can freely relabel the tenant by rewriting only the `shop-domain` header, causing the host app's `WebhookHandler` to process/store data under a different tenant's identity. This is a cross-tenant confused-deputy condition arising directly from this gem's webhook verification design, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any party that operates or controls one legitimate shop installation of the app (a routine, unprivileged position for a public Shopify app) can obtain valid `body`/HMAC pairs from real Shopify webhook deliveries and then send a crafted HTTP request to the app's webhook endpoint with an altered `shop-domain` header. No access to `api_secret_key`, access tokens, or any privileged credential is required — only the ability to send an HTTP POST to the app's public webhook route, which is by design internet-reachable.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) inside the value that is HMAC-verified, or otherwise cryptographically/contextually bind the `shop` header to the verified body before it is exposed via `WebhookMetadata`. At minimum, `Registry.process` should treat `request.shop` as untrusted until it is corroborated by a mechanism outside attacker control (e.g., verifying the shop against Shopify's per-request signed payload envelope rather than a bare header), consistent with Shopify's guidance to not rely on unsigned headers for identity decisions.

### Proof of Concept
1. App owner (attacker) installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and its valid `X-Shopify-Hmac-Sha256` value.
2. Attacker replays a POST to the app's webhook endpoint with the same `raw_body`/HMAC but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and performs tenant-scoped actions (e.g., data writes/deletes) against the victim shop's records, even though the victim shop never sent this event.
