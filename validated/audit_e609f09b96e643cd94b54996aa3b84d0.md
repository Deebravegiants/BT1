### Title
Webhook shop-domain (and topic) not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `ShopifyAPI::Utils::HmacValidator.validate` verifies exactly that string against the `X-Shopify-Hmac-Sha256` header. The `shop` (tenant identity) and `topic` values used by `ShopifyAPI::Webhooks::Registry.process` to dispatch the webhook to the host application are read straight from unauthenticated HTTP headers that are never part of the signed bytes, breaking the binding `shop-verified-by-HMAC == shop-acted-on`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`/`topic` are read directly from headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop`/`request.topic` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because a merchant can install the app on their own store (unprivileged relative to any other tenant), Shopify will legitimately deliver a body + valid `hmac-sha256` for that attacker-controlled shop. Since the shop-domain header is not part of the signed bytes, the attacker can replay the exact same body/HMAC pair while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` will pass `shop: <victim-domain>` to the app's webhook handler — the gem provides no other authentication of which tenant a webhook belongs to.

### Impact Explanation
This is a cross-tenant identity-binding break: the value the handler acts on (`data.shop`) is not covered by the value the gem cryptographically verifies (the raw body). Any host application that trusts `WebhookMetadata#shop` to route webhook side effects (e.g., processing `app/uninstalled` to purge/reset a shop's stored token, handling `shop/redact`/`customers/redact` GDPR deletion requests, or updating per-shop billing/subscription state) can be made to apply an attacker-crafted, legitimately-HMAC'd payload against an arbitrary victim shop, since the gem never binds the `shop` header to the signature. This meets the Critical bar of cross-tenant access via the app's own trusted webhook channel.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the app on any shop they control (a normal, unprivileged action for any Shopify developer/merchant) and capture one legitimate webhook delivery — no `api_secret_key`, access token, or privileged account is needed. The replay itself is a trivial HTTP request with a modified header, so likelihood is high wherever a host app keys per-tenant logic off `WebhookMetadata#shop`.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed payload validation instead of trusting bare headers: either derive the shop for routing solely from a value that is cryptographically covered, or require the host app to independently confirm `request.shop` corresponds to a shop that actually has this app installed with a matching secret/session before acting, and document this gap clearly if header binding cannot be added to `to_signable_string`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook Shopify will send legitimately, e.g. `app/uninstalled`, capturing the raw body `B` and the real `X-Shopify-Hmac-Sha256: H` (computed by Shopify with the app's `client_secret` over `B`).
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic` unchanged (e.g. `app/uninstalled`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`, unchanged) — validation passes. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the app-uninstall/redact logic against the victim tenant, even though nothing about the request was ever verified by Shopify for that shop.
