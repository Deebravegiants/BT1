### Title
Global workflow-count limit can be exhausted by any unprivileged workflow owner, causing DOS of legitimate CRE workflow activations - ([File: core/services/workflows/syncerlimiter/limiter.go])

### Summary
The CRE workflow syncer enforces a two-tier resource quota — `Global` (node-wide cap across all owners) and `PerOwner` (per-owner cap) — before allowing a workflow to be activated on a node. Because the `Global` pool has no reservation carved out for any particular owner, any address that can register/activate workflows on the on-chain `WorkflowRegistry` (a permissionless, non-privileged action open to any workflow owner) can consume the shared `Global` capacity with cheap/junk workflows, denying other legitimate owners the ability to activate their workflows — the same "shared limited resource, no per-actor reservation" DOS pattern described in the OpenQ report (`TOKEN_ADDRESS_LIMIT` exhausted by any caller of `fundBountyToken()`).

### Finding Description
`syncerlimiter.NewWorkflowLimits` builds a `MultiResourcePoolLimiter` composed of an owner-scoped limiter and a single global-scoped limiter: [1](#0-0) 

The `Global` limiter tracks usage across *all* owners with no per-owner reservation or set-aside capacity — it is a single shared pool, exactly like the `tokenAddresses` set/`TOKEN_ADDRESS_LIMIT` in the OpenQ bounty contract that any caller can push toward its cap: [2](#0-1) 

When a workflow is registered/activated (driven by on-chain `WorkflowRegistered` events processed by the syncer's event handler), the handler calls into these limiters (`workflowLimits.Use(ctx, 1)`), and if the `Global` cap is reached, subsequent, otherwise-legitimate workflow owners are rejected with `ErrGlobalWorkflowCountLimitReached`, even though they are each well within their own `PerOwner` allowance: [3](#0-2) 

The unit test explicitly demonstrates the exhaustion mechanics: three distinct owners (`user1`, `user2`, `user3`) each register a single workflow (well under `PerOwner: 1`), which is enough to exhaust `Global: 3`; a fourth, entirely legitimate owner (`user4`) is then rejected purely due to the shared `Global` scope being full, not because of anything it did: [4](#0-3) 

Registering a workflow via the `WorkflowRegistry` contract is a normal, unprivileged action available to any workflow owner (analogous to `fundBountyToken()` being callable by anyone) — there is no mechanism reserving `Global` capacity for a specific "issuer"/privileged owner, so an attacker who controls multiple owner addresses (or reuses many cheap workflow registrations from one address up to its `PerOwner` cap) can starve the shared `Global` pool and block unrelated, legitimate owners' workflow activations node-wide.

### Impact Explanation
This is a node-wide (or DON-wide, if the same defaults are applied fleet-wide) denial-of-service: legitimate workflow owners are prevented from activating workflows because an unrelated, unprivileged actor consumed the shared `Global` quota. Default configuration values (`Global = 200`, `PerOwner = 200`) mean a single owner alone could exhaust the entire `Global` pool with 200 cheap/no-op workflow registrations, before any other owner gets a slot — directly mirroring the "any caller can exhaust the shared cap and block the real depositor" impact from the OpenQ report. [5](#0-4) 

### Likelihood Explanation
Likelihood is moderate: workflow registration itself happens on-chain via the `WorkflowRegistry` contract and its associated fees/permissions are outside this repo, but from the node's perspective the syncer/limiter code applies no privileged carve-out or fairness mechanism for the `Global` bucket — any account able to get a `WorkflowRegistered` event recognized by the node (which appears to require no special node-level authorization beyond being a valid registry event) can count against `Global`. The bug is triggerable purely through the normal registration flow, without any privileged role, exactly matching the class of vulnerability described (unprivileged actor exhausting a shared cap/allowlist to grief others).

### Recommendation
Introduce a reserved/guaranteed capacity per owner within the `Global` pool (e.g., always allow at least N slots per distinct owner even when `Global` is near its cap), or track `Global` usage in a way that weights against Sybil/burst registration from many distinct owners (e.g., decay/aging, or a minimum stake/cost per workflow registration). At minimum, expose a priority/reservation mechanism analogous to the "two-limit" recommendation in the original report — one relaxed limit for verified/known owners and a tighter limit for new/unknown owners — so legitimate owners cannot be starved out of the shared `Global` quota by unrelated third parties.

### Proof of Concept
The existing test `TestWorkflowLimits` in `core/services/workflows/syncerlimiter/limiter_test.go` already demonstrates the core mechanics:
1. `Global: 3`, `PerOwner: 1`.
2. `user1`, `user2`, `user3` each register one workflow — none exceed `PerOwner`, but together they exhaust `Global` (3/3).
3. `user4`, a legitimate new owner with zero prior usage, attempts to register one workflow and is rejected with `ErrorResourceLimited{Scope: ScopeGlobal}` purely because unrelated owners filled the shared pool first: [6](#0-5) 

This is reproduced end-to-end at the engine level in `TestEngine_Start_RateLimited`, where `engine4` (a distinct, legitimate `WorkflowOwner`) fails to start solely due to the `Global` limit being consumed by other owners' engines, receiving `types.ErrGlobalWorkflowCountLimitReached`: [7](#0-6) 

Note: I could not locate/verify the on-chain `WorkflowRegistry` contract's access-control logic for workflow registration within this index (it may live in a separate contracts repo not covered here), so I cannot confirm whether there is any additional gating (e.g., fees, allowlisting) at the contract layer that would raise the cost of this attack beyond what's shown in the node-side limiter code. If contract-level registration is entirely permissionless and cheap, the likelihood of this analog is high; if it requires meaningful cost/stake per workflow, the practical severity is reduced accordingly.

func NewWorkflowLimits(lggr logger.Logger, cfg Config, lf limits.Factory) (limits.ResourceLimiter[int], error) {
	lggr = logger.Named(lggr, "WorkflowExecutionLimiter")
	cfg.PerOwnerOverrides = normalizeOverrides(cfg.PerOwnerOverrides)

	ownerLimit := cresettings.Default.PerOwner.WorkflowLimit // make a copy
	if cfg.PerOwner > 0 {
		ownerLimit.DefaultValue = int(cfg.PerOwner)
	}
	perOwner := make(map[string]string, len(cfg.PerOwnerOverrides))
	for k, v := range cfg.PerOwnerOverrides {
		perOwner[k] = strconv.Itoa(int(v))
	}
	lf.Settings = keyedOwnerSettings{getter: lf.Settings, key: ownerLimit.Key, vals: perOwner}
	owner, err := limits.MakeResourcePoolLimiter(lf, ownerLimit)
	if err != nil {
		return nil, fmt.Errorf("failed to create owner resource limiter: %w", err)
	}

	globalLimit := cresettings.Default.WorkflowLimit // make a copy
	if cfg.Global > 0 {
		globalLimit.DefaultValue = int(cfg.Global)
	}
	global, err := limits.MakeResourcePoolLimiter(lf, globalLimit)
	if err != nil {
		return nil, fmt.Errorf("failed to create global resource limiter: %w", err)
	}

	lggr.Debugw("workflow limits set", "perOwner", cfg.PerOwner, "global", cfg.Global, "overrides", cfg.PerOwnerOverrides)

	return limits.MultiResourcePoolLimiter[int]{owner, global}, nil
}
