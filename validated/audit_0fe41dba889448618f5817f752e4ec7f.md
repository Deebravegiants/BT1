### Title
Webhook shop identity spoofing — `shop` field is trusted for tenant routing but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` directly from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header [1](#0-0) , while the HMAC verification performed by `Utils::HmacValidator` only signs and checks the raw request body (`to_signable_string` returns `@raw_body`) [2](#0-1) [3](#0-2) . `Registry.process` validates only that HMAC before dispatching to the handler with the (unauthenticated) `shop` value [4](#0-3) . This breaks the binding `shop authenticated == shop used for tenant identity`.

### Finding Description
The webhook signature scheme signs only the raw JSON body:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

and `HmacValidator.validate` compares the computed HMAC of that body against the value from the `hmac-sha256` header:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [3](#0-2) 

None of `topic`, `shop`, `api_version`, or `webhook_id` — all read straight from headers — are part of the signed material:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [1](#0-0) 

`Registry.process` uses this unauthenticated `shop` to build the `WebhookMetadata` passed to the app's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

`WebhookMetadata#shop` is a `String` const that app code is expected to use for tenant-scoped work (looking up the shop's stored session, updating shop-specific records, etc.) [5](#0-4) , but the gem itself never verifies that the header-supplied `shop` corresponds to the shop whose secret actually produced the HMAC over the body.

Because the HMAC is computed with the app's single `api_secret_key` and does not bind to any per-shop value, any legitimate webhook received by the app for *any* installed shop (including a shop the attacker controls, e.g. their own free/dev store with the app installed) carries a valid signature that is completely independent of the `X-Shopify-Shop-Domain` header. An attacker who controls a shop with the app installed can capture one legitimately signed webhook delivery for their own store, then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop domain. The HMAC still validates (it only checks the body), and the dispatched `WebhookMetadata.shop` will be the victim's domain, causing the app to process attacker-supplied `body` content as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity binding break: the equality the gem should enforce — `hmac-authenticated origin == request.shop used to route/act on tenant data` — does not hold, since `shop` is excerpted from a header outside the HMAC's coverage. Depending on how the host application consumes `WebhookMetadata#shop` (e.g., for looking up/mutating the victim shop's stored session or shop-scoped records, or for authorization decisions based on shop identity), an attacker can inject attacker-controlled webhook payloads that the app believes originate from a different, victim tenant. This matches the "Critical - cross-tenant access" impact category since it lets an unprivileged internet user (anyone who can install the app on their own free store) forge webhook events attributed to an arbitrary victim shop.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app on a shop they control (a standard, unprivileged action for any Shopify developer/merchant), (2) the attacker captures one webhook delivery from Shopify to the app's public endpoint (trivial, since they own that shop and can trigger any registered topic), and (3) the attacker replays the captured body+HMAC to the app's endpoint with the `shop-domain` header changed to the victim domain. No credentials, TLS interception, or privileged access are required — this is achievable entirely from a normal, unprivileged internet-facing position, satisfying the scan's scope for unprivileged-user analogs.

### Recommendation
Bind the webhook's claimed shop to the value actually verified by the signature — e.g., verify webhooks per-shop by looking up the shop's own credential/secret before trusting `request.shop`, or require the host application to independently cross-check `request.shop` against a shop it expects to receive that specific `topic`/`webhook_id` for, before acting on `WebhookMetadata`. At minimum, the gem's documentation should explicitly warn that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-identity decisions without additional verification (e.g., matching against a known/expected shop for the specific webhook subscription).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal app install, no privilege needed).
2. Attacker triggers a webhook topic the app has registered (e.g., `orders/create`) on their own shop; Shopify sends:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of body computed with app's api_secret_key>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   {"id": 1, ...attacker-controlled order payload...}
   ```
3. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` header to the app's public webhook endpoint, but swaps:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC [6](#0-5) ; `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker payload>, ...)` to the app's handler [4](#0-3) , causing the app to act on attacker-controlled data believing it belongs to the victim tenant.
