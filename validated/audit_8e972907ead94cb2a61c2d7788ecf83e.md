### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` domain returned by `Request#shop` is read from an HTTP header that is never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then passes the *unverified* header-derived `shop` value straight into `WebhookMetadata`, which the gem's own documentation instructs app authors to treat as "The shop domain of the webhook" and use for tenant-scoped logic. An attacker who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the app on a shop they control) can replay that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop, and the HMAC check will still pass.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. Meanwhile `shop` is derived independently from headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC using only `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` performs this HMAC check, then immediately builds `WebhookMetadata` using `request.shop`, the header value that was never part of the signed input: [4](#0-3) 

The identity binding that should hold is: `shop_that_authorized_the_HMAC == shop_the_app_believes_it_received`. Because the header is outside the MAC, this equality is not enforced — the byte range verified by the HMAC (`@raw_body`) is a strict subset of the byte range trusted by the application (`raw_body` + `shop-domain` header). This matches the "field acted on but not covered by the HMAC" identity-binding break pattern.

The gem's docs reinforce that downstream apps are expected to trust this field directly without extra verification: [5](#0-4) [6](#0-5) 

### Impact Explanation
An attacker who owns/controls one Shopify shop (any developer/merchant can install a public or their own app) can capture a legitimately-signed webhook body+HMAC pair for a topic whose body doesn't uniquely bind it to that shop (e.g., generic/mandatory topics such as `app/uninstalled`, `shop/redact`, or any topic where the body content is shop-independent or attacker-controlled/predictable). The attacker then replays the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still succeed because it only checks the raw body against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop. Applications that key session lookup, uninstall/data-deletion logic, or subscription state off `data.shop` (as the docs instruct) can be made to act on the wrong tenant — e.g., wrongly marking a victim shop as uninstalled, deleting/rotating the victim's stored session, or triggering shop-scoped side effects for a shop the attacker does not own. This is a cross-tenant identity-binding bypass driven entirely by this gem's own webhook verification API.

### Likelihood Explanation
Medium. Exploitation requires the attacker to possess a valid signed body/HMAC pair from a shop they control (trivial to obtain by installing the target app on their own store or dev shop) and requires the app to have a topic whose body content doesn't itself embed shop-identifying data that the app cross-checks. This is realistic for several common Shopify mandatory/compliance topics and any custom low-payload topic.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed input, or independently verify `request.shop` against a value obtained by a channel bound to the HMAC (e.g., look up the webhook subscription/shop record via `webhook_id`, or require callers to pass the expected shop and compare it). At minimum, document prominently that `shop` in `WebhookMetadata` is unauthenticated header data and must not be trusted for tenant-scoping decisions without independent verification.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body = "{}" # generic body used by many topics (e.g., app/uninstalled test payloads)

hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)
valid_hmac_header = Base64.encode64(hmac)

# Attacker obtained the above (body, hmac) pair from a webhook sent to THEIR OWN shop
# (e.g. "attacker-shop.myshopify.com"), then replays it with a spoofed shop header:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => valid_hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# Passes: HMAC only ever verifies `body`, never the shop header.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
```
