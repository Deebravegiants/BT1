### Title
Panic-on-untrusted-input DoS in Pharos SPV membership/non-membership proof parsing — (File: `modules/consensus/pharos/primitives/src/spv.rs`)

### Summary
`verify_membership_proof` (and its non-membership counterpart) in `modules/consensus/pharos/primitives/src/spv.rs` reads `last.proof_node[1..33]` and `last.proof_node[33..65]` and copies them into a fixed 32-byte buffer without first checking that `last.proof_node` is at least 65 bytes long:

```rust
let last = proof_nodes.last().ok_or(Error::EmptyProof)?;
if !is_leaf(&last.proof_node) { return Err(Error::InvalidLeaf); }
if last.proof_node[1..33] != sha256(key) { return Err(Error::KeyMismatch); }
let mut value_hash = [0u8; 32];
value_hash.copy_from_slice(&last.proof_node[33..65]);
``` [1](#0-0) 

This mirrors exactly the CWE-248 bug class in the report: attacker-controlled, variable-length bytes are indexed/sliced without a length check before the fallible operation, so a short `proof_node` (e.g. a single byte that satisfies whatever `is_leaf` checks but is shorter than 65 bytes) causes a Rust slice-index-out-of-bounds panic rather than a typed `Result::Err`.

### Finding Description
`PharosStateMachine::verify_membership` (in `modules/ismp/state-machines/pharos/src/lib.rs`) decodes a `PharosStateProof` from the untrusted `proof.proof` bytes carried in an ISMP `Proof`, then calls `spv::verify_membership_proof` per commitment key using attacker-supplied `storage_proof_nodes`:

```rust
let pharos_proof = decode_pharos_state_proof(proof)?;
...
spv::verify_membership_proof(storage_proof_nodes, &spv::build_storage_key(&address, &slot_key), &state_root.0)
``` [2](#0-1) 

`PharosProofNode.proof_node` is a raw `Vec<u8>` decoded via SCALE with no length constraint enforced at decode time (matching the general pattern the codebase itself has repeatedly had to patch for GRANDPA, sync-committee, and the Ethereum RLP trie decoder — see the `empty_hp_prefix_returns_error_not_panic` regression test and the sync-committee `multi_proof.len()` guard added specifically to stop attacker-controlled proof shapes from panicking the runtime). Here, the same defensive check was never added: `is_leaf` presumably inspects only a leading byte/flag and does not guarantee a minimum length of 65, so a `proof_node` of, say, 2 bytes that is classified as a "leaf" reaches the unchecked slices `[1..33]` and `[33..65]` and panics.

This verification path is reached by `PharosClient::verify_consensus` state updates and by `PharosStateMachine::verify_membership`/`verify_non_membership`, which are invoked from `pallet-ismp`'s `handle_unsigned` extrinsic — an unsigned, unauthenticated, free-to-submit transaction that anyone can send with an arbitrary `RequestMessage`/`ResponseMessage` carrying a crafted `Proof`. There is no prior authentication or bonding: the message only needs to pass SCALE decoding to reach the state-machine client's `verify_membership`/`verify_non_membership` call, at which point the malformed `proof_node` triggers the panic deep inside runtime execution of an unsigned extrinsic.

### Impact Explanation
A panic during extrinsic execution on affected Pharos-backed state machines is a denial-of-service against that facet of the ISMP message-delivery pipeline: it aborts execution of `handle_unsigned` for the batch containing the malicious message (and, depending on how the panic unwinds through the transaction-pool validation path — which also calls the same `execute`/`verify` logic during `ValidateUnsigned::validate_unsigned` — it can repeatedly disrupt block-building/transaction-pool validation for any node that evaluates the crafted message). Since `handle_unsigned` is free and requires no fee or stake, a single relayer/attacker can submit a Pharos-destined request/response message with a malformed storage-proof node and repeatedly panic the runtime's unsigned-transaction validation and/or execution path, blocking legitimate message delivery to/from the Pharos state machine — i.e., "a route unable to deliver messages," which meets the High-severity bar (network-reachable, single-message, no privilege, denial of service against protocol message delivery).

### Likelihood Explanation
High. The trigger requires only crafting a `PharosStateProof` (or `PharosProofNode`) whose `proof_node` byte vector satisfies `is_leaf(...)` while being shorter than 65 bytes, then submitting it inside an ISMP `RequestMessage`/`ResponseMessage`/consensus update targeting a Pharos-backed `StateMachineId` via the permissionless `handle_unsigned` extrinsic. No cryptographic material, signatures, or special permissions are needed — only a `StateMachine::Evm(pharos_chain_id)` consensus client configured (already the case for any Hyperbridge deployment supporting Pharos), and knowledge of the byte layout that `is_leaf` treats as a leaf.

### Recommendation
In `verify_membership_proof` and the non-membership counterpart in `modules/consensus/pharos/primitives/src/spv.rs`, validate `last.proof_node.len() >= 65` (or the precise minimum length required by the leaf encoding) before performing the `[1..33]`/`[33..65]` slices, returning a typed error (e.g. `Error::InvalidLeaf` or a new `Error::ProofNodeTooShort`) instead of allowing the slice operation to panic. Apply the same length-defensiveness pattern already used elsewhere in the codebase (e.g. the Ethereum RLP node codec's empty-HP-prefix check and the sync-committee `multi_proof` length guard) to every other unguarded slice/index operation over `PharosProofNode` fields, and add a regression test analogous to `empty_hp_prefix_returns_error_not_panic` feeding a truncated leaf node through `verify_membership_proof`/`verify_non_membership_proof` to assert an `Err` rather than a panic.

### Proof of Concept
1. Construct a `PharosProofNode` whose `proof_node` is recognized as a leaf by `is_leaf` (e.g., the minimal byte pattern that satisfies whatever leading-byte/tag check `is_leaf` performs) but is fewer than 65 bytes long — e.g., 2–10 bytes.
2. Embed it as the sole element of `storage_proof` for a queried commitment slot inside a SCALE-encoded `PharosStateProof`, itself embedded as the `proof.proof` bytes of an ISMP `Proof` in a `RequestMessage`/`ResponseMessage`/`GetRequestsWithProof` addressed to (or coming from) a Pharos-backed `StateMachineId`.
3. Submit this as the `messages` argument of `pallet_ismp::Call::handle_unsigned` (unsigned, free, no prior authentication) — or, equivalently, ensure `ValidateUnsigned::validate_unsigned` in `pallet-ismp` evaluates it (it also calls `Self::execute`, which reaches the same code path during transaction-pool validation).
4. `PharosStateMachine::verify_membership` decodes the proof and calls `spv::verify_membership_proof`, which indexes `last.proof_node[1..33]` / `[33..65]` on the short vector and panics with an index-out-of-bounds trap, aborting the extrinsic's execution (and potentially the pool-validation call) rather than returning `Err(Error::InvalidLeaf)`.

/// Verify that a key exists in the trie (inclusion proof).
/// Returns the value hash from the leaf on success.
pub fn verify_membership_proof(
	proof_nodes: &[PharosProofNode],
	key: &[u8],
	root: &[u8; 32],
) -> Result<[u8; 32], Error> {
	if proof_nodes.len() > MAX_PROOF_DEPTH {
		return Err(Error::ProofTooDeep);
	}

	let last = proof_nodes.last().ok_or(Error::EmptyProof)?;

	if !is_leaf(&last.proof_node) {
		return Err(Error::InvalidLeaf);
	}

	if last.proof_node[1..33] != sha256(key) {
		return Err(Error::KeyMismatch);
	}

	let mut value_hash = [0u8; 32];
	value_hash.copy_from_slice(&last.proof_node[33..65]);

	verify_proof_walk(proof_nodes, key, root)?;
	Ok(value_hash)
}

pub fn verify_membership<H: Keccak256 + Send + Sync>(
	commitments: Vec<H256>,
	root: StateCommitment,
	proof: &Proof,
	contract_address: H160,
) -> Result<(), Error> {
	let pharos_proof = decode_pharos_state_proof(proof)?;

	let state_root = H256::from_slice(&root.state_root[..]);
	let address: [u8; 20] = contract_address.0;

	let commitment_keys = req_commitment_key::<H, _>(commitments, |k| k.to_vec());

	// Pharos uses a flat trie — storage proofs verify directly against state_root.
	for slot_hash in commitment_keys {
		let storage_proof_nodes = pharos_proof
			.storage_proof
			.get(&slot_hash)
			.ok_or(PharosStateMachineError::MissingCommitmentStorageProof)?;

		let slot_key: [u8; 32] = slot_hash
			.try_into()
			.map_err(|e: Vec<u8>| PharosStateMachineError::InvalidSlotHashLength(e.len()))?;

		spv::verify_membership_proof(
			storage_proof_nodes,
			&spv::build_storage_key(&address, &slot_key),
			&state_root.0,
		)
		.map_err(|e| PharosStateMachineError::SpvVerificationFailed(alloc::format!("{e:?}")))?;
	}
