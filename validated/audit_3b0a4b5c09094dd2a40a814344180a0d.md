### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then trusts `request.shop`/`request.topic` as-is when dispatching to the app's webhook handler. Any party capable of obtaining one valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key` (e.g. by installing the app on their own, attacker-controlled store) can replay that body/HMAC pair while substituting an arbitrary `shop-domain` header, causing the app to process forged data as if it originated from a different (victim) tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature check to `@raw_body` only: [1](#0-0) [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from attacker-suppliable headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — which validates `to_signable_string` (the body) against the `hmac` header — and then immediately trusts `request.shop`/`request.topic` to build the `WebhookMetadata` passed to the host application's handler: [4](#0-3) 

`HmacValidator.validate` performs a straightforward HMAC-SHA256 compare of the signable string against the secret — it has no visibility into, and does not cover, the `shop`/`topic` headers: [5](#0-4) 

This is the same class of bug as the reported fee-on-transfer issue: a value that is *acted upon* (here, the `shop` identity attributed to the webhook payload) is not the same as the value that was actually *authenticated* (only the raw body bytes are HMAC-verified). The binding that should hold — `shop header == shop cryptographically bound to the signed payload` — does not exist.

### Impact Explanation
Because `api_secret_key` is shared across all shops that install a given app (it is a per-app secret, not a per-shop secret), any user who installs the app on their own Shopify store can receive a legitimately-signed webhook `(raw_body, hmac)` pair from Shopify. That user can then POST the exact same `raw_body` and `hmac` header to the app's public webhook endpoint while changing the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a different, victim shop. The HMAC check still passes (it only checks the body bytes), and `Registry.process` will dispatch the forged data to the app's handler tagged with the victim's shop domain — a cross-tenant data-injection/spoofing primitive that can corrupt per-shop data stores, trigger unauthorized actions for another tenant, or spoof events (e.g. `app/uninstalled`, orders, GDPR topics) as if for a merchant the attacker does not control.

### Likelihood Explanation
Likelihood is realistic but not trivial: it requires the attacker to (a) be able to install the target app on a store they control (freely available for public apps) and (b) know/guess the webhook endpoint is shared and does not perform additional shop-scoped checks in the host application. Any host app that relies solely on this gem's HMAC validation and uses `WebhookMetadata#shop` as the tenant key (a documented, expected usage pattern) is exposed.

### Recommendation
Include the authenticated shop/topic identity in the value that is cryptographically verified, or otherwise cryptographically bind the headers to the signed payload — e.g., have `Request#to_signable_string` incorporate `shop`, `topic`, and `webhook_id` (if Shopify's signing scheme allows it), or require callers to independently verify that `shop` matches a known/registered shop for an active session before trusting webhook data. At minimum, the gem should document loudly that `shop`/`topic` are unauthenticated and must be independently cross-checked by the host application against a real installed-shop record before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, generating a legitimate webhook delivery, e.g., topic `customers/data_request` with body `{"...":"..."}` and header `x-shopify-hmac-sha256: <valid-hmac-of-body>` computed with the app's shared `api_secret_key`.
2. Attacker replays the exact same raw body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. In `Request.new`, `shopify_header("shop-domain")` returns `"victim-shop.myshopify.com"`. [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates `@raw_body` against the HMAC — unaffected by the header substitution. [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, and the host application processes the payload as belonging to `victim-shop.myshopify.com` even though it never sent or authorized this data.
