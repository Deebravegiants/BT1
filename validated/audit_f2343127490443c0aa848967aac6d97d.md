### Title
Webhook Shop/Topic Spoofing via HMAC That Only Covers the Raw Body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC signature over the raw request body only, while `topic`, `shop`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the signed payload. Any party who can obtain one genuinely-signed webhook body/HMAC pair (e.g., a merchant with the app installed on their own shop, receiving real webhook deliveries) can replay that exact body+HMAC with a forged `shop-domain` (and/or `topic`) header to make the gem attribute the event to a different, arbitrary shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no binding to the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only checks the HMAC against `to_signable_string`, i.e., the raw body bytes: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the handler, without any additional check that the shop asserted in headers matches the shop the body was actually signed for: [4](#0-3) 

The broken identity binding is: `HMAC-verified bytes (raw_body) != shop/topic used to route and process the event (request.shop / request.topic)`. Because the header fields are never part of the signable string, they can be freely modified after obtaining any valid `(raw_body, hmac)` pair, without needing the app's `api_secret_key`. A malicious merchant with the app legitimately installed on their own store can capture a real webhook delivery (valid body + HMAC for their own shop) and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or the `x-shopify-topic` changed). The HMAC check still passes because it never inspected those headers, and the handler executes believing the event originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: an attacker-controlled request can be attributed to another merchant's shop. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., loading/creating store-scoped state, triggering shop-specific side effects, or feeding into session lookups), this enables cross-tenant data manipulation/impersonation, which maps to the Critical "cross-tenant access" category in scope.

### Likelihood Explanation
Exploitability requires only unprivileged access already available to any real user of the platform: the attacker installs the app on their own shop (a normal, non-privileged action), captures one legitimate webhook delivery for their shop, and replays the exact body/HMAC with altered `shop-domain`/`topic` headers directly to the app's public webhook endpoint. No access to the app's `api_secret_key`, TLS interception, or social engineering is required, since the HMAC scheme itself never binds the header fields it later trusts.

### Recommendation
Bind the identity-relevant metadata into the signed material actually verified, or otherwise cryptographically/contextually verify that the `shop`, `topic`, and `webhook_id` headers match the shop/subscription the webhook body was generated for (e.g., cross-check against Shopify's registered webhook delivery metadata per shop/subscription id, or require the caller to supply/verify shop identity through a channel not solely derived from unauthenticated headers). At minimum, document and enforce that `Webhooks::Registry.process` must only be invoked behind infrastructure that guarantees the headers were not tampered with after Shopify's own signing (e.g., mutual TLS to Shopify's IP ranges), and consider incorporating header values into the HMAC computation if the delivery protocol allows.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to, capturing the raw HTTP request Shopify sends, including body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's real secret).
2. Send a new POST request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`.
4. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata` whose `shop` is `victim.myshopify.com`, even though the payload was never signed in association with that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
