### Title
Zero-valued Merkle sibling is misinterpreted as "no more path" instead of a real padding hash, permanently/temporarily freezing spendable UTXOs - (File: circuits/MerkleRootCalculator.circom)

### Summary
`MerkleRootCalculator` treats a sibling value of `0` as a signal to *skip* that tree level entirely rather than perform the real hash step, but the on-chain incremental tree in `Merkle.sol` legitimately pads an unpaired node with the literal value `0` and **does** hash it (`hash2(prevHash, 0)`) to compute the root that gets stored in `roots[...]`. The circuit therefore cannot reconstruct a correct Merkle proof for any commitment whose real sibling at some level is `0`, causing valid ZK proofs for that leaf to be unconstructable against that historical root and the on-chain transaction to revert with `"Invalid Proof"`.

### Finding Description
In `circuits/MerkleRootCalculator.circom`: [1](#0-0) 
the sibling at each level is checked with `IsZero`, and if it equals `0`, `hashesProcessed[i]` is forced to `0`, which makes `rootHashes[i+1]` simply carry forward the *previous* root value instead of the real Poseidon hash of `(currentHash, 0)`. This design intentionally supports variable-depth Merkle proofs (shallow historical roots produced while the tree is still growing), where "no more real path" is signaled by a zero sibling.

However, `contracts/Merkle.sol`'s `insertOne` produces roots that legitimately incorporate a *real* hash step with a literal `0` sibling whenever a leaf is inserted alone (unpaired) at a given level: [2](#0-1) 
Concretely, for an odd-sized subtree (e.g. leaf inserted alone, count=3 in an 8-leaf tree), the stored root is `hash2(hash2(leaf1,leaf2), hash2(leaf3,0))` — i.e. `hash2(leaf3,0)` is a genuine, required hash step to reach that specific historical root captured in `roots[newIndex-1]`, which remains queryable later via `rootHashExists`: [3](#0-2) 

Because `MerkleRootCalculator` interprets `commitmentSiblings[i] == 0` as "stop, don't hash," any prover trying to spend `leaf3` against that specific historical root cannot produce a matching Merkle root: the circuit will output `leaf3` itself (skipped) instead of `hash2(leaf3,0)`, and the equality check [4](#0-3) 
against `rootHashHinkal` will fail, so `verifyProof` in `Hinkal.sol` reverts with `"Invalid Proof"`.

### Impact Explanation
This breaks the spendability equality the protocol relies on: a value-bearing leaf that was genuinely inserted into the tree (and whose commitment/nullifier the owner knows) becomes unspendable whenever the only valid inclusion path for a chosen historical root requires hashing with a real zero sibling. The user's shielded funds are frozen against that root snapshot. Because users (or relayers building the proof) can reference any historical `rootHashHinkalIndex` still in range, but the circuit fundamentally cannot represent this padding case correctly, this is a genuine circuit/tree modeling mismatch matching the rules' "value-bearing leaf left unspendable" category. If the tree fails to receive a subsequent insertion that completes the pairing (e.g. low-activity periods, end of protocol life, or a token/tree segment that stops growing), the freeze becomes effectively permanent for that state; otherwise it is at minimum a temporary freeze of user funds until the tree is padded by further deposits.

### Likelihood Explanation
This triggers deterministically and requires no attacker privilege — it happens naturally any time the total leaf count is odd at the moment a user (or their relayer/prover tooling) builds a Merkle witness against a root snapshot where their leaf is the "odd one out." No admin, relayer collusion, or unusual assumptions are required; it is a direct consequence of the padding scheme used in `Merkle.sol` versus the skip-on-zero shortcut in `MerkleRootCalculator.circom`.

### Recommendation
Disambiguate "real zero sibling" from "no more path" in `MerkleRootCalculator`. For example, pass an explicit `pathLength`/`enabled` signal per level (rather than inferring truncation from `sibling == 0`), so a genuine `hash2(x, 0)` padding step is always performed when it is part of the real tree, and truncation is only applied past the tree's actual current depth.

### Proof of Concept
1. Tree starts empty (`m_index = MINIMUM_INDEX`).
2. Insert `leaf1`, `leaf2` together → `roots[idx_a] = hash2(leaf1, leaf2)`.
3. Insert `leaf3` alone (odd count) → per `insertOne`, `roots[idx_b] = hash2(hash2(leaf1,leaf2), hash2(leaf3, 0))` (see `contracts/Merkle.sol` lines 77-91).
4. A holder of `leaf3` attempts to build a `MainEVMCircuit` witness proving inclusion of `leaf3` under `rootHashHinkal = roots[idx_b]`. The only correct siblings are `[0, hash2(leaf1,leaf2)]`.
5. Feeding `commitmentSiblings[0] = 0` into `MerkleRootCalculator` causes level 0 to be skipped (`hashesProcessed[0] = 0`), so `hashes[1]` used going forward is `leaf3` unmodified rather than `hash2(leaf3, 0)`.
6. The computed `rootHash` output no longer equals `roots[idx_b]`, so the `ForceEqualIfEnabled` check in `circuits/MainEVMCircuit.circom` (lines 145-148) cannot be satisfied for this root, and the corresponding proof cannot be generated/verified — `Hinkal.sol`'s `transact` call reverts with `"Invalid Proof"`, leaving `leaf3`'s value frozen against that root state.

    function insertOne(
        uint256 currentNodeIndex,
        uint256 twoPower,
        uint256 prevHash
    ) internal {
        for (uint256 i = 0; i <= twoPower; i++) {
            if (currentNodeIndex % 2 == 0 || currentNodeIndex == 1) {
                tree[i] = prevHash;
                if (i != twoPower) prevHash = hash2(prevHash, 0);
            } else {
                prevHash = hash2(tree[i], prevHash);
            }
            currentNodeIndex /= 2;
        }
    }
