### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only covers the raw body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, but the webhook HMAC signature verifies only the raw request body, never the shop-domain header. This breaks the binding `shop authenticated == shop stored/used as tenant key`, allowing a forged or replayed body+HMAC pair to be attributed to an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is read straight from the `shop-domain` header, entirely outside the signed payload: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received signature: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` only checks `Utils::HmacValidator.validate(request)` and then dispatches the handler using `request.shop` as the tenant identifier, with no additional binding between the verified bytes and the shop value: [4](#0-3) 

Because the signable string is `@raw_body` only, two requests with an identical body produce an identical valid HMAC regardless of what `shop-domain` header accompanies them. The equality the gem implicitly (and incorrectly) relies on is:
`HMAC_valid(body) == shop_header_authentic`
but the actual guarantee provided is only `HMAC_valid(body) == body_authentic`; the `shop` value is never inside the MAC'd string, so it is parsed but never verified.

### Impact Explanation
An attacker who can obtain one legitimate webhook delivery for their own shop (any merchant installing the app is a legitimate, unprivileged source of such a webhook, or can trigger deliveries at will by causing store events) can replay the exact same raw body + valid HMAC to the app's webhook endpoint while substituting a different value in the `X-Shopify-Shop-Domain` header. `Registry.process` will accept the HMAC (it only verifies body bytes) and hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop: [5](#0-4) 

Any host application that uses `data.shop` from the webhook handler to look up/mutate per-tenant state (sessions, orders, uninstall handling, GDPR data, etc.) — which is exactly the documented usage pattern of `WebhookHandler#handle` — can be made to act on a shop identifier that was never authenticated. This is a cross-tenant identity-binding break reachable by any unprivileged party capable of sending HTTP requests to the app's public webhook endpoint, no access token or `client_secret` needed.

### Likelihood Explanation
Webhook endpoints are public HTTP endpoints by design (Shopify calls them over the open internet), so no credentials, TLS interception, or privileged access are required to reach `Registry.process`. Obtaining a valid body+HMAC pair only requires being (or having been) a legitimate installer of the app for any shop, or observing/guessing a deterministic-body webhook payload — the attacker's own tenant's traffic is sufficient. The vulnerable code path (`hmac` validated on `@raw_body` alone, `shop` read from an unrelated header) is unconditional and always in effect for every webhook processed via `Registry.process`.

### Recommendation
Include the shop-domain (and other identity-relevant headers such as topic/api-version/webhook-id) in the HMAC-signed representation, or otherwise cryptographically bind them to the verified payload, so that `to_signable_string` cannot be satisfied by an attacker who controls only the header while replaying someone else's signed body. At minimum, `WebhookMetadata`/handlers should not be allowed to trust `request.shop` unless it is proven to correspond to the same request whose body was HMAC-verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook with raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B`, the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` computes over `@raw_body` only (`to_signable_string` = `B`), so `HmacValidator.validate` succeeds: [6](#0-5) 
4. `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"`, even though the HMAC never verified that shop value: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
