### Title
Webhook `shop` field is trusted for tenant identification without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates only that body against the HMAC. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated headers and handed to the app's handler as the trusted tenant identifier, breaking the equality `shop-authenticated-by-HMAC == shop-used-by-handler`.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it with the `hmac` field: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body, excluding the `shop`, `topic`, `webhook-id`, and `api-version` headers from the signed material: [2](#0-1) 

`Registry.process` only checks this body-only HMAC, then immediately trusts `request.shop` (parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identity passed to the app's handler: [3](#0-2) 

Because `api_secret_key` is a single app-wide (not per-shop) secret, any unprivileged internet user who installs the app on their own store will legitimately receive HMAC-valid `(body, hmac)` pairs signed with that same secret. Since `shop` is never part of the signed payload, that same valid `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `shopify-shop-domain` header swapped to any other merchant's domain — the HMAC check in `HmacValidator.validate` still passes, and `WebhookMetadata.shop` will be set to the attacker-chosen value: [4](#0-3) 

This is the exact identity-binding gap called out in the report's bug-class hint: a field ("shop") that is acted upon by the handler is not covered by the authentication mechanism ("hmac"), so the value verified (body only) diverges from the value trusted for tenant scoping (`shop`).

### Impact Explanation
Any app built on this gem that uses `data.shop` from `WebhookMetadata` to key writes/updates for a merchant (e.g., updating that shop's stored settings, order records, or triggering shop-scoped side effects) can be made to apply attacker-supplied webhook content to an arbitrary victim shop identifier, because the shop value is never authenticated. This is a cross-tenant identity-binding bypass reachable by any user capable of installing the app on their own store and capturing one legitimate webhook body+HMAC pair — no access token, `api_secret_key`, or privileged account is required beyond a normal app install.

### Likelihood Explanation
Reachable by any unprivileged user who can install the app (a normal, unprivileged flow) and receive at least one real webhook delivery to observe a valid `(body, hmac)` pair, then replay it to the app's public webhook endpoint with a modified `shopify-shop-domain` header. No secrets or elevated access are needed to perform the replay itself.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the signed material used for HMAC verification, or otherwise cryptographically bind the delivered `shop` to the webhook subscription/session that requested it, so that `HmacValidator.validate` fails if the `shop` header is altered independently of the body.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker.myshopify.com`), receiving a legitimate `orders/create` webhook with raw body `B` and header `x-shopify-hmac-sha256: H`, computed as `HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays the exact same body `B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` — matching `H` — and returns `true` per `lib/shopify_api/utils/hmac_validator.rb:12-22`.
4. The app's handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` per `lib/shopify_api/webhooks/registry.rb:198-199`, and processes attacker-controlled body content as if it legitimately originated from `victim.myshopify.com`.
