### Title
Bad-debt wipeout clamps `supply_index` up to `SUPPLY_INDEX_FLOOR_RAW`, resurrecting wiped-out suppliers' phantom claims that drain later depositors' cash - (File: contracts/pool/src/interest.rs)

### Summary
When bad debt is socialized, `apply_bad_debt_to_supply_index` computes the post-wipeout supply index as `supply_index * (supplied_value - bad_debt) / supplied_value` and then clamps it to a minimum of `SUPPLY_INDEX_FLOOR_RAW` (`RAY/1000`) "to avoid a zero index". On a total or near-total wipeout, this clamp **raises** the index above its correct near-zero value, leaving every pre-wipeout supply share with a residual claim backed by nothing. Like CVE-2024-48958's `src` running past `dst`, the written index overshoots the bound the write-down was supposed to establish. The phantom claim is only temporarily masked by `require_reserves` while cash is zero; the first fresh deposit makes the claim payable and it is paid out of the new depositor's funds.

### Finding Description
`apply_bad_debt_to_supply_index` (`contracts/pool/src/interest.rs:73-89`) caps the write-down at total supplied value, computes a `reduction_factor`, multiplies the index down, and then applies `.max(SUPPLY_INDEX_FLOOR_RAW)`:

```rust
cache.set_supply_index(new_supply_index.max(Ray::from(SUPPLY_INDEX_FLOOR_RAW)));
```

When `bad_debt >= total_supplied_value` (a full wipeout, exactly what `clean_bad_debt` / `seize` of an insolvent account produces), `remaining = 0`, so the correct index is `0`, but the clamp sets it to `RAY/1000`. All existing `scaled_amount` shares are left untouched while their claim is revalued to 0.1% of face — a phantom balance.

The pool's own test `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` (`contracts/pool/tests/interest.rs:372-428`) demonstrates the full sequence against the real `Cache` methods:

1. `supplied = 1000 RAY`, `supply_index = RAY`, cash `0`.
2. `apply_bad_debt_to_supply_index(cache, 5000 RAY)` → index clamps to `SUPPLY_INDEX_FLOOR_RAW` instead of going to 0.
3. `unscale_supply_floor(old_scaled)` still returns a positive `stranded` claim while `cash == 0` — "no cash yet: invariant only masked by `require_reserves`".
4. A fresh depositor supplies `fresh_cash = stranded`; the old position then withdraws via `resolve_withdrawal(i128::MAX, old_scaled)` → `gross = fresh_cash`, and `cache.cash() < fresh_claim`: the fresh supplier's claim can no longer be covered.

The reachable path for an unprivileged address: any account driven below the bad-debt dust threshold gets cleaned via `liquidate` → `check_bad_debt_after_liquidation` → `execute_bad_debt_cleanup` (`contracts/controller/src/positions/liquidation/apply.rs:313-315`, `bad_debt.rs:14-49`), which calls `pool_seize_positions_call`; the pool writes the unpaid debt down through `apply_bad_debt_to_supply_index`. `clean_bad_debt` exposes the same write-down. After the clamp, every supplier of that hub market retains shares redeemable at `RAY/1000` index with zero backing; subsequent `supply` deposits restore pool cash, and `withdraw` on a stale position pays the phantom claim out of the new money.

### Impact Explanation
Theft of user funds / protocol insolvency. Suppliers whose claims were economically wiped out can withdraw real tokens equal to `floor(scaled * RAY/1000)` once any new deposit lands in the market, and the new depositors' positions become unbacked by exactly the drained amount. On a thin or fully wiped market the stranded aggregate is up to 0.1% of pre-wipeout face value, paid by whoever supplies next.

### Likelihood Explanation
Requires a market to reach the socializable bad-debt state (total debt vs. collateral under the dust cap) — an ordinary tail event for volatile collateral, and `liquidate`/`clean_bad_debt` are permissionless. No privileged action, price manipulation beyond normal liquidation flow, or timing race is needed; the clamp fires deterministically whenever the write-down would push the index below `RAY/1000`, i.e. whenever bad debt exceeds ~99.9% of supplied value, which is precisely the wipeout scenario the function exists for. The payout only needs one later deposit into the same market — normal protocol usage.

### Recommendation
Remove the floor clamp for the wipeout path, or pair it with share reset: when `bad_debt >= total_supplied_value`, set `supply_index` to 0 (or the floor) **and** zero/burn all `supplied` shares so no residual claim survives — mirroring the debt side, where seized positions are deleted rather than clamped. Alternatively, track the clamped-away shortfall as a permanent deficit against the pool (e.g., a negative cash reserve marker) so `require_reserves` keeps rejecting the phantom withdrawal even after fresh deposits. At minimum, `resolve_withdrawal` payouts to pre-wipeout shares must be capped by actual cash attributable to them rather than the floored index value.

### Proof of Concept
The repository's own test proves the sequence end-to-end at the cache layer (pool ops use exactly these `Cache` methods):

```rust
// contracts/pool/tests/interest.rs:372-428
apply_bad_debt_to_supply_index(&mut cache, Ray::from(5_000 * RAY));
assert_eq!(cache.supply_index().raw(), SUPPLY_INDEX_FLOOR_RAW);
let stranded = cache.unscale_supply_floor(old_scaled);
assert!(stranded > 0);                       // phantom claim survives wipeout
// ... fresh deposit of `stranded` arrives ...
let (burn, gross) = cache.resolve_withdrawal(i128::MAX, old_scaled);
assert_eq!(gross, fresh_cash);               // wiped position drains fresh deposit
assert!(cache.cash() < fresh_claim);         // new supplier's funds lost
```

On-chain reproduction: (1) borrow against collateral, crash the price or accrue debt until `is_socializable_bad_debt` holds; (2) call `liquidate` (or `clean_bad_debt`) so the pool seizes the positions and runs `apply_bad_debt_to_supply_index` with `bad_debt` exceeding supplied value → index clamps to `RAY/1000`; (3) a victim supplies any amount to the market; (4) a holder of pre-wipeout shares calls `withdraw(account_id, 0)` — `require_reserves` now passes against the fresh cash and pays out the unbacked claim, leaving the new supplier undercollateralized.

One caveat I could not fully verify within the tool budget: whether `update_indexes`/`seize` on the pool side performs an additional correction (e.g., zeroing `supplied`) that would neutralize the phantom shares. The unit test shows none is applied at the `Cache`/`apply_bad_debt_to_supply_index` level, and `docs/reference/formulas.md` does not document a share reset on index clamping.
