### Title
Arithmetic underflow (revert-DoS) in `Router._computeBuy`'s overflow-cap branch when a token donation inflates real balance above stored reserve - ([File: packages/contracts/src/Router.sol])

### Summary
CVE-2017-9949 is a `grub_memmove` stack-based buffer underflow triggered by attacker-crafted input that violates an assumed size ordering. The Solidity analog here is an unchecked `uint256` subtraction that assumes `reserveToken ≥ tokensOut` but can be driven false by an unprivileged, permissionless action — a raw ERC20 `transfer` of `Token` directly into the curve `Pair` — causing a Panic-revert (underflow) rather than memory corruption, but with an equivalent "crafted input → crash" root cause. `Router._computeBuy`'s overflow-cap branch subtracts `reserveToken - tokensOut` without checking that `tokensOut` (set to `pair.tokenBalance()`) cannot exceed `reserveToken`.

### Finding Description
`Router._computeBuy` computes the capped buy path as: [1](#0-0) 

```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // <-- underflows if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

The code assumes the protocol-wide invariant `pair.tokenBalance() < reserveToken` (asserted by `test_inv_virtualReserveAlwaysExceedsRealBalance` in `GraduationInvariants.t.sol`). That invariant is a property of curve-internal accounting only; it is **not** enforced against direct ERC20 donations. Anyone can call `Token.transfer(pair, amount)` on a launched token to inflate `pair.tokenBalance()` arbitrarily above the stored `reserveToken`, exactly the scenario the codebase itself documents and has already had to patch once, elsewhere: [2](#0-1) 

That earlier fix patched only `Bonding.previewLtUntilGraduation`'s supply leg with an explicit guard: [3](#0-2) 

```solidity
// Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
if (realBalance >= reserveToken) return ltUntilThreshold;

uint256 cappedReserveToken = reserveToken - realBalance;
```

`Router._computeBuy` performs the structurally identical subtraction (`reserveToken - tokensOut` where `tokensOut = realBalance`) but was never given the equivalent guard, so the underflow class the team already fixed once in `Bonding.sol` remains live in `Router.sol`.

### Impact Explanation
Once a caller donates enough `Token` to the pair to push `pair.tokenBalance() > reserveToken` (demonstrated reachable and cheap in `test_donation_realBalanceExceedsReserveToken`), any subsequent buy sized large enough to trip the overflow-cap branch (`tokensOut > realBalance`, e.g. an oversized buy like the one used in `test_inv_overflowCap_refundsLt`) causes `Router._computeBuy` to revert with a `Panic(0x11)` underflow instead of executing the capped buy. This is a denial-of-service on the largest/closing buys on that curve — the exact trade class responsible for firing the supply-trigger graduation (`tokenBalance() == 0`). Because the donation is irreversible (there is no ungraft path to remove the donated tokens before graduation burns them in `_prepareGraduationLiquidity`), any closing/cap-binding buy attempt on the affected token reverts until the pair is eventually graduated by the USD trigger instead — or is permanently un-graduatable via the supply trigger for as long as an attacker keeps re-donating. This is a freezing/DoS impact on a normal trading and graduation path reachable by any unrelated wallet via a plain ERC20 transfer, satisfying the "permanent freezing" bar for a Medium/High finding.

### Likelihood Explanation
High reachability, low cost: the precondition (`pair.tokenBalance() > reserveToken`) requires only (1) buying most of the curve's real token supply through the normal `Bonding.buy`/`Zap.buy` path (no privilege needed), and (2) a plain `Token.transfer(pair, amount)` — both are unprivileged, single-transaction operations already exercised end-to-end in the existing `_stageDonationAttack` test helper. Triggering the underflow additionally requires one oversized buy call (`Bonding.buy`/`Zap.buy` with a large `amountIn`), which is also unprivileged and cheap (bounded by LT mint cost). No governance, oracle manipulation, or timing dependency is required.

### Recommendation
Add the same `realBalance >= reserveToken` guard used in `Bonding.previewLtUntilGraduation` to `Router._computeBuy` before computing `cappedReserveToken`, e.g. clamp `tokensOut` to `min(realBalance, reserveToken - 1)` or explicitly branch to a donation-safe cap path when `realBalance >= reserveToken`, mirroring the fix already applied in `Bonding.sol`. Add a regression test that stages the existing `_stageDonationAttack` helper and then issues an oversized buy (as in `test_inv_overflowCap_refundsLt`) to assert the trade still succeeds instead of reverting with a Panic.

### Proof of Concept
1. Launch a token via `Zap.createToken` (unprivileged creator).
2. As any unrelated wallet, drain most of the curve via `Zap.buy`/`Bonding.buy` (mirrors `_stageDonationAttack`'s `bonding.buy(drainLtSpent, tokenAddr, 0, drainer)`), acquiring > 250M `Token`.
3. `Token.transfer(pairAddr, donatedTokens)` — a plain ERC20 transfer, no special role required — pushing `pair.tokenBalance() > reserveToken` (per `test_donation_realBalanceExceedsReserveToken`).
4. Any wallet calls `Zap.buy`/`Bonding.buy` with an oversized LT amount (as in `test_inv_overflowCap_refundsLt`'s `oversizedBuy = 1_000_000_000 ether`) that would size `tokensOut` above the now-inflated `realBalance`.
5. `Router._computeBuy` executes `cappedReserveToken = reserveToken - tokensOut` with `tokensOut = realBalance > reserveToken`, underflows, and the transaction reverts with `Panic(0x11)`, denying that buy (and any similarly sized buy) on the token going forward.

Note: I was not able to run this PoC in a live environment (no code execution available in this analysis mode); the reachability of each step is supported directly by existing test helpers (`_stageDonationAttack`, `test_donation_realBalanceExceedsReserveToken`, `test_inv_overflowCap_refundsLt`) in the repository, but the exact revert behavior of the combined donation + oversized-buy sequence against `Router._computeBuy` specifically was inferred from the code logic rather than an executed test — a background agent with test-execution access should add and run the regression test described above to confirm the Panic revert before treating this as fully confirmed.
