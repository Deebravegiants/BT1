## Analysis Result [1](#0-0) 

### Title
Nil Pointer Dereference in Gateway JSON-RPC Request Decoding via Missing `params` Field - (File: core/services/gateway/api/jsonrpccodec.go)

### Summary
`JSONRPCCodec.DecodeJSONRequest` unconditionally dereferences the request's `Params` pointer (`*request.Params`) without checking for `nil`, and this function is called directly on every raw request that reaches the gateway's internet-facing HTTP entrypoint, before any authentication, DON/service routing, or validation occurs.

### Finding Description
The gateway's `ProcessRequest` function is the entrypoint invoked by the HTTP server for every incoming client request: [2](#0-1) 

It first decodes the raw bytes into a generic `jsonrpc2.Request[json.RawMessage]`, then immediately calls `g.codec.DecodeJSONRequest(jsonRequest)`. Inside `DecodeJSONRequest`:

```go
func (*JSONRPCCodec) DecodeJSONRequest(request jsonrpc2.Request[json.RawMessage]) (*Message, error) {
	var msg Message
	err := json.Unmarshal(*request.Params, &msg)
```

`request.Params` is a `*json.RawMessage`. Per the JSON-RPC 2.0 spec, the `"params"` member is optional and MAY be omitted entirely by a client. If an unprivileged client sends a well-formed JSON-RPC envelope (valid version/method/id) but omits the `"params"` field — or explicitly sends `"params": null` (depending on how the underlying `jsonrpc2.DecodeRequest` populates the field) — `request.Params` will be `nil`, and `*request.Params` dereferences a nil pointer, causing a runtime panic.

Notably, other code paths in the same codebase that decode the legacy `params`-embedded message explicitly guard against this exact condition before dereferencing, e.g.: [3](#0-2) 

and the dummy handler: [4](#0-3) 

`DecodeJSONRequest` lacks this same nil check, making it inconsistent with the rest of the codebase's defensive pattern for handling optional `Params`.

This is directly analogous to CVE-2017-15019's root cause class: a parsing/decode routine that fails to validate a pointer/allocation result before dereferencing it, triggered by a malformed/incomplete externally supplied input on a code path reachable by any unauthenticated caller.

### Impact Explanation
A panic in `ProcessRequest` — the gateway's core HTTP request-processing function — would crash the goroutine handling that HTTP request. Depending on how the gateway's HTTP server recovers from panics (or fails to), this could crash the entire gateway process or terminate connection handling, resulting in denial of service for the internet-facing gateway shared by all DON nodes and users. Because `ProcessRequest` is called before any authentication or handler dispatch (`g.handlers`/`g.serviceToMultiHandler` lookups happen afterward), the crash is reachable by a completely unauthenticated, unprivileged actor.

### Likelihood Explanation
Triggering this requires only sending a single JSON-RPC 2.0 request to the gateway's HTTP endpoint omitting (or nulling) the `params` field — no authentication, signature, or prior state is required, since the panic occurs at line 28 before any of the version/method/ID/DON-ID/legacy-message validation logic in `gateway.go` executes.

### Recommendation
Add an explicit nil check on `request.Params` in `DecodeJSONRequest` (mirroring the pattern already used in `ValidatedMessageFromReq` and `handler.dummy.go`) and return a decode error instead of dereferencing, and/or ensure the gateway's HTTP handler has panic recovery middleware so any similar oversight cannot crash the whole server.

### Proof of Concept
Send a raw JSON-RPC request to the gateway's HTTP endpoint with a valid envelope but no `params` field, e.g.:
```json
{"jsonrpc":"2.0","id":"1","method":"anyMethod"}
```
If `jsonrpc2.DecodeRequest` does not itself reject requests with a missing `params` field (leaving `Params` as `nil` in the resulting struct), the subsequent call to `g.codec.DecodeJSONRequest(jsonRequest)` in `core/services/gateway/gateway.go:227` will panic at `json.Unmarshal(*request.Params, &msg)` in `core/services/gateway/api/jsonrpccodec.go:28`.

*Note: `jsonrpc2.DecodeRequest` itself lives in the `chainlink-common` dependency, which is outside this repository's index — confirming whether it always guarantees non-nil `Params` (and thus fully neutralizes this path) requires inspecting that library's source, which I could not access here. If `chainlink-common` already enforces non-nil `Params`, this finding would be mitigated at that layer; a Devin session with full repository/dependency access would be needed to verify this precisely.*
