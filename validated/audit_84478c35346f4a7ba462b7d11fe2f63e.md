### Title
Incomplete XRPL address equality allows bypass of token-self-send protection - (File: packages/intents-sdk/src/lib/compareAddresses.ts)

### Summary
`compareAddresses` uses raw string equality (`a === b`) for XRPL addresses, but `validateAddress`/`validateXrpAddress` accepts two different textual encodings (classic address and X-address) that can represent the same underlying account. An attacker can supply the token's custody/origin-chain address encoded as an X-address to bypass the `DestinationAddressMatchesTokenAddressError` self-send check in `poa-bridge.ts`.

### Finding Description
`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:207-219` calls `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)` to block withdrawals where the destination equals the token's own custody address on the destination chain — preventing funds from being irrecoverably sent back into the bridge's own vault/token address.

For XRPL, `validateAddress` (`packages/intents-sdk/src/lib/validateAddress.ts:47-48`, `333-335`) accepts both classic addresses (`xrp_isValidClassicAddress`) and X-addresses (`xrp_isValidXAddress`) as valid destination formats. An X-address is simply an alternate encoding that embeds the same classic account (plus an optional destination tag) — the same underlying account, e.g. `origin_chain_address = "rXXXX..."` can be equivalently expressed as `X7YYYY...`.

`compareAddresses` (`packages/intents-sdk/src/lib/compareAddresses.ts:48-60`) groups `Chains.XRPL` with `Near`, `Bitcoin`, `Cardano`, etc. and performs plain `a === b`. It contains no logic to decode an X-address into its underlying classic account before comparison (unlike the `Chains.Tron` branch, which normalizes base58/hex forms via `compareTronAddress`, or `Chains.TON`, which normalizes raw/friendly forms via `compareTonAddress`).

Consequently, if `tokenInfo.origin_chain_address` is a classic address `r...` and the attacker-supplied `destinationAddress` is the X-address encoding of that exact same account, `compareAddresses` returns `false` (not equal) even though both refer to the identical XRPL account. This breaks the equality the check is meant to enforce: "the destination address is not the token's own custody address."

### Impact Explanation
If exploited, a withdrawal that should be blocked as a self-send to the bridge's own custody address on XRPL instead proceeds. Funds would be transferred to the bridge's own vault account via an X-address alias, which is the exact condition `DestinationAddressMatchesTokenAddressError` exists to prevent. Per the rules, this maps to "a withdrawal stuck until manual intervention" / funds delivered into the bridge's own address that require the bridge operator to manually recover them rather than an ordinary user redemption path — a High-severity outcome, since the bridge account itself is not a normal user's address and receiving unexpected direct transfers there is treated by the bridge/back-office as an anomalous, manually-reconciled event. ### Likelihood Explanation
The attacker only needs to know the token's XRPL custody address (an on-chain, discoverable value returned by `getSupportedTokens`/`origin_chain_address`) and re-encode it as an X-address using the standard, publicly documented `ripple-address-codec` `classicAddressToXAddress` routine — the same library already imported by this SDK (`ripple-address-codec`) for the reverse operation. No privileged access or cooperation from the bridge/relayer is required; this is purely a client-side input-crafting exploit against the SDK's own validation logic.

### Recommendation
In `compareAddresses.ts`, add an XRPL-specific comparison branch (mirroring the Tron/TON pattern) that decodes both `a` and `b` via `xrp_isValidXAddress`/`xAddressToClassicAddress` when applicable, normalizes both to their classic-address + tag form, and compares those normalized values instead of raw strings.

### Proof of Concept
1. Suppose `tokenInfo.origin_chain_address` for XRP is the bridge's custody account `rBRIDGEVAULTADDRESSXXXXXXXXXXXX`.
2. Encode that same classic address as an X-address, e.g. via `ripple-address-codec`'s `classicAddressToXAddress('rBRIDGEVAULTADDRESSXXXXXXXXXXXX', false, false)` → `XVAULTXADDRESSFORM...`.
3. Call `bridge.validateWithdrawal({ assetId: "nep141:xrp.omft.near", amount: <amt>, destinationAddress: "XVAULTXADDRESSFORM..." })`.
4. `validateAddress` passes (X-address is a valid XRPL address form per `validateXrpAddress`).
5. `compareAddresses(origin_chain_address, "XVAULTXADDRESSFORM...", Chains.XRPL)` returns `false` because the raw strings differ, even though they resolve to the same account — so `DestinationAddressMatchesTokenAddressError` is never thrown, and the withdrawal proceeds to send funds to the bridge's own custody address encoded differently.
