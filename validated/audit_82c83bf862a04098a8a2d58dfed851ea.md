I have enough evidence to write up the finding. The core issue: `ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so the HMAC verification in `HmacValidator.validate` never covers the `shop` (tenant) identity header, yet `Registry.process` hands that unauthenticated `shop` value straight to the app's webhook handler as the trusted tenant identifier.

### Title
Webhook `shop` (tenant identity) field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body via `to_signable_string`, while the tenant-identifying `shop-domain` header is read separately and passed to the app's handler as trusted, verified data. Because the identity binding "HMAC-verified bytes == data acted on" only holds for the body and not for `shop`, any party who can obtain one genuine, HMAC-signed webhook delivery (e.g. by installing the app on their own store) can replay that same body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will treat the forged shop as authentic.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop` accessor pulls straight from the (fully attacker-controllable when replayed) HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop`, which is never part of the signed bytes: [4](#0-3) 

This breaks the intended identity binding: `bytes verified by HMAC == bytes/fields acted on by the app`. The `shop` field is acted on (passed to the handler, used by apps to scope database writes, credential lookups, and GDPR-type actions per the docs) but is not covered by the HMAC. Since Shopify's webhook signature is computed only over the body for a specific delivery, and the same app is shared across many merchant tenants, a merchant that installs the app on their own store (an ordinary, unprivileged action) legitimately receives real, validly-signed webhook deliveries for their own shop. That merchant can capture such a delivery's exact `body` + `hmac-sha256` header, then replay the identical HTTP request to the app's public webhook endpoint while changing only the shop-domain header to any other tenant's domain. `HmacValidator.validate` still succeeds because the signature only covers the unchanged body, and `Registry.process` forwards the forged shop straight to the handler as `data.shop`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker who is a legitimate (but unprivileged, relative to other tenants) merchant of the app can inject webhook events with attacker-controlled body content that the app will process as if they originated from a victim's shop. Depending on how the host app's handler uses `data.shop` (as most apps do, per the gem's own documentation example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data injection/corruption, triggering shop-scoped side effects (e.g. writing attacker data under a victim's shop record, or firing mandatory compliance topics like `customers/redact`/`shop/redact` for a shop the attacker doesn't own) purely because the shop identity field escapes HMAC coverage.

### Likelihood Explanation
Any user of the app (an "unprivileged internet user" relative to other tenants) can install the public app on their own store to legitimately receive at least one valid `(body, hmac)` pair, then trivially replay it against the app's public webhook HTTP endpoint with a modified shop header. No access to `api_secret_key`, access tokens, or privileged accounts is required — only capturing/replaying one's own genuine webhook traffic, which is fully within reach of a normal merchant/tenant.

### Recommendation
Include the tenant-identifying fields (at minimum `shop-domain`, ideally `topic` and `webhook-id` too) in the HMAC-covered signable string, or otherwise cryptographically bind them to the body (e.g. verify that `shop` matches an expected/pre-registered store instead of trusting the header verbatim). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC check and must be independently validated by host apps against their own known-shop list before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal merchant onboarding, unprivileged).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-topic: customers/redact`
   - Body: `{"customer": {"id": 123}, ...}`
3. Attacker captures this request and replays it to the same endpoint, changing only the shop header:
   - Headers: `x-shopify-shop-domain: victim-shop.myshopify.com`, `x-shopify-hmac-sha256: <same valid HMAC>` (unchanged), `x-shopify-topic: customers/redact`
   - Body: unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` returns only the unchanged raw body.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs whatever shop-scoped action the app implements for that topic, attributed to `victim-shop.myshopify.com` even though the request never originated from Shopify for that shop.
