### Title
Non-embedded session cookie carries an unsigned, predictable session id trusted verbatim, enabling session fixation / cross-tenant hijack - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser cookie's value directly to `session.id` (e.g. `"offline_{shop}"`, a pure deterministic function of the public shop domain), and `SessionUtils.cookie_session_id`/`current_session_id` return that raw cookie value with no signature, MAC, or shop re-verification of any kind. Any attacker who can send an HTTP request with a forged `shopify_app_session` cookie for a target shop domain can obtain that exact session id back from this gem, and if the host app (as documented) looks that id up in its own session storage, the attacker is handed the victim shop's stored session/access token.

### Finding Description
The intended binding, if one existed, would be:
`cookies[SessionCookie::SESSION_COOKIE_NAME] == a value that only the browser which completed Oauth.validate_auth_callback for shop S could ever possess`

In reality, the code enforces no such binding:
- `cookie_session_id` simply returns `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` unchanged: [1](#0-0) 
- `current_session_id`, when `Context.embedded?` is false (or when embedded but no `shopify_id_token` is present), routes directly to `cookie_session_id` with no additional check: [2](#0-1) 
- The value that legitimately gets placed into this cookie by `validate_auth_callback` is `session.id`, set as the raw cookie value with no HMAC/signature applied by the gem: [3](#0-2) 
- `session.id` for offline sessions is `offline_session_id(shop)` = `"offline_#{shop}"`, a value derived solely from the public shop domain string, with no random or secret component: [4](#0-3) 
- The gem's own docs instruct storing this value in a **plain** (not Rails `signed`/`encrypted`) cookie: [5](#0-4) 

Because `offline_#{shop}` requires only knowledge of the target's `*.myshopify.com` domain (routinely public/guessable), an attacker never needs to go through OAuth themselves for the victim shop. They simply send a request to any of the app's endpoints that call `SessionUtils.current_session_id` with `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`. The gem hands that string straight back as "the current session id," which per the gem's own documented usage pattern is then used by the host app to look up the (real, previously stored) session/access token for that shop: [6](#0-5) 

None of the existing guards intervene: `HmacValidator.validate` and the `state == auth_query.state` check in `validate_auth_callback` only protect the *initial* OAuth callback, not subsequent requests that read the cookie via `SessionUtils`; `Context.embedded?`/`Context.private?` gate which branch runs but add no cryptographic verification; there is no JWT path involved in the non-embedded/cookie branch at all.

### Impact Explanation
An attacker who knows or guesses a victim merchant's `*.myshopify.com` domain can, for a non-embedded app, forge the session-id cookie value and cause the host app (using this gem exactly as documented) to resolve the victim's own previously-stored session — including its access token — for use in the attacker's own request. This is cross-tenant access: one tenant's (attacker's) request retrieves and can act with another tenant's (victim's) session/access token. Every request against the app is independently forgeable this way; the attack is fully repeatable against any shop whose domain the attacker knows.

### Likelihood Explanation
Preconditions: the host app must be non-embedded (or embedded but falling back to the cookie path), configured and used as documented by this gem, and must already have completed OAuth for the victim shop at some point (i.e., a session already exists in the host's session storage for that shop id). The attacker needs no credentials, no browser same-site trickery, and no secret — merely knowledge of the target shop's domain, which is typically public (visible in storefront URLs, checkout pages, app-store listings). Cost is a single crafted HTTP request with a chosen `Cookie` header, fully within the attacker's declared capabilities.

### Recommendation
Do not use a predictable, unsigned value as the session-cookie payload. Sign/HMAC the cookie value (or wrap it with a MAC binding it to the shop and an app-secret-derived key) in `SessionCookie`/`Oauth.validate_auth_callback`, and have `SessionUtils.cookie_session_id` verify that signature before trusting the extracted id. Alternatively, use an unguessable random session identifier for the cookie value instead of the deterministic `"offline_#{shop}"` / `"#{shop}_#{user_id}"` strings, keeping those deterministic ids purely as internal storage keys never exposed to the client.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (illustrative addition)
def test_forged_offline_cookie_is_trusted_verbatim_for_non_embedded_app
  ShopifyAPI::Context.stubs(:embedded?).returns(false)

  forged_session_id = "offline_victim-shop.myshopify.com"
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_session_id }

  # Attacker never completed OAuth for victim-shop.myshopify.com, never held
  # api_secret_key, and never received a validly-signed callback for this shop.
  returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # Binding check: gem returns the attacker-forged id unchanged and unverified,
  # identical to what Oauth.validate_auth_callback would have produced for the
  # real victim session (ShopifyAPI::Utils::SessionUtils.offline_session_id("victim-shop.myshopify.com")).
  assert_equal(forged_session_id, returned_id)
  assert_equal(
    ShopifyAPI::Utils::SessionUtils.offline_session_id("victim-shop.myshopify.com"),
    returned_id,
  )
end
```
This demonstrates that `SessionUtils.current_session_id`/`cookie_session_id` return an attacker-chosen string identical to the real victim's legitimate session id with no signature or shop-ownership check, satisfying the broken-binding proof requested.

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
