### Title
Webhook shop/topic identity spoofing via headers not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and label the webhook to a handler are read from HTTP headers that are never included in the signed material. An attacker who obtains one legitimately-signed webhook body+HMAC pair (trivially available by installing the app on a shop they control and capturing the webhook Shopify sends to the app's endpoint) can replay that exact body/HMAC to the same endpoint while substituting an arbitrary `shop-domain` (and/or `topic`) header. The gem will accept it as valid and hand the forged `shop` value to the host application's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` is invoked with the `Webhooks::Request` object in `Registry.process`: [1](#0-0) 

The HMAC is validated against `to_signable_string`, which returns only the raw body: [2](#0-1) 

However `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers, which sit entirely outside the HMAC's signed scope: [3](#0-2) 

The header parsing/validation logic only checks for the *presence* of `topic`, `hmac-sha256`, and `shop-domain` headers (in either the legacy `x-shopify-*` or new `shopify-*` naming), never their integrity: [4](#0-3) 

Because the HMAC only binds the body bytes, `verifiable_query.hmac` being valid tells you nothing about which shop or topic header accompanied that body. The equality the code implicitly (and incorrectly) assumes is:

`shop header value == shop that produced the HMAC-signed body`

but the gem only proves:

`HMAC(secret, raw_body) == received_hmac`

These are not equivalent — the `shop-domain`/`topic` headers can be swapped on an intercepted, still-validly-signed body without invalidating the HMAC.

### Impact Explanation
The `Registry.process` method forwards the unauthenticated `shop` value straight to the registered `WebhookHandler`: [1](#0-0) 

Any application that uses `data.shop` from `WebhookMetadata` to select which merchant's tenant record to update (a standard pattern for webhook handlers, e.g., updating orders/inventory for "the shop in the webhook") can be made to apply Shopify-signed webhook body content under an attacker-chosen shop identity. This is a cross-tenant data confusion issue: an attacker-controlled shop can generate arbitrary signed webhook bodies (from their own store, using their own legitimate topics) and relabel them as originating from any victim shop domain, since nothing about the `shop-domain` header is authenticated.

### Likelihood Explanation
Exploitation only requires: (1) the attacker's own Shopify store subscribed to a webhook topic handled by the target app (trivial — installing the target app on a store the attacker controls), (2) capturing the raw body and `X-Shopify-Hmac-Sha256` value of a webhook Shopify sends for their own store, and (3) POSTing that exact body/HMAC pair to the app's public webhook endpoint with a forged `shop-domain` header. No credentials, access tokens, or `client_secret` knowledge are required — this is reachable by any unprivileged internet user/merchant.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the material verified against the HMAC (or otherwise separately authenticate the shop against an internally-tracked, trusted binding, e.g., a webhook subscription ID that is itself validated) rather than trusting headers that sit outside the signed body. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated and must not be used by host applications for tenant-scoping decisions without independent verification (e.g., cross-checking against the shop associated with a known, previously stored `webhook_id`/subscription).

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) for a resource the attacker fully controls.
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent for that request — this HMAC is valid because it was produced by Shopify using the app's real `api_secret_key` for the attacker's own store's payload.
3. Replay the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally alter `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds because the body is unmodified.
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's forged/controlled body content, despite Shopify never having sent this pairing.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
