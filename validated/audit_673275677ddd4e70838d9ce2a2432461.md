### Title
Unauthenticated Pipeline Task Resume Endpoint Allows Anyone to Inject Task Results and Force Job Run Completion - ([File: core/web/router.go])

### Summary
The route `PATCH /v2/resume/:runID` is registered on the unauthenticated route group (`unauthedv2`) in `core/web/router.go`, and dispatches to `PipelineRunsController.Resume`, which accepts an arbitrary `runID` (task UUID) and a caller-supplied JSON result body, then calls `App.ResumeJobV2` to inject that result into a paused pipeline task and resume the job run — with no authentication, authorization, or ownership check performed by the handler itself. [1](#0-0) [2](#0-1) 

### Finding Description
`v2Routes` mounts `unauthedv2.PATCH("/resume/:runID", prc.Resume)` outside of the `auth.Authenticate(...)`-wrapped `authv2` group used for every other job/pipeline-related endpoint (e.g. `/v2/jobs/:ID/runs`, `/v2/replay_from_block/:number`, etc., all wrapped with `auth.Authenticate` plus role checks like `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`). [3](#0-2) 

`PipelineRunsController.Resume` parses `runID` directly from the URL path into a task UUID, decodes an attacker-controlled JSON body into a `pipeline.ResumeRequest`, converts it into a `Result`, and calls `prc.App.ResumeJobV2(ctx, taskID, result)` without checking `auth.GetAuthenticatedUser` or `auth.GetAuthenticatedExternalInitiator` (unlike the sibling `Create` handler in the same file, which explicitly checks `isUser`/`isEI`). [4](#0-3) 

This mirrors the audit finding's root cause pattern: a state-mutating operation (`OperationsRegistry.addOperation` in the report; here, task-result injection that drives pipeline execution) is reachable with zero access control, relying solely on the caller supplying an identifier (an operation name in the report; a task UUID here) rather than any authenticated/authorized session. The only "protection" is that the UUID is meant to be unguessable, i.e., a bearer-token-in-URL pattern — but nothing in the code enforces that the caller is the intended external adapter/initiator that originated the pending task, nor limits how the endpoint may be abused if the UUID is exposed (e.g., via logs, error messages, browser history, referrer headers, proxies, or a compromised bridge/adapter).

### Impact Explanation
Because the endpoint is completely unauthenticated, anyone who obtains or guesses a valid task `runID` can:
- Inject arbitrary result data into a paused pipeline task, directly influencing downstream job outcomes (e.g., price/data values, VRF-adjacent flows, or any pipeline depending on external-adapter callbacks).
- Force resumption/completion of job runs without any role or session check, unlike every comparable operation elsewhere in the API which requires at least `run`/`edit`/`admin` role via `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`. [5](#0-4) 

This is functionally equivalent to the reported OperationsRegistry issue: a state-changing entry point that should require privileged/authorized access instead allows any unauthenticated actor to modify system behavior, compromising integrity/availability of job execution and potentially the correctness of on-chain reporting/aggregation, since bridge/task results feed into downstream trigger/aggregation logic.

### Likelihood Explanation
Exploitation requires knowledge of a valid pending task UUID. The application itself flags this handler specially by emitting the audit event `audit.UnauthedRunResumed`, an explicit acknowledgment that this call path is unauthenticated by design. [6](#0-5) 

While UUIDv4 has significant entropy making blind guessing impractical, the identifier can leak through operational channels (proxy/access logs, error responses, external-adapter logs, monitoring systems, or a compromised/malicious downstream HTTP consumer that the task result is meant to be posted to). Given the endpoint performs no authentication, no rate limiting was found in the route registration (unlike `sessionRoutes`, which explicitly wraps `/sessions` in a `rateLimiter`), and no binding to the specific external initiator/bridge that spawned the task, likelihood is elevated relative to a properly-authenticated design. [7](#0-6) 

### Recommendation
- Require the resume request to carry a credential(secret) tied to the specific bridge/task (e.g., a per-task signed token or the external initiator's outgoing token/secret) and verify it server-side before accepting the result, rather than relying solely on URL-embedded UUID secrecy.
- Alternatively, move this route into the authenticated `authv2` group and validate that the caller (external initiator or admin/run-role user) is authorized to resume that specific task/job.
- Add rate limiting and audit-based anomaly detection specifically for this endpoint given its unauthenticated nature.
- Document explicitly (as the audit report recommends for `OperationsRegistry`) the security model relied upon (capability-URL pattern) and ensure the UUID is never leaked via logs/headers.

### Proof of Concept
1. Create/observe a job that produces an external-adapter/bridge pipeline task, and note that its task/run UUID is returned or logged somewhere accessible (e.g., debug logs, error text, or a leaked internal API response).
2. Without any authentication (no session cookie, no API token, no `X-Chainlink-EA-AccessKey`/`Secret` headers), send:
   ```
   PATCH /v2/resume/<taskID>
   Content-Type: application/json

   {"data": {"result": "<attacker-controlled-value>"}}
   ```
3. Observe `prc.App.ResumeJobV2` completes the task with the attacker-supplied result and the pipeline run proceeds to completion, as confirmed by the route being registered under `unauthedv2` (no `auth.Authenticate` middleware) in `core/web/router.go` and the handler performing no user/EI check in `core/web/pipeline_runs_controller.go`. [8](#0-7) [4](#0-3) 

Note: I was unable to fully trace `ResumeJobV2`'s implementation and `UpdateTaskRunResult`'s state-machine checks (e.g., whether a task can only be resumed once, or whether it validates the task is actually awaiting a bridge callback) within the indexed codebase content, since the concrete `orm.go` implementation body and `application.go`'s `ResumeJobV2` body were not returned by the tools in this session. This limits certainty about secondary safeguards (idempotency/replay protection) beyond the confirmed lack of authentication at the HTTP layer. A Devin session with full repository access would be needed to verify these details conclusively.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
