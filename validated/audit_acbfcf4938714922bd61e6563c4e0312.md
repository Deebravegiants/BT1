### Title
`IntentGatewayV2.withdraw` (Tron) performs unconditional zero-value token transfers, permanently freezing escrowed intent funds - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` has a `withdraw()` function that iterates over a `WithdrawalRequest.tokens` array and unconditionally attempts an ERC20 `transfer` for every entry, including entries whose `amount` is `0`. Unlike the mainline EVM intents implementation (`IntentsBase._withdraw`), which explicitly skips zero-amount legs with `if (amount == 0) continue;`, this Tron contract has no such guard. If the transferred token reverts on zero-value transfers (a known non-standard ERC20 behavior), every call path that reaches `withdraw()` for that order commitment reverts permanently, locking the escrowed funds forever.

### Finding Description
`withdraw()` loops over `body.tokens`, and for every entry calls the token's `transfer` unconditionally: [1](#0-0) 

There is no `amount == 0` skip, unlike the equivalent function on the mainline EVM path: [2](#0-1) 

An order placer can construct an `Order` whose `inputs` array contains a duplicate entry for the same token with `amount = 0` listed *before* the entry carrying the real amount. This is only possible through the "predispatch" escrow path, which — unlike the plain escrow path that explicitly reverts on a zero input amount — performs no such validation: [3](#0-2) [4](#0-3) 

Because `_orders[commitment][token]` is summed across all entries for the same token at placement time, the escrow balance for that token becomes non-zero as soon as the real (non-zero) entry is accounted for, even though the zero-amount duplicate entry contributes nothing: [5](#0-4) 

`withdraw()` always replays `body.tokens` in the exact order recorded in the immutable order commitment. Because the zero-amount duplicate is listed first, the pre-transfer guard `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` passes (the escrow for that token is still non-zero, since the real amount hasn't been decremented yet), and the function proceeds to call `token.transfer(beneficiary, 0)`. If the token reverts on a zero-value transfer, the entire `withdraw()` call reverts.

`withdraw()` is reachable from every unprivileged settlement path for the order:
- Same-chain cancellation by the order's own user: [6](#0-5) 
- Cross-chain `RedeemEscrow`/`RefundEscrow` delivery via the ISMP host after relayer proof submission: [7](#0-6) 
- GET-response driven refund after a relayed cancellation proof: [8](#0-7) 

Since the token list, its ordering, and the amounts are all fixed inside the hashed `Order` (part of `commitment`), every future attempt to settle this specific order — fill, cancel, or refund — replays the identical sequence and reverts identically. The transaction revert is atomic, so `_orders[commitment][token]` is never actually decremented; the order is stuck in escrow permanently.

### Impact Explanation
Any escrowed input tokens (and the attached protocol/relayer fee token) tied to an order that is deliberately or accidentally crafted with a duplicate zero-amount entry preceding the real entry for a zero-value-transfer-reverting token become permanently unrecoverable — no fill, cancellation, or refund path can ever complete for that commitment. This is a permanent freezing-of-funds condition reachable purely through the normal `placeOrder`/predispatch flow, without any privileged action, satisfying the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
The order placer fully controls the `Order.inputs` array and can freely include a duplicate zero-amount leg via the predispatch escrow path, which has no zero-amount validation (unlike the plain escrow path). The only prerequisite is that the affected token disallows zero-value `transfer` calls — a documented behavior of several real-world ERC20 tokens (e.g., legacy LEND-style tokens referenced in the original report). No governance or privileged role is required; it is purely a user-triggered, self-contained escrow lock, matching the bug class described in the external report (loops performing unconditional token transfers for legs whose value can legitimately be zero).

### Recommendation
Mirror the guard already present in `IntentsBase._withdraw`: skip the transfer (and the underflow-prone `_orders[...] -= amount` decrement) whenever `amount == 0`, and additionally validate at `placeOrder` (including the predispatch branch) that no input entry has a zero `amount`, to eliminate the root cause of degenerate/duplicate zero-value legs entirely.

```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) { unchecked { ++i; } continue; }
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
}
```

### Proof of Concept
1. User calls `placeOrder` with `predispatch.call`/`predispatch.assets` populated (a minimal no-op call satisfies the branch condition) and `order.inputs = [{token: X, amount: 0}, {token: X, amount: 100}]`, where `X` is an ERC20 that reverts on `transfer(to, 0)`.
2. The predispatch branch in `placeOrder` accepts this without any zero-amount check; `_orders[commitment][X]` ends up at `100` (only the second entry contributes).
3. Later, the user calls `cancelOrder` (same-chain) or the order is filled/refunded cross-chain, invoking `withdraw(body, ...)` with `body.tokens = order.inputs` in the original order.
4. In `withdraw`, iteration `i=0` reads `amount = 0` for token `X`; the guard `_orders[commitment][X] == 0` is false (still `100`), so it proceeds to `X.transfer(beneficiary, 0)`, which reverts on-chain.
5. The whole transaction reverts; `_orders[commitment][X]` is never decremented. Every subsequent call to `cancelOrder`/`onAccept`/`onGetResponse` for this exact commitment replays the same sequence and reverts identically, permanently freezing the escrowed 100 `X` tokens (and any attached fee).
