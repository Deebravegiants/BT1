### Title
Webhook `shop-domain` header is trusted for tenant attribution without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body, while the `shop` value it exposes to application code is read verbatim from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header. `Registry.process` validates the HMAC over the body only and then hands `request.shop` straight to the app's `WebhookHandler` as the trusted tenant identifier, so the identity a handler acts on behalf of is never cryptographically bound to the payload that was verified.

### Finding Description
`to_signable_string` in `lib/shopify_api/webhooks/request.rb` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is pulled from a header supplied by whoever sends the HTTP request: [2](#0-1) 

`Utils::HmacValidator.validate` (shared by OAuth and webhooks) computes the signature purely from `verifiable_query.to_signable_string`, i.e. only the body for webhooks: [3](#0-2) 

`Registry.process` checks that HMAC and then immediately constructs `WebhookMetadata` using `request.shop` (the header) as the shop of record, passing it to the app-supplied handler as the authoritative tenant identity: [4](#0-3) 

The documented contract explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and shows it being used directly (e.g., enqueuing jobs keyed by `shop_domain: data.shop`): [5](#0-4) 

The identity binding broken here is:
`shop authenticated by HMAC (∅, since HMAC covers only body bytes)` ≠ `shop the app acts on behalf of (unauthenticated header value returned by request.shop)`.

Because the header is not part of the signed content, any party who can get one genuinely-signed webhook body/HMAC pair from Shopify (e.g., an app installed on their own store, an unprivileged merchant/tenant) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will pass the attacker-chosen shop domain to the handler as if it were verified.

### Impact Explanation
This is a cross-tenant identity-confusion primitive in the gem's own webhook-processing API: the gem markets `Registry.process`/`Request#shop` as verifying that "the request did indeed come from Shopify" (per `docs/usage/webhooks.md` line 125) and hands the shop domain to the handler as trusted metadata, but the shop attribution is not part of that verification. Any app that follows the gem's documented pattern of keying storage/jobs/state by `data.shop` (as the docs themselves recommend) can be made to attribute a real, validly-signed event to the wrong tenant, since the shop identity is fully attacker-controlled while the HMAC still validates. This matches the "Critical - cross-tenant access" impact category, because it lets one tenant's traffic be misattributed to another tenant purely by manipulating an unauthenticated header.

### Likelihood Explanation
Any unprivileged actor who can install the app on a shop they control (or otherwise observe one legitimate webhook delivery, including test/mandatory webhooks such as `customers/data_request`) obtains a body+HMAC pair that remains valid regardless of the `shop-domain` header sent with it. Replaying that request to the app's public webhook endpoint with a forged `shop-domain` header requires nothing but the ability to send an HTTP POST — no access token, secret, or privileged account is needed. This is directly reachable through the gem's own public `Registry.process`/`Request` API exactly as documented, not dependent on the host app misusing an undocumented feature.

### Recommendation
Include the shop domain (and topic/webhook id, if used for authorization decisions) in the signable string, or otherwise cryptographically bind the header value to the request before trusting it — e.g., validate that `request.shop` matches a shop the app expects for that specific `webhook_id`/subscription, or require the caller to independently confirm shop ownership before acting on `data.shop`. At minimum, document prominently that `data.shop` is not verified by the HMAC and must not be used as a sole tenant-authorization signal.

### Proof of Concept
1. App AttackerCo installs the target Shopify app on shop `attacker.myshopify.com` and configures a webhook (e.g. `orders/create`) pointing at the shared handler endpoint `/webhooks`.
2. Shopify delivers a legitimately signed webhook to the endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker.myshopify.com`.
   - Body: `{"id": 123, ...}` (attacker fully controls this content because it's their own store's order).
3. Attacker captures this raw body + HMAC pair (both are just observed, no secret needed).
4. Attacker crafts a new HTTP POST to the same endpoint reusing the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) — this matches, so validation passes: [6](#0-5) 
6. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "victim.myshopify.com"`, and the app's handler processes attacker-controlled data as if it originated from the victim shop: [7](#0-6)

          received_signature = verifiable_query.hmac

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

    def handle(data:)

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
