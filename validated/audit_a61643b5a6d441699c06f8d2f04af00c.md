### Title
Unvalidated route venues can attach unrelated wallet transfers to a signed strategy - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
A crafted `swap` route passed to `swap_collateral` can route execution through an attacker-controlled venue that requests the caller’s authorization for an unrelated token transfer. When transaction simulation records that transfer beneath the caller’s `swap_collateral` authorization and the caller signs the resulting tree, the rogue venue can drain wallet tokens unrelated to the lending position while still returning enough output to satisfy the controller’s balance checks.

### Finding Description
`swap_collateral` accepts caller-controlled opaque `swap` bytes and requires only caller/account-owner authorization before processing the strategy. [1](#0-0) [2](#0-1) 

`swap_tokens` forwards those bytes unchanged to the configured router and only constrains the controller’s own authorization to one exact `token_in.transfer(controller, router, amount_in)` invocation. [3](#0-2) [4](#0-3) 

After the router returns, the controller rejects input overspending and requires positive measured `token_out` receipt, but it does not constrain other authorization requests made by route-selected venue contracts during execution. [5](#0-4) 

The authorization test demonstrates the missing boundary: a router can invoke the `hop_pool` address supplied in the route payload, and that contract can call `token.transfer(victim, attacker, amount)` while the caller’s strategy authorization is active. [6](#0-5) [7](#0-6) 

Simulation places the rogue wallet transfer as a child of the victim’s `swap_collateral` authorization; enforcing execution then succeeds when the victim signs that generated tree. [8](#0-7) [9](#0-8) 

### Impact Explanation
An attacker can steal unrelated token balances from a strategy caller’s wallet by supplying a malicious route and having the caller sign the simulated authorization tree. [10](#0-9) [11](#0-10) 

This is theft of user funds, not merely poor swap execution: the malicious venue can return a fair `token_out` amount so the controller’s measured-output and final-risk checks still pass while an unrelated token leaves the caller’s wallet. [5](#0-4) [10](#0-9) 

The same mechanism is reachable through the other route-based controller strategies because they share `swap_tokens` or `swap_tokens_or_passthrough`, including `multiply`, `swap_debt`, and `repay_debt_with_collateral`. [12](#0-11) [13](#0-12) [14](#0-13) 

### Likelihood Explanation
The attack needs an unprivileged attacker-controlled route venue and a victim who signs a transaction containing the extra authorization child, so it is not a fully unilateral theft. [15](#0-14) [16](#0-15) 

However, the malicious transfer is introduced by opaque route bytes rather than by an explicit user-facing transfer request, making it suitable for a malicious quote, frontend, or copied route payload. [1](#0-0) [3](#0-2) 

The required protocol prerequisites are ordinary ones: the victim needs an owned or delegated account and a strategy call that produces a non-empty route; no privileged role, leaked key, upgrade, or token malfunction is required. [2](#0-1) 

### Recommendation
Restrict route-selected venue/pool addresses to a governance-approved registry or a verifiable list of audited venue contracts before executing strategy routes. [3](#0-2) 

As defense-in-depth, generated transactions and wallets should simulate strategy calls and reject any authorization tree containing children beyond the exact expected input transfer for a direct router call, or no caller children for a controller strategy’s expected authorization model. [8](#0-7) 

### Proof of Concept
1. Alice supplies USDC and owns a lending account; the attacker deploys a contract exposing the expected venue entrypoint and funds it with enough ETH to return a fair swap output. [17](#0-16) 
2. The attacker builds `swap` bytes whose venue address is the malicious contract, then causes Alice to invoke `swap_collateral(Alice, account_id, USDC_key, amount, ETH_key, crafted_swap)`. [18](#0-17) [19](#0-18) 
3. During route execution, the malicious venue calls `transfer(Alice, attacker, unrelated_token_balance)` and separately lets the route return valid ETH output. [7](#0-6) 
4. Simulation records the unrelated transfer beneath Alice’s `swap_collateral` authorization; after Alice signs that tree, the transaction succeeds, Alice’s unrelated token balance is zero, and the account receives the expected ETH collateral. [20](#0-19) [11](#0-10)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
