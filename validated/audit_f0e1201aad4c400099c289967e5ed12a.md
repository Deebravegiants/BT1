This confirms the vulnerability. The `_withdraw` function pulls tokens by `safeTransfer` based purely on the ledger amount stored in `_orders[commitment][token]`, with no reconciliation against actual contract balance [1](#0-0) . The Tron `IntentGatewayV2.placeOrder` credits this same ledger using the pre-transfer `order.inputs[i].amount` (minus only protocol fee) without ever measuring what the contract actually received via `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);` followed directly by `_orders[commitment][token] += reducedInputs[i].amount;` [2](#0-1) . This is in contrast to the audited/fixed EVM mainline `IntentGatewayV2.sol`, which explicitly snapshots balances before/after transfer and rewrites `order.inputs[i].amount` to the actual received amount specifically to handle fee-on-transfer tokens [3](#0-2) .

### Title
Tron IntentGatewayV2.placeOrder credits escrow ledger with pre-transfer amounts, enabling fee-on-transfer token insolvency and fund freezing - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` escrows input tokens via `safeTransferFrom` but credits the internal `_orders[commitment][token]` ledger using the nominal `order.inputs[i].amount` (reduced only by the protocol fee), never checking the actual token balance received by the contract [2](#0-1) . For a fee-on-transfer ERC20, the contract's actual balance increase is less than the credited ledger amount, creating a discrepancy between accounted escrow and real token holdings.

### Finding Description
`placeOrder` (non-predispatch branch) does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
``` [2](#0-1) 

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus a protocol fee percentage — it is never adjusted to the amount actually received by the contract [4](#0-3) . If `token` charges a transfer fee, the contract's real balance increases by less than `reducedInputs[i].amount`, but the ledger records the full nominal amount as escrowed.

Since `_orders` is a shared per-token accounting ledger across all commitments backed by one pooled token balance in the contract, this discrepancy is not isolated to the order that used the fee-on-transfer token — it silently reduces the pool of real tokens available to satisfy the escrow claims of *other* legitimate orders using the same token. When `_withdraw` later releases escrow via `safeTransfer(beneficiary, amount)` based purely on the ledger value [1](#0-0) , the contract can run short of actual token balance, causing legitimate withdrawals (fills or cancellations) for unrelated orders to revert — a form of protocol insolvency/fund freezing induced by a single fee-on-transfer order.

This is a regression relative to the fixed main EVM `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf(address(this))` before and after `safeTransferFrom` and overwrites `order.inputs[i].amount` with the actual delta received, precisely to prevent this class of bug [3](#0-2) . The Tron variant (and its predispatch branch, which similarly credits `reducedInputs[i].amount` from the requested amount rather than the measured post-transfer balance delta) has not been given the same fix [5](#0-4) .

### Impact Explanation
An attacker (or even an unwitting user) can place an order using a fee-on-transfer/deflationary ERC20 as an input token. The gateway over-credits the escrow ledger relative to actual token balance held. Because `_orders[token]` balances are shared across all commitments for that token, this creates a permanent deficit in the contract's real token balance versus its accounted liabilities. Subsequent legitimate solvers filling other orders denominated in the same token, or users cancelling/refunding, can have their `safeTransfer` calls revert due to insufficient actual balance — a concrete freezing of funds for unrelated, honest participants. This meets the Medium/High bar for permanent freezing of user/solver funds through an unprivileged, single-transaction `placeOrder` call.

### Likelihood Explanation
Likelihood is moderate-to-high in principle for any deployment that allows fee-on-transfer or deflationary tokens as escrow inputs, since `placeOrder` is a fully permissionless entry point reachable by any user in a single transaction, and no allowlist/validation rejects such tokens in the shown code path. Exploitation requires the gateway operator to permit at least one fee-on-transfer token as a supported input asset on the Tron deployment; if governance restricts inputs to well-behaved tokens only, likelihood drops, but the code itself provides no such protection unlike the already-patched EVM mainline contract.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot the contract's `balanceOf` before and after each `safeTransferFrom` in the Tron `placeOrder` (both the direct-transfer and predispatch/call-dispatcher branches), and credit `_orders[commitment][token]` using the actual measured delta rather than the nominal requested amount, adjusting the order's `amount` fields and emitted `OrderPlaced`/commitment accordingly so escrow accounting always matches real custody.

### Proof of Concept
1. Governance/deployer permits a fee-on-transfer token `FOT` (e.g., 5% transfer fee) as a valid input asset for the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000}` and no predispatch. `safeTransferFrom` moves 1000 nominal `FOT`, but the contract only receives 950 due to the transfer fee.
3. `_orders[commitment][FOT] += reducedInputs[0].amount` (≈1000 minus protocol fee, e.g. 990) is credited, even though the contract's real `FOT` balance only increased by 950 [6](#0-5) .
4. Because `_orders` is a shared ledger keyed by `(commitment, token)`, other unrelated orders in `FOT` remain unaffected individually, but the contract's aggregate real `FOT` balance is now insufficient to cover the sum of all `_orders[*][FOT]` entries by the missing 40 units (990 credited vs 950 held).
5. When a solver fills this order (or the user cancels after expiry) and `_withdraw` attempts `IERC20(FOT).safeTransfer(beneficiary, 990)` [7](#0-6) , if the contract's total `FOT` balance across all orders is already tight, this transfer can revert due to insufficient balance, or it succeeds by consuming tokens escrowed on behalf of another still-open order, which then cannot be withdrawn — demonstrating fund freezing caused entirely by the unadjusted escrow bookkeeping.
