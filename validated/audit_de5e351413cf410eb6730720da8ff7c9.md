### No vulnerability found for this question.

This describes the intended, documented design of Kubernetes RBAC, not an exploitable bug reachable by an unprivileged attacker.

`EscalationAllowed` in `pkg/registry/rbac/escalation_check.go` intentionally short-circuits all escalation checks the moment a request's user carries the `system:masters` group, because the API server itself uses that group for privileged loopback connections and treats it as unconditional superuser authority by design. [1](#0-0) 

Both `clusterrole` and `role` `policybased.Storage.Create`/`Update` check `EscalationAllowed(ctx) || RoleEscalationAuthorized(ctx, s.authorizer)` first, and if either is true, they call straight into `s.StandardStorage.Create`/`Update` without ever calling `ConfirmNoEscalationInternal`, `hasAggregationRule` checks, etc. [2](#0-1) [3](#0-2) 

This is fully expected: any identity in `system:masters` is already granted the built-in `cluster-admin` `ClusterRoleBinding` and is treated as an unconditional superuser everywhere in the API server, not just in this escalation check. The question's premise explicitly requires the attacker to already possess `system:masters` group membership "via a compromised... identity" or "accidentally applied... by a cluster operator" — i.e., the attacker is *not* unprivileged under the stated rules, since holding `system:masters` is equivalent to (and in fact stronger than) cluster-admin. The rules for this audit explicitly exclude scenarios requiring cluster-admin access or misconfiguration as the root cause ("Attacker is unprivileged only... No cluster-admin... access" and "Reject... misconfiguration-only paths"). There is no code path here that lets an ordinary namespace-scoped, non-`system:masters` identity forge or acquire this group membership — that would be a separate authentication/token-forgery bug, not something demonstrated in this code. Given the group membership as a precondition, the observed lack of namespace/resourceName scoping is not a bypass of any control; it is the documented behavior of a superuser group.

func (s *Storage) Create(ctx context.Context, obj runtime.Object, createValidatingAdmission rest.ValidateObjectFunc, options *metav1.CreateOptions) (runtime.Object, error) {
	if rbacregistry.EscalationAllowed(ctx) || rbacregistry.RoleEscalationAuthorized(ctx, s.authorizer) {
		return s.StandardStorage.Create(ctx, obj, createValidatingAdmission, options)
	}

	clusterRole := obj.(*rbac.ClusterRole)
	rules := clusterRole.Rules
	if err := rbacregistryvalidation.ConfirmNoEscalationInternal(ctx, s.ruleResolver, rules); err != nil {
		return nil, apierrors.NewForbidden(groupResource, clusterRole.Name, err)
	}
	// to set the aggregation rule, since it can gather anything, requires * on *.*
	if hasAggregationRule(clusterRole) {
		if err := rbacregistryvalidation.ConfirmNoEscalationInternal(ctx, s.ruleResolver, fullAuthority); err != nil {
			return nil, apierrors.NewForbidden(groupResource, clusterRole.Name, errors.New("must have cluster-admin privileges to use the aggregationRule"))
		}
	}

	return s.StandardStorage.Create(ctx, obj, createValidatingAdmission, options)
}
