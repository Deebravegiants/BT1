### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) that the host application acts on directly from unauthenticated HTTP headers, while the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. This breaks the identity binding `hmac(raw_body) == verified` vs. `shop used for tenant routing == shopify-shop-domain header (unverified)`. An attacker who obtains any single valid `(raw_body, hmac)` pair signed with the app's secret (e.g. by triggering a webhook on their own connected store) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, causing the app to process/attribute that payload to a victim shop it does not control.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all read straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes an HMAC over `to_signable_string` (the body only) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` validates only this body HMAC, then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` struct passed to the host app's `WebhookHandler#handle`: [4](#0-3) [5](#0-4) 

The identity equality that should hold is: `shop bound in the HMAC-signed payload == shop the handler is told to act on`. In this gem, the equality actually enforced is: `hmac(raw_body) == hmac(raw_body)` (body integrity only) while `shop` is taken from a header that is completely outside that signed scope. Any request whose body/HMAC pair is valid — regardless of who or which shop it was originally issued for — will pass `HmacValidator.validate` no matter what `shopify-shop-domain` value is attached, because the header is never part of the signable string.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook dispatch logic (`Registry.process` → `WebhookHandler#handle`) will process data purportedly belonging to any shop the attacker names in the `shopify-shop-domain` header, as long as they can produce a body/HMAC pair that authenticates under the app's shared `client_secret`. Depending on how the host application implements `WebhookHandler#handle` (which the gem's documented contract assumes will use `data.shop` to select which merchant's records to create/update/delete, per `WebhookMetadata`), this allows an attacker to inject data under, or trigger destructive operations against (e.g. `customers/redact`, `shop/redact` style flows), a victim merchant they have no access to — a cross-tenant access violation, which the rules classify as Critical impact.

### Likelihood Explanation
The attacker does not need the app's `client_secret`, an access token, or any privileged credential belonging to the victim shop. They only need one legitimately signed `(raw_body, hmac)` pair, which is straightforward to obtain: register the same app on a shop they control (or otherwise legitimately receive a webhook) and capture the delivered body and `X-Shopify-Hmac-Sha256` header. They then replay that exact body+HMAC to the app's public webhook endpoint with a forged `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header. No TLS interception, social engineering, or victim credentials are required — only network access to the app's webhook endpoint, which is unprivileged by design (Shopify webhook endpoints are public HTTP endpoints).

### Recommendation
Bind the tenant-identifying headers into the signed material, or otherwise cryptographically tie them to a known-good value before trusting them:
- Do not rely on `shopify-shop-domain` (or `topic`/`webhook-id`) for authorization/routing decisions unless it is verified against an independently established relationship (e.g., look up the session/shop record associated with the webhook subscription ID returned by Shopify, rather than trusting the header verbatim).
- At minimum, document/enforce that `Registry.process` callers must cross-check `request.shop` against an expected shop context (e.g., the shop associated with the specific webhook endpoint or subscription) rather than treating the header as authenticated merely because the body HMAC validated.
- Consider including the shop domain in the value that is HMAC-verified, or validate it out-of-band (e.g., via a separate registered callback URL per shop) so that spoofing the header alone cannot redirect payload processing to an arbitrary tenant.

### Proof of Concept
1. Attacker installs/operates the same app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing:
   - raw body `B`
   - header `X-Shopify-Hmac-Sha256: H` (valid, since it's signed with the real `client_secret` for a legitimate delivery)
2. Attacker sends a forged POST to the app's webhook endpoint with:
   - body = `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since HMAC only covers body)
   - header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired
3. The gem's flow:
   - `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` succeeds (all required headers present).
   - `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes: [6](#0-5) 
   - `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop: "victim-shop.myshopify.com"` even though the payload/HMAC were never issued for that shop: [7](#0-6) 
   - The host app's `WebhookHandler#handle` receives this metadata and acts as if the event genuinely originated from `victim-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
