## Title
OAuth callback lets an attacker-chosen `shop` value (not restricted to trusted Shopify domains) determine the host that receives `client_secret` and the authorization `code` - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request host directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-exchange flow in the gem (`client_credentials.rb`, `refresh_token.rb`), which explicitly validate the `shop` value against `TRUSTED_SHOPIFY_DOMAINS` before using it to construct the request host.

### Finding Description
`validate_auth_callback` only checks that `auth_query.hmac` is a valid HMAC over the `code/host/shop/state/timestamp` tuple [1](#0-0) , then immediately uses the raw `auth_query.shop` string to build the session and HTTP client that will POST the app's `client_id`, `client_secret`, and the OAuth `code` to `https://#{shop}/admin/oauth/access_token`: [2](#0-1) 

`HttpClient#initialize` derives the request host directly from `session.shop` with no format check: [3](#0-2) 

Compare this to the two other credential-exchange call sites in the same gem, `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, both of which call `Utils::ShopValidator.sanitize!(shop)` before ever constructing a `Session`/`HttpClient`: [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!`/`sanitize_shop_domain` exists specifically to restrict the value used as a request host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) and to reject any string that doesn't resolve to one of those domains: [6](#0-5) 

`oauth.rb`'s `validate_auth_callback` is the one flow in the credential-exchange family that skips this validator entirely, relying solely on `Utils::HmacValidator.validate(auth_query)`. That validator confirms the query string was signed with `api_secret_key`, but it never constrains `shop` to be a `*.myshopify.com`/trusted-domain value — it will happily accept and pass through an HMAC that was computed (with the app's own valid secret, via any flow that lets the value be echoed back, e.g., a custom/private app owner replaying their own signed values, or any code path that constructs an `AuthQuery` from externally-influenced parameters such as the documented `request.parameters.symbolize_keys` pattern) over a `shop` field containing an arbitrary hostname: [7](#0-6) 

The binding that should hold is: *the shop value validated as a trusted Shopify host == the shop value that receives the app's `client_secret`*. In every other flow this is enforced (`ShopValidator.sanitize!`); in `validate_auth_callback` this binding is broken because there is no domain allow‑list check on `auth_query.shop`, only an HMAC integrity check with no domain constraint on the signed content.

### Impact Explanation
If `auth_query.shop` can carry a non-Shopify hostname at the point `validate_auth_callback` is invoked (e.g., because the host application builds the `AuthQuery` from raw callback parameters as shown in this gem's own `docs/usage/oauth.md` example, `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters.symbolize_keys.except(:controller, :action))`, and an attacker can supply/influence any of these parameters before the HMAC check consumes them), the app's `client_secret` and the just-obtained authorization `code` would be sent via SSRF to an attacker-controlled host. This matches the "High - SSRF with the app's credentials" category since the app's `client_secret` and OAuth `code` are exfiltrated to a host that was never checked against `TRUSTED_SHOPIFY_DOMAINS`.

### Likelihood Explanation
Exploitation requires the attacker to produce a value for `shop` (and the corresponding HMAC) that this gem will accept without the domain allow-list check enforced elsewhere in the same gem. Because `HmacValidator.validate` only proves that the string was signed with the app's own `api_secret_key`/`old_api_secret_key`, it does not independently constrain `shop` to a Shopify domain — the domain restriction is enforced only via the separate, and here unused, `ShopValidator`. Given this gem explicitly maintains `ShopValidator` and applies it in the two structurally similar credential-exchange flows but omits it in `validate_auth_callback`, this is a genuine inconsistency in the library's own trust boundary rather than merely a host-application misuse of a documented, safe API.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, `validate_auth_callback` should call `Utils::ShopValidator.sanitize!(auth_query.shop)` (as `client_credentials.rb` and `refresh_token.rb` already do) before constructing `null_session`/`Session.from`, so that the host receiving `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of what value was present in the (merely integrity-checked, not domain-checked) `shop` field of the callback query.

### Proof of Concept
1. An app builds `ShopifyAPI::Auth::Oauth::AuthQuery` from callback parameters as shown in the gem's own documentation (`docs/usage/oauth.md`), i.e., directly from request parameters.
2. If an attacker can influence the `shop`/`hmac` pair fed into this constructor (for example, through any code path that lets externally-controlled values reach `AuthQuery` before `validate_auth_callback` is called, since the gem's own contract for this constructor is "pass request parameters directly"), `Utils::HmacValidator.validate` only confirms internal consistency of the signed tuple against the app's secret — it does not confirm `shop` is `*.myshopify.com`.
3. `validate_auth_callback` then does: `null_session = Auth::Session.new(shop: auth_query.shop)` → `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` → POST to `https://#{auth_query.shop}/admin/oauth/access_token` with body `{ client_id, client_secret, code, expiring }`.
4. Because `shop` was never passed through `Utils::ShopValidator.sanitize!`, this request host is unconstrained, in contrast to `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which reject any `shop` not matching `TRUSTED_SHOPIFY_DOMAINS` before making the identical `client_secret`-bearing request.

      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
