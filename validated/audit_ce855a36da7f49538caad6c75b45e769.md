### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, while the `shop` value that identifies which tenant the webhook belongs to is taken from an HTTP header that is never included in that signature. Since the HMAC secret (`api_secret_key`) is shared by every shop that has installed a given app, any shop that has legitimately installed the app can capture one of its own validly-signed webhook deliveries and replay the exact body with a different `x-shopify-shop-domain`/`shopify-shop-domain` header value, producing a request that still passes HMAC validation but is attributed to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read straight from a header that is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over `to_signable_string` (i.e., the body) and compares it to the `hmac` header — the `shop` header plays no role in the comparison: [3](#0-2) 

`Registry.process` uses this same HMAC check as its sole authenticity gate, then forwards the unverified `request.shop` value straight to the app's handler as the tenant identifier: [4](#0-3) 

The binding that should hold is: `shop header trusted by handler == shop bound into the HMAC-signed bytes`. It does not hold — the HMAC only binds the body, not the shop. Because `api_secret_key` is the same for every shop that installs a given app (not a per-tenant secret), any shop that has installed the app (an "unprivileged" tenant relative to other tenants of the same app) can obtain a genuinely Shopify-signed `(body, hmac)` pair for its own webhook traffic, then replay that exact pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `HmacValidator.validate` still returns `true` (the body/hmac pair is authentic), and `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the attacker-chosen value.

The gem's own documentation reinforces the false guarantee, describing `process` as verifying "the request did indeed come from Shopify" and presenting `data.shop` as a trustworthy per-webhook value that application code should key its records on: [5](#0-4) [6](#0-5) 

### Impact Explanation
An app author following the gem's documented pattern uses `data.shop` as the tenant key when persisting or acting on webhook payloads (as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). A malicious merchant who has installed the app can forge webhook deliveries that the app will process as belonging to a different, victim shop, causing cross-tenant data injection/corruption in the app's backend under the shared multi-tenant `api_secret_key` model. This matches the Critical "cross-tenant access" impact category, since the identity of the tenant is not cryptographically bound to the authenticated payload.

### Likelihood Explanation
Exploitation only requires being a legitimate, unprivileged installer of the target app (any internet user can install most public Shopify apps) and the ability to capture one of their own shop's webhook deliveries and replay it with a modified header — no access to `api_secret_key`, access tokens, or any other shop's credentials is required.

### Recommendation
Bind the shop identity into the authenticated bytes: either include the shop domain (and topic/webhook-id) in the HMAC-signable string, or independently verify the header-derived `shop` value against a durably associated identifier (e.g., look up the recipient shop from an existing session/webhook subscription record rather than trusting the header outright) before dispatching to the handler. At minimum, document explicitly that `data.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, becoming a legitimate recipient of Shopify webhooks signed with the app's shared `api_secret_key`.
2. Attacker triggers an event (e.g., updates a product) to receive a genuine webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker resends the exact same `B`/`H` pair to the app's webhook endpoint, replacing `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in [3](#0-2)  succeeds because `B`/`H` still match.
5. `Registry.process` in [4](#0-3)  dispatches to the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the app to record/act on attacker-controlled data as if it originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
