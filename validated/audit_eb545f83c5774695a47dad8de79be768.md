### Title
Protocol fee floors to zero on IntentGatewayV2 `placeOrder`, letting an attacker split same-chain self-fills to avoid protocol fees - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2::placeOrder` computes the protocol fee taken from each order input with truncating integer division, `protocolFee = (originalAmount * protocolFeeBps) / 10_000`, instead of rounding up. This is the exact same rounding-direction defect as the DeliHook `baseFeeSpecified` bug: any `originalAmount` below `10_000 / protocolFeeBps` pays zero protocol fee, and an attacker can repeatedly place/self-fill tiny same-chain orders of a low-decimal, high-unit-value token to extract many rounding-down "free" fee windows.

### Finding Description
`placeOrder` deducts the protocol fee before escrowing and hashing the order commitment: [1](#0-0) 

`protocolFee = (originalAmount * protocolFeeBps) / 10_000` truncates toward zero. Whenever `originalAmount * protocolFeeBps < 10_000`, `protocolFee` evaluates to `0` and no `DustCollected` event fires, meaning the order pays no protocol fee at all — this is functionally identical to `DeliHook::_beforeSwap()` rounding `baseFeeSpecified` down instead of up. The same floor-division pattern exists in the Tron deployment of the contract: [2](#0-1) 

and in the surplus split helper used across withdrawals: [3](#0-2) 

`placeOrder` is reachable by any unprivileged address submitting an ordinary transaction (a "message dispatcher"/order placer), and for same-chain orders the fill can be self-serviced with `order.fees = 0` (demonstrated in the test suite, e.g. `testSameChainSwap_WithProtocolFee`), meaning an attacker acting as both order placer and solver pays no separate relayer/solver premium to offset the rounding loss — unlike a cross-chain order, which must carry `order.fees` to cover the settlement relayer.

The threshold at which `protocolFee` floors to zero is `originalAmount < 10_000 / protocolFeeBps`. With the documented production default of 5 bps, that threshold is `originalAmount < 2000` raw token units. For a token with few decimals and high USD value per unit (e.g., an 8-decimal wrapped BTC-style asset), 2000 raw units is a fraction of a cent-scale trade, but the point of the abuse is repetition: an attacker splits what would be one large, fee-bearing order into many same-chain self-filled orders each individually sized just under the flooring threshold, paying $0 protocol fee on each, and repeats this at scale since same-chain placeOrder→fillOrder round trips only cost L2 gas.

### Impact Explanation
Every order routed this way causes the protocol to collect strictly less (down to zero) of the `protocolFeeBps` revenue it is entitled to on that input, with the truncated fraction retained by the attacker rather than the gateway (analogous to the original report's "100% fee loss for users of the protocol"). Because `protocolFeeBps` and the flooring threshold are public, deterministic, and the same-chain self-fill path requires no `order.fees` payment, an attacker can structure trade flow to systematically avoid this revenue stream, degrading protocol fee income (`DustCollected`) that funds governance-swept dust. This is a fee-bypass class issue: concrete, repeatable underpayment of protocol fees rather than a one-off rounding artifact.

### Likelihood Explanation
Likelihood is constrained relative to the original DeliHook report: DeliHook's exploit was a single, cheap, atomic swap-loop against a hook with no counterparty requirement. Here, each abuse cycle requires a full `placeOrder` + `fillOrder` pair (two state-changing calls, event emission, storage writes for escrow/commitment tracking) even in the self-fill, zero-fee, same-chain case, so the gas cost per iteration is materially higher than a bare swap. The attack is only economically attractive when: (1) the input token has very high value per raw unit (low decimals) so the truncated fee fraction is worth more than gas, and (2) the attacker is willing to self-fill (own both sides of the trade) to avoid paying an offsetting solver/relayer fee. These conditions are plausible for governance-configured low-decimal, high-value tokens but not universal across all IntentGatewayV2 traffic, so likelihood is medium.

### Recommendation
Round the protocol fee up, mirroring the SDK's own `divCeil` mitigation already used elsewhere in the code (`grossUpForProtocolFee` / `divCeil` in `sdk/packages/sdk/src/protocols/intents/quote/shared.ts`), inside the on-chain `placeOrder` fee computation in `evm/src/apps/IntentGatewayV2.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`, and any downstream fee-splitting math in `evm/src/apps/intentsv2/IntentsBase.sol::_splitSurplus`, so `protocolFee = ceil(originalAmount * protocolFeeBps / 10_000)` and no order can be structured to pay strictly zero fee when `protocolFeeBps > 0`.

### Proof of Concept
1. Governance configures `protocolFeeBps = 5` (documented production default) on `IntentGatewayV2`.
2. An attacker who also controls a solver address places a same-chain order with `order.fees = 0` and `order.inputs[0].amount = 1999` (raw units of a low-decimal, high-value input token), which is below the `10_000/5 = 2000` flooring threshold, per the fee logic at [4](#0-3) .
3. `protocolFee` computes to `0`; no `DustCollected` event fires and the full `1999` units are escrowed and released to the attacker's own solver address on self-fill.
4. Repeating steps 2–3 across many orders lets the attacker move an arbitrarily large aggregate notional through the gateway while the protocol fee floors to zero on every individual order, in contrast to placing one large order of the same aggregate size, which would correctly charge `floor(amount*5/10000)` fee proportional to the full notional.
