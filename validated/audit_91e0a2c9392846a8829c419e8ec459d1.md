### Title
Webhook shop-domain header is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are taken directly from HTTP headers that are never included in the HMAC-signed material. Any party who can obtain one validly-signed webhook body (e.g. by installing the app on their own store) can replay that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, causing the payload to be processed and attributed to a victim shop of the attacker's choosing.

### Finding Description
`HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw request body: [2](#0-1) 

But the `shop` (and `topic`/`webhook_id`/`api_version`) accessors used downstream are pulled straight from HTTP headers that are not part of the signed string at all: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then unconditionally trusts `request.topic` and `request.shop` to dispatch to a handler and build the `WebhookMetadata` that is handed to app code as the tenant identity for this event: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(body) == true` is treated as `shop_header == authentic_source_shop`, but the equality that is actually cryptographically proven is only `hmac_valid(body)`, with `shop` header being an independent, unauthenticated field. Since the HMAC secret (`api_secret_key`) is the same for every shop that installs a given app, anyone who can trigger a webhook from a store they control (a free/dev store with the app installed is sufficient — no privileged credentials or leaked secrets required) can capture a validly-signed `(body, hmac)` pair, then POST it to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header for a different, victim shop.

### Impact Explanation
The app's webhook handler receives `WebhookMetadata` with an attacker-chosen `shop` value while the HMAC check passes, because the shop field is never bound to the signature. Any app logic that uses `WebhookMetadata#shop` to look up per-tenant records, update per-shop state, or otherwise key data by shop domain can be tricked into acting on/for a shop the attacker does not own — a cross-tenant data integrity issue reachable by an unprivileged internet user with no access token, client secret, or leaked credential. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any shop the attacker controls (freely obtainable via a Shopify partner/dev store) to receive one legitimately-signed webhook body+HMAC pair, and (2) replaying that exact body/HMAC to the app's public webhook endpoint with a modified shop-domain header. No secrets, tokens, or privileged access are needed, and the gem performs no additional binding of the shop header to the signed payload nor any sender IP/host validation.

### Recommendation
Include the shop domain (and ideally the topic) in the material that is verified, e.g. bind `to_signable_string` (or a separate check in `Registry.process`) to also validate that `request.shop` matches an expected/allow-listed value, or extend the signable string used for HMAC comparison to incorporate the header fields the app trusts, so that a replayed body cannot be re-attributed to an arbitrary shop.

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify — this HMAC is valid because it's computed with the app's real `api_secret_key` against the raw body only.
2. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and any desired `x-shopify-topic`).
3. `HmacValidator.validate` passes because it only checks `Digest.hexencode(...)` against `@raw_body`, per `lib/shopify_api/webhooks/request.rb:11-13,35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process/attribute the event as if it came from the victim shop.
