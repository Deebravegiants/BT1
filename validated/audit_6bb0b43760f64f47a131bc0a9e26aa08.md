### Title
Connected-origin authorization checks trust of the origin but not the specific wallet account, leaking addresses of unrelated accounts - (File: features/connected-origins/module/connections.js)

### Summary
The Astaria report's root cause is that `lendToVault` authorizes based on a coarse check (`vaults[address] != 0`) that does not verify the specific type/scope of the resource being accessed (`PublicVault` vs `PrivateVault`), letting an unintended actor interact with a resource it was never meant to reach. The Hydra analog is `ConnectedOrigins.getConnectedAccounts`, which authorizes disclosure of wallet-account addresses to a dapp origin using only a coarse `isTrusted({ origin })` check, without confirming that the specific wallet account(s) being returned are the ones the user actually consented to share with that origin.

### Finding Description
`ConnectedOrigins#getConnectedAccounts` gates the entire response on origin-level trust only: [1](#0-0) 

It then iterates over **every entry** in `#connectedAccountsAtom` (which is populated from `#enabledWalletAccountsAtom`, i.e. all enabled wallet accounts in the wallet) and returns their addresses for the origin's `assetNames`, regardless of which specific `walletAccount` was actually selected/consented at connect time: [2](#0-1) 

Note that a `walletAccount` field is stored per connection when adding an origin: [3](#0-2) 

but this stored `walletAccount` field is never consulted by `getConnectedAccounts` (or `isTrusted`) to scope which accounts' addresses are disclosed — the only check performed is `isTrusted`: [4](#0-3) 

This is structurally identical to the Astaria bug class: an authorization mapping/check (`vaults[addr] != 0` / `isTrusted(origin)`) validates *that* the caller has *some* relationship to the system, but not *which specific resource* (vault type / wallet account) that relationship was scoped to, so the broader set of resources (all vaults / all wallet accounts) becomes reachable.

### Impact Explanation
Any dapp origin that becomes "trusted" (even by connecting a single, perhaps disposable/low-value wallet account) can call `connectedOrigins.getConnectedAccounts` and receive addresses for **all** enabled wallet accounts in the user's wallet for the connected asset(s), not just the account(s) the user explicitly authorized for that origin. This breaks account isolation: it allows an origin to link/deanonymize a user's other, unrelated accounts (including accounts the user never intended to expose to that site), which is a privilege/data bleed across account boundaries. The `connectedAccountsAtom` explicitly sits on "unsafe" storage designed to work without unlocking the wallet, so this address enumeration can also occur in a locked-wallet state, increasing exposure: [5](#0-4) 

### Likelihood Explanation
Any web page a user connects to (even via a single low-trust dapp) can trigger this by simply calling the exposed `connectedOrigins.getConnectedAccounts` API once trust is established — no additional user interaction is required, and the multi-account test fixtures confirm the current behavior returns all accounts, not just the connected one: [6](#0-5) 

### Recommendation
Scope `getConnectedAccounts` (and the underlying `#connectedAccountsAtom` population) to only the wallet account(s) recorded in the origin's `walletAccount`/consented-accounts field, rather than returning addresses for all enabled wallet accounts. Require an explicit per-account grant list per origin and filter the returned addresses against that list before returning them to the caller.

### Proof of Concept
1. User visits `exodus.com`, connects wallet account `exodus_0` for `solana`; `connectedOrigins.add({ origin: 'exodus.com', connectedAssetName: 'solana', assetNames: ['solana'], trusted: true, walletAccount: 'exodus_0' })` is called.
2. The wallet independently has a second, unrelated account `exodus_1` (never shared with `exodus.com`).
3. The connected dapp calls `exodus.connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })`.
4. As shown by the existing test at [6](#0-5)  the response includes the address of `exodus_1` as well, even though it was never granted to that origin — confirming the account-isolation bleed.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }

```javascript
import { createStorageAtomFactory, dedupe } from '@exodus/atoms'

/**
 * This atom caches addresses of connected accounts so they can be used when eagerly connecting without a user interaction.
 * We cannot use address provider in that case because the wallet may not be unlocked. This atom however sits on top of
 * the unsafe storage.
 */
export default function createConnectedAccountsAtom({ storage }) {
  return dedupe(
    createStorageAtomFactory({ storage })({
      key: 'accounts',
      defaultValue: {},
      isSoleWriter: true,
    })
  )
}
```
