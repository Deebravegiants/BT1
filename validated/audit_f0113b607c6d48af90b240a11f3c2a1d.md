Confirmed: the Tron `IntentGatewayV2.placeOrder` (unlike the mainline EVM version) never refunds leftover `msgValue` after the fee swap — this is the strongest analog to the reported bug class.

### Title
Excess native token sent to `placeOrder` is permanently stuck in Tron `IntentGatewayV2` - (evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.sol`, `placeOrder()` accepts native token (`msg.value`) both for ERC20-only orders (mistakenly) and for paying `order.fees` via a Uniswap swap, but never refunds unused native to the caller. The mainline EVM `IntentGatewayV2.sol` at `evm/src/apps/IntentGatewayV2.sol` explicitly refunds unspent `msgValue` at the end of `placeOrder`; the Tron port at `evm/tron/contracts/apps/IntentGatewayV2.sol` omits this refund entirely.

### Finding Description
`placeOrder()` tracks a local `msgValue` counter starting at `msg.value` [1](#0-0) . For each input token, if the token is `address(0)` the required amount is deducted from `msgValue`; for ERC20 inputs, `msgValue` is left untouched even though the user may have sent native token along with an all-ERC20 order [2](#0-1) .

When `order.fees > 0`, if `msgValue > 0` the contract swaps native for the exact fee-token amount via `swapETHForExactTokens{value: msgValue}` — this call only consumes the ETH necessary to produce `order.fees` fee tokens and refunds any leftover ETH to the caller of the swap, which is the `IntentGatewayV2` contract itself (not the end user) [3](#0-2) .

After this block the function immediately emits `OrderPlaced` and returns, with no code path that returns any residual native balance to `msg.sender` [4](#0-3) .

Contrast this with the mainline (non-Tron) `IntentGatewayV2.placeOrder`, which performs the identical fee-swap accounting but then explicitly refunds any leftover native token to `msg.sender`: [5](#0-4) 

This is the exact bug class from the referenced report: a function that branches on token type (native vs ERC20) fails to account for / return excess `msg.value` sent alongside an ERC20 flow, and additionally, even in the native-fee-payment flow, any swap-induced dust is not returned to the user, only ever recoverable by the contract owner via a `SweepDust`-style admin flow (not by the depositor).

### Impact Explanation
Any native token sent to `placeOrder` beyond what is strictly consumed by native inputs and the fee-token swap becomes permanently stuck in the contract with no method for the original depositor to reclaim it. This directly matches "concrete... permanent freezing of funds" for end users interacting with this reachable, unprivileged entry point (anyone calling `placeOrder` can trigger fund loss for themselves, and gas-price/slippage variance in `swapETHForExactTokens` makes some residual dust essentially unavoidable even for careful callers).

### Likelihood Explanation
High likelihood: any user who (a) places an all-ERC20 order but attaches nonzero `msg.value` (e.g., wallet/SDK misconfiguration, or copying calldata from a native-input order template), or (b) pays `order.fees` in native token and the Uniswap swap consumes slightly less than the full `msg.value` due to price movement, will lose the excess. This is a routine operational path (fee payment via native swap), not an edge case requiring privileged or adversarial behavior.

### Recommendation
Mirror the mainline EVM contract's behavior: after all escrow and fee-swap accounting, refund any remaining `msgValue` to `msg.sender`:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    (bool sent, ) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
placed just before the `OrderPlaced` event emission, matching `evm/src/apps/IntentGatewayV2.sol` lines 394-397.

### Proof of Concept
1. User calls `placeOrder` with an order whose single input is an ERC20 token (`token != address(0)`) and `order.fees = 0`, but sends `msg.value = 1 ether` (e.g. due to a client-side bug or leftover value field from a template).
2. In the ERC20 branch, `msgValue` is never decremented since the token isn't `address(0)` [6](#0-5) .
3. `order.fees == 0`, so the fee-swap/refund block at lines 471-488 is skipped entirely.
4. The function emits `OrderPlaced` and returns; the 1 ether sent by the user remains in the contract's balance with no accounting entry and no way for the user to withdraw it. Only an admin-invoked dust-sweep of `address(0)` (if one applies to raw `msg.value`, which it does not — `DustCollected`/`SweepDust` accounting only tracks amounts explicitly credited via `emit DustCollected`) can move it, and even then not back to the original depositor.
