### Title
Session token `dest` (shop identity) accepted without binding it to `iss` (token issuer) - ([File: lib/shopify_api/auth/jwt_payload.rb])

### Summary
`ShopifyAPI::Auth::JwtPayload` decodes and verifies an App Bridge session token's signature and audience, but never checks that the `dest` claim (which the library exposes as the authoritative `shop`/`shopify_domain` identity) actually corresponds to the `iss` claim (the origin that issued the token). This breaks the intended equality `iss == "#{dest}/admin"` that other official Shopify session-token verifiers enforce, allowing the shop identity used by host applications to be trusted without being bound to the token's true issuer.

### Finding Description
`JwtPayload#initialize` decodes the token, checks only the signature and `aud == Context.api_key`: [1](#0-0) 

It then exposes `shop`/`shopify_domain` purely from the `dest` claim, with no cross-check against `iss`: [2](#0-1) 

`admin_session_token?` even reads `@iss` directly but only to check a suffix, never comparing it to `@dest`: [3](#0-2) 

Because `api_secret_key` is shared by the app (not per-shop), and any consumer of this library uses `JwtPayload#shop` as the authoritative tenant identity (e.g., to select which shop's offline/online `Session` to load from storage), the library is trusting the `dest` claim as the session/tenant key without verifying it is bound to the same principal that issued (`iss`) the token — exactly the "JWT claim trusted without being bound" identity-binding gap. This mirrors the report's underlying bug class: two logically-linked values (issuer vs. destination, analogous to the report's two block-range groups that should move together) are allowed to diverge because the code only checks one of them in isolation.

### Impact Explanation
If `iss` and `dest` are ever allowed to diverge for a token that otherwise passes signature and `aud` checks (e.g., non-canonical `dest` formatting, or multi-store token confusion within the same app installation), any host application relying on this gem's `JwtPayload#shop` to resolve the merchant's session will resolve and act using the *wrong tenant's* shop identity while treating the token as valid — a cross-tenant session/access issue. This aligns with the "scope or expiry check bypass" / cross-tenant category, since the missing check is precisely the tenant-binding validation official Shopify libraries perform.

### Likelihood Explanation
Likelihood is moderate-to-low in the common case because Shopify's App Bridge normally issues tokens with consistent `iss`/`dest` pairs, but the library provides no defense-in-depth check that other official Shopify SDKs implement, so any deviation (malformed/legacy tokens, multi-shop embedding edge cases, or future changes in how `dest` is populated) is silently accepted rather than rejected.

### Recommendation
In `JwtPayload#initialize`, after decoding, enforce the binding explicitly:
```ruby
raise ShopifyAPI::Errors::InvalidJwtTokenError, "Session token had mismatched dest/iss" unless @iss == "#{@dest}/admin"
```
This ensures the `shop` value exposed to consumers is always bound to the actual token issuer, not merely an independent claim.

### Proof of Concept
1. Obtain (or have Shopify issue) a session token where `aud` matches the app's `api_key` (satisfying the only real check performed) but where `dest` is not equal to the shop implied by `iss` (e.g., a token whose `iss` is `https://shop-a.myshopify.com/admin` while `dest` is `https://shop-b.myshopify.com`).
2. Call `ShopifyAPI::Auth::JwtPayload.new(token)`; construction succeeds because only `aud == Context.api_key` is validated: [4](#0-3) 
3. Call `.shop` on the resulting payload — it returns `shop-b.myshopify.com`, taken solely from `dest`: [5](#0-4) 
4. A host application that loads the offline/online `Session` for `shop-b.myshopify.com` based on this value will act on behalf of `shop-b` using a token that was never bound to `shop-b` as its issuer, since the library never verified `iss` corresponds to `dest`.
