### Title
Unbounded ECDSA-recover loop over attacker-supplied BEEFY signatures allows free, permissionless resource-exhaustion via `handle_unsigned` - (File: modules/consensus/beefy/verifier/src/lib.rs)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is intentionally unsigned/free so relayers never pay fees, and its `validate_unsigned` hook fully executes the message (including consensus proof verification) during transaction-pool validation, before any economic cost is applied. [1](#0-0)  When the message is a `ConsensusMessage` for a BEEFY client, verification calls `verify_mmr_update_proof`, which recovers a secp256k1 public key for *every* signature present in the submitted proof before it ever checks those signatures against the real merkle-committed authority set. [2](#0-1)  The only gate before that loop, `check_participation_threshold(signatures_length, authority_set.len)`, enforces a *minimum* supermajority ratio, not a *maximum* bound on `signatures_length` — an attacker can pad the `signatures` vector with an arbitrarily large number of garbage/duplicate entries (bounded only by extrinsic/block size limits) and every single one is passed through the expensive `secp256k1_recover` primitive. [3](#0-2)  This is the same bug class as the OPC UA advisory (CWE-770, "Allocation of Resources Without Limits or Throttling") — an unauthenticated party triggers unbounded computational work, causing gradual node performance degradation.

### Finding Description
`pallet_ismp::Pallet::validate_unsigned` runs `Self::execute(messages.clone())` synchronously for every submitted `handle_unsigned` extrinsic while validating it for the transaction pool — this is the *only* gate before the message is admitted, and it is explicitly free (unsigned, no fee, callable by anyone). [4](#0-3)  For a `Message::Consensus` targeting a BEEFY consensus client, this routes through `verify_consensus` → `verify_mmr_update_proof`. [5](#0-4) 

Inside `verify_mmr_update_proof`:
1. `signatures_length` is read directly from the attacker-supplied `mmr.signed_commitment.signatures` vector — fully attacker-controlled. [6](#0-5) 
2. `check_participation_threshold(signatures_length as u32, authority_set.len)` is checked, but this only enforces that enough signatures are present relative to the *real* authority set size (a lower bound / supermajority requirement) — there is no corresponding upper bound rejecting a `signatures_length` that grossly exceeds `authority_set.len`. [7](#0-6) 
3. Once that check passes (trivially satisfiable by padding extra signatures on top of enough "real-looking" entries, or even reusing the same signature/index repeatedly), the code iterates over **every** entry in `signatures` and performs a `secp256k1_recover` for each one, unconditionally, before any merkle-membership check is performed on the results. [8](#0-7) 

Because the whole message set is decoded and this verification path runs inside `validate_unsigned` — i.e., during transaction-pool admission, before the extrinsic is even included in a block or evaluated for cost — an attacker can flood many collator/full nodes with unsigned `handle_unsigned` extrinsics carrying oversized `signatures` vectors (limited only by generic extrinsic/block-length limits, not by any BEEFY-specific bound), each one forcing potentially thousands of expensive elliptic-curve recovery operations per submission, at zero cost to the attacker. This mirrors the OPC UA CVE-2024-45526 pattern: an unauthorized/unauthenticated caller triggers unbounded resource consumption causing gradual node performance degradation, distinct from any of this repo's excluded categories (it's not admin/governance/collator/node-level, not p2p/sync-only, not a dependency bug, and not resource-only in the "no on-chain relevance" sense — it directly targets the reachable `pallet-ismp` `handle_unsigned` consensus-message dispatch path named in scope).

By contrast, the project has already hardened an analogous vector for the generic call-decompressor path (bounding claimed decompressed size before any expansion happens in `validate_unsigned`) with an explicit comment describing exactly this class of attack ("a fee-less attacker could ... have a tiny ... bomb expanded ... before any size check"). [9](#0-8)  No equivalent upper bound exists for the number of BEEFY signatures accepted into the ECDSA-recovery loop.

### Impact Explanation
This is a route-availability / resource-exhaustion issue reachable by any unprivileged party submitting a `handle_unsigned` extrinsic (or Tesseract relaying such a call) with a crafted BEEFY `ConsensusMessage`. Because `validate_unsigned` performs the full, unbounded ECDSA-recovery loop for free before rejecting the proof, repeated submissions let an attacker consume disproportionate CPU on every node validating the transaction pool, degrading throughput and potentially delaying legitimate consensus/message delivery on the chain that runs the BEEFY-based ISMP host (Nexus/Gargantua and other parachains configured with the BEEFY client). This matches "a route unable to deliver messages" under sustained abuse, and is a medium-severity availability degradation rather than a fund-theft/mint bug — consistent with the CVSS:3.1 A:L (low availability impact) rating of the referenced advisory.

### Likelihood Explanation
Likelihood is moderate-to-high: `handle_unsigned` is explicitly designed to be callable by anyone with no signature/fee requirement, and the vulnerable code path (`verify_mmr_update_proof`) is reached whenever a `Message::Consensus` names a BEEFY `consensus_state_id`. Crafting an oversized-but-threshold-satisfying `signatures` vector requires no cryptographic breakage — an attacker only needs enough plausible-looking entries to pass `check_participation_threshold`, then can append arbitrary additional garbage/duplicate signature entries which are still processed by the recovery loop before failing membership verification. The main constraint is extrinsic/block size limits, which still permit a large multiple of the real authority-set size.

### Recommendation
Add an explicit upper bound on `mmr.signed_commitment.signatures.len()` (and the analogous check in the Solidity `EcdsaBeefy.verifyMmrUpdateProof`) relative to `authority_set.len` (e.g., reject if `signatures_length > authority_set.len`) *before* entering the `secp256k1_recover` loop, mirroring the fix already applied to `call-decompressor`'s size-before-expansion pattern. Additionally, consider deduplicating/rejecting repeated `authorityIndex` values up front, and evaluate whether BEEFY consensus messages processed via `validate_unsigned` should carry a lightweight pre-check (e.g., cheap structural/size validation) before the expensive cryptographic verification is invoked, to avoid unbounded, fee-less computational cost during mempool validation.

### Proof of Concept
1. Attacker observes the current trusted BEEFY authority set (`current_authorities`/`next_authorities`) for a target consensus state, including its real `len` (public state).
2. Attacker constructs a `ConsensusMessage` whose `mmr.signed_commitment.commitment.validator_set_id` matches one of the known sets, with `signatures` containing: enough entries to satisfy `check_participation_threshold` (real or garbage — the loop runs regardless) plus N additional garbage/duplicate `SignatureWithAuthorityIndex` entries, where N is as large as the extrinsic/block size budget allows.
3. Attacker submits `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(msg)] }` as an unsigned extrinsic (no fee, no signer) — exactly the pattern exercised in the existing test harness that calls `handle_unsigned` with `RuntimeOrigin::none()`. [10](#0-9) 
4. `validate_unsigned` calls `Self::execute` → `verify_mmr_update_proof`, which loops `secp256k1_recover` over all N+ signatures before failing the subsequent merkle-membership check — burning CPU on every node validating the transaction, for free, repeatable indefinitely by resubmitting new (distinct) garbage batches to bypass mempool dedup via the `provides` tag. [11](#0-10)
