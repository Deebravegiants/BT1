This confirms the vulnerability. `Registry.process` validates the webhook HMAC via `Utils::HmacValidator.validate(request)`, but the `Request#to_signable_string` only returns `@raw_body` [1](#0-0) . The `shop` field, read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, is never included in the HMAC-signed content [2](#0-1) . `Registry.process` nonetheless passes this unauthenticated `request.shop` value straight into `WebhookMetadata`, which the host app's handler uses as the tenant/shop identifier [3](#0-2) .

### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant shop-domain spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the `shop` (tenant identifier) is taken from an HTTP header that is excluded from the signed content. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the authenticated tenant for the webhook payload, breaking the binding `shop authenticated == shop used by handler`.

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature from `verifiable_query.to_signable_string` and compares it to the `hmac` value [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) , so the HMAC authenticates *the body bytes* but says nothing about which shop sent them. The `shop` accessor simply reads the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, which is completely outside the signed data [2](#0-1) .

`Registry.process` performs the HMAC check and, immediately after, builds `WebhookMetadata` using `request.shop` as the shop for the handler to act on [3](#0-2) . Because the app's HMAC signing secret (`api_secret_key`) is shared across every shop that has the app installed (it is not shop-specific — see `HmacValidator.validate` using the single `Context.api_secret_key`/`Context.old_api_secret_key`) [5](#0-4) , any tenant that has legitimately installed the app can capture a validly-signed webhook delivery for their own shop and replay the identical body with only the `x-shopify-shop-domain` header value swapped to a different shop. The HMAC still validates (it only checks the body), but the host app will process the payload as if it originated from the victim shop, since `request.shop` — not any authenticated value — is what flows into the handler.

This mirrors the reported bug class: a field ("shop") is acted upon by the consuming logic but is not covered by the cryptographic binding ("HMAC") that is supposed to authenticate the request.

### Impact Explanation
Any handler that uses the `shop` field from `WebhookMetadata` to select which tenant's data/session to update (a documented and expected use, since `WebhookMetadata#shop` exists specifically for that purpose) can be tricked into applying another shop's webhook data/events under an attacker-chosen shop domain. This enables cross-tenant data confusion/injection — one merchant can cause the host app to record or act on events "on behalf of" a different shop, which falls under cross-tenant access.

### Likelihood Explanation
Exploitation requires the attacker to already be a legitimate, authenticated recipient of the app's webhooks (i.e., a merchant who installed the app), so it's not exposed to a fully anonymous internet user, but it does not require the app's `client_secret`, an access token, or any privileged account — only the ability to receive one's own shop's webhook and replay it against the app's public webhook endpoint with a modified header. Given webhook endpoints are usually public HTTP endpoints, this is straightforward to carry out.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed content, or otherwise cryptographically bind the `shop` header to the payload before trusting it — e.g., have `Request#to_signable_string` incorporate the shop/topic headers, or have `Registry.process`/the host app independently verify that `request.shop` corresponds to a shop that is expected to receive the given webhook id/topic, instead of trusting the raw header value directly for tenant selection.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook (e.g. `orders/create`) at the app's public webhook endpoint, with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some raw JSON body `B`.
2. Attacker resends the exact same HTTP request to the app's webhook endpoint, but changes the header `x-shopify-shop-domain` to `victim-shop.myshopify.com` (or another shop domain that also has the app installed), leaving the body `B` and `x-shopify-hmac-sha256` untouched.
3. `Utils::HmacValidator.validate` in `Registry.process` recomputes the HMAC solely from the raw body and finds it matches (since the body and the app-wide secret are unchanged) [1](#0-0) .
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop` now equal to `victim-shop.myshopify.com` [6](#0-5) , causing the host app's handler to process attacker-controlled body content under the victim shop's identity.
