### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the tenant-identifying `shop` (and `topic`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then dispatches to the handler using this unauthenticated `shop` value as the tenant identity, breaking the binding between "the shop the HMAC actually vouches for" and "the shop the application treats the payload as belonging to." This is the same class of defect described in the report: a value (the pre/post-hook pairing there, the `shop` header here) that is *acted on* by the trust boundary but *not covered* by the cryptographic check that is supposed to establish trust.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are parsed straight from the HTTP headers, with no relation to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `to_signable_string` (the body) and compares it with the `hmac-sha256` header value — it never incorporates `shop`: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately uses the unauthenticated `request.shop` to build the `WebhookMetadata` passed to the app's handler — the value the handler will use to determine *which merchant/tenant* the event belongs to: [4](#0-3) 

The equality the system implicitly relies on is:
`shop authenticated by HMAC == shop used as the tenant/session key for the handler`

In reality, the HMAC only proves "this body was signed with the app's secret key at some point by Shopify for some shop that installed this app" — it says nothing about which `shop` header value is attached to the request that arrives at the app's webhook endpoint. Any holder of one valid `(body, hmac)` pair — trivially obtainable by installing the app on their own store, since webhooks are delivered to public endpoints and merchants can inspect their own webhook deliveries — can replay that exact `body`/`hmac` pair while substituting an arbitrary `shop-domain` header for a victim shop. `HmacValidator.validate` will still pass because it only checks the body, and the handler will process the request under the attacker-chosen tenant identity.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce: an unprivileged app user (any merchant who has installed the app, i.e., attacker) can make the host application process a webhook body as if it originated from a different, victim shop. Depending on how the host app's `handler.handle` uses `WebhookMetadata#shop` (e.g., looking up/mutating tenant records, deleting resources, updating billing/subscription state, triggering uninstall flows, etc.), this constitutes cross-tenant access — a Critical-severity impact per the stated scope. It does not require the `api_secret_key`, an access token, TLS interception, or social engineering: only the ability to receive one legitimate webhook for the attacker's own shop.

### Likelihood Explanation
Likelihood is Medium-High: the attacker needs a real installation of the target app (a normal, unprivileged action) and a network client capable of sending an arbitrary HTTP request with a forged `shop-domain`/`x-shopify-shop-domain` header and a legitimate replayed `(body, hmac)` pair to the app's public webhook endpoint. No secret material or interception is required, since the exploit relies purely on the gem never binding `shop` into the signed payload.

### Recommendation
- Short term: Do not trust `request.shop` for tenant identification unless it can be cryptographically tied to the signed payload. If Shopify's webhook payload does not include the shop domain in the body, treat the header value as untrusted for anything beyond routing, and require the host app to independently verify the shop (e.g., cross-check against a shop/session store keyed by data that is itself HMAC-covered, or validate against the `webhook_id` via a follow-up authenticated API call) before performing any tenant-scoped side effects.
- Long term: Extend `Utils::VerifiableQuery`/`HmacValidator` so any header-derived value that downstream code treats as an identity binding (shop, topic, webhook id) is part of the signed/verified string, mirroring the `Auth::Oauth::AuthQuery#to_signable_string` pattern where every relied-upon field is included in the HMAC input.

### Proof of Concept
1. Attacker installs the app (a normal, unprivileged action) on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g., `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid for secret key `S` and body `B`), plus header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same `(B, H)` pair to the app's public webhook endpoint but replaces the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers, exposing `shop == "victim.myshopify.com"`, `hmac == H` (from `Digest.hexencode(Base64.decode64(...))`). [5](#0-4) 
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (== `B`) and compares to `H` — this succeeds because `B` and `H` are unchanged and still valid for secret `S`. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)`, i.e., `shop == "victim.myshopify.com"`, even though the payload/HMAC only ever proved authenticity for the attacker's own shop's webhook. [7](#0-6) 

If the host application's handler uses this `shop` value to select/update tenant-scoped state (session lookup, billing, data deletion, etc.), the attacker has achieved cross-tenant action against `victim.myshopify.com` without ever possessing its access token, session, or the app's `client_secret`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
