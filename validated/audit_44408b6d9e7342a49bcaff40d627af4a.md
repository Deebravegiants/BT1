### Title
Predictable, Unauthenticated Session Cookie Enables Cross-Tenant Session Hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
For non-embedded apps, the gem stores the fully deterministic session identifier (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`) directly as the plaintext value of the `shopify_app_session` cookie, and later trusts whatever value it finds in that cookie verbatim as the session id to look up. There is no signature, MAC, or other binding tying the cookie to the browser/session that actually completed OAuth — the "session id" byte string is unauthenticated, exactly matching the "session id derived from unauthenticated bytes" bug class.

### Finding Description
When OAuth completes, `Session.from` assigns a deterministic id: [1](#0-0) 

For non-embedded apps, `Oauth.validate_auth_callback` puts this id directly, unsigned, into the session cookie value: [2](#0-1) 

`SessionCookie` is a plain struct with no signature/HMAC field at all: [3](#0-2) 

On subsequent requests, the gem's documented retrieval helper reads the id straight out of the cookie hash with no verification whatsoever: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs host applications to feed this raw cookie value into `current_session_id` and use the returned string to look up the persisted `Session` (which contains the shop's access token): [6](#0-5) 

The equality that is supposed to hold is: `session id presented by the client == session id that was legitimately issued to that specific client after OAuth`. Because the id format is `"offline_#{shop}"` (fully derivable from the public, well-known `.myshopify.com` domain) and the cookie carrying it is unsigned, an attacker can construct that exact string without ever having participated in the OAuth flow. The check therefore degrades to `session id presented by the client == some syntactically valid session id`, which is always true for any shop the attacker can name.

### Impact Explanation
This meets the Critical bar of "cross-tenant access" / "theft of a merchant access token": a session id served solely from an unauthenticated cookie is used, as gem-documented, as the lookup key into whatever store holds the shop's `Session` (including `access_token`). An attacker who supplies the crafted cookie value for a victim shop causes the host application to treat their own request as authenticated for that victim tenant, exposing the victim's Admin API access token and data to the attacker.

### Likelihood Explanation
The offline session id format (`"offline_" + shop_domain`) is fixed and documented behavior of this gem (`Session.from`, `SessionUtils.offline_session_id`), and target shop domains are public/discoverable (they are `*.myshopify.com` store names). No secret, access token, or privileged state is required — only setting a single cookie header, which is standard unprivileged-internet-user capability. This applies specifically to non-embedded apps that follow the cookie-based flow the gem itself exposes and documents.

### Recommendation
Do not use the raw, predictable session id as the sole cookie value/lookup key. Either sign/MAC the cookie value (binding it to the actual `Session`, e.g. HMAC with `api_secret_key` over the id, verified before use) or issue an unguessable, random token as the cookie value that is mapped server-side to the session id, rather than emitting the deterministic `"offline_#{shop}"` / `"#{shop}_#{user_id}"` value directly to the browser.

### Proof of Concept
1. Identify a victim shop's domain, e.g. `victim-shop.myshopify.com` (public/discoverable).
2. As an unauthenticated attacker, send a request to the host application with cookie:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged (`cookie_session_id` at [5](#0-4) ) without any signature check.
4. The host app (per the gem's documented pattern) looks up the persisted `Session` for that id and uses its `access_token` to serve the attacker's request as if it were the victim shop.

```markdown
#### Cookie
Cookie based authentication is not supported for embedded apps due to browsers dropping support for third party cookies due to security concerns. Non-embedded apps are able to use cookies for session storage/retrieval.

For *non-embedded* apps, you can pass the cookies into:
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)` for online (user) sessions or
 - `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` for offline (store) sessions.
```
