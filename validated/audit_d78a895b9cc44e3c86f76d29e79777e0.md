### Title
Missing `VestingSchedule` input validation in `LockupFactory::create` / `LockupContract::new` allows unprivileged users to deploy lockups with malformed vesting timestamps - (File: lockup-factory/src/lib.rs, lockup/src/lib.rs)

### Summary
This is the same root-cause class as the Bond Protocol `BondBaseSDA.setDefaults` bug: a struct that has a dedicated `assert_valid()` validation method is accepted as external input but the validation method is never actually invoked before the values are persisted and used in downstream financial calculations.

### Finding Description
`VestingSchedule` defines an `assert_valid()` helper that checks `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp`: [1](#0-0) 

The same struct/method exists in the `lockup-factory` crate: [2](#0-1) 

However, `assert_valid()` is never called anywhere along the input path. The public, unprivileged entrypoint `LockupFactory::create` accepts a `vesting_schedule: Option<VestingScheduleOrHash>` parameter directly from the caller and forwards it, unvalidated, into the `LockupArgs` used to initialize the new lockup contract: [3](#0-2) 

The `lockup-factory` README explicitly documents that this function is open to any account: "It allows any user to create and fund the lockup contract" and shows how to pass an explicit `vesting_schedule` object with `start_timestamp`, `cliff_timestamp`, `end_timestamp` in the `create` call. [4](#0-3) 

On the receiving side, `LockupContract::new` (the `#[init]` function deployed at the newly created lockup account) validates `owner_account_id`, `staking_pool_whitelist_account_id`, and conditionally `transfer_poll_account_id` / `foundation_account_id`, but it never calls `VestingSchedule::assert_valid()` on the vesting schedule contents themselves: [5](#0-4) 

Grepping the entire `lockup` and `lockup-factory` crates confirms `assert_valid` is only referenced at its own definition site in `types.rs` in both crates — it is dead code, never called from `lib.rs` in either crate.

### Impact Explanation
Because the vesting timestamps are stored unchecked (`VestingInformation::VestingSchedule(vs)` at `lockup/src/lib.rs:225-227`), any subsequent calculation that derives the vested/unvested percentage using `(cliff_timestamp - start_timestamp) / (end_timestamp - start_timestamp)` (per the lockup README's documented formula) can:
- Divide by zero or underflow (`start_timestamp > end_timestamp`, or `start_timestamp == end_timestamp`) causing the lockup contract's balance/vesting getters and transfer-availability checks to panic on every call.
- Produce a lockup contract whose vesting math is permanently broken, meaning the owner's tokens can never be correctly assessed as vested/unvested, and the NEAR Foundation's termination flow (which depends on correctly computing the unvested amount to reclaim) can also break.

This falls squarely in the "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release ... flows" impact category, since a newly created lockup account (holding real attached NEAR, minimum `MIN_ATTACHED_BALANCE`) could become permanently unable to release or correctly account for its tokens.

### Likelihood Explanation
`create_staking_pool`-style factory calls are the direct, unprivileged, public entrypoint by design (the whole purpose of `lockup-factory` is to let arbitrary funding accounts create lockups without foundation involvement). No authorization, no trusted role, and no privileged account is required — any account can call `create` with an attached deposit and an arbitrary `VestingScheduleOrHash::VestingSchedule` payload. This directly parallels the disclosed Bond Protocol issue, where unchecked configuration values broke the ability to create/use markets correctly.

### Recommendation
Call `vesting_schedule.assert_valid()` (for the `VestingScheduleOrHash::VestingSchedule` variant) inside `LockupContract::new` before constructing `VestingInformation::VestingSchedule`, and/or validate it inside `LockupFactory::create` before forwarding the parameters, mirroring the fix applied upstream in Bond Protocol's `setDefaults`.

### Proof of Concept
1. Call `lockup-factory`'s public `create` method as any unprivileged account, attaching `MIN_ATTACHED_BALANCE`, with `vesting_schedule: { "VestingSchedule": { "start_timestamp": "1000", "cliff_timestamp": "500", "end_timestamp": "100" } }` (i.e., `cliff_timestamp < start_timestamp` and `end_timestamp < start_timestamp`).
2. `LockupFactory::create` forwards this unchanged to the new lockup contract's `new` constructor (`lockup-factory/src/lib.rs:108-154`).
3. `LockupContract::new` stores it as `VestingInformation::VestingSchedule(vs)` without calling `assert_valid()` (`lockup/src/lib.rs:216-228`).
4. Any later call that computes vested/unvested amounts using `(cliff_timestamp - start_timestamp)` or `(end_timestamp - start_timestamp)` on unsigned timestamps underflows/divides by zero, permanently reverting and freezing the deployed lockup contract's fund-release logic.

impl VestingSchedule {
    pub fn assert_valid(&self) {
        assert!(
            self.start_timestamp.0 <= self.cliff_timestamp.0,
            "Cliff timestamp can't be earlier than vesting start timestamp"
        );
        assert!(
            self.cliff_timestamp.0 <= self.end_timestamp.0,
            "Cliff timestamp can't be later than vesting end timestamp"
        );
        assert!(
            self.start_timestamp.0 < self.end_timestamp.0,
            "The total vesting time should be positive"
        );
    }

# Lockup Factory Contract

This contract deploys lockup contracts. 
It allows any user to create and fund the lockup contract.
The lockup factory contract packages the binary of the 
<a href="https://github.com/near/core-contracts/tree/master/lockup">lockup 
contract</a> within its own binary.

To create a new lockup contract a user should issue a transaction and 
attach the required minimum deposit. The entire deposit will be transferred to 
the newly created lockup contract including to cover the storage.

The benefits: 
1. Lockups can be funded from any account.
2. No need to have access to the foundation keys to create lockup.
3. Auto-generates the lockup from the owner account.
4. Refund deposit on errors.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
