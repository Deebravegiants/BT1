This confirms the vulnerability: `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over the raw body only, and the `shop` field (tenant identifier passed to the app's handler as `data.shop`) is read from a separate, unauthenticated header and never bound into the signature.

### Title
Webhook shop-domain tenant identifier is not covered by HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only [1](#0-0) , while the `shop` (tenant identity) is read from a separate header that is never part of the signed bytes [2](#0-1) . `Registry.process` validates only this body HMAC and then dispatches the handler using the unauthenticated `request.shop` value as the tenant identifier [3](#0-2) .

### Finding Description
The binding that should hold is:
`shop-domain header used for tenant routing == shop bound inside the HMAC-authenticated payload`

This binding is broken. `HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string` and the app's `client_secret` (`api_secret_key`) [4](#0-3) . For webhooks, `to_signable_string` is defined as the raw body alone [1](#0-0) . The `shop` accessor, however, is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is not included in the signable string at all [2](#0-1) .

Because every webhook for every shop installed on a given app is signed with the same `client_secret`, and the signature never incorporates the shop domain, a valid `(raw_body, hmac)` pair generated by Shopify for one shop remains a **valid signature for that same body under any other shop-domain header value**. `Registry.process` trusts this unbound header directly: it validates the HMAC [5](#0-4)  and then passes `request.shop` straight into `WebhookMetadata` as the authoritative tenant identifier for the app's handler [6](#0-5) . The documented usage pattern confirms apps are expected to trust `data.shop` as the tenant key for storing/attributing webhook data (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) .

### Impact Explanation
An attacker who legitimately installs the target app on their own shop (an ordinary, unprivileged action, not requiring any special credential) can trigger a real Shopify webhook for their own store, capturing a Shopify-issued, validly-signed `(raw_body, hmac)` pair for a resource they control (e.g. `orders/create`, `customers/data_request`, etc.). Because the signature is independent of the shop domain, the attacker can replay that exact body and HMAC to the app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to name a victim shop. `Registry.process` will validate the HMAC successfully and hand the forged `shop` value plus attacker-controlled body to the app's handler as if it came authentically from the victim tenant. This is a cross-tenant data/state injection: the app will process attacker-supplied data attributed to another merchant's shop, potentially triggering data mutations, redaction workflows (`shop/redact`, `customers/redact`), or business logic keyed on tenant identity for a shop the attacker does not own.

### Likelihood Explanation
Likelihood is significant: no secret material is needed by the attacker beyond legitimately using the app on their own store (a normal, unprivileged onboarding flow) and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint — both trivially available to any internet user.

### Recommendation
Bind the shop domain (and ideally other routing headers) into the HMAC-signed material, or require the caller to separately re-verify that the shop in the payload body matches the shop header before trusting it for tenant routing. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should not be the sole trust anchor for `shop`; `Registry.process` should cross-check that the `shop` header corresponds to a shop that is actually subscribed/expected for the specific `webhook_id`/topic, or the gem should document explicitly that host applications must not use `data.shop` as an authenticated tenant key without additional verification (e.g. checking against a known, previously-registered shop list) since it is not covered by the Shopify HMAC signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and completes OAuth normally.
2. Attacker performs an action that fires a subscribed webhook (e.g. creates an order), causing Shopify to POST a body `B` to the app's webhook endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `B` and `H` (e.g. via their own controlled receiving proxy, or by reasoning about deterministic body content they crafted for the resource).
4. Attacker sends a forged request directly to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and finds it matches `H` — validation succeeds since `shop` is never part of the signed string [1](#0-0) .
6. The app's handler is invoked with `data.shop == "victim.myshopify.com"` and attacker-controlled `data.body`, causing the host application to process/attribute the forged webhook to the victim tenant [6](#0-5) .
