## Validation

**Equality claimed to hold (and broken):** For `n` deposit tuples with identical `(erc20Address, amount, stealthAddress)` submitted in one call, the number of ERC20 units Hinkal is authorized to pull for a given token (`sum(uniqueAmounts)` approved by `HinkalWrapper`) should equal the number of units it actually needs to move (`sum(amounts)` for that token), AND each of the `n` leaves inserted into the Merkle tree should be independently, permanently spendable by the rightful owner. Both must hold for the deposit to be "safe."

## Trace

`HinkalWrapper.prooflessDeposit` first settles the fee, then calls `_pullAndApproveDepositTokens`, which pulls each `amounts[i]` individually via `transferERC20TokenFrom` but only *approves* the deduplicated sum `uniqueAmounts[idx]` per unique token via `approveERC20Token`. [1](#0-0) 

It then forwards the original, un-merged `erc20Addresses`/`amounts`/`stealthAddressStructures` unchanged to `IHinkal(hinkal).prooflessDeposit`. [2](#0-1) 

Inside `Hinkal.prooflessDeposit`, `_calcTokenChangesForProoflessDeposit` independently re-derives the same per-token merged sum, and `_handleTransfersFromProoflessDeposit` pulls exactly that merged sum once per unique token via `transferERC20TokenFromOrCheckETH`. [3](#0-2) 

Since the wrapper's approval (`uniqueAmounts[k]`) exactly matches the sum Hinkal actually pulls, the `safeTransferFrom` call succeeds — the merged-allowance mismatch the question worries about does not cause a revert.

The freeze, however, comes from `_createProoflessDepositCommitments`, which iterates over the **original, non-deduplicated** arrays and creates one leaf per index using `block.timestamp` (identical for the whole tx): [4](#0-3) 

Each leaf is `hash4(amount, erc20Address, stealthAddress, block.timestamp)` computed in `createOnchainCommitment`: [5](#0-4) 

For duplicated `(erc20Address, amount, stealthAddressStructure)` tuples in the same call, this produces two (or more) **identical** commitment values inserted at two different tree positions.

On the spend side, the nullifier is `Poseidon(commitment, signature)` where `signature = Poseidon(nullifyingPrivateKey, commitment)` — both are pure functions of the commitment value and the owner's private key, with **no dependency on the leaf's tree position/index**: [6](#0-5) [7](#0-6) 

Because the two leaves share the same commitment value, spending either one (via a Merkle proof to either tree index) yields the **same nullifier**. `insertNullifiers` enforces `!nullifiers[inputNullifiers[i][j]]`, so once the owner spends the first duplicate leaf, the nullifier is marked used, and any attempt to spend the second (structurally distinct, differently-positioned) leaf reverts with `"Nullifier cannot be reused"`: [8](#0-7) 

No existing guard prevents this: `performProoflessDepositChecks` only validates array-length consistency and per-item positivity, not uniqueness of `(erc20Address, amount, stealthAddress)` tuples: [9](#0-8) 

The `HinkalWrapper` path changes nothing about this root cause — its deduplication in `_pullAndApproveDepositTokens` only affects the ERC20 allowance bookkeeping and succeeds transparently; it never touches `_createProoflessDepositCommitments`, so the duplicate-leaf freeze reproduces identically whether the attacker calls `Hinkal.prooflessDeposit` directly or through `HinkalWrapper.prooflessDeposit`.

### Title
Duplicate deposit tuples routed through `HinkalWrapper.prooflessDeposit` produce colliding on-chain commitments, permanently freezing part of the depositor's funds - (File: `contracts/HinkalWrapper.sol`, `contracts/Hinkal.sol`, `contracts/HinkalBase.sol`)

### Summary
`HinkalWrapper.prooflessDeposit` forwards the caller-supplied, potentially duplicated `(erc20Address, amount, stealthAddressStructure)` tuples unchanged to `Hinkal.prooflessDeposit`. `Hinkal`'s `_createProoflessDepositCommitments` creates one leaf per original index using `hash4(amount, erc20Address, stealthAddress, block.timestamp)`, so duplicated tuples in the same call yield bit-identical commitments inserted at different tree indices. Since nullifiers are derived purely from the commitment value (not leaf position), only one of the duplicate leaves can ever be spent — the other is permanently unspendable.

### Finding Description
The transfer/allowance path is not the vulnerability: `HinkalWrapper`'s merged approval matches exactly what `Hinkal._handleTransfersFromProoflessDeposit` pulls (both dedupe to the same per-token sum), so no revert occurs there. The actual break is that `Hinkal._createProoflessDepositCommitments` (called after the transfer step) does not deduplicate, and the commitment formula `hash4(amount, erc20Address, stealthAddress, block.timestamp)` has no per-index/nonce differentiator. An attacker (the depositor themself, fully unprivileged) calls `HinkalWrapper.prooflessDeposit` with two or more identical tuples (same token, same amount, same `stealthAddressStructure`). Two identical leaves are inserted into the Merkle tree at different positions. When the owner later constructs a spend proof for either leaf, the circuit-derived nullifier (`Poseidon(nullifyingPrivateKey, commitment)` then `Poseidon(commitment, signature)`) is identical for both leaves since it depends only on `commitment` and the private key, not on tree position. `insertNullifiers`'s `nullifiers[...]` mapping check therefore blocks spending the second occurrence once the first is spent.

### Impact Explanation
The depositor's own funds corresponding to every duplicate beyond the first become permanently unspendable/frozen — a Critical impact ("permanent freezing of user funds") per the scoring rubric. This is repeatable per unique duplicate group per transaction and is entirely attacker/self-triggerable (no privileged role needed), though it only harms the depositor who crafted the duplicate call (self-inflicted but a genuine protocol design flaw reachable through the wrapper's public entry point).

### Likelihood Explanation
Trivial to trigger: any unprivileged EOA can call `HinkalWrapper.prooflessDeposit` with duplicated tuples in a single transaction, no special tree/action state or timing is required beyond `block.timestamp` being identical (guaranteed within one tx), and cost is only the deposited token amount plus gas. No proof or off-chain relay/oracle assumption is needed to trigger the freeze itself (only to later demonstrate the second UTXO is unspendable).

### Recommendation
Include a per-leaf disambiguator in the on-chain commitment (e.g., the loop index `i`, or `m_index`/leaf position at time of insertion) so that `createOnchainCommitment`/`_createProoflessDepositCommitments` never produces two identical leaves for legitimately-distinct duplicate deposits, mirroring the fix needed in `Hinkal.prooflessDeposit` itself (the underlying root cause is not specific to `HinkalWrapper`).

### Proof of Concept
Foundry test: deploy `Hinkal`, `HinkalHelper`, `HinkalWrapper` pointed at `Hinkal`; mint/approve an ERC20 to the attacker EOA; call `HinkalWrapper.prooflessDeposit` with `erc20Addresses = [token, token]`, `amounts = [X, X]`, `stealthAddressStructures = [S, S]` (identical), and valid non-empty `onChainEncryptedOutputs`. Assert two `NewCommitment` events are emitted with the same `commitment` value at two different `m_index` positions. Then simulate spending: compute `commitment = hash4(X, token, S.stealthAddress, timestamp)`, derive `signature = Poseidon(nullifyingPrivateKey, commitment)` and `nullifier = Poseidon(commitment, signature)` off-chain (matching circuit logic), and show both leaves would produce this same `nullifier`; after simulating one successful spend that sets `nullifiers[nullifier] = true` via `insertNullifiers`, assert that any subsequent attempt to spend the second leaf with the same nullifier reverts with `"Nullifier cannot be reused"`.

    function _pullAndApproveDepositTokens(
        address[] calldata erc20Addresses,
        uint256[] calldata amounts
    ) internal {
        uint256 len = erc20Addresses.length;
        address[] memory uniqueTokens = new address[](len);
        uint256[] memory uniqueAmounts = new uint256[](len);
        uint256 uniqueCount;

        for (uint256 i = 0; i < len; i++) {
            address token = erc20Addresses[i];
            if (token == address(0) || amounts[i] == 0) continue;

            transferERC20TokenFrom(
                token,
                msg.sender,
                address(this),
                amounts[i]
            );

            uint256 idx = uniqueCount;
            for (uint256 j = 0; j < uniqueCount; j++) {
                if (uniqueTokens[j] == token) {
                    idx = j;
                    break;
                }
            }
            if (idx == uniqueCount) {
                uniqueTokens[uniqueCount] = token;
                uniqueCount++;
            }
            uniqueAmounts[idx] += amounts[i];
        }

        for (uint256 k = 0; k < uniqueCount; k++) {
            approveERC20Token(uniqueTokens[k], hinkal, uniqueAmounts[k]);
        }
    }

        private
        pure
        returns (TokenWithAmount[] memory uniqueTokens, uint256 uniqueCount)
    {

        for (uint256 i = 0; i < erc20Addresses.length; i++) {
            bool found = false;
            for (uint256 j = 0; j < uniqueCount; j++) {

                    uniqueTokens[j].amount += amounts[i];
                    found = true;

                    erc20Address: erc20Addresses[i],
                    amount: amounts[i]

            }
        }
    }

    function _handleTransfersFromProoflessDeposit(
        TokenWithAmount[] memory uniqueTokens,
        uint256 uniqueCount
    ) private {
        for (uint256 i = 0; i < uniqueCount; i++) {
            address erc20Address = uniqueTokens[i].erc20Address;
            uint256 amount = uniqueTokens[i].amount;

            uint256 balanceBefore = getERC20OrETHBalance(erc20Address);
            if (erc20Address == address(0)) balanceBefore -= msg.value;

            transferERC20TokenFromOrCheckETH(
                erc20Address,
                msg.sender,
                address(this),
                amount
            );

            uint256 balanceAfter = getERC20OrETHBalance(erc20Address);

            require(
                balanceAfter - balanceBefore == amount,
                "proofless deposit balances must be equal"
            );
        }
    }
