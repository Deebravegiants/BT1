### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` header verbatim and hands it to the app's handler as the tenant identity. Because the HMAC secret (`api_secret_key`) is the same for every shop installed on a given app, and the signature never covers the shop identifier, an attacker who controls one installed shop can replay a validly-signed payload while substituting an arbitrary `shop-domain` header, causing the handler to process the event under a different tenant's identity.

### Finding Description
`Registry.process` performs authentication like this: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes the signature only over `request.to_signable_string`: [2](#0-1) 

That signable string is defined as just the raw body: [3](#0-2) 

Meanwhile `request.shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signed bytes: [4](#0-3) 

`HmacValidator.validate` confirms only that the body was signed with the app's `api_secret_key` (or `old_api_secret_key`); it never inspects or incorporates `shop`: [5](#0-4) 

After that check passes, `Registry.process` forwards the untrusted `request.shop` straight into `WebhookMetadata`, which the app's handler treats as the authenticated tenant identifier: [6](#0-5) [7](#0-6) 

The equality that should hold is: `shop == the tenant whose secret/body was actually used to produce a valid HMAC`. Instead the library only proves `hmac == HMAC(api_secret_key, body)`, and treats the header-supplied `shop` as if that equality also held for it. Since `api_secret_key` is shared across all shops on the same app (it identifies the *app*, not the *shop*), a legitimate webhook delivery to Shop A produces a body+HMAC pair that is equally "valid" when replayed with Shop B's domain in the header — the signature says nothing about which shop it belongs to.

### Impact Explanation
Any user who has installed the app on their own store (an otherwise unprivileged "internet user" relative to other tenants) can capture a webhook Shopify delivered to them and replay it to the app's webhook endpoint with the `shop-domain` header changed to point at a victim shop. If the app's `WebhookHandler#handle` implementation uses `data.shop` to select which tenant's data/session to act on (a common and endorsed pattern, since this is the only tenant identifier the gem exposes for webhooks), the attacker can inject falsified events attributed to another merchant — e.g. forcing `orders/create`, `app/uninstalled`, `customers/data_request`, or GDPR-topic side effects against a shop they do not own. This is a cross-tenant integrity/confusion issue reachable without any credentials beyond having installed the app once.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any shop (self-service, no privilege), (2) receiving one real webhook to capture a valid body/HMAC pair, and (3) POSTing that same body with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or TLS interception is needed — the attacker owns their own valid webhook delivery. This is fully within the unprivileged-internet-user threat model.

### Recommendation
Bind the shop identity into the authenticated bytes: either include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed payload the gem validates, or require callers to cross-check `request.shop` against the shop associated with the session/subscription that the app itself registered the webhook under, rather than trusting the header value as an authenticated fact. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify delivers a request to the app's endpoint with a valid `x-shopify-hmac-sha256` for that raw JSON body.
2. Capture the raw body and its HMAC (both computed with the app's single shared `api_secret_key`).
3. Replay the exact body and HMAC to the same webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com` (and any other shop headers of choice).
4. `Utils::HmacValidator.validate` succeeds because it only rehashes the body against `api_secret_key`, per `lib/shopify_api/utils/hmac_validator.rb` lines 12-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38.
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as if the event genuinely originated from the victim shop.
