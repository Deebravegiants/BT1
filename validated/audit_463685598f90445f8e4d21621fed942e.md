### Title
Blacklisted relayer can permanently block delivery of an entire GET-response batch - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` unconditionally pays the relayer fee via `IERC20(feeToken()).safeTransfer(relayer, fee)` after a successful `onGetResponse` callback, with no try/catch around the transfer. `HandlerV2.handleGetResponses` calls this once per response inside a loop over the whole batch, so a single relayer whose address is blacklisted on the configured `feeToken` (an ERC20 such as USDC/USDT that supports blacklisting) can make the fee transfer revert and take down the entire batch, including unrelated responses destined for other modules/users.

### Finding Description
`HandlerV2.handleGetResponses` verifies a Merkle-mountain-range membership proof for a whole batch of `GetResponseLeaf`s, then iterates and dispatches each one to the host: [1](#0-0) 

`EvmHost.dispatchIncoming` for `GetResponse` calls the destination app's `onGetResponse`, and — critically — only wraps the *app callback* in a low-level `call` with a `success` check. If the app callback succeeds, it then does an **unguarded** `safeTransfer` to pay the relayer's fee: [2](#0-1) 

Compare this to the sibling POST-request path, `dispatchIncoming(PostRequest, address relayer)`, which only calls the app callback and defers all fee logic — it has no token transfer at all in the same function, so it cannot revert on a bad recipient: [3](#0-2) 

The `relayer` parameter passed into every `dispatchIncoming(GetResponse,...)` call for the whole batch is `_msgSender()` — i.e. the single address that submitted the `handleGetResponses` transaction: [4](#0-3) 

This is structurally identical to the CrabNetting bug class: a loop that processes multiple independent items (there, withdrawal receipts; here, GET responses) performs an ERC-20 `transfer`/`safeTransfer` to a single external address inside the loop with no isolation, so if that recipient is blacklisted by the token, the whole batch reverts and blocks delivery for every other item in the batch — not just the offending relayer's own request.

Because the relayer address here is the transaction sender (not something an attacker directly controls per-request), the practical trigger is: any relayer whose delivery address later becomes blacklisted on the configured `feeToken` (governance-configurable and settable to any ERC-20, e.g. a Circle-controlled stablecoin) can no longer successfully submit `handleGetResponses` batches at all — every batch they submit reverts on the fee payout, and since `handleGetResponses` is permissionless, any other relayer attempting to include that same set of GET-response leaves inherits the same fundamental risk only if they are the blacklisted party; more importantly, once a request/response commitment is bundled by a blacklisted relayer's submission, delivery of the whole bundled batch fails, and unrelated responses in that batch cannot be delivered until resubmitted by a non-blacklisted relayer or split apart — which for a maliciously constructed batch (an attacker acting as a relayer, deliberately including their own now-guaranteed-to-be-blacklisted address, or front-running/bundling honest relayers' larger batches) turns into a denial-of-service primitive on GET response delivery, i.e. **a route unable to deliver messages**.

### Impact Explanation
`handleGetResponses` is a core, permissionless message-delivery path. A relayer address that is (or becomes) blacklisted on the fee token permanently DoSes its own ability to deliver GET responses, and any batch it constructs (which can bundle many unrelated GET responses from many different requesters/apps to save gas) fails entirely and cannot be delivered until resubmitted differently. This blocks legitimate cross-chain state-query responses from ever settling, which is a "route unable to deliver messages" — freezing the completion of any app relying on GET responses (state membership/non-membership proofs consumed by apps) for that batch. Given `feeToken` is configurable by governance and can be any ERC-20 with blacklist capability (e.g., a stablecoin), this is a realistic, non-theoretical risk with no privileged actor required to trigger it beyond becoming (or acting as) an unprivileged relayer.

### Likelihood Explanation
Medium: it requires (a) the deployment's `feeToken` to be a blacklistable ERC20, and (b) a relayer to be or become blacklisted (their own address ending up on a sanctions/blacklist list, or an attacker deliberately relaying with a to-be-blacklisted address to grief a batch). Both are outside factors, but relayer addresses are public and permissionless — anyone can call `handleGetResponses`, including an attacker with a blacklisted address, deliberately bundling their submission with victims' responses to block delivery, mirroring the CrabNetting PoC where the attacker's own blacklisted status was used to jam the shared queue.

### Recommendation
Isolate the relayer fee payout from the app-callback success/failure control flow the same way `dispatchIncoming(PostRequest,...)` isolates callback failures: wrap the `safeTransfer` in a low-level call with a success check (or a try/catch), and if it fails, credit the relayer's fee to an internal "unclaimed fees" balance (mirroring the pallet-relayer withdrawal pattern already used elsewhere in the protocol) rather than reverting the whole batch. This way a single bad recipient degrades gracefully (their fee is queued/held) instead of blocking delivery of every other response bundled in the same batch.

### Proof of Concept
1. Deploy/point `EvmHost` at a blacklistable ERC-20 as `feeToken` (governance-settable via `setHostParams`).
2. Have address `R` (a relayer) become blacklisted on that `feeToken` (e.g., sanctioned address, or an attacker self-selects a known-blacklisted address before relaying).
3. `R` submits `handleGetResponses(host, message)` with a `GetResponseMessage` batch containing N unrelated `GetResponseLeaf`s, each with nonzero `fee`.
4. For the first leaf, `EvmHost.dispatchIncoming(GetResponse, R)` succeeds through `onGetResponse`, then calls `IERC20(feeToken()).safeTransfer(R, fee)`, which reverts because `R` is blacklisted.
5. The revert propagates up through `HandlerV2.handleGetResponses`'s loop, reverting the entire batch transaction — none of the N responses are delivered, even though N-1 of them belong to unrelated, unblocked requesters.
6. Until a non-blacklisted relayer resubmits a batch that excludes `R`'s association (or the fee token is changed), those responses cannot be delivered through that batch.

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
