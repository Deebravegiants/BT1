## Finding

### Title
Webhook HMAC validation excludes the `shop-domain`, `topic`, and `webhook-id` headers, allowing shop-identity spoofing in webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body alone, while the `shop`, `topic`, and `webhook_id` values used to route and process the webhook are read from unauthenticated HTTP headers. This breaks the binding `shop_authenticated == shop_acted_on`: the HMAC only proves the body bytes are genuine, not which shop or topic the event belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, and `#webhook_id` are all pulled straight from request headers, none of which are included in that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, so it never touches the shop-domain header: [3](#0-2) 

`Registry.process` validates only this body-only HMAC and then dispatches to the handler using the unauthenticated `request.shop` and `request.topic`: [4](#0-3) 

Because the HMAC is `HMAC(secret, raw_body)` with no header binding, any request carrying a `raw_body`/`hmac` pair that is valid for shop A's webhook can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to shop B. The HMAC still validates (it never covered the header), and the handler receives `WebhookMetadata` attributing the body to shop B instead of the shop that actually produced/owns that body.

An attacker who legitimately installs the app on their own shop (an "unprivileged" merchant relative to other tenants) can capture a genuine `raw_body`/`hmac-sha256` pair delivered to their own endpoint for their own shop, and then resubmit that exact pair with an arbitrary `shop-domain` header value pointing at a victim shop. Nothing in `Request` or `Registry.process` cross-checks the header against anything covered by the signature.

### Impact Explanation
This allows an authenticated-looking webhook to be attributed to an arbitrary target shop of the attacker's choosing, i.e., cross-tenant identity confusion at the webhook-handling boundary: the receiving application will process/store data keyed to a shop domain that the HMAC never actually vouched for. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., to update per-merchant records, revoke access, or trigger merchant-scoped side effects), this enables one tenant to inject events attributed to another tenant, meeting the "cross-tenant access" bar.

### Likelihood Explanation
Exploitability requires only sending a raw HTTP POST to the app's webhook endpoint with attacker-controlled headers and a body/HMAC pair the attacker can legitimately obtain by installing the app on their own store — no access to `api_secret_key` or any other tenant's credentials is required.

### Recommendation
Include the shop domain (and ideally topic/webhook id/API version) in the HMAC-signable representation, or otherwise cryptographically bind these header values to the signed payload, so `Utils::HmacValidator.validate` cannot pass for a body whose signature was computed for a different shop.

### Proof of Concept
1. App installs `ShopifyAPI::Webhooks::Registry` handler and exposes an endpoint that constructs `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` from the incoming HTTP request, then calls `Registry.process(request)` — this mirrors `test/webhooks/registry_test.rb`'s `test_process_with_new_format_headers` pattern.
2. Attacker installs the app on Shop A and captures a legitimately delivered webhook: `raw_body = "{...}"`, `hmac-sha256 = Base64.encode64(HMAC-SHA256(api_secret_key, raw_body))`, `shop-domain = "shop-a.myshopify.com"`.
3. Attacker resends the identical `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `shop-domain: "shop-b.myshopify.com"`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC — [5](#0-4)  — and `Registry.process` dispatches the handler with `shop: request.shop` equal to `"shop-b.myshopify.com"` even though the signature was never computed over that value.
