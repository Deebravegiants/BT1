### Title
Deleting and re-adding an access key resets its nonce to a value that can be lower than nonces already used, enabling transaction replay - (File: runtime/runtime/src/access_keys.rs)

### Summary
`add_regular_key()` unconditionally reseeds a re-added access key's nonce from the current block height instead of preserving the previous nonce, mirroring the `offboard()`/`onboard()` bug class in the external report: a "clear and recreate" flow resets a nonce counter that is depended on by replay protection.

### Finding Description
When an `AddKey` action is processed for a regular (non-gas) key, `add_regular_key` always overwrites the nonce with `initial_nonce_value(block_height)`, regardless of any prior nonce the same public key may have already reached: [1](#0-0) 

`initial_nonce_value` computes `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (1,000,000): [2](#0-1) 

The nonce-validity upper bound enforced at verification time is `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`: [3](#0-2) 

This means at a given block height `H`, a key's nonce can legitimately grow anywhere up to just under `H * 1_000_000`. If the same public key is deleted (`DeleteKey`) and re-added (`AddKey`) at that same height `H` (e.g., as two actions in one transaction, or as two separate transactions within the same block), `delete_regular_key` simply removes the trie entry without recording its prior nonce: [4](#0-3) 

and the subsequent `add_regular_key` reseeds the nonce down to `(H-1) * 1_000_000` — up to ~999,999 lower than the nonce the key had already reached. `verify_nonce`'s Monotonic check only requires `tx_nonce > current_nonce` (the newly-lowered value): [5](#0-4) 

so any previously signed (and possibly already executed) transaction whose nonce falls in the now-reopened range becomes valid again, as long as its `block_hash` is still within `transaction_validity_period`. This is the direct analog of the reported Solidity bug: `offboard()`'s `delete orgs[msg.sender]` wipes `packedPayoutNonces[]`, and a subsequent `onboard()` allows replay of old approved payouts — here, `DeleteKey`+`AddKey` on the same public key wipes/reseeds the nonce counter and allows replay of old signed transactions.

Unlike account/implicit-account deletion+recreation (which is safe because it necessarily happens at a strictly later block height, so `(H'-1)*1e6 >= H*1e6` for `H' > H`), the `DeleteKey`+`AddKey` path can occur within the *same* block height, which is what creates the exploitable window. The original mitigation for issue #3779 (seeding nonce from block height to avoid hash collisions on re-creation) assumed re-creation implies increasing height; it does not hold for same-height key rotation.

### Impact Explanation
Any full-access key holder (the account owner, or an attacker who compromised/holds a full-access key) can execute `DeleteKey`+`AddKey` for the same public key in a single transaction to reset that key's nonce downward within the current block's 1,000,000-wide range. Anyone possessing a copy of an older, already-broadcast signed transaction from that key (transactions are public once submitted/included) can then resubmit it, and it will pass nonce validation and execute again — effectively re-executing an already-completed transfer, function call, or other action. This is a concrete unauthorized state/balance change (double execution) reachable purely through normal transaction/action processing, not requiring any validator or network-layer compromise.

### Likelihood Explanation
The precondition (submitting `DeleteKey` then `AddKey` for the same public key within a single block height) is trivially achievable by any account with a full-access key, using ordinary batched actions in one transaction. The attacker only needs an old valid signed transaction (their own, or one they can obtain, e.g., a payment tx they signed and that was already relayed) whose `block_hash` is still within `transaction_validity_period`. No cryptographic secrets need to be re-derived — the old signature remains valid because the message (Transaction) is unchanged.

### Recommendation
When re-adding a key with a public key that previously existed on the account (via `DeleteKey` immediately followed by `AddKey`, or `AddKey` after a prior `DeleteKey` at the same height), the nonce should never be allowed to decrease. Options analogous to the report's suggested fixes:
- Track the maximum nonce ever used per public key/account (even across deletion) and only allow a re-added key to start at `max(initial_nonce_value(block_height), highest_previous_nonce + 1)`.
- Disallow re-adding a previously-deleted public key within the same block height (or same `ACCESS_KEY_NONCE_RANGE_MULTIPLIER` window) unless the new nonce is explicitly bounded above the old one.
- Persist a per-account "key generation" counter that must be included when computing/verifying nonces, so key recreation cannot roll back the effective nonce space.

### Proof of Concept
1. At block height `H`, account `A` uses full-access key `K` to sign and execute many transactions, driving `K`'s on-chain nonce close to `H * 1_000_000` (the current upper bound), e.g., nonce = `H*1_000_000 - 10`.
2. Attacker/owner submits a single transaction from `A` at height `H` with actions `[DeleteKey(K), AddKey(K, full_access)]`.
3. `action_delete_key` → `delete_regular_key` removes `K`'s entry [4](#0-3) ; `action_add_key` → `add_regular_key` resets `K.nonce = (H-1)*1_000_000` [1](#0-0) .
4. An old signed transaction from `A`/`K` with nonce, say, `H*1_000_000 - 5000` (already executed earlier, still within `transaction_validity_period` relative to its `block_hash`) is resubmitted.
5. `verify_nonce` accepts it because `tx_nonce (H*1_000_000-5000) > current_nonce ((H-1)*1_000_000)` [5](#0-4) , causing the old transaction's actions (e.g., a transfer) to execute a second time.

    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
