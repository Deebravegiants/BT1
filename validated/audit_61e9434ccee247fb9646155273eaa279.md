### Title
Webhook HMAC signature only authenticates the raw body, not the `shop-domain`/`topic`/`webhook-id` headers used for tenant dispatch - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . However, the `shop`, `topic`, `webhook_id` and `api_version` fields that `Registry#process` uses to route the payload to a handler and to stamp the tenant identity in `WebhookMetadata` are all read straight from unauthenticated HTTP headers, never included in the HMAC input [3](#0-2) .

### Finding Description
The identity binding that should hold is: `hmac_verified_bytes == bytes_that_determine_tenant/topic_routing`. In `Request`, the HMAC only certifies the raw body bytes came from a holder of `api_secret_key`; it says nothing about which shop or topic the body belongs to, since `shop`, `topic`, and `webhook_id` are all pulled from headers via `shopify_header` [4](#0-3) , and headers are never mixed into `to_signable_string`.

`Registry#process` trusts these header-derived values directly after the HMAC check passes: it raises only if `Utils::HmacValidator.validate(request)` fails, then dispatches using `request.topic` and stamps the tenant with `request.shop` in `WebhookMetadata` [5](#0-4) . Because the shop/topic headers are not bound to the HMAC, any request that carries a *previously valid* `(raw_body, hmac)` pair — for example one obtained from a webhook legitimately delivered to the attacker's own installed shop — will still pass `HmacValidator.validate` even if the attacker rewrites the `shop-domain`/`topic`/`webhook-id` headers to arbitrary values (e.g. a different shop domain) before replaying the request to the app's public webhook endpoint. The handler then processes and stores/acts on the payload under the attacker-chosen tenant identity.

### Impact Explanation
This breaks the equality `authenticated_content == dispatched_tenant/topic`, letting an unprivileged attacker who has captured any one valid `(body, hmac)` pair (trivially obtainable by installing the app on their own store and receiving a real webhook) impersonate an arbitrary shop domain and/or topic when replaying it to the app's webhook endpoint. Because the gem hands the webhook handler a `WebhookMetadata` object whose `shop` field is unauthenticated, any downstream logic that scopes data writes/reads by `shop` (a very common pattern for webhook handlers) can be fed cross-tenant data under a forged shop identity — a cross-tenant access condition.

### Likelihood Explanation
Requires no secret material: the attacker needs only a legitimate, previously-observed `(raw_body, hmac)` pair (e.g. from a webhook delivered to their own installed shop) and the ability to POST to the app's public webhook endpoint with arbitrary headers, both of which are available to any unprivileged internet user / app installer.

### Recommendation
Bind the signable content to the identity fields used for dispatch — e.g. include `shop`, `topic`, and `webhook_id` in the HMAC input (or otherwise cryptographically bind them, as Shopify does not sign headers, the app should independently verify shop/topic against out-of-band trusted state, such as the shop stored for the subscription/registration) before using header values for routing or tenant scoping, rather than trusting `shopify_header` output implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook to the app's endpoint, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` value `H` for that delivery (computed only over `B`, per `to_signable_string`) [1](#0-0) .
2. Attacker replays a POST to the app's public webhook endpoint with the exact same body `B` and `hmac-sha256` header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `Utils::HmacValidator.validate(request)` succeeds because it only re-derives the HMAC over `@raw_body`, which is unchanged [6](#0-5) .
4. `Registry#process` dispatches to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` now reads `"victim-shop.myshopify.com"` from the forged header [7](#0-6) , causing the app to process/store the attacker's payload as if it belonged to `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
