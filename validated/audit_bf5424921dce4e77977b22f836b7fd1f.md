### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant shop-domain forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` fields solely from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the HMAC over `to_signable_string`, which returns `@raw_body` and nothing else. The `shop` claim that downstream handlers rely on for tenant identification is therefore never bound to the cryptographic signature.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC check computes the signature only from `to_signable_string`: [2](#0-1) 

And `Request#to_signable_string` returns just the raw body — no headers are included: [3](#0-2) 

Meanwhile, `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed content: [4](#0-3) 

After HMAC validation succeeds, `request.shop` is passed straight into the handler as the tenant identifier via `WebhookMetadata`: [5](#0-4) 

Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that has the app installed, any merchant who has the app installed on their own shop can capture one legitimate `(raw_body, hmac)` pair delivered to their own endpoint, then replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates because it only checks the body against the shared secret — it never binds the signature to the `shop` header. This breaks the intended identity equality: `shop_claimed_by_handler == shop_that_actually_produced_the_signed_body`.

### Impact Explanation
This is a cross-tenant confusion vector: an attacker (any merchant with the app installed on at least one shop — an unprivileged, low-cost position) can cause the host application's webhook handler to process attacker-controlled/attacker-replayed data under an arbitrary victim shop's identity, since `data.shop` is trusted without being cryptographically bound to the signed payload. Depending on how a host app uses `WebhookMetadata#shop` (e.g., to look up the session/access token for that shop, or to route the payload's contents into that shop's records), this can lead to cross-tenant data corruction or logic confusion — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker have the app installed on any shop (to obtain one valid `(raw_body, hmac)` pair) and the ability to send an HTTP POST to the app's public webhook endpoint with a forged `shopify-shop-domain` header — both trivially achievable by any unprivileged internet user/merchant, no access token or `client_secret` needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed material verified by `Utils::HmacValidator`, or independently verify that the `shop` header matches a shop known to be associated with the specific webhook subscription/API version before trusting it in `WebhookMetadata`. At minimum, document that `shop` must be cross-checked by the host application against its own session store rather than trusted as an authenticated claim.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: body `B` with header `x-shopify-hmac-sha256: H` (computed over `B` using the app's `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the same body `B` and same `hmac` header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` is `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (`= B`) using the app's secret and it matches `H`, so validation passes: [6](#0-5) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host app to act on attacker-controlled content under the victim's tenant identity.
