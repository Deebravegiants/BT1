### Title
Webhook `shop` and `topic` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, but the `shop` and `topic` values that are then handed to the app's webhook handler as the "authenticated" identity of the event come from HTTP headers that are never included in the HMAC-signed material. This breaks the intended identity binding `hmac_verified_bytes == identity_bytes_acted_on`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers and are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC over exactly `verifiable_query.to_signable_string`, i.e. the raw body only: [3](#0-2) 

`Registry.process` uses the HMAC check as its sole authentication gate, then immediately forwards the *unauthenticated* `request.shop` and `request.topic` values to the app's handler as the trusted identity of the event: [4](#0-3) 

Because the HMAC only binds the body bytes to the secret, and does not bind the `shop-domain`/`topic` header bytes, any party who possesses one valid `(body, hmac)` pair for the app's secret (e.g., a merchant who has legitimately installed the app on their own store and thus receives real, correctly-signed webhooks) can replay that exact body+hmac to the app's public webhook endpoint while substituting arbitrary values for `x-shopify-shop-domain` and `x-shopify-topic`. The HMAC check in `HmacValidator.validate_signature` still passes because it only compares the body-derived digest, so `Registry.process` will invoke the registered handler believing the event was authentically emitted `by` the spoofed shop for the spoofed topic — i.e., `hmac_verified(bytes) == true` while `shop_acted_on != shop_bound_by_hmac`.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is a legitimate (if unprivileged) merchant of a multi-tenant app can forge webhook events that are processed as if they originated from a victim shop of their choosing, and/or under a topic of their choosing (e.g. relabeling a harmless webhook as `app/uninstalled` or `customers/data_request`, or attributing an event to another shop's domain). Depending on how the host application's handler uses `data.shop`/`data.topic` (e.g., to look up/mutate that shop's session, trigger data deletion, or update per-shop state), this can result in cross-tenant data manipulation — satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only (a) the attacker to be able to send arbitrary HTTP requests to the app's public webhook endpoint (always true, it is internet-facing), and (b) possession of one valid `(raw_body, hmac)` pair signed with the app's secret — trivially obtainable by any merchant who installs the app on their own shop and captures one legitimate webhook delivery (many webhook bodies, like `app/uninstalled`, are content-independent or easily reproducible). No access to `api_secret_key`, access tokens, or privileged accounts is required.

### Recommendation
Include the identity fields that the handler relies on (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify `shop`/`topic` headers against Shopify's servers as returned in a mutually-authenticated channel, or require the signable string to be a canonical concatenation of header values + body rather than body alone). At minimum, document that `request.shop`/`request.topic` are not authenticated by `HmacValidator.validate` and must not be trusted for tenant-isolation decisions without additional verification (e.g., cross-checking against a known/registered shop before acting).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimately-signed webhook, capturing the raw body `B` and its valid `hmac` header `H` (computed by Shopify using the app's real secret over `B` only, per `Request#to_signable_string`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the digest over `B` and it matches `H`, so validation succeeds: [5](#0-4) 
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is now `victim-shop.myshopify.com` — a value the attacker fully controls and that was never covered by the HMAC — despite the app believing the webhook's authenticity guarantees the shop identity as well.
