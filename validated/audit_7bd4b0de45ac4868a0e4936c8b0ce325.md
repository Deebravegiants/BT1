## Analysis

The Gitcoin bug class is: an unprivileged, unauthenticated function operates on a contract's balance using fully attacker-controlled parameters (arbitrary recipient/amount) with no check that the funds "belong" to the caller or to a legitimate operation — so any stray balance that ends up in the contract is drainable by anyone.

`CallDispatcher` in Hyperbridge reproduces this exact pattern. It is a single, shared, permissionless intermediary used by `HyperFungibleToken`/`WrappedHyperFungibleToken` and `IntentGatewayV2` to execute attacker/user-supplied `Call[]` batches, and it accepts ETH via a bare `receive()`: [1](#0-0) 

`dispatch()` has no access control whatsoever — no `onlyHost`, no caller allow-list, nothing — and executes `to.call{value: call.value}(call.data)` with fully caller-supplied `to`, `value`, and `data`.

The token bridge contracts explicitly document sending minted funds directly to this shared dispatcher address for post-mint calldata execution: [2](#0-1) 

And the `onAccept` handler mints straight to whatever `beneficiary` the cross-chain message specifies (which per the docs is meant to be set to the `CallDispatcher` address), then forwards `message.data` to it — with **no sweep-back step** afterward: [3](#0-2) 

Contrast this with `IntentGatewayV2`'s `_execute`, which does explicitly sweep any residual balance left in the dispatcher back to the gateway after a call batch: [4](#0-3) 

`HyperFungibleToken`/`WrappedHyperFungibleToken` has no equivalent sweep. If the attached `Call[]` calldata doesn't consume 100% of the minted/transferred tokens (slippage on a swap, a malformed call array, a partial revert-tolerant sequence, or simply a user/relayer mistake), the leftover balance is stranded in `CallDispatcher` — a contract that, by design, is not supposed to hold funds long-term. Since `dispatch()` is open to any caller, anyone can then submit `Call[{to: token, value: 0, data: transfer(attacker, strandedBalance)}]` (or `{to: attacker, value: strandedBalance, data: ""}` for native ETH) and pull it out, exactly as the Gitcoin report drained the voting-strategy contract by calling an unauthenticated `vote()` with a self-chosen recipient/amount once tokens accidentally sat there.

### Title
Unrestricted `CallDispatcher.dispatch()` lets anyone drain stray funds left behind by incomplete calldata execution - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public, unauthenticated function that executes caller-supplied `Call[]` batches (`to`, `value`, `data` all attacker-controlled) against its own balance. `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept()` mints/unlocks tokens directly to the dispatcher address (per the documented calldata-execution pattern) and forwards attached calldata to it, but performs no sweep-back of unconsumed balance afterward. Any ETH or ERC20 tokens left in the shared `CallDispatcher` — from slippage, a malformed `Call[]`, a partially-effective swap, or any other app's leftover dust — can be withdrawn by any address, since `dispatch()` has no caller restriction.

### Finding Description
`CallDispatcher` is deployed once and shared across every app that supports calldata execution (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `IntentGatewayV2`). Its `dispatch(bytes memory encoded)` function decodes an arbitrary `Call[]` and executes `to.call{value: call.value}(call.data)` for each entry with zero access control:

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [5](#0-4) 

`HyperFungibleToken.onAccept()` mints tokens to `beneficiary` (which the docs instruct integrators to set to the `CallDispatcher` address when the calldata needs to spend the bridged funds) and then dispatches the attached calldata, with no subsequent balance check or sweep: [3](#0-2) 

If the `Call[]` doesn't consume the full minted amount (e.g., a DEX swap encoded with an exact-input amount smaller than what was minted, or a call sequence that leaves change), the residue permanently sits in `CallDispatcher`. Because `dispatch()` is callable by anyone and accepts an arbitrary target/value/data, any unprivileged actor can immediately call it with a `Call[]` that transfers the dispatcher's balance to themselves. This is functionally identical to the reported Gitcoin issue: an unauthenticated function operating on a contract's balance with attacker-chosen recipient/amount and no ownership/legitimacy check on the funds.

### Impact Explanation
Any residual native ETH or ERC20 balance accumulated in the shared `CallDispatcher` — arising from any user's cross-chain transfer with calldata across any integrating app — is permanently and trivially stealable by an unrelated third party. Because the dispatcher is shared infrastructure, the blast radius covers every app that routes calldata through it, not just one gateway instance. This is a concrete theft-of-funds path reachable from a single relayed message delivery (no privileged role required to exploit), satisfying High severity.

### Likelihood Explanation
Likelihood depends on funds actually being left behind, which can happen from ordinary operational conditions (slippage-tolerant swaps, DEX calls that don't spend to the wei, integrators following the documented "set `to` to `CallDispatcher`" pattern without adding a sweep of their own). Once any residue exists, exploitation is a single, permissionless transaction available to any observer of the dispatcher's balance — no proof, no timing window, no special access needed.

### Recommendation
Add a caller allow-list (or `onlyHost`/registered-app check) to `CallDispatcher.dispatch()`, or restrict it to only the app(s) that funded the current batch (e.g., pull-based execution keyed to a caller-supplied session so unrelated addresses can't invoke it against another user's leftover balance). Additionally, have `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept()` sweep any residual balance from `CallDispatcher` back to the beneficiary after calldata execution, mirroring the dust-sweep already implemented in `IntentGatewayV2._execute`.

### Proof of Concept
1. A cross-chain `send()` on `HyperFungibleToken` includes calldata (`data`) whose `Call[]` batch swaps the bridged amount via a DEX with an input amount slightly less than the minted `amount` (or the swap partially reverts/tolerates less than full spend).
2. On `onAccept()`, `_mint(beneficiary, message.amount)` mints the full amount to the `CallDispatcher` address (per the documented pattern), then `ICallDispatcher(_dispatcher).dispatch(message.data)` executes the swap, consuming less than the full minted balance.
3. The unconsumed remainder sits in `CallDispatcher`.
4. Any attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedBalance)})]))` (or the native-ETH equivalent) and receives the stranded funds — with no relationship to the original order/message.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;

            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    function _execute(Order calldata order, uint256 outputsLen) internal {
        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {
            Call[] memory finalCalls = new Call[](sweepCount);
            for (uint256 i; i < sweepCount;) {
                finalCalls[i] = sweepCalls[i];
                unchecked {
                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
    }
