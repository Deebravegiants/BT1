### Title
Missing `return` after email-claim-extraction and session-DB-insert failures allows account confusion / auth bypass in OIDC token exchange - (File: core/sessions/oidcauth/oidc.go)

### Summary
`handleTokenExchange`, the handler behind the unauthenticated `/oidc/token` (or equivalent) callback endpoint reached by any client completing the OAuth2/OIDC code exchange, fails to `return` after two distinct error conditions it detects, exactly mirroring the reported bug class where a failure/return value is checked but not acted upon, letting execution proceed with corrupted state.

### Finding Description
In `handleTokenExchange`: [1](#0-0) 
when `claims["email"]` is not a string (missing/malformed `email` claim from the identity provider), the code logs the error and writes an HTTP 500 body via `c.String(...)`, but does **not** `return`. Execution falls through with `email` left as its zero value (`""`).

Processing then continues to compute the RBAC `role` from `idClaims` and insert a new session row keyed by the empty email: [2](#0-1) 
The `INSERT INTO oidc_sessions (id, user_email, user_role, created_at)` statement executes with `strings.ToLower(email)` == `""`. A second, identical missing-`return` bug exists right after this INSERT: if the `ExecContext` call itself fails, the code again only logs/writes a 500 body but does not `return`, so it proceeds to set the session cookie anyway: [3](#0-2) 
`ginSession.Set(webauth.SessionIDKey, clSession.ID)` and `ginSession.Save()` are called and, absent a save error, the handler returns `ExchangeTokenResponse{Success: true}` — i.e., the client receives a "200 success" response body (the earlier `c.String(500, ...)` write does not abort the gin handler chain by itself) along with a valid, authenticated session cookie bound to a session ID that was never persisted (in the second case) or persisted with an empty `user_email` (in the first case).

`AuthorizedUserWithSession` later looks the session up by ID against `oidc_sessions`: [4](#0-3) 
For the empty-email case, a valid session row with `user_email = ''` and an attacker-influenced `role` (from `IDClaimsToUserRole`, driven by group claims from the IdP) is created and usable for subsequent authenticated requests, i.e., a distinct/unlinked identity ("") is granted node access, and any audit trail attributes actions to email `""` rather than a real user — a cross-user/identity confusion analogous to the "wrong accounting update on failure" pattern in the reported issue.

### Impact Explanation
An attacker who controls (or can influence) the identity-provider response — e.g., a malicious or misconfigured IdP, or a race where the `email` claim is intermittently absent — can cause the node to mint an authenticated session under an empty/unintended `user_email` while still receiving group/role claims that map to elevated RBAC roles (Admin/Edit) via `IDClaimsToUserRole`. This breaks the intended identity binding of the session-to-email invariant relied on elsewhere (e.g. `FindUser`, audit logging, per-user session listing/`ClearNonCurrentSessions`), enabling authentication/authorization confusion and audit-log poisoning on the node's HTTP admin API.

### Likelihood Explanation
Reaching this code requires only a normal OIDC login flow through `handleSignIn`/`handleTokenExchange`, which is by design reachable by any client with network access to the node's UI/API. The failure only triggers when the `email` claim is missing/malformed or the DB insert transiently fails, which is a config/IdP-dependent condition rather than something a purely external, unauthenticated attacker can trivially force against a compliant IdP — but it is fully within reach of anyone who operates or can influence the configured IdP (or exploits a transient DB error), making this a real, code-provable defect rather than a purely theoretical one.

### Recommendation
Add `return` immediately after each of the two error-handling blocks in `handleTokenExchange`:
- After the `if !ok { ... c.String(http.StatusInternalServerError, "Failed to get email from claims") }` block (around line 229).
- After the `if err != nil { ... c.String(http.StatusInternalServerError, "Error creating session") }` block following the `oidc_sessions` insert (around line 259).

This prevents session creation/cookie issuance from proceeding with an invalid email or an unpersisted session row.

### Proof of Concept
1. Configure a Chainlink node with `OIDCAuth` enabled and RBAC claim mappings.
2. Point the OIDC provider config at an IdP (or a test double) that completes a valid `code`/`state` exchange and returns a verifiable ID token whose claims include the group claim used by `oi.config.RunClaim()` (or higher) but omit the top-level `email` claim.
3. Drive the normal flow: `GET /oidc/sign-in` → redirect to IdP → IdP redirects back with `code`/`state` → frontend calls `handleTokenExchange` with that `code`/`state`.
4. Observe: `handleTokenExchange` logs "Failed to get email from claims" and writes a 500 body, but does not return; it proceeds to `IDClaimsToUserRole`, inserts a row into `oidc_sessions` with `user_email = ''` and the mapped `role`, sets the gin session cookie, and finally responds `{"success": true}`.
5. Use the returned session cookie against any authenticated endpoint; `AuthorizedUserWithSession` finds the valid, non-expired session row and authorizes the request as a user with email `""` and the mapped role — confirming a session was granted despite the detected identity-extraction failure.

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
