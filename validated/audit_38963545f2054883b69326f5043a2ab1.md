### Title
Webhook HMAC signature does not bind the `shop` field, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop` attribute used to identify which tenant a webhook belongs to is read from an unauthenticated HTTP header. Any party in possession of one valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` can replay it with an arbitrary `shop-domain` header and have `ShopifyAPI::Webhooks::Registry.process` accept it as a legitimate webhook for a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` is decoded from the `hmac-sha256` header, and `shop` is read from the separate `shop-domain` header — neither the shop nor any other header is part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over the body and, once it passes, dispatches the handler using `request.shop` taken straight from the unauthenticated header — the tenant identity is never checked against anything covered by the signature: [3](#0-2) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against a signature computed from `to_signable_string`, i.e. the body — it has no knowledge of, and does not bind, the `shop` field: [4](#0-3) 

This breaks the identity binding: the equality that should hold is `shop_bound_by_signature == shop_acted_on`, but here `shop_acted_on` (`request.shop`, from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in `shop_bound_by_signature` (empty — only the body is signed). Because `api_secret_key` is a single shared secret for the whole app, any legitimate webhook delivery to any shop that installed the app is a valid `(body, hmac)` pair for every other shop of that same app. An unprivileged user who installs the app on any shop (including a free/trial store they control) will receive genuine webhook deliveries with valid `body`/`hmac`. They can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a different, victim shop of the same app. `Utils::HmacValidator.validate` still succeeds (the body/signature pair is unmodified), and the handler executes with `request.shop` set to the victim's domain.

### Impact Explanation
This crosses a tenant boundary: an attacker can make the application process a forged webhook event and attribute it to any other shop running the same app, without ever compromising that shop's credentials. Depending on what webhook handlers do (e.g., updating local records keyed by shop domain, triggering actions using the target shop's stored session/access token, or reacting to `app/uninstalled`, `shop/update`, etc.), this can lead to state corruption, unauthorized actions performed "as" another tenant, or injection of attacker-controlled data into another shop's data store — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any unprivileged attacker who can install the target app on a shop they control (a standard, low-barrier action for any Shopify app) and can send arbitrary HTTP requests to the app's public webhook endpoint. No secret, access token, or privileged account is required — only a legitimately received `(body, hmac)` pair from their own shop's webhook deliveries, plus the ability to set an arbitrary `shop-domain` header value.

### Recommendation
Include the `shop` (and other identity-relevant headers such as `topic`/`webhook_id`, if used for authorization decisions) in the value covered by the HMAC check, or otherwise cryptographically bind the shop domain to the signed payload before trusting it. At minimum, `to_signable_string` should incorporate the shop header so that `HmacValidator.validate` fails if the shop is swapped, or the library should document/require verifying the shop against a set of shops with known active installations for the app before dispatching handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a shop they control) and lets Shopify deliver a normal webhook, capturing the raw request body `B` and the `x-shopify-hmac-sha256` header value `H` (valid for the app's shared `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but header `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds a request whose `hmac` and `to_signable_string` (= `B`) are unchanged from step 1.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature check only covers `B`.
5. The registered handler for the topic in `B` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the payload actually originated from the attacker's own shop.
