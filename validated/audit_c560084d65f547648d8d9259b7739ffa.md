## Title
Tron `IntentGatewayV2.placeOrder` credits escrow with the requested amount instead of the tokens actually received, breaking accounting for fee-on-transfer/deflationary tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` pulls ERC20 input tokens via `safeTransferFrom` and then credits the internal escrow ledger `_orders[commitment][token]` with the pre-fee, user-declared `order.inputs[i].amount` (reduced only by the protocol fee), rather than the amount the contract actually received. This reproduces exactly the fee-on-transfer/deflationary-token bug class described in the external report: if the token takes a transfer fee (fixed or governance-upgradeable, e.g. USDC-style pausable/fee-capable tokens), the contract will believe it holds more tokens than it actually does.

### Finding Description
In the non-predispatch branch of `placeOrder`, tokens are transferred in and escrow is credited without ever checking the contract's actual token balance delta: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            // native token
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }

        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` minus the protocol fee bps — it never reflects the token balance actually held by the gateway. This is the identical root cause flagged in the external report (`BvbProtocol.sol` crediting `takerPrice` instead of the actual received balance).

By contrast, the primary EVM `IntentGatewayV2.sol` (non-Tron) fixed this exact class of bug by measuring `balanceOf` before/after the transfer and mutating `order.inputs[i].amount` to the actual received amount before computing the commitment and escrow: [2](#0-1) 

The Tron contract lacks this balance-delta measurement entirely, both in the no-predispatch path shown above and in the predispatch path, where escrow is credited via `reducedInputs[i].amount` (still derived from the user-declared `order.inputs[i].amount`) rather than the dispatcher/gateway's measured balance change: [3](#0-2) 

### Impact Explanation
If an `allowedAsset`/input token later becomes (or already is) a fee-on-transfer/deflationary token — plausible for upgradeable/pausable stablecoins or any token whose fee mechanics can change — `_orders[commitment][token]` will overstate the actual balance escrowed in the gateway by the transfer-fee amount. Downstream withdrawal paths (`withdraw()` on `RedeemEscrow`/`RefundEscrow`, cancellation refunds) will attempt to pay out the inflated escrowed amount to solvers or users. Because the gateway is a shared-custody pool across many concurrent orders, this creates a systemic shortfall: either legitimate withdrawals revert (permanent freezing of funds for the affected order), or — because the ledger is a mapping decoupled from actual balances — the shortfall is paid out of other users' escrowed balances, i.e. one order's fee-on-transfer input silently drains funds belonging to other orders. This is a concrete freezing/theft-of-funds vector reachable directly from `placeOrder`, a fully unprivileged, single-transaction entry point.

### Likelihood Explanation
Likelihood depends on the input token exhibiting or acquiring fee-on-transfer/deflationary behavior, but requires no privileged actor and no special conditions beyond placing an order with such a token — any user can trigger it in one transaction. The same class of tokens is explicitly called out as a real-world risk in the audit report (upgradeable tokens like USDC potentially adding a fee), and the sibling EVM contract in this very repository was already patched for this exact issue, confirming the maintainers recognize it as a valid, reachable bug class that the Tron port failed to inherit.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` (or `dispatcher`) before and after each `safeTransferFrom`/predispatch sweep, mutate `order.inputs[i].amount` to the actual received delta, and derive `reducedInputs`/`commitment`/`_orders[commitment][token]` from that measured amount instead of the caller-declared `order.inputs[i].amount`.

### Proof of Concept
1. Admin (or governance) allows a token `T` as a valid input asset for the Tron `IntentGatewayV2`.
2. `T` charges (or later upgrades to charge) a 5% transfer fee.
3. User calls `placeOrder` with `order.inputs = [{token: T, amount: 1000}]`.
4. `IERC20(T).safeTransferFrom(msg.sender, address(this), 1000)` results in the gateway actually receiving only 950 `T`.
5. `_orders[commitment][T] += reducedInputs[i].amount` credits ~1000 (minus protocol fee bps) regardless of the 950 actually received.
6. When the order is filled and settled cross-chain, `withdraw()` attempts to transfer out the credited (inflated) amount of `T` to the solver, which either reverts (freezing the order and any queued fills) or succeeds by consuming `T` balance escrowed for unrelated orders, breaking their accounting.
