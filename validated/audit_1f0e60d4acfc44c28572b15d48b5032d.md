Webhook `shop` (and `topic`) identity is trusted from unauthenticated headers while the HMAC only signs the raw body, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop` and `topic` fields consumed by `ShopifyAPI::Webhooks::Registry.process` are pulled straight from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` and `X-Shopify-Topic` headers, which are never part of the HMAC computation. Any tenant that legitimately installs the app (and therefore knows the shared `api_secret_key`-signed payloads Shopify sends them) can capture one of their own valid `(raw_body, hmac)` pairs and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. The library's own `Utils::HmacValidator.validate` will accept it, and `Registry.process` will hand the forged shop identity straight to the app's `WebhookHandler`.

### Finding Description
`Request#hmac`/`Request#to_signable_string` is defined as: [1](#0-0) 

Note that `to_signable_string` returns `@raw_body` only — none of `topic`, `shop`, `api_version`, or `webhook_id` are folded into the signed string, even though they're all read straight from attacker-controllable headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string` (i.e., the body) with the app's `Context.api_secret_key`, which is the single shared secret used across *every* shop that installs the app: [3](#0-2) 

`Registry.process` only checks this body HMAC before trusting `request.shop` and `request.topic` and forwarding them into the handler's metadata: [4](#0-3) 

Because the HMAC secret is shared across tenants, an attacker who installs the app on their own shop receives genuine webhooks for their own store, each with a valid `(raw_body, hmac)` pair signed by the app's `client_secret`. Since the header carrying `shop-domain` (and `topic`) is outside the signed content, the attacker can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim merchant's domain. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)`, breaking the intended binding of `shop authenticated by HMAC == shop the event data is attributed to`.

### Impact Explanation
This is a cross-tenant confusion vector: an app's webhook handler that uses `data.shop` to select which merchant's records to update (e.g., mapping an `orders/create` payload to a store) can be tricked into applying attacker-controlled body content under a victim shop's identity, since the only authentication (`HmacValidator`) never binds the claimed shop to the signature. Depending on how the host app trusts `data.shop`, this can lead to writing/mutating another merchant's data or misattributing events across tenants — a cross-tenant access impact.

### Likelihood Explanation
Any unprivileged party can install the target app on their own development/trial store (a normal, unauthenticated action any internet user can perform) and thereby legitimately receive real webhooks signed with the shared `api_secret_key`. Forging the replay only requires changing one HTTP header value, no cryptographic secret is needed, and the library performs no other binding check between the signed body and the shop/topic headers.

### Recommendation
Include the identity-bearing fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string in `Request#to_signable_string`, or otherwise cryptographically bind the `shop`/`topic` to the signed payload, so that a captured `(body, hmac)` pair from one shop cannot be replayed against the endpoint under a different shop's identity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, satisfying OAuth normally.
2. Shopify sends the app a legitimate webhook, e.g. `orders/create`, to the app's registered endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <hmac-of-body>`, and some JSON body.
3. Attacker intercepts/replays this exact request but rewrites the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`, keeping the same raw body and HMAC.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: modified_headers))`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only checks the (unchanged) body against the (unchanged) HMAC: [5](#0-4) 
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's crafted body content, processing it as though it legitimately originated from the victim's store.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
