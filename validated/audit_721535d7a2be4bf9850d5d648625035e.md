### Title
Hostile mint pre-seed can force `finalizeGraduation` to seed the HyperSwap LP materially away from curve-close price when the rebalance swap exceeds its 99% budget cap - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._seedRebalancing` / `_pairRebalance` defend graduation against an attacker who front-runs `finalizeGraduation` with a self-funded `pair.mint()` at a hostile TOKEN/LT ratio. The defense computes a no-fee rebalance swap to push the HyperSwap V2 pair back toward the curve-close ratio, but caps that swap at 99% of the attacker-reachable inventory (`_swapBudget`). For a sufficiently lopsided pre-seed, the swap needed to fully correct the ratio exceeds this cap, so the pair is deposited into and permanently locked in `LPLock` at a price materially different from the bonding curve's last traded price — exactly the "LP seeded away from the curve close price" impact class, reachable by any unprivileged wallet holding the launched token and its paired LT.

### Finding Description
Any address can permissionlessly call the HyperSwap V2 factory to create the `TOKEN/LT` pair before `Bonding.finalizeGraduation` runs (phase 2 of the two-phase graduation), then `transfer` both assets to that pair at an arbitrary ratio and call `pair.mint(attacker)` to seed real LP at that ratio, as described in the contract's own natspec [1](#0-0) .

When `finalizeGraduation` later runs, `_seedUniswapV2Direct` detects `pair.totalSupply() != 0` and routes into `_seedRebalancing`, which computes the swap required to move the pool to the cached `(tokensForLP, ltFromPair)` ratio via `_pairRebalance`, using a budget capped at 99% of the available side: [2](#0-1) 

`_pairRebalance` executes the swap directly against the pair using `_noFeeSwapInput`, capped by `maxSwap`: [3](#0-2) 

For an extreme enough pre-seed ratio, the optimal swap that would fully correct the price exceeds the 99% budget, so the swap only partially rebalances the pool before `_routerDepositAndDispose` deposits the remaining inventory and `finalizeGraduation` locks the resulting LP into `LPLock`. This is directly reproduced and acknowledged in the test suite: [4](#0-3) 

### Impact Explanation
`ltFromPair` and `tokensForLP` represent real LT and tokens raised from legitimate curve traders and the creator's seed buy — not attacker capital. When the pool opens materially off curve-close (the test demonstrates >20% deviation, and the setup is engineered so the true correction is ~2x the budget), the LP that gets permanently locked in `LPLock` (which has no withdraw/rescue path in v1, per `docs/contracts-scope.md`) is mispriced relative to the bonding curve's actual last trade. This immediately exposes the pool to arbitrage that extracts value from the protocol-owned LP position funded by real trader/creator capital, and the off-ratio side excess is unilaterally swept to `owner()` rather than reflecting the trade history that funded it — a concrete instance of "LP seeded away from the curve close price."

### Likelihood Explanation
The attack requires only: (1) holding some amount of the launched `Token` and its paired LT (both freely acquirable via `Zap.buy`/`Zap.createToken`), (2) permissionlessly creating the HyperSwap V2 pair and minting LP against it before `finalizeGraduation` executes, and (3) sizing the pre-seed ratio extreme enough that the required correction swap exceeds `_swapBudget`'s 99% cap. Since `finalizeGraduation` is itself permissionless and can be delayed (the keeper is best-effort, and the AGENTS.md explicitly states "anyone can call to rescue a stuck token"), an attacker who front-runs it has a viable window in every graduation. This is a known, tested residual gap (labeled "M-02" in the test suite) rather than a hypothetical.

### Recommendation
Either (a) widen or make the rebalance budget adaptive to the actual required correction (not a flat 99% of one side's inventory) so the swap can fully close the gap for any realistic pre-seed size, or (b) when the budget cannot achieve a bounded price deviation, fall back to burning/escrowing the attacker's hostile LP contribution (rather than merely capping the swap and depositing anyway) so `LPLock` never locks a materially mispriced position funded by real curve-raised assets.

### Proof of Concept
Adapted from the existing regression test, demonstrating the accepted-but-unresolved deviation: [5](#0-4) 

1. Launch a token and buy until `_enterGraduating` fires (phase 1), caching `tokensForLP`/`ltFromPair`.
2. Before `finalizeGraduation`, create the HyperSwap pair and seed it via `transfer` + `pair.mint(griefer)` with `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200` (a ~200x LT-rich ratio), as done by `_grieferMintPreSeed`.
3. Call `bonding.finalizeGraduation(tokenAddr)` — it succeeds (no brick), but the resulting pool price is proven to sit >20% off the curve-close price (`_poolPriceLtPerToken` assertion), with the LP permanently locked in `LPLock` at that skewed price.

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.

A cheaper variant skips step 3 entirely: `transfer(pair, dust) + pair.sync()` forces the stored reserves to the dust ratio without minting any LP, leaving the pair at `reserves > 0 && totalSupply == 0`. Regime 1 below covers both shapes by keying on supply rather than reserves.

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    /// @notice M-02 reproducer. An LT-rich mint pre-seed so lopsided that the
    ///         TOKEN-side rebalance swap exhausts its full budget (~99% of
    ///         `tokensForLP`) without reaching the cached ratio, so the pool
    ///         deposits materially off curve-close. Finalize must still succeed
    ///         (no brick), the over-funded LT side must be confiscated to the
    ///         owner, and the pre-seeder must end net-negative.
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
