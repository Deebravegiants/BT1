The `Request#hmac` (`Digest.hexencode(Base64.decode64(shopify_header("hmac-sha256")))`) verifies only `@raw_body` via `to_signable_string`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to that signature. `Registry.process` trusts `request.shop` to build `WebhookMetadata`, which the host app uses as the tenant key.

### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` fields come from unauthenticated HTTP headers that are never mixed into the signed content. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then unconditionally trusts `request.shop` as the tenant identifier passed to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for webhooks `to_signable_string` returns just `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then builds `WebhookMetadata` using the unauthenticated `request.shop` header value and dispatches it to the app's handler as the trusted tenant identifier: [3](#0-2) [4](#0-3) 

This breaks the identity binding that `shop-covered-by-signature == shop-acted-on`: the equality the design implicitly assumes is `HMAC(raw_body, api_secret_key) covers shop-domain`, but in reality `HMAC` only covers `raw_body`, and `shop-domain` is read out-of-band. Because `api_secret_key` is the same for every shop that installs a given app, any merchant who installs the app on their own store (an unprivileged, ordinary internet user with no special access) can legitimately trigger a webhook with a body they fully control content of (e.g. by editing a resource), capture the resulting valid `(raw_body, hmac)` pair delivered by Shopify to the app's registered endpoint, and then replay that exact `raw_body`/`hmac` pair to the same endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop. The HMAC still validates because it never depended on the shop header, and the host application's handler processes the payload as if it originated from the victim's tenant.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an attacker who legitimately controls one shop can make the gem attribute arbitrary attacker-chosen webhook bodies to a different, victim shop domain, since the shop identifier is never authenticated by the HMAC. Any host application logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop cached state, triggering shop-scoped side effects, writing to a shop's records) can be corrupted or hijacked using attacker-controlled data pretending to be from another tenant, which is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for an app builder relying on this gem as-is: any user who can install the app on a shop they control (a fully unprivileged action) can generate a validly signed webhook body/HMAC pair and then simply resend it with a spoofed shop header to the app's public webhook endpoint — no secrets, tokens, or privileged access are required beyond normal app installation.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header value into the signed material checked by `HmacValidator`, or otherwise cryptographically tie the delivered shop-domain header to the specific signature/delivery (e.g., by having `Registry.process` cross-check `request.shop` against a webhook subscription/session lookup rather than trusting the header verbatim), so a valid HMAC for shop A's payload cannot be replayed while claiming to originate from shop B.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., updates a product), causing Shopify to POST a `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's registered callback URL — this HMAC is computed with the app's shared `api_secret_key`.
2. Attacker captures this `(raw_body, hmac)` pair (they own the shop and thus can observe or replay traffic to their own registered endpoint).
3. Attacker resends an HTTP POST to the same app endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because it only hashes `raw_body`: [5](#0-4) 
5. `WebhookMetadata` is built with `shop: request.shop` = `"victim-shop.myshopify.com"`, and the handler processes attacker-controlled data as though it belongs to the victim tenant.
