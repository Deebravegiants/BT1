## Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only, while the `shop` (tenant) identity used by `ShopifyAPI::Webhooks::Registry.process` to route and label incoming webhook data is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is derived purely from an HTTP header that is never mixed into that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `to_signable_string` against the HMAC header, so it never verifies that `shop` matches the content that was actually signed: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity for dispatch, after only checking that the HMAC validates (which says nothing about the header): [4](#0-3) 

This breaks the identity binding: `shop` acted upon (tenant routing key handed to the app's handler) ≠ `shop` covered by the HMAC (which is empty — only body bytes are signed). Since a single app-level `api_secret_key` signs webhooks for every shop that installs the app, any merchant who installs the app on their own store receives genuinely Shopify-signed webhook deliveries for their own shop. That merchant can capture a valid `(raw_body, hmac-sha256)` pair from their own store's webhook and replay it to the app's webhook endpoint while rewriting the `shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged app installer (no special credentials beyond installing the app themselves) can make the app process webhook payloads under an arbitrary shop's identity. Depending on the handler, this can be used to inject or misattribute data for another tenant, or interfere with mandatory GDPR topics (`shop/redact`, `customers/redact`, `customers/data_request`) by targeting them at the wrong shop, since `Registry` treats `MANDATORY_TOPICS` specially but still relies on the same unauthenticated `request.shop`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be able to install the app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) and then send a crafted HTTP request with a valid, previously-received `(body, hmac)` pair but a substituted `shopify-shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or other privileged credential is required.

### Recommendation
Include the shop domain (and other routing-relevant headers such as topic/api-version if they affect handler behavior) inside the HMAC-signable content, or otherwise cross-check `request.shop` against a value derived from data that is actually part of the signed payload before dispatching to handlers. At minimum, `Registry.process` should refuse to trust `request.shop` unless it is corroborated by tenant state already known to the app (e.g., an installed-shop lookup) rather than treating a successful body HMAC as validating the header-derived shop.

### Proof of Concept
1. App developer installs their own app on `attacker-shop.myshopify.com`; Shopify sends a legitimately signed webhook: body `B`, header `shopify-hmac-sha256: H` (valid for `B`), `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the same `B`/`H` to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate(request)` succeeds because it only checks `B` against `H` via `to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-22`).
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the app to process attacker-controlled data under the victim shop's identity.
