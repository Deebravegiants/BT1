In `Registry.process`, the `shop` value dispatched to the app's handler comes directly from `request.shop`, which reads the `X-Shopify-Shop-Domain`/`shopify-shop-domain` **header**, while `Utils::HmacValidator.validate(request)` only verifies the HMAC over `request.to_signable_string`, which returns `@raw_body` — the raw JSON body, not the headers.### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but then dispatches the handler using the `shop` value read from an HTTP header that is never included in that HMAC computation. This breaks the intended binding `hmac_verified(body) == shop_trusted`, allowing a party who possesses one genuine, HMAC-valid webhook (for their own shop) to relabel it as originating from a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all extracted from HTTP headers, which are outside the signed payload: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` (which calls `verifiable_query.to_signable_string`, i.e. the body only) and then unconditionally trusts `request.shop` and `request.topic` to look up the handler and construct the metadata passed to the app's webhook handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field/header — again, headers such as `shop-domain` play no role in the signature: [4](#0-3) 

Because Shopify webhook HMACs are computed with the **app-level `client_secret`** (shared across every shop that installs the app), not a per-shop secret, any shop that has installed the app can receive a completely legitimate webhook (correct body + valid HMAC) for its own shop, then replay that same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` (it never inspects the header), and `Registry.process` will hand the forged shop identity straight to the app's handler via `WebhookMetadata`. This is precisely the "field acted on but not covered by the HMAC" identity-binding break called out in scope.

### Impact Explanation
This is a cross-tenant identity confusion: the app's own webhook-processing logic (through this gem) will act on behalf of a shop the request did not actually come from. Any app whose webhook handler uses `data.shop` for tenant-scoped operations (looking up per-shop data, associating events/orders/customer data with a shop record, triggering per-tenant side effects such as data deletion for `customers/redact`/`shop/redact`, etc.) can be tricked into applying an event meant for shop A to shop B's tenant context — a cross-tenant access/data-integrity issue at the library's trust boundary.

### Likelihood Explanation
Exploitation only requires an attacker who can install the app on any shop (a low-privilege, self-service action available to any Shopify merchant/developer) and can send an arbitrary HTTP request with the correct body/HMAC to the app's public webhook endpoint while spoofing headers — both entirely realistic for an "unprivileged internet user" once they've installed the app themselves. No access to the app's `client_secret`, tokens, or the victim's data is required.

### Recommendation
Include the identity-relevant fields (`shop-domain`, `topic`, and ideally `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed payload, so that `Utils::HmacValidator.validate` fails if any of these headers are altered independently of the body. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop/topic headers (Shopify's own HMAC signing mechanism only covers the body, so this may require the app-side gem to combine header + body hashing, or to separately cross-check the shop header against an application-known/allow-listed shop before trusting `request.shop`).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a genuine webhook delivery to the app's endpoint with body `B`, headers including `shopify-shop-domain: attacker-shop.myshopify.com`, and a valid `shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's `client_secret`).
2. Attacker captures this exact HTTP request (body `B`, HMAC `H`).
3. Attacker resends the request to the app's webhook endpoint, replacing only the `shopify-shop-domain` header with `victim-shop.myshopify.com` (body `B` and HMAC `H` unchanged).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (`B`) — identical to `H` — and returns `true`.
5. `Registry.process` looks up the handler by `request.topic` (unchanged, still valid) and invokes it with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process the event under the wrong shop's identity.
