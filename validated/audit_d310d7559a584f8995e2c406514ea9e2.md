### Title
Unrestricted `superApprove` on `HyperFungibleTokenImpl` allows theft of any holder's token balance - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl`, the role-based fungible token used as Hyperbridge's fee token (deployed in `evm/script/DeployIsmp.s.sol`), exposes a `public` function `superApprove(address owner, address spender)` that grants `type(uint256).max` allowance from `owner` to `spender` with **no access control** whatsoever — no `onlyRole`, no `onlyOwner`, no `msg.sender == owner` check. Anyone can call this function to set themselves (or any address) as an infinite-allowance spender over any token holder's balance, then drain the funds via `transferFrom`. This mirrors the Dough Finance bug class cited in the report: an unauthorized code path that lets an attacker extract funds it was never entitled to, due to a contract-level access-control flaw.

### Finding Description
`HyperFungibleTokenImpl.sol` implements an ERC-20 with `AccessControlEnumerable`-gated `mint`/`burn` (properly restricted to `MINTER_ROLE`/`BURNER_ROLE`), but also ships a helper meant only for tests: [1](#0-0) 

```solidity
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
```

This function is `public`, takes `owner` as an arbitrary parameter (not `msg.sender`), and calls the internal `_approve` directly — bypassing the standard ERC-20 `approve()` semantics that require the caller to be the token owner. Any externally owned account or contract can invoke `superApprove(victim, attacker)` for **any** `victim` holding this token, then call `transferFrom(victim, attacker, balance)` to steal the entire balance.

This contract is not a test mock confined to the test tree — it lives under `evm/src/utils/` (production sources) and is referenced by the deployment script for the ISMP host's fee token: [2](#0-1) 
and by `TokenFaucet.sol`, both outside the test directory. Since the fee token is the asset used throughout the protocol for relayer fees, dispatch fees, and ISMP message payments (e.g., pulled via `transferFrom` in `HyperFungibleToken.send`/`dispatchWithFeeToken`), any account holding balances of a token deployed from `HyperFungibleTokenImpl` — including protocol fee escrows — is at risk.

### Impact Explanation
Any address can drain the full balance of any holder of a `HyperFungibleTokenImpl`-based token (e.g., the fee token used by `EvmHost`/`IDispatcher` for relayer fees) by calling the unguarded `superApprove` followed by `transferFrom`. This is a direct, unauthorized-theft primitive reachable from a single transaction with no special privileges, satisfying the "concrete theft of funds" bar for High severity.

### Likelihood Explanation
Likelihood is high: the function is `public`, requires no privileged role, no proof, and no cross-chain interaction — a single call from any EOA is sufficient. The only prerequisite is that a deployment of `HyperFungibleTokenImpl` (e.g., the fee token) holds real value, which is the expected production configuration per `DeployIsmp.s.sol`.

### Recommendation
Remove `superApprove` from production code entirely, or if a test-only helper is required, move it into the test tree, gate it behind `onlyRole(DEFAULT_ADMIN_ROLE)` combined with an explicit test-environment flag, or require `msg.sender == owner`. At minimum, add a role-based or ownership check so arbitrary callers cannot set allowances on behalf of other token holders.

### Proof of Concept
```solidity
// Attacker contract/EOA, given a deployed HyperFungibleTokenImpl `token` with a
// victim holding balance:
token.superApprove(victim, address(this));      // no access control needed
token.transferFrom(victim, address(this), token.balanceOf(victim)); // drains victim
```
No role, signature, or proof is required — `superApprove` is `public` with no modifiers, so this PoC succeeds against any deployed instance of `HyperFungibleTokenImpl`, such as the fee token instantiated in `evm/script/DeployIsmp.s.sol`.
