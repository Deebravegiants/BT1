### Title
Fee-on-transfer tokens desynchronize escrow accounting from actual balances in the Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits the internal `_orders` escrow mapping using the user-declared `order.inputs[i].amount` (reduced only by protocol fee), instead of measuring the tokens actually received by the contract via `IERC20.safeTransferFrom`. For fee-on-transfer/deflationary ERC20 tokens, this causes the escrow ledger to overstate the gateway's real token balance for that order.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the *requested* `order.inputs[i].amount` minus only the protocol fee (see the `reducedInputs` computation at lines 359-385). No balance-before/after check is performed to capture the actual amount received.

This is a regression relative to the hardened, non-Tron `evm/src/apps/IntentGatewayV2.sol`, which explicitly measures actual received amounts and mutates `order.inputs[i].amount` accordingly before crediting escrow or computing the commitment: [2](#0-1) 
That fixed version is also covered by dedicated tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`) confirming the intended behavior is to reconcile escrow with actual balance: [3](#0-2) 

The Tron contract's predispatch branch has the same issue — it credits `_orders[commitment][token] += reducedInputs[i].amount` based on the requested amount even while separately tracking `dust = balance - requiredAmount` for excess (not deficit) cases: [4](#0-3) 

Since `placeOrder` is a public, unprivileged, payable entry point reachable by any user submitting an order with an arbitrary ERC20 `token` address, an attacker (or even an unwitting user using a real-world deflationary/fee token) can place an order for a fee-on-transfer token, and the escrow bookkeeping (`_orders[commitment][token]`) will register more tokens than the gateway actually holds for that order.

### Impact Explanation
Because `_orders` is a shared per-token/per-commitment ledger backing multiple orders' fills/cancellations/withdrawals in the same contract, over-crediting escrow for one order results in the gateway's aggregate ledger exceeding its real token balance. When the corresponding `withdraw()` path (triggered via `cancelOrder`, `onAccept` RedeemEscrow/RefundEscrow) later attempts to pay out the recorded escrow amount, either:
- the payout for that specific order reverts (denial of service / stuck escrow) if the token's `transfer` also imposes a fee and the gateway lacks sufficient balance, or
- more critically, the shared token balance becomes insufficient to service other legitimately-escrowed orders for the same token, effectively allowing one fee-on-transfer order to drain/starve funds owed to other users — a permanent freezing-of-funds condition for a subset of orders.

This matches the "Medium" classification of the original Allo report: internal accounting is desynchronized from actual balances, leading to reverts or fund lock-ups downstream.

### Likelihood Explanation
Likelihood is limited to fee-on-transfer/deflationary ERC20 tokens being configured as an order's input `token`. The protocol does not appear to restrict `order.inputs[*].token` to a vetted whitelist at the Tron `placeOrder` level (any ERC20 address can be encoded into `TokenInfo.token`), so any user submitting an order can trigger this by choosing a deflationary token as input. This is a routine, permissionless action requiring no privileged role — anyone acting as an intent submitter can reach it.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to the Tron contract: measure `balanceOf(address(this))` before and after each `safeTransferFrom` (and after the predispatch sweep) and use `balanceAfter - balanceBefore` as the actual received amount when computing `reducedInputs`, the `commitment`, and the `_orders[commitment][token]` credit — mirroring lines 312-329 (and the predispatch phase logic at lines 260-311) of the non-Tron implementation.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC20 token (e.g., a 1% transfer-fee token, as modeled by the `FeeOnTransferToken` test helper: [5](#0-4) ).
2. User approves and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` via the non-predispatch path (lines 450-469 of the Tron contract).
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` results in the gateway actually receiving only 990e18 (1% fee burned/retained), yet `_orders[commitment][FOT] += reducedInputs[0].amount` credits (up to) 1000e18 minus only the protocol fee — an amount the gateway does not hold.
4. When this or another order sharing the same `FOT` token attempts `withdraw()` (via `cancelOrder` same-chain path or cross-chain `RedeemEscrow`/`RefundEscrow`), the sum of escrowed amounts recorded across orders can exceed the gateway's actual `FOT` balance, causing a payout revert or leaving a later order's rightful beneficiary unable to withdraw their funds.

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
