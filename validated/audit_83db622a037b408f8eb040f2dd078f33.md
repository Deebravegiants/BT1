### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body, not the `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unauthenticated HTTP headers when constructing the `WebhookMetadata` passed to the host app's handler. This is the same bug class as the reported issue: an identity field ("who this belongs to") is not covered by the same authenticator that is verified, so it can be swapped without invalidating the check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` gates entirely on this HMAC check and then immediately trusts the header-derived `request.shop`/`request.topic`/`request.webhook_id` to build the metadata delivered to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop header == shop that Shopify actually generated this signed body for`.

In this implementation that equality does not hold, because the signature covers only body bytes, not the `shop-domain` (or `topic`/`webhook-id`) header. An unprivileged Shopify merchant who has installed the same app on their own store legitimately receives a validly HMAC-signed webhook body from Shopify (e.g., an `orders/create` payload for their own shop, or any webhook whose body content is attacker-controllable such as `app/uninstalled`, or even a payload with predictable/empty content). They can then replay that exact `raw_body` + `hmac-sha256` header pair to the victim app's webhook endpoint while substituting the `x-shopify-shop-domain` header with an arbitrary victim shop domain (and/or a different `x-shopify-topic`/`webhook-id`). `HmacValidator.validate` still succeeds because it only checks the body against the secret-derived signature — it never checks whether the `shop`/`topic` headers were the ones Shopify actually signed for. `Registry.process` then calls the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, i.e., the attacker-chosen (spoofed) shop and topic, while the HMAC "proves" only that *some* valid body was once signed by Shopify for *some* topic — not that it belongs to the claimed shop/topic.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (or `#topic`) to select which merchant's tenant record to update — a standard usage pattern shown in the gem's own webhook docs — can be tricked into applying data belonging to one shop's legitimately-signed webhook body under a different shop's identity, or into mis-typing an event's topic. This crosses a tenant boundary using only a re-broadcast of a webhook the attacker (as their own legitimate merchant/app-installer) already received — no access token, `client_secret`, or privileged account is required. This matches the Critical "cross-tenant access" bar, since a request intended for shop A's data is processed by the app as if it belonged to shop B, achieved by an ordinary internet-reachable merchant with no elevated privilege.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on their own Shopify store (or otherwise receive one legitimately signed webhook whose body they can predict/control) and can send an arbitrary HTTP POST with modified headers to the app's public webhook endpoint — both trivially available to any unprivileged internet user/merchant. No secret material, TLS interception, or social engineering is needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signable material, or otherwise cryptographically bind them to the verified payload before trusting them in `Registry.process`. At minimum, `to_signable_string` should not silently omit fields (`shop`, `topic`) that are later used for tenant-scoping decisions by consuming applications; document/enforce that host apps must independently correlate `request.shop` against the session/tenant they expect for that webhook subscription, and/or add explicit binding so `HmacValidator.validate` fails when the headers used to route/process the webhook are inconsistent with the signed body's origin.

### Proof of Concept
1. Attacker installs the victim app (or any app using this gem) on their own store `attacker.myshopify.com` and registers/receives a webhook, e.g. `app/uninstalled` with body `{}` (empty JSON is deterministic/predictable), and captures the valid `X-Shopify-Hmac-Sha256` header computed by Shopify over that body using the app's real `api_secret_key`.
2. Attacker sends a POST to the same app's webhook endpoint with:
   - `raw_body`: the same `{}` (or any other body they can produce a valid signature for)
   - `X-Shopify-Hmac-Sha256`: the captured valid signature
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (spoofed)
   - `X-Shopify-Topic`: `app/uninstalled` (or another topic sharing the same/predictable body)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the signature [5](#0-4) .
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)` [6](#0-5) , causing the host application to act (e.g., deprovision, disable, or mutate data) on the victim tenant based on a webhook the attacker fabricated for their own store.
