### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` identity used by the registry/handler is taken from an unauthenticated header. Any attacker who possesses one valid `(body, hmac)` pair — trivially obtainable as the owner of any shop that has the app installed and receives real webhooks — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the signature check still passes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controlled HTTP header, with no cross-check against the signed content: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` handed to the app's handler, treating the whole request — including the shop identity — as if it had been verified: [3](#0-2) 

The `HmacValidator.validate` call only ever compares `verifiable_query.hmac` against a signature computed from `to_signable_string`: [4](#0-3) 

The broken identity binding, expressed as an equality that the gem fails to enforce:
`HMAC-verified bytes (raw_body)` ≠ `identity field consumed downstream (shop-domain header)`.

Because the shop domain is never folded into the signed payload, two different requests carrying the same body and the same valid HMAC — one legitimately generated by Shopify for shop A, and one replayed by an attacker who owns shop A and simply swaps the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to shop B — are indistinguishable to `Registry.process`. The library reports both as HMAC-valid and forwards `shop: "shop-b.myshopify.com"` (attacker-chosen) to the app's webhook handler.

This mirrors the report's bug class: a value (`nominal`) that is silently exempted from an update path is treated as still-authoritative, permanently corrupting downstream accounting for a token that was skipped. Here, a value (`shop`) that is exempted from the signed payload is nonetheless treated as authoritative by the caller, permanently confusing which tenant a verified webhook body belongs to.

### Impact Explanation
Any app built on this gem that branches on `WebhookMetadata#shop` to select tenant-specific state (session lookup, per-shop database rows, entitlement checks, GDPR data-request/redaction routing, etc.) can be made to process a cryptographically "valid" webhook under an attacker-chosen shop identity. This is a cross-tenant identity-binding bypass: the gem asserts "this webhook body is authentic and its `shop` field can be trusted" when in fact only the body — not the shop — was ever covered by the signature.

### Likelihood Explanation
Exploitation requires only that the attacker control (or previously receive webhooks from) at least one shop with the app installed — no privileged credentials, access tokens, or `client_secret` access are needed. They simply resend an already-valid `(body, hmac)` pair to the app's public webhook endpoint with a modified shop header, which is a purely network-level, unprivileged-internet-user action.

### Recommendation
Include the `shop` (and ideally `topic`) in the signed/verified content, or independently verify that the `shop-domain` header corresponds to a shop that could plausibly have produced this exact body/HMAC (e.g., re-derive/verify against a per-shop secret or bind shop into `to_signable_string`). At minimum, document that `request.shop` is unauthenticated and must not be used as a trust boundary without additional verification by the consuming application.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `client_secret`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same body `B` and same `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds a request whose `to_signable_string` is still `B`; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H` — validation succeeds.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the body was never actually signed for `victim-shop.myshopify.com`. [3](#0-2) [5](#0-4)
