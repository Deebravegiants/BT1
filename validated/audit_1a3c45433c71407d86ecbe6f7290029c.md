### Title
Empty-pool share-price reset in `pool_u64`/`pool_u64_unbound` lets a depositor capture pool-owned coins after a full-redemption event - (File: `aptos-move/framework/aptos-stdlib/sources/pool_u64.move`)

### Summary
`aptos_std::pool_u64` (and its unbounded twin `pool_u64_unbound`) is the generic shares-accounting primitive used by `staking_contract.move` and `vesting.move` to track staker/operator/beneficiary shares of pending stake distributions of real APT. Its share-pricing functions treat a pool as "fresh" (1:1 coin-to-share) whenever *either* `total_coins == 0` **or** `total_shares == 0`, instead of requiring both to be zero together. This is structurally identical to the CToken/Compound "empty pool exchange-rate" bug in the report: rounding-driven full redemptions can leave the pool in an inconsistent state (`total_shares == 0` while `total_coins > 0`, or vice versa), and the next depositor's `buy_in` is priced against the wrong baseline, letting them mint shares worth more than their own deposit or letting a stale minority holder capture value contributed by a later depositor.

### Finding Description
`amount_to_shares_with_total_coins` and `shares_to_amount_with_total_coins` both special-case the pool as empty using an OR condition: [1](#0-0) 

```
if (self.total_coins == 0 || self.total_shares == 0) {
    coins_amount * self.scaling_factor
} else { ... }
```

and symmetrically in `shares_to_amount_with_total_coins`: [2](#0-1) 

The invariant these accounting pools must hold is: **share price is only undefined/reset when the pool is truly empty (`total_coins == 0 && total_shares == 0`)**. Whenever `redeem_shares` is called against a shareholder whose entire share balance is redeemed, `deduct_shares` removes them from the `shares`/`shareholders` table entirely (dropping `total_shares` for that user to 0 in aggregate if they were the sole holder), while `shares_to_amount` uses floor division (`math64::mul_div`), so `redeemed_coins` can be strictly less than the shareholder's true proportional stake. This can leave `total_shares == 0` with `total_coins > 0` (dust left behind), or, via `update_total_coins` — which is called unconditionally by `staking_contract.move`/`delegation_pool.move` to resync the pool's coin total against the real stake balance after rewards accrue — `total_coins` can be pushed to any externally-observed value without any assertion tying it to `total_shares`: [3](#0-2) 

```
public fun update_total_coins(self: &mut Pool, new_total_coins: u64) {
    self.total_coins = new_total_coins;
}
```

Because `update_total_coins` performs no check that `total_shares == 0` implies `total_coins` should also be reset to 0 (or that a non-zero `total_coins` with `total_shares == 0` is disallowed), a pool can end up with `total_shares == 0` and `total_coins > 0` (residual/"donated" balance analogous to the report's step 4, "Transfer underlying from user1 to market"). The very next `buy_in` call takes the OR-branch and mints `new_shares = coins_amount * scaling_factor` — priced as if the pool held **zero** coins — while `self.total_coins += coins_amount` then includes the pre-existing residual balance too. The new depositor thus becomes the *sole* shareholder (100% of `total_shares`) entitled to 100% of `total_coins`, which now also contains the stale residual balance that rightfully belonged to no one (or to a previous shareholder who has already been evicted from the `shares` table by `deduct_shares`).

### Impact Explanation
This corrupts the custody accounting of a live staking/vesting distribution pool: an unprivileged depositor who buys into a `Pool` right after it transiently reaches `total_shares == 0` (a state reachable through ordinary flooring-rounding in `redeem_shares`, and directly settable via `update_total_coins`) can mint shares that entitle them to coins deposited/accrued by others, and any shareholder still tracked but not yet purged from the pool loses their pro-rata claim once `total_coins`/`total_shares` are silently rebased. Since `pool_u64` backs `staking_contract.move`'s pending-distribution pool (real staker/operator commission payouts of APT) and `vesting.move`'s shareholder reward pool, this is a supply/custody accounting corruption that misroutes real APT value between stakeholders — a high-severity custody impact.

### Likelihood Explanation
Exploitation depends on being able to reliably drive a pool to the `total_shares == 0, total_coins > 0` (or reverse) state before another party's deposit lands, and on the magnitude of dust/rounding or in-flight residual balances being economically meaningful. In `staking_contract.move`/`delegation_pool.move`, `update_total_coins` is called by privileged/system flows to resync balances after stake unlocks, not by arbitrary users, which narrows — but given the report's requirement to prove "unprivileged root cause," I could not, within available context, fully confirm an *unprivileged* caller can trigger the residual `total_coins > 0`/`total_shares == 0` sequencing in `staking_contract.move` or `delegation_pool.move` (this would require deeper tracing through `unlock_stake`, `distribute`, and commission-request code paths, which I was not able to complete before running out of investigation budget).

### Recommendation
Change the empty-pool check in both `amount_to_shares_with_total_coins` and `shares_to_amount_with_total_coins` to require `total_coins == 0 && total_shares == 0` (not `||`), and add an invariant assertion in `update_total_coins` (and anywhere `total_coins` is mutated) that if `total_shares == 0`, `new_total_coins` must also be `0`, mirroring the "check exchange rate/use internal cash for empty pools" recommendation from the source report.

### Proof of Concept
Conceptual sequence (mirrors the CToken flow 1:1, using `pool_u64::Pool`):
1. Shareholder A buys in with `coins_amount = X`, receiving `X` shares (`total_coins = X`, `total_shares = X`).
2. A redeems all `X` shares; due to floor division in `shares_to_amount`, `redeemed_coins < X` in general, but consider the scenario where `update_total_coins` is subsequently invoked (e.g., stale reward resync) setting `total_coins = Y > 0` while `total_shares` is already `0` because A was fully evicted by `deduct_shares`.
3. Shareholder B calls `buy_in` with `coins_amount = Z`. Because `total_shares == 0`, the OR-branch prices `new_shares = Z` (ignoring the pre-existing `Y`), yet `total_coins` becomes `Y + Z`.
4. B now owns 100% of `total_shares` and can `redeem_shares` for the full `Y + Z`, capturing the `Y` residual that should not have been attributable to B's deposit alone.

Note: full end-to-end reachability from an unprivileged transaction through `staking_contract.move`/`delegation_pool.move` call sites was not fully traced due to investigation-budget limits; the accounting flaw itself is confirmed directly in `pool_u64.move`'s pricing functions.     public fun buy_in(self: &mut Pool, shareholder: address, coins_amount: u64): u64 {
```text
        if (coins_amount == 0) return 0;

        let new_shares = self.amount_to_shares(coins_amount);

        self.total_coins += coins_amount;
        self.total_shares += new_shares;
        self.add_shares(shareholder, new_shares);
        new_shares
    }
```

```text
    /// Allow `shareholder` to redeem their shares in `self` for coins.
    public fun redeem_shares(self: &mut Pool, shareholder: address, shares_to_redeem: u64): u64 {
        assert!(self.contains(shareholder), error::invalid_argument(ESHAREHOLDER_NOT_FOUND));
        assert!(self.shares(shareholder) >= shares_to_redeem, error::invalid_argument(EINSUFFICIENT_SHARES));

        if (shares_to_redeem == 0) return 0;

        let redeemed_coins = self.shares_to_amount(shares_to_redeem);
        self.total_coins -= redeemed_coins;
        self.total_shares -= shares_to_redeem;
        self.deduct_shares(shareholder, shares_to_redeem);

        redeemed_coins
    }
```

```text
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u64 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            coins_amount * self.scaling_factor
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount, self.total_shares, total_coins)
        }
    }
```

```text
    /// Return the number of coins `shares` are worth in `self` with a custom total coins number.
    /// `shares` needs to big enough to avoid rounding number.
    public fun shares_to_amount_with_total_coins(self: &Pool, shares: u64, total_coins: u64): u64 {
        // No shares or coins yet so shares are worthless.
        if (self.total_coins == 0 || self.total_shares == 0) {
            0
        } else {
            // Shares price = total_coins / total existing shares.
            // Shares worth = shares * shares price = shares * total_coins / total existing shares.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(shares, total_coins, self.total_shares)
        }
    }
```
