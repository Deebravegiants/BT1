### Title
Bandwidth gate is enforced on `on_accept` (POST requests) but never actually called on `on_response` (GET responses), despite a comment claiming parity — `ProxyModule::on_response` in the Gargantua/Nexus ISMP router - ([File: parachain/runtimes/gargantua/src/ismp.rs])

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` is the mechanism that meters and rate-limits inbound cross-chain traffic per `(source chain, app)`, analogous to a rate limiter guarding an expensive operation. It is correctly invoked in `ProxyModule::on_accept` before a POST request is processed, but the mirrored `ProxyModule::on_response` path for GET responses — which performs the same class of expensive verification/dispatch work — has no call to `try_consume` at all, even though its comment explicitly says it "mirrors the request path in `on_accept`". This is structurally the same bug class as CVE-2026-54037: a security control applied to one of two functionally-equivalent endpoints but silently omitted from its sibling.

### Finding Description
`ProxyModule::on_accept` in [1](#0-0)  explicitly gates every non-purchase POST request through `pallet_bandwidth::Pallet::<Runtime>::try_consume(&request.source, &request.from, bytes)` before any further processing, rejecting the message with `bandwidth gate: ...` if the app's allowance is insufficient.

The sibling handler, `ProxyModule::on_response`, in the same file, carries a comment claiming equivalent protection: [2](#0-1) 
```
fn on_response(&self, response: GetResponse) -> Result<Weight, anyhow::Error> {
    // Bandwidth gate. Mirrors the request path in `on_accept`: the chain
    // and module that produced the response pay for the bytes they
    // deliver. Compiled out when the `no-bandwidth` flag is on.
    if response.dest_chain() != HostStateMachine::get() {
        return Ok(Weight::from_parts(0, 0));
    }
    ...
}
```
There is no call to `try_consume`, `BandwidthGate`, or any equivalent metering primitive anywhere in the function body — only a destination check followed by direct dispatch to the destination module's `on_response`. The same absence exists in the Nexus runtime's `ProxyModule::on_response` [3](#0-2) , which has no bandwidth-related comment or code at all.

Per the protocol documentation, the bandwidth gate is meant to be "a hook the ISMP router consults on every inbound request from a source chain" , and the end-to-end flow description states the gate runs "before processing the request" for dispatch generally. The `on_response` path for `GetResponse` delivery performs comparable state-proof verification and dispatch work (see the ISMP `response.rs` handler which does storage-proof verification, receipt bookkeeping, and module callback dispatch) [4](#0-3) , yet none of that cost is metered by the bandwidth allowance the way POST-request delivery is.

### Impact Explanation
An app that is subject to the bandwidth gate on the POST-request path (i.e., not on the allowlist, and depleted or never subscribed) can still have GET-response traffic delivered to it for free and without limit, because `on_response` never checks or drains its `(source, app)` allowance. This lets an attacker (or a legitimately depleted app/relayer) exhaust the analogous resource — computationally expensive state-proof verification and dispatch cycles gated by the bandwidth model — via the GET-response delivery path, exactly bypassing the protection intended to prevent unmetered resource consumption, mirroring how `/api/convos/duplicate` bypassed the rate limiter applied to `/api/convos/fork`. Because the bandwidth-purchase economics (`docs/content/developers/evm/bandwidth/overview.mdx`) assume the gate is the sole mechanism metering inbound traffic cost, an unmetered response path is a genuine gap in the resource-accounting invariant, not merely a low-severity oversight — it defeats the protocol's DoS mitigation for one entire message class.

### Likelihood Explanation
High likelihood of reachability: any relayer can submit a `Response` (`GetResponseMessage`) through the standard `handle_unsigned` unsigned-extrinsic path, which is free to submit (subject only to proof validity, not bandwidth) [5](#0-4) . As long as valid GET requests/responses exist (or can be manufactured against permissible destinations), an attacker or unprivileged relayer can drive `on_response` calls indefinitely without ever needing a funded bandwidth subscription, since the check is simply never invoked.

### Recommendation
Add the same `BandwidthGate::try_consume` call (with an equivalent purchase/allowlist bypass check) to `ProxyModule::on_response` in both `parachain/runtimes/gargantua/src/ismp.rs` and `parachain/runtimes/nexus/src/ismp.rs`, metering response bytes analogously to how `on_accept` meters request bytes, before the message is forwarded to the destination module.

### Proof of Concept
1. Do not purchase any bandwidth subscription for app `X` on source chain `S` (or exhaust its subscription).
2. Have `X` on the destination chain issue enough `GetRequest`s that a relayer can construct a `ResponseMessage` (`Message::Response`) targeting `X`.
3. Submit `handle_unsigned` with a `Message::Response` batch for `X` via the free unsigned-extrinsic path.
4. Observe that `ProxyModule::on_response` dispatches to `X`'s callback without any `GateError::NoAllowance` / `Insufficient` rejection, whereas an equivalent POST request would be rejected by `on_accept`'s bandwidth check. Repeating this indefinitely demonstrates unmetered resource consumption despite the bandwidth allowance being empty.

Note: I was unable to fully verify whether an upstream layer (e.g., `pallet-state-coprocessor`'s `handle_get_requests`, which does reference dedup logic) independently applies a bandwidth charge for responses before they reach `ProxyModule::on_response`; the `RuntimeBandwidthGate` type alias is wired into `pallet_state_coprocessor::Config` [6](#0-5) , so it is possible metering happens elsewhere in the GET-response construction pipeline rather than in `on_response`. Confirming this would require tracing `pallet-state-coprocessor`'s use of `RuntimeBandwidthGate` end-to-end, which was not fully covered by the available search results.
