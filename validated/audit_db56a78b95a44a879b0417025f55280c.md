### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header, yet `Registry.process` trusts `request.shop` as the tenant identifier when dispatching webhook data to the host application's handler. Any actor who possesses one valid `(body, hmac)` pair — including a legitimate merchant receiving their own genuine webhooks — can replay that pair while substituting an arbitrary `shop-domain` header, and the HMAC check still passes, causing the payload to be processed under a different tenant's identity.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes_the_app_attributes_the_request_to)`. In practice the gem computes and verifies: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; the `hmac` is likewise decoded from the `hmac-sha256` header alone. Neither includes the `shop-domain` header. But `shop` is read straight from an attacker-controllable header: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then forwards `request.shop` — unauthenticated with respect to the signature — to the app's handler as the trusted tenant identifier: [4](#0-3) 

`Utils::HmacValidator.validate` confirms this: it signs/verifies `verifiable_query.to_signable_string` (the raw body) against the secret, never touching `shop`: [5](#0-4) 

Before the attacker's request: `hmac` is valid for `(raw_body, shop=A)` as originally sent by Shopify to the app for shop A's tenant.
After the attacker's request: the same `raw_body`/`hmac` pair is resent with `shop-domain` header rewritten to `shop=B`. `HmacValidator.validate` still returns `true` because the signature never depended on `shop`, so `Registry.process` builds `WebhookMetadata` claiming the data came from shop B and invokes the handler accordingly — breaking the equality `shop_authenticated_by_hmac == shop_used_for_tenant_routing`.

### Impact Explanation
This is a cross-tenant identity-binding break: the webhook signature authenticates the payload bytes but not the tenant the payload is attributed to. A host application that keys any tenant-scoped side effect (e.g., updating shop records, triggering per-shop business logic, writing to a shop-specific data store) off `WebhookMetadata#shop` as delivered by this gem will process another tenant's data as if it belonged to the attacker-chosen shop, since the gem itself performs no binding check between the verified bytes and the `shop` field it hands to the handler.

### Likelihood Explanation
Any entity that receives at least one genuine webhook for a shop they control (e.g., any merchant who installs the app) obtains a valid `(body, hmac)` pair without ever needing `api_secret_key`. They can then replay that exact pair against the app's webhook endpoint with a different `shop-domain` header value. No privileged access, secret leakage, or TLS interception is required — only the ability to send an HTTP request carrying previously-seen, self-obtained webhook bytes with a modified header, which squarely matches an unprivileged-internet-user analog of the Oracle-swap bug (a field acted upon, `shop`, is not covered by the same integrity check, `hmac`, as the rest of the trusted state).

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header bytes in the value that is HMAC-verified, or otherwise cryptographically bind `shop` to the signature before it is exposed via `WebhookMetadata`. At minimum, `to_signable_string` should incorporate the shop domain so that `Utils::HmacValidator.validate` fails whenever the shop header is altered relative to what was originally signed.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com`: raw body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B`), header `shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (who legitimately received this webhook, e.g. as the shop-a merchant) resends the identical `B` and `H` to the app's webhook endpoint but sets `shopify-shop-domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "shop-b.myshopify.com"})` is constructed; `request.shop` now returns `"shop-b.myshopify.com"`.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because `B` and `H` are unchanged.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: parsed(B), ...))` runs, causing the host app to process shop A's webhook payload as if it originated from shop B.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
