### Title
Auto-lock timeout bypass via `maxTtl` fallback in `PassphraseCache.get()` — cached passphrase remains valid far longer than the user-configured auto-lock timer - (File: `features/application/src/modules/passphrase-cache.ts`)

### Summary
`PassphraseCache` caches the wallet's plaintext passphrase in storage so the wallet can auto-unlock without re-prompting the user, gated by a user-configurable auto-lock timer (`ttl`, stored via `autoLockTimerAtom`) and an absolute `maxTtl` ceiling. The validity check in `get()` uses two different time bases depending on whether `inactiveAt` has been recorded: when it has not (i.e., before `scheduleClear()` is ever invoked), the code validates the cache against `this.#maxTtl` instead of the actual configured `ttl`, letting the cached secret remain usable for up to the full `maxTtl` window regardless of a much shorter user-chosen auto-lock duration.

### Finding Description
`PassphraseCache.set()` stores the passphrase together with `addedAt` (current time) and the current `ttl` value read from `autoLockTimerAtom`: [1](#0-0) 

`get()` then decides whether the cached passphrase can still be returned: [2](#0-1) 

There are two branches:
- If `inactiveAt` has been set (via `scheduleClear()`), validity is `inactiveAt + ttl > Date.now()` — correctly using the actual configured `ttl`.
- If `inactiveAt` has **not** been set, validity is `addedAt + this.#maxTtl > Date.now()` — using the fixed, generally much larger `maxTtl` ceiling instead of the user's configured `ttl`.

`this.#maxTtl` is derived independently from configuration (defaulting to 60 minutes) and is intended only as an absolute cap on `changeTtl()`, not as the operative session timeout: [3](#0-2) [4](#0-3) 

`inactiveAt` is only populated by `scheduleClear()`, which is a distinct code path from `set()`/`get()`: [5](#0-4) 

Because the primary defense against a lingering plaintext-passphrase-in-storage is the "clear-passphrase" alarm scheduled in `#scheduleClear()`/`changeTtl()`, and because `scheduleClear()` (which sets `inactiveAt`) is only triggered by specific lifecycle events, any `get()` call that happens before that lifecycle event fires (or in any state where `inactiveAt` was never written, e.g. right after the alarm-driven flow was skipped or the extension/service worker restarted before that hook ran) is validated against `maxTtl`, not the user's chosen `ttl`. This is structurally the same class of bug as the reported flaw: the algorithm silently substitutes the wrong reference value (a global ceiling instead of the actual, up-to-date per-session rate/parameter) when computing whether a time-bounded resource is still "owed"/valid, producing a result inconsistent with the intended security invariant — the auto-lock timer configured by the user.

### Impact Explanation
The auto-lock timer is a core wallet-security control: it defines how long the plaintext passphrase (which decrypts the seed) may remain cached in local storage after the last user activity. If `get()` accepts the cached passphrase using `maxTtl` instead of the actual configured `ttl`, an attacker who gains local access to the device/browser-extension storage (e.g., via another local exploit, or simply someone with physical/session access to an unattended device) can retrieve or trigger auto-unlock using the still-cached plaintext passphrase well beyond the window the user believed they had configured (e.g., a user sets a 1-minute auto-lock, but the passphrase remains usable for up to `maxTtl`, default 60 minutes). This directly weakens a wallet-secret protection boundary and can lead to unauthorized wallet unlock/signing without user re-authentication — a direct wallet-compromise-adjacent impact.

### Likelihood Explanation
The discrepancy is deterministic and does not require rounding or race conditions to manifest — it occurs on every `get()` call made before `inactiveAt` is ever set for a caching session. Since `inactiveAt` is set only through the separate `scheduleClear()` lifecycle hook, an extended plaintext-passphrase validity window is a normal-path branch of the code, not a rare edge case, making the flawed timeout comparison readily reachable in ordinary wallet usage.

### Recommendation
Always evaluate cache validity against the actual, currently-configured `ttl` (from `autoLockTimerAtom`/`TTL_KEY`), never against `maxTtl`, which should only function as a hard ceiling applied in `changeTtl()`. Concretely, replace the `addedAt + this.#maxTtl` branch with `addedAt + ttl` (using the `ttl` read from storage), so that both branches of `get()` enforce the same, user-configured session lifetime, with `maxTtl` never used as a substitute for the real per-session expiry.

### Proof of Concept
1. Configure `autoLockTimerAtom` (via `changeTtl`) to a short value, e.g. 1 minute, while `config.maxTtl` remains at its default (60 minutes).
2. Call `passphraseCache.set(passphrase)`; this persists `addedAt = now`, `ttl = 1m`.
3. Do **not** trigger any code path that calls `scheduleClear()` (i.e., `inactiveAt` remains unset in storage) — the app is simply idle/backgrounded without hitting whatever lifecycle hook invokes `scheduleClear()`.
4. Wait more than 1 minute (the configured `ttl`) but less than 60 minutes (`maxTtl`).
5. Call `passphraseCache.get()` — per [6](#0-5) , since `inactiveAt` is falsy, the code checks `addedAt + this.#maxTtl > Date.now()`, which is still true, and the plaintext passphrase is returned — contradicting the user's configured 1-minute auto-lock expectation.

    const [passphrase, addedAt, inactiveAt, ttl] = (await this.#storage.batchGet([
      PASSPHRASE_KEY,
      ADDED_AT_KEY,
      INACTIVE_AT_KEY,
      TTL_KEY,
    ])) as [string, number, number, number]

    if (passphrase) {
      if (inactiveAt) {
        if (inactiveAt + ttl > Date.now()) {
          this.#logger.log('fetched cached passphrase, in activity period')
          return passphrase
        }
      } else if (addedAt + this.#maxTtl > Date.now()) {
        this.#logger.log('fetched cached passphrase')
        return passphrase
      }

      this.#logger.log('fetched expired passphrase, clearing and preventing unlock')
      void this.clear()
    }

    this.#logger.log('passphrase not in cache')
  }
