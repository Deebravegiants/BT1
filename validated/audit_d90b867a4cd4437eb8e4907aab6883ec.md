### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop-identifying header (`shop-domain`) — along with `topic`, `webhook-id`, and `api-version` — is read directly from unauthenticated HTTP headers and never included in the HMAC-signed payload. `Registry.process` validates only that the *body* bytes are authentic, then blindly trusts `request.shop` (and `request.topic`) to route/attribute the webhook. This breaks the intended binding: `HMAC-verified bytes == data acted upon`.

### Finding Description
The webhook flow is: [1](#0-0) [1](#0-0) 

`hmac` is computed only over `@raw_body` (`to_signable_string` returns `@raw_body`), yet `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, and then constructs `WebhookMetadata` directly from the unauthenticated `shop` header: [3](#0-2) 

Because the app's `api_secret_key` (used to HMAC the body) is a single shared per-app secret, not a per-shop secret, *any* merchant who has this app installed can legitimately receive a webhook with a valid HMAC over its body. That merchant (an "unprivileged internet user" with respect to any other tenant) can then replay the exact same raw body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a different (victim) shop's domain. The HMAC still validates — it only proves the *body* bytes are Shopify-authentic, not that they originated for the claimed shop or topic. The equality the code implicitly (and incorrectly) assumes is:

`HMAC_valid(raw_body) == (shop_header, topic_header) are authentic`

but the actual guarantee is only `HMAC_valid(raw_body) == raw_body is authentic`. This is the same class of defect as the referenced report's unsigned `nlrType`: a value that determines how data is interpreted/attributed (there, the validator type; here, the tenant/topic) is not included in the signed material, so an attacker can freely swap it while keeping the signature valid.

### Impact Explanation
This enables cross-tenant confusion in any host application that relies on `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata#shop` to attribute incoming webhook data to the correct shop (which is the gem's documented usage pattern). An attacker-controlled shop can cause the app to process/store data, or trigger shop-scoped side effects (e.g. mandatory `shop/redact`, `customers/redact`, `customers/data_request` compliance topics), under a victim shop's identity. This is a cross-tenant access/data-integrity issue directly caused by this gem's `Request`/`Registry` design, not by any documented API misuse from the host app.

### Likelihood Explanation
Any user able to install the app on their own store (a normal, unprivileged action) can obtain a validly-HMAC-signed webhook body and replay it with a forged shop header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the shared `api_secret_key`-derived HMAC of a body the attacker can legitimately obtain for their own tenant.

### Recommendation
Bind the shop (and ideally topic) into the signed material, or otherwise cryptographically tie the header claims to the HMAC-verified request. Since Shopify's actual HMAC only covers the raw body by protocol, the gem should independently corroborate the `shop-domain` header against the session/shop the app expects for that webhook, and/or require host apps be given an API that verifies the header set matches a shop with an active, known offline session before dispatching to handlers — rather than trusting `request.shop` as attacker-opaque input straight from the registry's `process` method.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it receive a real webhook (e.g. `orders/create`) — Shopify sends a POST with a body `B` and header `X-Shopify-Hmac-Sha256: HMAC(app_secret, B)` plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `B` and the valid HMAC value.
3. Attacker POSTs the same body `B` and same valid HMAC header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally changes `X-Shopify-Topic` to a mandatory-compliance topic).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(app_secret, raw_body)` — see [4](#0-3)  and [5](#0-4) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, causing the host app to misattribute/act on data for a tenant that never sent it.
