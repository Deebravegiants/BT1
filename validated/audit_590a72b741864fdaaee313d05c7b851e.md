## Title
Webhook shop identity spoofing — HMAC covers only the raw body, not the `shop-domain` header trusted for tenant routing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC over the body only, then dispatches to the app's handler using the header-derived `shop` value without any cryptographic binding between that value and the signed bytes.

### Finding Description
`Request#hmac`/`to_signable_string` sign/verify only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no relation to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) and then trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `shop asserted to handler == shop that produced the HMAC-signed body`. Because `shop-domain` is not part of `to_signable_string`, this equality is never checked — the gem verifies "these bytes were HMAC'd with our secret" but not "these bytes came from the shop this request claims to be from." An attacker who at any point legitimately receives one authentic `(raw_body, hmac)` pair for their own shop (e.g. from a webhook fired against their own dev/trial store using the app) can replay that exact body/HMAC pair against the app's public webhook endpoint while substituting the `shop-domain` header for any other tenant. `HmacValidator.validate` still succeeds since it only checks the body signature, and `Registry.process` forwards the attacker-chosen `shop` to the host application's handler as if it were authentic.

### Impact Explanation
This breaks the `shop`-based tenant binding for any application that uses `WebhookMetadata#shop` (i.e., `request.shop`) to route webhook data to the correct tenant/session in storage. An attacker can inject forged data attributed to another merchant's shop — a cross-tenant data-integrity/access issue, matching the "Missing Constraint" bug class from the reference advisory where a claimed data source is not bound to the verified signature.

### Likelihood Explanation
Exploitability requires only: (1) being (or briefly acting as) an unprivileged user with access to any single shop running the target app to obtain one authentic `(body, hmac)` pair, and (2) sending an HTTP POST to the app's public webhook endpoint with the header changed. No access token, `client_secret`, or privileged account is needed, and the gem itself performs no IP allow-listing or additional binding.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string alongside the body, or otherwise cryptographically bind the claimed `shop` to the verified payload before dispatching to handlers, e.g. by having `to_signable_string` incorporate all Shopify-controlled headers, not just `@raw_body`.

### Proof of Concept
1. Attacker installs/uses the app on their own shop `attacker.myshopify.com` and captures one legitimate webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data as if it originated from `victim.myshopify.com`.
