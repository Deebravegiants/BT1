### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by HMAC-validating the raw request body, but the tenant identifier (`shop`) that the gem hands to the app's `WebhookHandler` is read from an HTTP header that is never included in the signed bytes. This breaks the identity binding: `hmac-verified-bytes == raw_body` but `tenant-key-used-downstream == shop-domain header`, and these two are never bound together.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with `to_signable_string` returning only `@raw_body`: [1](#0-0) 
The `shop` accessor, however, is derived entirely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which plays no part in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` as the tenant identity forwarded to the app-supplied handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) using the app's shared `api_secret_key`: [4](#0-3) 

Because the `api_secret_key` is shared across all shops/tenants of a given app, any legitimate webhook (body + valid HMAC) that Shopify sends to the app for one shop is a valid `(body, hmac)` pair for *any* shop the attacker chooses to claim, since the shop-domain header is completely outside the signed payload. A user who installs the target app on their own store receives genuine webhook deliveries (real body + real HMAC signed with the app's secret). They can capture such a `(raw_body, hmac)` pair and replay it directly to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuinely valid) and will invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain: [5](#0-4) 

The gem's own documentation explicitly instructs app developers to trust `data.shop` as the tenant key returned from a "verified" request, reinforcing that this is the intended binding the gem is supposed to provide: [6](#0-5) 

This contrasts with the OAuth flow in the same gem, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, so `shop` cannot be substituted without invalidating the HMAC: [7](#0-6) 
The webhook path lacks this equivalent protection.

### Impact Explanation
An attacker who is merely an installer of the target app on their own (unprivileged) shop can forge webhook deliveries that appear, to the app's handler, to originate from a different, victim shop — a cross-tenant identity confusion. Depending on how the host application uses `WebhookMetadata.shop` (e.g., looking up the victim's local records, acting on GDPR "customers/redact" data, updating cached order/product data, or triggering shop-scoped business logic) this can result in cross-tenant data corruption, cross-tenant data disclosure inference, or spoofed compliance-webhook processing for a shop the attacker does not own — satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one genuine `(raw_body, hmac)` webhook pair, which requires having the app installed on some shop (an ordinary, unprivileged action any user can take by installing a public app). No `api_secret_key`, access token, or privileged credential is required — the attacker never needs to compute a valid HMAC themselves, only replay one they legitimately received. This is fully reachable through the gem's documented `Registry.process` / `Request` API with no reliance on the host app ignoring the gem's contract.

### Recommendation
Bind the `shop` identity into the HMAC-verified payload rather than trusting an unauthenticated header. Concretely, `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop-domain` header (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or `Registry.process` should cross-check the header-derived `shop` against an independently trusted source (e.g., require the caller to supply the expected shop, or validate that the shop is one currently subscribed for that specific webhook topic/registration) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify delivers a genuine webhook (e.g., `customers/redact`) to the app's endpoint with a valid raw body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker captures `B` and `H`, then sends a forged HTTP request to the same endpoint with headers `shopify-shop-domain: victim-shop.myshopify.com`, `shopify-topic: customers/redact`, `shopify-hmac-sha256: H`, and body `B`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`, which is unaffected by the header change. [8](#0-7) 
5. `Registry.process` calls the app handler with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to act as if the victim shop sent this compliance/business webhook, even though the victim never did.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
