### Title
Webhook HMAC signature does not cover the `X-Shopify-Shop-Domain` header, allowing shop-identity spoofing on a validly-signed request - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop` value used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant is read from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed payload.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body ++ shop ++ topic)` (i.e., the authenticated tenant identity should be bound to the signature). Instead, the actual binding implemented is:

- Verified: `hmac == HMAC(secret, body)` — [1](#0-0) 
- Acted on: `shop` taken from an unauthenticated header — [2](#0-1) 

`Registry.process` validates the HMAC and then directly hands `request.shop` (and `request.topic`) — both unauthenticated header values — to the registered handler without any check that they were part of the signed material: [3](#0-2) 

`HmacValidator.validate_signature` compares `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, and for `Request` that signable string is just `@raw_body`: [4](#0-3) 

Because a merchant who has a legitimate app installation receives real webhooks from Shopify (body + a validly computed HMAC using the app's real `client_secret`, which the merchant does not know but legitimately possesses as ciphertext for their own shop's traffic), that merchant can replay the exact same `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header (and potentially the `topic` header) for a different shop. The signature will still validate because it never covered those headers, and the host application's handler will process the payload as if it came from — and pertains to — a different tenant.

### Impact Explanation
This breaks the shop-identity binding at the gem level: `Registry.process` asserts a validated HMAC while forwarding an unauthenticated `shop` value to the webhook handler [5](#0-4) . Any host application that trusts `WebhookMetadata#shop` (the standard, documented pattern shown in the gem's own tests, e.g. `assert_equal(@shop, data.shop)`) as the authenticated tenant identifier for the request is exposed to cross-tenant data corruption/access: an attacker with any legitimate app install (i.e., a normal unprivileged merchant, not a privileged account, no leaked credentials, no TLS interception) can cause a webhook payload to be attributed to a shop of their choosing, e.g., forging `customers/redact`, `orders/create`, `app/uninstalled`, etc. against a victim's tenant record.

### Likelihood Explanation
The mechanics require only that the attacker be able to trigger any webhook to their own installed app (trivial — any store owner can generate webhooks against their own store, e.g. by placing/canceling an order) and replay the HTTP POST with modified headers to the app's public webhook endpoint (unauthenticated internet-reachable endpoint by design). No access to `api_secret_key`, tokens, or privileged accounts is required, matching this gem's "unprivileged internet user" attacker model and the "field acted on but not covered by the HMAC" analog explicitly called out as in-scope.

### Recommendation
Include the shop domain (and ideally the topic and API version) in the signed material verified for webhook requests, or otherwise cryptographically bind the header-derived `shop`/`topic` values to the signature before they are consumed. If Shopify's wire protocol only signs the body, the gem should treat `shop`/`topic` from headers as untrusted for authorization decisions and document this, or provide a way for consumers to cross-check `shop` against the value returned by a separate trusted channel (e.g. requiring an out-of-band confirmed shop-to-secret mapping) rather than exposing it via `WebhookMetadata` as if it were authenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), receiving from Shopify a POST with:
   - Headers: `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid_hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body: `{"id": 1, ...}` (attacker fully controls order content on their own store).
2. Attacker resends the exact same request to the app's public webhook endpoint, but changes only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` if desired), keeping body and `X-Shopify-Hmac-Sha256` identical.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) — this matches the original, unmodified body, so validation succeeds: [6](#0-5) [7](#0-6) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is now `victim-shop.myshopify.com` — a header value that was never covered by the signature: [8](#0-7) 
5. Any host application logic keyed on `data.shop` (the pattern this gem's own tests exercise, e.g. `assert_equal(@shop, data.shop)`) now performs a cross-tenant action attributed to the victim shop, using attacker-supplied body content.
