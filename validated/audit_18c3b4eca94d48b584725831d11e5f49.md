Audit Report

## Title
Silent Failure to Deduct Overspend in Workflow Metering `Report.Settle` Allows Local Credit Balance to Exceed Actual Reserved Funds - (File: `core/services/workflows/metering/metering.go`)

## Summary
`Report.Settle` refunds unused earmarked credits via `r.balance.Add(step.Deduction.Sub(spentCredits))`, but when a capability's actual reported spend (`spentCredits`) exceeds its earmark (`step.Deduction`), the resulting negative amount is rejected by `balanceStore.Add`'s guard against negative values, and the error is only logged, never handled. This leaves the in-execution local credit balance artificially inflated relative to real consumption for the remainder of that workflow execution.

## Finding Description
`Deduct` (via `ByResource` and `ByDerivedAvailability`) earmarks credits by calling `r.balance.Minus(bal)` / `r.balance.Minus(limit.Decimal)`, both confirmed at [1](#0-0) and [2](#0-1) . `Settle` later aggregates the actual reported spend into `spentCredits` and attempts to return the unused earmark with `r.balance.Add(step.Deduction.Sub(spentCredits))`, logging only "invariant: spend exceeded reserve" on error, at [3](#0-2) . `balanceStore.Add` explicitly rejects negative amounts with `ErrInvalidAmount` at [4](#0-3) , so when `spentCredits > step.Deduction`, the excess is never subtracted from `r.balance`. `r.balance.Get()` is subsequently used unmodified by `getMaxSpendForInvocation` to compute credit budgets for later steps in the same execution, at [5](#0-4) , meaning the local per-execution quota enforcement is desynchronized from actual usage for the rest of that execution.

Notably, `r.balance.AddSpent(spentCredits)` is called unconditionally regardless of the `Add` outcome, so the final aggregate total reported to the billing service via `SendReceipt`'s `CreditsConsumed: r.balance.GetSpent().String()` remains numerically correct — the flaw is isolated to the *local, intra-execution* available-balance bookkeeping that gates further `Deduct` calls, not the final billed amount.

## Impact Explanation
This is a genuine logic bug that breaks the stated invariant in the code's own comment ("capability should not let spend exceed reserve"). Its effect is that within a single workflow execution, after one capability step overspends its earmark, subsequent `Deduct` calls (`ByResource`/`ByDerivedAvailability`) see a higher `r.balance.Get()` than truly remains, letting later steps in the same execution be authorized for more spend than the execution's reservation should allow. However, the end-of-execution billing (`SendReceipt`/`CreditsConsumed`) still reflects the true cumulative spend via `AddSpent`, so this does not enable free/uncharged capability usage or fund theft — it only weakens the in-flight per-execution spend-limiting mechanism that gates concurrent/sequential capability calls, potentially letting an execution consume more resources than its reservation nominally permitted before eventually being billed correctly for whatever was actually used.

## Likelihood Explanation
Reaching this requires a capability/DON response whose reported `Metering` spend for a step exceeds what was earmarked for that step — plausible under normal conditions (e.g., gas price volatility causing on-chain spend to exceed an earlier gas estimate) without any malicious actor. This is a real code defect confirmed by direct inspection.

## Recommendation
In `Report.Settle`, when `spentCredits > step.Deduction`, explicitly deduct the excess via `r.balance.Minus(spentCredits.Sub(step.Deduction))` or switch to metering mode via `r.switchToMeteringMode(...)` so the local balance is not left in an inconsistent, overly-generous state, consistent with the fail-safe pattern already used elsewhere in the file (e.g., `switchToMeteringMode` calls in `Deduct` and `Settle`'s conversion-error branches).

## Proof of Concept
1. Call `Report.Reserve` to establish a fixed local balance.
2. Call `Report.Deduct("stepA", ByResource(spendType, capID, X))`, earmarking `X` and reducing `r.balance` by `X`.
3. Call `Report.Settle("stepA", metadata)` with `metadata.Metering` such that aggregated `spentCredits = Y`, where `Y > X`.
4. Observe `r.balance.Add(X.Sub(Y))` returns `ErrInvalidAmount` (logged only) and `r.balance.Get()` is unchanged (not reduced by `Y - X`).
5. Call `Report.Deduct("stepB", ByDerivedAvailability(...))` and observe it computes its spend limit from the inflated `r.balance.Get()`, granting stepB a larger budget than the execution's true remaining reserve. A unit test in `core/services/workflows/metering/metering_test.go` asserting `r.balance.Get()` after an overspending `Settle` call would directly demonstrate the discrepancy.

func (r *Report) getMaxSpendForInvocation(
	userSpendLimit decimal.NullDecimal,
	openConcurrentCallSlots int,
) (decimal.NullDecimal, error) {
	nullCapSpendLimit := decimal.NewNullDecimal(decimal.Zero)
	nullCapSpendLimit.Valid = false

	if openConcurrentCallSlots == 0 {
		// invariant: this should be managed by the consumer (engine)
		return nullCapSpendLimit, ErrNoOpenCalls
	}

	if !r.reserved {
		return nullCapSpendLimit, ErrNoReserve
	}

	if r.meteringMode {
		return nullCapSpendLimit, nil
	}

	// Split the available local balance between the number of concurrent calls that can still be made
	spendLimit := r.balance.Get().Div(decimal.NewFromInt(int64(openConcurrentCallSlots)))

	if userSpendLimit.Valid {
		spendLimit = decimal.Min(spendLimit, userSpendLimit.Decimal)
	}

	return decimal.NewNullDecimal(spendLimit), nil
}
