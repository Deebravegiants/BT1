### Title
POA Bridge Misreports Withdrawal Completion Status by Matching Only on `assetId`, Causing Wrong Tx-Hash/Status for Batched Same-Token Withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves withdrawal status by matching the bridge's response list solely on `assetId` via `findMatchingWithdrawal`, ignoring the `index` that uniquely identifies each withdrawal produced from a single NEAR transaction. When a caller batches multiple withdrawals of the same token in one transaction (a pattern the SDK explicitly supports via `createWithdrawalCompletionPromises`, which accepts an array of `withdrawalParams`), every one of those withdrawals resolves against the *first* matching entry returned by the POA bridge API, so distinct withdrawals (potentially with different destination addresses/amounts) are reported "completed" with the same `txHash`/status.

### Finding Description
`describeWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 313-343) calls:
```
const withdrawal = findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId);
```
`findMatchingWithdrawal` (lines 409-427) is explicitly documented as matching only by `assetId`:
```
// NOTE: Currently only matches by assetId. This means multiple withdrawals
// of the same token in a single transaction are not supported.
```
and returns `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — the first array element with the matching token, regardless of `args.index`, `destinationAddress`, or `amount`.

The `WithdrawalIdentifier` type (`shared-types.ts` lines 434-441) carries a per-bridge `index` specifically to disambiguate multiple withdrawals from the same NEAR transaction, and `createWithdrawalIdentifier` in the same file does receive `args.index`, but it is never threaded into the matching logic for the POA bridge (unlike `HotBridge.describeWithdrawal`, which correctly indexes into a `nonces` array by `args.index`, and `OmniBridge.describeWithdrawal`, which indexes `getTransfer(...)[args.index]`).

`IntentsSDK.createWithdrawalCompletionPromises` (exercised by `sdk.createWithdrawalCompletionPromises.test.ts`) accepts an array of `withdrawalParams` for a single `intentTx` and creates one watcher per entry, explicitly supporting multiple withdrawals batched into a single NEAR transaction — including, structurally, multiple withdrawals of the same `assetId` to different destinations. For the POA bridge route, all such entries will collapse onto the single (first) matching bridge-side withdrawal record.

This breaks the equality "status/hash reported for withdrawal N" == "the on-chain outcome of withdrawal N": the SDK instead reports "the on-chain outcome of whichever withdrawal the POA API listed first" for every batched entry sharing that `assetId`.

### Impact Explanation
An integrator that fans out several same-token POA withdrawals in one NEAR transaction (e.g. paying out several different users' BTC/ZEC withdrawals in a single batched intent) will receive `{status: "completed", txHash: X}` for all of them once the *first* one settles, even though the other withdrawals are still pending or point to a different destination address entirely. This is a status misreport that can make an integrator credit/mark-as-complete multiple withdrawals based on a single actual on-chain payout, matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. The bug is in first-party SDK code (not a POA API/relayer trust assumption): the code has the `index` available and simply doesn't use it for POA, unlike the analogous Hot/Omni bridge implementations that do disambiguate by index.

### Likelihood Explanation
Requires the integrator to batch ≥2 withdrawals of the identical `assetId` within one NEAR transaction using the POA bridge route — a supported, non-malicious usage pattern (no attacker input needed; this is a correctness bug triggered by legitimate multi-withdrawal batching). The comment in the source (`// Response list is unsorted, so we match by assetId instead of index`) confirms the authors were aware only single-withdrawal-per-asset-per-tx is safe, but nothing in the SDK enforces or validates that constraint before allowing batched calls, so the unsafe path is reachable through normal API usage.

### Recommendation
- Either reject/validate at `createWithdrawalIntents`/`createWithdrawalCompletionPromises` time when multiple POA-route withdrawals share the same `assetId` within a batch (fail fast with a clear error), or
- Implement the ordering-based disambiguation the code comment already proposes: sort both the bridge API's returned withdrawals and the local `withdrawalParams` list by amount (since fees are equal per token, relative amount ordering is preserved) and match positionally, so each `index` maps to the correct on-chain withdrawal instead of always the first same-asset match.

### Proof of Concept
1. Build and sign one NEAR intents transaction containing two `ft_withdraw` intents for the same POA-bridged asset (e.g. `nep141:btc.omft.near`) to two different destination addresses, `addrA` (amount 100000) and `addrB` (amount 200000).
2. Call:
```ts
const promises = sdk.createWithdrawalCompletionPromises({
  intentTx: { accountId, hash: txHash },
  withdrawalParams: [
    { assetId: "nep141:btc.omft.near", amount: 100000n, destinationAddress: addrA, feeInclusive: false },
    { assetId: "nep141:btc.omft.near", amount: 200000n, destinationAddress: addrB, feeInclusive: false },
  ],
});
```
3. The POA bridge's `getWithdrawalStatus({withdrawal_hash: txHash})` returns two withdrawal records for `btc.omft.near` (one per destination), in API-determined (unsorted) order.
4. `findMatchingWithdrawal` is invoked identically for both `promises[0]` and `promises[1]` (both querying `assetId = "nep141:btc.omft.near"`), so `Array.prototype.find` returns the *same first record* for both — both promises resolve to the same `{status:"completed", txHash: <hash of whichever withdrawal completed first>}`, even though `addrB`'s withdrawal may still be pending or refer to a completely different transfer. /**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
