This confirms the finding: the gem's own documentation explicitly tells developers to trust `data.shop` from the webhook payload as "The shop domain of the webhook" [1](#0-0)  and its own example handler treats `data.shop` as an authenticated tenant identifier, passing it directly into job processing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`), all *after* `ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" [2](#0-1) . The vulnerability is squarely inside the gem's own verification logic, not host-app misuse.

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` (and `topic`/`webhook_id`) values that are handed to the app's handler are read from unauthenticated HTTP headers that are excluded from the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

`ShopifyAPI::Utils::HmacValidator#validate_signature` computes/compares the HMAC exclusively over `verifiable_query.to_signable_string`: [4](#0-3) 

`ShopifyAPI::Webhooks::Registry.process` uses this HMAC check as its sole authenticity gate, then builds `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id` — all of which come from the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` HTTP headers, not from the signed body: [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `shop value cryptographically bound by HMAC == shop value delivered to the handler`. Because `shop` (and `topic`) are excluded from `to_signable_string`, this equality does not hold — the bytes verified (body only) are not the bytes the handler trusts as the tenant identifier.

Critically, Shopify signs webhook HMACs with the app's single `client_secret`, which is identical for every shop that installs the app — it is **not** shop-specific. This means:
- Before the attack: attacker installs the target app on their own store (a normal, unprivileged action requiring no victim credentials) and receives genuine webhooks with valid HMACs computed over their own store's body content, signed with the app's shared secret.
- After the attack: the attacker replays that exact raw body and valid HMAC to the app's webhook endpoint, but substitutes the `shopify-shop-domain` header (and optionally `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain that also has the app installed.
- `HmacValidator.validate` still succeeds (body+HMAC pair is genuine), so `Registry.process` dispatches the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled content>, ...)`.

Any host application following this gem's own documented pattern — using `data.shop` to select which merchant's session/access token/business data to act on — will process attacker-supplied body content under the victim shop's identity, a direct cross-tenant confusion made possible entirely by this gem's verification logic.

### Impact Explanation
This breaks tenant isolation between merchants of the same app: an attacker who only controls their own (potentially free/trial) shop installation can inject fabricated webhook events attributed to any other merchant using the same app, without needing that merchant's credentials, access token, or the app's `client_secret`. Depending on how the host app processes `orders/create`, `app/uninstalled`, `customers/data_request`, etc., this can lead to data corruption, spoofed business events, or triggering privileged per-shop workflows against another tenant — matching the "cross-tenant access" Critical impact category.
