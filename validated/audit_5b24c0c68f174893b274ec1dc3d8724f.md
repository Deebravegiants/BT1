### Title
Personal-Custody Package Silently Dropped from Data-Uploader Queue Without Logging or Signal, Causing Permanent Loss of Biometric Retention Data - (File: `src/agents/data_uploader.rs`)

### Summary
The `data_uploader` agent enqueues Tier‑1/Tier‑2 personal-custody packages (encrypted iris/face biometric data) for asynchronous upload to the backend. When the queue for a tier reaches its configured `dropping_threshold`, the agent calls `Queue::drop_oldest` to evict a package *before* pushing the new one, with no logging of the drop and no notification back to the signup flow that already reported success to the caller. This mirrors the MasterChef "under-supply" bug class: a resource-capacity shortfall (upload throughput/queue capacity) causes silent, un-signaled loss of the expected deliverable instead of an explicit failure or retry, and the caller has no way to detect or recover the lost data.

### Finding Description
`Input::Pcp` handling in the agent loop checks queue length against `dropping_thresholds` and unconditionally evicts the oldest queued package via `drop_oldest()` before pushing the new one: [1](#0-0) 

`Queue::drop_oldest` for the in-memory variant (`Queue::Memory`, the default queue type since `Persistent` is `#[allow(dead_code)]` and unused in `run`) simply pops from the deque with **no tracing/log call at all**: [2](#0-1) 

The signup flow that feeds this queue treats the `send()` call as fire-and-forget success — once `orb.data_uploader...send(...)` returns `Ok`, the signup pipeline proceeds and reports success without any further confirmation that the Tier‑1/Tier‑2 package was ever uploaded: [3](#0-2) 

The only backpressure mechanism is `WaitQueues`, which blocks new signups once the (higher) `blocking_threshold` is reached, but this is a separate, larger threshold than `dropping_threshold`: [4](#0-3) 

Because `dropping_threshold < blocking_threshold` by design, there is a window where the queue keeps accepting new signups (not blocked) while simultaneously discarding older, already-queued biometric packages that belong to *other, already-completed* signups — with zero logging, zero metrics, and zero mechanism to re-upload or alert. This is functionally identical to the reported bug class: when the sink (upload capacity) is under-supplied relative to demand (signup rate), the system silently fails to deliver the expected output for some users instead of erroring out or queueing durably, and there's no visibility into which signups were affected.

### Impact Explanation
A dropped package means the corresponding user's Tier‑1/Tier‑2 personal-custody package (encrypted iris/face biometric key material required for account recovery/self-custody) is permanently never uploaded to the backend, yet the Orb has already reported the signup as successful. This is a retention/availability failure of biometric custody data reachable purely through normal, unprivileged user signup flow (no special access needed — any burst of signups exceeding upload throughput triggers it), and it happens completely silently: no error log, no metric, no alert distinguishing it from a normally-processed signup.

### Likelihood Explanation
This requires no attacker privilege — it is triggered by ordinary operational conditions: a burst of signups, a slow/degraded backend connection, or network issues that reduce Tier‑1/Tier‑2 upload throughput below intake rate. Given `PARALLEL_UPLOAD_STREAMS = 4` and per-package retry loops in `upload_pcp` that block a upload slot until success, any backend slowdown directly increases queue backlog and increases the likelihood of hitting `dropping_threshold`. This is analogous to the original finding's judged severity: "situational" but with a "very clear example" and real "loss of yield" (here, loss of custody data) — a reasonably foreseeable operational condition rather than a rare edge case.

### Recommendation
- Log a warning/error (and emit a Datadog metric) whenever `drop_oldest` actually discards a package, including the `signup_id`/`user_id` and tier, so operators can detect and potentially recover/reconcile affected signups.
- Do not silently drop packages that have not yet been attempted for upload; prefer increasing `blocking_threshold` enforcement or applying backpressure (block new pushes / fail the signup explicitly) rather than silently evicting already-accepted work.
- Consider making `dropping_threshold` behavior surfaced to the signup flow (e.g., return a result indicating the enqueue may be dropped) instead of a fire-and-forget `send()`.

### Proof of Concept
1. Configure `pcp_tier1_dropping_threshold` (or tier2) to a small value (e.g., 2) via backend config, per `Config::from_backend` / `pcp_tier1_dropping_threshold` field: [4](#0-3) 
2. Cause the backend to be slow/unreachable so `upload_pcp`'s retry loop keeps failing (or simulate this in a unit test by never resolving `backend::upload_personal_custody_package::request`).
3. Perform signups faster than uploads complete, so `queues[i].len()` reaches the `dropping_threshold` while remaining below `blocking_threshold`.
4. Observe (per `run`'s `Input::Pcp` branch) that `drop_oldest()` is invoked, silently discarding the oldest queued Tier‑1/Tier‑2 package for a previously-completed signup, with no corresponding log/metric emitted, while that signup was already reported as `success: true` to the operator/UI.

    async fn drop_oldest(&mut self) {
        match self {
            Self::Memory { queue } => {
                queue.pop_back();
            }
            Self::Persistent { path, queue, .. } => {
                let Some(id) = queue.pop_back() else { return };
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during drop_oldest, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {}
                }
            }
        }
    }
