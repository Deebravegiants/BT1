### Title
Fixed O(1) weight on `handle_unsigned` for unbounded `GetRequestsWithProof` batches enables free, unbounded MMR-leaf accumulation that can overload block finalization - (File: `modules/pallets/state-coprocessor/src/lib.rs`)

### Summary
`pallet_state_coprocessor::handle_unsigned` is a fee-free unsigned extrinsic whose declared weight is a flat constant regardless of how many `GetRequest`s are packed into the batch, while its actual execution cost (proof verification, state-proof verification, and one MMR leaf push per response) scales linearly with the batch size. Every leaf pushed lands in `pallet_mmr_tree`'s `IntermediateLeaves` map, which is drained by an unconditional, mandatory `on_finalize` loop (`Mmr::finalize`) that iterates over every leaf buffered in the block. This is structurally the same bug class as the RootManager report: cheap/free, permissionless, repeatable calls accumulate unbounded work into a queue that a later, un-skippable system call must fully drain in one pass, risking failure/overrun of that pass and blocking the entire pipeline (block finalization / MMR root commitment for the block) for all other requests and consensus updates.

### Finding Description
`GetRequestsWithProof.requests` is an unbounded `Vec<GetRequest>` [1](#0-0) . `handle_get_requests` loops over every request to validate it, verify membership/non-membership proofs, verify a state proof per request, and then loops again to push one MMR leaf per response via `dispatch_get_response` [2](#0-1) [3](#0-2) .

The dispatchable that invokes this is declared with a **fixed** weight independent of the number of requests in the batch: [4](#0-3) 

It is also validated and executed for free as an unsigned transaction (`ensure_none`, and `validate_unsigned` only dedupes by content hash, not cost) [5](#0-4) . The docs confirm the general design intent that ISMP messages executed via `handle_unsigned` are processed "for free" [6](#0-5) .

Every `GetResponse` produced pushes a leaf into `pallet_mmr_tree::IntermediateLeaves`, a `CountedStorageMap` with no cap [7](#0-6)  via the `push` implementation that just increments a counter and inserts [8](#0-7) .

At the end of every block, `pallet_ismp`'s **mandatory** `on_finalize` hook calls `T::OffchainDB::finalize()` unconditionally [9](#0-8) , and `Mmr::finalize()` loops over **every** leaf accumulated in `IntermediateLeaves` during that block, calling `mmr.push` for each one before writing the block's MMR root and child-trie/consensus digest that downstream light clients/relayers rely on to prove any message in that block [10](#0-9) .

This is directly analogous to the RootManager report: (1) a call reachable by any relayer with valid proofs is essentially free/cheap and repeatable many times per block (batch size is attacker-controlled and the declared weight does not scale with it, meaning the runtime weight accounting under-charges the true cost), (2) each invocation feeds an unbounded accumulator (`IntermediateLeaves`) that is not drained by the caller but by a separate, later, mandatory system routine (`on_finalize` → `finalize()`), and (3) that later routine must process the entire accumulated backlog in a single pass with no batching/limit, exactly mirroring `dequeueVerified`/`insert` looping over `pendingInboundRoots` in `RootManager.propagate`.

### Impact Explanation
If an attacker (who can supply enough valid Get-request/response proofs — which they can generate themselves since they can also be the ones dispatching/querying arbitrary state) submits multiple `handle_unsigned` calls with large `requests` arrays within a single block, each individually validated by the mempool (unique `provides` tag derived from message content) and cheap/free to include, the aggregate number of MMR leaves buffered for that block can grow far beyond what the flat, O(1) weight for each call accounted for. When `on_finalize` runs, the resulting `finalize()` loop must synchronously process all of them before the block can complete, which can blow the block's execution-time/weight budget. Because this hook is mandatory (not opt-in per-extrinsic and not weight-limited by the individual extrinsics that fed it), an oversized backlog can stall or fail block finalization for that block, which — mirroring the RootManager scenario — would prevent the MMR root/consensus digest for that block from being produced correctly, blocking proof generation and thus message delivery (for Get responses and, by association, all other ISMP traffic whose commitments are anchored in the same MMR/child-trie) until the backlog is resolved. This is a High severity availability/DoS issue on Hyperbridge's own coordination hub (the coprocessor), affecting the core cross-chain message-proving pipeline.

### Likelihood Explanation
Likelihood is Medium-High: the entrypoint is permissionless, requires only assembling a large batch of valid Get-request/response proofs (feasible since GET requests can be self-dispatched by an attacker's own application, at whatever cost dispatching them costs on the source side), and the unsigned-transaction path makes repeated large-batch submissions essentially free on the coprocessor chain. The main constraint is the attacker's ability to produce many valid proofs before a block closes, which is achievable by pre-computing responses to self-issued GET requests.

### Recommendation
1. Make `pallet_state_coprocessor::handle_unsigned`'s declared weight scale with `message.requests.len()` (e.g., a linear weight function similar to what other batched dispatchables in this codebase use, such as `ismp_parachain::add_parachain(n)`), so the fee/weight system properly reflects true per-request cost and enforces Substrate's block weight limit against it.
2. Enforce an explicit maximum batch size on `GetRequestsWithProof.requests` (bounded `Vec` or an explicit length check) at the top of `handle_get_requests` and/or in `validate_unsigned`.
3. Bound the amount of work `pallet_mmr_tree::finalize()` can perform per block — e.g., cap `IntermediateLeaves` growth per block (rejecting/queueing pushes beyond the cap) or process the MMR insertion queue across multiple blocks in bounded chunks, mirroring the "bound and batch" mitigation recommended for RootManager's `pendingInboundRoots`.

### Proof of Concept
Conceptual PoC (cannot be executed without a live node, but the mechanics are directly traceable in the code):
1. Attacker dispatches many cheap `GetRequest`s from a state-coprocessor-aware application to itself (using the coprocessor as the state-query router), generating self-controlled `GetRequest`s that will time out slowly.
2. Attacker (acting as a relayer) collects the state/response proofs and assembles multiple `GetRequestsWithProof` messages, each carrying a very large `requests` Vec.
3. Attacker submits several such `handle_unsigned` unsigned extrinsics within the same block via `pallet_state_coprocessor::Call::handle_unsigned` — each is validated by `validate_unsigned` (which only checks proof validity and a content-hash-based `provides` tag for dedup, not cost) [5](#0-4) , and each is charged only the fixed `reads_writes(1,2)` weight [11](#0-10)  regardless of the number of requests inside.
4. Each call pushes one MMR leaf per `GetResponse` into `IntermediateLeaves` [12](#0-11) .
5. At block end, `pallet_ismp::on_finalize` unconditionally calls `Mmr::finalize()`, which iterates over every buffered leaf from all these calls in the same block [13](#0-12) , potentially exceeding the block's true execution budget despite the extrinsics themselves having been "priced" as cheap/free.

```rust
	/// Insert a get response into the MMR and emits an event
	pub fn dispatch_get_response(
		get_response: GetResponse,
		address: Vec<u8>,
	) -> Result<(), ismp::Error> {
		let commitment = hash_get_response::<<T as Config>::IsmpHost>(&get_response);
		let req_commitment =
			hash_request::<<T as Config>::IsmpHost>(&Request::Get(get_response.get.clone()));
		let event = pallet_ismp::Event::Response {
			request_nonce: get_response.get.nonce,
			dest_chain: get_response.get.source,
			source_chain: get_response.get.dest,
			commitment,
			req_commitment,
		};

		let leaf_index_and_pos = <T as Config>::Mmr::push(Leaf::GetResponse(get_response));
		let meta = FeeMetadata::<T> { payer: [0u8; 32].into(), fee: Default::default() };

		pallet_ismp::child_trie::ResponseCommitments::<T>::insert(
			commitment,
			RequestMetadata {
				offchain: LeafIndexAndPos {
					leaf_index: leaf_index_and_pos.index,
					pos: leaf_index_and_pos.position,
				},
				fee: meta,
				claimed: true,
			},
		);
		pallet_ismp::Responded::<T>::insert(req_commitment, true);
		pallet_ismp::Pallet::<T>::deposit_event(event.into());
		let event = pallet_ismp::Event::GetRequestHandled(RequestResponseHandled {
			commitment: req_commitment,
			relayer: address.clone(),
		});

		pallet_ismp::Pallet::<T>::deposit_event(event.into());

		Ok(())
	}
```

```text
## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
```

```rust
	fn finalize() -> Result<H256, Error> {
		let buffer_len = IntermediateLeaves::<T, I>::count() as u64;
		// no new leaves? early return
		if buffer_len == 0 {
			return Ok(RootHash::<T, I>::get().into());
		}

		let leaves = NumberOfLeaves::<T, I>::get();
		let mut mmr: ModuleMmr<mmr::storage::RuntimeStorage, T, I> = mmr::Mmr::new(leaves);

		// append new leaves to MMR
		let range = 0u64..buffer_len;
		for index in range {
			let leaf = IntermediateLeaves::<T, I>::get(index).ok_or(Error::Push)?;
			// Mmr push should never fail
			match mmr.push(leaf) {
				None => {
					log::error!(target: "pallet-mmr", "MMR push failed ");
					// MMR push never fails, but better safe than sorry.
					Err(Error::Push)?
				},
				Some(position) => {
					log::trace!(target: "pallet-mmr", "MMR push {position}");
				},
			}
		}

		// Update the size, `mmr.finalize()` should also never fail.
		let (leaves, root) = match mmr.finalize() {
			Ok((leaves, root)) => (leaves, root),
			Err(e) => {
				log::error!(target: "pallet-mmr", "MMR finalize failed: {:?}", e);
				Err(Error::Commit)?
			},
		};

		let _ = IntermediateLeaves::<T, I>::clear(buffer_len as u32, None);
		NumberOfLeaves::<T, I>::put(leaves);
		RootHash::<T, I>::put(root);

		Ok(root.into())
	}
```
