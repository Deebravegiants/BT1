### Title
`WrappedHyperFungibleToken.send()` dispatches the full requested amount even when a fee-on-transfer underlying token delivers less, enabling an unbacked mint on the destination chain - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` (and the identical logic in `WrappedHyperFungibleTokenUpgradeable.send()`) pulls the underlying ERC20 with `safeTransferFrom(msg.sender, address(this), params.amount)` but then encodes and dispatches the cross-chain `Message` using the caller-supplied `params.amount`, never the amount actually received by the contract. This is the exact bug class from the referenced report (`LimitOrders.vy` using `order.amount_in` instead of the actually-received balance), but here the consequence is worse: instead of a revert, it results in an unbacked mint/release on the destination chain.

### Finding Description
In `send()`:
```solidity
// sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:266-290
function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    uint256 msgValue = msg.value;
    if (_isWeth && msgValue >= params.amount) {
        msgValue = msgValue - params.amount;
        IWETH(_underlying).deposit{value: params.amount}();
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }

    DispatchPost memory request = _buildDispatchPost(params);
    ...
}
```
`_buildDispatchPost` encodes the message body using `params.amount` directly:
```solidity
// sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:237-253
bytes memory body = abi.encode(Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,
    data: params.data
}));
```
If `_underlying` is a fee-on-transfer (or rebasing/deflationary) ERC20, the contract's actual received balance is `params.amount - fee`, but the dispatched `Message.amount` still claims `params.amount`. When the corresponding message is delivered on the destination chain (either another `WrappedHyperFungibleToken.onAccept` releasing underlying tokens, or `HyperFungibleToken.onAccept` minting native wrapped supply), the destination credits `message.amount` in full — more than what is actually locked in custody on the source chain.

This is the same root cause identified in the audit report: using the pre-transfer requested amount instead of the balance-difference-derived actual amount for downstream accounting. Notably, the codebase's own `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol:319-323`) explicitly guards against this by measuring `balanceOf` before and after `safeTransferFrom` and using the delta for escrow/commitment — confirming the team is aware of and mitigates this exact bug class elsewhere, but the fix was not applied to `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`. ### Impact Explanation
Each cross-chain leg for a fee-on-transfer underlying causes the destination chain to credit more value (`message.amount`) than what is actually escrowed/locked on the source chain (`received amount < params.amount`). Since `WrappedHyperFungibleToken` releases from a shared custody pool of the underlying token on redeem, and `HyperFungibleToken` mints new supply 1:1 with the message amount, repeated calls progressively drain the custody reserve / mint unbacked supply, permanently under-collateralizing the bridge and allowing attackers (or unaware normal users bridging a deflationary token) to redeem more value than was deposited. This is an unbacked mint / permanent value leak, meeting the Medium-to-High bar (concrete theft/freezing of funds via unbacked mint).

### Likelihood Explanation
Any unprivileged caller can invoke `send()` with an arbitrary `_underlying` configured by the token deployer (this depends on whichever ERC20 is set as `_underlying` for the wrapper). If the owner configures a wrapper for a fee-on-transfer, deflationary, or rebasing token — which is common among widely-used ERC20s — every single `send()` call using the non-native path silently mis-mints on the destination. No special conditions or governance compromise are required beyond an already-supported token being fee-on-transfer; this is a standard ERC20 integration hazard the codebase already defends against elsewhere (`IntentGatewayV2`), confirming it is a realistic, reachable scenario.

### Recommendation
In `WrappedHyperFungibleToken.send()` and `WrappedHyperFungibleTokenUpgradeable.send()`, measure the underlying token balance before and after `safeTransferFrom`, and use the delta (actual received amount) both for the custody accounting and for the `Message.amount` encoded in the dispatched request — mirroring the pattern already used in `IntentGatewayV2.placeOrder` (`balBefore`/`balanceOf` diff). Alternatively, explicitly document/enforce that only strictly-conforming, non-fee-on-transfer/non-rebasing ERC20s may be configured as `_underlying`, and add a runtime check that reverts if the received amount differs from `params.amount`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` (or the Upgradeable variant) configured with `_underlying` set to a fee-on-transfer ERC20 (e.g., 1% fee).
2. Deploy a peer `WrappedHyperFungibleToken`/`HyperFungibleToken` on a destination chain, funded with some underlying reserve for redemptions.
3. Caller approves `params.amount = 1000` tokens and calls `send({dest, to, amount: 1000, timeout, relayerFee, data})`.
4. `safeTransferFrom` transfers 1000 requested, but due to the 1% fee only 990 lands in the wrapper contract's balance (`_underlying.balanceOf(address(this))` increases by only 990).
5. `_buildDispatchPost` still encodes `Message.amount = 1000` and dispatches the ISMP POST request.
6. On the destination chain, `onAccept` decodes `message.amount = 1000` and unlocks/mints 1000 tokens to the beneficiary — 10 tokens more than what was actually escrowed on the source chain.
7. Repeating this process continuously drains the underlying custody balance / inflates unbacked supply on the destination chain.
