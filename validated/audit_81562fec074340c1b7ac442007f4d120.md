## Title
Missing zero-address validation on cross-chain recipient permanently burns bridged native ETH in `WrappedHyperFungibleToken.onAccept` - (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` lets any caller specify an arbitrary destination-chain recipient (`params.to`) with no validation. On delivery, `onAccept` decodes this attacker/user-controlled 20 bytes into `beneficiary` via `_toAddr`, which only checks the byte length (`== 20`) and never rejects the all-zero address. When the wrapped underlying is WETH (`_isWeth == true`), the contract withdraws native ETH and pushes it with a raw `.call{value: ...}("")` to `beneficiary`. A low-level call to `address(0)` (no code) always succeeds, so the ETH is silently and irrecoverably sent to the zero address instead of reverting or falling back to the WETH-transfer safety path.

### Finding Description
`send()` locks/escrows the underlying token (or wraps native ETH into WETH) on the source chain and dispatches an ISMP POST whose body encodes `to: params.to` exactly as supplied by the caller: [1](#0-0) 

On the destination chain, `onAccept` extracts the beneficiary purely by byte-length and never checks for the zero address: [2](#0-1) 

For WETH-wrapped assets, the withdrawn ETH is pushed with a raw call. `address(0).call{value: amount}("")` returns `(true, "")` because there is no code to execute at the zero address, so the `!sent` fallback (which would otherwise re-wrap into WETH and use `safeTransfer`, which does revert on zero-address recipients for OZ tokens) is never triggered: [3](#0-2) 

Because the raw call "succeeds," `onAccept` completes normally, the ISMP request is marked delivered, and no timeout/refund path is ever triggered — the funds are gone permanently. This is the direct analog of the reported `mintForToken()` issue: an unvalidated destination address lets a legitimate cross-chain transfer permanently destroy value instead of reverting or refunding.

### Impact Explanation
Any account that calls `send()` (or is instructed to via a compromised/careless integrator, front end, or `data`-driven composable call routing tokens to `CallDispatcher`/zero) with `to = address(0)` — whether by mistake or via a bug in an integrating contract — causes real native ETH, already escrowed on the source chain, to be sent into the unrecoverable zero-address sink on the destination chain once delivered. This is a genuine, unbacked loss of funds with no recovery mechanism (the message is recorded as successfully delivered, so `onPostRequestTimeout` never fires). This satisfies the "concrete... permanent freezing of funds" criterion.

### Likelihood Explanation
Reaching this path requires only a single permissionless `send()` call with an easily-constructed `to` value (20 zero bytes) and requires the wrapped asset to be configured as WETH (`_isWeth == true`), which is a supported, documented configuration for native-ETH bridging. No privileged role, governance, or malicious relayer/collator is needed — the relayer/host merely delivers the already-signed message as designed.

### Recommendation
Validate `beneficiary != address(0)` (and `refundee != address(0)`) in `_toAddr` or immediately after decoding in both `onAccept` and `onPostRequestTimeout` of `WrappedHyperFungibleToken` (and its upgradeable counterpart, `WrappedHyperFungibleTokenUpgradeable.sol`, which shares the same logic), reverting rather than allowing the raw ETH push to silently succeed against the zero address.

### Proof of Concept
1. Configure `WrappedHyperFungibleToken` with `_isWeth = true` and register a valid peer chain.
2. Caller invokes `send(SendParams({ dest: validChain, to: abi.encodePacked(address(0)), amount: X, ... }))`, locking `X` worth of ETH (wrapped as WETH) in the contract.
3. A relayer delivers the POST request on the destination chain; `onAccept` decodes `beneficiary = address(0)`, calls `IWETH(_underlying).withdraw(X)`, then `address(0).call{value: X}("")`, which returns `sent == true`.
4. `onAccept` completes without reverting, emitting `Received` — `X` ETH is now permanently stuck at `address(0)` with no refund path, since the request is considered successfully delivered.

    /// @notice Extracts an address from the first 20 bytes of a bytes memory value
    function _toAddr(bytes memory b) internal pure returns (address addr) {
        if (b.length != 20) revert InvalidAddress(b.length);
        // casting to 'bytes20' is safe because we already checked length
        // forge-lint: disable-next-line(unsafe-typecast)
        return address(bytes20(b));
