### Title
Webhook `shop` (tenant identity) header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the unrelated `shop-domain` header as the tenant identity that is handed to the app's webhook handler. Because the HMAC signature and the tenant-identifying field are not cryptographically bound together, an attacker who can obtain one valid `(raw_body, hmac)` pair (e.g., from webhooks legitimately delivered by Shopify for a shop the attacker controls/owns) can resubmit that same body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, causing the payload to be processed under a different (victim) tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts several fields from HTTP headers, including the tenant-identifying `shop` value: [1](#0-0) 

But the value returned by `to_signable_string`, which is what actually gets HMAC-verified, is only the raw body: [2](#0-1) 

`Registry.process` verifies only this body-based HMAC before forwarding the request (including the header-derived, unauthenticated `shop`) to the registered handler: [3](#0-2) 

`Utils::HmacValidator.validate` in turn only ever checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [4](#0-3) 

The identity binding that should hold is: `shop used to authorize/process the webhook == shop cryptographically covered by the HMAC`. In this gem, that equality does not hold — the HMAC only proves knowledge of `api_secret_key` over the body bytes, not over the `shop-domain` header. Since `api_secret_key` is a single shared secret for the whole app (not shop-specific), any request whose body+HMAC pair was legitimately produced by Shopify for *any* installed shop (including a shop the attacker owns) will pass validation regardless of which `shop-domain` header value is attached to the request.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce: `Registry.process` calls the app's handler with `WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...)`, and the `shop` value is the only tenant discriminator the handler receives. A forged `shop-domain` header lets an attacker who possesses one valid signed body (from a shop they control) impersonate a different shop to the handler, i.e., cross-tenant access/injection of attacker-controlled webhook data into a victim shop's processing path. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to already possess at least one legitimately-signed `(raw_body, hmac)` pair, most plausibly from webhooks delivered for a shop the attacker owns/controls (a realistic condition for any public app, since anyone can install it on their own store and receive valid webhook deliveries). No access to `api_secret_key` itself is needed — only reuse of a previously observed valid signature with a different `shop-domain` header on a direct POST to the app's public webhook endpoint.

### Recommendation
Bind the tenant/shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed payload (e.g., include the header in the signable string, or require the caller to independently confirm the `shop` is one for which a session actually exists and was established via a previously verified OAuth/token-exchange flow) before passing `WebhookMetadata` to a handler. At minimum, document that `request.shop` is unauthenticated and must not be used as the sole tenant key without additional verification (e.g., checking it against shops with an active, stored session).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), which Shopify delivers to the app's public webhook URL with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this `(B, hmac)` pair (they own the shop and can inspect what is sent, e.g. by proxying their own store's traffic to a logging endpoint before forwarding, or by controlling a dev-store integration).
3. Attacker sends a new POST directly to the app's public webhook endpoint with the same body `B` and same `hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, `Utils::HmacValidator.validate` succeeds (it only checks `B` against `hmac`), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, as shown in [3](#0-2)  and [5](#0-4) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
