### Title
Unvalidated `from` field in `DispatchPost`/`DispatchGet` lets any pallet or extrinsic caller impersonate another module's identity - (File: modules/ismp/core/src/dispatcher.rs)

### Summary
The `IsmpDispatcher::dispatch_request` interface accepts a caller-supplied `from: Vec<u8>` field on `DispatchPost`/`DispatchGet` with no validation that it corresponds to the calling pallet, account, or contract's actual module identity [1](#0-0) . This is directly analogous to the Discourse CVE-2023-45147 bug class: an unprivileged actor can attach an arbitrary "custom field" (here, the `from` module identifier) to a protocol object, and downstream consumers that trust this field for authorization/accounting are exposed depending on what "plugins" (in Hyperbridge's case, pallets/routers) key their logic off it.

### Finding Description
`pallet-ismp`'s `dispatch_request` implementation forwards `dispatch_post.from` / `dispatch_get.from` verbatim into the constructed `PostRequest`/`GetRequest` without any check that it matches the identity of the pallet or account that invoked it [2](#0-1) . Any pallet on the runtime — including one exposing a signed, permissionless extrinsic — can call `IsmpDispatcher::dispatch_request` and set `from` to an arbitrary module id, e.g. another pallet's well-known `PALLET_ID` or a hyperbridge system module id such as the host-executive or token-governor ids.

This `from` field is subsequently trusted for security-relevant decisions in multiple places:
- The new outbound-request relayer-reward allowlist keys reward payout eligibility directly by `request.from` with no additional check that the request truly originated from that module's logic: `let module_id: BoundedVec<u8, ModuleIdBound> = request.from...; let reward = OutboundRequestDeliveryReward::<T>::get(&module_id);` [3](#0-2) . The documentation for this feature explicitly states "the relayer never gets to claim under a different module identifier than the one the request was actually dispatched with" — but this guarantee only holds if the *dispatch site* itself cannot forge `from`, which it can [4](#0-3) .
- Bandwidth accounting is billed against `request.from` as the paying module: `try_consume(&request.source, &request.from, bytes)` [5](#0-4) .
- Timeout routing on the destination-turned-source chain dispatches back to whichever pallet's callback matches `request.from`/`post.from`, e.g. `pallet_hyper_fungible_token::PALLET_ID => ...on_timeout(timeout)` [6](#0-5) .
- Deprecated-TokenGateway blocking is enforced by string-matching `request.from` [7](#0-6) .

Because `from` is not bound to the calling extrinsic origin or pallet identity at the dispatch entrypoint, any permissionless pallet call path that ultimately routes into `Pallet::<T>::dispatch_request` (or any custom pallet built against this trait, as the demo pallet illustrates by freely setting `from: PALLET_ID.to_bytes()`) can spoof the module id of a privileged system module [8](#0-7) .

### Impact Explanation
If any signed-extrinsic-reachable pallet on a Hyperbridge parachain forwards user-controlled `from` bytes into `IsmpDispatcher::dispatch_request` (a pattern the demo pallet and documentation both show as the intended usage), an attacker could:
1. Impersonate a reward-eligible system module (e.g. host-executive, token-governor, or the relayer withdrawal path) to make their own low-value spam requests eligible for the `OutboundRequestDeliveryReward` treasury payout, causing unbacked draining of the treasury PalletId account.
2. Bill their bandwidth consumption against another module's `from` id, freezing or disrupting service for the legitimate module (denial of bandwidth / accounting corruption).
3. Bypass or trigger destination-side timeout/response routing intended for a different pallet, potentially causing state corruption in that pallet's `on_timeout`/`on_response` handlers.

This maps to concrete theft of funds (treasury reward draining) and unauthorized app action (spoofed module routing), which fits the Medium/High severity bar. The actual blast radius depends on which concrete pallets in a given runtime expose `dispatch_request` behind a permissionless extrinsic without independently binding `from` to the caller — this could not be fully confirmed for every production runtime pallet within the scope of this review, since only the low-level trait and the demo pallet's unrestricted usage were directly inspected.

### Likelihood Explanation
The core dispatcher primitive (`modules/ismp/core/src/dispatcher.rs`, `modules/pallets/ismp/src/dispatcher.rs`) performs no validation of `from` and this is by design a low-level, "trust the caller" API intended to be wrapped by higher-level pallets that are expected to set `from` correctly themselves. Likelihood therefore hinges on whether any production pallet's public extrinsic passes a caller-influenced `from` through unchecked; the demo pallet (and the docs' example `pallet_example`) hardcode their own module id, which is safe, but the pattern is fragile — the security invariant is enforced only by pallet-author discipline, not by the framework, exactly mirroring the "topic custom fields are only dangerous depending on what the plugin does with them" caveat in the original Discourse advisory.

### Recommendation
Enforce that `from` cannot be freely chosen by dispatch callers: bind the dispatcher's accepted `from` to a value derived from the calling pallet's `PalletId`/origin at the trait boundary (e.g., require callers to implement a trait that returns their own fixed module id, or have `dispatch_request` accept an opaque caller-context type instead of raw bytes) rather than trusting `DispatchPost.from`/`DispatchGet.from` verbatim. At minimum, any downstream consumer that keys security-relevant logic off `request.from` (reward allowlists, bandwidth billing, deprecated-module blocklists) should independently re-derive or attest the true sender rather than trusting the wire-level `from` field alone.

### Proof of Concept
Conceptual PoC (not runnable without a full runtime, since the vulnerable surface is the shared `IsmpDispatcher` trait rather than a single fixed extrinsic):
1. Deploy/identify a permissionless pallet extrinsic on a Hyperbridge parachain that accepts user-supplied bytes and forwards them as `DispatchPost.from` into `T::IsmpDispatcher::dispatch_request` (the pattern shown in `modules/pallets/demo/src/lib.rs::dispatch_to_evm` and `docs/content/developers/polkadot/dispatching.mdx`, if such an extrinsic exists without hardcoding its own `from`).
2. Governance sets `OutboundRequestDeliveryReward[module_id]` for a legitimate system module id such as `b"ismp-ast"` (as in the documented example) [9](#0-8) .
3. Attacker calls the permissionless extrinsic with `from = b"ismp-ast"`, dispatching a cheap request that reaches the destination.
4. Attacker (or colluding relayer) submits `claim_outbound_request_delivery_reward` with the forged request; `process_outbound_request_delivery_claim` only checks `request.source`, replay, and `request.from`'s presence in the reward map — none of which detect the impersonation — and pays out the treasury reward [10](#0-9) .
