## Title
Webhook tenant identity (`shop-domain`) not bound by HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (tenant identifier) is read from the `X-Shopify-Shop-Domain` HTTP header, a field that is never included in the signed bytes. `Registry.process` trusts `request.shop` as the tenant key when dispatching to the host application's webhook handler, so the value verified by the HMAC (`raw_body`) and the value acted upon as the tenant identity (`shop` header) are not the same bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is derived independently from a header, outside of that signed string: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string`, i.e., the raw body, never touching the shop header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately uses `request.shop` as the trusted tenant key handed to the host application's handler: [4](#0-3) 

Since a single Shopify app has one shared `client_secret` used to HMAC-sign webhook deliveries to *every* installing shop, any shop that has installed the app (an unprivileged, non-credentialed party relative to other tenants) legitimately receives `(raw_body, hmac)` pairs for its own webhooks. Because `shop` is excluded from the signed bytes, that same valid `(raw_body, hmac)` pair remains valid when replayed with the `X-Shopify-Shop-Domain` header changed to any other shop's domain. `HmacValidator.validate` still returns `true` (it only checks `raw_body`), and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata`, which the host application uses to attribute/process the payload for that tenant.

This breaks the intended binding:
`shop_value_verified_by_hmac == shop_value_used_as_tenant_key`
Here, the left side is undefined (no shop is bound by the signature at all), while the right side is fully attacker-controlled via an unsigned header, for any request whose `raw_body`+`hmac` pair the attacker can obtain from a genuine delivery to their own shop.

### Impact Explanation
This is a cross-tenant confusion: an attacker who is a legitimate installer of the app for their own shop can cause the library to report to the host application that a webhook payload belongs to a different, victim shop, while presenting a validly-signed request. Any host logic that trusts `WebhookMetadata#shop` for tenant-scoped data writes, deduplication, redaction (e.g., GDPR `shop/redact`), or access decisions can be poisoned across tenant boundaries without possessing the victim's credentials, access token, or the app's `client_secret`. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is realistic but requires one precondition: the attacker must be able to observe a real webhook delivery (raw body + `X-Shopify-Hmac-Sha256`) sent to their own shop's endpoint — trivial for anyone who installs the app and controls (or proxies) their own callback URL. No secrets, access tokens, or privileged accounts are needed; only replay of an unsigned header value.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) into the HMAC-signed material, or otherwise cryptographically bind the header values to the signed body (e.g., include them in `to_signable_string`, or require the caller to independently verify that the `shop` header matches an expected/registered shop before trusting `WebhookMetadata#shop`). At minimum, document that `request.shop` is unauthenticated and must not be used as a sole tenant-scoping key without additional verification.

### Proof of Concept
1. Attacker installs the target app for `attacker-shop.myshopify.com` and configures/observes the webhook endpoint traffic (e.g., via a debugging proxy) to capture a legitimate delivery: `raw_body`, and header `X-Shopify-Hmac-Sha256: <hmac>`.
2. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` — the forged `shop` header is never checked: `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` builds `WebhookMetadata.new(..., shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and forwards it to the host app's `handler.handle`, causing the payload (originally the attacker's own shop's data) to be processed/attributed under the victim shop's identity: `lib/shopify_api/webhooks/registry.rb:198-199`.
