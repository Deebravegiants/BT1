Confirmed vulnerability found: `fillOrder()` at `evm/src/apps/IntentGatewayV2.sol:443-472` authorizes only the *solver address*, not the specific output amounts the solver publicly bid, allowing a bait-and-switch analogous to the Berachef "queue then swap" report.

### Title
Solver selection authorizes only the solver address, not the bid content, permitting a bait-and-switch redirection of intent output amounts - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
Analogous to the Berachef bug, where a validator could publicly advertise a favorable cutting-board configuration to attract stakes and then substitute a different configuration right before activation, Hyperbridge's intent solver-selection flow lets a solver publicly advertise an attractive bid (output amounts) to win the user's off-chain selection, then substitute a different, less favorable `fillOrder` call at execution time — because the on-chain authorization commits only to the solver's address, not to the bid's content.

### Finding Description
The intent flow is: a solver posts a `PackedUserOperation` bid containing specific output amounts via `fillOrder` calldata, signed with a standard 65-byte ECDSA signature over `userOpHash` (docs: `docs/content/developers/evm/intent-gateway/overview.mdx:132`). The user reviews the bid's advertised amounts off-chain and authorizes the winning solver by signing an EIP-712 `SolverSelection{commitment, solver}` message with the session key [1](#0-0) . Critically, this struct commits only to the order `commitment` and the `solver` **address** — not to the output amounts or any other content of the specific bid the user reviewed.

On-chain, `_select()` recovers the session key from this signature and stores `keccak256(abi.encode(options.solver, sessionKey))` in transient storage [2](#0-1) . Then `fillOrder()` checks only that this stored hash matches `keccak256(abi.encode(msg.sender, order.session))` [3](#0-2)  — again binding only the caller's address and session, with **no binding to the `FillOptions.outputs` amounts** that were actually authorized.

Because `select()` and `fillOrder()` are separate calls (bundled only by convention inside the same `SolverAccount` UserOperation), and because the authorization hash carries no commitment to fill amounts, a selected solver can call `fillOrder()` with `FillOptions.outputs` that differ arbitrarily from the amounts in the bid the user reviewed and approved — as long as they satisfy the loose array-length checks at `evm/src/apps/IntentGatewayV2.sol:474-476`. There is no on-chain floor tying the delivered outputs to the previously "queued"/advertised bid, mirroring the Berachef flaw where the activation of a favorable configuration could be silently swapped for a different one after third parties had already committed based on the public promise.

### Impact Explanation
A solver can advertise an attractive bid to win user selection (analogous to attracting BGT stakes with a favorable cutting board), then deliver a worse output amount at fill time — directly reducing the user's expected proceeds. Since `fillOrder` performs the token transfer/settlement based on `FillOptions.outputs` supplied at call time rather than the bid amounts the session signature was based on, this is a concrete theft/value-extraction vector against the user, reachable by any unprivileged solver with a valid selection signature. This is a Medium-severity issue, consistent with the original report's severity rating.

### Likelihood Explanation
Any solver participating in the public auction can exploit this without needing any privileged role — solvers are, by design, unprivileged and permissionless participants who compete for orders. The attack requires only that a solver be selected, then submit a `fillOrder` call with a different, still-valid-shaped `FillOptions.outputs` array (same array length as `order.output.assets`) but with worse values, or values satisfying only the protocol's minimum enforcement (if any) rather than the amounts advertised in the winning bid. Whether protocol-level surplus/slippage checks elsewhere in `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` constrain this further could not be fully verified within the scope of this investigation — the exact fill-amount validation logic in `_fillSameChain`/`_fillCrossChain` was not retrieved, so it is uncertain whether any minimum-output enforcement partially mitigates this. This should be verified against those functions before concluding definitive exploitability.

### Recommendation
Bind the `SolverSelection` EIP-712 message (and the transient-storage authorization hash) to a commitment of the specific `FillOptions` (output token amounts, fees) the user reviewed and approved — not merely to the solver's address. For example, include a hash of the bid's `FillOptions` in the `SolverSelection` struct and re-derive/verify that hash in `fillOrder()` against the actual `options` argument, so a solver cannot substitute different output amounts after being selected.

### Proof of Concept
1. Solver posts a bid `UserOperation` with `fillOrder(order, FillOptions{outputs: [1000 DAI]})`, signed over `userOpHash`.
2. User reviews the bid off-chain, is satisfied with 1000 DAI, and signs `SolverSelection{commitment, solver}` with the session key — note this signs nothing about the 1000 DAI amount.
3. Solver calls `select()` with this signature, staging `keccak256(abi.encode(solver, sessionKey))` in transient storage [2](#0-1) .
4. In the same or a subsequent call within the same transaction, the solver calls `fillOrder(order, FillOptions{outputs: [500 DAI]})` instead. The check at `evm/src/apps/IntentGatewayV2.sol:464-472` only verifies `msg.sender`/`order.session` match — it passes regardless of the output amount — so the fill succeeds with half the advertised value [4](#0-3) .

    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();
