### Title
Excess native-token overpayment is never refunded in `EvmHost.dispatch()`/`fundRequest()` due to a swallowed `swapETHForExactTokens` return value and a meaningless `block.timestamp` deadline - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` allow any unprivileged caller to pay the protocol's relayer fee in native token by sending `msg.value`, which is then swapped for `feeToken` via `swapETHForExactTokens`. Unlike the analogous fee-swap logic in `IntentGatewayV2.placeOrder()`, which captures the router's returned `amounts[0]` and refunds any unspent native token to the caller, `EvmHost`'s three dispatch/fund entry points discard the router's return value entirely and never refund leftover ETH. Combined with hard-coding `block.timestamp` as the swap deadline (a well-known Uniswap anti-pattern that provides no real "late execution" protection), this is the same missing-slippage/missing-deadline bug class as the reported DODO issue, but here it manifests as concrete, permanent loss of user funds rather than just price risk.

### Finding Description
In `evm/src/core/EvmHost.sol`, `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` each contain: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three functions, `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` is called with the *entire* `msg.value` as the max input and `fee` as the exact output. `swapETHForExactTokens` refunds any unspent ETH to the caller of the router — which is `EvmHost` itself, not the original transaction sender. None of these three functions capture the returned `amounts` array or forward any leftover ETH back to `msg.sender`.

This is directly comparable to `IntentGatewayV2.placeOrder()`, which performs the identical swap pattern but correctly tracks the unspent input and refunds it: [4](#0-3) 

Additionally, all of these swaps use `block.timestamp` as the Uniswap deadline parameter, which is evaluated at execution time and therefore never actually expires — this is the same "no late execution protection" defect flagged in the reported DODO issue, since a relayer/miner can hold the transaction and it will still be considered "on time" whenever it is eventually mined, well past the price the caller expected when computing `msg.value`.

Because `msg.value` for these fee-token swaps is normally computed off-chain via `quoteNative`/`getAmountsIn` for a target fee, any user whose transaction is delayed, or who intentionally/unintentionally overestimates the required native amount, will have the surplus ETH permanently trapped inside `EvmHost` with no code path to reclaim it (no sweep/withdraw function was found for arbitrary native balance in `EvmHost`).

### Impact Explanation
Every unprivileged application/user that dispatches a POST or GET request, or funds an in-flight request, by paying with native token (a documented, encouraged payment path) risks having any overpayment permanently frozen in the `EvmHost` contract. This is a direct, concrete freezing-of-funds vulnerability reachable from a single call to a core, publicly documented dispatch entry point used throughout the protocol (including third-party integrators building `HyperApp`s), not a privileged or governance-only path.

### Likelihood Explanation
Likelihood is high: `msg.value` is virtually always an estimate (computed off-chain via `quoteNative`, which itself is a Uniswap-based estimate documented to be "subject to slippage"), so exact equality between `msg.value` and the swap's actual required input is unlikely in normal operation. Every dispatch/fundRequest call paid in native token that overshoots the required input amount by even 1 wei loses that surplus. The bug requires no attacker action — it triggers under ordinary use, and is worsened by the meaningless `block.timestamp` deadline, which allows delayed execution to increase the divergence between the estimated and actual required input.

### Recommendation
Capture the array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder()`. Additionally, replace the `block.timestamp` deadline argument with a caller-supplied deadline parameter so the swap can actually expire if not mined promptly, consistent with the "late execution protection" recommendation from the original report.

### Proof of Concept
1. Off-chain, a `HyperApp` estimates `nativeCost` for a `DispatchPost` via `quoteNative`, adding a buffer (as documented in `docs/content/developers/evm/messaging/get-requests.mdx` and `post-requests.mdx`), then calls `EvmHost.dispatch{value: nativeCost}(post)`.
2. Inside `dispatch`, `swapETHForExactTokens{value: nativeCost}(post.fee, path, address(this), block.timestamp)` executes; because the estimate included a buffer (or the pool price improved since estimation), the router only consumes `amounts[0] < nativeCost` and refunds `nativeCost - amounts[0]` ETH to `address(this)` (i.e., `EvmHost`).
3. `dispatch()` returns without ever checking `amounts` or transferring the difference back to the caller.
4. The surplus ETH accumulates in `EvmHost` with no corresponding accounting or withdrawal path exposed to the original payer, permanently locking those funds. [1](#0-0)
