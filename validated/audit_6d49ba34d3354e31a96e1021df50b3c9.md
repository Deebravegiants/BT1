Based on the code analysis, I found a concrete identity-binding break in the webhook verification path.

### Title
Webhook `shop-domain` header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by computing an HMAC over the raw request body only, while the `shop` (tenant identity) is read from an unauthenticated header that is never part of the signed bytes. An attacker who can obtain any single valid `(raw_body, hmac)` pair signed with the app's `client_secret` (trivially available to them by installing the app on their own, attacker-controlled shop) can replay that exact body/HMAC pair to the victim app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` will report the request as valid because it only checks `to_signable_string` (the raw body), never the shop header, so the forged request is processed by the app's webhook handler as if it originated from the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` and compares it against the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` only calls `HmacValidator.validate(request)` before dispatching to the handler with `request.shop` taken verbatim from the unauthenticated header: [4](#0-3) 

This breaks the identity binding: `hmac(secret, raw_body) == valid` should imply `shop == the tenant that generated raw_body`, but the code allows `shop` to be substituted independently of the signed bytes, since `shop ∉ to_signable_string`. Because a single Shopify Partner `client_secret` is shared across every shop that installs the app, an attacker can legitimately install the target app on a shop they control, capture a validly-signed webhook (e.g., `app/uninstalled`, `shop/redact`, or any other subscribed topic) with its correct `raw_body` and `hmac`, and replay that exact pair against the same app's webhook endpoint with the `shop-domain` header rewritten to a victim `myshopify.com` domain. The signature still validates because it only covers `raw_body`.

### Impact Explanation
This is a cross-tenant authentication/identity bypass: the app's webhook handler will process attacker-supplied (but validly-signed-by-secret) events under the label of a shop the attacker does not control. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to key merchant records, revoke sessions, purge data on `app/uninstalled`, or execute `customers/redact`/`shop/redact` compliance flows), this allows an attacker to trigger tenant-scoped side effects (data deletion, session invalidation, redaction) for a shop they don't own, purely by controlling the header on an otherwise-legitimate signed payload. This matches the "cross-tenant access" critical-impact category since the gem's own verification logic fails to bind the claimed tenant to the signed bytes.

### Likelihood Explanation
The prerequisite — installing the target app on an attacker-controlled development/trial shop to obtain one legitimately-signed webhook — is realistic for any public or semi-public app, since Shopify app installation by any merchant (including the attacker themselves) is unprivileged from the gem's perspective. No access token, leaked secret, or privileged account is required; only receipt of one webhook delivery for a topic the attacker's own shop can trigger (e.g. `app/uninstalled` by uninstalling their own test install). The replay itself is a simple HTTP POST with a modified header, so likelihood is moderate-to-high for apps that rely on the shop header for tenant-critical processing.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable content, or otherwise cryptographically bind the shop identity to the signed payload before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document that consumers must not treat the `shop-domain` header as authenticated on its own and must cross-check it against a known/expected shop (e.g., an active session) before performing tenant-scoped side effects.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com` and configure/trigger a subscribed webhook topic (e.g. uninstall the app to receive `app/uninstalled`).
2. Capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` Shopify sent for that delivery — both are valid because `H = HMAC-SHA256(client_secret, B)`.
3. Replay the request to the target application's webhook endpoint, keeping body `B` and header `H` unchanged, but replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (== `B`) and finds it matches `H`, so validation succeeds: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload and signature were generated by the attacker's own shop, demonstrating the identity/tenant binding failure.
