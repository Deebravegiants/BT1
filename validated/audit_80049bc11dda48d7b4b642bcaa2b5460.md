### Title
Webhook `shop`, `topic`, and `webhook_id` metadata are not covered by HMAC verification, allowing cross-tenant webhook spoofing via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but `Registry.process` only HMAC-verifies the request body (`to_signable_string` returns `@raw_body` only). An unprivileged attacker who can obtain one valid `(body, hmac)` pair for any webhook delivery (e.g. by installing the app on their own store and triggering a webhook whose body they control) can replay that exact body/HMAC pair while forging the `shop-domain`, `topic`, and `webhook_id` headers. `Registry.process` will accept the request as valid and dispatch attacker-controlled body content to any registered handler under an arbitrary spoofed `shop` and `topic`, breaking the binding that the metadata used to route/attribute a webhook actually corresponds to the HMAC-authenticated payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, which in turn calls `to_signable_string` (body-only) per the `VerifiableQuery` interface: [3](#0-2) [4](#0-3) 

After the HMAC check passes, the (unauthenticated) `topic`, `shop`, `webhook_id`, and `api_version` are handed directly to the registered handler as trusted metadata: [5](#0-4) 

The binding that should hold is: `hmac_valid(raw_body) ⇒ (shop, topic, webhook_id) are exactly what Shopify sent for that body`. In reality the library only proves `hmac_valid(raw_body)`; the routing/attribution fields are unauthenticated bytes parsed from headers, so the equality `verified_bytes == acted_on_fields` does not hold. Any unprivileged actor who can legitimately obtain one signed `(raw_body, hmac)` pair — for instance by installing the app on their own free development store and triggering a webhook whose body they can influence (e.g. a `products/update` payload with an attacker-chosen title/description) — can resend that exact body and HMAC to the app's webhook endpoint while substituting a victim's `shop-domain` header and/or a different `topic`/`webhook-id` header. `Registry.process` will still validate because the HMAC only covers `raw_body`, and it will dispatch the handler with the forged `shop`/`topic` metadata.

### Impact Explanation
This breaks the tenant isolation the webhook handler relies on: an app that keys off `data.shop` (e.g., to look up which merchant's session/access token to use, or to attribute the event to a specific tenant) can be made to process attacker-supplied body content as if it originated from an arbitrary victim shop, or to route the payload to a different webhook handler than the one Shopify actually signed it for by spoofing `topic`. This is a cross-tenant data/action confusion vulnerability reachable by any user capable of installing the app on their own store — no access token, `client_secret`, or victim credentials required.

### Likelihood Explanation
Requires only that the attacker can trigger at least one legitimate webhook delivery for their own store/install (a normal, unprivileged app-installation capability) and can then freely rewrite the `shop-domain`/`topic`/`webhook-id` headers when replaying that request to the target endpoint, since none of those headers are covered by the signature. This is a straightforward, low-effort replay once one valid `(body, hmac)` sample is captured.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other routing-relevant header) in the signed content used for HMAC verification, or otherwise cryptographically bind these header values to the authenticated body (e.g., require the app to independently confirm the `shop` against its own session store before trusting `data.shop`, and document this requirement clearly). At minimum, `Registry.process` should not treat header-derived `shop`/`topic` as verified simply because the raw body's HMAC checked out.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development store (unprivileged action) and triggers a webhook (e.g., `products/update`) whose body content they can shape (e.g., set the product title to arbitrary text). They capture the resulting `raw_body` and the `x-shopify-hmac-sha256` header Shopify computed for it.
2. Attacker sends a forged request to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: <different-topic>` and a fabricated `x-shopify-webhook-id`.
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` line 190) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` (`lib/shopify_api/webhooks/request.rb` lines 35-38).
4. The handler registered for the forged `topic` is invoked with `WebhookMetadata` carrying the attacker's `shop`/`topic`/`webhook_id` values (`lib/shopify_api/webhooks/registry.rb` lines 198-199), even though Shopify never actually signed or sent a webhook with that shop/topic combination.
