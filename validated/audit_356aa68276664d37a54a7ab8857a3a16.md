### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is permanently trapped in the contract instead of being refunded to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and swap it for an exact amount of fee token through UniswapV2. Any ETH left over from that swap is refunded by the router to whichever address called it — which is `EvmHost` itself, not the original transaction sender. The excess therefore becomes stranded in the `EvmHost` contract instead of returning to the user who paid it, unlike every other native-value-consuming entrypoint in this codebase (`IntentGatewayV2`, `ExtrinsicIntents`, `IntrinsicIntents`, `WrappedHyperFungibleToken`), which all explicitly forward unspent `msg.value` back to `msg.sender`.

### Finding Description
`dispatch(DispatchPost)` in [1](#0-0)  does:

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        address[] memory path = new address[](2);
        address uniswapV2 = _hostParams.uniswapV2;
        path[0] = IUniswapV2Router02(uniswapV2).WETH();
        path[1] = feeToken();
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
```

Standard `UniswapV2Router02.swapETHForExactTokens` refunds any unspent ETH via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. In this call chain, the router's `msg.sender` is `EvmHost` (the contract that made the call), not the EOA/contract that originally called `dispatch()`. Consequently, any overpayment beyond what's needed to purchase exactly `post.fee` worth of fee token lands back in `EvmHost`'s own native balance — it is never credited or forwarded to `_msgSender()`. There is no bookkeeping of this dust nor any withdrawal path that returns it to the original payer.

The identical pattern exists in `dispatch(DispatchGet)` at [2](#0-1)  and in `fundRequest()` at [3](#0-2) .

This is the exact bug class from the reported issue (native `msg.value` overpayment not refunded to the payer) — except here it doesn't revert; it silently confiscates the excess funds into the contract, which is a fund-loss variant of the same root cause. Contrast this with every application built on top of `EvmHost` that correctly tracks and refunds leftover `msg.value`, e.g. `ExtrinsicIntents._fillCrossChain` [4](#0-3) , `IntrinsicIntents` [5](#0-4) , `IntentGatewayV2.placeOrder` [6](#0-5) , and `WrappedHyperFungibleToken.send` [7](#0-6) . `EvmHost` is the only dispatch surface missing this refund step, despite being directly callable by any unprivileged message dispatcher/relayer/app.

### Impact Explanation
`dispatch()` and `fundRequest()` are `external payable` and callable by anyone (any app, relayer, or EOA) directly on `EvmHost` — they are the base primitive that `IDispatcher` consumers (including all the apps mentioned above) call into, and nothing stops a direct caller from sending excess `msg.value`. Any caller who slightly overestimates the ETH needed to cover `post.fee`/`get.fee`/`amount` permanently loses the difference — it accumulates as unaccounted ETH inside `EvmHost` with no accounting entry and no path to reclaim it. This is a permanent loss of user funds for any transaction where the exact fee-token price at execution time is lower than expected (e.g., due to price movement between quoting and execution, which is common since `quote()` estimates gas/price off-chain).

### Likelihood Explanation
High likelihood: overestimating `msg.value` for a swap-for-exact-tokens call is the normal/expected way callers pad for slippage, and every other native-value entrypoint in the same codebase treats this as the default case requiring a refund (see the extensive refund test suite for `IntentGatewayV2`). Any relayer or app dispatching a POST/GET request directly through `EvmHost.dispatch()` with native payment and any slippage buffer will trigger fund loss on every call.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute the actual ETH spent (`amounts[0]` returned by the swap) and refund `msg.value - amounts[0]` to `_msgSender()`, mirroring the refund pattern already used in `ExtrinsicIntents`/`IntrinsicIntents`/`IntentGatewayV2`.

### Proof of Concept
1. Attacker/relayer calls `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)`/`fundRequest`) with `msg.value` slightly greater than the ETH cost required to buy `post.fee` fee tokens via `swapETHForExactTokens`.
2. `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), ...)` executes; the router computes `amounts[0] < msg.value` and refunds `msg.value - amounts[0]` to its caller, which is `EvmHost`, via `TransferHelper.safeTransferETH(msg.sender, ...)`.
3. `EvmHost`'s native balance increases by the refund amount, but no state variable tracks this as belonging to the original `_msgSender()`, and the function returns without forwarding any ETH back to the caller.
4. The caller has permanently lost `msg.value - amounts[0]` in ETH with no recovery mechanism, while `EvmHost` retains it as an unaccounted native balance.
