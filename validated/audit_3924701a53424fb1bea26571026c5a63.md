## Analysis Result

**Custody invariant reduced from the external bug:** a migration function must not blindly overwrite state that was already authoritatively set by a privileged party in the "new" system, without first checking who holds/controls that state.

I evaluated several candidates (coin→FA migration frozen-flag sync, `resource_account::create_resource_account` front-run, `multisig_account::create_with_existing_account*`, `init.move` re-initialization gating). The strongest, independently-provable local analog is the frozen-flag reconciliation inside `coin::maybe_convert_to_fungible_store`.

### Title
Coin-to-Fungible-Asset migration allows unprivileged unfreeze of a primary fungible store - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`coin::maybe_convert_to_fungible_store` (invoked by the permissionless, self-callable entry functions `migrate_to_fungible_store` and `migrate_coin_store_to_fungible_store`) reconciles the legacy `CoinStore.frozen` flag with the new primary fungible store's frozen flag by simply overwriting the store's flag to match the CoinStore's flag whenever they differ, with no check of which side is authoritative.

### Finding Description
`maybe_convert_to_fungible_store` moves a legacy `CoinStore<CoinType>` out of the account and, if it holds a non-zero balance, deposits it into the (possibly pre-existing) primary fungible store: [1](#0-0) 

The critical lines are the frozen-flag sync: [2](#0-1) 

```move
// Note:
// It is possible the primary fungible store may already exist before this function call.
// In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
// function would convert and deposit the rest coin into the primary store and freeze it to make the
// `frozen` semantic as consistent as possible.
if (frozen != fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, frozen);
}
```

The code's own comment only documents the *safe* direction (CoinStore frozen → newly-frozen primary store). It does not document, and does not guard against, the opposite direction: if an issuer/compliance authority has already frozen the account's primary fungible store (e.g. via `primary_fungible_store::set_frozen_flag` using a `FreezeRef`, which is the standard mechanism used to block a flagged/sanctioned wallet), and the account still holds a legacy, unfrozen `CoinStore<CoinType>` with a nonzero balance, then calling `migrate_to_fungible_store` will set `frozen = false` on the primary store — **the migration silently reverses the issuer's freeze**. Since `migrate_to_fungible_store` is a `public entry fun` callable directly by the account owner (`account: &signer`) with no privilege requirement other than owning the account being migrated, any user whose primary store was frozen by an authority can trigger this call themselves to lift the freeze, as long as they still have any dust or balance in the pre-migration `CoinStore`.

This exactly mirrors the `FollowNFT.tryMigrate()` bug class: a migration path writes into shared/critical state introduced by the newer system without verifying the current authoritative value, letting an unprivileged actor corrupt that state (there: follower/graph state and counts; here: freeze/custody-control state).

### Impact Explanation
This breaks the freeze-control custody invariant: freeze state on a fungible asset primary store is supposed to be controlled exclusively by the holder of the asset's `FreezeRef`/`TransferRef` capability (e.g. a stablecoin issuer enforcing compliance blocks). The migration path lets the account owner — an unprivileged party with respect to freeze authority — unilaterally clear that freeze by exploiting a stale legacy `CoinStore`. For any regulated fungible asset relying on freeze semantics for custody/compliance enforcement (a live, mainnet-relevant control), this is a High-severity authority-bypass: it defeats the freeze mechanism that is the whole basis of that asset's custody control, allowing withdrawal/transfer of the affected balance after the improper unfreeze.

### Likelihood Explanation
Requires: (1) the target coin type has been paired with a fungible asset (`ensure_paired_metadata`), (2) the account's primary FA store was frozen by an authority while the account still has an un-migrated `CoinStore<CoinType>` with balance > 0, and (3) the account owner calls the permissionless `migrate_to_fungible_store`/`migrate_coin_store_to_fungible_store` entry function. Given that coin→FA migration is an ongoing, actively encouraged/automatic process across the ecosystem (see `migrate_coin_store_to_fungible_store` batch entry and `coin_migrate_to_fungible_store`), and freezing legacy-coin holders who haven't yet migrated is a realistic compliance scenario, likelihood is Medium-to-High for any asset still relying on `CoinType`/legacy CoinStore semantics alongside FA freeze enforcement.

### Recommendation
In `maybe_convert_to_fungible_store`, only ever tighten (freeze), never loosen (unfreeze), the primary store's flag as a side effect of migration, or better, remove the auto-sync entirely and require an explicit privileged call to reconcile frozen state:
```move
if (frozen && !fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, true);
}
```
This preserves the intended "freeze wins" one-directional consistency described in the surrounding comment, while eliminating the path where an unprivileged migration call clears an authority-set freeze.

### Proof of Concept
1. Asset issuer creates `CoinType`, pairs it with a fungible asset via `ensure_paired_metadata`.
2. User holds `CoinStore<CoinType>` with balance `X > 0`, unfrozen (`frozen = false`), and has not migrated.
3. Issuer/compliance authority calls (using its `FreezeRef`) `primary_fungible_store::set_frozen_flag(freeze_ref, user_addr, true)`, freezing the user's primary FA store for `CoinType`'s metadata (`ensure_primary_store_exists` creates the store if absent).
4. User calls `coin::migrate_to_fungible_store<CoinType>(&user_signer)` (a permissionless entry function).
5. Inside `maybe_convert_to_fungible_store`: `frozen` (from CoinStore) = `false`, `fungible_asset::is_frozen(store)` = `true` → mismatch → `fungible_asset::set_frozen_flag_internal(store, false)` is invoked, clearing the issuer's freeze.
6. User's primary fungible asset store is now unfrozen despite the issuer never having authorized this, and the user can freely transfer/withdraw the balance.

Note: I was not able to fully trace the exact call sites of `freeze_coin_store`/`unfreeze_coin_store` in `coin.move` or confirm every downstream consumer of `fungible_asset::set_frozen_flag_internal` within the available iterations; the core vulnerable logic and its unconditional bidirectional overwrite, however, is fully confirmed in `coin.move` lines 707–714 as cited above.

```text
    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.
                // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
                // function would convert and deposit the rest coin into the primary store and freeze it to make the
                // `frozen` semantic as consistent as possible.
                if (frozen != fungible_asset::is_frozen(store)) {
                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
            } else {
                destroy_zero(coin);
            };
            event::destroy_handle(deposit_events);
            event::destroy_handle(withdraw_events);
        };
    }
```
