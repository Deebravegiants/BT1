### Title
Deposit/Withdraw pnl-realization uses the pool's own manipulable spot reserve ratio as "current price" - (File: program/src/processor.rs)

### Summary
`Processor::calc_take_pnl`, invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl`, treats the *instantaneous* on-chain vault balances (`total_pc_without_take_pnl` / `total_coin_without_take_pnl`, derived directly from `amm_pc_vault.amount` and `amm_coin_vault.amount`) as the authoritative "current price" (`x1`/`y1`) used to decide how much accumulated fee-profit to realize into `need_take_pnl_pc`/`need_take_pnl_coin`, and this same instantaneous ratio is then used unmodified to compute LP mint/redeem exchange rates. This is the same root-cause class described in the Predy `slot0` finding: an unprotected spot price read from the AMM's own reserves is used to drive a state-changing calculation (there, `reallocate`; here, `calc_take_pnl` + LP mint/burn), and that spot price can be trivially manipulated by a swap executed immediately before the dependent call, all inside attacker-controlled transaction ordering.

### Finding Description
`calc_take_pnl` computes a "current price" purely from the AMM vault balances at call time: [1](#0-0)

`x1`/`y1` are computed right before the call as the normalized current vault balances: [2](#0-1) 

Inside `calc_take_pnl`, this "current price" `x1/y1` is combined with the last recorded reserve snapshot (`target.calc_pnl_x` / `target.calc_pnl_y`) to derive how the LP-fee surplus (the growth in constant-product `k`) is split between `pc` and `coin` and moved into `need_take_pnl_pc`/`need_take_pnl_coin`: [3](#0-2) 

This is invoked directly inside `process_deposit`: [4](#0-3) 
and inside `process_withdraw`: [5](#0-4) 

Because `x1`/`y1` are read from the live vault balances in the *same* instruction, and Solana transactions can bundle a swap instruction immediately before the Deposit/Withdraw instruction in a single atomic transaction, an attacker can:
1. Execute `SwapBaseIn`/`SwapBaseInV2` (an unprivileged, permissionless instruction) to shift the pool's `pc`/`coin` ratio to an extreme value.
2. Immediately call `Deposit` or `Withdraw` in the same transaction while the ratio is skewed, forcing `calc_take_pnl` to compute `delta_x`/`delta_y` at the manipulated ratio.
3. Reverse the swap (or let the attacker's own deposit/withdraw benefit from the skewed `InvariantPool`/`InvariantToken` exchange computed right after, since `total_pc_without_take_pnl`/`total_coin_without_take_pnl` are mutated by `calc_take_pnl` and then immediately reused for LP mint/burn math): [6](#0-5) [7](#0-6) 

This mirrors exactly the reported bug class: a permissionless instruction relies on a spot/instantaneous price derived from the pool's own state (there `slot0`, here the vault token balances) to gate a value-transfer calculation, and that price is trivially manipulable within a single attacker-controlled transaction.

### Impact Explanation
Skewing the ratio before Deposit/Withdraw distorts:
- How much of the accrued LP fee surplus is siloed into `need_take_pnl_pc`/`need_take_pnl_coin` versus left in `total_*_without_take_pnl` (which backs LP redemption value), and
- The exchange rate (`InvariantPool`/`InvariantToken`) at which the same transaction's depositor/withdrawer mints or burns LP tokens.

An attacker controlling both the preceding swap and the Deposit/Withdraw call can bias `delta_x`/`delta_y` and the subsequent `coin_amount`/`pc_amount` (withdraw) or `mint_lp_amount` (deposit) in their own favor, extracting value from remaining LPs or corrupting the pool's `need_take_pnl_*` bookkeeping, leading to LP-value dilution/insolvency over repeated exploitation. This is a fund-loss/insolvent-accounting issue for LPs, reachable by any unprivileged swapper/depositor.

### Likelihood Explanation
High reachability: `SwapBaseIn`/`SwapBaseInV2` and `Deposit`/`Withdraw` are all unprivileged, permissionless instructions reachable in one attacker-composed transaction with attacker-chosen amounts. No signer beyond the transaction owner is required, and repeated execution (each incurring only swap fees) compounds the effect, analogous to the "multiple re-allocations ... continuously drain the funds" escalation noted in the source report.

### Recommendation
Do not derive the pnl-realization "current price" solely from the instantaneous vault balances read in the same instruction as the state-changing swap. Consider snapshotting/averaging reserves over multiple slots (a TWAP-like mechanism), or decoupling `calc_take_pnl` invocation from being triggerable atomically alongside a same-transaction swap (e.g., disallow taking pnl within the same slot as a swap on the same pool, or use a delay/oracle check). Additionally, minting/burning LP amounts should not be computed from a ratio that was just mutated by an attacker-controlled preceding instruction within the same transaction.

### Proof of Concept
1. Attacker submits a single transaction containing: `SwapBaseIn` (large `amount_in` in one direction to skew `amm_pc_vault.amount`/`amm_coin_vault.amount`) → `Withdraw` (or `Deposit`) instruction for the same AMM.
2. `process_withdraw`/`process_deposit` reads the now-skewed vault balances via `calc_total_without_take_pnl_no_orderbook` [8](#0-7) , computes `x1`/`y1` from them, and calls `calc_take_pnl` with the manipulated ratio.
3. `calc_take_pnl`'s `delta_x`/`delta_y` split and the immediately following `InvariantPool::exchange_pool_to_token` computations [6](#0-5)  are computed at the skewed price, yielding a distorted `coin_amount`/`pc_amount` payout (or distorted `mint_lp_amount` on deposit) favorable to the attacker.
4. Attacker can reverse the swap in a follow-up transaction (or accept the swap fee cost as the price of manipulating the payout), repeating to extract value across multiple transactions.
