### Title
`IntentGatewayV2.instance()` Tron fallback lets a forged peer gateway drain any chain's escrow via `RedeemEscrow`/`RefundEscrow` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron build of `IntentGatewayV2` authenticates incoming cross-chain `RedeemEscrow`/`RefundEscrow` messages by comparing `request.from` against `instance(request.source)`. Unlike the mainline EVM implementation, which reverts with `UnknownInstance` when no peer has been registered for a state machine, the Tron `instance()` getter silently falls back to `address(this)` for any unregistered source chain. Because the gateway is designed to be deployed at the same address across chains, an attacker who controls (or can deploy identical bytecode/address on) any state machine that Hyperbridge routes messages for — but that has never been explicitly registered as a peer via `NewDeployment` — can dispatch a forged `RedeemEscrow`/`RefundEscrow` request whose `from` field equals that shared address, pass `authenticate()`, and drain escrowed tokens belonging to real orders on the target chain.

### Finding Description
`authenticate()` is the sole gate protecting `withdraw()` from arbitrary callers: [1](#0-0) 

```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```

`_instances` is only populated by a `NewDeployment` request that itself must originate from Hyperbridge governance: [2](#0-1) 

For any state machine that has *not* gone through `NewDeployment`, `instance()` returns `address(this)` rather than reverting. `authenticate()` then accepts a `RedeemEscrow`/`RefundEscrow` request whenever `request.from == address(this)`. This is trivially satisfiable: the contract is meant to be deployed at a deterministic address across chains (the SDK/tests treat `gateway.instance(...)` returning `address(gateway)` as the expected same-address peer pattern), so an attacker only needs to get a message legitimately routed through Hyperbridge's ISMP host from *any* state machine where a contract exists at that same address (which they can arrange via CREATE2 on a chain Hyperbridge already supports but the target gateway has never explicitly registered as a peer).

Once authenticated, `withdraw()` transfers tokens to an attacker-chosen `beneficiary` for any commitment that still has non-zero escrow: [3](#0-2) 

The only integrity check is `_orders[commitment][token] == 0` revert-on-zero — it does not verify that the withdrawal request actually originated from the genuine peer gateway tied to that order's declared `source`/`destination`. This mirrors the reported LiFi flaw: a value that should gate fund delivery (`_stargateData.callTo` vs. the checked `bridgeData.receiver`) is not the value actually enforced, so validation passes while funds are routed to an attacker.

### Impact Explanation
Any escrowed order on a chain running this Tron `IntentGatewayV2` can be redeemed to an attacker-controlled beneficiary by forging a `RedeemEscrow` or `RefundEscrow` message from an unregistered source chain whose module address collides with the gateway's own address. This is concrete theft of escrowed user funds (input tokens plus accrued transaction fees) with no privileged access required beyond routing a legitimately-proven ISMP message from a chain the attacker controls.

### Likelihood Explanation
Exploitability depends on (1) Hyperbridge's ISMP host actually permitting delivery of a POST request whose `source` is a state machine not registered as a peer of this specific gateway instance, and (2) the attacker being able to place a contract at the identical address as the real `IntentGatewayV2` on that source chain (straightforward via CREATE2, since deterministic-address deployment is the intended pattern for this contract family). Both conditions are plausible in a multi-chain deployment where new EVM chains are periodically onboarded to Hyperbridge before every existing app peer-registers them, making this a realistically reachable, not merely theoretical, path.

### Recommendation
Change `instance()` (or `authenticate()`) in `evm/tron/contracts/apps/IntentGatewayV2.sol` to revert (e.g., `UnknownInstance`) when `_instances[keccak256(stateMachineId)] == address(0)`, matching the mainline `IntentsBase._instance` behavior, instead of defaulting to `address(this)`. Never treat an unregistered chain as implicitly trusted.

### Proof of Concept
1. A user places a cross-chain order on chain A, escrowing tokens in `IntentGatewayV2` deployed at address `G` on chain B (destination).
2. Attacker deploys a contract via CREATE2 at address `G` on chain C, a state machine Hyperbridge already routes for but that chain B's gateway has never registered via `NewDeployment` (`_instances[keccak256("C")] == address(0)`).
3. From that contract on chain C, attacker dispatches an ISMP POST request to chain B's gateway with body `RedeemEscrow` + `WithdrawalRequest{commitment: <victim's real commitment>, tokens: <victim's escrowed tokens>, beneficiary: <attacker>}`.
4. Hyperbridge relays and proves this message is genuinely from chain C (real consensus proof — `request.source = "C"`, `request.from = G`).
5. On chain B, `onAccept` calls `authenticate(request)`: `instance("C")` returns `address(this) == G` (fallback), `module == G` (from field) → check passes.
6. `withdraw()` executes: `_orders[commitment][token] != 0` (the real escrow), so the attacker's `beneficiary` receives the victim's escrowed tokens and fees.
