### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-attribution spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct whose `shop` field is taken from an unauthenticated header. The equality the gem implicitly relies on — "the shop the signed payload was generated for" == "the shop attributed to the webhook by the handler" — is never enforced, because `shop` is not part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and then builds `WebhookMetadata` using `request.shop`, the unauthenticated header value, without ever checking it against anything derived from the signed payload: [3](#0-2) 

`WebhookMetadata#shop` is documented and used by consuming apps as the tenant identifier to key their per-shop logic (job dispatch, session lookup, data updates): [4](#0-3) [5](#0-4) 

Because the HMAC only proves "this body was produced with the app's `client_secret`" and not "this body belongs to shop X", an attacker who can obtain any one legitimately-signed `(body, hmac)` pair — trivially available to them if they install the app on a shop they control and capture the real webhook delivery — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value for a different, victim shop. `HmacValidator.validate` still returns true (it never looks at the header), and the handler receives `data.shop` equal to the attacker-chosen victim domain even though the signed body never originated from that shop.

Equality broken: `shop_that_produced_the_signed_body == shop_attributed_by_WebhookMetadata`. The gem never enforces this; `shop` is fully attacker-controlled and out-of-band from the cryptographic check.

### Impact Explanation
Any consuming application that uses `data.shop` from `WebhookMetadata` to select which merchant's session/database record to update (this is the documented, encouraged usage pattern shown in `docs/usage/webhooks.md`) can be tricked into applying attacker-supplied webhook body content under a victim shop's identity — a cross-tenant write/attribution issue. This satisfies the "cross-tenant access" criterion in the Critical impact bucket, since the identity binding that is supposed to tie signed content to a specific tenant is absent at the gem level.

### Likelihood Explanation
High. No secrets are required beyond having (or emulating) a normal legitimate webhook delivery for any shop, which any unprivileged internet user can obtain by installing the (public) app on their own store and observing/capturing the plaintext HTTP webhook request Shopify sends them (webhooks are delivered in plaintext over HTTPS to the app's public endpoint; nothing prevents a merchant/attacker from logging their own inbound webhook and its headers). The victim's shop domain is a low-entropy, easily guessable/enumerable string (`*.myshopify.com`), so no privileged access, TLS interception, or credential leakage is needed — only a normal, self-service app install.

### Recommendation
Include the shop domain (and other routing-relevant headers such as `topic`/`api-version`) inside the value that is HMAC-verified, or otherwise bind the header-derived `shop` to a value that Shopify signs — e.g., verify that the webhook's declared shop matches a shop for which the app currently holds an active webhook subscription/session before dispatching to the handler, rather than trusting the header verbatim. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically authenticated and must not be used for tenant-scoped authorization decisions without additional verification (e.g., cross-checking against a known/installed shop list).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real event (e.g., `orders/create`), causing Shopify to POST a legitimately HMAC-signed webhook to the app's public webhook endpoint.
2. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value from that real delivery.
3. Attacker crafts a new HTTP request to the same endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `request.to_signable_string` (the raw body) and compares against the HMAC header — this succeeds because the body/HMAC pair is untouched: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and any app logic keyed on `data.shop` (per the documented pattern) now processes attacker-controlled body content as if it came from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end

end
