This gem's webhook processing pipeline exhibits the "field acted on but not covered by the HMAC" pattern that the reported bug class targets.

### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant payload replay - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the raw request body matches an HMAC signature, but the `shop-domain`, `topic`, and `webhook-id` headers used to route and attribute the payload are never included in what is signed.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, not any of the Shopify-supplied headers. [1](#0-0) 

`HmacValidator.validate` computes and compares the HMAC purely against `to_signable_string`, i.e. the body bytes: [2](#0-1) 

`Registry.process` uses this same HMAC check as the sole authenticity gate, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all read straight from unauthenticated headers — to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

Because the `client_secret` used to compute the HMAC is shared across every shop that has installed the app, any unprivileged user can install the app on their own (free) development store, trigger a real webhook, and capture a genuinely-signed `(raw_body, hmac)` pair. That pair remains valid forever for that exact body, regardless of which `shop-domain`/`topic`/`webhook-id` header values accompany it, because those header values were never part of the signed content. The attacker can then replay the identical body + HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`, `x-shopify-webhook-id`) with a victim shop's domain or a different topic. `Registry.process` will accept it as valid and hand it to the handler labeled as if it came from the victim shop.

This breaks the intended binding: **shop authenticated by the HMAC == shop the handler acts on**. In this implementation, `shop` is authenticated by nothing — it flows straight from an attacker-controlled header — while only the body bytes are checked.

### Impact Explanation
An app's webhook handler typically uses `data.shop` to decide which tenant's records to create/update/delete (e.g. order sync, inventory sync, uninstall handling). A replay with a forged `shop` header causes the handler to write or mutate data under the wrong tenant, i.e. cross-tenant data corruption/access — the Critical-tier "cross-tenant access" impact called out in scope.

### Likelihood Explanation
Any internet user can register as a Shopify partner and install the target app on their own store for free, which is enough to legitimately receive an HMAC-signed webhook without needing the app's `client_secret`. Replaying that captured request with edited headers requires no credentials at all, since headers are not part of the signed payload — this is straightforward and repeatable.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC signable string, or otherwise require the host application to separately validate `request.shop` against a known/expected shop before trusting it (and document this requirement prominently, since the current API surface implicitly suggests `request.shop` is already verified once `HmacValidator.validate` succeeds).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers, e.g., an `orders/create` webhook.
2. Attacker's endpoint (or a proxy they control) captures the raw POST body and the `x-shopify-hmac-sha256` header value — both legitimately produced by Shopify using the app's shared `client_secret`.
3. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `@raw_body` and compares — it passes. [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `request.shop` is `"victim-shop.myshopify.com"` — a value the attacker fully controls and that was never covered by the signature. [6](#0-5)
