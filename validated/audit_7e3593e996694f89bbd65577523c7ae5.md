### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Allows Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` as the tenant identity and passes it straight to the host app's `WebhookHandler#handle` without any binding to the HMAC-verified bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from HTTP headers, which are never included in the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC (`Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` covering only the body) and then unconditionally trusts `request.shop` and `request.topic` from the headers to dispatch the webhook: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop acted upon by handler`. Because the HMAC only covers `@raw_body`, this equality is never enforced — the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`) headers can be modified in transit or replayed with a different value while the same `(body, hmac)` pair remains valid, since the app's webhook HMAC secret (`Context.api_secret_key`) is the same for every shop that installed the app, not shop-specific. An attacker who has ever received (or can produce) one valid `(body, hmac)` pair — e.g., by installing the app on a shop they control and capturing a legitimate webhook — can resend the same body/hmac to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, and `HmacValidator.validate` will still return `true` because it never inspects the header values.

### Impact Explanation
This crosses a tenant boundary: `WebhookMetadata.shop` is what host applications (per the intended use of this gem) use to select the correct merchant/session context when acting on the webhook payload (e.g., updating records, revoking access, triggering redact operations). By spoofing `shop`, an attacker can make the app process/attribute a webhook body as belonging to a different, victim merchant, i.e., cross-tenant confusion within the officially exposed API of this gem's webhook processing surface (`Registry.process` → `WebhookHandler#handle`). This matches the "cross-tenant access" Critical impact category, since the identity binding the host app relies on (shop authenticated == shop acted upon) is not enforced by the library despite being marketed as "HMAC validated."

### Likelihood Explanation
Requires only an unprivileged attacker who can install the app on any shop (even a free/dev store) to capture one legitimate `(body, hmac)` pair, then replay it against the app's public webhook endpoint with a modified `shop-domain` header — no access token, `client_secret`, or privileged account needed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the signable string / HMAC computation, or otherwise cryptographically bind the shop identity to the verified payload before it is handed to `WebhookHandler#handle`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering topic `orders/create`; Shopify delivers a webhook with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <hmac-of-body>`, and some JSON body.
2. Attacker resends the exact same request to the app's webhook endpoint but replaces the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`, keeping body and `X-Shopify-Hmac-Sha256` unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (= `@raw_body` only) and matches — validation passes.
4. `request.shop` now returns `"victim-shop.myshopify.com"`, and `handler.handle(data: WebhookMetadata.new(shop: request.shop, ...))` is invoked as if the event legitimately originated from the victim shop. [4](#0-3) [5](#0-4)
