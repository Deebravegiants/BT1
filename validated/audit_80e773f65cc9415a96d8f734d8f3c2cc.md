### Title
Webhook Shop-Domain Header Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
Shopify webhook authenticity is verified by computing an HMAC over the *raw request body* using the app-wide `api_secret_key`. The `x-shopify-shop-domain` header — the value the library treats as the authoritative tenant identifier for the webhook — is never included in the signed data. Because the same `api_secret_key` is used to sign every shop's webhooks, any actor who can obtain one valid `(body, hmac)` pair for a webhook belonging to a shop they control can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header, and `HmacValidator.validate` will still accept it. This breaks the equality that should hold: `shop authenticated by HMAC == shop acted upon by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the (attacker-controllable, over-the-wire) header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and the app's `api_secret_key`/`old_api_secret_key` — it never mixes in the shop domain: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop` (the unauthenticated header value) as the tenant identity for the event: [4](#0-3) 

Because Shopify signs webhooks for *every* installed shop of an app with the same app-level `api_secret_key` (not a per-shop secret), a `(raw_body, hmac)` pair that is valid for shop A's webhook is also a valid HMAC for the exact same bytes regardless of which shop header accompanies it. An attacker who legitimately receives (or can generate, e.g. by installing the target app on their own shop and triggering a webhook) one valid `(body, hmac)` pair can replay that request against the app's webhook endpoint with `x-shopify-shop-domain` swapped to any other shop's domain (a victim tenant). `HmacValidator.validate` will pass because it only checks the body bytes, and the handler will process the payload as if it originated from the victim shop — a direct violation of the identity binding `shop authenticated (by HMAC) == shop stored/acted upon (session key used by handler)`.

### Impact Explanation
This is a cross-tenant integrity issue: an unprivileged actor able to obtain (or self-generate, by using the app on their own store) one valid signed webhook body can inject/replay that event under a different, arbitrary shop's identity into any host application built on this library. Depending on the webhook topic (e.g. `app/uninstalled`, `shop/update`, order/customer topics), this can cause the host app to perform tenant-scoped actions (data deletion, state changes, session/shop record mutations) attributed to the wrong shop — a cross-tenant access/confusion condition, matching the "cross-tenant access" Critical impact category in scope.

### Likelihood Explanation
Likelihood is realistic for any app developer/attacker who can install the target Shopify app on their own store (a normal, unprivileged action) and capture one legitimate webhook body+HMAC (topics with static/predictable/empty bodies, such as `app/uninstalled`, make this trivial since the body content itself needs no secret to reproduce). No access token, `api_secret_key`, or privileged Shopify account is required — only the ability to send an HTTP request to the app's webhook endpoint with attacker-chosen headers, which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the shop identity cryptographically to the HMAC verification: include `x-shopify-shop-domain` (and ideally `webhook-id`/`api-version`) as part of the signed material verified against Shopify's out-of-band webhook subscription record for that shop, or cross-check the `shop` header against a known/registered shop for the specific `webhook_id` before dispatching to the handler. At minimum, document and enforce that host applications must validate `request.shop` against their own webhook registration records (mapping `webhook_id` → expected shop) rather than trusting the header as an authenticated value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and captures a legitimate webhook delivery, e.g. `app/uninstalled` with body `{}` and its valid `x-shopify-hmac-sha256` header (computed by Shopify using the app's shared `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with the *same* raw body and *same* HMAC header, but sets:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <captured-valid-hmac>
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:26-31` recomputes HMAC over the raw body only and it matches, so `Registry.process` in `lib/shopify_api/webhooks/registry.rb:188-200` proceeds and invokes the registered handler with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, even though this webhook was never issued for that shop.
