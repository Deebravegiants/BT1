### Title
`recapitalize` refunds pool cash for a deposit that was never made — unprivileged caller drains supplier funds - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `recapitalize` entrypoint credits cash and pays a "refund" without ever verifying that the payer actually transferred tokens in. The function assumes the controller pre-funds the pool (`"The controller transfers amount into the pool before this call"`, contracts/pool/src/ops/recapitalize.rs:4), but the pool contract itself is directly callable. An unprivileged caller can therefore invoke `recapitalize` with an arbitrary `amount`, book `min(amount, backing_shortfall)` as cash, and receive `amount − applied` paid out of real supplier custody — while having deposited nothing. This mirrors the reported class: the protocol honors a deposit bookkeeping flow without tying it to an actually-received asset.

### Finding Description
`recapitalize::accounting` computes `applied = amount.min(backing_shortfall)` and `refund = amount − applied` purely from the `amount` argument (contracts/pool/src/ops/recapitalize.rs:52-55). It then calls `cache.credit_cash(applied)` and commits, and `apply` executes `outcome.cache.transfer_out(&payer, outcome.refund)` (lines 34, 57). At no point does the pool measure `token.balance(pool)` before/after, pull tokens from `payer`, or `require_auth` an inbound transfer. The deposit is a documentation-level assumption, not a code-level invariant.

The pool's own test suite demonstrates the concrete consequence: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (contracts/pool/tests/flows.rs:3408-3483) calls `t.client().recapitalize(&hub(&t.asset), &payer, &custody)` directly on the pool with a payer that holds zero tokens, and asserts `token.balance(&t.pool) == 0` — the entire supplier custody is paid out as the "refund". The cash book still reports `>= deposit`, so the supplier's subsequent `withdraw` passes `require_reserves` and then fails inside the SAC transfer with `BalanceError = 10`.

This is the same defect shape as the OpenQ report: deposit and claim paths are decoupled. There, NFTs could be deposited but never claimed; here, `recapitalize` pays out against a deposit that the contract never confirmed occurred, and the falsely credited cash book then misleads the liquidity guard (`require_reserves` reads the book, not the balance — test lines 3441-3453).

### Impact Explanation
Theft of user funds followed by freezing: a single unprivileged call to `pool.recapitalize(hub_asset, attacker, custody_amount)` transfers the pool's real token balance to `attacker` while leaving the `cash` book claiming the funds still exist. Legitimate suppliers' withdraws then clear every pool-level solvency guard and revert inside the token transfer — suppliers' funds are stolen and their shares unredeemable until someone recapitalizes for real.

### Likelihood Explanation
`recapitalize` is listed as a public pool entrypoint (reachable unprivileged per the scope rules) and the in-repo test proves it executes end-to-end with a zero-balance payer. No special timing, oracle state, or admin flag is required; the only precondition is a market with real custody.

### Recommendation
Make the deposit real before paying the refund: either gate `recapitalize` (and `supply`, `repay`, which share the same "controller pre-transfers" trust model per contracts/pool/README.md:334-335) to the controller address, or measure the inbound amount via a balance-delta (`token.balance(pool)` before vs. the controller's measured transfer) and bound `applied + refund` by what was actually received. At minimum, `credit_cash(applied)` should be conditioned on verified receipt so the cash book cannot diverge from custody.

### Proof of Concept
From the pool's own test (contracts/pool/tests/flows.rs:3408-3483):

```rust
// Supplier deposits legitimately: custody == cash book == deposit
token_admin.mint(&t.pool, &deposit);
t.client().supply(&t.sup(0, deposit));

// Attacker (zero balance, no auth on the transfer in) drains custody:
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);        // theft succeeded
assert!(t.state_snapshot().cash >= deposit);  // book still claims solvency

// Supplier withdraw reverts inside the SAC transfer (BalanceError = 10),
// not at any pool guard:
t.client().try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
```

The refund leg in `apply` (`transfer_out(&payer, outcome.refund)`, recapitalize.rs:34) pays the attacker out of supplier custody because `accounting` never validated that `amount` tokens arrived.

Note: I was able to verify the accounting/refund logic and the confirming test, but could not fully read `contracts/pool/src/lib.rs` within the iteration limit to confirm the exact auth surface on `recapitalize`; the harness test's direct, successful call strongly indicates no controller-only gate is enforced.
