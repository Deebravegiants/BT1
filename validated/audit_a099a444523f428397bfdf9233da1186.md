### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook exclusively from the `x-shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates is computed over the raw body only. The `shop-domain` header value is never part of the signed material, so an attacker who obtains one valid `(raw_body, hmac)` pair delivered to the app's public webhook endpoint can freely rewrite the `shop-domain` header and have the gem accept it as authentic for a *different* shop.

### Finding Description
`Request#shop` reads the header directly: [1](#0-0) 

But `to_signable_string`, which is the only input fed into HMAC verification, returns just the raw body: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, immediately trusts `request.shop` as the tenant for the event without any independent binding check: [3](#0-2) 

The equality that should hold but is broken is:
`shop_used_to_dispatch_webhook_handler == shop_that_the_HMAC_actually_authenticates`

Since the HMAC only authenticates `@raw_body` (`to_signable_string`), and `shop` is read from a separate, unsigned header, these two values are never cryptographically bound together. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) confirms only that *some* valid webhook body was HMAC-signed by the app's secret at some point — it says nothing about which shop sent it.

### Impact Explanation
Any internet-reachable app webhook endpoint receives Shopify-signed payloads that an attacker (e.g. sitting in front of, or replaying against, the endpoint) can capture and resend with an altered `x-shopify-shop-domain` header while keeping the original, still-valid `hmac-sha256` header/body pair intact. `Registry.process` will pass HMAC validation and dispatch the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the attacker-chosen shop rather than the shop that actually triggered the event. Any host application that scopes data mutation, session lookup, or GDPR compliance actions (`shop/redact`, `customers/redact`, `customers/data_request` are exactly the `MANDATORY_TOPICS` handled here — `lib/shopify_api/webhooks/registry.rb:8-12`) by `data.shop` is exposed to cross-tenant data corruption: e.g. an attacker can trigger a real, validly-signed `app/uninstalled` or `shop/redact` payload against their own low-value shop and immediately replay it with a victim shop's domain, causing the app to treat the victim's tenant as uninstalled/redacted.

### Likelihood Explanation
Requires no credentials beyond the ability to see/replay one legitimate webhook delivery to the app's own public webhook endpoint (a normal, uncredentialed HTTP endpoint) and to send a second forged request with a different `shop-domain` header — no possession of `api_secret_key` or an access token is needed. The attacker only needs control over a shop that installs the same app (freely available), which is not a "privileged" prerequisite as defined by the scope rules.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signed material, or otherwise cryptographically tie the claimed shop to the payload before dispatching to handlers — e.g. include the header in `to_signable_string`, or cross-check `request.shop` against a shop value embedded in the JSON body / a stored expected-shop mapping before calling `handler.handle`.

### Proof of Concept
1. Register an app-owned shop (`attacker-shop.myshopify.com`) and configure a webhook (e.g. `app/uninstalled`) to the app's endpoint.
2. Trigger the webhook; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this pair is valid per `HmacValidator.validate`.
3. Resend the identical body and `hmac-sha256` header to the same endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`@raw_body`) against the secret — it succeeds because the body/hmac pair is genuinely valid.
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)`, causing the host app to act on the victim shop's tenant data using an event that never originated from Shopify for that shop.
