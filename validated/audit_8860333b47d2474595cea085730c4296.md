### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is trusted from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant confusion - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC over the raw request body only, then unconditionally trusts the `x-shopify-shop-domain` (and `topic`/`webhook-id`) header values — which are never included in the signed bytes — to build the `WebhookMetadata` handed to the app's handler. This is the same bug class as the WebAuthn report: a value that is *acted on* by the consumer (shop identity) is not actually bound by the cryptographic check that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are read directly, unauthenticated, from HTTP headers: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then immediately forwards `request.shop` (an unauthenticated header) into `WebhookMetadata`, which is what the consuming app's handler uses to identify which merchant the payload belongs to: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely from `verifiable_query.to_signable_string` (the raw body) and the shared app secret, with no shop/topic binding: [4](#0-3) 

Because the `api_secret_key` is shared across **all** shops that install a given app, any attacker who installs the app on their own store is an "unprivileged internet user" from the perspective of any other merchant, yet they can legitimately trigger a webhook delivery from their own shop and obtain a *validly signed* `(body, hmac)` pair. Since the HMAC never binds `shop`, the attacker can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body bytes and secret are unchanged), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop — breaking the identity binding:

```
shop authenticated by the signature (attacker's own shop) != shop delivered to the handler (spoofed victim shop)
```

This mirrors the report's root cause: a value that should be part of the authenticated/bound data (the counter in `AUTHENTICATOR_DATA`, here the `shop` domain) is instead supplied out-of-band and trusted without verification.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which merchant's records to create/update/delete (a standard and documented pattern — see `docs/usage/webhooks.md` guidance on using `data.shop`) can be tricked into applying a legitimately-signed payload under an attacker-chosen victim shop identity. This is a cross-tenant data integrity/access issue: an attacker-controlled webhook body (from their own store) gets attributed to another merchant's tenant record, or conversely a victim's legitimate webhook data can be relabeled to the attacker's own shop if the attacker can intercept normal-cost delivery timing, causing state confusion between tenants in the app's data store. The severity is bounded by what the specific handler implementation does with `shop`, but the gem provides no protection and no documented warning that `shop` is not authenticated.

### Likelihood Explanation
Likelihood is moderate: the attacker must (1) be a legitimate installer of the target app on their own shop (a normal, low-privilege action for any public app), (2) capture one legitimately-signed webhook body+HMAC pair from their own store (easily done by triggering an action that fires a webhook), and (3) replay it directly to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secrets, tokens, or privileged access are required — only the ability to install the app and send an HTTP POST, which satisfies the "unprivileged internet user" bar.

### Recommendation
Bind the shop (and ideally topic) into the authenticated data before trusting it, e.g. verify that `x-shopify-shop-domain` matches a shop the requesting app instance is actually authorized to receive on record (checked against a stored per-shop session/webhook registration), or require the consuming application to independently verify `shop` ownership before acting on `WebhookMetadata#shop`. At minimum, the gem's documentation and API should make explicit that `shop`/`topic`/`webhook_id` headers are **not** covered by the HMAC and must not be trusted for tenant selection without additional verification (e.g., cross-checking against the app's own session store keyed by a shop domain obtained through OAuth).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a normal, valid webhook delivery (e.g., `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a raw HTTP POST to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since HMAC only covers body)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `B`.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app processes the attacker's own order data as if it belongs to `victim-shop.myshopify.com`. [5](#0-4)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
