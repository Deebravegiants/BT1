### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by the HMAC signature, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and passed straight to the app's webhook handler after the HMAC check passes. Because the same app-level secret signs every merchant's webhooks, an attacker who legitimately receives one authentic webhook (e.g. via their own free/trial install) can replay the exact `body`+`hmac` pair while substituting an arbitrary `shop` (and `topic`) header, and the library will accept it as valid, feeding the handler attacker-chosen `shop`/`topic` values it treats as authenticated.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all derived from HTTP headers that are **not** part of the signed content: [3](#0-2) 

`Registry.process` only checks that the (body-only) HMAC is valid, then dispatches the handler using the unauthenticated `shop` and `topic` values: [4](#0-3) 

Because the HMAC secret is the app's `client_secret`, which is identical across every merchant installation, a valid `(body, hmac)` pair captured from **any** legitimate delivery (including one delivered to an attacker's own free/dev-store install) remains valid regardless of which `shop-domain`/`topic` header accompanies it. The equality the library should enforce — `shop_header == shop_bound_by_signature` — is never checked; only `hmac == HMAC(secret, body)` is checked, and `body` carries no shop identity of its own in the general case (many webhook payloads reference the shop only implicitly or not at all, e.g. `app/uninstalled`, `shop/update`, GDPR webhooks).

### Impact Explanation
An attacker with a legitimate, low-privilege relationship to the app (any developer/trial store can install almost any public app) can capture one authentic `raw_body` + `x-shopify-hmac-sha256` pair from a webhook delivered to their own store, then replay it to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header naming a victim merchant. `Registry.process` will treat the request as an authentic webhook "for" the victim shop and invoke the app's handler with `shop: <victim>`, causing the host application — which relies on this gem's documented `WebhookMetadata#shop` as the authenticated tenant identifier — to perform cross-tenant actions (e.g., marking the victim shop as uninstalled, triggering GDPR/data-erasure workflows, updating shop-scoped state) using attacker-controlled payload data. This is a cross-tenant access vulnerability requiring no knowledge of the app's `api_secret_key`.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one authentic webhook delivery only requires installing the app on a store the attacker controls (many apps are free or offer trial installs), which is achievable by any unprivileged internet user. No secret material, TLS interception, or privileged account is needed — only the ability to capture headers from a webhook the app itself sends to the attacker's own endpoint and replay it elsewhere.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed payload verification, e.g. by including these header values in `to_signable_string` (if server-side re-signing is feasible) — but since Shopify controls the wire format and only signs the body, the correct mitigation within this gem is to have `Registry.process` validate that the shop conveyed in the header actually corresponds to a shop with an active session/installation known to the host app (cross-referencing against session storage) before invoking handlers, and to document this requirement prominently so host apps do not treat `WebhookMetadata#shop` as authenticated purely because the HMAC passed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives (or triggers) a webhook, e.g. `app/uninstalled`, capturing the raw POST body and the `x-shopify-hmac-sha256` header — both fully legitimate since Shopify signed them with the app's real secret.
2. Attacker replays the exact same body and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, raw_body)` and it matches the replayed `hmac` header (secret is app-wide, not shop-specific), so `Registry.process` proceeds. [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` and performs shop-scoped logic against the victim, believing the request was authentically delivered by Shopify for that shop.
