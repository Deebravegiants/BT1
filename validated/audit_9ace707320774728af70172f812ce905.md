The `WebhookMetadata.shop` field, delivered directly to app handlers as a trusted tenant identifier, is populated from `request.shop` which is read purely from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header, while the HMAC (`Utils::HmacValidator.validate`) only ever signs `to_signable_string`, which for `Webhooks::Request` returns just `@raw_body`.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as fully authenticated once `Utils::HmacValidator.validate(request)` passes, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`, `request.api_version`) to build the `WebhookMetadata` passed to the app-provided handler. But the HMAC only ever signs the raw body, not these header-derived fields, so the shop attribution can be forged independently of the signature.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

Its `to_signable_string` returns only `@raw_body`: [2](#0-1) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC of that same `to_signable_string` (i.e., the body) and then forwards the unauthenticated header values straight to the handler as if they were verified: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` confirm this — they only ever hash `verifiable_query.to_signable_string`, i.e. the raw body, never the shop header: [5](#0-4) 

The binding that should hold is:
`HMAC(secret, raw_body) valid` ⇒ `shop-domain header == shop that produced raw_body`

but the code only proves the left side; it never proves the right side. `WebhookMetadata.shop` is a plain `String` field with no separate authentication, and is exactly what handler implementations are expected to use to key their tenant/session lookup: [6](#0-5) 

**Attack path:** Any unprivileged internet user can install the target Shopify app for free on their own store (a self-service, unprivileged action for any public app). Shopify will then deliver at least one legitimately HMAC-signed webhook body to the app's public webhook endpoint, addressed with that attacker's own `shop-domain` header. Because the signature covers only the body bytes, the attacker can capture that exact `(raw_body, hmac)` pair and replay it to the same public endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to any victim shop that also uses the app. `HmacValidator.validate` still returns `true` (the body/hmac pair is untouched), so `Registry.process` calls the handler with `WebhookMetadata#shop` equal to the victim's domain, `topic`/`webhook_id`/`api_version` also attacker-controlled, and the attacker's own (but validly-signed) body content. Any app that uses `data.shop` to select which merchant's session/data-store record to update, or that uses `data.topic`/`data.webhook_id` to decide processing/idempotency (e.g. mandatory-compliance webhooks like `customers/redact`, `shop/redact`), can be made to act on the wrong tenant.

### Impact Explanation
This breaks the shop/tenant identity binding relied upon by every consumer of `ShopifyAPI::Webhooks::Registry.process`: the gem asserts "Invalid webhook HMAC" as the sole gate before handing off `shop`, `topic`, and `webhook_id` to the handler, implying those fields were authenticated together with the body. They were not. This is a cross-tenant boundary break (Critical) — an attacker with no privileged credential can cause an app's webhook processing pipeline to attribute arbitrary, attacker-chosen webhook content (body they control, since they registered it under their own store) to any other shop identifier of their choosing, or attribute their own data under a spoofed mandatory-compliance topic/webhook id.

### Likelihood Explanation
The prerequisite is only the ability to install a public Shopify app on a self-owned store (trivial, unprivileged, self-service) and the ability to send an HTTP POST to the app's public webhook endpoint (also always network-reachable, since Shopify itself must reach it). No `api_secret_key`, access token, or any privileged credential is required — the attacker only needs one legitimately-delivered `(body, hmac)` pair obtained under their own tenant, which is guaranteed to arrive automatically upon installation/topic subscription.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the signed material, or independently verify `request.shop` against the set of shops known to have that webhook registered/installed before invoking the handler. At minimum, `Webhooks::Registry.process` should cross-check `request.shop` against an app-level registry of installed/authorized shops (or the `shop`/`webhook_id` should be echoed in and verified from the JSON body where Shopify includes it) before constructing `WebhookMetadata`, rather than passing header-only fields straight through as if HMAC-validated.

### Proof of Concept
1. As an attacker, install the target public app on `attacker-shop.myshopify.com`; subscribe to any http webhook topic the app registers.
2. Capture the resulting POST to the app's webhook endpoint, e.g.:
   ```
   POST /webhook
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <attacker-webhook-id>
   body: {"id": 1, ...attacker-controlled...}
   ```
3. Replay the exact same request to the same endpoint, only changing:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`) still returns `true`, since it only hashes the untouched raw body.
5. `ShopifyAPI::Webhooks::Registry.process` (per `lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker JSON>, webhook_id: <attacker-chosen>)`, i.e. attacker-controlled content attributed to a tenant the attacker never had access to.
