### Title
Accrual-time `i128` overflow panic in `scaled_to_original` permanently freezes all exits and repayments on a whale market - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary
The CVE-2017-11590 bug class is a crash (NULL pointer dereference) reached by a crafted input, causing denial of service. The on-chain analog is a hard panic on attacker-influenced state. In XOXNO Lending, interest accrual computes `scaled × index` through `Ray::mul` inside `scaled_to_original`; when a market's scaled totals are large enough, index growth drives the RAY-scaled product past the `i128` ceiling and every subsequent call that accrues panics with `MathOverflow`. Because accrual runs first on every verb, the market is permanently bricked: no withdraw, no repay, no liquidation.

### Finding Description
`scaled_to_original` performs an unchecked RAY multiplication:

```rust
// common/src/rates/scaling.rs:14-16
pub fn scaled_to_original(env: &Env, scaled: Ray, index: Ray) -> Ray {
    scaled.mul(env, index)
}
```

`Ray::mul` (`common::math::fp`) panics with `GenericError::MathOverflow` when `scaled * index` exceeds `i128::MAX`. Accrual in `contracts/pool/src/interest.rs` rescales the accrued debt back into shares with `scaled_to_original`, and `ops::synced_market` accrues before every mutating pool op. `Cache::calculate_utilization` (contracts/pool/src/cache/scale.rs:19-27) also calls `scaled_to_original` on `borrowed`/`supplied`, so even guarded paths hit the same overflow.

The borrow index is capped at `MAX_BORROW_INDEX_RAY`, but the cap is applied *after* the value computation — the overflow fires inside the multiplication before the cap can engage. The protocol's own harness test confirms this exactly: at 98% utilization on the steep XLM rate curve with a ~1e18-decimals whale market, the index reaches ~170x within the test horizon, `update_indexes` panics with error #33 (`MathOverflow`), and the test asserts the market is frozen:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:354-356
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The test comment notes the index cap "never engages" and that "every verb accrues first, so the market freezes: no repay, no withdraw, no liquidation." It also flags that the documented bound in `docs/reference/formulas.md` is wrong, so this is not an acknowledged ADR trade-off.

An unprivileged path exists: any account can `supply` an 18-decimals asset and `borrow` against other collateral (controller `supply`/`borrow`), pushing `borrowed` scaled shares toward the value ceiling; once utilization sits high on a steep curve, accrual does the rest. `clean_bad_debt`, `liquidate`, `recapitalize`, `flash_loan`, and `update_indexes` all accrue through the same path and cannot rescue it.

### Impact Explanation
Permanent freezing of funds for every supplier and borrower in that (hub, token) book: once the panic condition is reached, no entrypoint touching the market can complete, so supplier principal and yield are locked forever, and liquidations cannot execute, compounding insolvency risk on other books via the shared pool balance. This is stronger than the CVE's transient crash — it is a permanent, unrecoverable halt.

### Likelihood Explanation
Likelihood is low-to-moderate. It requires a whale-scale position (billions of units of an 18-decimal asset) and sustained near-max utilization for the index to multiply scaled totals past `i128::MAX`. However, no privileged action is needed, rate curves place no bound on per-block index growth, caps and the `MAX_BORROW_INDEX_RAY` ceiling demonstrably do not prevent it, and the project's own test reproduces the cliff within the simulated horizon. An attacker with sufficient capital (or via `flash_loan`-amplified positioning to maximize utilization) can deliberately push a market into this regime.

### Recommendation
Bound the product, not just the index: before rescaling in accrual (`contracts/pool/src/interest.rs`), clamp or check `borrowed * borrow_index` against `i128::MAX` and cap effective growth so `scaled_to_original` cannot overflow — e.g., enforce the documented `MAX_BORROW_INDEX_RAY` bound *before* value computation, or accrue in chunks (`millisecond chunked accrual` already exists) sized so each accrual step keeps `scaled × index` in range. Additionally, make `Cache::calculate_utilization` use saturating rescale for the utilization check so a near-ceiling market degrades to "max utilization" instead of trapping every subsequent call, and add a regression bound test for the `docs/reference/formulas.md` index-cap claim.

### Proof of Concept
The repo's own test demonstrates it (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`): supply `BILLION * 1e18` of an 18-decimals asset, borrow 98% of it against collateral, advance time in yearly steps; `update_indexes` reverts with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` revert identically — the market is permanently frozen.
