### Title
JWT replay-protection check-then-act race allows concurrent reuse of a single signed HTTP trigger token - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The gateway's HTTP Trigger `Authorize` path is reachable directly by an unprivileged internet-facing client (the caller of the HTTP trigger endpoint) supplying a signed JWT alongside a `workflows.execute` request. Replay protection for that JWT is implemented as a non-atomic check-then-record sequence, allowing the same signed token to authorize more than one concurrent execution.

### Finding Description
`WorkflowMetadataHandler.Authorize` verifies the JWT, checks whether its `jti` claim has been used before via `h.jwtCache.isReplay(claims.ID)`, and — only if not a replay — later calls `h.jwtCache.recordUsage(claims.ID)`: [1](#0-0) 

The `jwtReplayCache` implementation takes an `RLock` for the read check and a separate `Lock` for the later write, with no shared critical section covering both operations: [2](#0-1) 

Because `isReplay` and `recordUsage` are independent, unsynchronized operations, two (or more) concurrent `HandleUserTriggerRequest` calls carrying the identical signed JWT can both pass `isReplay` before either calls `recordUsage`, since `authorizeRequest` invokes `Authorize` directly on the unprivileged, internet-facing request path: [3](#0-2) 

This is invoked from `HandleUserTriggerRequest`, which is the entry point for external client-triggered workflow execution requests: [4](#0-3) 

The only other duplicate-suppression mechanism, `setupCallback`'s `requestID`-uniqueness check, operates on the caller-supplied JSON-RPC `id`, not the JWT `jti` — an attacker or a replaying party can simply vary the JSON-RPC `id` field on each concurrent submission while replaying the exact same JWT+signature, bypassing both the request-ID dedup and racing past the JWT replay cache: [5](#0-4) 

### Impact Explanation
A single valid, signed authorization token intended to authorize exactly one workflow execution can be used to trigger multiple concurrent executions of the workflow. Since the trigger path leads to `sendWithRetries`, which fans requests out to DON members to execute a workflow with the caller's authorized key attached, replaying a captured/observed token lets an unprivileged actor cause extra, unauthorized job/workflow runs beyond what the token holder intended or was billed/rate-limited for — directly matching the "unauthorized job run" impact category. This mirrors the UwU Lend pattern of leveraging previously obtained/valid credentials beyond their single intended use to cause repeated unauthorized effects.

### Likelihood Explanation
Exploitation requires only submitting the same valid JWT twice in close temporal proximity (e.g., via two parallel HTTP requests with different JSON-RPC `id`s) — no cryptographic break or privileged access is needed, only network-level concurrency, which is trivial for an external client to induce. The race window is small but real (verify → check → later record), and any legitimate token holder or an observer who intercepts/replays a token before its single use is recorded can win the race.

### Recommendation
Make replay-check-and-record atomic: perform the "has this jti been seen" check and the recording of usage under a single lock acquisition (e.g., a `CompareAndSwap`-style `TryRecord(jti)` that atomically inserts the entry only if absent and returns whether it was newly inserted), and reject the request if the entry already existed. Additionally, consider tying the per-JWT replay guard to the JSON-RPC `id`/execution context so that request-ID variation cannot be used to bypass the intended single-use semantics of the token.

### Proof of Concept
1. Obtain (or observe in transit) one valid signed JWT (`jti`=X) authorized for workflow `W`.
2. Send two (or more) concurrent `workflows.execute` HTTP trigger requests to the gateway with distinct JSON-RPC `id` values but the identical JWT/signature in the `Auth` field.
3. Both goroutines call `WorkflowMetadataHandler.Authorize`; both call `h.jwtCache.isReplay(X)` before either calls `h.jwtCache.recordUsage(X)`, since these are separate lock sections.
4. Both requests pass authorization and are dispatched via `sendWithRetries`/`sendToShard` to the DON, resulting in two independent workflow executions from a single-use token — demonstrated by the absence of any atomic check in `jwtReplayCache.isReplay`/`recordUsage` shown above.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
