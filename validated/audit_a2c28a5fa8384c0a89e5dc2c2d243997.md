### Title
`shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers while only the raw body is HMAC-covered - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC validated by `Utils::HmacValidator.validate` only proves the *body bytes* came from Shopify. The `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from HTTP headers and are never included in the signed material, yet `Registry.process` passes them, unauthenticated, into `WebhookMetadata` that the host app's `WebhookHandler#handle` uses to attribute the event to a tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only `@raw_body` is signed. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC and then trusts these header-derived fields to build `WebhookMetadata`, which is handed to the app's handler as the tenant identity for the event: [3](#0-2) [4](#0-3) 

The binding this breaks, expressed as an equality that the gem should enforce but does not:
`shop_authenticated_by_hmac == shop_delivered_to_handler`

Before the attack: for a genuine Shopify-delivered webhook, the `x-shopify-hmac-sha256` header is `HMAC(secret, raw_body)`, and `x-shopify-shop-domain` is set correctly by Shopify for that same tenant — the two happen to agree only because Shopify's own delivery infrastructure sets them consistently, not because this gem enforces it.

After the attack: an unprivileged internet user who has ever observed one valid `(raw_body, hmac)` pair for topic X (e.g., their own store's `orders/create` webhook, or any webhook whose body content is not tenant-specific/secret, such as `app/uninstalled` with a generic payload, or a replayed webhook body) can send a forged HTTP request directly to the app's webhook endpoint with the original valid `hmac`/`raw_body`, but with an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds because it only checks the body against the secret; `Registry.process` then dispatches to the handler with `WebhookMetadata.shop` set to the attacker-chosen shop domain. `Request#shop` performs no validation against a known/registered shop list, and `hmac` covers none of the headers.

This matches the report's underlying bug class of "a field acted on but not covered by the signature/HMAC" — here `shop` (and `topic`/`webhook_id`) are the analogous unbound fields, mirroring how the referenced eETH report showed value credited without validation of its true provenance.

### Impact Explanation
If a host application uses `WebhookMetadata#shop` (as documented/intended by the struct) to select which merchant record/session to update in response to a webhook, an attacker who can obtain any single valid `(body, hmac)` pair can cause the handler to act as if the event pertains to a different shop — a cross-tenant data-integrity issue driven entirely through this gem's public webhook-processing API, without needing the app's `client_secret` or an access token. This is a scope/authenticity check that answers permissively for header fields not covered by the signature.

### Likelihood Explanation
Medium-to-High: the webhook endpoint is by design internet-facing and unauthenticated (no other credential is required), the HMAC secret is not needed to forge the shop header, and obtaining one valid `(body, hmac)` pair is straightforward for topics with static or attacker-observable payloads (e.g., `app/uninstalled`, or any webhook the attacker's own store legitimately receives). The severity of impact depends on how strictly the host application trusts `WebhookMetadata.shop`, which is outside this gem, but the gem provides no protection here and its `WebhookMetadata` struct explicitly surfaces `shop` as if it were authenticated.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable string used for HMAC verification, or otherwise cryptographically/contextually bind them to the verified body (e.g., document clearly that only the body is authenticated and these headers must be independently validated by the host app against known/registered shops before use).

### Proof of Concept
1. Attacker has one legitimate delivery: `raw_body = "{}"`, `hmac = HMAC-SHA256(secret, "{}")` (from any past webhook, e.g. their own store's `app/uninstalled`).
2. Attacker POSTs to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256: <the valid hmac from step 1>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (arbitrary/forged)
   - `x-shopify-topic: app/uninstalled`
   - body: `{}`
3. `ShopifyAPI::Webhooks::Request.new` accepts headers, `Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though this shop never actually sent the webhook.
