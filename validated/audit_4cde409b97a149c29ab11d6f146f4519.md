Audit Report

## Title
Cross-Chain Bridge DoS via Sovereign Account Drain — Shared Fee Pool Pattern in `SovereignPaidRemoteExporter` / `pallet-xcm-bridge-hub-router` (File: `polkadot/xcm/xcm-builder/src/universal_exports.rs`)

## Summary
`SovereignPaidRemoteExporter` funds `ExportMessage` execution on the Bridge Hub from the sending parachain's sovereign account there, and this exact type is still live in the current `asset-hub-rococo` runtime's `XcmRouter` for the Ethereum lane, contradicting the claim's own likelihood assessment that this was fully mitigated. However, the claim does not establish a realistic drain vector: the per-message fee (`BridgeHubEthereumBaseFee` ≈ 3.8e12 units, roughly on the order of full-DOT-equivalent amounts, not "dust") is a substantial economic cost that scales linearly with the number of messages sent, so "cheap/dust messages" draining the account is not demonstrated and is not architecturally analogous to a free/near-free spam vector.

## Finding Description
`SovereignPaidRemoteExporter::validate` builds `WithdrawAsset(fees) -> BuyExecution -> SetAppendix(refund) -> ExportMessage` and forwards it to the Bridge Hub in the sending parachain's origin, debiting that parachain's sovereign account balance held there. [1](#0-0) 
This is confirmed as still actively wired into asset-hub-rococo's live `XcmRouter` for the Ethereum export lane (`SovereignPaidRemoteExporter<bridging::EthereumNetworkExportTable, XcmpQueue, UniversalLocation>`), meaning the claim's premise that this pattern exists in-repo is accurate. [2](#0-1) 
However, `asset-hub-westend` has already moved this specific lane to `UnpaidRemoteExporter` wrapped in `PausableExporter`, so the exposure is inconsistent across runtimes, not universal. [3](#0-2) 
Critically, the fee charged per export to Ethereum is not a "dust" amount — it is a fixed base fee (`DefaultBridgeHubEthereumBaseFee = 3_833_568_200_000`, roughly ~0.38 ROC given 12 decimals) explicitly calibrated to cover the real delivery/relaying cost, not an economically negligible value. [4](#0-3) 
The `pallet-xcm-bridge-hub-router` variant additionally applies a dynamic, congestion-scaling `fee_factor` multiplier and a per-byte fee on top of the base fee, further increasing cost under load rather than allowing cheap repeated draining. [5](#0-4) 

## Impact Explanation
The claim's premise (that the design pattern exists) is technically correct for at least one production lane (asset-hub-rococo → Ethereum). But the reported impact — an attacker draining the sovereign account with "cheap/dust value messages" to achieve an economically disproportionate DoS — is not substantiated. Each `ExportMessage` costs a real, non-trivial, fixed fee that is withdrawn from the *attacker's own* transferred value/fees at the point the XCM program executes (the fee still must be sourced from assets present in the program's holding register, ultimately paid for by whoever initiates the cross-chain send); draining the account requires the attacker to actually pay (or cause to be paid) that fee for every message, which is a 1:1 cost, not an amplification attack. This is fundamentally different from LayerZero's bug, where a fixed shared pool is drained by messages that cost the attacker far less than what is drained from the pool. No such asymmetry is shown here.

## Likelihood Explanation
The report itself acknowledges this is unconfirmed and speculative ("I could not fully confirm... this is an open item"), and the investigation here confirms the pattern exists in only one runtime/lane (asset-hub-rococo → Ethereum) while asset-hub-westend already migrated away from it. No amplification/asymmetric-cost mechanism was identified that would let an unprivileged attacker drain the sovereign account for less than the value it costs them to do so — the base fee plus per-byte and congestion-scaled fee factor mean draining the account costs the attacker proportionally the same amount they'd need to fund it themselves, which is neither cheap nor different in economics from the intended operation of the bridge. This is a known operational design tradeoff (requiring sovereign-account top-ups), which the SDK team has already documented and progressively mitigated (PR 11694, PR 8599), not an exploitable vulnerability with disproportionate attacker leverage.

## Recommendation
No code change required to address a security vulnerability. As already tracked by the project, continue migrating remaining paid-export lanes (e.g., asset-hub-rococo's Ethereum lane) to `UnpaidRemoteExporter`/`pallet-xcm-bridge-hub-router`-managed dynamic fees, and ensure operational monitoring of sovereign account balances, consistent with existing engineering direction. This is an operational/architectural consideration, not a security flaw with attacker-exploitable asymmetric cost.

## Proof of Concept
None provided or feasible from static analysis; the report explicitly states no PoC was constructed, and no amplification mechanism was identified that would let a PoC demonstrate an attacker draining the account for less cost than the account replenishment requires.

					return None;
				},
			},
			None => 0,
		};

		// compute fee amount. Keep in mind that this is only the bridge fee. The fee for sending
		// message from this chain to child/sibling bridge hub is determined by the
		// `Config::ToBridgeHubSender`
		let message_size = message.encoded_size();
		let message_fee = (message_size as u128).saturating_mul(T::ByteFee::get());
		let fee_sum = base_fee.saturating_add(message_fee);
		let fee_factor = Self::get_fee_factor(());
		let fee = fee_factor.saturating_mul_int(fee_sum);

		let fee = if fee > 0 { Some((T::FeeAsset::get(), fee).into()) } else { None };

			to=?(network, remote_location),
			bridge_fee=?fee,
			%fee_factor,
			"Going to send message ({message_size} bytes) over bridge."
		);

		Some((bridge_hub_location, fee))
