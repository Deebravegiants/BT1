**Analysis:**

The premise doesn't match how `api/src/events.rs` actually works. Unlike the transactions endpoint, the events listing path never calls `Page::compute_start` with a separately-computed `max`. Instead, `list()` captures a single `LedgerInfo` snapshot once (`latest_ledger_info`, obtained via `Account::new` before `list` is called) and threads that same `ledger_version` through both `page.limit(&latest_ledger_info)` and `context.get_events(...)`: [1](#0-0) 

There is no two-step "capture max, then separately query" sequence for events to race against; the bound used for the actual DB/indexer lookup (`ledger_version`) is the exact same value used to validate the page parameters, taken from one consistent snapshot at the start of request handling.

The storage layer further enforces this bound deterministically: `lookup_events_by_key` stops iterating as soon as it sees a transaction version greater than the passed `ledger_version`, so results are always consistent with that single snapshot, not influenced by events appended afterward: [2](#0-1) 

The `determine_limit` function in `api/src/page.rs` only bounds the page *size* (rejecting 0, capping at `max_page_size`); it has no interaction with ledger versioning at all: [3](#0-2) 

Even hypothetically, if a new multisig-owner-add event were appended to the ledger after a watcher's snapshot was taken, that event is not "permanently unreachable" — it is simply not yet visible in that one request's result set. Any subsequent call re-fetches a fresh `latest_ledger_info` and fresh `ledger_version`, and the append-only event log guarantees the new event becomes visible then. There is no state where the event is dropped or made unreachable forever.

Most importantly, this scenario does not cross a custody boundary as defined by the review's decision standard. Adding a multisig owner requires the multisig module's own authorization checks (owner/threshold approval) enforced on-chain; this is unrelated to how a read-only, off-chain watcher paginates through the events API. A momentary lag in an unprivileged observer's visibility of an already-authorized event is, at most, an event-level/monitoring consistency question — it does not change who can own, move, mint, burn, freeze, upgrade, or recover any asset, and does not grant any unprivileged caller new authority. Per the Decision Standard, this must be rejected as a cosmetic/event-level mismatch rather than a custody-grade vulnerability.

pub fn determine_limit<E: BadRequestError>(
    // The limit requested by the user, if any.
    requested_limit: Option<u16>,
    // The default limit to use, if requested_limit is None.
    default_limit: u16,
    // The ceiling on the limit. If the requested value is higher than this, we just use this value.
    max_limit: u16,
    ledger_info: &LedgerInfo,
) -> Result<u16, E> {
    let limit = requested_limit.unwrap_or(default_limit);
    if limit == 0 {
        return Err(E::bad_request_with_code(
            format!("Given limit value ({}) must not be zero", limit),
            AptosErrorCode::InvalidInput,
            ledger_info,
        ));
    }
    // If we go over the max page size, we return the max page size
    if limit > max_limit {
        Ok(max_limit)
    } else {
        Ok(limit)
    }
