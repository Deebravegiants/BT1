### Title
Predictable, unsigned session identifiers used as raw cookie values enable session fixation / cross-tenant hijack - (File: lib/shopify_api/auth/session.rb, lib/shopify_api/auth/oauth.rb, lib/shopify_api/utils/session_utils.rb)

### Summary
`ShopifyAPI::Auth::Session.from` derives session IDs deterministically from public information (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{associated_user.id}"` for online sessions), and `Oauth.validate_auth_callback` writes that exact deterministic string as the value of the `shopify_app_session` cookie for non-embedded (and, per the fallback branch, potentially embedded) apps. `SessionUtils.cookie_session_id` then reads this cookie back with **zero cryptographic verification**, trusting it as an authenticated session identifier. Because the ID has no HMAC/signature/random component, any attacker who knows a shop's domain can forge the same cookie value and cause a host app's session store to hand back that shop's real `Session` (including `access_token`).

### Finding Description
Intended binding: `cookie_session_id(cookies) == <a value only derivable by someone who completed OAuth for that shop>`. Actual: `cookie_session_id(cookies) == <the raw, attacker-supplied cookie string, verified against nothing>`, and that string's expected legitimate value is itself a deterministic function of public data.

Trace:
1. `ShopifyAPI::Auth::Session.from` (`lib/shopify_api/auth/session.rb:107-117`) sets `id = "#{shop}_#{associated_user.id}"` (online) or `id = "offline_#{shop}"` (offline) — no `SecureRandom`, purely derived from `shop` (and `associated_user.id` for online). [1](#0-0) 
2. `Oauth.validate_auth_callback` uses that `session.id` directly as the browser cookie value for non-embedded apps: `SessionCookie.new(value: session.id, expires: ...)`. For embedded apps the value is cleared to `""`, but the library still exposes and permits the cookie-fallback branch in `current_session_id` regardless of `Context.embedded?`. [2](#0-1) 
3. `SessionUtils.current_session_id` (`lib/shopify_api/utils/session_utils.rb:19-37`), when no `shopify_id_token` is supplied, falls back to `cookie_session_id(cookies)` — this branch exists for both the embedded and non-embedded paths. [3](#0-2) 
4. `cookie_session_id` performs no HMAC, no JWT, no signature check — it is a pass-through of the raw cookie value: `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]`. [4](#0-3) 

Attacker's exact request: send any HTTP request to the host app with no `Authorization` header and a `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` header (or `victim-shop.myshopify.com_<known_user_id>` for an online session). Since `"offline_#{shop}"` requires only the public `myshopify.com` domain, this value is 100% attacker-computable with zero secret knowledge. `current_session_id` returns this string verbatim as the "session id" to the host app, which (per the gem's own documented pattern in `docs/usage/oauth.md`, where the returned `cookie.value`/`session` are stored and later looked up verbatim by ID) will resolve it to the victim shop's real, previously persisted `Session` object — including its live `access_token` — and use it to serve the attacker's request as if it came from the victim shop.

None of the existing guards apply on this path: `HmacValidator.validate` and the OAuth `state` check only run during the callback (`lib/shopify_api/auth/oauth.rb:64-71`), not on this cookie-fallback lookup; `JwtPayload`'s `aud`/`exp` checks never execute because no JWT is presented; `Context.embedded?` only selects which branch of `current_session_id` runs, it does not add verification to the cookie branch itself.

### Impact Explanation
An attacker who knows only a shop's public `myshopify.com` domain (or a staff user's numeric id, for online sessions) can cause a vulnerable host app to treat the attacker's request as an authenticated session belonging to that shop, exposing the shop's real access token's worth of privileges (reading/writing orders, customers, products, etc.) to the attacker — a cross-tenant access issue. This is repeatable against any shop that has completed OAuth with the app, at zero cost per attempt, since offline session IDs require no guessing at all.

### Likelihood Explanation
Preconditions: the host app must use cookie-based session lookup (the gem's own documented pattern for non-embedded apps, and a permitted fallback branch for embedded apps per `current_session_id`) and must have a previously stored session for the targeted shop (i.e., the victim already installed the app). No app secret, access token, or victim interaction is required — the attacker only needs the shop's domain, which is public. This makes the attack cheap, deterministic, and repeatable against every installed shop for offline sessions.

### Recommendation
Do not use deterministic, publicly-derivable strings as session lookup keys placed in unsigned cookies. Either (a) generate `Session#id` as a cryptographically random value (e.g. `SecureRandom.uuid`, as already used as a fallback in `Session#initialize` when `id` is not passed) instead of the deterministic `"offline_#{shop}"` / `"#{shop}_#{user_id}"` format when that ID will be stored client-side, or (b) sign/HMAC the cookie value (and verify the signature in `cookie_session_id`) so `SessionUtils.cookie_session_id` cannot be satisfied by an attacker-forged value.

### Proof of Concept
```ruby
# test/utils/session_utils_forged_cookie_test.rb
require "test_helper"

class SessionUtilsForgedCookieTest < Test::Unit::TestCase
  def test_offline_session_cookie_value_is_publicly_derivable
    shop = "victim-shop.myshopify.com"

    # 1. Simulate the legitimate flow: OAuth completes for the victim shop.
    access_token_response = ShopifyAPI::Auth::Oauth::AccessTokenResponse.from_hash(
      "access_token" => "real-secret-token",
      "scope" => "read_products",
    )
    legit_session = ShopifyAPI::Auth::Session.from(shop: shop, access_token_response: access_token_response)

    # Binding under test, LHS = what the gem stored as the cookie value:
    stored_cookie_value = legit_session.id

    # 2. Attacker independently computes the same value with zero secret knowledge.
    forged_cookie_value = ShopifyAPI::Utils::SessionUtils.offline_session_id(shop)

    # Equality holds -> cookie value is not a secret, purely derived from public shop domain.
    assert_equal(stored_cookie_value, forged_cookie_value)

    # 3. Attacker sends forged cookie, no Authorization header, non-embedded (or embedded fallback) path.
    ShopifyAPI::Context.stubs(:embedded?).returns(false)
    cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

    returned_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

    # cookie_session_id performs no verification: returned id equals attacker's forged value,
    # and it also equals the ID under which the victim's real session (with access_token) is stored.
    assert_equal(forged_cookie_value, returned_id)
    assert_equal(legit_session.id, returned_id)
  end
end
```
This demonstrates, entirely within this repo's own classes (`ShopifyAPI::Auth::Session`, `ShopifyAPI::Utils::SessionUtils`), that the value an attacker can compute unaided is byte-for-byte identical to the lookup key under which the victim's authenticated session (and access token) is stored — confirming `cookie_session_id` provides no authentication guarantee.
