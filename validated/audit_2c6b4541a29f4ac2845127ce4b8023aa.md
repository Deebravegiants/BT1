### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are all read from unauthenticated HTTP headers that are never part of the signed bytes. `Registry.process` accepts any request whose body HMAC validates, then trusts `request.shop` (from the header) when constructing `WebhookMetadata` passed to the app's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string`, i.e. the raw body — it never incorporates the shop header into the signature check: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC, then forwards `request.shop`, `request.topic`, and `request.webhook_id` — all header-derived, unauthenticated values — to the app's handler as trusted metadata: [4](#0-3) 

The broken identity binding is:
`shop domain that produced the HMAC-signed body` ≠ `shop domain the SDK reports to the handler in WebhookMetadata#shop`

An unprivileged internet user who controls any Shopify store can subscribe that store to a webhook topic, capture a genuine `(raw_body, hmac)` pair that Shopify computed with the app's real `client_secret`, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` still succeeds because it only checks the body against the same secret — it has no knowledge of, or binding to, the shop header. `Registry.process` then invokes the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value while `body` is genuine attacker-owned-shop data: [5](#0-4) 

Any app whose webhook handler uses `data.shop` to key storage, lookups, or side effects (a documented, expected usage pattern for this SDK) will attribute/write attacker-controlled data under a victim shop's identity, or trigger shop-scoped side effects (e.g. `customers/redact`, `shop/redact` mandatory handlers) against a shop the attacker doesn't own.

### Impact Explanation
This breaks the tenant boundary the webhook signature is supposed to enforce: any handler that trusts `WebhookMetadata#shop` as the authenticated source of the payload can be made to process attacker-supplied body content under an arbitrary victim shop identity, since the HMAC never binds `shop` to the signed bytes. This is a cross-tenant confusion/injection vulnerability reachable by any unprivileged internet user who can install/operate their own Shopify development store to obtain a validly-signed webhook.

### Likelihood Explanation
Medium-High: the attacker needs only their own shop (a free/dev store) to generate a legitimately-signed webhook body, and full control over which HTTP headers they send to the target app's public webhook endpoint — no secrets, tokens, or privileged access to the victim are required.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-verified signable string, or otherwise cryptographically authenticate the header values (e.g., require the caller to independently verify that the header-derived shop is one that is actually registered/expected for the given signed payload) before trusting `WebhookMetadata#shop` in `Registry.process`.

### Proof of Concept
1. Register a personal development store `attacker.myshopify.com` with the target app and subscribe to any webhook topic (e.g. `orders/create`).
2. Trigger the webhook; capture the raw request body and the `x-shopify-hmac-sha256` header — this HMAC is valid for that exact body under the app's real `client_secret`.
3. Replay a POST to the app's webhook endpoint with the identical body and `x-shopify-hmac-sha256` header, but set `x-shopify-shop-domain: victim-shop.myshopify.com`, and `x-shopify-webhook-id`/`x-shopify-topic` as desired.
4. `Utils::HmacValidator.validate` in `Registry.process` passes (body/HMAC unchanged), and the handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload originated from and was signed for the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
