### Title
Permanent freezing of cross-chain escrow when the redeeming solver/beneficiary is blacklisted by the escrowed ERC-20 - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` (and its Tron-fork twin `IntentGatewayV2.withdraw()`) releases escrowed order funds with a single push-style `safeTransfer`/raw `.call` to a `beneficiary` address that is not controlled by the party paying the cost of a stuck transfer — it is either the order's own `output.beneficiary` or, for cross-chain fills, the **solver** address baked into the `RedeemEscrow` message. If that address is blacklisted by a blacklist-capable token (USDT/USDC-style), the transfer reverts every time the message is delivered, and there is no pull-based claim or beneficiary-redirect fallback, unlike the analogous relayer-fee module which explicitly supports beneficiary redirection.

### Finding Description
`_withdraw()` iterates the withdrawal request's tokens and pushes them straight to `beneficiary` via `IERC20(token).safeTransfer(beneficiary, amount)` [1](#0-0) , and pays out any accumulated protocol fee to the same address [2](#0-1) . The Tron fork of the same contract uses an equivalent low-level `.call` push pattern that reverts with `TransferFailed()` on failure [3](#0-2) .

For a cross-chain fill, the beneficiary of this withdrawal is not the order's user — it is the **solver** who filled the order on the destination chain: `_fillCrossChain` encodes `bytes32(uint256(uint160(msg.sender)))` (the solver) as the beneficiary of the `RedeemEscrow` request dispatched back to the source chain [4](#0-3) . When that message is delivered on the source chain, `onAccept` eventually calls `_withdraw`, pushing the escrowed input tokens directly to the solver.

If the input token is USDT/USDC and the solver's address happens to be (or becomes) blacklisted, the `safeTransfer` call reverts every single time the `RedeemEscrow` message is processed. `EvmHost.dispatchIncoming` isolates this failure by deleting the request receipt and returning without reverting the whole batch, explicitly "so that it can be retried" [5](#0-4)  — but retrying the same message with the same blacklisted beneficiary fails identically forever. Unlike the relayer-fee module, which supports a signed `beneficiary_details` redirect so a relayer whose default address is unusable can still claim to an alternate address [6](#0-5) , `IntentsBase`/`IntentGatewayV2` has no such override: the beneficiary embedded in the commitment/body is immutable, so the escrowed input tokens on the source chain become permanently undeliverable and stuck in the gateway contract.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by an ordinary, unprivileged solver filling a cross-chain intent: once the solver's own address is blacklisted for the escrowed token, the source-chain escrow release can never complete, locking the user's escrowed input funds in the `IntentGatewayV2`/`ExtrinsicIntents` contract indefinitely, with the message stuck in an infinite failing-retry loop rather than a one-off revert.

### Likelihood Explanation
Requires the input token to be a blacklist-capable stablecoin (USDT/USDC, common intent assets) and the filling solver's receiving address to be or become blacklisted — a realistic scenario for any solver operating at scale, or one that could be deliberately triggered by a solver targeting its own future orders, or exploited by regulators/attackers who get a target solver blacklisted after it has filled orders.

### Recommendation
Replace the push-based `_withdraw`/`withdraw` transfer with a pull pattern (credit an internal claimable balance keyed by beneficiary, let the beneficiary or a designated fallback address withdraw separately) or support a signed beneficiary-redirect mechanism analogous to `pallet-ismp-relayer`'s `beneficiary_details`, so a blacklisted recipient does not permanently block release of escrowed funds.

### Proof of Concept
1. Solver fills a cross-chain `Order` whose input asset is USDC; `_fillCrossChain` dispatches `RedeemEscrow` with `beneficiary = solver` [4](#0-3) .
2. Before the message is delivered on the source chain, USDC's issuer blacklists the solver's address (or the solver had already been blacklisted for unrelated reasons).
3. Relayer delivers `RedeemEscrow`; `onAccept` calls `_withdraw`, which calls `IERC20(USDC).safeTransfer(solver, amount)` and reverts [1](#0-0) .
4. `EvmHost.dispatchIncoming` swallows the revert and deletes the receipt, marking the message retryable [5](#0-4) .
5. Every subsequent relay attempt fails identically since `beneficiary` cannot change; the escrowed USDC remains locked in the gateway with no pull-claim or redirect path available.
