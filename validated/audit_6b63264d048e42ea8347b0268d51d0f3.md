### Title
Ambiguous `'-'`-delimited StateMachine ID parsing allows dest/source identifier spoofing — (File: `modules/ismp/core/src/host.rs`)

### Summary
`StateMachine`'s `FromStr` implementation reconstructs a chain identifier by naive `str::split('-')` on a string that was itself built by simple concatenation (`Display` uses `format!("{PREFIX}-{id}")`), exactly the pattern the httparty advisory flags: a delimiter character (`-`) that can legitimately appear *inside* the untrusted payload (the `Substrate`/`Tendermint`/`Relay` variants carry an arbitrary 4-byte identifier, not an ASCII-only, hyphen-free value) is never escaped before being embedded into the delimited string, and the parser blindly takes `.last()` / a fixed positional segment instead of length-prefixed or otherwise unambiguous decoding.

### Finding Description
`StateMachine::fmt` builds the wire-format identifier by string concatenation: [1](#0-0) 

`StateMachine::from_str` reverses this by splitting on `'-'` and taking `.last()` (for `SUBSTRATE-`/`TNDRMINT-`) or a fixed index (`values.get(1)` for `RELAY-`): [2](#0-1) 

The `Substrate`/`Tendermint`/`Relay` identifiers are raw 4-byte arrays, only required to be valid UTF‑8 — nothing prevents one of those bytes from being `0x2D` (`'-'`). When such an id is round-tripped through `Display`→`FromStr`, the extra embedded hyphen shifts the split boundaries: `.last()` returns only the bytes after the final `'-'`, not the full original 4-byte id. This is the identical bug class described in the CVE — an unescaped delimiter character inside a user/attacker-influenced sub-field corrupts the boundaries of an adjacent field when the two are concatenated and later re-parsed, letting one crafted string decode into a different logical identity than intended (or letting two different byte sequences decode into the same identity).

This parsing path is exercised on data that originates from cross-chain messages, not just static config: `abi.rs` converts `PostRequestEvent`/`GetRequestEvent`/`PostRequest` structs — decoded straight from `EvmHost`/`HandlerV2` ABI-encoded `source`/`dest` byte fields — back into `router::PostRequest`/`router::GetRequest` via exactly this `StateMachine::from_str` call: [3](#0-2) [4](#0-3) 

`source`/`dest` on `PostRequest`/`GetRequest` are attacker-chosen `bytes` supplied by whatever unprivileged contract calls `dispatch` on `EvmHost`; nothing in the ABI decoding path validates that these bytes are free of embedded `-` before they are turned into a `String` and fed to `FromStr`. The same ambiguous `FromStr` is also relied on by relayer components that route messages by `StateMachine` key (e.g. `clients.get(&dest_chain)`): [5](#0-4) 

### Impact Explanation
Because two distinct id byte-strings can collapse to the same parsed `StateMachine` value (or a single legitimate id containing an embedded `-` can silently mis-decode to a truncated/incorrect id), any component that keys routing, consensus-client lookup, or delivery decisions off the *parsed* `StateMachine` rather than the raw committed bytes can be tricked into treating a message as coming from/going to a different chain than what is embedded in the commitment. This maps to "a route unable to deliver messages" / "unsound state commitment" — a dispatcher can craft a `dest`/`source` byte string whose textual representation collides with another registered `StateMachine`, causing messages to be misrouted to the wrong consensus client/module or rejected/dropped by relayers that route on the parsed value while the on-chain commitment hash (computed over the raw bytes) still matches the original request.

### Likelihood Explanation
The `Substrate`/`Tendermint`/`Relay` id bytes are 4 raw bytes with no restriction against containing `0x2D`, and any application dispatching a request through `EvmHost`/`HandlerV2` fully controls the `source`/`dest` bytes of its own `PostRequest`/`GetRequest`. Triggering the collision only requires choosing 4 bytes that are valid UTF‑8 and contain a hyphen at the wrong position — no privileged access, governance, or malicious-node assumption is needed, satisfying the "unprivileged message dispatcher" reachability bar.

### Recommendation
Do not use character-delimited splitting to decode `StateMachine` ids. Either:
- Encode the fixed-length id fields (`Substrate`/`Tendermint`: 4 bytes, `Relay`: 4-byte relay tag + numeric id) with an unambiguous, length-prefixed format instead of `PREFIX-<raw-bytes>` string concatenation, or
- Reject/escape any embedded delimiter byte (`0x2D`) in the 4-byte id before formatting, and parse by taking a fixed number of bytes after the known-length prefix rather than splitting on `'-'` and using `.last()`/positional indexing.

### Proof of Concept
1. An unprivileged contract calls `EvmHost.dispatch(...)` (or `HandlerV2` delivery path) with a `PostRequest.dest` set to the bytes `SUBSTRATE-` + `[0x41, 0x2D, 0x43, 0x44]` (i.e. `"SUBSTRATE-A-CD"` as UTF‑8, where the 4-byte consensus id is `A-CD`).
2. On decode, `abi.rs`'s `TryFrom<PostRequest>` converts `dest` to the string `"SUBSTRATE-A-CD"` and calls `StateMachine::from_str`.
3. `from_str`'s `SUBSTRATE-` arm does `name.split('-').last()`, which returns `"CD"` (2 bytes) instead of the intended 4-byte id `"A-CD"`. Depending on other candidate ids, a different, independently-registered `[0x-D,0x43,0x44,x]`-style id can be crafted to make `.last()` produce an identical 4-byte tail to a different legitimate id, causing the message to resolve to a `StateMachine::Substrate` value that does not match the id encoded in the original committed request bytes, while relayers/pallet routing logic key off this parsed value for consensus-client selection and delivery.
