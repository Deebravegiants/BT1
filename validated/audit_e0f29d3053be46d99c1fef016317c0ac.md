### Title
DirectBridge reports `completed` for `ft_withdraw`+`msg` intents without verifying the `ft_transfer_call` outcome - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
When a NEAR withdrawal is routed through `DirectBridge` with a non-empty `msg` (via `createNearWithdrawalRoute(msg)`), the emitted `ft_withdraw` intent becomes a `ft_transfer_call` with `min_gas` intentionally omitted. `describeWithdrawal` unconditionally reports `{status: "completed", txHash: args.tx.hash}` as soon as the NEAR intent transaction is included, without inspecting whether the receiver's `ft_on_transfer` refunded or redirected the tokens.

### Finding Description
The broken equality: "tokens credited to `destinationAddress` == `amount` requested" is never checked before the SDK reports `completed`.

Code path:
- `createNearWithdrawalRoute(msg)` sets `routeConfig = { route: RouteEnum.NearWithdrawal, msg }` [1](#0-0) .
- `DirectBridge.createWithdrawalIntents` forwards `msg` straight into `createWithdrawIntentPrimitive` [2](#0-1) .
- `createWithdrawIntentPrimitive` builds an `ft_withdraw` intent with `msg` set and `min_gas: undefined` whenever `msg !== undefined`, only logging a warning that "gas consumption is unpredictable" [3](#0-2) . Setting `msg` on an NEP-141 `ft_withdraw` causes the underlying token contract to perform `ft_transfer_call` rather than a plain `ft_transfer`, meaning the receiver's `ft_on_transfer` callback governs how many tokens are actually retained by `destinationAddress` (it may return any unused amount, which gets refunded).
- `validateWithdrawal` only checks that `destinationAddress` is a valid NEAR account, exists, and isn't the token contract itself — it does nothing to validate the semantics of `msg` or the receiver's callback behavior [4](#0-3) .
- `describeWithdrawal` for `DirectBridge` unconditionally returns `completed` using the already-known NEAR intent tx hash, with no receipt/outcome inspection: [5](#0-4) .
- `watchWithdrawal` treats any `completed` status as final and resolves the polling loop, surfacing the tx hash to the caller of `processWithdrawal` [6](#0-5) .

Because the outer NEAR transaction that dispatches `ft_withdraw`/`ft_transfer_call` succeeds regardless of what the asynchronous `ft_on_transfer` callback on the receiving contract eventually does (a callback returning an "unused amount" does not fail the top-level transaction), the SDK's "completed" status is decoupled from whether `destinationAddress` actually ended up holding `amount` tokens.

### Impact Explanation
An integrator or the SDK caller who forwards attacker-supplied `routeConfig.msg` (e.g., a counterparty's payload in an OTC/settlement flow) can cause the SDK to report a withdrawal as `completed` with a valid `txHash`, while the funds were partially or fully refunded/redirected by the receiving contract's `ft_on_transfer` logic. This is a status misreport that could lead an integrator to credit a user (or itself) as if the withdrawal succeeded, matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. It is repeatable on every withdrawal that uses `createNearWithdrawalRoute(msg)` with a NEP-141 `assetId`.

### Likelihood Explanation
Preconditions: caller/integrator must pass a non-empty `msg` via `createNearWithdrawalRoute`, targeting a NEP-141 `assetId` (e.g. `nep141:btc.omft.near`), with a `destinationAddress` that is a deployed contract whose `ft_on_transfer` can be crafted to refund/redirect. This requires no special privilege — any unprivileged caller of `IntentsSDK.processWithdrawal`/`createWithdrawalIntents` with their own funds, or any integrator that blindly forwards a counterparty-controlled `msg`, can trigger it. The cost is a single withdrawal transaction.

### Recommendation
`DirectBridge.describeWithdrawal` should not report `completed` purely from tx inclusion when `msg` was used. It should inspect the NEAR transaction's execution outcome/receipts for the `ft_transfer_call`/`ft_on_transfer` result (e.g., check for a refund transfer event or the returned "unused amount") before declaring the withdrawal `completed`, or otherwise require an explicit `min_gas`/success confirmation path when `msg` is set.

### Proof of Concept
vitest plan (mock only HTTP/RPC, per repo test patterns in `direct-bridge.test.ts`):
1. Call `createWithdrawIntentPrimitive({ assetId: "nep141:btc.omft.near", destinationAddress: "attacker.near", amount: 1000n, storageDeposit: 0n, msg: "malicious-msg" })` and assert the returned intent has `msg: "malicious-msg"` and `min_gas: undefined` (asserting the first side of the equality: nothing constrains actual delivered amount).
2. Construct a `WithdrawalIdentifier` with an arbitrary `tx.hash` and call `DirectBridge.prototype.describeWithdrawal(wid)`; assert it returns `{status: "completed", txHash: wid.tx.hash}` unconditionally, with no call to any RPC to check receipts/refunds — demonstrating the SDK cannot distinguish a full refund from a successful transfer.
3. Assert `amount credited to destinationAddress` (simulated as 0 due to refund) !== `args.withdrawalParams.amount` (1000n) while `describeWithdrawal` still reports `completed`, proving the invariant is violated.

	async validateWithdrawal(args: {
		assetId: string;
		amount: bigint;
		destinationAddress: string;
		logger?: ILogger;

		if (validateAddress(args.destinationAddress, Chains.Near) === false) {
			throw new InvalidDestinationAddressForWithdrawalError(
				args.destinationAddress,
				Chains.Near,
			);
		}

		const { contractId: tokenAccountId } = utils.parseDefuseAssetId(
			args.assetId,
		);

		if (
			compareAddresses(tokenAccountId, args.destinationAddress, Chains.Near)
		) {
			throw new DestinationAddressMatchesTokenAddressError(
				tokenAccountId,
				args.assetId,
			);
		}

		// Only check account existence for explicit (named) accounts
		if (
			utils.isImplicitAccount(args.destinationAddress) === false &&
			(await this.getCachedAccountExistenceCheck(args.destinationAddress)) ===
				false
		) {
			throw new DestinationExplicitNearAccountDoesntExistError(
				args.destinationAddress,
			);
		}

		return;
	}
