## Title
Unbounded gas forwarding in `EvmHost.dispatchIncoming()` allows a gas-griefing attack that can revert an entire batched message delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming()` forwards messages to destination applications via a plain, un-gas-capped low-level `.call()`, and `HandlerV2.handlePostRequests`/`handleGetResponses` invoke this function in a loop for every request in a relayer's batch. Because the destination address of a request is fully controlled by the original dispatcher (anyone can call `IDispatcher.dispatch()` and set `to` to any address, including a contract they deployed themselves), an attacker can seed a batch with malicious "app" contracts engineered to consume ~63/64 of whatever gas is forwarded to them (the EIP-150 retention rule). Chaining a handful of such malicious deliveries inside the same relayer transaction exponentially drains the remaining gas of the enclosing `handlePostRequests`/`handleGetResponses` call until it genuinely runs out of gas, which reverts the *entire* batch — including every honest, unrelated request bundled in it — rather than merely failing the one malicious delivery gracefully as designed.

### Finding Description
`EvmHost.dispatchIncoming` resolves the destination purely from attacker-supplied request data and calls it with no gas stipend: [1](#0-0) 

The intended failure mode is graceful: if the destination call fails, the receipt is deleted and the function `return`s without reverting, allowing the batch to continue. This works for an ordinary revert, but it does not protect against gas exhaustion, because the low-level `.call` by default forwards all but 1/64th of the currently available gas (EIP-150). A destination contract that deliberately loops until `gasleft()` is nearly zero can consume essentially everything it was handed.

`HandlerV2.handlePostRequests` and `handleGetResponses` call `dispatchIncoming` in a loop over a caller-supplied batch, once per proven request/response, all within a single transaction and without any per-call gas cap: [2](#0-1) [3](#0-2) 

The `to` field of a `PostRequest` (and therefore the destination `dispatchIncoming` calls into) is set by whoever originally dispatched the request via `EvmHost.dispatch(DispatchPost)`, which is a fully permissionless, unprivileged entry point that only requires paying the (optional) relayer fee: [4](#0-3) 

Because destination selection is attacker-controlled and gas is never bounded per delivery, an attacker can:
1. Deploy a malicious contract on the destination chain whose `onAccept`/`onGetResponse` loops until it has burned ~63/64 of whatever gas is forwarded to it.
2. Dispatch several such requests (paying the modest fee token cost) targeting that contract.
3. Wait until a relayer batches these together with legitimate, unrelated user messages in one `handlePostRequests`/`handleGetResponses` call (batching many proofs into a single MMR-verified transaction is the documented, expected relayer behavior for gas efficiency).
4. As the loop processes the malicious entries one after another, the transaction's remaining gas shrinks by a factor of ~1/64 at each malicious call. After only a few such entries, the amount of gas left for the handler's own bookkeeping (storage writes, event emission, or even initiating the next `CALL`) becomes insufficient, causing a genuine out-of-gas exception in the handler itself rather than a caught `success == false` in the nested call.

Unlike the intended failure path (`if (!success) { delete ...; return; }`), an out-of-gas exception raised in the *caller's own frame* (not inside the nested low-level call) is not caught anywhere in `dispatchIncoming` or the `handlePostRequests`/`handleGetResponses` loop — there is no `try/catch`, so it propagates and reverts the whole transaction, undoing delivery of every other (honest) request bundled in that same batch.

### Impact Explanation
This is a denial-of-service / griefing vector against message delivery, not merely against the attacker's own request:
- Honest users' cross-chain POST requests/GET responses bundled by a relayer into the same `handlePostRequests`/`handleGetResponses` transaction can be forced to fail atomically, denying delivery of legitimate, already-proven messages (including token bridge mints/burns and intents fills that rely on this delivery path).
- Relayers waste real gas expenditure on reverted transactions, degrading protocol liveness and relayer economics, and repeated griefing can stall a route's message delivery, matching the "route unable to deliver messages" acceptance criterion.
- The cost to the attacker is low (fee-token cost of a few dispatches plus deployment of a simple gas-bomb contract), while the damage scales with how much relayers batch (which the protocol explicitly optimizes for).

### Likelihood Explanation
The `to` destination of a POST/GET is entirely attacker-controlled through the permissionless `dispatch()` entry point, requiring no special privilege beyond paying a fee. Gas-griefing via nested calls retaining 63/64 gas is a well-understood, easily reproducible Solidity pattern. Relayers batching multiple proven requests into one transaction is the documented normal operating mode (`batchCall`/`PostRequestMessage` support arrays of leaves), so exploitation only requires an attacker to get a malicious request accepted into the same batch as other pending deliveries, which a relayer processing a queue of pending proofs would ordinarily do without additional on-chain protection against this pattern.

### Recommendation
Cap the gas forwarded to destination applications in `EvmHost.dispatchIncoming` (both the `PostRequest` and `GetResponse` overloads) to a fixed, protocol-defined stipend (e.g. `.call{gas: MAX_APP_GAS}(...)`), so a single malicious destination can never consume more than a bounded amount of the enclosing transaction's gas regardless of how many malicious entries are chained in one batch. This mirrors the report's core recommendation of validating/bounding a caller-influenceable gas parameter before it is used to drive an external call.

### Proof of Concept
1. Deploy `EvilApp` implementing `IApp` where `onAccept` runs `while(gasleft() > 1000) {}` (or any loop that consumes almost all forwarded gas) before returning normally (so it is a valid, non-reverting call — the DoS comes from gas exhaustion, not from an explicit revert).
2. From an unprivileged account, call `EvmHost.dispatch(DispatchPost{ to: abi.encodePacked(evilApp), ... })` several times (e.g. 3-4 times) with the minimum required relayer fee, on the source chain, targeting `EvilApp` on the destination chain.
3. Also have a legitimate user dispatch an ordinary POST request in parallel.
4. Once all requests are provable, have a relayer submit a single `HandlerV2.handlePostRequests` call whose `PostRequestMessage.requests` batches the legitimate request together with the several `EvilApp` requests.
5. Observe that as `dispatchIncoming` is invoked for each `EvilApp` entry, forwarded gas shrinks by ~63/64 each time; after a small number of entries, the `handlePostRequests` transaction reverts with out-of-gas, and the legitimate request is not delivered even though its proof was valid and it consumed no unusual gas itself.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
