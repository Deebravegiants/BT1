### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook HMAC over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values used by the handler are read directly from unauthenticated HTTP headers. Any party capable of obtaining one validly-signed webhook payload for the shared app secret can replay that exact body with a forged `X-Shopify-Shop-Domain` header, and the signature check will still pass — because the header is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled straight from headers that are never mixed into the HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e. the body) and compares it with the header-supplied `hmac`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof that the entire request — including `request.shop` — is authentic, and hands it straight to the app's handler: [4](#0-3) 

The intended binding is: `shop bound to verified HMAC == shop the handler acts on`. In reality: `HMAC binds only raw_body`, and `shop` is an independent, unauthenticated header value. Any app installed on multiple shops shares the same `api_secret_key`. A merchant who installs the app on their own store (shop A) legitimately receives a correctly-signed webhook (body + valid HMAC, both signed with the app's shared secret). That merchant can then POST the exact same body and HMAC to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed to a victim shop B. `HmacValidator.validate` still succeeds because it never inspects the shop header, and `Registry.process` calls the handler with `shop: request.shop == "shop-B"`, `body` matching the payload signed for shop A. Any app logic keyed off `data.shop` (e.g. GDPR data-request/erasure webhooks, uninstall webhooks, order/customer processing tied to a shop record) is now executed under shop B's identity using attacker-controlled body content, from a party who was never authorized for shop B.

### Impact Explanation
This breaks tenant isolation: an unprivileged attacker who legitimately installs the app on a shop they control can trigger webhook-driven side effects that the app attributes to an arbitrary victim shop, since the shop identity is unauthenticated while only the body is authenticated. This is cross-tenant access/data confusion driven entirely by unprivileged use of the gem's documented `Webhooks::Request`/`Registry.process` flow — no leaked secret or privileged account is required beyond having any app installation.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled shop (standard, unprivileged), (2) capturing one legitimately delivered webhook (any topic the app subscribes to) sent to that shop, and (3) replaying it to the app's public webhook endpoint with a modified shop-domain header. No cryptographic secret needs to be recovered; the attacker reuses a signature Shopify itself generated for them.

### Recommendation
Bind the shop identity to the verified request rather than trusting the header independently: include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or have `Utils::HmacValidator`/`Webhooks::Request` require the app to look up and pin the expected shop for a given webhook subscription instead of trusting `shopify-shop-domain` as authoritative post-HMAC-success.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; Shopify sends a legitimately HMAC-signed webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's `api_secret_key`).
2. Attacker replays the identical body `B` and header `H` to the same webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds a request whose `hmac` still equals `H` and whose `to_signable_string` is still `B`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` and matches `H` → returns `true`. [5](#0-4) 
5. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker-signed body `B`, even though `victim.myshopify.com` never sent or authorized this webhook.

          received_signature = verifiable_query.hmac
