### Title
`superApprove` in `HyperFungibleTokenImpl` grants unlimited ERC-20 approval to any caller for any owner, enabling theft of bridged token balances - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl` is deployed as a real fungible/bridge token contract (referenced from the production deployment script `evm/script/DeployIsmp.s.sol` and `evm/src/utils/TokenFaucet.sol`), not confined to test helpers. It exposes a `public` function, `superApprove(address owner, address spender)`, that sets an unlimited ERC-20 allowance (`type(uint256).max`) from an arbitrary `owner` to an arbitrary `spender`, with **no access control whatsoever** — no `onlyRole`, no `msg.sender == owner` check.

### Finding Description [1](#0-0) 

```solidity
/**
 * @notice Helper function for tests - approves unlimited tokens
 * @param owner The owner of the tokens
 * @param spender The spender address
 */
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
```

Unlike the mint/burn paths in the same contract, which are properly gated behind `MINTER_ROLE`/`BURNER_ROLE`: [2](#0-1) 

`superApprove` performs no authorization check at all. Anyone can call `superApprove(victim, attacker)` to grant `attacker` an unlimited allowance over `victim`'s token balance, then immediately call `transferFrom(victim, attacker, balance)` to drain the victim's entire holding of this token. This is analogous to the "revocable grants" report's root issue — a privileged fund-moving operation (there, revoke-and-seize vesting tokens; here, unrestricted approval-and-drain) that is reachable without the intended authorization gate, resulting in unbacked transfer of another party's funds.

The contract is wired into deployment tooling: [3](#0-2) 
and `evm/script/DeployIsmp.s.sol`, meaning it is not exclusively a test double — if deployed as a live fee token or bridged asset, every holder's balance is at risk from any unprivileged address.

### Impact Explanation
Any unprivileged address can drain the full token balance of any holder of a `HyperFungibleTokenImpl`-based token by calling the unauthenticated `superApprove` followed by `transferFrom`. This is a direct, concrete theft-of-funds primitive with no precondition beyond the victim holding a nonzero balance — satisfying "concrete theft ... of funds" reachable from a single unprivileged transaction.

### Likelihood Explanation
High, if this contract is used for any live/production token deployment (fee token, bridged asset, or via `TokenFaucet`). The function is `public`, requires no special role, and the exploit is a two-call sequence (`superApprove` + `transferFrom`) available to any external account.

### Recommendation
- Remove `superApprove` entirely from any contract that could be deployed to a live network, or
- Restrict it to test-only build artifacts (e.g., a separate `Mock`/`Test` contract not referenced by `DeployIsmp.s.sol` or `TokenFaucet.sol`), and/or
- If retained for legitimate test tooling, gate it with `onlyRole(DEFAULT_ADMIN_ROLE)` and/or require `msg.sender == owner`.

### Proof of Concept
1. Deploy/observe a `HyperFungibleTokenImpl`-based token where `victim` holds a nonzero balance.
2. Attacker calls `token.superApprove(victim, attacker)` — no revert, since there is no access control.
3. Attacker calls `token.transferFrom(victim, attacker, token.balanceOf(victim))`, draining the victim's entire balance. [1](#0-0)
