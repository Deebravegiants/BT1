## Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
This is the same bug class as the CtrlChar report: a field that downstream logic trusts as authenticated is never included in the value that is actually cryptographically verified. In the report, `simulationResult` was displayed as trusted even though it was never part of any signature. In this gem, `ShopifyAPI::Webhooks::Request#shop` (and `topic`, `webhook_id`, `api_version`) are taken directly from HTTP headers and handed to the webhook handler as authenticated tenant context, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The headers that carry tenant identity are parsed independently and are not part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string` (i.e., the raw body) using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC check passes, then constructs `WebhookMetadata` using `request.shop` — an unauthenticated header value — as the tenant identity handed to the app's handler: [4](#0-3) 

The equality that should hold is: `shop asserted to the handler == shop cryptographically bound to the signed payload`. Instead: `shop asserted to the handler == x-shopify-shop-domain header (unauthenticated)`, while `HMAC verifies == raw_body only`. Since `api_secret_key` is a single shared secret for the whole app (not per-shop), any tenant that can legitimately trigger a webhook for their own store obtains a `(raw_body, hmac)` pair that is valid HMAC-wise regardless of which shop domain header accompanies it. That pair can be resubmitted with a different `x-shopify-shop-domain` header, and `HmacValidator.validate` still returns true because the header is never part of `to_signable_string`.

### Impact Explanation
This breaks the tenant/shop identity binding that host applications rely on `ShopifyAPI::Webhooks::Registry.process` to enforce. A malicious merchant (an "unprivileged" tenant relative to other merchants using the same app) can:
1. Trigger a webhook delivery on their own shop to obtain a body they control together with a validly-computed HMAC for that body (computed with the app's shared secret).
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and `webhook-id`/`topic`) with a victim shop's domain.
3. `Registry.process` will pass HMAC validation and invoke the handler with `WebhookMetadata.shop` set to the victim's shop, causing the host application to process attacker-supplied data under another tenant's identity.

Depending on how the host app keys sessions/data by `WebhookMetadata#shop` (a documented, expected usage of this gem's webhook API), this enables cross-tenant data corruption or injection of attacker-controlled data into another merchant's records — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires being a legitimate (even free/trial) merchant installer of the target app — no access to `api_secret_key`, access tokens, or privileged credentials is needed, and no TLS interception or social engineering is required. The attacker only needs to observe one webhook delivery for their own shop and replay it with a modified header, which is fully within reach of any user who can install the app.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the request (e.g., cross-check `request.shop` against the shop associated with the specific webhook subscription/registration rather than trusting the header verbatim). At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a tenant-selection key without an independent authorization check.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and receives a legitimate webhook there.
raw_body = '{"id": 1}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Same (raw_body, hmac) pair, but header claims a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # unauthenticated, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HmacValidator.validate (only raw_body is checked) and calls handler.handle
#    with WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)
```
