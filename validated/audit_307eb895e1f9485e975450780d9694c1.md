### Title
Wallet Contract uses a hardcoded, build-time-baked `CHAIN_ID` instead of the on-chain genesis chain id, enabling cross-chain replay of signed Ethereum-style transactions - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs)

### Summary
The Near Wallet Contract (used to let Ethereum-style ECDSA keys control an eth-implicit NEAR account via a relayed, RLP-encoded `Transaction2930`) validates the `chain_id` field of every relayed transaction against a compile-time constant baked into the WASM binary at build time, rather than reading the actual chain/network identity dynamically from the runtime. This is the same bug class as the reported Brink `EIP712SignerRecovery.sol` issue: a "unique" chain identifier is supplied by the deployer/build process instead of being derived from the chain itself, creating a cross-chain replay risk for signed messages.

### Finding Description
`CHAIN_ID` is defined as a compile-time constant loaded from a text file at build time: [1](#0-0) 

This value is used as the sole discriminator to validate that a relayed Ethereum-style transaction was intended for "this" chain: [2](#0-1) 

The build script (`runtime/near-wallet-contract/build.rs`) compiles three separate WASM artifacts with three hardcoded constants — mainnet (397), testnet (398), and, critically, a single shared `LOCALNET_CHAIN_ID = 399` for every non-official/local deployment: [3](#0-2) 

Unlike Ethereum's `block.chainid`, which is a protocol-level value unique per network and readable on-chain, NEAR already exposes an actual on-chain, genesis-derived chain identity through the `chain_id` host function (verified end-to-end by `test-loop-tests/src/tests/chain_id.rs`, which shows a contract calling `chain_id` and getting back the genesis-configured string, e.g. `"test"`): [4](#0-3) 

The wallet contract does not use this on-chain, genesine-derived value at all. Instead every "localnet"-class deployment (any privately-run NEAR network, sandbox, or bounty/test network that is not the two officially registered mainnet/testnet chains) ships with the exact same hardcoded value `399`, since it is "not officially registered on chainlist.org" and is reused verbatim by the build script for every local/private network.

### Impact Explanation
Because `chain_id` validation only compares against a static, build-baked integer rather than a value unique to the specific chain instance, any two independently operated NEAR-compatible networks that both use the "localnet" wallet-contract build (chain_id 399) will accept the identical set of relayer-forwarded, ECDSA-signed transactions. A user's Ethereum-style signature authorizing a transfer/call on their eth-implicit account on Network A can be captured and replayed verbatim by a relayer/attacker against the user's identically-derived eth-implicit account on Network B, since `validate_tx_relayer_data` only checks `tx.chain_id != Some(CHAIN_ID)` and both networks compile with `CHAIN_ID == 399`. This can result in unauthorized execution of actions (transfers, function calls, or `AddKey`/`DeleteKey` operations via `ADD_KEY_SIGNATURE`/`DELETE_KEY_SIGNATURE`) against the victim's account balance and access keys on the second chain — a genuine unauthorized state/balance change reachable purely through the relayer submitting an RLP-encoded transaction, with no privileged or validator role required.

### Likelihood Explanation
Likelihood depends on the number of distinct "localnet"-class NEAR networks that are simultaneously live and share the same user keys/accounts (e.g., a user testing across two internal testnets, or two bounty/staging networks derived from the same genesis records) — this is a realistic operational scenario for NEAR (multiple sandboxes, forknets, mocknets, and bounty-localnet environments are explicitly part of this repo's tooling, as seen in `tools/bounty-localnet/`). For mainnet vs. testnet the risk is effectively mitigated since chain ids 397/398 are unique and officially registered, mirroring Spearbit's original conclusion that a hardfork changing an established, unique chain id is unlikely. The residual risk is concentrated specifically in the shared, non-unique `LOCALNET_CHAIN_ID = 399` value used across all private/non-official deployments of the Wallet Contract.

### Recommendation
Replace the compile-time `CHAIN_ID` constant with a value read dynamically from the chain itself at execution time — e.g., call the existing `chain_id` host function/env (as exercised in `test-loop-tests/src/tests/chain_id.rs`) or otherwise derive the identifier from genesis config, so that every distinct network instance (including every "localnet" deployment) enforces a value unique to that specific chain rather than a shared hardcoded constant. At minimum, `LOCALNET_CHAIN_ID` should never be reused across independently operated networks.

### Proof of Concept
1. Build/deploy the Wallet Contract on two independent local NEAR networks, both using the default "localnet" build (`LOCALNET_CHAIN_ID = 399`), as done by `runtime/near-wallet-contract/build.rs`.
2. A user generates an eth-implicit account with secret key `sk` and deploys the Wallet Contract to that account address identically on both networks (same derived address since it's derived from the public key, independent of network).
3. The user signs an `aurora_engine_transactions::eip_2930::Transaction2930` with `chain_id: 399` authorizing a transfer, following the pattern used in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/utils/mod.rs::create_signed_transaction`: [5](#0-4) 
4. A relayer submits this same signed transaction via `rlp_execute` to Network A — it succeeds, per `validate_tx_relayer_data`'s check (`tx.chain_id != Some(CHAIN_ID)`, both being 399), consistent with `test_relayer_wrong_chain_id`'s converse behavior where only a mismatched chain id is rejected: [6](#0-5) 
5. The relayer replays the identical signed transaction bytes against Network B's Wallet Contract instance for the same address — since Network B's build also uses `CHAIN_ID = 399`, the `chain_id` check passes there too and the action executes a second time, unauthorized by any fresh user intent for Network B.

// A relayer sending a transaction signed with the wrong chain id is a ban-worthy offense.
#[tokio::test]
async fn test_relayer_wrong_chain_id() -> anyhow::Result<()> {
    let TestContext { worker, mut wallet_contract, wallet_sk, wallet_address, .. } =
        TestContext::new().await?;

    let relayer_pk = wallet_contract.register_relayer(&worker).await?;

    let transaction = aurora_engine_transactions::eip_2930::Transaction2930 {
        nonce: 0.into(),
        gas_price: 0.into(),
        gas_limit: 0.into(),
        to: Some(Address::new(wallet_address)),
        value: Wei::zero(),
        data: [
            crate::eth_emulation::ERC20_BALANCE_OF_SELECTOR.to_vec(),
            ethabi::encode(&[ethabi::Token::Address(wallet_address)]),
        ]
        .concat(),
        chain_id: CHAIN_ID + 1,
        access_list: Vec::new(),
    };
    let signed_transaction = crypto::sign_transaction(transaction, &wallet_sk);

    let result = wallet_contract
        .rlp_execute(wallet_contract.inner.id().as_str(), &signed_transaction)
        .await?;

    assert!(!result.success);
    assert_eq!(result.error.as_deref(), Some("Error: faulty relayer"));

    assert_revoked_key(&wallet_contract.inner, &relayer_pk).await;

    Ok(())
}
