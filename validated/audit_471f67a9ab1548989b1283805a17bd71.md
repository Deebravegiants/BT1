### Title
Stale `total supply` accounting on burn-via-refund allowed overcounted issuance in `pallet-assets` `do_refund` — ([File: substrate/frame/assets/src/lib.rs])

### Summary
The reported class — a balance-reducing operation that fails to update the corresponding total-supply/accounting state — has a direct historical analog in `pallet-assets`: the `refund` extrinsic's `allow_burn = true` path destroyed a user's asset balance without decrementing `AssetDetails.supply`, exactly mirroring the `SelfPeggingAsset::rebase` bug where `poolToken.removeTotalSupply` reduced the buffer without syncing `balances`/`totalSupply`.

### Finding Description
The fix commit is documented at [1](#0-0) : "When a user calls `refund` with `allow_burn = true`, their token balance is destroyed, but the asset's total supply was never updated. This caused `total_issuance()` to overcount." This is confirmed by the `do_try_state` invariant relaxation still present in the code, which explicitly documents the historical mismatch: [2](#0-1)  — the check uses `>=` instead of `==` specifically because "the provided `do_refund` implementation historically destroyed the account balance without decrementing the asset supply... existing on-chain state may still contain overcounted supply from prior refunds," with a `TODO` to migrate and tighten the invariant.

The correctly-fixed pattern, by contrast, is visible in `do_burn` / `decrease_balance`, where the balance debit and the `details.supply` decrement happen atomically inside the same `try_mutate`: [3](#0-2)  and [4](#0-3) . The `refund`'s buggy path failed to follow this same coupling, exactly as in the external report where `rebase` called `poolToken.removeTotalSupply` but never touched `balances`/`totalSupply`.

### Impact Explanation
An overcounted `AssetDetails.supply` breaks the fundamental invariant that supply equals the sum of account balances plus held balances, corrupting any downstream logic (e.g., price/AMM calculations in `pallet-asset-conversion`, DEX precompiles, or off-chain accounting) that trusts `total_issuance()`. The prdoc notes this discrepancy was actually observed on Westend, confirming real on-chain impact, and a follow-up migration issue (#11443) was opened to reconcile the corrupted state.

### Likelihood Explanation
The bug required only an unprivileged, signed user manually calling the `refund` extrinsic with `allow_burn = true` on their own held/refundable balance — no special privilege was needed, per the prdoc: "only users manually submitting the refund extrinsic with the burn flag would hit it." This matches the external report's characterization of an unprotected, externally callable function.

### Recommendation
This specific issue is already fixed per PR #11441, which decrements `supply` and emits a `Burned` event on the `allow_burn` path. The residual risk is only in un-migrated on-chain state predating the fix (tracked in issue #11443) — a supply-recalculation migration should be run to correct any already-corrupted `AssetDetails.supply` values, after which the `do_try_state` check at `substrate/frame/assets/src/lib.rs:2099` can be tightened from `>=` back to `==`.

### Proof of Concept
Historical (pre-fix) sequence, per the prdoc: a user with a refundable/held asset balance calls `refund(asset_id, allow_burn = true)`; the account balance is destroyed but `Asset::<T,I>::get(asset_id).supply` is left unchanged, so `total_issuance()` overcounts by the refunded amount. This is fixed in the current codebase's `refund` implementation (mirroring `do_burn`'s supply decrement), but any chain state produced before the fix (e.g., Westend, per the prdoc) still requires the pending migration.
