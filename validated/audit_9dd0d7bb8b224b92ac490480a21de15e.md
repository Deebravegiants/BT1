### Title
Fraud detection is permanently disabled in the production signup pipeline - ([File: src/plans/mod.rs], [File: src/plans/fraud_check.rs])

### Summary
The `MasterPlan::detect_fraud` function, invoked unconditionally on the production signup path, is hard-coded to always return `Ok(false)`, so no signup is ever flagged as fraudulent, regardless of what the biometric pipeline detects. This mirrors the `ExpiringMarket.isClosed`/`stop` pattern in the referenced report: a control designed to gate/pause a sensitive operation exists syntactically but has been stubbed to a constant value that defeats its purpose.

### Finding Description
`detect_fraud` is called from `do_signup` whenever `skip_fraud_checks()` is `false` (the default production configuration, only overridable via the `allow-plan-mods` dev feature): [1](#0-0) 

The function body itself, however, contains no actual fraud-checking logic — it unconditionally returns `false`: [2](#0-1) 

This is backed by `src/plans/fraud_check.rs`, where the number of fraud checks is hard-coded to `0` and every check-producing function (`fraud_checks`, `enabled_checks_from_config`, `feedback_messages`, `FraudChecks::run`) returns an empty array or an empty `Report`: [3](#0-2) [4](#0-3) [5](#0-4) 

The downstream logic that consumes the fraud result treats every signup as `SignupReason::Normal` since `fraud_detected` is always `false`: [6](#0-5) 

Just as `isClosed()` always returning `false` makes the `can_offer`/`can_buy`/`can_cancel` modifiers' emergency-stop checks vacuous, `detect_fraud` always returning `false` makes the fraud-gating branch in `do_signup` vacuous — the "pause" mechanism for suspicious/fraudulent signups exists in structure but never fires.

### Impact Explanation
Because `fraud_detected` can never be `true`, every completed biometric capture is enrolled and credentials/PCP packages are issued as `SignupReason::Normal`, even for signups that a functioning fraud engine would have flagged (e.g., contact lenses, masks, multiple faces, underage subjects — all enumerated in `PipelineFailureFeedbackMessage` but never actually triggered). This allows misattributed/fraudulent signups to be treated identically to legitimate ones, undermining the biometric uniqueness/fraud-prevention guarantee of the system and enabling issuance of identity credentials that should have been blocked. [7](#0-6) 

### Likelihood Explanation
The vulnerable path is reached on every default production signup — `skip_fraud_checks()` is `false` by default and only settable via the dev-only `allow-plan-mods` feature, so no attacker action or special configuration is required for the disabled check to apply; it is the standing production behavior. [8](#0-7) 

### Recommendation
Restore real fraud-check implementations behind `Report::fraud_checks`/`enabled_checks_from_config`/`feedback_messages` and `FraudChecks::run`, and ensure `detect_fraud` actually computes and returns the pipeline's fraud determination (e.g., via `Report::fraud_detected_with_config`) rather than an unconditional `false`. At minimum, treat the currently-empty fraud engine as fail-closed (block or flag signups) rather than fail-open, and add regression tests asserting that known fraud signals (contact lenses, mask, multiple faces, underage) actually propagate to `SignupReason::Fraud`.

### Proof of Concept
1. Complete a normal signup flow so that `pipeline` is `Some` and `do_signup` reaches the fraud-check branch: [1](#0-0) 
2. Regardless of the biometric pipeline outputs (e.g., simulated contact-lens/mask detection), `detect_fraud` returns `Ok(false)` because its body is stubbed: [9](#0-8) 
3. `signup_reason` is computed as `SignupReason::Normal` (since `fraud_detected` is `false`), and the enrollment/PCP-issuance path proceeds as if no fraud indicators existed: [10](#0-9) 

Note: I could not verify from the index whether any other backend-side (server) fraud gate exists outside `orb-core` that would compensate for this; this analysis is limited to the on-orb code path shown here.
