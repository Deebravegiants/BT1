## Finding confirmed



### Title
Cardano bech32 case-variant bypasses `DestinationAddressMatchesTokenAddressError` in `validateWithdrawal` - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`validateCardanoAddress` in `packages/intents-sdk/src/lib/validateAddress.ts` accepts both all-lowercase and all-uppercase forms of a Cardano bech32 address (per BIP-173, only mixed case is invalid), because `bech32.decode` from `@scure/base` lowercases the whole string internally before checksum/prefix/word extraction. `compareAddresses` for Cardano, however, is `a === b` raw string comparison with no case canonicalization. An attacker can submit the token contract's own address in all-uppercase as `destinationAddress`; it passes `validateAddress`, but `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, "cip34:...")` returns `false` because the stored `origin_chain_address` is lowercase, so `DestinationAddressMatchesTokenAddressError` is never thrown.

### Finding Description
The broken equality: for Cardano, if `d` and `t` are different bech32 case-encodings of the same address, `compareAddresses(t, d, Chains.Cardano)` should be `true`, but the implementation performs `return a === b` at `packages/intents-sdk/src/lib/compareAddresses.ts:60`, which is case-sensitive and does not canonicalize bech32 addresses (unlike the special-cased chains: Ethereum via `getAddress`, hex-chains via `normalizeHexAddress`, TON/Tron via dedicated decoders, Stellar via `.toUpperCase()`).

Path:
1. `validateWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:170-259`) first calls `validateAddress(args.destinationAddress, assetInfo.blockchain)` (line 182). For Cardano this dispatches to `validateCardanoAddress` (`packages/intents-sdk/src/lib/validateAddress.ts:475-495`), which does `bech32.decode(address, 120)`, checks `prefix === "addr"`, and validates `addrType` from the decoded bytes. `bech32.decode` in `@scure/base` lowercases the entire string first and only rejects genuinely *mixed*-case strings (BIP-173 behavior) — a fully uppercase address decodes identically to its lowercase counterpart, same prefix, same words/bytes.
2. Later, at line 207-219, the token's own address (`tokenInfo.origin_chain_address`, stored/returned by the PoA bridge API in its canonical lowercase bech32 form) is compared against `args.destinationAddress` via `compareAddresses(tokenInfo.origin_chain_address, args.destinationAddress, assetInfo.blockchain)`.
3. Since Cardano falls into the `a === b` branch (`compareAddresses.ts:57,60`), submitting the uppercase encoding of `tokenInfo.origin_chain_address` makes this comparison `false`, even though it is the exact same on-chain account, so `DestinationAddressMatchesTokenAddressError` is not thrown.
4. `createWithdrawalIntents` then builds and signs the withdrawal intent using the attacker-supplied, differently-cased address as the on-chain destination, which — because Cardano wallets/nodes resolve addresses byte-wise regardless of bech32 text case — routes the withdrawn tokens to the token contract's own address.

Existing guards do not catch this: `validateAddress` accepts the input (format check only, not equality-aware), `compareAddresses` catches thrown errors but here no error is thrown — it simply evaluates a case-sensitive string equality that legitimately diverges from the invariant it exists to enforce.

### Impact Explanation
The withdrawal intent is signed and executed sending the user's own funds to the token's contract address on Cardano, which is unrecoverable since the token contract address is not a spendable/controlled account in the normal sense used for asset holding by users. This matches "funds delivered to a wrong address/chain/contract with no recovery" (Critical), and it is repeatable for every Cardano-bridged asset and every withdrawal call using this bypass.

### Likelihood Explanation
- Precondition: attacker only needs to know the Cardano token's `origin_chain_address` (public information returned by `getSupportedTokens`) and re-encode it in uppercase — trivial, no special privileges.
- Route: PoaBridge / Cardano assets only (`nep141:cardano.omft.near`-style assetIds).
- Attacker cost: none beyond calling `processWithdrawal`/`createWithdrawalIntents` with a normal amount and the crafted `destinationAddress`.
- Fully feasible and repeatable per call.

### Recommendation
In `compareAddresses.ts`, add a Cardano-specific canonicalization branch (decode both addresses via `bech32.decode` — lowercasing internally — and compare the decoded `(prefix, words)`/byte payload), instead of relying on `a === b` raw string comparison, mirroring the pattern already used for TON/Tron/hex-chains.

/**
 * Validates Cardano mainnet addresses (Base + Enterprise)
 * Returns true if valid, false if invalid
 */
export function validateCardanoAddress(address: string) {
	try {
		// max length big enough for any Cardano Bech32 addr
		const { prefix, words } = bech32.decode(
			address as `${string}1${string}`,
			120,
		);

		// only mainnet
		if (prefix !== "addr") return false;

		// convert 5-bit words back to bytes
		const data = bech32.fromWords(words);
		//@ts-expect-error
		const addrType = data[0] >> 4;

		return addrType >= 0 && addrType <= 7;
	} catch {
		return false;
	}
}
