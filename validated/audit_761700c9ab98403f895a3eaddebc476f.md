### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied (and unauthenticated) `X-Shopify-Shop-Domain` header straight through to the app's handler as the tenant identifier. The `shop` value therefore is *not* bound to the bytes actually verified by the HMAC, breaking the identity binding `hmac_verified_bytes == identity_used_by_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` then trusts `request.shop` (read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never part of the signed bytes) and forwards it, unauthenticated, to the app's handler: [3](#0-2) [4](#0-3) 

Because only `hmac(secret, raw_body)` is checked, and `shop` is taken from a header that is completely excluded from that computation, `hmac_valid(raw_body) == true` does **not** imply `shop_header == shop_that_actually_produced(raw_body)`. Any HTTP client capable of producing one genuinely HMAC-valid `(raw_body, hmac)` pair — trivially obtainable by an unprivileged attacker who installs the app on their own store and lets Shopify deliver one real webhook to them — can replay that exact body to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` value. `Registry.process` will still pass HMAC validation (it only checks the body) and will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen (victim) domain.

### Impact Explanation
This breaks the tenant boundary the whole webhook subsystem is meant to enforce: the gem's own API contract is that a webhook delivered with a valid signature can be trusted to originate from, and describe data belonging to, the `shop` reported in the metadata. An attacker who owns any ordinary (unprivileged) shop can forge webhook deliveries that the host application will process as belonging to a different, victim tenant — e.g. injecting fabricated `orders/create` or `app/uninstalled` events attributed to a shop they do not control. Any app that keys per-tenant side effects (order sync, billing state, uninstall cleanup, GDPR-topic handling) off `WebhookMetadata#shop` is exposed to cross-tenant data confusion/injection, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires no privileged credentials, secrets, or access tokens — only:
1. An attacker-owned (free/dev) Shopify store with the target app installed, to obtain one legitimately HMAC-signed webhook body+HMAC pair, and
2. The ability to POST to the app's public webhook receiver endpoint with custom headers (a capability inherent to any HTTP client).

The gem performs no additional binding (no shop-in-signature, no per-shop secret, no cross-check of the header against the body) so the replay is deterministic and repeatable for any topic the attacker can trigger on their own store.

### Recommendation
Bind the reported `shop` (and ideally `topic`/`api_version`/`webhook_id`) to the verified payload rather than trusting an unauthenticated header:
- If feasible, include the shop domain in the value that is HMAC-verified (e.g., derive/validate it against data already present and signed inside the JSON body, when the topic's payload includes shop-identifying fields), or
- Require host applications to independently correlate `webhook_id`/`shop` against a per-shop record established during OAuth (e.g., only accept webhooks for shops with a known, previously stored session/access token), and document this requirement prominently since the gem's HMAC check alone cannot vouch for the shop header, or
- At minimum, add an explicit warning next to `WebhookMetadata#shop` documentation/`Request#shop` stating this value is unauthenticated and must not be trusted as a tenant boundary without additional application-side verification.

### Proof of Concept
1. Attacker creates their own development/trial Shopify store `attacker.myshopify.com` and installs the target app, subscribing it to a webhook topic (e.g. `orders/create`).
2. Shopify delivers a real webhook to the app's endpoint:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of raw_body using api_secret_key>
   X-Shopify-Shop-Domain: attacker.myshopify.com

   {"id": 1, ...}
   ```
3. Attacker captures `raw_body` and its valid `X-Shopify-Hmac-Sha256` value.
4. Attacker replays the identical body/HMAC to the same endpoint, only changing the shop header:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same valid HMAC>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com

   {"id": 1, ...}
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC [5](#0-4) , and the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this webhook.
