### Title
msg.value double-counted when `address(0)` appears twice in `circomData.erc20TokenAddresses` in `Hinkal.transact` - (File: contracts/Hinkal.sol)

### Finding Description
The broken equality is: **total ETH received by the contract (`msg.value`) must equal the sum of exactly one accounting term per real on-chain balance change.** In `Hinkal.transact`, the per-token balance-reconciliation loop computes, for every index `i` in `circomData.erc20TokenAddresses`:

```solidity
if (circomData.erc20TokenAddresses[i] == address(0)) {
    balanceDif = int256(newBalances[i]) + int256(msg.value) - int256(oldBalances[i]);
}
...
require(
    balanceDif == (circomData.onChainCreation[i] ? int256(0) : circomData.amountChanges[i]) + int256(utxoAmount),
    ...
);
``` [1](#0-0) 

`oldBalances`/`newBalances` are snapshots of `address(this).balance` taken once before and once after `_internalTransact`/`_externalTransact`, via `getBalancesForArray`, which simply loops over `circomData.erc20TokenAddresses` and calls `getERC20OrETHBalance` for each index — it does **not** deduplicate addresses [2](#0-1) . Because `transact` is `payable`, `msg.value` is already reflected in `oldBalances[i]` for every index that maps to `address(0)`. Consequently, if an attacker lists `address(0)` twice in `erc20TokenAddresses`, both indices compute an *identical* `balanceDif` (same underlying `address(this).balance` delta) that each independently re-adds the *same* `msg.value` once. Each index is checked against its own independent `amountChanges[i] + utxoAmount` equation, so the same physical ETH transfer can be used to simultaneously satisfy a legitimate deposit leg (`amountChanges[0] = X`) at one index and to "back" a freshly minted UTXO/on-chain commitment of amount `X` (`utxoAmount[1] = X`) at a second, duplicate `address(0)` index — without any additional ETH ever entering the contract.

`_internalTransact`'s ETH deposit check, `transferERC20TokenFromOrCheckETH`, only asserts `require(msg.value == _value)` per index and performs no running total/decrement across indices [3](#0-2) , so it does not detect or prevent the same `msg.value` being "claimed" by two separate `erc20TokenAddresses` entries.

I could not verify from the code reviewed whether `HinkalHelper.performHinkalChecks`/`dimensionsCheck` (in `HinkalHelper.sol`, not fully inspected due to tool-call limits) enforces uniqueness of `erc20TokenAddresses`. If such a check exists and rejects duplicate token addresses, this finding would be mitigated; I was unable to confirm this within the available investigation budget.

Note: this bug lives in `Hinkal.transact`'s balance-diff loop, not in `Hinkal.prooflessDeposit`. `prooflessDeposit` itself deduplicates and sums amounts for repeated addresses via `_calcTokenChangesForProoflessDeposit` before doing any transfer/balance check [4](#0-3) , and its balance check compares `balanceAfter - balanceBefore == amount` using the summed amount and a single `msg.value` adjustment [5](#0-4) , so the specific double-count mechanism described does not manifest there.

### Impact Explanation
If exploitable (pending confirmation of `dimensionsCheck`), a single ETH deposit of amount `X` could be used to back both a normal deposit accounting term and a second UTXO/on-chain-commitment term of the same magnitude, effectively minting unbacked shielded ETH equal to the duplicated leg's value. This would be a Critical finding (minting shielded value without backing / protocol insolvency) as defined in the rubric, repeatable on every transaction where the attacker can include `address(0)` twice in `erc20TokenAddresses`.

### Likelihood Explanation
This requires only an unprivileged attacker calling `transact` with a self-crafted `CircomData`/proof containing a duplicated `address(0)` entry and a matching UTXO output — no privileged role needed. Feasibility hinges entirely on whether `performHinkalChecks`/`dimensionsCheck` (unverified in this investigation) rejects duplicate token addresses in `erc20TokenAddresses`; if it does not, the attack is fully attacker-controlled and repeatable.

### Recommendation
In `Hinkal.transact`, deduplicate `circomData.erc20TokenAddresses` (or explicitly reject duplicates, especially for `address(0)`) before/within the balance-reconciliation loop, and/or restructure the `address(0)` branch so `msg.value` is credited exactly once across the whole loop (e.g., subtract `msg.value` from `oldBalances[i]` only for the first occurrence, or track a `msgValueConsumed` flag/accumulator enforced to equal `msg.value` in total, not per-index).

### Proof of Concept
Foundry test plan (requires locally generated proof/circomData fixtures):
1. Deploy `Hinkal` with test verifier/hooks.
2. Craft `circomData.erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, 0]`, `onChainCreation = [false, false]`, one output UTXO of `(erc20Address = address(0), amount = X)` mapped to index 1 via `utxoSet`.
3. Call `transact{value: X}(...)`.
4. Assert both balance-diff equality checks pass with a single `X` wei sent (`address(this).balance` increased by exactly `X`), yet the emitted/inserted commitments encode a total shielded ETH value of `2X` (deposit `X` + minted UTXO `X`).
5. Assert `address(this).balance` post-tx == `pre-tx balance + X`, while total newly-created shielded UTXO value == `2X`, proving the equality "`msg.value` backs exactly one accounting term" is violated.
