### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing a malicious merchant to attribute forged webhook data to a victim shop - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request **body**, then trusts the `shop` value taken from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header — a field that is never included in the signed payload. Because the header is not bound to the HMAC, any party who can obtain one genuine, validly-signed webhook (e.g. a merchant who installs the app on their own store and receives real Shopify webhooks for their own shop) can replay that exact signed body to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header. The signature still validates, and the handler is invoked with `WebhookMetadata.shop` set to the attacker-chosen value, breaking the identity binding `shop_that_actually_signed_the_body == shop_attributed_to_the_processed_event`.

### Finding Description
`Registry.process` validates a webhook exclusively with: [1](#0-0) 

`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw body (`@raw_body`); the `shop` accessor is read straight from an unauthenticated header: [3](#0-2) 

Because the HMAC covers `@raw_body` only, the `shop-domain` header is completely outside the signed material. Since the `api_secret_key` used to compute this HMAC is the **app's** single shared secret across all shops that install the app (not a per-shop secret), any legitimate merchant who installs the app receives genuinely-signed webhook payloads for their own store's events. That attacker can capture such a payload (valid body + valid HMAC) and resend the identical bytes to the app's webhook callback route while changing only the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` forwards the spoofed shop straight into the handler: [4](#0-3) 

The gem's own documentation instructs host applications to key business logic (e.g. enqueuing jobs, updating shop-specific records) directly off `data.shop`, with no guidance that this value requires independent verification: [5](#0-4) 

### Impact Explanation
This breaks the binding between the entity whose data was authentically signed and the entity the application believes sent the webhook, i.e. a cross-tenant confusion: `shop` (used to route/attribute the event) ≠ `shop` (that Shopify actually signed the payload for). An app that stores/acts on data keyed by `data.shop` (as recommended in the gem's own docs) can be made to apply another shop's webhook data to, or attribute events for, a shop the attacker does not control — this is a cross-tenant access vulnerability reachable by any unprivileged merchant who has installed the app on their own store, requiring no access to the app's `client_secret`/`api_secret_key`, no privileged account, and no TLS interception.

### Likelihood Explanation
Any user who signs up for an app that uses this library and registers webhook processing this way is, by design, able to receive genuinely HMAC-signed webhook bodies for their own shop. Replaying those bytes to the public webhook endpoint with a modified `Shop-Domain` header is trivial (a simple HTTP request with attacker-controlled headers), requiring no cryptographic material beyond what Shopify already legitimately delivered to the attacker.

### Recommendation
Bind the shop domain into the material verified by the webhook HMAC check, or otherwise cryptographically/authoritatively confirm that the header-supplied `shop` actually corresponds to the shop for which the signed body was generated (for example, cross-check `request.shop` against a shop-scoped record established at webhook registration time, or require the shop to be validated via a lookup keyed by `webhook_id`/subscription rather than trusting the header verbatim). At minimum, document prominently that `data.shop` in `WebhookMetadata` is unauthenticated and must not be used to key sensitive per-tenant operations without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g. `orders/create`) the app already handles.
2. Shopify delivers a legitimate webhook to the app's callback URL:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid signature over raw body>`, `x-shopify-topic: orders/create`
   - Body: `{"id": 123, ...}` (attacker's own order data)
3. Attacker captures this exact raw body and HMAC value (they can even generate custom body content directly, since it's their own shop's data).
4. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks the raw body against the signature — the header was never covered: [6](#0-5) 
6. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload was never actually associated with that shop, letting the attacker inject/attribute data cross-tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          received_signature = verifiable_query.hmac

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
