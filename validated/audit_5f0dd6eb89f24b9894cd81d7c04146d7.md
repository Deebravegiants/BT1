### Title
Webhook `shop` identity header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `x-shopify-shop-domain` header as the tenant identity that gets forwarded to the host application's handler. The signature never binds the `shop` field, so the identity used to dispatch/attribute the webhook is not the identity that was actually authenticated.

### Finding Description
`Utils::HmacValidator.validate` computes/verifies the HMAC exclusively over `verifiable_query.to_signable_string`. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is derived purely from the `hmac-sha256` header: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before trusting `request.shop` (read from the unauthenticated `shop-domain` header) and forwarding it to the registered handler: [3](#0-2) [4](#0-3) 

The binding that should hold is: `shop authenticated by HMAC == shop delivered to handler`. In this implementation that equality never holds — the `shop` header is fully independent of the signed bytes. Because `Context.api_secret_key` is a single secret shared by the app across *all* installed shops (not shop-specific), any tenant that has legitimately installed the app can obtain a validly-signed `(raw_body, hmac)` pair for their own account (e.g., by pointing a webhook subscription at a URL they control) and then re-send that exact `raw_body`/`hmac` pair to the real app endpoint with an arbitrary `x-shopify-shop-domain` header value naming a different, victim shop. `HmacValidator.validate` will pass (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` object asserting `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to route webhook data per tenant (e.g., updating records keyed by `shop`, triggering shop-scoped side effects, or logging as a specific tenant). An attacker who has only ever installed the app on their own shop (an unprivileged internet user with respect to any other tenant) can cause the host application to process attacker-controlled webhook bodies under an arbitrary victim shop's identity — a cross-tenant confusion/spoofing primitive, since the shop value is never cryptographically bound to the authenticated bytes.

### Likelihood Explanation
The library provides only body-based HMAC verification and exposes `request.shop` from an unauthenticated header as if it were an authenticated identity. Any application built directly on `ShopifyAPI::Webhooks::Registry.process` that uses `WebhookMetadata#shop` to select the tenant record to act on is exposed. Exploitation requires no credentials, no TLS interception, and no privileged account — only the ability to install the app on one's own shop and replay a captured valid webhook body/HMAC with a modified `shop` header.

### Recommendation
Include the shop domain (and ideally `topic`/`webhook_id`) inside the signable bytes actually used for HMAC verification, or independently verify that the `shop` header corresponds to a shop known to have that specific webhook subscription/delivery (e.g., cross-check against Shopify's per-delivery webhook ID via the Admin API, or maintain a registry of expected shops). At minimum, document clearly that `request.shop` is not authenticated by `HmacValidator` and must not be trusted for tenant attribution without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers (or lets Shopify deliver) a webhook whose delivery endpoint the attacker controls or can sniff, obtaining a real `raw_body` and `x-shopify-hmac-sha256` value signed by the app's shared `api_secret_key`.
2. Attacker sends that identical `raw_body` and `hmac-sha256` value directly to the target app's real webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts the headers (only checks presence, not shop-hmac correlation): [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates `raw_body` against the HMAC, ignoring headers: [6](#0-5) 
5. The application's webhook handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-supplied data as if it came from the victim shop.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
