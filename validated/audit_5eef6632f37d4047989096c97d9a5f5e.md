### Title
Unchecked parallel-array length mismatch between `order.inputs` and `order.output.assets` in `_fillSameChain` permanently DoSes order fulfillment - ([File: evm/src/apps/intentsv2/IntrinsicIntents.sol])

### Summary
`IntrinsicIntents::_fillSameChain` iterates using `outputsLen = order.output.assets.length` as the loop bound, but indexes into two other independently-sized arrays — the solver-supplied `options.outputs[i]` and the order's own `order.inputs[i]` — without ever verifying that `order.inputs.length`, `order.output.assets.length`, and `options.outputs.length` are equal. This is the same bug class as the referenced `TelcoinDistributor::batchTelcoin` finding: iterating parallel arrays whose lengths are assumed but never enforced to match, causing out-of-bounds reverts.

### Finding Description
`_fillSameChain` computes: [1](#0-0) 

`outputsLen` is derived solely from `order.output.assets.length`. The loop body then reads `order.inputs[i].token` / `order.inputs[i].amount` at line 113–117 and `options.outputs[i]` at line 67/71, treating `order.inputs` and `options.outputs` as if they were guaranteed to be at least `outputsLen` long: [2](#0-1) 

Looking at `IntentGatewayV2::placeOrder`, `inputsLen = order.inputs.length` and `outputsLen_ = order.output.assets.length` are computed and used independently for their own transfer/escrow loops, but there is no `require`/revert check anywhere in `placeOrder` enforcing `order.inputs.length == order.output.assets.length`: [3](#0-2) 

Since `order` is hashed into the `commitment` and stored as-is (via `keccak256(abi.encode(order))`), a user can place an order where `order.inputs.length != order.output.assets.length`. Any solver who later calls `fillOrder`/`_fillSameChain` for that order will hit `order.inputs[i]` at an out-of-bounds index once `i >= order.inputs.length`, and the entire fill transaction reverts (standard Solidity array-index revert behavior on calldata/memory arrays).

### Impact Explanation
This matches the report's bug class (parallel-array length mismatch causing full-transaction revert / DoS) and satisfies the "route unable to deliver" acceptance criterion: an order with mismatched `inputs`/`output.assets` lengths can never be successfully filled by any solver, no matter how the solver-controlled `options.outputs` is shaped, because the revert is caused by the order's own on-chain-committed data (`order.inputs`), not solver input. Escrowed tokens for such an order remain locked in the gateway and are unusable for their intended purpose (fulfilling the intent) — the only recovery path is `_cancelSameChain`, which only the original order creator (`order.user`) can invoke. This can be used to grief solvers who spend gas attempting a fill that always reverts, and it permanently breaks intent fulfillment for any order (malicious or accidental) with mismatched array lengths, undermining the guarantee that a placed, escrowed order is always fillable.

### Likelihood Explanation
Likelihood is straightforward: `placeOrder` accepts an arbitrary `Order` struct from any caller with no cross-length validation between `inputs` and `output.assets`, so any user (malicious or simply buggy client/SDK) can trigger this state with a single `placeOrder` call. No special privileges or unusual conditions are required — it is reachable directly from an unprivileged, single transaction.

### Recommendation
In `IntentGatewayV2::placeOrder` (or in `_fillSameChain` defensively), enforce `order.inputs.length == order.output.assets.length` (and additionally that `options.outputs.length == order.output.assets.length` in `_fillSameChain`) and revert with `InvalidInput()` if they diverge, mirroring the `require(destinations.length == amounts.length, ...)` fix recommended in the referenced report.

### Proof of Concept
1. Caller submits `placeOrder` with `order.inputs` containing 1 element and `order.output.assets` containing 2 elements (both non-zero amounts, no duplicate output tokens). `placeOrder` performs its per-array loops (`inputsLen = 1`, `outputsLen_ = 2`) independently and successfully escrows the single input token — no check compares the two lengths.
2. `commitment = keccak256(abi.encode(order))` is computed and the order is now live/escrowed.
3. A solver calls `fillOrder` with `options.outputs` sized to 2 (matching `order.output.assets`).
4. `_fillSameChain` sets `outputsLen = 2` and loops `i = 0..1`. At `i = 1`, `order.inputs[1]` is accessed but `order.inputs` only has index `0` — the call reverts with an out-of-bounds panic.
5. Every solver attempting to fill this order hits the same revert; the order can never be filled, only cancelled by `order.user` via `_cancelSameChain`.
