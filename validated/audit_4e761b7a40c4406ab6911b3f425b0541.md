### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, but the `shop` identity that the app's handler receives and trusts is read from an HTTP header that is **not** included in the signed bytes. An attacker who can obtain any single validly-signed webhook (e.g., by installing the target app on their own, attacker-controlled shop) can replay that exact body/HMAC pair while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header for a victim shop, and the gem will accept it as an authentic webhook for the victim tenant.

### Finding Description
`Request#to_signable_string` is defined as just the raw body: [1](#0-0) 

Meanwhile `Request#shop` is derived purely from the `shop-domain` header, which is never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which calls `request.to_signable_string` (i.e., only the body) — and then, once that check passes, immediately trusts `request.shop` to build the `WebhookMetadata` object handed to the app-registered handler as the tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string`, so it never inspects the `shop-domain` header: [4](#0-3) 

This breaks the identity binding: `shop-domain header == HMAC-verified shop`. In reality the equality is `raw_body == HMAC-verified bytes` while `shop` is an unauthenticated, attacker-controllable header. Any entity that can obtain one legitimately-signed webhook payload for topic T (trivially achievable by installing the app on a shop they control, since Shopify signs webhooks per-app-secret, not per-shop) can resend that same body+HMAC pair to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop. `Registry.process` will pass HMAC validation (since the body/HMAC pair is genuine) and will invoke the handler with `WebhookMetadata#shop` set to the victim's domain, causing the app to process/attribute a mandatory or regular webhook (e.g. `customers/redact`, `shop/redact`, `customers/data_request`, or any registered business topic) as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged party who only controls their own shop installation of the app can cause the host application (via this gem's own `Registry.process`) to process attacker-supplied webhook data under another merchant's identity. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to select which tenant's data to redact, update, or key session/storage lookups), this can lead to cross-tenant data corruption or disclosure — matching the "cross-tenant access" Critical impact category, since the gem itself fails to bind the trusted identity field to the cryptographically verified bytes.

### Likelihood Explanation
Moderate-to-high likelihood: no access token, `api_secret_key`, or privileged account is required. The only prerequisite is obtaining one legitimate webhook (trivial — install the app on any free/dev shop you control and capture a real webhook delivery for the desired topic), then replaying it with a spoofed header to the app's public webhook endpoint. This is analogous to the referenced report's root cause: a field (`marketHelper`/here, `shop-domain`) is used by trusted logic without being covered by the same integrity check that authorizes the operation.

### Recommendation
Bind the shop identity into the HMAC-verified payload instead of trusting an unauthenticated header. Concretely, `Request#to_signable_string` should incorporate `shop` (and ideally `topic`/`webhook_id`) alongside the raw body, or the gem should require the host application to independently correlate `request.shop` against a shop already known/authorized for that installation (e.g. matching it against a stored offline session) before invoking `handler.handle`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted as a tenant identifier without additional verification.

### Proof of Concept
1. Install the target app (or any app using this gem) on an attacker-controlled shop `attacker.myshopify.com`, and configure a webhook handler for a topic of interest (e.g. `customers/redact`).
2. Capture a legitimately-delivered webhook HTTP request for that topic — its body and the `x-shopify-hmac-sha256` header are cryptographically valid for the app's `api_secret_key`.
3. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:190) calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (lib/shopify_api/webhooks/request.rb:36-38) — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` (lib/shopify_api/webhooks/request.rb:20-23), even though the payload never actually came from Shopify on behalf of that shop.
