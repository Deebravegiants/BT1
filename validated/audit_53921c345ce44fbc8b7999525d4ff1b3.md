### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` verifies the integrity/authenticity of the body only. The `shop` value used for dispatching and identifying the tenant in `Webhooks::Registry.process` is read from the `x-shopify-shop-domain` header, which is never included in the HMAC computation.

### Finding Description
The HMAC check for inbound webhooks is: `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` compared against the `x-shopify-hmac-sha256` header, as implemented in `Utils::HmacValidator.validate_signature`/`compute_signature`. [1](#0-0) 
`Webhooks::Request#to_signable_string` returns only `@raw_body`, while `#shop` is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header: [2](#0-1) 
`Webhooks::Registry.process` validates the HMAC over the body, then constructs `WebhookMetadata` using `request.shop` taken from that same unauthenticated header, and dispatches it to the app's handler as the tenant identity: [3](#0-2) 

This is the same class of bug as the reported analog: a field that is *acted on* (the shop/tenant the webhook is attributed to) is not covered by the cryptographic binding (the HMAC) that is used to establish trust in the request. The binding that should hold is:
`hmac == HMAC(secret, body || shop)` but the code only enforces `hmac == HMAC(secret, body)`, leaving `shop` unauthenticated.

### Impact Explanation
Because all shops installed under a given app share the same `api_secret_key`, any merchant who installs the app can legitimately receive HMAC-valid webhook deliveries for their own shop and body content. That same `(body, hmac)` pair remains valid regardless of which `shop-domain` header accompanies it, since the header is excluded from the signed payload. A malicious/dishonest merchant (an unprivileged actor, no access token or leaked credential required — only their own legitimate installation) can replay a body+hmac pair they legitimately obtained while substituting a victim shop's domain in the `x-shopify-shop-domain` header. The app-side handler will process this as a genuine webhook event "from" the victim shop, since `Registry.process` only checks the body HMAC before dispatching `WebhookMetadata` keyed by the forged shop. This crosses a tenant boundary using only the attacker's own legitimately-issued webhook material, matching the "Critical — cross-tenant access" impact bucket described in scope.

### Likelihood Explanation
Exploitation requires only:
1. Being an app-installed merchant (or otherwise obtaining one valid webhook body/HMAC pair for the shared app secret — normal, unprivileged usage of the app).
2. The ability to POST an HTTP request with attacker-controlled headers to the app's webhook endpoint (any external actor can do this; no TLS interception or credential theft is needed since the header is not authenticated and the body/HMAC are reused verbatim).

This is a straightforward host-application-facing exploitation path *through this gem's own webhook verification logic* (`HmacValidator` + `Webhooks::Request` + `Webhooks::Registry.process`), not a misuse of a documented app-only invariant, so it does not fall under the "host ignoring documented API" exclusion — the gem's own `process` method is the one trusting the header.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed payload check, or otherwise reject/flag a mismatch condition, e.g. compute/verify the signature over `raw_body` together with the `shop-domain` header value (or require the host application to independently verify `request.shop` belongs to a shop with a stored, previously-established session before trusting it), so that `HmacValidator.validate` enforces `hmac == HMAC(secret, body || shop)` rather than `hmac == HMAC(secret, body)` alone.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com`, gets it to send a webhook (e.g. `orders/create`) with body `B`.
2. Shopify's real webhook delivery computes `hmac = HMAC(api_secret_key, B)` and sends headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: hmac`.
3. Attacker captures `(B, hmac)` and re-POSTs to the same app webhook endpoint, replacing the header with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, which still matches `hmac` (body unchanged), so validation passes: [3](#0-2) 
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: ...)` and invokes the app's handler, which now believes this event genuinely originated from `victim.myshopify.com`, even though the victim never sent it.
