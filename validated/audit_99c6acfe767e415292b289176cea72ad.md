## Title
Fee-on-transfer fee tokens cause overstated `TRANSACTION_FEES` escrow, leading to insolvency/DoS in `IntentGatewayV2.withdraw` — (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder` was hardened against fee-on-transfer tokens for `order.inputs` (it now measures `balanceOf` before/after the `safeTransferFrom` and stores the *actual received* amount), but the `order.fees` (fill-fee) escrow path was not given the same treatment. It credits `_orders[commitment][TRANSACTION_FEES] = order.fees` using the *requested* amount regardless of what the gateway actually received, so a fee-on-transfer fee token creates a permanent escrow-accounting overstatement.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol`, the input-token loop was fixed to be fee-on-transfer-safe: [1](#0-0) 
uses `balBefore`/`balanceOf` delta to record the actual amount received.

But the fee-token escrow credit right after it does not do this: [2](#0-1) 
`IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees)` is called, then `_orders[commitment][TRANSACTION_FEES] = order.fees` is set unconditionally to the *requested* amount, not the amount actually received by the contract. The same pattern exists in the Tron variant: [3](#0-2) 

When the order is later settled or refunded, `_withdraw`/`withdraw` unconditionally transfers out the full stored `fees` value from the contract's pooled balance: [4](#0-3) [5](#0-4) 

Because `feeToken` is a single Hyperbridge-configured token shared across *all* orders on the gateway (`IDispatcher(hostAddr).feeToken()`), if that token ever charges a transfer fee (e.g., an upgradeable stablecoin enabling a fee, or governance selecting a deflationary/fee token as the fee token), every `placeOrder` call escrows more `TRANSACTION_FEES` credit than tokens actually delivered to the contract. The shortfall accumulates across orders in the shared token balance.

### Impact Explanation
This breaks the internal escrow accounting invariant (`sum of escrowed balances == actual contract token balance`) for the fee-token pool:
- Each order records more `TRANSACTION_FEES` than the contract actually holds for it, so later withdrawals begin double-counting from the shared pool — the same underlying tokens funding one order's registered "escrow" are actually needed to cover another order's shortfall. This can allow a subsequent withdrawer to drain fee-token balance that rightfully belongs to un-settled orders (fund loss for other users), or cause `safeTransfer` in `withdraw`/`_withdraw` to revert once the shared feeToken balance is insufficient, permanently blocking `withdraw()` for orders sharing that commitment (since `withdraw` processes both the escrowed inputs and the fee release atomically — a fee-token transfer failure reverts the whole call, freezing the user's/solver's legitimately-escrowed input tokens too).
- This is analogous to the reported `lockTokensToBasket` bug class (fee-on-transfer token breaking an escrow/accounting invariant), but manifests here as fund freezing/insolvency in the shared escrow pool rather than an immediate revert.

### Likelihood Explanation
Requires the configured `feeToken` to become (or already be) a fee-on-transfer token. Since Hyperbridge explicitly designs for and tests fee-on-transfer input tokens elsewhere in the same contract (see the `FeeOnTransferToken` test suite), the same class of token is a realistic candidate for the fee token, especially given upgradeable stablecoins can add such a mechanism after deployment/governance configuration.

### Recommendation
Apply the same balance-delta measurement used for `order.inputs` to the `order.fees` escrow path: snapshot `feeToken.balanceOf(address(this))` before `safeTransferFrom`/swap and after, and store the actual delta in `_orders[commitment][TRANSACTION_FEES]` instead of the raw `order.fees` value, in both `evm/src/apps/IntentGatewayV2.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Governance/host configures `feeToken` to a token that later enables (or already has) a 1% transfer fee.
2. User calls `placeOrder` with `order.fees = 100` fee-token units, paid via `safeTransferFrom` (non-native path).
3. Contract actually receives 99 units, but `_orders[commitment][TRANSACTION_FEES] = 100` is recorded (line 391/487).
4. Repeat across multiple orders — the aggregate recorded `TRANSACTION_FEES` liabilities across all commitments exceed the gateway's actual `feeToken` balance.
5. On settlement, `_withdraw`/`withdraw` attempts to pay out the full recorded `fees` for each order; once cumulative shortfall exceeds the buffer, a `safeTransfer` reverts, freezing legitimate `withdraw()` calls (and hence release of escrowed input tokens) for affected orders, or earlier withdrawers drain tokens that should have backed later orders' fee escrow.
