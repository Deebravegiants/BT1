## Title
Permanent blocking of an inbound LayerZero-over-Hyperbridge channel via un-relayed / out-of-order strict nonce enforcement - (File: `sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol`)

### Summary
`HyperbridgeLzEndpoint` bridges LayerZero-style messages over Hyperbridge's ISMP transport. Inbound delivery enforces a strictly monotonic per-`(receiver, srcEid, sender)` nonce, exactly the "sequential nonce, incremented only on delivery" pattern flagged in the referenced Cardex report. Because ISMP relaying is a permissionless, unordered process with no guaranteed delivery order and (for this adapter) no request timeout, a single message that is never relayed — or is relayed out of order — permanently blocks every subsequent message on that channel, requiring manual `skip()` intervention by the OApp/delegate to recover.

### Finding Description
`send()` assigns a strictly incrementing outbound nonce per `(msg.sender, dstEid, receiver)` and dispatches an independent ISMP `PostRequest` with `timeout: 0` (never expires): [1](#0-0) 

On the destination, `onAccept` requires the incoming message's embedded nonce to equal `_inboundNonce + 1` exactly, or the whole call reverts before any delivery attempt: [2](#0-1) 

Each `send()` call produces its own independent ISMP `PostRequest` commitment/proof; ISMP relaying is permissionless and relayers are free to choose which commitments to prove and in what order — there is no protocol-level guarantee that request N is relayed before request N+1. Since the dispatched request carries `timeout: 0` (no expiry, confirmed by `onPostRequestTimeout` being a no-op), a request that is simply never relayed (censored, dropped, insufficient relayer incentive, or relayer processes a later commitment first) can never time out and free the fee/queue slot: [3](#0-2) 

Once nonce N is missing, every later-numbered message for that `(receiver, srcEid, sender)` triple reverts at the `InvalidNonce` check in `onAccept` — the try/catch only shields `lzReceive` execution, not the nonce gate itself, so out-of-order delivery attempts fail entirely and are not retained for retry the way a reverting `lzReceive` is via `_inboundPayloadHashes`. The only recovery path is `skip()`, gated to the OApp or its configured delegate: [4](#0-3) 

This mirrors the Cardex root cause precisely: a signer/relayer-controlled, strictly sequential counter that only advances on successful completion of the prior item, so a single missing/delayed item permanently blocks all later items in the queue until an external (off-chain/administrative) actor manually intervenes.

### Impact Explanation
Any relayer failure, censorship, fee-related delay, or benign out-of-order proof submission for a single message freezes the entire inbound channel between an OApp pair (e.g., an OFT token bridge built on this adapter) — every subsequent cross-chain transfer to that receiver from that sender is undeliverable until the OApp/delegate manually calls `skip()`. Funds already locked/burned on the source side for the affected and all subsequent transfers are effectively frozen in transit (route unable to deliver messages) until manual recovery, and no permissionless recovery mechanism exists (unlike `retryPayload`, which any address can call for failed `lzReceive` executions, `skip()` is restricted to the OApp/delegate). This satisfies the "route unable to deliver messages" / freezing-of-funds impact category.

### Likelihood Explanation
Reaching this requires only a single submitted message on the route failing to be relayed before a later one is relayed — plausible via ordinary relayer downtime, fee competition, censorship by any of the permissionless relayers, or a relayer intentionally submitting proofs out of order. No privileged access is needed; it is reachable purely from the unprivileged relayer/message-dispatch path that Hyperbridge exposes.

### Recommendation
Do not enforce strict global FIFO ordering for inbound delivery when the underlying transport (ISMP relaying) provides no ordering guarantees. Options: allow out-of-order acceptance with a replay-protected set (e.g., accept any nonce once, keyed by nonce, instead of requiring exact successor), add a timeout/expiry to the dispatched `PostRequest` so a stuck message can be permissionlessly cleared and skipped by the underlying ISMP timeout flow, or make `skip()`/recovery permissionless (or time-delayed to a permissionless fallback) so a censored/delayed message cannot indefinitely brick the channel without requiring the OApp operator to actively monitor and intervene.

### Proof of Concept
1. OApp `A` (deployed as an OFT adapter using this endpoint) sends message 1 to receiver `R` on `srcEid` — `_outboundNonce[A][dstEid][R]` becomes 1, ISMP `PostRequest` #1 dispatched with `timeout=0`.
2. OApp `A` sends message 2 — `_outboundNonce` becomes 2, ISMP `PostRequest` #2 dispatched.
3. A relayer (or lack of any relayer) never submits the proof for request #1 (e.g. it under-prices the relayer fee, or the relayer is offline/censoring), but successfully relays request #2 to `onAccept`.
4. `onAccept` decodes nonce=2, computes `expectedNonce = _inboundNonce[R][srcEid][A] + 1 = 1`, and reverts with `InvalidNonce(1, 2)` — request #2 is not delivered and no in-progress-retry state is stored for it (unlike a reverting `lzReceive`).
5. Request #1 is never relayed (no timeout ever fires since `timeout=0`), so `_inboundNonce` never advances past 0.
6. All subsequent legitimate messages between `A` and `R` on this route permanently fail at the same `InvalidNonce` check until `R`'s owner or delegate calls `skip()` — an action requiring active operator monitoring, not guaranteed to happen automatically.

```text
        // Validate and advance the nonce. The nonce is committed BEFORE (and independently of)
        // OApp execution: a reverting `lzReceive` must not roll back this write. Otherwise the
        // message would be retried forever at the same nonce and every later nonce would be
        // permanently rejected, bricking the (receiver, srcEid, sender) channel.
        address receiverAddr = address(uint160(uint256(receiver)));
        uint64 expectedNonce = _inboundNonce[receiverAddr][srcEid][sender] + 1;
```

```text
    /// @notice Advances the inbound nonce past `_nonce` (which must be the next expected nonce),
    /// discarding any stored payload at that slot. Callable by the OApp or its delegate.
    function skip(
        address _oapp,
        uint32 _srcEid,
        bytes32 _sender,
        uint64 _nonce
    ) external override onlyOAppOrDelegate(_oapp) {
        uint64 expected = _inboundNonce[_oapp][_srcEid][_sender] + 1;
        if (_nonce != expected) revert InvalidNonce(expected, _nonce);
        _inboundNonce[_oapp][_srcEid][_sender] = _nonce;
        delete _inboundPayloadHashes[_oapp][_srcEid][_sender][_nonce];
        emit InboundNonceSkippedBy(_oapp, _srcEid, _sender, _nonce);
    }
```
