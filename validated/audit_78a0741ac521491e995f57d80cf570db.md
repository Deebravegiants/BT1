### Title
`Oauth.begin_auth` builds the OAuth redirect host from an unvalidated `shop` parameter, enabling forced OAuth completion / login CSRF - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` accepts a caller-supplied `shop:` string and feeds it directly into `auth_base_uri(shop)` to build the URL the merchant's browser is redirected to, without ever running it through `Utils::ShopValidator.sanitize!`, unlike every other entry point in the gem that accepts a `shop` string.

### Finding Description
`begin_auth` builds the authorization redirect URL as `auth_base_uri(shop) + "/oauth/authorize?..."`, and `auth_base_uri` returns `"https://#{shop}/admin"` for any `shop` value that isn't a `.my.shop.dev` dev-server host. [4](#0-3) 
No call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` occurs anywhere in `begin_auth`, and `ShopValidator` exists precisely to reject non-Shopify domains such as `evil.com` or lookalike hosts. [5](#0-4) 
By contrast, the sibling flows `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which take the exact same kind of `shop:` argument, explicitly call `Utils::ShopValidator.sanitize!(shop)` before using it to build the request host that is later sent `client_id`/`client_secret`. [1](#0-0) [2](#0-1) 

This breaks the identity binding that `shop` (the destination host the merchant's browser is sent to for authorization) should equal a trusted Shopify domain. The host actually used to satisfy the redirect is whatever the untrusted caller (typically taken straight from a request parameter such as `request.headers["Shop"]` per the gem's own documented usage example) supplies, without going through the same allow-list used everywhere else in the library. [6](#0-5) 

Note that `validate_auth_callback`'s use of `auth_query.shop` is not affected in the same way, because that `shop` value is bound by the OAuth callback's HMAC (covering `code, host, shop, state, timestamp`), so it cannot be forged by an unprivileged attacker without the `api_secret_key`. [7](#0-6) 

### Impact Explanation
An unprivileged internet user who can influence the `shop` value passed into `begin_auth` (e.g., via a URL query parameter or header on the host application's login route, as shown in the gem's own documented integration example) can cause the victim's browser to be redirected to an attacker-chosen host instead of a genuine `*.myshopify.com`/`*.myshopify.io` domain, while still carrying the app's real `client_id` and the app's real `redirect_uri` in the query string. This matches the "session fixation or forced OAuth completion" High-impact category: the attacker can force the OAuth flow to proceed against a shop of their choosing (e.g., a shop the attacker controls) while the victim's browser holds the app's anti-CSRF `state` cookie, or otherwise phish/redirect the victim off the legitimate Shopify authorization host. `client_secret` is not sent at this stage, so the impact is bounded to forced/steered OAuth initiation and open-redirect-style phishing rather than direct secret exfiltration.

### Likelihood Explanation
Exploitability depends entirely on the host application passing through an unvalidated, attacker-influenced `shop` value to `begin_auth` (which the gem's own documentation example does, taking `shop` from a request header without first sanitizing it via `ShopValidator`). Given that `ShopValidator.sanitize!` exists in this gem specifically to close this gap and is used in the two structurally identical flows (`ClientCredentials`, `RefreshToken`), its absence in `begin_auth` is very likely an oversight rather than an intentional design difference.

### Recommendation
In `Oauth.begin_auth`, validate the `shop` parameter with `Utils::ShopValidator.sanitize!(shop)` (as done in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`) before passing it to `auth_base_uri`, raising `Errors::InvalidShopError` for any host that isn't a trusted Shopify domain.

### Proof of Concept
1. Host application implements the login route exactly as shown in the gem's documentation, taking `shop` from an unauthenticated request header/param and calling `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")`. [6](#0-5) 
2. Attacker sends the victim a link that triggers this login route with `shop=attacker-controlled-host`.
3. `begin_auth` computes `auth_route = "https://attacker-controlled-host/admin" + "/oauth/authorize?client_id=...&redirect_uri=<app's real callback>&state=..."` because no `ShopValidator` check rejects the non-Shopify host. [8](#0-7) 
4. The victim's browser is redirected to the attacker's host with the app's real `client_id`/`redirect_uri`/`state`, while the anti-CSRF `state` cookie is set on the victim's browser for the attacker's chosen flow — enabling forced OAuth completion / login-CSRF style abuse, in contrast to `ClientCredentials`/`RefreshToken`, which would reject the same input via `ShopValidator.sanitize!`.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
