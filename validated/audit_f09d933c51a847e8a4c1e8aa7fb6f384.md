### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is used by `ShopifyAPI::Webhooks::Registry.process` to build the `WebhookMetadata` object passed to the app's webhook handler. However, the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body — the `shop-domain` header is never part of the signed content. This lets an attacker who legitimately controls one shop replay a validly-signed webhook body under a different, victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads directly from the (client-supplied) `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to it: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" (per the gem's own documentation) and then forwards `request.shop` unchecked into `WebhookMetadata`, which is handed to the app's handler as trusted tenant context: [4](#0-3) [5](#0-4) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," reinforcing that consumers are meant to trust `data.shop` as an authenticated part of the request: [6](#0-5) 

The identity binding that should hold is: **shop that authorized/produced the signed body == shop attributed to the webhook event (`request.shop`)**. Because the signature only binds the body bytes and not the shop header, this equality is never checked. Since Shopify signs all webhooks for an app using the same app-wide `client_secret` (not a per-shop secret), any shop that installs the app can obtain a validly-signed `(body, hmac)` pair for its own tenant, and then submit that exact pair to the app's webhook endpoint with an arbitrary `shop-domain` header. `HmacValidator.validate` still succeeds (it only checks the body/hmac pair), and `Registry.process` calls the handler with `shop: <victim-shop>` and the attacker's own body content.

### Impact Explanation
This breaks tenant isolation: an unprivileged party who installs the app on their own store (a normal, low-privilege action) can cause the app to process attacker-chosen webhook payloads that are attributed to a different merchant's shop. Any app logic that keys off `data.shop` — e.g., to select which shop's session/access token to act on, to write attacker data into a victim's shop-scoped records, or to trigger shop-scoped side effects (like `shop/redact`, `customers/redact`, `orders/create` handling, etc.) — can be tricked into acting on behalf of, or against the data of, a shop the attacker does not control. This is a cross-tenant access primitive rooted entirely in this gem's webhook verification code.

### Likelihood Explanation
The prerequisite (installing the app on an attacker-controlled shop to receive a legitimately-signed webhook) is trivial for many public/embedded Shopify apps that allow open installation, and requires no leaked secrets, no privileged account, and no host-application misuse — only use of the documented `ShopifyAPI::Webhooks::Request` / `Registry.process` API exactly as intended.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the HMAC-signable content, or otherwise cryptographically bind `shop` to the verified payload before constructing `WebhookMetadata`. At minimum, update `VerifiableQuery`/`HmacValidator` usage for webhooks so that `to_signable_string` incorporates the shop domain header, and document clearly that `request.shop` is currently unauthenticated so host apps do not treat it as a verified tenant identifier without additional cross-checks (e.g., verifying the shop is one for which the app holds an installed session).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, becoming a legitimate (if low-privilege) merchant of the app.
2. Shopify sends the attacker's app installation a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker captures `(B, H)` and replays them to the app's webhook endpoint, substituting the header:
```
POST /callback/orders/create
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim.myshopify.com
<body B>
```
4. `ShopifyAPI::Webhooks::Request` parses this into `shop = "victim.myshopify.com"`; `HmacValidator.validate` recomputes HMAC over `B` only, which matches `H`, so `Registry.process` proceeds: [7](#0-6) 
5. The registered handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled B>, ...)` and performs shop-scoped work as if this were a legitimate event from the victim's store, despite the attacker never having any relationship with `victim.myshopify.com`.
