### Title
Webhook shop/topic identity spoofing via HMAC that only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the shop domain, topic, webhook id and API version used by the registry to route and label the webhook are taken directly from unauthenticated HTTP headers. Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any attacker who can obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and triggering a webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `shop-domain` (and `topic`/`webhook-id`) headers to a victim shop. `HmacValidator.validate` will pass because it only checks the body against the shared secret, and `Registry.process` will then hand the spoofed shop identity to the app's webhook handler as if it were authentic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, never covered by the signature: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) using the app's (shop-independent) `api_secret_key`: [3](#0-2) 

`Registry.process` trusts `request.shop`/`request.topic` (unauthenticated header values) directly as the tenant identity once the HMAC check on the body passes, and forwards them to the app's webhook handler: [4](#0-3) 

The broken identity binding is: `handler.handle` should only be invoked with `request.shop` equal to the shop that actually produced (and whose install is bound to) the HMAC-signed content, but here `request.shop` is an attacker-controlled header while the HMAC only proves "signed by *some* installation of this app," not "signed by this shop." Because `client_secret`/`api_secret_key` is one value shared by all shops that install the same app, any tenant of the app can generate a valid `(body, hmac)` pair (by triggering any webhook-eligible event in their own store) and then replay it against the app's webhook endpoint with a different `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) header, causing the receiving application to process attacker-supplied body content labeled as belonging to a victim shop.

### Impact Explanation
This breaks the shop-to-signature binding that webhook consumers rely on for per-tenant data isolation, allowing an attacker who has installed the app on their own store to inject or spoof webhook payloads attributed to any other shop of their choosing, without needing that shop's or the app's `client_secret`. This is a cross-tenant integrity/isolation violation: applications built on this gem's `Registry.process`/`Utils::HmacValidator.validate` will accept and act on attacker-controlled body data as if authored by an arbitrary victim shop.

### Likelihood Explanation
Any unprivileged internet user can install the target Shopify app on their own free/development store, trigger any webhook (e.g., `orders/create`) to obtain a legitimately-signed `(body, hmac)` pair, and then POST that same body/HMAC to the app's public webhook endpoint with a forged `shop-domain` header. No credentials beyond a normal app install are required, and the exploit path goes entirely through this gem's `Webhooks::Request` and `Utils::HmacValidator`/`Registry.process` code.

### Recommendation
Bind the shop identity into the material that is actually verified, e.g. by including `shop-domain` (and ideally `topic`, `webhook-id`) inside `to_signable_string`, or by validating that the resolved `request.shop` matches a shop for which the app currently holds an active session/installation before dispatching to the handler. At minimum, document that `Registry.process` implementers must not rely on `request.shop`/`request.topic` for tenant-sensitive decisions unless independently corroborated (e.g. against a known-installed shop list), since the current HMAC does not bind those header values.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook-eligible event (e.g., creates an order) and captures the resulting request: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header.
5. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H` because the secret and body are unchanged — validation passes.
6. `Registry.process(request)` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`, where `shop` is `victim-shop.myshopify.com`, even though the payload was never produced by or for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
