### Title
Unauthorized nonce transactions pass bank-level admission check and can grief legitimate nonce-tx scheduling via nonce-address dedup - ([File: runtime/src/bank/check_transactions.rs])

### Summary
`Bank::check_age_and_compute_budget_limits` calls `check_transaction_age` with `strict_nonce_authority_check=false`, so `check_nonce_transaction_validity` returns a valid `nonce_address` for any transaction that references a live nonce account and satisfies its stored blockhash, without verifying that the transaction's signer matches `nonce_data.authority`. Because the real authority check is deferred to the SVM layer, an attacker who does not control a nonce account's authority can still get their transaction admitted at the bank-check stage as a "valid nonce transaction," letting it participate in nonce-address-keyed scheduler bookkeeping alongside a legitimate transaction for the same nonce.

### Finding Description
`check_age_and_compute_budget_limits` (runtime/src/bank/check_transactions.rs) invokes `self.check_transaction_age(tx.borrow(), max_age, &next_durable_nonce, &hash_queue, error_counters, strict_nonce_size_check, false)` — the final `false` is `strict_nonce_authority_check`. [1](#0-0) 

`check_transaction_age` delegates to `check_nonce_transaction_validity`, which only enforces the authority-signer match when `strict_nonce_authority_check` is true: [2](#0-1) 

By contrast, `check_transaction_without_status_cache` (used elsewhere, e.g. forwarding/replay-adjacent leader paths) passes `true` for this flag: [3](#0-2) 

This confirms the bank-level admission check used in the normal receive/buffer path (`check_age_and_compute_budget_limits` → `check_transactions_with_processed_slots` → `check_transactions`) does not verify nonce authority, and only checks: (1) the transaction's `recent_blockhash` equals the nonce account's stored durable nonce, and (2) the nonce account exists and (optionally) has the correct size. An attacker can therefore craft a transaction whose `AdvanceNonceAccount` instruction names a victim's nonce account but signs with the attacker's own key as the "authority" account (satisfying sanitization/sigverify, since the attacker can sign for their own key), set `recent_blockhash` to the nonce's stored hash, and have it accepted at this stage with `Some(nonce_address)` returned — exactly matching a legitimate transaction using the same durable nonce.

The transaction scheduler tracks nonce transactions by address via `container.get_nonce_transaction_priority_id` (confirmed present in `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs` and `transaction_state_container.rs`) to avoid buffering mutually-exclusive transactions against the same nonce. Since the bank-level check cannot distinguish the spoofed transaction from a legitimate one (both return the same `nonce_address`), the spoofed transaction can occupy or contest that nonce-address slot in the container, potentially causing the legitimate authorized transaction to be dropped or delayed by the dedup logic — even though the spoofed transaction can never actually commit (the real authority check happens later in SVM's nonce validation and would reject it before execution).

### Impact Explanation
This is a resource-exhaustion/griefing vector against the TPU/scheduler admission path: an unprivileged attacker can consume scheduler bookkeeping slots and potentially interfere with the ability of a legitimate nonce-based transaction (e.g., an offline-signed or delayed-submission transaction) to be scheduled, without ever being able to settle themselves. It does not cause fund loss, double settlement, or state divergence, so it is a lower-severity availability/griefing issue rather than a consensus or funds-safety bug.

### Likelihood Explanation
Exploitability requires only knowledge of a target nonce account's public address (nonce accounts are on-chain and typically discoverable) and no leaked keys or special privileges — the attacker only needs to be able to sign a transaction with their own key while naming the victim's nonce account and matching its current stored blockhash. This is feasible for any unprivileged user broadcasting to a public TPU/RPC endpoint, though it does require timing (submitting before/alongside the legitimate transaction) to have effect on the dedup/eviction path.

### Recommendation
Verify the exact behavior of the nonce-address dedup/eviction logic in `receive_and_buffer.rs`/`transaction_state_container.rs` (full source review needed beyond what indexed search returned here). If it can evict or preferentially drop a transaction based solely on the unauthenticated `nonce_address` returned by `check_nonce_transaction_validity`, consider either (a) performing a cheap authority pre-check (without full account lock) before using `nonce_address` for scheduler dedup decisions, or (b) ensuring the dedup logic only ever drops the objectively lower-priority/lower-fee transaction and never blindly favors first-arrival for unauthenticated nonce claims.

### Proof of Concept
Unit/integration test plan (requires access to full `TransactionViewReceiveAndBuffer`/`TransactionStateContainer` source, not fully available via index):
1. Set up a bank with a nonce account whose authority is `real_authority_keypair`.

3. Build `tx_spoofed`: `AdvanceNonceAccount(nonce_pubkey, attacker_keypair.pubkey())` + payload, signed by `attacker_keypair`, using the same nonce blockhash — this differs only in which signer is named as "authority," so it sanitizes and passes `check_nonce_transaction_validity` due to `strict_nonce_authority_check=false`.
4. Feed both into the receive/buffer path (`TransactionViewReceiveAndBuffer` insertion / `TransactionStateContainer`) in varying arrival order and with varying priority fees.
5. Assert: `tx_legit` is never dropped/evicted from the container as a result of `tx_spoofed`'s presence, and that `container.get_nonce_transaction_priority_id(nonce_pubkey)` ultimately resolves to `tx_legit` regardless of arrival order, since `tx_spoofed` can never pass the SVM-level authority check.

If step 5's assertions fail (i.e., `tx_legit` can be dropped/evicted due to `tx_spoofed`), the finding is confirmed as exploitable; this final confirmation requires running the test against the actual container implementation, which I was unable to fully inspect via the indexed search tools in this session.

    pub(super) fn check_nonce_transaction_validity(
        &self,
        message: &impl SVMMessage,
        next_durable_nonce: &DurableNonce,
        strict_nonce_size_check: bool,
        strict_nonce_authority_check: bool,
    ) -> Option<(Pubkey, u64)> {
        let nonce_is_advanceable = message.recent_blockhash() != next_durable_nonce.as_hash();
        if !nonce_is_advanceable {
            return None;
        }

        let (nonce_address, nonce_data) =
            self.load_message_nonce_data(message, strict_nonce_size_check)?;

        if strict_nonce_authority_check
            && !message
                .get_ix_signers(NONCED_TX_MARKER_IX_INDEX as usize)
                .any(|signer| signer == &nonce_data.authority)
        {
            return None;
        }

        let previous_lamports_per_signature = nonce_data.get_lamports_per_signature();

        Some((nonce_address, previous_lamports_per_signature))
    }
