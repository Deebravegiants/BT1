### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to application webhook handlers from an unauthenticated HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body. This breaks the intended binding `HMAC-authenticated bytes == identity used for tenant routing`.

### Finding Description
`Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

But `Request#shop` (and `#topic`, `#api_version`, `#webhook_id`) are read directly from HTTP headers that are never fed into the signable string: [2](#0-1) 

`Registry.process` validates only that the HMAC matches, then immediately forwards the unauthenticated `request.shop` to the application's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` (used by `Registry.process`) computes the HMAC purely over `verifiable_query.to_signable_string`, i.e., just the body: [4](#0-3) 

Because the same `client_secret`/`api_secret_key` is shared across every shop installed on a given app, any HMAC that is valid for one shop's webhook body is equally valid for every other shop's webhook endpoint on that app — the header that says "this belongs to shop X" is not part of what is cryptographically authenticated. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality that should hold is `authenticated_bytes.shop == identity_used_by_handler`, but instead `authenticated_bytes` (the body) says nothing about shop, while `identity_used_by_handler` (`request.shop`) comes from an arbitrary, unauthenticated header.

### Impact Explanation
An attacker who can obtain (or replay) one valid `(raw_body, hmac)` pair delivered for the app — e.g., their own shop's outbound webhook, which they fully control the timing and content of, or one relayed through any intermediary/proxy — can resend that exact body and HMAC to the app's webhook endpoint while forging the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a *different* installed shop. The app's `WebhookMetadata` is constructed with that forged `shop`, and its handler will process/persist the payload as if it originated from the victim tenant. Depending on the host app's handler logic (e.g., updating per-shop caches, triggering per-shop side effects, writing to shop-scoped records), this results in cross-tenant data confusion/injection — a Critical-class impact (cross-tenant access) achieved purely through this gem's webhook verification primitive.

### Likelihood Explanation
The attacker needs no possession of `api_secret_key`, access token, or any Shopify-side privilege beyond running their own app installation on at least one shop (to generate one valid signed webhook body) or intercepting one webhook delivery in transit/at a proxy. Forging the shop header is a trivial HTTP header change; no cryptographic material needs to be broken. The only constraint is that the attacker needs a body whose content is acceptable/meaningful for the target topic/handler, which is often satisfiable (e.g., replaying identical topic webhooks across shops, or crafting content that is topic-generic).

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise independently bind the verified body to the claimed shop (e.g., require the receiving application to cross-check `request.shop` against a shop that is already known/installed and reject webhooks for shops that never established a relationship with this specific delivery). At minimum, document prominently that `shop` is not authenticated by the HMAC and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. App is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com`, sharing one `api_secret_key`.
2. Attacker triggers/receives a legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(B, secret)`.
3. Attacker POSTs the identical body `B` and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (line `lib/shopify_api/utils/hmac_validator.rb:13-21`, HMAC computed only over `B`).
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the app's handler processes attacker-controlled data as belonging to the victim shop.
