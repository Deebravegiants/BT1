## Title
Webhook `shop-domain` Header Is Not Bound to the HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (from the `x-shopify-shop-domain` header) is read separately and passed unauthenticated into `WebhookMetadata` and the app's handler. This mirrors the reported bug class: a field that is *acted on* (used to attribute the webhook to a tenant) is not *covered by* the integrity check (the HMAC).

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header` [2](#0-1) . `Utils::HmacValidator.validate` verifies the `hmac` field against `to_signable_string` computed with the app's shared secret [3](#0-2) , but the `shop-domain` header value is never included in that signed string. `Registry.process` calls `Utils::HmacValidator.validate(request)` and, once it passes, immediately forwards `request.shop` into the handler as the tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) .

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has installed the app, any tenant that has installed the app can legitimately trigger webhook deliveries (e.g., by creating an order in their own store) that are validly HMAC-signed for that body. Since the header carrying the shop attribution is outside the signed content, that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to any other shop's domain, and `HmacValidator.validate` will still return `true` because it only checks the body/hmac pair — never the shop header.

The binding that should hold is:
`shop_attributed_to_event == shop_bound_inside_signed_payload`

but the actual binding enforced by the gem is only:
`hmac == HMAC(raw_body, secret)`

with `shop` sourced from an entirely separate, unauthenticated channel (an HTTP header). This is the same class of defect as the reported issue: data that is used downstream (bytecode / here, tenant attribution) is not covered by the mechanism meant to guarantee its integrity/authenticity (L1 data availability / here, HMAC).

### Impact Explanation
If a host application trusts `WebhookMetadata#shop` (as the documented API implies it should, since it's the only tenant-identifying field exposed by this gem's webhook processing path) to select which merchant's session/data to update, an attacker who controls one legitimate shop installation can forge webhook deliveries that are attributed to a different shop. This is a cross-tenant data-integrity/confusion issue: the victim shop's application state could be modified using data that was never actually sent by Shopify for that victim shop. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to control at least one legitimate installation of the target app (a normal, unprivileged merchant relationship) — no leaked secrets, no privileged account, and no TLS interception are required. The attacker only needs to be able to trigger a webhook-worthy event on their own store and then replay the resulting HTTP body with a spoofed `shop-domain` header directly to the app's public webhook endpoint. This is a realistic, low-effort attack path for any app built on this gem that relies on the gem's own `Request`/`Registry` abstractions for tenant attribution.

### Recommendation
Bind the `shop` domain (and ideally `topic`/`webhook-id`) into the signed payload verification, or otherwise cryptographically tie the header-derived shop to the request before exposing it via `WebhookMetadata`. At minimum, document prominently that `request.shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier without additional verification (e.g., cross-checking against a known/installed shop list keyed by a value that *is* covered by the signature, such as content embedded in the JSON body).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on victim `victim-shop.myshopify.com`, both sharing the same `client_secret` for HMAC (`Context.api_secret_key`).
2. Attacker triggers an event (e.g. `orders/create`) on their own store, capturing the resulting webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)` — this is valid because `Digest.hexencode(Base64.decode64(H))` matches `HmacValidator.compute_signature(B, secret)` [5](#0-4) .
3. Attacker replays the same `body: B` / `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`, to the app's webhook endpoint.
4. `Request.new(raw_body: B, headers: ...)` succeeds (all required headers present) [6](#0-5) .
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes since it only checks `B` against `H` [7](#0-6) .
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, attributing attacker-controlled content to the victim tenant [8](#0-7) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
