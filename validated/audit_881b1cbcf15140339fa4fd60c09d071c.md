### Title
Uniswap V4 spot-price venue pricing is flash-loan manipulable and un-guarded by default, letting a placer drain a Simplex solver's escrowed output at a fabricated rate - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Simplex's Uniswap-V4 "pool-based pricing" venue prices curveless intent pairs directly from the pool's current `sqrtPriceX96` with no TWAP, no size/impact term, and no execution-cost adjustment. The only defense, `referencePrice`/`maxDeviationBps`, is optional and, per the project's own docs, leaves the chain "unguarded" when omitted. An attacker who flash-loan-manipulates the pool's spot price and, in the same block, places/fills an intent order priced off that spot value can force the solver to deliver output tokens at a fabricated rate — the same bug class as the SurgeBNB incident (spot-price dependency with no manipulation resistance, exploited atomically for profit).

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` derives the USD price of the exotic token straight from `sdkPool.token0Price`/`token1Price`, which is built from the pool's live `sqrtPriceX96` read via `refresh()`: [1](#0-0) 

`UniswapV4LiquidityState.refresh` fetches `getSlot0`/`getLiquidity` fresh right before pricing/planning a withdrawal, so the price used is whatever the pool's spot state is at call time — no time-weighting: [2](#0-1) 

The project's own flow documentation states this explicitly: the guard only checks deviation from a static reference, never execution cost or manipulation resistance, and the pool's own fee tier is never applied to the priced quantity: [3](#0-2) 

And the pricing doc states the guard is opt-in and, if the two fields aren't both set, "leaves the chain unguarded": [4](#0-3) 

Attack shape: an attacker flash-loan-swaps against the exact Uniswap V4 pool the solver's `[vault.uniswapV4]` position tracks, pushing `sqrtPriceX96` far off its true mid; in the same transaction/block, the attacker (as the order's user, or coordinating with the order timing) places an intent order sized so the solver's automated pricing/fill path reads the manipulated spot price via `getExoticTokenPrice`, computes an inflated `output` requirement or an under-priced fill via `computeLegPolicyOutput`'s linear extension of that mid, and the solver's `IntentGateway.fillOrder` call (from `UniswapV4FundingPlanner.planWithdrawalForToken`, which withdraws LP liquidity priced from the same manipulated `sqrtPriceX96`) delivers output tokens far in excess of their real value. The attacker then reverses the flash-loan swap, restoring the pool and pocketing the mispriced difference — funds taken directly from the solver's escrowed LP position, delivered through `IntentGatewayV2.fillOrder`/`IntrinsicIntents._fillSameChain` or `ExtrinsicIntents._fillCrossChain`.

### Impact Explanation
This is concrete theft of funds: the solver's Uniswap V4 LP liquidity (their capital backing intent fills) is drained by a single attacker-controlled transaction, mirroring the SurgeBNB pattern — a spot-price-dependent computation with no flash-loan resistance, exploited atomically. Because `[vault.uniswapV4]`'s price guard (`referencePrice`/`maxDeviationBps`) is optional and the docs confirm omitting it leaves the pricing path fully exposed, any operator running default/unguarded config is directly vulnerable, and the loss is realized through a legitimate, unprivileged intent-fill transaction — no privileged access is required.

### Likelihood Explanation
Medium-High: exploitation requires only (1) a Simplex operator configured with `[vault.uniswapV4]` pool-based pricing and no `referencePrice`/`maxDeviationBps` guard (an explicitly documented, permitted configuration), and (2) a pool with liquidity thin enough to move materially within one flash-loaned transaction. This is standard, well-understood DeFi tooling (flash loans, Uniswap V4 swaps) and does not require any protocol bug beyond the missing manipulation-resistance in the pricing source.

### Recommendation
Require the `referencePrice`/`maxDeviationBps` guard (or an equivalent TWAP-based check) unconditionally whenever `[vault.uniswapV4]` pool-based pricing is enabled, rather than leaving it optional; alternatively, derive the venue price from a time-weighted average (e.g., Uniswap V4's observation/TWAP oracle) instead of the instantaneous `sqrtPriceX96`, and incorporate the position's own swap fee tier and a size/impact term into `computeLegPolicyOutput` rather than extending the mid linearly.

### Proof of Concept
Not independently executable from the index — the exploit requires a forked-mainnet or testnet harness (a funded Uniswap V4 pool + `[vault.uniswapV4]` Simplex config with no `referencePrice` set, an attacker contract performing a flash-loan swap to skew `sqrtPriceX96`, and an intent order sized to that skewed price) that this Ask session cannot execute. The reachable path and lack of default protection are demonstrated above by `computeDirectPoolPriceUsd` (raw spot price, no TWAP), `UniswapV4LiquidityState.refresh` (fetch-then-price with no staleness/impact bound), and the project's own docs confirming the guard is optional and the chain is "unguarded" without it.

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

Verified 2026-08-19.

```
resolveLegRates(...)

         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price

    -> rate = 1 / venueUsd

```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
