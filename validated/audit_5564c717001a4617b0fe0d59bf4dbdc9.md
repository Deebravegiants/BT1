### Title
Tron `IntentGatewayV2.placeOrder` credits escrow with pre-fee amounts for fee-on-transfer tokens, over-crediting `_orders` relative to actual token balance held - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron fork of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not measure the gateway's actual token balance before/after `safeTransferFrom` in the non-predispatch escrow path, unlike the canonical EVM `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol`), which explicitly snapshots balances to support fee-on-transfer tokens. As a result, for a fee-on-transfer ERC20 used as an order input, the Tron gateway credits `_orders[commitment][token]` with more tokens than it actually received and holds.

### Finding Description
In `evm/src/apps/IntentGatewayV2.sol` (the audited/fixed EVM version), the non-predispatch escrow branch explicitly accounts for fee-on-transfer tokens: [1](#0-0) 
It records `balBefore`, performs the transfer, and overwrites `order.inputs[i].amount` with the *actual* delta received before computing protocol fees and the commitment/escrow amounts: [2](#0-1) 

The Tron variant of the same function, `evm/tron/contracts/apps/IntentGatewayV2.sol`, computes `reducedInputs`/`commitment` from the caller-supplied `order.inputs[i].amount` *before* any transfer occurs: [3](#0-2) 

Then, in the non-predispatch escrow branch, it simply calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and credits `_orders[commitment][token] += reducedInputs[i].amount` — a value derived from the nominal `amount`, not from any measured balance delta: [4](#0-3) 

For a fee-on-transfer ERC20 token (e.g. USDT-style tokens with a nonzero fee, or any deflationary/rebasing token), the gateway will receive strictly less than `order.inputs[i].amount`. The escrow ledger entry `_orders[commitment][token]` will therefore record more tokens than the contract actually holds for that order.

### Impact Explanation
Because `_orders[commitment][token]` overstates the gateway's real, physically-held balance of the fee-on-transfer token for that commitment, any subsequent accounting operation against this ledger entry (fill/redeem via `RedeemEscrow`, or cancellation/refund via `withdraw`/`RefundEscrow` in the `cancelOrder` flow) will attempt to release/settle more tokens than the gateway actually possesses. Since the ERC20 balance of the gateway contract is a single shared pool across all outstanding commitments, this either:
- causes the withdrawal for this order to revert (denial of service / permanent freezing of the user's genuinely deposited funds, since the commitment can no longer be redeemed or cancelled correctly), or
- causes the shortfall to be silently paid out of tokens escrowed for *other* users' commitments in the same token, effectively draining/stealing funds from unrelated depositors when their own orders are later filled/refunded and found short.

This satisfies "concrete theft or permanent freezing of funds" via a single submitted `placeOrder` transaction using a fee-on-transfer token as an order input — a directly reachable path for any unprivileged user placing an order.

### Likelihood Explanation
Likelihood is high wherever the deployed instance of this Tron gateway variant is configured to accept a token that charges a transfer fee (fee-on-transfer, deflationary, or similar non-standard ERC20 behavior), which is common among stablecoins deployed with switchable fees (USDT-style) and various Tron-native TRC20 tokens. No special privileges are required — a single `placeOrder` call with such a token as an input asset triggers the mismatch. The bug is fully deterministic and reproducible; it is exactly the class of issue the sibling EVM contract was patched against, and the presence of dedicated fee-on-transfer regression tests for `evm/src/apps/IntentGatewayV2.sol` (e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`) confirms this was a known, fixed issue in the main EVM contract but the fix was not carried over to the Tron variant. [5](#0-4) 

### Recommendation
Apply the same balance-snapshot pattern used in `evm/src/apps/IntentGatewayV2.sol` to the Tron variant: for each non-native input token, record `balanceOf(address(this))` before calling `safeTransferFrom`, then set the actual received amount as `balanceOf(address(this)) - balBefore`, and derive `reducedInputs`, the `commitment`, and the `_orders[commitment][token]` escrow credit from this measured amount rather than the caller-supplied nominal `amount`. The same fix should also be verified/applied to the predispatch branch of the Tron contract (lines 387–449), which likewise trusts `order.inputs[i].amount` as the amount transferred out of the call dispatcher without reconciling it against measured balances after the sweep in the way the main EVM version does.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC20 token `FOT` with, say, a 1% transfer fee (as modeled by `FeeOnTransferToken` in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, lines 2691-2735). [6](#0-5) 
2. User approves the gateway for `1000 * 1e18 FOT` and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, no predispatch call.
3. In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `commitment` and `reducedInputs[0].amount` are computed from the full `1000e18` (minus only protocol fee if any) at lines 348-385, *before* the transfer.
4. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual `FOT` balance only increases by `990e18`.
5. `_orders[commitment][FOT] += reducedInputs[0].amount` credits `~1000e18` (or `1000e18` minus protocol fee) even though the gateway holds only `990e18` of `FOT` for this order — a 10e18 token shortfall recorded as available escrow.
6. When this order is later cancelled/refunded or otherwise redeemed against the recorded escrow amount, the shortfall causes either a revert (funds frozen) or is paid out of other users' pooled `FOT` balance in the same contract (funds stolen from other depositors).

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
