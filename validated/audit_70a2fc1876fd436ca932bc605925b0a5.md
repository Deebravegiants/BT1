### Title
Escrow Redemption Can Be Permanently Blocked by a Pausable/Blacklistable Input or Output Token, Trapping Funds in `IntentsBase` Escrow - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`ExtrinsicIntents.onAccept` and `IntrinsicIntents` fill/cancel paths release escrowed order funds by calling `_withdraw`, which performs an unconditional `IERC20.safeTransfer`/native transfer to a beneficiary address baked into the already-dispatched cross-chain message body. If the input/output token is a pausable or blacklistable ERC20 (e.g. USDC-style tokens) and the token issuer pauses the token or blacklists the specific beneficiary, `_withdraw` reverts every time it is invoked for that commitment, permanently preventing redemption of the escrowed funds — mirroring the reported `Pawn.sol`/`sRWA.sol` pattern where an NFT's own pause/blacklist control blocks a required action in another protocol's core settlement flow.

### Finding Description
`IntentsBase._withdraw` releases escrow unconditionally and reverts the whole call if any single token transfer fails: [1](#0-0) 

This function is invoked from `ExtrinsicIntents.onAccept` for both `RedeemEscrow` and `RefundEscrow` message kinds: [2](#0-1) 

The beneficiary address is fixed inside the ISMP message body at the time the `RedeemEscrow`/`RefundEscrow` request is dispatched (from the destination chain's `_cancelFromDest`/fill logic) and cannot be altered afterward: [3](#0-2) 

When `EvmHost.dispatchIncoming` delivers this message, a failing `onAccept` only deletes the request receipt so the *same* message can be retried later — it does not change the beneficiary or skip the failing token: [4](#0-3) 

If the escrowed/output token (e.g. a blacklist-capable stablecoin) pauses or blacklists the fixed beneficiary before or after the message is dispatched, every retry of the same message will deterministically revert in `IERC20.safeTransfer`, since there is no mechanism to change the beneficiary, skip the offending token leg, or otherwise route around the failure. The equivalent Tron `IntentGatewayV2.withdraw` has the identical unconditional-transfer-or-revert pattern: [5](#0-4) 

This is structurally the same root cause as the reported issue: a critical, single-shot settlement action (`liquidate`/burn in the original report, `_withdraw`/transfer here) is fully gated by an external token's pause/blacklist controls that are entirely outside the protocol's control, with no fallback path once that state is set for the fixed recipient.

### Impact Explanation
Once the destination-chain settlement message (`RedeemEscrow` or `RefundEscrow`) is dispatched with a beneficiary that becomes blacklisted (or while the token is globally paused), the escrowed input tokens for that order become permanently unredeemable: the solver cannot collect payment, and the user cannot recover a refund. Because the beneficiary is immutable once encoded into the dispatched message, and `_withdraw` has no per-token failure isolation, this is a full loss-of-access to escrowed funds for that order — a permanent freezing of funds condition, not merely a temporary delay, since the request will fail identically on every retry until the token issuer (an entity outside Hyperbridge's control) reverses the block.

### Likelihood Explanation
Any unprivileged user can place an order (`placeOrder`) using a widely-used pausable/blacklistable stablecoin (e.g., USDC/USDT-style tokens) as an input or output asset — a completely normal, expected usage pattern for an intents/bridging protocol, not requiring any Hyperbridge admin or governance action. Blacklisting of a specific address by a major stablecoin issuer is a real, observed event in production (sanctions/fraud enforcement), making the triggering condition realistic rather than purely theoretical.

### Recommendation
- Decouple settlement finality from the transferability of any single token: isolate per-token transfer failures in `_withdraw` (e.g. try/catch per leg) so a blocked token does not block release of the other escrowed assets or the whole order.
- Support a "pull" style claim / redirect-beneficiary escape hatch so a user whose designated beneficiary becomes blacklisted can still recover funds via an alternate address once the deadline or a grace period passes.
- Avoid baking an immutable beneficiary into a cross-chain message that, once dispatched, cannot be updated if the recipient later becomes unable to receive the token.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2`/`ExtrinsicIntents.placeOrder` with input token `USDC`, escrowing funds in `_orders`.
2. Order is filled on the destination chain, or cancelled/expires, triggering a `RedeemEscrow`/`RefundEscrow` POST request back to the source chain with the beneficiary hardcoded in the message body (`ExtrinsicIntents.sol:297-307`).
3. Before the message is delivered (or even during transit), USDC blacklists the beneficiary address (or pauses globally).
4. Relayer delivers the message; `EvmHost.dispatchIncoming` calls `onAccept` → `_withdraw` → `IERC20.safeTransfer(beneficiary, amount)` reverts (`IntentsBase.sol:451-470`).
5. `EvmHost.dispatchIncoming` catches the failure and deletes the receipt so the message can be retried (`EvmHost.sol:805-817`), but every subsequent retry with the same immutable beneficiary fails identically, leaving the escrowed tokens permanently stuck.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
