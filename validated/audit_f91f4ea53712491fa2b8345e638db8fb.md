Based on the research gathered, the strongest analog to the Kairos unbounded-loop DoS in this codebase is the `withdraw()` loop over `body.tokens` in the IntentGateway apps, reached from the permissionless `onAccept()` message-delivery path.

### Title
Unbounded `order.inputs` array lets an order-placer force a permanent DoS on Intent escrow settlement - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` iterates over `body.tokens`, transferring each escrowed input token to the beneficiary, whenever a `RedeemEscrow` or `RefundEscrow` cross-chain message is delivered via `onAccept()`. The array length is set by `order.inputs.length` at order placement, and I found no cap on this length in the reviewed placement logic.

### Finding Description
`withdraw()` loops over `body.tokens` performing an external call (native send or ERC-20 `transfer`) per element: [1](#0-0) 

This function is invoked from the permissionless message-delivery path: a relayer submits a proof through `IHandler.handlePostRequests` / `HandlerV2.handlePostRequests`, which calls `host.dispatchIncoming` to invoke the destination app's `onAccept()`, which decodes the `WithdrawalRequest` and calls `withdraw()`: [2](#0-1) 

`body.tokens` is populated from `order.inputs` at order-placement time (`placeOrder`), a user-supplied array (see the `WithdrawalRequest` construction path in tests referencing `order.inputs`): [3](#0-2) 

Unlike the ISMP batch handlers (`HandlerV2.handlePostRequests`, `handleGetResponses`, pallet-ismp's `handle_unsigned`/`dedup_requests`), where the array size is chosen and paid for by the same transaction sender submitting the batch (self-limiting, and additionally deduplicated against padding), here the array size is fixed by the *order placer* at `placeOrder` time but the gas cost of iterating it is paid later by an unrelated relayer delivering the settlement message. This mirrors the Kairos pattern: an attacker seeds an array cheaply (many low-value/dust `TokenInfo` entries as `order.inputs`), and a different, unprivileged party (the relayer completing settlement) is later forced to pay for iterating the full array in a single transaction.

### Impact Explanation
If `order.inputs.length` has no upper bound, an attacker can place an order with enough distinct input tokens that the `withdraw()` loop's external calls exceed the destination chain's block gas limit. Because `RedeemEscrow`/`RefundEscrow` messages must fully succeed for the escrow to move, this permanently blocks settlement of that order — the escrowed tokens can never be released or refunded, resulting in the "route unable to deliver messages" / permanent freezing of funds outcome accepted by the rubric.

### Likelihood Explanation
Requires only a normal user's `placeOrder` call with an attacker-chosen `TokenInfo[]` of many entries and no cross-chain trust assumptions — reachable from a single unprivileged transaction, matching the required threat model (submitted transaction/order). Likelihood depends entirely on whether `placeOrder` (not fully inspected in the accessible excerpts) enforces a maximum on `inputs.length`; I could not confirm the presence or absence of such a cap from the code reached during this investigation (no `MAX_INPUTS`/length-check constant was found via search, but the full `placeOrder` body was not completely read).

### Recommendation
Enforce an explicit, low maximum on `order.inputs.length` (and correspondingly on `order.output.assets.length`) at `placeOrder`/order-validation time, sized so the worst-case `withdraw()` gas cost stays well under the destination chain's block gas limit, and reject orders exceeding it.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.inputs` containing N (e.g., 500+) distinct dust `TokenInfo` entries, each with a nonzero `amount`, escrowing negligible value per token.
2. Attacker fills/cancels the order, causing `_body(RequestKind.RedeemEscrow, commitment, order.inputs, ...)` to be dispatched cross-chain.
3. A relayer eventually delivers the `PostRequest` via `handlePostRequests` → `onAccept` → `withdraw(body, ...)`.
4. `withdraw()`'s `for` loop over N tokens performs N external calls in one transaction; once N is large enough, the transaction consistently exceeds the block gas limit and reverts on every retry, permanently freezing the escrow.

**Note on confidence:** I was not able to fully verify whether `placeOrder` already caps `order.inputs.length` before this loop is ever reached (the relevant validation code was not fully retrieved within the available search budget). If such a cap already exists elsewhere in `IntentsBase`/`IntrinsicIntents`, this finding would be mitigated/invalid — this should be confirmed against the full `placeOrder` implementation before treating this as conclusively exploitable.

        address beneficiary = address(uint160(uint256(body.beneficiary)));

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
