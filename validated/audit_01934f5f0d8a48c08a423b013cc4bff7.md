### Title
Webhook shop-tenant binding is not covered by the HMAC, allowing cross-tenant webhook forgery - ([File: `lib/shopify_api/webhooks/request.rb`])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-signed content, while `Utils::HmacValidator` only validates the raw request body. Because the app's `api_secret_key` is a single, per-app secret shared by every shop that installs the app, any merchant of that app can obtain a genuinely-signed webhook and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, and the signature will still validate.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are pulled straight from HTTP headers and are never fed into `to_signable_string`: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. the body only) and compares it to the `hmac` header, then immediately trusts `request.shop` and `request.topic` (read from unauthenticated headers) to build the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate_signature` confirms this — the comparison is strictly against `verifiable_query.to_signable_string`, with no dependency on `shop`: [4](#0-3) 

The equality this breaks is: **shop authenticated by the HMAC (bytes actually signed = raw body) ≠ shop stored/used as the tenant key (`request.shop`, taken from an unsigned header)**. Because `Context.api_secret_key` is one shared secret for the whole app across all its shop installations (not a per-shop secret), any unprivileged merchant who installs the app on their own store legitimately receives webhooks with valid HMACs computed with that same shared secret. That merchant can capture such a webhook (same topic/body they legitimately generate on their own shop, e.g. an `orders/create` webhook) and replay the identical raw body + HMAC to the app's endpoint while substituting the `x-shopify-shop-domain`/`shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` because it never checked the shop header, and `Registry.process` will hand the attacker-chosen `shop` value to the app's `WebhookHandler`, causing the host application to process/act on data under the wrong tenant.

### Impact Explanation
This breaks tenant isolation: a merchant with no special privileges over other shops can make the host application believe a forged/replayed payload originated from a different, arbitrary shop, since the `shop` binding used for tenant-scoped side effects is not covered by the signature that is supposed to authenticate the message. This is a cross-tenant access vector against any app built on this gem's webhook processing.

### Likelihood Explanation
Exploitation only requires becoming a legitimate (even free/trial) installer of the target app — no access to `api_secret_key`, access tokens, or the victim's credentials is needed, since the secret is shared across all shops of the app. Capturing one's own valid webhook and replaying it with a modified shop header is trivial for any attacker who can reach the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them, e.g. by having Shopify sign a canonicalized string of headers+body, or by re-verifying the shop against a value obtained through an authenticated channel) so that `Utils::HmacValidator.validate` fails whenever any of these header-derived identity fields are altered relative to what was actually signed.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) so Shopify sends a request with body `B` and header `shopify-hmac-sha256: H`, computed with the app's single `api_secret_key`.
2. Capture that request.
3. Replay it to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but setting `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are unaffected by the header change; `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and it matches `H`, so `Registry.process` proceeds and invokes the handler with `shop: "victim.myshopify.com"`, letting the attacker inject/forge webhook-driven state for a shop they do not control.
