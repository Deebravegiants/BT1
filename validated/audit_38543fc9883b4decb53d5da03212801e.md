### Title
Webhook shop-domain header is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely through `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop` (and `topic`/`webhook_id`) are pulled from HTTP headers that are never part of the signed material. The `shop` value is nonetheless trusted and forwarded into `WebhookMetadata`, which the app-supplied handler uses to attribute the event to a tenant.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`HmacValidator.validate_signature` computes the signature from `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `Webhooks::Request`, `hmac` is read from the `shopify-hmac-sha256` header, `shop` is read from the `shopify-shop-domain` header, but `to_signable_string` returns only the raw request body: [3](#0-2) 

This means the equality the HMAC is supposed to guarantee is:
`HMAC_valid == (raw_body authentic)`, **not** `HMAC_valid == (shop_domain_header authentic)`.

Because `shop` (and `topic`/`webhook_id`) is acted on (passed to the handler as the tenant identifier) but is not part of the signed payload, an attacker who obtains any single genuine `(raw_body, hmac)` pair signed with the app's secret — e.g., by installing the app on their own development/test store and capturing one of their own legitimate webhook deliveries — can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (and topic) for a victim shop. `HmacValidator.validate` still succeeds because it only checks the body's signature, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

### Impact Explanation
Any app logic that trusts `WebhookMetadata#shop` to select/act on tenant data (e.g., look up the victim's session by shop domain, write shop-scoped records, trigger side effects "on behalf of" that shop) can be tricked into acting for the wrong tenant using an attacker-controlled shop value that was never covered by the authenticity check. This is a cross-tenant integrity issue: the binding between "HMAC-authenticated bytes" and "the shop the event is attributed to" is broken.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the app on any shop they control (common for public apps) or otherwise obtain one legitimate webhook delivery, then resend that exact body with a forged `shopify-shop-domain` header to the app's already-public webhook endpoint. No access token, `api_secret_key`, or privileged access is required — only observation of a body/HMAC pair the attacker can legitimately obtain via their own installation.

### Recommendation
Bind the identity fields to the HMAC by including `shop`, `topic`, and `webhook_id` in `to_signable_string` (or by independently validating a signed nonce/shop binding), or otherwise cryptographically tie the shop-domain header to the request signature rather than trusting it as free-form header data. At minimum, cross-check `request.shop` against session storage using an identifier established from a signed source before invoking handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body` and the resulting `shopify-hmac-sha256` value (both a function of the app's `api_secret_key`, which the attacker never needs to know directly since it's supplied by the server).
2. Attacker sends `POST /webhooks` to the target app with the same `raw_body`/`shopify-hmac-sha256`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` since it only checks `raw_body` against the HMAC [4](#0-3) .
4. `Registry.process` calls `handler.handle` with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to process an attacker-supplied event as if it originated from the victim shop.
