## Analysis

The external report's bug class — printing/logging highly sensitive secrets (private keys) to stdout/logs that get captured by log aggregation — has a direct analog in `orb-core`.

### Title
Unverified User Identity Data (including `identity_commitment`) Logged via `tracing::info!` Before Authenticity Verification - (File: `src/backend/user_status.rs`)

### Summary
`orb-core`'s user QR-code validation flow logs the full backend-returned `authenticated_app_data` (`orb_qr_link::UserData`), including the user's `identity_commitment` and `self_custody_public_key`, via `tracing::info!("User QR-data: {user_data:?}")` — and it does so *before* the data's authenticity is verified against the QR code's `user_data_hash`.

### Finding Description
In `request()` in `src/backend/user_status.rs`, the backend HTTP response is deserialized into `authenticated_app_data: Option<orb_qr_link::UserData>`. As soon as `backend_keys` and `user_data` are both present, the full struct is logged in debug form: [1](#0-0) 

Only *after* this logging does the code perform the HMAC-style verification of `user_data` against `qr_code.user_data_hash`: [2](#0-1) 

The logged struct carries `identity_commitment` (the user's biometric-derived identity commitment) and `self_custody_public_key`, both of which are subsequently unpacked into the orb's internal `UserData` and used to build the Personal Custody Package for signup: [3](#0-2) [4](#0-3) 

`tracing::info!` output is captured by systemd/journald and any downstream log-forwarding pipeline on the orb, exactly the class of exposure described in the report (stdout/stderr captured by container/systemd/cloud logs and readable by anyone with log access).

Similarly, elsewhere in the signup flow, raw operator/user QR-code structs (which include `user_id`) are logged at multiple points, e.g.: [5](#0-4) [6](#0-5) 

but the `identity_commitment` logged at `user_status.rs:164` is the most sensitive item, since it is a durable identifier tying a physical person's biometrics/enrollment to a specific signup and is normally treated as confidential material that flows only over authenticated channels (compare `secure_element.rs`'s handling of signing material, and `mecard.rs`'s explicit `Debug` redaction pattern for Wi-Fi `Password`, which shows the project is otherwise aware of this class of risk): [7](#0-6) 

No equivalent redaction exists for `orb_qr_link::UserData`'s `Debug` impl used at `user_status.rs:164`.

### Impact Explanation
Anyone with access to the orb's logs (local log files, journald, or any log-forwarding/telemetry backend the orb ships to) can read a user's `identity_commitment` and `self_custody_public_key` for every signup session performed on that orb — before that data has even been cryptographically verified as authentic. This is a biometric-identity data disclosure: the `identity_commitment` can be used to correlate or misattribute a user's identity across signups/sessions, and because the log entry precedes the `user_data.verify()` check, log-based auditing/monitoring cannot distinguish verified from unverified/potentially inconsistent identity data.

### Likelihood Explanation
This code path executes on every successful user-QR validation call during normal signup — no attacker action is required to trigger the logging; it is a straightforward, always-reachable code path in the standard signup flow, so any actor with log access will inevitably see this data for every user signup processed by the orb.

### Recommendation
Remove or redact the sensitive fields (`identity_commitment`, `self_custody_public_key`) from the log line, or implement a custom `Debug`/`Serialize` for `orb_qr_link::UserData` that masks sensitive fields (following the pattern already used for `mecard::Password`). Additionally, move any necessary logging to occur only after `user_data.verify()` succeeds, and log only non-sensitive metadata (e.g., `pcp_version`, `user_centric_signup`) rather than the full struct.

### Proof of Concept
1. Trigger a normal signup flow so that `backend::user_status::request()` is called with a valid user QR code.
2. Observe the orb's journald/systemd logs (or any log-forwarding sink configured for the orb).
3. Find the line `User QR-data: UserData { identity_commitment: "...", self_custody_public_key: "...", ... }` emitted at `src/backend/user_status.rs:164`, confirming the identity commitment and self-custody public key are present in plaintext logs, prior to hash verification.
