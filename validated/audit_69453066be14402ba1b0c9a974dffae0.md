### Title
Webhook `shop`, `topic`, and `webhook_id` Fields Are Trusted Without Being Covered by the HMAC Signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using `shop`, `topic`, and `webhook_id` values taken from HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC exclusively over that signable string: [2](#0-1) 

But `Registry.process` uses `request.topic`, `request.shop`, and `request.webhook_id` — all parsed straight from headers (`shopify-topic`, `shopify-shop-domain`, `shopify-webhook-id`) — to select the handler and build the `WebhookMetadata` object passed to app code: [3](#0-2) [4](#0-3) 

The equality that should hold is: *bytes verified by HMAC == bytes acted upon by the handler*. Here, only `raw_body` is verified, while `shop` (the tenant identifier), `topic`, and `webhook_id` are acted upon without being part of the signed payload — breaking that binding.

### Impact Explanation
Any party who can obtain one genuine `(raw_body, hmac)` pair for a webhook topic that their own shop can trigger (e.g., a merchant installing the app on their own store and receiving a legitimate `orders/create` webhook for their own order) can replay that exact body/HMAC pair directly to the app's registered webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-webhook-id`) header. Because the gem's `HmacValidator` never examines those headers, the forged request passes validation and `WebhookMetadata#shop` will report the attacker-chosen victim shop to the app's handler. If the app's webhook handler uses `data.shop` to determine which tenant's records to update (a common, documented pattern shown in `docs/usage/webhooks.md`), the attacker can cause data belonging to one tenant to be attributed to and written into another tenant's context — a cross-tenant integrity/access issue.

### Likelihood Explanation
Exploitation requires no privileged credentials: the attacker only needs (a) the ability to send arbitrary HTTP requests to the app's public webhook endpoint, and (b) a single legitimately-signed `(body, hmac)` pair, which any merchant using the app can generate for themselves via ordinary store activity (e.g., creating an order). Both conditions are trivially satisfiable by an unprivileged internet user/merchant, making this practically reachable, though its ultimate impact depends on how strictly a specific app's handler trusts `data.shop` versus independently re-verifying tenancy.

### Recommendation
Bind the tenant-identifying and dispatch-critical fields into the HMAC-covered material, or otherwise cryptographically tie the `shop-domain`, `topic`, and `webhook-id` headers to the signature (e.g., include them in the signable string used by `to_signable_string`, or require the host application to independently confirm the `shop` header against a shop known to have registered for that specific `webhook_id`/topic before trusting it).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real event (e.g., creates an order), causing Shopify to POST a legitimately HMAC-signed webhook (`raw_body`, `x-shopify-hmac-sha256`) to the app's endpoint.
2. Attacker captures that `(raw_body, hmac)` pair.
3. Attacker sends a new POST request directly to the app's public webhook endpoint with the same `raw_body` and `hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `raw_body` against the secret.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) dispatches to the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the body content actually originated from the attacker's own shop.
