### Title
Webhook `shop` (tenant) header is not covered by the HMAC, allowing cross-tenant webhook spoofing via HMAC replay - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw body via `Utils::HmacValidator.validate(request)`, then trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all taken directly from HTTP headers — to build the `WebhookMetadata` object passed to app handlers. The `Request#to_signable_string` method returns only `@raw_body`, so none of the identifying headers, especially `shop`, are cryptographically bound to the signature. [3](#0-2) [4](#0-3) 

### Finding Description
The equality that should hold is: `shop authenticated by HMAC == shop attributed to the tenant-scoped webhook data`. Here it does not: the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs a given app — it is an app-level credential, not a per-shop one. `HmacValidator.validate_signature` computes the signature only over `verifiable_query.to_signable_string`, which for `Webhooks::Request` is just the raw JSON body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no signature coverage: [5](#0-4) 

`Registry.process` then builds `WebhookMetadata` (documented as the tenant-scoping struct handed to app code) directly from these unauthenticated header values once the body-only HMAC check passes: [2](#0-1) [6](#0-5) 

Because the same `api_secret_key` produces a valid HMAC for *any* shop using that app, an attacker who is simply a merchant with a free/dev store that has installed the target app can trigger a real webhook delivery, capture the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair (a valid signature over that body under the app's shared secret), and then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` (and optionally `topic`/`webhook_id`) header for a different shop. `HmacValidator.validate` still returns `true` because it only checks the body, so `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen value while the `body` actually originated from the attacker's own store.

### Impact Explanation
Any app handler that keys per-tenant side effects (loading a shop's access token, updating shop-specific records, deduplicating by shop, driving billing/entitlement decisions, etc.) off of `WebhookMetadata#shop` is exposed to cross-tenant data confusion: attacker-controlled body content gets attributed to an arbitrary victim shop domain of the attacker's choosing. This is a cross-tenant boundary break stemming from this gem's own webhook verification design — the `shop` field is documented and handed to app code as trustworthy tenant metadata, but it is not part of the authenticated payload.

### Likelihood Explanation
Exploitation requires only steps available to any unprivileged user: (1) install the target Shopify app on a free/dev store to receive at least one legitimate webhook with a valid HMAC over some body, then (2) resend that captured request to the app's public webhook callback URL with the `shop-domain` header changed to any value. No access token, `api_secret_key`, or privileged access is required — the attacker never needs to know the secret because the valid HMAC was generated for them by Shopify's own delivery.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind `shop` to the payload before trusting it — analogous to how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signable string. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain and topic alongside the raw body, and `HmacValidator` should be recomputed over that expanded canonical string so a replayed body cannot be reattributed to a different shop. [7](#0-6) 

### Proof of Concept
1. Install the target app (any public Shopify app) on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header from the delivery — this is a valid `(body, hmac)` pair under the app's shared `api_secret_key`, as verified by: [8](#0-7) 
3. Replay that same body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` validates the HMAC (passes, since it only checks the body) and calls the handler with `WebhookMetadata#shop == "victim.myshopify.com"` even though the `body` is entirely attacker-supplied content from `attacker.myshopify.com`: [2](#0-1)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
