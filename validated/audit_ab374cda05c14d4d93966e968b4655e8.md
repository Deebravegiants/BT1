## Analysis

Confirmed: `Bonding.sol` has no generic ERC20 rescue/withdraw function for the protocol owner. The only sweep mechanism, `_sweepLTToOwner` [1](#0-0) , only runs inside `finalizeGraduation` and only sweeps the amount *above* `protectedLT` — it never touches `protectedLT` itself.

### Title
Direct LT donations to `Bonding` become permanently unrecoverable via the `protectedLT` mechanism - (File: packages/contracts/src/Bonding.sol)

### Summary
The report's bug class is "an unprivileged, permissionless action corrupts shared accounting that a downstream safety check relies on, permanently freezing state/funds until manual/no intervention exists." The alt.fun analog is a direct ERC20 transfer of the reserve LT to `Bonding` by any unrelated wallet, which is unconditionally classified as `protectedLT` on the *next* `finalizeGraduation` call and is then permanently excluded from both the LP deposit and the sweep-to-owner path, with no other recovery function in the contract.

### Finding Description
`finalizeGraduation` snapshots `protectedLT = balanceOf(this) - p.ltFromPair` at the top of every call [2](#0-1) . This value is deliberately treated as "off-limits" — assumed to belong to a concurrent graduation's escrow or to be stray dust, and is threaded through `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`, where the deposit allowance is capped at `balanceOf(this) - protectedLT` [3](#0-2) . At the end of `finalizeGraduation`, `_sweepLTToOwner(lt, protectedLT)` sweeps only the amount above `protectedLT`, leaving `protectedLT` itself untouched [1](#0-0) .

The documentation itself acknowledges the two cases this is meant to cover — concurrent graduation escrow, and "cross-token LT residue... old residue or a misdirected transfer sitting in Bonding" [4](#0-3)  — and states plainly that "contamination stays in `Bonding`" rather than being recovered. Unlike a concurrent graduation's escrow (which is eventually consumed when that graduation's own `finalizeGraduation` runs and treats it as its own `ltFromPair`), genuine third-party dust that is never any graduation's `ltFromPair` is never consumed by anyone — every subsequent `finalizeGraduation` on any token sharing that LT re-derives the exact same "protect it" classification and skips it again. There is no owner-callable rescue/withdraw function anywhere in `Bonding.sol` for arbitrary ERC20 balances (confirmed by search — the only sweep helper is `_sweepLTToOwner`, invoked exclusively from inside `finalizeGraduation` with `keep = protectedLT`).

This is directly reachable by any unrelated wallet: `IERC20(lt).transfer(bondingAddress, amount)` is a plain unprivileged ERC20 transfer, matching the allowed threat class ("direct ERC20 transfers of ... an LT into ... Bonding").

### Impact Explanation
Any LT sent directly to `Bonding` (accidentally or via `pair.skim` routing donations back into `Bonding` during Regime 2 pre-seed handling — see `_seedUniswapV2Direct`'s Regime 2 [5](#0-4) ) becomes permanently locked. Because there is no rescue function, this is a permanent freeze of third-party/protocol funds — the LT is neither returned to any user, added to a locked LP, nor swept to the protocol owner. Over time and across many graduations on shared LTs, this can accumulate meaningful, permanently stranded value. This satisfies the "permanent freezing of trader/creator/LP funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) a mistaken/careless direct transfer to `Bonding` by any wallet (plausible — it's the same contract address users interact with for other purposes), or (b) the donation-pre-seed defense's own `pair.skim(address(this))` call pulling attacker/donor funds into `Bonding` during Regime 2 handling, which the docs confirm is an intended, reachable code path for hostile-pre-seed graduations. No privileged role or precise timing is required — a single unprivileged transfer suffices.

### Recommendation
Add an owner-gated (or otherwise access-controlled) rescue function in `Bonding.sol` that can sweep LT/token balances beyond what is provably earmarked by any *currently pending* graduation (i.e., beyond the sum of all `pendingGraduation[*].ltFromPair` values still outstanding), so stray dust that is not eventually consumed by a real graduation can be recovered instead of being permanently and silently protected forever.

### Proof of Concept
1. Token A launches against LT `L` and reaches `Lifecycle.Curve`.
2. An unrelated wallet calls `IERC20(L).transfer(address(bonding), 1000e18)` — a plain, permissionless ERC20 transfer with no interaction with `Bonding`'s external functions.
3. Token A (or any other token sharing LT `L`) reaches its graduation threshold and someone calls `bonding.finalizeGraduation(tokenA)`.
4. Inside `finalizeGraduation`, `ltBalance = IERC20(L).balanceOf(address(this))` includes the donated `1000e18`; `protectedLT = ltBalance - p.ltFromPair` therefore includes the donation [6](#0-5) .
5. `_routerDepositAndDispose` deliberately excludes `protectedLT` from the deposit [7](#0-6) , and `_sweepLTToOwner(lt, protectedLT)` only sweeps amounts *above* `protectedLT`, so the donated `1000e18` is never moved [8](#0-7) .
6. No token B graduation will ever consume this dust either, since it was never anyone's `ltFromPair` — it will be re-classified as `protectedLT` and preserved on every future `finalizeGraduation` call on `Bonding`, indefinitely.
