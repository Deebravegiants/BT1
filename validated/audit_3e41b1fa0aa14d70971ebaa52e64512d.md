## Title
Unrestricted `CallDispatcher.dispatch()` allows theft of any residual assets left on the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

## Summary
`CallDispatcher` is a persistent, singleton contract referenced by address in `IntentsBase._params.dispatcher` and used by both `IntentGatewayV2.placeOrder` (predispatch) and `IntentsBase._execute` (postdispatch) to run solver/user-supplied `Call[]` batches against escrowed funds. Its `dispatch(bytes)` function has no access-control modifier — any address, not just the intent gateway, can call it directly and force the dispatcher to execute arbitrary `Call`s with arbitrary `value`, using whatever balance the dispatcher happens to hold at the time. [1](#0-0) 

## Finding Description
`CallDispatcher.dispatch()` is declared `external` with no `restrict`/`onlyGateway`/`onlyOwner` guard, and the contract also accepts arbitrary ETH via a permissionless `receive()`: [2](#0-1) 

The gateway's normal flows are careful to sweep back *every* token amount they know about after executing predispatch/postdispatch calldata: `placeOrder`'s predispatch phase transfers the *entire* dispatcher balance of each `order.inputs[i].token` back to the gateway, and `IntentsBase._execute` sweeps the entire dispatcher balance of every token enumerated in `order.output.assets` back to the base contract. [3](#0-2) [4](#0-3) 

Both sweeps are scoped only to tokens the caller explicitly enumerated (`order.inputs`/`order.output.assets`). Any token that the executed `Call[]` batch causes to land on the dispatcher but that is *not* in that enumerated list — e.g. a reward/airdrop token from a DEX swap, dust from a multi-hop route, or a token a malicious/careless solver's postdispatch calldata intentionally leaves behind — is never swept and remains sitting on the dispatcher indefinitely. Because `dispatch()` has no access control, that residual balance (and any ETH sent to `receive()`) is immediately and permanently drainable by any unrelated third party: they simply call `CallDispatcher.dispatch(...)` directly with a `Call{to: token, data: abi.encodeWithSelector(transfer.selector, attacker, balance)}`.

This is functionally the same bug class as the referenced CVE: a component meant to execute only trusted, tightly-scoped instructions instead executes arbitrary attacker-supplied instructions in a context that holds value/privilege, because the entry point that triggers execution is not restricted to the intended caller.

## Impact Explanation
Any value that ends up parked on the shared `CallDispatcher` — through solver postdispatch calldata that doesn't fully account for every token it touches, a fee-on-transfer/rebasing token quirk, or an accidental direct transfer/airdrop to the dispatcher address — is concrete, permanent, theftable value: any address can call `dispatch()` unauthenticated and route it to themselves. This is a direct theft-of-funds primitive reachable from a single, unprivileged transaction with no relation to order ownership, solver selection, or governance.

## Likelihood Explanation
Likelihood is High: `dispatch()` requires no special permission, no proof, and no interaction with the intent-gateway flow at all — an attacker only needs to monitor the dispatcher's token/ETH balance and race to call `dispatch()` whenever a nonzero balance appears (e.g. after any postdispatch call that produces a token outside the declared `order.output.assets` set, or a solver's swap route producing extra reward tokens). Because the dispatcher is a shared, long-lived contract used by every order, the attack surface accumulates over the life of the protocol, not just within a single transaction.

## Recommendation
Restrict `CallDispatcher.dispatch()` to only the authorized caller(s) — e.g. the specific `IntentsBase`/`IntentGatewayV2` instance(s) configured via `_params.dispatcher` — using an `onlyGateway`/`restrict` modifier analogous to the `restrict(_hostParams.handler)` pattern already used elsewhere in the codebase (see `EvmHost.dispatchIncoming`). Alternatively, make the dispatcher a per-call/per-order ephemeral contract (e.g., deployed via `CREATE2` and self-destructed or left with zero balance guaranteed by construction) so it can never accumulate residual value between calls. [5](#0-4) 

## Proof of Concept
1. A solver fills a cross-chain order whose `order.output.call` swaps output tokens through a DEX aggregator that also emits a small amount of a reward token (e.g., a liquidity-mining token) directly to the caller of the swap — which is the `CallDispatcher`, since `IntentsBase._execute` routes the call through `ICallDispatcher(dispatcher).dispatch(order.output.call)`.
2. `_execute` only builds sweep calls for `order.output.assets` (the tokens the order actually specifies), so the reward token balance is left on `CallDispatcher`.
3. An attacker, watching the dispatcher's token balances, calls `CallDispatcher.dispatch(abi.encode([Call({to: rewardToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — no relation to the order, no proof required — and receives the reward tokens. [6](#0-5) [4](#0-3)

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
