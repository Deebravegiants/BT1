### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from raw HTTP headers, but `to_signable_string` — the value the HMAC is computed over and checked against — only includes the raw request body. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler, without that field ever being covered by the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from headers with no cryptographic binding to the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) via `Utils::HmacValidator.validate`, then immediately constructs `WebhookMetadata` using `request.shop`, `request.topic`, etc., and hands it to the app-registered handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and compares it to the received `hmac`: [4](#0-3) 

This breaks the intended identity binding: `HMAC(secret, raw_body) == received_hmac` is verified, but the actual security-relevant equality the app relies on — `header_shop_domain == body's originating shop` — is never checked. An unprivileged internet user who has observed (or replayed) any single valid webhook delivery (e.g., from a public/sharable event, a leaked log, or a shop they themselves control on the same app) can resend the identical body and HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header value. `Request` and `HmacValidator` will accept it as valid, and `Registry.process` will hand the app a `WebhookMetadata` claiming the payload belongs to the victim shop, even though it never originated from Shopify for that tenant. Because `WebhookHandler#handle` implementations in host apps use `data.shop` to select the tenant's session/database row to write into, this becomes a mechanism for cross-tenant data confusion driven entirely by an unauthenticated header, directly analogous to the `fd_store` bug class where a field flowing through unverified (`fd_shred34_t` contents / `shred34->pkts`) was acted upon downstream without validation against the signed/trusted portion.

### Impact Explanation
This lets an unprivileged attacker who can capture or generate one valid signed webhook body (e.g. by installing/owning any shop that has the app installed, since `api_secret_key` is shared across all shops for a given app) forge webhook deliveries attributed to an arbitrary victim shop domain. Any host application logic that keys writes, session lookups, or data mutation off `WebhookMetadata#shop` — the value this gem hands it — can be tricked into applying attacker-controlled body content under another tenant's identity, i.e. cross-tenant access/data corruption.

### Likelihood Explanation
Moderate-to-high: an attacker needs only network access to the app's webhook endpoint and one legitimately-signed body from any shop using the same app (which is common in multi-tenant public apps where the attacker can self-install a free/trial shop). No leaked credentials, `client_secret`, or access token is required — only interaction with the app's own public webhook receiver.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`) header values in the HMAC-signed content computed by `to_signable_string`, or otherwise cryptographically bind the header-derived `shop` to the verified payload before it is exposed via `WebhookMetadata`, so `Registry.process` cannot deliver a `shop` value that wasn't part of what was authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or captures a webhook delivery some other way) and receives a legitimate webhook POST with body `B`, headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body `B` and same `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, matches `H`, and returns true: [5](#0-4) 
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B), ...)`: [3](#0-2) 
5. The host application's handler processes attacker-controlled body content as if it were legitimately delivered for `victim-shop.myshopify.com`.
