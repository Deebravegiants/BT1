### Title
`Wallet.getMnemonic()` bypasses the lock gate, allowing mnemonic disclosure while locked and independent of `#isLocked` state - ([File: features/wallet/module/wallet.js])

### Summary
`getMnemonic` in `Wallet` never calls `#assertWalletIsUnlocked()`, unlike `addSeed` and `removeManySeeds`, which do call it. It only relies on `#getSeed({ passphrase })` decrypting the on-disk `walletStorage` entry directly, so the mnemonic can be retrieved regardless of `this.#isLocked`, as long as the correct passphrase (or an auto-generated passphrase) is known/derivable.

### Finding Description
`getMnemonic` is defined as: [1](#0-0) 

It calls `#getSeed({ passphrase })` directly: [2](#0-1) 

Contrast this with `addSeed` and `removeManySeeds`, which explicitly call `#assertWalletIsUnlocked()` before touching secret material: [3](#0-2) [4](#0-3) 

`lock()` only removes seeds from the in-memory `#keychain` and flips `#isLocked = true`; it does not touch `walletStorage`, so the encrypted seed on disk remains fully accessible via `#getSeed`: [5](#0-4) 

If `config.useAutoGeneratedPassword` is true, `#getSeed` will silently substitute the stored `GENERATED_PASSPHRASE_KEY` value when no passphrase is supplied, meaning `getMnemonic()` (no args) succeeds with zero attacker-known secrets even while locked: [2](#0-1) 

The existing test suite documents this exact behavior as expected/working, not as an attack: `wallet.getMnemonic() to work without providing a passphrase` after `wallet.create()` (no `lock()` in that test, but no unlock assertion either), and the `wallet.import` scenarios explicitly test `locked: true` followed directly by calling `wallet.import`, not `getMnemonic` while locked. Critically, there is no existing test that calls `wallet.lock()` followed by `wallet.getMnemonic()` and asserts a throw — the only enforced-lock test found is for `addSeed`: `'throws if wallet is locked'`. [6](#0-5) 

Up the call chain, `Application.getMnemonic` simply forwards to `this.#wallet.getMnemonic(opts)` with no additional lock check of its own: [7](#0-6) 

This is exposed to RPC/dapp callers via the headless SDK API (`applicationWalletApi.getMnemonic` / `exodus.application.getMnemonic`), reachable from ordinary API/RPC callers without any additional authorization layer visible in this code path: [8](#0-7) 

### Impact Explanation
This allows full mnemonic/seed disclosure — the highest-severity wallet secret — from an unprivileged caller who can invoke the RPC/API surface, as long as they can supply (or the wallet is configured to auto-generate and internally use) the correct passphrase. The lock state (`#isLocked`) is meant to be the gate preventing secret export while the wallet is locked, but `getMnemonic` does not check it at all, violating the "Locked means locked" invariant. This matches Hydra's "full wallet secret disclosure / unauthorized signing-equivalent" bounty impact category, since mnemonic disclosure is equivalent to complete compromise of all derived keys.

### Likelihood Explanation
Feasibility depends on the passphrase requirement:
- If `config.useAutoGeneratedPassword = true` and no explicit passphrase is set by the user, `getMnemonic()` with no arguments succeeds without any secret input from the attacker — this is trivially and always reproducible whenever this config flag is enabled, entirely independent of lock state.
- If the user has set an explicit passphrase, the attacker must know/guess it, which is a stronger precondition, but this is the same passphrase-only protection that already backs `unlock()` — the vulnerability here is specifically that `getMnemonic()` provides an entirely separate, unlock-independent path to the same secret, meaning `lock()` provides zero additional protection against mnemonic exfiltration when password support is unused or auto-generated.

The core defect (missing `#assertWalletIsUnlocked()` call, present in sibling methods `addSeed`/`removeManySeeds`) is present in the code regardless of config and is fully reproducible via unit test.

### Recommendation
Add `await this.#assertWalletIsUnlocked()` at the start of `getMnemonic` (and consider `changePassphrase`, which has a similar gap), consistent with `addSeed`/`removeManySeeds`, so mnemonic export is only possible when the wallet has been explicitly unlocked in the current session, not merely by knowing/deriving the storage passphrase.

### Proof of Concept
Unit test in `features/wallet/module/__tests__/index.test.js`:
```js
it('getMnemonic() throws when wallet is locked', async () => {
  await wallet.create() // may use useAutoGeneratedPassword or explicit passphrase per describe.each matrix
  await wallet.unlock()
  await wallet.lock()

  await expect(wallet.isLocked()).resolves.toBe(true)
  await expect(wallet.getMnemonic()).rejects.toThrow(/locked/i)
})
```
Fuzz across the existing `describe.each` matrices for `usePassword` / `useAutoGeneratedPassword` combinations and with/without explicit `passphrase` argument, asserting in every combination that `getMnemonic()` rejects while `isLocked()` is `true`, and only succeeds after a corresponding `unlock()` call.

  getMnemonic = async ({ passphrase, seedId } = {}) => {
    try {
      // always need to get primary seed first to make sure the user entered the right passphrase
      // even if passed seedId is not primary
      const { mnemonic } = await this.#getSeed({ passphrase })
      if (!mnemonic) throw new Error('Wrong password. Try again.')

      if (!seedId || (await this.getPrimarySeedId()) === seedId) return mnemonic

      // Sequential, as sync fallback is slower
      for (const seed of await this.#getExtraSeeds()) {
        if (seedId !== (await getSeedId(seed.seed))) continue
        if (!seed.mnemonic) throw new Error('No mnemonic found for seedId.')
        return seed.mnemonic
      }

      throw new Error('No seed matches seedId.')
    } catch (err) {
      if (err.message === 'No seed matches seedId.') {
        this.#logger.debug('getMnemonic() failed: no seed matches seedId.')
        throw err
      }

      this.#logger.debug('getMnemonic() failed: wrong password')
      throw new Error('Wrong password. Try again.')
    }
  }
