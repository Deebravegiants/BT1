### Title
Rebasing/yield-bearing ERC20 escrowed in IntentGateway causes permanently stuck rewards or a stuck/unwithdrawable escrow - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`/`IntentsBase` escrows arbitrary ERC20 tokens supplied by users as order inputs and holds them in the gateway contract for the duration of the cross-chain settlement window (from `placeOrder` until the `RedeemEscrow`/`RefundEscrow` ISMP message is delivered and proven on the source chain). The escrowed amount is recorded once, as a fixed integer, in `_orders[commitment][token]`, and later paid out via a fixed-amount `IERC20.transfer`. If the escrowed input token is a rebasing/yield-bearing asset (e.g. `stETH`), the contract's actual token balance drifts away from this fixed bookkeeping value over the holding period — exactly the bug class described in the referenced Sherlock report (M‑9, Mellow `DepositQueue`).

### Finding Description
When a user places an order, `placeOrder` transfers the exact `order.inputs[i].amount` of the input token into the gateway and stores that number verbatim as the escrow accounting value: [1](#0-0) 

For cross-chain orders, these tokens then sit in the gateway contract for the full settlement window: the solver fills on the destination chain, dispatches a `RedeemEscrow` POST request, and only once that message is authenticated on the source chain via Hyperbridge's consensus/state proofs does `withdraw`/`_withdraw` run: [2](#0-1) [3](#0-2) 

The same holding period applies to cancellations, which additionally require a `DispatchGet` storage-proof round trip before `withdraw()` is called: [4](#0-3) 

Crucially, the payout in `_withdraw` transfers the exact stored `amount` from `body.tokens[i]` — a static number set at `placeOrder` time — and decrements the bookkeeping mapping by that same static number: [5](#0-4) 

Nowhere in this flow is `IERC20(token).balanceOf(address(this))` re-checked against the live balance for a rebasing token. This is the same root cause as the Mellow `DepositQueue` bug: the contract escrows a snapshot amount, then holds the token for an indeterminate period during which a rebase can move the real balance away from that snapshot, and the release logic only ever operates on the fixed, stale amount:

- **Positive rebase** (e.g., a normal `stETH` daily positive rebase): the gateway's real balance of that token grows above `_orders[commitment][token]` while escrowed. `_withdraw`/`withdraw` only ever transfers the recorded (pre-rebase) `amount`, so the excess balance is never released to the user, the solver, or the protocol. There is no mechanism that captures this drift — `DustCollected`/`SweepDust` only track the deliberate protocol-fee and predispatch-dispatcher-sweep dust computed at `placeOrder` time, not balance changes that occur afterward while tokens are escrowed: [6](#0-5) 
The rebase yield is permanently and unrecoverably stuck in the gateway contract.

- **Negative rebase** (any rebasing token whose balance can also decrease, or an economic/slashing event affecting the wrapped asset): the gateway's real balance drops below the sum of `_orders[commitment][token]` for all outstanding orders in that token. When `_withdraw` tries to `safeTransfer(beneficiary, amount)` for the recorded amount, the transfer reverts because the contract does not hold enough of the token. Since `_withdraw` iterates over *all* tokens in the `WithdrawalRequest` and reverts atomically on any transfer failure, this can block release of an entire multi-token order (not just the rebasing leg), freezing solver payouts (`RedeemEscrow`) and user refunds (`RefundEscrow`) alike for affected commitments.

### Impact Explanation
This breaks the accounting invariant that `_orders[commitment][token]` accurately represents the redeemable claim on the gateway's token holdings. Any positive-yield rebase permanently strands funds inside the `IntentGatewayV2`/`IntentsBase` contract with no sweep path, and any negative movement of the underlying balance can revert and permanently block escrow release for legitimate solver fills and user refunds/cancellations — a freezing-of-funds condition reachable by any unprivileged user simply by placing a cross-chain order whose input token is a rebasing ERC20. Given the multi-chain, general-purpose nature of `IntentGatewayV2` (it accepts arbitrary ERC20 tokens as inputs, not merely stablecoins), and that popular liquid-staking tokens like `stETH` are natural candidates for solvers/users to route as intent inputs, this is a realistic Medium-severity impact: unbacked/unaccounted value accrual and potential freezing of escrowed value, without any admin/governance action required.

### Likelihood Explanation
Likelihood is driven entirely by ordinary use of the protocol: any user placing a cross-chain (or even same-chain, given fill delays/partial fills across blocks) intent order with a rebasing token as an input triggers this. No malicious actor, privileged role, or unusual chain configuration is needed — only the passage of time between `placeOrder` and settlement, which is inherent to cross-chain ISMP message delivery (consensus proof generation + relaying + verification).

### Recommendation
- Reject known rebasing/fee-on-rebalance tokens as valid `order.inputs`/`order.output.assets` tokens (e.g., via an allow/deny-list check in `placeOrder`), or
- Require wrapped, non-rebasing equivalents (e.g., `wstETH` instead of `stETH`) at the integration/documentation level, or
- If rebasing tokens must be supported, track escrow using `balanceOf`-delta accounting (shares-based bookkeeping) rather than a fixed amount snapshot, and add an explicit sweep function for any balance drift accrued while tokens are escrowed, mirroring the mitigation suggested in the referenced report.

### Proof of Concept
1. Deploy `IntentGatewayV2` with a mock rebasing ERC20 (mirroring the report's `MockRebaseERC20`) registered as a supported input token.
2. `user` calls `placeOrder` with `order.inputs[0] = {token: mockRebaseToken, amount: X}` for a cross-chain order; `_orders[commitment][mockRebaseToken] = X` is recorded (see `IntentGatewayV2.sol:361-373`).
3. Before the `RedeemEscrow`/`RefundEscrow` settlement message is delivered (which requires waiting for ISMP consensus proof relay, per `docs/.../intent-gateway/overview.mdx:50-69`), increase the mock token's share price (simulating a Lido-style positive rebase), causing `mockRebaseToken.balanceOf(gateway)` to exceed `X`.
4. Once settlement occurs, `_withdraw` transfers exactly `X` to the beneficiary (`IntentsBase.sol:451-470`) — the excess balance remains stranded in the gateway with no code path to claim it.
5. Alternatively, simulate a negative rebase before settlement so `mockRebaseToken.balanceOf(gateway) < X`; the subsequent `safeTransfer(beneficiary, X)` in `_withdraw` reverts, blocking release of the entire `WithdrawalRequest` (including any other, non-rebasing tokens bundled in the same order).

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;

### Settlement

When the settlement message arrives on the source chain, the ISMP host calls `onAccept()`. The handler authenticates the message (verifying it came from a known IntentGateway instance), decodes the `WithdrawalRequest`, and calls `withdraw()` which:

1. Marks the order as filled (`_filled[commitment] = solver`)
2. Transfers each escrowed input token to the solver
3. Releases stored transaction fees (in fee token) to the solver
4. Emits `EscrowReleased(commitment, tokens)`

### Cancellation

There are two modes for cross-chain cancellation:

`cancelOrder` emits `OrderCancelled(commitment, canceller)` on the chain the cancellation is initiated from, before it routes to either path below. `EscrowRefunded` remains the terminal event, on the source chain, once the escrow is actually returned.

**Cancel from source chain**: The user calls `cancelOrder()` on the source chain, which dispatches a `DispatchGet` storage read request to query the destination chain's fill status. The `CancelOptions.height` must be greater than `order.deadline` — this ensures the proof is taken from a block after the order has expired. A relayer processes this request on Hyperbridge by providing storage proofs from the destination chain. If the storage slot for `_filled[commitment]` is empty (order unfilled), Hyperbridge dispatches a response back to the source chain. The `onGetResponse` handler verifies the empty proof and calls `withdraw()` to refund the escrowed tokens to the user. If the order was filled, the response contains a non-empty value and the handler reverts with `Filled()`.

![Cancel from Source Chain](./images/intent-gateway-cancel-source.svg)

**Cancel from destination chain**: Before the deadline, only the order owner can call `cancelOrder()` on the destination chain. After the deadline, anyone can cancel. The function marks the order as cancelled locally (`_filled[commitment] = user`) to prevent future fills, then dispatches a cross-chain `RefundEscrow` message back to the source chain. When the source chain receives this message via `onAccept()`, it calls `withdraw()` to refund the escrowed tokens to the user and emits `EscrowRefunded(commitment, tokens)`.
