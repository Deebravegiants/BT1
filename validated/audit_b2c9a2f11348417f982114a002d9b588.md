## Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` / `SweepDust` permanently loses escrowed funds for non-reverting tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` escrows and later releases ERC20 tokens using a raw low-level `.call` with the `IERC20.transfer` selector, checking only that the call itself did not revert (`success`) but never inspecting the ABI-decoded boolean return value. Tokens that signal transfer failure by returning `false` (rather than reverting) will cause the contract to treat a failed payout as successful, permanently marking escrow as released/refunded/swept while the beneficiary receives nothing.

In `withdraw()`, which is invoked from the permissionless `onAccept` entrypoint whenever a relayer delivers a `RedeemEscrow`/`RefundEscrow` ISMP message, escrowed ERC20 tokens are paid out like this: [1](#0-0) 

The same unchecked pattern is used for the fee-token payout in the same function: [2](#0-1) 

and for the governance-triggered `SweepDust` handler: [3](#0-2) 

`success` here only reflects whether the external call reverted; it does not decode/validate the returned `bool` from `IERC20.transfer`. Per the ERC20 standard, a conforming token is permitted to return `false` instead of reverting to signal failure (this is the exact bug class flagged in the referenced Sherlock report for BufferRouter/BufferBinaryOptions). Notably, the same file imports and uses `SafeERC20` correctly on the *deposit* side (`safeTransferFrom` in the escrow-collection logic), showing the payout side is an inconsistent regression relative to the intended safe-transfer pattern used elsewhere in this contract: [4](#0-3) 

Regardless of whether the actual transfer succeeds, `withdraw()` unconditionally updates escrow accounting and marks the order as filled/refunded: [5](#0-4) 

### Impact Explanation
If any escrowed input or fee token used with this deployment is a token that returns `false` on failed transfer instead of reverting (this includes some pausable/blacklist tokens whose `transfer` returns `false` for blacklisted/frozen recipients, and Tron's native TRC20 tokens are known to have more return-value/EVM-compat inconsistencies than mainstream EVM chains, which is precisely why this Tron-specific fork exists), then:
- `_orders[body.commitment][token] -= amount` still executes, permanently zeroing/decrementing the escrow accounting for tokens that were never actually delivered.
- `_filled[body.commitment]` is set and `EscrowReleased`/`EscrowRefunded` is emitted, closing out the order as though beneficiaries were paid.
- The tokens remain stuck in the `IntentGatewayV2` contract with no remaining accounting path to recover them for the intended beneficiary — a permanent freezing/loss of user/solver funds.

This is reachable purely by relaying a legitimate cross-chain `RedeemEscrow`/`RefundEscrow` message (a normal, permissionless part of the intents flow) once the underlying token exhibits non-reverting failure semantics; no admin/governance privilege is required to trigger the loss.

### Likelihood Explanation
Likelihood depends on the token deployed as the intent's input/fee token exhibiting non-reverting `transfer` failures (e.g., blacklist/pause-and-return-false tokens, or Tron TRC20 tokens with EVM-compat return-value quirks — the reason this file is a distinct Tron port in the first place). This is a realistic, not purely theoretical, class of ERC20/TRC20 tokens, and the contract already anticipates non-standard tokens elsewhere (e.g., dust reconciliation via balance-delta checks in the pre-dispatch path), showing the codebase is otherwise aware of similar token quirks.

### Recommendation
Replace the raw `.call(...)` + `success`-only check with `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` in this same file) for the payout paths in `withdraw()` and the `SweepDust` handler, so both call-reverted and returned-false failures cause the whole transaction (and therefore the escrow-state mutation) to revert atomically.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an input token `T` whose `transfer` implementation returns `false` when the recipient is blacklisted, without reverting (a common real-world TRC20/ERC20 pattern).
2. A user creates an order escrowing `T` with the eventual beneficiary later becoming blacklisted by `T`'s issuer (or the beneficiary address is already blacklisted at fill time, e.g. a malicious solver front-running/redirecting a fill to a blacklisted address for griefing).
3. A relayer submits a valid `RedeemEscrow` proof; `onAccept` → `withdraw()` runs: `token.call(...transfer...)` succeeds at the EVM-call level but returns `false`; `success` is `true`; `_orders[...][token] -= amount` executes and `EscrowReleased` fires.
4. `T` tokens never leave the `IntentGatewayV2` contract, yet the escrow record is deleted/decremented and the order is marked filled — the tokens are now permanently unrecoverable through the intents flow.
