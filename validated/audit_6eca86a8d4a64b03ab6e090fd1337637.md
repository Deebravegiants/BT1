### Title
Permanently frozen creator fees in `FeeVault` if a creator's address is later blacklisted by USDC - ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` pays out a creator's entire pooled USDC balance by transferring directly to `msg.sender`, with no admin-assisted recovery or redirect path. If a token creator's address is later blacklisted by the USDC issuer (Circle routinely blacklists sanctioned/compromised addresses), that creator's entire accrued `creatorBalance` becomes permanently stuck inside `FeeVault` with no on-chain mechanism to move it to a fresh address, mirroring the referenced `STADIUM_ADDRESS`-blacklist freeze in the Sparkn `Distributor`.

### Finding Description
`FeeVault.accrue` credits `creator` (looked up live from `Bonding.tokenInfo(token).creator` via `Zap._accrueFee` → `bonding_.creatorOf(tokenAddress)`) into `creatorBalance[creator]` [1](#0-0) . The only exit for that balance is `claim()`, which unconditionally transfers to `msg.sender`:

```solidity
function claim() external nonReentrant returns (uint256 amount) {
    FeeVaultStorage storage $ = _s();
    amount = $.creatorBalance[msg.sender];
    if (amount == 0) revert NothingToClaim();
    $.creatorBalance[msg.sender] = 0;
    $.totalAccruedCreator -= amount;
    $.usdc.safeTransfer(msg.sender, amount);
    emit CreatorFeesClaimed(msg.sender, amount);
}
``` [2](#0-1) 

If USDC (`$.usdc`) blacklists the specific `creator` address before they claim, `safeTransfer(msg.sender, amount)` reverts unconditionally for that address, exactly as `Distributor._commissionTransfer` reverted for a blacklisted `STADIUM_ADDRESS`. Unlike `FeeVault.feeTo` — which the docs explicitly note is rotatable via the owner-only `setFeeTo` [3](#0-2)  — there is no analogous mechanism for `creatorBalance`. `Bonding.transferCreator` only redirects *future* fee attribution ("transfers role and future fee attribution") [4](#0-3) ; it does not move funds already sitting in `creatorBalance[oldCreator]`. `sweepDonations()` only sweeps the *unbacked* surplus above `totalAccruedCreator + protocolBalance` [5](#0-4) , so a backed, blacklisted creator's balance is never reachable by that path either. There is no owner function that can reassign or force-pay a stuck `creatorBalance[creator]` to a different address.

### Impact Explanation
Once a creator address is blacklisted by the USDC operator, 100% of that creator's already-accrued (and any future, since accrual still succeeds — only the pull-side `claim()` fails) USDC fee balance is permanently locked in the `FeeVault` contract with no recovery path for the creator or the protocol owner. This is a permanent freeze of creator funds, satisfying the High-severity bar of the referenced report's bug class (irrecoverable blacklist-induced fund lock), scoped here to the affected creator's balance rather than the whole vault.

### Likelihood Explanation
Likelihood is lower than the original report (creator addresses are less likely global sanction targets than a protocol's own stadium/treasury address), but it is fully realistic: any creator whose EOA is later flagged by Circle (e.g., through unrelated activity, a hack, or regulatory action) permanently loses access to legitimately earned fees, and this can also be self-inflicted/griefed by a creator deliberately launching from a blacklist-prone address and then having a third party report/trigger the blacklist, since `creatorOf` attribution and `claim()`'s recipient are both tied to the same immutable key with no admin override.

### Recommendation
Add an owner-gated (or creator-signed, e.g. EIP-712) `migrateCreatorBalance(address oldCreator, address newCreator)` function in `FeeVault` that moves `creatorBalance[oldCreator]` to `newCreator]` (updating `lifetimeCreatorEarned` bookkeeping consistently), or allow `claim()` to accept a `to` parameter so the creator can direct the payout to any non-blacklisted address before their own address is flagged.

### Proof of Concept
1. `Zap.buy`/`Zap.sell` accrues fees for `creator` via `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)` [6](#0-5) , growing `creatorBalance[creator]`.
2. The USDC operator blacklists `creator`'s address (external, out-of-protocol event).
3. `creator` calls `FeeVault.claim()`; `$.usdc.safeTransfer(msg.sender, amount)` reverts because `msg.sender` is blacklisted by USDC's `transfer`/`transferFrom` guard.
4. `creator` cannot claim; `Bonding.transferCreator` only reroutes future accruals, leaving the existing `creatorBalance[creator]` permanently stuck; no owner function exists to move or force-pay it out.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }

        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));

**File:** docs/contracts-scope.md (L117-121)
```markdown
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.
```
