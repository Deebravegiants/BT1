### Title
`ShopifyAPI::Auth::Oauth.validate_auth_callback` sends the app's `client_secret` to an unsanitized `shop` host - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.exchange_token` all call `Utils::ShopValidator.sanitize!(shop)` before using the shop value to build the `HttpClient` that sends `client_secret` to `https://#{shop}/admin/oauth/access_token` [1](#0-0) [2](#0-1) . `Oauth.validate_auth_callback`, however, uses `auth_query.shop` directly, with no call to `ShopValidator.sanitize!`, to build the `null_session` that is handed to `HttpClient`, which derives the request host straight from `session.shop` [3](#0-2) [4](#0-3) .

### Finding Description
`HmacValidator.validate` binds `code`, `host`, `shop`, `state`, `timestamp` together via HMAC computed with `Context.api_secret_key` [5](#0-4) [6](#0-5) . `validate_auth_callback` checks this HMAC and the `state` cookie, then trusts `auth_query.shop` as-is to construct the session used for the token exchange request [7](#0-6) . Unlike every other credential-issuing flow in this gem (`ClientCredentials`, `RefreshToken`, `TokenExchange` sanitize `shop` against `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before it is used to build the request host [8](#0-7) ), the classic OAuth authorization-code callback path (`Oauth.validate_auth_callback`) has no equivalent check — the identity binding "the host that receives `client_secret` == a verified `*.myshopify.com`/trusted Shopify domain" is not enforced here, breaking the pattern established elsewhere in the same library.

This mirrors the reported bug class: just as `IncreaseLock()` omitted the `MIN_LOCK_DURATION` check that `lockTokens` enforced (allowing bypass of an invariant that other code paths uphold), `validate_auth_callback` omits the `ShopValidator.sanitize!` check that sibling OAuth/token flows enforce, allowing the `shop` binding to be used unsanitized when constructing the URL that carries the app's `client_secret`.

### Impact Explanation
If `auth_query.shop` can be influenced to a value outside the trusted domain set while still passing HMAC/state validation (e.g., a caller integrating with a non-Shopify-verified query, or via an old/rotated secret path in `HmacValidator.validate` covering `old_api_secret_key`), the gem would issue a POST containing `client_id` and `client_secret` to a host chosen by that `shop` value rather than to Shopify's own myshopify.com domain — leaking the app's `client_secret` to an attacker-controlled endpoint (SSRF carrying the app's credentials).

### Likelihood Explanation
Likelihood is limited in the strict, normal flow because Shopify itself computes the HMAC over the authorize-callback query using the real `client_secret`, and Shopify only issues that HMAC for a shop it has already validated as a genuine myshopify.com store. Exploitation would require a scenario where the `AuthQuery` reaching `validate_auth_callback` is not exclusively the one generated by Shopify's own redirect (e.g., an app path that constructs/relays an `AuthQuery` from other input, or a secret-rotation window where `old_api_secret_key` matches an attacker-obtainable value) — I could not find and did not verify such a call path within the indexed library code, so this should be treated as a defense-in-depth gap consistent with the library's own established pattern rather than a confirmed exploitable path from an unprivileged, credential-less attacker.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before constructing `null_session`/`Session.from`, mirroring `ClientCredentials`, `RefreshToken`, and `TokenExchange`, so the `shop` value used to build the request host that receives `client_secret` is always constrained to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not independently verifiable within the indexed code: I could not locate a call path where `AuthQuery.shop` is populated from anything other than Shopify's own signed authorize-callback redirect, so a concrete exploit sequence reachable by an unprivileged attacker without the app's `api_secret_key`/`client_secret` could not be confirmed. The finding is reported as an inconsistency versus the gem's own established `ShopValidator.sanitize!` pattern in the sibling OAuth/token-exchange flows [7](#0-6) [9](#0-8) .

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
