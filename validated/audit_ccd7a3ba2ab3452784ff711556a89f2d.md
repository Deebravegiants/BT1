### Title
Webhook shop-domain and topic are trusted for tenant dispatch without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator` cryptographically authenticates the body content but never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Webhooks::Registry.process` nonetheless uses those unauthenticated header values to select the handler and to populate `WebhookMetadata.shop`, which host applications use as the tenant key for the incoming event.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only `@raw_body` is signed. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then dispatches using the unauthenticated `topic`/`shop` values and forwards `request.shop` into `WebhookMetadata`, which downstream handlers use to scope/identify the tenant: [3](#0-2) 

Because `HmacValidator.validate` (and `validate_signature`) only checks `verifiable_query.to_signable_string` against the shared `Context.api_secret_key`: [4](#0-3) 

the same `api_secret_key` is shared across *every* shop/tenant that has installed the app. Any merchant that has installed the app is an "unprivileged" party relative to other tenants, and legitimately receives real webhooks addressed to their own store with a body + HMAC that is valid under the app's single shared secret. Because the header fields (shop-domain, topic, webhook-id) are not included in the signed content, that merchant can capture one genuinely-signed `(body, hmac)` pair from their own store and replay it directly to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different shop. `HmacValidator.validate` will still return `true` (the body/HMAC pair is untouched and valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop, even though the shop identity was never authenticated.

This is the same class of bug the external report describes — a value that is *used* in a security-relevant decision without being covered by the value that is cryptographically verified (there, `priceMarkup`/`priceUpdateThreshold` precision vs. the verified `PRICE_DENOMINATOR` scale; here, `shop-domain` tenant identity vs. the verified request body).

### Impact Explanation
A host application built on this gem uses `WebhookMetadata.shop` (and `.topic`) as the tenant/session key to decide which shop's data or session to update in response to a webhook (e.g. syncing order data, revoking access on `app/uninstalled`, etc.). Forging the shop while keeping a validly-signed body lets one tenant inject events that are processed as if they originated from a different, victim tenant — a cross-tenant confusion/impersonation that can lead to state corruption or unauthorized actions being taken against another merchant's data, without the attacker ever possessing `api_secret_key` or any victim credential.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (unprivileged) merchant with the app installed — a low bar that is explicitly allowed under the rules ("unprivileged internet user"). No secret, token, or victim credential is needed; the attacker only needs one authentic webhook delivery to their own store (trivial to obtain) and the ability to POST to the app's public webhook endpoint with modified headers.

### Recommendation
Bind the tenant-identifying headers into the signed content, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or independently verify `shop` against the session/shop registered for the given `webhook_id`) before trusting them in `Registry.process` and `WebhookMetadata`. At minimum, cross-check `request.shop` against an out-of-band, per-tenant record before acting on it.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` and capture a real webhook delivery, e.g. body `{"id":123}` with headers `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in [5](#0-4)  succeeds because it only checks the (untouched) body.
4. `Registry.process` in [3](#0-2)  invokes the registered handler with `WebhookMetadata` claiming `shop: "victim.myshopify.com"`, causing the host app to process attacker-controlled data under the victim's tenant identity.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

            result

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
