### Title
Unchecked ERC20 `transfer` return value in Tron `IntentGatewayV2.withdraw()` allows silent transfer failures that finalize escrow release - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds and protocol fees using a raw low-level `.call()` with the `IERC20.transfer` selector, and only checks the boolean `success` return of the *call itself* (i.e. that the callee didn't revert). It never decodes/validates the ABI-encoded `bool` payload that ERC20 `transfer` is supposed to return. For any input/output token that follows the pre-EIP20-strict pattern of returning `false` on failure instead of reverting, the gateway will treat a failed transfer as a success, permanently finalizing escrow accounting while the beneficiary receives nothing.

### Finding Description
`withdraw()` — invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages and from `onGetResponse()` for cancellation refunds — releases escrowed tokens like this: [1](#0-0) 

Specifically:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
```
and for fees:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same unchecked pattern is used in the `SweepDust` handler inside `onAccept`: [3](#0-2) 

In each case, `success` from a raw `.call()` only reflects whether the callee reverted — it says nothing about the ABI-encoded return data. Any ERC20 token that implements the legacy pattern (`return false` on insufficient balance/allowance rather than reverting) will make this call return `success == true` with return data encoding `false`. The gateway ignores that returned boolean entirely, so:
- `_orders[body.commitment][token] -= amount` proceeds and the escrow accounting is decremented/zeroed even though the beneficiary got nothing.
- `_filled[body.commitment] = beneficiary` is set, permanently finalizing the order.
- `EscrowReleased`/`EscrowRefunded` events fire, signalling success to indexers/relayers/users.

This is precisely the bug class described in the external report (Cooler.sol not checking `transferFrom`/`transfer` return values) reproduced in a Hyperbridge production contract reachable by an ordinary relayer delivering a `RedeemEscrow`/`RefundEscrow` POST message (the entry point any relayer can submit once they have a valid state proof) or by anyone triggering a `GET` response for order cancellation.

Note the EVM mainline `IntentGatewayV2.sol`/`IntentsBase.sol` use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` throughout (`using SafeERC20 for IERC20;`), which correctly enforces the return-value check. The Tron contract, however, replaced these with raw `.call()` invocations (likely due to Tron TVM incompatibilities with `SafeERC20`), and in doing so dropped the return-value validation, reintroducing the vulnerability class the rest of the codebase avoids.

### Impact Explanation
If an input or output token used in an order on Tron is a non-reverting ERC20 (returns `false` on failure), the escrow-release path silently "succeeds" while tokens never move to the intended beneficiary. This causes:
- Permanent loss of the beneficiary's expected funds (solver claims escrow but the transfer silently fails, or a refund silently fails leaving the user's actual balance unmoved even though the order is marked filled/refunded and cannot be retried).
- Escrow accounting desync — `_orders[commitment][token]` is decremented without the funds actually leaving the contract, so leftover balances become permanently stranded/unaccounted dust that no path can sweep for the rightful owner.
- Because `_filled[commitment]` is set, the failed release can never be retried through the normal flow, making the loss permanent.

This satisfies "concrete theft or permanent freezing of funds" via a token-bridge/intents-escrow code path reachable by an unprivileged relayer/solver delivering a settlement message.

### Likelihood Explanation
Exploitability depends only on at least one order using a non-standard-compliant ERC20 as an input or output token — a routine and realistic condition for any permissionless intents system that accepts arbitrary ERC20s. No privileged role is required; any relayer delivering a valid `RedeemEscrow`/`RefundEscrow`/GET-response message triggers `withdraw()`, and the flawed check is unconditionally reached whenever the token is such an ERC20.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept()` with a proper return-value check, e.g. use OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` elsewhere in the file) or manually decode and validate the returned boolean when the call succeeds and data length is non-zero:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success || (data.length != 0 && !abi.decode(data, (bool)))) revert TransferFailed();
```

### Proof of Concept
1. Deploy a token `FalseERC20` whose `transfer`/`transferFrom` return `false` (instead of reverting) when the sender lacks funds or when the recipient is blacklisted, without reverting — a legal ERC20 pattern.
2. A user calls `placeOrder` escrowing `FalseERC20` as an input (or a solver's output uses this token).
3. Once a solver fills the order and dispatches the `RedeemEscrow` (or a refund/`RefundEscrow`) message, a relayer delivers it and `onAccept` → `withdraw()` runs:
   `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true`, data decodes to `false` (e.g., because the contract's internal transfer logic hits an edge case returning false, or because of an intentionally malicious/broken token).
4. `withdraw()` proceeds: decrements `_orders[commitment][token]`, sets `_filled[commitment] = beneficiary`, emits `EscrowReleased`. The beneficiary's on-chain balance is unchanged — the funds are neither delivered nor recoverable, since the order is now marked filled.

                if (!success) revert TransferFailed();
            }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
