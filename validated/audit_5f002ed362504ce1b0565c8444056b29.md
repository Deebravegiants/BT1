## Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body/HMAC pair is valid, then hands the handler the header-derived `shop` value with no cryptographic binding between the two. This is the same double-counting/identity-binding defect pattern as the reported Portfolio.sol bug: a value that drives downstream trust decisions (`shop`) is decoupled from the value that was actually authenticated (`raw_body`).

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body` — the `shop` (from the `shopify-shop-domain` / `x-shopify-shop-domain` header) is never included in the signed payload: [3](#0-2) 

`HmacValidator.validate` verifies exactly that signable string against the HMAC: [4](#0-3) 

`Registry.process` performs no additional check that the `shop` header corresponds to the request that was actually HMAC-authenticated; it passes the raw header-derived `shop` straight into the handler metadata: [5](#0-4) 

This breaks the intended identity binding: `authenticated(raw_body) == authenticated(shop)` is assumed true by callers of `handler.handle`, but the code only proves `authenticated(raw_body)`; `shop` is attacker-controlled and independent of the signature.

### Impact Explanation
Because the HMAC only covers the body, any `(raw_body, hmac)` pair that is valid for one shop remains valid verbatim regardless of the `shop` header value sent alongside it. An unprivileged attacker who controls their own shop (a normal, unprivileged install of the target app) can:
1. Trigger a real webhook delivery to their own endpoint from their own store, capturing a legitimate `(raw_body, hmac)` pair signed with the app's `client_secret`.
2. Replay that exact body/HMAC pair directly to the app's public webhook endpoint, but with the `shopify-shop-domain` header rewritten to a victim shop's domain.
3. `Utils::HmacValidator.validate` still returns `true` (body unchanged), and `Registry.process` calls the handler with `shop: <victim shop>` and `body: <attacker-authored order/refund/etc. content>`.

If the host application's webhook handler uses `data.shop` to look up that shop's stored session/access token to act on the (attacker-supplied) `data.body` (the documented/expected pattern for webhook handlers in this gem), the attacker causes the app to process forged event data attributed to a victim tenant, using the victim's own stored credentials — a cross-tenant data/action confusion. This satisfies the Critical "cross-tenant access" impact bucket in the rules.

### Likelihood Explanation
Likelihood is high for any app that: (a) allows self-serve/dev installs (so an attacker can generate a legitimately-signed body from their own store), and (b) keys webhook handling logic off `data.shop` (the exact usage pattern demonstrated in the gem's own webhook tests, e.g. `assert_equal(@shop, data.shop)`). No secrets, tokens, or privileged access are required — only the ability to receive one real webhook on a shop the attacker controls and to send a raw HTTP POST to the app's public webhook endpoint.

### Recommendation
Include the shop identity in the HMAC-verified surface, or otherwise cryptographically bind it, e.g.:
- Reject/ignore the `shop` header for trust decisions and instead resolve the shop strictly from data that is itself covered by the signature (e.g., embed/verify shop identity via the topic-specific payload, or require a secondary signed channel), or
- If Shopify's webhook delivery model does not sign headers, treat `request.shop` as merely advisory and require applications to cross-check it against an independent, already-authenticated source (e.g., correlate with the `webhook_id` via a GraphQL query to Shopify using the shop's own stored session) before using it to select credentials, and document this requirement clearly in `lib/shopify_api/webhooks/registry.rb`.

### Proof of Concept
```ruby
# 1. Attacker installs app on their own (attacker-controlled) shop, triggers any webhook
#    (e.g. orders/create) and captures the raw POST body + shopify-hmac-sha256 header
#    that Shopify sent — this is a fully valid signed pair for the attacker's own shop.

captured_body = attacker_captured_raw_body
captured_hmac_header = attacker_captured_hmac_header

# 2. Attacker crafts a new request to the same app endpoint, keeping body/hmac identical,
#    but swapping the shop-domain header to the victim's shop.
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => captured_hmac_header,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, not signed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# 3. HMAC validation succeeds because it only checks raw_body vs hmac:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process invokes the handler with shop == "victim-shop.myshopify.com"
#    and body == attacker-controlled content, despite the victim never sending this webhook.
ShopifyAPI::Webhooks::Registry.process(request)
