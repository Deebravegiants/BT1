### Title
Retroactive application of a changed `pnl_numerator/pnl_denominator` to unsettled trading fees causes unfair value transfer between LPs and the `pnl_owner` - ([File: program/src/processor.rs])

### Summary
`ArrakisV2` accrues manager fees continuously but only realizes the current `managerFeeBPS` at the moment of a `mint`/`burn`, so changing the fee rate retroactively re-prices fees that accrued under the old rate. Raydium AMM has a structurally similar defect: trading-fee growth ("pnl") that accumulates in the pool's `k`-invariant is only crystallized into `need_take_pnl_coin/pc` at the next `Deposit`, `Withdraw`, or `WithdrawPnl` call, using whichever `amm.fees.pnl_numerator`/`pnl_denominator` is current at that moment, not the rate(s) that were in effect while the fees were actually accruing.

### Finding Description
`calc_take_pnl` computes the amount of accumulated `k`-invariant growth since the last checkpoint (`target.calc_pnl_x`/`calc_pnl_y`) and splits it into an LP-owned portion and a manager/protocol-owned portion (`need_take_pnl_pc`/`need_take_pnl_coin`) using the *current* `amm.fees.pnl_numerator`/`pnl_denominator`: [1](#0-0) 

This settlement is only triggered from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — it is not run on every swap: [2](#0-1) [3](#0-2) 

The fee ratios (`pnl_numerator`, `pnl_denominator`, `trade_fee_numerator`, etc.) live in the `Fees` struct on the `AmmInfo` account and can be overwritten wholesale by the admin via `SetParams`/`AmmParams::Fees`, which simply validates the new fractions and replaces `amm.fees` in one shot — with no reconciliation of previously-accrued, unsettled growth against the old rate: [4](#0-3) [5](#0-4) 

Because `target_orders.calc_pnl_x/calc_pnl_y` is a checkpoint that can lag arbitrarily far behind the current pool state (it only advances when `Deposit`/`Withdraw`/`WithdrawPnl` is executed), all `k`-growth accumulated between two settlements — regardless of how much of it occurred before vs. after a `pnl_numerator` change — is split entirely according to whatever ratio is active at the moment the *next* unprivileged `Deposit` or `Withdraw` transaction happens to trigger `calc_take_pnl`. This is the same root cause as the reported Arrakis issue: fee-rate parameter changes are applied retroactively over an unsettled accrual window instead of being prorated by time, and an ordinary user's `Deposit`/`Withdraw` instruction (not the admin) is what actually crystallizes the incorrect split.

### Impact Explanation
Whichever `Deposit` or `Withdraw` transaction lands first after a `pnl_numerator` change absorbs the entire unsettled `k`-growth at the new rate:
- If the rate is raised, a disproportionate share of trading fees that economically belong to existing LPs (accrued while the old, lower rate applied) is siphoned into `need_take_pnl_pc`/`need_take_pnl_coin`, redeemable only by the `pnl_owner`, permanently reducing `total_pc_without_take_pnl`/`total_coin_without_take_pnl` used to price LP shares and diluting existing LPs.
- If the rate is lowered, LPs who deposit right after the change effectively "buy in" under-pricing a manager-fee liability that should have been settled at the higher historical rate, unfairly diluting LPs who held through the change.

This directly affects unbacked/insolvent LP-share pricing computed in `process_deposit`/`process_withdraw` via `InvariantPool::exchange_token_to_pool` / `exchange_pool_to_token`, which use `total_coin_without_take_pnl`/`total_pc_without_take_pnl` immediately after `calc_take_pnl` runs: [6](#0-5) 

### Likelihood Explanation
Realizing this requires two ordinary, always-reachable ingredients: (1) a window with no `Deposit`/`Withdraw`/`WithdrawPnl` while swap-driven `k` grows (common for low-traffic settlement periods), and (2) any `SetParams(AmmParams::Fees)` update to `pnl_numerator`/`pnl_denominator` during that window. The actual value-transfer is triggered by a completely unprivileged `Deposit` or `Withdraw` transaction — the attacker/beneficiary does not need special permissions to crystallize the mispriced settlement, they simply need to be the first (or can even race) to submit a `Deposit`/`Withdraw` after the fee change.

### Recommendation
Settle (crystallize) `need_take_pnl_coin`/`need_take_pnl_pc` against the currently active `pnl_numerator`/`pnl_denominator` *before* `SetParams` is allowed to change those fields, so that the checkpoint (`target.calc_pnl_x`/`calc_pnl_y`) is always brought current at each rate change. Concretely, `process_set_params` should force a `calc_take_pnl`-equivalent settlement (updating `target_orders` and `need_take_pnl_*`) whenever `AmmParams::Fees` modifies `pnl_numerator`/`pnl_denominator`, so that accrued growth is always split at the rate that was in effect while it accrued.

### Proof of Concept
1. Pool has been active with swaps for some time; no `Deposit`/`Withdraw`/`WithdrawPnl` has been submitted recently, so `target_orders.calc_pnl_x/calc_pnl_y` lags well behind current reserves — a large unsettled `k`-growth (`diff_x`/`diff_y`) exists.
2. Admin calls `set_params`/`UpdateConfigAccount`-analog `SetParams(AmmParams::Fees, fees)` ( [5](#0-4) ), raising `pnl_numerator/pnl_denominator` from the historical value (e.g., default `12/100`, [7](#0-6) ) to a much higher ratio.
3. Any unprivileged user submits an ordinary `Deposit` (or `Withdraw`) instruction. `process_deposit` calls `calc_take_pnl` ( [2](#0-1) ), which computes `delta_x`/`delta_y` over the entire unsettled window using the newly-raised `pnl_numerator`, moving a disproportionately large amount into `need_take_pnl_pc`/`need_take_pnl_coin` and reducing `total_pc_without_take_pnl`/`total_coin_without_take_pnl`.
4. LP share pricing for the incoming deposit (and for any subsequent withdrawal by existing holders) is computed off this already-slashed total ( [6](#0-5) ), so existing LPs who held their position through the entire unsettled window lose value that should have been split at the old, lower manager-fee rate, while the `pnl_owner` recovers an outsized `need_take_pnl_pc`/`need_take_pnl_coin` balance via `WithdrawPnl` ( [8](#0-7) ).
