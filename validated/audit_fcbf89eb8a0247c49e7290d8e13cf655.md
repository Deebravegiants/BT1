### Title
Webhook HMAC does not bind the `shop` domain, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching to the app's handler with a shop identity. In reality, the HMAC signature validated by `Utils::HmacValidator.validate` only covers the raw request body, never the `shop` value that the handler uses to determine which tenant/session the event belongs to. Any party who can obtain one valid `(body, hmac)` pair for a topic they legitimately subscribe to (e.g. their own installed shop) can replay it with an arbitrary forged `X-Shopify-Shop-Domain` header, and the library will treat it as an authenticated event for that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) [2](#0-1) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to `to_signable_string`: [1](#0-0) 

`Registry.process` validates the HMAC and then unconditionally forwards `request.shop` (the unauthenticated header) into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identity: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`: [4](#0-3) 

For `Request`, `to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, or `webhook_id`: [2](#0-1) 

This breaks the identity binding: `shop_authenticated_by_hmac (∅, since HMAC covers body only)` ≠ `shop_used_for_dispatch (request.shop, an unauthenticated header)`. Compare this with `Auth::Oauth::AuthQuery#to_signable_string`, where `shop` **is** part of the signed parameter set: [5](#0-4) 

so the OAuth path correctly binds `shop`, but the webhook path does not — an inconsistency that is the root cause.

The gem's own documentation instructs app developers to trust `data.shop` after `Registry.process`: [6](#0-5) [7](#0-6) 

### Impact Explanation
An unprivileged internet user who controls a legitimate, installed shop (a normal, non-privileged merchant tenant of the app) can subscribe to a webhook topic for their own store and capture a valid `(raw_body, hmac)` pair signed with the app's `client_secret` — no elevated privileges are required, only a normal install. They can then send this same body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will accept it as authentic (HMAC check passes, since it never covered `shop`), and the handler receives `WebhookMetadata` claiming the event is for the victim shop. Any app logic keyed off `data.shop` (e.g., updating that shop's local records, triggering side effects tied to the victim's session/account) executes under the wrong tenant — this is a cross-tenant data integrity/spoofing issue reachable purely by an unprivileged attacker who never needs the app's `client_secret`.

### Likelihood Explanation
High likelihood for any multi-tenant app using this gem as documented: obtaining a valid `(body, hmac)` sample is trivial for any merchant who installs the app (they receive real webhooks for their own store), and replaying it with a different `shop` header requires no cryptographic secret at all — only a basic HTTP replay/tamper capability against the app's public webhook endpoint.

### Recommendation
Include `shop` (and ideally `topic`/`webhook-id`) in the HMAC-signable representation for webhooks, or otherwise cryptographically bind the shop domain to the signed payload before it is trusted for per-tenant dispatch. At minimum, `Utils::HmacValidator.validate` should be extended (or a webhook-specific validator introduced) so `to_signable_string` for `Webhooks::Request` incorporates the shop-domain header, mirroring the binding already done for `Auth::Oauth::AuthQuery#to_signable_string`. Documentation in `docs/usage/webhooks.md` should be corrected to avoid implying that `Registry.process` authenticates the `shop` field.

### Proof of Concept
1. App developer installs the gem and registers a webhook handler as shown in `docs/usage/webhooks.md`, trusting `data.shop` to select tenant context.
2. Attacker installs the app on their own store `attacker.myshopify.com` and triggers the subscribed event (e.g., `orders/create`) on their own store, capturing the real webhook POST — raw body `B` and header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the shared `client_secret`).
3. Attacker replays the exact same body `B` and header `H` to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (= `B`) and compares to `H` — validation succeeds since `shop` was never part of the signed string.
5. The handler's `handle(data:)` receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, `body` from the attacker's own order, and processes it as an authenticated event for the victim tenant.

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`.     )
    render json: {success: true}.to_json
  end
