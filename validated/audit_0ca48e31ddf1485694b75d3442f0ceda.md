### Title
Donation-inflated `tokenBalance()` underflows `Router._computeBuy`'s overflow cap, permanently DoSing the curve - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's real token balance when the constant-product output would exceed it, then back-calculates the LT actually required via `cappedReserveToken = reserveToken - tokensOut`. This subtraction assumes `reserveToken >= tokensOut` (i.e. `reserveToken >= realBalance`). The codebase's own regression tests prove that assumption is false: a token-donation attack (buy-then-transfer tokens directly into the pair) can drive `pair.tokenBalance() > pair.reserveToken()`. When that state exists and a buy lands on the overflow-cap branch, `cappedReserveToken` underflows and reverts, permanently bricking every subsequent buy on that curve — an availability failure directly analogous to CVE-2016-8884's "incomplete fix" pattern, where a known bug class (donation-driven `realBalance > reserveToken`) was partially patched in one call path but left reachable in another.

### Finding Description
`Router._computeBuy` (called by `Router.buy`, which is the only path `Bonding.buy`/`Zap.buy` use): [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // underflows if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

The comment and existing invariant test (`test_inv_virtualReserveAlwaysExceedsRealBalance` in `packages/contracts/test/GraduationInvariants.t.sol`) assert `pair.tokenBalance() < reserve0` always holds "under normal operation," making the `cappedReserveToken == 0` guard the only defensive check envisioned. But the protocol's own donation-attack regression test demonstrates the invariant can be broken by an ordinary, unprivileged trade sequence: [2](#0-1) 

`_stageDonationAttack` buys a large amount of tokens off the curve (`bonding.buy`) and then `transfer`s the received tokens directly to the pair address, which raises `pair.tokenBalance()` (a live `balanceOf` read) without moving `reserveToken` (the stored AMM reserve, only mutated by `Pair.swap`). `test_donation_realBalanceExceedsReserveToken` confirms `realBalance > reserveToken` is reachable this way.

The only fix that shipped for this bug class lives in `Bonding.previewLtUntilGraduation` (per `test_donation_previewLtUntilGraduation_returnsThresholdLeg`), which guards that specific view function's own subtraction. It does **not** touch `Router._computeBuy`. Once `realBalance > reserveToken` exists on a pair, any subsequent buy whose unclamped `tokensOut` exceeds `realBalance` — a normal, not-even-oversized buy near the curve's remaining real supply — enters the overflow-cap branch and executes `reserveToken - tokensOut` with `tokensOut = realBalance > reserveToken`, causing an unconditional Solidity 0.8 panic revert. Every future `Zap.buy`/`Bonding.buy` on that token then reverts identically, since the donation is irrevocable (tokens are stuck in the pair and can't be un-donated), permanently freezing trading (and graduation, since graduation is only triggered inline at the end of a successful buy) on that curve.

### Impact Explanation
This is a permanent denial-of-service that freezes trader funds economically: once the donation-inflated state exists, the token can never buy again (all buys on the affected pair revert), and since graduation triggers are only evaluated inside a successful buy (`Bonding.canGraduate` is checked at the end of `_executeBuy`), the token can also become permanently stuck in the `Curve` lifecycle, unable to graduate via the supply trigger (`tokenBalance() == 0` can never be satisfied since donations only inflate `tokenBalance()` further) unless the USD trigger fires from a sell-less rate pump. Holders' curve-side capital becomes effectively frozen — sells still work (only `_computeBuy` is affected), but buys are permanently bricked, which breaks the "brick resistance" property the protocol explicitly designs around elsewhere (e.g., `finalizeGraduation`'s regime handling) but failed to apply here.

### Likelihood Explanation
High. The precondition (`realBalance > reserveToken`) requires only an unprivileged wallet to (1) buy a large chunk of tokens near the curve's remaining real supply and (2) `transfer` those tokens directly to the pair address — both ordinary ERC20/Zap operations reachable by any trader, and the protocol's own test suite (`_stageDonationAttack`) demonstrates the exact sequence works with off-the-shelf `bonding.buy` + `Token.transfer`. No special role or timing is needed, and the attack is cost-bounded by the LT spent on the initial buy (which the attacker eventually can partially recover via the K-invariant on the buy itself), while griefing every other trader out of the ability to buy again.

### Recommendation
Apply the same underflow guard used in `previewLtUntilGraduation` inside `Router._computeBuy`'s overflow-cap branch: when `realBalance >= reserveToken`, either clamp `cappedReserveToken` to a floor (treating the excess as already-graduated supply) or revert with a dedicated, non-panic error and route the caller to trigger graduation (mirroring how the supply trigger is meant to have already fired before this state is reachable). More robust: recompute/clamp `tokensOut` against `min(realBalance, reserveToken)` before the cap branch runs, so the subtraction can never underflow regardless of how `tokenBalance()` and `reserveToken` diverge.

### Proof of Concept
1. Launch a token via `Zap.createToken`, no special privilege needed.
2. As an unprivileged trader, call `Bonding.buy`/`Zap.buy` for a large LT amount to acquire a large token balance close to the curve's remaining `tokenBalance()` (mirrors `_stageDonationAttack`'s sizing: `ltIn = virtual/3` yields `tokensOut ≈ 500M`, per the existing test's comment).
3. `Token(tokenAddr).transfer(pairAddr, donatedTokens)` — directly donate the purchased tokens to the pair, inflating `pair.tokenBalance()` above `reserveToken` (as proven by `test_donation_realBalanceExceedsReserveToken`).
4. Any subsequent trader calls `Zap.buy`/`Bonding.buy` with an amount large enough that unclamped `tokensOut` (from `_computeBuy`'s constant-product calc) exceeds the now-inflated `realBalance` — entering the `tokensOut > realBalance` branch.
5. `cappedReserveToken = reserveToken - tokensOut` underflows (`tokensOut == realBalance > reserveToken`), the call panics/reverts.
6. All future buys on this token pair revert identically forever — the curve is permanently bricked for buyers.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function _stageDonationAttack(
        address tokenAddr
    ) internal returns (uint256 drainLtSpent, uint256 donatedTokens) {
        address pairAddr = bonding.getTokenInfo(tokenAddr).pair;
        address drainer = makeAddr("donationDrainer");
        // Size the drain so `tokensOut > 250M` (the LP-reserve floor) under
        // any `VIRTUAL_LIQUIDITY_USD`. Constant-product math gives
        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses
        // 250M (= ¼ of TOTAL_SUPPLY) when `ltIn = virtual / 3`. Spending the
        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.
        drainLtSpent = _initialVirtualLt();
        lt.mintDirect(drainer, drainLtSpent);
        if (!bonding.isRouter(drainer)) bonding.addRouter(drainer);
        vm.startPrank(drainer);
        lt.approve(address(curveRouter), drainLtSpent);
        bonding.buy(drainLtSpent, tokenAddr, 0, drainer);
        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
        Token(tokenAddr).transfer(pairAddr, donatedTokens);
    }

    function test_donation_realBalanceExceedsReserveToken() public {
