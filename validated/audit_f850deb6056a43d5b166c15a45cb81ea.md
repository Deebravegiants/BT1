### Title
`deposit` mints zero `zft` shares for a nonzero underlying transfer once `total-assets-preview` grows large relative to `total-supply-preview`, permanently donating the depositor's funds to existing shareholders - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`deposit` computes `inkind = convert-to-shares-preview(amount)` and mints `inkind` shares without ever asserting `inkind > 0`, unlike its symmetric counterpart `redeem`, which explicitly guards against a zero output with `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`. Once accrued interest (partially materialized as `treasury-lp` to `.dao-treasury`) makes `ta = total-assets-preview` large relative to `ts = total-supply-preview`, a small `amount` causes `mul-div-down(amount, ts, ta)` to truncate to `u0`, so the caller's underlying is pulled into the vault and added to `assets`, but zero shares are minted to `recipient`.

### Finding Description
Broken identity: for a successful `deposit`, value transferred in must be represented by shares minted out:
`amount > 0 ⇒ inkind > 0`, where `inkind = mul-div-down(amount, ts, ta)`.

Code path [1](#0-0) :
- `inkind` is computed via `convert-to-shares-preview` [2](#0-1) , which returns `mul-div-down(amount, ts, ta)` whenever `ts != 0` and `ta != 0`.
- `deposit` only asserts `amount > 0`, `inkind >= min-out`, and the supply cap; it never asserts `inkind > 0`.
- By contrast, `redeem` explicitly guards the symmetric case: `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` [3](#0-2) .
- If the caller passes `min-out = u0` (default, unprivileged, fully attacker-controlled), the slippage check `(>= inkind min-out)` passes trivially even when `inkind = u0`.
- `receive-underlying` unconditionally pulls `amount` of `ststx` from the caller into the contract, and `assets` is incremented by `amount`, but `ft-mint? zft u0 recipient` mints nothing (Clarity's `ft-mint?` performs a no-op mint of 0 rather than reverting).

Root cause: asymmetric input validation between `deposit` and `redeem` — the zero-share-output guard present in `redeem` is missing in `deposit`. The precondition (`ta` large relative to `ts`) is a natural, permissionless consequence of interest accrual: `accrue` [4](#0-3)  continuously grows `total-assets-preview` from non-materialized interest while only the reserve-fee slice is minted as `treasury-lp` shares to `.dao-treasury`, so `ta` naturally outpaces `ts` over time until share price is high enough that `mul-div-down(amount, ts, ta)` truncates to zero for realistic deposit sizes.

Existing guards fail to stop this: `min-out=0` bypasses slippage protection, `cap-supply` only bounds total size not zero-share edge cases, and there is no `ERR-OUTPUT-ZERO`-style check on the deposit side.

### Impact Explanation
Each triggering deposit call causes the caller's full `amount` of `ststx` to be irrevocably absorbed into `assets` with zero shares issued to `recipient` — a 100% loss of the deposited principal for that call, which increases the per-share value captured by all existing `zft` holders (including `.dao-treasury`'s `treasury-lp`). This is repeatable indefinitely as long as the share-price/precision condition holds (any wallet can keep calling `deposit` with small amounts and keep losing funds, or the bug can silently strike any real user who happens to deposit a small amount once share price has grown large enough). It matches "permanent freezing of funds" — funds enter the vault with no corresponding claim ever created, and are unrecoverable by the depositor. It does not steal from other users' principal directly, but it is a real fund-loss bug reachable by any unprivileged caller with no protections in place.

### Likelihood Explanation
Preconditions require the vault to have accrued enough interest, over enough time, without proportional supply growth, that `ta/ts` exceeds `1/amount` for some plausible deposit size. This state arises naturally from normal `accrue` operation (no DAO or privileged action required) given enough elapsed time and utilization; the question's stated preconditions (net-zero real deposits/redeems, treasury-lp minted) are consistent with ordinary vault lifecycle, not an artificial setup. Any unprivileged principal can trigger the exact code path by calling `deposit` with `min-out = u0` — trivial capital cost equal to the (lost) `amount`, fully repeatable.

### Recommendation
Add the same zero-output guard used in `redeem` to `deposit`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the other `deposit` assertions in `mainnet/contracts/vault/v0-vault-ststx.clar` (and the mirrored `v0-vault-ststxbtc.clar`, and the `local-testing` counterparts), before `receive-underlying`/`ft-mint?` are executed, so that a would-be zero-share deposit reverts instead of silently consuming the caller's underlying asset.

### Proof of Concept
Clarinet simnet test plan:
1. Deploy/initialize `v0-vault-ststx` (calls `initialize` which mints `MINIMUM-LIQUIDITY` shares to `NULL-ADDRESS`).
2. Simulate/borrow and repeatedly advance `stacks-block-time` and call `accrue` (or trigger it implicitly via `deposit`/`redeem`) with a configured interest rate high enough that `total-assets-preview` grows much larger than `total-supply-preview` (e.g., set `points-ir` to a high rate and `system-borrow` most of the liquidity so utilization/interest compounds over simulated years).
3. Record `ta = (get-total-assets)` and `ts = (+ (get-total-supply) (calc-treasury-lp-preview))` (or read via `convert-to-shares`).
4. Choose `small_amount` such that `(mul-div-down small_amount ts ta)` is asserted to equal `u0` via `(convert-to-shares small_amount)`.
5. Call `(deposit small_amount u0 attacker)` from an attacker principal that holds `small_amount` of `ststx-token`.
6. Assert:
   - `(> small_amount u0)` — value was sent.
   - Attacker's `zft` balance is unchanged (`(is-eq (get-balance attacker) u0)`).
   - `assets` increased by `small_amount` (`(is-eq (get-assets) (+ old-assets small_amount))`).
   - Attacker's `ststx-token` balance decreased by `small_amount` with no compensating `zft` minted — demonstrating `amount > 0` and `inkind = u0` simultaneously, i.e., the FLOW_CLOSURE identity `amount * ts // ta = 0` while `amount` was actually transferred.

  (let ((ta (total-assets-preview))

                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))

                false)
