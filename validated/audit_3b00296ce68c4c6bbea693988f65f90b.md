## Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted for tenant identity but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating `Request#hmac` against `Request#to_signable_string`, but `to_signable_string` only covers the raw HTTP body. The `shop` (tenant identity), `topic`, and `webhook_id` fields — read straight from unauthenticated HTTP headers — are handed to the app's handler as if they were verified. This breaks the intended binding `hmac(secret, body) == received_hmac ⇒ (shop, topic, body) are all authentic`, since only `body` is actually bound.

## Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body` (line 37), while `shop` (line 21-23), `topic` (line 16-18), and `webhook_id` (line 30-33) are pulled directly from the `x-shopify-shop-domain` / `shopify-shop-domain` headers with no cryptographic binding to the HMAC.

`Registry.process` then does: [2](#0-1) 

It calls `Utils::HmacValidator.validate(request)` — which internally computes `HMAC(secret, request.to_signable_string)` and compares it against `request.hmac`: [3](#0-2) 

Since `to_signable_string` == `@raw_body` only, this check proves nothing about the `shop` header. Yet immediately after the check passes, `request.shop` is forwarded, unverified, as the tenant identifier into `WebhookMetadata`, which the host application uses to attribute the payload to a specific merchant/shop.

This is exactly the class of "field acted on but not covered by the HMAC" bug: contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, which explicitly includes `shop` inside `to_signable_string` so the shop is cryptographically bound to the signature: [4](#0-3) 

The webhook path has no equivalent binding for `shop`.

## Impact Explanation
Because the gem itself defines the shop-identity boundary for webhook processing (`WebhookMetadata#shop` is what host apps use to route/attribute per-tenant data such as `orders/create`, `customers/data_request`, etc.), an unprivileged internet user who can obtain any one genuine `(raw_body, hmac)` pair signed with the target app's `api_secret_key` (e.g., by installing the app on their own store and capturing a webhook delivery, which any developer/merchant can do) can replay that exact body+hmac to the victim app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary target shop. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will hand the attacker-chosen `shop` straight to the handler as though it were authenticated. This is a cross-tenant identity-binding break: the equality the code should enforce — `authenticated_bytes(shop) == asserted_shop` — never holds, because `shop` is never part of `authenticated_bytes` at all.

## Likelihood Explanation
Any actor capable of triggering a legitimate webhook once (e.g., a developer with a free/dev store using the same app) can capture a valid `(body, hmac)` pair and freely relay it with a forged shop header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the target merchant's credentials is required — only the ability to send an HTTP POST to the app's public webhook URL, which is by design internet-reachable.

## Recommendation
Bind the tenant/shop identity (and ideally topic and webhook id) into the signed material, mirroring how `AuthQuery#to_signable_string` includes `shop`. Concretely, change `Webhooks::Request#to_signable_string` (or `HmacValidator`) so the comparison is computed over `shop + topic + raw_body` (or otherwise incorporate the shop header into the HMAC-covered string), or require the host application to independently verify that the `shop` in the webhook belongs to a session already provisioned for that shop before trusting it. At minimum, document clearly that `WebhookMetadata#shop` is not authenticated by `HmacValidator.validate` and must be cross-checked by the caller against known installed shops.

## Proof of Concept
1. Attacker installs the target Shopify app on their own store (a legitimate, unprivileged action) and triggers a webhook, e.g., `customers/data_request`, capturing the raw POST body and the `x-shopify-hmac-sha256` header sent to their callback URL. This `(body, hmac)` pair is validly signed with the app's real `api_secret_key`.
2. Attacker replays the exact same `body` and `hmac` header to the victim app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own shop domain.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body without issue (`lib/shopify_api/webhooks/request.rb:45-63`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — identical to the original since `raw_body` is unchanged — and returns `true` (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` using the attacker-forged `victim-shop.myshopify.com` as `shop` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process/store attacker-controlled webhook data under the victim shop's tenant context.
