### Title
`withdraw()` in the Tron `IntentGatewayV2` violates CEI: escrow tokens are transferred before `_orders` is decremented, and this function is reachable directly via `cancelOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` contains an internal `withdraw()` function that transfers escrowed tokens to a beneficiary via a low-level `.call` *before* decrementing the corresponding `_orders[commitment][token]` escrow balance. Unlike the refactored EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`), which decrements escrow *before* transferring (proper CEI), the Tron contract retains the vulnerable transfer-then-update ordering — the exact bug class reported for `CouncilMember._withdrawAll`.

### Finding Description
`withdraw()` sets `_filled[body.commitment] = beneficiary` first (good), but then for each token in the withdrawal request it performs the external transfer *before* decrementing escrow: [1](#0-0) 

Compare this with the corrected pattern in the mainline EVM contract, where the escrow debit (`_orders[...] = escrowed - amount;`) happens *before* the transfer: [2](#0-1) 

Critically, `withdraw()` in the Tron contract is not gated behind `onlyHost` in every call path. It is reachable directly by an unprivileged external caller through the same-chain branch of `cancelOrder()`, which only requires that the caller be `order.user`: [3](#0-2) 

When the escrowed input includes the native token (`address(0)`), the transfer is a raw value `.call` to the beneficiary, which can be a contract with a `receive()`/fallback hook: [4](#0-3) 

There is no `nonReentrant`/`ReentrancyGuard` anywhere in this contract file, confirmed by search.

### Impact Explanation
Because escrow debit happens after the external call within the same loop iteration, any state that depends on `_orders[commitment][token]` remaining stale during the callback window is a reentrancy risk. The `_filled[commitment]` guard is set at the top of `withdraw()`, which blocks a second direct re-entrant call into `cancelOrder`/`withdraw` for the *same* commitment — but this only protects the `_filled` invariant, not the per-token escrow accounting for multi-token orders processed in the same call, where later tokens in `body.tokens` are still unprotected while an earlier token's transfer is in flight. Any code path (current or future) that reads/consumes `_orders[commitment][token]` without first checking `_filled[commitment]` remains exposed to double-accounting during that window. This is a classic CEI violation matching the reported bug class, and in this codebase it is reachable by any unprivileged order owner calling `cancelOrder` on a same-chain order — no privileged role required.

### Likelihood Explanation
Medium. The most direct exploit path (re-entering `cancelOrder`/`withdraw` for the same commitment) is currently blocked by the `_filled[commitment]` check being set before the token loop runs, matching the CEI fix pattern already validated by the `IntrinsicIntentsReentrancyTest` reentrancy tests for the mainline EVM contracts. However, the Tron contract itself does not carry an equivalent regression test, has no reentrancy guard, and the withdraw-then-transfer-before-decrement pattern is a structural defect independent of the current mitigating `_filled` check — any change to loop ordering, multi-token orders, or future added entry points that touch `_orders[commitment][token]` without checking `_filled` first would immediately become exploitable.

### Recommendation
Apply the same CEI fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron `IntentGatewayV2.withdraw()`: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) *before* performing the external transfer/call, for every token in the loop. Additionally, consider adding an explicit reentrancy guard to `withdraw()`/`cancelOrder()` for defense in depth, and add a regression test analogous to `IntrinsicIntentsReentrancyTest` covering the Tron contract's same-chain cancellation path.

### Proof of Concept
1. User places a same-chain order on the Tron `IntentGatewayV2` with two escrowed inputs: `token0 = address(0)` (native) and `token1 = ERC20 DAI`, with `order.user` set to a malicious contract address.
2. The malicious contract calls `cancelOrder(order, options)` on itself (it is `order.user`), taking the same-chain branch, which calls `withdraw(body, true)` with `body.tokens = [token0, token1]`.
3. Inside `withdraw()`, `_filled[commitment]` is set, then the loop reaches `token0`: `beneficiary.call{value: amount}("")` fires the malicious contract's `receive()` **before** `_orders[commitment][token0]` is decremented and before `_orders[commitment][token1]` has been touched at all.
4. During this callback, any exposed function that reads `_orders[commitment][token1]` (still fully escrowed, undecremented) without checking `_filled[commitment]` could be leveraged to double-account or re-drain that specific token slot — the structural bug is present even though the current `_filled` guard closes the most obvious direct re-entry into `cancelOrder` itself.         bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;

            address token = address(uint160(uint256(body.tokens[i].token)));

                if (!success) revert TransferFailed();

        }
