## Title
Precision loss (integer-division truncation) in `hyper-fungible-token`'s ERC20→local balance conversion causes under-crediting on incoming cross-chain transfers — ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

## Summary
The `SdtStakingPositionService._claimCvgSdtRewards` bug class — integer-division truncation on a value crediting operation causing silent, permanent token loss — has a structural analog in `pallet-hyper-fungible-token`'s `convert_to_balance` helper, which truncates the local balance credited to a recipient on every incoming cross-chain token transfer whose ERC20 amount is not an exact multiple of the local/EVM decimal scale factor.

## Finding Description
`convert_to_balance` converts an inbound ERC20 `U256` amount to the pallet's local balance type by dividing by `10^(erc_decimals - local_decimals)`: [1](#0-0) [2](#0-1) 

Solidity/EVM integer division (and the equivalent Rust `U256` division used here) truncates toward zero, exactly the arithmetic pattern flagged in the original report (`(157*100)/1000` truncating `15.7` to `15`). The README documents that this conversion happens on `on_accept`, when an inbound `Send` message from the counterpart EVM contract is processed: the pallet maps the source contract back to a local asset, "scales the amount using `Precisions`, then mints (non-native) or releases from escrow (native) to the beneficiary": [3](#0-2) 

The counterpart direction (`send`, local → ERC20) uses `convert_to_erc20`, a pure multiplication with no truncation: [4](#0-3) 

This means the pallet's own outbound path always dispatches an ERC20 amount that is an exact multiple of the local-decimal unit (since it's derived by multiplying the local amount up), but the pallet cannot control what amount an EVM-side sender's contract dispatches inbound — any ERC20 amount not cleanly divisible by `10^(erc_decimals - local_decimals)` (e.g. a user paying with decimal precision the EVM contract supports but the local chain does not) has its remainder silently dropped by `convert_to_balance`'s integer division, and that dropped remainder is neither minted, refunded, nor tracked anywhere in the visible code.

## Impact Explanation
Any unprivileged token bridger who dispatches (or whose relayer delivers) an inbound `Send` message with an ERC20 amount not aligned to the local decimal granularity causes a portion of the transferred value to be permanently lost — never credited to the beneficiary and never recoverable, matching the "small accumulated losses become huge over time" impact reasoning in the original report. Because this fires on every asset pair where `erc_decimals > local_decimals` (a decimals mismatch the docs explicitly anticipate via the `Precisions` map), this is a systemic, per-transfer fund-loss bug rather than an edge case.

## Likelihood Explanation
High. This code path executes on every single inbound cross-chain token transfer for any asset registered with a decimals mismatch between the EVM and local chain (the pallet's `Precisions` storage exists specifically to record such mismatches, e.g. `BridgeToken` mints with 18 EVM decimals against BRIDGE's 12 native decimals — a 10^6 scale factor per `evm/src/apps/BridgeToken.sol` comments). No admin or governance action is required to trigger it; it fires on the ordinary token-bridging flow.

## Recommendation
Track the truncated remainder (dust) per beneficiary/asset and either (a) accumulate it until it forms a full local unit and credit it then, or (b) refuse/refund transfers whose amount isn't an exact multiple of the decimal scale factor, or (c) use a higher-precision internal accounting unit so no remainder is ever dropped. At minimum, emit an event recording the truncated dust so it isn't silently and permanently lost.

## Proof of Concept
Given `erc_decimals = 18`, `local_decimals = 12` (the exact BRIDGE token scale documented in `evm/src/apps/BridgeToken.sol`), the scale factor is `10^6`. An inbound message carrying `value = 1_000_000_999999` (i.e., 1 local unit plus 999,999 wei of ERC20-side sub-unit precision) computes:

```
convert_to_balance(1_000_000_999_999, 18, 12)
  = 1_000_000_999_999 / 10^6
  = 1_000_000            // truncated; 999_999 units of value vanish
``` [2](#0-1) 

The beneficiary is minted/released `1_000_000` local units instead of the full value backed by the corresponding EVM-side lock/escrow, and the `999_999`-unit remainder is dropped with no accounting trail — the same class of loss described in the original `SdtStakingPositionService` report, applied to a token-bridge mint/release path.
