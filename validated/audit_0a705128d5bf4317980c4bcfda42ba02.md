Based on my research, I found a legitimate analog in `pallet-consensus-incentives`. The bug class is the same shape as the Ramses report: a reward is computed as `(elapsed_span) × (a rate/state value read at settlement time)`, and the elapsed span can grow arbitrarily large across a gap during which the rate parameter changed, because there is no accumulator that locks in the rate that applied to each sub-interval of that span.

### Title
Consensus relayer rewards computed with current `block_cost` applied retroactively over the entire unclaimed height span, inflating/deflating rewards across a cost change - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`pallet-consensus-incentives::calculate_reward` pays a relayer `(latest_height - baseline) * block_cost`, where `baseline` is the previously-rewarded watermark and `block_cost` is whatever `StateMachinesCostPerBlock` holds *at the moment the message is processed*. Nothing in the protocol bounds how large `latest_height - baseline` can grow, or ties historical block spans to the cost that was configured for them. Any single unprivileged relayer, by simply delaying submission of a `ConsensusMessage` (a permissionless, unsigned-fee extrinsic path) until after a cost update, converts a large backlog of blocks into a payout at the new rate instead of the rate(s) that actually applied while those blocks accrued.

### Finding Description
`process_message` looks up the current `block_cost` for the state machine and calls `calculate_reward`: [1](#0-0) 

`calculate_reward` computes the reward purely from the delta between `latest_commitment_height` and a `baseline` (the max of `LastRewardedHeight` or `previous_commitment_height`), multiplied by whatever `block_cost` was passed in: [2](#0-1) 

`block_cost` itself is a single mutable value per state machine, updatable at any time via the privileged `update_cost_per_block` call: [3](#0-2) [4](#0-3) 

There is no per-height/per-period accumulator (analogous to `endSecondsPerLiquidityPeriodX128` in the Ramses report) that records what cost applied to each historical block. Instead, the *entire* unrewarded span `latest_height - baseline` — which can be arbitrarily large if a relayer (or all relayers) simply doesn't submit a `ConsensusMessage` for a while — is billed at whatever cost happens to be configured when the message finally lands. This is the same root defect pattern as the Ramses bug: a rate/accumulator meant to represent "value that applied over a bounded prior interval" is instead evaluated at settlement time and silently stretched over a much larger, unbounded interval when submissions are delayed ("period skipped").

`process_message`/`calculate_reward` is invoked from the `FeeHandler::on_executed` hook, which fires whenever a `ConsensusMessage` is executed by `pallet-ismp` — this is triggered by any unprivileged relayer submitting a signed consensus proof: [5](#0-4) 

### Impact
An unprivileged relayer can withhold consensus updates for a state machine (there is no liveness requirement forcing timely submission) and wait for `update_cost_per_block` to be raised (a routine governance action, not an attack in itself). When the relayer finally submits, the reward formula bills the *entire* backlog of blocks since the last-rewarded watermark at the new, higher rate, paying out treasury funds far in excess of what was earned under the rate schedule that actually applied during most of that span. This is a direct drain on the `TreasuryAccount` (unbacked/over-minted reward, since `ReputationAsset::mint_into` also mints proportional reputation tokens): concrete theft/over-distribution of funds is possible with a single permissionless extrinsic, with no attacker-side cost beyond normal relaying gas.

### Likelihood Explanation
This requires: (1) a lull in consensus updates for a given state machine (easy — a relayer, possibly the attacker itself, simply doesn't submit for a period, and there is no other relayer racing to submit first since doing so would only shrink the attacker's own backlog), and (2) a cost-per-block increase occurring during that lull (a normal, expected governance action to keep incentives calibrated, not an exploit of the protocol). Unlike the original Ramses finding — which needed an unlikely "dead pool" precondition — here the attacker fully controls the timing of their own submission, so they can simply wait until after any announced/observed cost increase before submitting their backlog. This makes the precondition much easier to satisfy, and is analogous in severity to the Medium rating ultimately assigned to the original report.

### Recommendation
Do not apply a single point-in-time `block_cost` over an unbounded historical span. Either (a) cap the maximum span a single reward calculation may cover (e.g., require watermark to be updated at least every N blocks, rejecting/truncating larger gaps), or (b) record `block_cost` changes with their effective height and integrate the correct historical rate(s) over each sub-interval of `[baseline, latest_height]`, similar to how the Ramses fix recommends tracking distinct start/end accumulator values per period rather than reusing a single evaluated-at-settlement value.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[X] = C_low` via `update_cost_per_block`.
2. No relayer submits a `ConsensusMessage` for state machine `X` for a long span of blocks (`latest_commitment_height` advances far beyond `LastRewardedHeight`/`previous_commitment_height`) — the attacker, as an unprivileged actor, can simply choose not to submit, and need not collude with anyone else since no other relayer is incentivized to submit first.
3. Governance later raises `StateMachinesCostPerBlock[X] = C_high` (a routine parameter update, unrelated to this attack).
4. The attacker (or any relayer) now submits a single `ConsensusMessage` proof for `X`. `on_executed` → `process_message` → `calculate_reward` computes `reward = (latest_height - baseline) * C_high`, paying out the entire backlog at the new, higher rate rather than at `C_low`, which is what applied for most of the span. 	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

impl<T: Config> FeeHandler for Pallet<T>
where
	<T as frame_system::Config>::AccountId: From<[u8; 32]>,
{
	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
