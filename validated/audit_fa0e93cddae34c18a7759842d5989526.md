### Title
`findMatchingWithdrawal` in `PoaBridge.describeWithdrawal()` matches by `assetId` only, ignoring `index`, causing a status/hash misreport across distinct withdrawals of the same token in one transaction - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
When a NEAR transaction contains multiple `ft_withdraw` intents for the *same* token to different destinations/amounts (a batch of withdrawals), `PoaBridge.describeWithdrawal()` resolves the status of each `WithdrawalIdentifier` (distinguished by `index`) using `findMatchingWithdrawal`, which selects the first API record whose `near_token_id` matches the requested `assetId` - it never uses `index` to disambiguate. This breaks the equality "status/txHash reported for withdrawal N" == "on-chain outcome of withdrawal N", allowing the wrong `txHash`/completion status to be reported for a distinct withdrawal with a different destination address or amount.

### Finding Description
`createWithdrawalIdentifier` for POA produces a `WithdrawalIdentifier` carrying `index`, `withdrawalParams` (including `destinationAddress`/`amount`), and the shared `tx` hash: [1](#0-0) 

`describeWithdrawal` then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, explicitly documented as matching "by assetId instead of index": [2](#0-1) 

The matcher implementation confirms it only compares `nep141:{near_token_id}` to `assetId`, with no use of `destinationAddress`, `amount`, or `index`: [3](#0-2) 

The same limitation exists in the `internal-utils` counterpart used for direct polling: [4](#0-3) 

Both implementations' own comments acknowledge: "multiple withdrawals of the same token in a single transaction are not supported" - i.e., the code authors are aware this equality (`identifier index` ↔ `matched on-chain withdrawal record`) does not hold in that case, yet `describeWithdrawal` still returns a definitive `"completed"` status with a `txHash` rather than failing safe or surfacing an error.

If a user/integrator batches two POA withdrawals of the same asset (e.g., withdrawing to two different exchange deposit addresses in one NEAR transaction), `SDK.withdraw()`/`watchWithdrawal()` will call `describeWithdrawal` once per `index`. Both calls hit the same `response.withdrawals` array and `find()` on the same predicate, so **both indices resolve to the same withdrawal record** - typically the first one returned by the API (order is explicitly "unsorted"). Consequently:
- Withdrawal #2 (different destination/amount) is reported `completed` with the `txHash` that actually belongs to withdrawal #1's on-chain settlement.
- If an integrator uses this reported status/hash to mark the withdrawal as settled or to release a corresponding credit/refund, it does so based on a hash/status that does not correspond to withdrawal #2's actual on-chain destination.

### Impact Explanation
This falls under "a status or hash misreport making an integrator credit or refund twice" (High). An integrator that tracks multiple concurrent withdrawals of the same token from the same NEAR tx (a legitimate, unprivileged batching flow) can be told that withdrawal B settled with the txHash of withdrawal A. This can lead to premature/incorrect crediting of withdrawal B (or a mismatch between the recorded destination and the reported hash), and in the case where withdrawal A fails/is refunded while B is reported completed via A's hash, double bookkeeping errors for the integrator become possible.

### Likelihood Explanation
Batching multiple `ft_withdraw` intents for the same POA-bridged asset in a single signed intent/transaction is a normal, unprivileged usage pattern supported by the SDK's array-based `withdrawalParams`/`index` design (`createWithdrawalIdentifier` explicitly takes an `index` for this purpose). No malicious actor is required - any legitimate multi-destination withdrawal of the same token triggers this bug. However, exploitation for material gain still depends on how a downstream integrator uses the misreported hash, which is unverified from this codebase alone.

### Recommendation
Disambiguate `findMatchingWithdrawal` using more than `assetId`: match against `destinationAddress` (and `amount`, since the note itself suggests amount-based tie-breaking is possible) or, failing a unique match, return a distinguishable error/`"pending"` state instead of a possibly-wrong `"completed"` result. At minimum, when multiple candidates match the same `assetId`, `describeWithdrawal` should not silently return a match for the wrong `index`; it should throw/flag ambiguity so integrators are not given an incorrect settlement hash.

### Proof of Concept
1. User signs one NEAR intents transaction containing two `ft_withdraw` intents for `nep141:usdc.omft.near`: one to `destinationAddress=A` (amount=100), one to `destinationAddress=B` (amount=200).
2. SDK creates two `WithdrawalIdentifier`s via `createWithdrawalIdentifier` with `index=0` and `index=1`, both sharing `tx.hash`.
3. POA bridge indexer settles both, returning an unsorted `withdrawals` array e.g. `[{near_token_id:"usdc.omft.near", transfer_tx_hash:"hashA", ...}, {near_token_id:"usdc.omft.near", transfer_tx_hash:"hashB", ...}]`.
4. `describeWithdrawal({index:0, withdrawalParams:{assetId:"nep141:usdc.omft.near", destinationAddress:A,...}})` and `describeWithdrawal({index:1, withdrawalParams:{assetId:"nep141:usdc.omft.near", destinationAddress:B,...}})` both call `findMatchingWithdrawal` with the same `assetId`, both returning the **first** entry (`hashA`) regardless of `index`, as shown by `find()` in [5](#0-4) .
5. `watchWithdrawal` for index=1 (destination B) resolves with `{status:"completed", txHash:"hashA"}` - the transaction hash that actually corresponds to the transfer sent to destination A, not B.

Note: I could not fully verify how downstream consumers (e.g., `sdk.ts`'s multi-withdrawal orchestration) use the per-index `describeWithdrawal` results in the presence of same-asset batches, since that wiring wasn't in the retrieved context; the core defect (index-blind matching contradicting the code's own index-based identifier design) is confirmed directly in the cited files.

```typescript
	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
```

```typescript
/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

```typescript
/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
```
