### Title
Excess native token sent to `IntentGatewayV2.placeOrder()` is never refunded and becomes permanently frozen (Tron `IntentGatewayV2`) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` tracks `msg.value` in a local `msgValue` counter, decrements it as native-token order inputs and native-swap solver fees are consumed, but — unlike the EVM (`evm/src`) sibling contract — never refunds the leftover `msgValue` to the caller at the end of the function. Any native token sent in excess of what the order actually requires is permanently stuck in the contract.

### Finding Description
`placeOrder()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` computes `uint256 msgValue = msg.value;` [1](#0-0)  and then subtracts native input amounts from it as it processes `order.predispatch.assets` and `order.inputs` [2](#0-1) [3](#0-2) . It also spends `msgValue` on a Uniswap swap when `order.fees > 0` [4](#0-3) . The function then emits `OrderPlaced` and returns [5](#0-4)  without ever checking whether `msgValue` is still non-zero and, if so, returning it to `msg.sender`.

Compare this to the canonical EVM implementation of the same function, `evm/src/apps/IntentGatewayV2.sol`, which explicitly refunds unspent native token at the end of `placeOrder`:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
``` [6](#0-5) 

This refund logic is entirely absent from the Tron port. Because `placeOrder` is `payable` and a caller may legitimately send `msg.value` greater than the sum of native `order.inputs[].amount` and any native-fee-swap amount (e.g., due to slippage buffers, wallet/dApp rounding, or a caller intentionally over-provisioning gas-fee headroom as documented for the SDK's placement flow, where the transaction's `value` is described as "the order's native-token input amounts — plus the quoted nativeValue when paying the solver fee in native token" [7](#0-6) ), any surplus native token silently accumulates in the contract with no code path to reclaim it. There is no `sweep`/refund/withdraw function visible in this contract that returns arbitrary excess native balance to the original depositor — `cancelOrder`/escrow release logic in this contract only tracks amounts recorded in `_orders[commitment][token]`, which is set to the fee-adjusted `reducedInputs[i].amount`, not to whatever raw `msg.value` was sent.

This is the same root-cause bug class as the reported `LMPVaultRouterBase::deposit()` issue: a function accepts `payable` native value alongside token-amount parameters, but the accounting of "how much native token was actually needed vs. supplied" is not reconciled/refunded, so unspent native value is orphaned inside the contract and effectively removed from the depositor's control.

### Impact Explanation
Any user who over-sends native token when calling `placeOrder()` on the Tron `IntentGatewayV2` permanently loses the excess — the funds remain locked in the contract with no code path identified in this contract to recover them for the specific depositor. This is a direct loss/freezing of user funds reachable by any unprivileged order-placer via a single transaction, matching the "permanent freezing of funds" acceptance criterion. Because Tron's fee/gas model and typical wallet UX commonly result in `value` being computed with margin/rounding (mirrored by the SDK guidance to send input amount plus quoted native fee, never zeroing out `value`), overpayment is a realistic, not merely theoretical, scenario.

### Likelihood Explanation
Likelihood is high: no attacker action or malicious input is even required — the bug triggers whenever a normal user (or SDK-generated transaction) sends `msg.value` strictly greater than the amount actually consumed by native inputs and the fee-token swap, which is a routine occurrence when native tokens are used to pay solver fees (swap `amountIn` from Uniswap can leave dust) or when clients pad `value` for safety margins.

### Recommendation
Add the same trailing refund check present in the EVM version to the Tron `placeOrder()`:
```solidity
// Refund any unspent native tokens to the user.
if (msgValue > 0) {
    (bool sent, ) = msg.sender.call{value: msgValue}("");
    if (!sent) revert InsufficientNativeToken();
}
```
placed immediately before (or after) the `OrderPlaced` emission, mirroring `evm/src/apps/IntentGatewayV2.sol` lines 394-397, and audit any other Tron-specific contracts derived from the same EVM source for the same missing-refund pattern.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder{value: 2 ether}(order, graffiti)` where `order.inputs` contains a single native-token leg of `1 ether` and `order.fees == 0`.
2. Inside `placeOrder`, `msgValue` starts at `2 ether`, is decremented by `1 ether` for the native input leg (`msgValue -= order.inputs[i].amount;`) [8](#0-7) , leaving `msgValue == 1 ether`.
3. Because `order.fees == 0`, the fee-escrow branch is skipped, so the remaining `1 ether` in `msgValue` is never spent.
4. Execution reaches the end of the function and returns without any refund logic, so the extra `1 ether` remains in the contract's balance [5](#0-4) , permanently inaccessible to the user through any code path in this contract.
