## Analysis

The strongest analog to the LooksRare "fix the wrong price for future rounds via deposit" bug class in this codebase is the phantom-order price aggregation mechanism that feeds `LiquidityPool.buyRate`/`sellRate`, which `IntentGateway.quoteIntent` then uses to size **real, escrowed IntentGatewayV2 orders**. Just as the LooksRare bug let an attacker unilaterally "fix" a price via a low-cost deposit that a later, real financial event trusted unconditionally, a solver here can unilaterally fix a leg's published price via a bid that costs it nothing to place, and that fixed price is later trusted verbatim by real user orders.

### Title
Solver-dominated weighted-median lets a single bidder fix a wrong `LiquidityPool` price consumed by real IntentGateway orders - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` prices each phantom-order leg with a liquidity-weighted **median** (a selection, not a blend) of solver quotes, weighted only by each bidder's own token balance on the destination chain. Any solver whose balance exceeds half of a leg's total quoted weight has its exact quoted price selected as the leg's `medianPrice` verbatim, with no bound relative to other quotes. This price flows unmodified into `PhantomOrderPriceSnapshotV2`, then into `LiquidityPool.sellRate`/`buyRate` via `updateLiquidityPools`/`mergeChainRowsIntoPool`, and `IntentGateway.quoteIntent`'s default `indexed_rates` strategy uses that pool rate to size real, capital-escrowing orders for any caller of the SDK.

### Finding Description
`weightedMedian` in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts` returns one bidder's price exactly once its weight passes the 50% cumulative-weight threshold: [1](#0-0) 

The weight backing a bid is simply the bidder's own on-chain balance of the leg's output token, read at the snapshot block, with no requirement that the balance be traded away or otherwise put at risk: [2](#0-1) 

The indexer's own documentation acknowledges the design property directly — "a solver holding over half the leg's weight sets the published price verbatim" — and only guards the opposite extreme (a zero-inventory solver quoting an outlier), not a well-funded one: [3](#0-2) 

That per-chain median is merged into the pool's single `sellRate`/`buyRate` by a depth-weighted mean: [4](#0-3) 

Real orders are then priced directly off this figure. `IntentGateway.quoteIntent` defaults to the `indexed_rates` strategy, which reads `LiquidityPool.buyRate`/`sellRate` and uses it to compute the exact `amountIn`/`amountOut` a caller places on-chain, with no sanity check against any independent price source: [5](#0-4) [6](#0-5) 

This is structurally identical to the LooksRare bug class: a party who controls the "first submission" (here, the dominant-weight bid, rather than the first ERC20/ERC721 deposit) can unilaterally fix a price consumed later by unrelated, real financial actions (real escrowed IntentGatewayV2 orders instead of round entries), and the fixed price has no bound tying it to any real market rate.

### Impact Explanation
A solver that funds itself (or several EIP-7702-delegated fillers) with enough of a leg's output token to exceed 50% of that leg's total bidder weight on one chain can submit an arbitrarily favorable or unfavorable quote and have it selected verbatim as `medianPrice`. Because `weightedRate` is a depth-weighted mean across chains, a chain where the attacker dominates weight can materially skew the pool's published `buyRate`/`sellRate`, especially for pairs/chains with thin competing liquidity. Once skewed:
- Users calling `quoteIntent` construct real orders at the wrong rate and escrow real tokens on `IntentGatewayV2`.
- The manipulating solver (or any solver) can then fill those mispriced orders, extracting value from the escrowed input — the same "steal ETH depositors" outcome as the original report — or simply decline to fill orders priced against them, effectively freezing/DoSing that route the same way an inflated fixed price DoS'd LooksRare's future rounds.

This is a concrete-theft / unsound-price vector reachable by any unprivileged solver holding sufficient inventory and submitting a single phantom bid, so it qualifies as High per the report's own class and this task's validation bar.

### Likelihood Explanation
Placing a phantom bid requires no privileged role — any address that is EIP-7702-delegated to a `SolverAccount` and passes `isVerifiedSolverBid` can bid, and bidding costs nothing beyond already holding the output-token balance the weight is computed from (no forced trade, no slashing on an unfilled bid). Thin-liquidity chains/pairs, or moments right after `PhantomOrderConfig` adds a new pair, make it comparatively cheap to exceed 50% of the leg's total quoted weight, so the precondition is realistic rather than theoretical.

### Recommendation
Do not let a single bidder's balance-weighted quote become the leg price outright. Options: cap any single bidder's contribution to the total weight (e.g., a max share like 30–40%) before computing the weighted median; require the resulting price to fall within a bounded deviation of a secondary reference (e.g., prior snapshot, TWAP, or an external oracle) before it is allowed to update `LiquidityPool.sellRate`/`buyRate`; or require `quoteIntent`'s `indexed_rates` strategy to reject/flag rates that moved beyond a sane bound since the last snapshot instead of consuming them unconditionally.

4. On `PhantomBidWindowExhausted`, `aggregatePhantomBids`'s `weightedMedian` (lines 709-724) selects the attacker's price verbatim as `medianPrice` because cumulative weight crosses 50% at the attacker's entry.
5. `handlePhantomOrderPrices` writes this into `PhantomOrderPriceSnapshotV2`, and `updateLiquidityPools`/`mergeChainRowsIntoPool` (lines 470-496) folds it into `LiquidityPool.sellRate`/`buyRate`.

7. The attacker (or any solver) fills the mispriced order on favorable terms, extracting value from the user's escrowed input — or refuses to fill any order priced against it, freezing that route until the rate ages out or is corrected.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

function mergeChainRowsIntoPool(pool: LiquidityPool, rows: PoolChainLiquidity[], referenceBlock: bigint): void {
	for (const direction of [SELL, BUY]) {
		const directionRows = rows.filter((row) => row.direction === direction)
		if (directionRows.length === 0) continue

		// Blocks are processed in order, so the difference is non-negative in practice; a row
		// from a "future" block would simply count as fresh, which is the right reading anyway.
		const fresh = directionRows.filter((row) => referenceBlock - row.lastUpdatedBlock <= MAX_SAMPLE_AGE_BLOCKS)
		const merged = fresh.length > 0 ? fresh : directionRows

		warnOnDivergentSample(pool.id, direction, merged)

		const depth = merged.reduce((acc, row) => acc + row.depth, 0n)
		const rate = weightedRate(merged)
		const bidCount = merged.reduce((acc, row) => acc + row.bidCount, 0)

		if (direction === SELL) {
			pool.sellRate = rate
			pool.sellDepth = depth
			pool.sellBidCount = bidCount
		} else {
			pool.buyRate = rate
			pool.buyDepth = depth
			pool.buyBidCount = bidCount
		}
	}
}

# 2026-08-25 — Intent quotes default to directional indexed rates without fallback

Chosen: `quoteIntent` defaults to an `indexed_rates` strategy that selects the depth-weighted aggregate `LiquidityPool.buyRate` for base-to-quote orders and `sellRate` for quote-to-base orders. Source and destination chains resolve the configured token deployments; raw amounts are calculated from the indexer's 18-decimal whole-token pool rate and both tokens' configured decimals. A missing directional rate is an error.

Alternatives considered:

- **Keep defaulting to the legacy directional Phantom snapshot.** Rejected: those snapshots resolve through a canonical Base market and do not use the pair-centric pool rate, so quotes can disagree with the indexer's current market.
- **Quote directly from one source/destination pair of `PoolChainLiquidity` rows.** Rejected: those rows are inputs to the indexer's pool price. `LiquidityPool.buyRate` and `sellRate` are the maintained depth-weighted merge of fresh chain samples and are the intended market-level quote.
- **Silently fall back to Phantom or Uniswap when a rate is absent.** Rejected: an order would be priced from a different market than the caller requested, hiding stale or incomplete indexer coverage and producing another unfillable quote.
