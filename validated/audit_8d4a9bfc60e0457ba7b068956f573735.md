### Title
`PassphraseCache.changeTtl` retroactively extends the cached-passphrase validity window using a stale `inactiveAt` anchor - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
`PassphraseCache` caches the wallet passphrase in (session) storage to support auto-unlock, and gates its validity by comparing a stored inactivity/creation anchor timestamp plus a TTL against `Date.now()`. When the auto-lock TTL is changed via `changeTtl()`, the code updates the stored `TTL_KEY` but never re-anchors `ADDED_AT_KEY`/`INACTIVE_AT_KEY` to the current time, so the new (potentially larger) TTL is applied on top of an already-elapsed, stale anchor — the exact same class of bug as the `DyadXPv2.initialize` report, where a recalculated value is derived from a state snapshot without accounting for the time that has already elapsed since the anchor was recorded.

### Finding Description
`PassphraseCache.get()` validates a cached passphrase using either `inactiveAt` or `addedAt` as the time anchor: [1](#0-0) 

`changeTtl()` is the entry point exposed to the user/app via `Application.changeLockTimer` (`exodus.application.changeLockTimer`), and it only updates `TTL_KEY` in storage, leaving the existing `inactiveAt`/`addedAt` anchor untouched: [2](#0-1) [3](#0-2) 

This mirrors the reported root cause precisely: a state-recalculation function (`_computeXP` / here, the TTL-vs-anchor comparison in `get()`) is fed a *new* parameter (a larger TTL, analogous to a freshly computed accrual rate) but is combined with a *stale* anchor timestamp (`lastAction` / here `inactiveAt`) instead of re-anchoring to "now," so elapsed time that should invalidate/reduce the remaining window is silently ignored, and the new TTL is applied as if it had been in effect for the whole elapsed period.

Concretely: if a passphrase is cached with `inactiveAt = T0` and `ttl = 1 minute`, and at `T0 + 50s` the user (or anyone able to invoke `changeLockTimer`, e.g. through the exposed headless API) calls `changeLockTimer({ ttl: 60 * 60 * 1000 })` (max allowed by `maxTtl`), `get()` will now evaluate `inactiveAt(T0) + 3600000 > Date.now()`, granting a valid cached-secret window that effectively started counting from `T0`, not from the moment the TTL was changed. This is the same "recompute derived value from persisted state without accounting for already-elapsed time since the anchor" defect as the original report.

### Impact Explanation
The impacted value is not a reward accrual figure but the validity window of a **cached wallet passphrase used for auto-unlock**. A wrong/expanded window means the secret (raw passphrase) sourced from storage can be treated as valid for materially longer than the effective auto-lock policy intends, directly weakening the auto-lock security boundary that is meant to force re-authentication after inactivity. This falls squarely in the "auth" / "encrypted storage" trust-boundary category and has a direct wallet-security impact (extended exposure window for a stored secret that can unlock the wallet), matching the required "auth bypass"/"secret disclosure" bar.

### Likelihood Explanation
Likelihood is High for the code-level condition (it triggers on ordinary use: any call to `changeLockTimer` while a passphrase is already cached with an existing `inactiveAt`), and the API is part of the documented public headless surface (`changeLockTimer`) reachable from application/UI code without special privilege.

### Recommendation
In `changeTtl()`, re-anchor the relevant timestamp to the current time whenever the TTL is changed (i.e., set `INACTIVE_AT_KEY` to `Date.now()` alongside `TTL_KEY`, mirroring what `scheduleClear()` does), so the new TTL always applies prospectively from the moment of the change rather than being combined with a stale anchor:
```diff
 async changeTtl(ttl: number) {
   const newTtl = Math.min(this.#maxTtl, ttl)
   await this.#autoLockTimerAtom.set(newTtl)
   const passphrase = await this.#storage.get(PASSPHRASE_KEY)
   if (passphrase) {
     await this.#storage.set(TTL_KEY, newTtl)
+    await this.#storage.set(INACTIVE_AT_KEY, Date.now())
     void this.#scheduleClear()
   }
 }
```

### Proof of Concept
1. Unlock wallet with a passphrase; `passphraseCache.set(passphrase)` stores `addedAt = T0`. [4](#0-3) 
2. Trigger inactivity handling (e.g., app backgrounding calls `restartAutoLockTimer` → `passphraseCache.scheduleClear()`), which sets `inactiveAt = T0 + Δ`. [5](#0-4) [6](#0-5) 
3. Shortly before the original short TTL would expire, call `exodus.application.changeLockTimer({ ttl: maxTtl })` (`Application.changeLockTimer` → `PassphraseCache.changeTtl`). [7](#0-6) 
4. `get()` now computes `inactiveAt + maxTtl > Date.now()`, using the old `inactiveAt` anchor with the new, much larger TTL — granting a cached-passphrase validity window far beyond what the original inactivity timer intended, without ever having re-validated recent user activity. [8](#0-7)

      INACTIVE_AT_KEY,
      TTL_KEY,

    if (passphrase) {
      if (inactiveAt) {
        if (inactiveAt + ttl > Date.now()) {
          this.#logger.log('fetched cached passphrase, in activity period')
          return passphrase
        }
      } else if (addedAt + this.#maxTtl > Date.now()) {
        this.#logger.log('fetched cached passphrase')
        return passphrase
      }

    }

  }
