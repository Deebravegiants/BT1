### Title
Webhook tenant (`shop`) header is not covered by the HMAC digest, allowing shop-domain spoofing on a validly-signed webhook body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts an HTTP webhook as authentic solely because `Utils::HmacValidator.validate(request)` returns true. That validation only covers `@raw_body` (`Request#to_signable_string`), never the `shop-domain`, `topic`, or `webhook-id` headers. Yet `request.shop` — read verbatim from the attacker-controllable `shopify-shop-domain`/`x-shopify-shop-domain` header — is forwarded unchanged into `WebhookMetadata#shop` and handed to the app's webhook handler as the authoritative tenant identifier.

### Finding Description
The identity binding that should hold is: `shop header value == value verified by HMAC digest`. In reality:
- Before request: `hmac = HMAC(secret, raw_body)`; `shop` header is unsigned, freely settable by whoever sends the HTTP request to the app's public webhook endpoint.
- After request: `HmacValidator.validate` recomputes `HMAC(secret, raw_body)` and compares to the header's HMAC — this only proves the *body* bytes were produced (at some point) with the app's secret. It proves nothing about which shop the header claims.
- `Registry.process` ( [1](#0-0) ) then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches to the handler using this unauthenticated `shop`.

Because Shopify signs webhooks with a single app-level `client_secret` shared across every shop that installs the app (not a per-shop secret), any merchant who has installed the app can legitimately capture one of their own `(raw_body, hmac)` pairs from a real webhook delivery. That pair remains a valid HMAC for the *same* app on *any* shop. An attacker (a merchant with the app installed, i.e., an "unprivileged" caller relative to other tenants) can replay that exact `raw_body`/HMAC to the app's public webhook URL while substituting an arbitrary `shopify-shop-domain` header value naming a different, victim shop. `HmacValidator.validate` still passes because it never inspects the `shop` header, and `Registry.process` calls the handler with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant boundary: an app handler that trusts `WebhookMetadata#shop` (as the gem's own documentation instructs developers to do, e.g. `shop_domain: data.shop` in `docs/usage/webhooks.md`) to look up per-shop session/state can be made to process attacker-supplied webhook content under a victim shop's identity — effectively cross-tenant data injection/impersonation using a webhook payload the attacker fully controls (their own shop's order/product/customer data) but attributed to another store. This matches the Critical "cross-tenant access" impact category, analogous to the EIP712 finding where a field consumed by application logic (`data`) was not bound into the verified digest the way the recipient of the signature assumed.

### Likelihood Explanation
Likelihood is realistic for any real-world deployment because: (1) the app-level secret is the same for all shops per Shopify's own webhook design, so any app-installing merchant can obtain a valid `(body, hmac)` pair for free; (2) the webhook endpoint is a public, unauthenticated HTTP route by design; (3) no additional secret or credential is needed — only observation of one's own legitimately received webhook.

### Recommendation
Do not treat `request.shop` as authenticated tenant context on its own. At minimum, document this limitation prominently, and/or extend `HmacValidator`/`Request` so that the signable string, or a secondary check, incorporates a value that ties the payload to the specific shop it claims to originate from (e.g., cross-check `shop` against the body's own shop/domain fields where present, or require the consuming app to independently verify that `data.shop` corresponds to a shop with an active, verified installation/session before trusting webhook content for that tenant) — mirroring the EIP712 fix of ensuring every value the recipient will act on is actually included in what was cryptographically verified.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker receives a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` (valid for the app's shared `client_secret`).
2. Attacker crafts a new HTTP POST to the app's public webhook route with the same raw body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H})` is constructed by the app's controller (per the documented integration pattern in `docs/usage/webhooks.md`).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body` (`Request#to_signable_string`).
5. The handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` and processes attacker data as if it belonged to `victim-shop.myshopify.com`.
