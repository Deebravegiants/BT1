### Title
Webhook shop/topic identity is taken from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry uses to route and label a webhook are read from HTTP headers that are never included in the signed data. This breaks the equality that should hold: `bytes_covered_by_hmac == bytes_that_determine_tenant/topic_attribution`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then dispatches the handler using the header-derived, **unauthenticated** `topic` and constructs the metadata using the header-derived, **unauthenticated** `shop`: [3](#0-2) 

`HmacValidator.validate` confirms this: it only checks the `hmac` field against `to_signable_string`, i.e. the body — it never touches headers: [4](#0-3) 

Because the `shop-domain` and `topic` headers are outside the cryptographic envelope, any actor who legitimately receives one authentic (body, HMAC) pair from Shopify — for example, by installing the app on their own free/dev store, an action any unprivileged internet user can perform — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (and/or `x-shopify-topic` header). `HmacValidator.validate` will still pass, because the raw body and its HMAC are genuinely valid together; the check never verifies that the claimed shop is consistent with the body/signature origin. The registry then hands the handler a `WebhookMetadata` object whose `shop` is the attacker-controlled header value paired with body content that actually originated from the attacker's own store, breaking the binding `authenticated_body == the_tenant_it_is_attributed_to`.

### Impact Explanation
This is a cross-tenant identity confusion at the point where the library itself asserts "this payload is for shop X." Any host application that trusts `WebhookMetadata#shop` (as documented/intended usage of this gem) to select which merchant's data to update, gate business logic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`), or key a cache/session is exposed to another tenant's data or actions being misattributed to a victim shop supplied purely via an unauthenticated header. This satisfies the Critical "cross-tenant access" bar even though it does not require possession of `api_secret_key`, an access token, or any privileged account — only the ability to install/operate the app on the attacker's own store (an action available to any unprivileged internet user) and to reach the target app's public webhook endpoint.

### Likelihood Explanation
Webhook endpoints are inherently internet-reachable (Shopify calls them over HTTP from the outside), so no additional network position is required. Obtaining a genuine (body, HMAC) pair only requires operating any store that has the target app installed, which is trivially available via Shopify's free developer/partner program. No secret material, token, or credential belonging to the app or any other merchant is needed — only header manipulation on replay.

### Recommendation
Bind the tenant/topic identity into the signed material instead of trusting headers verbatim:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable string (or otherwise cryptographically bind headers to the body), matching what Shopify itself asserts when it originally sent the webhook.
- Alternatively/additionally, cross-check the header-derived `shop` against the shop associated with the currently active/looked-up session or installation record before invoking any handler, rejecting mismatches.
- Reject replay by tracking `webhook_id` uniqueness per shop once the shop binding above is fixed.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and lets it register for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint: raw body `B` with header `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H` (valid HMAC over `B`), `x-shopify-topic: orders/create`.
3. Attacker captures `(B, H)` and replays a POST to the same endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` computes `to_signable_string` (= `B`) and confirms `H` matches — validation passes because it only ever checked the body. [5](#0-4) 
5. `Registry.process` builds `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker's order data>, ...)` and invokes the app's handler, which now believes attacker-controlled order content belongs to `victim.myshopify.com`. [3](#0-2)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
