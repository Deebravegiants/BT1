## Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC, allowing shop-domain spoofing on webhook delivery — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `api_version`, and `webhook_id` from unauthenticated HTTP headers, but its `to_signable_string` — the value the HMAC is computed and verified against — only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` passes the header-derived `shop` value straight through to the app's handler as the authoritative merchant identity, without it ever being bound by the signature check.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s `hmac` against `to_signable_string`. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from headers that are never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC and then hands the *header-derived* `shop` (and `topic`) to the app's `handler.handle`, treating it as the authenticated tenant identity for the event: [3](#0-2) 

This breaks the identity binding: `HMAC(raw_body, client_secret)` ≠ `HMAC(raw_body ‖ shop ‖ topic, client_secret)`. The equality the gem should enforce — "the shop this HMAC was computed for" == "the shop the handler is told the event belongs to" — is never checked. Since the `client_secret`/API secret is shared across every shop that installs a given app (not per-shop), any installer of the app can capture a genuine `(raw_body, hmac)` pair from their own shop's legitimate webhook delivery, then resend that identical body+hmac to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will invoke the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to the attacker-chosen victim shop.

### Impact Explanation
Any app built on this gem that trusts `WebhookMetadata#shop` from `Registry.process` to select which merchant's stored session/data to act on (a standard, documented usage pattern) can be tricked into processing an attacker-supplied event under another merchant's shop identity — a cross-tenant identity-binding bypass reachable by any unprivileged user who has installed the app on their own store (no access token, `client_secret`, or elevated privileges required beyond normal app installation).

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled shop to receive one legitimate webhook (readily available to any merchant/unprivileged user), and (2) replaying that captured body+HMAC to the app's public webhook endpoint with a forged shop-domain header. No secrets need to be extracted; the HMAC stays valid because it never covered the shop field in the first place.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the signable payload (or otherwise cryptographically bind them to the HMAC/verification step), or document explicitly that `request.shop`/`request.topic` are unauthenticated and must never be trusted as tenant identifiers by consuming apps without an independent verification step (e.g., cross-checking against a known, previously stored session for that shop).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app registers a webhook (e.g. `orders/create`).
2. Attacker triggers the event and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC_SHA256(client_secret, B)`), and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` computes `HMAC_SHA256(client_secret, B)` and finds it still equals `H`, so validation passes: [4](#0-3) 
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, `topic` and `body` from the attacker's captured event, even though `victim-shop` never sent this data: [5](#0-4)
