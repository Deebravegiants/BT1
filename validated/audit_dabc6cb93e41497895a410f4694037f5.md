This confirms the asymmetry: `AuthQuery#to_signable_string` includes `shop` in the HMAC-signed content [1](#0-0) , whereas `Webhooks::Request#to_signable_string` returns only the raw JSON body and never includes the `shop-domain` header [2](#0-1) . The `shop` value that is later trusted and dispatched to the handler comes straight from an unauthenticated header [3](#0-2) [4](#0-3) , while `HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string` using the app's single shared `api_secret_key` [5](#0-4) .

### Title
Webhook `shop-domain` header is not covered by HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` never covers the `shop-domain` header [2](#0-1) [4](#0-3) . The `shop` value from that unverified header is nonetheless passed on as the tenant identity in `WebhookMetadata` handed to the app's handler [3](#0-2) .

### Finding Description
The equality that should hold is: **bytes verified by HMAC == bytes that determine tenant identity acted upon**. Here it breaks: HMAC verifies only `@raw_body`; tenant identity (`shop`) is read from a separate, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`) via `shopify_header("shop-domain")` [3](#0-2) .

Compare with the OAuth callback path, where the analogous `shop` field IS included in the signed content, `AuthQuery#to_signable_string`, and thus is bound to the signature [1](#0-0) . The webhook path lacks this binding.

All apps built on this gem share one `api_secret_key` (the app's `client_secret`) across every installed shop/tenant — `HmacValidator.validate_signature` computes the signature using `Context.api_secret_key`, which is not shop-specific [6](#0-5) . Consequently, any tenant that has legitimately installed the app can receive real, validly-signed webhook bodies for their own shop. Because the header carrying `shop-domain` is outside the signed content, that same tenant can resend an identical `raw_body` + valid `hmac` pair to the app's webhook endpoint while substituting a different `shop-domain` header value. `HmacValidator.validate` will still return `true` (it only recomputes the HMAC over `@raw_body`), and `Registry.process` will dispatch the handler with `request.shop` set to the attacker-chosen victim shop domain [7](#0-6) .

### Impact Explanation
This crosses a tenant boundary: `shop == shop` (attacker's own shop) is what should hold for every processed webhook, but the gem allows `shop != shop` — a validly-HMAC'd body attributable to shop A is processed by the app as if it came from shop B, because the field the app acts on (tenant/shop) is not part of what the HMAC certifies. This is a cross-tenant confusion at the application layer that can drive downstream business logic (e.g. `shop/redact`, `app/uninstalled`, `customers/redact`, subscription changes) keyed off the untrusted `shop` value, matching the "High: cross-tenant access" category via a broken identity binding, analogous to the reported bug class where a field acted upon (balance delta) diverged from the field that was actually checked (previous vs current balance).

### Likelihood Explanation
Any merchant who installs the app (an unprivileged internet actor from the app's perspective — no special credentials, no access to `api_secret_key`) can obtain a legitimately signed `raw_body` + `hmac` pair from their own real webhook deliveries and replay it with a modified `shop-domain` header. No secret material needs to be extracted; the attacker only needs a webhook endpoint reachable over the internet (which webhook receivers must be, by design) and one legitimate webhook delivery to their own shop.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header value inside the signed content that `to_signable_string` returns for `Webhooks::Request`, or otherwise cryptographically bind the shop identity to the HMAC check (e.g., verify the HMAC over `raw_body + shop_domain` rather than `raw_body` alone), mirroring how `AuthQuery#to_signable_string` includes `shop` in the OAuth callback flow.

### Proof of Concept
1. App has one shared `api_secret_key` for all merchant installs (per `Context.api_secret_key` usage in `HmacValidator.validate_signature`) [6](#0-5) .
2. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: `raw_body = '{"id":123}'`, header `shopify-hmac-sha256 = <valid HMAC of raw_body>`, header `shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker resends the same request to the app's webhook endpoint, keeping `raw_body` and `shopify-hmac-sha256` identical, but changing `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses this fine (all required headers present) [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`raw_body` only) and it matches [9](#0-8) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-supplied body content as if it originated from the victim shop [10](#0-9) .

          received_signature = verifiable_query.hmac
