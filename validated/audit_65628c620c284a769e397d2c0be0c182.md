### Title
`usdk::transfer_from` approval replay via non-consuming sequence-number nonce enables unlimited unauthorized fungible-asset drains - (File: `aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move`)

### Summary
The stablecoin example's meta-transaction transfer authorization (`transfer_from`) binds a signed `Approval` to the token owner's **account sequence number** as a "nonce," intending it to be single-use. However, `transfer_from` is executed by the `spender`, not by `from`, so executing it never increments `from`'s sequence number. The signed approval therefore remains valid and can be replayed an unbounded number of times by anyone holding the `proof` bytes, moving up to `amount` out of `from`'s primary fungible store on every replay until `from` happens to submit an unrelated transaction of their own. This is the same class of bug as the reported guardian-share replay: a credential meant to be bound to a single "session"/usage is verified against a value that is never invalidated by the very operation it authorizes.

### Finding Description
`transfer_from` constructs the challenge that the `from` owner must have signed: [1](#0-0) 

The `nonce` field is populated with `account::get_sequence_number(from)` — the on-chain sequence number of the **owner** account, not of the transaction sender (`spender`). Because the transaction that invokes `transfer_from` is signed and submitted by `spender`, the Aptos VM increments `spender`'s sequence number for that transaction, not `from`'s. Nothing in `transfer_from`, `account::verify_signed_message`, or `primary_fungible_store::transfer_with_ref` records that this specific `Approval` (or this specific nonce value) has already been consumed: [2](#0-1) 

Consequently, the exact same `proof` bytes verify successfully against the identical `Approval` struct on every subsequent call, because `account::get_sequence_number(from)` still returns the same value it did when the owner signed it — the owner's sequence number only changes when `from` itself sends a transaction, which is unrelated to and not triggered by `transfer_from`.

This is functionally the same root cause as the reported Swafe bug: a value intended to bind an authorization to one "session" of use (there, a recovery `dkey`; here, an owner's nonce) is not actually invalidated by the very operation that consumes it, so a captured but stale credential remains fully valid and can be replayed against fresh state.

### Impact Explanation
Any spender who obtains a single valid `Approval` signature (e.g. from one legitimate authorized transfer, from logs, from mempool observation, or from an off-chain relayer) can call `transfer_from` repeatedly, draining `amount` from `from`'s USDK primary fungible store on each call, up to the full balance, without any further authorization from the owner. This is direct, repeatable theft of fungible-asset value from the account holder — a custody-grade impact (unauthorized transfer/drain of held fungible assets), not merely a denial of service. Because `transfer_from` uses `primary_fungible_store::transfer_with_ref` with the module's `TransferRef`, the transfer bypasses any single-use restriction that per-operation logic would need to impose; the only "protection" is the assumption that the nonce changes between uses, which is false in this call path.

### Likelihood Explanation
Likelihood is high once any single approval has been observed: replay requires no cryptographic break, only resubmitting the same `proof`, `from`, `to`, `amount` argument tuple already known to be valid. The `from` account's sequence number is public on-chain state and does not change as a side effect of `transfer_from`, so an attacker (the spender itself, or anyone who intercepts the calldata/approval) can trivially determine the nonce will remain valid and can automate repeated withdrawal until the owner happens to submit an unrelated transaction that increments their own sequence number (which many wallets/users do infrequently).

### Recommendation
Do not use the owner's account sequence number as the anti-replay nonce for actions executed by a third party. Instead:
- Maintain an explicit, monotonically increasing per-owner approval nonce (or per-approval unique ID) stored in module state (e.g., in a `Roles`/`Management`-adjacent resource keyed by owner address), and increment/consume it inside `transfer_from` itself before or after the transfer succeeds.
- Alternatively, bind the approval to a one-time, single-use hash (mark it spent in a table) rather than to a value external to the consuming transaction.
- Optionally add an expiration timestamp to `Approval` to bound the replay window, in addition to consuming the nonce.

### Proof of Concept
1. `from` signs one `Approval { owner: from, to: recipient, nonce: account::get_sequence_number(from), chain_id, spender, amount: 100 }` authorizing `spender` to move 100 USDK.
2. `spender` calls `usdk::transfer_from(spender, proof, from, scheme, pubkey, recipient, 100)`. This succeeds; `primary_fungible_store::transfer_with_ref` moves 100 USDK from `from` to `recipient`.
3. `from`'s account sequence number is unchanged, because `spender` was the transaction sender in step 2, not `from`.
4. `spender` calls `usdk::transfer_from` again with the identical `proof`/arguments. `account::verify_signed_message` re-derives the same `Approval` struct (nonce still equal to `from`'s unchanged sequence number) and the signature check passes again, moving another 100 USDK.
5. Step 4 can be repeated arbitrarily until `from`'s balance is exhausted or `from` submits any transaction of their own (incrementing their sequence number and invalidating further replays of that specific nonce value). [1](#0-0)
