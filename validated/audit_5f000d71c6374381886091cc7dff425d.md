### Title
NULL Pointer Dereference in Vault Gateway Handler's `PublicKeyGet` Method Crashes Node on Missing Params - (File: `core/capabilities/vault/gw_handler.go`)

### Summary
The Vault capability's node-side gateway handler dereferences the JSON-RPC `Params` field without a nil check when handling the `vault_publicKeyGet` method, unlike every other method in the same dispatch table. An unauthenticated client sending a `MethodPublicKeyGet` request through the public Gateway HTTP endpoint with a missing/null `params` field can reach this code path and trigger a nil pointer dereference panic, crashing the handling goroutine/service — directly analogous to the CVE-2018-6534 bug class (crafted message causing NULL pointer dereference/crash).

### Finding Description
`GatewayHandler.HandleGatewayMessage` dispatches incoming vault requests by method: [1](#0-0) 

For `MethodSecretsCreate`, `MethodSecretsUpdate`, `MethodSecretsDelete`, and `MethodSecretsList`, the request is routed through `h.requestProcessor.ProcessRequest`, whose per-method processors (`processCreateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`, etc.) all explicitly guard against `req.Params == nil` before dereferencing: [2](#0-1) [3](#0-2) 

However, `MethodPublicKeyGet` bypasses `requestProcessor` entirely and calls `handlePublicKeyGet` directly, which unmarshals `*req.Params` with **no nil check**: [4](#0-3) 

If `req.Params` is `nil`, `*req.Params` panics with a nil pointer dereference.

This is reachable from an unprivileged, unauthenticated client: a user sends an HTTP request to the Gateway's public `/user` endpoint with method `vault_publicKeyGet` and no (or `null`) `params`. The Gateway's `ProcessRequest` decodes the envelope and forwards it to the vault handler's `HandleJSONRPCUserMessage`: [5](#0-4) 

The gateway-side vault handler's own pre-checks (seen in `TestHandleJSONRPCUserMessage_RequestIDTooLong`, which sends `Params: nil` with method `MethodPublicKeyGet`) do not reject nil params for this method — only ID length is validated before dispatch: [6](#0-5) 

The request is then relayed to the node over the Gateway↔node connector, where the node's `GatewayHandler.HandleGatewayMessage` invokes the unguarded `handlePublicKeyGet`, causing the panic described above.

### Impact Explanation
A successful trigger causes a panic in the goroutine handling the gateway-to-node message (the connector's `readLoop`, per `core/services/gateway/connector/connector.go`), which can crash or destabilize the node's vault-handling service, denying availability of the Vault capability to legitimate workflows/nodes — the same "crash via crafted, no-auth-required message" bug class as the Icinga CVE.

### Likelihood Explanation
High: the trigger requires only a single unauthenticated JSON-RPC request to the public Gateway `/user` endpoint (`method: "vault_publicKeyGet"`, no `params` field), with no signature, allowlist entry, or JWT needed for this particular method, since it bypasses the authorization/params-validation pipeline that other vault methods use.

### Recommendation
Add an explicit `req.Params == nil` guard at the start of `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, returning a `UserMessageParseError`/invalid-params response (consistent with the pattern already used in `processCreateSecretsRequest`, `processDeleteSecretsRequest`, and `processListSecretIdentifiersRequest`), before dereferencing `*req.Params`.

### Proof of Concept
1. Send an HTTP POST to the Gateway's `/user` endpoint with body:
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault_publicKeyGet"}
```
(no `params` key, or `"params": null`).
2. The Gateway forwards this as a `jsonrpc.Request[json.RawMessage]` with `Params == nil` to the target node via the vault handler's `HandleJSONRPCUserMessage`.
3. The node's `GatewayHandler.HandleGatewayMessage` matches `case vaulttypes.MethodPublicKeyGet` and calls `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` — dereferencing the nil `*json.RawMessage` pointer and panicking. [7](#0-6) [4](#0-3) 

**Note on confidence**: I could not fully trace whether an intermediate layer in the gateway (outside the files inspected) might independently reject nil `params` for `vault_publicKeyGet` before forwarding to the node — the one test I found (`TestHandleJSONRPCUserMessage_RequestIDTooLong`) uses `Params: nil` for this method and only surfaces an ID-length error, which supports reachability, but I did not locate a dedicated "nil params" test case for `MethodPublicKeyGet` specifically to confirm the exact server-side crash behavior. A Devin session with full repo/test execution access would be needed to definitively confirm the panic occurs at runtime.
