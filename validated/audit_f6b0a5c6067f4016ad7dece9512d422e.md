### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers when dispatching to the app's handler. Because those identity fields are never included in the signed material, any party capable of obtaining one valid `(body, hmac)` pair for the app's `client_secret` — e.g. a merchant who has installed the app and receives their own legitimate webhooks — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the library to report the payload as originating from a different, victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.to_signable_string` (i.e. the body) against the secret — it has no knowledge of, and never incorporates, the shop/topic/webhook-id headers: [3](#0-2) 

`Registry.process` performs exactly that HMAC check and then immediately trusts `request.shop`/`request.topic` to build the metadata handed to the app's business logic, without any secondary binding of the shop identity to the signed body: [4](#0-3) 

This is the same class of bug as the Holograph report: a value that is *acted upon* (here, the `shop` used to attribute/dispatch the webhook) is not covered by the authenticity check (the HMAC), so the binding `verified_bytes == acted_upon_identity` is broken. The equality that should hold — `HMAC-covered data == data used to determine the tenant` — does not hold, since only the body is covered while the tenant-identifying header is not.

### Impact Explanation
An attacker who operates their own Shopify store with the target app installed receives legitimate webhooks for their own shop, each with a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `client_secret`. Because the shop header isn't part of the signed payload, the attacker can resend that exact valid body+HMAC to the app's public webhook endpoint while forging `x-shopify-shop-domain` to name a victim shop. `Registry.process` will accept the HMAC as valid (it only checks the body) and pass `shop: <victim-shop>` to the app's webhook handler along with attacker-controlled body content. Any host application that trusts `WebhookMetadata#shop` (as the library's design implies it should, since it is the field surfaced post-HMAC-validation) will attribute and process attacker-supplied data under the victim tenant's identity — a cross-tenant data/action injection.

### Likelihood Explanation
Any merchant who installs the app (an "unprivileged" tenant relative to other tenants) can trivially capture their own valid webhook body/HMAC pairs (e.g. by inspecting their own webhook deliveries) and replay them with a modified shop header — no access to `api_secret_key` or any victim credential is required. This is a purely mechanical HTTP replay against the app's public webhook receiving endpoint.

### Recommendation
Bind the tenant/topic identity into the signed material, or otherwise cryptographically tie the `shop`, `topic`, and `webhook_id` header values to the verified request before they are relied upon:
- Prefer validating that `request.shop` is a known/expected shop for the currently-configured app installation (cross-check against stored sessions) rather than trusting the header value on its own.
- Alternatively, extend `to_signable_string`/`HmacValidator` (or add a distinct verification step) so the shop-domain and topic headers are included in what's authenticated, and reject requests where they don't match an expected registration.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over `B` — it succeeds since `H` matches `B`+secret regardless of the shop header: [5](#0-4) 
4. The app's registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the data never originated from that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
