Confirmed the vulnerability. The webhook `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) validates only `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` — and for `Webhooks::Request`, `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`) and are never part of the HMAC-signed payload. `Registry.process` then trusts `request.shop` and `request.topic` unconditionally to dispatch the handler and build `WebhookMetadata` (`lib/shopify_api/webhooks/registry.rb:190-199`).

### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only, then dispatches the webhook handler using the unverified `shop`/`topic` header values. An attacker who legitimately receives one genuine, correctly-signed webhook delivery (e.g., by installing the app on their own store, which requires no privileged credentials) can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting a different `shop-domain` header. The HMAC check still passes because it never covered the header, so the app processes the payload as if it came from a victim shop it was never sent by.

### Finding Description
The identity binding that should hold is:
`shop header value used by the handler == shop that the HMAC-signing secret actually attests to`

In this gem, that binding is broken:
- `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) computes/compares the HMAC only over `verifiable_query.to_signable_string`.
- For webhooks, `to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) is just `@raw_body`.
- `shop`, `topic`, `webhook_id`, `api_version` are all pulled from headers (`lib/shopify_api/webhooks/request.rb:15-33`), none of which participate in the signed bytes.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) validates the HMAC, then unconditionally trusts `request.shop` and `request.topic` to select and invoke the handler and to populate `WebhookMetadata`.

Because the signature is body-only, any request with a previously-observed valid `(body, hmac)` pair remains "valid" under the app's own `client_secret` no matter what `shop-domain`/`topic` header value is attached, letting the header dictate which tenant's data/handler context the payload is attributed to. ### Impact Explanation
This is a cross-tenant identity confusion: a shop-domain value fully controlled by the request sender is used, post-"verification", to attribute a webhook body to a tenant, without that shop ever actually being the origin of the signed bytes. Any application built on this gem that trusts `WebhookMetadata#shop` for per-tenant authorization, data storage keys, or side effects (e.g., writing/deleting data keyed by shop, or triggering shop-scoped app logic) can be made to act on a victim shop's identity using a payload the attacker fully controls. This matches the Critical "cross-tenant access" impact category, since no access token, `api_secret_key`, or privileged credentials are required — only a genuine webhook delivery to any shop that installed the app (including the attacker's own store).

### Likelihood Explanation
Likelihood is meaningful but requires the attacker to hold at least one legitimate `(raw_body, hmac)` pair, which they can trivially obtain by installing the app on any shop they control (a normal, unprivileged action) and capturing one of the webhooks Shopify sends them. From there, replaying that captured request with a substituted `shop-domain` (and/or `topic`) header is a pure network-level replay with no cryptographic secret needed, since the signature check is header-independent.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable payload used for HMAC verification, or otherwise cryptographically bind them (e.g., verify the caller-supplied shop against the shop associated with the API version/secret used, or require the host application to cross-check `request.shop` against the shop that a corresponding active session/registration expects) before dispatching to a handler. At minimum, document that `WebhookMetadata#shop` and `#topic` are unauthenticated and must not be trusted for authorization decisions without independent verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (no special privileges needed) and receives a genuine webhook delivery, e.g. `orders/create`, with raw body `B` and Shopify-computed header `x-shopify-hmac-sha256: H` (where `H = HMAC(app_client_secret, B)`).
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed; `hmac` decodes to the same value Shopify originally sent.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) and matches `H` — validation succeeds (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:27-31`).
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though `victim-shop.myshopify.com` never sent or authorized this payload. [5](#0-4) [6](#0-5)
