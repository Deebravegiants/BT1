### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header is trusted by `Registry.process` without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , so the HMAC verified by `Utils::HmacValidator.validate` in `Registry.process` [2](#0-1)  attests only that "some request signed with `api_secret_key` produced this exact body." The `shop`, `topic`, `webhook_id` and `api_version` values are read straight from unauthenticated HTTP headers [3](#0-2)  and are handed to the host app's handler unchanged, with `shop: request.shop` passed directly into `WebhookMetadata` [2](#0-1) .

### Finding Description
This mirrors the report's bug class: an identity field (`shop`) is *acted upon* (passed to the handler and, per the gem's own documentation, used to key merchant-specific data: `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [4](#0-3) ) but is *not* bound by the cryptographic check that is supposed to authenticate the request. The binding that should hold is:

`HMAC-verified(shop_header) == shop_header_delivered_to_handler`

but what is actually verified is:

`HMAC-verified(raw_body) ≠ shop_header_delivered_to_handler` (the header is outside the signed scope).

Because any merchant who has installed the app (an "unprivileged" party with respect to *other* tenants of the same app) legitimately receives real Shopify webhooks for their own shop with a body and a correctly-computed HMAC over that body, they can capture that request and replay it against the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to a victim shop's domain. Since `Request#to_signable_string` never includes the shop header, the exact same HMAC over the same body remains valid, `Utils::HmacValidator.validate` returns `true`, and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` to the handler with the attacker-chosen victim shop.

`Registry.process` performs no cross-check between `request.shop` and any list of shops that are actually subscribed to that topic, nor does it correlate `webhook_id` to a specific tenant: [2](#0-1) .

### Impact Explanation
Per the gem's own documented usage pattern, apps are expected to key business logic and possibly session/data lookups off `data.shop` directly [5](#0-4) . An attacker who is a legitimate (if malicious) installer of the app can forge the tenant identity of inbound webhook events for any other shop, without needing that victim shop's access token, `client_secret`, or any credential belonging to the victim. This is a cross-tenant data/identity confusion in a security-relevant primitive that host apps are told to trust (`Registry.process`/`WebhookMetadata`), matching the "Critical - cross-tenant access" impact bucket in spirit, since it defeats the tenant-isolation guarantee the HMAC check is supposed to provide.

### Likelihood Explanation
Moderate-to-high: it requires only (a) the attacker to install the target app on their own store (a normal, unprivileged action any internet user can take for a public app) to obtain one genuinely-signed webhook body+HMAC pair, and (b) the ability to send an arbitrary HTTP POST with custom headers to the app's public webhook endpoint, which is by definition internet-reachable. No secret material or victim credentials are needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise validate `request.shop` against the specific shop that the receiving endpoint/subscription belongs to before constructing `WebhookMetadata`. At minimum, the gem's documentation should explicitly warn implementers not to trust `data.shop` as an authenticated tenant identifier since it is not covered by the signature, and `Registry.process` could reject requests where the shop header cannot be correlated to a known/expected registration.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggers a webhook event (e.g. `orders/create`), and captures the raw POST: body `B`, and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and the same `X-Shopify-Hmac-Sha256: H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac: H...})` is constructed; `to_signable_string` returns `B` only [1](#0-0) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B) == H` [6](#0-5) .
5. The host app's handler receives `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's data>, ...)` and processes it as if it were a genuine event for `victim.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
