## Analysis

The reported bug class (a contract that accepts native ETH via `receive()` but has no protected mechanism to recover it) has a stronger, more severe analog in Hyperbridge's `CallDispatcher`. Unlike the audited `SwapRouter.sol`, where the issue is that funds become *permanently unrecoverable*, in `CallDispatcher.sol` the issue is that any ETH balance held by the contract is *fully drainable by any unprivileged caller*, because the only function capable of moving its balance has zero access control.

### Title
Unrestricted `CallDispatcher.dispatch()` allows any address to drain native ETH held by the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a shared, permissionless utility contract used by `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` to execute arbitrary post-bridge calldata on behalf of `onAccept` (e.g., unwrapping WETH and forwarding native ETH to a router for a swap). It implements `receive() external payable {}` to accept ETH [1](#0-0) , but its only externally callable function, `dispatch`, has no `onlyHost`/`onlyOwner`/caller restriction whatsoever, and directly forwards the contract's ETH balance to caller-specified targets: [2](#0-1) .

### Finding Description
`dispatch(bytes memory encoded)` decodes an array of `Call{to, value, data}` structs and executes `to.call{value: call.value}(call.data)` for each entry, with the only check being that `to` has nonzero code size [2](#0-1) . There is no restriction limiting who may call `dispatch`, nor any check that the caller is the legitimate `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` instance that is supposed to orchestrate the flow described in the docs (unwrap WETH → forward ETH via `Call.value` to a router) [3](#0-2) .

Because `CallDispatcher` is a single globally shared contract (not per-caller), any native ETH balance it holds — whether from (a) a race window between the wrapper sending ETH to it and calling `dispatch` in the intended flow, (b) leftover/unswept dust from a prior `dispatch` execution where `call.value` did not consume the full balance, or (c) anyone mistakenly or deliberately sending ETH directly via `receive()` — is fully exposed. Any external, unprivileged account can call `dispatch()` directly with a `Call[]` array targeting an address they control with `value` equal to `address(this).balance`, extracting all native ETH currently held by the contract.

This differs from the reported `SwapRouter` bug (funds permanently stuck) — here the funds are not merely lost, they are actively stealable by any third party who front-runs or simply calls the unrestricted function.

### Impact Explanation
Any native ETH balance sitting in `CallDispatcher` — even briefly, as part of the documented cross-chain calldata-execution flow that unwraps WETH into native ETH on the destination chain — can be swept by an unrelated third party before the legitimate `dispatch` call completes its intended purpose, or via reentrancy/front-running around the wrapper's `onAccept` execution. This constitutes concrete theft of protocol/user funds moving through the `HyperFungibleToken` calldata-execution path, which the docs explicitly say "the `CallDispatcher` can hold and forward native tokens."

### Likelihood Explanation
Likelihood is elevated by the fact that `dispatch` is `external` with no caller check, and requires only that the target has code — trivially satisfied by deploying a minimal contract. Any user with knowledge of the pending ETH balance (visible on-chain) or the ability to front-run a pending `dispatch` transaction in the mempool can immediately extract the funds. No privileged role, governance action, or malicious-admin assumption is required — a single unprivileged transaction suffices.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by the specific authorized app contract(s) (e.g., an `onlyAuthorizedCaller` modifier checking `msg.sender` against a registry of `HyperFungibleToken`/`WrappedHyperFungibleToken` instances), or make `dispatch` accept and immediately consume ETH passed via `msg.value` in the same call rather than relying on a pre-funded contract balance, eliminating any window where unprotected ETH sits in the shared dispatcher.

### Proof of Concept
1. `WrappedHyperFungibleToken.onPostRequestTimeout`/`onAccept`-driven flow (or any other integrator) sends native ETH to `CallDispatcher` (e.g., via `IWETH.withdraw` followed by a transfer, or the wrapper forwarding value) ahead of calling `dispatch`.
2. Before the legitimate `dispatch(calls)` transaction is mined (or if any dust remains after a prior `dispatch` execution), an attacker submits:
   ```solidity
   Call[] memory calls = new Call[](1);
   calls[0] = Call({ to: address(attackerContract), value: address(callDispatcher).balance, data: "" });
   callDispatcher.dispatch(abi.encode(calls));
   ```
3. Since `dispatch` has no caller restriction [2](#0-1) , this succeeds and transfers the full ETH balance held by `CallDispatcher` to the attacker's contract.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
