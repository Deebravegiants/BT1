## Title
Unrestricted Cross-Chain Bandwidth Sponsorship Lets Any Purchaser Evict and Permanently Destroy Any Other App's Paid Bandwidth Subscriptions - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth` credits prepaid bandwidth into a `(chain, app)` bucket that is selected entirely by fields inside the purchase message body (`msg.chain`, `msg.app`), not by the actual `request.source` of the payer. Any account that can call `purchase()` on any *one* registered `BandwidthManager` can therefore write into the bandwidth "namespace" belonging to *any other* app on *any other* chain. Because each namespace's subscription list is a FIFO capped at 1024 entries that silently evicts the oldest entry on overflow, an attacker can flood a victim's `(chain, app)` bucket with throwaway purchases to evict the victim's real, already-paid-for subscriptions — permanently destroying funds the victim spent and causing their future messages to be rejected by the gate (denial of service), all while the victim never authorized or was even aware of the write into "their" namespace.

### Finding Description
The `Allowance` storage map is explicitly keyed by an attacker-supplied field rather than by the chain that actually paid: [1](#0-0) 

The purchase handler `on_accept` only validates that `request.from` matches the *registered manager contract* for `request.source` — it performs no check that the caller has any relationship to the `(msg.chain, msg.app)` pair it is about to write into: [2](#0-1) 

`push_subscription` unconditionally appends to the target list and, once the list is at the 1024 cap, evicts the *oldest* entry regardless of its remaining byte balance or who purchased it: [3](#0-2) 

This mirrors the structure of the reported Vault bug class: a resource/policy that is supposed to be scoped and isolated to one "namespace" (here, an app's own `(chain, app)` bandwidth bucket, analogous to a Sentinel RGP scoped to one Vault namespace) can instead be mutated/consumed by an unrelated, unprivileged party from a different namespace, because the enforcement only checks the *dispatching* chain/manager identity and never checks ownership of the *target* namespace being written to. The docs confirm this is intentional for "sponsorship" but do not mention any guard against griefing: [4](#0-3) 

### Impact Explanation
An attacker who can execute `purchase()` from any single chain with a registered `BandwidthManager` (this is a public, permissionless call available to anyone with the fee token — no relationship to the victim app is required) can:
1. Target any `(app_chain, app)` pair on Hyperbridge, including apps on entirely different chains than the one the attacker is transacting from.
2. Repeatedly purchase the cheapest tier to push the victim's FIFO subscription list to the 1024 cap and beyond, causing `push_subscription` to evict the victim's genuine, already-paid, unexpired subscriptions (`Event::SubscriptionEvicted`).
3. Permanently destroy the victim's prepaid bandwidth (funds loss — the victim paid real fee tokens for bytes that are now gone) and drive the victim's live allowance to zero, causing `BandwidthGate::try_consume` to reject the victim's subsequent legitimate ISMP messages with `GateError::NoAllowance` — i.e., a denial of service against that app's ability to use Hyperbridge, matching the "route unable to deliver messages" / "permanent freezing of funds" impact bar.

This is reachable by a fully unprivileged relayer/user simply calling the public `BandwidthManager.purchase()` entry point — no governance/admin/malicious-node capability is needed.

### Likelihood Explanation
The only prerequisite is that at least one `BandwidthManager` is registered on some chain (which is expected to be true in production, since this is how the bandwidth feature works at all) and that the attacker has enough fee tokens to fund the eviction purchases. The number of purchases required equals `1024 - victim_current_subscription_count`, so a victim with few live subscriptions (the common case) is cheap to evict entirely. No race condition, no special timing, and no interaction with any other subsystem is required — this is a straightforward, repeatable write path.

### Recommendation
Bind the credited namespace to something the payer cannot freely choose, or require explicit authorization from the target app before crediting/affecting its bucket:
- Restrict `msg.chain`/`msg.app` sponsorship so it can only append to a bucket the caller controls, or require the target app to opt in (e.g., an allow-sponsor list per `(chain, app)`).
- Alternatively, decouple sponsorship from the FIFO cap logic: track "sponsored-by" provenance and never let an externally-sponsored purchase evict a subscription the app itself purchased, or raise/segregate the cap per payer rather than sharing one global 1024-slot FIFO per `(chain, app)`.
- At minimum, emit alerts / rate-limit cross-chain sponsorship writes and consider evicting the *cheapest/smallest* remaining entry rather than strictly FIFO-oldest, to reduce the blast radius of griefing purchases.

### Proof of Concept
1. Governance registers `BandwidthManager` for `StateMachine::Evm(A)` (attacker's cheap chain) as well as for `StateMachine::Evm(B)` where the victim app `V` lives, per normal onboarding (see `set_manager` at [5](#0-4) ).
2. Victim `V` legitimately purchases bandwidth: `purchase()` on `BandwidthManager` on chain `B`, crediting `Allowance[(Evm(B), V)]` with e.g. 1 subscription of 300 KB (Tier 2), via the normal path in `on_accept` ( [6](#0-5) ).
3. Attacker, holding no relationship to `V`, calls `purchase()` on `BandwidthManager` deployed on chain `A` (or even chain `B`) `1024` times with `tier = TierOne` (cheapest) and payload `chain = Evm(B)`, `app = V`'s app bytes.
4. Each purchase dispatches a `PostRequest` to `pallet-bandwidth` with `msg.chain = Evm(B)`, `msg.app = V`; `on_accept` decodes it and calls `push_subscription(&msg.chain, &key, ...)`, unconditionally appending to `Allowance[(Evm(B), V)]` ( [7](#0-6) ).
5. Once the list length reaches 1024, further attacker purchases trigger `list.remove(0)`, evicting `V`'s original, legitimately-paid subscription with `Event::SubscriptionEvicted { app_chain: Evm(B), app: V, lost_bytes: 300_000, .. }`.
6. `V`'s next real ISMP message routes through `BandwidthGate::try_consume(&Evm(B), &V, bytes)` ( [8](#0-7) ) and is now rejected with `GateError::NoAllowance` even though `V` paid for and expected that bandwidth to still be available — funds lost, message delivery denied.

```rust
		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}
```

```rust
	impl<T: Config> IsmpModule for Pallet<T> {
		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}
```

```rust
impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
```

```text
## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```
