### Title
Webhook HMAC verification does not cover the `shop`, `topic`, or `webhook_id` headers used for dispatch, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` + `to_signable_string`. For webhooks, `to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated HTTP headers and are never part of the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate`/`validate_signature` only re-computes the HMAC over `to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header — it never binds `shop`/`topic`/`webhook_id` into the check: [3](#0-2) 

`Webhooks::Registry.process` performs this body-only HMAC check and then unconditionally trusts the header-derived `request.shop`, `request.topic`, and `request.webhook_id` to build the dispatched metadata and select the handler: [4](#0-3) 

This is exactly the identity-binding gap described in the analog bug class: the "index" (here, `shop`/`topic`) that the downstream logic acts on is not the same thing the cryptographic check actually verifies. Contrast this with `Auth::Oauth::AuthQuery`, where `shop` and `host` are explicitly folded into `to_signable_string` and therefore are bound by the HMAC: [5](#0-4) 

The equality the check should enforce is:
`HMAC_secret(body ‖ shop ‖ topic) == received_hmac`
but the gem only ever checks `HMAC_secret(body) == received_hmac`, so `shop`/`topic` float free of the signature.

### Impact Explanation
Because the app's `api_secret_key` is shared across every merchant install of the app, any `(body, hmac)` pair that is valid for one shop/topic is *also* valid for every other shop/topic, since the header fields are not part of the signed content. An attacker who can obtain even one legitimate `(body, hmac)` pair — trivially, by installing the app on their own shop and receiving a real webhook, or by observing a webhook whose body is predictable/constant (e.g. `{}` payloads) — can replay that exact body+hmac to the app's public webhook endpoint while forging the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers to point at a victim shop and a different topic. `HmacValidator.validate` passes, and `Registry.process` will hand `WebhookMetadata` bearing the attacker-chosen `shop`/`topic` straight to the registered handler. Depending on how the host app's handlers key off `shop` (session lookup, data deletion on `app/uninstalled`, order/customer record updates, etc.), this allows cross-tenant confusion/impersonation of a victim merchant's webhook stream using only a body the attacker legitimately obtained for their own tenant — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to hold at least one valid `(body, hmac)` pair for the target app (obtainable by installing the app themselves, a low-privilege/unauthenticated-from-the-victim's-perspective action), plus the ability to POST directly to the app's public webhook endpoint with arbitrary headers, which any internet user can do since Shopify webhook endpoints are unauthenticated HTTP endpoints by design. The header/body split is baked into the gem's `Webhooks::Request`/`HmacValidator`/`Registry` classes, so every consumer of this gem's webhook feature inherits the gap regardless of how carefully the host app implements its handlers.

### Recommendation
Bind the routing fields into the signed content check, or otherwise verify that the headers used for dispatch actually correspond to the delivery that produced the HMAC:
- Track/require the shop and topic pairing to be validated against a source that Shopify itself binds to the HMAC context, or
- Have `HmacValidator`/`Webhooks::Request` refuse to reuse the same `(body, hmac)` pair across different `shop`/`topic`/`webhook_id` combinations, e.g. by tracking `webhook_id` (which Shopify intends to be unique per delivery) for replay/cross-binding detection, and treat `shop`/`topic` as attacker-controlled input that must not be trusted purely because the body-only HMAC passed.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (or otherwise obtains a webhook body that is constant/predictable, e.g. `{}`), and receives a legitimate webhook delivery, capturing `raw_body` and the `x-shopify-hmac-sha256` header — this HMAC is valid because it is computed only over `raw_body` with the app's shared `api_secret_key`, per `Request#to_signable_string`/`HmacValidator.validate_signature`.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body`/`hmac` but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: app/uninstalled` (or any registered topic) and an arbitrary `x-shopify-webhook-id`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the secret (see `lib/shopify_api/utils/hmac_validator.rb` L12-31), then dispatches `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` to the app's registered handler, letting the attacker trigger shop-scoped webhook logic for a shop they do not own.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
