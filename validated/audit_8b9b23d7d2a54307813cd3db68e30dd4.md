### Title
Excess native ETH sent to `EvmHost.dispatch`/`fundRequest` for fee swaps is refunded to the Host contract, not the caller, and is permanently unrecoverable - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward it directly to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, ...)` to buy the exact fee-token amount needed. This mirrors the FootiumAcademy pattern of accepting a native payment without validating it matches the required amount exactly and without returning the unused portion to the payer.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
the full `msg.value` is forwarded to `swapETHForExactTokens`. Uniswap V2's router refunds any unused ETH (`msg.value - amounts[0]`) via `TransferHelper.safeTransferETH(msg.sender, ...)`, where `msg.sender` from the router's perspective is `EvmHost` itself (the direct, immediate caller), not the original transaction sender or the calling application contract. The same pattern repeats in `dispatch(DispatchGet)` and `fundRequest`: [2](#0-1) [3](#0-2) 

After the swap call returns, none of these three functions checks for or forwards back any leftover native balance to `_msgSender()` or `post.payer`. The excess ETH becomes part of `EvmHost`'s balance. I found no `withdraw`/`sweep` function in `EvmHost.sol` that could return this stranded ETH to the original payer — it is not part of the discoverable interface in this file, and per the code that governs revenue withdrawal (`hostManager`, described as the channel for hyperbridge governance to withdraw *protocol revenue*), any recovered balance would go to governance/relayers rather than the original overpaying caller.

This is structurally the same root cause as the reported FootiumAcademy issue: a `payable` entry point that computes and skims only the "required" amount from `msg.value` and silently retains the remainder, where the retaining party is not the payer.

By contrast, higher-level apps in this same codebase (`IntentGatewayV2`, `ExtrinsicIntents`, `WrappedHyperFungibleTokenUpgradeable`) explicitly track `msgValue` after their own swap calls and refund the leftover to `msg.sender`: [4](#0-3) 
This confirms the project's own convention is to refund unused native value — a convention `EvmHost.dispatch`/`fundRequest` does not follow, since the swap's refund target (the `EvmHost` contract itself) is not the same address as the caller who needs the refund.

### Impact Explanation
Any app contract or EOA that dispatches a POST/GET request or funds a request by sending native ETH slightly (or significantly) more than the exact amount needed for the Uniswap swap into the fee token will permanently lose the excess to the `EvmHost` contract's balance, with no user-facing mechanism to reclaim it. Since `EvmHost` is the sole, shared dispatch entry point used by essentially all Hyperbridge apps (`IHyperFungibleToken`, `BandwidthManager`-style apps, custom `IApp` integrations, LayerZero adapter, etc.) that choose to pay in native token, this affects a broad set of unprivileged callers across the protocol, not just one isolated app. This satisfies "permanent freezing/loss of funds" for the overpaying party.

### Likelihood Explanation
Overpayment is likely in practice: callers must estimate the ETH amount required to cover a Uniswap swap for an unpredictable `fee` amount (subject to price slippage/quoting inaccuracy), and the documentation for `quote()` explicitly recommends adding buffers (e.g., "Apply a generous 2x buffer... Excess native is refunded by the uniswap router") based on an incorrect assumption that the router's refund reaches the original caller: [5](#0-4) 
This shows that even the project's own downstream integrations (e.g. `HyperbridgeLzEndpoint`) assume the excess reaches the payer, when in fact for direct `EvmHost.dispatch` calls it does not.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the router's return value/actual ETH consumed (`amounts[0]`) and refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated `payer`), following the same pattern already used in `IntentGatewayV2`/`ExtrinsicIntents`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 refund = msg.value - amounts[0];
if (refund > 0) {
    (bool sent, ) = payable(_msgSender()).call{value: refund}("");
    if (!sent) revert FailedToSendETH(refund);
}
```

### Proof of Concept
1. App contract `A` calls `EvmHost.dispatch{value: 1 ether}(DispatchPost{..., fee: X})` where the actual ETH needed to buy `X` fee tokens via Uniswap is `0.3 ether` (due to conservative overestimation, slippage buffer, or price movement between quote and execution).
2. Inside `dispatch`, `swapETHForExactTokens{value: 1 ether}(X, path, address(this), ...)` executes, consuming `0.3 ether` for the swap and refunding the remaining `0.7 ether` to `msg.sender` of the router call — which is `EvmHost`, not contract `A`.
3. `dispatch` returns; the commitment is recorded; the request proceeds normally.
4. `EvmHost`'s native balance is now permanently `0.7 ether` higher, with no function reachable by `A` or its end-users to recover it. [1](#0-0)
