### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator` verifies the payload bytes but never binds them to the `shop` value that the same request carries. `Registry.process` nonetheless trusts `request.shop` (taken straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header) as the tenant identity handed to the host application's handler once the HMAC check passes.

### Finding Description
`Request#hmac` and `Request#to_signable_string` compute/verify the signature solely over `@raw_body`: [1](#0-0) [2](#0-1) 

`Request#shop` is read from an independent, unsigned header: [3](#0-2) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature and compares it with `verifiable_query.hmac`: [4](#0-3) 

Because `to_signable_string` never includes the shop header, the HMAC only proves "these body bytes were signed with `api_secret_key`" — it proves nothing about which shop they belong to. `Registry.process` nevertheless uses the validated request's `shop` field, straight from the header, to build the `WebhookMetadata` passed into the app's own `WebhookHandler#handle`: [5](#0-4) [6](#0-5) 

This breaks the intended identity binding `hmac_verified_bytes == claimed_shop`. Because the `api_secret_key` is shared by the app across every merchant that installs it, any merchant (an unprivileged, self-service installer of the app — not requiring the app's `client_secret` or any elevated credential) can:
1. Trigger a legitimate event in their own store (e.g., create an order) so Shopify sends a genuinely HMAC-signed webhook `POST` to the app's endpoint, with body `B` and valid `hmac(B, secret)`.
2. Capture that request and replay it to the same endpoint, keeping `B` and its valid HMAC byte-for-byte identical, but rewriting only the `x-shopify-shop-domain` header to name a victim shop.
3. `HmacValidator.validate` still succeeds, because the signature never depended on the shop header.
4. `Registry.process` forwards `WebhookMetadata.new(shop: "<victim-shop>.myshopify.com", body: B, ...)` to the host app's handler, which typically uses `shop` to select the tenant record to update/create/delete.

The result is that data or events genuinely produced by the attacker's own store can be attributed to and processed against an arbitrary victim tenant inside the app's business logic, purely by forging one HTTP header on a byte-identical, validly-signed request.

### Impact Explanation
This crosses a tenant boundary using only self-service capabilities (installing the app in one's own store) — no access token, no `client_secret`, no privileged account is required. Because host applications commonly key persistence and side effects (creating orders, cancelling subscriptions, updating billing state, etc.) directly off the webhook's reported shop, this allows cross-tenant data confusion/injection, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs a real, low-privilege merchant account (trivial to obtain, e.g. a free trial install) capable of generating at least one genuine webhook event, plus the ability to replay an HTTP request with one modified header — no cryptographic material or secret is needed. This is a realistic, low-effort attack path in any deployment that relies on the gem's `Webhooks::Registry`/`Request`/`HmacValidator` for tenant attribution.

### Recommendation
Include the shop domain (and topic/webhook-id) in the signable string used for HMAC verification, or explicitly require the host application to cross-check `request.shop` against an out-of-band trusted mapping (e.g. the shop that owns the corresponding registration) before trusting it. At minimum, `Utils::HmacValidator`/`Webhooks::Request` should bind the shop identity into the same bytes that are HMAC-verified so that `hmac_verified_bytes == claimed_shop` holds.

### Proof of Concept
1. App merchant A installs the app and triggers an event in shop `a.myshopify.com`; Shopify sends:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over body B>
x-shopify-shop-domain: a.myshopify.com
Body: B
```
2. Attacker (merchant A) resends the identical request but changes only the header:
```
x-shopify-shop-domain: victim.myshopify.com
```
3. `Utils::HmacValidator.validate` (via `Request#to_signable_string` returning only `B`) reports the signature as valid. [7](#0-6) 
4. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and body `B`, causing the app to act on the victim tenant using attacker-supplied content.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
