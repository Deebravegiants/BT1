### Title
Webhook shop-domain (and topic/webhook-id/api-version) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never included in the signed material [2](#0-1) . The equality the gem is supposed to enforce is `shop authenticated by HMAC == shop the handler acts on`, but in reality the HMAC only binds the body bytes, leaving the `shop` header free for anyone who can produce a body+HMAC pair to swap in.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors simply read the corresponding `shopify-*`/`x-shopify-*` headers with no cryptographic binding to the body or to each other [5](#0-4) .

`Registry.process` validates HMAC once, then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop` value and dispatches it to the app-supplied handler [6](#0-5) . The documented handler contract explicitly instructs integrators to key business logic (e.g., "shop_domain") off `data.shop` [7](#0-6) , meaning `shop` is treated by design as an authenticated tenant identifier even though it never entered the signature computation.

Because any merchant/attacker who operates a shop connected to the app can receive a legitimately-signed webhook (valid body + HMAC, signed by Shopify with the app's real secret) for *their own* shop, they can capture that `raw_body`/`hmac` pair and replay it to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header for a different (victim) shop. `HmacValidator.validate` still passes because the body is byte-for-byte identical and the HMAC only covers the body — the shop header is invisible to the signature check. The handler then executes with `data.shop` pointing at the victim tenant while `data.body` contains attacker-controlled content from the attacker's own shop, breaking the equality `shop verified by HMAC == shop acted upon`.

### Impact Explanation
This is a cross-tenant confusion vector reachable by any unprivileged user who operates (or has previously operated) a shop installed on the target app — no access token, `client_secret`, or privileged account is required, only a captured genuine webhook payload from their own store. Depending on how the host application's `WebhookHandler#handle` uses `data.shop` (per the documented pattern of using it as `shop_domain` for tenant-scoped database writes, background jobs, or side effects), this can let an attacker inject attacker-controlled webhook payloads that get attributed to and processed against a victim shop's tenant record, causing cross-tenant data corruption or unauthorized state changes under another merchant's identity.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have (or have had) a shop connected to the app so they can obtain at least one genuinely-signed webhook body/HMAC pair, and it requires the host app to reuse that same body across topics/shops in a way that's meaningful (e.g., replaying an `orders/create` payload against a different shop). The gem's own test suite demonstrates the header-based `shop`/`topic`/`webhook_id` values are trusted without any linkage to the HMAC [8](#0-7) , confirming the mechanism is exploitable exactly as designed rather than as an edge case.

### Recommendation
Include `shop`, `topic`, and any other identity-bearing headers as part of the HMAC-signed material for webhook requests (or otherwise cryptographically bind them to the raw body), and/or have `Registry.process` independently verify that the `shop` domain matches an app-known, previously-registered shop for that specific webhook subscription rather than trusting the unauthenticated header value. At minimum, document that `data.shop` from `WebhookMetadata` is not itself HMAC-protected and must not be used as the sole tenant-authorization key without additional verification (e.g., cross-checking against the webhook_id registered for that shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), receiving a legitimate POST with a valid `x-shopify-hmac-sha256` computed over the raw JSON body using the app's real secret.
2. Attacker replays that exact raw body and HMAC header to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the headers [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the HMAC only ever covered `@raw_body`, and that body is unmodified [1](#0-0) .
4. The handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` [10](#0-9) , causing the app to process attacker-controlled webhook content as if it originated from the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
