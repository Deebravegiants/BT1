### Title
Any unprivileged `runAction` caller can drain vault shares (or any owner-gated asset) left custodied by the shared `Emporium` contract from another user's CASE-2 stateless op - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable` is a single, protocol-wide singleton contract shared by all users for "Stateless Interaction" (CASE-2) ops [1](#0-0) . Its only integrity check after executing an arbitrary `op.endpoint.call(op.callData)` is a before/after balance diff over `circomData.erc20TokenAddresses`, an array fully chosen by whoever's `runAction` call is currently executing [2](#0-1) . If a victim's op mints an ERC4626-style share token to `address(this)` (i.e. to the Emporium contract) and that share token is never listed in `erc20TokenAddresses`, the resulting shares sit unaccounted for in Emporium's own persistent balance. Any later, completely unrelated attacker can submit their own `runAction` with an op that calls `vault.redeem(shares, attacker, Emporium)`; because the call originates from Emporium itself, `msg.sender == owner` is satisfied trivially inside the vault, and ERC4626's `redeem` pushes the underlying assets straight to `receiver=attacker`, bypassing Emporium's balance and therefore bypassing every Hinkal accounting check entirely.

### Finding Description
The broken equality: victim's zero-knowledge proof only authorizes "debit victim's shielded UTXO for `assets`, deposit `assets` into `vault`, credit Emporium (the shared contract) with `shares`" — it never authorizes any later transfer of those `shares` to anyone. Attacker's proof for their own `runAction` call only authorizes changes to *attacker's own* UTXOs/`erc20TokenAddresses` (which can be an empty or unrelated array). Yet the attacker's op is able to move value that was never part of either party's circuit-constrained balance change, because:

1. `EmporiumUpgradeable.runAction` executes CASE-2 ops via `op.endpoint.call{value: op.value}(op.callData)` with Emporium as the literal caller [1](#0-0) .
2. The only post-condition check is `balancesAfter[i] - balancesBefore[i]` for `i` in `circomData.erc20TokenAddresses`, an array the *current* caller fully controls [3](#0-2) ; `getBalancesForArray` only inspects addresses passed in [4](#0-3) .
3. Nothing ties a given `erc20TokenAddresses` entry, or the set of tokens an op can touch, to who originally caused Emporium to hold that balance — Emporium's token holdings (vault shares, stray ERC20/ETH, approvals) are global state persisting across transactions, not per-user.
4. `onlyAllowedRecipient` only checks that `msg.sender` calling `EmporiumUpgradeable.runAction` is the trusted `Hinkal.sol` forwarder [5](#0-4) ; it says nothing about whose funds `op.callData` may operate on.
5. `verifyWallet`/`usedMessages` only prevents signature/message replay for the *current* signer's own ops [6](#0-5) ; it does not constrain `op.endpoint`/`op.callData` targets to assets the signer legitimately owns.

Attacker's exact call: `Hinkal.transact(...)` → `_externalTransact` → `EmporiumUpgradeable.runAction` with an `EmporiumStack` whose CASE-2 op is `vault.redeem(shares, attacker, Emporium)`. Since the ERC4626 vault checks `msg.sender == owner` (satisfied because the call literally originates from the Emporium contract) and pushes assets directly to `receiver = attacker`, the theft completes entirely outside of any nullifier/root/amountChange checks that Hinkal performs on the attacker's own proof.

### Impact Explanation
Direct theft of another user's deposited/converted funds (now held as vault shares, or any other owner-gated balance, under the shared Emporium contract) by any unprivileged third party, with the loss credited straight to the attacker's wallet. This matches Critical severity — theft of shielded/in-flight user funds via a path the victim's proof never authorized. It is repeatable for every stray balance Emporium accumulates through CASE-2 ops interacting with any external protocol that gates withdrawal on `msg.sender` identity (ERC4626 vaults, lending-market `redeem`/`withdraw`, etc.) rather than tracking ownership through Hinkal's own UTXO/nullifier system.

### Likelihood Explanation
Preconditions are fully within the reach of an unprivileged actor: any user (including the victim, unknowingly) can trigger a CASE-2 op depositing into a vault with `receiver = address(this)` (Emporium), and the attacker only needs to know/observe Emporium's on-chain share-token balance (public) to craft a subsequent `runAction` redeeming those shares to themselves. No special role, allowance, or victim cooperation is required — the attacker only needs the ability to submit their own valid `transact`/`runAction` call, which every user has. This is broadly feasible whenever any DeFi integration is added to Emporium's CASE-2 flow without explicitly listing every token that flow can create/consume in `erc20TokenAddresses`.

### Recommendation
Do not let Emporium hold ownable/withdrawable balances (like ERC4626 shares) across transaction boundaries as a shared/pooled resource. Options: (a) require CASE-2 ops to fully settle/sweep any newly created token balances within the same transaction into `circomData.erc20TokenAddresses` so the balance-diff check captures and converts them to a UTXO for the depositing user only; (b) enforce that all owner-gated calls made from Emporium use a per-user proxy/wallet (the CASE-1 stateful path via `IHinkalWallet`) rather than the shared singleton, so `msg.sender`/`owner` in downstream protocols is scoped to one user; (c) require `circomData.erc20TokenAddresses` (and the balance-diff check) to include, or explicitly allow-list, every token type an external protocol's op could mint/transfer to Emporium, rejecting ops whose calldata targets tokens not declared.

### Proof of Concept
Hardhat test with a mock ERC4626 vault (`msg.sender == owner` gated `redeem`):
1. Deploy `Hinkal`, `EmporiumUpgradeable`, mock ERC20 underlying, mock ERC4626 vault.
2. Victim: `transact` → `runAction` with CASE-2 op `vault.deposit(assets, address(EmporiumUpgradeable))`; assert `vault.balanceOf(Emporium) == shares` and victim's UTXO commitment reflects `assets` debited with no returned UTXO for the share token (since it's absent from `erc20TokenAddresses`).
3. Attacker (no relation to victim, no shared keys): `transact` → `runAction` with CASE-2 op `vault.redeem(shares, attacker, Emporium)`, `erc20TokenAddresses` empty or unrelated.
4. Assert `underlying.balanceOf(attacker) == assets` (stolen) and `vault.balanceOf(Emporium) == 0`, while victim never authorized any withdrawal and their commitment/nullifier state shows no debit/credit for this step — proving the equality "shares belong to victim's deposit" vs "redemption proceeds credited to attacker" is broken with no guard preventing it.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
