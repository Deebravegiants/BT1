### Title
Permanent loss of burned funds on `HyperFungibleToken`/`WrappedHyperFungibleToken` when destination peer is not yet configured and `timeout = 0` is chosen - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and only afterwards dispatches an ISMP `POST` request. Delivery on the destination is gated by a per-chain owner-controlled allow-list (`_supportedChains` / `addChain`/`removeChain`); if the destination has not registered (or has removed) the peer for the request's source chain, `onAccept` reverts with `UnsupportedChain`/`UnauthorizedSource` and the burn can never be finalized. Because the protocol explicitly supports `timeout = 0` to mean "never expire," a sender who (or whose wallet/SDK default) picks `timeout = 0` has no recovery path at all if the destination peer is missing or misconfigured at delivery time — this is the exact "automatic deploy / peer-registration disabled → sender's already-locked funds are frozen" pattern from the SKALE finding.

### Finding Description
`send()` burns the caller's balance before the cross-chain message is guaranteed to be deliverable: [1](#0-0) 

On the destination, `onAccept` requires the source chain to be present in `_supportedChains` and the `from` address to match exactly, otherwise it reverts unconditionally, before any minting occurs: [2](#0-1) [3](#0-2) 

`_supportedChains` is populated/cleared exclusively by the owner via `addChain`/`removeChain` — this is the direct analog of SKALE's `automaticDeploy` flag: [4](#0-3) 

When `onAccept` reverts, `EvmHost.dispatchIncoming` does not revert the whole batch — it deletes the request receipt and silently returns, leaving the message theoretically "retryable": [5](#0-4) 

The only way to reclaim the burned tokens if delivery can never succeed (peer never added, or intentionally removed/misconfigured) is the timeout path, which mints the tokens back to the sender: [6](#0-5) 

However, the timeout path is only reachable when the request's `timeout()` has actually elapsed. The protocol explicitly documents `timeout = 0` as meaning the message **never expires**: [7](#0-6) [8](#0-7) 

`HandlerV2.handlePostRequestTimeouts` enforces `MessageNotTimedOut` unless `request.timeout() <= state.timestamp`, so a `timeout = 0` request can never satisfy this and the refund path is permanently unreachable: [9](#0-8) 

Putting this together: a user calls `send()` with `timeout = 0` (a documented, legitimate configuration for "no timeout") targeting a chain where the destination's `HyperFungibleToken`/`WrappedHyperFungibleToken` owner has not yet called `addChain` for the source (e.g., a newly-registered chain pair mid-rollout, an intentionally deferred peer, or a peer removed via `removeChain` for maintenance/incident response, exactly analogous to disabling `automaticDeploy` in the SKALE report). The tokens are already burned on the source. Delivery permanently fails with `UnsupportedChain`. Because `timeout = 0`, the `on_timeout`/`onPostRequestTimeout` refund can never be triggered. The burned tokens are permanently unrecoverable by any on-chain mechanism, identical in structure to the SKALE finding: source-side state change committed before destination-side authorization is confirmed, destination-side admin-controlled gate can reject delivery, and there is no way to force a refund once that gate is closed and the timeout safety valve is disabled.

The identical pattern exists in `WrappedHyperFungibleToken` (locks instead of burns) and the upgradeable variants, which share the same `_supportedChains`/`onAccept`/`timeout=0` structure: [10](#0-9) [11](#0-10) 

### Impact Explanation
This results in concrete, permanent freezing of user funds. Any user who burns/locks tokens via `send()` targeting a chain whose peer registration is missing, delayed, or removed, while using `timeout = 0`, loses access to those funds with no on-chain recovery mechanism — matching the "Medium" severity classification given to the original SKALE finding (config/admin-contingent but directly causing fund loss for ordinary, unprivileged users following documented usage patterns).

### Likelihood Explanation
`timeout = 0` is not a misuse — it is explicitly documented as a first-class, encouraged option ("or 0 for no timeout... Messages will never expire"). Peer registration via `addChain`/`removeChain` is routine chain-owner administration (initial rollout ordering, incident response, deprecations) and is not synchronized with in-flight user transactions, so a race between a user's `send()` and the destination owner's `addChain`/`removeChain` state is a realistic, unprivileged-triggerable scenario, not merely a deliberate-malicious-admin scenario (the freezing occurs even under benign/normal operational timing, e.g. a chain pair not yet fully configured on both ends before users can already dispatch).

### Recommendation
- Disallow `timeout = 0` (or any excessively long timeout) at the application layer (`HyperFungibleToken`/`WrappedHyperFungibleToken`/upgradeable variants) for `send()`, enforcing a bounded maximum timeout so every dispatched transfer has a deterministic timeout-based recovery path.
- Alternatively/additionally, require destination-chain peer configuration to be verified before allowing `send()` to a given `dest` with `timeout = 0` (e.g., an on-chain quorum/attestation of the destination's `_supportedChains` state, or simply forbid `timeout = 0` entirely for cross-chain token transfers regardless of destination).
- Consider adding a permissionless "force timeout" escape hatch independent of `timeoutTimestamp` for token-bridge apps specifically, so admin-side deregistration of a peer cannot indefinitely trap already-committed funds.

### Proof of Concept
1. Chain A and Chain B each deploy `HyperFungibleToken`. Chain A's owner calls `addChain` registering Chain B; Chain B's owner has **not yet** called `addChain` for Chain A (e.g., rollout not finished, or `removeChain` was called to pause the corridor).
2. Alice on Chain A calls `send({dest: ChainB, to: bob, amount: 100e18, timeout: 0, relayerFee: 0, data: ""})`. This burns Alice's 100 tokens immediately per `HyperFungibleToken.sol#L264-282`.
3. A relayer submits the proof to Chain B's `HandlerV2.handlePostRequests`, which calls `EvmHost.dispatchIncoming`, which calls `HyperFungibleToken(ChainB).onAccept(...)`.
4. `onAccept` reverts with `UnsupportedChain` because `_supportedChains[ChainA]` is empty on Chain B (`HyperFungibleToken.sol#L295-297`), matching test `testOnAcceptRevertsUnsupportedChain` (`evm/tests/foundry/HyperFungibleTokenTest.sol#L276-295`).
5. `EvmHost.dispatchIncoming` swallows the revert (deletes the receipt, returns without reverting the batch) — the message is never delivered, but also never explicitly fails at the protocol level.
6. Because `timeoutTimestamp == 0`, `HandlerV2.handlePostRequestTimeouts`'s check `request.timeout() > state.timestamp` can never be false, so `MessageNotTimedOut` always reverts — Alice can never submit a timeout proof to trigger `onPostRequestTimeout` and re-mint her 100 tokens.
7. Result: Alice's 100 tokens are permanently burned with no path to recovery unless Chain B's owner retroactively calls `addChain` for Chain A *and* a relayer resubmits the exact same proof before any other invalidation — a purely discretionary, out-of-band remedy outside the protocol's guarantees.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
