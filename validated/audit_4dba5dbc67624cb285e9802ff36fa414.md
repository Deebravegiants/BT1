### Title
Webhook shop-domain and topic headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop-domain`, `topic`, and `webhook-id` values that the handler subsequently trusts to identify the tenant and dispatch business logic are read from HTTP headers that are **not** included in the signed payload, breaking the intended binding `hmac == HMAC(secret, body + shop + topic)` down to just `hmac == HMAC(secret, body)`.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only [1](#0-0) , while `#shop` and `#topic` are pulled from the `X-Shopify-Shop-Domain` / `X-Shopify-Topic` headers without any signature coverage [5](#0-4) .

`Registry.process` verifies `Utils::HmacValidator.validate(request)` and, on success, immediately builds `WebhookMetadata` from `request.topic`, `request.shop`, and `request.webhook_id` and invokes the registered handler for that topic [3](#0-2) . Because the HMAC is computed only over the body, any request carrying a body+HMAC pair that is valid for *some* shop can be replayed with the `shop-domain` and/or `topic` headers rewritten, and the gem's own verification will still report success — the identity ("this event belongs to shop X, topic Y") is never cryptographically bound to the accepted signature.

A host application that installs a public app receives genuine webhook deliveries — with a fully valid `hmac-sha256` header — for its own store. Since the signature only commits to the JSON body, that exact `(raw_body, hmac)` pair remains valid regardless of which `shop-domain` or `topic` header accompanies it in a replayed POST to the app's public webhook endpoint. An unprivileged internet user who controls a shop can capture one of their own legitimate webhook deliveries and then send a forged HTTP request straight to the victim app's webhook endpoint with the same body/HMAC but an arbitrary `X-Shopify-Shop-Domain` (a victim tenant) and/or `X-Shopify-Topic` header. `Registry.process` will accept it as authentic and hand `data.shop == <victim shop>` to the handler.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is supposed to enforce and enables cross-tenant webhook injection: the app processes attacker-supplied body content as if it originated from, and pertains to, a different merchant's shop (or a different topic than actually signed), directly matching the Critical "cross-tenant access" impact category, since business logic keyed off `data.shop`/`data.topic` (order/customer updates, redaction handling, billing events, etc.) executes for the wrong tenant.

### Likelihood Explanation
Likelihood is high for any developer that installs the target app on a shop they control (trivial for public apps) and can therefore obtain at least one genuinely-signed webhook body/HMAC pair, then replay it against the app's public webhook endpoint with modified `shop-domain`/`topic` headers — no access token, `client_secret`, or privileged account is required.

### Recommendation
Include `shop`, `topic`, and (if relied upon) `webhook_id`/`api_version` in the signed material that `Utils::HmacValidator` checks, or otherwise cryptographically bind the header-derived identity fields to the verified body (e.g., require the host application to independently confirm `request.shop` against its own installed-shop registry before dispatch, and document this requirement clearly) so that `Registry.process` cannot be fed a validly-signed body under an attacker-chosen shop or topic.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST: body `B`, and headers including `X-Shopify-Hmac-Sha256: H` (valid because `H == HMAC(secret, B)`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker sends a new POST to the same app endpoint with identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — still equal to `H` since the body is unchanged — and returns `true` [7](#0-6) .
4. `Registry.process` proceeds to invoke the registered `orders/create` handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)` [8](#0-7) , causing the host application to process attacker-controlled data as though it were an authentic event for `victim-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
