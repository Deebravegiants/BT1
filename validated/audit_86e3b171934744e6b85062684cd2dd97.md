### Title
Webhook `shop` (tenant identity) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to app webhook handlers from the `X-Shopify-Shop-Domain` HTTP header, but `Utils::HmacValidator` only authenticates the raw request body, not this header. This breaks the equality the gem is supposed to guarantee: `hmac_verified_bytes == bytes_that_determine_tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes an HMAC over `request.to_signable_string`: [1](#0-0) 

That signable string is exclusively the raw request body: [2](#0-1) 

`HmacValidator.validate_signature` compares the received HMAC to the computed HMAC of only that string: [3](#0-2) 

Meanwhile, `request.shop` — the field the registry passes to the app's handler as the authoritative tenant identifier — is read straight from the `shop-domain` header, which is never included in the signed bytes: [4](#0-3) 

`Registry.process` then forwards this unauthenticated header value into `WebhookMetadata`, which the app's handler treats as the trusted shop for the event: [5](#0-4) 

The documented contract explicitly tells integrators that `data.shop` is "The shop domain of the webhook" and shows it being used directly to route/attribute work (e.g., `shop_domain: data.shop`) without any further verification, i.e., the gem presents this field as already-verified tenant identity: [6](#0-5) 

Because the HMAC only binds the body, any two requests with identical bodies but different `shop-domain` headers produce the same valid HMAC. An unprivileged internet user who has observed one legitimate webhook delivery (its body plus its valid HMAC — e.g., from a publicly-visible test/logging endpoint, a shared body across multiple merchants for the same event schema, or by triggering webhooks with a controlled shop where they know the exact resulting body) can replay it with an altered `X-Shopify-Shop-Domain` header pointed at a *different* victim shop. `HmacValidator.validate` still returns true because it never inspects the shop header, and the handler will process/attribute the event as belonging to the victim tenant — a violation of `hmac_verified_bytes == bytes_used_for_tenant_binding`.

### Impact Explanation
This is a cross-tenant boundary violation: the gem allows webhook payloads to be attributed to an arbitrary shop chosen by the request sender, independent of which shop the HMAC-signed body actually originated from. Any host application that follows the gem's documented usage (using `data.shop` as the tenant key to look up sessions/access tokens, enqueue per-shop jobs, or write per-shop records, exactly as shown in the gem's own docs) can be made to process or persist data under the wrong merchant's identity, or to invoke shop-scoped business logic (e.g., app-uninstalled/GDPR handlers, order/customer sync) for a shop that never actually sent that event. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires the attacker to possess a valid `(body, hmac)` pair — the HMAC itself still requires the shared secret to forge from scratch, so this is not a full unauthenticated bypass. However, once any such pair is observed (webhooks are delivered over plain HTTP endpoints that are often logged, proxied, or visible to multiple parties, and many webhook bodies for a given topic/schema are deterministic or attacker-shop-controlled), the shop header can be swapped freely with no additional secret knowledge, because the gem never binds it to the signature. This is a structural gap in the gem's verification logic rather than a purely theoretical concern.

### Recommendation
Include the `shop-domain` header (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed material for webhooks, or otherwise cryptographically bind the tenant identifier to the signed payload before exposing it via `WebhookMetadata`. At minimum, document clearly that `data.shop` is unauthenticated and must not be trusted for tenant attribution without independent verification (e.g., cross-checking against a known session for the topic).

### Proof of Concept
1. Attacker controls (or observes) a legitimate webhook delivery for `topic=orders/create` with body `B` and valid header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B`, the same valid `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of the original shop.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this succeeds since `B` and `H` are unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `request.shop` returns `victim-shop.myshopify.com` from the forged header (`lib/shopify_api/webhooks/request.rb:20-23`).
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and, following the documented pattern, processes/enqueues work attributed to the victim shop even though the victim shop never sent this event.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

  extend ShopifyAPI::Webhooks::WebhookHandler

      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)

end
