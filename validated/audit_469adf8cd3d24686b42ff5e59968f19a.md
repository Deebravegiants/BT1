### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC that is validated only signs the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are handed to the application's webhook handler unverified. This breaks the identity binding: `HMAC(body)` is verified, but `(shop, topic)` used by the handler is not bound to that HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the raw body) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` then trusts `request.topic` and `request.shop` — sourced from unauthenticated headers — to look up a handler and construct `WebhookMetadata` passed to the app's handler: [4](#0-3) 

Because only the body bytes are authenticated, any raw body + valid HMAC pair the attacker can obtain (e.g., by installing the app on their own shop and capturing one legitimate webhook delivery for any topic) can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to an arbitrary victim shop domain and/or the `x-shopify-topic` header changed to a different registered topic (as long as the JSON body still parses, since `parsed_body` merely calls `JSON.parse(@raw_body)` with no schema validation tied to topic). The HMAC will still validate because it only checks the body bytes, not the header values that determine which shop/topic the handler believes the event is for.

### Impact Explanation
This crosses a tenant/authentication boundary: an app's webhook handler acts on data attributing an event to `shop` X while the cryptographic proof (HMAC) does not bind that shop or topic at all. Depending on the handler's logic, this can cause cross-tenant actions — e.g., forging a `shop/redact` or `app/uninstalled` webhook for a victim shop, causing the app to delete/redact victim shop data, deactivate a victim's integration, or otherwise perform shop-scoped side effects triggered by attacker-controlled headers. This matches the "Critical - cross-tenant access" impact bucket since the binding broken is exactly `HMAC(body) verified ≠ (shop, topic) trusted-and-acted-upon`.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(raw_body, hmac)` pair signed with the app's real secret. This is realistically achievable by an unprivileged attacker who installs the gem-using app on their own free development/test shop (a normal, unprivileged action any internet user can take), then captures any webhook delivery Shopify sends to the app for that shop (the raw body + `x-shopify-hmac-sha256` header). The attacker then replays this exact body/HMAC pair against the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim's shop and/or the `x-shopify-topic` header for a different topic registered by the app. No access token, `client_secret`, or privileged account for the target shop is required — only a webhook capture from any shop the attacker controls.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, at minimum) in the HMAC-signable content, or otherwise cryptographically bind them to the payload before trusting them in `Registry.process`. Alternatively, validate that the shop encoded in the payload/topic is consistent with an expected, previously-registered shop/session before invoking the handler, and reject `shop`/`topic` values that are not derivable from the signed body.

### Proof of Concept
1. Attacker registers a free/dev shop `attacker.myshopify.com` and installs the target app, which registers webhook topic `T` (e.g. any topic the app handles).
2. Shopify sends a real webhook to the app's endpoint: body `B`, headers `x-shopify-topic: T`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
3. Attacker captures `(B, H)`.
4. Attacker sends a new HTTP POST to the same public webhook endpoint with body `B` unchanged, `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different registered `x-shopify-topic`).
5. `Utils::HmacValidator.validate` computes `HMAC(secret, B)` — matches `H` — validation passes.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to perform shop-scoped actions against the victim shop it never actually sent a webhook for. [4](#0-3) [5](#0-4)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
