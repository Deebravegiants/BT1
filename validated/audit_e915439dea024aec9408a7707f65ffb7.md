## Title
Uniswap fee-swap deadline hardcoded to `block.timestamp` enables sandwich-attack fund loss - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all perform an on-chain `swapETHForExactTokens` call to convert native tokens into the protocol fee token, but pass `block.timestamp` as the swap's `deadline` argument. The same pattern is repeated in `IntentGatewayV2.placeOrder` (both `evm/src/apps/IntentGatewayV2.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol`) when a user funds `order.fees` with native tokens. Passing `block.timestamp` as the deadline is equivalent to no deadline at all, because Uniswap's router check (`require(deadline >= block.timestamp)`) is evaluated in the same block the swap actually executes in, so it can never fail — this is exactly the anti-pattern described in the reference report.

### Finding Description
In `EvmHost.sol`, any unprivileged caller can invoke the payable `dispatch` functions or `fundRequest` and supply `msg.value`; the host swaps that ETH for the exact fee-token amount needed: [1](#0-0) [2](#0-1) [3](#0-2) 

The same construct also appears in the Intent Gateway's `placeOrder`, invoked by any user placing an order and paying `order.fees` in native token: [4](#0-3) [5](#0-4) 

Because `deadline == block.timestamp` at execution time, the deadline check inside the Uniswap router is always satisfied no matter how long the transaction has been pending in the mempool or how it was ordered by a block builder. A transaction that a user broadcast expecting prompt execution can instead be included much later — or deliberately delayed/reordered by a searcher/builder — after the WETH/fee-token pool price has moved. Since `swapETHForExactTokens` is called with the caller's full `msg.value` as the implicit input cap, a builder/MEV actor can sandwich the swap: pump the pool price with a front-run trade so the exact fee-token output now costs close to the caller's entire `msg.value`, shrinking (or eliminating) the ETH refund the caller expects to receive back, and back-run to capture that value. A properly bounded, caller-supplied deadline (and/or slippage bound) would not eliminate the sandwich entirely, but a deadline fixed to `block.timestamp` provides literally zero protection against the transaction being stale or maliciously delayed/reordered, which is precisely the vulnerability class cited in the reference report.

### Impact Explanation
Any user who dispatches a POST/GET request, funds a pending request, or places an Intent Gateway order using native token to cover fees is exposed to MEV sandwiching with no on-chain safeguard, resulting in loss of the excess ETH that should have been refunded. Because these entry points (`EvmHost.dispatch`, `EvmHost.fundRequest`, `IntentGatewayV2.placeOrder`) are core unprivileged, permissionless message-dispatch and order-placement paths, this affects every user who pays dispatch fees in native currency across all deployments using the Uniswap V2 fee-swap path. This is a direct value-extraction/theft vector against ordinary users, matching the "Medium" severity classification of the underlying bug class.

### Likelihood Explanation
Likelihood is significant: `dispatch`, `fundRequest`, and `placeOrder` are all frequently used, permissionless, payable entry points that any address can call with native token value, and no caller-supplied `deadline` parameter exists to opt out of the vulnerable path. Exploitation only requires an MEV-aware block builder/searcher monitoring the mempool or block-building process for these calls, which is a routine capability on the EVM chains Hyperbridge deploys to.

### Recommendation
Add a caller-supplied `deadline` parameter (or a small explicit buffer, e.g. `block.timestamp + X minutes`) that is genuinely bounded by the time the user intends the swap to remain valid, and thread it through `DispatchPost`, `DispatchGet`, `fundRequest`, and `Order`/`FillOptions`-style fee-funding calls instead of hardcoding `block.timestamp`. Additionally, consider allowing callers to specify a maximum acceptable ETH input (already partially bounded by `msg.value`, but currently with no minimum-output/price-staleness protection) so that a stale or reordered transaction reverts instead of executing at an attacker-favorable price.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` (or `fundRequest`/`IntentGatewayV2.placeOrder`) with `msg.value` generously funding the fee swap; the resulting swap call is `swapETHForExactTokens{value: msg.value}(fee, [WETH, feeToken], address(this), block.timestamp)`.
2. The transaction sits in the mempool (or is delayed by a builder) and is eventually included in a block whose base pool price has been pushed up by a front-run trade from the same builder/searcher.
3. Because `deadline` is stamped as `block.timestamp` of whichever block ultimately includes the transaction, the router's `deadline >= block.timestamp` check trivially passes regardless of the delay or reordering.
4. `swapETHForExactTokens` now consumes far more of the user's `msg.value` to obtain the same exact `fee` output, shrinking the ETH refund; the attacker back-runs to restore the pool price and captures the difference, resulting in silent value loss to the dispatching user with no revert and no on-chain indication anything went wrong.
