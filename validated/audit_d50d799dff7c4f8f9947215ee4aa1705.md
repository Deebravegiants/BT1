### Title
Webhook `shop` attribution is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop` (and `topic`) values are pulled directly from HTTP headers that are never covered by that signature. `Registry.process` validates the body HMAC and then hands the unauthenticated `shop` header straight to the app's webhook handler as the tenant identifier. This is the same "field acted on but not covered by the identity binding" defect class as the `recoverEther`/`currentWithheldETH` report: the binding the code *should* enforce (`hmac_signed_bytes == shop_attributed_to_this_request`) never actually happens.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e. the raw body) against the HMAC: [4](#0-3) 

`Registry.process` validates that body HMAC and then constructs `WebhookMetadata` — the object handed to the app's `handle` callback — using the unauthenticated `request.shop`: [5](#0-4) 

The documented contract explicitly tells app developers that `data.shop` in the handler is *the* shop domain of the webhook, to be used for tenant attribution (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [6](#0-5) 

Because Shopify signs webhook bodies with the app's single `api_secret_key` (shared across every shop/tenant that installs the app) and the signature never covers the shop header, any party who can obtain one legitimately-signed webhook body+HMAC pair (trivially available to any merchant that installs the app and receives their own real webhooks) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` will report success (it only checks the body bytes), and `Registry.process` will call the app's handler with `data.shop` set to the attacker-chosen shop domain instead of the domain that Shopify actually signed the webhook for.

Expressed as the identity-binding equality this class of bug is meant to preserve:
`hmac_verified_bytes == shop_the_handler_attributes_the_event_to`
Here the left side is `@raw_body` only, while the right side is a wholly separate, unauthenticated header value — the equality is never enforced.

### Impact Explanation
This breaks cross-tenant isolation (Critical, per rubric): an app that persists webhook data or performs shop-scoped side effects keyed off `WebhookMetadata#shop` (exactly as the gem's own documentation recommends: `shop_domain: data.shop`) can be made to attribute another merchant's legitimate webhook body to a different, attacker-chosen shop record, or vice versa — attaching one's own data to another tenant's account. Because the gem's public contract explicitly instructs consumers to trust `data.shop` as the authenticated shop for the request, and the gem itself is the component silently failing to bind it to the signed content, this is a defect in the gem, not a misuse of an undocumented API.

### Likelihood Explanation
Any of the app's own merchants (an "unprivileged" party relative to other tenants) already receives a real, validly-HMAC'd webhook body from Shopify for their own shop. Capturing that raw body + HMAC (e.g., from their own webhook receiver logs, or by triggering an event and observing the outgoing webhook) and replaying it to the app's public webhook endpoint with a forged `shopify-shop-domain` header requires no access to `api_secret_key`, no TLS interception, and no privileged account — only the ability to send an HTTP POST to the app's public webhook callback URL, which by design is a public, unauthenticated endpoint.

### Recommendation
Include the shop domain (and topic) in the HMAC-signed material that `to_signable_string` returns, or otherwise cryptographically bind the `shop` header to the verified body before it is trusted, e.g. by having `Registry.process` re-derive/verify `request.shop` against a known-good session/shop associated with the specific webhook subscription (via `webhook_id`) rather than trusting the header verbatim.

### Proof of Concept
```ruby
# Attacker (a legitimate merchant "shop-a.myshopify.com") first captures a genuine webhook
# delivered to their own endpoint, e.g.:
#   headers: {
#     "x-shopify-topic" => "orders/create",
#     "x-shopify-hmac-sha256" => "<valid-hmac-of-raw-body>",
#     "x-shopify-shop-domain" => "shop-a.myshopify.com"
#   }
#   raw_body: '{"id":123,"secret_note":"..."}'
#
# Attacker replays the identical raw_body + hmac to the SAME app endpoint, but with a
# forged shop header pointing at a victim tenant:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<same-valid-hmac-of-raw-body>", # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",     # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":123,"secret_note":"..."}', headers: headers)

# HMAC validation succeeds because it only checks the (unchanged) raw body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily invokes the app handler attributing the event to victim-shop:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
