### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC signature over the raw request body only, while the `shop` (and `topic`) values that are forwarded to the application's webhook handler come from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic tie to the HMAC: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` accepts the request once the body-only HMAC passes, then dispatches the handler using the *unauthenticated* `request.shop` value: [4](#0-3) 

The binding that should hold is: `shop attributed to a webhook == shop that Shopify actually generated the signed body for`. Because the header is excluded from the signed string, an attacker can break this equality: take any legitimately-signed `(raw_body, hmac)` pair — e.g. one delivered to a webhook endpoint for a shop the attacker legitimately controls (their own dev/test store) — and resubmit it to the app's webhook endpoint with the `shopify-shop-domain` header changed to point at a different (victim) shop. The HMAC check still passes because it only validates the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop: [5](#0-4) 

This is the exact class of bug described in the reference report: a field that is *acted upon* downstream (`bucketIndex`/`shop`) is not actually *covered* by the verification step that is supposed to bind it (`_indexOf` bounds check / HMAC signature), letting the check pass while the attacker-controlled value flows through unauthenticated.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (the value returned by `Registry.process`) to scope tenant data, authorize actions, or select which merchant's session/access token to use, can be tricked into processing attacker-supplied webhook events under a victim shop's identity. This is a cross-tenant access vector: an unprivileged party who can obtain even one legitimately HMAC-signed webhook body (e.g., from their own store, or any topic with a predictable/minimal body) can impersonate delivery from an arbitrary other shop domain, without possessing that shop's access token or the app's `client_secret`.

### Likelihood Explanation
Any internet user can freely POST to a public webhook endpoint. Obtaining at least one valid `(body, hmac)` pair only requires installing the app on a store they control (or using a webhook topic whose body content is static/predictable, e.g. `{}`), which is a normal, unprivileged action. No TLS interception, leaked secrets, or privileged account access is required — the header simply is not part of the trust boundary the gem sets up.

### Recommendation
Include the shop domain (and ideally the topic/webhook id) inside the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed body before it's trusted downstream. At minimum, `Registry.process`/`Request` should not surface `shop` as an authenticated field to handler code unless it has been bound to the signature; document clearly (or enforce) that consuming applications must independently verify the `shop` against their own registered-shop list rather than trusting the header value coming out of this gem.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers/receives a legitimate webhook delivery, capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256: H` (computed as `HMAC-SHA256(api_secret_key, B)`).
2. Attacker crafts a new POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, matches `H`, and returns `true`. [6](#0-5) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the payload was never issued for that shop, achieving cross-tenant impersonation.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
