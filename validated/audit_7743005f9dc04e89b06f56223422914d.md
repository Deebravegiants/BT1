## Analog Found: Global `challengePeriod` retroactively applied to already-committed state heights

### Title
Mutable global challenge period is applied retroactively to already-verified state commitments, enabling unexpected message freezing or premature acceptance - (File: `evm/src/core/EvmHost.sol`, `modules/ismp/core/src/handlers.rs`)

### Summary
The Lido report flags `Voting.sol.unsafelyChangeVoteTime()` for mutating a single shared `voteTime` variable that is then applied to all *existing* votes instead of being snapshotted per-vote, retroactively altering outcomes that were already in motion. Hyperbridge has the same bug-class in its challenge-period mechanism: the delay used to gate delivery of a request/response is read from a live, mutable, chain-wide (or per-state-machine) parameter at *verification* time, rather than being captured at the time the underlying state commitment was stored.

### Finding Description
On the EVM side, `updateHostParamsInternal()` lets `_hostParams.challengePeriod` be rewritten at any time via cross-chain governance: [1](#0-0) 

`HandlerV2.handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts` all compute the elapsed delay against the *current* value of `host.challengePeriod()`, not the value that was in effect when the referenced `StateCommitment` was stored: [2](#0-1) 

The same pattern exists on the substrate/pallet-ismp side: `verify_delay_passed` fetches `host.challenge_period(proof_height.id)` fresh on every call and compares it against `state_machine_update_time`, again with no snapshot of the challenge period that applied when the commitment for that height was first stored: [3](#0-2) 

Because the parameter is never pinned to the `StateCommitment`/`StateMachineHeight` record itself (unlike, e.g., `supportRequiredPct`/`minAcceptQuorumPct` being copied into the `Vote` struct in the referenced report's recommendation), any later update to the challenge period changes the effective rules for state commitments that were already stored and were already being relied upon by relayers to deliver pending requests/responses/timeouts.

### Impact Explanation
If the challenge period is increased, state commitments that had already satisfied the old (shorter) delay — and on which relayers were about to deliver already-dispatched requests/responses/timeouts — instantly stop satisfying the new, longer delay. Every `handlePostRequests`, `handleGetResponses`, `handlePostRequestTimeouts`, and `handleGetRequestTimeouts` call against that height now reverts with `ChallengePeriodNotElapsed` until the new delay elapses, freezing in-flight message delivery (and any escrowed funds/fees gated on delivery, e.g. `IntentGatewayV2` fills or ISMP request relayer fees) for an unbounded extra duration relative to what was guaranteed at dispatch time. Conversely, decreasing the value shortens the effective security delay for state commitments that were stored under the assumption of a longer delay, weakening the fraud-proof/fisherman window relied upon by dependent applications. This falls squarely under "a route unable to deliver messages" and can also degrade the security guarantee (challenge period) that underpins state-commitment finality for already-stored heights.

### Likelihood Explanation
No malicious actor is required to trigger it — this is a routine parameter tuning operation (raising/lowering `challengePeriod` for operational or security reasons) which is expected to happen over the protocol's lifetime, exactly analogous to the referenced report's scenario where legitimate use of `unsafelyChangeVoteTime()` unexpectedly perturbs already-running votes. Any relayer or application with a request/response/timeout pending against a height committed under the old delay is affected the moment governance publishes an update.

### Recommendation
Snapshot the challenge period into the `StateCommitment`/`StateMachineHeight` (or an auxiliary mapping keyed by height) at the time the commitment is stored, and have `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts` (EVM) and `verify_delay_passed` (pallet-ismp) read that stored value instead of the live `challengePeriod()`/`challenge_period()` getter. This mirrors the report's recommendation to persist `voteTime` inside the `Vote` struct rather than reading a mutable, shared variable at evaluation time.

### Proof of Concept
1. Governance (via `HostManager`) calls `updateHostParams` on `EvmHost`, increasing `challengePeriod` from `X` to `X + 7 days`.
2. A `StateCommitment` for height `H` was stored `X + 1 hour` ago (already satisfying the *old* delay), and a relayer holds a valid `PostRequestMessage` proof against height `H`.
3. Before the update, `handlePostRequests` would have succeeded (`delay > challengePeriod`).
4. After the update, the same call to `handlePostRequests` reverts with `ChallengePeriodNotElapsed` for up to `X + 7 days - 1 hour`, even though the underlying consensus/state proof and its original elapsed-delay guarantee are unchanged — see the check at: [4](#0-3)

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
