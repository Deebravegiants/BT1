### Title
Missing Chainlink circuit-breaker (min/max) price validation in `SimplexPaymaster._getOraclePrice` allows draining the paymaster with a de-pegged/crashed token - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` only rejects a non-positive or stale Chainlink answer; it never checks whether the returned answer is pinned at the aggregator's `minAnswer`/`maxAnswer` circuit-breaker bound. Since this price feeds directly into the gas-fee token pricing that any ERC-4337 UserOp sender can trigger, a crashed/de-pegged registered token whose feed hits its floor lets an attacker pay for gas with worthless tokens at the frozen, stale price, draining the paymaster's EntryPoint deposit/stake.

### Finding Description
`_getOraclePrice` is the sole gate on Chainlink data used throughout the contract: [1](#0-0) 

It checks only `answer <= 0` and staleness via `updatedAt`; there is no comparison against the aggregator's documented `minAnswer`/`maxAnswer` circuit-breaker bounds. Chainlink aggregators clamp `answer` to these bounds during extreme price moves (the exact "Venus/LUNA" scenario cited in the report), so a de-pegged or crashed asset keeps reporting the floor price indefinitely instead of reverting or reflecting the true market price.

This price is consumed by `_tokenPrice`, which every UserOp using this paymaster passes through during `_fetchDetails` (called from `_validatePaymasterUserOp`) to compute how much ERC-20 token the sender is charged for gas: [2](#0-1) [3](#0-2) 

`_fetchDetails`/`_prefund` are reached by any unprivileged account that submits a UserOp naming a registered token in `paymasterData` (mode `0x00` permit or `0x02` Permit2) — no governance or admin gating is involved in this call path: [4](#0-3) 

The same unguarded price is also used to size the treasury's `swapAndDeposit` (though that entry point is treasury-gated): [5](#0-4) 

### Impact Explanation
If a registered token's Chainlink feed enters its circuit-breaker floor (e.g., a stablecoin de-pegs to a fraction of a cent but the aggregator's `minAnswer` is ~$0.99), `_getOraclePrice` keeps returning the pinned floor price. `_tokenPrice` then continues pricing gas as if the token is still worth close to $1. An attacker can acquire the crashed token for a fraction of a cent on the open market and repeatedly submit self-relayed UserOps that pay for gas in that token at the inflated, frozen oracle price. The paymaster pays out real native gas (via `entryPoint().depositTo`/stake funded by the treasury) while receiving essentially worthless tokens, resulting in a direct drain/theft of the paymaster's funded EntryPoint deposit and stake — concrete theft of funds reachable from a single unprivileged UserOp.

### Likelihood Explanation
Any account can construct and submit an ERC-4337 UserOp naming a registered token; no privileged role is needed to trigger `_fetchDetails`/`_prefund`. The only precondition is that one of the governance-registered tokens experiences a de-peg/crash severe enough to hit its feed's circuit-breaker bound — a realistic and historically observed event for stablecoins and volatile assets (as referenced by the Venus/LUNA precedent). Once that happens, exploitation requires no special access and can be repeated at scale until the paymaster's funds are exhausted or the token is deactivated by governance.

### Recommendation
In `_getOraclePrice`, fetch and cache each oracle's `minAnswer`/`maxAnswer` (or configure them per token during `_registerToken`/`_setParams`) and revert when `answer` is at or beyond those bounds, e.g.:
```solidity
if (answer <= minPrice || answer >= maxPrice) revert InvalidOraclePrice(address(oracle), answer);
```
Alternatively, cross-check the primary feed against a secondary source (e.g., a Uniswap TWAP) and revert or deactivate the token when the two diverge beyond a configured tolerance, mirroring the existing Uniswap `checkPriceGuard`/`maxDeviationBps` pattern already used elsewhere in this codebase for pool pricing.

### Proof of Concept
1. Governance registers `TokenX` with a Chainlink token/USD feed whose `minAnswer` floor is `0.99e8` (typical ~1% deviation band around $1), via `_registerToken`.
2. `TokenX` de-pegs on secondary markets to `$0.01` (e.g., a stablecoin collapse). The Chainlink aggregator's circuit breaker clamps `latestRoundData().answer` to `minAnswer = 0.99e8` and keeps returning it.
3. Attacker buys a large amount of `TokenX` cheaply (~$0.01/unit) on the open market.
4. Attacker submits UserOps through `SimplexPaymaster` (mode `0x00` or `0x02`) naming `TokenX`. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(cfg.tokenOracle, ...)` returns the frozen `~$0.99` price, so `tokenPrice` is computed as if `TokenX` is still worth close to $1.
5. The paymaster charges the attacker `TokenX` at the inflated price while paying real gas cost out of its EntryPoint deposit/stake (funded by treasury).
6. Attacker repeats across many UserOps, converting near-worthless `TokenX` into real native-asset value drained from the paymaster.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
