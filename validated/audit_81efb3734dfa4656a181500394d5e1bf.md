This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC over the body and then trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Title
Webhook tenant/topic identity (`shop`, `topic`, `webhook_id`) not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body [4](#0-3) . However, the `shop`, `topic`, `webhook_id`, and `api_version` values used afterward to identify the tenant and dispatch to a handler are all pulled from HTTP headers that are never part of the signed payload [5](#0-4) . This breaks the equality the HMAC is supposed to guarantee: `bytes_verified (raw_body) == bytes_acted_on (raw_body + shop + topic + webhook_id)` does not hold, since only `raw_body` is verified while `shop`/`topic`/`webhook_id` are trusted unverified.

### Finding Description
The Shopify webhook signature scheme is meant to prove that a request originated from Shopify for a specific shop/topic. In this gem, `Request#hmac` decodes the `X-Shopify-Hmac-Sha256` header and `Request#to_signable_string` returns `@raw_body` only [5](#0-4) . `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, raw_body)` and compares it to the received value using `OpenSSL.secure_compare` [6](#0-5) . Since the `client_secret` is a single per-app secret shared across all shops that install the app, any tenant that has installed the app can obtain a genuinely-signed `(raw_body, hmac)` pair for their own account (e.g. by triggering `orders/create` in their own store).

An attacker who controls one installed tenant can then replay that valid `(raw_body, hmac)` pair to the app's public webhook callback endpoint while substituting the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers with values belonging to a victim shop/topic. `Registry.process` will still find `Utils::HmacValidator.validate(request)` to be `true` (it only checks the body), then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` from the forged headers and dispatches it to the topic's handler as if it were a legitimate event for the victim shop [3](#0-2) . Per the documented handler contract, apps are expected to trust `data.shop` and `data.topic` to route persistence/business logic (e.g., `shop_domain: data.shop`) [7](#0-6) .

### Impact Explanation
This is a cross-tenant integrity issue: an unprivileged internet user who is a legitimate tenant of the multi-tenant app (i.e., has installed it on their own store, an "unprivileged" position relative to other merchants) can forge webhook events attributed to a different shop by reusing a validly-signed body with swapped identity headers, since those headers are not covered by the signature. This lets the attacker inject fabricated data (topic/body of their choosing) that the host application will process as if it originated from the victim shop, satisfying the "cross-tenant access" impact criterion, because the shop binding that the recipient of the access token/session relies on is not authenticated.

### Likelihood Explanation
Exploitation requires only: (1) being an installed tenant of the target app (any merchant can install a public app, no elevated privilege needed), and (2) the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers, both trivially available to any internet user interacting with the app normally. No access to `client_secret`, access tokens, or any privileged credential is required — the attacker only ever needs a valid HMAC for *their own* traffic.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` values into the signed payload verification, not just the raw body. Concretely, `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not be the sole point of trust for `shop`/`topic`; `Registry.process` should cross-check the header-derived `shop` against an application-level expectation (e.g., verify the `shop` belongs to a shop with an active/registered webhook for that specific `webhook_id`/topic combination) rather than propagating raw header values as trusted identity to the handler. At minimum, document prominently that `data.shop`/`data.topic` are unauthenticated header values not covered by HMAC, and that host apps must independently confirm the shop is one that installed the app before trusting webhook payload contents for that shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the genuine request: raw body `B`, headers including `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `client_secret`), `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`, `shopify-webhook-id: W1`.
2. Attacker resends this exact request to the app's webhook callback endpoint, keeping body `B` and `hmac` header `H` unchanged, but overwriting `shopify-shop-domain` to `victim-shop.myshopify.com` (and/or `shopify-webhook-id`/`shopify-topic` to a value of interest).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` = `B` only and finds it matches `H` [6](#0-5) ; validation passes despite the forged shop header.
4. The registered handler for the topic is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, exactly as it would be for a genuine Shopify-originated event for that victim [3](#0-2) .
