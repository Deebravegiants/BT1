### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook impersonation - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by validating an HMAC that covers only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by the app are taken from unauthenticated HTTP headers. Any party who can obtain one genuine (body, HMAC) pair signed with the app's shared secret — trivially available to any merchant who installs the app on their own store — can replay that body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop. `Registry.process` accepts the forged request as valid and dispatches it to the handler tagged with the attacker-chosen shop, breaking the binding between "shop verified by the HMAC" and "shop the handler acts on."

### Finding Description
The HMAC validation is generic and delegated to `Utils::HmacValidator.validate`, which calls `verifiable_query.to_signable_string` to get the bytes that were signed: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never included in that signed string: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC (body-only) and then trusts `request.shop` (a header, entirely outside the signed scope) to build the `WebhookMetadata` passed to the app's handler: [5](#0-4) 

This is the same root-cause pattern as the reported analog bug class: a value that is acted upon (`shop`) is not covered by the cryptographic check (`hmac` over `raw_body` only) that is supposed to authenticate the whole request. The equality that should hold is:

`shop verified by HMAC == shop the handler acts on`

but in reality:

`shop the handler acts on = unauthenticated header value`, independent of the HMAC-covered `raw_body`.

### Impact Explanation
An attacker who installs the app on their own (attacker-controlled) shop receives genuine webhook deliveries from Shopify, each with a valid `X-Shopify-Hmac-Sha256` computed with the app's `client_secret` over the raw body. Because the HMAC never binds the body to the shop domain, the attacker can replay that exact body+HMAC pair to the app's public webhook endpoint while changing only the `X-Shopify-Shop-Domain` header to name a victim shop. `Registry.process` will accept it as authentic (HMAC over body checks out) and invoke the registered handler with `shop: <victim>`. Any app logic that uses `WebhookMetadata#shop` as a tenant key (e.g., to look up/update a per-shop record, to act using a stored session for that shop, or to trigger shop-scoped side effects) will act cross-tenant on the attacker's chosen victim shop identity — an unprivileged internet user (any merchant who can install the app) crossing a tenant boundary they should not be able to cross. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that is installable by arbitrary third-party merchants (the common case for public Shopify apps using this gem): installing the app is unprivileged and gives the attacker a legitimate signed body/HMAC pair for at least the mandatory webhook topics (`shop/redact`, `customers/redact`, `customers/data_request`) and any topic registered by the app. No access token, `client_secret`, or privileged account is required — only normal app installation, which is standard unprivileged merchant behavior.

### Recommendation
Bind the tenant identity to the authenticated payload instead of trusting an unauthenticated header:
- Include the shop domain (and ideally topic) inside the HMAC-signed material, or cross-check `request.shop` against a shop domain embedded/verified elsewhere in the authenticated request (e.g., derived from the body itself, or from a per-shop webhook secret rather than the single app-wide `client_secret`).
- At minimum, document/enforce that `WebhookMetadata#shop` must not be treated as a trusted tenant identifier unless the deployment also validates request provenance out-of-band (e.g., Shopify's source IP ranges), and add a check that rejects a request whose header-derived `shop` cannot be correlated with any HMAC-covered data.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a webhook topic (or receives a mandatory topic delivery).
2. Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: <topic>`, and `X-Shopify-Hmac-Sha256: <valid HMAC over raw body>`.
3. Attacker captures `raw_body` and the valid HMAC, then re-sends an HTTP request to the same endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `raw_body`, unaffected by the header change (`lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though Shopify never sent a webhook for that shop — demonstrating the cross-tenant identity break.
