### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the webhook HMAC only to the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant are read directly from unauthenticated HTTP headers. This breaks the intended identity equality `shop_that_produced_the_HMAC == shop_used_to_process_the_webhook`, mirroring the report's bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is signed. The `shop` accessor, however, is taken straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only the body-vs-HMAC relationship, then dispatches the handler using the unauthenticated `shop` header as the tenant identifier: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is the app's single shared `client_secret`, not a per-shop secret, any merchant who has *legitimately installed the app on their own store* can trigger a real webhook event (e.g., `orders/create`) and receive an authentic `(raw_body, hmac)` pair signed with that shared key. That merchant can then replay the exact same body and HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will succeed (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the attacker-controlled body to the handler tagged with the victim's shop, since `WebhookMetadata.shop` is populated purely from the spoofed header: [4](#0-3) 

Any host application that trusts `WebhookMetadata#shop` (as the library's own docs instruct: "handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))") to scope persisted data to a tenant will write or act on attacker-supplied data under the wrong shop — a cross-tenant data-injection primitive rooted entirely in this gem's `Request`/`Registry` implementation, not in host-app misuse.

### Impact Explanation
This breaks tenant isolation (cross-tenant access) without needing the app's `client_secret`, an access token, or any privileged credential — only a normal, unprivileged installation of the app on an attacker-controlled store, which is available to any internet user who can install the app. Per the provided impact matrix, cross-tenant access is Critical.

### Likelihood Explanation
Requires the attacker to be able to install (or already have installed) the target app on any Shopify store they control and to be able to POST directly to the app's public webhook endpoint with custom headers — both of which are readily available to any unprivileged internet user, no interception or secret leakage needed.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the signed payload used for HMAC verification, or otherwise cryptographically tie the header-derived shop to the specific installation the raw body was generated for (e.g., verify the shop against a known, previously-stored value for the given webhook subscription/id, or use per-shop signing where supported) rather than trusting the raw header once the generic body HMAC passes.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com`, triggering a real webhook (`orders/create`). Shopify sends `raw_body` and header `x-shopify-hmac-sha256: H`, computed with the app's shared `client_secret`.
2. Attacker intercepts (via their own server) or replays that exact `raw_body` and `H` directly to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)`, which passes because it validates only `raw_body` against `H`.
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: attacker_controlled_body, ...)`, causing the host application to process attacker-supplied data as if it originated from the victim's shop.
