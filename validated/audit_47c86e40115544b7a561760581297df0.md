## Title
Webhook `shop` identity is not covered by the HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop` value used to attribute the webhook to a tenant is read straight from an HTTP header that is never part of the signed content. Because the HMAC secret (`api_secret_key`) is identical for every shop that installs the same app, a party that legitimately receives one authentic webhook for their own shop can capture the (body, HMAC) pair and replay it to the app's webhook endpoint with a forged `shop-domain` header claiming to be a different, victim shop. `ShopifyAPI::Webhooks::Registry.process` only checks the HMAC and then hands `request.shop` straight to the app's handler, so the forged tenant identity is accepted as authentic.

## Finding Description
The identity binding that should hold is:
`hmac_valid(body, api_secret_key) == true` should imply `shop == the-shop-that-actually-sent-this-body`.

In practice the gem only proves the first half. `Request#hmac` and `#to_signable_string` are: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; the `shop` accessor (line 20-23) simply reads the `shopify-shop-domain`/`x-shopify-shop-domain` header verbatim, and that header is never mixed into the signed string. `Utils::HmacValidator.validate` re-derives the signature purely from `to_signable_string`: [3](#0-2) 

`Registry.process` performs exactly this check and then forwards the unauthenticated `request.shop` to the app's handler as the tenant identifier: [4](#0-3) 

Since `api_secret_key` is the app's single client secret (shared by every shop that installs the app), any two shops that use the same app produce webhooks whose HMAC is computed with the same key. An attacker who installs the app on their own shop (or otherwise legitimately receives one authentic webhook, e.g. `orders/create` with `{}`-like body) obtains a valid `(raw_body, hmac)` pair. Because `shop` is outside the signed content, the attacker can resend that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` reporting the victim's shop — a value the gem never authenticated.

## Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce for multi-tenant apps: an unprivileged user of an app (any merchant who installs it) can cause the host application to process an app-defined webhook body as if it originated from a different, victim merchant, since the only integrity check the gem performs (`HmacValidator.validate`) does not bind `shop` to the signed bytes. Any application logic keyed off `WebhookMetadata#shop` (the gem's own documented output) — e.g. upserting per-shop records, triggering shop-scoped side effects, or resetting shop-scoped state — can be forced to act under another tenant's identity. This matches the Critical bar for cross-tenant access.

## Likelihood Explanation
Exploitation requires only: (1) the attacker holds/installs the app on any shop (or otherwise gets one real webhook payload for a body they control/predict), and (2) the app's webhook endpoint is internet-reachable, which is inherent to Shopify's push-webhook model. No access token, `client_secret`, or privileged account is needed — the attacker only reuses a body/HMAC pair they were legitimately sent. This is fully reachable through the gem's documented `Registry.process`/`WebhookMetadata` flow, not a misuse of the API.

## Recommendation
Bind the shop identity into what is cryptographically verified: either include the `shop-domain` header in the signable content the way it is compared against the per-app secret, or require callers to additionally validate `request.shop` against the list of shops that have completed OAuth for this app/session store before trusting it as a tenant key. At minimum, document that `request.shop` is unauthenticated and must be cross-checked by the host application against a known-installed-shops list before being used as a data-partition key.

## Proof of Concept
1. App `A` is installed on both `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`; both installs share the same `Context.api_secret_key`.
2. Shopify sends `attacker-shop` a webhook: body `{"id":1}`... with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`. The attacker captures the raw body and HMAC.
3. Attacker sends a POST to the app's webhook endpoint with the identical body and HMAC, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only checks `to_signable_string` (the raw body), per `lib/shopify_api/webhooks/request.rb` lines 35-38 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: {"id":1}, ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the app to process attacker-controlled data under the victim shop's identity.
