### Title
Zero-valued `virtualLtReserve` zeroes `Pair.k()` and lets the entire curve supply be bought for free — (File: `packages/contracts/src/Bonding.sol`, `packages/contracts/src/Router.sol`, `packages/contracts/src/Pair.sol`)

### Summary
`Bonding._deployAndSeed` derives the launch-time virtual LT reserve as `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate()` and only guards the *upper* bound of this value (reverting when it is too large). If the paired LT's `exchangeRate()` is large enough that this division rounds down to `0`, `Pair.mint` is called with `assetReserve = 0`, which sets `_pool.k = tokenReserve * 0 = 0`. With `k == 0`, `Router._computeBuy`'s overflow-cap arithmetic degenerates such that the very first buy on the curve computes `amountInUsed = 0` while still returning the entire real curve supply (`curveSupply`, 750M tokens) as `tokensOut` — i.e. an attacker (or even an honest buyer) can drain the whole bonding curve of its launched tokens for a real LT cost of zero.

### Finding Description
`_deployAndSeed` computes: [1](#0-0) 

The only sanity check is `if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();`, which protects against `exchangeRate()` being too *small* (causing `virtualLtReserve` to overflow uint112 headroom). There is no check that `virtualLtReserve != 0`, which happens whenever `exchangeRate() > VIRTUAL_LIQUIDITY_USD * 1e18` — entirely plausible for a BounceTech LT that has appreciated significantly over time via leverage, exactly the kind of external, unprivileged, live-priced reserve asset this protocol is built around.

This value is passed straight into `Router.addInitialLiquidity` → `Pair.mint`, which sets: [2](#0-1) 

With `assetReserve == 0`, `_pool.k = tokenReserve * 0 = 0` permanently (K is set once and never touched by `swap`, per the protocol's own documented `Pair.k()` identity used elsewhere in `_launchTimeVirtualLtReserve`).

Now the first buy hits `Router._computeBuy`: [3](#0-2) 

With `k == 0`: `tokensOut = reserveToken - (0 / newReserveAsset) = reserveToken` (the full virtual `totalSupply`), which is `> realBalance` (the real 750M `curveSupply` actually transferred to the pair), so the overflow-cap branch fires: `cappedReserveToken = reserveToken - tokensOut = totalSupply - curveSupply = LP_RESERVE (250M)`, and `cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken = (0 + 250M - 1) / 250M = 0` (integer floor division). Therefore `amountInUsed = cappedReserveAsset - reserveAsset = 0 - 0 = 0`.

`Router.buy` then only pulls `amountInUsed = 0` LT from the buyer via `safeTransferFrom`, but transfers the full capped `tokensOut = realBalance` (the entire 750M-token curve supply) to the buyer: [4](#0-3) 

Because `Zap.buy`'s overflow-refund logic returns any LT minted but not consumed (`ltMinted - amountInUsed`) straight back to the buyer as LT, and `amountInUsed == 0`, the buyer effectively keeps their entire LT and receives the whole curve's real token supply for free.

### Impact Explanation
This is a direct, unbounded theft of the entire launched-token curve supply (750M real tokens, `curveSupply`) for zero real LT cost, the moment the pair is created with a degenerate zero virtual reserve. It also permanently corrupts `Pair.k() == 0` for that token, which is relied upon elsewhere (`_launchTimeVirtualLtReserve`, `canGraduate`, `_prepareGraduationLiquidity`) to recover the "real LT raised," further corrupting graduation accounting for that token. This satisfies the accepted impact class of "unbacked token ... payouts" and outright theft of curve-held token supply.

### Likelihood Explanation
Reachable purely via `Zap.createToken` (an unprivileged token-creator action explicitly in scope) paired against any allow-listed LT whose live `exchangeRate()` happens to exceed `VIRTUAL_LIQUIDITY_USD * 1e18`. Since `exchangeRate()` is an external, ever-appreciating, leverage-driven value with no upper-bound enforcement in `_deployAndSeed` (only a lower-bound-on-exchangeRate check exists, guarding the opposite failure mode), any sufficiently mature/appreciated leveraged LT reaching this threshold makes every *new* token launched against it instantly exploitable by the first buyer. This requires no admin privilege, no LT-internals bug, and no malicious validator — only normal LT price appreciation over time plus a single `createToken` + `buy` call sequence from an unrelated wallet.

### Recommendation
Add an explicit lower-bound check in `_deployAndSeed` immediately after computing `virtualLtReserve`:
```solidity
if (virtualLtReserve == 0) revert ExchangeRateTooHigh();
```
mirroring the existing upper-bound `ExchangeRateTooLow()` guard, so `Pair.mint` can never be called with a zero `assetReserve`/zero `k`.

### Proof of Concept
1. Identify (or wait for) a BounceTech LT `L` whose `exchangeRate()` has appreciated such that `exchangeRate() > VIRTUAL_LIQUIDITY_USD * 1e18`.
2. Call `Zap.createToken` (any unprivileged creator) to launch a new `Token` paired with `L`. `_deployAndSeed` computes `virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate() == 0`, and `Pair.mint(totalSupply, 0)` sets `k = 0`.
3. As any unprivileged trader, call `Zap.buy(tokenAddress, minimalUsdcAmount, 0, referrer)`. Trace through `Bonding.buy` → `Router.buy` → `_computeBuy`: `tokensOut` caps to `realBalance` (750M tokens) while `amountInUsed` computes to `0` due to the `k == 0` degenerate division.
4. `Zap.buy` transfers the full `tokensOut` (750M tokens) to the trader and refunds essentially all minted LT back to them (since `amountInUsed == 0`), realizing the entire curve supply for free. [5](#0-4) [6](#0-5) [7](#0-6)

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
