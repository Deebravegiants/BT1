## Title
Webhook shop/topic/webhook-id spoofing via HMAC that only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the unsigned `shop-domain`, `topic`, `webhook-id`, and `api-version` headers when building the `WebhookMetadata` passed to the app's handler. Because those headers are not part of the signed material, any unprivileged actor who can obtain one valid `(body, hmac)` pair from Shopify (e.g. by triggering a webhook on their own store) can replay that exact body/HMAC to a victim app's webhook endpoint while freely rewriting the `shop-domain` (and `topic`/`webhook-id`) headers, causing the app to process forged, cross-tenant webhook data as if it legitimately originated from a different shop.

### Finding Description
`Registry.process` performs authentication like this: [1](#0-0) 

The HMAC check itself calls `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — none of the identifying headers are included: [3](#0-2) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers and forwarded unchanged into the metadata object the host app's handler consumes: [4](#0-3) [5](#0-4) 

The identity binding this breaks is: **`hmac(signed material)` should equal `hmac(shop, topic, webhook_id, body)`**, but in fact `hmac` only equals `hmac(body)`. The `shop` value acted upon by the handler is not covered by the signature that "authenticates" the request.

The gem's own documentation tells integrators that calling `Registry.process` "will verify the request did indeed come from Shopify" and explicitly instructs handlers to key business logic off `data.shop`: [6](#0-5) [7](#0-6) 

So this is not "the host app ignoring documented behavior" — the gem documents `shop` as trustworthy output of a verified request, when it is not actually bound by the signature.

### Impact Explanation
Any internet user who is a merchant/developer for *some* Shopify store (trivial to obtain — free dev stores are available) can capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from a real webhook Shopify sends them (the HMAC secret is the app's `client_secret`, shared across all shops installing that app, so a valid signature obtained from any tenant is valid for all tenants of that app). They can then POST that identical body+HMAC to the target app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain (and/or the `X-Shopify-Topic` header for a more sensitive topic whose payload shape happens to match). `HmacValidator.validate` still succeeds because only the body is signed, and the app's handler executes business logic attributing the (attacker-supplied) payload to the victim shop. Depending on how the host app uses `data.shop` (queueing jobs, updating per-shop state, looking up sessions/access tokens keyed by shop), this enables cross-tenant data injection/corruption — satisfying the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
Exploitation requires no credentials belonging to the victim, no access to `api_secret_key`, and no privileged account — only the ability to receive one real webhook from Shopify for any shop where the same app is installed (including the attacker's own store) and the ability to POST to the target app's public webhook endpoint. This is squarely within reach of an "unprivileged internet user."

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verifiable material for webhook requests, or otherwise cryptographically bind `shop` to the payload before trusting it (e.g., independently verify the shop against a known/registered installation record rather than trusting the header). At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should not treat headers used for authorization decisions as out-of-band from the HMAC it validates.

### Proof of Concept
1. Install the target app; also install it (or use it) on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook topic on `attacker.myshopify.com` whose payload is empty/benign, e.g. `{}`. Capture the request: `raw_body = "{}"`, `X-Shopify-Hmac-Sha256: <valid hmac of "{}">`.
3. Replay to the target app's webhook endpoint:
```
POST /callback/orders/create HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <captured hmac of "{}">
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: forged-id

{}
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `"{}"` only and matches — validation passes.
5. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {}, ...)`, even though Shopify never sent any such event for `victim-shop`. [1](#0-0) [8](#0-7)

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
