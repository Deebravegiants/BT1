### Title
Webhook shop identity spoofing - HMAC only binds the request body, not the `shop-domain` header used for tenant routing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , and `HmacValidator.validate` verifies the HMAC exclusively against that signable string [2](#0-1) . The `shop` value that `Registry.process` hands to the host application's handler, however, comes from the `shopify-shop-domain` header, which is never part of the signed material [3](#0-2) .

### Finding Description
`Registry.process` performs exactly one integrity check before dispatching a webhook to the app's handler: `Utils::HmacValidator.validate(request)` [4](#0-3) . That validation only proves that `raw_body` was signed with `api_secret_key` — it says nothing about the `topic`, `shop-domain`, `webhook-id`, or `api-version` headers, because `to_signable_string` is defined as `@raw_body` alone:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

Immediately after the HMAC check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated header value `request.shop`, and passes it to the app-supplied handler:

```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

The equality this code implicitly assumes is:
`hmac_valid(raw_body) == true` ⟹ `shop header == the shop that generated raw_body`

That equality does not hold. Because the header is excluded from the signed string, anyone who can reach the app's webhook endpoint (this is a public HTTP endpoint by design) and who possesses **any** previously-valid `(raw_body, hmac)` pair — e.g. captured from their own shop's legitimate webhook delivery, which any merchant/developer can trivially obtain by installing the app on a store they control — can resend that exact body/HMAC pair while substituting an arbitrary value in the `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `HmacValidator.validate` still returns `true` because it never looks at that header, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the forged shop as the event source.

This is precisely the analog class called out in the rules: "a field acted on but not covered by the HMAC." The `shop` field is acted upon (used for tenant identification/session lookup by the host app) but is not bound by the cryptographic check that is supposed to authenticate the whole request.

### Impact Explanation
Host applications built on this gem are documented and expected to key their per-shop session/data lookups off `WebhookMetadata#shop` (see the handler examples in `test/webhooks/registry_test.rb`, which assert on `data.shop`) [6](#0-5) . Because the gem gives the illusion that a passed `HmacValidator.validate` check authenticates the entire webhook (topic + shop + body) it does not — this enables cross-tenant confusion: a caller can make the app believe an event body belongs to shop B when it was really generated for shop A. Depending on how the host app uses this shop value (e.g., writing attacker-supplied JSON body content into shop B's records, or triggering redaction/data-request flows keyed by `shop/redact` and `customers/redact`/`customers/data_request` — the three `MANDATORY_TOPICS` [7](#0-6) ), this is a cross-tenant integrity/data-confusion vector that arises purely from a gap in this gem's own verification logic, not from any assumption the host app should have caught since the gem hides this by presenting `HmacValidator.validate` as sufficient authentication.

### Likelihood Explanation
Exploitability requires only network access to the app's public webhook endpoint plus one legitimately observed `(body, hmac)` pair, which is easy to obtain (install the app on any shop, even a free/dev shop, and capture the delivered webhook). No access to `api_secret_key`, access tokens, or any other privileged credential is required — only the ability to observe one's own webhook traffic and then modify unsigned headers on a replayed request.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material used by `to_signable_string`, or otherwise cryptographically bind the shop-domain header to the payload before trusting it (e.g., look up the expected shop for a given webhook-id via an authenticated API call, or require host applications to cross-check `shop` against known installed shops). At minimum, document prominently that `HmacValidator.validate` does not authenticate anything beyond the raw body, so host apps do not treat `WebhookMetadata#shop` as trustworthy without additional verification.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (any real, even trial, Shopify store the attacker controls).
2. Trigger a webhook (e.g., `orders/create`) and capture the raw HTTP request: headers including `x-shopify-hmac-sha256: <hmac>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, plus the raw JSON body.
3. Resend the exact same body and the exact same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` still succeeds because it only hashes `@raw_body`, which is unchanged; `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, matching the code path at `lib/shopify_api/webhooks/registry.rb:190-199`.
5. The host application's handler now processes attacker-controlled body content under `victim-shop.myshopify.com`'s identity.
