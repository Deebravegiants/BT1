### Title
Webhook `shop` domain is not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, but the HMAC is computed only over the raw request body [1](#0-0) . The `shop` (and `topic`, `webhook_id`, `api_version`) fields that are handed to the app's webhook handler are read directly from unauthenticated HTTP headers and never enter the signable string [2](#0-1) .

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, which for a webhook `Request` is just `@raw_body` [3](#0-2) [1](#0-0) . The `shop` value comes from the `x-shopify-shop-domain`/`shopify-shop-domain` header via `shopify_header("shop-domain")` [4](#0-3) , which is not part of the signed bytes at all.

`Registry.process` only checks the body HMAC, then immediately constructs `WebhookMetadata` using `request.shop` (and `request.topic`, `request.webhook_id`) straight from headers and passes it to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [5](#0-4) . This breaks the identity binding: `HMAC-verified bytes == raw_body` but `shop identity attributed to the event == header value`, i.e. `bytes_verified != bytes_used_for_tenant_attribution`.

Because the app's `client_secret`/`api_secret_key` is fixed per app and shared across every merchant that installs it (not per-shop), an attacker who legitimately installs the app on their own store (or otherwise obtains one authentic `(raw_body, hmac)` pair for any shop) can capture a real, correctly-signed webhook request and then replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC check still passes (it only re-verifies the body against the same shared secret), and `Registry.process` will invoke the handler believing the event originated from the victim shop, per the documented `data.shop` contract used by consuming apps to route/scope processing (e.g. `shop_domain: data.shop` in the gem's own webhook doc example) [6](#0-5) .

### Impact Explanation
This yields cross-tenant data confusion: a handler that trusts `data.shop`/`data.topic` to select which merchant's records to update (the pattern the gem's own documentation recommends) can be tricked into applying attacker-controlled, but validly-signed, webhook content under a different (victim) shop's identity. This matches the "Critical — cross-tenant access" impact class, since the shop-identity boundary that the HMAC is supposed to protect is not actually bound by it.

### Likelihood Explanation
Requires the attacker to possess one authentic `(body, hmac)` pair, obtainable by installing the app themselves (a normal, low-privilege action any merchant can take) or by intercepting one legitimate webhook delivery. No knowledge of `api_secret_key` is needed — only a header rewrite on replay. Whether this is practically exploitable depends on whether a given handler implementation actually uses `data.shop`/`data.topic` for per-tenant trust decisions without independent verification (e.g., matching against the topic-specific expected schema or session lookup) — the gem itself provides no protection against this and its own documentation encourages using `data.shop` directly.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable representation (or otherwise cryptographically bind them, e.g. requiring apps to cross-check `data.shop` against an active, previously-established session for that shop before trusting the payload), rather than relying solely on the raw body signature while sourcing tenant-identifying fields from unauthenticated headers.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's shared `client_secret`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic: orders/create`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `HmacValidator.validate` recomputes HMAC over `B` only and matches `H` [7](#0-6) [3](#0-2) .
4. `Registry.process` accepts the request and calls the handler with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's own store [5](#0-4) .
