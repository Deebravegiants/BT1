### Title
Unbounded numeric string parsing in `@exodus/currency`/`@exodus/bigint` reachable via untrusted dApp `eth_sendTransaction` params enables verifier-side DoS - (File: `libraries/currency/src/number-unit-utils.js`, `libraries/bigint/src/native-bigint.js`)

### Summary
`stringToNumberFraction`/`createNumber` in `libraries/currency/src/number-unit-utils.js` and `Wrapper.wrap` in `libraries/bigint/src/native-bigint.js` convert caller-supplied decimal/hex strings into native `BigInt` via `BigInt(numberLike)`/`BigInt('0x' + numberLike)` with no length or canonicalization bound before parsing. These functions back `NumberUnit` construction (e.g. `ethereum.wei(value)`), which is used to interpret amount/gas fields (`value`, `gasPrice`, `gas`) supplied by an untrusted web page through the injected `window.exodus.ethereum.request({ method: 'eth_sendTransaction', params: [...] })` RPC bridge documented in `docs/web3-providers/ethereum-provider-api.md`.

### Finding Description
`Wrapper.wrap` performs unchecked, proportional-cost big-integer parsing: [1](#0-0) 

`stringToNumberFraction` in the currency library accepts arbitrary numeric strings (decimal or `0x`-prefixed hex) and, for hex, immediately calls `BigIntWrapper.wrap(num, 16)`: [2](#0-1) 

and `createNumber` funnels any string into `stringToNumberFraction` then `BigIntWrapper.wrap`: [3](#0-2) 

There is no upper bound on string length, and no rejection of unreasonably large numeric literals (e.g. a `value`/`gasPrice`/`gas` field containing a hex or decimal string with millions of digits) before the expensive `BigInt(...)` conversion runs. This mirrors the reported gnark issue: unbounded numeric string input is handed directly to a big-integer parser without a pre-check.

The exposed, unprivileged-attacker-reachable surface is the injected Ethereum provider RPC bridge that any web page can call: [4](#0-3) 

Transaction fields such as `value`, `gasPrice`, and `gas` in this call are exactly the kind of numeric strings that flow into `NumberUnit`/`BigIntWrapper` parsing when the wallet processes the transaction request (fee estimation, display formatting, amount conversion), since `NumberUnit.create`/unit constructors (e.g. `ethereum.wei(...)`) route through `createNumber`.

### Impact Explanation
A malicious or compromised web page connected to the wallet via the standard dApp provider bridge can submit an `eth_sendTransaction` (or similar) request with an oversized numeric string in `value`, `gasPrice`, or `gas`. Because parsing cost in `BigInt()` grows with input size, this can induce significant CPU/memory consumption in the wallet's background/extension process while it processes the pending request (before any signing confirmation), degrading availability of the wallet UI/background process for the user session. This is a denial-of-service concern on the RPC bridge trust boundary between untrusted web content and the wallet, not a signing bypass or fund-loss issue.

### Likelihood Explanation
Likelihood is moderate: any web page can invoke `window.exodus.ethereum.request(...)` without prior user interaction to submit a crafted transaction request; no permission is required merely to submit a request to be parsed. However, actual severity depends on whether numeric fields are parsed via this code path before user confirmation and on any implicit string-length practical limits imposed elsewhere (e.g. JSON transport limits), which were not verified in this pass.

### Recommendation
- In `Wrapper.wrap` (`libraries/bigint/src/native-bigint.js`) and `stringToNumberFraction`/`createNumber` (`libraries/currency/src/number-unit-utils.js`), enforce a hard maximum input length for numeric strings (decimal and hex) before calling `BigInt(...)`, sized to the largest legitimate on-chain numeric value (e.g. 256-bit integers require at most ~78 decimal digits or 64 hex digits).
- Reject strings exceeding this bound immediately with a descriptive error rather than attempting to parse them.
- Apply the same bound check at the dApp/RPC ingestion boundary (wherever `eth_sendTransaction`/similar params are first received from `window.exodus.ethereum.request`) so oversized fields are rejected before reaching `NumberUnit` construction.

export function createNumber(num, power) {
  if (num.isBigIntWrapper?.()) {
    return num
  }

  if (isMaybeBN(num) && power > 0) {
    // throwing error because this convo truncated zeros incorrectly.
    throw new Error(
      `You are creating a NU providing a BN.js number ${num} with a power of ${power}. Please use base units, string or decimal numbers!`
    )
  }

  if (typeof num === 'bigint' && power > 0) {
    // this convo is controversial for some devs. Better not to use it.
    deprecationWarning(
      `You are creating a NU providing a bigint number ${num} with a power of ${power}. Please use base unit, string or decimal numbers!`
    )
  }

  if (BigIntWrapper.isUnderlyingInstance(num)) {
    const wrapped = BigIntWrapper.wrap(num)
    return power
      ? wrapped.mutateMul(BigIntWrapper.wrap(10).pow(BigIntWrapper.wrap(power)))
      : wrapped
  }

  const value = stringToNumberFraction(num, power, { numberOnly: true })
  return BigIntWrapper.wrap(value)
}
