## Title
Unbounded Gas Consumption via Return-Data Bomb in `EvmHost` Message Dispatch - (File: `evm/src/core/EvmHost.sol`)

## Summary
`EvmHost.dispatchIncoming`, `dispatchIncoming(GetResponse ...)`, and `dispatchTimeOut` invoke destination `IApp` callbacks with a bare low-level `.call(...)`, discarding the return value with `(bool success,)`. Solidity's high-level `.call()` wrapper always copies the *entire* returndata buffer into memory before the tuple is destructured, regardless of whether the caller uses it. This is exactly the bug class in CVE-2022-35915 (`ERC165Checker`): an external, attacker-reachable target can return an arbitrarily large payload and force the caller to pay unbounded, quadratic memory-expansion gas for a call that is "generally assumed to be bounded."

## Finding Description
`dispatchIncoming` resolves the destination application from attacker-controlled request data and calls it with no return-data limiting: [1](#0-0) 

The same unbounded-copy pattern repeats for GET responses and timeouts: [2](#0-1) [3](#0-2) 

Crucially, `request.to` (the destination module address) is fully attacker-controlled: any unprivileged sender on the source chain can dispatch a `PostRequest` whose `to` field points at a contract they deployed themselves on the destination chain. A relayer then submits these requests in a batch via `HandlerV2.handlePostRequests`, which loops over `requestsLen` calling `host.dispatchIncoming` for each request within a single transaction: [4](#0-3) 

Since `.call()` implicitly performs a full `returndatacopy` into memory as part of assigning the tuple result, a malicious "destination module" whose fallback returns a huge buffer forces the *caller* (the relayer's batched delivery transaction) to pay the memory-expansion cost of copying that data — even though the result is immediately discarded. This mirrors the root cause described in the OpenZeppelin `ERC165Checker` advisory, where an `staticcall`'s return value was blindly assumed to be cheap.

## Impact Explanation
Because `handlePostRequests`/`handleGetResponses` process many leaves in one transaction, a single malicious request embedded in a batch can consume gas disproportionate to its own message size, exhausting the transaction's gas budget and reverting the whole batch. This drops delivery of every other legitimate, unrelated message bundled in the same transaction, wasting relayer gas and fees, and can be used to repeatedly grief specific routes/relayers — matching the "route unable to deliver messages" impact category. Because a failed `dispatchIncoming` call only deletes the `_requestReceipts` entry (allowing retry) rather than permanently failing, an attacker can requeue the same poison-pill request cheaply to repeatedly disrupt batches that include it.

## Likelihood Explanation
No privileged role is required: deploying a destination contract with an oversized-return fallback and dispatching a `PostRequest` to it are both permissionless, single-transaction actions available to any user of the bridge (an "unprivileged message dispatcher"). Relayers batch multiple pending requests for gas efficiency, so the probability that a malicious request ends up bundled with legitimate ones is realistic in normal relayer operation.

## Recommendation
Replace the unbounded `.call(...)` pattern in `dispatchIncoming`, the `GetResponse`/`GetRequestTimeout` dispatch functions, and any other call into untrusted `IApp` targets with a call that caps the copied return data (e.g., an "excessively safe call" pattern using inline assembly with an explicit zero/limited output size), so the copy cost is bounded independent of what the destination returns. Consider also capping the gas forwarded to each individual `onAccept`/`onGetResponse`/`onGetTimeout` invocation so no single destination can starve the rest of a batched delivery transaction.

## Proof of Concept
1. On the destination chain, deploy:
```solidity
contract GasBomb {
    fallback() external payable {
        assembly { return(0, 2000000) } // large arbitrary length
    }
}
```
2. On the source chain, dispatch a `PostRequest` (via any `HyperApp`/`EvmHost.dispatch`) with `to = address(GasBomb)`.
3. A relayer collects this request along with several legitimate pending requests and calls `HandlerV2.handlePostRequests`, which loops through the leaves and calls `host.dispatchIncoming` for each [4](#0-3) .
4. When `dispatchIncoming` reaches the `GasBomb` leaf, `.call(...)` triggers the fallback, which returns a huge buffer; Solidity copies it into memory for the discarded `(bool success,)` assignment [5](#0-4) , consuming gas disproportionate to the call and potentially exhausting the batch transaction's gas limit, reverting delivery of all other bundled messages.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
