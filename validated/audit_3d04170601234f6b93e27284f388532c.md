### Title
Webhook tenant attribution (`shop` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, excluding the `shopify-shop-domain` (and `topic`, `webhook-id`, `api-version`) headers from the HMAC-covered material, while `ShopifyAPI::Webhooks::Registry.process` still uses `request.shop` as the authoritative tenant identity handed to the application handler after the HMAC check succeeds.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
It returns only `@raw_body`. The `shop` accessor, however, is read straight from an attacker-controllable HTTP header: [2](#0-1) 

`Registry.process` validates the HMAC over the signable string (i.e., only the body) and then, on success, immediately builds `WebhookMetadata` using `request.shop` — a value that was never part of what the HMAC authenticated: [3](#0-2) 

The binding that should hold is: `hmac_verified_payload == (body, shop, topic, webhook_id)`, i.e., every field the application acts on should be covered by the signature that authenticates the request came from Shopify for that specific shop. What is actually enforced is only `hmac_verified_payload == body`; the `shop` (and `topic`/`webhook_id`/`api_version`) fields are parsed but never verified. This is the same bug class as the referenced report: a field the code trusts and acts on (tenant attribution) is decoupled from the field actually covered by the cryptographic check (only the body).

`HmacValidator.validate` itself simply HMACs `verifiable_query.to_signable_string`, which for webhooks is only the body, confirming the shop header is outside the MAC: [4](#0-3) 

### Impact Explanation
An attacker who has legitimate access to their own shop (any developer can install a public/free app on a test store) can capture a valid `(raw_body, hmac)` pair for a real webhook Shopify sent for their own shop. They can then replay that exact body+hmac to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and topic/webhook-id) with a victim shop's domain. The HMAC check in `Registry.process` still passes because it only covers the body, but the handler receives `WebhookMetadata` attributing the (attacker-controlled) payload to the victim shop. In a multi-tenant app that uses `data.shop` to select which merchant's session/state to update (e.g., processing an "app/uninstalled" or data payload against the wrong tenant's records), this results in cross-tenant data corruption/confusion driven entirely through this gem's trusted metadata contract, which meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must first obtain one genuine `(body, hmac)` pair, which is achievable simply by installing the app on any shop they control and receiving a real webhook (webhooks are delivered to a fixed, often shared, path per app configuration, and the endpoint has no other authentication). Because Shopify's own webhook HMAC scheme by design signs only the body, this is a systemic characteristic of the delivery mechanism that this gem's `Registry.process`/`WebhookMetadata` construction does not compensate for by re-binding the header-derived `shop` to anything cryptographically verified.

### Recommendation
Do not treat `request.shop`, `request.topic`, or `request.webhook_id` as trusted/verified fields based solely on `HmacValidator.validate(request)` succeeding. At minimum, document clearly that these header values are unauthenticated, and/or extend the signable string / verification step used before calling handlers to additionally bind the `shop`, `topic`, and `webhook_id` values (e.g., by requiring the consuming application to cross-check `request.shop` against an expected, session-derived shop before trusting the payload), rather than allowing `Registry.process` to hand off header-derived tenant identity as if it were verified.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they control) and triggers a real webhook delivery, capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` value Shopify computed for it.
2. Attacker sends a POST to the app's webhook endpoint (the same endpoint wired to `ShopifyAPI::Webhooks::Registry.process`) using the captured `raw_body` and `hmac`, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
3. `HmacValidator.validate` recomputes the HMAC over `raw_body` only (per `to_signable_string`) and it matches, so `Registry.process` proceeds.
4. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, i.e., the attacker-controlled body is now attributed to the victim shop inside the gem's own trusted metadata object, despite `shop` never having been covered by the signature.
