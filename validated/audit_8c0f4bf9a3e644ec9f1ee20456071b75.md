### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Signature, Allowing Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` authenticates the *body* against the app's single, shop-independent `Context.api_secret_key`, but never binds that signature to the `shop-domain` header. The `shop` value that `Registry.process` passes into `WebhookMetadata` (and therefore to the host application's webhook handler) is read straight from an unauthenticated header field.

### Finding Description
The identity binding that should hold is: `hmac_signature == HMAC(secret, raw_body + shop)`, i.e. the verified bytes should equal the bytes that determine which tenant (`shop`) the event is attributed to. Instead, the gem verifies only `hmac_signature == HMAC(secret, raw_body)` and separately trusts `request.shop`, which is parsed directly from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header with no cryptographic tie to the signature: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC and then forwards the unauthenticated `request.shop` value directly to the handler: [3](#0-2) 

The HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every merchant shop that installs the app — it is not per-shop. Any merchant that installs the app is an unprivileged party with respect to every other merchant's data, yet they legitimately receive webhook deliveries whose bodies are validly HMAC-signed with that same shared secret. Because the `shop-domain` header is excluded from `to_signable_string`, a merchant can take one of their own genuinely-signed webhook deliveries (valid `hmac-sha256` header for that body) and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only recomputes the signature over `raw_body`, and `Registry.process` will then hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled `body`/`topic` content, which the host application will process as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant isolation the HMAC signature is supposed to provide: verified bytes (raw body signed by the app secret) do not equal the bytes the host application uses to select the tenant context (`shop` header). An unprivileged shop owner can cause the host app to process forged/replayed webhook events attributed to a different shop, i.e., cross-tenant access/data confusion without needing that victim's credentials, access token, or `client_secret`.

### Likelihood Explanation
Any merchant who installs the app can capture one legitimate, validly-signed webhook for their own shop (e.g., by inspecting their own endpoint logs) and replay it with a modified `shop-domain` header. No secret, access token, or privileged access is required beyond normal app installation, which any user can do.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside `to_signable_string`, or otherwise cryptographically bind the `shop-domain` header to the HMAC before trusting `request.shop` in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that host applications must independently verify the incoming `shop` against their own known/installed shop list rather than the gem implicitly treating the header as trusted.

### Proof of Concept
1. App has two installed shops, `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both configured with the same `api_secret_key`.
2. Attacker's shop receives a genuine webhook, e.g., topic `app/uninstalled`, with body `{"id":1}` and header `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`.
3. Attacker resends the same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body`.
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the handler processes the forged event as if it came from the victim shop.
