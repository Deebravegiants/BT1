### Title
Unvalidated `txMeta.keyId` override lets a signing request bypass the caller-declared `walletAccount`/`baseAssetName` scope - (File: `features/tx-signer/src/module/seed-signer.ts`)

### Summary
`SeedBasedTransactionSigner.signTransaction` derives the signing key from `walletAccount`/`baseAssetName` by default, but if the caller-supplied `unsignedTx.txMeta.keyId` is present, it is used verbatim to build the `KeyIdentifier` used for signing, with only structural validation (`KeyIdentifier.validate`) and no check that the `keyId` is actually associated with, or permitted for, the declared `walletAccount`/`baseAssetName`.

### Finding Description
Analogous to the CodedEstate `rental_type` bug — where a discriminator field (`rental_type`) existed in the data model but was never enforced by the functions operating on it, letting a short-term rental be manipulated through a long-term-rental function and pay out in the wrong denomination — `seed-signer.ts` has a similar unenforced discriminator: whether the transaction should be signed with the account's default derived key, or with a caller-supplied override key (`txMeta.keyId`). [1](#0-0) 

```js
signTransaction = async (opts) => {
  const { baseAssetName, unsignedTx, walletAccount } = opts
  ...
  const keyId = unsignedTx.txMeta?.keyId
  ...
  if (!keyId) {
    const signer = await this.#getSignerForWalletAccount({ walletAccount, baseAsset })
    return signTx({ unsignedTx, signer })
  }

  // Sometimes we need a different keyId than the default.
  // One example is signing an EOS tx with the Ethereum key, another is ripple
  assert(KeyIdentifier.validate(keyId), `txMeta.keyId must be a key identifier object`)

  const signer = await this.#getSignerForKeyId({ seedId: walletAccount.seedId, keyId })
  return signTx({ unsignedTx, signer })
}
```

`KeyIdentifier.validate` only confirms the object is a well-formed `KeyIdentifier` (has a supported `derivationAlgorithm`, `keyType`, valid `derivationPath` string), not that it is scoped to the `walletAccount` or `baseAssetName` for which the caller is requesting a signature. [2](#0-1) 

The intended legitimate use of this override is narrow (e.g. signing an EOS tx with an Ethereum-derived key) per the code comment, but the check does not enforce that narrowness — any syntactically valid `KeyIdentifier` (any `derivationPath`, any `assetName`) can be substituted, exactly as the CodedEstate contract allowed any rental-cancellation function to act on any rental regardless of its `rental_type`.

### Impact Explanation
If `unsignedTx.txMeta` (or an equivalent RPC-facing signing request) is attacker/dApp-influenced without the caller enforcing that `keyId` matches the intended `walletAccount`/asset, a request nominally scoped to sign a transaction for one asset/account could be redirected to sign with a key derived along a different, attacker-chosen derivation path under the same seed. Because `#getSignerForKeyId` only anchors on `seedId` (not on `baseAssetName`/`accountIndex` consistency), this bypasses the intended per-asset/per-account signing scope, which is the kind of unauthorized-signing outcome analogous to the original report's "steal funds via mismatched type" pattern.

### Likelihood Explanation
Reachability depends on whether the caller of `signTransaction` (UI, RPC bridge, or web3 provider path) blindly forwards a `txMeta.keyId` value that could be influenced by an untrusted origin/dApp rather than being generated purely internally by asset code. I could not confirm from the indexed files whether any RPC/dApp-facing entry point actually lets an external caller set `txMeta.keyId` directly — the only concrete internal legitimate uses referenced (EOS/Ripple fallback-claim) are asset-internal. This is the main uncertainty: without confirming an untrusted-input path into `txMeta.keyId`, likelihood is moderate/unconfirmed rather than proven.

### Recommendation
Enforce that any `txMeta.keyId` override is consistent with the declared `walletAccount`/`baseAssetName` (e.g., restrict allowed `assetName`/derivation prefixes to an explicit allow-list per asset, or verify `keyId.derivationPath` starts with `walletAccount`'s account-index/coin-type as derived from `baseAsset.api.getKeyIdentifier`), rather than accepting any structurally-valid `KeyIdentifier`.

### Proof of Concept
Not independently verified end-to-end (no confirmed untrusted-input entry point into `txMeta.keyId` was found in the indexed code); the mechanism itself (bypassing default per-account key derivation via a caller-supplied `keyId` validated only for shape, not scope) is demonstrated directly in `seed-signer.ts` lines 136-151 shown above — supplying `unsignedTx.txMeta.keyId` as a `KeyIdentifier` for an arbitrary `derivationPath`/`assetName` under the same seed causes `#getSignerForKeyId` to sign with that key instead of the key implied by `walletAccount`/`baseAssetName`.
