In `modules/consensus/grandpa/primitives/src/justification.rs`, `GrandpaJustification::verify_with_voter_set` calls `.expect(...)` on the result of `.min_by_key(...)` over `self.commit.precommits`, on the theory that "commit has been validated above; valid commits must include precommits." This mirrors the BIND CVE-2017-3138 bug class exactly: an unprivileged, permissionless input (a submitted consensus/finality proof) reaches a code path guarded by an *assumption* rather than an explicit check, and if that assumption is wrong the process panics/aborts rather than returning a typed error — a REQUIRE-style assertion failure triggerable by a relayer.

### Title
Unvalidated assumption that `finality_grandpa::validate_commit` rejects empty-precommit commits lets a relayer panic the GRANDPA consensus-client via `.expect()` in `verify_with_voter_set` - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`GrandpaJustification::verify_with_voter_set` (`modules/consensus/grandpa/primitives/src/justification.rs:66-107`) computes the ancestry base hash via `self.commit.precommits.iter().min_by_key(...).map(...).expect("can only fail if precommits is empty; commit has been validated above; ...")`. The comment records an assumption — that `finality_grandpa::validate_commit` will never return `is_valid()` for a commit with zero precommits — rather than an enforced invariant. This is the same bug class as CVE-2017-3138: a permissionless, network-facing message-processing path assumes a well-formed structure and panics instead of failing gracefully when that assumption doesn't hold.

### Finding Description
`GrandpaJustification` is decoded straight from attacker/relayer-controlled bytes (SCALE-decoded consensus proof payload dispatched via `pallet_ismp::Call::handle_unsigned`/`handle`, ultimately reaching `ismp-grandpa`'s client wrapper which calls `verify`/`verify_with_voter_set`). `verify_with_voter_set` first calls `finality_grandpa::validate_commit(&self.commit, voters, &ancestry_chain)` and only proceeds past that call if `result.is_valid()`. The code then assumes that a "valid" commit necessarily has a non-empty `precommits` vector, and unwraps the `min_by_key` over `precommits` with `.expect(...)`.

This mirrors exactly the pattern already flagged and fixed elsewhere in this same file/module family: `modules/consensus/grandpa/verifier/src/error.rs:50-58` documents a prior case where the verifier `.expect()`'d a header lookup and panicked, subsequently converted to a typed `RelayHeaderNotInUnknownHeaders` error; `modules/consensus/sync-committee/verifier/src/lib.rs:184-192` similarly hardened a `calculate_multi_merkle_root` panic risk with an explicit length check; `modules/trees/ethereum/src/node_codec.rs:79-84` and `modules/consensus/pharos/primitives/src/spv.rs` (nibble_at_depth, MAX_PROOF_DEPTH) both document identical "attacker-controlled proof caused an index-out-of-bounds panic in on-chain execution" regressions that were fixed to return `Err` instead. The `min_by_key(...).expect(...)` in `justification.rs` is the one remaining unconverted instance of this exact pattern in the GRANDPA verification path: it depends entirely on the correctness of an external crate's (`finality_grandpa`) validation semantics for an empty-precommit set, which is not verified anywhere in this codebase, and if `validate_commit` ever treats an empty-precommit commit as valid (e.g. vacuously — zero threshold-of-zero voters reached, or a future/alternate `VoterSet`/threshold configuration), the `.expect()` fires and panics the process handling the message.

### Impact Explanation
A panic inside consensus-proof verification that runs on unsigned/permissionless dispatch (`pallet_ismp::handle_unsigned`, executed by the runtime's `validate_unsigned`/`execute` path) crashes the collator/validator node processing that block — a runtime panic during block execution is a liveness/DoS failure of the state machine client, taking down the coprocessor's consensus updates for the affected chain and halting message delivery through that route until patched. This satisfies the "route unable to deliver messages" acceptance criterion in the Validate rules.

### Likelihood Explanation
Reachability requires only that `finality_grandpa::validate_commit` return `Verdict`/`is_valid() == true` for a `Commit` whose `precommits` is empty for some VoterSet/threshold configuration Hyperbridge feeds it (e.g., a `VoterSet` with total weight/threshold of 0, or any edge case in the external crate's vacuous-truth handling for empty inputs) — this is a crate-boundary assumption the Hyperbridge code does not independently verify or test against. Given that this exact assumption class (relying on an implicit invariant from upstream logic instead of checking it locally) has already caused three separate documented panics in sibling consensus verifiers in this very codebase (GRANDPA's own `RelayHeaderNotInUnknownHeaders`, sync-committee's multiproof length, and the Ethereum trie codec's HP-prefix and depth checks), the likelihood that this specific unguarded `.expect()` is also exploitable is non-trivial, though I could not fully confirm from the index alone whether `finality_grandpa::validate_commit` guarantees a non-empty `precommits` for every `is_valid()` result across all versions/configurations used — that would require running the external crate against a crafted empty-precommit `Commit` and inspecting its actual validation semantics, which requires deeper testing/build access than available here.

### Recommendation
Replace the `.expect(...)` with a checked path: after `validate_commit` succeeds, explicitly verify `!self.commit.precommits.is_empty()` and return a typed error (consistent with the rest of the module, e.g. an `anyhow!("empty precommits in otherwise-valid commit")` or a new `Error` variant) before calling `min_by_key`. This removes reliance on an unverified upstream invariant and matches the hardening already applied to the other panic sites in this codebase.

### Proof of Concept
Not independently reproducible from the available index/tools: exploiting this requires constructing (or finding) a `Commit` with `precommits: vec![]` that `finality_grandpa::validate_commit` accepts as valid under the `VoterSet`/threshold Hyperbridge constructs, then submitting it as a GRANDPA `ConsensusMessage` via `handle_unsigned`. Confirming whether such a `Commit` exists requires exercising the actual `finality_grandpa` crate's `validate_commit` with an empty-precommit input and a permissive `VoterSet` (e.g., zero-weight or empty authority list edge cases), which needs a full build/test environment rather than static code search. This should be validated empirically before treating it as a confirmed exploit rather than a defense-in-depth gap.
