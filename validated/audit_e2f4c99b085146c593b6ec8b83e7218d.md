Confirmed: `performProoflessDepositChecks` in `HinkalHelper.sol` only validates array-length matching and `amounts[i] > 0`; it never checks that `msg.value` corresponds to any requested ETH amount when `address(0)` is absent from `erc20Addresses`. [1](#0-0) 

### Title
`prooflessDeposit()` permanently locks any ETH sent when no `address(0)` token is included in the deposit list - (File: contracts/Hinkal.sol, contracts/HinkalHelper.sol)

### Summary
`Hinkal.prooflessDeposit()` is `payable` and accepts an arbitrary `msg.value`, but the ETH accounting path is only entered for tokens equal to `address(0)` inside the caller-supplied `erc20Addresses` array. If a caller (directly, or via `HinkalWrapper`) sends ETH while `erc20Addresses` contains no `address(0)` entry, that ETH is received by the contract but never checked, never used to create a commitment/leaf, and never refunded — it is silently added to the contract's ETH balance with no corresponding accounting entry, i.e. permanently locked/stuck for the depositor.

### Finding Description
`prooflessDeposit()` first calls `hinkalHelper.performProoflessDepositChecks()`, which only validates that array lengths match and that `amounts[i] > 0`; there is no constraint tying `msg.value` to the sum of any ETH amounts requested. [2](#0-1) 

It then computes `uniqueTokens`/`uniqueCount` from the caller-supplied `erc20Addresses`/`amounts` and calls `_handleTransfersFromProoflessDeposit`. [3](#0-2) 

Inside `_handleTransfersFromProoflessDeposit`, the ETH balance-reconciliation logic (`balanceBefore -= msg.value; ... require(balanceAfter - balanceBefore == amount, ...)`) is only executed for the iteration where `erc20Address == address(0)` is present among `uniqueTokens`. [4](#0-3) 

If the caller never includes `address(0)` in `erc20Addresses` (e.g., only deposits ERC20 tokens), this loop body for ETH never runs, and there is no other place in `prooflessDeposit()` that checks `msg.value == 0` or refunds unexpected ETH. Any ETH attached to the call is simply absorbed into the contract balance with no leaf/commitment created for it, and no path exists in this function to reclaim it later.

The same gap propagates through `HinkalWrapper.prooflessDeposit()`: `_settleFee()` only checks `msg.value >= feeStructure.feeAmount` (a `>=`, not `==`, matching the analog bug class) and forwards `ethForHinkal = msg.value - feeStructure.feeAmount` to `Hinkal.prooflessDeposit{value: ethForHinkal}(...)`. If the caller overpays the fee, or if `erc20Addresses` doesn't include `address(0)`, that excess/forwarded ETH again lands in `Hinkal` unaccounted. [5](#0-4) 

By contrast, the main `transact()` entrypoint enforces a *strict* balance equation (`balanceDif == amountChanges[i] + utxoAmount`) for every token including ETH, so overpaying ETH there reverts instead of getting stuck. [6](#0-5)  `prooflessDeposit()` lacks this equivalent global reconciliation for ETH when `address(0)` is absent from the token list — this is the equality that's broken relative to the golom pattern (checked-and-enforced amount vs. actually received amount).

### Impact Explanation
ETH sent to `prooflessDeposit()` outside the accounted `erc20Addresses`/`amounts` set becomes permanently stuck in the `Hinkal` contract: it is not associated with any nullifier/leaf/commitment the depositor can later spend, and no owner/rescue function was found for arbitrary ETH withdrawal in the reviewed contracts. This is a permanent freezing of user funds — Critical/High impact per the given classification (permanent freezing of user funds).

### Likelihood Explanation
Any unprivileged EOA calling `prooflessDeposit()` (or `HinkalWrapper.prooflessDeposit()`) directly with a nonzero `msg.value` while omitting `address(0)` from `erc20Addresses`, or overpaying the ETH fee/amount, triggers this. No special permissions, timing, or race conditions are required — likelihood is high for any accidental or exploratory overpayment, and can be weaponized to grief users through UI/integration bugs or induced overpayment (e.g., a malicious relay/frontend crafting a call that attaches unaccounted ETH on a victim's behalf, though that scenario needs the victim to sign/send the transaction themselves).

### Recommendation
Enforce a strict, contract-wide ETH accounting invariant in `prooflessDeposit()` analogous to `transact()`'s balance equation: track the total ETH amount claimed across `erc20Addresses`/`amounts` (sum of amounts where `erc20Addresses[i] == address(0)`) and `require(msg.value == totalEthClaimed, ...)` unconditionally, even when no `address(0)` entry exists (in which case require `msg.value == 0`). Likewise, in `HinkalWrapper._settleFee()`, use `require(msg.value == feeStructure.feeAmount + <declared ETH deposit amount>, ...)` instead of `>=` so no excess ETH can be forwarded unaccounted.

### Proof of Concept
1. Attacker calls `Hinkal.prooflessDeposit(erc20Addresses, amounts, ..., orderId)` where `erc20Addresses = [USDC]`, `amounts = [1e6]`, and attaches `msg.value = 1 ether`.
2. `performProoflessDepositChecks` passes (lengths match, `amounts[0] > 0`). [2](#0-1) 
3. `_calcTokenChangesForProoflessDeposit` produces `uniqueTokens = [USDC]`; `_handleTransfersFromProoflessDeposit` only processes the USDC transfer via `transferERC20TokenFromOrCheckETH`, never touching the ETH balance check block because `erc20Address == address(0)` never occurs. [4](#0-3) 
4. Transaction succeeds; the 1 ETH sent along with the call is now part of `address(this).balance` with no corresponding commitment/leaf ever created for it, and no function that lets the depositor reclaim it.

    function _handleTransfersFromProoflessDeposit(
        TokenWithAmount[] memory uniqueTokens,
        uint256 uniqueCount
    ) private {
        for (uint256 i = 0; i < uniqueCount; i++) {
            address erc20Address = uniqueTokens[i].erc20Address;
            uint256 amount = uniqueTokens[i].amount;

            uint256 balanceBefore = getERC20OrETHBalance(erc20Address);
            if (erc20Address == address(0)) balanceBefore -= msg.value;

            transferERC20TokenFromOrCheckETH(
                erc20Address,
                msg.sender,
                address(this),
                amount
            );

            uint256 balanceAfter = getERC20OrETHBalance(erc20Address);

            require(
                balanceAfter - balanceBefore == amount,
                "proofless deposit balances must be equal"
            );
        }
    }

    function _settleFee(
        ProoflessFeeStructure calldata feeStructure
    ) internal returns (uint256 ethForHinkal) {
        ethForHinkal = msg.value;
        if (feeStructure.feeToken == address(0)) {
            require(
                msg.value >= feeStructure.feeAmount,
                "insufficient ETH for fee"
            );
            ethForHinkal = msg.value - feeStructure.feeAmount;
            if (feeStructure.feeAmount > 0) {
                transferETH(feeStructure.feeRecipient, feeStructure.feeAmount);
            }
        } else if (feeStructure.feeAmount > 0) {
            transferERC20TokenFrom(
                feeStructure.feeToken,
                msg.sender,
                feeStructure.feeRecipient,
                feeStructure.feeAmount
            );
        }
    }
