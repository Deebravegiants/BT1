### Title
Webhook `shop-domain` header not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute/verify the HMAC over `@raw_body` only. The `shop` accessor, which host applications rely on to identify which merchant/tenant a webhook belongs to, is read straight from the `shop-domain`/`x-shopify-shop-domain` header and is never included in the signable string.

### Finding Description
The identity binding that should hold is: `shop reported in the request == shop covered by the verified HMAC`. In this gem, `hmac` is computed as `HMAC(api_secret_key, raw_body)` [3](#0-2)  and the value the caller uses to route/authorize the webhook, `shop`, comes from an HTTP header that is never mixed into that signature [4](#0-3) [2](#0-1) . The gem's own `Utils::HmacValidator.validate` only checks that `HMAC(secret, to_signable_string)` matches the presented `hmac`; it says nothing about whether the `shop` header is authentic [5](#0-4) .

Since the raw body of a legitimate webhook for shop A is a byte string whose HMAC is valid for the app's shared secret, and that same byte string carries no shop information at all, an attacker who has ever observed one legitimate webhook delivery (raw body + valid HMAC signature) for the app — e.g., from their own store/installation, which is unprivileged and freely obtainable — can replay it with an arbitrary `X-Shopify-Shop-Domain` header claiming to be a different shop. The HMAC still validates because it only signs the body, not the shop.

Contrast this with the OAuth callback flow, where `shop` **is** included in `to_signable_string` for `AuthQuery` [6](#0-5) , and with `JwtPayload`, where the `dest`/shop claim is embedded inside the signed JWT itself [7](#0-6) . The webhook path is the only one of the three identity-binding mechanisms in this library where the tenant identifier is transmitted out-of-band from the signature.

### Impact Explanation
Any application that trusts `ShopifyAPI::Webhooks::Request#shop` after calling the gem's HMAC validation (which is the documented pattern) is exposed to cross-tenant data confusion: an attacker can make the host application process a webhook event under an arbitrary shop's identity while still passing the gem's cryptographic check. Depending on how the host app uses that shop identifier (e.g., to fetch/attach a stored access token or to trigger tenant-scoped side effects), this can lead to cross-tenant access — one of the explicitly in-scope Critical impacts.

### Likelihood Explanation
Requires the attacker to have legitimately received at least one real webhook (trivial — install/uninstall a free app on their own dev store, or trigger any subscribed event on their own tenant) and then replay that raw body with a forged `shop-domain` header to the app's webhook endpoint. No access to `api_secret_key`, tokens, or the merchant account is required — this fits the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the value that is cryptographically verified. Options:
- Include the `shop-domain` header (and ideally `topic`/`webhook_id`) in `to_signable_string`, or
- Cross-check `shop` against a value embedded in the (still-unsigned) JSON body only after confirming the body's HMAC, and document/enforce that host apps must independently correlate the delivered `webhook_id` with the shop they expect, rather than trusting the header outright.

At minimum, the library documentation should make explicit that `shop` is unauthenticated and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (or triggers any subscribed webhook topic legitimately).
2. Attacker captures the resulting webhook HTTP request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(secret, B)`.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and the same header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. The app constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` and calls `Utils::HmacValidator.validate(request)`; validation succeeds because `to_signable_string` only returns `B` [2](#0-1) .
5. The host app reads `request.shop` and obtains `"victim-shop.myshopify.com"` [4](#0-3) , processing the (attacker-controlled-content) webhook as if it originated from the victim tenant, despite a "successfully verified" HMAC.
