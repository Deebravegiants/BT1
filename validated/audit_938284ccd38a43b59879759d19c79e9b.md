## Title
Incorrect decimal-scaling direction in `pallet-hyper-fungible-token`'s ERC20 amount conversion causes unbacked minting / fund freezing on cross-chain token bridge transfers - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s cross-chain amount converters, `convert_to_erc20` and `convert_to_balance`, use `saturating_sub` to compute the scaling exponent between a token's local (substrate) decimals and its EVM-side (ERC20) decimals. `saturating_sub` silently clamps to zero whenever the subtraction would be negative, meaning the functions correctly scale only when `erc_decimals >= local_decimals`. When a registered token pair has `erc_decimals < local_decimals`, no compensating scale-down (on send) or scale-up (on receive) is applied at all — the raw numeric value is passed through unchanged, corrupting the amount by a factor of `10^(local_decimals - erc_decimals)`.

### Finding Description
`convert_to_erc20` is used in `Pallet::send` (an unprivileged, signed extrinsic) to convert a locked/burned local balance into the ERC20-precision amount embedded in the cross-chain `Message` dispatched to the paired EVM contract: [1](#0-0) 

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

If `erc_decimals < local_decimals` (e.g., a local asset registered with 18 decimals bridged to an EVM contract deployed with 6 decimals, which `register_token`/`ChainConfig.decimals` permits for arbitrary asset pairs), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the multiplier is `10^0 = 1`. The function returns `value` completely unscaled instead of dividing it down by `10^(local_decimals - erc_decimals)`. This inflated `erc20_amount` is what gets ABI-encoded into the `Message` body dispatched via ISMP to the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract, which mints that raw value verbatim on `onAccept`: [2](#0-1) 

The symmetric function, `convert_to_balance`, used in `on_accept` (inbound EVM → substrate path) has the identical flaw in the opposite direction: [3](#0-2) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}
```

Here too, when `erc_decimals < local_decimals`, the divisor clamps to `1`, so no scale-up is applied and `Pallet::on_accept` mints/releases far fewer local-denomination tokens than the sender actually escrowed/burned on the EVM side: [4](#0-3) 

This is precisely the same bug class as the referenced `DebtToken.totalSupply` report: an arithmetic helper that only correctly handles one direction of a decimal/scale comparison (using an operator, here `saturating_sub`, that silently clamps instead of branching on which side is larger), so the "wrong direction" case passes an unscaled value through instead of applying the required inverse operation.

### Impact Explanation
- On the `send()` path (substrate → EVM), any unprivileged user calling the `send` extrinsic on a token pair configured with `erc_decimals < local_decimals` causes the destination EVM contract to mint tokens at the raw `value` magnitude instead of the correctly scaled-down amount — an unbacked mint of up to `10^(local_decimals - erc_decimals)`× the intended amount, i.e., theft of value from the bridge's backing.
- On the inbound `on_accept` path (EVM → substrate) for the same class of token pair, users receive `10^(local_decimals - erc_decimals)`× less than they are owed — a permanent freeze/loss of the escrowed/burned value.
- Both are triggered by ordinary, single-transaction usage of the pallet's core cross-chain transfer flow (`send`/`onAccept`), not by any malicious admin, governance, or privileged actor — the pallet's own `register_token` extrinsic legitimately allows registering tokens with `erc_decimals` on either side of `local_decimals` (e.g., an 18-decimal local asset bridged to a 6-decimal ERC20 stablecoin representation), which is a foreseeable, ordinary configuration.

### Likelihood Explanation
The bug fires deterministically and silently whenever a registered token's `erc_decimals < local_decimals` — no attacker action beyond a normal `send()` call is required, and no error or revert signals the corruption. Given that many ERC20 tokens use fewer decimals (6 or 8) than common substrate asset configurations (10, 12, or 18), this decimal relationship is a realistic and likely occurrence for tokens registered on this general-purpose bridging pallet.

### Recommendation
Fix both helpers to branch explicitly on which side has more decimals rather than relying on `saturating_sub` to implicitly handle only one direction:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the mirror-image fix for `convert_to_balance`, ensuring a scale-down is applied when `erc_decimals < local_decimals` instead of being silently skipped. Add test coverage for token pairs where `erc_decimals < local_decimals` in both `send` and `on_accept` directions.

### Proof of Concept
Register a token with `local_decimals = 18` and `erc_decimals = 6` (a plausible configuration for e.g. a stablecoin bridged to a 6-decimal ERC20 representation):

1. User calls `send(amount = 1_000_000_000_000_000_000 /* 1 token, 18 decimals */)`.
2. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so it returns `1e18` unchanged (raw U256), instead of the correct `1e18 / 10^12 = 1_000_000` (1 token at 6 decimals).
3. The dispatched `Message.amount` field carries `1e18`. On the destination EVM contract, `onAccept` mints `1e18` raw units of a 6-decimal token — i.e., `1,000,000,000,000` tokens instead of `1` token, a `10^12`× unbacked mint. [5](#0-4)  shows the existing test harness only exercises the `erc_decimals(18) > local_decimals(10)` direction (`convert_to_erc20(SEND_AMOUNT, 18, 10)`), leaving the inverse (`erc_decimals < local_decimals`) case — where the bug manifests — untested.
