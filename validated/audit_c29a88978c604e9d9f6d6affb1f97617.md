Confirmed: in the Tron `IntentGatewayV2.placeOrder`, `msgValue` is set once from `msg.value` and there is no final refund of leftover `msgValue` (unlike the EVM/src version's `if (msgValue > 0) { _sendValue(msg.sender, msgValue); }` at the end of `_placeOrder`). Combined with the discarded `swapETHForExactTokens` return value, the excess ETH refunded by the Uniswap router back into the contract during the fee-swap is never tracked or returned to the user — it is permanently stuck in the `IntentGatewayV2` (Tron) contract.

### Title
Unchecked/discarded return value of `swapETHForExactTokens` causes permanently stuck native-token dust in `IntentGatewayV2` (Tron) - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, when a user pays the dispatch fee with native value, the contract calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(...)` but discards the returned `amounts` array entirely, and — unlike the canonical EVM implementation — never refunds any unspent `msgValue` to the caller afterward.

### Finding Description
`swapETHForExactTokens` returns the actual amount of ETH consumed by the swap (`amounts[0]`), refunding any excess ETH sent with the call back to the caller (the `IntentGatewayV2` contract itself, since it is `msg.sender` to the router). The canonical EVM implementation in `evm/src/apps/IntentGatewayV2.sol` correctly captures this: [1](#0-0) 
It computes `msgValue -= amounts[0]` and then refunds any remaining `msgValue` to `msg.sender` via `_sendValue`.

The Tron port omits both steps — the return value is discarded and no post-swap refund of leftover `msgValue` exists anywhere in `placeOrder`: [2](#0-1) 

Because the router refunds unspent ETH to the contract (not to the original user), and the contract's accounting/refund logic for that ETH is missing, the refunded ETH remains stranded in the `IntentGatewayV2` contract's balance with no code path to reclaim it for the user who overpaid.

### Impact Explanation
Any native-ETH overpayment used to cover `order.fees` (e.g., due to price movement between quote and execution, or a user intentionally sending slightly more than required) results in that surplus ETH being permanently locked in the `IntentGatewayV2` (Tron) contract. There is no `_sendValue`/refund step and no admin sweep path for this specific ETH-in-contract balance keyed to a particular order, so funds are unrecoverable by the affected user — a permanent freezing of funds analogous to the stuck `aTokens` in the referenced Aave report (unchecked return value → residual funds trapped in the calling contract).

### Likelihood Explanation
This triggers on essentially every `placeOrder` call on the Tron deployment where `order.fees > 0` and the user pays with native value, since `swapETHForExactTokens` almost always leaves some dust (exact output swaps rarely consume 100% of `msg.value` unless the caller pre-computes the exact required input off-chain, which the contract does not enforce). This makes it a high-likelihood, low-friction fund-loss bug for ordinary users rather than an edge case.

### Recommendation
Mirror the EVM implementation: capture the `amounts` array returned by `swapETHForExactTokens`, subtract `amounts[0]` from `msgValue`, and refund any remaining `msgValue` to `msg.sender` at the end of `placeOrder`, exactly as done in `evm/src/apps/IntentGatewayV2.sol` lines 383-397.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.fees = X` and sends `msg.value = Y` where `Y` pays for both `order.fees`-equivalent input tokens and the fee-swap, with some ETH slack beyond what the swap needs.
2. `swapETHForExactTokens{value: msgValue}(order.fees, path, address(this), block.timestamp)` executes, consuming `amounts[0] < msgValue` ETH and refunding `msgValue - amounts[0]` back to the `IntentGatewayV2` contract's own balance.
3. The return value is discarded; `msgValue` is never decremented and no refund call is made.
4. The refunded dust ETH sits in the contract's balance indefinitely — no getter, sweep, or accounting entry associates it with the user, and it is not part of any `_orders[commitment]` escrow that could later be withdrawn.
