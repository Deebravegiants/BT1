Confirmed: the webhook `shop-domain` header is verified only for *presence*, not integrity — the HMAC in `ShopifyAPI::Webhooks::Request` is computed exclusively over `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated headers [2](#0-1) . `Registry.process` validates only this body-only HMAC and then hands `request.shop` straight to the handler as the tenant identifier [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers, which the handler uses to attribute the payload to a specific merchant, are never included in the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the `hmac` field [4](#0-3) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`; `hmac` is parsed from the `X-Shopify-Hmac-Sha256`/`shopify-hmac-sha256` header, and `shop` is parsed independently from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header with no cryptographic relationship between the two [5](#0-4) .

Because Shopify apps use a single `client_secret` shared across every shop that installs the app, HMAC validity says only "this body was actually signed by Shopify for *some* installation of this app" — it proves nothing about *which* shop. `Registry.process` treats a successful HMAC check as sufficient and forwards the attacker-controllable `shop` header directly into `WebhookMetadata`, which is what the app-provided `WebhookHandler#handle` uses to decide which tenant's data the payload belongs to [3](#0-2) , [6](#0-5) .

The binding that should hold but does not:
`bytes covered by HMAC == bytes the app trusts to identify the tenant`
Here: `HMAC covers raw_body` while `tenant identity (shop) comes from an unsigned header`.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (a normal, unprivileged action any merchant can perform) will receive genuine webhook deliveries with a valid `X-Shopify-Hmac-Sha256` computed over a body they can fully observe/control (e.g. by triggering `orders/create` with attacker-chosen order data). They can then replay that exact `(raw_body, hmac)` pair to the same app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop that also has the app installed. `HmacValidator.validate` still passes because it only checks the body, and the app's handler will process/store the attacker's payload under the victim's shop identity — a cross-tenant data-injection/confusion primitive.

### Likelihood Explanation
Any merchant with the target app installed can generate arbitrarily many valid `(body, hmac)` pairs for their own shop and then forge the `shop-domain` header when replaying the request to the app's public webhook endpoint. No secret material, access token, or privileged access is required — only knowledge of the app's public webhook URL, which is normally documented/discoverable.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the HMAC-verified material, or independently verify the `shop-domain` header against a known/registered shop for this webhook (e.g. cross-check against the shop that owns `webhook_id`, or require topic+shop+body to be canonically included in `to_signable_string`). At minimum, treat the `shop-domain` header as untrusted until corroborated by data retrievable via an authenticated API call scoped to that specific installation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and configures/receives a webhook for `orders/create`.
2. Attacker triggers an order event, capturing the raw POST body `B` and its valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's shared `client_secret`, `H = HMAC-SHA256(secret, B)`).
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim-shop.myshopify.com` from the header [7](#0-6) ; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [8](#0-7) .
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))`, causing the app to process attacker-supplied data as if it originated from the victim shop.
