### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook replay/spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` only proves that the caller who produced the HMAC knows the app's `api_secret_key`; for webhooks the signed material is the raw body only. The `shop`, `topic`, and `webhook_id` values that identify *which tenant* the payload belongs to come from HTTP headers that are never part of the signed string, so they are trusted without being cryptographically bound to the HMAC that "authenticates" the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are read straight from headers with no relation to the signature: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e., that `hmac == HMAC(api_secret_key, raw_body)` — and then hands the *unverified* `shop`/`topic`/`webhook_id` straight to the app's handler: [3](#0-2) 

`WebhookMetadata` carries this unverified `shop` value on to the host application's business logic as if it were authenticated: [4](#0-3) 

Because the `api_secret_key` (`client_secret`) is shared across *every* shop that installs a given app, and the HMAC only binds the body bytes, a valid `(raw_body, hmac)` pair generated for one shop remains valid when replayed with a different `shop-domain` header claiming a different (victim) shop. The equality actually verified is:
`HMAC(secret, raw_body) == received_hmac`
but the equality the application logic implicitly relies on is:
`request.shop == "the shop that produced this signed body"`
These are not the same guarantee — the identity binding is broken.

### Impact Explanation
Any actor who can obtain one legitimately-signed `(raw_body, hmac)` pair for the target app (e.g., by installing the app themselves on a shop they control and capturing their own webhook deliveries) can resubmit that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop that also uses the same app. `HmacValidator.validate` will still return `true` because only the body is signed, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain. Any host application that uses `data.shop` (the gem's documented/intended field for tenant attribution) to key data writes, trigger fulfillment, update inventory, or route billing will attribute attacker-controlled content to the victim tenant — a cross-tenant data-injection/spoofing primitive.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/unprivileged) installer of the target app on their own store — no access to the app's `client_secret`, no privileged account, and no TLS interception is needed. The attacker only replays their own previously-received, validly-signed webhook payload with a modified `shop-domain` header. This is a realistic, low-effort attack path since apps commonly install on many independent merchant shops sharing one `api_secret_key`.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable material, or otherwise cryptographically bind the asserted `shop` to the HMAC (e.g., re-derive/validate the shop against a known registration, or require the host app to independently confirm the shop is expected to be receiving that specific webhook topic/id). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be cross-checked against server-side shop state before being trusted for tenant attribution.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a chosen JSON body `B`.
2. Real Shopify computes `hmac = HMAC-SHA256(api_secret_key, B)` and delivers headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: base64(hmac)`.
3. Attacker resends the identical raw body `B` and identical `hmac` header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` decodes the same signature; `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` — identical to before — and returns `true`, per [5](#0-4) .
5. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, per [3](#0-2) , causing the host app to process attacker-supplied data under the victim's tenant identity.
