### Title
Webhook `shop-domain` header is trusted as the tenant identifier while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's HMAC over the raw request body only, then forwards the `shop-domain` header — which is never covered by that HMAC — to the app's handler as if it were an authenticated part of the same signed message. This breaks the intended binding `verified(bytes) == acted_on(shop)`: the signature proves the body came from someone holding `Context.api_secret_key`, but says nothing about which shop the request is "for," because the shop identity travels in an unauthenticated header.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only over `Request#to_signable_string`, which returns `@raw_body`: [1](#0-0) 
The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic relationship to the HMAC at all: [2](#0-1) 

`Registry.process` validates the HMAC and then, treating the request as trustworthy, builds `WebhookMetadata` directly from `request.shop` and hands it to the registered handler: [3](#0-2) 

Because `Context.api_secret_key` is a single shared secret used to sign webhooks for *every* shop that has installed the app, `HMAC(body, secret)` is identical regardless of which shop the delivery is "for." An unprivileged internet user who is simply a legitimate installer of the app on their own shop will receive real, validly-signed webhook deliveries containing (`raw_body`, `hmac`) pairs computed with that same shared secret. Any topic whose body content is attacker-influenceable or predictable (e.g. a topic where the body is static, empty, or the attacker fully controls the store data reflected into the payload) lets the attacker capture a `(body, hmac)` pair that passes `HmacValidator.validate` for that exact body, and then replay it to the app's webhook endpoint with only the `shopify-shop-domain` header swapped to a victim shop. `HmacValidator.validate(request)` still returns `true`, because it never inspects `shop` — the equality actually enforced by the gem is `hmac == HMAC(body)`, but the equality the handler *needs* is `hmac == HMAC(body, shop)`. The gem does not compute or check the latter, so `shop` is accepted for tenant-scoped side effects (per `WebhookMetadata#shop`) without being bound to the signature that "authenticated" the request.

This is exactly the identity-binding gap called out in the rules: a field acted on (the `shop` used by the handler to select/mutate tenant data) is not covered by the HMAC that gates the request.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` from `Registry.process` to key session storage, delete data, or perform per-tenant side effects (e.g. an `app/uninstalled` handler that deletes the stored `Session` for `data.shop`) is exposed to cross-tenant interference: one merchant's legitimately-signed webhook delivery can be replayed with a forged `shop-domain` header to affect a different, unrelated shop's data, without ever needing the app's `client_secret`, an access token, or any privileged account. This matches the "cross-tenant access" Critical category, since the confused-deputy path lets a low-privilege actor (a regular app installer) cause the app to act on another tenant's identity.

### Likelihood Explanation
Requires only that the attacker (1) install the target app on a shop they control (an ordinary, unprivileged action) and (2) receive at least one webhook whose body is either static/empty or fully attacker-supplied via their own shop's data (common for several standard Shopify topics), then replay that exact body with a spoofed `shop-domain` header. No credential leakage, TLS interception, or social engineering is needed; the whole exploit is achievable purely by an internet user with normal app-install access.

### Recommendation
Do not treat `request.shop` as authenticated purely because `HmacValidator.validate` returned `true`. Either (a) include the shop domain in the HMAC signable input (matching what is actually verified to what is actually acted upon), or (b) cross-check `request.shop` against shop-scoped data embedded in the parsed body itself before handing it to `WebhookMetadata`, and document to consumers that `shop`/headers are not covered by the HMAC and must not be trusted for tenant selection without additional verification (e.g., confirming the webhook via the Admin API using a session already known to be scoped to that shop).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (ordinary action, no secrets required).
2. Attacker configures/triggers a webhook topic whose delivered body is static or fully attacker-controlled (e.g., body `"{}"`), and captures the legitimate `shopify-hmac-sha256` header Shopify computed for that exact body using the app's shared `client_secret`.
3. Attacker replays the exact same raw body and `hmac` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` builds the request; `Utils::HmacValidator.validate` recomputes `HMAC(body, secret)` and finds it matches the replayed `hmac`, returning `true`: [4](#0-3) 
5. `Registry.process` passes validation and invokes `handler.handle` with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` is `"victim-shop.myshopify.com"`: [3](#0-2) 
6. Any handler logic keyed off `data.shop` (e.g. deleting/updating stored session or app data for that shop) now executes against the victim shop, even though the signature only ever proved knowledge-of-secret for the body, not for the shop.
