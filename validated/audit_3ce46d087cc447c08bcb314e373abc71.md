### Title
Webhook `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers are trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` authenticates the JSON payload bytes only. The `shop`, `topic`, `api_version`, and `webhook_id` values that the framework hands to the app's webhook handler are taken straight from unauthenticated HTTP headers and are never bound into the signed material.

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the app-supplied handler: [1](#0-0) 

The HMAC verification itself is delegated to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For a `Webhooks::Request`, `to_signable_string` is defined as just the raw body, and `shop`, `topic`, `api_version`, `webhook_id` are pulled from headers that are never fed into the signature at all: [3](#0-2) 

This is the exact bug-class pattern in the report: an identity field (`shop`) that downstream code acts on (it is placed into `WebhookMetadata` and handed to the app's business logic, and is often used to select which merchant's tenant data to mutate) is not covered by the integrity check (`HmacValidator`) that is supposed to bind the whole message together — the equality that should hold, `hmac_signed_bytes == bytes_the_handler_trusts_for_tenant_identity`, does not hold, because `hmac_signed_bytes = raw_body` while `bytes_the_handler_trusts_for_tenant_identity = headers["shopify-shop-domain"]`.

Since Shopify signs webhooks per-app (using the app's single `client_secret`) rather than per-shop, any entity that can obtain one validly-signed `(raw_body, hmac)` pair for the app — e.g., by installing the app on their own attacker-controlled store and capturing/replaying one of their own legitimate webhooks — can resubmit that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (a victim shop's domain). `HmacValidator.validate` will still succeed because it only checks `raw_body` against `hmac`; `Registry.process` will then call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain.

### Impact Explanation
Any app logic that trusts `WebhookMetadata#shop` (or `Request#shop`) as an authenticated tenant identifier — for example to look up/update a merchant record, write order/inventory data, or as a session key to load an access token for that shop — can be spoofed into acting on behalf of a shop that never sent the webhook. This crosses the tenant boundary the gem is supposed to enforce (Critical - cross-tenant access), since the `shop` field carried to the handler has no cryptographic binding to the payload the HMAC actually authenticates.

### Likelihood Explanation
Exploitation only requires the attacker to be an installer of the app on their own store (an unprivileged, ordinary merchant) capable of triggering and capturing one legitimate webhook delivery for their own shop, then replaying the identical body/HMAC pair to the app's webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account for the victim is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signable material verified by `HmacValidator`, or otherwise cryptographically bind `Request#shop` to the verified payload before it is exposed via `WebhookMetadata`. At minimum, `Registry.process` should independently validate that the reported `shop` header corresponds to a shop that is expected/known to the app (e.g., cross-checked against a persisted session/shop registry) rather than passing the raw header value through unauthenticated.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the request: raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` recomputes HMAC over `B` only (see `to_signable_string`), which matches `H`, so validation passes.
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)`, and any handler logic keyed on `shop` now operates as if the (attacker-controlled) payload came from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
