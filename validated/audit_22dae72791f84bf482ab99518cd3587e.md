### Title
Ready oracle governance execution can invalidate prefetched flash-position prices mid-call - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
`flash_position` caches oracle prices before invoking an arbitrary receiver, then reuses those cached prices for post-callback collateral and solvency checks. A receiver can execute any already-ready governance `ConfigureAssetOracle` operation during the callback, replacing the collateral oracle while the controller continues to value the final position using the pre-callback price. This is a reachable time-of-check/time-of-use race between the price fetch and final risk evaluation.

### Finding Description
`process_flash_position` calls `prefetch_strategy_prices` before borrowing and invoking the receiver. [1](#0-0)  The receiver callback is then invoked inside the flash guard. [2](#0-1)  After the callback, measured collateral is deposited and `strategy_finalize` performs the final solvency gate using the same `Context`. [3](#0-2)  `Context::fetch_prices` deliberately retains already-cached prices, and `cached_price` returns that retained value rather than consulting the aggregator again. [4](#0-3) 

Governance permits anyone to execute a ready operation when `executor` is `None`. [5](#0-4)  A scheduled `ConfigureAssetOracle` resolves to the price aggregator's owner-gated `set_oracle` entrypoint. [6](#0-5)  Because governance and the price aggregator are not already on the controller → receiver call stack, the receiver can execute that ready operation during the callback; only a direct call back into the controller or pool would hit the host re-entry prohibition. [7](#0-6) 

### Impact Explanation
An attacker can open or extend debt using collateral valued under an obsolete higher oracle configuration, while the transaction itself replaces that oracle with a configuration returning a lower current value. The final controller risk check still sees the old price, so it can persist an account that is undercollateralized under the oracle configuration now active in storage. [8](#0-7) 

If the attacker keeps the borrowed proceeds and abandons the position, later liquidations observe the lower price and may leave residual bad debt. Bad-debt cleanup socializes residual debt by writing down the affected market's supply index, so the loss is borne by suppliers and can cause protocol insolvency rather than merely affecting the attacker's account. [9](#0-8) 

### Likelihood Explanation
The attack requires an already-scheduled and ready oracle configuration change whose resulting price differs materially from the currently valid configuration. The attacker does not need a governance role because ready `execute` calls may be driven by any address. [10](#0-9)  Oracle migrations are a realistic governance operation precisely because the active source can become stale or disagree with the replacement source; the attack only times its public execution inside the callback.

The flash-position receiver must return at least the declared positive collateral minimum and the final account must still retain debt and supply. [11](#0-10) [12](#0-11)  These constraints do not prevent the race: they only constrain how much undercollateralization the stale valuation can hide.

### Recommendation
Treat oracle configuration as mutable across external strategy callbacks. After `invoke_receiver` returns, either clear and refetch all prices used by the final risk check, or compare an oracle-registry version/configuration identifier captured before the callback with the version after the callback and revert on a change. The same post-external-call refresh should be applied to router-based strategy paths that currently prefetch prices before calling external code. [13](#0-12) 

### Proof of Concept
1. Governance has scheduled a `ConfigureAssetOracle` operation for collateral token `COL`; its delay has elapsed. The current oracle values `COL` at `P_high`, while the replacement configuration resolves to `P_low`, low enough that the intended borrow would fail the final health-factor check.
2. An attacker calls `Controller::flash_position` with:
   - `caller`: attacker-controlled contract or account;
   - `account_id`: a suitable existing `Multiply`/`Long`/`Short` account, or `0` to create one;
   - `debt`: `(hub_id, USDC)`;
   - `amount`: an amount supported by collateral only under `P_high`;
   - `receiver`: attacker-controlled WASM receiver;
   - `collaterals`: a `COL` leg with a positive minimum;
   - `refund_assets`: optionally the debt asset, allowing unused debt tokens to return to the caller.
3. The controller prefetches `COL` and debt prices into `Context`, mints the debt, forwards the measured tokens, and invokes `execute_flash_position`. [14](#0-13) 
4. Inside `execute_flash_position`, the receiver calls:
   - `Governance::execute(None, price_aggregator_address, "set_oracle", scheduled_args, predecessor, salt)`
   for the ready `ConfigureAssetOracle` operation. Governance executes `set_oracle` on the price aggregator, changing the active oracle configuration before the controller's final risk check. [6](#0-5) 
5. The receiver transfers the required `COL` collateral to the controller and returns.
6. The controller measures and deposits that collateral, but `cached_price(COL)` still returns `P_high` because the context retains fetched prices. [4](#0-3) 
7. `strategy_finalize` therefore passes a position that is insolvent under the newly installed `P_low` oracle configuration. [15](#0-14) 
8. The attacker retains the borrowed asset proceeds or refund; subsequent liquidations price the collateral at `P_low`, leaving bad debt to be socialized through the pool's supply-index write-down. [9](#0-8)

```rust
    pub(crate) fn fetch_prices(&mut self, assets: &Vec<Address>) {
        let missing = collect_uncached_keys(&self.env, assets, &self.token_prices);
        if missing.is_empty() {
            return;
        }
        let fetched = external::price_aggregator::fetch_prices(&self.env, &missing);
        for (asset, feed) in fetched.iter() {
            self.token_prices.set(asset, feed);
        }
    }

    }
```

```markdown
### INV-LIQ-04 — Bad-debt socialization is explicit and total

Permissionless cleanup requires ceil risk debt greater than half-up unweighted
collateral and collateral at or below the fixed $5 dust threshold. Owner-only
forced cleanup omits the dust cap. Both require debt, readable account and NFT
state, valid required prices and no active flash guard. Listing flags and
global pause do not block standalone cleanup.

Cleanup reclassifies all remaining collateral shares as revenue and writes off
all remaining debt against each debt's market. It releases spoke usage and
atomically removes account entries and the NFT. It does not net same-market
supply against debt. Standalone cleanup emits `CleanBadDebtEvent` with
pre-cleanup USD totals, without a controller position-update batch.

Ordinary liquidation and cleanup apply no final account-health or full-backing
assertion. The index floor can leave a shortfall. Recapitalization fills that
shortfall without restoring the lost index or deleted account.
```

```markdown
## Governance

Constructor `(admin: Address, min_delay: u32)` initializes the owner, access-control admin, five operational roles and a nonzero minimum delay. Scheduled operations use the interface's `AdminOperation` variants.

`execute` must match a scheduled operation hash and predecessor and run within its execution window. With `executor = None`, anyone can execute a ready operation. With `Some(address)`, that address must authorize and hold EXECUTOR_ROLE.
```
