### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (tenant) identity solely from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` validates is computed only over the raw request body. Because the `shop` field is not part of the signed material, an attacker who possesses one validly-signed webhook body/HMAC pair (e.g., from webhooks Shopify sent for their own store) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. The signature check still passes (it only checks the body), but the handler receives a forged `shop` claim.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) . `Request#shop` is parsed straight from a header with no cryptographic binding to the body or its HMAC [2](#0-1) . `Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header field, never touching `shop` [3](#0-2) . `Registry.process` gates entirely on this HMAC check and then trusts `request.shop` as the tenant identity passed into the handler's `WebhookMetadata` [5](#0-4) .

The equality that should hold is: `shop bound in HMAC == shop acted upon by handler`. Here the left side is empty (no shop material is signed) while the right side is attacker-controlled header input, so the binding is broken. Any party that can obtain one legitimately-signed webhook body (trivial for a merchant that installs the app on their own store and receives real webhooks) can resubmit that same body/HMAC pair with a different `shop-domain` header to the app's public webhook endpoint, and the gem will report it as validated and hand it to the app's handler tagged with the attacker-chosen shop.

### Impact Explanation
This breaks the shop-authentication boundary the gem is documented to provide via `Utils::HmacValidator.validate`/`Registry.process`: it enables cross-tenant data injection — an attacker can cause data destined for/attributed to their own shop to be processed and stored by the host application under a victim shop's identity (e.g., corrupting per-shop records, triggering shop-scoped side effects like `app/uninstalled` cleanup, or poisoning GDPR `customers/redact` handling for a shop they don't control). This matches the Critical "cross-tenant access" category since it lets an attacker act, with a validly-signed message, on behalf of a tenant they do not own.

### Likelihood Explanation
High. Any developer/merchant using the app can generate legitimately-signed webhook payloads for their own shop (webhooks are delivered constantly, e.g. `orders/create`), capture body+HMAC, and replay them to the app's public webhook receiver endpoint with a forged `shop-domain` header — no access token, secret, or privileged account is required.

### Recommendation
Bind the `shop` field into the signed material that is verified, e.g., include the `shop-domain` header value in `to_signable_string` (matching how Shopify actually signs the payload if it does), or independently verify that the `shop` claimed in the header matches a shop the receiving endpoint is expecting (e.g., cross-check against the session/shop context associated with the endpoint) before trusting `request.shop` for any shop-scoped action.

### Proof of Concept
1. Register the app's webhook handler for topic `orders/create` and capture a legitimately delivered webhook for `attacker-shop.myshopify.com`: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's secret), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Replay the identical `B` and `H` to the same webhook endpoint, changing only the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B) == H` [6](#0-5) .
4. `Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
