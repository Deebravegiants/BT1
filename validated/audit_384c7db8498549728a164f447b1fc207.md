### Title
Predictable, unsigned session cookie value enables cross-tenant session hijacking - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
The non-embedded session lookup path trusts the raw, unsigned `shopify_app_session` cookie value as a session-store key, and this gem also generates that value deterministically as `"offline_#{shop}"` for offline sessions. Because the value is neither an HMAC-bound nor otherwise unguessable token, and `shop` (a `.myshopify.com` domain) is public information, any unprivileged internet user can construct the exact session id belonging to a target merchant and use it as their own cookie value, causing the host application to load and use that other shop's session (and its access token) via the gem's supplied session-id derivation helpers.

### Finding Description
`ShopifyAPI::Auth::Session.from` (the method used at the end of the OAuth callback in `lib/shopify_api/auth/oauth.rb:97-98` and by `TokenExchange`/`ClientCredentials`/`RefreshToken`) sets the session `id` for offline access tokens to a fully deterministic value: [1](#0-0) 

For non-embedded apps, this exact id is also what gets written into the un-signed `shopify_app_session` cookie: [2](#0-1) 

The cookie itself carries no signature or HMAC — it's a plain `name`/`value`/`expires` struct: [3](#0-2) 

And the gem's own `Utils::SessionUtils`, which host applications are expected to call to resolve "the current session id" from incoming request data, simply returns the raw cookie value verbatim with no cryptographic verification of any kind: [4](#0-3) [5](#0-4) 

This breaks the intended binding: `session id == identity authenticated by OAuth for shop`. Instead, the actual binding enforced by the gem is `session id == bytes present in an unauthenticated cookie header`, and those bytes are attacker-predictable (`"offline_" + known myshopify domain`) rather than a random, unguessable token bound to the specific browser/session that completed OAuth.

### Impact Explanation
Any application built on this gem's documented, non-embedded flow (`SessionUtils.current_session_id` → look up `Session` by that id in the host's session storage → use `session.access_token`) is exposed to cross-tenant access: an attacker who knows or guesses a legitimately-installed shop's domain can set `shopify_app_session=offline_<victim-shop>.myshopify.com` in their own request and have the host app load and act with the victim shop's stored offline access token. This satisfies the "Critical - cross-tenant access" bar, since the identity binding broken is exactly "session id derived from unauthenticated bytes" / "shop authenticated versus shop stored as session key" called out as in-scope.

### Likelihood Explanation
High for any non-embedded app following the gem's documented cookie-based session pattern: no secret, access token, or privileged access is required — only knowledge of the target's `myshopify.com` domain, which is routinely public (e.g., visible in storefront URLs, app listings, or simply guessable/enumerable shop names). The online-session id (`"#{shop}_#{user_id}"`, `lib/shopify_api/auth/session.rb:114`) is similarly a deterministic concatenation rather than a random token, compounding the issue for apps using online tokens too.

### Recommendation
- Do not use a deterministic, guessable value (`"offline_#{shop}"` / `"#{shop}_#{user_id}"`) as the literal cookie value that grants session lookup. Either sign/HMAC the cookie value (bind it to the shop + a server secret) so it cannot be forged/guessed, or use a random opaque token as the cookie value that is separately mapped server-side to the deterministic session id.
- `SessionUtils.cookie_session_id`/`current_session_id` should verify integrity of the cookie-derived id (e.g., an HMAC computed with `Context.api_secret_key`) before returning it, mirroring what `Utils::HmacValidator` already does for OAuth/webhook payloads.

### Proof of Concept
1. Attacker learns/guesses a target shop's domain, e.g. `victim-shop.myshopify.com` (public knowledge).
2. Attacker computes the deterministic offline session id per `Session.from`: `offline_victim-shop.myshopify.com` (`lib/shopify_api/auth/session.rb:116`).
3. Attacker sends a request to the vulnerable (non-embedded) app with cookie `shopify_app_session=offline_victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns that raw value unchecked (`lib/shopify_api/utils/session_utils.rb:31-36`, `68-71`).
5. The host app looks up this id in its session store, finds the victim shop's genuine `Session` (previously created after the victim's real OAuth), and the attacker's request is now serviced using the victim shop's access token — cross-tenant access achieved without any credentials.
