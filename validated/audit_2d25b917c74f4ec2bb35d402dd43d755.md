### Title
Unauthenticated `emporiumMessage`/`EmporiumStack` in the token-less "Emporium-Min" circuit path lets any EOA drain `EmporiumUpgradeable`'s native/ERC20 balance via unauthorized arbitrary calls - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `Hinkal.transact()` is called with `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes proof-input construction to `formInputEmporiumMin`, which is meant to be verified against `MainEVMCircuitMin`. That circuit performs **no** EdDSA signature check and **no** nullifier/ownership check — it only recomputes `message = Poseidon(messageSeed)` from a free private input. This means any caller can trivially produce a valid proof for **any** `emporiumMessage` value of their choosing, without owning any shielded UTXO, key, or wallet. `EmporiumUpgradeable.runAction` then treats `stack.signerAddress == address(0)` as "no wallet is being authorized," skips the EIP-712 ECDSA signature check entirely, and executes the attacker-supplied `EmporiumOperation[]` as raw `endpoint.call{value: op.value}(op.callData)`. Because `erc20TokenAddresses` is empty in this path, none of the balance/slippage equalities in `Hinkal.transact()` or in `runAction`'s own balance-change loop apply to this call, so an attacker can direct Emporium to send its own ETH (and any ERC20 balance it holds, via `callData`) to an attacker-controlled endpoint with no signer or prover authorization at all.

### Finding Description
The bug-class analog to the Augur report is: a "reset"/no-op state path (here, the token-less proof path) leaves a downstream consumer (`EmporiumUpgradeable.runAction`) trusting a value (`emporiumMessage`/`EmporiumStack`) that is *not* actually bound to any real signer/prover secret, breaking the intended equality "every action executed by Emporium was authorized by the wallet/prover that signed it."

1. `MainEVMCircuitMin` [1](#0-0)  has only `outTimeStamp` and `calldataHash` as public inputs and computes `message <== Poseidon(1)([messageSeed])` from a fully free private `messageSeed`. There is no `spendingPublicKey`, no `eddsaSignature`, no `signedMessageHash` check, and no nullifier/commitment logic at all — unlike `MainEVMCircuit` [2](#0-1) .

2. `CircomDataBuilder.formInputForCircom` selects this trivial circuit path whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0` [3](#0-2) . In that path `emporiumMessage` becomes a public signal ("message") produced from an attacker-chosen `messageSeed`, with zero cryptographic binding to any wallet key.

3. `performHinkalChecks` only verifies that `calldataHash` matches a hash the *same caller* computed over the *same calldata* they are submitting in this very transaction [4](#0-3) . It does not prove that some other, authorized party previously approved this specific payload — that authentication is supposed to come from the ZK proof binding `signedMessageHash`, which is entirely absent for the Min path.

4. In `EmporiumUpgradeable.runAction`, `verifyWallet` checks only that `emporiumMessage` hasn't been used before, and then — critically — returns immediately without any signature check when `stack.signerAddress == address(0)` [5](#0-4) .

5. Back in `runAction`, for `stack.signerAddress == address(0)` and `op.invokeWallet == false` ("Stateless Interaction"), the contract performs `(success, err) = op.endpoint.call{value: op.value}(op.callData);` [6](#0-5) . The only restriction is that the call's function selector cannot be `callHinkalWallet`/`doSendToRelay`; any other endpoint/value/calldata is permitted.

6. Because `circomData.erc20TokenAddresses` is empty in this path, the enclosing balance-change checks in `runAction` (`balancesBefore`/`balancesAfter` loop) and in `Hinkal.transact()` never execute for any token, including native ETH, so no equality catches the outbound value transferred by the stateless call.

Net effect: any unprivileged EOA can call `Hinkal.transact()` with a self-crafted `circomData` (empty `erc20TokenAddresses`, `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: attacker, invokeWallet: false, value: <EmporiumBalance>, callData: ""}], ...})`), a trivially-generated Groth16 proof for the near-empty `MainEVMCircuitMin`, and a fresh unused `emporiumMessage`. This authorizes Emporium to send its own ETH/token holdings to the attacker with no wallet-owner or prover authorization whatsoever — an unauthorized asset movement / theft of protocol funds held by the Emporium contract.

### Impact Explanation
This is High/Critical impact under the given rubric: "theft or permanent freezing of protocol/relay fees" and "executing calls or moving assets a wallet owner or prover never authorised." Any ETH or ERC20 balance that accumulates in `EmporiumUpgradeable` (e.g., transient relay-fee balances, dust left from prior `runAction` calls, or funds intentionally routed through Emporium as an intermediary) can be siphoned by an attacker who never owns a shielded balance, never signs anything, and never controls any wallet registered with Emporium.

### Likelihood Explanation
Likelihood is high for any attacker who understands the proof-input construction: no admin/relayer/manager privilege is required, only the ability to call `Hinkal.transact()` (a public, unprivileged entry point) and generate a Groth16 proof for a circuit with no real constraints. The main precondition is that `EmporiumUpgradeable` actually holds a nonzero balance at attack time, which depends on operational usage (fee-forwarding patterns, leftover dust, or funds transiently parked there by other Emporium operations).

### Recommendation
- Require that `MainEVMCircuitMin` (or the Emporium-Min public-input construction) cryptographically binds `emporiumMessage`/the entire `EmporiumStack` to a real signer identity (e.g., verify an EdDSA signature over `signedMessageHash` even in the token-less path), rather than allowing an unconstrained `Poseidon(messageSeed)` to stand in for authorization.
- In `EmporiumUpgradeable.verifyWallet`, do not silently skip signature verification for `stack.signerAddress == address(0)`; instead, restrict the "Stateless Interaction" branch to cases where the operation is provably paid for/authorized by shielded funds actually moved in the same transaction, or require an explicit relayer/owner-level authorization for arbitrary external calls with `value`.
- Include native ETH in the balance-equality checks so that any outbound value transfer performed inside `runAction` (including stateless calls with `op.value`) is forced to balance against `deltaAmountChanges`/`amountChanges`, closing the gap that currently exists whenever `erc20TokenAddresses` is empty.

### Proof of Concept
1. Attacker observes/knows `EmporiumUpgradeable` holds a nonzero ETH (or ERC20) balance and is registered in `Hinkal.externalActionMap[HINKAL_EMPORIUM_ACTION_ID]`.
2. Attacker builds `circomData`:
   - `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `slippageValues = []`, `onChainCreation = []` (dimensions.tokenNumber = 0).
   - `externalActionData = { externalAddress: EmporiumUpgradeable, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack({ v:0, r:0, s:0, signerAddress: address(0), ops: [ EmporiumOperation({ endpoint: attackerContract, invokeWallet: false, value: <EmporiumBalance>, callData: "" }) ], maxFee: 0, deadline: type(uint256).max })) }`.
   - `emporiumMessage`: any value not yet in `usedMessages`.
   - `calldataHash = CircomDataBuilder.getHashedCalldata(circomData)` (self-computed, trivially satisfiable since attacker controls all inputs).
3. Attacker computes a valid Groth16 proof for `MainEVMCircuitMin` by choosing any `messageSeed` such that `Poseidon(messageSeed) == emporiumMessage`, satisfying the circuit's only constraint.
4. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)`. `performHinkalChecks` passes (self-consistent hash), `verifyProof` passes (trivial circuit), `rootHashExists` is irrelevant/bypassable since no UTXOs are touched, and `_externalTransact` invokes `EmporiumUpgradeable.runAction`.
5. `verifyWallet` marks `emporiumMessage` used and returns early (no signature check) because `signerAddress == address(0)`.
6. The stateless op executes `attackerContract.call{value: EmporiumBalance}("")`, draining Emporium's ETH to the attacker with no wallet-owner or prover authorization.

*Note: exact byte-level layout of `Dimensions`/verifier registration for the token-count-0 case, and the precise conditions under which `EmporiumUpgradeable` accumulates a nonzero balance in production, were not independently confirmed from the indexed portion of the repo and would benefit from full-repo verification via a Devin session.*

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }

        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return

                block.chainid,
                hinkalAddress,
                circomData
            );
    }
