### Title
Webhook shop/topic/id headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values entirely from HTTP headers, while the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies is computed only over the raw request body. Any party who can obtain one validly-signed webhook body (e.g. a malicious merchant receiving webhooks for their own installed shop, since all shops share the same app `client_secret`) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, and the signature check will still pass.

### Finding Description
The binding that should hold is:
`shop identity used for dispatch == shop identity cryptographically bound by the HMAC`

In `HmacValidator.validate`, the signature is verified against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — none of the headers: [2](#0-1) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic` as the authoritative tenant/topic identity for dispatch to the handler: [4](#0-3) 

Because the header fields are outside the signed content, the equality above does not actually hold: the HMAC only proves the body came from Shopify for *some* webhook event, not that it came from the specific shop/topic named in the headers. This is the same class of bug as the reported vault issue — a field that is acted upon (`shop`) is not covered by the validation that is supposed to bind identity (`isDepositLimitSetRoleHolder` checked but `depositLimitSetRoleHolder` not enforced together).

### Impact Explanation
Any merchant who has installed the app (an "unprivileged" actor from the perspective of other tenants) legitimately receives webhooks addressed to their own shop, complete with a valid `x-shopify-hmac-sha256` value computed with the app's single shared `client_secret`. That merchant can capture the raw body + HMAC header from one of their own webhooks and re-POST it to the app's webhook endpoint with the `shop-domain` header changed to any victim shop's domain (shop domains are public/guessable, not secret). `HmacValidator.validate` will still return `true` because it only checks the body against the secret. `Registry.process` then calls the app's handler with `shop:` set to the victim's domain and the attacker-controlled body, causing the app to act as though the victim shop sent that event (e.g. mandatory `customers/redact`/`shop/redact` triggering data deletion for the victim, or fabricated `orders/create`/`customers/create` data being attributed to and stored under the victim shop's tenant record). This is a cross-tenant identity confusion enabled purely through this gem's verification logic, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any shop (a routine, unprivileged action available to any merchant), (2) capturing one webhook delivery for that shop, and (3) replaying the raw body/HMAC pair to the same endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or the victim's credentials is needed. The `Request` and `Registry` code paths exercised are exactly the documented, expected usage of the gem, so this is reachable through standard integration.

### Recommendation
Include the shop domain, topic, api version and webhook id in the signable content used for HMAC verification of webhook requests, or otherwise cryptographically bind these header-derived values to the body before trusting them in `Registry.process`. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop-domain` (and ideally `topic`/`webhook-id`) header values so that tampering with them invalidates the signature.

### Proof of Concept
1. App has processed a real webhook for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker (who controls `attacker-shop`) records `B` and `H`.
3. Attacker sends a new HTTP POST to the app's webhook endpoint with the same body `B`, same `hmac-sha256` header `H`, `topic` header unchanged, but `shop-domain` header set to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com"})` is constructed; `request.shop` returns `"victim-shop.myshopify.com"`.
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-hashes `B` with `client_secret` and compares to `H` — headers are never part of `to_signable_string`.
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to treat attacker-controlled webhook content as originating from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
