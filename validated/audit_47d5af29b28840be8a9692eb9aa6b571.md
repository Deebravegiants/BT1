### Title
Webhook `shop-domain`, `topic`, `webhook_id`, and `api_version` headers are trusted for tenant routing despite not being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` only proves that the *body bytes* were signed with the app's shared `api_secret_key` — it never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` HTTP headers [2](#0-1) . `Registry.process` nonetheless uses these unauthenticated headers directly to route and tag the webhook to a tenant: it calls `Utils::HmacValidator.validate(request)` and then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)`, handing attacker-controlled header values straight to the host app's handler as the "shop" and "topic" of the event [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop/topic/webhook_id authenticated by HMAC == shop/topic/webhook_id acted upon by the handler`

Instead, only `raw_body` is covered by the HMAC (`to_signable_string` returns `@raw_body` alone, see `request.rb:35-38`), while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly and unconditionally from attacker-influenceable HTTP headers (`shopify_header`/`shopify-*` or `x-shopify-*`) with no cryptographic tie to the signed payload [4](#0-3) .

Because the app's `api_secret_key` (client secret) is shared across every shop that installs the app, any merchant who installs the app is an "unprivileged internet user" with respect to every *other* tenant of that same app. Such a merchant can:
1. Trigger a real event in their own store, causing Shopify to send a genuinely-HMAC-signed webhook (`hmac-sha256` computed over `raw_body`, `shop-domain: attacker-shop.myshopify.com`).
2. Intercept/replay that exact HTTP request to the app's webhook endpoint while modifying only the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header, since the body (and therefore the HMAC) is left untouched.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — it succeeds, because the body was never altered [5](#0-4) .
4. The forged `shop` value is then handed to the app's registered handler as the identity of the tenant the event belongs to [6](#0-5) .

This lets one tenant's data/events be attributed to another tenant purely by header substitution, despite a "valid" HMAC — the classic "field acted on but not covered by the HMAC" identity-binding break.

### Impact Explanation
This is a cross-tenant integrity issue: the webhook consumer (via this gem's `Registry.process`/`WebhookMetadata`) treats the `shop` field as authenticated identity for dispatch, but the gem provides no mechanism binding `shop`/`topic`/`webhook_id` to the HMAC. Any application built on the documented `Registry.process` API inherits this gap without any way to detect the mismatch, since the gem exposes no "was shop covered by signature" guarantee. This matches the Critical category of cross-tenant access: an attacker who legitimately controls one shop can cause the app to process (and act on) webhook content while impersonating an arbitrary other shop domain string.

### Likelihood Explanation
Moderate-to-high: exploitation requires only (a) installing the app on an attacker-controlled shop (a normal, unprivileged action any Shopify merchant/developer can take), and (b) the ability to replay/modify HTTP headers to the app's public webhook endpoint (trivial, no secrets required — `api_secret_key` is never revealed to the attacker, only reused implicitly since the body+HMAC pair is unchanged). No access token, session, or leaked credential is needed.

### Recommendation
Include `shop-domain`, `topic`, and `webhook_id` in the signable string used for HMAC verification, or otherwise cryptographically bind them (e.g., re-derive the expected topic/shop from a side channel verified independently of the header, or require the host app to cross-check `request.shop` against a shop it has an active offline session for before trusting it). At minimum, document clearly that `request.shop`/`request.topic` are *not* authenticated by `HmacValidator.validate` and must be independently verified by the host application before being used to key any tenant-scoped operation.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), causing Shopify to POST a signed webhook:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Webhook-Id: <id>`
   - Body: `raw_body` (order JSON).
2. Attacker replays this exact body+hmac to the app's webhook endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` accepts it (all required headers present) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` returns only `raw_body`, unchanged from step 1 [1](#0-0) .
5. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker's order data>, ...)` is passed to the app's handler, which now believes `victim-shop.myshopify.com` generated this order event [6](#0-5) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
