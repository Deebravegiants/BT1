### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only, while the `shop` (tenant identifier) is read from a separate, unsigned HTTP header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then forwards the unsigned `shop` value to the app's webhook handler as the authoritative tenant identifier. Because the signed bytes (`body`) and the trusted identity field (`shop`) are not cryptographically bound together, an attacker who possesses one validly-signed webhook (trivially obtainable by installing the app on their own store, which any unprivileged internet user can do) can replay that exact body/HMAC pair while substituting an arbitrary victim shop domain in the `x-shopify-shop-domain` header, and the gem will accept it as an authentic webhook "from" the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` derive the verified signature purely from `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` is read independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which plays no part in the HMAC computation at all: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac`, so it never touches the `shop` field: [4](#0-3) 

`Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` as the tenant identifier passed to the app's handler: [5](#0-4) 

The documented handler pattern treats `data.shop` as the trusted tenant key for routing/storing webhook data (e.g. `shop_domain: data.shop`): [6](#0-5) 

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC-verified(body) == HMAC-verified(shop)` — in reality only `HMAC-verified(body)` is true; `shop` is asserted, not authenticated.

**Before attacker action:** Shopify sends webhook `(body_A, hmac_A, shop=A)` to the app for the attacker's own store `A`. This is a fully legitimate, correctly signed request that any unprivileged user can generate by simply operating their own Shopify dev store and installing the target app.

**Attacker action:** The attacker captures `(body_A, hmac_A)` and re-sends it to the app's webhook endpoint, but replaces the `x-shopify-shop-domain` header with `shop=Victim`.

**After attacker action:** `HmacValidator.validate` recomputes HMAC over `body_A` only, which still matches `hmac_A`, so validation passes. `Registry.process` then invokes the app's handler with `WebhookMetadata(shop: "Victim", body: body_A, ...)` — the handler processes attacker-controlled data under the victim's tenant identity.

### Impact Explanation
This breaks the tenant-isolation boundary the whole webhook subsystem is meant to enforce: the `shop` field is the sole tenant discriminator that host applications (per this gem's own documented usage pattern) use to route and persist webhook payloads per-merchant. An attacker can inject fabricated event data attributed to an arbitrary victim shop into any app that follows the documented handler pattern, without needing the app's `client_secret`, an access token, or any privileged account — only the ability to trigger one legitimate webhook to themselves (installing the app on a shop they control) and replay it with a modified header. This is a cross-tenant data-integrity/confusion vector reachable by any unprivileged internet user.

### Likelihood Explanation
High likelihood: no secrets, tokens, or privileged access are required. Creating a development store and installing a target app is free and self-service; capturing one's own legitimately-delivered webhook and replaying it with a different header value is trivial (no TLS interception needed since the attacker controls both ends of the legitimate delivery). The vulnerable code path (`Request#hmac`, `Request#shop`, `HmacValidator.validate`, `Registry.process`) is exercised on every http webhook processed by any app using this gem as documented.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) value into the signed material verified by `HmacValidator`, or explicitly document/require that host applications cross-check `request.shop` against an independently known/authorized list of shops for their app before trusting it as a tenant identifier. At minimum, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the shop-domain header (mirroring how Shopify's HMAC actually only signs the body, which means the gem should treat `shop` as untrusted unless separately verified via `Registry.get_webhook_id`/an authoritative session lookup) rather than exposing it to handlers as if it were authenticated.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker-shop.myshopify.com`, triggering Shopify to send a legitimately-signed webhook:
   ```
   POST /webhook
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, "note": "test"}
   ```
2. Attacker captures the exact body and `x-shopify-hmac-sha256` value.
3. Attacker resends the identical body and HMAC header to the same endpoint, changing only the shop header:
   ```
   POST /webhook
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {"id": 1, "note": "test"}
   ```
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC successfully (it only checks the body), and invokes the app handler with `shop: "victim-shop.myshopify.com"`, causing the app to process/store attacker data as belonging to the victim tenant.
