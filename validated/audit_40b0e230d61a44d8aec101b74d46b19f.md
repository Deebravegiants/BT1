### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header — HMAC covers only the raw body, not the tenant identifier ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then hands the app's handler a `shop` value that comes from an HTTP header that is never covered by that HMAC. This breaks the identity binding `hmac_verified_bytes == data_acted_on`: the gem verifies the *body*, but the *tenant identifier* (`shop`) used by the app to route/attribute the payload is taken from an unauthenticated header.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable content strictly from the raw body: [1](#0-0) 

and derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers that are entirely outside the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop` header value and dispatches it to the app-supplied handler: [3](#0-2) 

`HmacValidator.validate` confirms this — it only ever compares a signature computed over `to_signable_string` (the raw body) against the received signature: [4](#0-3) 

The identity binding that should hold is: `hmac_secret_proves(raw_body) == raw_body AND shop == the tenant that raw_body belongs to`. In this implementation only the first half holds. Because the HMAC key (`api_secret_key`) is shared by the app across *all* installing shops (it's the app's own secret, not per-shop), any shop that has installed the app receives legitimately-signed webhook deliveries whose `raw_body`+HMAC pair is valid for that exact body under the shared app secret. This gives an unprivileged attacker who owns/controls their own installed shop the ability to capture a body+HMAC pair that is valid under the app's secret without ever having to know or leak that secret, and to construct a new HTTP request to the app's webhook endpoint with that unmodified `raw_body`/HMAC header pair but a different `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will accept the HMAC (it only checks the body) and hand the handler `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker's own body, ...)`.

The gem's own documentation instructs developers to key their downstream processing directly on `data.shop`: [5](#0-4) 
so the shop value is treated by design as the authenticated tenant identifier, yet nothing in the gem binds it to the signed payload.

### Impact Explanation
This crosses a tenant boundary: an attacker with only a legitimate installation of the app on their *own* shop can force the app's webhook processing pipeline to attribute attacker-controlled webhook data (and topic/webhook_id/api_version) to an arbitrary victim shop domain, without possessing the app's `client_secret` or the victim's access token. This maps to "cross-tenant access" (Critical) per the rules — the HMAC validation gives false confidence that `shop` is authenticated when it is not covered by the signature at all.

### Likelihood Explanation
High. No secret, TLS interception, or privileged access is required — only that the attacker install the app on a shop they control (standard, low-privilege action for any Shopify merchant/developer) in order to obtain a valid `raw_body` + `hmac-sha256` pair, and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a substituted `shop-domain` header (the endpoint is a normal public URL configured by the app to receive webhook `POST`s).

### Recommendation
Bind the shop identity to the signed content rather than trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`/`webhook_id`) in the HMAC-signable string in `ShopifyAPI::Webhooks::Request#to_signable_string`, or
- Cross-verify that `shop` extracted from headers matches a shop field embedded in the (also-signed) body/topic context, or
- Require that `Registry.process` be given the expected shop out-of-band (e.g. resolved from the endpoint routing/session) and reject mismatches against the header value.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (normal, unprivileged action). Shopify subsequently delivers a legitimate webhook to the app's endpoint, e.g. `orders/create`, with:
   - `raw_body = '{"id":1,...}'`
   - `x-shopify-hmac-sha256 = Base64(HMAC-SHA256(app_secret, raw_body))`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (both are visible to them as the shop owner / can be replayed via any request-capturing proxy they control on their own infrastructure — no interception of Shopify's channel needed).
3. Attacker sends a new POST directly to the app's public webhook endpoint, reusing the same `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — this succeeds because it only checks `raw_body` against the HMAC, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb` (`to_signable_string`).
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 198–199, causing the app to process attacker-supplied data under the victim tenant's identity.
