### Title
Missing chain/domain binding in pallet-hyper-fungible-token's calldata authorization signature allows cross-chain replay of a user-authorized dispatchable call - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s `on_accept` lets a beneficiary authorize an arbitrary `RuntimeCall` to be dispatched from their own account as soon as a cross-chain token transfer lands, by attaching an ECDSA/Sr25519/Ed25519 signature over `(nonce, runtime_call)` inside the ERC-20 message's `data` field. The signed payload never binds the destination chain, the source contract/state machine, or any Hyperbridge-instance-specific value — exactly the same class of defect flagged for `ECDSAPPSOracle` (message hash omitting chain-binding data such as `block.chainid`/`address(this)`), just realized here as a missing `StateMachine`/genesis-hash binding in a Substrate ISMP module.

### Finding Description
In `on_accept` [1](#0-0) , when `message.data` is non-empty, the pallet decodes a `SubstrateCalldata{ signature, runtime_call }` and, if a signature is present, verifies it against:

```
let nonce = frame_system::Pallet::<T>::account_nonce(beneficiary.clone());
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
```

for all three signature schemes (Ed25519, Sr25519, ECDSA) [2](#0-1) . On success, it dispatches `runtime_call` as `RawOrigin::Signed(beneficiary)` and only then increments the local nonce [3](#0-2) .

The message hash has no reference to:
- the destination `StateMachine` / chain, or the chain's genesis hash,
- the source contract address or source chain (`source`, `from`) the request arrived on,
- any Hyperbridge-instance identifier.

The only replay guard is `frame_system`'s per-account `nonce`, which is local to each chain (and each chain's `AccountId` namespace). Any account that has not yet transacted on a given chain starts at nonce `0`, so a signature produced for `(0, runtime_call)` verifies identically on every chain running this pallet where the same beneficiary derivation applies. `message.data` (containing `signature` and `runtime_call`) is delivered as part of a public, ISMP `PostRequest.body`, visible on-chain/off-chain to any indexer or relayer once first submitted [4](#0-3) . This is the closest reachable analog to the external report: the same "no chain-id / no domain separator ⇒ replayable authorization" root cause, here enabling unbacked, unauthorized dispatch of a `RuntimeCall` as the victim's account.

By contrast, every other signature-authorized flow in this codebase deliberately binds the state machine/chain into the signed message (e.g., `pallet-ismp-relayer`'s `message(nonce, dest_chain, beneficiary)` and `beneficiary_message(nonce, state_machine, beneficiary)` [5](#0-4) [6](#0-5) , with an explicit test asserting cross-chain replay is rejected [7](#0-6) ), and EIP-712 flows in the EVM intents stack fold `chainId`/`verifyingContract` into the domain separator [8](#0-7) . `pallet-hyper-fungible-token`'s calldata-authorization signature is the outlier that omits this binding.

### Impact Explanation
An attacker (any relayer/observer, no special privilege) who captures a beneficiary's signed `(nonce=0, runtime_call)` payload from one destination's on-chain data can construct or wait for a second `PostRequest` addressed to a different HFT-enabled parachain (any chain that also maps the same source contract via `ContractToAsset` and derives the same `AccountId` for the victim's key) and get the same `RuntimeCall` dispatched as the victim's account there — with no fresh authorization from the victim. Depending on what `BaseCallFilter` permits, this is unauthorized app/account action (arbitrary dispatchable execution under the victim's identity on an unintended chain), which can range from unwanted transfers to governance/staking actions.

### Likelihood Explanation
Medium: it requires (1) the same source ERC-20 contract/state-machine registered in `ContractToAsset` on more than one HFT deployment (plausible in a multi-parachain Hyperbridge topology sharing common bridged contracts), and (2) the victim's account nonce on the second chain to match the signed nonce (trivially true, `0`, for any account that hasn't transacted there yet). Both conditions are realistic for a fresh/first-time user interacting with a newly bridged asset across chains, and the signed payload is inherently public once relayed once.

### Recommendation
Bind the signed payload to the destination context, mirroring `pallet-ismp-relayer`'s pattern: include the local `StateMachine`/genesis hash (or an explicit `T::HftInstanceId`), and ideally the `source` contract and originating `StateMachine`, in the hashed message, e.g.:
```rust
let payload = (nonce, frame_system::Pallet::<T>::block_hash(0u32.into()) /* genesis */, source, from, substrate_data.runtime_call.clone()).encode();
```
so a signature is only valid for the specific chain/contract pairing it was created for, exactly as recommended for `ECDSAPPSOracle` (fold `block.chainid`/`address(this)`-equivalent context into the hash before verification).

### Proof of Concept
1. Victim signs `(nonce=0, runtime_call=C)` intending it to execute once their HFT transfer lands on Chain A (mirrors `should_receive_asset_with_calldata` [4](#0-3) ).
2. Relayer submits the `PostRequest` to Chain A; `on_accept` verifies the signature against `(0, C)`, dispatches `C` as the victim, and increments the victim's nonce to `1` on Chain A only.
3. The same `message.data` bytes (signature + `runtime_call`) are visible from Chain A's post request body. A relayer repackages them into a new `PostRequest` targeting Chain B's HFT pallet instance (registered for the same source contract), where the victim's derived `AccountId` still has nonce `0`.
4. Chain B's `on_accept` independently recomputes `(nonce=0, C)`, recovers the same signer, and dispatches `C` as the victim on Chain B — without any new authorization from the victim.

pub fn message(nonce: u64, dest_chain: StateMachine, beneficiary: Option<Vec<u8>>) -> [u8; 32] {
	if let Some(beneficiary) = beneficiary {
		return sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode());
	}
	sp_io::hashing::keccak_256(&(nonce, dest_chain).encode())
