### Title
Withdraw/borrow authorization checks a stale creation-time owner instead of the current NFT owner, so an account's previous holder retains control after transferring the position NFT - (contracts/controller/src/account.rs)

### Summary

Cal.com CVE-2025-66489 is a conditional-logic flaw where the wrong credential is checked, letting authentication be bypassed. The analog in XOXNO Lending is that sensitive position entrypoints authorize against `Account.owner` — the address recorded when the account NFT was minted — while the protocol's own invariant (stated in `position-nft/src/contract.rs`) is that `owner_of(token_id)` is the account owner. Since the position NFT is freely transferable and the controller is never notified on transfer, `account.owner` becomes stale the moment the NFT changes hands. `is_owner_or_delegate` short-circuits `true` when `caller == owner` [1](#0-0) , so the previous owner keeps full withdrawal/borrow authority over the account.

### Finding Description

- `create_account_with` stores `owner` inside the `Account` struct at mint time [2](#0-1) .
- `process_withdraw` and `process_borrow` authorize via `require_owner_or_delegate(env, account_id, caller, &account.owner)` [3](#0-2) [4](#0-3) , which returns early when `caller == owner` — the stale stored owner [5](#0-4) .
- The authoritative ownership check `require_account_owner` reads the live NFT owner via `storage::account_owner` [6](#0-5) , but is only used by `renew_account` and delegate management — not by withdraw, borrow, or the `Migrate`/`Multiply` guards, which all trust `account.owner` [7](#0-6) .
- The NFT contract documents that token id == account id and `owner_of` is the account owner [8](#0-7) , and it implements the stock OZ transferable enumerable NFT with no callback to the controller, so nothing updates `Account.owner` on transfer.

Additionally, delegates are keyed by the stored owner (`get_delegates(env, account_id, owner)` [9](#0-8) ), so delegates granted by the previous owner also remain valid after transfer.

### Impact Explanation

Theft of user funds. After a victim buys or receives a position NFT (or after a hacked/phished transfer), the original minter — or any earlier owner — can call `withdraw(account_id, [(_, 0)], Some(attacker))` (zero = withdraw-all sentinel [10](#0-9) ) to drain all collateral, and `borrow` to take max debt against the victim's collateral and send proceeds to themselves via `to`. The NFT buyer acquires an account that a stranger can still fully control.

### Likelihood Explanation

Reachable by a single unprivileged address: mint an account, supply collateral, transfer the NFT, then call `withdraw`. The only caveat I could not fully verify within the available tool iterations is whether `storage::get_account` re-syncs `owner` from the NFT on load — the grep results showed `account_owner` exists as a separate NFT-backed accessor, which strongly suggests `get_account` returns the stored `Account` as-is, but `contracts/controller/src/storage/account.rs` should be read to confirm before reporting externally.

### Recommendation

In `load_or_create_account`, `process_withdraw`, `process_borrow`, and all delegate/migrate/multiply guards, replace `account.owner` with `storage::account_owner(env, account_id)` (or re-sync `account.owner` from `owner_of` on every `get_account` load) so authorization always follows the live NFT owner, and key delegate sets to the account rather than a stored owner address.

### Proof of Concept

1. Alice calls `supply(0, spoke, [(hub, amt)])`; controller mints account `id=7`, stores `owner=Alice`.
2. Alice calls position-nft `transfer(Alice, Bob, 7)` (or approves a marketplace sale). `Account.owner` still equals Alice.
3. Alice calls `withdraw(7, [(hub, 0)], Some(Alice))`. `require_owner_or_delegate` sees `caller == account.owner` and returns; `settle_withdraw` pays out Bob's entire collateral to Alice.
