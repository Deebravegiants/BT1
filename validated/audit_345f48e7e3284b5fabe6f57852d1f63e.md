### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while the `shop` value (from the `X-Shopify-Shop-Domain` header) is read separately and never included in the HMAC-covered content. `Registry.process` validates the HMAC and then immediately trusts `request.shop` to attribute the webhook payload to a tenant. This breaks the identity binding `HMAC-verified bytes == bytes that determine the tenant`, allowing an attacker who legitimately receives real, validly-signed webhooks for their own shop (because they installed the app) to relay the same signed body to the app's webhook endpoint while substituting a different `shop-domain` header value, causing the receiving app to process/store the attacker's data under a victim shop's identity.

### Finding Description
The `deposit`/`tokensReceived` bug class in the external report is about a value (credited balance) being derived from data that bypassed the intended single-path validation, letting an attacker double-count the same transferred value under one identity. The applicable analog here is a value (the `shop` identity) that is *acted upon* by the receiving application but is *not bound* by the same authentication mechanism (HMAC) that guards the rest of the payload.

Concretely:
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` is read directly from an HTTP header, independent of the signed content: [2](#0-1) 
- `HmacValidator.validate` computes/compares the HMAC solely over `to_signable_string`, i.e., only the body: [3](#0-2) 
- `Registry.process` validates that HMAC, then hands `request.shop` straight into the handler's metadata as the tenant identifier, with no further correlation to the signed body: [4](#0-3) 

Because the same `api_secret_key` is shared across every shop that installs the app, an HMAC valid for a given body proves only "Shopify (or someone holding this app's secret) generated this exact body at some point" — it proves nothing about *which* shop that body belongs to. The `shop` field, which the gem uses to route/attribute the resulting data, sits entirely outside that proof. This is the same class of defect as the ERC777 case: a credited/attributed value (`shop`) is set through a path (the raw header) that isn't reconciled with the value that was actually verified (the signed body).

### Impact Explanation
An attacker who is a legitimate merchant of the target app (i.e., an ordinary, unprivileged installer — no special access needed) receives genuine webhook deliveries from Shopify for their own store, each with a valid HMAC over the body. By replaying that exact `raw_body`/HMAC pair to the app's public webhook endpoint while changing only the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to a victim shop's domain, the request still passes `HmacValidator.validate` (since only the body is checked), and `Registry.process` will call the app's handler with `WebhookMetadata.new(shop: request.shop, body: request.parsed_body, ...)` where `shop` is now the attacker-chosen victim domain. This lets the attacker inject or overwrite data (orders, customers, inventory, GDPR-topic payloads, etc.) attributed to a shop they do not own — a cross-tenant integrity/confidentiality break in any multi-tenant app built on this gem's webhook processing.

### Likelihood Explanation
Any merchant who installs the app and subscribes to webhooks can obtain a valid `(body, hmac)` pair for their own shop trivially (it's simply the webhook delivery they legitimately receive). Forging the header is a one-line HTTP client change. No secret material, TLS interception, or privileged access is required — only knowledge of the app's public webhook URL, which is required infrastructure for the app to function at all.

### Recommendation
Bind the tenant identity into the verified material: include the shop domain (and ideally the webhook id / topic) inside `to_signable_string`, or independently verify that the `shop` header value belongs to the API client that legitimately owns the webhook subscription (e.g., cross-check against a per-shop webhook id/secret stored at registration time) before trusting `request.shop` for attribution in `Registry.process`.

### Proof of Concept
1. App merchant A installs the target app and registers `orders/create` webhooks; A receives a real Shopify webhook POST with a valid `X-Shopify-Hmac-Sha256` header for a JSON body describing one of A's orders.
2. A captures this raw request (body + hmac header) via a proxy.
3. A resends the identical body and hmac header to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over the untouched `raw_body`: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, and the host application stores/acts on A's order data as if it belonged to `victim-shop`: [6](#0-5)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)

        end
