## Analysis

The vulnerability is confirmed. The core equality that should hold is:

**assets Emporium can move in a tx == assets accounted for in `balancesBefore`/`balancesAfter`**

This breaks because when `erc20TokenAddresses.length == 0`, `EmporiumUpgradeable.runAction`'s accounting loop `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` at [1](#0-0)  never executes, so nothing constrains what `stack.ops` did.

`formInputForCircom` routes any call with `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` to `formInputEmporiumMin`: [2](#0-1) . The circuit backing this minimal path, `MainEVMCircuitMin`, proves only `message == Poseidon(messageSeed)` with public signals `outTimeStamp` and `calldataHash` — it constrains nothing about `ops`, `signerAddress`, amounts, or tokens: [3](#0-2) .

In `runAction`, `verifyWallet` is the only guard on `stack.ops`, but if `stack.signerAddress == address(0)` it returns immediately after marking the message used, skipping all EIP-712 signature verification: [4](#0-3) . The ops loop then executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own context: [5](#0-4) .

**Exploit path**: An attacker calls `Hinkal.transact` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = []`, and `externalActionData.externalActionMetadata` ABI-encoding an `EmporiumStack{ signerAddress: address(0), ops: [{ endpoint: <someERC20Emporium holds>, invokeWallet: false, value: 0, callData: transfer(attacker, balance) }] }`. Since the token array is empty, the circuit only needs a trivial `MainEVMCircuitMin` proof (attacker knows their own `messageSeed`), and `performHinkalChecks`/`getHashedCalldata` only bind `calldataHash` to the exact `circomData` bytes supplied — they do not constrain `ops` content or `signerAddress` semantics. On execution, `verifyWallet` skips signature checks (signer is zero), the op executes `IERC20(token).transfer(attacker, amount)` from the Emporium contract itself, and the post-loop accounting (`balancesBefore`/`balancesAfter` diff, `deltaAmountChanges`) never runs because `erc20TokenAddresses.length == 0`. Any ERC20 balance sitting in the Emporium contract (e.g., from other in-flight/dust transfers, prior swaps, or fee residue) is drained to the attacker with zero UTXO issuance and zero on-chain accounting.

The "amount at CIRCOM_P boundary" framing in the question is not actually load-bearing here — the Min circuit and `formInputEmporiumMin` carry no `amountChanges` signal at all, so no modular-encoding edge case is required; the theft path works for any balance Emporium holds, independent of amount encoding.

### Title
Emporium Min-proof path bypasses all balance accounting, enabling theft of any ERC20 balance held by the Emporium contract - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` and constrains nothing about the `EmporiumStack` ops. Combined with `verifyWallet` skipping signature verification when `signerAddress == address(0)`, and `runAction`'s balance-accounting loop being bounded by the (empty) token array, an unprivileged attacker can execute an arbitrary op (e.g., an ERC20 `transfer`) from the Emporium contract's identity with zero balance accounting or UTXO issuance, stealing any ERC20 balance sitting in the Emporium contract.

### Finding Description
The broken equality: *assets Emporium can move via `stack.ops` in a transaction* must equal *assets accounted for in `balancesBefore`/`balancesAfter` diffing*. `runAction` computes `balancesBefore`/`balancesAfter` and iterates only over `circomData.erc20TokenAddresses` [6](#0-5) . If that array is empty, the loop body (which reverts on negative balance change and mints an out-UTXO for positive change) never runs, regardless of what `stack.ops` actually did.

`formInputForCircom` deliberately selects the minimal-proof path exactly when `erc20TokenAddresses.length == 0` [7](#0-6) , and `formInputEmporiumMin` only feeds `emporiumMessage`, `timeStamp`, and `calldataHash` into the circuit [8](#0-7) . The corresponding circuit, `MainEVMCircuitMin`, proves nothing but `message == Poseidon(messageSeed)` [3](#0-2)  — it has no knowledge of, and places no constraint on, `stack.ops`, `stack.signerAddress`, or any amount.

`verifyWallet` is the sole runtime guard on `stack.ops`, and it unconditionally returns without any signature check when `stack.signerAddress == address(0)` [4](#0-3) . The ops execution loop then performs `op.endpoint.call{value: op.value}(op.callData)` as the Emporium contract [5](#0-4) , so any `callData` encoding `ERC20.transfer(attacker, amount)` against a token Emporium holds succeeds and moves real funds — with no gate other than the blocked `callHinkalWallet`/`doSendToRelay` selectors, which are irrelevant here since `invokeWallet` is false.

`performHinkalChecks` only validates `originalSender`/`relay` consistency, `getHashedCalldata` integrity, relay allow-listing, `dimensionsCheck`, and `checkOnchainCreation` [9](#0-8)  — none of these constrain the semantic content of `stack.ops` or forbid an empty `erc20TokenAddresses` array paired with a nonzero-value op. `runAction` itself is only reachable through `onlyAllowedRecipient`, i.e. via `Hinkal.transact`, which is exactly the attacker's entrypoint, so this is not a privileged-caller-only bug.

### Impact Explanation
Any ERC20 tokens held by the Emporium contract (from residual/dust balances, in-flight multi-step operations, or accumulated fee remnants) can be transferred out to the attacker with zero accounting and zero circuit constraint — a direct theft of funds the protocol holds. This matches Critical: direct theft of shielded or in-flight user funds. The attack is repeatable for every fresh `emporiumMessage` and for every ERC20 balance the Emporium contract accumulates.

### Likelihood Explanation
No privileged role is required — the attacker only needs to call `Hinkal.transact` with a self-chosen `EmporiumStack` (`signerAddress = address(0)`) and generate a trivial `MainEVMCircuitMin` proof for their own `messageSeed`, which any user can do. The precondition is that the Emporium contract holds an exploitable ERC20 balance at call time (e.g., from another in-flight transaction, prior op leaving residue, or an attacker first funding it via a legitimate deposit path). Attacker cost is a single transaction plus proof generation for the minimal circuit, which is cheap.

### Recommendation
Do not allow the Emporium-Min proof path to authorize arbitrary `stack.ops` execution. Specifically: (1) require `stack.signerAddress != address(0)` (i.e., always verify the EIP-712 signature) whenever `stack.ops.length > 0`, regardless of `erc20TokenAddresses.length`; (2) bind the accounting loop to reflect actual token movement even when `erc20TokenAddresses` is empty — e.g., disallow any op execution at all when the token array is empty, or require the Min proof path to still constrain `stack.ops` (e.g., hash of ops into the circuit's public/private inputs) rather than leaving it entirely unconstrained.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, fund it directly with an ERC20 token (`token.transfer(address(emporium), 1000e18)`), and register it as an allowed external action recipient of `Hinkal`.
2. As an unprivileged attacker EOA, build `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({v:0,r:0,s:0, signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))})], maxFee: 0, deadline: block.timestamp + 1}))`.
3. Generate a valid `MainEVMCircuitMin` proof for a fresh `messageSeed` locally (snarkjs), set `calldataHash` correctly per `getHashedCalldata`.
4. Call `Hinkal.transact(...)` as attacker.
5. Assert: before call, `token.balanceOf(attacker) == 0` and `token.balanceOf(emporium) == 1000e18`; after call, `token.balanceOf(attacker) == 1000e18` and `token.balanceOf(emporium) == 0`, with no UTXO minted to attacker's shielded balance for this amount — proving assets moved with zero accounting.
