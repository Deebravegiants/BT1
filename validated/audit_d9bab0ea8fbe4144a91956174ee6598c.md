### Title
Order escrow can be permanently locked when an order targets an unregistered destination instance - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol, evm/src/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` escrows a user's input tokens for a cross-chain order without validating that a gateway instance is registered for `order.destination`. If no `NewDeployment` has been delivered by Hyperbridge governance for that destination chain (or the destination bytes are simply mistyped/unsupported), the funds are escrowed but neither of the two recovery paths can complete, because `_cancelFromSource` itself calls `instance(order.destination)` — which reverts with `UnknownInstance()` when unregistered — to build the storage-proof key for its GET request.

### Finding Description
`placeOrder` in `evm/src/apps/IntentGatewayV2.sol` (lines 194-415) escrows `order.inputs` into `_orders[commitment][token]` and only performs chain-identity/format checks — it never calls `instance()`/`_instance()` to verify that `order.destination` has a registered gateway before accepting the deposit. [1](#0-0) 

Recovery of a cross-chain order that is never filled is expected to go through `cancelOrder` → `_cancelFromSource`, which dispatches a Hyperbridge `DispatchGet` request to read the `_filled` storage slot on the destination gateway. Building the storage key requires resolving the destination gateway address via `instance(order.destination)`: [2](#0-1) 

`instance()`/`_instance()` reverts with `UnknownInstance()` whenever no `Deployment` has been registered for that state machine: [3](#0-2) 

Registration only happens via governance-delivered `NewDeployment` requests processed in `onAccept`, gated to Hyperbridge/relayer-authorized senders: [4](#0-3) 

Because `placeOrder` accepts orders for any `destination` bytestring — registered or not — and `_cancelFromSource` unconditionally reverts on an unregistered destination, a user who places an order to a chain that Hyperbridge governance has not (yet, or ever) registered a gateway for has no way to recover the escrowed tokens on the source chain: fill is impossible (no valid instance exists on the destination side to authenticate the settlement message back), and cancel-from-source reverts before it can even dispatch the query.

This mirrors the reported Carousel pattern: a user-initiated deposit/escrow action succeeds and queues the user's assets for a future, protocol-controlled event (a new epoch in Carousel; a registered `NewDeployment` in IntentGatewayV2) that may never occur, and the withdrawal/cancellation path has no fallback for the "event never happened" case — it simply reverts.

### Impact Explanation
Any single `placeOrder` transaction from an unprivileged user with an unregistered (or as-yet-unregistered) `destination` value permanently locks the escrowed input tokens and any collected fee-token amount (`order.fees`) in the `IntentGatewayV2` contract, with no on-chain recovery path. This is a concrete freezing-of-funds bug reachable purely from a user-submitted transaction, satisfying the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high: destination chain identifiers are raw, unchecked `bytes` supplied by the caller (SDK/off-chain code, a malformed integration, or simple user/typo error), and there is no on-chain safeguard preventing an order from being placed against a destination that has not (yet) had its gateway registered. Any race between order placement and governance's `NewDeployment` delivery, or any client bug that supplies a wrong/unsupported chain id, triggers this condition without requiring any malicious actor.

### Recommendation
Either (a) have `placeOrder` validate `instance(order.destination)` exists (or is intentionally deferred) before escrowing funds for cross-chain orders, revert otherwise, or (b) add a cancellation fallback that does not depend on `instance()` succeeding — e.g., allow a source-side refund after the deadline has passed when the destination has no registered instance, without requiring a storage proof from a chain the protocol has no relationship with.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` on the source-chain `IntentGatewayV2` with `order.destination = "SOME_UNREGISTERED_CHAIN"` and valid `order.inputs`; tokens are transferred into escrow and `_orders[commitment][token]` is set. [5](#0-4) 
2. No solver can complete settlement because there is no gateway instance for that chain to build the return message.
3. After `order.deadline`, the user (or anyone) calls `cancelOrder(order, options)` with `options.height > order.deadline`, routing to `_cancelFromSource`.
4. `_cancelFromSource` calls `instance(order.destination)` while constructing the storage-proof key, which reverts with `UnknownInstance()` because no `Deployment` was ever registered for that chain. [2](#0-1) [6](#0-5) 
5. The transaction reverts every time it is retried; the escrowed tokens remain stuck in the contract indefinitely.

(Note: I was unable to fully re-verify the exact `_cancelFromSource` body in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` in this session due to a tool error on the final read attempt; the equivalent Tron contract source at the cited lines shows the same `instance()` call pattern, and the mainline EVM contract shares the same `IntentsBase._instance` helper, so the revert path is expected to be identical, but a direct read of `ExtrinsicIntents.sol`'s `_cancelFromSource` implementation would be needed to close out any doubt.)

    /**
     * @dev Resolves the IntentGateway instance address for a given state machine.
     * Reverts with `UnknownInstance` if no remote deployment has been registered for that chain.
     * @param stateMachineId The raw state machine identifier bytes.
     * @return The gateway address for the given state machine.
     */
    function _instance(bytes calldata stateMachineId) internal view returns (address) {
        address gateway = _instances[keccak256(stateMachineId)];
        if (gateway == address(0)) revert UnknownInstance();
        return gateway;
    }
