### Title
IntentGatewayV2 (Tron variant) records escrow using nominal input amount instead of actual tokens received, breaking accounting for fee-on-transfer tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder` credits the `_orders[commitment][token]` escrow mapping with `reducedInputs[i].amount` — a value derived purely from the user-supplied `order.inputs[i].amount` minus the protocol fee — rather than the amount the contract actually received via `safeTransferFrom`. This is the same root cause as the referenced Sherlock report: an accounting variable (`poolAmount` there, `_orders[commitment][token]` here) diverges from the token balance actually custodied by the contract whenever a fee-on-transfer token is used.

### Finding Description
`placeOrder` computes `reducedInputs` from `order.inputs[i].amount` (the amount the user claims to be depositing) before any transfer takes place: [1](#0-0) 

It then, for the non-predispatch path, calls `safeTransferFrom` for exactly `order.inputs[i].amount`, but immediately credits escrow with `reducedInputs[i].amount` regardless of what the contract actually received: [2](#0-1) 

The predispatch path has the same flaw — it checks `balance < requiredAmount` (a floor check) but always credits `reducedInputs[i].amount` to escrow, and only emits `DustCollected` for any *positive* surplus over `requiredAmount`; it never reduces the escrow credit when the dispatcher/gateway received less than required due to transfer fees on the way through: [3](#0-2) 

If the escrowed token has any transfer fee (deflationary/fee-on-transfer ERC20), the contract's actual token balance for that order is strictly less than the amount recorded in `_orders[commitment][token]`. This directly mirrors the audit finding: an internal accounting value overstates real custodied funds.

Notably, the primary (non-Tron) `evm/src/apps/IntentGatewayV2.sol` was hardened against exactly this class of bug — it snapshots `balanceOf` before/after each transfer and mutates `order.inputs[i].amount` to the actual received amount before computing `reducedInputs` and crediting escrow: [4](#0-3) [5](#0-4) 

This fix is confirmed by dedicated fee-on-transfer regression tests in the test suite for the main contract: [6](#0-5) 

However, the Tron variant at `evm/tron/contracts/apps/IntentGatewayV2.sol` does not contain this balance-diff correction — it is missing the fix that was applied to the mainline EVM contract, reintroducing the vulnerability class for any deployment of this Tron contract.

### Impact Explanation
Any solver/relayer who fills an order denominated in a fee-on-transfer token, or the pool owner reconciling escrow, will find the contract cannot pay out the full amount recorded in `_orders[commitment][token]` for that token, because the actual token balance held is less than the sum of escrow credits. Depending on withdrawal ordering, this can lead to: (a) some legitimate withdrawals reverting due to insufficient balance (denial of funds/permanent freezing for the last claimant), or (b) if multiple orders share the token balance, later orders' rightful escrow being unpayable — a form of fund freezing/loss for users. This satisfies the "permanent freezing of funds" acceptance criterion, reachable directly by any unprivileged user submitting a `placeOrder` transaction with a fee-on-transfer input token — no privileged role required.

### Likelihood Explanation
Likelihood is proportional to adoption of fee-on-transfer/deflationary tokens on chains where this Tron `IntentGatewayV2` is deployed. Since `placeOrder` is a fully permissionless, single-transaction entry point open to any user with an ERC20 supporting a transfer fee, exploitation (or accidental triggering) requires no special conditions beyond selecting such a token as an order input — and the intent-gateway system is explicitly a general-purpose ERC20 order/escrow mechanism, not restricted to a fixed allowlist of non-fee tokens in this contract (unlike the primary contract, no such restriction/fix exists here).

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` (or `balanceOf(dispatcher)` for the predispatch path) before and after each `safeTransferFrom`/sweep, use the actual received delta as `order.inputs[i].amount` before computing `reducedInputs`/`commitment`, and credit `_orders[commitment][token]` only with the actually-received (post-fee) amount.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g. 1% fee, as in `FeeOnTransferToken` from the test suite) and the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no protocol fee (`protocolFeeBps == 0`), so `reducedInputs[0].amount == 1000e18`.
3. Inside `placeOrder`, `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000e18)` is executed, but due to the 1% fee the gateway's actual `balanceOf` increases by only 990e18.
4. `_orders[commitment][token] += reducedInputs[0].amount` credits `1000e18`, even though the gateway holds only `990e18` of that token.
5. When the order is subsequently cancelled/withdrawn (`withdraw`/`cancelOrder`) for the full escrowed `1000e18`, the ERC20 transfer out will revert or leave the contract under-collateralized for other pending orders sharing the token, freezing part of the funds. [2](#0-1)

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
