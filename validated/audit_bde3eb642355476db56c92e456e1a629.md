## Analysis

The reachable bug-class analog here is a **field acted on but not covered by the HMAC** — specifically, the webhook `shop` (and `topic`/`webhook_id`) identity used to route/attribute a webhook event is never included in the HMAC signature computation, even though the gem's HMAC check is what's supposed to authenticate the whole webhook request.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers, entirely independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` against `hmac`, i.e. it only authenticates the body bytes: [3](#0-2) 

`Registry.process` then trusts the HMAC check as proof of authenticity for the *entire request*, and dispatches to the app handler using `request.shop` / `request.topic` / `request.webhook_id`, none of which were part of what was actually verified: [4](#0-3) 

### Why this is exploitable by an unprivileged internet user

Shopify signs webhook bodies with the app's `client_secret` — the **same secret across every shop that installs the app**. An attacker can install the target app on their own free/unprivileged development store, receive a legitimately-signed webhook (valid `hmac-sha256` header for some body), and then replay that exact `raw_body` + `hmac` pair directly to the app's public webhook endpoint while swapping the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to point at a victim shop. Since the signature only ever covered the body — never the headers — `HmacValidator.validate` still returns `true`, and `Registry.process` hands the handler a `WebhookMetadata` claiming the event belongs to the victim's shop.

This breaks the equality that should hold: **shop authenticated by the HMAC == shop acted upon by the handler**. Before the attack, both sides trivially match (the real webhook for the attacker's own shop). After the attacker's replay with a modified header, the HMAC still validates against the attacker's own body, but the `shop` value handed to the app's business logic is the victim's — a cross-tenant identity mismatch introduced entirely within this gem's webhook-processing code, not by ignoring documented API contracts.

### Title
Webhook `shop`/`topic`/`webhook_id` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body. The `shop`, `topic`, and `webhook_id` values consumed by `Registry.process` and forwarded to app handlers via `WebhookMetadata` come solely from unauthenticated HTTP headers, so they are never bound to the HMAC signature that the gem treats as the request's authenticity proof.

### Finding Description
`Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) raises `InvalidWebhookError` unless `HmacValidator.validate(request)` succeeds, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` as authenticated tenant/event identifiers. But `HmacValidator.validate` only compares a computed HMAC over `to_signable_string`, which for `Webhooks::Request` is defined as `@raw_body` alone (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop`/`topic`/`webhook_id` accessors read straight from request headers (`lib/shopify_api/webhooks/request.rb:15-23`) with no cryptographic tie to the signature. Because the app's `client_secret` is shared across all shops that install the app, any shop owner (unprivileged internet user relative to other tenants) can capture a validly-signed webhook delivered to their own store and replay it to the app's public webhook endpoint with the shop/topic headers swapped to a victim's domain, producing a request that passes `HmacValidator.validate` yet misattributes the event to another tenant.

### Impact Explanation
This is a cross-tenant access primitive: an attacker with no relationship to the victim shop beyond both using the same app can cause the app to process arbitrary attacker-supplied webhook payloads as if they originated from the victim tenant, without ever touching the victim's access token, session, or credentials. Depending on what the app's webhook handlers do with `shop` (e.g., look up/mutate victim tenant records, trigger billing or fulfillment side effects), this can lead to data corruption or unauthorized actions scoped to another merchant.

### Likelihood Explanation
Requires only that the attacker be able to install the app on any shop (a normal, unprivileged action) and be able to send arbitrary HTTP requests to the app's public webhook endpoint URL — no secrets, tokens, or elevated access needed. This makes it a fairly easily reachable authentication-binding gap.

### Recommendation
Include the shop-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the signable content, or otherwise cryptographically bind them to the verified payload (e.g., verify that `shop` header matches an installation record independently authenticated via `access_token`/API lookups) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the target app on an attacker-controlled development store; Shopify delivers a legitimately HMAC-signed webhook (e.g. `orders/create`) to the app's endpoint with headers `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker captures the raw body and the valid `hmac-sha256` value.
3. Attacker sends a new POST request directly to the app's public webhook endpoint with the identical body and `hmac-sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body against the (unmodified) hmac (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: <attacker-controlled>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data under the victim's tenant identity.
