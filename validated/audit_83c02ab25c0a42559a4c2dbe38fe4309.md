### Title
Webhook `shop`/`topic` identity fields are unauthenticated by the HMAC check, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC only ever covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which the gem hands to the app's handler as the trusted identity of "which shop/topic this webhook is about" — come from HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC of `request` (i.e., of the body) and, on success, unconditionally forwards `request.shop` and `request.topic` to the registered handler as authoritative identity data: [4](#0-3) 

`HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the body) matches the HMAC — it says nothing about the headers: [5](#0-4) 

The documented integration pattern feeds `request.headers.to_h` straight from the raw HTTP request into `Request.new`, and the docs explicitly tell developers that `data.shop` is "the shop domain of the webhook" — i.e., the gem's own documentation instructs developers to trust this field as the tenant identifier: [6](#0-5) [7](#0-6) 

**Identity binding broken (equality that should hold but doesn't):**
`shop header authenticated-by-HMAC == shop value the handler trusts` is false. The gem only proves `HMAC(secret, raw_body) == received_hmac`; it never proves `HMAC(secret, raw_body + shop + topic) == received_hmac` or otherwise binds the shop/topic headers to the signed payload.

**Exploitation path:** An unprivileged internet user who is (or has ever been) a legitimate merchant/installer of the app receives genuine webhook deliveries containing a valid `(raw_body, x-shopify-hmac-sha256)` pair for their own shop. Because the HMAC never covers the `shop`, `topic`, or `webhook_id` headers, that same `(raw_body, hmac)` pair remains valid when replayed directly to the app's public webhook endpoint with attacker-chosen `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers. `Registry.process` will accept it (the HMAC check passes because the body/HMAC pair is genuinely valid) and hand the handler a `WebhookMetadata` claiming to be from a different shop or topic than actually produced the signed body.

### Impact Explanation
This crosses a tenant boundary: the app's handler is designed (per the gem's own docs) to key persistence/business logic off `data.shop` and `data.topic`. An attacker who controls the `shop`/`topic` headers, while supplying an unrelated but validly-signed body, can cause the handler to act as though the payload originated from an arbitrary victim shop (e.g., trigger `app/uninstalled`, `orders/create`, or other topic-specific side effects attributed to a shop the attacker doesn't control), or spoof `webhook_id` to defeat idempotency/duplicate-detection logic that other apps rely on for correctness. This satisfies the "cross-tenant access" Critical impact category, since the shop-scoped identity used by downstream business logic is forgeable without any Shopify- or victim-issued credential.

### Likelihood Explanation
Any internet user who has legitimate access to at least one real webhook delivery (trivial — install the target app on any development/test store, or on their own paid store) obtains a valid `(raw_body, hmac)` pair. The webhook HTTP endpoint is, by design, a public, unauthenticated endpoint (that is the entire point of webhook delivery), so replaying a POST with modified headers requires no special access, no TLS interception, and no leaked secret — only a normal HTTP client. Likelihood is high given the endpoint's necessarily public nature and the gem exposing header-derived identity fields as if they were authenticated.

### Recommendation
Extend `VerifiableQuery`/`HmacValidator` (or a webhook-specific validator) so that the signable string incorporates the identity-bearing headers (`shop`, `topic`, `webhook_id`) in addition to the raw body, or otherwise cryptographically bind them (e.g., include them in an HMAC computed over a canonical `header+body` structure). At minimum, document prominently that `data.shop`/`data.topic` are unauthenticated and must be cross-checked by the host application against a known, previously-registered shop/session before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. for `carts/update`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a direct POST to the app's public webhook endpoint (the same route registered via `ShopifyAPI::Webhooks::Registry.add_registration`) with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged, still valid since `HmacValidator.validate` only checks the body)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic: app/uninstalled` (forged, if the topic string, not the body shape, drives handler behavior)
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (they satisfy the required-header check), and `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `H` correctly matches `HMAC-SHA256(secret, B)`.
4. The handler registered for that topic executes with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to perform shop-scoped actions (e.g., deprovisioning, data deletion, or state changes) attributed to `victim-shop.myshopify.com` even though the victim shop never sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
