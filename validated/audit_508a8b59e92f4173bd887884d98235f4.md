### Title
Escrow balance decremented after external transfer in Tron `IntentGatewayV2.withdraw()`, reintroducing a CEI violation already fixed in the mainline contract - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()` in the Tron build of `IntentGatewayV2` performs the outbound token/native transfer to `beneficiary` **before** decrementing the per-token escrow accounting (`_orders[commitment][token]`). This is the same class of "external call before effects" ordering flagged in the reference report (external call precedes the state write that should have gated it). The mainline EVM implementation of the same logic, `IntentsBase._withdraw`, was already patched to apply checks-effects-interactions (CEI) — decrementing escrow *before* the transfer — and Hyperbridge even ships a dedicated regression suite (`IntrinsicIntentsReentrancyTest.sol`) proving exactly this bug class was found and fixed for `fillOrder`. The Tron contract's `withdraw()` was not updated to match.

### Finding Description
`withdraw()` sets `_filled[body.commitment]` up front (correct CEI for the "who redeemed" state), but for each escrowed token it does: [1](#0-0) 

```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;   // <-- effect happens AFTER the external call
```

Compare this to the mainline, already-hardened version, which decrements the escrow slot **before** transferring: [2](#0-1) 

Because `token` and `beneficiary` both originate from attacker-controlled input — the token address comes from `order.inputs` (user-supplied at `placeOrder`), and for the `RefundEscrow` path `beneficiary` is `order.user` itself, i.e. the attacker's own address — an attacker can supply a malicious ERC20 contract (or, for refunds, a malicious `beneficiary` contract that receives the native-token branch directly) whose `transfer`/`receive` hook executes arbitrary code while `_orders[body.commitment][token]` still reflects the pre-transfer (stale) escrow balance.

`withdraw()` itself is only reachable through the `onlyHost`-gated `onAccept`/`onGetResponse` entry points, and `EvmHost.dispatchIncoming` writes its own replay-protection receipt before invoking the module callback, which blocks a trivial re-entry into the *exact same* delivered message. This materially limits — but, given the time available for this analysis, does not conclusively rule out — a path back into a state read of the stale `_orders[commitment][token]` value from other externally-reachable, non-`onlyHost` functions on the same contract (e.g. `cancelOrder`) during the reentrant callback.

### Impact Explanation
If a reachable path exists back into logic that consumes the stale (not-yet-decremented) `_orders[commitment][token]` value, the result is a double-spend of escrowed input tokens/native currency — direct theft of user funds held by the Tron `IntentGatewayV2` deployment. Even absent a full double-spend, this is a structural CEI violation identical to a bug class Hyperbridge already treated as security-relevant and fixed elsewhere, so it represents unnecessary residual risk in a contract that handles escrowed user funds.

### Likelihood Explanation
Medium. The attacker fully controls the ingredients needed to trigger the callback (a malicious token contract listed as an order input, or, for refunds, a malicious `beneficiary`/`order.user` contract), since these are supplied by the order creator at `placeOrder` time. The main uncertainty — and the reason this is not rated Critical outright — is that the only functions that invoke `withdraw()` are gated `onlyHost`, and the host's own receipt bookkeeping already blocks straightforward re-delivery of the identical message; a concrete secondary read-path exploiting the stale escrow value was not fully confirmed within this review and would need dedicated fuzzing/PoC against `cancelOrder` and any other function reading `_orders[commitment][token]`.

### Recommendation
Apply the same CEI fix used in `IntentsBase._withdraw` to the Tron `IntentGatewayV2.withdraw()`: decrement `_orders[body.commitment][token]` (and clear `TRANSACTION_FEES`) **before** performing the `.call`/`safeTransfer` to `beneficiary`, for every token in the loop. Add a regression test mirroring `IntrinsicIntentsReentrancyTest.sol` targeting the Tron contract to lock in the fix.

### Proof of Concept
Not independently reproduced against a live reentrant callback path in this review (tool budget exhausted before confirming a concrete secondary read of the stale escrow slot). The structural defect — external transfer call preceding the `_orders[...] -= amount` state update — is directly demonstrated by the code excerpt above and by diffing against the already-CEI-hardened mainline `IntentsBase._withdraw`.
