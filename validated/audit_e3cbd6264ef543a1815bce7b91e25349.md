### Title
Simplex `FXFiller` venue pricing trusts the raw, un-timeweighted Uniswap V4 pool mid-price for intent order fills, allowing flashloan/same-block manipulation of the fill rate - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
When a Simplex trading pair has no static bid/ask curves, `FXFiller` prices cross-asset intent orders directly from the live Uniswap V4 pool's instantaneous `sqrtPriceX96` mid, with no TWAP and no execution-size/fee adjustment. The only defense is an *optional* static `referencePrice` / `maxDeviationBps` guard that a filler operator may or may not configure. This reproduces the exact bug class in the referenced report: a spot on-chain reserve/price is used directly to value an asset for a payout decision, making it manipulable within a single transaction (flashloan or self-funded swap) to extract value from the solver at settlement.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` picks the most-liquid configured position and returns `computeDirectPoolPriceUsd`'s raw pool mid derived from `sqrtPriceX96`: [1](#0-0) 

As documented, this price is a naive spot read with no size/impact term and the pool's own fee tier is never applied: [2](#0-1) 

`FXFiller.resolveLegRates` consumes this venue quote directly as the fill rate for the order leg (`rate = 1 / venueUsd`), used to compute how much of the exotic token the solver delivers or accepts: [3](#0-2) 

The only mitigation is `checkPriceGuard`, which compares the quote to a static, operator-configured `referencePrice` within `maxDeviationBps`. This guard is explicitly optional ("omit both to leave the chain unguarded") and is checked with `guard.reference.lte(0)` / absence returning `true` (pass): [4](#0-3) [5](#0-4) 

Even when configured, the guard only bounds *deviation from a static reference*, not manipulation happening within that band, and does not account for the price impact/fees a real swap through that same pool would incur when the solver later has to source inventory: [2](#0-1) 

This is structurally identical to the LP pricing formula bug in the original report: an unprivileged actor (here, an intent order submitter) can move the on-chain price used as a valuation oracle within the same transaction/block (via a swap against the very pool being read, funded by a flashloan or the attacker's own capital), causing the solver's fill logic to compute a favorable-to-attacker exchange rate, then reverse the manipulating swap to recover most of the capital.

### Impact Explanation
An attacker who identifies a venue-priced pair (no static curve, `[vault.uniswapV4]` position configured, especially one without `referencePrice`/`maxDeviationBps`, or with a wide band) can:
1. Swap into the underlying Uniswap V4 pool to push `sqrtPriceX96` in the direction that inflates the exotic token's apparent USD value (or depresses the solver's asking price).
2. Submit an intent order for Simplex to fill at that manipulated rate; the `FXFiller` uses the live pool mid unadjusted for size/fees as the fill rate.
3. Reverse the manipulating swap afterward, paying only pool fees/slippage.

This causes the solver's vault to overpay (deliver more output tokens than the true value received) — a direct, concrete theft of solver funds, satisfying "concrete theft ... of funds" in scope.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a venue-priced pair configured without a tight/enabled price guard, and (b) sufficiently thin liquidity in the referenced Uniswap V4 position relative to what an attacker can flashloan/self-fund to move the tick meaningfully within the guard's tolerance (or when no guard exists at all). Given the guard is optional per-position and per the docs many operators may run "unguarded" chains, and given the pricing explicitly has no size/impact term, this is a realistic operational misconfiguration risk directly analogous to the audited Behodler finding, not a purely theoretical one.

### Recommendation
- Make the Uniswap venue price guard (`referencePrice` + `maxDeviationBps`) mandatory rather than optional whenever `[vault.uniswapV4]` pool pricing is used for a pair.
- Replace or supplement the instantaneous `sqrtPriceX96` mid with a manipulation-resistant price: a TWAP/observation-based oracle, or cross-checking against an independent off-chain price feed before accepting a fill.
- Incorporate the pool's real fee tier and a size/impact term into `computeDirectPoolPriceUsd`/`computeLegPolicyOutput` so the priced notional reflects the cost of actually sourcing/redeeming that liquidity, consistent with Alpha Finance's fair-pricing recommendation from the referenced report.
- Consider rejecting fills when the venue pool's liquidity is below a minimum threshold relative to the order notional, reducing the capital required for an attacker to move price meaningfully.

### Proof of Concept
1. Configure (or discover) a Simplex `[[pairs]]` entry priced purely from `[vault.uniswapV4]` (no curves) for a chain, e.g. `USDC/CNGN` on `EVM-8453`, with either no `referencePrice`/`maxDeviationBps` guard or a wide one.
2. Attacker takes a flashloan of USDC (or the paired quote token) and swaps into the referenced Uniswap V4 position's pool to shift `sqrtPriceX96`, moving the token1-per-USD mid by up to the guard's `maxDeviationBps` (or unboundedly if unguarded).
3. Attacker immediately submits/fills an intent order sized so that `FXFiller.resolveLegRates` → `checkPriceGuard` accepts the manipulated venue quote (`getExoticTokenPrice` → `computeDirectPoolPriceUsd`), obtaining an exchange rate more favorable than the pool's true equilibrium price.
4. Solver's `UniswapV4FundingPlanner` withdraws liquidity/delivers the exotic token to fill the order at the manipulated rate.
5. Attacker reverses the initial swap, repays the flashloan, and nets the difference between the manipulated fill rate and the pool's fair value, at the cost of swap fees only — mirroring the referenced Behodler `burnAsset` LP-price manipulation exactly, applied to Simplex's Uniswap V4 venue pricing path.

		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.
```
