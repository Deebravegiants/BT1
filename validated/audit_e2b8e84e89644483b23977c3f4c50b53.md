I found a concrete analog to the reported bug class (missing minimum-value validation during pool initialization leading to unexpected degenerate pool state with locked/frozen user funds).

### Title
Missing minimum-liquidity check in `process_initialize2` allows initial depositor to receive zero LP tokens, permanently freezing their deposited funds - (File: `program/src/processor.rs`)

### Summary
`Initialize2` computes the initial LP amount to mint to the pool creator using a `checked_sub` that only guards against *underflow*, not against the result being exactly zero. This is the same bug class as the reported issue: a missing **minimum** bound check (there, `minProtectionDurationInSeconds`; here, the minimum initial LP amount) lets a pool be created in a degenerate state that harms the depositor.

### Finding Description
In `Processor::process_initialize2`, after the coin/pc vaults are funded via `Invokers::token_transfer` with attacker-supplied `init.init_coin_amount` and `init.init_pc_amount`, the program computes the pool's initial liquidity and the LP amount to mint to the depositor: [1](#0-0) 

```
let liquidity = Calculator::to_u64(
    U128::from(amm_pc_vault.amount)
        .checked_mul(amm_coin_vault.amount.into())
        .unwrap()
        .integer_sqrt()
        .as_u128(),
)?;
let user_lp_amount = liquidity
    .checked_sub((10u64).checked_pow(lp_mint.decimals.into()).unwrap())
    .ok_or(AmmError::InitLpAmountTooLess)?;
...
Invokers::token_mint_to(..., user_lp_amount)?;
```

The only guard here is `checked_sub(...).ok_or(...)`, which only fails when `liquidity < 10^decimals` (i.e., prevents *underflow*). It does **not** enforce `liquidity > 10^decimals`. If the caller supplies `init_coin_amount`/`init_pc_amount` such that `sqrt(coin_amount * pc_amount) == 10^lp_decimals` exactly, `user_lp_amount` evaluates to exactly `0`, which passes the check (as `Some(0)`), and `Invokers::token_mint_to` is called to mint `0` LP tokens — a valid, no-op SPL Token mint call that does not fail.

The two prior checks only reject a *zero* vault balance: [2](#0-1) [3](#0-2) 

Neither of these, nor the LP-amount subtraction, prevents the specific "liquidity == 10^decimals" edge case from producing zero LP tokens.

Because `Initialize2` is callable by any unprivileged user with attacker-chosen accounts and instruction data (no signer other than the caller/depositor themselves), an attacker can deliberately choose `init_coin_amount` and `init_pc_amount` so that this boundary is hit exactly.

### Impact Explanation
When `user_lp_amount == 0`, the initial `init_coin_amount` and `init_pc_amount` tokens are transferred into the pool's coin/pc vaults (owned by the pool's PDA authority), but the depositor is minted **zero** LP tokens. Since withdrawal (`process_withdraw`) is gated by burning LP tokens proportional to the withdrawn share, there is no LP supply outstanding to redeem this locked liquidity — the deposited tokens become permanently unbacked and unrecoverable by anyone. This is a "permanent freezing of user funds" and also results in an insolvent/unbacked liquidity state for the pool (vault balances exceed the LP supply's backing), directly matching the accepted impact categories.

Additionally, because the AMM/target-orders/vault PDAs are derived deterministically from the `market`, `coin_mint`, and `pc_mint` (see `generate_amm_associated_account`/`generate_amm_associated_spl_token` calls at lines 748-814), only one pool can ever be initialized for a given market/mint combination — an attacker triggering this degenerate initialization also permanently prevents a legitimate, correctly-funded pool from ever being created for that pair (`AmmError::AlreadyInUse` on any retry).

### Likelihood Explanation
The attacker needs only to call `Initialize2` (unprivileged, single transaction) with self-chosen `init_coin_amount`/`init_pc_amount` values satisfying `sqrt(init_coin_amount * init_pc_amount) == 10^lp_mint.decimals`, which is trivial to compute given the mint decimals are public and readable in advance (e.g., for 6-decimal mints, `init_coin_amount = init_pc_amount = 1_000_000`). No race condition, privileged role, or off-chain component is required.

### Proof of Concept
1. Choose a coin mint and pc mint with the same/known decimals `d` (e.g., `d = 6`).
2. Submit `Initialize2` with `init_coin_amount = 1_000_000` and `init_pc_amount = 1_000_000` (so `liquidity = sqrt(1e6 * 1e6) = 1_000_000 = 10^6`).
3. `user_lp_amount = liquidity - 10^d = 1_000_000 - 1_000_000 = 0`, which is `Some(0)`, so the `ok_or` check passes.
4. `Invokers::token_mint_to` mints `0` LP tokens to the depositor's ATA — a valid CPI, does not error.
5. `amm.lp_amount = liquidity` (`1_000_000`) is recorded in state, but total LP supply outstanding is `0`.
6. The 1,000,000 coin and 1,000,000 pc tokens deposited into the vaults are now permanently locked: no LP token exists anywhere that can be burned via `process_withdraw` to reclaim any portion of them, and the pool (keyed to this specific market/mint combination) cannot be re-initialized to fix the state.

### Recommendation
Change the check from `checked_sub(...).ok_or(...)` to explicitly require `user_lp_amount > 0` (e.g., require `liquidity > 10^decimals`, not `>=`), rejecting the transaction with `AmmError::InitLpAmountTooLess` when the resulting LP mint amount would be zero.
