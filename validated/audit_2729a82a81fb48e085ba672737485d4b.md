### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` for HMAC validation, but its `to_signable_string` returns only the raw request body [1](#0-0) , while the `shop` accessor used to identify the tenant is read directly from the unauthenticated `shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates the HMAC and then forwards `request.shop` straight into the handler as the tenant identity, without the shop ever being part of the signed payload [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop-domain header == the shop the HMAC-signed body actually belongs to`. Because `HmacValidator.validate` only checks `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is derived from `verifiable_query.to_signable_string` [4](#0-3) , and for webhooks that signable string is just `@raw_body` [1](#0-0) , the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are all excluded from what is actually authenticated. Only the byte-for-byte body content is verified, not the header-derived tenant/topic metadata that is subsequently trusted and acted upon.

This differs from the OAuth callback path in the same gem, where `AuthQuery#to_signable_string` explicitly includes `shop`, `host`, `code`, `state`, and `timestamp` in the signed content [5](#0-4) , correctly binding the shop identity to the HMAC. The webhook path lacks the equivalent binding.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (an unprivileged internet user with respect to any other merchant) will receive real, validly-signed webhooks from Shopify for their own shop, with a correct HMAC over the body. Because the HMAC never covers the `shop-domain` header, the attacker can replay that captured request to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain; `Utils::HmacValidator.validate(request)` still returns `true` because it only re-derives the signature from `@raw_body`, and `Registry.process` will invoke the handler with `WebhookMetadata` claiming the victim shop `shop: request.shop` [6](#0-5) . Any host application that trusts `data.shop` from `WebhookMetadata` to select the tenant record to update (the officially documented usage pattern) will apply attacker-controlled webhook body content under an arbitrary victim shop's identity — a cross-tenant data-injection/spoofing primitive reachable purely from the confirmed HMAC-valid status the gem reports.

### Likelihood Explanation
Any developer/merchant who can install the app once (a normal, unprivileged flow) can obtain a validly HMAC-signed webhook of a chosen topic and body, and only needs to modify one plaintext HTTP header before resending it to the app's public webhook endpoint. No secrets, tokens or elevated access are required beyond becoming an ordinary app user.

### Recommendation
Include the tenant-identifying header(s) (`shop-domain`, and ideally `topic`/`webhook-id`) inside the signed content evaluated by `to_signable_string`, or independently verify that `request.shop` matches an expected/known shop for the given API credentials before dispatching to the handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used as a trusted tenant selector.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture an incoming webhook request, e.g. `orders/create`, with headers `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, and body `raw_body`.
2. Verify locally: `hmac == Digest.hexencode(Base64.decode64(header)) == HMAC-SHA256(api_secret_key, raw_body)` — this matches regardless of the `shop-domain` header value, since `to_signable_string` returns only `raw_body` [1](#0-0) .
3. Resend the identical request to the app's webhook endpoint, replacing only `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which returns `true` (body unchanged) [7](#0-6) , then invokes `handler.handle` with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: <attacker's body> ...)` [6](#0-5) , causing the host application to process attacker-supplied data attributed to the victim shop.
