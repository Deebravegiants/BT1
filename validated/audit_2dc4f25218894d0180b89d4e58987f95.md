### Title
LDAP/Local/OIDC session login returns distinguishable error messages enabling user enumeration - (File: core/sessions/ldapauth/ldap.go)

### Summary
The `/sessions` `POST` endpoint (`SessionsController.Create`) forwards the raw error from `AuthenticationProvider().CreateSession` straight to the HTTP client via `jsonAPIError`, which serializes `err.Error()` into the JSON response body. All three authentication providers (`ldapauth`, `localauth`, `oidcauth`) return content-distinguishable error strings depending on whether the submitted email corresponds to an existing account, mirroring the exact bug class described in CVE-2023-3462 (HashiCorp Vault LDAP user enumeration).

### Finding Description
`SessionsController.Create` calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and, on failure, passes the returned `error` unmodified to `jsonAPIError(c, http.StatusUnauthorized, err)`, which JSON-encodes `err.Error()` back to the caller. [2](#0-1) 

For the local authentication provider (`core/sessions/localauth/orm.go`), `CreateSession` returns `"Invalid email"` when the account does not exist (or a lookup error is returned by `FindUser`), but `"Invalid password"` when the account exists and only the password is wrong: [3](#0-2) 

The OIDC provider's local-login fallback (`localLoginFallback` in `core/sessions/oidcauth/oidc.go`) exhibits the identical pattern, returning `"invalid email"` vs `"invalid password"`: [4](#0-3) 

The LDAP provider's local fallback (`localLoginFallback` in `core/sessions/ldapauth/ldap.go`) also distinguishes `"invalid email"` from `"invalid password"`: [5](#0-4) 

Additionally, `ldapAuthenticator.CreateSession` itself produces multiple distinguishable messages depending on whether the bind succeeded and whether the user had assigned groups: `"unable to log in with LDAP server. Check credentials"` vs `"log in successful, but no assigned groups to assume role"` (the latter only reachable when the account/password pair is valid), before falling through to the local fallback which further distinguishes invalid email vs invalid password: [6](#0-5) 

An unprivileged, unauthenticated attacker hitting the `/sessions` endpoint can therefore submit a candidate email with an arbitrary password and directly read back from the HTTP response body whether the error was `"Invalid email"`/`"invalid email"` (account does not exist) or `"Invalid password"`/`"invalid password"`/the LDAP-groups message (account exists), which is precisely the LDAP-based user-enumeration oracle from GHSA-9v3w-w2jh-4hff / CVE-2023-3462.

### Impact Explanation
This allows any unauthenticated network client to enumerate valid Chainlink node operator account emails (whether backed by local DB, LDAP, or OIDC-fallback auth) by observing the JSON error message content returned from a single unauthenticated `POST /sessions` request per candidate email. Confirmed valid accounts are higher-value targets for subsequent credential-stuffing, phishing, or brute-force attacks against the node's admin/API interface. This matches CWE-203 (Observable Discrepancy) and the Medium severity classification of the referenced advisory, since it discloses account existence but does not itself grant access.

### Likelihood Explanation
Likelihood is high: the endpoint is unauthenticated by design (it's the login endpoint), requires no special network position, and the discrepancy is a static string difference always present in the JSON response body (not merely a timing side channel), making it trivially scriptable.

### Recommendation
Normalize all authentication failure messages returned from `CreateSession` (local, LDAP, and OIDC fallback) to a single generic string (e.g., `"invalid credentials"`) regardless of whether the account exists, the password is wrong, LDAP bind failed, or group mapping failed — mirroring the internal detailed error only in server-side audit logs (which is already partially done via `auditLogger.Audit(...)`). Ensure `jsonAPIError` for the `/sessions` `Create` handler does not leak the underlying provider error text to the client at all, similarly to how other truly generic-error paths are already handled.

### Proof of Concept
1. As an unauthenticated client, `POST /sessions` with `{"email":"knownadmin@example.com","password":"wrong"}`.
2. Observe the JSON response body contains `"Invalid password"` (local) / `"invalid password"` (OIDC/LDAP fallback), or the LDAP-specific `"log in successful, but no assigned groups to assume role"` message.
3. `POST /sessions` with `{"email":"doesnotexist@example.com","password":"wrong"}`.
4. Observe the JSON response body instead contains `"Invalid email"` / `"invalid email"` / `"unable to log in with LDAP server. Check credentials"`.
5. The differing message content (returned in every request, not requiring timing analysis) allows automated enumeration of valid account emails against the target node. [7](#0-6)

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {

	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {

		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}
