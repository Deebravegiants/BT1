### Title
Webhook HMAC does not cover the `shop`, `topic`, `webhook_id`, or `api_version` headers, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` only authenticates the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are read straight from attacker-influenceable headers and then handed to the app's handler as the tenant/shop identity — are never covered by the HMAC. This breaks the intended binding `hmac == sign(body ‖ shop ‖ topic)`; in this gem it is actually `hmac == sign(body)` only, with `shop` completely unauthenticated.

### Finding Description
`Request#hmac` reads the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Registry.process` validates the request purely through `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the received HMAC: [2](#0-1) 

After that single check passes, `Registry.process` immediately forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all sourced from HTTP headers that are not part of the signed string — into `WebhookMetadata`, which the host app's handler uses to identify which merchant/tenant the webhook belongs to: [3](#0-2) 

Because the HMAC only binds the JSON body, any request that reuses a body/HMAC pair that was legitimately generated by the app's own secret for the attacker's own shop — but with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header swapped to point at a different, victim shop — still passes `HmacValidator.validate`. The identity binding the equality check is supposed to enforce is:

`hmac_received == HMAC(secret, body)` **and separately** `shop_used_by_handler == shop_that_actually_sent_the_request`

but the gem only verifies the first half; the second is asserted without any cryptographic proof. An unprivileged user who can install the app on their own store (a normal, unprivileged onboarding action requiring no leaked credentials) legitimately receives real `(raw_body, hmac)` pairs signed with the app's `client_secret`/webhook secret for their own shop's webhooks. They can then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop domain. `HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` calls the handler with `shop: <victim shop>` while `body` is attacker-controlled content signed only for the attacker's own tenant.

### Impact Explanation
This crosses a tenant boundary: the app's webhook handler executes business logic (e.g., updating merchant records, triggering redact/data-request flows, syncing order/product data) attributing attacker-chosen body content to a victim shop, i.e., cross-tenant access/data confusion driven by an unauthenticated field. This matches the Critical "cross-tenant access" impact category, since the shop identity used by the host application for authorization/lookup is not actually authenticated by the HMAC check this gem performs.

### Likelihood Explanation
Any user who can install the target app on their own development/test store obtains valid `(body, hmac)` pairs signed by the real app secret without needing to steal any credentials. The webhook endpoint is by design internet-reachable and unauthenticated apart from the HMAC check. Forging the `shop-domain`/`topic`/`webhook-id` headers on an HTTP request is trivial for any client. The only constraint is that the replayed request must expose the same topic-shaped body already accepted for that topic — which is easy to satisfy since the attacker fully controls their own store's webhook content (e.g., renaming a product, creating an order) before capturing the resulting signed payload.

### Recommendation
Include the identity-critical headers (`shop-domain` and `topic`, and ideally `webhook-id`) in the HMAC-signable string in `Request#to_signable_string`, or otherwise cryptographically bind them (e.g., by validating that the shop present in the parsed body, when present, matches the header, and rejecting mismatches). At minimum, document that the `shop` header is unauthenticated so host applications should not trust it for authorization decisions without independent verification (e.g., matching it against a previously stored, authenticated shop/session record) rather than passing it straight into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and configures a webhook subscription.
2. Attacker triggers an event (e.g., `products/update`) on their own store, capturing the raw POST body Shopify sends plus the valid `x-shopify-hmac-sha256` header (signed with the app's real secret).
3. Attacker replays this exact `raw_body` to the app's public webhook endpoint but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`), keeping the original `x-shopify-hmac-sha256` header untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body`, so validation succeeds: [4](#0-3) 
5. The registered handler executes with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, even though the request never actually originated from, or was authenticated for, that shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
