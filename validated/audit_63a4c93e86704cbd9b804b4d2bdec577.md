### Title
Webhook `shop-domain` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) and event type (`topic`) from raw HTTP headers, but `Utils::HmacValidator.validate` only ever authenticates the raw request body via `to_signable_string`, which returns `@raw_body` alone. This breaks the identity binding: `HMAC(secret, body) == valid` should imply `(shop, topic, body)` is authentic, but the gem only proves `body` is authentic, not `shop` or `topic`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates on the body HMAC only: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values consumed and forwarded to the app's handler come straight from headers: [2](#0-1) 

But the HMAC is computed only over the raw body: [3](#0-2) 

and `HmacValidator.validate` simply recomputes `HMAC(secret, to_signable_string)` and compares it to the header `hmac`: [4](#0-3) 

Because all shops on a public app share the same `api_secret_key`, and the signature never binds to `shop-domain` or `topic`, an attacker who has legitimately received one valid `(raw_body, hmac)` pair (e.g., by installing the app on their own store, triggering any webhook event for their own tenant) can replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (impersonating a different, victim tenant) and/or a different `shopify-topic` header (impersonating a different, more sensitive event). `HmacValidator.validate` still returns `true` because the body and hmac are untouched and match, and `Registry.process` dispatches the forged event to the handler for the spoofed topic, passing the spoofed shop into `WebhookMetadata`: [5](#0-4) 

The identity binding that should hold is: `authenticated(shop, topic, body) == HMAC-verified(shop, topic, body)`. In this code, it degrades to `HMAC-verified(body)` only, so `shop` and `topic` are trusted without being cryptographically bound to the signature — matching the "field acted on but not covered by the HMAC" bug class.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to select the tenant context (session/store lookup, DB writes, cache keys) or `WebhookMetadata#topic` to select business logic will process a forged event as if it legitimately originated from an arbitrary victim shop and/or arbitrary topic, despite passing the gem's HMAC check. This is a cross-tenant data-integrity break: an attacker who only needs to obtain one legitimately-signed webhook for their own store (a trivial unprivileged action — installing the app) can cause the receiving app to attribute an event to a different merchant's shop. This maps to the "cross-tenant access" impact category.

### Likelihood Explanation
Requires no access to `api_secret_key`, no privileged account, and no token theft — only the ability to install the app (or otherwise legitimately receive one webhook delivery) to capture a valid `(raw_body, hmac)` pair, and the ability to POST directly to the app's public webhook endpoint with altered headers. The webhook endpoint is, by design, a public HTTP endpoint that only relies on this HMAC check for authentication, so likelihood is realistic for any determined unprivileged actor.

### Recommendation
Bind the identity fields into the signed material, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body:
- Include `shop-domain`, `topic`, and `webhook_id` header values as part of the string passed to `HmacValidator` (e.g., concatenate them with the body before computing/verifying the HMAC), matching how `Auth::Oauth::AuthQuery#to_signable_string` binds all identity-relevant fields.
- Alternatively, cross-check the delivered `shop` against a session/store already known to the app for that specific `webhook_id`/subscription before processing, rather than trusting the header value outright.
- Document clearly (and enforce in code) that `WebhookMetadata#shop` and `#topic` must not be treated as authenticated unless additionally bound to the signature.

### Proof of Concept
1. Install the target public app on attacker-controlled store `attacker.myshopify.com`; capture a legitimately delivered webhook request, e.g. topic `carts/update`, headers:
   - `X-Shopify-Topic: carts/update`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`
   - body: `{"id": 1, ...}`
2. Replay the exact same body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but change:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: <any other registered topic the app handles>`
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers because they satisfy the presence check only: [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (unchanged) and succeeds, then dispatches `handler.handle(data: WebhookMetadata.new(topic: "<spoofed-topic>", shop: "victim.myshopify.com", ...))`, causing the app to act on a forged tenant/topic combination that never actually occurred for `victim.myshopify.com`.
