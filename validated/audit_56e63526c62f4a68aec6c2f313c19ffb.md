## Title
Webhook HMAC does not bind the `shop`/`topic` identity headers, enabling cross-tenant webhook forgery — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the HMAC exclusively over that body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never included in the signed content. Any actor who can obtain a single valid `(body, hmac)` pair — trivially available to anyone who installs the app on their own store and receives one legitimate webhook — can replay that exact body/hmac to the app's public webhook endpoint while forging the `shop-domain` (and `topic`) headers to name a different, victim shop. The library will accept the signature as valid and hand the attacker-controlled body to the app's handler labeled as coming from the victim shop.

### Finding Description
The identity binding that should hold is:
`shop_the_HMAC_was_computed_for == shop_the_library_attributes_the_webhook_to`

In this gem that binding is broken:

- `Request#to_signable_string` signs only the body: [1](#0-0) 

- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are parsed directly from headers, with no cryptographic tie to the body that was actually signed: [2](#0-1) 

- `Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [3](#0-2) 

- `Registry.process` gates on that same body-only HMAC check, then trusts the header-derived `request.shop` / `request.topic` to build the metadata handed to the app's handler: [4](#0-3) 

Because the shop and topic are never part of the signed bytes, a valid `(raw_body, hmac)` pair generated for one shop/topic is equally "valid" for any other shop/topic an attacker chooses to put in the headers when POSTing to the same public webhook endpoint.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (a free, unprivileged action requiring no credentials belonging to the victim) receives real webhooks containing bodies that are, in part, attacker-controlled (product titles, customer fields, order notes, metafields, etc., depending on subscribed topic). By capturing one such genuine `(body, hmac)` pair, the attacker can POST it directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop (and optionally a forged topic header). `HmacValidator.validate` passes because it only checks the body, and `Registry.process` dispatches the attacker-controlled payload to the handler labeled as the victim shop's data. This is a cross-tenant identity confusion: data attributed to shop A is actually attacker-supplied data from shop A being falsely presented, at will, as belonging to shop B, with no interaction from shop B required. Depending on how the host app's webhook handlers use `shop`/`body` (e.g., updating shop-scoped records, triggering `app/uninstalled` cleanup, GDPR data handling), this can result in cross-tenant data injection or corruption.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining a valid signed webhook is as easy as installing the (often public/free) app once, and the webhook endpoint is by design a public, unauthenticated internet-facing URL. No secret, token, or victim interaction is required — only the ability to install the app once and control some content in one's own store data that ends up in a webhook body.

### Recommendation
Include the shop domain, topic, and webhook id in the signed/verified material — e.g., compute/verify the HMAC over a canonical string that binds `shop-domain`, `topic`, `webhook-id`, and body together (or independently verify that the shop domain in the header matches a shop known/authorized for this webhook subscription) rather than relying on the raw body alone in `Request#to_signable_string`.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and subscribes it to `products/update`.
2. Attacker edits a product's title to a value that becomes part of the webhook JSON body; Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: products/update`, and a valid `X-Shopify-Hmac-Sha256` computed over that JSON body.
3. Attacker captures this `(raw_body, hmac)` pair (e.g., via their own reverse proxy/logging on their own webhook receiver, or by running the same app code themselves against the same endpoint if self-hosted/testing).
4. Attacker sends a new POST directly to the app's public webhook endpoint reusing the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds (body/hmac match), and `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and the attacker-controlled body — despite the signature never having certified anything about `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
