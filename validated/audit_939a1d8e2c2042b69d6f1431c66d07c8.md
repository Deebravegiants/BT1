### Title
Rounding drift in `calc_pnl_x`/`calc_pnl_y` can make `calc_take_pnl` permanently revert, freezing all deposits and withdrawals - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` enforces an invariant that the pool's current value (`total_pc_without_take_pnl * total_coin_without_take_pnl`) must be `>=` the previously recorded reference value (`target.calc_pnl_x`/`calc_pnl_y` restored to native decimals). Every unprivileged `Deposit` and `Withdraw` call invokes this function unconditionally (outside of the admin-only `WithdrawOnly` status), and if the invariant check fails once, `AmmError::CalcPnlError` is returned and the transaction reverts before `calc_pnl_x`/`calc_pnl_y` can be re-synchronized — permanently blocking every future deposit and withdraw.

### Finding Description
`calc_take_pnl` compares `pool_pc_amount * pool_coin_amount` against `calc_pc_amount * calc_coin_amount` (the latter restored from the persisted `target.calc_pnl_x` / `target.calc_pnl_y`), and reverts with `AmmError::CalcPnlError` whenever the pool's current product is smaller: [1](#0-0) 

This function is called unconditionally in `process_deposit`: [2](#0-1) 

and in `process_withdraw` (only skipped when `amm.status == WithdrawOnly`, an admin-controlled status unreachable by regular users): [3](#0-2) 

and in `process_withdrawpnl`: [4](#0-3) 

`calc_pnl_x`/`calc_pnl_y` are only ever updated *after* `calc_take_pnl` succeeds, using `normalize_decimal_v2`/`restore_decimal`, both of which perform floor (truncating) division: [5](#0-4) 

In `process_withdraw`, the post-operation reference value is updated by *subtracting* the floor-rounded normalized withdrawn amount from the pre-operation normalized total: [6](#0-5) 

Because the amount subtracted is floor-rounded (i.e. rounded down), `calc_pnl_x`/`calc_pnl_y` end up slightly *overstating* the true remaining pool value relative to `total_pc_without_take_pnl`/`total_coin_without_take_pnl` after each withdrawal. This rounding bias accumulates over repeated, ordinary user-initiated withdrawals. Once accumulated drift is large enough that `restore_decimal(calc_pnl_x) * restore_decimal(calc_pnl_y) > total_pc_without_take_pnl * total_coin_without_take_pnl`, `calc_take_pnl` will revert on every subsequent call — and since the only code path that could realign `calc_pnl_x`/`calc_pnl_y` with reality is gated behind a successful `calc_take_pnl` call, the pool becomes permanently stuck: no further `Deposit`, `Withdraw`, or `WithdrawPnl` can succeed.

This mirrors the structure of the BigBang `debtStartPoint` bug: a stale/incorrectly-tracked invariant (`debtStartPoint` in BigBang, `calc_pnl_x`/`calc_pnl_y` here) is checked inside a helper (`getDebtRate()`/`calc_take_pnl()`) that is invoked from every state-mutating entrypoint, and once the check fails there is no remaining path to repair the invariant, permanently freezing user funds.

### Impact Explanation
Once triggered, this locks all LP funds in the affected pool: `Deposit` and `Withdraw` (the only ways to add/remove liquidity and reclaim LP tokens' underlying assets) both revert unconditionally through `calc_take_pnl`. LP holders cannot redeem their share of `coin`/`pc` tokens, and the `pnl_owner` can no longer collect protocol PnL via `withdrawpnl`. Only `swap_base_in`/`swap_base_out` (which do not call `calc_take_pnl`) remain functional, so trading continues but LP capital becomes permanently frozen — a critical, unrecoverable loss-of-funds condition for liquidity providers.

### Likelihood Explanation
This requires no privileged action or malicious input — it can occur through purely benign, repeated `Withdraw` calls due to the floor-rounding bias in `normalize_decimal_v2`/`restore_decimal` used to update `calc_pnl_x`/`calc_pnl_y`. The drift accumulates monotonically in one direction per withdrawal, so given enough withdrawal activity over the life of a pool (especially pools with mismatched `pc_decimals`/`coin_decimals` and low `sys_decimal_value` precision, which amplify rounding loss), the invariant flip is a matter of when, not if. This is a Medium-to-High likelihood issue reachable purely through normal LP withdrawal activity from unprivileged accounts.

### Recommendation
- Update `target.calc_pnl_x`/`calc_pnl_y` using ceiling (rounding up) when subtracting withdrawn amounts (mirroring `RoundDirection::Ceiling` used elsewhere for user-favorable rounding), so tracked reference value never overstates true remaining pool value.
- Alternatively, remove the hard revert in `calc_take_pnl`'s `else` branch (lines 267-277) and instead skip PnL-taking (treat `delta_x = delta_y = 0`) when the invariant momentarily doesn't hold, allowing deposit/withdraw to proceed and self-correct `calc_pnl_x`/`calc_pnl_y` rather than reverting and leaving the stale state permanently unrepairable.
- Add invariant self-healing: if `calc_take_pnl`'s check fails, resynchronize `target.calc_pnl_x`/`calc_pnl_y` to the current pool state (`x1`,`y1`) instead of erroring out.

### Proof of Concept
1. Initialize a pool with `pc_decimals` and `coin_decimals` set to induce maximal rounding loss relative to `sys_decimal_value` (e.g. large decimal gap), via `process_initialize2`.
2. Repeatedly call `process_deposit` followed by `process_withdraw` with amounts chosen so the floor-rounding in `normalize_decimal_v2`/`restore_decimal` (`program/src/math.rs:96-116`) consistently truncates the subtracted term in the `target_orders.calc_pnl_x`/`calc_pnl_y` update at `program/src/processor.rs:1818-1838`.
3. After sufficient iterations, `restore_decimal(target.calc_pnl_x) * restore_decimal(target.calc_pnl_y)` exceeds `total_pc_without_take_pnl * total_coin_without_take_pnl`.
4. The next call to `process_deposit`/`process_withdraw`/`process_withdrawpnl` invokes `calc_take_pnl` (`program/src/processor.rs:190-277`), the `if` condition fails, and `AmmError::CalcPnlError` is returned — reverting the transaction and leaving `target.calc_pnl_x`/`calc_pnl_y` unchanged (still in the broken, over-stated state), so all subsequent calls revert identically forever.

    pub fn restore_decimal(val: U128, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**6) -> (1.23*10**9)
        // let ret:u64 = val.checked_mul((10 as u64).pow(native_decimal.into())).unwrap().checked_div(amm.sys_decimal_value).unwrap();
        let ret_mut = val
            .checked_mul(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        let ret = ret_mut.checked_div(sys_decimal_value.into()).unwrap();
        ret
    }

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)

        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }
