### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop-domain` header (and `topic`/`api-version`/`webhook-id` headers) are trusted and passed on to the app's webhook handler without being part of the signed material. This breaks the identity binding: `shop verified by HMAC == shop acted upon by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` verifies the received HMAC solely against that signable string using `Context.api_secret_key` [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers without any cryptographic binding to that HMAC [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` handed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) . Because only the body is signed, any attacker who possesses one valid `(raw_body, hmac)` pair (e.g., from a webhook delivered to their own store, or any store that shares the same `api_secret_key`/app) can freely substitute the `shopify-shop-domain` header value while keeping the same body+HMAC, and the signature will still validate — since the shop value never enters `to_signable_string`. This lets the attacker cause the host app to process a webhook "as" a different tenant than the one that actually triggered it.

This is the shopify-api-ruby analog of the reported rounding-error class: a value that is *acted upon* by the downstream logic (here, the `shop` used to attribute the webhook event to a merchant/tenant) is not the value that is *actually verified* by the authentication mechanism (the body-only HMAC). The equality that should hold — `shop bound by HMAC == shop used by handler` — does not hold.

### Impact Explanation
Any host application that uses `request.shop` from `WebhookMetadata` to select which merchant's data to update (a standard and documented usage pattern) is exposed to cross-tenant data corruption/confusion: an attacker can trigger updates, deletions, or business logic tied to Shop A's webhook body while making the app believe it originated from Shop B, purely by manipulating an unsigned header. This falls under "cross-tenant access," matching the Critical impact category defined in scope.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid `(body, hmac)` pair for the target app's `api_secret_key` — most naturally from a webhook delivered to a store the attacker controls/owns within the same app installation, or one otherwise observable to them (e.g., via a low-privilege shop they operate). Once obtained, no additional secrets are needed to replay it with a forged `shop-domain` header, since the gem performs no verification that the header matches the shop implied by the signed body. Likelihood is moderate: it requires network delivery access to the app's webhook endpoint and a captured legitimate payload, but no privileged credentials or the `api_secret_key` itself.

### Recommendation
Bind the `shop-domain` (and ideally `topic`, `api-version`) header into the signed material verified against the HMAC, or independently verify that `request.shop` corresponds to a shop known to have generated the specific signed body (e.g., cross-check against session/shop registered for that webhook subscription) before invoking the handler. At minimum, document prominently that `shop` is unauthenticated relative to the HMAC and must not be trusted by host apps for tenant attribution without additional verification.

### Proof of Concept
1. Attacker's own shop (`attacker-shop.myshopify.com`) receives a legitimate webhook from Shopify: body `B`, headers include `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays this exact `(B, H)` pair to the app's public webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Request.new` accepts the headers (all required headers present) [5](#0-4) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) and succeeds, since `B` and `H` are unchanged [6](#0-5) [7](#0-6) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` but the attacker-controlled body `B`, and the host app processes it as if `victim-shop` sent that data.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
