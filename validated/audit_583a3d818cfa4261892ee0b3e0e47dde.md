Audit Report

## Title
CORS Origin Allowlist Bypass via Improper Suffix Check in Gateway `isAllowedOrigin` - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's HTTP server validates the `Origin` header against wildcard entries in `CORSAllowedOrigins` using an unanchored `strings.HasSuffix` check instead of verifying a proper subdomain boundary (a preceding `.`). This allows an attacker who registers a domain that merely ends with an allowed suffix (e.g. `evil-ethereum.org` matching `*.ethereum.org`) to have their Origin accepted as trusted, even though it is not a legitimate subdomain.

## Finding Description
In `isAllowedOrigin` at `core/services/gateway/network/httpserver.go` (lines 184-190), the wildcard branch strips the `*.` prefix from the configured allowed host and then does:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```
`strings.HasSuffix("evil-ethereum.org", "ethereum.org")` returns `true`, so any domain ending in the literal allowed suffix string passes, regardless of whether a `.` separator precedes it — there is no subdomain-boundary check. This value is then used directly in `handleRequest` (lines 195-202) to set `Access-Control-Allow-Origin` to the raw, attacker-controlled `Origin` header, granting the browser permission to read cross-origin responses. There is no other validation layer between `isAllowedOrigin` and the CORS header being reflected back. [1](#0-0) [2](#0-1) 

## Impact Explanation
This is an unprivileged-client-reachable allowlist bypass on the Gateway's HTTP CORS check. When an operator uses a wildcard entry in `CORSAllowedOrigins` (a documented, supported configuration pattern shown in `core/scripts/gateway/sample_config.toml` and `sample_config_tls.toml`), an attacker who registers/controls any domain ending in the same suffix string (without a dot boundary) can have their page's cross-origin JavaScript read the Gateway's JSON responses via the reflected `Access-Control-Allow-Origin` header. This falls into the "allowlist bypass" / cross-origin response corruption impact category.

## Likelihood Explanation
Exploitation requires only (1) the operator to configure a wildcard entry in `CORSAllowedOrigins`, and (2) the attacker to register a domain string ending in the same suffix without a `.` boundary — a low-cost, purely domain-registration action requiring no special privileges, network position, or insider access. The vulnerable code path is directly reachable by any unprivileged web client sending a normal cross-origin request with a crafted `Origin` header.

## Recommendation
Enforce a proper subdomain boundary in the wildcard match:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```

## Proof of Concept
1. Configure the Gateway with `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From a page hosted at `https://evil-ethereum.org`, send a `fetch`/XHR request to the Gateway endpoint with `Origin: https://evil-ethereum.org`.
3. Observe `isAllowedOrigin` returns `true` via `strings.HasSuffix("evil-ethereum.org", "ethereum.org")`, and the server responds with `Access-Control-Allow-Origin: https://evil-ethereum.org`, letting the attacker page read the Gateway's JSON response cross-origin despite not being a legitimate subdomain.

A Go unit test calling `isAllowedOrigin("https://evil-ethereum.org")` against a config with `CORSAllowedOrigins: []string{"https://*.ethereum.org"}` and asserting it returns `true` (when it should return `false`) would confirm this directly.
