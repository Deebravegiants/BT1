### Title
Unfunded `repay` refunds unmeasured "overpayment" out of pool custody, draining reserves - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's `repay` op computes `overpayment = declared_amount − ceil(debt)` purely from the caller-declared `action.amount`, and `apply` transfers that overpayment back to `payer` out of the pool's real token custody (`cache.transfer_out`) without verifying that any tokens were actually received. The refund neither debits `cash` nor passes `require_reserves`. When the position's debt is below the declared amount — including zero debt — the entire declared amount is paid out of other users' deposits. This is the same class as the reference report: a debt adjustment computed against the declared amount rather than the actual obligation, producing a transfer not backed by the book.

### Finding Description
`common/src/rates/scaling.rs::resolve_repay` returns `(pos_scaled, amount − current_debt_ceil)` when `amount >= current_debt_ceil`, so any `amount` above the position's true debt is classified as "excess". `contracts/pool/src/ops/repay.rs::accounting` then credits only `net_repay = amount − overpayment` to `cash`, and `apply` executes `outcome.cache.transfer_out(payer, outcome.overpayment)` — a token transfer funded from custody. The comment "The controller transfers the repay amount into the pool before this call" is an assumption, not an enforced invariant: nothing in the pool measures a balance delta, and the refund is issued in the same call regardless of inbound transfer.

The repo's own test proves the reachable state: `contracts/pool/tests/flows.rs::test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `client().repay(&payer, &ract(0, custody_before))` directly on a market with `borrowed == 0`, asserts `actual_amount == 0` (no debt retired, book untouched), and asserts the full `custody_before` was drained to the payer. The test comments explicitly note "Neither refund debits `cash` or passes `require_reserves`."

An unprivileged caller therefore calls `repay(payer, [(hub_asset, X)])` on any listed market — directly on the pool contract, or via the controller path with `amount` exceeding the leg's debt — with `X` up to the pool's token balance, receives `X − debt` in tokens, while `cash` is only incremented by `net_repay`. With no transfer-in, the book claims the refunded tokens are still reserves, so the loss is socialized across suppliers: either withdrawals later fail (frozen funds) or the deficit is hidden insolvency. `ops::recapitalize::apply` exhibits the identical shape (refund of the excess over the shortfall paid from custody without `require_reserves`), compounding the same class.

### Impact Explanation
Theft of user funds and/or permanent freezing: the attacker receives tokens backed by suppliers' `cash`/`supplied` book entries. Since the refund does not decrement `cash`, the book overstates reserves by the stolen amount; later withdraws or liquidation payouts will fail for lack of token funds, or the deficit accrues silently as protocol insolvency. This satisfies "theft of user funds" and "contract unable to operate from lack of token funds".

### Likelihood Explanation
Single unprivileged transaction: any address can call `repay` (pool client is invoked directly in the fixture with a generated `payer` and no controller precondition; via the controller, `repay` is a permissionless entrypoint). Precondition is only that the declared `amount` exceeds the position's ceiling-rounded debt — trivially true with `borrowed == 0` markets or dust debt. No price, timing, or privilege requirements. The only open question I could not fully confirm is whether the production pool `repay` entrypoint enforces an authorization check restricting callers to the controller; the in-repo test invokes it directly with an arbitrary payer, and the module comment treats the inbound transfer as caller responsibility rather than an auth-gated invariant.

### Recommendation
Measure the inbound transfer instead of trusting `action.amount`: record the pool token balance before pulling/expecting funds and cap `net_repay + overpayment` at the measured delta, or require the controller to settle `amount` before the refund is issued and assert `balance_before + amount == balance_after` post-refund. At minimum, route the overpayment refund through `cash`/reserves accounting (`credit_cash(amount)` then debit the refund) so the refund cannot exceed recorded reserves, and enforce `require_reserves` on `transfer_out` for refund paths.

### Proof of Concept
1. Pool has custody `B` tokens backing `cash == B`, `borrowed == 0` (or attacker position with debt `d < B`).
2. Attacker calls `repay(attacker, [(hub, asset)], amount = B)`.
3. `resolve_repay`: `current_debt_ceil == 0` (or `d`), `amount >= ceil` → `overpayment = B` (or `B − d`), `net_repay = 0`.
4. `RepayRoundsToZeroShares` assert passes on the `net_repay == 0` disjunct.
5. `apply` → `cache.transfer_out(attacker, B)` pays the full declared amount from custody; `cash` unchanged.
6. Result: attacker holds `B` tokens; book still records `cash = B`; supplier withdrawals now fail — funds stolen/frozen. This is exactly the scenario executed by `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` in `contracts/pool/tests/flows.rs`.
