### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while `Utils::HmacValidator` only verifies the HMAC over the raw request body via `to_signable_string`. The `shop` value returned to the application's webhook handler is therefore never bound to the cryptographic proof of authenticity, breaking the intended equality `hmac-authenticated body == request attributed to shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes the signature exclusively over that signable string using the app's `client_secret` [2](#0-1) . Meanwhile, `Request#shop` is read directly from the `shop-domain` header with no relation to the signed bytes [3](#0-2) . `Registry.process` validates only the HMAC and then forwards `request.shop` straight into the handler's `WebhookMetadata` as the tenant identity used by application business logic [4](#0-3) .

Because the app's `client_secret` (used to sign webhooks) is shared across every shop that installs the app — not scoped per shop — any merchant who has legitimately installed the app receives genuine webhook deliveries for their own store consisting of a `(raw_body, hmac)` pair that is valid under the app's single shared secret. That merchant can replay the exact same `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop as the source [5](#0-4) .

This exactly matches the reported bug class translated into an identity-binding failure: a field (`shop`) that downstream code acts on is not covered by the same authentication mechanism (HMAC) that is used to gate acceptance of the request.

### Impact Explanation
Applications built on this gem are documented to trust `data.shop` as the authoritative tenant identifier once `Registry.process` validates the HMAC [6](#0-5) . An attacker who controls one legitimately-installed shop can forge webhook events (with attacker-chosen body content, since they trigger the real event on their own store) attributed to any other shop, achieving cross-tenant access/injection into whatever the host application does with webhook data keyed by shop (e.g., updating stored shop state, triggering billing or entitlement changes, writing records associated with a different tenant).

### Likelihood Explanation
Any app developer who follows the documented pattern in `docs/usage/webhooks.md` (using `data.shop` from `Registry.process` as the trusted tenant key) is exposed. Exploitation requires only that the attacker be a real, unprivileged merchant with the app installed on their own store — no access to `api_secret_key`, tokens, or TLS interception is needed, since they legitimately receive real signed webhooks for their own store.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise separately authenticate the shop domain against a value already tied to the installation (e.g., look up the shop from server-side state keyed by `webhook_id`/API version rather than trusting the header). At minimum, document and encourage validating that the shop domain in the webhook maps to a shop known to have this specific webhook subscription/`webhook_id` registered, rather than trusting the header value directly as the tenant identity.

### Proof of Concept
1. App A is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, sharing one `client_secret`.
2. Attacker triggers a real event on `attacker-shop` (e.g., creates a product with attacker-controlled content), causing Shopify to deliver a webhook with a valid `x-shopify-hmac-sha256` computed over the JSON body using the shared `client_secret`.
3. Attacker captures `raw_body` and the `hmac` header from this genuine delivery.
4. Attacker replays a POST to the app's webhook endpoint with the same `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` returns `true` (verifies against `raw_body` only) [7](#0-6) ; `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` [8](#0-7) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
