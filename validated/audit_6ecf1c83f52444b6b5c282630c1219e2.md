### Title
Missing Reentrancy Guard on Tron `IntentGatewayV2.placeOrder()` Allows Reentrant Manipulation via User-Controlled Predispatch Calldata - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder()` executes fully attacker/user-supplied calldata (`order.predispatch.call`) through the `CallDispatcher` *before* escrow accounting and dust events are finalized, and — unlike the canonical EVM implementation — does so without a reentrancy guard, mirroring the exact hazard the 31Third report flagged (arbitrary attacker-controlled calldata executed mid-flow, combined with missing reentrancy protection around the equivalent of `batchTrade()`).

### Finding Description
`placeOrder` accepts an `Order` whose `predispatch.call` field is an arbitrary ABI-encoded `Call[]` chosen entirely by the order placer (`msg.sender`), not vetted against `order.inputs`/`order.output` beyond a post-hoc balance check. When `predispatch.call.length > 0`, the function:
1. Transfers `predispatch.assets` to the `CallDispatcher`.
2. Calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` — executing arbitrary attacker-chosen calls to arbitrary targets.
3. Only afterward reads `balanceOf(dispatcher)` to compute how much to sweep back into escrow and emits `DustCollected` for any excess. [1](#0-0) 

Compare this to the canonical EVM `IntentGatewayV2.placeOrder`, which is explicitly protected: `function placeOrder(Order memory order, bytes32 graffiti) public payable nonReentrant`. [2](#0-1) 

The Tron variant's `placeOrder` declaration carries no such modifier: [3](#0-2) 

Because the predispatch call is dispatched via a raw low-level `.call{value}(...)` inside `CallDispatcher.dispatch` to any attacker-chosen target with attacker-chosen calldata, and this happens mid-way through `placeOrder` (after `order.nonce = _nonce++` and commitment computation, but before escrow bookkeeping/state settles), an attacker can make the predispatch target reenter `placeOrder` (or other state-mutating entry points such as `fillOrder`/`cancelOrder`) on the Tron gateway. This is structurally identical to the 31Third class of bug: user-supplied calldata that is not fully bound to the declared trade/order parameters, executed against external targets, without a reentrancy lock — exactly the two remediation items the 31Third auditors called out (validate/bind calldata to declared struct fields; add a reentrancy lock around the trade/order entrypoint).

### Impact Explanation
A successful reentrant call during predispatch execution can let an attacker manipulate the gateway's escrow-accounting state (e.g., `_nonce`, `_orders[commitment][token]`, or duplicate-output-token checks) between the moment tokens are sent to `CallDispatcher` and the moment escrow accounting is written, potentially allowing the attacker to place or manipulate multiple orders that reference overlapping/incorrect escrow balances, or to trigger sweep/dust logic against balances belonging to a different, concurrently-processed order commitment. Given the `CallDispatcher` is a single shared contract holding funds transiently for whichever order is currently mid-flight, reentrancy during this window threatens confused-escrow accounting and potential theft or freezing of escrowed user funds — a Medium/High severity issue depending on exploitability of the reentrant path into `fillOrder`/`cancelOrder`/second `placeOrder` call.

### Likelihood Explanation
Any unprivileged user can trigger this path by simply calling `placeOrder` with a `predispatch.call` that targets a malicious/attacker-controlled contract (this is a completely user-chosen field with no allow-listing). Reaching a state-corrupting reentrant callback only requires the target contract to call back into the gateway during token receipt (e.g., an ERC777-style hook, or a plain external call target the attacker controls) — a common and well-understood reentrancy vector, and the EVM version has already been hardened against exactly this via `nonReentrant`, confirming the developers consider it a real risk they intentionally patched on EVM but appear to have missed on Tron.

### Recommendation
1. Add the equivalent of `nonReentrant` (or a Tron-compatible reentrancy guard) to `IntentGatewayV2.placeOrder` (and any other externally-callable functions in the Tron contract that route through `CallDispatcher.dispatch` with user-controlled calldata, e.g. `fillOrder`), matching the protection already present in `evm/src/apps/IntentGatewayV2.sol`.
2. Ensure state that affects escrow accounting (`_nonce`, `_orders` bookkeeping, output-token duplicate checks) is fully settled, or protected by the reentrancy lock, before any call to `ICallDispatcher.dispatch` with attacker-supplied calldata.
3. Audit all Tron contract entrypoints for parity with the hardening applied to the main EVM contracts (the `nonReentrant` modifier, transient-storage duplicate-output guard) since the Tron fork appears to be a divergent, less-hardened copy.

### Proof of Concept
1. Attacker deploys a malicious ERC20/receiver contract `Evil` that, when its `transferFrom`/callback is invoked by the `CallDispatcher` during predispatch, calls back into `IntentGatewayV2.placeOrder()` with a second order.
2. Attacker calls `placeOrder(order1, graffiti)` on the Tron gateway with `order1.predispatch.call` encoding a `Call` to `Evil`.
3. Inside `dispatcher.dispatch(order.predispatch.call)` [4](#0-3) , `Evil` reenters `placeOrder(order2, ...)` before `order1`'s escrow bookkeeping (`_orders[commitment][token] += ...`) and dust events are finalized.
4. Because there is no `nonReentrant` guard (contrast with `evm/src/apps/IntentGatewayV2.sol:194`), the reentrant `order2` call proceeds using shared `CallDispatcher` balances and `_nonce` state, allowing manipulation of commitment/escrow bookkeeping across the two interleaved order-placement calls — full exploitation depth (exact fund-extraction path) requires further live testing on the Tron contract's downstream `fillOrder`/`cancelOrder` state transitions, which was not verifiable via static review alone.
