## Title
`IntentsBase::_withdraw` reverts entirely if any single escrowed token transfer fails, permanently freezing the whole order's escrow - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase::_withdraw`, the single escrow-release routine used for `RedeemEscrow`, `RefundEscrow`, and same-chain cancel/refund flows, iterates over *all* of an order's input tokens in one loop and performs an unconditional `IERC20.safeTransfer` for each. There is no isolation between tokens: if any single token in the list reverts on transfer (e.g. a compliance-paused/blacklisted stablecoin, or any non-standard ERC20), the entire withdrawal reverts, blocking release of every other, unaffected token escrowed for that order — directly analogous to the reported `LiqFacet::removeLiq` issue where one paused vault blocks withdrawal from all vaults.

### Finding Description
Users create multi-input orders whose tokens are escrowed individually per order commitment [1](#0-0) . When the order is filled or cancelled, `_withdraw` is invoked to release *all* of the order's escrowed input tokens back to a beneficiary in a single loop:

```solidity
function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
    ...
    for (uint256 i; i < len; i++) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (amount == 0) continue;
        uint256 escrowed = _orders[body.commitment][token];
        if (escrowed == 0) revert UnknownOrder();
        _orders[body.commitment][token] = escrowed - amount;
        if (token == address(0)) {
            _sendValue(beneficiary, amount);
        } else {
            IERC20(token).safeTransfer(beneficiary, amount);
        }
    }
    ...
}
``` [1](#0-0) 

This is the sole entry point reached from three unprivileged/relayed paths:
- `ExtrinsicIntents.onAccept` for `RedeemEscrow`/`RefundEscrow`, delivered by any relayer relaying a valid Hyperbridge message [2](#0-1) .
- `ExtrinsicIntents.onGetResponse`, triggered after a user-initiated `cancelOrder`/GET proof round trip [3](#0-2) .
- `IntrinsicIntents._cancelSameChain`, callable directly by the order creator [4](#0-3) .

Because `safeTransfer` reverts the entire transaction on failure, a single problematic input token (e.g. USDC-style blacklisting of the beneficiary, a paused ERC20, or any token whose transfer function reverts) causes the *whole* `_withdraw` call — and therefore every other unaffected token's release for that same order commitment — to fail. State changes (the `_orders` decrement) are rolled back with it, so the order remains permanently un-settleable through this path: every retry of the same relayed message or resubmission of cancel/redeem hits the identical revert, since the poisoned token condition does not change.

### Impact Explanation
This can permanently freeze legitimate user/solver funds: all tokens escrowed for a multi-input order become unrecoverable if just one of them cannot be transferred, mirroring the impact class of the referenced report (Medium impact — funds get stuck rather than stolen, but with no recovery mechanism since the loop has no per-token skip/retry logic).

### Likelihood Explanation
Likelihood is Medium: orders with multiple input tokens are a normal, expected usage pattern of the intents system, and any one of those tokens becoming non-transferable post-escrow (compliance freeze/blacklist on a stablecoin, third-party pause, non-standard token behavior) is a realistic, externally-triggered event outside the protocol's or the order-creator's control — exactly the same trigger class (external pause) as the original report.

### Recommendation
Make `_withdraw`'s per-token transfer failure-tolerant: wrap each token transfer in a try/catch (or low-level call) so that a failing token is skipped/queued for later retry (e.g., accounted separately for pull-based withdrawal) rather than reverting the whole loop and blocking release of the other, unaffected escrowed tokens.

### Proof of Concept
1. User creates a cross-chain order with two input tokens: `USDC` and `DAI`, both escrowed in `IntentsBase._orders[commitment]`.
2. Before the order is filled/cancelled and settled, `USDC` blacklists the intended beneficiary address (a realistic, externally-controlled compliance action, not an admin action of this protocol).
3. Order fill/cancel proceeds normally on the counterparty side, and `_withdraw` is invoked with `body.tokens = [USDC, DAI]`.
4. The loop in `IntentsBase::_withdraw` [5](#0-4)  processes `USDC` first; `IERC20(USDC).safeTransfer(beneficiary, amount)` reverts because the beneficiary is blacklisted.
5. The entire transaction reverts, so the escrowed `DAI` (an otherwise perfectly transferable token) is never released either, and the `_orders` decrement for both tokens is rolled back.
6. Every subsequent relayed `RedeemEscrow`/`RefundEscrow` message or `cancelOrder` retry for this commitment hits the same revert indefinitely, permanently freezing both the poisoned and the healthy token's escrow.

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
