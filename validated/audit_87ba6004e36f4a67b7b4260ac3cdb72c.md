### Title
Unbounded per-key/per-request CPU cost in `pallet_state_coprocessor::handle_unsigned` is metered with a flat, size-independent weight - (File: `modules/pallets/state-coprocessor/src/lib.rs`)

### Summary
`pallet_state_coprocessor::Pallet::handle_unsigned` is a permissionless (`ensure_none`) unsigned extrinsic that decodes a `GetRequestsWithProof` message containing an attacker-controlled `Vec<GetRequest>`, where each `GetRequest` itself carries an attacker-controlled `Vec<Vec<u8>>` of storage `keys`. The extrinsic is charged a fixed weight of `T::DbWeight::get().reads_writes(1, 2)` regardless of how many requests or keys are in the message, while the actual execution work in `handle_get_requests`/`verify_state_proof` scales linearly (or worse) with `requests.len() * keys.len()` — hashing every key, rebuilding/cloning trie proofs per contract, and grouping/looking up values for every key. This is the same bug class as ALPINE-CVE-2026-27859: a message field whose element count is not capacity-bounded relative to the fixed processing cost charged/allotted for it, letting a single fee-less submission consume disproportionate CPU.

### Finding Description
The extrinsic is declared with a flat weight: [1](#0-0) 

It is dispatchable by anyone with no origin check beyond `ensure_none`, and it is also reachable through the transaction pool without fees since it is unsigned.

The actual work done per call is `handle_get_requests`, which iterates over every `GetRequest` in the batch, and for each one calls `verify_state_proof` with that request's full `keys` vector: [2](#0-1) 

Inside the EVM state-machine implementation, `verify_state_proof` performs an O(keys) duplicate check, then an O(keys) grouping-by-contract pass (each involving a keccak hash), then for every contract clones the whole contract proof and rebuilds a trie walk for every key in that contract group: [3](#0-2) 

Neither `GetRequestsWithProof.requests` nor `GetRequest.keys` are `BoundedVec`s or otherwise capped before this processing occurs; there is no `MaxKeys`/`MaxRequests`-style configuration item in this pallet analogous to the bounds seen elsewhere in the codebase (e.g. `call-decompressor`'s `MaxCallSize` gate before decompression, or `MAX_PROOF_DEPTH` in the Pharos SPV verifier). Because the extrinsic's weight is fixed and independent of `requests.len()`/`keys.len()`, a large number of keys/requests can be crammed into a single unsigned transaction (bounded only by the runtime's generic extrinsic/block length limit, not by any coprocessor-specific cap), causing execution time far in excess of the weight actually charged against the block.

### Impact Explanation
Because `handle_unsigned` is permissionless and unsigned (no fee is paid, `ensure_none` origin), an attacker can repeatedly submit `GetRequestsWithProof` messages with the maximum number of `GetRequest` entries and the maximum number of `keys` per entry that fit within the extrinsic/block size limit. Each such message is metered with the same fixed `reads_writes(1, 2)` weight as a message with a single key, but the real execution cost (keccak hashing, trie cloning, and proof verification per key) grows with the batch size. This lets an attacker consume disproportionate block-authoring CPU time relative to the weight budget consumed, a resource-exhaustion condition that can degrade block production / transaction processing for the whole chain — the same bug class as the CVE (excessive per-message parameter count driving CPU cost far beyond what the message's declared "cost" implies).

### Likelihood Explanation
The path is trivially reachable: `handle_unsigned` is `ensure_none` (no signature or balance required) and is also exercised through `ValidateUnsigned::validate_unsigned`, so a would-be attacker only needs to construct oversized but proof-invalid or proof-valid `GetRequestsWithProof` payloads (invalid proofs still force full traversal/hash cost before failing) and gossip them to the network repeatedly.

### Recommendation
- Bound `GetRequestsWithProof.requests` and each `GetRequest.keys` with `BoundedVec<_, MaxRequests>` / `BoundedVec<_, MaxKeys>` (or explicit length checks at the top of `handle_get_requests`) similar to the `MaxCallSize` bound already used in `pallet-call-decompressor`.
- Make the extrinsic's declared `#[pallet::weight(...)]` scale with `requests.len()` and total `keys.len()` (e.g. via a benchmarked per-key/per-request weight function) so the metered weight matches actual execution cost, and reject batches whose size would exceed the configured maximum before doing any proof work.

### Proof of Concept
1. Construct a `GetRequestsWithProof` with the maximum number of `GetRequest`s that fits in a block, each carrying the maximum number of `keys` entries (bytes only bounded by generic runtime extrinsic size limits, not by any coprocessor-specific cap).
2. Submit it as an unsigned extrinsic to `pallet_state_coprocessor::handle_unsigned`.
3. Observe that `handle_get_requests` → `verify_state_proof` performs hashing/trie-cloning work proportional to `requests.len() * keys.len()`, while the extrinsic is charged the fixed `reads_writes(1, 2)` weight declared at [4](#0-3) , regardless of batch size.

**Note on confidence:** I could not fully verify, within the available search budget, whether an upstream generic Substrate limit (e.g. a global max extrinsic/block length, or a `BoundedVec` enforced elsewhere in encoding/decoding) already caps the practical size of `requests`/`keys` tightly enough to make this impractical to exploit. I did not find any pallet-specific `MaxKeys`/`MaxRequests` bound in `pallet-state-coprocessor` itself, but a Devin session with full repo access should confirm the effective maximum extrinsic size on the target runtimes (gargantua/nexus) before treating this as fully confirmed exploitable at scale.

pub fn verify_state_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: &Proof,
	ismp_address: H160,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
	// Reject repeats before doing any work at all. They are already an error — repeats collapse
	// in the map returned below, so the caller's key-count check fails — but reaching that
	// check means every repeat has been verified first, and for account queries that is a
	// clone of the whole contract proof each time.
	let mut seen_keys = BTreeSet::new();
	for key in &keys {
		if !seen_keys.insert(key.as_slice()) {
			return Err(EvmStateMachineError::DuplicateKey.into());
		}
	}

	let evm_state_proof = decode_evm_state_proof(proof)?;
	let mut map = BTreeMap::new();
	let mut contract_to_keys = BTreeMap::new();
	let mut contract_account_queries = Vec::new();

	// Group keys by the contract address they belong to
	for key in keys {
		// For keys that are 52 bytes we expect the first 20 bytes to be the contract address and
		// the last 32 bytes the slot hash.
		// For keys that are 20 bytes we expect that to the
		// contract or account address.
		// For keys that are 32 bytes we expect that to be a slothash in
		// the Ismp EVM host
		let contract_address = if key.len() == 52 {
			H160::from_slice(&key[..20])
		} else if key.len() == 32 {
			ismp_address
		} else if key.len() == 20 {
			contract_account_queries.push(H160::from_slice(&key));
			continue;
		} else {
			return Err(EvmStateMachineError::UnsupportedKeyLength.into());
		};
		let entry = contract_to_keys.entry(contract_address.0.to_vec()).or_insert(vec![]);

		let slot_hash = if key.len() == 52 {
			H::keccak256(&key[20..]).0.to_vec()
		} else {
			H::keccak256(&key).0.to_vec()
		};

		entry.push((key, slot_hash));
	}

	// The storage proof must correspond exactly to the contracts a key was requested from:
	// every one covered, and nothing else. Both directions are settled here, before a single
	// entry is resolved — resolving one clones the whole contract proof and rebuilds its trie,
	// so checking as we go would let a proof padded with unrequested accounts do that work
	// before being rejected, and would make which error surfaces depend on map ordering.
	// The honest prover already emits exactly this set, deriving its map from the requested
	// keys, so nothing legitimate is turned away.
	let result = contract_to_keys
		.clone()
		.into_keys()
		.all(|contract| evm_state_proof.storage_proof.contains_key(&contract));
	if !result {
		return Err(EvmStateMachineError::IncompleteStorageProof.into());
	}

	if evm_state_proof
		.storage_proof
		.keys()
		.any(|contract| !contract_to_keys.contains_key(contract))
	{
		return Err(EvmStateMachineError::UnrequestedContractProof.into());
	}

	for (contract_address, storage_proof) in evm_state_proof.storage_proof {
		// Unreachable: the correspondence check above already rejected any entry without a
		// requested key. Kept as a hard error rather than a skip so the invariant survives if
		// that check is ever moved or relaxed.
		let Some(keys) = contract_to_keys.remove(&contract_address) else {
			return Err(EvmStateMachineError::UnrequestedContractProof.into());
		};

		let contract_root = get_contract_account::<H>(
			evm_state_proof.contract_proof.clone(),
			&contract_address,
			root,
		)?
		.storage_root
		.0
		.into();

		let slot_hashes = keys.iter().map(|(_, slot_hash)| slot_hash.clone()).collect();
		let values = get_values_from_proof::<H>(slot_hashes, contract_root, storage_proof)?;
		keys.into_iter().zip(values).for_each(|((key, _), value)| {
			map.insert(key, value);
		});
	}
