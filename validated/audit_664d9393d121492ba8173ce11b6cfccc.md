## Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while the `shop` identity value returned by `Request#shop` is read from the unauthenticated `x-shopify-shop-domain` header. `Registry.process` validates the HMAC of the body and then hands the (unverified) `shop` value straight to the application's webhook handler as the tenant identifier, so a request whose body's HMAC is valid can still carry an arbitrary, attacker-chosen shop domain.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`shop` is pulled from the `shopify-shop-domain`/`x-shopify-shop-domain` header, but `to_signable_string` returns only `@raw_body` — the header is never included in the bytes that get HMAC-verified.

Compare this with the OAuth callback flow, where the same `shop` value IS folded into the signable string and therefore is bound by the HMAC: [2](#0-1) 

`Registry.process` verifies the HMAC (which only covers `raw_body`) and then trusts `request.shop` unconditionally to build the metadata passed to the app's handler: [3](#0-2) 

This breaks the identity binding: `shop` acted on (used as the tenant key in `WebhookMetadata`) ≠ `shop` covered by the HMAC (only `raw_body` is). Any request whose `raw_body` produces a valid HMAC for the app's `client_secret` — for example a legitimately Shopify-signed webhook the attacker received for their *own* shop (since they have installed the app and Shopify will sign webhooks with the app's shared secret for any installing shop) — can be replayed with the `x-shopify-shop-domain` header rewritten to any other shop domain. `HmacValidator.validate` will still accept it because it only checks `raw_body` against the secret, never the shop claim: [4](#0-3) 

### Impact Explanation
Host applications rely on `WebhookMetadata#shop` to decide which merchant's records the webhook payload applies to (e.g., looking up that shop's session/data and applying the order/update payload to it). Since the shop claim is not authenticated, an attacker who is themselves a merchant using the app can generate a validly-HMAC'd webhook body (from actions in their own store) and relabel it as coming from a different shop, causing the app to process/apply that payload under another tenant's identity — a cross-tenant data confusion/injection that can corrupt another merchant's data or trigger tenant-scoped side effects (e.g., order creation, fulfillment, uninstall handling) attributed to the wrong shop. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be able to send an HTTP POST to the app's webhook endpoint with attacker-controlled headers and a body they can obtain a valid signature for (trivially available to them as an installed merchant receiving their own legitimate webhooks). No access token, `client_secret`, or privileged credential is required — only the ability to POST arbitrary headers to the public webhook URL, which is by design internet-reachable.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed payload used by `to_signable_string`, or otherwise cryptographically bind the `shop` header to the verified body (e.g., have `HmacValidator`/`Registry.process` compute the signature over `shop + raw_body` rather than `raw_body` alone), mirroring the approach already used for `Auth::Oauth::AuthQuery`.

### Proof of Concept
1. App is installed on attacker's own shop `attacker.myshopify.com`; Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(client_secret, B)`.
2. Attacker captures this raw request and re-sends it to the same webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` while keeping body `B` and `hmac-sha256: H` unchanged.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and finds it equal to `H` — validation passes: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` — the application now believes payload `B` originated from `victim.myshopify.com`, even though the shop domain was never authenticated.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
