## Title
Webhook `shop` (and `topic`) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw request body only. The `shop` (and `topic`) values that the registry uses to route and attribute the webhook to a specific merchant are read from unauthenticated HTTP headers that are never included in the signed content. An attacker who legitimately owns one Shopify store (and therefore receives real, correctly-signed webhooks for that store) can take a genuine `raw_body`/HMAC pair issued for their own shop and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. The HMAC still validates, but the handler receives the victim's shop identity attached to the attacker's forged/self-controlled payload.

### Finding Description
`Request#hmac` decodes the signature from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` and `topic`, however, are pulled straight from headers with no cryptographic binding to the body or to the HMAC: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (i.e., the body) — it never factors in `shop` or `topic`: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the authoritative tenant identity for dispatching to the app's handler: [5](#0-4) 

The identity-binding equality that should hold is:
`shop authenticated by HMAC == shop acted upon by the handler`

Because `shop` is outside the HMAC's scope, this equality is not enforced: `shop delivered in header` can be swapped by anyone controlling the raw body/HMAC pair for *any* shop's webhook, while the body's actual signed content is unrelated to the header. Any Shopify merchant (an "unprivileged internet user" relative to other tenants of the app) can generate a validly-signed body for their own shop, then replay it to the app's public webhook callback URL with a different `shop-domain` header. `HmacValidator.validate` passes since the body/HMAC pair matches, and `WebhookMetadata` is built with `shop: request.shop` — the attacker-chosen value — while `body` is the attacker's own (self-controlled) shop data. Downstream app logic (per the gem's documented handler contract) uses `data.shop` to determine which merchant's records to update, per the gem's own webhook usage guide: [6](#0-5) 

This lets an attacker inject data attributed to a shop they do not own into a victim merchant's data pipeline — a cross-tenant identity confusion rooted entirely in this gem's `Request`/`Registry`/`HmacValidator` trio, not requiring any Shopify credential beyond controlling one's own store.

### Impact Explanation
This breaks the shop/tenant identity boundary the HMAC is meant to guarantee. An attacker (who is a legitimate Shopify merchant of their own store, i.e., an "unprivileged internet user" with respect to other tenants of the host app) can make the app process attacker-supplied webhook bodies under a victim shop's identity, causing cross-tenant data injection into the app on behalf of a shop the attacker does not control. This matches the "cross-tenant access" Critical-impact category, since the app’s per-shop data isolation relies on `request.shop`/`data.shop` being trustworthy once HMAC validation succeeds.

### Likelihood Explanation
Any developer who signs up their own store as a Shopify merchant can generate a genuinely-signed webhook payload for their own store on demand (e.g., updating an order) and replay the raw body + `hmac-sha256` header with a modified `shop-domain` header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required — only the ability to trigger webhooks on one's own store and knowledge of the target app's webhook URL, which is typically documented/public.

### Recommendation
Include `shop` (and ideally `topic`) in the value that is authenticated, or otherwise cryptographically/contextually bind the `shop` header to the specific HMAC-signed body before it is trusted by `Registry.process`. Concretely:
- Extend `VerifiableQuery`/`to_signable_string` (or add a dedicated check in `HmacValidator`/`Registry.process`) to incorporate `shop` and `topic` into what's verified, matching how the OAuth `AuthQuery` binds its params.
- At minimum, cross-check `request.shop` against an expected/whitelisted shop context (e.g., the session or app-installation record the webhook is expected for) before dispatching to the handler, rather than trusting the header value verbatim once only the body's HMAC has been checked.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), obtaining a genuine `raw_body` and its correctly-computed `X-Shopify-Hmac-Sha256` value signed with the app's real `client_secret`.
2. Attacker POSTs to the app's webhook endpoint using the intercepted `raw_body` and `hmac-sha256` value unchanged, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body, and `HmacValidator.validate` succeeds because it only checks the HMAC against `raw_body`: [7](#0-6) 
4. `Registry.process` dispatches `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` to the app's handler, causing the app to associate attacker-controlled data with the victim shop: [8](#0-7)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
