## Analog Found: Unauthenticated privileged extrinsic execution via cross-chain calldata in `pallet-hyper-fungible-token`

### Title
Insufficient authorization validation allows arbitrary RuntimeCall execution under a spoofable account identity - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
CVE-2023-6186 is fundamentally a case where a normally passive, low-trust action (activating a hyperlink) is allowed to trigger a privileged action (macro execution) without independently validating that the user actually authorized that specific privileged action. The same pattern exists in `Pallet::<T> as IsmpModule::on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs`: an incoming cross-chain token-transfer message (a low-trust, ISMP-relayed event) is allowed to trigger dispatch of an **arbitrary `RuntimeCall`** as a signed, privileged extrinsic, using an origin account derived purely from attacker-controlled message content, with no independent cryptographic proof binding that specific call to that account's consent.

### Finding Description
`on_accept` decodes the optional `message.data` as `SubstrateCalldata` [1](#0-0) . If a signature is present, it verifies it against `beneficiary` (the token recipient). If **no signature is present**, the code falls into an `else` branch that derives the dispatch `origin` purely from `message.from` — bytes that live inside the ABI-decoded message body, not from any authenticated field of the ISMP request: [2](#0-1) 

That derived `origin` is then used to dispatch an attacker-supplied `RuntimeCall`, gated only by the generic `BaseCallFilter`, with no signature check at all: [3](#0-2) 

The only authentication performed earlier in `on_accept` is a check that the *module/contract address* the request came from (`from`, the ISMP `PostRequest.from`) maps to a registered asset via `ContractToAsset::<T>::get(source, &from)`: [4](#0-3) 

This validates *which bridge contract* sent the request — it says nothing about the `message.from` field embedded inside the ABI-encoded `Message` body, which is a completely separate value chosen by whoever calls `send()` on the source-chain contract. Nothing in the substrate-side handler cryptographically ties `message.from` to the actual EVM caller; it is trusted at face value. Consequently, the no-signature branch converts this untrusted `from` value into a Substrate `AccountId` (via `EvmToSubstrate::convert` or direct 32-byte reinterpretation) and dispatches a privileged call *as that account*, without ever verifying the account's owner consented to this specific call — exactly analogous to LibreOffice executing a macro target from an untrusted hyperlink without an explicit user-permission gate.

### Impact Explanation
Any account for which `T::BaseCallFilter` permits at least one dangerous call (transfers, approvals, proxy/staking actions, etc.) can have that call executed on its behalf as soon as an attacker can get a `Message.data` payload with a matching `from` value delivered through `on_accept` — with zero cryptographic proof that the holder of that identity authorized the call. Depending on what the source-chain sending contract enforces for the `from` field of its `Message` struct, this ranges from "the real sender authorizes calls under their own EVM-derived account with no Substrate signature" (a weaker but still non-standard authorization model) up to full account impersonation and fund theft if the `from` field is not strictly bound to `msg.sender` on the sending contract. This is a High severity, direct-fund-risk class of bug consistent with the required "unauthorized app action" / "theft of funds" impact bar.

### Likelihood Explanation
The vulnerable path is reachable by any unprivileged user simply by calling the cross-chain `send()`/transfer entrypoint on the source-chain `HyperFungibleToken`/`WrappedHyperFungibleToken` contract with a non-empty `data` field and no `SubstrateCalldata.signature`, then having any relayer deliver the resulting request — this requires no special privileges, matching the "unprivileged relayer/token bridger" reachability requirement in scope.

### Recommendation
Require a valid cryptographic signature (the existing `substrate_data.signature` verification branch) for **every** calldata-execution path, or, at minimum, cryptographically bind `origin` derivation to a value that is provably controlled by the transaction's true initiator (e.g., always require the signature check, or restrict the no-signature path to only ever dispatch as `beneficiary` and never as an unauthenticated `message.from`-derived account). Additionally, verify on the EVM sending contracts that `Message.from` is hard-set to `msg.sender` and cannot be spoofed by the caller.

### Proof of Concept
1. Attacker calls `HyperFungibleToken.send()` (or the wrapped variant) on the source chain, crafting `SendParams.data` to encode a `SubstrateCalldata { signature: None, runtime_call: <arbitrary call encoded, e.g. Balances::transfer_all> }`, and setting `Message.from` to the bytes of a target victim's EVM address (if the sending contract does not force `from == msg.sender`) or to their own address to demonstrate the missing-signature dispatch path.
2. A relayer delivers the resulting `PostRequest` to the destination chain; `on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs` mints/unlocks tokens to `beneficiary`, then reaches the `data`-execution block.
3. Since no `signature` is present, `origin` is derived solely from the attacker-chosen `message.from` bytes [2](#0-1) , and the attacker's `RuntimeCall` is dispatched as that account without any signature check [5](#0-4) .

**Note on unverified assumption:** I was not able to fetch the exact `send()` implementation in `sdk/packages/core/contracts/apps/HyperFungibleToken.sol` to confirm whether `Message.from` is strictly hard-coded to `msg.sender` or is caller-suppliable; this materially affects whether the impact is "impersonation of arbitrary accounts" (critical) versus "self-authorization without a Substrate signature" (still a deviation from expected authorization semantics, but lower impact). A Devin session with full repository access should verify this before finalizing severity.
