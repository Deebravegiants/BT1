### Title
Webhook `shop-domain`, `topic`, and `webhook-id` Headers Are Trusted Without Being Covered by the HMAC Signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
The `ecrecover` bug class is "a value acted upon that is not actually bound by the cryptographic check meant to validate it." In `ShopifyAPI::Webhooks::Request`, the HMAC signature only covers the raw request body, while the `shop`, `topic`, and `webhook_id` values used by the application to dispatch and attribute the webhook are taken from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
but `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to those headers: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches to a handler using the unauthenticated `shop`, `topic`, and `webhook_id` fields taken straight from the request object: [3](#0-2) 

Because the identity fields (`shop-domain`, `topic`, `webhook-id`) are not part of the signed content, the equality that should hold — *the shop/topic bound by the HMAC == the shop/topic the handler acts on* — does not actually hold. The HMAC only proves the body bytes came from Shopify (using the shared `client_secret`); it says nothing about which shop or topic that body is associated with.

### Impact Explanation
This is a header/body binding gap rather than a directly exploitable cross-tenant attack by an anonymous unprivileged user: producing a *valid* HMAC for arbitrary body content still requires knowledge of the app's `api_secret_key`, which is out of scope per the rules (excluding anything requiring the app's secret). However, if an attacker can obtain **any single legitimate webhook delivery** (e.g., by intercepting/replaying an event from their own shop's webhook subscription, which they legitimately receive), they can resend that exact `raw_body` + valid `hmac-sha256` pair to the victim app's webhook endpoint while freely rewriting the `shop-domain`, `topic`, and `webhook-id` headers. `Utils::HmacValidator.validate` will still pass because it only checks the body against the secret, and `Registry.process` will hand off attacker-controlled `shop`/`topic`/`webhook_id` metadata to the app's handler as if it were authentic — causing the handler to process/store data (e.g., `customers/redact`, `shop/redact` data-deletion webhooks) under a different, attacker-chosen shop identity. This crosses a tenant boundary within the app's own webhook processing logic.

### Likelihood Explanation
Exploitation requires the attacker to already control (or have received) at least one legitimate webhook body+HMAC pair from Shopify for their own shop — an unprivileged but real, low-cost precondition (any merchant installing the app receives such deliveries). No access to `api_secret_key` or any other shop's credentials is needed. This is more likely than the zkASM-style analog with no such precondition, but it's still gated by needing one authentic webhook sample.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed content used for HMAC verification (or otherwise cryptographically bind them, e.g., by validating the `shop-domain` header against a known/allow-listed set of shops for the receiving app, and rejecting webhook deliveries where header values are inconsistent with previously established session state). At minimum, document that consumers must independently correlate `shop` from the webhook against their own subscription/session store before trusting it, since the gem does not verify this binding itself.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the app installed and receives a legitimate webhook for topic `customers/redact` with body `B` and a valid `x-shopify-hmac-sha256` header `H` (valid because it's HMAC(secret, B), and the attacker legitimately possesses this one valid pair from their own installation).
2. Attacker resends the same `B` and `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-webhook-id`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (only body `B` and `H` are checked): [4](#0-3) 
4. `Registry.process` calls the registered handler with `shop: "victim-shop.myshopify.com"` even though the signed body never came from or referenced that shop: [5](#0-4)
