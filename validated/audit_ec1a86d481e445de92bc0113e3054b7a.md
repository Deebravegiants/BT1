### Title
Zero-liquidity mint from HyperSwap `addLiquidity` can permanently brick `finalizeGraduation` for a manipulated hostile-mint pre-seed - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._routerDepositAndDispose` forwards the post-rebalance deposit to HyperSwap's `router.addLiquidity`, and the resulting `liquidity` is passed straight through `_seedUniswapV2Direct` → `finalizeGraduation` → `LPLock.recordLock` with no zero check anywhere in that chain. `LPLock.recordLock` itself does check `amount == 0` and reverts (`ZeroAmount`), but that revert happens *after* `router.addLiquidity` already succeeded — the real failure mode is that V2's own `mint()` (`liquidity = min(amount0·S/r0, amount1·S/r1)`) can round down to zero and revert *inside* `addLiquidity`, which reverts the whole `finalizeGraduation` transaction. This is the exact bug class from the referenced ArrakisV2 report ("no check that liquidity-to-mint rounds to zero before calling `pool.mint()`"), reachable here through the hostile mint-pre-seed defense that the protocol itself added (`_seedRebalancing` / `_pairRebalance` / `_swapBudget` / `_routerDepositAndDispose`) but did not fully close.

### Finding Description
The mint-pre-seed defense caps the rebalance swap at 99% of the available inventory via `_swapBudget`: [1](#0-0) 

The stated rationale is that reserving 1% of the token/LT balance for the deposit leg "guarantees the deposit leg always lands AND mints non-zero LP." That guarantee only protects against `remToken == 0` / `remLT == 0` in absolute terms; it says nothing about V2's `mint()` ratio math, which can still round `liquidity` down to `0` even when both `remToken` and `remLT` are non-zero, if the pre-existing LP's `totalSupply()` is very small relative to the post-swap reserves.

`_routerDepositAndDispose` calls `addLiquidity` and takes whatever `liquidity` it returns without any zero check: [2](#0-1) 

`finalizeGraduation` then unconditionally uses that value to lock LP: [3](#0-2) 

The V2/HyperSwap mint formula for a non-empty pool (`totalSupply() != 0`, which is exactly the Regime-3 rebalance path Bonding takes) is: [4](#0-3) 

`require(liquidity > 0, "MockPair: INSUFFICIENT_LIQUIDITY_MINTED")` mirrors the real V2 `pair.mint` revert condition. This `require` reverts *inside* `router.addLiquidity`, which is called with no try/catch, so it reverts the entire `finalizeGraduation` transaction.

**How an attacker forces `liquidity == 0`:**
1. Front-run pair creation (permissionless `factory.createPair`) between phase 1 (`_enterGraduating`) and phase 2 (`finalizeGraduation`), as already described in the protocol's own Regime-3 threat model.
2. Mint an extreme, minimal-`totalSupply` LP position: choose `amount0`/`amount1` such that `floor(sqrt(amount0·amount1)) == MINIMUM_LIQUIDITY + 1` (e.g. `amount0 = 1`, `amount1 ≈ 1,002,001`), so `totalSupply()` after the attacker's own `pair.mint()` is `1`. This costs the attacker only 1 wei of the launched token plus a negligible dust amount of LT.
3. Choose the ratio so skewed (in the direction Bonding's inventory is on the "cheap" side) that `_noFeeSwapInput`'s uncapped result exceeds `maxSwap = _swapBudget(...)` — i.e. the correction the pre-seed requires is bigger than 99% of Bonding's available inventory. `_pairRebalance` then clamps the swap to `maxSwap`, and the post-swap reserve on the swapped-in side grows to roughly `maxSwap` while only the reserved ~1% (`remToken` or `remLT`) is left for the deposit.
4. Because `totalSupply()` was pinned at `1` by step 2, `liquidity0 = remToken · totalSupply / reserve0` (or the symmetric `liquidity1` calc) becomes `(1% of inventory) · 1 / (~99% of inventory)`, which is `< 1` and rounds down to `0`. `min(liquidity0, liquidity1) == 0`.

This reproduces the "liquidity rounds to zero, transaction reverts in `pool.mint()`" pattern from the cited ArrakisV2 report, mapped onto alt.fun's graduation LP-seeding path, and it happens on a code path the protocol added specifically to be "brick-proof" (per its own natspec/AGENTS.md claims), but the 1%-reservation fix only prevents the absolute-zero case, not the ratio-rounding case.

### Impact Explanation
`finalizeGraduation` is deterministic given the cached `(tokensForLP, ltFromPair)` and the attacker's already-mined pre-seed reserves; every retry hits the identical revert. There is no admin override, no alternate seeding path, and `LPLock.recordLock` is a strict one-shot function (`AlreadyLocked` guard) with no rescue mechanism. Once bricked, the token is permanently stuck in `Lifecycle.Graduating`:
- All curve-raised LT (`ltFromPair`) held in `Bonding` for this token becomes permanently unreachable.
- The 250M reserved tokens (`tokensForLP`) parked in `Bonding` for this token are permanently unreachable.
- Trading never resumes (curve is already drained/frozen at `Graduating`), so all holders of that token are permanently frozen out of both the curve and any secondary market.

This is a permanent freeze of trader/creator funds, satisfying the Medium/High bar.

### Likelihood Explanation
The attack requires only: (a) the ability to permissionlessly create the HyperSwap pair and mint an initial LP position with an attacker-chosen extreme ratio (both already established as reachable by the protocol's own documented Regime-3 threat model), and (b) picking `amount0`/`amount1` to pin `totalSupply()` at the minimum non-reverting value (`1`) while making the ratio skewed enough to force the 99%-cap swap clamp. Both steps cost negligible capital (a few wei of the launched token and a dust amount of LT) and are executable by any unprivileged address between `_enterGraduating` and `finalizeGraduation`. The window always exists because graduation is intentionally split into two transactions.

### Recommendation
- After computing `liquidity` in `_routerDepositAndDispose`, check `liquidity == 0` and fall back to the existing `_seedDirectMint` overpowering path (the same fallback already used when `_pairRebalance` returns `false`), rather than letting the zero-liquidity condition propagate into an unguarded `addLiquidity` revert.
- Alternatively/additionally, don't rely solely on reserving 1% of inventory; explicitly compute the expected V2 `min(amount0·S/r0, amount1·S/r1)` before calling `addLiquidity` and route to `_seedDirectMint` whenever it would round to zero, mirroring the same round-to-zero precheck pattern already used for the swap step (`_pairRebalance`'s `expectedOut == 0` guard).

### Proof of Concept
1. Attacker (any unprivileged address) waits for `_enterGraduating(token)` to fire (permissionless via `triggerGraduation` or an ordinary buy that crosses the threshold), caching `(tokensForLP, ltFromPair)`.
2. Attacker calls `factory.createPair(token, lt)` on HyperSwap before the keeper's `finalizeGraduation` lands.
3. Attacker transfers `amount0 = 1` wei of `token` and `amount1 ≈ 1,002,001` wei of `lt` to the new pair, then calls `pair.mint(attacker)`. This mints `totalSupply() == 1` LP token to the attacker (satisfies V2's `MINIMUM_LIQUIDITY` check by exactly 1 unit above the floor) at an extremely skewed ratio.
4. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedUniswapV2Direct` sees `totalSupply() != 0`, enters `_seedRebalancing`; the required correction swap (per `_noFeeSwapInput`) exceeds `_swapBudget(...)` (99% of the relevant side's inventory) and clamps at `maxSwap`, leaving only ~1% of Bonding's inventory (`remToken`/`remLT`) for the deposit.
5. `_routerDepositAndDispose` calls `router.addLiquidity(...)`; V2's `mint()` computes `liquidity = min(remToken·1/reserve0, remLT·1/reserve1)`, which rounds to `0` because `totalSupply() == 1` and the post-swap reserve on the swapped side dwarfs the deposit's residual 1% share.
6. `addLiquidity`'s underlying `pair.mint` reverts with `INSUFFICIENT_LIQUIDITY_MINTED`, reverting `finalizeGraduation`. Every subsequent call reverts identically, permanently freezing `token`'s LT and `tokensForLP` inside `Bonding`.

Note: I was unable to run the actual Foundry test suite to numerically confirm the exact reserve/swap magnitudes reproduce a strict `liquidity == 0` (vs. `liquidity == 1`) for a concrete `tokensForLP`/`ltFromPair` pair from the live launch parameters — the arithmetic above demonstrates the mechanism is sound (deposit share `≈1%` of a swap-dominated reserve, multiplied by `totalSupply=1`, rounds down), but the precise threshold at which the rounding hits exactly zero depends on the specific `tokensForLP`/`ltFromPair` values at trigger time and would need to be verified with a Foundry PoC (`test/TwoPhaseGraduation.t.sol` already has the harness/mocks needed: `_grieferMintPreSeed`, `_noFeeSwapInputUncapped`, `MockHyperswapPair`).

    ///      so the subsequent `addLiquidity` always has a non-zero amount

    ///      pre-seed (massively imbalanced reserves) drives the

    ///      `finalizeGraduation` returns `liquidity = 0`, and
