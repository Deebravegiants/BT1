Based on the analysis, I've confirmed the vulnerability. This is a legitimate analog to the reported bug class: an identity field (`shop`) is acted upon by the application but is not covered by the HMAC that authenticates the request.

### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant data attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then hands off `request.shop` — read from the unauthenticated `x-shopify-shop-domain` header — as the tenant identifier to the host application's webhook handler. Because the shop header is never part of the signed payload, the equality "authenticated shop == acted-upon shop" does not hold, letting an attacker who controls a genuine, validly-signed webhook rebind it to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` field of the request via `OpenSSL.secure_compare` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`, the JSON body of the request [2](#0-1) . The `shop` accessor, however, is derived independently from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header and is never included in the signable string [3](#0-2) .

`Registry.process` validates the HMAC and, on success, immediately trusts `request.shop` as the tenant identity, passing it straight into the handler's `WebhookMetadata`: [4](#0-3) 

Since `api_secret_key` is a single app-wide secret shared across every merchant that installs the app (it is not per-shop), a valid HMAC only proves "this body was signed by Shopify using this app's secret" — it proves nothing about which shop the body belongs to. The `shop` header is fully attacker-controllable in the sense that it is unauthenticated bytes riding alongside an otherwise-genuine, validly-signed payload.

The equality that should hold is:
```
shop authenticated by HMAC == shop acted upon by the handler
```
Instead the gem enforces:
```
body authenticated by HMAC != shop acted upon by the handler (header, unsigned)
```

### Impact Explanation
An attacker who operates their own legitimate installation of the target app receives real webhooks from Shopify for their own store, each with a valid HMAC (computed with the app's shared `api_secret_key`) over the body. By replaying that exact body/HMAC pair while substituting `x-shopify-shop-domain` with a victim merchant's domain, the attacker produces a request that still passes `Utils::HmacValidator.validate` [5](#0-4) , yet is delivered to the host application's handler tagged as belonging to the victim shop [6](#0-5) . Any host application that uses `WebhookMetadata#shop` to route data, update tenant-scoped records, or resolve a session/access token for further API calls will act on attacker-supplied data under another tenant's identity — a cross-tenant data-integrity breach that can cascade into cross-tenant access if the handler uses the shop value to look up or act with that tenant's stored access token.

### Likelihood Explanation
Likelihood is Medium-to-High for any multi-tenant app built on this gem, because: (1) obtaining a genuinely-signed webhook is trivial for anyone who installs the app themselves (no secret needs to be stolen); (2) HTTP headers are fully attacker-controlled on a replayed/forged request; and (3) the gem's own documentation and API surface (`WebhookMetadata#shop`) actively encourage host apps to treat `request.shop`/`data.shop` as a trusted tenant identifier, since it looks like it went through the same `HmacValidator` gate as the rest of the request.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) in the signable string used to compute/verify the webhook HMAC, or otherwise cryptographically bind the shop header to the signed payload before it is exposed via `Request#shop`. At minimum, document prominently that `request.shop` is not covered by the HMAC and must be independently cross-checked against a known/registered shop for the installation before being trusted, rather than exposing it as if it were part of the authenticated payload.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), receiving from Shopify a genuine POST with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker resends this exact `raw_body` and `hmac` header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not correlation to the body) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body`, unaffected by the shop header change [8](#0-7) .
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)` and processes attacker-controlled data as if it belonged to the victim tenant [9](#0-8) .
