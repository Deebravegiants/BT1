### Title
Webhook `shop` identity is derived from an unauthenticated header not covered by the HMAC, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by validating the HMAC over the raw body only, but the `shop` value that the gem hands to the app's handler as the tenant identifier is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed content. This breaks the intended binding `verified(hmac) == acted_on(shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads the tenant identifier straight from a header, independent of that signed body: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the `@raw_body` bytes were signed with `Context.api_secret_key`) and then dispatches the handler using `request.shop`, an unauthenticated field: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm the check only compares the computed HMAC over `to_signable_string` (the body) against the received `hmac`; no header, including `shop`, participates in the signature: [4](#0-3) 

The documented processing flow explicitly tells developers that `Registry.process` "will verify the request did indeed come from Shopify" and then forwards `data.shop` to their handler as the trusted tenant, without any additional binding step: [5](#0-4) [6](#0-5) 

Equality that should hold but doesn't: `hmac_verified_bytes == identity_acted_on` — the gem verifies `@raw_body` but acts on `shop-domain` header, a value outside that verified byte range.

### Impact Explanation
An unprivileged actor who legitimately installs the app on their own (attacker-controlled) shop can capture a valid `(raw_body, hmac)` pair generated for their own tenant, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. Because `HmacValidator.validate` never inspects the `shop` header, the forged request passes validation, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain — while the payload content itself may pertain to the attacker's own store. Depending on how the host app keys sessions/state off `data.shop` (as the docs instruct), this enables cross-tenant confusion: an attacker can inject or spoof events attributed to a shop they do not control, potentially triggering per-tenant business logic (e.g., data sync, billing, redact flows) under a victim's identity.

### Likelihood Explanation
Moderate-to-high. Any app developer that installs their own app (a normal, unprivileged action available to any Shopify Partner) obtains legitimate `(body, hmac)` pairs for their own shop and can freely re-send them with a modified `shop-domain` header to any internet-reachable webhook endpoint of the target app, since no additional secret or privilege is required to forge the header.

### Recommendation
Include the shop domain (and ideally other identifying headers such as `webhook-id`, `topic`) in the value that is actually authenticated, or otherwise cryptographically bind them to the signed payload before use. At minimum, `Request#to_signable_string` (or `Registry.process`) should incorporate the `shop-domain` header into what is verified, or the gem should require callers to independently confirm `request.shop` against a known/installed session store before trusting it as the tenant identity, and this requirement should be enforced/asserted by the library rather than left implicit.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com" and
# captures a real webhook delivery: raw_body + X-Shopify-Hmac-Sha256 header.

raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.hexdigest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
b64_hmac = Base64.strict_encode64([hmac].pack("H*"))

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => b64_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, unauthenticated
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "any-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Passes HMAC validation because only raw_body is signed:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
