### Title
Unrestricted `superApprove` allows any caller to grant unlimited ERC20 allowance on behalf of any token holder - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl` is a production ERC20 implementation used for cross-chain fungible tokens (bridged via the `HyperFungibleToken` mechanism, referenced from `TokenFaucet.sol`). It exposes a `public` function, `superApprove(address owner, address spender)`, that calls the internal `_approve(owner, spender, type(uint256).max)` directly, bypassing the standard `msg.sender == owner` requirement that ERC20's `approve()` enforces. [1](#0-0) 

### Finding Description
Normal ERC20 `approve(spender, amount)` only ever lets `msg.sender` (the token owner) set its own allowance. `HyperFungibleTokenImpl.superApprove` instead takes `owner` as an arbitrary parameter and calls the internal OpenZeppelin `_approve(owner, spender, amount)` primitive with no caller restriction and no signature/permit check:
```solidity
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
``` [1](#0-0) 

This is functionally identical to — but strictly worse than — the referenced `approveToRouter` bug class: instead of only being able to force the contract itself to grant an approval, any unprivileged caller can force an **arbitrary third-party owner's** balance to grant unlimited allowance to an **arbitrary spender** of the caller's choosing. The function carries no `onlyRole`, `onlyOwner`, or `msg.sender == owner` check, unlike every other privileged mutator in the same contract (`mint`, `burn`, `grantMinterRole`, etc.), which are all correctly gated with `onlyRole(...)`. [2](#0-1) 

The docstring calls it a "Helper function for tests," but it is compiled into the production contract source at `evm/src/utils/HyperFungibleTokenImpl.sol`, not a test-only mock, and it is referenced by `TokenFaucet.sol` in the same `evm/src/utils` production directory, confirming this implementation is part of deployable app-side token infrastructure rather than isolated test tooling. [3](#0-2) 

### Impact Explanation
Any address can call `superApprove(victim, attacker)` on a deployed `HyperFungibleTokenImpl` token to grant itself (or any spender) unlimited allowance over the victim's balance, then immediately call `transferFrom(victim, attacker, balance)` to drain the victim's entire token balance. This is a direct, unauthorized theft-of-funds primitive with no privileged role required — a Critical/High severity token-theft vector matching the report's bug class (unrestricted approval-granting entry point) but with a stronger blast radius (per-holder unlimited drain vs. router-approval-only exposure in the original report).

### Likelihood Explanation
Trivially and deterministically exploitable: `superApprove` is `public`, requires no special state, no proof, no signature, and no prior interaction from the victim. Any address holding tokens minted via a `HyperFungibleTokenImpl` deployment is exposed the moment the contract is deployed and any balance exists.

### Recommendation
Remove `superApprove` from production source entirely, or, if a helper is genuinely needed for tests, move it into a test-only mock contract under `evm/tests/` and never ship it in `evm/src`. If any production use case requires it, restrict it at minimum to `msg.sender == owner` (matching ERC20 semantics) or gate it behind role-based access control consistent with the rest of the contract's admin functions.

### Proof of Concept
1. Deploy or locate any live `HyperFungibleTokenImpl` token where `victim` holds a balance `B`.
2. Attacker (any address, no special role) calls:
   ```solidity
   token.superApprove(victim, attacker);
   ```
   This directly sets `allowance[victim][attacker] = type(uint256).max` via `_approve`, bypassing the `msg.sender == owner` check that `approve()` normally enforces.
3. Attacker calls `token.transferFrom(victim, attacker, B)` to drain the victim's entire balance. [4](#0-3)
