### Title
Endpoint-only validation in `swap_tokens` lets a delegate route collateral through an unvalidated intermediate venue that returns dust — ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller validates only the declared endpoints of a strategy swap — `token_in` (exact authorized pull) and `token_out` (positive measured balance delta) — while every intermediate hop inside `swap_xdr` executes against venues and tokens the controller never validates. This is the direct analog of the pyLoad SSRF redirect bypass: the initial URL (declared endpoints) is checked, but the hops actually traversed (redirect targets / route venues) are not. An account delegate, a permissioned-but-non-owner role, can invoke `swap_collateral` on a victim account with a crafted route whose venue absorbs nearly all input and returns dust, passing every controller check.

### Finding Description
`process_swap_collateral` authorizes the caller, checks the destination market via `require_can_supply`, then calls `withdraw_and_swap_from_supply`, which lands in `swap_tokens` [1](#0-0) .

`swap_tokens` performs exactly three validations:

1. `authorize_transfer_as_current` — grants the router one exact `token_in` pull [2](#0-1) 
2. `RouterOverspend` — `actual_spent <= amount_in` on the declared `token_in` [3](#0-2) 
3. `NoSwapOutput` — `received > 0` on the declared `token_out` [4](#0-3) 

The `swap` bytes are forwarded to the router untouched (`router.execute_strategy(&controller, &amount_in, swap)` at swap.rs:37). The controller never inspects `token_in`/`token_out` declared in the packed program header, never checks intermediate hop tokens, and never restricts venues. The router itself measures only its own per-hop balance deltas (`received <= 0 → ZeroOutput`; `spent != amount_in → InvalidAmount`) and enforces the payload's `min_out`, which the route author sets — so a hop that returns 1 unit of output against a huge input passes, and a `min_out` of 1 passes the final check. The threat model confirms the router "keeps no allowlist" of the pool/token addresses its payload names [5](#0-4) .

Back in the controller, `swap_collateral` then deposits the dust `swapped_amount` and runs `strategy_finalize`; for an account with no borrows, the health-factor gate is skipped entirely (`test_swap_collateral_no_borrows_skip_hf` shows the no-debt path succeeds unconditionally) [6](#0-5) . Even with borrows, the caller sizes `from_amount` so final HF still passes.

Critically, the call only requires `require_owner_or_delegate` — not ownership [7](#0-6) . A delegate is a limited permission (analogous to pyLoad's ADD permission), not the account owner, yet it can route the owner's collateral through an attacker-deployed venue.

### Impact Explanation
Theft of user funds. A delegate calls `swap_collateral(account_id, current, from_amount, new, steps)` where `steps` encodes a route through a venue contract the attacker controls. The venue receives `amount_in` from the router and returns a minimal positive output. The router's per-hop and min_out checks pass (all thresholds attacker-chosen), the controller's `NoSwapOutput` check passes on dust, and the residual collateral is deposited. The attacker pockets `from_amount − dust` of the victim's collateral at the venue. Repeatable until the supply position is drained; bounded only by position size and `from_amount` per call. `swap_debt`, `multiply`, and `repay_debt_with_collateral` share the same `swap_tokens` plumbing, but `swap_collateral` is the cleanest theft since it spends existing collateral with no HF gate when the account has no debt.

### Likelihood Explanation
Requires delegate authorization on the victim account — a real but restricted permission (delegates are typically automation/strategy contracts users authorize). That matches the advisory's reduced severity (authenticated ADD permission vs. unauthenticated). No oracle manipulation, no privileged admin, no upgrade needed; the malicious venue is a standard Soroban contract the attacker deploys, reachable because routes use unallowlisted venues by design. Likelihood is moderate: it needs a victim who has granted delegation, but nothing else.

### Recommendation
Do not rely on endpoint-only validation. Concretely:

- Decode the `StrategySwap` payload header in the controller and assert its `token_in`/`token_out` fields equal the declared assets before authorizing the input transfer (currently impossible — the controller forwards bytes blindly; the packed header fields are documented in `skills/xoxno-swap-aggregator/payload.md`).
- Enforce a controller-side minimum output for `swap_collateral`/`swap_debt` derived from Context-cached oracle prices (a `max_slippage_bps`-style bound), so dust output cannot satisfy `NoSwapOutput`.
- For delegate callers specifically, restrict strategy verbs to owner-or-approved-route allowlists, or add a per-account delegate permission flag for swap strategies.

### Proof of Concept
1. Attacker deploys `EvilVenue` contract: `swap(token_in, amount_in, token_out, to)` pulls `amount_in` via the router's invoker auth and returns `token_out.transfer(to, 1)`.
2. Victim account has USDC supply, no borrows, and has granted delegate status to attacker address/contract.
3. Attacker builds a `StrategyPayload` route: hop `USDC → EvilVenue → ETH` with `min_out = 1`.
4. Attacker calls `Controller::swap_collateral(attacker_delegate, victim_id, hub0(USDC), FULL_SUPPLY, hub0(ETH), steps)`.
5. Flow: collateral withdrawn to controller → router pulls exact `amount_in` → venue hop sends 1 ETH dust back → `min_out=1` passes → controller measures `received = 1 > 0` → deposits 1 wei ETH to victim → `strategy_finalize` passes (no debt). Attacker keeps ~all USDC at `EvilVenue`.
