### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on valid webhook deliveries - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  which is the exact byte string that `Utils::HmacValidator.validate` verifies against `Context.api_secret_key` [2](#0-1) . However, `Registry.process` trusts `request.shop` (parsed from the `x-shopify-shop-domain`/`shopify-shop-domain` header, not the body) to attribute the incoming event to a tenant when constructing `WebhookMetadata` [3](#0-2) , and `Request#shop` is implemented purely as a header read with no cryptographic binding [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`HMAC-verified-bytes == bytes-that-determine-shop-identity`

In `Request`, `hmac` is computed from the `x-shopify-hmac-sha256` header [5](#0-4) , and it is checked against `to_signable_string`, which is only `@raw_body` [1](#0-0) . The `shop` accessor is derived independently from the `shop-domain` header [4](#0-3)  and is never part of the signed material. `Registry.process` validates the HMAC over the body only, then unconditionally uses `request.shop` for the delivered `WebhookMetadata` that the host application's handler consumes to determine which tenant/shop the payload belongs to [3](#0-2) .

This means: an attacker who can produce (or replay/relay) any body+HMAC pair that is valid for the app's secret (e.g., from their own store's genuine Shopify webhook, or in a scenario where Shopify itself/any relay forwards the same signed body under an altered `shop-domain` header — e.g. through a proxy, load balancer, or logging/analytics intermediary that the host app trusts to pass headers through unmodified) can cause the gem to report the event as coming from a shop that never produced the payload. Since the HMAC never binds `shop-domain`, `Utils::HmacValidator.validate(request)` returns `true` regardless of what value is set in that header, satisfied purely by body/secret matching.

### Impact Explanation
This crosses a tenant boundary: the gem's own webhook processing pipeline hands the host application a `shop` value that is unauthenticated relative to the cryptographic guarantee the API surface (`HmacValidator.validate`) advertises to consumers. Any host application that follows the documented contract ("HMAC validated ⇒ shop is trustworthy") and uses `WebhookMetadata#shop` to look up per-tenant state, credentials, or to fan out data (e.g., customer data_request/redact GDPR webhooks) can be made to act on/for the wrong tenant. This matches the High-impact class of "cross-tenant access" via an identity-binding break, since the shop attribution is not actually validated by the signature check exposed by this gem.

### Likelihood Explanation
Exploitation requires the attacker to control or influence a header (`x-shopify-shop-domain`) independently of the signed body — realistic wherever headers pass through infrastructure not fully locked down to Shopify's exact forwarding (proxies, multi-tenant webhook ingestion endpoints, header-rewriting CDNs, or a merchant of one shop replaying their own genuinely-signed payload while manipulating the shop header before it reaches the app, since nothing in this gem prevents that). The gem provides no other tenant-binding check, so likelihood is moderate and entirely dependent on infrastructure/host trust in headers, which the gem's `Request`/`Registry.process` do not defend against.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the HMAC-signed material, or otherwise cryptographically bind them, e.g., by having `to_signable_string` concatenate the shop domain header with the raw body, or by requiring the host application to independently cross-check `request.shop` against a known/expected shop for the current request context before trusting `WebhookMetadata#shop`. At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is **not** part of the HMAC and must not be treated as authenticated.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com` and receives a legitimately Shopify-signed webhook with body `raw_body` and header `x-shopify-hmac-sha256: <valid_hmac>` computed over `raw_body` with the app's real `api_secret_key`.
2. Attacker (or an intermediary the host trusts to pass headers through) resends the exact same `raw_body`/`x-shopify-hmac-sha256` pair to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which recomputes the HMAC solely over `raw_body` [7](#0-6)  and succeeds because the header's shop value plays no part in the signature.
4. `WebhookMetadata.new(topic:, shop: request.shop, ...)` is built with `shop: "victim-shop.myshopify.com"` [8](#0-7) , and the host app's handler processes attacker-controlled data as though it originated from `victim-shop`.
