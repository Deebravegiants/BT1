## Title
Sub-`MINIMUM_LIQUIDITY` graduation permanently bricks `finalizeGraduation`, freezing curve-raised LT and the 250M LP reserve forever - (File: `packages/contracts/src/Bonding.sol`)

### Summary
The external report describes strongSwan mishandling an "empty but non-NULL" encoding during cloning, which is never freed correctly and later causes a fatal double-free when both copies are destroyed — a degenerate near-zero value that the code assumed could never legitimately occur, but does. The alt.fun analog is `Bonding._prepareGraduationLiquidity` / `finalizeGraduation`, which assumes `tokensForLP`/`ltFromPair` will always be large enough to satisfy HyperSwap V2's `pair.mint` `MINIMUM_LIQUIDITY` floor. When a token graduates via the **supply-exhaustion trigger** while the paired LT's `exchangeRate()` is tiny, `ltFromPair` (and consequently `tokensForLP`) can be pinned, at phase 1, to a value whose product's square root is `≤ 1000` — a legitimate, reachable "empty-but-non-zero" state that `finalizeGraduation` never re-derives or works around. Every call to `finalizeGraduation` then reverts inside `pair.mint`, permanently bricking the token in `Lifecycle.Graduating` with the curve's entire raised LT and the 250M reserved tokens frozen with no rescue path.

### Finding Description
`Bonding._enterGraduating` caches `(tokensForLP, ltFromPair, lpBurned, unsoldBurned)` from `_prepareGraduationLiquidity` at the moment the supply trigger (`IPair.tokenBalance() == 0`) or USD trigger fires: [1](#0-0) 

`ltFromPair` is computed purely from stored pair reserves (`assetReserve - virtualLtReserve`), and `tokensForLP` is `ltFromPair * tokenReserve / assetReserve`, both of which scale with the raw LT-wei amount actually raised on the curve — not with any USD floor. The supply trigger is explicitly designed to fire "in flat/bear markets where $9K is never reached," i.e. exactly the scenario where the LT's `exchangeRate()` can be arbitrarily depressed and the LT-wei amount raised for a full 750M-token sellout can be driven to a handful of wei: [2](#0-1) 

These cached values are frozen and reused verbatim in phase 2 — by design, "a recompute would return byte-identical values": [3](#0-2) 

`finalizeGraduation` then feeds the cached amounts straight into `_seedUniswapV2Direct` → `_seedDirectMint` (the empty-pair / dust-preseed regime, which covers ~99% of graduations) with no lower-bound check: [4](#0-3) [5](#0-4) 

`_seedDirectMint` transfers `tokensForLP` / `ltFromPair` to the pair and calls the canonical HyperSwap V2 `pair.mint(lpLock)`. Standard `UniswapV2Pair.mint` for a first deposit computes `liquidity = sqrt(amount0*amount1) - MINIMUM_LIQUIDITY` (locking `MINIMUM_LIQUIDITY = 1000` permanently) and reverts with `INSUFFICIENT_LIQUIDITY_MINTED` if that underflows or is zero. If `sqrt(tokensForLP * ltFromPair) <= 1000`, `pair.mint` reverts unconditionally on every future call, because the cached `(tokensForLP, ltFromPair)` never changes and there is no code path that adjusts, tops up, or bypasses this floor.

The same fragility is visible in `LPLock.recordLock`, which independently enforces `amount != 0` as a hard invariant with no rescue: [6](#0-5) 

This confirms the protocol's own design has no tolerance anywhere in the graduation pipeline for a degenerate near-zero LP mint — exactly the "empty but non-NULL" state class from the CVE, where a value that is technically non-zero/non-null but abnormally small is never re-validated before being consumed by code that assumes it is well-formed, and the consequence (here: a permanently reverting mint / permanently bricked lifecycle state) is catastrophic rather than benign.

Once `pair.mint` reverts inside `finalizeGraduation`, the token is stuck in `Lifecycle.Graduating` forever: `Bonding.buy`/`Bonding.sell` already reject trades in this lifecycle (`TokenIsGraduating`), phase 1 (`_enterGraduating`) cannot be re-run because `triggerGraduation` requires `Lifecycle.Curve`, and `_prepareGraduationLiquidity`'s drain (`Router.graduate(tokenAddress, ltFromPair)`) already moved the curve's real LT into `Bonding` at phase 1 — so that LT, plus the 250M `LP_RESERVE` tokens held by `Bonding`, are permanently unreachable by any unprivileged transaction.

### Impact Explanation
This is a permanent freeze of trader/LP funds: the curve's entire raised LT (drained into `Bonding` at phase-1 via `Router.graduate`) and the protocol's 250M reserved LP tokens become permanently stuck once a token's graduation lands with a sub-`MINIMUM_LIQUIDITY` mint size, since `finalizeGraduation` is the only path out of `Lifecycle.Graduating` and it deterministically reverts every time it is called against the frozen `pendingGraduation` values. There is no owner/admin escape hatch to adjust `tokensForLP`/`ltFromPair` or bypass the V2 mint floor. This satisfies the "permanent freezing of trader, creator or LP funds" acceptance criterion.

### Likelihood Explanation
Reachable by an unprivileged trader with no special permissions: buy on a freshly launched curve down to the last token via ordinary `Zap.buy`/`Bonding.buy` calls while the paired LT's `exchangeRate()` is low (either because the LT is naturally cheap, or a bear-market LT crash occurs, both explicitly anticipated by the protocol's own "flat/bear markets" rationale for the supply trigger). The attacker only needs `ltFromPair`/`tokensForLP` at full sellout to multiply to `≤ MINIMUM_LIQUIDITY^2 (1,000,000)` in raw units — plausible for any sufficiently cheap or high-precision LT, and entirely within a single trader's control since they choose how much LT to spend per buy and can size the final buy precisely via `Router.buy`'s overflow cap.

### Recommendation
Add a floor check in `_prepareGraduationLiquidity` / `_enterGraduating` (or `finalizeGraduation`) that verifies `sqrt(tokensForLP * ltFromPair) > MINIMUM_LIQUIDITY` before caching/committing to phase 2, and provide either an owner-gated remediation path (e.g., a way to top up the pair with additional inventory to clear the floor) or a defined fallback (skip HyperSwap LP seeding and let holders redeem their pro-rata share of the parked LT/tokens directly) for tokens that structurally cannot clear the V2 mint floor.

### Proof of Concept
1. `Zap.createToken` launches a token paired against an LT (`lt`).
2. `lt.exchangeRate()` is depressed (either a naturally cheap LT, or simulate a bear-market LT price crash via the mock's `setExchangeRate` in a test harness) so that buying the full 750M curve supply consumes only a few thousand LT-wei total.
3. An unprivileged trader repeatedly calls `Zap.buy` (respecting `Router.buy`'s overflow cap on the final buy) until `IPair.tokenBalance() == 0`, firing the supply trigger and `Bonding._enterGraduating`.
4. `_prepareGraduationLiquidity` caches `tokensForLP`/`ltFromPair` such that `sqrt(tokensForLP * ltFromPair) <= 1000`.
5. Any address calls `Bonding.finalizeGraduation(tokenAddress)`; the call reverts inside HyperSwap V2's `pair.mint` (`INSUFFICIENT_LIQUIDITY_MINTED`), and will revert identically on every future retry because `pendingGraduation[tokenAddress]` never changes.
6. The token is permanently stuck in `Lifecycle.Graduating`: no buys/sells are possible, and the curve-raised LT plus the 250M reserved tokens held in `Bonding` are unrecoverable.

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

Any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
