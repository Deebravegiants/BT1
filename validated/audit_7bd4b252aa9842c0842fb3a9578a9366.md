### Title
Session identity resolved from unverified, guessable cookie bytes enabling cross-tenant session hijack - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` resolves "the current session" for non-embedded requests (and for embedded requests lacking a session token) purely from the raw, client-supplied `shopify_app_session` cookie value, with no cryptographic verification that the value was ever issued by this library to the requesting client. Combined with the fact that this library generates fully deterministic, guessable session identifiers (`offline_#{shop}` / `#{shop}_#{user_id}`), an attacker who supplies a forged cookie value can make the host application resolve another merchant's session id, breaking the binding "session id returned == session id actually authenticated for this requester."

### Finding Description
When a session is created via `ShopifyAPI::Auth::Oauth.validate_auth_callback`, the resulting `Session#id` is computed deterministically: [1](#0-0) 

This id becomes the literal `value` of the cookie the gem instructs the host app to set on the browser: [2](#0-1) 

`ShopifyAPI::Auth::Oauth::SessionCookie` is a plain struct with no signature/MAC field at all: [3](#0-2) 

When resolving "the current session," `SessionUtils.current_session_id` and its helper `cookie_session_id` read this value straight out of the supplied `cookies` hash and return it unchanged — there is no HMAC check, no re-derivation, and no comparison against any authenticated identity: [4](#0-3) [5](#0-4) 

This is the exact analog called out in the rules: "a session id derived from unauthenticated bytes." The equality the library is supposed to guarantee is:

`session_id returned by SessionUtils == session_id that was legitimately bound to this specific caller's authenticated OAuth completion`

but the code actually implements:

`session_id returned by SessionUtils == whatever bytes appear in cookies["shopify_app_session"]`

Because `Session#id` for offline sessions is simply `"offline_#{shop}"` — a value fully determined by a shop domain that is normally public/discoverable — and for online sessions is `"#{shop}_#{associated_user.id}"` — a value determined by a shop domain plus a typically small, enumerable numeric Shopify user id — an attacker does not even need to observe a real cookie to construct a valid-looking session id for an arbitrary target shop.

### Impact Explanation
If the host application follows the documented pattern (store the `Session` object keyed by `session.id` in `SessionRepository`, and load "current session" using `SessionUtils.current_session_id`), an attacker who sets their own request's `shopify_app_session` cookie to `"offline_{target-shop}.myshopify.com"` (or `"{target-shop}.myshopify.com_{user_id}"`) causes the library to hand back that exact string as the resolved session id with zero verification. If the host's session store then loads the corresponding `Session`/access token by that id (exactly as shown in the gem's own documented flow), the attacker's request proceeds using another merchant's stored access token — cross-tenant access to that merchant's Shopify data using their access token, without ever completing OAuth for that shop. This matches the Critical impact category: cross-tenant access / theft of use of another merchant's access token.

### Likelihood Explanation
The precondition is only that the host session storage keys sessions by `Session#id` and that `current_session_id`'s returned value is used verbatim as a storage lookup key — which is precisely the pattern the gem's own API and flow encourage (`Session#id` is the only stable identifier exposed, and `SessionUtils` exists specifically to recover "the" session id from request context). No secret, token, or privileged access is required by the attacker: shop domains are public, and online-session user ids are small integers. The cookie itself carries no MAC, so nothing in this library prevents an attacker from fabricating it.

### Recommendation
- Never resolve a "current session id" from an unauthenticated, unsigned cookie value inside the library. At minimum, `SessionCookie` should carry a MAC (e.g., HMAC over the value using `Context.api_secret_key`) and `SessionUtils.cookie_session_id` should verify it before returning the id.
- Avoid embedding public/guessable identifiers (shop domain, sequential user id) directly as the sole session lookup key trusted from client-supplied bytes; if used, always require the accompanying request to independently prove the shop and user identity (e.g., signed session token) rather than trusting a raw cookie echo.
- Document explicitly (and enforce in-code where possible) that the `shopify_app_session` cookie value must never be treated as authenticated without an accompanying signature check performed by this library.

### Proof of Concept
1. Attacker knows (or discovers) `target-shop.myshopify.com`, a normal, non-secret piece of information.
2. Attacker sends a request to the host application (built per the gem's documented flow) with header/cookie:
   `Cookie: shopify_app_session=offline_target-shop.myshopify.com`
3. Host app framework calls:
   ```ruby
   session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)
   # => "offline_target-shop.myshopify.com"
   session = SessionRepository.load_session(session_id)
   ```
4. `SessionUtils.current_session_id` → `cookie_session_id` → returns the attacker-supplied string unchanged, per [4](#0-3)  and [5](#0-4) , with no verification that this id was ever legitimately issued to this caller.
5. If `target-shop`'s offline session was previously stored under exactly this key (as the documented flow does, since `Session.from` computes the same `"offline_#{shop}"` id per [1](#0-0) ), the host app now operates using `target-shop`'s stored access token on the attacker's behalf.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
    end
