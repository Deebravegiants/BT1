Webhook shop-domain (and topic/webhook-id/api-version) header not covered by HMAC allows tenant-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` but its `to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never part of the HMAC-verified bytes. `Registry.process` validates the HMAC and then hands the header-derived `shop` straight to the app's webhook handler as the trusted tenant identifier, without any check that it matches the shop that actually produced the signed body.

`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers, not from the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` then trusts `request.shop` (a header value never covered by the HMAC) as the tenant identifier passed into the app's handler via `WebhookMetadata`: [4](#0-3) [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` is shared across all shops installing the app (it is not per-shop), any party who can obtain one validly-signed webhook body for a topic (e.g., their own shop's webhook, or any webhook whose body content they can predict/replay, such as an empty-body `app/uninstalled` or a webhook with attacker-controlled resource content) can resubmit that exact body to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. The HMAC still validates because it is computed only from the body and the shared secret — it says nothing about which shop the header claims to be. This breaks the intended identity binding: **shop header == shop that produced the HMAC-signed bytes**. Instead the gem enforces only: **HMAC(body, secret) == received HMAC**, with `shop` parsed but never verified against the signature.

This exactly matches the reported bug class ("a field acted on but not covered by the HMAC") from the referenced report, applied here to the webhook shop-domain binding instead of a numeric swap value.

### Impact Explanation
This is a cross-tenant integrity issue: the documented and recommended usage pattern (`docs/usage/webhooks.md`) explicitly tells app developers to use `data.shop` as the shop/tenant key to route or persist webhook effects (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). Any app built per this gem's documented API is therefore exposed to processing an HMAC-"valid" webhook while attributing it to an attacker-chosen `shop` value, enabling cross-tenant data confusion/corruption in the host application — data intended for shop A gets attributed to and acted upon for shop B purely by header manipulation, without needing the app's actual secret for shop B or breaking cryptography. This rises to a High/Critical-tier cross-tenant impact per the classification (cross-tenant access), since the gem itself performs no binding between the verified bytes and the claimed shop.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook receiving endpoint and one legitimately-signed webhook body (which any merchant with the app installed can obtain by observing their own store's webhook traffic, or by triggering topics with static/predictable/empty bodies, e.g. many system topics send `{}`). No access token, `api_secret_key`, or privileged account is required — this fits squarely in the unprivileged-internet-user threat model. The attack is a straightforward HTTP replay with one header changed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) to the HMAC-verified data instead of trusting the raw header value in isolation:
- Include the shop-domain header (and other header fields the app will use for routing) in the signed string that `HmacValidator` verifies, or
- Cross-check the header-provided `shop` against a separate authenticated source of truth (e.g. verify the webhook by fetching/confirming the resource via an authenticated Admin API call to that specific shop's stored access token before trusting the header), or
- At minimum, update documentation and `WebhookMetadata` to make explicit that `shop` is unauthenticated header data and must not be used as a sole tenant key by consuming applications, while providing a verified-shop API that binds the header to the signed body.

### Proof of Concept
1. App has webhook topic `X` registered whose body Shopify sends as a fixed/empty JSON body, e.g. `{}` (as used in the gem's own tests):
```ruby
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, "{}")
headers_shop_a = {
  "x-shopify-topic" => "some/topic",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "shop-a.myshopify.com",
}
```
This is a legitimately-signed webhook for `shop-a`.

2. Attacker (or any party who intercepted/received this legitimate webhook to their own endpoint via their own installed app instance) resends the exact same body and HMAC header to the app's webhook endpoint, but swaps the shop header:
```ruby
headers_shop_b = headers_shop_a.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: headers_shop_b)
ShopifyAPI::Webhooks::Registry.process(request)
```

3. `Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb#26-31`, since it only hashes `"{}"`), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — the app now processes a forged webhook as if it originated from `victim-shop`, despite `victim-shop` never actually sending it.
