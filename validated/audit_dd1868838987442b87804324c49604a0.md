### Title
Unchecked `U128::as_u64()` truncation in `swap_token_amount_base_out` fee calculation can let a swapper pay far less than required input - ([File: program/src/processor.rs])

### Summary
`process_swap_base_out` / `process_swap_base_out_v2` compute the amount a user must pay in with `Calculator::swap_token_amount_base_out`, then convert the fee‑adjusted `U128` result to `u64` with `.as_u64()` instead of the checked `Calculator::to_u64()` helper used elsewhere in the same file. This is the same bug class as the external Halborn report: a value is silently truncated by an unchecked numeric downcast (there `uint80`, here the low 64 bits of a `U128`) instead of being validated, allowing the on‑chain accounting to diverge from the real, unbounded value.

### Finding Description
`Calculator::swap_token_amount_base_out` computes, for `Coin2PC`:
`amount_in = coin * amount_out / (pc - amount_out)` [1](#0-0) 

`amount_out` is fully attacker-controlled (`swap.amount_out` from `SwapInstructionBaseOut`), and the only guard before this call is a `checked_sub().unwrap()` inside the function, which merely prevents `amount_out >= pc` from underflowing (it panics instead) [2](#0-1) . An attacker can therefore pick `amount_out = pc_total - 1`, making the denominator `1`, so `amount_in = coin_total * amount_out`, a `U128` value that can vastly exceed `u64::MAX` (both `coin_total` and `pc_total` are `u64` pool reserves, so the product can be up to ~3.4×10^38, near the `U128` ceiling).

The processor then converts this oversized `U128` to `u64` using the unchecked `.as_u64()` conversion generated by `uint::construct_uint!` (`program/src/math.rs:11-16`), rather than `Calculator::to_u64()`, which uses `TryInto` and returns an error on overflow [3](#0-2) :

```rust
let swap_in_after_add_fee = swap_in_before_add_fee
    .checked_mul(amm.fees.swap_fee_denominator.into())
    .unwrap()
    .checked_ceil_div(...)
    .unwrap()
    .as_u64();
``` [4](#0-3) 

The identical pattern exists in `process_swap_base_out_v2` [5](#0-4) .

Whether this manifests as a full fund-theft primitive depends on the exact semantics of `uint::construct_uint!`'s `as_u64()` (wrap-around low‑64‑bits truncation vs. an internal panic on overflow). I could not fully confirm from the indexed source which behavior this crate macro implements in this repository's dependency version — this needs to be verified directly against the vendored/`Cargo.lock` version of the `uint` crate, ideally with a unit test reproducing `swap_token_amount_base_out` with `amount_out` close to a large pool's `total_pc_without_take_pnl`. If it truncates (as `as u64` casts do, and as the analogous Solidity bug in the report demonstrates for `uint80`), `swap_in_after_add_fee` becomes an arbitrary small value while `swap.amount_out` (the tokens paid to the user) remains attacker-chosen and large, and the only remaining guards (`user_source.amount < swap_in_after_add_fee`, `swap.max_amount_in < swap_in_after_add_fee`) would trivially pass, letting the swapper drain `amm_coin_vault`/`amm_pc_vault` for a negligible payment.

### Impact Explanation
If the underlying `as_u64()` behaves as a truncating cast (mirroring the reported Solidity `uint80` overflow), this allows direct theft of pool/vault funds by any unprivileged swapper submitting a single `SwapBaseOut`/`SwapBaseOutV2` transaction with an `amount_out` chosen close to the pool's `total_pc_without_take_pnl`/`total_coin_without_take_pnl`. That is a critical, direct-fund-loss primitive matching the "unbacked minting/insolvent pool accounting" impact class.

### Likelihood Explanation
The precondition (choosing `amount_out` just under the pool reserve) is fully within the caller's control and requires no special permissions—only a single transaction to a public swap instruction with attacker-chosen `amount_out`. Likelihood is high assuming the truncation behavior is confirmed; it depends entirely on the semantics of the `uint` crate's `as_u64()`, which I was unable to verify from the indexed files.

### Recommendation
Replace the unchecked `.as_u64()` calls that follow `swap_token_amount_base_out` (and any other place converting a "before validation" `U128` swap result) with the already-existing checked `Calculator::to_u64()` helper, returning `AmmError::ConversionFailure` on overflow instead of silently truncating, consistent with how `InvariantToken`/`InvariantPool` and `get_max_sell_size_at_price` already use `Calculator::to_u64` in some paths.

### Proof of Concept
Conceptual reproduction (needs confirmation against the actual `uint` crate build):
1. Create/observe a pool with large `total_coin_without_take_pnl` (`coin`) and `total_pc_without_take_pnl` (`pc`).
2. Call `SwapBaseOut` with `swap.amount_out = pc - 1` (direction `Coin2PC`), `swap.max_amount_in = <attacker's actual balance>`.
3. `swap_token_amount_base_out` computes `amount_in = coin * (pc - 1) / 1`, a huge `U128`.
4. `.as_u64()` on the further fee-adjusted `U128` silently drops high bits (if that is indeed the crate's behavior), yielding a small `swap_in_after_add_fee`.
5. The `user_source.amount < swap_in_after_add_fee` and `max_amount_in < swap_in_after_add_fee` checks pass trivially.
6. Attacker pays the tiny truncated amount but the vault sends out `swap.amount_out` (`pc - 1`), draining the pool.

Because I could not directly confirm the truncation-vs-panic semantics of `uint::construct_uint!`'s `.as_u64()` in this repository's exact dependency version, this should be validated with a concrete unit test (e.g., extending the existing `test_swap_base_in`/`test_calc_take_pnl` tests in `program/src/processor.rs` and `program/src/math.rs`) before treating this as a confirmed, exploitable finding.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
