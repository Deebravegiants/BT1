### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop` value that identifies which tenant the webhook belongs to is taken from an unauthenticated HTTP header that is never included in the HMAC computation. Because every shop that installs the app shares the same `api_secret_key`, an attacker who controls one legitimately-installed shop can capture a validly-signed webhook and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to point at a different, victim shop. The signature still validates because it only covers the body, so the handler processes attacker-controlled webhook data under the victim's tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is completely independent of the signed body: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. only the body is authenticated: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authentication gate, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler — there is no cross-check that the `shop` header corresponds to the secret/tenant that actually produced the signature: [4](#0-3) 

The equality that should hold is: `shop bound by HMAC == shop used as the tenant key for the handler`. In this implementation, the HMAC only binds `raw_body`, so `shop` (header) is disjoint from what is cryptographically verified. Since the same `api_secret_key` authenticates webhooks for every shop that has installed the app, any attacker who owns one such shop can obtain a validly-signed body/HMAC pair (e.g., by triggering any webhook topic on their own store) and then re-POST that body with the `hmac` unchanged but the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still return `true`, because it recomputes the signature only from `secret` and the body — the header value plays no role. The handler is invoked with `WebhookMetadata#shop` set to the spoofed victim shop, letting the attacker inject arbitrary webhook body content attributed to a shop they do not control.

### Impact Explanation
This breaks the tenant/identity boundary the HMAC is meant to enforce: an unprivileged holder of any one shop's installation can forge webhook events (arbitrary topic + arbitrary body, since they choose what triggers the original webhook and can send further bodies as long as they compute a valid HMAC using the shared secret is not even necessary — the HMAC of one legitimate event, replayed with a different `shop` header, is enough for the app to accept a spoofed tenant/shop attribution for that body). Any application logic keyed off `WebhookMetadata#shop` (order/customer syncing, billing, data writes scoped by shop) can be corrupted for a shop the attacker never installed the app on — cross-tenant access/injection.

### Likelihood Explanation
Any developer/merchant with the app installed on their own store can generate legitimately HMAC-signed webhook bodies at will (by performing actions that trigger webhooks, e.g. updating an order) and then replay that body to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secret, access token, or privileged access to the victim is required — only a normal, unprivileged install of the app by the attacker on their own account.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the signed material that is verified, or otherwise cryptographically tie the header values to the HMAC before trusting them:
- Include the `shop-domain` header (and other identity-bearing headers) in the string that is HMAC-verified, rejecting the request if they don't match what was signed, or
- Require the host application to independently confirm that the `shop` in the webhook belongs to a shop with a currently valid installed session before acting on the payload, and document this requirement prominently in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Attacker triggers any webhook topic on their own shop, capturing the resulting `raw_body` and its valid `x-shopify-hmac-sha256` value (both are delivered to the attacker's own registered endpoint, so no secret extraction is needed).
3. Attacker POSTs the exact same `raw_body`/`hmac` pair to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the signature from `raw_body` only and it matches, so `Registry.process` at [5](#0-4)  proceeds and calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and was authorized for `attacker-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
