### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute solely from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, while the HMAC signature that `Registry.process` validates only covers the raw request body. This breaks the identity binding: `shop delivered to the handler == shop covered by HMAC` does not hold, because the HMAC never signs the shop-domain header.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly and unauthenticated from a header: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string` (the body), never against `shop`: [3](#0-2) 

`Registry.process` accepts the request once the HMAC over the body validates, then forwards `request.shop` — the unauthenticated header value — straight into the handler's metadata, which is the value application code uses to attribute the webhook to a tenant: [4](#0-3) 

This is the same bug class as the report's `withdrawMarginUsd()` issue: a value that is *acted upon* (there: `pnl` amount driving `isMissingMargin`; here: the `shop` used for tenant attribution) is not actually covered by the mechanism meant to guarantee its integrity (there: `round down` silently zeroing the required check; here: the HMAC silently not covering the header). The identity equality that should hold — `shop authenticated by HMAC == shop delivered to the tenant-scoped handler` — is broken.

### Impact Explanation
Because Shopify webhooks are shared-secret HMAC (not per-shop keyed against the header) and any merchant/unprivileged user who installs the app can receive genuine webhook deliveries for their own shop with a valid HMAC, that same unprivileged user can capture a legitimate `(raw_body, hmac)` pair for their own shop and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still passes (it never inspected the header), and `Registry.process` calls the handler with `WebhookMetadata` populated from the attacker-controlled `shop` value. Any host application that uses `data.shop` to look up sessions/access tokens or to write data keyed by shop (which is the intended and documented usage pattern for webhook handlers in this gem) will process/attribute data under the wrong tenant — a cross-tenant confusion driven entirely by unauthenticated input that the gem itself hands to the handler as if it were verified.

### Likelihood Explanation
High feasibility for the described actor: no secrets are required beyond a webhook the attacker's own shop legitimately receives (attacker only needs their own app installation, which is available to any unprivileged merchant/tester). The header is trivially rewritable in any HTTP client, and the gem performs no comparison between the header and the HMAC-covered payload.

### Recommendation
Include the shop domain (and ideally topic/api-version) in the HMAC-signable payload, or otherwise cryptographically bind the shop identity delivered to the handler to the same bytes that are HMAC-verified (e.g., verify the header against a signed value not just the body), mirroring the report's remediation of ensuring the value acted upon is fully covered by the verification, not left to trust an unauthenticated side-channel field.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`) to the app's endpoint; attacker captures `raw_body` and the `x-shopify-hmac-sha256` value from that delivery.
2. Attacker POSTs the exact same `raw_body` and `x-shopify-hmac-sha256` to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual: `shop` becomes `"victim-shop.myshopify.com"` per [2](#0-1) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`raw_body` only) and succeeds since the body is unchanged: [5](#0-4) [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's order payload, which downstream application code will treat as authentic data belonging to the victim tenant: [7](#0-6) .

Note: I could not locate a separate `webhook_metadata.rb` file in the indexed portion of the repo (only references in `registry.rb`, `webhook_handler.rb`, and docs were found); the exact fields of `WebhookMetadata` beyond `shop`/`topic`/`body` could not be fully verified due to index coverage limits. If a full view of that struct is needed, a Devin session with full filesystem access could confirm.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
