### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the tenant-identifying field (`shop`) — read directly from the `x-shopify-shop-domain` header — is trusted and forwarded to the handler without being covered by that signature. The report's bug class is "entitlement/identity source that is validated on one field but acted on with another, unbound field"; here the equality that should hold is `hmac_signed_bytes == identity_bytes_acted_on`, but it does not.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are extracted straight from unauthenticated HTTP headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` validates only that the body's HMAC matches (`Utils::HmacValidator.validate(request)`), and if it passes, immediately trusts `request.shop` as the tenant identity for the handler, with no cross-check that the signed bytes are bound to that shop: [3](#0-2) 

`Utils::HmacValidator.validate_signature` computes the digest purely from `verifiable_query.to_signable_string` (i.e., raw body) and does a constant-time compare against the header-supplied `hmac` value — again, `shop` is never part of what's signed: [4](#0-3) 

The resulting `WebhookMetadata.shop` (used by host applications to route/scope data to a tenant) is populated from this unbound header value: [5](#0-4) 

Because Shopify computes this same HMAC over `raw_body` only (not headers) when delivering webhooks, any entity who has legitimately received one valid `(raw_body, hmac)` pair for their own store (which any merchant installing the app can obtain, as they receive their own webhooks) can replay that exact body+HMAC pair while substituting the `x-shopify-shop-domain` header value to name a different shop. `HmacValidator.validate` will still pass because the signature check never inspects the shop header, so the identity-binding equality `hmac-authenticated bytes == bytes used to establish tenant identity` is broken.

### Impact Explanation
This crosses the "cross-tenant access" impact category: a normal merchant/tenant of the app (unprivileged relative to other tenants) can forge webhook deliveries that the host application will process as originating from a victim shop, since the gem's own `Registry.process`/`Request` abstraction offers no protection — it hands host applications a `shop` value it never actually verified against the signed payload. Any host app relying on this gem's webhook verification for tenant attribution (a documented, intended use of `ShopifyAPI::Webhooks::Registry`) inherits this cross-tenant spoofing risk.

### Likelihood Explanation
Medium-to-high: exploitation requires only a normal app installation (any merchant can install a public app and receive at least one legitimate webhook for their own shop), no access token or secret is needed, and the attack is a simple HTTP replay with one header value changed. The generic JSON body used for many webhook topics (e.g., mandatory/compliance topics or shop-scoped topics whose payload doesn't itself repeat the shop domain) makes this practically exploitable, though the concrete impact for a given topic depends on whether the host app's handler further validates payload contents against `shop`.

### Recommendation
Bind the shop domain (and ideally the topic/webhook-id) into the value that is HMAC-verified — either by including these header fields in `to_signable_string`, or by having `Registry.process`/`HmacValidator` require Shopify's documented webhook signature scheme to also authenticate the shop-domain header (e.g., verify the webhook against the specific shop's session/secret and reject if the two identities disagree), consistent with how `Oauth::AuthQuery#to_signable_string` includes `shop` in its own signable fields: [6](#0-5) 

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture one legitimate webhook delivery for that shop: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid because `HMAC(secret, B) == H`), and `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but set `x-shopify-shop-domain = victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes `HMAC(secret, B)` and compares to `H` — it never inspects the shop header — so validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON B>, ...)`, and the host application processes/attributes body `B` to `victim-shop`, even though it never came from Shopify for that shop.
