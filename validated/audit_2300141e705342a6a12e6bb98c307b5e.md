### Title
`recapitalize` pays a real-token refund and credits cash from an unverified caller-supplied `amount`, draining pool custody — (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The `recapitalize` op treats the `amount` argument as proof that tokens were injected. It credits `min(amount, backing_shortfall)` to the cash book and transfers `amount - applied` of the pool's own token balance back to `payer`, without measuring the pool's balance delta. Any invocation that reaches this op without a preceding inbound transfer — i.e., an "unfunded" recapitalize via the controller's permissionless `recapitalize` entrypoint — causes the pool to pay out real custody tokens as a "refund" of money that never arrived, while still inflating `cash` by up to the shortfall. This is the on-chain analog of the EtherCrash cold-wallet drain: custody leaves the pool under the control of an unprivileged caller.

### Finding Description
`ops::recapitalize::accounting` computes `applied = amount.min(guards::backing_shortfall(&cache))` and `refund = amount - applied`, credits `applied` to cash and commits the state — all derived purely from the `amount` argument [1](#0-0) . `apply` then unconditionally sends `refund` tokens to `payer` via `cache.transfer_out` [2](#0-1) . There is no balance-delta measurement anywhere in the op: the header comment states the funding precondition ("The controller transfers `amount` into the pool before this call") as a convention, not an enforced check [3](#0-2) .

Unlike the measured-receipt settlement used elsewhere (the flash loan "checks the token balance after payout, after the callback and after repayment" [4](#0-3) ), `recapitalize` never reads the SAC balance. The pool's own regression test demonstrates the end state of an unfunded call: `recapitalize(hub, payer, custody)` leaves `token.balance(pool) == 0` while the cash book still claims the supplier's deposit exists, so subsequent withdrawals pass the pool's liquidity guards and only fail inside the SAC transfer [5](#0-4) .

Because the cash book is credited without custody, `backing_shortfall` shrinks by the phantom `applied` amount and `require_reserves`-style guards keep passing on a drained pool — the same book/custody divergence the test documents: "the book still claims more than the supplier's deposit" [6](#0-5) .

### Impact Explanation
Two compounded impacts on a single unprivileged call:

1. **Theft of user funds**: the refund leg transfers `amount - applied` of the pool's token balance to the attacker's `payer` address. Passing `amount` equal to the pool's full balance drains all custody, as demonstrated by the test assertion `assert_eq!(token.balance(&t.pool), 0, "custody is gone")` [7](#0-6) .
2. **Permanent freezing of the remainder / insolvency masking**: the `applied` portion inflates `cash` without backing, so solvency and liquidity guards read a solvent book while custody is empty. Legitimate suppliers' withdrawals revert inside the SAC `transfer` with `BalanceError = 10` rather than any pool guard [8](#0-7)  — every remaining depositor is permanently frozen out for the unbacked amount.

### Likelihood Explanation
The attack requires only reaching `pool.recapitalize` (owner-gated to the controller) through the controller's `recapitalize` entrypoint — which is on the permissionless surface (`scripts/permissionless_entrypoints.txt`) — with an `amount` the controller forwards to the pool without first completing an inbound token pull of the same magnitude. The pool provides no defense in depth: it trusts the argument, pays the refund in real tokens, and credits the book. No privileged role, leaked key, oracle manipulation, or timing dependency is needed; one transaction produces both the payout and the corrupted book. Note: the guarantee depends on the controller path forwarding `amount` unfunded; the pool side demonstrably performs no verification of that precondition, and the dedicated test asserts the drain is possible whenever the funding leg is skipped [9](#0-8) .

### Recommendation
Make `recapitalize` a measured-receipt op like the flash path:

1. In `ops::recapitalize::apply`, snapshot `token.balance(pool)` before accounting, and set `applied`/`refund` from `min(received_delta, backing_shortfall)` where `received_delta = balance_after - balance_before` of the actual inbound transfer — never from the caller-supplied `amount`.
2. Alternatively (or additionally), have the pool perform the pull itself via `transfer_from(payer, pool, amount)` inside the op, so custody and the book update atomically in one call.
3. After `cache.commit()`, assert `token.balance(pool) >= cache.snapshot().cash` (or the pool's standard backing check) and revert otherwise, converting any unfunded invocation into a no-op instead of a drain.


Call sequence an attacker needs (unprivileged): `controller.recapitalize(hub_asset, amount = pool_token_balance)` → pool credits `min(amount, shortfall)` to cash → pool transfers `amount - applied` to attacker. Repeating across every `(hub, token)` market empties the pool while books report solvency.

```rust
pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();
```

```rust
/// the SAC transfer. The market reports itself solvent and cannot pay.
#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
```
