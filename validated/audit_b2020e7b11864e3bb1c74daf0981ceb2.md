### Title
No vulnerability — `connection_worker.rs` client-side lack of size validation does not affect leader-side sanitize/cost-model guarantees - (File: tpu-client-next/src/connection_worker.rs)

### Summary
The premise that `connection_worker.rs`/`send_data_over_stream` performing no size/shape validation creates a leader-side vulnerability is incorrect. `tpu-client-next` is an outbound client library; the receiving validator's QUIC streamer independently enforces stream size bounds and rejects oversized payloads before any transaction reaches sanitize or cost-model logic, regardless of what an attacker's client sends.

### Finding Description
`ConnectionWorker::send_transaction` calls `send_data_over_stream`, which simply opens a QUIC unidirectional stream and writes the raw `WireTransaction` bytes with no size checks on the client side: [1](#0-0) , [2](#0-1) . However, this is entirely client-side code used by honest callers of the crate; an unprivileged attacker does not need to use this library at all — they can write arbitrary bytes directly to a QUIC stream against any validator's TPU endpoint. The actual security boundary is enforced on the **receiving** side in `streamer/src/nonblocking/quic.rs::handle_chunks`, which tracks accumulated stream size against `max_stream_data_bytes` and rejects (closing the connection) any stream whose size exceeds that configured limit: [3](#0-2) . The QUIC transport config additionally sets `stream_receive_window` to bound flow control at the same limit: [4](#0-3) . In the validator runtime, both `stream_receive_window_size` and `max_stream_data_bytes` are explicitly set to `solana_message::v1::MAX_TRANSACTION_SIZE`, i.e. the same bound the sanitizer/cost-model assumes: [5](#0-4) . A regression/unit test in the repo already asserts this rejection behavior for oversized streams: [6](#0-5) . Therefore any oversized "WireTransaction" byte buffer is deterministically rejected by the leader independent of what the sending client validates, and the sanitize/cost-model path downstream never sees a payload larger than the configured bound.

### Impact Explanation
No impact within scope. The client-side omission of validation in `connection_worker.rs` cannot cause a mismatch between declared compute-budget/loaded-accounts-data-size and real payload size on the leader, because the leader enforces its own independent, deterministic size bound at the QUIC transport layer before any parsing/sanitize/cost-model logic runs.

### Likelihood Explanation
Not applicable — the described attack does not require exploiting `connection_worker.rs` at all (an attacker can send raw bytes directly to a TPU QUIC endpoint), and regardless of the path taken, the receiving validator's `handle_chunks`/QUIC stream-size enforcement makes oversized payloads unreachable to the sanitize/cost-model path.

### Recommendation
No fix needed for this specific claim. (Optional hardening, out of scope: `send_data_over_stream` could pre-validate transaction length against `MAX_TRANSACTION_SIZE` before writing to the stream purely as a client-side fast-fail optimization, but this has no security implication since the server enforces the bound independently.)

### Proof of Concept
Not applicable — no vulnerability. The existing test `test_client_connection_close_invalid_stream` in `streamer/src/nonblocking/quic.rs` already demonstrates that a stream of `PACKET_DATA_SIZE + 1` bytes is rejected and the connection closed with `CONNECTION_CLOSE_CODE_INVALID_STREAM`, confirming the invariant holds.
