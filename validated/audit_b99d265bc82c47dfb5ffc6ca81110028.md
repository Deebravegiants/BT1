### Title
Forced solver-only beneficiary in `IntentsBase._withdraw()` permanently freezes all escrowed input tokens for a commitment if the solver is blacklisted on any one token - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` iterates over every token in a `WithdrawalRequest` and transfers each one to a single `beneficiary` address, plus any accumulated relayer/protocol fees. For cross-chain fills, `ExtrinsicIntents._fillCrossChain()` hardcodes this beneficiary to `msg.sender` (the solver) with no ability to designate a different recipient per token, unlike the order's own `output.beneficiary` field which is configurable by the order creator.

### Finding Description
In `_fillCrossChain` (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:164-220`), the escrow-redemption message dispatched back to the source chain is built with: [1](#0-0) 
which hardcodes the beneficiary field to `bytes32(uint256(uint160(msg.sender)))` — the filling solver — with no parameter to specify an alternate recipient.

When this `RedeemEscrow` message lands on the source chain, `onAccept` calls `withdraw()`/`_withdraw()`, which loops through **all** escrowed input tokens for the commitment and transfers each to that single `beneficiary`: [2](#0-1) 

and then forwards any accumulated relayer/transaction fees to the same address: [3](#0-2) 

If any single escrowed token (e.g., a USDC-like token with an issuer-controlled blacklist) is blacklisted for the solver's address, `IERC20(token).safeTransfer(beneficiary, amount)` reverts. Because the loop and the whole `_withdraw` call are atomic, that single reverting transfer aborts release of **every other token** in the order's input set as well as the accumulated transaction fees — there is no partial-success path and no way for the solver to redirect the stuck token (or even the unaffected tokens) to a different address. The equivalent Tron variant, `IntentGatewayV2.withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol:691-730`, has the identical structure and root cause.

### Impact Explanation
This can permanently freeze a solver's legitimately earned input-token escrow across an entire multi-token order: a blacklist on just one token (well within the issuer's unilateral control, e.g., USDC) is enough to lock the solver out of all other tokens and fees tied to that commitment, since `_withdraw()` has no recipient override and no per-token retry/partial-fill mechanism for the settlement leg. This is a concrete freezing-of-funds scenario reachable by any solver who fills a cross-chain intent order in the ordinary course of protocol use — no privileged action required.

### Likelihood Explanation
Likelihood is realistic wherever the escrow token set includes a centrally-blacklistable stablecoin (USDC being the most prominent example) and a solver's address is or becomes blacklisted for any reason (e.g., prior involvement in a flagged transaction, sanctions list additions, or issuer error). Since solver addresses are typically hot, actively-trading addresses interacting with many counterparties, the exposure surface is non-trivial and increases with protocol usage over time.

### Recommendation
Allow the solver to specify a distinct recipient per redemption (or at minimum an alternate global recipient) analogous to `order.output.beneficiary`, and/or make `_withdraw()` resilient to a single token's transfer failure — e.g., by attempting each transfer independently and accounting a failed transfer as a separately claimable balance (pull-based) rather than reverting the whole batch, so a blacklist on one token cannot block release of the rest.

### Proof of Concept
1. Solver A fills a cross-chain order whose `order.inputs` escrow two tokens on the source chain: USDC and DAI.
2. Solver A calls `fillOrder`/`_fillCrossChain` on the destination chain; this hardcodes the redeem-escrow beneficiary to Solver A's address and dispatches the `RedeemEscrow` POST request to the source chain (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:207-212`).
3. Before the message is delivered, Solver A's address is added to the USDC blacklist (by Circle, independent of the protocol).
4. When the relayer delivers the message, `onAccept` → `withdraw()` → `_withdraw()` attempts to transfer USDC first (or DAI first, order-dependent); the USDC `safeTransfer` to Solver A reverts because of the blacklist.
5. The entire `_withdraw()` call reverts, so Solver A cannot retrieve the escrowed DAI either, and the accumulated relayer/transaction fees for the commitment also remain stuck, with no parameter in the withdrawal path to redirect any of these assets to an unblacklisted address.
