### Title
Budget-capped rebalance swap lets an attacker seed the HyperSwap V2 graduation pool materially off the curve-close price, transferring value out of the protocol-locked LP - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`quoteAllAvailablePoolsWithTimePeriod` in M-11 was exploitable because it derived a price from a set of Uniswap V3 pools whose liquidity an attacker could dominate, letting a low-liquidity outlier skew the weighted-average price used downstream. alt.fun has no multi-pool price oracle, but it has the structural analog the task's mapping calls out explicitly: LP seeding into an attacker-influenceable HyperSwap V2 pair during graduation, where the *pool's own reserves* (fully controllable pre-graduation by any wallet) are used as the input to a corrective pricing calculation (`_pairRebalance` / `_noFeeSwapInput`) that determines the final LP-open price. Because the corrective swap is capped at a fixed per-side budget, an attacker who seeds an extreme reserve ratio can force the cap to bind, and the LP is deposited materially away from the curve-close price - the exact "LP seeded away from curve close price" impact category called out as in-scope.

### Finding Description
Graduation computes a target ratio `(tokensForLP, ltFromPair)` from the curve's own reserves at the moment of the threshold-crossing buy (`_prepareGraduationLiquidity`, `packages/contracts/src/Bonding.sol:1073-1096`) and caches it in `pendingGraduation`. Anyone can, before `finalizeGraduation` runs, permissionlessly create the HyperSwap V2 TOKEN/LT pair and call `pair.mint()` against a self-funded, arbitrarily skewed reserve ratio (the "mint pre-seed" regime documented in `packages/contracts/AGENTS.md:176-189`).

`finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` then tries to correct the hostile ratio back toward the cached target by computing a no-fee corrective swap size (`_noFeeSwapInput`, closed-form `s = sqrt(reserveIn·reserveOut·targetN/targetD) − reserveIn`) and executing it directly against the pair via `_pairRebalance`, capped at a fixed fraction of the graduation's own inventory (the "per-side budget" referenced in `AGENTS.md:180` and exercised by `test_hostilePreSeed_budgetCappedSwap_isNotProfitable`, `packages/contracts/test/TwoPhaseGraduation.t.sol:864-900`). When the attacker's pre-seed ratio is extreme enough (the test uses TOKEN reserve at 1% of target and LT reserve at 200x target), the *optimal* corrective swap size exceeds the budget cap, so the swap only partially corrects the ratio, and the remaining inventory is deposited via `router.addLiquidity` at whatever ratio results.

The test explicitly demonstrates and accepts the outcome: [1](#0-0) 

The comment on this test states the pool "opens materially off curve-close" - roughly 2x the target price in the reproduced scenario - and the security writeup rationalizes this purely from the *attacker's* P&L ("Net P&L ≤ 0"), never analyzing the *protocol-owned LP's* exposure: [2](#0-1) 

Because the LP tokens minted from this off-ratio deposit are permanently locked in `LPLock` (`packages/contracts/src/Bonding.sol:1031`, `LPLock.recordLock` is documented as a one-shot call `finalizeGraduation` cannot skip), the protocol/LP holders - not the attacker - are on the hook for the arbitrage loss that closes the price gap once the pool is live: an arbitrageur who is not the attacker trades against the mispriced pool, extracting the price-gap value from the locked LP's reserves.

### Impact Explanation
This is the alt.fun-shaped analog of M-11's "manipulatable low-liquidity price source distorts a downstream financial calculation": an attacker-controlled, essentially zero-cost pre-seed of the HyperSwap pool (a low-liquidity venue the attacker fully dominates pre-graduation) is used as an input to the rebalance math, and when the correction is budget-capped, the protocol's own permanently-locked LP opens materially off the curve-close price. The subsequent arbitrage that closes the gap extracts real value from LP holders (the protocol/LPLock), i.e., LP fund loss - one of the explicitly accepted impact categories (LP seeded away from curve close price). This qualifies as Medium severity: it requires a specific, attacker-chosen extreme pre-seed ratio to bind the budget cap (not every pre-seed triggers it), it does not brick the flow, and honest graduations are unaffected, but when triggered it causes a quantifiable, permanent value transfer out of the protocol-locked liquidity.

### Likelihood Explanation
Reachable by any unprivileged wallet: `Bonding.finalizeGraduation` is permissionless and pool creation/`pair.mint()` on HyperSwap V2 require no special role. An attacker only needs to fund a token+LT pre-seed at an extreme ratio (as cheaply as dust on one side, inflated on the other) before the keeper's `finalizeGraduation` call lands, which is a race the attacker can win by front-running or simply acting before any bot does (the two-phase graduation design leaves a window between phase 1 entering `Graduating` and phase 2 finalizing). The team's own test suite constructs and validates this exact scenario, confirming it is a known, reachable configuration rather than a theoretical edge case.

### Recommendation
- Do not rely solely on a fixed-percentage swap budget to bound the correction; instead, either (a) revert/queue finalization when the required corrective swap exceeds the budget rather than silently depositing at an off-ratio price, routing to an operator-assisted retry path, or (b) size the budget dynamically so it always fully corrects the ratio regardless of how extreme the pre-seed is (using the full available inventory before falling back to a partial deposit), and (c) explicitly account for and cap the maximum LP-value loss to `LPLock` in the invariant tests, rather than only asserting attacker P&L ≤ 0.
- At minimum, extend the accepted-residual documentation and tests to bound and monitor the case where the price-gap loss is borne by the protocol-locked LP rather than the attacker.

### Proof of Concept
Already present in the repository's own test suite, confirming the mechanism end-to-end: [3](#0-2) 

1. Launch a token and let it enter `Lifecycle.Graduating` (`_enterGraduating`), caching `(tokensForLP, ltFromPair)`.
2. Before `finalizeGraduation` is called, an unprivileged attacker creates the HyperSwap V2 TOKEN/LT pair and calls `pair.mint()` with `reserveToken = tokensForLP/100` and `reserveLt = ltFromPair*200` (the `_grieferMintPreSeed` helper in the test).
3. Call `Bonding.finalizeGraduation(tokenAddress)` (permissionless).
4. The optimal corrective swap size computed by `_noFeeSwapInput` exceeds the per-side budget cap, so the swap only partially rebalances; `_routerDepositAndDispose` deposits the remaining inventory at the still-skewed ratio.
5. Post-finalization, `_poolPriceLtPerToken` shows the pool price is >1.2x (in the reproduced test, ~2x) the cached curve-close target, and the resulting LP is permanently locked via `LPLock.recordLock`, exposing it to arbitrage loss.

```text
    function test_hostilePreSeed_budgetCappedSwap_isNotProfitable() public {
        (address tokenAddr,) = _launchToken();
        _enterGraduating(tokenAddr);

        (uint256 tokensForLP, uint256 ltFromPair,,) = bonding.pendingGraduation(tokenAddr);

        // Extreme LT-rich shape: TOKEN side at 1% of target, LT side at 200x.
        // The optimal TOKEN-in swap to reach the cached ratio is ~1.4x
        // `tokensForLP`, so the 99%-of-`tokensForLP` budget cap binds and the
        // pool stays ~2x off curve-close after the swap.
        uint256 reserveToken = tokensForLP / 100;
        uint256 reserveLt = ltFromPair * 200;

        // M-02 precondition: the optimal swap exceeds the budget (this is the
        // budget-capped regime, distinct from the swap-rounds-to-zero fallback
        // covered by the dust tests above).
        assertGt(
            _noFeeSwapInputUncapped(reserveToken, reserveLt, tokensForLP, ltFromPair),
            (tokensForLP * 99) / 100,
            "setup: optimal rebalance swap must exceed the per-side budget (M-02 regime)"
        );

        deal(tokenAddr, griefer, reserveToken);
        address hyperPair = _grieferMintPreSeed(tokenAddr, reserveToken, reserveLt);
        uint256 grieferLp = MockHyperswapPair(hyperPair).balanceOf(griefer);
        uint256 ownerLtBefore = lt.balanceOf(bonding.owner());

        bonding.finalizeGraduation(tokenAddr);
        assertTrue(bonding.isGraduated(tokenAddr), "finalize must succeed despite an unrecoverable pre-seed");

        // The accepted residual: no bounded swap can correct a 200x LT-rich
        // pre-seed, so the pool opens materially off curve-close.
        assertGt(
            _poolPriceLtPerToken(hyperPair, tokenAddr),
            (((ltFromPair * 1e18) / tokensForLP) * 12) / 10,
            "M-02 regime: pool opens materially off curve-close"
        );
```

```markdown
### Attacker P&L outcome

After the fix, the attacker holds LP at the curve-close ratio. The arbitrage-back-to-true-price step that the attacker wanted to extract from is gone (we already arb'd it during the rebalance, paying the V2 0.3% fee back to ourselves as ~99% LP holder via the pair's K-invariant accounting). Attacker's LP claim ≈ what they put in, modulo the `MINIMUM_LIQUIDITY` lock and a tiny share of the fee they paid. **Net P&L ≤ 0** — the attack is cost-negative. This property was previously asserted directly but is no longer guarded by an automated test; future protocol changes that touch the rebalance / deposit path should re-derive it manually.

### Pool-open precision

Honest graduations open at 0 bps gap (Regime 1, exact direct mint). Dust mint pre-seeds also open at ~0 bps — they take the `_seedDirectMint` fallback, which deposits at the cached ratio with only a vanishing skew from the dust reserves. Larger mint pre-seeds (where the rebalance swap fires) open within ~50 bps — the structural ceiling is the V2 fee landing between rebalance and deposit (~30 bps) plus integer rounding in the router's `quote()`-based split (~10 bps). 50 bps is well inside "exploit denied" — arbitrage closes the gap within blocks and the attacker still loses pre-seed value.
```
