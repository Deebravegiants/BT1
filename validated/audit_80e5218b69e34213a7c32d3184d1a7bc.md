### Title
Race between `write()` and `destroy()` in seco-rw allows encryption with a zero-filled `blobKey` - (File: `libraries/seco-rw/src/index.js`)

### Summary
`seco-rw`'s `write()` checks the `destroyed` flag synchronously at entry but then performs long-running `await`ed encryption using the same `blobKey` `Buffer` object that `destroy()` can zero-fill in place with no locking. Because `destroy()` is synchronous and mutates the shared buffer by reference, a `destroy()` call interleaved after the `destroyed` check (but before the underlying async encryption in `secure-container` finishes consuming the key) can cause the wallet file to be encrypted with a zeroed/corrupted key.

### Finding Description
`write()` in [1](#0-0)  checks `destroyed` once, synchronously, then calls `secoFile.write(file, data, { metadata, blobKey, overwrite: true, header })` passing the module-scoped `blobKey` Buffer by reference. `destroy()` is fully synchronous and does not set any lock or in-flight-operation flag: [2](#0-1) .

`secoFile.write` forwards the same `options` object (including the `blobKey` reference) into `secure-container`'s `encrypt()`: [3](#0-2) . Inside `encrypt()`, when `options.metadata && options.blobKey` are supplied, `blobKey = options.blobKey` reuses the exact same buffer object (no copy) and it is then passed into `await conBlob.encrypt(data, metadata, blobKey)`: [4](#0-3) .

Because JS is single-threaded but `await` yields control at each async boundary, if an attacker-influenced code path (e.g., a dapp/RPC-triggered wallet lock/logout flow calling `destroy()`) races with an in-flight `write()` (e.g., a pending wallet backup/persist operation), `destroy()`'s `blobKey.fill(0)` can execute after `write()`'s synchronous `destroyed` check has already passed but before `conBlob.encrypt` has finished consuming the key bytes. Since `blobKey` is the same object reference throughout the call chain (never cloned before use), zero-filling it in `destroy()` directly corrupts the key `write()` is using for encryption in that in-flight call, producing a file encrypted with an all-zero/corrupted key.

No mutex, in-flight-operation counter, or key-cloning exists at any layer (`seco-rw`, `seco-file`, `secure-container`) to prevent this interleaving.

### Impact Explanation
If `destroy()` is invoked concurrently with `write()`, the resulting wallet backup/persisted file can be encrypted using a zero-filled or corrupted `blobKey` instead of the intended key material, silently producing an insecure/predictable-key wallet file at rest. This is a wallet-storage integrity/confidentiality issue: any party later reading or exfiltrating that file could recover plaintext wallet data because the encryption key is not the intended random 32-byte key.

### Likelihood Explanation
Exploitability requires that both `write()` and `destroy()` on the same `seco-rw` instance be reachable and triggerable near-simultaneously by application logic driven by untrusted RPC/dapp events (e.g., a dapp-triggered lock/logout racing a pending write/backup). Whether this dual-call pattern is reachable from an unprivileged dapp/RPC surface depends on how the wallet application wires `seco-rw` instances to lock/write flows, which is outside `seco-rw` itself — this repo only confirms the underlying primitive is unsafe under concurrent use, not that a concrete unprivileged caller path exists in this codebase. This uncertainty should be resolved by checking the wallet-side callers of this library's `write`/`destroy` methods.

### Recommendation
- Guard `destroy()` and `write()`/`read()` with an in-flight-operation counter or mutex so `destroy()` waits for pending operations to complete (or immediately aborts/rejects the in-flight call) before zero-filling `blobKey`.
- Clone `blobKey` into a local buffer before passing it down the async call chain, and zero the clone (not the shared buffer) so `destroy()` cannot corrupt a key already committed to an in-flight encryption.
- Re-check `destroyed` after each `await` point in `write()`/`read()`, or make `destroy()` mark the buffer for later destruction only after in-flight promises settle.

### Proof of Concept
Integration test in `libraries/seco-rw/test/seco-rw.test.js`:
1. Create a `seco-rw` instance and call `write(data)` once to establish `blobKey`/`metadata` (unlocking the `metadata` branch of subsequent writes).
2. Fire a second `write(newData)` and, before its promise resolves, synchronously call `destroy()` (e.g., via `Promise.resolve().then(() => destroy())` scheduled to run in the same microtask window as `conBlob.encrypt`'s internal `await`).
3. Await the `write()` promise, then read the raw encrypted file / instrument `conBlob.encrypt` to capture the `blobKey` value used at encryption time.
4. Assert either: (a) `write()` throws/aborts entirely once `destroy()` has been called, or (b) the key bytes actually used for encryption are never all-zero and match the pre-`destroy()` key. Currently this assertion fails intermittently depending on scheduling, demonstrating the race.
