### Title
Unbounded index into MMR/heads Merkle-proof leaves array via attacker-supplied `leaf_index`/`index` in BEEFY parachain-heads and MMR-leaf verification - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The CVE analog is a bounds-unchecked index derived from untrusted, attacker-controlled input driving an array access. In Hyperbridge's BEEFY consensus verifier, `verify_parachain_headers` and `verify_mmr_leaf` build leaf indices directly from relayer-supplied `ParachainHeader.index` and `MmrProof.leaf_indices` fields and pass them into `rs_merkle`/`mmr_lib` proof verification without validating that these indices are within the bounds implied by `total_leaves`/`leaf_count` before use.

### Finding Description
`verify_parachain_headers` takes `para_header.index` values straight from the untrusted `ConsensusMessage.parachain.parachains` vector (submitted by any relayer in an unsigned extrinsic) and uses them, unchecked against `parachain_proof.total_leaves`, as leaf indices for the merkle multi-proof verification: [1](#0-0) 

Likewise, `verify_mmr_leaf` reads `mmr.mmr_proof.leaf_indices[0]` (already guarded for length==1, per a documented prior panic fix) and derives `mmr_size`/`leaf_pos` from it, feeding those into `MmrMerkleProof::verify` with items whose count also comes from the same untrusted message: [2](#0-1) 

This is analogous to the Xpdf `FoFiType1C::convertToType1` bug class: an attacker-controlled index value is used to look up/derive positions in an array structure (`charset`/leaves) without validating the index is within the bounds implied by the structure's declared size, before any deeper cryptographic check can reject it. Here the equivalent "array" is the (`proof.items`, MMR size) pair and the ("leaves", `total_leaves`) pair; `leaf_index_to_mmr_size`/`leaf_index_to_pos` and `rs_merkle`'s verify walk index computations based on this attacker value.

The Pharos SPV verifier module in this same codebase demonstrates the project was previously bitten by exactly this bug class: `nibble_at_depth` used to panic on out-of-bounds indices derived from an over-deep, attacker-supplied proof (`modules/consensus/pharos/primitives/src/spv.rs`), and was fixed with an explicit `MAX_PROOF_DEPTH` guard and `Option`-returning bounds check: [3](#0-2) 

The BEEFY verifier's `verify_mmr_leaf` similarly documents a prior panic from an unchecked `[0]` index on an empty `leaf_indices` vector that was fixed by adding a length check for exactly one entry: [4](#0-3) 

However, `verify_parachain_headers` does not have an equivalent explicit bound on `para_header.index` relative to `parachain_proof.total_leaves`/`proof.len()` before those indices flow into `MerkleProof::verify`'s internal indexing logic; the correctness relies entirely on the underlying `rs_merkle` library's internal bounds handling rather than an explicit domain check in this codebase, unlike the Pharos module which was hardened after a discovered panic.

### Impact Explanation
If the underlying merkle-proof library does not itself gracefully reject an index that is out of bounds relative to the declared leaf/subtree size (as was the case for the in-house Pharos hexary-trie code before its fix, and for BEEFY's own `leaf_indices[0]` before its fix), an attacker submitting a crafted unsigned BEEFY consensus message (`handle_unsigned` / `verify_consensus`) could trigger a panic (denial of service on validator/runtime nodes processing the extrinsic) or, in the worst case, an out-of-bounds read that could corrupt/misattribute verification results in the finality/height determination path used by `EvmHost`/`HandlerV2` and other pallets that trust the resulting parachain header commitments.

### Likelihood Explanation
Medium: this path is reachable by any unprivileged relayer submitting a consensus proof/extrinsic (`pallet-ismp::handle_unsigned` / BEEFY consensus proof submission), matching the required "single dispatched request/relayed proof" reachability. The codebase's own commit history (visible via the fix comments for `leaf_indices[0]` and Pharos's `nibble_at_depth`) shows this exact bug class has already manifested twice in this repository, which raises confidence that the pattern recurs where explicit bound checks were not added — specifically in `verify_parachain_headers`'s use of `para_header.index`.

### Recommendation
Explicitly validate that every `para_header.index` (and any other relayer-supplied leaf index feeding merkle/MMR verification) is strictly less than the corresponding declared leaf count (`parachain_proof.total_leaves`) before it is used to build `leaf_indices`/before calling `MerkleProof::verify`, mirroring the guard already added for `mmr.mmr_proof.leaf_indices.len() != 1` and for Pharos's `MAX_PROOF_DEPTH`/`nibble_at_depth` bounds check. Apply the same defensive check anywhere else in the consensus-verifier crates where an untrusted numeric field is used as an array/tree index before proof verification.

### Proof of Concept
A relayer submits a `ConsensusMessage` whose `parachain.parachains` contains a `ParachainHeader { index: <value >= total_leaves or otherwise out of the tree's addressable range>, ... }` alongside a `proof.total_leaves` that does not bound it, and dispatches this via the unsigned consensus-update extrinsic path that reaches `verify_consensus` → `verify_parachain_headers`. Whether this crashes the node/panics or is silently rejected depends on `rs_merkle`'s internal handling, which is not verified/tested in this codebase for out-of-range indices (unlike the `MAX_PROOF_DEPTH` regression test present for the Pharos path) — this residual uncertainty is exactly the class of issue CVE-2019-12957 describes (unvalidated index into a bounded structure).

pub fn verify_parachain_headers<H: Keccak256>(
	heads_root: H256,
	parachain_proof: ParachainProof,
) -> Result<Vec<ParachainHeader>, Error> {
	if parachain_proof.parachains.is_empty() {
		return Ok(vec![]);
	}

	let mut indexed_leaf_hashes = Vec::with_capacity(parachain_proof.parachains.len());

	for para_header in &parachain_proof.parachains {
		let leaf = (para_header.para_id, para_header.header.clone());
		let hash: [u8; 32] = H::keccak256(&leaf.encode()).into();
		indexed_leaf_hashes.push((para_header.index as usize, hash));
	}

	indexed_leaf_hashes.sort_by_key(|(index, _)| *index);

	let (leaf_indices, leaf_hashes): (Vec<usize>, Vec<[u8; 32]>) =
		indexed_leaf_hashes.into_iter().unzip();
	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(parachain_proof.proof.clone());
	let valid = merkle_proof.verify(
		heads_root.0,
		&leaf_indices,
		&leaf_hashes,
		parachain_proof.total_leaves as usize,
	);

	if !valid {
		Err(Error::InvalidParachainProof)?;
	}

	Ok(parachain_proof.parachains)
}

fn verify_mmr_leaf<H: Keccak256 + Send + Sync>(
	mmr: &MmrProof,
	mmr_root: H256,
) -> Result<(), Error> {
	// `leaf_indices` is supplied by the relayer in the unsigned consensus message;
	// an empty vector previously panicked the runtime via the unchecked `[0]` index
	// after the BEEFY signature and authority membership checks had already succeeded.
	// This verifier checks a single MMR leaf, so reject any proof that does not carry
	// exactly one leaf index.
	if mmr.mmr_proof.leaf_indices.len() != 1 {
		Err(Error::InvalidMmrProof)?
	}
	let leaf_index = mmr.mmr_proof.leaf_indices[0];
	let leaf_hash = H::keccak256(&mmr.latest_mmr_leaf.encode());
	let mmr_size = leaf_index_to_mmr_size(leaf_index);

	let mmr_proof = MmrMerkleProof::<[u8; 32], KeccakMerge<H>>::new(
		mmr_size,
		mmr.mmr_proof.items.iter().map(|h| (*h).into()).collect(),
	);
	let leaf_pos = leaf_index_to_pos(leaf_index);
	let leaf = (leaf_pos, leaf_hash.into());
	let valid = mmr_proof
		.verify(mmr_root.into(), vec![leaf])
		.map_err(|e| Error::MmrVerificationFailed(e.to_string()))?;

	if !valid {
		Err(Error::InvalidMmrProof)?
	}

	Ok(())
}
