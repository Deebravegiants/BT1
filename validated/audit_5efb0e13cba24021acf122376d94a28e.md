### Title
Persistent PCP upload queue resets `next_id` counter while un-popped entries still exist on disk, allowing ID reuse and cross-signup overwrite of biometric custody package data - (File: `src/agents/data_uploader.rs`)

### Summary
The `data-uploader` agent's `Queue::Persistent` variant assigns each queued personal-custody package (PCP) a `u64` id used as its on-disk directory name, and advances a `next_id` counter for uniqueness. `Queue::commit` resets this counter back to `0` whenever the number of "in-flight" (popped-but-uncommitted) items reaches zero — without checking whether the `queue` (items already written to disk but not yet popped) still holds entries with higher, still-live ids. This mirrors the reported analog bug class: deriving a "new/next id" from a value that can regress (here, `in_progress == 0`) instead of a strictly-monotonic counter, enabling id collisions between logically distinct records.

### Finding Description
`Queue::Persistent` stores three pieces of state: `queue: VecDeque<u64>` (ids of PCPs written to disk awaiting upload), `next_id: u64` (counter for freshly pushed PCPs), and `in_progress: u64` (count of popped-but-not-yet-committed PCPs). [1](#0-0) 

`push` writes the PCP to `path.join(next_id.to_string())` and then increments `next_id`: [2](#0-1) 

`commit` decrements `in_progress` and, critically, resets `next_id` to `0` whenever `in_progress` drops to zero — with no check on whether `queue` (un-popped entries still sitting on disk with higher ids) is empty: [3](#0-2) 

Sequence that triggers collision:
1. Several PCPs get pushed, receiving ids `0,1,2,3,4,5` (`next_id` reaches 6). Suppose only ids `0` and `1` get popped (`in_progress = 2`) while ids `2..5` remain in `queue` un-popped, still persisted on disk under directories `2/`, `3/`, `4/`, `5/`.
2. Both in-flight uploads (id `0`, `1`) complete and `commit(0)` / `commit(1)` are called. On the second commit, `in_progress` reaches `0`, so `next_id` is reset to `0` — even though ids `2..5` are still un-popped, live entries on disk.
3. New PCPs are pushed. They reuse ids starting at `0`, and as pushing continues (`0,1,2,3,...`) the counter will again reach `2`, `3`, `4`, `5`, which are the same directory names as the still-pending, uncommitted entries from step 1.
4. `push` calls `fs::create_dir_all` and `fs::write` on `path.join(id.to_string())` for the colliding id, silently overwriting `meta.json` and `data.bin` of the pre-existing, not-yet-uploaded PCP belonging to a different signup.

This is directly analogous to the reported bug: a "new unique identifier" is derived from a variable (`in_progress` reaching 0) that does not correlate with whether all previously-issued ids are actually retired, just like `totalSupply()+1` did not correlate with whether all previous token ids were retired.

### Impact Explanation
A PCP (`Pcp` struct) carries a signup's `signup_id`, `user_id`, iris/face image data, and checksums destined for biometric backend upload. If the id-collision path above overwrites a still-queued PCP directory with another signup's data, the corrupted/overwritten record will later be popped and uploaded under the wrong association: either the wrong `signup_id`/`user_id` metadata is now paired with someone else's biometric data (misattribution/cross-signup state bleed), or data for one signup is silently lost (checksum mismatch or missing custody package leading to failed retention pipeline for that user). This is a data-integrity and cross-signup contamination issue for sensitive biometric image data.

### Likelihood Explanation
This requires the persistent (SSD-backed) queue path to be exercised (i.e., the in-memory fallback isn't used) with enough throughput/backpressure that multiple ids are outstanding on disk while others are being committed — plausible under normal high-volume signup / degraded network conditions where `PARALLEL_UPLOAD_STREAMS` throttling and retries (`upload_pcp` retry loop) cause a mix of popped-in-flight and still-queued disk entries. It doesn't require a malicious actor; it's a logic bug reachable by ordinary orb operation under load or intermittent connectivity, not test-only or dependency-only.

### Recommendation
Do not reset `next_id` based on `in_progress == 0`. Persist and always advance `next_id` monotonically (e.g., track the true maximum id ever issued, as is already correctly done in `Queue::new` via `queue.back().map_or(0, |id| id + 1)`), and only reset it when both `queue.is_empty()` and `in_progress == 0` (i.e., the directory is truly empty), or better, simply never reset it during the agent's lifetime and only recompute it from `queue.back()`/directory scan on startup.

### Proof of Concept
Given the existing test harness pattern in `src/agents/data_uploader.rs` (`test_persistent_queue`):
1. Push PCPs so that `next_id` advances to `6` (ids `0..=5` written to disk).
2. `pop()` ids `0` and `1` only (leaving `2,3,4,5` in `queue`, un-popped, still on disk).
3. `commit(0)`, then `commit(1)` — after the second commit, `in_progress` hits `0`, and per lines 333-337 `next_id` is reset to `0`.
4. `push()` four more PCPs — they will be written to `path.join("0")`, `path.join("1")`, `path.join("2")`, `path.join("3")`, the last two of which collide with and overwrite the still-pending, un-popped directories `2/` and `3/` from step 1, corrupting those signups' custody-package data.

    async fn push(&mut self, pcp: Pcp) {
        match self {
            Self::Memory { queue } => {
                queue.push_back(pcp);
            }
            Self::Persistent { path, queue, next_id, .. } => {
                let ssd_perform = ssd::perform_async(async {
                    let path = path.join(next_id.to_string());
                    let meta = serde_json::to_string(&pcp)?;
                    fs::create_dir_all(&path).await?;
                    fs::write(path.join("meta.json"), meta).await?;
                    fs::write(path.join("data.bin"), &pcp.data).await?;
                    Ok(())
                });
                match ssd_perform.await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during push, switching to memory"
                        );
                        *self = Self::Memory { queue: vec![pcp].into() };
                    }
                    Some(()) => {
                        queue.push_back(*next_id);
                        *next_id = next_id.checked_add(1).expect("shouldn't grow so fast");
                    }
                }
            }
        }
    }
