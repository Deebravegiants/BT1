### Title
Unvalidated `txMeta.keyId` override lets caller sign with a key unrelated to the declared `baseAssetName`/`walletAccount` - (File: features/tx-signer/src/module/seed-signer.ts)

### Summary
`SeedBasedTransactionSigner.signTransaction` accepts a caller-supplied `unsignedTx.txMeta.keyId` that completely overrides which private key is used to sign, while the surrounding API contract (`baseAssetName`, `walletAccount`) is what establishes the "context" the caller/UI believes it is signing for. The only check performed is a structural shape check (`KeyIdentifier.validate`), never a check that `keyId` is consistent with `baseAssetName`/`walletAccount`. This is the same bug class as the referenced Morpho finding: one variable (`_asset`) declares the intended context while a different, unvalidated value (`loanToken`)/here (`keyId`) is actually used for the sensitive operation.

### Finding Description
In `SeedBasedTransactionSigner.signTransaction`: [1](#0-0) 

```
signTransaction = async (opts: InternalSignTransactionParams) => {
    const { baseAssetName, unsignedTx, walletAccount } = opts
    const baseAsset = this.#assetsModule.getAsset(baseAssetName)
    ...
    const keyId = unsignedTx.txMeta?.keyId
    const signTx = baseAsset.api.signTx!

    if (!keyId) {
      const signer = await this.#getSignerForWalletAccount({ walletAccount, baseAsset })
      return signTx({ unsignedTx, signer })
    }

    // Sometimes we need a different keyId than the default...
    assert(KeyIdentifier.validate(keyId), `txMeta.keyId must be a key identifier object`)

    const signer = await this.#getSignerForKeyId({ seedId: walletAccount.seedId, keyId })
    return signTx({ unsignedTx, signer })
}
```

When `txMeta.keyId` is present, the code bypasses the normal derivation (`baseAsset.api.getKeyIdentifier` tied to `walletAccount.index`/`baseAssetName`) and instead signs with whatever `KeyIdentifier` was supplied in `txMeta`, as long as it is a *structurally* valid `KeyIdentifier` object (right shape/enum values) — `KeyIdentifier.validate` does not verify that `keyId.assetName`, `derivationPath`, or `keyType` correspond to `baseAssetName` or `walletAccount.index`. The comment in the code acknowledges this is intentionally used for legitimate cross-asset cases (e.g. signing EOS with the Ethereum key, Ripple fallback claims), which confirms `keyId` is deliberately not required to match `baseAssetName`.

This mirrors the Morpho bug precisely: `_asset` (declared/approved context) vs `loanToken` (actually used) — here `baseAssetName`/`walletAccount` (the caller's declared signing context, and presumably what any UI approval screen displays) vs `txMeta.keyId` (the actual key material used), with no cross-validation between the two.

The public surface (`ITransactionSigner.signTransaction` → `transactionSignerApi.signTransaction`) forwards `unsignedTx` (including `txMeta`) essentially unchanged from the caller through to this internal signer: [2](#0-1) [3](#0-2) 

There is only a shallow `typeof txMeta === 'object'` assertion at the `TransactionSigner` level; nothing constrains the *contents* of `txMeta`, including `keyId`.

### Impact Explanation
If any caller that can invoke `exodus.transactionSigner.signTransaction` (or the underlying feature API) with attacker-influenced `unsignedTx.txMeta` — including a compromised/less-trusted UI process talking to the background SDK over the RPC bridge (`@exodus/sdk-rpc` / `@exodus/browser-extension-rpc`), or a feature/plugin that forwards partially-untrusted transaction metadata — can set `txMeta.keyId` to an arbitrary but structurally valid `KeyIdentifier` (any `assetName`, `derivationPath`, `keyType`) independent of the `baseAssetName`/`walletAccount` parameters. Because `KeyIdentifier` accepts arbitrary derivation paths (see `libraries/key-identifier/src/key-identifier.js`), this could make the wallet sign attacker-supplied transaction bytes with the private key derived for a *different* account index or a *different* asset than what the user was shown/approved, producing a valid signature under an unintended key without the requesting flow's asset/account context ever being checked against the key actually used. This does not directly transfer funds by itself, but it undermines the guarantee that "sign for asset X, account Y" only ever uses key material for X/Y, which is a core wallet-signing invariant analogous to the report's core issue (approve on one asset, use another).

### Likelihood Explanation
Reachability depends on whether `txMeta.keyId` can be influenced by an untrusted/lower-privilege caller in a given app built on this SDK (e.g., a browser-extension UI process, or a plugin/feature that builds `unsignedTx` from less-trusted input). The code comments show this override path is real and used in production flows (EOS/Ripple fallback), so the plumbing is live, but I could not fully confirm within the indexed code whether the browser-extension content-script/dApp-facing web3 providers (`bitcoin-provider.md`, injected `window.*Provider`) route directly into this exact `signTransaction`/`txMeta.keyId` path, or whether `txMeta` construction is always fully trusted/internal before reaching this signer. This is a gap in what I could verify from the index — a full audit of every caller of `transactionSigner.signTransaction` across `assets-feature`, hardware-wallet flows, and RPC exposure would be needed to establish concrete external reachability.

### Recommendation
Validate that any caller-supplied `txMeta.keyId` is consistent with the declared signing context before using it: e.g., assert `keyId.assetName` is either unset or matches an allow-listed set of "compatible" assets/accounts for the given `walletAccount`/`baseAssetName` (as is already done implicitly for the known EOS/Ripple cases), rather than accepting any structurally valid `KeyIdentifier`. At minimum, tie `keyId`'s account index to `walletAccount.index` and require an explicit, hard-coded allow-list of asset pairs for the "different keyId" use case instead of accepting arbitrary caller input.

### Proof of Concept
Not independently reproducible from the indexed code alone — a full PoC would require constructing an `unsignedTx` with `txMeta.keyId` pointing to an unrelated account/derivation path and demonstrating the RPC/feature call path an untrusted process could use to reach `SeedBasedTransactionSigner.signTransaction`, which I was unable to fully trace end-to-end within the available index (see Likelihood Explanation).
