### Title
Biometric credential package (PCP) is uploaded to the backend and to the data-uploader agent before the backend's own signup validation/fraud check completes - ([File: src/plans/mod.rs])

### Summary
In `do_signup`, the encrypted personal-custody biometric credential package (PCP tiers 0-2) is built and uploaded (a network "callback" to the backend and an IPC "callback" to the `data_uploader` agent) *before* `enroll_user` is invoked, which is the step that actually performs the backend's authoritative signup validation (duplicate/in-flight/fraud detection via `signup_post`/`signup_poll`). This mirrors the reported bug class: an external interaction is placed before the state/checks that determine whether the operation should be considered valid at all.

### Finding Description
`MasterPlan::do_signup` executes, in order: biometric capture, biometric pipeline, local fraud check (`detect_fraud`), then builds the PCP credentials and calls `upload_pcp_tier_0` followed by sending tier-1/tier-2 packages to `orb.data_uploader` — all of this happens before `self.enroll_user(...)` is called: [1](#0-0) 

`enroll_user` is the function that actually performs the backend round-trip (`signup_post::request` + polling via `signup_poll::request`) that determines duplicate detection, in-flight matches, and backend-side fraud detection, per the comments in `enroll_user::Plan::run`: [2](#0-1) 

Locally, `detect_fraud` is fully neutered — it always returns `false` ("FOSS: WE HAVE DELETED ALL FRAUD CHECKS") — so the only remaining authoritative signup-acceptance check is the backend call made inside `enroll_user`, which happens strictly *after* the PCP (biometric credential) upload: [3](#0-2) 

The `signup_post` request itself carries no acknowledgment of validity beyond a software-version status; actual accept/reject/duplicate/fraud determination is only known later via `signup_poll`: [4](#0-3) [5](#0-4) 

Because the PCP upload (`upload_pcp_tier_0` plus tier-1/tier-2 sends to `data_uploader`) precedes this validation step, biometric credential data reaches the backend/S3 storage pipeline regardless of whether the subsequent authoritative check later reports the signup as a duplicate, in-flight conflict, or fraud.

### Impact Explanation
If the backend's later `signup_poll` result indicates failure (duplicate signup, in-flight match, or backend-detected fraud), the biometric credential package for that user has already been persisted/uploaded. This creates a cross-signup state bleed / biometric data disclosure risk: data tied to a signup that is ultimately rejected as invalid, duplicate, or fraudulent is not held back pending validation, but exposed to external systems ahead of time. Given the local `detect_fraud` is a no-op stub, the backend check performed inside `enroll_user` is the sole gate, yet the credential upload does not wait for it.

### Likelihood Explanation
This occurs on every signup that reaches the PCP-building stage (i.e., every non-early-aborted signup), since the code path is unconditional: `build_pcp` → `upload_pcp_tier_0` → tier-1/tier-2 uploads → only then `enroll_user`. No user-controlled reordering is needed; it is a structural sequencing issue in `do_signup`.

### Recommendation
Reorder `do_signup` so that the authoritative backend enrollment/fraud/duplicate check (`enroll_user`) completes and returns `Status::Success` before the PCP tier-0/1/2 packages are uploaded to the backend and handed to `data_uploader`. If uploads must be pipelined for latency reasons, gate the actual persistence/finalization (e.g., committing tier data server-side) on a successful `enroll_user` result, or add a compensating deletion/retraction call for cases where `enroll_user` ultimately fails.

### Proof of Concept
Not applicable in the traditional sense (no exploit script), since this is a Rust orchestration bug, not a smart-contract reentrancy bug. The ordering itself is the proof: [6](#0-5)
