### Title
Webhook `shop-domain` (and `topic`/`api-version`) header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api_version`, and `webhook_id` fields come from unauthenticated HTTP headers. `Registry.process` validates only the body's HMAC and then passes the unauthenticated `shop` value straight into `WebhookMetadata`, which host applications use as the tenant identifier to route/attribute the webhook. This breaks the identity binding `shop_verified == shop_acted_on`.

### Finding Description
The signable string for a webhook request is defined as just the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` performs exactly that check and then forwards the request's unauthenticated `shop`/`topic` fields directly into `WebhookMetadata`, which is what the host application's handler consumes to decide which tenant the webhook belongs to: [4](#0-3) [5](#0-4) 

Because the app's `client_secret` (api_secret_key) is shared across every shop that installs the app, any unprivileged merchant who installs the app on their own store legitimately receives real, correctly-signed webhooks (body + valid HMAC) for their own shop. Since the HMAC only binds the body — never the `shop-domain` header — that same body+HMAC pair remains valid if the `x-shopify-shop-domain` header is swapped for a different (victim) shop's domain. `HmacValidator.validate` will still pass because it never inspects `shop` at all.

**Binding broken (as an equality):**
`shop_that_HMAC_authenticates == raw_body_source_shop`, but the gem instead treats it as
`shop_delivered_to_handler == header["x-shopify-shop-domain"]` (unauthenticated, attacker-controlled)
— i.e. the field acted upon (`shop`) is not covered by the HMAC that is verified.

### Impact Explanation
This is a cross-tenant identity confusion at the gem boundary: a low-privilege attacker (any user who can install the target app on a shop they control) can produce a validly-signed webhook `Request` whose `shop` claims to be an arbitrary victim shop, while the body content is entirely attacker-controlled (their own shop's data). Any host application built on this gem that uses `WebhookMetadata#shop` to determine which merchant's records to create/update/delete (a standard and documented usage pattern shown in `docs/usage/webhooks.md`) will attribute attacker-crafted data to the victim tenant, since the gem's own `Registry.process` provides no cross-check between the verified body and the claimed shop. This matches the "cross-tenant access" High-impact category — the gem hands the host app a `shop` value it never actually authenticated.

### Likelihood Explanation
Likelihood is straightforward for any attacker who can register/install the app on a shop of their own (a normal, unprivileged flow for any public or custom Shopify app) — no leaked secrets, tokens, or privileged access are required. They only need to capture one legitimate webhook delivery to themselves and replay it with a modified `shop-domain` header to the app's webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`) values in the signed material, or otherwise cryptographically bind them to the payload before verification — e.g., verify HMAC over a canonical string that concatenates body + shop + topic, or require the host application to independently confirm the resolved `shop` against a shop known to be associated with the webhook subscription (e.g., via the `webhook_id` returned from Shopify's `webhookSubscriptions` API) rather than trusting the raw header value implicitly. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be trusted without an independent tenant check.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Shopify delivers a legitimate webhook to the app's endpoint:
   ```
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   raw_body: {"id": 1, "note": "malicious payload"}
   ```
3. Attacker captures this raw body + hmac header (both valid, since HMAC covers only the body).
4. Attacker POSTs the same body and hmac to the app's webhook endpoint, but changes the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) calls `Utils::HmacValidator.validate(request)`, which only checks the body's HMAC — it succeeds.
6. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {"id": 1, "note": "malicious payload"}, ...)` and processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
