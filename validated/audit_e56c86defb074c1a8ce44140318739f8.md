## Analysis: Unchecked ERC20 return value in Tron IntentGatewayV2 escrow withdrawal

The reported bug class — silent failure from not checking token transfer return values — has a genuine analog in `evm/tron/contracts/apps/IntentGatewayV2.sol`. Unlike the standard EVM `IntentGatewayV2.sol` (which consistently uses OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer` that reverts on failure), the Tron variant replaces outbound transfers with raw low-level `.call()` invocations and only checks that the call itself didn't revert — it never inspects the returned ABI-encoded boolean.

### Title
Unchecked ERC20/TRC20 `transfer` return value can silently fail in Tron `IntentGatewayV2.withdraw()` and `SweepDust` handling - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` and the `SweepDust` request handler in the Tron `IntentGatewayV2` contract move escrowed tokens using `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check the low-level `success` flag, never decoding/validating the boolean return data of `transfer()`.

Both call sites check `(bool success,) = token.call(...)` but never decode `data` to confirm the token itself reports success. Many ERC20/TRC20-style tokens (particularly nonstandard implementations that don't strictly follow the interface, or ones that return `false` instead of reverting on failure — e.g., insufficient balance edge cases, blocklists, or paused tokens) will make the raw `.call()` succeed (`success == true`) while the encoded return data is `false` or empty in a way that indicates failure. Since the code treats any non-reverting call as success, it proceeds to decrement `_orders[commitment][token]`, delete `TRANSACTION_FEES`, and emit `EscrowReleased`/`EscrowRefunded`/`DustSwept` as if the beneficiary received funds — even though no tokens actually moved.

This directly mirrors the reported bug class: the return value of the transfer call is not validated, so the "accounting" (escrow state, order-filled markers) diverges from the actual token balances, and the failure is invisible on-chain.

Note this differs from the standard EVM `IntentGatewayV2.sol`, which uses `SafeERC20` (`safeTransfer`/`safeTransferFrom`) throughout — `SafeERC20` explicitly checks the return data and reverts on a `false` result, so that contract is not affected. The Tron variant deliberately departs from this pattern for all outbound token movements in `withdraw()` and `SweepDust`.

### Impact Explanation
`withdraw()` is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` cross-chain message is delivered by the relayer, and from `onGetResponse()` on cancellation — both reachable from a single relayed proof/message with no privileged role required to trigger delivery. If the escrowed token silently fails to transfer:
- The solver/user beneficiary permanently loses the escrowed funds (they are never delivered).
- The escrow accounting (`_orders[commitment][token]`) is zeroed out as if payment succeeded, and `EscrowReleased`/`EscrowRefunded` is emitted, meaning the funds cannot be reclaimed through any other code path — the tokens remain stuck in the contract with no accounting reference tying them back to a recoverable order.

This is a permanent, unbacked loss of escrowed user/solver funds — satisfying the "permanent freezing of funds" / theft-equivalent bar.

### Likelihood Explanation
Triggering requires only that the escrowed/swept token be a nonstandard ERC20/TRC20 that returns `false` (or non-standard-encoded data implying failure) instead of reverting under some failure condition (e.g., temporary pause, blocklist, insufficient balance due to fee-on-transfer quirks, or non-compliant token implementations common in the Tron ecosystem). Given the IntentGateway is designed to support arbitrary listed tokens across order inputs, and Tron's TRC20 ecosystem includes many nonstandard token implementations, this is a realistic condition rather than a purely theoretical one.

### Recommendation
Replace the raw `.call()` + `success`-only check pattern in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the rest of the codebase (as already done in the standard EVM `IntentGatewayV2.sol` and `Funding`-style transfer helpers elsewhere). At minimum, decode and validate the returned boolean when `data.length > 0`, matching the `SafeERC20` semantics, before proceeding to update escrow state or emit success events.

### Proof of Concept
1. A user places a cross-chain order on the source (Tron) chain, escrowing `TokenX` (a nonstandard token that returns `false` from `transfer()` under some failure condition rather than reverting).
2. A solver fills the order on the destination chain; a `RedeemEscrow` message is relayed back to the Tron `IntentGatewayV2`.
3. `onAccept()` calls `withdraw()`, which executes `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`.
4. `TokenX.transfer()` returns `false` (e.g., due to an internal restriction) but does not revert; `success` from the low-level call is `true` since the call did not throw.
5. `withdraw()` proceeds: `_orders[commitment][token] -= amount` and emits `EscrowReleased`, even though the beneficiary's balance never increased — the escrowed tokens remain trapped in the contract with the corresponding escrow entry erased, making them permanently unrecoverable through the normal withdrawal path.
