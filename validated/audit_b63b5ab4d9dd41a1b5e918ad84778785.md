## Analog Vulnerability Found

### Title
Missing Account ID Validation and Missing Refund Callback in `MultisigFactory::create` Leads to Irrecoverable Loss of Attached Deposit - (File: `multisig-factory/src/lib.rs`)

### Summary
The external report flags `getBaseEntropy`/`getSignIdentity` for concatenating unsanitized, attacker-controlled strings directly into a security-critical structure without validating the resulting value, allowing misuse. The analogous root cause exists in `MultisigFactory::create`, which concatenates an unvalidated, attacker-supplied `name: AccountId` directly into the target account ID string used for account creation, and — unlike the sibling `staking-pool-factory` and `lockup-factory` contracts — never validates the resulting ID nor registers a callback to detect and refund a failed creation.

### Finding Description
In `multisig-factory/src/lib.rs`, the `create` entrypoint builds the new sub-account ID by simple string formatting of caller-controlled input, with no validation of `name` and no check that the resulting `account_id` is a valid NEAR account ID: [1](#0-0) 

Compare this to `staking-pool-factory/src/lib.rs`, which performs equivalent input handling but explicitly rejects `.` in the prefix and validates the composed account ID before proceeding: [2](#0-1) 

and which registers a callback, `on_staking_pool_create`, that detects promise failure and refunds the attached deposit to the original caller: [3](#0-2) 

`lockup-factory/src/lib.rs` follows the same safe pattern (deterministic hashed account id plus an `on_lockup_create` callback): [4](#0-3) 

`multisig-factory::create` has neither protection: it never calls `env::is_valid_account_id` on the composed `account_id`, and the `Promise::new(account_id).create_account()...` chain has no `.then(...)` callback at all. Any attacker-controlled `name` value (empty string, characters not permitted in NEAR account IDs, an already-existing account name, or a `name` chosen so the resulting `account_id` collides with an account that already exists) will cause the underlying `create_account`/`deploy_contract`/`transfer`/`function_call` receipt to fail. Because there is no callback to detect this failure, the attached deposit that was meant to fund the new multisig account is never returned to the caller — the refund from the failed receipt returns to `multisig-factory`'s own account balance, not to the original depositor, and the contract exposes no method to reclaim or forward it back.

### Impact Explanation
Any unprivileged user calling the public `create` method with attached NEAR and a `name` that causes account creation to fail (invalid characters, name collision, insufficient deposit for storage of the new contract state, etc.) permanently loses their attached deposit with no recovery path in the contract. This matches the "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... factory refund ... flows" High-severity impact category, since it stems from an unauthenticated, protocol-level public entrypoint with unsanitized/unvalidated user input.

### Likelihood Explanation
Likelihood is high: `create` is a fully public, unprivileged entrypoint that any account can call, and unlike its sibling factories it lacks both input validation and a completion callback. Triggering the failure path requires no special conditions — an ordinary account-naming collision, minor typo producing an invalid account-id fragment, or attaching a deposit insufficient to cover the newly deployed multisig2 contract's storage cost is enough to strand the funds.

### Recommendation
Mirror the pattern already used in `staking-pool-factory` and `lockup-factory`:
1. Validate `name` does not contain `.` and validate `env::is_valid_account_id(account_id.as_bytes())` before issuing the `create_account` promise.
2. Add a `.then(ext_self::on_create(...))` callback that checks `is_promise_success()` and, on failure, refunds `env::attached_deposit()` back to `env::predecessor_account_id()`, exactly as done in `on_staking_pool_create`/`on_lockup_create`.

### Proof of Concept
1. Caller invokes `multisig-factory.create({ name: "bad name!", members: [...], num_confirmations: 1 })` with an attached deposit of, e.g., 5 NEAR.
2. `account_id = format!("{}.{}", name, env::current_account_id())` produces an account ID containing a space/invalid character.
3. `Promise::new(account_id).create_account().deploy_contract(...).transfer(...).function_call(...)` is scheduled; the NEAR runtime rejects the invalid account ID and the receipt fails.
4. Because `create` has no `.then()` callback, the failed receipt's refund is credited back to `multisig-factory`'s own account balance rather than to the caller.
5. The caller's 5 NEAR deposit is unrecoverable — no method in `multisig-factory/src/lib.rs` exposes a way to withdraw or reroute it back to the caller.

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
