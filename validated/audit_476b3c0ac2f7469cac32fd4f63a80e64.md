### Title
Webhook Shop-Domain Header Is Not Bound to the HMAC-Authenticated Body, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, but then trusts the unauthenticated `x-shopify-shop-domain` (and `topic`/`webhook-id`/`api-version`) header to identify which tenant the payload belongs to. An attacker who legitimately owns a shop with the app installed can capture a genuine `(raw_body, hmac)` pair from their own shop's real webhook delivery and replay it to the app's webhook endpoint with a forged shop-domain header pointing at a victim shop, causing the app to process attacker-controlled data under the victim's tenant identity.

### Finding Description
The webhook verification chain is: [1](#0-0) 

`process` calls `Utils::HmacValidator.validate(request)`, which only signs/verifies `to_signable_string`: [2](#0-1) 

`to_signable_string` returns `@raw_body` only — none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are part of the signed material: [3](#0-2) 

Yet after HMAC validation succeeds, `Registry.process` builds the trusted tenant context directly from these unauthenticated headers and hands it to the app's handler: [4](#0-3) 

The resulting `WebhookMetadata` struct — the only interface the gem exposes to the handler — carries `shop`, `topic`, `webhook_id`, and `api_version` as first-class trusted fields, with no indication to the consuming app that they are unauthenticated: [5](#0-4) 

The broken identity-binding equality is:
`shop asserted by the `x-shopify-shop-domain` header` == `shop that actually produced/owns the HMAC-signed `raw_body``

Before the attack: for a legitimate webhook, the header's shop domain and the HMAC-covered body both originate from the same Shopify delivery for the same shop, so they coincide.

After the attack: the attacker sends an HTTP request assembled from two different provenances — the HMAC-valid `raw_body` (and its signature) taken from their own shop's genuine webhook, and the `x-shopify-shop-domain` header rewritten to name a victim shop. `HmacValidator.validate` still returns `true` because only `raw_body` is checked; `request.shop` reads directly off the attacker-controlled header, so the equality no longer holds, yet the gem asserts it did by packaging both into a single trusted `WebhookMetadata`.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` to select which tenant's session, database records, or business logic to act on (the documented and expected usage pattern shown in this gem's own webhook docs) can be made to attribute attacker-supplied webhook `body` content to an arbitrary victim shop. Depending on the webhook topic (e.g., orders, customer data, app uninstall/redact topics), this enables cross-tenant data injection or corruption without any credentials belonging to the victim, satisfying the "cross-tenant access" critical-impact category — an unprivileged attacker with only their own legitimate shop installation can pollute another merchant's data path.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs their own (or any) shop with the target app installed to obtain a valid `(raw_body, hmac)` pair by triggering any webhook naturally (e.g., placing a test order), then replaying that exact body/HMAC to the app's public webhook endpoint with a modified shop-domain header. No secret material, TLS interception, or privileged access is required — this is a pure unprivileged-internet-user request-forgery against the endpoint the app itself exposes per this gem's documented integration pattern.

### Recommendation
Bind the shop identity to the same authenticated channel as the body, e.g., include the shop domain (and ideally topic/webhook id) in the signable string used for HMAC verification, or independently cross-check `request.shop` against a shop the app already trusts for the given `topic`/subscription before dispatching to the handler. At minimum, document prominently in `WebhookMetadata` that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header values and must not be used as sole tenant selectors without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed over `B` with the app's shared secret.
2. Attacker sends a new HTTP POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256`: `H` (unchanged, still valid since only body is signed)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`/`x-shopify-webhook-id`: forged as desired
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers; `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only checks `B`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled webhook data as if it belonged to `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
