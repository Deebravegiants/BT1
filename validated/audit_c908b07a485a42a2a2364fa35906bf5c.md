### Title
Excess native token payment in `EvmHost.dispatch()`/`fundRequest()` is refunded to the host contract instead of the original caller, permanently trapping user overpayments - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept native token payment (`msg.value`) and swap it for the exact required `feeToken` amount via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`. Standard Uniswap V2 routers refund any unused ETH to `msg.sender` of the swap call — but that "swap caller" is `EvmHost` itself (since `EvmHost` invokes the router, not the original dispatcher). Any leftover native token from an overpayment therefore lands back in `EvmHost`'s own balance rather than being returned to `_msgSender()`/`post.payer`, with no code path afterward to forward it to the user.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 
and `dispatch(DispatchGet)`: [2](#0-1) 
and `fundRequest()`: [3](#0-2) 

all follow the same pattern: if `msg.value > 0`, call `swapETHForExactTokens{value: msg.value}(exactFeeAmount, path, address(this), block.timestamp)`. None of these functions check the return value of the swap or refund any unspent native token to `_msgSender()`. This is unlike other parts of the codebase (`IntentGatewayV2.sol`, `ExtrinsicIntents.sol`) that explicitly compute leftover `msgValue` and call `_sendValue(msg.sender, msgValue)` to refund overpayment: [4](#0-3) [5](#0-4) 

Standard `UniswapV2Router02.swapETHForExactTokens` refunds any unused ETH back to `msg.sender` of the call. Since `EvmHost` is the direct caller of the router (`{value: msg.value}` sent from the host's own execution context), the refund lands in `EvmHost`'s balance, not in the wallet of the user/app that originally sent the transaction with excess `msg.value`. The custom wrapper routers in this repo (`UniV4UniswapV2Wrapper.sol`) confirm this behavior explicitly refunding to `msg.sender`: [6](#0-5) 
which, from `EvmHost`'s call, is `EvmHost` itself.

`EvmHost.sol` has no `receive()`/refund-forwarding logic after the swap call in `dispatch()` or `fundRequest()` to sweep this excess back to the caller — this was confirmed by grepping the file for refund/withdraw patterns around the dispatch functions.

### Impact Explanation
Any unprivileged relayer, app, or user calling `IDispatcher.dispatch(DispatchPost/DispatchGet)` or `fundRequest()` with native token and slightly overestimating the required ETH (which is expected in practice, since the exact swap price is not known until execution — front-end quoting via `quoteNative()` is inherently an estimate) will have the excess permanently stuck in `EvmHost`, unrecoverable by the depositor. This is a direct, protocol-wide loss-of-funds bug affecting the primary message dispatch path (`EvmHost` is the core message dispatcher used by all apps, `HyperApp`-based integrations, `BandwidthManager`, `IntentGatewayV2`'s cross-chain leg, and the LayerZero adapter). Given `dispatch()` is the single most frequently invoked function in the entire protocol, and every native-token payment path funnels through it, the aggregate value lost is potentially large and continuous. This qualifies as concrete theft/permanent freezing of funds via the core dispatch path a message dispatcher reaches directly.

### Likelihood Explanation
High likelihood: any caller providing native token payment that swaps for slightly more than the exact fee token amount needed (due to slippage buffer, price movement between quote and execution, or simply rounding up an off-chain estimate) triggers this on every single call. The documentation itself instructs integrators to send a generous buffer of native token expecting it to be refunded automatically by the swap, and other in-repo contracts (`IntentGatewayV2`, `ExtrinsicIntents`) demonstrate this refund pattern is the intended, expected behavior — yet `EvmHost` itself, the base dispatcher, omits it.

### Recommendation
Capture the actual ETH consumed by the swap (via before/after balance snapshot as done in `UniV4UniswapV2Wrapper._sendValue` pattern) or capture `amounts[0]` returned by `swapETHForExactTokens`, and forward `msg.value - amounts[0]` back to `_msgSender()` (or `post.payer`/`get.payer` where applicable) in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, mirroring the refund logic already present in `IntentGatewayV2.sol` and `ExtrinsicIntents.sol`.

### Proof of Concept
1. Attacker/user calls `EvmHost.dispatch{value: 2 ether}(DispatchPost{..., fee: X})` where the actual feeToken cost of `X` only requires 1 ETH worth of swap input.
2. `dispatch()` executes `swapETHForExactTokens{value: 2 ether}(X, [WETH, feeToken], address(this), ...)`.
3. The router consumes ~1 ETH and refunds ~1 ETH back to `msg.sender` of the swap call, which is `EvmHost`.
4. `EvmHost`'s native balance increases by ~1 ETH; no code path in `dispatch()` forwards this back to the original caller.
5. The caller has permanently lost the excess 1 ETH with no recovery mechanism, repeatable on every dispatch call with any native overpayment.
