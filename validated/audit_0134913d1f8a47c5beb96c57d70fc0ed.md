### Title
Unfunded `recapitalize` refund drains pool custody while the cash book still reports the funds — withdrawals pass the liquidity check but can never settle - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The Rio bug is an availability check that reads a balance which does not subtract already-committed obligations, so a withdrawal is *admitted* but can never be paid, and a later settlement step is stuck. XOXNO Lending has the same shape: `Cache::require_reserves` / `debit_cash` gate exits against the accounting `cash` field, not the real token balance, and `recapitalize`'s refund path pays tokens out of the pool *without* debiting `cash` — correct only under the assumption that the payer funded the full declared amount first. An unprivileged caller can violate that assumption, leaving `cash` permanently overstating custody. Every subsequent withdrawal clears `require_reserves` (the book says the money is there) and then reverts inside the SAC transfer — the same "request accepted, settlement impossible" failure as the Rio report.

### Finding Description
`require_reserves` reads only the book: `assert!(self.cash >= amount)` in `contracts/pool/src/cache/cash.rs:15-21`, and `transfer_out` then performs the real SAC transfer without re-checking custody (`cash.rs:46-53`). Withdraw admits the exit on the book via `gate_and_debit` (`contracts/pool/src/ops/withdraw.rs:111-118`).

`recapitalize` (and `repay`) "refund from pool cash without debiting it, correct only because the controller transferred the full amount in first" (`contracts/pool/README.md` ~L334). When the measured receipt is zero, the refund equals the full declared amount and is paid from pool custody while `cash` is untouched. The committed test proves end-to-end exploitability from the permissionless entrypoint:

`contracts/pool/tests/flows.rs:3408-3483` (`test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`):
1. Supplier deposits; book `cash` equals real balance.
2. Attacker calls `recapitalize(hub, payer, custody)` where `payer` never transferred anything → `token.balance(pool) == 0` while `state_snapshot().cash >= deposit`.
3. Honest `withdraw` returns an error, and the test pins that it is **not** `InsufficientLiquidity` or `PoolInsolvent` — the pool's own guard passed on the stale book — but SAC `BalanceError = 10` from inside the token transfer. State rolls back, so the book still overstates custody and the next exit fails identically.

`controller::recapitalize` is permissionless: `scripts/permissionless_entrypoints.txt:73` — "Anyone may donate their own funds … the excess is refunded to the payer." The attacker only needs to control the `payer` auth; no real funding is required because the refund is paid against the declared amount, not the measured receipt.

This is the Rio pattern exactly: Rio's `availableShares` ignored pending-but-unsettled withdrawals, so a withdrawal was admitted that the protocol couldn't fulfill and `rebalance` bricked; here `cash` ignores custody already refunded out, so withdrawals are admitted that the pool can't fulfill, and exits brick.

### Impact Explanation
Permanent freezing of user funds plus theft of protocol liquidity. The attacker pockets the entire pool balance as the "refund" (theft), and simultaneously every supplier's withdrawal reverts forever: `require_reserves` keeps passing on the phantom book, the SAC transfer keeps failing, and there is no code path that reconciles `cash` down to real custody (donations don't raise the book either — `formulas.md` ~L82: "incidental token donations do not increase" tracked cash). Borrows, `claim_revenue`, and `flash_loan` against that market are equally stuck. Per-market impact; each market can be drained independently.

### Likelihood Explanation
One unprivileged call per market, no capital, no timing dependence, no privileged role. The only requirement is that the pool holds custody — i.e., the attack is profitable whenever the market has any un-borrowed liquidity. The refund is paid to an address the attacker controls. Repeatable until every market's custody is zero.

### Recommendation
Reconcile the refund with reality, the mirror of Rio's `sharesOwedTotal` fix — never pay out value the book doesn't debit:
- Debit `cash` by the refund amount when paying the refund (the pool should treat the refund as a draw on reserves, guarded by `require_reserves`), or
- Compute the refund strictly from the *measured* receipt shortfall and only refund tokens that were actually received in this call — i.e., `refund = received - applied`, never `declared - applied`. If `received == 0`, refund is zero.
- Longer term, make `require_reserves` compare `cash` against `token.balance(pool)` (or assert `cash <= balance` at commit) so a book/custody divergence can never silently admit unpayable exits.

### Proof of Concept
```rust
// contracts/pool/tests/flows.rs — existing committed test, already reproduces it
let deposit = 10_000_000_000i128;
token_admin.mint(&t.pool, &deposit);
let supplied = t.client().supply(&t.sup(0, deposit)).get_unchecked(0)
    .position.scaled_amount;

// Attacker: no tokens transferred, yet the full custody is refunded out.
let custody = token.balance(&t.pool);
t.client().recapitalize(&hub(&t.asset), &payer, &custody);
assert_eq!(token.balance(&t.pool), 0);          // custody gone
assert!(t.state_snapshot().cash >= deposit);    // book unchanged

// Honest supplier: requestWithdrawal-admitted, settlement-impossible.
let res = t.client().try_withdraw(&receiver, &false,
    &t.wdr(supplied, i128::MAX, 0));
// res is SAC BalanceError(10), NOT InsufficientLiquidity(112):
// require_reserves passed on the phantom book; the transfer fails.
assert!(res.is_err());
```

Via the controller the same flow is `controller::recapitalize(hub_asset, payer, amount)` with `payer` authorizing a call that transfers nothing; the pool's measured-receipt/excess-refund logic pays `amount` out of custody without debiting `cash`, after which all `controller::withdraw` calls on that market revert inside the token transfer indefinitely.

Note: the exact lines of `contracts/pool/src/ops/recapitalize.rs` were not fully read; the refund-pays-declared-excess behavior is inferred from the committed test and the README note "refund from pool cash without debiting it, correct only because the controller transferred the full amount in first." If the implementation instead refunds only `received - applied`, this analog collapses — but the test at `flows.rs:3408` demonstrates the payout already occurs today.
