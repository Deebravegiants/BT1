### Title
Address-aliased ERC20 tokens in `erc20TokenAddresses` allow minting shielded UTXO value without any backing transfer - (File: `contracts/Hinkal.sol`, function `transact`)

### Summary
`Hinkal.transact` validates each entry of `circomData.erc20TokenAddresses` **independently** by comparing a `balanceOf`-based snapshot diff (`balanceDif`) against `amountChanges[i] + utxoAmount`, with no check that the addresses actually correspond to distinct underlying balances. Since the circuit only forces the addresses to be numerically distinct (`distinctErc20AddressChecks` in `circuits/MainEVMCircuit.circom`), an attacker can supply a second "alias" token address whose `balanceOf` simply mirrors a real token's balance, causing one real balance increase (e.g. from a LiFi swap output) to satisfy two independent per-token equalities and mint double the shielded value for the same underlying funds.

### Finding Description
The broken equality: **net real tokens entering Hinkal (`D_out`, a single swap output) == sum of shielded value minted (`D_out` for the real output token UTXO + `D_out` phantom `amountChanges` deposit for the alias token) → 2×D_out minted for D_out received.**

Code path:
1. `Hinkal.transact` snapshots balances for `circomData.erc20TokenAddresses` before and after `_externalTransact`: [1](#0-0) 
2. It then loops over `erc20TokenAddresses` and, for each index `i`, independently checks `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount`: [2](#0-1) 
3. `getBalancesForArray` simply calls `balanceOf` per address with no uniqueness or aliasing check: [3](#0-2) 
4. `LifiExternalAction.callRouter`/`ExternalActionSwap.swap` only operate on `erc20TokenAddresses[0]` (input) and `[1]` (output); any additional token slots in the array are never touched by the swap logic: [4](#0-3) [5](#0-4) 
5. The only circuit-level guard on the addresses only forbids numerically identical entries, not addresses that alias the same real balance: [6](#0-5) 
6. Per-token accounting inside the circuit is fully independent (`inTotal + amountChanges[i] === outTotal`), and the merkle-root equality check for a token slot is only enabled when that slot has non-zero spent inputs (`enabled <== inAmounts[i][j]`): [7](#0-6) 

Exploit flow:
- Attacker deploys a real ERC20 `TokenX` and a trivial wrapper `TokenXAlias` whose `balanceOf(addr)` simply forwards to `TokenX.balanceOf(addr)` (no proxy trickery needed — attacker fully controls the deployed token).
- Attacker calls `Hinkal.transact` with `dimensions.tokenCount = 3` and `erc20TokenAddresses = [inputToken, TokenX, TokenXAlias]`, targeting the LiFi swap external action (`externalActionId` mapped to `LifiExternalAction`).
- The real swap in `ExternalActionSwap.swap` sends `amountToSendToHinkal` (`D_out`) of `TokenX` into Hinkal, legitimately backing a UTXO for index 1 (`utxoAmount[1] = D_out`, `amountChanges[1] = 0`), satisfying `balanceDif[1] == utxoAmount[1]`.
- Because `TokenXAlias.balanceOf(Hinkal)` mirrors `TokenX.balanceOf(Hinkal)`, `newBalances[2] - oldBalances[2]` also equals `D_out`, even though `utxoSet` (built only from the swap's real `outputToken` address) contains no entry for `TokenXAlias`, so `utxoAmount[2] = 0`.
- The attacker sets `circomData.amountChanges[2] = D_out` and crafts a proof with zero spent inputs for token index 2 (`inTotal[2] = 0`) and new output UTXO commitments totaling `D_out` — the circuit constraint `inTotal + amountChanges[2] === outTotal` is trivially satisfiable with self-chosen values, and the merkle-root check for that slot is disabled (`enabled <== inAmounts[2][j] = 0`), so no valid pre-existing leaf/root is even required.
- On-chain, `balanceDif[2] == amountChanges[2]` (`D_out == D_out`) passes, minting `D_out` worth of brand-new shielded UTXOs for `TokenXAlias` that are entirely unbacked — the vault never actually received any `TokenXAlias` tokens.

None of the existing guards catch this: `performHinkalChecks`/`dimensionsCheck` only validate structural array-length consistency, `rootHashExists` is bypassed for the phantom slot because its enabling signal is zero, `verifyProof` accepts the proof because the circuit's per-token equation is locally consistent, and the on-chain `balanceDif` check is satisfied because it reads the aliased balance rather than verifying token identity/uniqueness.

### Impact Explanation
The attacker mints shielded UTXO value (`D_out`) with zero real backing, directly causing protocol insolvency: total shielded liabilities exceed the tokens actually held by the vault by the phantom amount, which the attacker can later withdraw by spending the phantom UTXO through a normal withdrawal/transfer, draining real funds belonging to other users. This is repeatable per transaction and scales with the swap output size, matching the "Critical: minting shielded value without backing (protocol insolvency)" category.

### Likelihood Explanation
Feasible for any unprivileged attacker: no special role is needed, only the ability to deploy a wrapper ERC20 contract whose `balanceOf` mirrors another token, to route a LiFi swap through `ExternalActionSwap`, and to author a valid proof for a self-created token slot with zero spent inputs (fully within the attacker's private-witness control, as `inTotal`, `outAmounts`, and `outCommitments` for that slot are the attacker's own choices). The technique does not require any specific merkle tree size or root state, because the disabling of the root check for zero-input token slots removes any dependency on tree contents.

### Recommendation
Enforce real-world uniqueness of token identity in `Hinkal.transact`'s balance-diff loop, not just numeric inequality of addresses supplied by the prover. Concretely: track balances via a canonical identifier that cannot be spoofed by wrapping (e.g., disallow any token whose `balanceOf` result for the same address matches another listed token's `balanceOf` result before AND after the external action in a way that indicates a shared underlying balance), or restructure the invariant so unbacked deposits (`amountChanges[i] > 0` when `onChainCreation[i]` is false and no corresponding transfer was actually pulled into Hinkal by the external action) require an explicit, action-attributed transfer rather than a bare balance snapshot comparison across independently-controlled addresses.

### Proof of Concept
Foundry test plan:
1. Deploy `TokenX` (mintable ERC20) and `TokenXAlias` whose `balanceOf(addr)` delegates to `TokenX.balanceOf(addr)`.
2. Deploy `LifiExternalAction` wired to a mock LI.FI router that swaps `inputToken -> TokenX` for a fixed `D_out`.
3. Fund the attacker with `inputToken`, generate a valid proof for a `CircomData` with `tokenCount = 3`, `erc20TokenAddresses = [inputToken, TokenX, TokenXAlias]`, `amountChanges = [-inputAmount, 0, D_out]`, `onChainCreation = [false,false,false]`, and a zero-input/UTXO-output-only sub-proof for index 2.
4. Call `Hinkal.transact(...)`.
5. Assert: `TokenX.balanceOf(Hinkal) - oldBalanceTokenX == D_out` (real value received), while total credited shielded value == `D_out (token1 UTXO) + D_out (phantom token2 amountChanges)` == `2*D_out`.
6. Assert the transaction does not revert, proving `balanceDif == amountChanges[i] + utxoAmount` holds for both index 1 and index 2 despite only one real balance increase — confirming vault balance delta (`D_out`) < credited UTXO value (`2*D_out`).

        CircomData calldata circomData,
        int256[] calldata deltaAmounts

            inputAmount -= circomData.feeStructure.flatFee;

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );

        uint256 relayFee = circomData.feeStructure.flatFee;

        uint256 hinkalFee = hinkalHelper.calculateRelayFee(
            swappedAmount,
            0,
            circomData.feeStructure.variableRate
        );

        if (circomData.feeStructure.feeToken == outputToken) {
            sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
        } else {

                circomData.relay,
                relayFee,
                circomData.feeStructure.feeToken

            sendToRelay(circomData.relay, hinkalFee, outputToken);

        utxoSet = new UTXO[](1);

            amount: amountToSendToHinkal,
            erc20Address: outputToken,
            stealthAddressStructure: circomData.stealthAddressStructure,
            timeStamp: block.timestamp
        });
    }

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
