### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` to attribute the webhook payload to a tenant without that value ever being covered by the HMAC check. This breaks the identity binding: `shop verified by HMAC` ≠ `shop attributed to the processed data`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field of the same object [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` — the request body — and does not incorporate any headers [2](#0-1) .

However, `shop`, `topic`, and `webhook_id` are all parsed straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) with no cryptographic binding to the body or to the HMAC signature [3](#0-2) .

`Webhooks::Registry.process` validates only the HMAC (i.e., only the body) via `Utils::HmacValidator.validate(request)`, then constructs `WebhookMetadata` using `request.shop` — the header value that was never authenticated — and dispatches it to the registered handler: [4](#0-3) 

This is structurally analogous to the reported `TroveManager` bug: a value that participates in a security-relevant computation/decision (`totalActiveDebt` there, `shop` tenant-binding here) is silently decoupled from the authoritative source that is supposed to keep it consistent (the interest accrual there, the HMAC signature here), producing state that looks validated but isn't actually tied to what was checked.

### Impact Explanation
Shopify webhooks are delivered over plain HTTP POST to a merchant-configured public callback URL; any client (not just Shopify) can send a POST to that endpoint with attacker-chosen headers and a body. An attacker who can obtain one legitimate `(body, hmac)` pair signed with the app's `client_secret` — e.g., by installing the app on their own Shopify development/trial store and capturing the resulting webhook delivery — can replay that exact `(body, hmac)` pair to the same endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header with an arbitrary victim shop domain. `Utils::HmacValidator.validate` still succeeds because it only checks the untouched body against the untouched hmac; `Registry.process` then hands the handler a `WebhookMetadata` claiming the payload originated from the attacker-chosen `shop`, even though the real originating shop never sent it.

Depending on how the host application uses `data.shop` (e.g., to look up the session/access token for that shop, to key data written to per-tenant storage, or to trigger tenant-scoped side effects such as data deletion in `customers/redact`/`shop/redact` handlers), this enables cross-tenant data confusion/injection under an HMAC check that appears to have "passed" — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint and possession of one validly-signed `(body, hmac)` pair, which any developer can obtain non-privileged by installing the target app on their own store (a standard, unprivileged Shopify Partner/dev-store action) and observing the webhook Shopify sends them. No access to `client_secret`, access tokens, or the merchant's account is needed, and the gem provides no additional binding of `shop`/`topic` to the signature that would prevent this.

### Recommendation
Bind the tenant-identifying headers into the signed payload before comparing/relying on them: include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, e.g., by having `HmacValidator`/`Registry.process` verify a signature computed over `headers + body`), so that any tampering with `shop-domain` invalidates the HMAC. At minimum, document that consuming applications must not trust `WebhookMetadata#shop` for tenant-scoping decisions without independently re-validating it against a known/registered shop for that webhook subscription.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`). Shopify delivers a POST with a real HMAC signed with the app's `client_secret`:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid_hmac_of_body>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: <id>
Body: {"id":123,...}
```
2. Attacker captures this exact `(body, x-shopify-hmac-sha256)` pair.
3. Attacker replays it to the same endpoint, only changing the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same_valid_hmac_of_body>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: {"id":123,...}   # unchanged
```
4. `ShopifyAPI::Webhooks::Request.new` parses the forged `shop` header [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over the unchanged body and succeeds [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the payload never having been sent by or for that shop [7](#0-6) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
