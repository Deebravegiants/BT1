### Title
Webhook `shop` field is passed to handlers without being covered by the HMAC signature, allowing cross-tenant shop spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
The reported bug class is a broken identity binding: a value the code acts on is not actually covered by the cryptographic check that is supposed to authenticate the request. In `MyStrategy.sol`, the check gated withdrawal on `LOCKER.balanceOf(...)`, a value an attacker could manipulate independently of the legitimate owner's intent.

The analogous binding break exists in this gem's webhook processing pipeline. `ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` is defined to be only the raw HTTP body: [1](#0-0) 

The HMAC validator computes and compares the signature strictly against this `to_signable_string` (i.e., the body) and the shared `api_secret_key`: [2](#0-1) 

However, `Registry.process` extracts `request.shop` — read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header — and forwards it to the app's handler as trusted tenant identity, alongside the HMAC-validated body: [3](#0-2) [4](#0-3) 

The equality that should hold is: `shop that authorized/produced this HMAC == shop delivered to the handler`. But the HMAC only binds the *body bytes* to the secret key — it says nothing about which shop's header value accompanies those bytes. The `shop` field is a "field acted on but not covered by the HMAC."

### Impact Explanation
Because the `shop-domain` header is outside the HMAC's signed scope, anyone who possesses one valid `(body, hmac)` pair — e.g., a webhook payload legitimately delivered for their own shop/store (attacker is a merchant who installed the app) — can replay that exact body+HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass, since it only checks the body against the secret. `Registry.process` will then hand the handler a `WebhookMetadata` claiming an attacker-chosen `shop`, paired with a body the attacker actually controls the content shape of, or at minimum controls whether it's replayed with a spoofed tenant label. Apps that key their data store or business logic purely on `data.shop` (e.g., "update customer record for `data.shop`") can be tricked into associating the replayed content with the wrong tenant, corrupting cross-tenant boundaries — this matches the "cross-tenant access" Critical impact category, since the gem's own API exposes an authenticated-looking metadata object whose tenant field is in fact forgeable independent of the HMAC.

### Likelihood Explanation
Exploitation requires the attacker to have received at least one legitimately signed webhook for a shop they control (any developer/merchant with the app installed on a test/dev store can obtain this), and requires the host app to trust `WebhookMetadata#shop` as the authoritative tenant identifier without independently confirming it against a shop known to be associated with that body (which is the exact API contract the gem's own docs advertise: `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify"). This is a realistic and unprivileged-internet-facing path, not merely theoretical, since the vulnerable header is directly exposed to the internet-facing webhook endpoint and the gem provides no binding between shop and payload.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the signable string used by `HmacValidator`, or otherwise cryptographically bind them to the HMAC, so that any mismatch between the signed body and the accompanying headers is detected and rejected in `Utils::HmacValidator.validate`/`Webhooks::Request#to_signable_string`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be independently corroborated by the host application before being used as a tenant key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) to receive a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `api_secret_key`.
2. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` value to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the body only) — [1](#0-0)  — and it matches, since the body is unchanged.
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` — [5](#0-4)  — and passes it to the app's `handle` callback as if Shopify itself confirmed this shop sent this data.
