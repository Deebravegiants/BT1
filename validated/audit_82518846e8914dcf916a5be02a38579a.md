### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, allowing cross-tenant spoofing via header manipulation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The webhook HMAC signature only authenticates the raw request body. The `shop`, `topic`, and `webhook-id` values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler as trusted tenant-identifying metadata are read from unauthenticated HTTP headers that are never part of the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC purely against `to_signable_string`: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only that HMAC, then trusts `request.shop`, `request.topic`, and `request.webhook_id` (all parsed from headers, never part of the signable string) to build the `WebhookMetadata` object handed to the app's handler: [3](#0-2) 

Contrast this with the OAuth callback flow, where the equivalent tenant-identity field (`shop`) *is* included in the signed payload via `Oauth::AuthQuery#to_signable_string`: [4](#0-3) 

This is exactly the binding pattern called out in the report's bug class: a field acted upon by the application (`data.shop`, used by the app to select which merchant/tenant a webhook belongs to) is not covered by the cryptographic proof (HMAC) that supposedly authenticates the request. The equality that should hold is:

`shop bound inside the HMAC-signed bytes == shop the handler acts on`

but the actual state is:

`shop bound inside the HMAC-signed bytes (∅, never included) ≠ shop the handler acts on (request.shop, taken from an unauthenticated header)`

Any party who can obtain one valid `(raw_body, hmac)` pair for topic X — for example, by installing the app on their own store and receiving a genuine webhook — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Utils::HmacValidator.validate` will still return `true` because it only checks the untouched raw body against the secret-derived HMAC; `Registry.process` will then dispatch to the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value, impersonating any other shop for that webhook topic.

### Impact Explanation
This crosses a tenant boundary: the gem lets an app trust `shop` as an authenticated, per-merchant identity for a payload whose signature never covered that value. Any host application that follows this gem's documented pattern of using `WebhookMetadata#shop` from `Registry.process` to route data, credentials, or side effects to a specific merchant (the intended and only way this gem surfaces webhook shop identity) will process attacker-controlled payloads as if they came from an arbitrary target shop, causing cross-tenant data confusion.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one genuine `(body, hmac)` pair, which is achievable by any unprivileged party who installs the app on their own store (a normal, unprivileged action) and captures the resulting real webhook call. No `api_secret_key`, access token, or privileged account is required — only the ability to receive one legitimate webhook and replay it with a modified `shop`-domain header to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, and `webhook-id` in the signable string used for HMAC computation in `ShopifyAPI::Webhooks::Request#to_signable_string`, mirroring the approach used for `Oauth::AuthQuery`, so that the identity fields consumed by `WebhookMetadata` are cryptographically bound to the same request they were validated against, rather than trusting unauthenticated headers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook for topic `orders/create`. Shopify sends the app a real request with body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the shared `client_secret`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures `(B, H)`.
3. Attacker sends a new POST to the app's webhook endpoint with the same raw body `B` and the same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` recomputes HMAC over `to_signable_string` (== `B`) and finds it matches `H`, so validation passes: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and was authenticated for `attacker-shop.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
