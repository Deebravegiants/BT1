### Title
Webhook shop-domain identity is unauthenticated by the HMAC check, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC verification performed by `HmacValidator`/`Registry.process` only covers the raw request body. This breaks the identity binding "shop authenticated == shop used to key tenant data," letting an attacker with one valid (body, HMAC) pair replay it with an arbitrary shop-domain header and have it accepted as authentic for a different tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signed bytes: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. just the body) and compares it to the header-supplied HMAC: [3](#0-2) 

`Webhooks::Registry.process` treats a passing HMAC check as authorization to trust the whole request, then hands the caller's handler a `WebhookMetadata` keyed by `request.shop` — the very field that was never covered by the signature: [4](#0-3) 

The equality this breaks is:

`shop bound by HMAC (∅, since to_signable_string = raw_body only)` **≠** `shop used to key/act on tenant data (request.shop, read from header)`

Because the signature never touches the shop header, once an attacker is in possession of any single legitimate `(raw_body, hmac)` pair — trivially obtainable by installing the app on their own store and observing/logging their own store's webhook deliveries to their endpoint — they can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim shop's domain). `HmacValidator.validate` still succeeds because it only re-derives the HMAC from the body, and `Registry.process` passes the forged `shop` straight to the handler as authenticated tenant identity.

### Impact Explanation
Any app built on this gem that follows the documented pattern of trusting `WebhookMetadata#shop` (returned by `Registry.process`) as the tenant identifier for looking up sessions/records is exposed to cross-tenant confusion: an attacker-controlled body can be attributed to a victim shop, letting the attacker inject or overwrite data keyed by the victim's shop identifier, or trigger shop-scoped business logic (e.g., app-uninstall handling, order/fulfillment side effects, GDPR data requests) as if it originated from the victim. This crosses the tenant boundary this scan is targeting (Critical: cross-tenant access), since it lets one merchant's traffic be attributed to another merchant purely by header substitution — no possession of `api_secret_key`, access tokens, or the victim's credentials is required.

### Likelihood Explanation
Likelihood is non-trivial but requires enumeration: the webhook endpoint must be internet-reachable (true for essentially all embedded Shopify apps, since Shopify itself must reach it), and the attacker needs at least one legitimately signed `(body, hmac)` pair, which any unprivileged user who installs the target app on their own development/trial store can generate on demand by triggering webhook-eligible events (e.g., `orders/create`) in their own store and capturing the outgoing webhook. No secret material, leaked tokens, or social engineering is needed — only observation of one's own app-installation traffic, which matches the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the material that is actually verified, or otherwise cryptographically corroborate it before trusting `request.shop`:
- Include the `shop-domain` header (and other headers you intend to trust, e.g. `webhook-id`, `api-version`) in the HMAC-signed material, i.e. change `to_signable_string` to canonicalize header+body together, and require host apps to independently verify the resulting shop against their own session store keyed by `webhook_id`/topic before acting.
- At minimum, document explicitly that `WebhookMetadata#shop` is derived from an unsigned header and must not be used as the sole tenant key for authorization decisions; require callers to cross-check against a shop already known/authorized for that specific `webhook_id`, or maintain and check a per-installation shared secret independent from the header value.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook-eligible event (e.g. creates an order), causing Shopify to POST a legitimately signed webhook to the app's public endpoint:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over raw body B>
x-shopify-shop-domain: attacker.myshopify.com
Body: B
```
2. Attacker captures `(B, valid_hmac)` from this legitimate delivery (e.g. via logging on their own infra if self-hosted, or via a network capture on a channel they control).
3. Attacker replays the exact same request to the same endpoint, but rewrites only the header:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same valid_hmac>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: B
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`, unchanged) and finds it matches — validation passes. [4](#0-3) 
5. `request.shop` now returns `"victim-shop.myshopify.com"`, and the handler receives `WebhookMetadata` claiming the payload `B` came from the victim shop, even though the shop-domain was never covered by the signature. [5](#0-4)
