**Reasoning:** The `send_cross_shard_msg`/`receive_cross_shard_msg` pair in `execution/executor-service/src/remote_cross_shard_client.rs` uses plain, symmetric `bcs::to_bytes`/`bcs::from_bytes` calls on the same `CrossShardMsg` enum [1](#0-0) . `RemoteTxnWrite` and `CrossShardMsg` derive `Serialize`/`Deserialize` uniformly with no custom/hand-rolled (de)serialization logic on either side [2](#0-1) , so there is no encode/decode asymmetry to exploit — bcs round-trips deterministically for these types by construction, and no crafted `WriteOp` bytes can decode into a different value than the sender encoded.

Beyond the missing asymmetry, this path also fails the review-bounds requirement: `RemoteCrossShardClient` is internal, validator-side infrastructure for the sharded/remote block executor service, used between trusted shard processes within a single node's execution pipeline, not an entrypoint reachable from an unprivileged transaction, package, view, authenticator, API, or bytecode input. There is no attacker-controlled path that lets an unprivileged actor inject or tamper with the bytes flowing through `message_txs`/`message_rxs`, so no custody boundary is actually crossed by unprivileged input.

    fn send_cross_shard_msg(&self, shard_id: ShardId, round: RoundId, msg: CrossShardMsg) {
        let input_message = bcs::to_bytes(&msg).unwrap();
        let tx = self.message_txs[shard_id][round].lock().unwrap();
        tx.send(Message::new(input_message)).unwrap();
    }

    fn receive_cross_shard_msg(&self, current_round: RoundId) -> CrossShardMsg {
        let rx = self.message_rxs[current_round].lock().unwrap();
        let message = rx.recv().unwrap();
        let msg: CrossShardMsg = bcs::from_bytes(&message.to_bytes()).unwrap();
        msg
    }
