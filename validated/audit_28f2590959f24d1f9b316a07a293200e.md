### Title
Missing reentrancy guard on `redeem`/`transfer` allows draining vault liquidity during an active flashloan callback - (File: mainnet/contracts/vault/v0-vault-stx.clar and equivalent v0-vault-*.clar / vault-*.clar files)

### Summary
The Zest vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, and their `local-testing` equivalents) implement a manual reentrancy flag `in-flashloan` that is checked only in `deposit` [1](#0-0)  and set/cleared inside `flashloan` [2](#0-1) . The guard is not applied to `redeem`, `transfer`, `system-borrow`, `system-repay`, or `socialize-debt`, which is the same inconsistent-guard bug class described in the referenced Across Protocol commit ("Add reentrancy guards to all public methods").

### Finding Description
`flashloan` sends `amount` of the underlying token out via `send-underlying` and only calls back the caller's contract with `(contract-call? fc callback amount fee data)` before pulling the funds plus fee back with `receive-underlying` [3](#0-2) . Critically, the `assets` accounting variable is never decremented when the funds leave the contract during the flashloan — it is only updated in `deposit`/`redeem`/`system-repay`/`socialize-debt`, not in `flashloan` itself.

During the external callback window, the attacker's `fc` contract fully controls execution and can re-enter the vault. `redeem` computes `current-assets`, `available-assets`, and `inkind` purely from `(var-get assets)`/`get-available-assets`, and only checks pause-state, balance, and slippage — it has no `(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)` check [4](#0-3) . Because `assets` was never reduced by the in-flight flashloan `amount`, `redeem` (and `transfer`, which also lacks the guard [5](#0-4) ) sees stale, inflated liquidity/accounting figures and will let the attacker pull real underlying tokens out of the contract while the flashloan principal is simultaneously outstanding to the same attacker.

This breaks the value identity that should hold for a tokenized vault: `sum(underlying token balance in contract) == assets (accounting variable) - (amount currently lent out via flashloan)`. Since `assets` and `available-assets` are not adjusted for the in-flight flashloan draw, an attacker can, in a single transaction, (1) take out a flashloan, (2) re-enter `redeem` mid-callback to withdraw underlying against the stale `assets`/`available-assets` figures, and (3) still satisfy the flashloan's post-callback repayment check using unrelated liquidity — extracting more value than their shares should permit, or causing the vault to become insolvent relative to remaining depositors once the flashloan completes.

### Impact Explanation
This is a direct value-extraction/insolvency vector on a lending vault holding real user deposits (protocol insolvency / theft of principal), matching the Critical impact bucket, since it lets an attacker manipulate share-redemption accounting mid-flashloan to withdraw underlying assets that the accounting layer no longer correctly tracks as available.

### Likelihood Explanation
The precondition is straightforward: attacker needs (a) some zft shares (from a prior, ordinary deposit) and (b) `can-flashloan` permission (or to be a non-exempt flashloan borrower, which appears to be a permissioned/whitelisted flag per `get-flashloan-permissions`) [6](#0-5) . If flashloan access is permissionless or broadly whitelisted, likelihood is high since the entire attack fits in one transaction using a single malicious callback contract implementing `flash-callback`.

### Recommendation
Apply the existing `in-flashloan` reentrancy check consistently to every state-mutating public method that touches `assets`, share supply, or the debt ledger — at minimum `redeem`, `transfer`, `system-borrow`, `system-repay`, and `socialize-debt` — mirroring the check already present in `deposit`. Additionally, decrement the `assets` accounting variable (or otherwise mark funds as encumbered) at the start of `flashloan` before invoking the external callback, so that `get-available-assets`/`current-assets` correctly reflect in-flight flashloan liquidity even if a guard is bypassed.

### Proof of Concept
Conceptual sequence (per affected vault, e.g. `v0-vault-stx.clar`):
1. Attacker deposits normally to obtain `zft` shares tied to account A.
2. Attacker calls `flashloan(amount, some-receiver, attacker-callback-contract, data)`. This sets `in-flashloan = true` and sends `amount` underlying to the receiver via `send-underlying`, without touching the `assets` var.
3. Inside the callback (`contract-call? fc callback ...`), the attacker's contract calls back into the same vault's `redeem` (or `transfer`) using account A's shares. Since `redeem` never checks `in-flashloan`, it proceeds using the still-inflated `assets`/`available-assets` values and transfers out additional real underlying tokens via `send-underlying`.
4. The callback returns; `flashloan` then pulls `amount + fee` back from the (now further-drained) contract via `receive-underlying`, potentially failing only if there truly isn't enough balance — but if there is sufficient float from other depositors' funds, both operations succeed, and the attacker has extracted value beyond what their share balance and the vault's real assets should allow.

Note: I was not able to fully trace the exact implementation of `get-available-assets`/`ubalance`/`receive-underlying` bodies within the remaining tool budget to confirm the precise numeric bypass conditions (e.g., whether `receive-underlying`'s balance check would abort step 4 in all cases) — this would need to be validated against the full contract body (`define-private (get-available-assets) ...`, `define-private (send-underlying ...)`, `define-private (receive-underlying ...)`) to construct an exact numeric PoC.
