### Title
Interest-accrual value overflow permanently freezes a large high-utilization market - (File: `common/src/rates/scaling.rs`)

### Summary
A sufficiently large market can make `borrowed * borrow_index` exceed `i128::MAX` before the borrow index reaches its configured ceiling. Because every mutating pool operation runs interest accrual first, the resulting `MathOverflow` repeatedly aborts withdrawals, repayments, liquidations, recapitalization, and revenue operations for that market. The issue is reachable through ordinary `supply`, `borrow`, and permissionless `update_indexes` calls once market caps permit the required book size.

### Finding Description
`accrue_step` converts aggregate scaled debt and supply into unscaled RAY values before calculating utilization and updating the borrow index. [1](#0-0)  The conversion delegates to `scaled.mul(env, index)`, which can overflow `i128`. [2](#0-1) 

Although `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, that cap is applied only after the already-overflowing aggregate valuation is calculated for utilization. [3](#0-2)  Consequently, a market with enough scaled debt can exceed the RAY value domain while its stored index remains below the intended cap.

The pool’s `synced_market` helper runs `interest::global_sync` before returning a market cache. [4](#0-3)  `global_sync` invokes `accrue_step` for each elapsed accrual chunk, so the panic occurs before any requested mutation can execute. [5](#0-4)  The controller exposes this path to an unprivileged caller through `update_indexes`. [6](#0-5) 

An existing integration test demonstrates the condition with a valid 18-decimal asset, one billion whole tokens supplied, 98% utilization, and a steep but admissible rate curve. [7](#0-6)  The test observes `MATH_OVERFLOW` while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`, and both withdrawal and repayment fail with the same error. [8](#0-7) 

### Impact Explanation
Once the threshold is crossed, every operation that touches the affected `(hub_id, asset)` market re-enters the overflowing accrual calculation. Supplier funds and unclaimed yield in that market are frozen, borrowers cannot repay, and liquidators cannot reduce the unsafe position because liquidation performs repay and withdraw legs that first sync the market. [9](#0-8) 

The freeze persists absent an upgrade or another privileged repair path because time cannot move backward and the stored scaled balances remain large enough to overflow on every subsequent accrual attempt. This is permanent freezing of user funds and can leave the protocol unable to resolve bad debt in the affected market.

### Likelihood Explanation
The attack requires an unusually large valid market rather than a cheap transaction-level trigger. Governance can admit assets up to 18 decimals, and the cap domain permits roughly 170 billion whole-token equivalents. [10](#0-9) [11](#0-10) 

A borrower still needs sufficient collateral and enough available liquidity to hold utilization near the steep part of the rate curve while interest compounds. The impact is therefore conditional on market scale and configuration, but it does not require privileged execution, oracle dishonesty, token misbehavior, or a reentrancy primitive once such a market exists.

### Recommendation
Bound scaled balances and index growth using the actual `i128` product domain, not only `MAX_BORROW_INDEX_RAY`. In particular:

- Before `borrowed * borrow_index` and `supplied * supply_index`, check `scaled.raw() <= i128::MAX / index.raw()` and clamp or fail safely.
- Perform utilization and aggregate accrual in `I256`, or clamp values before converting back to `i128`.
- Apply `MAX_BORROW_INDEX_RAY` before computing aggregate debt so the cap remains reachable.
- Enforce a market-size ceiling derived from `i128::MAX / MAX_BORROW_INDEX_RAY` and the asset’s decimal scaling.
- Consider an emergency no-accrual settlement path for a market already past the arithmetic boundary.

### Proof of Concept
1. On a listed 18-decimal market with admitted caps above one billion whole tokens and a high-rate curve, suppliers deposit `1_000_000_000` whole tokens.
2. A borrower supplies sufficient collateral in another listed asset and calls controller `borrow` for 98% of that liquidity. The test setup uses `principal / 100 * 98`. [12](#0-11) 
3. Anyone periodically calls controller `update_indexes(caller, [hub_asset])`; the controller forwards the market to the owner-only pool accrual endpoint. [13](#0-12) [14](#0-13) 
4. Once `borrowed_scaled * borrow_index` exceeds `i128::MAX`, `accrue_step` panics inside `scaled_to_original` while computing utilization. [15](#0-14) [2](#0-1) 
5. The test then confirms `update_indexes`, `withdraw`, and `repay` all return `MATH_OVERFLOW`, while the stored borrow index remains under its cap. [8](#0-7)
