Audit Report

## Title
Node crash via nil pointer dereference in vault `GetPublicKey` gateway handler when `params` is null - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.handlePublicKeyGet` dereferences `*req.Params` in `json.Unmarshal(*req.Params, r)` without a nil check, unlike every sibling handler which is gated by an explicit `req.Params == nil` check in `GatewayVaultRequestProcessor` before invocation. A JSON-RPC request with method `vaulttypes.MethodPublicKeyGet` and omitted/null `params` causes an unrecovered nil pointer dereference panic on the node.

## Finding Description
`HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` with no pre-validation, while `MethodSecretsCreate`/`Update`/`Delete`/`List` are first passed through `h.requestProcessor.ProcessRequest`, whose sub-handlers all explicitly check `if req.Params == nil` before unmarshalling: [1](#0-0) [2](#0-1) 

`handlePublicKeyGet` performs `json.Unmarshal(*req.Params, r)` directly with no nil guard: [3](#0-2) 

There is no unit or integration test in `gw_handler_test.go` covering `MethodPublicKeyGet` with nil/omitted params, confirming this path is untested and unguarded (verified by searching the test file for `MethodPublicKeyGet`/`handlePublicKeyGet`/`GetPublicKeyRequest`, which returned no matches).

Critically, the panic is not contained. The connector's `readLoop` invokes `handler.HandleGatewayMessage` directly in the per-gateway read goroutine with no `recover()` wrapper: [4](#0-3)  Unlike other capability handlers in the codebase (e.g. `confidentialrelay.Handler.HandleGatewayMessage`, which explicitly launches request processing via `h.eng.GoCtx` — itself typically wrapped with panic recovery in the `services.Engine`), the vault `GatewayHandler.HandleGatewayMessage` executes `handlePublicKeyGet` synchronously in the connector's read loop, so an unrecovered panic here will propagate up and terminate that goroutine, breaking the node's read loop for the affected gateway connection.

## Impact Explanation
This is an availability-impacting denial-of-service: an unauthenticated/unprivileged caller able to route a request to the vault service's `HandleGatewayMessage` via the Gateway can crash the per-gateway read loop goroutine by sending a `vault_getPublicKey` request with `params` omitted or `null`. This disrupts the node's ability to process further gateway traffic on that connection. `GetPublicKeyGet` requires no authorization (unlike Create/Update/Delete/List, which go through `requestProcessor.ProcessRequest`/`AuthorizeRequest`), so the vulnerable code executes before any credential check.

## Likelihood Explanation
High. The trigger requires a single JSON-RPC request with `method: "vault_getPublicKey"` and `params` omitted or `null`, requiring no valid credentials, encryption keys, or prior authorization state, since `MethodPublicKeyGet` bypasses the `requestProcessor.ProcessRequest` authorization/validation pipeline entirely.

## Recommendation
Add an explicit `if req.Params == nil { return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, errors.New("request params must not be nil")) }` guard at the start of `handlePublicKeyGet`, mirroring the pattern in `processCreateSecretsRequest`/`processUpdateSecretsRequest`/etc. Consider routing all dispatch-switch methods through a shared nil-check helper such as `vaultutils.InspectJSONRPCParams` to prevent recurrence.

## Proof of Concept
1. As an unprivileged external client, send a Gateway-forwarded request that resolves to the Vault service's `HandleGatewayMessage` with body:
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault_getPublicKey"}
```
(no `params`, or `"params": null`).
2. `GatewayHandler.HandleGatewayMessage` routes to `handlePublicKeyGet` because `req.Method == vaulttypes.MethodPublicKeyGet`.
3. `handlePublicKeyGet` executes `json.Unmarshal(*req.Params, r)` where `req.Params` is `nil`, panicking with a nil pointer dereference, uncaught by any `recover()` in `gatewayConnector.readLoop`, killing that goroutine.

A Go unit test analogous to existing table-driven tests in `gw_handler_test.go` (`TestGatewayHandler_HandleGatewayMessage`), adding a case `{name: "public key get - nil params", request: &jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, ID: "1", Params: nil}}`, would demonstrate the panic (`require.Panics` or observe the crash) where all other methods return a typed error instead.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
