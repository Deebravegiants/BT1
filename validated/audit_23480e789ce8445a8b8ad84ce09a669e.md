## Title
Object-to-object transfers can form a multi-object ownership cycle with no reachable account owner, permanently and irrecoverably locking the involved objects - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

## Summary
The Hats Protocol bug reduces to one invariant: a hierarchical/graph traversal used to validate a mutation (adding a child under an "admin" chain) can be tricked into accepting an invalid graph shape by phantom/non-existent intermediate nodes, because the validity check is evaluated against a partial/stale view of the structure rather than the final result. Aptos's `object::verify_ungated_and_descendant` (used by `object::transfer`/`transfer_to_object`) has the same class of flaw: it validates reachability from the *destination* back to the *current owner* using the pre-transfer ownership graph, but never verifies that the *resulting* graph after the mutation still terminates at a real account. This allows a legitimate owner (or any automated flow acting on their behalf) to construct a 2-object mutual ownership cycle in which neither object is ever reachable by an account again.

## Finding Description
`object::transfer_to_object` / `object::transfer_raw` call `verify_ungated_and_descendant(owner_address, destination)`: [1](#0-0) 

This function walks the ownership chain starting at `destination` (the *new* owner target) and stops as soon as it finds `owner_address` in the chain, bounded by `MAXIMUM_OBJECT_NESTING = 8`: [2](#0-1) 

Crucially, this check is only about whether `owner_address` is currently reachable from `destination` *before* the transfer is applied. It does not check whether performing the transfer (`transfer_raw_inner`, which simply sets `object_core.owner = to`) would create a closed cycle among object addresses with no account (EOA) in it.

Consider two objects `obj1` and `obj2`, both owned by `creator`:

1. `transfer_to_object(creator, obj2, obj1)` → destination is `obj1`. Its current owner is `creator`, which trivially satisfies the loop (0 hops), so the transfer succeeds. State: `obj1.owner = creator`, `obj2.owner = obj1`.
2. `transfer_to_object(creator, obj1, obj2)` → destination is `obj2`. Walking from `obj2`: `obj2.owner = obj1`, `obj1.owner = creator` — `creator` is found within `MAXIMUM_OBJECT_NESTING`, so the check passes. `transfer_raw_inner` then sets `obj1.owner = obj2`.

Final state: `obj1.owner = obj2`, `obj2.owner = obj1` — a 2-node cycle with **no account anywhere in the chain**. This is exactly the "phantom levels" pattern: the validity check only inspects the graph state *before* the edit and never asserts the invariant that must hold *after* the edit (that a bounded walk from any object must terminate at a real, non-object address).

Once this cycle exists:
- `object::owns()` will loop through the 2-cycle, incrementing its `count` guard every iteration and never finding the target owner, eventually hitting the same `MAXIMUM_OBJECT_NESTING` assertion and **aborting**: [3](#0-2) 
- Any future `transfer`/`transfer_raw` on either object will likewise abort via `verify_ungated_and_descendant`.
- `object::root_owner()` has **no depth bound at all** and will loop indefinitely (until it runs out of gas) if called on either object: [4](#0-3) 
- `object::burn()`/`unburn()` require `is_owner(object, signer)` which does a direct field comparison (`object.owner() == owner`); since the owner field is now an object address rather than any signable account address, no transaction signer can ever satisfy this check: [5](#0-4) 

The framework's own tests only cover the *self*-loop case (a single object transferred to itself), which is caught on the *second* attempt because the first transfer's destination-chain check is trivially satisfied and the second correctly detects the immediate self-cycle: [6](#0-5) 

No test exercises the **2-object mutual cycle**, which succeeds on both transfers because each individual check only looks at the graph state that exists at the time of that specific call.

## Impact Explanation
Any fungible-asset primary store, NFT/token object, code object, or other object-held resource involved in an object-to-object transfer chain can be permanently and irrecoverably locked (no future transfer, no burn/unburn, no `owns()`/`root_owner()` call succeeds) if the resulting ownership graph closes into a cycle with no account terminal. This matches the "Permanent lock or non-recoverable loss of object-held ... value" and "destroys recovery rights" custody impact categories. It is not gated behind any privileged role — it only requires performing two ordinary, individually-valid `transfer`/`transfer_to_object` calls (which any object-managing dApp, marketplace escrow, or vault contract that shuffles objects between sub-objects could inadvertently trigger), and once formed the loss is permanent under the current code.

## Likelihood Explanation
The transfers required are entirely standard, publicly-callable entry points (`object::transfer`, `object::transfer_to_object`) with no special privileges beyond being the current owner of both objects, and both individual transfer calls pass all existing validity checks. Complex object graphs (marketplaces, vaults, nested container patterns, resource-account-owned objects performing autonomous transfers) are common on Aptos, making an unintentional or adversarially-crafted PTB combining two such transfers plausible in real integrations, especially those that programmatically move objects between sibling containers.

## Recommendation
When validating a transfer (`verify_ungated_and_descendant`), simulate/validate the ownership chain as it will exist *after* the pending mutation (i.e., treat `destination`'s eventual owner as `to` for the object being moved), not just the chain as it exists before the mutation. Alternatively, after performing `transfer_raw_inner`, immediately re-walk the resulting chain from the moved object to confirm it still terminates at a non-object address within `MAXIMUM_OBJECT_NESTING`, aborting the transaction if not. This closes the "phantom-cycle" class of bug the same way Hats Protocol added an independent `isValidHatId` check to validate the *entire* resulting id path rather than only the immediately-checked segment.

## Proof of Concept
```move
// Setup: creator owns obj1 and obj2 (e.g., two ObjectCore-only test objects)
let obj1 = create_simple_object(creator, b"o1");
let obj2 = create_simple_object(creator, b"o2");

// Step 1: move obj2 under obj1. Passes because destination(obj1)'s
// current owner is `creator` (0 hops).
transfer(creator, obj2, obj1.object_address());
// state: obj1.owner = creator, obj2.owner = obj1

// Step 2: move obj1 under obj2. Passes because walking from
// destination(obj2) -> obj1 -> creator finds `creator` within
// MAXIMUM_OBJECT_NESTING (2 hops).
transfer(creator, obj1, obj2.object_address());
// state: obj1.owner = obj2, obj2.owner = obj1  <-- closed cycle, no account

// From here on:
owns(obj1, signer::address_of(creator));   // aborts (EMAXIMUM_NESTING) once count hits 8
root_owner(obj1);                          // loops indefinitely / out-of-gas, no bound check
transfer(creator, obj1, @0x999);           // aborts, creator can never reach obj1 again
burn(creator, obj1);                       // aborts, is_owner(obj1, creator) is false forever
```
Both objects, and any resources stored under them (fungible stores, tokens, etc.), are now permanently unreachable by any account.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    #[view]
    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// Returns the root owner of an object. As objects support nested ownership, it can be useful

    public fun root_owner<T: key>(self: Object<T>): address {
        let obj_owner = self.owner();
        while (is_object(obj_owner)) {
            obj_owner = address_to_object<ObjectCore>(obj_owner).owner();
        };
        obj_owner
    }
