### Title
Single shareholder can permanently block `vesting::distribute()` (and `staking_contract` reward distribution) for all other shareholders by opting out of direct coin transfers - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
The external report's core custody invariant is: *a single malicious/uncooperative party interacting with a shared batch settlement process should not be able to abort that process and freeze funds owed to everyone else in the batch.* In Aptos, `vesting::distribute()` and `staking_contract`'s equivalent distribution function reproduce this exact pattern: they iterate over **all** shareholders in one atomic transaction and call `aptos_account::deposit_coins` for each recipient. Any single shareholder can unprivilegedly opt out of un-registered coin transfers, causing every future `distribute()` call to abort and permanently blocking reward distribution to all other shareholders.

### Finding Description
`vesting::distribute()` withdraws all currently withdrawable stake into a local `Coin<AptosCoin>`, then loops over every shareholder in the vesting contract's `grant_pool` and pays them out via `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` contains an unprivileged self-service gate: if the recipient's `CoinStore<CoinType>` is not registered, the call **requires** that the recipient currently allows arbitrary/un-registered coin transfers (`can_receive_direct_coin_transfers`), otherwise it aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`: [2](#0-1) 

The `DirectTransferConfig.allow_arbitrary_coin_transfers` flag is fully controlled by the account owner itself (any account can flip it), as shown by the `DirectTransferConfig` resource definition: [3](#0-2) 

Because Move aborts revert **all** state changes in the transaction (including the earlier `stake::withdraw_with_cap` / `pool_u64::redeem_shares` calls performed inside `distribute()`), a single shareholder who (a) never registers a `CoinStore<AptosCoin>` for their account, and (b) calls the self-service `aptos_account::set_allow_direct_coin_transfers` type function to disable un-registered transfers, will cause `distribute()` to abort on their turn in the loop every single time it is invoked. Since the loop always starts by iterating `grant_pool.shareholders()` (an unordered set) and there is no per-recipient try/catch or skip-and-continue logic, the malicious shareholder cannot be "worked around" — the whole batch fails as long as they remain a shareholder and refuse the deposit.

The identical shared-batch pattern exists in `staking_contract`'s commission/reward distribution loop, which likewise redeems shares and calls `aptos_account::deposit_coins` for every recipient inside a `while` loop in one atomic call: [4](#0-3) 

This is the direct Aptos analog of the CollateralToken/PublicVault issue: instead of a malicious ERC721's `approve()` reverting and halting Seaport-auction-driven epoch processing for all lien holders, an Aptos account's own unprivileged coin-transfer preference reverts a shared distribution transaction and halts reward release for all co-shareholders of a vesting contract or staking contract.

### Impact Explanation
- Legitimate co-shareholders' vested/staking rewards (APT, custody-grade value) become **non-recoverable via the normal path** — `distribute()`/`distribute_many()` will always abort once the withdrawable coins are pulled from the stake pool and one shareholder's deposit fails, because the abort reverts the withdrawal too, so funds are never actually lost from the stake pool, but they are permanently stuck as un-distributable pending/inactive stake as long as the poisoned shareholder is in the set.
- This is a genuine denial-of-custody-recovery condition: normal users cannot extract funds owed to them because of one uncooperative co-owner of the shared vesting/staking-contract pool, matching the report's "epoch processing halted for all vault participants" impact class.
- The only recovery path is admin intervention via `update_beneficiary`/`update_beneficiary_for_operator` to redirect the poisoned shareholder's payout to a different (registered) address — an out-of-band, privileged fix, not something the affected users can trigger themselves, exactly mirroring the report's recommendation that a privileged strategist must intervene.

### Likelihood Explanation
Any account can trivially reach this state today: registering an account, deliberately never registering a `CoinStore<AptosCoin>`, and calling the framework's own `set_allow_direct_coin_transfers(false)` function requires no special privilege, and grant/shareholder addresses in `vesting::create_vesting_contract` are supplied by the vesting `admin` without any code enforcing they stay registered or opted-in for direct transfers. A hostile or simply disinterested shareholder (or an attacker who convinces an admin to include their address as a shareholder) can trigger this at will and repeatedly, since every subsequent `distribute()` call will hit the same abort.

### Recommendation
- Make `distribute()`/the `staking_contract` distribution loop resilient to per-recipient failures, e.g. by using `deposit_coins`-style calls wrapped so a failed deposit routes the payout to an escrow/claimable balance for that shareholder instead of aborting the whole batch, or by pre-validating that all recipients can currently receive the coin before withdrawing stake from the pool.
- Alternatively, require/verify at shareholder registration time (`create_vesting_contract`) that all shareholders have a registered `CoinStore<AptosCoin>` or currently allow direct transfers, and re-validate this invariant before each distribution rather than mid-loop.
- Provide a non-admin-gated mechanism for other shareholders to force a partial distribution that skips a persistently-failing recipient, so one uncooperative party cannot indefinitely lock the shared batch process for everyone else.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[Alice, Bob]` via `create_vesting_contract`, each with grant shares in `grant_pool`. [5](#0-4) 
2. Bob's account never registers `CoinStore<AptosCoin>` (skips normal onboarding) and calls the framework's self-service opt-out to disable un-registered direct coin transfers, setting `DirectTransferConfig.allow_arbitrary_coin_transfers = false` for his account. [3](#0-2) 
3. Time passes, rewards accrue and become withdrawable on the stake pool; anyone calls `vesting::distribute(contract_address)`. [6](#0-5) 
4. `distribute()` withdraws all pending coins, then in the shareholder loop attempts `aptos_account::deposit_coins(Bob, ...)`; since Bob has no registered `CoinStore<AptosCoin>` and `can_receive_direct_coin_transfers(Bob) == false`, this call aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. [7](#0-6) 
5. The entire transaction reverts, including the earlier stake withdrawal — Alice's (and every other legitimate shareholder's) portion of the rewards is not paid, and every subsequent call to `distribute()` fails identically until the vesting `admin` proactively calls `update_beneficiary` for Bob to redirect his share elsewhere.

I was not able to directly view the exact source location of the `set_allow_direct_coin_transfers` entry function in this index (only its supporting `DirectTransferConfig` struct/fields and the `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` check were retrieved), so its exact line numbers are unconfirmed; if full verification of that entry point is needed, a Devin session with full repo access should be used to confirm the exact function signature and any additional guard conditions.

    /// Distribute any withdrawable stake from the stake pool.
    public entry fun distribute(contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        let coins = withdraw_stake(vesting_contract, contract_address);
        let total_distribution_amount = coin::value(&coins);
        if (total_distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        // Distribute coins to all shareholders in the vesting contract.
        let grant_pool = &vesting_contract.grant_pool;
        let shareholders = &grant_pool.shareholders();
        shareholders.for_each_ref(|shareholder| {
            let shareholder = *shareholder;
            let shares = pool_u64::shares(grant_pool, shareholder);
            let amount = pool_u64::shares_to_amount_with_total_coins(grant_pool, shares, total_distribution_amount);
            let share_of_coins = coin::extract(&mut coins, amount);
            let recipient_address = get_beneficiary(vesting_contract, shareholder);
            aptos_account::deposit_coins(recipient_address, share_of_coins);
        });

        // Send any remaining "dust" (leftover due to rounding error) to the withdrawal address.
        if (coin::value(&coins) > 0) {
            aptos_account::deposit_coins(vesting_contract.withdrawal_address, coins);
        } else {
            coin::destroy_zero(coins);
        };

        emit(
            Distribute {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
                amount: total_distribution_amount,
            },
        );
    }
