### Title
Webhook `shop` (and topic/api-version) claims are not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw body, then trusts the unauthenticated `shop-domain` (and `topic`/`api-version`/`webhook-id`) headers to attribute the payload to a specific merchant. Because the shop identity is never covered by the signature, a captured (body, HMAC) pair from one shop can be replayed with a forged `shop-domain` header pointing at a different shop, breaking the intended binding `hmac == HMAC(secret, body)` from also implying `shop == owner-of(body)`.

### Finding Description
The webhook HMAC computation only signs the raw request body: [1](#0-0) 

`hmac` itself is derived from the `hmac-sha256` header, and `shop`, `topic`, `webhook_id`, `api_version` are all pulled straight from separate, unauthenticated headers: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)` — which in turn calls `to_signable_string` (i.e., the body only) — and then immediately builds `WebhookMetadata` using the unauthenticated `shop` header value, handing it to the host application's handler as trusted data: [3](#0-2) 

`HmacValidator.validate` confirms this: the signable string it hashes is exactly `verifiable_query.to_signable_string`, which for webhooks is just `@raw_body`: [4](#0-3) 

This is the classic "field acted on but not covered by the HMAC" defect: the equality the library implicitly promises to callers is `hmac_valid(request) ⇒ (body, shop, topic) all originated together from Shopify for that shop`. In reality it only proves `hmac_valid(request) ⇒ body originated from Shopify for *some* shop using this app's secret`. The `shop` (and `topic`/`webhook_id`) fields are attacker-controllable header values that ride along unauthenticated.

### Impact Explanation
An attacker who operates their own installation of the app (a legitimate, low-privilege tenant) receives real, validly-signed webhook deliveries for their own store. Because the HMAC is independent of the `shop-domain` header, the attacker can intercept/replay that exact `(body, hmac)` pair while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` will still return `true` since it only recomputes the signature over the body, and `Registry.process` will invoke the host application's webhook handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that uses this `shop` field to key persistence, trigger shop-scoped side effects, or select which merchant's session/access token to act on will process attacker-supplied data under the victim's tenant identity — a cross-tenant data/state injection rooted entirely in this gem's verification logic, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any merchant who installs the app (no special privilege required) can obtain genuine `(body, hmac)` pairs from their own webhook deliveries, since Shopify signs all shops' webhooks for a given app with the same `client_secret`. Forging the `shop-domain`/`topic` header on a replayed POST to the app's public webhook endpoint requires no cryptographic knowledge — only that the header isn't part of the signed content, which is exactly what `to_signable_string` implements. This is directly reachable through the gem's public API (`Webhooks::Registry.process`) as documented for host integration.

### Recommendation
Bind the trust-critical identity fields into the HMAC-verified content rather than treating them as separate, implicitly-trusted inputs:
- Include `shop`, `topic`, and `webhook_id`/`api_version` in `Request#to_signable_string` if Shopify's signature scheme allows it, or
- At minimum, document/require that host applications cross-check `WebhookMetadata#shop` against a shop they already have an active, independently-authenticated session for before acting on webhook contents, and provide a gem-level helper that enforces this rather than exposing the raw unauthenticated `shop` header as if it were verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) by placing a normal order, capturing the POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker (or a man-in-the-middle on their own inbound traffic, which they fully control since it's their own server) resends the request to the app's webhook endpoint, keeping body `B` and header `H` unchanged but rewriting `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(client_secret, B)` and finds it equals `H` — validation succeeds because `shop` was never part of the signed input: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`, causing the host app to process attacker-controlled data under the victim tenant's identity.
