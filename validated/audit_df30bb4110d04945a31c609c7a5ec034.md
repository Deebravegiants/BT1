### Title
Webhook shop/topic identity not bound by HMAC, enabling cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from attacker-controllable HTTP headers with no cryptographic binding to the signed body [2](#0-1) . `Utils::HmacValidator.validate` only checks that the HMAC matches `to_signable_string` (the body) [3](#0-2) , so the tenant-identifying `shop` field is completely unverified. `Registry.process` trusts `request.shop` as the tenant identity passed to the handler after only validating the body's HMAC [4](#0-3) .

### Finding Description
The binding that should hold is: `hmac_valid(body, secret) ⟹ shop_header == shop_that_generated_body`. In this gem, that equality does not exist — `hmac_valid` only proves body integrity, not shop origin, because `shop-domain`, `topic`, and `webhook-id` headers are excluded from `to_signable_string`.

An unprivileged merchant who has installed the app on their own store legitimately receives webhooks for their own shop, each delivered with a valid `x-shopify-hmac-sha256` header computed by Shopify using the app's single, shared `api_secret_key` (the same secret is used to sign webhooks for every shop that installs the app). The attacker can capture one such legitimately-signed `(raw_body, hmac)` pair from their own shop, then replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain (and optionally a different `x-shopify-topic`). Because the HMAC only covers `raw_body`, `HmacValidator.validate` still returns `true`, and `Registry.process` dispatches to the handler with `WebhookMetadata.shop` set to the victim's domain [5](#0-4) . The application, trusting `shop` from `WebhookMetadata` as the authenticated tenant identity, will process attacker-supplied body content attributed to a shop the attacker does not control.

### Impact Explanation
This breaks the tenant boundary this gem is responsible for enforcing at the webhook-verification layer: HMAC validation is the sole mechanism `ShopifyAPI::Webhooks::Registry` provides to authenticate the origin of a webhook, yet it fails to bind the claimed shop to the verified bytes. Any downstream app logic that keys work off `WebhookMetadata#shop` (billing, data updates, redact/GDPR handlers, order processing, etc.) can be triggered against an arbitrary victim shop using content the attacker fully controls (their own legitimately-issued webhook body), constituting cross-tenant data injection/spoofing.

### Likelihood Explanation
Exploitation only requires an ordinary, unprivileged merchant to install the app once to receive at least one valid webhook (trivial and expected for any installed app), then replay that request with a modified `shop-domain` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's environment is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed/verified content, or otherwise cryptographically bind them to the request before trusting `request.shop` — e.g., require that `Registry.process` verify the shop against a shop-specific expectation from the caller, or extend `to_signable_string` to combine header values with the body in a canonical, signed form so the HMAC covers the full identity tuple.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` returns `"victim.myshopify.com"` while `hmac`/`to_signable_string` still only reflect body `B` [6](#0-5) .
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [7](#0-6) .
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)` [5](#0-4) , causing the host app to process attacker-controlled data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
