### Title
Collision-prone `create_token_seed` allows token/object address squatting via ambiguous `collection::name` concatenation - (File: aptos-move/framework/aptos-token-objects/sources/token.move)

### Summary
`create_token_seed` builds the deterministic seed used to derive a named token's object address by concatenating `collection.bytes()`, the literal delimiter `b"::"`, and `name.bytes()` with no length prefixing: [1](#0-0) 

This is structurally the same defect class as the reported ERC712/BatchCompact bug: a struct/array encoding that concatenates variable-length fields without an unambiguous, length-prefixed boundary. Just as `idsAndAmounts` was flattened instead of individually hashed, `collection` and `name` are flattened into one byte string with only a literal (and forgeable) `"::"` separator. Since `"::"` can legally appear inside either a collection name or a token name, two distinct `(collection, name)` pairs can produce an identical seed byte string, and therefore an identical derived object address for the same creator.

### Finding Description
`create_named_token`, `create_named_token_object`, and `create_named_token_as_collection_owner` all compute the token's address as: [2](#0-1) 

via `create_token_seed(collection, name)` feeding `object::create_named_object(creator, seed)`, which derives the address as `sha3_256(creator | seed | 0xFE)`: [3](#0-2) 

Because `create_token_seed` does not length-prefix `collection` or `name` before concatenation, for a fixed `creator`:
```
seed(collection = "A::B", name = "C")   == "A::B::C" (bytes)
seed(collection = "A",    name = "B::C") == "A::B::C" (bytes)
```
These two logically distinct token identities collide to the exact same seed, hence the exact same derived address. The same construction is reused in `create_token_address` (the public/view helper used off-chain by indexers, wallets, and marketplaces to compute a token's address without querying on-chain state) and in `create_token_name_with_seed`, which appends yet another unbounded, non-length-prefixed `seed: String` on top: [4](#0-3) 

`object::create_named_object` aborts if an object already exists at the derived address (`EOBJECT_EXISTS`), so the practical exploitation is a front-run: an attacker (or any party able to choose a `collection`/`name` string under a shared/permissive `creator`, e.g. a marketplace, launchpad, or shared minting resource account where end users supply collection/token names) computes a colliding `(collection', name')` pair that hashes to the same seed as a victim's anticipated `(collection, name)`, then creates their own token there first. The victim's later `create_named_token(...)` call with the "real" `(collection, name)` will abort (denial of service), while any off-chain system that calls the `create_token_address`/`create_token_address_with_seed` view functions to locate "the" token for `(collection, name)` will instead resolve to the attacker's pre-planted `Token`/`Collection` object at that address — silently substituting attacker-controlled token identity, metadata, royalty, and ownership for what callers believe is the legitimate token.

### Impact Explanation
This breaks the custody invariant that a named object's address uniquely and unambiguously identifies the logical entity (collection, name) that a creator intended to control. Concretely:
- Denial of service / griefing: legitimate collection/token creation can be permanently blocked by a pre-computed colliding seed.
- Identity/metadata spoofing: any protocol or off-chain integration that locates a token via `create_token_address`/`create_token_address_with_seed` (a pattern explicitly provided as a `#[view]` helper for "offline applications", as seen even in the framework's own example `managed_fungible_token.move`) can be made to operate against an attacker-controlled object instead of the intended one, corrupting downstream custody decisions (e.g., which object metadata backs a fungible asset, which object is transferred/frozen, or which collection a token is presented as belonging to).
- This risk is concentrated wherever `creator` is shared/multi-tenant (e.g., a marketplace or launchpad resource account that mints on behalf of many end-users using end-user-supplied `collection_name`/`name` strings), since collision requires only matching seeds under the same `creator` address.

Given the potential for token/object identity confusion feeding into downstream custody logic (e.g., `managed_fungible_token.move`'s own pattern of deriving a `Metadata` object's address purely from `create_token_seed`), this is rated High: it does not itself move value, but it can be used to hijack the identity resolution of an asset that a wallet, marketplace, or fungible-asset module trusts as ground truth.

### Likelihood Explanation
Likelihood is moderate: exploitation requires (a) a shared/multi-tenant `creator` address where an attacker can influence or predict the victim's future `(collection, name)` choice, and (b) a consumer relying on `create_token_address`/`create_token_address_with_seed` for identity resolution rather than validating the resolved object's actual `collection`/`name` fields on-chain. Both conditions are realistic in launchpad/marketplace integrations built on `aptos-token-objects`, and crafting a colliding string pair is trivial (no cryptographic difficulty — it is a straightforward string-boundary ambiguity, not a hash preimage problem).

### Recommendation
Encode `collection` and `name` (and the optional `seed`) with unambiguous length-prefixing before concatenation, e.g. use `bcs::to_bytes(collection)` and `bcs::to_bytes(name)` (which include a length prefix) instead of raw `.bytes()` concatenation, mirroring how `object_code_deployment::object_seed` already does this correctly: [5](#0-4) 

Apply the same fix to `create_token_seed` and `create_token_name_with_seed` in `token.move`.

### Proof of Concept
1. Attacker knows/observes that a victim marketplace will soon create a named token via a shared `creator` address with `collection_name = "A"`, `name = "B::C"`.
2. Attacker front-runs by calling `create_named_token(creator, collection_name = "A::B", description, name = "C", ...)` (assuming the shared minting flow allows attacker-chosen strings, e.g. self-serve collection creation under the same resource-account creator).
3. `create_token_seed(&"A::B", &"C")` and `create_token_seed(&"A", &"B::C")` both evaluate to the byte string `"A::B::C"`: [6](#0-5) 
4. Both seeds feed `object::create_object_address(creator, seed)` / `object::create_named_object`, producing the identical derived address for the same `creator`.
5. When the victim's transaction executes, `object::create_named_object` aborts with `EOBJECT_EXISTS` (DoS), or if the victim/dApp instead queries `create_token_address(creator, "A", "B::C")` off-chain to locate "their" token, it resolves to the attacker's token object planted in step 2, which is exactly `object::create_token_address`: [7](#0-6) 

**Note on verification limits:** I was unable to execute this locally (no build/test environment available), and I could not fully audit every downstream module that relies on `create_token_address`/`create_token_seed` for trust decisions (e.g., all marketplace/launchpad integrations) within the indexed codebase; the `managed_fungible_token.move` example is confirmed as one real consumer of this exact pattern, but the full blast radius of confused-deputy consumers cannot be exhaustively enumerated from the index alone.

    /// Named objects are derived from a seed, the token's seed is its name appended to the collection's name.
    public fun create_token_seed(collection: &String, name: &String): vector<u8> {
        assert!(name.length() <= MAX_TOKEN_NAME_LENGTH, error::out_of_range(ETOKEN_NAME_TOO_LONG));
        let seed = *collection.bytes();
        seed.append(b"::");
        seed.append(*name.bytes());
        seed
    }

    public fun create_token_name_with_seed(collection: &String, name: &String, seed: &String): vector<u8> {
        assert!(seed.length() <= MAX_TOKEN_SEED_LENGTH, error::out_of_range(ESEED_TOO_LONG));
        let seeds = create_token_seed(collection, name);
        seeds.append(*seed.bytes());
        seeds
    }
