### Title
Webhook shop-domain identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw body, while the `shop` (tenant) identity is read from an unauthenticated header. Because the `api_secret_key` is shared across every shop that installs the same app, any merchant who receives a legitimate, validly-signed webhook for their own shop can replay that exact `(body, hmac)` pair while substituting the `x-shopify-shop-domain` header for a different, victim shop, producing a request that still passes `HmacValidator.validate` but is attributed to the wrong tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived from the `shop-domain` header, which is not part of the signed content: [3](#0-2) 

`Utils::HmacValidator.validate` verifies the signature strictly against `to_signable_string` (the body), never the shop header: [5](#0-4) 

`Registry.process` accepts the request once the body-only HMAC checks out, then constructs `WebhookMetadata` using the unauthenticated `request.shop` and hands it to the app's handler as the tenant identity: [6](#0-5) 

The identity binding that should hold is: `shop asserted in header == shop the HMAC actually authenticates`. Since the HMAC only authenticates the body bytes and the `api_secret_key` is per-app (not per-shop), that equality is never enforced — any body/hmac pair valid for shop A remains valid when replayed with shop B's domain in the header, because the secret and signature are identical across all shops of the app. This mirrors the reported bug class: a field acted upon (the shop identity used for tenant attribution) is not covered by the authenticating value (the HMAC), so an attacker can rebind an authenticated payload to an unauthenticated identity.

### Impact Explanation
This is a cross-tenant confused-deputy vector: a malicious merchant who has installed the app can capture a webhook payload/HMAC pair delivered to their own shop and resend it to the app's webhook endpoint with the `shop-domain` header changed to a different (victim) merchant's domain. The app's handler receives `WebhookMetadata` claiming the payload belongs to the victim shop, and will process, store, or act on attacker-controlled webhook body content (e.g., orders/create, app/uninstalled, customer data payloads) as though it originated from the victim tenant. Depending on the handler logic (job enqueueing keyed by `shop_domain`, data writes, triggering side effects tied to a shop record), this can result in cross-tenant data corruption or the app taking action against the wrong merchant's session/store — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires that the attacker be a legitimate (even single) installer of the app to obtain one authentic `(body, hmac)` sample for any topic they control (e.g. `app/uninstalled`, `orders/create` triggered from their own store), then replay it toward the endpoint with a forged `shop-domain` header. No access to `api_secret_key`, access tokens, or any other shop's credentials is required, since the header is never covered by the signature and the secret is shared per-app rather than per-shop.

### Recommendation
Bind the shop identity into the signed content check, or otherwise require server-side lookup that ties the header shop to an installation the app independently trusts before acting on the payload as belonging to that shop:
- Reject/flag webhooks where the `shop-domain` header does not correspond to a shop for which the app currently holds an active session/installation record, rather than trusting the header at face value.
- At minimum, document/require that host apps must cross-check `data.shop` against their own installed-shops list before using it as a tenant key, since `shopify_api` itself cannot include shop in the HMAC (Shopify signs only the body upstream).

### Proof of Concept
1. App is installed on `attacker.myshopify.com` and on victim shop `victim.myshopify.com`, sharing the same app `api_secret_key`.
2. Attacker triggers a webhook on their own shop (e.g., updates a product) and captures the raw body `B` and the resulting valid header `x-shopify-hmac-sha256: H` sent to the app's webhook endpoint.
3. Attacker resends the identical request to the app's webhook URL, keeping `raw_body: B` and `x-shopify-hmac-sha256: H`, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H`, so validation passes [7](#0-6) .
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop: "victim.myshopify.com"` even though the actual signed payload came from the attacker's own shop event, and the app's handler processes it as belonging to the victim tenant [2](#0-1) .
