### Title
Webhook `shop-domain` header is trusted as the tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header to the app's handler as the trusted tenant identifier, even though that header was never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string: [2](#0-1) 

`Registry.process` uses this same validation to decide the request is authentic, then reads `request.shop` (parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed bytes) and passes it into the handler as the tenant identity: [3](#0-2) [4](#0-3) [5](#0-4) 

The identity binding that should hold is:
`shop authenticated by the HMAC == shop acted upon by the handler`

But the HMAC only proves "this body was signed with the app's `client_secret`" — it says nothing about which shop the body belongs to. The `shop` field consumed by `WebhookMetadata` and handed to app-level handler code comes from an unauthenticated header. Since a single `client_secret` is shared across every shop that has installed the app, any shop that installs the app can obtain a validly-HMAC'd body (its own webhook deliveries) and then replay that exact body/HMAC pair to the app's webhook endpoint with a different `shop-domain` header claiming to be a different (victim) shop. `HmacValidator.validate` will pass (the body+secret pair is genuinely valid), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

### Impact Explanation
If the host application's webhook handler trusts `WebhookMetadata#shop` to select which tenant's data to create/update/delete (the common integration pattern, and the only tenant signal this gem exposes for webhooks), an attacker who legitimately installs the app on their own shop can forge webhook deliveries that are processed as belonging to an arbitrary other shop domain. This is a cross-tenant access vector: attacker-controlled body content gets attributed to and acted upon under a victim shop's identity, without ever compromising that shop's credentials.

### Likelihood Explanation
Moderate-to-high: exploitation requires only that the attacker be able to install the public app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer), capture one legitimate webhook delivery to their own endpoint, and resend it with a modified header. No secrets, tokens, or privileged access are needed — only the gem's documented `Registry.process`/`Request` API is used exactly as intended, and the schema gap (HMAC not covering headers) lives entirely inside this gem's webhook verification code.

### Recommendation
Do not rely on `request.shop` (or any other unsigned header) as a trust boundary once `HmacValidator.validate` returns true. Either:
- Include the tenant-identifying fields (at minimum `shop-domain`, ideally `topic` and `webhook-id`) in the signable string used for HMAC verification, so `to_signable_string` binds headers to the signature; or
- Require the caller to independently correlate `request.shop` against a shop for which the app holds a stored access token/session before trusting the payload, and document clearly that `WebhookMetadata#shop` is unauthenticated with respect to the HMAC.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to.
2. Capture the raw POST body and the `X-Shopify-Hmac-SHA256` header Shopify sends (this HMAC is valid because it's signed with the app's `client_secret`, which is shared across all shops using the app).
3. Replay the identical body and HMAC to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `Digest.hexencode(Base64.decode64(hmac_header))` against `OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)` — this succeeds because the body/HMAC pair is genuinely valid: [6](#0-5) . The handler then receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, i.e., attacker-controlled data processed under the victim's tenant identity.
