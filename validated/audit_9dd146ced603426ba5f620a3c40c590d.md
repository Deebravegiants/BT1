### Title
`OmniBridge.describeWithdrawal` reports withdrawal status by raw array index instead of asset/destination identity - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal` selects the transfer to report status for by indexing directly into the array returned by the Omni Bridge indexer (`getTransfer(...)[args.index]`), instead of matching it against the specific withdrawal's asset/destination like the `PoaBridge` implementation does. If the indexer's response array is not guaranteed to preserve the exact submission order (which is the reason the PoA bridge implementation was hardened to match by identity instead of index), a batch withdrawal containing multiple transfers can have its status/txHash misreported for the wrong asset.

### Finding Description
`OmniBridge.describeWithdrawal` is: [1](#0-0) 

It fetches all transfers for a NEAR transaction hash and picks entry `[args.index]` with no further verification that this entry actually corresponds to the withdrawal (asset, destination, amount) the caller is asking about. `index` is simply the position of this withdrawal within the caller-supplied `withdrawalParams` array, as documented in `createWithdrawalIdentifier`: [2](#0-1) 

Contrast this with `PoaBridge.describeWithdrawal`, which the codebase deliberately does **not** index-match, and instead calls `findMatchingWithdrawal` keyed by `assetId`: [3](#0-2) 

There is an explicit regression test in the PoA bridge suite documenting why index-based matching was rejected: "Response list is unsorted, so we match by assetId instead of index": [4](#0-3) 

This is the same equality-breaking pattern as the DittoETH `H-06` finding: a value used to finalize an outcome (which SR/withdrawal is being resolved) is assumed to still correspond to the same on-chain entity that was true when the request was constructed, but the underlying indexer state can reorder/change between submission and status-check time, and the code does not re-validate identity before reporting.

The `describeWithdrawal` API is documented as authoritative, one-shot status reporting used directly by integrators: [5](#0-4) 

### Impact Explanation
If the Omni Bridge indexer ever returns transfers for a multi-transfer NEAR transaction (batch withdrawal) in an order that does not exactly match submission order — which is exactly the failure mode the PoA bridge was hardened against — `describeWithdrawal` will attribute one withdrawal's `txHash`/`status` to a different `index`. An integrator relying on `describeWithdrawal`/`WithdrawalStatus` to mark a specific withdrawal (asset + destination) as `completed` with a given `txHash` could:
- Credit/refund the wrong withdrawal as completed (a status misreport causing a double credit or a stuck/never-credited withdrawal for the actual asset).
- Record an incorrect destination transaction hash against the wrong asset/destination pairing.

This falls under the "status or hash misreport making an integrator credit or refund twice" High-severity impact class.

### Likelihood Explanation
This only manifests for batch/multi-transfer NEAR withdrawals routed through the Omni Bridge, and requires the Omni indexer's `getTransfer` response array to not preserve submission order for a given `transactionHash`. I could not verify from the available index whether the Omni Bridge indexer's ordering guarantee differs from PoA's (this is an external indexer behavior outside repo scope), so likelihood is uncertain/dependent on that external API's actual behavior. However, the codebase's own precedent (fixing this exact class of bug for PoA with an explicit "unsorted" comment and regression tests) suggests engineers should not assume order-preservation for any of these bridge indexers by default, making this a credible latent risk rather than a purely theoretical one.

### Recommendation
Mirror the PoA bridge's approach in `OmniBridge.describeWithdrawal`: match the returned transfer by asset/destination identity (e.g., recipient/token/omni address fields available in the `getTransfer` response) instead of raw array `index`, and only fall back to `pending`/error if no matching entry is found — the same fix pattern already applied and tested in `poa-bridge.ts`.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
