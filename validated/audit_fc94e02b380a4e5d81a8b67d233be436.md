### Title
Governance/HostManager `withdraw()` on `EvmHost` can drain fee-token balance backing unpaid relayer fees, causing relayer fee payouts to revert - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.withdraw()` transfers an arbitrary, governance-specified amount of the fee token (or native token) out of the host contract without checking whether that balance is already earmarked to pay relayer fees for requests/responses that are dispatched but not yet delivered. Because the fee-token balance is a single shared pool used both for protocol revenue withdrawals and for future relayer fee payouts, a withdrawal that leaves the balance below the sum of outstanding `_requestCommitments[...].fee` obligations will cause the relayer's fee payout (executed automatically at delivery time via `safeTransfer`) to revert, exactly mirroring the Futaba `Gateway.sol` H-01 pattern where `withdraw()` zeroing/depleting a shared accounting pool causes a later relayer-facing function to revert.

### Finding Description
Each outgoing POST/GET request escrows its relayer fee in `_requestCommitments[commitment] = FeeMetadata({sender, fee})` at dispatch time [1](#0-0) [2](#0-1) . This fee is not moved into a separate escrow account — it stays in the contract's fee-token balance and is only paid out later, e.g. in `dispatchIncoming` for GET responses: [3](#0-2) 

Similar unconditional `safeTransfer`/native-transfer fee payouts happen on POST delivery, and on GET/POST timeout refunds [4](#0-3) .

Separately, `EvmHost.withdraw()` is the governance-facing function (invoked only through `HostManager.onAccept` on receipt of a Hyperbridge governance/host-executive `Withdraw` action) that pays out an arbitrary `params.amount` of the fee token or native asset to a beneficiary: [5](#0-4) 

This function performs no accounting check against the sum of unpaid/pending `_requestCommitments[...].fee` obligations — it only checks (implicitly, via `safeTransfer`/native transfer) whether the raw contract balance covers `params.amount`. There is no reserved/committed-liabilities counter anywhere in `EvmHost.sol` analogous to segregating "protocol revenue" from "relayer-fee escrow." The `pallet-host-executive`/`pallet-ismp-relayer` withdrawal flow that dispatches this `Withdraw` action likewise computes the withdrawal amount without querying outstanding relayer-fee liabilities on the destination EVM host [6](#0-5) .

This is structurally the same bug class as the Futaba `Gateway.sol` H-01 finding: a `withdraw()` path drains/zeroes a shared value that a later relayer-facing settlement function (`receiveQuery()` in Futaba, `dispatchIncoming`/`handlePostRequests`/timeout handlers in Hyperbridge) depends on, so that function reverts when the funds are no longer present.

### Impact Explanation
If the fee-token balance is drawn down below the sum of unpaid relayer-fee obligations for requests/responses already in flight (dispatched, awaiting proof delivery or timeout), then:
- Delivery of the affected request/response will still be processed and recorded (commitment/receipt consumed), but the relayer fee payout (`safeTransfer`) will revert, reverting the entire delivery transaction (or, on timeout, the refund) — matching the "Impact" of the referenced report (relayer/user paid or promised a fee that can never be collected).
- Because relayers are profit-driven, once fee payouts start reverting for a state machine, relayers stop delivering to it — this can degrade to "a route unable to deliver messages" for that chain, one of the explicitly accepted impact categories.
- Funds meant for a specific pending request's relayer fee are effectively at risk of being unpayable (frozen/lost) once withdrawn to governance/beneficiary, since `_requestCommitments` retains the fee amount as an accounting entry with no real backing balance.

### Likelihood Explanation
The `withdraw()` path is only reachable via a legitimate cross-chain governance/host-executive message (not by an arbitrary unprivileged actor), so it requires a routine — not necessarily malicious — governance withdrawal action, exactly as in the original report where an honest project owner triggers the conflict. Because `EvmHost` has no notion of "reserved/committed" balance vs "spendable revenue," any governance withdrawal sized to the full token balance (or without subtracting known pending fee commitments) will reliably trigger this race whenever there are outstanding dispatched-but-undelivered requests/responses at the time of withdrawal, which is a normal, expected operating condition on an active bridge.

### Recommendation
Track a running total of "committed" fee-token liabilities (sum of live `_requestCommitments[...].fee` values) separately from the raw ERC20/native balance, and have `withdraw()` only allow governance to withdraw the balance in excess of this committed amount, reverting (or capping) otherwise — analogous to fixing Futaba's `nativeTokenAmount` accounting by reserving funds tied to in-flight `query()` calls before allowing `withdraw()` to succeed.

### Proof of Concept
1. Application dispatches a POST/GET request via `EvmHost.dispatch(...)`, escrowing `fee` in `_requestCommitments[commitment]`, funded from the contract's fee-token balance [7](#0-6) .
2. Before the relayer delivers proof and claims the fee, Hyperbridge governance (via `pallet-host-executive::withdraw`) dispatches a `WithdrawalParams` request sized to (or exceeding) the current fee-token balance, which `HostManager.onAccept` forwards to `EvmHost.withdraw()` [8](#0-7) , draining the balance.
3. The relayer submits the delivery proof; `dispatchIncoming`/`dispatchTimeOut`/POST handling attempts `IERC20(feeToken()).safeTransfer(relayer, fee)` [9](#0-8) , which reverts because the balance was withdrawn in step 2, blocking delivery/timeout-refund for that request.

     * @dev withdraws host revenue to the given address, can only be called by cross-chain governance
     * @param params, the parameters for withdrawal
     */
    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
