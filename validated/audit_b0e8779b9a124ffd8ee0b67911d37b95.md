### Title
Undeclared flash-position callback assets are permanently locked in the controller - ([File: contracts/controller/src/strategies/flash_position.rs])

### Summary

`flash_position` refunds only positive controller-balance deltas for assets explicitly supplied in `refund_assets` and deposits only assets explicitly supplied in `collaterals`. A callback can therefore successfully deliver all required collateral while also transferring an additional listed asset, such as unused debt-token change, that belongs to neither list. The enclosing transaction succeeds, but the extra asset remains in the controller with no user-accessible recovery path.

### Finding Description

`process_flash_position` allows an authorized account owner or delegate to select a deployed receiver, mint debt into the controller, forward it to that receiver, and invoke `execute_flash_position`. [1](#0-0) [2](#0-1) 

After the callback, the controller snapshots only the declared collateral and refund assets, deposits positive declared collateral deltas, and invokes `refund_listed_assets` for `refund_assets`. [3](#0-2)  `refund_controller_balance_delta` refunds only the balance delta for the specific asset passed to it. [4](#0-3) 

Refund entries must be unique listed assets in the account spoke and debt hub and must be disjoint from the collateral list. [5](#0-4)  There is no corresponding default recovery pass over every token whose controller balance changed during the callback. [6](#0-5) 

The receiver is itself unprivileged and can execute arbitrary token transfers during its callback. [7](#0-6)  Consequently, a receiver that returns the required collateral plus an undeclared listed token satisfies the operation while leaving that token in controller custody. [8](#0-7) 

### Impact Explanation

The omitted callback output is neither credited as account collateral nor returned to the caller, so the user suffers permanent freezing of funds in the controller. [9](#0-8) [10](#0-9) 

This is directly analogous to a completed first settlement leg followed by an unrefunded residual asset: the transaction can succeed because all declared collateral minima are met, while a separately transferred output remains stranded. [8](#0-7)  The amount at risk is bounded by the undeclared assets transferred to the controller during the callback. [4](#0-3) 

### Likelihood Explanation

A user must authorize `flash_position`, provide a receiver, and have that receiver send a token that is absent from both `collaterals` and `refund_assets`. [11](#0-10) [12](#0-11) 

This can occur when a receiver route produces unused debt-token change or an intermediate output in addition to the required collateral. [13](#0-12)  Since refunding the debt token is supported but does not repay the minted debt, omission of that token from `refund_assets` leaves returned change stranded even though the operation itself remains valid. [10](#0-9) [14](#0-13) 

The issue requires a receiver integration mistake or incomplete refund declaration rather than an external attacker manipulating another user's transaction, making it Medium rather than Critical or High. [7](#0-6) 

### Recommendation

Refund every token whose controller balance increases during the callback, or reject the transaction when an undeclared positive balance delta is detected. [3](#0-2) 

If enumerating all possible token balances is impractical, require the receiver to return a machine-readable list of pushed assets and compare it against the declared collateral and refund sets before settlement succeeds. [7](#0-6)  At minimum, automatically treat the debt token as a refund asset when it was not consumed into a declared collateral position, without crediting it as repayment. [13](#0-12) [14](#0-13) 

### Proof of Concept

1. Alice creates or uses a `Multiply` account and calls `flash_position` with a flash-loan-enabled `ETH` debt market, `amount = 1 ETH`, `collaterals = [(USDC, required_min)]`, and `refund_assets = []`. [15](#0-14) [10](#0-9) 
2. The controller mints `1 ETH`, measures the receipt, forwards it to Alice's receiver, and invokes `execute_flash_position`. [16](#0-15) [7](#0-6) 
3. During the callback, the receiver transfers `required_min` USDC to the controller and also transfers `0.1 ETH` of unused debt-token change to the controller. [2](#0-1) 
4. The controller measures the USDC delta, deposits it as collateral, sees an empty `refund_assets` list, and completes the account risk checks. [6](#0-5) [8](#0-7) 
5. Alice's account has the new ETH debt and USDC collateral, but the `0.1 ETH` remains held by the controller because ETH was neither a collateral asset nor a refund asset. [3](#0-2) [10](#0-9) 
6. The test harness already demonstrates the intended complementary case: when the extra pushed asset is listed in `refund_assets`, the caller receives its exact delta and no collateral is credited. [17](#0-16)  Repeating that flow with `refund_assets` empty leaves the same positive callback receipt unprocessed. [18](#0-17)

```rust
/// Mints fee-free debt, verifies the controller receipt against the pool result,
/// then forwards it and returns the receiver's measured receipt.
fn mint_and_forward(
    env: &Env,
    account: &mut Account,
    debt: &HubAssetKey,
    amount: i128,
    receiver: &Address,
    cache: &mut Context,
) -> i128 {
    let controller = env.current_contract_address();
    let before = token::Client::new(env, &debt.asset).balance(&controller);

    let reported = borrow_into_controller(
        env,
        account,
        debt,
        amount,
        false,
        PositionAction::FlashPos,
        cache,
    );

    let measured = balance_delta_since(env, &debt.asset, &controller, before);
    assert_with_error!(env, measured == reported, GenericError::InternalError);
    assert_with_error!(env, measured > 0, GenericError::AmountMustBePositive);

    let forwarded = transfer_amount_measured(
        env,
        &debt.asset,
        &controller,
        receiver,
        measured,
        GenericError::AmountMustBePositive,
    );
    assert_with_error!(env, forwarded > 0, GenericError::AmountMustBePositive);
    forwarded
}
```

```rust
fn collect_collateral_deposits(
    env: &Env,
    controller: &Address,
    collaterals: &Vec<(HubAssetKey, i128)>,
    before: &Map<Address, i128>,
) -> Vec<(HubAssetKey, i128)> {
    let mut deposits: Vec<(HubAssetKey, i128)> = Vec::new(env);
    for (hub_asset, min_amount) in collaterals.iter() {
        let baseline = before
            .get(hub_asset.asset.clone())
            .unwrap_or_else(|| panic_with_error!(env, GenericError::InternalError));
        let delta = balance_delta_since(env, &hub_asset.asset, controller, baseline);
        assert_with_error!(
            env,
            delta >= min_amount,
            StrategyError::CollateralMinimumNotMet
        );
        if delta > 0 {
            deposits.push_back((hub_asset, delta));
        }
    }
    assert_with_error!(
        env,
        !deposits.is_empty(),
        StrategyError::CollateralMinimumNotMet
    );
    deposits
```

**File:** docs/reference/endpoints.md (L82-86)
```markdown
Pool supply measures receipts again. Borrow and supply caps are checked when each pool result merges into the account. Supply and the declared debt position must remain open after finalization.

Refund assets must be unique, listed in the debt hub and account spoke, disjoint from collateral declarations, and bounded by the maximum supply-position count. Refund eligibility requires an active spoke and an existing listing; it does not check collateralizable, borrowable, paused or frozen flags. Only positive balance changes above pre-callback balances return to the caller. The debt token can be a refund asset, but refunding it does not repay the minted debt.

Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint. Refunds produce token transfer events, without a dedicated controller refund event.
```
