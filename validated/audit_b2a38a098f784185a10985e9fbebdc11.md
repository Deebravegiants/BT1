### Title
Overpaid native token in `IntentGatewayV2.placeOrder` is permanently stuck (missing refund) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` tracks a running `msgValue` counter as it consumes native-token inputs and, when `order.fees` is paid in native token, swaps the remainder for the fee token — but unlike the reference EVM implementation in the same repo, it never returns any leftover `msgValue` to the caller. Any overpayment of `msg.value` (either on native-token order inputs or on the fee swap) is permanently locked in the contract.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` accepts `msg.value` and decrements a local `msgValue` variable as native-token inputs are escrowed: [1](#0-0) 

If `order.fees > 0` and the user pays with native token, the remaining `msgValue` is passed wholesale to `swapETHForExactTokens{value: msgValue}(order.fees, ...)`. The Uniswap router only needs `amounts[0]` of that value to produce the exact `order.fees` output and refunds the excess ETH back to `msg.sender` of the swap call — which is the `IntentGatewayV2` contract itself, not the end user: [2](#0-1) 

After this block, the function immediately emits `OrderPlaced` and returns — there is no step that forwards any leftover native balance back to `msg.sender`: [3](#0-2) 

This is functionally identical to the reported bug class: a `payable` entrypoint that partially consumes `msg.value` and leaves the remainder stuck in the contract instead of returning it to the caller. Confirming the fix exists elsewhere in the same repo, the primary EVM `IntentGatewayV2.placeOrder` at `evm/src/apps/IntentGatewayV2.sol` explicitly captures the swap's actual spend and refunds the difference: [4](#0-3) 

The Tron contract omits both the `amounts[0]` capture and the final `_sendValue(msg.sender, msgValue)` refund, meaning the two code paths diverged and the Tron deployment reintroduced the exact "funds stuck in the router/contract" class of bug that the EVM version deliberately guards against.

### Impact Explanation
Any user who submits `msg.value` in excess of what is strictly required (e.g., paying `order.fees` in native TRX when the actual on-chain swap cost is less than the quoted/estimated amount, which is common since swap output amounts fluctuate with pool state between quote time and execution time) will have that excess permanently locked in the `IntentGatewayV2` contract with no accounting entry (`_orders` mapping) tracking it and no owner-only or user-only withdrawal path for it. This is a permanent, protocol-level loss of user funds on every overpaid native-fee order placement on the Tron deployment, matching the "concrete... permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is high: any ordinary user calling `placeOrder{value: ...}(order, graffiti)` with `order.fees` paid in native token and a `msg.value` that doesn't exactly equal the router's actual required input (which is the normal case, since off-chain quoting cannot guarantee an exact on-chain swap cost) will trigger this loss on every single call. No special privileges or adversarial setup are required — it is a routine user-facing entrypoint.

### Recommendation
Mirror the `evm/src/apps/IntentGatewayV2.sol` logic in the Tron contract:
1. Capture the `amounts` array returned by `swapETHForExactTokens` and subtract `amounts[0]` from `msgValue`.
2. After all escrow/fee logic, add a final step that refunds any remaining `msgValue` to `msg.sender` (e.g., via a low-level `call` with value, matching `_sendValue` in the EVM variant).

### Proof of Concept
1. User calls `placeOrder{value: order.fees_estimate + extra}(order, graffiti)` where the order has a native-token input of `X` and pays `order.fees` in native token.
2. Inputs consume `X` from `msgValue`. Remaining `msgValue = order.fees_estimate + extra - X`.
3. `swapETHForExactTokens{value: msgValue}(order.fees, ...)` is called; suppose the actual native cost to buy `order.fees` fee-tokens is `amounts[0] < msgValue`. The router refunds `msgValue - amounts[0]` back to the `IntentGatewayV2` contract address (the caller of the swap), not to the user.
4. Function returns without ever moving that refunded balance back to `msg.sender`. The contract's TRX balance permanently increases by `msgValue - amounts[0]`, with no mapping entry crediting it to the user and no withdrawal path exposed for it — the funds are permanently unrecoverable by the user who overpaid.
