### Title
Missing validation of critical `Params` in Tron `IntentGatewayV2`'s `setParams` and `onAccept(UpdateParams)` can permanently brick the gateway and freeze escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` accepts and stores critical configuration parameters (`host`, `dispatcher`, `protocolFeeBps`, `surplusShareBps`, `priceOracle`) both in the one-shot `setParams` admin function and in the cross-chain governance `onAccept(UpdateParams)` handler, without performing any of the sanity checks that the canonical EVM implementation enforces via `IntentsBase._validateParams`.

### Finding Description
The canonical EVM `IntentGatewayV2`/`IntentsBase` implementation validates every parameter update through `_validateParams` before it is applied: [1](#0-0) 

This checks that `host` and `dispatcher` are non-zero contracts, that `surplusShareBps <= 10_000`, that `protocolFeeBps < 10_000`, and that `priceOracle` is either zero or a contract, explicitly to prevent "any value [that] would brick the gateway or cause arithmetic errors in fee calculations."

The Tron port of the same contract omits this validation entirely in both places parameters are set:

1. `setParams` (one-shot admin initializer) writes `_params = p` directly with no field checks: [2](#0-1) 

2. The cross-chain governance handler `onAccept` for `RequestKind.UpdateParams` likewise applies `_params = update.params` and destination-fee overrides with no bound check on `feeBps`, `host`, `dispatcher`, or `priceOracle`: [3](#0-2) 

Because `host()` on the Tron contract simply returns `_params.host`, and `onlyHost`/host-gated flows (in the shared `HyperApp` base) authorize callers by comparing `msg.sender` to `host()`: [4](#0-3) 

...an `UpdateParams` message (or the one-shot `setParams` call) that sets `host` to `address(0)` or to an address that never calls back into this contract permanently removes the only entity (`onlyHost`) allowed to call `onAccept`. Since `onAccept` is the sole entry point for `RedeemEscrow`, `RefundEscrow`, `NewDeployment`, `SweepDust`, and subsequent `UpdateParams` messages, this bricks all future cross-chain governance and settlement on this gateway instance — including release of already-escrowed funds recorded in `_orders`.

Separately, an out-of-range `protocolFeeBps >= 10_000` (100%+) is not rejected. `placeOrder` computes: [5](#0-4) 
`reducedAmount = originalAmount - protocolFee` will underflow/revert whenever `protocolFeeBps > 10_000` (Solidity 0.8 checked arithmetic reverts), making `placeOrder` permanently unusable until another (also unvalidated) `UpdateParams` message repairs it — itself only possible if `host`/`dispatcher` were not also corrupted in the same update.

### Impact Explanation
This maps to the audit report's bug class ("Validate critical input parameters") exactly: privileged setters accept unchecked values that can silently brick core protocol functionality. Concretely on Tron `IntentGatewayV2`:
- Setting `host = address(0)` (or a non-callback address) via `setParams` or a governance `UpdateParams` message permanently disables `onlyHost`-gated `onAccept`/`onGetResponse`, freezing any tokens already escrowed in `_orders` for cross-chain redemption/refund with no recovery path (the only way to fix `host` is itself an `onAccept(UpdateParams)` call, which is now unreachable).
- Setting `dispatcher` to an invalid/non-contract address bricks `predispatch` call flows in `placeOrder`.
- Setting `protocolFeeBps >= 10_000` causes `placeOrder` to always revert (denial of service on new orders) until fixed.

This satisfies "permanent freezing of funds" and "a route unable to deliver messages" per the validation criteria.

### Likelihood Explanation
`setParams` is a one-shot function guarded only by `msg.sender == _admin` with no other sanity check, so a single mistaken transaction (fat-finger, wrong deployment script argument, or compromised deployer key acting without malice) is sufficient to trigger the bug — this is precisely the "oversight" class of finding the original report targets, not a "malicious admin" exploit. The `onAccept(UpdateParams)` path is reachable by relayers delivering a legitimately-proven Hyperbridge governance message; if that message's payload was constructed with an unvalidated `Params` value (e.g., copy-paste error, wrong ABI encoding, or a value that was valid on the EVM contract but interacts differently here), the Tron contract applies it with no defense-in-depth, unlike its EVM sibling.

### Recommendation
Add the equivalent of `IntentsBase._validateParams` to the Tron `IntentGatewayV2.sol` and call it from both `setParams` and the `UpdateParams` branch of `onAccept`, before assigning `_params`:
- Require `p.host != address(0)` and has code.
- Require `p.dispatcher != address(0)` and has code.
- Require `p.surplusShareBps <= 10_000`.
- Require `p.protocolFeeBps < 10_000`.
- Require `p.priceOracle == address(0) || p.priceOracle.code.length > 0`.
- Require each `destinationFees[i].destinationFeeBps < 10_000` in the `UpdateParams` loop.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with `admin = A`.
2. `A` calls `setParams(Params({host: address(0), dispatcher: D, solverSelection: false, surplusShareBps: 0, protocolFeeBps: 0, priceOracle: address(0)}))`. This succeeds (no validation) and zeroes `_admin`. [6](#0-5) 
3. `host()` now returns `address(0)` forever (no path exists to call `setParams` again since `_admin` is zeroed, and `onAccept` requires `onlyHost` which can never be `address(0)`). [4](#0-3) 
4. Any user who had escrowed tokens via `placeOrder` (or does so before noticing the misconfiguration) can never have their order redeemed or refunded, since `withdraw` is only reachable from `onAccept`/`onGetResponse`, both gated `onlyHost` and now permanently unreachable — funds are frozen in the contract indefinitely.

    /**
     * @dev Validates gateway configuration parameters. Reverts with InvalidInput if any
     * value would brick the gateway or cause arithmetic errors in fee calculations.
     *
     * @param p The parameters to validate.
     */
    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
