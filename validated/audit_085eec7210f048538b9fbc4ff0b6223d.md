### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` cryptographically authenticates the webhook *body bytes* but never binds them to the `shop-domain` header. `Webhooks::Registry.process` nonetheless trusts that unauthenticated header as the tenant identity passed to the app's handler, breaking the identity binding `shop authenticated by HMAC == shop used as tenant/session key`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are the two members required by `Utils::VerifiableQuery` to make a payload verifiable: [1](#0-0) 

In `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

while `shop` is read straight from an HTTP header with no relationship to the signed body: [3](#0-2) 

`Registry.process` validates the HMAC over the body only, then immediately forwards the (unauthenticated) `request.shop` value to the app's webhook handler as the tenant identity: [4](#0-3) 

`HmacValidator.validate` confirms this: it only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`, so any field excluded from `to_signable_string` (here, the shop header) is not covered by the cryptographic guarantee at all: [5](#0-4) 

The identity binding that should hold is: `shop value cryptographically bound in the HMAC-signed payload == shop value used to attribute/act on the webhook`. This gem breaks that equality — the HMAC only proves "these bytes came from Shopify (or someone who knows the secret)", not "this webhook belongs to shop X".

### Impact Explanation
Because the `api_secret_key` is shared across every shop that installs the app, any unprivileged user can install the target app on their own free/trial Shopify store and receive genuine, correctly-HMAC-signed webhook deliveries for their own shop. Since the `shop-domain` header is not part of the signed content, that same valid `(body, hmac)` pair remains valid no matter what `shop-domain` header value is sent. An attacker can therefore replay/craft a POST to the app's public webhook endpoint using a real `(body, hmac)` pair they legitimately obtained, but with the `shop-domain` header changed to a victim merchant's domain. `Registry.process` will accept it (HMAC check passes) and hand the app's handler a `WebhookMetadata` claiming the event came from the victim shop — i.e., cross-tenant identity spoofing purely through this gem's own webhook verification logic.

### Likelihood Explanation
Any internet user can become a legitimate tenant of the app for free (install on a free/dev store), letting them harvest real `(body, hmac)` pairs signed with the shared `api_secret_key`. The webhook endpoint is by definition public/internet-reachable (Shopify must be able to POST to it), and no additional secret or credential is required to replay a request with a different header. This requires no token theft, TLS interception, or social engineering — only crafting an HTTP request, which matches the "unprivileged internet user" threat model.

### Recommendation
Bind the shop identity into the verified signature, or otherwise cross-check it against a trusted source before it is used for tenant attribution:
- Include the shop domain (and ideally topic/webhook id) in `to_signable_string`, matching what Shopify actually authenticates, or
- After computing the shop from the header, cross-validate it against the shop stored in the app's own session/installation record for the associated webhook subscription before invoking the handler in `Registry.process`, and reject on mismatch.

### Proof of Concept
1. Attacker installs the target Shopify app on their own free/trial store (`attacker-shop.myshopify.com`) and triggers a legitimate webhook (e.g. `orders/create`), capturing the raw POST: body `B` and header `shopify-hmac-sha256: H` (valid because `HMAC-SHA256(api_secret_key, B) == H`), along with `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends this exact request to the same app's public webhook endpoint, but replaces only the `shopify-shop-domain` header with `victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses headers and body normally; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` (`to_signable_string`) — unaffected by the header change — and the check passes (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `request.shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198`), even though that shop never sent this webhook — the app processes attacker-controlled data attributed to the victim tenant.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
