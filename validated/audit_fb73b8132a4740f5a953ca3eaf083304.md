Based on my investigation, I found the vulnerable pattern.

### Title
Unvalidated `message.from` length in `HyperFungibleToken::on_accept` causes a `copy_from_slice` panic reachable from any permissionless cross-chain POST request - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`Pallet::<T>::on_accept` (the `IsmpModule` callback invoked when a POST request destined for this pallet is delivered via `pallet_ismp::handle_unsigned`) decodes an ABI-encoded `Message` body and, for the calldata-execution branch, derives a dispatch origin from `message.from` for non-EVM source chains by copying it directly into a fixed `[u8; 32]` buffer with `copy_from_slice`, without first checking its length.

### Finding Description
In `on_accept` [1](#0-0) , when `message.data` is non-empty and no `signature` field is present in the decoded `SubstrateCalldata`, the code takes the branch:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [2](#0-1) 

`message.from` is an attacker-controlled field inside the ABI-encoded `body` of an ISMP `PostRequest` [3](#0-2) . Note this is distinct from the `PostRequest.from` module identifier (which is checked against `ContractToAsset` for authentication) — `message.from` is a nested field inside the ABI body that the sending module can set to any byte length, since it is only interpreted as a beneficiary-account-derivation hint, not validated against a fixed size before use.

For the `to_bytes` field just above, the pallet correctly validates the length (accepting only 32 or 20 bytes and erroring via `HftError::InvalidRecipientLength` otherwise) [4](#0-3) . The `from_bytes` non-EVM branch has no equivalent check: `copy_from_slice` traps (panics) if `from_bytes.len() != 32`, exactly the `copy_from_slice`-length-mismatch pattern the codebase has already fixed elsewhere (see the regression tests and comments explicitly calling this out as "a wasm trap reachable from untrusted input... in the runtime this...aborts/crashes"). [5](#0-4) [6](#0-5) 

This callback is invoked during `pallet_ismp::execute` → `handle_incoming_message` → request handler → `router.module_for_id(...).on_accept(...)`, which runs both during `validate_unsigned` (mempool validation, executed by every node/collator for every submitted `handle_unsigned` extrinsic) and during actual block execution [7](#0-6) . A panic here is a Wasm trap during runtime execution, which — per the exact precedent already documented in this codebase for the identical bug class — aborts the node process/worker (crashing collators/full nodes), analogous to the Fabric CVE where an unvalidated proposal field crashed the peer gateway service.

### Impact Explanation
Any user/relayer able to dispatch an ISMP POST request from a registered non-EVM (Substrate) source chain to a HFT-token-authorized `ContractToAsset` pair, with a crafted `body` whose `Message.from` field is not exactly 32 bytes and whose `data` is non-empty and unsigned, can trigger a runtime panic on delivery. Depending on how `validate_unsigned`/`execute` panics propagate, this can crash the collator/validator node executing the block or processing the extrinsic in the transaction pool — a Denial of Service on message delivery for the affected chain, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Reaching this path requires: (1) a registered `ContractToAsset` mapping for `(source, from_module)` to pass authentication, and (2) the source chain being configured as non-EVM (`is_evm() == false`) at the pallet/dispatcher level. Given these preconditions, any account able to dispatch a POST request from that source chain (an ordinary, permissionless action) fully controls the ABI-encoded `Message.from` bytes and can set an arbitrary length, making exploitation straightforward once a non-EVM HFT deployment exists.

### Recommendation
Validate `from_bytes.len()` before using it, mirroring the existing `to_bytes` length check (accept only the expected fixed length, e.g. 32 bytes for Substrate account IDs) and return `HftError::InvalidRecipientLength`-style error instead of panicking, exactly as already done for `to_bytes` a few lines above.

### Proof of Concept
1. Deploy/configure `pallet-hyper-fungible-token` with a `ContractToAsset` entry for a non-EVM `source` state machine and its `from` module id.
2. From that source chain, dispatch (or have a relayer submit via `handle_unsigned`) a POST request to the HFT module whose `body` ABI-encodes a `Message` with: a valid `to` (32 or 20 bytes), a valid `amount`, and `data` set to a non-empty `SubstrateCalldata` encoding with `signature: None`, and `from` set to a byte vector of any length other than 32 (e.g., 1 byte or 40 bytes).
3. Submit the message for execution (`pallet_ismp::Call::handle_unsigned`).
4. `on_accept` reaches the `else` branch of the `is_evm()` check, calls `account.copy_from_slice(from_bytes)` with mismatched lengths, and traps, crashing the executing node's runtime — reproducible offline by unit-testing `on_accept` with such a crafted `PostRequest`.
