This confirms the exploitable pattern: `CallDispatcher` routinely holds real ERC20 balances and ETH mid-transaction — `IntentGatewayV2.placeOrder` transfers `predispatch.assets` to the dispatcher and swap output tokens are sent directly to `address(dispatcher)` (e.g. `recipient: address(dispatcher)` in the Uniswap V3 test, `path[1]` swaps to `address(dispatcher)` in V2 tests, and `HyperFungibleToken` docs recommend minting cross-chain transfers straight `to: CALL_DISPATCHER`). Yet `CallDispatcher.dispatch(bytes)` [1](#0-0)  has **no access control** — it is a bare `external` function callable by anyone, not gated by `onlyHost`, `msg.sender` checks, or a caller allow-list.

### Title
Unrestricted `CallDispatcher.dispatch()` allows theft of any tokens/ETH the shared dispatcher is holding mid-transaction - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a shared, address-reused utility contract deployed once per chain and referenced by `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, etc. [2](#0-1) . Multiple flows deliberately route ERC20 tokens and native ETH into the dispatcher's own address as an intermediate step (predispatch swaps, output "beneficiary" set to the dispatcher, cross-chain HFT calldata minting to the dispatcher) before the dispatcher's `dispatch()` sweeps them back out. `dispatch(bytes memory encoded)` is `external` with **no caller restriction**: `abi.decode`s an arbitrary `Call[]` and executes each `to.call{value: call.value}(call.data)` with `CallDispatcher` as `msg.sender` [1](#0-0) .

### Finding Description
Because `dispatch()` has no `onlyHost`/`onlyOwner`/caller check, any address can call it directly at any block, independent of `IntentGatewayV2`'s or `HyperFungibleToken`'s own logic. If, at the moment of the call, `CallDispatcher` holds any ERC20 balance or ETH — which by design it transiently does during `placeOrder`'s predispatch/postdispatch execution (`evm/src/apps/IntentGatewayV2.sol:236-289`, `evm/tron/contracts/apps/IntentGatewayV2.sol:390-449`) or during HFT calldata delivery when tokens are minted directly `to: CALL_DISPATCHER` [3](#0-2)  — an attacker can front-run/interleave a call to `dispatch()` with a `Call[]` that transfers those tokens/ETH to themselves before the legitimate sweep-back executes.

This is directly analogous to the CVE-2024-23052 bug class: an externally reachable entry point that deserializes/decodes attacker-controlled data (`abi.decode(encoded, (Call[]))`) and immediately acts on it with the contract's own authority/funds, with no gating on who may trigger it — the Solidity equivalent of `fastjson.parseObject()` executing attacker-chosen instructions with the caller's privileges.

The intermediate holding is not a rare edge case: it is the intended UniswapV2/V3 swap pattern used throughout `IntentGatewayV2Test.sol` (`recipient: address(dispatcher)`, `path[1]` output to dispatcher) and the HFT/WHFT docs explicitly instruct integrators to mint tokens to the dispatcher so it can "spend the tokens" — meaning on live deployments the dispatcher is expected to briefly custody real user/solver funds within a single transaction, but between the transfer-in and the gateway's own `dispatch()` call there is no reentrancy or atomicity guarantee preventing a second, attacker-issued `dispatch()` call from draining the balance mid-flight (e.g., via a malicious `to` contract invoked in the legitimate `Call[]`, which can re-enter `CallDispatcher.dispatch()` itself since `dispatch` has no reentrancy guard).

### Impact Explanation
Concrete theft of funds: an attacker can drain the ERC20/native balance `CallDispatcher` is holding during `IntentGatewayV2.placeOrder`'s predispatch/postdispatch swap sequence or during `HyperFungibleToken.onAccept`'s calldata execution, by calling `dispatch()` themselves (directly, or via reentrancy from a malicious `to` target invoked inside the legitimate call sequence) before the gateway/token contract sweeps the balance back to itself. Given `CallDispatcher` is a single shared deployment referenced by every intent order and every HFT transfer with calldata on a chain, the blast radius covers all concurrent in-flight predispatch/postdispatch executions and any minted-to-dispatcher HFT deliveries.

### Likelihood Explanation
High reachability, no privilege required, and the vulnerable window occurs on every `placeOrder` call that uses `predispatch`/`postdispatch` with token transfers to the dispatcher, and every HFT transfer that mints `to: CALL_DISPATCHER`. This does not require breaking consensus proofs, ISMP handler verification, or any relayer authorization — it is a plain reentrancy/front-running attack against an unguarded public function holding transient funds.

### Recommendation
Add a reentrancy guard to `CallDispatcher.dispatch()` and/or restrict `dispatch()` to a caller allow-list (the specific gateway/token contracts that are expected to invoke it), so it cannot be triggered by an arbitrary EOA or re-entered mid-execution while it is custodying funds. Alternatively, redesign the flow so `CallDispatcher` never holds a standing balance observable/exploitable between transfer-in and sweep-back within the same transaction (e.g., single atomic call that both funds and sweeps, with `nonReentrant`).

### Proof of Concept
1. Attacker monitors mempool for an `IntentGatewayV2.placeOrder` call with non-empty `predispatch.assets`/`predispatch.call`, or an inbound `HyperFungibleToken.onAccept` delivery whose `message.to` is `CALL_DISPATCHER`.
2. Between the legitimate transfer of tokens to `dispatcher` (`evm/src/apps/IntentGatewayV2.sol:248-251`) and the sweep-back `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` (`evm/src/apps/IntentGatewayV2.sol:289`), the attacker submits their own transaction directly calling `CallDispatcher.dispatch(encodeAttackerCalls)` where `attackerCalls = [{to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, dispatcherBalance)}]`.
3. Because `CallDispatcher.dispatch` has no access control, this succeeds, transferring the dispatcher's temporarily-held tokens to the attacker before the legitimate gateway sweep runs (or causing the legitimate sweep to under-transfer / revert on insufficient balance, corrupting order-input accounting `evm/src/apps/IntentGatewayV2.sol:274-306`).
4. Alternatively, a malicious `to` contract placed inside a legitimate `Call[]` (e.g., an attacker-controlled "router" address used in `order.predispatch.call`) can re-enter `CallDispatcher.dispatch()` before the outer sequence completes, since `dispatch()` has no `nonReentrant` modifier.
