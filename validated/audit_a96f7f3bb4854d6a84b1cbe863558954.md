## Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong `txHash`/status to be reported for one of several same-asset withdrawals in a batch - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

## Summary
`PoaBridge.describeWithdrawal()` and the internal-utils twin `waitForWithdrawalCompletion()` resolve which on-chain withdrawal record corresponds to a given `WithdrawalIdentifier` purely by matching `assetId` (`nep141:${near_token_id}`), ignoring the `index` that uniquely distinguishes multiple withdrawals of the same asset created in one NEAR transaction. When a batch withdrawal contains two or more entries for the same asset (e.g., two `ft_withdraw` intents for `btc.omft.near` to two different destination addresses), every index resolves to the same (first) matching record, so the SDK reports the wrong `status`/`txHash` for at least one of the withdrawals.

## Finding Description
`findMatchingWithdrawal()` in both locations does an unconditioned `.find()` over the bridge's withdrawal list using only the asset identifier: [1](#0-0) 

The same pattern (and same documented limitation) is duplicated in the internal-utils helper used by `waitForWithdrawalCompletion`: [2](#0-1) 

`describeWithdrawal()` then trusts whatever record `findMatchingWithdrawal` returns and reports its status/txHash unconditionally: [3](#0-2) 

The equality that should hold is: *"the status/txHash reported for withdrawal index N must be the on-chain outcome for the specific withdrawal request at index N."* Because matching is keyed solely on `assetId`, two withdrawal requests for the same asset (different `index`, different `destinationAddress`, possibly different `amount`) collapse onto whichever bridge-side record happens to be first in the unsorted API response. If withdrawal #0 is still `PENDING`/`FAILED` while withdrawal #1 (same asset) is `COMPLETED`, both `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` will return the *same* record — reporting completion (with a `txHash` belonging to the other withdrawal) for a request that has not actually settled, or vice versa.

This is explicitly acknowledged as a known limitation in the code comment: *"multiple withdrawals of the same token in a single transaction are not supported."* It is not a hypothetical edge case — any caller of `IntentsSDK.processWithdrawal()`/`createWithdrawalCompletionPromises()` that batches two withdrawals of the same asset in one intent (a legitimate, unprivileged use of the public batch-withdrawal API) triggers it.

## Impact Explanation
This breaks the "status reported == on-chain outcome" invariant explicitly called out as in-scope. An integrator (exchange, custodian, wallet) polling `describeWithdrawal`/`waitForWithdrawalCompletion` to decide when to mark a withdrawal complete and unlock further balance/credit could:
- Treat a still-pending or failed withdrawal as `completed`, releasing further funds/credit prematurely based on a `txHash` that belongs to a *different* withdrawal request (misattributed proof of settlement — a status/hash misreport that can make an integrator credit twice, matching the defined High-impact category "a status or hash misreport making an integrator credit or refund twice").
- Conversely, treat a completed withdrawal as pending/failed, causing a stuck-funds/manual-intervention situation.

## Likelihood Explanation
Likelihood is moderate to high in practice: any unprivileged SDK consumer performing a routine batch withdrawal (`sdk.processWithdrawal`/`createWithdrawalCompletionPromises` with multiple `withdrawalParams`) containing two entries for the same PoA-bridged asset (a supported, documented flow — nothing prevents it) will trigger the collision. No malicious actor is required; it is triggered by ordinary API usage combined with the bridge's unsorted response ordering.

## Recommendation
Disambiguate withdrawals of the same asset by additional discriminating fields returned by the POA API (e.g., `amount`, `address`, `created` timestamp, or an explicit index/nonce if the API exposes one), or fall back to matching by `(assetId, destinationAddress, amount)` tuple, and only return `completed` when a record uniquely correlates to the specific withdrawal index. If the POA API cannot disambiguate deterministically, the SDK should refuse to resolve status for duplicate same-asset withdrawals in a single transaction rather than silently returning a matching-but-wrong record.

## Proof of Concept
1. Call `sdk.processWithdrawal`/`createWithdrawalCompletionPromises` with two `withdrawalParams` for the same PoA asset, e.g. `nep141:btc.omft.near`, sent in one batch/transaction to two different destination addresses (index 0 and index 1).
2. Assume the bridge processes withdrawal #0 (index 0) as `PENDING` and withdrawal #1 (index 1) as `COMPLETED` with `transfer_tx_hash = "btc-tx-hash-1"`.
3. Call `bridge.describeWithdrawal()` for `index: 0` — `findMatchingWithdrawal` filters only by `assetId === "nep141:btc.omft.near"` and returns whichever record appears first in the (unsorted) `withdrawals` array — potentially the `COMPLETED` record belonging to index 1.
4. The SDK reports `{status: "completed", txHash: "btc-tx-hash-1"}` for withdrawal index 0, even though index 0's actual on-chain withdrawal has not completed — the reported outcome does not match the on-chain outcome for that specific withdrawal. [1](#0-0) [3](#0-2)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
