### Title
Token exchange sends `client_secret` to an unsanitized host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the OAuth token-exchange request host directly from `jwt_payload.shop`, which is derived from the JWT `dest` claim, without ever calling `Utils::ShopValidator.sanitize!` on it. Every other credential-bearing flow in this gem (`client_credentials`, `refresh_access_token`, `migrate_to_expiring_token`) explicitly sanitizes the `shop` value with `ShopValidator` before using it to build the request URI.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the `dest` claim of the decoded JWT and returns it verbatim: [1](#0-0) 
`JwtPayload.initialize` only verifies the JWT signature and that `aud == Context.api_key`; it never validates that `dest`/`iss` is a genuine `*.myshopify.com` (or otherwise trusted) domain: [2](#0-1) 

`exchange_token` then takes this unsanitized `dest_shop` and uses it directly to build the session/host for the outbound HTTP request that carries the app's `client_id` and `client_secret`: [3](#0-2) 

Compare this to the three sibling methods that build an identical `client_id`/`client_secret`-bearing request but which route the `shop` value through `Utils::ShopValidator.sanitize!` first: [4](#0-3) [5](#0-4) [6](#0-5) 

`ShopValidator.sanitize!` exists specifically to enforce that a shop-derived host resolves to a trusted Shopify domain (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) before it's used to build a request URI: [7](#0-6) 

The binding that should hold is: *host that receives `client_secret` == a shop domain that has passed `ShopValidator.sanitize!`*. In `exchange_token` this equality is broken — the host is only constrained by JWT signature validity (i.e., it must be a domain string that the app itself encoded into a JWT it signed with its own secret), not by domain trust rules. Because `JwtPayload` never restricts `dest` to `*.myshopify.com`-style domains, any string can appear in `dest`, and a host application that (per this gem's documented flow) simply forwards `sessionToken`/`id_token` values it receives from the browser into `exchange_token` will make this gem's HTTP client POST the app's `client_id`/`client_secret` to `https://<dest>/admin/oauth/access_token`, where `<dest>` came from a JWT payload's `dest` field.

### Impact Explanation
If `dest` can be influenced to point at an attacker-controlled host, this results in SSRF carrying the app's credentials (`client_id`/`client_secret`) to a non-Shopify host — matching the "High: SSRF with the app's credentials" impact category in scope. This is a genuine inconsistency in this gem's own code (three of four analogous methods sanitize; one does not), not merely a host-application misuse issue.

### Likelihood Explanation
Exploitability hinges on whether an unprivileged party can get a JWT with attacker-controlled `dest`/`aud` signed by the app's own `api_secret_key`/`old_api_secret_key` accepted here — this gem only accepts session tokens signed with the app's configured secret(s) and matching `aud == Context.api_key` (`lib/shopify_api/auth/jwt_payload.rb:43-44`). I could not confirm, from the code available in this index, any path where an unprivileged internet user supplies a JWT that passes this signature/audience check yet carries an attacker-chosen `dest`, since normal session tokens are minted by Shopify itself. Without that, the missing `ShopValidator` call is a code-consistency/defense-in-depth gap rather than a demonstrated remotely-triggerable SSRF.

### Recommendation
Sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` in `exchange_token` before constructing `shop_session`/`Clients::HttpClient`, matching the pattern already used in `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
Could not construct a concrete unprivileged-attacker PoC: doing so would require producing a session token whose `dest` claim is attacker-controlled yet which still passes JWT signature verification against the app's `api_secret_key`, which is not achievable without the secret. This is flagged as a code-consistency/defense-in-depth gap rather than a proven exploit given the available index contents.

        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
