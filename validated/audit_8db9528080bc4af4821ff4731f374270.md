Confirmed root cause. The gem's webhook HMAC only ever signs the raw request body, never the `shop`, `topic`, `webhook_id`, or `api_version` headers.### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) fields entirely from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only ever verifies the raw request body against the HMAC. `Registry.process` accepts the request once the body's HMAC checks out and then hands the handler a `WebhookMetadata` object whose `shop` value was never part of the signed material, breaking the equality `shop authenticated by HMAC == shop used as the tenant key by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read directly out of the `shopify-*`/`x-shopify-*` headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` trusts this validation and then constructs the metadata the host app relies on for tenant identification directly from the unauthenticated header value: [4](#0-3) 

Because the app's `client_secret` (and thus the HMAC key) is shared across every shop that has installed the app, any shop that installs the app receives genuine webhook deliveries with a body+HMAC pair that is valid for that secret regardless of which shop the request nominally targets. An attacker who controls their own installation of the app can capture one such valid `(raw_body, X-Shopify-Hmac-Sha256)` pair, then replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` invokes the registered handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain and `body`/`topic` from the attacker's own store. The gem's documented handler contract explicitly tells host apps to key work off `data.shop`: [5](#0-4) 
so any app that follows this documented pattern (looking up the victim's stored session/access token, or writing data attributed to the victim shop, based on `data.shop`) can be tricked into acting on attacker-controlled content under another tenant's identity.

### Impact Explanation
This is a cross-tenant identity-binding break as described in the rules: the `shop` acted upon by the handler is not the `shop` actually covered by the signature check. A malicious but otherwise unprivileged app-installer can forge the tenant identity of a webhook delivery, causing the host application to process attacker-controlled data or trigger the app's own logic (which typically loads the victim shop's access token/session) under the wrong shop — a cross-tenant access scenario.

### Likelihood Explanation
Exploitation requires only that the attacker install the app on their own store (available to any merchant/unprivileged internet user in an app-listing scenario) and be able to POST an HTTP request to the app's public webhook endpoint with modified headers — no access to the app's `client_secret` or any privileged credential is needed, since the captured HMAC/body pair from the attacker's own legitimate delivery remains valid.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC verification, e.g., by including the shop domain in the signable string, or by requiring the caller to independently confirm the delivered `shop` header corresponds to a shop the app has an active installation/session for before trusting `WebhookMetadata#shop`. At minimum, document loudly that `data.shop` is unauthenticated and must be validated against known installed shops before use.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker.myshopify.com`) so Shopify delivers a genuine webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Replay the same request to the app's webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com` from the header, and `HmacValidator.validate` succeeds because it only hashes `B`: [6](#0-5) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's data>, ...)`, causing the host app (following the documented pattern) to act on attacker data as if it were victim data.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
