### Title
RAY value overflow during interest accrual permanently freezes a market - (File: common/src/rates/scaling.rs)

### Summary

A market whose scaled supply or debt value exceeds `i128::MAX` cannot complete interest accrual. `accrue_step` converts both stored scaled totals back to RAY-denominated values using `scaled_to_original`, which performs `scaled * index / RAY` and panics when the result cannot fit in `i128`. [1](#0-0) [2](#0-1) [3](#0-2) 

The borrow-index ceiling is applied only after `scaled_to_original` has already multiplied the stored scaled debt by the current borrow index, so it cannot prevent the arithmetic failure. [4](#0-3) [5](#0-4) 

### Finding Description

Every market operation loads its `Cache` and calls `interest::global_sync` before performing the requested action. [6](#0-5)  `global_sync` invokes `accrue_chunk` for each elapsed accrual window, and `accrue_chunk` invokes `accrue_step`. [7](#0-6) 

`accrue_step` first evaluates:

```rust
borrowed * borrow_index
supplied * supply_index
```

through `scaled_to_original`. [8](#0-7)  `scaled_to_original` delegates to `Ray::mul`, whose result must fit `i128`; an unrepresentable result raises `GenericError::MathOverflow`. [2](#0-1) [9](#0-8) 

A permissionless caller can reach this through `Controller::update_indexes(caller, assets)`, which authorizes the caller and forwards the selected `HubAssetKey`s to `pool_update_indexes`. [10](#0-9) [11](#0-10)  The pool then calls `ops::market::accrue`, which executes `global_sync` for each requested market. [12](#0-11) 

The failure becomes sticky because the problematic multiplication occurs before state changes required to reduce `borrowed`, `supplied`, or either index. `repay`, `withdraw`, liquidation seizure, and other market legs all call `load_leg` or `synced_market`, both of which perform `global_sync` first. [6](#0-5) [13](#0-12) [14](#0-13) [15](#0-14) 

### Impact Explanation

Once elapsed time causes either `borrowed * borrow_index` or `supplied * supply_index` to exceed the representable `i128` range, the selected market cannot process repayment, withdrawal, borrowing, liquidation, bad-debt seizure, further index updates, or other operations that begin with accrual. [6](#0-5)  Suppliers cannot exit, borrowers cannot reduce the offending scaled debt, and liquidators cannot remove it through seizure because all of those paths panic before mutation. [16](#0-15) [17](#0-16) [18](#0-17) 

This permanently freezes all funds assigned to that market under the deployed code. The repository’s own integration test demonstrates the condition: after sustained high utilization, `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [19](#0-18) 

### Likelihood Explanation

The market does not require malformed storage or privileged intervention at trigger time. Governance-admitted supply and borrow caps can permit a large market, and an unprivileged account can later call `update_indexes` after time has advanced enough for the scaled value to cross the `i128` ceiling. [10](#0-9) [11](#0-10) 

The existing harness constructs an 18-decimal market with one billion whole supplied tokens and 98% utilization on the steep test curve, advances time until synchronization fails, and confirms that repayment and withdrawal also fail. [20](#0-19)  Although this requires a whale-scale position and substantial collateral for borrowing, it is reachable through normal `supply`, `borrow`, and `update_indexes` calls within the protocol’s admitted arithmetic domain. [21](#0-20) [10](#0-9) 

### Recommendation

Prevent market accrual from evaluating an unrepresentable scaled total before reducing or clamping it. In particular:

- Bound scaled supply and debt by an accrued-value ceiling stricter than `i128::MAX`, rather than relying only on `MAX_SUPPLY_INDEX_RAY` and `MAX_BORROW_INDEX_RAY`.
- Perform the utilization calculation with saturating or widened arithmetic, and handle the over-limit state deterministically.
- Add a recovery path that can reduce debt or supply shares without first calling the panicking total-value multiplication.
- Enforce caps during supply and borrow using the projected post-accrual scaled value, not only the configured token-unit cap.
- Preserve a non-accruing administrative or permissionless emergency settlement path for markets already over the representable-value boundary.

Any fix must account for `scaled_to_original` being used both for utilization and later reward calculations, since a saturating utilization alone will not protect `calculate_supplier_rewards` and `update_supply_index`. [22](#0-21) [23](#0-22) [24](#0-23) 

### Proof of Concept

The repository already contains a deterministic reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`:

1. Create an 18-decimal market using the steep `xlm_curve`, plus collateral market `COL`.
2. Raise both markets’ supply and borrow caps to `max_cap_for_decimals`.
3. Supply `1_000_000_000 * 10^18` units of the market asset.
4. Supply sufficient `COL` and borrow 98% of the market asset.
5. Advance time and repeatedly call the permissionless `update_indexes`.
6. Observe `MathOverflow` before `MAX_BORROW_INDEX_RAY` is reached.
7. Confirm subsequent `withdraw` and `repay` calls also fail with `MathOverflow`. [19](#0-18) 

Equivalent production invocation:

```rust
controller.update_indexes(
    attacker,
    vec![HubAssetKey {
        hub_id,
        asset: oversized_market_asset,
    }],
);
```

After the ledger timestamp has advanced enough, the pool reaches `accrue_step`, evaluates `scaled_to_original(borrowed, borrow_index)` or `scaled_to_original(supplied, supply_index)`, and panics before committing a usable state transition. [1](#0-0) [12](#0-11)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero

    require_nonzero_divisor(env, d);

        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
