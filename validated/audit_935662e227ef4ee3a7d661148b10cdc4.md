Audit Report

## Title
Stale `effective_weight_limit` after `bank_pending_storage_changes` deposit charge allows weight to be spent past the true Ethereum gas budget - (File: substrate/frame/revive/src/metering/mod.rs)

## Summary
`FrameMeter::bank_pending_storage_changes` (at `substrate/frame/revive/src/metering/mod.rs` L678-684) delegates to `RawMeter::bank_pending_changes` (`substrate/frame/revive/src/metering/storage.rs` L514-528), which can call `charge_deposit` and thereby increase `total_deposit` via `record_charge`, but unlike its sibling methods (`charge_contract_deposit_and_transfer`, `record_contract_storage_changes`) it never calls `self.adjust_effective_weight_limit()` afterward. This leaves `WeightMeter::effective_weight_limit` stale in `TransactionLimits::EthereumGas` mode, where the effective weight ceiling is derived jointly from weight and deposit consumption.

## Finding Description
`adjust_effective_weight_limit` is explicitly documented as needing to be "called whenever there is a change in the deposit meter" [1](#0-0) , and both deposit-mutating paths that are meant to keep the weight ceiling in sync correctly call it right after mutating `self.deposit`: `charge_contract_deposit_and_transfer` [2](#0-1)  and `record_contract_storage_changes` [3](#0-2) .

`bank_pending_storage_changes`, however, only calls `self.deposit.bank_pending_changes(contract, info)` and returns `()`, with no follow-up adjustment call [4](#0-3) . Its underlying `RawMeter::bank_pending_changes` applies the pending diff to `ContractInfo` and, when the resulting deposit is non-zero, calls `self.charge_deposit(contract, deposit)`, which calls `record_charge(&amount)` and increases `total_deposit` [5](#0-4) . This function is explicitly documented as being used before creating a nested frame in a same-contract reentrant call, referencing contract-issues#213 [6](#0-5) .

Since `effective_weight_limit` is a function of both weight and deposit consumption in Ethereum gas mode via `weight_left()` → `math::ethereum_execution::weight_left` [7](#0-6) , and `WeightMeter::charge` checks `new_consumed.any_gt(self.effective_weight_limit)` against whatever `effective_weight_limit` currently holds [8](#0-7) , an increase to `total_deposit` via `bank_pending_storage_changes` that is not followed by a recompute leaves the weight ceiling too high relative to the true remaining eth-gas budget.

## Impact Explanation
In `TransactionLimits::EthereumGas` mode, a call path that triggers `bank_pending_storage_changes` (same-contract reentrancy, per the documented contract-issues#213 use case) followed by further weight-consuming operations (e.g., `charge_weight_token`, which calls `self.weight.charge(token)` directly) could allow weight consumption to exceed what the true combined gas/weight/deposit budget should permit, because the ceiling used by `WeightMeter::charge` was not lowered to reflect the additional deposit consumed by the banking operation. This constitutes accounting drift in the resource-metering component that underpins Ethereum-gas-equivalent execution limits.

## Likelihood Explanation
The code-path discrepancy is real and directly verifiable: `bank_pending_storage_changes` is the only deposit-affecting `FrameMeter` method that omits the `adjust_effective_weight_limit()` call that its siblings perform [9](#0-8) . However, whether this is actually attacker-reachable and produces a measurable overrun depends on execution-flow details not confirmed here: whether `bank_pending_storage_changes` is called mid-frame-execution before further weight charges are made in the same frame (as opposed to only at frame-teardown/entry boundaries where no further `charge_weight_token` calls follow before an eventual re-adjustment elsewhere), and whether other call sites in `exec.rs` re-derive the effective weight limit shortly after (e.g., via a subsequent `record_contract_storage_changes`/`charge_contract_deposit_and_transfer` or an equivalent adjustment on frame entry/exit) that would mask or bound the staleness window. The available regression tests (`same_contract_reentry_does_not_double_count_storage`) verify storage/deposit accounting correctness but do not test or demonstrate a weight-limit bypass; no PoC in the report actually exercises the eth-gas weight-limit-bypass scenario.

## Recommendation
Add `self.adjust_effective_weight_limit()?` inside `FrameMeter::bank_pending_storage_changes` immediately after `self.deposit.bank_pending_changes(...)`, matching the pattern in `charge_contract_deposit_and_transfer` and `record_contract_storage_changes`, and update the function signature to return `DispatchResult` so errors (e.g. `OutOfGas`) propagate to callers in `exec.rs`.

## Proof of Concept
No executable PoC demonstrating an actual weight-limit bypass was provided or verified; the report proposes (but does not include) a unit test in `substrate/frame/revive/src/metering/tests.rs` that would construct a `TransactionMeter` in `EthereumGas` mode, drive a `FrameMeter` through `record_contract_storage_changes` then `bank_pending_storage_changes`, and attempt a `charge_weight_token` call that succeeds against the stale (higher) `effective_weight_limit` but would fail against a correctly recomputed one — this test should be written and run to confirm the exploitability and magnitude of the drift before treating this as a confirmed, exploitable overrun rather than a code-path inconsistency.

	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}
