## Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then dispatches the handler using a `shop` value taken from an HTTP header that is never included in that HMAC computation. This breaks the intended binding `hmac_verified_bytes == identity_bytes_trusted`, letting anyone who can produce one valid `(body, hmac)` pair for the shared app secret redirect the payload to an arbitrary victim shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all read directly from HTTP headers, independent of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC strictly against `verifiable_query.to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` uses this same HMAC check as the sole authenticity gate, then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The documented integration pattern instructs host apps to wire raw headers straight into `Request.new` and treat `data.shop` from the resulting `WebhookMetadata` as the authenticated shop identity, with no additional binding step documented: [5](#0-4) [6](#0-5) 

**Broken identity binding (as an equality):**
`shop_field_covered_by_HMAC` should equal `shop_field_used_for_tenant_dispatch`. Here:
- Bytes verified by HMAC = `raw_body` only.
- Bytes used to select the tenant (`shop`) for the handler = `x-shopify-shop-domain` / `shopify-shop-domain` header, which is disjoint from the signed bytes.

Since every merchant installing a multi-tenant app shares the same `api_secret_key` used to sign *all* shops' webhooks (`Context.api_secret_key`, `Context.old_api_secret_key`), any single merchant of the app can locally capture one valid `(raw_body, hmac)` pair from a webhook legitimately delivered to their own shop (e.g., by installing the app on a free/dev store and triggering `orders/create`). They can then submit that identical `(raw_body, hmac)` directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (a victim's shop). `HmacValidator.validate` will still pass, since it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged app user (any merchant able to install the app, which is normally an unprivileged/self-service action for public apps) can make the host application process arbitrary body content attributed to a shop they do not control. Depending on how the host implements its `handle` callback (documented as typical usage: enqueuing jobs keyed by `data.shop`, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` per the doc example), this can be used to inject/spoof events, corrupt or mutate another tenant's stored data (orders, inventory, app-uninstalled state, subscription/billing state), or trigger app-level actions against a shop the attacker never installed on — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any multi-tenant app built on this gem's documented webhook flow, because:
1. Obtaining one valid `(body, hmac)` pair requires nothing more than installing the app on any store (including the attacker's own free development store) — no leaked secret or elevated privilege needed.
2. The webhook HTTP endpoint is, by design, public and unauthenticated aside from the HMAC header.
3. The gem provides no header-shop binding, and the documentation does not instruct developers to independently verify the `shop` header/claim against anything cryptographically tied to the payload.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material the HMAC is checked against, or otherwise cryptographically bind `request.shop` to the verified payload before it is handed to `WebhookMetadata`/handlers — e.g., verify the HMAC over `shop-domain header || raw_body` rather than `raw_body` alone, or require the host-configured expected shop set to be checked against a value that is itself derived from a value covered by the signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-owned-shop.myshopify.com` (a legitimate, self-service action requiring no special privilege).
2. Shopify delivers a real webhook (e.g. `orders/create`) to the app's public webhook URL with headers:
   - `x-shopify-shop-domain: attacker-owned-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC over raw_body computed with the app's shared api_secret_key>`
   - body: `{"id": 1, ...}`
3. Attacker records this exact `raw_body` and `x-shopify-hmac-sha256` value (trivial, since they own the shop generating it).
4. Attacker replays a new HTTP POST directly to the same public webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this header as `shop`; `Utils::HmacValidator.validate` re-computes the HMAC over `raw_body` only and it matches, so `Registry.process` calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though that shop never sent this webhook. ```markdown
If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

```markdown
To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
