### Title
Unchecked scaled-value growth can permanently freeze an entire lending market - (File: common/src/rates/scaling.rs)

### Summary
A market whose scaled borrow or supply totals grow beyond the `i128` result domain causes accrual to panic before the configured index ceiling is reached. Because every market mutation synchronizes interest before applying the operation, repayment, withdrawal, liquidation, bad-debt cleanup, recapitalization, flash loans, and keeper index updates all revert once this state is reached. The result is permanent freezing of all funds and debt administration for that market absent a privileged contract upgrade.

### Finding Description
Each accrual step first converts total scaled borrow and supply into RAY-denominated values through `scaled_to_original`, which performs `scaled.mul(env, index)` and requires the result to fit in `i128`. [1](#0-0) [2](#0-1)  The subsequent `update_borrow_index` ceiling only limits the index after this unscaled total has already been calculated. [3](#0-2) 

The mutating pool path calls `interest::global_sync` from `ops::market::accrue`, while all position legs call `ops::synced_market` before mutating state. [4](#0-3) [5](#0-4)  An unprivileged user can trigger the same pool accrual through `controller.update_indexes(caller, assets)`, which forwards the market list to `pool.update_indexes`. [6](#0-5) [7](#0-6) [8](#0-7) 

The repository’s long-horizon test demonstrates the failure boundary: a large 18-decimal market at high utilization eventually fails in `scaled_to_original`, while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`; subsequent withdrawal and repayment attempts both fail with `MathOverflow`. [9](#0-8) 

### Impact Explanation
All suppliers and borrowers in the affected `(hub_id, asset)` market are permanently unable to execute the pool paths needed to recover or resolve their positions. Withdrawals, repayments, liquidation debt payments, bad-debt socialization, revenue claims, flash loans, strategy debt creation, and recapitalization all depend on loading an interest-synced market, so a single arithmetic panic bricks the market rather than merely rejecting one malicious transaction. [5](#0-4) [10](#0-9) 

This satisfies permanent freezing of user funds and protocol insolvency-processing failure: collateral cannot leave, debt cannot be reduced, liquidators cannot repair unhealthy accounts, and governance cannot apply a safer rate model because `update_params` also accrues under the old model before replacing it. [11](#0-10) 

### Likelihood Explanation
Likelihood is limited by the large market exposure required and by the need for debt to remain outstanding while interest compounds into the overflow boundary. Nevertheless, no privileged action or external-service failure is needed: an ordinary account can supply collateral, borrow an allowed large position, and any signed keeper can later call `update_indexes` with the affected `HubAssetKey` to commit the state transition into the frozen condition. [12](#0-11) [6](#0-5) 

The scenario is more plausible for high-decimal assets, steep utilization curves, high utilization, and markets with permissive caps. The included test reaches the condition using only public lending flows and shows that the configured index ceiling does not prevent the intermediate unscaled-value overflow. [13](#0-12) 

### Recommendation
Do not require total debt or total supply to fit in `i128` merely to perform accrual. The accrual engine should use a wider intermediate representation for `scaled * index`, accrued debt, supplier rewards, and utilization, or enforce a market-level exposure invariant that proves `borrowed * MAX_BORROW_INDEX_RAY / RAY` and `supplied * MAX_SUPPLY_INDEX_RAY / RAY` can never exceed `i128::MAX`. A safe recovery path should also allow repayments, withdrawals, liquidation, and bad-debt cleanup when the projected index reaches the ceiling rather than panicking during pre-update valuation.

### Proof of Concept
1. On a high-decimal market with a steep rate curve and permissive caps, one user supplies sufficient collateral and then calls `controller.supply` and `controller.borrow` to create a very large, high-utilization borrow position.
2. Any signed caller invokes:
   ```text
   controller.update_indexes(caller, vec![HubAssetKey { hub_id, asset }])
   ```
3. Repeat accrual as ledger time advances. Each call passes through `markets::update_indexes`, `pool_update_indexes_call`, `pool.update_indexes`, `ops::market::accrue`, `global_sync`, and finally `accrue_step`.
4. When `borrowed.mul(borrow_index)` or `supplied.mul(supply_index)` no longer fits `i128`, `scaled_to_original` panics with `MathOverflow`; the index ceiling is never reached.
5. Subsequent calls to `controller.repay`, `controller.withdraw`, `controller.liquidate`, `controller.clean_bad_debt`, `controller.recapitalize`, and other accrual-first paths hit the same panic, leaving all funds in the market frozen.

The existing deterministic reproduction is `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which supplies a billion 18-decimal units, borrows 98%, advances accrual until `update_indexes` fails, and then confirms both withdrawal and repayment fail with `MATH_OVERFLOW`. [14](#0-13)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
