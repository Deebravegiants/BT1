### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook signature verification binds the HMAC only to the raw request body, not to the `shop-domain` or `topic` headers that `ShopifyAPI::Webhooks::Registry.process` uses to identify which tenant/topic a webhook belongs to. This breaks the identity binding: `hmac == HMAC(body)` while `shop` used downstream comes from an unauthenticated header, so `shop_acted_on != shop_covered_by_hmac`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `HmacValidator.validate_signature` computes `HMAC-SHA256(api_secret_key, to_signable_string)` and compares it to the `hmac` accessor, which reads the `hmac-sha256`/`x-shopify-hmac-sha256` header [5](#0-4) [6](#0-5) . The `shop`, `topic`, `api_version`, and `webhook_id` fields are all read directly from headers without any cryptographic binding to the body or to each other [7](#0-6) .

`Registry.process` uses exactly this unvalidated `shop` value to build the `WebhookMetadata` object handed to the app's registered handler [4](#0-3) , meaning the handler receives an attacker-controlled tenant identifier alongside an authentic body+HMAC pair.

Because Shopify computes the webhook HMAC purely from the body and the shared `api_secret_key` — independent of the shop — any entity able to install the app on a shop they control (an ordinary, unprivileged merchant/attacker) receives genuine `(body, hmac)` pairs from Shopify for their own shop's events. That attacker can replay the exact `body`+`hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` will still pass because it only checks the body against the HMAC [8](#0-7) , yet `Registry.process` will invoke the handler believing the event originated from the victim shop [4](#0-3) .

### Impact Explanation
This crosses a tenant boundary: an app that keys any behavior off `WebhookMetadata#shop` (e.g., updating per-shop state, triggering shop-scoped side effects, writing to a shop's records, or emitting shop-scoped audit/log entries) can be made to attribute attacker-controlled, authentically-signed data to a shop the attacker does not own. This matches the "Critical - cross-tenant access" impact category, since the identity binding the app relies on (`hmac` covers `shop`) does not actually exist in this gem.

### Likelihood Explanation
Exploitation only requires the attacker to install the vulnerable app on any shop they control (an unprivileged, self-service action for any Shopify merchant) and to be able to POST arbitrary headers/body to the app's public webhook endpoint — no access token, `client_secret`, or victim credentials are needed. The only skill required is capturing one legitimate webhook delivery from their own shop and replaying it with a modified `shop-domain` header.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable string that the HMAC is computed and verified over, or otherwise cryptographically bind them to the request (e.g., verify `shop` against a separately-authenticated channel/session rather than trusting the header verbatim). At minimum, document that `request.shop`/`request.topic` are NOT covered by HMAC verification so consuming apps do not treat them as trusted tenant identifiers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker performs a legitimate action that triggers a subscribed webhook (e.g., `orders/create`) and captures the raw POST: headers including `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, and the raw JSON body `B`.
3. Attacker replays this exact request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping body `B` and header `x-shopify-hmac-sha256: <H>` unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `to_signable_string` is still `B` [1](#0-0) .
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `<H>` — validation succeeds [9](#0-8) .
6. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` [10](#0-9) , causing the app to process attacker data under the victim shop's identity.
