This confirms end-to-end reachability of the claim. The gateway-side handler forwards the client-supplied `req` (via `ar.req`) unmodified to nodes through `fanOutToVaultNodes` -> `h.don.SendToNode(ctx, node.Address, &ar.req)`, and `HandleJSONRPCUserMessage` in `core/services/gateway/handlers/vault/handler.go` (L404-420) does no `req.Params` nil-check before that path — it only checks a cache and otherwise calls `h.newActiveRequest(req, callback)` then `h.handlePublicKeyGet(ctx, ar)`, which for a cache-miss forwards straight to `fanOutToVaultNodes`, sending `ar.req` (with `Params: nil` as the external client sent it) to every DON node. [1](#0-0) [2](#0-1) [3](#0-2) 

This is confirmed by the existing test `TestVaultHandler_PublicKeyGet`, which explicitly constructs a `MethodPublicKeyGet` request with `Params: nil` and passes it through `HandleJSONRPCUserMessage`/`handlePublicKeyGet` without any rejection. [4](#0-3) 

On the node side, `GatewayHandler.HandleGatewayMessage` dispatches `MethodPublicKeyGet` directly to `handlePublicKeyGet` bypassing `requestProcessor.ProcessRequest` (unlike Secrets* methods), and `handlePublicKeyGet` unconditionally dereferences `*req.Params`. [5](#0-4) [6](#0-5) 

Node-side message dispatch happens in an unrecovered goroutine: `gatewayConnector.readLoop` unmarshals the incoming JSON-RPC request and calls `handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)` synchronously with no `recover()`. [7](#0-6)  The codebase does have a general panic-recovery utility (`core/recovery/recover.go`), but it is not used to wrap this read loop's handler dispatch. [8](#0-7) 

This fully validates the claim's previously-unverified end-to-end reachability concern: the gateway does **not** reject or normalize a nil `params` for `PublicKeyGet` before relaying to nodes — it forwards the raw client request verbatim. Combined with the missing nil-check in `handlePublicKeyGet` and the lack of panic recovery in `readLoop`, an unauthenticated external client can crash a node process with a single malformed `vault_publicKeyGet` request with `params` omitted or `null`.

Audit Report

## Title
Unvalidated nil `req.Params` dereference in Vault gateway `PublicKeyGet` path causes node-crashing panic - (File: core/capabilities/vault/gw_handler.go)

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor.ProcessRequest`, and `handlePublicKeyGet` dereferences `*req.Params` with no nil check. An unauthenticated external client can send a `vault_publicKeyGet` JSON-RPC request with omitted/null `params` through the gateway, which forwards the request unmodified to every DON node, triggering a nil-pointer-dereference panic inside the un-recovered `gatewayConnector.readLoop` goroutine and crashing the node process.

## Finding Description
The gateway's public-facing handler (`core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage`) treats `MethodPublicKeyGet` as an unauthenticated method and, on cache miss, forwards the client's original request object (`ar.req`, including whatever `Params` the client supplied, potentially `nil`) verbatim to all DON member nodes via `fanOutToVaultNodes` → `h.don.SendToNode(ctx, node.Address, &ar.req)`. There is no validation anywhere in this path that rejects a request with `Params == nil`. [1](#0-0) [2](#0-1) [3](#0-2) 

On the node side, `gatewayConnector.readLoop` unmarshals the incoming JSON-RPC message and dispatches it synchronously to the registered handler with no `recover()`. [7](#0-6)  `GatewayHandler.HandleGatewayMessage` special-cases `MethodPublicKeyGet` to skip the `requestProcessor.ProcessRequest` authorization/validation pipeline that all `Secrets*` methods use (that pipeline explicitly checks `req.Params == nil` before proceeding). [5](#0-4) [9](#0-8)  `handlePublicKeyGet` then unconditionally executes `json.Unmarshal(*req.Params, r)`, dereferencing a nil `*json.RawMessage` when `Params` is nil. [6](#0-5)  This panics, and because `readLoop` has no `recover()`, the panic propagates and crashes the entire node process, even though the codebase has a reusable `recovery.WrapRecover`/`HandleFn` utility elsewhere that is not applied here. [10](#0-9) 

## Impact Explanation
This is a remote, pre-authentication denial-of-service: any external client able to reach the gateway's vault endpoint can crash Oracle/Vault DON node processes by submitting one crafted `vault_publicKeyGet` request with missing/null `params`, since `PublicKeyGet` is intentionally unauthenticated and is forwarded to nodes without params validation. This maps to node availability disruption via a gateway-relayed malformed message — a legitimate in-scope DoS/crash impact class.

## Likelihood Explanation
Very high likelihood/low effort: no credentials, allowlist membership, JWT, or workflow ownership are required to trigger `MethodPublicKeyGet`; the request is a single, trivially crafted JSON-RPC message forwarded verbatim by the gateway to every DON node member, and the existing test `TestVaultHandler_PublicKeyGet` confirms `Params: nil` requests are accepted and processed through this exact path today. [4](#0-3) 

## Recommendation
Add a `req.Params == nil` guard in `handlePublicKeyGet` (core/capabilities/vault/gw_handler.go) that returns a `UserMessageParseError` response instead of dereferencing a nil pointer, matching the pattern already used in `GatewayVaultRequestProcessor`. Additionally, wrap the per-message handler dispatch in `gatewayConnector.readLoop` (core/services/gateway/connector/connector.go) with `recovery.WrapRecover`/`HandleFn` so a panic in any single handler invocation cannot crash the whole node process. Consider similarly validating/normalizing `params` on the gateway side (`core/services/gateway/handlers/vault/handler.go`) before relaying `PublicKeyGet` requests to nodes.

## Proof of Concept
1. As an external, unauthenticated client, submit a JSON-RPC request to the gateway's vault user endpoint:
```json
{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}
```
with `"params"` omitted (or `null`).
2. The gateway's `handler.HandleJSONRPCUserMessage` treats this as unauthenticated, and (on a cache miss) `handlePublicKeyGet` → `fanOutToVaultNodes` forwards the request, including `Params: nil`, to every DON node via `don.SendToNode`.
3. On each node, `gatewayConnector.readLoop` decodes the message and calls `GatewayHandler.HandleGatewayMessage`, which routes `MethodPublicKeyGet` straight to `handlePublicKeyGet`.
4. `json.Unmarshal(*req.Params, r)` dereferences the nil `*json.RawMessage`, panicking inside the un-recovered `readLoop` goroutine and crashing the node process.
5. A Go unit test mirroring `TestVaultHandler_PublicKeyGet` (core/services/gateway/handlers/vault/handler_test.go, L1272-1317) but targeting `core/capabilities/vault/gw_handler.go`'s `HandleGatewayMessage`/`handlePublicKeyGet` with a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` reproduces the panic directly.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}

func WrapRecoverHandle(lggr logger.Logger, fn func(), onPanic func(recovered any)) {
	HandleFn(fn, func(recovered any) {
		logger.Sugared(lggr).Criticalw("Recovered goroutine panic", "panic", recovered)

		if onPanic != nil {
			onPanic(recovered)
		}
	})
}

	}()
