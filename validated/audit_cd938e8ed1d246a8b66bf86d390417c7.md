## Title
Webhook `shop` and `topic` identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream to route and attribute the webhook are taken from HTTP headers that are never included in the signed payload. This breaks the identity binding `hmac_signed_bytes == authenticated_shop_context`, mirroring the reported bug class where a value acted upon (the destination account/shop) is not covered by the same check that is supposed to guarantee integrity (the balance/HMAC check).

### Finding Description
`to_signable_string` — the value that `Utils::HmacValidator` signs/verifies against — returns only the raw body: [1](#0-0) 

But the `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived independently from headers, entirely outside the HMAC-covered bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body, then unconditionally trusts `request.shop` and `request.topic` (header-derived, unauthenticated) to dispatch the handler and populate `WebhookMetadata`: [3](#0-2) 

`Utils::HmacValidator.validate` simply confirms the *body* bytes were signed by `Context.api_secret_key`; it never asserts anything about which shop the signature was intended for, because the shop was never part of `to_signable_string`: [4](#0-3) 

Because a single app-wide `api_secret_key` is used for HMAC across **every** shop that has the app installed, and the header carrying the shop identity is unauthenticated, a request with a legitimately-signed body from Shop A can be replayed against the same public webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header rewritten to Shop B. The gem will report the HMAC as valid (it only checked the body) and will hand the handler a `WebhookMetadata` claiming the event came from Shop B, when the signature only ever attested to the body content, not to the shop.

This is the direct analog of the reported bug: just as `transferFrom` incremented/decremented a balance without the check binding source-must-differ-from/have-enough-for-destination, here the HMAC check binds only to `raw_body` without binding to `shop`/`topic`, letting an attacker present authenticated-looking bytes under an arbitrary shop identity.

### Impact Explanation
Any host application that uses `request.shop` from this gem to key persistence, authorization, or per-tenant business logic (a documented, expected usage pattern shown in `WebhookMetadata`) can be made to process a validly-HMAC'd payload under the wrong shop's identity. This is a cross-tenant identity-binding break: data or actions intended to be scoped to Shop A's webhook can be attributed to Shop B purely by header manipulation, without needing Shop B's credentials, access token, or `client_secret`.

### Likelihood Explanation
Exploitability requires only:
1. The attacker controls (or has installed the app on) any one shop able to trigger a webhook with attacker-influenced body content (e.g., `products/create`, `orders/create` content the attacker controls to some degree), giving them one genuinely-signed `(raw_body, hmac)` pair.
2. The attacker sends an HTTP request directly to the app's public webhook endpoint (which must be internet-reachable to receive Shopify webhooks) with the same body/HMAC but a rewritten `shop-domain` header.

No access token, `client_secret`, or `api_secret_key` disclosure is needed — the attacker only reuses a signature they were legitimately given for their own shop's event.

### Recommendation
Include `shop` (and ideally `topic`) in `to_signable_string`/the value used for signature verification is not possible since Shopify itself only signs the body — instead, the gem should not treat `request.shop` as authenticated. At minimum, document prominently that `request.shop`/`request.topic` are unauthenticated header values and must be cross-checked by the host app against a known/registered shop, or additionally verify that the `shop` header corresponds to a shop for which this webhook topic/registration was actually created before dispatching `WebhookMetadata`.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `{"id":1}` and header `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Attacker (who owns `shop-a`) captures this raw body + HMAC pair.
3. Attacker POSTs the same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks `raw_body` against the shared `api_secret_key` — validation succeeds.
5. `WebhookMetadata.new(shop: request.shop, ...)` reports `shop-b.myshopify.com` as the source shop to the handler, even though the signature never attested to that binding. [3](#0-2) [5](#0-4)
