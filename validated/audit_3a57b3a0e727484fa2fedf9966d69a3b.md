### Title
Overflow in `scaled_to_original` during accrual permanently freezes a high-value market before the borrow-index cap engages — ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
The bug class in CVE-2019-14875 is *a fallible operation whose failure is not anticipated, crashing the caller*. The analog here is accrual arithmetic: every state-changing verb on a market accrues interest first, and the accrual multiplies the scaled `borrowed`/`supplied` totals by their indexes via `Ray::mul`. The index cap `MAX_BORROW_INDEX_RAY` is checked on the *index*, but the *value* `scaled * index` overflows `i128` long before the index approaches the cap when the scaled position is large. An unprivileged whale can create exactly that precondition — huge supply, near-full borrow — and time does the rest, permanently bricking every entry point on that book.

### Finding Description
Accrual computes supplier rewards by unscaling the whole scaled book:

- `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` and `borrowed.mul(env, old_borrow_index)` [1](#0-0) , and `calculate_utilization` calls `scaled_to_original(borrowed, borrow_index)` on every accrual [2](#0-1) .
- `scaled_to_original` is `scaled.mul(env, index)` [3](#0-2) ; `Ray::mul` panics with `MathOverflow` when `scaled * index` exceeds `i128` range [4](#0-3) .
- The only safety bound is on the index itself: `update_borrow_index` clamps `new_index` at `MAX_BORROW_INDEX_RAY` *after* the multiply [5](#0-4) . With `scaled` close to `i128::MAX`, the product overflows at an index far below the cap, so the cap never protects the value computation.
- Since every verb accrues first, once the product overflows, `repay`, `withdraw`, `borrow`, `liquidate`, `update_indexes`, and `recapitalize` all revert — no escape path accrues with a different (smaller) operand.

This is demonstrated by the repo's own harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which supplies ~10²⁸ units of an 18-decimal asset, borrows 98%, advances time, and observes `update_indexes`, `withdraw`, and `repay` all failing with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY` — and explicitly notes the documented bound in `docs/reference/formulas.md` is wrong [6](#0-5) . So this is not a documented/accepted ADR choice; the documented guarantee is incorrect.

### Impact Explanation
Permanent freezing of funds. All suppliers' deposits in the affected (hub, token) book become unwithdrawable forever, borrowers cannot repay (locking their collateral across the whole account, since health/withdrawal reads accrue too), and liquidations cannot proceed — the book is insolvent-in-practice even if solvent on paper. No privileged recovery exists because the overflow is inside accrual itself.

### Likelihood Explanation
Requires a whale-scale supply in a high-decimal asset and sustained high utilization so the borrow index grows ~170× — capital-intensive and slow, but entirely unprivileged (`supply` + `borrow` + time), no governance action, oracle manipulation, or leaked key needed. Once triggered there is no remediation path. Consistent with a Medium severity analog.

### Recommendation
Bound the *value* product, not just the index: either cap `borrowed`/`supplied` scaled totals relative to `MAX_BORROW_INDEX_RAY` (enforce `scaled * MAX_INDEX ≤ i128::MAX` at `supply`/`borrow` time via `calculate_scaled_cap`-style checks), or make `scaled_to_original`/`calculate_supplier_rewards` saturate at `i128::MAX` instead of panicking so accrual remains callable and the index cap can engage. Also correct the bound stated in `docs/reference/formulas.md`.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`: with `BIG18` (18 decimals), supply `BILLION * 1e18`, borrow 98%, then `advance_time` yearly — `try_update_indexes_for(["BIG18"])` fails with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequently `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both fail with `MATH_OVERFLOW`, confirming permanent market freeze.

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
