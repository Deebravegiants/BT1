### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted for tenant routing while excluded from the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the caller-supplied `shop-domain`, `topic`, `webhook-id` and `api-version` headers to the app's handler as trusted metadata. None of these header values are covered by the HMAC, so the "authenticated" identity of the webhook (which tenant/shop it came from) is not actually bound to the signature that proves authenticity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Webhooks::Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from unauthenticated HTTP headers with no cryptographic tie to the body: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` — which checks `HMAC(secret, raw_body)` — and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop header == shop that produced the HMAC'd body`. Because the signature only covers bytes verified (the body) and not the shop/topic/webhook-id bytes parsed from headers, this equality is never enforced by the library. `HmacValidator.validate` only proves "some request body was signed with this app's shared secret" — it does not prove which shop the body came from: [5](#0-4) 

An app's client secret (`api_secret_key`) is shared across every shop that installs the app — it is not a per-tenant secret. Any ordinary merchant who installs the app is an "unprivileged internet user" relative to other tenants of the same app, yet Shopify will legitimately sign webhook payloads on their behalf using that shared secret whenever their store triggers a subscribed topic (e.g. `products/update`, containing attacker-influenceable JSON such as a product title/description). Because the header carrying the shop identity is excluded from the signature, that attacker can capture a validly-HMAC'd `(body, hmac)` pair generated from their own store's webhook traffic and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to name a victim shop. `Registry.process` will accept it: the HMAC check passes (it only re-hashes the body), and the forged `shop` value is handed to the host application's handler as if Shopify itself had asserted it came from that shop.

### Impact Explanation
Host applications built on this gem (the documented pattern, see `docs/usage/webhooks.md`) use `WebhookMetadata#shop` to look up the tenant record/session associated with a shop and act on the webhook body in that tenant's context (e.g., updating stored product/customer/order data, or in the worst case reacting to `app/uninstalled`/`shop/update` to revoke or mutate tenant state). Since the shop identity is unauthenticated relative to the signed body, an attacker controlling one tenant (Shop A) can inject data that the host application attributes to a different tenant (Shop B), achieving cross-tenant data injection — one of the explicitly in-scope Critical impacts ("cross-tenant access").

### Likelihood Explanation
Exploitation requires no leaked secrets, no privileged account, and no host cooperation beyond the gem's documented `Registry.process` API: an attacker only needs (a) their own legitimate installation of the target app on a shop they control, so Shopify signs webhook bodies for them with the shared `api_secret_key`, and (b) the ability to send an arbitrary HTTP POST with attacker-chosen headers to the app's public webhook endpoint (trivially replaying a captured Shopify webhook with edited headers). This is realistic and low-effort for any merchant/tenant of a multi-tenant app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable material verified against the HMAC, or independently authenticate the shop header — for example, cross-check `request.shop` against a per-shop-registered webhook secret/callback association, or require the host application to validate that the shop identified by the header actually has an active, previously-established session before trusting the payload's tenant attribution. At minimum, `Registry.process` should not silently pass an unauthenticated `shop` value through as trusted metadata without documenting that callers must independently verify shop identity out-of-band before using it for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (a normal, unprivileged install — no special access needed).
2. Attacker performs an action that triggers a subscribed webhook topic with attacker-controlled content, e.g. updates a product title to `"legit-payload"`, causing Shopify to POST:
   - Body: `{"id":123,"title":"legit-payload", ...}`
   - Headers: `X-Shopify-Hmac-Sha256: <valid HMAC of body>`, `X-Shopify-Topic: products/update`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   The attacker captures this exact `(body, hmac)` pair from their own endpoint logs.
3. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the same app's webhook endpoint, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` — the unchanged raw body — and it matches, since the body byte-for-byte is unmodified.
5. `process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` header and invokes the app's handler, which acts as though `victim-shop.myshopify.com` produced this webhook — a cross-tenant spoof that the gem never detects.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
