### Title
Webhook `shop` (and topic/version/id) header not bound by HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers and are never part of the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identity forwarded to the host application's handler via `WebhookMetadata`.

### Finding Description
The intended binding, mirroring the report's pattern, is:
`HMAC(secret, signed_bytes) == received_hmac` should imply `signed_bytes` (and therefore every field the handler relies on for tenant identity, including `shop`) is authentic.

In this gem, `to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `shop` is read from a separate, unsigned header: [4](#0-3) 

`Registry.process` validates the HMAC against `raw_body` only, then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata`, which is handed to the app's webhook handler as the source of tenant identity: [5](#0-4) 

Because the `shop` header is not part of the signed bytes, any request bearing a `raw_body` + `hmac` pair that is valid for the app's shared `api_secret_key` will pass `Utils::HmacValidator.validate` regardless of what `shop` header accompanies it. An attacker who can obtain (or predict) one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — e.g., a legitimate webhook payload for their own shop, which any merchant installing the app naturally receives — can resubmit the exact same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a different, target shop. `Registry.process` will still call `Utils::HmacValidator.validate` successfully (it only checks the body), and will then invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen value.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to route webhook side effects (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`, as shown in the gem's own documentation) can be tricked into applying another merchant's data under the wrong shop, or applying a merchant's own crafted payload under a victim shop's identity — a cross-tenant data/action confusion. This matches the "Critical – cross-tenant access" impact category, since the tenant boundary (`shop`) is not cryptographically bound to the verified payload.

### Likelihood Explanation
Exploitation requires only that the attacker (an ordinary merchant who has installed the app, hence an "unprivileged internet user" relative to other tenants) has captured a legitimate `(raw_body, hmac)` pair for their own shop — something they can trivially do by installing the app and intercepting/replaying their own webhook traffic to the app's public endpoint. No access to `api_secret_key` is needed since the HMAC value is reused verbatim; only the accompanying `shop` header is swapped. This is a realistic, low-effort replay requiring no secret material.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) to the signature: either include the shop domain in the signable string, or independently verify that the shop header matches a value the app already trusts (e.g., an existing session for that shop) before acting on it. At minimum, document explicitly that `WebhookMetadata.shop` is derived from an unauthenticated header and must not be treated as cryptographically verified, and provide a way for the signature to cover the header set—consistent with the recommendation in the referenced report to not silently trust fields the signature doesn't cover.

### Proof of Concept
1. App merchant "attacker-shop.myshopify.com" installs the app and receives a real webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid HMAC over body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same raw body and HMAC value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC — see [3](#0-2)  and [6](#0-5) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: {"id":1} ...)` — see [7](#0-6) .
5. The host application (following the gem's own documented usage pattern) performs actions "for" `victim-shop.myshopify.com` using attacker-controlled data, a cross-tenant confusion.
