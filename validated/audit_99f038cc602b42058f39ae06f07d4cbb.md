The strongest match to the reported bug class is in `ShopifyAPI::Webhooks::Request`/`Registry`: the HMAC only authenticates the raw JSON body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the app's handler trusts and acts on come from unauthenticated HTTP headers.### Title
Webhook HMAC only covers the request body, allowing shop/topic header spoofing that bypasses cross-tenant isolation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the app's registered handler subsequently trusts and acts on are read from unauthenticated HTTP headers that are not covered by that signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it against the `hmac` value pulled from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands the *header-derived* `shop`/`topic` to the app's handler as trusted identity/routing data: [4](#0-3) 

The equality this code is implicitly relying on is: `HMAC-valid body` ⇒ `(shop, topic, webhook_id, api_version) are authentic for that body`. That equality does not hold, because the HMAC signable string is `@raw_body` alone — the headers are outside the MAC. This is exactly the bug class in the report: an authenticator (HMAC/redis-command bytes) is computed over one set of bytes/fields while a different, unauthenticated set of fields is trusted downstream.

Concretely: any entity that has legitimately received one valid `(raw_body, hmac)` pair from Shopify for its own shop/topic (e.g., a merchant who installed the app and can observe webhooks delivered to their own endpoint, or any party that can otherwise obtain one valid body+HMAC pair for the configured `api_secret_key`) can replay that exact body and HMAC to the app's webhook endpoint while substituting arbitrary `shopify-shop-domain` and `shopify-topic` headers. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` dispatches to the handler for the *attacker-chosen* topic/shop combination, e.g. claiming the payload is a `shop/redact` or `app/uninstalled` event for a victim shop, or attributing an arbitrary body to a different shop than the one that actually produced it.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: a handler written against this gem's documented contract (`WebhookMetadata`'s `shop`/`topic` are attacker-forgeable even though `Utils::HmacValidator.validate(request)` returned `true`) can be made to act on behalf of, or against, a shop that never actually sent that payload — a cross-tenant identity confusion. Depending on what the app's handler does with `topic`/`shop` (data deletion for GDPR mandatory topics, cache invalidation, entitlement changes, order processing, etc.), this can lead to cross-tenant data exposure or corruption while the gem itself reports the request as "HMAC valid."

### Likelihood Explanation
Exploitation requires possession of at least one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — which any shop that has the app installed and receives real webhooks already has, without needing the secret itself, TLS interception, or privileged access. This is a moderate-likelihood, protocol-design issue reachable by any party that can receive one legitimate webhook delivery and then forge headers on a replayed POST to the same endpoint.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC computation, or otherwise cryptographically bind them to the body (e.g., concatenate them with the body before hashing, consistent with how Shopify signs the payload). At minimum, document/enforce that `request.shop`/`request.topic` must not be trusted independently of the raw body content, and consider deriving shop/topic from the JSON body itself where Shopify includes it, rather than solely from headers.

### Proof of Concept
1. Attacker's own shop (`attacker.myshopify.com`) has the app installed; Shopify delivers a legitimate webhook to the app's endpoint:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B for api_secret_key>
x-shopify-shop-domain: attacker.myshopify.com
x-shopify-webhook-id: w1
x-shopify-api-version: 2024-01
Body: B
```
2. Attacker captures `(B, valid HMAC)` and replays it against the same endpoint with forged headers:
```
POST /webhooks
x-shopify-topic: shop/redact
x-shopify-hmac-sha256: <same valid HMAC of body B>
x-shopify-shop-domain: victim.myshopify.com
Body: B   (unchanged)
```
3. `ShopifyAPI::Webhooks::Request.new` parses these headers verbatim (`lib/shopify_api/webhooks/request.rb:15-33`), and `Utils::HmacValidator.validate` recomputes the HMAC over `B` only and finds it valid (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) treats the request as an authentic `shop/redact` event for `victim.myshopify.com` and invokes the registered handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, even though the actual signed content came from a different shop and topic.
