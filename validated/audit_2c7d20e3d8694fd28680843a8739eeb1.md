## Title
`CallDispatcher.dispatch()` has no access control, letting any address steal stranded tokens/ETH left on the shared dispatcher by prior HFT bridge or IntentGateway calldata executions - (File: `evm/src/utils/CallDispatcher.sol`)

## Summary
`CallDispatcher` is a single, shared, unauthenticated contract used by both `HyperFungibleToken`/`WrappedHyperFungibleToken` and `IntentGatewayV2` to execute attacker/user-supplied `Call[]` batches (approve+swap, etc.) with funds that are temporarily routed to it. Its `dispatch()` entrypoint has **no caller restriction whatsoever** [1](#0-0) . Because the sweeping logic in both callers only recovers the tokens that are explicitly declared as `inputs`/`output.assets` (or the bridged token), any intermediate/hop token or leftover native ETH that is not enumerated in that list is left stranded on the dispatcher after the transaction completes. Since `dispatch()` is public and unauthenticated, any unprivileged address can subsequently call it directly with a self-crafted `Call[]` (e.g. a plain `transfer(attacker, balance)`) to sweep away that stranded value — the same "attacker fully controls the swap/execution calldata used against funds transiting a shared contract" root cause as the referenced Particle `liquidatePosition()` finding, generalized from a liquidator-controlled swap payload to an unauthenticated `dispatch()` call.

## Finding Description
`CallDispatcher.dispatch(bytes memory encoded)` decodes an arbitrary `Call[]` and executes each call as itself, with no `onlyOwner`/`onlyGateway`/`onlyHost` guard: [1](#0-0) . It also has an unrestricted `receive()` that accepts ETH from anyone [2](#0-1) .

Both integrations rely on this shared, address-fixed dispatcher and route user-defined calldata through it:
- `IntentGatewayV2`/`IntentsBase._execute()` dispatches the order's `output.call` (`PaymentInfo.call`, set by the order's *user* at placement time) and then sweeps back only the balances of `order.output.assets[i].token` [3](#0-2) . Any intermediate token used inside the swap path (e.g. WETH when the declared output asset is USDC) or excess native ETH forwarded via `Call.value` that a router refunds to the dispatcher is never included in this sweep loop and is left on the dispatcher.
- The predispatch path likewise only sweeps `order.inputs[i].token` balances back to the gateway [4](#0-3) ; hop tokens not in `inputs` are stranded the same way.
- `HyperFungibleToken.onAccept()`/`WrappedHyperFungibleToken` mint/unlock to the recipient (optionally the `CallDispatcher` address itself, per the documented pattern) and then `dispatch()` the sender-supplied `data` with **no sweep at all** afterward [5](#0-4) . Any residual bridged tokens, approvals, or swap remainders are simply left on the dispatcher.

Because `CallDispatcher` is deployed once and shared across every `HyperFungibleToken`/`WrappedHyperFungibleToken` instance and `IntentGatewayV2`, any dust, unswept hop-token balance, or stray ETH left behind by one user's legitimate cross-chain transfer or intent fill becomes a pool of value sitting at a **public, unauthenticated** address. Since `dispatch()` takes attacker-controlled `Call[]` with no origin check, any unprivileged address can call it directly (bypassing `IntentGatewayV2`/`HyperFungibleToken` entirely) with a call such as `{to: strandedToken, data: transfer(attacker, balance)}` or `{to: attacker, value: strandedEthBalance, data: ""}` to drain it.

## Impact Explanation
This is a direct theft-of-funds vector: value that legitimately belongs to bridge users or intent-order participants (hop-token remainders, router refunds, native ETH dust) can be permanently extracted by any third party who simply calls the public `dispatch()` function on the shared `CallDispatcher`. The docs even acknowledge the dispatcher "holds tokens temporarily" and recommend exact (non-infinite) approvals — implicitly acknowledging balances can sit there — but provide no protection against a completely unrelated address invoking `dispatch()` to sweep whatever happens to be present. This qualifies as concrete theft of funds reachable from a single unprivileged transaction, matching the required High/Critical bar.

## Likelihood Explanation
Likelihood is meaningfully high: predispatch/postdispatch calldata that swaps through an intermediate token (a common, documented use case — the docs' own examples use WETH↔USDC/DAI hops and native-ETH forwarding through the dispatcher) will routinely leave dust because the sweep loops are scoped strictly to `order.inputs`/`order.output.assets`, not to "every token the executed calls touched." `HyperFungibleToken`'s calldata-execution path has no sweep logic at all, so any use of that documented feature leaves the full swap-path remainder exposed. No special privileges, timing, or victim cooperation are required to exploit the exposure once dust exists — a bot can simply monitor the dispatcher's token/ETH balances and call `dispatch()` opportunistically.

## Recommendation
- Restrict `CallDispatcher.dispatch()` to only be callable by an allow-listed set of caller contracts (the registered `IntentGatewayV2` and HFT instances), or make the dispatcher per-caller/ephemeral (e.g. deploy a fresh minimal-proxy dispatcher per call) so it can never hold cross-call residual balances reachable by unrelated callers.
- In `IntentsBase._execute()` and the predispatch sweep, sweep the dispatcher's *entire* balance of every token touched by the executed `Call[]` (not just the declared input/output assets), plus any native ETH balance, back to the gateway before returning.
- Add an explicit sweep step to `HyperFungibleToken`/`WrappedHyperFungibleToken`'s `onAccept()` calldata-execution branch, mirroring the intent gateway's dust collection.

## Proof of Concept
1. A user places a cross-chain/same-chain order (or bridges tokens) whose `output.call`/`data` swaps through an intermediate token, e.g. `USDC -> WETH -> DAI`, with `order.output.assets` only declaring `DAI` (or bridges USDC with calldata that leaves WETH dust on the dispatcher).
2. The fill/`onAccept` executes normally: `CallDispatcher.dispatch()` performs the swap, `DAI` is correctly delivered/swept, but the intermediate `WETH` balance (or ETH refund) remains on the `CallDispatcher` contract because it is not part of the declared `output.assets`/`inputs` sweep set.
3. Any unrelated address (attacker) calls `CallDispatcher.dispatch(abi.encode([Call({to: WETH, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedBalance)})]))` directly — no authentication is required by `dispatch()` [1](#0-0) .
4. The stranded `WETH` (or ETH via a `{to: attacker, value: balance, data:""}` call) is transferred to the attacker, permanently removing value that should have remained recoverable by the protocol/user.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
