### Title
Reentrant escrow drain in `IntentGatewayV2.withdraw` (Tron variant) — escrow debit occurs after external `.call` to attacker-controlled beneficiary - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements its own `withdraw` routine for settling escrow (`RedeemEscrow`/`RefundEscrow`) that violates checks-effects-interactions in the same way as the original `Buyout.start`/`_sendEthOrWeth` bug: it sends value to a caller-controlled `beneficiary` via a low-level `.call` *before* updating the accounting that guards against reuse of that same escrow slot, and the whole contract has no `ReentrancyGuard`/`nonReentrant` protection anywhere.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2.sol` is: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
    }
    ...
}
```

The escrow balance guard `_orders[body.commitment][token]` is only checked for `== 0` (not `>= amount`) and is decremented *after* the native/ERC20 `.call` executes. This is the exact structural flaw the external report describes for `Buyout._sendEthOrWeth`/`start`: the state that is supposed to be mutated to prevent re-use of the funds is updated only after control has already been handed to an untrusted address.

Compare against the "main" EVM `IntentGatewayV2.sol`, where this exact bug class was found and fixed by moving `_filled[commitment] = msg.sender` to the top of `_fillSameChain`/`_fillCrossChain` *before* any external transfer, and by adding `nonReentrant` to `fillOrder`: [2](#0-1) 

The regression tests document that this was previously exploitable and confirm the CEI ordering is what blocks it: [3](#0-2) 

A grep across the whole `.sol` codebase shows `nonReentrant`/`ReentrancyGuard` usage exists only in `evm/src/apps/IntentGatewayV2.sol` — the Tron contract, its `withdraw()` and its `_orders` bookkeeping have no such protection at all, and the debit-after-call ordering was never fixed for this path.

### Impact Explanation
`withdraw()` is reachable from `onAccept` for `RequestKind.RedeemEscrow`/`RefundEscrow` and from `onGetResponse` after a cancel/query flow: [4](#0-3) [5](#0-4) 

`beneficiary` is derived from `body.beneficiary`, which mirrors `order.user`/`order.output.beneficiary` — an address fully controlled by whoever placed or is redeeming the order (an unprivileged solver/user can be the beneficiary of their own escrow). If `body.tokens` names the same token more than once (or a solver/relayer can trigger a second delivery attempt for the same commitment before the decrement lands), the attacker's beneficiary contract can, from its `receive()`/token `transfer` callback hook, re-enter into any other externally reachable path in the gateway that reads `_orders[body.commitment][token]` while the pre-decrement value is still stored, extracting more value than was actually escrowed for that commitment (fund theft from the gateway's pooled token/ETH balance), or corrupting escrow accounting so `_orders` underflows/reverts permanently, effectively bricking redemption for that order and locking any counterpart-chain funds tied to it (permanent freezing), mirroring the "perpetual, un-endable state" outcome in the original report.

### Likelihood Explanation
This is High-likelihood if the Tron intent gateway is deployed in production for cross-chain intents: the beneficiary address is always attacker-choosable (it is the user's own address in the honest flow), and reaching `withdraw()` only requires a normal, permissionless `RedeemEscrow`/`RefundEscrow` message delivery — no special privileges, no governance action, and no malicious relayer/collator assumption is required, satisfying the "unprivileged" reachability bar. The only fix present anywhere in the repo for this bug class (`nonReentrant` + CEI reordering) was applied solely to `evm/src/apps/IntentGatewayV2.sol`, confirming the maintainers recognize the class of bug but the Tron fork was not brought in line.

### Recommendation
Apply the same fix used in the main EVM `IntentGatewayV2.sol`:
1. Decrement `_orders[body.commitment][token]` (and any other escrow-accounting state) *before* making the external `.call`/token transfer, following checks-effects-interactions.
2. Add `ReentrancyGuard`/`nonReentrant` to `withdraw()`'s external entry points (`onAccept`, `onGetResponse`) in the Tron contract, matching the guard on `fillOrder` in `evm/src/apps/IntentGatewayV2.sol`.
3. Change the guard from `_orders[...][token] == 0` to an explicit `amount > escrowed` check to prevent any accounting underflow/double-spend even without reentrancy.

### Proof of Concept
Exact reachability of a double-spend via reentrancy (i.e., which second entry point a malicious `beneficiary` contract's callback would call to read the stale `_orders[commitment][token]` value) could not be fully confirmed with the available index — this requires tracing the Tron `IsmpHost`'s message-delivery re-entrancy surface and confirming whether `body.tokens` can contain duplicate token entries or whether a second `onAccept`/`onGetResponse` call for the same commitment can be triggered before the first call returns. A Devin session with full repo/build access would be needed to write a Foundry PoC (deploy the Tron `IntentGatewayV2`, a malicious beneficiary contract implementing `receive()`/`onERC20Received`-style reentry, and confirm whether the escrow decrement can be bypassed) and to verify whether the underlying Tron `IsmpHost` blocks nested/duplicate message delivery within a single external call.

            }
