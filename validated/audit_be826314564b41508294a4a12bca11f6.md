### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body as the value verified by the HMAC, while the `shop` (i.e., `shop-domain`) header used to attribute the webhook to a specific merchant is read separately and never included in the signed material. This breaks the identity binding `shop-domain header == shop covered by HMAC`, allowing an attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own shop) to relay the identical body to the app's webhook endpoint while substituting an arbitrary `shop-domain` value, and have it pass HMAC validation as if it originated from a different, victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

but the signable string used by `Utils::HmacValidator` only consists of the raw request body: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string and, on success, unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the host application's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [4](#0-3) 

Because `to_signable_string` excludes the shop domain, the identity binding "shop the event is attributed to" ↔ "bytes covered by the HMAC" does not hold. The shared secret (`Context.api_secret_key`) used to compute Shopify webhook HMACs is the app's single secret, not a per-shop secret — so a body that is genuinely signed for shop A (an attacker's own store, on which the attacker can freely install the app and receive real webhooks) is a valid HMAC for the exact same body no matter which `shop-domain` header accompanies it. An attacker can therefore capture a legitimately-signed webhook payload delivered to their own endpoint for their own shop, then POST that identical body to the target app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (keeping topic/hmac headers as originally received, or reusing any topic supported by the target). `Registry.process` will validate the HMAC (body unchanged, signature unchanged) and forward the forged `shop` field to the host application's webhook handler, letting the attacker inject a webhook "from" a shop they do not control.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged attacker (any developer who can install the app on a shop they control) can make the gem hand the host application data falsely attributed to another merchant. Any host-application logic that keys writes, redactions, credential lookups, or business actions off `WebhookMetadata#shop` can be tricked into acting on/against a shop the attacker does not own, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires operating (or trialing) the app on one shop to legitimately receive a correctly-signed webhook body, then replaying it with a modified `shop-domain` header to the same public webhook endpoint. No access token, `client_secret`, or privileged account is required — this is fully reachable by an ordinary internet user with a Shopify development store.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed material verified against the HMAC, or otherwise independently authenticate the `shop` claim (e.g., verify the `x-shopify-hmac-sha256` per Shopify's documented scheme, but additionally require that the resolved shop match a shop-specific expectation such as an active session/installation record) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` (valid because it's HMAC(`B`, api_secret_key)).
2. Send a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H`, and `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged shop header; `Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only checks `B` against `H`, per [2](#0-1) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, per [5](#0-4) , despite the event never originating from the victim.
