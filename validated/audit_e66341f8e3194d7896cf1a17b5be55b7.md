### Title
Unbounded exact-out fee quote lets a single solver drain a user's withdrawal via `getFeeQuote` - (File: packages/intents-sdk/src/lib/estimate-fee.ts)

### Summary
`getFeeQuote`'s primary exact-out branch passes whatever `amount_in` a solver returns straight into `feeEstimation.amount`/`quote.amount_in` with no upper-bound sanity check, unlike the exact-in fallback branch which enforces a 1.2x/1.5x ratio check. Since `solverRelay.getQuote`'s `matchesRequest` only validates the fixed side (`amount_out === exact_amount_out` for exact-out requests), a solver is free to report an arbitrarily large `amount_in` and have it accepted as the winning quote whenever it is the only (or cheapest-looking, per its own inflated number relative to competitors that fail to quote) valid responder.

### Finding Description
The broken equality: `withdrawalParams.amount == feeEstimation.amount + actualAmountReceived` should hold with `feeEstimation.amount` bounded by real relayer/storage costs, but nothing enforces that bound in the exact-out path.

- `getFeeQuote` (packages/intents-sdk/src/lib/estimate-fee.ts:63-80) calls `solverRelay.getQuote` with `exact_amount_out: feeAmount.toString()` and returns whatever quote comes back, with **no post-hoc check on `amount_in`**.
- `matchesRequest` (packages/internal-utils/src/solverRelay/getQuote.ts:119-139) for the exact-out case only checks `BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out)`; the `amount_in` side is explicitly documented as "what the solver competes on" and is not validated.
- `sortQuotes` (packages/internal-utils/src/solverRelay/getQuote.ts:96-113) picks the quote with the smallest `amount_in` among *valid* quotes — but if a malicious solver's inflated quote is the only valid quote returned (e.g., other solvers don't quote this pair, or all other solvers are colluding/absent), it wins by default since it is compared against nothing.
- The exact-in QuoteError-fallback branch (lines 139-159) has an explicit 1.2x/1.5x ratio sanity check and a `< feeAmount` check, but this only executes if the exact-out request throws `QuoteError` (i.e., zero valid quotes returned) — it never runs for the primary exact-out success path.
- The returned `quote.amount_in` is used directly as the debited amount from the user. In `HotBridge.createWithdrawalIntents` (packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts:208-219), `args.feeEstimation.quote.amount_in` is placed into the `token_diff` intent as `-${quote.amount_in}` — a literal debit from the user's balance for the asset being withdrawn. `OmniBridge.estimateWithdrawalFee` similarly does `amount += BigInt(quote.amount_in)` (packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:622-631).
- The only guard against this is `FeeExceedsAmountError`, which fires when `feeEstimation.amount >= withdrawalParams.amount` (i.e., fee ≥ full withdrawal amount) — it does not constrain the fee to any fraction of real cost, so a solver can set `amount_in = withdrawalParams.amount - 1` and stay just under this guard while capturing nearly the entire withdrawal.

### Impact Explanation
A permissionless solver answering the exact-out quote can cause the user to sign a `token_diff` intent (via `HotBridge`) or an inflated fee amount (via `OmniBridge`/`DirectBridge`/`AuroraEngineBridge`, all of which call `getFeeQuote` first) debiting up to `withdrawalParams.amount - 1` of the withdrawn asset to the solver, in exchange for the fixed, tiny `feeAmount` of the fee asset. This is repeatable on every withdrawal for the affected asset/route as long as the attacker can be the (sole or best-ranked) responder to that particular quote request. It matches "Critical — a fee error draining a material share of the amount, against the withdrawing user."

### Likelihood Explanation
Requires the malicious solver to actually win the quote comparison in `sortQuotes`, which for exact-out favors the *smallest* `amount_in`, so a naively "arbitrarily large" `amount_in` would normally lose against any honestly-priced competing quote. The attack is realistic mainly for illiquid asset pairs/chains where few or no other solvers respond (so the attacker's inflated quote is the sole valid one and wins by default), or in scenarios where the attacker can suppress/outrace competing quotes. It does not require compromising the relayer itself — only submitting an ordinary quote as one of many permissionless solvers — placing it within the stated attacker model.

### Recommendation
Add a sanity/ratio bound on `amount_in` in the exact-out success branch of `getFeeQuote`, analogous to the 1.2x/1.5x check already present in the fallback branch (e.g., compare `quote.amount_in` against an independent price-oracle-derived expected cost and reject/re-quote if it exceeds a small multiple, such as 1.5x).

### Proof of Concept
```ts
// vitest, mocking only the HTTP quote endpoint used by solverRelay.getQuote
it("accepts an oversized amount_in from a single solver on exact-out quotes", async () => {
  using solverRelayMock = await useMockedSolverRelay();
  const { IntentsSDK } = await import("./sdk");
  const sdk = new IntentsSDK({ referral: "", intentSigner });

  const feeAmount = 1000n;               // real relayer fee, in fee asset
  const withdrawalAmount = 1_000_000n;   // user's withdrawal amount, in token asset

  solverRelayMock.getQuote.mockResolvedValueOnce({
    amount_in: (withdrawalAmount - 1n).toString(), // attacker-controlled, huge
    amount_out: feeAmount.toString(),               // matches exact_amount_out -> passes matchesRequest
    defuse_asset_identifier_in: "nep141:token.near",
    defuse_asset_identifier_out: "nep141:wrap.near",
    expiration_time: new Date(Date.now() + 60_000).toISOString(),
    quote_hash: "malicious-quote",
  });

  const feeEstimation = await sdk.estimateWithdrawalFee({
    withdrawalParams: {
      assetId: "nep141:token.near",
      amount: withdrawalAmount,
      destinationAddress: "0x...",
      feeInclusive: true,
    },
  });

  // LHS: attacker-controlled fee, HS: real relayer cost (feeAmount, or a small multiple)
  expect(feeEstimation.amount).toBe(withdrawalAmount - 1n); // fails FeeExceedsAmountError only if >= amount
  expect(feeEstimation.amount).toBeGreaterThan(feeAmount * 10n); // no bound relative to real cost enforced
});
```
This demonstrates `feeEstimation.amount` can be set to near the entire `withdrawalParams.amount` by a single solver's exact-out quote, with no ratio check applied, before the intent is even built.
