I've confirmed the root cause. Let me verify the final key detail — that `topic`, `shop-domain`, `api-version`, and `webhook-id` headers are trusted directly from the request without any cryptographic binding to the HMAC signature, which only covers `@raw_body`.### Title
Webhook shop-domain header is trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC that is computed over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from unauthenticated HTTP headers to build the `WebhookMetadata` handed to the app's handler. The shop identity that a host application binds the payload to is never covered by the cryptographic proof, breaking the equality `shop verified by HMAC == shop attributed to the payload`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (i.e., the body) against the HMAC, using `Context.api_secret_key` — a secret shared across **every shop** that installs the app: [3](#0-2) 

`Registry.process` validates only this body HMAC, then constructs `WebhookMetadata` directly from `request.shop`/`request.topic`/etc. and dispatches it to the app's handler as if the shop header were authenticated: [4](#0-3) 

Because Shopify signs webhooks with the app's single `client_secret` (not a per-shop secret), any merchant who installs the app can generate a body+HMAC pair that is valid for the app as a whole — the HMAC only proves "this body was signed with the app's secret," never "this body came tagged as shop X." An attacker who controls one installed shop can capture a legitimate `(raw_body, hmac)` pair from their own store's webhook deliveries and replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the untouched body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` carrying attacker-chosen body content.

This exactly matches the report's bug class: "a field acted on but not covered by the HMAC" — here the `shop` (tenant) field is acted upon (used to attribute/process the webhook data) but is not part of what the HMAC actually authenticates.

### Impact Explanation
If a host application (as documented/intended, e.g. per `docs/usage/webhooks.md` and `WebhookMetadata#shop`) uses `data.shop` from the handler callback to decide which merchant's records to update/create/delete, an attacker can inject spoofed webhook events under an arbitrary victim shop's identity without ever possessing that shop's session or access token — this is a cross-tenant integrity/confusion issue satisfying the Critical "cross-tenant access" criterion, since the gem's own webhook authentication API provides no way to bind body-HMAC validity to the specific shop header being trusted.

### Likelihood Explanation
Requires the attacker to control at least one shop that has installed the target app (a routine, unprivileged action any internet user can take by installing a public app), then capture one legitimate webhook delivery from their own store (trivial, e.g. via a local endpoint) and replay it with a modified `shop-domain` header to the app's public webhook URL. No access token, `api_secret_key`, or privileged credential is required — only participation as a normal merchant of the app, which fits the "unprivileged internet user" threat model. Likelihood is moderate-to-high wherever the host app trusts `WebhookMetadata#shop` for tenant scoping, which is the documented usage pattern.

### Recommendation
Extend `Utils::VerifiableQuery`/`HmacValidator` so that webhook validation binds the header fields (`shop`, `topic`, `api_version`, `webhook_id`) into the signed material actually verified, or require callers to additionally reconcile `request.shop` against the shop associated with the currently-active/expected session before dispatching to a handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must be independently verified (e.g., against a known list of installed shop domains) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers any webhook topic on their own shop and captures the raw POST body and its legitimate `X-Shopify-Hmac-SHA256` header (valid because Shopify signs with the app's shared `client_secret`).
3. Attacker crafts a new POST to the app's webhook endpoint reusing the exact captured body and `X-Shopify-Hmac-SHA256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which only checks the (untouched) body against the HMAC — validation succeeds, per [5](#0-4) .
5. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the host app's handler, per [6](#0-5) , causing the attacker-controlled payload to be processed as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
