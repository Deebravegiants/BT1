### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` validates webhook authenticity by HMAC-signing only the raw request body, while the `shop` value used to attribute the event to a tenant is read from an unauthenticated header and is never part of the signed material.

### Finding Description
`Webhooks::Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` succeeds [1](#0-0) . That validator computes the signature purely from `verifiable_query.to_signable_string` and the app's shared `api_secret_key`, comparing it against the `hmac` header value [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, i.e. the HMAC covers the body bytes exclusively [3](#0-2) . Meanwhile, `shop` (`x-shopify-shop-domain` / `shopify-shop-domain`) is read straight from request headers with no cryptographic binding to the body or the signature [4](#0-3) . After HMAC validation passes, `request.shop` is forwarded directly into `WebhookMetadata` and handed to the app's handler as the tenant identifier for that event [1](#0-0) .

The broken binding, stated as an equality that the gem should enforce but does not:
`shop asserted by the HMAC-signed payload == shop attributed to the event by Registry.process`
In this codebase, the left side does not exist — the signature says nothing about which shop the body belongs to — yet the right side (`request.shop`, taken from an unauthenticated header) is treated as trustworthy tenant-identifying data.

### Impact Explanation
Because the api_secret_key is shared by the app across all of its shop installations (not shop-specific), any raw body + HMAC pair valid for one installation is also a valid signature for the same body claimed against any other shop, since the shop value is outside the signed content. If such a body/HMAC pair is replayed with an altered `shop-domain` header, `Registry.process` will still treat the HMAC as valid and dispatch the event to the handler with an attacker-chosen `shop`, letting a party who possesses one legitimately-signed payload inject data attributed to a different, unrelated tenant (cross-tenant data confusion) into the host app.

### Likelihood Explanation
Exploitation requires the attacker to be in possession of at least one legitimately HMAC-signed `(raw_body, hmac)` pair from the app's real webhook traffic. Within the boundaries of this gem, there is no code path exposed to an unauthenticated internet user that leaks such a pair — obtaining one would require observing the app's own inbound webhook deliveries, which is not something the library exposes to an "unprivileged internet user" and effectively requires the same access (server-side or network interception) that is explicitly excluded from scope. This weakens the likelihood significantly compared to a fully remote, credential-free attack.

### Recommendation
Bind the shop identity to the signed material — e.g., include the `shop-domain` (and/or `topic`/`webhook-id`) header value in `to_signable_string`, or otherwise cryptographically bind the header to the body — so that `Utils::HmacValidator.validate` fails if the `shop` header is altered relative to the body it was originally issued for.

### Proof of Concept
Given a previously observed legitimate webhook delivery for shop A with body `B` and header `x-shopify-hmac-sha256: H` (valid because `HMAC(secret, B) == H`):

```ruby
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => H,        # unchanged, still matches B
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # changed
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks B and H,
# and the handler is invoked with shop: "victim-shop.myshopify.com".
```

Note on confidence: this is a real logical gap in this gem's own code (`lib/shopify_api/webhooks/request.rb` / `registry.rb`), but I could not identify a fully credential-free, purely-remote way for an unprivileged internet user to obtain the required `(raw_body, hmac)` pair using only this gem's exposed surface, since the app's webhook endpoint and Shopify's outbound delivery are outside this library. This uncertainty is called out above and should be weighed when triaging.
