Confirmed: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates HMAC via `Utils::HmacValidator.validate(request)`, and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body` — the `shop-domain` header used to route/identify the tenant (`Request#shop`, line 20-23) is never part of the signed material.

### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, enabling cross-tenant webhook confusion - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (tenant identifier) is read from a separate, unsigned header. `Registry.process` trusts this unsigned `shop` value when dispatching to the handler.

### Finding Description
`Utils::HmacValidator.validate` verifies that `HMAC(secret, verifiable_query.to_signable_string) == received_hmac` [1](#0-0) . For webhooks, `to_signable_string` is defined to return only the raw HTTP body [2](#0-1) , while `shop` is parsed independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the signature [3](#0-2) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching, then builds `WebhookMetadata` using `request.shop` taken straight from that unsigned header, without re-validating that this shop matches anything covered by the signature [4](#0-3) .

This is exactly the identity-binding gap described in the report's bug class: the field that downstream logic acts on (`shop`, used to identify which merchant/tenant the webhook belongs to) is not covered by the authentication mechanism (`HMAC`) that is trusted to authenticate the message. The equality that should hold — `shop_bound_by_signature == shop_acted_on_by_handler` — is broken: the signature binds only the body bytes, while the handler acts on an independently-supplied, unauthenticated `shop` field.

### Impact Explanation
A tenant (any shop that has installed the app, an "unprivileged internet user" relative to other tenants) receives genuine webhooks from Shopify for its own store, each with a valid HMAC signed over the body. Because the signature never covers `shop`, that tenant can replay a captured body+HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a *different* victim shop's domain. The HMAC check still passes (body unchanged), and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the victim's domain [5](#0-4) . Any handler logic keyed by `shop` (e.g., updating per-shop settings, redact/GDPR handling, billing state, order sync) can be tricked into operating on the wrong tenant's data — a cross-tenant confusion/impact, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Any shop that has the app installed can trivially capture one of its own legitimately-signed webhook deliveries (bodies for common topics like `orders/create` or `app/uninstalled` are attacker/tenant-controllable to some extent, and always attacker-observable) and replay it with a forged `shop` header value, requiring no access to `api_secret_key` or any privileged credential — only the ability to receive one webhook for an owned shop and to send an HTTP request to the app's public webhook endpoint.

### Recommendation
Include the `shop`/tenant identifier as part of the HMAC-signed material verified by `Request`, or otherwise cryptographically bind it to the request (e.g., verify it matches a value embedded in the webhook body/topic metadata rather than trusting the header). At minimum, `to_signable_string` should incorporate the shop domain header so that `Utils::HmacValidator.validate` fails if the header is tampered with independently of the body.

### Proof of Concept
1. App has installed webhooks for shop `victim.myshopify.com` and shop `attacker.myshopify.com` (attacker legitimately installed the app on their own store).
2. Shopify sends a webhook to the app for `attacker.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker captures this delivery (e.g., from their own server logs) and replays it to the app's webhook endpoint, replacing only the `x-shopify-shop-domain` header with `victim.myshopify.com`, keeping body `B` and the same HMAC header.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (unchanged) and it matches — validation succeeds [6](#0-5) .
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`, `body: parsed_body(B)` — the app now processes attacker-controlled webhook content under the victim tenant's identity [7](#0-6) .

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
