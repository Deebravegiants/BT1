### Title
`Auth::Oauth.begin_auth` sends the app's `client_id` and OAuth `redirect_uri` to an unvalidated, attacker-controllable `shop` host, enabling forced/hijacked OAuth completion - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization redirect URL directly from the caller-supplied `shop` string without validating that it is a genuine `*.myshopify.com`/trusted Shopify domain. Every other credential-bearing entry point in the same library (`ClientCredentials`, `RefreshToken`, `TokenExchange`) explicitly runs the `shop` value through `Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` before using it, but `begin_auth` does not.

### Finding Description
`begin_auth` takes an unvalidated `shop:` argument and uses it only to build the target host for the OAuth authorize redirect: [1](#0-0) 

The host is derived via `auth_base_uri(shop)`, which simply interpolates the raw `shop` string into a URL with no domain check: [2](#0-1) 

The resulting `auth_route` embeds the app's public `client_id` and the app's `redirect_uri` (built from `ShopifyAPI::Context.host`) as query parameters, and the caller is instructed to 307-redirect the merchant's browser to it, after setting a `state` cookie: [3](#0-2) 

The library's own documentation instructs developers to source `shop` directly from an inbound, unauthenticated request header (`request.headers["Shop"]`) and pass it straight into `begin_auth`: [4](#0-3) 

This is the same bug class as the report: a check exists somewhere in the system (`ShopValidator`) that is supposed to bind an identity ("shop") to a trusted domain, but one accepting code path skips it — analogous to a Merkle proof verifier that checks the hash chain but omits the length/boundary check, letting a caller substitute an unvalidated "intermediate" value for the fully-verified one. Here the missing check is domain-trust validation on `shop`, and `begin_auth` is the "unverified" code path.

Contrast with the sibling OAuth-adjacent methods, which do call `ShopValidator.sanitize!` before using `shop` to build a request host that will receive `client_id`/`client_secret`: [5](#0-4) [6](#0-5) 

The dedicated validator that should be applied is: [7](#0-6) 

Because `begin_auth` never calls it, a caller who forwards attacker-influenced input (e.g. an unauthenticated `Shop` header/query parameter, which is exactly the pattern shown in the gem's own docs) as `shop` will have the gem construct a redirect to `https://<attacker-domain>/admin/oauth/authorize?client_id=...&redirect_uri=...&state=...&grant_options[]=...`. Note the `state` value that is placed in the merchant's session cookie is also disclosed in this URL to the attacker-controlled host, and the merchant's browser is sent there with that state already fixed.

### Impact Explanation
This matches the report's "High" bucket: "session fixation or forced OAuth completion." A merchant's browser can be redirected to an attacker-controlled host carrying the app's `client_id` and the legitimate `redirect_uri`. Because the `state` nonce is fixed by the app before the redirect and stored in a cookie scoped to the app's own domain, an attacker who controls the destination host can use this to run OAuth flow-confusion/phishing attacks against the merchant, and can potentially force the completion of an OAuth grant flow that the attacker initiated (session fixation), since `state` and `shop` are trusted and echoed back by `validate_auth_callback` without any check that the "shop" that appears in the callback is a Shopify-trusted domain. `validate_auth_callback` re-validates HMAC and state-cookie equality but never validates `auth_query.shop` against `ShopValidator` either, so the shop that ends up embedded in the resulting `Session` (used later for API calls with the merchant's access token) is also unauthenticated with respect to domain trust.

### Likelihood Explanation
Likelihood is high for any application that (as the gem's own documentation recommends) derives `shop` from request input without separately validating it, since the gem provides `ShopValidator` specifically to prevent this but does not enforce/apply it inside `begin_auth`. Any unprivileged internet user who can influence the `shop` value passed to `begin_auth` (a header, query string, or path segment in the host app) can trigger this without any credentials.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, validate/sanitize the `shop` parameter with `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) at the top of both `begin_auth` and `validate_auth_callback` (for `auth_query.shop`) before it is used to build `auth_base_uri`/`Session`, mirroring the pattern already used in `ClientCredentials`, `RefreshToken`, and `TokenExchange`.

### Proof of Concept
1. Host app implements the documented pattern: `shop = request.headers["Shop"]` (or a query param), then calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` as shown in `docs/usage/oauth.md`.
2. Attacker sends a link to the merchant that causes this route to be hit with `Shop: attacker-controlled-domain.example`.
3. `begin_auth` computes `auth_base_uri("attacker-controlled-domain.example") => "https://attacker-controlled-domain.example/admin"`, with no domain check, and returns `auth_route = "https://attacker-controlled-domain.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=...&redirect_uri=https://legit-app.example/auth/callback&state=<nonce>&grant_options[]=..."`.
4. The host app sets the `state` cookie and 307-redirects the merchant's browser there, per the documented flow — sending the app's `client_id` and callback URL to the attacker's host and exposing the fixed `state` nonce, which can be leveraged for phishing/forced-OAuth-completion against the merchant.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
