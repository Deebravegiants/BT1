### Title
Excess native-token dust from `swapETHForExactTokens` in `EvmHost.dispatch()`/`fundRequest()` is refunded to the Host contract instead of the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are all `payable`, and when `msg.value > 0` they forward the entire `msg.value` to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), ...)`, an exact-output swap that only needs `fee` amount of ETH.

### Finding Description
`swapETHForExactTokens` refunds any unused ETH (`msg.value - amounts[0]`) back to `msg.sender` of that Uniswap call. Since `EvmHost` itself is the caller of the router (`address(this)` performs the swap, not the original transaction sender), any dust refunded by the router lands back inside `EvmHost`, not with the application/user that originally called `dispatch()` or `fundRequest()`. [1](#0-0) [2](#0-1) [3](#0-2) 

There is no logic in any of these three functions to compute the exact ETH cost up front or to forward only the required amount, nor is there a per-caller reimbursement path for the swap's dust refund; the refunded ETH is simply absorbed as generic native balance of `EvmHost`. The only way this ETH can ever leave the contract again is via the privileged, cross-chain-governance-gated `withdraw()`/`IHostManager.withdraw()` path restricted to `_hostParams.hostManager`, which pays out to a beneficiary chosen by Hyperbridge governance, not to the original overpaying caller. [4](#0-3) 

Any application contract (e.g. `IntentGatewayV2`, `WrappedHyperFungibleTokenUpgradeable`, `HyperbridgeLzEndpoint`) that estimates fees client-side and pads the value sent with `dispatch{value: msg.value}(...)`, or any relayer/user calling `fundRequest` with imprecise `msg.value`, will have any overpayment permanently diverted from their control into the Host's balance instead of being refunded to them. [5](#0-4) [6](#0-5) 

### Impact Explanation
This is a fund-freezing bug for end users/applications rather than for the protocol: overpaid native token supplied to `dispatch()`/`fundRequest()` is not recoverable by the payer under any circumstance. It becomes commingled with protocol fee-token-swap proceeds inside `EvmHost` and can only be extracted by cross-chain governance to an arbitrary beneficiary — never back to the original overpayer. Given that exact fee estimation for a Uniswap exact-output swap (which depends on live pool reserves) is inherently imprecise on the client side, overpayment is a routine occurrence, not an edge case, making the loss broad in practice across every EVM deployment that supports native-token dispatch payment.

### Likelihood Explanation
High. Any caller (application contract or EOA via a passthrough app) supplying `msg.value` slightly above the exact swap input — which is the normal, expected way of using this API given documented fee-estimation guidance ("estimate fees on the client side before users submit transactions") — triggers the issue on every such call. No malicious actor is required; it happens under standard usage. [7](#0-6) 

### Recommendation
Either:
1. Compute the exact ETH cost via `IUniswapV2Router02.getAmountsIn(fee, path)` before swapping and only forward that exact amount with the swap call, refunding any remaining `msg.value` directly to `_msgSender()` in the same transaction; or
2. After calling `swapETHForExactTokens`, forward the router's returned dust (the difference between `msg.value` and the actual amount spent) back to `_msgSender()` instead of letting it settle as host balance.

### Proof of Concept
1. An application contract (e.g. one built on `HyperApp`) calls `EvmHost.dispatch{value: X}(post)` where `X` is a client-side fee estimate for `post.fee` fee-tokens, using the pattern shown in the docs and in `HyperbridgeLzEndpoint.send()` / `IntentGatewayV2.execute()`.
2. Due to normal price movement/slippage buffer, `X` exceeds the exact ETH required by the Uniswap pool for `post.fee` fee tokens.
3. `EvmHost.dispatch()` calls `swapETHForExactTokens{value: X}(post.fee, path, address(this), ...)`; the router consumes only `amounts[0] < X` and refunds `X - amounts[0]` ETH to `msg.sender`, which is `EvmHost` (since `EvmHost` itself invoked the router).
4. The refunded dust increases `EvmHost`'s native ETH balance permanently; the original caller has no function to reclaim it — only Hyperbridge governance can later move it via `withdraw()` to any beneficiary it chooses, not necessarily the original overpayer.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
