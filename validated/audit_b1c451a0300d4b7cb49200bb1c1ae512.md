## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never part of the signed bytes. Because Shopify signs webhooks with a single app-level `api_secret_key` shared across every shop that installs the app, a valid `(raw_body, hmac)` pair obtained from one shop can be replayed with a different `shop` header value, and the gem will accept it as authentic for that different shop.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers and are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e. the raw body) against the `hmac` value, so it never binds `shop` to the signature: [3](#0-2) 

`Registry.process` relies exclusively on this HMAC check, then forwards the unverified `request.shop` straight to the application's webhook handler as the tenant identifier: [4](#0-3) 

The broken identity binding, expressed as an equality that the code implicitly (and incorrectly) assumes holds:

`verify(HMAC, secret, raw_body) == true  ⇒  header["shopify-shop-domain"] == shop_that_Shopify_actually_signed_for(raw_body)`

This does not hold, because `shopify-shop-domain` ∉ bytes(raw_body). Shopify's webhook HMAC is computed with the app's single `api_secret_key`, which is identical for every shop that has installed the app — it is not shop-specific. Consequently, any `(raw_body, hmac)` pair that validates for shop A also validates for any other header value an attacker chooses to attach, because the signature check is entirely independent of the header.

## Impact Explanation
This is a cross-tenant identity-binding break analogous to the Yeti report's root cause: an amount (there) / a field (here) that is *acted upon* is not actually covered by the check that is supposed to authenticate it. Here, `WebhookMetadata.shop` — the value host applications use to determine which merchant's data a webhook event applies to — is fully attacker-controllable while still passing HMAC validation, as long as the attacker can produce one legitimately-signed `(raw_body, hmac)` pair. Any unprivileged actor who can install the app on their own store (a normal, unprivileged onboarding action) receives real webhooks signed with the same app-wide secret, and can replay that exact body+hmac to the app's public webhook endpoint with an arbitrary victim `shop` header. `Registry.process` will accept it as authentic and dispatch it to the handler labelled with the victim shop, resulting in cross-tenant data corruration/impersonation in the host application.

## Likelihood Explanation
Likelihood is meaningful, not merely theoretical: any user who signs up for the target app on their own shop already possesses a valid signed webhook body/HMAC pair for at least one real event (e.g. `app/uninstalled`, `orders/create`), because the shared app secret makes every one of their own captured webhooks universally valid regardless of the `shop` header. No credential leakage, TLS interception, or privileged access is required — only a normal install and a normal HTTP request to the app's public webhook endpoint with a forged header, which is squarely reachable via this gem's own `Registry.process`/`Request` API.

## Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) cryptographically or structurally to the authenticated request instead of trusting an unauthenticated header:
- Where the host application maintains a known set of installed shop domains/session records, `Registry.process` (or the caller) should cross-check `request.shop` against that known-shop list before dispatching, rather than trusting the header outright.
- At minimum, document prominently that `request.shop` is unauthenticated and must not be used as the sole tenant selector by handlers, since HMAC validation in `Utils::HmacValidator` covers only `raw_body`.

## Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action any internet user can perform for any public app).
2. The app receives a legitimate webhook for `attacker-shop.myshopify.com`, e.g.
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id":1,...}
   ```
3. Attacker replays the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, changing only:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the unchanged `raw_body` with the same shared `api_secret_key` and finds it valid (`lib/shopify_api/utils/hmac_validator.rb:12-31`), then calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))` (`lib/shopify_api/webhooks/registry.rb:188-200`) — even though Shopify never signed this event for `victim-shop.myshopify.com`.
