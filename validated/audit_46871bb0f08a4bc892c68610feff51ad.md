### Title
Unswapped input-token dust from LI.FI router calls is permanently stuck in `ExternalActionSwap`/`LifiExternalAction` and lost to users - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
When a user performs a shielded swap through `Hinkal.transact` with `externalActionId` pointing to `LifiExternalAction`, `Hinkal._externalTransact` transfers the **entire** negative delta amount of the input token out of the Hinkal contract into the swap contract *before* the router call is made [1](#0-0) . The swap logic in `ExternalActionSwap.swap` then hands this full `inputAmount` to `callRouter`, which simply approves the LI.FI router for the input token and executes an arbitrary, off-chain-generated calldata blob against it [2](#0-1) . Nothing in `swap()` verifies that the router actually consumed the full `inputAmount`, nor does it return any unspent input token — only the resulting `outputToken` balance is measured and forwarded back to Hinkal [3](#0-2) .

### Finding Description
`Hinkal.transact` enforces a strict balance equality per token: `balanceDif == amountChanges[i] + utxoAmount` [4](#0-3) . For the input token of a swap, `amountChanges[0]` is the full (negative) amount the user's proof claims to spend, and because Hinkal has already unconditionally pushed that entire amount to the external action contract in `_externalTransact` [5](#0-4) , Hinkal's own balance change matches `amountChanges[0]` exactly regardless of how much of it the router actually spent. The equality check therefore passes even when the router (LI.FI, driven by arbitrary calldata that is not verified on-chain) only partially consumes the input amount — e.g., due to slippage-limited partial fills, a stale/mis-quoted route, or a route that simply spends less than approved.

Any input-token remainder is left sitting in the `LifiExternalAction`/`ExternalActionSwap` contract's own balance. This contract has:
- No accounting of leftover input token (`swap()` only computes `swappedAmount` from the output token's balance delta) [6](#0-5) .
- No UTXO created for leftover input token — `utxoSet` only ever contains one entry for `outputToken` [7](#0-6) .
- No owner/admin sweep or rescue function anywhere in `OwnerHinkal`, `ExternalActionBaseV2`, or `ExternalActionSwap` to recover stray tokens.

Because the shared `ExternalActionSwap`/`LifiExternalAction` contract is reused across all users (`onlyAllowedRecipient` only checks that the caller is Hinkal, not which user), leftover dust from one user's swap also becomes commingled with the contract's balance and is unrecoverable by anyone, including the user whose shielded balance was debited for it.

This is the exact analog of the reported sense-v1 issue (M-5): funds are transferred out for a swap/unwrap operation but the router/quote does not guarantee full consumption, and no code path returns the unused remainder — except here the debited value comes directly out of a user's shielded UTXO balance inside a zero-knowledge shielded-pool protocol, making the loss unrecoverable and undetectable via any monitoring of encrypted state.

### Impact Explanation
This breaks the fundamental accounting invariant of the shielded pool: the user's proof states they spent `amountChanges[0]` of input token, but only part of it produced value (the output UTXO); the rest is real, tangible token value permanently locked in `LifiExternalAction`, with no code path returning it to the user, to Hinkal, or to any recoverable UTXO. This is a permanent freezing (effectively theft, since it's non-recoverable and belongs to no one) of user funds routed through the swap external action — meeting the High/Critical bar under "permanent freezing of user funds" / "temporary freezing" categories.

### Likelihood Explanation
This does not require any admin, relayer or attacker privilege — it happens under completely normal usage whenever the LI.FI swap does not consume 100% of the approved input (common with aggregator swaps due to slippage guards, partial-fill routes, or minor quote staleness between calldata generation and execution, since `SWAP_DEADLINE_WINDOW` allows up to 10 minutes of drift [8](#0-7) ). No adversarial front-running is even required, though an adversary who can influence route pricing (e.g. via a small trade before the swap executes) can deliberately widen the gap between quoted and consumed amounts to maximize stuck dust.

### Recommendation
After the router call in `LifiExternalAction.callRouter` / `ExternalActionSwap.swap`, measure the residual `inputToken` balance and return any unspent amount back to `msg.sender` (Hinkal) so it can be reflected as an additional UTXO for the input token, mirroring the fix applied upstream in sense-v1/auto-roller (`_fromTarget`/`_toTarget` returning excess sell tokens). Concretely: track `inputBalanceBefore`/`inputBalanceAfter` around the router call, transfer back `inputBalanceBefore - inputBalanceAfter < inputAmount` leftover, and include it as an extra `UTXO` entry (or fold it back into an existing input-token UTXO) so the balance equation in `Hinkal.transact` accounts for it and the user is made whole.

### Proof of Concept
1. User submits a shielded swap via `Hinkal.transact` with `externalActionId` set to the LI.FI action, `amountChanges[0] = -1000` (input token), and off-chain-generated `externalActionMetadata` (LI.FI calldata) that, due to slippage protection inside the aggregated route, only actually pulls `900` of the approved `1000` tokens (LI.FI/aggregator behavior, not attacker-controlled).
2. `Hinkal._externalTransact` sends the full `1000` input tokens to `LifiExternalAction` [5](#0-4) .
3. `LifiExternalAction.callRouter` approves the router for `1000`, calls the router, which only spends `900`; `100` tokens remain in `LifiExternalAction`'s balance [6](#0-5) .
4. `swap()` computes `swappedAmount` purely from `outputToken` balance delta, pays relay fees, and forwards the resulting output tokens back to Hinkal as a single UTXO — the `100` leftover input tokens are never referenced again [9](#0-8) .
5. Back in `Hinkal.transact`, the balance-equality check for the input token still passes because Hinkal's own balance dropped by exactly `1000` (matching `amountChanges[0]`), even though only `900` produced value [10](#0-9) .
6. The `100` tokens are now permanently stranded in `LifiExternalAction`'s contract balance with no owner rescue function and no UTXO ever created to represent them — a real, unrecoverable loss to the user whose shielded balance was debited for the full `1000`.

    function swap(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) internal returns (UTXO[] memory utxoSet) {
        address inputToken = circomData.erc20TokenAddresses[0];
        uint256 inputAmount = uint256(-deltaAmounts[0]);

        if (inputToken == circomData.feeStructure.feeToken) {
            inputAmount -= circomData.feeStructure.flatFee;
        }

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );

        uint256 relayFee = circomData.feeStructure.flatFee;

        uint256 hinkalFee = hinkalHelper.calculateRelayFee(
            swappedAmount,
            0,
            circomData.feeStructure.variableRate
        );

        if (circomData.feeStructure.feeToken == outputToken) {
            sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
        } else {
            sendToRelay(
                circomData.relay,
                relayFee,
                circomData.feeStructure.feeToken
            );
            sendToRelay(circomData.relay, hinkalFee, outputToken);
        }

        uint256 totalFee = hinkalFee +
            (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
        uint256 amountToSendToHinkal = swappedAmount - totalFee;

        transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);

        utxoSet = new UTXO[](1);
        utxoSet[0] = UTXO({
            amount: amountToSendToHinkal,
            erc20Address: outputToken,
            stealthAddressStructure: circomData.stealthAddressStructure,
            timeStamp: block.timestamp
        });
    }
