The strongest analog to the `Operator::setReserveFactor` bug class in `orb-core` is in `MasterPlan::run`, where safety-relevant config parameters are snapshotted once and then reused stale across many subsequent signups, even though the shared config is updated live in the background.

### Title
Stale `self_serve` / `operator_qr_expiration_time` config snapshot in `MasterPlan::run` bypasses backend-tightened signup authorization window - (File: `src/plans/mod.rs`)

### Summary
The Operator.sol finding is a class of bug where a security-relevant parameter is updated in the config store, but code paths that gate a security threshold keep operating on a value computed/cached before the update, instead of re-reading it. `orb-core` has the same pattern: `Config::self_serve`, `self_serve_button`, and `operator_qr_expiration_time` are destructured once from the shared `Arc<Mutex<Config>>` at the top of `MasterPlan::run`, before entering the long-lived signup loop, and that stale snapshot is fed into every loop iteration's QR-scan/idle-wait gating logic for the entire lifetime of the orb process.

### Finding Description
`MasterPlan::run` reads the config once: [1](#0-0) 

and then loops indefinitely, calling `scan_initial_qr_codes` and `idle_wait_for_signup_request` with these same stale `self_serve`, `self_serve_button`, and `operator_qr_expiration_time` values for every subsequent signup: [2](#0-1) 

`scan_initial_qr_codes` uses `operator_qr_expiration_time` to decide whether a previously captured operator QR/location authorization (`OperatorData` with a `timestamp`) is still considered fresh enough to skip re-scanning the operator QR code in self-serve mode: [3](#0-2) 

By contrast, `do_signup` — called from within the same loop — re-reads the config fresh on every single call: [4](#0-3) 

showing that the intended design is for config to be re-read per-signup, but the outer loop's `self_serve`/`self_serve_button`/`operator_qr_expiration_time` decisions were left un-refreshed — the equivalent of Operator.sol changing `reserveFactor` without calling `_regenerate` to propagate the new threshold into the already-cached market-side state.

Meanwhile, the backend genuinely can push a tightened value for these fields at any time; the shared config object is updated live by the background observer task: [5](#0-4) 

and persisted via `Config::download_and_store`: [6](#0-5) 

`self_serve` and `operator_qr_expiration_time` are exactly the kind of security-relevant thresholds described in the config schema: [7](#0-6) [8](#0-7) 

### Impact Explanation
If the backend operator disables self-serve mode (`self_serve: false`) or shortens `operator_qr_expiration_time` in order to force renewed operator authorization/oversight for subsequent signups (e.g. after detecting operator QR misuse, revoking an operator, or narrowing the trust window), the already-running `MasterPlan::run` loop keeps using the old snapshot for its outer gating decisions (`scan_initial_qr_codes`, `idle_wait_for_signup_request`). This means:
- Self-serve signups (which bypass explicit per-signup operator-button gating) can continue to be accepted even after the backend disabled self-serve mode for that orb, until the orb process restarts.
- A previously scanned operator QR code/location authorization can continue to be treated as valid for the old (longer) expiration window rather than the backend's newly tightened window, allowing signups to proceed under stale operator authorization data.

This creates a window for unauthorized or misattributed signups to be processed under an operator/location context the backend intended to have already expired or restricted.

### Likelihood Explanation
The orb's `MasterPlan::run` is long-lived (it loops continuously across many signups without re-entering the function, only breaking for `oneshot`/biometric-input debug modes), while the backend config poll interval refreshes the shared `Arc<Mutex<Config>>` independently on its own schedule. Any operator/backend action that changes `self_serve` or `operator_qr_expiration_time` while an orb is actively running will trigger this staleness deterministically — no attacker-controlled race is required, only normal backend config propagation timing, making this readily reachable in production operation.

### Recommendation
Re-read `self_serve`, `self_serve_button`, and `operator_qr_expiration_time` from `orb.config.lock().await` at the top of each loop iteration in `MasterPlan::run` (i.e., move the destructuring inside the `loop { ... }` block) rather than once before it, so these gating parameters stay consistent with `do_signup`'s per-call refresh behavior and reflect the latest backend-pushed values for every signup attempt.

### Proof of Concept
1. Backend sets `self_serve: true` for an orb; orb starts `MasterPlan::run`, snapshotting `self_serve = true` before the loop.
2. Orb processes several self-serve signups using the idle-scan path gated by the stale `self_serve` flag: [9](#0-8) 
3. Backend operator flips `self_serve` to `false` (e.g. to require operator button-press oversight going forward) and/or shortens `operator_qr_expiration_time`; the background observer downloads and stores the new config into the shared `Arc<Mutex<Config>>`.
4. Because `MasterPlan::run`'s outer loop still holds the pre-update local copies of `self_serve`/`operator_qr_expiration_time`, subsequent loop iterations keep calling `idle_wait_for_signup_request`/`scan_initial_qr_codes` with the old values, continuing to accept self-serve signups (or reuse a stale operator QR authorization) contrary to the backend's updated intent, until the orb process is restarted.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }

    /// Downloads the latest configuration from the backend, updates the shared
    /// configuration object, and stores the updated configuration to the file
    /// system.
    pub async fn download_and_store(config: Arc<Mutex<Config>>) -> Result<()> {
        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }
