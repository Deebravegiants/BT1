### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant impersonation - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity via `Utils::HmacValidator.validate(request)`, which signs and checks only `to_signable_string`, and that method returns solely the raw HTTP body. The `shop-domain` header — the value used downstream as the tenant identifier — is never part of the signed bytes. This breaks the intended binding: `shop trusted by the handler == shop attributable to the verified signature`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, with no relation to the signed body: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header using `OpenSSL.secure_compare`; it never touches `shop`: [3](#0-2) 

`Registry.process` accepts any `Request` whose HMAC validates, and then forwards the *unverified* `request.shop` value straight to the handler as the tenant identifier: [4](#0-3) 

Because all shops using the same Shopify app share the same `api_secret_key`, and the signature only binds the body (not the shop), any party who can obtain one valid `(raw_body, hmac)` pair for that shared secret — e.g. by installing the app on their own store and triggering a webhook, or by controlling a store that receives real webhooks — can replay that same body/hmac pair while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it only checks the body against the secret, and the handler will receive `WebhookMetadata` with the attacker-chosen `shop`, spoofing the tenant.

This matches the report's underlying bug class ("a field acted on but not covered by the HMAC"): the value used for authorization/routing decisions (`shop`) is disjoint from the value actually authenticated (`raw_body`).

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged party who can obtain any valid signed webhook payload for the shared app secret can forge the `shop-domain` for that payload and have it processed by the app's handler as if it originated from a different, victim shop. Any handler logic that trusts `WebhookMetadata#shop` to select per-tenant state, access tokens, or data (a common and encouraged pattern, since `Registry.process` passes `shop` directly) is exposed to cross-tenant data confusion or forged tenant-scoped actions purely by manipulating an unauthenticated header.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimately signed `(body, hmac)` pair under the app's shared secret — trivially achievable by installing the app (even a free/trial install) on an attacker-controlled shop and capturing a real webhook delivery, or by controlling any shop that already has the app installed. From then on, replay with a different `shop-domain` header requires no secret material, no privileged access, and no host cooperation — only crafting an HTTP request to the app's public webhook endpoint. The library performs no cross-check that `shop` is consistent with the signed content, so this is reachable without needing `api_secret_key`, TLS interception, or social engineering, satisfying the "unprivileged internet user" bar.

### Recommendation
- Short term: Document that `WebhookMetadata#shop` (and `Request#shop`) is derived from an HTTP header not covered by the HMAC, and instruct integrators to independently verify that the shop domain matches an installed/known shop before trusting it for tenant-scoped operations.
- Long term: Include the shop domain (and/or webhook id/topic) inside the signed material used by `to_signable_string`, or otherwise validate `Request#shop` against a value derived from data that is itself covered by the signature (e.g., cross-checking against Shopify's published sending IPs or a `webhook_id`/topic-to-shop mapping fetched via an authenticated API call), so a forged `shop-domain` header cannot pass HMAC validation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (or controls any shop where the app is installed), triggering a real webhook delivery to the app's webhook endpoint, and captures the full request: raw body `B`, and header `shopify-hmac-sha256: H` (valid for `B` under the shared `api_secret_key`).
2. Attacker replays a POST to the same webhook endpoint with:
   - body = `B` (unchanged)
   - `shopify-hmac-sha256` = `H` (unchanged, still valid because the signature only covers `B`)
   - `shopify-shop-domain` = `victim-shop.myshopify.com` (forged)
   - `shopify-topic` = topic of choice registered by the app
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (= `B`) and matches `H`, so validation succeeds: [4](#0-3) 
4. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the payload was never generated by or for `victim-shop`, demonstrating the forged tenant binding.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
