## Title
Webhook `shop` (and `topic`/`webhook_id`) fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `ShopifyAPI::Webhooks::Registry.process` proves nothing about the `shop`, `topic`, or `webhook_id` values that the handler is invoked with. Any party that can obtain one genuine `(body, hmac)` pair for the app (e.g., a merchant who has installed the app on their own store) can replay that pair to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` header to claim to be a different merchant. The webhook handler will then process the payload as if it originated from the victim shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body is included in the signable string. The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all derived from headers that are never mixed into that signable string: [2](#0-1) 

`HmacValidator.validate` only checks the HMAC over `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` uses this "verified" request to build the handler's `WebhookMetadata`, trusting `request.shop` and `request.topic` as authenticated identity data: [4](#0-3) 

The equality this breaks is: `shop_that_produced_the_valid_hmac == shop_passed_to_the_handler`. Because the app's `api_secret_key` is shared across every merchant installation of the app (it is the app's client secret, not a per-shop secret), any merchant who has the app installed on their own store can capture a legitimate webhook delivery (raw body + valid `X-Shopify-Hmac-Sha256`) and resend that exact `(body, hmac)` pair directly to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` (and optionally different `topic`/`webhook-id`) header. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the forged `shop`/`topic` values to the app's handler as if Shopify itself sent them.

### Impact Explanation
This is a cross-tenant identity confusion: the handler receives attacker-controlled `shop` (and `topic`) values that it treats as authenticated. Depending on how the host application's webhook handler uses `WebhookMetadata#shop` (e.g., to look up a session/access token, apply data to a tenant's records, or trigger fulfillment actions), this can lead to cross-tenant data corruption or actions being attributed to/executed against the wrong merchant — matching the Critical "cross-tenant access" impact category, since the trust boundary between tenants is defined entirely by this unverified header.

### Likelihood Explanation
Any unprivileged internet user who can install the app on their own store (a normal, low-privilege action for any Shopify merchant/dev) can obtain one valid `(body, hmac)` pair by observing traffic to their own webhook endpoint, then replay it against the app's public webhook URL with a forged shop header. No access token, `api_secret_key`, or other privileged credential is required — the attack uses only their own legitimately-issued webhook.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signable material, or independently verify that `request.shop` corresponds to a shop that actually has an active session/installation before trusting it, and route the webhook to a handler keyed by a value that is cryptographically bound to the HMAC (e.g., verify the shop against a stored, previously-authenticated session, not from an unauthenticated header echoed back by the caller).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (or observes a legitimate webhook they receive), capturing a real webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker sends a new POST directly to the app's public webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this passes. [4](#0-3) 
4. The registered handler is invoked with `shop: "victim-shop.myshopify.com"`, despite the request never having been authenticated as originating from that shop.
