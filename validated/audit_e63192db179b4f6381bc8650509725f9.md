Based on my investigation, I've confirmed a genuine identity-binding flaw in the webhook processing path.

### Title
Webhook shop-domain header is not covered by HMAC, enabling cross-tenant spoofing of webhook attribution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Request#shop` is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the HMAC-covered content [2](#0-1) . `Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string` (i.e., the body) [3](#0-2) . `Registry.process` then trusts `request.shop` as the tenant identity, passing it straight into `WebhookMetadata` for the handler to act on: [4](#0-3) . The broken identity binding is: `shop attributed to webhook data (request.shop, from header) == shop whose data is HMAC-verified (raw_body only)` — this equality does not hold, because the header is fully attacker-controllable while the HMAC provides no binding to it.

### Impact Explanation
An attacker who possesses any single valid `(raw_body, hmac)` pair — for example, from webhooks legitimately delivered to their own installed shop — can replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still pass because it only checks the body against the secret, not the shop header [5](#0-4) . The webhook handler will then execute tenant-scoped side effects (e.g., data updates, redaction actions, order/product processing) attributing the attacker's payload to the victim's shop, since `WebhookMetadata#shop` is trusted unconditionally by `Registry.process` [6](#0-5) . This is cross-tenant access/data corruption in applications that key persistence or business logic off `WebhookMetadata#shop` (the documented and expected usage pattern of this API).

### Likelihood Explanation
Any developer or merchant who can install the app on a shop they control (a normal, unprivileged flow) can obtain valid `(body, hmac)` pairs for webhooks delivered to that shop, since the HMAC only signs the body and is otherwise independent of shop identity. No `api_secret_key` or elevated credentials are needed to construct the forged request — only replaying/re-POSTing an intercepted or self-generated legitimate webhook with a modified header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-verified signable content, or independently bind the header-derived `shop` value to a value that is cryptographically tied to the payload before trusting it for tenant-scoped operations. At minimum, document that `WebhookMetadata#shop` is not cryptographically bound to the request body and must not be trusted for tenant identification without additional verification (e.g., checking against an app-known shop-token mapping).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, or intercepts a webhook delivery to the app's registered endpoint.
2. Attacker captures a legitimately-signed webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker re-sends a POST to the same webhook endpoint with the same body `B` and `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B` [3](#0-2) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` [6](#0-5) , causing the app to act on the victim shop's tenant record using attacker-supplied data.
