### Title
Off-by-one in `pallet_call_decompressor::decompress` size gate rejects legitimate maximum-size calls - (File: modules/pallets/call-decompressor/src/lib.rs)

### Summary
`pallet_call_decompressor::Pallet::decompress` gates the caller-claimed decompressed size against the configured `MaxCallSize` using a strict `<` comparison, which rejects an exactly-maximum-size call instead of only calls that actually exceed the maximum, mirroring the `AvailBridge.sendMessage` off-by-one pattern in the external report.

### Finding Description
The gate is: [1](#0-0) 

```rust
pub fn decompress(
    compressed_bytes: Vec<u8>,
    encoded_call_size: u32,
) -> Result<Vec<u8>, DispatchError> {
    ensure!(encoded_call_size < T::MaxCallSize::get() * ONE_MB, Error::<T>::CallSizeOutOfBound);
    ...
```

`T::MaxCallSize` is documented as "the maximum original(uncompressed) encoded call size in Megabyte that the pallet allows in the runtime" [2](#0-1) . Since "maximum" implies the boundary value is the upper limit inclusively, the check should be `encoded_call_size > T::MaxCallSize::get() * ONE_MB` (reject only what exceeds the max) or `<=` for the accept condition. Using strict `<` means any `encoded_call_size` exactly equal to `MaxCallSize * ONE_MB` is rejected with `CallSizeOutOfBound`, even though it is within the documented allowed maximum. This choke point gates both the signed dispatch path (`decompress_call`) and the unsigned mempool `validate_unsigned` path, per the code comments [3](#0-2) , both of which forward decompressed calls into `pallet_ismp::Call::handle_unsigned` and `pallet_ismp_relayer::Call::accumulate_fees` [4](#0-3) .

### Impact Explanation
Any relayer or unprivileged caller attempting to submit a compressed ISMP `handle_unsigned` batch (or a relayer fee `accumulate_fees` call) whose exact uncompressed size equals `MaxCallSize * ONE_MB` will have that call unconditionally rejected as `CallSizeOutOfBound`, even though it is a legitimate, in-bounds call. This can cause valid message-delivery batches sized precisely at the boundary to be permanently undeliverable through this route (the caller must always keep the payload strictly under the configured maximum, silently shrinking the effective capacity by one byte). This falls in the "route unable to deliver messages" impact category for this exact boundary size, matching the severity class of the referenced report.

### Likelihood Explanation
Likelihood of hitting the exact boundary is generally low unless a relayer or batching tool deliberately packs a message batch up to the configured maximum size to maximize throughput (which is a realistic operational pattern for relayers trying to minimize the number of submitted messages/gas). No special privileges are required — this is reachable by any unprivileged submitter of a compressed call through the public `decompress_call` extrinsic / `validate_unsigned` mempool path.

### Recommendation
Change the size check from a strict `<` to `<=`:

```rust
ensure!(encoded_call_size <= T::MaxCallSize::get() * ONE_MB, Error::<T>::CallSizeOutOfBound);
```

so that a call whose exact size equals the configured maximum is accepted, and only calls that exceed the maximum are rejected.

### Proof of Concept
1. Configure `MaxCallSize = ConstU32<N>` for some `N` MB.
2. Construct/compress a valid `RuntimeCall::Ismp(pallet_ismp::Call::handle_unsigned { .. })` whose uncompressed encoded length is exactly `N * ONE_MB` bytes.
3. Call `pallet_call_decompressor::Pallet::<T>::decompress(compressed_bytes, N * ONE_MB)` (or dispatch `decompress_call` with `encoded_call_size = N * ONE_MB`).
4. Observe the call reverts with `Error::<T>::CallSizeOutOfBound`, even though `N * ONE_MB` is the documented maximum allowed size, matching the existing test pattern that exercises the boundary check at [5](#0-4) .

	pub fn decompress(
		compressed_bytes: Vec<u8>,
		encoded_call_size: u32,
	) -> Result<Vec<u8>, DispatchError> {
		// Bound the claimed decompressed size against the configured maximum here,
		// at the single choke point every caller flows through. Previously this
		// gate lived only in `decompress_call` (the dispatch path); the unsigned
		// `validate_unsigned` mempool path called `decompress` directly with no
		// bound, so a fee-less attacker could claim `encoded_call_size = u32::MAX`
		// and have a tiny zstd "bomb" expanded to gigabytes during transaction-pool
		// validation, before any size check. Enforcing it here protects both paths.
		ensure!(encoded_call_size < T::MaxCallSize::get() * ONE_MB, Error::<T>::CallSizeOutOfBound);
