## Analysis

Raydium's classic AMM `Deposit` instruction exhibits the same class of insufficient slippage control as the Lockbox V2 report: the amount of pool-share ("LP") tokens a depositor receives is derived from the *current on-chain reserves* at execution time, and the instruction gives the caller no way to bound that output directly — only the underlying token amounts are bounded.

### Title
Deposit instruction lacks a minimum-LP-output check, allowing sandwich manipulation of `mint_lp_amount` - (File: `program/src/processor.rs`)

### Summary
`process_deposit` computes `deduct_coin_amount`/`deduct_pc_amount` from the pool's live vault balances and the caller-supplied `max_coin_amount`/`max_pc_amount`/optional `other_amount_min`, then derives `mint_lp_amount` from those live balances via `InvariantPool::exchange_token_to_pool`. There is no `min_lp_amount` (or equivalent) parameter, so a depositor cannot bound the actual LP output they receive, only the token amounts they pay in.

### Finding Description
`DepositInstruction` only carries `max_coin_amount`, `max_pc_amount`, `base_side`, and an optional `other_amount_min`: [1](#0-0) 

In `process_deposit`, the pool's live reserves (`amm_coin_vault.amount` / `amm_pc_vault.amount`) are read and pnl-adjusted into `total_coin_without_take_pnl` / `total_pc_without_take_pnl`: [2](#0-1) 

The "other side" amount is derived from these live reserves and only checked against the caller's `max_*` / `other_amount_min` bounds (an `ExceededSlippage` check exists here, analogous to Lockbox's `token_max_a`/`token_max_b`): [3](#0-2) 

Crucially, `mint_lp_amount` — the actual value the depositor receives — is computed independently as `deduct_coin_amount / total_coin_without_take_pnl * lp_amount` (or the pc-side equivalent), with **no corresponding minimum-output check**: [4](#0-3) [5](#0-4) 

This is structurally identical to the reported Lockbox V2 flaw: the token-side amounts are bounded, but the pool-share output is a nonlinear function of live reserves and is left completely unbounded. An attacker can front-run a deposit with a `SwapBaseIn`/`SwapBaseOut` (or, if not otherwise gated, a direct token transfer into the vault) that shifts `total_coin_without_take_pnl`/`total_pc_without_take_pnl` just enough to stay within the victim's `max_coin_amount`/`max_pc_amount`/`other_amount_min` tolerance (which in practice is set loosely, e.g., the CLI's own example sets `config.set_slippage(50)` i.e. 0.5%) while still reducing `mint_lp_amount` for the same token contribution. The attacker, holding LP tokens (or acquiring them around the same window), then reverses the price move and captures the value the victim under-received in LP shares, exactly mirroring the "buy token B → sandwich deposit → sell back" pattern from the external report.

### Impact Explanation
A victim depositor can receive materially fewer LP tokens than the fair value of their contribution while every explicit protocol check still passes, transferring that value to the sandwiching attacker/existing LPs. This is a direct value-theft vector against LPs reachable by any unprivileged actor who can submit ordered transactions (e.g., via Jito bundles), consistent with a Medium-severity finding as in the original report.

### Likelihood Explanation
The `Deposit` instruction is a core, frequently used user-facing instruction, and slippage tolerances (`max_coin_amount`/`max_pc_amount`/`other_amount_min`) are commonly set to accommodate normal price drift, leaving a workable window for a sandwich attacker with no need to bypass any explicit check — the vulnerability is a gap in what is checked, not a bypass of an existing check.

### Recommendation
Add a client-supplied minimum LP-output parameter (e.g., `min_lp_amount`) to `DepositInstruction`, and enforce `mint_lp_amount >= min_lp_amount` in `process_deposit` (in both the `base_side == 0` and `base_side != 0` branches), returning `AmmError::ExceededSlippage` if not met, mirroring the pattern already used for `other_amount_min`.

### Proof of Concept
1. Attacker observes a pending `Deposit` transaction (`base_side = 0`, `max_coin_amount = C`, `max_pc_amount = P`, `other_amount_min = M`) targeting pool with reserves `(coin0, pc0)` and `lp_amount0`.
2. Attacker front-runs with a `SwapBaseIn`/`SwapBaseOut` that increases `total_coin_without_take_pnl` (and proportionally `total_pc_without_take_pnl`, staying inside `[M, P]`) so that the resulting `deduct_pc_amount` for `C` still satisfies `M <= deduct_pc_amount <= P` (no `ExceededSlippage` revert).
3. Victim's `Deposit` executes: `mint_lp_amount = C / total_coin_without_take_pnl' * lp_amount0`, which is lower than it would have been against `coin0` — see the unguarded computation at [6](#0-5) .
4. Attacker back-runs, reversing the swap and/or exploiting the now-inflated pool value per LP token from their own LP holdings, realizing profit at the victim's expense.
