### Title
Accrual-time i128 overflow in `calculate_supplier_rewards` permanently freezes a market once debt value crosses the Ray ceiling — ([File: common/src/rates/index.rs])

### Summary
CVE-2019-13223 is a reachable assertion causing denial of service on a crafted input. The analog in XOXNO Lending is a reachable arithmetic panic (`Ray::mul` → `MathOverflow`) inside the mandatory interest-accrual preamble. `global_sync` runs before every market verb, and `calculate_supplier_rewards` multiplies `borrowed` (scaled debt shares) by the new borrow index in raw RAY precision. When `borrowed * borrow_index` exceeds `i128::MAX`, the multiplication panics. Because the panic happens inside accrual — before any state is written and before `update_borrow_index`'s `MAX_BORROW_INDEX_RAY` cap can engage on the *value* side — every subsequent call to the market reverts the same way, permanently freezing all supplied funds in it.

### Finding Description
Every pool mutation loads the cache and calls `interest::global_sync` before touching state (`contracts/pool/src/interest.rs:20-33`). `global_sync` calls `accrue_step`, which computes the new borrow index via `update_borrow_index` (`common/src/rates/index.rs:13-19`) — capped at `MAX_BORROW_INDEX_RAY` — and then calls `calculate_supplier_rewards` to split interest:

```rust
let old_total_debt = borrowed.mul(env, old_borrow_index);
let new_total_debt = borrowed.mul(env, new_borrow_index);
```

(`common/src/rates/index.rs:80-81`)

`borrowed` is total scaled debt in raw RAY; `borrow_index` is also raw RAY. Their product `borrowed * index / RAY` must fit in `i128`. The index cap bounds the *index* at 10³⁶ raw RAY but does nothing to bound the *product*: a market carrying very large scaled debt (e.g., a high-decimals asset with whale-scale borrow at sustained high utilization) pushes `borrowed * new_borrow_index` past `i128::MAX` well before the index cap engages. `Ray::mul` panics with `MathOverflow` (33). The same value overflow exists in `Cache::calculate_utilization` via `scaled_to_original` (`contracts/pool/src/cache/scale.rs:23-26`) and in `apply_bad_debt_to_supply_index` (`contracts/pool/src/interest.rs:74`), but the accrual path is the fatal one because it is unconditional.

The repo's own integration test demonstrates the freeze end-to-end: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356` advances a ~98%-utilization whale market until `update_indexes` fails with `MATH_OVERFLOW`, then asserts both `withdraw` and `repay` fail identically — the market is frozen, no exit path exists.

### Impact Explanation
Permanent freezing of funds. Once a market crosses the cliff, `last_timestamp` is never advanced (`mark_accrued` at `interest.rs:32` is never reached because the panic aborts the call), so the overflow re-triggers on every subsequent invocation. All suppliers' deposits, all borrowers' collateral, all pending liquidations, bad-debt cleanup, and `recapitalize` in that market are permanently bricked — this is not a transient revert but a terminal market state. A freeze triggered this way also strands the collateral positions in the controller that reference the dead spoke market.

### Likelihood Explanation
Reachable by an unprivileged address. `update_indexes` is permissionless, and creating the precondition needs only ordinary `supply` + `borrow` calls: list a high-decimals market, supply a very large principal, borrow near-maximum against other collateral, then let (or permissionlessly drive) accrual at high utilization. No privileged action, oracle manipulation, or external dependency is required — the cliff is a pure function of market size, index growth, and time. The cost is high (whale-scale capital or an organic whale market plus accrual time), matching a Medium-severity analog of the reachable-assertion class: an assertion on a reachable state causes a protocol-level denial of service rather than a single-request DoS.

### Recommendation
Make accrual total-overflow-safe instead of letting the panic be the bound:

- In `calculate_supplier_rewards` (`common/src/rates/index.rs`), cap the effective `new_borrow_index` so `borrowed * new_borrow_index` stays under `i128::MAX` — e.g., compute `max_index = i128::MAX * RAY / borrowed` via saturating `mul_div` and clamp `new_borrow_index` to `min(computed, cap_from_value)` before multiplying. This makes the value ceiling a graceful interest halt (like the `MAX_BORROW_INDEX_RAY` cap already is) rather than a trap.
- Apply the same saturating treatment in `update_supply_index`'s `supplied.mul(env, old_index)` (`index.rs:34`) and `apply_bad_debt_to_supply_index`'s `supplied * supply_index` (`interest.rs:74`), which share the exposure.
- Alternatively, gate `global_sync` so that when a value-overflow is detected it records a "rate frozen" flag and lets withdrawals/repayments proceed against the last good index, instead of panicking on every verb.

### Proof of Concept
Mirroring the existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

1. Admin lists a market on an 18-decimals asset with an aggressive rate curve (e.g., `xlm_curve()`).
2. Attacker/whale calls `supply(BIG18, 1e9 * 10^18)` — scaled supply ≈ 10⁴⁵ raw RAY.
3. Attacker supplies collateral on a second market and calls `borrow(BIG18, 0.98 * principal)` — `borrowed` ≈ 9.8·10⁴⁴ raw RAY.
4. Time accrues at ~98% utilization; anyone calls the permissionless `update_indexes(&[BIG18])` periodically. Each accrual raises `borrow_index`; the interest value `borrowed * new_borrow_index / RAY` grows toward `i128::MAX` ≈ 1.7·10³⁸.
5. On the accrual where the product crosses the ceiling, `calculate_supplier_rewards` panics with `MathOverflow` inside `global_sync`. `last_timestamp` is never updated.
6. Every subsequent call — `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `update_indexes` — re-runs `global_sync`, hits the same product, and reverts. All supplier funds in the market are permanently frozen, and the `MAX_BORROW_INDEX_RAY` index cap never engaged because the index itself remained below it.
