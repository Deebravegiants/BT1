### Title
Unbounded object-ownership chains via `TransferRef::transfer_with_ref` bypass the `MAXIMUM_OBJECT_NESTING` depth check, enabling gas-exhaustion / permanent-lock DoS on ownership-verification paths - (File: `aptos-move/framework/aptos-framework/sources/object.move`)

### Summary
`aptos_framework::object` enforces a hard-coded nesting depth cap (`MAXIMUM_OBJECT_NESTING = 8`) whenever ownership chains are walked during a normal, capability-free transfer (`transfer`, `transfer_raw`, `transfer_to_object` → `verify_ungated_and_descendant`) and during `owns()`. However, `transfer_with_ref`, which is driven by a `LinearTransferRef` derived from an object's own `TransferRef`, performs **no** such check, and `root_owner()` performs **no bound check at all**. An object creator (fully unprivileged w.r.t. any other party) can therefore chain their own objects to an arbitrary depth using only `TransferRef`s they legitimately hold, producing an ownership graph that other, bounded custody-verification code paths cannot safely traverse.

### Finding Description
Ownership of an Aptos object is a single-address field, `ObjectCore.owner`, and this field may itself be another object address, creating an ownership chain. Several functions must walk this chain to answer authority questions:

- `verify_ungated_and_descendant` (used by `transfer`/`transfer_raw`/`transfer_to_object`) and `owns` both loop with an explicit guard: `assert!(count < MAXIMUM_OBJECT_NESTING, ...)` [1](#0-0) [2](#0-1) 
- `root_owner` loops with **no bound at all**: `while (is_object(obj_owner)) { obj_owner = address_to_object<ObjectCore>(obj_owner).owner(); }` [3](#0-2) 

Critically, `transfer_with_ref` — the entry point used whenever a module holds a `TransferRef`/`LinearTransferRef` for an object (the mechanism explicitly designed to bypass `allow_ungated_transfer`) — sets ownership directly with **no depth verification whatsoever**:
```
public fun transfer_with_ref(self: LinearTransferRef, to: address) {
    ...
    let object = borrow_global_mut<ObjectCore>(self.self);
    assert!(object.owner == self.owner, error::permission_denied(ENOT_OBJECT_OWNER));
    ...
    object.owner = to;
}
``` [4](#0-3) 

Any object creator holds `ConstructorRef` → can call `generate_transfer_ref()` on their own object, and `generate_linear_transfer_ref()` has no depth restriction either: it only checks `!exists<Untransferable>(self.self)` [5](#0-4) . This means an attacker can create N objects they own and, for each `obj_i`, call `transfer_with_ref` to set `obj_i.owner = obj_{i+1}`, forming an ownership chain of arbitrary length N, entirely under their own control and without triggering the `MAXIMUM_OBJECT_NESTING` guard that exists specifically to keep such chains bounded.

This breaks the invariant documented in the code comment itself — "Note, this is limited to a depth of 8" [6](#0-5)  — which the framework assumes holds for *all* objects, but which is only enforced on the `transfer`/`owns` code path, not on the `TransferRef`-driven path.

### Impact Explanation
Two distinct custody-relevant consequences follow directly from local code:

1. **Permanent lock of object-held value.** Any downstream custody logic that relies on `object::owns()` to authorize a withdrawal (e.g., "does `sender` (indirectly) own this deposited object?") will unconditionally `abort` with `EMAXIMUM_NESTING` once the object's ownership chain exceeds 8 hops [7](#0-6) . If such a deeply-nested object is ever placed into escrow/vault/lending logic that gates release on `owns()`, the check can never succeed again — a permanent, non-recoverable loss of access to that object's value, matching the "Permanent lock or non-recoverable loss of object-held value" impact category. Because chain construction requires only `transfer_with_ref` calls the attacker fully controls (their own objects, own refs), this is entirely self-inflicted infrastructure that nonetheless corrupts any later authority check performed by the framework's own `owns` primitive.
2. **Unbounded gas cost on `root_owner`.** Since `root_owner` has no depth limit at all, its cost is O(chain length) with no cap, reproducing the exact "attacker grows an iterated structure, victim's later call becomes disproportionately expensive" pattern from the original report. Any code (framework or application) that calls `root_owner` on an object whose ownership chain an unprivileged party controls can be forced to pay unbounded gas, up to exceeding the block gas limit.

I was not able to confirm, from local aptos-framework code alone, a specific *framework* function (as opposed to third-party marketplace/vault modules) that calls `owns()` or `root_owner()` directly in a custody-critical release path at mainnet scope within the indexed portion of the repo — the direct callers of `owns`/`root_owner` I could confirm in-repo are in `object.move`, `init.move`, `fungible_asset.move`, and `code.move` [8](#0-7) , and I could not fully verify within the remaining budget whether `fungible_asset.move`'s or `code.move`'s usages sit on an unprivileged, asset-controlling path. This is the primary source of uncertainty in this finding: the depth-check bypass is proven and is a genuine invariant break in local code, but a fully self-contained (framework-only) exploitation chain ending in "custody impact" would benefit from confirming a concrete framework caller of `owns`/`root_owner` on attacker-supplied nested objects.

### Likelihood Explanation
Likelihood is high for the mechanical part of the bug (constructing an out-of-spec deep ownership chain): it requires only standard, permissionless operations (`create_object`, `generate_transfer_ref`, `generate_linear_transfer_ref`, `transfer_with_ref`) that any account can perform on objects it creates, with no interaction from any other party. The remaining uncertainty is solely whether a given custody-relevant consumer (framework or ecosystem contract) invokes `owns()`/`root_owner()` on such attacker-influenced objects in its release/authorization path — which is common practice in Aptos object-based marketplaces, vaults, and lending protocols that use `object::owns` for depositor verification.

### Recommendation
- Enforce the same `MAXIMUM_OBJECT_NESTING` bound in `transfer_with_ref` (and in `generate_linear_transfer_ref`/`generate_transfer_ref` chain-building generally) that is already enforced in `verify_ungated_and_descendant`/`owns`, so `TransferRef`-driven transfers cannot construct ownership chains deeper than the documented invariant.
- Add an explicit, bounded loop guard to `root_owner`, mirroring `owns`, so it aborts (or returns a partial/best-effort result) rather than performing unbounded storage traversal.
- Consider recording/caching an object's nesting depth as part of `ObjectCore` so all traversal-based checks can reject depth violations in O(1) instead of re-walking the chain each time.

### Proof of Concept
```move
// Attacker-controlled, no third-party interaction required.
// 1. Create N objects, each attacker retains its own ConstructorRef.
let ctor_1 = object::create_object(attacker_addr);
let obj_1  = object::object_from_constructor_ref<ObjectCore>(&ctor_1);
let tref_1 = object::generate_transfer_ref(&ctor_1);
... // repeat for obj_2 .. obj_N (N > 8, e.g. N = 100)

// 2. Chain them: obj_i.owner = obj_{i+1}, using transfer_with_ref,
//    which performs NO MAXIMUM_OBJECT_NESTING check.
let i = 1;
while (i < N) {
    let ltref_i = object::generate_linear_transfer_ref(&tref_i);
    object::transfer_with_ref(ltref_i, object_address(obj_{i+1}));
    i += 1;
};
// obj_N.owner == attacker_addr (real account), depth = N-1 >> 8.

// 3a. Any later call to object::owns(obj_1, attacker_addr) now
//     unconditionally aborts with EMAXIMUM_NESTING (out_of_range),
//     permanently breaking any custody logic gated on owns().
// 3b. Any later call to object::root_owner(obj_1) performs N-1
//     unbounded storage reads with no abort/cap, imposing
//     attacker-controlled, unbounded gas cost on the caller.
```

    /// time of generation is the owner at the time of transferring.
    public fun generate_linear_transfer_ref(self: &TransferRef): LinearTransferRef {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));
        let owner = Object<ObjectCore> { inner: self.self }.owner();
        LinearTransferRef {
            self: self.self,
            owner,
        }

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }

    #[view]
    /// Return true if the provided address has indirect or direct ownership of the provided object.
    ///
    /// Note: intentionally not using `self` as first argument, as a.owns(b) syntax would be ambiguous.
    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        if (current_address == owner) {
            return true
        };

        let object = borrow_global<ObjectCore>(current_address);
        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }
