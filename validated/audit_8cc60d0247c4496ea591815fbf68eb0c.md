### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted by the dispatch/handler layer but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw HTTP body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values, however, are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never mixed into the signed material [2](#0-1) . After the HMAC check passes, `Registry.process` still uses those unauthenticated header values to select the handler and to build the `WebhookMetadata` object that is handed to the app's business logic [3](#0-2) .

### Finding Description
This is structurally the same class of bug as the reported Astaria issue: a value that is *used* to determine ownership/identity (`receiver` in the Solidity report, `shop` here) is not part of what the cryptographic check actually binds (the strategy signature in Astaria, the raw-body HMAC here).

The binding that should hold is:
`shop used by the handler == shop for which the signature (HMAC) was computed`

Before the request reaches the handler, the gem only proves:
`HMAC(api_secret_key, raw_body) == received_hmac`

It never proves anything about the `shopify-shop-domain` (or `shopify-topic` / `shopify-webhook-id`) header, so an attacker fully controls those fields independently of the body that was actually signed.

Because `Context.api_secret_key` is the single app-wide client secret (shared across every shop that installs the app), any unprivileged user can become "self-registered" the same way the PoC attacker self-registers a private vault: they install the target app on their own store (a store they fully control), causing Shopify to send them a webhook whose body is HMAC-signed with the app's shared secret [4](#0-3) . That attacker now holds a "valid commitment" — a `(raw_body, hmac)` pair that will pass `HmacValidator.validate` — that is not bound to their own shop identity in any way the gem checks.

The attacker can then combine this valid `(body, hmac)` pair with an arbitrary `shopify-shop-domain` header value (the "receiver" analog) and POST it directly to the app's public webhook endpoint. `Registry.process` will accept it as authentic [3](#0-2)  and hand the app's handler a `WebhookMetadata` claiming to be from the victim shop, with attacker-chosen body content [5](#0-4) . The documented, intended usage pattern is for host apps to key business logic (session lookups, job dispatch, tenant-scoped writes) directly off `data.shop`, as shown in the gem's own example handler [6](#0-5) .

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: the shop identity the app acts on is not the shop that the signature actually authenticates for. An attacker with no privileges beyond installing the app on their own store can forge webhook events that appear to originate from any other shop (including ones they have never interacted with), with body content of their choosing (limited to whatever body their own legitimately-triggered webhook contained, and to whatever topic/webhook_id they choose to send, since none of it is signed). Depending on what the host app's webhook handlers do with `data.shop`/`data.body` (e.g. `shop/redact`, `app/uninstalled`, order/customer processing keyed by shop), this can produce cross-tenant data corruption, spoofed mandatory GDPR webhooks, or triggering of shop-scoped side effects for a shop the attacker doesn't control. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app using the HTTP webhook delivery path documented by this gem: it requires no credentials beyond the ability to install the app on an attacker-owned/dev store (the normal, unprivileged way any merchant obtains a working webhook signature), and no interception of TLS or access tokens. The only "skill" needed is noticing that `to_signable_string` in `Request` never contributes the shop/topic/webhook-id headers to the signed payload.

### Recommendation
Bind the identity fields into what is verified before they are trusted:
- Include `shop`, `topic`, and `webhook_id` (not just the raw body) in the material passed to `HmacValidator`, e.g. by having `Request#to_signable_string` concatenate a canonical representation of the relevant headers plus the body, mirroring how `AuthQuery#to_signable_string` binds `shop`/`state`/`code` for OAuth.
- Alternatively/additionally, require host apps to cross-check `request.shop` against a shop that is known to have actually registered that specific `webhook_id`/topic (e.g. verify a stored mapping) before acting on the payload, and document this as a mandatory step rather than leaving `data.shop` implicitly trusted in the reference handler example.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (self-registration, no special privilege required).
2. Attacker triggers any subscribed webhook topic on their own shop (e.g. `orders/create`) and captures the raw request Shopify sends to the app's webhook endpoint, including the valid `x-shopify-hmac-sha256` header (computed by Shopify with the app's shared `client_secret` over the raw body) [7](#0-6) .
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers because only presence, not authenticity, of `shop-domain`/`topic`/`hmac-sha256` is checked at construction [8](#0-7) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` and finds it matches — validation succeeds despite the shop header being forged [9](#0-8) .
6. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, i.e. `shop: "victim-shop.myshopify.com"` with attacker-controlled body — the app now performs shop-scoped logic under a false tenant identity [10](#0-9) .

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

```ruby
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
