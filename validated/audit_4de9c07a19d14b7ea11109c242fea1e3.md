### Title
Webhook shop identity (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature that `Registry.process` validates only covers the raw request body. This breaks the identity binding `verified_bytes == acted_on_identity`, exactly mirroring the reported bug class where a value used to key a security-relevant mapping (`referrer`/`referralInfoMap[referrer]`) was not the value actually authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `shop` is read straight from the `shop-domain` header without any cryptographic binding to that signed body [2](#0-1) .

`Utils::HmacValidator.validate` only ever checks `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)` [3](#0-2) , so for a `Webhooks::Request` object it authenticates the body bytes only — never the topic, api-version, webhook-id or, critically, the shop-domain header.

`Registry.process` uses this unauthenticated `request.shop` value directly as the tenant identity handed to the application's webhook handler: [4](#0-3) 

The resulting `WebhookMetadata.shop` field [5](#0-4)  is the value host applications are documented to trust for looking up the correct merchant/session and applying the webhook payload to that tenant's data — exactly analogous to `referralInfoMap[referrer]` being keyed off a value that was never verified to belong to the entity acting on it.

Binding that should hold: `hmac_signed_bytes ⊇ identity_used_for_tenant_routing`. Here it does not: `hmac_signed_bytes = raw_body` while `identity_used_for_tenant_routing = header["x-shopify-shop-domain"]`, an entirely separate, unsigned channel.

### Impact Explanation
Any actor who has ever received (or can generate) one genuine `(raw_body, hmac)` pair signed with the app's `client_secret` — trivially available to any merchant who installs the app on their own store and triggers a webhook-eligible event (e.g., creating an order) — can capture that pair and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to name a different, victim shop. `HmacValidator.validate` still passes because it never inspected the header, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the victim's domain. Any host application that uses this field to select which merchant record, session, or access token to act on (the documented use case) will apply the attacker-supplied body to the wrong tenant, constituting cross-tenant data confusion/injection — matching the "Critical – cross-tenant access" impact bucket.

### Likelihood Explanation
No special privileges, leaked secrets, or `client_secret`/access-token access are required: an unprivileged internet user with a normal store install can generate their own valid `(body, hmac)` pairs through ordinary use of the app, then replay them with a forged header at will. The only capability needed is the ability to send an HTTP request with a custom header, which any client of the app's public webhook endpoint has.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id/api-version) in the HMAC-signed material, or otherwise cryptographically bind them to the body — e.g., derive `shop` only from data returned by an authenticated call back to Shopify, or fold the header values into `to_signable_string` so `HmacValidator.validate` fails whenever they are altered after signing.

### Proof of Concept
1. Install the app on Shop A (attacker-controlled) and trigger any webhook-registered event, capturing the legitimate request: `raw_body`, `x-shopify-hmac-sha256`, and `x-shopify-topic` headers.
2. Send this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint again, but replace `x-shopify-shop-domain` with Shop B's domain (a shop the attacker does not control).
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `Registry.process` returns `true` because it only hashes `raw_body` [1](#0-0) .
4. The handler receives `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's payload>, ...)` [6](#0-5)  and, if the host app trusts `data.shop` to select the tenant record to update, Shop A's data is written/acted upon under Shop B's identity.
