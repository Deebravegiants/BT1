### Title
Empty `erc20TokenAddresses` bypasses all value-conservation checks, letting Emporium ETH balance be drained via `runAction` — ([File: contracts/Hinkal.sol], [File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `CircomData.erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes proof-input generation to `formInputEmporiumMin`, which uses `MainEVMCircuitMin` — a circuit whose only constraint is `message <== Poseidon(1)([messageSeed])`, with `outTimeStamp` and `calldataHash` left completely unconstrained. Because `dimensionsCheck` forces every per-token array (including `slippageValues`, `amountChanges`, `inputNullifiers`, `outCommitments`) to have length 0 to match `tokenNumber = 0`, the balance-conservation loop in `Hinkal.transact` (lines 97-146) never executes. Meanwhile `EmporiumUpgradeable.runAction` still executes `stack.ops` and can send arbitrary `msg.value` ETH to an arbitrary `op.endpoint`, since `verifyWallet` performs zero validation when `stack.signerAddress == address(0)`.

### Finding Description
The broken equality is the per-token conservation check in `Hinkal.transact`:
```
balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount
``` [1](#0-0) 

This check is inside a `for (uint64 i; i < circomData.erc20TokenAddresses.length; i++)` loop. When the attacker sets `erc20TokenAddresses = []`, the loop body never runs, so no equality is ever evaluated, even though real ETH leaves the `Emporium` contract's custody.

Path traced:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks` → `dimensionsCheck` requires all per-token arrays to have length `dimensions.tokenNumber` [2](#0-1) . Setting `tokenNumber=0` makes all these arrays empty, which is self-consistent and passes.
2. `formInputForCircom` detects `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length==0` and calls `formInputEmporiumMin`, producing public signals `[emporiumMessage, timeStamp, calldataHash]` [3](#0-2) .
3. `MainEVMCircuitMin` only constrains `message = Poseidon(messageSeed)`; `calldataHash` and `outTimeStamp` are declared as public inputs but never used in any constraint [4](#0-3) . The attacker picks an arbitrary `messageSeed`, computes `message`, and sets `emporiumMessage = message` — this is a valid witness requiring no knowledge of any nullifier, root, or balance. `verifyProof` therefore succeeds trivially.
4. `rootHashExists(circomData.rootHashHinkal, ...)` only checks that a *previously published* root exists in `roots[]` (or that root `0` is valid pre-genesis); it does not tie the proof to any specific note the attacker owns, since no nullifiers are ever supplied/checked (`inputNullifiers.length == 0`) [5](#0-4) .
5. `Hinkal._externalTransact` computes `deltaAmountChanges` over the empty `erc20TokenAddresses` array (empty result) and calls `EmporiumUpgradeable.runAction(circomData, [])` [6](#0-5) .
6. Inside `runAction`, `balancesBefore = getBalancesForArray([])` is empty, `verifyWallet` marks the message used and returns immediately because `stack.signerAddress == address(0)` — **no signature, no maxFee, no deadline check at all** [7](#0-6) . The `ops` loop then executes `op.endpoint.call{value: op.value}(op.callData)` with `op.value` set to the entire ETH balance of the Emporium contract and `op.endpoint` an attacker-controlled contract [8](#0-7) . `balancesAfter` is again computed over the empty array, so the post-loop reconciliation `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` never runs and produces `utxoSet` of length 0 [9](#0-8) .
7. Back in `Hinkal.transact`, `oldBalances`/`newBalances` are computed over the same empty `erc20TokenAddresses`, so the drained ETH is invisible to the top-level conservation loop; `insertNullifiers([])` and `insertCommitments([], ...)` are no-ops, so no UTXO/commitment is ever created to account for the transferred value.

Existing guards fail specifically because: `dimensionsCheck` only checks internal array-length consistency, not that `tokenNumber > 0` is required whenever ETH is present in Emporium; the circuit does not bind `calldataHash`/action content to any deposit or note; and `verifyWallet`'s `signerAddress == 0` branch is meant for "self-authorized, checked via ZK proof" flows but the corresponding ZK proof (`MainEVMCircuitMin`) provides no such authorization when `erc20TokenAddresses` is empty.

### Impact Explanation
Any unprivileged caller can drain the entire ETH balance held by the `Emporium` contract to an address they control, in a single `transact()` call, with a trivially-generated proof and no real deposit, no spent nullifier, and no slippage/balance check ever evaluated. This is direct theft of funds in custody (any prior depositor's/relay's in-flight ETH sitting in Emporium), a proof/verification bypass (the circuit never binds actions to real value), and value never recorded as a UTXO or nullifier spend — squarely Critical.

### Likelihood Explanation
Preconditions are realistic and inexpensive: Emporium merely needs a non-zero ETH balance at call time, which naturally occurs whenever any legitimate multi-step swap/stateful op temporarily routes ETH through Emporium before completion, or when any user's transaction leaves residual ETH there. The attacker needs only: (1) ability to call `Hinkal.transact` (any EOA), (2) ability to generate a snarkjs proof for the tiny `MainEVMCircuitMin` circuit (public, no secret witness required beyond an arbitrary self-chosen seed), (3) any valid previously-published root hash (trivially obtainable, e.g. root `0` pre-genesis or any historical root), and (4) an attacker-deployed recipient contract. No signature, whitelisted relay, or privileged role is required. The attack is fully repeatable each time Emporium accumulates ETH.

### Recommendation
Reject `runAction` execution (or the entire `HINKAL_EMPORIUM_ACTION_ID` fast path) whenever `stack.ops` contains any non-zero `op.value`/state-changing calls but `circomData.erc20TokenAddresses.length == 0`; i.e., require `tokenNumber > 0` (and thus real slippage/balance-diff enforcement) for any Emporium action that can move value. Alternatively, compute `balancesBefore`/`balancesAfter` in `EmporiumUpgradeable.runAction` (and the mirrored check in `Hinkal.transact`) using the full set of assets actually touched by `stack.ops` (derived on-chain from calldata/`op.value`, not attacker-supplied `erc20TokenAddresses`), and enforce that any balance decrease is fully accounted for by `deltaAmountChanges`/`utxoAmount` regardless of the declared dimensions. Additionally, `verifyWallet` should not allow `signerAddress == address(0)` to bypass all authorization when `ops` contain non-zero `value` or arbitrary `callData` — some binding between the ZK proof's public signals and the concrete `ops`/value being executed is required (e.g., include a hash of `externalActionMetadata` or the ETH amount as a real circuit constraint, not just an off-chain `calldataHash` integrity check).

### Proof of Concept
Hardhat fork test plan:
1. Deploy the full stack (Hinkal, HinkalHelper, MerkleBase-derived Merkle, VerifierFacade with real `mainEVMCircuitMin0v4` verifier, `EmporiumUpgradeable` registered as `HINKAL_EMPORIUM_ACTION_ID` and set as `allowedRecipient`, and a `HinkalWallet`).
2. Fund Emporium with ETH via a legitimate prior call (e.g., a normal deposit-and-swap flow that leaves ETH on Emporium, or directly send ETH to Emporium in test setup to simulate the precondition) — record `emporium.balance == B > 0`.
3. Deploy `AttackerSink` contract with a `receive()` function.
4. Off-chain: pick random `messageSeed`, compute `message = poseidon([messageSeed])` with circomlibjs, generate a real snarkjs Groth16 proof for `MainEVMCircuitMin` with public inputs `[message, timeStamp, calldataHash]`.
5. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges=[]`, `onChainCreation=[]`, `slippageValues=[]`, `inputNullifiers=[]`, `outCommitments=[]`, `encryptedOutputs=[]`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: emporium}`, `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress:address(0), ops:[{endpoint: attackerSink, invokeWallet:false, value: B, callData:"0x"}]})`, `emporiumMessage = message`, `calldataHash` computed via `CircomDataBuilder.getHashedCalldata` logic, `rootHashHinkal = 0` (or any published root) with matching `rootHashHinkalIndex`, `dimensions.tokenNumber=0, nullifierAmount=0, outputAmount=0`.
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from an unprivileged EOA.
7. Assert: `emporium.balance == 0` and `attackerSink.balance == B` after the call, while `usedMessages[message] == true` and no new leaf/commitment was inserted into the Merkle tree (`m_index` unchanged) — i.e. `balanceDif` (real: `B` ETH moved) is never checked against `amountChanges + utxoAmount` (recorded: `0`), proving the equality is bypassed.
