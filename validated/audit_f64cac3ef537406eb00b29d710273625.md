The reported bug class is a **distributed-consensus non-determinism** issue: two Aptos validators executing the same block could promote different hot-state keys because `BlockHotStateOpAccumulator` capped promotions while iterating a `HashSet` whose enumeration order differs across processes/runs.

This bug class has no analog in alt.fun's Solidity contracts. EVM execution is deterministic by protocol design — every node executes the identical bytecode against identical state and gets identical results, so there is no cross-validator "different nodes picked different keys" failure mode to replicate. Searching the in-scope contracts (`Bonding.sol`, `Router.sol`, `Zap.sol`, `FeeVault.sol`) for anything resembling unordered-set accumulation with a cap applied post-hoc (the actual root cause in the report) turns up nothing: graduation math (`canGraduate`, `previewLtUntilGraduation`, `_prepareGraduationLiquidity`) operates on scalar stored reserves (`assetReserve`, `tokenReserve`, `Pair.k()`) via ordinary arithmetic, not on any set/map whose iteration order could vary. Since no unordered-collection-driven, order-dependent cap-and-drop mechanism exists anywhere in the in-scope contract surface, and EVM semantics preclude the validator-divergence failure mode described in the report, there is no valid analog to construct here.

        uint256 k = pair.k();

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {

            if (cappedReserveToken == 0) revert OverflowCapDegenerate();

    }
