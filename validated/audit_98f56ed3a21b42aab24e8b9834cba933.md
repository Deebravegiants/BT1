### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its `shop`, `topic`, `api_version`, and `webhook_id` values from HTTP headers, but `to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the raw request body. Consequently, `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity for a webhook whose HMAC never bound that value, breaking the equality "shop authenticated == shop the payload is attributed to."

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` treats a valid HMAC as sufficient proof of authenticity, then forwards `request.shop` — a header value entirely outside the signed content — to the handler: [3](#0-2) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the body or any authenticated value: [4](#0-3) 

Because the shop identity is carried in an unsigned header while only the body is signed, any body+HMAC pair that is valid for one shop remains HMAC-valid if replayed with a different `shop-domain` header value. An unprivileged user who can install the target app on their own store (a normal, unprivileged action for public apps) will receive genuine webhook deliveries — real `raw_body` + real `hmac` — for their own shop. They can then submit that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspected `shop`), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain, causing the host application to attribute attacker-controlled webhook content to a tenant the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: the value used to select which merchant's data/session a webhook affects (`shop`) is not part of what the HMAC guarantees. Any host application that uses `WebhookMetadata#shop` to route webhook effects (e.g., updating per-shop records, triggering per-shop side effects, or looking up a stored session by shop) can be made to apply attacker-supplied webhook bodies to an arbitrary other shop, i.e., cross-tenant access/injection using only the credentials of a normal app installer, with no access token or `client_secret` needed.

### Likelihood Explanation
Requires only unprivileged actions: install (or already have installed) the target public app on any shop to receive one legitimate webhook, capture its `raw_body`/`hmac`, and send a crafted HTTP request directly to the app's public webhook endpoint with a different `shop-domain` header. No TLS interception, no leaked secrets, and no privileged account are required — this matches the “field acted on but not covered by the HMAC” pattern directly.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content, or otherwise cryptographically tie the header-derived shop to the payload before trusting it — e.g., include `shop`/`topic` in `to_signable_string`, or require the host app to independently verify that the shop delivering the webhook matches a shop with an active, previously-established session/registration, rather than trusting the header value implicitly once HMAC-over-body passes.

### Proof of Concept
1. Attacker installs the target (public) Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`.
2. Shopify sends: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B` with the app's `client_secret`), header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker crafts their own HTTP POST directly to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (spoofed)
4. `ShopifyAPI::Webhooks::Request.new` parses these headers/body; `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(B) == H`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, and the host app applies attacker-controlled content (`B`) as if it originated from `victim-shop.myshopify.com`.
