### Title
Webhook shop-domain identity is unauthenticated and can be spoofed independently of the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic for a given shop as soon as `Utils::HmacValidator.validate` succeeds, but the HMAC only ever covers the raw request body, never the `shop-domain` header that the library hands to the app as the tenant identifier. The equality the gem implicitly claims — "HMAC-verified bytes == bytes that establish which shop this webhook is for" — does not hold, because the shop identity is read straight from an unauthenticated header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely outside of what is signed: [2](#0-1) 

`Registry.process` validates only the body's HMAC and then immediately forwards the caller-supplied `request.shop` (the header value) to the app's handler as the tenant identifier, with no cross-check that this shop matches the entity that actually produced the signed body: [3](#0-2) 

`Utils::HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (i.e., the body) matches the digest — it has no visibility into, and makes no claim about, the shop header: [4](#0-3) 

Because the signature covers `body` but the identity binding used downstream is `shop-domain header`, these two are not cryptographically bound to each other, which is exactly the pattern this scan is looking for: a field (`shop-domain`) that is acted upon (used as the tenant key delivered to `WebhookMetadata`) but not covered by the HMAC.

### Impact Explanation
A user who has legitimate access to any shop (e.g., a free/dev store they install the target app on) receives a genuinely-signed webhook from Shopify for their own shop. Because the digest is computed purely over the JSON body, that exact `(body, hmac)` pair remains valid no matter what the `shop-domain` header says. The attacker can replay the captured request to the same app endpoint while substituting a different shop's domain in the header. `Registry.process` will pass HMAC validation and call the host app's handler with `WebhookMetadata#shop` set to the forged domain while `body` is still the attacker's own shop data. Any app that uses the library's HMAC pass as authentication proof for `shop` (the natural assumption, since this is the entire authentication surface the gem exposes for webhooks) will misattribute data — for example, storing/loading merchant-scoped records, invoking `shop/redact` or `app/uninstalled` handling, or updating a session/store keyed by the spoofed shop — resulting in cross-tenant data injection or corruption. This satisfies the Critical bar for cross-tenant access.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one real, validly-signed webhook payload from Shopify for a shop the attacker controls (trivially available to anyone who installs a free/dev app), and (2) replaying it against the public webhook endpoint with a modified shop header — no access to `api_secret_key`, no TLS interception, and no privileged account is needed. This is realistic and directly reachable through the gem's own `Registry.process`/`Request` API as documented for webhook handling.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically verify it, instead of trusting the raw header:
- Include the shop domain (and ideally topic/webhook-id) in `to_signable_string`, matching what Shopify actually signs for the webhook delivery, or
- Cross-check `request.shop` against an independently-authenticated source (e.g., the shop associated with the currently registered webhook subscription/session) before invoking the handler, and
- Document explicitly that `WebhookMetadata#shop` is not itself authenticated by `Utils::HmacValidator.validate` and that consuming apps must not treat it as trusted tenant context by itself.

### Proof of Concept
1. Install the target app on shop `attacker-shop.myshopify.com`; trigger any webhook (e.g., `orders/create`) and capture the resulting HTTP request Shopify sends, including its valid `X-Shopify-Hmac-Sha256` header and JSON body.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. In the library:
   - `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object where `hmac` verifies against `@raw_body` only.
   - `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because the body is unchanged.
   - `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"` even though the body's actual data belongs to `attacker-shop.myshopify.com`. [3](#0-2) [5](#0-4)
