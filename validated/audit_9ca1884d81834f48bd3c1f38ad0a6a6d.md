### Title
Protocol treasury reward is silently discarded when the treasury account is also a validator, causing minted tokens to be lost - (File: chain/epoch-manager/src/reward_calculator.rs)

### Summary
`RewardCalculator::calculate_reward` seeds a `HashMap<AccountId, Balance>` with the protocol treasury's share first, then iterates over all validators and inserts each validator's reward into the *same* map keyed by `AccountId`. If the protocol treasury account is also a chunk/block producer in that epoch (nothing in the code prevents this), the validator-reward insert overwrites the treasury insert for that key, exactly the "duplicate key overwrites the first entry" bug class described in the reference report (there: a token address appearing twice in a reward list; here: an account id appearing twice as a map key).

### Finding Description
The reward map is built like this: [1](#0-0) 

```
let mut res = HashMap::new();
...
res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury);
if num_validators == 0 { return (res, Balance::ZERO); }
let epoch_validator_reward = epoch_total_reward.checked_sub(epoch_protocol_treasury).unwrap();
let mut epoch_actual_reward = epoch_protocol_treasury;
``` [2](#0-1) 

Then, for every validator in `validator_block_chunk_stats`: [3](#0-2) 

```
for (account_id, stats) in validator_block_chunk_stats {
    ...
    res.insert(account_id, reward);
    epoch_actual_reward = epoch_actual_reward.checked_add(reward).unwrap();
}
(res, epoch_actual_reward)
``` [4](#0-3) 

If `account_id == self.protocol_treasury_account` (i.e., the treasury account is itself a validator that produced blocks/chunks in the epoch — a state fully reachable since nothing restricts a treasury account from staking), the `res.insert(account_id, reward)` call **overwrites** the earlier `res.insert(self.protocol_treasury_account.clone(), epoch_protocol_treasury)` entry instead of summing them. The final map contains only `reward` for that account, silently dropping `epoch_protocol_treasury`.

Critically, `epoch_actual_reward` (the "minted amount" returned alongside `res` and later stored in `EpochInfo::minted_amount`, which feeds into total-supply accounting — see `core/primitives/src/epoch_info.rs` and `chain/chain/src/chain.rs`) still includes **both** `epoch_protocol_treasury` and the validator `reward` added together, because it is accumulated independently of the `res` map. So the protocol's total-supply bookkeeping counts the treasury reward as minted, while the returned per-account map (which downstream code uses in `runtime/runtime/src/lib.rs::update_validator_accounts` to actually credit `account.locked()` / `account.amount()`) never credits it to any account: [5](#0-4) 

This is the same root-cause pattern as the referenced Sherlock finding H‑3: a data structure keyed by an identifier (token address there, `AccountId` here) is built by naively inserting/overwriting entries from two separate sources (bribes+rewards there, treasury+validator-reward here) without checking for a collision, causing the first entry's value to be permanently lost while the aggregate/expected total still counts it.

### Impact Explanation
The tokens attributed as the protocol treasury's epoch reward are minted into total supply accounting (`minted_amount`) but never actually credited to any account balance, since the map entry that would have applied that credit is overwritten by the treasury account's ordinary validator reward. This produces a permanent, unrecoverable loss of newly minted tokens and an unreconciled total-supply divergence versus the sum of on-chain account balances — a direct token-loss / state-divergence bug reachable purely through normal protocol operation (treasury account choosing to stake and become a validator), not requiring any malicious actor.

### Likelihood Explanation
This requires only that the account configured as `protocol_treasury_account` in genesis config also stakes and becomes a block/chunk producer in some epoch — a legitimate, permissionless action available to any account, including the treasury account itself. There is no validation anywhere in `RewardCalculator::calculate_reward`, `chain/epoch-manager/src/lib.rs`, or `chain/epoch-manager/src/validator_selection.rs` preventing this collision. On live networks, the actual treasury account is typically not a validator, which likely explains why this has not surfaced, but nothing in the protocol code enforces or documents this as an invariant, so the bug is a latent, silently-triggerable loss-of-funds condition.

### Recommendation
In `RewardCalculator::calculate_reward`, use `entry(...).and_modify(|v| *v = v.checked_add(reward).unwrap()).or_insert(reward)` (or equivalent) instead of a blind `res.insert(account_id, reward)`, so that if the protocol treasury account is also a validator, both reward components are summed rather than one overwriting the other. Additionally, add an explicit invariant check/test asserting that `res.values().sum() == epoch_actual_reward` to catch this class of bug at the source, mirroring the recommendation from the referenced report to deduplicate/aggregate before inserting into a map keyed by a potentially colliding identifier.

### Proof of Concept
1. Configure genesis such that `protocol_treasury_account = "treasury.near"`.
2. Have `treasury.near` submit a `Stake` transaction and become an active block/chunk producer for epoch `T`.
3. At the end of epoch `T`, `EpochManager::compute_validators_to_reward_and_kickout` builds `validator_block_chunk_stats` that includes `treasury.near` as a validator entry.
4. `RewardCalculator::calculate_reward` first inserts `res["treasury.near"] = epoch_protocol_treasury`, then in the validator loop re-inserts `res["treasury.near"] = reward` (the validator's own uptime-based reward), overwriting the treasury amount while still adding `epoch_protocol_treasury` into `epoch_actual_reward`.
5. `update_validator_accounts` in `runtime/runtime/src/lib.rs` credits `treasury.near`'s locked balance only with `reward`, not `reward + epoch_protocol_treasury`.
6. Total supply (driven by `minted_amount`/`epoch_actual_reward`) increases by `epoch_protocol_treasury + reward`, but the sum of all account balance increases is short by `epoch_protocol_treasury` — those tokens are permanently unaccounted for/lost.
