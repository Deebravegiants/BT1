### Title
Webhook HMAC Does Not Cover the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before dispatching webhook data to the app's handler, but the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken directly from unauthenticated HTTP headers — are never part of the signed data, so any request bearing a body/HMAC pair that is valid for the shared app `client_secret` can be replayed with an arbitrary `x-shopify-shop-domain` header and will be processed as if it belongs to that shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` trusts `Utils::HmacValidator.validate(request)` as the sole authenticity check, then forwards `request.shop` (and `request.topic`) straight to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [4](#0-3) 

Because the app's `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any shop — including one controlled by the attacker — can legitimately trigger a webhook and thereby obtain a `(raw_body, hmac)` pair that is valid for that same secret. Nothing in `HmacValidator` or `Registry.process` binds that pair to the `x-shopify-shop-domain` header. An attacker can therefore capture a genuine, validly-signed webhook delivery from their own shop and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop. The signature check still passes because the signable string never included the shop, so `Registry.process` calls the handler with `WebhookMetadata` claiming the data belongs to the victim shop: [5](#0-4) 

This breaks the identity binding `authenticated_shop == claimed_shop` that `Registry.process`'s "verify the request did indeed come from Shopify" guarantee implies (see doc claim): [6](#0-5) 

### Impact Explanation
Any app that keys per-tenant state (session lookups, order/customer records, entitlements) off `WebhookMetadata#shop` as returned by this gem's `Registry.process` can have attacker-controlled webhook content attributed to a different, victim shop, without the attacker ever needing that victim's credentials. This is a cross-tenant confusion vulnerability rooted entirely in this gem's webhook verification logic — the gem asserts the payload is authentic and shop-attributed, but the "shop" attribution is never authenticated.

### Likelihood Explanation
Any developer or business account can freely install a public app to obtain a legitimate `(body, hmac)` pair signed with the same `client_secret` used for all installations, then replay it toward the target endpoint with a modified `shop-domain` header. No access token, session, or leaked secret is required — only the app's public webhook endpoint URL, which is inherently discoverable/config'd by the merchant-developer. This makes the likelihood high for any app relying on `Registry.process`/`Request#shop` for tenant attribution.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed payload used for verification, or otherwise cryptographically bind the shop identity to the HMAC-covered bytes before trusting `request.shop`. At minimum, `Utils::HmacValidator` should not be the only gate — `Registry.process` should cross-check the claimed shop against session/store state already known to belong to that HMAC-body pairing, or the gem should document clearly that `request.shop` is unauthenticated and must not be trusted for tenant attribution without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (any shop can install a public app).
2. Attacker triggers a subscribed webhook topic (e.g. `orders/create`) on their own shop, capturing the exact `raw_body`, `x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers Shopify sends — this HMAC is valid because it's computed with the app's shared `client_secret`, not anything shop-specific.
3. Attacker replays this exact request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes HMAC over `raw_body` only — it still matches, so validation succeeds.
5. The registered handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)`, causing the host application to process attacker-supplied data as if it originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
