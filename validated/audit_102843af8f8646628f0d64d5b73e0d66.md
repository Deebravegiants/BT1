The reported issue is specific to ERC20's `approve(spender, value)` semantics on Ethereum, where calling `approve` twice creates a race condition allowing a spender to front-run and use both the old and new allowance. This program is a Solana on-chain program with no ERC20-style `approve`/allowance model. The only token-related helpers exposed via `Invokers` are `token_burn`, `token_close_with_authority`, `token_mint_to`, `token_transfer`, `token_transfer_with_authority`, `token_set_authority`, and lamport-wrapping helpers [1](#0-0) ; none of them construct or invoke an `spl_token::instruction::approve` (delegate) instruction. All in-scope reachable instructions (Initialize2, Deposit, Withdraw, and the swap variants) move funds exclusively via `token_transfer`/`token_transfer_with_authority` under PDA authority signed seeds, not via a user-revocable allowance mechanism [2](#0-1) [3](#0-2) . Additionally, the initialization path explicitly rejects vaults that have any delegate set (`amm_coin_vault.delegate.is_some()` / `amm_pc_vault.delegate.is_some()`), further confirming that delegate/allowance-based transfers are not part of this program's fund-movement model [4](#0-3) . Since there is no approve/allowance analog reachable by an unprivileged swapper, LP, or pool creator in this codebase, the ERC20 approve front-running bug class does not map to any concrete vulnerability here.
