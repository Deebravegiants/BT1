### Title
Stale delegate authorization reactivates after position NFT ownership returns - (File: contracts/controller/src/storage/account.rs)

### Summary

Controller account delegates are bound to the granting owner’s address, but not to an ownership epoch or transfer generation. A transfer disables the previous owner’s delegate grant while another address owns the position NFT, but the same stored grant becomes active again if that NFT later returns to the original owner. The reactivated delegate can then call owner-or-delegate endpoints such as `borrow` or `withdraw` and direct proceeds to itself.

### Finding Description

`DelegateGrant` explicitly stores `granted_by` and a delegate list, with no ownership-generation field; its documented behavior is that the grant “re-arms” if the NFT returns to `granted_by` before another owner overwrites or removes it. [1](#0-0) 

Account authorization accepts a caller when it is either the current NFT owner or an active position manager present in `get_delegates(account_id, owner)`. [2](#0-1)  Because ownership is resolved from the current NFT owner, transferring the token back to the original grantor makes the old `granted_by` value current again without requiring a fresh `add_delegate` authorization. [3](#0-2) 

The revived authority is security-sensitive: `borrow` authenticates the delegate, permits an arbitrary `to` recipient, and then settles pool assets to that recipient. [4](#0-3)  Similarly, `withdraw` permits an owner or delegate to withdraw collateral to an arbitrary recipient, subject to post-withdrawal solvency. [5](#0-4) 

This is analogous to executing an authorization with a stale logged-out session: leaving and re-entering the account does not permanently invalidate the old authorization.

### Impact Explanation

A formerly delegated position manager can steal assets after the position returns to the grantor. It can withdraw collateral to its own address or borrow pool liquidity to its own address up to the account’s solvency limits. This results in theft of user collateral and can leave the account with protocol debt.

### Likelihood Explanation

The attack requires an active delegate grant that survived an intermediate NFT ownership period and was not overwritten or removed by that intermediate owner. Position NFTs are transferable by design, and account custody may move through sales, contracts, operators, accidental transfers, or temporary migration arrangements. If ownership returns to the original grantor, no new signature from that owner is needed to restore the old delegate’s authority.

### Recommendation

Bind delegate grants to an ownership epoch rather than only the owner address. Track a per-account `owner_epoch` or `last_owner` in controller storage; whenever account loading observes a different NFT owner, increment the epoch and invalidate or delete `Delegates(account_id)`. Require both `granted_by == current_owner` and `grant_epoch == owner_epoch`. Alternatively, emit an NFT transfer notification or otherwise ensure every ownership transition purges stale delegate state.

Add a regression test covering:

1. Owner grants an active delegate.
2. Owner transfers the NFT to another address.
3. The NFT returns to the original owner without a delegate-list mutation.
4. The old delegate’s `borrow` and `withdraw` calls revert with `NotAuthorized`.

### Proof of Concept

1. Alice supplies collateral through `controller::supply(caller=alice, account_id=0, ...)`, creating account `A` and NFT token `A`.
2. Governance has already registered manager `M` as an active position manager.
3. Alice calls `controller::add_delegate(caller=alice, account_id=A, delegate=M)`.
4. Alice calls `position-nft::transfer(from=alice, to=bob, token_id=A)`. While Bob owns the NFT, Alice’s grant is inactive because `owner != grant.granted_by`.
5. Bob later transfers token `A` back to Alice and performs no `add_delegate` or `remove_delegate` call.
6. The controller resolves Alice as the owner again. The stored `DelegateGrant { granted_by: alice, delegates: [M] }` becomes live again.
7. `M` calls `controller::borrow(caller=M, account_id=A, borrows=[debt_asset], to=Some(M))` or `controller::withdraw(..., to=Some(M))`; `require_owner_or_delegate` accepts `M`, and the assets are paid to `M`.

```rust
/// Accepts the owner or a registered, active manager delegated by that owner.
pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```

```rust
pub(crate) fn process_borrow(

    caller: &Address,
    account_id: u64,
    borrows: &Vec<HubPayment>,
    to: Option<Address>,
) {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_positive_payments(env, borrows);
```

```rust
/// Withdraws for an authorized owner/delegate and checks post-pool solvency.
/// Zero requests withdraw all; returns the pool's actual payouts per asset.
pub(crate) fn process_withdraw(
    env: &Env,
    caller: &Address,
    account_id: u64,
    withdrawals: &Vec<HubPayment>,
    to: Option<Address>,
) -> Vec<HubPayment> {
    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);
    require_owner_or_delegate(env, account_id, caller, &account.owner);

    let recipient = to.unwrap_or_else(|| caller.clone());
    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_payments(env, withdrawals, payments::ZeroLeg::MeansAll);

    let paid = settle_withdraw(env, &mut account, &recipient, &aggregated, &mut cache);
    let _ = enforce_post_pool_solvency(env, &mut cache, &mut account);
```
