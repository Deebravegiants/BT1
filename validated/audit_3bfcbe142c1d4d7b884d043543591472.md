### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature it validates against only covers the raw request body, not this header. This breaks the identity binding `HMAC-verified bytes == bytes acted on for tenant identity`, allowing an attacker who can produce (or replay) one valid `(body, hmac)` pair to relabel that webhook as belonging to any other shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `#shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (body only) and `request.hmac` (also derived from a header), and then forwards `request.shop` — untouched by the HMAC check — straight into the handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to `verifiable_query.hmac`; it never incorporates `shop`: [4](#0-3) 

Because a single Shopify app uses one `client_secret` (`Context.api_secret_key`) to sign **every** shop's webhooks, any shop that has the app installed can generate a legitimately-HMAC-valid `(body, hmac)` pair by triggering an event in its own store. The equality that should hold is:

`shop_bound_by_signature == shop_used_for_tenant_routing`

but here `shop_bound_by_signature` doesn't exist at all — the signature binds only the body — while `shop_used_for_tenant_routing = request.shop`, taken from an attacker-controllable header. An attacker (an unprivileged merchant who has the app installed on their own shop) can capture a valid webhook request they legitimately received/triggered, then replay the identical body+HMAC to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain. The signature still validates (it only checks the body), and `WebhookMetadata.new(... shop: request.shop ...)` hands the forged victim shop identity to the app's handler.

### Impact Explanation
This is a cross-tenant confusion vector at the trust boundary of a multi-tenant Shopify app: the app processes attacker-supplied data (their own webhook body/content) under the identity of a different merchant. Depending on how the host application's `WebhookHandler` uses `shop` (e.g., updating per-shop settings, redacting/writing customer data, revoking access, billing state), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's records — satisfying the Critical "cross-tenant access" impact category, since the binding between the cryptographically verified bytes and the tenant identifier is absent.

### Likelihood Explanation
Likelihood is realistic but requires two things the attacker controls: (1) they must operate their own valid shop installation of the target app to obtain one authentic `(body, hmac)` pair, and (2) they must be able to send an HTTP request directly to the app's webhook endpoint with a modified `shop-domain` header (trivial, since it's just an HTTP header, not a network-level or TLS-derived value). No access token, `client_secret`, or privileged credentials are needed — only a normal merchant install of the app, which is an "unprivileged internet user" from the perspective of other tenants.

### Recommendation
Include the shop domain (and topic/webhook-id) in the signed payload verification, or independently verify that the `shop-domain` header matches a shop your application expects to receive that specific webhook for (e.g., cross-check against the currently registered webhook subscription/shop mapping) before trusting `request.shop`. At minimum, document that `shop` is not integrity-protected by the module's `HmacValidator` and require host applications to bind it via additional server-side validation (e.g., look up the webhook by `webhook_id`/registration rather than trusting the header shop for authorization decisions).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store, `attacker.myshopify.com`.
2. Attacker triggers a webhook event (e.g., updates a product) causing Shopify to POST a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid hmac of body>`, and the JSON body.
3. Attacker captures this exact HTTP request (body + HMAC header unchanged) and replays it to the same endpoint, only changing `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (the raw body only) — this still matches the received HMAC because the shop header was never part of the signed content: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to process attacker-controlled data attributed to the victim's tenant. [6](#0-5)

          received_signature = verifiable_query.hmac
