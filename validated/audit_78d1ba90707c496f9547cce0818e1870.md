Confirmed: the `shop-domain` header flows directly into `WebhookMetadata.shop` passed to the app's handler, with no separate verification tying it to the HMAC-signed payload.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then trusts the `shop-domain` header — which is never included in that signature — to identify which merchant/tenant the webhook belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0)  while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to that value: [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes the signature over `to_signable_string` (the body only) and compares it to the `hmac` header: [3](#0-2)  and [4](#0-3) . After the HMAC check passes, `request.shop` (the unauthenticated header value) is forwarded straight into the handler via `WebhookMetadata.new(... shop: request.shop ...)`: [5](#0-4) .

This breaks the identity binding: `HMAC-verified-shop == shop-acted-upon` does not hold. The HMAC only proves "this body was signed by the app's `client_secret`," not "this body belongs to shop X." Since the same `client_secret` is used to sign webhooks for every shop that has the app installed, any merchant who installs the app on their own store receives legitimate webhooks with a valid HMAC over a body they fully control the origin of. That attacker can capture one such `(raw_body, hmac)` pair from their own shop's webhook delivery and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because the header is not part of the signed content, and the handler receives `WebhookMetadata` claiming the payload is for the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged app-installing merchant can make the host application process webhook data while asserting it belongs to a different merchant. Depending on how the host app's webhook handler uses `shop` (e.g., to look up/update per-shop records, uninstall/redact data, or trigger tenant-scoped side effects), this can lead to cross-tenant data corruption or actions being taken against a victim shop's account — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires an attacker to install the target app on their own (even free/dev) store — no `api_secret_key`, access token, or privileged account is needed. This is a realistic "unprivileged internet user" scenario for any app that accepts installs from the public app store or allows free trials.

### Recommendation
Include the shop identity in the signed content the HMAC is validated against, or otherwise cryptographically bind the `shop-domain` header to the payload before trusting it (e.g., include it in `to_signable_string`, or cross-check `request.shop`/`webhook_id` against a value looked up server-side from Shopify rather than trusting the header). At minimum, document that consuming applications must independently validate `request.shop` against known/installed shops before using it, since the gem does not authenticate it.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC secret [4](#0-3) .
5. `handler.handle` is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"` [5](#0-4) , causing the host application to process attacker-supplied data under the victim's tenant identity.
