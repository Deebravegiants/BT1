Confirmed vulnerability. `ValidatePodGroupUpdate` in `pkg/apis/scheduling/validation/validation.go` only validates `ObjectMeta` on update and does **not** enforce immutability of `Spec.Priority` or `Spec.PriorityClassName`, unlike the pod case where the code comment explicitly states "API validation prevents mutations to Priority and PriorityClassName." Combined with the `Admit` dispatcher in `plugin/pkg/admission/priority/admission.go` only calling `admitPodGroup` on `admission.Create` (never on `admission.Update`), a PodGroup's `spec.priority` and `spec.priorityClassName` can be freely rewritten via update/patch with no admission-time re-computation and no API-level immutability check.

### Title
Unvalidated update path allows mutation of PodGroup `spec.priority`/`spec.priorityClassName` after creation - (File: `plugin/pkg/admission/priority/admission.go`)

### Summary
The `Priority` admission plugin's `Admit` function only invokes `admitPodGroup` for `admission.Create` operations (`plugin/pkg/admission/priority/admission.go:114-118`), and `ValidatePodGroupUpdate` (`pkg/apis/scheduling/validation/validation.go:88-90`) only validates `ObjectMeta` changes, leaving `Spec.Priority` and `Spec.PriorityClassName` completely unguarded on update/patch. This lets a user with only `update`/`patch` permission on `podgroups` set an arbitrary `spec.priority` value or reference an arbitrary `PriorityClassName` after creation, bypassing the priority-class-derived value the plugin computed at create time.

### Finding Description
`Admit` routes `podGroupResource` requests to `admitPodGroup` only `if operation == admission.Create` [1](#0-0) . For `admission.Update`, no priority-related admission logic runs at all, unlike `admitPod`, which explicitly re-derives/preserves `Spec.Priority`/`Spec.PreemptionPolicy` on update [2](#0-1) . The pod path's safety additionally relies on the stated invariant that "API validation prevents mutations to Priority and PriorityClassName" [3](#0-2) .

For PodGroup, the corresponding validation function `ValidatePodGroupUpdate` only calls `ValidateObjectMetaUpdate` and performs no immutability check on `Spec.Priority` or `Spec.PriorityClassName` [4](#0-3) . Compare this to `ValidatePriorityClassUpdate`, which explicitly enforces immutability of `Value` and `PreemptionPolicy` on `PriorityClass` objects [5](#0-4) ; no analogous protection exists for `PodGroup`.

As a result: an attacker with RBAC `update`/`patch` on `podgroups` (a resource they legitimately own/created) can submit an update request setting `spec.priority` to any integer or `spec.priorityClassName` to any priority class name (including higher-privileged ones), and neither the admission plugin nor object validation will reject or recompute it — the value is persisted as-is.

### Impact Explanation
This breaks the invariant enforced at create time (that `spec.priority` must match the value derived from the referenced/default `PriorityClass`), allowing a low-privileged tenant to escalate a PodGroup's scheduling priority/preemption behavior after creation without needing `use` verb authorization on a higher-priority `PriorityClass` resource (which is normally required to prevent unauthorized use of privileged priority classes via `ClusterRoleAggregation`/priority-class RBAC). This matches Admission bypass -> control of a protected field/identity (privilege escalation / isolation escape), since PodGroup priority directly affects scheduling and preemption ordering, letting workloads unfairly preempt others or evade eviction in resource pressure scenarios.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs standard namespace-scoped RBAC to `update`/`patch` a `podgroups` object they can already create (typical for a namespace-scoped workload owner), and the `GenericWorkload` feature gate enabled (gating `admitPodGroup` itself). No cluster-admin or special role is required. The exploit is a single API `update`/`patch` call, fully repeatable, and requires no other component compromise.

### Recommendation
- In `Admit`, also route `admission.Update` for `podGroupResource` (and `compositePodGroupResource`) through the priority admission logic, mirroring `admitPod`'s update handling: preserve/re-derive `Spec.Priority`/`Spec.PriorityClassName`/`Spec.PreemptionPolicy` from the old object rather than trusting attacker-supplied values.
- Add immutability checks in `ValidatePodGroupUpdate` (and `ValidateCompositePodGroupUpdate`) for `Spec.Priority`, `Spec.PriorityClassName`, and `Spec.PreemptionPolicy`, analogous to `ValidatePriorityClassUpdate`'s handling of `Value` and `PreemptionPolicy`.

### Proof of Concept
Unit test in `plugin/pkg/admission/priority/admission_test.go`:
1. Enable `GenericWorkload` feature gate; create a `PriorityClass` "high" with value 1000000 and a default `PriorityClass` "default" with value 1000 via the lister.
2. Create a PodGroup via `Admit` with `admission.Create`, no `PriorityClassName` set — assert plugin sets `spec.priority=1000`, `spec.priorityClassName="default"`.
3. Submit an `admission.Update` on the same PodGroup with `oldObject` = the created PodGroup and new object setting `spec.priorityClassName="high"` (or directly `spec.priority=1000000`) via `p.Admit(ctx, attrs, o)` with `operation=admission.Update`.
4. Assert: currently `Admit` returns `nil` (no error) and the mutated priority value is unchanged from attacker input — i.e., no recomputation/rejection occurs, proving the object as persisted (post `ValidatePodGroupUpdate`) contains the attacker-controlled `spec.priority`/`spec.priorityClassName`.
5. Expected (fixed) behavior: either the admission plugin overwrites the attacker's value back to the original, or `ValidatePodGroupUpdate` rejects the change with a "field is immutable" error.

// ValidatePriorityClassUpdate tests if required fields in the PriorityClass are
// set and are valid. PriorityClass does not allow updating name, value, and preemptionPolicy.
func ValidatePriorityClassUpdate(pc, oldPc *scheduling.PriorityClass) field.ErrorList {
	// name is immutable and is checked by the ObjectMeta validator.
	allErrs := apivalidation.ValidateObjectMetaUpdate(&pc.ObjectMeta, &oldPc.ObjectMeta, field.NewPath("metadata"))
	// value is immutable.
	if pc.Value != oldPc.Value {
		allErrs = append(allErrs, field.Forbidden(field.NewPath("value"), "may not be changed in an update."))
	}
	// preemptionPolicy is immutable.
	allErrs = append(allErrs, apivalidation.ValidateImmutableField(pc.PreemptionPolicy, oldPc.PreemptionPolicy, field.NewPath("preemptionPolicy"))...)
	return allErrs
}
