### Title
Missing length check before indexing `request.body[0]` allows any dispatched message to permanently brick delivery of intent-gateway cross-chain requests - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents.onAccept` reads the first byte of the incoming ISMP `PostRequest.body` to determine the `RequestKind` before performing any authentication or length validation, mirroring the root cause of CVE-2024-57802 (netrom accessing `skb->data` before checking `skb->len`): a message dispatcher path decodes attacker-influenced bytes without first checking that the buffer is long enough to be indexed.

### Finding Description
`onAccept` is the `HyperApp` callback invoked by the ISMP host (via `HandlerV2.handlePostRequests` → `host.dispatchIncoming`) whenever a proven `PostRequest` targets this contract. The very first operation on the request body is: [1](#0-0) 

```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    _checkRelayer(incoming.relayer);
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
    ...
```

`incoming.request.body` is arbitrary calldata supplied by whoever dispatched the original `PostRequest` on the *source* chain — any unprivileged account/contract can call `IDispatcher.dispatch` there with `dest` set to this gateway's address and `body = ""` (zero length). Unlike the C/Rust case referenced in the CVE, Solidity's compiler-inserted bounds check on `bytes calldata` indexing will `panic`/revert rather than read uninitialized memory, so this is not a memory-safety bug — but it still fully satisfies the underlying bug class ("check buffer length before accessing it") and produces the same operational consequence: **the message can never be delivered**. `_checkRelayer` and `_authenticate` (source-address checks) both run *after* the length-unsafe read, so there is no gate that prevents an arbitrary, unauthenticated sender from constructing a request that trips this revert.

Because the ISMP request commitment (hash of source/dest/nonce/body/timeouts, computed on the source chain and immutably tied to the message) is what relayers prove membership of, the empty-body payload is baked into the request forever. Every relayer attempt to call `handlePostRequests`/`handleGetResponses` for that commitment will revert identically, and the request cannot be re-encoded with different bytes since it is already committed on the source state machine.

### Impact Explanation
- Any request routed to this specific `IHandler` will be undeliverable, and the destination gateway can never accept it via `onAccept`; the message can only ever reach timeout handling (`onPostRequestTimeout`), so it is a route-availability ("route unable to deliver messages") defect rather than a fund-theft path.
- Because relayers batch multiple messages per call (see `HandlerV2.handlePostRequests`/`handleGetResponses` loops), a single malformed/malicious commitment mixed into a batch will cause the entire batch transaction to revert unless the relayer proactively filters it out, degrading relayer throughput and creating a griefing vector against honest cross-chain traffic destined for the intent gateway.
- This does not appear to lead to memory corruption, forged messages, or unbacked minting — Solidity's automatic bounds check prevents that class of exploitation, which limits the severity below the original kernel CVE (network-reachable OOB read/info-leak). The residual issue is availability/DoS of the intent-gateway delivery path, and possibly relayer fee loss if such requests are included in gas-limited batches that then always fail.

### Likelihood Explanation
Triggering this requires only: (1) an unprivileged actor calling the standard, permissionless `dispatch`/`dispatchPost` entry point on any source chain with `dest` = the intent gateway's known/predictable address and an empty `body`, and (2) a relayer submitting the resulting proof through the normal `HandlerV2` flow. No privileged role, governance, or compromised key is needed — this is reachable from a single unprivileged dispatched request, consistent with the required threat model.

### Recommendation
Validate `incoming.request.body.length > 0` (and any other minimum-length assumptions for each `RequestKind`'s subsequent `abi.decode`/slice operations) before indexing or slicing `body`, and revert with a clear, catchable error (e.g., `InvalidInput()`) prior to any state-dependent side effects. Apply the same length check symmetrically wherever `body[1:]` is passed to `abi.decode` for `WithdrawalRequest`, `Deployment`, `ParamsUpdate`, `SweepDust`, and `Execute`, since `abi.decode` on a body shorter than the expected struct will similarly always revert for that specific committed message. Consider also moving `_authenticate`/source checks ahead of any speculative parsing so malformed/unauthenticated payloads fail fast and uniformly.

### Proof of Concept
1. On a source state machine, call the standard ISMP `dispatch`/`dispatchPost` function (available to any account) with:
   - `dest` = state machine hosting `ExtrinsicIntents`
   - `to` = the deployed `ExtrinsicIntents` (intent gateway) address
   - `body` = `0x` (empty bytes)
2. Wait for/obtain the consensus + state proof for this request as any relayer normally would.
3. Submit the corresponding `PostRequestMessage` to `HandlerV2.handlePostRequests` on the destination chain.
4. `host.dispatchIncoming` invokes `ExtrinsicIntents.onAccept`, which executes `uint8(incoming.request.body[0])` on a zero-length `bytes calldata` and reverts (`Panic(0x32)`), aborting the whole `handlePostRequests` call (and any other legitimate requests batched with it).
5. Because the request commitment (including the empty body) is fixed by the source-chain dispatch, no future call with different body bytes can satisfy this request's hash — the message is permanently undeliverable except via timeout.

Note: I was not able to view the full `HandlerV2.sol` "handlePostRequests" body or the exact statements between `body[0]` and `_authenticate`/subsequent branches in this final pass (tool calls were exhausted), so the exact ordering of `_checkRelayer`/`_authenticate` relative to `body[0]` access and the precise batching/loop behavior of `handlePostRequests` for post requests (as opposed to `handleGetResponses`, which was inspected) should be re-confirmed against the current source before treating this as launch-ready.
