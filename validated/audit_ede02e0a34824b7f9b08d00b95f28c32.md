### Title
Untracked-token drain via `EmporiumUpgradeable.runAction`/`handleOut` — arbitrary `EmporiumOperation` calls can move value in tokens absent from `circomData.erc20TokenAddresses` with zero on-chain accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` only snapshots balances via `getBalancesForArray(circomData.erc20TokenAddresses)` before/after executing attacker-supplied `stack.ops` [1](#0-0) , and `handleOut` only creates/returns a UTXO (and only sweeps out) a token that is present at index `i` in that same array [2](#0-1) . Since `stack.ops[i].endpoint.call(op.callData)` is executed with no allowlist on `endpoint` (only the `callHinkalWallet`/`doSendToRelay` selectors are blocked for the stateless path) [3](#0-2) , an attacker can include an operation that moves or drains a token never listed in `circomData.erc20TokenAddresses`; that movement is invisible to every downstream equality check.

### Finding Description
The equality the protocol relies on is: for every tracked token `i`, `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` in `Hinkal.sol` [4](#0-3) , and inside Emporium, `balanceChange` (after adjusting for pre-funded `deltaAmountChanges`) must be `>= 0` and is swept via `handleOut` [5](#0-4) . Both equalities are computed strictly over `circomData.erc20TokenAddresses`, an array fully chosen by the caller. `stack.ops` is decoded from `circomData.externalActionData.externalActionMetadata` [6](#0-5)  and each op's `endpoint`/`callData` is executed as an arbitrary low-level call from the Emporium contract, with no restriction that `op.endpoint` be one of `circomData.erc20TokenAddresses` or any registered router.

While `circomData.externalActionData` (containing `externalActionMetadata`) is bound into `calldataHash`, which is checked against `getHashedCalldata()` and fed to the circuit as a public input [7](#0-6) [8](#0-7) , this only prevents a third party (e.g. a relay) from tampering with the ops after the prover signed them — it places no restriction on what ops the prover (the attacker themselves, per the threat model) chooses to author in the first place. Nothing in the circuit or Solidity constrains `op.endpoint`/`op.callData` to only touch tokens in `erc20TokenAddresses`.

Concretely, any token balance the Emporium contract happens to hold that is not included in a given transaction's `erc20TokenAddresses` (e.g. dust/rewards left over from a prior swap operation whose output token the depositor forgot to list, or any ERC20/ETH sent to Emporium outside the tracked path) can be extracted by a subsequent, unrelated attacker: they submit a valid `transact()` call (with their own UTXO/proof, satisfying `performHinkalChecks`, `verifyProof`, `rootHashExists`) whose `erc20TokenAddresses` simply omits that token, and include an `EmporiumOperation` with `endpoint = <dust token>` and `callData = transfer(attacker, amount)`. Because that token address never appears in `circomData.erc20TokenAddresses`, it is never included in `balancesBefore`/`balancesAfter` in `runAction`, never appears in `handleOut`, and never appears in the `Hinkal.transact` balance-diff loop — so the transfer succeeds and none of the `require` statements ("`BalanceChangeShouldBePositive`", the slippage `require`, or the "Balance Diff Should be equal…" `require`) ever observe it.

An even more severe variant exists: `CircomDataBuilder.formInputForCircom` special-cases `HINKAL_EMPORIUM_ACTION_ID` with `erc20TokenAddresses.length == 0`, routing to `formInputEmporiumMin`, a minimal circuit requiring only `emporiumMessage`, `timeStamp`, `calldataHash` [9](#0-8) . With an empty `erc20TokenAddresses` array, both the `Hinkal.transact` balance-diff loop and the `runAction`/`handleOut` balance snapshots iterate zero times, so `stack.ops` executes with essentially no economic constraint from the token-balance accounting at all (subject only to the unrelated root-hash / signature checks, which do not police what tokens move).

### Impact Explanation
Any value the Emporium contract holds in a token outside the current transaction's tracked `erc20TokenAddresses` set — dust, unclaimed swap remainders, protocol/relay-routed leftovers, or funds mistakenly sent to the contract — can be moved or exfiltrated by any unprivileged attacker without triggering any of the protocol's balance, slippage, or UTXO-equality checks. This matches the High-severity category "theft or permanent freezing of protocol/relay fees or third-party value routed through Emporium," and moving value a wallet owner/prover never authorized. The action is repeatable for every occurrence of such untracked residual balances and costs the attacker only gas plus a self-authored proof.

### Likelihood Explanation
The precondition (some token balance sitting on the Emporium contract that is absent from the attacking transaction's `erc20TokenAddresses`) is plausible in normal operation whenever a prior composite operation (e.g., a swap producing an unexpected/secondary output token, referral rewards, or rounding dust) leaves residue that its own depositor did not enumerate. The `erc20TokenAddresses.length == 0` ("Emporium Min") path lowers the bar further by removing essentially all balance accounting for a whole class of transactions. The attacker fully controls all `CircomData` fields per the given threat model, requires no privileged role, and the attack is a single `transact()` call.

### Recommendation
Bind `op.endpoint` for every `EmporiumOperation` to be either explicitly excluded from touching any token, or require that any token whose balance changes during `runAction` be a member of `circomData.erc20TokenAddresses` (e.g., by disallowing calls to arbitrary token contracts, or by tracking all balance changes for every token actually touched and folding them into the same equality checks). At minimum, forbid using the zero-length `erc20TokenAddresses` / "Emporium Min" circuit path when `stack.ops` includes calls capable of moving assets held by the contract, and sweep/verify that Emporium's balance for every token referenced anywhere in `stack.ops` returns to zero (or is otherwise accounted for) after `runAction` completes.

### Proof of Concept
1. Deploy Emporium, Hinkal, HinkalHelper, and a mock ERC20 `DUST` token; mint `DUST` directly to the Emporium proxy address to simulate leftover residue (or, more faithfully, have a first, legitimate transaction's swap op deposit `DUST` into Emporium as an unlisted swap output).
2. As an unprivileged attacker with their own valid UTXO, generate a proof for a `transact()` call whose `circomData.erc20TokenAddresses` does **not** include `DUST` (or is length 0, using the `HINKAL_EMPORIUM_ACTION_ID`/empty-array "Emporium Min" path), and whose `externalActionData.externalActionMetadata` decodes to an `EmporiumStack` with one `EmporiumOperation{endpoint: DUST, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer, (attacker, dustAmount))}`.
3. Call `Hinkal.transact(...)`.
4. Assert: the call succeeds; all `require`s in `EmporiumUpgradeable.runAction` (`BalanceChangeShouldBePositive`) and in `Hinkal.transact` (slippage and "Balance Diff Should be equal…") pass trivially (loop length 0 or `DUST` absent from the array); and `DUST.balanceOf(attacker)` increased by `dustAmount` while `DUST.balanceOf(Emporium)` decreased by the same amount — a movement fully outside the `balanceDif == amountChanges + utxoAmount` equation for every tracked token.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(

            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
