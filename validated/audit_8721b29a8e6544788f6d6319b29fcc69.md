### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when validating a webhook's authenticity, but the `shop` identity field that downstream application code relies on (via `WebhookMetadata#shop`) is read from an HTTP header that is never included in the signed content. This breaks the equality that should hold between "the shop whose secret validated this request" and "the shop the application believes sent it," enabling a merchant who has installed the app to replay their own validly-signed webhook body against a victim shop's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes an HMAC over whatever `to_signable_string` returns for the given `VerifiableQuery` and compares it to the `hmac` value, using the app's shared `Context.api_secret_key`: [1](#0-0) 

For incoming webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop` is pulled from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header, a field that is never part of the signed material: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only the HMAC and then dispatches to the registered handler using `request.shop` as the tenant identity, together with the (signed) body: [3](#0-2) 

Because `Context.api_secret_key` is the app's single `client_secret`, shared across every shop that has installed the app (it is not shop-specific), any merchant who installs the app can trigger a legitimate webhook delivery for their own shop and thereby obtain a `(raw_body, hmac)` pair that is valid under the app's secret. Since the shop identity is carried entirely in an unsigned header, that attacker can replay the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body against the secret, and `Registry.process` passes the attacker-controlled `shop` value straight to the app's handler as `WebhookMetadata#shop`.

This is the same bug class as the referenced report: a value that downstream logic treats as authoritative (there, whether new resting orders may be created for a Fill-or-Kill order; here, which tenant a webhook belongs to) is not actually constrained by the check that is supposed to guarantee it (there, the FoK invariant assertion; here, the HMAC signature). The equality that should hold — `shop_bound_by_hmac == shop_used_by_handler` — does not hold, because `shop` is excluded from `to_signable_string`.

### Impact Explanation
Any application built on this gem that trusts `WebhookMetadata#shop` (as the documented API for webhook handlers instructs) to attribute incoming webhook data to a tenant can be made to ingest attacker-supplied data under a victim shop's identity — e.g., faking `orders/create`, `app/uninstalled`, `customers/data_request`, or other topic payloads as if they originated from the victim store. This is a cross-tenant data-integrity/confidentiality breach reachable by any unprivileged user who can install the app on their own store, satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on a store they control (a normal, unprivileged action for any merchant on any public app), (2) they capture a legitimate webhook body + HMAC delivered to their own endpoint (trivial, since they control the endpoint receiving their own installed app's webhooks) and (3) they POST that same body/HMAC to the shared webhook processing endpoint with a forged `x-shopify-shop-domain` header. No secrets, tokens, or privileged access to the victim are needed.

### Recommendation
Bind the shop identity into the HMAC-verified material, or otherwise cross-check it against a source of truth before trusting it:
- Do not treat the `x-shopify-shop-domain` / `shopify-shop-domain` header as authenticated on its own. Require host applications (and document clearly) that the resolved `shop` must be cross-referenced against a shop the app has an active, stored session/install record for before acting on the payload.
- Where feasible, have `Request#to_signable_string` incorporate the shop-domain header (and other headers the application logic depends on) into the signed payload, matching how it's verified, or expose a dedicated verified-shop accessor that fails if the header cannot be corroborated against installation state.
- At minimum, update `docs/usage/webhooks.md` and `WebhookMetadata` documentation to explicitly warn that `shop` is unauthenticated header data and must be validated against the app's own shop/session store, not solely relied upon for tenant attribution.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store `attacker.myshopify.com`. Configure a webhook receiver under attacker's control to capture the raw POST the app's webhook endpoint would normally handle (or intercept a webhook delivered to the app itself).
2. Observe/capture a delivered webhook's raw body and its `x-shopify-hmac-sha256` header (computed by Shopify using the app's `client_secret`, shared across shops):
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-for-body>
   x-shopify-shop-domain: attacker.myshopify.com
   x-shopify-webhook-id: ...
   x-shopify-api-version: 2024-01

   { ...order payload attacker controls via their own store... }
   ```
3. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `Request#to_signable_string` only hashes `@raw_body`, per `lib/shopify_api/webhooks/request.rb` line 36-38. The handler is then invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` (`lib/shopify_api/webhooks/registry.rb` line 198), causing the app to process attacker-controlled data as if it belongs to `victim.myshopify.com`.
