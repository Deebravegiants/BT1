### Title
Recapitalize trusts a declared deposit and refunds `amount - applied` from pool custody, leaving the `cash` book overcommitted and supplier withdrawals bricked - ([File: contracts/pool/src/ops/recapitalize.rs])

### Summary
The bug class in the external report is an accounting variable (`currentWithheldETH`) that is consulted to admit claims but is not decremented when the claim is created, so several claims are committed against the same funds and later settlers are denied service. XOXNO Lending's analog is the pool `cash` ledger in `PoolStateRaw`. Every liquidity gate (`require_reserves`, `require_liquidation_buffer`, `backing_shortfall`, utilization checks) reads this *book* value, while `transfer_out` pays from the pool's actual SAC balance. `ops::recapitalize` desynchronizes the two: it accepts a caller-declared `amount`, credits only `min(amount, backing_shortfall)` to `cash`, and transfers `amount - applied` back to the `payer` from pool custody — without ever verifying that `amount` was actually deposited first. An unprivileged caller can therefore drain real tokens via the "refund" while the `cash` book still reports them present. Subsequent `withdraw`/`borrow`/`claim_revenue` calls pass `require_reserves` (the book says the cash exists) and then revert inside the SAC `transfer` for lack of custody — the same overcommitment DoS as the report: a variable admitting exits against funds that are no longer there.

### Finding Description
`recapitalize::accounting` computes `applied = amount.min(backing_shortfall(&cache))`, does `cache.credit_cash(applied)`, and returns `refund = amount - applied` (`contracts/pool/src/ops/recapitalize.rs:44-67`). `apply` then calls `outcome.cache.transfer_out(&payer, outcome.refund)` (`contracts/pool/src/ops/recapitalize.rs:26-38`). `transfer_out` moves real tokens but explicitly "does not adjust accounting cash" (`contracts/pool/src/cache/cash.rs:43-53`), and `debit_cash`/`require_reserves` only check the in-memory `self.cash` book (`contracts/pool/src/cache/cash.rs:14-41`). The only thing standing between the pool's custody and the refund is the doc-comment contract "The controller transfers `amount` into the pool before this call" (`recapitalize.rs:4`) — a cross-contract, check-then-act assumption identical in shape to trusting `currentWithheldETH` until `withdraw()`.

The pool's own test suite demonstrates the desync end-to-end: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3483`) calls `recapitalize(&hub, &payer, &custody)` with no deposit, the SAC balance drops to 0, `state.cash` still reports ≥ the supplier's deposit, and a subsequent `withdraw` passes both `InsufficientLiquidity` and `PoolInsolvent` guards and fails only inside the SAC transfer with `BalanceError = 10` — mirroring Bob's failed `withdraw()` after the shared reserve was consumed.

### Impact Explanation
If any reachable path (direct pool call if the entrypoint lacks a controller-only auth check, or `controller.recapitalize` if it does not atomically pre-fund `amount` via `balance_delta`/transfer-in) lets an unprivileged address set `amount` larger than what was deposited, the attacker receives `refund` tokens they never paid (theft of user funds), and the `cash` book remains overstated. From that point, every supplier exit and borrower draw on that hub market is a temporary freeze of funds / "contract unable to operate from lack of token funds": guards green-light the operation on book value, and the whole transaction aborts at token transfer until real tokens are re-injected — precisely the denial of service the report describes.

### Likelihood Explanation
The reachable entrypoint list explicitly includes `recapitalize`, and the exploit needs only one call with a large `amount` on a market with little or no backing shortfall (so `applied ≈ 0` and `refund ≈ amount`). The residual uncertainty is the auth/funding check on the controller side (`contracts/controller/src/markets.rs` and `external/pool.rs::pool_recapitalize_call`), which I could not fully verify within the available context: if the controller enforces a measured balance-delta deposit before invoking the pool, the attack surface collapses to whoever can satisfy it. The pool-level primitive and the demonstrated book/custody divergence are confirmed by code and by an existing test.

### Recommendation
Do not trust the declared `amount`. In `recapitalize::apply`, measure the actual deposit with a balance delta (token balance of the pool before vs. after the controller's transfer-in, as `payments::balance_delta_since` does elsewhere), compute `applied`/`refund` from the *measured* amount, and/or restrict the entrypoint to the controller via `require_auth`. Independently, make `transfer_out`/`require_reserves` defense-in-depth consistent by capping draws at `min(cash_book, actual SAC balance)` so an overstated book cannot admit exits that revert at settlement.

### Proof of Concept
1. Supplier deposits 10 XLM-equivalent into hub market H; `state.cash = SAC balance = 10`.
2. Attacker (unprivileged) calls `recapitalize(H, attacker, 10)` with zero tokens deposited. `backing_shortfall = 0` → `applied = 0`, `refund = 10`; `transfer_out(attacker, 10)` pays the entire custody. `state.cash` still reads ≥ 10.
3. Supplier calls `controller.withdraw` (full close). `require_reserves(10)` passes against the book; `gate_and_debit` commits; `transfer_out(receiver, 10)` reverts inside the SAC with `BalanceError`.
4. Every subsequent `withdraw`, `borrow`, `claim_revenue`, and `flash_loan` repayment-settlement on H reverts the same way until the market is re-funded — the Alice/Bob overcommitment replayed on the `cash` ledger. This is already encoded as `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs:3408-3483`.
