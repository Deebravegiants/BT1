### Title
Fraud/liveness enforcement bypass — biometric validity is never checked before enrollment - ([File: src/plans/mod.rs])

### Summary
`Orb::detect_fraud` in `src/plans/mod.rs` is a stub that unconditionally returns `Ok(false)` (no fraud detected), regardless of the biometric pipeline's actual quality/validity output. This mirrors the reported bug class: data that should be gated by a "validity" check (`checkValidityERC721`) is instead accepted unconditionally, deferring the missing check to a later, more consequential step.

### Finding Description
`detect_fraud` explicitly discards the pipeline and always returns `false` (not fraudulent): [1](#0-0) 

This function is invoked during the signup flow and its `false` result is treated as "no fraud/liveness issue detected," allowing the flow to continue to `enroll_user`/`build_pcp` regardless of the actual face/iris validity signals produced by the pipeline (e.g., `FIIsValidOutput`/`IsValidOutput.is_valid`, `score` fields) which exist in the codebase but are not consulted here: [2](#0-1) 

Downstream, `build_pcp` only checks that fields are *present* (`Some(...)`) — it never checks whether the face identifier bundle or iris data was marked invalid/low-quality/fraudulent before packaging it for backend enrollment: [3](#0-2) 

This is directly analogous to the `MarginTrading::provideERC721` issue: the entry point that should gate acceptance based on a "validity" predicate (there: `checkValidityERC721`; here: fraud/liveness validity from the pipeline) skips the check entirely, and the invalid/unauthorized data is carried forward into the expensive, security-critical downstream operation (there: `liquidate`; here: `enroll_user`/backend signup enrollment), which then must process it without ever having gated on validity.

### Impact Explanation
An unprivileged user at the orb can attempt signup with attacks that would normally be caught by liveness/fraud detection (e.g., using a photo, mask, or otherwise defeating the biometric-capture-time checks) and this code path never independently vets pipeline-level fraud/liveness signals before handing the capture off for enrollment. Because the local `detect_fraud` gate is stubbed out (per the comment "FOSS: WE HAVE DELETED ALL FRAUD CHECKS"), any biometric capture that survives capture-time checks proceeds straight into enrollment without the orb-side content sanity/fraud gating, which increases the risk of misattributed/fraudulent signups and unauthorized identity binding — matching the "unauthorized or misattributed signup" impact category.

### Likelihood Explanation
Likelihood is low-to-moderate: successful signup still additionally requires passing biometric-capture-time gating (elsewhere in the pipeline) and backend-side verification/fraud detection, so this local stub alone is not sufficient for an end-to-end bypass. However, it removes one full independent layer of local defense that the code structure implies should exist (the function is explicitly named/wired as a fraud-detection gate in the signup flow), which is exactly the "avoidance of enforcement via unchecked validity" pattern from the source report — high impact if it is one of the layers actually relied upon, but likelihood is reduced because other layers (backend-side, capture-time) may still catch it. I could not fully verify within the available index whether the backend-side and capture-time checks are fully redundant/sufficient replacements for this local check, since related feature-gated code (`fraud_check.rs`, `biometric_pipeline/mod.rs`) was only partially visible in the index.

### Recommendation
Restore/implement `detect_fraud` to actually consult the biometric pipeline's fraud/liveness/validity signals (e.g., `FraudChecks`, `IsValidOutput.is_valid`/`score`) and reject/flag signups that fail these checks, rather than unconditionally returning `Ok(false)`. Additionally, `build_pcp` should check not just the presence but the *validity* (`is_valid`, error-free, and quality score) of the face identifier bundle and iris data before constructing and uploading the personal custody package for enrollment.
