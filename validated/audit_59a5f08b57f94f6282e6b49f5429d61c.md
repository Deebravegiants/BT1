## Analysis

The HoneyFactory bug pattern is: a security-gating function counts items in a loop (`registeredAssets`) to decide whether to flip a protocol-wide mode, without validating that each counted item represents *genuine, distinct* weight — a zero-balance/fully-resolved entry is counted the same as a real one, letting the count clear a threshold it shouldn't.

The same bug class exists in Hyperbridge's `EcdsaBeefy` consensus client. Its supermajority gate counts `votes.length` without checking that each vote comes from a **distinct** authority — unlike the BSC, Pharos, and sync-committee verifiers in the same repo, which explicitly guard against this exact padding technique.

### Title
Supermajority threshold in EcdsaBeefy is satisfied by duplicated votes, not distinct signers - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` computes `sigLen = relayProof.signedCommitment.votes.length` and checks it against the 2/3+1 threshold via `checkParticipationThreshold`, then verifies each vote's recovered authority via a merkle multi-proof. Neither step rejects duplicate entries (same signature or same `authorityIndex` submitted multiple times), so `sigLen` can be inflated by repetition rather than genuine distinct authority participation, exactly mirroring the reported bug class where a loop-based mode/threshold switch is fooled by degenerate/zero-weight entries.

There is no dedup check on `vote.authorityIndex` (or on the recovered `authority` address). A caller can take a single valid signature from one honest authority and place it `n` times in `votes` (with the same `authorityIndex`/leaf each time), inflating `sigLen` past the supermajority threshold while the merkle multi-proof still validates because each repeated `(index, hash)` pair is trivially a valid leaf of the authority set (proving the same leaf twice does not require additional distinct authorities).

This is the same root-cause shape as the reported HoneyFactory issue: a threshold/mode decision is computed by counting loop entries without confirming each entry represents genuine, non-degenerate weight (there, zero-balance assets counted toward "basket mode"; here, duplicated votes counted toward "supermajority"). Notably, sibling verifiers in this same codebase were hardened against the analogous class of padding attack: [3](#0-2)

### Impact Explanation
`handleConsensus` in `HandlerV2.sol` is permissionless and calls `IConsensusV2(host.consensusClient()).verify(...)` directly on relayer-submitted proofs: [5](#0-4) 
```solidity
function handleConsensus(IHost host, bytes calldata proof) external notFrozen(host) {
    ...
    (bytes memory verifiedState, IntermediateState[] memory intermediates, uint256 nextAuthoritySetId) =
        IConsensusV2(host.consensusClient()).verify(previousState, proof);
```
If `EcdsaBeefy` accepts a forged supermajority backed by fewer than 2/3+1 distinct authorities, an attacker controlling even a small minority of relay-chain authority keys (or possibly a single compromised/former key, depending on the underlying merkle-tree library's handling of duplicate leaves) could get arbitrary `IntermediateState`s (fake parachain state commitments) accepted as canonical. Those state commitments back all subsequent request/response proof verification in `HandlerV2.handlePostRequests`, so this is a path to forged message delivery / unsound state commitments across the bridge — including potentially unbacked minting via token-gateway messages relying on that state.

### Likelihood Explanation
Exploitation requires only that an attacker submit a crafted `ConsensusMessage`/proof through the permissionless `handleConsensus` entry point, and depends on the underlying `MerkleMultiProof.VerifyProof` implementation not rejecting duplicate `(index, hash)` leaves (a common property of naive multi-proof verifiers, since proving the same leaf twice is not inherently invalid in many implementations). Given that three other consensus verifiers in this same codebase were explicitly patched against duplicate/padding attacks on participant counts, this suggests the underlying risk is real and was addressed elsewhere but missed in `EcdsaBeefy.sol`.

### Recommendation
In `verifyMmrUpdateProof`, deduplicate votes by `authorityIndex` (and/or recovered `authority` address) before computing `sigLen` and before building the `authorities` array, rejecting the proof if any duplicate index/signer is present — mirroring the `DuplicateParticipant` check already used in the Pharos verifier and the beyond-range bit checks in the BSC/sync-committee verifiers.

### Proof of Concept
1. Obtain one valid signature `s` from authority `A` (index `k`) over a legitimate BEEFY commitment for the current authority set.
2. Construct `votes = [ (k, s), (k, s), (k, s), ... ]` repeated enough times that `votes.length >= (2*total)/3 + 1`.
3. Submit this via `handleConsensus(host, proof)` where `proof` encodes this `RelayChainProof`.
4. `checkParticipationThreshold` passes on the inflated `sigLen`; each duplicated leaf `(index: k, hash: keccak256(A))` is verified by `MerkleMultiProof.VerifyProof` as a valid member of the authority set (since it is the same legitimately-committed leaf, just supplied multiple times), so `InvalidAuthoritiesProof` is never raised.
5. The forged/underweight-signed commitment is accepted, and its `IntermediateState`s (fake parachain state commitments) are stored as canonical by `EvmHost.storeStateMachineCommitment`.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
