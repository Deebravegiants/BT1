### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is read from an HTTP header that is never part of the signed data. The binding "HMAC valid" ⇒ "shop value is authentic" does not hold, because the `shop` (and `topic`, `webhook_id`, `api_version`) fields are excluded from the signable string.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all derived from HTTP headers that are outside the HMAC-signed payload: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery` — only checks `hmac` against `to_signable_string` (i.e., the raw body): [3](#0-2) [4](#0-3) 

After this single check passes, `request.shop` (an unauthenticated header value) is forwarded to the developer's handler as `WebhookMetadata#shop`, which apps are expected to treat as the authoritative tenant identifier: [5](#0-4) 

The identity binding that should hold is:
`HMAC-SHA256(secret, raw_body) == received_hmac` ⇒ `shop header == originating shop`

But the actual binding enforced is only:
`HMAC-SHA256(secret, raw_body) == received_hmac` ⇒ `raw_body == raw_body`

The `shopify-shop-domain` (and topic/webhook-id/api-version) headers are completely outside this equality. Anyone who can obtain one legitimately-signed `(raw_body, hmac)` pair from Shopify — e.g., by installing the app on their own store and receiving a real webhook — can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `Utils::HmacValidator.validate` will still return `true` (it never inspects the shop header), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen shop.

### Impact Explanation
This is a cross-tenant identity spoofing primitive scoped entirely within this gem's own webhook-processing code path, not a misuse of a documented API by the host application: the gem's documented contract is "if `process` doesn't raise `InvalidWebhookError`, the webhook (including `shop`) is verified." Any app that trusts `WebhookMetadata#shop` (as the docs imply is safe, since it comes from the same object whose HMAC was checked) to select which tenant's data/settings to update, delete, or resend credentials for is exposed to cross-tenant action — e.g., a handler that deletes local records for `data.shop`, disables billing for `data.shop`, or writes attacker-controlled body content against another merchant's tenant record.

### Likelihood Explanation
Moderate-to-high: it requires only (1) a public HTTP endpoint (a standard requirement for Shopify webhooks) and (2) one authentic `(raw_body, hmac)` sample, which any developer/attacker can obtain simply by installing the same app on their own free development store and capturing the webhook Shopify sends them. No access token, `client_secret`, or privileged account is required — only a normal Shopify install, which fits the "unprivileged internet user" threat model.

### Recommendation
Include the identity-relevant headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the payload before exposing them via `WebhookMetadata`, so that `HmacValidator.validate` cannot pass while these fields are attacker-controlled. At minimum, document prominently that only the body is authenticated and that `shop`/`topic` header values must not be trusted for authorization decisions.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com` and let Shopify deliver a legitimate webhook to the app's endpoint; capture the raw body `B` and header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B`).
2. Resend an HTTP POST to the same webhook endpoint with:
   - body = `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (attacker-supplied, arbitrary)
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B`: [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the request was never authenticated for that shop, demonstrating the broken binding between the verified bytes (`raw_body`) and the trusted identity field (`shop`).
