Confirmed: `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` in `evm/src/core/EvmHost.sol` all execute a Uniswap V2 `swapETHForExactTokens` call whenever `msg.value > 0`, with `address(this)` (the Host) as the swap recipient and `block.timestamp` as the deadline. Any excess ETH beyond what is needed for the exact-output swap is refunded by the router to `msg.sender` of the router call, which is the Host contract itself — not the original dispatcher — and there is no code path that forwards that refund back to the caller.

### Title
Uniswap V2 exact-output swap in `EvmHost.dispatch`/`fundRequest` has no real deadline and traps overpaid native token as an unrecoverable donation to the Host - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` let any unprivileged message dispatcher pay the relayer fee in native token. When `msg.value > 0`, the Host performs an on-chain Uniswap V2 `swapETHForExactTokens` call priced entirely off the current AMM reserves, using `block.timestamp` as the deadline (a no-op deadline) and refunding any unspent ETH to itself rather than the caller.

### Finding Description
In `evm/src/core/EvmHost.sol`, lines 921-932 (`dispatch(DispatchPost)`), 974-985 (`dispatch(DispatchGet)`), and the equivalent block in `fundRequest` (~1031-1039), the same pattern is repeated: [1](#0-0) 

The caller is expected to compute `msg.value` off-chain via `HyperApp.quote()`, which itself uses `getAmountsIn` against the live pool and is explicitly documented as unsafe on-chain: [2](#0-1) [3](#0-2) 

Two compounding issues make the on-chain swap itself unsafe, independent of the caller's off-chain quote:

1. **No real deadline.** The router call passes `block.timestamp` as the `deadline` argument. Since this is evaluated at execution time, it is always satisfied — it provides zero protection against a transaction sitting in the mempool and being executed later at an unfavorable price, unlike a deadline chosen up front by the caller.
2. **Refund goes to the wrong party.** `swapETHForExactTokens` is an exact-output swap: it computes `amountIn` from current reserves at execution time and refunds `msg.value - amountIn` to whoever called the router — which is `EvmHost` itself (`address(this)` is only the swap recipient of the output tokens, not the ETH-refund address inside the router's internal accounting; the router's `msg.sender` in this call context is the Host contract). No code in `dispatch`/`fundRequest` forwards this refund back to `_msgSender()`. Any ETH sent above the exact amount needed for the swap at execution-time price is silently retained by the Host contract with no accounting entry or recovery path for the dispatcher.

Because the required input amount for a fixed output amount (`post.fee`/`get.fee`) is a direct function of the pool's spot price, an attacker who front-runs a `dispatch`/`fundRequest` transaction (or simply times their own dispatch after moving the pool) can shift the effective price so that the swap consumes less ETH than the dispatcher intended to spend, with the difference becoming an unrecoverable donation to the Host, or — in the opposite direction — cause the swap to need more ETH than sent, reverting the message dispatch entirely (denial of the message-delivery path for any user relying on a tight, off-chain-computed `msg.value`).

### Impact Explanation
This reaches every unprivileged sender of a Hyperbridge message that opts to pay in native token, which is a documented, explicitly recommended payment path (`dispatch{value: msg.value}(...)`, `fundRequest{value: ...}(...)`). Depending on pool-price movement between quote time and execution time:
- Excess ETH sent is permanently trapped in `EvmHost` with no user-facing accounting or refund mechanism — a fund-freezing bug for the dispatcher.
- Insufficient ETH (relative to the manipulated spot price) reverts the dispatch/fundRequest call outright, meaning a legitimate message or fee top-up cannot be delivered — "a route unable to deliver messages" for native-token payers until they resubmit with a larger buffer.

Both outcomes match the report's core defect class (a swap execution priced solely off manipulable on-chain AMM state, invoked in an unprivileged, fee-paying user flow, without any protection tying the executed price back to what the caller actually authorized).

### Likelihood Explanation
Every `dispatch()`/`fundRequest()` call with `msg.value > 0` triggers this code path; no special conditions or privileges are required. Any address holding native token on an EVM host chain can call it directly. Exploiting the price-timing gap only requires the attacker to submit a transaction that shifts the WETH/feeToken pool reserves before the victim's dispatch/fundRequest is mined (a standard front-run), which is trivial on any chain where the Host's configured Uniswap V2 pool has moderate liquidity.

### Recommendation
- Replace `block.timestamp` with a caller-supplied `deadline` parameter (or derive one from the request's own timeout) so a stale transaction cannot execute at an arbitrarily later, disadvantageous price.
- After the swap, explicitly compute and refund any leftover native balance introduced by `msg.value` (or unused WETH) back to `_msgSender()`, rather than letting the router's internal refund settle silently on the Host's own balance.
- Consider bounding the acceptable swap price against a TWAP or oracle-derived sanity check, or require callers to pass an explicit `maxNativeIn`/slippage parameter that the Host enforces, rather than relying entirely on an off-chain `quote()` call that the docs themselves flag as sandwich-vulnerable.

### Proof of Concept
1. Attacker monitors the mempool of the EVM host chain for a `dispatch(DispatchPost)`/`dispatch(DispatchGet)`/`fundRequest` call carrying `msg.value` computed from an off-chain `HyperApp.quote()`/`quoteNative()` call against the Host's configured Uniswap V2 pool.
2. Attacker front-runs with a large swap in the same pool (WETH ⇄ feeToken) to move the spot price, then optionally back-runs to restore it (a standard sandwich).
3. If the price moves such that less ETH than `msg.value` is now required for the same exact `post.fee`/`get.fee` output, the victim's transaction succeeds, `EvmHost` (not the victim) receives the ETH refund from the router, and the difference is permanently unrecoverable by the victim — see the refund-target gap in [1](#0-0) .
4. If instead the price moves such that more ETH is needed than `msg.value` provides, the router call reverts and the victim's message/fee-top-up is not dispatched, forcing a retry — a griefing/DoS vector on the native-token payment path, reachable by any unprivileged user with no special access.
