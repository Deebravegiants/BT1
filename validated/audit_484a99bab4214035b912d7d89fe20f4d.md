I found a valid, concrete analog to this CVE class. The OpenSMTPD bug is characterized as "the issue exists because of an incorrect return value upon failure of input validation" — allowing execution to continue past a failed validation check into a privileged code path. The exact same pattern exists in `oi.handleTokenExchange` in the OIDC login handler.

### Title
Missing `return` after failed email-claim extraction allows session creation to proceed despite input validation failure - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `handleTokenExchange`, the type-assertion check on the `email` claim writes an HTTP 500 error body but omits the `return` statement, so gin's handler function keeps executing. The rest of the authentication flow — role mapping, `oidc_sessions` row insertion, session-cookie establishment, and a final 200 OK JSON response — runs unconditionally, even though the email-extraction step "failed."

### Finding Description [1](#0-0) 

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
oi.lggr.Tracef("Received and validated ID claims: %v\n", idClaims)
```

There is no `return` in the `!ok` branch. Unlike every other error branch in this same function (lines 166-172, 178-183, 190-196, 201-204, 209-212, 216-219, 221-225, 267-271 — all of which correctly `return` after writing an error response), this one does not. `c.String()` in gin only writes bytes to the response buffer; it does not abort request processing or set `c.Abort()`. Execution therefore falls through into the privileged remainder of the handler: [2](#0-1) 

This means role derivation, `INSERT INTO oidc_sessions`, `ginSession.Set(webauth.SessionIDKey, clSession.ID)`, `ginSession.Save()`, and the final `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})` all execute after the "failure" — with `email` left as its zero value (`""`). The final 200 response silently overwrites the earlier 500 body that gin had already buffered, so the client receives a success response and a valid, cookie-bound authenticated session.

This directly parallels the reported CVE's root cause: "incorrect return value upon failure of input validation" causing continuation into a security-relevant execution path that should have been unreachable.

### Impact Explanation
An OIDC identity token whose claims lack an `email` field (or where `email` is present but not a string) still results in a fully authenticated, role-bearing session being created and returned to the caller as `Success: true`. The session is recorded in `oidc_sessions` with an empty `user_email`, and the audit log entry for `AuthLoginSuccessNo2FA` records `email: ""` — obscuring the true actor. Any party able to influence the ID token's claim set delivered to this endpoint (e.g., via a compromised/misconfigured OIDC provider, or any code path that can reach `idToken.Claims` with an email-less payload while still satisfying group-claim role mapping) obtains a working authenticated Chainlink node session/role without a valid email identity — a concrete authentication/session-establishment bypass and cross-identity confusion bug.

### Likelihood Explanation
Exploitability depends entirely on the identity provider's token response (or any spoof/misconfiguration of it) omitting/mistyping the `email` claim while still providing valid group claims that satisfy `IDClaimsToUserRole`. Since `email` and `idClaims` (via `oi.config.ClaimName()`, i.e. the groups claim) are independently sourced from the same token, they are not required to be consistent, and role mapping does not depend on `email` at all — so this is reachable purely by a token/provider inconsistency, not requiring code injection.

### Recommendation
Add the missing `return` immediately after the `c.String(http.StatusInternalServerError, "Failed to get email from claims")` call at line 229, matching the pattern used by every other error branch in this function, so that session creation cannot proceed when the email claim is missing/invalid.

### Proof of Concept
1. Configure/point the OIDC provider (or intercept the token exchange response in a test/dev environment) so the ID token's claims contain valid group claims mapping to a role (e.g., admin) but omit the `email` field or set it to a non-string value.
2. Call `POST /sessions/exchange` (the endpoint wired to `handleTokenExchange`) with a valid `code`/`state`.
3. Observe: despite `oi.lggr.Errorf("Failed to get email from claims...")` firing and a 500 body being written, the handler continues, inserts a row into `oidc_sessions`, sets `webauth.SessionIDKey` in the gin session, and returns `HTTP 200 {"success":true}` with a working session cookie — granting an authenticated session with the mapped role and an empty email.
