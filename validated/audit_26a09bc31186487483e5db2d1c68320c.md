### Title
Webhook shop-domain / topic identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop-domain`, `topic`, and `webhook-id` values that are then handed to the app's handler are taken from unauthenticated HTTP headers, breaking the binding "shop authenticated == shop acted upon."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` covers exclusively the JSON body: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic binding to the body or the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC and then immediately dispatches to the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` values as the tenant/routing identity: [4](#0-3) 

Because the signature validates the body bytes but the app trusts the header bytes for shop identity, `shop_authenticated_by_hmac != shop_used_by_handler`. Any party that can obtain one valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` for their own shop (e.g., a merchant who installed the app and can observe/replay their own genuine webhook deliveries) can resend that exact body/HMAC pair while substituting the `X-Shopify-Shop-Domain` header for a different (victim) shop. `HmacValidator.validate_signature` will still pass because it re-computes the HMAC over the same raw body and compares it via `OpenSSL.secure_compare` — it never inspects the shop header: [5](#0-4) 

The handler then receives `WebhookMetadata` carrying the forged `shop` value, and the app (per the documented usage pattern) uses it to look up/act on a specific tenant's data: [6](#0-5) 

### Impact Explanation
This crosses a tenant boundary: an actor legitimately possessing (or able to capture) one HMAC-valid webhook payload for shop A can cause the app to process/attribute that webhook data as belonging to shop B, achieving cross-tenant confusion/access without ever knowing the app's `client_secret` or any other shop's credentials. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires the attacker to have at least one genuine `(body, hmac)` pair from any shop using the app (trivially available to any merchant who installs the app, since Shopify delivers real webhooks to their own endpoint, or to anyone who can intercept a delivery over an insecure channel/logging pipeline). No secret material or victim credentials are needed — only header spoofing on the replayed HTTP request, which is entirely within reach of an unprivileged actor controlling the request to the app's public webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cross-check the header-derived shop against a value derivable from the signed body/session context before dispatching to handlers. At minimum, document that consumers must independently verify `request.shop` against the app's own installed-shop registry rather than trusting the header as an authenticated identity, since the gem does not perform this binding itself.

### Proof of Concept
1. App is installed on `victim-shop.myshopify.com` and `attacker-shop.myshopify.com` (both use the same app, hence the same `api_secret_key`).
2. Attacker's shop receives a genuine webhook delivery: raw body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the request to the app's webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and matches `H` — validation succeeds: [7](#0-6) 
5. `request.shop` returns `victim-shop.myshopify.com` (from the forged header), and `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` is passed to the app's handler, which will act on/attribute the payload to the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
