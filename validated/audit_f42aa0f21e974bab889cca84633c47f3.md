### Title
Webhook shop domain and topic are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, and `webhook_id` values solely from unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the raw request body. The shop identity handed to the app's `WebhookHandler` is therefore never bound to the HMAC signature that is supposed to authenticate the message.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` and compares it to the received signature: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body, never the `shop`, `topic`, or `webhook-id` headers: [2](#0-1) 

Compare this to the OAuth callback path, `Auth::Oauth::AuthQuery`, where `shop` (and `host`, `code`, `state`) are explicitly included in `to_signable_string` and thus are cryptographically bound to the HMAC: [3](#0-2) 

`Registry.process` validates only the body HMAC, then forwards the raw, unauthenticated `request.shop` and `request.topic` values straight to the app's handler: [4](#0-3) 

The resulting `WebhookMetadata#shop` field — which host applications use to identify which tenant/shop the webhook belongs to — is populated from a header that carries no cryptographic binding to the signed body: [5](#0-4) 

Because a single `api_secret_key` is shared across every shop that installs the app, anyone who can obtain one genuine webhook delivery for their own shop (trivial — a merchant can install the app on their own store and trigger any webhook topic themselves) possesses a validly-signed `(hmac, raw_body)` pair. That pair remains valid for *any* `shop-domain` / `topic` header value, since those headers are not part of the signed content. Replaying the same body with a different `x-shopify-shop-domain` (or `x-shopify-topic`) header still passes `HmacValidator.validate`, letting the attacker have the app process arbitrary webhook bodies "on behalf of" a shop they do not control.

The equality the design should enforce is:
`shop header used by WebhookMetadata == shop bound inside the HMAC-signed payload`
but this gem enforces only:
`bytes verified by HMAC (raw body) == bytes actually used for authentication decisions (raw body)`, while `shop`/`topic` are parsed but never verified.

### Impact Explanation
This breaks the identity binding between the authenticated bytes and the tenant identifier that host applications rely on to route webhook data (e.g., to look up/update the correct shop's records, or to gate mandatory-webhook compliance actions such as `shop/redact`, `customers/redact`). An attacker with legitimate access to only their own shop can cause the app to process a webhook body while spoofing another shop's domain and/or topic, resulting in cross-tenant data confusion in any host application that trusts `WebhookMetadata#shop`/`#topic` as authenticated (which is the gem's own documented contract, since `Registry.process` raises `InvalidWebhookError` only on HMAC failure and otherwise treats the metadata as trusted).

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free/trial) merchant capable of installing the app on their own store and triggering any webhook of their choosing (most webhook topics are attacker-triggerable, e.g., `orders/create`, `app/uninstalled`), then replaying the exact captured HTTP body to the app's public webhook endpoint with a modified `shop-domain`/`topic` header. No access to `api_secret_key`, access tokens, or any other privileged credential of the target tenant is needed.

### Recommendation
Bind the shop domain (and ideally the topic and webhook id) into the HMAC-verified payload, or otherwise cryptographically tie them to the signed body — e.g., by validating the `shop-domain` header against an app-known list of currently-installed shops with a stored session, or by having `to_signable_string` incorporate a canonical representation of the shop/topic/webhook-id along with the body so tampering with those headers invalidates the signature.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`, trigger any webhook (e.g. `orders/create`) and capture the raw POST: body `B`, and headers including `x-shopify-hmac-sha256: H` (valid HMAC of `B` computed with the shared `api_secret_key`), `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the identical request to the app's webhook endpoint, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) still succeeds because it only checks `B` against `H`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)` to the app's handler, which now processes attacker-controlled data under the victim shop's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
