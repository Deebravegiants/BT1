## Title
Missing relayer authorization gate on IntentGatewayV2's escrow withdrawal path (TRON deployment) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The BigONE post-mortem describes attackers who bypassed risk-control checks by tampering with the internal authorization logic that gates withdrawals, so that the system treated unauthorized fund releases as legitimate. The analogous bug class in Hyperbridge is a withdrawal path that is missing an authorization/relayer gate that an equivalent, security-critical path enforces elsewhere. The TRON port of `IntentGatewayV2.sol`'s `onAccept` handler processes `RedeemEscrow`/`RefundEscrow` messages (which directly call `withdraw()` and transfer escrowed tokens to a beneficiary) without the `_checkRelayer` gate that the canonical EVM implementation (`ExtrinsicIntents.sol`) enforces on the same code path.

### Finding Description
On the reference EVM implementation, `ExtrinsicIntents.onAccept` calls `_checkRelayer(incoming.relayer)` as the very first statement before dispatching on `RequestKind`, including `RedeemEscrow`/`RefundEscrow`: [1](#0-0) 

`_checkRelayer` enforces that once an authorised relayer is configured, only that relayer's deliveries are accepted for this callback: [2](#0-1) 

The TRON deployment's `IntentGatewayV2.onAccept`, however, performs no equivalent `_checkRelayer` (or any relayer-based) check before handling `RedeemEscrow`/`RefundEscrow` — it goes straight to `authenticate(incoming.request)` and then `withdraw(...)`: [3](#0-2) 

`authenticate` (analogous to `_authenticate` on EVM) only checks that `request.from` matches the registered peer gateway instance for the source chain — it says nothing about which relayer delivered the message. The `withdraw` function it feeds into performs the actual token transfer to the beneficiary from escrow: [4](#0-3) 

This means that on the TRON deployment, any relayer capable of delivering an ISMP message to this contract's `onAccept` (i.e. whatever plays the role of `HandlerV2`/host delivery on TRON) can trigger an escrow withdrawal without being the operator-designated relayer, whereas the same logical flow on the canonical EVM code is deliberately restricted to a single authorised relayer once one is configured. This is precisely the "risk-control logic silently missing/bypassed on one path but not another" pattern from the BigONE report: production logic that gates a fund-release action is present in one deployment but absent in a parallel one that performs the identical operation.

### Impact Explanation
If the TRON `IntentGatewayV2` is deployed without an equivalent relayer allowlist enforced elsewhere (e.g., at the host/handler layer for TRON), any party able to submit deliveries to `onAccept` can redeem or refund escrowed order funds to attacker-chosen destinations by crafting/relaying `RedeemEscrow`/`RefundEscrow` messages from the peer gateway address, bypassing the intended single-relayer control. This is a direct theft-of-escrowed-funds vector on the TRON leg of the intents system, reachable by an unprivileged relayer/message deliverer — a Critical-severity fund-freezing/theft class matching the required "concrete theft of funds" impact criterion.

### Likelihood Explanation
Likelihood depends on whether TRON's host/handler equivalent independently restricts who may call `onAccept`, and whether `_relayer` is actually unset (open) on this TRON contract in production. Based solely on the contract code available, the gate that the EVM contract relies on to close this path (`_checkRelayer`) is simply absent from the TRON contract's `onAccept`, so the withdrawal path is authorization-equivalent to "gate not configured" regardless of any `_relayer` state variable that might exist elsewhere in the file (grep found only incidental relayer references, not a `_checkRelayer` invocation in `onAccept`). I could not fully verify within the available index whether TRON's host layer enforces relayer identity before calling into `onAccept`, since full TRON host/handler source was not indexed in this session — this should be confirmed by a maintainer/Devin session with full TRON repo access.

### Recommendation
Add the same `_checkRelayer(incoming.relayer)` call at the top of TRON's `IntentGatewayV2.onAccept`, before branching on `RequestKind`, mirroring `ExtrinsicIntents.sol`. Audit all TRON app contracts for parity with their canonical EVM counterparts on every authorization gate (relayer allowlist, `onlyHost`, source/module checks) rather than assuming logic parity across ports.

### Proof of Concept
1. Deploy/observe the TRON `IntentGatewayV2` with escrowed order funds present (via `placeOrder`).
2. As an arbitrary relayer (not the operator's designated one, if any exists at the host layer), submit an ISMP delivery invoking `onAccept` with `request.body[0] == RequestKind.RedeemEscrow`, `request.from` spoofed/matched to the registered peer `instance(order.source)` address, and a `WithdrawalRequest` body naming an attacker-controlled `beneficiary`.
3. Because `onAccept` never calls `_checkRelayer`, the call proceeds to `authenticate` (which only checks `request.from` against the known peer instance, not the relayer identity) and then `withdraw`, transferring escrowed tokens to the attacker's `beneficiary`. [3](#0-2) [4](#0-3)

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;

                ++i;
            }
        }
