### Title
Swap output slippage protection is declared but never enforced against actual swap output - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap()` requires that a per-token slippage floor `circomData.slippageValues[1]` be non-zero, but never compares the actual `swappedAmount` returned by the router against this floor. This mirrors the reported class of bug — a value meant to enforce a real economic constraint (an exchange-rate/amount floor) is present in the code path but not actually used to gate the output, so users can receive far less value than the amount their ZK-signed data committed to.

### Finding Description
The swap flow is: [1](#0-0) 

`circomData.slippageValues[1]` is checked only for `!= 0`, never for `swappedAmount >= circomData.slippageValues[1]`. The `swappedAmount` comes directly from `callRouter()`, which for the LI.FI adapter is simply the balance delta after executing arbitrary `externalActionMetadata` calldata against `router`: [2](#0-1) 

`slippageValues` is part of `CircomData` and is included in `dimensionsCheck` (length must match token count) and is presumably folded into `getHashedCalldata`/`calldataHash`, meaning the prover/user commits to this slippage floor as part of their signed intent: [3](#0-2) [4](#0-3) 

However, nowhere in `swap()` is the actual amount received from the router compared to this committed floor. The resulting UTXO is created using whatever `amountToSendToHinkal` results from the real swap, regardless of whether it satisfies the user's committed minimum: [5](#0-4) 

This breaks the intended equality "value credited to the user's shielded UTXO ≥ value the user authorized/committed to (`slippageValues[1]`)". Because `externalActionMetadata` is arbitrary calldata forwarded to an external router, a relay or the router path itself can cause the swap to execute at an arbitrary (even worst-case) rate, and the contract will silently accept and shield whatever amount results — the on-chain "slippage protection" is a no-op beyond a zero-check.

### Impact Explanation
This allows silent value loss for shielded user funds during swaps: the amount actually shielded into the user's new UTXO can be arbitrarily lower than the floor the user signed off on, with no revert. Since the relay chooses/controls the transaction execution context and `externalActionMetadata` execution, this is a path where value is moved "but not counted/verified in the balance equation" the user actually authorized — qualifying as theft of in-flight shielded funds (Critical) up to the difference between the committed floor and the real payout, or at minimum temporary/permanent freezing of expected value (High).

### Likelihood Explanation
Any relay/caller invoking `transact` with a swap external action and controlling or influencing `externalActionMetadata`/router path (e.g., through unfavorable routing, sandwiching, or a malicious/compromised relay) can trigger this with no special privileges beyond being an unprivileged relay/caller of a normal swap flow — no admin/owner keys required.

### Recommendation
Enforce `swappedAmount >= uint256(circomData.slippageValues[1])` (accounting for the token's decimals/direction) immediately after `callRouter()` returns, reverting the transaction if the actual output is below the user-committed floor, consistent with how `slippageValues` is already threaded through `calldataHash`/dimension checks.

### Proof of Concept
1. User builds a shielded swap with `slippageValues[1] = X` (their signed minimum acceptable output) as part of `CircomData`, which is hashed into `calldataHash`.
2. Relay submits the transaction via `Hinkal.transact` → `ExternalActionSwap.swap()`.
3. `callRouter()` executes the LI.FI/router calldata and returns an output amount `swappedAmount < X` (e.g., due to bad routing, MEV, or a compromised `externalActionMetadata`).
4. `swap()` only checked `slippageValues[1] != 0` beforehand — no comparison against `swappedAmount` occurs.
5. The under-value amount is shielded into the user's new UTXO with no revert, silently violating the user's committed minimum-output guarantee. [6](#0-5)

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
