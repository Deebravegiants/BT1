### Title
Refund-before-charge ordering in `try_into_deposit` permanently strands the storage base deposit when a contract self-terminates during instantiation - (`substrate/frame/contracts/src/storage/meter.rs`)

### Summary
`RawMeter::try_into_deposit` splits all queued `Charge`/`Refund` entries into two independent passes — refunds first, then charges — instead of processing them per-contract in causal order. When a contract terminates itself in the same call frame where a `Deposit::Charge` for that same contract account was queued but not yet transferred (e.g. the base-deposit charge produced by `charge_instantiate`), the refund pass tries to release a hold that doesn't exist yet, silently drops the shortfall via `Precision::BestEffort`, and then the charge pass still moves the deposit to the now-terminated/dead contract account, where it becomes permanently stuck.

### Finding Description
`RawMeter::terminate` sets `own_contribution = Contribution::Terminated { deposit: Deposit::Refund(info.total_deposit()), beneficiary }` [1](#0-0)  using `info.total_deposit()`, which already reflects any in-memory `ContractInfo` field updates (e.g. `storage_base_deposit`) even though the corresponding on-chain balance hold has not been created yet.

During instantiation, `charge_instantiate` computes the base deposit via `contract_info.update_base_deposit(&code_info)` and immediately queues it with `self.charge_deposit(contract.clone(), deposit)`, which pushes a `Charge{contract, Deposit::Charge(deposit), Alive}` entry directly into `self.charges` without performing any transfer at that point [2](#0-1) . If the contract's constructor immediately self-terminates (calls `seal_terminate`), `terminate()` runs on the very same nested meter, and `info.total_deposit()` already includes this un-transferred base deposit.

When this nested meter is absorbed into its parent, `absorb()` first copies the already-queued `Charge{contract, Charge(deposit), Alive}` entry via `self.charges.extend_from_slice(&absorbed.charges)`, then appends a second entry `Charge{contract, Refund(total_deposit), Terminated{beneficiary}}` from the terminated `own_contribution` [3](#0-2) . Both entries reference the same contract account, but only the first is a real matching amount — the refund amount was never actually held.

At the top of the call stack, `try_into_deposit` processes all `Refund` entries first, then all `Charge` entries, regardless of ordering or causal dependency [4](#0-3) . In `ReservingExt::charge`'s `Deposit::Refund` branch, `transfer_on_hold` is called with `Precision::BestEffort`; since no hold for the base deposit exists yet, `transferred` is short, and the code merely logs an error rather than failing the call [5](#0-4) . Because `state` is `Terminated`, this same branch also decrements the consumer ref and sweeps all remaining reducible balance from the contract to the beneficiary [6](#0-5) . Only afterward does the charge pass run `transfer_and_hold`, actually moving the deposit amount from `origin` to the now-terminated, consumer-decremented contract account and placing a hold there [7](#0-6) . That balance is now held on a dead contract account with no remaining contract logic that could ever trigger its release.

The comment "We only have one charge per contract hence the size of this vector is limited by the maximum call depth" [8](#0-7)  shows the design assumed at most one `Charge` entry per contract account, but `charge_deposit` and termination can both legitimately add an entry for the same account within a single call frame, breaking that assumption and the refund/charge ordering invariant.

### Impact Explanation
An unprivileged account that instantiates a contract whose constructor immediately self-terminates causes the base storage deposit to be paid by the origin and locked as a hold on the terminated (dead) contract account instead of being refunded. The funds are neither returned to the origin nor usable/held meaningfully by any live contract — they are permanently stranded (`HoldReason::StorageDepositReserve` on an account with no `ContractInfo` left to release it), a real loss of user funds matching the scoped "stuck/lost" impact.

### Likelihood Explanation
This requires no special privilege — any account can submit an `instantiate`/`instantiate_with_code` extrinsic whose constructor calls `seal_terminate`. It is fully deterministic and repeatable on every such instantiation, since `charge_instantiate` always queues the base deposit via `charge_deposit` before constructor execution, and `terminate()` always captures `info.total_deposit()` at that point.

### Recommendation
Process deposit entries per-contract in causal (insertion) order rather than splitting into a global refund-then-charge pass, or ensure `try_into_deposit`/`absorb` merge same-contract `Charge`/`Refund` entries into a single net amount before applying transfers, so a refund can never be attempted against an amount that has not yet been transferred/held for that same contract.

### Proof of Concept
Rust unit test in `substrate/frame/contracts/src/storage/meter.rs` test module:
1. Build a `TestMeter` root meter for `ALICE` with a limit.
2. Create a nested meter for contract `BOB`, call `charge_deposit(BOB, Deposit::Charge(100))` to emulate the base-deposit queue from `charge_instantiate`.
3. On the same nested meter call `terminate(&info_with_total_deposit_100, CHARLIE)`.
4. Absorb into root, call `try_into_deposit(&Origin::Signed(ALICE))`.
5. Assert via `TestExt` recorded charges that a `Deposit::Refund(100)` for `BOB` is dispatched to `E::charge` before the corresponding `Deposit::Charge(100)` for `BOB`, proving the refund executes with no prior matching hold.
6. In an integration test using `ReservingExt` with real `pallet-balances` holds, assert final invariant: `held_balance(BOB) + free_balance(ALICE-delta) == expected`, and show it fails (deposit amount ends up permanently held on `BOB`, `ALICE` never receiving it back), reproducing the silent `log::error!` under-transfer path.

	pub fn absorb(
		&mut self,
		absorbed: RawMeter<T, E, Nested>,
		contract: &T::AccountId,
		info: Option<&mut ContractInfo<T>>,
	) {
		let own_deposit = absorbed.own_contribution.update_contract(info);
		self.total_deposit = self
			.total_deposit
			.saturating_add(&absorbed.total_deposit)
			.saturating_add(&own_deposit);
		self.charges.extend_from_slice(&absorbed.charges);
		if !own_deposit.is_zero() {
			self.charges.push(Charge {
				contract: contract.clone(),
				amount: own_deposit,
				state: absorbed.contract_state(),
			});
		}
	}

	pub fn charge_instantiate(
		&mut self,
		origin: &T::AccountId,
		contract: &T::AccountId,
		contract_info: &mut ContractInfo<T>,
		code_info: &CodeInfo<T>,
	) -> Result<(), DispatchError> {
		debug_assert!(matches!(self.contract_state(), ContractState::Alive));

		// We need to make sure that the contract's account exists.
		let ed = Pallet::<T>::min_balance();
		self.total_deposit = Deposit::Charge(ed);
		T::Currency::transfer(origin, contract, ed, Preservation::Preserve)?;

		// A consumer is added at account creation and removed it on termination, otherwise the
		// runtime could remove the account. As long as a contract exists its account must exist.
		// With the consumer, a correct runtime cannot remove the account.
		System::<T>::inc_consumers(contract)?;

		let deposit = contract_info.update_base_deposit(&code_info);
		let deposit = Deposit::Charge(deposit);

		self.charge_deposit(contract.clone(), deposit);
		Ok(())
	}
