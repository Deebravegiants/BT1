### Title
Missing relayer-authentication gate on `BandwidthManager.onAccept` leaves `Withdraw`/`SetTiers` governance actions unprotected against the forged-consensus attack that every other app-level governance handler defends against - (File: evm/src/apps/BandwidthManager.sol)

### Summary
Every other Hyperbridge app that receives cross-chain governance instructions (`ExtrinsicIntents.onAccept`, `SimplexPaymaster.onAccept`, `HostManager.onAccept`) checks `incoming.relayer` against a stored, admin-set authorized relayer before decoding or acting on the request body. This second layer of authorization was specifically added (documented in `sdk/packages/core/docs/ai/decisions/2026-09-03-hostmanager-deliveries-are-gated-too-and-that-does-not-touch.md`) because a forged consensus proof lets an attacker swap in a malicious handler that reports any address as `incoming.relayer`, defeating the `request.source == hyperbridge` check alone. `BandwidthManager.onAccept` never adopted this gate, leaving its `Withdraw` and `SetTiers` actions reachable by anyone able to deliver a message whose `source` field claims to be Hyperbridge — exactly the "high-risk actions not covered by the existing checks" pattern from the referenced report, where some sensitive admin/governance actions got the mitigating check and others (analogous to `MigrateKernel`) did not.

### Finding Description
`BandwidthManager.onAccept` ( [1](#0-0) ) only checks `onlyHost` and `request.source.equals(hyperbridge)` before dispatching on `OnAcceptActions.SetTiers` or `OnAcceptActions.Withdraw`. It does not check `incoming.relayer` against any authorized address.

Compare this to `HostManager.onAccept`, which gates on both the host and the admin/relayer before decoding `Withdraw`/`SetHostParam`/`SetAdmin`: [2](#0-1) 

And `ExtrinsicIntents.onAccept`, which calls `_checkRelayer(incoming.relayer)` before any governance action is decoded: [3](#0-2) 

And `SimplexPaymaster.onAccept`, same pattern: [4](#0-3) 

The design rationale explicitly documents why this second check matters: the `source == hyperbridge` check alone is insufficient once a handler swap has occurred (or, more directly, once the underlying consensus proof itself is forged), because a forged consensus proof lets the attacker set `request.source` to whatever it wants inside the fabricated message; only the extra relayer identity check — anchored to an admin-controlled value, not to consensus-verified data — narrows who can actually exploit that: [5](#0-4) 

`BandwidthManager` never received this hardening, so its `Withdraw` (which transfers the contract's ERC-20 or native balance to an arbitrary beneficiary) and `SetTiers` (which controls the fee schedule) actions remain reachable by any relayer that can get a forged/compromised consensus proof accepted by the handler, exactly the gap the HostManager gate was built to close for the rest of the system.

### Impact Explanation
`Withdraw` directly transfers out any ERC-20 or native token balance held by `BandwidthManager` (accumulated bandwidth-purchase revenue) to an attacker-chosen `beneficiary` — concrete theft of funds. `SetTiers` lets the attacker rewrite the price of every bandwidth tier, which can be used to grief the purchase flow. Because `BandwidthManager` is the one app-level governance handler in the codebase without the relayer gate, it is a weak link: exploiting the same class of consensus-forgery risk that motivated gating `HostManager`, `ExtrinsicIntents`, and `SimplexPaymaster` still succeeds against `BandwidthManager`.

### Likelihood Explanation
This requires the same precondition the HostManager gate was built to defend against (a forged/compromised consensus proof reaching the handler) — not a trivial precondition, but one the codebase's own security model treats as a real threat worth defending every other governance-receiving app against. Given that defense exists everywhere else, `BandwidthManager`'s omission is a genuine, identifiable inconsistency rather than a hypothetical.

### Recommendation
Add the same relayer-authorization gate used by `HostManager`, `ExtrinsicIntents`, and `SimplexPaymaster` to `BandwidthManager.onAccept`: store an authorized relayer/admin address and require `incoming.relayer == authorizedRelayer` before decoding and acting on `SetTiers` or `Withdraw`, mirroring `_checkRelayer`/`restrict(incoming.relayer, admin)` patterns already present elsewhere in the codebase.

### Proof of Concept
1. Attacker forges (or otherwise compromises) a consensus proof that the `handler` accepts, producing a `PostRequest` with `source = hyperbridge`, `to = BandwidthManager`, and `body = [OnAcceptActions.Withdraw] ++ abi.encode(Withdrawal{token: feeToken, beneficiary: attacker, amount: fullBalance})`.
2. Attacker (as any relayer) submits this through `HandlerV2.handlePostRequests`, which calls `host.dispatchIncoming(request, attacker)`.
3. `EvmHost.dispatchIncoming` calls `BandwidthManager.onAccept(IncomingPostRequest(request, attacker))`.
4. `onAccept` checks only `onlyHost` and `request.source == hyperbridge`; both pass. It decodes the `Withdraw` action and transfers `fullBalance` of `feeToken` to `attacker` — no check is ever made that `attacker` (the relayer) is authorized, unlike the equivalent code paths in `HostManager`, `ExtrinsicIntents`, and `SimplexPaymaster`.

# 2026-09-03 — `HostManager` deliveries are gated too, and that does not touch permissionless relaying

Chosen: `HostManager.onAccept` refuses any relayer but the one the host admin set, zero included.

The app gates check an address the host reports, and the host takes it from its handler. The
handler is a host parameter that a `SetHostParam` governance message can replace, and until now
any relayer could deliver that message once its consensus proof verified. Under a forged consensus
an attacker would swap in a handler that reports the whitelisted relayer on every message, and the
app gates would pass. Gating the HostManager closes that route.

It does not weaken the open-relayer model because the HostManager never carries user traffic. Its
first check already rejects anything not sourced from Hyperbridge, so the only messages it ever
sees are Polytope's own `Withdraw` and `SetHostParam`. Third-party relayers keep delivering every
ordinary message to every ordinary app exactly as before.
