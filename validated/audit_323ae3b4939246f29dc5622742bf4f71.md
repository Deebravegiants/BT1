## Title
Order placer can collide an input token with the `TRANSACTION_FEES` sentinel address to corrupt fee accounting and freeze the solver's fee payout - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase` stores per-order escrow amounts in `_orders[commitment][token]`, keyed by the token's `address`. Relayer/solver fees collected at `placeOrder` time are stored in the *same* mapping under a public sentinel key, `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))` [1](#0-0) . Because `Order.inputs[i].token` is a `bytes32` chosen entirely by the order placer and is only truncated to an `address` before being used as a mapping key, nothing stops an order from declaring an "input token" equal to this same sentinel address, letting the placer collide their own fake escrow entry with the real fee-accounting slot.

### Finding Description
`placeOrder` credits each declared input into escrow using the raw truncated address as the key, with only a same-commitment duplicate check, no check against `TRANSACTION_FEES` or any other reserved address: [2](#0-1) 

If the order fee is set (`order.fees > 0`), the same key is *unconditionally overwritten*: [3](#0-2) 

At settlement time, `_withdraw` iterates `body.tokens` (which is simply `order.inputs`, attacker-controlled) and, for each entry, decrements `_orders[commitment][token]` and calls `IERC20(token).safeTransfer(...)` or `_sendValue(...)`: [4](#0-3) 

Then, separately, it reads whatever remains at the `TRANSACTION_FEES` key and pays it out in the *real* fee token: [5](#0-4) 

Because `TRANSACTION_FEES` is a `public constant` address with no deployed contract code, calling `IERC20(TRANSACTION_FEES).safeTransfer(...)`/`safeTransferFrom(...)` against it is a no-op "success" (an external call to an address with no code trivially returns success with empty return data, which OpenZeppelin's `SafeERC20` treats as a successful transfer). This lets an order placer:

1. Add a bogus `TokenInfo` to `order.inputs` with `token = TRANSACTION_FEES` and an attacker-chosen `amount = Y`. No real value is escrowed for this entry (the `safeTransferFrom` against the sentinel address moves nothing).
2. If `order.fees > 0`, that same storage slot is subsequently overwritten to `order.fees` (a real amount of the fee token that *is* actually pulled from the placer during `placeOrder`).
3. During settlement (`onGetResponse`/`onAccept` → `_withdraw`), the bogus input entry `{token: TRANSACTION_FEES, amount: Y}` is processed against `_orders[commitment][TRANSACTION_FEES]`, which now actually holds `order.fees`:
   - If `Y > order.fees`: `escrowed - amount` underflows and the whole withdrawal reverts (`_withdraw` is the only path that returns escrow or fees to anyone), **permanently freezing** the entire order's escrow and fees — no cancellation, fill, or timeout path can ever complete, since every settlement route funnels through this same function.
   - If `Y <= order.fees`: the loop siphons `Y` "units" out of the shared slot via a no-op transfer, so the subsequent `fees = _orders[commitment][TRANSACTION_FEES]` block only pays out `order.fees - Y` of the real fee token to the beneficiary (solver on a fill, or the user on a cancel), even though the placer deposited the full `order.fees` amount of the real fee token up front. The difference is stranded, permanently unaccounted for, in the gateway contract.

This is the direct analog of the Brave/BAT bug: a single reserved accounting bucket (there, `batFundDeposit`'s pre-minted balance; here, the `TRANSACTION_FEES` key) is reachable through the same public entry point (there, `refund()`; here, `placeOrder`'s attacker-controlled `inputs` array feeding into `_withdraw`) that legitimate participants use, without a guard preventing the privileged/reserved key from being manipulated by an ordinary caller.

### Impact Explanation
- **Freezing of funds (High):** By setting a bogus input `amount` larger than `order.fees`, the placer can force every future call to `_withdraw` for that order commitment to revert (arithmetic underflow), permanently trapping the escrowed input tokens and the fee-token deposit in the `IntentGatewayV2` contract with no recovery path (same-chain cancel, source-chain cancel-via-GET, destination-chain cancel, and normal fill/settlement all route through `_withdraw`).
- **Fee-token value siphoning / stuck dust (Medium-High):** With a smaller bogus amount, the solver/relayer or refunded user receives less of the fee token than the order committed to pay, while the gateway silently retains the shortfall — a partial, systemic value leak from every order that uses this trick.

### Likelihood Explanation
Likelihood is high: `TRANSACTION_FEES` is a `public constant`, trivially computable off-chain (`keccak256("txFees")` truncated). Any order placer fully controls `Order.inputs` and can add this collision entry at zero cost beyond normal placement gas (the token "transfer" for the sentinel is a costless no-op). No special privileges, front-running, or race conditions are required — a single `placeOrder` transaction is sufficient to set up the freeze/siphon.

### Recommendation
In `placeOrder` (and the Tron variant), explicitly reject any `order.inputs[i].token` (and `output.assets[i].token`) that truncates to the `TRANSACTION_FEES` sentinel address (and any other reserved address, e.g. keep the `address(0)` native-token exception explicit and disjoint from other reserved slots). Revert with `InvalidInput()` if `token == TRANSACTION_FEES`. Additionally, consider isolating the fees accounting into a dedicated mapping (e.g. `_orderFees[commitment]`) instead of overloading the same `token => amount` mapping used for arbitrary user-supplied token addresses, removing the possibility of key collisions entirely.

### Proof of Concept
1. Attacker computes `TRANSACTION_FEES = address(uint160(uint256(keccak256("txFees"))))` (public constant, same value on every deployment).
2. Attacker calls `placeOrder` with:
   - `inputs = [ {token: <real token>, amount: X}, {token: TRANSACTION_FEES, amount: Y} ]`
   - `fees = F` (any nonzero real fee, e.g. paid in DAI/fee-token)
3. `placeOrder`'s Phase 3 loop sets `_orders[commitment][TRANSACTION_FEES] = Y` first (from the bogus input, no real transfer occurs since there's no contract at that address), then the `order.fees > 0` block overwrites it to `_orders[commitment][TRANSACTION_FEES] = F` (real fee-token pulled from attacker).
4. Attacker cancels same-chain (or lets a solver fill / cancels cross-chain) — `_withdraw` is invoked with `body.tokens` containing the bogus `{TRANSACTION_FEES, Y}` entry.
5. Case `Y > F`: `_orders[commitment][TRANSACTION_FEES] - Y` underflows → revert. The entire order (all escrowed inputs, plus the real fee-token deposit) is permanently stuck since `_withdraw` can never succeed for this commitment again.
6. Case `Y <= F`: the loop's no-op transfer of `Y` "units" of the sentinel pseudo-token succeeds and decrements the shared slot to `F - Y`; the subsequent fee payout block sends only `F - Y` of the real fee token to the beneficiary, permanently stranding `Y` units of real fee token in the gateway contract, unaccounted for by any event or recoverable path.
