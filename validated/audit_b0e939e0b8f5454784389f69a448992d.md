### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never included in the signed material, so any attacker who can obtain one validly-signed webhook body (which happens automatically for every shop that installs the app, since Shopify signs webhooks using the app's single shared `api_secret_key`, not a per-shop key) can replay that body with forged identity headers and impersonate any other tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers that are outside that signed string: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string`, i.e. the raw body, using the single app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values straight to the handler: [4](#0-3) 

This breaks the intended binding: `HMAC-authenticated bytes (raw_body) == identity used by the application (shop, topic, webhook_id)`. Because Shopify signs app webhooks with the app's shared `client_secret`/`api_secret_key` (the same key used for OAuth HMAC validation, not a per-installation secret), *any* shop that has installed the app receives genuinely-signed webhook deliveries. A malicious merchant can therefore:
1. Install the app on their own shop and capture one legitimate webhook `{raw_body, X-Shopify-Hmac-Sha256}` pair.
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with an arbitrary victim shop domain.
3. `HmacValidator.validate` still succeeds (the body/HMAC pair is untouched), and `Registry.process` calls the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload never originated from Shopify for that shop.

### Impact Explanation
This is a cross-tenant boundary break: the gem hands the host application attacker-chosen `shop`/`topic`/`webhook_id` values as if they were authenticated by Shopify, for any shop the application serves — including shops the attacker does not control. Any host application logic keyed off `WebhookMetadata.shop` (record lookups, state transitions, `app/uninstalled` handling, GDPR/webhook processing, etc.) can be triggered against a victim tenant using only the attacker's own legitimately-received webhook traffic and no access to the app's `client_secret` or any victim credentials. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Any unprivileged internet user who can install the app on a shop they control (a normal, low-privilege action for a public Shopify app) automatically receives correctly-signed webhook traffic, because the signing key is shared across all installations rather than being shop-specific. No special access, leaked secret, or social engineering is required — only reuse of the library's documented `Registry.process` API exactly as intended by the host application.

### Recommendation
Bind the trusted identity fields to the authenticated bytes instead of trusting headers outright:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them), or
- Require the host application to independently verify that the `shop` in `WebhookMetadata` corresponds to a shop with an active session/installation known to the app before acting on the payload, and
- Document/enforce that the `shop-domain` header must never be treated as authenticated purely on the strength of a body-only HMAC.

### Proof of Concept
```ruby
# Attacker installs the app on attacker-shop.myshopify.com and captures a real
# order/create webhook delivery it receives, e.g.:
raw_body = '{"id":1,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SHARED_SECRET, raw_body)

# Attacker replays the exact body/HMAC to the app's webhook endpoint,
# forging the shop header to a victim it does not own:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker does not control this shop
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes because HMAC only ever covered `raw_body`:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", ...))
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
