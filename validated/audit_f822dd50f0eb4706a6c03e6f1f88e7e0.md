## Finding

Given the constraints (must map to a reachable Hyperbridge path, medium+ severity, concrete impact), the closest legitimate analog to OKX's "fake sats displayed in the order book" is the phantom-order price aggregation pipeline, where an unweighted, unpinned balance read lets a bidder's quote dominate the published liquidity-weighted price that downstream consumers (LiquidityEngine/quote routing) treat as real, tradeable depth.

### Title
Unpinned "at-head" balance reads let a solver momentarily inflate its weight to force an arbitrary price into the published phantom-order snapshot - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights each solver's quoted price for a leg by that solver's live on-chain balance of the leg's output token, read via `getBalance`/`memoizedSolverBalance`. Unlike the event-triggered inventory refresh path, which pins reads to a specific historical block via `blockTags` [1](#0-0) , the phantom price-snapshot path explicitly reads "every chain at its head" with no block pinning [2](#0-1) . `weightedMedian` is a selection function, not a blend — a single bidder whose weight crosses 50% of total weight has its exact quoted price published verbatim as `medianPrice`/`lowestPrice`/`highestPrice` [3](#0-2) .

### Finding Description
Per-leg weights are computed by calling `getBalance(destUrl, chain, outputToken, solver)` at aggregation time and summing any owned Uniswap V4 position value, with no block anchoring [4](#0-3) . Because this read hits the chain "at its head" rather than at a block tied to when the bid was placed, a solver can transiently acquire a large balance of the leg's output token (e.g. moving funds in from another controlled address, or timing the read against a large balance it briefly holds) purely to inflate its `weight` for the RPC call window, then move the funds away immediately after. `weightedMedian` then selects that solver's arbitrary quoted price as the leg's published price once its weight crosses half of total weight [5](#0-4) , and the docs explicitly note this design property: "a solver holding over half the leg's weight sets the published price verbatim" [6](#0-5) .

This published, per-leg `medianPrice` is persisted as `PhantomOrderPriceSnapshotV2` and then folded by `updateLiquidityPools`/`resolvePoolLeg` into the pool's `sellRate`/`buyRate` used by the SDK's `LiquidityEngine` and `quote/indexedRates.ts` for real order quoting and routing [7](#0-6) . Because there is no verification that the balance backing the winning quote is durable capital rather than a momentary spike captured by an unpinned "latest" read, a solver with no real intent to fill at that price can transiently poison the published rate that other users and solvers rely on to price and route intents — directly analogous to OKX's order book momentarily displaying fake sats that users traded against.

### Impact Explanation
Users and downstream routing logic (`LiquidityEngine`, `indexedRates`) treat the published `medianPrice`/pool rates as a trustworthy, liquidity-backed quote. A manipulated snapshot can misprice a route, causing real users to commit real order flow expecting a rate that no durable solver capital actually backs, resulting in economic loss (bad fills, mispriced routing, or an order the "backing" solver cannot or will not actually fill at). This is a Medium-severity data-integrity issue affecting the intents pricing pipeline reachable from any relayed bid — a permissionless, unprivileged action (submitting a phantom-order bid) can corrupt a value multiple downstream consumers of Hyperbridge's intent infrastructure use for real financial decisions.

### Likelihood Explanation
Exploitation requires only: (1) being a delegated `SolverAccount` (a normal, permissionless step any address can complete via EIP-7702 delegation), (2) submitting a well-formed, signed bid for a phantom order, and (3) timing a transient balance inflation of the leg's output token to coincide with the indexer's unpinned RPC read. No privileged role, governance, or consensus-layer compromise is needed — this is reachable from a single relayed bid/order, satisfying the in-scope "unprivileged … bandwidth purchaser/intent solver" reachability bar.

### Recommendation
Pin the phantom-order balance/position reads (`getBalance`, `readPosition`) used in `aggregatePhantomBids` to a specific, deterministic block (e.g., the block at which the bid window closed / `PhantomBidWindowExhausted` fired), mirroring the `blockTags` mechanism already used by the event-triggered inventory-refresh path in `solverBalance.ts`. Alternatively, require weight to be attested by a minimum holding duration or a bonded/staked amount rather than a spot balance, so a solver cannot manufacture instantaneous weight to dictate the published price.

### Proof of Concept
1. Attacker becomes a delegated solver for chain `X` (standard EIP-7702 delegation to `SolverAccount`).
2. Attacker submits a phantom-order bid quoting an extreme price for a leg, satisfying `isVerifiedSolverBid` (valid nonce binding + signature) [8](#0-7) .
3. Immediately before/during the indexer's `PhantomBidWindowExhausted`-triggered aggregation run, attacker transiently funds its solver address with a large balance of the leg's output token (e.g. a short-lived transfer from another wallet it controls), then withdraws it right after.
4. `getBalance` reads this balance at "head" with no block pin [9](#0-8) , giving the attacker's quote overwhelming weight.
5. `weightedMedian` selects the attacker's arbitrary quoted price as `medianPrice`/`lowestPrice`/`highestPrice` for that leg [10](#0-9) , which is persisted to `PhantomOrderPriceSnapshotV2` and folded into the pool rates consumed by real intent quoting/routing.

/** The on-chain reads a refresh needs, pinned to one block and memoized for it. */
export interface BlockReaders {
	getBalance: SolverBalanceReader
	/** Null when the position no longer exists; throws when it cannot be read at all. */
	readPosition: (chain: string, tokenId: bigint) => Promise<V4PositionState | null>
}

// Reads are point-in-time and cannot differ within a block, so one memo serves every read on it —
// without this, several orders closing on the same Hyperbridge block would each repeat the full
// liquidity sweep, and several events in one EVM block would each re-read the same bidders and the
// same positions. Blocks are processed in order, so keeping only the current block's memo is enough.
let memoKey: string | null = null
let memo: BlockReaders | null = null

/**
 * The readers for `key`, which must identify one block of one chain (handlers for different chains
 * run in separate processes, so the key only has to be unique within one).
 *
 * `blockTags` pins a chain to a specific block, so an event's re-read returns the same value on a
 * replay as it did live. The phantom sweep pins nothing and reads every chain at its head.
 */
export function blockReaders(key: string, blockTags: Record<string, string> = {}): BlockReaders {
	if (memoKey !== key || !memo) {
		memo = {
			getBalance: memoizedSolverBalance(YIELD_VAULT_ADDRESSES, blockTags),
			readPosition: positionReader(blockTags),
		}
		memoKey = key
	}
	return memo
}

// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

async function isVerifiedSolverBid(params: {
	userOp: PackedUserOperation
	commitment: string
	sessionKey: HexString
	chainId: bigint
	solverAccounts: readonly string[]
	evmRpcUrl: string
	recoverSigner: RecoverBidSigner
	bidNonceKey: BidNonceKeyFn
	/** Cached per aggregation, so duplicate fillers and retries do not re-read the same answer. */
	isDelegated: DelegationReader
	logger?: AggregationLogger
}): Promise<boolean> {
	const {
		userOp,
		commitment,
		sessionKey,
		chainId,
		solverAccounts,
		evmRpcUrl,
		recoverSigner,
		bidNonceKey,
		isDelegated,
		logger,
	} = params
	const solver = userOp.sender

	const parsed = splitBidSignature(userOp.signature)
	if (!parsed) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: malformed userOp signature")
		return false
	}

	// Cheap early-out ONLY. The prefix sits inside userOp.signature, which userOpHash excludes, so it
	// is attacker-mutable and must never be what binds a bid to an order — the nonce key below is.
	if (parsed.commitment.toLowerCase() !== commitment.toLowerCase()) {
		logger?.warn(
			{ solver, commitment, signedFor: parsed.commitment },
			"Rejecting phantom bid: signed for another order",
		)
		return false
	}

	// The authoritative binding, mirroring SolverAccount.validateUserOp on-chain. The nonce IS
	// covered by userOpHash, so a solver signature stays valid only for the (order, sessionKey) pair
	// its nonce key was derived from. `sessionKey` is read from the bid's own calldata, which is also
	// covered by userOpHash — so every operand here is signed, leaving nothing for a replay to swap.
	if (BigInt(userOp.nonce) >> 64n !== bidNonceKey(commitment as HexString, sessionKey)) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: nonce does not bind order and session key")
		return false
	}

	// SolverAccount._rawSignatureValidation recovers over the bare userOpHash and requires the signer
	// to be the account itself, which under EIP-7702 is the sender EOA.
	const signer = await recoverSigner(userOp, ENTRY_POINT_V08_ADDRESS, chainId, parsed.solverSignature)
	if (!signer || signer.toLowerCase() !== solver.toLowerCase()) {
		logger?.warn({ solver, commitment, signer }, "Rejecting phantom bid: signature does not recover to the sender")
		return false
	}

	if (!(await isDelegated(evmRpcUrl, solver, solverAccounts))) {
		logger?.warn({ solver, commitment, solverAccounts }, "Rejecting phantom bid: sender is not a delegated solver")
		return false
	}

	return true
