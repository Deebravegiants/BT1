Confirmed: the Tron variant of the intent gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) escrows and later releases the *requested/reduced* amount rather than the amount actually received, unlike the primary EVM implementation which was hardened against fee-on-transfer tokens.

### Title
Fee-on-transfer / deflationary token accounting mismatch causes escrow insolvency in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`placeOrder` in the Tron `IntentGatewayV2.sol` credits the internal `_orders[commitment][token]` escrow ledger with `reducedInputs[i].amount` — the user-declared amount minus the protocol fee — without ever verifying that this is the amount the contract actually received via `safeTransferFrom`. For fee-on-transfer/deflationary ERC20 tokens, the actual balance increase is smaller than the credited escrow value, creating a permanent accounting deficit that is paid out of other users' escrowed funds when `withdraw()` is later called.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally increments `_orders[commitment][token] += reducedInputs[i].amount`. It never measures `balanceOf(address(this))` before/after the transfer, so for a fee-on-transfer token the escrow ledger records more tokens than the gateway physically holds.

The predispatch branch has the same flaw: it computes `dust = balance - requiredAmount` and credits escrow with `reducedInputs[i].amount` (the pre-fee requested amount reduced only by the protocol fee), rather than the amount actually swept from the dispatcher, at: [2](#0-1) 

This is in stark contrast to the primary EVM implementation, `evm/src/apps/IntentGatewayV2.sol`, which explicitly snapshots balances before and after every transfer and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment and crediting escrow: [3](#0-2) 
The code comment there states: *"For fee-on-transfer tokens, the gateway receives less than the requested amount... We mutate order.inputs to reflect actual received so the commitment and escrow are consistent with what the gateway holds."* This hardening is absent from the Tron contract.

When `withdraw()` later pays out the escrowed amount to the solver/beneficiary: [4](#0-3) 
it transfers `body.tokens[i].amount` (the inflated, ledger-recorded amount) out of the contract's actual token balance, which is insufficient to cover all outstanding escrows across all orders once a fee-on-transfer token has been used once.

### Impact Explanation
Any order placed with a fee-on-transfer/deflationary ERC20 token overcredits the escrow ledger relative to the tokens physically held by the contract. Because `_orders` is a shared per-token accounting structure across all commitments, this shortfall is not isolated to the depositor's own order — it is paid for out of the pooled balance of that same token across all other orders/users, i.e. later legitimate withdrawals for unrelated orders can fail (funds frozen) or, if solvers/relayers race withdrawals, the last claimants are left unable to redeem their rightful escrow (funds effectively stolen from them). This is a fund-loss/freezing bug directly reachable by a single unprivileged `placeOrder` call with an attacker-chosen or naturally fee-on-transfer token.

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with a fee-on-transfer or rebasing-deflationary ERC20 as an input token — no special privileges, governance, or relayer collusion required. Many real-world tokens (some stablecoins under certain modes, various "tax" tokens) implement this behavior, and nothing in `placeOrder` or the token allow-list logic in this file prevents such tokens from being used as inputs.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot `balanceOf(address(this))` (or the dispatcher's balance, for the predispatch path) immediately before and after each `safeTransferFrom`/sweep, and credit `_orders[commitment][token]` with the actually-received delta (after subtracting the protocol fee proportionally), not with the caller-declared `order.inputs[i].amount` / `reducedInputs[i].amount`. Apply the same actual-received accounting consistently to both the direct-transfer and predispatch branches of `placeOrder` in the Tron contract.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 token `FOT` that deducts, e.g., 1% on every `transfer`/`transferFrom`.
2. User A calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000}` (no protocol fee, `protocolFeeBps == 0`). The contract's `safeTransferFrom` call actually delivers only 990 FOT to the gateway, but `_orders[commitmentA][FOT]` is credited with `1000`.
3. User B independently places another order using the same `FOT` token, similarly overcrediting `_orders[commitmentB][FOT]` relative to actual balance received.
4. When solver fills order A and the settlement message triggers `withdraw()`, the contract calls `token.call(transfer, beneficiary, 1000)` — drawing on the pooled `FOT` balance that includes the shortfall from order A itself plus tokens meant for order B's escrow.
5. Once cumulative escrow entries across orders exceed the gateway's actual `FOT` balance, subsequent legitimate `withdraw()` calls for other orders revert/fail (transfer with insufficient balance) or race to drain the remaining balance, leaving some order beneficiaries permanently unable to redeem escrowed funds they are entitled to.
