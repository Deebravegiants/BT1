### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards the `shop-domain` header — a value that is *not* part of the signed bytes — to the application's webhook handler as the tenant identity. Since Shopify webhook HMACs are computed with the app's single `client_secret` (shared across every shop that installs the app), any shop that has legitimately installed the app can obtain a validly-signed `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. The gem will report the request as authentic and hand the attacker-chosen `shop` value to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines its signable content as only the raw body: [1](#0-0) [2](#0-1) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which plays no part in `to_signable_string`. `ShopifyAPI::Utils::HmacValidator.validate` only ever hashes `to_signable_string` (the body) against `Context.api_secret_key`: [3](#0-2) 

`Registry.process` uses this single check as the sole authentication gate, then passes the unauthenticated `request.shop` straight into the metadata handed to the app's webhook handler: [4](#0-3) 

The broken identity binding, stated as an equality that the code assumes but does not enforce:
`hmac_valid(raw_body, api_secret_key) == true` is treated as implying `shop-domain header == tenant that produced this event`, but the header is never included in the HMAC input, so the two are independent.

Because Shopify signs webhooks with the app's `client_secret` — the same secret regardless of which installed shop the event originates from — any unprivileged user who installs the app on their own (attacker-controlled) development store legitimately receives `(body, hmac)` pairs that are valid under the app's secret. That user can then POST the exact same body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at headers), so `Registry.process` dispatches the forged event to the handler tagged with the victim's shop.

### Impact Explanation
This breaks tenant isolation: an attacker with a legitimate installation of the app (no credentials belonging to the victim) can make the host application believe an event (e.g., `app/uninstalled`, `customers/data_request`, `shop/update`, or any subscribed topic) originated from an arbitrary victim shop. Any host-application logic that keys off `WebhookMetadata#shop` for tenant-scoped side effects (updating shop settings, triggering data deletion, revoking access, billing state changes, etc.) can be manipulated cross-tenant using only the attacker's own valid HMAC secret knowledge. This matches the Critical "cross-tenant access" impact category, since the binding between the cryptographically verified bytes and the tenant identity used for authorization does not hold.

### Likelihood Explanation
Likelihood is Medium-to-High for apps that trust the `shop` field of `WebhookMetadata` for tenant-scoped actions (the documented/intended use, since `WebhookMetadata` exposes `shop` precisely for this purpose). Exploitation requires only: (1) the attacker legitimately installs the target app on any shop they control (a normal, unprivileged action), (2) knowledge of the app's public webhook endpoint (also public/documented), and (3) the ability to send an HTTP POST with custom headers — no access token, `client_secret`, or victim credentials are needed.

### Recommendation
Do not treat headers as authenticated once only the body HMAC has been checked. Either:
1. Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signed payload verification (would require Shopify-side signing changes), or
2. Cross-check the `shop-domain` header against a shop known/expected by the app (e.g., only accept webhooks for shops that have an active session/installation record) before dispatching to the handler, and document clearly in `WebhookMetadata` that `shop` is unauthenticated header data that must be revalidated by the host app, or
3. At minimum, add a check in `Registry.process` that the shop the webhook claims to be for has a currently valid installation/session, rejecting unknown or mismatched shops before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev store `attacker.myshopify.com`, subscribing to a webhook topic (e.g. `app/uninstalled`).
2. Shopify sends the webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` and resends a POST to the same endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `HmacValidator.validate` recomputes HMAC over `B` only and matches `H` — validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the host app's handler as if the event came from the victim shop.

          received_signature = verifiable_query.hmac
