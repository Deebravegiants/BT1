### Title
Webhook shop-domain identity spoofing — HMAC covers only the raw body, not the `shop-domain` header used for tenant identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only. The `shop-domain` (tenant identity) header is read separately and is **not** included in the HMAC-covered bytes, yet `Registry.process` forwards that unauthenticated header directly to the app's handler as the trusted shop identity.

### Finding Description
The webhook signature verification path is:

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` is parsed independently from the `x-shopify-shop-domain`/`shopify-shop-domain` header, outside the signed bytes: [2](#0-1) 
- `HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`, i.e. only the body: [3](#0-2) 
- `Registry.process` checks only this body-HMAC, then dispatches `request.shop` — the unauthenticated header — straight into `WebhookMetadata`, which the handler treats as the verified tenant identity: [4](#0-3) 
- `WebhookMetadata#shop` is a plain `String` field with no further validation or binding to the signature: [5](#0-4) 

The binding that is broken is:
`shop authenticated (bytes covered by HMAC)` ≠ `shop used as tenant/session key (request.shop header, unauthenticated)`.

Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every shop that has installed the app, any merchant who has installed the app can capture a real, validly-signed webhook delivered to their own endpoint (a normal, unprivileged action — merchants receive their own webhooks) and replay the identical body with the `x-shopify-shop-domain` header rewritten to a different tenant's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen domain, causing the host application to act on data attributed to a different, victim tenant.

### Impact Explanation
This lets one tenant (installer of the app) impersonate another tenant's webhook stream to the shared handler, i.e. cross-tenant confusion. If the host application uses `WebhookMetadata#shop` to look up per-shop state, credentials, or to trigger merchant-scoped side effects (order sync, inventory updates, uninstall/GDPR handling, billing events, etc.) without independently re-verifying the shop against its own install records, an attacker-controlled shop can inject events that are processed under a victim shop's identity — a cross-tenant access primitive that meets the Critical bar in this analysis. It requires no access token, no leaked secret, and no privileged account: only the ability to install the app once (unprivileged internet user) and replay an HTTP request with a modified header.

### Likelihood Explanation
Moderate-to-high. Any developer/tester who signs up for the app can capture a legitimate webhook (body + valid HMAC) sent to their own endpoint, then simply change one header value and re-POST it to the app's webhook listener. No cryptographic material beyond what a normal installer already legitimately receives is needed. The precondition — the app trusting `request.shop`/`WebhookMetadata.shop` without cross-checking against its own installation records — is a natural, easy-to-miss integration mistake given that the gem's `process` method gives the impression that a validated `Request` carries fully-authenticated metadata.

### Recommendation
Include the tenant-identifying headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the signable content used for HMAC verification in `Request#to_signable_string`, or otherwise cryptographically bind them to the payload before exposing `WebhookMetadata` to handlers. Until fixed, document prominently that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host app against its own list of installed shops before use.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (no privileges beyond normal merchant install).
2. Shopify sends a legitimately-signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
   - Body: `{"id": 123, ...}`.
3. Attacker captures this request and resends it to the same endpoint, changing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - Body and `x-shopify-hmac-sha256` left untouched.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, raw_body)` — identical to the original, unchanged body — and returns `true` [6](#0-5) .
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , causing the app to process attacker-supplied data as if it originated from the victim shop.
