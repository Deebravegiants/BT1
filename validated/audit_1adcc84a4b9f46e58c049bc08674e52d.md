## Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()`/`SweepDust` on Tron leads to permanent loss of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` replaces `SafeERC20.safeTransfer` with raw low-level `.call()` invocations of the ERC20 `transfer` selector, and only checks whether the call itself reverted (`success`), never decoding/validating the boolean value the token actually returns. This is the same bug class as the referenced report: a token-moving operation's return value is never handled, only the low-level call's revert status is checked.

### Finding Description
In `withdraw()`, which releases escrowed order funds to a beneficiary on `RedeemEscrow`/`RefundEscrow`, and in the `SweepDust` admin path, token transfers are performed like this: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the external call reverted at the EVM/TVM level — it does **not** inspect the ABI-encoded return data of the call. Per the ERC20 standard, `transfer` can return `false` on failure rather than reverting (this is common for many TRC20/legacy ERC20 implementations on Tron, which is presumably why this file deviates from `SafeERC20` used elsewhere in the codebase, e.g. `evm/src/apps/IntentGatewayV2.sol` and the sibling `IntentsBase.sol`, which consistently use `IERC20(token).safeTransferFrom`/`safeTransfer`): [2](#0-1) 

Because the raw `.call()` succeeds (does not revert) even when the token contract internally returns `false`, `withdraw()` will proceed to decrement `_orders[body.commitment][token] -= amount` and emit `EscrowReleased`/`EscrowRefunded` as if the beneficiary was paid, while the tokens actually remain stuck in the `IntentGatewayV2` contract. The same unchecked pattern also appears in the transaction-fee redemption right after and in the `SweepDust` handler: [3](#0-2) [4](#0-3) 

### Impact Explanation
Once `withdraw()` runs, `_orders[body.commitment][token]` is decremented (or deleted for fees) and `_filled[body.commitment]` is set unconditionally, regardless of whether the token transfer actually delivered funds. Since `_orders[...][token] == 0` is used as the "already filled/unknown order" guard, a token that returns `false` on a failed transfer (e.g., due to a paused token, blacklist, or insufficient contract balance at time of transfer) causes:
- The escrowed tokens to become permanently unrecoverable — the beneficiary never receives them, and the escrow accounting no longer reflects a claimable balance, so the funds are stuck in the contract with no path to retry or refund.
- This is a direct fund-freezing/loss condition for solvers and users relying on `RedeemEscrow`/`RefundEscrow` fulfillment on the Tron deployment of `IntentGatewayV2`.

### Likelihood Explanation
This is reachable by anyone completing a normal cross-chain intent lifecycle (fill → relay → `RedeemEscrow`/`RefundEscrow` handling) using any ERC20/TRC20 token whose `transfer` function returns `false` instead of reverting on failure — a well-documented and common non-conforming-token behavior, especially relevant on Tron given TRC20 token ecosystem variance. No malicious actor is required; a normal, non-malicious but non-standard-compliant token is enough to trigger silent fund loss.

### Recommendation
Replace the manual `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()`, the fee-redemption block, and `SweepDust` with `SafeERC20.safeTransfer`, which is already imported and used (`using SafeERC20 for IERC20;`) elsewhere in this same contract, so both the call success and the decoded boolean return value (when present) are validated before state is updated.

### Proof of Concept
1. Create and fill an order whose input token is a non-standard ERC20/TRC20 that returns `false` on a failed `transfer` (e.g., simulate a token paused mid-flow, or one that returns `false` when the recipient is blacklisted) instead of reverting.
2. Trigger `RedeemEscrow`/`RefundEscrow`, causing `onIsmpModuleCall`/`withdraw()` at [5](#0-4)  to call `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))`.
3. The token's `transfer` returns `false` without reverting; `success` is `true`, so `if (!success) revert TransferFailed();` does not trigger.
4. `_orders[body.commitment][token] -= amount;` executes, `_filled[body.commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — the order is marked settled even though `beneficiary` never received the tokens, which remain locked in the `IntentGatewayV2` contract with no further withdrawal path for that commitment.
