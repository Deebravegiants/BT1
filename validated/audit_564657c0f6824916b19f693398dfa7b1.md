### Title
Stale public-key cache in `MemoizedKeychain#exportKey` survives `removeSeeds()`/`removeAllSeeds()`, returning public data for removed/replaced seeds - ([File: features/keychain/module/memoized-keychain.js])

### Summary
`MemoizedKeychain` caches public key export results in an in-memory `#publicKeys` map keyed only by `keyId`, with no dependency on which seed/master currently backs that `keyId`. Neither `Keychain#removeSeeds()` nor `Keychain#removeAllSeeds()` is overridden in `MemoizedKeychain` to invalidate this cache, and even the overridden `clear()` only deletes the persisted storage entry without resetting the in-memory `#publicKeys` object, so subsequent `exportKey({ ..., opts: { exportPrivate: false } })` calls can serve stale public key/xpub data instead of re-deriving from the current `#masters`.

### Finding Description
`MemoizedKeychain#exportKey` (`features/keychain/module/memoized-keychain.js:38-49`) checks `#getCachedKey(keyId)` and returns the cached value immediately whenever `opts.exportPrivate` is falsy, bypassing `super.exportKey()` entirely: [1](#0-0) 

The cache key is derived purely from `keyId` via `stableStringify` [2](#0-1)  and is never namespaced by seed generation/version, and populated results are persisted to storage and kept in the in-memory `#publicKeys` object indefinitely [3](#0-2) .

Critically, `MemoizedKeychain` does not override `removeSeeds` or `removeAllSeeds` at all — those methods live only on the base `Keychain` class and only mutate `#masters`/`#seedLockStatus`: [4](#0-3) 

They have zero interaction with `MemoizedKeychain`'s `#publicKeys` cache. Even the overridden `clear()` in `MemoizedKeychain` only calls `super.clear()` (not shown but presumably clears `#masters`) and deletes the persisted `CACHE_KEY` storage entry — it never resets the in-memory `this.#publicKeys` object itself: [5](#0-4) 

So the exploit flow is: (1) caller exports a public key for `keyId` A (tied to seed S1), warming `#publicKeys[cacheKey(A)]`; (2) seed S1 is removed via `removeSeeds([S1])` or `removeAllSeeds()`, or a new seed is imported that reuses the same derivation path/`keyId` shape; (3) caller calls `exportKey(A, { exportPrivate: false })` again — the memoized cache hit at line 41-42 returns the old cached `{xpub, publicKey}` without ever calling `super.exportKey()`, which would otherwise throw `seed with id "..." is not initialized` (`features/keychain/module/keychain.js:230`) or derive fresh data from the currently active master.

### Impact Explanation
UI/API surfaces relying on `exportKey(..., { exportPrivate: false })` for address/xpub derivation can display stale public key material belonging to a seed that no longer exists in the keychain (removed, replaced, or wallet reset). This is a cross-wallet/cross-seed state-confusion bug: an address or xpub for a de-provisioned seed could be shown as if it belongs to the currently active wallet state, misleading users about which funds/addresses are actually controlled by the live seed set. This does not leak private keys or enable signing (exportPrivate:false path only returns public data), so the impact is confined to display/state integrity rather than direct fund loss.

### Likelihood Explanation
Highly reproducible and requires no privileged access: any caller that exercises the normal exportKey → removeSeeds/removeAllSeeds → exportKey sequence (a realistic app flow such as switching wallets, restoring a new seed, or removing an account) will trigger it deterministically, since there is no code path anywhere that clears or invalidates `#publicKeys` on seed removal.

### Recommendation
Override `removeSeeds` and `removeAllSeeds` in `MemoizedKeychain` to invalidate (delete relevant entries from, or fully clear) `#publicKeys` and the persisted storage cache; alternatively, namespace cache keys by seed id/generation so removed seeds can never produce a cache hit. Also fix `clear()` to reset the in-memory `#publicKeys` object (`this.#publicKeys = Object.create(null)`), not just delete the storage-persisted copy.

### Proof of Concept
Integration test in `features/keychain/module/__tests__/`:
1. Construct a `MemoizedKeychain`, call `addSeed(seed)` to obtain `seedId`, build a `keyId`.
2. Call `exportKey({ seedId, keyId }, { exportPrivate: false })` to warm the cache; assert result contains correct `xpub`/`publicKey`.
3. Call `keychain.removeSeeds([seedId])` (or `removeAllSeeds()`).
4. Call `exportKey({ seedId, keyId }, { exportPrivate: false })` again.
5. Expected (secure) behavior: throws `seed with id "..." is not initialized` (matching base `Keychain` behavior) or re-derives from current `#masters`.
6. Actual (vulnerable) behavior: returns the stale cached `{ xpub, publicKey }` from step 2 without throwing, proving the cache is not invalidated on seed removal.

    const existingSeedIds = new Set([
      ...Object.keys(this.#masters),
      ...Object.keys(this.#seedLockStatus),
    ])
    const seedIdsToRemove = seedIds.filter((seedId) => existingSeedIds.has(seedId))
