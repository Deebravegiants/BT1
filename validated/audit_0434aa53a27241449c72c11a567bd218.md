### Title
Cross-dispatch-class corruption of `BlockWeight` via un-keyed `ExtrinsicWeightReclaimed` value - (File: cumulus/pallets/weight-reclaim/src/lib.rs)

### Summary
`ExtrinsicWeightReclaimed` is a single `StorageValue<T, Weight>` that is not keyed by `DispatchClass`, yet it is written at the end of one extrinsic's `post_dispatch` and consumed at the start of the very next extrinsic's `post_dispatch` to "undo" a prior weight adjustment before re-applying an accurate one. The undo step always uses the *current* extrinsic's `info.class`, not the class of the extrinsic that produced the stored value, so when a Normal-class extrinsic is immediately followed by an Operational-class extrinsic (or vice versa), weight that was reduced from one class bucket gets accrued back into the other class bucket, corrupting `BlockWeight` per-class accounting.

### Finding Description
In `StorageWeightReclaim::post_dispatch_details` [1](#0-0) , the pattern is:

```rust
let already_reclaimed = frame_system::ExtrinsicWeightReclaimed::<T>::get();
current_weight.accrue(already_reclaimed, info.class);
current_weight.reduce(info.total_weight(), info.class);
current_weight.accrue(accurate_weight, info.class);
```

and at the end of the same function the value is overwritten again for the *current* extrinsic's class:
```rust
frame_system::ExtrinsicWeightReclaimed::<T>::put(accurate_unspent);
``` [2](#0-1) 

The same "read leftover -> accrue to current class -> reduce -> re-accrue -> overwrite" pattern also exists in the wrapped/inner extension's own `reclaim_weight` logic used by `frame_system::extensions::check_weight::CheckWeight` and `frame_system::extensions::weight_reclaim::WeightReclaim`, which this pallet invokes via `S::post_dispatch(...)` before doing its own correction [3](#0-2) . The unit tests for `WeightReclaim` in `substrate/frame/system/src/extensions/weight_reclaim.rs` confirm this exact accrue/reduce pattern keyed on `info.class`, and every test that pre-sets `ExtrinsicWeightReclaimed` uses the *same* class for both the pre-set value and the current extrinsic's `info.class` (e.g. `extrinsic_already_refunded_more_precisely`, `extrinsic_already_refunded_less_precisely`, `different_dispatch_class`) [4](#0-3) [5](#0-4) . There is no test exercising two consecutive extrinsics of *different* `DispatchClass` where one leaves a non-zero `ExtrinsicWeightReclaimed` value for the other to consume.

Root cause: `ExtrinsicWeightReclaimed` is a global, class-agnostic hand-off value between consecutive extrinsics within a block, but the code that consumes it (`current_weight.accrue(already_reclaimed, info.class)`) implicitly assumes the value belongs to the *same* class as the extrinsic currently being processed. In a real block, extrinsics of different classes (Normal vs Operational) can be interleaved — transaction pool ordering is driven by priority, not grouped by `DispatchClass` — so this assumption does not hold.

Exploit flow:
1. Extrinsic A (Normal class) dispatches; its `post_dispatch_details` computes `accurate_unspent` and stores it via `ExtrinsicWeightReclaimed::<T>::put(accurate_unspent)`, having reduced the *Normal* bucket of `BlockWeight` by that amount.
2. Extrinsic B (Operational class) dispatches immediately after, in the same block. Its `post_dispatch_details` reads the stale `already_reclaimed` value (which was earned/subtracted against the Normal bucket) and does `current_weight.accrue(already_reclaimed, DispatchClass::Operational)` — crediting the Operational bucket with weight that was never actually consumed by an Operational extrinsic, while the Normal bucket permanently lost that weight.
3. Net effect: `BlockWeight` for Normal is understated (allows more Normal weight to fit than actually consumed) and `BlockWeight` for Operational is overstated (artificially consumes the Operational/reserved allowance), or vice versa depending on ordering — breaking the invariant that each dispatch-class bucket in `BlockWeight` reflects only extrinsics of that class.

No signature, nonce, origin, or fee check can prevent this because it is purely a bookkeeping bug that fires on ordinary, unprivileged interleaving of Normal- and Operational-classified extrinsics inside a single block (Operational classification does not require a privileged origin — many ordinary user-facing extrinsics across runtimes are marked Operational for priority/DoS-resistance reasons).

### Impact Explanation
This corrupts core weight/PoV accounting (`frame_system::BlockWeight`) used to enforce per-class block limits. Depending on transaction ordering, it can let the Normal class silently exceed its intended budget (weight/PoV limit bypass, potential PoV-size-based DoS or block execution failure at the relay chain) or spuriously exhaust the Operational reserved pool (denial of legitimate operational/priority transactions), or accumulate drift over the block/chain lifetime as extrinsics of alternating classes are included. This directly violates the stated invariant "Fee, weight, gas, storage, and queue logic must not be bypassable by normal users" and "critical queues and validation paths must not be permanently halted by valid user input" (Operational starvation case).

### Likelihood Explanation
High feasibility: an attacker only needs to submit (or simply benefit from naturally occurring) a Normal-class extrinsic followed by an Operational-class extrinsic, or vice versa, in the same block — a common, unprivileged, entirely normal transaction-pool scenario since ordering is priority-based, not class-grouped. No special origin, proxy, or governance access is required. It reproduces deterministically whenever `ExtrinsicWeightReclaimed` is non-zero at a class boundary.

### Recommendation
Key `ExtrinsicWeightReclaimed` by `DispatchClass` (e.g. make it a bounded map/array indexed by class, or store `(Weight, DispatchClass)` pairs) so that the "undo" step in both `frame_system::Pallet::reclaim_weight` and `StorageWeightReclaim::post_dispatch_details` accrues the leftover value back into the class it was originally taken from, not into the class of the extrinsic currently being processed. Alternatively, reset/clear `ExtrinsicWeightReclaimed` whenever `info.class` differs from the class recorded together with the stored value.

### Proof of Concept
Rust integration test (extend `cumulus/pallets/weight-reclaim/src/tests.rs` or `substrate/frame/system/src/extensions/weight_reclaim.rs`):
1. Build a mock block executing two extrinsics via the full `TxExtension` pipeline (`StorageWeightReclaim<CheckWeight<...>>` or equivalent):
   - Extrinsic 1: `DispatchClass::Normal`, with a `post_info.actual_weight` lower than `info.call_weight` so a non-zero `accurate_unspent`/`ExtrinsicWeightReclaimed` is produced and the Normal bucket of `BlockWeight` is reduced.
   - Extrinsic 2: `DispatchClass::Operational`, dispatched immediately after in the same block, with its own accurately measured proof size.
2. After both extrinsics complete, assert:
   - `BlockWeight::<T>::get().get(DispatchClass::Normal)` equals exactly extrinsic 1's own accurately-measured consumption (no leakage subtracted twice).
   - `BlockWeight::<T>::get().get(DispatchClass::Operational)` equals exactly extrinsic 2's own accurately-measured consumption (no foreign credit from extrinsic 1 added in).
3. Expected failing assertion under the current code: the Operational bucket total will include `already_reclaimed` from extrinsic 1's Normal-class refund (or the Normal bucket will be shorted), demonstrating the cross-class corruption.
