### Title
Unverified assumption in `MAINNET_EPOCH_LENGTH_SECS`/`TESTNET_EPOCH_LENGTH_SECS` propagates into the `UNBONDING_PERIOD` used for consensus state initialization - (File: `modules/consensus/pharos/primitives/src/constants.rs`)

### Summary
`pharos_primitives::constants` hardcodes `MAINNET_EPOCH_LENGTH_SECS` (4 hours) and `TESTNET_EPOCH_LENGTH_SECS` (30 minutes) as fixed durations, and derives `UNBONDING_PERIOD` directly from them via `DEFAULT_WITHDRAW_WINDOW_EPOCHS * EPOCH_LENGTH_SECS`. This mirrors the reported analog class: a time-duration constant whose value is presented as documentation-derived but has no protocol guarantee of remaining fixed, silently affecting downstream consensus/security parameters.

### Finding Description
`MAINNET_EPOCH_LENGTH_SECS` and `TESTNET_EPOCH_LENGTH_SECS` are hardcoded as `4 * 60 * 60` and `30 * 60` respectively: [1](#0-0) 

These feed directly into `Config::UNBONDING_PERIOD`, a default-implemented constant with no on-chain verification against the actual staking contract's epoch length: [2](#0-1) 

Both `Mainnet` and `Testnet` `Config` impls use these fixed constants without any mechanism to detect or react to a real on-chain change: [3](#0-2) 

Critically, the codebase itself proves that Pharos's epoch length is **not** a compile-time-safe constant — it is stored on-chain and readable via storage proof (`epochLength` slot), and there is even a dedicated test verifying a storage proof of `epochLength` against `state_root`: [4](#0-3) 

`UNBONDING_PERIOD` (computed from the hardcoded seconds constant) is used directly when constructing the initial consensus state that is submitted on-chain to the counterparty (`CreateConsensusState`): [5](#0-4) 

Unlike `current_epoch` verification in `verify_pharos_block`, which is proven per-block via storage proof (`verify_current_epoch_proof`) and thus self-correcting: [6](#0-5) 

`UNBONDING_PERIOD` has no such proof-based correction — it is baked in at compile time from the assumed epoch length and withdrawal window (`DEFAULT_WITHDRAW_WINDOW_EPOCHS = 84`), values sourced from Pharos's staking-contract documentation/observed behavior rather than a protocol guarantee.

### Impact Explanation
`unbonding_period` set via `CreateConsensusState` governs how long the counterparty light client considers this consensus client's finalized state valid/challengeable before treating updates as stale, directly gating whether state commitments produced by the Pharos consensus client can be trusted for a given duration (used identically to `EPOCH_SECONDS`'s role in `get_current_timestamp`/`get_timestamp_from_now_by_days` in the referenced report). If the real Pharos epoch length or withdrawal window changes on-chain (which the codebase itself acknowledges is possible, since it is a readable/provable storage value, not an immutable chain parameter), the hardcoded `UNBONDING_PERIOD` becomes wrong. An unbonding period set too short relative to the actual value could allow state commitments to be treated as final/trusted before the real unbonding window elapses, weakening the security assumptions of Hyperbridge's Pharos consensus client and, in the worst case, allowing a validator-set rotation or long-range-style attack to be accepted as valid during what is actually still a bonded/slashable period. This is a medium-severity soundness assumption bug rather than direct fund theft.

### Likelihood Explanation
This is triggered anytime the Pharos staking contract's real epoch length (`epochLength` storage slot) or withdrawal window changes after initial consensus-state creation, or if the initial hardcoded assumption never matched production configuration for one of the two networks. No malicious actor action is required — it is a latent parameter-drift bug analogous to the reported `EPOCH_SECONDS` issue, activated by any deviation between the hardcoded constant and the network's actual on-chain configuration at `set_initial_consensus_state` time or afterward.

### Recommendation
Do not hardcode `EPOCH_LENGTH_SECS` / `UNBONDING_PERIOD` as compile-time constants sourced from assumed/observed values. Instead, read `epochLength` and any withdrawal-window parameter directly from the Pharos staking contract at consensus-state initialization time (the code already has the machinery to storage-prove `epochLength`, as shown in `pharos_state_machine.rs`), and periodically re-verify/allow governance-driven updates to `unbonding_period` if the on-chain value changes, rather than trusting a documentation-derived constant indefinitely.

### Proof of Concept
Not directly exploitable via a single transaction/proof; this is a configuration-soundness gap. To demonstrate: read `epochLength` from Pharos's staking contract via `eth_getProof` (as exercised in `test_pharos_multiple_storage_proofs`), compare against `MAINNET_EPOCH_LENGTH_SECS`/`TESTNET_EPOCH_LENGTH_SECS` in `constants.rs`, and observe there is no code path enforcing equality between the two — `UNBONDING_PERIOD` used in `query_initial_consensus_state`/`CreateConsensusState` is computed solely from the hardcoded constant.

	trusted_state: VerifierState,
	update: VerifierStateUpdate,
) -> Result<VerifierState, Error> {
	let update_block_number = update.block_number();
	let current_block_number = trusted_state.finalized_block_number;

	if update_block_number <= current_block_number {
		return Err(Error::StaleUpdate {
			current: current_block_number,
			update: update_block_number,
		});
	}

	let computed_hash = Header::from(&update.header).hash::<H>();

	if computed_hash != update.block_proof.block_proof_hash {
		return Err(Error::BlockProofHashMismatch {
			computed: computed_hash,
			provided: update.block_proof.block_proof_hash,
		});
	}

		update.header.state_root,
		&update.current_epoch_proof,
	)?;
