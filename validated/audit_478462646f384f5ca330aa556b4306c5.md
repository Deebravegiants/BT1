This confirms the finding. The gem's own documentation states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" as a whole, but the implementation only HMACs the raw body — the `shop`, `topic`, and `webhook_id` fields consumed and handed to the app's handler are taken from unauthenticated headers.

### Title
Webhook shop/topic/webhook_id fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body, but the `shop`, `topic`, and `webhook_id` values it passes on to the app's `WebhookHandler` are read from HTTP headers that are excluded from that signature. This breaks the identity binding `HMAC(secret, verified_bytes) == HMAC(secret, bytes_the_app_acts_on)`.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, exposing `hmac` (from the `hmac-sha256` header) and `to_signable_string`, which returns only `@raw_body`: [1](#0-0) 

`Registry.process` verifies only that HMAC-over-body: [2](#0-1) 

and then constructs `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id`, which are read directly from unauthenticated headers: [3](#0-2) [4](#0-3) 

The gem's own documentation states `Registry.process` "will verify the request did indeed come from Shopify," implying the whole webhook (including shop attribution) is authenticated — but only `@raw_body` is bound by the HMAC: [5](#0-4) 

Because `shop-domain`, `topic`, and `webhook-id` headers are entirely outside the signed material, any body+HMAC pair that Shopify has ever legitimately produced for **any** merchant/topic (e.g., an attacker's own store, which they fully control and can trigger webhooks for) remains a cryptographically valid pair regardless of which `shop-domain`/`topic`/`webhook-id` headers are sent alongside it. An unprivileged internet user who operates their own shop can capture one legitimate `(raw_body, hmac)` pair delivered to their own webhook endpoint, then replay that exact body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a different, victim merchant's shop domain or a more sensitive topic string. `Registry.process` will accept it as authentic (the HMAC check only covers the body) and dispatch it to the app's handler with `WebhookMetadata#shop` set to the victim shop and `WebhookMetadata#topic` set to whatever topic the attacker chose. This is the same class of bug as the report's core issue: a value used downstream (here, tenant/topic attribution) is derived from data outside the cryptographic proof (there, "new" reserves derived incorrectly instead of from the actually-verified state).

### Impact Explanation
This breaks tenant isolation (cross-tenant confusion): the host application receives forged webhook events falsely attributed to an arbitrary victim shop and arbitrary topic, sourced from a body the attacker fully controls the content of (their own store's data). Any app logic that keys persistence, session lookup, billing, or side effects off `WebhookMetadata#shop`/`#topic` will act on the victim's tenant using attacker-supplied body content and an attacker-chosen topic — satisfying the "cross-tenant access" Critical impact criterion, since the crossing of the tenant boundary is achieved purely by an unauthenticated internet user forging header fields excluded from the signature.

### Likelihood Explanation
High. The `shopify-api-ruby` gem processes every webhook this way; the only prerequisite is that the attacker has access to at least one genuine `(body, hmac)` pair, trivially obtainable by installing the target app on their own store (or any store) and receiving one real webhook. No secret, access token, or privileged account is needed — only observation of one legitimate webhook delivery.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` (and any other header fields consumed downstream) into the HMAC-verified material, e.g. by including the relevant header values in `to_signable_string`, or by having `Registry.process` explicitly compare a pre-registration-bound expectation (e.g., verifying the topic matches the handler being invoked for that registration, and verifying `shop` against a known/authenticated tenant list) rather than trusting the raw header. At minimum, document and enforce that `shop`, `topic`, and `webhook_id` are not authenticated by this gem, and require callers to independently verify shop membership before acting on webhook data.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`.     )
    render json: {success: true}.to_json
  end
end
