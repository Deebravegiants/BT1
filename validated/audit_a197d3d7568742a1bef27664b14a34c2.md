## Analog Found: Webhook `shop` identity not bound by the HMAC signature - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The reported EXECUTOR bug is a class of "a value that is *acted on* is not covered by the value that is *cryptographically verified*." The same class exists in this gem's webhook processing path: `ShopifyAPI::Webhooks::Registry.process` verifies only the raw request body via HMAC, but the `shop` (tenant identity) used by the handler comes from an unsigned header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from unauthenticated HTTP headers, not covered by the signature: [2](#0-1) 

`Registry.process` verifies only the body/HMAC pair, then trusts `request.shop`, `request.topic`, etc. to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes and compares a signature over `verifiable_query.to_signable_string` only — i.e., the body — using the single app-wide `Context.api_secret_key` shared across every shop that installs the app: [4](#0-3) 

**Identity binding broken (as equality):**
`shop_used_by_handler (unsigned header) == shop_that_actually_produced_the_signed_body` is assumed but never checked. Only `hmac(body) == hmac(body, secret)` is checked; nothing binds the header-supplied `shop` to the signer of that specific body.

### Impact Explanation
Any merchant who has legitimately installed the app on their own shop (an unprivileged actor, no special access) is a valid source of app-secret-signed webhook deliveries for their own tenant. Because the HMAC signing key (`api_secret_key`) is shared across all shops using the app — not per-tenant — that attacker can:
1. Trigger a real webhook delivery to their own shop (e.g., `app/uninstalled`, `products/update`), capturing a genuine `(raw_body, hmac)` pair.
2. POST directly to the app's public webhook endpoint, replaying the captured body/HMAC unchanged, but substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` passes (body signature is untouched), and `Registry.process` invokes the app's handler with `shop: <victim-shop>` — cross-tenant event injection/confusion, e.g. forging `app/uninstalled` for a victim tenant (triggering cleanup/deletion logic keyed by shop) or injecting fabricated order/customer data attributed to a shop the attacker doesn't own.

This satisfies the required Critical impact class: cross-tenant access, achieved purely through this gem's own webhook-processing code, without needing `api_secret_key`, an access token, or any leaked credential.

### Likelihood Explanation
Any developer using `ShopifyAPI::Webhooks::Registry.process` per the documented usage pattern is affected, since the shop binding gap is in the gem's core verification logic, not something the host app can fix without re-implementing HMAC validation itself. The only prerequisite for the attacker is possessing (or being able to trigger) one legitimate webhook delivery to any shop under the same app installation — a low bar for a public/multi-tenant Shopify app.

### Recommendation
Bind the tenant identity into the verified material. Options:
- Include `shop`/`topic` in the signable content that `HmacValidator` verifies (not possible to change Shopify's wire format, but the gem can instead require the host app pass the expected `shop` and cross-check it against `Context`/session storage before dispatching), or
- Require callers of `Registry.process` to supply the expected shop (from the route/session context) and raise if it doesn't match `request.shop`, so the header value is corroborated against an independently-trusted source rather than trusted outright.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`.
2. Attacker triggers `app/uninstalled` (or any webhook with a predictable/replayable body) on their own shop, capturing headers `x-shopify-hmac-sha256: <H>` and raw body `B`.
3. Attacker sends:
```
POST /webhooks HTTP/1.1
Host: victim-app.example.com
x-shopify-topic: app/uninstalled
x-shopify-hmac-sha256: <H>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: replayed-id

<B>
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `<H>` matches `HMAC(B, api_secret_key)` regardless of the `shop` header. [5](#0-4) 
5. The handler executes with `data.shop == "victim-shop.myshopify.com"`, even though the event actually originated from the attacker's shop. [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
