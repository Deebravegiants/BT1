### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body alone and then trusts `request.shop`/`request.topic` taken from those headers to route and tag the payload. This is the same "field acted on but not covered by the signature" defect described in the report: the signature secures one data set (the body) while a different, unauthenticated data set (the headers, in particular the tenant identifier `shop`) is what the application actually acts on.

### Finding Description
`Request#hmac` and `#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`; `shop`, `topic`, `api_version`, and `webhook_id` are pulled from HTTP headers via `shopify_header`, which are never included in the signed material: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`, i.e. the body only: [5](#0-4) 

`Registry.process` validates that HMAC and then immediately uses `request.shop` (an unsigned header) to build `WebhookMetadata` that is handed to the application's handler as the tenant identity: [6](#0-5) 

Because the same `client_secret`/`api_secret_key` is shared across every shop that installs a given app, any body+HMAC pair that is valid for Shop A's webhook is also a valid HMAC for the identical body regardless of which shop header accompanies it — the signature says nothing about `shop`. The binding the application relies on is:

`request.shop` (unauthenticated header, used as tenant key) == the shop the HMAC was actually computed for (never checked, since `shop` isn't in `to_signable_string`)

That equality is never enforced, so the two sides can diverge.

### Impact Explanation
An attacker who can obtain any one valid `(raw_body, hmac)` pair from the app (e.g., by installing the app on a shop they control, or by replaying/observing a legitimate webhook delivery) can resend the identical body and HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) header for a different, victim tenant. `Registry.process` will pass HMAC validation (it only checks the body) and will dispatch the payload to the handler tagged with the attacker-chosen `shop`. This lets an attacker inject or spoof events into another merchant's data path within the same app — a cross-tenant boundary violation, since the webhook handler and any downstream storage keyed by `shop` will treat attacker-controlled data as if it originated from the victim's store.

### Likelihood Explanation
Any user who can install the target app on a shop under their control (a standard, self-service, unprivileged action for public Shopify apps) can capture a genuine `(body, hmac)` pair for their own shop's webhook deliveries and replay it against the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only observation of one legitimate webhook call to the app that the attacker already has a relationship with.

### Recommendation
Bind the tenant identity to the signature. Either:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed material used by `to_signable_string`/HMAC computation (matching how the identity fields are actually consumed downstream), or
- Have the application layer independently verify that `request.shop` corresponds to a shop with a currently valid session/installation *and* reject/deduplicate on `webhook_id` per shop, so a captured signature for one tenant cannot be replayed under another tenant's identity.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the legitimate request: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(secret, B)`), plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new POST to the app's webhook endpoint using the exact same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (a real shop that has installed the same app).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — the signature check passes because the body `B` and secret are unchanged: [7](#0-6) 
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
