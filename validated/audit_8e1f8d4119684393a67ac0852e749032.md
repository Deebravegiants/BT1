### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (shop-domain) and `topic` fields that the app relies on to attribute the webhook to a tenant are taken directly from unauthenticated HTTP headers. `Utils::HmacValidator` never verifies these header values, so they can be freely rewritten without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic`, however, are pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` and `shopify-topic` / `x-shopify-topic` headers, with no cryptographic binding to those values: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC by recomputing it from `verifiable_query.to_signable_string` (i.e., the body) and comparing to `verifiable_query.hmac`, but it never touches `shop` or `topic`: [3](#0-2) 

`Registry.process` trusts `request.shop` (and `request.topic`) after HMAC validation succeeds, and hands them straight to the app's handler as the tenant identity for the webhook payload: [4](#0-3) 

The identity binding that should hold is: **the `shop` value the app attributes the webhook to == the shop for which the signed body was actually generated by Shopify**. Because the HMAC only covers `raw_body` and the app's `client_secret` is shared across all shops the app serves (it is not shop-specific), any party who can obtain one valid `(raw_body, hmac)` pair signed with the app's secret — trivially available to the operator of any shop that has this app installed, since Shopify delivers real webhooks with a valid HMAC to that merchant's own webhook traffic — can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it never checks `shop`, so `Registry.process` will dispatch the (attacker-controlled) body to the registered handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: an unprivileged user who merely owns any shop with the app installed (no access to the app's `client_secret`, no privileged account) can make the host application process attacker-supplied webhook data under a completely different (victim) shop's identity. Depending on how the host app's webhook handler uses `data.shop` (e.g., to look up the merchant's session/access token and act on their store, or persist data keyed by shop), this enables cross-tenant data injection/corruption and can also be leveraged to trigger app logic (order changes, GDPR/compliance flows, uninstall flows, etc.) against a shop the attacker does not control. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is High for any deployment that exposes the webhook endpoint publicly (the documented pattern in `docs/usage/webhooks.md`) and relies on the app being installed on more than one shop (i.e., any multi-tenant SaaS app, which is the typical use case for this gem). The only prerequisite is the ability to observe one legitimate `raw_body` + `hmac-sha256` pair generated by Shopify for the app — obtainable simply by being a merchant who installs the app and inspects the request their own store triggers (e.g., via a debugging proxy on their own webhook consumer, or reusing a webhook body Shopify already sent for a topic where the body is not shop-specific, such as `app/uninstalled` payloads that just contain `{}`/generic data as seen in the test fixtures). No access to `api_secret_key` or any victim credential is required.

### Recommendation
Include `shop` (and ideally `topic`) in the value that is HMAC-verified, or otherwise bind the header-derived `shop`/`topic` to the signed body before trusting them:
- Simplest fix: change `to_signable_string` to include the shop-domain and topic headers concatenated with the raw body (matching what is actually authenticated), and update `HmacValidator`/tests accordingly.
- Alternatively, since Shopify's actual webhook HMAC is computed over the raw body only by design, the gem should not expose `shop`/`topic` as validated/trusted fields without documenting that they are unauthenticated, or it should require callers to cross-check `request.shop` against an expected/allow-listed shop before dispatch in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker-shop.myshopify.com`.
2. A real webhook fires from Shopify to the app's endpoint with body `B` and a valid `hmac-sha256` header `H`, both computed by Shopify using the app's shared `client_secret`:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: B
   ```
3. Attacker captures `(B, H)` (e.g., via their own reverse proxy/logging in front of their self-hosted app instance, or any environment where they can see outbound bytes to their own endpoint).
4. Attacker crafts a new request to the same public endpoint with the identical body and HMAC but a different `shop-domain`:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: B
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only [5](#0-4) , matches `H`, and passes.
6. The handler is invoked with `data.shop == "victim-shop.myshopify.com"` even though the payload originated from the attacker's own shop event, as constructed at [6](#0-5) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
