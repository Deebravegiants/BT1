### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the shop identity (`shop-domain` header) is read out-of-band and never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` to attribute the webhook payload to a tenant. Any party able to produce one genuinely-signed webhook (e.g., an unprivileged merchant on their own shop that has the app installed) can replay that body/HMAC pair while substituting a different `shop-domain` header, and the gem will accept it as coming from the spoofed shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read independently from a header that is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` using the app's shared `client_secret`: [3](#0-2) 

`Registry.process` checks the HMAC and then trusts `request.shop` to build `WebhookMetadata` handed to the host app's handler: [4](#0-3) 

Because the same `client_secret` is used to sign webhooks for every shop that has installed the app, a legitimate-but-unprivileged merchant can obtain a validly-signed webhook (raw body + `X-Shopify-Hmac-Sha256`) for their own store. Since the `shop-domain` header is not part of the signed bytes, that same body/HMAC pair remains valid if replayed with an arbitrary `shop-domain` header value pointing at a different (victim) shop. `Registry.process` will pass HMAC verification and deliver the payload to the handler tagged with the attacker-chosen `shop`, breaking the intended binding: `authenticated_bytes == raw_body` but `identity_used == header.shop`, i.e. `shop_verified_by_HMAC != shop_trusted_by_handler`.

### Impact Explanation
This is a cross-tenant identity/data-attribution bypass: a request cryptographically proven to originate from shop A can be delivered to the host application labeled as shop B. Any host app logic that keys off `WebhookMetadata#shop` (e.g., updating shop-specific records, triggering `shop/redact`-style deletion flows, syncing data) can be manipulated into acting on/for the wrong tenant using attacker-supplied body content, purely through header substitution — no access token, secret, or privileged account required beyond having any installation of the target app.

### Likelihood Explanation
Requires only: (1) the attacker's own shop has the target app installed (this is normal, unprivileged merchant access — installing a public app requires no special privilege), and (2) the ability to send an HTTP POST to the app's public webhook endpoint with a modified header, which is standard for any internet-reachable webhook receiver. No secrets, tokens, or insider access are needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-covered bytes, or otherwise cryptographically bind the trusted `shop` value to the same request that produced the HMAC (e.g., derive/validate shop against Shopify's known registered shop for that HMAC, or require the signature to cover a canonicalized string containing shop+body rather than raw body alone).

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` has the target app installed; Shopify delivers a real webhook to the app with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the shared `client_secret`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker captures `(B, H)` and re-sends a POST to the same webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds since `shop-domain` was never part of the signed data.
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)` and invokes the registered handler, which now processes attacker-controlled data attributed to `victim.myshopify.com`. [5](#0-4)
