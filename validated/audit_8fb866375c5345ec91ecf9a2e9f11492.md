### Title
Censorship of inbound DMP/HRMP messages via conservative worst-case check in `check_enough_messages_included_advanced` - (File: cumulus/pallets/parachain-system/src/parachain_inherent.rs)

### Summary
`check_enough_messages_included_advanced` validates the collator-supplied split between full and hashed messages using only the *maximum possible* size of a hashed message (`first_hashed_msg_max_size`), not the actual size of the specific message being hashed, because `HashedMessage` never stores original message length. A malicious collator can therefore construct a full-messages budget that is smaller than `max_full_messages_size` but still large enough that `full_messages_size + first_hashed_msg_max_size <= max_full_messages_size` is false only when the real hashed message is near the channel's max size — for any hashed message whose real size is smaller than `first_hashed_msg_max_size`, the collator can leave it hashed instead of full while still satisfying the assertion.

### Finding Description
The check computes: `assert!(full_messages_size + first_hashed_msg_max_size > max_full_messages_size, ...)` [3](#0-2) . This only fails to catch censorship if there existed room in the budget (`max_full_messages_size - full_messages_size`) that is `>= first_hashed_msg_max_size`. If the actual target message (e.g. a user's DMP reserve-transfer XCM) is smaller than `first_hashed_msg_max_size` (e.g. HRMP channel's configured `max_message_size`, which is generally much larger than a typical XCM payload), the collator can craft `full_messages_size` so that:

`(max_full_messages_size - full_messages_size) < first_hashed_msg_max_size` (check passes, no panic)

while still

`(max_full_messages_size - full_messages_size) >= actual_size_of_target_message` (i.e., the real message would have fit).

Concretely: set `max_full_messages_size = 100`, `first_hashed_msg_max_size = 60` (channel max), and craft `full_messages_size = 45` by including other lower-priority messages ahead of the target message in the ordering. The check computes `45 + 60 = 105 > 100` → passes. But the target message (real size 30) would have fit in the remaining 55-byte budget and should have been included as a full message. `check_enough_messages_included_advanced` cannot detect this because `HashedMessage` (used as `Message::CompressedMessage`) discards the original message length, so the runtime has no ground truth to compare against actual size — only the protocol-wide upper bound is available [4](#0-3) .

This is used for the HRMP path in `enqueue_inbound_horizontal_messages`, using `channel.max_message_size` as the bound [2](#0-1) . Notably, the DMP path (`enqueue_inbound_downward_messages`) does not call `check_enough_messages_included_advanced` at all — only `check_enough_messages_included_basic`, which merely requires at least one full message, not "as many as possible" [5](#0-4) . This means DMP censorship of a specific message (the scenario cited in the question, "reserve-asset-transfer DMP message") is not bounded by the advanced check at all — the collator has essentially free rein to hash any DMP message as long as at least one full DMP message exists.

### Impact Explanation
A malicious collator can selectively keep a specific user's inbound DMP or HRMP message (e.g., a reserve-asset transfer) hashed rather than fully included, while other messages around it are processed normally. Since hashed messages are never dispatched (only their hash is folded into the MQC), the targeted message never executes on the destination parachain, permanently stalling the user's transfer as long as the malicious collator (or a colluding rotation of collators) continues to author blocks and repeats this pattern each block, keeping the message hashed and effectively out of the queue's dispatch path. This matches the scoped impact: permanent censorship/halt of a specific user's DMP/HRMP message.

### Likelihood Explanation
Requires the attacker to control an active collator (or a majority/consistent subset of collators for a specific parachain) — this is a real, permissioned relayer role but not requiring any privileged runtime/governance origin, and is achievable by any entity that can win a collator slot (e.g., via staking/collator selection in permissionless collator sets). No signature/origin/proxy check applies since inherents aren't user-signed extrinsics. The size-boundary crafting is deterministic and requires no special relay-chain race condition — the collator fully controls which messages precede the target message and how large the "full" portion is, and can retry indefinitely across blocks (subject to the DMP watermark / MQC only allowing forward progress, not requiring the specific target to be included).

### Recommendation
Store the actual message length in `HashedMessage` (or a size-preserving compressed representation) so `check_enough_messages_included_advanced` can compare against the real size of the first hashed message rather than the channel/queue's theoretical maximum. Additionally, apply the same "advanced" advancement-rule check to the DMP path (`enqueue_inbound_downward_messages`) instead of only the basic check, using the actual DMP max message size bound consistently.

### Proof of Concept
Rust unit test extending the existing `check_enough_messages_included_advanced_works` test in `cumulus/pallets/parachain-system/src/parachain_inherent.rs`:
```rust
#[test]
fn advanced_check_allows_censoring_smaller_than_max_message() {
    // Target user's real message is small (30 bytes) but channel max is 60 bytes.
    let messages = AbridgedInboundHrmpMessages {
        full_messages: vec![(1000.into(), InboundHrmpMessage { sent_at: 0, data: vec![1; 45] })],
        hashed_messages: vec![(2000.into(), HashedMessage { sent_at: 1, msg_hash: Default::default() })],
        // real size of the hashed message (not recoverable from HashedMessage) was 30 bytes
    };
    // Should panic because the real message (30 bytes) would fit in the remaining
    // budget (100 - 45 = 55), but currently passes because it only checks against
    // first_hashed_msg_max_size = 60.
    messages.check_enough_messages_included_advanced(
        "Test",
        AbridgedInboundMessagesSizeInfo { max_full_messages_size: 100, first_hashed_msg_max_size: 60 },
    ); // does NOT panic today — demonstrates the gap
}
```
A fuzz/invariant extension: generate `(full_messages_size, first_hashed_msg_max_size, actual_hashed_msg_size)` triples with `actual_hashed_msg_size <= first_hashed_msg_max_size`, and assert that whenever `full_messages_size + actual_hashed_msg_size <= max_full_messages_size` (i.e., the real message would have fit), `check_enough_messages_included_advanced` panics. This assertion will fail whenever `actual_hashed_msg_size < first_hashed_msg_max_size`, proving the check is not tight and allows selective censorship of specific messages smaller than the protocol's max message size.
