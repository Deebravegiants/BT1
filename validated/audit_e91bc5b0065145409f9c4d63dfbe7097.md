### Title
Missing reentrancy guard on Tron `IntentGatewayV2.placeOrder` allows escrow/dust accounting manipulation via callback tokens - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The mainline EVM `IntentGatewayV2` contract inherits `ReentrancyGuardTransient` and guards `placeOrder` with `nonReentrant` [1](#0-0) [2](#0-1) [3](#0-2) . The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the identical `placeOrder`/escrow logic but inherits only `HyperApp, EIP712` — no `ReentrancyGuard` and no `nonReentrant` modifier anywhere in the file [4](#0-3) .

### Finding Description
`placeOrder` on Tron performs external token calls (`safeTransferFrom`, native transfers, `ICallDispatcher.dispatch`, Uniswap swaps) and then derives escrowed/dust amounts from balance snapshots taken before and after those calls — exactly the "credit is computed from the balance delta around an external call" pattern that enabled the Akropolis exploit [5](#0-4) [6](#0-5) . On the audited/hardened mainline EVM contract, this exact class of accounting (fee-on-transfer/dust handling via `balance - balancesBefore`) is only safe because `placeOrder` is wrapped in `nonReentrant` [3](#0-2) [7](#0-6) . The Tron contract carries the same balance-diff/dust logic but without that reentrancy protection, and there is no other guard (mutex flag, transient-storage lock) present in the file. An attacker who controls a token contract (e.g., an ERC-777-style token or a token with a `transfer`/`transferFrom` hook, or any callback surface reachable during the predispatch `ICallDispatcher.dispatch` step) can re-enter `placeOrder` (or other unsigned-integer-tracking functions) mid-call, before the outer call's escrow bookkeeping (`_orders[commitment][token] += reducedInputs[i].amount`) is finalized, letting the reentrant call observe and manipulate intermediate balances to receive escrow credit disproportionate to tokens actually transferred in — the same "credit-before-invariant-is-settled" bug class as Akropolis's reentrant deposit.

### Impact Explanation
`placeOrder` is a fully permissionless, unprivileged entry point invoked directly by any user's transaction, matching the required reachable path (a single submitted transaction to an intents escrow). A successful reentrant manipulation of the balance-diff/dust accounting could let an attacker escrow more credit than tokens actually deposited, or double-count deposits across nested calls, resulting in outright theft of gateway-held funds when the order is later filled/withdrawn by a solver — a concrete "theft of funds" impact matching the required severity bar.

### Likelihood Explanation
Exploitability depends on the attacker's ability to insert a callback during the token transfer or predispatch call sequence (e.g., a malicious/hook-bearing ERC-20-like token, or a token whose `transferFrom` invokes attacker code). Since Tron's ecosystem includes TRC-20 tokens and custom token implementations with varying transfer semantics, and the predispatch path explicitly invokes `ICallDispatcher.dispatch` (attacker-influenced calldata) before the balance snapshots are compared, the reentrancy window is real and directly reachable without any privileged role.

### Recommendation
Add a reentrancy guard (`ReentrancyGuard`/`ReentrancyGuardTransient`) to `evm/tron/contracts/apps/IntentGatewayV2.sol` and apply `nonReentrant` to `placeOrder`, `fillOrder`, `cancelOrder`, and any other externally callable function that performs external token calls before finalizing escrow/dust state, mirroring the protections already present in `evm/src/apps/IntentGatewayV2.sol`. Additionally, apply checks-effects-interactions ordering to the balance-diff accounting so escrow credit is fixed before any external call that could reenter.

### Proof of Concept
Not independently executable from the available index — this assessment is based on static comparison of the Tron contract's inheritance/guard set (`contract IntentGatewayV2 is HyperApp, EIP712`, no `ReentrancyGuard`) against the mainline hardened contract (`contract IntentGatewayV2 is IntrinsicIntents, ExtrinsicIntents, ReentrancyGuardTransient, Initializable`) and the shared balance-diff dust/escrow logic in `placeOrder`. I was unable to fully trace `fillOrder`/`cancelOrder` internals in the Tron file before running out of tool iterations, so the exact reentrant call sequence (specific hook-bearing token or precise state corruption path) is not fully confirmed — a Devin session with full repo/file access should complete tracing `fillOrder`, `cancelOrder`, and `onAccept` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to construct a concrete exploit transaction sequence and confirm exploitability before remediation.
