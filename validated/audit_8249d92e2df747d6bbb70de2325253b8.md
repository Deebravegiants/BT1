## Finding: Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing

### Title
Webhook Tenant Identity (`shop`, `topic`, `webhook_id`) Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` proves nothing more than "this body was HMAC-signed with the app's secret at some point." The `shop`, `topic`, `webhook_id`, and `api_version` values come from HTTP headers that are never included in that signature, yet `Registry.process` trusts them as the tenant identity forwarded to the app's handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from attacker-controllable HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only this body-only HMAC and then dispatches the *header-derived* `shop`/`topic`/`webhook_id` straight to the app's handler as trusted `WebhookMetadata`: [3](#0-2) 

This is exactly the "field acted on but not covered by the HMAC" bug class: the identity binding that should hold is `shop header == shop cryptographically bound to signed bytes`, but in reality `shop header ⊄ signed bytes` (only `raw_body` is signed). The gem's own documentation asserts a stronger guarantee than what is implemented — it explicitly states `Registry.process` "will verify the request did indeed come from Shopify": [4](#0-3) 
and the documented example handler trusts `data.shop` directly to route/store the payload: [5](#0-4) 

Since only the byte-identical body is checked, any request whose body was previously legitimately signed by Shopify for the attacker's *own* shop (i.e., an install of the app on a shop the attacker controls) remains valid under any combination of `shop-domain`, `topic`, `webhook-id`, `api-version` headers the attacker chooses to send it with.

### Impact Explanation
An unprivileged internet user who can install the target app on their own store (a normal, non-privileged action any Shopify merchant can perform) can:
1. Trigger a webhook delivery to their own shop with body content they control (e.g., a resource with a note/field of their choosing).
2. Capture that exact HTTP request (same `raw_body`, same valid `x-shopify-hmac-sha256`).
3. Replay it to the app's webhook endpoint after swapping `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) to any victim shop's domain.

`Utils::HmacValidator.validate` still passes because it only checks the untouched `raw_body`. `Registry.process` then calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain, so any app logic that uses `data.shop` to select the tenant record to update (exactly as shown in the gem's own documented example) will write/attribute attacker-controlled data against another tenant — a cross-tenant data integrity/confusion impact meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
No secrets, tokens, or privileged access are required — only the ability to install/use the app on an attacker-owned shop (freely available to any internet user) and to send arbitrary HTTP requests to the app's public webhook endpoint. The header/body split is baked into the gem's `Request`/`Registry` implementation, so every app built on top of this gem's documented webhook flow inherits the gap.

### Recommendation
Bind the tenant/topic identity into the verified signable content, or otherwise cryptographically tie the headers to the signature — e.g., include `shop`, `topic`, and `webhook_id` in the HMAC-covered material (this would require a corresponding change compatible with Shopify's signing scheme), or, at minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop`/`data.topic`/`data.webhook_id` are **not** authenticated by `Registry.process` and must be independently cross-checked (e.g., against the registered webhook_id/shop pairing) before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an `orders/create` webhook with body `{"id":1,"note":"payload"}`.
2. Shopify sends the app: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, body `{"id":1,"note":"payload"}`.
3. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` → `Utils::HmacValidator.validate(request)` succeeds (only `raw_body` is checked) at: [6](#0-5) 
5. Handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: {"id"=>1,"note"=>"payload"}, ...)`, causing the app to process attacker data under the victim tenant's identity.
