### Title
Emporium wallet-fee token is not bound to the wallet-owner's ECDSA authorization, allowing an unauthorized token to be drained from `HinkalWallet` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.verifyWallet()` recovers the smart-wallet owner's signature over `EMPORIUM_SIGNATURE_TYPEHASH`, which binds only `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline`. It never binds `circomData.feeStructure.feeToken` (or `circomData.relay`). The wallet-fee payment path (`signerAddress != address(0)`) then calls `sendToRelayFromWallet` → `HinkalWallet.doSendToRelay`, which transfers `feeStructure.flatFee` of `feeStructure.feeToken` straight out of the wallet's own balance to `circomData.relay`, with only the numeric cap `flatFee <= maxFee` checked — the token identity and recipient are unconstrained by the signature.

### Finding Description
`verifyWallet` builds the signed digest as: [1](#0-0) 

and enforces only the flat-fee cap against the signed `maxFee`: [2](#0-1) 

The actual withdrawal from the wallet uses `circomData.feeStructure.feeToken`, an address chosen by whoever assembles `circomData` for the `transact()` call, which is never part of the `EMPORIUM_SIGNATURE_TYPEHASH` digest: [3](#0-2) 

This is transferred out of `HinkalWallet`'s own balance via a privileged call gated only by `onlyEmporium`, not by any check that the token matches what the wallet owner intended: [4](#0-3) 

This mirrors the reported "Trader"/`targetTracer` pattern: the signed authorization (`ops`, `maxFee`, `deadline`, `message`) is valid for one context (an intended `feeToken`), but the contract does not check that the field actually acted upon (`feeStructure.feeToken`) equals what was implicitly intended by the signer — so a valid wallet signature can be executed against a different, more valuable token that the wallet also holds. Additionally, this fund movement happens directly on `HinkalWallet`'s balance and is not captured anywhere by the `balanceDif`/`amountChanges` equality checks performed in `Hinkal.transact()`, so it is a value transfer "outside the balance equation."

### Impact Explanation
An unprivileged party who can submit a `transact()` call (self as prover, needing only a previously-obtained, not-yet-consumed valid `EmporiumOperation` wallet signature for some `maxFee`) can choose `feeStructure.feeToken` to be any ERC-20 held by the `HinkalWallet`, extracting up to `flatFee` of that token to an address of their choosing (`circomData.relay`) — funds the wallet owner never authorized to move in that token. This is direct theft of wallet-held funds outside of the balance-equation checks that otherwise guard `Hinkal.sol`'s own balance, meeting the Critical/High bar for "moving assets a wallet owner ... never authorised."

### Likelihood Explanation
Exploitation requires the attacker to possess a valid, still-unused wallet-owner signature (`stack`) — which is the normal mode of operation for the Emporium's off-chain-signed relay flow — and only requires them to set an unconstrained `CircomData` field (`feeStructure.feeToken`) when building their own SNARK proof/calldata for submission; no admin, relay, or owner privileges are needed.

### Recommendation
Include `feeStructure.feeToken` (and ideally `circomData.relay`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` digest so the wallet owner explicitly authorizes the exact fee token (and recipient) alongside `maxFee`, mirroring the Tracer fix of checking `order.targetTracer == market` before execution.

### Proof of Concept
1. Wallet owner signs an `EmporiumStack` (`ops`, `maxFee = 10`, `deadline`, `message = M`) intending the flat fee to be paid in USDC (their off-chain client sets `feeStructure.feeToken = USDC` when preparing the transaction, but this token choice is never part of the signed digest).
2. Before that transaction is submitted, an unprivileged actor who knows the signature tuple `(message, ops, maxFee, deadline, v, r, s)` builds their own SNARK proof/`circomData` for `Hinkal.transact()`, setting `circomData.emporiumMessage = M`, the same `ops`, `maxFee = 10`, `deadline`, but `circomData.feeStructure = {feeToken: WETH, flatFee: 10, ...}` and `circomData.relay = attacker`.
3. `verifyWallet` recomputes the same EIP-712 digest (since `feeToken` isn't included) and recovers the legitimate `signerAddress` — signature check passes; `usedMessages[M]` is marked used.
4. `payRelayFees` → `sendToRelayFromWallet` → `HinkalWallet.doSendToRelay(attacker, 10, WETH)` sends 10 WETH from the wallet to the attacker, even though the wallet owner never authorized spending WETH. [5](#0-4)
