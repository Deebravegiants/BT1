This confirms the finding: the docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (docs/usage/webhooks.md:125), and the `shop` field of `data: WebhookMetadata` is documented as "The shop domain of the webhook" (docs/usage/webhooks.md:14) — implying it is trustworthy after that verification, yet it is derived from a header never covered by the HMAC computation.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC of the raw request body via `Utils::HmacValidator.validate(request)` [1](#0-0) . The `Request#to_signable_string` used for that HMAC computation returns only `@raw_body` [2](#0-1) , so the `shop-domain` header — which is read separately via `request.shop` and passed on as the trusted tenant identifier in `WebhookMetadata` — is never bound to the signature [3](#0-2) [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac_signed_bytes == bytes_that_determine_the_trusted_shop`. In this gem, `hmac_signed_bytes` is only `@raw_body` [5](#0-4) , while `bytes_that_determine_the_trusted_shop` is the `x-shopify-shop-domain`/`shopify-shop-domain` header, read independently of the signed payload [3](#0-2) . `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes and compares the HMAC over that raw body [6](#0-5) [7](#0-6) . After this single check passes, `request.shop` is forwarded unchecked into `WebhookMetadata.shop`, which the app's handler is documented to trust as "The shop domain of the webhook" [4](#0-3) [8](#0-7) .

Because the body is the only thing bound by the HMAC, any unprivileged actor who has ever received one genuine, validly-signed webhook for their own shop (e.g., by installing the app on their own store — no special privilege or leaked secret needed) possesses a byte string plus a valid HMAC tag that remains valid for that same body under any set of headers. They can replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it never looks at headers, and the handler receives `data.shop` set to the attacker-chosen victim domain, with only the attacker's own body content but the label of a different tenant.

### Impact Explanation
This breaks the tenant boundary the library is documented to enforce ("verify the request did indeed come from Shopify" for a specific shop) [9](#0-8) . Any host application that uses `data.shop` from `WebhookMetadata` (as the library's own example handler does: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) to look up or mutate per-tenant records will act on a victim shop's identity using attacker-supplied content, enabling cross-tenant data confusion/corruption — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate, unprivileged installer of the app on their own store (to obtain one genuine signed webhook payload) and the ability to POST to the app's public webhook endpoint with custom headers — both trivially available to any internet user, no `api_secret_key`, access token, or other credential needed.

### Recommendation
Include the shop domain (and other identity-bearing headers such as topic/webhook-id) in the signed/verified material, or otherwise cryptographically bind the `shop-domain` header to the verified body (e.g., verify it against a webhook-id/shop mapping obtained via an authenticated API call) before trusting `request.shop`/`WebhookMetadata.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and lets it register for `orders/create`. When they place a test order, Shopify sends a legitimately HMAC-signed webhook: body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and same HMAC header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this still matches because the body is unchanged [7](#0-6) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: B, ...)` [4](#0-3) , so the app processes attacker-controlled order data attributed to the victim shop.
