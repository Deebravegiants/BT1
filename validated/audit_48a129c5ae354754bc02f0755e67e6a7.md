### Title
Shared Emporium identity lets any transact() sweep a prior victim's CASE-2 external-protocol balance/position into an attacker's UTXO - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable` is a single, shared contract address used as `msg.sender` for every user's CASE 2 ("Stateless Interaction") external calls. Because `runAction` mints an output UTXO purely from the pre/post balance delta of the Emporium contract and assigns it to whatever `circomData.stealthAddressStructure` the *current* caller supplies, any externally-held asset/position that persists under Emporium's identity between transactions (e.g., a locked stake recorded as `staker == Emporium`) can be swept by a later, unrelated, unprivileged caller.

### Finding Description
The broken equality: an asset that becomes claimable from an external protocol only via `msg.sender == Emporium` (created by victim's earlier CASE 2 op, e.g. `stakingContract.stake(amount)`) should be redeemable only by the victim's stealth address / nullifier path, but Hinkal's `runAction` logic instead attributes **any** balance increase realized during **any** subsequent `runAction` invocation to the UTXO of whoever is the current caller.

Code path:
- CASE 2 branch calls `op.endpoint.call{value: op.value}(op.callData)` directly, with `op.endpoint`/`op.callData` fully attacker-controlled via `circomData.externalActionData.externalActionMetadata` (decoded into `EmporiumStack`), the only restriction being blocking `callHinkalWallet`/`doSendToRelay` selectors: [3](#0-2) .
- Attribution of resulting funds is purely balance-diff based, not identity based: `balancesBefore`/`balancesAfter` are compared, `deltaAmountChanges[i]` (the amount the *current* caller declared moving into the endpoint) is subtracted, and any remaining positive `balanceChange` becomes a UTXO for the current caller's stealth address, unconditionally: [4](#0-3)  and [5](#0-4) .
- The comment at line 138-139 explicitly acknowledges balances can persist on Emporium across calls ("the only case when balanceChange can be < 0 is when there were some funds on emporium before the call"), i.e., this is treated as expected/normal state, not sanitized against.
- `onlyAllowedRecipient` only checks that the caller of `runAction` is the registered Hinkal core contract, not that the balance increase originated from *this* caller's own prior deposit: [6](#0-5) .

Exploit flow: Victim calls `transact` with a CASE 2 op `stakingContract.stake(amount)` (Emporium ends up as `staker` in the external protocol, with a locked balance/position outside Emporium's own token balance until withdrawn). Later, attacker calls `transact` with a CASE 2 op `stakingContract.withdraw(victimStakeId)` (or `unstake`) — the staking contract only checks `msg.sender == staker == Emporium`, so the call succeeds and funds land in Emporium's own balance. `runAction`'s balance-diff logic then sees a large positive `balanceChange` unrelated to the attacker's own `deltaAmountChanges` for this tx, and mints a shielded UTXO for the attacker's own `stealthAddressStructure` for that entire amount, then also directly transfers the equivalent tokens out to `msg.sender` (Hinkal.sol, which in turn shields for the attacker) via `handleOut`. No nullifier tied to the victim's original stake is ever spent, and no proof constraint ties the withdrawn amount to the attacker's own prior deposits — the ZK circuit only enforces the caller's own in/out UTXO balance for the amounts the caller declares (`deltaAmountChanges`), not that on-chain windfalls belong to them.

### Impact Explanation
Critical — direct theft of another user's locked/staked funds held externally under the shared Emporium identity, without ever spending the victim's nullifier. The attacker can repeat this against any CASE 2 position left open by any user against any external protocol that authorizes purely by `msg.sender`. This is a structural consequence of Emporium being a single shared contract identity combined with balance-diff-based UTXO minting having no ownership binding to the depositor of the underlying asset.

### Likelihood Explanation
Preconditions: a victim must have used CASE 2 (stateless, `signerAddress == address(0)` or `invokeWallet == false`) to open a persisting position/balance on an external protocol that (a) records `staker`/owner as `msg.sender` (i.e., Emporium) and (b) allows any caller matching that owner to withdraw to itself. This is a realistic integration pattern for staking/lending/locking protocols and is exactly the scenario CASE 2 is documented for ("Stateless Interaction"). Attacker cost is a single `transact` call with attacker-chosen calldata; no special privilege, timing, or race condition is needed — the attacker only needs to observe (via on-chain events) that a locked position exists under Emporium's address at a given external contract, which is public information since Emporium is the shared caller. Fully repeatable across users/protocols.

### Recommendation
Do not rely purely on Emporium's own token-balance delta to attribute ownership of funds returned by CASE 2 stateless calls when the underlying position can outlive a single transaction. Options: (1) require CASE 2 interactions that create persistent external state to be scoped to per-user `HinkalWallet` instances (CASE 1, stateful) rather than the shared Emporium address, so external protocols see a per-user identity; (2) maintain on-chain internal accounting in Emporium mapping which depositor/session is entitled to claim balance increases from a given external endpoint, and reject `runAction` mint if the increase cannot be attributed to the current caller's own recorded deposit; (3) disallow CASE 2 usage entirely for endpoints/selectors that are known to create withdrawable, non-atomic positions, restricting composability to atomic (deposit-and-return-in-same-tx) interactions like swaps.

### Proof of Concept
