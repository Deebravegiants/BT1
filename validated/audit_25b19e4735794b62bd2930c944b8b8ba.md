### Title
Signup success determined solely by local `signup_reason` when `user_centric_signup=true`, bypassing backend `enroll_user` (signup_post/signup_poll) attestation - ([File: src/plans/mod.rs])

### Summary
In `MasterPlan::do_signup`, when `qr_codes.user_data.user_centric_signup` is `true` and the orb config `ignore_user_centric_signups` is `false`, the signup `success` flag is computed directly from the locally-derived `signup_reason` (`SignupReason::Normal`) without ever invoking `self.enroll_user(...)`, which is the code path that performs backend verification. This means the backend round-trip that would otherwise confirm liveness/duplicate status is skipped entirely for this branch.

### Finding Description
`do_signup` computes `signup_reason` purely from local pipeline results and `detect_fraud`: [1](#0-0) 

Then, for the `user_centric_signup` branch, `success` is set directly from `signup_reason == SignupReason::Normal`, with no call into `enroll_user`, which is where backend calls (`signup_post`/`signup_poll`) live: [2](#0-1) 

Only the `else` branch (i.e., `!user_centric_signup || ignore_user_centric_signups`) calls `self.enroll_user(...)`, whose `.is_success()` result is used, and which is the path presumably backed by backend `signup_post`/`signup_poll` verification (per `src/plans/enroll_user.rs`). The `user_centric_signup` branch instead only sets `debug_report.enrollment_status` locally based on `signup_reason`, and derives `success` from that same local variable — no `enroll_user` call occurs in this branch, hence no backend signup_post/signup_poll network round trip for authorization.

This confirms the attack surface described in the question: an attacker whose QR/session data marks `user_centric_signup=true` (controlled by backend `user_status` response for that user, but reachable/observable by the attacker's own signup session), combined with `ignore_user_centric_signups=false` (default orb config), will have their signup marked successful/enrolled purely by local pipeline output (`signup_reason`), which itself depends on `detect_fraud` — a check the audit set already flags as potentially neutralized/bypassable locally. If `detect_fraud` returns false (no fraud detected) and pipeline succeeded, `signup_reason = Normal`, and `success = true`, with **no backend liveness/duplicate verification call performed by this branch**.

### Impact Explanation
This allows a signup to be marked as authorized/successful based solely on orb-local computation, without backend confirmation of liveness or duplicate-user status. Combined with a locally bypassable/neutralized fraud detector, this creates a path to register a fraudulent or duplicate identity as "successful" on the orb's local records/UI/dbus signals (`debug_report.signup_successful()`, `dd_incr!(...successful_signup)`), and drive downstream biometric package building/upload (`build_pcp`, `upload_pcp_tier_0`) without the backend attestation gate that normally exists for standard enrollments. This matches a liveness/fraud-bypass and signup-authorization-integrity impact category.

### Likelihood Explanation
Preconditions are narrow but attacker-reachable within the rules: `user_data.user_centric_signup=true` must be returned by the backend `user_status` for the QR/session in play, and the orb config `ignore_user_centric_signups` must be `false` (its apparent default, given the `else` fallback exists specifically for the opposite case). Given these two conditions — both determined by data outside attacker's direct control but reachable through a normal signup session/backend response — the bypass is deterministic and repeatable each time `signup_reason == Normal` is achieved locally.

### Recommendation
Route the `user_centric_signup` branch through the same backend-verifying `enroll_user` call (or equivalent backend attestation) rather than deriving `success` purely from the local `signup_reason`. At minimum, require an actual backend confirmation (e.g., `signup_post`/`signup_poll`) before marking `debug_report.enrollment_status` and `result.success` as successful for user-centric signups.

### Proof of Concept
Integration test plan in `src/plans/mod.rs` / `src/plans/enroll_user.rs` test harness:
1. Construct `qr_codes.user_data.user_centric_signup = true`.
2. Set orb config `ignore_user_centric_signups = false`.
3. Mock/stub `detect_fraud` to return `false` (no fraud detected) and pipeline to return `Some(pipeline)` (simulate a "locally undetected fraudulent" capture per the `detect_fraud` bug).
4. Run `do_signup` end-to-end and assert:
   - No network call to `signup_post`/`signup_poll` endpoints was made (via mock backend call counter/spy).
   - `result.success == true` and `debug_report.enrollment_status == Some(enroll_user::Status::Success)`.
5. Contrast with the `ignore_user_centric_signups=true` (or `user_centric_signup=false`) case where `enroll_user` (and thus backend calls) are invoked, to demonstrate the branch divergence.
