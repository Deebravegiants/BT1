### Title
Webhook `shop-domain` / `topic` Headers Not Covered by HMAC Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Webhooks::Registry.process` authenticate an inbound webhook solely by validating the HMAC over the raw request **body**, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the library hands to the host application's handler are read directly from unauthenticated HTTP headers, which are excluded from the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to those headers [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (the body only) and compares it against the `hmac` header using `OpenSSL.secure_compare` [3](#0-2) . Once that body-only check passes, the library immediately trusts the unauthenticated `request.shop` value and forwards it to the app's webhook handler as the tenant identifier: [4](#0-3) .

The broken identity binding is:
```
HMAC-verified bytes (raw_body)  !=  bytes used to select the tenant (shop-domain header)
```
Because the header is outside the signed payload, an attacker who is an unprivileged internet user (any developer can create a free Shopify partner/dev store and install a public/test app to receive genuinely-signed webhooks for that shop) can capture a real `(raw_body, hmac)` pair issued by Shopify to their own store, then replay it to the app's webhook endpoint while altering only the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the app's own `api_secret_key`, which the attacker never needs to know. `Registry.process` then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the handler with the spoofed victim `shop` [5](#0-4) .

### Impact Explanation
Any host application that (reasonably, given the library's job is "verify the webhook") trusts `WebhookMetadata#shop` as an authenticated tenant identifier will process attacker-controlled data under a victim shop's tenant context — a cross-tenant confusion. Concretely this can be used to inject attacker-controlled order/customer/product data into the victim shop's app-side records, or to trigger mandatory compliance webhooks (e.g. `shop/redact`, `customers/redact`, `app/uninstalled`) against a victim shop, causing the app to erase or alter victim tenant data or state it was never authorized to touch. This crosses the tenant boundary this gem is responsible for enforcing, matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Exploitation requires only that the attacker control a Shopify store where the target app (or any app sharing the same `api_secret_key`/webhook endpoint) is installed — something any internet user can set up via a free development store — and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed; the attacker relies purely on genuine signed traffic from their own tenant and the fact that identifying headers sit outside the signed payload.

### Recommendation
Bind the tenant/topic identity to the HMAC-verified payload instead of trusting headers alone: include `shop`, `topic`, and `webhook_id` in the signable string (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its HMAC input, see [6](#0-5) ), or otherwise verify server-side that the header-derived shop domain matches an app-known/installed shop before dispatching to the handler, and document clearly that host apps must not rely on `WebhookMetadata#shop` without independent verification.

### Proof of Concept
1. Attacker installs a public/test version of the target app on their own Shopify dev store `attacker.myshopify.com`, and triggers a real webhook (e.g. `orders/create`) so Shopify sends a POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker crafts a new request to the app's webhook endpoint reusing the exact body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate`, which recomputes `HMAC-SHA256(secret, B)` and compares to `H` — this matches, since `B` and `H` are untouched [7](#0-6) .
4. `Request#shop` returns `victim.myshopify.com` from the (unsigned) header [8](#0-7) , and this value is passed into `WebhookMetadata` and delivered to the app's handler as if it were an authentic webhook for the victim shop.
