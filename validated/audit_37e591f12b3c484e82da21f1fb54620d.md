### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant spoofing via header manipulation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` checks the HMAC solely against that body. The `shop` attribute, read separately from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header, is never included in the signed bytes, yet `Registry.process` trusts this header value and hands it directly to the app's webhook handler as the tenant identifier.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. `Request#shop` is read independently from headers: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively over `to_signable_string`: [3](#0-2) 

`Registry.process` then passes `request.shop` — unauthenticated, header-derived data — straight into the handler without verifying it is bound to the signed body: [4](#0-3) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body || shop)`,
but the actual implementation only enforces:
`hmac == HMAC(secret, raw_body)`

with `shop` entirely outside the MAC. Because `body` and `hmac` remain valid for *any* shop header value, a party who can obtain one valid `(raw_body, hmac)` pair from Shopify for their own installed shop (e.g., a merchant on their own store — no privileged credential, access token, or `api_secret_key` needed) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop domain. The signature still validates because it never depended on the shop field, and `Registry.process` forwards the attacker-chosen `shop` to `WebhookMetadata`, letting the handler act (e.g. look up/attribute data, trigger side effects, or fetch that shop's stored session/access token) under the wrong tenant's identity.

### Impact Explanation
This breaks the cross-tenant isolation boundary: an unprivileged actor (merely an app-installing merchant on their own store, not privileged and without needing the app's `client_secret` or another shop's access token) can make the library report a `WebhookMetadata` with `shop` pointing at an arbitrary victim tenant while still passing HMAC validation. Downstream host applications that rely on `Registry.process`/`WebhookMetadata#shop` to select which merchant's session/access token to use for automated actions can be tricked into operating on/for a different tenant's data — a cross-tenant access condition.

### Likelihood Explanation
Likelihood is limited by the precondition that the attacker must obtain at least one genuine `(raw_body, hmac)` pair, which requires operating their own real Shopify store and installed app instance (achievable by any unprivileged internet user who installs public apps), then replaying the captured POST to the app's public webhook callback URL with a modified shop header — no secrets or access tokens required. Root cause is structural in `ShopifyAPI::Webhooks::Request`/`HmacValidator`, so it applies to every webhook processed by this gem.

### Recommendation
Include `shop` (and ideally `topic`) as part of the signed payload, or explicitly bind the verified `shop` header to a value the app already trusts (e.g., cross-check against the topic-registration's shop, or require the caller to supply the expected shop and compare it before trusting `request.shop`) rather than exposing an unauthenticated header as an equally-trusted identity field alongside the HMAC-verified body.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; Shopify sends a legitimate webhook: body `B`, headers include `shopify-hmac-sha256: HMAC(secret, B)` and `shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same POST to the app's webhook endpoint, only changing `shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` is constructed; `hmac` still equals `HMAC(secret, B)` since `to_signable_string` only returns `B`. [5](#0-4) 
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload/HMAC actually originated from `attacker.myshopify.com`, demonstrating the identity-binding break.
