### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC that `HmacValidator.validate` checks binds the *body* to the app's shared `api_secret_key`, but never binds the `shop-domain` header. `Registry.process` accepts any request whose body/HMAC pair verifies and then hands `request.shop` straight to the app's handler as the authoritative tenant identifier, without any additional binding between that header and the signed content.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. The HMAC verification path (`HmacValidator.validate` → `validate_signature` → `compute_signature(verifiable_query.to_signable_string, secret)`) therefore checksums only the body bytes against the app-wide `Context.api_secret_key`: [2](#0-1) 

Meanwhile `request.shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity passed to the app's `WebhookHandler`: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` const with no further verification: [5](#0-4) 

This breaks the intended identity binding: `signed_bytes == HMAC(shop_bound_payload, secret)` should equal `shop_header used for tenant routing`, but instead `HMAC` only ever covers `raw_body`, independent of `shop`. Because the `api_secret_key` is a single per-app secret shared across every shop that installs the app (not per-tenant), any legitimate webhook a merchant receives for their own store — with a valid HMAC over that exact body — remains **HMAC-valid** if replayed to the app's webhook endpoint with the `shop-domain` header changed to a different (victim) shop. The gem provides no mechanism to detect this, since the shop field is never part of the signed content.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who legitimately installs the app on their own store (an ordinary, unprivileged action any internet user can take) receives real webhook deliveries signed with the app's shared secret. By replaying such a request to the shared webhook endpoint while altering only the `shop-domain` header, the attacker can cause the host application (relying on `WebhookMetadata.shop` as returned by this gem) to process/attribute data — e.g. GDPR `customers/redact`, `customers/data_request`, order or app-uninstall events — as if they originated from a different merchant's shop. This matches the Critical "cross-tenant access" impact category: data or actions destined for tenant A can be injected/attributed to tenant B purely by manipulating an unauthenticated header, without possessing that tenant's credentials.

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker must (a) install the app on a shop they control to receive at least one legitimately-signed webhook body, and (b) be able to reach the app's public webhook endpoint directly (webhook URLs are typically public HTTP(S) endpoints, satisfying the "unprivileged internet user" threat model). No access token, `client_secret`, or privileged account is required — only a normal merchant install and the ability to POST an HTTP request with custom headers, both trivially available to any internet user.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed payload used for verification, or independently authenticate the `shop-domain` header against a known/expected value (e.g., cross-check against the shop already associated with the specific webhook registration/subscription id, or require a per-shop secret/lookup rather than a single app-wide `api_secret_key`) before it is exposed via `WebhookMetadata.shop`. At minimum, document prominently that `WebhookMetadata.shop` is not itself HMAC-verified and must not be trusted as a tenant boundary without additional application-side verification (e.g., matching against the shop's stored offline session/webhook subscription record).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw JSON body `B` and the resulting `X-Shopify-Hmac-Sha256` header value `H`, both generated by Shopify using the app's shared `api_secret_key`.
2. Attacker sends a POST directly to the app's public webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (changed)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` computes `HMAC(B, api_secret_key)` and finds it equals `H` (since verification never involves the `shop` header) — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Registry.process` passes validation and invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body(B), ...)` — see `lib/shopify_api/webhooks/registry.rb:188-200` — causing the host app to process attacker-supplied data under the victim tenant's identity.
