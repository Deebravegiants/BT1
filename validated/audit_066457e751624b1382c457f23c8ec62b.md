### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers and passed straight through to the app's webhook handler. Because the same `api_secret_key` is used to sign every webhook for every shop that has the app installed, any merchant who installs the app can capture a legitimately-signed webhook payload from their own shop and replay it with a forged `x-shopify-shop-domain` header pointing at a victim shop, without invalidating the HMAC.

### Finding Description
The bug-class pattern from the external report ("a field acted on but not covered by the HMAC") maps directly onto this code. The binding that should hold is:

`shop header value used by the handler == shop that actually produced/authorized the signed body`

but this gem never enforces that equality.

- `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `shop` is read straight from the (attacker-controlled, unauthenticated) header, with no relation to the signature: [2](#0-1) 
- `HmacValidator.validate_signature` computes and compares the signature only against `to_signable_string` (i.e. the body), never the shop/topic/webhook-id headers: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`, handing it to the app's handler: [4](#0-3) 

The gem's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" and states that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole `WebhookMetadata` (including `shop`) is authenticated — which it is not.

Attack sequence:
1. Attacker installs the app on their own shop (`attacker.myshopify.com`) and lets Shopify send a legitimate webhook (e.g. `orders/create`). The attacker captures the raw body and the valid `x-shopify-hmac-sha256` header — both signed with the app's shared `api_secret_key`.
2. Attacker replays this exact body + HMAC header to the app's webhook endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's own data>, ...)` and invokes the handler.
5. The host application, following the documented usage pattern (`data.shop`), attributes the attacker-supplied body to the victim shop — e.g., persisting fake orders/customers, or triggering shop-scoped business logic under the victim's tenant identity.

### Impact Explanation
This crosses a tenant boundary: an unprivileged app-installer (attacker) can make the app believe arbitrary attacker-chosen payloads originated from a different, victim shop, without ever needing the victim's credentials or access token. This is a cross-tenant data-integrity/access vulnerability driven purely by this gem's failure to bind the `shop` identity to the HMAC-verified bytes.

### Likelihood Explanation
Any user can freely sign up for the app on their own store to obtain a validly-signed webhook body, and replaying an HTTP request with a modified header requires no special access, TLS interception, or leaked secrets — only standard HTTP tooling. The likelihood is high wherever the host application trusts `WebhookMetadata#shop` for tenant attribution, which is exactly what the gem's own documentation recommends.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the HMAC-verified data rather than trusting raw headers:
- Extend `VerifiableQuery`/`Request#to_signable_string` (or add a separate check) so the `shop-domain`, `topic`, and `webhook-id` headers are included in what's cryptographically bound to the signature, or
- Cross-check the header-provided `shop` against an independently-verified value (e.g., require callers to pass the expected shop and compare it against `request.shop`), rejecting mismatches before constructing `WebhookMetadata`.

### Proof of Concept
```ruby
# 1. Attacker installs app on their own shop and captures a real webhook:
raw_body = '{"id":1,"note":"legit order from attacker-shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# 2. Attacker replays it, spoofing the shop-domain header for a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HMAC validation passes (it only checks raw_body), and the handler receives
# WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled data)
```
