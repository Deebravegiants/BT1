### Title
Unnecessary precision loss in `VWAPOracle.recordSpread` from multiplying the result of a division - ([File: evm/src/utils/VWAPOracle.sol])

### Summary
`VWAPOracle.recordSpread()` computes a per-fill spread in basis points via integer division, then multiplies that already-truncated value back up by the input volume to derive the volume-weighted spread contribution. This is the exact anti-pattern from the referenced GMX report: multiplication performed on the output of a division amplifies rounding error rather than avoiding it.

### Finding Description
`recordSpread` is called by `IntentGatewayV2` (`restrict(_intentGateway)`) on every intent fill to record how much spread a solver captured or gave up, normalizing both input and output amounts to 18 decimals and computing:

```solidity
// evm/src/utils/VWAPOracle.sol:203-211
int256 spreadBps = 0;
if (inputAmountNormalized > 0) {
    int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
    spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
}

int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
_updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);
``` [1](#0-0) 

`spreadBps` truncates `amountDiff * BPS_DENOMINATOR / inputAmountNormalized` toward zero, discarding the fractional bps. `weightedSpread` then re-multiplies that truncated integer by `inputAmountNormalized`, which does not recover the lost precision — it amplifies the truncation error by the full input volume of the fill. The mathematically correct approach (following the report's recommendation) is to skip the intermediate division entirely and accumulate `amountDiff * BPS_DENOMINATOR` directly as the weighted term, dividing only once, at read time, in `spread()`:

```solidity
// evm/src/utils/VWAPOracle.sol:141-147
function spread(bytes memory sourceChain, address token) external view returns (int256) {
    ...
    return data.weightedSpreadSum / int256(data.totalVolume);
}
``` [2](#0-1) 

Because `_updateCumulativeSpread` accumulates `weightedSpreadSum` and `totalVolume` across every fill and `spread()` divides once at the end, computing `weightedSpread` from the pre-truncated `spreadBps` (rather than from `amountDiff * BPS_DENOMINATOR` directly) introduces avoidable, volume-scaled error into every accumulated data point, biasing the reported VWAP spread away from the true value.

### Impact Explanation
`recordSpread` is reachable from any solver filling an intent via `IntentGatewayV2` (an unprivileged, solver-submitted transaction), since `IntentGatewayV2` is the sole authorized caller and passes through solver-supplied output amounts and gateway-tracked input amounts on every fill. The oracle is exposed via `IIntentPriceOracle` and configured as `Params.priceOracle`, meaning its cumulative `spread()` value is intended to reflect the true historical VWAP spread for a token pair and is consumable by governance/price-guard logic built on top of `IIntentPriceOracle`. The truncate-then-multiply pattern systematically skews `weightedSpreadSum` (and hence the derived `spread()`), with the error compounding per-fill and scaling with fill volume rather than being bounded to a fraction of a basis point. This corrupts the oracle's reported data, which downstream logic depending on `IIntentPriceOracle.spread()` (e.g., a price-deviation guard) would then rely on with a systematically biased input.

### Likelihood Explanation
This triggers on every ordinary intent fill that flows through `IntentGatewayV2` — no special conditions, privileged roles, or malicious actors are required; it is a deterministic arithmetic defect present in the normal call path (`fillOrder` → `recordSpread`).

### Recommendation
Remove the intermediate division before the multiplication. Accumulate the un-truncated weighted term directly:

```solidity
int256 weightedSpread = amountDiff * int256(BPS_DENOMINATOR); // no intermediate division
_updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);
```

Keep `spreadBps` (still computed via division) only for the `SpreadRecorded` event, and let `spread()`'s existing single division (`weightedSpreadSum / totalVolume`) be the only place precision is dropped, exactly as recommended in the referenced report.

### Proof of Concept
1. Solver A fills an order with `inputAmountNormalized = 3` and `outputAmountNormalized = 4` (contrived small values to make truncation visible; in practice these are 18-decimal normalized amounts so any non-exact ratio truncates).
2. `amountDiff = 1`; `spreadBps = (1 * 10_000) / 3 = 3333` (true value 3333.33..., truncated).
3. `weightedSpread = 3333 * 3 = 9999`, whereas the mathematically exact weighted contribution is `amountDiff * BPS_DENOMINATOR = 10_000`.
4. The error (`1` unit here, scaling with `inputAmountNormalized` in general) is permanently baked into `weightedSpreadSum`, and repeats on every fill, so the oracle's reported `spread()` diverges further from the true VWAP as fill volume accumulates — with no way to correct it after the fact since the truncation already occurred before storage.
