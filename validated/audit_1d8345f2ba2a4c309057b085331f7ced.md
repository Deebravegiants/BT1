### Title
Partial-fill escrow release rounds down to zero, letting a solver deliver output tokens without receiving any input-token compensation - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntrinsicIntents._fillSameChain` computes the escrowed input amount owed to a filler for a partial fill as `(order.inputs[i].amount * fillAmount) / totalRequired` [1](#0-0) . This is structurally the same division pattern flagged in the external JOJO report: a paperChange/creditChange style multiply-then-divide by a large denominator that can truncate to zero, causing the counterparty who "sold" (here, the solver who transferred output tokens to the beneficiary) to receive no credit while still losing real funds.

### Finding Description
In `_fillSameChain`, for each output asset the solver supplies `fillAmount` of the output token directly to the beneficiary and, in exchange, is meant to receive a proportional share of the user's escrowed input token:
```solidity
uint256 escrowedAmount;
if (amountFilled == totalRequired) {
    escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
} else {
    escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
}
``` [2](#0-1) 

The solver's payment to the beneficiary (`beneficiaryTotal = fillAmount + beneficiaryShare`) is unconditionally transferred out regardless of what `escrowedAmount` resolves to [3](#0-2) . There is no check that `escrowedAmount > 0` before proceeding with the fill. If `order.inputs[i].amount` is small relative to `totalRequired` (e.g., the order's input token has very few base units, or `totalRequired` is intentionally set very large), a `fillAmount` that is a genuinely small-but-nonzero fraction of `totalRequired` can make `(order.inputs[i].amount * fillAmount) / totalRequired` truncate to `0` due to Solidity integer division. In that case the loop proceeds, `outputFills[i]` still records `fillAmount` was paid, `_partialFills` is updated, the solver sends real output tokens to the beneficiary, but `escrowedInputs[i].amount == 0` — the solver is credited with zero input tokens for that leg via `_withdraw`.

This mirrors the JOJO root cause exactly: `paperChange * creditAmount / paperAmount == 0` meant the seller lost paper without receiving credit; here `order.inputs[i].amount * fillAmount / totalRequired == 0` means the filler loses output tokens without receiving input-token credit. The order creator/beneficiary controls `order.inputs[i].amount` and `totalRequired` (the order parameters), so a malicious order creator can deliberately craft an order (tiny input amount relative to a large/fine-grained output requirement) such that any partial fill below the full order amount silently zeroes the filler's compensation for that leg, while the beneficiary still receives the solver's tokens.

Existing tests only address the complementary "leftover dust" problem — ensuring the final solver who completes an order gets the residual rounding dust rather than it being locked in the contract [4](#0-3) . They do not cover or guard against a single partial fill's `escrowedAmount` computing to exactly zero.

### Impact Explanation
A solver (unprivileged party reachable via a single `fillOrder` transaction) can transfer real value to a beneficiary and receive zero compensation for that leg, resulting in direct loss of funds for the filler. Because order parameters (`inputs[i].amount`, `output.assets[i].amount`) are attacker-controlled by whoever places the order, a malicious order creator can structure orders to repeatedly extract value from partial fillers who are unaware of (or don't defend against) the rounding trap — a concrete theft/loss-of-funds scenario matching the "Medium" severity class defined in the rules (concrete theft of funds via unsanitized division).

### Likelihood Explanation
Reachable directly from a single `fillOrder` call by any solver, no privileged role required. The condition is triggerable whenever `order.inputs[i].amount * fillAmount < totalRequired`, which is easy to arrange by choosing token decimal combinations or crafting large `totalRequired` values, and is likely to occur unintentionally too whenever input/output tokens have very different value-per-decimal ratios and fills are small.

### Recommendation
Revert (or skip crediting escrow only after ensuring correctness) when the computed `escrowedAmount` for a leg would be zero despite a nonzero `fillAmount`, e.g.:
```solidity
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
if (escrowedAmount == 0) revert ZeroEscrowRelease();
```
Alternatively, enforce a minimum fill size per output asset so that `fillAmount` can never be small enough relative to `totalRequired` to truncate the escrow release to zero, consistent with the fix already applied for the complementary rounding-dust leftover issue.

### Proof of Concept
1. User places an order with `inputs[0].amount = 1` (e.g., 1 unit of a high-value/low-supply token) and `output.assets[0].amount = 1_000_000e18` (a token requiring many base units for the same economic value), escrowing 1 unit of input token.
2. A solver calls `fillOrder` with `options.outputs[0].amount = 999_999e18` (a genuine, non-completing partial fill just short of `totalRequired`).
3. In `_fillSameChain`: `fillAmount = 999_999e18`, `escrowedAmount = (1 * 999_999e18) / 1_000_000e18 = 0` (integer truncation).
4. The solver's `999_999e18` output tokens are transferred to `beneficiary` via `safeTransferFrom`/native transfer, but `escrowedInputs[0].amount = 0` is what gets released to the solver via `_withdraw`.
5. The solver has paid out real tokens and received nothing in return for that leg — a direct, unrecoverable loss of funds, exactly analogous to the JOJO seller who loses paper but receives no credit when price truncates to zero.

    /*//////////////////////////////////////////////////////////////
                    ROUNDING DUST IN PARTIAL FILLS (Finding #4)
    //////////////////////////////////////////////////////////////*/

    /// @notice Verifies that rounding dust from integer division in partial fills
    /// is not permanently locked. The final solver completing the order should
    /// receive the full remaining escrow balance rather than a truncated amount.
    function testPartialFill_RoundingDustReleasedToFinalSolver() public {
        // Choose amounts that produce rounding truncation:
        // input = 100 USDC (100e6), output = 3 DAI (3e18)
        // Each of 3 solvers fills 1 DAI. Proportional release per fill:
        //   100e6 * 1e18 / 3e18 = 33333333 (truncated from 33333333.33...)
        // Without fix: 3 * 33333333 = 99999999, leaving 1 unit locked.
        // With fix: final solver gets remaining balance = 100e6 - 2*33333333 = 33333334
        uint256 inputAmount = 100 * 1e6; // 100 USDC
        uint256 outputAmount = 3 * 1e18; // 3 DAI

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: outputAmount});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        // User places order
        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;

        uint256 fillPerSolver = 1e18; // Each solver fills 1 DAI
        uint256 truncatedRelease = (inputAmount * fillPerSolver) / outputAmount; // 33333333

        // --- Solver 1 fills 1 DAI ---
        address solver1 = makeCleanAddr("solver1");
        vm.deal(solver1, 1 ether);
        deal(address(dai), solver1, 10 * 1e18);
        uint256 solver1UsdcBefore = usdc.balanceOf(solver1);

        vm.startPrank(solver1);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out1 = new TokenInfo[](1);
        out1[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out1}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver1),
            solver1UsdcBefore + truncatedRelease,
            "Solver1 should receive truncated proportional USDC"
        );

        // --- Solver 2 fills 1 DAI ---
        address solver2 = makeCleanAddr("solver2");
        vm.deal(solver2, 1 ether);
        deal(address(dai), solver2, 10 * 1e18);
        uint256 solver2UsdcBefore = usdc.balanceOf(solver2);

        vm.startPrank(solver2);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out2 = new TokenInfo[](1);
        out2[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out2}));
        vm.stopPrank();

        assertEq(
            usdc.balanceOf(solver2),
            solver2UsdcBefore + truncatedRelease,
            "Solver2 should receive truncated proportional USDC"
        );

        // --- Solver 3 fills final 1 DAI (completes the order) ---
        address solver3 = makeCleanAddr("solver3");
        vm.deal(solver3, 1 ether);
        deal(address(dai), solver3, 10 * 1e18);
        uint256 solver3UsdcBefore = usdc.balanceOf(solver3);

        vm.startPrank(solver3);
        dai.approve(address(intentGateway), fillPerSolver);
        TokenInfo[] memory out3 = new TokenInfo[](1);
        out3[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: fillPerSolver});
        intentGateway.fillOrder(order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: out3}));
        vm.stopPrank();

        // Final solver should receive the remaining balance (truncatedRelease + 1 rounding unit)
        uint256 expectedFinalRelease = inputAmount - (2 * truncatedRelease); // 33333334
        assertEq(
            usdc.balanceOf(solver3),
            solver3UsdcBefore + expectedFinalRelease,
            "Final solver should receive remaining escrow including rounding dust"
        );
        assertGt(expectedFinalRelease, truncatedRelease, "Final release should be larger due to rounding dust");

        // Gateway should have zero USDC — no dust locked
        assertEq(usdc.balanceOf(address(intentGateway)), 0, "Gateway should have zero USDC - no rounding dust locked");
    }
