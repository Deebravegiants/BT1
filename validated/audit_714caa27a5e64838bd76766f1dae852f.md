### Title
Unvalidated index into Omni Bridge transfer list causes wrong destination tx hash / status to be reported for batched withdrawals - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal` picks the transfer describing a withdrawal's outcome purely by numeric array position (`args.index`) in the array returned by the Omni Bridge indexer API, with no check that the picked entry actually corresponds to the withdrawal being polled (its `assetId`/`destinationAddress`). This is the same bug class as the HackerOne report: an index taken from application/caller-controlled bookkeeping is used to select an element out of an externally-supplied array, and the selected element is trusted without verifying it belongs to the expected record.

### Finding Description
In `OmniBridge.describeWithdrawal`: [1](#0-0) 

the code does:
```ts
const transfer = (
    await this.omniBridgeAPI.getTransfer({ transactionHash: args.tx.hash })
)[args.index];
```
and then, once `transfer` is non-null, unconditionally treats `transfer.recipient` / `transfer.finalised?.transaction_hash` / `transfer.utxo_meta?.pending_sign_id` as the outcome for the polled withdrawal — reporting `status: "completed"` with that `txHash`: [2](#0-1) 

There is no check that `transfer.recipient` matches `args.withdrawalParams.destinationAddress`, or that `transfer.token_id`/related asset matches `args.withdrawalParams.assetId`. The array is API-returned data for a NEAR transaction hash, and when a single NEAR transaction carries multiple withdrawal intents (batched withdrawals — a scenario the SDK explicitly supports, see the batch-withdrawal design doc and `sdk.createWithdrawalCompletionPromises`/`createWithdrawalIdentifiers` machinery), the indexer's list of transfers for that tx hash is populated independently and its ordering is not guaranteed to match the order the withdrawal intents were issued in the transaction.

Notably, the sibling `PoaBridge.describeWithdrawal` implementation explicitly documents and fixes this exact same risk by matching by content instead of position: [3](#0-2) 
```ts
// Response list is unsorted, so we match by assetId instead of index
const withdrawal = findMatchingWithdrawal(
    response.withdrawals,
    args.withdrawalParams.assetId,
);
```
`OmniBridge` never received the analogous fix, and still trusts raw positional indexing into the same class of "unsorted list from external API" data, as shown by the test comment/case that asserts the byte-for-byte counterpart ("returns correct transfer by index") assumes ordering, without a matching-by-identity safety net: [4](#0-3) 

### Impact Explanation
If the Omni Bridge indexer returns transfers for a batched NEAR transaction in an order that does not match `args.index` (e.g., differing processing/finalization order between two withdrawals batched in one transaction, which is entirely plausible since each transfer finalizes independently on its own destination chain at its own pace), `describeWithdrawal` for withdrawal A can pick up and report the `txHash`/status belonging to withdrawal B. This is a status/hash misreport: the caller (integrator) polling withdrawal completion via `watchWithdrawal`/`sdk.createWithdrawalCompletionPromises` would be told withdrawal A is "completed" with a transaction hash that in fact corresponds to a different withdrawal (different recipient, different amount, different chain in the worst case), potentially causing the integrator to mark/credit the wrong withdrawal as done or to release funds/confirmations based on the wrong destination tx.

This matches the described High-impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no privileged access or malicious behavior on the caller/integrator's part — it is triggered purely by ordinary use of the SDK's supported batched-withdrawal feature (multiple withdrawal intents composed into one signed/published NEAR transaction) combined with the Omni Bridge API returning transfers for a transaction hash in an order that isn't guaranteed to align with intent submission order. Whether the current Omni Bridge indexer backend happens to always return transfers in submission order could not be independently confirmed here (this is an external API's behavior, out of this repo), so likelihood depends on that external guarantee — but the code itself provides no defensive matching, unlike the analogous `PoaBridge` code that treats the same kind of list as unordered.

### Recommendation
Match transfers by content (e.g., recipient address / token id / amount) rather than solely by `args.index`, mirroring the `findMatchingWithdrawal`-by-`assetId` approach already used in `PoaBridge.describeWithdrawal`. At minimum, validate that `transfer.recipient` decodes to `args.withdrawalParams.destinationAddress` (and ideally that the token matches `args.withdrawalParams.assetId`) before trusting `transfer.finalised`/`utxo_meta` data for that withdrawal; if no transfer with a matching recipient/asset is found at any position, return `pending` instead of assuming index alignment.

### Proof of Concept
1. Submit two Omni Bridge withdrawal intents (e.g., withdrawal A → address X on Ethereum, withdrawal B → address Y on Solana) composed atomically in a single NEAR transaction (via `signAndSendIntent` with `signedIntents` composition, as supported by `IntentExecuter`).
2. Call `sdk.createWithdrawalCompletionPromises` (or directly `OmniBridge.describeWithdrawal`) for withdrawal A with `index: 0` and withdrawal B with `index: 1`.
3. Have (or mock, as in the existing test suite) `omniBridgeAPI.getTransfer({ transactionHash })` return the two transfers in reverse order relative to intent submission order (`[transferForB, transferForA]`) — a realistic scenario since each transfer's `finalised` status is populated independently by its own destination chain.
4. Observe that `describeWithdrawal` for withdrawal A (`index: 0`) returns `{ status: "completed", txHash: <B's tx hash> }`, misreporting B's destination transaction as A's outcome, while `destinationAddress`/`assetId` of A were never checked against the returned `transfer.recipient`.
