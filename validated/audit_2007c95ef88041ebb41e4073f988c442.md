### Title
Missing existence check for protocol treasury account in `update_validator_accounts` causes epoch-boundary node panic if the treasury account is deleted - (File: `runtime/runtime/src/lib.rs`)

### Summary
`update_validator_accounts` (`runtime/runtime/src/lib.rs:1663-1759`) distributes validator stake-returns and epoch rewards, including to the `protocol_treasury_account_id`. Unlike the sibling per-validator gas-reward code at `runtime/runtime/src/lib.rs:1072-1084`, which gracefully skips crediting a reward if the receiver account no longer exists (`if let Some(ref mut account) = account`), the protocol-treasury branch at `runtime/runtime/src/lib.rs:1731-1736` unconditionally calls `get_account(...)?.ok_or_else(|| StorageError::StorageInconsistentState(...))?` — i.e. it assumes the treasury account is always present and turns a missing account into a fatal `StorageInconsistentState` error instead of a normal, recoverable outcome.

### Finding Description
This mirrors the reported analog bug class: one function in a set of parallel/sibling functions omits a precondition check ("is the account able to receive this credit?") that a directly comparable function in the same codebase does perform, and the missing check converts an otherwise-benign runtime condition into a hard failure of downstream critical logic.

- `update_validator_accounts` is invoked unconditionally at every epoch boundary from `Runtime::apply` whenever a `ValidatorAccountsUpdate` is supplied (built in `chain/chain/src/runtime/mod.rs:233-277`, which sets `protocol_treasury_account_id` to `Some(self.genesis_config.protocol_treasury_account.clone())` whenever that account belongs to the current shard) [1](#0-0) .
- If `validator_accounts_update.stake_info` does not already contain the treasury account (i.e., the treasury isn't itself a staked validator — true on mainnet/testnet), the code fetches the account and, if missing, immediately errors out with `StorageError::StorageInconsistentState` [2](#0-1) .
- `check_actor_permissions`/`check_actor_permissions` for `DeleteAccount` only blocks deletion when `account.locked()` is non-zero (`DeleteAccountStaking`) [3](#0-2) ; a non-staking treasury account with zero balance can be deleted via an ordinary `DeleteAccount` action from an unprivileged predecessor with access, with no special protection for the protocol-treasury identity.
- Once the treasury account no longer exists in state and the next epoch boundary arrives, `update_validator_accounts` returns `RuntimeError::StorageError(StorageError::StorageInconsistentState(...))`, and the chain-layer caller `apply_chunk` in `chain/chain/src/runtime/mod.rs` explicitly `panic!`s on any `StorageError` other than `FlatStorageBlockNotSupported`/`MissingTrieValue` [4](#0-3) .
- By contrast, the almost-identical "pay reward to an account, but the account might not exist" scenario for the *contract gas reward* is handled without any error — the reward is simply dropped/retained as burnt rather than crashing anything: `if let Some(ref mut account) = account { ... } ` [5](#0-4) .

### Impact Explanation
A panic inside `apply_chunk` during normal chunk/epoch processing is not a recoverable per-transaction failure — it aborts the validator/node process executing that shard, which every validator tracking that shard would hit identically at the same epoch boundary (deterministic panic), producing a chain-wide stall rather than a single-node divergence. This satisfies the "node panic or chain stall" acceptance bar from an unprivileged, reachable path (anyone able to zero out and delete the treasury account, or more generally any similarly-treated non-validator reward-recipient account referenced by `ValidatorAccountsUpdate`).

### Likelihood Explanation
Likelihood depends entirely on whether the protocol treasury account can be reduced to zero balance and deleted by an ordinary account holder. `action_delete_account`/`check_actor_permissions` impose no special protection for well-known/system accounts beyond the `locked() != 0` stake check [3](#0-2) ; if the treasury account (`near` on mainnet/testnet) has zero balance and zero locked stake, and its access-key holder issues a `DeleteAccount` action, the very next epoch boundary will hit the fatal branch. This requires control of the treasury account's keys (a privileged-in-practice but not protocol-privileged actor) and should be validated by an engineer with full repo access for whether treasury accounts are additionally special-cased elsewhere (e.g. genesis re-seeding, `add it as a user account with zero balance` in `core/chain-configs/src/test_genesis.rs:478-489` suggests treasury presence is assumed elsewhere too, indicating an existing latent assumption).

### Recommendation
Make the protocol-treasury reward-crediting branch in `update_validator_accounts` tolerant of a missing account, symmetric with the gas-reward handling: if `get_account` returns `None`, skip crediting (treat the reward as burnt/dropped, matching the existing invariant documented at `protocol-model/spec/economics.md:99` for gas rewards) rather than returning `StorageError::StorageInconsistentState`. Alternatively, if the protocol treasury account is intended to be a protected, non-deletable identity, enforce that invariant explicitly in `action_delete_account`/`check_actor_permissions` so it can never be removed from state, eliminating the panic path entirely.

### Proof of Concept
1. Deploy/point at a network where the protocol treasury account (`protocol_treasury_account_id`, e.g. `near`) is not a validator and can be independently controlled (holds a full-access key), with zero `amount` and zero `locked`.
2. From that key, submit a `DeleteAccount { beneficiary_id: <other> }` transaction. `check_actor_permissions` only rejects deletion when `locked() != 0` (`runtime/runtime/src/actions.rs:761-776`), so the deletion succeeds and the account is removed from the trie.
3. Wait for the next epoch boundary. `chain/chain/src/runtime/mod.rs:233-277` builds a `ValidatorAccountsUpdate` with `protocol_treasury_account_id = Some(treasury_id)` for the shard hosting that account.
4. `Runtime::apply` calls `update_validator_accounts` (`runtime/runtime/src/lib.rs:1663`); since `stake_info` doesn't contain the treasury account, it hits `get_account(...)?.ok_or_else(|| StorageError::StorageInconsistentState(...))?` at `runtime/runtime/src/lib.rs:1731-1736`, returning `Err(RuntimeError::StorageError(...))`.
5. `apply_chunk` in `chain/chain/src/runtime/mod.rs:1281-1286` matches this as a non-whitelisted `StorageError` and calls `panic!("{err}")`, crashing every node/validator applying that shard for that block — a deterministic, reproducible chain stall.
