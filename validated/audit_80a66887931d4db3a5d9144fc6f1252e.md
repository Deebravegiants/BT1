### Title
Hardcoded 18-decimal / 6-decimal scaling assumptions in `Zap.sell`'s USD-floor check break for any BounceTech LT that isn't 18-decimal - (File: packages/contracts/src/Zap.sol)

### Summary
The Sherlock report describes a `decimalPad` scaling constant computed for a token's decimals once and then baked into a ratio calculation that silently produces wrong results if the actual token's decimal representation ever diverges from what the constant assumes. In alt.fun's `Zap.sell`, the analogous pattern is not a mutable `decimals()` cache but a pair of *hardcoded* decimal-scale literals (`1e18` and `1e12`) baked directly into the USD-floor comparison, under the unstated assumption that every BounceTech LT is an 18-decimal token and that USDC is always 6-decimal. Because `launch()`/`createToken` accept an arbitrary `ltAddress` gated only by `GlobalStorage.ltExists` (not by a decimals check), any BounceTech LT with a non-18 decimal representation would make this scaling wrong by orders of magnitude, exactly mirroring the report's "ratio calculation is off by 10^12" failure mode.

### Finding Description
`Zap._sellInternal` computes the USD value of the LT the seller is about to redeem and compares it against the live 6-decimal USDC floor: [1](#0-0) 

```
uint256 grossUsdcEstimate = (ltReceived * IBounceLeveragedToken(lt).exchangeRate()) / 1e18;
if (grossUsdcEstimate / 1e12 < minUsdcAmount()) revert BelowMinAmount();
```

This line embeds two independent decimal assumptions as literal constants rather than deriving them from the actual token:
1. `/ 1e18` assumes `ltReceived` (an amount of the paired LT) is itself expressed in 18-decimal units, i.e. that `IBounceLeveragedToken(lt).decimals() == 18`.
2. `/ 1e12` assumes the difference between that 18-decimal USD figure and `minUsdcAmount()` (sourced from BounceTech's `GlobalStorage.minTransactionSize()`, denominated in native USDC's 6 decimals) is always exactly `10^12`.

The `exchangeRate()` interface itself documents this same baked-in assumption ("USDC per LT unit, 18-dp"): [2](#0-1) 

Nothing in `Bonding.launch()` (the entry point that accepts an arbitrary `ltAddress` from an unprivileged creator via `Zap.createToken`) enforces that the supplied LT actually has 18 decimals — the only registration gate found is BounceTech's `GlobalStorage.ltExists` check (referenced in `BondingStorage.bounceGlobalStorage` comments): [3](#0-2) 

This same 18-dp assumption for the LT recurs throughout the protocol — `_ltForUsd`/`_initialVirtualLt` in tests, the `mint`/`baseToLtAmount` mock, and Bonding's `VIRTUAL_LIQUIDITY_USD`/`exchangeRate` combination — meaning a non-18-decimal LT would desynchronize virtual reserve sizing, graduation threshold math, and this sell-floor check simultaneously, not just one isolated view function.

### Impact Explanation
If a BounceTech LT with decimals other than 18 (e.g. 6 or 8, which is plausible for a permissionlessly-registered external LT that a creator can pair via `createToken`) is ever paired:
- `grossUsdcEstimate` would be off by a factor of `10^(18-actualDecimals)`, corrupting the `BelowMinAmount` floor check on every sell.
- If the miscalculation makes the estimate appear artificially small, legitimate sells above BounceTech's true redemption floor would revert with `BelowMinAmount`, freezing sellers' ability to exit via `Zap` (their tokens/LT get stuck; they'd need to fall back to direct pair interaction, if even possible).
- If the miscalculation makes the estimate appear artificially large, dust sells that should be rejected pre-flight instead reach `LT.redeem`, which (per the code's own comments) reverts with BounceTech's undecodable `0x05eb05ac` selector — a griefing/DoS on the seller's own transaction, and worse, the same wrong-scale assumption feeds into `Bonding`'s graduation-threshold and virtual-reserve math, which could misprice the entire curve and the eventual LP seeding, causing an LP seeded away from the true close price (freezing/mispricing trader and LP funds).

This satisfies "permanent freezing of trader funds" / "an LP seeded away from the curve close price" per the validation criteria, is reachable purely through the permissionless `Zap.createToken`/`Bonding.launch` LT-selection path, and requires no privileged action.

### Likelihood Explanation
Likelihood is Medium: it requires a creator (unprivileged, permissionless) to launch a token against a BounceTech LT that is registered in `GlobalStorage` but does not have 18 decimals. The codebase's own documentation and interface comments assume all BounceTech LTs are 18-dp, which suggests this may hold for all currently-deployed LTs, but nothing in `Bonding.launch`/`Zap.createToken` enforces it on-chain — the check is missing rather than a design guarantee. If BounceTech ever deploys or has deployed a non-18-decimal LT reachable via `ltExists`, any creator can trigger this by simply selecting that LT at launch, at zero extra cost. Given the sherlock report's root cause is precisely "no on-chain enforcement of a decimals assumption baked into a downstream ratio," this maps directly.

### Recommendation
- At `Bonding.launch()`, explicitly read and validate `IBounceLeveragedToken(ltAddress).decimals() == 18` (or the token's real decimals via a decimals()-like accessor if BounceTech exposes one) and revert if it doesn't match the assumption baked into `Zap`/`Bonding`'s math, OR
- Replace every hardcoded `1e18`/`1e12` scaling literal in `Zap.sell`/`Zap.buy`/`Bonding` with dynamically-fetched decimals (`10 ** IERC20Metadata(lt).decimals()` and `10 ** IERC20Metadata(usdc).decimals()`), computed per-call or cached per-token at launch time and validated against the live token, so a differently-scaled LT can't silently corrupt the USD-floor and graduation math.

### Proof of Concept
Conceptual (cannot be executed without a concrete non-18-decimal `MockLeveragedToken` deployment, which was not found in the indexed test suite — the only mock available, `MockLeveragedToken`, is a plain `ERC20` that inherits OZ's default 18-decimal `decimals()` and was not observed being instantiated with a custom decimals override in the explored test files):
1. Creator calls `Zap.createToken(..., ltAddress = <BounceTech LT with 6 decimals>, seedUsdcAmount)`, which passes BounceTech's `ltExists` gate (no decimals check).
2. A trader buys tokens on the curve, receiving LT-denominated proceeds internally sized in the LT's true 6-decimal units.
3. On `Zap.sell`, `ltReceived` (6-dp units) is divided by the hardcoded `1e18` in `grossUsdcEstimate = (ltReceived * exchangeRate()) / 1e18`, undercounting the true USD value by `10^12`.
4. `grossUsdcEstimate / 1e12` further shrinks the (already wrong) estimate, so a sell that is well above BounceTech's real `minTransactionSize()` floor incorrectly reverts with `BelowMinAmount`, freezing the seller's exit through `Zap` for that token.

**Note on verification limits:** due to index size limits, not all files (e.g., BounceTech's actual `LeveragedToken.sol` source, or a possible explicit decimals-enforcement check elsewhere in `Bonding.launch`/`Factory.sol`) were retrievable through the available search tools. A full audit pass with direct file access (e.g., a Devin session with filesystem access) would be needed to conclusively confirm whether any out-of-band decimals validation exists for `ltAddress` at launch time before treating this finding as fully confirmed.
