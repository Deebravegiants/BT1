### Title
Non-embedded session identity is derived directly from an unsigned, attacker-controllable cookie value with no cryptographic binding to the OAuth-issued session - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`ShopifyAPI::Utils::SessionUtils.cookie_session_id` returns the raw `shopify_app_session` cookie value verbatim, with no signature, HMAC, or any cryptographic check that this value was actually issued by this gem's OAuth flow for the current shop. This mirrors the report's root-cause pattern: a value that controls "who owns this stored state" (`amountInShelter[lpToken]` in the original finding; here, the session id used to fetch a shop's stored access token) can be set/overwritten by an untrusted actor without the binding being re-verified.

### Finding Description
After a successful OAuth callback, for non-embedded apps the gem sets a plaintext `SessionCookie` whose `value` is `session.id` (e.g. `"{shop}_{user_id}"` or `"offline_{shop}"`), built in `Auth::Oauth.validate_auth_callback`: [1](#0-0) 

On every subsequent request, `SessionUtils.current_session_id` reads this cookie back and, for non-embedded apps (or as a fallback for embedded apps without a JWT), returns it unmodified via `cookie_session_id`: [2](#0-1) [3](#0-2) 

Unlike the JWT path (`session_id_from_shopify_id_token`), which derives the session id from a value cryptographically signed with `Context.api_secret_key` via `Auth::JwtPayload`, the cookie path performs **no verification at all** — `cookie_session_id` just echoes `cookies[SESSION_COOKIE_NAME]`. The `SessionCookie` struct itself carries no signature or MAC field: [4](#0-3) 

The binding that should hold is: `session_id_returned_to_host_app == session_id_that_this_gem_actually_issued_via_OAuth_for_this_shop`. Because the cookie value is trusted as-is, if the host application's cookie transport is not itself independently signed/encrypted (this gem does not set `HttpOnly`/signing attributes on the cookie it hands back — it only returns a `name`/`value`/`expires` struct for the host app to set), any code path that lets an attacker influence or read/replay this cookie value (e.g., an app that stores it in a non-signed cookie jar, exposes it in a URL/log, or a subdomain-cookie-overwrite scenario for the app's own domain) lets the attacker's chosen id be used directly as the lookup key into the host's session storage. This is not a hypothetical implementation detail of the host framework misuse — the gem's exported `current_session_id` API returns this unauthenticated value as the definitive session-id "of record" for a shop's session, without ever cross-checking it against any signed claim.

This is directly analogous to the original bug's root cause: a value that is later trusted to select/authorize a specific tenant's stored resource (`amountInShelter[lpToken]` there; the session id used to key `SessionStorage` lookups here) is set/read without re-validating the underlying binding, so a party with only the ability to influence the plaintext value can redirect which tenant's stored token is served.

### Impact Explanation
If a session id is attacker-influenceable and is used verbatim by the host app to fetch a stored `Session` (containing the merchant's access token) from `SessionStorage`, this allows cross-tenant session confusion / access-token exposure: requesting with a crafted `shopify_app_session` cookie value equal to another shop's session id (`"{other-shop}_{user}"` or `"offline_{other-shop}"`) causes the wrong merchant's session/access token to be loaded and used on behalf of the attacker. This satisfies the Critical bar (cross-tenant access / access-token theft) once combined with any cookie-jar weakness in the surrounding app, since the gem itself provides no defense-in-depth (no HMAC/signature) at this specific trust boundary, unlike the JWT path which is signed with `api_secret_key`.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the host application's session cookie to be non-signed/non-tamper-protected (common when developers wire this gem's `current_session_id` cookie fallback into a plain unsigned cookie rather than a framework's signed session store), and requires the attacker to be able to set/replay that specific cookie value on the app's domain. This is squarely the "unprivileged internet user" bucket for apps that follow the gem's documented but weakly-specified cookie fallback path, rather than a theoretical concern — the gem has no HMAC binding on this cookie at all, whereas every other identity-carrying value in the library (OAuth callback params, JWT) is HMAC/JWT signed.

### Recommendation
Sign/HMAC the `SessionCookie` value (e.g., using `Context.api_secret_key` similar to `Utils::HmacValidator`) and verify that signature in `cookie_session_id` before trusting it as a session id, so that a value used to key merchant session/token lookups can only originate from this gem's own OAuth issuance, not from an unauthenticated cookie value.

### Proof of Concept
1. App completes OAuth for `shop-a.myshopify.com`; gem sets cookie `shopify_app_session=offline_shop-a.myshopify.com` (see `Auth::Oauth.validate_auth_callback`, lines 105-109).
2. Attacker, on a request to the same app, supplies (or otherwise causes to be set) `shopify_app_session=offline_shop-b.myshopify.com`.
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, {"shopify_app_session" => "offline_shop-b.myshopify.com"}, false)`.
4. `cookie_session_id` returns `"offline_shop-b.myshopify.com"` unchanged — no signature is verified — and the host app's `SessionStorage.load_session("offline_shop-b.myshopify.com")` returns shop-b's stored access token, which the attacker's subsequent API calls then use. [5](#0-4)
