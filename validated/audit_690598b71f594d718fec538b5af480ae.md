Audit Report

## Title
Missing role-based permission check on GET /v2/external_initiators discloses initiator AccessKey and OutgoingToken to any authenticated 'view' role user - (File: core/web/router.go)

## Summary
The `GET /v2/external_initiators` route is registered in `v2Routes` without any `auth.Requires*Role` wrapper, while the sibling `POST` and `DELETE` routes for the same resource explicitly require `auth.RequiresEditRole`. This allows any authenticated user — including one with the lowest-privilege `UserRoleView` role — to list all external initiators and obtain each one's `AccessKey` and `OutgoingToken`.

## Finding Description
In `core/web/router.go`, the external initiator routes are registered as: [1](#0-0) 
Note that `Create` and `Destroy` are wrapped with `auth.RequiresEditRole`, but `Index` is bound directly via `paginatedRequest(eia.Index)` with no role check.

`ExternalInitiatorsController.Index` fetches all external initiators and serializes them through `presenters.NewExternalInitiatorResource`: [2](#0-1) 

`ExternalInitiatorResource` includes the raw `AccessKey` and `OutgoingToken` fields in its JSON output: [3](#0-2) 

These credentials are exactly what `AuthenticateExternalInitiator` uses to authenticate a caller as an external initiator and implicitly grant `UserRoleRun`, which is sufficient to trigger job runs. The only gate applied to this route is `auth.Authenticate` (session/token validation) at the route-group level; no `RequiresEditRole`/`RequiresAdminRole` check exists on `Index`, unlike the mutating handlers on the same resource.

The test suite's own RBAC expectations table confirms this is a real, currently-existing gap (not an intentional design choice documented as safe) — it explicitly documents that `GET /v2/external_initiators` is reachable by `viewOnlyAllowed: true`, in contrast to `POST`/`DELETE` on the same path which are `false`: [4](#0-3) 

This is an inconsistency in the API's own security model: a resource whose creation/deletion requires edit privileges exposes its secret material to read-only viewers.

## Impact Explanation
This maps to the in-scope "key/secret exfiltration" and "unauthorized job run" impact classes. A `view`-role authenticated user (intended for read-only access with no mutation capability) can retrieve `AccessKey` and `OutgoingToken` for every configured external initiator via a simple GET request. The `OutgoingToken` (paired with the initiator's secret, which is a separate credential not disclosed here) is part of the authentication flow used to impersonate the external initiator and trigger job runs. This is a genuine authorization gap: a lower-privileged role obtains sensitive credential material that the API design intends only edit/admin roles to manage.

## Likelihood Explanation
Exploitation requires only holding valid Chainlink node credentials at the `UserRoleView` level, which is explicitly the least-trusted authenticated role in the system and may be provisioned to broader/less-trusted operators for monitoring purposes. No exploit complexity beyond an authenticated GET request is needed, making this trivially and repeatably exploitable by anyone holding view-level access.

## Recommendation
Wrap the `GET /v2/external_initiators` route with `auth.RequiresEditRole` (or `auth.RequiresAdminRole`, matching the sensitivity of returned secrets), consistent with `Create`/`Destroy`:
```go
authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```
Additionally, consider removing `AccessKey`/`OutgoingToken` from list responses entirely, only surfacing secrets once at creation time via `ExternalInitiatorAuthentication`, as is already done for `Create`.

## Proof of Concept
1. Provision/obtain a node account or API token with `UserRoleView`.
2. Authenticate to the node web API as that view-only user.
3. Issue `GET /v2/external_initiators` — request succeeds (200) and returns JSON containing `accessKey` and `outgoingToken` for every registered external initiator, per `ExternalInitiatorsController.Index` and `ExternalInitiatorResource`.
4. Confirm the discrepancy: attempt `POST /v2/external_initiators` or `DELETE /v2/external_initiators/:Name` as the same user — these correctly return 401 Unauthorized due to `auth.RequiresEditRole`, demonstrating the GET route is the outlier lacking a role check.
5. A Go test analogous to the existing `TestAuth_RBAC` table in `core/web/auth/auth_test.go` (asserting `viewOnlyAllowed: false` for `GET /v2/external_initiators` once fixed) would directly validate the fix.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
