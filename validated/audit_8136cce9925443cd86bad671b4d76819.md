### Title
Zero-share deposit rounding lets users donate underlying assets to the vault without receiving `zft` shares - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`)

### Summary
The Zest v2 tokenized vaults compute shares to mint on deposit via `convert-to-shares-preview`, which performs a floor-rounding division (`mul-div-down amount ts ta`). Unlike `redeem`, which explicitly reverts if the computed output is zero (`ERR-OUTPUT-ZERO`), `deposit` has no equivalent floor check on the minted-share amount `inkind`. This is the same rounding-to-zero share/asset value-identity break identified in Notional's `_convertBPTClaimToStrategyTokens` (H-3): a user can transfer underlying assets into the vault (increasing `assets`) while receiving zero (or fewer than expected) `zft` shares in return, permanently losing their principal to the remaining shareholders.

### Finding Description
`convert-to-shares-preview` in the vault contracts (e.g. `mainnet/contracts/vault/v0-vault-stx.clar:308-315`) computes:
```clarity
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
``` [1](#0-0) 

`mul-div-down` truncates toward zero, so whenever `amount * ts < ta`, the result is `0`. This occurs after the vault has accrued sufficient assets relative to its share supply (e.g., through interest accrual raising `total-assets-preview` faster than `total-supply-preview`, or simply once the vault's price-per-share exceeds `amount`).

In `deposit`, the computed `inkind` is used to mint shares and the deposited `amount` is unconditionally added to `assets`:
```clarity
(inkind (convert-to-shares-preview amount)))
...
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
...
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
``` [2](#0-1) 

There is no `(asserts! (> inkind u0) ...)` check in `deposit`, whereas `redeem` explicitly guards against a zero output:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
``` [3](#0-2) 

Because `min-out` is a caller-supplied parameter (not enforced to be non-zero by the protocol), any user (or front-end) that submits `min-out = 0` — the natural default when a user doesn't know the exact expected output — passes the slippage check `(>= inkind min-out)` even when `inkind` is `0`. The deposit then succeeds: `receive-underlying` pulls the user's assets, `assets` is incremented by the full deposit amount, but `ft-mint?` mints `0` shares to the recipient. The deposited value is fully absorbed into vault backing and redistributed pro-rata to existing shareholders, permanently diluting the depositor's principal to zero shares.

This breaks the "shares minted vs. backing" invariant: `Δassets_vault = amount > 0` while `Δshares_user = 0`, i.e. value is transferred out of the depositor with no corresponding claim minted — the exact class of bug described in the external Notional report (`StrategyUtils._convertBPTClaimToStrategyTokens`), where BPT deposits could mint 0 strategy tokens due to precision-ratio rounding.

### Impact Explanation
This is a direct theft of user principal (not merely unclaimed yield): the depositor's underlying asset becomes vault-owned backing that inflates the redemption value (`convert-to-assets-preview`) for all other existing shareholders, while the depositor receives no `zft` tokens and thus no claim on withdrawal. This matches the "Critical" impact bar (direct theft of user funds at rest) since the deposited principal is irreversibly transferred to other users with no compensating mint.

### Likelihood Explanation
The zero-share condition arises once the vault's price-per-share (`ta/ts`) has grown large enough that `amount * ts < ta`, which is more likely as the vault accrues interest over time or if `total-supply-preview` is low relative to `total-assets-preview` (e.g., shortly after vault creation, or after a large single depositor withdraws most shares while assets remain). No malicious actor input is even required — any ordinary user submitting a deposit with `min-out=0` (or a UI that doesn't reject a computed zero-share preview) can trigger it unintentionally, and a griefer/MEV actor could also target unsuspecting depositors by front-running to inflate the share price just above the depositor's implied threshold. Likelihood is assessed as reachable under normal, permissionless vault operation without any privileged or DAO action.

### Recommendation
Add an explicit zero-shares guard in `deposit`, mirroring the existing `ERR-OUTPUT-ZERO` check already present in `redeem`, e.g.:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed immediately after computing `inkind` in every vault's `deposit` function (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), ensuring any deposit that would mint zero shares reverts instead of silently absorbing the depositor's assets. Additionally, consider requiring `min-out > 0` at the protocol/UI level as defense-in-depth against precision loss.

### Proof of Concept
1. Assume a `v0-vault-stx` instance has accrued interest such that `total-assets-preview = 2_000_000` and `total-supply-preview = 1_000_000` (price-per-share = 2:1).
2. Alice calls `deposit(amount=1, min-out=0, recipient=Alice)`.
3. `convert-to-shares-preview(1)` computes `mul-div-down(1, 1_000_000, 2_000_000) = 0` (floor rounding).
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes since `0 >= 0`.
5. `receive-underlying` transfers Alice's `1` unit of underlying into the vault; `(var-set assets (+ current-assets 1))` increases vault assets.
6. `(try! (ft-mint? zft 0 Alice))` mints zero shares to Alice.
7. Alice has permanently lost her deposited asset with no `zft` balance to redeem it; the extra backing inflates `convert-to-assets-preview` for all existing shareholders. [4](#0-3)
