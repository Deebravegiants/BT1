Audit Report

## Title
Missing rate limiting/allowlist on user-initiated WebAPI trigger requests enables client-side DoS via unbounded DON fan-out - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` accepts any message that carries a syntactically valid ECDSA signature and forwards it to every member of the DON via `don.SendToNode`, with no allowlist check and no per-sender/global rate limiter guarding this fan-out. The gap is explicitly marked by a `// TODO: apply allowlist and rate-limiting here` comment, unlike the sibling node-originated path (`handleWebAPIOutgoingMessage`) which does enforce `nodeRateLimiter`.

## Finding Description
The externally reachable entry point is `gateway.ProcessRequest` (`core/services/gateway/gateway.go`, L221-295), invoked directly by `httpServer.handleRequest` (`core/services/gateway/network/httpserver.go`, L195-245) with no authentication step of its own — it simply reads the body, optionally extracts a bearer token, and calls `s.handler.ProcessRequest(ctx, rawMessage, jwtToken)`. For legacy DON-ID requests, `ProcessRequest` calls only `msg.Validate()` (L256) before dispatching to `h.HandleLegacyUserMessage(ctx, msg, callback)` (L272). `Message.Validate` (`core/services/gateway/api/message.go`, L54-88) checks structural constraints and calls `ExtractSigner`, which recovers *some* valid ECDSA signer address from the signature — it does not check that address against any allowlist tied to the DON/topic being targined.

Inside `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go`, L341-421), after payload decoding and a staleness check, the code reaches the explicit `// TODO: apply allowlist and rate-limiting here` (L384) and then, for any message with `Method == MethodWebAPITrigger`, stores a callback and loops over `h.donConfig.Members`, calling `don.SendToNode` for each member (L416-419) — with no rate limiter or allowlist gating this loop. This is corroborated by the handler's own test suite, which explicitly notes the gap is untested: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` (`handler_test.go`, L365-366). By contrast, `handleWebAPIOutgoingMessage` (node→gateway direction) enforces `h.nodeRateLimiter.Allow(nodeAddr)` before proceeding (L164-168), and the newer v2 HTTP handler (`core/services/gateway/handlers/capabilities/v2/http_handler.go`) implements JWT-based authorization plus rate limiting for its equivalent `HandleUserTriggerRequest` path — confirming that this legacy handler lacks the protections its sibling implementations already apply.

## Impact Explanation
Each accepted request causes `len(h.donConfig.Members)` `SendToNode` calls — one RPC per DON node — with no per-sender or global throttle at this call site. Since `savedCallbacks` growth is only bounded reactively (a periodic prune), and the fan-out itself is unmetered, an attacker able to produce a validly-signed message can force each DON node to process a request repeatedly, and can grow gateway memory faster than the prune interval reclaims it. This matches an in-scope Chainlink impact category of resource exhaustion / DoS against the gateway and its DON members caused by an unprivileged/low-cost client action producing outsized downstream work.

## Likelihood Explanation
The path is reachable through the standard external HTTP entry point with no additional authentication layer in `httpServer.handleRequest` or in `gateway.ProcessRequest` beyond signature well-formedness via `msg.Validate()`. Any party capable of generating an ECDSA keypair and signing a `MethodWebAPITrigger` message with a fresh `MessageID` and current timestamp can repeat this indefinitely; the missing-mitigation TODO comment and the corresponding TODO in the test file both confirm this is a known, unaddressed gap in this handler's code path (not something enforced elsewhere in the connection/auth layer that this trace could not find). This is a legitimate, currently-reachable weakness rather than a speculative scenario.

## Recommendation
Add a per-sender (and/or global) rate limiter to `HandleLegacyUserMessage`, keyed on the recovered `msg.Body.Sender`, analogous to the existing `nodeRateLimiter` used in `handleWebAPIOutgoingMessage`. Replace the TODO with an actual allowlist check restricting which signer addresses may submit `MethodWebAPITrigger` requests for a given DON/topic, following the pattern already implemented for JWT-based authorization and rate limiting in `core/services/gateway/handlers/capabilities/v2/http_handler.go` / `http_trigger_handler.go`.

## Proof of Concept
1. Generate any ECDSA keypair (no special privilege required).
2. Construct an `api.Message` with `Body.Method = MethodWebAPITrigger`, a valid `TriggerRequestPayload` (fresh `Timestamp`), and a unique `MessageID`; sign it with the keypair via `msg.Sign(key)` as done in `triggerRequest()` in `handler_test.go` (L193-234).
3. POST the JSON-RPC-encoded message to the gateway's legacy HTTP endpoint repeatedly with unique `MessageID`s and fresh timestamps.
4. Observe that each request passes `msg.Validate()` and `HandleLegacyUserMessage`'s method/staleness checks, is stored in `savedCallbacks`, and triggers one `don.SendToNode` call per DON member — with no rejection due to sender frequency, unlike `handleWebAPIOutgoingMessage`, which would reject excess node-originated traffic via `nodeRateLimiter`. func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
