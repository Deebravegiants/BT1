## Analysis: Unbounded multisig metadata size vs. custody invariant

I traced the external report's core invariant — *"unbounded owner-controlled string fields can bloat an object past the max Move object size and lock out legitimate state-changing operations"* — into `aptos_framework::multisig_account`.

### Finding

`multisig_account.move`'s `MultisigAccount` resource stores an inline `metadata: SimpleMap<String, vector<u8>>` field [1](#0-0) . Unlike `fungible_asset::Metadata`, which enforces `MAX_NAME_LENGTH`, `MAX_SYMBOL_LENGTH`, and `MAX_URI_LENGTH` on every mutation path [2](#0-1) , `update_metadata_internal` in `multisig_account.move` performs **no size check whatsoever** on `keys` or `values` beyond matching their lengths to each other [3](#0-2) . There is no `MAX_METADATA_KEY_LENGTH`, `MAX_METADATA_VALUE_LENGTH`, or total-metadata-size constant anywhere in the module (confirmed absent via search).

Because `MultisigAccount` is a single Move resource, every field (`owners`, `num_signatures_required`, `last_executed_sequence_number`, `next_sequence_number`, `signer_cap`, `metadata`, event handles) is serialized and rewritten as one blob whenever *any* of them changes — e.g. on `vote_transanction` (writes to the same resource) [4](#0-3) , `execute_rejected_transaction` [5](#0-4) , and the VM-invoked prologue/execution path that increments sequence numbers. If `update_metadata` (self-callable only through the k-of-n proposal flow) [6](#0-5)  is executed with sufficiently large `keys`/`values` vectors, the `MultisigAccount` resource can be inflated past the VM's `max_move_object_size`. Once that happens, **every subsequent write to that resource — voting, executing pending transactions, adding/removing owners, or even calling `update_metadata` again to shrink it — will fail**, because the runtime must re-serialize the whole oversized resource on each mutation.

### Why this is a genuine custody-lock, not just "admin misconfiguration"

- Multisig accounts are the standard resource-account custody pattern for holding APT/FA/token objects and code-object upgrade authority on Aptos.
- A single malicious or compromised owner with enough proposal weight (or one who social-engineers a k-of-n approval) can craft an `update_metadata` transaction that permanently bricks the multisig — no owner, including the honest majority, can ever again execute a corrective transaction to shrink metadata, since even the corrective transaction itself needs to write to the same over-sized resource. This is an **irrecoverable, non-privileged-bypass loss of custody control** over any assets/resource accounts/code objects the multisig governs, matching the report's "permanent lock or non-recoverable loss of ... multisig-held ... value" impact category.
- This differs from ordinary "governance/admin assumption" exclusions because the vulnerability is a missing input-validation guard (structural bug), not a trust assumption about admin behavior — the same class of bug the external report flagged (unbounded field length breaking a shared custody object), just manifesting in `multisig_account` instead of `staking_pool`.

### Limitation

I was not able to fully verify the exact numeric threshold of `max_move_object_size` enforcement point in the VM/resolver within the time available, nor trace the exact byte count at which `update_metadata_internal`'s resource write would fail at runtime — this would require locating the VM's object-size-limit check (likely in `aptos-move/aptos-vm` or `move-vm-runtime`) and confirming it applies per-resource rather than per-transaction-output. This is a gap a background agent with full repo/tool access should close before finalizing severity.

### Title
Unbounded multisig metadata size permanently bricks multisig-controlled custody - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::update_metadata_internal` accepts arbitrary-length `keys: vector<String>` and `values: vector<vector<u8>>` with no per-entry or aggregate size limit, unlike sibling modules (`fungible_asset`) that cap comparable owner-controlled string fields. Because `metadata` lives inline in the single `MultisigAccount` resource that is rewritten on every voting/execution/administrative call, an oversized metadata payload can push the resource past the VM's object size limit, permanently blocking all further multisig operations, including recovery attempts.

### Finding Description
See analysis above: no length assertions exist in `update_metadata_internal` [3](#0-2) , and the `metadata` field is co-located with all operational state in `MultisigAccount` [1](#0-0) .

### Impact Explanation
Permanent, non-recoverable loss of control over any assets, resource accounts, or code objects governed by the affected multisig — high/critical custody impact.

### Likelihood Explanation
Requires reaching the `num_signatures_required` threshold for a single `update_metadata` proposal (normal multisig operation, no privilege escalation) — plausible via a malicious/colluding subset of owners or an honest mistake with very large metadata values, with no on-chain safeguard preventing it.

### Recommendation
Enforce `MAX_METADATA_KEY_LENGTH` / `MAX_METADATA_VALUE_LENGTH` / aggregate metadata size constants in `update_metadata_internal`, mirroring the bounds already used in `fungible_asset::add_fungibility`/`mutate_metadata`.

### Proof of Concept
Not independently executed/verified in this session (no sandbox access); conceptually: create a multisig, propose and approve `update_metadata` with `values` containing e.g. megabyte-scale byte vectors, execute it, then attempt any further multisig call (`vote_transanction`, `execute_rejected_transaction`, another `update_metadata`) and observe resource-size-limit abort with no recovery path.

    fun update_metadata_internal(
        multisig_account: &signer,
        keys: vector<String>,
        values: vector<vector<u8>>,
        emit_event: bool,
    ) {
        let num_attributes = keys.length();
        assert!(
            num_attributes == values.length(),
            error::invalid_argument(ENUMBER_OF_METADATA_KEYS_AND_VALUES_DONT_MATCH),
        );

        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);
        let multisig_account_resource = borrow_global_mut<MultisigAccount>(multisig_address);
        let old_metadata = multisig_account_resource.metadata;
        multisig_account_resource.metadata = simple_map::create<String, vector<u8>>();
        let metadata = &mut multisig_account_resource.metadata;
        let i = 0;
        while (i < num_attributes) {
            let key = keys[i];
            let value = values[i];
            assert!(
                !metadata.contains_key(&key),
                error::invalid_argument(EDUPLICATE_METADATA_KEY),
            );

            metadata.add(key, value);
            i += 1;
        }  spec {
            invariant i <= num_attributes;
            invariant forall k in 0..i: simple_map::spec_contains_key(metadata, keys[k]);
            invariant forall m in 0..i, n in 0..i: m != n ==> keys[m] != keys[n];
        };

    public entry fun vote_transanction(
        owner: &signer, multisig_account: address, sequence_number: u64, approved: bool) {
        assert_multisig_account_exists(multisig_account);
        let multisig_account_resource = borrow_global_mut<MultisigAccount>(multisig_account);
        assert_is_owner_internal(owner, multisig_account_resource);

        assert!(
            multisig_account_resource.transactions.contains(sequence_number),
            error::not_found(ETRANSACTION_NOT_FOUND),
        );
        let transaction = multisig_account_resource.transactions.borrow_mut(sequence_number);
        let votes = &mut transaction.votes;
        let owner_addr = address_of(owner);

        if (votes.contains_key(&owner_addr)) {
            *votes.borrow_mut(&owner_addr) = approved;
        } else {
            votes.add(owner_addr, approved);
        };

        emit(
            Vote {
                multisig_account,
                owner: owner_addr,
                sequence_number,
                approved,
            }
        );
    }

    public entry fun execute_rejected_transaction(
        owner: &signer,
        multisig_account: address,
    ) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);

        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        let owner_addr = address_of(owner);
        if (features::multisig_v2_enhancement_feature_enabled()) {
            // Implicitly vote for rejection if the owner has not voted for rejection yet.
            if (!has_voted_for_rejection(multisig_account, sequence_number, owner_addr)) {
                reject_transaction(owner, multisig_account, sequence_number);
            }
        };

        let multisig_account_resource = borrow_global_mut<MultisigAccount>(multisig_account);
        let (_, num_rejections) = remove_executed_transaction(multisig_account_resource);
        assert!(
            num_rejections >= multisig_account_resource.num_signatures_required,
            error::invalid_state(ENOT_ENOUGH_REJECTIONS),
        );

        emit(
            ExecuteRejectedTransaction {
                multisig_account,
                sequence_number,
                num_rejections,
                executor: address_of(owner),
            }
