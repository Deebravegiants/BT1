### Title
Webhook shop-domain/topic/webhook-id are trusted from unauthenticated headers while HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request body, then dispatches to the app's handler using `shop`, `topic`, and `webhook_id` values that are read from HTTP headers never covered by that HMAC. This breaks the identity binding: `hmac(raw_body) == valid` is treated as proof that `shop-domain header == the shop that produced this payload`, but the signature never binds those two facts together.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight out of request headers with no cryptographic tie to the body or to each other: [2](#0-1) 

`HmacValidator.validate` computes the HMAC over exactly that signable string (the body) and secure-compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` uses this validation as its sole authenticity gate, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated) to construct the `WebhookMetadata` handed to the app's handler: [4](#0-3) [5](#0-4) 

Because the app's `client_secret` (the HMAC key) is shared across all shops that install the app, not shop-specific, a valid `(body, hmac)` pair produced by Shopify for one merchant remains a valid `(body, hmac)` pair regardless of which `shop-domain` header accompanies it. The gem's `process` method never checks that the `shop` header is consistent with anything cryptographically bound to the signature. This is the direct analog of the reported bug class: a field that is acted upon (`shop`, used as the tenant identity for the handler) but is not covered by the integrity check (`HMAC` covers only `raw_body`) — i.e., the equality the code implicitly assumes, `hmac_valid(raw_body) ⇒ shop_header is authentic`, does not hold.

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` **is** included in `to_signable_string` and thus is bound by the HMAC: [6](#0-5) 
This confirms the OAuth callback path correctly binds `shop` to the signature, while the webhook path does not — the asymmetry is the root cause.

### Impact Explanation
An attacker who controls (or has legitimately installed) the app on one shop ("Shop A") can capture any legitimate webhook delivery (raw body + valid `hmac-sha256`) for Shop A, then replay the exact same body and signature to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop ("Shop B"). `HmacValidator.validate` still returns `true` because the signature only ever covered the body. `Registry.process` will then invoke the app's handler with `WebhookMetadata(shop: "Shop B", ...)`, causing the host application to process (and likely persist, act on, or expose) attacker-controlled data under a victim tenant's identity. Depending on how the host app implements handlers (most apps key persistence and side effects off `data.shop`), this enables cross-tenant data injection/corruption — data confusion across merchant boundaries, which falls under Critical (cross-tenant access) impact.

### Likelihood Explanation
Exploitation requires only: (1) the app installed on at least one shop the attacker controls, (2) the ability to intercept or trigger one legitimate webhook delivery to obtain a valid `(body, hmac)` pair, and (3) the ability to send a forged HTTP request to the app's public webhook endpoint with a modified `shop-domain` header — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. This is squarely within the "unprivileged internet user" threat model specified in scope.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (or otherwise cryptographically/contextually validated), for example by:
- Extending `Webhooks::Request#to_signable_string` to include the shop-domain (and ideally topic/webhook-id) alongside the body, matching how `AuthQuery` binds `shop` into its signable string, or
- Cross-checking the header-derived `shop` against an independently trusted source (e.g., requiring the caller to pass the expected shop and rejecting mismatches) before dispatching to `handler.handle`.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker captures a legitimate webhook POST Shopify sends to the app's endpoint, including headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac>`, and the raw JSON body.
2. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally a `webhook_id`/`topic` of their choosing).
3. Server calls `ShopifyAPI::Webhooks::Registry.process(request)`:
   - `Utils::HmacValidator.validate(request)` succeeds because it only verifies `raw_body` against the unchanged `hmac`. [7](#0-6) 
4. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker data as if it originated from the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
