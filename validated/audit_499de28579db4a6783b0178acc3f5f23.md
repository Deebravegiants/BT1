## Finding

### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for every processed webhook from the `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` verifies is computed only over the raw request body. Because the header is not part of the signed material, an attacker who can obtain one genuinely-signed webhook delivery for the app can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header value, and the gem will hand the handler a `WebhookMetadata` object claiming to be from a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable HTTP header, independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string, then immediately forwards `request.shop` (and other header-derived fields) to the app's handler as the trusted tenant identifier, with no cross-check that the shop is consistent with anything in the signed body: [3](#0-2) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body)` should imply `shop == the shop that originated raw_body`.

In reality the equality only proves `hmac == HMAC(secret, raw_body)`; `shop` is an independent, unauthenticated value taken from a header, so the binding `(raw_body, hmac) → shop` does not hold. Any request with a previously valid `(raw_body, hmac)` pair for the app's shared `api_secret_key` can be replayed with a different `shop-domain` header and will still pass `Utils::HmacValidator.validate`, shown here: [4](#0-3) 

### Impact Explanation
Because the app's `api_secret_key` is shared across every shop that has the app installed, a merchant with a legitimate installation (i.e., any unprivileged user who installs the app on their own store) can capture a genuine webhook body/HMAC pair sent to their own callback URL, then resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop's domain. Since `Registry.process` never re-derives or verifies `shop` against the signed body, the handler will process attacker-supplied data under a spoofed tenant identity — a cross-tenant data injection into the app's business logic (e.g., triggering `customers/redact` handling, updating cached order/product data, or any other tenant-scoped action keyed off `WebhookMetadata#shop`) for a shop the attacker does not control.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop to receive a legitimately-signed webhook (something any unprivileged internet user can do for a public app), and (2) replaying the same raw body/HMAC with a modified `Shop-Domain`/`X-Shopify-Shop-Domain` header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required beyond having installed the app once.

### Recommendation
Do not treat header-derived `shop`, `topic`, `api_version`, or `webhook_id` as trusted merely because the body's HMAC is valid. Either include these header values in the signable string used for HMAC validation, or require the host application to independently confirm that the `shop` header corresponds to a shop with an active, matching webhook/subscription (e.g., cross-reference `webhook_id` against the shop's registered subscriptions) before acting on `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering Shopify to send a real webhook: body `B`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC(api_secret_key, B)`.
2. Attacker resends an HTTP POST to the app's webhook endpoint with the identical body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation passes.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on attacker-controlled data under the victim shop's identity.
