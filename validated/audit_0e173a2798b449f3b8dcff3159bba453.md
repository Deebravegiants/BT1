### Title
Webhook shop/topic/id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read directly from unauthenticated HTTP headers that are never included in the signed payload. Since a Shopify app's webhook HMAC is computed with the app's single, shop-wide `client_secret` (the same secret is used to sign webhooks for every shop that installs the app), any user who installs the app on their own store can capture a validly-signed `(raw_body, hmac)` pair and replay it against the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header pointing at a victim shop, causing the app to process attacker-controlled data as if it originated from a different tenant.

### Finding Description
`Utils::HmacValidator.validate` only verifies the digest over `verifiable_query.to_signable_string`, and for webhooks that string is exactly the raw body: [1](#0-0) 

None of the other fields exposed by `Request` — `shop`, `topic`, `webhook_id`, `api_version` — are part of the signed string; they are read straight out of caller-supplied HTTP headers: [2](#0-1) 

`Registry.process` trusts these unauthenticated header values once the body HMAC check passes and forwards them verbatim to the app's handler as the tenant identity of the event: [3](#0-2) 

The identity binding that should hold is: `shop asserted to the handler == shop that the HMAC actually authenticates`. Because the HMAC is computed only over `raw_body` with the app's single shared `client_secret` (identical across every shop that installs the app), this equality does not hold — `hmac` authenticates "some body was signed with this app's secret," not "this body came from shop X." An attacker who legitimately installs the app on their own store receives real webhook deliveries with a valid `(raw_body, hmac)` pair signed by that same shared secret. They can then POST that exact body and HMAC to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different topic/webhook-id). `HmacValidator.validate` still succeeds because it never looks at those headers, and `Registry.process` calls the handler with `shop: "victim-shop.myshopify.com"`, `body:` attacker-chosen content, and an attacker-chosen `topic`/`webhook_id`.

### Impact Explanation
This crosses a tenant boundary: data attributed to one shop can be injected as if it belongs to another shop that the attacker does not control or have access to. Depending on how the host application's webhook handler uses `shop` (e.g., looking up the victim's stored session/access token to react to the "event", writing attacker data into the victim's tenant records, or triggering shop-scoped side effects such as inventory/order updates), this enables cross-tenant data injection/corruption using only the attacker's own legitimately-issued webhook credentials — a Critical-class cross-tenant access issue per the rules.

### Likelihood Explanation
Any user can install a public/free Shopify app on their own store to become a legitimate app installer, which is enough to obtain valid `(raw_body, hmac)` pairs signed with the app's shared `client_secret`. No access to `api_secret_key`, tokens, or victim credentials is required — only the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is standard unprivileged internet access.

### Recommendation
Bind the tenant/topic/id identifiers into the authenticated payload instead of trusting bare headers: include `shop`, `topic`, and `webhook_id` in the signed string checked by `HmacValidator`, or otherwise require the handler/registry to cross-check the header-derived `shop` against a shop that is verified to be one the app is actually installed on (e.g., compare against a stored, previously-established session for that shop) before dispatching to the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, unprivileged installation).
2. Shopify delivers a real webhook to the app: raw body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the same request to the app's webhook route but rewrites the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (body `B` and hmac `H` unchanged).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC(client_secret, B)` and matches `H` — validation passes as shown in [4](#0-3) .
5. The handler is invoked with `shop: "victim-shop.myshopify.com"` even though the request never actually originated for that shop, per [5](#0-4) .
