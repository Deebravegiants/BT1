## Analysis

The HDF5 CVE describes a **stack buffer overflow from insufficient bounds-checking on data written into a fixed-size field**. The closest analog in `alt.fun`'s production code (`packages/contracts/src`) is the fixed-width `uint112` reserve slot on the real HyperSwap V2 pair (a genuine UniswapV2 fork, which — like canonical V2 — reverts with `OVERFLOW` if either reserve exceeds `type(uint112).max` when `_update` runs on `mint`/`swap`). `Bonding.sol` only bounds this hazard at **launch time**, not at **graduation time**, which is where the actual write into the fixed-width slot happens. [1](#0-0) 

That guard (`ExchangeRateTooLow`) checks only the launch-time `virtualLtReserve` derived from the LT's exchange rate at the moment of `launch()`. It never re-validates the value that actually gets deposited into the real V2 pair at graduation time — `ltFromPair`/`tokensForLP`, computed in `_prepareGraduationLiquidity` from the curve's *live* `assetReserve` — which grows as users buy against the curve using an LT whose `exchangeRate()` can decay severely between launch and graduation (LTs are leveraged and can lose most of their value). [2](#0-1) 

Because the graduation USD trigger is dollar-denominated (`realLtRaised × exchangeRate ≥ $9K`), a depressed `exchangeRate` means far more *raw* LT units are needed to cross the same USD threshold — this raw amount becomes `assetReserve`, and later `ltFromPair`, which is drained into `Bonding` by `Router.graduate` inside phase 1 (`_enterGraduating`) before any check against the V2 pair's `uint112` ceiling is performed. [3](#0-2) [4](#0-3) 

If `ltFromPair` (or `tokensForLP`) ends up exceeding `type(uint112).max` by the time phase 2 runs, `finalizeGraduation`'s direct `pair.mint`/`pair.swap` calls against the real HyperSwap V2 pair permanently revert (canonical V2 `OVERFLOW` guard), and there is no fallback or recovery path in `_seedUniswapV2Direct`/`_seedRebalancing`/`_seedDirectMint` for this condition — unlike the hostile-pre-seed brick-resistance design, this failure mode was never load-bearing-tested (only the launch-time value is asserted safe in `AGENTS.md`). [5](#0-4) [6](#0-5) 

Since phase 1 already flips `lifecycle` to `Graduating` (freezing trading) and drains the curve's real LT into `Bonding` before this failure surfaces, a permanently-reverting `finalizeGraduation` leaves the token irrecoverably stuck: trading is frozen forever, the LP is never seeded, `LPLock.recordLock` never fires, and all curve-raised LT plus the 250M reserved tokens are permanently locked in `Bonding` with no rescue path exposed for this state.

### Title
Graduation-time LT reserve can exceed HyperSwap V2's `uint112` slot, permanently bricking `finalizeGraduation` and freezing all curve-raised funds - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.launch` bounds the *launch-time* virtual LT reserve to `≤ type(uint112).max / 4` to avoid overflowing the HyperSwap V2 pair's `uint112` reserve slot at graduation, but this check is never re-validated at graduation time against the *actual* value being deposited (`ltFromPair` / `tokensForLP`), which is computed from the curve's live `assetReserve` and can grow arbitrarily large if the paired LT's `exchangeRate()` decays severely between launch and graduation.

### Finding Description
`canGraduate` fires the USD trigger once `realLtRaised × exchangeRate ≥ graduationThresholdUsd` ( [7](#0-6) ). Because this condition is dollar-denominated, a lower `exchangeRate` requires proportionally more raw LT units to cross the threshold — and BounceTech LTs are leveraged tokens whose `exchangeRate` can depreciate substantially post-launch (this is inherent to leverage, and is explicitly acknowledged elsewhere in the codebase as an accepted economic property of the reserve asset).

`_enterGraduating` → `_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve` and `tokensForLP` purely from the pair's stored reserves, with no bound against `type(uint112).max` ( [8](#0-7) ). It immediately calls `Router.graduate(token, ltFromPair)`, draining the real LT out of the curve `Pair` into `Bonding`, and caches the amounts in `pendingGraduation`, flipping the token to `Lifecycle.Graduating` and freezing trading ( [4](#0-3) ).

Only `Bonding.launch`'s `ExchangeRateTooLow` guard checks a `uint112`-related bound, and it does so against the *initial* virtual reserve derived from the *launch-time* exchange rate ( [1](#0-0) ) — not against the value that will actually be written into the HyperSwap V2 pair's fixed-width reserve slot at graduation. If the LT's exchange rate has since fallen enough that the raw LT needed to cross `graduationThresholdUsd` exceeds `type(uint112).max`, phase 2's `_seedUniswapV2Direct`/`_seedRebalancing`/`_seedDirectMint`/`_routerDepositAndDispose` all eventually call `IUniswapV2Pair(pair).mint(...)` or `.swap(...)` against the real HyperSwap V2 pair ( [9](#0-8)  and [10](#0-9) ), which — mirroring canonical UniswapV2Pair's `_update` — reverts with its own `OVERFLOW` guard once a reserve would exceed `type(uint112).max`. There is no fallback path in the three-regime defense for this failure mode; the natspec only documents the launch-time mitigation for this exact hazard, not a graduation-time one.

### Impact Explanation
Once phase 1 (`_enterGraduating`) has fired, the token is irreversibly in `Lifecycle.Graduating`: trading is frozen (`Bonding.buy`/`sell` require `Lifecycle.Curve`) and the real LT raised by the curve has already been drained via `Router.graduate` into `Bonding`. If `finalizeGraduation` then permanently reverts because the deposit amount overflows the V2 pair's `uint112` slot, there is no other entry point to move the token out of `Graduating`, seed the LP, or recover the drained LT and the 250M reserved tokens sitting in `Bonding`. This is a permanent freeze of all curve-raised trader/LP funds for that token — the same class of impact ("stack buffer overflow" → hard failure on a fixed-size structure) as the underlying CVE, translated to an unrecoverable on-chain revert instead of memory corruption.

### Likelihood Explanation
This requires the paired LT's `exchangeRate()` to fall far enough after launch that the raw LT needed to cross the fixed `graduationThresholdUsd` exceeds `type(uint112).max` (~5.19e33 raw units, i.e. ~5.19e15 whole LT at 18 decimals). This is an extreme depreciation scenario for a leveraged token, but it is exactly the failure mode the `ExchangeRateTooLow` launch-time check was designed to prevent — the developers evidently recognized the hazard class but only guarded the launch-time snapshot, not the graduation-time value, leaving a residual gap for any LT that depreciates meaningfully post-launch. No privileged action is needed to trigger it — an ordinary buyer's trade during a period of severe LT devaluation is sufficient to cross the USD threshold and fire `_enterGraduating`.

### Recommendation
Add an explicit bound check in `_prepareGraduationLiquidity` (or immediately in `_enterGraduating` before draining LT via `Router.graduate`) that reverts if `ltFromPair` or `tokensForLP` would exceed `type(uint112).max`, mirroring the existing `ExchangeRateTooLow` launch-time guard but evaluated against the live, graduation-time reserves rather than only the launch-time snapshot. Alternatively, cap the USD trigger's effective raw-LT contribution so it can never produce a deposit that would overflow the target AMM's reserve encoding, and provide an explicit recovery/pause path for a token stuck in `Graduating` should this ever occur.

### Proof of Concept
1. Creator launches a token paired with LT `L` at a normal `exchangeRate` (passes `ExchangeRateTooLow`).
2. Over time, `L`'s `exchangeRate()` drops sharply (inherent leverage decay/loss — no attacker action needed, though a malicious/compromised LT deployment could accelerate this).
3. An unprivileged trader calls `Zap.buy` / `Bonding.buy` with an amount of `L` large enough (in raw units, cheap in USD terms because `exchangeRate` is now tiny) to push `realLtRaised × exchangeRate` over `graduationThresholdUsd`.
4. `canGraduate` returns true; `_executeBuy` calls `_enterGraduating`, which computes `ltFromPair`/`tokensForLP` from the now-huge raw `assetReserve`, drains the LT via `Router.graduate`, and flips the token to `Lifecycle.Graduating`, freezing trading.
5. The keeper (or anyone) calls `finalizeGraduation`; `_seedUniswapV2Direct`'s eventual `pair.mint`/`pair.swap` call against the real HyperSwap V2 pair reverts with the V2 `OVERFLOW` guard because the deposit exceeds `type(uint112).max`.
6. `finalizeGraduation` can never succeed for this token; it is permanently stuck in `Graduating`, with the curve-raised LT and the 250M reserved tokens frozen in `Bonding`.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }

    function _seedUniswapV2Direct(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        // Regime 2 — pull any donation pre-seed into this contract so it
        // doesn't pollute the post-swap ratio. Routed to `address(this)`
        // (NOT `lpLock`) so donated TOKEN can be burned and donated LT
        // can be swept to the owner via `_sweepLTToOwner` — `LPLock` has
        // no rescue path, so anything sent there is permanently stuck.
        // No-op on a freshly-created pair (balance == reserves == 0).
        IUniswapV2Pair(pair).skim(address(this));

        // Regime 1 — no LP minted yet (`totalSupply == 0`): a pristine empty
        // pair, or a dust pre-seed from `transfer(pair, dust) + sync()` that
        // leaves reserves non-zero while supply is still zero. Keying on
        // supply rather than reserves routes the dust shape here instead of
        // the rebalance path: with zero supply V2 mints from our amounts
        // alone, so the pool opens at the cached ratio and any dust becomes
        // reserves with no LP claim.
        if (IUniswapV2Pair(pair).totalSupply() == 0) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Regime 3 — mint pre-seed: rebalance, then deposit balanced subset.
        // `lpLock_` re-read from storage inside `_routerDepositAndDispose`.
        // Reserves and token-ordering re-read inside `_seedRebalancing` to
        // keep this function's stack pressure under solc's 16-slot ceiling
        // without `viaIR`.
        return _seedRebalancing(tokenAddress, lt, pair, tokensForLP, ltFromPair, protectedLT);
    }
