Confirmed root cause. The webhook `shop-domain` header is never part of the HMAC-signed payload — `Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop` is read independently from an unauthenticated header, and both `WebhookMetadata.shop` and the delivered `body` are then handed to the host application's handler as if they were bound together.

### Title
Webhook `shop-domain` header is not covered by HMAC, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop-domain` header used to attribute the webhook to a specific merchant/tenant is read out-of-band and never included in the signed material. `Registry.process` trusts `request.shop` when constructing `WebhookMetadata` passed to the host app's handler, so the (body, hmac) pair is validated independently of the shop it is claimed to belong to.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, and for webhooks that method returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) and then unconditionally trusts `request.shop` and `request.topic` (also unsigned headers) to build the `WebhookMetadata` delivered to the app's handler: [3](#0-2) [4](#0-3) 

The broken identity binding is: `HMAC(raw_body)` is verified, but the tuple `(shop, raw_body)` that the handler actually acts on is never verified as a unit — i.e., `verified(raw_body) == verified(shop, raw_body)` does not hold. This is the same defect class as the reported issue: a piece of data that the code acts on (`shop`, used for tenant attribution) is not covered by the authenticity check (the HMAC), even though a byte string (`raw_body`) is.

A merchant who has installed the app receives genuine webhook deliveries containing a valid `raw_body` + `hmac-sha256` pair, computed by Shopify with the app's shared secret — this pair is not shop-specific. Because the webhook endpoint is a single shared HTTP endpoint for all shops using the app, this same merchant (an otherwise unprivileged party with respect to *other* merchants' data) can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `shop-domain` header value with a different, victim shop's domain. `HmacValidator.validate` will still pass because it only checks `raw_body` against `hmac`, and the forged `shop-domain` value flows straight into `WebhookMetadata.shop`, which the host application will use to attribute/store/act on the (attacker-controlled) payload as if it originated from the victim shop.

### Impact Explanation
This breaks the shop/tenant binding for webhook processing without requiring the app's `client_secret` or any privileged credential — only participation as a normal (even attacker-controlled) merchant install is needed to obtain one valid signed body. The result is cross-tenant data injection/confusion: a handler that persists or acts on `data.shop` + `data.body` (e.g., updating order/inventory records keyed by shop) can be made to apply an attacker-chosen payload against a victim shop's records, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker needs: (1) their own real installation of the target app (any merchant can install most public apps), (2) the ability to capture at least one legitimate webhook delivery for their own shop (trivial, since it's delivered to their own configured endpoint or can be intercepted via a proxy they control), and (3) knowledge or a guess of a target `shop-domain` (public `*.myshopify.com` values, easily discoverable). No secret key or token is required. Exploitability depends entirely on whether the host application trusts `WebhookMetadata#shop` for tenant scoping without independent verification (e.g., cross-checking against the shop's stored session/access token) — a common but not universal pattern.

### Recommendation
Bind the shop identity to the signed payload before trusting it: either (a) require handlers/host apps to independently verify that `WebhookMetadata#shop` corresponds to a shop with a known, valid installation/session before using it for any tenant-scoped action, or (b) extend `to_signable_string` (or add a secondary check) so the verified material includes the shop domain in a way that can be cross-checked, and document clearly that `shop`, `topic`, and `webhook_id` are unauthenticated header values not covered by the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook, capturing `raw_body` and the `x-shopify-hmac-sha256` header (both valid, produced by Shopify using the app's secret).
2. Attacker sends a POST to the app's shared webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts the headers (all required headers present), `HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC: [5](#0-4) 
4. `Registry.process` invokes the host handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's own webhook body>, ...)`, and any handler logic keyed on `data.shop` now applies attacker-supplied data to the victim shop's records.
