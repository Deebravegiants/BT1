## Title
Unchecked ERC20 return-value in `IntentGatewayV2.withdraw()` (Tron variant) allows non-reverting failed transfers to silently drain escrow accounting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` performs escrow release and dust-sweep token transfers using raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call itself did not revert (`success`). It never inspects the returned data to confirm the ERC20 `transfer` actually returned `true`. This is exactly the "use safe version ERC20" bug class from the referenced report: non-standard tokens that return `false` on failure instead of reverting will be treated as successful transfers.

### Finding Description
In `withdraw()`, escrowed input tokens and accumulated protocol fees are released with: [1](#0-0) 

and dust sweeping in `onAccept` for `RequestKind.SweepDust` does the same: [2](#0-1) 

In all three call sites, `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only reverts if `success` is `false` (i.e., the callee reverted or the call target has no code). It does not decode `returndata` to verify the token actually returned `true`. Some ERC20 tokens (deflationary/blacklist/pausable tokens, or any non-conforming token) return `false` on failure rather than reverting; for these, `success` is `true` even though no tokens moved. Note this contrasts with the rest of the codebase (e.g. `IntentsBase.sol`, `IntentGatewayV2.sol` on EVM, `HyperFungibleToken.sol`) which consistently use OpenZeppelin's `safeTransfer`/`safeTransferFrom`, confirming this Tron variant is an outlier that reintroduced the unchecked-transfer pattern.

`withdraw()` is invoked from `onAccept()` (`RedeemEscrow`/`RefundEscrow`) and `onGetResponse()`, both reachable by any relayer delivering a valid ISMP proof from a paired IntentGateway instance on another chain — no privileged role is required: [3](#0-2) [4](#0-3) 

Critically, before the (unchecked) transfer, the escrow accounting is unconditionally decremented: [5](#0-4) 

so if the underlying `transfer` call returns `false` without reverting, `_orders[body.commitment][token]` is still reduced (and on finalization `_filled[body.commitment]` is set), permanently marking the order/fees as settled even though the beneficiary received nothing.

### Impact Explanation
For any escrowed token or fee token deployed on Tron that does not strictly revert on failed transfers (a real possibility for TRC20/USDT-style tokens and other non-standard tokens), a failed release goes undetected. The escrow balance is deducted and the order is finalized as filled/refunded, but the beneficiary receives zero tokens. This is a permanent freezing/loss of user and solver funds — the tokens remain locked in the `IntentGatewayV2` contract with no accounting path left to reclaim them, since `_orders[commitment][token]` has already been zeroed and `_filled[commitment]` is set. This matches the "permanent freezing of funds" impact category.

### Likelihood Explanation
`withdraw()` executes on every legitimate cross-chain settlement (`RedeemEscrow`/`RefundEscrow`) and cancellation refund (`onGetResponse`) for the Tron IntentGatewayV2, and is triggered by ordinary relayer message delivery — no attacker privilege is needed. The trigger condition is solely that the configured input/fee token behaves non-standardly (returns `false` instead of reverting), which is plausible on Tron's TRC20 ecosystem where several widely used tokens (e.g., TRC20-USDT) are known to deviate from strict EIP-20 semantics.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported and used elsewhere via `using SafeERC20 for IERC20;`), which reverts on both call failure and a `false` boolean return, ensuring escrow accounting is never decremented for a transfer that did not actually move funds.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20 whose `transfer()` returns `false` on failure instead of reverting (e.g., a paused/blacklisted-recipient token, or any minimal ERC20 mock implementing `return false;` on insufficient conditions).
2. A user places an order escrowing that token via `placeOrder`; a solver fills it on the destination chain, and the IntentGateway on the escrow chain later receives a `RedeemEscrow` `onAccept` call from a relayer.
3. Arrange (e.g., via a blacklist/pause on the token, or a mock token used for testing) for the `transfer()` call inside `withdraw()` to return `false` without reverting.
4. Observe: `withdraw()` completes without reverting, `_orders[commitment][token]` is decremented to zero, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — but `beneficiary`'s token balance never increases. The escrowed tokens remain stuck in the contract with no code path to release them again.
