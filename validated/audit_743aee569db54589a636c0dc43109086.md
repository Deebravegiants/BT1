### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the webhook HMAC over the raw body only, while the `shop` identity (taken from the `X-Shopify-Shop-Domain` header) is never part of the signed material. `Webhooks::Registry.process` trusts this `shop` value once the body-only HMAC checks out, so the binding "HMAC-verified request == shop attributed to that request" does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header that is completely outside that signed string: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only ever HMACs `verifiable_query.to_signable_string`, i.e. the body — it has no knowledge of headers: [4](#0-3) 

`Registry.process` validates that HMAC and then immediately forwards `request.shop` to the app's handler as the authenticated tenant identity, with no additional binding check between the verified body and the header-derived shop: [5](#0-4) 

The equality the library implicitly claims to guarantee is:
`shop that produced the HMAC-valid body == request.shop passed to the handler`

but the header carrying `request.shop` is never included in the HMAC-signed bytes, so this equality is not actually enforced by the gem — it is silently assumed to be true.

### Impact Explanation
Because HMAC-sha256 is computed only over the body, any legitimate webhook payload+HMAC pair issued by Shopify to shop A remains a valid `(body, hmac)` pair regardless of which `shop-domain` header accompanies it. An unprivileged holder of one authentic webhook delivery (e.g., a merchant's own webhook receipt captured from their own store, or one obtained via a shared/misconfigured endpoint) can resend the same body/HMAC with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a different, victim tenant's domain. `Registry.process` will validate the HMAC successfully (it never looked at the header) and dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop. Any app logic that keys tenant lookups, authorization, or state changes off `data.shop` from the handler is now operating under a spoofed tenant identity — a cross-tenant identity-confusion condition delivered entirely by this gem's `Webhooks::Request`/`Registry` code, independent of how the host app is written.

### Likelihood Explanation
The prerequisite is possession of any one genuine `(body, hmac)` pair — which is trivial for a merchant/attacker to obtain for their own shop by installing the app and triggering any webhook topic they control (e.g. `app/uninstalled`, `orders/create` on their own store), since Shopify signs the body with the fixed app-wide `api_secret_key`, not anything shop-specific. Replaying with a different `shop-domain` header requires only crafting an HTTP request; no access token, secret, or privileged account is needed. This is a low-effort, entirely unauthenticated (from the perspective of the vulnerable check) attack path.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` to the verified body before it is handed to application handlers, so that a body/HMAC pair cannot be revalidated under an attacker-chosen tenant identity. At minimum, document and enforce that `request.shop` must never be trusted as an authenticated tenant identifier by itself — the library should not present it via the same `WebhookMetadata` object that also asserts a passed HMAC check.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook delivery, e.g.:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid-for-body>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: {}
   ```
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value, but changes the header:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Request.new` accepts it (all required headers present), `HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged, still-valid) signature — see: [5](#0-4) 
4. `handler.handle` is invoked with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the host app to act as though the (attacker-controlled) payload originated from the victim tenant.
