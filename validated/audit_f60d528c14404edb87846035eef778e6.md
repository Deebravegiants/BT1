### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` header, but the value the HMAC actually authenticates (`to_signable_string`) is only the raw request body. Because the same `api_secret_key` is shared by every shop that has the app installed, any merchant who receives a legitimate webhook delivery for their own shop can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the header, and it will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an attacker-controllable HTTP header, entirely outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop`: [3](#0-2) 

`Registry.process` trusts this unauthenticated `shop` value once the body-only HMAC passes, and forwards it straight to the app's registered handler as the tenant identifier: [4](#0-3) 

The broken identity binding is:
`bytes verified by HMAC (raw_body)` ≠ `shop identity acted upon (X-Shopify-Shop-Domain header)`.

Since `api_secret_key` is one shared app-level secret across every installed shop (not shop-specific), an installed merchant — an otherwise unprivileged actor with no special access — can capture a genuine `(raw_body, hmac)` pair delivered to their own endpoint, and simply resend it with the `shop-domain` header swapped to any other shop that also has the app installed. `HmacValidator.validate` will succeed because the body is untouched, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim's `shop`. This is worst for topics with fixed/near-empty payloads independent of shop content (e.g. `app/uninstalled`, or any topic whose body an attacker can predict/reuse), where the exact same signed body is valid for every shop.

### Impact Explanation
This crosses the tenant boundary described in the rules: a webhook attributed to shop A can be forced to be processed as belonging to shop B. Any host application that keys per-tenant state changes off `WebhookMetadata#shop` (uninstall handling, GDPR redact requests, plan/billing changes, config resets, etc.) can be made to act on the wrong tenant's data purely from a replayed/forged header, without the attacker ever possessing the victim's credentials or the app's `api_secret_key`. This matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires the attacker to be an ordinary merchant with the app installed on their own store (no elevated privileges, no leaked secrets) and simply resend an HTTP request they legitimately received with one header changed. For topics with static/empty bodies (this repo's own tests use `raw_body: "{}"`), no guessing of secret material is needed at all, making the attack trivially reproducible.

### Recommendation
Bind the trusted `shop` value to the signed payload instead of an unauthenticated header: either include the shop domain in the HMAC-signed content, cross-check the header `shop` against a shop the app has actually installed/registered (with a corresponding stored shop-specific credential rather than relying solely on the shared `api_secret_key`), or otherwise reject/flag webhook deliveries where the header-provided shop cannot be independently corroborated before invoking application handlers.

### Proof of Concept
1. App has shared `api_secret_key`. Attacker installs the app on `attacker-shop.myshopify.com` and observes Shopify deliver, e.g., an `app/uninstalled` webhook with body `{}` and header `X-Shopify-Hmac-Sha256: <valid-hmac-of-"{}">`.
2. Attacker resends the identical request to the app's webhook endpoint, changing only:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: {...})` builds successfully (all required headers present), `Utils::HmacValidator.validate` succeeds because it only checks `"{}"` against the (unchanged) valid HMAC: [5](#0-4) 
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the host app to treat the victim shop as uninstalled/de-provisioned even though the victim never triggered this event.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
