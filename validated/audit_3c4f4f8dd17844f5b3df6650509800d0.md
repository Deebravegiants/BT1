Audit Report

## Title
Nil Pointer Dereference in Vault `GetPublicKey` Handler via Missing Params on Gateway-Forwarded Request - (File: core/capabilities/vault/gw_handler.go)

## Summary
`handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go` dereferences `*req.Params` without a nil check, while `MethodPublicKeyGet` bypasses `GatewayVaultRequestProcessor.ProcessRequest`, which is the only place enforcing `req.Params == nil` checks for the other vault methods. Since `req.Params` is a `*json.RawMessage`, a JSON-RPC request omitting the `params` field (legal per JSON-RPC 2.0) unmarshals to a nil pointer, and `json.Unmarshal(*req.Params, r)` on a nil pointer causes a runtime panic. [1](#0-0) [2](#0-1) 

## Finding Description
The `HandleGatewayMessage` dispatcher routes `MethodSecretsCreate/Update/Delete/List` through `h.requestProcessor.ProcessRequest`, which explicitly validates `req.Params != nil` in `processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, and `processListSecretIdentifiersRequest`. [3](#0-2)  However, `MethodPublicKeyGet` is dispatched directly to `h.handlePublicKeyGet(ctx, gatewayID, req)`, bypassing that validation entirely: [4](#0-3) 

`handlePublicKeyGet` then unconditionally dereferences `req.Params`: [2](#0-1) 

I confirmed this same unguarded dereference pattern (`*req.Params` without nil-check) also exists in `handleSecretsDelete`, `handleSecretsList`, `handleSecretsCreate`, `handleSecretsUpdate` on the node side, and even in `JSONRPCCodec.DecodeJSONRequest` in `core/services/gateway/api/jsonrpccodec.go`. [5](#0-4)  However, for the secrets methods, `ProcessRequest`'s nil check runs *before* these unmarshal calls execute (it gates whether `handleSecretsCreate` etc. are even invoked in `HandleGatewayMessage`), so those are protected. `MethodPublicKeyGet` has no equivalent guard.

On the gateway side, `HandleJSONRPCUserMessage` explicitly documents that `MethodPublicKeyGet` "doesn't require authorization" and is processed immediately, either from cache or by forwarding to nodes via `h.handlePublicKeyGet(ctx, ar)` on a cache miss. [6](#0-5)  I was not able to fully trace, within the available iterations, exactly how the gateway's `handler.handlePublicKeyGet(ctx, ar)` constructs the outbound request forwarded to nodes — specifically whether it re-marshals a fresh `GetPublicKeyRequest` payload (which would always populate `Params`) or forwards the raw/possibly-nil `Params` from the original user request unchanged. This is a material gap: if the gateway always constructs its own non-nil `Params` when forwarding to nodes, the node-side code path is unreachable with `Params == nil`, and the vulnerability would not be exploitable end-to-end despite the code smell in `handlePublicKeyGet`.

## Impact Explanation
If reachable, this would be a node-side DoS (nil pointer panic in `GatewayHandler.HandleGatewayMessage`), consistent with an availability-impact-only vulnerability. However, given the uncertainty in the exploit chain (whether the gateway forwards user-controlled nil `Params` to nodes, or synthesizes its own), the concrete, end-to-end impact from an unprivileged external client is not established with certainty.

## Likelihood Explanation
Unconfirmed. While `MethodPublicKeyGet` is documented as not requiring authorization, the actual precondition — that a nil/omitted `params` field on the client's JSON-RPC request propagates unchanged all the way to the node-side `req.Params` — was not verified from the code inspected. Go's `encoding/json` does set an omitted JSON field to `nil` for pointer-typed struct fields, which supports the plausibility of the claim, but the full request-forwarding path between gateway and node was not confirmed within the available tool budget.

## Recommendation
Regardless of the above uncertainty, defensive coding warrants adding an explicit `req.Params == nil` check in `handlePublicKeyGet` (`core/capabilities/vault/gw_handler.go`), mirroring `GatewayVaultRequestProcessor`'s pattern, to eliminate this divergence and remove any doubt about reachability.

## Proof of Concept
Not independently reproduced. To confirm exploitability, a reviewer should trace `handler.handlePublicKeyGet(ctx, ar)` in `core/services/gateway/handlers/vault/handler.go` (the gateway-side function forwarding to nodes) to determine whether the outbound request to nodes preserves a nil `Params` from the original client request, then send a JSON-RPC request for `vault_getPublicKey` with `params` omitted to a gateway with a cold public-key cache, and observe whether the node's `GatewayHandler.HandleGatewayMessage` panics.
