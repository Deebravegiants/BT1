## Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

## Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the `x-shopify-hmac-sha256` header against the raw request body. The `shop` identifier that is handed to the application's webhook handler (and used to attribute the event to a tenant) comes from the `x-shopify-shop-domain` header, which is never included in the signed material. Any shop that has the app installed can capture one of its own genuine webhook deliveries (a valid `(body, hmac)` pair, since the signing secret is the single app-wide `api_secret_key` shared across all installs) and replay it to the app's webhook endpoint with the `shop-domain` header swapped to point at a different (victim) tenant. The signature still validates, and `Registry.process` will invoke the app's handler with `shop: <victim shop>` even though the payload actually originated from — and was signed by — the attacker's own installation.

## Finding Description
The HMAC binding that should hold is:
`shop authenticated by HMAC == shop the application acts on`

In `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only the raw JSON body: [1](#0-0) 

while `shop` is pulled straight from an unauthenticated header: [2](#0-1) 

`Registry.process` verifies only the HMAC of that signable string and then forwards `request.shop` — unauthenticated — directly into the data passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the digest over `verifiable_query.to_signable_string` (the raw body) using the single, app-wide `Context.api_secret_key`: [4](#0-3) 

Because `Context.api_secret_key` is one shared secret for the whole app across every merchant installation (not a per-shop secret), any merchant who installs the app can trigger a real webhook to their own endpoint, capture the valid `(raw_body, hmac)` pair Shopify sent them, and then replay that exact body/hmac to the app while substituting the `x-shopify-shop-domain` header for another tenant's domain. `HmacValidator.validate` will report success (the body and secret are unchanged), and `Registry.process` will call the handler with `WebhookMetadata` claiming `shop: <victim-shop>` even though the event content is fully attacker-controlled and the true source is the attacker's own shop.

This breaks the identity binding "bytes verified vs. bytes parsed": the bytes verified by HMAC are only the body, while the `shop` field the application relies on for tenant attribution is parsed from an unverified header.

## Impact Explanation
This qualifies as Critical — cross-tenant access. Any app that keys business logic, database writes, or authorization decisions off `WebhookMetadata#shop` (e.g., "update order status for shop X", "revoke access for shop X on `app/uninstalled`") can be manipulated by an unprivileged merchant (attacker only needs their own valid app installation) into performing actions attributed to, or affecting, a different, victim tenant. This is a direct violation of the multi-tenant isolation the HMAC check is meant to provide.

## Likelihood Explanation
Likelihood is high for any app author who follows this gem's own webhook API as documented: `Registry.process` is the sanctioned single verification entry point, and its only authentication signal is the HMAC-over-body check; the `shop` value is exposed to handlers without any indication that it is unauthenticated. An attacker needs nothing more than a normal, legitimate installation of the target app on their own store to obtain valid `(body, hmac)` pairs, then simply modifies the `shop-domain` header value.

## Recommendation
Bind the `shop` field into the value that is actually verified, or verify it out-of-band:
- Include the `shop`/`x-shopify-shop-domain` value in the signable string used for HMAC computation, or
- After HMAC validation, independently confirm that `request.shop` corresponds to a shop with a currently valid, stored session/access token for this app before trusting it, rather than passing the raw header value straight into `WebhookMetadata`.

## Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a real webhook (e.g. by placing a test order) and captures the raw POST body plus its `x-shopify-hmac-sha256` header — this is a valid `(body, hmac)` pair under the app's shared `api_secret_key`.
3. Attacker sends the identical body/hmac to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks the body signature.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app handler with `shop: "victim-shop.myshopify.com"`, causing the app to act on behalf of, or against, the victim tenant using attacker-controlled body content.
