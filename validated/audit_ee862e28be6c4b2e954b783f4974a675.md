### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, and `webhook_id` values used to route and attribute the webhook are taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identifier after only checking the HMAC over the body, so the shop identity that a host application binds the webhook payload to is never actually authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Request#shop`, `#topic`, and `#webhook_id` are read straight from HTTP headers with no cryptographic binding to the body: [2](#0-1) .

`Utils::HmacValidator.validate` (used by `Registry.process`) verifies the signature over `to_signable_string` (the body) using `OpenSSL.secure_compare`: [3](#0-2) .

`Registry.process` accepts the request once `Utils::HmacValidator.validate(request)` passes, and then constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — as the tenant identifier passed to the app's handler: [4](#0-3) .

This breaks the identity binding: `shop_value_covered_by_HMAC == shop_value_used_for_tenant_routing` does not hold, because only the body is covered by the HMAC while `shop` (the field the host application relies on to select which tenant's data the payload belongs to) is not.

### Impact Explanation
An unprivileged internet user who owns any Shopify store (trivially obtainable, free store) can receive genuine webhooks from Shopify for their own shop, each with a valid `(body, hmac)` pair signed by the app's real `client_secret`. Because `shop`, `topic`, and `webhook_id` are not part of the signed content, the attacker can re-POST the exact same `raw_body`/`hmac-sha256` pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or topic/webhook-id) header with a victim shop's domain. `HmacValidator.validate` still succeeds (the body and secret match), and `Registry.process` hands the handler a `WebhookMetadata` claiming the data originated from the victim shop. Any host application that uses `WebhookMetadata#shop` as the tenant key (e.g., to look up/update per-shop records) will attribute attacker-controlled webhook data to another merchant's tenant — a cross-tenant data injection/impersonation, which maps to the Critical "cross-tenant access" category.

### Likelihood Explanation
The prerequisite is only that the attacker can (a) operate a real or trial Shopify shop to obtain a legitimately signed webhook body/HMAC pair, and (b) know or guess the target app's public webhook receiver URL. No access to the app's `client_secret`, access tokens, or any privileged account is required, and the gem itself does no server-side authentication of the `shop` header — it only validates the body integrity. This is reachable by any internet user without insider access.

### Recommendation
Include the identity-binding fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., by having `to_signable_string` incorporate the headers used for routing), so that `Utils::HmacValidator.validate` fails if any of these headers are altered independently of the body.

### Proof of Concept
1. Attacker creates a development/trial Shopify store and registers the target app, subscribing it to a webhook topic (e.g. `orders/create`).
2. Shopify sends the attacker a legitimate webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker captures this request and replays it to the app's public webhook endpoint, keeping `raw_body` and `hmac-sha256` unchanged but replacing the header `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B)` against the (unaltered) body.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and invokes the app's handler, which now processes attacker-controlled data as if it belongs to `victim-shop.myshopify.com`.
