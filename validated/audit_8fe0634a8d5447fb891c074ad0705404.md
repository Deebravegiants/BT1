Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`), while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers (`lib/shopify_api/webhooks/request.rb:15-33`) and are never included in the HMAC-signed content. `Utils::HmacValidator.validate` only checks the `hmac` against `to_signable_string` [1](#0-0) , and `Registry.process` trusts `request.shop` to build `WebhookMetadata` after that check passes [2](#0-1) .

### Title
Webhook `shop` (tenant identity) header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)` [3](#0-2) . The `shop` attribute that identifies which tenant the webhook belongs to is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [4](#0-3) , but `to_signable_string` — the value the HMAC is computed and checked over — is only the raw body [5](#0-4) . The `shop` header is therefore never covered by the signature.

### Finding Description
The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_which_shop_the_data_is_attributed_to`

In this gem that equality is broken: `hmac_signed_bytes = raw_body` only [5](#0-4) , while `shop` (and `topic`, `webhook_id`, `api_version`) come from headers that are entirely outside the signed content [6](#0-5) .

`Registry.process` does:
1. `Utils::HmacValidator.validate(request)` — passes as long as `raw_body` matches the HMAC computed with `Context.api_secret_key` [7](#0-6) .
2. It then dispatches to the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [8](#0-7) .

Because a single shared `api_secret_key` authenticates webhooks for *every* shop installed on a multi-tenant app, an attacker who legitimately installs the app on their own store receives real, validly-signed webhook deliveries (body + HMAC) for their own shop. Since the `shop` header is not part of the signed bytes, that attacker can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and the handler is invoked believing the data came from the victim shop, i.e. `request.shop` is trusted without being bound to the signature that authenticated the payload.

### Impact Explanation
This breaks the tenant/shop identity boundary in a multi-tenant app built on this gem: webhook payloads/business events can be attributed to (injected into the processing pipeline of) a shop the attacker does not control, using only a signed message the attacker legitimately obtained for their own tenant. This is a cross-tenant access primitive, matching the Critical impact category (cross-tenant access) defined for this analysis.

### Likelihood Explanation
No special privilege is required beyond installing the app on the attacker's own shop (a normal, unprivileged action) to obtain a validly-signed body/HMAC pair, and being able to send an HTTP POST with attacker-controlled headers to the app's public webhook endpoint. No access token, `client_secret`, or leaked credential is needed — only knowledge of the gem's own `Webhooks::Request`/`Registry` verification logic, which is intrinsic to the gem.

### Recommendation
Include the tenant-identifying fields (`shop`, and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the verified body (e.g., mirror Shopify's actual behavior where the HMAC is computed over the full raw body but the consuming application is expected to independently verify the `shop` domain against a known/installed-shop allowlist before trusting `request.shop`). At minimum, `Utils::HmacValidator.validate` or `Registry.process` should assert that the `shop` header corresponds to a shop with an active session/installation before invoking the handler, rather than trusting the header value as-is.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a legitimate, unprivileged action.
2. Shopify delivers a real webhook to the app's endpoint: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: HMAC(secret, B)`. Attacker captures `B` and the HMAC value (attacker controls the endpoint's traffic or logs it via a proxy under their control, since it is their own installation).
3. Attacker sends a forged POST to the same webhook endpoint with the same body `B` and same HMAC header, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally (`lib/shopify_api/webhooks/request.rb:45-63`); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC — the forged `shop` header is irrelevant to that check.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the host application to process attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
