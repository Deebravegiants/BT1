### Title
Webhook tenant identity (`shop`) is delivered outside the HMAC-signed content, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body [1](#0-0) , while the tenant-identifying `shop` field is read directly from an HTTP header that is never included in the signed content [2](#0-1) . `Registry.process` validates the HMAC and then forwards `request.shop` unchanged to the handler as the tenant identity [3](#0-2) . This breaks the intended binding `HMAC-verified-bytes == bytes-acted-on-for-tenant-routing`: the bytes verified are the body only, but the bytes acted on for tenant identification (`shop-domain` header) are unverified.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies the query's HMAC by recomputing `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and comparing it against the `hmac` field, using `Context.api_secret_key` (shared by the app across all installed shops) [4](#0-3) .

For `Auth::Oauth::AuthQuery`, this is done correctly: `shop`, `host`, `code`, `state`, and `timestamp` are all included in `to_signable_string`, so the shop identity is cryptographically bound to the signature [5](#0-4) .

For `Webhooks::Request`, however, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled from HTTP headers via `shopify_header` and are never part of the signed material [6](#0-5) [7](#0-6) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body integrity) before dispatching `request.shop` (unverified) to the registered handler as the authoritative tenant identity for that event [3](#0-2) .

Because the app's `api_secret_key` is a single shared secret used for every merchant/shop installation of the app (not per-shop), any (`raw_body`, `hmac`) pair that is valid for one shop is a valid HMAC for the exact same body regardless of which shop header accompanies it — the signature is body-only and shop-independent. An attacker who legitimately installs the app on their own shop (an unprivileged action available to anyone) receives real, validly-signed webhook deliveries for their own store. If the attacker can influence or predict the body content of a webhook they receive (or simply capture a delivery with a body that is empty or fully attacker-controlled, e.g. `{}` for topics with generic bodies), they can replay that exact `(raw_body, hmac)` pair to the app's own webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers to name a different, victim shop. `HmacValidator.validate` will still pass because it only checks the body against the shared secret; `Registry.process` will then hand the handler a `WebhookMetadata` claiming the victim's `shop` domain [8](#0-7) , with no re-derivation or cross-check against the value Shopify actually associated with that signature.

This is the "field acted on but not covered by the HMAC" identity-binding break called out in the task instructions: `request.shop` is acted upon (used as the tenant key passed to the host app's handler) but is not part of the HMAC-verified bytes (`request.to_signable_string`).

### Impact Explanation
Any host application that trusts `WebhookMetadata#shop` from a gem-validated webhook (i.e., relies on `Utils::HmacValidator.validate` having "authenticated" the whole request, including the shop) to route or attribute the event to a tenant can be made to apply another merchant's webhook to the wrong shop context, or attacker-controlled content to a victim shop's records — a cross-tenant data integrity/access issue. This matches the "Critical - cross-tenant access" impact category, since the shop-scoping guarantee the gem appears to provide (`HmacValidator.validate` gating `Registry.process`) does not actually cover the field applications use to select the tenant.

### Likelihood Explanation
Exploitation requires: (1) the attacker to be an ordinary merchant who can install the app on their own shop (unprivileged, no special access needed), (2) a webhook topic/body that is attacker-influenced or constant/predictable (common for topics with minimal or templated bodies), and (3) the host application deriving tenant scope from `request.shop`/`WebhookMetadata#shop` without an independent authoritative check (e.g., cross-referencing against a shop that is known to have installed the app via a signed installation record). Given that `Registry.process` itself does no such cross-check and the library's own webhook signing contract omits the shop from signed bytes, likelihood is moderate.

### Recommendation
Include the tenant-identifying and routing fields (`shop-domain`, `topic`, `webhook-id`) in the HMAC-signable content for webhook requests, or otherwise cryptographically bind them (e.g., verify `shop` against a known/authoritative list of shops for which the app holds an offline token) before passing `WebhookMetadata` to handlers. At minimum, document clearly that `Utils::HmacValidator.validate` for `Webhooks::Request` only attests to body integrity and that consumers must independently authenticate the `shop` header against their own installation records before trusting it for tenant scoping.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate, unprivileged action).
2. Shopify delivers a webhook to the app with a body `raw_body` and header `shopify-hmac-sha256: HMAC(raw_body, app_secret)` computed with the app's single shared `api_secret_key`.
3. Attacker replays the exact same `raw_body`/`hmac` pair to the app's webhook endpoint, replacing `shopify-shop-domain` with `victim-shop.myshopify.com` (and, if desired, `shopify-topic`/`shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [9](#0-8) , which passes because it only checks `raw_body` against the shared secret.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [8](#0-7) , where `shop` is `"victim-shop.myshopify.com"` despite the payload never having been signed for or by that shop — the host application processes attacker-influenced content under the victim's tenant identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
