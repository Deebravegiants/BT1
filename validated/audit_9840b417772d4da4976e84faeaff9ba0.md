## Finding

### Title
Reserve-balance based LP share accounting allows donation/front-running attack to steal a victim's deposit - ([File: program/src/math.rs], [File: program/src/processor.rs])

### Summary
`Deposit` and `Withdraw` compute the pool's economic reserves from the *live* SPL token balances of the coin/pc vaults rather than from an internally tracked, deposit-only ledger. Because anyone can transfer tokens directly into these vault accounts using the standard SPL Token program (the vaults are simply owned by the AMM authority PDA for withdrawal purposes, not access-restricted on the receive side), an attacker who already holds LP tokens can inflate the vault balances immediately before a victim's `Deposit` executes, causing the victim to be minted disproportionately few LP tokens for the funds they contribute, then immediately `Withdraw` to capture a share of the victim's deposited funds.

### Finding Description
`Calculator::calc_total_without_take_pnl_no_orderbook` derives the pool's "total" coin/pc amounts directly from the token account balances passed in (`amm_pc_vault.amount`, `amm_coin_vault.amount`), which are themselves fetched via `Self::unpack_token_account` on the live vault accounts: [1](#0-0) 

This same reserve figure is used to size LP minted on deposit: [2](#0-1) [3](#0-2) 

and to size the token payout on withdrawal, using `amm.lp_amount` (the internally-tracked total supply counter) as the numerator/denominator base against the *live* vault balances: [4](#0-3) 

Because the vaults are ordinary SPL token accounts, any unprivileged token holder can invoke the standard SPL Token `Transfer` instruction to send extra coin or pc tokens directly to `amm_coin_vault`/`amm_pc_vault` without calling `Deposit` and without any LP tokens being minted in return - the program has no way to distinguish "donated" balance from balance contributed through `Deposit`. `Invokers::token_transfer`/`token_mint_to` in `invokers.rs` only guard the program's own outgoing/minting calls, not third-party incoming SPL transfers to the vault.

An LP holder (attacker) can therefore:
1. Observe a victim's pending `Deposit` transaction.
2. Insert/front-run a plain SPL `Transfer` of a large amount of coin and/or pc tokens directly into the vault(s), inflating `total_coin_without_take_pnl`/`total_pc_without_take_pnl` without changing `amm.lp_amount`.
3. Let the victim's `Deposit` execute against the inflated reserves - `mint_lp_amount` (computed via `InvariantPool::exchange_token_to_pool` at line 1248/1300) is now computed against an artificially large denominator, so the victim receives far fewer LP tokens than the fair-value of the coin/pc they just transferred into the vault.
4. Immediately `Withdraw` using the attacker's pre-existing LP balance. Since `amm.lp_amount` only grew by the small `mint_lp_amount` credited to the victim while the vault balances grew by the full donation *and* the victim's full deposit, the attacker's unchanged LP balance now claims a share of a much larger pool, letting them redeem back their donation plus a slice of the victim's newly deposited funds.

### Impact Explanation
This lets an LP holder extract value directly from another depositor's funds in a single block/transaction sequence, without any privileged access - a concrete theft of user funds via share-price/ratio manipulation, matching the "attacker can steal user funds via first/careful-timed donation to reserve" bug class from the referenced report. Unlike the referenced Surge `Pool`, Raydium does apply an initial-liquidity floor at `Initialize2` (`InitLpAmountTooLess`, requiring `sqrt(init_pc*init_coin) > 10^lp_decimals`), which prevents the *degenerate 1-unit first-depositor* variant, but it does **not** prevent this donation attack against subsequent depositors on an already-initialized, live pool, since deposit/withdraw math still keys off mutable, freely-donatable live vault balances.

### Likelihood Explanation
The attack requires the attacker to already hold LP tokens in the target pool and to be able to order their donation transaction immediately before the victim's `Deposit` transaction (transaction-ordering/front-running, which is feasible for any observer of pending transactions/mempool-equivalent on Solana, e.g. via bundling). No signer privilege, leaked key, or validator collusion is required - only a normal wallet, prior LP position, and standard SPL `Transfer`/`Deposit`/`Withdraw` instructions with attacker-chosen amounts, which satisfies the "single submitted transaction sequence with attacker-chosen accounts and data" bar.

### Recommendation
Track pool reserves via an internal, program-controlled counter that is only updated inside `Deposit`/`Withdraw`/`Swap` instruction processing (mirroring `amm.lp_amount`'s bookkeeping), instead of reading live SPL token account balances (`amm_coin_vault.amount`/`amm_pc_vault.amount`) for `calc_total_without_take_pnl_no_orderbook`. Alternatively, reconcile/ignore any balance surplus above the internally expected reserve when computing deposit/withdraw ratios so unsolicited donations cannot influence share issuance or redemption.

### Proof of Concept
1. Attacker deposits into a pool via `Deposit`, becoming an LP holder with balance `L_a` while `amm.lp_amount = L_total` [5](#0-4) .
2. Attacker observes victim's pending `Deposit` (max_coin/max_pc, base_side) and submits a plain `spl_token::instruction::transfer` sending a large amount `D` of coin and/or pc tokens directly to `amm_coin_vault`/`amm_pc_vault`, ordered to land just before the victim's deposit.
3. Victim's `Deposit` executes: `total_coin_without_take_pnl`/`total_pc_without_take_pnl` now include `D` [6](#0-5) ; `mint_lp_amount` computed via `InvariantPool::exchange_token_to_pool(amm.lp_amount, RoundDirection::Floor)` is diluted relative to the victim's actual contribution [3](#0-2) , yet the victim's full `deduct_coin_amount`/`deduct_pc_amount` are still pulled into the vaults [7](#0-6) .
4. Attacker immediately calls `Withdraw` with `L_a`: `coin_amount`/`pc_amount` are computed as `L_a / amm.lp_amount_after * total_reserves_after` [4](#0-3) , where `total_reserves_after` includes both the attacker's donation `D` and the victim's full deposit, while `amm.lp_amount_after` only grew by the diluted `mint_lp_amount`. Attacker's redemption value now exceeds `L_a`'s pre-attack fair value plus `D`, at the victim's expense.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
