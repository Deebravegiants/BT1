### Title
Webhook HMAC signature covers only the raw body, allowing shop/topic header spoofing that breaks the `shop`/`topic` identity binding in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC that `Registry.process` validates never covers the `shop-domain` or `topic` headers. Yet `Registry.process` uses those unauthenticated header values both to select the handler and to populate `WebhookMetadata` (which app code treats as verified per-tenant identity). Any party who can obtain one validly HMAC-signed `(body, hmac)` pair — trivially available to anyone who installs the target app on their own store and receives a real webhook — can replay that exact body/HMAC to the app's webhook endpoint while freely rewriting the `shop-domain` and `topic` headers, since `secure_compare` only checks the body signature.

### Finding Description
The identity binding that should hold is:
`shop/topic authenticated by HMAC == shop/topic acted upon by the webhook handler`

In `Request#to_signable_string`, only `@raw_body` is returned: [1](#0-0) 

`shop` and `topic` are read straight from attacker-controllable HTTP headers, with no cryptographic tie to the signed body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` trusts the HMAC check as proof of authenticity for the *whole request*, then dispatches based on `request.topic` and forwards `request.shop` into `WebhookMetadata` as if it were verified tenant data: [4](#0-3) 

Because the signature never binds `shop-domain` or `topic`, an attacker who has legitimately received one signed webhook (e.g., by installing the target app on their own store, which many Shopify apps allow via public install) can take that exact `raw_body` + `x-shopify-hmac-sha256` pair and resend it to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` (any victim shop) and/or arbitrary `x-shopify-topic`. The signature check still passes because it only validates the body bytes, not the headers that determine which tenant and which business logic path the payload is attributed to.

### Impact Explanation
This breaks the app's cross-tenant isolation: the gem's own `Registry.process` API attributes attacker-chosen, replayed data to a shop the attacker does not control, and can route it to a different handler than the one Shopify actually intended for that payload (topic confusion). Any host application built on this gem's stated contract — "`process` will verify the request did indeed come from Shopify" (per `docs/usage/webhooks.md`) — inherits this false trust, and downstream handlers that key state changes off `WebhookMetadata#shop` (e.g., app/uninstall bookkeeping, GDPR data requests, order/customer sync per shop) can be tricked into acting on/for a victim tenant using attacker-supplied body content. This matches "cross-tenant access" (Critical).

### Likelihood Explanation
The only prerequisite is possession of one validly signed `(body, hmac)` pair for the target app, which is obtainable by installing the app on an attacker-controlled store (a common, low-privilege action offered by most public Shopify apps) and capturing any inbound webhook. No `api_secret_key`, access token, or victim credential is required — the attacker only replays previously-observed ciphertext-equivalent bytes with forged headers.

### Recommendation
Include the `shop-domain` and `topic` header values (and ideally `webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signature before `Registry.process` uses them to route/attribute the webhook, matching how the OAuth `AuthQuery#to_signable_string` binds all relevant fields: [5](#0-4) 

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with raw body `B` and header `x-shopify-hmac-sha256: H` (valid signature of `B`).
2. Attacker sends `POST /webhooks` to the same app with body `B` unchanged, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: app/uninstalled`.
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes HMAC over `B` only, matches `H`, returns `true`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) looks up the handler for the attacker-chosen topic and invokes it with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to act on behalf of `victim-shop.myshopify.com` using attacker-supplied data even though Shopify never sent this request for that shop/topic.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
