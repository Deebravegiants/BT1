## Custody Analog Found: Transaction fee reward truncation permanently destroys validator-owed fees

### Title
Per-epoch-per-pool transaction fee cap silently destroys already-accrued validator fee rewards instead of carrying them forward - (File: `aptos-move/framework/aptos-framework/sources/stake.move`)

### Summary
The Olas bug reduces to one invariant: an amount that has been formally reserved/recorded as owed (`effectiveBond`) must not be silently truncated by an unrelated, later-applied limit at the moment of actual minting/payout — any shortfall must not simply vanish. In Aptos's `stake` module, `record_fee` accrues exact per-validator transaction-fee amounts into `PendingTransactionFee.pending_fee_by_validator` during the epoch [1](#0-0) . At epoch end, `update_stake_pool` reads and **removes** the full accrued amount, but only mints/credits up to a separately configured `TransactionFeeConfig.max_fee_octa_allowed_per_epoch_per_pool`, discarding any excess with no carry-over, refund, or alternate accounting [2](#0-1) .

### Finding Description
`record_fee` is a VM-only, protocol-driven entry point that precisely tracks how much transaction fee each validator index has earned this epoch [3](#0-2) . This is the exact analog of `effectiveBond` in the Olas report: a running ledger of value the protocol has already promised to a specific party.

At `on_new_epoch()` → `update_stake_pool()`, the code does:
```
let fee_octa = pending_fee_by_validator.remove(&validator_index).read();
if (fee_octa > fee_limit) {
    fee_octa = fee_limit;
};
``` [2](#0-1) 

The map entry is fully removed (`.remove(...)`) regardless of whether `fee_limit` is smaller than the recorded amount. Only the truncated `fee_octa` is then split into `fee_active`/`fee_pending_inactive` and minted via `coin::mint` into the validator's stake pool [4](#0-3) . The difference between what was recorded as owed and what was actually minted is never minted, never re-queued for a future epoch, and never routed anywhere else — it is permanently lost.

This is confirmed by the framework's own test: 222 octa is accrued for validator 1 via three separate `record_fee` calls, then a config with `max_fee_octa_allowed_per_epoch_per_pool: 20` is set, and after `end_epoch()` only 20 octa is distributed — the other 202 octa is gone with no compensating event [5](#0-4) . The cap can be changed by `aptos_framework` governance at any time (including mid-epoch, as the test does), so a cap lowered after fees have already accrued in the pending map retroactively destroys already-earned rewards for that epoch, exactly mirroring how the Olas bond's `effectiveBond` reservation could outlive the mint-time inflation window and be silently truncated.

### Impact Explanation
This is a supply/custody accounting corruption: value that the protocol's own ledger (`PendingTransactionFee`) states is owed to a specific validator's stake pool is unrecoverably destroyed rather than delivered or preserved, with the accrual entry deleted and no burn/redirect event emitted to reconcile the discrepancy. Validators lose real fee revenue with no recovery path — the same "lost payout" custody pattern as the seed report, applied to APT stake-pool rewards instead of Olas bond payouts.

### Likelihood Explanation
This triggers under any normal operating condition where `distribute_transaction_fee` is enabled and a pool's accrued per-epoch fees exceed `max_fee_octa_allowed_per_epoch_per_pool` — no attacker action or unprivileged exploit path is required beyond ordinary high transaction volume routed to a validator, or governance adjusting the cap between record and distribution. It does not require breaking any access control; it is a straightforward accounting gap in the cap-then-remove sequence.

### Recommendation
When `fee_octa > fee_limit`, do not discard the remainder: either (a) re-insert `fee_octa - fee_limit` back into `pending_fee_by_validator` for the validator's carried-forward pending fee (keyed persistently rather than by ephemeral, per-epoch-reassigned validator index, or accounted by stable validator address), or (b) route the excess to a defined destination (e.g., treasury) with an emitted event, so that no fee amount that has been formally recorded as owed can be silently destroyed.

### Proof of Concept
The framework's existing test demonstrates the loss directly: `test_transaction_fee_limit` accrues 222 octa for `validator_1` via `record_fee`, sets `max_fee_octa_allowed_per_epoch_per_pool = 20`, and asserts only `fee_amount: 20` is ever distributed [6](#0-5) ; the remaining 202 octa is never minted, never appears in any event, and the map entry backing it has already been removed by `update_stake_pool` at that point.

    public(friend) fun record_fee(
        vm: &signer,
        fee_distribution_validator_indices: vector<u64>,
        fee_amounts_octa: vector<u64>
    ) acquires PendingTransactionFee {
        // Operational constraint: can only be invoked by the VM.
        system_addresses::assert_vm(vm);

        assert!(
            fee_distribution_validator_indices.length() == fee_amounts_octa.length()
        );

        let num_validators_to_distribute = fee_distribution_validator_indices.length();
        let pending_fee = borrow_global_mut<PendingTransactionFee>(@aptos_framework);
        let i = 0;
        while (i < num_validators_to_distribute) {
            let validator_index = fee_distribution_validator_indices[i];
            let fee_octa = fee_amounts_octa[i];
            pending_fee.pending_fee_by_validator.borrow_mut(&validator_index).add(
                fee_octa
            );
            i += 1;
        }
    }
