### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw webhook body, so the HMAC signature validated by `HmacValidator` never covers the `shop-domain` (or `topic`/`webhook-id`) header. `Registry.process` nonetheless trusts `request.shop` taken straight from that unauthenticated header when dispatching webhook data to the host application's handler, letting any merchant using the app relabel a legitimately-signed webhook payload as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` verifies only the value returned by `to_signable_string` (the body) against the shared `api_secret_key`: [3](#0-2) 

`Registry.process` treats this validation as sufficient authentication of the whole request, then passes the unauthenticated `request.shop` value straight into the app-facing `WebhookMetadata`: [4](#0-3) 

The `api_secret_key` used to compute the HMAC is a single value shared across every shop installed on the app, not a per-shop secret — this is confirmed by the test setup, which signs the same secret for any `shop.myshopify.com`: [5](#0-4) 

This breaks the intended identity binding:
`HMAC-verified bytes (body)` ≠ `shop identity acted upon (header value trusted by handler)`.

Because the secret is shared across all installed shops, any merchant that has the app installed can receive a legitimately Shopify-signed webhook addressed to their own shop (e.g. by triggering an `orders/create` event), capture the raw body + `x-shopify-hmac-sha256` value from their own endpoint logs/proxy, and replay that exact body+HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` calls the app's handler with `shop: "victim-shop.myshopify.com"`, causing the host application to process/store data as if it originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity bypass: an unprivileged app user (any merchant with the app installed) can make the host application attribute arbitrary webhook payload data to a different, victim shop's tenant record, without needing the app's `api_secret_key`, an access token, or any credential belonging to the victim. Depending on how the host app's webhook handler acts on `data.shop` (e.g. updating customer/order records, triggering downstream provisioning, or uninstall/GDPR flows), this can lead to cross-tenant data corruption or injection — classified as Critical (cross-tenant access) per the impact rubric.

### Likelihood Explanation
Likelihood is realistic: the attacker only needs their own legitimate app installation (any merchant can install most public apps) and the ability to observe body+HMAC pairs sent to their own webhook endpoint, which requires no special access beyond controlling their own server/proxy. No secrets or victim credentials are needed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed content, or otherwise cryptographically bind the shop to the payload before trusting it (e.g., verify the shop against a separately authenticated channel, or require Shopify's newer per-request signature scheme that covers headers). At minimum, `to_signable_string` should not silently exclude data (`shop`, `topic`) that downstream handlers treat as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., updates an order) so Shopify sends a signed webhook to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of raw body using the app's shared api_secret_key>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker captures the exact raw body and HMAC value from their own server logs/proxy (no secret required — they legitimately received this request).
3. Attacker resends the same body and same `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) recomputes HMAC over the (unchanged) body and it matches — validation passes.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the host application to process attacker-controlled data under the victim tenant's identity.
