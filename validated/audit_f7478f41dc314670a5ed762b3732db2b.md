## Title
Webhook `shop` (and `topic`, `api_version`, `webhook_id`) headers are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-validated signable content solely from the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook are read from unauthenticated HTTP headers. This breaks the identity binding `hmac_covers(shop) == shop_used_for_tenant_attribution`, allowing a party who possesses one genuine `(raw_body, hmac)` pair to relabel it as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`/`api_version`/`webhook_id`) accessors are parsed straight from headers, independent of the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `hmac` against `to_signable_string` (the body only) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` checks only that the body-HMAC is valid, then trusts the header-derived `shop` to build `WebhookMetadata` and dispatches it to the app's handler: [4](#0-3) 

Because `Context.api_secret_key` (the app's `client_secret`) is shared across every shop that has installed the app, any shop that has installed the app can obtain a genuine `(raw_body, x-shopify-hmac-sha256)` pair for a payload of its choosing (e.g. by creating an order/customer with attacker-controlled field values in its own store, which Shopify will sign and deliver as a real webhook). Because the `shop-domain` header is not part of the signed content, that attacker can replay the same body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` will invoke the app's handler with `data.shop` set to the victim's domain and `data.body` fully attacker-controlled.

### Impact Explanation
This crosses the multi-tenant boundary the gem is meant to preserve: the handler is invoked believing the event, and its attacker-chosen payload, originates from a specific victim tenant when it did not. Host applications commonly key business logic (order/customer records, credits, inventory updates, notifications) directly off `data.shop`, so this enables cross-tenant data injection/spoofing without requiring any credentials belonging to the victim shop — only requiring that the attacker's own shop has the app installed. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any merchant who installs the app (a fully unprivileged, self-service action) can generate arbitrary genuine webhook bodies for their own store and needs no access to the app's `client_secret`, the victim's credentials, or TLS interception — only the ability to send an HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. This makes the attack straightforward for any adversarial merchant/tenant.

### Recommendation
Bind the routing/tenant fields into the verified signature material, or otherwise cryptographically bind `shop` to the HMAC-covered body (e.g., include the shop domain in `to_signable_string`, or require the receiving app to look up an existing installed session for the claimed shop and compare it against an independently-authenticated identifier before trusting `data.shop`). At minimum, document prominently that `data.shop` in `WebhookMetadata` is not authenticated by the HMAC and must not be used as a sole tenant-selection key without corroboration.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining an active install with the same `Context.api_secret_key` used for all merchants.
2. Attacker triggers a webhook (e.g. `orders/create`) on their own shop with a payload body of their choosing; Shopify sends a POST to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`.
3. Attacker (or a party who can reach the endpoint, since it's a public HTTP endpoint) resends the identical `raw_body`/`x-shopify-hmac-sha256` pair, only replacing the header to `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the replaced header, and `Utils::HmacValidator.validate` succeeds since it only recomputes over `raw_body`, per [1](#0-0)  and [5](#0-4) .
5. `Registry.process` calls the app's handler with `data.shop == "victim.myshopify.com"` and `data.body` equal to the attacker-controlled payload, per [4](#0-3) .
