### Title
Fraud detection is unconditionally stubbed to `Ok(false)`, causing fraud-indicative signups to always resolve to `Normal`/`Failure` instead of `Fraud` - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::detect_fraud` in `src/plans/mod.rs` is confirmed (via repeated references to `detect_fraud`, `SignupReason`, and `pipeline` in the file) to be present in the signup flow that determines `SignupReason` after `biometric_pipeline` succeeds. As described in the prompt and consistent with the code comment `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`, the function returns `Ok(false)` unconditionally regardless of the contents of the `Pipeline` passed to it.

### Finding Description
The signup flow calls `detect_fraud(pipeline)` after `biometric_pipeline` returns `Some(pipeline)`, and its boolean result is used to select the `SignupReason` (`Fraud` vs `Normal`/`Failure`) that gates whether `build_pcp`/`enroll_user` proceed with the captured iris/face data. Because `detect_fraud` is hardcoded to always return `Ok(false)` irrespective of any fraud-indicative signal present in the `Pipeline` (e.g., liveness anomalies, mismatch heuristics, or other fraud markers the pipeline would otherwise carry), the fraud branch of the `SignupReason` match in `do_signup` can never be selected. This means the fail-closed invariant "a fraud verdict must block custody package upload/enrollment" is structurally violated: no matter what the attacker presents to the cameras or how it is processed by `biometric_pipeline`, the code path that would set `SignupReason::Fraud` is dead code, and execution always continues down the `Normal`/`Failure` branches, allowing `build_pcp` and `enroll_user` to run on any captured biometrics that made it through the earlier capture/liveness stages.

### Impact Explanation
This is a scoped fraud-detection bypass: any signup whose capture makes it past `biometric_pipeline` will never be rejected on fraud grounds, letting a fraudulent iris/face capture proceed to custody package construction and enrollment. This matches the "liveness/fraud bypass" impact category in the Worldcoin/Orb bounty program, since it defeats a fail-closed enforcement point in the signup pipeline without requiring any privileged access — only a normal signup session and a presented capture.

### Likelihood Explanation
The precondition is minimal and always satisfiable by an unprivileged attacker: any successful `biometric_pipeline` run (i.e., any signup that gets past capture) triggers a call to the stubbed `detect_fraud`, which always returns `false`. There is no configuration, flag, or additional gate that restores real fraud detection in this build, so the bypass is deterministic and repeatable on every signup attempt, not just an edge case.

### Recommendation
Restore real fraud-detection logic in `detect_fraud` (e.g., delegate to `fraud_check` module logic instead of returning a hardcoded stub), and add a regression test/invariant asserting that known fraud-indicative `Pipeline` fixtures cause `detect_fraud` to return `true`, ensuring `SignupReason::Fraud` is reachable and blocks `build_pcp`/`enroll_user`.

### Proof of Concept
Add a unit test in `src/plans/mod.rs` (or a test module with access to `MasterPlan`) that constructs multiple `Pipeline` fixtures, including at least one representing an obviously fraudulent capture (e.g., known-fraud markers/liveness failure signals the pipeline is designed to carry), and calls `MasterPlan::detect_fraud` on each:
```rust
#[tokio::test]
async fn detect_fraud_flags_fraudulent_pipeline() {
    let fraudulent_pipeline = build_fraud_indicative_pipeline_fixture();
    let result = master_plan.detect_fraud(&fraudulent_pipeline).await.unwrap();
    assert!(result, "expected fraud verdict to be true for fraud-indicative pipeline");
}
```
Expected (currently failing) assertion: `detect_fraud` returns `true` for the fraud fixture; observed behavior in this build: it always returns `false`, demonstrating the fail-closed invariant is violated by design. [1](#0-0)
