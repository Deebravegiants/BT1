### Title
Accrual `scaled_to_original` overflows i128 before the borrow-index cap engages, permanently freezing a large high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
The bug class in ALPINE-CVE-2019-13108 is "arithmetic edge case (integer overflow) crashes the program → denial of service." The analog in XOXNO Lending is an i128 overflow inside the interest-accrual path: `accrue_step` computes `borrowed_original = scaled_to_original(borrowed, borrow_index)` — an unbounded `x * y / RAY` multiply — *before* `update_borrow_index` can clamp the index to `MAX_BORROW_INDEX_RAY`. Once `scaled_borrowed * borrow_index` exceeds `i128::MAX`, accrual panics with `MathOverflow`, and since every state-changing entrypoint accrues first, the market is permanently bricked.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-61` unscales both debt and supply at the start of each compounding chunk:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` (`common/src/rates/scaling.rs:14`) is `scaled.mul(env, index)` → `mul_div_half_up` (`common/src/math/fp_core.rs:108`), which panics with `GenericError::MathOverflow` when the product `scaled * index` does not fit `i128`. The index cap `MAX_BORROW_INDEX_RAY` is applied only later inside `update_borrow_index` (`common/src/rates/index.rs:13-19`), so the cap cannot prevent the value-level overflow: the product of scaled debt (which grows unboundedly with pool size) times the index overflows well before the index itself reaches `10^36`.

The mutating path `global_sync` (`contracts/pool/src/interest.rs:20-33`) runs `accrue_chunk` → `accrue_step` at the top of every pool verb. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) proves the sequence end-to-end: after accrual panics once, `withdraw` and `repay` revert with `MATH_OVERFLOW`, and `borrow_index < MAX_BORROW_INDEX_RAY` confirms the cap never engaged. The test notes the documented safety bound in `docs/reference/formulas.md` is wrong.

### Impact Explanation
Permanent freezing of funds and protocol insolvency on the affected market. Once `scaled(borrowed) × borrow_index ≥ i128::MAX`, every call that accrues — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `update_indexes` — reverts unconditionally. Suppliers can never withdraw, borrowers can never repay, liquidators cannot clear positions, and bad debt cannot be socialized. All cash held in that market's book is frozen permanently because Soroban contracts have no recovery path once every entrypath panics.

### Likelihood Explanation
Reachable by unprivileged addresses using only `supply` and `borrow` plus elapsed time — no privileged action needed. The trigger condition is mechanical: scaled debt (RAY) × borrow index > i128::MAX ≈ 1.7e38. With an index of ~170×RAY this requires on the order of 10^9 whole-token units of open debt; at lower debt it just needs proportionally more index growth. On a steep rate curve at sustained ~98% utilization, the index grows past the cliff within years to a few decades (the test bounds it under 40 years). The main mitigants are the very large capital required to seed the market and the long duration at high utilization — a whale or attacker with a large position can deliberately keep utilization pinned near the kink to accelerate index growth. This matches a Medium severity: a real, deterministic, attacker-influenceable permanent freeze, but gated by significant capital and time.

### Recommendation
Make the accrual overflow-safe rather than panicking:

- In `accrue_step`/`simulate_update_indexes_body`, detect saturation: use a checked/saturating variant of `scaled_to_original` (e.g. `mul_div_floor_saturating`-style) for `borrowed_original`/`supplied_original` used only for the utilization ratio, or clamp utilization inputs so `calculate_borrow_rate` still returns the steep-segment rate.
- Clamp `borrow_index` to `MAX_BORROW_INDEX_RAY` when the unscale would overflow, so the cap engages and accrual goes sticky instead of bricking the market (the capped-index path already accrues nothing per `common/tests/rates/simulate.rs:351-367`).
- Alternatively, cap total scaled debt/supply per market at listing time so `scaled × MAX_BORROW_INDEX_RAY < i128::MAX` is an enforced invariant.

### Proof of Concept
The existing harness test is the PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`):

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);            // seed whale market
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// => Error(Contract, MATH_OVERFLOW) with borrow_index < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),  errors::MATH_OVERFLOW);
```

An unprivileged attacker executes: `supply(hub, BIG18, huge_amount)`, `borrow(BIG18, ~0.98×supply)` via collateral in another market, then lets time pass while keeping utilization high (e.g., topping up debt or donating to keep the ratio pinned). The first accrual after `scaled_debt × borrow_index` crosses `i128::MAX` panics inside `accrue_step` → `global_sync`, and every subsequent market verb panics identically, freezing all supplier funds in that market forever.
