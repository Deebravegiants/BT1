Audit Report

## Title
CORS wildcard origin allowlist bypass via missing subdomain boundary check in `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` validates wildcard CORS entries (`*.domain.com`) using a bare `strings.HasSuffix(originHost, allowedHost)` check after stripping the `*.` prefix, with no verification that a `.` boundary separates the attacker-controlled prefix from the allowed suffix. This allows an attacker who controls a domain such as `evilethereum.org` to be treated as an allowed origin under a `*.ethereum.org` wildcard entry, since `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`.

## Finding Description
The relevant code is: [1](#0-0) 

which strips the `*.` prefix from the configured allowed host and then checks only a raw string suffix match, with no dot-boundary check. This means any domain string that happens to end with the configured suffix (e.g. `evilethereum.org`, `notarealethereum.org`) will match, even though it is not a subdomain of the intended allowed domain.

This flawed check feeds directly into `handleRequest`, which reflects the attacker-supplied `Origin` header value back as `Access-Control-Allow-Origin` once `isAllowedOrigin` returns `true`: [2](#0-1) 

The existing test suite verifies the negative case where a origin does not end with the allowed suffix at all (`ethereum.remix.org` vs `ethereum.org`), but does not cover the no-dot-boundary bypass case (`evilethereum.org` vs `ethereum.org`), confirming the gap is untested and unaddressed.

The scheme and port checks earlier in the function are exact-match and do not mitigate this host-suffix flaw.

## Impact Explanation
When a Gateway operator enables CORS (`CORSEnabled = true`) and configures a wildcard entry in `CORSAllowedOrigins` (a supported, documented configuration pattern, not a misuse of the feature), an attacker who registers or hosts content on a domain sharing the allowed suffix (e.g. `evilethereum.org` for an intended `*.ethereum.org` policy) can have their origin reflected in `Access-Control-Allow-Origin`. This lets JavaScript running on the attacker's page make cross-origin `fetch` requests to the Gateway's HTTP endpoint and read the JSON-RPC-style response body, corrupting the intended origin-isolation boundary the CORS allowlist is meant to enforce. This maps to the in-scope "allowlist bypass" / cross-origin response disclosure category for the Gateway.

## Likelihood Explanation
The vulnerable check is reachable by any unprivileged remote client sending a normal HTTP request with a crafted `Origin` header to an internet-facing Gateway instance that has CORS enabled with at least one wildcard entry. The only precondition is that the operator uses the wildcard CORS feature as documented (not a misconfiguration) and that the attacker registers/hosts a domain with the matching suffix — a cheap, realistic, and repeatable setup requiring no credentials, elevated network position, or leaked secrets.

## Recommendation
Require an explicit boundary when matching wildcard hosts, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[2:]
    if originHost == suffix || strings.HasSuffix(originHost, "."+suffix) {
        return true
    }
}
```
This ensures `evilethereum.org` is rejected while `remix.ethereum.org` still correctly matches `*.ethereum.org`.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send an HTTP request to the Gateway endpoint with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirming `isAllowedOrigin` incorrectly returned `true` for a non-subdomain sharing only a string suffix.
4. Extend `core/services/gateway/network/httpserver_test.go` (alongside `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) with a case using origin `https://evilethereum.org` against allowed `https://*.ethereum.org`, asserting the header is currently (incorrectly) set, to prove the bypass.
