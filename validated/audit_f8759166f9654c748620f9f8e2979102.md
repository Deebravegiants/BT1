## Title
Webhook `shop-domain`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing shop-identity spoofing in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are never part of the signed material. `Registry.process` validates the HMAC and then unconditionally trusts these unauthenticated header values as the shop identity handed to the host app's handler, breaking the binding `hmac-verified bytes == bytes acted on`.

### Finding Description
`Webhooks::Request` parses several Shopify headers but only the raw body participates in HMAC verification: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` come from `shopify_header`, which just reads `@headers["shopify-#{name}"]` with no cryptographic tie to `hmac`: [2](#0-1) 

`Registry.process` validates the request via `Utils::HmacValidator.validate(request)`, which only recomputes and compares the signature over `to_signable_string` (i.e., the raw body): [3](#0-2) 

Once the HMAC check passes, `Registry.process` immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` — all unauthenticated fields — and forwards them as the tenant identity to the host application's handler: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no independent verification, so whatever the attacker put in the `shop-domain` header flows straight into the handler: [5](#0-4) 

Because `api_secret_key` is shared across all shops that install a given app (it is not per-shop), an attacker who legitimately installs the app on their own store receives genuinely-signed webhook deliveries (valid `raw_body` + valid `hmac`). Since the signature never covers `shop-domain`/`topic`/`webhook_id`, the attacker can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while swapping the `shop-domain` header to a victim shop (or the `topic` header to a mandatory-sensitive topic). `HmacValidator.validate` still returns `true` because it only checks the body bytes, so `Registry.process` accepts the forged identity and dispatches it to the handler as if it originated from the victim shop.

This is exactly the "bytes verified versus bytes parsed" binding break: the equality that should hold is `hmac_covers(shop, topic, webhook_id, body) == fields_acted_on(shop, topic, webhook_id, body)`, but in this gem `hmac_covers(body) ⊊ fields_acted_on(shop, topic, webhook_id, body)`.

### Impact Explanation
This allows cross-tenant identity confusion: an attacker with a valid app installation on their own shop can forge webhook deliveries that the host application will process under a different (victim) shop's identity, because the shop that is cryptographically authenticated is not the shop that is acted upon. Depending on how the host app uses `WebhookMetadata.shop` (e.g., to select which tenant's session/data to mutate), this can lead to cross-tenant access to another merchant's data or state — meeting the Critical bar for cross-tenant access.

### Likelihood Explanation
Any developer/attacker who can install the target app on a shop they control (a normal, unprivileged action) automatically obtains genuinely-signed webhook payloads from Shopify. Replaying the body with a modified `shop-domain` (or `topic`/`webhook_id`) header requires no secret material and no privileged access — it only requires the ability to send an HTTP POST to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (all Shopify-controlled header values that the handler acts on) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a shop they fully control.
2. Shopify sends a legitimately HMAC-signed webhook to the app's endpoint, e.g. body `{"id":123}`, headers `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`.
3. Attacker captures this exact `raw_body` and `hmac` header value (nothing secret required — they legitimately received it).
4. Attacker replays the identical `raw_body`/`hmac` to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
5. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the signature over `to_signable_string` (raw body only) — it matches, so validation passes.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` builds `WebhookMetadata.new(shop: request.shop, ...)` using the attacker-supplied `victim-shop.myshopify.com`, and the host app's handler processes the forged webhook as if it came from the victim shop. [6](#0-5)
