### Title
`Webhooks::Request` HMAC signature excludes headers, letting an attacker relabel a self-signed webhook body to a victim shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Webhooks::Request#shop` returns the raw, unsigned `x-shopify-shop-domain` header value. `HmacValidator.validate` only checks the HMAC over the body, so an attacker who possesses one validly-signed `(body, hmac)` pair for their own shop can replay it directly to the app's webhook endpoint with the `shop-domain` header swapped to a victim's domain, and it will pass validation.

### Finding Description
The broken binding is: **bytes verified by `compute_signature` == bytes later trusted as the shop identity**. In practice:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) 
- `Request#shop` returns the raw `x-shopify-shop-domain` (or `shopify-shop-domain`) header, unauthenticated and outside the signed material [2](#0-1) 
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., HMAC over the body alone — and compares it to the received HMAC header, never touching the shop header [3](#0-2) 
- `Registry.process` passes `request.shop` straight into `WebhookMetadata`, handed to the host app's handler, without any further binding to the verified body [4](#0-3) 
- The gem's own documented usage pattern routes shop-scoped work keyed on `data.shop` taken straight from this unverified field: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) 

Attack flow: the attacker installs the app on their own development shop (unprivileged, self-service), triggers any webhook event they control (e.g., renaming one of their own products to an attacker-chosen string), and captures the resulting `(raw_body, x-shopify-hmac-sha256)` pair, which is validly signed by Shopify using the app's real `api_secret_key`. The attacker then POSTs directly to the app's webhook endpoint (bypassing Shopify's delivery entirely — nothing requires the request to originate from Shopify's IPs to reach this code path), reusing that exact body and HMAC, but substituting `x-shopify-shop-domain` with the victim merchant's domain. `HmacValidator.validate` recomputes the HMAC over the (unchanged) body and it matches, so the request is accepted. `Registry.process` then builds `WebhookMetadata` with `shop` set to the victim's domain but `body` set to the attacker's own, attacker-crafted content, and dispatches it to the host app's handler as if it were an authentic event for the victim.

No existing guard catches this: `ShopValidator`, `state` comparisons, and JWT `aud`/`iss` checks are part of the OAuth/session-token paths, not the webhook path; `Context.setup?`/`private?`/`embedded?` are unrelated; Sorbet signatures only constrain types, not header/body binding.

### Impact Explanation
An attacker can inject data they fully control (the body of their own legitimately-signed webhook) into the app's processing pipeline while it is misattributed to an arbitrary victim merchant's shop domain. Any host app that follows the gem's documented pattern of dispatching or persisting webhook data keyed by `data.shop` (as shown in the gem's own docs) will act on attacker-controlled content believing it belongs to the victim. This is repeatable against arbitrary victim shop domains (which are guessable/enumerable `*.myshopify.com` names or the app's own custom domains) at will, since the attacker only needs one self-signed webhook payload to replay indefinitely with different shop headers. This matches "Critical - cross-tenant access: one shop's request reads or mutates another merchant's data."

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: create a free development shop, install the target app, trigger one webhook, capture body+HMAC via their own server or network logs, then send a raw HTTP POST to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header. No secrets, no privileged access, and no interaction with the victim are required. The only host-app-side mitigation is if the app additionally cross-checks the shop against a locally stored, installed-shop allowlist/session before acting — but that is not part of this gem's contract and isn't reflected in its documented usage example.

### Recommendation
Bind the shop domain (and other Shopify headers used for routing/authorization) into the signed material, or have `HmacValidator`/`Registry.process` require the caller to supply a trusted shop context (e.g., a known/installed shop record) that the incoming `x-shopify-shop-domain` must match before it is treated as authoritative. At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically authenticated and must be cross-checked by the host app against its own installed-shops list prior to any state-mutating action.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_shop_domain_header_can_be_forged_without_invalidating_hmac
  body = '{"id":123}'
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
  encoded_hmac = Base64.encode64(hmac)

  # Attacker's own, validly-signed webhook for their own shop
  attacker_headers = {
    "x-shopify-topic" => "products/update",
    "x-shopify-hmac-sha256" => encoded_hmac,
    "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  }
  attacker_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: attacker_headers)
  assert(ShopifyAPI::Utils::HmacValidator.validate(attacker_request))

  # Same body+hmac, relabelled to a victim shop -- still validates
  forged_headers = attacker_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

  assert_equal(attacker_request.hmac, forged_request.hmac)
  assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))
  assert_equal("victim-shop.myshopify.com", forged_request.shop)
end
```
This demonstrates that `Request#hmac` and `HmacValidator.validate` are identical for two requests differing only in the (unsigned) `x-shopify-shop-domain` header, confirming the byte-identity invariant is broken and the shop label reaching `WebhookMetadata#shop` is attacker-controlled.
