### Title
`WouldBurn` strict-zero-balance check in `do_refund_other` can permanently block existence-deposit reclamation - (File: `substrate/frame/assets/src/functions.rs`)

### Summary
The external report describes a Solana program where closing a token account is blocked by a strict `amount == 0` check that a griefer can trigger by dusting the account with a tiny transfer. The equivalent accounting pattern — "refund/close is gated on an exact zero-balance check that any third party can falsify by sending funds to the target account" — exists in `pallet-assets`' deposit-refund logic in `substrate/frame/assets/src/functions.rs`.

### Finding Description
`do_refund_other` (called from the `refund_other` extrinsic, used by a depositor/admin/freezer to reclaim an existence deposit placed on behalf of another account) unconditionally requires the target account's asset balance to be zero: [1](#0-0) 

Unlike `do_refund` (self-service refund), which accepts an `allow_burn` flag letting the caller force-burn any dust balance to unblock the refund, `do_refund_other` has no burn-override path: [2](#0-1) 

Because `pallet-assets` transfers/mints are permissionless for holders of the asset (any account holding units of asset `id` can call `transfer` to send an arbitrary, even minimal, amount to the target account), an attacker who is not the depositor, not the admin, and not the freezer can grief the deposit-reclaim flow: transferring even 1 unit of the asset into the target account makes `account.balance.is_zero()` false, and `refund_other` will return `Error::WouldBurn` indefinitely, as confirmed by the existing test: [3](#0-2) 

### Impact Explanation
The depositor's reserved existence-deposit becomes permanently stuck as long as the griefer (or anyone) keeps the balance non-zero, since re-dusting after every honest burn attempt is trivial and cheap. This is a low-severity griefing/DoS on deposit reclamation, not a loss of principal or an accounting break — the admin can still forcibly `burn` the balance (a privileged Issuer-role action) to clear it before calling `refund_other`, so the block is not unconditional/irrecoverable, only inconvenient and requires privileged intervention.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) an account with a `DepositFrom` reason (created via `touch_other`) that someone wants to reclaim, and (b) the attacker holding any amount of the same asset to transfer into that account. Both preconditions are easily met by any user of a permissionless asset, making this trivially triggerable, but the impact is bounded because the asset's Issuer/admin can always resolve it via `burn` — this is a workflow inconvenience/griefing vector rather than an unrecoverable fund-locking bug, unlike the original Solana report where there was reportedly no sweep path at all before the fix.

### Recommendation
Add an `allow_burn`-style parameter (or equivalent forced-burn path) to `refund_other`/`do_refund_other`, mirroring the self-service `refund` extrinsic, so the depositor/admin can force-clear dust balances and reclaim the deposit without needing separate privileged `burn` calls.

### Proof of Concept
1. Admin/depositor `X` calls `Assets::touch_other(origin, asset_id, victim)` to create an asset account for `victim` and reserve a deposit.
2. Attacker `Y`, holding units of `asset_id`, calls `Assets::transfer(origin, asset_id, victim, 1)` (or any nonzero amount) — permissionless if `Y` owns any of that asset.
3. `X` calls `Assets::refund_other(origin, asset_id, victim)` → fails with `Error::<T>::WouldBurn` per `do_refund_other`'s `ensure!(account.balance.is_zero(), Error::<T, I>::WouldBurn)` check [4](#0-3) , and this is reproducible indefinitely as shown by the existing regression test [3](#0-2) .

	/// Returns a deposit or a consumer reference, destroying an asset-account.
	/// Non-zero balance accounts refunded and destroyed only if `allow_burn` is true.
	pub(super) fn do_refund(id: T::AssetId, who: T::AccountId, allow_burn: bool) -> DispatchResult {
		use AssetStatus::*;
		use ExistenceReason::*;

		let mut account = Account::<T, I>::get(&id, &who).ok_or(Error::<T, I>::NoDeposit)?;
		ensure!(matches!(account.reason, Consumer | DepositHeld(..)), Error::<T, I>::NoDeposit);
		let mut details = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(matches!(details.status, Live | Frozen), Error::<T, I>::IncorrectStatus);
		ensure!(account.balance.is_zero() || allow_burn, Error::<T, I>::WouldBurn);

	/// Refunds the `DepositFrom` of an account only if its balance is zero.
	///
	/// If the `maybe_check_caller` parameter is specified, it must match the account that provided
	/// the deposit or must be the admin of the asset.
	pub(super) fn do_refund_other(
		id: T::AssetId,
		who: &T::AccountId,
		maybe_check_caller: Option<T::AccountId>,
	) -> DispatchResult {
		let mut account = Account::<T, I>::get(&id, &who).ok_or(Error::<T, I>::NoDeposit)?;
		let (depositor, deposit) =
			account.reason.take_deposit_from().ok_or(Error::<T, I>::NoDeposit)?;
		let mut details = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
		ensure!(details.status == AssetStatus::Live, Error::<T, I>::AssetNotLive);
		ensure!(!account.status.is_frozen(), Error::<T, I>::Frozen);
		if let Some(caller) = maybe_check_caller {
			ensure!(caller == depositor || caller == details.admin, Error::<T, I>::NoPermission);
		}
		ensure!(account.balance.is_zero(), Error::<T, I>::WouldBurn);
