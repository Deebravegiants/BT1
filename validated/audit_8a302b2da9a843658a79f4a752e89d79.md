### Title
Webhook shop domain, topic, and webhook-id are not covered by the HMAC signature, allowing shop-domain spoofing in webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, `api_version`, and `webhook_id` from raw HTTP headers, but `Utils::HmacValidator` only verifies the HMAC over the request body. The header-derived `shop` value is trusted and forwarded to the app's webhook handler without being part of the signed data, breaking the binding `hmac == HMAC(secret, signed_data)` where `signed_data` should include the shop identity but doesn't.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes and compares the HMAC solely against that signable string [2](#0-1) . Meanwhile, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or the HMAC [3](#0-2) .

`Registry.process` validates only the body HMAC and then constructs `WebhookMetadata` using the unauthenticated `request.shop` header value, passing it straight to the app-registered handler [4](#0-3) .

Because `shop` (the tenant identity binding) is not part of `to_signable_string`, an unprivileged internet user who can obtain any single valid `(raw_body, hmac)` pair — trivially available since anyone can install a public app on their own store and receive a genuinely-signed webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `Utils::HmacValidator.validate` will still return `true` because it never inspects the shop header, and `Registry.process` will dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
If the host application's webhook handler uses `data.shop` (as documented/intended by this gem) to look up sessions, access tokens, or otherwise scope side effects per-tenant, an attacker can impersonate a different shop's webhook delivery, causing the handler to execute against or attribute data to a shop it does not control. This is a cross-tenant identity confusion rooted entirely in this gem's `Request`/`HmacValidator`/`Registry` code, since the signature never binds to the shop domain that the app subsequently trusts.

### Likelihood Explanation
Likelihood is bounded by the attacker's ability to obtain one legitimate `(body, hmac)` pair, which is easy: install the public app on an attacker-owned/free development store to trigger any webhook topic, capture the body and its valid `x-shopify-hmac-sha256`, then resend it to the app's webhook endpoint with a forged `shop-domain` header. No secret material is needed, matching the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string that `HmacValidator` verifies, or independently verify that the `shop` header corresponds to a shop the app actually has an active installation/session for before dispatching to handlers, rather than trusting the header value once body-HMAC passes.

### Proof of Concept
1. Install the target public Shopify app on an attacker-controlled shop (`attacker.myshopify.com`) and trigger any webhook topic that is registered.
2. Capture the resulting raw POST body and the `X-Shopify-Hmac-Sha256` header — both are legitimately signed by Shopify for `attacker.myshopify.com`.
3. Replay the exact same body and HMAC header to the same app endpoint, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC [5](#0-4)  and passes, then invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim.myshopify.com` [6](#0-5) , even though the request was never sent or signed by Shopify on behalf of the victim shop.
