### Title
Panic (Denial-of-Service) from unchecked `copy_from_slice`/subtraction on attacker-controlled `message.from` length in `hyper-fungible-token` calldata execution - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::<T>::on_accept` in the `hyper-fungible-token` ISMP module decodes an ABI-encoded `Message` from the ISMP `PostRequest.body` and, when the message carries optional calldata with no attached signature, derives the dispatch origin directly from the message's `from` field without validating its length before copying it into a fixed-size buffer. This mirrors the CVE-2020-19144 bug class (an unchecked-length buffer copy causing a crash), but here the crash is a Rust panic reachable from a permissionless, relayed cross-chain message.

### Finding Description
`on_accept` authenticates only the pair `(source, from)` — the ISMP request's source chain and source contract address — against `ContractToAsset` to establish that the *counterparty contract* is a registered token bridge for some asset: [1](#0-0) 

It then ABI-decodes an arbitrary `Message` struct from `body`, whose fields (including `message.from`) are fully attacker/counterparty-controlled data, not further length-checked at decode time (`Message::abi_decode` only enforces ABI shape, not semantic field length).

When `message.data` is non-empty and no signature is attached, the code derives the dispatch origin's `AccountId` from `message.from` with no bounds validation: [2](#0-1) 

Two panics are reachable here:
1. `source.is_evm()` branch: `&from_bytes[from_bytes.len() - 20..]` — if `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows a `usize`, panicking with "attempt to subtract with overflow" in debug builds (and producing an out-of-range slice index panic in release builds).
2. Non-EVM branch: `account.copy_from_slice(from_bytes)` into a fixed `[u8; 32]` — this panics unconditionally whenever `from_bytes.len() != 32`.

This is functionally the same bug class as the reported CVE: a length-unchecked buffer copy (`_TIFFmemcpy`/`copy_from_slice`) driven by attacker-supplied input causing an abort/DoS, rather than returning a graceful error as is done everywhere else in this same function (e.g. the `to_bytes` length handling a few lines above at lines 63-71, and the codebase's own hardening precedent in `modules/ismp/core/src/host.rs` and `modules/utils/serde/src/lib.rs`, which explicitly fix identical `copy_from_slice`-panic patterns elsewhere): [3](#0-2) [4](#0-3) 

### Impact Explanation
`on_accept` is the pallet-ismp module callback invoked while processing an incoming, relayer-submitted ISMP `PostRequest` (i.e., reachable from `pallet_ismp::Call::handle_unsigned`, an unsigned/permissionless extrinsic). A panic inside runtime message-dispatch execution is a WASM trap that aborts the extrinsic's execution context; depending on how `handle_unsigned`/executive wraps module dispatch, this can disrupt block execution for the whole batch of ISMP messages being processed and is a reliable, repeatable node-level denial of service against the token-bridge message-delivery path. This satisfies the "route unable to deliver messages" / DoS-of-funds-delivery bar for a Medium-severity analog.

### Likelihood Explanation
High. The vulnerable path requires only: (1) a source chain/contract pair already registered in `ContractToAsset` (a normal, expected bridge configuration, not an attacker precondition), (2) a `Message.data` field that is non-empty, and (3) no `signature` set (or a signature whose `Option` is `None`). All three are attacker-controlled ABI-encoded fields inside the ISMP request body that any relayer can submit once a legitimate token bridge integration exists — no admin/governance compromise or privileged role is needed.

### Recommendation
Validate `from_bytes.len()` before use, mirroring the existing `to_bytes` handling pattern in the same function: accept exactly 20 bytes (EVM) or 32 bytes (non-EVM) and return `HftError` variants (e.g. a new `InvalidFromLength`) otherwise, instead of slicing/`copy_from_slice`-ing unchecked lengths.

### Proof of Concept
1. Register a bridge contract pair `(source_chain, contract_addr)` in `ContractToAsset` (standard setup for any hyper-fungible-token deployment).
2. Craft an ISMP `PostRequest` from `source_chain`/`contract_addr` whose ABI-encoded body decodes to a `Message` with: `data` non-empty (any non-empty bytes to enter the calldata branch), `signature = None`, and `from` set to a byte string that is neither exactly 20 bytes (if `source.is_evm()`) nor exactly 32 bytes (if not) — e.g. `from = vec![0u8; 5]`.
3. Submit this via `pallet_ismp::Call::handle_unsigned` (relayer-submitted proof/message) to the runtime.
4. `Pallet::on_accept` reaches the branch at `module.rs:176-187`; for `source.is_evm()` with `from.len() < 20` the subtraction underflows and panics; for the non-EVM branch with `from.len() != 32` the `copy_from_slice` panics — crashing execution of that message/extrinsic.
