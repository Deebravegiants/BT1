### Title
Webhook shop-domain identity spoofing via HMAC that only covers the raw body, not the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` in `Registry.process` verifies solely that the body bytes match the app's shared secret. The `shop` attribute, sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header, is passed unverified into `WebhookMetadata` and handed to the host app's `WebhookHandler#handle`. Because every shop installed on an app shares the same app-level `client_secret` for HMAC signing, a webhook payload/HMAC pair that is genuinely valid for one tenant (e.g., an attacker's own shop) remains a valid HMAC when replayed with the `shop-domain` header swapped to a victim shop's domain — the equality the gem should enforce (`hmac-authenticated shop == data.shop delivered to handler`) is never checked.

### Finding Description
`Request#hmac` decodes the `hmac-sha256` header and `Request#to_signable_string` returns only the raw JSON body: [6](#0-5) [2](#0-1) 

`Registry.process` validates only that HMAC: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the digest exclusively over `verifiable_query.to_signable_string` (the body), with no mixing-in of `shop`, `topic`, or `webhook_id`: [7](#0-6) 

`request.shop` is read straight from an attacker-controlled header with no cryptographic binding: [8](#0-7) 

and is forwarded verbatim into the struct passed to the host app's handler: [5](#0-4) 

Since Shopify computes the webhook HMAC using the app's single `client_secret` (not a per-shop secret), a body+HMAC pair captured from a legitimate delivery to any shop that has installed the app (including a shop the attacker themselves controls) remains a cryptographically valid pair regardless of which shop it is claimed to be for. An attacker can therefore POST that same body and HMAC to the app's webhook endpoint while setting the `shop-domain` header to an arbitrary victim shop domain; `Utils::HmacValidator.validate` will accept it because it never inspects `shop`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim tenant.

### Impact Explanation
This breaks the tenant-identity binding the whole webhook subsystem exists to provide: the shop that the HMAC actually authenticates versus the shop attributed to the event and delivered to the host app's handler. Any host app that uses `data.shop` from `WebhookHandler#handle` to select a session/access token, update per-shop state, or make trust decisions (this is the documented intended use of `WebhookMetadata#shop`) can be made to act on/against an arbitrary victim shop using attacker-supplied (self-consistent) body content, which is cross-tenant confused-deputy behavior.

### Likelihood Explanation
Requires only unauthenticated network access to the app's public webhook endpoint plus a legitimately-signed body/HMAC pair, which an attacker obtains trivially by installing the target app on their own shop (a normal, unprivileged action) and capturing one of the webhooks Shopify sends them. No access to the app's `client_secret`, access tokens, or any victim credentials is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified — e.g., have `Request#to_signable_string` incorporate the shop-domain header, or have `Registry.process` cross-check the header-derived `shop` against an independently-established value (such as the session looked up via `webhook_id`/topic against Shopify's API) before constructing `WebhookMetadata`, rather than trusting the raw header outright.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a genuine webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(client_secret, B)`), along with `x-shopify-topic` and `x-shopify-webhook-id`.
2. Replay a request to the app's webhook endpoint with the same body `B` and same `H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and matches `H` — validation succeeds since `shop` is not part of the signed material (`lib/shopify_api/webhooks/registry.rb:188-199`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The app's `WebhookHandler#handle` is invoked with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process an attacker-crafted body as if it were legitimately sent by the victim shop.
