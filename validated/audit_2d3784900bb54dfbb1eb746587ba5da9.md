### Title
Undeliverable Cross-Chain Message When Wrapped Token's Underlying ERC20 Reverts on Blacklisted Recipient - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.onAccept` credits an incoming cross-chain transfer by calling `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` directly to the decoded recipient address, with no fallback path if that transfer reverts. Because the wrapped `_underlying` token can be an arbitrary ERC20 (the docs explicitly describe wrapping stablecoins like USDC/USDT/WETH), and such tokens can implement issuer-side blacklists, a message whose recipient is blacklisted on the underlying token (but was not blacklisted, or became blacklisted after dispatch, and is not checked at all on the source chain) makes `onAccept` permanently revert for that specific commitment.

### Finding Description
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 on the source chain and dispatches an ISMP `PostRequest` encoding the beneficiary as raw bytes, with no knowledge of or check against the underlying token's blacklist state on the destination chain: [1](#0-0) 

On the destination chain, `onAccept` decodes the recipient and unconditionally attempts `IERC20(_underlying).safeTransfer(beneficiary, message.amount)` (or the WETH push/re-wrap path for the WETH case), with no blacklist-aware fallback such as redirecting to the contract owner: [2](#0-1) 

If `_underlying` is a token with issuer-controlled blacklisting (e.g. USDC, USDT), and the beneficiary address is blacklisted on the destination chain's underlying token, `safeTransfer` reverts. Because `onAccept` performs the ERC20 transfer and the message accounting atomically, and there is no `try/catch` or redirect-to-owner logic (unlike the pattern recommended in the referenced audit, which credits the owner instead of reverting), the entire `onAccept` call reverts. This is the exact bug class from the external report: blacklist state is not synchronized/checked at dispatch time on the source chain, and the destination-side credit path has no graceful degradation, so the relayer's delivery attempt for that specific commitment fails deterministically and repeatedly.

`WrappedHyperFungibleTokenUpgradeable.sol` contains the identical pattern: [3](#0-2) 

### Impact Explanation
Every relayer that attempts to deliver this specific POST request will have `onAccept` revert, since the underlying blacklist check happens deterministically inside `safeTransfer` regardless of who calls it. The request becomes an undeliverable message for its entire timeout window — the intended recipient can never receive the funds, matching the "route unable to deliver messages" impact category. Recovery only occurs via the timeout/refund path, which returns funds to the original sender rather than the intended recipient, meaning the cross-chain transfer's business intent (crediting the beneficiary) permanently fails for that message even though total funds are eventually not lost.

### Likelihood Explanation
This requires the token wrapped by a specific `WrappedHyperFungibleToken` deployment to be one with issuer-controlled blacklisting (USDC/USDT-class tokens), which the contract and its documentation explicitly support wrapping. Any deployment operator choosing to wrap such a token, combined with any recipient address that is (or becomes) blacklisted on the underlying asset — a state entirely outside this bridge contract's control or awareness — triggers the condition. No special privileges are needed to trigger it: normal `send()` usage targeting (or being targeted at) a blacklisted destination address is sufficient.

### Recommendation
In `WrappedHyperFungibleToken.onAccept` (and the upgradeable variant), wrap the `safeTransfer` to the beneficiary in a low-level call / try-catch, and on failure redirect the underlying tokens to the contract `owner()` (or another designated recovery address) instead of allowing the whole `onAccept` to revert, mirroring the mitigation from the referenced audit (crediting the owner rather than reverting when the recipient cannot receive funds). Emit an event (e.g. `RedistributeFunds`) so downstream systems can detect and handle stuck deliveries without leaving the message permanently undeliverable.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain B wrapping `_underlying = USDC` (or any blacklist-capable ERC20).
2. On chain A, a user calls `send()` targeting a recipient address `R` on chain B; at dispatch time `R` is not blacklisted on USDC (source chain has no knowledge of the destination token's blacklist).
3. Before the message is relayed, USDC's issuer blacklists `R` on chain B (or `R` was already blacklisted and the sender didn't know/check).
4. Any relayer submits the proof and calls `EvmHost` → `onAccept`; `IERC20(_underlying).safeTransfer(R, amount)` reverts because USDC's `transfer` enforces the blacklist.
5. `onAccept` reverts entirely; every subsequent relayer attempt to deliver the same commitment fails identically until the request times out, at which point funds are refunded to the original sender on chain A instead of ever reaching `R`. [4](#0-3)

    /**
     * @notice Handles incoming cross-chain token transfer messages
     * @dev Called by the ISMP host when a POST request is received. Verifies the source
     * address matches the configured contract for that chain, then transfers the underlying
     * ERC20 to the recipient. If calldata is present, executes it via the CallDispatcher.
     * @param incoming The incoming POST request containing the token transfer message
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
