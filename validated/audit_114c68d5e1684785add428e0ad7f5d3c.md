Based on my analysis, this is a valid, real vulnerability.

### Title
`feeStructure.feeToken` unbound by owner's EIP-712 signature allows fee debit in an unintended token - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
The owner's off-chain authorization (`EMPORIUM_SIGNATURE_TYPEHASH`) signs only `emporiumMessage`, `ops`, `maxFee`, and `deadline` — never `feeStructure.feeToken`. `verifyWallet` only checks `feeStructure.flatFee > stack.maxFee` numerically, with no binding to which ERC-20 token the fee is denominated in, so whoever calls `runAction` can freely choose `feeStructure.feeToken` and have `payRelayFees` → `sendToRelayFromWallet` → `IHinkalWallet.doSendToRelay` pull `flatFee` of an arbitrary, attacker-chosen token directly from the victim's `HinkalWallet`.

### Finding Description
The claimed broken equality is: `feeToken implicitly authorized by signer` == `feeToken actually debited by payRelayFees`.

- The signature hash is computed in `verifyWallet`: [1](#0-0) , using `EMPORIUM_SIGNATURE_TYPEHASH` which is defined as `keccak256("EmporiumSignature(uint256 message,EmporiumOperation[] ops,uint256 maxFee,uint256 deadline)...")` [2](#0-1)  — no `feeToken` field.
- The only fee-related check after signature verification is purely numeric: `if (circomData.feeStructure.flatFee > stack.maxFee) revert FeeExceedsSignedMax();` [3](#0-2) . `maxFee` is a raw `uint256` carried in the signed `EmporiumStack`, with no token context at all [4](#0-3) .
- `feeStructure` (including `feeToken`) is only bound into `getHashedCalldata2`, i.e. `circomData.calldataHash` [5](#0-4) , which is a public signal checked by the ZK proof verifier — a completely separate authorization channel from the owner's EIP-712 signature over `EmporiumStack`.
- `payRelayFees` uses `feeStructure.feeToken` to decide which token to debit and calls `sendToRelayFromWallet(relay, signerAddress, flatFee, feeToken)` when `signerAddress != address(0)` [6](#0-5) , which forwards straight to `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` [7](#0-6) .
- `HinkalWallet.doSendToRelay` performs no token-specific validation; it is gated only by `onlyEmporium` and blindly transfers whatever ERC-20 `erc20TokenAddress` and amount it's told: [8](#0-7) .

Root cause: the EIP-712 signature that authorizes a signer-based Emporium action authenticates *that the signer approved these `ops`/`maxFee`/`deadline`*, but the actual fee-token selection is supplied out-of-band via `circomData.feeStructure`, which is bound only to the ZK-proof's public input (`calldataHash`), not to the signature the wallet owner actually produced. Whoever constructs the `circomData` passed into `runAction` (the entity submitting the transaction — which per the `onlyAllowedRecipient` external-action dispatch model is the caller through `Hinkal.transact`, not necessarily the wallet owner) can set any `feeToken` while keeping `flatFee <= stack.maxFee`, and the numeric-only check will pass.

Existing guards do not prevent this: `verifyWallet`'s ECDSA check only proves the signer approved `ops`, `maxFee`, `deadline`, not `feeToken`; the ZK proof binds `feeStructure` to `calldataHash`, but that only proves the *prover* (who could be the attacker/submitter, not the signer) chose that value consistently with their own proof generation — it does not prove the *signer* authorized that specific `feeToken`. The two authorization mechanisms (EIP-712 signature and ZK-proof calldata hash) are disjoint over the `feeToken` field, so no on-chain check ever verifies "signer approved fee in *this* token."

### Impact Explanation
An attacker who can submit the `runAction`-triggering transaction (e.g., a relay or any party in possession of the victim's already-signed `EmporiumStack` bytes obtained off-chain, as stated in the preconditions) can redirect `doSendToRelay` to debit a high-value token from the victim's `HinkalWallet` instead of the low-value stablecoin the victim intended, up to `flatFee` (bounded only by `maxFee`, a token-less numeric cap). This is theft of user (wallet-holder) funds executed via a fee mechanism the signer never priced/authorized for that token — categorized as Critical (direct theft of user funds) per the rubric, since it moves value out of a `HinkalWallet` in a token dimension the signature never constrained. It is repeatable each time a signed `EmporiumStack` blob is reused or intercepted, up to `maxFee` per submission (and unlimited across different signed messages if the attacker can obtain multiple).

### Likelihood Explanation
Preconditions per the question are somewhat strong: the attacker must already be able to submit the `runAction` call carrying attacker-chosen `circomData` for a victim's pre-signed `EmporiumStack` — meaning they control transaction construction/relaying for that action (the same relay-adjacent role that legitimately calls `Hinkal.transact`/`runAction`). Given that role, the attack is trivial and cheap: just set `feeStructure.feeToken` to the expensive token and keep `flatFee` numerically ≤ `maxFee`. The wallet must hold the higher-value token for the attack to have outsized impact, but `doSendToRelay` will attempt the transfer for any ERC-20 balance present regardless.

### Recommendation
Include `feeStructure.feeToken` (and ideally the full `feeStructure`) inside the `EMPORIUM_SIGNATURE_TYPEHASH` digest that the wallet owner signs, so `verifyWallet`'s ECDSA recovery cryptographically binds the exact fee token and amount the signer approved, not just a token-agnostic numeric cap. Alternatively, hardcode/whitelist a single fee token per `EmporiumStack` signature and reject any `feeStructure.feeToken` that doesn't match the signed value.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable` (or its test harness), a `HinkalWallet` owned by `signerAddress` = victim, and two ERC-20 tokens: `CHEAP` and `EXPENSIVE`. Fund the victim's `HinkalWallet` with both.
2. Victim signs an `EmporiumStack{ops: [], maxFee: X, deadline: future}` via EIP-712 using `EMPORIUM_SIGNATURE_TYPEHASH`, intending fee payment in `CHEAP` (never encoded in the signature).
3. Attacker (as `msg.sender`/relay submitter) builds `circomData` with `feeStructure = {feeToken: EXPENSIVE, flatFee: X, variableRate: 0}` and `circomData.externalActionData.externalActionMetadata = abi.encode(stack)` using the victim's valid `v,r,s`.
4. Call `runAction(circomData, deltaAmountChanges)` (bypassing/mocking `onlyAllowedRecipient` and proof verification for the test, or supplying a locally generated valid proof matching `calldataHash`).
5. Assert: `verifyWallet` does not revert (signature verifies, `flatFee <= maxFee`), and after execution the victim's `HinkalWallet` `EXPENSIVE` token balance decreased by `X` while `CHEAP` balance is unchanged — i.e., assert `feeTokenSigned (undefined/CHEAP) != feeTokenDebited (EXPENSIVE)` and that value was extracted in a token dimension outside the signer's authorization.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
