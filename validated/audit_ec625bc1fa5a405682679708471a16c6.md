### Title
`IntentGatewayV2.select()` is permissionless and writes to a `commitment`-keyed transient slot with no caller binding, letting any bundled UserOp grief a legitimate solver's `fillOrder()` into reverting with `Unauthorized` - (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.select()` and its implementation `IntentsBase._select()` are fully public/unauthenticated. They unconditionally `tstore` a selection hash at a slot keyed only by `order` `commitment` — a value that is public (derivable from any placed order or its `OrderPlaced` event) — regardless of whether the supplied signature actually corresponds to that order's session key. `fillOrder()` later `tload`s the same slot and reverts with `Unauthorized()` if it doesn't match `keccak256(msg.sender, order.session)`. Anyone who gets a call to `select()` with the victim's `commitment` executed in the same transaction as the legitimate solver's fill (which happens naturally via ERC-4337 bundling of independent UserOperations into one `handleOps` transaction) can overwrite that slot and cause the real solver's `fillOrder()` to revert.

### Finding Description
`select()` has no access control: [1](#0-0) 

Its implementation recovers whatever address a supplied (possibly garbage) signature yields and stores the resulting hash keyed solely by `commitment`, with no check that the recovered `sessionKey` is legitimate or that `msg.sender`/`options.solver` is authorized in any way: [2](#0-1) 

`fillOrder()` later relies on that same slot for its authorization decision when `solverSelection` is enabled: [3](#0-2) 

Because the slot is scoped only to `commitment` — not to the caller, not to a nonce that's consumed once and only once by the intended party — any third party who supplies a syntactically valid ECDSA signature (trivial: any well-formed `(v, r, s)` with `s` below the curve-order half and `v` in `{27,28}` recovers to *some* address without reverting) can call `select(commitment, anyAddress, garbageSig)` and overwrite the transient slot for that commitment. If this call lands anywhere in the same top-level transaction after the legitimate solver's `select()` call but before the legitimate `fillOrder()` executes, the real solver's authorization check fails.

This is exactly the same bug class as the reported `CrabNetting.checkOrder` issue: an unrestricted, "just checks/records something" external function shares mutable state with a privileged flow that depends on that state not having been tampered with, and a third party can invalidate/corrupt it before the legitimate call runs, forcing a revert. The key structural difference is that Hyperbridge's shared state is EIP-1153 transient storage rather than persistent storage, so the interference must occur within the same transaction rather than merely the same block — but ERC-4337 makes this realistic: solver bids for `solverSelection`-enabled orders are executed as UserOperations, and bundlers routinely batch multiple independent parties' UserOperations from the public mempool into a single `EntryPoint.handleOps` transaction for gas efficiency. All UserOp validations run in one loop before any execution runs in a second loop (per the documented flow, the `SolverAccount.validateUserOp` calls `select()` during validation), so an attacker's own low-cost UserOp — which does nothing more than call `select()` with the target `commitment` — can be bundled alongside the victim's fill UserOp and clobber the transient slot before the victim's `fillOrder()` executes.

### Impact Explanation
A successful griefing call causes the legitimate, selected solver's `fillOrder()` to revert with `Unauthorized()`:
- The solver's gas for the fill is wasted (and, per the SDK docs, the bid's ERC-4337 nonce is consumed on this path too, since the attack window is the same window the docs already flag for a related griefing vector), and the order goes unfilled through that solver.
- If this can be repeated across the order's remaining validity window, the order's `deadline` can pass without being filled, at which point the user (or, after the deadline, anyone) must cancel it and go through source/destination cancellation and refund flow instead of a normal fill — a denial-of-service against the intents fill mechanism whenever `solverSelection` is enabled, directly harming the order's economics (missed fills, wasted solver gas, delayed user settlement).
- This does not itself steal funds, but it is a concrete "route unable to deliver" style failure for the intents fill path, which is one of the explicitly in-scope categories (intents escrow and bids).

### Likelihood Explanation
`solverSelection` is an explicit, supported deployment mode (`Params.solverSelection`), and its whole raison d'être — public bidding via a public bundler mempool with an EIP-712 session signature — is exactly the setting where a malicious bundler-visible actor (a rival solver with an incentive to see a competitor's fill fail) can construct a trivial UserOp calling `select()` with an arbitrary signature and the victim's public `commitment`, and have a realistic chance of it being bundled together with the victim's fill UserOp by a bundler optimizing for batch gas efficiency. No secret data, no cryptographic break, and no privileged role is required — only a syntactically valid but otherwise garbage signature and knowledge of the public `commitment`.

### Recommendation
Bind the transient-storage write to the caller (and/or require that the recovered `sessionKey` matches `order.session` at `select()` time, which requires passing `order.session` into `select()`), so an unrelated party's call cannot clobber another commitment's selection slot. At minimum, key the transient slot by `keccak256(abi.encode(commitment, msg.sender))` so only the actual solver executing `fillOrder()` (which passes `msg.sender` at that time) can write the entry it will itself later validate, or have `select()` validate the recovered `sessionKey` against `order.session` before writing, reverting on mismatch instead of silently storing a bogus hash that a legitimate solver check will later compare against.

### Proof of Concept
1. A user places a `solverSelection`-enabled order; its `commitment = keccak256(abi.encode(order))` is public (emitted in `OrderPlaced`).
2. Solver S is selected via a signed EIP-712 `SolverSelection`; S submits a UserOperation whose validation calls `IntentGatewayV2.select(commitment, S, sessionSig)` and whose execution calls `fillOrder(order, options)`.
3. Attacker A submits a second, independent UserOperation to the same public bundler mempool whose execution simply calls `IntentGatewayV2.select(commitment, A, garbageSig)` with a syntactically valid but meaningless 65-byte signature.
4. A bundler batches both UserOperations into one `EntryPoint.handleOps` transaction, with A's op ordered after S's `select()` validation/execution but before S's `fillOrder()` executes.
5. `tstore(commitment, keccak256(abi.encode(A, recoveredGarbageAddress)))` overwrites the value S's flow expects.
6. S's `fillOrder()` executes, `tload(commitment)` returns A's overwritten value, `expectedSelectionHash = keccak256(abi.encode(S, order.session))` does not match, and the call reverts with `Unauthorized()` — griefing S and leaving the order unfilled by its rightful, selected solver.

```text
    function _select(SelectOptions calldata options) internal returns (address) {
        bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
        bytes32 digest = _hashTypedDataV4(structHash);
        address sessionKey = ECDSA.recover(digest, options.signature);

        bytes32 commitment = options.commitment;
        bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
        assembly {
            tstore(commitment, selectionHash)
        }

        return sessionKey;
    }
```
