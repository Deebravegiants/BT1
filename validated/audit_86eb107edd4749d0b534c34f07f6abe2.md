### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook shop-domain spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by verifying the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values pulled from unsigned HTTP headers to build the `WebhookMetadata` handed to the app's handler. None of these header fields are covered by the HMAC, so the cryptographic check that "authenticates" the webhook does not bind the `shop` identity to the verified content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [1](#0-0) 

while `shop` (and `topic`, `webhook_id`, `api_version`) are read directly from HTTP headers with no cryptographic tie to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature over `to_signable_string` (the body only) and compares it against the supplied `hmac`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authenticating the *entire* request, then forwards the unverified `request.shop` header straight into `WebhookMetadata`, which is the value host apps use to identify which merchant/tenant the webhook belongs to: [4](#0-3) 

The equality this breaks is: **shop bound by the HMAC == shop acted upon by the handler**. In reality, `HmacValidator.validate(request) == true` only proves "this body byte-string was signed with the app's secret at some point" — it proves nothing about which shop header accompanied that signature. Since Shopify apps share one `client_secret` across every merchant installation, any legitimately signed webhook (from any shop that installed the app) can have its `x-shopify-shop-domain` header swapped for an arbitrary target shop domain, and `Registry.process` will still accept it and hand the (forged) `shop` value to the handler as if it were authenticated.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability. An unprivileged actor who can install the target app on their own (attacker-controlled) shop can trigger genuine, correctly-HMAC'd webhooks for that shop (e.g. `orders/create`), capture the raw body + HMAC pair, then replay that exact body/HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header. `Registry.process` will validate the HMAC successfully (the body wasn't altered) and invoke the handler with `WebhookMetadata#shop` set to the victim's domain. Any host application logic that looks up per-shop sessions/access tokens, updates per-shop records, or makes trust decisions keyed off `data.shop` will act on attacker-supplied data under the wrong tenant's identity — a cross-tenant data injection/confusion condition.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that: (a) is installable by arbitrary merchants (the normal Shopify app model), and (b) uses the `shop` field from `WebhookMetadata` to key privileged operations (as the gem's own documentation encourages, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). No secret material beyond the ability to install the app on one's own store is required, since the app's `client_secret` is shared across all shops that install the app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed/verifiable content the gem checks, or at minimum cross-verify the `x-shopify-shop-domain` header against a known/registered shop (e.g. the currently active session's shop) before constructing `WebhookMetadata`. At the very least, the gem should document explicitly that `WebhookMetadata#shop` is not cryptographically authenticated and must be independently validated by the host application against its own shop/session records before being trusted.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. create an order) so Shopify sends a legitimately signed `orders/create` webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed by Shopify over `B` using the app's shared `client_secret`).
2. Capture `B` and `H`.
3. Replay a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(..., B)` against `H` — this still passes: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, i.e., attacker-controlled data falsely attributed to the victim shop.
