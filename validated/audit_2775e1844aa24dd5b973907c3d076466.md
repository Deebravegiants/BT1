### Title
Compulsory accrual can overflow RAY debt value and permanently freeze a market - (File: common/src/rates/index.rs)

### Summary

A whale-scale borrower can leave a high-decimal market at sustained high utilization until `borrowed * borrow_index` exceeds `i128::MAX`, after which every operation that touches the market reverts during mandatory interest accrual. Because repayment, withdrawal, liquidation, bad-debt cleanup, recapitalization, and `update_indexes` all synchronize the same market first, the market has no unprivileged recovery path and supplier funds remain frozen. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

Each pool leg calls `ops::load_leg`, which loads the market and runs `interest::global_sync` before validating or applying the requested action. [1](#0-0)  `global_sync` invokes `accrue_step` for every elapsed chunk, and `accrue_step` first computes `scaled_to_original(borrowed, borrow_index)` to derive utilization. [4](#0-3) [5](#0-4)  `scaled_to_original` is a checked `Ray` multiplication, so a scaled-debt balance whose current value no longer fits `i128` panics with `MathOverflow`. [6](#0-5) [7](#0-6) [8](#0-7) 

Even if the old debt value still fits, `calculate_supplier_rewards` computes `borrowed * new_borrow_index` and subtracts `borrowed * old_borrow_index`, so the next index update itself can overflow before any mutation-specific guard runs. [3](#0-2)  The index ceiling does not prevent this condition because it is applied after `update_borrow_index` computes a new index, not by capping the economically representable `borrowed * index` product. [9](#0-8) 

The in-repository scenario seeds one billion whole 18-decimal tokens, borrows 98% of the market, advances accrual, and observes `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow` while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [10](#0-9) 

### Impact Explanation

Once the debt-value product crosses the `i128` range, every pool mutation for that market aborts before reaching its operation-specific logic because `load_leg` or `synced_market` executes accrual first. [1](#0-0)  Consequently, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize the debt market, `clean_bad_debt` cannot socialize it, `recapitalize` cannot measure or repair a shortfall, and `update_indexes` cannot advance the market timestamp. [11](#0-10) [12](#0-11) [13](#0-12) [14](#0-13) 

This is permanent freezing of user funds rather than a bounded temporary halt: reverting accrual does not persist a new `last_timestamp`, so subsequent calls repeat the same overflowing calculation. [2](#0-1) [15](#0-14) 

### Likelihood Explanation

The attacker must create or use a very large high-decimal market, supply enough target liquidity, post enough collateral in another listed asset, and borrow enough target assets to keep utilization high while interest compounds. A single unprivileged owner can perform this through two owned controller accounts: `supply` can create a normal account and deposit the target asset, while a second account can supply collateral and call `borrow` against it. [16](#0-15) [17](#0-16) 

No oracle manipulation, leaked key, privileged call, token misbehavior, or invalid parameter is required beyond governance having admitted caps and rate parameters that permit the relevant scale. Feasibility is therefore market-configuration- and liquidity-dependent, but the arithmetic condition is reachable through admitted user positions rather than storage corruption. [18](#0-17) 

### Recommendation

Bound market exposure in representable-value terms, not only in token-unit caps and index limits. In particular, enforce `supplied * MAX_SUPPLY_INDEX_RAY` and `borrowed * MAX_BORROW_INDEX_RAY` headroom during entry, or compute a per-market representability ceiling and cap index growth before `borrowed.mul(new_borrow_index)` and `supplied.mul(new_supply_index)` can overflow. [19](#0-18) [3](#0-2) 

Also provide an emergency accounting path that can reduce debt or supply shares without first evaluating the overflowing aggregate value, so repayment, withdrawal, seizure, or recapitalization can recover a market at the numeric boundary. [1](#0-0) 

### Proof of Concept

1. In a listed 18-decimal market, the attacker supplies approximately `1_000_000_000 * 10^18` base units through `supply`, creating the target liquidity position. [16](#0-15) [20](#0-19) 
2. Through another owned account, the attacker supplies sufficient collateral and calls `borrow` for approximately 98% of the target market, subject to the configured utilization and liquidation-buffer checks. [17](#0-16) [21](#0-20) 
3. Interest accrues until `scaled_to_original(borrowed, borrow_index)` or `borrowed.mul(new_borrow_index)` no longer fits `i128`. [22](#0-21) [3](#0-2) 
4. `update_indexes`, `repay`, and `withdraw` all revert with `MathOverflow`, because each call synchronizes the market before executing its repayment or withdrawal logic. [23](#0-22) [24](#0-23) [11](#0-10) 
5. The repository’s long-horizon test reproduces this state and confirms that both repayment and withdrawal remain unavailable after the first overflow. [25](#0-24)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
