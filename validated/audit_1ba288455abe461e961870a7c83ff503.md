### Title
Webhook `shop-domain` header is not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates nothing but the byte content of the body. The `shop-domain` header, which `Registry.process` uses as the tenant identity passed to the app's `WebhookHandler`, is never bound to that signature.

### Finding Description
`Registry.process` treats a request as an authentic Shopify webhook if `Utils::HmacValidator.validate(request)` succeeds: [1](#0-0) [2](#0-1) 

That validation only checks the HMAC against `to_signable_string`, which is defined as the raw body alone: [3](#0-2) 

`request.shop` (used as the tenant key handed to the app) is read from the `X-Shopify-Shop-Domain` / `Shopify-Shop-Domain` header, which is not part of the signed message at all: [4](#0-3) 

`Utils::HmacValidator.validate_signature` performs a constant-time comparison, but it is only comparing against the body bytes: [5](#0-4) 

Finally, the handler is invoked using `request.shop` as the authoritative tenant identity, together with the (HMAC-verified) body: [6](#0-5) 

**Identity binding broken:** the equality `shop_bound_by_HMAC == shop_used_as_tenant_key` does not hold. The HMAC binds only `raw_body`; `shop` (and `topic`, `webhook_id`) are unauthenticated header values that the caller can freely change while keeping a valid signature, because the signature was computed by Shopify over a *different* legitimate delivery (any shop the attacker controls) and never covered the header block.

### Impact Explanation
Any unprivileged internet user can install the app on their own store (or otherwise trigger a legitimate webhook to their own store, e.g. `app/uninstalled`, `customers/data_request`, `shop/redact`). Shopify will deliver that webhook to the app's endpoint with a body and a valid `hmac-sha256` signature over that body. The attacker can then resend the exact same body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop's domain. Because `to_signable_string` never includes the header, the HMAC check still passes, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's shop while `body` is attacker-controlled. Depending on how the host application keys its per-tenant state off `WebhookMetadata.shop` (e.g., revoking access tokens on `app/uninstalled`, deleting merchant data on `shop/redact`, or fulfilling `customers/data_request`), this allows cross-tenant state corruption without any credential belonging to the victim — this qualifies as Critical (cross-tenant access) per the impact rubric.

### Likelihood Explanation
High. Exploitation requires only a free Shopify store/app-install (no admin access token, no `api_secret_key`, no TLS interception) plus the ability to send an arbitrary HTTP POST with attacker-chosen headers to the app's public webhook endpoint — an operation entirely within reach of an unprivileged internet user.

### Recommendation
Bind the tenant/topic identity into the signed message, or otherwise independently authenticate it:
- Include `shop-domain`, `topic`, and `webhook-id` in the value passed to `to_signable_string` if Shopify's signing scheme supports it, or
- If Shopify's HMAC genuinely only covers the raw body (per Shopify's documented webhook verification), require the consuming application to cross-check the `shop-domain` header against a shop that is actually known/registered by the app (e.g. has an active session) before trusting `WebhookMetadata.shop`, and document this requirement prominently, since `Registry.process` currently offers no such safeguard and implicitly treats the header as trusted once the raw-body HMAC passes.
- At minimum, make it explicit in `Registry.process`/`WebhookMetadata` that the `shop` field is unauthenticated and must be corroborated independently by the caller before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com` and triggers a webhook that the app subscribes to (e.g. `app/uninstalled`), or captures any legitimate webhook delivery to their own endpoint.
2. Shopify POSTs to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`, and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the identical request to the same endpoint, keeping `B` and `H` unchanged but replacing the header value with `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H`, as shown in [3](#0-2) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to act on victim's tenant using attacker-supplied data.
