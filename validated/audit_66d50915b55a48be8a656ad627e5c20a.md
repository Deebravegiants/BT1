## Analysis

The Curve report's root cause is that an oracle blindly trusts a manipulable, unvalidated ratio (`get_virtual_price()`) and uses it directly to scale a returned price, with no sanity bound on the value or its rate of change. The reachable analog in this codebase is in `process_deposit` in `program/src/processor.rs`.

`Processor::process_deposit` computes the pool's live reserves straight from the SPL vault token accounts with no bound-checking or TWAP smoothing: [1](#0-0) 

Those two `u64` values (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) are then used as the sole denominator for computing how many LP tokens a depositor receives: [2](#0-1) [3](#0-2) 

Critically, `DepositInstruction` exposes only `max_coin_amount`, `max_pc_amount`, `base_side`, and `other_amount_min` — there is **no `min_lp_amount_out`** field: [4](#0-3) 

`other_amount_min` only bounds the *deducted* amount of the non-base token, never the number of LP tokens minted (`mint_lp_amount` is unconditionally accepted as long as it isn't exactly `0`): [5](#0-4) 

Because the vault balances (`amm_coin_vault.amount` / `amm_pc_vault.amount`) are ordinary SPL token accounts, any unprivileged actor can inflate one side by directly transferring extra tokens into the vault address (a plain SPL `Transfer`, entirely outside the AMM program) immediately before a victim's `Deposit` transaction lands in the same block/bundle. This inflates the `total_*_without_take_pnl` denominator used in the LP-mint formula without moving `amm.lp_amount`, so the victim's `mint_lp_amount` is diluted — while the required `deduct_coin_amount`/`deduct_pc_amount` can still satisfy the victim's `max_coin_amount`/`max_pc_amount`/`other_amount_min` bounds, because those only constrain the token *ratio*, not the LP shares issued per unit deposited. The attacker, holding a majority of `amm.lp_amount` from before the donation (e.g., as the pool creator, protected only by the tiny `InitLpAmountTooLess` burn), can then immediately `Withdraw` and redeem a disproportionate share of the pool's total assets — capturing the value the victim just deposited. [6](#0-5) 

This mirrors the Curve bug class exactly: an unvalidated, externally-influenceable ratio (`get_virtual_price()` there, live vault balances here) is fed directly into a value-conversion formula with no sanity check, no minimum-output slippage protection, and no smoothing — allowing an attacker to manipulate share/price computations to their benefit at another user's expense.

### Title
Deposit LP-mint amount can be diluted via unvalidated vault-balance donation (missing min_lp_amount_out) - (File: program/src/processor.rs)

### Summary
`process_deposit` computes minted LP tokens as `deduct_amount * amm.lp_amount / total_{coin,pc}_without_take_pnl`, where the denominator is read directly, unvalidated, from live SPL vault balances. `DepositInstruction` provides no `min_lp_amount_out` guard, so a depositor has no protection against the number of LP tokens they receive being manipulated, even though their deposited-token amounts pass the existing `max_coin_amount`/`max_pc_amount`/`other_amount_min` checks.

### Finding Description
Anyone can transfer extra coin or pc tokens directly into `amm.coin_vault`/`amm.pc_vault` (plain SPL transfers, not gated by the AMM program) right before a victim's `Deposit` transaction. This inflates `total_coin_without_take_pnl`/`total_pc_without_take_pnl` computed in `Calculator::calc_total_without_take_pnl_no_orderbook` [7](#0-6) , which is used unchecked as the denominator in `InvariantPool::exchange_token_to_pool` for LP-mint calculation [8](#0-7) . Since the deposit's slippage checks only bound the deduced coin/pc amounts (`ExceededSlippage` on `deduct_pc_amount`/`deduct_coin_amount` vs. `max_*`/`other_amount_min`) and not `mint_lp_amount` itself [9](#0-8) , the victim's deposit can proceed while receiving fewer LP shares than their fair proportional value.

### Impact Explanation
An attacker holding a dominant share of `amm.lp_amount` (trivially achievable by being the pool's creator, since only a small fixed `InitLpAmountTooLess` burn protects the initial mint) can dilute a victim's `Deposit` and then immediately `Withdraw` to capture a disproportionate share of pool assets, including the victim's newly deposited funds. This is direct theft of user funds and insolvent LP accounting relative to fair share value.

### Likelihood Explanation
Requires only ordinary SPL token transfers plus ordering control (e.g., transaction bundling/front-running within a slot) and holding a majority LP position, both of which are attainable by any unprivileged actor without special keys, satisfying the "unprivileged swapper/LP/pool creator" reachability requirement.

### Recommendation
Add a `min_lp_amount_out` parameter to `DepositInstruction` and enforce it in `process_deposit`, so depositors can directly bound the number of LP tokens they will receive, independent of ratio-based deduct-amount checks.

### Proof of Concept
1. Attacker creates (or already holds majority LP in) a pool via `Initialize2`, receiving `user_lp_amount` LP tokens [6](#0-5) .
2. Attacker observes victim's pending `Deposit` transaction (base_side = coin) with fixed `max_coin_amount`/`max_pc_amount`/`other_amount_min`.
3. Attacker sends a plain SPL `Transfer` of coin tokens into `amm.coin_vault`, inflating `total_coin_without_take_pnl`.
4. Victim's `Deposit` executes: `deduct_pc_amount` decreases (still passes `other_amount_min`), but `mint_lp_amount = deduct_coin_amount * amm.lp_amount / total_coin_without_take_pnl(inflated)` is reduced [2](#0-1) .
5. Attacker calls `Withdraw` for their existing LP tokens, redeeming a share of `total_coin_without_take_pnl`/`total_pc_without_take_pnl` (now including the victim's contribution) computed via `InvariantPool::exchange_pool_to_token` [10](#0-9) , capturing more value than their fair share while the victim is left under-compensated for their deposit.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

    /// Exchange rate
    pub fn exchange_token_to_pool(
        &self,
        pool_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
