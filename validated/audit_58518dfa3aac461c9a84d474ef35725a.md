## #Vulnerability found for this question.

### Title
Missing Chainlink L2 sequencer uptime check in `SimplexPaymaster` oracle pricing - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `AggregatorV3Interface.latestRoundData()` for both the native-asset feed and each registered token feed, but only validates answer positivity and staleness relative to `block.timestamp`; it never checks whether the L2 sequencer feeding that chain's Chainlink deployment is up, per Chainlink's documented L2 sequencer-uptime-feed guidance (https://docs.chain.link/data-feeds/l2-sequencer-feeds).

### Finding Description
`_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` is the sole gate on Chainlink data used for gas pricing: [1](#0-0) 

It reverts on non-positive answers (`InvalidOraclePrice`) and on staleness beyond `maxOracleAge` (`StaleOraclePrice`), but it never consults a Chainlink `SequencerUptimeStatusFeed` (no `isSequencerUp`/`GRACE_PERIOD` logic exists anywhere in the repo — confirmed via search). This contract is used across multiple L2 deployments: the `nativeOracle` doc comment explicitly lists "BNB/USD on BSC, ETH/USD on Ethereum, etc.", and the SDK's Chainlink price-feed address registry independently confirms Base, Optimism, and Arbitrum (all L2s with a Chainlink sequencer-uptime feed) as target chains: [2](#0-1) [3](#0-2) 

On an OP-stack/Arbitrum-style L2, when the sequencer goes down, the underlying Chainlink aggregator round data can stop updating for an extended period, then jump on sequencer restart. During the outage window, `updatedAt` may still appear "fresh enough" relative to `maxOracleAge` (especially with the loosely bounded `MAX_ORACLE_AGE = 7 days` allowed by governance), or the first round(s) posted after restart can reflect a price that is stale relative to the true off-chain market but still passes the staleness check because the feed's own internal heartbeat resumed. Without an explicit sequencer-uptime check and grace period, `_getOraclePrice` will accept this data as valid.

This pricing function is reached by every unprivileged UserOp sender who is a bandwidth (gas) purchaser using the paymaster: `_tokenPrice` → `getTokenPrice`/`estimateTokenCost` (view) and, more importantly, `_prefund`'s permit/permit2 flow which computes the actual ERC-20 amount pulled from the sender during `validatePaymasterUserOp`. A known project decision log even flags that oracle freshness bounds were deliberately deferred as "out of scope," underscoring that oracle-derived validity is an acknowledged gap: [4](#0-3) 

### Impact Explanation
If the sequencer-fed price is stale/incorrect during or immediately after an L2 sequencer outage, `_getOraclePrice`/`_tokenPrice` will compute an incorrect `nativeUsd`/`tokenUsd` ratio. Since `_prefund` uses this ratio to determine how much ERC-20 token to pull from the UserOp sender via Permit/Permit2 to cover the paymaster's gas cost, a mispriced oracle can:
- Overcharge unprivileged users (bandwidth purchasers) far beyond the true gas cost, or
- Undercharge, draining the paymaster's `treasury`/EntryPoint deposit balance disproportionate to gas actually consumed.

Either direction is a fund-safety issue reachable purely by submitting a normal UserOp during a sequencer disruption — no privileged role required. This is a Medium-severity issue matching the reported bug class exactly (unchecked Chainlink L2 sequencer uptime), applied to an in-scope, currently-live pricing path rather than the removed upstream `ChainlinkWrapper`.

### Likelihood Explanation
L2 sequencer downtimes are infrequent but have occurred historically on Arbitrum, Optimism-stack chains, and Base. Because `SimplexPaymaster` is explicitly designed to be deployed to these chains (per the doc comments and the shared price-feed address registry) and the check is entirely absent (not merely misconfigured), any sequencer outage on a deployed L2 within the `maxOracleAge` window would trigger the issue without any special attacker action — a normal UserOp submitted during/after the outage is sufficient.

### Recommendation
Add a per-chain Chainlink `SequencerUptimeStatusFeed` check (analogous to `AggregatorV2V3Interface` sequencer feeds) inside `_getOraclePrice` (or a new `_checkSequencer()` guard called before it), reverting or enforcing Chainlink's recommended grace period (e.g., 3600s) if the sequencer is down or has just come back up, consistent with https://docs.chain.link/data-feeds/l2-sequencer-feeds. This should be configurable per L2 deployment (some chains, like BSC, have no sequencer and don't need the check) via the governance-settable `Params` struct.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an L2 (e.g., Base) per the documented multi-chain support.
2. Simulate a sequencer outage window (Chainlink feed's `latestRoundData().updatedAt` stalls but remains within `maxOracleAge`, or resumes with a stale first tick).
3. Submit a normal UserOp using the token-permit paymaster mode; `_prefund` → `_tokenPrice` → `_getOraclePrice` accepts the stale/incorrect price with no `StaleOraclePrice`/`InvalidOraclePrice` revert because no sequencer status is checked.
4. The sender is charged (or the paymaster is charged) an incorrect ERC-20 amount based on the incorrect price, demonstrated directly via `_getOraclePrice`'s check logic: [5](#0-4)

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```

```markdown
# 2026-08-19 — Not adopted: soft-failing the prefund, and oracle-derived validity bounds (#1071)

Rejected: returning `prefunded = false` instead of reverting in the mode-2 `_prefund`. Upstream advises it to protect bundler reputation, but reading EntryPoint v0.8 shows both outcomes are `revert FailedOp` — AA33 for a paymaster revert, AA34 for a sig-failure — so both revert `handleOps` identically. The change would trade the `Permit2Failed(token, reason)` diagnostic, which carries Permit2's own revert data, for no bundle-level benefit.

Also deferred at the maintainer's direction: bounding `validationData`'s `validUntil` by oracle freshness so bundlers drop soon-to-be-stale ops instead of building bundles that revert. Sound in principle and would have made stale-oracle failures expire cleanly, but it touches every pricing path and was out of scope for this pass.
```
