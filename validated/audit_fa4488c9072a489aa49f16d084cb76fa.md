### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity headers are not covered by the HMAC signature, allowing shop-spoofing replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` only proves the JSON body was produced with the app's `api_secret_key`. The tenant-identifying `shop` value (and `topic`, `webhook_id`, `api_version`) is read straight from unauthenticated HTTP headers and handed to the app's handler as trusted data, breaking the intended binding `hmac_signed_bytes == identity_used_by_handler`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all extracted from headers via `shopify_header`: [2](#0-1) 
`Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` unconditionally to build `WebhookMetadata` passed to the app's handler: [3](#0-2) 
`WebhookMetadata.shop` is a plain `String` field with no cryptographic binding to the signed body: [4](#0-3) 

The gem's own test setup demonstrates the disconnect: the same HMAC (`OpenSSL::HMAC.digest(... , "{}")`) is valid regardless of what `shop`/`topic`/`webhook_id` headers accompany it: [5](#0-4) 

Equality that should hold but doesn't: `hmac_signed_bytes (raw_body only) == identity_bytes_trusted_by_handler (shop header)`. Since the HMAC never covers `shop`, an attacker who can obtain any single valid `(raw_body, hmac)` pair signed by the app's secret (e.g. from a legitimate webhook delivered to their own store, which they fully control and can intercept) can resend the identical body+hmac while substituting the `x-shopify-shop-domain` header with a victim shop's domain. The signature still validates because it only proves body integrity, and `Registry.process` forwards the attacker-chosen `shop` value to the handler as if it were the real, Shopify-verified tenant.

### Impact Explanation
This is a cross-tenant identity confusion: the app-side webhook handler (as documented in `docs/usage/webhooks.md`, handlers key persistence/business logic off `data.shop`) will process attacker-controlled webhook bodies under an arbitrary victim `shop` value, despite the HMAC only certifying that the *body* came from Shopify — not that the *shop* did. Depending on handler logic (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`), this can trigger tenant-scoped side effects (data deletion, session invalidation, state changes) attributed to a shop the attacker does not control, i.e. cross-tenant access without possessing that shop's credentials.

### Likelihood Explanation
The attacker only needs to be a legitimate (even free-trial) merchant of the app — an unprivileged internet user relative to other merchants' data — who can receive one authentic webhook for their own store and replay it with a forged `shop` header at the app's public webhook endpoint. No access token, `client_secret`, or TLS interception is required; this only depends on the gem's own header-vs-signature handling in `Request`/`Registry`.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable string (or otherwise cryptographically bind them to the signed payload), so `Utils::HmacValidator.validate` fails if any of these header-derived identity fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Register a webhook handler for topic `app/uninstalled` (or any sensitive topic) that keys persistence off `data.shop`.
2. As a merchant, install the app on `attacker-shop.myshopify.com`; capture the legitimate webhook Shopify sends: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`, per `Request#to_signable_string`/`hmac_validator.rb`).
3. Resend an HTTP POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` returns `true` (it only checks `B` against `H`), and `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` is passed to the handler, which now acts on the victim's tenant data despite the attacker never having credentials for `victim-shop`.
