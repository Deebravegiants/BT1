### Title
Webhook `shop` and `topic` identity are not bound by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the `Utils::HmacValidator.validate` check that gates `ShopifyAPI::Webhooks::Registry.process` cryptographically authenticates *only* the body bytes. The `shop-domain` and `topic` headers — which are the values actually used to dispatch to a handler and to identify the tenant the webhook is "for" — are read straight off the unauthenticated HTTP headers and are never included in the signed material.

### Finding Description
`Request#hmac`/`#to_signable_string` is defined as: [1](#0-0) [2](#0-1) 

Only `@raw_body` is fed into `to_signable_string`, whereas `topic` and `shop` are pulled from the (unauthenticated) `shopify-topic` / `shopify-shop-domain` headers via `shopify_header`.

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header: [3](#0-2) 

Since `to_signable_string` for a webhook `Request` is only the body, the signature says nothing about which `shop` or `topic` the body was originally sent for. `Registry.process` nonetheless trusts these unauthenticated fields to route and identify the tenant: [4](#0-3) 

The identity binding that should hold is:
`shop asserted to the handler (request.shop) == shop that Shopify actually signed the webhook for`

but the code only proves:
`bytes verified by HMAC (raw_body) == bytes that were originally hashed`

with no linkage from `raw_body` to `shop`/`topic`. Any entity capable of legitimately receiving one authentic, HMAC-signed webhook from Shopify for a body it does not control the semantics of (e.g. `app/uninstalled` with an empty/near-empty JSON body `{}`, or any topic whose payload doesn't strongly bind to the sending shop) can capture that `(raw_body, hmac)` pair once — e.g. by installing the app on a store they legitimately control — and then replay the identical body+hmac to the app's webhook endpoint while substituting arbitrary `shopify-shop-domain` and `shopify-topic` header values. `HmacValidator.validate` will still pass because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming an attacker-chosen `shop` and `topic`: [5](#0-4) 

Any host application that keys business logic off `WebhookMetadata#shop` (e.g. uninstall/deauthorize a shop, delete a shop's data, disable billing, etc., as the gem's own docs instruct apps to do) can be made to act on a shop the attacker does not control, purely by manipulating headers on a replayed, still-validly-signed request.

### Impact Explanation
This breaks the tenant-identity binding between the cryptographically authenticated content and the acted-upon shop, allowing a party with no relationship to the victim shop to make the app process a forged webhook "as if" it came from that shop — a cross-tenant action performed on the strength of another merchant's captured payload. This matches the Critical "cross-tenant access" impact category, since the app cannot distinguish a genuine webhook for shop A from a replayed body claiming to be for shop B.

### Likelihood Explanation
Requires only unprivileged access: an attacker installs the app on any store they control (free/dev store), captures one legitimate webhook body+HMAC pair Shopify sends for a topic with a static/predictable/empty body, and replays it to the app's public webhook endpoint with a forged `shopify-shop-domain`/`shopify-topic` header. No `api_secret_key`, access token, or privileged account is needed — the attacker is a normal merchant using the gem's documented webhook flow against itself.

### Recommendation
Include `shop` and `topic` (and ideally `api_version`/`webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind them (e.g., require the host app to additionally verify the recomputed HMAC against a canonicalized string containing `shop`+`topic`+`body`) rather than trusting the raw headers once body-only HMAC validation succeeds.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a genuine webhook, e.g. `app/uninstalled` with body `{}` and header `shopify-hmac-sha256: H` (H is valid for secret `S` and body `{}`).
2. Attacker POSTs to the app's webhook endpoint with the same raw body `{}` and same `shopify-hmac-sha256: H`, but sets:
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic: app/uninstalled` (or another topic whose handler logic doesn't depend on distinguishing fields inside `{}`)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`{}`), so it validates successfully because the body and HMAC genuinely match under secret `S`.
4. The registered handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", body: {}, ...)` and executes shop-scoped logic (e.g., deauthorization/data deletion) against `victim-shop.myshopify.com`, despite that shop never having sent/authorized this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
