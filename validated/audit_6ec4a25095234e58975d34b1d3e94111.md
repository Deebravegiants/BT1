### Title
Case-sensitivity bypass of `DestinationAddressMatchesTokenAddressError` allows BTC withdrawal to the Omni Bridge's own custody address - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.validateWithdrawal` blocks withdrawals whose `destinationAddress` equals the bridge's own destination-token custody address using `compareAddresses`, which for Bitcoin performs a raw case-sensitive string comparison. Bech32 Bitcoin addresses are valid in both all-lowercase and all-uppercase form, and `deriveOmniWithdrawIntentParams` explicitly lowercases any `bc1`-prefixed address (case-insensitively matched) before building the on-chain intent. An attacker can submit the custody address in uppercase to defeat the equality check at validation time, while the address is silently normalized to the exact custody address before the withdrawal intent is created and executed.

### Finding Description
`validateWithdrawal` computes the bridge's own destination token address and rejects a withdrawal if it equals the user-supplied `destinationAddress`: [1](#0-0) 

The equality check delegates to `compareAddresses`, which for Bitcoin (grouped with Near, Litecoin, Solana, etc.) performs plain `a === b`, with no case normalization: [2](#0-1) 

`validateAddress` for Bitcoin, however, accepts bech32 addresses regardless of case (bech32/bech32m decode succeeds for all-uppercase input as long as the case is internally consistent): [3](#0-2) 

Separately, `deriveOmniWithdrawIntentParams`, which builds the actual withdrawal intent, explicitly lowercases the destination address whenever it case-insensitively matches the `bc1` prefix — and the surrounding comment states this is because "the Omni contract only accepts lowercase bech32 addresses; uppercase/mixed-case bech32 is spec-valid but rejected on-chain": [4](#0-3) 

So the equality that the code intends to enforce — "the recipient the intent will actually pay is not the token/bridge custody address" — is checked *before* case normalization but the payment is executed *after* normalization. Given the custody/connector address is stored/returned canonically in lowercase by `getCachedDestinationTokenAddress`/`getAddress`, an attacker who submits that same address in uppercase:
1. Passes `validateAddress` (format-valid Bitcoin bech32 address).
2. Fails to trip `compareAddresses` at line 386-396 because `"BC1Q..." !== "bc1q..."`, so `DestinationAddressMatchesTokenAddressError` is never thrown.
3. Has their address silently lowercased in `deriveOmniWithdrawIntentParams` (line 120-124) to exactly the custody address before the `ft_withdraw`/transfer intent is constructed and signed.

### Impact Explanation
This breaks the intended equality "destination paid ≠ token custody address" that the code deliberately enforces to stop funds from being sent to the bridge's own connector/custody address (an address the withdrawing user cannot control and from which BTC cannot be recovered through normal means). The result is funds delivered to a wrong/unintended address with no recovery path for the user — a Critical-class outcome under the stated impact criteria ("funds delivered to a wrong address/chain/contract with no recovery").

### Likelihood Explanation
No privileged access is required — any unprivileged caller of the SDK's withdrawal flow (`createWithdrawalIntents`/`estimateWithdrawalFee` → `validateWithdrawal`) can trigger this by supplying an uppercase bech32 form of a known/discoverable custody address for the asset being withdrawn. The custody/connector address is a piece of protocol metadata retrievable via `getCachedDestinationTokenAddress`, not a secret.

### Recommendation
Normalize both sides of the comparison before checking equality for chains whose canonical/on-chain-accepted encoding is case-insensitive (in particular Bitcoin bech32/bech32m): either lowercase both addresses inside `compareAddresses`'s Bitcoin branch (mirroring the normalization already applied in `deriveOmniWithdrawIntentParams`), or perform the `DestinationAddressMatchesTokenAddressError` check using the already-normalized address (i.e., run address normalization once, upfront, and reuse the normalized value for both validation and intent construction) so validation and execution never operate on different representations of the same address.

### Proof of Concept
1. Identify the Omni Bridge BTC custody/connector address for a given `nep141:*` asset (e.g. via `getCachedDestinationTokenAddress` output, which is lowercase bech32, e.g. `bc1q...custody`).
2. Call the SDK withdrawal flow (`sdk.createWithdrawalIntents` / `estimateWithdrawalFee`) with `assetId` for that asset and `destinationAddress` set to the uppercase form of the custody address, e.g. `BC1Q...CUSTODY`.
3. `validateAddress` accepts the uppercase bech32 address as valid.
4. `compareAddresses(destTokenAddress /* lowercase */, "BC1Q...CUSTODY", Chains.Bitcoin)` returns `false` because of the case-sensitive `a === b` check, so `DestinationAddressMatchesTokenAddressError` is not thrown.
5. `createWithdrawalIntents` → `deriveOmniWithdrawIntentParams` lowercases the address (regex `/^bc1/i` matches) producing the exact custody address as `recipient`, and the resulting `ft_withdraw` intent sends the withdrawal to the bridge's own custody address.
