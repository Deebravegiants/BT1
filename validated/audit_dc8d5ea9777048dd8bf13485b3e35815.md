### Title
CostModel underprices account-load work when `set_loaded_accounts_data_size_limit` is set below actual account sizes, because the recorded `loaded_accounts_data_size` is clamped to the attacker's declared limit rather than reflecting bytes actually read from accounts-db - ([File: svm/src/account_loader.rs])

### Summary
`LoadedTransactionDataSize`'s `From<LoadedTransactionDataSize> for u32` conversion caps the reported loaded-accounts size to `min(actual_running_total, requested_limit)` instead of the real bytes touched before failure. Because `load_transaction_accounts` fully loads each account (including large program/programdata/ALT-resolved accounts) from accounts-db *before* checking the running total against the requested limit, an attacker can set a tiny `set_loaded_accounts_data_size_limit` while still forcing the validator to read a large account, yet the cost model only ever sees the tiny declared limit for cost accounting.

### Finding Description
`LoadedTransactionDataSize::increase_calculated_data_size` accumulates `loaded_accounts_data_size` and only returns `Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)` *after* the delta for the just-loaded account has already been added [1](#0-0) . Since `load_transaction_account`/`account_loader.load_account` reads the full `AccountSharedData` (fee payer, then each subsequent account, then programs/programdata) from accounts-db before this check runs, the actual read/deserialize work for the account that trips the limit has already occurred [2](#0-1) .

When the load fails, `From<LoadedTransactionDataSize> for u32` clamps the value that survives to `value.loaded_accounts_data_size.min(value.requested_loaded_accounts_data_size_limit)` — i.e., the small attacker-declared limit, not the true accumulated size at time of failure [3](#0-2) . This capped value is what gets stored as `loaded_accounts_data_size` on the `FeesOnlyTransaction` (when `define_ltds_fee_only_semantics` is active) [4](#0-3) , or on a successful `LoadedTransaction` [5](#0-4) .

That reported size flows into `CommittedTransaction::loaded_account_stats` and is fed to `CostModel::calculate_cost_for_executed_transaction`, which calls `calculate_loaded_accounts_data_size_cost` on it to compute the actual `loaded_accounts_data_size_cost` used for block-cost tracking [6](#0-5) [7](#0-6) . `calculate_loaded_accounts_data_size_cost` simply divides the passed byte count into 32KB pages and multiplies by `DEFAULT_HEAP_COST` [8](#0-7) , so it has no way to recover the true bytes actually read when it is only given the clamped/attacker-declared value.

An attacker can broadcast a transaction that: (1) lists a large account (up to `MAX_PERMITTED_DATA_LENGTH`, ~10 MiB) as the first non-fee-payer account key, or references a large account/program/programdata through an ALT, and (2) sets `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit` to a tiny value (e.g., 1 byte). `load_transaction_accounts` reads the fee payer (already loaded pre-validation) and then the large account, incurring the real accounts-db read/deserialize cost, before `increase_calculated_data_size` detects the overflow and aborts with `MaxLoadedAccountsDataSizeExceeded`. The transaction still pays its base signature/priority fee (independent of `loaded_accounts_data_size`) as a `FeesOnlyTransaction`, but the cost-tracker-visible `loaded_accounts_data_size_cost` is computed from the tiny declared limit rather than the actual bytes read, undercharging the account-load work that was already performed.

No existing guard corrects for this: the pre-execution admission estimate in `get_estimated_execution_cost` also just uses the user-declared `loaded_accounts_data_size_limit`, not real sizes [9](#0-8) , and the post-execution "actual" value is likewise clamped by the `From` impl, so the true work is never reflected in the block-cost tracker at any stage.

### Impact Explanation
This falls under "cost-model estimate must upper-bound real account-load work" / materially underpriced execution: an attacker can repeatedly force the validator to perform real accounts-db reads of large accounts while being charged (for block-cost-tracker admission purposes) only the tiny declared `loaded_accounts_data_size_limit`. Repeated at scale this lets an attacker's transactions consume disproportionate account-load I/O relative to the cost budget they occupy in a block, degrading the accuracy of the cost model's resource accounting used for block-cost-limit enforcement.

### Likelihood Explanation
Fully attacker-controlled and requires no privileges: any user can craft a transaction with an arbitrary account list/ALT and any `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit` value, broadcasting it via ordinary TPU/RPC submission. The only cost to the attacker is the fixed signature/priority fee of a failed (fees-only) transaction, which is independent of `loaded_accounts_data_size`. It is trivially repeatable per transaction.

### Recommendation
When a load fails due to `MaxLoadedAccountsDataSizeExceeded`, record and propagate the true accumulated `loaded_accounts_data_size` (the pre-clamp running total, or at least the size delta of the specific account that caused the overflow) instead of clamping to `requested_loaded_accounts_data_size_limit` in `From<LoadedTransactionDataSize> for u32`, so that post-execution cost accounting in `CostModel::calculate_cost_for_executed_transaction` reflects real bytes touched rather than the attacker-declared limit.

### Proof of Concept
Rust unit test plan (in `svm/src/account_loader.rs` test module, alongside existing tests like `test_increase_calculated_data_size`):
```rust
#[test]
fn test_loaded_size_undercounted_on_limit_exceeded() {
    let mut error_metrics = TransactionErrorMetrics::default();
    let requested_limit: u32 = 1; // attacker declares tiny limit
    let mut acc = LoadedTransactionDataSize::with_max_size(requested_limit);

    // Simulate loading one large account (e.g. 10 MiB) whose full read
    // already happened in accounts-db before this check runs.
    let big_account_bytes: usize = 10 * 1024 * 1024;
    let result = acc.increase_calculated_data_size(big_account_bytes, &mut error_metrics);

    assert_eq!(result, Err(TransactionError::MaxLoadedAccountsDataSizeExceeded));
    // BUG: reported size is clamped to the declared limit, not the actual
    // bytes read (big_account_bytes), so cost-model input undercounts by
    // ~10 MiB.
    assert_eq!(u32::from(acc), requested_limit);

    let reported_cost = CostModel::calculate_loaded_accounts_data_size_cost(
        requested_limit,
        &FeatureSet::default(),
    );
    let true_cost = CostModel::calculate_loaded_accounts_data_size_cost(
        big_account_bytes as u32,
        &FeatureSet::default(),
    );
    // Invariant violated: cost model must upper-bound real work, but
    // reported_cost << true_cost.
    assert!(reported_cost < true_cost);
}
```
An integration-level PoC can extend `fee_only_loaded_transaction_data_size` in `svm/tests/integration_test.rs` (which already exercises the `fail_limit_transaction` path) by asserting that `output.processing_results[1].loaded_accounts_data_size()` is far smaller than the sum of actual account sizes referenced by the transaction, demonstrating the discrepancy between real work performed and cost charged.

    fn increase_calculated_data_size(
        &mut self,
        data_size_delta: usize,
        error_metrics: &mut TransactionErrorMetrics,
    ) -> Result<()> {
        // this branch is unreachable in practice (though not by construction),
        // since it would imply an account >4gb in size
        let Ok(data_size_delta) = u32::try_from(data_size_delta) else {
            self.loaded_accounts_data_size = u32::MAX;
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            return Err(TransactionError::MaxLoadedAccountsDataSizeExceeded);
        };

        self.loaded_accounts_data_size = self
            .loaded_accounts_data_size
            .saturating_add(data_size_delta);

        if self.loaded_accounts_data_size > self.requested_loaded_accounts_data_size_limit {
            error_metrics.max_loaded_accounts_data_size_exceeded += 1;
            Err(TransactionError::MaxLoadedAccountsDataSizeExceeded)
        } else {
            Ok(())
        }
    }

            // transaction. By checking account_keys, we never double-count a programdata account
            // that was explicitly included in the transaction. We also use a hashset to gracefully
            // handle cases that LoaderV3 presumably makes impossible, such as self-referential
            // program accounts or multiply-referenced programdata accounts, for added safety.
            //
            // If in the future LoaderV3 programs are migrated to LoaderV4, this entire code block
            // can be deleted.
            //
            // If this is a valid LoaderV3 program...
            if bpf_loader_upgradeable::check_id(account.owner())
                && let Ok(UpgradeableLoaderState::Program {
                    programdata_address,
                }) = bincode::deserialize(account.data())
            {
                // ...its programdata was not already counted and will not later be counted...
                if !account_keys.iter().any(|key| programdata_address == *key)
                    && !additional_loaded_accounts.contains(&programdata_address)
                {
                    // ...and the programdata account exists (if it doesn't, it is *not* a load failure)...
                    if let Some(programdata_account) =
                        account_loader.load_account(&programdata_address)
                    {
                        // ...count programdata toward this transaction's total size.
                        loaded_tx_data_size.increase_calculated_data_size(

                                .saturating_add(programdata_account.data().len()),
                            error_metrics,
                        )?;
                        additional_loaded_accounts.insert(programdata_address);
                    }
                }
            }

            loaded_transaction_accounts.push((*key, account));

            Ok(())
        };

    for (account_index, account_key) in account_keys.iter().enumerate().skip(1) {

            load_transaction_account(account_loader, message, account_key, account_index, rent)?;

    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }
