### Title
Fee-on-transfer tokens allow unbacked destination mints in WrappedHyperFungibleToken - (File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol)

### Summary
`WrappedHyperFungibleToken.send()` escrows the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and immediately builds the cross-chain `Message` using the user-supplied `params.amount`, without ever measuring the contract's actual balance delta. If the underlying token charges a fee on transfer (e.g., a future fee-enabled USDT/USDC, or any deflationary/fee-on-transfer ERC20 an owner configures as `_underlying`), the contract receives less than `params.amount`, yet the dispatched message still promises the destination chain the full `params.amount`.

### Finding Description
In `send()`: [1](#0-0) 

The contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` without checking `balanceOf(address(this))` before/after, then `_buildDispatchPost(params)` encodes `params.amount` verbatim into the `Message` body: [2](#0-1) 

On the destination chain, `HyperFungibleToken.onAccept` mints `message.amount` unconditionally to the beneficiary: [3](#0-2) 

If `onPostRequestTimeout` fires instead, `WrappedHyperFungibleToken` unlocks `message.amount` (the full pre-fee amount) back to the sender from its own escrow: [4](#0-3) 

In every path — delivery or timeout — the amount used is the un-adjusted `params.amount`/`message.amount`, not the amount actually escrowed. This breaks the core lock/mint 1:1 backing invariant that `WrappedHyperFungibleToken` is documented to preserve ("Locks the underlying token on the source chain and mints/unlocks on the destination chain") [5](#0-4) . Notably, the codebase already recognizes and defends against exactly this bug class elsewhere — `IntentGatewayV2` measures actual balance deltas before crediting escrow specifically to handle fee-on-transfer tokens, as shown by its dedicated `FeeOnTransferToken` test suite [6](#0-5) , but `WrappedHyperFungibleToken` (and its `Upgradeable` twin, which has identical logic [7](#0-6) ) has no equivalent protection.

### Impact Explanation
This is a permissioned-configuration but unprivileged-exploitation issue: any single user calling `send()` with a fee-on-transfer underlying (whenever the owner configures such a token, or an existing token later activates a transfer fee as USDT/USDC reserve the right to do) causes the destination chain to mint more tokens than were actually locked in escrow on the source chain. Each such transfer creates a permanent shortfall between the escrowed balance and the total amount promised/minted across all chains. Over repeated use this insolvency compounds, ultimately preventing legitimate users from redeeming their locked tokens on the source chain (the contract's `_underlying` balance runs out before all outstanding mints/unlocks can be honored) — i.e., unbacked mint and eventual freezing of funds for other bridge users.

### Likelihood Explanation
Likelihood is Medium: it requires the deployer/owner to configure a fee-on-transfer ERC20 as `_underlying` via `configure()`, or an already-configured token later enabling a transfer fee (a documented risk specifically called out for USDT/USDC). Given `WrappedHyperFungibleToken` is a generic wrapper meant to support arbitrary existing ERC20s [8](#0-7) , this is a realistic deployment scenario, not a contrived edge case, and requires no privileged action from an attacker — merely calling `send()` normally.

### Recommendation
In `send()`, measure `balanceOf(address(this))` before and after `safeTransferFrom` (or WETH deposit), and use the actual received delta — not `params.amount` — when building the dispatch message. Symmetrically, ensure `onAccept`/`onPostRequestTimeout` release exactly what was escrowed for that commitment rather than trusting the message-encoded amount, mirroring the balance-delta pattern already used in `IntentGatewayV2.placeOrder` [9](#0-8) .

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` with `_underlying` set to a token that charges a 1% transfer fee (or an existing token like USDT that later activates its dormant fee mechanism).
2. Alice calls `send({amount: 1000e6, to: bob, dest: chainB, ...})`.
3. `safeTransferFrom(alice, address(this), 1000e6)` actually delivers only 990e6 to the contract (10e6 retained as fee by the token contract itself); the contract's escrowed balance increases by only 990e6.
4. `_buildDispatchPost` encodes `amount: 1000e6` in the `Message`, and the ISMP request is dispatched with this uncorrected value.
5. On chain B, `HyperFungibleToken.onAccept` mints Bob 1000e6 tokens — 10e6 more than what is actually backing them on chain A.
6. If Bob (or a subsequent holder) bridges the full 1000e6 back to chain A, `onAccept`'s `safeTransfer(beneficiary, message.amount)` attempts to release 1000e6 from an escrow that only holds 990e6 (plus whatever surplus exists from other users' deposits), eventually causing reverts/insolvency once the shortfall accumulates across multiple transfers.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),

            amount: params.amount,
            data: params.data

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,

        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
