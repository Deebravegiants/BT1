### Title
Multisig timelock-bypass threshold (`override_threshold`) is silently reduced for already-pending transactions when owners are removed - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account.move` adds a custom `MultisigAccountTimeLock` resource with an `override_threshold` field that is meant to let a supermajority of owners bypass a pending transaction's timelock early. This threshold is stored globally on the multisig account (not per-transaction), and `update_owner_schema` — the function backing `add_owners`, `remove_owners`, `swap_owners`, and `update_signatures_required` — silently clamps `override_threshold` down whenever the owner set shrinks: [1](#0-0) 

### Finding Description
`update_owner_schema` clamps `timelock.override_threshold` to `num_owners` whenever owners are removed and the old override threshold exceeds the new owner count, then only re-validates that `override_threshold > num_signatures_required`: [2](#0-1) 

This mutation is not scoped to future transactions — it changes a single global field read live by every already-pending `MultisigTransaction`. At prologue time, `validate_multisig_transaction` checks the timelock bypass condition using the *current* on-chain state: `can_execute_with_timelock(multisig_account, sequence_number, num_approvals)`, evaluated after quorum, using live values rather than values captured when the transaction was created: [3](#0-2) 

This mirrors the external report's root cause exactly: a governance/authority parameter (`quorumNumerator` there, `override_threshold` here) that determines whether a pending decision can be finalized is mutable after the decision was proposed, and the finalization check reads the *current* value instead of a value snapshotted at proposal creation. Here, any owner-removal transaction (itself just another multisig transaction requiring only `num_signatures_required` approvals, not unanimous consent) can retroactively lower the bar required to bypass the timelock on a transaction that is already pending and was expected to require a supermajority override.

### Impact Explanation
If the intended custody invariant is "a pending, still-timelocked, high-value multisig transaction (e.g., a large APT transfer or upgrade payload) can only be executed early by an override supermajority of `override_threshold` owners," this invariant is retroactively weakened by any owner-set change that occurs while the transaction is pending. Owners could first pass an unrelated `remove_owners` transaction (meeting only the normal `num_signatures_required` quorum), shrink the owner set, causing `override_threshold` to clamp down toward `num_signatures_required`, and thereby unlock early bypass-execution of an already-queued, still-timelocked, high-value transaction with fewer approvals than the timelock override was designed to require. This is a custody-grade authority weakening: it can allow premature release of resource-account/multisig-controlled value (APT, fungible assets, or code-object control) before the intended timelock protection window, using an approval count lower than what voters/owners understood was required when the transaction was proposed.

### Likelihood Explanation
The precondition is realistic in normal multisig operation: owner set changes (`add_owners`, `remove_owners`, `swap_owners`) are common maintenance actions and only require the standard `num_signatures_required` quorum, not owner-set-change-specific supermajority. Any owner subset that can pass a routine owner-removal transaction can affect the override threshold for all currently pending transactions, including transactions proposed by other owners for entirely different purposes.

### Recommendation
Snapshot the effective override threshold (and/or the timelock parameters generally) into the `MultisigTransaction` struct at creation/proposal time, and have `can_execute_with_timelock` evaluate against the snapshotted value rather than the live `MultisigAccountTimeLock.override_threshold`. Alternatively, disallow `update_owner_schema` from mutating `override_threshold` while any transaction relying on the timelock-override path is still pending, or require re-validation/re-approval of pending transactions whenever the owner set or override threshold changes.

### Proof of Concept
Conceptual sequence (exact PoC requires confirming `can_execute_with_timelock`'s full logic, which I could not retrieve in the available iterations):
1. Multisig has owners = 5, `num_signatures_required = 3`, timelock configured with `override_threshold = 5` (unanimous override).
2. Owner A creates a high-value transaction (e.g., APT transfer); it is still within its timelock period, so it can't execute normally and would need all 5 owners to approve to bypass the timelock early.
3. Before 5 owners approve, owners B, C, D pass a `remove_owners` transaction (meeting only the 3-of-5 quorum) removing one owner, shrinking `num_owners` to 4.
4. `update_owner_schema` clamps `override_threshold` from 5 down to 4 [4](#0-3) .
5. The pending high-value transaction from step 2 can now be bypass-executed with only 4 approvals instead of the originally required 5, via `validate_multisig_transaction`'s live read of `can_execute_with_timelock` [5](#0-4) .

**Caveat**: I was unable to view the full implementation of `can_execute_with_timelock` (only its call site) before the iteration budget was exhausted, so I cannot cite the exact comparison it performs against `override_threshold`/`timelock_period`. If `can_execute_with_timelock` re-derives its own snapshot from transaction `creation_time_secs` and never consults the live `override_threshold` for approval-count purposes, this finding's severity would be reduced accordingly — this should be verified directly in a follow-up session before treating this as fully confirmed.
