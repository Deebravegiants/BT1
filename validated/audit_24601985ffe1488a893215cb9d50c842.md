## Title
Webhook `shop`/`topic` fields are not covered by the HMAC signature yet are trusted by `Registry.process`, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body HMAC and then hands the header-derived `shop` straight to the app's handler as if it were verified, breaking the intended binding between "this request passed HMAC verification" and "this request is for shop X."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from attacker-controllable headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` only checks the body HMAC, then dispatches using the unverified `request.shop`: [3](#0-2) 

`HmacValidator.validate` proves the *body bytes* were signed with the app's `api_secret_key`, but that secret is shared by the app across **every** installed shop — it is not shop-specific. Since the signature never covers the `shop-domain` header, a valid `(body, hmac)` pair obtained from a webhook for one shop remains valid when replayed with a different `shop-domain` header value. This is the same class of bug as the reported `ACLFacet.updateRoleGroup()` issue: a check exists (`require`/`HmacValidator.validate`) but it does not cover the actual field that downstream code trusts and acts on (`_group` / `shop`), so the check can be satisfied while the acted-upon value is attacker-controlled.

The broken identity binding, stated as an equality that the code assumes but never enforces:
`shop used by handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` == `shop that Shopify actually generated/signed this body for`.

### Impact Explanation
An attacker who has legitimately installed the target app on their own (even free/dev) store can trigger a webhook, capturing a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`. They can then POST that same body/HMAC to the app's public webhook endpoint while setting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to an arbitrary victim shop's domain. Because `Registry.process` never revalidates that the header-derived shop matches anything cryptographically bound to the payload, the app will process attacker-supplied webhook data (e.g., order/product/customer payloads) as if it belongs to the victim shop — a cross-tenant confusion that can corrupt or leak data associated with another merchant, satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the app on any shop (including their own trial/dev store, which is typically open to anyone) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed. This is a realistic, unprivileged-internet-user path.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed content that `HmacValidator` verifies, or require the host application to independently confirm that `request.shop` corresponds to a shop with an active session/installation before trusting it, rather than presenting these header values as already-trustworthy fields of a "verified" `Request` object. At minimum, document clearly that `shop` is unauthenticated and must be cross-checked by the caller against known installed shops.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends (valid against the app's `api_secret_key`).
3. Replay this exact body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `@raw_body`; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) then invokes the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-controlled data under the victim's tenant.
