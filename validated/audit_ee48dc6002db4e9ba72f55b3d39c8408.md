## Finding [1](#0-0) 

### Title
Webhook `shop` identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`/`webhook-id`) values used by the app's webhook handler come from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

but `#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to that body: [3](#0-2) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate`, which only checks `verifiable_query.to_signable_string` (i.e. the body) against `verifiable_query.hmac`: [4](#0-3) 
It then immediately trusts `request.shop` and hands it to the app's handler as authenticated tenant identity: [5](#0-4) 

Critically, the secret used for HMAC verification, `Context.api_secret_key`, is a single app-wide secret, not a per-shop secret: [6](#0-5) 

This means any valid `(body, hmac)` pair generated by Shopify for *any* shop installed on the app — including a shop fully controlled by an attacker (e.g. their own free development store with the app installed) — will pass HMAC validation for *every other* shop, because the `shop` header is never part of the signed content. An attacker who controls a shop that has the merchant app installed can capture one legitimate webhook delivery (valid body + hmac for their own shop), then replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will accept it (same secret, same body/hmac), and `Registry.process` will pass `WebhookMetadata.new(shop: request.shop, ...)` — with the attacker-chosen shop — to the app's handler, allowing forged webhook events to be injected under a *different* tenant's identity.

Contrast this with `Auth::Oauth::AuthQuery`, which correctly binds `shop` into the signed content used for OAuth callback verification: [7](#0-6) 
No equivalent binding exists for the webhook `shop` field, which is the asymmetry described in the report's bug class (field acted upon but not covered by the integrity check).

### Impact Explanation
This breaks the identity binding `shop_authenticated == shop_used_by_handler`. It enables cross-tenant webhook injection: an attacker with access to one shop's install of the app (unprivileged relative to any *other* merchant) can produce HMAC-valid webhook payloads attributed to a victim shop domain of their choosing. Depending on how the app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up/update per-shop records, trigger per-shop side effects, or associate data), this can result in cross-tenant data corruption or unauthorized actions performed against another merchant's tenant — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on a shop they control (a normal, unprivileged action available to any Shopify developer/merchant) and to be able to reach the app's public webhook endpoint — both realistic preconditions for any embedded Shopify app. No possession of `api_secret_key` or any victim credential is required; the attacker only needs one legitimate `(body, hmac)` pair produced for their own shop.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed content verified for webhooks, or otherwise cryptographically tie the header-derived shop identity to the signature (for example, by requiring the receiving app to independently confirm the shop against a session/install record rather than trusting the header value alone). At minimum, document that `request.shop` is untrusted, and update `HmacValidator`/`Webhooks::Request` so the HMAC check covers the full set of Shopify-provided identity headers, not just the body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event, capturing the legitimate raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (both computed by Shopify against the app's shared `api_secret_key`).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses this into a request whose `hmac` is `H` and `to_signable_string` is `B`; `Utils::HmacValidator.validate` recomputes the signature over `B` with the app-wide secret and it matches `H`, so validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and invokes the app's handler, which now processes attacker-controlled data as if it belongs to `victim-shop.myshopify.com`. [5](#0-4)
