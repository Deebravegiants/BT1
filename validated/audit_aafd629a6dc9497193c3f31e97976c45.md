### Title
Deposit rounds shares down to zero, silently accepting principal with no shares minted - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
The `deposit` function in every Zest vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) computes shares via `convert-to-shares-preview`, which performs a floor-division (`mul-div-down`), but never asserts the resulting `inkind` (shares) is non-zero before minting and accepting the underlying transfer. The symmetric `redeem` function *does* enforce this invariant (`ERR-OUTPUT-ZERO`), but `deposit` does not, breaking the identity that "assets received by the vault == backing for shares minted."

### Finding Description
`convert-to-shares-preview` in `mainnet/contracts/vault/v0-vault-stx.clar` (lines 308-315) computes:

```
(mul-div-down amount ts ta)
```

which is `(amount * ts) / ta` using integer (floor) division. Once the share price (`ta`/`ts`) rises above `1` (which happens as soon as any interest has accrued via `accrue`, since `total-assets` grows while `total-supply` stays roughly fixed), any `amount` such that `amount * ts < ta` will floor to `0`.

`deposit` (lines 763-795) then does:

```
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)   ;; passes trivially if min-out is 0
...
(try! (receive-underlying amount account))    ;; pulls in the real underlying
(try! (ft-mint? zft inkind recipient))        ;; mints 0 shares - succeeds
(var-set assets (+ current-assets amount))    ;; assets accounting still increases
```

There is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` guard, unlike `redeem` (line 811 of the same file):

```
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```

Because `ft-mint?` of `0` succeeds and `min-out` defaults to (or can simply be passed as) `0`, a caller depositing an `amount` small enough to floor to zero shares under the current share price has their underlying fully pulled into the vault (`assets` incremented) while receiving **zero** `zft` shares in return — with no revert. This breaks the value identity: `assets contributed > 0` while `shares minted = 0`, i.e., principal is contributed but no claim on it is issued to the depositor, and it is effectively donated to all other existing shareholders.

### Impact Explanation
This causes permanent, silent loss (freezing/theft) of the depositor's principal: the underlying tokens are transferred out of the caller's control and recorded into vault `assets`, but the caller receives no `zft` shares and thus has no mechanism to redeem that value back. Because it happens without a revert, the caller has no on-chain signal that their deposit produced no shares (aside from `shares-minted: 0` in the printed event, which most integrators/UIs will not check). This is the deposit-side analog of the crowdfund `_processContribution` bug: a floor-rounding-to-zero code path that the symmetric function (redeem/refund) explicitly guards against but the mirrored function (deposit/contribute) does not.

### Likelihood Explanation
This is reachable by any unprivileged user, no DAO or admin involvement required, and requires no oracle or flashloan interaction. Reachability depends only on: (1) the vault's share price (`total-assets-preview`/`total-supply-preview`) having drifted above `1:1`, which happens naturally after any interest accrues, and (2) the caller sending a sufficiently small `amount` relative to that price (`amount < ta/ts`). Every vault instance is initialized 1:1 (`initialize` deposits `MINIMUM-LIQUIDITY` at parity), so the exposure window widens over time as the vault accrues interest and the effective share price rises — the smallest amount that can be lost this way shrinks in relative terms but is always achievable at the "amount = 1 base unit" boundary once price > 1.

### Recommendation
Add an explicit zero-output guard to `deposit`, mirroring `redeem`:

```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```

placed alongside the other `asserts!` in `deposit`, in every vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
1. Vault is initialized (`initialize`), setting `total-supply = total-assets = MINIMUM-LIQUIDITY`.
2. Time passes / borrow-repay activity accrues interest via `accrue`, so `total-assets-preview() > total-supply-preview()` (share price > 1).
3. A user calls `deposit(amount, 0, recipient)` with a small `amount` such that `(amount * total-supply-preview) / total-assets-preview == 0` (floor rounding).
4. `deposit` passes all `asserts!` (`amount > 0`, `inkind >= min-out=0`, supply cap not exceeded), pulls `amount` of underlying from the user via `receive-underlying`, mints `0` shares via `ft-mint? zft 0 recipient`, and increments `assets` by `amount`.
5. The call returns `(ok u0)` without reverting; the user has permanently lost `amount` of principal with no `zft` shares to reclaim it, while all other vault shareholders benefit from the increased `assets` backing their existing shares. [1](#0-0) [2](#0-1) [3](#0-2)

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))

        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
