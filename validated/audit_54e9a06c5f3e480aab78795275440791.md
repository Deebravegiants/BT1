### Title
Bad-debt write-down clamps `supply_index` to `SUPPLY_INDEX_FLOOR` instead of zeroing supply shares, resurrecting wiped suppliers' phantom claims that drain fresh deposits - ([File: contracts/pool/src/interest.rs])

### Summary
The TDengine report is an integer underflow that produces a wrong result (size underflow → crash). The analog in XOXNO Lending is a subtraction/clamp that produces a wrong *bounded* result instead of the correct zero: when `apply_bad_debt_to_supply_index` socializes a full wipeout, `remaining` underflows to zero economically, but the code clamps the new supply index *up* to `SUPPLY_INDEX_FLOOR_RAW` (RAY/1000). Every pre-wipeout scaled supply share keeps a nonzero claim (1/1000 of its last value) that the protocol never backed with cash, and that claim is paid out of the next depositor's tokens.

### Finding Description
`apply_bad_debt_to_supply_index` in `contracts/pool/src/interest.rs:73-89` computes `remaining = total_supplied_value - min(bad_debt, total_supplied_value)`, derives `reduction_factor = remaining / total_supplied_value`, and sets `supply_index = max(supply_index * reduction_factor, SUPPLY_INDEX_FLOOR_RAW)`. When `bad_debt >= total_supplied_value` (a complete wipeout), `remaining = 0`, so the economically correct index is 0 — but the floor clamp revives it to RAY/1000. Because positions store raw `scaled_amount` shares (never reset), all wiped suppliers retain `scaled_amount * RAY/1000` of claim.

The seize path reaches this: `ops/seize.rs:24-28` maps `AccountPositionType::Borrow` entries to `unscale_borrow_ceil_ray(position)` → `apply_bad_debt_to_supply_index` → `burn_debt`. `clean_bad_debt` is a permissionless controller entrypoint that emits `PoolSeizeEntry` records for both sides (`bad_debt.rs:14-49`), so any address can trigger the socialize-and-clamp once an account carries dust bad debt. `Deposit` entries call `absorb_supply_as_revenue` — the victim's own shares are reclassified to revenue only when that account is cleaned; *other* suppliers' shares in the same hub market keep their phantom claim.

The repo's own test proves the drain: `contracts/pool/tests/interest.rs:372-427` (`test_raw_cache_floor_clamp_strands_claim_without_supply_guard`) shows a wiped supplier's `old_scaled` resolves to a positive `gross` withdrawal that equals a fresh depositor's full `fresh_cash`, leaving the pool unable to cover the fresh claim. The test name flags that the loss is currently masked only by `require_reserves`/liquidity guards — i.e., the phantom claim is real state, held in check by guards rather than by correct accounting.

### Impact Explanation
Theft of user funds / protocol insolvency. After a bad-debt event that exceeds total supplied value (e.g., a sharp oracle move on a thin market, or deliberately engineered dust bad debt in an illiquid hub book), the clamped index leaves stranded claims. The first fresh deposit into that market is withdrawable by the phantom claimant via `withdraw` (`resolve_withdrawal(i128::MAX, old_scaled)` burns shares and pays the floored balance). The pool's cash then cannot cover the honest depositor — an effective transfer of the new supplier's tokens to the wiped position holder, and a permanent backing shortfall (`backing_shortfall` in `guards.rs:61-66` becomes positive).

### Likelihood Explanation
Reachable by a single unprivileged address: create underwater debt (own position liquidated partially, leaving residual bad debt below cleanup dust thresholds, or in a market where debt value briefly exceeds supplied value), then call `clean_bad_debt` — permissionless per the in-scope entrypoint list. No auth is required on the pool seize call (it is invoked by the controller). Exploitation requires a wipeout-scale bad-debt event, which is uncommon in deep markets but feasible in thin/newly listed hub assets or via self-liquidation chains. Severity capped by the fact that the loss lands on whoever supplies next into the affected market; guards (`require_reserves`, `require_backed_market`) may revert the payout until fresh cash arrives, converting the bug into theft of the *next* deposit rather than existing cash — still a qualifying impact.

Uncertain: I could not fully confirm whether `clean_bad_debt` imposes a dust-threshold or full-wipeout precondition that prevents reaching the `remaining == 0` branch while `supplied > 0`. If cleanup is gated such that the clamp branch is unreachable, likelihood drops; the unit test, however, exercises the clamp on a cache state that mirrors real post-seize state.

### Recommendation
In `apply_bad_debt_to_supply_index`, when `remaining == Ray::ZERO` (full wipeout), zero the supply index *and* the aggregate `supplied`/`revenue` share counters rather than clamping to `SUPPLY_INDEX_FLOOR_RAW`. Alternatively, keep the floor but rewrite surviving positions' `scaled_amount` to zero in the same socialize pass, so no share can ever unscale to a positive claim against an index that no longer represents real backing. Add an invariant: `supply_index` below the floor is only legal when `supplied == 0`.

### Proof of Concept
The repo already contains the demonstration — `test_raw_cache_floor_clamp_strands_claim_without_supply_guard` at `contracts/pool/tests/interest.rs:372-427`:

1. Market state: `supplied = 1000*RAY` shares, `supply_index = RAY`, cash = 0, then `apply_bad_debt_to_supply_index(cache, 5000*RAY)` (debt exceeds supply → wipeout).
2. Assert `supply_index == SUPPLY_INDEX_FLOOR_RAW` — the clamp resurrects the index instead of zeroing shares; `unscale_supply_floor(old_scaled) > 0` (phantom claim).
3. A fresh supplier deposits `fresh_cash = stranded`; `mint_supply` + `credit_cash`.
4. Wiped holder calls withdraw-all: `resolve_withdrawal(i128::MAX, old_scaled)` returns `gross == fresh_cash`; after `burn_supply`/`debit_cash`, `cash < fresh_claim` — the fresh deposit is gone.

On-chain path: `controller.clean_bad_debt(account_id)` → `pool_seize_positions_call` → `seize::apply` (Borrow entry) → `apply_bad_debt_to_supply_index` → clamp; then `controller.supply` (victim) and `controller.withdraw(0)` (phantom claimant) settle through `resolve_withdrawal`/`require_reserves` in `contracts/pool/src/ops/withdraw.rs`.
