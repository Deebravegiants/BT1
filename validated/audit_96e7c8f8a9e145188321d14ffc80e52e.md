## Finding

### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, `api_version`, and `webhook_id` values pulled from HTTP headers — none of which are covered by that signature — and hands them to the app's handler as the tenant identity for the event.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (i.e., the raw body) against `request.hmac`. It never checks that `request.shop` is bound to that signature. It then immediately trusts `request.shop` as the tenant identifier passed into the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and the app's `api_secret_key`/`old_api_secret_key`: [4](#0-3) 

This is the same bug class as the report's root cause — a value that is *acted upon* (here, the `shop` tenant identity used to dispatch/attribute the webhook) is not *covered by the integrity check* (the HMAC), so the two are silently allowed to diverge, exactly analogous to "a field acted on but not covered by the HMAC" from the rules.

Because a single app's `api_secret_key`/`client_secret` is shared across every shop that installs the app, any merchant who installs the app on their own store receives genuinely-signed webhooks for their own shop (valid `hmac` over a real raw body). Since the `shop` header is not part of the signed content, that same merchant can replay the intercepted `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` / `x-shopify-shop-domain` header to name an arbitrary other shop. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` forwards the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler to act on.

### Impact Explanation
This breaks the tenant boundary the app relies on: `verified-signature shop == handler-trusted shop` is not actually enforced — it should be but isn't. An app that uses `WebhookMetadata#shop` to write/update per-tenant records (as documented and expected usage of this gem) can be made to attribute or apply another shop's webhook payload to a shop the attacker does not own, i.e., cross-tenant data injection/corruption via a value the gem itself hands to the host application as trustworthy. This matches the High-impact category of cross-tenant access via a bypassed identity-binding check.

### Likelihood Explanation
Any developer/merchant who can install the target app on a shop they control automatically has a valid `(raw_body, hmac)` pair for real webhook topics without needing the app's `client_secret` — they only need to observe traffic to their own webhook endpoint, which is normal usage. Forging the header value is trivial once a valid raw_body/hmac pair for any topic is known. No secret material, TLS interception, or social engineering is required beyond controlling one's own installed shop, satisfying the scope constraints.

### Recommendation
Bind the tenant identity to the signed content instead of trusting headers independently of the HMAC. For example, include `shop` (and ideally `topic`/`webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop domain to the signature (e.g., require the host application to additionally verify `request.shop` against the shop associated with the session/subscription that the webhook was registered for) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger a real webhook (e.g., `orders/create`) and capture the raw POST: headers (including `x-shopify-hmac-sha256` and `x-shopify-shop-domain: attacker-shop.myshopify.com`) and raw body.
2. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change `x-shopify-shop-domain` (and/or `shopify-shop-domain`) to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only the raw body against the HMAC — validation succeeds because the body/HMAC pair is unmodified: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload never originated from Shopify for that shop: [6](#0-5)
