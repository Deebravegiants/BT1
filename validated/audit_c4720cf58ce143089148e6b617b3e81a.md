## Title
Native-fee dispatch swaps in `EvmHost` use no minimum-price protection, letting anyone sandwich a dispatcher's ETH-to-feeToken swap - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost::dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all convert native ETH sent with the call into the protocol's `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, executed unconditionally against the live pool at whatever price exists at execution time. Because any address can trigger this swap (it fires whenever `msg.value > 0`) and the swap has no price bound beyond the caller's own `msg.value`, an attacker can sandwich a victim's dispatch transaction to inflate the AMM price immediately before it executes, extracting the value from the buffer the caller included over the on-chain quote — the same "swap at any price" abuse pattern described in the reference report, just applied to `EvmHost`'s own fee-conversion path instead of `Vault::claimTokens`.

### Finding Description
`EvmHost::dispatch(DispatchPost)` performs this conversion: [1](#0-0) 

The identical pattern repeats for GET requests and for topping up an existing request's relayer fee: [2](#0-1) [3](#0-2) 

`swapETHForExactTokens(post.fee, path, address(this), block.timestamp)` fixes only the *output* amount (`post.fee`); the maximum acceptable input is implicitly `msg.value`. Any caller wanting the transaction to succeed under normal (non-manipulated) conditions must send `msg.value` with some slippage buffer above the currently quoted input, because the on-chain quote used by callers (`HyperApp.quote()`) is explicitly documented as unsafe if relied on too tightly and is meant for off-chain estimation only: [4](#0-3) 

The docs even confirm the intended flow is "user sends enough native tokens... The Host will swap native -> feeToken via Uniswap" and separately warn that `quote()` "uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks": [5](#0-4) [6](#0-5) 

Because the swap is a standard, unprotected V2 exact-output swap executed at whatever spot price the pool has at inclusion time, an attacker watching the mempool can:
1. Front-run with a buy that pushes the WETH→feeToken price up.
2. Let the victim's `dispatch{value: msg.value}(...)` execute, consuming more of the victim's supplied ETH buffer than the true market price would require (up to the full `msg.value`) to obtain the same fixed `post.fee` output.
3. Back-run to sell and capture the price impact as profit — a textbook sandwich, extracting value directly from whatever slippage margin the dispatcher included.

The same unguarded `swapETHForExactTokens{value: msgValue}` call is repeated in `IntentGatewayV2::placeOrder`'s native-fee escrow path, so the issue is systemic across every entry point that lets a caller pay Hyperbridge protocol fees in native token: [7](#0-6) 

This directly parallels the reported bug class: a publicly triggerable function performs an AMM swap with no minimum-output/maximum-slippage guard beyond the caller's own naive input, letting anyone sandwich it to skim value.

### Impact Explanation
Any user or contract that dispatches an ISMP POST/GET request or funds a request using native ETH (a normal, documented usage path) is exposed to MEV extraction on the ETH they send for fee conversion. Since real-world integrations must send a buffer above the exact quoted amount to tolerate normal price drift and avoid reverts, that buffer becomes free money for sandwichers, and it recurs on every native-fee dispatch across every deployment of `EvmHost` and `IntentGatewayV2`. This is a genuine, repeatable value-extraction vector against the core dispatch path (in-scope per the reachable "EvmHost ... dispatch and delivery" primitive), meeting the Medium bar of concrete value loss to protocol users.

### Likelihood Explanation
High likelihood: dispatching with native token is a first-class, publicly documented flow (`dispatch{value: msg.value}(...)`), requires no special privileges, and sandwiching a pending mempool transaction against a known, low-liquidity WETH/feeToken V2 pool is a well-understood and automatable MEV strategy. Every dispatch that supplies any slippage buffer is a candidate victim.

### Recommendation
Do not let `EvmHost` (or `IntentGatewayV2`) perform an unguarded on-chain swap sized only by the caller's `msg.value`. Instead:
- Require callers to pass an explicit `amountInMax` (or equivalently compute and enforce a maximum acceptable input derived from a TWAP/oracle price with a small configured buffer) and pass that as the true bound to `swapETHForExactTokens`, reverting if the market has moved unfavorably beyond the buffer.
- Alternatively, refund any leftover `msg.value` precisely and price fee conversion off a manipulation-resistant oracle (e.g., Uniswap V3 TWAP or Chainlink) rather than the instantaneous V2 spot price, consistent with the original report's recommendation.

### Proof of Concept
1. Attacker monitors mempool for a `dispatch{value: v}(DispatchPost{... fee: F ...})` call where `v` is comfortably above the currently quoted `getAmountsIn(F, [WETH, feeToken])[0]` (a normal safety buffer).
2. Attacker front-runs with a large WETH→feeToken buy on the same V2 pool referenced by `_hostParams.uniswapV2`, moving the price so that the ETH input required to receive exactly `F` feeToken rises toward `v`.
3. Victim's transaction executes `swapETHForExactTokens{value: v}(F, path, address(this), block.timestamp)` inside `EvmHost.dispatch`, consuming close to the full `v` instead of the pre-manipulation quote, leaving little/no refund headroom that the victim expected.
4. Attacker back-runs, selling feeToken back for WETH, capturing the price-impact spread as profit — funds effectively taken from the value the honest dispatcher would otherwise have retained.
