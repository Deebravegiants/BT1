### Title
Webhook shop-domain identity spoofing via unauthenticated header — cross-tenant webhook forgery ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then trusts the `shop` value taken from an unauthenticated HTTP header to identify the tenant the webhook belongs to. Because the HMAC signature never covers the shop-domain field, and because the same `api_secret_key` is shared across every merchant that installs the app, any merchant who has legitimately installed the app can produce a validly-signed webhook body and relabel it as belonging to a different merchant (tenant), breaking the shop-identity binding the host application relies on.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other request fields — `topic`, `shop`, `api_version`, `webhook_id` — are read straight from HTTP headers without any cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac` field, using `Context.api_secret_key`, which is the single secret shared by the app across all installed shops: [3](#0-2) 

`Webhooks::Registry.process` performs exactly that check and then builds the `WebhookMetadata` passed to the app's handler using the unauthenticated `request.shop`: [4](#0-3) 

The binding the gem is expected to enforce is:
```
HMAC(raw_body, api_secret_key) valid  ⇒  (topic, shop, webhook_id, api_version) are exactly what Shopify sent
```
In reality the equality that actually holds is only:
```
HMAC(raw_body, api_secret_key) valid  ⇒  raw_body is unmodified
```
`shop` (and `topic`/`webhook_id`/`api_version`) are outside the signed scope, so `request.shop == data.shop` used by the handler is not authenticated at all — it is attacker-controlled header data that is merely parsed and forwarded.

### Impact Explanation
Because `api_secret_key` is one value per app (not per shop), any merchant who has installed the app can trigger a legitimate webhook for their own store, capture its `raw_body` + valid `X-Shopify-Hmac-Sha256`, and replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it only checks the body), and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain. If the app's webhook handler uses `data.shop` — as the gem's own model and documentation encourage — to select which tenant's records to update (a standard, expected usage pattern for this gem), an attacker can inject forged webhook content attributed to another merchant's tenant, causing cross-tenant data corruption/injection. This satisfies the "Critical – cross-tenant access" impact bucket: the identity binding between an authenticated payload and the tenant it is attributed to is broken by design in this library's webhook verification path.

### Likelihood Explanation
Exploitation requires only that the attacker be an ordinary merchant who has installed the target app (no special privilege, no access to `api_secret_key`, no TLS interception) — they merely need one legitimate webhook delivery from their own shop and the ability to POST to the app's public webhook endpoint with a modified header. This is trivially achievable for any unprivileged internet user who onboards as a customer/merchant of the app, which matches the required unprivileged-attacker threat model. The library's `Webhooks::Registry`/`Request`/`HmacValidator` code offers no secondary binding of `shop` to the signed content, so the gate is purely on header value spoofing.

### Recommendation
Include the shop-domain (and ideally topic/webhook_id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is handed to `WebhookMetadata`/handlers — e.g., verify that the shop asserted in the header matches a shop for which the raw body's content was actually produced (such as validating that the webhook's declared shop matches records already known via OAuth for that installation, or requiring the app to cross-check `shop` independently rather than trusting the gem's `WebhookMetadata#shop`). At minimum, the gem's documentation/API should make explicit that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant-selection key without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate install, offline access token like any other merchant).
2. Attacker triggers any event (e.g., creates an order) causing Shopify to deliver a webhook to the app's endpoint with body `B` and a valid `X-Shopify-Hmac-Sha256` header computed as `HMAC-SHA256(api_secret_key, B)`.
3. Attacker intercepts/replays this exact request but changes only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`, keeping body `B` and the HMAC header unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: spoofed_headers)` is built; `Utils::HmacValidator.validate(request)` returns `true` since it only re-hashes `B`.
   - Corresponding code paths: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body, ...)`. The app's handler processes/records the attacker-controlled payload `B` under the victim shop's tenant context, achieving cross-tenant data injection without ever needing the victim's credentials or the app's `api_secret_key`.
