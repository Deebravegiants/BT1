### Title
Webhook Shop Domain Spoofing via Unsigned Header Breaks Tenant Isolation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (merchant identity) is read from an unsigned HTTP header. Because the HMAC secret (`api_secret_key`) is shared across every shop that has installed the app, any shop that can produce one valid `(raw_body, hmac)` pair for its own webhook can replay that same pair while swapping the `x-shopify-shop-domain` header to a victim shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic for the victim.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` reads the shop identity straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the received HMAC purely against `to_signable_string` (i.e., the raw body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate(request)` passes, then dispatches to the handler using `request.shop` taken from the same unauthenticated header: [4](#0-3) 

The identity binding that is broken, expressed as an equality that should hold but doesn't:
`HMAC(api_secret_key, raw_body)` is verified, but `shop_header` is never included in the signed material, so the binding `shop_header == shop_that_the_secret_authenticates` is never enforced. Since `api_secret_key` is a single app-wide secret shared by every merchant that installs the app (not a per-shop secret), any tenant of the app can generate a self-consistent `(raw_body, hmac)` pair (e.g., by triggering a real webhook to their own endpoint under their own shop) and then re-submit that exact `raw_body` + `hmac` to the host application's webhook endpoint with the `x-shopify-shop-domain` header changed to point at a different, victim shop. The signature still validates because it never covered the shop field, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is merely a legitimate (or trial) installer of the app can make the host application process arbitrary webhook payloads under another merchant's shop identity. Depending on how the host app's webhook handlers use `data.shop` (e.g., to look up/act on merchant records, trigger `shop/redact`/`customers/redact`/`customers/data_request`-style side effects, or update per-tenant state), this can lead to cross-tenant data corruption, unauthorized data deletion, or data leakage attributed to the wrong shop — matching the Critical "cross-tenant access" impact category, since tenant isolation is enforced entirely by this unauthenticated header rather than by the HMAC.

### Likelihood Explanation
Any actor able to install the app on their own shop (a normal, unprivileged action for a public/dev app) can capture a valid `(raw_body, hmac)` pair from their own legitimate webhook deliveries and replay it with a modified shop header — no access token, `client_secret`, or privileged credential is required beyond ordinary app installation.

### Recommendation
Include the shop domain (and other identity-determining fields such as topic/api-version if relied upon) inside the HMAC-signed payload comparison, or independently verify that the `x-shopify-shop-domain` header matches a shop that is actually associated with the delivered `webhook_id`/registration before dispatching to handlers. At minimum, document that host applications must not trust `request.shop` for authorization decisions without additional verification, and/or bind it into `to_signable_string`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers any webhook topic.
2. Shopify delivers a legitimate webhook to the attacker's endpoint: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(api_secret_key, B)`, header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker resends the exact same `raw_body = B` and the exact same `hmac` header to the target host application's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, B)` — identical to the received value — and returns `true`, since the shop header is not part of the signed string.
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))`, causing the host app to process the attacker-controlled payload under the victim's tenant identity.
