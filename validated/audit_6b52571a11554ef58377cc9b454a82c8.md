### Title
Unvetted route-pool code executes under the caller's authorization tree in controller swap strategies, enabling wallet draining via a poisoned signed auth tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The CVE-2017-10114 class — untrusted code executing inside a trusted security context (Java sandbox escape) — maps onto XOXNO Lending's strategy paths: user-supplied `swap` bytes are forwarded to the configured router, which invokes arbitrary pool/token contract addresses named inside the payload. That third-party code runs on the call stack *below the victim's authorization*, and any `require_auth`-protected call it makes (e.g. `token.transfer(victim, attacker, ...)`) is recorded by simulation as a child of the victim's auth entry and executes if the victim signs the simulated tree. Neither the controller's scoped input-transfer grant, the router's `min_out` check, nor the final account risk gates bound this loss.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs` (lines 33–38) authorizes exactly one `token_in.transfer(controller, router, amount_in)` invoker-auth entry and calls `router.execute_strategy(controller, amount_in, swap)` under the flash guard, then only measures the controller's own input/output balance deltas (`RouterOverspend`, `NoSwapOutput`). The route bytes — the pool addresses each hop calls — come entirely from the caller-supplied `swap` argument of `swap_collateral` / `swap_debt` / `multiply` / `repay_debt_with_collateral` (`contracts/controller/src/lib.rs:283-303`, `swap_collateral.rs:55-65`).

The router keeps no allowlist of pool/token addresses: `Program::decode` validates only byte format and indices, and `dispatch_hop` (`venues/mod.rs:34-40`) invokes whatever pool address the payload names. `docs/explanation/threat-model.md:154-165` confirms the consequence: route-named third-party code sits on the stack below the caller's authorization; a `transfer` it initiates from the caller is recorded as a child of the caller's auth entry and executes when the caller signs that tree. Because standard wallet flows copy the simulator-produced auth tree into the transaction, a victim signing what appears to be a normal `swap_collateral` silently authorizes a wallet-token transfer to the attacker — the exact "untrusted code escapes its sandbox by riding on trusted authority" shape of the CVE.

The pinned harness test proves both halves: `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` and `enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer` (`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-269`) show a `RogueHopPool` named by the route draining the caller's unrelated wallet token balance when the recorded tree is signed.

### Impact Explanation
Theft of user funds beyond the routed amount: the rogue pool can transfer *any* token the victim holds (not just `token_in`/`amount_in`) to an attacker address. The loss is bounded only by the victim's wallet balances, not by `total_in`, `min_out`, or account risk checks. This directly satisfies "theft of user funds." Severity: High (CVSS-like profile AV:N/AC:H/PR:N/UI:R, matching the source CVE's user-interaction requirement).

### Likelihood Explanation
Requires an unprivileged attacker to get a victim to submit a controller strategy call carrying the attacker's route (phishing UI, compromised/malicious quote path, or a front-end serving crafted `routeXdr`) and to sign the simulated auth tree without inspecting child invocations. The controller performs no venue validation that would reject such a payload, and the router deliberately trusts payload-named addresses, so no protocol-side check stands in the way — the only defenses are client-side tree inspection, which the threat model itself states users must perform.

### Recommendation
Validate route structure server-side/contract-side rather than relying on the signer to detect poisoned auth trees. Concretely: enforce a governance-managed allowlist of venue pool contracts in the controller or router (mirroring `INV-STRAT-03`'s approved-pool model for Blend), or have the router reject payloads whose pool/token addresses are not registered venues. Until then, wallets/SDKs building these transactions should refuse to sign any auth tree whose root (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or `execute_strategy`) has children other than the single expected input `transfer`.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. Attacker deploys `RogueHopPool` whose `swap()` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` (lines 51-72).
2. Victim calls `controller.swap_collateral(alice, account_id, usdc, amount, eth, route)` where `route.hop_pool` is the rogue pool (lines 147-164); the router pays fair output so all controller checks pass.
3. Simulation records `wallet_token.transfer(alice → attacker)` as a child of Alice's `swap_collateral` auth entry (lines 206-222); signing that tree executes the theft — `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE` (lines 265-268).
