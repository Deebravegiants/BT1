Audit Report

## Title
Bearer/JWT authentication token logged in plaintext via Debug-level request logging in the Vault gateway handlers - (File: core/services/gateway/handlers/vault/handler.go)

## Summary
Both the public/connector-facing Vault gateway handler and the OCR-plugin-facing Vault gateway handler log the full `jsonrpc.Request[json.RawMessage]` object at Debug level before authorization occurs. This object carries the caller-supplied bearer/JWT token in its `Auth` field, confirmed by system-test code that extracts `jsonRequest.Auth` and sets it as `Authorization: Bearer <token>`.

## Finding Description
`core/services/gateway/handlers/vault/handler.go:403` logs the entire inbound request via `h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)` prior to any authorization check. [1](#0-0) 

Similarly, `core/capabilities/vault/gw_handler.go:182` logs `reqLggr.Debugw("received message from gateway", "req", req)` on message receipt, and line 231 logs the full outgoing response object with `reqLggr.Infow("Sent message to gateway", "resp", response)` (note: this second one is `Infow`, not `Debugw`, making it enabled by default rather than gated behind debug level). [2](#0-1) [3](#0-2) 

By contrast, the authorization pipeline in `gateway_vault_request_processor.go` deliberately avoids logging the raw token, logging only `req.Auth != ""` as a boolean `hasAuth` field, demonstrating the developers were aware credentials should not be logged raw. [4](#0-3) 

The system tests confirm `jsonRequest.Auth` is a live bearer/JWT token used for HTTP `Authorization: Bearer <token>` headers, and that tests explicitly strip it via `outboundRequestWithoutAuth` before further use — an internal acknowledgment elsewhere in the codebase that this field is sensitive and must not be passed around unredacted. [5](#0-4) 

I could not locate the `jsonrpc.Request`/`Response` struct definitions in this repo's index — they come from an external dependency module (chainlink-common-style) not included in this index — so I cannot confirm whether these types implement a custom `String()`/`MarshalJSON()`/`LogValue()` method that might redact `Auth` when passed to a structured logger's `%v`/`%+v` formatting. This is a genuine gap in my verification: if such a redaction method exists on the type, the `Debugw("...", "request", req)` calls might not actually leak the raw token even though the struct field is populated. The claim's author raised the same caveat.

Assuming no such redaction method exists (consistent with the fact that the codebase elsewhere manually avoids logging `req` and instead logs a `hasAuth` boolean — behavior that would be redundant if the struct redacted itself), the log statements do write the plaintext token to log output when Debug logging is enabled.

## Impact Explanation
If confirmed (i.e., if `jsonrpc.Request`/`Response` do not self-redact `Auth`), enabling Debug-level logging on a node/gateway running the Vault capability would cause a caller's bearer/JWT authentication token to be written verbatim to logs. Anyone with read access to those logs could extract and replay the token to impersonate the original caller for `SecretsCreate`/`SecretsUpdate`/`SecretsDelete`/`SecretsList` operations — a credential-disclosure and gateway request impersonation vector, which is an in-scope Chainlink impact category.

## Likelihood Explanation
The exposure is gated entirely behind Debug-level logging being enabled, which is not the production default; `Infow("Sent message to gateway", "resp", response)` at line 231, however, runs at the default `Info` level and is not gated at all, which increases realistic likelihood for that specific line since Debug logging need not be enabled for it to fire. Exploitation additionally requires the attacker to have read access to node/gateway logs (log aggregation, support bundles, or shared log infrastructure) — this is not something an unprivileged network client can trigger by itself; log access is a separate precondition outside the caller's control.

## Recommendation
- Remove the raw `req`/`request`/`resp` struct from the `Debugw`/`Infow` calls in `core/services/gateway/handlers/vault/handler.go:403` and `core/capabilities/vault/gw_handler.go:182,231`.
- Replace with an explicit minimal field list (`method`, `requestID`, `hasAuth`), matching the pattern already used correctly in `gateway_vault_request_processor.go:270-276`.
- If feasible, add a `LogValue()`/custom `MarshalJSON` to the `jsonrpc.Request`/`Response` types (in the shared dependency) that redacts `Auth` by default, so future ad-hoc logging of the whole struct is safe.

## Proof of Concept
1. Start a chainlink node/gateway with the Vault capability enabled and `Log.Level = 'debug'`.
2. Send an authorized `SecretsCreate` request to the gateway with `Authorization: Bearer <token>`, as constructed in `sendVaultSignedOCRRequestToGateway` (`system-tests/tests/smoke/cre/vault_don_test_helpers.go:547-559`).
3. Inspect gateway/node logs for the lines `"handling vault request", ..., "request", req` and `"received message from gateway", "req", req"` / `"Sent message to gateway", "resp", response"`, and check whether the plaintext `Auth` value appears in the emitted log line.
4. This step should be executed by a Devin session with full dependency access to confirm whether `jsonrpc.Request`/`Response`'s default `%v` formatting exposes `Auth` in plaintext or whether a redaction mechanism in the dependency already prevents this — this determines whether the finding is a true positive.
