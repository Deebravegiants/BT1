### Title
Dispatch fee payment trusts unguarded Uniswap V2 spot price, enabling sandwich extraction from native-token dispatchers - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` convert a caller's native-token payment into the protocol `feeToken` by calling `swapETHForExactTokens` directly against a single Uniswap V2 pool (`_hostParams.uniswapV2`), with no TWAP, no Chainlink-style oracle, and no deviation guard. `HyperApp.quote()` prices the same swap via `getAmountsIn` on the identical pool. This is the same bug class as the reported finding: relying on a manipulable AMM spot price (Uniswap V2 reserves) as the sole pricing source for a value-bearing operation.

### Finding Description
In `EvmHost.dispatch(DispatchPost)`: [1](#0-0) 
the contract builds a `[WETH, feeToken]` path and calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. The identical unguarded pattern is repeated in `dispatch(DispatchGet)` [2](#0-1)  and in `fundRequest()` [3](#0-2) .

`HyperApp.quote()` — the function every `HyperApp` integrator (including `HyperFungibleToken`) calls to price a dispatch in native token before submitting it — uses the same pool via `getAmountsIn`, again with no bound or freshness check: [4](#0-3) 

Unlike `SimplexPaymaster`, which explicitly guards its Chainlink price feed against stale/non-positive answers (`_getOraclePrice` reverts on staleness) [5](#0-4) , the core dispatch path has no analogous protection: the price used to convert a user's native payment into `feeToken` is read live from a single AMM pool's reserves at execution time, with `swapETHForExactTokens`'s `msg.value` acting only as a maximum-input cap, not a deviation-from-reference check.

This is the exact bug class in the external report (`UniswapV2PoolTokenPrice.sol#L306`): the code acknowledges elsewhere that "the local uniswap router" is used for pricing (see the `dispatch()` NatSpec) but applies no protection against reserve manipulation via flash loans/sandwiching.

### Impact Explanation
Any account (an unprivileged dispatcher — including ordinary `HyperFungibleToken.send()` users, `TokenGateway` teleporters, or any `HyperApp` caller paying with native token) that calls `dispatch()`/`fundRequest()` with `msg.value` can be sandwiched: an attacker manipulates the `[WETH, feeToken]` pool's reserves immediately before the victim's transaction (front-run) so `getAmountsIn`/`swapETHForExactTokens` compute an inflated ETH requirement within the victim's `msg.value` slack, then reverses the manipulation after (back-run), extracting the price-impact spread from the victim's overpaid native token. Because there is no minimum-received/maximum-deviation guard tied to a trusted reference price, this is a direct value-extraction vector against Hyperbridge's own core message-dispatch fee payment mechanism — impacting every EVM deployment that has `_hostParams.uniswapV2` pointed at a low-liquidity or thinly-traded V2 pool (a common case for `feeToken`/WETH pairs on smaller EVM chains).

### Likelihood Explanation
Every dispatch that pays fees natively (a standard, frequently-used path — it is the default in `HyperFungibleToken.bridge()` and `TokenGateway`) is exposed. The precondition is simply a pool with reserves cheap enough to move within a single block/flash loan, which is realistic for the smaller-liquidity V2 pools Hyperbridge is deployed against on several supported chains. No privileged role is required; the attacker only needs capital for a flash-loan-funded sandwich, which is routine MEV infrastructure.

### Recommendation
Do not rely purely on the live spot reserves of a single Uniswap V2 pool for a value-bearing conversion. Either (a) bound the swap by a maximum acceptable deviation from a TWAP/Chainlink reference price (revert if spot price deviates beyond a threshold, mirroring `SimplexPaymaster._getOraclePrice`'s staleness/validity checks), or (b) use a TWAP-based quote for `getAmountsIn`/`swapETHForExactTokens` instead of instantaneous reserves, or (c) require `msg.value` to closely match a server-quoted amount with a small, explicit slippage tolerance rather than an unbounded "max input" semantics.

### Proof of Concept
1. Attacker identifies an EVM deployment of `EvmHost` whose `_hostParams.uniswapV2` points to a thin `[WETH, feeToken]` pool.
2. Attacker takes a flash loan and swaps into the pool to skew the WETH/feeToken price, front-running a pending victim transaction that calls `HyperFungibleToken.send()` (which calls `HyperApp.quote()` then `dispatch{value: nativeFee}(post)`), or a raw `dispatch()`/`fundRequest()` call with generous `msg.value`.
3. The victim's `dispatch()` executes `swapETHForExactTokens{value: msg.value}(post.fee, [WETH, feeToken], address(this), block.timestamp)` against the now-manipulated pool, consuming ETH from `msg.value` at the manipulated (unfavorable) rate — still succeeding as long as it stays under `msg.value`.
4. Attacker back-runs, reversing the pool skew and capturing the price-impact spread paid by the victim, net of flash-loan fees.
5. Repeated across many dispatches, this systematically extracts value from Hyperbridge users paying fees in native token, with no code path currently bounding or detecting the manipulation.

Note: I was not able to fully trace whether `EvmHost` has any `receive()`/native-fund-sweep logic to confirm a secondary "stuck ETH" sub-issue (refund-to-`address(this)` on `swapETHForExactTokens`); that aspect is unconfirmed and not required for the primary finding above, which rests on the unguarded spot-price dependency itself.

    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
