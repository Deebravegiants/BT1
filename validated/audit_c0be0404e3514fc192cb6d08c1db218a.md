### Title
PoA Bridge `describeWithdrawal` misreports status/txHash for batched same-asset withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` and the shared `waitForWithdrawalCompletion` helper resolve a withdrawal's status by looking up the POA bridge API response using `findMatchingWithdrawal`, which matches purely by `assetId` (i.e., `near_token_id`) and ignores the caller-supplied `index`, `destinationAddress`, and `amount` that make a `WithdrawalIdentifier` unique.

### Finding Description
`WithdrawalIdentifier` is defined with a per-bridge `index` specifically to disambiguate multiple withdrawals originating from the same NEAR transaction: [1](#0-0) . `createWithdrawalIdentifiers` assigns a distinct, sequential `index` per bridge route for every withdrawal in a batch: [2](#0-1) .

However, `PoaBridge.describeWithdrawal` discards this `index` and instead calls `findMatchingWithdrawal`, which returns the *first* withdrawal in the API's (explicitly unsorted) response list whose `near_token_id` matches the requested `assetId` — regardless of destination address, amount, or position: [3](#0-2) [4](#0-3) . The identical matching flaw exists in the internal-utils helper used for waiting on POA withdrawal completion: [5](#0-4) .

This is confirmed as intentional/known behavior by an existing test explicitly titled "matches withdrawal by assetId, not by index," which shows `describeWithdrawal` returning the `eth`-chain withdrawal's `transfer_tx_hash` when queried for a same-tx `btc` withdrawal purely because of list ordering assumptions; more critically, if two withdrawals of the *same* asset (same `near_token_id`) but different `destinationAddress`/`amount` are batched in one NEAR transaction, the lookup can return the txHash and completion status belonging to the wrong withdrawal: [6](#0-5) .

`watchWithdrawal` in the SDK's withdrawal watcher treats a `"completed"` status/`txHash` from `describeWithdrawal` as final truth and resolves immediately, without any secondary check that the returned data belongs to the queried index/destination: [7](#0-6) . `createWithdrawalCompletionPromises` fans out one `watchWithdrawal` call per withdrawal index in a batch and returns each promise's resolved `TxInfo` independently to the caller/integrator: [8](#0-7) .

The equality broken: "status/txHash reported for withdrawal at index N" is not guaranteed to equal "the on-chain outcome of withdrawal at index N" when two same-asset withdrawals with different destination addresses/amounts are batched — the caller can be told withdrawal N is `completed` with a destination-chain `txHash` that actually corresponds to a different withdrawal in the same batch.

### Impact Explanation
An integrator that batches two withdrawals of the same NEP-141 asset in a single NEAR transaction (e.g., withdrawing the same token to two different destination addresses in one intent execution) can receive a `completed` status and `txHash` for withdrawal index 0 that actually belongs to withdrawal index 1 (or vice versa), while the real destination for index 0 is still pending, failed, or refunded. This matches the High-impact bucket: "a status or hash misreport making an integrator credit or refund twice" — the integrator could mark the wrong recipient's withdrawal as complete, refund/re-issue the actually-uncompleted one, or fail to notice a genuinely failed withdrawal because a sibling withdrawal's success masked it.

### Likelihood Explanation
This requires no malicious action — it is triggered by ordinary use: a single unprivileged user submitting a NEAR transaction with multiple withdrawal intents for the same POA-bridged asset (e.g., withdrawing to two different addresses in one batch, or a self-service "split withdrawal" flow). The POA bridge API response order is explicitly documented as unsorted, and both the `poa-bridge.ts` and `internal-utils` matching functions have an inline code comment acknowledging that "multiple withdrawals of the same token in a single transaction are not supported," confirming the root cause is real and known but unmitigated at the API-consumption layer.

### Recommendation
Change `findMatchingWithdrawal` in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` to disambiguate by destination address and amount (or ordinal position after sorting both sides deterministically) in addition to `assetId`, so that a status/txHash is only reported for the withdrawal it actually corresponds to. Until the POA API supports a stable per-withdrawal identifier, either reject/serialize batched same-asset POA withdrawals, or fail closed (return `pending`/throw) when more than one candidate withdrawal matches the same `assetId` in the response rather than silently returning the first match.

### Proof of Concept
1. User submits one NEAR transaction containing two POA-bridge withdrawal intents for the same asset `nep141:eth.omft.near`: index 0 → `destinationAddress: 0xAAA...`, amount 1; index 1 → `destinationAddress: 0xBBB...`, amount 2.
2. The POA bridge processes index 1 (to `0xBBB`) first and marks it `COMPLETED` with `transfer_tx_hash: "0xhash-for-BBB"`, while index 0 (to `0xAAA`) is still `PENDING`.
3. SDK calls `describeWithdrawal` for `WithdrawalIdentifier{ index: 0, assetId: "nep141:eth.omft.near", ... }`.
4. `findMatchingWithdrawal` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`) scans the unsorted `withdrawals` array and returns the first entry with `near_token_id === "eth.omft.near"` — which is the `0xBBB` entry — regardless of `index` or `destinationAddress`.
5. `describeWithdrawal` returns `{ status: "completed", txHash: "0xhash-for-BBB" }` for the caller's index-0 (`0xAAA`) request, exactly as demonstrated by the existing unit test `"matches withdrawal by assetId, not by index"` (`packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1107`), which asserts this cross-match behavior for the `nep141:btc.omft.near` case.
6. An integrator relying on `watchWithdrawal`/`createWithdrawalCompletionPromises` believes the withdrawal to `0xAAA` completed with `0xhash-for-BBB`, even though funds were never sent to `0xAAA`.

	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
