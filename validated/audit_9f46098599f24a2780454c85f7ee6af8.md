### Title
Permanent lock of 10% of liquidity-pair reserves during DEX graduation - ([File: aptos-move/move-examples/bonding_curve_launchpad/sources/liquidity_pairs.move])

### Summary
The external report's root custody invariant is: *value received/held by a contract function must always have a valid path to be moved or accounted for; if a function computes only a partial use of received/held value, the remainder becomes permanently stuck.* The Aptos-native analog exists in the `bonding_curve_launchpad` example's `graduate()` flow in `liquidity_pairs.move`, where 10% of both APT and FA reserves held by the `LiquidityPair` object are silently withheld from the DEX liquidity deposit and have no subsequent code path to be withdrawn.

### Finding Description
When a bonding-curve pair's APT reserves cross `APT_LIQUIDITY_THRESHOLD`, `swap_apt_to_fa` triggers `graduate()`: [1](#0-0) 

Inside `graduate()`, only 90% of the tracked reserves are passed as the desired liquidity amounts to `add_liquidity_coin_entry_transfer_ref`: [2](#0-1) 

`graduate()` then immediately disables the pair (`is_enabled = false`) and unfreezes the FA (`is_frozen = false`), which is the *only* way the module gates access to the `LiquidityPair`'s APT balance and `fa_store`: [3](#0-2) 

After graduation, `is_enabled == false` causes both `swap_fa_to_apt` and `swap_apt_to_fa` to abort with `ELIQUIDITY_PAIR_DISABLED`: [4](#0-3) [5](#0-4) 

There is no other public, entry, or friend function in `liquidity_pairs.move` or `bonding_curve_launchpad.move` that references `liquidity_pair.fa_store` or the `LiquidityPair` object's APT account balance after graduation. The `LiquidityPair` resource is never deleted, and no `TransferRef`/`ExtendRef`-based withdrawal is exposed to the creator, an admin, or any signer for the residual 10%. This mirrors the external report's core defect: computed/received value (`apt_updated_reserves / 10` and `fa_updated_reserves / 10`) is deliberately excluded from the only consumption path (`add_liquidity_coin_entry_transfer_ref`) and the code never adds a corresponding withdrawal or refund path, so the value becomes permanently stranded in the object's custody.

### Impact Explanation
This breaks the custody invariant that "object-held value must preserve the intended controller and remain recoverable." Every FA that graduates from the bonding curve to the external DEX permanently strands 10% of its APT reserves (which must exceed `APT_LIQUIDITY_THRESHOLD = 600_000_000_000` octas, i.e., ≥6,000 APT, meaning ≥600 APT stranded per graduation) plus 10% of the FA reserves, inside the `LiquidityPair` object with no reachable withdraw function. This is a permanent, non-recoverable loss of custody-held value for every token that graduates — a high-severity, mainnet-relevant impact under the "Permanent lock or non-recoverable loss of object-held ... value" custody pivot.

### Likelihood Explanation
This is triggered automatically and unconditionally by normal, unprivileged usage: any user calling `swap` (`swap_apt_to_fa`) that pushes `apt_updated_reserves` above `APT_LIQUIDITY_THRESHOLD` causes `graduate()` to execute, with no special permissions required. There is no way to avoid the stranding once the threshold is crossed, so likelihood is effectively certain for every bonding-curve pair that successfully graduates.

### Recommendation
Modify `graduate()` to either (a) pass the full `apt_updated_reserves`/`fa_updated_reserves` (or an intentional, explicitly-labeled fee amount) to `add_liquidity_coin_entry_transfer_ref`, or (b) if a 10% reserve buffer is intentional, add an explicit, access-controlled withdrawal function using the `LiquidityPair`'s `extend_ref`/a stored `TransferRef` that allows the creator or protocol admin to reclaim the residual APT and FA balance after graduation.

### Proof of Concept
1. Call `bonding_curve_launchpad::create_fa_pair` to launch a new FA/APT pair.
2. Repeatedly call `bonding_curve_launchpad::swap(account, name, symbol, /*swap_to_apt=*/false, amount_in)` (i.e., `swap_apt_to_fa`) until `apt_updated_reserves > APT_LIQUIDITY_THRESHOLD` (600_000_000_000 octas), triggering `graduate()` at [6](#0-5) .
3. Observe that `add_liquidity_coin_entry_transfer_ref` only withdraws 90% of `apt_updated_reserves`/`fa_updated_reserves` from the pair's balance/`fa_store` [7](#0-6) , leaving 10% behind.
4. Attempt any further swap on the same pair — both `swap_fa_to_apt` and `swap_apt_to_fa` abort with `ELIQUIDITY_PAIR_DISABLED` because `is_enabled` is now `false`, confirming the remaining balance is unreachable through any exposed entry point in the module.

```text
    fun graduate(
        liquidity_pair: &mut LiquidityPair,
        fa_object_metadata: Object<Metadata>,
        transfer_ref: &TransferRef,
        apt_updated_reserves: u128,
        fa_updated_reserves: u128
    ) {
        // Disable Bonding Curve Launchpad pair and remove global freeze on FA.
        liquidity_pair.is_enabled = false;
        liquidity_pair.is_frozen = false;
        // Offload onto third party, public DEX.
        router::create_pool_coin<AptosCoin>(fa_object_metadata, false);
        let liquidity_pair_signer = object::generate_signer_for_extending(&liquidity_pair.extend_ref);
        add_liquidity_coin_entry_transfer_ref<AptosCoin>(
            transfer_ref,
            &liquidity_pair_signer,
            liquidity_pair.fa_store,
            fa_object_metadata,
            false,
            ((apt_updated_reserves - (apt_updated_reserves / 10)) as u64),
            ((fa_updated_reserves - (fa_updated_reserves / 10)) as u64),
            0,
            0
        );
        // Send liquidity provider tokens to dead address.
```
