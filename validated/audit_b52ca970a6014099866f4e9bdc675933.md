### Title
OAuth callback fails to sanitize `shop` before it is used to build the access-token request host, exposing `client_id`/`client_secret`/authorization `code` to an unvalidated domain - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the `Auth::Session` used to send the app's `client_id`, `client_secret`, and authorization `code` to `https://#{auth_query.shop}/admin/oauth/access_token` using the raw `auth_query.shop` value, without ever calling `Utils::ShopValidator.sanitize!` on it. [1](#0-0)  By contrast, every other credential-exchange flow in the same module (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host that will receive the `client_secret`. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The identity binding that should hold is: *the host that receives the app's `client_secret` == a domain independently validated to belong to Shopify's trusted domain set* (as enforced by `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`). [5](#0-4) 

In `validate_auth_callback`, the `shop` value is taken directly from `auth_query.shop` — a field that is only checked against the HMAC signature computed by `Utils::HmacValidator.validate`, and against the `state` cookie. It is never passed through `ShopValidator.sanitize!`. [6](#0-5)  The unsanitized `shop` is used to construct `null_session = Auth::Session.new(shop: auth_query.shop)`, which is then handed to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` to POST the app's `client_id`, `client_secret`, and the OAuth `code` to `path: "access_token"` — i.e. `https://#{auth_query.shop}/admin/oauth/access_token`. [7](#0-6) 

This is the exact "host validated versus host that receives the access token or `client_secret`" binding break called out in the rules: the gem checks that the request *is* HMAC-authentic, but never checks that the *shop* embedded in that authenticated request is actually a Shopify-owned domain before using it as the destination host for the client credentials.

Critically, this makes the code's correctness for defense-in-depth solely dependent on the assumption that Shopify's OAuth authorization server will only ever echo back a `shop` value ending in a Shopify-owned domain in a validly-HMAC'd callback. The gem itself provides `ShopValidator` specifically to enforce this invariant independently and applies it in three of four credential-exchange code paths, but omits it in the fourth (the OAuth authorization-code callback, `validate_auth_callback`) — the highest-value path, since it is the one that hands the raw `client_secret` value out on every single install/callback for every merchant.

### Impact Explanation
If any code path upstream of `validate_auth_callback` can produce (or an app is induced into presenting) an `AuthQuery` with a `shop` value that is not a genuine Shopify domain but which nonetheless carries a valid HMAC (e.g., a stale/replayed but validly-signed callback whose `host`/`shop` combination was recorded for a different purpose, or any HMAC-valid record retained/forwarded by the host application), the gem will `POST` the app's `client_secret`, `client_id`, and authorization `code` to that arbitrary host. This is a High-severity credential-leakage/SSRF-with-credentials issue per the rules ("SSRF with the app's credentials, ... credential leakage into logs or error output") because the gem's own code — not the host application — decides the destination host for the client secret without applying its own documented domain-allowlist check.

### Likelihood Explanation
Likelihood is constrained by the fact that, under Shopify's real OAuth flow, `shop` is bound by HMAC and normally only ever set by Shopify's genuine OAuth server to a real `*.myshopify.com` domain. The concrete exploitation path (i.e., how an unprivileged attacker forces a validly-HMAC'd `AuthQuery` with a non-Shopify `shop` through this gem without already possessing `api_secret_key`) could not be fully confirmed from the in-scope code alone. What is proven with certainty by the code is the missing defense-in-depth check itself: the asymmetry between `validate_auth_callback` and the other three credential-exchange call sites, all of which the gem's own maintainers considered important enough to explicitly guard with `ShopValidator.sanitize!`.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` at the start of `validate_auth_callback` (immediately after the HMAC/state checks) and use the sanitized value everywhere the shop is used to build the session and access-token request, consistent with `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
```ruby
# lib/shopify_api/auth/oauth.rb, current behavior:
def validate_auth_callback(cookies:, auth_query:)
  ...
  raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
  ...
  null_session = Auth::Session.new(shop: auth_query.shop)  # <- no ShopValidator.sanitize! applied
  body = {
    client_id: Context.api_key,
    client_secret: Context.api_secret_key,   # sent to https://#{auth_query.shop}/admin/oauth/access_token
    code: auth_query.code,
    expiring: Context.expiring_offline_access_tokens ? 1 : 0,
  }
  client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
  client.request(Clients::HttpRequest.new(http_method: :post, path: "access_token", body: body, body_type: "application/json"))
  ...
end
```
Contrast with the guarded call sites:
```ruby
# lib/shopify_api/auth/client_credentials.rb
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
```
```ruby
# lib/shopify_api/auth/refresh_token.rb
validated_shop = Utils::ShopValidator.sanitize!(shop)
shop_session = ShopifyAPI::Auth::Session.new(shop: validated_shop)
```
No `ShopValidator` call exists anywhere in `lib/shopify_api/auth/oauth.rb`, confirmed by repository-wide search showing `ShopValidator` referenced only in `client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`, and `clients/graphql/storefront.rb` — not `oauth.rb`.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
