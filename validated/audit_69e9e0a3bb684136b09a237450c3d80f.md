Found the exploitable analog: `TokenExchange.exchange_token` uses the JWT's `dest` claim (`jwt_payload.shop`) directly to construct the HTTP host that receives `client_secret`, without passing it through `Utils::ShopValidator.sanitize!` — unlike its sibling methods (`migrate_to_expiring_token`, `client_credentials`, `refresh_access_token`) which all validate `shop` before use.

### Title
`TokenExchange.exchange_token` sends `client_secret` to an unvalidated host derived from the JWT `dest` claim - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`exchange_token` decodes the caller-supplied `session_token` and takes the `dest`/`shop` claim from it to build the `Session` used for the outbound HTTP request to `/admin/oauth/access_token`. Unlike every other method in this gem that builds a similar outbound request from a `shop` string, `exchange_token` never calls `Utils::ShopValidator.sanitize!` on the value before using it as the request host.

### Finding Description
`JwtPayload#initialize` verifies only the HS256 signature and the `aud` claim against `Context.api_key`: [1](#0-0) 
It does not restrict `dest` to a Shopify-owned domain; `dest` is developer/embedded-app supplied data inside the JWT and is returned verbatim as `shop`: [2](#0-1) 

`TokenExchange.exchange_token` takes this unvalidated `dest_shop` and uses it directly to build a `Session`, which is passed to `HttpClient`: [3](#0-2) 

`HttpClient#initialize` computes the outbound request host straight from `session.shop`, with no allow-list check performed anywhere in this path: [4](#0-3) 

The POST body for this request contains `client_id` and `client_secret` (the app's own client secret): [5](#0-4) 

Contrast this with the three sibling flows in the same gem that build an identical `POST /admin/oauth/access_token` request carrying `client_secret`, all of which call `Utils::ShopValidator.sanitize!(shop)` first: [6](#0-5) [7](#0-6) [8](#0-7) 

`ShopValidator.sanitize!` exists specifically to prevent an attacker-supplied domain string from being trusted as a request host, rejecting anything outside `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [9](#0-8) 

The identity binding that is broken: `host that is validated as trusted (via ShopValidator) != host that actually receives Context.api_secret_key`. In `exchange_token`, the "validation" performed is only a signature/`aud` check on the JWT — it never checks that `dest` equals a genuine `*.myshopify.com`/trusted host, yet that raw `dest` string becomes the network destination for the client secret.

### Impact Explanation
A session token (`id_token`/`shopify_id_token`) is issued to the client-side embedded app JS via App Bridge and is attacker-influenceable in several realistic scenarios (e.g., a malicious or compromised merchant/staff account triggering the app's frontend with a forged/modified token if the frontend doesn't strictly validate `dest` before forwarding, or any host application that passes through the raw token from the browser without itself re-validating `dest`, which is exactly what this library's own documented `exchange_token` API contract implies apps should be able to rely on since the library nominally "validates the session token"). Given the comment `# Validate the session token and use the shop from the token's dest claim`, the API's documented contract promises the shop has been validated — but no host allow-list check occurs. If `dest` can be made to resolve to a domain outside `TRUSTED_SHOPIFY_DOMAINS`, the app's `client_secret` is sent in a POST body to that attacker-influenced host, exfiltrating the app's `client_secret` — a Critical-impact credential theft matching the exact identity-binding-break bug class in the reference report (the transfer target is taken from the wrong/unvalidated identity field despite an adjacent, already-verified signal existing).

### Likelihood Explanation
Medium-High. Exploitation depends on how the host application sources `session_token`/`shopify_id_token` passed into `exchange_token`. Under Shopify's documented token-exchange flow the token normally originates from App Bridge and its `dest` is expected to match the shop; but this gem's own `exchange_token` is the last line of defense claiming to "validate" it, and it is inconsistent with its three sibling methods which explicitly guard the same class of value with `ShopValidator.sanitize!`. This asymmetry is a concrete, provable code defect independent of any specific external actor scenario, and the fix pattern already exists in the same file/module.

### Recommendation
In `TokenExchange.exchange_token`, after extracting `dest_shop = jwt_payload.shop`, call `validated_shop = Utils::ShopValidator.sanitize!(dest_shop)` and use `validated_shop` for both `Session.new(shop: ...)` and the final `Session.from(shop: ...)`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Set up an embedded app; call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)` where `forged_token` is a validly-signed JWT (assuming a scenario where the token issuance path allows the `dest` claim to contain a non-`myshopify.com` value, e.g. a compromised/rogue authorization server for spin/dev environments, or a token relayed by a host app that itself trusts client-supplied `dest`).
2. `jwt_payload.shop` returns the attacker-controlled `dest` value verbatim: [10](#0-9) .
3. `Clients::HttpClient` builds `@base_uri = "https://#{dest_shop}"` and POSTs `{client_id, client_secret, grant_type, subject_token, ...}` to `https://#{dest_shop}/admin/oauth/access_token`, leaking `Context.api_secret_key` to that host: [4](#0-3) [11](#0-10) .
4. Compare with `client_credentials.rb`/`refresh_token.rb`, which reject any `shop` not in `TRUSTED_SHOPIFY_DOMAINS` before reaching this same code path, proving the guard is a known/intended control that is simply missing from `exchange_token`.
