Based on my investigation, I found a concrete analog to the netfilter `eth_hdr()` bug class: code that assumes a byte buffer has a minimum fixed length and slices it from a computed offset without validating the length first, causing a panic/DoS on attacker-influenced input in a message-delivery path.

### Title
Unchecked-length slice on ISMP `from` address panics the runtime in `pallet-hyper-fungible-token`'s calldata execution path - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token`'s inbound message handler, when executing optional calldata carried in an HFT `Message`, derives the EVM origin address by slicing the ISMP `PostRequest.from` bytes with `&from_bytes[from_bytes.len() - 20..]`, assuming the buffer is at least 20 bytes long whenever the source chain `is_evm()`. This mirrors the reported netfilter class: extracting a fixed-size header/address from a buffer whose length was checked for the *wrong* thing (or not checked at all) rather than validated to be at least as long as the fixed structure being read, e.g. `eth_hdr()` being called without first confirming `skb_mac_header` + `ETH_HLEN` fits.

### Finding Description
In the calldata-execution branch of the inbound handler: [1](#0-0) 
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```
`message.from` is decoded from the `Message.from` field of the abi-encoded HFT `Message` struct carried inside `request.body`, which is itself relayed via an ISMP `PostRequest` that any relayer can submit a proof for (subject only to `onAccept`'s source-contract check on `request.from`, which is unrelated to `message.from`). The 20-byte slice on `from_bytes.len() - 20` is only reached when `substrate_data.signature` is `None` and `message.data` is non-empty — i.e. an attacker can craft an HFT message whose ABI-encoded `Message.from` field is shorter than 20 bytes (any length works because `bytes` in Solidity ABI encoding is arbitrary-length) while making `source.is_evm()` true. `from_bytes.len() - 20` then underflows `usize`, which panics on a runtime built with overflow checks (as most Substrate runtimes are for safety) or produces a huge, out-of-range slice index in a release build — either way, `H160::from_slice` reached with garbage or the arithmetic itself panics before ever reaching it. This is functionally identical to `eth_hdr()`-class bugs: fixed-length structure access is performed based on an unchecked length assumption tied to a type flag (`is_evm()` in this codebase vs. "device is Ethernet" in the kernel), rather than an explicit length check of the buffer being sliced.

The `else` branch has a similar defect: `account.copy_from_slice(from_bytes)` requires `from_bytes.len() == 32` exactly, and will panic if not, for the substrate-origin case.

### Impact Explanation
A panic inside pallet logic invoked from `on_execute` / message-dispatch during block execution halts block production for that runtime (denial of service to the whole chain), since Substrate panics during transaction/inherent execution are not gracefully recoverable the way a `Result::Err` is — this is reachable from an unprivileged relayer delivering a single proven ISMP `PostRequest` to `pallet-hyper-fungible-token`'s `onAccept`-equivalent handler. This satisfies "route unable to deliver messages" / broader liveness impact for the affected chain, warranting High severity given the DoS blast radius (the whole hyper-fungible-token pallet, and potentially the runtime executive if unwrapped panics are not caught by transactional or `try_state` layers).

### Likelihood Explanation
Likelihood is high: it requires only a single crafted cross-chain POST request with an arbitrary-length `from` field in the ABI-encoded `Message`, and a valid state/consensus proof for that request's inclusion, both of which an unprivileged relayer/message submitter fully controls. No governance or privileged role is needed — the crafted `Message.from` field is entirely attacker-chosen at ABI-encoding time on the source chain side (or fully attacker-forged if the source chain allows sending, e.g. via a compromised or minimal contract), and the destination-side `EvmToSubstrate::convert` slicing has no length guard.

### Recommendation
Before slicing, explicitly validate `from_bytes.len() >= 20` (EVM case) and `from_bytes.len() == 32` (substrate case), returning a decode/validation error (e.g. extend `HftError`) instead of performing the raw slice/`copy_from_slice`. This matches the netfilter fix's approach: verify the buffer is at least as long as the fixed-size structure before extracting it.

### Proof of Concept
1. From an EVM source chain state machine, submit (or forge via a malicious/compromised sender contract) an HFT-formatted ISMP `PostRequest` whose body ABI-decodes to a `Message` with `from` set to fewer than 20 bytes (e.g. `0x1234`) and `data` non-empty with no `signature` set in the embedded `SubstrateCalldata`.
2. Relay this request with a valid state proof to the destination `pallet-hyper-fungible-token` instance; `source.is_evm()` evaluates true for the EVM source.
3. Execution reaches [2](#0-1) 
, where `from_bytes.len() - 20` underflows because `from_bytes.len() == 2 < 20`, panicking the runtime (or, without overflow checks, producing an out-of-bounds slice index panic in `H160::from_slice`/indexing).
