## Finding

<title>Webhook shop identity is not bound to the HMAC-verified payload, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)</title>

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the application's webhook handler are read directly from unauthenticated HTTP headers and are never covered by, or cross-checked against, that HMAC. This breaks the binding "shop that produced the HMAC-valid body" == "shop passed to the handler."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no validation (no `ShopValidator.sanitize!`, no cross-check against anything covered by the signature): [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (i.e., only the body) and compares it against the `hmac-sha256` header using the app's `client_secret`. It then immediately trusts `request.shop` (and other headers) to build the `WebhookMetadata` passed to the application's handler: [3](#0-2) 

The HMAC computation itself confirms this — only the body bytes are signed: [4](#0-3) 

Because the shop identity is carried in a header outside the HMAC's coverage, any request whose body+HMAC pair is valid for the app's `client_secret` will pass verification regardless of what `shop`, `topic`, `webhook_id`, or `api_version` headers are attached to it. Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where `shop` (and `host`, `state`, `code`, `timestamp`) are explicitly included in `to_signable_string` and therefore bound by the HMAC: [5](#0-4) 

### Impact Explanation
An attacker who controls (or compromises) any single shop that has the app installed receives genuine webhooks with a valid `hmac-sha256` for arbitrary bodies of their choosing (they fully control their own shop's data, e.g. by editing an order/product to control body content, or simply replaying/relaying an existing valid webhook). They can then resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and `X-Shopify-Webhook-Id`/`X-Shopify-Topic` if desired) with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: request.shop, ...)` reporting the victim shop as the source. Any host application that uses the webhook `shop` field to key per-tenant data (updating records, revoking access, processing `shop/redact`/`customers/redact` mandatory compliance webhooks, billing, etc.) can be tricked into acting on another merchant's tenant record using attacker-controlled data — a cross-tenant data integrity/confusion issue.

### Likelihood Explanation
Any developer/merchant who can install the app on their own store (a low bar — this is the normal "unprivileged internet user" installing a public app) can obtain valid HMAC-signed webhook bodies for content they control, then trivially replay them with a forged shop header to any exposed webhook endpoint that uses this gem's `Registry.process`/`Request` classes. No access token, `client_secret`, or privileged access to the victim's data is required.

### Recommendation
Bind the shop identity to the HMAC-verified content. At minimum:
- Include `shop` (and `topic`/`webhook_id`) in `to_signable_string` if the design is changed to sign a canonical string instead of the raw body, or
- Since Shopify's real webhook HMAC only ever covers the raw body, applications relying on this gem's `Request#shop` should not need to — the gem should not expose `Request#shop` as trustworthy for tenant-identification purposes without a documented, loud warning, and ideally the library should offer/require a secondary authenticated channel to confirm the shop (e.g., validate `shop` matches an actively registered subscription for the given `webhook_id`/topic via a stored mapping) before invoking the handler.
- At minimum, `Registry.process` should sanitize `request.shop` through `Utils::ShopValidator` and document explicitly that `shop`/`topic`/`webhook_id` headers are NOT covered by the HMAC and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures the app's webhook subscription for a topic (e.g. `orders/create`).
2. Attacker triggers a webhook on their own shop; Shopify sends:
   ```
   POST /webhooks HTTP/1.1
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of BODY using app client_secret>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: BODY
   ```
3. Attacker replays this exact request to the app's webhook endpoint, only changing the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
   Body and `X-Shopify-Hmac-Sha256` are unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `BODY` only and matches — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though this data never originated from `victim-shop`, demonstrating the shop field is unauthenticated relative to the HMAC.
