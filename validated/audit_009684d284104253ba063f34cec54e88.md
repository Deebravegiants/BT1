Webhook tenant identity (`shop`, `topic`, `webhook_id`) is trusted from unauthenticated headers, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC signature over the raw request **body only**, while the shop-tenant identity (`shop-domain`), `topic`, and `webhook_id` are read straight from HTTP headers that are never included in the signed content. `ShopifyAPI::Webhooks::Registry.process` treats a passing HMAC check as proof that the *entire request*, including these header-derived fields, is authentic, and forwards them unmodified to the host application's handler as `WebhookMetadata`. This breaks the intended binding: `HMAC-verified bytes == the whole trusted webhook`, when in reality `HMAC-verified bytes == raw_body only`.

### Finding Description
`Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) validates a `VerifiableQuery` by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing to `verifiable_query.hmac`.

For webhooks, `ShopifyAPI::Webhooks::Request` implements this interface as: [1](#0-0) 

- `hmac` is read from the `hmac-sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from headers and are **not** part of `to_signable_string`.

`Registry.process` performs the HMAC check and then immediately trusts the header-derived fields to build tenant/dispatch metadata: [2](#0-1) 

The check `Utils::HmacValidator.validate(request)` only proves that `@raw_body` was signed with `Context.api_secret_key` (or `old_api_secret_key`) at some point in the past — it proves nothing about which shop or topic that body was originally sent for. Because `shop`, `topic`, and `webhook_id` are excluded from the signable string, an attacker who has ever captured one legitimate webhook delivery (e.g., by installing the app in their own store, or from a network position that observes their own webhook traffic — no `api_secret_key` or access token required) can **replay that exact `raw_body` + valid `hmac` header, while freely rewriting the `shop-domain`, `topic`, and `webhook-id` headers**. `HmacValidator.validate` will still return `true` because the body and signature are unchanged, and `Registry.process` will dispatch the (attacker-chosen) `topic`/`shop`/`webhook_id` combination to the host application's handler as if Shopify itself vouched for that shop and topic: [3](#0-2) 

This is a direct instance of the target bug class: "bytes verified versus bytes parsed" / "a field acted on but not covered by the HMAC." The equality the gem is expected to guarantee is:
`HMAC-verified content == {shop, topic, webhook_id, body}` used by the handler
but what is actually guaranteed is only:
`HMAC-verified content == raw_body`.

### Impact Explanation
This enables cross-tenant confusion: a webhook payload legitimately generated for shop A (the attacker's own store, or one they can observe) can be replayed with the `shop-domain` header set to shop B (a victim tenant) and any `topic` the attacker chooses, while still passing HMAC verification inside this gem. Any host application that relies on `ShopifyAPI::Webhooks::Registry.process`'s successful HMAC validation as proof that `data.shop`/`data.topic` are authentic (which is the gem's own documented contract — HMAC validation is presented as the authenticity guarantee for the whole webhook) will process attacker-controlled tenant/topic claims as trusted. Depending on the handler logic, this can cause actions to be applied against the wrong merchant's account/data — a cross-tenant integrity issue.

### Likelihood Explanation
Exploitability requires only: (1) the ability to receive at least one legitimate webhook with a valid signature for *some* body (trivially available to any developer/attacker who installs the app on a store they control, or a network observer who can capture their own store's webhook), and (2) the ability to POST an HTTP request with arbitrary headers to the app's webhook endpoint. No `api_secret_key`, access token, or privileged account is needed — the whole point of the flaw is that the header fields are not cryptographically bound to the signature at all, so no secret is needed to alter them.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in the signable content verified by `HmacValidator`, or otherwise cryptographically bind these header values before trusting them in `Registry.process`/`WebhookMetadata`. Short term, document prominently that `request.shop`/`request.topic`/`request.webhook_id` are **not** covered by the HMAC and must not be treated as authenticated by the host application without additional verification (e.g., cross-checking against the shop's own token-derived session). Long term, extend `to_signable_string` (or add a secondary verification step) so a passing HMAC check certifies the full `{shop, topic, webhook_id, body}` tuple that `Registry.process` dispatches.

ShopifyAPI::Context.setup(

# 1. Attacker captures ONE legitimate webhook delivered to their own shop:

  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_secret", raw_body)
).strip

# 2. Attacker replays the SAME body + SAME (still-valid) hmac, but forges the
#    shop/topic headers to target a different tenant:

  "x-shopify-hmac-sha256" => valid_hmac,    # unchanged, still verifies
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation still succeeds because it only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# The registry will dispatch this to the handler believing it is an
# authentic webhook for "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
