### Analysis

The equality claimed broken: `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]`, evaluated independently per index `i` in the loop at [1](#0-0) . This loop treats each `erc20TokenAddresses[i]` as an economically distinct asset, but nothing in the code enforces that. `getBalancesForArray`/`getBalancesForArrayMemory` simply call `balanceOf`/`.balance` on whatever address is supplied, once before and once after the external action [2](#0-1) , and there is no check anywhere (`dimensionsCheck`, `checkOnchainCreation`, `performHinkalChecks`) that the entries of `erc20TokenAddresses` are unique or refer to independent underlying balances [3](#0-2) .

**Exploit path:**
1. Attacker deploys a real token `A` and a second attacker-controlled contract `B` whose `balanceOf(Hinkal)` simply proxies/reads `A`'s balance for `Hinkal` (a shared-storage/aliasing "view" token), while `B.transferFrom` is a no-op that returns `true` without moving anything.
2. Attacker calls `Hinkal.transact` with `externalActionData.externalActionId` pointing to `DepositOnChainUtxosExternalAction`, `erc20TokenAddresses = [A, B]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]` (mandatory when `onChainCreation` is true, per `checkOnchainCreation` [4](#0-3) ), and `externalActionMetadata` encoding `utxoAmounts = [[X], [X]]`.
3. Inside `runAction`, for index 0 (`A`) a real `transferFrom(user, Hinkal, X)` moves `X` real tokens into Hinkal; for index 1 (`B`) the no-op `transferFrom` moves nothing, yet still creates a UTXO entry of amount `X` tagged with `erc20Address = B` [5](#0-4) .
4. Back in `transact`, `oldBalances`/`newBalances` for index 1 are taken via `B.balanceOf(Hinkal)`, which — because `B` aliases `A`'s real ledger — also shows an increase of `X` (the same real deposit from step 3, index 0). So `balanceDif[1] == X`, exactly matching `utxoAmount[1] = X`, and the check at line 137-146 passes for both indices [6](#0-5) .
5. Net result: `X` real tokens entered Hinkal, but `2X` of shielded value was minted (one on-chain UTXO under `A` for `X`, one on-chain UTXO under `B` for `X`), both inserted into the Merkle tree via `insertCommitments` [7](#0-6) .

No guard in `verifyProof`, `rootHashExists`, `dimensionsCheck`, or `checkOnchainCreation` inspects whether two indices in `erc20TokenAddresses` reference the same underlying value — the circuit only operates on field-encoded addresses per index and has no notion of real-world asset identity, so it cannot prevent this Solidity-level accounting flaw.

### Title
Per-index balance-diff check in `Hinkal.transact` lets an aliased/proxy ERC20 pair mint shielded UTXOs without matching real backing - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` verifies `balanceDif == deltaAmountChange + utxoAmount` independently for every entry of `circomData.erc20TokenAddresses`, assuming each entry represents an economically independent asset. An attacker can supply two addresses where one (`B`) is a thin proxy that reads the real balance of the other (`A`) but performs no real transfer, so a single genuine deposit of `X` tokens is reflected as a `balanceDif` of `X` under both indices, letting `DepositOnChainUtxosExternalAction` mint two on-chain UTXOs of `X` each while only `X` real tokens entered the vault.

### Finding Description
The broken equality is `balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` for each `i`, computed in `Hinkal.transact` [1](#0-0) . `oldBalances`/`newBalances` are produced by naively calling `balanceOf` on attacker-supplied addresses [8](#0-7) , and no code path (`dimensionsCheck`, `checkOnchainCreation`, `performHinkalChecks` in `contracts/HinkalHelper.sol`) requires the entries of `erc20TokenAddresses` to be unique or backed by independent storage. Because `DepositOnChainUtxosExternalAction.runAction` performs a real `transferFrom` per index only when `tokenAddress != address(0) && tokenTotal > 0` and blindly trusts the attacker-declared `utxoAmounts` per index [9](#0-8) , an attacker-deployed second token address `B` that mirrors `A`'s balance (via a proxy `balanceOf`) but implements `transferFrom` as a no-op satisfies the per-index check for both `A` and `B` using only one real transfer. The verifier proof and circuit constraints operate purely on field-encoded values and cannot detect that `A` and `B` are the same real asset, so `verifyProof`/`rootHashExists` provide no defense here.

### Impact Explanation
The attacker mints shielded on-chain UTXOs worth `2X` (one under token `A`, one under token `B`) while only `X` of real value entered the Hinkal vault. This is minting shielded value without backing, directly causing protocol insolvency — every later legitimate holder of real deposits is at risk because the vault's tracked liabilities exceed its real assets. This matches the Critical category ("minting shielded value without backing... protocol insolvency"). The attack is repeatable for any amount `X` and any number of aliased token pairs the attacker chooses to deploy.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: deploying two token contracts (one real, one a balance-aliasing proxy with a no-op `transferFrom`), and crafting `CircomData`/`externalActionMetadata` for a self-issued `DepositOnChainUtxosExternalAction` call. No special protocol state, roles, or race conditions are required, and the attacker only pays gas plus the cost of the single real deposit `X`. It is fully repeatable at will.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` (revert on duplicates) in `dimensionsCheck` or `performHinkalChecks`, and/or replace the per-index balance check with a global invariant that ties `sum(real balance deltas)` to `sum(amountChanges) + sum(all minted UTXO amounts)` across the whole call rather than validating each index against a `balanceOf` call on an attacker-chosen address in isolation. Additionally, consider maintaining a registry/allowlist of accepted token addresses rather than trusting arbitrary attacker-supplied `erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy real ERC20 `TokenA` (mint `X` to attacker).
2. Deploy `TokenBProxy` with `balanceOf(addr) => TokenA.balanceOf(addr)` and `transferFrom(...) => true` (no state change).
3. Attacker approves `TokenA` allowance to Hinkal's `DepositOnChainUtxosExternalAction` recipient for `X`.
4. Craft `CircomData` with `erc20TokenAddresses = [TokenA, TokenBProxy]`, `onChainCreation = [true, true]`, `amountChanges = [0,0]`, `slippageValues = [0,0]`, `externalActionData` targeting `DepositOnChainUtxosExternalAction` with metadata `utxoAmounts = [[X],[X]]`; generate a valid proof for this shape (locally, using the repo's circuits/test harness).
5. Call `Hinkal.transact(...)`.
6. Assert: `TokenA.balanceOf(Hinkal) - balanceBefore == X` (real inflow), while `sum(minted UTXO amounts)` inserted into the tree (via emitted `NewCommitment` events / `onChainCommitments`) `== 2*X`.
7. Assert the transaction does not revert — confirming both per-index `balanceDif` checks pass despite the mismatch between real inflow (`X`) and total minted shielded value (`2X`).
