### Title
Webhook `shop` and `topic` values are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values used by the host application entirely from HTTP headers, while `Utils::HmacValidator.validate` only verifies the HMAC signature against the raw request **body** (`to_signable_string` returns `@raw_body`). The headers that carry the tenant identity (`shop-domain`, `topic`) are never part of the signed material, so their authenticity is never actually checked.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` and compares it to the `hmac-sha256` header value: [2](#0-1) 

But `Registry.process` uses `request.shop` and `request.topic` — both parsed straight from headers, not from the signed body — to dispatch the webhook and construct the `WebhookMetadata` passed to the handler: [3](#0-2) 

`Request#shop` and `Request#topic` are simple header reads with no cross-check against the HMAC-signed body: [4](#0-3) 

The identity binding this breaks is: **HMAC-authenticated bytes == bytes acted upon**. Concretely, `hmac == HMAC(raw_body)`, but the code acts on `shop-domain`/`topic` header values that are *not* part of `raw_body`. An attacker who can forge or replay a request with a *valid signature over some body* (e.g., replaying a legitimate webhook payload/signature pair captured for their own shop, or any payload whose HMAC they can compute if they possess a webhook payload+signature pair) can freely set the `shop-domain` header to a victim shop's domain and the `topic` header to any topic, since these headers are never bound to the signature. The gem's `process` method will then hand the handler a `WebhookMetadata` claiming to be for the victim shop/topic while only the (attacker-controlled) body was ever authenticated.

More directly: even without forging the HMAC, this design means the `shop` value that host applications use to look up/authorize per-tenant data (a common integration pattern documented for this gem) is an **unauthenticated header value with respect to the cryptographic proof**, since the signature never covers it. This is the same root cause as the referenced VaultTracker.sol bug: a value is used post-validation (`vlt.exchangeRate`/here, `shop`/`topic`) that was never actually constrained by the check that's supposed to protect it (`maturityRate` cap/here, HMAC coverage).

### Impact Explanation
This allows cross-tenant confusion in webhook processing: an unprivileged attacker who obtains any single valid `(body, hmac)` pair from Shopify for their own shop (any legitimate webhook they receive) can replay it with a modified `shop-domain` header, causing the host application (via `Registry.process`'s `WebhookMetadata`) to process a webhook payload as if it originated from a different shop or topic. In host applications that trust `WebhookMetadata#shop`/`#topic` for authorization or record association without independent header-to-payload binding, this can lead to cross-tenant data corruption/access — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires the attacker to already be a legitimate recipient of at least one valid webhook (to obtain a valid signature/body pair) and requires them to be able to set arbitrary HTTP headers to the endpoint (trivial for any external caller of a public webhook endpoint, since Shopify webhook receivers are just public HTTP routes). No access token, `api_secret_key`, or privileged account is needed. Likelihood is moderate — it depends on the host app trusting `shop`/`topic` from `WebhookMetadata` without extra validation, but the gem itself provides no protection against this binding gap.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or independently validate that these header values are consistent with data embedded in the authenticated body, mirroring the fix pattern from the referenced report (constrain the value actually used to what was verified). At minimum, document that `shop`/`topic` are not covered by the HMAC and must not be trusted for authorization decisions without additional verification (e.g., cross-checking `shop` against the app's known installed shops via a fully authenticated channel).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook for topic `orders/create`, capturing `raw_body`, the `X-Shopify-Hmac-Sha256` header, and other headers.
2. Attacker resends the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or `X-Shopify-Topic: orders/paid`.
3. `HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `@raw_body` against the (unchanged) signature: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: "orders/paid", shop: "victim-shop.myshopify.com", body: <attacker's original order payload>, ...)`, despite `shop`/`topic` never having been bound to the payload's HMAC — demonstrating the identity-binding break.
