### Title
Uniswap V4 spot `sqrtPriceX96` used as the sole price guard for venue-priced Simplex pairs is manipulable within a single block - (File: sdk/packages/simplex/src/strategies/fx.ts)

### Summary
Simplex's venue-priced pairs (pairs with no configured bid/ask curve) derive the fill rate directly from a Uniswap V4 pool's instantaneous `sqrtPriceX96`/tick, and the only defense against a bad quote is `checkPriceGuard`, which compares that spot price against a static `referencePrice`/`maxDeviationBps` band rather than a time-weighted price. This mirrors the reported `SimpleManager` issue: an instantaneous AMM price used for a deviation check can be pushed to any value within the configured band using a flash-loan swap in the same block, defeating the guard's purpose.

### Finding Description
`resolveLegRates` in `sdk/packages/simplex/src/strategies/fx.ts` prices curveless pairs from a live venue quote: [1](#0-0) 

The venue quote is `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which is documented as returning "the raw pool mid derived from `sqrtPriceX96`": [2](#0-1) 

That price flows through `checkPriceGuard`, whose only protection is a static `referencePrice`/`maxDeviationBps` band configured per position: [3](#0-2) 

The pool's live `sqrtPriceX96` and `tick` are read fresh via `StateView.getSlot0` immediately before pricing/withdrawal planning in `UniswapV4LiquidityState.refresh()`: [4](#0-3) 

Because this is the pool's current-block spot price (not a TWAP), it can be moved to any level up to the edge of `maxDeviationBps` with a single large swap (e.g. via flash loan) immediately before the order is priced/filled, and reversed afterward — the classic same-block sandwich pattern flagged in the source report against `SimpleManager`'s `sqrtPriceX96` check. `checkPriceGuard` only bounds deviation from a static reference; it performs no TWAP consultation, no minimum-liquidity/depth check, and no execution-cost/impact adjustment (the same flow doc notes "there is no size or impact term").

### Impact Explanation
An attacker who manipulates the exotic-token pool's spot price just inside the configured `maxDeviationBps` band can cause a venue-priced pair to quote a bid/ask rate favorable to the attacker's own intent order. Since `checkLegPolicyOutput`/`resolveLegRates` linearly extends this manipulated mid across the whole leg notional with no depth/impact term, the solver (Simplex) can be induced to fill an order at an economically unfavorable rate, or an attacker can extract value from the solver's Uniswap V4-backed inventory through repeated sandwich-priced fills. This is a direct loss of solver funds (theft via mispriced fills), medium/high severity depending on `maxDeviationBps` width and pool depth.

### Likelihood Explanation
Likelihood is credible but bounded by the operator's chosen `maxDeviationBps` and pool liquidity/fee tier: a tighter guard and deeper pool require more capital to manipulate, and the guard does at least reject grossly stale/broken quotes. However, since `referencePrice`/`maxDeviationBps` is optional ("omit both to leave the chain unguarded") and even when configured only bounds deviation rather than eliminating same-block manipulation, any attacker able to flash-loan a swap on the underlying pool in the fill's block can bias pricing within the allowed band at will, and this requires no privileged access — any actor able to submit a transaction on the destination chain and place a matching intent order can attempt it.

### Recommendation
Replace or supplement the spot `sqrtPriceX96` reference used by `computeDirectPoolPriceUsd`/`checkPriceGuard` with a Uniswap V4 (or V3) TWAP oracle observation over a meaningful window (e.g., several minutes), and/or require multiple consecutive spot-price reads with agreement before accepting a venue-priced quote. Consider tightening `maxDeviationBps` defaults, adding a minimum on-chain pool liquidity requirement, and applying a size/impact-aware price rather than a flat linear mid across the whole leg notional.

### Proof of Concept
Conceptual (cannot be fully executed without live pool state, but the code path is verifiable statically):
1. Operator configures a curveless pair with `[vault.uniswapV4]` positions and `referencePrice`/`maxDeviationBps` (e.g. 200 bps) per `docs/content/developers/evm/simplex/pricing.mdx`.
2. Attacker takes a flash loan and swaps in the configured Uniswap V4 pool to move `sqrtPriceX96` to the edge of the ±200 bps band around `referencePrice`.
3. In the same block, attacker (or colluding party) places an intent order matched to that pair; Simplex's `resolveLegRates` → `venueUsdPrice` reads the now-manipulated spot price via `UniswapV4LiquidityState.refresh()`/`getSlot0`, and `checkPriceGuard` accepts it because it sits inside the deviation band.
4. Simplex fills the order at the manipulated rate through `UniswapV4FundingPlanner.planWithdrawalForToken`, using the manipulated `sqrtPriceX96` for withdrawal pricing as well.
5. Attacker reverses the swap, restoring the pool price and pocketing the price difference at the solver's expense.

```text
## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
