### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body-derived HMAC and then dispatches the handler using these unauthenticated header values as the tenant/event identity, breaking the equality that should hold between "bytes verified" and "bytes acted on."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to that signed body: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which calls `request.to_signable_string` (the body only) — and, once that single check passes, immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to look up the handler and build `WebhookMetadata` that is handed to app code: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever signs/verifies `verifiable_query.to_signable_string`: [4](#0-3) 

The equality the gem should enforce is: **bytes verified by HMAC == bytes/identity acted upon by `Registry.process`**. Because the header-derived `shop`/`topic`/`webhook_id` are outside the signed payload, that equality does not hold. An unprivileged internet user who is a merchant on their own shop (Shop A) can legitimately trigger a webhook delivery to the app's endpoint (a valid `raw_body` + valid `hmac-sha256` header pair, since Shopify signs with the app's shared secret for events genuinely occurring on Shop A). That attacker can capture this valid `(raw_body, hmac)` pair from their own installation and replay it to the same webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to claim the event originated from a different shop (Shop B). `Utils::HmacValidator.validate` still returns `true` because it only checks `@raw_body`, and `Registry.process` will invoke the topic handler with `WebhookMetadata` claiming `shop: <spoofed shop B>` while `body: <shop A's genuine payload>`.

### Impact Explanation
This breaks the tenant-identity binding that `HmacValidator` is supposed to guarantee for webhook authenticity: a signature that is only valid proof of "this body came from Shopify for some event" is being treated by `Registry.process` as proof of "this event, with this shop/topic, came from Shopify." Any app built on this gem's documented `Registry.process`/`WebhookMetadata` API and that keys tenant-scoped actions off `WebhookMetadata#shop` (which the gem itself supplies and asserts is validated because it passed `HmacValidator.validate`) is exposed to cross-tenant data confusion — data attributed to one merchant's shop can be injected under another merchant's shop identity. This matches the Critical "cross-tenant access" impact category, since the tenant/shop boundary that the HMAC check is meant to enforce is not actually bound to the value used for tenant dispatch.

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a legitimate but unprivileged merchant with the target app installed on their own store (to obtain one genuinely signed `raw_body`+`hmac` pair from their own webhook deliveries — no `api_secret_key` or elevated privilege required), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with modified headers, which is trivial. No secret material, TLS interception, or social engineering is needed, and the flaw is entirely within this gem's `Webhooks::Request`/`Webhooks::Registry` code path — it is not a misuse of an undocumented API since `process` and `WebhookMetadata#shop` are the documented, intended way for apps to consume verified webhook shop identity.

### Recommendation
Bind the identity fields used for dispatch to the same signed payload that the HMAC protects: either (a) sign a canonical string that includes `shop`, `topic`, and `webhook_id` alongside the body before computing/verifying the HMAC (analogous to how `AuthQuery#to_signable_string` includes `shop`/`host`/`state` in its signed representation), or (b) cross-check the header-derived `shop`/`topic` against values embedded in the verified JSON body (Shopify webhook payloads typically carry these identifiers redundantly) and reject the request if they disagree, rather than trusting header values that sit outside the HMAC's coverage.

### Proof of Concept
1. App has the gem's webhook endpoint wired to `ShopifyAPI::Webhooks::Registry.process`, registered for topic `orders/create` (or any topic) as shown in `docs/usage/webhooks.md`.
2. Attacker installs the app on their own shop, `attacker-shop.myshopify.com`, and triggers a real event (e.g., creates an order) so Shopify delivers a webhook to the app with a genuine `X-Shopify-Hmac-Sha256` computed over the real `raw_body`.
3. Attacker captures that exact `raw_body` and `X-Shopify-Hmac-Sha256` value (e.g., via their own logging proxy in front of their app instance, or a captured request).
4. Attacker replays an HTTP POST to the same webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`@raw_body`) — validation succeeds.
6. The topic handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's shop data>, ...)`, causing the app to process attacker-controlled data under the victim shop's tenant identity.
