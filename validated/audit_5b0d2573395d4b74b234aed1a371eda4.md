## Title
Webhook shop-domain identity spoofing via unauthenticated header field bypasses HMAC tenant binding - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the HMAC-signed material. Because the HMAC secret (`api_secret_key`/`client_secret`) is shared across every shop that installs the app, any shop can generate a genuinely valid `(body, hmac)` pair for itself and replay it against the app's webhook endpoint with an arbitrary `shop-domain` header, causing the app to process attacker-controlled webhook data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is derived from the `hmac-sha256` header and `to_signable_string` returns only `@raw_body`. The `shop` accessor, in contrast, is read straight from the `shop-domain` header and is never mixed into `to_signable_string`: [2](#0-1) 

`Registry.process` validates the request using exactly this HMAC-over-body check, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` performs a timing-safe compare of the HMAC computed from `to_signable_string` (the body only) against the received HMAC, using `Context.api_secret_key`: [4](#0-3) 

The identity binding that should hold is:
`HMAC_valid(body, shop-domain, secret) == true` before the app treats `shop-domain` as authentic.

What actually holds is:
`HMAC_valid(body, secret) == true`, independent of `shop-domain`.

Since `api_secret_key` is the same for every shop that installs a given app, any shop (including one the attacker legitimately installs the app on, an "unprivileged internet user" action) can capture a real webhook `(raw_body, hmac-sha256 header)` pair generated by Shopify for its own store, and replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value naming a victim shop. `Registry.process` will pass HMAC validation (the body/HMAC pair is genuinely valid) and will call the registered handler with `shop: <victim-shop>`, `topic`, and `body` all attacker-influenced except that the body content is limited to whatever the attacker's own store actually emitted.

### Impact Explanation
This breaks the tenant boundary the webhook payload is supposed to carry: apps rely on `WebhookMetadata#shop` to route webhook effects (e.g. updating per-shop records, triggering shop-scoped side effects, handling `app/uninstalled`, `shop/redact`, `customers/redact`, etc.) to the correct tenant. An attacker able to control which shop a validly-signed webhook body is attributed to can cause cross-tenant data corruption/attribution — e.g. forcing shop-scoped uninstall/redact cleanup logic to run against a victim shop, or injecting attacker-chosen (but real-webhook-shaped) data as if it originated from the victim. This is a cross-tenant identity-binding bypass, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite — installing the target app on a shop the attacker controls (e.g., a free Shopify development store) in order to legitimately receive a validly-signed webhook — is achievable by any unprivileged internet user with no special credentials, TLS interception, or leaked secrets required. The victim's shop domain is public knowledge. The only work needed afterward is replaying an HTTP POST with a modified header, which any of this gem's documented webhook consumers is subject to since the gem itself performs no binding of `shop` to the signed content.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header values in the HMAC-covered signable string, or otherwise cryptographically bind the shop identity to the verified payload before it is handed to `WebhookMetadata`/handlers, e.g.:
```ruby
# lib/shopify_api/webhooks/request.rb
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{topic}\n#{@raw_body}"
end
```
Note: this requires computing the signature the same way on the app side that issues webhooks it controls, or — since Shopify itself does not include these headers in its HMAC by design — the gem should, at minimum, document the fact that `shop`/`topic` are unauthenticated and unsuitable as a tenant boundary on their own, and provide/encourage cross-checking `request.shop` against a shop that is independently known to have this specific webhook `topic`/subscription registered (e.g. verifying webhook_id ownership via a stored mapping) rather than trusting the header value directly for tenant-sensitive operations.

### Proof of Concept
1. Attacker creates their own (free) Shopify store `attacker.myshopify.com` and installs the target app, which shares one `api_secret_key` across all installs.
2. Attacker triggers a real event (e.g. updates a product) so Shopify sends a genuinely-signed webhook to the app's endpoint: headers include `x-shopify-hmac-sha256: <valid HMAC of raw body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: products/update`, and some `raw_body`.
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker sends a new POST to the same webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `ShopifyAPI::Utils::HmacValidator.validate` succeeds because `to_signable_string` only checks `raw_body`, per [5](#0-4) .
6. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"`, per [3](#0-2) , even though the payload actually originated from the attacker's own store.
