### Title
Single global `maxOracleAge` staleness bound applied uniformly to all Chainlink feeds in SimplexPaymaster - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using two Chainlink feeds — a `nativeOracle` and each token's `tokenOracle` — and validates freshness with a single, contract-wide `maxOracleAge` value that is applied identically to every feed regardless of that feed's own heartbeat, exactly the bug class reported in the Renzo finding (one fixed `MAX_TIME_WINDOW` used to validate all Chainlink feeds regardless of their differing per-token/per-chain heartbeats).

### Finding Description
`_getOraclePrice` checks staleness the same way for both the native/USD feed and every registered token/USD feed: [1](#0-0) 

```
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
```

`maxOracleAge` is one storage variable shared by `nativeOracle` and **every** `TokenConfig.tokenOracle` registered via `RegisterToken`: [2](#0-1) 

Governance sets it once for the whole contract through `UpdateParams`, bounded only by a non-zero floor and a hard `MAX_ORACLE_AGE` (7 days) ceiling: [3](#0-2) [4](#0-3) [5](#0-4) 

There is no per-oracle or per-token heartbeat mapping — as the deployment script itself acknowledges, different Chainlink feeds run different heartbeats ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h"), and `maxOracleAge` is a single knob that must simultaneously fit the native feed and every registered token feed: [6](#0-5) [3](#0-2) 

This is the same root cause as the Renzo `M-03` finding: one fixed staleness threshold used to validate price data from feeds with materially different update cadences. If governance sets `maxOracleAge` loose enough to accommodate the slowest-heartbeat registered token (as intended, per the comment), every faster-heartbeat feed — including `nativeOracle`, which every single price computation depends on via `_tokenPrice` — inherits that same loose bound and can be treated as "fresh" long after it would normally have updated.

### Impact Explanation
`_tokenPrice` computes the ERC-20 amount charged for gas directly from `nativeUsd`/`tokenUsd`: [2](#0-1) 

Because this paymaster is fully permissionless (any UserOperation can invoke `fetchDetails`/pricing paths through the EntryPoint), an attacker who observes that a feed with a naturally short heartbeat has not refreshed for a period well beyond its intended cadence — but still within the loosely-configured global `maxOracleAge` — can submit UserOperations priced off that stale rate. Depending on the direction the underlying asset has moved, this lets the attacker pay materially less ERC-20 token than the true gas cost, draining native ETH from the paymaster's EntryPoint deposit/treasury reserve (the surplus/markup design is defeated), which is a concrete value-extraction/fund-loss vector, not merely a DoS. This mirrors the "consuming outdated prices" impact the Renzo report describes, translated to a value-transfer-denominating context instead of a mint-rate context.

### Likelihood Explanation
Reaching the vulnerable price path requires nothing privileged — any account can submit a UserOperation using this paymaster's `PERMIT`/`PERMIT2` modes, hitting `_tokenPrice → _getOraclePrice` on every gas-sponsored call. The precondition (a single `maxOracleAge` value forced to cover heterogeneous-heartbeat feeds) is a structural property of the deployed configuration rather than a rare edge case, and governance is explicitly documented as choosing the value to fit the "slowest" feed, guaranteeing faster feeds get a looser effective staleness bound than their own heartbeat implies. The team's own AI decision log confirms staleness-bound tightening (tying `validUntil` to oracle freshness) was considered and explicitly deferred as "out of scope," indicating the risk is known but unmitigated. [7](#0-6) 

### Recommendation
Replace the single global `maxOracleAge` with a per-oracle (per `nativeOracle` and per `TokenConfig`) staleness bound, set to a small buffer over that specific feed's own documented Chainlink heartbeat, mirroring the mitigation recommended in the referenced report (store a heartbeat/staleness mapping per token/feed rather than one contract-wide constant).

### Proof of Concept
1. Governance registers `tokenA` whose Chainlink feed has a 24h heartbeat and calls `UpdateParams` with `maxOracleAge = 86400` (near the max allowed by `MAX_ORACLE_AGE`) so `tokenA` prices don't spuriously revert, per the flow in `_setParams`/`RegisterToken`: [8](#0-7) .
2. `nativeOracle` (e.g. ETH/USD) has a much shorter effective heartbeat but its Chainlink node stalls (or is simply queried) 6–12 hours after its last update — well past its normal cadence, but still `< 86400` seconds old.
3. Native asset price moves materially in that window (e.g. drops).
4. An attacker submits a UserOperation through the paymaster; `_getOraclePrice(nativeOracle, ...)` at line 662-668 accepts the stale `updatedAt` because `block.timestamp - updatedAt <= maxOracleAge`, and `_tokenPrice` at lines 653-658 computes an ERC-20 charge based on the stale, higher native price, undercharging the attacker's token payment relative to true gas cost, draining paymaster reserves over repeated calls.

```text
    /// @dev Registers or updates a supported ERC-20 token with its token/USD feed.
    ///      Re-registering is also the recovery path for a misbehaving oracle.
    function _registerToken(address token, AggregatorV3Interface oracle) internal {
        if (token == address(0) || address(oracle) == address(0)) revert ZeroAddress();

        bool isNew = !tokenConfigs[token].active && address(tokenConfigs[token].tokenOracle) == address(0);

        tokenConfigs[token] = TokenConfig({
            tokenOracle: oracle,
            tokenOracleDecimals: oracle.decimals(),
            tokenDecimals: IERC20Metadata(token).decimals(),
            active: true
        });

        if (isNew) {
            registeredTokens.push(token);
        }

        emit TokenRegistered(token, address(oracle));
    }
```

```markdown
# 2026-08-19 — Not adopted: soft-failing the prefund, and oracle-derived validity bounds (#1071)

Rejected: returning `prefunded = false` instead of reverting in the mode-2 `_prefund`. Upstream advises it to protect bundler reputation, but reading EntryPoint v0.8 shows both outcomes are `revert FailedOp` — AA33 for a paymaster revert, AA34 for a sig-failure — so both revert `handleOps` identically. The change would trade the `Permit2Failed(token, reason)` diagnostic, which carries Permit2's own revert data, for no bundle-level benefit.

Also deferred at the maintainer's direction: bounding `validationData`'s `validUntil` by oracle freshness so bundlers drop soon-to-be-stale ops instead of building bundles that revert. Sound in principle and would have made stale-oracle failures expire cleanly, but it touches every pricing path and was out of scope for this pass.
```
