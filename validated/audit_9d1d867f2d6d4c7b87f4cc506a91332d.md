## Title
CORS Origin Allowlist Wildcard Subdomain Bypass via Improper Suffix Matching - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` implements wildcard CORS matching (`*.domain.com`) with a bare `strings.HasSuffix(originHost, allowedHost)` check that lacks a dot-boundary requirement. This lets any origin host that merely ends with the configured suffix string (e.g., `evilremix.com` against a `*.remix.com` allowlist entry) be treated as a valid subdomain, bypassing the intended origin allowlist protecting the gateway's internet-facing HTTP endpoint.

## Finding Description
In `core/services/gateway/network/httpserver.go`, the wildcard branch of `isAllowedOrigin` strips the `*.` prefix and then performs a raw suffix comparison: [1](#0-0) 

Because `strings.HasSuffix` has no notion of domain-label boundaries, `strings.HasSuffix("evilremix.com", "remix.com")` returns `true` even though `evilremix.com` is not a subdomain of `remix.com`. This directly gates the response header set in `handleRequest`: [2](#0-1) 

When `isAllowedOrigin` returns `true`, the server reflects the attacker's `Origin` header value verbatim into `Access-Control-Allow-Origin`, granting that origin cross-origin access to the gateway's HTTP API — a class of bug analogous to CVE-2024-0753 (subdomain/host boundary matching failures in allowlists). The exact match (`originHost == allowedHost`) and scheme/port checks above this branch do not mitigate the suffix flaw since the vulnerable branch is reached independently.

## Impact Explanation
This maps to the in-scope "gateway request impersonation / allowlist bypass" category. If an operator configures a wildcard entry such as `https://*.remix.com` in `CORSAllowedOrigins`, an external, unprivileged attacker who registers or controls any domain ending in that suffix (e.g., `evilremix.com`, `attacker-remix.com`) can have their page's cross-origin browser requests to the gateway accepted, with `Access-Control-Allow-Origin` reflecting the attacker's origin. This undermines the intended origin-scoping control on the gateway's public HTTP listener, letting an attacker-controlled web page interact with the gateway API as if it were a trusted subdomain.

## Likelihood Explanation
Exploitation requires only (1) the gateway operator to configure a wildcard `CORSAllowedOrigins` entry — a supported, documented configuration option present in `core/scripts/gateway/sample_config.toml` and `sample_config_tls.toml` — and (2) the attacker to register a domain sharing the suffix, both low-cost and requiring no privileges on the node/network. No mocking, internal access, or victim interaction beyond visiting the attacker's page is needed, making this directly reachable via a normal cross-origin browser request.

## Recommendation
Enforce a dot-boundary in the wildcard match, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```
This ensures `originHost` must equal the base domain or be a genuine subdomain (preceded by `.`), preventing suffix-only string matches like `evilremix.com` against `remix.com`.

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: ["https://*.remix.com"]`.
2. From an attacker-controlled page hosted at `https://evilremix.com`, issue a `fetch` request to the gateway's HTTP endpoint with `Origin: https://evilremix.com`.
3. `isAllowedOrigin` computes `allowedHost = "remix.com"` and evaluates `strings.HasSuffix("evilremix.com", "remix.com")` → `true`, so `handleRequest` sets `Access-Control-Allow-Origin: https://evilremix.com`, granting the untrusted origin CORS access.
4. A Go unit test calling `isAllowedOrigin("https://evilremix.com")` against a server configured with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it returns `true` (unexpectedly) demonstrates the bug directly against `core/services/gateway/network/httpserver.go`.
