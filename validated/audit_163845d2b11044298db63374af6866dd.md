### Title
Unchecked `assetReserve - virtualLtReserve` subtraction panics and permanently freezes trading once curve-only round-trips drain real LT below the virtual seed - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate`, `Bonding.previewLtUntilGraduation`, and `Bonding._prepareGraduationLiquidity` all recover the curve's real (non-virtual) LT raised as `assetReserve - _launchTimeVirtualLtReserve(...)`, with no floor check before the subtraction. In Solidity 0.8.24 an underflow here reverts with a raw arithmetic `Panic(0x11)`, exactly analogous to the Nimiq `Coin::sub` panic in the referenced advisory, where an attacker-reachable precondition (`min_cap > balance`) was not validated before subtracting.

### Finding Description
`_launchTimeVirtualLtReserve` recovers the pair's launch-time virtual LT reserve as an invariant identity: [1](#0-0) 

`canGraduate` uses this to compute the real LT raised without any bound check: [2](#0-1) 

The same unguarded pattern recurs in the graduation-preview view: [3](#0-2) 

and, most critically, in the phase-1 graduation state transition that is invoked inline from every buy that crosses the graduation trigger, as well as from the permissionless `triggerGraduation`: [4](#0-3) 

Notably, the developers were aware of exactly this underflow risk and defensively guarded a structurally identical subtraction elsewhere in the same file — but only in `finalizeGraduation`, not in `canGraduate` / `previewLtUntilGraduation` / `_prepareGraduationLiquidity`: [5](#0-4) 

The precondition `assetReserve >= _launchTimeVirtualLtReserve` holds at launch (`assetReserve` is initialized to exactly `virtualLtReserve` in `Router.addInitialLiquidity`, called from `_deployAndSeed`): [6](#0-5) 

but nothing in the curve's buy/sell path (`Router`, `Pair`) or in `Bonding.sell` re-asserts it. `Bonding.sell` only blocks a sell once the token is already graduatable — it does not prevent the *stored* `assetReserve` from being pushed back down toward, or transiently below, `virtualLtReserve` via ordinary buy/sell round-trips through the bonding-curve AMM, whose `Pair.swap` `+1` K-slack rounding (part of alt.fun's curve-fee-free AMM design) can leave the pool with slightly less real LT after a full round trip than before it. Because `canGraduate` is called unconditionally on **every** buy (`_executeBuy` → `if (canGraduate(tokenAddress))`) and on every sell (`Bonding.sell` → `if (canGraduate(tokenAddress))`), once `assetReserve` is driven below the recovered virtual reserve, the subtraction panics and every subsequent buy and sell for that token reverts with an unhandled `Panic(0x11)` — the token's curve is permanently bricked, since even `triggerGraduation` and `previewLtUntilGraduation` share the same unguarded subtraction and cannot be used to recover it either. [7](#0-6) [8](#0-7) 

### Impact Explanation
This permanently freezes trading (and therefore all trapped LT/curve tokens) for the affected token: `Zap.buy`/`Zap.sell` call into `Bonding.buy`/`Bonding.sell`, both of which unconditionally evaluate `canGraduate`, so once the underflow condition is hit, no further trade, no `triggerGraduation`, and no graduation can ever execute for that token — funds parked on the curve become permanently stuck. This is a direct, unprivileged-reachable denial-of-service with fund-freezing consequences, matching the "Medium" class of the referenced advisory (an attacker-reachable precondition violation causing an unchecked subtraction to panic).

### Likelihood Explanation
Reachability depends on whether repeated buy/sell round trips through the curve's constant-product `Pair.swap` (with its documented `+1` K-slack) can, over enough cycles, net-decrease the stored `assetReserve` below the recovered `virtualLtReserve` before `tokenBalance() == 0`/USD-threshold graduation is reached. The `+1` K-slack is called out explicitly as part of alt.fun's AMM design; I was not able to fully re-derive from `Pair.sol` (not read in this pass) the exact sign/direction of that rounding to conclusively prove the drain direction and required number of round trips, so likelihood should be validated against `Pair.swap`'s exact rounding before treating this as confirmed-exploitable versus only latent/defense-in-depth-missing.

### Recommendation
Add an explicit floor check (mirroring the saturating pattern already used in `finalizeGraduation`) before every `assetReserve - _launchTimeVirtualLtReserve(...)` subtraction in `canGraduate`, `previewLtUntilGraduation`, and `_prepareGraduationLiquidity`, returning/treating the real-raised amount as `0` when `assetReserve <= virtualLtReserve`, instead of letting the subtraction panic.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a minimal seed buy (`MIN_SEED_USDC`), establishing `assetReserve == virtualLtReserve` initially (per `_deployAndSeed`/`Router.addInitialLiquidity`).
2. Repeatedly call `Zap.buy` then `Zap.sell` on the same token in tight round trips before the USD/supply graduation trigger is hit, exploiting `Pair.swap`'s `+1` K-slack rounding on each leg so that the pool's stored `assetReserve` (real LT) trends downward relative to the fixed virtual seed recovered by `_launchTimeVirtualLtReserve`.
3. Once `assetReserve` dips below `_launchTimeVirtualLtReserve(token, pair)`, the next call to `Bonding.canGraduate` (invoked from any `buy`/`sell`) executes `assetReserve - _launchTimeVirtualLtReserve(...)` and reverts with `Panic(0x11)` (arithmetic underflow), rather than a clean revert.
4. Because `canGraduate` is invoked unconditionally inside `Bonding.buy`/`Bonding.sell`, every subsequent trade transaction on this token now reverts, and `triggerGraduation`/`previewLtUntilGraduation` share the identical unguarded subtraction — freezing the token's curve and any funds still parked in it, with no owner-privileged recovery path exposed in `Bonding.sol`.

        address trader

        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];

        if (info.lifecycle == Lifecycle.Graduating) revert TokenIsGraduating();
        if (info.lifecycle != Lifecycle.Curve) revert TokenNotTrading();

        // `triggerGraduation`; rejecting here stops any router that skipped
        // that step from un-ripening a ready graduation.

        emit Trade(tokenAddress, trader, false, assetOut, amountIn, newCurveSupply, newLtReserve);

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;
