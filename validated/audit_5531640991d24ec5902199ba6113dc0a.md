## Title
Withdrawal validation fails to reject the zero/burn address for Sui, Aptos, Starknet, Movement, and other non-EVM chains, enabling misdelivery of funds to an unspendable address - (File: `packages/intents-sdk/src/lib/validateAddress.ts`)

### Summary
The reported bug is that Gearbox's `CreditManager.sol` never checks that `to != address(0)`, allowing a transfer to the zero address. The same class of defect exists in this SDK's `validateAddress` function: for EVM chains the zero address (and the `...dead` burn address) is explicitly excluded, but for several other supported chains — Sui, Aptos, Starknet, Movement — the validator's regex/logic happily accepts the all-zero address as "valid," so a withdrawal to that address passes `validateWithdrawal()` in every bridge that relies on `validateAddress()`.

### Finding Description
`validateAddress()` dispatches per-chain to different validator functions [1](#0-0) . For EVM chains, `validateEthAddress` explicitly special-cases and rejects the zero address and the `0x…dead` burn address before delegating to `isAddress`: [2](#0-1) 

However, the equivalent "null/burn address" guard is missing for other chains that have their own well-known null address representable purely as all-zero bytes:

- Sui: `validateSuiAddress` is a bare regex `^(?:0x)?[a-fA-F0-9]{64}$`, which matches an all-zero 64-hex-char string. [3](#0-2) 
- Aptos: `validateAptosAddress` is `^0x[a-fA-F0-9]{64}$`, likewise matching all zeros. [4](#0-3) 
- Starknet: `validateStarknetAddress` is `^0x[a-fA-F0-9]{1,64}$`, which accepts `0x0` as a "valid" (short-form) address. [5](#0-4) 
- Movement: `validateMovementAddress` treats any hex string of length ≥ 60 as valid unconditionally (no zero check), and pads/accepts all-zero short forms too. [6](#0-5) 

These validators are the sole gate used by every bridge's `validateWithdrawal()` (Hot Bridge, Omni Bridge, POA Bridge, Direct Bridge, Intents Bridge) to decide whether a `destinationAddress` is acceptable: [7](#0-6) [8](#0-7) [9](#0-8) 

None of these bridges perform any additional zero-address sanity check beyond calling `validateAddress`, and the follow-up check `DestinationAddressMatchesTokenAddressError` only compares against the specific token's own contract/origin address, not the chain's null address — so it does not catch this case either. This exactly mirrors the reported bug class: an unprivileged, unchecked equality (`destinationAddress == <chain-null-address>`) that the validation layer was supposed to reject but does not, for a subset of supported chains.

### Impact Explanation
If a withdrawal is created with a destination address equal to the zero/null address on Sui, Aptos, Starknet, or Movement (e.g., due to a caller bug, a copy-paste error, or a malicious/compromised integrator UI prefilling a bad default), the SDK's own validation will not block it. The withdrawal intent will be built and (if unrelated on-chain protections in the destination bridge contract on that specific chain do not independently reject it) funds could be irrecoverably sent to an address nobody controls — a "funds delivered to a wrong address with no recovery" scenario, matching the Critical/High impact bucket in scope.

### Likelihood Explanation
The condition requires only that a `destinationAddress` value equal to the chain's zero address be passed to `createWithdrawal`/`validateWithdrawal` — no privileged actor, no relayer or bridge misbehavior, no external RPC assumptions are needed. Given `validateAddress` is the only defense, and it demonstrably special-cases the zero address for EVM but omits the equivalent check for Sui/Aptos/Starknet/Movement, this is a straightforward, reachable gap purely in first-party SDK code within scope.

### Recommendation
Add an explicit rejection of the all-zero (and any other well-known chain-specific null/burn) address in `validateSuiAddress`, `validateAptosAddress`, `validateStarknetAddress`, and `validateMovementAddress`, mirroring the guard already present in `validateEthAddress` (`packages/intents-sdk/src/lib/validateAddress.ts:105-113`). Audit the remaining chain validators (Aleo, Cardano, TON, Zcash, Tron, etc.) for the same class of missing null-address exclusion.

### Proof of Concept
```ts
import { validateAddress } from "packages/intents-sdk/src/lib/validateAddress";
import { Chains } from "packages/intents-sdk/src/lib/caip2";

// All of these incorrectly return `true`, unlike the EVM case which returns `false`
validateAddress("0x" + "0".repeat(64), Chains.Sui);      // -> true (should be false)
validateAddress("0x" + "0".repeat(64), Chains.Aptos);    // -> true (should be false)
validateAddress("0x0", Chains.Starknet);                 // -> true (should be false)
validateAddress("0", Chains.Movement);                   // -> true via padStart (should be false)

// Compare with EVM, which is correctly guarded:
validateAddress("0x0000000000000000000000000000000000000000", Chains.Ethereum); // -> false
```
Any of the accepted zero-address strings above would pass unmodified through `HotBridge.validateWithdrawal` / `OmniBridge.validateWithdrawal` / `PoaBridge.validateWithdrawal`, since these bridges rely exclusively on `validateAddress` for format/null-address screening.

```typescript
function validateEthAddress(address: string) {
	if (
		address === "0x0000000000000000000000000000000000000000" ||
		address.toLowerCase() === "0x000000000000000000000000000000000000dead"
	) {
		return false;
	}
	return isAddress(address, { strict: true });
```

```typescript
function validateMovementAddress(address: string) {
	let parsedAddress = address;
	if (address.startsWith("0x")) {
		parsedAddress = address.slice(2);
	}

	if (parsedAddress.length === 0 || parsedAddress.length > 64) {
		return false;
	}

	if (!/^[a-fA-F0-9]+$/.test(parsedAddress)) {
		return false;
	}

	if (parsedAddress.length >= 60) {
		return true;
	}

	const paddedAddress = parsedAddress.padStart(64, "0");
	return /^0{63}[0-9a-fA-F]$/.test(paddedAddress);
}
```
