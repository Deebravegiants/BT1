### Title
Unprivileged ETH sent directly to `IntentGatewayV2` via its bare `receive()` is silently absorbed and only recoverable by governance, never by the sender - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2` (and its Tron/SDK counterparts) exposes a no-op `receive() external payable {}` so it can accept escrow deposits from `placeOrder` and swept balances from `CallDispatcher`. Because the function performs no bookkeeping, any account that sends ETH to the gateway directly (instead of calling `placeOrder`) has those funds absorbed into the contract's general balance with no order created, no commitment recorded, and no `_orders` entry crediting the sender.

### Finding Description
`placeOrder` is the only function that converts `msg.value` into an accounted escrow entry, via `_orders[commitment][token]` bookkeeping [1](#0-0) . In contrast, the bare `receive()` performs no such accounting at all [2](#0-1) .

Once ETH lands in the contract through `receive()`, the only extraction path is `_sweepDust`, invoked exclusively from `onAccept` when the incoming request's `RequestKind` is `SweepDust` and its `source` equals the registered Hyperbridge chain — i.e., only governance can trigger it, sending funds to a beneficiary of its choosing [3](#0-2) [4](#0-3) . There is no self-service withdrawal function for a sender who mistakenly transfers ETH directly to the gateway; the original depositor cannot reclaim their funds, and governance decides who ultimately receives the swept balance (which need not be the original sender).

### Impact Explanation
Any ETH sent directly to `IntentGatewayV2` (e.g., a wallet doing a plain transfer instead of calling `placeOrder`, or a user mis-copying the gateway address as a deposit target) is permanently locked from the sender's perspective. Recovery requires a governance-initiated `SweepDust` cross-chain message, and even then funds go to whatever `beneficiary` governance specifies — not necessarily back to the original sender. This matches the reported bug class: an unprivileged party's ETH enters a contract with a bare `receive()` but produces no corresponding credit/mint, resulting in effective freezing of the sender's funds.

### Likelihood Explanation
Likelihood is driven by ordinary user error rather than an active exploit: any account (wallet, exchange withdrawal, or misconfigured integrator) that sends ETH to the well-known, publicly deployed `IntentGatewayV2` address without calling `placeOrder` triggers this loss. Given the gateway is meant to receive native-token deposits, users are plausibly conditioned to send ETH to it directly.

### Recommendation
Either (a) remove the bare `receive()` and require all native-token intake to flow through `placeOrder`'s explicit accounting, or (b) track a per-sender "unaccounted deposit" ledger inside `receive()` and expose a permissionless `withdrawStray()` function so the original sender — not only governance — can reclaim ETH sent outside of `placeOrder`.

### Proof of Concept
1. Attacker/careless user calls `intentGateway.call{value: 1 ether}("")` directly (no calldata), which resolves to `receive()`.
2. `receive()` executes with an empty body — no `Order`, no `_orders[commitment][...]` entry, no `OrderPlaced` event.
3. `address(intentGateway).balance` increases by 1 ETH, but nothing is escrowed on the sender's behalf; `_filled`/`_orders` mappings show no trace of the sender.
4. The sender has no function to call to get the 1 ETH back; only a Hyperbridge-governance-originated `SweepDust` message (verified in `testSweepDustNative`, [5](#0-4) ) can move that ETH out, and it goes to whatever beneficiary governance names, not necessarily the original sender.

    function _sweepDust(SweepDust memory req) internal {
        uint256 outputsLen = req.outputs.length;
        for (uint256 i; i < outputsLen;) {
            TokenInfo memory info = req.outputs[i];
            address token = address(uint160(uint256(info.token)));
            uint256 amount = info.amount;

            if (token == address(0)) {
                _sendValue(req.beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(req.beneficiary, amount);
            }
            unchecked {
                ++i;
            }
            emit DustSwept(token, amount, req.beneficiary);
        }
