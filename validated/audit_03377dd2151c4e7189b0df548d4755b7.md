Confirmed: `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . The `topic` and `shop` accessors are read straight from HTTP headers with no cryptographic binding to the body or to each other [3](#0-2) . `Registry.process` raises `Errors::InvalidWebhookError` only when the body's HMAC fails, then dispatches to the handler using `request.topic` and `request.shop` from the same unauthenticated headers [4](#0-3) , and `WebhookMetadata.shop`/`.topic` are passed straight through into the handler [5](#0-4) .

This is a real structural gap: the signature never binds `topic`/`shop-domain`, only the raw body. But turning that gap into an exploit requires the attacker to actually control an HTTP request reaching the app's public webhook endpoint with a valid body+HMAC pair for headers they've altered. The threat model here grants the attacker their own dev shop, their own webhook endpoint, and their own validly-signed webhook deliveries — meaning they can capture a genuine `(raw_body, hmac)` pair issued for their own shop/topic, then re-POST that exact body+HMAC to the app's real webhook route with a forged `x-shopify-shop-domain` and/or `x-shopify-topic` header. Since `HmacValidator.validate` never inspects headers, this forged request passes validation and is routed to whichever handler is registered for the spoofed topic, carrying `WebhookMetadata.shop` set to the attacker-chosen (potentially victim) shop domain.

This matches the reported bug precisely: `Registry.process` provides no secondary consistency check binding `request.topic`/`request.shop` to the signed body, so a validated request does not imply the topic/shop are trustworthy — only that the body bytes weren't tampered with.

### Title
Webhook HMAC signs only the raw body, not `topic`/`shop-domain` headers, allowing topic/shop spoofing via replay - (`lib/shopify_api/webhooks/registry.rb`)

### Summary
`Registry.process` treats `Utils::HmacValidator.validate(request)` as the sole authenticity gate for a webhook, but the HMAC is computed over `request.to_signable_string` which is just `@raw_body` [1](#0-0) . Since `topic` and `shop` are read from unsigned headers [3](#0-2) , an attacker who has legitimately received one validly-signed webhook (body+HMAC) for their own dev shop can replay that same body+HMAC to the app's public webhook endpoint with a forged `shop-domain`/`topic` header pair, and `Registry.process` will accept it and dispatch the handler with attacker-chosen `WebhookMetadata.shop`/`.topic` values [6](#0-5) .

### Finding Description
The broken binding: `HmacValidator.validate(request) == true` is treated as implying `request.shop` and `request.topic` are authentic, but the equality that actually holds is only `HMAC-SHA256(secret, request.raw_body) == received_hmac` — a property of the body alone [2](#0-1) . `request.topic` and `request.shop` are plain header reads with zero cryptographic linkage to the body or the HMAC [3](#0-2) .

Attack flow: the attacker registers their own webhook endpoint on their own dev shop and lets Shopify deliver a genuine webhook (any topic they can trigger, e.g., an order/product event), capturing the exact `raw_body` and the `x-shopify-hmac-sha256` value that shipped with it. Because the app's api_secret_key is shared across all shops installing that app (not per-shop), this HMAC is valid for that raw body under the app's secret regardless of which shop it nominally came from. The attacker then sends a new POST directly to the app's public webhook route, reusing that same body and HMAC value, but substituting `x-shopify-shop-domain` and/or `x-shopify-topic` with values of their choosing (e.g., another merchant's `.myshopify.com` domain, or a topic like `shop/redact`/`customers/data_request` that the app has a handler for). `Registry.process` only calls `Errors::InvalidWebhookError` on HMAC mismatch [7](#0-6) ; since the body and HMAC are untouched, validation passes, and the code proceeds to look up `@registry[request.topic]` and invoke `handler.handle` with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [8](#0-7) , both taken from the now-forged headers.

No code path in `registry.rb`, `request.rb`, or `hmac_validator.rb` cross-checks `shop`/`topic` against anything derived from the signed body. `ShopValidator`, `JwtPayload`'s `aud` check, and `HttpRequest#verify` are unrelated to this inbound-webhook path and do not intervene here.

### Impact Explanation
The app-level handler receives a `WebhookMetadata` whose `shop` and `topic` fields are attacker-controlled while `body` is the original, differently-sourced payload. Any host app that uses `data.shop` from `WebhookMetadata` as the trusted merchant identifier to route data-affecting actions (a documented, expected usage pattern, e.g. mandatory `shop/redact`/`customers/data_request`/`customers/redact` handlers) can be made to act against a merchant/shop the attacker does not control, using an attacker-supplied body. This is a scope-binding bypass: the gem's only authenticity gate (HMAC) does not enforce that the validated body actually belongs to the claimed shop/topic, matching the "High - scope or expiry check bypass" category. Blast radius is cross-tenant to the extent the host app trusts `data.shop`/`data.topic` without independent verification, which is exactly what this gem's own API encourages callers to do.

### Likelihood Explanation
Preconditions: the app must have a webhook handler registered for a topic the attacker wants to spoof (trivial for mandatory topics), and the attacker needs one genuinely-signed webhook body+HMAC pair, obtainable for free by installing the app on their own dev shop and triggering any event. No secrets, tokens, or privileged access are required — only the ability to POST directly to the app's public webhook URL, which is by design internet-reachable. This is fully repeatable against arbitrary shop-domain values since the header is never validated against Shopify's actual shop registry inside this gem.

### Recommendation
Bind `topic` and `shop-domain` into the signed material checked by this gem, or otherwise validate them independently of the header values — e.g., cross-check `request.shop` against the session/shop the webhook registration was created for, verify the sending IP/source against Shopify's documented webhook IP ranges, or extend `to_signable_string`/`HmacValidator` to include topic and shop in the string that's HMAC-verified (matching how HMAC is verified in other Shopify webhook implementations that canonicalize headers into the signed payload). At minimum, document that host apps must not trust `WebhookMetadata.shop`/`.topic` without an out-of-band shop-existence check.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_accepts_forged_topic_and_shop_with_valid_body_hmac
  handler_called = false
  captured_shop = nil
  captured_topic = nil

  handler = TestHelpers::FakeWebhookHandler.new(
    lambda do |data|
      captured_shop = data.shop
      captured_topic = data.topic
      handler_called = true
    end,
  )

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "shop/redact", path: "path", delivery_method: :http, handler: handler,
  )

  # Genuine HMAC computed over the raw body only, exactly as HmacValidator does
  raw_body = "{}"
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

  # Attacker-forged headers: topic/shop-domain do not match what the body was "meant" for
  forged_headers = {
    "x-shopify-topic" => "shop/redact",
    "x-shopify-hmac-sha256" => Base64.encode64(hmac),
    "x-shopify-shop-domain" => "victim-shop.myshopify.com",
    "x-shopify-webhook-id" => "forged-id",
    "x-shopify-api-version" => "2024-01",
  }

  request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

  # No InvalidWebhookError is raised despite header/topic mismatch with the original signer's intent
  ShopifyAPI::Webhooks::Registry.process(request)

  assert(handler_called)
  assert_equal("victim-shop.myshopify.com", captured_shop)
  assert_equal("shop/redact", captured_topic)
end
```
This demonstrates that `Registry.process` never raises `Errors::InvalidWebhookError` for header/topic/shop spoofing as long as the body+HMAC pair is valid, and that the forged `shop`/`topic` values flow unchecked into `WebhookMetadata` delivered to the handler.
