Audit Report

## Title
CORS origin allowlist bypass via unanchored suffix matching in Gateway HTTP server - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function validates wildcard CORS entries (e.g., `*.remix.com`) using `strings.HasSuffix(originHost, allowedHost)` without verifying a label boundary (a preceding literal dot). This allows an attacker who registers a domain that merely ends with the same character sequence as the allowlisted domain (e.g., `evilremix.com` for allowlist `*.remix.com`) to be treated as a trusted CORS origin.

## Finding Description
`isAllowedOrigin` splits the `Origin` header and each configured `CORSAllowedOrigins` entry via `splitURL`, then for entries prefixed with `*.` strips the prefix and performs a bare suffix check: [1](#0-0) . Because `strings.HasSuffix` has no boundary requirement, `HasSuffix("evilremix.com", "remix.com")` evaluates to `true`, incorrectly matching an unrelated domain as if it were a genuine subdomain of `remix.com`. This function directly gates the CORS response headers in `handleRequest`: [2](#0-1) . When `isAllowedOrigin` wrongly returns `true`, the server reflects `Access-Control-Allow-Origin: <attacker origin>`, granting the attacker's page the same cross-origin privileges as a legitimate subdomain, including reading responses from `ProcessRequest` which processes JWT/allowlist-gated JSON-RPC requests. No other check anchors the suffix match to a dot boundary anywhere in the function.

## Impact Explanation
This is a genuine allowlist bypass in code logic (not a misconfiguration): an operator legitimately configuring a wildcard CORS entry like `*.remix.com` — a supported and documented feature of `CORSAllowedOrigins` — unintentionally also allowlists any domain ending in `remix.com`, such as attacker-registered `evilremix.com` or `notremix.com`. This lets an unprivileged, unrelated third party have their origin treated as trusted, enabling cross-origin reads of Gateway JSON-RPC responses (a gateway request/response impersonation and cross-user response corruption class impact) for any victim whose browser sends credentialed/authenticated requests from the attacker's page to the Gateway endpoint.

## Likelihood Explanation
Exploitation requires only registering an inexpensive domain string that lexically ends with the configured allowlisted suffix — a trivial, low-cost, and fully attacker-controlled action requiring no compromise of Chainlink infrastructure, no operator/admin role, and no host access. The vulnerable comparison operates purely on the client-supplied `Origin` header, which is entirely attacker-controlled, making the bug directly and repeatably triggerable by an unprivileged actor.

## Recommendation
Replace the unanchored `strings.HasSuffix` check with a boundary-aware comparison, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
This ensures only true subdomains (separated by a literal dot) of the allowlisted domain are accepted, not arbitrary hostnames sharing a trailing substring.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. From a browser page hosted at `https://evilremix.com`, send a fetch/XHR request to the Gateway's configured `Path` endpoint with header `Origin: https://evilremix.com`.
3. `splitURL` parses `originHost = "evilremix.com"`; `allowedHost` becomes `"remix.com"` after stripping the `*.` prefix.
4. `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, so `isAllowedOrigin` returns `true`, and the server responds with `Access-Control-Allow-Origin: https://evilremix.com`.
5. A Go unit test calling `httpServer.isAllowedOrigin("https://evilremix.com")` with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting the (currently incorrect) `true` result would demonstrate the bypass; asserting `false` would validate the fix.
