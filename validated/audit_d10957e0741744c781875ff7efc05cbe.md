## Title
Webhook shop/topic identity is not bound to the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but its `to_signable_string` only returns the raw request body. `Utils::HmacValidator` therefore only proves the body was signed with the app's secret — it says nothing about which shop or topic that signature belongs to. `Registry.process` nonetheless trusts these header-derived fields to build the `WebhookMetadata` handed to the app's handler.

### Finding Description
The webhook HMAC check is:
```ruby
# lib/shopify_api/webhooks/request.rb
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

and

```ruby
# lib/shopify_api/utils/hmac_validator.rb
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, `api_version` come straight from attacker-controllable headers:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`Registry.process` validates only the body's HMAC, then dispatches using the unauthenticated `shop`/`topic` fields:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The binding that should hold is:

`HMAC_valid(body) ⟹ (shop, topic) == (shop, topic) that Shopify actually sent for this body`

What is actually enforced is only:

`HMAC_valid(body) ⟹ body is unmodified`

Since a single app's `client_secret` is shared across every shop that installs it, any shop owner (an unprivileged actor with respect to other tenants) receives legitimately HMAC-signed webhook deliveries for their own store. That body+HMAC pair remains valid regardless of the `X-Shopify-Shop-Domain` (or topic/webhook-id) header sent alongside it, because those headers are never part of the signed data. An attacker can therefore replay a legitimately-signed body to the app's public webhook endpoint while substituting the shop-domain header to name a victim shop, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the shop-identity binding used to select the tenant context for incoming webhook data, matching the "Critical — cross-tenant access" bucket: an app relying on `WebhookMetadata#shop` (the value this gem promises is authenticated) to determine whose records to create/update/delete can be made to apply attacker-supplied, attacker-controlled body content under a different, victim merchant's identity, since the gem never actually authenticates that binding.

### Likelihood Explanation
Any internet user who installs the target app on their own store (a normal, unprivileged action) automatically receives valid signed webhooks for their own shop, giving them everything needed (a valid body+HMAC pair) to mount the header-substitution replay against the app's public webhook endpoint — no special privileges, secrets, or victim cooperation required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the HMAC signature. Since Shopify does not include shop/topic in the signed payload options exposed by this gem, `Registry.process`/`Utils::HmacValidator` should require the caller to additionally verify `request.shop` against an out-of-band trusted source (e.g. an active session/install record for that shop) before trusting it as tenant context, and this expectation should be enforced or explicitly surfaced in `WebhookMetadata`, rather than silently treated as authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) with a legitimate `X-Shopify-Hmac-Sha256` computed by Shopify over the JSON body using the app's shared `client_secret`.
2. Attacker captures the raw body and the `X-Shopify-Hmac-Sha256` value.
3. Attacker crafts a new HTTP request to the app's webhook endpoint reusing the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only [1](#0-0)  and it matches, so `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to process attacker-controlled data under the victim tenant's identity.
