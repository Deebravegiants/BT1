### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` and handed to `WebhookHandler#handle` are read from unauthenticated HTTP headers that are never included in the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)` [1](#0-0) , which computes the HMAC over `verifiable_query.to_signable_string`, i.e. `@raw_body` only [2](#0-1) . The `shop` attribute that is subsequently used to build `WebhookMetadata` and passed to the app's handler is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to that value [3](#0-2) . The `topic`, `webhook_id`, and `api_version` headers are likewise excluded from the signed bytes [4](#0-3) .

This breaks the intended identity binding: `hmac_valid(raw_body) == true` is treated as equivalent to `shop_header == origin_shop`, but the HMAC only proves `bytes_verified == raw_body`, not `shop_header == shop_that_produced(raw_body)`. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4)  and instructs app developers to trust `data.shop` for tenant routing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5)  and `WebhookMetadata#shop` is populated straight from `request.shop` [7](#0-6) . Because the header is outside the signed envelope, any request whose body happens to carry a valid HMAC for the app's secret (for example, a genuine webhook the attacker's own shop legitimately received, since the attacker is a real merchant with a working installation and thus receives real, validly-signed webhook deliveries for their own tenant) can be replayed to the same endpoint with the `shop-domain` header rewritten to a victim shop's domain, and the signature check in `HmacValidator.validate` will still pass because it never looks at that header [8](#0-7) .

### Impact Explanation
An attacker who is themselves an installed/authenticated merchant of the app (unprivileged with respect to other tenants) can cause the app to misattribute webhook payloads to a different shop's tenant context. Since apps are told to key their per-shop job queues, database writes, or session lookups off `data.shop`, this is a cross-tenant confusion vector: data legitimately generated for shop A can be injected into shop B's processing pipeline while still passing this gem's own "verify the request did indeed come from Shopify" check. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker needs a valid signed webhook body for the target app (trivially obtainable by installing the app on their own shop and triggering the relevant webhook topic themselves), plus the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header — both of which are within reach of any unprivileged internet user who can install the app. No access token, `client_secret`, or privileged credential is required.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api_version`, `webhook_id`) header values in the signable string used for HMAC verification, or have `Registry.process`/`WebhookHandler` cross-check the header-derived `shop` against a shop known to be legitimately associated with the webhook (e.g. validate it against the currently registered/expected shop for that subscription) before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and trigger a webhook topic the app subscribes to (e.g. `orders/create`); Shopify delivers a POST with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared secret, and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture this raw request (attacker controls their own client/network path since it is their own shop's delivery).
3. Replay the identical `raw_body` (and thus identical, still-valid HMAC) to the same app endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged header [9](#0-8) , `HmacValidator.validate` passes because it only checks `@raw_body` [10](#0-9) , and `Registry.process` invokes the app handler with `WebhookMetadata(shop: "victim.myshopify.com", ...)` even though the payload actually originated from the attacker's own shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
