### Title
Webhook HMAC only covers the raw body, letting an attacker forge the shop/topic/webhook-id identity bound to a valid signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an HMAC-valid webhook as fully authenticated and hands the `shop`, `topic`, and `webhook_id` values straight to the app's handler, but the HMAC signature computed by `ShopifyAPI::Webhooks::Request` only covers the raw request body — not those header-derived identity fields. This breaks the binding "HMAC-verified sender == shop attributed to the handler," letting a merchant who has installed the app (and therefore legitimately receives real webhook body/HMAC pairs for their own shop) replay that exact body+signature to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to point at a different, victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`: [2](#0-1) 

`Registry.process` accepts the request once this body-only HMAC checks out, then forwards the *unauthenticated* `shop`, `topic`, and `webhook_id` fields (which are read straight from HTTP headers) to the app's handler as trusted metadata: [3](#0-2) [4](#0-3) 

The library's own documentation tells app authors that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is safe metadata to key business logic on: [5](#0-4) [6](#0-5) 

So the equality that should hold is: `shop bound by the verified signature == shop delivered to the handler`. In reality the signature binds nothing about `shop`/`topic`/`webhook_id`, so any attacker who can produce one legitimate `(raw_body, hmac)` pair (e.g., by installing the app on their own store and capturing a real webhook delivery, since the HMAC is computed with the app's shared `client_secret`) can resubmit the identical body and HMAC to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming an arbitrary victim shop. `HmacValidator.validate` still returns `true` (it never looks at the shop header), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`.

### Impact Explanation
Apps built on this gem are documented to trust `data.shop` from `WebhookMetadata` as the tenant identifier for looking up sessions, updating per-merchant records, or driving downstream API calls. An attacker able to forge the shop attribution of a validly-signed webhook payload can inject or misattribute events to a different tenant (cross-tenant access), potentially causing another merchant's data to be modified using attacker-supplied body content, or the attacker's own actions to be laundered under a victim shop's identity. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires a merchant to install the app (a normal, unprivileged onboarding action) to obtain one legitimate `(raw_body, hmac)` pair from a real webhook delivery, then replay it to the public webhook endpoint with a modified shop header — no access to `api_secret_key`, access tokens, or privileged accounts is needed. The webhook endpoint is by design internet-reachable and unauthenticated apart from the HMAC.

### Recommendation
Include the shop domain, topic, and webhook ID in `to_signable_string` (or otherwise cryptographically bind them), or require `Registry.process` to independently verify that the `shop` header corresponds to a shop with an active app installation/session before trusting it, rather than passing header-derived fields through as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to deliver a real webhook (e.g., `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
2. Attacker replays the exact captured HTTP request to the app's webhook endpoint, but rewrites the header `x-shopify-shop-domain` to `victim-shop.myshopify.com` (keeping body `B` and `x-shopify-hmac-sha256: H` unchanged).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H})` is constructed; `HmacValidator.validate` recomputes `HMAC_SHA256(client_secret, B)` which still equals `H`, so validation passes.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled data under the victim's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
