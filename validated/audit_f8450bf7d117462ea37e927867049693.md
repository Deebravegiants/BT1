### Title
`flash_position` permanently locks callback-delivered tokens on the controller when they are not declared in `collaterals`/`refund_assets` — ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
Analogous to the `xcall` relayer-fee lock, `flash_position` forwards value through a settlement hop where any token arriving at the controller that was not pre-declared is neither credited nor refunded, and the controller exposes no sweep/rescue entrypoint. Once the call finalizes, those tokens are locked on the controller contract forever — the caller has no "increase the fee / update the route" equivalent to recover them.

### Finding Description
`process_flash_position` snapshots controller token balances for two fixed lists — `collaterals` (deposit with minima) and `refund_assets` (refund to caller) — before invoking the receiver callback [1](#0-0) . After the callback it processes only those two lists: `collect_collateral_deposits` deposits declared deltas and `refund_listed_assets` refunds declared deltas [2](#0-1) . The docs confirm "Undeclared callback assets receive neither credit nor refunds. There is no controller sweep endpoint" [3](#0-2) , and a grep over production contracts shows no `sweep`/`rescue`/`recover` function on the controller or pool — only the out-of-scope swap-aggregator has `sweep_balance`. A dedicated test even asserts that pre-existing token balances on the controller are intentionally never touched [4](#0-3) .

The lists are bounded (`refund_assets.len() <= max_supply_positions` [5](#0-4) ), so a receiver that legitimately produces more distinct tokens than fit the lists — or a caller that simply omits a token the callback will deliver — has a structural ceiling on what can ever be recovered.

### Impact Explanation
Any token balance the callback (or any prior stranded transfer) leaves on the controller is permanently frozen. The position still finalizes solvent — the protocol keeps the account healthy while the user's tokens sit unclaimable on the controller with no recovery path for anyone, including governance. This is permanent freezing of user funds, matching the source report's "claim locked inside Connext" shape.

### Likelihood Explanation
Reachable by any unprivileged caller via `flash_position` with their own Wasm receiver (`require_wasm_receiver`, `is_flashloanable` market) [6](#0-5) . Likelihood depends on a receiver delivering an undeclared token — e.g., a multi-output swap, a pool emitting a bonus/reward token, or a caller hitting the `max_supply_positions` bound on the refund list — plausible in composed flows but not automatic, so Medium rather than High.

### Recommendation
Add a bounded recovery path: either treat every positive post-callback controller balance delta in listed markets as a refund candidate (sweep a per-asset "all leftovers" mode), or add an owner-gated `sweep`/`rescue_token` entrypoint for balances exceeding accounted liabilities — mirroring the report's recommendation to give the beneficiary a way to unstick the settlement.

### Proof of Concept
1. Alice deploys a flash receiver and calls `controller.flash_position(caller=alice, account_id=0, debt=USDC, collaterals=[(XLM, min>0)], refund_assets=[USDC])`.
2. Inside `execute_flash_position`, the receiver transfers the declared XLM collateral plus an extra token `B` (a listed spoke asset omitted from both lists) to the controller.
3. Call succeeds: collateral deposits measured, USDC delta refunded, account finalized solvent.
4. `B` tokens remain on the controller. No entrypoint (`supply` requires an existing position and only pulls from caller; `refund_listed_assets` ran only for declared assets; no sweep exists) can ever move them — permanently frozen.
