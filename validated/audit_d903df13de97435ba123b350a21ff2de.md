## Summary

`aptos_framework::object::root_owner` walks an object's ownership chain without the cycle-nesting bound (`MAXIMUM_OBJECT_NESTING`) that every other ownership-chain walker in the same module enforces (`owns`, `verify_ungated_and_descendant`). Because `object::transfer`/`transfer_raw_inner` never rejects transferring an object to itself, any object owner can create a 1-cycle in the ownership graph (`ObjectCore.owner == self`) with an ordinary, unprivileged `object::transfer` call. Any code path that calls `root_owner()` on such an object can no longer terminate. The only current caller of `root_owner()` outside tests is the lazy-module-self-initialization security gate (`init::assert_may_self_initialize`, invoked transitively by `init::internal_maybe_initialize` and recorded by `code::publish_package`), so an object that has been self-transferred permanently loses the ability to complete self-initialization — any capability (mint/transfer refs, resource-account signer, etc.) that the module's init logic was supposed to move under that object's signer can never be produced again.

### Title
Unbounded ownership-chain walk in `object::root_owner` permanently bricks lazy code-object self-initialization via a self-transfer cycle - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Finding Description
`object.move` implements the ownership-chain walk in three places:

- `owns` bounds the walk with `MAXIMUM_OBJECT_NESTING` and a `count` counter. [1](#0-0) 

- `verify_ungated_and_descendant` (used by every `transfer`/`transfer_raw` call) is likewise bounded. [2](#0-1) 

- `root_owner`, however, has **no** bound at all: [3](#0-2) 

`transfer_raw_inner` never checks that `to != object`, so an owner can transfer an object to itself: [4](#0-3) 

The framework's own test confirms a self-loop can be created on the **first** call — it is only the *second* transfer that trips the nesting guard in `verify_ungated_and_descendant`: [5](#0-4) 

Once `ObjectCore.owner == self`, calling `root_owner()` on that object loops forever (`is_object(obj_owner)` stays true, `obj_owner` never changes), consuming the entire gas budget and aborting every transaction that reaches it.

The only production caller of `root_owner()` is the lazy module self-initialization gate, feature-gated by `LAZY_MODULE_INITIALIZATION`:

- `code::publish_package` records the object's `root_owner()` at publish time for object-hosted modules: [6](#0-5) 

- `init::assert_may_self_initialize` re-derives `root_owner()` on every self-init attempt to check the owner hasn't changed: [7](#0-6) 

If the hosting object has been self-transferred (cycle length 1), `assert_may_self_initialize` — and therefore `internal_maybe_initialize` — can never return; the transaction always runs out of gas. [8](#0-7) 

### Impact Explanation
`internal_maybe_initialize` is documented as the mechanism by which a code-object-hosted module mints its own signer to move resources (mint/transfer/burn refs, resource-account capabilities, or any other custody-critical state) into storage on first use, replacing a genesis-time `init_module`. If the hosting object is self-transferred (a single, ordinary, unprivileged transaction available to the object's own owner or anyone who otherwise controls the object), the module can never complete self-initialization again. Any value or authority (e.g., a `MintRef`/`TransferRef` for a fungible asset, or a capability the module was designed to store under the object's signer) that only becomes reachable after successful self-init is **permanently and non-recoverably locked**, since every future attempt aborts with an out-of-gas failure rather than a clean, catchable error. This matches the "Permanent lock or non-recoverable loss of object-held ... value" custody-impact category.

### Likelihood Explanation
Triggering the self-transfer requires no special privilege beyond normal object-owner authority (`object::transfer`/`transfer_call`), and the underlying gap (`root_owner` lacking the nesting bound that every sibling ownership-walk function has) is unconditional framework code, not test-only. However, the concrete custody impact is currently gated behind `features::is_lazy_module_initialization_enabled()` (`LAZY_MODULE_INITIALIZATION`, described in the codebase as a "transient" feature flag), so the blast radius depends on that feature's rollout status on mainnet at time of exploitation. The `root_owner()` termination bug itself is unconditional and exploitable today regardless of that feature flag; its currently-known custody-relevant consequence is limited to the lazy-init path.

### Recommendation
1. Bound `root_owner()`'s traversal with the same `MAXIMUM_OBJECT_NESTING` counter used by `owns` and `verify_ungated_and_descendant`, aborting with `EMAXIMUM_NESTING` (or a dedicated error) instead of looping unboundedly.
2. Additionally (defense in depth), reject self-transfers in `transfer_raw_inner`/`transfer_raw` (`assert!(object != to, ...)`) so an object can never become its own owner, closing the root cause of the cycle rather than only the traversal symptom.
3. Audit other current or future callers of `root_owner()` for the same unbounded-loop assumption before adding new dependents.

### Proof of Concept
```move
// 1. Create an object owned by `creator` and publish a module to it with
//    LAZY_MODULE_INITIALIZATION enabled, so code::publish_package records
//    root_owner() as the deploy owner (see code.move:179-187).
let ctor = object::create_object(signer::address_of(creator));
let obj: Object<ObjectCore> = object::object_from_constructor_ref(&ctor);
// module M is published at obj's address, calling init::internal_maybe_initialize()
// on first use to move a MintRef/TransferRef under its own signer.

// 2. Owner self-transfers the object -- this SUCCEEDS (see the framework's own
//    test_cyclic_ownership_transfer_should_fail, first transfer call, object.move:1083-1088).
object::transfer(creator, obj, obj.object_address());
// ObjectCore.owner is now == obj.object_address() itself.

// 3. Any later call to M's entry function that invokes
//    init::internal_maybe_initialize(..) now calls assert_may_self_initialize,
//    which calls root_owner() on `obj` -- this loops forever (is_object(obj_owner)
//    is always true, obj_owner never changes) and the transaction runs out of gas
//    every time it is attempted. The module's mint/transfer capability can never
//    be initialized, permanently locking any value gated behind it.
```

The self-loop construction and its acceptance on the first `transfer` call is directly reproducible from the existing framework unit test `test_cyclic_ownership_transfer_should_fail`; the unbounded loop in `root_owner()` follows directly from its code, since it lacks the `MAXIMUM_OBJECT_NESTING`/`count` guard present in `owns` and `verify_ungated_and_descendant` in the same file.

    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),

            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };

    public fun owns<T: key>(object: Object<T>, owner: address): bool {
        let current_address = object.object_address();

            error::not_found(EOBJECT_DOES_NOT_EXIST),

            return true
        };

        let current_address = object.owner;

        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            if (!exists<ObjectCore>(current_address)) {
                return false
            };

            let object = borrow_global<ObjectCore>(current_address);
            current_address = object.owner;
        };
        true
    }

    /// Returns the root owner of an object. As objects support nested ownership, it can be useful

        let obj_owner = self.owner();
