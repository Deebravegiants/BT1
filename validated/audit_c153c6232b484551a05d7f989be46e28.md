Confirmed: the `shop` header used to populate `WebhookMetadata.shop` is not part of the HMAC-signed material for `ShopifyAPI::Webhooks::Request`.

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then trusts `request.shop` as the tenant identity for dispatch [1](#0-0) , and [2](#0-1) .

### Finding Description
Shopify signs webhook HTTP bodies using the app's `client_secret` (`Context.api_secret_key`), which is the same shared secret for every merchant/shop that has the app installed [3](#0-2) . The library's `HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, and for webhook `Request` objects that signable string is exactly the raw body — nothing else [4](#0-3) .

`Registry.process` raises unless `Utils::HmacValidator.validate(request)` succeeds, and then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, `request.parsed_body`, `request.webhook_id`, and `request.api_version`, all of which are read straight from attacker-controllable headers with no cryptographic binding to the HMAC [2](#0-1) .

Because the secret is shared across tenants (any shop that has the app installed can trigger genuine Shopify-signed webhook deliveries with a valid HMAC for a given body), an unprivileged internet user who controls their own shop installation of the app can:
1. Receive a legitimate webhook from Shopify for their own shop (body `B`, valid HMAC `H` computed with the shared `client_secret`).
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Webhook-Id`/`X-Shopify-Topic`) header with a victim shop's domain.
3. Because `to_signable_string` never includes `shop`, the HMAC still validates (it's still `HMAC(secret, B) == H`), and `Registry.process` dispatches the payload to the app's handler tagged as coming from the victim shop.

This breaks the identity binding: `shop authenticated` (none, since `shop` isn't covered by HMAC) ≠ `shop used for dispatch/session key` (`request.shop`, fully attacker-controlled). This is the same bug class as the audit report's core issue — a value that is *acted upon* by the protocol/library but *not covered* by the cryptographic proof that is supposed to authenticate the whole message.

### Impact Explanation
Depending on how the host application's `WebhookHandler#handle` uses `data.shop` (e.g., to look up which shop's local records to update, enqueue background jobs keyed by shop, or process `shop/redact`, `customers/redact`, `app/uninstalled` events), an attacker can inject cross-tenant events: causing data to be applied to, deleted for, or fabricated against a shop they don't own. This matches the "cross-tenant access" High/Critical impact category, since the shop-scoping check answers permissively — it trusts an unauthenticated header field entirely.

### Likelihood Explanation
Requires only that the attacker operate their own installation of the app (a normal, unprivileged merchant), which is a very low bar — no access token, no `client_secret`, and no privileged account is needed. The attacker only needs the ability to receive one legitimate webhook and replay it with a modified header, which any HTTP client can do.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that is authenticated, or otherwise independently verify that the shop domain header corresponds to a shop actually associated with the webhook subscription/registration before dispatching to handlers. At minimum, `Registry.process` should not trust `request.shop` for any tenant-scoping decision unless it can be cryptographically tied to the signed body (e.g., by validating it against `parsed_body`'s own shop-identifying fields, or by using Shopify's newer per-topic verification headers if available).

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers a real event (e.g., updates a product) and captures the resulting webhook POST — raw body `B`, headers including `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: products/update`.
2. Attacker resends the identical body `B` and `X-Shopify-Hmac-Sha256: H` to the same webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` is constructed by the host app and passed to `ShopifyAPI::Webhooks::Registry.process`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes `HMAC(secret, B)`, which still equals `H` [5](#0-4) .
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload/HMAC actually originated from `attacker-shop.myshopify.com` [2](#0-1) .
