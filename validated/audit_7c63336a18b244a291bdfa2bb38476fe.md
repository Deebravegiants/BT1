Confirmed: `CallDispatcher.dispatch()` has zero access control - callable by any address, executing arbitrary `to.call{value}(data)` from the CallDispatcher's own context with no `onlyGateway`/`onlyHFT` restriction and no reentrancy guard. [1](#0-0) 

### Title
Permissionless `CallDispatcher.dispatch()` allows anyone to hijack tokens/ETH held by the shared dispatcher mid-flow, draining escrowed order inputs and bridged funds - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, un-owned utility contract reused by `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentsBase` to execute arbitrary calldata (predispatch swaps, postdispatch routing, calldata-on-mint) on users' behalf. Its `dispatch(bytes encoded)` function is `external` with **no caller restriction whatsoever** and **no reentrancy guard**. This is directly analogous to the referenced `PrivatePool.execute()` bug: an arbitrary-execution primitive that is reachable by anyone, sitting in front of tokens that are not fully protected by an access-control boundary.

### Finding Description
`CallDispatcher.dispatch()`:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    ...
}
``` [2](#0-1) 

has no `onlyOwner`/`onlyGateway`/`onlyHFT` modifier and no `ReentrancyGuard`. Any EOA or contract can call it directly with an arbitrary `Call[]` (target, value, data), and the call executes in the `CallDispatcher`'s own context (`msg.sender == CallDispatcher`), able to move **whatever balance the CallDispatcher currently holds**.

The `CallDispatcher` is deliberately designed to hold user/protocol funds transiently across multiple production call sites:
- `IntentGatewayV2.placeOrder` transfers `predispatch.assets` (user's input tokens/ETH) directly to `dispatcher` before invoking `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, then later reads `dispatcher`'s balance to sweep it back. [3](#0-2) 
- `IntentsBase._execute` dispatches `order.output.call` (attacker-influenceable calldata attached to the order) against the dispatcher, then sweeps back only the token set enumerated in `order.output.assets`, based on the dispatcher's balance *at that moment*. [4](#0-3) 
- `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept` mint/unlock tokens then immediately call `ICallDispatcher(_dispatcher).dispatch(message.data)` with attacker-controlled calldata delivered cross-chain. [5](#0-4) 

Because the sweep-back logic in every one of these call sites only recovers balances for tokens it explicitly enumerates (the order's declared input/output token list), any token balance that ends up on the `CallDispatcher` outside that enumerated set — e.g. because the user-supplied/solver-supplied calldata in `predispatch.call`/`postdispatch.call`/HFT `data` performs a swap into an unlisted token, or a call partially fails to consume an approval, or a fee-on-transfer/rebasing token leaves a remainder — is **not swept back to the protecting contract**. Since `dispatch()` has no access control, that residual balance sitting on the `CallDispatcher` is immediately stealable by any third party who simply calls `CallDispatcher.dispatch()` themselves with a `Call({to: token, value: 0, data: transfer(attacker, balance)})` payload, since the `CallDispatcher` itself owns those tokens outright (no approval needed — direct `transfer` suffices).

This mirrors the H-02 root cause precisely: an unrestricted arbitrary-execution entry point sitting next to funds that were only ever intended to be moved by a specific, trusted caller (the owning pool in the original report; the gateway/HFT contract here) — the "recommended mitigation" in that report was exactly to add a target/caller restriction, which `CallDispatcher.dispatch()` lacks entirely.

### Impact Explanation
Any residual token/ETH balance left on the `CallDispatcher` between the moment funds are delivered to it and the moment the invoking app sweeps its enumerated tokens back is permanently and immediately stealable by an arbitrary unprivileged account — a relayer, a solver, or any bot watching pending transactions/mempool for predispatch/postdispatch/HFT calldata that could leave dust in an unlisted token. Because `CallDispatcher` is a single shared, unauthenticated proxy for every Hyperbridge app that uses calldata execution (`IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`), the blast radius spans all of these products rather than a single pool instance as in the original report. This is concrete theft of user/protocol funds.

### Likelihood Explanation
Exploitation requires only that: (1) a user or solver sets `predispatch.call`/`output.call`/HFT `data` such that the swap/route touches a token outside the enumerated escrow/output asset list (a normal, permitted use case per the docs — "swap-then-escrow", "fill-then-act" flows explicitly support routing through arbitrary DeFi protocols), and (2) an attacker monitors the chain for such a transaction and calls `dispatch()` in the same block after it lands. No privileged role or governance action is needed on the attacker's side — `dispatch()` is public by design.

### Recommendation
Restrict `CallDispatcher.dispatch()` to be callable only by the specific set of authorized app contracts (e.g., an `onlyAuthorizedCaller` allowlist of `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken` instances), or make each app deploy/own its own dedicated `CallDispatcher` instance with an `onlyOwner` check, mirroring the fix accepted in the referenced report (restricting the arbitrary-execution surface so it cannot be reached by unrelated third parties). Additionally, ensure every call site fully sweeps *all* token balances (not just the enumerated input/output set) off the dispatcher before returning control, or wrap the dispatch+sweep sequence in a reentrancy guard so no window exists where unswept balances are observable/stealable by a third party.

### Proof of Concept
1. A user calls `IntentGatewayV2.placeOrder` with `order.predispatch.call` encoding a swap that converts the escrowed native ETH into an ERC20 token `X` that is **not** included in `order.inputs` (e.g., the swap target/path is misconfigured, or the DEX returns a different token via a multi-hop route that leaves an intermediate token balance on `CallDispatcher`).
2. `IntentGatewayV2` calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`; the swap executes and leaves a balance of token `X` sitting on `dispatcher`. [6](#0-5) 
3. `IntentGatewayV2` sweeps back only the tokens present in `order.inputs`; token `X`'s balance is never read/pulled. [7](#0-6) 
4. An attacker, observing the transaction, immediately calls `CallDispatcher.dispatch(abi.encode([Call({to: X, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, X.balanceOf(dispatcher))})]))` directly — no permission check exists on `dispatch`, so this succeeds and transfers token `X`'s balance to the attacker. [2](#0-1)

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
