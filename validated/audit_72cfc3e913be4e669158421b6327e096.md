### Title
Missing validation of governance-supplied `Params`/`ParamsUpdate` in `IntentGatewayV2.onAccept` (Tron variant) allows unbounded fee basis points and unvalidated host/dispatcher addresses to brick escrow settlement - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.onAccept` applies an incoming `UpdateParams` request directly to storage (`_params = update.params;`) with **no validation** of the decoded struct, unlike the canonical EVM implementation which routes all parameter updates through `IntentsBase._validateParams`/`_updateParams`, enforcing bounds and code-existence checks before committing.

### Finding Description
In the mainline EVM app, `_validateParams` in `evm/src/apps/intentsv2/IntentsBase.sol` explicitly checks that `host`/`dispatcher` are non-zero contracts, `surplusShareBps <= 10_000`, `protocolFeeBps < 10_000`, and that `priceOracle` (if set) has code, before any `ParamsUpdate` is applied: [1](#0-0) 

The Tron port of `IntentGatewayV2` implements the equivalent `RequestKind.UpdateParams` branch of `onAccept` but skips this validation step entirely — it decodes the untrusted payload and writes it straight into the `_params` storage slot: [2](#0-1) 

This is structurally the same class of bug as the reported `_parseIntoOracle` issue: an externally-supplied parameter struct (`ParamsUpdate`/`Params`) is consumed and persisted without confirming the referenced addresses are valid contracts or that numeric fields fall within safe bounds. The same contract's `setParams` function (admin-gated) similarly assigns `_params = p` with no checks, confirming the omission is consistent across both entry points, not merely a one-off admin trust assumption: [3](#0-2) 

Because `host`, `dispatcher`, `protocolFeeBps`, and `surplusShareBps` all directly gate escrow accounting and cross-chain dispatch (`instance()`, `IDispatcher(hostAddr).dispatch`, fee-bps math in order settlement), an unvalidated update can:
- Set `protocolFeeBps >= 10_000`, causing fee arithmetic (`amount - amount*feeBps/10_000`) to underflow/revert, DoS-ing all subsequent `placeOrder`/`fillOrder`/`withdraw` calls that use it.
- Set `surplusShareBps` out of the intended `[0, 10_000]` range, corrupting surplus distribution logic.
- Point `host` or `dispatcher` at a non-contract or unintended address, breaking `IDispatcher` calls used to relay refund/redeem/fill dispatch messages, which can strand escrowed funds that can only be released via those dispatch paths.

### Impact Explanation
Any of the above conditions permanently or persistently breaks the settlement path for escrowed order funds (revert-on-fee-calculation or broken dispatcher target), which fits the "permanent freezing of funds" / "route unable to deliver messages" acceptance criteria — assets already escrowed under `_orders`/`_filled` become unrecoverable through the normal `withdraw`/dispatch flow until a further corrective governance message (itself subject to the same unvalidated path) is delivered.

### Likelihood Explanation
The `UpdateParams` request still requires the request to originate from the configured Hyperbridge source (`keccak256(incoming.request.source) == keccak256(hyperbridge)`) and pass through `onlyHost`, so this is not directly reachable by an arbitrary unprivileged EOA — it requires a message actually dispatched from the Hyperbridge governance channel. However, unlike the mainline EVM contract, there is no defense-in-depth: a single malformed/mistaken governance payload (e.g., an off-by-one on the fee scale, a typo'd address) that would be caught and reverted by `_validateParams` on the canonical implementation instead succeeds silently on the Tron variant, and there is no comparable second-line validation in `IntentGatewayV2.sol` (Tron) to prevent it. The presence of an already-implemented, actively-tested validation routine on the sibling EVM contract (see `evm/tests/foundry/IntentGatewayV2Test.sol` `testRevert_SetParams_*` cases) indicates this bounds/code-check logic is expected security-critical behavior that was not ported to the Tron contract.

### Recommendation
Port `IntentsBase._validateParams` (host/dispatcher code checks, `surplusShareBps <= 10_000`, `protocolFeeBps < 10_000`, `priceOracle` code check if non-zero) into the Tron `IntentGatewayV2.sol`, and invoke it from both `setParams` and the `onAccept` `RequestKind.UpdateParams`/destination-fee-update branches before committing `_params` or `_destinationProtocolFees`.

### Proof of Concept
1. Hyperbridge dispatches (or is spoofed/misconfigured to dispatch, per the trust model of `onAccept`) a `PostRequest` to the Tron `IntentGatewayV2` with `body[0] == RequestKind.UpdateParams` and an ABI-encoded `ParamsUpdate` where `params.protocolFeeBps = 10_000` (100%).
2. `onAccept` decodes and assigns `_params = update.params` with no bounds check [4](#0-3) .
3. Any subsequent order flow that computes `amount - amount * protocolFeeBps / 10_000` (fee deduction) either always transfers 0 to the intended beneficiary or reverts depending on implementation, effectively freezing escrowed funds tied to `placeOrder`/`fillOrder`/`withdraw` for that gateway instance.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }
