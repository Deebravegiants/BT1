Confirmed: `handle_unsigned` in `pallet-ismp` is an unsigned, permissionless call — "This is an unsigned extrinsic that permits anyone execute ISMP messages for free, provided they have valid proofs" [1](#0-0) , and `Message::Consensus` messages route through `ConsensusClient::verify_consensus`, which for the parachain client calls `read_proof_check_for_parachain` [2](#0-1) .

### Title
Truncated relay-chain storage proof silently drops parachain header updates instead of rejecting the consensus message - (File: modules/ismp/state-machines/substrate/src/lib.rs)

### Summary
`read_proof_check_for_parachain` treats a `TrieError::IncompleteDatabase` for an individual key as a reason to `continue` (skip the key) rather than fail the whole proof, silently omitting that key from the result map.

### Finding Description
`read_proof_check_for_parachain` iterates the requested parachain-header keys against the supplied trie proof. For each key it either inserts `Some(decoded)`, inserts `None` on a genuine trie miss, or — when the trie is missing the nodes needed to resolve that specific key (`TrieError::IncompleteDatabase`) — simply `continue`s, leaving that key entirely absent from the returned `BTreeMap`: [3](#0-2) 

This is called from `ParachainConsensusClient::verify_consensus` with `header_keys` built from every registered parachain (`Parachains::<T>::iter_keys()`), so the proof is expected to cover every parachain's header key: [2](#0-1) . The caller then iterates only the entries that actually exist in the returned map and processes each one to build a `StateCommitmentHeight`: [4](#0-3) .

Because a partially incomplete trie (an attacker-submitted `storage_proof` that omits the sibling nodes needed to prove one specific parachain's key) causes that key to vanish from the map rather than causing `verify_consensus` to return an error, the whole consensus message is accepted as valid even though it fails to actually resolve one or more of the parachain headers it should have proven. This is the same bug class as the malcontent advisory: a failure to fully process a nested/aggregate structure (nested archive / batch of trie keys) is silently swallowed and the partial result is treated as authoritative, instead of surfacing the failure and rejecting the input.

### Impact Explanation
`handle_unsigned` is a permissionless, unsigned extrinsic reachable by any relayer with a `Message::Consensus` payload [5](#0-4) . By crafting a `ParachainConsensusProof` whose `storage_proof` intentionally omits the trie nodes needed to resolve a specific parachain's header key while still fully proving all the other parachain keys, a relayer can cause `verify_consensus` to succeed while silently omitting the state-commitment update for the targeted state machine (`intermediates` never gets an entry for that `StateMachineId`) [4](#0-3) . Since the consensus message overall reports success (no error, `StateMachineUpdated` events fire for the other parachains), it is accepted into the transaction pool and applied on-chain, leaving that particular route's state commitment stale. Requests destined for or originating from that parachain can no longer be delivered/verified against a current state root until a later, honestly-formed proof happens to update it — effectively a selective, relayer-triggerable freeze of message delivery for a targeted route ("route unable to deliver messages").

### Likelihood Explanation
Medium. Exploitation requires no privileged access — any party able to submit an unsigned ISMP message with a validly-verifiable-but-partially-incomplete relay-chain storage proof can trigger it (the transaction-pool's `validate_unsigned` executes `Self::execute` and would only reject the message if it errors, which it does not in this case) [6](#0-5) . Constructing a genuinely valid trie proof for N-1 parachains while making it deliberately incomplete for exactly the target parachain requires some care (removing the right set of intermediate nodes while keeping the memory-db still `contains(root, EMPTY_PREFIX)` valid) but is a mechanical, offline computation, not requiring any special privilege or timing.

### Recommendation
Change `read_proof_check_for_parachain` so any `TrieError::IncompleteDatabase` for a requested key propagates as an error (fail the whole `verify_consensus` call) rather than silently `continue`-ing past it, matching the more conservative sibling function `read_proof_check` which already returns `Err` on trie-read failures. Alternatively, after building `result`, explicitly assert `result.len() == keys.len()` (as `EvmStateMachine`/`SubstrateEvmStateMachine` already do via `MismatchedValuesAndKeys`) before returning, so a key silently dropped due to incomplete proof data is rejected.

### Proof of Concept
1. An attacker builds a valid `ParachainConsensusProof` for a relay height where all registered parachains (`Parachains::<T>::iter_keys()`) have their header stored under `parachain_header_storage_key(id)`.
2. Generate the full storage proof covering all parachain header keys, then remove the minimal set of trie nodes that are exclusively needed to resolve the header key of the target parachain `P`, while keeping all nodes needed for every other parachain's key intact (the underlying trie library documents `IncompleteDatabase` as the failure returned by `trie.get` when required nodes are missing).
3. Submit `Ismp::handle_unsigned([Message::Consensus{ consensus_proof: ParachainConsensusProof{ relay_height, storage_proof }, ... }])` as an unsigned extrinsic [5](#0-4) .
4. `read_proof_check_for_parachain` hits `Err(TrieError::IncompleteDatabase)` for `P`'s key and `continue`s, omitting `P` from `headers` [3](#0-2) ; all other parachains resolve normally and get inserted into `intermediates`.
5. `verify_consensus` returns `Ok((state, intermediates))` with no entry for `P`'s `StateMachineId`, the extrinsic succeeds, and `StateMachineUpdated` fires only for the unaffected parachains — `P`'s state commitment silently fails to advance for this update round, with no error surfaced anywhere in the pipeline.
