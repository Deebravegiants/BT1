## Title
Permanent freezing of an entire multi-asset order's escrow when a single token transfer to the beneficiary reverts (blacklist/pause) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` iterates over every escrowed token in an order and performs a hard-reverting transfer (`safeTransfer` / low-level `call` that reverts on failure) for each one in a single atomic loop. Because ISMP delivery of the `RedeemEscrow`/`RefundEscrow` message that triggers `_withdraw` is a one-shot, all-or-nothing callback, a single non-transferable token/beneficiary pair anywhere in the loop (e.g. a USDC-style blacklist hitting the order's beneficiary, or a paused/broken token) permanently blocks release of *all* other, otherwise-transferable assets escrowed for that same order — exactly the "one bad token/beneficiary DoS's the whole withdrawal batch" bug class from the referenced FactoryDAO report.

### Finding Description
`_withdraw` loops over `body.tokens` and reverts the whole call if any single transfer fails: [1](#0-0) 

This function is reached from `onAccept` for both `RedeemEscrow` (pay the solver) and `RefundEscrow` (refund the original user) message kinds: [2](#0-1) 

The Tron variant of `IntentGatewayV2` has the identical structural flaw — one failed `.call` in the loop reverts the whole `withdraw`: [3](#0-2) 

Delivery of this message is a single-shot, permission-gated ISMP callback: `EvmHost.dispatchIncoming` writes a request receipt, calls `IApp.onAccept`, and if that low-level call reverts, it deletes the receipt so the message can be retried — but retried with the *same* body and the *same* permanently-blacklisted beneficiary/token pair, so it will revert identically forever: [4](#0-3) 

Because a `RefundEscrow`/`RedeemEscrow` message carries the *entire remaining* `order.inputs` (potentially several distinct ERC-20s) for one commitment in a single batch, a permanent transfer failure on just one of those tokens (or on the fee-token transfer at the end of `_withdraw`) makes it impossible to ever release *any* of the other tokens still escrowed under that commitment, since the whole function must succeed atomically for the commitment's escrow accounting (`_orders[commitment][token] -= amount`) to be persisted.

Unlike the original FactoryDAO bug, this isn't a shared pool blocking every user — the blast radius here is scoped to a single order commitment. However, the assets frozen are the order creator's/solver's entire escrowed basket, not merely the token affected by the blacklist, and there is no owner/governance escape hatch or per-token partial-withdraw fallback, and no timeout mechanism recovers the funds either (the message never times out because it keeps being retried without a persisted receipt, or if it does time out the affected leg of tokens can't be recovered piecemeal).

### Impact Explanation
Any user calling `placeOrder` with multiple input tokens (or receiving multiple output tokens as a solver via `fillOrder` on the destination chain) is exposed. If the order's `beneficiary` (the user on refund, or the solver on redeem) becomes unable to receive just one of the escrowed tokens — via an ERC-20 blacklist, a token pause, or any other malicious/broken token behavior — every other token escrowed for that commitment, plus any accrued transaction fees in the fee token, become permanently unrecoverable. This is a genuine freezing-of-funds bug reachable by an ordinary, unprivileged intent placer or solver, not an admin or governance actor.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) a token in the order's input/output set implementing a blacklist (common for USDC/USDT-style stablecoins, which are exactly the kind of tokens intents protocols are built to move) and the beneficiary address ending up on that blacklist, or (b) a token becoming paused/broken mid-flight, or (c) a malicious solver/user deliberately choosing a beneficiary they know is (or will become) blacklisted on one of several escrowed tokens to grief their own or a counterparty's multi-asset order. Because `placeOrder`/`fillOrder` allow arbitrary attacker-chosen token lists and beneficiaries, a malicious actor can trigger this condition cheaply and deterministically for any order they construct.

### Recommendation
Do not let one token's transfer failure block release of the others in the same withdrawal batch:
- Wrap each per-token transfer in `_withdraw` (and in the fee-token transfer) in a try/catch (or low-level `call` without bubbling a top-level revert), and route amounts belonging to un-transferable tokens into a separate per-beneficiary "stuck balance" ledger that can be claimed once the token/beneficiary becomes transferable again, or claimed by governance under a defined recovery process, rather than blocking the whole loop from persisting `_orders` decrements for the succeeding tokens.
- Alternatively, allow `_withdraw` to persist partial success (decrement escrow and transfer per-token independently, catching failures) so a single problematic token doesn't gate the redemption/refund of the rest of the order's escrow.

### Proof of Concept
1. User places a multi-input order via `placeOrder` with `order.inputs = [USDC, DAI]`, escrowing both tokens in `IntentsBase`/`IntentGatewayV2`.
2. Order is filled/cancelled on the destination chain, generating a `RedeemEscrow`/`RefundEscrow` `PostRequest` whose body encodes a `WithdrawalRequest` covering both `USDC` and `DAI` amounts for the beneficiary.
3. Before the message is delivered, the beneficiary address is added to USDC's blacklist (or USDC is paused).
4. Relayer delivers the message; `EvmHost.dispatchIncoming` invokes `onAccept` → `_withdraw`, which reaches `IERC20(USDC).safeTransfer(beneficiary, amount)` in the loop shown in `IntentsBase.sol:451-470` and reverts.
5. `EvmHost.dispatchIncoming` catches the revert and deletes the request receipt so the message is marked undelivered and can be retried — but every retry hits the exact same USDC transfer and reverts identically.
6. The `DAI` amount escrowed under the same commitment, which could otherwise be released without issue, is now permanently unreachable because it can only be released atomically together with the failing USDC leg.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
