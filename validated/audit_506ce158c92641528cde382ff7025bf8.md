### Title
Authenticated Nil-Pointer Dereference DoS via Missing `params` in Vault `publicKeyGet` Gateway Message - (File: `core/capabilities/vault/gw_handler.go`)

### Summary
The node-side Vault gateway handler dereferences `req.Params` without a nil check when processing `vaulttypes.MethodPublicKeyGet` requests forwarded from the gateway, unlike every other Vault method which is first routed through `GatewayVaultRequestProcessor`, which explicitly rejects nil `Params`. An authenticated caller who can reach the gateway's Vault user-facing endpoint can send a `publicKeyGet` request with a missing/null `params` field, causing the node to panic on `*req.Params` when handling the forwarded gateway message. This mirrors the LXD CVE-2026-9639 pattern: an authenticated, low-privileged actor supplies a request that omits a field the handler assumes is always present, triggering a nil-pointer dereference and a denial-of-service crash.

### Finding Description
For the write/list/delete Vault methods, `GatewayHandler.HandleGatewayMessage` first calls `h.requestProcessor.ProcessRequest`, and each of the processor's per-method functions (`processCreateSecretsRequest`, `processUpdateSecretsRequest`, `processDeleteSecretsRequest`, `processListSecretIdentifiersRequest`) explicitly guard against nil params: [1](#0-0) [2](#0-1) 

Only after this validated pipeline succeeds does `HandleGatewayMessage` invoke the corresponding `handleSecretsCreate` / `handleSecretsUpdate` / `handleSecretsDelete` / `handleSecretsList`, so their own unguarded `json.Unmarshal(*req.Params, ...)` calls are safe by construction: [3](#0-2) 

However, `vaulttypes.MethodPublicKeyGet` bypasses the request processor entirely and is dispatched directly to `handlePublicKeyGet`: [4](#0-3) 

`handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go:364-386` dereferences `req.Params` unconditionally: [5](#0-4) 

If `req.Params` is `nil` (i.e., the JSON-RPC request omits the `params` field, or sets it to `null`), the line `json.Unmarshal(*req.Params, r)` dereferences a nil `*json.RawMessage`, causing a runtime panic.

On the gateway side, the corresponding user-facing handler `handler.HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go:394-424`) special-cases `MethodPublicKeyGet` and forwards the request to the node via `fanOutToVaultNodes`/`SendToNode` without ever validating that `Params` is non-nil for this method — that validation only happens for the other secrets methods via `h.requestProcessor.ProcessRequest`. This means a caller of the gateway's Vault HTTP/JSON-RPC API can submit a `publicKeyGet` request with `"params": null` (or the field omitted, since `*json.RawMessage` is nilable), and it will be relayed unchecked to every node in the DON, where `GatewayHandler.HandleGatewayMessage` will panic in `handlePublicKeyGet`.

I could not fully confirm whether the goroutine that ultimately executes `HandleGatewayMessage` (via the gateway connector's message dispatch loop) is wrapped in a `recover()` at a higher layer — my search for `recover()` in the connector/dispatch path (`core/services/gateway/connector/connector.go`) did not show a panic-recovery wrapper, unlike `core/capabilities/remote/dispatcher.go`, which does have one. This is a point of uncertainty: if the connector's per-message handling goroutine is unprotected, the panic will crash the node process (full DoS); if it is protected by a top-level recover, the impact is limited to a dropped/failed request rather than a full crash, though it would still be an unhandled internal error for every DON member simultaneously.

### Impact Explanation
A successful trigger crashes (or at minimum, causes an unhandled panic/error in) every node in the Vault DON that receives the forwarded `publicKeyGet` message, since the gateway fans the request out to all DON members (`fanOutToVaultNodes` iterates `h.donConfig.Members`). This is a genuine authenticated availability impact matching the CVSS profile of the referenced CVE (`AV:N/AC:L/PR:L/S:U/A:H`), since it requires only the ability to submit Vault gateway requests (a role most other Vault write methods already gate through allowlist/JWT authorization, but `publicKeyGet` is explicitly designed to skip authorization).

### Likelihood Explanation
`publicKeyGet` is intentionally unauthenticated/unauthorized by design (per the code comment "Public key requests don't require authorization"), so the barrier to reaching this code path is low — any client capable of sending JSON-RPC to the gateway's Vault service can attempt it. The only precondition is supplying a request with `params` omitted or null, which is trivial to construct.

### Recommendation
Add the same nil-params guard used elsewhere before dereferencing `req.Params` in `handlePublicKeyGet` (both node-side in `core/capabilities/vault/gw_handler.go` and gateway-side in `core/services/gateway/handlers/vault/handler.go`), returning an `api.UserMessageParseError`/`api.InvalidParamsError` response instead of unmarshalling a nil pointer. Route `MethodPublicKeyGet` through a lightweight structural validation step consistent with the other methods' `req.Params == nil` checks in `GatewayVaultRequestProcessor`.

### Proof of Concept
1. Submit a JSON-RPC request to the gateway's Vault user-facing endpoint:
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault.publicKeyGet"}
```
(no `params` field, or `"params": null`).
2. The gateway-side `handler.HandleJSONRPCUserMessage` does not validate presence of `Params` for this method and forwards the request via `fanOutToVaultNodes` to all DON nodes.
3. Each node's `GatewayHandler.HandleGatewayMessage` dispatches to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, panicking with a nil-pointer dereference in every DON member simultaneously.
