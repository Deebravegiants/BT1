### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing shop-domain spoofing via header/body mismatch - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The header is never included in the signed bytes, so the "authenticated" bytes and the "tenant-identifying" bytes diverge — exactly the class of identity-binding bug called out in the prompt (bytes verified vs. bytes parsed).

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely with: [1](#0-0) 

That call delegates to `Utils::HmacValidator.validate`, which recomputes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` is only the raw body — it does not include any headers: [3](#0-2) 

Yet the `shop` accessor — which becomes the tenant key handed to the app's `WebhookHandler#handle` via `WebhookMetadata.shop` — is read straight from the unauthenticated `shop-domain` header: [4](#0-3) [5](#0-4) [6](#0-5) 

The identity binding the gem is supposed to enforce is: `shop header used by the app == shop cryptographically attested by the HMAC sender`. Because the HMAC covers only the body, that equality never actually holds — any principal who can obtain one valid `(raw_body, hmac)` pair for topic *T* (for example, a merchant who installed the app and can trigger/observe their own shop's genuine webhook for that topic) can resend the exact same body and HMAC to the app's webhook endpoint while substituting a different `shop-domain` header value. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` field names the attacker-chosen victim shop instead of the shop that actually produced the signed bytes.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (the documented, intended way to scope webhook processing to a tenant — e.g. to look up per-shop session/access-token records, write to per-shop data, or perform authorization decisions) is exposed to cross-tenant data poisoning/access: an attacker-controlled shop-domain string is trusted as if it were cryptographically bound to the request body. This matches the "cross-tenant access" impact category, since the gem itself supplies no mechanism to bind the claimed shop to the authenticated payload.

### Likelihood Explanation
Exploitation only requires possession of one legitimately-HMAC-signed `(body, hmac)` webhook pair for any topic the target app registers — something any merchant who installs the app on their own shop can obtain by observing their own genuine webhook traffic (e.g. via a proxy) — plus the ability to POST to the app's public webhook endpoint with a modified header. No access token, `client_secret`, or privileged account is required, satisfying the unprivileged-internet-user constraint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value inside the bytes that `Webhooks::Request#to_signable_string` returns, or otherwise cryptographically bind the parsed `shop` to the verified payload before constructing `WebhookMetadata`, so `HmacValidator.validate` fails whenever the claimed shop does not match the shop the signature actually covers.

### Proof of Concept
1. As a merchant, install the target app on `attacker.myshopify.com` and trigger a webhook topic the app registers (e.g. `orders/create`). Capture the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`).
2. Replay the exact same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes the HMAC over `B` (`lib/shopify_api/webhooks/request.rb:35-38`); it never inspects the `shop-domain` header.
4. The registered `WebhookHandler#handle` receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, so the app processes attacker-supplied data under the victim's tenant identity, even though the signed bytes never came from `victim.myshopify.com`.
