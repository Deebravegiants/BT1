### Title
Webhook tenant identity (`shop`) is derived from an HTTP header not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` (via `to_signable_string`) only covers the raw request body. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts `request.shop` as the tenant identifier passed to the app's handler, without the shop domain ever being bound to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop` is pulled from the `shop-domain` header, entirely outside that signed string: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately uses `request.shop` (the unauthenticated header) as the tenant identity forwarded to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body for webhooks) and the app's single `api_secret_key`: [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified bytes == bytes acted on`. In this case, `bytes verified` (raw body) ≠ `bytes parsed for tenant identity` (the `shop-domain` header). Because a single app uses one shared `client_secret`/`api_secret_key` across every shop that installs it, any merchant who installs the app on their own store receives genuine, correctly-signed webhook deliveries for their own shop. That merchant fully controls the HTTP request they forward to the app's webhook endpoint (headers included) and can therefore replay a legitimately-signed body while substituting an arbitrary value — e.g. a victim shop's domain — into the `X-Shopify-Shop-Domain` header. The gem will validate the HMAC successfully (it only checks the body) and hand the handler a `WebhookMetadata` object claiming the webhook belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion vulnerability. Any app built on this gem that uses `data.shop` (from the webhook handler) to key persistence, deduplication, authorization, or any per-tenant business logic can be made to attribute attacker-supplied (but validly-signed) webhook payloads to an arbitrary shop domain string of the attacker's choosing. This satisfies the "Critical — cross-tenant access" impact bar: an unprivileged internet user (any developer/merchant who can install the app on a store they control) can inject data or trigger tenant-scoped side effects under an identity they do not own, without possessing the victim's access token or any Shopify-issued secret beyond the app's shared client secret exposure surface (which they never need — they only replay a webhook they legitimately received).

### Likelihood Explanation
High. The attacker only needs to install the target app on a shop they control (often free via a Partner dev store), capture one legitimate webhook delivery (body + valid HMAC), and replay it to the app's public webhook endpoint with a modified shop-domain header. No secrets, tokens, or elevated access are required — this is achievable entirely from the public internet against any app using this library's webhook processing as documented.

### Recommendation
Bind the shop domain (and any other identity-bearing header actually used by the handler, e.g. `webhook_id`) into the HMAC-signed material, or require the host application to cross-check `request.shop` against a known/installed-shop allowlist before trusting it. At minimum, `Request#to_signable_string` should not be the sole basis for trusting `request.shop`; `Registry.process` should validate that the shop domain is one that the app has an active session/registration for before dispatching to the handler.

### Proof of Concept
1. Attacker creates a Partner/dev store `attacker-shop.myshopify.com` and installs the target Shopify app (using this gem).
2. Attacker triggers a real event (e.g., `orders/create`) on their own store, causing Shopify to send a webhook to the app's registered callback URL with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's `client_secret`.
3. Attacker captures this raw request (body + headers).
4. Attacker resends the identical body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only verifies `raw_body` against the HMAC — the forged `shop-domain` header is never checked: [3](#0-2) 
6. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-originated body, and performs tenant-scoped actions/writes under the victim's identity.
