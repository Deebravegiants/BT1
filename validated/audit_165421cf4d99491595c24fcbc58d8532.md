## Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (`File: lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) values from HTTP headers that are **not** included in the string that gets HMAC-verified. Only the raw request body is signed. Since the webhook secret (`api_secret_key`) is shared across every shop that installs the app, an attacker who legitimately installs the app on their own store can capture one of their own genuinely-signed webhook deliveries and replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. `HmacValidator.validate` will still pass because it only checks the (unmodified) body, letting the attacker inject events that the host application will process as if they came from the victim tenant.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string`, i.e. the body: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once that body-only HMAC passes, and then hands the **unverified** `request.shop` header value straight to the app's handler as the tenant identifier: [4](#0-3) 

This breaks the intended identity binding: the equality that should hold is
`shop authenticated by HMAC == shop the payload is attributed to`,
but here `shop` is completely outside the signed material, so
`shop verified by HMAC (∅, body only) ≠ shop acted on (attacker-controlled header)`.

Because the same `api_secret_key` signs webhooks for every shop that installs the app, any merchant (including an attacker who installs the app on their own free/dev store) can capture a validly-signed webhook body from their own shop and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim's `myshopify.com` domain. `Utils::HmacValidator.validate` still returns `true` (body unchanged), so `Registry.process` dispatches the forged event to the app's handler tagged with the victim's shop, crossing the tenant boundary.

## Impact Explanation
This is a cross-tenant access issue: an unprivileged user (an app installer on their own shop) can make the app process attacker-supplied webhook data under another merchant's identity (e.g. spoofed `orders/updated`, `app/uninstalled`, `customers/data_request`, or `shop/redact` events), potentially triggering data mutation, deletion, or GDPR-related side effects for a shop the attacker does not control. This matches the "cross-tenant access" Critical impact category defined for this scan.

## Likelihood Explanation
The prerequisite is only "any unprivileged Shopify merchant account" that installs the target app (webhook secrets are shared across all installs of a given app, not per-shop), plus the ability to capture and replay one legitimate webhook HTTP request with a modified header — no access to `api_secret_key`, access tokens, or privileged accounts is required. The webhook endpoint is a public HTTP endpoint by design.

## Recommendation
Include the tenant-identifying fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them (e.g. require the host app to cross-check `request.shop` against an installed/known shop list keyed by an independently-verified identifier), and document that the `shop` header must not be trusted for authorization decisions without such a cross-check.

## Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: customers/data_request
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"customer": {...}}
   ```
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, only changing:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only look at the (unchanged) body and `X-Shopify-Hmac-Sha256` header, so `Utils::HmacValidator.validate` returns `true`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the host app to process the attacker's forged payload as if it originated from the victim shop.
