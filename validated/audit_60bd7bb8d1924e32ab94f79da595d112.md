Based on my research, I was unable to fully retrieve the body of `findMatchingWithdrawal` itself (only its usage), but the call sites and test expectations clearly demonstrate its matching behavior is not unique-index-safe.

### Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong withdrawal to be reported for a given index - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` matches the on-chain withdrawal record purely by `assetId`, ignoring `args.index`, `destinationAddress`, and `amount`. This is confirmed by both the call site and by an explicit test comment stating the design intent.

### Finding Description
`describeWithdrawal` calls: [1](#0-0) 

which invokes `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` — passing only the `assetId`, not the withdrawal's `index`, `destinationAddress`, or `amount`. This is deliberate, as documented by the comment "Response list is unsorted, so we match by assetId instead of index" and tested explicitly here: [2](#0-1) 

The test suite only validates disambiguation between withdrawals of *different* `assetId`s in the same NEAR transaction. There is no test (and, per the call signature, no code path) that disambiguates two withdrawals of the *same* `assetId` batched in a single NEAR transaction (e.g., two `ft_withdraw` intents for the same token to different `destinationAddress`/`amount`, which `IntentExecuter`/`IntentPayloadBuilder` explicitly support via `addIntents`, executing atomically in one transaction — see `intent-payload-builder.ts` and `intent-executer.ts`). [3](#0-2) 

When a caller batches two same-asset withdrawals in one NEAR tx and later calls `describeWithdrawal` for each `index`, `findMatchingWithdrawal` returns whichever entry in the (unsorted) API response array matches the `assetId` first — potentially the wrong entry with respect to `index`. This can cause the wrong `transfer_tx_hash`/status to be attributed to a given `WithdrawalIdentifier`.

### Impact Explanation
This breaks the equality "status/txHash reported for withdrawal index N == actual on-chain outcome of withdrawal index N." Because `waitForWithdrawalCompletion`/`watchWithdrawal` (used by callers to decide when to credit/refund a withdrawal) rely on this status: [4](#0-3) 

an integrator could see withdrawal #0 (still pending on-chain) falsely reported as `completed` with the destination tx hash belonging to withdrawal #1 (or vice versa). This matches the listed High-impact class: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Requires no privileged access — any regular user/integrator batching two `ft_withdraw` intents for the same POA-bridged asset within a single signed transaction (a supported, unprivileged SDK feature) can trigger the ambiguous match. It's the ordinary, expected usage pattern of the SDK's batching capability, not a contrived edge case.

### Recommendation
Disambiguate `findMatchingWithdrawal` using additional fields beyond `assetId` — e.g., `destinationAddress` and `amount` (and/or `index`, if the indexer can provide stable ordering) — to uniquely identify the withdrawal record corresponding to each `WithdrawalIdentifier` before reporting `completed`/`txHash`.

### Proof of Concept
1. Build an intent batching two `ft_withdraw` primitives for the same `assetId` (e.g., `nep141:usdc.omft.near`) in a single `IntentPayloadBuilder`/`signAndSendIntent` call, with different `destinationAddress` and `amount` for each (index 0 and index 1).
2. Submit, and once the POA bridge processes both withdrawals, call `bridge.describeWithdrawal` for index 0 and index 1 against the same NEAR tx hash.
3. Because `findMatchingWithdrawal` filters only by `assetId`, both calls can resolve to the same underlying withdrawal record (or the wrong one), returning identical/incorrect `transfer_tx_hash` and `completed` status for a withdrawal that hasn't actually landed, or vice versa — as demonstrated by the assetId-only matching in [5](#0-4) .

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
