### Title
Webhook `shop-domain` Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while the `shop` (and `topic`/`api_version`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body but then trusts `request.shop` — taken from the header — to attribute the webhook to a tenant, without any cryptographic binding between the two.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from HTTP headers with no relationship to the HMAC at all: [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then immediately hands `request.shop` (the header value) to the handler as the tenant identifier: [3](#0-2) 

The identity-binding equality that should hold is:

`shop_bound_by_hmac == shop_used_for_tenant_attribution`

but the actual equality enforced by the code is only:

`HMAC(raw_body, api_secret_key) == received_hmac`

with `shop` entirely excluded from the signed material. `HmacValidator.validate_signature` confirms the signed string is exactly `verifiable_query.to_signable_string`, i.e. the raw body for webhooks: [4](#0-3) 

Because a single app installation shares one `api_secret_key` across every shop that installs it, a valid `(body, hmac)` pair generated by Shopify for one tenant (the attacker's own store, or any store the attacker can observe a webhook delivery for, e.g. via Shopify's admin "recent deliveries" webhook log which is visible to any store owner) remains cryptographically valid when replayed with the `shop-domain` header rewritten to a different, victim tenant. `Registry.process` has no mechanism to detect this because the shop value it forwards to the handler is never covered by the signature it checks.

### Impact Explanation
This breaks tenant isolation: an unprivileged actor who only needs to install the app on their own (attacker-controlled) shop — a normal, unprivileged action for any public/multi-tenant Shopify app — can capture one legitimately-signed webhook body+HMAC for their own store and replay it to the app's webhook endpoint with the `shop-domain` header changed to any other installed shop. Downstream webhook handlers that key persistence, cache invalidation, or business logic off `WebhookMetadata#shop` will process/store attacker-supplied data under a victim tenant's identity — a cross-tenant data injection/attribution vulnerability, without ever needing the app's `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant deployment of this gem's webhook registry: the attacker only needs (a) their own app installation (freely available for most public apps) and (b) visibility of one webhook delivery's raw body/HMAC (available via Shopify's own delivery logs, or simply by running an app instance they control), then a single crafted HTTP request against the target app's shared webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is verified, not merely delivered in headers, e.g.:
- Require server-side confirmation that `request.shop` corresponds to a shop with an active, previously stored session/installation before dispatching to handlers, or
- Include the shop domain in the HMAC-signed payload contract enforced by `Registry.process` (reject if it doesn't match an expected/registered shop), rather than trusting the header value implicitly once the body-only HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook-eligible event (e.g., updates a product) to receive a legitimately Shopify-signed webhook delivery, or obtains it from Shopify's delivery log for that install.
2. Attacker takes the exact `raw_body` and `x-shopify-hmac-sha256` header value from that delivery (both valid, since `HmacValidator.validate` only checks `HMAC(raw_body, secret) == received_hmac`, per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31 and `lib/shopify_api/webhooks/request.rb` lines 35-38).
3. Attacker POSTs this same body+HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain` (or `shopify-shop-domain`) to `victim-shop.myshopify.com`.
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb lines 188-200) validates the HMAC successfully (it never considered the shop header) and dispatches `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's own event body> ...)` to the app's handler, causing the app to associate attacker-controlled data with the victim tenant.
