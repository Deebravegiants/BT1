### Title
Excess native `msg.value` sent to `EvmHost.dispatch()` for fee-token swaps is not refunded and becomes permanently locked - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept `msg.value` and perform an exact-output Uniswap V2 swap (`swapETHForExactTokens`) to buy exactly `post.fee` / `get.fee` units of the fee token. Because this is an exact-output swap, the router only consumes the minimum ETH required and refunds any unused ETH — but that refund is returned to whichever address is `msg.sender` from the router's perspective, which is `EvmHost` itself, not the original transaction sender. Neither `EvmHost.dispatch()` nor its upstream callers (`HyperFungibleToken.send()`, `WrappedHyperFungibleToken.send()`) forward this leftover ETH back to the end user, so any overpayment of native currency for fee payment is permanently stranded in the host contract.

### Finding Description
`EvmHost.dispatch(DispatchPost)` swaps the full `msg.value` for an exact amount of fee token: [1](#0-0) 

The same pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 

`swapETHForExactTokens` is an exact-*output* swap: the router computes the minimal ETH input needed to receive `post.fee`/`get.fee` fee tokens and refunds any unused portion of `msg.value` to the immediate caller of the swap — i.e., `EvmHost`, not the address that originally sent value into `dispatch()`. `EvmHost.dispatch()` never re-forwards that refund to `_msgSender()` (the app contract or user who paid), so the difference between what the user sent and what the swap actually consumed stays trapped in `EvmHost`.

This is directly reachable by any unprivileged caller: apps such as `HyperFungibleToken.send()` and `WrappedHyperFungibleToken.send()` forward the caller's entire `msg.value` straight into `dispatch()` without pre-computing the exact fee amount or handling a refund: [3](#0-2) [4](#0-3) 

Because native fee prices fluctuate between `quote()` and the actual `send()` transaction, users are expected to send a small buffer over the quoted native fee to avoid reverts on slippage — but any of that buffer that the exact-output swap doesn't consume is not returned to the user or the calling app; it silently accumulates in `EvmHost`.

By contrast, `IntentGatewayV2.placeOrder()` handles the equivalent scenario correctly by tracking `msgValue` and refunding any unspent native tokens back to `msg.sender` after all native flows (including the same `swapETHForExactTokens` fee purchase) are settled: [5](#0-4) 

`EvmHost.dispatch()` and the token apps that call it directly lack this equivalent refund step, so the same bug class (unaccounted-for/excess `msg.value` being permanently absorbed instead of returned) is present.

### Impact Explanation
Any user or integrating app that overestimates the native fee (a common and expected practice to absorb slippage between `quote()` and execution) permanently loses the unused excess ETH into `EvmHost`, with no path to reclaim it. Given how frequently `send()` is used for cross-chain token transfers, and that overpayment is the recommended safe pattern (to avoid reverts from `swapETHForExactTokens` slippage failure), this results in a persistent, protocol-wide drip of permanently locked user funds — a medium-severity freezing-of-funds issue affecting any unprivileged caller of the fungible-token bridge apps or `EvmHost.dispatch()` directly.

### Likelihood Explanation
High likelihood of occurrence in normal operation: because on-chain price of the native/fee-token pair can move between the time a user calls `quote()` off the currently observed reserves and the time their `send()` transaction is mined, users must send a buffer above the quoted amount to avoid transaction failure. Every such buffer is lost. No malicious actor is required — this triggers under ordinary usage.

### Recommendation
After the `swapETHForExactTokens` call in `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)`, capture the `amounts[0]` actually spent and refund `msg.value - amounts[0]` back to `_msgSender()` (mirroring the refund pattern already implemented in `IntentGatewayV2.placeOrder()`), e.g.:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
if (msg.value > amounts[0]) {
    (bool sent, ) = _msgSender().call{value: msg.value - amounts[0]}("");
    require(sent, "EvmHost: refund failed");
}
```

### Proof of Concept
1. User calls `HyperFungibleToken.send()` (or `WrappedHyperFungibleToken.send()`) with `msg.value` set slightly above the value returned by `quote()`, as recommended to tolerate slippage. [3](#0-2) 
2. `send()` forwards the entire `msg.value` to `EvmHost.dispatch(DispatchPost)`. [1](#0-0) 
3. `swapETHForExactTokens` consumes only the ETH needed to buy exactly `post.fee` fee tokens and refunds the remainder to `EvmHost` (the caller of the router), not to the user.
4. `EvmHost.dispatch()` returns without forwarding any refund; the leftover ETH remains permanently in `EvmHost`'s balance, unrecoverable by the user or the calling app.
