### Title
Webhook `shop` identifier is trusted from an HTTP header that is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the tenant identifier straight from the `X-Shopify-Shop-Domain` header, but the HMAC signature that `Registry.process` verifies covers only the raw request body, never the headers. Any actor who can obtain one genuinely-signed webhook body/HMAC pair (e.g., by installing the app on their own store) can replay that exact body with a forged `shop-domain` header, and the library will pass the forged shop identity to the app's handler as authenticated data.

### Finding Description
The binding that should hold is:
`shop_used_by_handler == shop_that_HMAC_actually_authenticates`

`Request#to_signable_string` (used for HMAC verification) returns only `@raw_body`: [2](#0-1) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside that signed string: [3](#0-2) 

`Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string`, i.e. the body only) and then immediately builds `WebhookMetadata` using `request.shop`, handing it to the app's handler as trusted tenant context: [4](#0-3) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` field, never touching the `shop` header: [5](#0-4) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any user who installs the app on a store they control receives a genuinely HMAC-signed webhook for their own shop. They can capture that raw body + HMAC pair and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop. `Utils::HmacValidator.validate` still returns `true` because the signature only ever attested to the body, not the header, so `Registry.process` dispatches the (attacker-chosen) body to the handler labeled with the victim's shop domain.

### Impact Explanation
This breaks the tenant identity binding at the trust boundary the whole webhook-verification mechanism exists to protect: the HMAC is meant to prove "this event genuinely came from Shopify for this shop," but the shop attribution is unauthenticated. Any downstream code that uses `WebhookMetadata#shop` (or `request.shop`) to look up sessions, access tokens, or shop-scoped data will act on attacker-chosen tenant identity with attacker-chosen body content that has nevertheless passed HMAC verification — a cross-tenant data-confusion / cross-tenant access primitive that matches the report's bug class (verification covers different bytes than the value acted upon).

### Likelihood Explanation
An attacker needs only to be able to install the target app on a shop they control (a normal, unprivileged onboarding flow for any Shopify app) to obtain one legitimately signed webhook body/HMAC pair, then replay that body to the endpoint with a modified `shop-domain` header. No access token, `client_secret`, or victim credentials are required.

### Recommendation
Include the shop domain (and other identifying headers such as `topic`/`webhook-id`) inside the signed payload the HMAC is checked against, or otherwise cryptographically bind the header-derived `shop` value to the verified body (e.g., verify shop against a value embedded and covered by the HMAC, or require the consuming application to cross-check `request.shop` against the shop tied to the specific `webhook_id`/subscription it registered, not blindly trust the header).

### Proof of Concept
1. Install the vulnerable app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the raw POST body plus its `x-shopify-hmac-sha256` header (both are computed with the app's real `api_secret_key`, so the signature is valid).
2. Replay that captured request to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim.myshopify.com`, keeping the identical body and HMAC header.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` which passes (it only checks the raw body against the HMAC), then builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and dispatches it to the registered handler, which will process attacker-controlled data under the victim shop's identity.
