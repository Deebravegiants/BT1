Confirmed: the gem's documentation explicitly tells app developers to trust `data.shop` as "The shop domain of the webhook" (`docs/usage/webhooks.md:14`), and `Registry.process` passes `request.shop` straight into `WebhookMetadata` after only checking `Utils::HmacValidator.validate(request)` succeeds [1](#0-0) . But the HMAC is computed only over the raw body, never the `shop`, `topic`, or `webhook-id` headers [2](#0-1) [3](#0-2) , so the identity binding `shop == HMAC-authenticated shop` never actually holds.

### Title
Webhook `shop` (and `topic`/`webhook_id`) fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop as soon as `Utils::HmacValidator.validate(request)` passes, then forwards `request.shop` to the app's handler inside `WebhookMetadata`. However, `Request#to_signable_string` returns only `@raw_body` [4](#0-3) , and `HmacValidator` computes/compares the signature strictly against that signable string [3](#0-2) . None of the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers are included in the signed material — they are read straight from attacker-controllable HTTP headers [5](#0-4) .

### Finding Description
The intended identity binding is: `HMAC-authenticated payload == (shop, topic, body)` that Shopify actually sent for a specific merchant. In reality the code only proves `HMAC-authenticated payload == raw_body`; the `shop` (tenant), `topic`, and `webhook_id` values are unauthenticated headers that `Registry.process` reads and hands to the app's handler unchanged:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [6](#0-5) 

An unprivileged internet user who legitimately installs the merchant's app on their own store (a normal, unprivileged action requiring no special credentials) will receive genuine Shopify webhook deliveries containing a valid `body` + `hmac-sha256` header pair for their own shop. Because the HMAC never covers the `shop`/`topic`/`webhook-id` headers, that user can replay the exact same `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain or another topic value. `HmacValidator.validate` will still succeed since it only checks `raw_body` against the secret, and `Registry.process` will call the handler with `data.shop` set to the attacker-chosen victim domain and `data.body` containing the attacker's own (fully attacker-influenced, since it's their own store's data) payload.

Per the gem's own documentation, app authors are told to treat `data.shop` as authoritative — "the shop domain of the webhook" — and typically use it directly as the tenant key for database writes (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [7](#0-6) . This is exactly the documented, intended usage pattern of the gem's own API — not host-application misuse.

### Impact Explanation
This breaks tenant isolation: an attacker who is merely a self-service, unprivileged user of the platform (installs the app on their own store) can forge webhook deliveries that are processed by the target application as belonging to an arbitrary other shop, since only the body content is authenticated and not the shop identity attached to it. Depending on how the host app uses `data.shop`/`data.body` (webhook processing is documented as writing to per-shop records keyed by `data.shop`), this enables cross-tenant data corruption/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: the attacker only needs to install the app on their own shop (or otherwise obtain one valid signed webhook body) to harvest a valid `(raw_body, hmac)` pair, then replay it with a forged `shop-domain`/`topic` header to the app's public webhook endpoint. No secret material, access token, or privileged access is required — only standard HTTP request crafting.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` headers (not just the raw body) in the HMAC-signed/verified material, or independently validate that `request.shop` matches a shop for which the raw body's `hmac` was actually issued (e.g., by having `to_signable_string` incorporate the relevant headers, mirroring how `AuthQuery#to_signable_string` covers all OAuth query fields it authenticates). At minimum, document and/or enforce that `data.shop` must not be trusted as tenant-identifying without additional binding to the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook, e.g. `orders/create`, with a valid `x-shopify-hmac-sha256` computed over the JSON body.
2. Attacker captures the raw `body` and `hmac` header from this delivery.
3. Attacker POSTs the same `body` + `hmac` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `HmacValidator.validate` succeeds (it only checks `body` against secret) [8](#0-7) .
5. `Registry.process` invokes the app handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` [9](#0-8) , causing the host app to process attacker-controlled data under the victim shop's tenant identity.
