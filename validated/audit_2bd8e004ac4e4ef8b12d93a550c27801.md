### Title
`Oauth.begin_auth` omits `Utils::ShopValidator.sanitize!`, allowing OAuth-authorize redirect to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all call `Utils::ShopValidator.sanitize!(shop)` before using the shop value, rejecting anything that isn't a trusted Shopify domain. `Oauth.begin_auth` never performs this validation and instead interpolates the raw `shop` string directly into the constructed authorize URL via `auth_base_uri`, breaking the trust boundary that the rest of the gem enforces.

### Finding Description
The broken equality is: `shop accepted by Oauth.begin_auth` should equal `shop accepted by ClientCredentials.client_credentials / RefreshToken.refresh_access_token / TokenExchange.migrate_to_expiring_token` (i.e., only strings passing `Utils::ShopValidator.sanitize!`). It does not.

In `client_credentials`, `refresh_access_token`, and (per the question) `migrate_to_expiring_token`, the shop is validated with `validated_shop = Utils::ShopValidator.sanitize!(shop)` [1](#0-0) [2](#0-1)  before it is placed into a `Session`/base URI used for outbound HTTP requests.

`Oauth.begin_auth`, however, takes `shop` straight from its caller and passes it unvalidated to `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` (or a dev-server variant) with no domain check: [3](#0-2) [4](#0-3) . Only `Context.setup?` and `Context.private?` are checked; there is no call to `Utils::ShopValidator.sanitize!` anywhere in `begin_auth`.

`Utils::ShopValidator.sanitize!` raises `Errors::InvalidShopError` for any string whose host doesn't resolve to one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [5](#0-4) . Since `begin_auth` never calls this, an attacker-supplied `shop` such as `"attacker.example.com"` (or values that would normally raise) is accepted and used to build the OAuth authorize redirect URL that the host application returns to the caller (typically to redirect the user's browser). This means an app built per the gem's own documented usage — taking `shop` from a query/header param and passing it straight to `begin_auth` (see the documented example using `request.headers["Shop"]`) [6](#0-5)  — will construct and hand back a redirect URL pointing at an attacker-chosen host, carrying the app's `client_id`, requested `scope`, and callback `redirect_uri` in the query string, and setting a matching state cookie.

None of the existing guards prevent this: `HmacValidator.validate` and the `state` comparison only apply in `validate_auth_callback` (the return leg), not `begin_auth`; `Context.setup?`/`private?` only check global app configuration, not the shop string; there is no JWT/`aud` check involved in this code path since `begin_auth` doesn't process a session token.

### Impact Explanation
The impact is a trust-boundary inconsistency that lets an attacker force the app to generate (and typically have the app's browser-redirect logic send the user to) an authorize URL pointing at a host of the attacker's choosing, exposing the app's public `client_id`, requested `scope`, and configured `redirect_uri`, and binding a fresh anti-CSRF `state`/cookie to that flow. This matches the "SSRF-style redirect for a shop string" framing in the question and the "forced OAuth completion / SSRF driving a request to an unintended host" High-severity category, since it is the one entry point in the gem that skips the shared `ShopValidator` domain check used everywhere else. It does not, by itself, leak `api_secret_key`, an access token, or allow direct forging of `validate_auth_callback` (which is HMAC-protected), so it does not rise to Critical.

### Likelihood Explanation
Any app built on this gem that passes an unsanitized, request-derived `shop` value to `begin_auth` — exactly as shown in the gem's own documentation example (`shop = request.headers["Shop"]`) — is affected without any special configuration. The attacker only needs to control the `shop` value in a request to the app's login/OAuth-start endpoint, which is within the stated attacker capabilities (no secrets required). This is trivially repeatable per request/victim.

### Recommendation
Add `validated_shop = Utils::ShopValidator.sanitize!(shop)` at the start of `Oauth.begin_auth`, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, and use `validated_shop` in `auth_base_uri` instead of the raw `shop` parameter.

### Proof of Concept
```ruby
# test/auth/oauth_shop_validation_test.rb (proposed)
require_relative "../test_helper"

class OauthShopValidationTest < Test::Unit::TestCase
  def test_shop_validator_rejects_untrusted_shop
    assert_raises(ShopifyAPI::Errors::InvalidShopError) do
      ShopifyAPI::Utils::ShopValidator.sanitize!("not-a-shop")
    end
  end

  def test_begin_auth_does_not_validate_shop
    # begin_auth should raise the same InvalidShopError for consistency,
    # but currently does not.
    result = ShopifyAPI::Auth::Oauth.begin_auth(
      shop: "not-a-shop",
      redirect_path: "/cb",
    )
    assert result[:auth_route].start_with?("https://not-a-shop/admin/oauth/authorize")
    # Demonstrates begin_auth builds a redirect to an attacker-chosen host
    # while every other entry point (client_credentials, refresh_access_token,
    # migrate_to_expiring_token) would raise Errors::InvalidShopError for the
    # same input.
  end
end
```
This confirms the divergence: `ShopValidator.sanitize!("not-a-shop")` raises, but `Oauth.begin_auth(shop: "not-a-shop", ...)` succeeds and returns an `auth_route` targeting the untrusted host.

```ruby
        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
```

```ruby
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```

```markdown
class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
```
