### Title
Fee-on-transfer input tokens desynchronize escrow accounting from actual balances in `IntentGatewayV2.placeOrder` (Tron variant) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` credits the internal escrow ledger `_orders[commitment][token]` with the nominal (pre-transfer) `order.inputs[i].amount` (minus protocol fee), rather than the amount actually received by the contract. On fee-on-transfer ERC20 tokens, the contract's real token balance ends up lower than the value it has bookkept for withdrawal, causing later `withdraw()` calls to attempt paying out more tokens than the pool actually holds.

### Finding Description
In `placeOrder`, both the non-predispatch branch and the predispatch branch pull tokens in via `safeTransferFrom`/sweep `Call`s using the caller-specified `order.inputs[i].amount`/`requiredAmount`, but never re-measure the contract's actual balance delta afterward: [1](#0-0) 

The escrow ledger is incremented with `reducedInputs[i].amount`, which is computed purely from the user-declared `order.inputs[i].amount` minus the protocol fee — with no adjustment for a token-level transfer fee: [2](#0-1) 

The predispatch branch has the same issue: it computes `dust = balance - requiredAmount` for the dispatcher's balance *before* the sweep-out transfer (which itself may burn a fee when moving funds from the dispatcher to the gateway), yet still credits `reducedInputs[i].amount` (unadjusted) to `_orders[commitment][token]`: [3](#0-2) 

This is a real regression relative to the main EVM `IntentGatewayV2.sol`, which explicitly re-measures balances before/after each transfer specifically to protect against fee-on-transfer tokens, both in the predispatch sweep and the direct-transfer path: [4](#0-3) [5](#0-4) 

That measure-then-record fix is even covered by dedicated tests in the main EVM app (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, `testPlaceOrder_FeeOnTransferToken_Predispatch`): [6](#0-5) 

but no equivalent tests or logic exist for the Tron contract, confirming the divergence is unintentional.

Because ERC20 balances are pooled per token across all orders in the same contract (not segregated per-commitment), the ledger overstating one order's escrow means that order's `withdraw()` call — triggered either by a same-chain `fillOrder`-driven local settlement, a cross-chain `RedeemEscrow`/`RefundEscrow` message via `onAccept`, or a `GET` response via `onGetResponse` — will attempt to `transfer` more tokens than the contract's real balance permits for that slice of accounting, since `withdraw()` blindly sends `body.tokens[i].amount` (the escrowed, unadjusted amount) to the beneficiary: [7](#0-6) 

### Impact Explanation
Two concrete, unprivileged-reachable outcomes:
1. **Insolvency / fund freezing across orders**: Since the escrow bookkeeping for a fee-on-transfer order records more tokens than were actually deposited, the aggregate liabilities recorded in `_orders` across all commitments for that token can exceed the contract's real balance. When later orders (for the same token) attempt `withdraw()`, the `token.call(...transfer...)` can fail once the pool is drained below what is owed, permanently freezing legitimate users'/solvers' funds that were properly deposited without a transfer fee.
2. Any single order placed with a fee-on-transfer token silently under-collateralizes itself relative to what its own `withdraw()` will later try to pay out, degrading the destination-chain relayer's or a redeeming solver's ability to be made whole, and potentially reverting the intended settlement (DoS on that order specifically, or theft from the shared pool by other resolved orders that manage to withdraw first).

This is reachable by any unprivileged user simply by calling `placeOrder` with a fee-on-transfer ERC20 as an input token — no admin/governance/relayer privilege is required, satisfying the "unprivileged... token bridger/intent solver" reachability requirement. Given the potential for cross-order fund freezing/loss, this is Medium/High severity, consistent with the analogous Sherlock finding.

### Likelihood Explanation
Likelihood is Medium: it requires the order's input token to actually implement a transfer fee (e.g., STA, PAXG-style tokens, or any deflationary/rebasing ERC20), which is a known but non-universal class of tokens. The Tron deployment of `IntentGatewayV2` does not restrict `order.inputs` to a token allowlist that would exclude such tokens, so any user is free to submit an order using such a token as input, immediately triggering the desync described above.

### Recommendation
Mirror the main EVM `IntentGatewayV2.sol` fix in the Tron variant: measure the contract's (and dispatcher's) actual token balance before and after each `safeTransferFrom`/sweep, and use the measured delta — not the caller-declared `order.inputs[i].amount` — both to mutate `order.inputs[i].amount` for the commitment hash and to credit `_orders[commitment][token]`. Apply this to both the non-predispatch direct-transfer path and the predispatch sweep-from-dispatcher path in `evm/tron/contracts/apps/IntentGatewayV2.sol`, and add the equivalent fee-on-transfer regression tests that already exist for the main EVM gateway.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and a fee-on-transfer ERC20 (e.g., 1% fee, same semantics as `FeeOnTransferToken` used in the main EVM test suite: [8](#0-7) ).
2. User approves and calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}` and no protocol fee.
3. `safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual FOT balance only increases by `990e18`.
4. `_orders[commitment][FOT]` is incremented by `reducedInputs[0].amount == 1000e18` (unadjusted), i.e., 10e18 more than the contract actually holds for this order.
5. When the order is later redeemed via `withdraw()` (same-chain fill, `RedeemEscrow`, or `RefundEscrow`), the contract attempts to `transfer` `1000e18` FOT to the beneficiary, but only has `990e18` credited from this order's real deposit — either reverting (`TransferFailed`) if it's the last order for that token, or succeeding by consuming `10e18` worth of another order's escrowed FOT balance, desynchronizing the ledger for that other order as well.

        Order memory order = Order({

            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),

            output: output

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
