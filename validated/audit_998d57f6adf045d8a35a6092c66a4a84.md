## Custody invariant reduction

The external "escrow reuse" bug reduces to: **a one-time-use authorization condition must not be satisfiable across multiple, independent executions.** In `stablecoin::usdk`, the analog is a signed off-chain **approval message** used to gate an on-chain fungible-asset transfer — the same "condition" (a signature) must not be replayable to move funds more than once.

## Candidate paths considered

1. `object::burn`/`unburn` TombStone reuse — bounded by owner-only checks, no unprivileged path found.
2. `multisig_account` sequence-number-gated execution — sequence numbers are monotonic and transactions are removed on execution (`remove_executed_transaction`), so replay is prevented by design.
3. `resource_account::retrieve_resource_account_cap` — capability consumed via `SimpleMap::remove`, single-use, no reuse path.
4. **`stablecoin::usdk::transfer_from` nonce-based approval — strongest candidate**, broken replay protection.

## Title
Signed transfer approval in `usdk::transfer_from` is replayable, allowing unlimited unauthorized fund transfers - (File: aptos-move/move-examples/fungible_asset/stablecoin/sources/usdk.move)

## Summary
`transfer_from` authorizes a `spender` to move funds out of `from`'s account based on an off-chain-signed `Approval` message, using `account::get_sequence_number(from)` as the anti-replay nonce. Because `from` is never the transaction sender in this flow, `from`'s sequence number is never incremented as a side effect of this call, so the same signature can be submitted repeatedly, draining far more than the owner approved.

## Finding Description [1](#0-0) 

`transfer_from` builds an `Approval { owner: from, to, nonce: account::get_sequence_number(from), chain_id, spender, amount }` struct and verifies it against a signature supplied by the caller via `account::verify_signed_message`. The transaction is submitted and signed by `spender`, not by `from` — `from` is only referenced as a plain `address` parameter, not as a `&signer`. Aptos account sequence numbers are only incremented as part of normal transaction prologue/epilogue processing for the account that is the **sender** of a transaction. Since `from` is not the sender here, nothing in this call path increments `from`'s sequence number.

Consequently, the nonce embedded in the signed `Approval` (`account::get_sequence_number(from)`) remains constant across repeated calls to `transfer_from` with the same `proof`, unless `from` independently submits an unrelated transaction on its own (bumping its sequence number by exactly 1, which invalidates only one replay attempt before `from` acts). An attacker who obtains one valid `Approval` signature (e.g., a user approves a $10 transfer) can resubmit the identical `proof`/parameters to `transfer_from` an arbitrary number of times before `from`'s sequence number changes, each time passing the nonce check and moving `amount` out of `from`'s primary fungible store via `primary_fungible_store::transfer_with_ref`.

This breaks the custody invariant that an owner-authorized transfer of value should execute exactly once per authorization — the same "escrow condition" class of bug as the external report, but rooted in local, Aptos-native code: nonce derived from the wrong account's transaction-execution state rather than an explicit, self-incrementing single-use counter tied to the approval itself.

## Impact Explanation
This is a direct custody-grade impact: theft of fungible-asset value (`USDK`) from `from`'s primary store without additional owner authorization. A single approved transfer can be replayed to drain the entire balance of `from`'s store, limited only by `from`'s balance and by how quickly `from` submits any transaction of its own (which would only stop further replay, not undo the already-executed unauthorized transfers). This satisfies "Theft ... of ... fungible assets" and "Supply or custody accounting corruption that moves value to the wrong holder."

## Likelihood Explanation
High likelihood: `transfer_from` is a `public` function callable by anyone in possession of one legitimately obtained `proof`/signature (e.g., a spender who was approved for one transfer). No special privilege, admin assumption, or race condition is required — simply calling the function multiple times with identical arguments. The signature never needs to be re-derived because the nonce it commits to does not change across calls.

## Recommendation
Use a dedicated, self-incrementing, single-use nonce/counter stored per-owner inside the `usdk` module's own resources (incremented atomically as part of `transfer_from`, independent of the `from` account's global transaction sequence number), or otherwise bind the approval to a value that is guaranteed to change and be invalidated by the same execution that consumes it (e.g., store consumed approval hashes in a set to reject their reuse).

## Proof of Concept
1. `from` signs one `Approval { owner: from, to: attacker, nonce: N, chain_id, spender: attacker, amount: 10 }` where `N = account::get_sequence_number(from)` at signing time, and hands the signature to `spender`/`attacker` for a single intended $10 transfer.
2. `attacker` calls `usdk::transfer_from(attacker, proof, from, scheme, pubkey, attacker, 10)`. `account::verify_signed_message` succeeds because `nonce == account::get_sequence_number(from)` still holds (since `from` never signed/sent this transaction, its sequence number is untouched). 10 tokens move from `from` to `attacker`.
3. `attacker` calls the exact same `transfer_from(...)` again with identical parameters/`proof`. `from`'s sequence number is still `N` (unchanged), so the check passes again, moving another 10 tokens.
4. Repeat step 3 until `from`'s balance is exhausted or `from` submits any transaction of its own (which would only stop further replays after that point, without recovering already-stolen funds).

Confirming the exact epilogue code path that increments `Account.sequence_number` (in `aptos-move/framework/aptos-framework/sources/account/account.move`) would further solidify this, but was not fully re-verified due to tool-call limits in this session — a Devin session with full repo/test access could confirm via a Move unit test exercising `transfer_from` twice with the same signature.
