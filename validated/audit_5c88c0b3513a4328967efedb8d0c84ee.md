### Title
Attacker-supplied swap route invokes arbitrary on-chain contracts under the caller's signature, draining the caller's wallet beyond the routed amount - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The Jenkins `email-ext` bug (CWE-73) lets whoever controls content pass an unrestricted external reference (`file:` URL) that the system dereferences, so an attacker-chosen "resource" reaches data outside the intended scope. The same class exists here: the `swap` bytes a caller submits to `multiply` / `swap_collateral` / `swap_debt` / `repay_debt_with_collateral` (or directly to `execute_strategy`) carry a caller-controlled address registry of pools and tokens, and the router invokes whatever contract address the payload names as a "pool" — with no venue allowlist — while executing inside the subtree of the caller's `require_auth`. A route that still pays a fair `token_out` (so every settlement check passes) can name an attacker-deployed pool that calls `token.transfer(victim, attacker, x)` on any token in the victim's wallet; the host records that transfer as a child of the caller's authorization entry and it executes once the caller signs the simulated tree.

### Finding Description
`execute_strategy` decodes the payload's `assets` registry and per-hop pool indices (`contracts/swap-aggregator/src/execute/mod.rs:152-158`), then `dispatch_hop` → `aquarius::swap` → `invoke_pool_swap` performs `env.invoke_contract(pool, "swap", ...)` on the payload-supplied address with no check that the pool belongs to any known venue (`contracts/swap-aggregator/src/venues/aquarius/pool.rs:34`). On the controller side, `swap_tokens` forwards the raw `StrategySwap` bytes to the router and validates only measured `token_in`/`token_out` deltas plus the final account risk gate (`contracts/controller/src/strategies/swap.rs:29-54`), none of which constrains which third-party contracts run beneath the user's signature. A rogue pool can therefore execute arbitrary calls during the hop — most critically `transfer` on an unrelated wallet token from the `sender`, which the Soroban host attributes to the caller's auth entry because it sits below the `require_auth` invocation. The threat model itself acknowledges the router "keeps no allowlist" of pool/token addresses and that such a transfer "executes if the caller signs that tree" (`docs/explanation/threat-model.md:154-164`), and the harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates a `swap_collateral` route whose rogue hop pool transfers Alice's entire balance of an unlisted token to the attacker while still returning a fair output.

### Impact Explanation
Theft of user funds beyond the swapped amount: any token held by the victim's signing address can be pulled into the attacker-controlled pool call. The loss is the victim's whole wallet balance of any token the payload's embedded code chooses to name, unbounded by `amount_in`, `total_min_out`, or the controller's final risk check — the swap itself can settle at fair value so every protocol-side guard (`RouterOverspend`, `NoSwapOutput`, min-out, health factor) passes.

### Likelihood Explanation
Exploitation requires the victim to sign a transaction whose simulated authorization tree contains the rogue child entry. The route is opaque packed XDR (`program.rs`) built off-chain by a quote service; a user following the normal simulate-and-sign flow sees the theft only if their client decodes the auth tree and rejects non-standard children. Any route source the user does not fully verify (a poisoned quote, a spoofed router response, a malicious composability wrapper) can inject the extra hop. Attack path is reachable by any unprivileged address crafting the payload; it requires one victim signature, analogous to the report's "attacker controls the email content" precondition. Medium likelihood, high impact.

### Recommendation
Restrict each hop's `pool` address to a governance-controlled venue allowlist (or a per-venue pool registry) inside the router so payload bytes cannot name arbitrary contracts; alternatively have the controller validate the decoded route's pool set before authorizing the router call. Absent an on-chain allowlist, this is a signer-side hazard — documenting "decode the auth tree and refuse unexpected children" is a mitigation, not a fix, and every downstream integrator must implement it independently.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: an `UnlistedPoolRouter` stand-in plus a `RogueHopPool` deployed with a `(victim, wallet_token, attacker, amount)` plan; the route through `swap_collateral` pays the fair ETH output while the pool's `swap` executes `token::Client::transfer(victim, attacker, WALLET_BALANCE)`, which simulation records as a child of Alice's `swap_collateral` auth entry and which enforcing mode accepts once she signs the tree. With the real router the same injection works through `execute_strategy`'s `assets` registry: a `Swap` op's `idx_a` resolves to any caller-chosen address (`execute/mod.rs:152-157`, `venues/aquarius/pool.rs:34`), and neither `Program::decode` nor `dispatch_hop` constrains it to a known venue contract.
