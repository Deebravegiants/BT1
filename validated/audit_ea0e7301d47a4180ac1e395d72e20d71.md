Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by calling `Utils::HmacValidator.validate(request)`, which verifies the HMAC over `request.to_signable_string`. `Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop`, `topic`, and `webhook_id` values, read straight from unauthenticated HTTP headers, are never included in the signed material [2](#0-1) , yet they are trusted and forwarded verbatim into the handler as `WebhookMetadata` after only the body-HMAC check passes [3](#0-2) .

### Finding Description
The identity binding that should hold is:

`shop header value used to attribute/act on tenant data == shop that actually generated (and is cryptographically bound to) the HMAC-signed payload`

`HmacValidator.validate` computes `HMAC-SHA256(secret, raw_body)` and compares it (via `OpenSSL.secure_compare`) to the `hmac` supplied on the request [4](#0-3) . The secret (`Context.api_secret_key`) is a single per-app secret shared across every shop that installs the app — it is not shop-specific. Consequently, **any** raw body that was legitimately signed for **any** shop produces a signature that will validate successfully regardless of which `shop-domain` header accompanies it, because the shop identity is never part of the signed bytes.

`Registry.process` performs exactly one authentication check (`Utils::HmacValidator.validate(request)`) and, immediately after, builds `WebhookMetadata` from `request.topic`, `request.shop`, `request.parsed_body`, and `request.webhook_id` [5](#0-4) . Since `Request#shop`, `#topic`, and `#webhook_id` are simple header reads with no cryptographic tie to the HMAC [2](#0-1) , the "shop that produced the valid signature" and the "shop the handler is told to act on" are two independent, unauthenticated values that the library conflates.

Because a Shopify app's webhook endpoint is a public HTTP(S) URL (that is the entire point of webhooks — Shopify's servers POST to it), any unprivileged internet user who merely installs the target app on their own store receives genuine webhooks for that store, each carrying a correctly computed HMAC over that specific body. That attacker can now replay the exact same `(raw_body, hmac)` pair to the same endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (the body and secret are unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the forged shop.

### Impact Explanation
This is a cross-tenant identity confusion: an app's webhook handler typically uses `WebhookMetadata#shop` to look up which merchant's session/access token/records to act on (e.g., fulfilling an order, updating a customer, revoking data per GDPR topics). By forging the shop header while keeping a self-controlled, validly-signed body, an unprivileged attacker can make the host application perform tenant-scoped side effects against a **victim** shop's account instead of their own — a cross-tenant access impact, which falls squarely in the "Critical" bucket defined by the rules (cross-tenant access via a broken identity binding).

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-owned/attacker-controlled development store (an ordinary, unprivileged action any developer can take), (2) capturing one legitimate webhook delivery to observe a valid `(raw_body, hmac)` pair, and (3) replaying it to the app's public webhook URL with a different `shop-domain` header. No access token, `client_secret`, or privileged account is needed — this only requires the gem's own signature-checking logic to be as implemented. Exploitability further depends on the host application trusting `WebhookMetadata#shop` for tenant-scoped actions, which is the documented, expected usage pattern of this API (`handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`) [6](#0-5) .

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity to the cryptographic verification, rather than trusting header-only fields. For example, incorporate the `shop-domain` (and `topic`) header into the signable string used by `HmacValidator`, or require callers to independently verify that `request.shop` corresponds to a shop with a currently installed/active session for this app before invoking any handler — and document this requirement prominently since `Registry.process` currently performs no such check itself.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook, e.g. topic `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(app_secret, B)` — valid because it is signed with the app's single shared secret [7](#0-6) .
3. Attacker replays a POST to the app's public webhook endpoint with the unmodified body `B`, unmodified `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers with no cross-check between `shop` and `hmac` [8](#0-7) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)` — it returns `true` because the HMAC is computed only over `B` [9](#0-8) .
6. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body `B` as if it came from the victim shop.

        missing_headers = []

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
