### Title
`IntentGatewayV2.placeOrder` predispatch escrow trusts the shared `CallDispatcher`'s live token balance instead of the amount actually produced by the user's own predispatch call, letting an order claim any stray/dust funds sitting in the dispatcher - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
The predispatch branch of `placeOrder` escrows whatever balance the shared `CallDispatcher` contract currently holds for `order.inputs[i].token`, rather than the amount actually produced by the user's own `order.predispatch.call`/`order.predispatch.assets`. Because `CallDispatcher` is a single, shared, unrestricted contract (any address can send it ETH or tokens, and dust from other users' predispatch/postdispatch executions can be left unswept there), an attacker can place an order with a trivial/cheap predispatch, declare `order.inputs[i].token` to be a valuable token that happens to be sitting in the dispatcher, and have that entire balance swept into their own escrowed order — exactly the "use the contract's own balance of an unrelated token instead of the amount the user actually deposited" bug class described in the DODO `GatewayTransferNative` report.

### Finding Description
In `placeOrder`, when an order carries predispatch calldata, the flow is:

1. Only `order.predispatch.assets` are transferred from `msg.sender` into the `CallDispatcher`: [1](#0-0) 

2. The user-supplied `order.predispatch.call` is executed by the dispatcher: [2](#0-1) 

3. For each `order.inputs[i]` (a completely separate, user-chosen token/amount from `order.predispatch.assets`), the code reads the dispatcher's *current* balance of that token and, as long as it is `>= requiredAmount`, sweeps the dispatcher's **entire** balance of that token back to the gateway: [3](#0-2) 

4. The amount actually escrowed for the order is capped at `order.inputs[i].amount`; anything above that is emitted as protocol dust, but the capped amount is unconditionally credited to the attacker's own order: [4](#0-3) 

Crucially, the "received" delta at step 4 is measured against the **gateway's** balance before/after (`balancesBefore[i] = balanceOf(address(this))`), not against the **dispatcher's** balance before/after the predispatch call. There is no check that `order.inputs[i].token` is a token that `order.predispatch.call` actually produced, and no check that the value being transferred in was freshly generated by *this* predispatch execution rather than already resident in the dispatcher.

`CallDispatcher` is a single shared, non-custodial-by-design executor with an open `receive()` and no access control, used by every user's `placeOrder` (predispatch) and `fillOrder`/`_execute` (postdispatch) calls: [5](#0-4) 

Balances can and do land in it outside of the current transaction's control flow:
- `_execute`'s postdispatch dust-sweep only sweeps tokens that are part of `order.output.assets` for that particular fill; any token produced by `order.output.call` that isn't in that list is left stranded in the dispatcher indefinitely: [6](#0-5) 
- Anyone can also directly send ETH or ERC20 tokens to the dispatcher's address since it has no deposit gating.

Because the predispatch sweep in `placeOrder` only checks `balanceOf(dispatcher) >= requiredAmount` for the attacker-chosen `order.inputs[i].token`, any of this leftover/foreign value — dust from other users' fills, stray transfers, or a previous order's stranded token — can be claimed by a subsequent attacker who supplies a cheap/no-op predispatch and simply names that token as their own order input.

### Impact Explanation
An attacker can place an intent order whose "input" escrow is backed not by their own deposited funds but by value that happens to be sitting in the shared `CallDispatcher` (accumulated dust, stray sends, or stranded output tokens from unrelated orders). That escrow can then be:
- refunded to the attacker via `_cancelSameChain`/`_cancelFromSource` once the deadline passes, or
- used as the input side of a legitimate solver fill, letting the attacker receive real solver-provided output tokens in exchange for value they never actually deposited.

This is a direct theft/drain of protocol- or user-owned value that transits through the shared dispatcher, reachable by any unprivileged caller via a single `placeOrder` transaction — matching the "intents escrow" theft-of-funds category.

### Likelihood Explanation
Likelihood depends on the `CallDispatcher` holding a nonzero balance of some ZRC/ERC20/native asset at the time of attack. Given that:
- `_execute`'s sweep is scoped only to the current order's `output.assets`, tokens produced as side-effects of arbitrary output/predispatch calldata (e.g., swap dust, rounding remainders, reward tokens, approval residue) can accumulate unswept over time, and
- the dispatcher's `receive()` is unrestricted so third parties (or the attacker themselves in a prior transaction, e.g. via a failed/partial predispatch call) can seed it,

this condition is realistically reachable over the contract's operational lifetime, mirroring the "contract accumulates value via refunds/dust" precondition in the original DODO report. No privileged role is required to exploit it once the precondition holds.

### Recommendation
In `placeOrder`'s predispatch branch (and the `evm/tron` variant), measure the tokens escrowed strictly as the *delta* on the `CallDispatcher`'s own balance across the predispatch call (snapshot `balanceOf(dispatcher)`/`dispatcher.balance` immediately before executing `order.predispatch.call`, and only sweep/escrow the increase caused by that specific call), rather than trusting the dispatcher's absolute post-call balance. Additionally, restrict `order.inputs[i].token` sweeps to tokens that are provably outputs of the executed `order.predispatch.call` (e.g., via an allow-list supplied and validated as part of the call encoding), and ensure `_execute`'s postdispatch sweep cannot leave stray token balances unaccounted for in the shared dispatcher.

### Proof of Concept
1. Wait for (or cause) the shared `CallDispatcher` to hold a nonzero balance of a valuable token `X` that is not part of any pending order's tracked `output.assets`/`inputs` (e.g., dust left over from a prior `fillOrder`'s `output.call` producing token `X`, which `_execute`'s sweep loop never targets because `X` wasn't in that order's `output.assets`).
2. Attacker calls `placeOrder` with:
   - `order.predispatch.assets` = a trivial/cheap token/amount the attacker actually owns.
   - `order.predispatch.call` = a no-op or minimal call (e.g., an `approve(0)` on the cheap token) satisfying `dispatch()`'s "must be a contract" check.
   - `order.inputs[0].token = X`, `order.inputs[0].amount = <= dispatcher's existing balance of X>`.
3. `placeOrder` reads `IERC20(X).balanceOf(dispatcher) >= requiredAmount`, sweeps the dispatcher's full `X` balance to the gateway, and escrows `order.inputs[0].amount` of `X` against the attacker's order — funded entirely by value the attacker never deposited.
4. Attacker either lets the order time out and cancels for a refund of `X`, or has a solver fill the order, receiving the solver's output tokens in exchange for the "escrowed" `X` that cost the attacker nothing.

     * @dev Receive function to accept ETH transfers

    receive() external payable {}

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
