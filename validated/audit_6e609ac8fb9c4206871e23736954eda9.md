Based on the codebase analysis, I found a concrete analog matching the "field acted on but not covered by the HMAC" bug class from the rules.

### Title
Webhook shop/topic identity spoofable because HMAC signs only the request body, not the `shop-domain`/`topic` headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the values used for tenant/topic dispatch (`shop`, `topic`, `webhook_id`, `api_version`) entirely from HTTP headers, while `to_signable_string` — the only material fed into the HMAC check — is just the raw body. `Registry.process` verifies the HMAC and then trusts the header-derived `shop`/`topic` without re-authenticating them, handing them straight to the registered handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (the body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` checks only that HMAC, then immediately constructs `WebhookMetadata` from the unauthenticated header values (`request.shop`, `request.topic`) and dispatches to the topic's handler: [4](#0-3) 

The binding that is broken is: **the shop/topic the HMAC was computed for == the shop/topic acted on by the handler**. Because the app's `api_secret_key` is shared across every shop the app serves (it is not shop-specific), any body+signature pair that was ever validly produced for *any* shop in the app's history remains a valid `(body, hmac)` pair forever. An attacker who has observed one legitimate webhook delivery (e.g., from their own installed test shop, or a shop that later uninstalled/reinstalled) can replay that exact `raw_body` and `hmac-sha256` header combination while substituting an arbitrary `x-shopify-shop-domain` and/or `x-shopify-topic` header. `HmacValidator.validate` still returns `true` because it only checks the body against the secret, and `Registry.process` will happily dispatch that forged shop/topic pair to the handler as `WebhookMetadata`.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to look up which merchant's session/access token to act on (the documented pattern, e.g. loading a session and calling the Admin API on behalf of that shop), an attacker can trick the app into performing an authenticated action against a *different* tenant's shop record than the one that actually produced the payload — a cross-tenant confusion. This satisfies the "Critical - cross-tenant access" bar, since the shop identity bound by the HMAC is silently substituted for the shop identity acted on by the app.

### Likelihood Explanation
Exploitation requires the attacker to have previously observed at least one legitimate webhook `(raw_body, hmac)` pair for the target app (e.g., from their own store as an app installer, or a leaked/logged webhook delivery), and requires the target shop's webhook body shape to be compatible enough for the handler logic to act meaningfully (e.g., topics like `app/uninstalled` or `shop/redact` where the body carries little shop-specific data, so the header-derived `shop` is what drives the action). This is a real but non-trivial precondition, so likelihood is moderate rather than trivial.

### Recommendation
Bind `shop-domain` (and ideally `topic`/`api_version`) into the HMAC-signed material in `Request#to_signable_string`, or otherwise cryptographically bind the header-derived identity to the signed body so a captured `(body, hmac)` pair cannot be replayed against a different shop/topic. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are HMAC-unauthenticated and must not be used as the sole tenant key without corroboration (e.g., cross-checking against the session store keyed by an independently-verified identifier).

### Proof of Concept
1. App receives (or attacker otherwise obtains) a legitimate webhook delivery: `raw_body = "{}"`, `x-shopify-hmac-sha256 = HMAC(api_secret_key, "{}")`, `x-shopify-shop-domain = "victim-a.myshopify.com"`, `x-shopify-topic = "app/uninstalled"`.
2. Attacker replays the identical `raw_body`/`hmac-sha256` but sets `x-shopify-shop-domain: victim-b.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against `api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:26-31`), independent of the `shop-domain` header.
4. `Registry.process` builds `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-b.myshopify.com", ...)` and dispatches it to the app's handler as if `victim-b` genuinely sent that webhook (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app to act (e.g., delete/invalidate session data) for `victim-b` based on a payload that never actually came from `victim-b`.
