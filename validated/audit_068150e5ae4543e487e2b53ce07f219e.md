### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on a genuine, previously-observed webhook - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers and passed straight through to the application's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` verifies the HMAC against that signable string alone [2](#0-1) . Meanwhile `Registry.process` reads `request.shop`, `request.topic`, and `request.webhook_id` directly from headers and forwards them into `WebhookMetadata`, which is handed to the app's handler as the identity of the originating shop [3](#0-2) . `Request#shop`, `#topic`, and `#webhook_id` are all sourced from `shopify_header`, i.e., raw HTTP headers, not from any HMAC-covered content [4](#0-3) .

This means the equality the gem implicitly relies on — "shop that produced a validly-HMAC'd body" == "shop attributed by the `shop-domain` header" — does not actually hold. The HMAC only proves the request body was produced with knowledge of `api_secret_key`; it proves nothing about which shop the header claims to be from. An attacker who has legitimately received a genuine webhook (e.g., by installing the app in their own shop, or by observing a webhook payload/HMAC by any other means) can resend that exact same body+HMAC pair with an arbitrary `x-shopify-shop-domain` and `x-shopify-topic` header. The HMAC check still passes since the body is unchanged, but the app processes it as if it came from an arbitrary other shop/topic.

### Impact Explanation
This can cause cross-tenant data confusion in the host application: a webhook payload legitimately generated for the attacker's own shop can be replayed and falsely attributed to a victim shop id supplied by the attacker, or to a different (potentially more sensitive) topic than the one the payload was actually generated for. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., to look up/mutate the victim's stored session, trigger data updates, or fulfill GDPR/mandatory-topic type actions), this can result in the attacker injecting attacker-controlled data into another tenant's records — a cross-tenant integrity issue.

### Likelihood Explanation
Requires the attacker to possess at least one genuine `(body, hmac)` pair — most trivially obtained by installing the app on a shop the attacker controls and capturing a real webhook delivery — and the ability to send an arbitrary HTTP POST with modified headers to the app's webhook endpoint (unprivileged internet action once the endpoint is known). This is a scoped-down but realistic scenario: the requirement is only "having received one legitimate webhook ever," not access to `api_secret_key` or a stolen access token.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified surface, or cross-validate the header-derived shop against an independently-authenticated identity (e.g., require the shop domain to also appear inside the signed JSON body when available, or maintain a server-side mapping from webhook subscription id to expected shop that isn't attacker-suppliable). At minimum, document/require that host applications must not trust `WebhookMetadata#shop` for authorization decisions without an independent binding check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook for topic `customers/data_request` with body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `api_secret_key`).
2. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: shop/redact`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) .
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the host app to act on victim-shop's identity using attacker-supplied payload content.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
