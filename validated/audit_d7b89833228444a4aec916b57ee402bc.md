### Title
Shared Emporium vault lets any CASE 2 caller sweep another user's stranded external-protocol balance as their own UTXO - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` mints an outgoing UTXO purely from the raw pre/post ERC20 balance delta of the shared Emporium contract (`handleOut`/`balanceChange`), without verifying that the funds it observed actually came from the calling transaction's own declared `deltaAmountChanges`. Because CASE 2 ("Stateless Interaction") lets any unprivileged caller target an arbitrary `op.endpoint` with arbitrary `callData` and no wallet/signature binding, an attacker can withdraw a balance that a prior user left parked at a third-party protocol (or as an untracked side-token in the Emporium contract itself) and have it minted to their own shielded UTXO.

### Finding Description
Equality that should hold: `UTXO_minted_to_attacker == attacker_declared_amountChanges[i] + attacker_own_backing`.
Actual on-chain behavior: `UTXO_minted_to_attacker == balancesAfter[i] - balancesBefore[i] (adjusted by deltaAmountChanges[i])`, which is agnostic to whose funds produced that delta.

Path:
1. `Hinkal._externalTransact` (`contracts/Hinkal.sol:244-256`) computes `deltaAmountChanges[i]` solely from the caller's own `circomData.amountChanges`/`erc20TokenAddresses`, transfers only the caller-declared negative deltas to `externalActionData.externalAddress` (Emporium), then calls `runAction`.
2. `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) snapshots `balancesBefore`/`balancesAfter` of the Emporium contract itself for the tokens the *attacker* chose to list, then executes `stack.ops`. For CASE 2 ("Stateless Interaction", `op.invokeWallet == false` or `stack.signerAddress == address(0)`), it does a raw `op.endpoint.call{value: op.value}(op.callData)` (line 112) with no restriction on `op.endpoint` beyond blocking the `callHinkalWallet`/`doSendToRelay` selectors, and no requirement that `stack.signerAddress` be checked at all when it's `address(0)` (`verifyWallet` returns immediately, `EmporiumUpgradeable.sol:314-316`).
3. `handleOut` (`EmporiumUpgradeable.sol:162-184`) mints a UTXO for `balanceChange = balancesAfter[i] - balancesBefore[i]` (adjusted by the attacker's own `deltaAmountChanges[i]` if negative), with **no provenance check** on where that balance increase came from.
4. Because a *previous* user's transaction only ever balance-checks the tokens listed in *that* transaction's own `circomData.erc20TokenAddresses` (`Hinkal.sol:96-147`), any side-effect token the earlier user's CASE 2 op produced but did not list (e.g., an interest-bearing/receipt token from depositing into a lending protocol using the shared Emporium contract as `msg.sender`/depositor) is left sitting, unaccounted, in the Emporium contract. Since CASE 2 calls the target protocol directly from the Emporium contract's own address (not from a per-user `HinkalWallet`), any position or balance created that way is attributable to the *Emporium contract's identity*, shared across all callers.
5. An attacker, in a later transaction, crafts a CASE 2 op (`op.endpoint` = the same lending protocol or the leftover token itself) that pulls that stranded balance back into the Emporium contract's tracked ERC20 balance, declares a trivial `amountChanges[i]` (or even matches it to make `balanceChange` pass the `>=0` check), and `handleOut` mints them a UTXO for the *entire* recovered amount — funds that never came from the attacker's own deposit or nullifier-backed UTXOs.

None of the existing guards stop this: `onlyAllowedRecipient` (`ExternalActionBaseUpgradeable.sol:39-46`) only checks that `msg.sender == Hinkal`, not that `op.endpoint` is restricted; `verifyWallet` is a no-op when `signerAddress == address(0)`; `insertNullifiers`/`rootHashExists`/proof verification only constrain the attacker's own shielded inputs/outputs, not the provenance of funds pulled from `op.endpoint`; and the main `transact` balance/slippage loop only iterates over the attacker's self-chosen `erc20TokenAddresses`, so it cannot detect or prevent draining a token that a prior transaction never declared.

### Impact Explanation
Critical — direct theft of shielded/third-party funds. An attacker mints a shielded UTXO backed by another user's or protocol-position's balance rather than their own proof-committed deposit, i.e., minting shielded value without genuine backing from the attacker. This is repeatable any time residual/stranded balance exists in the shared Emporium contract (from any prior CASE 2 interaction that leaves an untracked token or unclosed external position), and costs the attacker only gas plus a trivial/no real deposit.

### Likelihood Explanation
Requires a precondition: some prior transaction (by any user) used the CASE 2 stateless path to interact with an external protocol in a way that leaves a balance/position attributable to the shared Emporium contract that is not fully closed out and not included in that transaction's declared `erc20TokenAddresses` set (a very plausible pattern for multi-step DeFi compositions — e.g., deposit-only legs, partial withdrawals, receipt/yield tokens). Once such a state exists, exploitation is a single, cheap, fully attacker-crafted transaction (`op.endpoint`, `callData`, `signerAddress = address(0)` all attacker-chosen) with no special privileges needed.

### Recommendation
Track per-user provenance for any balance the Emporium contract accumulates from CASE 2 calls (e.g., require CASE 2 external protocol interactions to always route deposits and withdrawals through amounts that are provably attributable to the current transaction's own `deltaAmountChanges`, or force `handleOut` to cap the minted UTXO amount to `-deltaAmountChanges` for that op rather than the raw contract-wide balance delta). Alternatively, disallow shared, non-wallet-bound (CASE 2) external calls from ever leaving positions/receipt tokens un-swept at the end of a transaction, and require that any token balance not explicitly zeroed by end-of-transaction be swept back to `address(0)`/burned rather than being claimable by the next arbitrary caller. At minimum, require every token balance touched by `op.endpoint.call` (including receipt/yield tokens) to be included in and validated against `circomData.erc20TokenAddresses` for that same transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a mock lending pool (`MockLendingPool`) with `deposit(token, amount)`/`withdraw(token, amount)` that tracks balance by `msg.sender` (i.e., credits/debits whichever address calls it — modeling a real pool where the depositor address is the contract itself).
2. Victim transaction: valid proof, CASE 2 op with `signerAddress = address(0)`, `op.endpoint = MockLendingPool`, `callData = deposit(USDC, 1000e6)`; `circomData.erc20TokenAddresses = [USDC]` only (receipt token `mUSDC` not listed). Assert Emporium's raw USDC balance change nets to zero (passes existing checks) while `MockLendingPool` now credits Emporium's deposit of 1000e6, and/or `mUSDC` balance of Emporium increases by 1000e6 with zero on-chain enforcement.
3. Attacker transaction: valid proof for attacker's own trivial UTXO, `amountChanges[i] = -1` (or 0), CASE 2 op `callData = withdraw(USDC, 1000e6)` (or transfers `mUSDC` out then redeems), `circomData.erc20TokenAddresses = [USDC]` (now including it to capture the sweep).
4. Assert: `utxoSet[0].amount == 1000e6` (full victim-funded withdrawal) even though `attacker_declared_amountChanges[0]` was `-1`/`0`, demonstrating `UTXO_minted_to_attacker != attacker_declared_amountChanges[i] + attacker_own_backing` but instead equals the full stranded balance sourced from the victim's deposit.     function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
        }

        payRelayFees(circomData, stack.signerAddress, deltaAmountChanges);

        uint256[] memory balancesAfter = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        UTXO[] memory utxoSet = new UTXO[](
            circomData.erc20TokenAddresses.length
        );

        uint256 utxoSetLength;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 balanceChange = int256(balancesAfter[i]) -
                int256(balancesBefore[i]);

            if (deltaAmountChanges[i] < 0) {
                balanceChange -= deltaAmountChanges[i];
                // this equation reads: total change of emporium balance = what was moved to emporium (-deltaAmountChange) + how emporium balance changed through tx (balanceChange)
            }

            // the only case when balanceChange can be < 0, when there were some funds on emporium before the call
            if (balanceChange < 0) {
                revert BalanceChangeShouldBePositive();
            }

            UTXO memory utxoOut = handleOut(balanceChange, circomData, i);

            if (utxoOut.amount > 0) {
                utxoSet[utxoSetLength++] = utxoOut;
            }
        }

        if (utxoSetLength < circomData.erc20TokenAddresses.length) {
            utxoSet.skipLast(
                circomData.erc20TokenAddresses.length - utxoSetLength
            );
        }

        return utxoSet;
    }

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
