## Title
Webhook shop identity spoofing via `X-Shopify-Shop-Domain` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute used by `Registry.process` to build `WebhookMetadata` from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature validated by `HmacValidator.validate` is computed only over the raw request body. The `shop` field is therefore an "acted on but not HMAC-covered" value: it can be freely tampered with while the HMAC still validates successfully, breaking the equality `shop authenticated by HMAC == shop attributed to the event by the handler`.

### Finding Description
`Request#to_signable_string` (the value fed into the HMAC check) returns only the raw body: [1](#0-0) 

`Request#shop` is read straight from an attacker-controllable header, entirely independent of that signed payload: [2](#0-1) 

`HmacValidator.validate` / `validate_signature` only ever verifies `verifiable_query.to_signable_string` (i.e. the body) against the received HMAC — the shop header is never part of the signed material: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, and then unconditionally trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's registered handler: [4](#0-3) 

Because the HMAC is keyed only to the body bytes and not to the shop header, any party who possesses one valid `(raw_body, hmac)` pair — for example the operator of their own installed shop who legitimately receives real webhook deliveries for their own store — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` (it never looks at the header), so `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen tenant, associated with the attacker-controlled body content. This is precisely the "field acted on but not covered by the HMAC" identity-binding break called out in the report's rule set: the equality `hmac-authenticated bytes == identity used to route/act on the event` does not hold, because only the body, not the shop identity, is authenticated.

### Impact Explanation
Host applications built on top of `shopify_api` (e.g. the documented `ShopifyApp`-style handler pattern) key their tenant-specific logic — looking up the correct stored session/access token, applying data mutations, honoring GDPR/mandatory webhooks, updating shop-scoped state — off of `WebhookMetadata#shop`. Since this value is not bound to the HMAC that gates acceptance of the request, an attacker who owns a legitimate installation (and therefore a valid HMAC/body pair for their own shop's webhooks) can cause the library to hand the handler event data that is falsely attributed to a different, victim shop. This is a cross-tenant identity-confusion vector at the library layer: the gem tells the calling application "this HMAC-verified webhook belongs to shop X" when X was never actually authenticated.

### Likelihood Explanation
Exploitation requires the attacker to already be able to obtain at least one legitimately-signed `(body, hmac)` pair, which any merchant that installs the app can obtain by triggering their own store's webhooks. No secret material, session, or access token is required beyond what any unprivileged app-installing user already has. Replaying that pair to the app's public webhook endpoint with a modified `shop` header is a simple HTTP request; the header spoofing is trivial to perform.

### Recommendation
Do not treat the `shop`/`shop-domain` header as trusted merely because the request's HMAC (body-only) validates. Either:
- Include the shop domain (and ideally topic/webhook-id) in the signed material checked by `HmacValidator`, or
- Have `Registry.process`/the consuming application cross-validate `request.shop` against an independently known, trusted association (e.g. the shop that the webhook subscription was registered for, or a stored session lookup) before trusting it for any tenant-scoped action, rather than passing the raw header value straight into `WebhookMetadata`.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger `orders/create` and capture the resulting POST request body and its `x-shopify-hmac-sha256` value — both are valid because Shopify signed the body with the app's real secret.
2. Replay that exact body and HMAC value to the app's webhook endpoint, but replace the `x-shopify-shop-domain` header with `victim.myshopify.com`:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <captured-valid-hmac>
x-shopify-shop-domain: victim.myshopify.com
x-shopify-webhook-id: <any>

<captured-valid-body>
```
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds (it only checks the body), and `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"` even though `victim.myshopify.com` never sent or authorized this event.
