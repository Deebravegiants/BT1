### Title
`canGraduate`'s unchecked subtraction underflows and permanently bricks buying/graduation once curve-side rounding drifts `assetReserve` below the immutable virtual LT floor - (File: `packages/contracts/src/Bonding.sol`)

### Summary
CVE-2014-0147 describes a QEMU QCOW2 bug where a signed/rounding logic error in a refcount calculation during snapshot creation corrupts accounting and crashes the process. The analogous class here is a rounding/logic assumption baked into `Bonding`'s graduation accounting: it assumes the pair's stored `assetReserve` can never drop below the immutable launch-time `virtualLtReserve`, and performs an unchecked `uint256` subtraction on that assumption. If ordinary sell activity ever violates the assumption by even 1 wei, the subtraction underflows and reverts, and because this calculation is invoked unconditionally at the end of every buy, the whole curve becomes permanently un-tradeable.

### Finding Description
`Bonding._launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve from the pair's immutable `k`: [1](#0-0) 

`canGraduate` (called unconditionally at the end of every `Bonding.buy` via `_executeBuy`, and directly by the permissionless `triggerGraduation`) does:
```
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [2](#0-1) 

This subtraction assumes `assetReserve >= virtualLtReserve` always holds. That assumption is enforced nowhere on-chain — it is a design invariant, not a checked one. `Router._computeSell` computes the new asset reserve via floor division:
```
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [3](#0-2) 

Because `k / newReserveToken` floors down, the *resulting* stored asset reserve after the sell (`reserveAsset - assetOut = floor(k / newReserveToken)`) can be strictly less than the "fair" continuous value — i.e. it rounds in the seller's favor rather than the pool's. `Pair.swap`'s K-check only requires `(newTokenReserve+1)*(newAssetReserve+1) >= k`, an intentionally loose slack that exists precisely to tolerate this rounding without reverting: [4](#0-3) 

For a full round-trip (buy then sell back the exact same token amount) the math cancels exactly, but for a *partial* round-trip (sell back less than the outstanding bought amount, or repeated partial sells that don't land on reserve values dividing `k` evenly) the floor-division deficit lets the computed `newReserveToken`-implied asset reserve fall below the true `virtualLtReserve` floor by 1+ wei while `Pair.swap`'s slack still accepts it. `_launchTimeVirtualLtReserve`/`canGraduate` have no defensive floor or saturating-subtract guard for this case (contrast with `finalizeGraduation`'s explicit saturating-subtract comment for exactly this class of drift risk): [5](#0-4) 

Once `assetReserve` drifts to `virtualLtReserve - 1` (or lower), every future call to `canGraduate` — which is unconditional inside `_executeBuy` on **every** subsequent buy — reverts with a Solidity Panic(0x11) arithmetic-underflow, not a custom revert that could be caught/handled. `previewLtUntilGraduation` has the identical unchecked subtraction and would revert the same way: [6](#0-5) 

### Impact Explanation
Once triggered, every `Bonding.buy` (and hence every `Zap.buy`) on the affected curve permanently reverts, and `triggerGraduation` permanently reverts as well, since both paths execute the same unchecked subtraction. This permanently freezes: the real LT already raised and sitting in the `Pair` (unreachable because `Router.graduate` is only reachable from `_prepareGraduationLiquidity`, itself only reachable from `_enterGraduating`, itself gated by `canGraduate == true`, which can never again evaluate without reverting), and the 250M `LP_RESERVE` tokens parked in `Bonding` for this token, which can never be minted into a HyperSwap LP. The token can never graduate and can never receive new buys — a permanent freeze of curve and creator/trader funds for that token, satisfying the "permanent freezing of trader, creator or LP funds" bar.

### Likelihood Explanation
Any unprivileged trader who has bought curve tokens can reach this purely through the standard, permissionless `Zap.buy` → `Zap.sell` (or direct `Bonding.sell`) flow, with no special privileges, by executing a buy followed by a partial (not full round-trip) sell sized so that `Router._computeSell`'s floor-division output lands the stored `assetReserve` exactly at or below `virtualLtReserve`. This requires no admin action, no oracle manipulation, and is well within the reach of a single wallet issuing ordinary transactions. That said, I was not able to fully hand-verify with concrete numeric examples (given tool-call limits) exactly how many sell operations / what sizing is required to force the drift to land 1+ wei below the floor versus always landing at-or-above it in every case tested by the existing invariant suite; the existing fuzz/invariant tests (`test_inv_kIdentity_recoversVirtualLtReserve`, `testFuzz_inv_graduationAlwaysClean`) exercise buys and sells together but do not appear to specifically target this boundary condition with adversarially-chosen partial-sell sizes.

### Recommendation
- Add an explicit floor check or saturating subtraction in `_launchTimeVirtualLtReserve`'s callers (`canGraduate`, `previewLtUntilGraduation`, `_prepareGraduationLiquidity`): if `assetReserve <= virtualLtReserve`, treat `realLtRaised` as `0` instead of underflowing.
- Alternatively/additionally, change `Router._computeSell` to round the resulting `newReserveAsset` up (ceil) rather than floor, so sells never leave the pool's stored asset reserve below the mathematically-implied floor, matching the rounding-favors-the-pool convention already used in `_computeBuy`.
- Add a fuzz/invariant test that specifically drives many small, non-round-tripping buy/sell pairs and asserts `assetReserve >= virtualLtReserve` (equivalently, that `canGraduate` and `previewLtUntilGraduation` never revert with a Panic) across the full curve lifetime.

### Proof of Concept
Conceptual reachable path (not fully numerically verified against the deployed rounding constants — flagged above as unverified):
1. Attacker (unprivileged) calls `Zap.buy(token, usdcAmount, 0, ref)` to acquire curve tokens, raising `Pair`'s stored `assetReserve` above `virtualLtReserve`.
2. Attacker calls `Zap.sell(token, partialTokenAmount, 0)` for an amount smaller than their full holdings, sized so `Router._computeSell`'s `k / newReserveToken` floor-rounds the implied post-sell `assetReserve` to `virtualLtReserve - 1` (or lower). `Pair.swap`'s `+1` K-slack accepts this without reverting.
3. Any subsequent call that reaches `canGraduate(token)` — the very next `Bonding.buy` by anyone (via `_executeBuy`'s unconditional `canGraduate(tokenAddress)` call) or a direct `triggerGraduation(token)` call — executes `assetReserve - _launchTimeVirtualLtReserve(...)` with `assetReserve < virtualLtReserve`, reverting with Panic(0x11).
4. The curve is now permanently un-buyable and un-gradable; the raised LT in `Pair` and the 250M `LP_RESERVE` tokens in `Bonding` are permanently stranded for that token.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
