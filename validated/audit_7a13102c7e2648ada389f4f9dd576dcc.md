This confirms the asymmetry: `Auth::Oauth::AuthQuery#to_signable_string` explicitly binds `shop` into the HMAC-signed string [1](#0-0) , but `Webhooks::Request#to_signable_string` returns only `@raw_body`, leaving the `shop-domain` header completely outside the HMAC coverage [2](#0-1) , and that unauthenticated header value is exactly what `Registry.process` forwards to the app's handler as the trusted tenant identifier [3](#0-2) .

### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant identification purely from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but `HmacValidator.validate` only verifies the raw request body against the HMAC signature. The header carrying the tenant identity is never bound into the signed payload, so it can be freely altered by anyone able to submit a request to the webhook endpoint with a body+HMAC pair that was legitimately signed by Shopify for a *different* purpose or shop, breaking the equality `shop asserted by HMAC == shop attributed to the event`.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` field via `OpenSSL.secure_compare` [4](#0-3) . For webhooks, `to_signable_string` is defined as simply `@raw_body` [5](#0-4) , and the `shop` accessor reads directly and only from an HTTP header that is parsed outside that signed string:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, which is used for the OAuth callback HMAC and *does* explicitly fold `shop` into `to_signable_string` before hashing [1](#0-0) . The library's own design intent is clearly that identity fields like `shop` must be part of the signed content — this was simply omitted for webhook processing.

`Registry.process` uses this unauthenticated `shop` field directly as the tenant identity handed to the app's business logic:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

Because the HMAC only certifies the byte content of `@raw_body`, an attacker who possesses *any* validly HMAC-signed webhook body/signature pair for the app (e.g., from a shop where they themselves installed the app, since Shopify signs all webhooks for an app with the same `client_secret` regardless of shop) can resend that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will still pass because it never looks at the header, yet `WebhookMetadata#shop` — the field host applications use to select/scope the tenant record to update — will report whatever shop the attacker chose. This is the exact bug class described in the report: a field that is acted upon (here, the tenant/shop identity used by the handler) is not covered by the integrity check (the HMAC), so multiple crafted requests can produce a state divergent from what the signature was meant to guarantee.

### Impact Explanation
This breaks the binding `shop verified by HMAC == shop used by the application`, enabling cross-tenant webhook injection: an unprivileged internet user who controls one shop where the app is installed can forge a validly-signed webhook body that will be attributed by the library to any other shop's domain. Any host application that uses `WebhookMetadata#shop` (as documented and demonstrated in the library's own webhook processing flow and tests) to look up/update per-tenant records, without independently re-validating the shop, will process attacker-chosen data as if it originated from a different merchant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the app's public webhook endpoint and possession of one legitimately-signed body/HMAC pair, obtainable by installing the target app on the attacker's own shop (a normal, unprivileged action) and capturing any webhook Shopify sends. No `api_secret_key`, access token, or privileged account is required — the `client_secret` itself is never exposed, only its output (the HMAC) is reused with a mismatched header, which is fully consistent with the report's threat model of an "unprivileged internet user."

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the string that is HMAC-verified for webhooks, mirroring the pattern already used in `Auth::Oauth::AuthQuery#to_signable_string`, or otherwise cryptographically tie the header-derived shop domain to the signed body (e.g., require the shop to also appear inside the verified body/topic-specific payload) before it is passed to `WebhookMetadata`/handlers.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; capture a webhook Shopify sends, e.g. body `{}` with headers `x-shopify-hmac-sha256: <valid HMAC>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim.myshopify.com`.
3. Build the request/process it as the library does:
```ruby
request = ShopifyAPI::Webhooks::Request.new(
  raw_body: "{}",
  headers: {
    "x-shopify-topic" => "orders/create",
    "x-shopify-hmac-sha256" => captured_valid_hmac, # still valid, since it only signs "{}"
    "x-shopify-shop-domain" => "victim.myshopify.com", # spoofed, not covered by HMAC
  },
)
ShopifyAPI::Webhooks::Registry.process(request) # HmacValidator.validate(request) still returns true
```
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `request.to_signable_string` (`@raw_body`) against the HMAC — see `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`. The registered handler then receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, even though that value was never authenticated, demonstrating the cross-tenant identity spoof.
