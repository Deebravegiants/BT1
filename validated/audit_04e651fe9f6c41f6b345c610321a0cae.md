## Analog Found

### Title
Residual tokens minted to the shared `CallDispatcher` during HyperFungibleToken calldata execution are permanently unrecoverable - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable.onAccept()` mints bridged tokens to a beneficiary and then executes attacker/user-supplied calldata via the shared `CallDispatcher` contract, exactly mirroring the reported Executor.sol pattern (transfer/allow tokens to a target, then let untrusted calldata run against them). Unlike the sibling intents flow (`IntentsBase._execute`), which explicitly sweeps any balance left on the dispatcher back to the calling contract, the HyperFungibleToken flow performs no such sweep, and `CallDispatcher.sol` itself has no owner, no recovery function, and no way to move out any token it ends up holding.

### Finding Description
Per the documented usage pattern (`docs/content/developers/evm/hyper-fungible-token/hyper-fungible-token.mdx:113-162`), calldata execution on the destination chain works by setting `to` to the `CallDispatcher` address so that minted tokens land on the dispatcher, which then executes the `Call[]` array (e.g., approve + swap) using those tokens: [1](#0-0) 

The actual mint-and-dispatch logic is in `onAccept()`: [2](#0-1) 

Tokens are minted to `beneficiary` (which per the documented pattern is the `CallDispatcher` address) and `ICallDispatcher(_dispatcher).dispatch(message.data)` executes the attached calls. `CallDispatcher.dispatch()` simply loops over the calls and low-level-calls each target; it does not return or sweep any leftover balance: [3](#0-2) 

`CallDispatcher` has no owner, no withdraw/sweep function, and no state at all beyond the `dispatch` loop — there is no code path anywhere in this contract that can move a token balance back out of it.

Contrast this with the intents module's equivalent flow, `IntentsBase._execute()`, which dispatches calldata to the very same `CallDispatcher` but then explicitly reads back the dispatcher's balance for every known output token/ETH and issues sweep calls to recover it, emitting `DustCollected`: [4](#0-3) 

The HyperFungibleToken `onAccept()` path has no analogous sweep step after `dispatch(message.data)`. `WrappedHyperFungibleTokenUpgradeable.onAccept()` has the identical gap: [5](#0-4) 

Any amount of the minted tokens not fully consumed by the attached `Call[]` — due to slippage, a partial-fill swap, a malformed/adversarial call sequence, or simply a user mis-specifying `data` — remains on the `CallDispatcher` balance permanently, since `CallDispatcher` is a shared singleton used across multiple apps (HFT, WrappedHFT, and intents) and offers no owner-controlled or public sweep mechanism of its own.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any user sending a cross-chain HFT/WrappedHFT transfer with non-empty `data`. Once delivered, any unconsumed portion of the minted amount is stuck in `CallDispatcher` with zero recovery path — worse than the original Executor.sol report, where at least a policy of "anyone can claim leftover funds" was adopted; here no such claim mechanism exists at all. Because `CallDispatcher` is shared across all `IApp` implementations that use it, dust from one app's execution also sits alongside other apps' in-flight funds, compounding the risk if amounts are non-trivial (e.g., a swap that reverts partway leaving the full principal on the dispatcher, or a user routing large amounts through a swap with unfavorable slippage bounds).

### Likelihood Explanation
High. This triggers on any ordinary calldata-execution transfer where the destination call sequence does not fully spend the minted amount — no malicious relayer or adversarial governance required, just normal use of the documented composability feature (e.g. swap slippage, partial liquidity, or a poorly constructed `Call[]`).

### Recommendation
Add a sweep step to `HyperFungibleTokenUpgradeable.onAccept()` and `WrappedHyperFungibleTokenUpgradeable.onAccept()` (mirroring `IntentsBase._execute()`) that reads back the dispatcher's balance of the bridged token after `dispatch()` returns and forwards any residual to the beneficiary (or emits a `DustCollected`-style event and returns it to a claimable location). Alternatively, add a generic, permissionless sweep function to `CallDispatcher.sol` itself so any token/ETH balance it accumulates can always be recovered by the caller or beneficiary, closing the gap for all current and future callers of this shared contract.

### Proof of Concept
1. User A calls `HyperFungibleTokenUpgradeable.send()` on the source chain with `to = CALL_DISPATCHER` (destination) and `data` encoding `Call[]` = [approve(router, amount), swapExactTokensForTokens(amount, minOut, path, recipient, deadline)].
2. On delivery, `onAccept()` mints `amount` tokens to `CALL_DISPATCHER` then calls `dispatch(data)`.
3. Due to slippage/partial liquidity, the swap only consumes `amount - X` tokens (e.g., a router that pulls exactly `minOut`-bounded input via `swapTokensForExactTokens`-style logic, or a call sequence that reverts on a downstream step is not chosen at all — even a straightforward `approve` + swap leaves `amount - amountIn` if the router doesn't pull the entire allowance).
4. `X` tokens remain in `CallDispatcher`'s balance. There is no function on `CallDispatcher`, `HyperFungibleTokenUpgradeable`, or any related contract that can transfer this `X` out — it is permanently stuck.

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);

            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});

                    });
