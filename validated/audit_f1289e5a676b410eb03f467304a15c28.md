## Title
`CallDispatcher.dispatch` has no access control, letting any caller drain tokens the contract holds mid-flight for intent orders - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a fully public, unauthenticated function that executes an arbitrary `Call[]` array against any target contract, using whatever ETH/ERC20 balance the dispatcher currently holds. It is used as a shared, singleton "temporary custody" contract by `IntentGatewayV2`/`ExtrinsicIntents` for `predispatch`/`postdispatch` swap flows, meaning it routinely holds user/solver funds mid-transaction. Because `dispatch` has no caller restriction and no accounting of "whose" funds are inside it, any address can call it directly and instruct it to transfer out whatever balance it is holding at that moment to an attacker-controlled address.

### Finding Description
`CallDispatcher.dispatch` decodes an arbitrary `Call[]` and executes each call with attacker-chosen `to`, `value`, and `data`, with the only check being that `to` has code: [1](#0-0) 

There is no `onlyGateway`/`onlyHost` modifier and no restriction on `msg.sender` at all - the contract is deployed as a shared utility and its `dispatch` entrypoint is `external` with no guard. This mirrors the root cause of the referenced sherlock finding: a permissionless function that moves out the contract's *current* token/ETH balance without validating that the balance is "safe" to release (not reserved for another pending flow), analogous to `AutoRoller.claimRewards` failing to exclude the adapter's staked balance.

`CallDispatcher` is used by `IntentGatewayV2.placeOrder` / `fillOrder` and `IntentsBase._execute` as temporary custody for order funds during predispatch/postdispatch DeFi routing: [2](#0-1) [3](#0-2) 

Documentation for the sibling `HyperFungibleToken` flow confirms the same singleton dispatcher is meant to briefly hold tokens for calldata execution across bridging flows, explicitly warning users to size approvals carefully "since the dispatcher contract holds tokens temporarily during execution": [4](#0-3) 

Because the same `CallDispatcher` address is reused across all orders and all HFT calldata-execution flows (a single deployed instance per chain, per the docs' "existing CallDispatcher deployments" reference), any window in which it is holding a nonzero token/ETH balance is an attack window: an unprivileged actor can call `dispatch()` directly (bypassing `IntentGatewayV2`/`HyperFungibleToken` entirely) with a `Call[]` that transfers that balance to themselves via `IERC20.transfer`/native value forwarding, exactly as `claimRewards` allowed sweeping the AutoRoller's reserved stake balance.

Concretely, reentrancy provides a fully constructible path: `order.predispatch.call` and `order.output.call` are attacker/user-supplied calldata that is executed by `CallDispatcher.dispatch` while the dispatcher is holding escrowed input/output tokens for that in-flight order (transferred to it just prior via `safeTransferFrom(msg.sender, dispatcher, amount)`). Since the calldata dispatched can call to arbitrary contracts, a malicious `predispatch.call`/`output.call` target can reenter `CallDispatcher.dispatch` (or have `dispatch` call into a malicious contract that itself calls `dispatch`) to sweep the just-deposited balance to an address that is not `address(this)` (the gateway) before the "measure actual received"/final sweep-back-to-gateway logic runs, or ahead of a subsequent legitimate `dispatch` call in the same tx that was going to transfer inputs back to the gateway: [5](#0-4) 

### Impact Explanation
Funds temporarily custodied by `CallDispatcher` during `placeOrder`/`fillOrder` predispatch/postdispatch flows (user input tokens, solver output tokens) or during `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution deliveries can be permanently stolen by any address that races or reenters `dispatch()` while a balance is present, since there is no restriction limiting `dispatch()` callers to the gateway/token contract that deposited the funds. This is a direct theft-of-funds path (High/Critical) affecting the intents escrow and token-bridge calldata-execution flows.

### Likelihood Explanation
`dispatch()` is `external` with zero access control, so the barrier to exploitation is purely about timing a call while the dispatcher holds a nonzero balance. Since order flows explicitly route arbitrary attacker/solver-supplied calldata (`order.predispatch.call`, `order.output.call`, HFT `data` field) through this same dispatcher while it is custodying funds, a malicious calldata payload can reenter `dispatch()` within the same transaction to redirect the balance before it is swept back to the legitimate recipient - making this reliably reachable without needing to win a mempool race.

### Recommendation
Restrict `CallDispatcher.dispatch` to be callable only by an authorized caller (e.g., an `onlyAuthorized` modifier checking `msg.sender` against a registry of gateway/token contracts allowed to use this dispatcher instance, or deploy a fresh, single-use dispatcher per call/order instead of a shared singleton). Additionally, add reentrancy guards around the multi-step dispatch/sweep sequences in `IntentGatewayV2`/`IntentsBase` so that a nested `dispatch` call cannot execute mid-flow, and consider snapshotting/asserting expected balances immediately before sweeping rather than trusting `balanceOf(dispatcher)` at an arbitrary point in execution.

### Proof of Concept
1. Attacker crafts an `Order` whose `predispatch.call` targets a malicious contract `M`.
2. User/attacker calls `IntentGatewayV2.placeOrder(order, ...)`; the gateway transfers `predispatch.assets` (e.g., 1000 USDC) to the shared `CallDispatcher` and calls `CallDispatcher.dispatch(order.predispatch.call)`.
3. `dispatch` executes the call to `M`, which reenters `CallDispatcher.dispatch()` directly (an unrestricted external function) with a `Call[]` encoding `IERC20(USDC).transfer(attacker, 1000e6)`.
4. The dispatcher, currently holding the 1000 USDC deposited in step 2, transfers it to the attacker before the gateway's own follow-up `dispatch(abi.encode(transferCalls))` call (meant to sweep inputs back to the gateway) executes.
5. The gateway's subsequent balance check finds an insufficient/zero balance and the original order's flow either reverts (griefing) or, if fee-on-transfer accounting silently treats the shortfall as "received," the escrow is under-collateralized while the attacker has extracted the funds - net theft of the deposited tokens from the shared dispatcher.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```

```text
The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
