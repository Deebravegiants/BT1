### Title
Emporium relay-fee payment moves signer-wallet funds in an attacker-chosen token to an attacker-chosen relay address, bypassing the owner's EIP-712 authorization - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`verifyWallet` binds the owner's EIP-712 signature only to `(emporiumMessage, ops-hash, maxFee, deadline)` and performs a purely numeric check `feeStructure.flatFee > stack.maxFee`. It never binds `circomData.feeStructure.feeToken` or `circomData.relay` to the signature. Because these two fields are supplied by whoever submits the `transact()` call (an unprivileged prover, not the wallet signer), an attacker can drain up to `maxFee` raw units of an arbitrary, attacker-chosen ERC-20 token from the signer's wallet to an arbitrary, attacker-chosen relay address, while satisfying every on-chain check.

### Finding Description
The claimed invariant is: *(fee token, fee amount, fee recipient) taken from the signer's wallet == what the signer's EIP-712 signature actually authorized.* This is broken.

`verifyWallet` computes the signed hash from only these fields: [1](#0-0) 
and its only fee-related guard is a bare numeric comparison with no token binding: [2](#0-1) 

`feeStructure.feeToken` and `circomData.relay` are never part of `EMPORIUM_SIGNATURE_TYPEHASH`/`EMPORIUM_OPERATION_TYPEHASH`. They are, however, both hashed into `calldataHash` and thus checked against the caller's own ZK proof: [3](#0-2) [4](#0-3) 

But that integrity check only proves that `circomData` matches what the *transaction submitter* (the prover generating the proof for their own UTXOs, i.e. the attacker) committed to — it says nothing about what the *wallet signer* (`stack.signerAddress`) authorized. The signer's signature never mentions `feeToken` or `relay` at all, so the attacker is free to pick both.

When `payRelayFees` runs for a signer-bound stack (`signerAddress != address(0)`), the fee actually paid is `flatFee` (bounded only by `<= maxFee`, a bare `uint256` with no denomination semantics), sent via the wallet itself: [5](#0-4) [6](#0-5) [7](#0-6) 

`sendToRelayFromWallet` calls `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` — moving `relayFee` units of `feeToken` out of the signer's wallet to `relay`, both attacker-chosen, trusting that Emporium already validated authorization (it did not, for these two fields).

Exploit flow:
1. Owner signs an `EmporiumSignature` off-chain with `maxFee = N` (raw integer), intending the fee to be denominated in some low-value token they hold in small quantity (e.g. a stablecoin with many decimals).
2. Attacker (any unprivileged EOA who can generate their own valid ZK proof over their own UTXOs to satisfy `performHinkalChecks`/`verifyProof`) submits `Hinkal.transact` with the same `stack.ops/maxFee/deadline/signature`, but sets `circomData.feeStructure.feeToken` to a token the signer's wallet holds that has a much higher value-per-raw-unit (e.g. a low-decimal, high-price token), and sets `circomData.relay` to the attacker's own address.
3. `verifyWallet` passes because signature/`maxFee`/deadline checks only cover signed fields, and `flatFee <= maxFee` is satisfied numerically regardless of token.
4. `payRelayFees` -> `sendToRelayFromWallet` transfers `N` raw units of the attacker-chosen token from the signer's wallet to the attacker-chosen relay address — a value the owner's signature never specified or bounded in real terms, and a recipient the owner never authorized.

Existing guards do not catch this: `verifyWallet`'s signature check, deadline check and `flatFee <= maxFee` check all pass; `onlyAllowedRecipient` only restricts who can call `runAction` (an allow-listed external-action router), not the fee token/relay; the ZK proof only certifies the attacker's own proof-side commitments, not the signer's authorization of `feeToken`/`relay`.

### Impact Explanation
An attacker can move an owner-signed-wallet's assets (fee amount, denominated in an attacker-chosen token) to an attacker-chosen destination address that the owner's EIP-712 signature never specified. This is "executing calls or moving assets a wallet owner ... never authorised" — High severity per the rubric. The theft magnitude is bounded by `maxFee` raw units of whichever token the attacker selects among tokens the signer's wallet holds, and is repeatable once per signed message (bounded by `usedMessages` replay guard, but new signed stacks can be procured indefinitely if the owner keeps signing emporium ops).

### Likelihood Explanation
Preconditions: the owner must have signed a valid `EmporiumSignature` with `signerAddress != address(0)` and a nonzero `maxFee`; the attacker needs the stack/signature (obtainable if relayed or leaked, or if the attacker is the one soliciting the signature under a different pretext) and must be able to submit their own valid ZK proof for the `transact` call (attacker controls their own UTXOs/proof generation, an explicitly allowed capability). No privileged role is required. This is straightforward for anyone with access to a valid signed stack.

### Recommendation
Bind `feeStructure.feeToken` and `circomData.relay` (and ideally the exact `flatFee`/`variableRate` used, not just an upper bound) into the EIP-712 typed data that the owner signs in `verifyWallet`, e.g. extend `EMPORIUM_SIGNATURE_TYPEHASH` to include `feeToken` and `relay`, and hash them in `_hashTypedDataV4`. Alternatively, require the wallet signer to explicitly pre-approve a fixed `(feeToken, relay)` pair per signed message instead of trusting values controlled by whoever submits the transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `IHinkalWallet` funded with two ERC20 tokens (`TokenA` low value/high decimals, `TokenB` high value/low decimals), and a mock relay/attacker address.
2. Owner signs an `EmporiumStack` with `maxFee = 1000`, `ops` referring to some innocuous action, `signerAddress = wallet`.
3. Craft `CircomData` #1 with `feeStructure.feeToken = TokenA`, `relay = legitimateRelay`, generate a valid proof for it (using the same signed stack bytes in `externalActionMetadata`), call `runAction`/`transact`, and record `TokenA` balance moved out of `wallet` to `legitimateRelay` — call this `X_intended`.
4. Craft `CircomData` #2 (different `emporiumMessage` to bypass replay guard, same signed stack fields otherwise) with `feeStructure.feeToken = TokenB`, `flatFee = 1000` (same raw number, `<= maxFee`), `relay = attacker`, and a fresh proof generated by the attacker for their own UTXOs.
5. Assert `verifyWallet` does not revert (signature/maxFee/deadline checks pass) and that `1000` raw units of `TokenB` are transferred from `wallet` to `attacker` — i.e., a token and destination the owner's signature never specified, demonstrating `(fee token, fee amount, fee recipient) actually paid != what the signature bound (only a bare numeric maxFee)`.
