### Title
Cached user-QR validation result is trusted through the entire signup instead of being re-checked before enrollment, allowing a since-blocked/invalidated user to still complete a signup - (File: `src/plans/mod.rs`)

### Summary
The bug class in the WLFI report is: a per-entity `enabled`/validity flag is checked once at *assignment* time but never re-checked at the later *consumption* (claim) time, so revoking eligibility after assignment has no effect on ongoing use. The closest reachable analog in `orb-core` is the user-QR-code validation path: `backend::user_status::request` (`src/backend/user_status.rs`) is called once, at QR-scan time, to decide whether a user is allowed to proceed, and the resulting `UserData` (validity-derived struct) is then carried unchecked through the rest of the signup (`biometric_capture` → `biometric_pipeline` → `enroll_user`) without any re-validation before the privileged action (enrollment / PCP upload) is performed.

### Finding Description
`scan_user_qr_code` → `handle_user_qr_code` → `verify_user_qr_code` (`src/plans/mod.rs`, `verify_user_qr_code` at lines ~1580-1623) calls the backend once: [1](#0-0) 

The returned `backend::user_status::UserData` (containing `user_centric_signup`, encryption keys, `id_commitment`, etc.) is embedded into `QrCodes::Both` / `ResolvedQrCodes` at the moment of the QR scan: [2](#0-1) 

This cached, one-time-validated struct is then reused, unmodified and unre-verified, throughout `do_signup` — after a multi-second wait, a full biometric capture, and the full biometric pipeline — to decide the enrollment outcome: [3](#0-2) 

Notably, when `user_centric_signup` is true, the orb **skips calling the backend enrollment endpoint entirely** and just trusts the previously-fetched flag to mark the signup successful: [4](#0-3) 

Similarly, the operator/user QR validity is cached with a timestamp and reused across multiple scan loops as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, without any second server round-trip to confirm the cached validity still holds: [5](#0-4) 

This mirrors the WLFI root cause exactly: the "enabled"/valid check (`ownerSetCategoryEnabled` ≈ `user_status::request`'s `valid` flag) is enforced only at the entry point (`_activateVest`/`wlfiSetCategory` ≈ QR scan/`verify_user_qr_code`), but the actual privileged action (`_claim` ≈ enrollment/PCP upload) consumes the previously-cached state (`UserInfo.category` ≈ `UserData`) without re-checking it.

### Impact Explanation
If a user becomes ineligible between the QR-code validation step and the enrollment step (e.g., is banned, already enrolled elsewhere, has its authorization revoked by the backend), the orb has no code path to catch this: the `user_centric_signup` branch marks the signup as successful purely based on the stale cached flag, without calling the backend enrollment/verification endpoint at all. This can result in unauthorized or misattributed signups completing that the backend intended to block, and personal-custody biometric data still being generated and uploaded for a user who should have been rejected. This falls within the "unauthorized or misattributed signup" impact category the validation rules call out.

### Likelihood Explanation
The exploitation window is the normal signup duration (QR scan → 3s wait → biometric capture → biometric pipeline → enrollment), which is not attacker-controlled but is a fixed, non-trivial amount of time during which backend-side state can change. This is a design/logic gap rather than something requiring privileged access, malicious hardware, or a compromised operator — a completely unprivileged end user going through the normal flow can benefit from this staleness window. Likelihood is moderate: it depends on backend-side state changing during a live signup, but the code provides no defense-in-depth re-check regardless of how that state changes.

### Recommendation
Re-validate the user's status immediately before performing the enrollment/upload step (i.e., inside or immediately before `enroll_user`/`build_pcp`/the `user_centric_signup` success branch), rather than relying solely on the `UserData` captured at QR-scan time. At minimum, the `user_centric_signup` short-circuit in `do_signup` (`src/plans/mod.rs` lines 639-656) should perform (or force) a fresh backend call so that revocation of eligibility between QR validation and enrollment is honored, mirroring the recommended fix of enforcing the flag at the "claim" point rather than only at "assignment."

### Proof of Concept
Conceptual reproduction (network/timing dependent, not runnable purely from static code):
1. Scan a valid user QR code; `verify_user_qr_code` succeeds and returns `UserData{ user_centric_signup: true, ... }`, which is cached in `QrCodes::Both`.
2. Before biometric capture completes, have the backend revoke/block that user's status (e.g., ban, duplicate signup detected) — this is not re-queried by orb-core.
3. Continue through `do_signup`; since `user_centric_signup` is `true` and `ignore_user_centric_signups` is `false`, the code path at `src/plans/mod.rs:639-645` marks the signup successful based solely on `signup_reason == SignupReason::Normal` (from the biometric pipeline) — it never re-contacts the backend to confirm the user is still eligible, so the signup is finalized despite the revoked status.

    async fn scan_remaining_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: QrCodes,
        operator_qr_expiration_time: Duration,
    ) -> Result<Option<ResolvedQrCodes>> {
        loop {
            match qr_codes {
                QrCodes::Both { operator_data, user_qr_code, user_data, user_qr_code_string }
                    if operator_data.timestamp.elapsed() < operator_qr_expiration_time =>
                {
                    break Ok(Some(ResolvedQrCodes {
                        operator_data,
                        user_qr_code,
                        user_data,
                        user_qr_code_string,
                    }));
                }
                QrCodes::Operator { operator_data }
                    if operator_data.timestamp.elapsed() < operator_qr_expiration_time =>
                {
                    let Some((user_qr_code, user_data, user_qr_code_string)) =
                        self.scan_user_qr_code(orb, &operator_data).await?
                    else {
                        break Ok(None);
                    };
                    break Ok(Some(ResolvedQrCodes {
                        operator_data,
                        user_qr_code,
                        user_data,
                        user_qr_code_string,
                    }));
                }
                _ => {
                    let qr_capture_start = Instant::now();
                    let Some(operator_qr_code) =
                        self.scan_operator_qr_code(orb, Some(self.qr_scan_timeout)).await?
                    else {
                        break Ok(None);
                    };
                    if !check_signup_conditions(orb).await? {
                        continue;
                    }
                    let Some(operator_qr_code) =
                        self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                    else {
                        break Ok(None);
                    };
                    let Some((duration_since_shot_ms, operator_location_data)) = self
                        .verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start)
                        .await?
                    else {
                        continue;
                    };
                    // a delay following the scan allows for a better user experience & increases the chance of
                    // not reusing any previous RGB frame for the next QR-code scan
                    if let Some(delay) =
                        QR_SCAN_INTERVAL.checked_sub(Duration::from_millis(duration_since_shot_ms))
                    {
                        sleep(delay).await;
                    }
                    let operator_data = OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    };
                    let Some((user_qr_code, user_data, user_qr_code_string)) =
                        self.scan_user_qr_code(orb, &operator_data).await?
                    else {
                        break Ok(None);
                    };
                    break Ok(Some(ResolvedQrCodes {
                        operator_data,
                        user_qr_code,
                        user_data,
                        user_qr_code_string,
                    }));
                }
            }
        }
    }
