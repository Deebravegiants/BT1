Confirmed: the webhook HMAC signature is computed only over the raw request body via `to_signable_string` returning `@raw_body`, while `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are read directly from HTTP headers that are never included in the signed payload.### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," and the tenant-identifying `shop` value it extracts is handed directly to the app's `WebhookHandler` for per-shop processing. In reality, the HMAC signature only authenticates the raw request body; the `shop`, `topic`, `webhook_id`, and `api_version` values — all read from HTTP headers — are never part of the signed data. An attacker who receives one legitimate webhook for their own (attacker-controlled) shop can replay the same body/HMAC pair while substituting the `shopify-shop-domain` header for a victim shop, and the signature check still passes.

### Finding Description
`Webhooks::Registry.process` gates all processing behind a single HMAC check: [1](#0-0) 

That check delegates to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhook requests, `to_signable_string` returns only the raw body: [3](#0-2) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from unauthenticated headers, with no cryptographic binding to the body that was signed: [4](#0-3) [5](#0-4) 

These unauthenticated values are then packaged into `WebhookMetadata` and passed straight to the app's handler as trusted tenant/topic identifiers: [6](#0-5) [7](#0-6) 

The gem's own documentation instructs integrators to treat `data.shop` as the authenticated shop for tenant routing (`shop_domain: data.shop`), reinforcing that this is the gem's intended, documented contract — not an integrator misuse: [8](#0-7) [9](#0-8) 

This is the same bug class as the WormholeFacet report: a value that is acted upon (`shop`, the tenant-binding field) is not covered by the same integrity check (`HMAC`) that is claimed to authenticate the whole request. The equality that should hold — `hmac-verified-request.shop == shop that data is attributed to` — does not hold, because HMAC only binds `body == body`, not `shop-header == shop-header`.

### Impact Explanation
An attacker who legitimately controls one shop with the app installed (an unprivileged actor relative to any other tenant) can capture a genuine webhook delivery (body + `x-shopify-hmac-sha256`) sent to their own endpoint, then resend that identical body/HMAC pair while altering only the `shopify-shop-domain` (or `x-shopify-shop-domain`) header to name a different, victim shop. `Registry.process` will still accept it as valid because the signature check never inspected the shop header. The handler then executes tenant-scoped logic (e.g., persisting/data-processing keyed by `data.shop`) attributing attacker-supplied webhook content to the victim tenant — a cross-tenant data integrity/confidentiality break. This meets the "Critical – cross-tenant access" bar.

### Likelihood Explanation
Any merchant with the app installed can capture their own genuine webhook deliveries (e.g., via inspecting their own webhook endpoint logs, a reverse proxy, or simply because it is directed to infrastructure they control) without needing the app's `client_secret`, an access token, or any privileged credential. Forging the header value and resending the exact same body/signature requires no cryptography, only a basic HTTP replay with one header changed — a low-effort, realistically exploitable path.

### Recommendation
Include the shop domain (and ideally topic/webhook_id/api_version) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body, rather than trusting header values independently of the signature. At minimum, before dispatching to a handler, cross-check that the `shop` claimed in headers is consistent with data embedded/expected in the verified body, or document explicitly (and enforce) that `shop` is unauthenticated and must not be used for tenant identification without independent verification against a known session/shop registered for that webhook subscription.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `customers/data_request`), receiving real webhook deliveries with a valid `shopify-hmac-sha256` computed over the body via `Utils::HmacValidator`/`OpenSSL::HMAC.hexdigest` as seen in [10](#0-9) .
2. Attacker captures one such delivery: `raw_body` (e.g. `{}` or attacker-controlled JSON since it originates from their own shop) plus its valid `x-shopify-hmac-sha256` value.
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request object whose `shop` returns `"victim-shop.myshopify.com"` per [11](#0-10) , while `hmac` validation still succeeds because it is computed purely from `@raw_body`, per [3](#0-2) .
5. `Registry.process` accepts the forged request and invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-supplied data under the victim tenant's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
```
