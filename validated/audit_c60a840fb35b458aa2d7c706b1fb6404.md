Confirmed finding: `ShopifyAPI::Auth::TokenExchange.exchange_token` derives the target shop directly from the JWT `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling `ClientCredentials.client_credentials` and `RefreshToken` flows which do sanitize the shop before using it to build the HTTP host that receives `client_id`/`client_secret`.

### Title
Unsanitized `dest` claim used as request host in `TokenExchange.exchange_token` leaks `client_secret` to attacker-controlled host - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`TokenExchange.exchange_token` takes `jwt_payload.shop` (derived from the JWT `dest` claim, stripped of `https://` only) and uses it unsanitized as the `shop` of a `Session`, which `Clients::HttpClient` uses to build the request host for the `/admin/oauth/access_token` POST that carries the app's `client_id` and `client_secret` in the body.

### Finding Description
The binding that should hold is: **the host that receives `client_secret` == a real, verified `*.myshopify.com` (or other trusted Shopify) domain**. `ClientCredentials.client_credentials` and `RefreshToken` enforce this by calling `Utils::ShopValidator.sanitize!(shop)` before constructing the session used for the outbound request: [1](#0-0) 

`TokenExchange.exchange_token`, however, takes the shop straight from `JwtPayload#shop` (`@dest.gsub("https://", "")`) with no call to `ShopValidator`: [2](#0-1) [3](#0-2) 

`JwtPayload` validates the JWT signature (`aud == Context.api_key`) but performs no validation that `dest` is a well-formed `*.myshopify.com`/trusted domain — it only strips a literal `"https://"` prefix. Since `Session#shop` is later used directly as the request host by `Clients::HttpClient`, an unsanitized `dest` value flows straight into the outbound POST target that carries `client_id` and `client_secret`.

### Impact Explanation
If `dest` can be a value that is not a genuine Shopify-controlled host (e.g. it contains a scheme/path/host confusion that `sanitize!`'s `Addressable::URI` parsing + `TRUSTED_SHOPIFY_DOMAINS` check would normally reject, such as `https://real-shop.myshopify.com@attacker.com` or `real-shop.myshopify.com.attacker.com`), the resulting request would send the app's `client_id`/`client_secret` to `attacker.com` instead of Shopify — credential exfiltration of the app's `client_secret`, which is Critical per the impact classes in scope. Because `JwtPayload` only strips a literal string prefix and does not run the same host/domain validation as `ShopValidator`, this code path lacks the defense-in-depth that the other two OAuth grant flows (`client_credentials`, `refresh_token`) apply to the exact same kind of value before it is used to build an outbound host.

### Likelihood Explanation
The token itself must carry a valid HMAC signed with `Context.api_secret_key`, which normally only Shopify can produce — this significantly limits who can supply an attacker-chosen `dest`. Exploitability therefore hinges entirely on whether Shopify's session-token issuance can ever place a value in `dest` that is not already a strictly validated `*.myshopify.com` host (which is outside this gem's control), or whether some other component of the host application constructs/forwards a token with attacker-controlled `dest` before this gem processes it. Within the gem itself, the absence of `ShopValidator.sanitize!` on this specific path is a clear inconsistency with the parallel `client_credentials.rb` and `refresh_token.rb` flows, and is best characterized as a missing defense-in-depth check rather than a demonstrated, directly-reachable exploit purely from this gem's code with attacker-only capabilities.

### Recommendation
In `lib/shopify_api/auth/token_exchange.rb`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!(jwt_payload.shop)` (mirroring `client_credentials.rb` and `refresh_token.rb`) before constructing `shop_session` and before it is used as the target host for the access-token exchange request, so that the same trusted-domain validation applies uniformly across all OAuth grant flows in the gem.

### Proof of Concept
1. Obtain (or otherwise cause the app to receive) a session token whose `dest` claim resolves, after the `gsub("https://", "")` strip in `JwtPayload#shop`, to a host string not restricted to `TRUSTED_SHOPIFY_DOMAINS` (e.g. any value bypassing the loose string transform that `ShopValidator.sanitize_shop_domain` would otherwise reject).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient.new(session: shop_session, ...)` builds the request host directly from this unsanitized value, and the POST body containing `client_id` and `Context.api_secret_key` is sent to that host — compare against `client_credentials.rb`, where the same value would be rejected by `ShopValidator.sanitize!` raising `Errors::InvalidShopError`.
