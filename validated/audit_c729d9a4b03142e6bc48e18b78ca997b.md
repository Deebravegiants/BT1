Confirmed: `Context.api_secret_key` is a single global secret (the app's `client_secret`) used for all shops the app is installed on [1](#0-0) . This secret is the same one used to compute webhook HMACs across every tenant, so it does not itself bind a webhook to a particular shop.

### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` (the data that is actually HMAC-verified) is only the raw request body. `Registry.process` validates the HMAC and then blindly trusts these header-derived fields when constructing `WebhookMetadata` and dispatching it to the host application's handler, creating a binding gap: `hmac_verified_bytes != bytes_used_for_tenant_identification`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to that body [3](#0-2) .

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (the body) using the app's single, shop-independent `api_secret_key` [4](#0-3) .

`Registry.process` then does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [5](#0-4) 

Because the HMAC only proves "this body was signed with the app's secret" and says nothing about which shop, topic, or webhook_id the sender claims, an attacker who can obtain any one genuine `(raw_body, hmac)` pair signed with the app's secret (e.g., by triggering a real webhook to their own store, which any merchant who installs the app can do) can replay that exact body+hmac to the app's webhook endpoint while substituting arbitrary values for the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, and `X-Shopify-Api-Version` headers. The HMAC check still passes (bytes verified = body only), yet `Registry.process` forwards the attacker-chosen `shop` value to the host application's handler as if it were authenticated. This exactly matches the "bytes verified versus bytes parsed" / "shop authenticated versus the shop trusted" binding break called out in scope.

### Impact Explanation
Any application handler that uses `WebhookMetadata#shop` to key persistence, authorization, or business logic (the documented, intended use of this field) will act on data believed to belong to shop B while actually processing attacker-supplied content originally issued for shop A. This is a cross-tenant integrity/spoofing issue: an unprivileged user (merchant of their own shop A, or anyone who can capture one valid webhook delivery) can inject fabricated events attributed to a victim shop B, without ever possessing B's access token or the app's `client_secret`. This satisfies the Critical "cross-tenant access" impact category, since the gem's own webhook-processing API delivers spoofed tenant-attributed data to the host application as if verified.

### Likelihood Explanation
High likelihood: any merchant who installs the app can trivially generate at least one legitimately-signed `(body, hmac)` pair by causing Shopify to fire a real webhook to their own endpoint, then replay that body/hmac with modified headers via a simple HTTP request to the same publicly reachable webhook endpoint. No secrets, tokens, or privileged access are required — only the ability to send an HTTP request and to have triggered one real webhook event under their own tenant.

### Recommendation
Bind the shop/topic/webhook identity into the signed material, or otherwise cryptographically tie the header-derived fields to the verified payload:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or verify them against fields embedded in the JSON body itself, where Shopify includes shop information) before trusting them in `WebhookMetadata`.
- Alternatively, require and validate a per-shop secret/lookup so that a valid HMAC for shop A cannot be replayed under shop B's identity — i.e., verify that the `shop` header corresponds to the store that owns the currently-processed webhook subscription (e.g., cross-check `webhook_id` against records registered for that shop) rather than trusting the header verbatim.
- Document this binding gap to consuming apps until the library-level fix ships, since the current API implicitly presents `request.shop` as though it were authenticated.

### Proof of Concept
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`) and triggers a real webhook (e.g., creates an order), receiving from Shopify a body `B` and a valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker replays this exact request to the app's public webhook endpoint but modifies:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version` as desired
   - Body `B` and header `H` unchanged.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B` [6](#0-5) .
4. `Registry.process` finds the registered handler for the (attacker-controlled) topic and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))`, passing `shop = "victim-shop.myshopify.com"` to the host app as though it were verified [5](#0-4) .
5. The host application's webhook handler processes/stores this event under the victim's tenant, completing the cross-tenant spoof.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
