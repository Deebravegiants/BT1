### Title
Webhook Shop/Topic/Metadata Headers Are Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the shop, topic, webhook id and API version entirely from unauthenticated HTTP headers, while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the identity binding: `hmac(raw_body) == valid` is treated as proof that `shop-domain header == the shop that generated the body`, but the header is never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC over exactly that signable string and compares it to the `hmac` extracted from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from headers that are never included in the signed bytes: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and the other header-derived fields) as the tenant identity handed to the app's webhook handler, gating only on the HMAC of the body: [4](#0-3) 

Because the `shop-domain` header is not part of the signed payload, any `(raw_body, hmac)` pair that is valid for one shop remains cryptographically valid when replayed with a different `shopify-shop-domain` header value. An unprivileged actor who can obtain one legitimate webhook delivery for a shop they control (e.g., their own development/trial store, which is a normal, unprivileged capability for anyone who can install a public Shopify app) can capture that valid `(body, hmac)` pair and resend it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming an attacker-chosen shop, even though the HMAC provides no assurance about which shop the payload belongs to.

### Impact Explanation
This is a cross-tenant identity-binding failure: the equality the app relies on — "HMAC valid ⇒ `shop-domain` header is trustworthy" — does not hold, since `shop-domain` is outside the MAC's scope. Any consuming application that uses `WebhookMetadata#shop` to look up/act on a specific merchant's session, tenant record, or data (a standard and expected usage pattern for this SDK) can be made to process or store data under a spoofed shop identity using a validly-signed body captured from a different (even attacker-owned) shop. This satisfies the "cross-tenant access" impact category, since the boundary between shops that the HMAC is supposed to enforce is not actually enforced for the shop attribute.

### Likelihood Explanation
Exploitation requires only a single legitimate webhook capture from any shop (including one the attacker owns, which is trivial and unprivileged to obtain by installing the app on a test store) and the ability to POST to the app's public webhook endpoint with a modified header — no access token, `client_secret`, or privileged account is needed. The gem itself provides no additional binding (e.g., no re-derivation of `shop` from signed data) to prevent this.

### Recommendation
Do not treat header-derived fields (`shop`, `topic`, `webhook_id`, `api_version`) as authenticated unless they are cryptographically bound to the signature. At minimum, the gem should document clearly that only the raw body is HMAC-verified and that host applications must independently validate/expect the shop domain (e.g., cross-check against a known/registered shop for the topic, or require TLS-terminated, Shopify-only network paths). Longer term, incorporate the shop/topic/webhook metadata into the signable string wherever the underlying Shopify webhook delivery mechanism allows for it, or provide an API that returns a shop value only after confirming it against a source of truth (e.g., a previously registered webhook_id ↔ shop mapping) rather than trusting the header verbatim.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — both are valid for the app's real `api_secret_key`.
2. Attacker replays this exact `(raw_body, hmac)` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the spoofed shop header successfully (headers are only checked for presence, not authenticity). [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `raw_body`. [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the payload actually originating from the attacker's own shop, allowing the host application's downstream logic (tenant lookup, data writes, etc.) to be misattributed to the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
