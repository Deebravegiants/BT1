Confirmed: `CatFeeConfig` at `tesseract/messaging/tron/src/catfee.rs:44-54` derives `Debug` and holds `api_key`/`api_secret` as plain `String` fields with no redaction, and `TronClient::new` logs the whole struct with the `{:#?}` debug formatter.

### Title
CatFee API key/secret written in cleartext to relayer logs via `{:#?}` debug formatting - (File: tesseract/messaging/tron/src/lib.rs)

### Summary
`TronClient::new` logs the entire `CatFeeConfig` struct — including `api_key` and `api_secret` — at `info` level whenever a TRON chain is configured with CatFee bandwidth-purchasing credentials, persisting the secret HMAC key material in the relayer's log output/files.

### Finding Description
`CatFeeConfig` derives `Debug` with no custom/redacted implementation: [1](#0-0) 

`TronClient::new` initializes this config from `catfee_api_key`/`catfee_api_secret` and immediately logs it with `{:#?}`, which invokes the derived `Debug` and prints every field, including the raw secret used to compute HMAC-SHA256 request signatures: [2](#0-1) 

This is the same bug class as CVE-2019-3500: a credential that authenticates a service call (there, HTTP Basic Auth; here, a CatFee HMAC API secret) is written verbatim into a log stream/file, where anything with read access to that log (local file access, shipped log aggregation, support-bundle collection, etc.) can recover it. Contrast this with how the relayer's own signer keys and other operator secrets are elsewhere carefully masked before ever reaching a persisted config/log — e.g. `maskToml`/`maskSecret` for filler-config secrets in the SDK filler package — showing the project treats "never print secrets" as an established invariant that this code path violates.

### Impact Explanation
Once the CatFee `api_secret` is exposed via logs, anyone with access to the relayer's log output can forge valid `CF-ACCESS-SIGN` HMAC signatures and impersonate the operator's CatFee account. Because CatFee is used to purchase TRON bandwidth/energy that funds the relayer's outbound message submission on TRON, this can result in:
- Theft/drain of funds tied to the CatFee account (unauthorized energy/bandwidth purchases billed to the operator).
- Denial of the CatFee-funded energy path, causing the TRON leg of the relayer to fall back to paying full TRX fees or fail to submit messages (a degraded/blocked delivery route), affecting message delivery reliability for the TRON destination chain.

This is a High-severity confidentiality/availability issue for the TRON messaging relayer component but does not directly compromise the on-chain ISMP host, consensus, or a bridge user's escrowed funds — the blast radius is scoped to the relayer operator's CatFee account and TRON-leg message delivery.

### Likelihood Explanation
Any operator who configures `catfee_api_key`/`catfee_api_secret` in `TronConfig` to enable bandwidth purchasing will unconditionally trigger this log line at every `TronClient::new` (i.e., every process start/reconnect), with no feature flag or conditional guard to suppress it. Exposure requires only that something reads the relayer's log stream (local log files, shipped stdout/stderr to a log aggregator, container logs, crash reports), which is a common and realistic access vector for an operationally-deployed relayer.

### Recommendation
- Remove the derived `Debug` for `CatFeeConfig` (or implement a manual `Debug` that redacts `api_key`/`api_secret`, similar to the `maskSecret`/`maskToml` pattern already used for the filler config's signer secrets).
- Change the log statements in `TronClient::new` to log only non-sensitive fields (e.g. `api_base`, `timeout`) instead of the full config via `{:#?}`.
- Audit other `log::info!`/`log::debug!("{:#?}", config)`-style calls across the `tesseract/*` clients for similar secret-bearing structs (e.g., signer/API configs) to ensure none of them are Debug-printed wholesale.

### Proof of Concept
1. Configure a TRON chain block with `catfee_api_key = "<key>"` and `catfee_api_secret = "<secret>"`.
2. Start the tesseract TRON messaging relayer; `TronClient::new` executes: [3](#0-2) 
3. Inspect the process's log output (stdout, log file, or any log aggregation sink the operator forwards logs to) — the line `"CatFee integration enabled: <api_key: "...", api_secret: "...", ...>"` contains the cleartext secret.
4. Use the recovered `api_secret` to compute a valid `Base64(HMAC-SHA256(secret, timestamp + method + requestPath))` signature per the documented scheme and issue authenticated CatFee API calls as the victim operator: [4](#0-3)

	/// Generate HMAC signature for API request
	///
	/// Signature format: Base64(HMAC-SHA256(secret, timestamp + method + requestPath))
	/// where requestPath includes query parameters
	fn generate_signature(&self, timestamp: &str, method: &str, request_path: &str) -> String {
		let message = format!("{}{}{}", timestamp, method, request_path);

		let mut mac = HmacSha256::new_from_slice(self.config.api_secret.as_bytes())
			.expect("HMAC can take key of any size");
		mac.update(message.as_bytes());

		BASE64.encode(mac.finalize().into_bytes())
	}
