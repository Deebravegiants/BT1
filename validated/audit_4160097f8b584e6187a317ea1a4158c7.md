### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body. The `shop` field, which is passed downstream to the handler as the tenant identifier for the payload, is read from an HTTP header that is never included in the signed bytes. Any party who can obtain one legitimately-signed `(body, hmac)` pair — trivially available to any merchant/attacker who installs the app on their own store — can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the app to process the payload as if it belonged to a different (victim) tenant.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines the signable content as only the raw body: [1](#0-0) 

The `shop` accessor is derived purely from an unauthenticated header and is never mixed into `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e., only the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately forwards `request.shop` — unauthenticated — as the tenant identity into the handler's `WebhookMetadata`: [4](#0-3) [5](#0-4) 

Because `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any shop owner can trigger a real event in their own store, capture the resulting legitimately-signed `(raw_body, hmac)` pair from Shopify, and then POST that same body and HMAC header to the app's public webhook endpoint while setting `X-Shopify-Shop-Domain` to a different, victim shop's domain. `HmacValidator.validate` will succeed (the body/HMAC pair is valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

This breaks the identity binding: `shop header verified == shop header consumed by the handler` does not hold, because the header is never part of what "verified" actually checks. The equality that should hold — `authenticated_shop == shop_acted_on` — fails, since only the body content is authenticated, not the shop attribution.

### Impact Explanation
An app that keys tenant-scoped operations (e.g., writing customer data, marking orders processed, deleting data on `shop/redact`, updating per-shop settings) off `WebhookMetadata#shop` can be manipulated into applying a legitimately-signed payload from an attacker's own shop against a different, arbitrary shop identifier. This is a cross-tenant data integrity/confusion issue: an unprivileged internet user who can merely install the app for free on a shop they control gains a mechanism to make the app misattribute data to any shop of their choosing, without needing the app's `api_secret_key`, an access token, or any privileged account.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop (an ordinary, unprivileged action available to anyone), (2) triggering an event that fires a subscribed webhook topic under attacker's own store, (3) capturing the raw body and `X-Shopify-Hmac-Sha256` header Shopify sends, and (4) replaying that exact body/HMAC pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No secrets, TLS interception, or social engineering are needed, and the webhook endpoint is by design a publicly reachable HTTP route.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise verify it out-of-band, before trusting it for tenant attribution:
- Include the `shop-domain` header (and/or `webhook-id`, `api-version`) in the signable string used for the body HMAC check, if the app controls the signing scheme, or
- Cross-check that the `shop-domain` header matches a known/expected shop for which this app currently holds an active session/webhook registration before dispatching to the handler, or
- Document explicitly that `WebhookMetadata#shop` is not covered by the HMAC and must be independently re-validated by every consumer of `Registry.process` against their own stored shop/session records before being used for any tenant-scoped write.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and subscribes to any HTTP webhook topic (e.g., `orders/create`).
2. Attacker triggers the event in their own store; Shopify POSTs to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`, plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the identical `B` and `H` to the same public endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `hmac_validator.rb` recomputes `HMAC-SHA256(api_secret_key, B)` and it still equals `H`, so validation passes.
5. `Registry.process` (`registry.rb:188-200`) builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim-shop.myshopify.com"` and invokes the handler, which now acts on attacker-supplied data under the victim shop's identity.
