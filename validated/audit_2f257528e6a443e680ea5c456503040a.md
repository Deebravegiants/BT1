Based on the investigation, I found a legitimate structural analog to the reported bug class ("no domain/chain separation, enabling cross-chain replay") in the production signing path.

### Title
Missing chainId enforcement for unrecognized EVM asset names allows cross-chain transaction replay via Ledger signing - (File: `features/hw-ledger/src/module/assets/ethereum.ts`)

### Summary
The Ledger hardware-wallet signing handler for EVM assets hardcodes the `chainId` only for three explicitly-known `assetName` values (`ethereum`, `matic`, `basemainnet`). Any other EVM-family asset name falls through the `switch` with no `default` case, leaving whatever `chainId` was already present in the caller-supplied `signableTransaction` untouched and unvalidated before it is signed by the hardware device.

### Finding Description
In `signTransaction`, the raw transaction bytes are deserialized and then a `switch (params.assetName)` block force-overwrites `deserializedTransaction.chainId` for the three hardcoded cases, explicitly commented `// No default` [1](#0-0) . For any EVM asset not in that list (e.g. new/renamed EVM chains added to the assets catalog, or any caller passing a mismatched `assetName`), the code trusts the `chainId` embedded in the already-serialized transaction bytes rather than deriving/asserting it from the asset being signed for. This is structurally the same defect class as the reported "ChainID should not be 1" issue: absence of an enforced, unique, per-network binding between what the wallet believes it is operating on and what gets embedded in the signed payload, which is exactly the condition EIP-155 chainId separation exists to prevent.

### Impact Explanation
If the `signableTransaction` bytes passed into this handler (built upstream from a dApp-originated `unsignedTx` or a bridged asset request) carry a `chainId` for a different network than the one the user is shown/approves on the Ledger device screen (e.g. mainnet `1`), the device will produce a validly-signed transaction that can be broadcast and replayed on that other chain (e.g. Ethereum mainnet) without the wallet software re-checking consistency. This is a direct unauthorized-signing / cross-chain replay condition originating from the wallet's own signing code, not from a malicious node or peer.

### Likelihood Explanation
Reachability requires a caller (feature module, extension asset config, or future EVM asset addition) to invoke Ledger `signTransaction` with an `assetName` outside the three hardcoded cases, or a signable transaction whose embedded chainId doesn't match the target asset. Given the codebase is actively adding EVM-compatible chains (the switch already had to add `basemainnet` after `ethereum`/`matic`), the fallthrough is a real, recurring integration hazard rather than a purely theoretical one, though it needs a new/misconfigured EVM asset entry point to trigger — it is not exploitable by an external attacker without such an upstream trigger.

### Recommendation
Replace the exhaustive-looking `switch`/no-default pattern with an explicit chainId lookup keyed by asset metadata (the same source used to render address/derivation info), and throw/assert if the asset is unrecognized rather than silently falling through. The device-embedded chainId should always be authoritatively set by the wallet based on the known asset network — never trusted verbatim from caller-supplied transaction bytes — mirroring the fix recommended in the original report (make chain identity explicit and unique, never rely on implicit/default values).

### Proof of Concept
1. Add or misconfigure an EVM-compatible asset (e.g. a new L2) whose `assetName` is not one of `'ethereum' | 'matic' | 'basemainnet'`.
2. Construct a `signableTransaction` (RLP-encoded, EIP-155 or EIP-1559) with `chainId: 1` embedded, but pass `assetName` for the new/misconfigured asset.
3. Call the Ledger asset handler's `signTransaction({ assetName: '<new-asset>', signableTransaction, derivationPaths })` [2](#0-1) .
4. Because the `switch` has no matching case, `deserializedTransaction.chainId` remains `1` as supplied, and the resulting signature is valid for replay on Ethereum mainnet even though the user believed they were signing for the new asset's network.
