### Title
Consensus-incentives `on_executed` attributes rewards for an entire `handle_unsigned` batch's state-machine updates to whichever signature happens to sit on message 0, letting any relayer steal reward that belongs to a different consensus proof's submitter - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-ismp::handle_unsigned` accepts an arbitrary `Vec<Message>` from any unprivileged caller and executes them all in one batch [1](#0-0) . When the batch finishes, `FeeHandler::on_executed` is invoked with the full list of executed messages and the full list of emitted ISMP events for the batch. `pallet-consensus-incentives`'s implementation recovers the relayer identity *only* from `messages[0]`'s signature, then pays out the reward for **every** `StateMachineUpdated` event produced anywhere in the batch to that single recovered signer [2](#0-1) . This is the same bug class as CVE-2024-45337: a value used to authorize a state-changing effect (which relayer gets paid) is not proven to be the value that actually produced that effect. Here, the `signer` field on a `ConsensusMessage` is a self-reported, unauthenticated attribution field (it is never checked for proof validity — proof verification is independent of `signer`), and only the first such field in a caller-controlled batch is trusted for the *entire* batch's rewards.

### Finding Description
`ConsensusMessage::signer` is documented purely as attribution metadata, not an authentication credential: `update_client`/consensus proof verification never checks it, only the embedded consensus proof is verified [3](#0-2) . `handle_unsigned` is a permissionless (`ensure_none`) call, so anyone can submit a batch of arbitrary `Message`s — including multiple independent `Message::Consensus` entries, each with its own, mutually-inconsistent `signer` field — as long as each entry's proof independently verifies against the trusted consensus state [4](#0-3) .

In `pallet-consensus-incentives::on_executed`:
- The relayer account is derived once, from `messages.get(0)` only: `Signature::decode(&mut &consensus_msg.signer[..])...verify_and_get_sr25519_pubkey(...)` [5](#0-4) .
- If that recovery succeeds, the code then scans *all* `IsmpEvent::StateMachineUpdated` events across the whole batch — which can be produced by any of the other, unrelated consensus messages in the same call — and pays a reward for each state machine's advance to the single recovered account [6](#0-5) .

Because BEEFY/GRANDPA/sync-committee/etc. consensus proofs are public artifacts (once produced or broadcast, anyone can resubmit the raw bytes — proof validity depends only on cryptographic properties of the source chain's finality, not on who submits it), an attacker can:
1. Take any legitimate, currently-valid consensus proof for chain B that a genuine relayer is about to submit (or has submitted and is still valid/replayable in this batch context), and
2. Wrap it as message index 1..N in their own `handle_unsigned` call, with their *own* trivial/cheap self-authored consensus message (any state machine, even one with `block_cost = 0` so `process_message` short-circuits cheaply) placed at index 0 carrying their own `signer`.

The pallet then attributes rewards for **every** `StateMachineUpdated` event in the batch — including the one produced by the "borrowed" proof for chain B — to the attacker's account recovered from message 0, since only that single signer field gates the whole loop.

### Impact Explanation
This directly causes theft of relayer-incentive treasury funds: `process_message` transfers `T::Currency::transfer` from the treasury account to the (attacker-controlled) `relayer_account` for each state machine's block-cost reward, and additionally mints reputation tokens via `T::ReputationAsset::mint_into` [7](#0-6) . An attacker can repeatedly harvest rewards intended for whoever actually produces/submits each chain's consensus update, by bundling any publicly-observable valid proof alongside a single cheap self-signed message. This is a Medium/High severity fund-diversion issue reachable from a single permissionless `handle_unsigned` extrinsic — no privileged role required.

### Likelihood Explanation
High likelihood of exploitability given the trigger requires nothing beyond assembling a batch: `handle_unsigned` is explicitly permissionless (`ensure_none`) and designed to accept relayer-submitted `Vec<Message>` batches. Consensus proofs are inherently public once observable (unlike a private key), so an attacker only needs to watch the mempool/relay-chain finality stream and race or piggyback a second valid consensus message into their own batch. The bug is not a mocked/test-only condition — it's the production `FeeHandler::on_executed` wired into `pallet-ismp`'s message-execution pipeline.

### Recommendation
Do not attribute a batch's rewards to a single globally-recovered signer. Instead:
- Correlate each `StateMachineUpdated` event to the specific `Message::Consensus` entry (and its own verified `signer`) that produced it, and pay/mint only against that message's own recovered signer.
- Reject batches whose consensus messages carry inconsistent/multiple distinct signers if a single-attribution model is intentional, or process per-message attribution explicitly instead of `messages.get(0)`.
- Consider treating `signer` as untrusted input for anything beyond best-effort UX and gating actual reward payment on stronger binding (e.g., requiring the consensus message's signer to match the extrinsic's actual submitter when that information is available, or restructuring `handle_unsigned` to disallow mixing consensus messages with unrelated signers in one batch for reward purposes).

### Proof of Concept
1. Attacker (relayer key `R_attacker`) monitors the network and observes any valid, still-verifiable `ConsensusMessage` proof `P_honest` (with proof bytes for e.g. Ethereum sync-committee update, whose real submitter is `R_honest`) that has not yet advanced the consensus client height (or is otherwise independently re-verifiable/valid against current trusted state).
2. Attacker crafts a `handle_unsigned` call with `messages = [M0, M1]` where:
   - `M0 = Message::Consensus(ConsensusMessage { consensus_proof: <cheap self-authored valid proof, e.g., for a low-cost/zero-cost state machine>, consensus_state_id: ..., signer: <Signature::Sr25519 over keccak256(M0.consensus_proof) signed by R_attacker> })`
   - `M1 = Message::Consensus(ConsensusMessage { consensus_proof: P_honest, consensus_state_id: <chain B>, signer: <anything, e.g. garbage or R_honest's leaked/observed signature bytes — irrelevant since only M0 is checked> })`
3. `Pallet::execute` verifies each message's proof independently and succeeds for both, emitting `StateMachineUpdated` for M0's chain (possibly reward=0 if `block_cost`=0) and for chain B (from `P_honest`).
4. `consensus-incentives::on_executed` runs: `messages.get(0)` is `M0`, its `signer` decodes and recovers `R_attacker`'s sr25519 pubkey successfully.
5. The pallet then iterates *all* `StateMachineUpdated` events, including chain B's, and calls `process_message(..., relayer_account = R_attacker)` for chain B too — paying `R_attacker` the block-cost reward and minting reputation for chain B's advance, even though `R_attacker` did not produce/sign `P_honest`.
6. `R_honest`, who actually crafted/would have submitted `P_honest`, receives nothing for that update once the attacker's batch lands first (idempotency via `LastRewardedHeight` prevents double payment, so the legitimate submitter's later, correctly-attributed submission is a no-op reward).

Note: I was not able to execute this end-to-end in a live test harness within this session; the PoC is derived directly from reading the reachable code paths (`handle_unsigned` → `Pallet::execute` → `FeeHandler::on_executed`) and their documented semantics. I recommend a Devin session to write a concrete `pallet_consensus_incentives` unit test (mirroring existing tests like `skip_incentivizing_of_relayer_when_cost_per_block_is_not_set`) that submits a two-message batch with mismatched signers/state machines and asserts the reward/mint goes to the wrong account, to fully confirm exploitability against the current test harness.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	fn on_executed(
		messages: Vec<MessageWithWeight>,
		events: Vec<IsmpEvent>,
	) -> DispatchResultWithPostInfo {
		let maybe_relayer_account = messages.get(0).and_then(|first_message| {
			if let Message::Consensus(consensus_msg) = &first_message.message {
				let data = sp_io::hashing::keccak_256(&consensus_msg.consensus_proof);
				Signature::decode(&mut &consensus_msg.signer[..])
					.ok()
					.and_then(|sig| sig.verify_and_get_sr25519_pubkey(&data, None).ok())
					.map(|pub_key| pub_key.into())
			} else {
				None::<[u8; 32]>
			}
		});

		if let Some(relayer_account) = maybe_relayer_account {
			// When a batch contains multiple `StateMachineUpdated` events for the
			// same `state_machine_id` (sequential consensus updates for the same
			// chain), `calculate_reward` reads the same persisted
			// `(latest_commitment_height, previous_commitment_height)` pair on
			// every iteration and pays the same block-span reward N times.
			// Collapse the per-state-machine event stream to the single highest
			// `latest_height` so each state machine receives one reward per
			// batch, sized by the actual span of its commitment advance.
			let mut highest_per_state_machine: BTreeMap<StateMachineId, u64> = BTreeMap::new();
			for event in events {
				if let IsmpEvent::StateMachineUpdated(update) = event {
					highest_per_state_machine
						.entry(update.state_machine_id)
						.and_modify(|h| {
							if update.latest_height > *h {
								*h = update.latest_height;
							}
						})
						.or_insert(update.latest_height);
				}
			}

			for (state_machine_id, latest_height) in highest_per_state_machine {
				let state_machine_height =
					StateMachineHeight { id: state_machine_id.clone(), height: latest_height };

				let _ = Self::process_message(
					state_machine_height,
					state_machine_id,
					relayer_account.clone().into(),
				);
			}
		}
