### Title
Missing Lower-Bound / Fee-vs-Amount Validation in `IntentsSDK.createWithdrawalIntents()` — (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents()` computes the actual withdrawal amount as `amount - feeEstimation.amount` whenever `feeInclusive: true`, but — unlike its sibling method `_estimateWithdrawalFee()` — it never checks that `amount` is actually greater than `feeEstimation.amount` before performing the subtraction.

### Finding Description
In `packages/intents-sdk/src/sdk.ts`, `_estimateWithdrawalFee()` explicitly guards against a fee that meets or exceeds the requested amount: [1](#0-0) 

However, the public `createWithdrawalIntents()` entry point performs the identical `feeInclusive` subtraction with **no equivalent check**: [2](#0-1) 

If a caller invokes `createWithdrawalIntents()` with a `withdrawalParams.amount` that is less than or equal to `feeEstimation.amount` (e.g., because the fee changed since it was last quoted, or was supplied out-of-band), `actualAmount` becomes `0n` or a negative `bigint`. This value is passed unchecked into `bridge.validateWithdrawal()` and `bridge.createWithdrawalIntents()`.

For the `IntentsBridge` route (`RouteEnum.InternalTransfer`, the first bridge checked in the bridge list), `validateWithdrawal()` performs **no amount validation whatsoever** — it only validates the destination address: [3](#0-2) 

`createWithdrawalIntents()` for this bridge then directly serializes the unchecked amount into a signed `transfer` intent: [4](#0-3) 

This mirrors the Craft Commerce bug class exactly: a user/caller-influenced amount field (here, the withdrawal amount relative to its fee) is used to construct a transfer instruction without first validating that the resulting net amount is strictly positive.

### Impact Explanation
A zero (or negative, which would be rejected downstream but still indicates the missing guard) net-transfer amount can be built and signed as a valid `transfer` intent via the SDK's supported public API, bypassing the exact protective check (`FeeExceedsAmountError`) that exists for the equivalent `estimateWithdrawalFee` path. This breaks the equality "amount debited must be amount minus fee, and must be > 0," letting a zero-value withdrawal/transfer intent be produced and published as if it were a valid funded transfer.

### Likelihood Explanation
This is reachable by any integrator/caller of the public SDK who calls `createWithdrawalIntents()` directly with a `feeEstimation` whose `amount` is stale or attacker-influenced relative to the requested withdrawal `amount`, without first passing through `estimateWithdrawalFee()`'s guard. No privileged access or malicious relayer/RPC behavior is required — only that the two public methods are not required to be called in lockstep.

### Recommendation
Add the same `amount <= feeEstimation.amount` guard (throwing `FeeExceedsAmountError`) inside `createWithdrawalIntents()` in `packages/intents-sdk/src/sdk.ts`, mirroring the check already present in `_estimateWithdrawalFee()`, before computing `actualAmount`. Additionally, consider adding an explicit `actualAmount > 0n` assertion inside `IntentsBridge.validateWithdrawal()` so the internal-transfer path does not rely solely on the caller performing this check upstream.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents({ withdrawalParams: { assetId, amount: 100n, destinationAddress, feeInclusive: true, routeConfig: internalTransferRoute }, feeEstimation: { amount: 100n, ... } })`.
2. `actualAmount = 100n - 100n = 0n`.
3. `IntentsBridge.validateWithdrawal()` only checks the destination address and returns successfully.
4. `IntentsBridge.createWithdrawalIntents()` returns a signed `transfer` intent with `tokens: { [assetId]: "0" }`, which the caller can proceed to sign and publish — a zero-amount transfer intent created without any explicit rejection, unlike the equivalent code path in `estimateWithdrawalFee`.
