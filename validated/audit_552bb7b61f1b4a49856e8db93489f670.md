### Title
Webhook `shop-domain` header is trusted for tenant dispatch but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (tenant identity) is read from a separate, unsigned HTTP header. `Registry.process` verifies the HMAC and then dispatches to the handler using that unauthenticated `shop` value, breaking the binding `authenticated_shop == shop_acted_on`.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is what the HMAC actually authenticates. For webhooks, `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed bytes at all: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately uses `request.shop` to build the metadata passed to the app's handler, without re-deriving or cross-checking the shop from any authenticated source: [3](#0-2) 

Because the signature covers `@raw_body` only, `OpenSSL.secure_compare(computed_signature, received_signature)` in `HmacValidator.validate_signature` will succeed for *any* combination of headers as long as the body bytes and HMAC match: [4](#0-3) 

This is the same bug class as the report: a field that is acted upon (here, the tenant/shop identity used for dispatch and downstream data attribution) is not covered by the cryptographic check that is supposed to authenticate the message (here, the HMAC). The check answers "is `raw_body` intact" but the code treats it as "is this entire webhook (including which shop it's from) authentic."

### Impact Explanation
If an unprivileged actor who controls or has visibility into one shop's webhook deliveries (e.g., their own installed test/dev shop, or any traffic they can capture/replay to the app's public webhook endpoint) resends a captured `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain, the gem's own validation (`HmacValidator.validate`) will still pass — because the header is outside the signed content. `Registry.process` then hands the handler a `WebhookMetadata` claiming the payload is from the victim shop: [5](#0-4) 

Depending on how the host app uses `data.shop` (e.g., looking up the merchant record, writing data keyed by shop, or triggering shop-scoped side effects), this enables cross-tenant data confusion/injection under a verified-looking (HMAC "valid") webhook — the app believes the request is authenticated for shop B when the cryptographic guarantee only ever covered "this body was signed with my secret," not "this body came labeled with the correct shop." This matches the Critical bucket ("cross-tenant access") criterion in scope, since the gem's own webhook authenticity primitive is what's being relied upon and it silently omits the tenant-identifying field from its guarantee.

### Likelihood Explanation
Medium-to-low, bounded by the requirement that the attacker have at least one legitimately-obtained `(raw_body, hmac)` pair from *some* shop (e.g., their own store, which they fully control and can generate arbitrary webhook payloads for by triggering ordinary shop events) and knowledge of a target shop domain to substitute. No knowledge of `api_secret_key` is needed — the attacker replays a real, previously-valid signature and only forges the unsigned header. This requires no privileged account, no TLS interception, and no host-app misuse beyond consuming `data.shop` as documented by the gem (`WebhookMetadata#shop`, which is explicitly exposed to handlers as the tenant identity).

### Recommendation
Include the shop domain (and topic/webhook id) in the signed/verified material, or independently verify that the `shop-domain` header corresponds to a shop your app has installed/expects for that specific HMAC, before trusting `request.shop` for dispatch. At minimum, document that `shop`, `topic`, and other headers are unauthenticated and must be independently validated by the host application against known installed shops before use, since currently `Request#to_signable_string` gives the false impression that the whole request is what's being verified.

### Proof of Concept
1. Attacker owns/operates their own Shopify dev shop (`attacker-shop.myshopify.com`) that has the app installed, and triggers a normal webhook event, capturing the resulting `(raw_body, X-Shopify-Hmac-Sha256)` pair sent to the app's public webhook endpoint.
2. Attacker (or anyone who can reach the app's public webhook endpoint) replays that exact `raw_body` and `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (i.e., `@raw_body` only) and finds it matches — validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though the payload/signature never had any cryptographic tie to that shop: [5](#0-4) 
5. Any handler logic that trusts `data.shop` for record lookup/creation/attribution now operates on the wrong tenant using attacker-supplied body content that passed HMAC verification.
