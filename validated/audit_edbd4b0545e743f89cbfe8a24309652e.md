## Analog Found

### Title
Vault token-account donation manipulates live reserve balances used for LP-mint/withdraw and swap math - ([File: program/src/processor.rs])

### Summary
Raydium's swap, deposit, and withdraw instructions compute the pool's economic state (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`) directly from the *live* SPL token balances of `amm_coin_vault` / `amm_pc_vault`, fetched via `unpack_token_account` on every instruction call, rather than from an internally-tracked accounting value. [1](#0-0) [2](#0-1)  Because these are ordinary SPL token accounts, anyone can permissionlessly increase their balance with a plain `spl_token::transfer` (no cooperation from the pool authority is required), exactly like donating DAI directly to a cToken contract in the Notional report to inflate its externally-observed exchange rate. [3](#0-2) 

### Finding Description
`Deposit` computes the LP tokens to mint from the *live* vault balances:
```
let (mut total_pc_without_take_pnl, mut total_coin_without_take_pnl) =
    Calculator::calc_total_without_take_pnl_no_orderbook(
        amm_pc_vault.amount, amm_coin_vault.amount, &amm)?;
...
let invariant_coin = InvariantPool { token_input: deduct_coin_amount, token_total: total_coin_without_take_pnl };
mint_lp_amount = invariant_coin.exchange_token_to_pool(amm.lp_amount, RoundDirection::Floor)...
``` [4](#0-3) 

`amm_coin_vault.amount` and `amm_pc_vault.amount` are read straight from the token account state (`Self::unpack_token_account`), not from a program-controlled counter. [5](#0-4)  Any account (including a passive observer with no relationship to the pool) can call the plain SPL Token `Transfer` instruction to send tokens directly into `amm_coin_vault` or `amm_pc_vault`; this requires no pool-side authorization since the vault is only the *destination* of the transfer. [3](#0-2) 

An attacker can compose a single transaction that (1) transfers extra coin/pc tokens directly into the vault (donation) and (2) invokes `Deposit` in the same atomic transaction. This inflates `total_coin_without_take_pnl`/`total_pc_without_take_pnl` used for `mint_lp_amount = deduct_amount / total_amount * amm.lp_amount` (Floor-rounded). [6](#0-5)  This is the same root cause class as the Notional bug: an externally-controllable token balance is trusted as the pricing input to a share-mint calculation, and the attacker can inflate it atomically before the affected operation executes. Because the attacker already holds (or immediately re-acquires via the same tx) a proportional share of LP tokens, they can later `Withdraw` and recapture the donated value plus the diluted share that should have gone to a legitimate depositor executed in the same/adjacent transaction, exactly mirroring the "donate then extract for more" pattern from the Notional report. [7](#0-6) 

The same live-balance read pattern is used identically for `swap_base_in`/`swap_base_out` (and their `_v2` variants), meaning a donation immediately prior to a swap also perturbs the constant-product invariant computed from `amm_coin_vault.amount`/`amm_pc_vault.amount` rather than from accounting state that only changes via authorized transfers. [8](#0-7) 

### Impact Explanation
This allows an attacker to dilute the LP-token share minted to a legitimate depositor for a given contribution, effectively transferring part of the depositor's contributed value to existing LP holders (including the attacker, if they hold LP tokens or immediately acquire them). This is most severe on newly created/low-liquidity pools (immediately after `Initialize2`, before broad LP distribution), matching the "low liquidity" precondition emphasized as valid-Medium in the source report. It is a real accounting-integrity issue: pool share price becomes manipulable by a single-transaction, permissionless token transfer.

### Likelihood Explanation
Requires only a standard SPL Token `Transfer` CPI plus normal `Deposit`/`Swap` instructions composed in one attacker-controlled transaction with attacker-chosen accounts and amounts — no privileged signer, no off-chain component, and no reliance on validator or Solana runtime behavior. Feasibility scales inversely with pool liquidity, consistent with the original report's caveat.

### Recommendation
Track pool reserves via program-internal state updated only through authorized CPIs (deposit/withdraw/swap transfers), rather than re-reading the raw SPL token account balance on every instruction; or reconcile/reject unexpected vault balance deltas (compare expected vs. observed balance before/after each instruction) before using them in mint/withdraw/swap math.

### Proof of Concept
1. Attacker creates (or targets) a freshly initialized, low-liquidity Raydium pool where they hold a majority of LP tokens.
2. In a single transaction: (a) `spl_token::transfer` a large amount of coin tokens directly to `amm_coin_vault`; (b) submit a `Deposit` transaction from a victim (or sandwich a pending victim `Deposit`) which computes `mint_lp_amount` off the now-inflated `total_coin_without_take_pnl`, producing fewer LP tokens for the victim's contributed tokens than fair value. [4](#0-3) 
3. Attacker calls `Withdraw` with their pre-existing LP tokens; the withdrawal amount is computed as `coin_amount = lp_share * total_coin_without_take_pnl / amm.lp_amount`, which now includes a pro-rata portion of both the donated tokens and the victim's under-compensated deposit. [7](#0-6)
