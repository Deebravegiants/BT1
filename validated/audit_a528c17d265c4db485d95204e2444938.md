### Title
Permissionless `execute` / `execute_self` can front-run `cancel` of a ready timelock operation - (File: contracts/governance/src/timelock/lifecycle.rs)

### Summary
The governance timelock lets any address execute an operation the moment its delay elapses (`executor: None` skips the executor-role check), while cancellation requires a `CANCELLER_ROLE` transaction to be authorized and mined. Once an operation reaches `OperationState::Ready`, a cancellation transaction broadcast by a canceller can be overtaken — or simply land after — a permissionless `execute` call, which clears the operation's scheduled state and makes the pending `cancel` fail permanently. This is the same cancel-vs-finalize race described in the report, mapped onto `Governance::cancel` vs `Governance::execute`/`execute_self`/`execute_canceller_reset`.

### Finding Description
`Governance::execute` accepts `executor: Option<Address>`; when `None`, `prepare_execute` performs no executor authorization, so any unprivileged address can drive a ready operation to completion ( [1](#0-0) ). The same applies to `execute_self` ( [2](#0-1) ) and `execute_canceller_reset` ( [3](#0-2) ). On success, `execute_operation`/`finish_execute` clear the scheduled state ( [4](#0-3) ), so a concurrently-broadcast `cancel` then fails in `cancel_operation` because the operation is no longer pending ( [5](#0-4) ).

The canceller's protections inside `cancel` — refusing to cancel recovery ops or a role-revocation targeting the canceller — do not help here: the race window is between "op becomes ready" and "canceller's transaction lands", during which literally anyone (including the keeper service that schedules executions of ready ops) can execute. Effective cancel authority therefore ends at the ready boundary, not at the delay tier's intended protective window plus any reaction time.

### Impact Explanation
If a scheduled operation becomes harmful after it was proposed — e.g., a `ConfigureAssetOracle`, `SetPriceAggregator`, `ApproveBlendPool`, `SetSwapAggregator`, `SetAccumulator`, or `TransferCtrlOwnership` that was reasonable at proposal time but dangerous after market conditions change or a dependency is found malicious — the canceller set loses the ability to stop it once the delay elapses. A watcher (public mempool/ledger observers, or the protocol's own keeper executing ready ops) submits `execute`/`execute_self` with `executor: None`; it lands before or instead of the canceller's `cancel`, and the harmful op executes. Depending on the op this enables theft of user funds (oracle/aggregator redirection enabling mispriced liquidations or borrowed-fund extraction) or permanent loss of control (`TransferCtrlOwnership`, `MigrateController`). Medium severity: it requires a ready op that governance wants cancelled, but removes the only defense available at that point.

### Likelihood Explanation
Low-to-moderate. It needs an operation that is both ready and unwanted, plus someone willing to execute it — but the second condition is nearly guaranteed: execution is permissionless, gas-paid by the executor, and a keeper service exists to execute ready ops automatically, so even benign automation will beat a racing `cancel` with no attacker needed.

### Recommendation
Treat the ready boundary as the end of cancellable authority and document that `cancel` cannot reliably beat a permissionless `execute` — or, if cancellation-through-ready is intended, restrict `executor: None` execution to leave a grace window, or add a canceller-authorized "veto" that blocks execution while a cancel is pending. Short of code changes, runbooks should require cancellers to act before `get_operation_ledger`, not after.

### Proof of Concept
1. Owner proposes `AdminOperation::SetPriceAggregator(evil_addr)` via `Governance::propose` before `evil_addr` is known-bad; operation id `op_id` scheduled with its delay tier.
2. `evil_addr` is revealed malicious after `op_id` becomes `OperationState::Ready` (ledger ≥ `get_operation_ledger(op_id)`).
3. Canceller `C` broadcasts `Governance::cancel(C, op_id)`.
4. Any unprivileged address (or the keeper) submits `Governance::execute(env, None, target, fn, args, predecessor, salt)` for the same operation in the same ledger; `prepare_execute` performs no auth for `executor: None` and `execute_operation` clears `op_id`'s scheduled state.
5. `C`'s `cancel` lands after and fails — `cancel_operation` reverts because `op_id` is no longer pending. The aggregator swap executes, enabling mispriced borrows/liquidations.

Relevant code:
- `contracts/governance/src/api.rs` — `execute`/`execute_self`/`execute_canceller_reset` accept `executor: Option<Address>` with no check when `None`.

```rust
pub(crate) fn cancel(env: &Env, canceller: &Address, operation_id: &BytesN<32>) {
    renew_instance(env);
    canceller.require_auth();
    access_control::ensure_role(env, &Symbol::new(env, CANCELLER_ROLE), canceller);
    assert_with_error!(
        env,
        !storage::is_recovery_op(env, operation_id),
        GenericError::OperationNotCancellable
    );
    if let Some(target) = storage::role_revocation_target(env, operation_id) {
        assert_with_error!(
            env,
            &target != canceller,
            GenericError::OperationNotCancellable
        );
    }
    cancel_operation(env, operation_id);
    storage::clear_operation_sidecars(env, operation_id);
```
