### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing shop-domain spoofing on a validly-signed webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` value that the library hands to the app's webhook handler — and that the app is documented to use as the tenant identifier — comes from an HTTP header that is never included in the signed bytes. This breaks the intended binding `hmac-signed bytes == the request's claimed tenant`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) 
The `hmac` accessor reads the `hmac-sha256` header, `shop` reads the `shop-domain` header, but `to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Registry.process` verifies the request using exactly this signable string: [3](#0-2) 
`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header — i.e. it authenticates the body bytes only, never the `topic`, `shop-domain`, `webhook-id` or `api-version` headers: [4](#0-3) 

The `shop` field is then propagated, unverified, straight into `WebhookMetadata` and passed to the host app's handler as the tenant identifier, exactly as documented ("`shop`, `String` - The shop domain of the webhook"): [5](#0-4) 

Because none of the identifying headers are part of the signed payload, the following equality the library implicitly promises to the host app is false:
`HMAC-verified(raw_body) == HMAC-verified(shop-domain header used for tenant routing)`

Any unprivileged actor who can obtain one genuine `(raw_body, hmac)` pair for any topic (e.g. by installing the same app on their own free/trial store and receiving one real webhook delivery for it) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting a different `shop-domain` header value. `Utils::HmacValidator.validate` will still return `true`, because it only ever re-hashes `@raw_body`. The library then reports the attacker-chosen `shop` value as authentic to the handler.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an app relying on `WebhookMetadata#shop` (as documented) to select which merchant record to update/create will process an event under the wrong (victim) shop's identity, based on a header that was never cryptographically bound to the signed content. This is a cross-tenant identity-binding break attributable to the gem's own webhook verification design, matching the "field acted on but not covered by the HMAC" analog class.

### Likelihood Explanation
Requires only the ability to install the app on an attacker-controlled store (unprivileged, standard Shopify developer/merchant action) to obtain one legitimately signed webhook body, plus the ability to POST a replayed body with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed body before exposing `WebhookMetadata#shop` to handlers, so that `Utils::HmacValidator.validate` fails whenever any of these headers are altered relative to the originally signed delivery.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same `H`, but header `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares to `H` — this succeeds because `to_signable_string` only ever returns `B`. [3](#0-2) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host app to process the attacker's payload under the victim shop's identity.
