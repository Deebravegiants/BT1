### Title
Unguarded `assetReserve - virtualLtReserve` subtraction in `canGraduate` can underflow and permanently freeze a bonding curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` (and its sibling `previewLtUntilGraduation`) compute the real LT raised by a curve as `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` [1](#0-0) . This is an unguarded `uint256` subtraction: if `assetReserve` (the pair's stored LT reserve) ever drops to or below the recovered launch-time virtual LT reserve, the subtraction underflows and reverts under Solidity 0.8 checked arithmetic. Because `canGraduate` is invoked unconditionally on **every** `Bonding.buy` and `Bonding.sell` [2](#0-1) [3](#0-2) , a single underflowing state permanently reverts every subsequent buy and sell on that curve — the reachable analog of CVE-2024-55627's unguarded-subtraction-causing-crash bug class, but here it's a smart-contract DoS/freeze instead of a memory-safety crash.

### Finding Description
`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT seed as `Pair.k() / Token.TOTAL_SUPPLY()` [4](#0-3) , a constant fixed at `Pair.mint` time. `canGraduate` subtracts this constant from the pair's **live stored** `assetReserve`:

```
(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [5](#0-4) 

`assetReserve` starts exactly equal to the virtual reserve at launch and is expected to only grow net-positive because every launched token undergoes a mandatory seed buy. However, `Router._computeSell`'s rounding is asymmetric versus `Router._computeBuy`'s rounding:

- Buy: `tokensOut = reserveToken - (k / newReserveAsset)` — `k/newReserveAsset` floors, so `tokensOut` is rounded **down** relative to the true curve value (protocol favored).
- Sell: `assetOut = reserveAsset - (k / newReserveToken)` — `k/newReserveToken` also floors, but here flooring the subtrahend means `assetOut` is rounded **up** relative to the true curve value (seller favored). [6](#0-5) [7](#0-6) 

Repeated buy→sell round trips by an unprivileged trader (using `Bonding.buy`/`Bonding.sell`, or `Zap.buy`/`Zap.sell` which route to the same internal `Router` calls) each leak a small amount of real LT out of the pair in the seller's favor due to this rounding asymmetry, while `Pair.k()` (and therefore the recovered virtual reserve) never changes. Enough iterations can, in principle, drive the pair's stored `assetReserve` down to (or below) the fixed virtual-reserve floor. The moment that happens, `canGraduate`'s subtraction underflows and reverts.

Because `canGraduate(tokenAddress)` is called at the tail of every `Bonding.buy` (via `_executeBuy`) [8](#0-7)  and at the top of every `Bonding.sell` [9](#0-8) , once the underflow condition is reached the curve becomes permanently un-tradeable: every future `Zap.buy` and `Zap.sell` for that token reverts, and the token can never reach the USD/supply graduation triggers either (since `previewLtUntilGraduation`, used by `Zap._executeBuy` to size mints, hits the exact same unguarded subtraction at line 722) [10](#0-9) . Holders' tokens and any LT sitting in the pair become permanently stuck on the curve with no path to sell, buy, or graduate.

This contrasts with the sibling supply-leg guard the codebase already added for a related donation-attack underflow in the same function (`if (realBalance >= reserveToken) return ltUntilThreshold;`, added per the `test/Zap.t.sol` "Donation attack regression" comments) [11](#0-10) [12](#0-11)  — the USD-leg subtraction (`assetReserve - virtualLtReserve`) at line 692/722 has no equivalent saturating/guarded form.

### Impact Explanation
If reachable, this permanently freezes the affected bonding curve: no further buys, sells, or graduation can occur, trapping any tokens or LT value held by traders and the creator on that curve indefinitely (no admin recovery path exists for `Bonding.buy`/`sell`/`canGraduate`, unlike `finalizeGraduation`'s explicit saturating-subtract safety net at line 1020 [13](#0-12) , which was clearly added as defense-in-depth for exactly this underflow class but was not applied to `canGraduate`/`previewLtUntilGraduation`). This is a concrete permanent freezing of trader/creator funds, matching the accepted impact classes.

### Likelihood Explanation
The magnitude of per-round-trip rounding leakage is at most a few wei of LT per sell, so triggering the underflow purely through organic rounding drift over the life of a single curve would require an extremely large number of round trips relative to the fixed virtual reserve (which is sized in `VIRTUAL_LIQUIDITY_USD` terms, typically thousands of USD worth of LT). This makes likelihood **low-to-uncertain** without further quantitative verification (e.g., fuzzing the exact bound between `Pair.swap`'s `+1` K slack, floor-division rounding in `_computeSell`, and the fixed virtual reserve size) — I was not able to run the test suite or a fuzzer to confirm a concretely exploitable number of transactions/gas cost. The finding should be treated as a **root-cause code asymmetry** (missing guard that the codebase's own test suite and AGENTS.md acknowledge is necessary for the sibling supply leg) rather than a confirmed cheap exploit; a background engineering session with test/fuzzing tooling is needed to bound the exact number of round trips (and their gas/fee cost) required to reach the underflow, which determines whether this is practically Medium or only theoretical.

### Recommendation
Mirror the guard already present for the supply leg (`realBalance >= reserveToken`) onto the USD leg: in both `canGraduate` and `previewLtUntilGraduation`, replace the raw subtraction with a saturating form, e.g. `assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0`, so the USD trigger degrades gracefully to `0`/"not yet graduatable" instead of underflowing and DoS-ing the entire curve. Additionally, audit `Router._computeSell` and `_computeBuy` rounding directions for any other rounding asymmetry that could allow the same reserve-draining rounding attack, and consider adding an invariant test that repeatedly round-trips buy/sell on a single curve to assert `assetReserve` never dips below the recovered virtual reserve.

### Proof of Concept
Conceptual sequence (unprivileged trader, reachable via `Zap.buy` / `Zap.sell`):
1. Launch a token normally (mandatory seed buy sets `assetReserve = virtualLtReserve + seedLT`).
2. Repeatedly call `Zap.buy(token, smallUsdc, 0, ref)` then `Zap.sell(token, tokensJustBought, 0)` in a loop. Each iteration's `_computeSell` rounds `assetOut` up in the seller's favor relative to the true curve value, incrementally reducing `assetReserve` toward `virtualLtReserve`.
3. Once `assetReserve <= virtualLtReserve`, the next `Zap.buy` or `Zap.sell` call hits `canGraduate`'s `assetReserve - _launchTimeVirtualLtReserve(...)` subtraction (`Bonding.sol:692`), which reverts with a Panic (arithmetic underflow), freezing the curve for all future callers.

I was unable to execute Foundry tests to empirically measure the number of round trips required to reach step 3 (no terminal/test-execution access in this mode); this should be validated with `forge test`/fuzzing against `Router._computeSell`/`_computeBuy` and `Bonding.canGraduate` before treating the exploit cost as confirmed.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
