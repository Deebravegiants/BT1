## Title
Vault node-side gateway handler logs the full JSON-RPC request — including the caller-supplied JWT `Auth` bearer token — to the node log at Debug level - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire incoming `jsonrpc.Request[json.RawMessage]` struct via `reqLggr.Debugw("received message from gateway", "req", req)` before any authorization check runs. That request type carries an `Auth` field which is the JWT bearer token used to authorize unprivileged workflow-owner requests, as confirmed by its use throughout `core/capabilities/vault/authorizer.go` (`req.Auth == ""`, `req.Auth != ""` checks). No redaction is applied, unlike the gateway-side vault handler which explicitly tests that raw sensitive fields never leak into logs.

## Finding Description
In [1](#0-0) , `HandleGatewayMessage` calls `reqLggr.Debugw("received message from gateway", "req", req)` immediately upon receipt, prior to calling `h.requestProcessor.ProcessRequest` (which performs authorization). The `req` argument is a pointer to the full `jsonrpc.Request[json.RawMessage]` struct, and zap's structured `Debugw` will serialize/reflect the entire value including any exported fields, not just `ID`/`Method`.

The `Auth` field on this struct is confirmed to carry the caller's JWT token: [2](#0-1)  shows `authorizeRequest` branching on `req.Auth == ""` to decide between allowlist-based and JWT-based authorization, and multiple log statements in the same file explicitly check `req.Auth != ""` as a boolean flag (deliberately avoiding logging the raw value) — e.g. [3](#0-2) . This shows the authorizer code is aware that `req.Auth` is sensitive and takes care to only log a boolean presence flag (`hasAuth`), never the raw value — but `gw_handler.go`'s `Debugw("received message from gateway", "req", req)` bypasses this care entirely by logging the whole struct wholesale.

By contrast, the gateway-side vault handler explicitly tests that no sensitive/raw field ever appears in any log entry: [4](#0-3) , and that test's own comment notes "Observed at Info level so the pre-existing whole-request Debug log is excluded" [5](#0-4)  — an explicit acknowledgment in the codebase that a whole-request Debug log exists and is known to carry sensitive content, but is deliberately excluded from the leak-detection test rather than fixed.

No existing authorization, redaction, or masking logic runs before this log line executes in `gw_handler.go`; the analogous protection pattern from the gateway-side handler is not mirrored on the node side.

## Impact Explanation
When Debug-level logging is enabled for the `VaultHandler` logger, every incoming Vault gateway request that carries a JWT `Auth` token is written verbatim to node logs. This falls under CWE-522 (Insufficiently Protected Credentials): anyone with read access to node log output (log aggregation, shared debug dumps, support/ops tooling) can harvest live JWT tokens and replay them to impersonate the legitimate workflow owner against the Vault capability — an unauthorized-action/impersonation impact consistent with in-scope categories such as gateway request impersonation and key/secret exfiltration-adjacent risk.

## Likelihood Explanation
The log statement executes unconditionally for every gateway message handled by the node's Vault handler, gated only by the logger's configured level (Debug), which is a normal operational/troubleshooting setting rather than a security control. Any unprivileged client that can submit a JWT-authorized Vault gateway request (e.g., `MethodSecretsCreate`) triggers the exposure with no special conditions.

## Recommendation
Redact or omit the `Auth` field before logging the request in `HandleGatewayMessage`, e.g., log only `req.ID`, `req.Method`, and `gatewayID` (as `requestLogger` already does via `.With(...)`), or construct a scrubbed copy of `req` with `Auth` cleared before passing it to `Debugw`. Apply the same treatment to the `"Sent message to gateway", "resp", response` log line if the response type can also carry sensitive fields. Consider extending the existing leak-detection test pattern (`TestVaultHandler_InvalidParamsDoesNotLogRawParams`) to cover the node-side `gw_handler.go` Debug log as well, rather than excluding it.

## Proof of Concept
1. Configure a Vault-capable node with Debug log level enabled for the `VaultHandler` logger component.
2. As an unprivileged workflow owner, send a JWT-authorized Vault gateway request (e.g., `MethodSecretsCreate`) with `Authorization: Bearer <token>` set, following the flow in `system-tests/tests/smoke/cre/vault_don_test_helpers.go` (`sendVaultJWTRequestToGatewayExpectError`).
3. Inspect the node's log output for the `"received message from gateway"` entry emitted at `core/capabilities/vault/gw_handler.go:182` — the JWT token supplied in `req.Auth` appears in the serialized `"req"` field in cleartext, prior to any authorization decision.
4. As a Go unit test, add assertions to `core/capabilities/vault/gw_handler_test.go` similar to `TestVaultHandler_InvalidParamsDoesNotLogRawParams`: capture a `zaptest`/`observer` log at Debug level, send a request with a known marker in `Auth`, and assert the marker does not appear in any log field — this test would currently fail against the existing code.
