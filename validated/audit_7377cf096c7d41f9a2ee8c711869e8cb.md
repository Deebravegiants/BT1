## Title
Missing per-relayer authorization gate in the Tron `IntentGatewayV2.onAccept` allows any relayer to trigger escrow withdrawal, deployment registration and dust-sweep actions that the EVM sibling restricts to a single authorised relayer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The EVM `ExtrinsicIntents` implementation of `IntentGatewayV2` (used on standard EVM chains) requires that `onAccept`/`onGetResponse` deliveries come only from a single, admin-set relayer address before any body byte is decoded (`_checkRelayer`, evm/src/apps/intentsv2/ExtrinsicIntents.sol:75-78, documented in `sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md`). The Tron variant of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, has no equivalent `_relayer`/`_checkRelayer` mechanism at all. Its `onAccept` (line 629) only checks `onlyHost` and, for governance-only actions, that `request.source` equals the Hyperbridge nexus; it never checks *who delivered* the message (the `incoming.relayer` field). This reproduces the OpenClaw bug class exactly: a lower-trust caller (any relayer who can produce a valid consensus/state proof through `HandlerV2`) can perform actions that the sibling implementation gates behind a stronger, cross-provider requester authorization check.

### Finding Description
`onAccept` in `evm/tron/contracts/apps/IntentGatewayV2.sol:629-683` dispatches on `RequestKind`:
- `RedeemEscrow`/`RefundEscrow` → calls `authenticate(incoming.request)` (which only checks `request.from` equals the registered gateway `instance(request.source)`) then `withdraw(...)`, moving escrowed tokens/fees to a beneficiary.
- `NewDeployment`/`UpdateParams`/`SweepDust` → checks only that `request.source` equals Hyperbridge's nexus state machine.

None of these branches ever inspects `incoming.relayer`. Compare with the EVM `ExtrinsicIntents._checkRelayer` (evm/src/apps/intentsv2/ExtrinsicIntents.sol:69-78), which the project's own decision log (`sdk/packages/core/docs/ai/changelog/2026-09-03-relayer-allowlist-on-the-intent-gateway.md`) states was added specifically so that "escrow redemptions, refunds and every governance action... are covered" by a single authorised-relayer check performed before the message body is decoded. The Tron contract was never updated with this hardening.

Because `HandlerV2.handlePostRequests`/`handleGetResponses` (evm/src/core/HandlerV2.sol:181-247) let *any* address submit a message once the MMR/state-commitment proof verifies, and `EvmHost.dispatchIncoming` (evm/src/core/EvmHost.sol:794-818) forwards whatever `relayer` address the caller (i.e. `_msgSender()`) happens to be, the Tron gateway's `onAccept` effectively accepts and executes escrow withdrawals, dust sweeps, and gateway-instance/parameter updates from *any* relayer that races to deliver a legitimately-proven cross-chain message, rather than only the operator-designated relayer required on EVM chains. This is precisely the "authorization bypass... allows lower-trust callers to perform actions requiring stronger authorization checks" class described in the OpenClaw advisory, mapped onto Hyperbridge's relayer-delivery model.

### Impact Explanation
An unprivileged but proof-capable relayer can front-run or race the designated/authorised relayer to deliver `RedeemEscrow`/`RefundEscrow` messages to the Tron gateway, releasing escrowed user funds to whatever beneficiary is encoded in the already-signed order — this is a lower severity than direct theft since the beneficiary is fixed by the order, but it removes the relayer-allowlist protection intentionally added elsewhere in the codebase, and any race/MEV-style delivery-order manipulation (e.g., extracting relayer fee, or delivering a stale/duplicate governance-relevant request first) is possible where on EVM chains it is blocked. It also means `NewDeployment` (which sets `_instances[stateMachineId] = gateway`, i.e. which remote gateway is trusted for that chain) and `UpdateParams` (protocol fee configuration) can be delivered by any relayer with a valid Hyperbridge-source proof rather than the specific authorised relayer, widening the operational trust surface and undermining the "single authorised relayer" invariant the rest of the gateway family enforces.

### Likelihood Explanation
High likelihood of being exploitable in practice: relaying is permissionless by design (any address can call `HandlerV2.handlePostRequests`/`handleGetResponses` with a valid proof), so the missing `_checkRelayer` gate is reachable by any actor monitoring the mempool/relayer network for Tron-bound intents messages — no privileged access or governance compromise is required, only observing an in-flight, provable cross-chain message and submitting it first.

### Recommendation
Port the `_relayer`/`_checkRelayer` gate (and `setRelayer`) from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and invoke `_checkRelayer(incoming.relayer)` at the top of `onAccept` and `onGetResponse` before any request body is decoded, matching the EVM implementation's ordering and semantics (zero address leaves the gate open until armed by governance/migration).

### Proof of Concept
1. A user creates a cross-chain order whose destination/source touches the Tron `IntentGatewayV2` deployment; a legitimate `RedeemEscrow`/`RefundEscrow` (or `NewDeployment`/`UpdateParams`) `PostRequest` is dispatched from the source chain/Hyperbridge with a valid state/consensus proof.
2. Any third party (not the operator-designated relayer) observes the pending, provable message and calls `HandlerV2.handlePostRequests` on the Tron chain, becoming `_msgSender()`/`relayer` in `EvmHost.dispatchIncoming`.
3. `EvmHost.dispatchIncoming` calls `IntentGatewayV2.onAccept(IncomingPostRequest(request, relayer))`; since `onAccept` never checks `incoming.relayer` against any allowlist (unlike `ExtrinsicIntents._checkRelayer`), the withdrawal/governance action executes successfully for the arbitrary caller.
4. This contrasts directly with the EVM `ExtrinsicIntents` deployment, where the identical delivery from a non-authorised relayer reverts with `Unauthorized` before the body is even read (as shown by the flow note `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md` and exercised by `testRejectedDeliveryStaysRetryableThroughHost`), confirming the Tron variant is missing the control.
