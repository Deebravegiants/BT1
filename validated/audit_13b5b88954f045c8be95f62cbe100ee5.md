## Analysis

The bug class here — an unbounded/uncapped external call in a loop consuming disproportionate gas (per EIP-150's 63/64 forwarding rule) and starving downstream operations of gas — has a direct analog in Hyperbridge's `HandlerV2.handlePostRequests` / `handleGetResponses` and `EvmHost.dispatchIncoming`.

### Root cause

`HandlerV2.handlePostRequests` iterates over a batch of proven requests and, for each one, makes a **raw, un-guarded external call** to `host.dispatchIncoming(...)`:

```solidity
for (uint256 i; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [1](#0-0) 

The same pattern exists in `handleGetResponses`: [2](#0-1) 

`EvmHost.dispatchIncoming` itself forwards essentially all remaining gas (no explicit gas cap) to the arbitrary destination module via a low-level `.call`, and only gracefully catches failure of *that inner* call by deleting the receipt:

```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
if (!success) {
    delete _requestReceipts[commitment];
    return;
}
``` [3](#0-2) 

The same construction exists for GET responses: [4](#0-3) 

Critically, the **outer** call from `HandlerV2` to `host.dispatchIncoming(...)` is *not* wrapped in try/catch. Since Solidity forwards up to 63/64 of remaining gas on every unqualified external call (EIP-150), a malicious destination `to` address registered as an ISMP app can burn nearly all gas forwarded into its `onAccept`/`onGetResponse` callback. Because `dispatchIncoming`'s inner low-level `.call` absorbs that failure internally, the call to `dispatchIncoming` itself doesn't revert from the module's OOG — but it exits having consumed the majority of the gas budget for that iteration. Across successive loop iterations in the same batch, remaining gas shrinks geometrically by 63/64 per malicious request, exactly matching the arithmetic in the original report ((1/64)^n). Once remaining gas becomes too small to complete a subsequent iteration's bookkeeping (receipt checks, hashing, SSTORE, or even the `CALL` opcode's own stipend requirement), that outer, un-guarded `host.dispatchIncoming` call itself throws out-of-gas — and since there is no try/catch at that call site, this **reverts the entire `handlePostRequests`/`handleGetResponses` transaction**, discarding all state changes (receipts, events) for every other — otherwise legitimate — request bundled in that same relayer batch.

### Title
Gas-griefing destination module in a batched `handlePostRequests`/`handleGetResponses` call can revert the whole batch, blocking delivery of co-batched legitimate requests - (File: evm/src/core/HandlerV2.sol)

### Summary
`HandlerV2.handlePostRequests` and `handleGetResponses` loop over a batch of proven cross-chain requests/responses and call `host.dispatchIncoming(...)` for each, with no try/catch and no gas cap. `EvmHost.dispatchIncoming` forwards up to 63/64 of remaining gas to an arbitrary, attacker-controlled destination `IApp.onAccept`/`onGetResponse` implementation. An attacker who is the destination of one of their own dispatched requests can deploy a module that intentionally consumes all forwarded gas. When this malicious request is processed in a batch alongside legitimate requests, gas depletes geometrically across loop iterations; once the remaining gas is insufficient to complete a later iteration, the un-guarded call to `host.dispatchIncoming` throws out-of-gas and reverts the *entire* batch transaction, rolling back delivery of the other, unrelated legitimate requests in that batch.

### Finding Description
`dispatchIncoming` writes the request receipt and then makes a low-level `.call` to the destination with unrestricted forwarded gas [5](#0-4) . This inner call's failure (including OOG) is caught locally and handled by deleting the receipt so it can be retried — this part is safe in isolation. The vulnerability is at the batch-loop call site in `HandlerV2`, where `host.dispatchIncoming(...)` is invoked directly, without a try/catch and without any gas stipend limit, once per request in the batch [1](#0-0) . Per EIP-150, each unqualified external `CALL` forwards up to 63/64 of the caller's remaining gas. A malicious destination module can consume nearly all of that forwarded gas in `onAccept`, leaving only ~1/64 of the pre-call gas for the rest of `HandlerV2`'s loop. Repeating this across several batched requests (even unintentionally, if several requests happen to route to gas-heavy modules) causes gas to shrink exponentially, eventually making a later loop iteration's own external call to `dispatchIncoming` fail with out-of-gas. Because this call is unguarded, the OOG exception propagates and reverts the whole `handlePostRequests`/`handleGetResponses` transaction — discarding the receipts and `PostRequestHandled`/successful delivery of every other request bundled in that same batch, even ones that had already succeeded earlier in the loop.

### Impact Explanation
This allows an unprivileged actor (anyone who can dispatch a POST request to a destination they control, or register a malicious `IApp` module) to grief relayers and block delivery of otherwise-valid, unrelated cross-chain messages that get batched together with the malicious one. Because relayers batch pending requests for gas efficiency, an attacker can repeatedly poison batches so that legitimate requests never successfully deliver in the same transaction as the malicious one, forcing relayers into a denial-of-service loop unless they can reliably identify and exclude the malicious request from every future batch — effectively "a route unable to deliver messages" for the affected destination/batch composition.

### Likelihood Explanation
Likelihood is moderate-to-high: dispatching a POST request to a self-controlled malicious destination contract is fully permissionless and requires no special privileges, only the cost of the source-chain dispatch fee. The attack only requires the malicious request to land in the same relayer-submitted batch as target requests, which is a normal, expected relayer behavior (batching improves throughput/gas costs), making this readily triggerable by a motivated griefer without needing to compromise relayer infrastructure.

### Recommendation
Wrap the per-item `host.dispatchIncoming(...)` calls inside the `handlePostRequests`/`handleGetResponses` loops in explicit gas-capped calls (e.g., `dispatchIncoming{gas: X}(...)`) combined with a try/catch, so a single malicious/gas-heavy destination module cannot starve or revert processing of the rest of the batch. Alternatively, catch failures of the outer `dispatchIncoming` call (including out-of-gas) per iteration so a single bad request can only fail its own delivery, without aborting or rolling back the other requests already processed in the same batch.

### Proof of Concept
1. Attacker deploys `EvilApp` implementing `IApp.onAccept` that spins in a gas-consuming loop until it nearly exhausts all forwarded gas (e.g., repeated `SSTORE`s or a loop bound by `gasleft()`), then returns normally (does not revert), so it still burns the gas via useful/useless work rather than reverting.
2. Attacker dispatches a POST request from a source chain with `to = EvilApp` and gets it proven/committed via the normal ISMP request flow.
3. A relayer bundles this request into a `PostRequestMessage.requests[]` array together with several legitimate pending requests and calls `HandlerV2.handlePostRequests(host, message)` [6](#0-5) .
4. During the loop, `host.dispatchIncoming` for the `EvilApp` request forwards ~63/64 of remaining gas to `EvilApp.onAccept`, which consumes nearly all of it.
5. Subsequent loop iterations (for legitimate requests) have geometrically less gas; the loop's un-guarded `host.dispatchIncoming` call for one of the remaining requests fails with out-of-gas.
6. Since this call is not wrapped in try/catch, the OOG exception propagates and reverts the entire `handlePostRequests` transaction, undoing delivery of all previously-processed legitimate requests in that batch and forcing the relayer to resubmit — repeating the same failure if the malicious request remains in the retry batch.

    function handlePostRequests(IHost host, PostRequestMessage calldata request) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(request.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 requestsLen = request.requests.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](requestsLen);

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // check destination
            if (!leaf.request.dest.equals(host.host())) revert InvalidMessageDestination();
            // check time-out
            if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.request.hash());
        }

        bytes32 root = host.stateMachineCommitment(request.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, request.proof.multiproof, leaves, request.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < requestsLen; ++i) {
            PostRequestLeaf memory leaf = request.requests[i];
            // duplicate request?
            if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.request, _msgSender());
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
