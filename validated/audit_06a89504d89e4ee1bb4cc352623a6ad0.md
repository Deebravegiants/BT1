### Title
Emporium victim's off-chain EIP-712 signature never binds `circomData.stealthAddressStructure`, letting any prover redirect the resulting shielded UTXO to themselves - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet` recovers `stack.signerAddress` from an EIP-712 signature that only commits to `emporiumMessage`, the hash of `stack.ops`, `maxFee`, and `deadline`. It never includes `circomData.stealthAddressStructure`, `erc20TokenAddresses`, or `amountChanges`. `handleOut` then mints the resulting UTXO directly to `circomData.stealthAddressStructure`, a field fully controlled by whoever submits the `transact()` call and generates the ZK proof, not by `stack.signerAddress`. Anyone who obtains a validly-signed `EmporiumStack` can resubmit it with their own `stealthAddressStructure` and steal the value the signed ops produce.

### Finding Description
Equality that must hold: `(owner of the UTXO minted in handleOut)` == `(stack.signerAddress, the party who authorized the ops that produced the balance increase)`.

Trace:
- `EmporiumUpgradeable.runAction` decodes `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and calls `verifyWallet(stack, circomData)` [1](#0-0) .
- `verifyWallet` builds `hashedMessage` from `EMPORIUM_SIGNATURE_TYPEHASH` over only `circomData.emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, `stack.deadline`, and recovers `stack.signerAddress` from `(v,r,s)` [2](#0-1) . Nowhere in this typed struct or its hash does `circomData.stealthAddressStructure`, `erc20TokenAddresses`, or `amountChanges` appear.
- The ops loop then invokes `IHinkalWallet(stack.signerAddress).callHinkalWallet(op.endpoint, op.callData, op.value)` for stateful ops - this executes arbitrary calls (e.g. unwrap/unstake/claim) from the victim's persistent `HinkalWallet` contract, which only checks `onlyEmporium` (i.e. `msg.sender == emporium`), not who submitted the outer transaction [3](#0-2) .
- After running the ops, `runAction` computes `balanceChange` from before/after token balances and calls `handleOut(balanceChange, circomData, i)`, which builds `outUtxo = UTXO(balanceChange, erc20Address, circomData.stealthAddressStructure, timeStamp)` - the destination is taken straight from `circomData`, supplied by the caller of `transact()`, with **no link at all to `stack.signerAddress`** [4](#0-3) .
- The only other place `stealthAddressStructure` is validated is inside `CircomDataBuilder.getSignedMessageHash`/`formBasicInput`, which folds `stealthAddressStructure.H1x/H1y/H0x/H0y` into the ZK circuit's `signedMessageHash`, verified against `spendingPublicKey` via the circuit's own EdDSA `SignatureVerifier` [5](#0-4) [6](#0-5) . That EdDSA key is the **prover's own** shielded-pool identity, entirely independent of `stack.signerAddress`'s EVM ECDSA key. Since the attacker generates their own ZK proof for the transaction (permitted per the threat model: attacker can craft `CircomData` and generate proofs), they simply plug in their own `spendingPublicKey`/`stealthAddressStructure` and sign the circuit's message with their own EdDSA key - the circuit happily verifies because it never checks that `spendingPublicKey` corresponds to `stack.signerAddress`.

Attacker's call: harvest a broadcast/relayed `EmporiumStack{v,r,s,signerAddress=victim, ops=[legit unwrap op], maxFee, deadline}`. Build a new `circomData` with the same `emporiumMessage`, the same `externalActionMetadata` (the harvested stack), consistent `erc20TokenAddresses`/`amountChanges` matching the token flow the ops will legitimately produce, but `stealthAddressStructure` set to the attacker's own stealth address (their own `H0/H1/stealthAddress`, generated from their own key material). Call `Hinkal.transact(a,b,c,dimensions,circomData)` with a proof generated under the attacker's own `spendingPublicKey`. `performHinkalChecks`/`verifyProof`/`rootHashExists`/`onlyAllowedRecipient` all pass because none of them tie `stealthAddressStructure` to `stack.signerAddress` - they only check proof validity for the *prover's own* claimed identity and consistency of nullifiers/roots/amounts, none of which encode "the signer of `ops` must equal the owner of the produced UTXO". `verifyWallet` passes because the ECDSA signature check is satisfied (the ops/maxFee/deadline/emporiumMessage are unchanged from the harvested signature). The ops execute, pulling/unwrapping the victim's assets into the Emporium contract's balance. `handleOut` then mints a UTXO to the attacker's `stealthAddressStructure` for that increased balance.

### Impact Explanation
Critical: direct theft of user funds. The value legitimately unwrapped/produced by the victim's signed authorization (e.g., unstaking, claiming rewards, withdrawing from an external protocol via their persistent `HinkalWallet`) ends up shielded to the attacker's own stealth address instead of the victim's, with `handleOut` even physically transferring the ERC20/ETH to `msg.sender` (the caller submitting the tx) via `transferERC20TokenOrETH(..., msg.sender, ...)` before wrapping it as a UTXO owned by the attacker's `stealthAddressStructure` [7](#0-6) . This is repeatable for any harvested `EmporiumStack` until `emporiumMessage` is consumed once (single-use via `usedMessages`), so each harvested signature is a one-time but complete theft of whatever balance the ops produce.

### Likelihood Explanation
Preconditions: attacker must observe/harvest a signed `EmporiumStack` (e.g. from a relay mempool, a leaked calldata, or a public relayer queue) before it is consumed, and must be able to submit `transact()` with their own valid ZK proof (fully within attacker capability per the threat model - no privileged role required). Cost is limited to gas plus generating one proof; feasibility is high because nothing in the flow requires attacker/victim key correlation. It is a single-shot exploit per harvested `EmporiumStack` (bounded by `usedMessages[emporiumMessage]`), but any victim/relayer flow that produces and broadcasts such signed stacks (e.g., meta-tx style relaying) is exploitable each time a new stack is generated.

### Recommendation
Bind `circomData.stealthAddressStructure` (and ideally `erc20TokenAddresses`/`amountChanges`, or at minimum a hash of the full `circomData` used for the UTXO output) into the EIP-712 struct that `stack.signerAddress` signs in `verifyWallet`, e.g. add `stealthAddressStructure` fields to `EMPORIUM_SIGNATURE_TYPEHASH` and `hashedMessage`, so the signer explicitly authorizes who receives the resulting shielded UTXO. Alternatively, require `handleOut`'s destination to be derived from a stealth address structure that was itself part of the ops signature payload, rejecting any `circomData.stealthAddressStructure` not matching what `stack.signerAddress` signed.

### Proof of Concept
Hardhat test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, `HinkalWallet` for victim, a mock ERC20 and a mock "unwrap" endpoint that transfers tokens from the victim's `HinkalWallet` to the Emporium contract when called via `callHinkalWallet`.
2. Victim signs an `EmporiumStack` (`ops` = one stateful op calling the mock unwrap endpoint via `invokeWallet=true`, `signerAddress=victim wallet`, `maxFee`, `deadline`) using EIP-712 domain `("Emporium","1.0.0")` and `EMPORIUM_SIGNATURE_TYPEHASH`.
3. Attacker builds `circomData` with: `externalActionData.externalActionMetadata = abi.encode(stack)`, matching `emporiumMessage`, `erc20TokenAddresses`/`amountChanges` reflecting the unwrap's expected balance delta, and `stealthAddressStructure` derived from the attacker's own spending key (`H0`,`H1`,`stealthAddress`).
4. Attacker locally generates a valid Groth16 proof for this `circomData` using their own `spendingPublicKey`/`nullifyingPrivateKey`/EdDSA signature over `signedMessageHash` (which incorporates the attacker's own `stealthAddressStructure`), satisfying `SignatureVerifier` and all in-circuit constraints (`inTotal + amountChanges === outTotal`, `OverflowPreventer`, `BabyJubjubSubgroupCheck`).
5. Attacker calls `Hinkal.transact(a,b,c,dimensions,circomData)`.
6. Assert: (a) the call succeeds, `verifyWallet` does not revert; (b) the victim's `HinkalWallet` balance decreased by the unwrapped amount; (c) the emitted/created on-chain commitment / off-chain UTXO decrypts (via `stealthAddressStructure`/shared secret) to the **attacker's** keys, not the victim's, proving `owner(UTXO) != stack.signerAddress` despite the balance increase originating entirely from the victim-signed ops.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
