Confirmed: `to_signable_string` for webhooks returns only the raw body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never part of the HMAC-signed material [2](#0-1) .

### Title
Webhook shop/topic/webhook_id identity fields are not covered by the HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) from raw, unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the request body against `Context.api_secret_key`. Consequently, any bytes that pass HMAC validation can be replayed with attacker-chosen header values, breaking the binding between "the request whose signature was verified" and "the shop/topic the app processes it as."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from headers that are excluded from that signable string: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., body only) and compares it against the `hmac-sha256` header using `OpenSSL.secure_compare`: [4](#0-3) 

`Webhooks::Registry.process` trusts these unauthenticated fields directly: it looks up the handler by `request.topic`, and forwards `request.shop`, `request.topic`, and `request.webhook_id` into `WebhookMetadata` without any cross-check against the signed body: [5](#0-4) 

The binding that should hold is:
`HMAC-verified(body) == HMAC-verified(shop, topic, webhook_id, body)`

but in this implementation:
`HMAC-verified(body) ⊄ {shop, topic, webhook_id}` — those three fields are outside the MAC's scope entirely.

Because Shopify signs the webhook body with the app's shared `client_secret` for every shop that has the app installed, an attacker who can install the app on their own store (a normal, unprivileged action for any public/dev app) can trigger a webhook containing body content they substantially control (e.g., a `products/create` event with attacker-chosen title/description/fields), capture the genuine `(raw_body, hmac)` pair Shopify computed for their own shop, and then POST that exact `raw_body` with the same `hmac-sha256` value directly to the app's public webhook endpoint — but with `x-shopify-shop-domain` set to a victim shop and/or `x-shopify-topic` set to a different registered topic. `HmacValidator.validate` will still succeed because the header values it never inspected are irrelevant to the check, and `Registry.process` will dispatch to whatever handler `@registry[forged_topic]` designates, tagging the resulting `WebhookMetadata` with the forged `shop`.

### Impact Explanation
This breaks the shop-identity binding a webhook consumer depends on for multi-tenant correctness: any downstream logic that trusts `WebhookMetadata#shop` (e.g., to look up which merchant's session/store the data belongs to) can be made to associate attacker-authored content with a different tenant, and/or trigger an unrelated topic handler with attacker-chosen body content. This is a cross-tenant data-integrity/impersonation issue arising directly from a gap in this gem's own signature verification design (only the body is authenticated; the identity headers are not).

### Likelihood Explanation
Any unprivileged internet user who can install the target app on a shop they control (the normal, documented installation flow, no leaked credentials or elevated access required) can obtain a genuine `(body, hmac)` pair and freely swap the `shop-domain`/`topic`/`webhook_id` headers before replaying the POST to the app's public webhook receiver endpoint. No secret material, TLS interception, or social engineering is needed — only the ability to install/use the app once and then send an unauthenticated HTTP POST.

### Recommendation
Extend `to_signable_string` (or add a second validation step) so the HMAC-covered material includes the identity-bearing headers (`shop`, `topic`, `webhook_id`) in addition to the body, or otherwise cryptographically bind them (e.g., derive an expected topic/shop from the verified body and reject mismatches) before `Registry.process` uses them for routing and tenant attribution. At minimum, document that consumers of `WebhookMetadata#shop`/`#topic` must not treat them as authenticated without additional server-side shop/topic membership checks.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event whose body content is attacker-influenced (e.g., create a product with a chosen title), causing Shopify to POST to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over that exact `raw_body` using the app's shared `client_secret`.
3. Capture `raw_body` and the `x-shopify-hmac-sha256` value.
4. Replay a POST to the same webhook endpoint using the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com` and/or `x-shopify-topic` to a different registered topic.
5. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`, only the body is checked), and `ShopifyAPI::Webhooks::Registry.process` (per `lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the forged `shop`/`topic` to the corresponding handler as if it were a legitimate webhook for `victim.myshopify.com`.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
