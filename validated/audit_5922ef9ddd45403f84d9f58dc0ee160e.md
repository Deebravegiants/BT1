### Title
Positional `zip` of `feeEstimation`/`withdrawalParams` in batch mode lets a caller pair a fee quote for token B with a withdrawal of token A, producing a `token_diff` that trades the wrong asset - (File: `packages/intents-sdk/src/sdk.ts`)

### Finding Description
`signAndSendWithdrawalIntent` accepts `withdrawalParams` and `feeEstimation` as parallel arrays in batch mode and pairs them purely by array index via `zip(withdrawalParamsArray, feeEstimations)`: [1](#0-0) 

Each pair is forwarded unchanged to `createWithdrawalIntents`, which dispatches to the matching bridge and calls `bridge.createWithdrawalIntents({ withdrawalParams, feeEstimation, ... })`: [2](#0-1) 

Every bridge implementation (direct, omni, hot) builds the `token_diff` leg directly from `feeEstimation.quote.defuse_asset_identifier_in` / `_out`, with **no comparison** to `withdrawalParams.assetId`: [3](#0-2) [4](#0-3) [5](#0-4) 

The only place a quote is cross-checked against a request is `matchesRequest` inside `getQuote`, which verifies a *solver's* returned quote matches the *request the SDK itself issued* (`defuse_asset_identifier_in/out`, amounts) — it has no bearing on a caller-supplied, already-built `FeeEstimation[]` array that is passed straight into `signAndSendWithdrawalIntent`: [6](#0-5) 

`feeEstimation` is a public parameter of `signAndSendWithdrawalIntent` / `processWithdrawal`, explicitly documented and typed to accept a pre-computed array rather than forcing in-line computation: [7](#0-6) 

Because nothing anywhere in `createWithdrawalIntents`, `_estimateWithdrawalFee`, or the individual bridges' `validateWithdrawal`/`createWithdrawalIntents` methods asserts `feeEstimation.quote.defuse_asset_identifier_in === withdrawalParams.assetId`, an attacker who supplies `withdrawalParams = [A, B]` and a `feeEstimation` array whose element 0 actually carries a quote for asset B (e.g., by calling `estimateWithdrawalFee` separately for A and B and reordering the results, or by hand-crafting the `FeeEstimation` object) causes `createWithdrawalIntents` for A to embed a `token_diff` that debits asset B's `defuse_asset_identifier_in` instead of A's. The final `ft_withdraw`/`mt_withdraw` intent for A still uses `withdrawalParams.assetId` (A) for the withdrawal leg, but the accompanying `token_diff` trades away B. Since all intents in the batch are signed together by the same `signAndSendIntent` call and settled atomically as one signed payload, the signer ends up authorizing a debit of B's balance that they did not request for that leg.

### Impact Explanation
This is intent manipulation: the `token_diff` intent — which debits `quote.amount_in` of `defuse_asset_identifier_in` from the signer and credits `quote.amount_out` of `defuse_asset_identifier_out` — is signed and published referencing an asset unrelated to the withdrawal it is nominally funding the fee for. This drains a balance of an asset the caller did not intend to spend for that withdrawal, matching the "Critical: intent manipulation moving funds the user did not authorise" category. It is repeatable on every batched call where the caller (or a library wrapping it) is careless/racing async fee estimations and does not itself re-verify ordering.

### Likelihood Explanation
Preconditions: `isBatchMode(args)` true (i.e., the caller uses the array overload of `withdrawalParams`/`feeEstimation`), and the caller supplies a `feeEstimation` array that isn't strictly derived from `estimateWithdrawalFee(withdrawalParams)` in the same call (e.g., built from two separate `estimateWithdrawalFee` calls raced and reordered, or manually constructed). This requires the caller (an "unprivileged" SDK user or an integrator forwarding solver-provided fee quotes) to supply mismatched data — the SDK API surface makes this possible with no cross-validation, and the vulnerability is entirely within the SDK's control-flow (`sdk.ts:704-713` plus each bridge's `createWithdrawalIntents`), not a documented "escape hatch" requiring deliberate misuse of a security control — there simply is no control to misuse.

### Recommendation
In `IntentsSDK.createWithdrawalIntents` (or immediately in the `zip(...)` mapper inside `signAndSendWithdrawalIntent`), assert that `feeEstimation.quote == null || feeEstimation.quote.defuse_asset_identifier_in === withdrawalParams.assetId` before invoking the bridge, throwing a descriptive error (e.g., `FeeEstimationAssetMismatchError`) on failure so mis-paired batches fail closed rather than silently building a `token_diff` for the wrong asset.

### Proof of Concept
```ts
// packages/intents-sdk/src/sdk.signAndSendWithdrawalIntent.test.ts (illustrative)
it("BUG: batched feeEstimation out of order drains wrong asset", async () => {
  const sdk = new IntentsSDK({ referral: "", intentSigner });

  const withdrawalParams = [
    { assetId: "nep141:asset-A.near", amount: 1000n, destinationAddress: "0x...A" },
    { assetId: "nep141:asset-B.near", amount: 1000n, destinationAddress: "0x...B" },
  ];

  // feeEstimation[0] actually quotes asset B, not A (as if two estimateWithdrawalFee
  // calls were raced and their results swapped before being passed in).
  const feeEstimationForB = {
    amount: 10n,
    quote: {
      defuse_asset_identifier_in: "nep141:asset-B.near", // MISMATCH vs withdrawalParams[0].assetId
      defuse_asset_identifier_out: "nep141:wrap.near",
      amount_in: "10",
      amount_out: "10",
      expiration_time: "",
      quote_hash: "hashB",
    },
    underlyingFees: {},
  };
  const feeEstimationForA = { ...feeEstimationForB, quote: { ...feeEstimationForB.quote, defuse_asset_identifier_in: "nep141:asset-A.near", quote_hash: "hashA" } };

  const feeEstimation = [feeEstimationForB, feeEstimationForA]; // swapped

  const intents = await sdk.createWithdrawalIntents({
    withdrawalParams: withdrawalParams[0],
    feeEstimation: feeEstimation[0],
  });

  // Assert the broken equality: feeEstimation[0].quote.defuse_asset_identifier_in
  // does NOT equal withdrawalParams[0].assetId, yet the token_diff still uses it.
  expect(feeEstimation[0].quote.defuse_asset_identifier_in).not.toBe(withdrawalParams[0].assetId);
  expect(intents[0]).toEqual({
    intent: "token_diff",
    diff: {
      "nep141:asset-B.near": "-10", // draining asset B, not asset A
      "nep141:wrap.near": "10",
    },
    referral: undefined,
  });
});
```
This test mocks nothing but constructs inputs directly (no HTTP needed for `createWithdrawalIntents` itself since `feeEstimation` is caller-supplied); it demonstrates that no assertion in `sdk.ts` or the bridge's `createWithdrawalIntents` rejects the mismatched pairing.

```typescript
function matchesRequest(
	quote: Quote,
	quoteParams: GetQuoteParams["quoteParams"],
): boolean {
	if (
		quote.defuse_asset_identifier_in !==
			quoteParams.defuse_asset_identifier_in ||
		quote.defuse_asset_identifier_out !==
			quoteParams.defuse_asset_identifier_out
	) {
		return false;
	}

	// Only the side fixed by the request is verified; the other side is what the
	// solver competes on (max amount_out for exact_in, min amount_in for
	// exact_out). Compare as BigInt so formatting differences don't matter.
	if (quoteParams.exact_amount_in != null) {
		return BigInt(quote.amount_in) === BigInt(quoteParams.exact_amount_in);
	}
	return BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out);
}
```
