### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body of an incoming webhook request: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values are all read directly from HTTP headers and are never included in the signed content: [2](#0-1) 

`Registry.process` validates the request purely with `Utils::HmacValidator.validate(request)`, which — per `VerifiableQuery`/`HmacValidator` — only proves the *body* was produced with the app's `client_secret`; it says nothing about which shop the body belongs to. Immediately after that check passes, `request.shop` (the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) is trusted as the tenant identity and handed to the app's handler: [3](#0-2) 

This breaks the intended binding `shop that authenticated the HMAC == shop the handler acts on`. In reality the equality is `shop that authenticated the HMAC (none, since shop isn't signed) != shop-domain header value used for dispatch`.

### Impact Explanation
Any actor who can install the app on their own shop (an unprivileged Shopify merchant, not requiring the app's `client_secret`) receives legitimate webhook deliveries containing a valid `(raw_body, hmac)` pair computed for their own tenant. Because the shop domain is never part of the signed content, that same `(raw_body, hmac)` pair remains valid regardless of the `shopify-shop-domain` header sent with it. The attacker can replay this pair to the app's own webhook receiving endpoint (implemented on top of this gem's `Registry.process`) while substituting a victim shop's domain in the header. `Utils::HmacValidator.validate` still returns `true` (it only re-hashes `@raw_body`), and the handler executes with `data.shop` set to the victim's shop — i.e., a cross-tenant confusion. This is especially severe for the mandatory GDPR topics wired into this same registry (`shop/redact`, `customers/redact`, `customers/data_request`), where an attacker-controlled body can be attributed to and acted upon for a shop they do not own.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on any shop they control (a routine, low-privilege action) and to be able to reach the app's public webhook endpoint — no access to `client_secret`, access tokens, or any Shopify-internal secret is needed. This is a straightforward, low-cost replay against a documented integration point (`Registry.process`), matching the "field acted on but not covered by the HMAC" bug class.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop-domain header to the signed body before it is trusted for dispatch, e.g.:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{@raw_body}"
end
```
so that `Utils::HmacValidator.validate` fails whenever the `shopify-shop-domain` header does not match the shop the body was actually generated for.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com`, gets the app's `client_secret`-derived webhook subscription, and receives a real webhook delivery: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker.myshopify.com`.
2. Attacker sends a forged HTTP request to the app's webhook receiving endpoint with the same `raw_body = B` and the same `hmac` header, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, request.to_signable_string)` = `HMAC(secret, B)` — matching, since the shop header is never part of `to_signable_string`. Validation passes. [4](#0-3) 
4. The handler is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` while the body content originated from the attacker's own shop, letting the attacker trigger shop-scoped business logic (including mandatory redact/data-request flows) attributed to `victim.myshopify.com`.
