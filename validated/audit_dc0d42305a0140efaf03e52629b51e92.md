### Title
Webhook `shop` and `topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts these unauthenticated headers to route the payload and to build the `WebhookMetadata` object that downstream handlers use as the tenant identity.

### Finding Description
`Request#hmac` decodes the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`request.shop` and `request.topic`, however, are read straight from headers (`shopify-shop-domain`, `shopify-topic`) and are never part of the signed string: [4](#0-3) 

`Registry.process` validates the HMAC (which only proves the body was signed by the app's `api_secret_key`), then unconditionally uses `request.shop` and `request.topic` — unauthenticated header values — to route to a handler and to construct the `WebhookMetadata` identity passed to the app's handler: [5](#0-4) 

Because `api_secret_key` is a single shared secret for the whole app (used across every shop that has it installed), any account that can get the app to send it a legitimately-HMAC'd body (e.g. by installing the app on their own store and receiving a real webhook, or by finding any body value the app will treat as valid, such as `{}`) can replay that body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` and/or `shopify-topic` header. `Registry.process` will still pass HMAC validation (since only the body is verified) and will hand the handler a `WebhookMetadata` claiming the payload came from a different topic/shop than it actually did. This breaks the identity equality `shop_header == shop_that_actually_produced_this_signed_body`.

### Impact Explanation
This is a cross-tenant identity-binding break: the `shop` value an app relies on to attribute/scope webhook data to a tenant is not authenticated by the same HMAC that authenticates the payload. An attacker controlling one shop's install of the app can produce validly-signed bodies and relabel them as belonging to another shop or another topic, letting them inject attacker-controlled (but validly signed) data attributed to a victim tenant, or trigger topic-specific handler logic (e.g. `app/uninstalled`, `shop/redact`) under a spoofed topic/shop pairing.

### Likelihood Explanation
Requires only an app installation (unprivileged, attacker's own shop) and the ability to POST an arbitrary HTTP request to the app's public webhook endpoint with attacker-chosen headers plus a body/HMAC pair obtained from a legitimate webhook delivery to the attacker's own store. No access token, `api_secret_key`, or privileged account is needed — this fits the "unprivileged internet user" threat model.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the HMAC (e.g., by having `HmacValidator` verify a canonicalized string that concatenates headers and body) so that a valid signature can only be produced for a specific shop/topic/body triple, not the body alone.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook delivery with body `B` and header `shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` and/or a different `shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata` claiming `shop: "victim-shop.myshopify.com"` even though the signed payload never originated from that shop.
