### Title
Signup proceeds with an implicit "Allowed" software-version status when the backend response omits the field, silently bypassing the version gate - (File: `src/backend/signup_post.rs`)

### Summary
The Reserve Protocol bug describes a case where a price-fetching function returns a "safe-looking" sentinel value (`(0, FIX_MAX)`) instead of reverting when data can't be fetched, and the caller trusts that sentinel without validating it, corrupting a downstream security-relevant calculation. The orb-core analog is in `signup_post::Response`, where the `software_version_status` field silently defaults to the permissive `Allowed` variant whenever the backend response is missing or fails to include that field, and the caller (`enroll_user::Plan::run`) unconditionally trusts this defaulted value to gate whether a signup should proceed.

### Finding Description
`signup_post::Response` deserializes the backend's signup response with: [1](#0-0) 

The `#[serde(default)]` attribute combined with `#[default] Allowed` on `SoftwareVersionStatus` means that if the backend's JSON response omits the `softwareVersionStatus` field for any reason (backend bug, partial response, serialization issue, network truncation that still passes `error_for_status_ref()`), the deserialized value silently becomes `SoftwareVersionStatus::Allowed` — the same value that legitimately means "this software version passed the backend's check" — with no distinction between "backend explicitly allowed this version" and "backend didn't tell us anything about the version."

The caller, `enroll_user::Plan::run`, has no way to detect this and unconditionally proceeds with the enrollment/signup flow for the `Allowed` (and also `Deprecated`/`Unknown`/`Empty`) branch: [2](#0-1) 

This mirrors the root cause of the Reserve Protocol report: a fetch/parse failure is masked by a default value that is indistinguishable from a genuine, successful result, and the downstream consumer performs a security-relevant decision (whether to allow the signup to proceed, i.e. the software-version gate meant to block outdated/incompatible Orb software from creating signups) based on that unchecked, potentially-erroneous value.

### Impact Explanation
The Orb backend software-version check exists specifically to block signups from Orbs running outdated/incompatible software (`SoftwareVersionStatus::Blocked` explicitly returns `Status::SoftwareVersionOutdated` and aborts the signup). Because the missing-field case is indistinguishable from `Allowed`, a partial/incomplete backend response silently defeats this control and lets the biometric enrollment pipeline continue as if the version check had passed, when in fact no real determination was ever made by the backend for that particular request.

### Likelihood Explanation
This requires no attacker action beyond a normal signup flow; it triggers whenever the backend's JSON response to `POST /api/v2/signups/{signup_id}` omits the `softwareVersionStatus` key (e.g., transient backend bug, response truncation surviving `error_for_status_ref()`, backwards-incompatible backend deploy). Because there's no positive signal differentiating "explicitly allowed" from "field absent," this can occur without any adversarial input and is not guarded against anywhere in the client code.

### Recommendation
Do not give `SoftwareVersionStatus` a safe/permissive default for the missing-field case. Instead:
- Make `software_version_status` a required field (remove `#[serde(default)]`) so that a missing field causes the response parse to fail and be treated as an error (mirroring the "network/decoding error" branch in `enroll_user.rs`, which already safely aborts the signup on `Err`).
- Alternatively, introduce a distinct enum variant (e.g., `Missing`) for the absent case and treat it identically to `Unknown`/`Blocked` (i.e., fail closed) rather than aliasing it to `Allowed`.

### Proof of Concept
1. Backend responds to `POST /api/v2/signups/{signup_id}` with a 2xx status and a JSON body that omits `softwareVersionStatus` (e.g., `{}`).
2. `signup_post::request` in `src/backend/signup_post.rs` parses this into `Response { software_version_status: SoftwareVersionStatus::Allowed }` via the serde default, with no error raised.
3. `enroll_user::Plan::run` in `src/plans/enroll_user.rs` matches on the `Allowed` arm and proceeds with signup polling as if the backend had explicitly approved the software version, even though no genuine approval was communicated.

```rust
/// Response of the signup endpoint.
#[derive(Deserialize, Debug)]
#[serde(rename_all = "camelCase")]
pub struct Response {
    /// Status of the Orb versions.
    #[serde(default)]
    pub software_version_status: SoftwareVersionStatus,
}

/// Versions status.
#[derive(Deserialize, Debug, Default)]
#[serde(rename_all = "SCREAMING_SNAKE_CASE")]
pub enum SoftwareVersionStatus {
    /// Versions are ok.
    #[default]
    Allowed,
    /// Ok, but strongly recommended to update.
    Deprecated,
    /// Too old for doing signups.
    Blocked,
    /// Backend doesn't know about this version
    Unknown,
    /// Backend sometimes returns empty string
    #[serde(alias = "")]
    Empty,
}
```
