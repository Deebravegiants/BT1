I have enough context on the router; let me confirm how the controller passes user-supplied route bytes and whether any venue/address allowlist exists.### Title
Attacker-supplied route bytes execute arbitrary contract code inside the victim's authorization tree, draining any wallet token - (File: contracts/swap-aggregator/src/venues/soroswap.rs)

### Summary
The PraisonAI bug class is "untrusted input interpreted as a program that runs arbitrary commands with the victim's authority." The on-chain analog exists verbatim in XOXNO Lending: `execute_strategy`'s `swap_xdr` is an attacker-crafted program whose `assets` registry names the contracts each hop invokes, and neither the controller nor the router allowlists them. A route can name an attacker-deployed contract as a hop "pool"; that code runs mid-transaction under the caller's `require_auth` tree and can call `token.transfer(victim, attacker, X)` on any token, which recording mode attaches as a child of the victim's own authorization entry. The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` pins this: the victim's whole `WALLET_BALANCE` of an unrelated token is moved to the attacker.

### Finding Description
The controller strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) take a user-supplied `swap: StrategySwap` byte blob and forward it unmodified to the configured router in `swap_tokens` — the only validation is `!swap.is_empty()` and post-hoc balance deltas (`RouterOverspend`, `NoSwapOutput`). [1](#0-0) 

Inside the router, `execute_op` resolves `hop.pool` purely from the payload's `assets` registry (`ctx.assets.get_unchecked(op.idx_a)`), and each venue adapter invokes that address directly — e.g. the Soroswap adapter calls `invoke_contract(&ctx.hop.pool, "swap", args)` with no venue/pool allowlist anywhere. [2](#0-1) [3](#0-2) 

Because `execute_strategy` runs under `sender.require_auth()`, a `token.transfer(sender, attacker, amount)` issued by the rogue pool is recorded by simulation as a child of the sender's auth entry and executes when the sender signs that tree. The threat model itself concedes: "a route can put third-party code on the call stack below the caller's authorization… the loss is then the caller's wallet, not the routed amount." [4](#0-3) 

The test proves the drain: `RogueHopPool::swap` calls `token::Client::transfer(victim, attacker, amount)` and the assertion shows `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the swap still "succeeds" and delivers the fair output. [5](#0-4) [6](#0-5) 

### Impact Explanation
Theft of user funds, unbounded by the swap size: the rogue contract can transfer *any* token the victim holds (including tokens the protocol never listed, and tokens unrelated to the strategy), for the full balance, within the victim's signed transaction. Neither the router's `min_out` check, the controller's `RouterOverspend`/`NoSwapOutput` deltas, nor the final health-factor gate bound the loss, because the theft is a side-effect authorized under the caller's own signature, not a measured router balance change.

### Likelihood Explanation
Reachable by any unprivileged address: the attacker only needs to craft a `swap_xdr` naming their contract as a hop pool and get a victim to run a controller strategy (or direct `execute_strategy`) with it — the standard quote-and-sign flow, where users routinely sign simulated auth trees produced by a quote server they must trust. This is precisely the PraisonAI shape (victim runs attacker-supplied "workflow file"); the only mitigating factor is that the victim must sign a tree containing the extra child, which wallets display poorly and the project itself mitigates only via off-chain client guidance.

### Recommendation
Enforce an allowlist of hop-pool addresses (or at minimum of venue contract addresses per venue type) in the router, set administratively like `set_swap_aggregator`, so `dispatch_hop` refuses payload-named contracts that were never registered. Alternatively, execute hops through a dedicated, non-`require_auth` sub-account/mechanism so payload-named code can never sit below the caller's auth tree; and have the controller validate that the route's asset registry contains only expected token addresses before authorizing the input transfer.

### Proof of Concept
The shipped test is a working PoC: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` registers `UnlistedPoolRouter` (which `invoke_contract`s the payload-named `hop_pool`) and `RogueHopPool` (which transfers `WALLET_BALANCE` of an unlisted token from victim to attacker), then calls `ctrl.swap_collateral(alice, account, usdc, amount, eth, route)` under `mock_all_auths`. Result asserted on-chain: the rogue transfer is recorded inside Alice's `swap_collateral` auth entry, `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while the strategy returns normally and credits Alice's ETH supply balance — demonstrating that arbitrary code execution via route bytes steals funds the swap's own safety checks never see. #[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
