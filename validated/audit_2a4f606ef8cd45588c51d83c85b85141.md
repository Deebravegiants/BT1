### Title
GRANDPA `AncestryChain::ancestry` Infinite Loop via Circular `parent_hash` Chain in Relayer-Supplied Justification - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The GRANDPA consensus client's ancestry-walking routine trusts an attacker-controlled `votes_ancestries` header set and follows each header's self-declared `parent_hash` field without any cycle detection or iteration bound. A relayer can submit a consensus proof containing two (or more) headers whose declared `parent_hash` fields point at each other, forming a cycle that is disjoint from the walk's `base` target. The verifier then loops forever walking `current_hash -> parent_hash -> current_hash -> ...`, exactly analogous to NanoZip's circular `NextOffset` chain causing an infinite loop in the untrusted ROMFS parser.

### Finding Description
`AncestryChain::ancestry` builds a lookup map keyed by each header's real computed hash, then walks parent pointers until it reaches `base`: [2](#0-1) 

The map is built directly from the untrusted `votes_ancestries: Vec<H>` field of the `GrandpaJustification`, which is fully attacker-controlled input decoded from a submitted consensus proof: [3](#0-2) 

Because a header's hash is computed over its full contents (including the `parent_hash` field value), and `parent_hash` is just an arbitrary field — not cryptographically tied to any real ancestry — an attacker can craft header `A` with real hash `H_A` and `parent_hash = H_B`, and header `B` with real hash `H_B` and `parent_hash = H_A`. Both entries land in the `ancestry` `BTreeMap` under their real hashes. If `base` is neither `H_A` nor `H_B` (trivial to arrange, since `base` is the lowest-numbered precommit target and is otherwise unconstrained relative to the attacker's synthetic cycle), the `while current_hash != base` loop alternates forever between `H_A` and `H_B`, since both lookups always succeed (`Some(current_header)`), never hitting the `_ => return Err(...)` branch and never converging on `base`.

This loop is reached in two places for every consensus proof: (1) internally, by the `finality_grandpa::validate_commit` call (which also calls `Chain::ancestry` on the same `AncestryChain`) at the top of `verify_with_voter_set`, and (2) explicitly afterward when routing each precommit target back to `base_hash`: [4](#0-3) 

and again in the outer `verify_grandpa_finality_proof` used for both standalone and parachain-header finality: [5](#0-4) 

This is the on-chain GRANDPA `ConsensusClient::verify_consensus` path, invoked via `pallet_ismp::Call::handle_unsigned`, an unsigned extrinsic that "permits anyone execute ISMP messages for free, provided they have valid proofs": [1](#0-0) 

Unlike the Pharos SPV proof verifier in this same codebase, which was explicitly hardened against this exact bug class (unbounded proof depth / cycles) with a `MAX_PROOF_DEPTH` guard and regression tests referencing "prior to the MAX_PROOF_DEPTH guard... panic... index-out-of-bounds inside on-chain execution", the GRANDPA `AncestryChain::ancestry` walk has no equivalent bound: no maximum hop count, no visited-set check, nothing preventing the walk from cycling indefinitely through attacker-supplied headers. [6](#0-5) 

### Impact Explanation
Triggering this loop during on-chain block execution (inside `handle_unsigned` -> `ConsensusClient::verify_consensus` -> `verify_grandpa_finality_proof` -> `justification.verify(...)` -> `AncestryChain::ancestry`) causes the executing node to spin forever inside that single extrinsic's execution, consuming the block's weight/time budget without terminating normally. This is a liveness/DoS impact on the GRANDPA consensus-update route: it can stall processing of that block or extrinsic and blocks legitimate consensus updates and any counterparty state commitments/messages gated behind that consensus client, effectively making the affected route unable to deliver messages until intervention (e.g. governance disabling the call, similar to the existing `IsmpCallFilter` used to gate BEEFY-only proof intake). This qualifies as Medium severity: no funds are directly stolen, but it is a concrete availability failure of a message-delivery-critical relayed-proof path reachable by any unprivileged submitter.

### Likelihood Explanation
Likelihood is high for any deployment that accepts raw GRANDPA justifications through this path (no external hardware/consensus is needed to craft the attack — the attacker fully controls the encoded `GrandpaJustification.votes_ancestries` field and merely needs two headers whose `parent_hash` fields point at each other and whose hashes both differ from the computed `base_hash`, which is easy to arrange since `base_hash` is derived from the lowest-numbered *precommit* target and does not have to intersect the attacker-chosen ancestry set at all beyond satisfying `validate_commit`'s and `verify_with_voter_set`'s pre-checks). No privileged role, governance, or off-chain infrastructure is required — this is purely a crafted unsigned extrinsic.

### Recommendation
Bound `AncestryChain::ancestry` with an explicit maximum hop count (e.g. equal to `votes_ancestries.len() + 1`) and/or track visited hashes, returning `Error::NotDescendent` (or an equivalent typed error) as soon as either the maximum number of hops is exceeded or a hash is revisited, mirroring the `MAX_PROOF_DEPTH` / cycle-rejection pattern already used in `modules/consensus/pharos/primitives/src/spv.rs`.

### Proof of Concept
1. Attacker crafts headers `A` and `B` (e.g. minimal `sp_runtime::generic::Header` instances) such that `A.parent_hash = B.hash()` and `B.parent_hash = A.hash()`.
2. Attacker builds a `GrandpaJustification` whose `commit.precommits` targets some legitimate-looking `base`/target block that is unrelated to `A`/`B`, and sets `votes_ancestries = vec![A, B]`.
3. Attacker encodes this justification into a `ConsensusMessage` for the GRANDPA `consensus_state_id` and submits it via `pallet_ismp::Call::handle_unsigned` as an unsigned extrinsic (no signer required — `ensure_none(origin)`).
4. During execution, `verify_grandpa_finality_proof` -> `justification.verify(...)` (either inside `finality_grandpa::validate_commit`'s internal `Chain::ancestry` call, or in the explicit per-precommit `ancestry_chain.ancestry(base_hash, ...)` loop) walks `A -> B -> A -> B -> ...` forever because `current_hash` never equals `base` and both lookups always succeed, hanging the executing node/block.

				let result = err.map_err(|_| {
					anyhow!("[verify_with_voter_set] Invalid ancestry while validating commit!")

				&signed.id,

			for hash in route {
