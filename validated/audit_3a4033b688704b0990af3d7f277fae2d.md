Audit Report

## Title
Missing authentication on LOOP plugin pprof/metrics proxy endpoints - (File: core/web/router.go)

## Summary
`loopRoutes` registers `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` directly on the unauthenticated top-level `api` group, in contrast to every comparable debug/metrics surface in the router (`metricRoutes`) which requires token or session authentication. This lets any unprivileged client with network access to the node reach internal LOOP plugin profiling and metrics data, and trigger arbitrarily-configured CPU profile captures, without any credentials.

## Finding Description
`NewRouter` calls `loopRoutes(app, api)` on the base `api` group, which only carries rate limiting and session middleware (`api := engine.Group("/", rateLimiter(...), sessions.Sessions(...))`), with no `auth.Authenticate` wrapper. All four routes registered inside `loopRoutes` — `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, `/plugins/:name/debug/pprof/symbol` — inherit this lack of authentication. By contrast, the node's own equivalent pprof/debug surface, `metricRoutes`, is explicitly nested inside `authv2`, a group gated by `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`. The handlers `pluginMetricHandler`, `pluginPPROFHandler`, and `pluginPPROFPOSTSymbolHandler` proxy the incoming unauthenticated request straight through to the internal LOOP plugin's HTTP `/metrics` and `/debug/pprof/*` server, including forwarding client-supplied `debug`, `gc`, and `seconds` query parameters that directly control the internal pprof capture behavior (e.g., CPU profile duration). No authentication, authorization, or role check exists anywhere in this code path.

## Impact Explanation
An unauthenticated network client can retrieve internal metrics and pprof profiling data (goroutine stacks, heap samples, potential in-memory state) from LOOP plugin processes that back Chainlink's Solana/Cosmos/etc. relayer LOOPPs. This is an information-disclosure vector reachable without any credential, inconsistent with the authentication enforced on the functionally identical `metricRoutes` surface. The CPU-profile-duration control (`seconds` parameter) additionally enables a resource-exhaustion effect on the plugin process, but that aspect alone maps to a "DDoS-only" impact, which is explicitly listed as out of scope in `SECURITY.md`. The in-scope impact here is the unauthenticated information disclosure of internal debug/profiling data, comparable in class to the authenticated `/v2/debug/pprof/*` surface.

## Likelihood Explanation
High. The endpoints are registered unconditionally with no build tag or dev-only gating, and are reachable on any node configured with at least one LOOP plugin (e.g., a non-EVM relayer LOOPP) with its web server exposed — a standard production configuration, not requiring any special operator/admin access. Any client capable of reaching the node's HTTP port can trigger the endpoints repeatedly with only knowledge of a configured plugin name.

## Recommendation
Move `loopRoutes(app, api)` registration to run under the authenticated group (e.g., `authv2`, or a group wrapped with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)`), matching how `metricRoutes` is handled for the node's own pprof/debug endpoints. Also consider bounding/removing the client-controlled `seconds` parameter or capping it server-side regardless of authentication status.

## Proof of Concept
1. Start a chainlink node with at least one LOOP plugin registered (e.g., a Solana relayer LOOPP) and its web server exposed on the network.
2. Without any session cookie or API token header, issue: `GET /plugins/<plugin-name>/metrics` and `GET /plugins/<plugin-name>/debug/pprof/profile?seconds=60`.
3. Observe both requests succeed and return internal plugin metrics/pprof data.
4. Compare with `GET /v2/debug/pprof/profile` (under `authv2`) using no credentials, which returns `401 Unauthorized` — demonstrating the inconsistency and confirming the missing auth check on the LOOP plugin proxy routes.

func pprofURLVals(gc *gin.Context) (urlVals url.Values, timeout time.Duration) {
	urlVals = make(url.Values)
	if db, ok := gc.GetQuery("debug"); ok {
		urlVals.Set("debug", db)
	}
	if gc, ok := gc.GetQuery("gc"); ok {
		urlVals.Set("gc", gc)
	}
	timeout = PPROFOverheadSeconds * time.Second
	if sec, ok := gc.GetQuery("seconds"); ok {
		urlVals.Set("seconds", sec)
		if i, err := strconv.Atoi(sec); err == nil {
			timeout = time.Duration(i+PPROFOverheadSeconds) * time.Second
		}
	}
	return urlVals, timeout
}

func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}
