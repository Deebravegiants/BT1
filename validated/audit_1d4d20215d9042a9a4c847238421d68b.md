## Finding

Unlike the other contracts in this repo, `lockup/src/lib.rs`'s `new()` initializer is missing the `assert!(!env::state_exists(), "Already initialized")` guard that every other contract in the same repository uses. [1](#0-0) 

Compare this to `whitelist/src/lib.rs`, `staking-pool/src/lib.rs`, `staking-pool-factory/src/lib.rs`, `voting/src/lib.rs`, and `lockup-factory/src/lib.rs`, all of which explicitly check for existing state before initializing: [2](#0-1) [3](#0-2) 

### Title
Reinitialization of an already-deployed and funded `LockupContract` via public `new` call lets an attacker hijack ownership and drain locked funds - (`File: lockup/src/lib.rs`)

### Summary
`near-sdk`'s `#[init]` macro does not itself prevent an `init` method from being invoked more than once — each contract must add its own `assert!(!env::state_exists(), ...)` guard. `LockupContract::new` in `lockup/src/lib.rs` omits this guard, while all sibling contracts in this repo (`whitelist`, `staking-pool`, `staking-pool-factory`, `voting`, `lockup-factory`) include it. As a result, `new` remains a public, unauthenticated, callable method on an already-deployed and already-funded lockup account forever.

### Finding Description
`new` is a plain public method with `#[init]` and no owner check, no `#[private]`, and no `assert!(!env::state_exists())`: [1](#0-0) 

Because the guard is missing, any unprivileged account can call `new` again against a live, previously-initialized, and funded lockup contract account (e.g. `near call lockup1 new '{"owner_account_id": "attacker", ...}' --accountId=attacker`). This overwrites the entire `LockupContract` state — `owner_account_id`, `vesting_information`, `staking_information`, `foundation_account_id`, and `lockup_information` (whose `lockup_amount` is recomputed from `env::account_balance()`, i.e., the funds already sitting in the account) — with attacker-chosen values.

This is the direct analog of the reported dForce `ControllerV2` issue: an unprotected/publicly reachable initializer that lets an attacker take over contract state that should only be set once at deployment. In the dForce case the attacker corrupts the implementation via `delegatecall`; here the attacker corrupts the `LockupContract`'s persistent state by re-running the constructor logic on an already-live account.

### Impact Explanation
Once the attacker becomes `owner_account_id`, they gain full owner privileges over `owner.rs` methods (`select_staking_pool`, `deposit_and_stake`, `unstake`, `withdraw_from_staking_pool`, key/transfer related owner methods, etc.), letting them route the locked NEAR balance to a staking pool they control and withdraw it, or otherwise move funds out to themselves — an unauthorized transfer/withdrawal of locked NEAR (Critical). The re-init also wipes `vesting_information` and `foundation_account_id`, permanently destroying the NEAR Foundation's ability to terminate vesting/reclaim unvested tokens (irrevocable loss of protocol funds/rights) — matching the "Permanent freezing/irrevocable loss ... in lockup release, vesting termination" impact category as well.

### Likelihood Explanation
The entry point is fully public and requires no special privilege — any account can send a `new` function call transaction to an existing, deployed lockup contract account ID (which are typically well known/derivable, e.g. via `lockup-factory`). No race condition, timing, or trusted-role assumption is required; it is a straightforward call to a still-open public method.

### Recommendation
Add the standard initialization guard to `LockupContract::new`, consistent with the other contracts in the repo:
```rust
assert!(!env::state_exists(), "Already initialized");
```
at the start of the function, before any state is constructed, so that any call to `new` after the contract has already been initialized reverts. [4](#0-3) 

### Proof of Concept
1. Foundation/owner deploys and initializes `lockup1` with `owner_account_id = "owner1"` and funds it with N NEAR (as in the README flow) [5](#0-4) .
2. Attacker (any account, e.g. `attacker.near`) calls:
```bash
near call lockup1 new '{
  "owner_account_id": "attacker.near",
  "lockup_duration": "0",
  "lockup_timestamp": null,
  "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "0"}},
  "vesting_schedule": null,
  "release_duration": null,
  "staking_pool_whitelist_account_id": "staking-pool-whitelist",
  "foundation_account_id": null
}' --accountId=attacker.near --gas=25000000000000
```
3. Because there is no `state_exists` guard, this succeeds and overwrites `owner_account_id` to `attacker.near`, clears vesting/foundation info, and recomputes `lockup_amount` from the account's current balance (the already-locked N NEAR).
4. Attacker now calls owner methods (e.g. `select_staking_pool`, `deposit_and_stake` to a pool they control, then `unstake`/`withdraw_from_staking_pool`) to move the locked funds out under their own control.

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
