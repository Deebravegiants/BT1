### Title
Malicious solver can permanently freeze cross-chain order escrow via a reverting `RedeemEscrow` beneficiary - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol / IntentsBase.sol)

### Summary
In cross-chain intent fills, `_fillCrossChain` sets the `RedeemEscrow` withdrawal beneficiary to `msg.sender` (the solver) without any validation that the address can safely receive funds. When Hyperbridge delivers this message back to the source chain, `EvmHost.dispatchIncoming` calls `IApp.onAccept` via a low-level `.call`; if it reverts, the receipt is deleted so the message can be retried — but if the beneficiary is a contract engineered to permanently revert on receiving native tokens (or is a token that always reverts `transfer`), the retry will fail forever, permanently freezing the user's escrowed input tokens.

### Finding Description
`_fillCrossChain` in `ExtrinsicIntents.sol` builds the `RedeemEscrow` withdrawal body with `beneficiary: bytes32(uint256(uint160(msg.sender)))` — the solver's own address, fully attacker-controlled — and dispatches it to the source chain: [5](#0-4) 

On the source chain, `onAccept` decodes this into a `WithdrawalRequest` and calls `_withdraw`, which unconditionally sends native tokens via `_sendValue` (reverts on failed native `.call`) or ERC-20 via `safeTransfer` to the solver-supplied `beneficiary`: [6](#0-5) [4](#0-3) 

This `onAccept` call is only reachable through `EvmHost.dispatchIncoming`, which wraps the delivery in a low-level `.call` and, on failure, simply deletes the request receipt to allow a later retry: [7](#0-6) 

The "retry on failure" design assumes the failure is transient (e.g., gas, temporary pausing). It does not account for a beneficiary address that is *permanently* incapable of receiving funds, exactly the bug class described in the Cooler.sol report where a party-controlled callback address that always reverts blocks the entire settlement flow. Here, the malicious party is the solver, an unprivileged, permissionless participant who fully controls which address is embedded as `beneficiary` in the `RedeemEscrow` message before it is even dispatched.

Because the order is already marked filled on the destination chain (`_filled[commitment] = msg.sender` at the top of `_fillCrossChain`), and the source-chain cancellation path (`_cancelFromSource` / `onGetResponse`) explicitly reverts with `Filled()` once the destination shows the order as filled, there is no alternate recovery path for the user's escrow once redemption is permanently blocked: [8](#0-7) 

### Impact Explanation
A malicious solver can fill a cross-chain order using a beneficiary contract with a `receive()` that always reverts (or, for ERC-20 escrow inputs, is irrelevant since ERC20 `safeTransfer` to the solver's chosen address can also be made to always fail if the solver is itself an unusual account — but native-token escrow is the clean case). Every delivery/retry of the `RedeemEscrow` message on the source chain will revert, so `_requestReceipts` is deleted every time and the message can be resubmitted indefinitely without ever succeeding. The user's escrowed input tokens for that order become permanently frozen: the order is filled on destination (so `cancelOrder`/`onGetResponse` refund path is blocked by the `Filled()` check), and redemption on source can never succeed. This is a permanent freezing-of-funds condition reachable by any unprivileged intent solver, satisfying High severity.

### Likelihood Explanation
Any solver can call `fillOrder` for a cross-chain order and simply be, or route through, a contract that reverts on receiving native tokens — no special privileges or governance access required. The condition triggers on the very first fill attempt; a solver willing to sacrifice their own output-token delivery (already made to the order's beneficiary on the destination chain) can grief a user's escrow with certainty. This is a straightforward, cheap, self-contained griefing vector.

### Recommendation
Do not let a single external transfer failure to an attacker-controlled address abort a critical funds-release path irreversibly. Options:
- Use a pull-based withdrawal pattern for `RedeemEscrow`/`RefundEscrow` beneficiaries: record the amount owed to the beneficiary in storage and let them `claim()` it separately, so a hostile receiving contract only harms itself.
- Wrap the native-token transfer in a try/catch (or check success without reverting the whole `onAccept`) and, on failure, credit the beneficiary's balance in an internal ledger for later withdrawal, instead of reverting the whole request and relying on indefinite retries.
- Alternatively, cap and isolate failures per-token/beneficiary rather than failing the entire `onAccept` dispatch, so other legitimate order fulfillments are not perpetually retried against a poisoned message.

### Proof of Concept
1. Deploy `EvilBeneficiary`, a contract with `receive() external payable { revert(); }`.
2. As solver, call `fillOrder(order, options)` on the destination chain for a cross-chain order whose native-token output has already been satisfied to the legitimate order beneficiary, but call it from `msg.sender = EvilBeneficiary` (or otherwise arrange that the solver address embedded as `beneficiary` in the dispatched `RedeemEscrow` body is `EvilBeneficiary`).
3. `_fillCrossChain` sets `_filled[commitment] = msg.sender` and dispatches `RedeemEscrow` with `beneficiary = EvilBeneficiary` back to the source chain.
4. On the source chain, Hyperbridge relays the message; `EvmHost.dispatchIncoming` calls `IntentGateway.onAccept`, which calls `_withdraw`, which attempts `_sendValue(EvilBeneficiary, amount)` — this reverts, causing `onAccept` to revert.
5. `dispatchIncoming` deletes the receipt and returns without reverting the batch, so the message is marked undelivered and can be resubmitted — but every resubmission hits the same revert.
6. The user's escrowed input tokens for `commitment` are now stuck: `cancelOrder`/`_cancelFromSource` cannot recover them because the destination-side `_filled[commitment]` is already set (order filled), so `onGetResponse` reverts with `Filled()`.

        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();

                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);

                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }

    /// @dev Native transfer that reverts with `InsufficientNativeToken` if refused.
    function _sendValue(address to, uint256 amount) internal {
        (bool sent,) = to.call{value: amount}("");
        if (!sent) revert InsufficientNativeToken();
    }

    /// @dev Splits overpayment between protocol and beneficiary. An order with output calldata
    /// gives the beneficiary nothing, since the surplus is not the caller's to give.
    function _splitSurplus(uint256 dust, bool hasOutputCall)
        internal
        view
        returns (uint256 protocolShare, uint256 beneficiaryShare)
    {
        if (hasOutputCall) return (dust, 0);
        protocolShare = (dust * _params.surplusShareBps) / 10_000;
        beneficiaryShare = dust - protocolShare;
    }

     * When `finalize` is true, the order is marked as filled in the `_filled` mapping,
     * any accumulated transaction fees (in the protocol fee token) are forwarded to the
     * beneficiary, and the appropriate event (EscrowReleased or EscrowRefunded) is emitted.
     *
     * When `finalize` is false (partial fills), only the proportional token amounts are
     * released without finalizing the order.
     *
     * @param body The withdrawal request containing the commitment, token amounts, and beneficiary.
     * @param isRefund If true, emits EscrowRefunded instead of EscrowReleased on finalization.
     * @param finalize If true, marks the order as complete and releases accumulated fees.
     */
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
