### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing a cross-tenant shop-identity spoof - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `X-Shopify-Shop-Domain` header, but the HMAC that `Utils::HmacValidator` verifies only signs the raw request body (`to_signable_string` returns `@raw_body`). The shop-domain value is never bound into the signature, so the cryptographic proof "this request came from Shopify for our app" is decoupled from "this request is about shop X." An attacker who legitimately controls a shop (any unprivileged internet user can install a public app on their own free/dev store) receives real webhooks with valid HMACs, then can replay that exact body/HMAC pair while substituting the `shop-domain` header for a victim shop, and the gem will report the payload as belonging to the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `to_signable_string` is only the raw body, and `shop` is read straight from an attacker-controlled header with no signature coverage at all: [2](#0-1) 

`Registry.process` validates only the HMAC, then forwards `request.shop` verbatim to the handler as the tenant identity, with no cross-check against the body, topic, or any session store: [3](#0-2) 

Equality that should hold but doesn't:
`shop authenticated by HMAC == shop consumed by the handler`

In reality: `shop consumed by the handler` is taken from an unauthenticated header, while the HMAC only authenticates `(secret, raw_body)`. Any request with a `(body, hmac)` pair that is valid for *some* shop under the app's shared secret — including one an attacker legitimately obtained by installing the app on their own store and receiving a real webhook — will pass validation regardless of which `shop-domain` header value is attached.

### Impact Explanation
This breaks the tenant-identity binding at the point the gem hands data to the host application: `Registry.process` treats `request.shop` as authenticated once `HmacValidator.validate` passes, but that check never covers `shop`. A host app that trusts `WebhookMetadata#shop` (as the gem's documented API implies is safe once HMAC validation succeeds) can be made to attribute attacker-supplied body content (order data, customer data, GDPR redact requests, etc.) to an arbitrary victim shop identifier of the attacker's choosing. This is a cross-tenant data/identity confusion at the library boundary — the exact "shop authenticated vs. shop used as identity" analog called out for this bug class.

### Likelihood Explanation
Exploitability requires only: (1) the attacker installs the target app on their own store (any unprivileged user can do this for public apps), (2) the attacker captures one legitimate webhook (body + valid `X-Shopify-Hmac-Sha256`) sent to their own endpoint, and (3) the attacker resends that same body/HMAC pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header set to the victim shop. No access to `api_secret_key`, access tokens, or the app's `client_secret` is needed. The main mitigating factor is that this depends on the host application not independently validating the `shop-domain` header against a known/expected value (e.g., cross-referencing an existing session) — which the rules note should be treated cautiously ("Reject analogs that depend on the host application ignoring this gem's documented API"). However, the gem itself provides no API to bind `shop` into the signature check, so any consumer following the documented `HmacValidator.validate` + `Registry.process` flow is exposed by design.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string used for webhook HMAC validation, or expose an explicit API that requires callers to supply the expected shop and have `Registry.process`/`HmacValidator` fail closed if the header-derived shop doesn't match. At minimum, document prominently that `Webhooks::Request#shop` is not authenticated by the HMAC and must be independently verified by the host application before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), causing Shopify to POST a body `B` with header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's real shared secret) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but replaces the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`, per: [4](#0-3) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, per: [5](#0-4) 
5. The host application processes attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
