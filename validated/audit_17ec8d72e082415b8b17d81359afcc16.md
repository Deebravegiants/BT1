### Title
Operator QR-code authorization is fully bypassed when the QR-code self-declares a "signup extension" flag, allowing an unprivileged operator/user to skip backend authorization - (File: `src/plans/mod.rs`)

### Summary
`verify_operator_qr_code` is the function that is supposed to authenticate an operator QR-code against the backend before an operator is trusted to run a signup. It short-circuits this backend check whenever the QR-code data has `signup_extension() == true`, and simply fabricates a "valid" result with dummy location data. [1](#0-0) 

The `signup_extension` flag is not something the backend attests to - it is a field parsed directly out of the QR-code string itself, using a client-side regex (`QR_CODE_SIGNUP_EXTENSION`), gated behind the `internal-data-acquisition` feature (a real, shippable Cargo feature, not `#[cfg(test)]`-only). [2](#0-1) [3](#0-2) 

This is the same bug class as the `TribeRedeemer` report: a safety/authorization gate is meant to depend on trusted external state (there, the token balance funded by the DAO; here, a backend-verified "is this a legitimate operator" check), but the gate can be trivially satisfied by data fully controlled by the untrusted party presenting it (there, tokens sent by an attacker; here, a self-declared flag inside the scanned QR-code string).

### Finding Description
`do_signup`/`scan_remaining_qr_codes` call `verify_operator_qr_code` on every scanned operator QR-code before granting operator authority for the session: [4](#0-3) 

```rust
async fn verify_operator_qr_code(...) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
    if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
        return Ok(Some((0, backend::operator_status::LocationData { ... })));
    }
    ...
}
```

`qr_code.signup_extension()` simply returns a boolean parsed from the raw QR text: [5](#0-4) 

That boolean is set to `true` by `Data::from_signup_extension`, which is invoked purely because the scanned string matched a client-side regex (`QR_CODE_SIGNUP_EXTENSION`) - no server-side verification of the QR-code's authenticity or of the presenter's operator status occurs in this path: [6](#0-5) [3](#0-2) 

Because `signup_extension` is entirely attacker-controlled (anyone can print/display a QR-code encoding `userid:<id>:<policy>::<mode>::`), any person - not just an authorized operator - can present such a code to the orb and have `verify_operator_qr_code` treat them as a fully validated operator, bypassing the real backend check (`backend::operator_status::request`) that would otherwise confirm operator legitimacy and location. This is structurally identical to the external report's flaw: a protective check ("balance != 0" there, "backend says operator is valid" here) is satisfied by state the untrusted party fully controls, defeating the intended guard.

The consequence is amplified downstream: when the resulting session carries a `signup_extension_config`, the master signup flow (`do_signup`) skips the entire biometric fraud-check pipeline and marks the signup as successful without running the identification pipeline: [7](#0-6) 

So a spoofed "operator" QR-code not only bypasses operator authorization, it can also be paired with a matching self-declared "signup extension" user QR-code to route the whole signup around fraud detection.

### Impact Explanation
An unprivileged party can impersonate an authorized operator by crafting a QR-code with a self-declared "extension" marker, bypassing the intended backend-verified operator authorization step. Depending on how downstream logic treats "operator-authorized" sessions (location trust, consent for handling data-acquisition/underage flows, and skipping fraud/pipeline checks per the `debug_report.signup_extension_config.is_some()` fast-success path), this can lead to unauthorized signup handling and fraud/liveness-check bypass without ever touching the legitimate backend validation service.

### Likelihood Explanation
Exploitation requires: (1) the orb build to have the `internal-data-acquisition` feature enabled (a real, non-test feature used for production data-acquisition orbs), and (2) the attacker to be physically in front of the orb able to present a printed/displayed QR-code during the operator-scan phase. There are no cryptographic or backend checks blocking a crafted QR-code from matching the client-side `QR_CODE_SIGNUP_EXTENSION` regex, so the bypass condition is trivially reachable whenever the feature is compiled in. Likelihood is moderate: it depends on this feature flag being present on the target orb fleet, which I could not confirm from the index alone (visibility into build/deployment configuration is limited).

### Recommendation
Never let a purely client/QR-supplied flag (`signup_extension`) substitute for a genuine backend authorization response. `verify_operator_qr_code` should always perform (or require a valid, previously cached) backend `operator_status::request` verification regardless of the `signup_extension` flag; the "skip backend call" shortcut should be restricted to explicit local/CLI testing paths (e.g., only when `operator_qr_code_override` is set from a trusted CLI argument), not to attacker-controlled QR-code content.

### Proof of Concept
1. Build/run an orb configuration with the `internal-data-acquisition` feature enabled.
2. Generate an arbitrary QR-code with the text `userid:<any-uuid-like-string>:1::0::` (matches `QR_CODE_SIGNUP_EXTENSION`), see [2](#0-1) .
3. Present this QR-code to the orb during "Operator QR-code scanning".
4. `handle_magic_operator_qr_code`/`verify_operator_qr_code` is invoked; since `qr_code.signup_extension()` is `true`, the function returns `Ok(Some(...))` immediately without ever calling `backend::operator_status::request`, granting the presenter operator authority for the session, as shown at [8](#0-7) .

    /// Checks if `qr_code` is a valid operator QR-code through the backend.
    #[allow(clippy::cast_possible_truncation)]
    async fn verify_operator_qr_code(
        &self,
        orb: &mut Orb,
        qr_code: &qr_scan::user::Data,
        qr_capture_start: Instant,
    ) -> Result<Option<(u64, backend::operator_status::LocationData)>> {
        if qr_code.signup_extension() || self.operator_qr_code_override.is_some() {
            return Ok(Some((0, backend::operator_status::LocationData {
                team_operating_country: "DEV".to_string(),
                session_coordinates: Coordinates { latitude: 0.0f64, longitude: 0.0f64 },
                stationary_location_coordinates: None,
            })));
        }
        let http_start = Instant::now();
        match backend::operator_status::request(qr_code).await {
            Ok(backend::operator_status::Status { valid: true, location_data, reason: _ }) => {
                let location_data = location_data
                    .expect("to always have a result from the backend if valid == true");
                orb.ui.qr_scan_success(QrScanSchema::Operator);
                dd_incr!("main.count.global.distr_code_validated");
                tracing::info!("Operator QR-code validated: {qr_code:?}");
                dd_timing!("main.time.signup.distr_qr_code_capture", qr_capture_start);
                return Ok(Some((http_start.elapsed().as_millis() as u64, location_data)));
            }
            Ok(backend::operator_status::Status { valid: false, .. }) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
                dd_incr!("main.count.signup.result.failure.distr_qr_code", "type:invalid_qr");
            }
            Err(_) => {
                orb.ui.qr_scan_fail(QrScanSchema::Operator);
            }
        }
        Ok(None)
    }
