### Title
Webhook shop identity spoofing via HMAC binding gap - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` never covers the `x-shopify-shop-domain` / `shopify-shop-domain` header. That header is nonetheless trusted as the tenant identity and handed straight to the app's webhook handler, breaking the binding `authenticated_bytes == acted_upon_shop`.

### Finding Description
`Webhooks::Request#hmac` returns the decoded `hmac-sha256` header, and `#to_signable_string` returns `@raw_body` only: [1](#0-0) [2](#0-1) 

`Registry.process` validates the request purely through this HMAC, then immediately trusts `request.shop` (sourced from the `shop-domain` header) as the tenant identifier passed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever verify `verifiable_query.to_signable_string` (the body) against the secret — the shop header is never part of the signed material: [4](#0-3) 

Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly folds `shop` into the signed params so the OAuth callback's shop claim is bound to the HMAC: [5](#0-4) 

No equivalent binding exists for webhooks. Because a single `api_secret_key` (`Context.api_secret_key`) is shared across every shop that installs the app, any shop that has installed the app can legitimately receive its own valid `(raw_body, hmac)` pair from Shopify for its own events. An unprivileged user who controls their own store installation can capture that legitimate pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `Registry.process` still finds `Utils::HmacValidator.validate(request)` to be `true` (the body/HMAC pair is genuine), and dispatches to the handler with `WebhookMetadata.new(... shop: request.shop ...)` carrying the attacker-chosen shop value: [6](#0-5) 

The binding that should hold is: `hmac_verified(bytes) => shop_claim(bytes) == shop_domain(bytes)`. Here the equality collapses to `hmac_verified(raw_body) ⇏ shop_header trustworthy`, since the shop header is disjoint from the signed bytes.

### Impact Explanation
Any application built on this gem that keys per-tenant behavior off `WebhookMetadata#shop` (e.g., loading the correct shop's session/access token, writing incoming order/inventory data against the wrong tenant's records, or triggering tenant-scoped side effects) can be made to process data under an attacker-chosen shop identity while the HMAC check reports success. This is a cross-tenant identity confusion primitive: the attacker cannot forge arbitrary payload content (they don't have `api_secret_key`), but they can attribute a genuine payload—content and all—to any shop of their choosing, including shops they have never had access to. This matches the "cross-tenant access" Critical impact class since the gem itself asserts request integrity via `Utils::HmacValidator.validate` and hands the caller a `shop` field implied to be equally trustworthy, when it is not derived from or bound to the verified bytes.

### Likelihood Explanation
The attacker only needs to be an ordinary merchant who has installed the target app on their own store (an "unprivileged internet user" relative to any other tenant) — this satisfies the analog rules' bar of not requiring `api_secret_key`, an access token, or any privileged credential belonging to the victim. Capturing one's own legitimate webhook and replaying it with a modified header requires no cryptographic material beyond what Shopify already sent them.

### Recommendation
Bind the shop-domain header into the signed material verified by `Utils::HmacValidator`, e.g. by having `Webhooks::Request#to_signable_string` incorporate the shop/topic/webhook-id headers (mirroring how `AuthQuery#to_signable_string` binds `shop`), or by independently verifying that `request.shop` matches an actively-installed/authorized shop before invoking the handler, rather than passing the header value through unchecked in `Registry.process`.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`; wait for Shopify to send a legitimate webhook — this arrives with a real `raw_body`, `x-shopify-hmac-sha256`, and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. In `Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only ever hashed `raw_body`, unaffected by the header change (`lib/shopify_api/webhooks/request.rb:35-43`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:196-200`), even though the payload never originated from that shop — demonstrating the identity-binding gap.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
