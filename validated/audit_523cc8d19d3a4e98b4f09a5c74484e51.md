Based on my research, the closest analog is the weighted-median price mechanism in `aggregatePhantomBids`, where a bid's influence over the published price is proportional to a live, unprivileged, self-controlled ERC-20/vault balance read via `eth_call` — structurally identical to the reported bug's reliance on a manipulable `currentTokenSupply()` to gate an outcome.

### Title
Phantom-order price snapshot can be skewed by a solver flash-inflating its own on-chain balance before the weighted-median aggregation reads it - (File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts)

### Summary
`aggregatePhantomBids` weights every solver's quoted leg price by that solver's own live ERC-20/vault balance on the destination chain (`getBalance`, backed by `getTotalSolverBalance`/`memoizedSolverBalance`), then feeds those weights into `weightedMedian` to pick the leg's published price. Because the balance is read via a plain `eth_call` at aggregation time rather than pinned to a trust-minimized, pre-committed snapshot, a solver can transiently and permissionlessly inflate its own weight (e.g. via a flash mint/borrow of the output token, or a temporary self-transfer) for the single block in which the RPC read occurs, exactly as `currentTokenSupply()` could be gamed to swing a governance threshold in the original report.

### Finding Description
`weightedMedian` documents itself as a *selection*, not a blend: "a solver holding over half the leg's weight sets the published price verbatim" [1](#0-0) . The weight itself is computed by summing a live balance read plus any V4 position value, with no minimum holding period or historical check: [2](#0-1) . The comparable design intent is explicit in the docstring for `weightedMedian` itself: "Each quote's influence is proportional to `weight` — the solver's total balance for the output token across native + vault venues — so a solver that can actually deliver size moves the price more than one quoting on thin liquidity," and the same comment warns that with an all-zero-weight set "the median becomes whoever quoted higher, settable by a solver holding no inventory at all" [3](#0-2) . This shows the authors treated "weight = balance" as equivalent to "capital committed," but the balance read (`ethCallUint`/`getBalance`) has no mechanism to distinguish capital that is genuinely locked from capital borrowed and returned within the same transaction/block — the same class of flaw as using an instantaneous `totalSupply()`/`currentTokenSupply()` read to gate a threshold decision, as described in the external report.

### Impact Explanation
The resulting `medianPrice` per leg feeds directly into `PhantomPriceSnapshot` and then `updateLiquidityPools`, which turns it into the pool's published `sellRate`/`buyRate` [4](#0-3) . A solver that transiently inflates its own balance for the read can force its own (potentially unfavorable-to-users) quoted price to become the sole published rate for that leg, since the median selects one bidder's exact price rather than an aggregate. Because downstream consumers (route pricing, other solvers deciding whether to compete, and later fills priced off this pool rate) treat that rate as trustworthy liquidity-weighted market data, this allows one solver to unilaterally and cheaply set the market rate other participants act on, extracting value from counterparties who fill against the manipulated rate.

### Likelihood Explanation
Any account can act as an intent solver/bidder — no privileged role is required to submit a phantom bid and have it aggregated. The balance read happens over a plain `eth_call` at whatever "latest" block the indexer processes at snapshot time; a solver holding a large token balance only momentarily (via a flash loan, flash mint capability, or a coordinated wrapped/liquid-staking token as called out in the original report's asset classes) faces no additional cost beyond gas and loan fees to dominate its own leg's weight for that read.

### Recommendation
Do not rely solely on an instantaneous live balance read as bid weight. Consider requiring balance to be observed consistently across multiple blocks/reads before it counts fully toward weight, weighting by a time-averaged balance, or capping how much a single solver's balance can influence the median regardless of size (e.g., a per-solver weight cap), mirroring the "avoid using a manipulable spot value; use min/max over a window" recommendation from the original report.

### Proof of Concept
1. Solver `S` holds negligible real balance of leg output token `T` on destination chain `C`.
2. In the same block the indexer's `handlePhantomOrderPrices` handler is expected to run its `eth_call` snapshot (triggered off `PhantomBidWindowExhausted`), `S` flash-mints/borrows a large amount of `T` into its own address (or into an ERC-4626 vault counted by `getTotalSolverBalance`).
3. `aggregatePhantomBids` reads `S`'s balance via `getBalance`/`ethCallUint` [5](#0-4)  and assigns it as `S`'s weight for the leg.
4. `weightedMedian` sees `S`'s cumulative weight cross the 50% threshold and returns `S`'s quoted price verbatim [6](#0-5) .
5. `S` repays the flash loan/burns the minted tokens after the read. The published `medianPrice` for that leg is now `S`'s chosen price, feeding into the pool's `sellRate`/`buyRate` used for subsequent order routing.

```typescript
// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
```

```typescript
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
```

```typescript
async function ethCallUint(evmRpcUrl: string, to: string, data: string, blockTag = "latest"): Promise<bigint> {
	const result = await rpcCall(evmRpcUrl, {
		id: 1,
		jsonrpc: "2.0",
		method: "eth_call",
		params: [{ to, data }, blockTag],
	})
	if (result.result === "0x") return 0n
	if (typeof result.result !== "string") {
		throw new PhantomRpcError(`eth_call returned no result for ${to} on ${evmRpcUrl}`)
	}
	return BigInt(result.result)
}
```
