### Title
Unbounded RAY index accrual permanently freezes oversized markets - (File: common/src/rates/index.rs)

### Summary

Interest accrual multiplies the market’s full scaled debt and supply books by their indexes using `Ray::mul`, but the global index cap is not adjusted for the market’s scaled principal. Once `scaled_amount * index / RAY` exceeds `i128::MAX`, accrual panics before any index can be committed. Because every market mutation synchronizes interest first, the market subsequently rejects repayment, withdrawal, liquidation settlement, recapitalization, and index updates, leaving user funds permanently frozen.

### Finding Description

`update_borrow_index` computes the new index and caps it only against the global `MAX_BORROW_INDEX_RAY`; it does not consider whether the resulting total debt remains representable in the RAY value domain. [1](#0-0) 

Immediately afterward, `calculate_supplier_rewards` computes `borrowed.mul(old_borrow_index)` and `borrowed.mul(new_borrow_index)`. Both products must fit into `i128`; if either does not, the typed math wrapper raises `MathOverflow` and aborts the call. [2](#0-1) 

The same failure exists on the supply side because `update_supply_index` computes `supplied.mul(old_index)` before it can commit a capped result. [3](#0-2) 

The pool’s `global_sync` applies every elapsed chunk and only calls `mark_accrued()` after all chunks complete. A panic in any chunk therefore rolls back the entire accrual and leaves `last_timestamp` in the past. [4](#0-3) 

Every pool leg loads a synchronized cache through `synced_market`, so all mutations hit the same arithmetic failure before their own logic runs. [5](#0-4)  Repayment calls `load_leg` before resolving or burning debt, and withdrawal calls `load_leg` before resolving or burning supply. [6](#0-5) [7](#0-6) 

The repository’s dedicated regression test demonstrates that a billion-token, 18-decimal market at 98% utilization reaches this RAY-value cliff before `MAX_BORROW_INDEX_RAY`, after which `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow`. [8](#0-7) 

### Impact Explanation

This causes permanent freezing of all funds in the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot settle positions, and permissionless bad-debt or recapitalization paths cannot proceed because each operation accrues first. The affected pool may still physically hold token balances, but its accounting paths can no longer operate.

The index cap does not prevent the state transition because representability is reached first: the overflow occurs when calculating total debt or supplied value, before the capped index is stored. The failed call is atomic, so the panic does not advance `last_timestamp` or provide partial progress.

### Likelihood Explanation

Reaching the condition requires an exceptionally large market principal, a high-decimal asset, sustained high utilization, and governance-configured caps large enough to admit that exposure. Those prerequisites reduce likelihood.

Nevertheless, all attacker-controlled actions use normal unprivileged flows:

1. `supply` deposits a very large amount.
2. `borrow` drives utilization high.
3. Ordinary time passage compounds the borrow index.
4. Anyone calls controller `update_indexes(caller, [HubAssetKey { hub_id, asset }])`.
5. The controller invokes pool `update_indexes`, which panics during accrual. [9](#0-8) 

No privileged call, oracle manipulation, malformed contract state, or leaked key is required after the market configuration admits the necessary principal.

### Recommendation

Enforce the representability bound before index accrual. At minimum:

- Derive per-market index ceilings from the current scaled books, such that both `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` remain below `i128::MAX`.
- Configure supply and borrow caps conservatively so their maximum scaled values cannot reach that bound before the global index caps.
- Detect impending value overflow before `calculate_supplier_rewards` and `update_supply_index`, cap the index below the unsafe value, and commit a safe state rather than reverting.
- Add a recovery path that can operate without full accrual if an existing deployment already approaches the boundary.

### Proof of Concept

1. Governance lists an 18-decimal market using the steep XLM-style rate curve and configures supply/borrow caps that permit at least `1e18` whole-token exposure.
2. An attacker or economically motivated whale supplies approximately `1_000_000_000 * 10^18` base units.
3. A borrower supplies sufficient collateral in another market and borrows approximately 98% of the large market.
4. Time passes at high utilization, causing the borrow index to compound until the debt’s RAY value approaches `i128::MAX`.
5. Any unprivileged account invokes controller `update_indexes` for that `HubAssetKey`.
6. Pool accrual computes `borrowed.mul(new_borrow_index)` or `borrowed.mul(old_borrow_index)` and aborts with `MathOverflow` before marking the market accrued.
7. Later `repay`, `withdraw`, `liquidate`, `recapitalize`, and further `update_indexes` calls repeat the same accrual-first path and fail identically.

The harness reproduces this exact sequence and confirms `update_indexes`, `withdraw`, and `repay` all fail while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [10](#0-9)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
