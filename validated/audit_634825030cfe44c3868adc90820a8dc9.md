### Title
Shared `CallDispatcher` residual token balances can be swept into an attacker's own order escrow during `placeOrder` predispatch - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder`'s predispatch flow sweeps the *entire current balance* of each `order.inputs[i].token` held by the shared `CallDispatcher` contract into the caller's own order escrow, rather than only the amount produced by that specific call's predispatch execution. Because `CallDispatcher` is a single, persistent, protocol-wide contract reused across every user's predispatch/postdispatch calls (and by `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution), any real token balance left sitting on it — whether from another user's incomplete sweep, un-listed dust from a prior predispatch swap, or bridged-token calldata execution — can be claimed by any later caller who simply names that token as one of their own order inputs.

### Finding Description
In `placeOrder`, when `order.predispatch.call` and `order.predispatch.assets` are non-empty, the contract builds sweep calls based on the token's *current total balance on the dispatcher*, not the delta attributable to the caller's own predispatch execution: [1](#0-0) 

```
uint256 balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({
    to: token,
    value: 0,
    data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
});
balancesBefore[i] = IERC20(token).balanceOf(address(this));
```

The full `balance` (not `requiredAmount`) is what actually gets transferred out of `dispatcher`: [2](#0-1) 

`_params.dispatcher` is a single, shared, stateless-by-convention contract deployed once and reused by every caller of `IntentGatewayV2` (predispatch and postdispatch) and by `HyperFungibleToken`/`WrappedHyperFungibleToken`, which route bridged-token calldata execution through it (docs explicitly describe minting tokens directly `to` the `CallDispatcher` so composed calls can spend them): [3](#0-2) 

`CallDispatcher` itself has no access control or per-caller isolation — it just executes whatever `Call[]` it's handed against its own balance: [4](#0-3) 

Because sweeps in `placeOrder` (and the analogous postdispatch sweep in `_execute`) only cover tokens explicitly listed in the *current* order's `inputs`/`output.assets`, any real token that ends up on the dispatcher outside of that list — e.g., a side-output of another user's predispatch swap, imprecise routing dust, or residual balance from an HFT calldata-execution mint — remains on the dispatcher indefinitely. A subsequent caller can then name that residual real token as one of their own `order.inputs`, set `amount` to the dispatcher's known on-chain balance, and have the entire amount attributed and escrowed to their own commitment: [5](#0-4) 

This is the same root-cause class as the Derby finding: a balance-based accounting check (`balanceOf` before/after) is used to attribute funds to the caller without verifying those funds were actually produced by the caller's own action in the current call, allowing funds that belong to someone else (here, residual/shared dispatcher balance) to be claimed.

### Impact Explanation
An attacker can permanently steal real ERC20 tokens (or ETH) that happen to be sitting on the shared `CallDispatcher` — funds that could originate from other users' unswept predispatch/postdispatch side-effects or from bridged-token (`HyperFungibleToken`) calldata execution — by crediting them to their own order escrow and then redeeming that escrow via a normal cancel (`_cancelSameChain`/cross-chain refund) or fill flow. This is direct, unauthorized theft of funds reachable from a single unprivileged `placeOrder` transaction.

### Likelihood Explanation
Exploitability depends on the `CallDispatcher` actually holding a nonzero real-token balance at the time of the attacker's `placeOrder` call. Given it is a single shared contract used across all `IntentGatewayV2` predispatch/postdispatch flows and all `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata deliveries, imprecise swap routing, partial calldata execution, or any order whose predispatch call incidentally produces a token not listed in that order's `inputs` will leave exploitable residue. An attacker only needs to monitor the dispatcher's public token balances and submit a normal order — no special privileges required.

### Recommendation
Do not sweep based on the dispatcher's total current balance. Instead, snapshot the dispatcher's balance of each relevant token *immediately before* executing the predispatch/postdispatch call and only sweep the delta produced by that specific call (mirroring the balance-before/after pattern already used for the non-predispatch path). Any balance already present on the dispatcher before the call must not be attributable to the current order. Additionally, ensure `_execute`'s dust sweep and the predispatch sweep cover the complete set of tokens the predispatch/postdispatch call could produce (or use per-call ephemeral dispatcher instances) so residue cannot accumulate and be attributed to unrelated future callers.

### Proof of Concept
1. User A places an order whose `predispatch.call` swaps ETH for token X via Uniswap, but `order.inputs` only lists token Y; token X lands on `CallDispatcher` and is never swept because it isn't in `order.inputs`/`output.assets`. (Or: an `HyperFungibleToken` cross-chain delivery mints token X directly `to` the `CallDispatcher` for a composed swap that doesn't fully consume it.)
2. Attacker observes `IERC20(tokenX).balanceOf(dispatcher) == R > 0` on-chain.
3. Attacker calls `placeOrder` with a trivial no-op `predispatch.call`/`predispatch.assets` (e.g., a 1-wei dummy asset and an empty `Call[]` payload, as shown in `testPlaceOrder_FeeOnTransferToken_Predispatch`) and `order.inputs = [{token: tokenX, amount: R}]`.
4. In `placeOrder`, `balance = IERC20(tokenX).balanceOf(dispatcher) == R >= requiredAmount`; the full `R` is transferred from `dispatcher` to the gateway and, since `received == order.inputs[i].amount`, credited entirely to the attacker's own commitment: [6](#0-5) 
5. Attacker cancels the order (same-chain refund path) to withdraw the escrowed `tokenX` directly to themselves, having stolen funds that belonged to another user's/protocol's residual dispatcher balance.

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
