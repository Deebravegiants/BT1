### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw webhook body, and `HmacValidator` verifies the HMAC solely against that body. The `shop` value, taken from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, is never included in the signed material. `Registry.process` trusts this unauthenticated `shop` value and passes it straight into the handler as the tenant identity, breaking the equality "shop authenticated by the HMAC == shop the payload is attributed to."

### Finding Description
`Request#hmac` and `Request#to_signable_string` bind the signature to `@raw_body` only: [1](#0-0) 

`Request#shop` is read directly from a header with no relation to the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC over the body, but then forwards `request.shop` (still unverified) as the tenant identity to the handler: [3](#0-2) 

Because the app's `api_secret_key` (client secret) is the same for every shop that installs the app, any authentic `(raw_body, hmac)` pair obtained from one webhook delivery — e.g. from a shop the attacker legitimately controls and has the app installed on — remains HMAC-valid no matter which `shop-domain` header is sent alongside it. The signature proves only "this body was signed with our app secret," not "this body belongs to shop X." An attacker can therefore replay a captured valid body+HMAC pair while substituting a victim's `shop-domain` header, and `Registry.process` will accept it as an authentic webhook for the victim shop, invoking the host application's handler with forged `WebhookMetadata#shop`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery: `shop` reaches host application code as trusted, HMAC-validated data, when it is in fact attacker-controlled. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up a shop's session/store record, gate GDPR `customers/redact`/`shop/redact` processing, or apply order/inventory changes), this enables cross-tenant confusion — data or actions intended for the attacker's own shop can be attributed to and processed against a victim shop record, and vice versa. This matches the Critical "cross-tenant access" impact category since the identity binding the host relies on (shop) is not actually authenticated by the cryptographic check the gem provides.

### Likelihood Explanation
Requires the attacker to have legitimate access to a shop (e.g., their own store) where the app is installed, so they can capture one authentic `raw_body` + `hmac-sha256` header pair from a real webhook delivery. Since the same `client_secret`/`api_secret_key` is shared across all shops using the app, that pair remains valid regardless of the `shop-domain` header sent. No access to the victim's credentials, session, or the app's secret is needed — only the ability to relay an HTTP POST to the app's webhook endpoint with a forged shop header, which is fully within an "unprivileged internet user" capability once they control any tenant of the same app.

### Recommendation
Bind the `shop` value into the verified material, e.g., include the `x-shopify-shop-domain` header (and other identity-bearing headers used downstream, like `webhook-id`/`api-version` if they affect trust decisions) in `to_signable_string`, or otherwise cryptographically bind shop identity to the payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that `shop` in `WebhookMetadata` is not authenticated by the HMAC and host apps must independently verify it corresponds to a shop with an active, matching session before acting on webhook contents.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header — both valid because they're signed with the app's shared `api_secret_key`.
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the body against the secret: [4](#0-3) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com`, even though the payload never originated from that shop: [5](#0-4) 
5. The host application processes attacker-supplied data as if it came from the victim shop.
