### Title
Panic/Trap via Unchecked `copy_from_slice` into Fixed-Size Signature Buffer in `From<Vote> for SignatureWithAuthorityIndex` - (File: evm/rust/src/conversions.rs)

### Summary
`pallet-beefy-consensus-proofs::submit_proof` accepts an unsigned/permissionless `PROOF_TYPE_NAIVE` proof, ABI-decodes it as `ismp_abi::ecdsa_beefy::BeefyConsensusProof` via `SolType::abi_decode_params`, and converts it into the internal SCALE representation using the `From` impls in `evm/rust/src/conversions.rs`. [1](#0-0)  One of those conversions, `From<Vote> for SignatureWithAuthorityIndex`, copies the Solidity `Vote.signature` field straight into a fixed 65-byte array with `copy_from_slice`, without first checking that the decoded byte length is exactly 65:

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        ...
    }
}
``` [2](#0-1) 

### Finding Description
This is the same bug class as the wolfSSL report: a length-unchecked copy of externally supplied data into a fixed-size buffer, where the source length is fully attacker-controlled. In the wolfSSL case, an oversized ECH config field overflowed a fixed stack buffer in `wc_HpkeLabeledExtract`. Here, `Vote.signature` in the Solidity ABI definition is a dynamic `bytes` field (per `SignedCommitment.votes: Vote[]` in `evm/src/consensus/Types.sol`), so `abi_decode_params` will happily decode a `Vote` whose `signature` field is any length — 0, 64, 66, or much larger. `Rust`'s `copy_from_slice` requires the source and destination slices to have identical lengths and panics (traps) otherwise, rather than corrupting memory the way a raw C buffer overflow would, but the security-relevant consequence is the same category: unchecked-length copy from fully attacker-controlled wire data feeding a fixed-size buffer on the message-processing path.

The call chain from an unprivileged, permissionless transaction is:
1. `BeefyConsensusProofs::submit_proof` (unsigned/any signer, no privilege) accepts raw proof bytes bounded only by `MaxProofSize`. [3](#0-2) 
2. `verify_and_apply` splits off the proof-type byte and ABI-decodes the remainder as `BeefyConsensusProof` for `PROOF_TYPE_NAIVE`. [1](#0-0) 
3. The decoded value is converted `.into()` a `beefy_verifier_primitives::ConsensusMessage`, which recursively invokes `From<SignedCommitment>` → iterates `votes: Vec<Vote>` → `From<Vote> for SignatureWithAuthorityIndex`, hitting the unchecked `copy_from_slice`. [2](#0-1) 

A signature field whose length is anything other than 65 bytes causes an immediate Rust panic inside `copy_from_slice`. In a Substrate/WASM runtime, an unhandled panic in a dispatched extrinsic aborts execution — this is exactly the pattern the codebase's own regression tests and comments elsewhere explicitly call out as dangerous ("a wasm trap reachable from untrusted input... in the runtime this is a wasm trap") and had already been fixed for `[u8; 4]` consensus-id parsing in `modules/ismp/core/src/host.rs` and `modules/utils/serde/src/lib.rs`, but the same defensive pattern was not applied here. [4](#0-3) [5](#0-4) 

### Impact Explanation
`submit_proof` is a permissionless extrinsic reachable by any account (per the referenced simtest, submitted with a normal signed transaction, not requiring privilege). [6](#0-5)  A crafted proof with a malformed `Vote.signature` length triggers a Rust panic deep in message-conversion code that runs inside `execute_with`/dispatch of the BEEFY consensus-update path — a route relied on for delivering all cross-chain messages secured by the BEEFY light client. If the panic is not caught by a `panic = "abort"`/unwind boundary appropriate for the runtime (Substrate runtimes typically wrap extrinsic execution to convert panics into transaction failures, but a trap inside WASM execution for certain panic configurations can still disrupt block execution or at minimum guarantee the extrinsic never validates cleanly, and any host/off-chain component built with `panic = "abort"` executing this same conversion code — e.g., the relayer/prover binary — would crash the process). This can be leveraged to reliably fail/DoS the BEEFY consensus-update dispatch path used to deliver ISMP messages, which is classified as "a route unable to deliver messages" impact.

### Likelihood Explanation
High. `PROOF_TYPE_NAIVE` requires no special conditions beyond a syntactically valid ABI encoding of `BeefyConsensusProof` with at least one vote whose `signature` bytes field has length ≠ 65 — trivial to construct and submit. The `abi_decode_params` call only validates ABI structural correctness, not field-level length invariants for dynamic `bytes` fields, so this input passes decoding and reaches the vulnerable conversion.

### Recommendation
In `evm/rust/src/conversions.rs`, validate `sig_bytes.len() == 65` before `copy_from_slice`, returning a `TryFrom`-style fallible conversion or filtering/rejecting non-conforming votes with an error propagated up through `verify_and_apply` (mapping to `Error::<T>::AbiDecodeFailed` or a new dedicated error), matching the pattern already used for `[u8; 4]` state-machine/consensus IDs elsewhere in the codebase.

### Proof of Concept
1. Construct a `BeefyConsensusProof` Solidity struct where `relay.signedCommitment.votes[0].signature` is set to a `bytes` value of length 64 (or any length ≠ 65).
2. ABI-encode it as `abi_encode_params` (matching `SP1Beefy.sol`/`EcdsaBeefy.sol` tuple-param encoding) and prefix with `PROOF_TYPE_NAIVE`.
3. Submit via `BeefyConsensusProofs::submit_proof(proof)` from any account, within `MaxProofSize`.
4. `verify_and_apply` decodes the payload successfully (ABI decoding does not check the `bytes` length against 65), then calls `.into()` which reaches `From<Vote> for SignatureWithAuthorityIndex::from` and panics at `signature.copy_from_slice(&sig_bytes)` due to length mismatch, rather than returning a clean dispatch error.
