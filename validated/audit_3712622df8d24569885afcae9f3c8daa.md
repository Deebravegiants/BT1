### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant shop-domain forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) . However, the `shop` value handed to the app's `WebhookHandler` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, a field that is never included in the signed string [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [4](#0-3) . The `shop` accessor, by contrast, is read directly from an unauthenticated header with no cryptographic binding to the HMAC at all [5](#0-4) .

`Registry.process` uses this same unauthenticated `request.shop` value to build the `WebhookMetadata` that is passed straight to the app-supplied handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [6](#0-5) . The gem's own documentation instructs app authors to treat `data.shop` as the authenticated tenant identifier for the webhook payload — e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` — reinforcing that host apps trust this field as bound to the signed body [7](#0-6) .

Equality that should hold but does not:
`shop bound by HMAC signature` == `shop delivered to WebhookHandler.handle`

Before attack: a legitimate webhook for shop A arrives with body B and header `shop-domain: A`; HMAC(B) is valid; handler receives `shop: "A"` correctly matching the signer of B.

After attack: an unprivileged internet user who has *any* means of observing one valid `(body, hmac)` pair (e.g., by installing the app on their own free/dev store and capturing the webhook their own store legitimately receives) can POST that exact same body+HMAC to the app's webhook endpoint, replacing only the `shopify-shop-domain` header with a victim shop domain `B`. `Utils::HmacValidator.validate` still returns `true` because it only checks `raw_body` against the secret [8](#0-7) , and `handler.handle` is invoked with `shop: "B"` even though shop B never sent or authorized this payload.

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler — which per the gem's documented contract is meant to trust `data.shop` as the shop that produced `data.body` — will process/act on data body attributed to an arbitrary victim shop domain chosen by the attacker. Depending on how the host application uses `data.shop` (e.g., to look up the victim's stored access token/session to perform work "on behalf of" that shop, or to write attacker-controlled data into the victim's tenant record), this can lead to cross-tenant access or data corruption using only a body the attacker legitimately received for their own shop.

### Likelihood Explanation
Reaching this requires only network access to the app's public webhook endpoint and possession of any single valid `(raw_body, hmac)` pair for the same app — trivially obtainable by any attacker who installs the target app on their own shop (free/dev store), since Shopify delivers real webhooks to real installs. No `api_secret_key`, access token, or privileged account is required, only crafting an HTTP request with a substituted `shop-domain` header value.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or independently verify that the shop-domain header corresponds to a shop that has an active, registered subscription/session for this app before dispatching to the handler, rather than trusting an unauthenticated header value that rides alongside a signature covering only the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggers an event (e.g., `orders/create`), and captures the resulting POST — raw body `B` and header `shopify-hmac-sha256: H` — sent by Shopify to the app's webhook endpoint.
2. Attacker replays this exact request to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` (keeping body `B` and header `H` unchanged).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => H})` is constructed [9](#0-8) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the secret [10](#0-9) .
5. `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed B, ...))` is invoked — the app now processes attacker-supplied event data as if it originated from and belongs to `victim.myshopify.com`.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|

          end
        end

          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @raw_body = raw_body
