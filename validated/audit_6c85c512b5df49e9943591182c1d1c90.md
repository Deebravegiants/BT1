### Title
Deferred `set`/`batchSet` calls resurrect stale/attacker state after `clear()` once `release()` fires - (File: libraries/deferring-storage/src/storage.ts)

### Summary
`DeferringStorage.clear()` executes immediately against the backing store, bypassing the lock/queue mechanism, while `set()` (and any other proxied method such as `batchSet`) awaits `this.#ready.promise` before writing. If a caller issues `set()`/`batchSet()` while storage is locked, then a `clear()` happens, and later `release()` is called, the previously-queued `set`/`batchSet` write executes *after* the clear, reintroducing the pre-clear value into storage.

### Finding Description
`DeferringStorage` wraps a backing `Storage` and defers most operations until `release()` resolves an internal `pDefer()` promise (`#ready`) [1](#0-0) . The explicit `set` method awaits `#ready.promise` before calling `this.#storage.set(key, value)` [2](#0-1) . Any other storage method not explicitly overridden, including `batchSet`, is deferred the same way via the Proxy `get` trap, which wraps async functions to `await this.#ready.promise` before delegating to the underlying storage [3](#0-2) .

In contrast, `clear()` is defined to call `this.#storage.clear()` directly, with no wait on `#ready` [4](#0-3) , a behavior explicitly confirmed by the existing test "does not defer clearing" [5](#0-4) .

This creates an ordering hazard: a `set(key, value)` call made while storage is locked is suspended at the `await` and has not yet written anything. If `clear()` is invoked next, it wipes the store immediately. When `release()` is eventually called (resolving `#ready`), the previously suspended `set` continues executing and writes its (now stale) value into the store — after the wipe took effect. Sequence: `set('key', v)` (suspends) → `clear()` (wipes now) → `release()` (resumes `set`, writes `v`) → final store state contains `v`, not the cleared state. The existing test suite only verifies that deferred calls flush after `release()` in isolation and that `clear()` is not deferred; it does not test the interleaving of a pending `set`/`batchSet` with an intervening `clear()`, so this ordering issue is unguarded by any code in the file.

Whether this is reachable by an "unprivileged" external attacker depends on the concrete adapter wiring `DeferringStorage` around a security-sensitive namespace (e.g., a trusted-origins/permissions store) and on whether that specific caller path allows an attacker to trigger `set`/`batchSet` while storage is locked. Searching the repository, `DeferringStorage` usage is limited to SDK app scaffolding, headless SDK migration tests, and the `atoms` library factory [6](#0-5) ; no usage tying it to a `trustedOrigins`/permission store or any remote-config/dapp-controlled write path was found in this codebase (no matches for `trustedOrigins` at all). Without a concrete call site that (a) exposes `set`/`batchSet` to untrusted/remote-config input, (b) locks storage at the time of that write, and (c) later calls `clear()` for a security wipe followed by `release()`, this is a latent design flaw in the library rather than a demonstrated wallet-compromise path from ordinary dapp/origin input as required by the rules.

### Impact Explanation
If such a wiring existed, the impact would be reintroduction of attacker-controlled trust/permission state immediately after an intended security wipe (e.g., resurrecting a malicious trusted-origins list right after a logout/reset), which would match a privilege-persistence / auth-bypass class impact. However, no such wiring was found in this repository, so the scoped impact could not be confirmed as reachable from ordinary dapp/origin requests, deeplinks, remote config, or RPC calls.

### Likelihood Explanation
The mechanical race exists in the code as written and is fully reproducible in isolation with a mocked backing store, and is not dependent on any test/mock-only artifact. Real-world exploitability depends entirely on an as-yet-unidentified consumer that (1) locks `DeferringStorage`, (2) allows an attacker to call `set`/`batchSet` on it pre-release, and (3) subsequently calls `clear()` for a security-relevant reset before `release()`. That consumer was not located in this codebase.

### Recommendation
Have `clear()` also respect the `#ready` gate (await it, or alternatively make it also cancel/discard any pending deferred writes) so that clearing always represents the terminal state, or make `set`/`batchSet`/`clear` share a single ordered queue rather than treating `clear()` as an immediate side-channel operation.

### Proof of Concept
```ts
test('clear() can be resurrected by a pending set() once release() fires', async () => {
  deferringStorage.set('trustedOrigins', ['attacker.evil'])
  deferringStorage.clear()
  await new Promise(setImmediate)
  expect(storage.clear).toHaveBeenCalled()

  deferringStorage.release()
  await new Promise(setImmediate)

  // Vulnerable: the pre-clear write is applied after clear()
  expect(storage.set).toHaveBeenCalledWith('trustedOrigins', ['attacker.evil'])
})
```
Expected (secure) behavior: `storage.set` should not fire post-clear with pre-clear data, or the final observable state (via a real in-memory `Storage` implementation) should reflect the clear, not the stale queued value.

```typescript
export class DeferringStorage<In, Out> {
  readonly #ready = pDefer()
  readonly #storage: Storage<In, Out>

  constructor(storage: Storage<In, Out>, ready = pDefer()) {
    this.#storage = storage
    this.#ready = ready

    return new Proxy(this, {
      get: (target, prop: keyof DeferringStorage<In, Out>) => {
        if (prop in target && typeof target[prop] === 'function') {
          return (...args: [never, never]) => target[prop](...args)
        }

        if (typeof this.#storage[prop as keyof Storage] === 'function') {
          return async (...args: [never, never]) => {
            await this.#ready.promise
            return this.#storage[prop as keyof Storage](...args)
          }
        }

        return this.#storage[prop]
      },
    })
```
