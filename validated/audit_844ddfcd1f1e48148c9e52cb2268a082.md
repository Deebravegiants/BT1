### Title
No Account Lockout / Rate Limiting on Mobile PIN Verification - (File: features/auth-mobile/module/auth.js)

### Summary
The `@exodus/auth-mobile` feature module, which implements PIN-based authentication gating access to the wallet on mobile, exposes an `isCorrectPin` method that performs an unthrottled equality check against the stored PIN with no attempt counting, delay, or lockout mechanism.

### Finding Description
`isCorrectPin` simply fetches the stored PIN secret from the keystore and does a strict string comparison against user input, returning a boolean with no state tracking of failed attempts: [1](#0-0) 

The PIN itself is fixed at exactly 6 digits (`value.length !== 6` throws `InvalidPasscodeLengthError`), meaning the full keyspace is only 10^6 combinations: [2](#0-1) 

There is no companion logic anywhere in the module — no failed-attempt counter, no exponential backoff, no temporary lockout state stored in the keystore or `authAtom` — before or after a failed `isCorrectPin` call is exercised in the shipped tests [3](#0-2) . The auth constants file, which enumerates all keystore keys used by this feature (PIN, bio-auth, device-auth, and their trigger keys), contains no lockout/attempt-counter key either [4](#0-3) . A grep across the module and its tests for `attempts`, `lockout`, `maxAttempts`, `rateLimit` found zero occurrences in the mobile auth path, confirming no such control exists at this layer.

This mirrors the reported bug class: weak short credential (6-digit numeric PIN, a fixed low-entropy secret analogous to the reported 4-character minimum password) combined with the complete absence of a lockout/rate-limiting safeguard against repeated guessing, exactly as described in the external HAL-10 report for the mobile app's passcode setup flow.

### Impact Explanation
On a device where an attacker has repeated or sustained access to the unlocked app UI (e.g., shared/unattended device, or a malicious app/automation driving UI input), the lack of any lockout allows unlimited PIN guesses against a 6-digit (10^6) keyspace, which is programmatically guessable in a bounded number of attempts if no external OS-level throttling exists. Because `shouldAuthenticate`/`hasPin` gates access to "protectworthy resources such as the mnemonic phrase" per the module's own documentation, a successful guess directly exposes the wallet's secret recovery phrase and signing capability — a direct wallet-compromise impact [5](#0-4) .

### Likelihood Explanation
Exploitation requires local/physical or automated UI-level access to the unlocked app surface where the PIN prompt is repeatedly presented (e.g., shared device, lost/stolen device, or a compromised automation layer able to invoke the PIN-entry flow programmatically). This is a real but constrained threat model — it does not work remotely over network — consistent with the original report's moderate likelihood rating for a lockout-policy gap.

### Recommendation
Add attempt tracking to the `Auth` class in `features/auth-mobile/module/auth.js`: increment and persist a failed-attempt counter on each unsuccessful `isCorrectPin` call, enforce a lockout window (e.g., temporary disablement) after a small number of consecutive failures (e.g., 5), and apply progressive delay between attempts. Reset the counter on success. Consider increasing minimum PIN length/complexity options beyond the fixed 6-digit numeric scheme for higher-value setups.

### Proof of Concept
```js
// features/auth-mobile/module/auth.js
isCorrectPin = async (input) => {
  const pin = await this.#keystore.getSecret(this.#key(AUTH_KEYSTORE_PIN_KEY))
  return !!pin && pin === input
}
```
An attacker with repeated access to the PIN-entry surface can call this path with all 10^6 combinations (`000000`–`999999`); nothing in `auth.js` or `constants.js` tracks failures or throttles retries, so every guess is processed identically regardless of prior failed attempts [1](#0-0) .
