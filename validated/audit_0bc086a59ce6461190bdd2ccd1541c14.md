### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler as the tenant/event identity are read directly from unauthenticated HTTP headers. The equality that should hold — "bytes verified == bytes that determine tenant identity" — is broken: the HMAC verifies only `@raw_body`, but the `shop` field used to route and label the delivered data to a specific merchant is never part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are not part of the signed string at all: [3](#0-2) 

`Registry.process` then verifies the HMAC and immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` that is handed to the app's handler as the record of "which shop/topic this payload belongs to": [4](#0-3) 

Contrast this with the OAuth callback path, where `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, so the shop value that is later trusted is provably bound to the signature: [5](#0-4) 

This asymmetry means the gem's own webhook-processing code, not a documented API-misuse by the host app, permits the "shop header" and "body" to disagree without detection. An unprivileged actor who is themselves a legitimate (even single-store, free-trial) installer of the same app receives real webhook deliveries from Shopify with valid HMACs for their own store. Because the signature covers only the JSON body — never the `X-Shopify-Shop-Domain` header — that same signed body/HMAC pair can be replayed to the app's public webhook endpoint with the `Shop-Domain` header rewritten to name an arbitrary victim shop. `HmacValidator.validate` will still pass (the body bytes and secret are unchanged), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop sent that payload.

### Impact Explanation
This is a cross-tenant identity-binding break inside the gem itself: the field the gem asserts is "verified" (the body) is disjoint from the field the gem asserts is "the shop" (the header). Any host application that follows the documented `Webhooks::Registry.process` / `WebhookHandler#handle(data:)` contract and uses `data.shop` to select which merchant's records to read or write — the officially intended use of `WebhookMetadata#shop` — inherits cross-tenant data confusion: attacker-controlled shop labeling on genuinely-HMAC-valid webhook traffic. Depending on the handler's logic this can drive cross-tenant reads/writes keyed by `data.shop`, satisfying the "cross-tenant access" bar.

### Likelihood Explanation
The attacker only needs to be an ordinary installer of the target app on their own (attacker-controlled) shop — no leaked secrets, no privileged account, and no TLS interception are required. Webhook endpoints are public HTTP endpoints by design, and Shopify's own webhook delivery already gives the attacker one perfectly valid `(body, hmac)` pair for their own store on every event; they need only replay it with a rewritten `X-Shopify-Shop-Domain` header. The gap is structural (built into `Request#to_signable_string`), not a misconfiguration, so it applies to every app built on this gem's documented webhook flow.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the signed material verified against the HMAC, or independently authenticate the `shop` header (e.g., cross-check it against a shop that is already known/authorized for the given `webhook_id`/topic via the Admin API) before constructing `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should be changed so the value trusted as tenant identity is provably part of what `HmacValidator` verifies, mirroring how `Auth::Oauth::AuthQuery` binds `shop` into its signable string.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (ordinary, unprivileged installation).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some JSON body `B`.
3. Attacker captures this exact request, then re-sends it to the same endpoint but rewrites the header to `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and the HMAC header byte-for-byte identical.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` (unchanged) and it matches — validation passes (`lib/shopify_api/webhooks/request.rb` lines 35-38, `lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-controlled `shop` header value `victim.myshopify.com` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), and hands it to the app's handler as if Shopify itself asserted this data belongs to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
