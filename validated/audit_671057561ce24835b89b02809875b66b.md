Audit Report

## Title
Missing `return` after failed email-claim extraction allows session creation to proceed despite input validation failure - (File: core/sessions/oidcauth/oidc.go)

## Summary
In `handleTokenExchange`, the `email, ok := claims["email"].(string)` type-assertion failure branch logs an error and writes an HTTP 500 body via `c.String()` but does not `return`, unlike every other error branch in the same function. [1](#0-0)  Because `c.String()` in gin only buffers a response and does not abort request handling, execution falls through into role mapping, `oidc_sessions` row insertion, session-cookie establishment, and a final `c.JSON(http.StatusOK, ...)` that overwrites the earlier 500 body — resulting in a 200 success response and an authenticated session being created with an empty `email` value.

## Finding Description
Every other failure branch in `handleTokenExchange` — JSON bind failure, state mismatch, token exchange failure, missing `id_token`, ID-token verification failure, claims-parse failure, and `ExtractIDClaimValues` failure — correctly calls `return` immediately after writing the error response. [2](#0-1)  The email-claim check breaks this pattern: it logs and writes a 500 body but omits `return`. [1](#0-0)  Execution then proceeds to `IDClaimsToUserRole`, the `INSERT INTO oidc_sessions` call using `strings.ToLower(email)` (empty string), the audit log call, `ginSession.Set`/`ginSession.Save()`, and finally `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})`. [3](#0-2)  None of these subsequent steps depend on `email`'s validity, so nothing else in the flow catches this failure. This is a genuine control-flow defect — the intended validation gate is not enforced due to a missing `return`, matching the described "incorrect return value upon failure of input validation" pattern.

## Impact Explanation
The practical effect is that an OIDC identity token lacking a string `email` claim (but otherwise validly signed by the configured/trusted provider and carrying group claims that satisfy role mapping) still results in a persisted `oidc_sessions` row with an empty `user_email`, an audit log entry (`AuthLoginSuccessNo2FA`) recording `email: ""`, and a successful `200 {"success":true}` response with a working session cookie. This is a real bug but its severity is bounded: role assignment is computed independently from `idClaims`/group claims and does not depend on `email` at all, so the affected user must already possess a validly signed ID token from the trusted provider with group claims that map to a role — this is not a mechanism by which an attacker without valid IdP-issued, role-mapping credentials can obtain elevated access. The concrete consequence is degraded audit-trail integrity (blank email in `oidc_sessions` and audit logs) and an incorrect "success" response overwriting an internally-generated failure state, rather than a privilege escalation or authentication bypass for an otherwise-unprivileged party.

## Likelihood Explanation
Triggering this requires a caller to complete the full OIDC code/state exchange and present an ID token that is successfully signature-verified by `oi.provider.Verifier(...).Verify(...)` and whose claims satisfy `IDClaimsToUserRole`, yet lack a string `email` field. This depends on the configured identity provider's token content (e.g., email scope not requested, or a user profile without an email attribute) rather than attacker-supplied forgeable input, since the token is cryptographically verified against the trusted provider. It is a legitimate, reachable inconsistency for certain IdP configurations/user types, but it does not constitute privilege escalation from an unprivileged starting point — the actor must already be a legitimately authenticated principal with role-granting group membership.

## Recommendation
Add `return` immediately after `c.String(http.StatusInternalServerError, "Failed to get email from claims")` at line 229 in `core/sessions/oidcauth/oidc.go`, consistent with every other error branch in `handleTokenExchange`, so that session/role creation and the audit log entry cannot proceed with an invalid or missing email claim.

## Proof of Concept
1. Configure a test OIDC provider (or a test harness signing tokens with the node's trusted key/well-known config) to issue an ID token containing valid group claims that map to a role via `IDClaimsToUserRole`, but omitting the `email` claim (or setting it to a non-string value).
2. Complete the `/sessions/redirect` → provider login → `POST /sessions/exchange` flow with a valid `code`/`state`, routing to `handleTokenExchange`.
3. Observe: `oi.lggr.Errorf("Failed to get email from claims...")` fires and a 500 body is buffered, but the handler continues; a row is inserted into `oidc_sessions` with `user_email = ''`, `ginSession.Set(webauth.SessionIDKey, ...)` and `ginSession.Save()` succeed, and the final response is `HTTP 200 {"success":true}` with a valid, role-bearing session cookie — confirming continuation past the failed validation check.
