I found `evm/src/utils/CallDispatcher.sol` — this is the strongest reachable analog to the MarkUs "arbitrary file write" bug class. It dispatches attacker-controlled `bytes` decoded into arbitrary `(address to, uint256 value, bytes data)` calls with no allowlist, and it's invoked from `HyperFungibleToken.onAccept` / `WrappedHyperFungibleToken.onAccept` whenever an incoming cross-chain transfer message carries non-empty `data` — reachable by any token bridger sending a transfer with an arbitrary source-chain module as `from`, provided the source address passes `_supportedChains`/`expectedSource` checks.

### Title
Unrestricted arbitrary external call via `CallDispatcher.dispatch` triggered by incoming token-transfer calldata - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch` decodes an attacker-supplied `bytes` blob into an array of `Call{to, value, data}` and executes each with `to.call{value}(data)`, with no restriction on `to` or `data` beyond requiring `to` to have code. `HyperFungibleToken.onAccept`, `HyperFungibleTokenUpgradeable.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `WrappedHyperFungibleTokenUpgradeable.onAccept` all invoke `ICallDispatcher(_dispatcher).dispatch(message.data)` whenever an incoming cross-chain `Message` carries non-empty `data`, where `message` is fully decoded from the incoming `PostRequest.body` supplied by the counterparty chain's module. ### Finding Description
This is functionally the same bug class as CVE-2024-51743: a component intended to perform one bounded, benign action (dispatching calldata related to a token receipt) instead performs an arbitrary, attacker-directed action (`to.call(data)` at any address with any value/calldata) because the destination and payload are taken wholesale from untrusted, cross-chain-controlled input, with essentially no scoping analogous to a jailed upload directory. `CallDispatcher` itself has no caller restriction (no `onlyHost`/`onlyOwner` modifier), and any HyperFungibleToken deployment that wires `_dispatcher` to it will `delegatecall`-adjacent-equivalent execute arbitrary calls whenever a `Message.data` field is populated by the sender on the source chain, gated only by `expectedSource`/`_supportedChains` — a check on the *module id string*, not a cryptographic guarantee that the source module cannot embed arbitrary payload bytes. Since token-transfer messages are user/app-initiated (not governance-only, unlike the `HostManager`/`Execute` action paths that are explicitly gated per `docs/ai/flows/...`), any account able to dispatch a `Post` message from an approved source module can direct `CallDispatcher.dispatch` to call any contract with any calldata and any `msg.value` drawn from the dispatcher's own balance.

### Impact Explanation
If `_dispatcher` for a HyperFungibleToken deployment holds any ETH/ERC20 approval or is itself approved by other contracts to move funds (a common pattern for calldata-execution helper contracts), an attacker-controlled cross-chain message can drain or misuse those funds via arbitrary external calls, or interact with any protocol contract as the `CallDispatcher` address. This satisfies "unauthorized app action" and potential "theft ... of funds" if the dispatcher accumulates value.

### Likelihood Explanation
Likelihood depends on whether any deployed `CallDispatcher` instance is left holding value or approvals, and on whether `_supportedChains`/`expectedSource` binds tightly enough to prevent an attacker from becoming an accepted source module (e.g. by deploying their own contract on a chain and having governance whitelist it, or by compromising an already-whitelisted source module). Given `CallDispatcher.dispatch` has no access control of its own, exploitability is high once any value reaches the dispatcher contract, but the direct funds-loss path requires the dispatcher to hold assets, which is not guaranteed in the base deployment pattern shown in `receive() external payable {}`.

### Recommendation
Restrict `CallDispatcher.dispatch` to trusted callers only (e.g. `onlyHyperFungibleToken`/`onlyOwner`), and/or ensure the dispatcher contract is never left holding balances or approvals between transactions (sweep to zero, or use per-message ephemeral value passing rather than shared contract balance). Consider adding an allowlist of permitted `to` targets or forbidding native-value transfers (`call.value`) entirely from message-triggered calldata paths.

### Proof of Concept
1. Deploy `HyperFungibleToken` with `_dispatcher` pointed at a `CallDispatcher` instance that has received ETH (e.g. via its `receive()` fallback from prior calls).
2. From a source chain whose module id is whitelisted in `_supportedChains`, dispatch a `PostRequest` whose body decodes to a `Message` with `data` set to `abi.encode([Call({to: attacker, value: dispatcherBalance, data: ""})])`.
3. On delivery, `onAccept` mints the transferred amount to `beneficiary` and then unconditionally calls `ICallDispatcher(_dispatcher).dispatch(message.data)` — [4](#0-3) , which drains the dispatcher's balance to `attacker`.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
