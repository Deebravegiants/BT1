Confirmed: `timeout: 0` in `_post` (line 133) means the RedeemEscrow/RefundEscrow POST request never times out — there is no fallback path if `_withdraw` permanently reverts.

### Title
Atomic multi-token withdrawal loop in `IntentsBase._withdraw` permanently freezes escrowed funds when any single input token transfer reverts (e.g. blacklisted beneficiary) - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s cross-chain settlement path releases *all* of an order's escrowed input tokens to a beneficiary in one atomic loop inside `_withdraw()`. Unlike a hypothetical "safe" variant that lets a caller exclude problematic tokens, there is no partial-withdrawal or pull-based fallback: if any single token in the `WithdrawalRequest.tokens` array reverts on transfer to the beneficiary (denylist/blacklist token such as USDC/USDT, paused token, or a token that reverts on transfers to certain addresses), the entire `_withdraw` call reverts, and since the settlement message is dispatched with `timeout: 0` (never expires), there is no other code path to ever release the escrow.

### Finding Description
`_fillCrossChain` (`evm/src/apps/intentsv2/IntentsBase.sol` and `ExtrinsicIntents.sol`) dispatches a `RedeemEscrow`/`RefundEscrow` POST request back to the order's source chain with `timeout: 0`: [1](#0-0) 

On the source chain, `onAccept` authenticates the message and calls `_withdraw`, which loops over every escrowed token and unconditionally performs `IERC20(token).safeTransfer(beneficiary, amount)` for each in a single transaction: [2](#0-1) [3](#0-2) 

An order can escrow multiple distinct `TokenInfo` entries (`order.inputs`) as part of a single order. If the beneficiary (the solver who filled the order, or the user on refund/cancel) is blacklisted on even one of those ERC20s (a realistic condition for centralized stablecoins like USDC/USDT which have `blacklist`/`freeze` functionality, or any token that reverts transfers to certain addresses), `safeTransfer` reverts, unwinding the whole `_withdraw` call — including the transfers of the other, non-blacklisted tokens that would otherwise have succeeded.

Because the message was dispatched with `timeout: 0`, `pallet-ismp`/the EVM host never marks this request as timed out, so there is no alternate "refund" path — the request must be delivered via `onAccept` exactly as encoded, and `onAccept` will deterministically revert for every future relayer attempt. The escrowed tokens for that commitment become permanently unreachable: they can never be transferred out because `_withdraw` has no ability to skip the failing token or fall back to a pull-based claim, unlike the reported `ragequit`/`safeRagequit` pattern which explicitly allowed excluding problematic tokens from the batch.

This is structurally identical to the reported bug class: an unprivileged actor's push-based, all-or-nothing multi-asset withdrawal batch is completely blocked by one asset's transfer failure, permanently locking every asset in that batch (not just the problematic one) with no way to retry or exclude the bad token.

### Impact Explanation
This results in permanent freezing of funds: the full set of escrowed input tokens for the affected order commitment (potentially multiple distinct ERC20s and arbitrary amounts) becomes permanently stuck in the `IntentGatewayV2`/`ExtrinsicIntents` contract. Neither the user (on refund) nor the solver (on redeem) can ever recover their legitimate share, since:
- The dispatch has no timeout (`timeout: 0`), so no alternate code path exists.
- `_withdraw` has no per-token skip/pull mechanism.
- The order is not finalized (`_filled` isn't set until after the loop completes for `finalize=true` cases at the top of `_withdraw`, but the storage decrement for already-processed tokens in the same call is also reverted since the whole transaction reverts), so it also can't be retried differently or re-triggered through a different withdrawal path.

This qualifies as a Medium/High severity permanent freezing of funds in the Intent Gateway, reachable by any solver filling and being paid out via the escrow release path, or by a normal user whose refund happens to include a token on which they've been blacklisted.

### Likelihood Explanation
Likelihood is realistic but not trivial: it requires an order's input tokens to include one that supports a denylist (USDC, USDT, and similar) and the beneficiary address to be on that denylist at settlement time, either because the address was already blacklisted before filling, or is blacklisted between fill and settlement (a window that can span multiple blocks/chains, given cross-chain proof delivery times). It could also be intentionally triggered by a malicious order composition (a user/solver deliberately including in an order's inputs a token where they know the counterparty is/will be blacklisted, in order to grief-freeze the whole batch), which raises the practical likelihood above pure accident.

### Recommendation
Adopt a pull-based settlement pattern in `_withdraw`, analogous to the recommended fix for `ragequit`: on a transfer failure for any individual token, catch/skip that specific transfer (e.g. using a try/catch around the external call, or a low-level `call` with success checked per-token rather than a reverting `safeTransfer`), credit that token amount to an internal claimable balance for the beneficiary, and let the beneficiary (or anyone) call a separate `claim(token, beneficiary)` function later to attempt withdrawal again (e.g. once un-blacklisted, or to redirect to a different address). This decouples the success of one token's transfer from the others in the same `WithdrawalRequest`, preventing a single problematic asset from freezing the entire batch.

### Proof of Concept
1. User places a cross-chain order with `order.inputs = [USDC(1000), DAI(1000)]`, escrowing both tokens on the source chain via `placeOrder`.
2. A solver fills the order on the destination chain via `_fillCrossChain`; Hyperbridge relays a `RedeemEscrow` `WithdrawalRequest{ tokens: [USDC, DAI], beneficiary: solver }` back to the source chain with `timeout: 0`.
3. Before delivery lands on the source chain, the solver's address gets frozen/blacklisted on USDC (via Circle's blacklist function, a realistic and previously-exercised capability).
4. Any relayer calls `onAccept` on the source-chain `IntentGatewayV2`/`ExtrinsicIntents` contract with the valid proof; `_withdraw` loops `[USDC, DAI]`, and the `USDC.safeTransfer(solver, 1000)` call reverts because the solver is blacklisted.
5. The entire `onAccept` transaction reverts. Because `timeout` is `0`, this message can never expire; every future relayer submission of the exact same request will deterministically revert the same way.
6. Both the escrowed USDC and DAI for that commitment are now permanently locked in the gateway contract — the solver can never claim the DAI it is otherwise entitled to, and the user/protocol has no way to recover or redirect these funds. [4](#0-3) [1](#0-0) [5](#0-4)

     * any accumulated transaction fees (in the protocol fee token) are forwarded to the
     * beneficiary, and the appropriate event (EscrowReleased or EscrowRefunded) is emitted.
     *
     * When `finalize` is false (partial fills), only the proportional token amounts are
     * released without finalizing the order.
     *
     * @param body The withdrawal request containing the commitment, token amounts, and beneficiary.
     * @param isRefund If true, emits EscrowRefunded instead of EscrowReleased on finalization.
     * @param finalize If true, marks the order as complete and releases accumulated fees.
     */
    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
