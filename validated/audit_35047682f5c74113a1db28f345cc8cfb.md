### Title
Webhook `shop` domain is trusted without being covered by the HMAC signature, enabling shop-impersonation / cross-tenant webhook processing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the webhook's raw body only, then hands the handler a `shop` value taken directly from an HTTP header that is never covered by that signature. An attacker who can produce (or replay/relay) any validly-signed webhook payload for their own shop can rewrite the `X-Shopify-Shop-Domain` header to any other shop while keeping the body and HMAC untouched, and the gem will present the forged shop identity to the host application's handler as authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor instead reads straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)` — which internally recomputes the HMAC over `verifiable_query.to_signable_string`, i.e. the body only) and then, on success, immediately constructs `WebhookMetadata` using `request.shop` and passes it to the registered handler without any further binding check between the verified body and the claimed shop: [3](#0-2) 

The HMAC validator itself only ever compares a signature computed from `verifiable_query.to_signable_string` (the body): [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified bytes (body)` ≠ `field acted upon (shop header)`. Any party capable of obtaining one validly-HMAC'd webhook body/signature pair (e.g., from their own shop's genuine webhook deliveries, which they legitimately receive) can resend that exact body+HMAC with an arbitrary `shop-domain` header value. Because `Registry.process` never re-derives or cross-checks the shop against the signed content, the handler receives `WebhookMetadata#shop` set to the attacker-chosen value while `Utils::HmacValidator.validate` still reports success, since it only checked the body.

Host applications that rely on `WebhookMetadata#shop` (as documented and shown in tests) to route data into per-tenant storage will process/store attacker-controlled data under an arbitrary other tenant's shop domain, i.e., a cross-tenant write, and could also trigger the app to treat forged data as coming from a specific shop for actions such as data sync, uninstall handling, or GDPR data-erasure.

### Impact Explanation
Because the shop domain claim is unauthenticated relative to the HMAC signature that this gem verifies, an attacker who owns any Shopify shop with the app installed (and can thus generate a genuinely-signed webhook payload) can make the gem hand a host application a webhook body claiming to originate from a different shop of their choosing, since verification only covers the body, not the identity binding to the shop. This is a cross-tenant identity confusion within the gem's own webhook-verification contract.

### Likelihood Explanation
The `shop` header is fully attacker-controlled request metadata handed straight through by `ShopifyAPI::Webhooks::Request#shop`, and `Registry.process` performs no additional check tying it to the verified body; any actor able to deliver an HTTP request to the app's webhook endpoint with a genuinely-signed body (trivial for an attacker who has the app installed on their own store) can freely swap this header.

### Recommendation
Bind the shop identity into the value that is cryptographically verified — either include the shop domain in the HMAC-signable string used by `to_signable_string`, or have `Registry.process`/`HmacValidator` cross-verify the `shop` header against an independently-trusted source (e.g., require callers to supply/compare the expected shop, or validate that the topic+shop combination matches a previously registered webhook subscription) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a genuine webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid signature of `B`, computed via `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker resends the identical HTTP request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`.
4. `WebhookMetadata.new(shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"`, and the host application's handler processes/stores `B` as though it came from `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
