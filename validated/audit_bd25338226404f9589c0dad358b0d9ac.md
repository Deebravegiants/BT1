### Title
Overly Permissive CORS Wildcard-Origin Matching via Improper Domain-Suffix Check - ([File: core/services/gateway/network/httpserver.go])

### Summary
The Gateway's custom CORS allowlist implementation in `isAllowedOrigin` validates wildcard entries (e.g. `*.ethereum.org`) using `strings.HasSuffix` without enforcing a `.` boundary between the attacker-controlled prefix and the allowed suffix. This lets an attacker register a domain like `evil-ethereum.org` (no dot separator) and have it treated as a subdomain of the allowed origin `ethereum.org`, bypassing the CORS allowlist — the same overly permissive whitelist bug class as CVE-2017-14460.

### Finding Description
`isAllowedOrigin` strips the leading `*.` from a wildcard entry and then checks the incoming request's `Origin` host with a raw suffix comparison: [1](#0-0) 

Because `strings.HasSuffix(originHost, allowedHost)` performs a plain string-suffix test with no dot-boundary enforcement, any origin host that simply *ends with* the allowed domain string (not just true subdomains) is accepted. For example, if the operator configures `CORSAllowedOrigins = ["https://*.ethereum.org"]`, the stripped allowed host is `ethereum.org`, and an origin such as `https://evil-ethereum.org` (which is a completely unrelated, attacker-registered domain) will satisfy `HasSuffix("evil-ethereum.org", "ethereum.org")` and be granted `Access-Control-Allow-Origin` for that origin: [2](#0-1) 

This function is used directly by the gateway's request handler for every incoming HTTP request to the JSON-RPC-style user-facing endpoint, which is reachable by any unprivileged client/browser (analogous to the Parity JSON-RPC CORS whitelist issue in the report), and gates whether CORS headers reflecting the origin (with credentials-adjacent trust) are returned.

The gateway sample configs and integration tests confirm wildcard allowed-origin usage is a supported, expected configuration pattern (not an edge case): [3](#0-2) 

### Impact Explanation
If a node operator configures a wildcard `CORSAllowedOrigins` entry (a documented/supported pattern per the tests), an attacker who registers or controls a domain that merely ends with the allowed suffix (no subdomain dot required) can have their malicious site's origin reflected in `Access-Control-Allow-Origin`. Combined with a victim visiting the attacker's page, this enables cross-origin reads of gateway JSON-RPC responses intended only for the legitimate whitelisted domain — a request-impersonation / allowlist-bypass condition consistent with the reported bug class.

### Likelihood Explanation
Exploitation requires: (1) the operator to configure at least one wildcard entry in `CORSAllowedOrigins`, and (2) the attacker to register/control a domain string sharing the suffix without a leading dot (e.g. `notethereum.org` vs `*.ethereum.org`, or more plausibly a hyphenated lookalike like `evil-ethereum.org`). This is a realistic scenario for any deployment using a wildcard entry, since domain suffix collisions are cheap for an attacker to engineer, and no additional privilege is needed beyond convincing a victim's browser to send a request (matching the "victim visits a malicious website" precondition in the CVE).

### Recommendation
Fix the suffix check in `isAllowedOrigin` to require a `.` boundary before the matched suffix, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures only true subdomains (`sub.ethereum.org`) match, not arbitrary strings that merely end with the allowed suffix (`evil-ethereum.org`).

### Proof of Concept
1. Configure the gateway user server with:
```toml
CORSEnabled = true
CORSAllowedOrigins = ["https://*.ethereum.org"]
```
2. Send a request to the gateway's user-facing endpoint with header `Origin: https://evil-ethereum.org`.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("evil-ethereum.org", "ethereum.org")` is `true`, and the server responds with `Access-Control-Allow-Origin: https://evil-ethereum.org`, as shown in `handleRequest`: [4](#0-3) 
4. A page hosted at `https://evil-ethereum.org` can now make cross-origin requests to the gateway and read the JSON-RPC responses via `fetch`/XHR, which the browser will permit because CORS explicitly allowed that origin.

```go
func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
```
