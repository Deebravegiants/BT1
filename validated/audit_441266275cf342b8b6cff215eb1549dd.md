### Title
Missing validation that the ISMP overlay-root digest was present allows a parachain header lacking `ISMP_ID` digest to commit a zero `overlay_root`, enabling forged non‑membership proofs — (File: `modules/ismp/clients/beefy/src/consensus.rs`)

### Summary
`BeefyConsensusClient::verify_consensus` mirrors the CVE-2017-13715 bug class: it initializes two out-parameters (`timestamp`, `overlay_root`) to defaults before an untrusted-format-dependent dissection loop over digest items, but only validates that one of the two (`timestamp`) was actually overwritten. `overlay_root` is allowed to silently remain `H256::default()` (all-zero) and is committed into the `StateCommitment` without any "was it found" check, exactly the pattern the CVE describes (`n_proto`/`ip_proto`/`thoff` left uninitialized because the dissector's type-dependent branches don't cover every case, and the caller never checks).

### Finding Description
In `verify_consensus`: [1](#0-0) 

`timestamp` and `overlay_root` are both seeded with sentinel/default values, then conditionally overwritten only if a matching `DigestItem::Consensus` entry with the right consensus engine ID (`ISMP_TIMESTAMP_ID` / `ISMP_ID`) is present in the decoded parachain header's digest log (`header.digest().logs`). This header comes from `para_header.header`, which is data carried inside the BEEFY-finalized MMR leaf for whatever parachain state machine is being tracked (`C::is_parachain_tracked`) — it is finalized by relay-chain consensus, but its digest *contents* are produced by that specific tracked chain's block author/runtime, not verified structurally by this function.

The code explicitly guards one field:
```rust
if timestamp == 0 {
    Err(BeefyError::TimestampNotFound)?
}
```
but has no equivalent guard for `overlay_root`. If the `ISMP_ID` consensus digest is absent from the header (e.g., a tracked chain that does not always emit it, a version mismatch, or any block where that digest branch is simply not hit), `overlay_root` is committed to the resulting `StateCommitmentHeight` as `Some(H256::default())`: [2](#0-1) 

This defaulted, unverified root is then trusted downstream as the ISMP child-trie root for both membership and non-membership proof verification: [3](#0-2) [4](#0-3) 

and again in the fee-accumulation/reward path: [5](#0-4) 
and in the reward-emission path of the BEEFY consensus-proofs pallet, which reads the same `overlay_root` unconditionally via `.ok_or_else(...)`: [6](#0-5) 

Once a zero root is accepted as the trusted overlay root for a `StateMachineHeight`, any subsequent `verify_non_membership` proof built against that root (an empty/near-empty trie rooted at `0x00…00`) will make every queried key resolve to `None`, i.e. "not delivered," regardless of the real delivery state. Since `verify_non_membership` is exactly the check the timeout handler uses to prove non-delivery before refunding a request, an attacker able to get such a state commitment accepted can submit spurious timeout proofs and reclaim funds/fees for requests that were actually delivered.

### Impact Explanation
Accepting an unauthenticated default value as a trusted state root, then using it to satisfy the non-membership check that gates request timeouts, is a forged-proof / fund-theft primitive: a relayer or attacker could cause funds escrowed for a request to be refunded via timeout even though the request was delivered, effectively double-spending the payment (delivery reward to the honest relayer plus a fraudulent timeout refund to the attacker). This matches the "forged message delivery" / "concrete theft of funds" acceptance criteria.

### Likelihood Explanation
Reachability requires only that the BEEFY-finalized parachain header for a tracked state machine lack the `ISMP_ID` consensus digest in a particular block — this is a data-shape condition on the *header content* of a chain whose blocks are otherwise legitimately BEEFY-finalized, not a compromise of Hyperbridge's own validator/collator set. I could not fully confirm from the indexed code whether `pallet_ismp` unconditionally inserts the `ISMP_ID` digest on every block of the tracked chain (the digest-insertion logic in `modules/pallets/ismp/src/utils.rs` was not retrievable within the investigation budget), so I cannot certify how often this branch is actually reachable in practice without a compromised/adversarial chain-side block author. The finding is a genuine gap in defensive validation regardless (asymmetric checking of `timestamp` vs. `overlay_root`), but its practical likelihood depends on that unconfirmed fact.

### Recommendation
Track whether the `ISMP_ID` digest was found the same way `timestamp` is tracked, and reject the parachain header (return `BeefyError::InvalidIsmpConsensusLog` or a new `OverlayRootNotFound` error) if it was not found, instead of silently defaulting `overlay_root` to `H256::default()`.

### Proof of Concept
Conceptual (not run against live code due to inability to confirm digest-emission invariants in `pallet_ismp`):
1. Obtain/produce a parachain block header for a `C::is_parachain_tracked` state machine whose digest log contains an `ISMP_TIMESTAMP_ID` entry (to pass the timestamp check) but omits the `ISMP_ID` entry.
2. Get this header BEEFY-finalized and include it in an MMR proof submitted via the BEEFY consensus client's `verify_consensus` (naive or SP1 proof path).
3. Observe that the resulting `StateCommitmentHeight.commitment.overlay_root` is stored as `Some(H256::default())`.
4. Submit a `verify_non_membership` proof (e.g., through the timeout-handling flow in `modules/ismp/state-machines/substrate/src/lib.rs:185-238`) against that state commitment for a commitment hash whose receipt was actually recorded on-chain but cannot be located because the root is zero — the check passes and the request is treated as never-delivered, enabling the timeout/refund path fraudulently.
