### Title
Excess native ETH sent to `placeOrder` is permanently stuck (no refund path) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` accepts native token payment (`msg.value`) for order inputs and for solver/protocol fees (via a Uniswap swap to fee token), but unlike the canonical EVM `IntentGatewayV2.sol`, it never refunds unspent `msgValue` back to the caller after escrow and fee accounting complete.

### Finding Description
`placeOrder` tracks a running `msgValue` local variable, decrementing it as native (`token == address(0)`) input legs and fee-swap costs are consumed: [1](#0-0) [2](#0-1) 
After the fee-collection block, which optionally performs `swapETHForExactTokens{value: msgValue}(...)` and again does not track/refund the residual `msgValue`, execution proceeds straight to emitting `OrderPlaced` with no `_sendValue`/refund call anywhere in the function: [3](#0-2) 

By contrast, the primary EVM `IntentGatewayV2.sol` explicitly refunds any unspent native tokens to the caller at the end of `placeOrder`: [4](#0-3) 

This is functionally the same bug class as the reported issue: a payable/fund-accepting entry point that can receive more native value than it actually needs for the operation, and silently retains the surplus instead of validating/returning it — the CosmWasm report's "multiple native coins → double payment" is the Cosmos-specific instance of "a fund-receiving function doesn't reconcile the exact amount consumed vs. supplied." Here the consequence is the inverse but equally damaging direction: caller overpayment in native ETH/TRX is trapped in the contract with no code path to retrieve it (no `_sendValue` call exists anywhere in the Tron contract).

### Impact Explanation
Any unprivileged user who calls `placeOrder` with `msg.value` greater than the sum required for native input legs plus the fee-swap cost has that surplus permanently locked in the `IntentGatewayV2` contract on Tron, with no user-facing withdrawal mechanism (`SweepDust` is only reachable via a signed cross-chain `onAccept` request controlled by the protocol/governance, not by the depositor). This is a permanent freezing of user funds triggered directly by a normal, single transaction (`placeOrder`), matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Overpayment is easy to trigger unintentionally: any caller that estimates native fee cost slightly high (e.g., due to slippage buffers in fee quoting, or if they mistakenly include fees for output-side surplus splitting that doesn't apply on `placeOrder`), or that reuses SDK logic ported from the main EVM path (which relies on the refund existing), will overpay and lose the difference. Given the Tron contract is a near-verbatim fork of `evm/src/apps/IntentGatewayV2.sol` minus the refund step, this is highly likely to be hit in normal usage rather than requiring adversarial conditions.

### Recommendation
Add the same unspent-native-token refund logic present in `evm/src/apps/IntentGatewayV2.sol` (`_sendValue(msg.sender, msgValue)` after fee escrow, guarded by `if (msgValue > 0)`) to `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `placeOrder` function, ensuring parity between the two deployments and eliminating the permanent-lock condition.

### Proof of Concept
1. Deploy/attach to the Tron `IntentGatewayV2` with `protocolFeeBps = 0` and no `predispatch`.
2. Construct an `Order` with one native (`token = address(0)`) input of `amount = 1 ether` and `order.fees = 0`.
3. Call `placeOrder{value: 2 ether}(order, graffiti)`.
4. Trace execution: in the `else` branch, `msgValue` is decremented by `1 ether` (leaving `1 ether` unspent); `order.fees == 0` so the fee block is skipped; function proceeds directly to `emit OrderPlaced` with no refund.
5. Verify `address(intentGateway).balance` increases by `2 ether` (not `1 ether`), and the caller has no function to reclaim the extra `1 ether` — confirming the funds are stuck, unlike the equivalent test `testPlaceOrder_RefundsExcessNativeToken` that passes against the main EVM contract at `evm/src/apps/IntentGatewayV2.sol`.
