### Title
Webhook shop identity spoofing via unsigned `shop-domain` header — cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
The library's webhook HMAC validation only authenticates the request body, not the `shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` verifies `Utils::HmacValidator.validate(request)` and then hands the caller-supplied `request.shop` value directly to the app's handler as trusted tenant identity, with no cryptographic binding between the signed bytes and that field.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from the (attacker-controllable) HTTP header with no participation in the signed string: [2](#0-1) 

`Utils::HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` uses this same HMAC check as the sole authenticity gate, then immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler: [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified(bytes) == bytes acted on for tenant identity`. In reality, only the raw body is verified; the `shop` field that downstream code (per the gem's own documented handler contract) treats as "The shop domain of the webhook" is never covered by the signature: [5](#0-4) 

Because a merchant who installs the app is a legitimate holder of the app's shared secret material (Shopify signs their real webhooks with the app's own `api_secret_key`), such a merchant (an "unprivileged internet user" relative to other tenants of the same app) can capture one of their own genuine signed webhook deliveries (`raw_body` + valid `x-shopify-hmac-sha256`) and resubmit it to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a different, victim shop. `HmacValidator.validate` still succeeds because it only checks the untouched body bytes, and `Registry.process` calls the handler with `shop: request.shop` set to the victim's domain, causing the host application (following the gem's documented API) to write/enqueue work attributed to a shop the attacker does not control.

### Impact Explanation
This is a cross-tenant identity confusion at the library's trust boundary: the field the gem's own contract designates as the tenant identifier (`shop`) is exposed to the app's business logic without being covered by the only integrity check the gem performs. Depending on what the host app does with `data.shop` (e.g., look up/update records, attribute billing events, trigger tenant-scoped actions) this enables cross-tenant data corruption/access — matching the "Critical: cross-tenant access" impact category. No access token, `client_secret`, or privileged account is required; only participation as any installed shop of the app (or capture of one legitimate webhook delivery) is needed.

### Likelihood Explanation
Moderate-to-high for apps that install the code path exactly as documented (`ShopifyAPI::Webhooks::Registry.process` + trusting `data.shop`, per `docs/usage/webhooks.md`). Any shop that has installed the app can trivially capture one legitimate webhook (body+hmac pair) sent to their own registered endpoint and replay it to the same endpoint URL with a modified shop header, since the endpoint is a public HTTP route by design (that's how Shopify delivers webhooks) and the gem does not bind body-signature to header-derived tenant identity.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`) in the HMAC-covered signable representation, or otherwise cryptographically bind the header-derived tenant identity to the verified payload (e.g., require the app to independently confirm the target shop has an active session/webhook registration matching the `webhook_id` before trusting `shop`). At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked by the host application against known installed shops/webhook IDs before use.

### Proof of Concept
1. Shop A installs the app; Shopify sends a legitimate webhook to the app's `/webhook` route with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some `raw_body`.
2. Shop A (attacker, acting only within their own unprivileged access to their own webhook traffic) records this raw body and HMAC.
3. Attacker resends the identical `raw_body`/`hmac-sha256` to the same public webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop also using the app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC — the shop header is never inspected: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` and the attacker-controlled body, and any tenant-scoped action the host app performs (per the documented handler contract) is now executed against/attributed to Shop B.
