### Title
Trezor THP autoconnect pairing credentials cannot be revoked once granted - (File: features/hw-trezor/src/module/discovery.ts)

### Summary
`TrezorDiscovery.submitPairingCode` stores autoconnect ("autoconnect credential") pairing credentials into `#thpCredentialsAtom` after a successful pairing, which is then used on every subsequent connection to skip the pairing confirmation. There is no `forget`/`revoke`/`unpair`/`clearCredentials` method exposed anywhere in the module, its API, or the plugin that would let a user (or the system) invalidate previously stored autoconnect credentials.

### Finding Description
When a Trezor device is paired via `submitPairingCode`, the module requests autoconnect credentials and persists them into `#thpCredentialsAtom` (or `#pendingCredentialsUpdate` while locked): [1](#0-0) 

These credentials are loaded on unlock via `onUnlock` and cached in `#cachedCredentials`, and reused for every future `scan()` call, since `ExodusTrezorEvents` is constructed with `pairingCredentials: this.#cachedCredentials`: [2](#0-1) [3](#0-2) 

The only mutator exposed for the pairing-related state is `clearPairingPrompt`, which resets the *pairing prompt* flag (`#pairingPromptAtom`), not the stored autoconnect credentials themselves: [4](#0-3) 

`hardwareWalletThpCredentialsAtomDefinition` is a plain storage atom with only generic `get`/`set`, and it is marked `public: false`, so no consumer-facing API can call `.set(undefined)` on it either: [5](#0-4) 

The `hardwareWalletsApi` (the surface actually exposed to the SDK consumer/UI) exposes `submitPairingCode` and `clearPairingRequest` but nothing to remove or invalidate the stored autoconnect credential: [6](#0-5) [7](#0-6) 

This is directly analogous to the reported bug class: a privileged trust grant (`approve strategist` ↔ `pair device with autoconnect credential`) is added via one function, but the codebase provides no corresponding revoke/removal path.

### Impact Explanation
If a device is paired once (e.g., by a user testing an untrusted/borrowed/compromised Trezor, or if the stored credential itself is later suspected to be compromised/leaked from storage), the wallet has no built-in mechanism to invalidate that trust and force re-confirmation on the device. Any code path that regains access to `#cachedCredentials`/the underlying atom (or an attacker who can replay/exfiltrate the stored credential blob) can silently reconnect and bypass the on-device pairing confirmation ("skip pairing confirmation on future connections"), a control that exists specifically to gate hardware-signing access. This weakens the on-device consent boundary that protects hardware wallet signing.

### Likelihood Explanation
Likelihood is moderate: this requires either (a) a legitimate device/credential later becoming untrusted (lost device, compromised credential storage) where the user would want to revoke access but cannot, or (b) storage-level compromise. It does not require any external website/dApp involvement, so it is a wallet-internal trust-management gap rather than a directly web3-attacker-triggerable bug, but it is fully reachable through the standard hardware wallet pairing flow with no additional privilege.

### Recommendation
Add an explicit `forgetDevice` / `revokePairing` method to `TrezorDiscovery` (and expose it through `hardwareWalletsApi`) that clears `#cachedCredentials`, `#pendingCredentialsUpdate`, and calls `this.#thpCredentialsAtom.set(undefined)`, forcing the device to require full pairing-code confirmation again. Surface this as a user-facing "un-pair device" action.

### Proof of Concept
1. Pair a Trezor device via THP: call `hardwareWallets.submitPairingCode({ code })`, which internally calls `TrezorDiscovery.submitPairingCode`, storing an autoconnect credential in `hardwareWalletThpCredentialsAtom`. [1](#0-0) 
2. Observe that every subsequent `scan()` reuses `this.#cachedCredentials` to skip the pairing prompt. [2](#0-1) 
3. Search the public API surface (`hardwareWalletsApi`) and the module itself for any method to clear/forget/revoke the stored credential — only `clearPairingRequest`/`clearPairingPrompt` exist, which only reset the "prompt" boolean, not the credential. [6](#0-5) [4](#0-3) 
4. Confirm no revoke path exists: `hardwareWalletThpCredentialsAtom` is `public: false` and provides no domain-specific clear method. [5](#0-4)

  submitPairingCode = async (code: string) => {
    let result
    try {
      // Complete initial pairing with the code
      result = await this.#events?.processThpCodeEntry(code)

      // Request autoconnect credentials so future connections don't require confirmation
      try {
        const autoconnectCredential = await this.#events?.getThpCredentials(true)
        this.#logger.debug('Got autoconnect credentials:', autoconnectCredential)

        // Update result with autoconnect credential
        if (result?.knownCredentials && autoconnectCredential) {
          // Replace the last credential (the one we just created) with the autoconnect version
          result.knownCredentials[result.knownCredentials.length - 1] = autoconnectCredential
        }
      } catch (autoconnectError) {
        // Log but don't fail pairing if autoconnect request fails
        this.#logger.warn('Failed to get autoconnect credentials:', autoconnectError)
      }
    } finally {
      this.#cachedCredentials = result

      if (this.#isUnlocked) {
        await this.#thpCredentialsAtom.set(result)
      } else {
        this.#pendingCredentialsUpdate = result
      }

      await this.#pairingPromptAtom.set(false)
    }

    return result
  }
