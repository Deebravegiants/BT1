### Title
Silent decimal-scaling truncation in `convert_to_balance`/`convert_to_erc20` mis-scales cross-chain HFT transfer amounts when `erc_decimals < local_decimals` — ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s decimal conversion helpers scale amounts between an EVM contract's decimals (`erc_decimals`) and the local asset's decimals (`local_decimals`) using `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent. `saturating_sub` silently clamps to `0` whenever `erc_decimals < local_decimals`, which collapses the required scale-up factor to `10^0 = 1` instead of the correct `10^(local_decimals - erc_decimals)`. This is the exact bug class described in the external Hubble report: a one-directional decimal-difference computation that is not defended against the case where the assumption (`erc_decimals >= local_decimals`) does not hold, producing a silently wrong cross-chain amount rather than a revert.

### Finding Description
`convert_to_balance` (used in `on_accept`/`on_timeout` when receiving from an EVM peer) and `convert_to_erc20` (used in `send` when transmitting to an EVM peer) both compute the scaling power as: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions are called on every `send` extrinsic (unprivileged, signed by any user) and on every inbound `on_accept`/`on_timeout` ISMP delivery (triggered by a relayed proof), with `decimals` read **live** at call time from `T::Decimals` (a fixed constant for the native asset) or dynamically from `<T::Assets as fungibles::metadata::Inspect>::decimals(asset_id)` for non-native assets, and `erc_decimals` read from the `Precisions` storage map set at registration time: [2](#0-1) [3](#0-2) 

The pallet clearly recognizes the invariant `erc_decimals >= local_decimals` is required for correctness — it declares a dedicated `ErcDecimalsBelowLocal` error for it: [4](#0-3) 

However, because `local_decimals` for non-native assets is read live from the `Assets` pallet's metadata rather than pinned at `register_token` time, any subsequent change to that asset's on-chain decimals (or a registration whose validation window is not re-checked on every path that touches `Precisions`/decimals) breaks the invariant after the fact, with no re-validation inside `convert_to_balance`/`convert_to_erc20` themselves — the `saturating_sub` silently absorbs the violation instead of erroring.

### Impact Explanation
If the invariant `erc_decimals >= local_decimals` is ever violated at the moment `send`/`on_accept`/`on_timeout` executes:
- `on_accept`: `convert_to_balance` divides by `10^0` instead of multiplying up by `10^(local_decimals-erc_decimals)`, so beneficiaries receive amounts many orders of magnitude smaller than the ERC20 amount actually locked/burned on the source chain — value is effectively destroyed for the receiving user (permanent freezing/loss of funds for the bridged amount).
- `send`: `convert_to_erc20` multiplies by `10^0` instead of dividing correctly, producing an ERC20-side amount that does not match the local amount escrowed/burned, letting a mismatched (potentially inflated, depending on direction) amount be dispatched to the remote HyperFungibleToken/BridgeToken contract, which mints on `onAccept` per the message's stated `amount` — an unbacked mint on the destination chain relative to what was actually escrowed/burned locally.

Both paths are reachable through ordinary unprivileged actions (`send` extrinsic, or delivering a relayed ISMP proof to `on_accept`), matching the required "single submitted extrinsic/relayed proof" reachability bar.

### Likelihood Explanation
Exploitability depends entirely on the invariant `erc_decimals >= local_decimals` being violated at call time. I was not able to fully verify, within available index coverage, whether `register_token`/`update_token` re-checks and pins this invariant against the *live* `Assets` pallet decimals on every registration path, or whether a decimals value can drift after registration (e.g., via `pallet-assets::set_metadata`, which is typically permissioned to the asset's own metadata-admin, separate from the HFT pallet's `CreateOrigin`). If such drift is possible even once, every subsequent transfer for that asset silently corrupts amounts with no additional privileged action required at exploit time. This uncertainty means the finding is plausible but not fully proven end-to-end from the indexed code alone.

### Recommendation
- Do not rely on `saturating_sub` to encode a direction assumption; compute the scaling exponent by comparing `erc_decimals` and `local_decimals` explicitly (as `_normalizeAmount` in `evm/src/utils/VWAPOracle.sol` does) and multiply/divide accordingly for both directions. [5](#0-4) 
- Re-validate `erc_decimals >= local_decimals` (or handle both directions correctly) at the point of use in `convert_to_balance`/`convert_to_erc20`, not only once at registration, since `local_decimals` for non-native assets is read live rather than cached.
- Add a defensive `ensure!`/error return (reusing `ErcDecimalsBelowLocal`) inside the conversion helpers themselves if the one-directional design is intentional, so a stale/violated invariant reverts the extrinsic instead of silently mis-scaling funds.

### Proof of Concept
Not independently reproducible from the indexed code alone; the mechanism requires confirming whether a registered non-native asset's `Assets`-pallet decimals can fall below its configured `erc_decimals` after `register_token`/`update_token` runs (e.g., via `pallet-assets::set_metadata`). Given that uncertainty, this should be validated with a live Devin session against the full `pallet-token-gateway`/`pallet-hyper-fungible-token` registration code and `pallet-assets` configuration before treating it as a confirmed, exploitable primitive rather than a latent defect in the scaling helpers.

        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
