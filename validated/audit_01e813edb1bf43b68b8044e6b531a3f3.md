### Title
Interest accrual can permanently freeze an oversized high-utilization market through `i128` value overflow - (File: common/src/rates/simulate.rs)

### Summary
The pool computes each accrual by unscaling total scaled debt and supply through `scaled_to_original`, which performs checked RAY multiplication and panics when the result does not fit in `i128`. [1](#0-0) [2](#0-1) [3](#0-2) 

An unprivileged user can create the prerequisite state through `supply` and `borrow`; after index growth makes either market value unrepresentable, the permissionless `update_indexes` call and every pool mutation that synchronizes the market fail before committing new state. [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
`accrue_step` first derives `borrowed_original = borrowed * borrow_index / RAY` and `supplied_original = supplied * supply_index / RAY`, then uses those values for utilization and index updates. [7](#0-6) 

Although `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, that cap is reached only after the old scaled balances have already been unscaled; therefore an oversized book can hit the RAY-value ceiling before the index cap. [8](#0-7) [7](#0-6) 

The failure is not confined to the keeper-style `update_indexes` path: supply, borrow, withdraw, repay, liquidation and related pool legs load their market through `synced_market`, which unconditionally calls `interest::global_sync`. [9](#0-8) [10](#0-9) 

The in-repository regression proves this exact state: a market holding `BILLION * 10^18` principal and 98% debt eventually makes `update_indexes` return `MathOverflow`, after which a one-unit withdraw and a one-unit repay also revert with `MathOverflow`. [11](#0-10) 

### Impact Explanation
This causes permanent freezing of user funds and leaves the affected market unable to operate. Once the value product exceeds `i128::MAX`, every mutating operation must first accrue through the current ledger timestamp, so repayment, withdrawal, liquidation, bad-debt processing, and recapitalization hit the same panic before their risk-reducing logic can run. [9](#0-8) [12](#0-11) 

Because no successful accrual can advance `last_timestamp` past the overflowing interval, waiting does not remove the condition; subsequent calls still attempt to unscale the same oversized balances against an index that is at least as large. [13](#0-12) [10](#0-9) 

### Likelihood Explanation
Likelihood is medium-low because the attacker must fund an exceptionally large market and sustain high utilization until index growth pushes a RAY-valued market total beyond the `i128` range. [14](#0-13) 

The path is nevertheless reachable without privileged authorization: the attacker supplies the target market, supplies collateral in another listed market, borrows most of the target liquidity, and any user can later invoke `update_indexes`. [4](#0-3) [5](#0-4) 

The existing test demonstrates the threshold within the protocol’s own admitted numeric domain rather than requiring storage corruption, privileged keys, or an invalid interest-rate model. [11](#0-10) 

### Recommendation
Do not make market synchronization depend on an unbounded `i128` valuation of total scaled supply or debt.

Compute utilization from a capped or saturating representation, perform the rate decision with widened `I256` values, and cap utilization before converting the result back to `i128`. The pool should also bound admitted scaled supply and debt against the maximum future representable value, not merely against the entry-time token-to-RAY conversion.

At minimum, `scaled_to_original` should gain a market-accounting variant whose behavior is deterministic at the domain boundary, so repayments, withdrawals and liquidations can still reduce the oversized book instead of reverting before those reductions execute.

### Proof of Concept
Conceptually reproduce the committed regression scenario:

1. Configure a high-decimals target market with a steep interest-rate curve and sufficiently high supply/borrow caps.
2. As one unprivileged caller, call `Controller::supply(caller, 0, spoke_id, [(target_hub_asset, BILLION * 10^18)])` to seed the target market.
3. Supply enough collateral in a second listed market, then call `borrow(caller, account_id, [(target_hub_asset, principal * 98 / 100)], None)`.
4. Advance ledger time and repeatedly call `update_indexes(caller, [target_hub_asset])`.
5. Once `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceeds `i128::MAX`, `update_indexes` reverts with `MathOverflow`.
6. Subsequent `withdraw`, `repay`, or `liquidate` calls touching that market revert before execution because their pool operation first enters `synced_market -> global_sync -> accrue_step -> scaled_to_original`.

The concrete regression is `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`, which asserts `MathOverflow` for index update, withdrawal, and repayment while the borrow index remains below `MAX_BORROW_INDEX_RAY`. [11](#0-10)

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
