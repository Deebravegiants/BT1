### Title
`AuroraEngineBridge` does not verify that the withdrawn token is actually integrated with the target Aurora Engine contract, allowing misdelivery of funds - (File: `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts`)

### Summary
`AuroraEngineBridge.supports()` accepts any NEP-141 `assetId` as long as a `VirtualChain` `routeConfig` is supplied, without ever checking that the specific `auroraEngineContractId` (or `proxyTokenContractId`) in that `routeConfig` actually custodies/recognizes the token being withdrawn. This is the same class of bug as the reported `CLGauge.deposit()` issue: a caller-supplied identifier (`tokenId` staked into a gauge / here, `auroraEngineContractId` + `assetId` pair) is never cross-checked against the real on-chain relationship it claims to have, so an intent can be produced whose receiver contract has no relation to the asset being sent.

### Finding Description
`supports()` in `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts` (lines 60-77) only checks:
1. `routeConfig.route === RouteEnum.VirtualChain`
2. `parseDefuseAssetId(params.assetId).standard === "nep141"` [1](#0-0) 

It never validates that the `auroraEngineContractId` supplied inside the same `routeConfig` is actually the Aurora Engine that mints/handles this particular token, nor that `proxyTokenContractId` (when set) corresponds to the token in `assetId`. Contrast this with `OmniBridge.supports()`, which explicitly calls `getCachedDestinationTokenAddress()` to verify a token is actually deployed on the destination chain before allowing the withdrawal: [2](#0-1) 

`createWithdrawalIntents()` then builds an intent using whatever `auroraEngineContractId` / `proxyTokenContractId` the caller passed, with no cross-check against the token: [3](#0-2) 

The actual intent construction in `createWithdrawIntentPrimitive()` sends an `ft_withdraw`/`ft_transfer_call`-style intent where `receiver_id` is either `auroraEngineContractId` directly, or (in the non-standard-decimals flow) `proxyTokenContractId`, with the token itself always taken from `assetId`: [4](#0-3) 

Because `auroraEngineContractId` and `proxyTokenContractId` are plain caller-supplied strings in `routeConfig` (see `withdrawalParamsInvariant` at lines 62-77 of the same file, which only asserts the route type, not the values) and are never validated against the `token` (`assetId`) being sent, a caller can construct a withdrawal that ships an arbitrary NEP-141 token to an arbitrary NEAR account (`auroraEngineContractId`/`proxyTokenContractId`) under the guise of a "virtual chain withdrawal," even though that receiving contract has no relationship to, or registration of, that token as a bridged asset for any virtual chain.

### Impact Explanation
This breaks the equality "bridge chosen custodies the token being withdrawn." If the receiving Aurora Engine (or proxy) contract does not recognize the token via `ft_on_transfer`, the transferred tokens can become permanently stuck (no automatic mint/credit occurs on the destination "virtual chain," and depending on the receiving contract's `ft_on_transfer` implementation, tokens may not be refunded), matching the High-severity impact category "a withdrawal stuck until manual intervention." In the worst case, if a malicious/compromised `auroraEngineContractId`/`proxyTokenContractId` is supplied (e.g. via a route config compromised by a malicious front-end, integrator, or a bug elsewhere that lets an attacker influence route selection), funds could be misdelivered to a contract that does absorb them without forwarding to the intended destination chain, i.e. "funds delivered to a wrong address/chain/contract with no recovery."

### Likelihood Explanation
The SDK performs zero on-chain verification tying the asset to the specific Aurora Engine/proxy contract before constructing and signing the withdrawal intent — this only requires the caller (or whatever assembles `routeConfig`) to supply a mismatched `auroraEngineContractId`/`proxyTokenContractId`/`assetId` triple, which is straightforward since these are ordinary string parameters with no cross-field consistency check performed by the SDK. `estimateWithdrawalFee()` does query `getNearNep141StorageBalance` for the given `auroraEngineContractId`, but this only checks storage registration, not that the pair is a legitimate bridged asset relationship — a registered account can still be entirely unrelated to the token's virtual-chain bridging.

### Recommendation
Before constructing the withdrawal intent in `AuroraEngineBridge.supports()` (or `createWithdrawalIntents()`), verify on-chain (or via a maintained allow-list/config, similar to `POA_TOKENS_MIGRATED_TO_OMNI_BRIDGE`) that the specific `auroraEngineContractId` (and `proxyTokenContractId`, if set) is a token that the target Aurora Engine actually recognizes/bridges for the token in `assetId`, throwing `UnsupportedAssetIdError`/a dedicated error otherwise — mirroring the pattern `OmniBridge` already uses with `getCachedDestinationTokenAddress()`/`TokenNotFoundInDestinationChainError`.

### Proof of Concept
1. Call `sdk.createWithdrawalIntents()` (or `AuroraEngineBridge.createWithdrawalIntents()` directly) with:
   - `assetId: "nep141:usdt.tether-token.near"` (an arbitrary, unrelated NEP-141 token)
   - `routeConfig: createVirtualChainRoute("some-unrelated-account.near", null)`
2. `supports()` returns `true` purely because the standard is `nep141` and the route is `VirtualChain` — see [1](#0-0) .
3. `createWithdrawalIntents()` builds an `ft_withdraw` intent sending `usdt.tether-token.near` tokens to `receiver_id: "some-unrelated-account.near"` with an Aurora-Engine-formatted `msg`, despite that receiver never having been established as bridging USDT to any virtual chain — see [5](#0-4) .
4. If `some-unrelated-account.near`'s `ft_on_transfer` does not correctly handle/refund the unexpected token+msg combination, the withdrawn funds are stuck at that contract with no path for the user to recover them through the SDK.

Note: I was unable to inspect the Aurora Engine / bridge contract's exact `ft_on_transfer` handling behavior (out of repo scope), so the precise on-chain consequence (revert-and-refund vs. permanent stuck funds) could not be fully confirmed from this codebase alone; this is stated as a caveat on the concrete on-chain impact.

	async supports(
		params: Pick<WithdrawalParams, "assetId" | "routeConfig">,
	): Promise<boolean> {
		if (params.routeConfig == null || !this.is(params.routeConfig)) {
			return false;
		}

		const assetInfo = parseDefuseAssetId(params.assetId);
		const isValid = assetInfo.standard === "nep141";

		if (!isValid) {
			throw new UnsupportedAssetIdError(
				params.assetId,
				"`assetId` does not match `routeConfig`.",
			);
		}
		return isValid;
	}

export function createWithdrawIntentPrimitive(params: {
	assetId: string;
	auroraEngineContractId: string;
	proxyTokenContractId: string | null;
	destinationAddress: string;
	amount: bigint;
	storageDeposit: bigint;
}): IntentFtWithdraw {
	const { contractId: tokenAccountId, standard } = utils.parseDefuseAssetId(
		params.assetId,
	);
	assert(standard === "nep141", "Only NEP-141 is supported");

	// Most cases
	if (params.proxyTokenContractId == null) {
		return {
			intent: "ft_withdraw",
			token: tokenAccountId,
			receiver_id: params.auroraEngineContractId,
			amount: params.amount.toString(),
			msg: makeAuroraEngineDepositMsg(params.destinationAddress),
			storage_deposit:
				params.storageDeposit > 0n
					? params.storageDeposit.toString()
					: undefined,
			min_gas: MIN_GAS_AMOUNT,
		};
	}

	//  Flow for transferring a base token to a virtual chain with a non-standard (non-ETH) base token
	return {
		intent: "ft_withdraw",
		token: tokenAccountId,
		receiver_id: params.proxyTokenContractId,
		amount: params.amount.toString(),
		msg: `${params.auroraEngineContractId}:${makeAuroraEngineDepositMsg(params.destinationAddress)}`,
		storage_deposit:
			params.storageDeposit > 0n ? params.storageDeposit.toString() : undefined,
		min_gas: MIN_GAS_AMOUNT_NON_STANDARD_DECIMALS,
	};
}
