### Title
Unfunded repay overpayment refund drains pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
`ops::repay::accounting` computes the overpayment refund from the *declared* `action.amount` against the position's outstanding debt, with no check that any tokens were actually transferred in. For a leg whose position carries zero scaled debt, `resolve_repay` takes its full-close branch (`amount >= current_debt_ceil == 0`), so the entire declared amount becomes `overpayment` and `cache.transfer_out(payer, overpayment)` pays it out of real pool custody while `credit_cash(net_repay)` credits nothing to the book. An unprivileged address can call the pool's `repay` entrypoint directly with an empty/zero position and a large declared `amount`, receiving pool funds it never deposited.

### Finding Description
`resolve_repay` in `common/src/rates/scaling.rs:171-192` returns `(pos_scaled, amount - current_debt_ceil)` whenever `amount >= current_debt_ceil`. With `pos_scaled == Ray::ZERO`, `unscale_borrow_ceil` yields `0`, so any positive `amount` is classified entirely as overpayment. In `ops::repay::accounting` (`contracts/pool/src/ops/repay.rs:40-67`):

- `net_repay = amount - overpayment = 0`, and the `RepayRoundsToZeroShares` assert passes because `net_repay == 0`.
- `burn_debt(burned)` and `credit_cash(net_repay)` are no-ops — the cash book is untouched.
- `apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)`, transferring `amount` of the market's underlying token from the pool to `payer`.

The refund is derived from the declared inbound amount rather than measured receipts — the pool assumes the caller (the controller's `settle_repay`, which performs `transfer_amount_measured` in `contracts/controller/src/positions/debt.rs:144-152` and rejects missing debt via `get_debt_position_or_panic`) has already funded it. Nothing in the pool leg verifies an inbound transfer occurred or that the declared `position` corresponds to real debt. The repo's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590-3611`) pins this behavior: calling `repay` with no transfer in and zero debt pays `custody_before` out to `payer` and leaves the book unchanged. The analogous gap exists in `ops::recapitalize::apply`, which refunds the excess over the backing shortfall on the same unfunded-declared-amount basis.

This mirrors CVE-2020-6821's shape: a request partially or fully outside the valid source region (declared repayment exceeding real, funded debt) must yield zero, but the implementation materializes value from nothing — here, custody belonging to suppliers rather than uninitialized memory.

### Impact Explanation
Theft of user funds. Each call transfers `amount` of the market token from pool custody to an arbitrary `payer` without any deposit, directly draining supplier cash. Repeating the call (or sizing `amount` at the full balance) extracts the pool's entire liquid balance for that market, i.e., the deposits backing every supplier's claim.

### Likelihood Explanation
Reachable by any address that can invoke the pool contract's `repay` entrypoint with a `PoolAction` naming a real market and a zero-scaled position — the production test in `contracts/pool/tests/flows.rs` does exactly this with a freshly generated `payer`. No special state is required beyond the market holding custody; even a market with live debt is vulnerable by declaring a position of zero, since `resolve_repay` only compares `amount` to that position's debt, not to a funded receipt. The only open question is whether the pool contract gates its ops entrypoints to the controller address; the in-repo tests invoke `client().repay` directly with an unrelated `payer`, and no `require_auth`-based caller check was found on this path.

### Recommendation
Derive refunds from measured value, not declared input: either require the caller to have transferred `amount` into the pool before `repay` executes (measure the pool's balance delta), or cap `overpayment` at the tokens actually received in the same transaction. At minimum, short-circuit the zero-debt / `net_repay == 0` case so no outbound transfer occurs when nothing was repaid, and apply the same funding check to the `recapitalize` excess refund.

### Proof of Concept
1. Identify a pool market holding supplier custody `C` (e.g., USDC) for `hub_asset`.
2. As an unprivileged address `payer`, invoke the pool's `repay` entrypoint with one `PoolAction { hub_asset, amount: C, position: 0 }` and send no tokens.
3. `resolve_repay` sees `current_debt_ceil == 0 <= C`, returns `overpayment = C`; `net_repay == 0` skips the zero-shares assert; `transfer_out(payer, C)` moves the pool's full token balance to `payer`.
4. Pool custody decreases by `C` while `cash`, `supplied`, and `borrowed` are unchanged — suppliers' claims are now unbacked, as pinned by `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3590-3611`).
