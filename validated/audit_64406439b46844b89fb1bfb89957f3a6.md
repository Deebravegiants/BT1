Audit Report

## Title
Cross-Workflow Response Cache Confusion in Gateway HTTP Action Handler - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

## Summary
The gateway's outbound HTTP response cache keys entries solely by `OutboundHTTPRequest.Hash()`, which incorporates `WorkflowOwner` but not `WorkflowID`, contradicting the README's documented "Workflow Isolation" guarantee. Two distinct workflows under the same owner issuing an identical outbound HTTP request will collide on the same cache key and can receive each other's cached response.

## Finding Description
`responseCache.Fetch` and `responseCache.Set` both compute the cache key via `req.Hash()` and store/retrieve entries from a single shared `map[string]*cachedResponse` [6](#0-5) [4](#0-3) . The struct's own doc-comment states the hash covers "(method, URL, headers, body, workflowOwner)" — omitting `WorkflowID` [5](#0-4) . This is directly confirmed by `TestRequestHash`'s `"having different workflowID results in same Hash"` and `"having same workflowOwner results in the same Hash"` subtests in this repo, which exercise the real `gateway_common.OutboundHTTPRequest.Hash()` from `chainlink-common` and assert exactly this behavior [7](#0-6) . No other isolation mechanism (e.g., per-workflow cache partitioning, namespacing by workflow ID) exists in `Fetch`/`Set`/`isExpiredOrNotCached`, so two workflows sharing an owner and issuing byte-identical requests will read/write the same cache slot.

## Impact Explanation
This produces cross-workflow response confusion, an in-scope "cross-user response corruption" class of impact: workflow B can receive HTTP action response data (status code and body) that was actually fetched/cached on behalf of workflow A, purely because both belong to the same owner and issue the same request shape. This undermines the "Workflow Isolation" property explicitly documented in the component's README, and can silently corrupt downstream workflow logic or leak workflow-specific data across workflow boundaries within the same owner.

## Likelihood Explanation
This requires no attacker action or elevated privilege — it can occur organically whenever a single owner/tenant runs multiple workflows that call the same external endpoint with an identical request shape (method/URL/headers/body) and both opt into caching (`CacheSettings.Store`/`MaxAgeMs`). Given that reusing common integration endpoints across a tenant's automations is a normal and expected usage pattern, and caching is opt-in per request with a real TTL window, the collision is realistically likely.

## Recommendation
Include `WorkflowID` in the `OutboundHTTPRequest.Hash()` computation (in `chainlink-common/pkg/types/gateway`) so the cache key is truly workflow-scoped, matching the documented behavior. Update `TestRequestHash` in `response_cache_test.go` to assert that different `WorkflowID` values produce different hashes, and audit `README.md` to ensure it matches actual code behavior.

## Proof of Concept
1. Run `TestRequestHash` subtest `"having different workflowID results in same Hash"` in `core/services/gateway/handlers/capabilities/v2/response_cache_test.go` (lines 139-149) — it currently passes, proving two requests differing only by `WorkflowID` hash identically.
2. Construct two `gateway.OutboundHTTPRequest` values with the same `WorkflowOwner`, same method/URL/headers/body, but different `WorkflowID`, both with `CacheSettings.Store = true` and `MaxAgeMs > 0`.
3. Call `responseCache.Set` with workflow A's request and a response payload, then call `responseCache.Fetch` with workflow B's request (different `WorkflowID`) — observe that `Fetch` returns workflow A's cached response to workflow B, demonstrating cross-workflow cache confusion.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {

	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
