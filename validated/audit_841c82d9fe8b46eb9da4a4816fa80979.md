### Title
Webhook `shop` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (`shopify-shop-domain` / `x-shopify-shop-domain` header) used to attribute the webhook to a tenant is read from an HTTP header that is never included in the signed material. `Registry.process` validates the HMAC and then blindly trusts the unauthenticated header value as the tenant identity passed to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, comes entirely from a header, independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, then immediately hands `request.topic`, `request.shop`, and `request.parsed_body` to the registered handler without any additional binding between the shop header and the signed content: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it with the header-supplied HMAC: [4](#0-3) 

Because the shop-domain header is outside the HMAC's coverage, the identity binding "shop verified by HMAC" == "shop attributed to the webhook by the handler" does not hold. Before an attack: for a genuine webhook delivered to a shop the attacker legitimately owns (app installed on their own store), Shopify computes `HMAC(secret, raw_body)` and sets `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`. After the attack: the attacker resends the exact same raw body and HMAC value to the app's webhook endpoint, but swaps the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds (the HMAC only ever covered `raw_body`, which is unchanged), so `Registry.process` invokes the handler with `WebhookMetadata` whose `shop` is now `victim-shop.myshopify.com` even though Shopify never sent a webhook for that shop with this content.

### Impact Explanation
This crosses a tenant boundary using only the trust an app already places in its own webhook signing key: an attacker who has legitimately installed the app on their own shop (an unprivileged relationship w.r.t. other merchants) can cause the host application to process attacker-controlled webhook payloads (order data, customer data, GDPR redact requests, etc.) as if they belonged to an arbitrary victim shop. Downstream host applications typically use `WebhookMetadata#shop` as the tenant key to look up/modify per-shop data (e.g., updating orders, deleting customer data on `customers/redact`), so this enables cross-tenant data corruption or unauthorized actions attributed to a shop the attacker does not control — matching the "cross-tenant access" impact class.

### Likelihood Explanation
Medium-to-High: exploitation only requires the attacker to install the target app on a shop they control (a normal, unprivileged action), capture one valid webhook delivery for a topic of interest, and replay it with a modified header value at the app's public webhook endpoint. No access token, `client_secret`, or privileged credential of the victim is needed.

### Recommendation
Include the shop-domain (and ideally topic, webhook-id, api-version) values in the HMAC-signable material, or otherwise cryptographically bind them to the signed payload, so that tampering with the `shopify-shop-domain` header invalidates the signature. At minimum, `Registry.process`/`Request` should require the caller to supply the expected shop out-of-band (e.g., from the authenticated route/session) and verify it matches the header before dispatching to the handler, rather than trusting the header as an authenticated tenant identifier.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a real webhook delivery, e.g. `orders/create`, noting `raw_body` and the `X-Shopify-Hmac-Sha256` header value computed by Shopify with the app's real `client_secret`.
2. Send a new HTTP request to the app's webhook endpoint with the identical `raw_body` and identical `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this successfully; `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC (`lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/request.rb` lines 35-38).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to process attacker-supplied data under the victim shop's tenant identity.
