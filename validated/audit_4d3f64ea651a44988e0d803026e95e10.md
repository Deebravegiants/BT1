Found the key issue: in `Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`), the `shop` field returned by `shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [1](#0-0) , but the HMAC signature (`to_signable_string`) only covers the raw request body, not the shop-domain header [2](#0-1) . `Registry.process` validates the HMAC over the body and then dispatches to the handler using `request.shop` taken straight from that unauthenticated header [3](#0-2) .

However, after reviewing this in the context of the rules for this exercise, this is exactly the class of "field acted on but not covered by the HMAC" that the rules call out as in-scope — but I need to verify whether it constitutes a genuine cross-tenant boundary break given that the body itself is HMAC-verified (proving the request came from Shopify) while only the shop identifier attached to it is unauthenticated. This means an attacker who has access to *any* valid webhook body+HMAC pair for their own shop (e.g., their own test/dev store, which they legitimately control) can resend it with a forged `x-shopify-shop-domain` header claiming to be a *different* merchant's shop, since the shop domain is never bound into the signed payload. Because `Registry.process` passes `request.shop` (attacker-controlled) into `WebhookMetadata` untouched, any host application that trusts `data.shop` to scope tenant data (e.g., to decide which merchant's records to update) will attribute the webhook payload to the wrong shop.

This satisfies the required identity-binding break: **shop authenticated (HMAC over body proves origin from *some* valid Shopify webhook) versus shop stored/used (header value, unauthenticated) are not the same shop**, enabling cross-tenant webhook spoofing.

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the value of the `x-shopify-shop-domain` HTTP header, but `to_signable_string` (used by `Utils::HmacValidator.validate`) only hashes the raw request body. An attacker who possesses one valid `(body, hmac)` pair for a webhook delivered to their own shop can replay it against the host app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, and `Registry.process` will accept it as authentic and dispatch it under the attacker-chosen shop identity.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`, exposing `hmac` (parsed from the `hmac-sha256` header) and `to_signable_string`, which returns only `@raw_body` [4](#0-3) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors all read directly from HTTP headers that are never included in `to_signable_string` [5](#0-4) .

`Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which recomputes the signature only over `to_signable_string` (the body) — and, once that passes, immediately trusts `request.shop` to build `WebhookMetadata` passed to the app's handler [3](#0-2) . Because the shop identity is never bound into the signed bytes, the binding "shop verified by HMAC" ≠ "shop used by handler" is broken: any request carrying a *valid* `(body, hmac)` combination (obtainable from a webhook the attacker's own store legitimately receives) can be replayed with a different `x-shopify-shop-domain` value and will still pass validation, but will be processed as if it came from the spoofed shop.

### Impact Explanation
This is a cross-tenant identity confusion: a host application that uses `WebhookMetadata#shop` (as populated by `Registry.process`) to determine which merchant's tenant data to update, delete, or invalidate (a common and encouraged pattern, since `data.shop` is the only shop identifier provided to handlers) can be manipulated by an unprivileged internet user controlling one legitimate shop into taking action against another shop's tenant data. This matches the "Critical – cross-tenant access" category since the trust boundary between tenants is broken purely by the library's design of what is/isn't covered by the signature.

### Likelihood Explanation
Exploitation requires only a single legitimate webhook capture from the attacker's own (possibly free/dev) Shopify store — this is trivially obtainable by any developer/merchant since HMAC secrets are per-app, not per-shop, so any valid webhook body+hmac pair from *any* shop installed on the app validates for *all* shops. The attacker does not need the app's `api_secret_key`; they only need to observe one webhook delivery to their own store and can then replay it with a forged shop header to the same public webhook endpoint.

### Recommendation
Bind the shop identity (and ideally topic/webhook id) into the signed payload verification, e.g., verify the HMAC over `raw_body` (as Shopify does) but require the host application to independently look up/validate that the `shop` header corresponds to a shop with an active installation before trusting it, or have `Registry.process` cross-check the shop domain against known installed shops before invoking the handler. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the webhook HMAC and must not be trusted for tenant-scoping without additional verification (e.g., matching it against a stored session/shop record).

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker receives a legitimate webhook, e.g., `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resends the exact same `POST` to the app's public webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `hmac` returns `H`'s decoded digest, `shop` returns `victim-shop.myshopify.com` [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) and compares to `H` — this matches, since `B` is unchanged [7](#0-6) .
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`, passing `shop: "victim-shop.myshopify.com"` to the host app's handler, even though the payload actually originated from `attacker-shop.myshopify.com`'s Shopify instance [8](#0-7) .
