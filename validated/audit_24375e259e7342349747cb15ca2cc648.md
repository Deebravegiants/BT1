### Title
Webhook HMAC only signs the raw body, letting an attacker rebind a valid webhook payload to a spoofed shop — cross-tenant confusion in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature that `Utils::HmacValidator.validate` checks in `Registry.process` never covers the `shop`, `topic`, or `webhook_id` values. Those values are read directly from unauthenticated HTTP headers and are handed to the app's webhook handler as trusted identifiers, breaking the intended binding `hmac == HMAC(secret, shop || topic || body)` down to `hmac == HMAC(secret, body)`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from request headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler, without any further check that these header values correspond to the shop the payload actually came from: [3](#0-2) 

The identity binding that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Because the signable string is only the raw body, this equality is not enforced — the `shop-domain`, `topic`, and `webhook-id` headers are attacker-controllable metadata riding alongside a cryptographically valid signature computed over unrelated content (the body).

### Impact Explanation
Any attacker who can obtain one legitimate `(raw_body, hmac)` pair signed with the app's shared secret (e.g., by triggering — or intercepting — a real webhook delivery for their own store, or any store integrated with the same app) can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary value in the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header. `Utils::HmacValidator.validate` will report success because it only checks the body, and `Registry.process` will dispatch to the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop. Any host application that relies on `data.shop` (as documented in `docs/usage/webhooks.md`) to scope tenant data will act on data attributed to the wrong shop — a cross-tenant confusion/access issue.

### Likelihood Explanation
Exploitation requires only unauthenticated HTTP access to the app's webhook endpoint plus possession of any single valid `(body, hmac)` pair for that app's shared secret — which is trivial to obtain since the attacker can be a legitimate merchant of the same app and simply capture/replay their own webhook deliveries while forging the shop header on replay.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (`to_signable_string`), or otherwise cryptographically bind these header-derived values to the payload before trusting them in `WebhookMetadata`, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host`/`state` into its signature.

### Proof of Concept
1. App registers a webhook handler for topic `orders/create` and stores per-request data keyed by `data.shop`.
2. Attacker (a merchant of the app) receives a genuine webhook delivery: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = H` (computed by Shopify over `B` using the app secret), header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays a forged HTTP POST directly to the app's webhook endpoint with the same `raw_body = B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B` only) — validation succeeds.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-controlled webhook content under the victim shop's identity.
