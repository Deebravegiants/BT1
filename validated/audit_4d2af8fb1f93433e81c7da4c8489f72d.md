### Title
Webhook `shop` identity is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`), `topic`, `api_version`, and `webhook_id` directly from unauthenticated HTTP headers, while the HMAC signature that `Webhooks::Registry.process` validates covers only the raw request body. An attacker who possesses one valid `(body, hmac)` pair — trivially obtainable by installing the target app on their own store and triggering any webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. The signature check still passes because the shop domain was never part of the signed data, and the webhook handler is invoked believing the event originated from the victim's store.

### Finding Description
`HmacValidator.validate` only verifies the HMAC over `verifiable_query.to_signable_string`, and `Webhooks::Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC and then trusts `request.shop` (and the other unauthenticated header fields) when constructing the data handed to the app's webhook handler: [3](#0-2) 

The identity binding that should hold is: `hmac_valid(raw_body) == true` implies `shop header == shop that actually generated raw_body`. In reality, `hmac_valid` only proves body integrity/authenticity; it says nothing about which shop the body belongs to. Before the attack: legitimate webhook `(body_A, hmac_A, shop=A)` is valid and `shop=A` is correct. After the attack: replayed request `(body_A, hmac_A, shop=B)` still passes `Utils::HmacValidator.validate` (line 190 of `registry.rb`) because `hmac_A` was computed only over `body_A`, yet the handler receives `WebhookMetadata` claiming `shop: B` — breaking the equality the app relies on to scope the webhook data to the correct tenant.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook consumers: any app that uses `request.shop` (surfaced via `WebhookMetadata#shop`) to decide which merchant's session/data record to update can be made to apply attacker-supplied webhook content under a victim shop's identity, since the gem provides no mechanism (and no documented warning) that the shop field is unauthenticated. This is a cross-tenant data integrity issue reachable by any actor who can install the app on any store (including a free/dev store) and capture one legitimate webhook.

### Likelihood Explanation
Any developer/merchant can install a public/embedded app on a store they control, trigger a webhook event (e.g., an order or product create), and capture the raw POST body plus its `x-shopify-hmac-sha256` value from their own server logs or a request-capturing endpoint. Replaying that exact body and HMAC while only changing `x-shopify-shop-domain` requires no secret material and no privileged access — only unprivileged control of a webhook-emitting Shopify store, satisfying the "unprivileged internet user" bar.

### Recommendation
- Include the shop domain (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting `request.shop`.
- Short of changing the signature scheme (which must remain compatible with Shopify's actual webhook delivery format), the gem should prominently document in `Webhooks::Request`/`Registry` that `shop`, `topic`, `api_version`, and `webhook_id` are **not** covered by the HMAC and that consuming apps must independently verify the shop against their own installed-shops/session store before trusting webhook data for that shop.
- Consider providing a built-in helper that cross-checks `request.shop` against a caller-supplied list/session lookup as part of `Registry.process`, rather than leaving this entirely to host applications.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger any webhook subscription (e.g., `orders/create`).
2. Capture the raw POST body (`raw_body`) and the `x-shopify-hmac-sha256` header value from the delivered webhook — no secret is needed, only observation of your own inbound request.
3. Replay the request to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks `OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's data>)`, causing the app to process attacker-controlled data as though it belongs to the victim shop.
