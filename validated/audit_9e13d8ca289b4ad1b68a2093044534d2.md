### Title
Arbitrary route pool can execute attacker code under the swapper's authorization tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
`execute_strategy` accepts a caller-supplied `StrategyPayload`, resolves pool and token addresses from its unauthenticated `assets` registry, and invokes the selected pool through a venue adapter. [1](#0-0) [2](#0-1) 

This is analogous to attacker-controlled JNDI resolution: an address supplied in the route determines which external code runs inside an operation authorized by the swapper. [3](#0-2) [4](#0-3) 

### Finding Description
`Router::execute_strategy` calls `sender.require_auth()` and then executes the decoded route without verifying that its pool addresses correspond to trusted or previously deployed venue contracts. [5](#0-4) 

For a swap operation, the payload's `idx_a` registry entry becomes `SwapHop.pool`, while `idx_b` and `idx_c` become the input and output token addresses. [6](#0-5) 

The venue dispatcher then calls the adapter selected by the payload opcode; no venue or pool allowlist is consulted. [7](#0-6) 

The Sushi adapter, for example, invokes attacker-selected `pool.token0`, `pool.token1`, `pool.get_oracle_hints`, and `pool.swap`. [8](#0-7) [9](#0-8) 

Because these calls execute beneath the authorized `execute_strategy` invocation, malicious pool code can request additional `sender.require_auth()` token transfers that are recorded as children of the caller's authorization tree. [10](#0-9) [11](#0-10) 

### Impact Explanation
A malicious route provider can cause a victim's swap transaction to include an additional child authorization transferring unrelated wallet tokens to the attacker.

The router's post-hop checks only require positive measured output and exact consumption of `amount_in`; they do not bound unrelated transfers performed by the pool under the swapper's authorization. [12](#0-11) 

The malicious pool can simultaneously return the expected output token to the router, allowing the route to pass `total_min_out`, while separately transferring victim wallet assets to the attacker. [13](#0-12) [14](#0-13) 

The result is theft of user funds beyond the declared swap input.

### Likelihood Explanation
An unprivileged attacker can deploy a contract that implements the expected pool functions, encode its address in the route's `assets` registry, and entice a victim or automated route client to submit that route.

The attack cannot bypass Soroban authorization by itself: the malicious transfer must appear in the authorization tree accepted by the victim or the victim's contract account. [15](#0-14) 

The design nevertheless expands a swap authorization from the expected input transfer into execution of arbitrary pool code capable of requesting unrelated transfers, making unsafe route composition and opaque authorization-tree approval sufficient for exploitation.

### Recommendation
Maintain a governance-controlled venue-pool allowlist keyed by `(venue, pool, token_in, token_out)`, and reject hops whose pool is not registered.

Alternatively, constrain each venue adapter to known immutable pool contracts or factory-derived pool identities, and fail closed when the payload supplies an unrecognized pool address.

Clients should also display every authorization child and reject any route that introduces transfers beyond the one expected input transfer, but contract-level allowlisting is necessary because opaque route XDR should not become an authorization escalation mechanism.

### Proof of Concept
1. The attacker deploys `MaliciousPool` configured with `victim`, `wallet_token`, and `attacker`.
2. `MaliciousPool` implements `token0`, `token1`, `get_oracle_hints`, and `swap`; `token0` and `token1` return the route's declared input and output tokens so `direction_for_pair` succeeds. [16](#0-15) 
3. The attacker builds a `StrategyPayload` whose `assets` registry contains `MaliciousPool`, the legitimate `token_in`, and `token_out`, with one Sushi swap instruction selecting those indices. [3](#0-2) [6](#0-5) 
4. The victim submits `execute_strategy(victim, total_in, payload_xdr)`, authorizing the simulated invocation tree produced for that route. [1](#0-0) 
5. During `MaliciousPool.swap`, it calls `token_in.transfer(router, attacker_or_pool, amount_in)` using the router's pool-pull authorization and sends a positive amount of `token_out` back to the router. [17](#0-16) [18](#0-17) 
6. In the same `swap` call, it calls `wallet_token.transfer(victim, attacker, stolen_amount)`, which the host can satisfy only because it was included as a child of the victim's route authorization.
7. `dispatch_hop` observes a positive `token_out` delta and exactly `amount_in` spent, so the unrelated wallet-token transfer does not make the swap fail. [12](#0-11) 
8. The router pays the measured output to the victim and completes successfully, while `stolen_amount` of an unrelated token has already been transferred to the attacker. [19](#0-18)
