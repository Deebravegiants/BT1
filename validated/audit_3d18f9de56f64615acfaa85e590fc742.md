## Title
Unbounded/overflowing string-length arithmetic in Pharos BLS validator-key decoding leads to panic / oversized allocation during consensus proof verification - (File: `modules/consensus/pharos/verifier/src/state_proof.rs`)

### Summary
The Pharos consensus verifier decodes a Solidity "long string" storage slot to recover a validator's BLS public key. The decoded length (`str_len`) is derived from a 256-bit on-chain storage value truncated to 64 bits via `.low_u64()`, with no upper bound check, and is then used in unchecked arithmetic (`str_len + 31`) and directly as a `Vec::with_capacity` argument. This mirrors the libexpat CVE-2024-45492 pattern: an attacker-influenced length field is fed into arithmetic that can overflow the platform's word size, invalidating the size checks meant to guard subsequent allocation/parsing.

### Finding Description
In `decode_bls_key_from_string_slot`, the long-string branch computes: [1](#0-0) 

```rust
let length = (header_val - 1) / 2;
let str_len = length.low_u64() as usize;
...
let slots_needed = (str_len + 31) / 32;
if data_slots.len() < slots_needed {
    return Err(...);
}
let mut string_data = Vec::with_capacity(str_len);
```

`header_val` is a `U256` read straight from a verified storage slot (`decode_u256_from_storage`) belonging to the Pharos staking contract's BLS-key string field [2](#0-1) . Because `.low_u64()` simply truncates the low 64 bits of a `U256`, `str_len` can be forced arbitrarily close to `u64::MAX`/`usize::MAX` by whoever controls that storage slot's contents (e.g. a validator/applicant registering with a crafted BLS-key string in the staking contract), even though the field is only ever meant to hold a ~96-98 character hex string.

With `str_len` near `usize::MAX`:
- `str_len + 31` overflows. In an overflow-checked build this panics immediately; in a wrapping build it silently truncates to a small number, causing `slots_needed` to shrink to a tiny value that trivially satisfies the `data_slots.len() < slots_needed` guard that was supposed to reject an oversized claim (the same "declared size not backed by validated content" bug class present in the CVE, and structurally identical to the `encoded_call_size` decompression-bomb guard the pallet's own `decompress` function was hardened against, see the comment at [3](#0-2) ).
- Execution then reaches `Vec::with_capacity(str_len)` with the original, still-enormous `str_len`, attempting a multi-exabyte allocation, which aborts the process (allocator failure) — a direct denial of service.

This function is reached from `verify_validator_set_proof` → `decode_validator_set_from_storage` → `decode_bls_key_from_string_slot`, which is the on-chain/light-client path used to accept a new Pharos validator set whenever `handle_unsigned` processes a relayed Pharos consensus/state update [4](#0-3)  and [5](#0-4) . Any relayer submitting a legitimately state-root-verified proof that happens to include such a maliciously-registered validator entry will trigger the panic/OOM while the runtime is verifying consensus.

### Impact Explanation
A panic or an aborting allocation inside consensus-proof verification, invoked from `handle_unsigned`, halts processing of that message and can be used to repeatedly break Pharos state-machine update ingestion, i.e. "a route unable to deliver messages" — one of the explicitly accepted High-severity impacts. Because verification is on the hot path of accepting new light-client-verified consensus/state updates, this is reachable by any relayer submitting a validly-rooted but adversarially crafted proof once the malicious storage value has been legitimately written into Pharos state.

### Likelihood Explanation
Requires only a single write of an oversized BLS-key length field to the relevant storage slot on the Pharos side (a normal registration/update transaction, not majority validator collusion) and one relayed proof referencing that state. No signature forgery or governance/admin access is needed on the Hyperbridge side.

### Recommendation
- Bound `str_len` explicitly (e.g. reject any length greater than the expected 96/98-character BLS key length, or a small sane maximum) immediately after decoding `header_val`, before any arithmetic is performed on it.
- Use checked arithmetic (`checked_add`/`checked_div`) for `slots_needed` and return an error on overflow instead of relying on wraparound behavior.
- Avoid `Vec::with_capacity(str_len)` with an untrusted length; only allocate after the value has been bounded and validated against `data_slots.len()`.

### Proof of Concept
1. On Pharos, register/update a validator's BLS public-key string slot such that its "long string" header value encodes `length` so that `low_u64()` yields `str_len ≈ usize::MAX - 10` (attacker controls the raw storage bytes at that slot, verified later only via Merkle inclusion, not content sanity).
2. Wait for/obtain a state root that includes this write (a routine block, no validator quorum collusion required for the write itself).
3. Submit a `ValidatorSetProof` covering this state root and validator entry through the normal relaying flow into `verify_validator_set_proof` (`modules/consensus/pharos/verifier/src/state_proof.rs:74`).
4. Verification proceeds to `decode_bls_key_from_string_slot`; `str_len + 31` overflows, `slots_needed` wraps small and passes the size guard, then `Vec::with_capacity(str_len)` is invoked with the original huge `str_len`, aborting the process (or panicking in overflow-checked builds) during consensus update handling.

	state_root: H256,

		return Err(Error::TooManyValidators { count, max: MAX_VALIDATORS });
	}

	let pool_set_start = 2;

		return Err(Error::InsufficientPoolIds {
			expected: pool_ids_end,
			validators: count,
			got: values.len(),
