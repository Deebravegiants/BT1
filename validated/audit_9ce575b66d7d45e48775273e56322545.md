### Title
Webhook Shop-Domain Header Spoofing Due to HMAC Covering Only Raw Body — Cross-Tenant Webhook Forgery ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request **body**. The `shop-domain` (and `topic`, `webhook-id`, `api-version`) values used to dispatch the event to a tenant-specific handler come from HTTP **headers** that are never included in the signed material. Any party that can obtain one valid `(body, hmac)` pair for the app's shared `client_secret` — trivially available to anyone who installs the app on their own store — can replay that exact body with a forged `shop-domain` header and have the request accepted as coming from an arbitrary other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and the `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, completely independent of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exactly against `verifiable_query.to_signable_string`, i.e. the body only: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`) to dispatch the event to the app's handler, having only checked that the *body* HMAC is valid: [4](#0-3) 

Because the HMAC is `HMAC(client_secret, raw_body)` and is completely independent of `shop`, `topic`, or `webhook_id`, the same `(raw_body, hmac)` pair is valid for **any** shop using the same app/client_secret. This breaks the intended identity binding: `shop authenticated (by HMAC) != shop attributed (used for dispatch)`.

### Impact Explanation
This is a cross-tenant integrity issue (Critical category: "cross-tenant access"). A user who is a legitimate merchant/installer of the app on their own store (an "unprivileged" party relative to other tenants of the same app) can:
1. Trigger a webhook event on their own shop whose body content they can shape (e.g. an `orders/create`, `products/update`, or a mandatory privacy webhook like `customers/redact`) and capture Shopify's legitimately signed `(body, hmac)` pair for it.
2. Replay that exact body/HMAC to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain (and/or a different `topic`/`webhook-id`).
3. Because `Registry.process` only checks the body HMAC — never binding it to `shop`/`topic` — the handler executes believing the event genuinely originated from, and pertains to, the victim shop, using attacker-controlled data.

Depending on what the host app's webhook handlers do with `shop` (e.g., look up/act on that shop's session or data, trigger data deletion, forge state changes), this enables cross-tenant data corruption, spoofed compliance/redaction actions, or forged business events attributed to another merchant, without ever needing the victim's or the app's credentials.

### Likelihood Explanation
Reasonably likely to be exploitable in real deployments: an attacker only needs to run their own installation of the target app (something any of the app's own merchants can do) to legitimately obtain valid `(body, hmac)` pairs, then simply resend that HTTP request with a modified header — no cryptographic secret is required from the attacker. The bug is systemic (applies to every webhook processed via `Registry.process`), not a one-off misconfiguration.

### Recommendation
Bind the tenant/shop identity (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed body (e.g., include it in the signable string, or require per-shop signing/verification instead of a single shared secret validating body-only signatures). At minimum, document/require that host applications independently verify `request.shop` against a known, previously-registered shop for that specific webhook subscription before trusting it, and update `Registry.process`/`Request#to_signable_string` to include `shop`, `topic`, and `webhook_id` in the signable material.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook subscription event (e.g., `products/update`) with attacker-chosen JSON body `B`. Capture the genuine `X-Shopify-Hmac-Sha256` header Shopify sends for body `B` (valid because it is a real Shopify-originated webhook for the attacker's own shop).
3. Send a new POST request to the app's webhook endpoint reusing body `B` and its captured HMAC, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com` (and optionally alter `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`B`) — it succeeds because `B` and its HMAC were never modified.
5. `Registry.process` proceeds to invoke the app's webhook handler with `shop: "victim-shop.myshopify.com"`, `topic`, and attacker-controlled body `B`, as if this were a legitimate event for the victim shop. [4](#0-3) [5](#0-4)

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end
