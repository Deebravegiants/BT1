### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is read from unauthenticated HTTP headers, not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` domain (and `topic`, `webhook_id`, `api_version`) that get passed to the app's handler as trusted tenant identity are read from HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` and compares it to the `hmac` value pulled from the request: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all derived from raw headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are completely independent of the HMAC computation: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards these unauthenticated header values directly to the app's webhook handler as trusted `WebhookMetadata`: [4](#0-3) [5](#0-4) 

The identity binding that is broken:
`shop domain trusted by the handler` ≠ `shop domain covered by the cryptographic signature`.

Since `shop` is not part of `to_signable_string`, the HMAC only proves "this body byte-sequence was signed by someone holding `api_secret_key`" — it proves nothing about which shop the body belongs to. Any party who can obtain one validly-signed `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and triggering any webhook-emitting action) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `Registry.process` will accept it (HMAC still matches the unchanged body) and hand the handler a `WebhookMetadata` claiming the data originated from a different (victim) shop.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: the gem itself vouches for `shop` as authenticated tenant identity to the app's handler, but it is not authenticated at all. Any consuming application that uses `WebhookMetadata#shop` to key persistence, side effects, or session/account lookups (the intended and documented use, per `WebhookHandler#handle`) can be made to apply attacker-supplied body content under a victim shop's identity — a cross-tenant access impact, without any credential or session token belonging to the victim shop.

### Likelihood Explanation
The only prerequisite is obtaining any one legitimately-signed `(body, hmac)` pair from the target app (trivially available to any merchant who installs the app, since `api_secret_key` is shared across all shops of that app) and network access to the app's webhook receiving endpoint. No access to `api_secret_key`, tokens, or victim credentials is required — only header manipulation, which is standard, low-effort attacker capability.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string, or otherwise cryptographically bind them to the body (e.g., include them as part of `to_signable_string`, or require the host app to separately verify `shop` against its own known-shop list before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted as tenant identity without independent verification against a known/installed-shop store.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` sent to the app's webhook endpoint. `H` is a valid HMAC-SHA256 of `B` under the app's shared `api_secret_key` — it validates via `Utils::HmacValidator.validate`, per `hmac_validator.rb` lines 12-22.
2. Attacker replays an HTTP request to the same webhook endpoint with the **exact same body `B`** and **exact same `x-shopify-hmac-sha256: H`**, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` returns only `@raw_body` (unchanged), the check passes (`lib/shopify_api/webhooks/request.rb` lines 35-38).
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` where `request.shop` now equals `"victim-shop.myshopify.com"` even though the body content is the attacker's own order data (`lib/shopify_api/webhooks/registry.rb` lines 188-199).
5. Any host application logic that trusts `data.shop` for record lookup/creation now processes attacker-controlled data under the victim shop's tenant identity.
