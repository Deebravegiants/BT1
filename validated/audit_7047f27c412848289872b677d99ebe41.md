### Title
Webhook shop identity is not bound to the HMAC signature, enabling shop-domain spoofing via webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC only over the raw request body, while the `shop` value that the registry hands to application handlers is read directly from the unsigned `X-Shopify-Shop-Domain` HTTP header. Because the header is never part of the signed payload, any actor who can obtain one valid `(body, hmac)` pair (e.g. by receiving a webhook to a shop they control) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary shop domain in the header, and the signature check still succeeds.

### Finding Description
The signable string for webhook HMAC validation is defined as just the raw body: [1](#0-0) [2](#0-1) 

`hmac` is computed from a header (`shopify-hmac-sha256`), and `to_signable_string` returns only `@raw_body`. The `shop` accessor pulls straight from the `shopify-shop-domain` header — a field with no cryptographic relationship to the HMAC at all: [3](#0-2) 

`Utils::HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`: [4](#0-3) 

`Registry.process` performs this body-only HMAC check, and then immediately trusts `request.shop` (the unsigned header) to build the `WebhookMetadata` passed to the app's handler — this is the exact tenant identity the app uses to attribute the webhook body to a shop: [5](#0-4) 

The documented handler contract explicitly instructs apps to treat `data.shop` as the trusted shop for that webhook body (e.g. for enqueueing per-shop jobs): [6](#0-5) 

The equality that should hold is: `shop_that_authorized_this_body == shop_attributed_to_this_body_by_the_gem`. Instead, the gem only proves `HMAC(secret, body)` is valid — it proves nothing about which shop the header claims to be from. `shop_that_authorized_this_body` (bound to the secret used to compute the HMAC) and `shop_header_value` (the field actually acted upon by `Registry.process`/`WebhookMetadata`) are never checked against each other.

### Impact Explanation
An attacker who can trigger or capture any single legitimate webhook delivery with a valid HMAC (trivial: install the target app on their own or a test shop and receive one webhook) can replay that unmodified body+HMAC to the same app's public webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to any victim shop domain. `Registry.process` will accept it (HMAC over the body is still valid) and hand the handler a `WebhookMetadata` claiming the body belongs to the victim shop. Any app that uses `data.shop` to key per-tenant storage, session lookups, or business logic (as the gem's own documentation recommends) will process attacker-controlled data under a victim shop's identity — a cross-tenant data-injection/confusion condition.

### Likelihood Explanation
Likelihood is high for any app built per this gem's documented pattern: the attacker needs no secrets, no privileged access, and no MITM — only the ability to receive one webhook from the target app (achievable by installing the app on any shop they control) and replay the HTTP request with a modified header to the app's public callback URL.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the signed payload used for HMAC verification, or otherwise cryptographically bind the header-derived `shop` to the verified body before constructing `WebhookMetadata`. At minimum, `Registry.process` should refuse to trust `request.shop` unless the app additionally verifies (e.g., via a prior registration lookup, webhook-id/shop mapping, or mutual TLS) that the header value matches the shop for which that specific webhook was registered.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (or otherwise legitimately triggers a webhook) and captures a delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(secret, B)`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == H` — this passes because `B` and `H` are unchanged.
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim-shop.myshopify.com"`, and the app's handler processes attacker-controlled body `B` as though it belongs to `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
