### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted without being covered by the HMAC signature, allowing tenant-spoofing replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC verification performed by `HmacValidator.validate` binds *only* the body bytes to the app's secret. The `shopify-shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are parsed independently and are never part of the signed material, yet `Registry.process` uses `request.shop` to build the `WebhookMetadata` that is handed to the app's handler as the tenant identity.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` only returns `@raw_body`; the `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` validates only this body HMAC, then trusts `request.shop` (and `request.topic`) to route and label the payload for the handler: [4](#0-3) 

This is the same bug class as the Lender.sol M-6 finding: an identity-relevant field (`RESERVE`'s balance vs. the balance actually used in reward accrual) is acted upon by a code path without being kept consistent with the value that was actually verified/updated elsewhere. Here, the equality that should hold is:

`shop used by Registry.process (request.shop, from header)` == `shop implicitly authenticated by the HMAC (none — HMAC only covers body bytes)`

Because the header is not part of the signed content, any request with a *valid* `(body, hmac)` pair — which an attacker can freely obtain by triggering a webhook on their **own** store (a store they legitimately control, requiring no privileged credentials) — can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to any victim shop domain. The HMAC still validates because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload came from the victim shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to look up per-tenant state (e.g., to update a shop's local order/inventory record, disable/uninstall processing, or select which merchant's access token/session to act on) — which is the intended, documented use of this field — an unprivileged attacker who owns any Shopify store can forge webhook deliveries that appear to originate from an arbitrary victim shop, achieving cross-tenant data injection/corruption in the host app. This matches the "Critical: cross-tenant access" impact category, since the tenant boundary (`shop`) is not cryptographically bound to the verified bytes.

### Likelihood Explanation
Likelihood is credible but requires two things outside pure network access: (1) the attacker must possess at least one own Shopify shop to generate a legitimate `(body, hmac)` pair (a low-privilege but non-anonymous prerequisite — any developer/merchant account is sufficient, not an admin/access-token secret of the *victim*), and (2) the host application must actually trust `request.shop`/`WebhookMetadata#shop` for tenant routing, which is the documented, expected usage pattern for this gem's webhook helper. Given the library ships `shop` as a first-class accessor specifically for host apps to use for tenant identification, and does nothing to bind it cryptographically, this is a structural gap in the library rather than a host-app misuse — it directly parallels the "bytes verified versus bytes parsed" analog category.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the signable string, or otherwise cryptographically bind them to the HMAC before exposing them via `Request`. At minimum, `Registry.process`/`WebhookMetadata` documentation should explicitly warn that `shop` is unauthenticated and must be independently verified against the app's list of installed shops before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook, capturing the raw `body` and the corresponding `x-shopify-hmac-sha256` value (both valid, since the attacker is a legitimate merchant of their own store).
2. Attacker POSTs to the app's webhook endpoint with the same `body`/`hmac` headers unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only re-computes the HMAC over `@raw_body` [2](#0-1) [4](#0-3) .
4. The registered handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and the attacker-controlled body, causing the host app to act on victim-shop data using attacker-supplied content.
