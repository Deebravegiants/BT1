## #Title
Fee-on-transfer underlying tokens cause unbacked mints/unlocks in `WrappedHyperFungibleToken.send` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable.send()`) locks the underlying ERC20 via `safeTransferFrom` but dispatches the cross-chain `Message` using the caller-supplied `params.amount` rather than the amount actually received by the contract. If the underlying token charges a transfer fee, the contract ends up holding less than `params.amount` while the destination chain unlocks/mints the full `params.amount`, permanently under-collateralizing the wrapper.

### Finding Description
In `send()`, the underlying token is pulled with a plain `safeTransferFrom` call and no before/after balance check: [1](#0-0) 

The `DispatchPost`/`Message` body is then built directly from `params.amount` via `_buildDispatchPost`, independent of what the contract actually received: [2](#0-1) 

On the destination side (a peer `WrappedHyperFungibleToken` unlocking the same underlying, or `HyperFungibleToken`/`pallet-hyper-fungible-token` minting the wrapped representation), the full `message.amount` from the POST body is unlocked/minted: [3](#0-2) 

If `_underlying` is a fee-on-transfer token, the escrowing contract on the source chain receives `params.amount - fee` but the message still claims `params.amount` was locked. The destination chain therefore unlocks/mints more than is actually backed by the source-chain escrow, exactly the root cause described in the reference report (assuming the full nominal amount is received after `transferFrom`). This same pattern is present in the upgradeable variant: [4](#0-3) 

Notably, the codebase already recognizes and correctly mitigates this exact bug class elsewhere — `IntentGatewayV2.placeOrder` explicitly snapshots balances before/after each token pull and mutates the recorded amount to the actually-received value for fee-on-transfer tokens: [5](#0-4) [6](#0-5) 

`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lack this same balance-delta accounting, meaning any owner-configured underlying token with a transfer fee turns every `send()` call into a shortfall between escrowed collateral and the cross-chain minted/unlocked liability.

### Impact Explanation
Each `send()` call with a fee-on-transfer underlying leaves the wrapper contract short of collateral by the fee amount while the destination side unlocks/mints the full nominal amount. Repeated over time, this drains the escrow relative to outstanding wrapped supply, so later legitimate `onAccept` unlocks or `onPostRequestTimeout` refunds can fail (insufficient underlying balance) or, in a burn/mint peer topology, create unbacked wrapped-token supply that cannot be redeemed 1:1 — a permanent loss/freezing of funds for other users of the bridge. This is a direct on-chain accounting flaw reachable by any unprivileged user of the token-bridge app once the owner configures an underlying with transfer fees (e.g., many real-world fee/rebasing tokens).

### Likelihood Explanation
Reachable by any user via a single `send()` call — no privileged access required. Likelihood depends on the owner configuring a fee-on-transfer token as `_underlying` (permitted by `configure()` with no restriction against such tokens), which is plausible since `WrappedHyperFungibleToken` is a generic wrapper meant to support "existing ERC20 tokens."

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder`: measure `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual received delta (not `params.amount`) both for the dispatched `Message.amount` and for the emitted `Sent` event, in both `WrappedHyperFungibleToken.sol` and `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and configures `_underlying` to a fee-on-transfer ERC20 (e.g., 1% fee), per `configure()` at [7](#0-6) .
2. User calls `send({amount: 1000e18, ...})`. `safeTransferFrom` pulls tokens from the user; due to the 1% fee, the contract's balance increases by only 990e18, but `_buildDispatchPost` encodes `amount: 1000e18` into the `Message`.
3. The ISMP request is delivered and verified on the destination chain; `onAccept` unlocks/mints 1000e18 to the beneficiary while only 990e18 of real collateral exists on the source chain.
4. Repeating this call systematically drains the wrapper's real underlying balance below its outstanding cross-chain minted/unlocked liability, eventually causing legitimate `onAccept`/`onPostRequestTimeout` calls to revert due to insufficient underlying balance, permanently freezing other users' funds.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

    function send(HyperFungibleTokenUpgradeable.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }
