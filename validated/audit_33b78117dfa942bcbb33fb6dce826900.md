### Title
Cross-tenant webhook shop-domain spoofing due to shop-domain header not covered by HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while the tenant-identifying `shop` value returned by `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC of the body via `Utils::HmacValidator.validate(request)` and then forwards `request.shop` unchanged to the app's webhook handler as the tenant identifier [3](#0-2) . The HMAC therefore authenticates the body but not the shop the body is claimed to belong to, breaking the binding `authenticated(body) == tenant_acted_upon(shop)`.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it against the `hmac` field using `OpenSSL.secure_compare` [4](#0-3) . For webhook requests, `to_signable_string` is defined as just `@raw_body` [1](#0-0)  — none of the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers participate in the signature. `Request#shop` simply reads the unauthenticated header value [2](#0-1) .

`Registry.process` validates the HMAC and, once it passes, immediately builds `WebhookMetadata` using `request.shop` (and `request.topic`) without any additional cross-check against the shop the HMAC was actually generated for [3](#0-2) . Because a single app has one shared `api_secret_key` used for every merchant installation, any unprivileged attacker who installs the app on their own store receives genuinely Shopify-signed webhook deliveries (valid body + valid HMAC, computed with the app's shared secret). The attacker can capture such a delivery and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. Since the header is outside the signed content, `HmacValidator.validate` still returns `true`, and the handler receives `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop.

The gem's own documentation instructs handler implementations to trust `data.shop` directly (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) , reinforcing that `request.shop` is presented by this gem as an authenticated tenant identifier when it is not cryptographically bound to the request.

### Impact Explanation
This qualifies as cross-tenant access (Critical): an attacker who is merely an installed merchant of the app (unprivileged relative to other tenants) can make the app process attacker-chosen webhook payloads under the identity of an arbitrary victim shop domain, as long as they know or guess the victim's `.myshopify.com` domain (which is generally public/discoverable). Depending on how the host application uses `data.shop` (e.g., to look up the victim's session/access token, update the victim's local records, or trigger `app/uninstalled` style logic), this can lead to cross-tenant data corruption or actions being taken against a shop the attacker does not control.

### Likelihood Explanation
Exploitation requires the attacker to install the app on at least one shop they control (a normal, unprivileged action available to any merchant) and to know the target's shop domain. No possession of the `client_secret` or any victim credentials is required, only the ability to intercept/replay their own legitimately-received webhook and modify a header. This is a realistic and directly reachable path through the gem's documented API (`Registry.process` / `Request.new`).

### Recommendation
Bind the shop identity to the signed content, or otherwise verify it independently before trusting it:
1. Include the shop-identifying header(s) (and ideally topic/webhook-id) in `to_signable_string` so they are covered by the HMAC, or
2. Have `Registry.process` cross-check `request.shop` against the shop associated with the webhook registration / an authenticated session store before invoking the handler, rejecting mismatches.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggers an event (e.g., `orders/create`), and captures the genuine webhook POST, including its valid `x-shopify-hmac-sha256` header and raw body.
2. Attacker replays the exact same request to the app's webhook endpoint but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#to_signable_string` still returns the (unmodified) raw body, so `Utils::HmacValidator.validate` succeeds using the app's shared `api_secret_key`.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the host application to act on `victim-shop.myshopify.com`'s behalf using attacker-supplied data.
