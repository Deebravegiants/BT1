Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while `shop` is derived purely from the unsigned `shopify-shop-domain`/`x-shopify-shop-domain` header.### Title
Webhook `shop` identity is derived from an unauthenticated header not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates an incoming webhook by validating the HMAC only over the raw request body, while the `shop` identity that is subsequently trusted and dispatched to the app's handler is taken verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed material. This breaks the intended binding of `authenticated_shop == shop_used_for_dispatch`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` verifies authenticity like this: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively from `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` returns only the raw body — no headers are included in the signable material: [3](#0-2) 

Yet `shop` (the value handed to the app as the tenant identifier) is read straight out of the unauthenticated `shopify-shop-domain` header, with no cryptographic tie to the HMAC that was just validated: [4](#0-3) 

This is passed unchanged into the dispatched metadata that the host application's handler acts on: [5](#0-4) 

The equality that should hold is: `shop_bound_by_hmac == shop_used_for_tenant_dispatch`. In this implementation that equality does not exist — the HMAC only proves "this body byte-string was signed with `api_secret_key`" (a secret shared by the app across *all* installed shops), it says nothing about which shop the body is "for." Any (body, hmac) pair that is valid for one shop is equally valid — HMAC-wise — for a request that claims to be from a different shop, because the shop domain is not part of the signed payload.

### Impact Explanation
Because the app's `api_secret_key` is shared across every shop that installs the app, a party who can obtain any one valid `(raw_body, hmac)` pair (e.g., a merchant who develops/tests against their own store and can observe payloads delivered to an endpoint they control, or any actor able to submit a request to the app's webhook endpoint with an arbitrary `shop-domain` header alongside a previously-valid body/HMAC pair) can cause the receiving application to process that body under an attacker-chosen `shop` value. Since `WebhookMetadata.shop` is what downstream host-application code uses to key sessions/data (as documented for this field), this constitutes cross-tenant confusion: data intended for/about one merchant can be attributed to and processed against a different merchant's tenant context, without the receiving app having any way to detect the mismatch using facilities this gem provides. This matches the "Critical - cross-tenant access" impact category, since the trust boundary between tenants is enforced only by a header value that carries no authentication.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately-signed `(body, hmac)` pair (trivial for a merchant on their own shop's webhooks, or via mandatory compliance webhooks such as `customers/data_request` fired for the attacker's own dev/test store) and the ability to POST to the target app's public webhook endpoint with a forged `shopify-shop-domain` header — both are within reach of an unprivileged internet user / app-installing merchant, since this gem performs no additional binding between the header and the signed body. `HmacValidator.validate` and `Webhooks::Registry.process` are the only checks performed, and neither ties `shop` to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signable string used for HMAC verification, or otherwise require the caller/host app to explicitly cross-check `request.shop` against an independently-known value (e.g., the shop associated with the session/install record) before trusting it — and document this requirement prominently, since today `Registry.process` implicitly presents `request.shop` as already-authenticated data.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives (or otherwise obtains) a legitimately signed webhook, e.g. for `customers/data_request`, with body `B` and header `shopify-hmac-sha256: H` where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker crafts a POST to the app's public webhook endpoint reusing body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts this (all required headers present), `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(api_secret_key, B) == H`, which is unaffected by the `shop-domain` header value. [6](#0-5) 
4. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"`, `body: JSON.parse(B)` — the host app now believes this event genuinely originates from `victim.myshopify.com`. [5](#0-4)
