## Title
CallDispatcher.dispatch() has no caller restriction, permanently exposing any token/ETH balance it holds — including "exchange leak" dust from predispatch/postdispatch swaps in IntentGatewayV2/HyperFungibleToken — to theft by any address - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared contract used by `IntentGatewayV2` (predispatch/postdispatch swap composability) and `HyperFungibleToken`/`HyperFungibleTokenUpgradeable` (calldata execution on token receipt) to execute arbitrary `Call[]` batches on behalf of orders and cross-chain transfers. [1](#0-0) 
Its `dispatch()` function is `external` with **no access control** — any address can call it directly and force the `CallDispatcher` to execute arbitrary `to.call{value}(data)` using whatever balance the dispatcher currently holds. [2](#0-1) 

### Finding Description
`IntentGatewayV2.placeOrder` and `IntentsBase._execute`/`_fillCrossChain` route "exchange"-style composability (predispatch swap-then-escrow, postdispatch fill-then-act) through this single shared `CallDispatcher`. Tokens are pushed to the dispatcher, arbitrary swap calldata is executed, and only the tokens that appear in the enumerated `order.inputs` / `order.output.assets` lists are swept back: [3](#0-2) [4](#0-3) 

The sweep is strictly scoped to the assets declared in the order structure. Any token balance the dispatcher ends up holding that is *not* one of the enumerated input/output assets (e.g., DEX reward tokens, referral tokens, an unexpected intermediate hop output, leftover approval dust, or native ETH sent to the `receive()` fallback) is never swept and stays parked in the dispatcher indefinitely. [5](#0-4) 

Because `dispatch()` has no `onlyOwner`/`onlyGateway`/`onlyHost` guard, once any value is stranded in the `CallDispatcher` — from a same-chain fill, a cross-chain HFT calldata mint, or any other integration sharing this singleton — anyone can call `CallDispatcher.dispatch()` directly with a `Call[]` that transfers that balance to themselves, since the call executes with `msg.sender == CallDispatcher` and therefore has full spending rights over its own balance.

This directly parallels the DeFi Saver "exchange leak" incident: an exchange/composability integration point that briefly or permanently held user funds during automated swap routing lacked sufficient access restriction, letting funds "leak" out to an unrelated party instead of being returned to the intended user.

### Impact Explanation
Any token or native value that is not accounted for in the fixed input/output enumeration of an order (or in the HFT calldata-execution flow) permanently accumulates in the shared, unrestricted `CallDispatcher`. Given the dispatcher is reused across every order and every HFT deployment on a chain, this residual balance can grow over time and is fully claimable by any third party — a permanent, unauthorized loss of protocol/user funds with no recovery path, since there is no sweep/owner-only rescue function and no restriction on who can invoke `dispatch()`.

### Likelihood Explanation
Composable swap calldata (Uniswap-style multi-hop swaps, DEX aggregators, lending deposits) commonly produces token amounts or intermediate reward tokens outside the exact enumerated asset list, especially under slippage or fee-on-transfer conditions already acknowledged elsewhere in the code (`placeOrder`'s fee-on-transfer handling). Any solver, order-creator, or bridging application using predispatch/postdispatch calldata with even a slightly mismatched token set will leave a balance in the `CallDispatcher` that is then permanently exposed, and exploitation requires only a single unrestricted call from any address — no privileged position needed.

### Recommendation
Restrict `CallDispatcher.dispatch()` to an allow-listed set of callers (e.g., the `IntentGatewayV2`/`IntentsBase` instance(s) and registered `HyperFungibleToken` deployments), or make the dispatcher single-use/ephemeral per order (e.g., deploy a fresh minimal-proxy dispatcher per call, or restrict execution to a caller-supplied allowlist validated against `msg.sender`). Additionally, ensure the sweep logic in `placeOrder`, `_execute`, and `_fillCrossChain` accounts for all tokens received/sent by predispatch/postdispatch calls (not just the enumerated set), or gives the caller a way to specify/settle unexpected token outputs safely.

### Proof of Concept
1. A solver or order-creator supplies `order.output.call` / `order.predispatch.call` that swaps through a path producing an incidental reward token (or excess of a token not equal to `order.output.assets[i].token`/`order.inputs[i].token`).
2. `_execute`/`placeOrder`'s sweep only iterates the declared `outputsLen`/`inputsLen` token set, so the incidental token balance remains on `CallDispatcher`. [6](#0-5) 
3. Any external address (not the gateway, not the order's parties) then calls `CallDispatcher.dispatch(abi.encode([Call({to: rewardToken, value:0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, rewardToken.balanceOf(dispatcher))})]))` directly. [2](#0-1) 
4. The call succeeds because `dispatch()` has no caller restriction, transferring the stranded balance to the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
