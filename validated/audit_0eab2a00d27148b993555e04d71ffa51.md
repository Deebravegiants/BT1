### Title
Webhook `shop` (and other identity headers) are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` object whose `shop` (and `topic`, `webhook_id`, `api_version`) values are taken directly from unsigned HTTP headers. Because those header values are never part of the signed payload, an attacker who legitimately receives real, correctly-signed webhooks for their own shop can replay that exact signed body while substituting the `x-shopify-shop-domain` (and other) headers to make the app attribute the payload to a different, victim tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies authenticity by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw body: [2](#0-1) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers that are completely outside the HMAC's signable string: [3](#0-2) 

`Registry.process` validates only the body-HMAC and then trusts these unsigned header-derived fields to build the metadata passed to the app's handler: [4](#0-3) 

The binding the gem is supposed to enforce is:
`hmac_valid(body) == (shop, topic, webhook_id that the handler acts on for that body)`

In reality the gem only checks `hmac_valid(body)` and separately, unauthenticated, trusts `shop == header["x-shopify-shop-domain"]`. Any bytes that reach `Registry.process` with a body whose HMAC matches *some* valid secret-holder's traffic will be accepted regardless of which shop's header is attached to it.

### Impact Explanation
An attacker who operates (or compromises) any shop installed on the app receives genuine, correctly HMAC-signed webhooks from Shopify for their own shop. Because the signature covers only the body, the attacker can resend that exact body to the app's webhook endpoint while swapping `x-shopify-shop-domain` to a victim shop's domain (and/or `x-shopify-topic`/`x-shopify-webhook-id`). `Utils::HmacValidator.validate` still succeeds since the body is byte-identical to what was originally signed, and `Registry.process` passes the forged `shop`/`topic` values straight to the app's handler as authentic. Any host application that uses `WebhookMetadata#shop` to look up/scope tenant records (the documented and expected usage pattern shown in `docs/usage/webhooks.md`) will act on attacker-supplied data under a victim tenant's identity — i.e., cross-tenant data injection/confusion, satisfying the Critical "cross-tenant access" impact criterion.

### Likelihood Explanation
Any actor with a legitimate (even a free/trial) shop install can obtain a valid signed webhook body/HMAC pair for themselves, then simply modify the shop-domain header of a replayed HTTP request — no secret material, TLS interception, or privileged access is required. The vulnerable code path (`Registry.process`) is exactly the API path documented in `docs/usage/webhooks.md` for processing webhooks, so this is directly reachable via the gem's own primary API surface, not a misuse of undocumented behavior.

### Recommendation
Bind the identity fields into the signed payload verification, e.g.:
- Require the host app-configured `shop` (from session/tenant context) to equal `request.shop` before dispatching to a handler, or
- Include `shop`, `topic`, and `webhook_id` header values in the HMAC-signable string (mirroring how `AuthQuery#to_signable_string` includes `shop`), so header tampering invalidates the signature, or
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must be cross-checked by the host application against the shop context under which the corresponding topic subscription was registered.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers for `orders/create` webhooks.
2. Shopify sends a legitimate webhook to the app:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over raw body B>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: B
   ```
3. Attacker replays the identical body `B` and HMAC header, but changes only the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC over raw body B>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: B
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B)` [5](#0-4) .
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)` [6](#0-5) , causing the host application to process attacker-controlled data under the victim tenant's identity.

          received_signature = verifiable_query.hmac
