### Title
RAY value overflow in `scaled_to_original` during interest accrual permanently freezes a market - (File: common/src/rates/scaling.rs)

### Summary
Cesanta MJS CVE-2021-46535 is a null/crash-class bug causing process-level denial of service. The analog in XOXNO Lending is a reachable arithmetic panic inside accrual: `accrue_step` computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` before any index-cap check, and `Ray::mul` panics with `GenericError::MathOverflow` when `scaled * index` exceeds `i128::MAX`. Once a market's scaled balances are large enough relative to index growth, the next accrual panics — and since every pool verb accrues first via `global_sync`, the market freezes permanently: no repay, no withdraw, no liquidation, no further `update_indexes`.

### Finding Description
`global_sync` in `contracts/pool/src/interest.rs` loops over elapsed time in `MAX_COMPOUND_DELTA_MS` chunks and calls `accrue_chunk`, which delegates to `accrue_step` in `common/src/rates/simulate.rs`. The first two lines of `accrue_step` unscale the totals:

```rust
// common/src/rates/simulate.rs:60-61
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

`scaled_to_original` is `scaled.mul(env, index)` (`common/src/rates/scaling.rs:14-16`), and `Ray::mul` calls `fp_core::mul_div_half_up`, which panics with `MathOverflow` when the product exceeds `i128::MAX` (`common/src/math/fp.rs:50-52`, `common/src/math/fp_core.rs`). A billion whole units of an 18-decimal asset is `1e9 × 1e18 × 1e27 = 1e54` ray… more precisely `1e36` raw ray for the scaled amount, and `i128::MAX ≈ 1.7e38` is only ~170× above that, so an index growth of ~170× on a whale-scale scaled balance overflows during this *value* computation — before the borrow-index cap (`MAX_BORROW_INDEX_RAY`) can engage, because the cap is applied to the new index after the step, while the panic happens computing the step inputs.

The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`) demonstrates exactly this: at 98% utilization on the XLM rate curve the index passes ~170×, `update_indexes` reverts with `MATH_OVERFLOW`, `borrow_index` is still below `MAX_BORROW_INDEX_RAY`, and subsequent `withdraw` and `repay` revert identically because they accrue first.

### Impact Explanation
Permanent freezing of funds. Once the value overflow is crossed, the panic in `accrue_step` precedes every state change in the market. Suppliers cannot withdraw (`unscale_supply` and `resolve_withdrawal` run after `global_sync`), borrowers cannot repay, liquidators cannot seize, and `clean_bad_debt`/`recapitalize`/`claim_revenue` all flow through the same accrual. `update_indexes` — a permissionless keeper entrypoint — is itself the trigger and becomes permanently reverted. All collateral and supplied cash backing that `(hub, token)` book in the pool is unreachable. The freeze is unrecoverable: no entrypoint writes the index without first computing the overflowing product, and index values only ever increase.

### Likelihood Explanation
Medium. The trigger requires scaled balances near `i128::MAX / 170`, i.e., roughly a billion whole units of an 18-decimal asset supplied, plus sustained high utilization so the borrow index compounds ~170× — reachable only for very high-supply assets and only after extended accrual at the steep segment of the rate curve. However, every input is reachable by unprivileged addresses: any user may `supply`/`borrow` to push utilization into the high-rate segment, and `update_indexes` is permissionless, so timing the final accrual that crosses the cliff needs no privilege. Caps on supply exist per market but the same test lifts only listing-time caps; where caps allow large positions (high-supply tokens), the cliff is reachable. The protocol's own test acknowledges the documented bound in `docs/reference/formulas.md` is wrong, so the safety margin assumed at design time does not hold.

### Recommendation
Saturate rather than panic in the value-unscaling path used by accrual, or enforce the index cap before the value computation:

- In `accrue_step` (`common/src/rates/simulate.rs`), clamp `borrow_index`/`supply_index` to `MAX_BORROW_INDEX_RAY` / the supply equivalent *before* calling `scaled_to_original`, so accrual still finalizes at the capped index instead of trapping.
- Alternatively, add saturating variants (`mul_div_*_saturating`, already used by `calculate_scaled_cap` in `common/src/rates/scaling.rs:26-32`) for `calculate_utilization`/`accrue_step`'s unscale calls, so utilization clamps at 1 and accrual continues bounded.
- Validate at market listing that `total_supply_cap × 10^(27−decimals) × MAX_BORROW_INDEX_RAY < i128::MAX` so no listable market can reach the cliff at all — extend `require_cap_within_asset_domain` to include the index ceiling term.

### Proof of Concept
Existing harness test demonstrating the freeze end-to-end — `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`:

```rust
let principal = BILLION * 10i128.pow(18);          // whale supply, 18 decimals
t.supply_raw(BOB, "BIG18", principal);
t.borrow_raw(ALICE, "BIG18", principal / 100 * 98); // ~98% utilization
// advance years at XLM curve steep segment:
//   try_update_indexes_for("BIG18") -> Error(Contract, MATH_OVERFLOW)
//   book("BIG18").borrow_index < MAX_BORROW_INDEX_RAY  (cap never engaged)
//   try_withdraw_raw(BOB, "BIG18", 1) -> MATH_OVERFLOW
//   try_repay(ALICE, "BIG18", 1.0)  -> MATH_OVERFLOW
```

Attack path (all unprivileged): an attacker supplies a very large amount of a high-decimal listed asset, borrows most of it to pin utilization on the steep curve segment, and lets index growth compound — anyone can then call `update_indexes` to cross the cliff. From that ledger onward every verb touching that market reverts in `accrue_step` → `scaled_to_original` → `Ray::mul` (`common/src/math/fp.rs:50-52`), permanently freezing all funds in the `(hub, token)` book.
