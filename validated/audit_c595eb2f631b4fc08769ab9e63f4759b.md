### Title
Unsigned `topic`/`shop-domain` headers permit cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates only the raw request body against the app's shared `api_secret_key`, then trusts the `topic` and `shop-domain` values taken from unsigned HTTP headers to select the handler and build `WebhookMetadata`. Because the HMAC never covers these headers, and there is no per-delivery replay tracking, any attacker who can obtain one validly-signed webhook body (e.g., by installing the app on their own development shop and receiving their own legitimate webhook) can resend that exact body with a forged `x-shopify-shop-domain`/`x-shopify-topic` header pointing at an arbitrary victim shop, and it will still pass validation.

### Finding Description
The invariant that should hold is: **shop authenticated by the signature == shop delivered to the handler**. Tracing the code shows this does not hold.

`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unsigned headers [2](#0-1) . `Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, raw_body)` and compares it to the `hmac` header [3](#0-2)  — it never incorporates `shop`, `topic`, or `webhook_id` into the signed material. `Registry.process` then uses the *unsigned* `request.topic` to look up the handler and the *unsigned* `request.shop` to build `WebhookMetadata`, which is passed unmodified to the app's handler: [4](#0-3) .

Critically, `api_secret_key` is a single per-app secret shared across **all** shops that install the app — it is not shop-specific. This is the same secret used regardless of which merchant's webhook is delivered. So the HMAC only proves "this body was sent by Shopify for this app," not "this body pertains to this shop." Since the header fields are outside the signed string, an attacker who operates their own development shop with the app installed can:
1. Install the app on their own shop and receive a legitimate webhook (valid `raw_body` + valid `hmac` computed with the app's real secret, since Shopify signs it for them too).
2. Replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint, substituting `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `HmacValidator.validate` still passes, because the signature check only depends on `raw_body`, which the attacker did not modify.
4. `Registry.process` builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the registered handler, which is application code that typically loads a session/store record keyed by `shop` and performs GraphQL/REST operations "on behalf of" that shop.

There is also no delivery-id or timestamp bookkeeping anywhere in `Registry.process` or `Request` to bound re-delivery or detect a replayed/relabeled payload — the same body can be resent indefinitely with different `shop`/`topic` header values, confirmed by the absence of any `webhook_id` de-duplication logic in `registry.rb`.

None of the existing guards catch this: `HmacValidator.validate` only binds the body, not headers [5](#0-4) ; there is no `ShopValidator.sanitize!` call in `process`; there is no JWT/`state` check in this path at all — `Registry.process` has no session/JWT step, it accepts `Request` objects built directly from raw HTTP input [6](#0-5) .

### Impact Explanation
An attacker who legitimately installs the target app on their own (even free/dev) shop can obtain arbitrarily many validly-HMAC'd webhook bodies and relabel the `shop-domain`/`topic` headers to impersonate any other merchant using the same app, since the app-level secret is identical for every tenant. Depending on the host app's handler logic (which typically trusts `WebhookMetadata#shop` to select the merchant's stored session/access token and perform actions), this can drive the app to read or mutate a different, arbitrary merchant's data using the victim's actual access token loaded by shop domain — a cross-tenant data access/mutation issue, matching "Critical - cross-tenant access."

### Likelihood Explanation
Preconditions are minimal and fully within the attacker's own control: register a development shop, install the target app, trigger any webhook topic supported by the app (e.g., `orders/create`) to capture one valid `(raw_body, hmac)` pair, then POST it to the app's public webhook endpoint with a forged `shop-domain` header naming any target shop that also uses the app. No credentials, JWTs, or `api_secret_key` values are needed. This is trivially repeatable against arbitrary victim shops that use the same app installation, and can be automated.

### Recommendation
Do not trust `shop-domain`/`topic`/`webhook_id` headers as unauthenticated identifiers. At minimum:
- Include the `shop-domain` (and ideally `topic`, `webhook_id`) in the signed material verified by `HmacValidator`, or require the host app to independently verify the shop against its own webhook delivery records before trusting `WebhookMetadata#shop`.
- Track `webhook_id` (delivery id) per shop with a bounded TTL and reject duplicates/replays.
- Document/enforce that `WebhookMetadata#shop` must not be used to bypass or replace normal session/authorization derivation.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_process_accepts_forged_shop_header_with_replayed_valid_hmac
  handler_called = false
  received_shop = nil

  handler = TestHelpers::FakeWebhookHandler.new(
    lambda do |data|
      received_shop = data.shop
      handler_called = true
    end,
  )

  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: @topic, path: "path", delivery_method: :http, handler: handler,
  )

  # Attacker legitimately captured this (raw_body, hmac) pair from their OWN shop's webhook
  hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, "{}")

  forged_headers = {
    "x-shopify-topic" => @topic,
    "x-shopify-hmac-sha256" => Base64.encode64(hmac), # unchanged, still valid
    "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unsigned
    "x-shopify-webhook-id" => "attacker-captured-id",
    "x-shopify-api-version" => "2024-01",
  }

  forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)

  # HMAC validation succeeds despite shop being forged, proving shop is not authenticated
  assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))

  ShopifyAPI::Webhooks::Registry.process(forged_request)

  assert(handler_called)
  assert_equal("victim-shop.myshopify.com", received_shop) # attacker fully controls "authenticated" shop
end
```
This demonstrates that `WebhookMetadata#shop` (the value handed to app code as "the authenticated shop") can be set to an arbitrary value chosen by the attacker while `HmacValidator.validate` still returns `true`, breaking the binding `shop authenticated by signature == shop delivered to handler`.
