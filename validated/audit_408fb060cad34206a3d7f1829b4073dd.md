I found a concrete vulnerability class match: a fee-on-transfer/deflationary token incompatibility, exactly matching the reported bug class, exists in the Tron variant of the intent-based bridge contract.

### Title
Deflationary/Fee-on-Transfer Token Escrow Over-Crediting in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` credits escrow accounting with the user-declared (fee-reduced) input amount instead of the amount the contract actually receives after `safeTransferFrom`. For any deflationary/fee-on-transfer ERC20 (a TRC20 variant is trivial to deploy and used as an order input token), the contract's real token balance ends up permanently short of the sum of `_orders[commitment][token]` it has promised to fillers/refund recipients.

### Finding Description
In the non-predispatch branch of `placeOrder`, the token is pulled in with a plain `safeTransferFrom` and no before/after balance check: [1](#0-0) 

```solidity
} else {
    for (uint256 i; i < inputsLen;) {
        ...
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
```

`reducedInputs[i].amount` is simply `order.inputs[i].amount` minus the protocol fee basis points — it is never reconciled against the actual amount the contract received: [2](#0-1) 

The predispatch branch has the same flaw: it measures `balance` at the dispatcher and computes `dust = balance - requiredAmount`, but again credits `_orders[commitment][token] += reducedInputs[i].amount` (the nominal, pre-fee-adjusted figure) rather than the actually-swept amount: [3](#0-2) 

This is precisely the bug class in the external report: a deflationary/fee-on-transfer token causes the contract's internal accounting (analogous to SafeDollar's reward-pool LP accounting) to diverge from the token's real balance, because the code trusts the nominal transfer amount rather than measuring the actual delta.

Contrast this with the canonical EVM `IntentGatewayV2.sol`, which was hardened against exactly this class of bug — it measures `balanceOf` before and after the transfer and overwrites `order.inputs[i].amount` with the real received amount before computing the commitment and crediting escrow: [4](#0-3) 

and there is a dedicated regression test proving this is intended, security-relevant behavior on the canonical contract: [5](#0-4) 

The Tron variant under `evm/tron/contracts/apps/` was evidently forked from an earlier version of `IntentGatewayV2.sol` before this fix was applied, and it never received the balance-delta correction.

### Impact Explanation
`_orders[commitment][token]` is a promise the contract makes to pay out `amount` of `token` to a filler (via `RedeemEscrow`) or to the user (via `RefundEscrow`/cancel) — reachable by any relayer delivering a signed cross-chain message or any user cancelling on the source chain: [6](#0-5) 

Because escrow credits are inflated relative to the token actually custodied, the sum of outstanding `_orders[*][token]` promises across all orders in that deflationary token exceeds the contract's real balance. Whichever order's `withdraw` executes once the pool is depleted will have its `token.call(...transfer...)` fail, causing `TransferFailed()` to revert the whole withdrawal — since `_filled[commitment]` is only durably set if the call succeeds, that order becomes permanently unfillable and un-refundable, permanently freezing that user's or filler's escrowed funds. This satisfies the "permanent freezing of funds" impact bar.

### Likelihood Explanation
No privileged access is required: any user can call `placeOrder` with a deflationary/fee-on-transfer TRC20 as an input token, and any relayer can deliver the resulting `RedeemEscrow`/`RefundEscrow` message once a solver fills or the order times out — this is the normal intent-fulfillment flow, not an admin or governance action. The shortfall accumulates automatically on every order placed in such a token, with no attacker cooperation needed beyond choosing (or a user unknowingly using) a deflationary token as an input asset.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom` (and after the predispatch sweep), and derive `reducedInputs[i].amount`/the escrow credit from the actual received delta rather than from the caller-declared `order.inputs[i].amount`.

### Proof of Concept
1. Deploy a TRC20 token with a transfer fee (e.g., 1% burned/redirected on every transfer), mirroring `FeeOnTransferToken` used in the EVM test suite: [7](#0-6) .
2. Call `IntentGatewayV2.placeOrder` on the Tron deployment with this token as an input, amount = 1000. `safeTransferFrom` moves only 990 to the contract, but `_orders[commitment][token] += reducedInputs[i].amount` credits 1000 (minus any protocol fee applied to the nominal 1000, not the received 990).
3. Repeat with a second unrelated order using the same token; the contract's on-chain balance is now short by the accumulated transfer-fee deltas relative to the sum of all `_orders[*][token]`.
4. Trigger `onAccept`/`RedeemEscrow` or `cancelOrder`/`RefundEscrow` for the orders in sequence; once accumulated deficits exceed the contract's remaining balance, `withdraw`'s `token.call(...transfer...)` fails and reverts with `TransferFailed`, permanently freezing that order's escrow.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
