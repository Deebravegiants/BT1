### Title
Emporium-min ERC20 drain via zero-length `erc20TokenAddresses` bypassing all balance/value-conservation checks - ([File: contracts/types/Dimensions.sol])

### Summary
When `dimensions.tokenNumber == 0` (and `circomData.erc20TokenAddresses.length == 0`), the protocol's own `CircomDataBuilder.formInputForCircom` routes to a dedicated, intentionally-reduced `formInputEmporiumMin` public-input path [1](#0-0) . In this state, every balance/value-conservation loop in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` iterates zero times, while the number and content of `EmporiumStack.ops` (arbitrary `endpoint`/`callData`/`value`) is completely unconstrained by `tokenNumber`. Combined with `signerAddress == address(0)` skipping the EIP-712 signature check in `verifyWallet`, an attacker can force Emporium to execute an arbitrary low-level call (e.g. `IERC20.transfer(attacker, fullBalance)`) that drains ERC20 tokens Emporium holds on behalf of other users, with zero on-chain accounting of the movement.

### Finding Description
The broken equality is: **VALUE CONSERVATION** — `tokens leaving Emporium via op == -deltaAmountChanges it received`. With `circomData.erc20TokenAddresses = []`:

- `deltaAmountChanges = new int256[](0)` in `Hinkal._externalTransact` [2](#0-1) .
- `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` are built from the same empty array [3](#0-2) , and the reconciliation loop that would normally catch a balance drop never executes because it iterates `circomData.erc20TokenAddresses.length` (0) times [4](#0-3) .
- `Hinkal.transact`'s own outer balance/slippage/value-conservation loop is likewise skipped entirely since it also iterates `circomData.erc20TokenAddresses.length` [5](#0-4) .

Meanwhile, `stack.ops` is decoded independently from `circomData.externalActionData.externalActionMetadata` and its length has no relationship to `dimensions.tokenNumber` [6](#0-5) . With `stack.signerAddress == address(0)`, `verifyWallet` returns immediately after marking the message used, without any signature check [7](#0-6) , and each op falls into the "stateless" branch, calling `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium's own context (so `msg.sender` in that call is the Emporium contract) [8](#0-7) . There is no allowlist on `op.endpoint`/`op.callData` beyond blocking the two `IHinkalWallet` selectors.

`dimensionsCheck` in `HinkalHelper.sol` never enforces `tokenNumber > 0`; it only checks that all the array lengths match `dimensions.tokenNumber` [9](#0-8) , so `tokenNumber == 0` is a fully legal dimension. This zero-token dimension is not a theoretical edge case — it is explicitly wired into `formInputForCircom`, which special-cases `HINKAL_EMPORIUM_ACTION_ID` with an empty token array to a minimal 3-signal public input (`emporiumMessage`, `timeStamp`, `calldataHash`) [1](#0-0) , confirming the protocol intentionally supports an "Emporium-min" proof path with no UTXO/token public signals at all.

Attacker call sequence:
1. Attacker deploys/targets an ERC20 that Emporium already holds (accumulated from other users' prior swap/withdraw legs).
2. Attacker builds `EmporiumStack{signerAddress: address(0), ops: [{endpoint: token, invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.transfer,(attacker, token.balanceOf(Emporium)))}], ...}`.
3. Attacker sets `dimensions = {tokenNumber:0, nullifierAmount:0, outputAmount:0}`, `circomData.erc20TokenAddresses = []`, `circomData.amountChanges = []`, generates a valid proof for the Emporium-min circuit (no UTXOs spent, no signature needed for wallet-less ops), and calls `Hinkal.transact`.
4. `performHinkalChecks` and `verifyProof` pass; `rootHashExists` passes (root is unrelated to any spend since no nullifiers). `_externalTransact` calls `EmporiumUpgradeable.runAction`, which executes the token transfer and returns `utxoSet` of length 0 (since `circomData.erc20TokenAddresses.length == 0`).
5. No balance check anywhere in the call stack observes the drained ERC20 balance because every check that would compare `balancesBefore`/`balancesAfter` or `oldBalances`/`newBalances` is gated by the same empty `erc20TokenAddresses` array.

Existing guards fail specifically because they are all indexed/looped over `circomData.erc20TokenAddresses`/`dimensions.tokenNumber`, and none of them independently bound `stack.ops.length`, `op.endpoint`, or `op.callData` to that dimension.

### Impact Explanation
Critical: theft of protocol-custodied ERC20 tokens belonging to other users who deposited into or are mid-flight through Emporium. The attack is fully repeatable for every ERC20 balance Emporium accumulates and requires no privileged role — only the ability to submit a self-generated proof and craft `CircomData`/`Dimensions`/`EmporiumStack`, consistent with the unprivileged attacker model in scope.

### Likelihood Explanation
Preconditions are low-cost and attacker-controlled: no special tree state is required beyond a valid Hinkal root (since `nullifierAmount == 0` means no UTXOs are spent), Emporium must merely hold a nonzero ERC20 balance from prior legitimate flows (a normal, expected operational state for the Emporium relayed-swap design), and the attacker needs only to generate one proof for the reduced "Emporium-min" circuit and pay gas. There is no owner/relay/whitelist gate blocking the call path since `circomData.relay` can be `address(0)` with `originalSender == sender`. This is directly and repeatably executable by any EOA once Emporium holds a drainable balance.

### Recommendation
Do not let the Emporium-min path bypass value conservation for ops that touch tokens outside `circomData.erc20TokenAddresses`. Specifically:
- Require `dimensions.tokenNumber > 0` (or otherwise track every token balance Emporium could touch) whenever `stack.ops` contains any operation whose `endpoint` is capable of moving ERC20/ETH out of Emporium.
- Alternatively, have `EmporiumUpgradeable.runAction` snapshot and re-check balances for every distinct `op.endpoint` address that is an ERC20-like contract (not just addresses listed in `circomData.erc20TokenAddresses`), so token movements can never bypass the "how did Emporium's balance change" reconciliation purely by omitting the token from the circom-dimension arrays.
- At minimum, restrict the "Emporium-min" (`tokenNumber == 0`) proof path to `EmporiumOperation`s that are provably incapable of transferring value out of Emporium (e.g., disallow direct calls to any address holding a nonzero balance, or require `op.value == 0` and disallow calls whose target is a token Emporium currently holds).

### Proof of Concept
Hardhat test plan:
1. Deploy Hinkal, `EmporiumUpgradeable`, register Emporium as `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]`, deploy a mock ERC20 (`USDC`).
2. Seed Emporium with `USDC` balance by simulating a prior legitimate swap/withdraw leg leaving residual balance in Emporium (mint directly to Emporium for test simplicity).
3. As attacker (unprivileged EOA), build `EmporiumStack{signerAddress: address(0), ops: [{endpoint: USDC, invokeWallet: false, value: 0, callData: USDC.interface.encodeFunctionData("transfer", [attacker, EmporiumUSDCBalance])}]}`.
4. Construct `Dimensions{tokenNumber:0, nullifierAmount:0, outputAmount:0}` and `CircomData{erc20TokenAddresses: [], amountChanges: [], onChainCreation: [], slippageValues: [], inputNullifiers: [], outCommitments: [], externalActionData:{externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionAddress: Emporium, externalActionMetadata: abi.encode(stack)}, ...}`.
5. Generate a valid proof for the Emporium-min verifier registered at `buildVerifierId(dimensions, HINKAL_EMPORIUM_ACTION_ID)` (no UTXO spend needed).
6. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker.
7. Assert: `USDC.balanceOf(attacker)` increased by exactly Emporium's prior balance; `USDC.balanceOf(Emporium) == 0`; and no entry in `amountChanges`/`circomData.erc20TokenAddresses` recorded this movement (array lengths are 0), proving the drain was invisible to the value-conservation checks in both `Hinkal.sol` and `EmporiumUpgradeable.sol`.
