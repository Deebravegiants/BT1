### Title
Local-only success determination for user-centric signups bypasses backend enrollment confirmation, causing misattributed signup success - ([File: src/plans/mod.rs])

### Summary
The reported Beanstalk bug is a class of "paired-state" accounting flaw: when `stalk` is minted, the code path that should also mint the corresponding `roots` is skipped, so the two values that must move together fall out of sync, letting a user be credited (or under-credited) unfairly. The closest reachable analog in `orb-core` is in `MasterPlan::do_signup`, where the "success" determination for the signup — the local analog of the paired state that gates whether a user is credited a successful, backend-confirmed identity — is derived from purely local state instead of the backend confirmation step that normally produces it.

### Finding Description
In `src/plans/mod.rs`, `do_signup` computes `signup_reason` locally (`Normal`/`Fraud`/`Failure`) from the pipeline result and the (FOSS-stubbed) fraud check, then branches on `user_centric_signup`: [1](#0-0) 

When `user_centric_signup` is `true` (and the config doesn't override it), the code **never calls `enroll_user`** — the plan that performs the actual backend round trip (`signup_post::request` + repeated `signup_poll::request`) that verifies the iris signature, checks for duplicates/fraud on the backend side, and only then returns `enroll_user::Status::Success`: [2](#0-1) 

Instead, `debug_report.enrollment_status` is set directly to `Success` or `Error` purely from the orb-local `signup_reason`, and `result.success` is derived from that same locally-set status: [3](#0-2) 

This mirrors the report's bug class: two states that are supposed to be updated together via one authoritative path (backend-confirmed enrollment ⇒ success flag) are instead updated through a shortcut that sets the "credited" flag (`enrollment_status`/`success`) without going through the step that is supposed to produce it (the backend's confirmation via `signup_post`/`signup_poll`). Just as Beanstalk's `stalk` was minted without the paired `roots` calculation, here the orb's local "success" state is set without the paired backend verification that is the actual source of truth for whether a signup should be accepted.

`user_centric_signup` is a flag returned by the backend itself via `user_status::request` (`orb_qr_link::UserData::user_centric_signup`), so this is not an attacker-controlled bypass by construction, but it means the orb's own bookkeeping (`SignupStatus::Success`, UI "signup success", `orb_relay`'s `SignupEnded{success: true}`, and metrics like `main.count.signup.result.success.successful_signup`) is emitted purely from local pipeline/fraud state whenever this backend flag is set, with no cross-check against the backend's own enrollment/duplicate/fraud verdict for that signup. [4](#0-3) 

### Impact Explanation
If `user_centric_signup` is set, the orb self-attests success/failure based solely on on-device pipeline output and fraud detection (which is itself explicitly stubbed out — `N_FRAUD_CHECKS = 0`): [5](#0-4) [6](#0-5) 

Combined with the `user_centric_signup` branch skipping the network-based `enroll_user`/`signup_post`/`signup_poll` round trip, a signup can be marked `Success` and surfaced to the UI/relay/metrics as a completed, credited signup without the backend ever confirming duplicate-detection, verification, or fraud status for that specific attempt. This is analogous to crediting a user (minting the "success" credit) without performing the check/step (paired "roots" mint / backend confirmation) that is supposed to gate that credit — i.e., a misattributed signup-success state.

### Likelihood Explanation
The path is reached deterministically whenever the backend sets `user_centric_signup: true` for a session (which is an intended backend-controlled behavior, not a user-triggerable bypass), so likelihood of the code path executing is moderate-to-high in whatever fleet configuration this flag is used, but exploitation as a security bypass depends entirely on backend-side trust in the orb's self-reported state and on the fact that fraud checks are compile-time stubbed to always return "no fraud" in this codebase.

### Recommendation
Ensure the "success"/`enrollment_status` credit for `user_centric_signup` sessions is only set after an authoritative confirmation step equivalent to `enroll_user`'s backend round trip (or an explicit backend acknowledgment tied to this specific `signup_id`), rather than deriving it solely from local `signup_reason`. At minimum, do not allow the local success determination to bypass a real fraud-check/duplicate-check backend response for this signup.

### Proof of Concept
Not applicable — this is a logic/control-flow issue rather than an externally triggerable exploit; conceptually: (1) backend marks a user's QR data with `user_centric_signup = true`; (2) orb runs biometric capture/pipeline; (3) `detect_fraud` always returns `false` (stubbed); (4) `signup_reason` becomes `Normal`; (5) `do_signup` sets `enrollment_status = Success` and treats the signup as fully successful without ever invoking `enroll_user`'s backend confirmation (`signup_post`/`signup_poll`).
