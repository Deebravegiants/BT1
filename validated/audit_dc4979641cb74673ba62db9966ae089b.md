### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-shop impersonation via header spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop`, `topic`, and `webhook_id` values that are handed to the app's webhook handler are read directly from unauthenticated HTTP headers and are never included in the signed payload. Any party able to obtain one valid `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC pair while substituting the `shop-domain` header for an arbitrary victim shop, and the gem will accept it as an authenticated webhook for that victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts the `shop`, `topic`, `webhook_id`, and `api_version` from headers, but its `to_signable_string` used for HMAC verification returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac` header value: [2](#0-1) 

`Registry.process` gates on this HMAC check and then forwards `request.shop` — read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — into the `WebhookMetadata` that is passed to the app's registered handler: [3](#0-2) 

The equality the system implicitly relies on is:
`shop (HMAC-verified)` == `shop (delivered to handler)`

In reality the code only verifies:
`HMAC(raw_body, api_secret_key) == received_hmac`

and separately, unauthenticated:
`shop (delivered to handler) = header["shop-domain"]`

Because the webhook signing secret (`api_secret_key`) is the app's single client secret, shared across every shop that has installed the app, any shop owner that has legitimately installed the app can trigger a webhook delivery to themselves (e.g. `app/uninstalled`, or any topic with a body they control/can predict), capture the resulting valid `(raw_body, hmac)` pair, and then send a forged HTTP request directly to the app's webhook endpoint with the same body/hmac but an arbitrary `shop-domain` header pointing at a different, victim shop. `HmacValidator.validate` will pass, and the app's handler will process the request believing it originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: cross-tenant impersonation of webhook events. Depending on how the host application's registered handler uses `WebhookMetadata#shop` (common patterns include marking a shop as uninstalled/deleting its stored access token, updating billing state, or triggering shop-scoped side effects), an attacker who is merely a legitimate installer of the app on their own store can cause the app to act on behalf of an arbitrary victim shop domain — e.g., forcing a false "uninstall" cleanup for a victim shop's stored session/access token, or forging other shop-scoped webhook effects. This is a cross-tenant action performed without ever needing the victim's credentials, `api_secret_key`, or an access token, satisfying the Critical/High bar of "cross-tenant access" through a spoofed identity binding.

### Likelihood Explanation
The only prerequisite is legitimately installing the app once (a normal, unprivileged action any merchant can do) to obtain one valid `(body, hmac)` pair, then issuing a normal HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or privileged access are required, and the required body content is trivial to obtain for topics with fixed/empty payloads (e.g. `app/uninstalled`).

### Recommendation
Bind the shop identity to the signature verification rather than trusting header data separately, e.g.:
- Include the `shop-domain` (and ideally `topic`, `webhook_id`) values as part of the string that is HMAC-verified, or
- After HMAC validation, cross-check `request.shop` against an internal, already-established registration/session record before invoking the handler, rejecting webhooks for shops the app doesn't recognize as expecting the given webhook_id, or
- At minimum, document/enforce that consuming applications must independently verify the `shop` against their own session store keyed by more than the header value alone.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker-shop.myshopify.com`), a normal unprivileged action.
2. Trigger a webhook with fixed/predictable body content, e.g. `app/uninstalled`, which typically has an empty JSON body `"{}"`. Capture the request:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <valid-hmac-for-"{}">
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {}
   ```
3. Replay this request to the app's webhook endpoint, changing only the shop header:
   ```
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same-valid-hmac-for-"{}">
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {}
   ```
4. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC only over the body `"{}"` [4](#0-3) , which matches, so validation passes [3](#0-2) , and the registered `app/uninstalled` handler is invoked with `shop: "victim-shop.myshopify.com"` — even though the request never actually originated from Shopify on behalf of that victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
