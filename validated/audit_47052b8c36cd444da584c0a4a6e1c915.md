### Title
`WrappedHyperFungibleToken.send` mints unbacked tokens on destination when the underlying is a fee-on-transfer/deflationary/rebasing ERC20 - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but never checks how much the contract actually received. It then builds and dispatches a cross-chain `Message` carrying the nominal `params.amount`, which the peer `HyperFungibleToken.onAccept` on the destination chain mints in full to the beneficiary. If the underlying token charges a transfer fee, is deflationary, or rebases, the wrapper's actual locked balance is less than `params.amount`, yet the full nominal amount is minted cross-chain — an unbacked mint that under-collateralizes the wrapped token supply.

### Finding Description
In `send()`:
```solidity
function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
    uint256 msgValue = msg.value;
    if (_isWeth && msgValue >= params.amount) {
        msgValue = msgValue - params.amount;
        IWETH(_underlying).deposit{value: params.amount}();
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }

    DispatchPost memory request = _buildDispatchPost(params);
    ...
``` [1](#0-0) 

`_buildDispatchPost` embeds `params.amount` — the requested amount, not the actual balance delta — directly into the cross-chain `Message`:
```solidity
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,
    data: params.data
}));
``` [2](#0-1) 

On the destination chain, `HyperFungibleToken.onAccept` mints exactly `message.amount` to the beneficiary with no reference to what was actually escrowed on the source chain:
```solidity
Message memory message = abi.decode(request.body, (Message));
address beneficiary = _toAddr(message.to);
_mint(beneficiary, message.amount);
``` [3](#0-2) 

The same pattern (and same bug) exists in the upgradeable variant, `WrappedHyperFungibleTokenUpgradeable.send`, which also calls `safeTransferFrom(msg.sender, address(this), params.amount)` and forwards `params.amount` unmodified. [4](#0-3) 

This is a variant of the exact bug class described in the external report: the contract assumes `transferFrom` delivers the exact requested amount, without verifying via balance-before/after accounting. Notably, the codebase demonstrates awareness of this exact hazard elsewhere — `IntentGatewayV2.placeOrder` explicitly snapshots balances before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount before computing the escrow/commitment:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [5](#0-4) 

`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` lack this equivalent protection.

### Impact Explanation
For any underlying token with fee-on-transfer, deflationary burn, or rebasing behavior, each `send()` call under-collateralizes the wrapper: the contract locks less than `params.amount` while the peer `HyperFungibleToken` mints `params.amount` in full on the destination chain. Repeated transfers accumulate an ever-growing shortfall between total minted wrapped supply and the wrapper's actual underlying balance. Eventually, redemptions (`onAccept` transferring underlying back out via `safeTransfer`) will fail for the last redeemers because the wrapper's underlying balance is insufficient — resulting in permanent freezing of funds for some users and an insolvent bridge pool. This is a concrete instance of "unbacked mint" / "permanent freezing of funds" as defined in scope.

### Likelihood Explanation
Exploitability depends entirely on which underlying token the wrapper owner configures via `configure()`/`_underlying`. If a fee-on-transfer, deflationary, or rebasing ERC20 is ever wrapped (a configuration decision, not an attack), every single `send()` call from any unprivileged user triggers the shortfall — no special conditions or race are required, making likelihood high once such a token is in use. The project's own test suite (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) shows fee-on-transfer tokens are a real class the team explicitly considers testing for the IntentGateway; that same handling was not carried over to `WrappedHyperFungibleToken`.

### Recommendation
In `WrappedHyperFungibleToken.send` (and the upgradeable variant), measure the underlying token balance before and after the `safeTransferFrom` call, and use the actual received amount (rather than `params.amount`) when building the dispatched `Message` and in the `Sent` event. Alternatively, explicitly document and enforce (e.g., via an allowlist check) that only standard, non-fee, non-rebasing ERC20 tokens may be configured as `_underlying`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer token (e.g., 1% fee burned on every transfer).
2. User calls `send({ amount: 1000, ... })`. `safeTransferFrom` moves 1000 tokens from user, but the wrapper's balance only increases by 990 (10 burned as fee).
3. `_buildDispatchPost` still embeds `amount: 1000` in the message body, and the ISMP request is dispatched with this value.
4. On the destination chain, `HyperFungibleToken.onAccept` calls `_mint(beneficiary, 1000)`, minting 1000 wrapped tokens although only 990 underlying tokens back them.
5. Repeating this drains the backing ratio; eventually a user trying to bridge wrapped tokens back (`onAccept` unlocking underlying via `safeTransfer`) finds the wrapper's underlying balance insufficient to fulfill withdrawal, reverting and freezing funds.
