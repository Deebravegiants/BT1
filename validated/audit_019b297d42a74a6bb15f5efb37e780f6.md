### Title
Webhook shop-domain attribution is not covered by the HMAC signature, allowing tenant-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The external report's bug class is: a verifier derives a security-critical randomness/decision from only part of the data it trusts, while other attacker-influenced inputs that feed the same decision are left unauthenticated. The closest reachable analog in this gem is `ShopifyAPI::Webhooks::Request`/`ShopifyAPI::Webhooks::Registry`: the HMAC that authenticates an inbound webhook is computed only over the raw request body, while the `shop` value that identifies *which tenant* the webhook belongs to is read from an HTTP header that is completely outside the HMAC's coverage.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Request#shop` is read directly from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is never mixed into `to_signable_string`: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC (which covers only the body) and then trusts `request.shop` unconditionally to build the `WebhookMetadata` that is handed to the app's handler — the tenant-identifying field is never checked against anything the HMAC protects: [4](#0-3) 

`HmacValidator.validate_signature` proves the equality it checks is `HMAC(secret, raw_body) == received_signature` — nothing about `shop` is part of that equality: [5](#0-4) 

The broken binding, stated as an equality that the code fails to enforce:
`shop_header_used_for_tenant_attribution == shop_that_the_HMAC_actually_authenticates`
Before the request: whatever tenant genuinely triggered the webhook and signed the body.
After an attacker-controlled request with the same body/HMAC pair but a substituted `shopify-shop-domain` header: the app processes the event as belonging to a different, attacker-chosen shop, while the HMAC check still reports success because it only ever validated the body bytes.

Any entity capable of triggering a real webhook delivery from Shopify to the app (e.g., by installing the app on their own store and performing an action that fires a webhook, such as `orders/create`) legitimately obtains a body+HMAC pair signed with the app's real `api_secret_key`. Nothing in this gem stops that same body+HMAC pair from being re-delivered to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain — the signature still validates because it was never bound to the shop field in the first place.

### Impact Explanation
This is a cross-tenant identity confusion: the value the app's webhook handler uses to key its data (`WebhookMetadata#shop` passed straight from the unauthenticated header) can be forged independently of the cryptographically verified body. For any multi-tenant app built on this gem, this allows an attacker who can obtain one authentic signed webhook delivery to spoof events under an arbitrary victim shop, corrupting or exfiltrating cross-tenant state (e.g., triggering `orders/create`-style processing that credits/debits or otherwise mutates a victim shop's records). This matches the "cross-tenant access" criterion for Critical/High impact.

### Likelihood Explanation
Exploitation requires only unprivileged internet access: an attacker installs the app on a shop they control (a normal, unprivileged action for any Shopify developer), triggers any webhook topic the app subscribes to, captures the resulting `raw_body` + `x-shopify-hmac-sha256` pair delivered to the app's public endpoint, and replays it to the same endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to the victim's domain. No access token, `api_secret_key`, or privileged credential is needed — the entire signature is body-only, so the header substitution is free.

### Recommendation
Bind the tenant-identifying field into the same value that is HMAC-verified. Concretely, `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should incorporate the `shop`, `topic`, and `webhook_id` header values (not just the raw body) before computing/verifying the HMAC, so that tampering with any of the values the handler later trusts invalidates the signature — analogous to the report's recommendation to fold in "chunk length, sample data, commitments, proofs, indices" rather than hashing a subset of the verifier's inputs.

### Proof of Concept
1. Attacker creates a Shopify development store and installs the target app, obtaining webhook deliveries signed with the app's real `api_secret_key`.
2. Attacker triggers a subscribed webhook topic (e.g., `orders/create`) on their own store, capturing the raw body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(secret, B)`.
3. Attacker resends an HTTP POST to the app's public webhook endpoint with:
   - body `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged, still valid because verification only checks `B`)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H`: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes the event as if it originated from the victim shop.
