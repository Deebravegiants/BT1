### Title
`canGraduate` unguarded subtraction underflows and permanently DoSes a token's curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` computes `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with no floor check. `assetReserve` is the pair's live, rounding-mutated reserve; `_launchTimeVirtualLtReserve` is a fixed value recovered from the immutable `k()`. `Pair.swap`'s `+1` K-invariant slack (`(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k`) permits the *actual* product `tokenReserve * assetReserve` to sit strictly below `k` after a sequence of buys/sells, without reverting. Because `canGraduate` is invoked on **every** `Bonding.buy`, `Bonding.sell`, and `triggerGraduation` call, a single unprivileged trader who drives the pair's rounding state to the edge of that slack can make the subtraction underflow, panic-revert, and permanently brick all trading and graduation for that token — an analog of the OpenSSL `GENERAL_NAME_cmp` NULL-pointer bug, where a routine "comparison" helper invoked on a hot, attacker-reachable path crashes on a crafted-but-otherwise-valid state instead of handling it safely.

### Finding Description
`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve as an exact identity: [1](#0-0) 

`canGraduate` then subtracts that fixed value from the pair's *live* `assetReserve`: [2](#0-1) 

This subtraction assumes `assetReserve >= k()/TOTAL_SUPPLY` always holds. That invariant is only approximately true: `Pair.swap` enforces the K-floor with a `+1` slack on both sides rather than an exact product check: [3](#0-2) 

`(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts only when the padded product falls below `k`; it does **not** require `newTokenReserve * newAssetReserve >= k`. Combined with `Router._computeBuy`'s ceil-rounded `amountInUsed` on the overflow-cap branch and `Router._computeSell`'s floor-rounded `assetOut`, a trader who repeatedly buys out the entire real token balance (triggering the capped/ceil-rounded branch) and then sells back down to `tokenReserve == TOTAL_SUPPLY` (the curve's maximum, since sellable supply is bounded by the 750M ever transferred out of the pair — see `_deployAndSeed`'s `curveSupply` transfer) can land the pair's stored `assetReserve` one wei below the recovered `virtualLtReserve`, inside the tolerance the `+1` slack allows: [4](#0-3) [5](#0-4) [6](#0-5) 

Once `assetReserve < virtualLtReserve`, `canGraduate`'s subtraction underflows and panics (0x11). This function is not an isolated view — it is called inline on the hot buy/sell path: [7](#0-6) [8](#0-7) 
and by the permissionless `triggerGraduation`: [9](#0-8) 

So every subsequent `buy`, `sell`, and `triggerGraduation` call for that token reverts unconditionally. Because the token's `Lifecycle` never advances past `Curve` (the revert happens before `_enterGraduating` runs), the token can never graduate either — there is no other path out of `Lifecycle.Curve`. `previewLtUntilGraduation` performs the same unguarded subtraction and would revert too, further crippling any keeper/off-chain rescue tooling that depends on it: [10](#0-9) 

### Impact Explanation
This is a permanent denial of service on an unprivileged, permissionless code path: once triggered, the affected token's curve is bricked forever — no further buys, sells, or graduation are possible. All LT/tokens held in the curve `Pair` for that token become permanently frozen (traders cannot sell back their tokens for LT, and the token can never migrate to the HyperSwap V2 LP for exit liquidity). This satisfies the "permanent freezing of trader, creator or LP funds" impact bar for a Medium-severity analog.

### Likelihood Explanation
Reachability requires only ordinary, permissionless `Zap.buy`/`Zap.sell` (or direct `Bonding.buy`/`sell` via an allowlisted router) calls from a single unprivileged wallet — no special privileges, no oracle manipulation, and no cross-contract collusion are needed. The trigger condition is a specific rounding alignment (drive the real token balance to zero via the capped/ceil-rounded buy branch, then sell back the exact bought amount to return `tokenReserve` to `TOTAL_SUPPLY`), which is a matter of careful, deterministic transaction crafting rather than probabilistic luck, making it reproducible by any sufficiently motivated attacker or even accidentally by adversarial-but-legitimate high-frequency trading against a low-liquidity curve.

### Recommendation
Replace the raw subtraction in `canGraduate` (and the mirrored one in `previewLtUntilGraduation`) with a saturating subtraction, matching the defensive pattern already used elsewhere in the same contract (e.g. `_sweepLTToOwner`'s `bal > keep ? bal - keep : 0` and `finalizeGraduation`'s `ltBalance > p.ltFromPair ? ... : 0`):
```solidity
uint256 virtualLt = _launchTimeVirtualLtReserve(token_, pair);
uint256 realLtRaised = assetReserve > virtualLt ? assetReserve - virtualLt : 0;
```
This treats an `assetReserve` at or below the virtual floor as "no real LT raised yet" instead of panicking, preserving `canGraduate`'s liveness on every call.

### Proof of Concept
Conceptual sequence (exact wei-level values depend on the launched LT's `exchangeRate()` and are not independently executed here, but the mechanism is fully supported by the cited code):
1. Launch a token; `Pair.mint` sets `k = TOTAL_SUPPLY (1e9 ether) * virtualLtReserve` per `_deployAndSeed`.
2. Trader repeatedly buys through `Zap.buy` → `Bonding.buy` → `Router.buy`/`_computeBuy` until the pair's real token balance hits `0`, forcing the capped, ceil-rounded `amountInUsed` branch in `_computeBuy` (`packages/contracts/src/Router.sol:140-147`) — this is the rounding source that can push `assetReserve` off the exact `k`-implied line.
3. Trader then sells back through `Zap.sell` → `Bonding.sell` → `Router.sell`/`_computeSell`, buying/selling in a pattern that returns `tokenReserve` exactly to `TOTAL_SUPPLY`, exploiting the `+1` slack in `Pair.swap`'s K-check (`packages/contracts/src/Pair.sol:71-73`) so that the *actual* stored `assetReserve` ends up one wei below `k()/TOTAL_SUPPLY`.
4. Any subsequent call to `Bonding.buy`, `Bonding.sell`, or `Bonding.triggerGraduation` on this token now executes `canGraduate` (`packages/contracts/src/Bonding.sol:688-694`), which underflows on `assetReserve - _launchTimeVirtualLtReserve(...)` and reverts with a `Panic(0x11)`, permanently bricking the token's curve.

        string calldata name_,
        string calldata ticker_,
        address ltAddress

        Token(tokenAddr).initialize(name_, ticker_, address(this));

        uint256 totalSupply = Token(tokenAddr).TOTAL_SUPPLY();
        uint256 curveSupply = (totalSupply * CURVE_BPS) / BPS_DENOM;

        pair = $.factory.createPair(tokenAddr, ltAddress);

        uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();
        if (exchangeRate == 0) revert ZeroExchangeRate();
        uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
        // The raised LT reserve peaks at `3 * virtualLtReserve` (curve sell-out)
        // and is later deposited into a HyperSwap V2 pair, whose reserves are
        // `uint112`. Bound it at launch (4x headroom) so graduation can never
        // exceed that slot.
        if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
