## Finding: Unchecked return-value transfers in Tron `IntentGatewayV2.withdraw()` / `SweepDust` handling

### Title
Silent-failure ERC20 `transfer()` in `withdraw()` and `SweepDust` on Tron `IntentGatewayV2` finalizes escrow settlement without verifying the transfer actually succeeded - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` uses raw low-level `.call()` with the `IERC20.transfer.selector` to move escrowed tokens to beneficiaries in `withdraw()` and to sweep dust in the `SweepDust` branch of `onAccept()`, but only checks whether the low-level call itself reverted (`success`). It never decodes/validates the boolean return value that `transfer()` returns. This is the mirror-image of the classic "unsafe ERC20 transfer" bug class: while it avoids reverting on tokens with no return data (e.g. USDT-style tokens), it fails to detect tokens that return `false` on failure instead of reverting, silently treating a failed transfer as a success.

### Finding Description
`withdraw()` iterates escrowed tokens and moves them to the beneficiary: [1](#0-0) 

and the fee-token payout uses the identical unchecked pattern: [2](#0-1) 

The `SweepDust` request handler in `onAccept()` has the same pattern: [3](#0-2) 

In all three cases, `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` only reflects whether the external call reverted, not whether the token's `transfer()` logic actually moved funds. Standards-compliant OpenZeppelin `SafeERC20.safeTransfer` additionally requires that returndata is either empty or decodes to `true`; this contract skips that check entirely. Any ERC20/TRC20 token that returns `false` on a failed transfer (common pattern for tokens with pausable transfers, blacklists, insufficient balance guards implemented without revert, etc.) will make `success == true` even though no tokens moved.

Notably, elsewhere in the very same file the developers correctly use `SafeERC20.safeTransferFrom` for pulling tokens into escrow (`placeOrder`, predispatch handling), confirming this is an inconsistency/oversight isolated to the outbound payout path (`withdraw`/`SweepDust`), not an intentional design choice: [4](#0-3) [5](#0-4) 

### Impact Explanation
`withdraw()` is invoked from `onAccept()` when a relayer delivers a `RedeemEscrow` or `RefundEscrow` cross-chain settlement message, and from `onGetResponse()` for cancellation refunds: [6](#0-5) [7](#0-6) 

If the escrowed token silently fails the `transfer()` (returns `false`), `withdraw()` will still:
1. Mark the order as finalized: `_filled[body.commitment] = beneficiary`
2. Decrement escrow accounting: `_orders[body.commitment][token] -= amount`
3. Emit `EscrowReleased`/`EscrowRefunded`

The beneficiary (user or solver) never receives the tokens, but the contract's internal state now considers the order fully settled — there is no retry path, since `_filled` is already set and escrow is already decremented. This is a permanent, unrecoverable loss of the escrowed funds for that beneficiary. The same applies to the `SweepDust` recovery mechanism, silently dropping protocol-fee dust with no recourse.

### Likelihood Explanation
This is reachable by any relayer submitting a normal, valid settlement proof for an order that used a non-standard token returning `false` instead of reverting on transfer failure (e.g., due to the escrow contract being blacklisted, a paused token, or any transfer-guard implemented via boolean return rather than revert). No malicious relayer/governance action is required — a legitimate relayer delivering a legitimate message is sufficient to trigger silent fund loss whenever the underlying token behaves this way. Since IntentGatewayV2 accepts arbitrary user-specified ERC20 tokens as order inputs (`order.inputs[i].token`), the attack surface includes any token the user or solver chooses to route through the gateway.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` (both the token loop and the fee-token payout) and in the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer()`, consistent with the `safeTransferFrom` usage already present elsewhere in the file. This ensures both call-revert and boolean-false failures cause the transaction to revert, preventing escrow state from being finalized without an actual, verified transfer.

### Proof of Concept
1. Place an order on the Tron `IntentGatewayV2` using a token `T` whose `transfer()` implementation returns `false` (rather than reverting) when the transfer cannot be completed (e.g., recipient blacklisted, contract paused, insufficient allowance edge case).
2. Have the order filled cross-chain and a valid `RedeemEscrow` proof relayed to `onAccept()`.
3. Arrange for `T.transfer(beneficiary, amount)` to return `false` inside `withdraw()` (e.g., beneficiary temporarily blacklisted by `T`, or `T` paused at call time).
4. `token.call(...)` returns `success = true` (no revert) even though `T.balanceOf(beneficiary)` did not increase.
5. `withdraw()` proceeds to decrement `_orders[commitment][token]`, set `_filled[commitment] = beneficiary`, and emit `EscrowReleased`.
6. The beneficiary's tokens are permanently lost — there is no remaining escrow balance and the order is already marked filled, so no retry or refund is possible.
