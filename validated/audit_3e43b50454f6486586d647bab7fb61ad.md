### Title
Swap output slippage floor (`circomData.slippageValues[1]`) is never enforced against actual swap output - (File: contracts/external-actions/swaps/ExternalActionSwap.sol)

### Summary
`ExternalActionSwap.swap` only checks that the user-supplied slippage floor `circomData.slippageValues[1]` is non-zero, but never compares the actual `swappedAmount` returned by the router against that floor. This is the direct analog of the reported Lambo.win bug: a price/slippage-protection parameter that exists in the data structure (and is committed to inside `calldataHash`) is never actually applied to bound the trade outcome, so the swap can execute at an arbitrarily bad price.

### Finding Description
In `swap()`: [1](#0-0) 

the only check on `circomData.slippageValues[1]` is `!= 0`. The actual amount returned by the swap, `swappedAmount`, is computed purely from the router call/balance diff via `callRouter`: [2](#0-1) 

Nowhere in `swap()` or `callRouter()` is `swappedAmount` compared to `circomData.slippageValues[1]` (or any minimum-out value). The field is included in the `calldataHash` that the ZK proof commits to (via `CircomDataBuilder`/`performHinkalChecks` in `HinkalHelper.sol`), meaning the user's proof authorizes a specific minimum-output value, but the on-chain code never uses that value to constrain the actual router execution — it is checked for non-zero-ness only, not for its intended purpose.

This mirrors the external report exactly: the report's bug was a price-limit parameter (`sqrtPriceLimitX96`) that existed conceptually to protect the trade but was hardcoded to `0`/unused, letting the swap execute at any price. Here, `slippageValues[1]` exists conceptually to protect the user's minimum output but is only sanity-checked for non-zero and never actually enforced against `swappedAmount`.

### Impact Explanation
Since the swap output is not floor-checked, `router` (an external, arbitrary-calldata target invoked via `externalActionMetadata`) can return far less output than the user intended/authorized in their proof, and the contract will still mint/credit `amountToSendToHinkal` (whatever it happens to be) into the user's new shielded UTXO: [3](#0-2) 

This breaks the equality between what the prover committed to (the minimum acceptable output encoded in `slippageValues[1]`, part of `calldataHash`) and what is actually credited back into the shielded pool. A sandwiched/adversarial router execution can cause the user's shielded balance to receive materially less value than authorized — a value loss/freezing of user funds that the proof was supposed to prevent.

### Likelihood Explanation
Any relayer or MEV actor that can influence transaction ordering around the `router.call(externalActionMetadata)` (e.g., sandwich attack on the underlying DEX aggregator route) can trigger this, since there is no code path that reverts when `swappedAmount` is below the user's declared minimum. This requires no privileged access — any third party capable of ordering transactions around the swap can exploit it.

### Recommendation
After computing `swappedAmount` in `swap()`, add an explicit check:
```solidity
require(
    int256(swappedAmount) >= circomData.slippageValues[1],
    "swap output below slippage floor"
);
```
so the on-chain enforcement matches what the ZK proof commits to via `calldataHash`.

### Proof of Concept
1. User submits a proof/circomData with `slippageValues[1] = X` (their required minimum output), which is baked into `calldataHash`.
2. `dimensionsCheck`/`performHinkalChecks` in `HinkalHelper.sol` only verify `calldataHash` integrity and `slippageValues.length`, never the actual output amount.
3. `ExternalActionSwap.swap()` only checks `circomData.slippageValues[1] != 0` (contracts/external-actions/swaps/ExternalActionSwap.sol lines 53-56), then calls `callRouter`, which returns whatever `swappedAmount` results from the external router call.
4. An adversary sandwiches the underlying router transaction (e.g., LI.FI route) to reduce output, or the router's `externalActionMetadata` simply routes through a bad-priced path.
5. `swappedAmount` ends up far below the user's intended `slippageValues[1]`, yet the transaction succeeds and mints a shielded UTXO with the reduced value — no revert occurs because the floor is never actually compared.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
