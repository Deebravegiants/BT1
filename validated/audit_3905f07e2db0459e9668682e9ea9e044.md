### Title
Tron IntentGatewayV2 uses raw `block.number` for order deadlines, which does not match Tron's block time / production semantics and can incorrectly gate cancellation and unauthorized-owner windows - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` compares order `deadline` values directly against `block.number` (`options.height <= order.deadline` and `order.deadline >= block.number`) to decide whether an order has expired and whether the original owner still has exclusive cancellation rights. This mirrors the exact bug class in the original report — using raw `block.number` for deadline logic without accounting for the target chain's actual block-production characteristics — and Polytope Labs itself acknowledged and patched this issue for Arbitrum in the EVM-mainline `IntentsBase.sol` contract via a dedicated `_blockNumber()` helper that queries the ArbSys precompile, but no equivalent adaptation exists for the separately-maintained Tron contract.

### Finding Description
`evm/src/apps/intentsv2/IntentsBase.sol` defines `_blockNumber()` specifically because `block.number` is unreliable across different EVM chains — for Arbitrum it returns the approximate L1 block number instead of the L2 height, so the contract queries the `ArbSys` precompile at `address(100)` instead: [1](#0-0) 

However, the Tron variant of the IntentGateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not use this abstraction at all and instead uses the raw `block.number` opcode directly in the order-cancellation flow: [2](#0-1) 
and again in the same-chain deadline check further up in `cancelOrder`: [3](#0-2) 

Order deadlines (`order.deadline`) are meant to be block-height denominated commitments that Hyperbridge/relayers interpret consistently across the source and destination chain. Tron's TVM `block.number` opcode reflects Tron's own block production (roughly 3-second blocks under the SR/DPoS scheme) which is not equivalent to Ethereum-style height semantics the rest of the protocol (state-machine height tracking, challenge periods, relayer height parameters like `options.height`) assumes. Because the destination-chain branch of `cancelOrder` gates the "only owner can cancel before expiry" protection purely on `order.deadline >= block.number`, and the source-chain branch gates the "not yet expired" check on `options.height <= order.deadline`, any mismatch between the intended deadline semantics (as expected by users/solvers who set the deadline assuming a particular block-time cadence) and Tron's actual block production rate causes deadlines to resolve earlier or later than intended.

### Impact Explanation
On the destination chain, once `block.number` on Tron passes `order.deadline` unexpectedly early (relative to what the order originator/solver assumed), the `Unauthorized()` guard protecting the original order owner's exclusive cancellation right silently lifts, allowing any third party to trigger the `RefundEscrow` dispatch and mark the order as cancelled — potentially racing a legitimate solver's fill and disrupting intent settlement, or conversely keeping the owner-only restriction active longer than intended, freezing the user's ability to cancel and reclaim escrowed funds. On the source chain, `cancelOrder`'s `NotExpired()` check relies on `options.height` (the relayer-supplied destination height parameter) versus `order.deadline`; if the destination chain's practical block-time-to-height ratio diverges from what the deadline was set against, orders can be cancelled prematurely (griefing solvers who filled just before the "true" deadline) or blocked from cancellation despite being genuinely expired (freezing user escrow). This affects fund availability/timing in the intents escrow flow reachable by any user submitting `placeOrder`/`cancelOrder` transactions — a single unprivileged transaction is enough to trigger the divergent behavior.

### Likelihood Explanation
Likelihood is high in practice: this code path executes on every `cancelOrder` call, is reachable by any unprivileged account, and Tron's block-time behavior is materially different from Ethereum L1/L2 chains that the rest of the protocol targets. The team has already recognized this exact class of bug is real enough to warrant a fix for Arbitrum (`_blockNumber()`), but the fix was not propagated to the Tron contract, leaving a known-risky pattern live specifically on the one non-EVM-standard, chain not covered by the `_blockNumber()` chain-id branches.

### Recommendation
Apply the same mitigation pattern used in `IntentsBase.sol`/`ExtrinsicIntents.sol` to the Tron `IntentGatewayV2.sol`: replace direct `block.number` reads in `cancelOrder` with a chain-appropriate block height accessor, and audit/document what block-height unit `order.deadline` and `options.height` are denominated in for Tron specifically, ensuring parity with whatever height Hyperbridge's Tron state-machine height tracking uses for challenge periods and finality.

### Proof of Concept
1. A user calls `placeOrder` on the Tron `IntentGatewayV2` with `order.deadline` set assuming Ethereum-like ~12s/block cadence expectations (as documented for the general Order type used cross-chain).
2. Tron produces blocks roughly every 3 seconds, so `block.number` on Tron advances roughly 4x faster than an EVM L1 chain for the same wall-clock time.
3. Before the wall-clock time the user intended as their "grace period", `order.deadline >= block.number` in `cancelOrder` (line 590) evaluates false much sooner than expected, dropping the `Unauthorized()` owner-only gate and letting any address trigger the `RefundEscrow` dispatch (lines 590-620) ahead of schedule.
4. This can be raced against a legitimate solver who is in the process of filling the order, or against the user's own expectations of when they regain unilateral control, resulting in unintended fund routing/timing in the escrow lifecycle.

    /**
     * @dev Returns the current block number of the host chain. Order deadlines are
     * denominated in the block heights Hyperbridge tracks for each state machine —
     * for Arbitrum chains that is the L2 block number, but the `block.number` opcode
     * there returns the approximate L1 block number, so the ArbSys precompile is
     * queried instead. The chain id check keeps the bytecode identical across all
     * chains, preserving the deterministic CREATE2 deployment addresses.
     * @return The chain-appropriate current block number.
     */
    function _blockNumber() internal view returns (uint256) {
        if (block.chainid == ARBITRUM_ONE || block.chainid == ARBITRUM_NOVA || block.chainid == ARBITRUM_SEPOLIA) {
            return IArbSys(ARB_SYS).arbBlockNumber();
        }
        return block.number;
    }
