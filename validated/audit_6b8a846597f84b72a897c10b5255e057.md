### Title
Webhook shop identity spoofing via unsigned `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook only by validating an HMAC over the raw request body. The `shop` value used to dispatch the webhook to the host application's handler is read from the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, which is never included in the HMAC-signed material. An attacker who can obtain any single genuinely-signed `(body, hmac)` pair — trivially done by installing the (public) app on their own free Shopify development store and triggering a webhook — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, causing the host application to process the webhook as if it came from a victim shop.

### Finding Description
The verification and the identity binding are split across two different pieces of data:

- HMAC validation: `Utils::HmacValidator.validate(request)` computes/verifies the HMAC only over `to_signable_string`, which for a webhook `Request` is simply the raw body: [1](#0-0) 

- Tenant identity used to act on the request: `shop` is parsed straight from an HTTP header, entirely outside the signed payload: [2](#0-1) 

- `Registry.process` validates the HMAC and then immediately builds and dispatches `WebhookMetadata` using `request.shop` (the unsigned header) as the tenant identifier passed to the app's handler: [3](#0-2) 

The equality that should hold but doesn't: `shop authenticated by HMAC == shop acted upon by the handler`. In reality, `HMAC` only proves `body` is authentic Shopify-signed content for *some* shop that legitimately received that payload — it says nothing about which shop the request currently claims to be for. Because `shop` is sourced from a header outside `to_signable_string`, any request carrying a valid `(body, hmac)` pair passes HMAC validation regardless of the `shop-domain` header value.

### Impact Explanation
This breaks the tenant-identity binding for a Critical-impact category (cross-tenant access): an attacker-controlled shop's legitimately-signed webhook can be replayed against the endpoint with a forged `shop-domain` header pointing at any victim shop. If the host application (as documented/intended usage of this gem, e.g. `WebhookMetadata#shop` in `handler.handle`) uses this `shop` value to select which merchant's session/data/token to act on (common patterns: deleting shop data on `app/uninstalled`, updating orders on `orders/create`, etc.), the attacker can trigger cross-tenant data manipulation for a shop they do not own or control, without ever needing the app's `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is high: the attacker only needs the capability of an ordinary internet user — creating a free Shopify partner/dev store and installing the target (presumably public) app to receive one legitimately-signed webhook body of their choosing. No secret material, privileged account, or social engineering is required, satisfying the "unprivileged internet user" threat model. The replay itself is a trivial HTTP request with a modified header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified material instead of trusting an unsigned header for tenant identity: include the shop domain in the value that is HMAC-verified (Shopify webhook payloads already include shop context that can be cross-checked), or require the host application to independently verify that `request.shop` corresponds to a shop with an active, previously-established session/installation before trusting it. At minimum, document explicitly that `request.shop` is unauthenticated and must not be used as the sole tenant-identity source without additional server-side verification (e.g., confirming an existing offline session exists for that shop before acting).

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (`attacker-shop.myshopify.com`) and triggers a webhook subscription (e.g., `app/uninstalled` or any topic they can trigger themselves).
2. Attacker's endpoint (or a capture proxy) records the exact `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent — a valid `(body, hmac)` pair, correctly signed with the app's real `api_secret_key` for the attacker's own shop.
3. Attacker sends a POST request to the victim application's webhook endpoint with:
   - Body: the captured `raw_body` (unchanged)
   - Header `x-shopify-hmac-sha256`: the captured HMAC (unchanged)
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks the body/HMAC pair, per [4](#0-3) .
5. `Registry.process` invokes the registered handler with `shop: request.shop` set to `victim-shop.myshopify.com`, per [5](#0-4) , causing the host app to act on the victim shop's tenant context using attacker-supplied payload data.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
