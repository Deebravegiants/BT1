### Title
Webhook shop-domain attribution is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` treats the HMAC signature as proof that a webhook body came from Shopify, but the `shop` attribute used downstream by the app (handler dispatch, `WebhookMetadata#shop`) is taken from an unsigned header rather than from the HMAC-covered payload.

`to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`HmacValidator.validate` only verifies `verifiable_query.hmac` against `to_signable_string` (the raw body) using the app's single, global `api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the data passed to the app's handler, which is the only tenant-identifying value the handler receives: [4](#0-3) 

The broken binding, stated as an equality that should hold but doesn't:
`shop value cryptographically bound inside the HMAC-signed bytes` == `shop value the handler acts on (request.shop from an unsigned header)`

Before the attack: for a genuine Shopify delivery, the header `shop-domain` happens to match the tenant that Shopify actually sent the event for, but nothing in the signed bytes ties them together — the equality holds only by convention, not by verification.

After the attacker's request: an attacker who operates their own Shopify store installs the app and receives a legitimate webhook delivery for their own shop — a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` (which is the same secret for every shop using this app, since HMAC verification here has no per-shop key). The attacker then POSTs that exact `raw_body` + `hmac` to the app's webhook endpoint again, but swaps the `x-shopify-shop-domain` header to a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks `raw_body` against the secret), and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This crosses a tenant boundary that the gem's own documentation claims to guarantee ("This will verify the request did indeed come from Shopify"), but the identity of *which* shop it came from is not authenticated. Any app relying on `data.shop` from the handler (as the documented usage pattern shows, e.g. `perform_later(topic:, shop_domain: data.shop, webhook:)`) can be made to process/attribute events (order data, `app/uninstalled`, `shop/redact`, etc.) to an arbitrary victim shop chosen by an unprivileged attacker who merely needs to be able to install the app somewhere (or capture any one legitimate delivery). This is a cross-tenant integrity issue at the trust boundary this gem is responsible for.

### Likelihood Explanation
Exploitation requires no secrets: an attacker only needs one valid webhook delivery (obtainable by installing the app on their own store, which is standard, unprivileged usage) and the ability to send an HTTP POST with a modified header to the app's public webhook endpoint. No knowledge of `api_secret_key` or any access token is needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind the `shop` header to the signed body before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document and enforce that consuming apps must independently verify `data.shop` is a shop with an active, stored session/installation before acting on the payload.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers any subscribed topic (e.g. `orders/create`), capturing the raw body and the resulting `x-shopify-hmac-sha256` header — both are delivered to the attacker's own endpoint and are not secret.
2. Attacker POSTs the identical `raw_body` to the victim app's public webhook route, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` while keeping the original `x-shopify-hmac-sha256`.
3. `ShopifyAPI::Webhooks::Request.new` builds a request object from these headers; `Utils::HmacValidator.validate` computes the HMAC over the (unchanged) raw body and it matches, since domain is never part of the signed string (`lib/shopify_api/webhooks/request.rb` line 36-38, `lib/shopify_api/utils/hmac_validator.rb` line 26-31).
4. `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as though the event originated from the victim shop.
