## Title
Unbounded gas forwarding in `EvmHost.dispatchIncoming` external calls enables gas-griefing DoS of batched message delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` (both the `PostRequest` and `GetResponse` overloads) invokes the destination application's `onAccept`/`onGetResponse` callback via a raw, un-stipended `.call(...)`, which under Solidity's 63/64 rule forwards essentially all remaining transaction gas to an address that is fully attacker-controlled (any dispatcher can name any contract as the message's `to`/`from`). These calls happen inside `HandlerV2.handlePostRequests`/`handleGetResponses`, which loop over an entire batch of proof-verified messages in one transaction. This mirrors the class of bug in the external report: an external call without a gas stipend to an untrusted/attacker-controlled address can be weaponized to consume the caller's gas and disrupt unrelated operations bundled in the same transaction.

This is called from a loop over an entire batch of requests verified in one Merkle proof: [2](#0-1) 

and similarly for GET responses: [3](#0-2) 

The design explicitly tolerates a *normal* revert from the destination module — the receipt is deleted and the function returns without reverting, so the message stays retryable and the rest of the batch proceeds, as documented: [4](#0-3) 

However, this graceful-failure handling only covers the case where the sub-call reverts cleanly with gas to spare. It does not protect against a malicious destination contract that deliberately burns nearly all of the gas forwarded to it (e.g., via a gas-metered loop that runs until `gasleft()` drops below a threshold, then reverts or returns). Because the call forwards essentially the entire remaining gas budget, a single malicious entry anywhere in the batch can leave insufficient gas for the loop to finish processing the remaining, legitimate requests in the same `handlePostRequests`/`handleGetResponses` transaction, causing the whole batch transaction to run out of gas and revert — rolling back every previously-processed, honest delivery in that batch.

### Impact Explanation
An unprivileged actor can dispatch a cross-chain POST/GET request whose destination (`to`/`from`) is a contract they control and that is engineered to burn gas. When a relayer batches this message together with other pending, legitimate deliveries (a normal efficiency practice, and something an attacker can encourage by timing/flooding), the entire delivery transaction can run out of gas and revert, so none of the bundled messages — including unrelated users' fund releases via `IntentGatewayV2`/`ExtrinsicIntents`/`HyperFungibleToken` — get delivered in that attempt. This is a liveness/DoS attack on the message-delivery route: it degrades the relayer's ability to deliver messages and can be repeated indefinitely by continuously injecting new malicious destinations, forcing relayers into smaller, less efficient batches or manual exclusion logic to route around the attacker, i.e. "a route unable to deliver messages" for as long as the attacker sustains the campaign.

### Likelihood Explanation
Likelihood is Medium-High: dispatching a POST/GET request with an arbitrary destination address is fully permissionless from any source chain, requires no special privileges, and the attack contract (a simple gas-burning loop) is trivial to write. The primary mitigating factor is that a sophisticated relayer can detect and exclude the malicious destination from future batches once identified, making the disruption per-incident rather than unconditionally permanent — but it remains a real, cheaply repeatable DoS lever against relayer throughput and batch atomicity.

### Recommendation
Cap the gas forwarded to destination modules in `EvmHost.dispatchIncoming` (e.g., `destination.call{gas: gasStipend}(...)`) with a bounded, configurable stipend sized for legitimate `onAccept`/`onGetResponse` implementations, so that no single destination can consume more than its allotted share of the batch's gas budget, preventing one malicious recipient from starving the rest of the batch.

### Proof of Concept
1. Attacker deploys `GasGriefer` implementing `onAccept(IncomingPostRequest calldata)` with a loop that consumes gas until `gasleft() < X`, then `revert()`.
2. Attacker dispatches an ISMP POST request from a source chain with `to = address(GasGriefer)`.
3. A relayer proves and batches this request together with several legitimate pending POST requests in one `handlePostRequests` call.
4. `HandlerV2.handlePostRequests` loops through `EvmHost.dispatchIncoming`, calling `GasGriefer.onAccept` which forwards ~63/64 of remaining gas and burns nearly all of it before reverting.
5. Subsequent iterations of the loop (processing legitimate requests) run out of gas, causing the entire `handlePostRequests` transaction to revert, undoing delivery of all bundled legitimate messages for that relaying attempt.

```text
    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
```
