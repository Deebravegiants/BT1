### Title
Per-delegator block reward share calculation can exceed the vote account's `pending_delegator_rewards` pool during epoch reward recalculation - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward` computes each stake account's share of a vote account's shared `pending_delegator_rewards` pool via `pending_delegator_rewards * stake / total_active_stake` (integer division), then clamps only the individual result to `pending_delegator_rewards`, without tracking or bounding the cumulative amount handed out to all delegators of that vote account. [1](#0-0) 

### Finding Description
`calculate_block_reward` distributes a vote account's `pending_delegator_rewards` (SIMD-0123) proportionally to each delegated stake account based on `stake / total_active_stake`: [2](#0-1) 

The function's own comment acknowledges the exact rounding-class risk described in the CQT report: during recalculation, an individual stake account's `stake` value can exceed `total_active_stake` (the denominator used for the ratio), which can make an individual computed share "look greater than the pending rewards." The code clamps that single call's result to `pending_delegator_rewards` with `.min(pending_delegator_rewards)`, but this clamp is applied independently, per delegator, per call — there is no running-total deduction from `pending_delegator_rewards` as each stake account's share is computed within `calculate_stake_rewards_and_commissions`, which invokes `calculate_block_reward` per delegation in a parallel iterator: [3](#0-2) 

This is structurally analogous to the CQT `_sharesToTokens`/`_tokensToShares` bug: a shared pool (CQT balance / `pending_delegator_rewards`) is divided among multiple claimants using multiply-then-divide arithmetic, and each claimant's share is validated only against the total pool value, not against what remains after other claimants' shares have already been paid out. In the CQT case, that allowed the last withdrawer's calculated (rounded) amount to exceed the contract's real remaining balance. Here, if more than one stake account is delegated to the same vote account and the "stake > total_active_stake" condition triggers (explicitly flagged as possible in the comment) for more than one delegator in the same recalculation pass, each delegator's block reward is independently computed and independently clamped to the *full* `pending_delegator_rewards` value rather than to the amount actually remaining in the pool after prior delegators were paid.

### Impact Explanation
If this per-delegator clamp is insufficient to prevent aggregate over-distribution, the sum of `block_reward` values credited to stake accounts for a single vote account could exceed the `pending_delegator_rewards` amount actually escrowed in that vote account's lamport balance. Because `block_reward` lamports are added to stake accounts via `account.checked_add_lamports(...)` in the reward-distribution path without a corresponding, tracked debit from the vote account bounded by a shrinking pool, this could create lamports that are not backed by any deducted balance — a capitalization/accounting divergence, or in a shortfall variant, cause the final distribution/redemption of the vote account's true pending rewards balance to fail due to insufficient backing (mirroring the "last withdrawal reverts" impact in the original report). [4](#0-3) 

### Likelihood Explanation
The triggering condition ("stake > total_active_stake" during recalculation) is explicitly called out by the developers as a known, if narrow, edge case reachable only during epoch-reward *recalculation* (not the normal first-pass calculation), and is stated to be "harmless in practice." I was not able to fully trace, within the available tool budget, (a) how `pending_delegator_rewards` is actually debited from the vote account's lamports/state field after distribution, and (b) whether a separate invariant elsewhere guarantees the sum of all `block_reward`s for a given vote account cannot exceed its `pending_delegator_rewards`/lamport balance. Without confirming that a global, cumulative check exists, likelihood cannot be conclusively assessed from the visible code; the existing per-call `.min(pending_delegator_rewards)` clamp may or may not be sufficient depending on downstream accounting in `distribution.rs`, which I could not fully inspect in the remaining budget.

### Recommendation
Verify (or add) that the total `block_reward` distributed to all stake accounts delegated to a given vote account within one recalculation/distribution pass is bounded by that vote account's actual `pending_delegator_rewards` value and lamport balance — e.g., by tracking a running remainder per vote account rather than clamping each individual delegator's share independently to the full pool value. Additionally, consider rounding the proportional share calculation in `calculate_block_reward` in a way that biases against over-payment in aggregate (e.g., rounding down and reconciling any remainder to the vote account, similar to `commission_split` vs. `commission_split_preserve_lamports`) rather than clamping post-hoc per delegator.

### Proof of Concept
Not independently constructed; the report relies on the code's own explicit acknowledgment of the "stake > total_active_stake" condition and per-call clamping in `calculate_block_reward` at [4](#0-3) . Existing test coverage (`test_calculate_block_reward_specific`, `test_calculate_block_reward_prop`) only validates a single delegation against `pending_delegator_rewards`, and does not test the multi-delegator/recalculation scenario where the sum of clamped rewards across delegators of the same vote account could exceed `pending_delegator_rewards`: [5](#0-4) 

I was unable to conclusively confirm within the remaining tool budget whether downstream code in `distribution.rs` enforces a cumulative bound preventing this from becoming a concrete value-creation/shortfall bug; this should be verified with a full trace of the distribution path before treating this as confirmed exploitable.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
