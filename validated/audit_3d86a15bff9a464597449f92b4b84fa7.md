### Title
`shop` field in `ShopifyAPI::Webhooks::Request`/`Registry.process` is trusted as tenant identity but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` struct containing `shop`. In reality, the HMAC only authenticates the request body; the `shop` field is read straight from an unsigned HTTP header and handed to the handler as the authoritative tenant identifier, breaking the intended binding `hmac-verified-body == shop-that-owns-the-body`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate` computes/compares the HMAC solely over that signable string using the app's shared `Context.api_secret_key`: [2](#0-1) . The `shop` accessor, however, is read directly from the `shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the body or to the HMAC at all: [3](#0-2) .

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` verbatim, passing it to the app-supplied handler as the trusted tenant identity: [4](#0-3) . `WebhookMetadata.shop` is declared as a plain `String` field with no further validation: [5](#0-4) .

The identity binding that should hold is: `shop` field the app acts on == `shop` value cryptographically bound into the HMAC-covered bytes. Before the attack: a legitimate webhook for shop A has `hmac = HMAC(secret, body_A)` and header `shop-domain: A`, and the two agree. After the attack: the same `body_A`/`hmac` pair is replayed with header `shop-domain: victim-B`. `HmacValidator.validate` still returns `true` because it never reads the `shop` header at all — its validation function is a pure function of `verifiable_query.to_signable_string` (the body), not of the shop claim: [6](#0-5) . `Registry.process` then dispatches `data.shop == "victim-B"`, `data.body == body_A` to the handler, which per the documented usage pattern uses `data.shop` to route/store the payload for that tenant: docs/usage/webhooks.md lines 14, 25-26 (out of scope for citation tags but directly establishes intended trust).

### Impact Explanation
Any actor who can obtain one genuine, validly-signed webhook body from the app (e.g., by installing the app on their own shop — a normal, unprivileged action for any Shopify merchant — and receiving webhooks the app sent them) can replay that exact body with a forged `X-Shopify-Shop-Domain` header naming a different, victim tenant of the same multi-tenant app. Because the api_secret_key is shared across all shops installing the app, the HMAC check passes unmodified. The app's handler, following the gem's documented contract, ingests attacker-controlled data tagged as belonging to the victim shop — a cross-tenant data-injection/impersonation primitive. This satisfies the Critical "cross-tenant access" impact category without requiring the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is high for any app built strictly per the gem's documentation: the only prerequisite is installing the target multi-tenant app on an attacker-controlled shop (freely available to any internet user) to obtain one signed, replayable body/HMAC pair, then forging one HTTP header on replay. No special access, secrets, or race conditions are needed, and the gem provides no mechanism (e.g., binding shop into the signed payload, or cross-checking `shop` against a known/registered shop before invoking the handler) to prevent it.

### Recommendation
Bind the `shop` claim into the value that is actually authenticated before it is trusted:
- Extend `VerifiableQuery`/`Request#to_signable_string` (or `HmacValidator`) so the shop-domain header participates in the signature check, or
- Have `Registry.process` cross-verify `request.shop` against a shop already known to be registered/authorized for the specific `webhook_id`/topic via a signed source (e.g., re-deriving expected shop context from a previously stored session tied to that `webhook_id`) before constructing `WebhookMetadata`, rejecting the request if they disagree.

### Proof of Concept
1. Attacker installs the app on shop `attacker.myshopify.com` (unprivileged, self-serve).
2. Attacker triggers/receives a genuine webhook, capturing `raw_body` and its valid `X-Shopify-Hmac-Sha256` header (both computed with the app's shared `api_secret_key`).
3. Attacker replays the exact same request to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `HmacValidator.validate` ( [6](#0-5) ) returns `true` since it never inspects the shop header.
5. `Registry.process` ( [4](#0-3) ) invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: attacker_body, ...)`, which the app — per documented usage — uses to route/persist data under the victim's tenant record.
