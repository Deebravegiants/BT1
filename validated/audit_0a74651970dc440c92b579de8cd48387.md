Confirmed: `Session.from` (`lib/shopify_api/auth/session.rb:107-140`) constructs the session id purely as `"#{shop}_#{associated_user.id}"` for online sessions or `"offline_#{shop}"` for offline sessions, both fully deterministic from public/knowable values (shop domain, numeric user id) with no server-side secret or randomness involved.

### Title
Non-embedded session cookie trusts a fully predictable, unsigned session id, enabling cross-tenant session fixation - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
In the non-embedded (and cookie-fallback) OAuth flow, the app's notion of "current session" is derived solely from the raw value of the `shopify_app_session` cookie via `SessionUtils.cookie_session_id`, with no cryptographic binding (no HMAC, no signature, no server-side random nonce) tying that value to the specific authenticated browser. Because the session id itself is generated as a deterministic string — `"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"` — from public/guessable values, any party who can place that exact string into a victim's cookie jar (classic session fixation) causes the host application to treat the victim as authenticated under the attacker-chosen session id, without the gem performing any verification that the cookie value was legitimately issued by the OAuth callback for that browser.

### Finding Description
After a successful OAuth callback, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the session cookie value directly to `session.id`: [1](#0-0) 

That `id` is computed by `Session.from` as a fully deterministic function of public/knowable inputs — the shop domain and the associated user's numeric id — with no random or secret component: [2](#0-1) 

On subsequent requests, `SessionUtils.current_session_id` retrieves this cookie value and returns it directly as the trusted session id, for both the non-embedded flow and as a fallback in the embedded flow when no JWT is present — with no HMAC/signature check on the cookie at all: [3](#0-2) [4](#0-3) 

The `SessionCookie` struct that carries this value has no signature or MAC field of its own: [5](#0-4) 

This breaks the intended identity binding `cookie_value == id_issued_by_this_gem_to_this_browser_at_OAuth_completion`. In practice the equality degrades to `cookie_value == f(shop_domain, user_id)`, where `f` is a public, unkeyed string template. Anyone who knows (or can enumerate) a target shop's domain and a target user's numeric id — both routinely observable (shop domain appears in the app URL/redirect flows; user ids are exposed in Shopify admin URLs, GraphQL `id` fields, and other webhooks/API responses) — can independently compute a valid-looking session id and inject it as the cookie value on a victim's browser via any of the standard session-fixation vectors (setting a cookie for a subdomain/path the app also serves, a response-splitting bug in another part of the host stack, or simply the victim being lured into visiting a URL that carries a `Set-Cookie` the attacker controls before completing login). Once the victim's browser carries that attacker-chosen cookie and the victim proceeds to interact with the app, `current_session_id` will happily hand back the attacker-predicted id, causing the host application's session storage lookup (keyed by this id) to be treated as this same session for both the victim and the attacker.

### Impact Explanation
If the host application's session store is keyed by this id (as the gem's documented usage pattern expects: `SessionStorage#load_session(current_session_id(...))`), an attacker who can seed a victim's cookie with a predicted id before the victim completes OAuth effectively fixates the session, and after the victim authenticates, the attacker's independently-known cookie value continues to resolve to the same stored session/access-token record. This is a session-fixation vulnerability leading to potential cross-tenant/cross-user access to a merchant's or user's authenticated session and, transitively, the access token associated with it — matching the High-impact "session fixation or forced OAuth completion" category.

### Likelihood Explanation
Exploitation requires (a) the host app to run the non-embedded (or JWT-less fallback) flow that this gem's `SessionUtils.current_session_id` supports, and (b) an avenue to place a chosen value into the victim's cookie jar before/at authentication time. The shop domain is essentially public, and merchant/user numeric ids are frequently exposed through normal Shopify admin URLs and API/webhook payloads, so computing the target id requires no privileged access. The main constraint is finding a cookie-injection vector on the host site (session fixation is a well-known class of web bugs), which is why this is rated High rather than Critical.

### Recommendation
Do not use a deterministic, attacker-computable string as the value stored in the session cookie. Instead, the cookie should carry a high-entropy, unguessable, unrelated identifier (e.g., `SecureRandom.uuid`, as `Session#initialize` already supports as the default when no `id` is passed), or the cookie value should be cryptographically signed/HMACed by the gem (binding it to the api_secret_key) so that `current_session_id` can verify authenticity before trusting it, mirroring the pattern already used for OAuth callback and webhook HMAC validation (`Utils::HmacValidator`).

### Proof of Concept
1. App is configured non-embedded; a merchant `example-shop.myshopify.com` installs the app and completes OAuth online access; `Session.from` computes `id = "example-shop.myshopify.com_902541635"` (the numeric id is visible to the attacker via, e.g., the Shopify Admin API `AssociatedUser`/customer id or admin URL).
2. Attacker independently computes the same string and sets it as the victim's `shopify_app_session` cookie value ahead of/at the time the victim visits the app (via any standard fixation channel on the host site, e.g. a subdomain cookie, or the app itself echoing an attacker-supplied cookie prior to login).
3. Victim proceeds to use the app; the OAuth callback stores/looks up the session under the id `"example-shop.myshopify.com_902541635"`.
4. Attacker, now separately holding a browser with the same fixated cookie value, calls the host app's endpoints; `SessionUtils.current_session_id` returns the same id from `cookie_session_id`, and the host's session storage (keyed on this predictable id, as documented for this gem) resolves the victim's session/access token for the attacker's request. # typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
