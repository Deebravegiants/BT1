### Title
Emporium's balance-accounting loop only protects caller-declared ERC20/ETH addresses, letting CASE 2 arbitrary calls exfiltrate any other asset custodied by the shared `EmporiumUpgradeable` contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`runAction` computes `balancesBefore`/`balancesAfter` only over `circomData.erc20TokenAddresses`, a list chosen entirely by the calling prover for their own transaction [1](#0-0) . `EmporiumUpgradeable` is a single shared/singleton contract (state initialized once via `initialize`, gated only by `onlyAllowedRecipient`), not a per-user instance [2](#0-1) [3](#0-2) . CASE 2 ("Stateless Interaction") performs a fully unrestricted `op.endpoint.call{value: op.value}(op.callData)` to any endpoint, blocking only two `IHinkalWallet` selectors [4](#0-3) , so any attacker who is an `onlyAllowedRecipient`-authorized caller (i.e. any user routed through the standard Hinkal flow) can direct Emporium to move out any asset it happens to hold that is not on their own declared ERC20 list.

### Finding Description
The equality the contract is supposed to enforce is: *every asset moved out of Emporium during `runAction` must be reflected by a corresponding entry in `balancesAfter - balancesBefore` for `circomData.erc20TokenAddresses`*. That equality is broken for any asset type/address not included in the caller's own `erc20TokenAddresses` array:

- `balancesBefore`/`balancesAfter` are computed strictly via `getBalancesForArray(circomData.erc20TokenAddresses)` [1](#0-0) [5](#0-4) , an array the *current* attacker fully controls when building their own proof/`circomData`.
- CASE 2 ops execute `op.endpoint.call{value: op.value}(op.callData)` with the shared Emporium contract as `msg.sender`/token owner, with no restriction on `op.endpoint` or on what asset/protocol is touched, other than blocking `callHinkalWallet`/`doSendToRelay` selectors [4](#0-3) .
- Because Emporium is a singleton contract (one `initialize`, one storage slot for `usedMessages`/`_hinkalHelper`) reused across all users [6](#0-5) , whatever balance any prior transaction leaves at the Emporium address (NFT, ERC1155, or an ERC20 the current attacker simply omits from their own `erc20TokenAddresses`) persists in on-chain state and is visible/movable by the next caller.
- `onlyAllowedRecipient` only checks that `msg.sender` (expected to be the main `Hinkal` router) is whitelisted [3](#0-2) ; it says nothing about which assets the attacker's ops may touch, and `verifyWallet` only checks the EIP-712 signature/replay of the ops the *attacker themselves* signed [7](#0-6) .

Attacker call: submit a valid proof of their own funds with `circomData.erc20TokenAddresses` intentionally excluding the target asset (or being an NFT/ERC1155 address that can never appear in that array), and `EmporiumStack.ops = [{endpoint: targetAsset, invokeWallet: false, callData: transferFrom/safeTransferFrom(emporium, attacker, id_or_amount)}]`. `runAction` executes the call, it succeeds, and the subsequent balance loop only iterates over the declared ERC20 list, which is empty/unrelated, so `balancesBefore == balancesAfter` for every tracked index and the check trivially passes with `deltaAmountChanges` matching the attacker's own (unrelated) UTXO spend.

### Impact Explanation
Any asset that is not an ERC20/ETH address explicitly declared by the *current* caller — most notably NFTs and ERC1155 tokens, but also any ERC20 the attacker chooses to simply not list — that is present at the Emporium contract's balance (from a prior operation, protocol interaction, dust, or airdrop) can be swept by any subsequent unprivileged caller with zero on-chain detection. This is direct theft of assets held in custody by the protocol's external-action executor, matching the Critical category (direct theft, no balance-loop or signature check catching the movement), and is repeatable for every distinct asset/leftover balance that ever appears at the shared Emporium address.

### Likelihood Explanation
Preconditions: (1) some asset not covered by the attacker's own `erc20TokenAddresses` declaration must be sitting at the Emporium contract's address (this can be an NFT/ERC1155 from any legitimate multi-step Emporium interaction, or ERC20 dust from rounding/fees/slippage from any prior transaction by any user), and (2) the attacker must be able to submit any valid Hinkal proof for their own unrelated UTXOs to reach `onlyAllowedRecipient`-gated `runAction` — a capability every ordinary user has. No privileged role, no cooperation from the victim beyond having previously interacted with Emporium, and no dependence on price oracles or third-party bugs is required. The attack is essentially free (one transaction, gas only) and repeatable for each stranded asset.

### Recommendation
Do not rely solely on a caller-declared ERC20 allowlist for the post-call balance check. Either (a) restrict CASE 2 endpoints/calldata to a protocol-controlled allowlist so arbitrary asset transfers out of Emporium are impossible, (b) require the contract to be stateless with respect to non-declared assets by tracking all assets that any operation touches (via return-value/selector inspection or a strict allowlist of interacting protocols) and enforcing zero-residual invariants for them, or (c) make Emporium single-use/ephemeral per transaction (e.g., a minimal proxy deployed and destroyed per call) so no asset can ever persist across transactions to be swept by a different, unrelated caller.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, an ERC721 mock, `Hinkal`/verifier mocks so a valid proof can be generated for an attacker-controlled UTXO.
2. Simulate a "prior" state by directly minting/transferring an NFT to the Emporium contract address (representing residue from any earlier legitimate interaction, not part of the attack transaction itself).
3. Attacker submits `runAction` with `circomData.erc20TokenAddresses = []` (or any list excluding the NFT) and `EmporiumStack.ops = [{endpoint: nft, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC721.safeTransferFrom, (emporium, attacker, tokenId))}]`.
4. Assert `runAction` returns success, `nft.ownerOf(tokenId) == attacker`, while `balancesBefore == balancesAfter` (both empty/unchanged arrays) for `circomData.erc20TokenAddresses`, demonstrating the accounting equality `assets_moved_by_ops == assets_counted_by_balanceChange_loop` is violated for the NFT with no revert or detection anywhere in `runAction`.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
