## Title
Unsafe token transfer return-value check in `IntentGatewayV2.withdraw()` and dust sweep on Tron — matches the "unchecked ERC20 transfer" bug class - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed intent funds using a raw low-level `.call()` to the token's `transfer` selector and only checks that the *call itself* did not revert (`success`), never decoding and validating the ERC20 boolean return value. State (escrow accounting and the `_filled` finality flag) is updated as though the transfer succeeded regardless of whether the token actually moved funds, exactly the class of bug described in the external report (unchecked transfer success leading to state inconsistency / fund loss).

### Finding Description
In `withdraw()`, escrow release/refund is performed like this: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    ...
    _orders[body.commitment][token] -= amount;
```

`success` here reflects only whether the external call reverted, not what the ERC20 `transfer()` function actually returned. Many TRC20/ERC20 implementations (including the historically common "return `false` instead of reverting on failure" pattern, e.g. legacy USDT-style tokens which are prevalent on the exact chain this file targets) will make this low-level `call` return `success = true` while the encoded return data is `abi.encode(false)`. The code never inspects that return data.

The same unchecked pattern appears in the dust-sweep handler in the same file: [2](#0-1) 

By contrast, the canonical EVM `IntentGatewayV2` and `IntentsBase` use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which correctly decode and validate the return value: [3](#0-2) 

The Tron variant deliberately diverges from this safe pattern for its outbound transfers, reintroducing exactly the vulnerability the external report describes.

Critically, `_filled[body.commitment] = beneficiary` (marking the order as finalized) and `_orders[body.commitment][token] -= amount` (decrementing escrow) happen unconditionally once the (unreliable) `success` check passes — this is a Checks-Effects-Interactions violation combined with the return-value bug, since state changes are irreversible once set (`if (_orders[body.commitment][token] == 0) revert UnknownOrder();` guards re-entry into the same commitment/token).

### Impact Explanation
This is reachable by any relayer delivering a valid `RedeemEscrow`/`RefundEscrow` cross-chain POST request (dispatched by an unprivileged intent solver/filler as part of normal `IntentGatewayV2` intent settlement) or by any account triggering `onGetResponse` for a timeout-refund path. If the underlying token used as escrow collateral is one that returns `false` on transfer failure rather than reverting (a well-known behavior class for tokens deployed on TVM/EVM-compatible chains, including legacy USDT-style implementations), a transfer that silently fails (e.g., due to a paused token, blacklist, or insufficient balance at redemption time due to fee-on-transfer edge cases) will still be treated as successful:
- The order is irreversibly marked `_filled`, preventing any retry or alternate redemption path.
- Escrowed accounting (`_orders[commitment][token]`) is decremented as if funds were delivered.
- The beneficiary never actually receives the tokens.

This results in permanent loss of the user's/solver's escrowed funds — the intent's collateral is effectively burned from the protocol's perspective (accounting says it's gone) while the beneficiary holds nothing, with no governance or user-level recovery mechanism, matching the "Medium/High — permanent freezing/theft of funds" impact bar.

### Likelihood Explanation
No privileged role is required — this is triggered through the standard intent fill/refund/timeout flow that any solver, filler, or relayer initiates as part of normal cross-chain intent settlement dispatched to `onAccept`/`onGetResponse`. It only requires that the escrowed token be one whose `transfer()` can return `false` instead of reverting under failure conditions (a realistic scenario given tokens on Tron/TVM-compatible chains commonly exhibit this legacy behavior), making the likelihood non-trivial for any deployment that whitelists such a token as an intent input/output asset.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere in the same file via `using SafeERC20 for IERC20;`), in both `withdraw()` and the `SweepDust` handler in `onAccept()`. Additionally, follow Checks-Effects-Interactions: perform the escrow-decrement and `_filled` state mutation strictly after confirming a successful transfer, not merely after a non-reverting low-level call.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an escrow token `T` whose `transfer()` implementation returns `false` (not revert) when the transfer cannot be completed (e.g., simulate via a mock token, mirroring known legacy USDT-style behavior).
2. A user places an order with input token `T`, escrowing `amount` in `_orders[commitment][T]`.
3. Arrange for `T.transfer(beneficiary, amount)` to internally fail and return `false` (e.g., token owner blacklists `beneficiary`, or a transfer-limit/pause condition is hit) without reverting.
4. Relayer delivers the `RedeemEscrow`/`RefundEscrow` POST request, invoking `onAccept` → `withdraw()`.
5. `token.call(...)` returns `(true, abi.encode(false))`; the code's `if (!success) revert TransferFailed();` check passes because `success == true`.
6. `_orders[commitment][T] -= amount` executes and `_filled[commitment] = beneficiary` is set, finalizing the order — yet `beneficiary`'s `T` balance never increased.
7. The escrowed `amount` of `T` is now permanently unaccounted for and unrecoverable by the beneficiary, since the commitment is already marked filled/refunded.
