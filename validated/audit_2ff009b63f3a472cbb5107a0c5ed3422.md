Confirmed: `timeout: 0` means the request **never expires** ("Messages will never expire") — this is documented explicitly in `docs/content/developers/evm/messaging/post-requests.mdx:44` and implemented in `Message.timeout()` returning `type(uint64).max` when `timeoutTimestamp == 0`, and `EvmHost.dispatch(DispatchPost)` sets `timeoutTimestamp = 0` when `post.timeout == 0` [1](#0-0) [2](#0-1) . Combined with `HyperFungibleToken.send()` burning the sender's tokens immediately before dispatch, and `onAccept()` unconditionally calling `_mint(beneficiary, message.amount)` on the decoded recipient with no zero-address check [3](#0-2) [4](#0-3) , this is a genuine analog of the reported bug class: an address-to-zero omission causes a deterministic, permanent revert in a finalization step whose preceding side effect (the burn) is already irreversible.

### Title
Unvalidated zero-address recipient in `HyperFungibleToken.send()` permanently burns tokens with no possible mint or refund - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, also `evm/src/apps/BridgeToken.sol`'s parent `HyperFungibleToken`, `evm/tron/contracts/apps/IntentGatewayV2.sol` variants where equivalent)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens and dispatches an ISMP POST request encoding an arbitrary `to` recipient with no validation. If `to` decodes to `address(0)` and `timeout` is `0` (the documented "never expires" value), the destination's `onAccept()` will always revert on `_mint(address(0), amount)` (OpenZeppelin's `ERC20._mint` rejects the zero address), and because the request never times out, `onPostRequestTimeout()` can never fire to re-mint a refund. The burned tokens are unrecoverable forever.

### Finding Description
`send()` burns tokens unconditionally before dispatch and forwards `params.to` verbatim as the message recipient, with no check that it decodes to a non-zero address:

```solidity
function send(SendParams calldata params) external payable whenNotPaused {
    _burn(msg.sender, params.amount);
    DispatchPost memory request = _buildDispatchPost(params);
    ...
}
``` [3](#0-2) 

On the destination chain, `onAccept()` decodes the recipient and mints without validation:

```solidity
Message memory message = abi.decode(request.body, (Message));
address beneficiary = _toAddr(message.to);
_mint(beneficiary, message.amount);
``` [5](#0-4) 

`_toAddr` only checks the byte length equals 20; it does not reject an all-zero value, so `to = abi.encodePacked(address(0))` passes through cleanly [6](#0-5) . `_mint(address(0), amount)` then reverts deterministically (OpenZeppelin `ERC20._update`/`_mint` rejects `address(0)`), so `EvmHost.dispatchIncoming`/`onAccept` will fail on every retry — the message can never be successfully delivered.

Recovery normally relies on the timeout path: `onPostRequestTimeout()` re-mints the burned amount to the original sender [7](#0-6) . But `SendParams.timeout` is fully caller-controlled, and the protocol explicitly documents `timeout: 0` as "no timeout... messages will never expire" [8](#0-7) , which `EvmHost.dispatch(DispatchPost)` and the shared `Message.timeout()` helper both implement literally (`timeoutTimestamp = 0` maps to `type(uint64).max`) [1](#0-0) [2](#0-1) . With `timeout = 0`, the message never becomes eligible for the non-membership timeout proof, so `onPostRequestTimeout()` is unreachable, and the burned balance is destroyed with no destination mint and no source-side refund possible — exactly the same "irrecoverable revert on a downstream finalization step whose preceding effect is already committed" shape as the original position-ownership-to-`address(0)` report, except here the destructive step (the burn) happens in the very same transaction that later becomes permanently undeliverable.

The same unguarded `_mint(beneficiary, ...)` / equivalent `IERC20.safeTransfer(beneficiary, ...)` pattern recurs in `WrappedHyperFungibleToken.onAccept()` [9](#0-8)  and `HyperFungibleTokenUpgradeable.onAccept()` [10](#0-9) , and `onPostRequestTimeout` refund paths there are similarly gated behind the same "never times out with `timeout=0`" caller choice.

### Impact Explanation
Any user who calls `send()` with a mistyped/zero-decoded `to` and `timeout = 0` permanently destroys their own bridged balance: the source-chain burn is final, the destination mint can never succeed, and the timeout refund path is unreachable by construction. This is a permanent freezing/loss of user funds reachable from a single unprivileged token-bridge transaction, matching the "permanent freezing of funds" acceptance criterion. Because HFT deployments (e.g. `BridgeToken`, the canonical bridged BRIDGE token) can hold meaningful value, this is at least a Medium-severity fund-loss bug; it escalates further for any integrator that lets a UI/relay pass through user-supplied `to`/`timeout` without sanitization, since a griefing frontend or compromised dependency could silently set `timeout=0` and a malformed `to` on a user's behalf.

### Likelihood Explanation
Reaching this requires only a single call to the public, unprivileged `send()` function with attacker/user-chosen `to = address(0)` (or 20 zero bytes) and `timeout = 0`; both are ordinary, unrestricted parameters with no contract-side validation. `timeout = 0` is not an edge case — it is the documented default for "no timeout," so it will occur in normal usage patterns and in any SDK/UI that omits an explicit timeout.

### Recommendation
- In `send()`/`_buildDispatchPost()`, decode and validate `params.to` resolves to a non-zero address before burning.
- Consider disallowing `timeout == 0` for value-bearing HFT transfers, or otherwise require a bounded timeout so a bad delivery is always recoverable via `onPostRequestTimeout`.
- Add an explicit zero-address check ahead of `_mint(beneficiary, ...)` in `onAccept()` across `HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleToken`, reverting with a descriptive error rather than relying on the implicit OpenZeppelin revert (which still leaves the funds unrecoverable without a timeout path).

### Proof of Concept
1. User calls `HyperFungibleToken.send()` with `SendParams{ dest: <valid chain>, to: abi.encodePacked(address(0)), amount: X, timeout: 0, relayerFee: 0, data: "" }`.
2. `_burn(msg.sender, X)` executes immediately — the tokens are destroyed on the source chain [11](#0-10) .
3. The ISMP POST request is dispatched with `timeoutTimestamp = 0`, i.e., never expiring [1](#0-0) .
4. Any relayer that delivers the message triggers `onAccept()`, which calls `_mint(address(0), X)` and reverts every time [5](#0-4) .
5. Because `timeoutTimestamp == 0`, `Message.timeout()` reports `type(uint64).max`, so the request is never eligible for a timeout proof and `onPostRequestTimeout()` is unreachable [2](#0-1) .
6. `X` tokens are permanently destroyed with no path to mint or refund them.

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
