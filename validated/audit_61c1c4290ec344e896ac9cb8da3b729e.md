### Title
Webhook shop identity is trusted from an unauthenticated header while only the raw body is HMAC-covered - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw HTTP body [1](#0-0) , while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from HTTP headers that are never included in the signed content [2](#0-1) . `Registry.process` only verifies the HMAC of the request and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler [3](#0-2) .

### Finding Description
The binding that should hold is:
`shop_used_by_handler == shop_that_actually_produced_and_was_authorized_for_the_signed_body`

`HmacValidator.validate` only proves `computed_signature(raw_body) == received_signature` [4](#0-3) . It says nothing about which shop the body belongs to, because `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is attacker-controlled input at the HTTP layer and carries no cryptographic binding to the body it accompanies [2](#0-1) .

`Registry.process` raises only if the HMAC check on the body fails, then immediately builds `WebhookMetadata` using `request.shop` (the unauthenticated header) and hands it to the registered handler [3](#0-2) .

Because any user who legitimately installs the app on their own store receives real, correctly-signed webhook deliveries (raw_body + hmac pair) for their own shop, that user fully controls a valid `(raw_body, hmac)` pair. Nothing prevents them from re-POSTing that exact body/hmac pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still succeed (it only checks the body against the signature), and the handler will process the payload believing it originated from the victim shop.

This is the direct analog of the reported bug class: a critical field (`shop`, which downstream code uses to select the tenant/session/database row to act on) is consumed without validating that it is bound to the artifact that was actually authenticated (the HMAC only "returns true" for the body, and that boolean result is trusted for more than what it proves — analogous to a `transfer()` return value being trusted without confirming it actually covers the state being relied upon).

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select which merchant's session/record/database row to mutate (the documented and expected pattern, per `docs/usage/webhooks.md`), an attacker with any legitimate install of the app can forge webhook deliveries that are misattributed to a different (victim) shop. This is a cross-tenant data integrity/confidentiality issue — data belonging to the attacker's own shop can be injected into, or trigger side effects against, another tenant's context. Per the rules, cross-tenant access is rated Critical.

### Likelihood Explanation
Exploitation requires no privileged credentials, no access token, and no knowledge of the app's `client_secret`: the attacker only needs (a) the ability to install the app once on a store they control (a completely normal, unprivileged step for any Shopify app), and (b) the ability to POST to the app's public webhook endpoint with custom headers, which is standard HTTP client capability. This makes the attack straightforward for any external unprivileged user who can create/use a development or trial store.

### Recommendation
Do not treat header-derived request attributes (`shop`, `topic`, `webhook-id`, `api-version`) as authenticated merely because the raw body's HMAC validates. Either:
1. Include the shop domain (and other identity-relevant headers) in the signed/verified content used by `to_signable_string`, or
2. Independently confirm that the `shop` header matches an expected/known value for the session/topic being processed before invoking the handler, or
3. Document explicitly (and enforce in the gem, where feasible) that `WebhookMetadata#shop` is not cryptographically authenticated and require host applications to cross-check it against out-of-band webhook subscription data (e.g., the webhook ID registered per-shop) before trusting it.

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com`, obtaining OAuth access and triggering a real webhook, e.g. `orders/create`.
2. Shopify posts the webhook to the app's endpoint with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - `x-shopify-topic: orders/create`
   and body `raw_body` (attacker fully observes this exact byte sequence and signature, e.g. via a local proxy/logging).
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint again, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. In `Webhooks::Request`, `hmac` and `to_signable_string` only depend on `raw_body` [5](#0-4) , so `Utils::HmacValidator.validate(request)` returns `true` (bytes match; the domain was never part of the signed input) [6](#0-5) .
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))` with `shop == "victim-shop.myshopify.com"` even though the body content is the attacker's own order data [3](#0-2) .
6. Any host application logic that keys off `data.shop` (e.g., "find the victim's stored session/DB row and apply this webhook payload") is fooled into cross-tenant processing.

Note: I was unable to locate `lib/shopify_api/webhooks/webhook_metadata.rb` in the indexed portion of the codebase (only its reference in `webhook_handler.rb` was found), so I could not directly inspect its field definitions; however, `Registry.process`'s call site confirms `shop: request.shop` is passed through unmodified. If the wiki/full repo contains additional binding logic inside `WebhookMetadata` itself, a Devin session with full file access would be needed to confirm there is no additional check there.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
