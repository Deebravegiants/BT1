### Title
Pausing `HyperFungibleToken`/`WrappedHyperFungibleToken` after a `send()` permanently blocks the timeout refund of already-burned/locked user funds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.send()` burns the caller's tokens immediately and dispatches an ISMP POST request. If the request later times out, the only way to get the burned tokens back is `onPostRequestTimeout()`, which re-mints them to the original sender. Both `send()` and `onPostRequestTimeout()` are gated by the same `whenNotPaused` modifier, so if the owner pauses the contract any time between the burn and the timeout delivery, the refund path reverts and the user's tokens remain destroyed with no compensating mint until (and unless) the contract is unpaused. The `WrappedHyperFungibleToken` variant has the identical pattern for locked collateral.

### Finding Description
In `send()` the caller's balance is burned unconditionally as soon as the function is entered: [1](#0-0) 

The compensating refund on timeout is implemented in `onPostRequestTimeout()`, which is the *only* code path that re-mints the burned amount back to the sender: [2](#0-1) 

Both functions share the `Pausable` state via the `whenNotPaused` modifier, controlled solely by the owner-only `pause()`/`unpause()` functions: [3](#0-2) 

Because `send()` already destroyed the tokens (line 265) before the ISMP round trip completes, and because `onPostRequestTimeout` requires `whenNotPaused` (line 321), any pause issued after a user's `send()` but before their timeout is delivered makes it impossible to restore the user's balance. The user has no other recovery mechanism — `_mint` only happens in `onAccept` (destination-side mint, irrelevant to the source-side refund) and `onPostRequestTimeout`.

The exact same construction appears in `WrappedHyperFungibleToken`, where instead of burn/mint the contract locks/unlocks the underlying ERC-20 (or WETH): [4](#0-3) [5](#0-4) 

Here the underlying ERC20/WETH is already escrowed in the contract (not destroyed), but the funds are still frozen for the user as long as the contract stays paused, since `onPostRequestTimeout` cannot execute while paused — there is no permissionless "claim later" fallback once the pause is lifted, other than waiting indefinitely.

`HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` mirror this exact pattern (confirmed via the same `whenNotPaused` modifier on `onPostRequestTimeout`), so the vulnerability is present in every deployment based on these base contracts, e.g. `BridgeToken`. [6](#0-5) 

### Impact Explanation
This is a real freezing-of-funds bug class analogous to the reported Ubiquity issue: the user has already irrevocably paid (burned tokens / locked collateral) at `send()` time, but the refund on failure (timeout) is gated behind the same pause switch used for the forward path. A routine operational pause (e.g., for an unrelated incident, migration, or upgrade) that happens to overlap with any in-flight cross-chain transfer will strand that specific user's funds for the duration of the pause — and for `HyperFungibleToken` specifically, the tokens are burned, so during the pause window the user holds nothing at all, not even the escrowed original. If the pause is indefinite (deliberate emergency freeze, forgotten unpause, or lost/rotated owner key), the loss becomes permanent. This satisfies the "permanent freezing of funds" bar for Medium severity.

### Likelihood Explanation
No privileged action is required from the affected user's perspective — a normal `send()` call by any unprivileged sender can be caught mid-flight by a legitimate, non-malicious pause. Cross-chain timeouts routinely take longer than a typical incident-response pause window, so overlap between "pending timeout" and "contract paused" is a realistic operational scenario rather than a contrived edge case.

### Recommendation
Do not gate the refund/timeout-recovery path (`onPostRequestTimeout`) behind `whenNotPaused`. Pausing should stop new inbound/outbound transfers (`send`, `onAccept`) but must still allow already-burned/locked funds to be returned to their original owners via timeout processing. Remove the `whenNotPaused` modifier from `onPostRequestTimeout()` in `HyperFungibleToken.sol`, `HyperFungibleTokenUpgradeable.sol`, `WrappedHyperFungibleToken.sol`, and `WrappedHyperFungibleTokenUpgradeable.sol` (and any downstream override such as `BridgeToken`), so refunds can always be settled regardless of pause state.

### Proof of Concept
1. Alice calls `HyperFungibleToken.send()` with `amount = 1000`, `timeout = T`. Her 1000 tokens are burned immediately (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:265`).
2. Before the ISMP request is delivered, the owner calls `pause()` for an unrelated reason (e.g., detecting a bug on another chain).
3. The request never gets delivered and times out; a relayer submits the timeout proof, which calls `onPostRequestTimeout()`.
4. Because the contract is paused, `onPostRequestTimeout` reverts on `whenNotPaused` (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:321`), so Alice's 1000 tokens are not re-minted.
5. Alice's balance remains at zero for as long as the pause lasts — with no other way to reclaim the burned tokens — even though she did nothing wrong and the pause had nothing to do with her transfer.

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Attempts to unwrap WETH and refund native tokens.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
