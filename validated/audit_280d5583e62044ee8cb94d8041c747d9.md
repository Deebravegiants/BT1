### Title
Missing `return` statements in OIDC token-exchange handler allow session cookie to be issued after failed/incomplete authentication - (File: core/sessions/oidcauth/oidc.go)

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` contains two error branches that log the error and write an HTTP response body, but omit the `return` statement, so execution falls through and continues the login flow anyway. This mirrors the reported bug class ("uncaptured/overshadowed control flow leading to unexpected outcomes" from unchecked/ignored results) applied to an authentication path reachable by any unprivileged client completing the OIDC login flow.

### Finding Description
In `handleTokenExchange` (`core/sessions/oidcauth/oidc.go`):

1. Missing `email` claim (lines 226-230): [1](#0-0) 
```
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
```
There is no `return` after writing the error response. Execution continues to role mapping, session insertion, and cookie issuance using an empty/zero-value `email`.

2. Failed session insert into `oidc_sessions` (lines 250-260): [2](#0-1) 
```
clSession := clsessions.NewSession()
_, err = oi.ds.ExecContext(
    ctx,
    "INSERT INTO oidc_sessions (id, user_email, user_role, created_at) VALUES ($1, $2, $3, now())",
    clSession.ID,
    strings.ToLower(email),
    role,
)
if err != nil {
    oi.lggr.Errorf("unable to create new session in oidc_sessions table %v", err)
    c.String(http.StatusInternalServerError, "Error creating session")
}
```
Again, no `return`. The function proceeds to audit-log a successful login, set the session cookie (`ginSession.Set(webauth.SessionIDKey, clSession.ID)`), save the cookie, and finally respond `200 OK` with `Success: true`: [3](#0-2) 
```
oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": email})

// save session
ginSession.Set(webauth.SessionIDKey, clSession.ID)
err = ginSession.Save()
...
c.JSON(http.StatusOK, ExchangeTokenResponse{
    Success: true,
})
```
This is the same class of defect as the report: an error/return-value is generated but not acted upon (not "captured"), so the caller's control flow proceeds as if nothing went wrong, and the response body ends up containing multiple, contradictory writes (an error string followed by a success JSON body / status).

The role (`role`) that gets embedded into the client's session cookie is derived purely from OIDC group claims (`IDClaimsToUserRole`) independent of whether `email` was successfully extracted, so the missing `return` on the email-claim branch does not gate role assignment on a valid email.

### Impact Explanation
- Audit log poisoning: `AuthLoginSuccessNo2FA` is recorded even when the underlying DB insert of the session failed, producing a false "success" audit trail for what was actually a failed login — undermining forensic/audit trust described as one of the unprivileged-actor-relevant areas (secret/session handling correctness).
- Cross-user response confusion: because two separate `c.String`/`c.JSON` writes can occur on the same `gin.Context` (error string then success JSON), the client can receive a malformed/ambiguous HTTP response (status code already committed by the first write, body then appended with the JSON success payload), which can confuse client-side session-state logic that only checks for `Success: true` in the JSON, potentially believing it is authenticated when the server-side session row was never persisted.
- Not a full authentication bypass: `AuthorizedUserWithSession` (lines 351-391) subsequently re-queries `oidc_sessions` by ID and requires a matching, non-expired row, so a session-insert failure alone will not let a request pass a later authorization check — the session cookie issued would reference a non-existent row and would fail on the next authenticated request. This limits the severity to inconsistent state / audit-trail corruption / malformed responses rather than direct privilege escalation.

### Likelihood Explanation
Requires the OIDC token-exchange DB insert to fail (e.g., transient DB error, duplicate ID collision, connectivity blip) or the `email` claim to be absent from the ID token — both are edge-case/error conditions rather than attacker-controlled inputs under normal operation, so likelihood is low-to-medium; it is not a reliably attacker-triggered bypass, but does represent a real code defect that produces incorrect audit records and inconsistent responses whenever those error paths occur.

### Recommendation
Add `return` immediately after both error branches in `handleTokenExchange`:
- After `c.String(http.StatusInternalServerError, "Failed to get email from claims")` (around line 229).
- After `c.String(http.StatusInternalServerError, "Error creating session")` (around line 259), before the audit log call and cookie set.

Additionally, consider not calling `oi.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, ...)` until after the session row is confirmed persisted and the cookie has been successfully saved, so audit records accurately reflect true login outcomes.

### Proof of Concept
Not independently reproducible from static analysis alone since it requires forcing a transient failure of `oi.ds.ExecContext` for the `INSERT INTO oidc_sessions` statement (e.g., via a DB fault-injection or a duplicate `clSession.ID`, which is a UUID and thus practically requires DB-level fault injection) or an ID token lacking an `email` claim from the IdP. Given the current tooling (read-only code search), I could not execute or verify runtime behavior; this assessment is based on direct code review of the control-flow in `core/sessions/oidcauth/oidc.go`. A Devin session with code-execution access would be needed to reproduce the double-write response and false audit log entry end-to-end.
