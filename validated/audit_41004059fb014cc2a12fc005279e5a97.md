### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but the `shop` value that identifies *which merchant/tenant* the webhook belongs to is taken from an HTTP header that is never included in the signed content. This breaks the intended binding `hmac == HMAC(secret, body || shop)` down to `hmac == HMAC(secret, body)`, letting an attacker replay a legitimately-signed webhook body under an arbitrary `shop-domain` header and have it processed as if it came from a different tenant.

### Finding Description
`Registry.process` verifies authenticity like this: [1](#0-0) 

The HMAC check calls into `Utils::HmacValidator.validate`, which computes the signature over `request.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only the raw body**, while `shop` is read from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`), completely independent of the HMAC computation: [3](#0-2) 

After the HMAC check passes, `request.shop` — never verified — is forwarded straight into the handler as the tenant identity: [4](#0-3) 

This is the same bug class as the report: a permission/identity value (`sender` in the ULN report; `shop` here) is acted upon by a security-relevant function while a completely separate, unauthenticated channel (`SetDenylist` with no `has_one = owner`; here the `shop-domain` header) controls it, breaking the equality between *the value the code trusts* and *the value that was actually authenticated*. Here the broken equality is: `shop used by the app to attribute/process the webhook == shop that produced the HMAC-signed body`. Only the second half of that equality is ever checked (implicitly, since the body's own JSON payload usually references a shop's resources) — but the header itself, and thus `WebhookMetadata#shop` that host applications key their session/tenant lookups on, is unauthenticated.

Any host application that uses `data.shop` from `WebhookMetadata` (as documented/intended for this gem) to look up the merchant's session, access token, or tenant-scoped data — the standard integration pattern for this gem — will attribute an HMAC-valid webhook body to whatever `shop` value the request supplied, regardless of which store's secret actually produced the signature-eligible body content. Since `to_signable_string` for webhooks is body-only, an attacker who obtains one legitimate signed webhook body (e.g., from their own trial/dev store, or a captured/replayed request) can resubmit the same body with a forged `shopify-shop-domain` header pointing at a victim shop; the HMAC still validates because the header was never part of what's signed.

### Impact Explanation
This crosses a tenant boundary: it lets an unprivileged/external actor cause the app to process a webhook payload as belonging to a shop chosen by the attacker rather than the shop whose secret actually authorized the request content, i.e., cross-tenant confusion of webhook events. Depending on how the host app keys per-shop side effects (e.g., app/uninstalled, shop/redact, orders/*, GDPR redact topics) off `WebhookMetadata#shop`, this can trigger unauthorized cross-tenant actions/state changes (e.g., marking another shop as redacted/uninstalled, corrupting another tenant's synced data) purely from a request an attacker fully controls in terms of headers, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Medium: the attacker needs one legitimately HMAC-signed webhook body (trivially obtainable by installing the app on their own free/dev store and capturing an outbound webhook Shopify sends them), and then can freely replay that body to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header, since nothing else in the request is checked against the shop.

### Recommendation
Bind the `shop` identity into the signed material or otherwise cryptographically tie it to the payload before trusting it:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `to_signable_string` for `Webhooks::Request` so the HMAC covers the full identifying context, not just the raw body, or
- Cross-check `shop` (and topic) against a value embedded inside the JSON body itself where Shopify includes shop-scoped identifiers, rejecting mismatches, before constructing `WebhookMetadata`.

### Proof of Concept
1. Install the app on attacker-controlled dev store `attacker.myshopify.com`; capture a legitimate outbound webhook Shopify sends: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Send a new POST to the app's webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (body-only per `Webhooks::Request#to_signable_string`) — it matches `H`, so `Registry.process` accepts the request.
4. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop == "victim.myshopify.com"`, even though nothing about `victim` participated in producing `H`; the app's handler now processes/acts as if `victim.myshopify.com` sent this webhook.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
