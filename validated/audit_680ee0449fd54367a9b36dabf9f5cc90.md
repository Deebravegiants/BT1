## Title
Webhook HMAC only covers the raw body, not the `shop-domain` header, allowing cross-tenant webhook forgery — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read from HTTP headers that are never included in the HMAC input. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC and then unconditionally hands `request.shop` (the unauthenticated header) to the handler as the tenant identifier. This breaks the intended identity binding `hmac_verified_bytes == (body, shop)`; in reality it only enforces `hmac_verified_bytes == body`, letting an attacker who can obtain one genuine signed webhook body reuse it with an arbitrary `shop-domain` header.

### Finding Description
- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` and compares it to the `hmac` header value: [3](#0-2) 
- `Registry.process` validates only that body HMAC, then immediately builds `WebhookMetadata` using `request.shop` (the unverified header) and dispatches it to the app's handler: [4](#0-3) 

Because the app's `api_secret_key` (client secret) is the same for every shop that has installed the app, any shop that installs the app (an ordinary, unprivileged action available to any internet user) can receive a genuine webhook, capture its raw body plus its valid `X-Shopify-Hmac-Sha256` value, and then send that exact `(body, hmac)` pair straight to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` only checks that the body's HMAC matches — it never checks that the signed body corresponds to the claimed shop — so the forged request passes validation. `Registry.process` then calls the handler with `shop: <attacker-chosen shop>`, causing the app to process attacker-controlled webhook data under another tenant's identity.

The equality that should hold: `authenticated_shop (bound into HMAC) == shop used to select/create tenant-scoped session/data`. What actually holds: `authenticated_bytes (body only) == verified` and `shop_used_by_handler = unauthenticated_header`, i.e. the shop used for tenant dispatch is never part of the authenticated material.

### Impact Explanation
This is a cross-tenant access vector: any actor able to install the app on their own store (fully self-service, no special privilege) can forge webhook deliveries that the receiving app will attribute to any other shop domain of the attacker's choosing, since the shop identity is never bound to the signature. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to select which merchant's session/token to update, invalidate, or act upon — e.g. `app/uninstalled`, `shop/redact`, order or customer data topics), this can lead to cross-tenant data corruption, unauthorized state changes tied to a victim shop, or improper triggering of tenant-scoped business logic under a spoofed identity — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple shops: obtaining one's own genuine webhook payload requires nothing more than installing the app (available to any unprivileged actor), and replaying it against the app's public webhook endpoint with a modified header requires only basic HTTP tooling — no secret material, no privileged account, and no interception of others' traffic is needed.

### Recommendation
Bind the shop identity into the authenticated material before dispatch: either include the shop domain (and topic) in the signable string used for HMAC verification, or independently cross-validate `request.shop` against a value provable to have come from Shopify for that specific delivery (e.g., verify it matches a shop the app has an active session/installation for, and/or verify webhook_id uniqueness/idempotency tied to a known shop). At minimum, document and enforce that `Registry.process` must not treat header-derived `shop`/`topic` as trusted beyond body-HMAC verification without an additional binding check.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker-shop.myshopify.com"
# and receives a legitimate webhook delivery, e.g.:
raw_body = '{"id": 123, "note": "hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
# (captured from the real Shopify-Hmac-Sha256 header of a genuine delivery to attacker's own shop)

# Attacker now POSTs directly to the app's public webhook endpoint,
# reusing the same body+hmac but claiming to be from the victim shop:
headers = {
  "X-Shopify-Topic" => "orders/create",
  "X-Shopify-Hmac-Sha256" => Base64.encode64(valid_hmac),
  "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body's HMAC.
# The handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though the body/HMAC never proved anything about victim-shop.
```
