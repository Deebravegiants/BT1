## Title
Unbounded PNL Accrual Leading to Permanent Freeze of Pool Funds via Division-by-Zero Panic in `calc_take_pnl` — (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl`, invoked unconditionally by the unprivileged `Deposit` instruction and by `WithdrawPnl`, monotonically accumulates `amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin` with no check against the AMM's actual vault balances at accrual time. Once these accrued values reach the total vault balance (driving `total_pc_without_take_pnl` or `total_coin_without_take_pnl` to `0`), the very next call into `calc_take_pnl` invokes `Calculator::calc_x_power`, which performs `checked_div(current_y).unwrap()` on that zero value, causing a hard panic. Because every state-mutating instruction (`Deposit`, normal-status `Withdraw`, `WithdrawPnl`) calls `calc_total_without_take_pnl_no_orderbook`/`calc_take_pnl` at the start of its execution, and nothing outside `WithdrawPnl` can ever decrease `need_take_pnl_*`, this single reachable zero-denominator state permanently bricks the pool — no further deposits, withdrawals, or pnl collection are possible, freezing all coin/pc vault funds and outstanding LP tokens.

### Finding Description
`calc_take_pnl` computes the pool's incremental PNL by comparing the current invariant (`x1`,`y1`, normalized current vault totals) against the last-recorded baseline (`target.calc_pnl_x`, `target.calc_pnl_y`) via `Calculator::calc_x_power`: [1](#0-0) 

`current_y` here is `y1` — the normalized `total_coin_without_take_pnl`. If that value is `0`, `checked_div(current_y).unwrap()` panics.

`need_take_pnl_pc`/`need_take_pnl_coin` are accumulated with plain `checked_add` and never validated against the real vault balance at accrual time: [2](#0-1) 

These accrued amounts are subtracted from the raw vault balance every time any instruction computes the pool's usable totals: [3](#0-2) 

`process_deposit` calls this + `calc_take_pnl` unconditionally on every deposit, regardless of amount or pool status: [4](#0-3) 

`process_withdrawpnl` — the only instruction capable of ever resetting `need_take_pnl_pc`/`need_take_pnl_coin` back to `0` — performs the exact same calculation before it can do anything else: [5](#0-4) 

Because `need_take_pnl_*` only ever grows (via `Deposit`/`Withdraw` calls that any unprivileged user can trigger, interleaved with price-moving `SwapBaseIn`/`SwapBaseOut` calls that shift the invariant and cause `calc_take_pnl` to detect additional "profit"), and there is no code path that bounds the accrual to the actual vault reserves before it is used, an attacker can drive `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) to exactly `0`. The very next `calc_take_pnl` invocation (from `Deposit` or `WithdrawPnl`) then panics inside `calc_x_power`. Since `WithdrawPnl` is the only mechanism to reduce `need_take_pnl_*`, and it panics under the same condition, the pool state becomes permanently unusable.

### Impact Explanation
Once triggered, this permanently freezes:
- All liquidity providers' locked coin/pc vault funds (they can no longer withdraw normally, since `Withdraw` in non-`WithdrawOnly` status also calls `calc_take_pnl` and would panic identically — see `program/src/processor.rs:1737-1749`).
- The protocol's own accrued PNL (`WithdrawPnl` panics too, so even the privileged `pnl_owner` cannot recover funds without an admin-forced pool status change and manual on-chain repair).

This satisfies the "permanent freezing of user or LP funds" criterion — a Solana-runtime program panic aborts that transaction, but because the poisoned state (`need_take_pnl_* == vault balance`) persists on-chain, every subsequent legitimate transaction into the affected instructions reproduces the same panic indefinitely, which is the direct on-chain analog of the CVE's "hang or repeatable crash" DOS bug class.

### Likelihood Explanation
The path is reachable purely through unprivileged instructions (`Deposit`, `SwapBaseIn`/`SwapBaseOut`) with attacker-chosen amounts, executable within one or a small number of transactions (multiple instructions can be packed into a single Solana transaction). It requires no leaked keys, no validator collusion, and no off-chain component — only repeated legitimate calls that exploit the unbounded accrual logic in `calc_take_pnl`.

### Recommendation
- Bound `need_take_pnl_pc`/`need_take_pnl_coin` accrual in `calc_take_pnl` so it can never exceed the actual current vault balance (i.e., clamp `pc_pnl_amount`/`coin_pnl_amount` to `min(computed_pnl, vault_balance - already_accrued)`).
- Replace the `.unwrap()` calls in `Calculator::calc_x_power` (and related normalize/restore helpers) with `checked_*` operations that return a proper `AmmError` instead of panicking, and explicitly guard against `current_y == 0` / `x1 == 0` before entering the division.
- Add an invariant check in `calc_total_without_take_pnl_no_orderbook` that fails gracefully (already partially done) and ensure `WithdrawPnl` can still make progress (e.g., allow partial pnl withdrawal down to available balance) even when `need_take_pnl_*` is inconsistent with real reserves.

### Proof of Concept
1. Attacker (or any user) creates a pool via `Initialize2` with the standard flow (`program/src/processor.rs:549`).
2. Attacker submits a transaction containing repeated `SwapBaseIn`/`SwapBaseOut` instructions (see `program/src/processor.rs:1843-2049`) to move the pool price away from the last recorded `target_orders.calc_pnl_x/y` baseline, followed by a small `Deposit` instruction (`program/src/processor.rs:1109` onward) to trigger `calc_take_pnl` and accrue `need_take_pnl_pc`/`need_take_pnl_coin`.
3. Attacker repeats step 2 (across one or a few transactions) until `amm.state_data.need_take_pnl_coin` (or `_pc`) equals the raw vault balance, making `total_coin_without_take_pnl` (or `_pc`) computed in `calc_total_without_take_pnl_no_orderbook` (`program/src/math.rs:238-250`) equal to `0`.
4. Any subsequent `Deposit` or `WithdrawPnl` call triggers `calc_take_pnl` → `Calculator::calc_x_power` → `checked_div(current_y).unwrap()` on `current_y == 0`, panicking the program (`program/src/math.rs:57-58`).
5. Since nothing outside `WithdrawPnl` can reduce `need_take_pnl_*`, and `WithdrawPnl` panics identically, the pool (and all LP/user funds within it) is permanently unusable.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
