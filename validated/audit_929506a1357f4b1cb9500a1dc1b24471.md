### Title
Missing receive-balance verification in Tron IntentGatewayV2.placeOrder lets fee-on-transfer/deflationary tokens over-credit escrow, insolvent by design - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` escrows tokens by trusting the caller-declared `order.inputs[i].amount` rather than measuring the token balance actually received by the contract, unlike the corrected `evm/src/apps/IntentGatewayV2.sol` implementation that measures `balanceOf` before/after every transfer.

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract does: [1](#0-0) 
It calls `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then immediately credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived purely from the user-supplied `order.inputs[i].amount` minus the protocol fee — never from an actual measured balance delta. In the predispatch branch, `requiredAmount`/`balance` checks only guard a `>=` floor (`if (balance < requiredAmount) revert`), and any surplus is emitted as `DustCollected`, but the escrow credit again uses `reducedInputs[i].amount`, not the measured `balance` actually swept into the gateway: [2](#0-1) 

For any ERC20 with a transfer fee/rebase/deflationary mechanic, the amount actually received by the gateway (`balanceOf(this)` delta) is strictly less than `order.inputs[i].amount`. The escrow ledger `_orders[commitment][token]` is nonetheless credited with the full (fee-reduced only by protocol fee, not by the token's own transfer tax) declared amount. This directly parallels the reported bug class: the contract lacks logic to reconcile internal accounting (`_orders`) against the balance actually received, instead trusting a caller-supplied or pre-transfer value.

The companion, currently-deployed EVM contract fixes exactly this by snapshotting `balanceOf` before and after every transfer/sweep and overwriting `order.inputs[i].amount` with the measured delta before it is used to compute `reducedInputs` and to credit `_orders`: [3](#0-2) 
This fix is validated by dedicated tests such as `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, and `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, confirming the project explicitly treats "escrow diverging from actual received balance" as a vulnerability class to be prevented. [4](#0-3) 

### Impact Explanation
Because `_orders[commitment][token]` can be credited with more than the gateway's real token balance for that order, `_withdraw` (used by both `RedeemEscrow` fills and `RefundEscrow` cancellations) will transfer out the over-credited amount: [5](#0-4) 
Since escrow for one order's inflated accounting is paid from the gateway's pooled token balance, a fee-on-transfer/deflationary input token creates a shortfall that is ultimately paid for out of other users' or solvers' escrowed balances of that same token — the last order(s) to be redeemed for that token will revert or receive less than owed once the pool is drained, i.e., permanent freezing/loss of funds for other legitimate order participants. This is a direct violation of the invariant (enforced elsewhere in the codebase) that on-chain escrow accounting must equal actually-held token balance.

### Likelihood Explanation
Reachable by any unprivileged user submitting a single `placeOrder` transaction with a fee-on-transfer or deflationary ERC20 as an input token — no special privileges, governance, or multi-step setup required. The only precondition is that such a token is accepted as an order input on the Tron deployment (there is no on-chain allowlist restricting input token types in `placeOrder`), making this trivially triggerable by any user of the Tron IntentGatewayV2.

### Recommendation
Apply the same fix already present in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: record `balanceOf(address(this))` (or the dispatcher's balance, for predispatch) immediately before and after each `safeTransferFrom`/sweep, and use the measured delta — not the caller-declared `order.inputs[i].amount` — as the basis both for the commitment hash and for crediting `_orders[commitment][token]`.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC20 and register it as a valid input token on the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, approving the gateway for `1000e18`.
3. `safeTransferFrom(user, gateway, 1000e18)` executes; due to the 1% tax the gateway's actual `balanceOf` increases by only `990e18`.
4. `_orders[commitment][FOT] += reducedInputs[0].amount` credits `1000e18` (minus only the protocol fee, if any) — i.e., ~1% (`10e18`) more than what the gateway physically holds for this order.
5. Repeat with additional orders using the same fee-on-transfer token; the sum of all `_orders[*][FOT]` entries will exceed `FOT.balanceOf(gateway)`.
6. When solvers/users call `RedeemEscrow`/`RefundEscrow` (`_withdraw`) to claim their escrow, the last claimant(s) for that token find the gateway's balance insufficient, causing their `safeTransfer` to revert (funds frozen) or, if partial fills already drained the balance, an earlier withdrawal effectively takes tokens that rightfully belonged to a later order — demonstrating the accounting-vs-actual-balance drift described in the report's bug class.

            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),

            output: output
        });

        assertEq(
