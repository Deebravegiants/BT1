### Title
Webhook shop identity (`x-shopify-shop-domain`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `Utils::HmacValidator` authenticates the payload bytes but not the `shop`, `topic`, `webhook_id`, or `api_version` values that `Registry.process` extracts from unauthenticated HTTP headers and hands to the host app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers (`shopify_header`) that are attacker-controllable on any POST to the app's webhook endpoint, yet `to_signable_string` only returns `@raw_body` — none of these headers are included in the HMAC-signed content.

`Registry.process` verifies the HMAC over just this signable string, then constructs `WebhookMetadata` using the unauthenticated header-derived `shop`, `topic`, and `webhook_id`: [2](#0-1) 

`Utils::HmacValidator.validate` (shared by both OAuth callback and webhook verification) computes the signature strictly from `to_signable_string` against `Context.api_secret_key`: [3](#0-2) 

Because `Context.api_secret_key` is the single app-wide client secret (identical for every shop that has installed the app), any body+HMAC pair that is valid for one shop's webhook is also valid — bit for bit — when replayed with a different `x-shopify-shop-domain` header. The equality the code should enforce is:
`shop bound by the HMAC == shop used to route/process the webhook`
but what is actually enforced is:
`HMAC validates raw_body == true` while `shop used to process = unauthenticated header value`.

This breaks the identity binding described in the rules: "a field acted on but not covered by the HMAC."

### Impact Explanation
An attacker who controls any shop that has the app installed (a normal, unprivileged merchant install — no special access token or secret needed) can capture a legitimate webhook delivery (raw body + `x-shopify-hmac-sha256`) sent to their own endpoint, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header to name a victim shop. `Registry.process` will validate the HMAC successfully (it only checks the body) and dispatch to the handler with `WebhookMetadata#shop` set to the victim's domain. Any host application logic that uses `data.shop` to select which tenant's session/access-token/records to act on (e.g., `app/uninstalled` cleanup, billing updates, order/customer record mutation keyed by shop) will operate on the wrong tenant, constituting cross-tenant access/manipulation.

### Likelihood Explanation
Likelihood is realistic: any entity that has installed the app on a shop they control (the minimal bar for any Shopify app — no credentials beyond a normal app install) can capture one legitimate webhook and immediately replay it against any other shop domain string of their choosing, since the shared secret and lack of header coverage make the exploit deterministic and repeatable, not probabilistic.

### Recommendation
Include the identity-relevant webhook headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed content, e.g. by having `to_signable_string` concatenate a canonical representation of these headers with the raw body, and reject requests where the recomputed signature does not match. Alternatively/additionally, cross-check `request.shop` against an expected/known shop associated with the session store before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate, low-privilege install).
2. Shopify sends a webhook, e.g. `orders/create`, to the app:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `{"id": 1, ...}`
3. Attacker captures the raw body and the `x-shopify-hmac-sha256` value from this delivery (they can trigger it themselves, e.g. by creating an order in their own store).
4. Attacker resends the identical body and HMAC header to the app's public webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) using the app's single `api_secret_key` — validation succeeds because the body was not modified.
6. `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: ..., ...)` is passed to the host app's handler, which now processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
