Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain`, `topic`, and `webhook-id` HTTP headers—none of which are covered by that signature—to build the `WebhookMetadata` object handed to the app's own handler. Because the same `client_secret` is shared across every shop that has installed the app, a malicious merchant who has installed the app can capture a valid `(raw_body, hmac)` pair from a webhook delivered for their own shop and resend it to the app's endpoint with a spoofed `shop-domain` header pointing at a victim shop. The signature will still validate, since it authenticates the app but not the tenant.

### Finding Description
The equality this code implicitly (and incorrectly) assumes is:

`shop-domain header value == shop that produced/authorized this HMAC`

but the HMAC actually only proves:

`raw_body == bytes signed by Shopify with this app's client_secret`

`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read directly from unauthenticated HTTP headers: [2](#0-1) 

`Registry.process` validates HMAC against the whole `request` object (which delegates to `to_signable_string` = raw body only), then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata` passed to the app-defined handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the raw body, with no binding to shop/topic/id: [4](#0-3) 

Because `api_secret_key` (the HMAC key) is a single, app-wide secret shared by all shops that installed the app (not a per-shop key), any shop that has legitimately installed the app can obtain valid `(raw_body, hmac)` pairs for events on their own store, then replay them against the app's webhook endpoint while swapping the `shopify-shop-domain` / `x-shopify-shop-domain` header to a different, victim shop that also has the app installed. `Registry.process` will accept it as authentic (`HmacValidator.validate` only checks the body) and will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

This directly matches the report's bug class: a field that is *acted upon* (`shop`, used by the handler as the tenant/session key to store or process data) is not covered by the identity-binding check (the HMAC), analogous to the price used for the collateral-ratio check not being the price that was actually revalidated.

### Impact Explanation
This is a cross-tenant data-injection / attribution vulnerability: an attacker who legitimately controls Shop A (a real, unprivileged app-install owner) can cause the app to process webhook payloads under a victim Shop B's identity. Depending on the host application's use of `WebhookMetadata#shop` (e.g., to select the DB row/session to update, to trigger back-end actions, or to indicate order/customer changes), this can lead to writing attacker-controlled data into a different tenant's records, or triggering privileged actions in the victim's context — satisfying the "cross-tenant access" Critical impact.

### Likelihood Explanation
Requires only that the attacker be a normal app installer (no special privileges, no access token or `client_secret` needed) and that the app process HTTP webhooks via this gem's `Webhooks::Registry.process`/`Webhooks::Request`. The attacker needs to intercept/capture one webhook delivery to their own shop (trivial, since they control the receiving endpoint or can sniff their own traffic) and know another installed shop's domain (often discoverable/guessable, e.g., via app listing or public storefront domain). No cryptographic material needs to be broken — the HMAC and its secret remain intact and valid; only the unauthenticated header is forged.

### Recommendation
Bind the shop (and preferably topic/webhook id) into the HMAC-protected signable string, or otherwise cryptographically tie the shop identity to the payload before trusting it. At minimum, `Request#to_signable_string` (or a new verification step in `Registry.process`) should include `shop-domain` so a body signed for shop A cannot be replayed while claiming to be from shop B. Since the header is set by Shopify and not user-supplied, this doesn't change Shopify's on-the-wire format—only how this gem verifies request authenticity per-tenant. Absent a change to the raw HMAC computation (which mirrors Shopify's actual wire format), the library should at minimum provide/require an explicit "expected shop" check so host applications aren't left implicitly trusting an unauthenticated header as a tenant identifier.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers an event that fires a webhook to the app's registered endpoint (e.g., updates a product), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header value — both valid, signed by the app's shared `client_secret`.
3. Attacker resends the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a different shop that also installed the app).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, client_secret, raw_body)` — this still matches, since `raw_body` and the secret are unchanged. [5](#0-4) 
5. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and invokes the app's handler, which processes the forged data as though it originated from the victim shop. [6](#0-5)
