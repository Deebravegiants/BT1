### Title
`EvmHost.dispatch`/`fundRequest` execute native→feeToken swaps priced at execution time with no caller-supplied minimum output, exposing dispatchers to sandwich/price manipulation - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` all accept native token payment and internally swap it to `feeToken` via `IUniswapV2Router02.swapETHForExactTokens`, sized so the *output* (the fee amount) is fixed and only the *input* (native spent) floats with `msg.value` as the implicit ceiling [1](#0-0) . This mirrors the reported `SwapperImpl.flash` pattern in spirit — a function that performs a price-dependent conversion inside a user transaction with only an implicit bound (`msg.value`) and no caller-declared maximum acceptable price/slippage parameter, and no protection against the AMM being manipulated within the same block.

### Finding Description
The dispatcher functions compute the swap path (`WETH -> feeToken`) and call `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` [1](#0-0) , `dispatch(DispatchGet)` [2](#0-1) , and `fundRequest` [3](#0-2) . The documentation explicitly acknowledges that fee estimation via `HyperApp.quote()` — which reads `getAmountsIn` from the same Uniswap V2 router — "**uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks**" and warns callers to only use it off-chain [4](#0-3) .

Because the actual on-chain conversion is bound only by `msg.value` (a value computed off-chain from a stale quote) rather than an explicit, caller-supplied minimum-fee-token-out or maximum-native-in parameter checked against a fresh on-chain price bound, an attacker who observes a pending `dispatch`/`fundRequest` transaction in the mempool can sandwich it: front-run to move the WETH/feeToken pool price so that the victim's `msg.value` becomes insufficient (reverting and wasting the victim's gas / delaying request submission), or, more importantly, manipulate the pool so that the swap consumes the *entire* `msg.value` for a fee amount the attacker has pre-priced favorably, extracting value from the dispatcher's native tokens via slippage that the dispatcher had no on-chain way to bound beyond the pre-computed `msg.value`.

Unlike `IntentGatewayV2.fillOrder`, where the order's `output.assets` amounts are fixed at order-placement time and enforced (`InvalidInput` if under), and unlike the V3/V4 wrapper contracts which correctly clamp `amountInMaximum` to `msg.value`, the core `EvmHost.dispatch`/`fundRequest` paths rely entirely on the caller pre-computing an off-chain quote and hoping the price hasn't moved by execution time — there is no protocol-level minimum feeToken-out parameter in `DispatchPost`/`DispatchGet`/`fundRequest`'s calldata that the contract itself validates against a tolerance.

### Impact Explanation
This is reachable by any unprivileged account dispatching a POST/GET request or funding a request with native token payment — a core, frequently used entry point (every cross-chain message dispatched with native payment goes through this code path). A sandwiched dispatcher either (a) loses part of the native tokens they sent as excessive slippage is absorbed silently in the swap execution price, or (b) has their transaction revert due to insufficient `amountIn`/output shortfall in a manipulated pool, wasting gas and potentially delaying critical cross-chain messages. Given the systemic and repeated nature of the dispatch path across the protocol, this is a Medium-severity fund-loss vector consistent with the reported bug class (price manipulation due to missing caller-declared minimum/maximum bound in a same-transaction swap).

### Likelihood Explanation
Native-token dispatch is documented as a primary, user-facing payment method (the docs present it as the convenient default for "one-off transactions, user-facing apps") [5](#0-4) , so the vulnerable path sees regular usage. Any MEV searcher monitoring the mempool for `EvmHost.dispatch`/`fundRequest` calls with `msg.value > 0` can attempt a sandwich, since the swapped pair (WETH/feeToken) is a known, low-additional-cost target and the victim's slippage tolerance is implicit and fixed at the moment they queried an off-chain quote, not enforced fresh on-chain.

### Recommendation
Add an explicit, caller-supplied minimum feeToken-out (or maximum native-in with a tolerance band) parameter to `DispatchPost`, `DispatchGet`, and `fundRequest`'s dispatch parameters, and have `EvmHost` validate it on-chain (e.g., via `swapExactETHForTokens` with a real `amountOutMin`, or by asserting the actual `feeToken` amount received meets a caller-specified floor) rather than relying solely on `msg.value` sized from a stale off-chain quote. Alternatively, document and encourage `dispatchWithFeeToken` (the ERC-20 path, which is exact and slippage-free) as the only recommended payment method for programmatic/contract-to-contract dispatches, and gate the native-swap path behind an explicit slippage parameter for direct user calls.

### Proof of Concept
Conceptual scenario (native token dispatch path):
1. Alice (an unprivileged dispatcher) queries `HyperApp.quote(DispatchPost)` off-chain, which returns a native amount `X` based on the current WETH/feeToken pool ratio via `getAmountsIn` [6](#0-5) .
2. Alice submits `EvmHost.dispatch{value: X}(post)` where `post.fee` is the desired feeToken fee amount.
3. A searcher observes the pending transaction, front-runs it with a large swap that shifts the WETH/feeToken pool price against Alice, then back-runs after her transaction executes (or lets it revert if `X` is now insufficient to buy `post.fee` worth of feeToken via `swapETHForExactTokens`) [1](#0-0) .
4. Alice's transaction either reverts (wasting gas and delaying dispatch) or, if `X` still barely covers the manipulated price, all of her `msg.value` is consumed for `post.fee` worth of tokens at an inflated implied rate, with the sandwicher pocketing the price impact — the same "no minimum/maximum guard against price manipulation" root cause identified in the external report for `SwapperImpl.flash`.

I was unable to fully verify whether `_hostParams.uniswapV2` pools used by `EvmHost` are low-liquidity enough in production deployments to make this practically profitable for an attacker — that would require on-chain liquidity data not available in this index, so likelihood should be validated against actual deployed pool depths.

        if (msg.value > 0) {
            address[] memory path = new address[](2);
