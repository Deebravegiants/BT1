### Title
Webhook `shop-domain` is taken from an unauthenticated header while the HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that covers only the raw request body, then dispatches the event to the app's handler using a `shop` value read from the `X-Shopify-Shop-Domain` header, which is never included in the signed bytes. Because the app's `api_secret_key` is shared across every shop that installs the app, anyone who can get one legitimately-signed webhook (e.g. by installing the app on their own store and triggering an event) can replay that exact body+HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will accept it as if it came from that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight from an attacker-controllable HTTP header with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`, i.e. the raw body, and never incorporates `shop`: [3](#0-2) 

`Registry.process` accepts the request once that body-only HMAC checks out, and then forwards `request.shop` (the unauthenticated header) directly into the dispatched `WebhookMetadata`, with no secondary check that the header shop actually produced that body: [4](#0-3) 

This is the same bug class as the `utilizationRate` report: a check is supposed to bind two quantities (here, "this body was really sent for this shop") but the formula/verification omits one side of that equality (`shop`) from what's actually verified (only `raw_body` is verified). The equality that should hold is:

`HMAC_valid(raw_body) ⇒ shop_header == shop_that_generated(raw_body)`

but the implementation only proves `HMAC_valid(raw_body)`, and `shop_header` is asserted, not verified.

### Impact Explanation
Because `Context.api_secret_key` is a single app-wide secret (not per-shop), any user who can install the app on their own store — a normal, unprivileged action available to any merchant/developer — can obtain a validly-HMAC'd webhook body for their own shop. They can then replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while setting `X-Shopify-Shop-Domain` to a victim shop that also uses the app. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. Any app logic that uses `data.shop` to select which merchant's session/store/data to update, delete, or reveal (a common pattern) can be manipulated cross-tenant — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
No access token, `api_secret_key`, or privileged account is required beyond what any developer/merchant can obtain by installing the app on a store they control (or from a webhook they can trigger for their own shop). The webhook HTTP endpoint is public by design. The only requirement is capturing/replaying one legitimately-signed webhook body for an event type the app also processes for other shops.

### Recommendation
Bind `shop` (and any other identifying header used for authorization decisions) into the signed material, or independently verify the header-derived shop against data intrinsic to the verified body/session before trusting it, e.g. include the shop domain in the HMAC computation or require it to be looked up via a pre-registered, per-shop webhook secret/session rather than trusted from the header. At minimum, `Registry.process` should not treat `request.shop` as authenticated purely because the (unrelated) body HMAC passed.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook event (e.g. `orders/create`), capturing the raw POST: headers `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, and the raw JSON body.
2. Attacker POSTs the identical raw body and identical `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint again, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) raw body using the shared `api_secret_key` and it matches, per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-200) accepts the request and calls the app's handler with `shop: "victim.myshopify.com"`, even though the payload was actually generated for `attacker.myshopify.com`.
