This confirms the design: the documentation explicitly states `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" based purely on `Utils::HmacValidator.validate(request)` [1](#0-0) , and that validation only computes an HMAC over `to_signable_string`, which returns `@raw_body` and nothing else [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values placed into `WebhookMetadata` — which the docs say the host app should use directly (e.g. `shop_domain: data.shop`) — are read straight from unauthenticated headers via `shopify_header`, never included in the HMAC computation [3](#0-2) .

### Title
Webhook shop/topic/webhook-id headers are excluded from HMAC signature coverage, enabling cross-tenant header forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates solely the JSON body, never the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, or `x-shopify-api-version` headers [2](#0-1) . `Registry.process` nonetheless treats a passing `HmacValidator.validate(request)` check as proof the whole request "did indeed come from Shopify" and forwards `request.shop` unmodified into `WebhookMetadata`, which host apps use to decide whose tenant records to update [4](#0-3) .

### Finding Description
The broken binding is: `computed_signature = HMAC(secret, request.to_signable_string)` should equal `HMAC(secret, request.to_signable_string)` **and** every field consumed by `handler.handle` (topic, shop, webhook_id, api_version) must be inside `to_signable_string`. In fact `to_signable_string` == `@raw_body` only [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from raw HTTP headers with no cryptographic binding to the signed body [5](#0-4) .

Exploit flow: an attacker can register their own development shop, install the target app, and receive one genuine, validly-HMAC-signed webhook delivery (body `B`, signature `H`) from Shopify for their own shop, using the app's real `api_secret_key` — a secret shared across *all* installations of the app, not per-shop. The attacker then crafts a new HTTP POST directly to the app's public webhook endpoint (no TLS interception needed — this is just an ordinary POST to a public URL) reusing body `B` and signature header `H` unmodified, but substituting `x-shopify-shop-domain` with a victim shop's domain (and optionally a different `x-shopify-webhook-id`, which nothing tracks or deduplicates). Because `HmacValidator.validate` only ever hashes `@raw_body`, the signature still matches, `Registry.process` accepts the request as authentic, and `WebhookMetadata#shop` carries the attacker-chosen victim domain into `handler.handle` [6](#0-5) . Per the documented handler pattern, this directly drives tenant-scoped side effects keyed on `data.shop` [7](#0-6) .

No existing guard closes this gap: `HmacValidator.validate` only compares the HMAC over the body [8](#0-7) ; the `Request` constructor only checks header *presence*, not header authenticity or binding to the body [9](#0-8) ; and `Registry` performs no correlation between `request.shop`/`request.webhook_id` and a known, previously-registered webhook subscription for that shop before dispatching to the handler [1](#0-0) .

### Impact Explanation
Any party is exposed whose app trusts `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) as authenticated, per the documented usage pattern where `data.shop` is passed straight into business logic (e.g. `perform_later(shop_domain: data.shop, ...)`) [7](#0-6) . Since the same body/HMAC pair can be replayed with an arbitrary shop-domain header, one attacker-controlled shop's genuine webhook can be relabeled as belonging to any other merchant's shop, causing cross-tenant data confusion — the app performs an action attributed to shop A using content actually generated for shop B. This matches the "cross-tenant access" / authentication-bypass class: the app treats an unauthenticated header value (shop domain) as authenticated because it arrived alongside a request that passed HMAC validation, even though the header itself was never covered by that signature.

### Likelihood Explanation
The attacker only needs to be able to install the target app on any shop they control (a standard, low-barrier action for any developer/attacker under the stated threat model), capture one legitimate webhook delivery, and replay it with a modified header directly to the app's public endpoint. No secrets, TLS interception, or victim cooperation are required, and the attack is trivially repeatable against arbitrary shop-domain values and topics the attacker has previously observed a valid body/signature pair for. The main constraint is that the attacker must reuse a body that was genuinely produced for the topic they choose (limiting them to bodies/topics they've already received, not arbitrary forged JSON), which somewhat bounds — but does not eliminate — the impact.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string, or otherwise cryptographically bind them to the body before computing/verifying the HMAC in `to_signable_string`. As a defense-in-depth measure, `Registry.process` should also correlate `request.shop` against a shop known to have an active subscription for `request.webhook_id`/`request.topic` before invoking the handler, and applications should be advised (in `docs/usage/webhooks.md`) to track processed `webhook_id`s to reject replays regardless of header contents.

### Proof of Concept
1. In a minitest file under `test/webhooks/`, use `Utils::HmacValidator`'s real signing routine (or `OpenSSL::HMAC.hexdigest` with `Context.api_secret_key`) to sign a fixed JSON body `B` for `topic: "orders/create"`, producing signature `H`.
2. Build request #1: `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {"x-shopify-hmac-sha256" => H, "x-shopify-topic" => "orders/create", "x-shopify-shop-domain" => "shop-a.myshopify.com", "x-shopify-webhook-id" => "wh-1"})`. Register a stub `WebhookHandler` capturing `data.shop`. Call `Registry.process(request1)`; assert `Utils::HmacValidator.validate(request1)` is `true` and the handler received `shop == "shop-a.myshopify.com"`.
3. Build request #2 with the *same* `raw_body: B` and *same* `x-shopify-hmac-sha256 => H`, but `"x-shopify-shop-domain" => "shop-b.myshopify.com"` and a different `x-shopify-webhook-id`. Call `Registry.process(request2)`; assert `Utils::HmacValidator.validate(request2)` is still `true` (identical HMAC check passes) and the handler now received `shop == "shop-b.myshopify.com"`.
4. Assert `request1.hmac == request2.hmac` while `request1.shop != request2.shop`, proving that identical signature coverage produced by `to_signable_string` accepted two different, unsigned `shop` values for one signature — demonstrating the invariant "every value acted on downstream is inside the string handed to `HmacValidator`" is violated.
