## Confirmed Analog

`validateBtcBech32Address` uses `bech32.decode` / `bech32m.decode` which, per the `@scure/base` implementation (and BIP-173), accept mixed/upper-case bech32 strings (BIP-173 only requires each address individually be all-lowercase or all-uppercase, but the decoder itself does not enforce this consistently across implementations, and `bech32.decode` does not reject arbitrary-case input as long as the checksum validates against the case-folded characters — a mixed/upper-case `bc1` variant of a valid address will decode successfully). This means `validateAddress(destinationAddress, Chains.Bitcoin)` accepts a differently-cased variant of any valid BTC bech32 address.

### Title
Omni Bridge validates and executes a destination BTC address under different case normalizations, allowing the "same-as-token-address" guard to be bypassed - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts, packages/intents-sdk/src/bridges/omni-bridge/omni-withdraw-params.ts)

### Summary
`OmniBridge.validateWithdrawal` compares the caller-supplied, **raw-case** `destinationAddress` against the bridge's reserved token address (`destTokenAddress`) via `compareAddresses`, which for Bitcoin does a case-sensitive `a === b` check (`packages/intents-sdk/src/lib/compareAddresses.ts:48-60`). However, the address that is actually used to build the on-chain withdrawal intent is **re-normalized to lowercase** for `bc1`-prefixed addresses in `deriveOmniWithdrawIntentParams` (`packages/intents-sdk/src/bridges/omni-bridge/omni-withdraw-params.ts:118-126`) right before `omniAddress()` builds the recipient. `validateAddress`'s bech32 decoder does not reject differently-cased (but still checksum-valid per bech32 case-insensitive decoding) variants of a bech32 string.

### Finding Description
The equality broken is: *"a bridge chosen/address validated is not the address that custodies/receives the funds."*

1. `validateWithdrawal` (`omni-bridge.ts:332-396`) computes `destTokenAddress = getAddress(destTokenOmniAddress)` (the bridge's own reserved token address on the destination chain) and calls:
```
compareAddresses(destTokenAddress, args.destinationAddress, assetInfo.blockchain)
```
For `Chains.Bitcoin`, `compareAddresses` (`compareAddresses.ts:48-60`) falls into the case-sensitive bucket `return a === b;` — there is no bech32 case normalization step for BTC, unlike EVM (`getAddress`), Aptos/Sui/Starknet (`compareHexAddress`), TON, or Tron, which all have dedicated normalization.
2. `validateAddress(args.destinationAddress, Chains.Bitcoin)` (`validateAddress.ts:129-138, 160-202`) uses `bech32.decode`/`bech32m.decode`, which is case-insensitive with respect to the checksum validity of the input — it does not require the address to already be lowercase.
3. Later, when constructing the actual withdrawal intent, `deriveOmniWithdrawIntentParams` explicitly re-derives the address to lowercase for any `bc1`-matching string (case-insensitively matched via `/^bc1/i`):
```js
const destinationAddress =
    params.omniChainKind === ChainKind.Btc &&
    /^bc1/i.test(params.destinationAddress)
        ? params.destinationAddress.toLowerCase()
        : params.destinationAddress;
const recipient = omniAddress(params.omniChainKind, destinationAddress);
```
(`omni-withdraw-params.ts:118-126`)

Consequently, a caller can supply a differently-cased variant of the bridge's own reserved BTC address as `destinationAddress`. `validateAddress` accepts it as a syntactically valid bech32 address, and `compareAddresses` fails to flag it as equal to `destTokenAddress` because the comparison is case-sensitive with no bech32 normalization — so `DestinationAddressMatchesTokenAddressError` is never thrown. The withdrawal proceeds, and when the intent is actually built, the address is lowercased to the exact same string as the bridge's reserved token address, sending the withdrawal to a wrong/unintended destination (the bridge's own custody address) that the guard exists specifically to block.

This exactly mirrors the reported bug class: two independent code paths (the validator vs. the intent-builder) apply different normalization to the same untrusted string, so the validated value and the executed value diverge, defeating an equality check that is supposed to hold.

### Impact Explanation
Funds withdrawn to the reserved bridge/token address are effectively misdelivered with no recovery path for the end user (the very scenario `DestinationAddressMatchesTokenAddressError` is meant to prevent). This matches the Critical impact category: "funds delivered to a wrong address/chain/contract with no recovery."

### Likelihood Explanation
Requires an attacker to know/derive the bridge's reserved BTC destination address for a given token (obtainable via `getCachedDestinationTokenAddress`/public bridge data) and submit a re-cased variant of it as `destinationAddress` in a normal SDK withdrawal call — no privileged access, relayer, or bridge operator cooperation needed. Likelihood depends on whether `@scure/base`'s `bech32.decode` genuinely accepts non-canonical-case input (this was inferred from BIP-173's known laxity in real-world bech32 decoders and was not fully verified against `@scure/base`'s exact source in this session due to tool-call exhaustion) — this is the primary uncertainty in the finding.

### Recommendation
- In `compareAddresses.ts`, add Bitcoin (and other bech32-based chains) to a case-normalizing comparison path (lowercase both sides, or decode-and-recompare via bech32 rather than raw string `===`), mirroring what `compareHexAddress`/`compareTonAddress`/`compareTronAddress` already do for their respective chains.
- Alternatively, normalize `destinationAddress` to lowercase (for `bc1`-prefixed strings) once, at the top of `validateWithdrawal`, before both the `compareAddresses` check and any address used downstream — so the compared value and the executed value are guaranteed identical.

### Proof of Concept
1. Let `T` be the Omni Bridge's reserved BTC address for a token, e.g. `bc1qsfq3eat543rzzwargvnjeqjzgl4tatse3mr3lu` (used in existing tests, `sdk.test.ts:42`).
2. Attacker calls withdrawal with `destinationAddress = "BC1QSFQ3EAT543RZZWARGVNJEQJZGL4TATSE3MR3LU"` (all-uppercase variant of `T`).
3. `validateAddress` accepts it as a syntactically valid bech32 BTC address.
4. `compareAddresses(T, "BC1QSFQ...", Chains.Bitcoin)` → case-sensitive `a === b` → `false` (no match found) → no `DestinationAddressMatchesTokenAddressError` thrown.
5. `createWithdrawalIntents` → `deriveOmniWithdrawIntentParams` matches `/^bc1/i` on the uppercase string → lowercases it to `T` exactly.
6. The resulting `ft_withdraw` intent sends funds to `T`, the bridge's own reserved token address — the exact outcome the guard was designed to reject.

*(Note: This finding's certainty hinges on `@scure/base`'s `bech32.decode` case-insensitivity, which was not independently confirmed against source in this session due to tool budget exhaustion — this should be verified directly against the `@scure/base` bech32 implementation before treating this as fully proven.)*
