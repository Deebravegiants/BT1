## Analysis

The reported bug class — an abstract base contract with storage variables but no `__gap`, extended by other contracts, making future upgrades unsafe — has a direct analog in `IntentGatewayV2`'s upgrade architecture.

`IntentsBase` is an abstract contract holding all shared storage for the intents system (`_filled`, `_nonce`, `_params`, `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, `_relayer`), but it declares no storage gap at the end of its variable list. [1](#0-0) 

It sits in a diamond inheritance chain — `IntentsBase` → `IntrinsicIntents`/`ExtrinsicIntents` → `IntentGatewayV2` — and `IntentGatewayV2` is the concrete contract deployed behind an ERC1967 (UUPS) proxy and upgraded in production. [2](#0-1) 

The upgrade path is reachable from a single relayed governance message: a Hyperbridge `PostRequest` with `RequestKind.Execute` is delegatecalled by `onAccept` into `upgradeToAndCall`, changing the ERC-1967 implementation slot while preserving all existing storage. [3](#0-2) [4](#0-3) 

The team's own decision records confirm this is an already-fragile, manually-managed layout rather than a compiler-enforced one: `_paused` and `_relayer` had to be "appended last to preserve existing storage slots" by hand, and a new field could not be added to the `Params` struct because it "would push every mapping behind it and corrupt escrow on the live proxy." [5](#0-4) 

By contrast, `SimplexPaymaster` — the codebase's other governance-upgradable contract — does reserve an explicit `uint256[48] private __gap` before its own state, showing the team is aware of the gap pattern but did not apply it to `IntentsBase`. [6](#0-5) 

Because `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` have no gap, any future upgrade that needs to add storage anywhere in this multi-contract abstract chain (rather than strictly appended at the very end of the concrete `IntentGatewayV2`) will shift the storage slots of every mapping/struct declared after it — corrupting `_orders` (escrow balances) and `_filled` (fill/cancel state) — since `_filled` is even pinned to a hard-coded slot (`FILLED_SLOT_BIG_ENDIAN_BYTES = slot 2`) used for cross-chain storage proofs. [7](#0-6) 

### Title
Missing storage gaps in `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` make the upgradeable `IntentGatewayV2` proxy unsafe to extend - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase`, the abstract base holding all `IntentGatewayV2` escrow/order storage, and its siblings `IntrinsicIntents`/`ExtrinsicIntents`, declare no `__gap` reserved storage slots, unlike `SimplexPaymaster` which does. `IntentGatewayV2` is deployed behind an ERC-1967 proxy and upgraded live via a Hyperbridge-relayed `Execute`/`upgradeToAndCall` request, so any new state variable added to one of these base contracts in a future implementation — instead of strictly at the tail of the final concrete contract — silently shifts every mapping/struct slot declared after it in derived contracts.

### Finding Description
`IntentsBase` declares `_filled`, `_nonce`, `_params`, `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, and `_relayer` with no trailing gap. [8](#0-7) 
`IntentGatewayV2` inherits from `IntrinsicIntents` and `ExtrinsicIntents`, both of which extend `IntentsBase`, and is itself `Initializable`/UUPS-upgradeable, deployed via `ERC1967Proxy`. [9](#0-8) 
The upgrade is delivered through `onAccept`'s `Execute` discriminator, which delegatecalls `upgradeToAndCall`/`setRelayer` with `msg.sender` still the host — a legitimate, relayer-gated but code-level-unprotected path for changing the implementation while storage persists. [10](#0-9) 
The team's own documented history shows this has already caused real constraints: appending `_paused`/`_relayer` had to be done "to preserve existing storage slots," and a `Params` struct field could not be added because it "would push every mapping behind it and corrupt escrow on the live proxy" — precisely the class of bug a `__gap` is designed to prevent. [5](#0-4) 
`_filled`'s slot is additionally hard-pinned into cross-chain proof verification (`FILLED_SLOT_BIG_ENDIAN_BYTES`), so any accidental slot shift from an ungapped upgrade would also break the cross-chain cancel-proof mechanism, not just local reads. [7](#0-6) 

### Impact Explanation
A future upgrade to `IntentGatewayV2` that adds a state variable anywhere in the `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` hierarchy (rather than only appending after all existing fields in the final concrete contract) shifts every mapping/struct slot declared after that point. Since `_orders` holds escrowed user/solver funds and `_filled`/`_partialFills` gate double-spend/double-fill protection, a slot shift corrupts live escrow accounting on an already-deployed proxy — able to permanently freeze or misdirect escrowed funds, and to break the fixed-slot cross-chain fill/cancel proof path tied to `_filled`.

### Likelihood Explanation
This is not a hypothetical: the project has already had to work around the absence of a gap twice (documented in the `_paused` and `_relayer` decision records), each time by manually verifying slot positions rather than relying on a compiler-enforced reservation. Given `IntentGatewayV2` is an actively upgraded (UUPS) production contract reachable by a single relayer-delivered `Execute` request, any subsequent legitimate feature upgrade that needs new base-contract state carries real risk of an unintentional storage collision, exactly the "not fully upgradable" scenario in the referenced report.

### Recommendation
Add an explicit `uint256[N] private __gap;` at the end of `IntentsBase` (and consider one in `IntrinsicIntents`/`ExtrinsicIntents` if they are expected to carry state independently in the future), mirroring the pattern already used in `SimplexPaymaster`. This reserves headroom so new storage variables can be inserted into the base abstract contracts without shifting the escrow-critical mappings/structs declared in subclasses, removing the need for the fragile "append-only, verify-by-hand" process currently documented in the decision records.

### Proof of Concept
1. `IntentGatewayV2` is deployed behind `ERC1967Proxy` with storage owned by `IntentsBase` (slots 0–13ish: `_filled` at slot 2, `_nonce`, `_params` slots 4–8, `_orders` at slot 9, etc.), as verified by the test asserting `_filled` occupies slot 2. [11](#0-10) 
2. Governance issues an `Execute` request through `onAccept`, delegatecalling `upgradeToAndCall` to a new implementation — the exact production upgrade mechanism. [4](#0-3) 
3. If that new implementation's `IntentsBase` (or `IntrinsicIntents`/`ExtrinsicIntents`) adds a new field anywhere other than strictly after `_relayer` — natural when a developer edits the "logical" location in an abstract base rather than the tail of the diamond — every mapping declared afterward (`_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`) is silently reinterpreted at a shifted slot, corrupting live escrow balances and fill records without any revert, and desynchronizing the hard-coded `FILLED_SLOT_BIG_ENDIAN_BYTES` proof path used for cross-chain cancellation.

 * This is the concrete entry-point contract that composes all intent logic via inheritance:
 *
 *            EIP712
 *              |
 *          IntentsBase
 *           /       \
 *  IntrinsicIntents  ExtrinsicIntents
 *           \       /
 *        IntentGatewayV2

contract IntentGatewayV2 is IntrinsicIntents, ExtrinsicIntents, ReentrancyGuardTransient, Initializable {
    using SafeERC20 for IERC20;

    /// @dev Privileged admin for future upgrade-gated actions (e.g. pausing). Immutable, so it must
    /// be identical across chains or the deterministic proxy address diverges. Does not gate
    /// `initialize`; atomic CREATE2 deployment already binds the init data to the canonical address.
    address public immutable _owner;

    /// @dev Sets the EIP-712 domain ("IntentGateway", "2"), records the admin, and locks this raw
    /// implementation against direct initialization.
    /// @param owner The privileged admin address.
    constructor(address owner) EIP712("IntentGateway", "2") {
        if (owner == address(0)) revert InvalidInput();
        _owner = owner;
        _disableInitializers();
    }

# 2026-09-03 — The relayer is a separate storage variable, not a `Params` field

Chosen: `address _relayer` appended after `_paused` in `IntentsBase`, set through its own
`setRelayer` call.

`Params` occupies slots 4 to 8 and `_orders` starts at slot 9. Adding a field to the struct would
push every mapping behind it and corrupt escrow on the live proxy. Reusing `UpdateParams` was
therefore never available, quite apart from it being a Hyperbridge-relayed message: the whole point
is to hold even if Hyperbridge's consensus is compromised, so the setter must not depend on it.
