### Title
Operator QR-code authorization validity is judged against a freshly-fetched expiration policy instead of the policy in effect when the checkpoint timestamp was recorded - (File: src/plans/mod.rs)

### Summary
`MasterPlan::run` caches `operator_qr_expiration_time` once from `orb.config.lock().await` at the start of the outer signup loop and uses that stale value to gate `scan_initial_qr_codes`/`idle_wait_for_signup_request`, while `do_signup` independently re-fetches a **fresh** copy of the same config field and uses it to evaluate `operator_data.timestamp.elapsed() < operator_qr_expiration_time` in `scan_remaining_qr_codes`. Because the checkpoint (`operator_data.timestamp`, set once when the operator QR-code was scanned) is never re-validated against the policy value that was active at scan-time, a backend config update to `operator_qr_expiration_time` that happens after the QR was scanned but before the signup proceeds gets applied retroactively to the already-elapsed window, exactly mirroring the reported bug class where a policy change is misapplied over a period during which a different policy was actually in force.

### Finding Description
The `operator_qr_expiration_time` "checkpoint + policy" pattern is structurally identical to the Vault `feesUpdatedAt`/`accruedManagementFee()` pattern: a timestamp is recorded once (`OperatorData::timestamp`, `Instant::now()` set in `scan_initial_qr_codes`/`scan_remaining_qr_codes`) [1](#0-0) , and elapsed time from that checkpoint is later compared against a currently-configured duration to decide whether the authorization ("operator has scanned a valid QR within the allowed window") is still valid [2](#0-1) .

The policy value used for that comparison is not read consistently:
- `MasterPlan::run` reads `operator_qr_expiration_time` a single time from the shared, mutable `orb.config` and holds it for the lifetime of the outer loop, passing it into `scan_initial_qr_codes` and `idle_wait_for_signup_request` [3](#0-2) .
- `do_signup` independently re-reads the same field fresh from `orb.config.lock().await` right before calling `scan_remaining_qr_codes` [4](#0-3) .

`orb.config` is updated asynchronously and repeatedly from the backend config endpoint (`backend::config`), whose response also carries a `last_updated` field that is never consulted to reconcile timing [5](#0-4) . Because the check in `scan_remaining_qr_codes` re-evaluates `operator_data.timestamp.elapsed() < operator_qr_expiration_time` using whatever value happens to be current at call time [6](#0-5) , an operator QR checkpoint recorded while a shorter expiration policy was in effect is validated against a newer, longer expiration policy fetched later in the same signup — the new policy is applied backward over the interval that already elapsed under the old policy, instead of only governing time going forward from the moment the policy changed.

### Impact Explanation
This allows an operator (or a stale-but-not-yet-timed-out) QR-code authorization to remain accepted by the orb well past the expiration window that was actually enforced at scan time, without the operator ID being re-verified through `verify_operator_qr_code` [7](#0-6) . Since the operator QR-code establishes the trusted location/identity context that is bound into the signup (`OperatorData` is carried through to `ResolvedQrCodes` and downstream user QR-code validation which uses operator location data) [8](#0-7) , extending the validity window retroactively can allow a signup to proceed under operator authorization that should already have expired and required re-scanning, weakening the intended freshness/liveness guarantee of the operator identity binding for that signup.

### Likelihood Explanation
This requires no attacker privilege on the orb itself — it only requires that `orb.config` be updated (a routine, backend-driven, periodic occurrence) between the time the operator QR-code is scanned and the time `do_signup` re-reads the config, which is entirely plausible for long idle periods between `scan_initial_qr_codes` and an eventual signup, especially in non-self-serve flows where the operator scan happens once per idle loop and signups can begin much later.

### Recommendation
Snapshot `operator_qr_expiration_time` (and any other policy fields used to judge a timestamp checkpoint) once, at the same moment the checkpoint itself is captured, and carry that snapshot alongside `OperatorData` for all subsequent validity checks — rather than re-reading the live config value at each check site. This ensures the expiration policy that applies to a given checkpoint is the one that was in effect when the checkpoint was created, consistent with the fix recommended for the analogous Vault bug (checkpoint the parameter together with the timestamp, so later re-evaluations cannot retroactively apply a changed policy to already-elapsed time).

### Proof of Concept
1. Orb is idle; `MasterPlan::run` loads `operator_qr_expiration_time = T1` (e.g. a short duration) at line 334 and passes it to `scan_initial_qr_codes`.
2. Operator scans QR-code; `OperatorData.timestamp = Instant::now()` is recorded (line 779).
3. Before the user proceeds to `do_signup`, the backend management config is updated so that `operator_qr_expiration_time` becomes `T2 >> T1`.
4. `do_signup` re-reads config and obtains `T2` (line 504), then calls `scan_remaining_qr_codes`, which checks `operator_data.timestamp.elapsed() < T2` (line 797/807) — now true even though `elapsed() > T1`, i.e., the operator authorization would have already expired under the policy active at scan time.
5. The signup proceeds using the stale operator authorization without a fresh operator QR re-scan/re-verification.
