### Title
Case-variant bech32m Aleo addresses bypass `compareAddresses` self-send check, letting funds be routed to the token's own address - ([File: packages/intents-sdk/src/lib/compareAddresses.ts])

### Summary
`compareAddresses` uses raw string equality (`a === b`) for `Chains.Aleo`, but Aleo addresses are bech32m-encoded (per BIP-173-style rules used elsewhere in this codebase), which permits an all-uppercase encoding of the exact same underlying bytes in addition to the canonical lowercase form. `validateAddress`/`validateAleoAddress` accepts both case variants as valid, so an attacker can submit an uppercase mirror of the token's own Aleo address as `destinationAddress`, causing `compareAddresses(tokenOriginAddress, destinationAddress, Chains.Aleo)` to return `false` even though both strings decode to the identical Aleo public key, bypassing `DestinationAddressMatchesTokenAddressError` in `PoaBridge.validateWithdrawal`.

### Finding Description
The broken equality is: `tokenOriginAddress` (Aleo, canonical case) vs. `destinationAddress` (Aleo, attacker-chosen case) — they should be considered equal because they decode to the same 32-byte Aleo group element, but `compareAddresses` treats them as different because it falls into the `a === b` branch for `Chains.Aleo`/`Chains.Dash`: [1](#0-0) 

Meanwhile `validateAleoAddress` decodes the address via `bech32m.decodeToBytes`, which — consistent with the bech32/bech32m spec and with this codebase's own explicit handling of mixed-vs-uppercase bech32 for Litecoin/Bitcoin (`validateLitecoinBech32Address`/`validateBtcBech32Address` only reject *mixed*-case, not all-uppercase) — accepts an all-uppercase encoding of the same payload as valid: [2](#0-1) 

This is the same class of encoding ambiguity the codebase already handles for other bech32-style/multi-encoding chains — TON (`compareTonAddress`), Tron (`compareTronAddress`), and the hex-based chains (`compareHexAddress`) — but the developers evidently assumed Aleo/Dash need only raw comparison, grouping them with genuinely case-sensitive/single-encoding chains like Near, Bitcoin, Solana, and XRPL. That assumption is incorrect for Aleo because bech32m is case-insensitive at the encoding level (uppercase-only re-encodings are valid per spec and per this repo's own bech32 decoders).

Exploit flow: an unprivileged NEAR Intents user requests a PoA Aleo withdrawal of a token whose `tokenAccountId`/custodial address is `aleo1abc...xyz`. They set `destinationAddress` to `ALEO1ABC...XYZ` (uppercase re-encoding of the identical bytes). `validateAddress(destinationAddress, Chains.Aleo)` returns `true` (valid format). `compareAddresses(tokenOriginAddress, destinationAddress, Chains.Aleo)` returns `false` because the strings differ by case, so `DestinationAddressMatchesTokenAddressError` is never thrown, and the withdrawal proceeds to send funds to the token's own custodial address — the exact self-send scenario the check exists to block.

Dash, by contrast, is base58check — base58 encoding is deterministic/injective for a given byte payload and case-sensitive in its alphabet, so there is no equivalent "different string, same bytes" collision for Dash; that half of the question's premise does not hold.

### Impact Explanation
Funds get misrouted to the token's own custodial Aleo address instead of a real recipient, with no automated recovery path — this is a self-send that the `DestinationAddressMatchesTokenAddressError` guard is specifically designed to prevent. This matches the Critical category: "funds delivered to a wrong address/chain/contract with no recovery." The bug is repeatable on every PoA Aleo withdrawal for any attacker (or careless integrator forwarding a case-varied address) and affects the caller's own funds being stranded at the bridge.

### Likelihood Explanation
Preconditions: a PoA bridge route for an Aleo-denominated token. Attacker cost: trivial — simply uppercase the known token address string (bech32m guarantees this remains a validly-decodable address referring to the same underlying point). No special privileges, timing, or race conditions required; it is deterministic and repeatable on every call.

### Recommendation
Normalize Aleo addresses before comparison, e.g. decode both sides with `bech32m.decodeToBytes` (as `validateAleoAddress` already does) and compare the decoded byte payloads (and prefix), analogous to `compareTonAddress`/`compareHexAddress`, instead of relying on raw string equality. Add `Chains.Aleo` to a dedicated comparison branch rather than grouping it with genuinely single-encoding, case-sensitive chains.

### Proof of Concept
```ts
import { bech32m } from "@scure/base";
import { describe, expect, it } from "vitest";
import { Chains } from "./caip2";
import { compareAddresses } from "./compareAddresses";
import { validateAddress } from "./validateAddress";

describe("Aleo case-variant bypass", () => {
  const lower = "aleo1dg722m22fzpz6xjdrvl9tzu5t68zmypj5p74khlqcac0gvednygqxaax0j";
  const upper = lower.toUpperCase();

  it("both case variants are valid Aleo addresses (same underlying bytes)", () => {
    expect(validateAddress(lower, Chains.Aleo)).toBe(true);
    expect(validateAddress(upper, Chains.Aleo)).toBe(true);
    const a = bech32m.decodeToBytes(lower);
    const b = bech32m.decodeToBytes(upper);
    expect(a.bytes).toEqual(b.bytes); // identical underlying key
  });

  it("compareAddresses incorrectly treats them as different (self-send bypass)", () => {
    // Should be true (same underlying address) but returns false, letting
    // DestinationAddressMatchesTokenAddressError be skipped in PoaBridge.validateWithdrawal
    expect(compareAddresses(lower, upper, Chains.Aleo)).toBe(false);
  });
});
```

```typescript
export function validateAleoAddress(address: string): boolean {
	try {
		const decoded = bech32m.decodeToBytes(address);
		if (decoded.prefix !== "aleo") return false;
		if (decoded.bytes.length !== 32) return false;

		// Extract x-coordinate, clearing the y-sign flag (MSB of last byte)
		const bytes = new Uint8Array(decoded.bytes);
		bytes[31] = (bytes[31] as number) & 0x7f;

		let x = 0n;
		for (let i = 31; i >= 0; i--) {
			x = (x << 8n) | BigInt(bytes[i] as number);
		}
		if (x >= P) return false;

		// y² = (1 + x²) / (1 - d·x²)  (equivalent to Rust: (a·x²-1)/(d·x²-1) with a=-1)
		const x2 = (x * x) % P;
		const num = (1n + x2) % P;
		const den = (((1n - ((D * x2) % P)) % P) + P) % P;
		if (den === 0n) return false;

		const denInv = modPow(den, P - 2n, P);
		const y2 = (num * denInv) % P;

		// Decompress: recover y via square root
		const y = modSqrt(y2);
		if (y === null) return false;

		// snarkVM checks both (x, y) and (x, -y) for subgroup membership
		const negY = y === 0n ? 0n : P - y;
		const p1: ExtPoint = [x, y, (x * y) % P, 1n];
		const p2: ExtPoint = [x, negY, (x * negY) % P, 1n];

		for (const pt of [p1, p2]) {
			if (isIdentity(scalarMul(pt, SUBGROUP_ORDER))) return true;
		}
		return false;
	} catch {
		return false;
	}
}
```
