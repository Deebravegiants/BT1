### Title
Webhook HMAC Validation Excludes `shop-domain`/`topic` Headers, Enabling Cross-Tenant Webhook Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read directly and unauthenticated from HTTP headers [2](#0-1) . `Registry.process` verifies only that the body's HMAC matches, then dispatches the handler using the header-derived (unsigned) `shop` value [3](#0-2) . Because the app's `api_secret_key` is shared across all shops that install the app (not shop-specific), a genuine webhook body+HMAC pair legitimately received for one shop can be replayed with a forged `shop-domain` header, and the HMAC check will still pass.

### Finding Description
This is the analog to the report's core bug class: "a field acted on but not covered by the HMAC." In the oracle report, the attacker exploits data that is validated (signature freshness) but not bound to the operation it authorizes (ordering/timestamp). Here, the identity binding broken is:

`shop asserted in header == shop the HMAC signature actually authenticates`

which should hold but does not, because:
- `HmacValidator.validate` computes/compares HMAC solely over `to_signable_string`, i.e., the raw body [4](#0-3) .
- `to_signable_string` for a webhook `Request` is just `@raw_body`, excluding `shop-domain` header entirely [1](#0-0) .
- `Registry.process` trusts `request.shop` (from headers) to build the `WebhookMetadata` handed to the app's business logic [5](#0-4) .

An attacker who legitimately installs the app on their own shop will receive real webhooks (valid body + valid HMAC, since HMAC uses the single shared `api_secret_key`, not a per-shop secret). They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different (victim) shop. `Utils::HmacValidator.validate` still returns `true` because the body and HMAC are unchanged and valid for the shared secret; the forged `shop` header is passed through unchecked to the handler.

### Impact Explanation
This breaks the tenant-identity binding that Shopify apps rely on to route webhook side effects (e.g., updating merchant-specific data, honoring `app/uninstalled`, `shop/redact`, `customers/redact`, billing events) to the correct shop record. Since host applications are expected to trust `WebhookMetadata#shop` as the authenticated tenant identifier (that is the entire purpose of exposing it after HMAC validation), an attacker can attribute attacker-chosen payload content to an arbitrary victim shop, causing cross-tenant data corruption/actions in the host application. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only that the attacker be an installed, unprivileged user of the app on their own shop (no leaked secrets, no privileged account, no TLS interception) — they only need to observe one webhook delivery to their own store, which Shopify sends automatically upon standard app events. Replaying it with a modified header against the app's public webhook endpoint is trivial.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed string (or otherwise cryptographically bind them to the payload) so that any tampering with these headers invalidates the signature. At minimum, the library should not expose an unauthenticated `shop` from `Webhooks::Request` for use as a trusted tenant identifier without documenting this hazard prominently, since `to_signable_string` only covers the body [1](#0-0) .

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., update a product) to receive a real delivery with valid `X-Shopify-Hmac-Sha256` and body `B`.
3. Replay the exact same body `B` and HMAC header to the app's webhook endpoint, replacing `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (called from `Registry.process`) returns `true` because it only checks `B` against the shared `api_secret_key` [6](#0-5) ; the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes attacker-controlled body content as if it originated from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
