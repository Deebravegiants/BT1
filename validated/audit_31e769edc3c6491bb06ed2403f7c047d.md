### Title
Unbounded-depth `RuntimeCall` decode in `pallet-hyper-fungible-token`'s `on_accept` allows relayer-triggered native stack exhaustion - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`hyper-fungible-token`'s `IsmpModule::on_accept` decodes an attacker-controlled `substrate_data.runtime_call` byte blob into `T::RuntimeCall` using the plain `Decode::decode`, with no recursion-depth limit, unlike the sibling `pallet-call-decompressor` which explicitly guards the same class of decode with `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)`.

### Finding Description
In `on_accept`, once a cross-chain `PostRequest` is routed to this pallet and the encoded `Message` carries non-empty `data`, the code decodes `SubstrateCalldata` and then dispatches an inner runtime call: [1](#0-0) [2](#0-1) 

The final decode step, `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)`, uses SCALE's unconstrained `Decode` trait method. Because `RuntimeCall` is a recursive enum (variants such as `Sudo::sudo{ call: Box<RuntimeCall> }`, `Utility::batch{ calls: Vec<RuntimeCall> }`, etc., as demonstrated by the runtime's own `RuntimeCall` composition seen in `parachain/runtimes/nexus/src/lib.rs`), an attacker can encode arbitrarily deep nesting of such calls into `substrate_data.runtime_call` bytes. Decoding this structure recurses once per nesting level with no bound, which can exhaust the node's native call stack and crash/abort the process performing the decode — this is architecturally the same bug class as CVE-2016-9933 (an unchecked, attacker-influenced value/structure driving unbounded recursion until the stack is exhausted).

The codebase has already identified and mitigated this exact bug class elsewhere: `pallet-call-decompressor` explicitly caps decode depth at `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT = 4` for structurally similar `RuntimeCall` decoding, with a regression test (`decompress_stack_exhaustion_poc`) proving a naive `decode`/`decode_all` (without a depth limit) would stack-overflow: [3](#0-2) [4](#0-3) [5](#0-4) 

`pallet-hyper-fungible-token::module::on_accept` was not given the same protection, leaving this second, independently-reachable `RuntimeCall` decode path exposed.

### Impact Explanation
`on_accept` runs as part of normal ISMP message delivery: any relayer can submit a `PostRequest` (proven via a valid consensus/state proof for a registered source contract, per `ContractToAsset` lookup) whose `body` decodes to a `Message` with a crafted `data` field. No privileged role is required — a permissionless message dispatcher/relayer delivering an otherwise-valid cross-chain token transfer message can embed the malicious deeply-nested calldata. If the recursive decode blows the native stack, it can crash the node process handling block execution/import for that extrinsic, which is a denial-of-service against the chain (a validator/collator processing the block panics/aborts), i.e., "a route unable to deliver messages" and worse — potential liveness loss for block production, which is High severity.

### Likelihood Explanation
Likelihood is high on paper (a single crafted extrinsic delivered by any relayer to a chain running `pallet-hyper-fungible-token` with an appropriately mapped `ContractToAsset` entry can trigger it), but this cannot be fully confirmed without also verifying: (1) how `on_accept` is invoked in the message pipeline (dispatcher/router code, which was not able to be pulled fully in this session), and (2) whether SCALE's `Decode` implementation for the runtime's specific `RuntimeCall` enum in this codebase is generated with `#[max_encoded_len]`/mem-tracking wrappers (`DecodeWithMemTracking`) that could impose an implicit bound at the `frame_support`/executive dispatch layer even though the pallet's own call site doesn't. Other locations in the codebase (`modules/pallets/intents-coprocessor/rpc/src/lib.rs`, `parachain/node/src/service.rs`) show `DecodeWithMemTracking` bounds required on `T::RuntimeCall` for extrinsic-level decoding, but `hyper-fungible-token`'s trait bounds (seen in the `impl<T: Config> IsmpModule for Pallet<T>` header) do not include such a bound, and the decode call itself is a manual `T::RuntimeCall::decode(...)`, not routed through frame's transaction pool depth-checked path — suggesting the depth guard used elsewhere is genuinely absent here.

### Recommendation
Apply the same protection used in `pallet-call-decompressor`: replace `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` with `T::RuntimeCall::decode_all_with_depth_limit(MAX_DECODE_DEPTH_LIMIT, &mut &*substrate_data.runtime_call)` (importing `codec::DecodeLimit`), choosing a depth limit appropriate to the runtime calls this module needs to support (mirroring the `call-decompressor`'s reasoning about required nesting depth). Additionally bound the overall size of `substrate_data.runtime_call`/`message.data` before decode to avoid compounding decompression/allocation costs.

### Proof of Concept
Conceptually mirrors the existing `decompress_stack_exhaustion_poc` regression test, but targeting `hyper-fungible-token::on_accept` instead of `call-decompressor::decode_and_execute`:
1. Construct `nested_calls = RuntimeCall::Sudo(pallet_sudo::Call::sudo{ call: Box::new(RuntimeCall::System(frame_system::Call::remark{ remark: vec![] })) })`, then wrap it in `pallet_sudo::Call::sudo` (or another boxed-recursive call) thousands of times, as done in: [6](#0-5) 
2. SCALE-encode `nested_calls` and place the bytes into `SubstrateCalldata.runtime_call`, `signature: None`.
3. ABI-encode this as the `data` field of the token-transfer `Message`, and deliver it as the `body` of a `PostRequest` from a `source`/`from` pair registered in `ContractToAsset`.
4. Have a relayer submit this `PostRequest` with a valid membership proof through the normal ISMP message-handling path so `on_accept` executes `T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)` on the malicious bytes, expecting a native stack overflow instead of a clean decode error — analogous to what `decompress_stack_exhaustion_poc` demonstrates was previously possible before `call-decompressor` added its depth limit.

#[test]
fn decompress_stack_exhaustion_poc() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		use crate::runtime::RuntimeCall;
		use codec::Encode;

		let inner_call = RuntimeCall::System(frame_system::Call::remark { remark: Vec::new() });

		let mut nested_calls =
			RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(inner_call) });

		for _ in 1..1000 {
			nested_calls =
				RuntimeCall::Sudo(pallet_sudo::Call::sudo { call: Box::new(nested_calls) });
		}

		let encoded = nested_calls.encode();
		let mut buffer = vec![0u8; 1000000];
		let compressed = zstd_safe::compress(&mut buffer[..], encoded.as_slice(), 3).unwrap();
		let final_compressed_call = buffer[..compressed].to_vec();

		let res = pallet_call_decompressor::Pallet::<Test>::decompress_call(
			RuntimeOrigin::none(),
			final_compressed_call.to_vec(),
			encoded.len() as u32,
		)
		.err()
		.unwrap();

		assert_eq!(
			res,
			DispatchError::Module(ModuleError {
				index: 10,
				error: [3, 0, 0, 0],
				message: Some("ErrorDecodingCall")
			})
		);
	});
}
