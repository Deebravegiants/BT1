### Title
Webhook HMAC only covers the request body, not the shop-domain header — allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `Utils::HmacValidator` never covers the `X-Shopify-Shop-Domain` (nor `X-Shopify-Topic`, `X-Shopify-Webhook-Id`, `X-Shopify-Api-Version`) headers. `Webhooks::Registry.process` nonetheless trusts `request.shop` (parsed straight from that unauthenticated header) as the tenant identity handed to the app's webhook handler. Anyone who legitimately receives one webhook for a shop they control can replay the exact same body + HMAC to the app's public webhook endpoint while swapping only the shop-domain header, and the gem will accept it as authentic and attribute it to a different tenant.

### Finding Description
`HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it against the `hmac` field using a constant-time comparison: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw request body — none of the Shopify headers participate in the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately builds a `WebhookMetadata` object using `request.shop`, which is read straight from the (unsigned) `shop-domain` header, and hands it to the registered handler as the authoritative tenant identity: [3](#0-2) 

The gem's own documentation instructs host apps to key persistence/enqueue operations off `data.shop`: [4](#0-3) 

The broken identity binding, stated as an equality:
`bytes_verified_by_HMAC (raw_body only) != bytes_relied_on_for_tenant_identity (shop header, topic header, webhook_id header)`

Because the header is not part of the signed material, an attacker who legitimately receives a webhook for **their own** shop (a normal, unprivileged app-installer) can take that valid `(raw_body, X-Shopify-Hmac-Sha256)` pair and re-POST it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds because the signature only ever covered the body, and `Registry.process` will dispatch the (attacker-controlled-domain, attacker's own real body) pair to the handler as if it originated from the victim shop.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce via HMAC verification: the whole purpose of `HmacValidator` on webhook `Request` objects is to let host apps trust the `shop` value without further checks (per the documented usage). Because `shop` is excluded from the signed bytes, a shop-A merchant can inject data that the app will process and store/act on as belonging to shop B — cross-tenant data corruption/confusion in the host application's persistence and any queued jobs keyed by `data.shop`. This satisfies the "cross-tenant access" Critical impact category, since the identity binding (shop authenticated by HMAC vs. shop trusted as the tenant key) is broken entirely within this gem's webhook-processing code path.

### Likelihood Explanation
Likelihood is high for any app that has more than one installed shop (the normal case for a multi-tenant Shopify app): the attacker only needs to be a legitimate merchant using the app on their own store (no secret, no privileged access, no TLS interception) to obtain a valid `(body, hmac)` pair, and the webhook endpoint is a publicly reachable HTTP route by design.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the bytes that are HMAC-verified, or otherwise cryptographically bind them to the body (e.g., by having `to_signable_string` incorporate them, or by requiring host apps to independently verify `request.shop` against a known/authorized shop record before trusting it). At minimum, document prominently that `data.shop` from `WebhookMetadata` is not covered by the HMAC and must be cross-checked against a shop known to have installed the app before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/receives a legitimate webhook, capturing the raw POST body `B` and header `X-Shopify-Hmac-Sha256: H` (valid signature over `B`, computed by Shopify using the app's real secret).
2. Attacker sends a new POST to the app's public webhook route with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...}))`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `request.to_signable_string` (`== B`) and it matches `H`, so validation passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-controlled body content as if it belonged to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
