### Title
Webhook `shop-domain` header is trusted for tenant identity but is excluded from the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the app-supplied `shop-domain` header — completely unauthenticated — to the app's handler as the tenant identifier.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed via `Utils::HmacValidator.validate` only binds the *body bytes* to the app's `client_secret`: [1](#0-0) 

`Registry.process` accepts the request purely on that body-HMAC check, and then reads `request.shop` — which is taken directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, entirely outside the signed payload — and forwards it to the app's `WebhookHandler` as the shop for that event: [2](#0-1) [3](#0-2) 

The identity binding broken here is:
`hmac_signed_bytes(request) == raw_body` **but** `tenant_identity_used_by_handler(request) == header["shop-domain"]`, i.e. the value verified by the HMAC (raw body) is not the same value trusted as the tenant/session key (`shop` header). This is exactly the "field acted on but not covered by the HMAC" class of bug: the shop is asserted via an unauthenticated header while only the body is covered by the signature.

Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that has the app installed, a valid `(raw_body, hmac)` pair produced for one shop's webhook delivery is cryptographically indistinguishable from a valid pair for any other shop — the signature says nothing about which shop it was for. An attacker who can obtain any one legitimately-signed `(raw_body, hmac)` pair (e.g., from their own store's webhook traffic, which they fully control as the receiving party for their own installation) can replay that exact body and HMAC to the app's public webhook endpoint while swapping in an arbitrary `x-shopify-shop-domain` value. `HmacValidator.validate` will accept it because it never inspects the header, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen domain: [4](#0-3) 

Any host application that follows this gem's intended contract — trusting `WebhookMetadata#shop` as the tenant key to look up sessions, write shop-scoped data, or trigger shop-scoped side effects (this is the documented purpose of the field) — will process the forged event under the wrong tenant's identity.

### Impact Explanation
This crosses a tenant boundary: an attacker who controls one shop/installation of the app can cause the app to execute shop-scoped webhook logic (data updates, GDPR/mandatory topics like `customers/redact`, `shop/redact`, order processing, etc.) attributed to a *different* merchant's shop, without ever needing that merchant's credentials, access token, or `client_secret`. That is cross-tenant access, matching the Critical impact bucket in scope.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair, which is achievable by any merchant/attacker who has the app installed on their own shop and can capture the exact bytes and signature Shopify sends for their own webhook deliveries (they are the legitimate recipient side of that specific delivery, so no TLS interception or secret leakage is required). They then only need to change one HTTP header (`shop-domain`) and resend the identical body+signature to the app's public webhook URL. No brute force, no credential theft, and no cryptographic break of HMAC-SHA256 is needed — only reuse of an unauthenticated header field.

### Recommendation
Include the shop domain (and ideally topic/api-version) inside the value covered by the HMAC, or independently verify that the `shop-domain` header matches an expected/authorized shop for that installation before invoking the handler. At minimum, document/require host apps to cross-check `request.shop` against a shop they expect for the associated `topic`/subscription, and consider having `Request#to_signable_string` incorporate the header values that the library exposes as trusted (`topic`, `shop`, `api_version`, `webhook_id`) so a mismatch between signed and asserted values is impossible.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`) on their own store, causing Shopify to POST a payload to the app's webhook endpoint with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `client_secret`.
2. Attacker captures this exact `raw_body` and `hmac` value (they are the operator of the shop that triggered it, so no interception is needed for this shop's own deliveries in various self-hosted/test setups).
3. Attacker resends an HTTP request to the app's public webhook endpoint with:
   - identical `raw_body`
   - identical `x-shopify-hmac-sha256`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `raw_body` against the HMAC: [5](#0-4) 
5. `WebhookMetadata.new(... shop: request.shop ...)` is built with `shop = "victim-shop.myshopify.com"` and passed to the app's handler, which processes the event as belonging to the victim's tenant.
