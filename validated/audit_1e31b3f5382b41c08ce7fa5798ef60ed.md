### Title
Webhook `shop`, `topic`, and `webhook-id` identifiers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable signable string from the raw body alone, while the `shop`, `topic`, and `webhook-id` values that drive the app's business logic are read directly from unauthenticated HTTP headers. Any party capable of obtaining one validly-signed webhook body/HMAC pair for the app (e.g., a merchant who installs the app on their own store) can replay that exact body with a forged `shop-domain`/`topic`/`webhook-id` header to the app's public webhook endpoint, and the HMAC check will still pass — because those identity fields were never part of what was signed.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing the HMAC over `to_signable_string` and comparing it to the provided `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw request body: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` — the fields the app actually acts on — are pulled straight from HTTP headers that are entirely outside the signed material: [3](#0-2) 

`Registry.process` only validates the HMAC over the body, then dispatches to the handler using the unauthenticated `shop`/`topic`/`webhook_id` from the request: [4](#0-3) 

These values are then handed to the app's handler as trusted metadata: [5](#0-4) 

This is the exact bug-class analog described in the report: the entity used to route/act on the request (`entryPoint` in the wallet analog; `shop`/`topic` here) is not bound into the value that is cryptographically verified (the `create2` salt in the wallet analog; the HMAC signable string here). The identity binding that should hold is:

`verified_bytes (HMAC-covered content) == acted_upon_identity (shop, topic, webhook_id used for routing/tenant attribution)`

but the gem only enforces `verified_bytes == raw_body`, leaving `acted_upon_identity` completely unauthenticated.

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app (it's a per-app secret, not per-shop), any unprivileged user who installs the app on a store they control automatically receives legitimately HMAC-signed webhook payloads. That HMAC/body pair remains valid regardless of which `shop-domain`, `topic`, or `webhook-id` header accompanies it, since none of those are covered by the signature.

### Impact Explanation
An attacker who has installed the app (an unprivileged action available to any internet user, similar to the wallet PoC's attacker calling a public factory function) can:
1. Capture a validly-signed webhook body+HMAC pair delivered to their own shop.
2. Replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header set to an arbitrary victim shop, and/or the `X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers changed.
3. The HMAC check still passes because it only verifies the body bytes.
4. The app's handler processes the payload attributing it to the wrong tenant (victim shop) or under the wrong topic, causing cross-tenant data confusion, unauthorized state changes tied to the victim's `shop` identity, or replay/injection of the mandatory GDPR topics (`shop/redact`, `customers/redact`, `customers/data_request`) against an arbitrary shop.

This maps to the Critical "cross-tenant access" impact category: an attacker leverages their own legitimate, unprivileged access to forge tenant/topic identity for a different customer's shop, without needing the app's `client_secret` or any privileged credential.

### Likelihood Explanation
Any user can become an "unprivileged internet user" attacker simply by installing the target app on a shop they control (a normal, publicly available action for Shopify apps), then capturing and replaying their own legitimately-signed webhook. No secret material, TLS interception, or social engineering is required — only observation of headers on a request the attacker already legitimately receives. This is directly reachable through the gem's own webhook verification API (`Utils::HmacValidator.validate` / `Webhooks::Registry.process`), not dependent on the host app ignoring documented behavior — the gem itself never binds these fields into the signature.

### Recommendation
Include the identity fields the application relies on (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) as part of the HMAC-signed material, or otherwise cryptographically bind them (e.g., verify `shop` against a value independently retrieved from a per-tenant registered webhook record, not merely trust the header). At minimum, document and enforce that consumers of `WebhookMetadata#shop`/`#topic` must cross-check them against the shop/topic combination the app registered the webhook for, rather than treating header values as attacker-uncontrollable.

### Proof of Concept
```ruby
# Attacker owns/installs the app on "attacker-shop.myshopify.com" and captures
# a real webhook delivery for "orders/create":
raw_body = '{"id":1,"note":"legit order"}'
real_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
  ),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Attacker replays the SAME body+hmac but swaps the shop header to the victim's shop.
# The HMAC still validates because only raw_body is signed (see Request#to_signable_string).
forged_headers = real_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...))
# The HMAC check in Utils::HmacValidator.validate(request) passes despite the shop being forged.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
