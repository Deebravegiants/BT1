### Title
Removing/updating a token's chain config via `update_token` permanently blocks timeout refunds for in-flight transfers - (File: `modules/pallets/hyper-fungible-token/src/lib.rs`, `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `update_token` extrinsic lets `CreateOrigin` remove (or reconfigure) a chain's `TokenContracts`/`ContractToAsset`/`Precisions` entries for an asset at any time, with no regard for cross-chain `send()` requests that are already in flight. When such an in-flight request later times out, `on_timeout` looks up the very same storage that was just wiped and reverts, permanently preventing the user's escrowed/burned funds from being refunded — the exact bug class described in the ThunderFuel report, where removing an asset from the allow-list after users had already deposited made their funds permanently unwithdrawable.

### Finding Description
A user calls `send()` on `pallet-hyper-fungible-token`, which locks (native asset) or burns (non-native asset) their tokens and dispatches an ISMP `PostRequest` to the destination chain: [1](#0-0) 

If the request is never delivered/accepted (destination congestion, relayer inaction, or dispute) it eventually times out, and `pallet-ismp` invokes this pallet's `on_timeout` to refund the sender. Crucially, `on_timeout` re-derives the asset and decimals from the *current* state of `ContractToAsset` and `Precisions`, keyed by `(dest, to)`/`(asset, dest)`: [2](#0-1) 

If those lookups fail, `on_timeout` errors out with `UnknownContractOnTimeout` or `DecimalsNotConfigured` instead of refunding: [3](#0-2) 

Meanwhile, `CreateOrigin` can call `update_token` at any time to add/remove chains for an asset. The `remove_chains` branch unconditionally deletes `ContractToAsset` and `Precisions` for that `(chain, asset)` pair: [4](#0-3) 

The `add_chains` branch (used, for example, to migrate a token to a new EVM contract address on the same chain) also unconditionally removes the *old* `ContractToAsset` reverse mapping before inserting the new one: [5](#0-4) 

Because `on_timeout` resolves the asset via `ContractToAsset::get(dest, &to)` using the **old** contract address embedded in the original request (`to` field of the `PostRequest`, unchanged since dispatch), any `update_token` call that removes a chain or re-points a chain to a new contract address between the time a `send()` is dispatched and the time it times out will cause the pending request's `on_timeout` handler to revert. `pallet-ismp`'s timeout processing does not retry with a different asset/decimals resolution strategy — the lookup is unconditionally tied to governance-mutable storage, so once that storage has moved on, the refund path for that specific in-flight message is permanently broken. The user's locked/burned tokens (already escrowed in `Pallet::<T>::pallet_account()` or already burned) can never be recovered through this pallet.

### Impact Explanation
This results in permanent freezing of user funds: an unprivileged user's `send()` locks or burns their assets, and once governance performs a routine, expected maintenance operation (`update_token` to swap a stale/compromised contract address, or to deprecate a chain), any transfer that was in flight at that moment loses its only refund path when it times out. There is no other function in the pallet to recover the locked/burned balance. This matches "Permanent freezing of funds" — a High severity impact, consistent with the original ThunderFuel finding where removing an asset from the manager's allow-list blocked withdrawal of already-deposited balances.

### Likelihood Explanation
`update_token` is a routine governance/operational action (e.g., migrating a token's EVM contract address, deprecating an unsupported chain) rather than a rare emergency-only path, so it is reasonably likely to occur while ordinary user transfers are in flight — especially on chains with long dispute/challenge windows, where the window between `send()` and timeout can be substantial. No special conditions beyond normal, permissionless `send()` usage by a user plus a routine config update by governance are needed to trigger the freeze.

### Recommendation
Snapshot the resolved `(local_asset_id, decimals, erc_decimals)` in the dispatched request's `PostRequest` body/context at `send()` time rather than re-deriving them from live storage in `on_timeout`. Alternatively, make `update_token`'s removal/reassignment additive-only (never delete/overwrite existing `ContractToAsset`/`Precisions` entries while pending requests referencing them could still time out), or maintain a historical/versioned mapping keyed by contract address that is never purged, so `on_timeout` can always resolve the asset and decimals for any previously dispatched request regardless of subsequent governance updates.

### Proof of Concept
1. Governance registers asset `X` for `StateMachine::Evm(1)` via `register_token`, mapping it to contract `C1` with decimals `D1` (populates `TokenContracts`, `ContractToAsset`, `Precisions`).
2. Alice calls `send()` with `asset_id = X`, `destination = Evm(1)`. Her tokens are locked/burned and a `PostRequest` with `to = C1` is dispatched via ISMP.
3. Before the request is delivered/timed out, governance calls `update_token` with `remove_chains = [Evm(1)]` (e.g., deprecating the chain) or `add_chains` pointing `Evm(1)` to a new contract `C2` (e.g., migrating after a contract redeploy). This removes `ContractToAsset::(Evm(1), C1)` and `Precisions::(X, Evm(1))`.
4. The original request eventually times out; `pallet-ismp` invokes `Pallet::<T>::on_timeout`, which looks up `ContractToAsset::get(Evm(1), C1)` — this returns `None`, and the call errors with `UnknownContractOnTimeout` (or, if `ContractToAsset` still resolves but `Precisions` was removed, `DecimalsNotConfigured`).
5. Alice's locked/burned tokens are never refunded — there is no other code path in the pallet to recover them, resulting in a permanent loss of her funds.

	fn on_timeout(&self, request: Request) -> Result<Weight, anyhow::Error> {
		match request {
			Request::Post(PostRequest { body, to, dest, .. }) => {
				let message = Message::abi_decode(&body).map_err(HftError::DecodeError)?;

				// Refund the original sender
				let from_bytes = message.from.as_ref();
				let mut sender_bytes = [0u8; 32];
				if from_bytes.len() == 32 {
					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
					sender_bytes[12..].copy_from_slice(from_bytes);
				} else {
					Err(HftError::InvalidSenderLength(from_bytes.len()))?
				}
				let beneficiary: T::AccountId = sender_bytes.into();

				// Look up the asset from the destination contract address
				let local_asset_id = ContractToAsset::<T>::get(dest, &to)
					.ok_or(HftError::UnknownContractOnTimeout)?;

				let decimals = if local_asset_id == T::NativeAssetId::get() {
					T::Decimals::get()
				} else {
					<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
						local_asset_id.clone(),
					)
				};
				let erc_decimals = Precisions::<T>::get(local_asset_id.clone(), dest)
					.ok_or(HftError::DecimalsNotConfigured(dest))?;
