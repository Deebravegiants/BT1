Audit Report

## Title
LDAP DN injection via filter-escaping used in bind DN construction - (File: core/sessions/ldapauth/ldap.go)

## Summary
`ldapAuthenticator.CreateSession` and `TestPassword` construct an LDAP bind DN by concatenating an attacker-supplied, unauthenticated `email` value that has only been passed through `ldap.EscapeFilter`, a filter-escaping routine that does not escape DN-reserved characters (`,`, `+`, `"`, `<`, `>`, `;`, `=`). This allows an unauthenticated caller to inject extra RDN components into the bind DN used by `conn.Bind`.

## Finding Description
`SessionsController.Create` reads `sr.Email` directly from the unauthenticated request body and forwards it to `AuthenticationProvider().CreateSession` before any authentication succeeds. In LDAP mode, `CreateSession` builds `searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())` where `escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))`. `EscapeFilter` only escapes `\`, `*`, `(`, `)`, and NUL — characters relevant to LDAP filter syntax — not DN syntax. `TestPassword` repeats the identical pattern. The resulting string is used directly as a bind DN in `conn.Bind(searchBaseDN, sr.Password)`, a DN context, not a filter context. An unescaped comma in the `email` field therefore terminates the intended RDN early and appends attacker-chosen RDN components, altering the DN structure targeted by the bind/search. This differs from the correctly-scoped filter usage in `FindUser`, where `EscapeFilter` output is placed inside an actual filter expression.

## Impact Explanation
An unauthenticated client can manipulate the DN structure used for the LDAP bind, causing the node to attempt binds against DNs outside the intended `UsersDN`/`BaseDN` scope. This violates the intended containment of the LDAP user search/bind scope. However, a successful bind still requires the attacker to supply a correct password for the resulting (attacker-shaped) DN, so this does not by itself grant authentication bypass — it enables targeting/probing of DNs outside the configured subtree, a legitimate but bounded confidentiality/scoping issue for the LDAP authentication path, consistent with Medium severity.

## Likelihood Explanation
Reachable by any unauthenticated caller when the node is configured with `WebServer.AuthenticationMethod = 'ldap'`, since `POST /sessions` requires no prior authentication and directly forwards the `email` field into DN construction. Triggering the malformed DN construction itself is trivial; achieving any further impact still requires the attacker to possess valid credentials for a DN reachable via the injected structure.

## Recommendation
Replace filter-based escaping with proper DN escaping when constructing `searchBaseDN` for `conn.Bind` in `CreateSession` and `TestPassword` (e.g., a dedicated DN-escaping function, or strict allow-list validation of `email`, such as `^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+$`, before use in DN contexts). Reserve `ldap.EscapeFilter` exclusively for values placed inside filter expressions.

## Proof of Concept
1. Configure a chainlink node with `WebServer.AuthenticationMethod = 'ldap'` and known `UsersDN`/`BaseDN`.
2. Send `POST /sessions` with body `{"email": "victim,ou=OtherGroup,dc=corp,dc=com", "password": "anything"}`.
3. Observe that `CreateSession` builds `searchBaseDN = "<BaseUserAttr>=victim,ou=OtherGroup,dc=corp,dc=com,<UsersDN>,<BaseDN>"`, an RDN chain diverging from the intended `UsersDN` scope, and issues `conn.Bind` against it — demonstrable via a unit test on `ldapAuthenticator.CreateSession` with a mocked `LDAPClient` asserting the DN string passed to `Bind`.
