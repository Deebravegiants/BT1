Having reviewed the webhook processing pipeline, there is a genuine analog: the `shop` value used to route/identify a webhook is never included in the data that the HMAC actually authenticates.

### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates its HMAC over the raw request body only, while `shop` (and `topic`, `webhook_id`, `api_version`) come from unauthenticated HTTP headers. `Registry.process` passes this unauthenticated `shop` straight to the app's handler as the tenant identifier, so a valid `(body, hmac)` pair captured from one merchant's webhook can be replayed with a different `shop-domain` header and will still pass validation.

### Finding Description
`VerifiableQuery#to_signable_string` for the webhook `Request` returns only the raw body: [1](#0-0) 

Meanwhile `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body) — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates only that HMAC and then dispatches to the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` as if they were trusted, tenant-identifying values: [4](#0-3) 

This is the same class of defect as the referenced report: a field that is *acted on* (here, `shop`, used as the tenant/session key for the webhook handler) is *not covered* by the authenticating primitive (the HMAC). Contrast this with `Auth::Oauth::AuthQuery`, where `shop` (along with `code`, `host`, `state`, `timestamp`) is explicitly included in `to_signable_string` and therefore *is* bound by the HMAC: [5](#0-4) 

Because the webhook path does not follow that same pattern, the equality that should hold — `shop_bound_by_hmac == shop_used_for_tenant_dispatch` — is false. Any entity that has legitimately received one valid `(raw_body, hmac)` pair for *any* shop (e.g., an attacker who installs the app on their own store and captures their own webhook deliveries) can resubmit that exact body/HMAC to the app's shared webhook endpoint with an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` will report success because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop: [6](#0-5) 

If the host application uses `data.shop` to key persistence, cache invalidation, or business logic (the documented intended use, per `WebhookMetadata`), this allows cross-tenant data confusion/injection using a passed-HMAC-check payload that was never actually issued for that tenant.

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`, an access token, or any privileged access — the only requirement is a valid `(body, hmac)` pair for *some* shop, which is trivially obtainable by installing the app once. Under the given severity buckets this maps to **High: cross-tenant access**, since the gem hands the application attacker-controlled/spoofed tenant identity (`shop`) alongside a payload whose authenticity check says nothing about that identity.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that lets untrusted parties install it (i.e., any public Shopify app), since capturing one's own webhook deliveries is trivial and the replay only requires re-posting to the app's public webhook endpoint with a modified header — no secrets, tokens, or elevated access required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is actually HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the request before it is handed to handlers — e.g., include the shop domain in `to_signable_string`, or require host apps to cross-check `request.shop` against a shop already known/installed in their own storage before trusting it (and document this requirement clearly, since the library does not enforce it).

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and receives a legitimate webhook delivery, capturing `raw_body` and the `x-shopify-hmac-sha256` header — both valid per `HmacValidator.validate`.
2. Attacker POSTs the identical `raw_body` and `hmac` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes, because validation only checks the body/HMAC pair (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. The handler executes with `WebhookMetadata#shop == "victim.myshopify.com"` even though the payload was never issued for that shop (`lib/shopify_api/webhooks/registry.rb:198-199`), letting the attacker inject/replay data under the victim's tenant identity in any host application that trusts `data.shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
