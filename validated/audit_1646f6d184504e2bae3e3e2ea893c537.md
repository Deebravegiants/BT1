### Title
Unlimited router approval lets attacker swap stranded/residual `inputToken` balance beyond `deltaAmounts[0]`, minting an unbacked output UTXO - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`ExternalActionSwap.swap` computes `inputAmount` strictly from `-deltaAmounts[0]`, but `LifiExternalAction.callRouter` grants the LI.FI `router` an **unlimited** ERC-20 approval (`approveUnlimited(inputToken, router)`) and then executes fully attacker-controlled `externalActionMetadata` against that router. Because the approval is not capped to `inputAmount`, an attacker can craft router calldata that pulls more of `inputToken` than Hinkal actually sent this transaction — specifically any residual/dust `inputToken` balance already sitting in the action contract from a prior transaction — and convert it into extra `outputToken`, which is entirely credited to the caller as `swappedAmount`.

### Finding Description
The invariant that should hold is: tokens leaving the action contract in a transaction == `-deltaAmountChanges` Hinkal sent it for that transaction. In `swap()`: [1](#0-0) 

`inputAmount` is derived solely from `deltaAmounts[0]` (the amount Hinkal transferred into the action for this call), and this is the only value the circuit publicly constrains via `inTotal + amountChanges === outTotal`. However, `callRouter` in `LifiExternalAction` does not actually enforce that only `inputAmount` of `inputToken` can be consumed by the router: [2](#0-1) 

`approveUnlimited(inputToken, router)` sets the router's allowance to the maximum, not to `inputAmount`. The subsequent `router.call(externalActionMetadata)` is fully attacker-supplied calldata (the attacker controls `externalActionMetadata` as stated in the target scope). Since LI.FI routers pull tokens via `transferFrom` up to the granted allowance, the attacker can encode a router operation that transfers the entire `inputToken` balance held by the action contract — not just the `inputAmount` portion Hinkal just sent — as long as that full balance is ≤ allowance (which is unlimited).

`swappedAmount` is then measured only as the *output*-token balance delta: [3](#0-2) 

If the action contract already holds a stranded/dust balance of `inputToken` (e.g., left over from a prior transaction whose swap under-consumed input, or from a direct transfer), the attacker's crafted swap consumes `inputAmount + dust_inputToken`, producing `swappedAmount` that reflects value beyond what Hinkal's `deltaAmounts[0]` backed. This entire `swappedAmount` (minus fees) is then sent to `msg.sender`/the caller-controlled recipient: [4](#0-3) 

The circuit only constrains the public `deltaAmounts`/`amountChanges` for the caller's own leaf accounting; it has no visibility into, and cannot constrain, the action contract's actual on-chain token balance or the router calldata's real transfer amount, since `externalActionMetadata` is opaque bytes passed straight to an external call. `performHinkalChecks`, `verifyProof`, and the circuit's `inTotal + amountChanges === outTotal` check only validate that the *caller's* nullifiers/UTXOs are consistent with the `deltaAmounts` array — none of them re-verify that the actual token amount pulled by the router equals `inputAmount`. Reordering `erc20TokenAddresses` is relevant only insofar as it lets the attacker choose which token index is treated as `inputToken`/`outputToken` for a given dust-holding token, but the root cause is the unlimited, uncapped approval combined with attacker-controlled router calldata.

### Impact Explanation
An attacker can drain any stranded ERC-20 (or wrapped-native) dust balance left in the shared `LifiExternalAction` contract by any prior user's swap, converting it into their own withdrawn/output funds — value that was never backed by their own `-deltaAmountChanges`. This is direct theft of protocol/user-parked funds, matching **Critical: direct theft of shielded or in-flight user funds**, since the action contract is shared across all Hinkal users routing through it, and any dust deposited by another user's transaction becomes fair game for the next caller. The attack is repeatable every time dust accumulates.

### Likelihood Explanation
Preconditions: the `LifiExternalAction` contract must hold a nonzero residual balance of some ERC-20 token (plausible given rounding/slippage on router swaps, partial fills, or direct/mistaken transfers — dust accumulation in shared multi-tenant action contracts is common). The attacker needs no privilege beyond being a normal Hinkal user able to submit a valid proof for their own UTXOs and to supply `externalActionMetadata`/router calldata of their choosing (explicitly granted in the attacker capability list). Cost is just gas plus proof generation for a legitimate small deposit; the reward is the entire stranded balance. This is straightforward and highly feasible whenever dust exists.

### Recommendation
Cap the router approval to exactly `inputAmount` per call (`approve(router, inputAmount)` instead of unlimited, and reset to zero after or use `forceApprove` patterns), and/or measure and enforce that the router's `inputToken` balance decrease from the contract equals exactly `inputAmount` (not just that `outputToken` increased), reverting if more `inputToken` than authorized was consumed. Additionally, avoid leaving any token balances in a shared action contract between transactions — sweep unexpected residual balances to a safe/owner-controlled path rather than allowing the next caller's swap to implicitly consume them.

### Proof of Concept
1. Deploy `LifiExternalAction` with a mock router that, given attacker-crafted calldata, performs `transferFrom(action, router, allowanceAmount)` for `inputToken` and mints/transfers a proportional amount of `outputToken` back to the action contract.
2. Seed residual: send `D` dust units of `inputToken` directly to the `LifiExternalAction` contract (simulate stranded balance from a prior tx).
3. User A performs a legitimate Hinkal `transact` → `runAction` → `swap` call with `deltaAmounts[0] = -inputAmount` (small, honest amount).
4. Craft `externalActionMetadata` so the mock router's `transferFrom` pulls `inputAmount + D` (using the unlimited allowance) rather than just `inputAmount`.
5. Assert: `swappedAmount` returned reflects conversion of `inputAmount + D`, and `amountToSendToHinkal` sent to `msg.sender` exceeds what `inputAmount` alone should produce.
6. Assert the broken equality: tokens leaving the action (`inputAmount + D` of `inputToken` consumed, `outputToken` credited proportionally) != `-deltaAmountChanges` (`inputAmount`) Hinkal sent that tx — confirming the attacker captured the pre-existing `D` dust as part of their own output UTXO.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
