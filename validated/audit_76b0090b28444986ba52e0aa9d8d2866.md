### Title
Withdrawal status/hash misattribution when multiple withdrawals share the same `assetId` in one NEAR transaction - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` matches a withdrawal's on-chain status by `assetId` rather than by `index`, per an explicit code comment: "Response list is unsorted, so we match by assetId instead of index" [1](#0-0) . This is analogous to the original report's root cause: the code relies on a loose grouping key (assetId, like the "quest/period" bucket) rather than a strict per-item identity (index) to attribute an on-chain outcome to a specific request.

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [2](#0-1) , and if a match is found, returns that entry's `status`/`transfer_tx_hash` as the definitive outcome for `args.index` [3](#0-2) . The existing test explicitly documents that matching happens "by assetId, not by index" and demonstrates it working correctly only because the two withdrawals in the fixture use *different* assetIds [4](#0-3) . This confirms the matching key is `assetId`, not a unique per-withdrawal identifier such as index, destination address, or amount.

If a single NEAR transaction contains two or more withdrawal intents for the *same* `assetId` (e.g., a batched call withdrawing the same POA-bridged token to two different destinations, or splitting one withdrawal into two chunks), `findMatchingWithdrawal` has no way to distinguish which API-returned withdrawal record corresponds to `args.index`. Whichever record satisfies the assetId match first would be reported for every index in the batch, breaking the equality "status/txHash returned for index N == actual on-chain outcome of withdrawal N."

### Impact Explanation
This falls under "a status or hash misreport making an integrator credit or refund twice." An integrator polling `describeWithdrawal` per index in a batch could see the same `completed` status and the same `transfer_tx_hash` for two logically distinct withdrawals, one of which may still be pending or may have gone to a different destination/amount. This could cause the integrator to treat both withdrawals as fulfilled (double credit) or to associate the wrong destination/amount with a given index.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the caller (or the SDK's own multi-withdrawal batching path) to submit more than one withdrawal for the same `assetId` within a single NEAR transaction — a legitimate, non-adversarial usage pattern (e.g., splitting a large withdrawal, or a user withdrawing the same token to two addresses in one call) rather than a malicious action. I was not able to confirm from the available code whether `createWithdrawalIntents`/batch flows in `sdk.ts` actually permit or commonly produce such same-asset multi-withdrawal batches through POA bridge, or whether `findMatchingWithdrawal` includes additional disambiguation (e.g., matching also by amount/destination) that would mitigate this — the function body itself was not retrieved before the tool budget was exhausted.

### Recommendation
Disambiguate matching by including more of the request's identifying fields (destination address, amount, and ideally a stable per-intent index or nonce returned by the POA API) rather than `assetId` alone, or have the POA bridge API return an explicit request-index/correlation id so `describeWithdrawal` can pair each on-chain outcome to the exact request that produced it.

### Proof of Concept
Not independently verified end-to-end due to tool budget exhaustion (the `findMatchingWithdrawal` implementation in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` could not be read in full). Conceptually:
1. Submit a single NEAR transaction containing two `ft_withdraw` intents for the same `assetId` (e.g., `nep141:eth.omft.near`) to two different destination addresses/amounts.
2. Call `describeWithdrawal({ index: 0, withdrawalParams: { assetId, ... } })` and `describeWithdrawal({ index: 1, withdrawalParams: { assetId, ... } })`.
3. If the POA API returns both withdrawal records for that NEAR tx hash, `findMatchingWithdrawal` (matching solely on `assetId`) would return the same record for both calls, causing both indices to report identical status/txHash even though they represent different on-chain transfers. [5](#0-4)

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
