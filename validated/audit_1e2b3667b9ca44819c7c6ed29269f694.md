### Title
Reentrant `instantiate` during contract construction can collide with the in-construction address in `pallet-contracts` (unlike `pallet-revive`, which was patched for this exact bug) - (File: `substrate/frame/contracts/src/exec.rs`)

### Summary
The Rubicon `BathToken.initialize()` bug is a reentrancy issue where state (`initialized`) is not finalized before an external call, letting an attacker re-enter and corrupt contract state before the guard is set. The polkadot-sdk analog is `pallet-contracts`'s `Stack::push_frame`/`ContractInfo::new`, where a contract's `ContractInfo` is only written to `ContractInfoOf` storage when a **`Call`** frame pops, not when a **`Constructor`** frame is on the stack. This is the exact same root-cause pattern that Parity itself identified and fixed in the sibling `pallet-revive` pallet via `prdoc/pr_12645.prdoc` ("Reject re-entrant instantiate at an in-construction address"), but the equivalent guard does not appear to exist in `pallet-contracts`.

### Finding Description
In `pallet-contracts`, a new contract's address is derived deterministically from `(sender, code_hash, input_data, salt)` with no dependence on the call-stack nonce for the address computation itself [1](#0-0) . When a constructor is executing, its `ContractInfo` is kept only in the in-memory `Frame::contract_info` and is **not** persisted to `<ContractInfoOf<T>>` until a `Call` frame (not `Constructor`) pops: [2](#0-1) 

`ContractInfo::new` — the only collision guard against double-instantiation — checks `<ContractInfoOf<T>>::contains_key(account)` [3](#0-2) . Because the in-construction contract's info was never inserted into that map, this check cannot see an address that is currently being constructed higher up the call stack.

`push_frame` in `pallet-contracts` builds the new frame via `Self::new_frame` and pushes it directly, with no additional cross-frame collision check against other `Constructor` frames already on the stack: [4](#0-3) 

Compare this to `pallet-revive`'s `push_frame`, which was patched (via PR fixing paritytech/polkadot-sdk#12639) to explicitly reject a nested `Constructor` frame whose `account_id` collides with an existing `Constructor` frame on the stack: [5](#0-4) [6](#0-5) 

`pallet-contracts::exec.rs::instantiate` (the `Ext` trait implementation used by contract code to instantiate sub-contracts) contains no analogous check: [7](#0-6) 

### Impact Explanation
If a contract's constructor calls back into a factory/deployer contract which then re-instantiates code with the *same* `code_hash`, `input_data`, and `salt` (deterministic address inputs), the resulting address collides with the address currently under construction, because the collision guard in `ContractInfo::new` cannot observe the in-progress constructor's state (it isn't in `ContractInfoOf` yet). This mirrors the Rubicon bug where a not-yet-finalized initialization state let an attacker re-enter and run "construction" logic twice for what should be a single, already-initializing entity — permanently corrupting per-account bookkeeping (e.g., leaking consumer references / storage-deposit accounting / running two constructor frames for a single account), exactly as described for `pallet-revive` prior to its fix. This is a state-corruption/DoS-class vulnerability triggerable by any attacker-authored contract (fully permissionless, no privileged origin needed), consistent with the "reentrancy" vuln class in the report.

### Likelihood Explanation
Likelihood is realistic for an unprivileged user: any account can deploy a malicious contract via the standard, permissionless `instantiate`/`instantiate_with_code` extrinsics, and the exploit requires only ordinary contract-to-contract calls (no privileged origin, no bridge/relay/node access, fully on-chain and reachable). The exact same code pattern was independently confirmed exploitable and worth patching by the Polkadot-SDK team for `pallet-revive` (see `prdoc/pr_12645.prdoc`), which strongly supports that the analogous, unguarded code path in `pallet-contracts` is a realistic issue rather than purely theoretical — though I was not able to fully re-verify (due to the final tool-call cutoff) whether some other structural difference in `pallet-contracts` (e.g. a different address-derivation formula elsewhere in `address.rs` that I could not re-inspect this session) incidentally prevents the collision. This should be verified directly against `substrate/frame/contracts/src/address.rs::contract_address` before treating this as fully confirmed.

### Recommendation
Add the same EIP-684-style guard used in `pallet-revive`'s `push_frame` to `pallet-contracts`'s `push_frame`: before pushing a new `Constructor` frame, check whether any existing frame on the stack is also a `Constructor` frame for the same `account_id`, and if so return `Error::<T>::DuplicateContract` instead of proceeding. This follows the same "shift the state check before the external effect" principle recommended by the original report's judge (CEI pattern), applied at the call-stack level instead of a single boolean flag.

### Proof of Concept
A concrete Rust unit test analogous to `pallet-revive`'s `reentrant_instantiate_at_same_address_is_rejected` [8](#0-7)  would need to be written for `pallet-contracts`: a constructor that re-enters a factory contract, which calls `Ext::instantiate` a second time with identical `code_hash`/`input_data`/`salt`, and assert whether it succeeds (bug present) or returns `DuplicateContract` (bug absent/fixed). I was unable to execute this test within the current tool-call budget, so this PoC is proposed but not yet run/verified against `substrate/frame/contracts`.

	/// Create a subsequent nested frame.
	fn push_frame(
		&mut self,
		frame_args: FrameArgs<T, E>,
		value_transferred: BalanceOf<T>,
		gas_limit: Weight,
		deposit_limit: BalanceOf<T>,
		read_only: bool,
	) -> Result<E, ExecError> {
		if self.frames.len() == T::CallStack::size() {
			return Err(Error::<T>::MaxCallDepthReached.into());
		}

		// We need to make sure that changes made to the contract info are not discarded.
		// See the `in_memory_changes_not_discarded` test for more information.
		// We do not store on instantiate because we do not allow to call into a contract
		// from its own constructor.
		let frame = self.top_frame();
		if let (CachedContract::Cached(contract), ExportedFunction::Call) =
			(&frame.contract_info, frame.entry_point)
		{
			<ContractInfoOf<T>>::insert(frame.account_id.clone(), contract.clone());
		}

		let frame = top_frame_mut!(self);
		let nested_gas = &mut frame.nested_gas;
		let nested_storage = &mut frame.nested_storage;
		let (frame, executable, _) = Self::new_frame(
			frame_args,
			value_transferred,
			nested_gas,
			gas_limit,
			nested_storage,
			deposit_limit,
			self.determinism,
			read_only,
		)?;
		self.frames.push(frame);
		Ok(executable)
	}

			gas_limit,
			deposit_limit,
			self.is_read_only(),
		)?;
		let account_id = self.top_frame().account_id.clone();
		self.run(executable, input_data).map(|ret| (account_id, ret))
	}

#[test]
fn reentrant_instantiate_at_same_address_is_rejected() {
	// EIP-684: while `B1` constructs at address `X`, its constructor re-enters the deployer to
	// instantiate the same code+salt. That resolves to `X` again and must be rejected rather
	// than run a second constructor for one account.
	let salt = [42u8; 32];

	let constructor_ch = MockLoader::insert(Constructor, |ctx, _| {
		// Re-enter the deployer (BOB) while we are still being constructed.
		ctx.ext
			.call(
				&CallResources::NoLimits,
				&BOB_ADDR,
				U256::zero(),
				vec![],
				ReentrancyProtection::AllowReentry,
				false,
			)
			.unwrap();
		exec_success()
	});

	let invocations = Rc::new(RefCell::new(0u32));
	let second_instantiate_error = Rc::new(RefCell::new(None::<DispatchError>));
	let factory_ch = MockLoader::insert(Call, {
		let invocations = Rc::clone(&invocations);
		let second_instantiate_error = Rc::clone(&second_instantiate_error);
		move |ctx, _| {
			*invocations.borrow_mut() += 1;
			let n = *invocations.borrow();
			// Bound the recursion in case the guard fails to reject the collision.
			if n <= 2 {
				let min_balance = <Test as Config>::Currency::minimum_balance();
				let value = Pallet::<Test>::convert_native_to_evm(min_balance);
				let result = ctx.ext.instantiate(
					&CallResources::NoLimits,
					Code::Existing(constructor_ch),
					value,
					vec![],
					Some(&salt),
				);
				if n == 2 {
					if let Err(err) = &result {
						*second_instantiate_error.borrow_mut() = Some(err.error);
					}
				}
			}
			exec_success()
		}
	});

	ExtBuilder::default()
		.with_code_hashes(MockLoader::code_hashes())
		.existential_deposit(15)
		.build()
		.execute_with(|| {
			let min_balance = <Test as Config>::Currency::minimum_balance();
			set_balance(&ALICE, min_balance * 1000);
			place_contract(&BOB, factory_ch);
			let origin = Origin::from_account_id(ALICE);
			let mut meter =
				TransactionMeter::<Test>::new_from_limits(WEIGHT_LIMIT, min_balance * 100).unwrap();

			// `B1` still constructs; only the colliding re-entrant instantiate fails.
			assert_ok!(MockStack::run_call(
				origin,
				BOB_ADDR,
				&mut meter,
				Pallet::<Test>::convert_native_to_evm(min_balance * 100),
				vec![],
				&ExecConfig::new_substrate_tx(),
			));

			// Initial call plus one re-entry; without the guard it would recurse further.
			assert_eq!(*invocations.borrow(), 2);
			assert_eq!(
				*second_instantiate_error.borrow(),
				Some(<Error<Test>>::DuplicateContract.into())
			);
		});
}
