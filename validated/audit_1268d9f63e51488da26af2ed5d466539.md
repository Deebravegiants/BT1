This confirms the vulnerability: the gem's documented processing flow (`docs/usage/webhooks.md` lines 123-136) explicitly instructs apps to trust `ShopifyAPI::Webhooks::Registry.process` to "verify the request did indeed come from Shopify," and hands the app a `WebhookMetadata` with a `shop` field the app is expected to use directly (see doc lines 12-14, 25-26). The gem's own `Utils::HmacValidator.validate` only checks `request.to_signable_string`, which in `ShopifyAPI::Webhooks::Request#to_signable_string` is `@raw_body` alone — the `shop-domain` header is never part of the signed bytes.### Title
Webhook shop-tenant identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` header (exposed as `request.shop`) to determine which merchant tenant the payload belongs to. Because the header is not part of the signed bytes, the binding `hmac-verified bytes == bytes the shop identity comes from` does not hold, letting any user who legitimately receives one webhook from Shopify for their own shop (i.e., a normal, unprivileged app-installer, not a Shopify or app operator) replay that same body/HMAC pair to the app's webhook endpoint with an arbitrary victim `shop-domain` header and have it accepted as authentic for the victim tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body` — none of the Shopify headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the bytes that get HMAC-verified. Yet `shop` is parsed straight from the unauthenticated header: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the raw body alone: [3](#0-2) 

`Registry.process` then dispatches to the app's handler using this unauthenticated `shop` value as the tenant identity, once the (body-only) HMAC check passes: [4](#0-3) 

The gem's own documentation instructs apps to treat `Registry.process` as proof "the request did indeed come from Shopify" and to consume `data.shop` directly as the shop identity for the payload, e.g. enqueuing background work keyed on it: [5](#0-4) [6](#0-5) 

Because the same `Context.api_secret_key` (the app's single `client_secret`) is used to sign every webhook for every shop that installed the app, an attacker who runs their own shop with the app installed will legitimately receive Shopify-signed webhooks (valid `raw_body` + valid HMAC) for their own shop. Nothing in the signed bytes ties that HMAC to their shop domain. The attacker can therefore resend that same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` with a victim shop's domain. `HmacValidator.validate` still returns `true` (it never looks at the header), and `Registry.process` calls the handler with `shop: <victim shop>` and `body: <attacker-controlled data>`, causing the application to process attacker-chosen webhook content under the victim's tenant identity.

### Impact Explanation
This breaks the tenant-identity binding `HMAC-verified bytes == shop derived from request`, enabling cross-tenant data injection/confusion: an unprivileged user (any merchant who has installed the app) can make the app believe attacker-controlled webhook data originated from a different, victim shop. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (e.g., to key database records, enqueue jobs, or trigger side effects for "that shop"), this can corrupt or exfiltrate another merchant's data — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only that the attacker operates their own shop with the target app installed (a normal, unprivileged app user), which is a low bar. They need to capture one legitimate raw webhook body + HMAC pair for their own shop (trivially done by logging their own webhook endpoint traffic) and replay it with a modified `shop-domain` header to the app's public webhook URL. No access token, `api_secret_key`, or privileged access is required.

### Recommendation
Bind the shop domain (and ideally topic/webhook-id) into the HMAC-verified payload instead of trusting an unauthenticated header. Since Shopify's HMAC only covers the body, the gem should require host apps to independently verify that the `shop-domain` header corresponds to a shop with an existing, valid session/installation record before trusting `data.shop`, and the documentation/`WebhookMetadata` API should make this required verification step explicit rather than implying `Registry.process` alone establishes tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimately signed webhook to the attacker's endpoint:
   - `raw_body = '{"id":1,...}'`
   - `X-Shopify-Hmac-Sha256 = Base64(HMAC-SHA256(client_secret, raw_body))`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
3. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `to_signable_string` is still just `raw_body`.
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `HmacValidator.validate(request)`, which passes because the signature only ever covered `raw_body`, unchanged by the attacker.
6. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: attacker_json, ...)`, and the host app processes attacker-controlled data as if it came from `victim.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
