### Title
Backend-Pushed Config Changes With Immediate Effect Can Alter Mid-Signup Enrollment/Fraud Decisions - (File: src/plans/mod.rs)

### Summary
The external report describes an `onlyOwner` role that can push protocol parameter changes with immediate effect while other state changes are subject to a timelock, letting the owner unintentionally (or maliciously) alter the outcome of an in-flight `settleAuction()` transaction. The orb-core analog is the shared, mutable `Config` object (`Arc<Mutex<Config>>`) which the backend can update at any time with immediate, unstaged effect via a background poller, while a single signup (`do_signup`) is a long-running, multi-stage async flow that re-reads this same `Config` object at different points in time. This allows a backend-driven config change to change behaviorally-significant flags (e.g. `ignore_user_centric_signups`) between the start of a signup and the enrollment decision later in the same signup, producing an inconsistent, unintended enrollment outcome.

### Finding Description
`Config` is loaded once at startup and then refreshed unconditionally every `CONFIG_UPDATE_INTERVAL` (10 seconds) by a background task in the observer broker, which swaps the entire shared config object in place with no staging or timelock: [1](#0-0) [2](#0-1) 

`Config::download_and_store` performs the same immediate, unstaged replacement: [3](#0-2) 

`MasterPlan::do_signup` is a long multi-stage async operation (QR scanning, sleeps, biometric capture, biometric pipeline, fraud checks, PCP building, uploads) that takes an initial snapshot of only a subset of config fields at the top of the function: [4](#0-3) 

but other fields, such as `ignore_user_centric_signups`, are read fresh, later in the same signup, via a separate `orb.config.lock().await` call, well after biometric capture and the biometric pipeline (each involving model timeouts and sleeps) have already executed: [5](#0-4) 

Because the 10-second background poller can swap the whole `Config` at any point during this window, the value of `ignore_user_centric_signups` observed at the enrollment-decision branch can differ from what was in effect when the signup began (or from what was in effect when `user_centric_signup` was determined from the QR payload). This mirrors the report's root cause exactly: a privileged party (`onlyOwner` in the DeFi analog; the backend/config admin here) can change a parameter with immediate effect while a multi-step user-facing operation is mid-flight, and the operation reads that parameter at multiple different times, producing a result that neither party intended.

### Impact Explanation
If `ignore_user_centric_signups` is `false` at the point of this check, the code trusts the QR-supplied `user_centric_signup` flag and treats the signup as successful purely based on `signup_reason == SignupReason::Normal`, without running the full `enroll_user` verification path: [6](#0-5) 
If it is `true`, the full `enroll_user` call (with associated debug/enrollment status reporting) is invoked instead: [7](#0-6) 
A backend-side config push that changes this flag mid-signup causes the orb to non-deterministically pick one branch or the other for reasons unrelated to the actual biometric result of that particular signup — i.e., the enrollment/fraud outcome recorded for the signup can be inconsistent with the state that was true when the signup was initiated, an unauthorized/misattributed signup outcome in the same sense as the auction bonder being over/under-compensated relative to the auction parameters that were true when they bonded.

### Likelihood Explanation
The background config refresh runs every 10 seconds unconditionally whenever network is unblocked, and a full signup routinely spans well beyond 10 seconds (fixed 3-second pre-capture sleep, biometric capture timeouts, and the biometric pipeline's model timeout), so the race window is reached on a very large fraction of signups, not merely a theoretical edge case. No operator action or attacker interaction is required beyond a normal backend config push, which the report's threat model already treats as an "owner privilege" that is exercised routinely, not maliciously.

### Recommendation
Take a single, consistent snapshot of the entire `Config` at the very start of `do_signup` (or at `start_signup`) and thread that snapshot through every subsequent stage of the signup, rather than re-locking and re-reading `orb.config` at multiple separate points. If specific fields must reflect near-real-time config (e.g. safety-related toggles), document and isolate those explicitly; all fields that affect the enrollment/fraud decision path should be fixed for the duration of a single signup, mirroring the original report's suggestion of having `bondForRebalance()`-equivalent logic snapshot external state up front instead of re-reading it later.

### Proof of Concept
1. Backend operator changes `ignore_user_centric_signups` from `false` to `true` (or vice versa) via the config endpoint consumed by `Config::download`/`from_backend`: [8](#0-7) 
2. The observer's `config_update` background task picks this up on its next 10-second tick and swaps `*config.lock().await` immediately, with no staging: [9](#0-8) 
3. A signup already in progress, having started with the old config value, reaches the enrollment-decision check in `do_signup` after the swap has occurred, and reads the new value of `ignore_user_centric_signups`: [10](#0-9) 
4. The signup is enrolled/rejected using a mix of config state that was never simultaneously valid — i.e., inconsistent with what was true when the signup, QR scan, and capture decisions were made.

    fn config_update(&mut self, observer: &mut Observer) -> Result<()> {
        if self.before_config_update()? {
            match observer.config_update.as_mut().map(future::FutureExt::now_or_never) {
                Some(None) => return Ok(()),
                Some(Some(result)) => result??,
                None => {}
            }
            let config = Arc::clone(&observer.config);
            let ui = observer.ui.clone();
            observer.config_update = Some(tokio::spawn(async move {
                if let Ok(new_config) = Config::download().await {
                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }

        *config.lock().await = Self::download().await.map_err(|e| {
            tracing::error!("Failed to download config: {:?}", e);
            e
        })?;
        let config_to_store = config.lock().await;
        tracing::info!("Downloaded latest config: {:?}", config_to_store);
        config_to_store.store().await.map_err(|e| {
            tracing::error!("Config downloaded but failed to be stored: {:?}", e);
            e
        })
    }
