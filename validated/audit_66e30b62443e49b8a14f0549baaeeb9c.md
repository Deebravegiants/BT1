### Title
Excess native-token payment in `EvmHost.dispatch()`/`fundRequest()` is not refunded to the caller and is stranded in the host contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept `msg.value` and forward the entire amount to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an exact amount of fee token. Unlike the sibling app-level contract `IntentGatewayV2` (which explicitly tracks `amounts[0]` returned by the swap and refunds the unused portion of `msg.value` back to `msg.sender`), `EvmHost` does none of this bookkeeping. This is directly analogous to the Aave `LendingPool.repay` bug: a function that accepts more Ether than is strictly required for an internal operation, but fails to forward/refund the surplus to the correct party, causing user funds to be effectively lost.

### Finding Description
In `EvmHost.sol`: [1](#0-0) 
the `dispatch(DispatchPost memory post)` function does:
```
if (msg.value > 0) {
    ...
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
```
The router computes `amounts[0]` (the ETH actually needed to buy `post.fee` worth of fee token) and, per standard Uniswap V2 semantics, refunds `msg.value - amounts[0]` to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender. `EvmHost` never captures or forwards this refund back to `_msgSender()`/`post.payer`.

The identical pattern repeats in `dispatch(DispatchGet memory get)`: [2](#0-1) 
and in `fundRequest()`: [3](#0-2) 

By contrast, the app-level `IntentGatewayV2.placeOrder()` correctly handles this exact scenario by tracking the swap output and refunding the difference: [4](#0-3) 
```
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
    order.fees, path, address(this), block.timestamp
);
msgValue -= amounts[0];
...
if (msgValue > 0) {
    _sendValue(msg.sender, msgValue);
}
```
This shows the codebase is aware that `swapETHForExactTokens` can leave unused native token that must be explicitly refunded — yet the core `EvmHost.dispatch`/`fundRequest` functions, which are reachable by any unprivileged app contract or EOA (both are `external payable` with no access restriction), omit this refund entirely.

The documentation explicitly warns callers not to rely on `quote()` on-chain due to sandwich-attack risk and instead to estimate fees off-chain — meaning callers are expected to send an amount that is only approximately correct, with the protocol responsible for making the excess whole. Given price movement between quoting and inclusion, or intentional overpayment as a safety margin, any excess ETH sent to `dispatch()`/`fundRequest()` is silently retained by the `EvmHost` contract rather than returned to the payer.

### Impact Explanation
Any unprivileged caller (a message dispatcher app, HyperFungibleToken/WrappedHyperFungibleToken wrapper, LayerZero endpoint adapter, or any custom `HyperApp`) that dispatches a POST/GET request or funds a pending request using native token payment permanently loses any ETH sent in excess of the exact swap requirement. This is a permanent freezing/loss of user funds bug, matching the "concrete theft or permanent freezing of funds" acceptance criterion. It affects the base `dispatch`/`fundRequest` entry points used across the whole EVM messaging surface (any `HyperApp.dispatchWithNative`, `HyperFungibleToken.send`, `WrappedHyperFungibleToken.send`, LayerZero endpoint, intents flows that fall back to raw `dispatch`), so the blast radius is broad.

### Likelihood Explanation
High likelihood: this triggers on ordinary usage whenever a caller supplies `msg.value` that isn't the exact wei amount required by the Uniswap quote at execution time — which is the expected/common case since the docs explicitly discourage on-chain exact quoting and recommend generous off-chain estimates. No malicious actor or special conditions are required; it happens on every slightly-overestimated dispatch call.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder()`: capture the `amounts[0]` returned from `swapETHForExactTokens` in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, and refund `msg.value - amounts[0]` back to `_msgSender()` (or `post.payer`, as appropriate) before returning.

### Proof of Concept
1. Deploy/observe `EvmHost` configured with a real `IUniswapV2Router02` (`_hostParams.uniswapV2`).
2. Call `dispatch(DispatchPost)` with `msg.value` set to, e.g., 2x the amount required to buy `post.fee` worth of fee token (a realistic scenario given the documented guidance to over-provision native value for a swap quoted off-chain, per `docs/content/developers/evm/messaging/post-requests.mdx` lines 236-238 warning against on-chain `quote()`).
3. `swapETHForExactTokens` executes, consumes only `amounts[0]` and refunds the remaining ETH to `EvmHost` (the caller of the router), not to the transaction sender.
4. Inspect `EvmHost`'s ETH balance post-call: it now holds the surplus ETH with no code path (`dispatch`, `fundRequest`, or any `withdraw`/`sweep` function found in the contract) that returns it to the original payer.
5. Compare against `evm/tests/foundry/IntentGatewayV2Test.sol::testPlaceOrder_FeeSwap_RefundsExcessNativeToken` [5](#0-4)  which demonstrates the correct refund behavior is achievable and tested elsewhere in the same codebase, confirming `EvmHost` is missing equivalent protection.

Note: I was unable to fully inspect the `withdraw`/`receive` functions found by grep in `evm/src/core/EvmHost.sol` (4 matches) before running out of tool calls, so I cannot rule out with full certainty whether an owner-only sweep function exists that could recover (but not return to the user) this stranded ETH. This does not change the core finding that ordinary callers have no path to reclaim their overpaid native token.

    /// @notice placeOrder with fee swap refunds unused ETH after swapETHForExactTokens.
    function testPlaceOrder_FeeSwap_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1000 * 1e6;
        uint256 feeAmount = 1 * 1e18; // 1 DAI worth of fees

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 1000,
            nonce: 0,
            fees: feeAmount,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userEthBefore = user.balance;

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        // Send 5 ETH for a fee swap that should cost much less
        intentGateway.placeOrder{value: 5 ether}(order, bytes32(0));
        vm.stopPrank();

        // User should get back most of the 5 ETH — the swap only needed a tiny fraction
        uint256 ethSpent = userEthBefore - user.balance;
        assertTrue(ethSpent < 1 ether, "User should have been refunded most of the 5 ETH");
        assertTrue(ethSpent > 0, "User should have spent some ETH on the fee swap");
    }
