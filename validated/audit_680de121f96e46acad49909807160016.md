## Title
Missing safe-transfer / post-transfer balance verification in `IntentGatewayV2` (Tron) predispatch escrow sweep allows unbacked escrow credit - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` moves tokens out of the `CallDispatcher` back to the gateway using a raw, unchecked `IERC20.transfer` call (constructed via `abi.encodeWithSelector`) and then unconditionally credits the order's escrow ledger with the *pre-transfer* balance snapshot, instead of verifying the actual post-transfer balance received. This is the same root-cause class as the referenced report (raw ERC20 transfer whose success/return value is never checked), but here it corrupts shared protocol accounting rather than a single external call.

### Finding Description
In the predispatch escrow flow of `placeOrder`, the gateway snapshots the dispatcher's token balance, builds a sweep `Call` using the raw selector `IERC20.transfer.selector` (not `safeTransfer`), and credits `_orders[commitment][token]` with `reducedInputs[i].amount` based on that pre-transfer snapshot — without ever re-checking `IERC20(token).balanceOf(address(this))` after the sweep executes: [1](#0-0) 

Compare this with the equivalent code path in the mainline (non-Tron) `IntentGatewayV2.sol`, which explicitly measures the *actual* received amount via a balance-before/balance-after diff on `address(this)` and mutates `order.inputs[i].amount` to that real value before it is used for escrow accounting: [2](#0-1) 

The Tron contract is missing this safeguard. `CallDispatcher.dispatch` only checks that the low-level `call` did not revert — it never inspects the ERC20's boolean return value: [3](#0-2) 

Because `order.inputs[i].token` is a caller-supplied address (any ERC20, since "this project assumes any ERC20"), a user placing an order can supply a non-standard-compliant or adversarial ERC20 whose `transfer()`/`balanceOf()` report success/balance without actually moving the expected amount of real tokens into the gateway. Since the escrow credit (`_orders[commitment][token] += reducedInputs[i].amount`) is derived from the pre-sweep balance snapshot rather than a verified post-sweep balance delta, the gateway's internal escrow ledger for that token can become inflated relative to the contract's real token holdings.

### Impact Explanation
`_orders[commitment][token]` is a shared per-token ledger that is later used to release/redeem escrowed funds to solvers/beneficiaries via `_withdraw`, which performs `IERC20(token).safeTransfer(beneficiary, amount)`: [4](#0-3) 
If the escrow ledger for a token is inflated beyond the gateway's actual balance, later withdrawals for that token (potentially belonging to other, legitimate orders) can be paid out of funds that were never actually deposited — draining real assets escrowed by other users of the same token. This is a fund-theft/insolvency vector on the protocol's shared token pool, meeting the Medium/High bar (unauthorized draining of escrowed funds due to unverified transfer accounting).

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` with `predispatch` enabled and specifying an attacker-controlled or non-standard ERC20 as an input token — no special privileges are required, only the ability to submit an order using a token of the attacker's choosing.

### Recommendation
Mirror the mainline `IntentGatewayV2.sol` pattern in the Tron contract: replace the raw `IERC20.transfer.selector` sweep call with a verified flow that snapshots `IERC20(token).balanceOf(address(this))` before dispatching the sweep and re-checks it afterward, crediting `_orders[commitment][token]` only with the actually-received delta (or switch fully to `SafeERC20.safeTransfer`/`safeTransferFrom` plus explicit balance-diff accounting) so escrow credit can never exceed real tokens held by the contract.

### Proof of Concept
1. Attacker deploys a malicious ERC20 `EvilToken` whose `transfer(address,uint256)` always returns `true` (or a truthy non-revert) but internally moves fewer tokens than requested (or none at all) to the target, while `balanceOf` can be made to temporarily reflect the "expected" pre-sweep amount held by the dispatcher.
2. Attacker calls `placeOrder` on Tron's `IntentGatewayV2` with `order.predispatch.assets` containing `EvilToken`, and `order.inputs` also referencing `EvilToken`.
3. During predispatch, `EvilToken` is transferred to the `CallDispatcher`; the sweep in `evm/tron/contracts/apps/IntentGatewayV2.sol:416-449` reads `balance = IERC20(EvilToken).balanceOf(dispatcher)`, builds the raw `transfer` call to move it back to the gateway, and — regardless of whether the gateway's actual `EvilToken` balance increased by that amount — credits `_orders[commitment][EvilToken] += reducedInputs[i].amount`.
4. A solver later fills the order and the escrow is redeemed via `_withdraw`, which calls `safeTransfer` for `reducedInputs[i].amount` of `EvilToken` out of the gateway's actual pooled `EvilToken` balance — a balance that includes real `EvilToken` deposits from other, legitimate orders — resulting in those other orders' funds being paid out to cover the unbacked escrow entry.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
