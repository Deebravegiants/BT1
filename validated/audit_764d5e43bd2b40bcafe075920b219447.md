### Title
`PoaBridge.describeWithdrawal()` Misreports Withdrawal Status/TxHash for Batched Same-Asset Withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal()` resolves an individual withdrawal's status by matching solely on `assetId` via `findMatchingWithdrawal`, ignoring the `index` field that is supposed to disambiguate which withdrawal within a batch is being queried. When a single NEAR intent contains two or more POA-bridge withdrawals of the same token (e.g., two USDC-to-XRPL withdrawals to different destination addresses within one batch), every `describeWithdrawal` call for that assetId returns the same (first) matching entry from the bridge API response, regardless of which index/withdrawal is actually being tracked.

### Finding Description
`createWithdrawalIdentifiers()` assigns each withdrawal params a monotonically increasing `index` per bridge route, and the SDK's contract (documented in `packages/intents-sdk/README.md` and the RFC) is: `promises[i]` corresponds to `withdrawalParams[i]`, with each promise resolving independently to the correct on-chain transaction for that specific withdrawal. [1](#0-0) 

However, `PoaBridge.describeWithdrawal()` never uses `args.index` to pick the correct entry — it only matches by `assetId`: [2](#0-1) 

```
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [3](#0-2) 

This is a known, explicitly-documented limitation in the code comment ("multiple withdrawals of the same token in a single transaction are not supported"), but the code does not fail safe — it silently returns the first matching withdrawal's status and `transfer_tx_hash` for *every* index that shares that assetId, instead of throwing or returning an unambiguous error.

Consequently, when `sdk.createWithdrawalCompletionPromises()` is used with two withdrawal params of the same POA asset (a supported, documented usage pattern per the batch-withdrawal RFC/README), both `promises[0]` and `promises[1]` poll the same underlying `describeWithdrawal` call path and will resolve to the **same `status` and `txHash`**, even though they represent different destination addresses/amounts on-chain. [4](#0-3) 

### Impact Explanation
This breaks the equality "status/hash reported for withdrawal N == on-chain outcome for withdrawal N." An integrator relying on `createWithdrawalCompletionPromises`/`watchWithdrawal` to track and reconcile individual withdrawals (e.g., crediting a user ledger, marking an off-chain order fulfilled, or triggering a refund) would receive the identical `txHash` for two distinct withdrawals. This can cause:
- Premature/incorrect completion reporting for a withdrawal that hasn't actually landed (the integrator believes withdrawal #2 is done because it got a "completed" status + hash that actually belongs to withdrawal #1).
- Double crediting/confirmation logic keyed off a single tx hash being applied to two different withdrawal records.

This matches the "High" impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious actor — it is triggered by an entirely legitimate, SDK-supported usage pattern: batching multiple withdrawals of the same asset to different destinations in a single intent via `withdrawalParams: WithdrawalParams[]` and `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion`. The bug is deterministic whenever two or more same-asset POA withdrawals are included in one batch, which the SDK's public batch-withdrawal API does not prevent or validate against.

### Recommendation
`findMatchingWithdrawal` should disambiguate multiple same-asset entries using additional deterministic criteria available at query time (e.g., destination address plus amount, or ordering withdrawals by amount as the code comment itself suggests), and should track/exclude already-matched withdrawals across concurrent `describeWithdrawal` calls for the same tx. At minimum, when more than one entry matches an assetId without a reliable way to disambiguate, the bridge should throw/return an explicit unsupported/ambiguous error rather than silently returning a possibly-wrong status and tx hash for the requested index.

### Proof of Concept
1. Submit an intent with `withdrawalParams = [ {assetId: "nep141:usdc.omft.near", amount: 100, destinationAddress: "addrA"}, {assetId: "nep141:usdc.omft.near", amount: 200, destinationAddress: "addrB"} ]` via POA bridge in a single NEAR tx.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams, intentTx })`, yielding `promises[0]` (for addrA) and `promises[1]` (for addrB).
3. Both promises internally call `PoaBridge.describeWithdrawal` with `index: 0` and `index: 1` respectively, but `findMatchingWithdrawal` ignores `index` and returns the same first entry (`w.data.near_token_id` match) from the API's `withdrawals` list for both calls.
4. Once the first withdrawal (addrA) completes on-chain, both `promises[0]` and `promises[1]` resolve to `{ hash: <addrA's transfer_tx_hash> }`, even though addrB's withdrawal may still be pending or may go to a different transaction entirely — as demonstrated by the code comment at [5](#0-4)  acknowledging same-token batches are not correctly handled.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
