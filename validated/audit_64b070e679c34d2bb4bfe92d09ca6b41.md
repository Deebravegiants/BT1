Audit Report

## Title
Disabled slippage control in `SwapFirstAssetTrader::refund_weight` swap-back - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight` swaps the unspent `Target`-asset portion of a collected XCM execution fee back into the original fee-paying asset by calling `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, disabling the slippage-protection mechanism that this trait explicitly supports. Unlike `buy_weight`, which uses `swap_tokens_for_exact_tokens` (output amount fixed at `fee`, so its input is self-bounded), `refund_weight`'s output is entirely unconstrained by the code.

## Finding Description
`refund_weight` extracts the unused portion of `total_fee` (in the `Target` asset) and calls:
```rust
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
)
```
at [1](#0-0) . `pallet_asset_conversion::SwapCredit::swap_exact_tokens_for_tokens` explicitly supports an `amount_out_min: Option<Balance>` parameter for slippage protection [2](#0-1) , and `do_swap_exact_credit_tokens_for_tokens` only enforces the bound when `Some(_)` is supplied [3](#0-2) . By passing `None`, `refund_weight` accepts any nonzero output from the pool. In contrast, `buy_weight`'s swap uses `swap_tokens_for_exact_tokens`, where the output is fixed at `fee` and the input consumption is bounded by the supplied credit [4](#0-3) . This trader is wired into production runtime configs, including Asset Hub Westend and Penpal [5](#0-4) [6](#0-5) .

The code does behave as claimed: the `None` literal is present and unconditional, and no bound is enforced on the refund swap-back.

## Impact Explanation
The impact is real but narrow in scope. `refund_weight` is invoked as part of processing a single specific XCM message, and the resulting credit is folded back into the holding register for that same message, i.e., it benefits the same account/message whose execution generated the fee overpayment (the message sender/beneficiary), not an arbitrary third party's funds and not protocol-level accounting. There is no cross-account fund drain, no insolvency, and no privilege escalation — the worst case is that the account being refunded receives a suboptimal amount if the specific `(Target, refund_swap_asset)` pool is thin and manipulated at the moment of the swap. This is a legitimate "missing slippage protection" bug, consistent in kind with issues flagged in `pallet_asset_conversion`'s own extrinsics (which do enforce `amount_out_min`), but the report itself does not (and the review here cannot) establish that this leads to loss of funds belonging to anyone other than the refund recipient, and it does not demonstrate protocol insolvency or a broken security invariant beyond "swap executed at unfavorable price."

## Likelihood Explanation
The submitter's own likelihood analysis is explicitly speculative and unresolved: it states uncertainty about whether inbound XCM (processed as inherents) can be sandwiched in the same block, and only weakly asserts plausibility for locally-submitted `pallet_xcm::execute` calls without demonstrating actual mempool-ordering control, block-authorship capability, or a working sandwich sequence. No PoC, fork test, or invariant test was executed; the report explicitly states "Not independently reproduced" and asks that this be "validated with a concrete PoC before treating this as high severity." The existing test suite in `cumulus/primitives/utility/src/tests/swap_first.rs` confirms `refund_weight`'s normal behavior but includes no test demonstrating an exploitable sandwich/loss scenario [7](#0-6) .

## Recommendation
Compute a bound for the refund swap (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` with a configurable tolerance) and pass `Some(min_amount)` instead of `None` to `SwapCredit::swap_exact_tokens_for_tokens`, falling back to returning the un-swapped `Target` asset if the quote cannot be met, consistent with how `pallet_asset_conversion`'s own dispatchables enforce `amount_out_min`.

## Proof of Concept
None provided or independently reproduced. A valid PoC would require setting up a thin-liquidity `AssetConversion` pool for `(Target, refund_swap_asset)`, triggering a `refund_weight` refund via an over-estimated-weight XCM program (e.g., through `pallet_xcm::execute`), and demonstrating — via a fork test or integration test — that an attacker can reliably interleave manipulating swaps within the same block to extract value from the specific victim's refund, at a lower amount than fair quoted price. This was not demonstrated in the submission; the finding rests solely on static code analysis of the missing `amount_out_min` bound.

#[test]
fn buy_and_refund_twice_for_target() {
	let client_asset_total = 15;
	let fee = 5;
	let refund1 = 4;
	let refund2 = 2;

	setup_pool(CLIENT_ASSET, 1000, TARGET_ASSET, 1000);
	// create pool for refund swap.
	setup_pool(TARGET_ASSET, 1000, CLIENT_ASSET, 1000);

	let holding_asset = create_holding_asset(CLIENT_ASSET, client_asset_total);
	let holding_change = create_holding_asset(CLIENT_ASSET, client_asset_total - fee);
	let refund_asset = create_holding_asset(CLIENT_ASSET, refund1);

	let target_total = Fungibles::total_issuance(TARGET_ASSET);
	let client_total = Fungibles::total_issuance(CLIENT_ASSET);

	let mut trader = Trader::new();
	let change = trader.buy_weight(weight_worth_of(fee), holding_asset, &xcm_context()).unwrap();
	assert_eq!(&change, &holding_change);

	assert_eq!(trader.total_fee.peek(), fee);
	assert_eq!(trader.last_fee_asset, Some(create_asset_id(CLIENT_ASSET)));

	let refund = trader.refund_weight(weight_worth_of(refund1), &xcm_context());
	assert_eq!(refund.as_ref(), Some(&refund_asset));

	assert_eq!(trader.total_fee.peek(), fee - refund1);
	assert_eq!(trader.last_fee_asset, Some(create_asset_id(CLIENT_ASSET)));

	assert_eq!(trader.refund_weight(weight_worth_of(refund2), &xcm_context()), None);

	assert_eq!(trader.total_fee.peek(), fee - refund1);
	assert_eq!(trader.last_fee_asset, Some(create_asset_id(CLIENT_ASSET)));

	assert_eq!(Fungibles::total_issuance(TARGET_ASSET), target_total);
	assert_eq!(Fungibles::total_issuance(CLIENT_ASSET), client_total);
}
