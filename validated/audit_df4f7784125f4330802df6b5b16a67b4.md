### No Vulnerability found for this question.

**Rationale:** The domain separation between V1 and V2 delegate action signatures is already enforced correctly. `SignableMessageType::DelegateAction` and `SignableMessageType::DelegateActionV2` map to distinct `MessageDiscriminant` values (`NEP_366_META_TRANSACTIONS` = 366 vs `NEP_611_GAS_KEYS` = 611) via `From<SignableMessageType> for MessageDiscriminant` [1](#0-0) . This discriminant is embedded as the first field of `SignableMessage<T>`, which is borsh-serialized and hashed before signing/verification in both `DelegateAction::get_nep461_hash` and `VersionedDelegateActionPayload::get_nep461_hash` [2](#0-1) [3](#0-2) .

Because the discriminant differs between the two message types, the hash preimage (and thus the signed hash) is different for V1 vs V2, so a signature produced under the V1 domain tag will not verify against a V2-tagged hash, and vice versa — the underlying ed25519 signature scheme guarantees this since `Signature::verify` checks the signature against the exact hash bytes passed in [4](#0-3) .

This is explicitly covered by an existing unit test, `test_signed_delegate_action_v2_verify`, which constructs a V1-tagged signature (`SignableMessageType::DelegateAction`) over a `DelegateActionV2` payload and asserts that `VersionedSignedDelegateAction::verify()` returns `false` [5](#0-4) . Additional coverage in `signable_message.rs` (`nep_366_wrong_nep`, `nep_366_wrong_msg_type`) confirms that any discriminant mismatch causes verification failure [6](#0-5) .

There is no code path where an attacker-supplied `VersionedSignedDelegateAction` with a cross-domain signature would pass `verify()`.
