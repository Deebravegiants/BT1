### Title
Webhook shop-domain identity spoofing via unauthenticated header (HMAC does not cover the shop binding) - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `hmac` verification exclusively over the raw request body, while the `shop` identity that the rest of the pipeline treats as the tenant of that verified payload is read from an unauthenticated HTTP header. This breaks the equality that should hold between "the payload the HMAC verifies" and "the tenant the framework attributes that payload to," allowing a replayed/forged webhook request to be processed under an attacker-chosen shop identity while still passing HMAC validation.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing `hmac` against `HMAC-SHA256(secret, to_signable_string)` [1](#0-0) .

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `shop` is pulled from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is **not** part of the signed string: [2](#0-1) 

`Webhooks::Registry.process` validates only the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler: [3](#0-2) 

The broken identity binding, stated as an equality that should hold but doesn't:

`shop_bound_by_hmac(raw_body) == shop_used_by_handler(request.shop_header)`

is false: `to_signable_string` depends only on `raw_body`, so the HMAC is invariant under changes to the `shopify-shop-domain` header. Any request whose `(raw_body, hmac)` pair is valid for the app's `api_secret_key` — which is a single, app-wide secret shared across every shop that has installed the app, not a per-shop secret — will pass `HmacValidator.validate` regardless of what `shop`-domain header accompanies it.

### Impact Explanation
Because the `api_secret_key` is one shared secret for the whole app (every merchant's webhook deliveries are signed with the same key), a merchant who has installed the app on their own store can capture one legitimate `(raw_body, hmac)` pair from a webhook Shopify sent them, then replay that exact body/HMAC to the app's own webhook endpoint with the `shopify-shop-domain` header (and optionally `shopify-webhook-id`/`shopify-topic`, also unauthenticated) rewritten to a victim shop's domain. `Registry.process` will accept it as authentic and dispatch `WebhookMetadata` carrying the attacker-chosen `shop` to the host application's handler. Depending on how a host app uses this trusted `shop` value (e.g. `app/uninstalled` clearing sessions, GDPR `customers/redact` or `shop/redact` processing, order/customer data ingestion keyed by shop), this allows cross-tenant data corruption or cross-tenant actions attributable to a shop that never sent the webhook — a direct violation of tenant isolation guaranteed by "the gem verified this payload for shop X."

### Likelihood Explanation
Exploitation requires only an unprivileged step available to anyone: installing the target app on one's own (attacker-controlled) shop to receive at least one real webhook, then replaying it with a modified header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed — the attacker never learns the secret, they only reuse a signature that the gem fails to bind to the shop identity it later trusts.

### Recommendation
Include the shop domain (and ideally webhook id / topic) in the signed payload used for verification, or otherwise cryptographically bind the shop identity to the HMAC-verified request before it is trusted downstream — e.g., extend `to_signable_string` to incorporate `shop`/`topic`/`webhook_id`, or require the host application to independently verify that `request.shop` corresponds to a shop with a stored, valid session/access token for this app before processing the payload.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a real delivered webhook: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay to the app's webhook endpoint:
```
POST /webhooks
X-Shopify-Topic: app/uninstalled
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com   <-- attacker-controlled, unauthenticated
X-Shopify-Webhook-Id: <any>

<body B, unmodified>
```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `B` [4](#0-3) .
4. `Registry.process` dispatches `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...))` [5](#0-4) , causing the host application to act on webhook content it believes is authentically bound to `victim-shop.myshopify.com`, even though it originated from the attacker's own shop.
