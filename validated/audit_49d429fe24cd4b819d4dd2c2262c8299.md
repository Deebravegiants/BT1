### Title
Missing set-once guard lets the owner re-point `HyperbridgeLzEndpoint._host`, resetting relayer-fee configuration and diverging the LZ↔ISMP bridge from its peer chains - ([File: sdk/packages/lz-endpoint/contracts/HyperbridgeLzEndpoint.sol])

### Summary
`HyperbridgeLzEndpoint.setHost()` is documented and structurally intended as a one-time configuration call (it wires the ISMP host and computes `_defaultRelayerFee` from that host's fee token) but carries no guard against being invoked again, unlike the codebase's own established pattern for the identical problem.

### Finding Description
`setHost` sets `_host`, `_eid`, and derives `_defaultRelayerFee` from `IDispatcher(hostAddr).feeToken()`: [1](#0-0) 

There is no check such as `if (_host != address(0)) revert` before overwriting `_host`. This is precisely the bug class in the external report — a function that is meant to run once but has no guard against repeated invocation by its authorized caller. The codebase itself recognizes this exact risk and fixes it everywhere else that a similar "bind once" setter exists:

- `BandwidthManager.setHost()` explicitly reverts if `_host` is already set: [2](#0-1) 
- `HostManager.init()` reverts with `AlreadyInitialized` if `_params.host != address(0)`, with NatSpec explicitly warning that a repeatable init "would let that key cut the host off from its own governance": [3](#0-2) 
- `EvmHost.setConsensusState()` is gated by `_canReinitConsensus()` so it can only run once on mainnet hosts: [4](#0-3) 

`HyperbridgeLzEndpoint` is missing the equivalent guard on its own host-binding setter, even though the same architectural concern applies: `_host` is the trust anchor for the entire contract — `host()` returns it and gates every `onlyHost`-protected callback (`onAccept`, `onPostRequestTimeout`), and `_eid` (the "local endpoint ID", used to build the `guid` and validate `srcEid` on every inbound message) is bound together with it in the same call.

### Impact Explanation
If `setHost` is called a second time (accidentally, by a mistaken owner action, by a multisig replay, or by a script re-run), it silently re-points `_host` and `_eid` and recomputes `_defaultRelayerFee`, without any events, without checking that the new host's fee token still matches assumptions made elsewhere (`lzToken()` reads `IDispatcher(_host).feeToken()` live, but `_defaultRelayerFee` is cached in decimals of whatever `feeToken` was active at last `setHost` call), and without accounting for in-flight outbound/inbound nonces still tracked under the old `_eid`. A repointed `_host`/`_eid` breaks the deterministic `guid` computation (which embeds `_eid`) and can desynchronize the contract's expected inbound `srcEid` used in `onAccept`'s `UnknownSource` check, effectively bricking message delivery from every previously configured peer chain until `setEidMapping` is redone for all EIDs, and potentially misconfiguring relayer fees so future dispatches are underpriced or overpriced relative to the actual host's fee token decimals.

### Likelihood Explanation
Low but non-zero: `setHost` is `onlyOwner`, so exploitation requires the same privilege level flagged as the trigger in the original report — not malice, but the absence of a safety rail against an authorized party calling it twice (deployment script re-run, governance replay, multisig double-execution). Given that every other host-binding setter in this same codebase (`BandwidthManager.setHost`, `HostManager.init`, `EvmHost.setConsensusState`) was deliberately hardened against exactly this scenario, its absence here is an inconsistency/omission rather than a deliberate design choice.

### Recommendation
Add a one-shot guard to `setHost`, mirroring `BandwidthManager.setHost`:
```solidity
function setHost(address hostAddr, uint32 localEid) external onlyOwner {
    if (_host != address(0)) revert UnauthorizedAction(); // or a dedicated AlreadyInitialized error
    _host = hostAddr;
    _eid = localEid;
    ...
}
```
If re-pointing the host is intentionally needed for migrations, gate it behind an explicit, separately named `migrateHost()` function with its own safety checks (e.g., re-registering all EID mappings, resetting nonces consistently), rather than allowing silent reuse of `setHost`.

### Proof of Concept
1. Owner deploys `HyperbridgeLzEndpoint` and calls `setHost(hostA, eidA)`; contract operates normally, peers registered via `setEidMapping`, messages flow with `_eid = eidA`.
2. Owner (or a compromised/careless governance multisig, or a re-run deployment script) calls `setHost(hostB, eidB)` again.
3. `_host` and `_eid` are silently overwritten; `_defaultRelayerFee` is recomputed against `hostB`'s fee token decimals.
4. All previously computed/expected `guid`s (which embed `_eid`) and inbound nonce/EID checks in `onAccept` (`expectedEid = _stateMachineToEid[keccak256(request.source)]`, checked against `srcEid`) are now inconsistent with the new `_eid`/`_host`, breaking delivery for every peer configured under the old host/eid until manual reconfiguration, and no event is emitted to alert integrators of the change (contrast with `BridgeToken.setRelayer` and `SimplexPaymaster._setRelayer`, which both emit `RelayerUpdated`).

```text
    /**
     * @notice Configures the ISMP host address and local endpoint ID
     * @param hostAddr The ISMP host contract address
     * @param localEid The LayerZero endpoint ID for this chain
     */
    function setHost(address hostAddr, uint32 localEid) external onlyOwner {
        _host = hostAddr;
        _eid = localEid;

        // Set default relayer fee to $0.30 based on feeToken decimals
        address feeToken = IDispatcher(hostAddr).feeToken();
        uint8 decimals = IERC20Metadata(feeToken).decimals();
        _defaultRelayerFee = (3 * 10 ** decimals) / 10; // 0.30
    }
```
