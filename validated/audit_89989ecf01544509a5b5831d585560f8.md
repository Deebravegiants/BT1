### Title
Webhook processing trusts the `shop`, `topic`, `webhook_id`, and `api_version` headers without HMAC coverage, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `Utils::HmacValidator` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Webhooks::Registry.process` nevertheless takes `request.shop` and `request.topic` straight from these unauthenticated headers and hands them to the app's handler as the tenant identity for the event. This is the same "field acted on ≠ field bound by the signature" defect pattern as the fee-on-transfer report: the value used to act (fee actually deducted / shop identity used) diverges from the value that was actually verified (transfer amount / signed bytes).

### Finding Description
`Webhooks::Request#to_signable_string` binds the HMAC to `@raw_body` only: [1](#0-0) 

`Webhooks::Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read directly from HTTP headers and are never part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` only re-computes the HMAC over `verifiable_query.to_signable_string`, i.e. over the body, and secure-compares it to the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` validates that HMAC, then immediately trusts `request.topic` and `request.shop` (unauthenticated headers) to build the `WebhookMetadata` delivered to the app's handler: [4](#0-3) 

The identity binding this breaks, stated as an equality that should hold but doesn't:
`shop authenticated by HMAC (over @raw_body only)` ≠ `shop the handler is told the event belongs to (request.shop header)`.

Because the HMAC is computed with the app's single `api_secret_key` regardless of which shop the body/topic came from, any party who can obtain one legitimately-signed `(body, hmac)` pair for the app — e.g., a merchant who installs the app on their own store and receives an ordinary webhook, or triggers a webhook themselves (e.g., `customers/redact`, `orders/create` on their own shop) — can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header for a different, victim shop. `Registry.process` will accept it as valid (the HMAC still matches the untouched body) and dispatch it to the handler labeled with the attacker-chosen `shop`.

### Impact Explanation
This lets an unprivileged app user (a merchant who has installed the app, hence not requiring the app's `client_secret`, an access token, or any privileged account beyond normal self-service installation) forge webhook events attributed to another tenant's shop domain. If the host application's webhook handler uses `WebhookMetadata#shop` to look up/act on shop-specific session or data (as is the documented pattern, matching `shop: request.shop` in `WebhookMetadata.new`), this constitutes cross-tenant access/confusion — one merchant can cause the app to process fabricated events as if they came from a different merchant's shop.

### Likelihood Explanation
Exploitation requires only: (1) being an app user who can obtain at least one legitimately HMAC-signed webhook body (trivial — any merchant with the app installed receives these routinely, or can trigger self-serve topics), and (2) sending a raw HTTP POST to the app's public webhook endpoint with a modified `shop-domain`/`topic` header and the captured, unmodified body+HMAC. No secrets or elevated privileges are needed, and the gem provides no header-binding to prevent it.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material (or otherwise cryptographically bind them to the body), so `Utils::HmacValidator.validate` fails if any of these are altered relative to what Shopify actually sent. At minimum, document and/or add an option so `Registry.process` cross-checks that `request.shop` corresponds to the tenant/session the app expects rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the app on their own shop (`attacker-shop.myshopify.com`) and captures a legitimate webhook delivery: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with the same raw body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`to_signable_string`), which still matches `H`, so validation passes: [5](#0-4) 
4. `Registry.process` dispatches to the app's handler with `shop: "victim-shop.myshopify.com"`, even though that shop never sent this request, letting the attacker forge cross-tenant webhook events.
