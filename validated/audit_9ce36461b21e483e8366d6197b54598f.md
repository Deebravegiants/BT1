### Title
Unbounded ancestry walk in GRANDPA `AncestryChain::ancestry` allows an attacker-crafted header cycle to hang consensus-message execution before signature verification - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` walks parent hashes from `block` back to `base` with no bound on iteration count and no cycle detection. The header set it walks (`finality_proof.unknown_headers`) is fully attacker-controlled and is *not* cryptographically validated until after this walk completes. An adversary can submit two (or more) headers whose `parent_hash` fields point at each other, forming a cycle that never reaches `base`, causing the `while current_hash != base` loop to run forever (and `route.push` to grow unboundedly), exactly the missing-input-validation-leads-to-infinite-loop pattern in CVE-2017-12852.

### Finding Description
`AncestryChain::ancestry` in [1](#0-0)  builds `route` by repeatedly looking up `current_hash` in a `BTreeMap` built directly from the submitted `unknown_headers` and following `parent_hash()` until `current_hash == base`. There is no limit on the number of hops and no set of "visited" hashes to detect a cycle. Since `unknown_headers` is attacker-supplied SCALE-decoded data (not chain-validated headers), an attacker can construct headers `H1` and `H2` with `H1.parent_hash == hash(H2)` and `H2.parent_hash == hash(H1)`, and set `base` to a hash never reached by this cycle.

Critically, `verify_grandpa_finality_proof` in [2](#0-1)  calls `headers.ancestry(base.hash(), consensus_state.latest_hash)` and `headers.ancestry(from, target.hash())` **before** `justification.verify(...)` runs — i.e., before any BLS/Ed25519 GRANDPA signature check. The same unguarded pattern is repeated for parachain headers and fraud-proof handling in `modules/ismp/clients/grandpa/src/consensus.rs` (lines 286-320), which is reachable via `ConsensusMessage::Polkadot`, `ConsensusMessage::Relaychain`, and `ConsensusMessage::StandaloneChain`.

This is reachable from `pallet_ismp::Call::handle_unsigned`, an unsigned, unprivileged extrinsic documented as executable by anyone with a syntactically valid proof ( [3](#0-2) ). Worse, `validate_unsigned` (used by every full node's transaction-pool validation, executed on p2p gossip *before* block inclusion) also calls `Self::execute(messages.clone())` ( [4](#0-3) ), so the infinite loop can be triggered on every node that merely receives the gossiped extrinsic, not just a block author.

### Impact Explanation
An attacker with no privileges can submit a single unsigned extrinsic carrying a GRANDPA `ConsensusMessage` whose `unknown_headers` contain a parent-hash cycle. This hangs `handle_unsigned` validation/execution before any cryptographic check succeeds, since `ancestry()` never returns. Depending on runtime weight metering around this specific loop, this can stall block execution/import and transaction-pool validation on any node processing the extrinsic, halting the GRANDPA consensus-client route entirely — i.e., "a route unable to deliver messages," which is within the explicit scope of acceptable impact for this analog.

### Likelihood Explanation
High. Crafting two headers with reciprocal `parent_hash` values requires no cryptographic material and no prior trust — headers are freely constructible SCALE-encoded structs, and the loop executes prior to authority-signature verification, so no valid GRANDPA justification or authority key is needed to trigger it.

### Recommendation
Bound `AncestryChain::ancestry`'s walk to at most `self.ancestry.len()` hops (or track visited hashes in a `BTreeSet`) and return `Err(NotDescendent)` once the bound is exceeded, mirroring the fixes already applied elsewhere in this codebase for attacker-controlled unbounded/empty-input loops (e.g., the `MAX_PROOF_DEPTH` guard in `modules/consensus/pharos/primitives/src/spv.rs` and the `leaf_indices.len() != 1` check in `modules/consensus/beefy/verifier/src/lib.rs`).

### Proof of Concept
1. Craft two headers `H1`, `H2` (arbitrary `number`, `state_root`, `extrinsics_root`, `digest`) such that `H1.parent_hash = Header::hash(&H2)` and `H2.parent_hash = Header::hash(&H1)`.
2. Set `finality_proof.unknown_headers = vec![H1, H2]`, `finality_proof.block = hash(H1)` (the higher-numbered of the two, satisfying `target`), and any well-formed (but not necessarily validly-signed) `GrandpaJustification` whose `commit.target_hash == hash(H1)`.
3. Set `consensus_state.latest_hash` to any hash not equal to `hash(H1)` or `hash(H2)` (trivially true for a freshly initialized or unrelated consensus state).
4. Wrap this into `ConsensusMessage::StandaloneChain` (or `Polkadot`/`Relaychain`), encode as the `proof` for `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(...)] }`, and submit as an unsigned extrinsic.
5. `verify_grandpa_finality_proof` calls `headers.ancestry(from, target.hash())` at [5](#0-4) , which enters `AncestryChain::ancestry` and loops forever alternating between `hash(H1)` and `hash(H2)`, since neither equals `from` and both are present in the map — reproducing the CVE-2017-12852 missing-validation infinite-loop pattern in a live consensus-verification path.
