### Title
Improper Authentication of Relayer Identity via Unverified `Signature::signer()` in Substrate Fee/Reward Attribution - (File: modules/pallets/relayer/src/accumulate.rs)

### Summary
`decode_receipt_relayer` decodes the value found at a proven `RequestReceipts[commitment]` storage slot on a substrate destination. When that value is a `Signature` blob (len > 32), it calls `.signer()` [1](#0-0)  which returns the embedded `public_key`/`address` field of the `Signature` enum directly, with no call to `Signature::verify()` [2](#0-1) . The identity used for fee attribution and reward payout is therefore whatever public key an attacker chooses to embed in that byte blob, without ever proving possession of the corresponding private key — the same class of bug as CVE-2019-12405, where an identity claim is accepted without verifying the credential that should back it.

### Finding Description
`StateMachineClient::receipts_state_trie_key`/`verify_state_proof` prove that a raw byte string exists at the destination's `RequestReceipts[commitment]` slot [3](#0-2) . This raw value is whatever the destination chain's ISMP request handler wrote as `signer` when it delivered the request — see `host.store_request_receipt(&wrapped_req, &msg.signer)` in the request handler [4](#0-3) , and `msg.signer` on `RequestMessage`/`Message::Request` is attacker-controlled arbitrary bytes supplied by whoever submits the unsigned `handle_unsigned` extrinsic delivering the message (see the `signer: signature.encode()` field freely constructed in the simtest harness) [5](#0-4) .

`decode_receipt_relayer` then decodes that arbitrary byte blob back into a `Signature` and, for substrate destinations, calls `.signer()` on it to get the "delivering relayer" identity that both:
1. Fee accumulation (`accumulate`) credits with the source-side fee amount for that commitment [6](#0-5) , and
2. `OutboundRequestDeliveryClaim` compares against the claim's `signature.verify(...)` result to authorize a treasury payout [7](#0-6) .

`Signature::signer()` is a plain match returning the enum's embedded `public_key`/`address` field [2](#0-1)  — it performs **no** cryptographic check (`ed25519_verify`, `sr25519_verify`, `secp256k1_ecdsa_recover`) that this public key ever signed anything. Contrast this with `Signature::verify()`, which requires a valid signature over a specific message before returning an identity [8](#0-7) .

Because the substrate destination itself is the one writing `RequestReceipts[commitment] = msg.signer` at message-delivery time, and `msg.signer` is entirely relayer-supplied (any bytes encode into a `Signature::Sr25519 { public_key, signature }` regardless of validity), an attacker can:
1. Submit a `handle_unsigned` `RequestMessage` for a request they relay, setting `signer` to a SCALE-encoded `Signature::Sr25519 { public_key: <victim_or_arbitrary_pubkey>, signature: <garbage> }` (any `Vec<u8>` decodes fine; the receipt-write path never validates the signature).
2. Later, submit `accumulate_fees`/`claim_outbound_request_delivery_reward` with a genuine state proof of that receipt slot. `decode_receipt_relayer` decodes the blob and returns `public_key` as the "delivering relayer" with zero cryptographic verification that this key actually delivered anything or that its holder authorized the claim.
3. Fees or outbound-request rewards get attributed to/paid toward whatever address the attacker embedded, or — combined with the `claim_outbound_request_delivery_reward` flow which requires a matching `signature.verify()` from the *claimant* — the attacker can set the embedded `public_key` to their own key, guaranteeing the "proven" delivery address always equals a key they control, sidestepping the intent that this address reflects the entity that genuinely executed the on-chain delivery.

### Impact Explanation
This breaks the authentication invariant that relayer-fee and reward accounting is tied to the account that cryptographically proved it performed the delivery. An attacker can fabricate the "delivering relayer" identity recorded in `RequestReceipts` for substrate destinations, then direct `Fees` accumulation (`modules/pallets/relayer/src/lib.rs` `Fees` map) or `OutboundRequestDeliveryReward` treasury payouts to an address of their choosing without ever needing a valid signature from that address for the actual delivery event. This is theft of relayer fees / reward funds — a substrate-destination-only bypass of the delivery-attribution authentication.

### Likelihood Explanation
High for any deployment routing ISMP messages to substrate destinations that use `pallet-ismp`'s generic child-trie state machine and where `msg.signer` for `Message::Request` is set by the unsigned relayer transaction rather than independently cryptographically enforced at delivery time. Any unprivileged party that can submit `handle_unsigned` with a `RequestMessage` (or otherwise get a request delivered) controls the `signer` bytes written to `RequestReceipts`, making exploitation reachable from a single unsigned extrinsic plus a subsequent unsigned `accumulate_fees`/`claim_outbound_request_delivery_reward` call.

### Recommendation
`decode_receipt_relayer`'s substrate branch must not treat `Signature::signer()` as a proven identity. Either (a) stop accepting a raw `Signature` blob as the receipt value and instead have the destination's delivery handler independently authenticate/record the delivering account (e.g., derived from `frame_system::ensure_signed` or an actually-verified signature at delivery time, not caller-chosen bytes), or (b) if a `Signature` must be decoded from the receipt, require `Signature::verify()` against the well-defined delivery message (not just `.signer()`) before trusting the recovered key, mirroring the pattern already used correctly in `outbound_request.rs`/`withdrawal.rs` and in `EvmHost`'s `msg.sender`-derived attribution.

### Proof of Concept
1. Attacker crafts `Message::Request(RequestMessage { requests: [post], proof, signer: Signature::Sr25519 { public_key: ATTACKER_KEY, signature: [0u8;64] }.encode() })` and submits via `Ismp::handle_unsigned` to a substrate destination — `store_request_receipt` writes these attacker-chosen bytes into `RequestReceipts[commitment]` with no signature validation [4](#0-3) .
2. Attacker (or any relayer) later submits `Relayer::accumulate` / `claim_outbound_request_delivery_reward` with a genuine state proof of that `RequestReceipts` slot.
3. `decode_receipt_relayer` decodes the blob, sees length > 32, and returns `Signature::Sr25519{ public_key: ATTACKER_KEY, .. }.signer()` = `ATTACKER_KEY` [1](#0-0)  — accepted as the "delivering relayer" with no check that a valid Sr25519 signature was ever produced.
4. Fees for the commitment accumulate to `ATTACKER_KEY` [9](#0-8) , which the attacker then withdraws via `withdraw()`, which *does* verify a proper signature (over the withdrawal message) but is signed by the same attacker key they seeded in step 1 — completing the theft with no actual delivery-authentication check ever having been satisfied at attribution time.

	pub fn verify(
		&self,
		msg: &[u8; 32],
		public_key_op: Option<Vec<u8>>,
	) -> Result<Vec<u8>, anyhow::Error> {
		match self {
			Signature::Evm { signature, .. } => {
				if signature.len() != 65 {
					Err(anyhow!("Invalid Signature"))?
				}

				let mut sig = [0u8; 65];
				sig.copy_from_slice(&signature);
				let pub_key = sp_io::crypto::secp256k1_ecdsa_recover(&sig, msg)
					.map_err(|_| anyhow!("Signature Verification failed"))?;
				let signer = sp_io::hashing::keccak_256(&pub_key[..])[12..].to_vec();
				Ok(signer)
			},
			Signature::Sr25519 { signature, public_key } => {
				Self::verify_sr25519(signature, public_key, msg, &public_key_op)?;
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
			Signature::Ed25519 { signature, public_key, .. } => {
				let signature =
					signature.as_slice().try_into().map_err(|_| anyhow!("Invalid Signature"))?;
				let pub_key = public_key_op
					.clone()
					.unwrap_or(public_key.clone())
					.as_slice()
					.try_into()
					.map_err(|_| anyhow!("Invalid Public Key"))?;
				if !sp_io::crypto::ed25519_verify(&signature, msg, &pub_key) {
					Err(anyhow!("Signature Verification failed"))?
				}
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},
		}

	fn verify_state_proof(
		&self,
		_host: &dyn IsmpHost,
		keys: Vec<Vec<u8>>,
		root: H256,
		proof: &Proof,
	) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
		// The trie root is supplied by the caller, bound to the calling context, so a relayer
		// cannot steer verification at the wrong trie.
		let StateMachineProof { hasher, storage_proof } =
			codec::Decode::decode(&mut &*proof.proof)
				.map_err(SubstrateStateMachineError::ProofDecodeError)?;
		let data = match hasher {
			HashAlgorithm::Keccak => {
				let db = StorageProof::new(storage_proof).into_memory_db::<Keccak256>();
				let trie = TrieDBBuilder::<LayoutV0<Keccak256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?
			},
			HashAlgorithm::Blake2 => {
				let db = StorageProof::new(storage_proof).into_memory_db::<BlakeTwo256>();
				let trie = TrieDBBuilder::<LayoutV0<BlakeTwo256>>::new(&db, &root).build();
				keys.into_iter()
					.map(|key| {
						let value = trie
							.get(&key)
							.map_err(|e| SubstrateStateMachineError::TrieError(format!("{e:?}")))?;
						Ok::<_, SubstrateStateMachineError>((key, value))
					})
					.collect::<Result<BTreeMap<_, _>, _>>()?
			},
		};

		Ok(data)
	}
}
