### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body against `Context.api_secret_key`, but the `shop` (and `topic`, `webhook_id`) values that the handler trusts and acts on are read from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw JSON body: [1](#0-0) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (the body) and compares it with the `hmac` header using a constant-time comparison — it never binds any header value: [4](#0-3) [5](#0-4) 

`WebhookMetadata.shop` is a plain `T::Struct` field with no further validation, consumed directly by the app-supplied `WebhookHandler#handle`: [6](#0-5) 

**Identity binding broken as an equality:** the shop that the HMAC secret was computed to authenticate is `body` only, while the shop the handler acts on is `request.shop` (the `X-Shopify-Shop-Domain` header). The gem implicitly claims `hmac_authenticated_source == header_shop`, but nothing enforces this — `to_signable_string ⊄ {shop, topic, webhook_id}`.

This differs from the OAuth `AuthQuery`, where `shop` *is* included in `to_signable_string` and thus bound by the HMAC: [7](#0-6) 

**Before/after the attacker's request:**
- Before: A multi-tenant app installed on both shop A (attacker-controlled) and shop B (victim) receives real webhooks from Shopify for shop A, each with a valid `(body, hmac)` pair computed by Shopify using the app's shared `client_secret`.
- Attack: The attacker (a legitimate but malicious merchant of shop A, i.e., an unprivileged party with respect to shop B) captures one such `(body, hmac)` pair and replays it to the app's webhook endpoint, only changing the `X-Shopify-Shop-Domain` header to `shop-b.myshopify.com` (and optionally the `topic`/`webhook-id` headers).
- After: `HmacValidator.validate` still passes because the signature only covers `body`, which is untouched. `Registry.process` then dispatches `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` to the handler, which believes the event genuinely originated from shop B.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability: an attacker who legitimately controls one tenant of a multi-tenant app can forge webhook events "from" any other tenant shop, without needing `client_secret`, an access token, or any credential belonging to the victim. Depending on how the app's `WebhookHandler` implementation uses `data.shop` (e.g., to look up/update per-shop state, trigger uninstall/redact flows such as `shop/redact`, or write to a per-tenant database record), this can lead to cross-tenant data corruption, spoofed mandatory GDPR webhooks, or triggering shop-scoped side effects (e.g., disabling access, deleting data) for a shop the attacker doesn't own. This matches the Critical "cross-tenant access" bucket, since the trust boundary between tenants of the same app is broken purely through this gem's own verification logic.

### Likelihood Explanation
Likely to be exploitable in any host app that is multi-tenant (i.e., the common case for a Shopify app used by many merchants) and whose `WebhookHandler` implementations key off `WebhookMetadata#shop` for tenant-scoped logic — which is the pattern shown in this gem's own webhook documentation and test suite (`data.shop` used directly by handlers). The attacker only needs to be a merchant who has installed the app themselves (an "unprivileged internet user" relative to any other tenant) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a captured body/HMAC pair and forged headers — no special network position or secret material is required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed payload (or otherwise bind the header-derived shop identity to the signed body, e.g., by having `to_signable_string` incorporate a canonical representation of these header fields alongside the body) so `HmacValidator.validate` can detect any header tampering or webhook replay against a different tenant.

### Proof of Concept
1. App is installed on shop A (attacker) and shop B (victim), sharing one `client_secret`.
2. Attacker captures a real webhook delivery to their own endpoint for shop A:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid_hmac_for_body>
   X-Shopify-Shop-Domain: shop-a.myshopify.com
   X-Shopify-Webhook-Id: <id>

   {"id": 1, ...}
   ```
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value, but changes the header:
   ```
   X-Shopify-Shop-Domain: shop-b.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the unmodified body against the unmodified HMAC: [8](#0-7) 
5. `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)` is dispatched to the app's handler, spoofing an event as originating from shop B.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
