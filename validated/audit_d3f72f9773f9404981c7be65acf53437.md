### Title
Webhook shop identity spoofing via unsigned `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the `shop-domain` value taken from an HTTP header — which is not covered by that HMAC — into the handler as the authoritative tenant identity for the payload.

### Finding Description
`Webhooks::Registry.process` validates a webhook exclusively with `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` for the signed bytes: [1](#0-0) 

`Webhooks::Request#to_signable_string` returns only `@raw_body`; the `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors are all derived from HTTP headers that are outside the HMAC-signed content: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only proves that `@raw_body` was produced with the app's `client_secret` — it says nothing about which shop, topic, or webhook-id header accompanied that body: [3](#0-2) 

After the HMAC check passes, `process` builds `WebhookMetadata` directly from the unauthenticated `request.shop` header and hands it to the app's handler as the tenant identity for the payload: [1](#0-0) 

**Binding broken (as an equality that should hold but doesn't):**
`shop authenticated-by-HMAC == shop delivered to handler as WebhookMetadata#shop`

Before the attacker's action: for a legitimately delivered webhook, `raw_body` and the `x-shopify-shop-domain` header both originate from Shopify for the same shop, so the equality happens to hold.

After the attacker's action: any party that possesses one valid `(raw_body, hmac)` pair signed with the app's `client_secret` — e.g. a merchant who installed the app and can observe/capture a legitimate webhook delivered to their own endpoint for their own shop — can resend the identical `raw_body`/`hmac` pair while substituting an arbitrary `x-shopify-shop-domain` header value. `Utils::HmacValidator.validate` still returns `true` because the signed bytes (`@raw_body`) are unchanged, but `WebhookMetadata#shop` (and thus whatever per-tenant record the host application keys off of) now reflects the attacker-chosen shop rather than the shop that actually owns the signed payload.

### Impact Explanation
This breaks the shop-identity binding the gem is trusted to guarantee to host applications: the documented contract is "if the webhook validates, `data.shop` is the shop that sent it." An attacker with legitimate but low-privilege access (any merchant with the app installed who has visibility into their own webhook deliveries) can cause the handler to process a valid-looking payload under a victim shop's identity, letting them write/update data keyed by `data.shop` for another tenant — a cross-tenant impact without needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Requires only: (1) the app is installed on at least one shop controlled by the attacker (a normal unprivileged capability), (2) the attacker can capture/replay one webhook delivery they legitimately receive, and (3) the host application trusts `WebhookMetadata#shop` from this gem to select the tenant record to act on — which is exactly how the documented webhook-handling flow is meant to be used. No cryptographic secret needs to be recovered; only reuse of a header field that the signature never covered.

### Recommendation
Include the shop-domain (and ideally the topic/webhook-id) inside the HMAC-signed material, or independently verify that the `x-shopify-shop-domain` header corresponds to a shop with an active session/installation known to the app before trusting it as the payload's tenant identity in `Webhooks::Registry.process` / `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers/observes a webhook for a topic they control, capturing the exact `raw_body` and `x-shopify-hmac-sha256` value Shopify sent them.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the identical `raw_body` and `hmac` header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the secret [4](#0-3) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` [5](#0-4) , and the host application's handler processes the attacker's payload as if it belonged to the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
