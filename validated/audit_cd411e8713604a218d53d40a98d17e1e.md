## Title
Reward-per-token griefing via block-by-block resets causes permanent loss of `pallet-asset-rewards` rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s reward accrual math (`reward_per_token`) computes an incremental reward-per-share value that is divided by `total_tokens_staked` and scaled only by a small constant (`PRECISION_SCALING_FACTOR = 4096`). Any unprivileged staker can call a rewards-updating extrinsic (`stake`, `unstake`, or `harvest_rewards`) every block, forcing `last_update_block` to reset each time so that the elapsed-block window used in the reward computation is always `1`. When `reward_rate_per_block * 1 * 4096 < total_tokens_staked`, the computed increment rounds down to zero, so `reward_per_token_stored` never advances while the attacker keeps calling. This is the same integer-division rounding-to-zero griefing pattern described in the referenced Sherlock report (`VaultRewarderLib.sol`'s `_getAccumulatedRewardViaEmissionRate`), applied to this pallet's Synthetix-style accumulator.

## Finding Description
The core vulnerable computation is: [1](#0-0) 

```rust

    pool_info: &PoolInfoFor<T>,
) -> Result<T::Balance, DispatchError> {
    if pool_info.total_tokens_staked.is_zero() {
        return Ok(pool_info.reward_per_token_stored);
    }
    let rewardable_blocks_elapsed: u32 = ...;
    Ok(pool_info.reward_per_token_stored.ensure_add(
        pool_info
            .reward_rate_per_block
            .ensure_mul(rewardable_blocks_elapsed.into())?
            .ensure_mul(PRECISION_SCALING_FACTOR.into())?
            .ensure_div(pool_info.total_tokens_staked)?,
    )?)
}
```

with the scaling factor defined as a tiny constant: [2](#0-1) 

`update_pool_rewards` unconditionally sets `last_update_block` to the current block every time it is invoked, regardless of whether the accumulated increment was zero: [3](#0-2) 

Any signed account that has joined the pool (even with a minimal stake) can permissionlessly trigger this update path once per block via `stake`, `unstake`, or `harvest_rewards` (the latter is callable by the staker themselves with no extra permission check before pool expiry): [4](#0-3) [5](#0-4) 

Because `rewardable_blocks_elapsed` is reset to `1` on every call, and `PRECISION_SCALING_FACTOR` is only `4096` (vs. `1e8`/`1e18` in comparable reward-accounting systems), the rounding-to-zero condition `reward_rate_per_block * 4096 < total_tokens_staked` is trivially satisfiable for any pool with meaningful TVL relative to its emission rate — far easier to trigger than in the referenced report. Since `reward_per_token_stored` is a single pool-wide value (not per-staker), a griefer freezing it affects **every** staker in the pool, not just themselves.

## Impact Explanation
While the griefer's calls keep `reward_per_token_stored` pinned, no staker in the pool accrues any reward share, even though the pool continues to burn through its bounded active window (`expiry_block`). `last_block_reward_applicable` caps accrual at `expiry_block`, and once that block passes, `reward_per_token` simply returns the stored (frozen) value forever — the reward accounting for that period is permanently and irrecoverably lost for all pool participants, not merely delayed. The pool's admin can later reclaim the pool's leftover reward balance via `cleanup_pool`, but honest stakers who should have earned during the griefed window never receive it. This is a definite loss of funds/rewards affecting an unbounded number of legitimate users, with no extensive preconditions beyond the attacker being any signed account that has staked in the pool.

## Likelihood Explanation
The attack requires only an ordinary signed account to `stake` a nominal amount into the target pool once, and thereafter call `unstake(0)`/`stake(0)`/`harvest_rewards` (all permissionless self-actions, no special origin) every block. Any parachain/relay chain runtime with low per-block extrinsic fees (analogous to the L2 low-fee condition in the original report) makes this economically feasible, especially against pools with high `total_tokens_staked` relative to `reward_rate_per_block` — a condition that becomes easier to trigger as the pool's popularity/TVL grows, exactly mirroring the growth argument in the original report.

## Recommendation
- Accumulate reward-per-token progress using higher internal precision (e.g., a `FixedU128`/`u256`-based accumulator as used in `pallet-nomination-pools`'s `RewardCounter`) rather than a fixed `u16` scaling factor of `4096`.
- Do not advance `last_update_block` past a point where the computed increment is zero relative to elapsed blocks; instead, only update `last_update_block` when a non-zero increment is recorded, or accumulate a fractional remainder carried across calls so that rapid successive calls cannot permanently zero out accrual.
- Consider rate-limiting or fee-weighting the frequency of pool-reward-updating calls (`stake`/`unstake`/`harvest_rewards`) per account per pool.

## Proof of Concept
1. Admin creates a pool via `create_pool` with `reward_rate_per_block = R` and some `expiry_block`.
2. Multiple legitimate stakers deposit tokens such that `total_tokens_staked = S`, where `S > R * 4096`.
3. Attacker calls `stake(pool_id, 1)` once to become a registered staker in `PoolStakers`.
4. Every subsequent block, attacker calls `harvest_rewards(pool_id, None)` (or `unstake(pool_id, 0, None)`).
5. Each call invokes `reward_per_token` with `rewardable_blocks_elapsed = 1`; since `R * 1 * 4096 < S`, the division `ensure_div(S)` truncates to `0`, so `reward_per_token_stored` never increases, and `last_update_block` is reset to the current block.
6. Repeat until `expiry_block` is reached — `last_block_reward_applicable` caps at `expiry_block`, and `reward_per_token_stored` never advanced during the entire window, so no staker (including honest ones who never call anything) can ever claim rewards for that period, which are permanently lost.
