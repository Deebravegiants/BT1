Webhook HMAC does not cover the `shop-domain`/`topic` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, but that HMAC only covers the raw request body. The `shop` and `topic` values, which are read from HTTP headers, are never included in the signed bytes and are therefore trusted without any cryptographic binding to the signature that was just validated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all parsed from unauthenticated headers: [2](#0-1) 

`Registry.process` validates only this body-only HMAC via `Utils::HmacValidator.validate`, then immediately trusts `request.shop` and `request.topic` to dispatch to a handler and build `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the body, and compares it against the `hmac` header — it has no visibility into `shop`/`topic` at all: [4](#0-3) 

This breaks the intended identity binding: the equality the library implicitly claims to guarantee is `HMAC-verified bytes == (shop, topic, body)`, but in reality it only guarantees `HMAC-verified bytes == body`. `shop` is a header value that can be freely set by anyone able to send an HTTP request to the app's webhook endpoint with *any* valid `(body, hmac)` pair signed under the app's secret — and such a pair is trivially obtainable by an unprivileged attacker who installs the target app on their **own** store (a normal, public app-install flow) and triggers any webhook delivery (e.g. `orders/create`). The attacker captures that legitimate `(raw_body, hmac)` pair from their own shop's delivery, then replays the exact same body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` (and optionally `shopify-topic`) header for a victim shop that has also installed the app. `Utils::HmacValidator.validate` still returns `true` (the body/secret pair is genuinely valid), and `Registry.process` hands the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
Any multi-tenant application built on this gem's documented webhook API (`ShopifyAPI::Webhooks::Registry.process` → `WebhookMetadata#shop`) uses `shop` as the tenant key to decide which merchant's data/state to mutate. Because `shop` is not covered by the signature, an attacker can forge webhook events attributed to an arbitrary victim shop, causing cross-tenant data corruption or unauthorized actions to be taken against another merchant's account within the host app — a cross-tenant access impact.

### Likelihood Explanation
No secrets, TLS interception, or privileged access are required. The only prerequisite is the ability to install the target app on an attacker-controlled store (a normal public flow for most Shopify apps) to obtain one legitimate `(body, hmac)` pair, then replaying it with a modified `shop-domain` header to the app's public webhook endpoint. This is reachable entirely by an unprivileged internet user/merchant.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload the gem verifies — or otherwise cryptographically bind them to the request — rather than trusting them as plain, unauthenticated headers. At minimum, `Utils::HmacValidator.validate` should be extended so `VerifiableQuery#to_signable_string` for webhooks incorporates the header values that downstream consumers (`WebhookMetadata`) rely upon for tenant identification.

### Proof of Concept
1. Attacker creates their own Shopify store and installs the target app (public OAuth/install flow), subscribing to a webhook topic such as `orders/create`.
2. Attacker triggers an action (e.g., creates an order) causing Shopify to deliver a legitimate webhook to the app's endpoint; attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header value (both are visible to the attacker because the delivery is addressed to infrastructure the attacker controls, e.g. a proxy in front of their own app instance, or by using a testing/dev store they control end-to-end).
3. Attacker resends the exact same body and HMAC header to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (body+secret combination unchanged), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)`, causing the app to treat the attacker's forged data as belonging to the victim shop.
