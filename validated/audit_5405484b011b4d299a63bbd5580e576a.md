### Title
Unbounded `keys` array in `DispatchGet` enables permanent DOS of GET-request processing via gas-exhausting atomic state-proof verification - (File: `evm/src/core/EvmHost.sol`, `modules/ismp/state-machines/evm/src/lib.rs`, `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
Any unprivileged caller can dispatch a single `GetRequest` whose `keys` array contains an arbitrarily large number of storage keys. This request is committed as one atomic, immutable unit (single commitment hash) with no protocol-level limit on `keys.length`. When Hyperbridge or a destination chain must produce/verify the response, `verify_state_proof` iterates over every key in one non-splittable pass. An attacker can size this array so the verification loop exceeds the block gas limit, making the request/response permanently unprocessable — the same "unbounded batch, no count validation, no ability to split later" root cause as Centrifuge's `Gateway.withBatch()` bug, just materialized in the `DispatchGet.keys` field instead of a message-batch array.

### Finding Description
`DispatchGet` is defined with an unbounded `bytes[] keys` field: [3](#0-2)  and the Rust-side equivalent [4](#0-3) . `EvmHost.dispatch(DispatchGet)` builds a `GetRequest` directly from `get.keys` with no length check and computes its commitment hash from the whole struct: [1](#0-0) . The pallet-side `dispatch_request` for `DispatchGet` does the same, with no bound on `keys`: [2](#0-1) .

Once dispatched, the request's commitment is fixed — it cannot later be split into smaller sub-requests, exactly the same "one atomic unit, no way to divide once created" property that made the Centrifuge batch unrecoverable. When the request must be processed:
- On Hyperbridge's coprocessor, `handle_get_requests` loops over every key in `req.keys.clone()` for `verify_state_proof` inside a single call: [5](#0-4) .
- The EVM state-machine's `verify_state_proof` groups keys by contract and performs a full trie-proof reconstruction and lookup per key, entirely inside one function call with no chunking: [6](#0-5) .
- The response handler on the destination likewise verifies all keys for all Get requests in the batch in one pass with no cap: [7](#0-6) .

No `MAX_KEYS`, count check, or gas-based rejection was found anywhere in this pipeline (confirmed via targeted grep across the repo). If an attacker submits a `DispatchGet` (or equivalently a `DispatchPost` with an oversized `body`, though `keys` is the more direct analog since each key triggers independent trie-proof work) with hundreds/thousands of keys, the resulting state-proof verification work becomes too large to fit in a single Substrate extrinsic weight budget or EVM block gas limit, and the request can never be completed — it is committed on-chain (via `dispatch()`already emitting its commitment/nonce) yet unprocessable, exactly mirroring the root cause described for Centrifuge's `Gateway.withBatch()`.

### Impact Explanation
A stuck `GetRequest` occupies a nonce/commitment slot and its relayer fee remains locked until it can be processed or timed out (if a timeout was set to 0, it never expires). More importantly, this establishes a class of requests that are permanently undeliverable, blocking any downstream application logic (`IApp.onGetResponse` callback) that depended on the response, and potentially forcing relayers/infrastructure to repeatedly attempt (and fail) gas estimation for the same request, wasting resources. This is a medium-severity availability/DOS issue analogous to the cited Centrifuge finding, but note: unlike Centrifuge's `UpdateHoldingAmount`/`ExecuteTransferShares` messages that are bundled *involuntarily* with attacker messages in the same batch, here the attacker's own oversized request is the one that becomes stuck — it does not directly brick unrelated critical protocol messages, since each `GetRequest`/`ResponseMessage` batch is relayer-assembled and relayers control which requests to group together (see `chunk_size` batching at [8](#0-7) ). This limits blast radius compared to the original Centrifuge report, where the DOS could take down critical unrelated messages bundled by an attacker.

### Likelihood Explanation
Likelihood is limited by two mitigating factors not present in the Centrifuge case: (1) the relayer, not the attacker, decides how to group `GetRequest`s into a `ResponseMessage`/`handleGetResponses` batch, and gas estimation (`estimate_gas`/`estimate_gas_batched`) would fail up-front for an oversized single request, so a competent relayer would simply refuse/skip it rather than being forced to submit it; and (2) fee economics — a request with enough keys to exceed a block gas limit would cost the attacker meaningfully more in relayer fees/dispatch gas than a normal request, and yields no direct benefit to the attacker beyond griefing their own request. There is no forcing mechanism analogous to Centrifuge's `withBatch()`, where a single batch bundles the attacker's junk with someone else's critical message; the attacker here can only grief their own future response, not other users' pending messages.

### Recommendation
Add an explicit maximum on `keys.length` in `DispatchGet` validation (both `EvmHost.dispatch(DispatchGet)` and the pallet's `dispatch_request` for `DispatchRequest::Get`), rejecting the dispatch outright if the count exceeds a configurable, governance-settable threshold sized to guarantee the corresponding `verify_state_proof` call fits comfortably within the smallest supported chain's block gas/weight limit. Additionally, consider bounding `DispatchPost.body` size similarly if not already enforced elsewhere, since arbitrarily large payloads can independently cause processing-cost DOS in destination `IApp.onAccept` callbacks.

### Proof of Concept
1. Attacker calls `EvmHost.dispatch(DispatchGet)` with `keys` containing, e.g., 5,000 valid 52-byte EVM storage keys (`address(20) || slot(32)`), paying the fee: [1](#0-0) .
2. The request commitment is emitted and the request is now permanently fixed with 5,000 keys, no way to split it into smaller queries later.
3. When a relayer (or the attacker via self-relay) attempts to fetch the corresponding storage proofs and submit them via `handleGetResponses`/`handle_get_requests`, `verify_state_proof` must reconstruct and verify trie/account proofs for all 5,000 keys in one call: [6](#0-5)  or [5](#0-4) .
4. This single call's gas/weight cost exceeds the destination chain's per-block/per-extrinsic gas or weight limit, causing the transaction to always revert/fail regardless of gas provided.
5. The `GetRequest` becomes permanently stuck — it cannot be delivered, cannot be split, and (if `timeout == 0`) never times out, permanently locking the attacker's own relayer fee and leaving a dangling unprocessable commitment in protocol state.

pub fn verify_state_proof<H: Keccak256 + Send + Sync>(
	keys: Vec<Vec<u8>>,
	root: H256,
	proof: &Proof,
	ismp_address: H160,
) -> Result<BTreeMap<Vec<u8>, Option<Vec<u8>>>, Error> {
	// Reject repeats before doing any work at all. They are already an error — repeats collapse
	// in the map returned below, so the caller's key-count check fails — but reaching that
	// check means every repeat has been verified first, and for account queries that is a
	// clone of the whole contract proof each time.
	let mut seen_keys = BTreeSet::new();
	for key in &keys {
		if !seen_keys.insert(key.as_slice()) {
			return Err(EvmStateMachineError::DuplicateKey.into());
		}
	}

	let evm_state_proof = decode_evm_state_proof(proof)?;
	let mut map = BTreeMap::new();
	let mut contract_to_keys = BTreeMap::new();
	let mut contract_account_queries = Vec::new();

	// Group keys by the contract address they belong to
	for key in keys {
		// For keys that are 52 bytes we expect the first 20 bytes to be the contract address and
		// the last 32 bytes the slot hash.
		// For keys that are 20 bytes we expect that to the
		// contract or account address.
		// For keys that are 32 bytes we expect that to be a slothash in
		// the Ismp EVM host
		let contract_address = if key.len() == 52 {
			H160::from_slice(&key[..20])
		} else if key.len() == 32 {
			ismp_address
		} else if key.len() == 20 {
			contract_account_queries.push(H160::from_slice(&key));
			continue;
		} else {
			return Err(EvmStateMachineError::UnsupportedKeyLength.into());
		};
		let entry = contract_to_keys.entry(contract_address.0.to_vec()).or_insert(vec![]);

		let slot_hash = if key.len() == 52 {
			H::keccak256(&key[20..]).0.to_vec()
		} else {
			H::keccak256(&key).0.to_vec()
		};

		entry.push((key, slot_hash));
	}

	// The storage proof must correspond exactly to the contracts a key was requested from:
	// every one covered, and nothing else. Both directions are settled here, before a single
	// entry is resolved — resolving one clones the whole contract proof and rebuilds its trie,
	// so checking as we go would let a proof padded with unrequested accounts do that work
	// before being rejected, and would make which error surfaces depend on map ordering.
	// The honest prover already emits exactly this set, deriving its map from the requested
	// keys, so nothing legitimate is turned away.
	let result = contract_to_keys
		.clone()
		.into_keys()
		.all(|contract| evm_state_proof.storage_proof.contains_key(&contract));
	if !result {
		return Err(EvmStateMachineError::IncompleteStorageProof.into());
	}

	if evm_state_proof
		.storage_proof
		.keys()
		.any(|contract| !contract_to_keys.contains_key(contract))
	{
		return Err(EvmStateMachineError::UnrequestedContractProof.into());
	}

	for (contract_address, storage_proof) in evm_state_proof.storage_proof {
		// Unreachable: the correspondence check above already rejected any entry without a
		// requested key. Kept as a hard error rather than a skip so the invariant survives if
		// that check is ever moved or relaxed.
		let Some(keys) = contract_to_keys.remove(&contract_address) else {
			return Err(EvmStateMachineError::UnrequestedContractProof.into());
		};

		let contract_root = get_contract_account::<H>(
			evm_state_proof.contract_proof.clone(),
			&contract_address,
			root,
		)?
		.storage_root
		.0
		.into();

		let slot_hashes = keys.iter().map(|(_, slot_hash)| slot_hash.clone()).collect();
		let values = get_values_from_proof::<H>(slot_hashes, contract_root, storage_proof)?;
		keys.into_iter().zip(values).for_each(|((key, _), value)| {
			map.insert(key, value);
		});
	}

	for contract_address in contract_account_queries {
		let account = get_contract_account::<H>(
			evm_state_proof.contract_proof.clone(),
			&contract_address[..],
			root,
		)?;

		// Using rlp encoding for uniformity, storage values from state proofs are rlp encoded
		let encoded = alloy_rlp::encode(account);

		map.insert(contract_address.0.to_vec(), Some(encoded));
	}

	Ok(map)
}
