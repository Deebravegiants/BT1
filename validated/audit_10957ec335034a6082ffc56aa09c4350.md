The documentation at `docs/usage/webhooks.md:125` explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" and then passes `data.shop` to the handler as an authoritative field (line 14: "The shop domain of the webhook"), so host apps are documented to trust `data.shop` once HMAC validation passes. ### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over `request.to_signable_string`, and that method returns only the raw request body. The `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header), `topic`, and `webhook_id` fields are read directly from unauthenticated HTTP headers and are never included in the signed material, yet `Registry.process` forwards `request.shop` straight into `WebhookMetadata` as the trusted tenant identity for the app's handler.

### Finding Description
The identity binding broken is: `shop` field acted on (used by the host app to attribute the webhook to a tenant) ≠ `shop` field covered by the HMAC.

- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `Request#shop` is read from an HTTP header with no cryptographic binding to the signature: [2](#0-1) 
- `HmacValidator.validate` / `validate_signature` compute and compare the HMAC solely against `verifiable_query.to_signable_string`: [3](#0-2) 
- `Registry.process` treats a passing HMAC check as authorization to trust `request.shop`, forwarding it unchecked into the handler's `WebhookMetadata`: [4](#0-3) 
- The documentation instructs developers that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," implying it is a verified, trustworthy value: [5](#0-4) [6](#0-5) 

Since a single `api_secret_key` is shared by an app across every shop that installs it, any merchant who installs the app can receive a legitimate, correctly-signed webhook for their own shop (body + valid HMAC). Because the signature never covers the `shop-domain` header, that attacker can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting a victim shop's domain in the `x-shopify-shop-domain` header. `HmacValidator.validate` still succeeds (only the body was checked), and `Registry.process` passes the attacker-chosen `shop` value straight to the handler as if Shopify had reported that event for the victim's shop.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook processing: the app's handler receives attacker-controlled, unauthenticated tenant identity (`data.shop`) that it cannot distinguish from Shopify-verified data. A host app that (as documented) uses `data.shop` to select which merchant record/session/queue to update will act on data addressed to the wrong shop — a cross-tenant data-integrity/isolation violation reachable purely through the gem's documented `Registry.process` / `Webhooks::Request` API, with no privileged credentials, TLS interception, or social engineering required beyond installing the app once as a normal merchant.

### Likelihood Explanation
Exploitation only requires being able to install the app on any shop (a normal, unprivileged action for any merchant/attacker) to obtain one legitimate signed webhook, then replaying it with a modified `shop-domain` header value to the app's public webhook endpoint. No secrets, tokens, or elevated access are needed, and the code path (`Request#shop`, `HmacValidator.validate`, `Registry.process`) is exercised on every webhook.

### Recommendation
Include the identity headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind `request.shop` to the signature (e.g., verify it separately against a known/expected shop per registration) before exposing it to the handler as trusted data. At minimum, update the documentation so it no longer states `data.shop` is verified, and require host apps to independently authenticate the shop (e.g., cross-check against an existing session for that shop) before using `data.shop` for tenant-scoped operations.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = ShopifyAPI::Context.api_secret_key
body   = '{"id":1,"note":"attacker shop event"}'

hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body)

# 1. Attacker installs the app on their own shop and captures a legitimate
#    webhook: valid body + valid hmac, shop-domain = "attacker.myshopify.com".
#
# 2. Attacker replays the identical body/hmac to the app's webhook endpoint,
#    but rewrites the shop-domain header to the victim's shop.
forged_headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim.myshopify.com", # forged, not covered by hmac
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# HmacValidator only checks `body`, so this succeeds even though shop-domain
# was changed after the signature was produced.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim.myshopify.com", ...))
```
