### Title
Panic-inducing lamport debit in `maybe_burn_vat_from_staked_accounts` can be triggered by unprivileged vote-account withdrawals - (File: runtime/src/bank.rs)

### Summary
`maybe_burn_vat_from_staked_accounts` unconditionally debits `vat_to_burn_per_epoch` lamports from every staked vote account listed in a previously-captured `VersionedEpochStakes` snapshot, relying entirely on the comment/assumption that `clone_and_filter_for_vat` already guaranteed sufficient balance. This mirrors the reported bug class ("a token transfer/balance-changing operation that is assumed to always succeed can fail and take down the whole surrounding process") — except here the failure mode is a `panic!`/`.expect()` abort instead of a revert, which is strictly worse: it can crash or halt bank processing instead of merely blocking one liquidation.

### Finding Description
`maybe_burn_vat_from_staked_accounts` iterates every vote account in `epoch_stakes.stakes().vote_accounts()` and does: [1](#0-0) 

```
// Vote accounts have already been filtered by clone_and_filter_for_vat to only include
// accounts with non-zero stake and sufficient balance.
for (vote_pubkey, _stake) in vote_accounts.delegated_stakes() {
    let mut account = self.get_account(vote_pubkey).unwrap();
    total_vat += vat_to_burn_per_epoch;
    account.set_lamports(
        account
            .lamports()
            .checked_sub(vat_to_burn_per_epoch)
            .expect(
                "Vote accounts should have already been filtered to contain enough \
                 balance for the VAT",
            ),
    );
    accounts_to_store.push((*vote_pubkey, account));
}
```

The safety invariant depends entirely on `clone_and_filter_for_vat` having been called against the *current* balance of each vote account just before this function runs: [2](#0-1) 

However, `filtered_distribution_vote_accounts`/`epoch_stakes` snapshots are computed earlier in the epoch-boundary pipeline (`compute_new_epoch_caches_and_rewards`), using a `stakes_cache` snapshot of vote accounts at that point in time: [3](#0-2) 

Vote accounts can freely withdraw lamports at any time via the vote program's unprivileged `Withdraw` instruction, signed only by the vote account's authorized withdrawer — this is not a validator/operator-privileged action, it's a normal token/lamport-movement instruction any vote-authority key holder can submit: [4](#0-3) 

If a withdrawal (or any other lamport-reducing operation on the vote account, e.g. commission collection failure paths, or another `Withdraw`) executes between the point the VAT-filter snapshot was taken and the point `maybe_burn_vat_from_staked_accounts` actually debits the account (both of which read live, mutable account state via `self.get_account`, not the frozen snapshot balance), the vote account's live balance can fall below `vat_to_burn_per_epoch`. The `checked_sub(...).expect(...)` then panics.

### Impact Explanation
A panic inside bank processing during the Alpenglow VAT burn (an unconditional per-epoch bank-commit-path routine, not a per-transaction rejectable path) crashes the validator process executing it. Because every validator running this code performs the identical `maybe_burn_vat_from_staked_accounts` step at the epoch boundary with the same epoch stakes, a withdrawal timed to land after the VAT-filter snapshot is taken (but before the burn executes) can simultaneously panic every validator on the network processing that epoch boundary — a cluster-wide halt caused by an ordinary, unprivileged vote-withdraw instruction. This is far more severe than the referenced token-transfer-revert bug (which only blocked one user's liquidation): here an untrusted, permissionless action turns into a consensus-halting crash across the fleet.

### Likelihood Explanation
Reaching this requires only: (1) Alpenglow feature active, (2) a vote account whose balance sits close to `minimum_vote_account_balance_for_vat()` (rent-exempt minimum + VAT), and (3) its authorized withdrawer submitting a `Withdraw` for enough lamports to drop below the VAT-burn threshold, timed within the window between the epoch-boundary snapshot computation and the actual `maybe_burn_vat_from_staked_accounts` invocation. Both operations are deterministic/derivable from public state (epoch boundary slot, vote balance), so an attacker controlling any vote account's withdraw authority can attempt this at will; success only requires timing the withdrawal transaction to land within that window, which is a bounded number of slots and thus feasible to target repeatedly.

I was not able to fully trace the exact call site and slot ordering of `maybe_burn_vat_from_staked_accounts` relative to `compute_new_epoch_caches_and_rewards`/`get_top_epoch_stakes` within the final iteration budget (grep for the call site under time constraints returned no direct match in `bank.rs` beyond the function definition itself), so the precise size of the exploitable window (number of slots/transactions between snapshot and burn) is unconfirmed and should be verified directly in the source before treating this as fully proven.

### Recommendation
Replace the panicking `.expect()`/`.unwrap()` calls in `maybe_burn_vat_from_staked_accounts` with saturating/clamped arithmetic (e.g., `saturating_sub`, floor at the rent-exempt minimum) and skip/re-filter any vote account whose live balance no longer covers the VAT burn at execution time, rather than assuming the earlier filter result remains valid. This makes the routine tolerant of intervening withdrawals instead of crashing the validator.

### Proof of Concept
1. Wait for/target an epoch boundary where a target vote account's balance is at or slightly above `minimum_vote_account_balance_for_vat()` (passes `clone_and_filter_for_vat`).
2. As the vote account's authorized withdrawer, submit `vote_instruction::withdraw` for an amount that drops the account's live lamports below `vat_to_burn_per_epoch` while keeping it above `InsufficientFunds`/closing thresholds checked by `withdraw()` in `programs/vote/src/vote_state/mod.rs` (lines 1062-1128), timed to land after the epoch-boundary snapshot used to build `filtered_distribution_vote_accounts`/`epoch_stakes` but before `maybe_burn_vat_from_staked_accounts` executes.
3. When the bank subsequently calls `maybe_burn_vat_from_staked_accounts`, `account.lamports().checked_sub(vat_to_burn_per_epoch)` underflows and `.expect(...)` panics, aborting bank processing on every validator executing that epoch boundary — reproducing the report's "token-transfer-can-revert-and-block-a-critical-process" bug class, escalated to a process-crash/consensus-halt impact.

    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));

/// Withdraw funds from the vote account
pub fn withdraw<S: std::hash::BuildHasher>(
    instruction_context: &InstructionContext,
    vote_account_index: IndexOfAccount,
    target_version: VoteStateTargetVersion,
    lamports: u64,
    to_account_index: IndexOfAccount,
    signers: &HashSet<Pubkey, S>,
    rent_sysvar: &Rent,
    clock: &Clock,
) -> Result<(), InstructionError> {
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;
    let vote_state = get_vote_state_handler_checked(&vote_account, target_version)?;

    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    let remaining_balance = vote_account
        .get_lamports()
        .checked_sub(lamports)
        .ok_or(InstructionError::InsufficientFunds)?;

    // Always zero until SIMD-0123 is activated.
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();

    if remaining_balance == 0 {
        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.
        if pending_delegator_rewards > 0 {
            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }

    vote_account.checked_sub_lamports(lamports)?;
    drop(vote_account);
    let mut to_account = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to_account.checked_add_lamports(lamports)?;
    Ok(())
