## Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the unauthenticated `shop-domain` header as the tenant identifier passed to the app's handler. Because the app's `api_secret_key` is shared across every shop that installs the app, and the HMAC signs only the body (never the shop identity), an attacker who owns/operates their own shop installation can capture a legitimately-signed `(body, hmac)` pair from their own webhook traffic and replay it to the victim app's endpoint with a forged `shop-domain` header, causing the app to process attacker-supplied data under a different tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` only (i.e., the raw body) and compares it against the `hmac` value, with no binding to `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` performs exactly this check and then forwards `request.shop` — the unauthenticated header value — straight into `WebhookMetadata`, which is handed to the app's handler as the tenant/shop identity: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is the app's single shared secret across all installations, any merchant using the app can obtain valid `(body, hmac)` pairs from webhooks legitimately delivered to their own shop, then replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header value. The signature check in `HmacValidator.validate` still passes because `shop` is never part of the signed content — breaking the equality `shop authenticated by HMAC == shop attributed by Registry.process to the handler`.

### Impact Explanation
This is a cross-tenant identity confusion: a handler that keys any state, deletion, or business action off `WebhookMetadata#shop` (which is exactly how `shop` is intended to be used, per `Request#shop`) can be made to act on behalf of a shop the attacker does not control. This is especially severe for mandatory compliance topics like `shop/redact` or `customers/redact`/`customers/data_request`, where an attacker-controlled shop's webhook body can be replayed to trigger destructive or data-disclosure actions attributed to an arbitrary victim shop domain, as long as the attacker can guess/know the victim's `myshopify.com` domain (which is generally public/discoverable). This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitability only requires the attacker to install the app on their own shop (or otherwise receive at least one legitimate webhook for any topic with a static/predictable body, e.g., `shop/redact` whose body is `{}`), capture the resulting `(raw_body, hmac)` pair, and replay it to the app's public webhook endpoint with a spoofed `shop-domain` header. No access to `api_secret_key`, access tokens, or the victim's credentials is required — this is achievable by any unprivileged internet user who can install the app for one shop and send arbitrary HTTP requests to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified signable content, or otherwise cryptographically tie the `shop-domain` header to the signed body — e.g., include `shop-domain` (and ideally `topic`, `webhook-id`) in the HMAC input, or require the resolved shop to already exist and be actively installed for this app (cross-checked against stored session/shop data) before dispatching to a handler. At minimum, document that handlers must not treat `WebhookMetadata#shop` as attacker-unforgeable without additional server-side verification, since only the raw body is currently authenticated.

### Proof of Concept
1. Attacker installs the vulnerable app on their own shop `attacker-shop.myshopify.com`, and triggers/observes a webhook for topic `shop/redact` (body is always `{}` for this mandatory topic).
2. Shopify sends the app: `X-Shopify-Hmac-Sha256: <valid_hmac_over_"{}">`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: shop/redact`.
3. Attacker replays the exact same body (`{}`) and the exact same `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `"{}"` using the app's shared `api_secret_key` — it matches, since `shop-domain` was never part of the signed content.
5. The `shop/redact` handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the app to process a data-redaction/compliance action attributed to a shop the attacker never installed the app on or controls.
