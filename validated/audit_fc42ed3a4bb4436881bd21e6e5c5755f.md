### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` exclusively from unauthenticated HTTP headers, while `Utils::HmacValidator` (via `to_signable_string`) verifies the HMAC over the raw request **body only**. Because the shop identity is never part of the signed material, any request bearing a validly-signed body can be replayed with an arbitrary `X-Shopify-Shop-Domain` header and will still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` gates handler dispatch solely on this body HMAC: [2](#0-1) 

Yet `shop`, `topic`, `webhook_id`, and `api_version` — all read straight from attacker-controllable headers — are passed unchecked into `WebhookMetadata` and handed to the app's `WebhookHandler#handle`: [3](#0-2) [4](#0-3) 

This breaks the intended identity binding: `shop` (the value the handler trusts and acts on) ≠ `shop` (the value actually covered by the cryptographic proof). In a multi-tenant app, the `api_secret_key` is shared across all installs of the app; any merchant using the app receives their own genuinely-signed webhooks with a valid HMAC over their own body. That merchant (an unprivileged internet user w.r.t. other tenants) can capture one such request and replay it to the shared webhook endpoint while swapping only the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `Utils::HmacValidator.validate` still succeeds because it only recomputes the HMAC over the untouched body, so `Registry.process` dispatches the forged metadata to the handler as if it originated from a different shop.

### Impact Explanation
This is a cross-tenant authentication/identity-binding bypass: the gem provides no mechanism ensuring the `shop` value trusted by the handler is cryptographically bound to the signed payload. A malicious tenant can make the host application believe arbitrary webhook data (including sensitive ones like `app/uninstalled`, `shop/redact`, `customers/data_request`) came from a victim shop, letting them inject fabricated events, trigger data deletion routines, or corrupt another tenant's state — cross-tenant access, matching the Critical impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate tenant of the same multi-tenant app (no `api_secret_key`, access token, or other privileged credential needed) — they only need one genuine webhook delivered to their own store to replay with modified headers. This is realistic for any SaaS-style Shopify app built on this gem.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string (or otherwise cryptographically bind them to the body) so that spoofing any of these fields invalidates the signature, and reject/warn if the app relies on `request.shop`/`request.topic` without independently verifying it against a known/registered value.

### Proof of Concept
1. Attacker (tenant A) receives a legitimate webhook at the app's shared endpoint:
   - Headers: `X-Shopify-Shop-Domain: tenant-a.myshopify.com`, `X-Shopify-Topic: orders/create`, `X-Shopify-Hmac-Sha256: <valid HMAC of body>`.
2. Attacker resends the identical raw body and HMAC header, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` to `app/uninstalled` if body content allows, or keeps topic and only forges shop).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only — unaffected by the header change — and passes.
4. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: ...)` is dispatched to the app's handler, which processes it believing it genuinely originates from `victim-shop.myshopify.com`. [2](#0-1)
