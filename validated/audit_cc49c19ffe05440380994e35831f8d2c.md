### Title
Unrestricted CASE 2 external call in `EmporiumUpgradeable.runAction` lets an unprivileged attacker plant a standing ERC20/Permit2 allowance from Emporium, later draining any token balance Emporium is left holding - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch only blocks the two `IHinkalWallet` selectors (`callHinkalWallet`, `doSendToRelay`) but otherwise executes `op.endpoint.call(op.callData)` with `msg.sender == Emporium` and no ownership/proof binding whatsoever. `verifyWallet` allows `stack.signerAddress == address(0)`, in which case it returns without checking any signature [1](#0-0) , so any unprivileged caller with a self-authorized proof can force Emporium to call `token.approve(spender, amount)` (or a Permit2-style `approve`) directly, permanently granting an allowance keyed on `owner = Emporium`. This allowance is unrelated to any specific user's proof, is never revoked by Hinkal, and can later be used to `transferFrom` any token balance Emporium happens to hold outside of the atomic `runAction` accounting.

### Finding Description
Broken equality: `allowance_granter == token_owner_authorized_by_proof`. In reality, `allowance_granter == Emporium` acting on behalf of no specific UTXO owner, since CASE 2 requires no signature when `stack.signerAddress == address(0)` [2](#0-1) , and the CASE 2 call filter only excludes two specific selectors: [3](#0-2) 

Nothing prevents `op.callData` from encoding `IERC20.approve(spender, amount)` or a Permit2-style `approve(token, spender, amount, expiration)`, executed by `op.endpoint.call{value: op.value}(op.callData)` where `msg.sender` is Emporium itself. This creates a real, persistent allowance in the token contract's own storage (`allowance[Emporium][spender]`), completely independent from `circomData`, `deltaAmountChanges`, or any nullifier/proof.

The transaction-level guard `balanceChange < 0 → revert BalanceChangeShouldBePositive()` [4](#0-3)  only protects against balance leaving Emporium *within the same atomic `runAction` call*. It does nothing to stop a later, separate, out-of-band `spender.transferFrom(emporium, attacker, amount)` call made directly against the token contract, bypassing Hinkal/Emporium entirely.

The precondition ("Emporium holds token balance for someone") is achievable because `handleOut` only sweeps balance changes for tokens listed in `circomData.erc20TokenAddresses` [5](#0-4) . Any token produced by a CASE 2 op call (e.g., a swap output, dust, or rounding remainder) that is *not* included in that array is never measured or swept back to `msg.sender`, and silently remains on Emporium's balance across transactions.

Exploit flow:
1. Attacker sends a self-authorized `transact` with `externalActionData.externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` (no signature needed) and a CASE 2 op whose `endpoint` is the token (or a Permit2 contract) and `callData = approve(attackerSpender, type(uint256).max)`. `balanceChange` for the approve call is `0`, so the `BalanceChangeShouldBePositive` check passes; the tx succeeds and the allowance is now permanently stored in the token contract.
2. At any later point — via a victim's transaction that leaves an untracked token balance on Emporium (token not in `erc20TokenAddresses`, or dust) — Emporium holds a nonzero balance of that token.
3. Attacker calls `attackerSpender.transferFrom(emporium, attacker, amount)` directly on the token contract. No proof, no Hinkal call, no `runAction` accounting is involved, so the `balanceChange` guard never runs. Funds move out of Emporium to the attacker.

### Impact Explanation
This is direct theft of funds that Emporium is holding, unconstrained by any user's proof — matching "Critical: direct theft of shielded or in-flight user funds." The stolen value is whatever token balance Emporium is left holding at the time the attacker calls `transferFrom`, which could belong to any past depositor/user whose op sequence left an untracked balance. The attack is repeatable: a single approval-planting transaction (cost: one legitimate self-proof deposit/op, no signature needed since `signerAddress == 0`) creates a standing right that can be exercised indefinitely and drains any future balance of that token on Emporium.

### Likelihood Explanation
- No privileged role required: any user who can submit a valid proof for their own UTXOs can construct the `EmporiumStack`/`CircomData` needed, satisfying the "unprivileged attacker" constraint.
- No signature required for CASE 2 (`stack.signerAddress == address(0)` skips ECDSA verification entirely).
- The precondition — Emporium holding an untracked token balance — is realistic given `handleOut` only sweeps tokens present in `circomData.erc20TokenAddresses`; any token not included in that specific call's array (e.g., an intermediate/output token from an op-chain swap) is left unswept indefinitely.
- Attack cost is minimal (gas for one `approve` call plus one direct `transferFrom` call), and it is fully repeatable against every future occurrence of an untracked balance.

### Recommendation
- In CASE 2, restrict `op.callData` to a strict allow-list of safe function selectors per `op.endpoint` (or disallow calling `approve`/`permit`-style selectors on ERC20/Permit2-like contracts entirely), rather than only excluding `callHinkalWallet`/`doSendToRelay`.
- Require `stack.signerAddress != address(0)` (i.e., mandatory signature) for any CASE 2 op that can mutate persistent allowance state, or disallow CASE 2 entirely for calls that don't move balance measurably within the same transaction.
- Ensure `handleOut`/balance accounting sweeps *all* tokens that could conceivably result from an op (not just those declared in `circomData.erc20TokenAddresses`), or revert if `op.endpoint.call` produces a token balance change on a token not in that array.
- After every `runAction` invocation, explicitly reset/zero any ERC20 allowances Emporium may have granted during that call (defensive clean-up), and/or use a per-call disposable proxy instead of the shared Emporium contract as the `msg.sender` for CASE 2 calls.

### Proof of Concept
Foundry test plan:
1. Deploy a mock ERC20 `Token` and a mock `Permit2`-like contract (or just use the ERC20's native `approve`).
2. Deploy `EmporiumUpgradeable`, wire it into a minimal `Hinkal` harness with a valid `externalActionMap` entry.
3. Attacker transaction 1 (`transact` with self-authorized proof, `deltaAmountChanges` all `>= 0`): craft `CircomData.externalActionData.externalActionMetadata` = `abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attackerSpender, type(uint256).max))})], ...}))`. Assert tx succeeds and `token.allowance(emporium, attackerSpender) == type(uint256).max`.
4. Simulate "victim funds transiently on Emporium": have a second op-chain transaction (or directly `token.mint(emporium, dustAmount)` to emulate an unswept output token) leave `token.balanceOf(emporium) == dustAmount` with that token *not* present in that transaction's `erc20TokenAddresses` array (so `handleOut` never sweeps it).
5. Attacker calls, directly on the token contract (no Hinkal involvement): `vm.prank(attacker); token.transferFrom(emporium, attacker, dustAmount);` and asserts success and `token.balanceOf(attacker) == dustAmount`, `token.balanceOf(emporium) == 0`.
6. Assert the equality violation: the `transferFrom` succeeded despite no ZK proof or UTXO nullifier ever authorizing this transfer of the victim's/emporium's funds — i.e., `AUTHORITY(from=emporium)` was never checked against any proof, only against the previously-planted, proof-independent ERC20 allowance.
