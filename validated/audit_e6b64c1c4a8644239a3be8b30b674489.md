Audit Report

## Title
Non-constant-time comparison of the Prometheus metrics bearer token enables timing side-channel token disclosure - (File: core/web/router.go)

## Summary
The `prometheusHandler` function in `core/web/router.go` gates the `/metrics` endpoint with a bearer-token check that uses Go's native `!=` string comparison (`core/web/router.go:693`) rather than a constant-time comparison. This is inconsistent with every other credential comparison in the codebase's authentication surface, which uses `subtle.ConstantTimeCompare` (e.g., `core/sessions/session.go:73`, `core/bridges/external_initiator.go:66`, `core/bridges/bridge_type.go:111`, `core/sessions/ldapauth/ldap.go:816-822`), and creates a byte-level timing side channel on the shared metrics token (CWE-208/CWE-200).

## Finding Description
`prometheusUse` wires the `/metrics` route with `e.GET(p.MetricsPath, prometheusHandler(p.Token, h))` whenever a `*ginprom.Prometheus` is configured (`core/web/router.go:672`), and `p.Token` derives from the operator-set `PrometheusAuthToken` config value (`core/services/chainlink/config.go`). Inside `prometheusHandler`, the `Authorization` header is extracted and compared against `"Bearer " + token"` using plain string inequality:

```go
bearer := "Bearer " + token
if header != bearer {
    c.String(http.StatusUnauthorized, ginprom.ErrInvalidToken.Error())
    return
}
```
(`core/web/router.go:691-696`)

Go's `!=` on strings does a length check followed by a linear byte scan and returns as soon as a mismatch byte is found, meaning candidate values that share a longer correct prefix take marginally longer to reject. This is the same class of bug as the reference CVE (secret comparison without constant-time semantics), and it is a clear deviation from the rest of this codebase's own established pattern of using `subtle.ConstantTimeCompare` for every other credential/token check in `core/auth`, `core/bridges`, and `core/sessions`.

## Impact Explanation
An attacker who can measure response timing with sufficient precision could, in principle, incrementally recover the Prometheus bearer token byte-by-byte rather than brute-forcing the whole token space, and thereby gain unauthenticated read access to the node's `/metrics` endpoint, which can leak internal operational/node information (CWE-200 information exposure). This maps to a low/informational-severity node API authentication weakness rather than a fund-movement or key-exfiltration issue, since `/metrics` itself does not expose signing keys or move funds.

## Likelihood Explanation
Exploitability is low-to-medium: it only matters when an operator has explicitly configured `PrometheusAuthToken`; the attacker must also perform many timing measurements to statistically distinguish sub-microsecond differences, which is very noisy over real networks and only realistically feasible from a co-located/same-host vantage point. No demonstrated statistical extraction was performed in the report — it is a theoretically valid but unproven timing channel, consistent with the general difficulty of exploiting Go string-comparison timing leaks remotely.

## Recommendation
Replace `header != bearer` with a constant-time comparison, e.g. `subtle.ConstantTimeCompare([]byte(header), []byte(bearer)) == 1`, matching the pattern already used throughout `core/sessions`, `core/bridges`, and `core/sessions/ldapauth` for all other secret comparisons.

## Proof of Concept
1. Start a chainlink node with Prometheus metrics enabled and `PrometheusAuthToken` set.
2. Send repeated `GET /metrics` requests with varying `Authorization: Bearer <guess>` values, incrementing the shared-prefix length with the true token.
3. Statistically average response latency across many trials per guess to detect the byte-scan short-circuit timing bias introduced by `header != bearer` at `core/web/router.go:693`.
4. Confirm that guesses sharing a longer correct prefix show a measurable (if small) latency increase relative to early-mismatch guesses, enabling incremental token recovery.
