### Title
Webhook `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not covered by the HMAC signature, allowing cross-tenant replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the *body* only, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Those headers are read straight from unauthenticated HTTP headers and forwarded verbatim as `WebhookMetadata#shop`/`#topic`/etc. to the app's handler. This is the same class of bug as the report: an actor-identifying field (`shop`) is *acted on* by the library's documented API but is not bound by the same authentication mechanism (HMAC) that protects the payload.

### Finding Description
`Request#to_signable_string` at [1](#0-0)  signs only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers, entirely outside the HMAC coverage: [2](#0-1) .

`Registry.process` validates only the HMAC via `Utils::HmacValidator.validate(request)` (which calls `to_signable_string` — body only), and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) . `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (body only) and compares it with `OpenSSL.secure_compare`: [4](#0-3) .

The identity binding broken: **shop bound by the HMAC signature == shop delivered to the handler** does not hold. In reality, `shop` is taken purely from an attacker-controllable header and is never part of the signed material.

Documented usage explicitly directs apps to key per-tenant behaviour off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so the library's own documented contract treats `shop` as a trusted, verified value: [5](#0-4) .

### Impact Explanation
An unprivileged actor who legitimately controls one shop (shop A) installed on a multi-tenant app can:
1. Receive a genuine, Shopify-signed webhook for shop A (a valid `raw_body` + `hmac-sha256` pair the attacker fully controls the content of, e.g. an `orders/create` payload they create themselves).
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while swapping only the unsigned `x-shopify-shop-domain` (or `shopify-shop-domain`) header to victim shop B's domain.
3. Because `HmacValidator.validate` only checks the body against the secret, the forged request passes validation, and the handler receives `WebhookMetadata#shop == "shop-b.myshopify.com"` with attacker-chosen body content.

This crosses a tenant boundary: data attributed to shop A is injected/processed as if it belongs to shop B, and any app logic that uses `data.shop` to select per-tenant state, queue jobs, or write records (which is exactly what the gem's own documentation recommends) will act on the wrong tenant. This matches the “cross-tenant access” impact category.

### Likelihood Explanation
Medium-High. It requires no secret knowledge, no TLS interception, and no privileged account — only that the attacker is a genuine merchant/tenant of the app (a standard unprivileged-but-authenticated-as-their-own-shop scenario) capable of triggering webhook events with content they choose and capturing/replaying the HTTP request to the shared webhook endpoint. All apps built on this gem using the documented `Request`/`Registry.process` flow are affected identically since the vulnerable code lives in the gem itself, not app code.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., verify `shop` against a session/store lookup keyed by webhook registration rather than trusting the header). At minimum, document loudly that `data.shop` is unauthenticated and must not be used for tenant selection without independent verification (e.g., cross-checking against the webhook subscription's registered shop via a stored webhook ID → shop mapping).

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and receives a legitimate webhook:
body = '{"id":1,"malicious":"payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
# (attacker doesn't know the secret, but Shopify sends them this valid pair for their own shop)

# Attacker replays the same body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "shop-b.myshopify.com", # victim shop, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (body+secret match),
#    handler.handle(data: WebhookMetadata(shop: "shop-b.myshopify.com", body: {...}))
#    is invoked as if the data legitimately came from shop-b.
```
