### Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only. The `shop` (and `topic`/`webhook_id`/`api_version`) values that the registry hands to the app's handler come from unsigned HTTP headers, so the shop identity the handler trusts is never bound to the HMAC that "authenticates" the webhook.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic coverage: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. against the body bytes, never against the shop header: [3](#0-2) 

`Registry.process` validates that HMAC and then forwards `request.shop` (an unsigned header) directly into `WebhookMetadata`, which the app's handler uses as the tenant identifier for the event: [4](#0-3) 

The identity-binding equality that should hold is:
`shop authenticated by HMAC == shop the handler treats as the event's tenant`

Here that equality is broken: the HMAC only proves "this body was signed with the app's secret at some point" (i.e., proves the body payload originated from Shopify for *some* delivery), but the `shop-domain` header attached to that signed body is completely unauthenticated. Any party who can capture one genuine, validly-signed webhook delivery for their own shop (an unprivileged merchant can install the app on their own store and receive real webhooks) can replay the same `raw_body` + valid `hmac-sha256` value while substituting an arbitrary `shop-domain` header. `Utils::HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to a victim shop chosen by the attacker.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker-controlled `shop` value reaches the app's webhook handler as if it were authenticated, while only the JSON body bytes were actually verified. Any app that uses `WebhookMetadata#shop` to select which tenant's session/data to act on (e.g., to look up a merchant's stored access token or to write/update records "for that shop") can be tricked into performing that action against a shop the attacker does not control, using a payload the attacker fully controls the semantics of within that shop's own legitimate webhook delivery. This crosses a tenant boundary using only a replayed, legitimately-signed body — meeting the High-impact bar of cross-tenant access enabled purely by an identity-binding gap in this gem's webhook verification code.

### Likelihood Explanation
Likelihood is moderate-to-high: no secret material is required beyond having received one legitimate webhook for the attacker's own store (trivial for any developer with a free/dev store and an installed app), and no part of the gem's `process` path re-checks that the header-derived `shop` matches anything inside the signed body.

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the value that is HMAC-verified, or otherwise independently authenticate the `shop-domain` header (e.g., require it to match a shop value embedded in the signed body, or maintain a separate signed channel for header metadata) before passing it into `WebhookMetadata`. At minimum, document and enforce that consuming apps must not use the unauthenticated `shop` header value for any privileged/tenant-scoped action without additional verification.

### Proof of Concept
1. Install the target app on an attacker-owned Shopify dev store `attacker-shop.myshopify.com` and register a webhook topic (e.g. `orders/create`).
2. Trigger the webhook so Shopify sends a real request with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`, plus `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Capture `B` and `H`. Replay a request to the app's webhook endpoint with the same body `B` and header `H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) recomputes the signature over `B` only and succeeds, since `H` is valid for `B`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the signed body `B` actually originated from and describes `attacker-shop.myshopify.com`'s data — demonstrating the shop-identity binding is not enforced by the HMAC check.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
