### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (tenant) identity is read from a separate, unsigned header. `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC validates and then trusts the header-derived `shop` value when constructing `WebhookMetadata` that is dispatched to the host application's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac` field, so it only proves the body's integrity, never the shop header's: [3](#0-2) 

`Registry.process` relies on this validation and then forwards `request.shop` verbatim into `WebhookMetadata`, which is the tenant-identifying field the host application's handler uses to route/process the webhook: [4](#0-3) [5](#0-4) 

The broken equality: `shop authenticated by HMAC` should equal `shop acted upon by the handler`, but the gem only authenticates the body bytes, not the shop header. Because the HMAC secret (`api_secret_key`) is a single, app-wide secret shared across every shop that installs the app (not shop-specific), any shop that has installed the app can legitimately receive genuine, correctly-signed webhooks for its own store. An attacker who controls such a shop (an ordinary, unprivileged merchant — no special credentials needed beyond installing the app on their own store, which any Shopify user can do) can capture one of these legitimate `(raw_body, hmac)` pairs and replay it to the same webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. Because the header is excluded from the signed content, `HmacValidator.validate` still returns `true`, and the forged request is dispatched to the handler tagged with the victim's shop.

### Impact Explanation
This breaks the tenant boundary that host applications rely on this gem to enforce: `WebhookMetadata#shop` is the only tenant signal the gem hands the application, and it is unauthenticated. Any application that uses `WebhookMetadata#shop` to look up the session/access token for the shop, update per-shop state, or otherwise act "on behalf of" that shop (the documented, intended use of webhook processing in this gem) can be made to process attacker-chosen webhook bodies under a victim shop's identity — a cross-tenant access primitive satisfying the Critical impact bar in scope.

### Likelihood Explanation
Likelihood is High: no special credentials, TLS interception, or leaked secrets are required. The only requirement is that the attacker themselves has (or creates) a shop that installs the target app — a fully unprivileged, self-service action — after which capturing a valid `(body, hmac)` pair from their own genuine webhook traffic and replaying it with a modified `shop-domain` header is trivial, since the gem's own `Request`/`HmacValidator` code never binds the header to the signature.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-signed material, or independently verify that `request.shop` corresponds to a shop session/installation known to the app before dispatching to the handler, mirroring how `AuthQuery#to_signable_string` binds `shop` into the signed OAuth callback payload: [6](#0-5) 

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (normal, unprivileged onboarding flow) and subscribes it to a webhook topic (e.g. `orders/create`).
2. Shopify sends the app a legitimate webhook: raw body `B`, header `x-shopify-shop-domain: attacker.myshopify.com`, and `x-shopify-hmac-sha256: HMAC(secret, B)` — this HMAC is computed with the single app-wide `api_secret_key`.
3. Attacker (who controls the store and can inspect/replay outbound-observable traffic, e.g. via a proxy configured for their own store's webhook delivery, or simply by triggering the webhook and capturing it before it reaches the app, since they own the shop) resends this exact `(B, hmac)` pair to the app's webhook endpoint, but replaces the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely over body `B` — this matches, since `B` and the secret are unchanged — and validation passes.
5. `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` is built and dispatched to the application's handler, which believes this data legitimately originated from `victim-shop.myshopify.com`.
