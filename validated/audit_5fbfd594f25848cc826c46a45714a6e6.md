## Custody Analog Found: Multisig Timelock Override-Threshold Desync

### Title
Multisig timelock `override_threshold` invariant (`override_threshold > num_signatures_required`) is not re-validated when the base quorum is later lowered, allowing the timelock safety buffer to collapse to zero - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The external report's core custody invariant is: *a "start" threshold must retain a mandatory safety margin above the "normal operating" threshold, and that margin must be re-enforced whenever either value changes*. In BigBang/Singularity, `liquidationStartsAt` reused `collateralizationRate` with no buffer, so borrowers at max LTV were instantly liquidatable. The Aptos-native analog is the multisig account's `MultisigAccountTimeLock`, which introduces exactly the same two-threshold pattern: `num_signatures_required` (normal quorum) and `override_threshold` (approvals needed to bypass the timelock). The invariant is documented in code but the resource is decoupled from `MultisigAccount`, updated by a separate code path. [1](#0-0) 

### Finding Description
`MultisigAccountTimeLock.override_threshold` is documented as "Must be greater than the number of signatures required normally and less than or equal to the number of owners" [2](#0-1) , and `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` exists specifically to enforce it at set-time [3](#0-2) .

The transaction execution path treats meeting `override_threshold` as sufficient to bypass the timelock entirely, separate from — and stronger than — the ordinary quorum check: [4](#0-3) 

`MultisigAccountTimeLock` is a standalone `key` resource, distinct from `MultisigAccount`, and is only asserted to co-exist with it (`exists<MultisigAccount>`) — there is no invariant tying its `override_threshold` value to the *current* `num_signatures_required`: [5](#0-4) 

Critically, the audited high-level requirement list for owner/threshold changes (requirement #12) only guarantees that `num_signatures_required` stays within `[1, num_owners]` after `add_owners`/`remove_owners`/`update_signatures_required` — it says nothing about re-checking the separately-stored timelock override threshold: [6](#0-5) 

This mirrors the report's root cause precisely: `collateralizationRate` (LTV) and the liquidation start threshold were the same variable with no buffer, and no mechanism kept a margin between them across changes. Here, `num_signatures_required` can be independently lowered (e.g., via `update_signatures_required`, or indirectly by adding/removing owners) after a `MultisigAccountTimeLock` has been configured, with no code path shown re-validating `override_threshold > num_signatures_required`. If `num_signatures_required` is later raised or the timelock configured with the minimum legal margin (`override_threshold == num_signatures_required + 1`) and then owners reduce `num_signatures_required` by more than one step, the "override" quorum can become equal to or even below the new normal quorum — collapsing the intended safety buffer and making the timelock's delay trivially bypassable by any transaction that would already pass ordinary voting.

### Impact Explanation
If the buffer collapses, any multisig transaction that reaches ordinary quorum also satisfies `override_threshold`, silently defeating the purpose of the timelock (which typically exists to give other owners time to react to malicious/compromised proposals, e.g. rotating funds out of a resource-account-backed multisig holding APT/fungible assets). Given `multisig_account` is a resource account with control over an on-chain treasury, this results in unauthorized/expedited transfer, ownership, or upgrade authority takeover of custody-held value without the intended cooling-off protection — a custody-grade impact under the "multisig control" and "resource-account control" categories.

### Likelihood Explanation
This requires only normal, permitted owner actions (configuring a timelock at the legal minimum margin, then later voting to reduce `num_signatures_required` — both of which are ordinary, allowed multisig governance operations, not privileged/admin-only actions) — no external attacker or leaked keys needed. I was not able to fully inspect the body of `update_signatures_required` (and related owner-management functions) in this session due to tool-call limits, so I cannot confirm with certainty whether it internally re-checks against an existing `MultisigAccountTimeLock`. This is the main open uncertainty; the absence of any such cross-check in the specification file (`multisig_account.spec.move`) and the decoupled-resource design are the strongest indicators supporting the bug, but a background agent should explicitly trace `update_signatures_required`, `remove_owners`, `swap_owners_and_update_signatures_required`, and any `upsert_timelock`/timelock-setting function to confirm whether they call a shared validator against the live `MultisigAccountTimeLock.override_threshold`.

### Recommendation
Any function that changes `num_signatures_required` (directly or via owner add/remove) must, if a `MultisigAccountTimeLock` resource exists for that account, re-assert `override_threshold > num_signatures_required`, aborting with `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD` if the buffer would be violated by the change, exactly as done at initial timelock configuration time.

### Proof of Concept
1. Multisig account created with `owners = 5`, `num_signatures_required = 2`.
2. Owners configure a `MultisigAccountTimeLock` with `override_threshold = 3` (passes the `> num_signatures_required` check at set time).
3. Owners later call `update_signatures_required` (or equivalent) to raise `num_signatures_required` to 3, and then further governance activity effectively needs only 3 approvals for both normal execution and override — the "buffer" is now zero.
4. If `update_signatures_required` does not re-validate against the stored `MultisigAccountTimeLock.override_threshold`, transaction proposers can immediately reach `override_threshold` with a completely ordinary quorum, bypassing `can_execute_with_timelock`'s intended delay for every subsequent transaction, negating the cooling-off protection for the account's controlled assets.

*(This PoC step 3–4 relies on the unverified behavior of `update_signatures_required`; confirming it is the necessary next step to fully validate this finding.)*
