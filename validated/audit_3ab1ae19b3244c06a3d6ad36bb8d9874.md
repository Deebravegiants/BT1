### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing shop-identity spoofing in webhook processing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator` verifies the HMAC solely against that body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never included in the signed payload, yet `Registry.process` forwards `request.shop` straight into the handler as the trusted tenant identifier.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` value from the request. [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that participate in no cryptographic binding whatsoever: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body's authenticity) and then unconditionally trusts `request.shop` and `request.topic` — values taken from headers with no signature coverage — to dispatch the handler and construct `WebhookMetadata`: [3](#0-2) 

This breaks the intended identity binding: `hmac == HMAC(secret, body)` should imply `shop == the shop that actually sent this event`, but the equality only holds for `body`, not for `shop`. Since `Context.api_secret_key` is the app's single `client_secret` shared across every shop that installs the app (not a per-shop secret), any merchant that installs the app can capture a legitimate signed webhook delivered to their own store (a valid `(body, hmac)` pair) and replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. The HMAC still validates because the body is untouched, yet the handler will process the event as if it originated from the victim shop named in the forged header, exactly the analog of the "entropy attributed to `initialOwners[tokenId]` but never actually bound to the acting owner" pattern in the referenced report — here the acting "owner" (`shop`) is not what's cryptographically bound.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (as returned by `Registry.process`) to decide which tenant's session/access token to load or which tenant's data to mutate is exposed to cross-tenant confusion: an unprivileged existing installer of the app can forge webhook deliveries that appear to originate from a different, arbitrary shop domain string of their choosing, despite passing HMAC verification. This matches the Critical "cross-tenant access" impact category, since the identity used to select the affected tenant is asserted via a header excluded from the signature.

### Likelihood Explanation
Any user who can install the app (which requires no special privilege — any Shopify store owner) automatically receives the app's shared `client_secret`-derived HMAC on their own webhooks, obtaining valid `(body, hmac)` pairs on demand. Replaying those pairs to the app's public webhook endpoint with a modified `shop-domain` header requires only basic HTTP tooling; no access token, secret leak, or privileged account is needed beyond ordinary app installation.

### Recommendation
Include the `shop`, `topic`, and other identity-bearing headers in the value that is HMAC-verified (or independently verify that the `shop-domain` header matches a shop the caller is entitled to represent, e.g. by cross-checking against a stored, previously-authenticated session/shop association) before exposing `WebhookMetadata#shop` to handler code. At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Capture this `(B, hmac)` pair.
3. Send a new POST request to the same webhook endpoint containing the identical body `B` and identical `hmac` header, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)` against the unmodified body. [3](#0-2) 
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, even though the event body/HMAC never bound to that shop, and dispatches it to the handler as if it were a genuine event for the victim shop. [4](#0-3)
