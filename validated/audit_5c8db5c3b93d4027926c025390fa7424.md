### Title
Webhook shop-domain identity spoofing via HMAC that only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` binds the tenant identity (`shop`) to a raw HTTP header that is never included in the HMAC-signed payload, while `ShopifyAPI::Webhooks::Registry.process` trusts that same header value to route the webhook payload to a merchant-specific handler.

### Finding Description
`Webhooks::Request#hmac` reads `x-shopify-hmac-sha256`, and `Registry.process` validates it via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` to compute the expected signature [3](#0-2) . `to_signable_string` returns only `@raw_body` [4](#0-3) . The `shop` accessor, however, is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header with no cryptographic binding to the body or HMAC [5](#0-4) .

`Registry.process` passes this unauthenticated `request.shop` value straight into `WebhookMetadata` handed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [1](#0-0) .

The equality the gem should enforce is: `shop-domain header == tenant bound by the HMAC signature`. Instead, the actual state is: `HMAC covers raw_body only`, while `shop is read from an independent, unsigned header`. Since the same `client_secret` is used to sign every webhook the app receives (across all installed shops), any body+HMAC pair captured from one legitimate webhook delivery (e.g., a webhook for the attacker's own installed shop) remains a **valid** signature for that body no matter what `shop-domain` header accompanies it. An attacker who controls one shop where the app is installed can:
1. Receive a legitimate webhook (valid body + HMAC) addressed to their own shop.
2. Resend that exact body and HMAC to the app's webhook endpoint, replacing only the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looks at `shop`), so `Registry.process` invokes the handler with `data.shop` set to the victim's domain and the attacker-controlled body.

If the host application uses `data.shop` (as documented and intended by this gem's `WebhookMetadata`) to select the merchant record, cache key, or session/store the webhook data under, this allows a shop-level attacker to inject/alter data attributed to a different, victim tenant — a cross-tenant write despite valid HMAC verification.

### Impact Explanation
This crosses the "Critical – cross-tenant access" bar: an attacker who is merely a user of one shop where the app is installed (not privileged, no leaked secrets) can cause the app to process and persist attacker-supplied webhook data under an arbitrary victim shop's identity, because the identity field used for tenant routing (`shop`) is not covered by the HMAC that the library treats as its sole authenticity guarantee.

### Likelihood Explanation
Any merchant/user with the app installed on their own shop can trigger real webhooks addressed to themselves (e.g. by creating an order/product), capture the raw body and HMAC signature, and replay it directly to the app's webhook endpoint with a forged `shop-domain` header. No access to `client_secret`, access tokens, or Shopify infrastructure is required — only the ability to author one webhook-triggering event on their own store and to send an HTTP POST to the app's public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`) values in the signable payload verified against the HMAC, or otherwise cryptographically bind them (e.g., require the app to look up/validate the receiving shop independently, such as verifying it against a known list of shops that have valid offline sessions before trusting `request.shop`), rather than trusting an unauthenticated header for tenant routing.

### Proof of Concept
1. App has two shops installed: `attacker.myshopify.com` and `victim.myshopify.com`, both webhooks signed with the same `client_secret`.
2. Attacker triggers an event on their own shop, capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent to the app's webhook endpoint (`H` is a valid HMAC-SHA256 of `B` under the shared `client_secret`).
3. Attacker replays a new HTTP request to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` constructs `Webhooks::Request` from these headers; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [4](#0-3) .
5. The registered handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and body `B`, even though `B` was never generated for `victim.myshopify.com` — demonstrating the identity-binding break.
