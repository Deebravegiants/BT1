### Title
Undeclared-token reconciliation gap in `Hinkal.transact`/`EmporiumUpgradeable.runAction` permanently strands victim wallet funds when an untrusted Emporium executor omits a token from `erc20TokenAddresses` - ([File: contracts/Hinkal.sol], [File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`Hinkal.transact`'s post-action balance/UTXO reconciliation and `EmporiumUpgradeable.runAction`'s local balance accounting both iterate strictly over `circomData.erc20TokenAddresses`, a field that is chosen and self-signed by whoever submits the transaction, not by the `EmporiumStack` signer (the wallet owner) whose `stack.ops` are the only thing cryptographically fixed. An untrusted executor entrusted with running a pre-signed op stack can omit the token that a swap op routes directly to the `Hinkal` contract from `erc20TokenAddresses`, causing that token's balance change to bypass every reconciliation check and become permanently unassigned to any UTXO or nullifier.

### Finding Description
The equality the code is supposed to maintain is:
`balanceDif[token] == (onChainCreation ? 0 : amountChanges[token]) + utxoAmount[token]`, evaluated for **every** token actually moved by the transaction.

In practice it is only evaluated for `i` in `circomData.erc20TokenAddresses`: [1](#0-0) 

`EmporiumUpgradeable.runAction` has the identical restriction — its own before/after balance loop, `handleOut`, and `payRelayFees` all iterate only `circomData.erc20TokenAddresses.length`, while the ops themselves (`stack.ops`) are unrestricted arbitrary calls: [2](#0-1) 

Crucially, the only cryptographic commitment over `stack.ops` is `EMPORIUM_SIGNATURE_TYPEHASH`, which binds `emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `maxFee`, and `deadline` — it does **not** include `circomData.erc20TokenAddresses`, `amountChanges`, or `stealthAddressStructure`: [3](#0-2) 

Separately, `circomData.erc20TokenAddresses` *is* folded into `signedMessageHash`, which is verified in-circuit via `SignatureVerifier` against `spendingPublicKey`: [4](#0-3) [5](#0-4) 

But `spendingPublicKey`/`nullifyingPrivateKey` are keys controlled by whoever *submits* `transact` and generates the proof — i.e. the executor running the Emporium job, not necessarily the `HinkalWallet` owner who signed `stack.ops`. Nothing forces the token list used for reconciliation to match the tokens the pre-authorized ops actually move.

Exploit flow: a `HinkalWallet` owner (victim) pre-signs an `EmporiumStack` authorizing ops that swap token A for token B, with the swap's `recipient` parameter set to the `Hinkal` contract address (a normal gas-saving pattern for the swap-to-UTXO path). They hand this signed stack to an untrusted executor (the intended trust model of Emporium: signature-only authorization for later, permissionless execution). The executor calls `Hinkal.transact` with a proof generated under their own throwaway `spendingPublicKey`, sets `circomData.erc20TokenAddresses = [A]` only (omitting B), and executes the same `stack.ops`. Because the ops are hash-committed, they run unchanged and successfully send token B to `Hinkal`. But since B is absent from `erc20TokenAddresses`:
- `EmporiumUpgradeable.runAction`'s balance loop never evaluates B, so no UTXO is emitted for it.
- `Hinkal.transact`'s `oldBalances`/`newBalances`/`balanceDif`/`utxoAmount` loop never evaluates B either (`getBalancesForArray(circomData.erc20TokenAddresses)` never queries B).

Token B is left sitting in `Hinkal`'s own balance, with no nullifier, no commitment, and no way for the victim (who never receives a shielded note or plaintext refund for it) to ever claim it.

### Impact Explanation
The victim (`HinkalWallet` owner who authorized a specific, ops-only-committed trade) permanently loses the swap output token, which becomes dead balance inside the `Hinkal` contract, unassigned to any UTXO/nullifier and unrecoverable through any protocol function. This matches the Critical category "permanent freezing of user funds" — the loss is inflicted on a third party (the wallet owner) by an unprivileged executor who never needed the wallet owner's keys, only the previously delegated, signature-limited op stack.

### Likelihood Explanation
Preconditions: a `HinkalWallet` owner must use the intended Emporium delegated-execution flow (pre-sign `stack.ops` for later, trust-minimized execution by a third party) with an op whose output token is routed directly to `Hinkal`. This is the designed trust model of Emporium (unprivileged, non-wallet-owner executors are expected to run these stacks), so the attacker requires no special privilege — only to be the one submitting `transact()`, which they can always be. The cost to the attacker is a small gas fee, and the exploit is repeatable against any wallet-owner-signed stack routed through the executor.

### Recommendation
Include `circomData.erc20TokenAddresses` (and ideally `amountChanges`/`stealthAddressStructure`, or their hash) inside the `EMPORIUM_SIGNATURE_TYPEHASH` payload that `stack.signerAddress` signs, so the wallet owner authorizes not just the calls but also the exact token list used for balance reconciliation. Additionally, consider having `Hinkal.transact`/`EmporiumUpgradeable.runAction` snapshot and diff balances for a token set derived from `stack.ops`' declared endpoints/calldata (or otherwise reject configurations where a token balance change occurs outside the declared `erc20TokenAddresses`), rather than trusting the submitter-chosen array unconditionally.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, `HinkalWallet`, a mock ERC20 pair (tokenA, tokenB), and a mock "router" contract whose `swap(...)` call transfers tokenB directly to the `Hinkal` contract address (simulating `recipient = hinkal`).
2. As the "victim," EIP-712 sign an `EmporiumStack` (`ops` = [approve tokenA to router; call router.swap(amountA, recipient=hinkal)], `signerAddress` = victim's `HinkalWallet`).
3. As the "attacker/executor," build `circomData` with `erc20TokenAddresses = [tokenA]` only (omitting tokenB), `externalActionData.externalActionMetadata` = the signed stack, and a locally generated Groth16 proof for a fresh throwaway `spendingPublicKey`/zero-UTXO input set.
4. Call `Hinkal.transact(...)`.
5. Assert: `IERC20(tokenB).balanceOf(address(hinkal)) > 0` after the call, and that no commitment/nullifier event exists referencing tokenB (no `insertCommitments` entry for tokenB, `usedMessages[emporiumMessage] == true`, transaction succeeded without reverting on `"Balance Diff Should be equal..."`). Compare against the manually computed equality `balanceDif[tokenB] == amountChanges[tokenB] + utxoAmount[tokenB]`, showing the check for tokenB is never executed (loop bound = `erc20TokenAddresses.length == 1`), proving tokenB is stranded.

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
