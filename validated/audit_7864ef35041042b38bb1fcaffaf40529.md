## Analysis

The current `evm/src/apps/IntentGatewayV2.sol` fixes the predispatch/postdispatch accounting properly: it snapshots the `CallDispatcher`'s balance before the sweep, measures the actual `received` delta after the predispatch call executes, and only credits escrow with `min(received, required)`, treating any excess as dust [1](#0-0) . Escrow is then credited from `reducedInputs[i].amount`, which is derived from that verified, actually-received amount [2](#0-1) .

The `evm/tron/contracts/apps/IntentGatewayV2.sol` variant of `placeOrder`, however, still contains the vulnerable pattern the external report describes: after running `order.predispatch.call` through the shared `CallDispatcher`, it does **not** snapshot the dispatcher's balance before the call and compute the actual delta produced by that specific predispatch execution. Instead it reads the dispatcher's **total current balance** for the token and only checks `balance >= requiredAmount` [3](#0-2) , then unconditionally credits the order's escrow with `reducedInputs[i].amount` regardless of whether the predispatch call (e.g. a swap) actually produced that value [4](#0-3) .

Because `_params.dispatcher` (`CallDispatcher`) is a single shared, stateful contract used by every order's predispatch/postdispatch calls, any token balance left sitting on it (dust from another order's swap, dust that was expected to be swept but wasn't, or tokens sent to the well-known dispatcher address by any third party) satisfies the `balance >= requiredAmount` check for a *completely unrelated* order — even one whose predispatch call is a no-op or a call that fails to actually swap anything of value. The escrow credited to the attacker's commitment is not tied to tokens their own predispatch call produced.

## Title
Predispatch escrow crediting trusts total CallDispatcher balance instead of the delta produced by the swap — (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch branch checks that the shared `CallDispatcher`'s token balance is `>= requiredAmount` after running the user-supplied predispatch call, but never verifies that this balance was actually produced by that call (no before/after snapshot). It then unconditionally credits `_orders[commitment][token]` with the full `reducedInputs[i].amount`, mirroring exactly the "swap cannot provide enough tokens" pattern from the referenced report — the check that matters (did *this* swap really pay out the required amount) is missing, and a shared account's balance can be substituted for the swap's actual output.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0`, predispatch assets are transferred to `_params.dispatcher`, and the caller-supplied `order.predispatch.call` is executed via `ICallDispatcher(dispatcher).dispatch(...)` [5](#0-4) . Immediately after, the contract reads `IERC20(token).balanceOf(dispatcher)` and only requires it to be `>= requiredAmount` [6](#0-5) , then it computes `dust = balance - requiredAmount` and, regardless of what the balance actually represents, adds `reducedInputs[i].amount` to `_orders[commitment][token]` — the order's on-chain escrow accounting [7](#0-6) .

There is no snapshot of the dispatcher's balance taken *before* `dispatch(order.predispatch.call)` is invoked, so the check cannot distinguish tokens produced by this specific predispatch call from tokens already resting on the dispatcher for unrelated reasons (dust never swept from a prior order's predispatch/postdispatch flow, tokens sent to the known dispatcher address by a third party, or funds from a concurrently-processed order in the same block via a different transaction). This is the exact bug class the analog report flags: a `_reduce`/credit operation trusts a post-hoc balance check instead of the delta actually generated by the swap, allowing the credited amount to exceed what the swap really produced.

By contrast, the current non-Tron `evm/src/apps/IntentGatewayV2.sol` fixes this precisely by recording `balancesBefore[i]` prior to the dispatcher call and computing `received = balance_after - balancesBefore[i]` before crediting escrow [1](#0-0)  — confirming the Tron variant is missing this protection.

### Impact Explanation
An attacker can place an order whose `predispatch.call` is a no-op or a failing/degenerate swap that produces little or no output, while relying on the `CallDispatcher`'s pre-existing token balance (dust from other users' orders, or tokens deliberately pre-seeded to the dispatcher address) to pass the `balance >= requiredAmount` check. The gateway will then credit the attacker's order commitment with the full `reducedInputs[i].amount` of escrow — tokens the attacker never actually contributed. This escrow is later paid out to a solver who fills the order (`_withdraw`/`EscrowReleased`), effectively minting fake, unbacked escrow value out of funds that belonged to the protocol/other users' dust, resulting in direct theft of funds/permanent loss for the gateway or other order participants.

### Likelihood Explanation
Exploitability depends on the `CallDispatcher` actually holding a spare token balance at the moment of the attack (e.g., unswept dust from previous predispatch/postdispatch flows, since dust is only emitted as an event and is not necessarily transferred elsewhere immediately, or tokens sent to the dispatcher's well-known address by anyone). Since the dispatcher address is public and used by every order, an attacker could also pre-fund it directly with a small amount and immediately place an order with a matching or lower `requiredAmount`, making this self-triggerable rather than dependent on chance. This is a Medium/High-likelihood, single-transaction-reachable issue for any unprivileged user who can call `placeOrder`.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: snapshot the dispatcher's token balance immediately before invoking `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, and after the call compute `received = balanceAfter - balanceBefore`. Credit escrow only with `min(received, reducedInputs[i].amount)` (post-fee-adjusted), emit `DustCollected` for any true excess, and revert (or reduce escrow) if `received` is insufficient — never credit escrow based on the dispatcher's absolute balance alone.

### Proof of Concept
Conceptually (cannot be executed without a live testnet/fork, described here for a background engineer to reproduce in Foundry against `evm/tron/contracts/apps/IntentGatewayV2.sol`):
1. Deploy `IntentGatewayV2` (tron variant) with its configured `CallDispatcher`.
2. Directly transfer `requiredAmount` of the input token to the `CallDispatcher` address from an unrelated account (simulating leftover dust from another order, or a direct pre-fund by the attacker).
3. As the attacker, call `placeOrder` with `predispatch.call` set to a benign call that does nothing useful (e.g., an `approve(0)` call to some contract) and `predispatch.assets` set to a trivial/zero-value transfer, while `order.inputs[i].amount == requiredAmount` for the pre-funded token.
4. Observe that `balance = IERC20(token).balanceOf(dispatcher) >= requiredAmount` passes purely because of the step-2 pre-funding, not because of anything the predispatch call produced.
5. Observe `_orders[commitment][token]` is credited with `reducedInputs[i].amount`, and the attacker's escrowed input is backed by tokens they never supplied via the intended swap.
6. A solver later fills the order and the attacker (or an accomplice) receives payout funded by the misappropriated escrow, while the tokens actually escrowed came from the pre-existing dispatcher balance rather than the attacker's own funds.
