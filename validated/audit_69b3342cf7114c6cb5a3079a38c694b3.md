### Title
`validateStarknetAddress` accepts hex values above the Starknet felt252 field prime, allowing withdrawals to unrepresentable Starknet addresses - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateStarknetAddress` only checks hex charset and digit count (1-64 hex chars), with no check against the Starknet field prime (2^251 + 17·2^192 + 1). A destination address like `0x` + 64 `f`s passes validation and hex-decodes to a value far above the prime, which is not a valid felt252 and therefore not a valid Starknet account, yet the SDK signs and submits a withdrawal intent to it.

### Finding Description
The broken equality is: **address accepted by `validateAddress`/`validateStarknetAddress`** should equal **address representable as a valid Starknet felt252 account**. The regex `/^0x[a-fA-F0-9]{1,64}$/` in `validateStarknetAddress` (`packages/intents-sdk/src/lib/validateAddress.ts:502-504`) enforces only hex format/length, not the field-prime bound.

This function is invoked from `validateAddress` (`packages/intents-sdk/src/lib/validateAddress.ts:74-75`), which is called by `OmniBridge.validateWithdrawal` (`packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:358-365`) as the sole format check on `args.destinationAddress` for `Chains.Starknet`. No subsequent code in `omni-bridge.ts` or `deriveOmniWithdrawIntentParams` (`packages/intents-sdk/src/bridges/omni-bridge/omni-withdraw-params.ts:120-126`) re-checks the numeric range; the raw string is passed straight into `omniAddress(params.omniChainKind, destinationAddress)` to build the `recipient` field of the signed intent. None of the other guards in `validateWithdrawal` (fee checks, `compareAddresses` against the token address, storage balance checks, min-amount checks) inspect the numeric value of the address — they operate on fees, amounts, and string equality with the token address, not on felt252 range.

Attacker input: `destinationAddress = '0x' + 'f'.repeat(64)`. This is 64 hex `f` characters, decoding to `2^256 - 1`, which exceeds the Starknet prime (~2^251.5) by a wide margin, so it can never correspond to a real Starknet account.

### Impact Explanation
A user (or an integrator forwarding user-supplied `destinationAddress`) can construct and sign a withdrawal intent whose Starknet `recipient` is an out-of-field value. Starknet cannot credit funds to an address that isn't a valid felt252, so once the intent is executed on `intents.near` and the Omni Bridge connector processes it, the withdrawn funds are effectively unrecoverable through the normal flow — this matches the "withdrawal stuck/funds delivered to a wrong/non-existent address with no automated recovery" category. The affected party is whichever account signs the withdrawal (the user themselves, or an integrator's end user if the integrator passes through unvalidated addresses). It is repeatable per call/per withdrawal attempt.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: `route = OmniBridge`, target chain resolves to Starknet (`routeConfig.chain = Chains.Starknet` or an asset native to Starknet), and any hex string of 1-64 hex characters exceeding the field prime as `destinationAddress`. No special privileges, timing, or race conditions are required — any ordinary SDK caller can trigger this by supplying a malformed-but-regex-valid Starknet address. This is a self-inflicted-input class issue (the caller supplies their own destination), but since integrators often pass through addresses supplied by counterparties/users, the acceptance of a strictly wider set than real Starknet addresses is a genuine validation gap in the SDK's stated guarantee ("format only" note is not itself sufficient, since the SDK explicitly attempts felt252 format validation and fails to check the field-prime bound that materially distinguishes a valid Starknet address from a random 256-bit value).

### Recommendation
In `validateStarknetAddress` (`packages/intents-sdk/src/lib/validateAddress.ts`), after the regex check, parse the hex value as a `BigInt` and reject any value `>=` the Starknet field prime `2n**251n + 17n*2n**192n + 1n` (mirroring the approach already used for Aleo/BLS12-377 field-prime checks in the same file).

### Proof of Concept

// validateAddress.spec.ts (vitest)
import { validateAddress } from "./validateAddress";
import { Chains } from "./caip2";

const STARKNET_PRIME = 2n ** 251n + 17n * 2n ** 192n + 1n;

it("rejects Starknet addresses exceeding the felt252 field prime", () => {
	const outOfFieldAddress = "0x" + "f".repeat(64);
	const value = BigInt(outOfFieldAddress);

	// LHS: value is out of the valid felt252 range
	expect(value >= STARKNET_PRIME).toBe(true);

	// RHS: current implementation still accepts it as "valid"
	const isConsideredValid = validateAddress(outOfFieldAddress, Chains.Starknet);
	expect(isConsideredValid).toBe(true); // demonstrates the broken equality

	// Desired post-fix behavior: isConsideredValid should be false
});

/**
 * Validates Starknet addresses
 * Starknet addresses are felt252 (252-bit field elements) represented as
 * hex strings with 0x prefix (up to 64 hex characters)
 */
function validateStarknetAddress(address: string): boolean {
	return /^0x[a-fA-F0-9]{1,64}$/.test(address);
}
