### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity used to route/process the webhook (`request.shop`) is taken from the `x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material. This breaks the intended binding `hmac == HMAC(secret, body || shop)`; in this implementation `hmac == HMAC(secret, body)` only, so `shop` is effectively unauthenticated.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` for the signable payload and `request.hmac` for the value to check [1](#0-0) . `Request#to_signable_string` returns only `@raw_body`, deliberately excluding every header, including `shop` [2](#0-1) . Yet immediately after HMAC validation succeeds, `process` builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` — all values pulled straight from unauthenticated HTTP headers — and hands them to the app's registered handler as trusted identity fields [3](#0-2) .

Because the shop domain is not part of the signed material, any party that has ever received one genuine webhook body+HMAC pair from Shopify for the app (e.g., by installing the app on their own store and observing a webhook) can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary value for the `x-shopify-shop-domain` (or `shopify-shop-domain`) header. `HmacValidator.validate` will still return `true` because it never looks at the shop header at all [4](#0-3) , so the forged shop value flows unchecked into the handler as if it were authenticated by Shopify.

This is the direct analog of the reported bug class: a field acted on (`shop`, used to key data to a tenant) is not covered by the identity-binding check (the HMAC), exactly as the fake-vault argument was acted on without being covered by any binding check in the original report.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` from this library to decide which merchant's data/session to mutate (e.g., revoking access tokens on `app/uninstalled`, deleting/altering customer data on GDPR topics, updating shop-scoped records) can be tricked into acting on the wrong tenant's data, because the shop value the gem hands to the handler is not actually authenticated. This is a cross-tenant boundary violation caused entirely by this gem's `Request`/`Registry`/`HmacValidator` code, matching the High/Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to first obtain one legitimate `(raw_body, hmac)` pair — trivially available to anyone who installs the app on their own (attacker-controlled) development store and captures the resulting webhook request. No access token, `api_secret_key`, or privileged access is required; only a normal webhook delivery to a store the attacker controls.

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the signable material, or independently verify `request.shop` against a known/installed shop (e.g., an existing offline session) before trusting it, rather than relying solely on `Utils::HmacValidator.validate` over the raw body.

### Proof of Concept
1. Install the target app on an attacker-owned development store; capture a legitimate webhook POST, including its raw body and the `x-shopify-hmac-sha256` header value (both computed correctly by Shopify using the shared `client_secret`).
2. Replay the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change `x-shopify-shop-domain` to the victim shop's domain.
3. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the raw body only) and finds it matches, so `ShopifyAPI::Webhooks::Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the payload never actually originated from that shop.
