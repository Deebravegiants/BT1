## Title
Confirmation-depth reorg protection can be bypassed by splitting a large cross-chain order into multiple smaller orders - (File: `sdk/packages/simplex/src/core/filler.ts`, `sdk/packages/simplex/src/config/interpolated-curve.ts`)

### Summary
Simplex's cross-chain reorg protection (`ConfirmationPolicy`) sizes the required number of source-chain confirmations from the USD value of a *single* order. Exactly like the GMX virtual-price-impact bug — where a threshold check only inspected the delta of one position change instead of the account's/protocol's aggregate exposure — an attacker can split one large cross-chain intent into several smaller ones, each valued just under a confirmation-curve breakpoint, so each individually receives a shallow confirmation depth while the aggregate value receives none of the protection a single large order would have gotten.

### Finding Description
`ConfirmationPolicy.getConfirmationBlocks(chainId, amountUsd)` maps an order's USD value to a number of required block confirmations via a per-chain interpolated curve (e.g. Ethereum: $1,000 → 2 blocks, $100,000 → 15 blocks). [1](#0-0) 

In `FillerService.handleNewOrder`, `inputUsdValue` is computed strictly per incoming order (`getInputUsdValue(order)` / `strategy.getOrderUsdValue(order)`), and `requiredConfirmations` is derived from that single order's value with no consideration of other orders from the same source address, same block, or same user within the acceptance/bidding window: [2](#0-1) 

The wait loop then blocks the fill only until that (single-order-derived) confirmation count is reached: [3](#0-2) 

There is no aggregation logic anywhere in the confirmation path (`ConfirmationPolicy`, `handleNewOrder`, `getOrderUsdValue`) that sums exposure across multiple concurrent orders from the same actor. An attacker who wants to exploit reorg risk against a solver can therefore escrow, say, $100,000 across ten $10,000 `OrderPlaced` events instead of one $100,000 order. On Ethereum this drops the effective reorg-resistance the solver relies on from 15 blocks to 2 blocks for the same aggregate value the solver ends up paying out, because each of the ten orders is independently evaluated against the curve at its own (small) USD value.

This mirrors the root cause in the referenced GMX report: a size/threshold-based anti-manipulation control that inspects only the individual transaction/order in isolation, rather than the actor's aggregate exposure, and is consequently trivially defeated by structuring.

### Impact Explanation
Confirmation depth exists specifically to protect the solver's capital from a source-chain reorg: Simplex observes an `OrderPlaced` event, waits N confirmations, then irrevocably pays out real stablecoins on the destination chain. If the source-chain deposit is later reorged out (e.g., via a validator/MEV-assisted short reorg, or any other chain-specific reorg vector), the solver has paid real funds for an escrow that no longer exists. Splitting a large order into confirmation-curve-minimum-sized pieces lets an attacker force the solver to commit funds to the full aggregate amount at the shallowest confirmation depth the curve allows, materially lowering the reorg depth an attacker needs to achieve to steal solver funds while receiving the full destination payout. This is a direct theft-of-funds vector against solver capital, scaled only by how many small orders the attacker is willing to submit.

### Likelihood Explanation
Any unprivileged user can place normal `OrderPlaced` intents through the standard `IntentGateway` escrow flow — no special privileges, governance, or infrastructure compromise required. Splitting a transfer into multiple sub-threshold orders is a trivial, cheap, and repeatable operation (gas cost of extra escrow calls only), directly analogous to the "chop large orders into smaller ones" technique from the referenced report. The only additional requirement is the capability to execute a short reorg on the source chain within the (now much shorter) confirmation window, which is exactly the attack the confirmation-curve mechanism was designed to price for — structuring simply lets the attacker buy that discount.

### Recommendation
Aggregate USD exposure per source, or per user/session, over a rolling window (e.g., all orders from the same `order.user`/source address still within their respective confirmation windows) when computing `requiredConfirmations`, rather than evaluating each order's curve value in isolation. At minimum, sum the USD value of all orders from the same source address that are concurrently pending confirmation and use that aggregate to select the confirmation depth, so an attacker cannot lower the effective reorg-resistance below what the total committed capital warrants.

### Proof of Concept
1. Configure Simplex with the default Ethereum confirmation policy: $1,000 → 2 blocks, $100,000 → 15 blocks (`DEFAULT_CONFIRMATION_POLICIES["1"]`). [4](#0-3) 
2. Attacker submits a single cross-chain `OrderPlaced` for $99,000: the filler computes `inputUsdValue ≈ 99,000` and requires ~15 blocks of confirmation before filling — enough time that a short reorg is not economically/practically feasible.
3. Instead, the attacker submits ten cross-chain orders of ~$9,900 each in quick succession. For each individual order, `getInputUsdValue`/`getOrderUsdValue` returns ~$9,900, so `ConfirmationPolicy.getConfirmationBlocks(1, 9900)` returns a value close to the curve's low end (a handful of blocks) rather than 15.
4. `handleNewOrder` waits only that short confirmation count per order (see `waitForConfirmations` in `filler.ts` lines 767-811) before executing each fill, paying out destination tokens for the full $99,000 aggregate at a fraction of the intended reorg-resistance.
5. The attacker then reorgs the source chain deep enough to invalidate the deposits underlying the fills (a target now only a few blocks deep instead of 15), reclaiming the escrowed input tokens on the source chain while having already been paid the destination output tokens by the solver.

		const curve = this.policies.get(chainId)
		if (!curve) throw new Error(`No confirmation policy found for chainId ${chainId}`)
		return curve.getValue(amountUsd)
