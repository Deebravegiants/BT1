### Title
Webhook `shop-domain` header is trusted as tenant identity but is not covered by the HMAC signature, enabling cross-tenant spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards the tenant identifier taken from the `shopify-shop-domain` HTTP header directly to the app's handler. That header is never included in the HMAC-signed data, so its value is unauthenticated with respect to the signature check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, a value fully independent from the body: [2](#0-1) 

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

After that check passes, `request.shop` (unauthenticated header value) is forwarded verbatim to the app-provided handler as the tenant context via `WebhookMetadata`: [4](#0-3) [5](#0-4) 

This exactly matches the bug class in the reference report: a field that is *acted on* (here, `shop`, used as the tenant identity for the handler's business logic) is not *covered by the HMAC* that authenticates the request. The binding the gem should enforce is:
`shop header value == shop cryptographically bound to the signed payload`
but instead the gem enforces only:
`HMAC(raw_body, secret) == received_hmac`
with `shop` completely decoupled from that check.

### Impact Explanation
An unprivileged internet user who controls (or has installed) any shop that has this app installed can obtain a legitimately Shopify-signed `(raw_body, hmac)` pair for an event they trigger in their own store (e.g., an `orders/create` webhook). Because `hmac` only signs the body, the attacker can replay that exact `raw_body` + `hmac` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with any other shop's domain (a victim tenant). `HmacValidator.validate` still succeeds (body/hmac pair is genuine), and `Registry.process` will invoke the app's handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain. Any handler logic keyed off `data.shop` (e.g., looking up/updating per-shop records, associating attacker-supplied `body` content with the victim's tenant) is subject to cross-tenant data confusion/injection — the impact category explicitly listed as Critical ("cross-tenant access").

### Likelihood Explanation
The prerequisite is only having a working webhook-producing shop (achievable by any merchant/developer who installs the app on a store), plus a public HTTP endpoint the gem exposes for receiving webhooks — no `api_secret_key`, access token, or privileged access is needed. Header spoofing on an outbound-facing HTTP request is trivial for any caller replaying the payload directly to the app.

### Recommendation
Bind the `shop` field into the value that the HMAC actually authenticates, or otherwise re-derive/validate `shop` from a signed source (e.g., look up the shop associated with the recipient's registered webhook subscription rather than trusting the header), and document that consumers of `WebhookMetadata` must not treat `shop` as authenticated purely because `HmacValidator.validate` succeeded.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and triggers any webhook event, capturing the genuine `raw_body` and `X-Shopify-Hmac-Sha256` header Shopify sends.
2. Attacker POSTs that identical `raw_body` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (keeping the same, still-valid `X-Shopify-Hmac-Sha256`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this passes because it only hashes `raw_body`: [6](#0-5) 
4. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing any shop-scoped logic in the handler to operate on the wrong tenant using attacker-supplied data.
