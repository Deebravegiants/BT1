### Title
Withdrawal status/tx-hash misattribution for batched same-asset withdrawals in PoA Bridge - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal by matching entries from an unsorted external API list **only by `assetId`**, explicitly discarding the batch `index` that uniquely identifies which withdrawal intent within a NEAR transaction the caller is asking about.

### Finding Description
`describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` and the inline comment states the rationale directly: "Response list is unsorted, so we match by assetId instead of index." [1](#0-0) 

The `Bridge` interface's `describeWithdrawal` contract is keyed by a `WithdrawalIdentifier` that includes an `index`, since a single NEAR transaction can carry multiple withdrawal intents (see `createWithdrawalIdentifier` / `WithdrawalIdentifier.index` usage across bridges). [2](#0-1) 

Because the POA implementation drops `index` and keys solely on `assetId`, any NEAR transaction that batches two or more withdrawal intents of the **same asset** (e.g., splitting one deposit into two payouts to different destination addresses, a common batching pattern the SDK itself allows via `createWithdrawalIntents`) cannot be disambiguated from the unsorted API response. The first (or any) matching record for that `assetId` is returned for every index that shares the same asset, regardless of which physical withdrawal it actually corresponds to.

This breaks the equality "status/hash reported == the on-chain outcome of *this* withdrawal index." A caller polling index 1 could receive the `transfer_tx_hash`/status that actually belongs to index 0's payout (different destination, different amount), because the matcher has no way to select the correct record among multiple same-asset entries.

### Impact Explanation
`watchWithdrawal` in `withdrawal-watcher.ts` treats a `"completed"` status with a `txHash` as ground truth and resolves the caller's promise/awaits with that hash. [3](#0-2) 

An integrator relying on `describeWithdrawal`/`watchWithdrawal` to confirm that a specific batched withdrawal reached its destination could be told the wrong withdrawal (to a different recipient/amount) is "completed," while the withdrawal it actually asked about is still pending or actually failed. This matches the accepted High-impact class: "a status or hash misreport making an integrator credit or refund twice" — the integrator may release funds, mark an obligation settled, or re-trigger a refund for the wrong leg of a batch based on a hash that doesn't belong to it.

### Likelihood Explanation
This requires no malicious actor — it is triggered by ordinary usage: an integrator creating **two withdrawal intents for the same asset** within one NEAR transaction (fully supported by `createWithdrawalIntents`, which allows multiple `ft_withdraw` intents targeting the POA bridge in a single call) and then relying on `describeWithdrawal`/index to distinguish outcomes. The unsorted nature of the underlying POA API response is called out explicitly in the code as the reason index correlation was abandoned, meaning collisions are an expected occurrence, not a hypothetical edge case.

### Recommendation
Disambiguate withdrawal records within the same `assetId` using additional fields returned by the POA API (e.g., `destinationAddress`/`amount`/`account_id`) so each `index` maps to a unique record, or track/pass a per-withdrawal correlation id (e.g., memo/external id) that the API preserves, instead of relying on `assetId` alone when multiple same-asset withdrawals exist in one transaction.

### Proof of Concept
1. Build a `createWithdrawalIntents` call producing two `ft_withdraw` intents for the same `assetId` (e.g. `nep141:btc.omft.near`) to two different `destinationAddress` values, submitted in a single NEAR transaction with indices 0 and 1.
2. Call `bridge.describeWithdrawal({ tx, index: 1, withdrawalParams: { assetId: "nep141:btc.omft.near", ... } })` while the POA bridge status API returns both withdrawal records (unsorted) for that `tx.hash`.
3. Observe `findMatchingWithdrawal` returns the first record whose `defuse_asset_identifier`/`near_token_id` matches `assetId` — which may be the record for index 0, not index 1 — causing `describeWithdrawal` to report index 1 as `"completed"` with a `transfer_tx_hash` that actually corresponds to the payout for index 0's destination address.

Note: I was not able to view the full body of `findMatchingWithdrawal` (only its call site and signature) within the available tool budget, so I cannot fully rule out that it uses additional disambiguating fields beyond `assetId`. If it does, this finding does not hold; the explicit comment "we match by assetId instead of index" strongly suggests it does not.
