## Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant routing without being covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the merchant identity (`shop-domain` header) and dispatch metadata (`topic`, `webhook-id`, `api-version` headers) are read from unauthenticated HTTP headers that are never included in the signed material. `ShopifyAPI::Webhooks::Registry.process` trusts these header-derived values for handler dispatch and passes `request.shop` straight into the handler as the tenant identifier, after validating only that the body's HMAC is correct.

### Finding Description
The equality that should hold is: **bytes verified by HMAC == bytes used to identify the tenant/topic**. In this gem that equality is broken.

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all read straight from HTTP headers, none of which are part of the signed string: [2](#0-1) 
- `HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (i.e., the body) and compares it to the `hmac-sha256` header value; it never binds the header values into the check: [3](#0-2) 
- `Registry.process` gates dispatch solely on this body-only HMAC check, then immediately uses `request.shop` and `request.topic` (unauthenticated header values) to route to a handler and construct the `WebhookMetadata` passed to application code: [4](#0-3) 

Because the api_secret_key used to compute the HMAC is the same for every webhook Shopify sends to a given app (not scoped per shop-domain header), any body/HMAC pair that Shopify has legitimately produced for the app (e.g., a webhook triggered on the attacker's own installed shop) is valid raw_body+hmac material. Since the `shop-domain`, `topic`, and `webhook-id` headers are outside the signed string, they can be freely substituted by an unprivileged attacker who controls the HTTP request delivered to the app's webhook endpoint, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This lets an unprivileged internet user who can reach the app's webhook endpoint (a merchant on their own shop, or anyone who can replay a captured legitimate webhook payload) forge the `shop-domain` header to any victim shop while keeping a body+HMAC pair that Shopify actually signed for the app. `Registry.process` will accept the forgery as authentic and hand `WebhookMetadata` to the app's handler with `shop:` set to the attacker-chosen victim domain and/or `topic` set to any registered topic — i.e., cross-tenant data injection into the host application's webhook processing pipeline, using only a single previously observed genuine webhook from the attacker's own store. Depending on what the handler does with `data.shop` (e.g., using it to look up/act on merchant records), this can result in cross-tenant access or data corruption without any credential beyond the ability to send an HTTP request.

### Likelihood Explanation
Likelihood is high for any app that has ever received at least one real webhook (trivial for the attacker to trigger on their own store by, e.g., updating a product) — the attacker only needs to capture that raw body + `x-shopify-hmac-sha256` value once and can then replay it against the same endpoint with an arbitrary `shop-domain`/`topic`/`webhook-id` header set, requiring no access token, no `client_secret`, and no privileged account.

### Recommendation
Bind the identity/routing fields into the signed material, or otherwise cryptographically tie the header values to the verified body:
- Include `shop-domain`, `topic`, and `webhook-id` in `to_signable_string` (this requires a coordinated change with Shopify's signing on the platform side), or
- At minimum, treat `hmac` verification as proof only of body integrity and separately re-validate `shop-domain` against the session/store the webhook is expected for (e.g., cross-check against `Context`-known shops or the registration that was created for that specific shop before dispatch), rejecting webhooks whose `shop-domain` was not the one the corresponding registration was created for.
- Document clearly for consumers that `Registry.process` does not guarantee the header-derived `shop`/`topic` are authentic, only that the body is unaltered from a Shopify-signed payload for this app.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and triggers any webhook (e.g., `products/update`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid for the app's `api_secret_key` and this exact body.
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - The same raw body and `x-shopify-hmac-sha256` value captured in step 1.
   - `x-shopify-shop-domain: victim.myshopify.com` (forged).
   - `x-shopify-topic`/`x-shopify-webhook-id` optionally forged to any registered topic.
3. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the untouched raw body) and successfully matches the supplied `hmac`, per [5](#0-4)  and [6](#0-5) .
4. The registered handler for that topic is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is the attacker-forged `victim.myshopify.com`, per [7](#0-6) , causing the host application to process attacker-controlled data as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
