### Title
Optimism dispute-game verifier accepts state roots without checking the dispute game's resolution status - (File: `modules/ismp/clients/optimism/src/lib.rs`)

### Summary
`verify_optimism_dispute_game_proof` and its helper `verify_not_challenged` accept an L2 state root sourced from a permissionlessly-creatable `FaultDisputeGame`/`AggregateVerifier` proxy by checking only that the game is *currently unchallenged* at the proof's L1 block height. Neither function ever reads or verifies the game's `status()` (i.e. whether it actually resolved `DEFENDER_WINS`) or `resolvedAt()`/clock-duration fields. This is structurally the same bug class as the reported Chainlink issue: a liveness/status flag that gates whether the underlying data source can be trusted (`sequencerUptimeFeed` for Chainlink, dispute-game `status`/`resolvedAt` for Hyperbridge) is never checked before the price/state data is consumed.

### Finding Description
`verify_optimism_dispute_game_proof` derives the `game_uuid`/`game_id` from the claimed L2 header and confirms the game is registered in the `DisputeGameFactory` and its implementation matches an expected address [1](#0-0) . It then calls `verify_not_challenged`, which — for `FaultDisputeGame` — proves that `claimData.length == 1`, i.e. no `move()` has yet been made against the root claim [2](#0-1) . For `AggregateVerifier` it proves `counteredByIntermediateRootIndexPlusOne == 0` [3](#0-2) .

Both checks only assert "not yet challenged at this instant" — they never verify `status()` (`IN_PROGRESS` vs `DEFENDER_WINS` vs `CHALLENGER_WINS`) or `resolvedAt()`/the game's clock/air-gap period, fields that exist on the `FaultDisputeGame` ABI itself [4](#0-3) . Anyone can create a dispute game (the relayer-side code explicitly notes this: "Since anyone can create dispute games including bots") [5](#0-4) , and a freshly-created game with a forged root claim is "unchallenged" by construction until an honest challenger acts. A relayer can therefore submit `handleConsensus`/the pallet's consensus-message handler with a proof against such a game the moment it's created, well before its dispute window and finalization have run, exactly the missing-liveness-check pattern in the report (trusting data without checking the gating liveness/finality signal).

### Impact Explanation
Accepting a state commitment sourced from a still-contestable, unresolved dispute game means Hyperbridge's on-chain `StateCommitment` for that OP-Stack chain can be forged before the real dispute process invalidates it. Downstream, this state root gates `handlePostRequests`/membership proofs (`HandlerV2.sol`), so a forged commitment can be used to fabricate message delivery or state proofs on Hyperbridge, i.e., forged message delivery / unsound state commitment — a Medium/High-severity outcome matching the validation criteria.

### Likelihood Explanation
Mitigating factors exist (a general challenge-period + fisherman veto architecture, and possibly an async `fish_opstack` watcher that could later blacklist a bad claim), but these are post-hoc/asynchronous defenses layered on top, not an atomic check at proof-acceptance time — the same structural weakness the Chainlink report criticizes. I was not able to fully verify, given remaining time, whether `fish_opstack.rs` (`tesseract/messaging/fisherman/src/opstack.rs`) closes this gap completely (e.g., whether it polls fast enough and always runs before a relayer can exploit the window, and whether the `challenge_period` value configured per state machine is always long enough relative to the dispute game's own dispute window). This uncertainty should be resolved by inspecting `tesseract/messaging/fisherman/src/opstack.rs` and the configured `challenge_periods` for OP-Stack chains before treating this as fully mitigated.

### Recommendation
Extend `verify_not_challenged` (or add a companion check) to also prove and verify the game's `status` slot equals `DEFENDER_WINS` and that `resolvedAt` plus the implementation's air-gap/finality period has elapsed relative to the L1 block used for the proof, mirroring the official Chainlink pattern of checking a liveness/finality flag before trusting the payload, rather than relying solely on "not yet challenged."

### Proof of Concept
1. Attacker (or bot) calls `DisputeGameFactory.create()` on the target OP-Stack chain with a forged `rootClaim` for a nonexistent/incorrect L2 state.
2. Immediately after creation, `claimData.length == 1` (unchallenged) and `counteredByIntermediateRootIndexPlusOne == 0` — both checks in `verify_not_challenged` pass [2](#0-1) .
3. A relayer submits a `ConsensusMessage`/dispute-game proof built from this fresh game to Hyperbridge's `handle_incoming_message`/`HandlerV2.handleConsensus`, which calls `verify_optimism_dispute_game_proof` and accepts the forged state root as a new `IntermediateState`/`StateCommitment` [6](#0-5) .
4. Because `status()`/`resolvedAt()` were never checked, this happens without any assurance the game will resolve `DEFENDER_WINS`; the honest challenge to invalidate the game on L1 may complete only after the corresponding request/response messages have already been processed against the (soon-to-be-proven-false) commitment on Hyperbridge, depending on how quickly (if at all) any secondary fisherman watcher reacts.

	match kind {
		DisputeGameImpl::FaultDisputeGame => {
			// `claimData` is a dynamic `ClaimData[]` at `FAULT_DISPUTE_CLAIM_DATA_SLOT`. Solidity
			// stores a dynamic array's element count in the slot itself (the elements live at
			// `keccak256(slot)`). A freshly created, unchallenged game holds exactly one entry —
			// the root claim appended in `initialize()` — and every `move()` (attack or defense)
			// appends another. So `claimData.length == 1` iff the game has not been challenged.
			// Any other length (including absence, i.e. length 0 for a game that never registered
			// its root claim) is rejected.
			//
			// The MPT trie path for a direct storage slot is `keccak256(slot)`.
			let storage_key = U256::from(FAULT_DISPUTE_CLAIM_DATA_SLOT).to_big_endian();
			let trie_path = H::keccak256(&storage_key);
			let value = get_value_from_proof::<H>(
				trie_path.0.to_vec(),
				proxy_storage_root,
				challenge_proof,
			)?
			.ok_or(Error::ClaimDataSlotMissing)?;
			let raw = <alloy_primitives::Bytes as Decodable>::decode(&mut &*value)
				.map_err(|_| Error::DecodeClaimData(format!("{:?}", value)))?
				.0
				.to_vec();
			if raw.len() > 32 {
				Err(Error::ClaimDataTooLong)?
			}
			// RLP strips leading zeros from the stored length; reconstruct the uint256 and require
			// it to be exactly one.
			if U256::from_big_endian(&raw) != U256::one() {
				Err(Error::FaultDisputeGameChallenged)?
			}
			Ok(())

			// `counteredByIntermediateRootIndexPlusOne` is a uint256 at a fixed slot.
			// Unchallenged <=> value is zero, which in the storage trie means either absent or
			// encoded as zero. `get_value_from_proof` returns `None` for absent keys.
			//
			// The MPT trie path for a direct storage slot is `keccak256(slot)`.
			let storage_key =
				H256(U256::from(AGGREGATE_VERIFIER_COUNTERED_BY_SLOT).to_big_endian());
			let trie_path = H::keccak256(&storage_key.0);
			let value = get_value_from_proof::<H>(
				trie_path.0.to_vec(),
				proxy_storage_root,
				challenge_proof,
			)?;
			match value {
				None => Ok(()),
				Some(v) => {
					let raw = <alloy_primitives::Bytes as Decodable>::decode(&mut &*v)
						.map_err(|_| Error::DecodeCounteredBy(format!("{:?}", v)))?
						.0
						.to_vec();

						Err(Error::CounteredByTooLong)?

						Err(Error::AggregateVerifierChallenged)?
					}
					Ok(())
