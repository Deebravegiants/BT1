## Analysis Result

### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header to identify which merchant/tenant the event belongs to. Since the shop identifier is never bound into the signed material, an attacker who can obtain one genuine, validly-signed webhook payload (e.g., by installing the app on their own shop and receiving real webhooks for their own store) can replay that exact `body`+`hmac` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the header. The signature still verifies, and the handler is invoked believing the event originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, completely independent of the signed body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, and — critically — the validator itself only ever calls `verifiable_query.to_signable_string`, i.e. the raw body, when computing/comparing the signature: [3](#0-2) 

Once the HMAC check passes, `Registry.process` immediately forwards `request.shop` — the unauthenticated header value — to the app-supplied handler as the tenant identifier, with no further binding check: [4](#0-3) 

This breaks the intended identity binding `HMAC-authenticated tenant == shop field consumed by handler`. The signature only proves "this body was produced by someone holding the app's `api_secret_key` (i.e., genuinely came from Shopify for *some* shop)" — it says nothing about *which* shop it came from. The `shop` field is a claim that rides along unauthenticated, exactly matching the reported bug class ("a field acted on but not covered by the HMAC").

### Impact Explanation
An attacker who installs the target app on their own (attacker-controlled) Shopify store is a legitimate recipient of real, correctly-HMAC-signed webhooks for that store (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`, etc.), since Shopify itself sends these once the app is installed — no credential theft required. The attacker captures one such genuine `raw_body` + `hmac` pair, then replays it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because the domain header was never part of the signed content, and the app's registered handler executes business logic (order processing, data-request/redact handling, uninstall cleanup, GDPR mandatory webhook handling, etc.) believing the event pertains to the victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop sessions/state, trigger data deletion, or update tenant records), this enables cross-tenant data confusion or forged mandatory-compliance events attributed to a shop the attacker does not control — satisfying the "cross-tenant access" impact bar.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that installs on multiple/public merchants: any user can install the app on their own store for free/trial, harvest one legitimately-signed webhook, and replay it against the shared webhook endpoint with a forged shop header — no `api_secret_key`, access token, or privileged access is required, only knowledge of the app's public webhook URL (which is typically fixed/documented).

### Recommendation
Bind the shop identity into the authenticated material before trusting it: either (a) require the app to independently confirm that `request.shop` corresponds to a shop with an active, previously-stored installation/session before acting, and/or (b) incorporate the `shop`/`webhook-id` headers into the HMAC-signable string (matching what the raw body signing actually covers) so that spoofing the shop header invalidates the signature. At minimum, `ShopifyAPI::Webhooks::Registry.process` and `Request#to_signable_string` documentation should make explicit that `shop` is unauthenticated and host apps must cross-check it against known/installed shops before use.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST body `B` and the corresponding `x-shopify-hmac-sha256` header `H` computed by Shopify with the app's real `api_secret_key`.
2. Attacker sends a forged request to the app's webhook endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: victim-shop.myshopify.com`
   - Body: `B` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` and calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes. [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the event data actually originated from the attacker's own shop, demonstrating the unauthenticated tenant-binding.
