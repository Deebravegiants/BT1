### Title
Webhook shop/topic identity spoofing via HMAC that covers only the request body - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` values taken straight from HTTP headers when dispatching the payload to the app's handler. Because these header fields are never included in the signed material, an attacker can take a body that was legitimately HMAC-signed for their own shop and replay it against the app's webhook endpoint with a forged `shop-domain` header, causing the host application to process it as data belonging to a shop it doesn't control.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

All other identity-bearing accessors — `topic`, `shop`, `api_version`, `webhook_id` — are parsed straight from headers and are not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` uses that body-only validation as its sole authentication check, then dispatches based on the unauthenticated `request.topic` header and forwards the unauthenticated `request.shop` header to the handler as the trusted tenant identifier: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is shared across every shop that has installed the app, an attacker who controls (or has installed the app on) their own shop can obtain a genuinely-signed webhook body (e.g. from `orders/create`, `app/uninstalled`, or a GDPR topic) and then POST that exact body to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop, and/or the `shopify-topic`/`webhook-id` headers changed. `HmacValidator.validate` still succeeds because it only checks the body bytes against the shared secret; nothing binds the signature to the shop, topic, or webhook id that the handler ultimately trusts. This breaks the identity binding `shop verified by HMAC == shop delivered to handler`, the exact "field acted on but not covered by the HMAC" pattern called out for this analog class.

### Impact Explanation
Any host application built on top of `ShopifyAPI::Webhooks::Registry` that uses `WebhookMetadata#shop` (or `#topic`) as a tenant key — e.g. to look up a session, write to a shop-scoped record, mark a shop uninstalled, or process a GDPR data request — can be tricked into attributing attacker-supplied webhook content to an arbitrary victim shop domain. This is a cross-tenant data-integrity/confusion issue: it lets one authenticated app-installer forge webhook events "from" another merchant's shop, which falls under the "cross-tenant access" Critical impact category since the tenant boundary (`shop`) is not cryptographically bound to the authenticated bytes.

### Likelihood Explanation
The attacker only needs to be an ordinary, unprivileged user who can install the target app on any shop (their own) to receive real, validly-signed webhook deliveries, and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (which by definition must be internet-reachable). No access to `api_secret_key`, access tokens, or the merchant's credentials is required — only reuse of a webhook body they legitimately received, with forged headers. No specialized tooling is required beyond replaying an HTTP request with modified headers.

### Recommendation
Include the identity-bearing fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the payload before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `request.shop`/`data.shop` and `request.topic` are NOT authenticated by the HMAC check and must not be treated as trusted tenant identifiers by consuming applications without additional verification (e.g., cross-checking against a shop that is already known/installed).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the resulting `x-shopify-hmac-sha256` header — both are valid because they're signed with the app's single, shared `client_secret`.
2. Attacker resends the exact same raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - (optionally) a different `x-shopify-topic` if it doesn't need to match content expectations.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — this passes because the body and secret are unchanged: [4](#0-3) 
4. The registered handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from and was signed for the attacker's own shop, letting the attacker inject cross-tenant webhook data into the host application.
