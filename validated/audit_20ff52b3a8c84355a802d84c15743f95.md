### Title
Webhook shop/topic/webhook-id identity is not covered by the HMAC, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an incoming webhook using an HMAC that is computed only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the registry hands to application handlers come from unauthenticated HTTP headers. An attacker who owns a legitimate (even free/dev) Shopify store can receive a validly-signed webhook for their own shop and then replay it to a target app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped to a victim shop's domain. The HMAC still validates because it never covered those header fields, so the forged request is accepted and the attacker-controlled body is dispatched to the handler as if it belonged to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are all read straight from HTTP headers with no cryptographic binding to that body: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before invoking the handler with `request.shop` from the unauthenticated header: [4](#0-3) 

This breaks the identity binding: the equality that should hold is `shop authenticated by HMAC == shop attributed to the webhook data`, but instead `shop attributed to webhook data` is taken from a header that is never part of the signed material. The documented usage pattern explicitly tells integrators to trust `data.shop` from the handler callback to key their application logic (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`), so any host app following the gem's documented API inherits this cross-tenant confusion: [5](#0-4) 

### Impact Explanation
An attacker who legitimately controls any Shopify store (even a free development store) can obtain a validly HMAC-signed webhook payload for their own shop from Shopify itself, then resend that exact body to the same app's public webhook endpoint while altering the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header to point at a different, victim tenant. Because the gem's HMAC check never covers these header values, the forged request passes verification, and the application handler receives attacker-controlled body content labeled as belonging to the victim shop. Any app that uses `data.shop` to key persistence, enqueue background jobs, or make trust decisions (as the gem's own documentation instructs) will process/act on forged data under the wrong tenant's identity — a cross-tenant integrity violation.

### Likelihood Explanation
High: no privileged credentials, access tokens, or `client_secret` are required — only a legitimately signed webhook from the attacker's own store (trivial to obtain by installing/using any real or dev shop) and the ability to send an HTTP POST with modified headers to the target app's public webhook route.

### Recommendation
Include the identity fields (`shop-domain`, `topic`, and ideally `webhook-id`) in the material that is HMAC-verified, or otherwise cryptographically bind them to the signed payload, so that `to_signable_string` cannot be satisfied by a body signed for one shop/topic while the headers claim a different shop/topic. At minimum, document and/or enforce that `data.shop`/`data.topic` must not be trusted without an independent verification path (e.g., cross-checking against the shop for which the specific `webhook_id` was registered).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets Shopify deliver a legitimate webhook, e.g. `orders/create`, to the app's webhook endpoint. This request has a correct `x-shopify-hmac-sha256` computed over the raw JSON body using the app's real `client_secret`.
2. Attacker captures the raw body and HMAC header value.
3. Attacker resends the identical raw body and HMAC header to the same endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and/or changes `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only rehashes `@raw_body` and succeeds because the HMAC still matches the unmodified body: [6](#0-5) 
5. The registered handler is invoked with `WebhookMetadata` whose `shop` is `victim.myshopify.com`, even though the body content actually originated from the attacker's own shop — a cross-tenant data-attribution forgery.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
