### Title
Token donation to a curve `Pair` poisons `Router._computeBuy`'s overflow-cap math, panic-reverting large buys and permanently blocking the supply-side graduation trigger - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy` caps `tokensOut` at `pair.tokenBalance()` (the pair's *real* token balance) whenever the uncapped constant-product output would exceed it, then back-calculates `amountInUsed` from `cappedReserveToken = reserveToken - tokensOut`. This subtraction assumes `reserveToken >= tokenBalance()` always holds. Any unprivileged wallet can violate that assumption for free by directly `transfer()`-ing the launched `Token` to its own `Pair` address (an explicitly in-scope reachable action), inflating `pair.tokenBalance()` above the virtual `reserveToken`. Once that happens, any buy whose uncapped `tokensOut` would exceed the (now donation-inflated) real balance drives `cappedReserveToken = reserveToken - tokensOut` into an unsigned underflow, causing a Solidity `Panic(0x11)` revert instead of the intended graceful cap.

### Finding Description
`Router._computeBuy` (`packages/contracts/src/Router.sol:127-148`):
```solidity
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // underflows if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [1](#0-0) 

The whole overflow-cap mechanism, and the invariant it depends on (`pair.tokenBalance() < reserveToken` at every point of a healthy curve), is documented as load-bearing: [2](#0-1) 

That invariant is only guaranteed under the *virtual reserve design* (`reserve0` seeded at `totalSupply`, only 75% of real tokens transferred) as long as no one adds *extra* real tokens beyond that design: [3](#0-2) 

Direct ERC20 donations of the launched `Token` to the `Pair` are exactly the class of unprivileged action the scope rules call out as reachable. Once a donation lands, `Pair.tokenBalance()` (a live `balanceOf` read) permanently exceeds the virtual `reserve0/tokenReserve`, because ordinary buys decrease `reserveToken` and `tokenBalance()` by the *same* `tokensOut` (via `Pair.transferToken` + `Pair.swap`), preserving the donation offset `D = tokenBalance() - tokenReserve` forever: [4](#0-3) 

The project's own regression-test comment for `Bonding.previewLtUntilGraduation` confirms this exact donation shape was already found to break that function's supply-leg math via underflow, and a guard (`if (realBalance >= reserveToken) return ltUntilThreshold;`) was added there: [5](#0-4) [6](#0-5) 

However, that fix was applied only to `previewLtUntilGraduation`'s *view*. `Router._computeBuy`, which is the function that actually executes state-changing buys via `Router.buy` (called by `Bonding.buy`, called by `Zap.buy`/`Zap.buyWithPermit`), contains no equivalent guard. It is reachable by every unprivileged buyer.

### Impact Explanation
Once `D > 0` is established (a single wei-scale donation is enough to trigger the underflow branch on a subsequent large buy):
1. **Availability/DoS on large buys.** Any buy whose uncapped constant-product `tokensOut` exceeds the current (inflated) real balance now reverts with an unhandled `Panic(0x11)` instead of executing at the intended capped amount. This is the direct analog of the CVE's "hang / repeatable crash" class — a network-reachable, unprivileged call that reliably aborts execution instead of completing.
2. **Permanent freezing of the supply-side graduation trigger.** Because `D` is preserved across ordinary (non-capped) buys, `pair.tokenBalance()` can never again reach `0` — the supply trigger (`IPair.tokenBalance() == 0`) documented as the mechanism that "handles flat/bear markets where $9K is never reached" becomes permanently unreachable for that token: [7](#0-6) 
If the paired LT's price never appreciates enough to independently trip the USD trigger, the token (and all curve-raised LT + creator/trader funds locked in `Bonding`/`Pair` for that token) is frozen on the curve indefinitely — it can never graduate, and holders can only exit via `Zap.sell`'s curve-sell path (subject to the same broken cap logic on large sells is not applicable, but large buys near sellout are permanently broken).
3. Even short of full graduation-blocking, every large "closing" buy near curve sellout — the exact scenario the overflow cap exists to protect — now non-deterministically panics for any token that has ever received a single donated-token transfer, which any address can trigger for $0 cost against any launched token.

### Likelihood Explanation
High. The precondition (`IERC20(token).transfer(pair, anyAmount)`) is a plain ERC20 transfer requiring no role, no fee, and no cooperation from `Bonding`/`Router`/`Zap` — it is explicitly one of the reachable, in-scope actions listed in the assignment ("direct ERC20 transfers of a launched Token ... into Pair"). No sophistication beyond calling `transfer` is needed, and the attack is cost-negative relative to the damage (permanent freeze of a token's curve). The only work is then waiting for/triggering a buy sized to exceed the now-inflated real balance, which happens naturally as any token's curve approaches sellout (the exact circumstance under which the overflow cap exists to activate).

### Recommendation
In `Router._computeBuy`, guard the overflow-cap branch against `realBalance >= reserveToken` the same way `Bonding.previewLtUntilGraduation` already does, e.g.:
```solidity
uint256 realBalance = pair.tokenBalance();
if (realBalance >= reserveToken) {
    // donation-inflated balance: supply-side cap is meaningless here,
    // fall back to the uncapped (or safely bounded) quote.
} else if (tokensOut > realBalance) {
    ...
}
```
More robustly, since `realBalance` can only exceed `reserveToken` via a donation (never through normal curve operation), consider sweeping/burning any token balance in excess of `reserveToken` at the top of every buy/sell (mirroring the "any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`" policy already used at graduation time), so the invariant `tokenBalance() <= reserveToken` is restored before the overflow-cap math runs rather than merely tolerated by another special-case branch.

### Proof of Concept
1. Launch a token via `Zap.createToken` (curve `Pair` created with `reserve0 = totalSupply`, real balance = `curveSupply` = 75%).
2. Attacker (any unprivileged wallet holding, or having bought, some of the launched `Token`) calls `IERC20(token).transfer(pairAddress, 1)` — a bare 1-wei donation directly to the `Pair`, no approvals or roles needed. Now `pair.tokenBalance() == reserveToken + 1`.
3. A legitimate trader (or the same attacker) calls `Zap.buy(token, usdcAmount, ...)` sized so that the uncapped constant-product `tokensOut` computed in `Router._computeBuy` exceeds `pair.tokenBalance()` (i.e., a buy that would normally hit/near the sellout overflow cap — trivially achievable by buying a large fraction of remaining curve supply, exactly the "closing buy" scenario the cap exists for).
4. Inside `_computeBuy`: `tokensOut = realBalance` (the now donation-inflated value) is set, then `cappedReserveToken = reserveToken - tokensOut` underflows because `tokensOut = reserveToken + 1 > reserveToken`. The call reverts with `Panic(0x11)` instead of completing the buy at the capped amount.
5. Because `D = 1` (or whatever donated amount) is preserved through every subsequent non-capped buy (`Pair.swap` decrements `tokenReserve` and the real balance by the identical `tokensOut`), `pair.tokenBalance()` can never again fall to `0`, permanently disabling the supply-side graduation trigger for this token, freezing any further capped/closing buys with the same panic, and leaving curve-raised funds and unsold curve tokens trapped whenever the USD trigger cannot independently fire.

**Uncertainty note:** I was not able to fully trace whether `Bonding.buy`/`_executeBuy` (the wrapper around `Router.buy`) contains any additional pre-flight guard against a `tokenBalance() > reserveToken` state before invoking `Router.buy`/`_computeBuy` — the visible slices of `Bonding.sol` show the graduation-preview guard but not the exact `Bonding.buy` body. If such a guard exists there, it would need to be checked against this same underflow path to confirm whether it is bypassed. A Devin session with full file access to `packages/contracts/src/Bonding.sol` (in particular the `buy`/`_executeBuy` functions) would be needed to close this gap definitively.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

```markdown
**Virtual token reserve.** The pair's `reserve0` is seeded at `totalSupply` (1B) while only `curveSupply = 75%` (750M) of real tokens are actually transferred. The other 250M are held in `Bonding` as `lpReserve`. This virtual-reserve design:

- Extends the curve beyond the sellable supply.
- Gives a deterministic supply trigger (curve exhausts at 750M sold).
- Makes the dynamic-LP-seeding parabola `tokensForLP(sold) = sold·(S−sold)/S` peak at exactly `S/4 = 250M = LP_RESERVE` — so `tokensForLP ≤ lpReserve` is a mathematical invariant, not a runtime guess.
```
