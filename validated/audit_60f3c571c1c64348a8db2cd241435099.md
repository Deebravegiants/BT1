### Title
Webhook `shop` and `topic` are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while the shop-identifying header (`X-Shopify-Shop-Domain`) and the `topic` header are read directly from unauthenticated headers and handed to the application's webhook handler as if they were verified. Because the webhook HMAC secret is the app's single `client_secret` (shared across every shop that installs the app), any shop that has legitimately installed the app can capture a valid `(raw_body, hmac)` pair from its own webhooks and replay it with a forged `shop-domain` header, causing the gem to authenticate the request and attribute attacker-controlled body data to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` and `topic` values are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` and `request.topic` to build the metadata dispatched to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(client_secret, to_signable_string)`, i.e. `HMAC(client_secret, raw_body)`, and compares it to the received signature — it never incorporates `shop` or `topic`: [4](#0-3) 

This breaks the intended identity binding: the equality that should hold is `HMAC(client_secret, raw_body ‖ shop ‖ topic) == received_signature`, but the gem only enforces `HMAC(client_secret, raw_body) == received_signature`, leaving `shop` and `topic` outside the signed scope even though they are the two fields the handler uses to decide *which tenant* and *which workflow* the payload applies to.

Because Shopify signs webhooks with the app-wide `client_secret` (not a per-shop secret), any shop with a legitimate install of the app can obtain a fully valid `(raw_body, X-Shopify-Hmac-Sha256)` pair from webhooks sent to its own endpoint, then resend that exact body/signature to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) changed to target a different, victim shop. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` will happily call the app's handler with `WebhookMetadata.new(shop: <victim-shop>, topic: <attacker-chosen-topic>, body: <attacker-controlled-json>, ...)`.

### Impact Explanation
This is a cross-tenant data injection: an unprivileged attacker (any merchant who installs the app, which typically requires no special vetting) can make the gem accept a "verified" webhook body under a victim shop's identity. Depending on how the host app's handlers use `WebhookMetadata#shop`/`#body` (e.g., updating per-shop billing/subscription state, processing `customers/data_request` or `shop/redact` compliance webhooks, or writing order/customer data keyed by `shop`), this can lead to writing or deleting data attributed to a shop the attacker does not control — a cross-tenant access violation, which the rules classify as Critical.

### Likelihood Explanation
Likelihood is realistic but requires a legitimate install: the attacker must install the target app on their own store (something any unprivileged internet user can normally do for a public app) to capture a valid signed webhook, then replay it with a rewritten `shop-domain` header against the app's public webhook endpoint. No access to the victim's credentials, the app's `client_secret`, or any privileged account is required — only observation of the attacker's own legitimately-received webhook traffic and header manipulation.

### Recommendation
Include `shop` and `topic` (and any other fields the handler trusts) inside the HMAC-signed scope, or independently verify that the `X-Shopify-Shop-Domain` header corresponds to a shop with an active, previously-established session/installation before dispatching to the handler. At minimum, `Registry.process` should cross-check `request.shop` against the session/shop that the webhook subscription was registered for, rather than trusting the header verbatim once the body-only HMAC succeeds.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged install).
2. Shopify sends a legitimate webhook to the app, e.g. `orders/paid`, with body `B` and headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC over B, computed with the app's client_secret>`
3. Attacker captures `(B, HMAC)` and resends it to the app's webhook endpoint, only changing the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed; `HmacValidator.validate(request)` in `Registry.process` recomputes `HMAC(client_secret, B)`, which still matches because `B` and the secret are unchanged — validation passes. [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
