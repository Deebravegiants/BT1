Based on the analysis, I found a valid analog to the "unbounded owner privilege / unenforced cap" bug class in the orb-core signup authorization flow.

### Title
Client-Determined Signup Success Bypasses Backend Fraud/Dedup Enforcement in User-Centric Signups - (File: src/plans/mod.rs)

### Summary
The `ForgottenRunesWarriorsMinter.teamSummon()` bug allowed a privileged actor to bypass an intended, documented enforcement boundary (a minting cap) because the enforcement was never encoded in the contract logic — it existed only "by design"/off-chain trust. The orb-core analog is `MasterPlan::do_signup` in [1](#0-0) , where the decision of whether a signup succeeded is made **entirely locally on the Orb**, bypassing the backend's authoritative dedup/fraud enforcement (`enroll_user`/`signup_post`/`signup_poll`), whenever `user_centric_signup` is true.

### Finding Description
In `do_signup`, after biometric capture and PCP upload, the code branches on `user_centric_signup` (a flag sourced from `qr_codes.user_data.user_centric_signup`, itself derived from `backend::user_status::UserData` at [2](#0-1) ): [1](#0-0) 

When `user_centric_signup` is `true` and the operator/orb config `ignore_user_centric_signups` is `false` (the default, see [3](#0-2) ), the Orb **never calls `enroll_user`** — the function that performs the network round-trip to the backend's `signup_post`/`signup_poll` endpoints, which is explicitly documented as being responsible for detecting "Backend duplicates," "Backend legacy signup requests," "Backend inflight matches," and "Backend detected fraud" (comment block in [4](#0-3) ). Instead, `success` is derived purely from `signup_reason`, a value computed entirely on-device from the local biometric pipeline result and the local `detect_fraud` check (`src/plans/mod.rs` line 565-571, computed before the branch).

This mirrors the `teamSummon()` root cause exactly: an enforcement mechanism (dedup/fraud checks against a global, authoritative ledger — analogous to a hard-coded mint cap) is **documented as necessary** but is **not actually invoked** on this code path; only a local, unresolvable-by-the-server determination is trusted. The `SignupReason` enum comment itself flags the distinction: "Signup was detected as a fraud attempt at the orb (**not to be confused with the backend fraud checks**)" ( [5](#0-4) ) — explicitly acknowledging these are different, non-overlapping checks, yet the user-centric path relies solely on the weaker, local one.

### Impact Explanation
This allows cross-signup state bleed / unauthorized signup attribution: a user (or app) that qualifies for `user_centric_signup` can be granted a "successful" enrollment status by the Orb without the backend's dedup/inflight-match/legacy-signup fraud logic ever running against the global signup corpus for that particular success determination. Combined with the fact that `PCP` data is still uploaded to the backend asynchronously (potentially after `success` has already been reported to the app/UI via `SignupEnded`), there is a window where the locally-declared "success" outcome and the backend's eventual authoritative dedup verdict can diverge — the equivalent of the Orb "minting" a successful-signup attestation without waiting for the authoritative check that was designed to gate it.

### Likelihood Explanation
This path is reached whenever the backend marks a QR-code's `authenticated_app_data.user_centric_signup` as `true` (an authenticated, hash-verified field from the backend, see [6](#0-5) ), which is a normal, unprivileged, reachable production configuration (app-centric self-serve signups), not a test-only or feature-gated path — `ignore_user_centric_signups` defaults to `false`, meaning this behavior is the default when the backend opts an app-centric flow into this mode.

### Recommendation
Require the Orb to always perform (or at minimum, always await/confirm) the backend `signup_post`/`signup_poll` round trip before reporting a signup as `Success`, even for `user_centric_signup` flows, so that dedup and backend-fraud enforcement cannot be structurally skipped by a client-observable flag. If the local `signup_reason` is to be trusted for UX responsiveness, ensure the final authoritative `SignupStatus` recorded and acted upon (e.g., PCP retention, dbus `signup_finished`) is reconciled with the backend's asynchronous dedup verdict.

### Proof of Concept
1. Backend returns `authenticated_app_data.user_centric_signup = true` for a given user QR code, verified via `user_data.verify(user_data_hash)` in `src/backend/user_status.rs`.
2. Orb runs `do_signup`; `qr_codes.user_data.user_centric_signup` propagates to line 573 of `src/plans/mod.rs`.
3. `orb.config.lock().await.ignore_user_centric_signups` is `false` (default per `src/config.rs` line 121/265-266).
4. `do_signup` takes the branch at `src/plans/mod.rs` lines 639-645 and sets `success = (signup_reason == SignupReason::Normal)` — computed solely from local pipeline/fraud results — never calling `self.enroll_user(...)`, i.e., never contacting `signup_post`/`signup_poll` to consult the backend's dedup/inflight-match/fraud database for this determination.
