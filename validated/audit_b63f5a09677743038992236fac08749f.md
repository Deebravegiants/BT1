### Title
Front-runnable, deterministic lockup account address lets an unprivileged attacker permanently squat a victim's lockup account and strip vesting/termination controls - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup contract's account ID solely from `sha256(owner_account_id)` and creates it with a one-shot `Promise::new(lockup_account_id).create_account()...`, with no binding to the deposit amount, vesting terms, or caller identity. [1](#0-0)  Any unprivileged account can call this public, payable function with an arbitrary `owner_account_id` (not necessarily their own) and attacker-chosen `vesting_schedule`/`lockup_duration`/`release_duration`/`whitelist_account_id` parameters. [2](#0-1)  Because NEAR account creation is a one-time, irreversible event and the resulting account name has no salt beyond the victim's `owner_account_id`, this is the same "deterministic account can only be initialized once" root cause as the reported Solana `InitializeNFTAccount`/PDA issue.

### Finding Description
In `lockup-factory/src/lib.rs`, `create()` computes:
```rust
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [3](#0-2) 

This address depends only on `owner_account_id`, which is fully attacker-controlled input, not the caller's own identity. `create()` then immediately fires `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(...).function_call("new", ...)` [4](#0-3) , with `vesting_schedule`, `foundation_account_id` (only set when `vesting_schedule.is_some()`), `lockup_duration`, `release_duration`, and `whitelist_account_id` all supplied by whoever calls `create`, not by any owner-side authorization. [5](#0-4) 

Since NEAR account creation succeeds exactly once (the second `create_account()` receipt for the same account fails), any account attempting to build a legitimate lockup for a given `owner_account_id` after an attacker has already done so will simply fail and be refunded via `on_lockup_create` [6](#0-5) . There is no reuse mechanism, no check that the caller is the intended owner or an authorized issuer (e.g. the foundation), and no way to later correct or replace a maliciously-initialized lockup account for that `owner_account_id` — this mirrors the reported `init`-only-once collateral account bug where a single-shot deterministic account blocks all future legitimate initialization.

Critically, `foundation_account_id` (which grants the NEAR Foundation the ability to terminate/claw back unvested tokens) is only attached when the caller supplies a `vesting_schedule` [7](#0-6) . An attacker can front-run the legitimate creation for a targeted `owner_account_id` by calling `create()` with `vesting_schedule = None`, permanently locking in a lockup contract for that owner with no vesting schedule and no foundation termination rights, before the legitimate (vested) lockup can ever be created.

### Impact Explanation
This is a High-severity account-binding failure: an unprivileged attacker can (a) deny an intended owner/foundation the ability to ever create their designated vested lockup contract (permanent DoS on a specific NEAR account-identity's lockup slot), and (b) unilaterally choose the lockup's parameters (duration, vesting presence, whitelist) for a target account before the legitimate issuer does, stripping the vesting/termination guarantee the foundation intended to impose. This matches "High: state-transition bypass / account-binding failure ... that lets an unprivileged user perform actions beyond intended authority" and "High: vesting ... divergence that lets an unprivileged user ... bypass ... limits" in the allowed impact scope. It does not directly let the attacker steal NEAR (the deposit only funds the account under `owner_account_id`'s control), but it does let them irrevocably strip foundation vesting/termination control over that account's lockup, which is itself a protocol-security-relevant, unrecoverable state.

### Likelihood Explanation
Likelihood is high for any environment where lockup account IDs for known/anticipated owners (e.g., public investor or team account IDs) are predictable ahead of the intended creation transaction, since `create()` is a public, unauthenticated, payable method requiring only the `MIN_ATTACHED_BALANCE` (3.5 NEAR) [8](#0-7) [9](#0-8) . Any attacker who learns (or predicts) the target `owner_account_id` before the foundation's official creation transaction lands (e.g., via mempool observation or public knowledge of upcoming lockups) can win the race trivially.

### Recommendation
Restrict `create()` so the deterministic address cannot be squatted with attacker-chosen terms: e.g., require the transaction predecessor to equal `owner_account_id` (self-service creation) or restrict `create()` to only the foundation/whitelisted issuer, and/or include the vesting-schedule hash / a caller-specific salt / a nonce in the derived account ID so it cannot be a single global slot per `owner_account_id`. At minimum, always require a `vesting_schedule` and always attach `foundation_account_id` regardless of caller input, and disallow arbitrary third parties from specifying `owner_account_id` for someone else without their authorization.

### Proof of Concept
1. Attacker observes/knows the account ID `victim.near` is intended to receive an official vested lockup from the foundation.
2. Attacker computes `lockup_account_id = sha256("victim.near")[..20] + "." + lockup-factory-account` (same computation as in `create()`) [3](#0-2) .
3. Attacker calls `create(owner_account_id="victim.near", lockup_duration=<attacker choice>, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` with `MIN_ATTACHED_BALANCE` attached, from their own unprivileged account.
4. The factory creates and deploys the lockup contract at the deterministic address with owner `victim.near` but no vesting schedule / no foundation termination rights, and the account is now permanently occupied. [10](#0-9) 
5. When the foundation later attempts the legitimate `create()` call for `victim.near` with the real vesting schedule, `create_account()` fails because the account already exists; `on_lockup_create` merely refunds the foundation's deposit [6](#0-5) , and the legitimate vested lockup can never be created for that account.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
