### Title
Unregistered source-chain fallback in `IntentGatewayV2.instance()` lets an attacker forge `RedeemEscrow`/`RefundEscrow` deliveries and drain escrow - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` authenticates incoming cross-chain Hyperbridge messages by checking that the `from` field of the `PostRequest` matches the gateway instance registered for `request.source`. When no instance has been registered for a given source chain, `instance()` silently falls back to returning `address(this)` instead of reverting, so the "delegated" trust check passes for *any* message whose `from` equals the receiving contract's own address — regardless of whether that source chain has ever been vetted or paired with a real gateway deployment.

### Finding Description
`instance()` is defined as: [1](#0-0) 
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}

function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    // IntentGateway only accepts incoming assets from itself or known instances
    if (instance(request.source) != module) revert Unauthorized();
}
```
This is the delegated-authorization gate for `RedeemEscrow` and `RefundEscrow` deliveries — the analog of the CVE's "main origin permission delegation" check. The check is supposed to delegate trust only to a *registered* peer gateway for `request.source`. Instead, for any `request.source` that has **not** been explicitly registered via `NewDeployment`, `instance()` defaults to `address(this)`. Because the gateway's bytecode/address is deployed deterministically across chains (the codebase itself notes "preserving deterministic CREATE2 deployment addresses" for this contract family, see `evm/src/apps/intentsv2/IntentsBase.sol` line 385), an attacker who can get a contract deployed at that same address on any chain Hyperbridge has a consensus/state client for (but which the gateway has never registered as a peer) automatically satisfies `instance(request.source) == module`.

Compare this to the corrected `_instance()` used by the newer `IntentsBase.sol`/`ExtrinsicIntents.sol` implementation, which reverts with `UnknownInstance` instead of defaulting to `address(this)`: [2](#0-1) 

The Tron contract still ships the vulnerable pattern and reaches the same privileged withdrawal logic: [3](#0-2) 

### Impact Explanation
`RedeemEscrow` and `RefundEscrow` both flow into `_withdraw`, which releases previously escrowed input tokens/fees to a beneficiary address encoded in the forged message body. Bypassing `authenticate()` lets an attacker construct an ISMP `PostRequest` (dispatched from a real, ISMP-verifiable but unregistered/foreign state machine, with `from` set to the gateway's own address) whose membership proof legitimately verifies, but whose *authorization semantics* are forged — the module never actually authorized this withdrawal. This allows theft of all escrowed order funds and fee balances held by the gateway (concrete theft of funds, directly on the reachable path "relayed proof → module `on_accept`/`onAccept`" called out in the scope rules).

### Likelihood Explanation
Reachable by any relayer/intent solver who can (a) get a contract deployed at the gateway's known, deterministic address on some EVM-compatible chain that Hyperbridge has a consensus client for but that the gateway operator has not registered as a peer, and (b) dispatch/relay a request from that chain with a forged `RedeemEscrow`/`RefundEscrow` body. No admin or governance compromise is required — only a relayer submitting a proof for a message dispatched from an address they control on an unregistered chain. The `_checkRelayer` gate (`onlyHost`/relayer allowlist) does not prevent this, since it only restricts *who* can deliver, not the source-chain authentication logic itself.

### Recommendation
Replace `instance()`'s silent `address(this)` fallback with an explicit revert (`UnknownInstance`), mirroring the already-corrected `_instance()` in `evm/src/apps/intentsv2/IntentsBase.sol`, so that `authenticate()` only accepts `RedeemEscrow`/`RefundEscrow` messages from state machines that have been explicitly registered via `NewDeployment`/`_addDeployment`.

### Proof of Concept
1. Identify that `IntentGatewayV2` (Tron) is deployed at a known deterministic address `A` via CREATE2-style deployment used elsewhere in the codebase.
2. Deploy an arbitrary contract to address `A` on some EVM chain `X` for which Hyperbridge has a consensus/state client but which has **not** been registered in `_instances` (i.e., `NewDeployment` was never dispatched for `X`).
3. From that contract on chain `X`, dispatch (or otherwise get relayed) a Hyperbridge `PostRequest` with:
   - `source = X`
   - `from = abi.encodePacked(A)` (20 bytes)
   - `body = abi.encodePacked(uint8(RequestKind.RedeemEscrow), abi.encode(WithdrawalRequest({commitment: <any valid/known commitment with escrow>, tokens: <escrowed tokens>, beneficiary: <attacker>})))`
4. A relayer submits the membership proof to the real host; `onAccept` calls `authenticate(request)`, which calls `instance(X)`. Since `X` is unregistered, `instance(X)` returns `address(this) == A == module`, so authentication passes.
5. `_withdraw` releases the escrowed tokens to the attacker-controlled `beneficiary`.

Note: full confirmation of the exact `onAccept` wiring in `evm/tron/contracts/apps/IntentGatewayV2.sol` beyond the reviewed excerpts (lines 1–120, 271–330) was limited by index size; the `authenticate`/`instance` pair and `RequestKind` enum confirmed above are sufficient to establish the vulnerable pattern, but a full read of the file (available via a Devin session) is recommended to confirm no additional guard exists between `onAccept` and `authenticate` for this specific Tron variant.
