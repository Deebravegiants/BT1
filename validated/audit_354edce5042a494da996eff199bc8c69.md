### Title
Webhook shop-identity spoofing via HMAC that covers only the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to application webhook handlers from an HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. This breaks the equality the host application relies on: *shop authenticated by the HMAC* ≠ *shop used to route/attribute the webhook*.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes and compares the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the body: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all parsed straight from headers that are never part of the signed bytes: [3](#0-2) 

`Registry.process` accepts a request as authentic once `HmacValidator.validate(request)` passes, then forwards `request.shop` (the unauthenticated header) straight into the handler as the tenant identifier: [4](#0-3) 

Because the same app `client_secret` is shared across every shop/tenant that installs the app, a party who can install the app on their own store (a normal, unprivileged merchant/dev-store signup — not a privileged account, not the app's `client_secret`) legitimately receives webhooks signed with that secret over a body they control. The `hmac` and `raw_body` pair is valid for *any* shop-domain header value, since the header is not part of the signed material. Replaying that (`raw_body`, `hmac`) pair to the app's webhook endpoint with a different `shopify-shop-domain` header value causes `HmacValidator.validate` to still return `true` (the signature matches the body), while `Registry.process` attributes the webhook — including its topic and body content — to a shop the attacker does not control.

This is exactly the class of bug called out in the prompt: *"a field acted on but not covered by the HMAC"* — here, `shop` (and also `topic`/`webhook_id`) are consumed and trusted by `Registry.process`/`WebhookMetadata` without being bound to the HMAC that establishes authenticity of the request.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to select which tenant's session/data to update (the documented purpose of this field), an attacker-controlled shop can force the library to authenticate a forged/replayed body as if it originated from a victim shop, causing the application to process attacker-chosen webhook payloads (e.g. `orders/create`, `app/uninstalled`, `customers/redact`) under the victim's tenant identity. This is a cross-tenant integrity/confidentiality issue: the gem's HMAC check gives applications false assurance that `request.shop` is trustworthy, when in fact it is only the request body that has been authenticated.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the target public app on an attacker-owned/free development store (ordinary, unprivileged action available to any internet user for public apps), (2) capturing a legitimate `(raw_body, hmac)` pair sent to the attacker's own endpoint, and (3) replaying it to the shared webhook endpoint with a forged `shopify-shop-domain` header. No access to the app's `client_secret`, no TLS interception, and no privileged account are needed — this fits squarely in the in-scope threat model.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material that `HmacValidator` verifies, or otherwise cryptographically bind the header claims to the body before trusting `request.shop` for tenant attribution — e.g., have `Request#to_signable_string` incorporate the shop-domain header, or independently verify that the shop in the header matches an expected, session-bound identity before dispatching to `WebhookMetadata`.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `evil-shop.myshopify.com`. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` and `X-Shopify-Shop-Domain: evil-shop.myshopify.com`.
2. Capture `B` and the HMAC value.
3. Replay a request to the same endpoint with the identical body `B` and HMAC header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (they are only checked for presence, not for binding), and `HmacValidator.validate` returns `true` since it only checks `B` against the HMAC: [4](#0-3) 
5. `Registry.process` dispatches to the app's handler with `shop: "victim-shop.myshopify.com"`, causing the application to treat attacker-controlled data as authenticated for the victim tenant.
