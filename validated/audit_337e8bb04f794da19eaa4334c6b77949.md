### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` allows OAuth redirect to attacker-controlled domain (forced OAuth phishing) - (`lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the Shopify authorization redirect URL directly from the caller-supplied `shop` string without validating that it is a genuine Shopify domain, while every other credential-issuing entry point in the same library (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!` before using the shop value to build a request host.

### Finding Description
`begin_auth` receives `shop:` (in real integrations this is taken from an unauthenticated source such as a `Shop` request header or query parameter, as shown in the gem's own documentation example at `docs/usage/oauth.md:181-185`) and passes it straight into `auth_base_uri`: [1](#0-0) 

```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
```

`auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"` is then returned to the caller and used as an HTTP redirect target for the merchant's browser. [2](#0-1) 

No call to `ShopifyAPI::Utils::ShopValidator.sanitize!`/`sanitize_shop_domain` is made anywhere in `begin_auth` or `auth_base_uri`. Contrast this with the other credential-exchanging modules that were hardened with the same validator (added specifically for this purpose per `CHANGELOG.md:7`, "Add `ShopifyAPI::Utils::ShopValidator`..."): [3](#0-2) [4](#0-3) [5](#0-4) 

`ShopValidator.sanitize!` is designed exactly to reject non-Shopify hosts (`test_rejects_attacker_controlled_domain`, `test_rejects_non_shopify_domain`) and only accept `TRUSTED_SHOPIFY_DOMAINS` (myshopify.com/io, spin.dev, shop.dev, shopify.com): [6](#0-5) [7](#0-6) 

The identity binding this breaks: the redirect host that the merchant's browser is sent to should equal a value drawn from `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (i.e. a real Shopify host), but in `begin_auth` the redirect host equals the raw, attacker-influenced `shop` string with no such equality check enforced.

### Impact Explanation
An unprivileged internet user who can influence the `shop` value passed into `begin_auth` (e.g. by controlling the `Shop` header/query param on a request to the host application's login route, exactly as shown in this gem's own documented integration pattern) can cause the app to generate an authorization URL pointing at an attacker-controlled host: `https://evil.example/admin/oauth/authorize?client_id=<real client_id>&scope=...&redirect_uri=<real app host>/auth/callback&state=<nonce>`. When the app redirects the victim merchant's browser there, the attacker's page can impersonate Shopify's OAuth consent screen and capture the merchant's Shopify credentials or otherwise force a spoofed "authorization" flow back to the app's genuine callback (forced OAuth completion / phishing setup). This matches the accepted High-impact class "session fixation or forced OAuth completion." It does not by itself leak `client_secret` (not sent in `begin_auth`), but it does expose the app's `client_id` and internal `redirect_uri` to an attacker-chosen host and stages a credential-phishing redirect against the merchant, entirely reachable without any secret, token, or privileged access.

### Likelihood Explanation
High reachability: the vulnerable code path is the documented, first step of the OAuth flow (`begin_auth`), intended to be driven by request data supplied by whoever visits the app's login endpoint — no authentication or prior session is required. The only precondition is that the host application does not itself re-validate the shop parameter before calling `begin_auth` (which the gem's own docs do not instruct developers to do, since the gem is expected to perform this validation, as it now does in sibling methods).

### Recommendation
Validate/normalize `shop` in `Oauth.begin_auth` using the existing `ShopifyAPI::Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) before it is used to construct `auth_base_uri`, mirroring the pattern already applied in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`. Raise `Errors::InvalidShopError` for any shop value that does not resolve to a trusted Shopify domain before generating the authorization redirect.

### Proof of Concept
```ruby
ShopifyAPI::Context.setup(api_key: "APP_KEY", api_secret_key: "APP_SECRET",
  host_name: "myapp.example.com", scope: "read_products", is_embedded: false)

result = ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.example", redirect_path: "/auth/callback")
puts result[:auth_route]
# => "https://evil.example/admin/oauth/authorize?client_id=APP_KEY&scope=read_products&redirect_uri=https://myapp.example.com/auth/callback&state=...&grant_options%5B%5D=per-user"
```
No `ShopifyAPI::Errors::InvalidShopError` (or any error) is raised, and the app would redirect a real merchant's browser to `evil.example`, unlike the equivalent flows in `client_credentials`/`refresh_access_token`/`migrate_to_expiring_token`, which reject this input via `ShopValidator.sanitize!`.

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings

          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
