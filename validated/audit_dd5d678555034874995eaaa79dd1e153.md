### Title
Unbounded "dust" collection during predispatch fee-on-transfer/swap sweeps can permanently forfeit economically significant user funds - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
The Increment Protocol report describes a fixed, notional-value-blind dust threshold that can donate economically significant token amounts (e.g., 1/10 vBTC ≈ $2,000) to the Insurance contract simply because the raw quantity fell under an absolute cutoff, regardless of what that quantity is actually worth. The analogous pattern exists in `IntentGatewayV2.placeOrder`'s predispatch-sweep logic: any amount received above the order's declared `order.inputs[i].amount` is unconditionally classified as "dust," emitted via `DustCollected`, and left stranded in the contract with no path back to the user — with no upper bound, no notional-value check, and no relation to what a "negligible" leftover should be.

### Finding Description
In the predispatch branch of `placeOrder`, the gateway executes an arbitrary user-supplied call (`order.predispatch.call`) via `ICallDispatcher`, then sweeps whatever balance resulted back to itself and measures the actual amount received per input token: [1](#0-0) 

```solidity
if (received > order.inputs[i].amount) {
    uint256 dust = received - order.inputs[i].amount;
    emit DustCollected(token, dust);
} else {
    order.inputs[i].amount = received;
}
```

There is no cap on `dust`, and no comparison against the token's actual value (unlike Increment's recommended fix of pricing the leftover via `indexPrice` before treating it as dust). Any surplus produced by the predispatch call — whether 1 wei or a substantial fraction of a high-value token's output from a swap, redemption, or other arbitrary call — is classified identically as "dust" and is not returned to the order's escrow, not credited to the user, and not refundable through `cancelOrder`, since the commitment/escrow is built from the reduced (`order.inputs[i].amount`) figure, not the actual received balance.

The same unbounded, magnitude-blind classification recurs in the Tron variant of the contract: [2](#0-1) 

This mirrors the root cause in the Increment report exactly: the protocol collapses "amount above X" into "dust" using a naive, absolute (and here, completely unbounded) delta, with no economic-significance check, so a user (or a solver front-running/crafting predispatch calldata to produce excess proceeds) can have arbitrarily large value siphoned off as if it were negligible rounding residue.

### Impact Explanation
Because the predispatch path executes an externally supplied `Call` (`order.predispatch.call`) before the sweep, the amount "received" is fully dependent on whatever that call does — e.g., a DEX swap, a redemption, or any other logic the order author encodes. If that logic yields materially more of the input token than `order.inputs[i].amount` (intentionally, by misconfiguration, by price movement between quoting and execution, or via a fee-on-transfer/rebasing token whose transfer yields more than expected), the entire surplus — which could represent a economically significant amount of a high-value token — is irrevocably swept out of the user's control and only emitted as an event; it never returns to the escrow or to the user. This is a permanent, protocol-level loss of funds triggered by a completely permissionless user action (`placeOrder`), matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
`placeOrder` with a `predispatch.call`/`predispatch.assets` is a normal, fully permissionless code path available to any user constructing an order (e.g., orders that first perform an on-chain swap before escrowing the swap's output). Any deviation between the predispatch call's actual output and the pre-declared `order.inputs[i].amount` — which is entirely plausible for slippage-sensitive operations, rebasing/fee tokens, or simple estimation error by the order author's off-chain tooling — triggers the unbounded dust sweep automatically, with no user opt-in or confirmation step.

### Recommendation
Do not treat the entire surplus (`received - order.inputs[i].amount`) as dust unconditionally. Either:
1. Return/credit the excess back into the order's escrowed `amount` (as is already done in the non-predispatch branch, where `order.inputs[i].amount = received` when `received <= declared amount`), rather than discarding any amount above the declared figure, or
2. If some sweep-to-protocol behavior is intended for genuine leftover rounding dust, bound it to a small, protocol-configured absolute/notional cap (and/or express it in USD-equivalent terms as Increment's fix recommends) so amounts that are not economically negligible are refunded to the user's escrow instead of being irrecoverably classified as dust.

### Proof of Concept
1. An order author (or malicious solver assisting in constructing the predispatch calldata) crafts `order.predispatch.call` such that the executed call produces `received` tokens materially greater than `order.inputs[i].amount` for one of the declared input tokens (e.g., a swap or redemption that yields more tokens than the order declares, due to favorable price movement or intentional overshoot).
2. `placeOrder` executes the call, measures `received`, and since `received > order.inputs[i].amount`, computes `dust = received - order.inputs[i].amount` and emits `DustCollected(token, dust)`. See [3](#0-2) .
3. `dust` remains in the `IntentGatewayV2` contract's balance, permanently excluded from `_orders[commitment][token]` (which is only credited with `order.inputs[i].amount`, the pre-declared, smaller figure).
4. Neither `cancelOrder` nor `fillOrder`'s settlement path (`_withdraw`, keyed off `_orders[commitment][token]`) has any mechanism to return `dust` to the user; it is unrecoverable. [4](#0-3)
