## Finding

### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value that is later used as the tenant key for dispatching webhook data purely from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies is computed exclusively over the raw request body. This breaks the identity binding between "HMAC-authenticated bytes" and "the shop the payload is attributed to," mirroring the reported bug class of a field being acted on without being covered by the integrity check.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `#shop` is read straight from the request headers, entirely outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC against `request.to_signable_string` (the body only), and then immediately trusts `request.shop` (the unsigned header) to build the `WebhookMetadata` object handed to the app's business logic: [3](#0-2) 

`Utils::HmacValidator.validate` re-computes the HMAC over `verifiable_query.to_signable_string` using the shared `api_secret_key`/`old_api_secret_key` and compares it to the supplied `hmac` header — it never incorporates `shop`: [4](#0-3) 

The equality this is supposed to guarantee is:
`shop_the_hmac_authenticates == shop_the_handler_attributes_data_to`

In reality, the HMAC only proves "these body bytes were produced using the app's `client_secret`" — it says nothing about which shop the header claims to represent. Because the `client_secret` is shared across every shop that installs the app, **any merchant who installs the app** can capture a validly-signed webhook body+HMAC pair for their own shop (e.g. by triggering a benign webhook topic on their own store), and then replay that exact `raw_body`/`hmac-sha256` pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value for a different, victim shop. Since the endpoint is a plain public HTTP receiver (not restricted to Shopify's IP range by this gem), any unprivileged internet actor who has legitimately installed the app once can forge this request. `HmacValidator.validate` will pass (the body/HMAC pair is genuinely valid), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (even trial) installer of the app can make the app process/attribute arbitrary previously-captured (but validly-HMAC-signed) webhook payloads as if they originated from a different merchant's shop, because the `shop` value used as the identity/tenant key is never bound to the HMAC. Depending on how the host application's webhook handler uses `data.shop` (e.g., to look up/update per-shop state, mark uninstall, disable billing, or otherwise mutate merchant-tenant records), this enables cross-tenant data corruption or spoofed events attributed to a shop the attacker doesn't control — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Medium-High: the attacker only needs the ability to install the app on any shop (including their own, free/dev store) to obtain a genuinely valid `(raw_body, hmac)` pair, and the ability to POST directly to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header. No access token, `client_secret`, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the signed payload verification, e.g. by requiring the host application to independently confirm the `shop-domain` header corresponds to a shop with an active, stored session/access token before trusting `WebhookMetadata#shop`, or by validating the request only after confirming the request originated from Shopify's known IP ranges/TLS-terminated delivery path, since the gem-level `to_signable_string` cannot itself include the shop without additional Shopify-side signing support.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers any webhook subscription so Shopify delivers a real webhook to a URL the attacker controls (or captures the raw POST via a proxy).
2. Attacker now possesses a valid `(raw_body, x-shopify-hmac-sha256)` pair that will pass `HmacValidator.validate` for this app's `client_secret`, since the signature covers only the raw body (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
3. Attacker sends a POST directly to the app's public webhook endpoint with the captured `raw_body` and `hmac-sha256` header unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds (body/HMAC match), then builds `WebhookMetadata.new(... shop: request.shop ...)` using the attacker-supplied `victim-shop.myshopify.com` value (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the app's handler to process/attribute the payload to the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
