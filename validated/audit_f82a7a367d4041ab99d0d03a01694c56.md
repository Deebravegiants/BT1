### Title
Webhook `shop` Identity Not Bound to HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (shop-domain) attribute — the value used to identify *which tenant* a webhook belongs to — is read from an HTTP header that is never included in the signed bytes. `Registry.process` trusts this header value and forwards it unchecked to the host app's `WebhookHandler`, breaking the binding `signed_bytes == acted_on_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against a signature computed over `verifiable_query.to_signable_string` (i.e., the body), never touching `shop`: [3](#0-2) [4](#0-3) 

`Registry.process` performs exactly this HMAC check and then dispatches the handler using the *unverified* `request.shop`: [5](#0-4) 

`WebhookMetadata.shop` is the field the host application is expected to key its tenant lookups on: [6](#0-5) 

This is the same bug class as the referenced report: a field that governs which entity an action applies to (`shop`, analogous to `price1Average`'s native-asset binding) is not covered by the integrity check (HMAC, analogous to the missing zero-check binding native price to the aggregator), so the check answers permissively for a value the header, not the signature, controls.

Equality that should hold but doesn't: `verified_bytes ⊇ shop` (the shop identity should be part of what `HmacValidator` verifies) is actually `verified_bytes = raw_body` and `shop ∉ raw_body-coverage`.

### Impact Explanation
The Shopify webhook HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across *all* merchant shops that install a given app — it is not per-shop. Consequently, any party capable of producing (or replaying) one validly-signed webhook body for the shared secret can attach an arbitrary `shop-domain` header to it, and `Registry.process` will accept it and hand `WebhookMetadata` with the attacker-chosen `shop` to the host app's handler. Since host apps are documented to key persistence/side effects (order sync, redact operations, entitlement changes, etc.) off `WebhookMetadata#shop`, this allows cross-tenant confusion: data or actions intended for shop A can be attributed to shop B purely by header manipulation, with the HMAC check still passing. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is High for any party who already receives legitimately-signed webhook traffic from the app (e.g., a merchant with their own installation, or anyone who can capture one webhook delivery) since they already possess body+HMAC pairs valid under the shared secret and only need to alter one header value to target another tenant — no knowledge of `client_secret` is required.

### Recommendation
Bind `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cross-check the header-derived `shop` against an independently-authenticated source (e.g., require the caller to also present a valid `X-Shopify-Api-Version`/registered webhook id lookup tied to a specific shop, or include the shop domain in the signable string used by `HmacValidator`). At minimum, `Request#to_signable_string` should not allow the `shop` attribute exposed via `WebhookMetadata` to be sourced from unauthenticated header bytes when the HMAC only covers the body.

### Proof of Concept
1. Operate/own Shop A, which is installed on the target app and therefore receives genuinely HMAC-signed webhooks from Shopify for its own events (headers include `X-Shopify-Hmac-Sha256`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, plus a JSON body).
2. Capture one such webhook POST (or trigger an event to generate one, e.g. `orders/create`).
3. Replay the exact same request to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header value with `victim-shop.myshopify.com`. Leave body and `X-Shopify-Hmac-Sha256` untouched.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-derives the HMAC from `request.to_signable_string` (`@raw_body`) — this still matches because the body wasn't changed: [7](#0-6) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs whatever tenant-scoped action the host app implements for that `shop`, even though the payload originated from and was cryptographically valid only for Shop A.
