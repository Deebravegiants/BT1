### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not covered by the HMAC, allowing tenant spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) against the HMAC header. The `shop` value that is subsequently trusted and handed to the app's handler as the tenant identifier is read from the `x-shopify-shop-domain` header, which is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only ever inspects `verifiable_query.hmac` and `verifiable_query.to_signable_string` (i.e., the body), never the headers: [3](#0-2) 

`Webhooks::Registry.process` treats a successful HMAC check as authenticating the entire request, then forwards `request.shop` (an unauthenticated header value) directly into `WebhookMetadata`, which is the struct the host application's handler uses to decide which tenant/shop the event belongs to: [4](#0-3) [5](#0-4) 

This breaks the identity binding: **shop authenticated by HMAC (the raw body only) ≠ shop trusted as the tenant key (`request.shop` from an unsigned header)**. Since every shop installed on an app shares the same `client_secret`/`api_secret_key`, any merchant that legitimately receives one authentic webhook for their own shop possesses a byte-for-byte body + valid HMAC pair signed with the app's shared secret. That merchant (an unprivileged actor with respect to any other tenant of the same app) can replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a different, victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding bypass in this gem's webhook processing: the gem asserts to the calling application that a webhook body has been verified as coming from `shop`, when in fact `shop` was never authenticated. Any host app that uses `WebhookMetadata.shop` (or `.topic`/`.webhook_id`) as a trust boundary — e.g., to select which merchant's session/access token to act on, or to route data into the corresponding tenant's records — can be made to process data attributed to the wrong shop. This matches the report's bug class (a value acted upon that was not actually covered by the integrity check) and the rules' cross-tenant-access impact category.

### Likelihood Explanation
Requires only that the attacker be a legitimate merchant of the target app (already unprivileged relative to other tenants) who can capture one webhook delivery to their own shop (trivial — webhooks are delivered to the app's own endpoint, and the attacker controls a public endpoint or a proxy in front of the app for their own shop) and replay it with a modified `shop`-domain header (and/or `topic`/`webhook-id`) to the app's shared webhook endpoint. No secret material, TLS interception, or privileged access is needed — only header manipulation on a replayed, previously-valid request.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable material verified by `HmacValidator`, or otherwise cryptographically bind them (e.g., verify `shop` against Shopify's authoritative webhook metadata / require it be embedded and signed rather than taken from a mutable header) before constructing `WebhookMetadata`. At minimum, document clearly that `WebhookMetadata.shop`/`.topic` are unauthenticated and must not be used as a tenant trust boundary by consuming applications, and add integrity coverage for these fields in `Request#to_signable_string`.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`. The attacker (merchant of `shop-a`) receives a legitimate webhook at their own endpoint (or intercepts it via their own reverse proxy) with body `raw_body` and header `x-shopify-hmac-sha256: H` valid against the app's shared `api_secret_key` (see `lib/shopify_api/utils/hmac_validator.rb:26-31`, verifying only `raw_body`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a victim shop also using the app).
3. `ShopifyAPI::Webhooks::Request.new` accepts it (headers present) — `lib/shopify_api/webhooks/request.rb:45-63`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because it only checks `raw_body` against `H` — `lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:13-22`.
5. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` — `lib/shopify_api/webhooks/registry.rb:198-199` — even though the webhook body actually originated from and was signed for `shop-a`, demonstrating the app-level trust boundary confusion.
