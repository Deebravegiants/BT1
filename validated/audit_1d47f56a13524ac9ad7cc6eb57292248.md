### Title
Curve buy/sell permanently freezes if `IBounceLeveragedToken.exchangeRate()` reverts, since it is embedded in `Bonding.canGraduate` on every trade with no emergency path - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate()` calls the external, protocol-controlled `IBounceLeveragedToken(info.ltAddress).exchangeRate()` on essentially every curve trade path (both buy, via `_executeBuy`, and sell, via `Zap._sellInternal`). Because this external call is unconditionally embedded in the hot path with no fallback, any permanent revert condition inside BounceTech's `exchangeRate()` (or the LT contract in a state where that view call reverts) freezes both buying and selling for the affected curve token, with no rescue/emergency-withdraw mechanism in `Bonding` or `Zap` — mirroring the Stargate `updatePool()`/`totalAllocPoint == 0` class of bug (external, admin-influenced state causing a mandatory dependency call embedded in every deposit/withdraw to revert forever).

### Finding Description
`canGraduate(token_)` is a `public view` used as a mandatory pre-check on every trade: [1](#0-0) 

It calls `IBounceLeveragedToken(info.ltAddress).exchangeRate()` whenever `IPair(pair).tokenBalance() != 0` — i.e., on virtually every trade until the curve is fully sold out: [2](#0-1) 

This call is invoked unconditionally after every buy in `_executeBuy`: [3](#0-2) 

and again on every sell attempt, since `Zap._sellInternal` calls `bonding_.canGraduate(tokenAddress)` before doing any sell logic: [4](#0-3) 

There is no equivalent of `emergencyWithdraw()` anywhere in `Bonding` or `Zap` that lets a curve trader bypass `canGraduate`/`exchangeRate()` to pull out their curve position (curve tokens or the underlying LT the Pair holds) if the LT's `exchangeRate()` becomes permanently unavailable. Both entry (`buy`) and exit (`sell`) share the identical dependency, so unlike the Stargate case (where `deposit`/`withdraw` both call `updatePool`, but Stargate itself exposes `emergencyWithdraw` as an escape valve), alt.fun's own code provides no analogous bypass for this externally-controlled read.

### Impact Explanation
If BounceTech's `exchangeRate()` reverts unconditionally for a given LT (e.g., due to an internal division-by-zero triggered by an admin action on their side, a paused/bricked oracle path, or any other permanent revert condition in their contract), every curve token backed by that LT becomes permanently untradeable: `Zap.buy`/`Bonding.buy` revert because `_executeBuy` calls `canGraduate` post-trade, and `Zap.sell` reverts because `_sellInternal` calls `canGraduate` pre-trade. All LT already raised by the curve (sitting in the `Pair`) and all creator/trader positions in that curve become permanently locked, with no owner-level or permissionless rescue function to bypass the broken read and let holders exit. This is a freezing of trader/creator funds for the affected token, matching the "Medium" severity class of the analog report.

### Likelihood Explanation
Likelihood depends entirely on BounceTech's `exchangeRate()` implementation being able to enter a permanently-reverting state — which is external to alt.fun and not verifiable from `packages/contracts/src` alone (no BounceTech LT source is in scope). Given the analog report's precedent (an external protocol's admin action zeroing a denominator used by a dependency call baked into every core operation), this is a plausible but not certain class of bug; the alt.fun-side root cause — no emergency bypass despite depending on this external view in both buy and sell paths for every curve token — is concretely present.

### Recommendation
Add a permissionless emergency-exit path (e.g., an owner/keeper- or time-gated fallback) that lets `canGraduate` be skipped or defaults to `false`/`true` deterministically if `exchangeRate()` reverts (e.g., wrap the call in try/catch and treat a persistent revert as "not graduatable" so sells can proceed, or add a stuck-curve rescue function in `Bonding` that returns raised LT / burns curve tokens pro-rata without depending on `exchangeRate()`). At minimum, `Zap._sellInternal`'s `canGraduate` check should be defensively guarded so a broken LT `exchangeRate()` cannot block sells, since sells are the users' only exit from the curve.

### Proof of Concept
1. A token is launched and several traders buy into the curve via `Zap.buy` → `Bonding.buy` → `Router.buy`, raising LT into the `Pair` per [3](#0-2) .
2. BounceTech's LT contract enters a state where `exchangeRate()` unconditionally reverts (external precondition, analogous to Stargate's `totalAllocPoint == 0` division-by-zero).
3. Any subsequent `Zap.buy` call reverts because the post-trade `canGraduate(tokenAddress)` check in `Bonding._executeBuy` reverts when it calls `IBounceLeveragedToken(info.ltAddress).exchangeRate()` ( [2](#0-1) ).
4. Any subsequent `Zap.sell` call also reverts, because `_sellInternal` invokes the same `bonding_.canGraduate(tokenAddress)` check before any sell logic executes ( [4](#0-3) ).
5. With both `buy` and `sell` permanently reverting and no rescue function present in `Bonding.sol` or `Zap.sol`, all LT raised by the curve for that token, and all holders' curve positions, are permanently locked.

```text
    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
```
