### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body [1](#0-0) , while the `shop` identity used downstream by handlers is read from the `shop-domain` header, which is never included in the signed data [2](#0-1) . `ShopifyAPI::Utils::HmacValidator.validate` only re-computes the signature over `to_signable_string` (the raw body) and compares it to the `hmac` header [3](#0-2) ; it never checks that the `shop` field is consistent with, or bound to, the signed payload. `ShopifyAPI::Webhooks::Registry.process` performs the HMAC check and then blindly forwards `request.shop` to the app's handler as the shop the webhook belongs to [4](#0-3) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, raw_body)` should imply `shop == the shop that Shopify actually generated this raw_body for`. In this gem that equality is never enforced — the HMAC binds only the body bytes, not the shop header.

The `api_secret_key` used for webhook HMACs is a single app-level secret shared across every shop/tenant that installs the app (it's not shop-specific) [5](#0-4) . An unprivileged actor who installs the app on their own (attacker-controlled) shop legitimately receives real webhooks from Shopify, each with a valid `raw_body` + `hmac` pair signed with that same app secret, and their own `shop-domain` header. Because `to_signable_string` never includes the shop header [1](#0-0) , the attacker can replay that exact `raw_body`/`hmac` pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with any victim shop domain. `HmacValidator.validate` still succeeds because the body is unchanged [5](#0-4) , and `Registry.process` hands the handler a `WebhookMetadata` tagged with the attacker-chosen `shop` value [4](#0-3) .

### Impact Explanation
This is a cross-tenant boundary break: an actor with only a low-privilege, self-controlled shop can make the host application attribute forged/replayed webhook data (order data, app-uninstalled events, GDPR events, etc.) to a completely different, victim shop that also uses the app. Any host application that trusts `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a documented, expected usage pattern of this gem's webhook API) can have its per-tenant data integrity and isolation compromised — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is realistic: obtaining a legitimate `raw_body` + `hmac` pair requires nothing more than installing the app on any dev/test shop (a routine, unprivileged action every app must support), and the attacker fully controls the headers of the HTTP request they send to the app's own webhook endpoint. No access to `api_secret_key`, access tokens, or privileged accounts is required.

### Recommendation
Bind the shop identity to the signed payload before trusting it: either include the `shop-domain` (and ideally `topic`/`webhook-id`) header inside the HMAC-signable string constructed by `to_signable_string`, or independently verify (e.g., by cross-checking against a known/allow-listed installed-shop record before dispatching) that the header-derived `shop` matches the shop the webhook was actually issued for, rather than trusting an unauthenticated header field that the HMAC does not cover.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (permitted, unprivileged action). Shopify sends a real webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw_body>`, and body `raw_body`.
2. Capture that `raw_body` and its `hmac` header value.
3. Replay an HTTP POST to the same webhook endpoint using the identical `raw_body` and `hmac` header, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present) [6](#0-5) ; `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only reflects the unchanged body [1](#0-0) [5](#0-4) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com` even though the payload actually originated from `attacker-shop.myshopify.com` [4](#0-3) .
