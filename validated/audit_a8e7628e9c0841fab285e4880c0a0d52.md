### Title
Missing future-timestamp validation in `HandleLegacyUserMessage` allows indefinite replay of signed Web API trigger messages - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Gateway's legacy Web API trigger handler only checks that a client-supplied message `Timestamp` is not *too old*; it never checks that the timestamp is not *in the future*. A user (workflow trigger caller) fully controls the `TriggerRequestPayload.Timestamp` field that is signed and sent to the gateway. By setting this timestamp arbitrarily far in the future, the staleness check can never fail, allowing the same signed trigger message to be replayed and forwarded to the DON indefinitely.

### Finding Description
`handler.HandleLegacyUserMessage` decodes the incoming `TriggerRequestPayload` and performs a single staleness check: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // stale message
}
```

This only rejects messages whose `payload.Timestamp` is older than `MaxAllowedMessageAgeSec`. There is no corresponding check that `payload.Timestamp <= time.Now().Unix()`, i.e. that the timestamp is not from the future. This is the exact bug class from the external report: a signed message's freshness window is enforced only from one side (`now > timestamp + validity`), but the other bound (`timestamp <= now`) is missing.

Because `Timestamp` is part of the client-supplied, signed payload but is not otherwise bound-checked, a message with a timestamp set far in the future will never be classified as "stale" — the subtraction `now - MaxAllowedMessageAgeSec` will remain smaller than the (future) `payload.Timestamp` for as long as the attacker chooses. The rest of the handler contains no other replay-protection: it only applies a rate limiter and sends the raw request to DON nodes via `don.SendToNode` for every member; there is no nonce or "already processed" tracking for this legacy trigger path (unlike the `RequestReplayGuard` used by Vault, or the `jwtReplayCache` used by the v2 HTTP trigger handler, both of which explicitly track already-seen digests/JTIs with expiry).

### Impact Explanation
An unprivileged but authorized workflow trigger caller (or anyone who captures/replays a previously valid signed trigger message, since signatures don't cover intent of one-time use beyond the timestamp) can bypass the intended freshness/replay window entirely by crafting (or reusing) a message with a future timestamp. This allows the same `web_api_trigger` message to be resent to the DON repeatedly, well past its intended validity period, causing unauthorized/duplicate workflow execution triggers ("unauthorized job run") for as long as the forged future timestamp remains greater than `now - MaxAllowedMessageAgeSec`. This directly maps to the accepted impact category of unauthorized job run caused by a missing future-timestamp bound, mirroring the original Reservoir oracle finding where a floor price with a future timestamp could be reused indefinitely.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment relying on the legacy Web API trigger path (`MethodWebAPITrigger`/`HandleLegacyUserMessage`), since the only gate is client-controlled input with a one-sided bound check. No special privileges are needed beyond being an already-`allowedSender`, and the flaw is a straightforward input-validation gap rather than a cryptographic break.

### Recommendation
Add a symmetric check rejecting messages whose `payload.Timestamp` is ahead of the current time (beyond a small clock-skew tolerance), in addition to the existing staleness check, e.g.:

```go
now := uint(time.Now().Unix())
if payload.Timestamp > uint64(now)+clockSkewToleranceSec {
    // reject: timestamp is in the future
}
if now-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // reject: stale message
}
```
Consider also adding explicit per-sender replay/nonce tracking (similar to `RequestReplayGuard`/`jwtReplayCache`) for this handler so that message freshness isn't the sole replay defense.

### Proof of Concept
1. A client authorized as an `allowedSender` for a workflow's `web_api_trigger` constructs a `TriggerRequestPayload` with `Timestamp` set to, e.g., `time.Now().Unix() + 10_000_000` (far future) and signs the message as usual.
2. Sends it once to the gateway; `HandleLegacyUserMessage` passes the staleness check because `now - MaxAllowedMessageAgeSec` will never exceed the future timestamp, so the message is forwarded to all DON members and the trigger fires.
3. The client (or anyone with the captured message) resends the identical signed message repeatedly, at any time in the future up to the forged timestamp; each resend again passes the staleness check (since there is no future-timestamp bound) and no other replay protection exists in this code path, causing the workflow to be triggered again each time.
