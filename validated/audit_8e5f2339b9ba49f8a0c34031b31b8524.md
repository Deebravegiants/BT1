## Finding

The webhook HMAC verification in this gem signs and validates only the raw request body, while the `shop` and `topic` values used downstream to route and attribute the webhook are taken from unauthenticated HTTP headers that are never included in the signed bytes.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` and `topic` are pulled from HTTP headers, not from the signed body: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the raw body only, then immediately trusts `request.topic` to select the handler and `request.shop` to build `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata.shop` and `.topic` become the tenant/topic identity the host application's `WebhookHandler#handle` implementation relies on: [4](#0-3) 

`HmacValidator.validate` simply compares the computed HMAC of `to_signable_string` (the raw body only) against the `hmac-sha256` header — it has no knowledge of `shop` or `topic`: [5](#0-4) 

### Title
Webhook `shop` and `topic` are trusted from unauthenticated headers not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, then trusts the `shopify-shop-domain` and `shopify-topic` HTTP headers — which are excluded from the signed payload — to determine which merchant the event belongs to and which handler processes it.

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, bytes-that-determine-tenant-and-topic)`. In this gem, the equality actually enforced is `hmac == HMAC(secret, raw_body)` while `shop` (tenant identity) and `topic` (handler selection) are read from separate headers outside that signed scope (`request.rb:16-23` vs `request.rb:36-38`). Once `HmacValidator.validate(request)` passes (`registry.rb:190`), `request.shop` and `request.topic` are used as authoritative values to build `WebhookMetadata` and dispatch to a handler (`registry.rb:192-199`), even though nothing cryptographically ties them to the signed body.

Because the HMAC does not bind `shop`/`topic` to the body, any request that reproduces a previously valid `(raw_body, hmac)` pair — for example a webhook legitimately delivered to the app for the attacker's own store — remains HMAC-valid regardless of what `shopify-shop-domain` or `shopify-topic` header values accompany it. An unprivileged user who controls their own shop's webhook traffic (or has otherwise observed one valid body/hmac pair for any topic) can resend that same body with the header changed to a different shop domain and/or topic, and the gem will still report the HMAC as valid and hand the host application attacker-chosen tenant/topic metadata alongside genuine (or reused) body content.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: it lets an attacker inject events attributed to a different merchant (`shop`) or a different `topic` than the one the signature actually covers, while still passing `HmacValidator.validate`. Since apps rely on `WebhookMetadata.shop`/`.topic` as the trusted routing/attribution values coming out of this gem, this results in cross-tenant data injection/attribution — matching the Critical "cross-tenant access" impact category, because the gem is the layer responsible for authenticating which shop and topic a webhook event belongs to and it fails to bind that identity to the cryptographic proof.

### Likelihood Explanation
Reaching this requires only the ability to send an HTTP request to the app's webhook endpoint with a captured or self-generated `(raw_body, hmac)` pair and modified `shopify-shop-domain`/`shopify-topic` headers — no access token, `client_secret`, or privileged account is needed, satisfying the unprivileged-internet-user constraint. A merchant installing the app can trivially obtain valid `(body, hmac)` pairs from their own store's legitimate webhook deliveries and replay them with altered headers against the shared endpoint.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`, `api_version`) inside the HMAC-signed scope, or otherwise cryptographically bind them to the verified payload before they are used for routing/attribution in `Registry.process`. At minimum, `Request#to_signable_string` should incorporate these header-derived values so `HmacValidator.validate` fails when they are altered independently of the body.

### Proof of Concept
1. App receives a legitimate webhook for shop `attacker-shop.myshopify.com`, topic `orders/create`, with raw body `B` and header `hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker resends a POST to the app's webhook endpoint with the same body `B` and same header `hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` and/or `shopify-topic: shop/redact`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and compares to `H` — validation succeeds because the body is unchanged (`registry.rb:190`, `request.rb:36-38`).
4. `Registry.process` looks up the handler for `request.topic` (now attacker-controlled) and constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with the attacker-controlled `shop` and `topic`, then invokes `handler.handle(data: ...)` (`registry.rb:192-199`), causing the host application to process data as if it legitimately originated from `victim-shop.myshopify.com` and/or under a different topic.
