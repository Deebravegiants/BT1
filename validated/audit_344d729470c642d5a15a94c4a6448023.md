Found the analog. This is the identity-binding break in `ShopifyAPI::Webhooks::Request` (`lib/shopify_api/webhooks/request.rb`): the `shop` (`shop-domain` header) and `topic` used to dispatch the webhook to a handler are **not covered by the HMAC**, while only `@raw_body` is signed.

### Title
Webhook `shop` and `topic` fields are trusted without HMAC coverage, enabling cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` and `topic` are read straight from unauthenticated HTTP headers (`shopify-shop-domain`, `shopify-topic`) with no cryptographic binding to those values [2](#0-1) . `Registry.process` verifies the HMAC over the body only, then dispatches the handler using the unverified `request.topic` and passes the unverified `request.shop` straight into the handler's `WebhookMetadata` as the tenant identifier [3](#0-2) .

### Finding Description
The binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ body)`, i.e., the shop and topic that the handler acts on must be the same bytes that were authenticated. Instead, the actual binding enforced is `hmac == HMAC(secret, body)` only [4](#0-3) ; `shop` and `topic` are parsed from attacker-reachable request headers that are never fed into the signable string [5](#0-4) .

Because the request body content for a given webhook topic (e.g., `orders/create`, `app/uninstalled`) is often predictable, static, or replayable (a merchant/attacker can trigger a real webhook for their own shop to obtain a validly-HMAC'd body, since HMAC only covers the raw JSON body and the merchant's own shop legitimately produces that same body shape), an attacker who controls the raw HTTP request reaching the app's webhook endpoint (e.g., because the host web framework proxies raw headers as-is, or the attacker directly posts to the exposed webhook route with a body captured from their own legitimate webhook delivery) can supply an arbitrary `shopify-shop-domain` header value while keeping the same HMAC-valid body. `HmacValidator.validate` will pass because it only checks the body bytes [6](#0-5) , yet `Registry.process` will hand the forged `shop` value to the handler as the authenticated tenant [3](#0-2) .

This mirrors the reported bug class exactly: "a field acted on but not covered by the HMAC" — here `shop`/`topic` are acted upon (used to select the handler and identify the tenant) but are excluded from the signed payload, unlike `code`/`host`/`shop`/`state`/`timestamp` in `AuthQuery`, which correctly are all included in its `to_signable_string` [7](#0-6) .

### Impact Explanation
If a host app's webhook handler uses `WebhookMetadata#shop` to look up per-tenant data, access tokens, or trigger tenant-scoped side effects (the documented intended use, per `docs/usage/webhooks.md`), an attacker able to reuse or forge the HTTP-level `shop-domain`/`topic` headers while preserving a validly-HMAC'd body can make the app process webhook data as if it belonged to a different shop — a cross-tenant data confusion. This matches the Critical bucket ("cross-tenant access") since the shop identity fed to per-tenant business logic is not authenticated.

### Likelihood Explanation
Exploitability depends on whether the deployment environment allows a client to control `shop-domain`/`topic` headers independently of the signed body (e.g., if the app's front-end proxy/ingress does not itself independently validate Shopify's IP range or re-derive shop from a separate trusted channel). Given the header-parsing code explicitly supports arbitrary caller-supplied header dictionaries and normalizes both legacy and new header names without any secondary authentication of shop/topic, the library itself provides no defense — the responsibility for this binding is silently dropped by the library rather than delegated intentionally. This is a root-cause defect in the gem, not a host-app misuse of a documented safe API.

### Recommendation
Include `shop` and `topic` (and ideally `webhook_id`) in the HMAC-signed payload, or independently verify that the `shop-domain` header value is consistent with a value derived from the signed body (if such a claim exists in Shopify's webhook body/headers) before dispatching to handlers. At minimum, document/require that `to_signable_string` cover all fields consumed by `WebhookMetadata`, following the same pattern used correctly in `AuthQuery#to_signable_string`.

### Proof of Concept
1. Attacker captures a legitimately delivered webhook for `attacker-shop.myshopify.com` with topic `orders/create`, including its raw body and valid `x-shopify-hmac-sha256` value (HMAC covers body only).
2. Attacker POSTs to the app's webhook endpoint with the same raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers without validation [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it hashes only `@raw_body` [9](#0-8) .
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process the request under the wrong tenant identity [10](#0-9) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
