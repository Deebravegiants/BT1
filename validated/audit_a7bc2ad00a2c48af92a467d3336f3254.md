### Title
Stale delegate grant silently reactivates when the position NFT returns to a previous owner, letting a manager drain the account - (File: contracts/controller/src/account.rs)

### Summary

CVE-2018-14348 is about a resource created with wider permissions than the configured restriction intended (mode 0666 ignoring umask). The analog in XOXNO Lending is a permission grant that outlives the context it was scoped to: account delegates are stored keyed by `(account_id, owner_address)` with no ownership epoch or generation. When the position NFT moves to a new owner, the old owner's delegate list becomes inactive — but it is never purged. If the NFT is ever transferred back to the original owner, the previously granted delegate regains full spending authority on the account without any new authorization, and `borrow`/`withdraw` let that delegate pick an arbitrary payout recipient.

### Finding Description

`is_owner_or_delegate` checks whether `caller` is in the delegate set stored under the *current* owner's address:

- `storage::get_delegates(env, account_id, owner).contains(caller)` in `is_owner_or_delegate` [1](#0-0) 
- The grant is written by `set_account_delegate` via `storage::add_delegate(env, account_id, caller, delegate)`, keyed by the granting owner [2](#0-1) 

The documented invariant confirms the gap: "A grant records the owner's address, without a transfer epoch. It is inactive under another owner but can reactivate if the NFT returns, unless an intervening owner overwrites or purges the grant" [3](#0-2) . Nothing on the NFT `transfer`/`transfer_from` path clears or versions delegate storage; `position-nft::transfer` only notes that "delegate grants from the previous owner go inactive," not deleted [4](#0-3) . There is also no automatic purge: `remove_delegate` must be called by the then-current owner, who may never have granted (or even know about) the stale entry [5](#0-4) .

Once reactivated, the delegate passes `require_owner_or_delegate` for `borrow` and `withdraw`, and both accept `to: Option<Address>` so proceeds go to an address of the delegate's choosing [6](#0-5) . INV-AUTH-02 itself concedes "delegates can choose external payout recipients, giving them broad economic control" [3](#0-2) .

### Impact Explanation

Theft of user funds. A reactivated delegate can `withdraw(account_id, withdrawals, to: Some(attacker))` all withdrawable collateral, or `borrow` up to the account's solvency limit and send proceeds to itself, leaving the owner with bad debt. The economic damage equals the account's free collateral value — bounded only by solvency checks, not by the delegate.

### Likelihood Explanation

Requires a chain of conditions: (1) the owner granted a delegate while holding the NFT, (2) the delegate remains an active governance-approved position manager (`set_account_delegate` rejects grants to inactive managers, and `is_owner_or_delegate` re-checks `config.is_active` at call time), (3) the NFT left the owner and later returned — plausible via NFT sale and repurchase, marketplace escrow round-trips, or accidental transfer/recovery. A malicious or compromised position manager can watch for accounts returning to a former granter and act in the same ledger the transfer lands. No privileged action is needed to exploit, but the owner must at some point reacquire the account, so this is opportunistic rather than freely triggerable — Medium severity.

One caveat: `account.owner` is read through `storage::account_owner`/the loaded `Account`, and the delegate set is keyed by the *current* owner address, so the reactivation only fires when ownership returns to the exact original granter address — confirmed by the invariant wording, though I could not fully trace every NFT-transfer hook for a hidden delegate purge (none appears in the sources searched).

### Recommendation

Scope delegate grants to an ownership epoch rather than the raw owner address:

- Store a `delegates_epoch` (or NFT transfer counter) per account, incremented on every ownership change observed by the controller (or hook NFT transfer into the controller), and key `Delegates` by `(account_id, epoch)`.
- Alternatively, have the position-NFT `transfer`/`transfer_from` invoke a controller hook that wipes `Delegates(account_id, *)` on every ownership change, so no stale grant can revive.
- As a mitigation without storage changes, document in `transfer` flows that a returning owner must call `remove_delegate` for every historical delegate before depositing collateral.

### Proof of Concept

1. Owner A creates `account_id` via `supply`, deposits collateral, and calls `add_delegate(account_id, M)` where `M` is an active position manager → `Delegates(account_id, A)` contains `M`.
2. A transfers the position NFT to B (sale). `M` is now inactive on the account, but the grant entry persists.
3. B deposits more collateral and later transfers the NFT back to A (buyback).
4. `M` calls `controller.withdraw(M, account_id, withdrawals, to: Some(M))`: `caller == owner` fails, but `get_position_manager(M).is_active` is true and `get_delegates(account_id, A).contains(M)` is still true → `require_owner_or_delegate` passes and collateral is transferred to `M`.
5. `M` repeats with `borrow(..., to: Some(M))` up to the solvency limit.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}
```

fn set_account_delegate(
    env: &Env,
    caller: &Address,
    account_id: u64,
    delegate: &Address,
    add: bool,
) {
    caller.require_auth();
    require_account_owner(env, account_id, caller);
    if add {
        // Reject dormant grants that could gain authority on later manager activation.
        assert_with_error!(
            env,
            storage::get_position_manager(env, delegate).is_some_and(|c| c.is_active),
            GenericError::NotAuthorized
        );
    }

    let changed = if add {
        storage::add_delegate(env, account_id, caller, delegate)
    } else {
        storage::remove_delegate(env, account_id, caller, delegate)
    };
```
