### Title
Relayer fee for emulated ETH/ERC-20 transfers is paid unconditionally, even when the underlying action fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEAR Wallet Contract's `inner_rlp_execute` dispatches the relayer-compensation fee as a **separate, independent receipt** before the user's actual intended action (base-token transfer or ERC-20 transfer) is executed. Because this fee-payment receipt is not causally chained to the outcome of the main action's promise, the relayer is paid even if the main action subsequently fails, and the failure-handling path (`rlp_execute_callback`) only refunds the `caller_deposit`, never the fee.

### Finding Description
In `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:374-385`), for `EOABaseTokenTransfer` and `ERC20Transfer` kinds with a non-zero `fee`, the code does: [1](#0-0) 
This spawns `env::promise_batch_create(&context.predecessor_account_id)` + `env::promise_batch_action_transfer` as a **brand-new, independent receipt**, dispatched unconditionally in the same function call that later also builds the main action's promise chain (`action_to_promise(...).then(ext.rlp_execute_callback(...))` or, for ERC-20, the `storage_balance_of` → `storage_deposit`/`ft_transfer` → `rlp_execute_callback` chain, see `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458`).

Because the fee-transfer receipt and the main-action promise chain are two separate, non-chained receipts emitted from the same function call, NEAR's protocol will execute and settle both independently (per `runtime/runtime/src/lib.rs` receipt processing described in `protocol-model/spec/runtime-execution.md:61-75`). There is no dependency (`.then()`/data receipt) linking the fee payment to the success of the main transfer. Consequently:
- If the main action later fails (e.g., insufficient token balance in the `ft_transfer` call, a blacklisted/unregistered receiver causing `storage_deposit`/`ft_transfer` to fail, or any other cross-contract failure), `rlp_execute_callback` (`lib.rs:276-317`) only refunds the `caller_deposit` NEAR attached by the original caller — it has no way to claw back the fee, which was already sent to the relayer via the independent receipt created earlier in `inner_rlp_execute`.
- This directly mirrors the reported bug class: an accounting/side-effect (fee payment, analogous to `accountRewardDebt` update) is committed unconditionally, decoupled from confirmation that the corresponding operation (analogous to reward claim) actually succeeded.

The nonce increment for user errors is a deliberate, documented Ethereum-compatibility choice (nonce always advances to prevent replay, even on failure) and is not itself the issue; the issue is specifically the **fee transfer to the relayer**, which is meant to be compensation *for successfully relaying a transaction*, not an unconditional protocol fee.

### Impact Explanation
A user whose eth-implicit wallet contract account submits (via a relayer) an ETH-emulated base-token transfer or ERC-20 transfer with a non-zero fee will pay the relayer fee out of their own NEAR balance regardless of whether the requested transfer actually completes. If the downstream `ft_transfer`/`storage_deposit` call fails for any reason (insufficient token balance, receiver not registered and insufficient NEAR for storage deposit, token contract reverting, etc.), the user's funds (the fee) are irrecoverably transferred to the relayer while receiving nothing in return — an unauthorized loss of user funds. This is a direct token-loss/unauthorized-balance-change class issue reachable from an ordinary, unprivileged transaction/RPC call routed through the Wallet Contract, matching the report's core defect: "state updated (fee sent) regardless of whether the intended operation succeeds."

### Likelihood Explanation
This is reachable by any relayer/user pair using the standard wallet-contract flow for ETH-emulated base-token or ERC-20 transfers with `fee > 0` — no special privileges, malicious node, or validator control needed. The failure conditions that trigger loss (token contract balance/storage/blacklist failures, or any downstream promise failure) are common, realistic scenarios in ERC-20/NEP-141 interactions, making this readily triggerable in normal usage rather than requiring an adversarial setup.

### Recommendation
Chain the fee-transfer to the relayer as part of the same promise sequence that executes the main action (e.g., attach it via `.then()` after the main action succeeds, or fold it into the same batch/receipt as the final step of the `rlp_execute_callback` success branch), so it is only paid out when the underlying action is confirmed successful. Alternatively, include the fee amount in the amount refunded/tracked by `caller_deposit`/an analogous "pending fee" field so that `rlp_execute_callback`'s failure branch can also refund the fee back to the current account (or avoid sending it at all) when the main promise fails.

### Proof of Concept
1. An eth-implicit wallet-contract account signs an Ethereum-style ERC-20 `transfer` (or a base-token transfer) transaction with `max_fee_per_gas * gas_limit > 0`, producing a non-zero `tx_fee` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:59-64`).
2. A relayer submits this via `rlp_execute` (`lib.rs:89`). `inner_rlp_execute` computes the `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. })` and immediately fires the fee transfer to the relayer as an independent receipt (`lib.rs:374-385`), before the `ft_transfer` promise chain is even created.
3. The subsequent NEP-141 token contract call (`ft_transfer`, reached through `nep_141_storage_balance_callback` → `action_to_promise` → `rlp_execute_callback`, `lib.rs:194-273`, `276-317`) fails — e.g., because the token contract's `ft_transfer` reverts due to insufficient balance or a blacklisted receiver.
4. `rlp_execute_callback` sees `PromiseResult::Failed` and only refunds `caller_deposit` (the attached NEAR of the external call), never the fee (`lib.rs:296-312`).
5. Net effect: the relayer already received the fee (step 2) unconditionally, and the user's intended token transfer never happened — the user has lost the fee for a service that was never rendered, with no code path providing a refund.

Note: I was unable to independently execute this scenario against a live runtime (no test harness invocation was run in this session); this assessment is based on static analysis of the control/data flow across `lib.rs` and `internal.rs`. It would be valuable for a maintainer to confirm the intended design tradeoff here (comment at `lib.rs:367-373` suggests the fee-for-service model is intentional to bootstrap relayer trust) versus whether pairing the fee payment with actual settlement of the main action was overlooked.
