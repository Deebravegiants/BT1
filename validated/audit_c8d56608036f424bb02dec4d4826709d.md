## Finding: Webhook Identity Fields (`shop`, `topic`, `webhook_id`) Are Not Covered by the HMAC That `Registry.process` Trusts

### Title
Webhook HMAC only binds the raw body, letting shop/topic/webhook-id headers be forged independently of the signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` returns true, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the dispatched `WebhookMetadata`. However `Request#to_signable_string` — the only thing the HMAC actually signs — returns just `@raw_body`; the shop-domain, topic, and webhook-id headers are never part of the signed payload.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against `verifiable_query.hmac` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`, while `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all pulled from separate, unsigned HTTP headers [2](#0-1) .

`Registry.process` performs exactly one check — HMAC validity — and then dispatches using `request.shop`, `request.topic`, and `request.webhook_id` as if they were verified together with the body: [3](#0-2) 

The equality the gem implicitly claims is:
`hmac_valid(raw_body) == identity_verified(shop, topic, webhook_id)`

but the actual guarantee is only `hmac_valid(raw_body)`. Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any unprivileged user who installs the app on their own store can capture one genuine `(raw_body, hmac)` pair from a real webhook delivery to their own shop, then POST that exact body/hmac pair to the app's public webhook endpoint while substituting a different value in `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`). `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` hands the handler a `WebhookMetadata` claiming the event came from the victim shop/topic.

### Impact Explanation
This breaks the tenant binding `shop_that_produced_the_signed_body == shop_attributed_by_the_library`, letting an unprivileged app-installer forge webhook events "from" another tenant. Any host application that uses `WebhookMetadata#shop` to key session lookups, tenant-scoped writes, or trust decisions (a documented, intended use of this field) is exposed to cross-tenant data injection using only the HMAC secret shared by the app across all installs — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Requires only an unprivileged app installation on the attacker's own store (standard onboarding flow, no privileged credentials, no `api_secret_key` leakage) plus the ability to POST directly to the app's public webhook URL, which is reachable by design from the internet.

### Recommendation
Bind the identity headers into the signed payload verified by `HmacValidator`, e.g. include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or perform a secondary check that the shop belongs to an active, previously stored installation before dispatching), rather than trusting header values that sit outside the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook with a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's `api_secret_key`.
2. Attacker replays that exact body/HMAC to the app's webhook endpoint, replacing only `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
3. `Utils::HmacValidator.validate` returns `true` because it only checks `@raw_body` [4](#0-3) .
4. `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the host app to act as if the event genuinely originated from the victim tenant.
