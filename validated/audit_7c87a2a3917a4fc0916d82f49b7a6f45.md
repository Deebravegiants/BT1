### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` are trusted for tenant dispatch despite not being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers and handed to the app's webhook handler as trusted identity/tenant data. `Registry.process` validates only the raw-body HMAC before dispatching, so the `shop` value used to route/attribute the webhook to a merchant tenant is never bound to the signature that "proves" the request came from Shopify.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers, with no cryptographic binding to the body's HMAC: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)`, which in turn only re-computes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac` header: [3](#0-2) [4](#0-3) 

After this check passes, `process` builds `WebhookMetadata` directly from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`, and dispatches it to the app's handler: [3](#0-2) 

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" and explicitly documents `data.shop` as "The shop domain of the webhook" that host apps are expected to trust for tenant dispatch (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`): [5](#0-4) [6](#0-5) 

This breaks the identity binding: `hmac-authenticated content == raw_body` but `shop trusted by the handler == x-shopify-shop-domain header`, which is not part of `raw_body`. Any attacker who can obtain one legitimately-signed `(raw_body, hmac)` pair for a webhook topic they control — for example by installing the app on their own store and letting Shopify deliver a real webhook to them — can replay that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g. a victim merchant's domain). `HmacValidator.validate` still succeeds because it only checks the body signature, and the forged shop value is passed straight through to the app's handler as trusted tenant data.

### Impact Explanation
This is a cross-tenant identity-binding break: an unprivileged user who has installed the app on their own shop (no special privilege, no token/secret needed) can make the app process attacker-supplied "shop" attribution for otherwise-legitimate webhook payloads. Any host application that follows the gem's documented pattern of trusting `data.shop` for tenant routing/attribution (exactly as demonstrated in the gem's own README example) will misattribute webhook events to an arbitrary shop domain, enabling cross-tenant data confusion/injection.

### Likelihood Explanation
Likelihood is high for any app that follows the documented usage pattern, since exploitation only requires: (1) installing the app on an attacker-owned development/trial store to receive a legitimately-signed webhook, and (2) resending the identical raw body + hmac header to the app's public webhook URL with a forged `x-shopify-shop-domain` header. No access token, `client_secret`, or privileged account is required.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the HMAC-signable content (or otherwise cryptographically verify them against a source of truth, e.g. by looking up the topic/shop from a value embedded in the signed body, or requiring TLS-pinned/allow-listed source IPs as a secondary control) before trusting them in `WebhookMetadata`, so that `to_signable_string` used by `HmacValidator` covers every field the handler treats as authenticated (particularly `shop`).

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimately-signed webhook to the app's endpoint: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's `client_secret`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and sends a new HTTP POST directly to the app's public webhook URL with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...forged shop...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
5. `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` is dispatched to the app handler, which per the documented pattern trusts `data.shop` for tenant routing, causing the attacker's payload to be processed as if it belongs to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
