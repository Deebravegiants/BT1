### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook using only the raw HTTP body against the `X-Shopify-Hmac-Sha256` header, while the `shop` identity that the gem hands to the app's handler comes from a completely separate, unauthenticated header (`X-Shopify-Shop-Domain`). Because Shopify signs webhooks with the app's single shared `client_secret` (identical for every shop that has installed the app), any merchant/attacker who can install the app on their own store can obtain a validly-signed `(raw_body, hmac)` pair and then replay it with an arbitrary `shop-domain` header, causing the gem to report an attacker-chosen body as belonging to a victim shop.

### Finding Description
`Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shop-domain` header with no cryptographic tie to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` only ever verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`, so for a `Webhooks::Request` it verifies the body only: [3](#0-2) 

`Registry.process` trusts `request.shop` unconditionally once the body HMAC passes, and forwards it to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is: **shop bound by HMAC == shop delivered to handler**. Because the HMAC secret (`client_secret`) is shared across every shop that installs the app, and the `shop-domain` header is excluded from the signed content, this equality does not hold — `hmac` only proves "this body was sent by *some* shop that installed this app," not "this body belongs to `shop-domain`."

### Impact Explanation
An attacker who installs the target app on their own (attacker-controlled) Shopify store can:
1. Trigger any webhook topic the app subscribes to (e.g. `orders/create`, `customers/data_request`) with attacker-chosen body content.
2. Capture the resulting `raw_body` and its valid `X-Shopify-Hmac-Sha256` value (computed with the app's shared `client_secret`).
3. Replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) rewritten to a victim shop's domain.
4. `Registry.process` validates the HMAC successfully (it only checks the body) and calls the app's handler with `WebhookMetadata.shop == victim-shop` and attacker-controlled `body`.

Any host application that uses `data.shop` from `ShopifyAPI::Webhooks::WebhookHandler` as the tenant key for persisting or acting on `data.body` (exactly the documented usage pattern in `docs/usage/webhooks.md`) will attribute attacker-controlled data to a shop the attacker does not own — a cross-tenant data-integrity/confidentiality breach rooted entirely in this gem's webhook verification primitive, not in host-application misuse of an undocumented contract.

### Likelihood Explanation
Likelihood is high for any developer building on this gem's public app: installing an app on one's own store to obtain valid signed webhook payloads is trivial and requires no special privilege beyond being a normal Shopify merchant, and forging HTTP headers on a replayed request requires no credentials at all. The only precondition is that the app relies on `data.shop` from `WebhookMetadata`, which is exactly the documented/intended way to consume webhook data from this gem.

### Recommendation
Bind the shop identity into the authenticated bytes, e.g. by requiring the caller to pass the expected shop (or by including the `shop-domain`, `topic`, and `webhook-id` headers in `to_signable_string` alongside the raw body), or by validating `request.shop` against a shop known independently and out-of-band (e.g. matching an active, previously-established session/webhook registration for that exact shop) before invoking the handler in `Registry.process`.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com"
# and captures a legitimately-signed webhook body from Shopify:
raw_body = '{"id": 1, "malicious": "payload"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), Context.api_secret_key, raw_body)
)

# Attacker replays the SAME body/hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,          # still valid! only covers raw_body
  "x-shopify-shop-domain" => "victim.myshopify.com", # spoofed, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (body HMAC matches)
# => handler.handle(data: WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_json, ...))
```
