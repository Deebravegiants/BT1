### Title
Missing multi-proof length validation before generalized-index lookup causes panic in sync-committee finality verification - ([File: modules/consensus/sync-committee/verifier/src/lib.rs])

### Summary
The CVE-2021-47265 root cause is a missing validation of a user-supplied index/value before it is used to access an internal structure, causing an out-of-bounds access/crash reachable from an unprivileged code path (`ib_uverbs_ex_create_flow` → `_create_flow_rule`). The Hyperbridge sync-committee consensus verifier contains the same bug class: a relayer-submitted consensus update drives `calculate_multi_merkle_root` with a `multi_proof` whose length is not validated against the number of `GeneralizedIndex` entries being verified, and the code comment itself documents that this "panics on a short `multi_proof`."

### Finding Description
In `verify_execution_payload` (or equivalent) in [1](#0-0) , the verifier builds an array of `GeneralizedIndex` values (`EXECUTION_PAYLOAD_STATE_ROOT_INDEX`, `EXECUTION_PAYLOAD_BLOCK_NUMBER_INDEX`, `EXECUTION_PAYLOAD_TIMESTAMP_INDEX`) and passes them along with a relayer-supplied `multi_proof` (part of the `ConsensusMessage`/update submitted permissionlessly via `handleConsensus`/`handle_unsigned`) into `calculate_multi_merkle_root`. The in-code comment flags that this function "panics on a short `multi_proof` because its final [...]" indexing logic assumes the proof array has enough elements to satisfy every generalized index being verified. No length/bounds check is performed on `multi_proof` before this call — this mirrors the RDMA bug where the `port` value (an index into internal flow-steering structures) was not validated before being dereferenced in `_create_flow_rule`, leading to an OOB read/panic.

This is directly analogous to the class of bugs already patched elsewhere in this same codebase for the identical root cause:
- `modules/consensus/beefy/verifier/src/lib.rs` (`verify_mmr_leaf`) — explicitly guards against an empty `leaf_indices` vector with a comment noting it "previously panicked the runtime via the unchecked `[0]` index."
- `modules/consensus/pharos/primitives/src/spv.rs` (`nibble_at_depth`) — explicitly guards against proofs deeper than `MAX_PROOF_DEPTH` that would otherwise index past a 32-byte hash and panic.
- `modules/trees/ethereum/src/node_codec.rs` — explicitly guards against an empty HP-prefix payload that previously caused `data[0]` to panic.

The sync-committee verifier lacks the equivalent guard for its own indexed-proof consumption.

### Impact Explanation
A malicious or careless relayer can submit a sync-committee consensus update (a fully unprivileged action, reachable via `handleConsensus`/`handle_unsigned` on any chain configured with the sync-committee client for Ethereum) with a truncated `multi_proof`. This drives `calculate_multi_merkle_root` past the bounds of its proof array, causing the runtime/EVM light-client verification to panic. In a Substrate pallet context (`pallet_ismp` unsigned extrinsic execution) an unhandled panic in consensus verification can halt block production or crash the node process handling that extrinsic, and in all cases it permanently blocks legitimate consensus updates and message delivery for any chains relying on that sync-committee client instance — i.e., "a route unable to deliver messages," which is an explicitly acceptable impact category per the validation rules.

### Likelihood Explanation
Likelihood is high: the vulnerable proof data is fully attacker-controlled and submitted by any relayer without special privileges (`ValidateUnsigned`/permissionless handler paths), no signatures or economic stake gate it before the panic point in this specific check, and the codebase's own comment already flags the exact failure mode as known but (based on available code) not yet remediated with an explicit length check, unlike the sibling fixes for BEEFY/Pharos/Ethereum trie proofs.

### Recommendation
Add an explicit length/bounds check before calling `calculate_multi_merkle_root` (or inside it), verifying that `multi_proof.len()` is sufficient for the supplied set of `GeneralizedIndex` values, and return a proper `Error::InvalidMerkleBranch`/similar instead of allowing the function to index out of bounds. This should mirror the fix pattern already applied to `verify_mmr_leaf` and `nibble_at_depth` in this repository.

### Proof of Concept
1. Configure a chain with the sync-committee consensus client for an Ethereum-anchored state machine.
2. As an unprivileged relayer, submit a `ConsensusMessage`/update whose `execution_payload_proof.multi_proof` array is shorter than what `calculate_multi_merkle_root` requires to resolve all three `GeneralizedIndex` entries (`EXECUTION_PAYLOAD_STATE_ROOT_INDEX`, `EXECUTION_PAYLOAD_BLOCK_NUMBER_INDEX`, `EXECUTION_PAYLOAD_TIMESTAMP_INDEX`).
3. Submit via the permissionless consensus-update path (`handleConsensus` on EVM / `handle_unsigned` on Substrate).
4. Observe the verifier panics instead of returning `Err`, per the documented behavior of `calculate_multi_merkle_root` noted in the surrounding code comment at line 184 of `modules/consensus/sync-committee/verifier/src/lib.rs`.
