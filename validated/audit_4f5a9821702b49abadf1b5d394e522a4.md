### Title
Webhook shop/topic identity is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, and `webhook_id` are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only, then trusts the header-derived `shop` and `topic` to attribute and route the webhook. Any actor who can obtain one genuinely-signed webhook (e.g., from a shop they themselves installed the app on) can replay it with the `shop-domain`/`topic` headers rewritten to a victim shop/topic, and the HMAC check still passes.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be just the raw body bytes: [2](#0-1) 

Meanwhile, `shop`, `topic`, and `webhook_id` are pulled straight from attacker-visible/attacker-modifiable HTTP headers, with no cryptographic binding to the HMAC: [3](#0-2) 

`Registry.process` validates only the body-bound HMAC, then unconditionally trusts `request.shop` and `request.topic` to build the `WebhookMetadata` handed to the app's business logic: [4](#0-3) 

The identity binding the library implicitly claims is: `shop header value == shop that produced the HMAC-covered body`. In reality the equality that holds is only `body bytes == HMAC-covered bytes`; the `shop`/`topic`/`webhook_id` headers are outside that binding. Because the app's `api_secret_key` (used to compute the webhook HMAC) is the same for every shop that installs the app, any merchant/attacker who installs the app on their own store can trigger a webhook event with attacker-chosen body content and a validly-computed HMAC for that body. That attacker can then replay the HTTP request to the app's webhook endpoint after swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to a victim shop, and `Utils::HmacValidator.validate` will still return `true` because it never inspects those headers.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an unprivileged user who can only install the app on their own store (no special privileges, no leaked credentials, no access token) can make the host application believe attacker-controlled data originated from an arbitrary victim shop, and dictate which handler/topic processes it (e.g. forging `shop/redact`, `customers/data_request`, or any registered topic handler as if it came from a different tenant). This is cross-tenant data/event injection into the host application's webhook processing pipeline, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-owned/trial shop (a normal, unprivileged action any internet user can perform), (2) triggering any webhook topic with attacker-influenced body content, (3) intercepting/replaying the resulting HTTP request with the `shop-domain`/`topic` headers rewritten. No access to `api_secret_key`, access tokens, or the target shop's credentials is required, and the gem provides no header-binding mechanism to prevent it.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api-version`) in the HMAC-signable payload, or otherwise cryptographically bind them (e.g., derive `shop` only from a value that is itself covered by the signature, or require the host app to cross-check the shop header against a known, previously-authorized session for that shop) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development/trial store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook whose body they control (e.g. `products/update` with a crafted title/body), causing Shopify to POST a request with a valid `X-Shopify-Hmac-Sha256` computed over that body using the app's shared `api_secret_key`.
3. Attacker intercepts this POST before/instead of forwarding it to the real endpoint, and resends it to the app's webhook route with the header `X-Shopify-Shop-Domain` changed to `victim-shop.myshopify.com` (and/or `X-Shopify-Topic` changed to a different registered topic).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unmodified) raw body against the HMAC — it succeeds.
5. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, confirming the cross-tenant spoof: [5](#0-4)
