### Title
Sustained high utilization drives debt value past i128 and permanently freezes the market (no repay, withdraw, or liquidation) — (File: contracts/pool/src/interest.rs)

### Summary
The analog to the rBPF `relocate` integer overflow is XOXNO Lending's RAY-domain debt/supply valuation overflow in the accrual path. `interest::global_sync` runs `accrue_step` before every state-changing pool verb, and `scaled_to_original` / `calculate_supplier_rewards` compute `borrowed * borrow_index` products that eventually exceed `i128`, panicking with `MathOverflow`. Because accrual precedes every mutation, a market that crosses this threshold is permanently bricked: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate. The borrow-index cap at `MAX_BORROW_INDEX_RAY` does not prevent it — the test harness proves the value cliff is hit *before* the index cap.

### Finding Description
- `accrue_step` (`common/src/rates/simulate.rs`) calls `calculate_supplier_rewards`, which computes `borrowed.mul(env, new_borrow_index)` — a `mul_div_half_up` over `i128` that panics with `GenericError::MathOverflow` when the result does not fit [1](#0-0) .
- `update_borrow_index` clamps the *index* to `MAX_BORROW_INDEX_RAY` only after multiplying; the cap does nothing for the `borrowed * index` value product [2](#0-1) .
- The panic propagates through `interest::global_sync`, which runs first in every pool flow ("mutate → guards → commit"), so `supply`, `borrow`, `withdraw`, `repay`, `clean_bad_debt`, `claim_revenue`, and controller `liquidate` all revert [3](#0-2) .
- The overflow threshold is ≈ `i128::MAX` RAY asset value — about 170 billion whole tokens at 18 decimals — attainable by ordinary `supply`/`borrow` calls once caps are lifted (caps are per-market config, not a hard ceiling on `i128`) [4](#0-3) .
- Unlike the rBPF bug (wraparound producing a wrong address), Soroban reverts on overflow, so the outcome is permanent freeze rather than silent corruption — but the freeze also blocks liquidations, turning underwater positions into forced bad debt that `clean_bad_debt`/`recapitalize` cannot clear because they accrue first.

### Impact Explanation
**Permanent freezing of funds + protocol insolvency.** All supplier deposits and all collateral routed through the frozen market are locked forever — every exit path (`withdraw`, `repay`, `liquidate`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, `flash_position`, `clean_bad_debt`) performs accrual before touching state, and accrual is the exact panic site. The harness test asserts both `try_withdraw_raw` and `try_repay` return `MATH_OVERFLOW` after the cliff [5](#0-4) . Since liquidation is impossible, the market's debt can never be resolved — guaranteed insolvency for that book.

### Likelihood Explanation
An unprivileged actor needs only: (1) a market with a borrow cap high enough to admit ~`1.7e29`-RAY debt value (cap maxima share the same bound, per formulas.md), (2) high utilization held long enough — the test reaches the cliff in under 40 simulated years at 98% utilization on a steep curve, and faster at higher configured borrow rates up to the 200% APR cap, and (3) simply waiting: accrual is time-driven and `update_indexes` is a public entrypoint, so any user can trigger the panic once the threshold is crossed. There is no admin escape hatch — the index cap is set below the value-overflow point in shares×index space, so no governance action can unwind the market either [6](#0-5) .

### Recommendation
Saturate rather than panic in the accrual valuation path: clamp `borrowed * borrow_index` in `scaled_to_original`/`calculate_supplier_rewards` to `i128::MAX` (mirroring the existing `mul_div_floor_saturating` used for `div_floor_saturating` and `protocol_fee_shares` [7](#0-6) ), or gate `update_borrow_index`/accrual so that once `borrowed * index` approaches the representable limit the index is pinned and no further `mul` is attempted. Alternatively enforce a per-market debt-value ceiling in `require_liquidation_buffer`/`borrow` guards strictly below `i128::MAX / index_headroom` so the cliff is unreachable.

### Proof of Concept
The repository contains an executable PoC at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`:

```rust
let principal = BILLION * 10i128.pow(18);      // ~1e27 tokens, 18 decimals
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;               // 98% utilization
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance time year-by-year; eventually:
assert_contract_error(t.try_update_indexes_for(&["BIG18"]), errors::MATH_OVERFLOW);
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY);   // cap never engages
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The unprivileged caller's path is `controller::borrow` (mint debt near the cap) → time passes / repeated `update_indexes` → `interest::global_sync` → `accrue_step` → `calculate_supplier_rewards` → `borrowed.mul(new_borrow_index)` overflows `i128` → every subsequent verb reverts permanently.

fn test_borrow_index_at_the_ceiling_multiplies_without_overflow() {
    let env = Env::default();

    // `update_borrow_index` multiplies before it clamps, so the pre-clamp
    // product at the ceiling times the largest reachable chunk factor is the
    // real overflow site. It must stay inside i128 with room to spare.
    let factor = max_chunk_growth_factor(&env, MAX_BORROW_RATE_RAY);
    let at_ceiling = Ray::from(MAX_BORROW_INDEX_RAY);

    let product = at_ceiling.mul(&env, factor);
    assert!(product.raw() > MAX_BORROW_INDEX_RAY);
    assert!(
        product.raw() < i128::MAX / 20,
        "pre-clamp headroom above the ceiling fell below 20x: {}",
        product.raw()
    );

    assert_eq!(
        update_borrow_index(&env, at_ceiling, factor).raw(),
        MAX_BORROW_INDEX_RAY,
    );
