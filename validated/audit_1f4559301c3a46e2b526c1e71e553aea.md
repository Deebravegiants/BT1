### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop-spoofing replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity with `Utils::HmacValidator`, but the HMAC signature only covers the raw request body. The `shop-domain` header — the value that the gem hands to webhook handlers as the tenant identifier — is read directly from an unauthenticated header and is never included in the signed payload. An attacker who can obtain one valid `(body, hmac)` pair (trivially, by installing the app on their own store and triggering any webhook) can replay that exact body/hmac to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the request still passes `HmacValidator.validate`.

### Finding Description
`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac` [1](#0-0) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` trusts `Utils::HmacValidator.validate(request)` as the sole authenticity gate, then forwards the unauthenticated `request.shop` straight to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is:
`shop-domain header used to route/scope the webhook == shop that Shopify actually signed for this body`

Because the signature never covers the shop header, this equality is not enforced. Any two values `(raw_body, hmac)` that were valid for shop A remain valid when replayed with shop B's domain in the header — the gem will report `Utils::HmacValidator.validate(request)` as `true` and dispatch shop A's body content to the handler tagged as belonging to shop B.

This matches the report's underlying theme (fragile internal bookkeeping that assumes an unverified value is trustworthy) mapped onto this gem's own security-critical binding: "a field acted on but not covered by the HMAC."

### Impact Explanation
Per the documented usage pattern (`docs/usage/webhooks.md`), host applications use `WebhookMetadata#shop` to determine which merchant/tenant record the webhook body applies to (e.g., looking up the session/store row to update). Since `shop` is unauthenticated, an attacker with no privileged credentials can:
1. Install the target app on their own (attacker-controlled) store — an ordinary, unprivileged action.
2. Trigger a webhook of interest on their own store to obtain a valid `(raw_body, hmac)` pair.
3. Replay that exact body/hmac pair to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop.

The gem will accept this request as authentic and hand the attacker's body content to the handler under the victim's shop identity — a cross-tenant identity-confusion vector that can corrupt or leak data across tenants depending on what the handler does with `data.shop` and `data.body`. This satisfies the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
Likelihood is high for any app that: (a) is installable by arbitrary merchants (the normal Shopify app model), and (b) uses `data.shop` from `WebhookMetadata` to scope handler logic, which is exactly the intended, documented use of this API. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only the ability to install the app on an attacker-owned store, which is available to any unprivileged internet user in the standard Shopify app-install flow.

### Recommendation
Bind the shop identity to the HMAC-verified payload rather than trusting the header in isolation:
- Include `shop-domain` (and ideally `topic`, `webhook-id`) in the signed string used for HMAC verification, or
- Cross-check the header-derived `shop` against a shop value embedded in the verified body (if available), or
- At minimum, document prominently that `request.shop` is not authenticated and that host apps must independently verify the shop against a known/expected value (e.g., an active session or registration record) before trusting it, rather than only relying on `HmacValidator.validate`.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures a legitimate webhook delivery.
captured_body = '{"id":123,"note":"attacker-controlled payload"}'
captured_hmac = "<hmac header value that Shopify computed for the above body>"

# Attacker replays the same body/hmac but swaps the shop-domain header.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,   # unchanged, still valid for captured_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled value
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# lib/shopify_api/utils/hmac_validator.rb only checks HMAC(secret, raw_body) == captured_hmac,
# so this passes even though "shop" was never signed:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process forwards request.shop = "victim-shop.myshopify.com" to the handler,
# even though the body actually belongs to "attacker.myshopify.com".
ShopifyAPI::Webhooks::Registry.process(request)
```
