This confirms the vulnerability. The `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are all pulled from HTTP headers that are never part of the signed content [2](#0-1) . `Registry.process` only calls `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` and `request.topic` [3](#0-2) , and `HmacValidator.validate_signature` compares the computed HMAC only against `to_signable_string` (i.e., the body) [4](#0-3) .

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the body, not the headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body alone, while the `shop`, `topic`, and `webhook_id` fields consumed by `Registry.process` are read from unauthenticated HTTP headers. Because the signature never binds these header values, an attacker who legitimately owns one shop (and thus receives a genuinely-signed webhook body/HMAC pair from Shopify for their own install) can replay the identical body+HMAC pair while substituting an arbitrary `shopify-shop-domain` and/or `shopify-topic` header value. `Registry.process` accepts this because `Utils::HmacValidator.validate` only re-derives the signature from the body and never checks that the header-derived identity fields were part of what was signed.

### Finding Description
The intended binding is: `hmac == HMAC(secret, body || shop || topic || webhook_id)` (i.e., the authenticated identity of the webhook, including which shop and topic it belongs to, should be covered by the signature). What is actually implemented is: `hmac == HMAC(secret, body)` only [1](#0-0) . The `shop`, `topic`, and `webhook_id` accessors read straight from caller-supplied headers with no cryptographic tie to the HMAC [2](#0-1) .

`Registry.process` trusts these header-derived values directly when building `WebhookMetadata` passed to the app's handler:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [5](#0-4) 

Since `HmacValidator.validate_signature` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the header-supplied `hmac` value [4](#0-3) , any request whose body+HMAC pair was legitimately produced by Shopify for one shop/topic can be resubmitted with a different `shop-domain`/`topic` header and will still pass validation. The gem exposes `shop`, `topic`, and `webhook_id` as validated/trusted fields to the multi-tenant host app's handler, but none of that identity metadata is actually authenticated.

### Impact Explanation
This breaks the tenant identity binding `shop_authenticated == shop_acted_on`, allowing a shop that has installed the app to forge webhook deliveries attributed to a different (victim) shop or a different topic, causing the host application to write, process, or act on attacker-controlled data as if it belonged to another tenant's account — a cross-tenant data-integrity/confusion vulnerability in an app relying solely on this gem's `Registry.process`/`HmacValidator` for webhook authenticity and tenant attribution.

### Likelihood Explanation
Any developer/attacker who can install the app on their own shop (or capture one real webhook delivery, which are commonly logged/replayable since HTTP headers are separate from body) obtains a valid `(raw_body, hmac)` pair. Forging the `shopify-shop-domain`/`shopify-topic` headers on a replayed POST to the app's webhook endpoint requires no secret material at all.

### Recommendation
Include the shop domain, topic, and webhook id in the signable content (or otherwise cryptographically bind them, e.g. by having `HmacValidator`/`Request#to_signable_string` incorporate the relevant headers, not just the raw body) so that the HMAC authenticates the full identity tuple (`shop`, `topic`, `webhook_id`, `body`), not merely the body bytes.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H == HMAC(secret, B)`).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: shop/redact` (or any registered topic).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — still equal to `H` — and returns true [6](#0-5) .
4. The registered handler for the spoofed topic is invoked with `shop: "victim-shop.myshopify.com"` [7](#0-6) , causing the host app to process attacker-controlled data (e.g. triggering GDPR-erasure logic, or writing order data) under the victim tenant's identity.
