### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in webhook processing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` header as the identity of the shop that generated the event. Because the app's webhook signing secret (`api_secret_key`) is the same for every shop that installs the app, any merchant that has installed the app can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop, without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor reads directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding: [2](#0-1) .

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it to the `hmac-sha256` header value: [3](#0-2) .

`Registry.process` performs only this body-HMAC check, then immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and dispatches it to the app's handler: [4](#0-3) . `WebhookMetadata#shop` is a plain `String` field with no further validation: [5](#0-4) .

The binding this breaks, expressed as an equality that should hold but doesn't:
`shop_that_cryptographically_authenticated_the_request == shop_the_handler_is_told_the_event_came_from`

Before the attacker's request: for a genuine webhook, both sides are Shop A (the request body and the shop header both originate from Shopify for Shop A's event, and the signature is valid for Shop A's payload).

After the attacker's request: the attacker (an authenticated merchant of Shop A, who has legitimately installed the app and can freely receive/capture Shopify's webhook POSTs to their own callback URL) takes a body that Shopify validly signed for Shop A, and re-POSTs it to the app's webhook endpoint with the `shop-domain` header rewritten to Shop B. `Utils::HmacValidator.validate` still returns `true` because it only checks the (unmodified) body against the (unmodified) signature — the header is outside the signed content. `Registry.process` therefore invokes the app's handler with `WebhookMetadata#shop == "shop-b.myshopify.com"`, while the actual authenticated origin was Shop A.

This is the JWT/session-binding class of bug applied to webhooks: exactly analogous to trusting an unbound claim — here, a request field (the shop identity) is acted upon by the library/host app while not being covered by the message authentication code that establishes trust in the request.

### Impact Explanation
Apps built on this gem use `WebhookMetadata#shop` (per the documented API, `data.shop`) to determine which tenant's data/session to act on when processing a webhook — e.g., looking up that shop's stored access token, updating that shop's records, or acting on the mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics. Since a malicious but legitimately-installed merchant can forge the shop identity of a webhook while keeping the HMAC valid, they can cause the app to process a webhook body under another shop's identity. Depending on the topic and how the host app trusts `data.shop`, this enables cross-tenant data confusion/access — for example, injecting spoofed data (order/customer/product changes, GDPR "redact" requests) attributed to a victim shop, or draining rate-limited resources associated with the victim shop's identity within the app. This meets the Critical "cross-tenant access" bar because the trust boundary broken is precisely the shop/tenant identity binding that the HMAC is supposed to guarantee.

### Likelihood Explanation
Any unprivileged internet user who can install the app on any shop (including a free/trial development store) can capture their own valid webhook deliveries (they control the callback endpoint) and replay them with a modified header — no access to `api_secret_key`, access tokens, or other shops' credentials is required. This requires no social engineering or privileged access to the target shop.

### Recommendation
Bind the `shop-domain` (and other trust-relevant headers such as `topic`, `api-version`, `webhook-id`) into the HMAC-signed content, or otherwise cryptographically bind the shop domain to the signature. Since curl `Curl_fopen`/CVE-2023-32001's fix pattern (open-then-verify, avoiding TOCTOU) is not directly transferable to this Ruby gem's request-shape validation problem, the correct mitigation here is to change `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` to include the security-relevant headers in the signable content, and update `Utils::HmacValidator` documentation/tests to reflect that the shop identity is now part of what's verified. At minimum, document prominently that `request.shop` is NOT authenticated by the HMAC and that host applications must independently verify that the shop in the webhook matches a shop with an active, valid app installation/session before trusting it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers an HTTP webhook (e.g., `orders/create`) pointing to a server they control.
2. Shopify sends a legitimate webhook POST to the attacker's endpoint:
   ```
   POST /webhooks/orders_create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over raw_body, signed with the app's shared api_secret_key>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...}
   ```
3. The attacker replays this exact request to the app's public webhook endpoint (`ShopifyAPI::Webhooks::Registry.process`), only replacing the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
   keeping `Body` and `X-Shopify-Hmac-Sha256` byte-for-byte identical.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only re-computes the HMAC over `raw_body`, per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the request never actually originated for `victim-shop.myshopify.com`.
