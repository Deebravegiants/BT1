### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` Identity Fields Are Not Covered by the HMAC Signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the tenant-identifying `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers and passed straight through to the host application's webhook handler as trusted metadata. This mirrors the reported bug class: a field that is acted upon (here, the `shop` used to attribute/dispatch the webhook) is not covered by the cryptographic authenticator (the HMAC), breaking the intended binding "shop verified == shop acted on."

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`: [1](#0-0) 

That method returns only `@raw_body`: [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all extracted from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) via `shopify_header`, none of which are included in the HMAC-signed preimage: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` to route the event and build `WebhookMetadata`, which is handed to the app's handler as the authenticated tenant identity: [4](#0-3) 

`HmacValidator.validate` only compares the HMAC over `to_signable_string` (the raw body) — it never binds the header values into the signature: [5](#0-4) 

Equality that should hold but doesn't: `shop authenticated-by-HMAC == shop acted-on-by-handler`. In reality, `shop authenticated-by-HMAC` is undefined (HMAC covers only the body bytes), while `shop acted-on-by-handler` is whatever value the caller supplies in the `shopify-shop-domain` header.

### Impact Explanation
Any party that can produce a body/HMAC pair valid under the app's `api_secret_key` (e.g., a merchant who installs the app on their own shop and thus legitimately receives real webhooks with valid HMACs for their own body content, or anyone able to replay/forward a previously captured legitimate webhook body+HMAC pair) can submit that same body+HMAC to the app's webhook endpoint while attaching an arbitrary `X-Shopify-Shop-Domain` header. `Registry.process` will pass HMAC validation and dispatch `WebhookMetadata` claiming an attacker-chosen `shop`, `topic`, `api_version`, or `webhook_id`. Any host application that uses `WebhookMetadata#shop` to look up per-tenant sessions/credentials, gate GDPR redaction, or otherwise scope side effects will act on the wrong tenant — a cross-tenant confusion primitive.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request with a valid body/HMAC pair (obtainable by any merchant who installs the app, since Shopify signs webhooks per-app not per-shop) and full control over the other headers, which are not authenticated at all by this gem. No access token, `client_secret`, or privileged account is needed beyond ordinary app installation, making this readily reachable by an unprivileged internet user relative to the app's webhook endpoint.

### Recommendation
Bind the identity/session fields into the signed preimage, or otherwise independently authenticate them:
- Have `Request#to_signable_string` (or a new verification step) require that `shop`, `topic`, and `webhook_id` be validated against Shopify's known registration data before being trusted, or
- At minimum, cross-check `shop` against a `ShopValidator`-sanitized allow-list and confirm the `webhook_id`/`topic` combination was actually registered for that shop before constructing `WebhookMetadata`, rather than trusting raw headers once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `evil.myshopify.com`; capture a legitimate webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-SHA256: H` (valid because it was actually sent by Shopify, signed with the app's own secret).
2. Replay the exact same request to the app's public webhook endpoint, but change the header `X-Shopify-Shop-Domain` to `victim.myshopify.com` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Utils::HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `B`.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` and invokes the host app's handler, which will act as if this event genuinely originated from `victim.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
