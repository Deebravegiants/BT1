### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by checking that the raw HTTP body was HMAC-signed with the app's shared secret. The `shop-domain` header — which the registry treats as the authoritative tenant identifier and hands to every webhook handler — is never included in the signed bytes. Any actor able to produce (or replay) one genuinely-signed webhook body for the app can therefore relabel that payload as belonging to a different shop, breaking the binding between "bytes verified" and "tenant acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while the tenant identity used downstream comes from a separate, unsigned header: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string only, then immediately trusts `request.shop` as the tenant for the handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` confirm only that *some* valid body+secret pair was used — they say nothing about which shop that body was destined for: [4](#0-3) 

Because the app's `api_secret_key` is shared across **every** shop that has the app installed (it is not per-tenant), any unprivileged user who owns a shop with the app installed can:
1. Trigger a real event on their own store, causing Shopify to send a genuinely HMAC-signed webhook (with a body/HMAC pair that is valid for the app's secret) to the app's public webhook endpoint.
2. Capture or predict that `raw_body` + `hmac-sha256` pair (it is fully attacker-controlled data on their own store).
3. Replay that exact `raw_body`/`hmac-sha256` pair to the app's public webhook URL, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.

`HmacValidator.validate` still returns `true` (the body/secret HMAC is valid), and `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `shop` is now the attacker-chosen victim domain, while `body` is attacker-controlled content from their own store.

The broken identity equality is:
`hmac_verified(raw_body) == true` should imply `shop_header == the_shop_that_body_was_signed_for`, but the code only proves the former, never the latter — `shop-domain` is a field acted on (used to key/attribute the webhook) but not covered by the HMAC.

### Impact Explanation
This is a cross-tenant access/data-injection primitive: an app that keys per-shop state, sends notifications, or triggers privileged per-shop actions based on `WebhookMetadata#shop` can be made to apply attacker-supplied event data to an arbitrary victim shop's tenant context, without ever compromising that shop's credentials. This matches the Critical category of "cross-tenant access."

### Likelihood Explanation
High for any attacker who has (or creates) a store that installs the target app — a normal, unprivileged path available to any internet user via Shopify's free developer/partner accounts. No access token, `client_secret`, or leaked credential is required; only reachable, public webhook infrastructure and the ability to trigger events on one's own store.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the HMAC-verified signable content, or independently verify that `request.shop` matches a shop the app has legitimately installed/authorized for the specific webhook subscription id returned by Shopify, before trusting it in `Registry.process`. At minimum, document and enforce that host applications must cross-check `webhook_id`/`shop` against their own webhook registration records rather than trusting the header value outright.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an event (e.g., updates an order) so Shopify sends a webhook to the app's public endpoint with a legitimate `raw_body` and `X-Shopify-Hmac-Sha256` computed with the app's `api_secret_key`.
2. Attacker intercepts/replays this exact `raw_body` + `hmac-sha256` value in a new POST to the same public endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the shared secret.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, causing the host app to process attacker data under the victim shop's identity.
