### Title
Emporium-Min public-input path omits `stealthAddressStructure` and `rootHashHinkal` from both `calldataHash` and the SNARK public-input vector, breaking the proof↔wallet-identity binding - ([File: contracts/CircomDataBuilder.sol])

### Summary
For the "Emporium-min" transaction path (`externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`), `CircomDataBuilder.formInputEmporiumMin` feeds the verifier only `[emporiumMessage, timeStamp, calldataHash]` [1](#0-0) , and `MainEVMCircuitMin.circom` only declares `outTimeStamp`/`calldataHash` as public and a private `messageSeed` whose Poseidon hash becomes `message` — it never constrains `stealthAddressStructure` or `rootHashHinkal` at all [2](#0-1) . Neither is `stealthAddressStructure` (H1x, H1y, H0x, H0y, stealthAddress) nor `rootHashHinkal` included in `calldataHash` (`getHashedCalldata1`/`getHashedCalldata2`) [3](#0-2) . In the "normal" path, this gap is filled by `getSignedMessageHash`, which explicitly binds `rootHashHinkal` and the stealth-address fields into a hash included as a public signal via `formBasicInput` [4](#0-3) , but `formInputEmporiumMin` never calls `getSignedMessageHash` and never includes any stealth-address or root-hash signal [5](#0-4) .

### Finding Description
`Hinkal.transact` dispatches to `_externalTransact`, which for the Emporium action ID performs no ERC20 balance-diff logic (since `erc20TokenAddresses` is empty) and simply calls `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` with the entire `circomData` struct, including `stealthAddressStructure` [6](#0-5) . The `stealthAddressStructure` (identifying the private-key-controlled wallet/identity that is supposed to be authorizing the emporium action, per the "normal" flow's `getSignedMessageHash`) is:
- Not part of `calldataHash` (`getHashedCalldata1`/`getHashedCalldata2` never reference it) [3](#0-2) .
- Not part of the SNARK public-input vector for this path (`formInputEmporiumMin` only emits `emporiumMessage`, `timeStamp`, `calldataHash`) [1](#0-0) .
- Not constrained inside `MainEVMCircuitMin.circom`, which has no signals at all for stealth address or root hash [2](#0-1) .

`HinkalHelper.dimensionsCheck` only requires `H0x != 0`, not that it matches any value proven by the circuit [7](#0-6) . `HinkalHelper.performHinkalChecks` verifies `calldataHash` integrity and dimension checks, but since `calldataHash` doesn't cover `stealthAddressStructure`/`rootHashHinkal`, those fields pass unchecked [8](#0-7) .

The result is that a valid Groth16 proof produced for one `emporiumMessage`/`calldataHash` combination places zero cryptographic constraint on which `stealthAddressStructure` (wallet identity) is submitted alongside it in the same `transact` call — the equality "the proof authorizes action X for stealth identity Y" is broken because Y is entirely absent from both the hash-committed calldata and the public-input vector for this specific dispatch path.

### Impact Explanation
If the Emporium/HinkalWallet action derives or targets a specific user wallet from `circomData.stealthAddressStructure` (as the "normal" path's design intends via `getSignedMessageHash`), an attacker could submit a previously-valid Emporium-min proof/`calldataHash` pair together with an arbitrary, unauthorized `stealthAddressStructure`, causing `runAction`/`HinkalWallet.callHinkalWallet` to execute an action attributed to or affecting a wallet identity that was never actually proven or signed for by that call. This matches the "executing calls or moving assets a wallet owner or prover never authorised" High-impact category.

### Likelihood Explanation
This requires the caller to control `circomData` fields for an Emporium-only transaction (`erc20TokenAddresses.length == 0`), which is directly reachable by any unprivileged EOA calling `Hinkal.transact` with a legitimately obtained proof/`calldataHash` for their own `emporiumMessage`; the missing binding is a structural gap in `formInputEmporiumMin` versus `formBasicInput`/`getSignedMessageHash`, not a rare edge case.

### Recommendation
In `CircomDataBuilder.formInputEmporiumMin`, include the `stealthAddressStructure` fields (and `rootHashHinkal`, if used to determine wallet state in the Emporium path) either directly as public-input signals or via a `getSignedMessageHash`-equivalent hash, mirroring `formBasicInput`, and add matching constraints in `MainEVMCircuitMin.circom` (or the correct top-level Emporium circuit) so the proof cryptographically binds the wallet identity to the authorized action, exactly as recommended in the referenced report for binding `finalBlockNumber` into the public input/verifier.

### Proof of Concept
Conceptual sequence (concrete exploitation requires the Emporium/HinkalWallet action contract, which was not available to fully inspect within tool budget):
1. Attacker obtains a valid Groth16 proof `(a, b, c)` for `MainEVMCircuitMin` with `messageSeed → message == emporiumMessage`, and a `calldataHash` computed with attacker-chosen `hookData`, `encryptedOutputs`, `feeStructure`, etc. (none of these need to reference any specific wallet).
2. Attacker calls `Hinkal.transact(a, b, c, dimensions, circomData)` with `erc20TokenAddresses = []`, `dimensions.tokenNumber = 0`, and sets `circomData.stealthAddressStructure` to an arbitrary value (only constrained to have `H0x != 0` by `dimensionsCheck`) [7](#0-6) .
3. `performHinkalChecks` passes (calldataHash matches, dimensions are internally consistent) [8](#0-7) ; `verifyProof` passes because the public input `[emporiumMessage, timeStamp, calldataHash]` still matches the circuit output regardless of the chosen `stealthAddressStructure` [1](#0-0) .
4. `_externalTransact` invokes `runAction(circomData, [])` using the attacker-substituted `stealthAddressStructure`, with no on-chain or in-circuit check that this identity matches the one that actually produced the proof [6](#0-5) .

Note: full end-to-end confirmation would require reviewing the concrete Emporium external-action contract (not located within available tool budget) to confirm exactly how `stealthAddressStructure` is consumed by `runAction`; this is flagged as an open verification item.

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
