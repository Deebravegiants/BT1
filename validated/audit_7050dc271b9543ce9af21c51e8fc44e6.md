## Title
Webhook shop identity spoofing via HMAC that only covers the raw body, not the `shop`/`topic` headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (and `request.topic`) taken straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header without that value ever being bound to the HMAC signature. Any caller who can obtain one legitimately-signed `(body, hmac)` pair for the shared app secret can resubmit that same body with an arbitrary `shop` header and have it processed by the app as belonging to a different, victim shop.

### Finding Description
The webhook signature is computed only over the body: [1](#0-0) 

`Request#shop` is parsed purely from headers and is not part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e., the body only), and then unconditionally forwards `request.shop` and `request.topic` to the handler as trusted identity metadata: [3](#0-2) 

The HMAC validator itself only checks the value returned by `to_signable_string` against the secret: [4](#0-3) 

The webhook secret (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app — it is not per-shop. So the binding that should hold is:
`HMAC-verified(body) == identity claimed for that body (shop, topic)`
but the code only enforces `HMAC-verified(body)`, and separately trusts the `shop`/`topic` headers with no cryptographic tie to the body they arrived with. This is exactly the "field acted on but not covered by the HMAC" pattern: `shop` (the tenant-identifying field) is not included in `to_signable_string`, so it can be swapped for any value without invalidating the signature.

The docs confirm the handler receives and is expected to act on `data.shop` as the deciding tenant identifier for the webhook: [5](#0-4) 

### Impact Explanation
Because the app's webhook `client_secret` is shared across all shops (not per-tenant), an attacker who installs the same app on their own store obtains genuinely HMAC-signed `(body, signature)` pairs. They can replay that exact body to the app's single public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Utils::HmacValidator.validate` still passes (it never inspects the header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop. Any host application logic keyed on `data.shop` for tenant-scoped work — e.g. GDPR mandatory topics `customers/redact`, `customers/data_request`, `shop/redact` — can be tricked into attributing attacker-supplied content to a shop the attacker does not control, a cross-tenant identity-binding break.

### Likelihood Explanation
Exploitation requires no privileged credentials: any internet user can self-serve install the target app on a shop they control (a normal, unprivileged action) to legitimately obtain a signed body/HMAC pair, then send a crafted HTTP request to the app's public webhook endpoint with a different `shop` header. No access token, `client_secret`, or TLS interception is required.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body (e.g., require the host app to independently confirm `request.shop` corresponds to a shop with an active installation/session before trusting `data.shop`), rather than relying solely on body-only HMAC verification in `Request#to_signable_string`.

### Proof of Concept
1. Attacker creates/uses a dev shop `attacker.myshopify.com` and installs the target app; Shopify calls the app's webhook endpoint with a body `B` and a valid `X-Shopify-Hmac-Sha256` computed over `B` using the app's `client_secret`.
2. Attacker captures `(B, HMAC(B))`.
3. Attacker POSTs to the same public webhook endpoint with body `B`, the captured (still valid) `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, a mandatory topic like `customers/redact`).
4. `Utils::HmacValidator.validate` (via `lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `B` against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the registered handler with `WebhookMetadata` claiming `shop: "victim.myshopify.com"` and the attacker-supplied `body`, causing the host app to process attacker-controlled content under the victim's tenant identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
