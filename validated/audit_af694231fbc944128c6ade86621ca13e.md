### Title
Webhook shop identity spoofing via unauthenticated `x-shopify-shop-domain` header not covered by HMAC - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request body, but the `shop` identity that is handed to the application's handler is read from an HTTP header that is never included in the signed material. This breaks the intended binding of "HMAC-verified request == the shop asserted by the request."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely independent of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers the body) and then constructs `WebhookMetadata` using `request.shop`, the unauthenticated header value, and hands it to the app's handler: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` — i.e. the body — using the app's shared `api_secret_key`: [4](#0-3) 

Because the HMAC secret (`api_secret_key`) is shared across all shops that install a given app, a genuine, validly-signed webhook delivered for one shop has a body+HMAC pair that will still validate successfully if replayed with a different `x-shopify-shop-domain` header value. The library's documented usage pattern explicitly trusts `data.shop` as the shop identity for the webhook (e.g. to route/store data per-tenant): [5](#0-4) [6](#0-5) 

The identity binding that is broken, expressed as an equality that should hold but doesn't:
`shop_that_HMAC_secret_was_computed_for == shop_passed_to_handler`

In fact the code only guarantees:
`HMAC(raw_body, api_secret_key) == received_hmac`

with no cryptographic tie between that body/HMAC pair and the `shop` header value that accompanies it.

### Impact Explanation
Any merchant who has installed the app (an unprivileged actor with respect to other merchants' data) receives real webhooks for their own shop, each with a valid body and HMAC signature (since the same `api_secret_key` is used for every shop of that app). That merchant can capture one such payload and replay it to the app's webhook endpoint after modifying only the `x-shopify-shop-domain` header to name a different (victim) shop. `HmacValidator.validate` will still pass because it never inspects the header, and the app's webhook handler will process the (attacker's own, but otherwise legitimate-looking) payload attributed to the victim shop. Depending on how the app's handler uses `data.shop` (e.g., attaching the payload to the victim's shop's session/store lookup, triggering side effects scoped by shop), this enables cross-tenant data confusion/injection — writing or triggering behavior against another tenant's account using data attributed as coming from them. This matches the "cross-tenant access" Critical impact category, as the identity binding between the cryptographically-verified payload and the shop it is attributed to is not enforced by the gem.

### Likelihood Explanation
Exploitation requires only: (1) being an installed merchant of the target app (no special privileges, no access to `api_secret_key` or any access token), (2) receiving at least one real webhook for one's own shop (trivial — webhooks fire automatically on standard shop events like `orders/create`), and (3) POSTing the captured body with a forged `x-shopify-shop-domain` header to the app's public webhook endpoint. No cryptographic secret needs to be broken; only the (by-design) fact that the HMAC never covers headers is leveraged. This is straightforward and repeatable for any developer building on this gem who — following its documented API exactly — trusts `data.shop`.

### Recommendation
Bind the shop identity to the verified payload, e.g. by requiring the webhook signature to also cover header fields the app depends on (not solely the body), or by cross-checking `request.shop` against an independently-verified source (such as the webhook's registered shop from Shopify's Admin API / an active session for that shop) before dispatching to the handler. At minimum, document explicitly that `data.shop` is not itself HMAC-verified and must not be trusted as a tenant boundary without additional verification (e.g., confirming the shop already has an app session/installation on record), and consider exposing/verifying the `webhook_id` against Shopify per-shop registration to bind topic+shop+signature together.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and it is a legitimate merchant, no special access needed.
2. Shopify sends a legitimate webhook, e.g. `orders/create`, to the app's endpoint with body `B`, header `x-shopify-hmac-sha256: H` (valid for `HMAC(B, api_secret_key)`), and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker (having received this webhook, e.g. via a proxy/logging tool they control, or by triggering an order on their own store and observing the raw request to their own endpoint) resends the exact same body `B` and `x-shopify-hmac-sha256: H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B, api_secret_key) == H` — unaffected by the header change: [3](#0-2) 
5. The app's handler receives `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` and processes/attributes the attacker-controlled body `B` as if it originated from `victim-shop.myshopify.com`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
