### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` covers the request body alone. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values, which are read from HTTP headers and handed directly to the host application's `WebhookHandler#handle` via `WebhookMetadata`, are never part of the signed material. This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop acted upon by the handler`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `shop` is read straight from the (unsigned) header: [2](#0-1) 

`Registry.process` validates the HMAC over that same `to_signable_string` (i.e. body-only) and then, without any further check that `request.shop` actually matches an installed/authorized shop for the given secret, forwards it verbatim to the registered handler: [3](#0-2) 

`HmacValidator.validate` itself only ever signs/verifies `verifiable_query.to_signable_string`, so whatever that method returns is the entire trust boundary: [4](#0-3) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields end up in `WebhookMetadata`, which is the only tenant-identifying information the host app's handler receives: [5](#0-4) 

Because a single `client_secret` is shared across every shop that installs the app, any merchant who has installed the app can receive a legitimately-HMAC-signed webhook for their own shop and body, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header for a different (victim) shop. Since `to_signable_string` never included those headers, the HMAC still validates, and `Registry.process` passes the attacker-controlled `shop` value straight into the handler as if it were the authenticated tenant for that payload/topic.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem authenticates only the body/secret pair, but the host application's handler is designed to trust `WebhookMetadata#shop`/`topic` as the authenticated tenant and event type for that body. An attacker who is a merchant on the app (i.e. possesses one valid HMAC/body pair from their own shop) can cause the handler to execute tenant-scoped logic (e.g. writing/deleting data, GDPR redact flows, or business logic keyed off `shop`) attributed to a shop they don't own, achieving cross-tenant access/action confusion without ever knowing the `client_secret`.

### Likelihood Explanation
Any shop that has installed the app can generate at least one valid `(body, hmac)` pair by triggering a real webhook event (e.g. `orders/create`) from their own store — this requires no credential leakage, TLS interception, or the `client_secret`, only normal merchant access to a shop that has the app installed. Replaying that request with a modified `shop-domain` header against the app's public webhook endpoint is straightforward for any unprivileged internet user with such access.

### Recommendation
Include the security-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the body (e.g., by having `Registry.process` cross-check them against out-of-band-verified state, such as an active `Auth::Session` for that shop) before constructing `WebhookMetadata` and dispatching to the handler. At minimum, document prominently that the `shop`/`topic`/`webhook_id` fields on `WebhookMetadata` are not covered by the HMAC and must not be trusted for authorization decisions without additional verification (e.g., confirming the shop has an active, stored session/install).

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) with body `{}`.
2. Shopify sends the app: `x-shopify-hmac-sha256: <valid HMAC of "{}">`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker replays this exact request to the app's public webhook endpoint but changes the header to `x-shopify-shop-domain: victim.myshopify.com` (leaving body and HMAC untouched).
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-computes the HMAC over the untouched `@raw_body` — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", ...)` and invokes the host app's `handler.handle(data:)`, which now executes tenant logic attributed to `victim.myshopify.com` even though the payload/HMAC never originated from that shop.         def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
