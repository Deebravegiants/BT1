Confirmed: the webhook HMAC only covers the raw body, while the `topic`, `shop-domain`, `webhook-id`, and `api-version` headers are parsed and trusted independently, with no cryptographic binding between them and the signed bytes.### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted as authenticated identity while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authentic for a given shop/topic purely because `Utils::HmacValidator.validate(request)` returns true, then hands `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` straight to the app's `WebhookHandler` as `WebhookMetadata`. However the HMAC signature only ever covers `@raw_body` (`to_signable_string` returns just the body), never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that `Request#shop`, `#topic`, `#webhook_id`, `#api_version` read. This is a "bytes verified vs. bytes parsed" mismatch: the cryptographic check authenticates the body bytes, but the identity fields the handler actually acts on are unauthenticated, attacker-controllable header values.

### Finding Description
- `Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it to the `hmac` field with `OpenSSL.secure_compare`. [1](#0-0) 
- For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 
- But `shop`, `topic`, `webhook_id`, and `api_version` are all parsed straight from HTTP headers, none of which are part of the signed data: [3](#0-2) 
- `Registry.process` validates the HMAC once, then dispatches to the handler using these unauthenticated header values as if they were verified: [4](#0-3) 
- The handler receives `WebhookMetadata` with `shop` and `topic` as plain, trusted `String` fields, with no indication to the app author that they are unauthenticated: [5](#0-4) 

Because the signature never binds `shop`, `topic`, or `webhook_id` to the body, anyone who can obtain one valid `(raw_body, hmac)` pair signed with the app's secret (e.g., by installing the app on their own store and capturing any real webhook delivery) can resubmit that exact body/HMAC pair to the app's webhook endpoint while freely rewriting the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming an arbitrary shop/topic/webhook_id, chosen entirely by the attacker.

### Impact Explanation
This breaks the binding "shop authenticated == shop the handler acts on." An attacker (any merchant who installed the app, i.e. any unprivileged internet user who can trigger one real webhook to themselves) can forge webhook deliveries that claim to originate from a different, victim shop or a different topic than the one that was actually signed. Depending on the handler logic (common patterns: writing per-shop state keyed by `data.shop`, honoring `shop/redact`/`customers/redact`/`app/uninstalled` topics to delete or reset data, or trusting `webhook_id` for idempotency), this enables cross-tenant data corruption/deletion or triggering privileged lifecycle events for shops the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that relies on the gem's `Registry.process`/`WebhookHandler` contract as documented, since:
1. Getting one legitimately signed `(body, hmac)` pair only requires installing the app on an attacker-controlled shop and waiting for/triggering any webhook.
2. The webhook HTTP endpoint is public-facing and the header fields are trivially rewritable in a replayed request.
3. Nothing in the gem's API surfaces a warning that `shop`/`topic`/`webhook_id` are unauthenticated, so app authors reasonably treat `WebhookMetadata#shop` as trustworthy, matching how the gem's own tests use it.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop` and `topic`) in the signable string used for HMAC validation, or otherwise cryptographically bind them to the verified body (e.g., derive/validate them only from a payload field that is itself part of the signed body, not from headers). At minimum, document prominently that these header-derived fields are unauthenticated and must not be used for authorization decisions without additional verification (e.g., cross-checking against a session/shop the app already trusts).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and lets it deliver one real webhook (e.g. `orders/create`), capturing the raw request body `B` and its valid header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid since only body is signed)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (rewritten)
   - `x-shopify-topic: shop/redact` (rewritten to any registered topic)
   - `x-shopify-webhook-id: <anything>`
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`. [6](#0-5) 
4. `Registry.process` looks up the handler for the forged `topic` and calls it with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, and the app's handler acts as if Shopify genuinely sent a `shop/redact` event for `victim-shop.myshopify.com`. [7](#0-6)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
