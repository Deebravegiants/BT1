Audit Report

## Title
Missing future-timestamp validation in `HandleLegacyUserMessage` allows indefinite replay of signed Web API trigger messages - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`HandleLegacyUserMessage` only checks that a client-supplied `TriggerRequestPayload.Timestamp` is not too old; it never checks that the timestamp is not in the future. Since `Timestamp` is fully attacker-controlled input carried in the signed payload, a caller can set it arbitrarily far ahead, making the staleness check `now - MaxAllowedMessageAgeSec > payload.Timestamp` permanently false and thereby defeating the freshness/replay window.

## Finding Description
The handler decodes the payload and performs a single one-sided bound check: [1](#0-0) 

There is no corresponding check rejecting `payload.Timestamp` values that lie ahead of `time.Now()`. Beyond this check, the only remaining logic is a method check, request transformation, and unconditional forwarding to every DON member — no nonce, digest, or "already-processed" tracking exists in this path: [2](#0-1) 

This confirms the root cause: the freshness check is asymmetric (only bounds the past), and no other replay-protection mechanism exists in `HandleLegacyUserMessage` to compensate. `savedCallbacks` keyed by `MessageID` exists only to track pending outbound callbacks for the gateway's own response routing, not to deduplicate/reject repeated incoming trigger messages.

I was unable to fully trace, within the available tool budget, where/whether message signature verification (sender authentication) occurs upstream of `HandleLegacyUserMessage` in `gateway.go`/`connectionmanager.go`; this is a known area of uncertainty. However, even assuming signatures are verified upstream (i.e., the sender is a legitimately allowed sender), the finding still holds: the signature only proves the sender's identity/authorization for that payload, not the payload's one-time validity, so replay of a validly-signed but future-dated message remains possible as described.

## Impact Explanation
This matches an in-scope "unauthorized job run" category: a message signed once by an authorized (but otherwise unprivileged) trigger caller could be resent repeatedly to the DON to re-trigger a workflow, bypassing the intended freshness-based replay control, for as long as the forged future timestamp remains ahead of `now - MaxAllowedMessageAgeSec`. The severity is bounded by the fact that this only affects the legacy Web API trigger method (`MethodWebAPITrigger`) and requires the workflow-level DON/OCR logic to also act on a duplicate trigger (out of scope here to verify), but the gateway-level input-validation gap itself is real and concrete.

## Likelihood Explanation
Likelihood is moderate: the only precondition is being an already-authorized sender for a workflow trigger (or capturing a previously valid signed message before its natural expiry), and constructing a `Timestamp` field with an arbitrarily large future value — a straightforward, low-effort input manipulation with no need to break cryptography. The bug is a plain missing-bound-check in input validation, consistent with the code shown.

## Recommendation
Add a symmetric future-timestamp bound in addition to the existing staleness check:
```go
now := uint(time.Now().Unix())
if uint64(payload.Timestamp) > uint64(now)+clockSkewToleranceSec {
    // reject: timestamp is in the future
}
if now-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    // reject: stale message
}
```
Additionally, consider adding per-sender/per-message replay tracking (similar to `RequestReplayGuard` or `jwtReplayCache` patterns used elsewhere in the gateway) so timestamp freshness is not the sole replay defense for this legacy trigger path.

## Proof of Concept
1. As an authorized trigger sender, construct a `TriggerRequestPayload` with `Timestamp = time.Now().Unix() + 10_000_000` and sign it per normal protocol.
2. Send it once via the gateway; `HandleLegacyUserMessage` passes the check at handler.go:372 because `now - MaxAllowedMessageAgeSec` never exceeds the future timestamp, so the message is forwarded to all DON members via `don.SendToNode` (handler.go:417-419).
3. Resend the identical signed message at any later point up to the forged timestamp; each resend again passes the same check, and since no nonce/replay cache exists in this handler, the trigger fires again.
4. A Go unit test extending `handler_test.go` asserting that two consecutive calls to `HandleLegacyUserMessage` with the same message and a future `Timestamp` both succeed (both forwarded, no rejection) would demonstrate the gap.
