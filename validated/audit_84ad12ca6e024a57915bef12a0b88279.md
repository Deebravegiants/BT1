### Title
No minimum-cost enforcement on attacker-supplied scrypt KDF parameters in `metadata.decryptBlobKey()` allows offline KDF downgrade of imported `.seco` files - ([File: libraries/secure-container/src/metadata.js])

### Summary
`metadata.decryptBlobKey()` derives the AES key that unwraps `blobKey` by calling `boxDecrypt()`/`stretchPassphrase()` with the `n`, `r`, `p` scrypt cost parameters taken verbatim from the file's own `metadata` section, with no lower bound check. Since these parameters are fully attacker-controlled bytes in an imported/crafted `.seco` file, and since consumers like `seco-rw`/`seco-keyval` explicitly cache and reuse a file's existing `metadata`/`blobKey` on subsequent writes to "avoid expensive scrypt operations," a maliciously crafted low-cost-KDF `.seco` file can permanently downgrade the KDF strength protecting all future secrets written into that vault.

### Finding Description
The metadata binary format embeds the scrypt `n`, `r`, `p` cost factors alongside the salt, wrapped-key material and cipher tag: [1](#0-0) 

`decode()` only warns if the buffer is larger than expected; it performs no semantic validation of the numeric fields: [2](#0-1) 

`decryptBlobKey()` passes `metadata.scrypt` — attacker-controlled — straight into `boxDecrypt()`: [3](#0-2) 

`boxDecrypt()`/`stretchPassphrase()` use these values directly as scrypt cost parameters with no minimum enforced: [4](#0-3) [5](#0-4) 

This is reached transitively from `secure-container`'s top-level `decrypt()`: [6](#0-5) 

and from `seco-file`'s `read()`, which is the documented, wallet-facing entry point for opening a `.seco` file: [7](#0-6) 

The root cause of persistence (not just one-time weak decryption) is that `seco-rw` and `seco-keyval` explicitly cache and reuse the `blobKey`/`metadata` obtained from an existing file across subsequent writes, rather than re-deriving with fresh parameters: [8](#0-7) [9](#0-8) 

Because `metadata.create()`/`createScryptParams()` only supplies *defaults* used when *new* metadata is generated, and never enforces a minimum on *decoded, attacker-supplied* metadata, an attacker who gets a victim to import/open a `.seco` file with `n=1` (or similarly trivial) locks in that low-cost KDF for the life of the vault as long as the application reuses the cached `metadata`/`blobKey` on subsequent writes: [10](#0-9) 

### Impact Explanation
If a victim's wallet software imports an attacker-crafted `.seco` backup and continues operating on it (reading it via `seco-file`/`seco-rw`/`seco-keyval` and writing real secrets back using the cached `metadata`/`blobKey`, which is the documented usage pattern), the KDF protecting the wrapped `blobKey` — and hence all encrypted wallet secrets in that container — is downgraded to whatever trivial cost factor the attacker chose. If the resulting file is later exfiltrated (e.g., cloud backup leak, stolen device, malware exfil), the attacker can brute-force the user's passphrase offline far faster than the intended scrypt cost would allow, leading to recovery of wallet secrets. This matches a "recovery of encrypted wallet secrets via KDF downgrade" impact.

### Likelihood Explanation
The precondition is narrow but plausible: the attacker must get their crafted `.seco` bytes accepted as the "existing" backing file for a persistent vault (e.g., malicious imported backup used as the working wallet file rather than replaced), and the application must follow the `seco-rw`/`seco-keyval` pattern of caching/reusing `metadata` and `blobKey` on write instead of re-deriving with a fresh, safe scrypt cost. Given that pattern is the documented, intended usage of these libraries, the likelihood of at least one consuming wallet doing this is meaningful, though it depends on downstream app behavior not shown in this library in isolation.

### Recommendation
Enforce minimum acceptable scrypt cost parameters (e.g., `n >= 16384`, `r >= 8`, `p >= 1`, or a computed minimum work factor) in `metadata.decode()` or in `decryptBlobKey()`/`boxDecrypt()` before deriving keys, rejecting metadata whose `n`/`r`/`p` fall below the threshold. Additionally, consider re-deriving (re-wrapping `blobKey`) with fresh, policy-compliant scrypt parameters whenever a vault is opened with a passphrase, rather than unconditionally trusting and reusing cached/on-disk KDF parameters across writes.

### Proof of Concept
Unit test in `libraries/secure-container/src/__tests__/metadata.test.js`:
1. Build a metadata object via `metadata.create({ salt: randomBytes(32), n: 2, r: 1, p: 1 })` (or `metadata.decode()` of a hand-crafted buffer with `n=1`).
2. Call `await metadata.encryptBlobKey(md, passphrase, blobKey)` to produce a validly-wrapped `blobKey` under these trivial parameters (simulating attacker-crafted bytes with correctly-computed wrap, or directly constructing the wrapped ciphertext via `boxEncrypt` with these params).
3. Call `await metadata.decryptBlobKey(md, passphrase)` and assert it **throws** (e.g., `"scrypt cost factor below minimum"`) instead of returning the unwrapped key.
4. Currently this assertion fails — `decryptBlobKey()` silently succeeds regardless of how low `n`/`r`/`p` are — demonstrating the missing minimum-KDF-cost enforcement.

export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}

export async function read (file: string, passphrase: BufOrStr) {
  let fileData = await fs.readFile(file)

  let result
  try {
    result = decrypt(fileData, passphrase)
  } catch (e) {
    if (e.message.match(/seco checksum does not match; data may be corrupted/)) {
      throw new Error(`${file}: seco checksum does not match; file may be corrupted`)
    }
    throw e
  }

  return result
}
