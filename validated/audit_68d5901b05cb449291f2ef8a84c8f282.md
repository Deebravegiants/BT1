### Title
Unrelated lifecycle-hook failure causes `unlock()`/`changePassphrase()` to desync wallet lock state - ([File: features/application/src/modules/application.ts])

### Summary
### Finding Description
`Application.fire()` executes all registered listeners for a lifecycle hook and re-throws any error a listener produces after logging it: [1](#0-0) 

`unlock()` calls `#wallet.unlock(opts)`, sets `#lockedAtom` to `false` (i.e. the wallet is now actually unlocked and the atom broadcasting that state to observers/UI is updated), and only afterwards fires `Hook.Migrate` and `Hook.Unlock`: [2](#0-1) 

Because hooks are run sequentially by default (`concurrent` is not passed for `Hook.Migrate`/`Hook.Unlock`), any plugin registered on `onMigrate`/`onUnlock` that throws (network hiccup, unrelated feature error, timeout, etc.) causes `fire()` to reject, which propagates out of `unlock()` and rejects the whole call — exactly the same "any failure anywhere reverts the whole unrelated operation" pattern described in the Canto `PostTxProcessing` report, where an unrelated CSR-specific failure (e.g. fee = 0) reverted a transaction that had nothing to do with CSR.

The plugin wrapper used to attach `onUnlock`/`onMigrate`/etc. methods does not swallow plugin errors — it only measures timing and clears a timeout, then re-throws the original plugin exception: [3](#0-2) 

Since `#wallet.unlock()` already succeeded and `#lockedAtom.set(false)` already executed *before* the failing hook runs, the security-relevant lock state (`lockedAtom`, which is broadcast to the UI/RPC layer as the `locked` event and consumed as the wallet's authorization gate) has already flipped to "unlocked" in memory when the `unlock()` promise subsequently rejects to the caller. Compare with the analogous migration hook, which is wrapped in its own try/catch and does not propagate errors: [4](#0-3) 
— i.e. the codebase already treats `Hook.Migrate` failures leniently in one place but the `unlock()` flow still lets any hook failure abort the call after the atom mutation has already taken effect.

`lockedAtom` is the primitive that downstream consumers observe to know the true lock state (e.g. it's propagated to the port/UI as the `locked` event): [5](#0-4) 

### Impact Explanation
When an unrelated `onUnlock`/`onMigrate` plugin throws (for reasons entirely outside the scope of authentication — e.g., a feature's post-unlock sync error), the caller of `unlock()` receives a rejected promise and will typically treat this as "unlock failed" (still locked). However, the underlying wallet state and `lockedAtom` have already transitioned to unlocked. This produces a state where the UI/RPC layer believes authentication failed/is pending while the wallet core is actually unlocked and capable of servicing signing/secret-disclosure operations that gate on `lockedAtom`/`isLocked()`. This is a lock-state/auth-state desynchronization bug directly analogous to the CSR `PostTxProcessing` issue, where an operation unrelated to the reverting condition (Turnstile fee distribution vs. CSR-unrelated tx) was aborted/misreported due to an unrelated hook's failure.

### Likelihood Explanation
This triggers whenever any registered `onUnlock`/`onMigrate` plugin throws — which can happen from ordinary conditions (timeouts, storage errors, network errors in an unrelated feature) since nothing in `fire()` isolates hook failures for these two hooks the way it does (implicitly, via try/catch) for migrations. No malicious actor is required to trigger the underlying desync (matching the original report's "can happen in normal circumstances" framing); an attacker who can induce any plugin to throw during unlock (e.g., via crafted remote-config, malformed data ingested by an unrelated feature) increases likelihood further, but even benign faults suffice.

### Recommendation
In `Application.fire()` (or specifically for `Hook.Unlock`/`Hook.Migrate`), log-and-continue instead of re-throwing hook errors, mirroring the pattern already used in `migrations/attach.js`. At minimum, ensure `unlock()`/`changePassphrase()` do not leave `lockedAtom` (or other authorization-relevant atoms) mutated ahead of hooks whose failure will abort the call; either move the atom mutation after all hooks resolve, or make hook failures non-fatal to these lifecycle calls, with errors reported via `errorTracking`/logger only.

### Proof of Concept
1. Register a plugin with an `onUnlock` handler that throws (e.g., a broken feature module calling an external API that fails intermittently), attached via `attachPlugins`: [6](#0-5) 
2. Call `application.unlock({ passphrase })`.
3. Observe: `#wallet.unlock()` succeeds and `#lockedAtom.set(false)` executes, then `fire(Hook.Unlock)` throws because of the unrelated plugin, and the `unlock()` promise rejects: [7](#0-6) 
4. The caller sees a rejected `unlock()` call (interpreted as "still locked"), while `lockedAtom` has already been broadcast as `false`/unlocked to any observers (e.g. UI, RPC port), producing an authorization-state mismatch.

```javascript
const attachPlugins = ({ plugins, application, logger, pluginTimeout }) => {
  const lifecycleFuncWrapper = (fn, name) => {
    const timeFn = async (...args) => {
      const timeoutPid = setTimeout(() => {
        logger.warn(`${name} reached time out of ${pluginTimeout}ms and is still running ...`)
      }, pluginTimeout)
      const start = Date.now()
      try {
        return await fn(...args)
      } finally {
        logger.debug(name, `${Date.now() - start}ms`)
        clearTimeout(timeoutPid)
      }
    }

    Object.defineProperty(timeFn, 'name', { value: name, writable: false })

    if (typeof fn.priority === 'number') {
      Object.defineProperty(timeFn, 'priority', { value: fn.priority, writable: false })
    }

    return timeFn
  }
```
