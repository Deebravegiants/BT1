### Title
Unsigned Emporium `EmporiumStack` (signerAddress == 0) combined with empty `erc20TokenAddresses` allows unauthorized, unaccounted arbitrary calls draining Emporium-held balances - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol / contracts/CircomDataBuilder.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes proof verification to `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin.circom`) only proves `message == Poseidon(messageSeed)` — a constraint any unprivileged party can satisfy for a message of their own choosing, with no binding to UTXO ownership, nullifiers, or amounts. Combined with `EmporiumUpgradeable.verifyWallet` short-circuiting all signature checks when `stack.signerAddress == address(0)`, and both `Hinkal.transact`'s and `runAction`'s balance-accounting loops iterating an empty `erc20TokenAddresses` array, an attacker can execute an arbitrary, self-crafted `EmporiumStack.ops[]` from Emporium's address with zero authorization and zero balance accounting.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which calls `CircomDataBuilder.formInputForCircom` [1](#0-0) . Because the attacker sets `erc20TokenAddresses.length == 0` and `externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `formInputEmporiumMin` is selected, producing only 3 public signals (`emporiumMessage`, `timeStamp`, `calldataHash`) [2](#0-1) .
2. The corresponding circuit `MainEVMCircuitMin.circom` only proves `message <== Poseidon(1)([messageSeed])` — a public, non-secret computation the attacker can perform themselves for any `message` value they choose [3](#0-2) . This proof carries **no** ownership/nullifier/root binding, unlike the full `MainEVMCircuit` which enforces `inNullifiers === calcNullifier.out` against `rootHashHinkal` [4](#0-3) .
3. `Hinkal.transact` proceeds to `_externalTransact`, building `deltaAmountChanges` of length `erc20TokenAddresses.length == 0` (empty), and calls `EmporiumUpgradeable.runAction` [5](#0-4) .
4. In `runAction`, the attacker-controlled `EmporiumStack` is decoded directly from `externalActionData.externalActionMetadata` [6](#0-5) . `balancesBefore`/`balancesAfter` are computed only over `circomData.erc20TokenAddresses`, which is empty, so they are empty arrays and account for nothing [7](#0-6) .
5. `verifyWallet` is called; when the attacker sets `stack.signerAddress == address(0)`, it marks the replay-protection flag and **returns immediately without any signature check** — no ECDSA verification, no deadline, no fee cap enforcement [8](#0-7) .
6. The `ops` loop then executes `stack.ops.length` operations — a length entirely independent of `erc20TokenAddresses.length` — performing `op.endpoint.call{value: op.value}(op.callData)` directly as Emporium, with the only restriction being a selector-block on `callHinkalWallet`/`doSendToRelay` [9](#0-8) .
7. Back in `Hinkal.transact`, the post-action balance/slippage/UTXO-accounting loop at lines 97-147 also iterates `circomData.erc20TokenAddresses` (empty), so it enforces nothing either [10](#0-9) .

Root cause: the only integrity guard that ties the attacker's calldata to the proof is `getHashedCalldata`/`calldataHash` equality in `performHinkalChecks` [11](#0-10) , which is a **self-consistency** check (the attacker computes the hash of their own chosen calldata) — it provides no actual authorization. Real authorization for arbitrary ops is supposed to come from either (a) a valid EmporiumOperation signature (`verifyWallet` with non-zero `signerAddress`), or (b) full-circuit proof of UTXO ownership tying `amountChanges`/`erc20TokenAddresses` to real funds. The Min-path bypasses (b) entirely, and setting `signerAddress == address(0)` bypasses (a) entirely, leaving no authorization gate at all for the `ops` execution, while the balance-accounting mechanism that would otherwise catch unauthorized value movement is neutralized by supplying an empty `erc20TokenAddresses` array.

### Impact Explanation
Any funds/tokens/ETH held at the Emporium contract's own address (e.g., dust, in-flight/parked balances from concurrent transactions, unclaimed relay-fee remainders, or ETH sent via `receive()`) can be moved out by an attacker-crafted `op.endpoint.call` (e.g., calling an ERC20 token's `transfer(attacker, balance)`, or calling `sendToRelay`-style flows on tokens Emporium holds) with **zero economic accounting and zero signature authorization**. This is direct theft of funds sitting at a Hinkal protocol contract, executed via calls the wallet owner/prover never authorized, repeatable for any subsequent balance Emporium accumulates. This matches Critical — "direct theft of shielded or in-flight user funds" / High — "executing calls or moving assets... a prover never authorised," depending on what value happens to be parked in Emporium at attack time.

### Likelihood Explanation
Preconditions: attacker needs no special role — any EOA can call `Hinkal.transact` (`onlyAllowedRecipient` on `runAction` only checks the caller is `Hinkal`/an allowed recipient dispatched via `externalActionMap`, which is satisfied by normal `Hinkal.transact` routing, not attacker identity). The attacker must self-generate a trivial Min-circuit proof (no secret witness required beyond a self-chosen `messageSeed`), craft `EmporiumStack{signerAddress:0, ops:[...]}`, and set `erc20TokenAddresses = []`. This requires funding gas only and is fully repeatable each time Emporium accumulates a balance. Feasibility is high since generating the Min proof requires no interaction with any victim's secrets.

### Recommendation
- Require `stack.signerAddress != address(0)` (i.e., always enforce a valid signature) whenever the Min-circuit/unauthenticated proof path is used, or disallow the Min path entirely for actions that permit `invokeWallet == false` self-calls.
- Bound `stack.ops.length` to `erc20TokenAddresses.length` or otherwise ensure every token/ETH balance touched by `ops` is included in `erc20TokenAddresses` and thus subject to the `balancesBefore`/`balancesAfter` diff and slippage checks.
- In `verifyWallet`, never fully skip authorization: require either a valid signature or that all `ops` operate only on `erc20TokenAddresses` positions that are properly deltaAmountChange-accounted.
- Consider removing the Min-circuit fast path for Emporium arbitrary-call operations, since it provides no cryptographic binding to a real UTXO or authorized signer.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (via proxy), register Emporium under `HINKAL_EMPORIUM_ACTION_ID`.
2. Fund Emporium directly with an ERC20 token balance (simulate "parked" balance, e.g. via a prior legitimate transact leaving dust, or direct `token.transfer(emporiumAddr, X)`).
3. As attacker EOA (not owner, not relay), construct:
   - `circomData.erc20TokenAddresses = []`
   - `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`
   - `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet:false, value:0, callData: abi.encodeCall(token.transfer, (attacker, X))})], maxFee:0, deadline:0, v:0,r:0,s:0}))`
   - `circomData.calldataHash = getHashedCalldata(circomData)` (self-computed)
4. Generate a valid `MainEVMCircuitMin` proof locally for a self-chosen `messageSeed`, setting `emporiumMessage = Poseidon(messageSeed)`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker.
6. Assert:
   - LHS: `token.balanceOf(emporiumAddr)` before == X, after == 0.
   - RHS: `sum(balancesBefore) - sum(balancesAfter)` as computed inside `runAction`/`Hinkal.transact` == 0 (since `erc20TokenAddresses` empty), demonstrating the equality "assets moved == assets accounted" is violated.
   - `token.balanceOf(attacker)` increased by X with no corresponding nullifier spent (`insertNullifiers` called with empty/no-op nullifier set) and no signature validated.
