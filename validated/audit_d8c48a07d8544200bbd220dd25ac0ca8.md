## Analog Found

### Title
Floor-division decimal conversion in `pallet-hyper-fungible-token` truncates cross-chain deposits to zero, permanently burning user funds - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` scales an incoming ERC20 amount down to the local asset's decimals using pure integer division. Because `register_token`/`update_token` only enforce `erc_decimals >= local_decimals` (never bound the *gap* between them), any amount smaller than the scale factor `10^(erc_decimals - local_decimals)` is truncated to `0`, while the full original amount was already irreversibly burned/escrowed on the EVM side. This mirrors the reported USSD bug where WBTC's 8 decimals were not accounted for in `calculateMint()`, causing sub-threshold deposits to mint `0`.

### Finding Description
`convert_to_balance` performs:
```
let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
``` [1](#0-0) 

This is invoked in `on_accept` and `on_timeout` to convert the ERC20-denominated `message.amount` received from an EVM `send()`/timeout into the local balance that gets minted/transferred to the beneficiary: [2](#0-1) [3](#0-2) 

The only guard on the decimal gap is in `register_token`/`update_token`, which merely rejects `config.decimals < local_decimals` — it places no upper bound on how large the gap can be: [4](#0-3) [5](#0-4) 

The shipped `BridgeToken` config already demonstrates a real 6-decimal gap (EVM 18 decimals vs. nexus 12 decimals, scale factor `10^6`): [6](#0-5) 

On the send-out path (local → EVM), `convert_to_erc20` multiplies, so no precision is lost there — the vulnerability is one-directional, exactly like the original WBTC report where only the mint/deposit side truncated: [7](#0-6) 

Because the EVM `send()` flow escrows/burns the sender's full ERC20 amount before the request is even dispatched, any relayed amount whose value is less than `10^(erc_decimals-local_decimals)` wei is fully consumed on the source chain but converts to `0` locally in `on_accept`, so nothing is minted/transferred to the beneficiary — the funds are simply gone. The same floor-division truncation also silently drops any non-multiple remainder on every transfer (not just full zeroing), and `on_timeout` refunds are computed with the *same* lossy conversion, so a timed-out message also refunds less than what was escrowed.

### Impact Explanation
Any unprivileged user bridging tokens through `pallet-hyper-fungible-token`'s registered assets can lose part or the entirety of a legitimate deposit whenever the decimal gap between the EVM ERC20 and the local Substrate asset is nontrivial (which the code explicitly allows and which the shipped `BridgeToken` config already exercises at `10^6`). This is a direct, permanent loss of user funds with no compensating mint or refund mechanism — matching the "users receive significantly less or even 0" impact of the analog report. Since the gap is fully governance-configurable and unbounded, a future asset registration with a larger gap (e.g., a low-decimal local asset paired with an 18-decimal ERC20) would let ordinary user deposits be reduced to zero.

### Likelihood Explanation
High for any transfer amount not aligned to the scale factor (dust loss on virtually every cross-chain transfer through this pallet), and total-loss likelihood scales directly with how large a decimal gap governance configures for a given asset — which the code permits without bound. No privileged action is needed to trigger the loss; a normal user calling `send()` on the EVM `HyperFungibleToken`/`BridgeToken` contract and having the message relayed is sufficient.

### Recommendation
- In `convert_to_balance`/`convert_to_erc20`, round the ERC20 amount down to the nearest exact multiple of the scale factor *before* burning/escrowing on the sender side (or reject `send()` amounts that are not multiples of `10^(erc_decimals-local_decimals)`), so no value is destroyed.
- Alternatively, track and refund/accumulate the truncated remainder rather than silently discarding it.
- Consider bounding the maximum allowed decimal gap in `register_token`/`update_token`, or emitting a minimum-transferable-amount check on the EVM `send()` side so users cannot submit amounts that will truncate to zero.

### Proof of Concept
1. Governance registers asset `X` with `local_decimals = 12` and an EVM chain with `erc_decimals = 18` (as already done for `BRIDGE`), giving a scale factor of `10^6`.
2. A user calls `send()`/bridges `999_999` wei (i.e., `< 10^6`) of the ERC20 token from the EVM side to nexus. The EVM contract burns/escrows the full `999_999` wei.
3. The relayed message reaches `on_accept` in `modules/pallets/hyper-fungible-token/src/module.rs`, which computes `amount = convert_to_balance(999_999, 18, 12)` → `999_999 / 10^6 = 0`.
4. `0` is minted/transferred to the beneficiary — the user's `999_999` wei is permanently lost with no refund path, reproducing the "receive 0" outcome from the original WBTC report.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```

///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
