This confirms the vulnerability chain. On the substrate side, `Message::from` is `who` (`ensure_signed(origin)`), authenticated by the substrate sender. But on the EVM side, the equivalent `HyperFungibleToken.sol` (Solidity) sends `Message.from` as part of `abi.encode`d body over `IDispatcher.dispatch`, and the `from` field is attacker-supplied ABI-decoded data, not necessarily `msg.sender` — the pallet's `on_accept` handler in `modules/pallets/hyper-fungible-token/src/module.rs` trusts `message.from` completely as the dispatch origin whenever `SubstrateCalldata.signature` is `None`.

### Title
Unsigned cross-chain calldata lets an attacker dispatch arbitrary RuntimeCalls as any account - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` decodes an untrusted SCALE-encoded blob (`SubstrateCalldata`, itself embedded in an ABI-encoded `Message.data` field originating from an EVM contract) and, when `substrate_data.signature` is `None`, derives the dispatch `origin` directly from the untrusted `message.from` field instead of from any relayer-agnostic, cryptographically-verified identity. It then instantiates and dispatches an arbitrary `T::RuntimeCall` under that derived `Signed` origin. This mirrors the DotCi-class bug: attacker-controlled bytes are deserialized into a live, executable object (here, a `RuntimeCall`) and immediately invoked with the authority implied by attacker-chosen metadata, rather than a value cryptographically bound to the caller.

### Finding Description
`on_accept` in [1](#0-0)  decodes `message.data` into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` via `SubstrateCalldata::decode`. When `signature` is `Some`, the code verifies it against `(nonce, runtime_call)` and the `beneficiary` computed from the token-transfer recipient — that path is sound. But when `signature` is `None`, the code takes:
```
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else {
    ... account.into()
}
```
as the dispatch `origin`, then decodes `substrate_data.runtime_call` into a live `T::RuntimeCall` and dispatches it as `RawOrigin::Signed(origin)` ( [2](#0-1) ).

`message.from` is a field of the ABI-encoded `Message` struct sent from the EVM side ( [3](#0-2) ). On the mirrored substrate `send()` extrinsic, `from` is hard-set to `who` (the caller) ( [4](#0-3) ), but the EVM-side `HyperFungibleToken.sol`/`WrappedHyperFungibleToken.sol` contracts populate `Message.from`/`data` from caller-supplied parameters of their own `send`-style function; nothing in the ISMP `PostRequest` on-chain proves that `from` is the actual initiator rather than an arbitrary address chosen by whoever calls the EVM contract's send function. Because the ISMP module only authenticates the *source contract* (`ContractToAsset::<T>::get(source, &from)` in the caller lookup is keyed on the token contract, not `message.from`) — see [5](#0-4)  — any account that can call the registered token contract's cross-chain send function can set `Message.from` to an arbitrary 20-byte value and attach `data` containing a `SubstrateCalldata` with `signature = None` and any `runtime_call` bytes.

The result: an unprivileged EVM-side caller decodes/dispatches an arbitrary `RuntimeCall` (bounded only by `BaseCallFilter`) under the `Signed` origin of a victim address of their choosing, without ever proving control of that address's private key. This is the direct analog of "deserializing untrusted input into a live, privileged object and instantiating/executing it" — the DotCi CVE's core defect — except here the "arbitrary type instantiation" is a `RuntimeCall` variant chosen by the attacker and the "code execution" is its `Dispatchable::dispatch`.

### Impact Explanation
This allows theft of funds and unauthorized app actions: an attacker can impersonate any substrate account reachable via `EvmToSubstrate::convert` (i.e., any address derivable from a 20-byte EVM address they choose) and dispatch any `RuntimeCall` not blocked by `BaseCallFilter` — e.g., `Balances::transfer`, `Assets::transfer`, or any other pallet call — draining that account's substrate-side funds or performing unauthorized privileged actions, as long as the call passes the base filter. This directly satisfies the "concrete theft of funds / unauthorized app action" bar.

### Likelihood Explanation
High: reaching this path requires only sending a normal cross-chain HFT transfer with a crafted `data` payload from the EVM side — no special permissions, no relayer collusion, no consensus manipulation. Any address able to call the registered EVM token contract's send-equivalent function (which is meant to be permissionless, matching pallet's own permissionless `send` extrinsic) can trigger it.

### Recommendation
Never derive a dispatch origin from unauthenticated cross-chain payload fields. Require a valid `MultiSignature` over `(nonce, runtime_call)` unconditionally (remove the `signature: None` fallback path), or bind the no-signature dispatch origin exclusively to the token-transfer beneficiary that was already cryptographically fixed by the mint/transfer step (`beneficiary` computed from `message.to`), never from `message.from`. If self-dispatch-as-sender is a required feature, `from` must be authenticated the same way `to` currently is (fixed-length decode plus provenance from a value the source-chain contract cannot spoof, e.g. actual `msg.sender` captured at dispatch time by the sending contract and separately committed).

### Proof of Concept
1. Register a `HyperFungibleToken` contract/asset pair between an EVM chain and the substrate chain per [6](#0-5) .
2. From the EVM contract, call the cross-chain send function specifying: `to` = attacker's own beneficiary (any address, receives the minted tokens), and `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <encoded Balances::transfer_all(victim_account_derived_bytes) or any privileged call> }`, while setting the ABI `Message.from` field to the victim's 20-byte address of choice.
3. On the destination substrate chain, `on_accept` in [7](#0-6)  decodes `message.data`, finds `signature == None`, derives `origin = EvmToSubstrate::convert(H160::from(message.from))` = the victim's mapped substrate account, and dispatches the attacker-supplied `runtime_call` as `RawOrigin::Signed(victim_account)`.
4. The victim's substrate account executes an arbitrary call (e.g., transferring away its balance) without ever authorizing it, because no signature bound to that account was checked.
