## Title
Webhook HMAC Validation Does Not Bind the `shop-domain` Header, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` header to identify which merchant/tenant the payload belongs to. Because the HMAC signable string never includes the shop domain, the cryptographic check proves only that *some* payload was signed with the app's shared `client_secret` — it proves nothing about *which shop* the payload is for. Any party who can obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the library will treat the payload as authentic data for the victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is not part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC exclusively against `verifiable_query.to_signable_string` (i.e., the body): [3](#0-2) 

`Webhooks::Registry.process` performs this body-only HMAC check, and then — having established only "this body was signed by the app's shared secret" — hands `request.shop` straight to the handler as the tenant identity, with no independent verification that the shop header matches whichever shop actually generated the signature: [4](#0-3) 

The identity-binding equality that should hold is: `shop asserted in header == shop that produced the HMAC`. Since the `api_secret_key` used for HMAC computation is shared across *all* shops of a given app (it is not a per-shop secret), and the shop domain is never part of the signed bytes, this equality is never actually checked — the HMAC binds "app," not "shop." Any attacker who legitimately installs the target app on their own store (a normal, unprivileged, self-service action requiring no special access to the victim or to the app's `client_secret`) will receive real webhooks with valid `(body, hmac)` pairs. They can then send an HTTP POST directly to the app's public webhook endpoint with that same body/HMAC and a forged `shop-domain` header naming the victim shop. `HmacValidator.validate` passes, and `Registry.process` invokes the app's handler with `WebhookMetadata` claiming the payload is for the victim shop.

### Impact Explanation
This breaks tenant isolation (cross-tenant access), one of the explicitly in-scope Critical impacts. Any app whose webhook handlers use `data.shop` to select which merchant's records to create/update/delete (a standard and expected usage pattern per this gem's own `WebhookMetadata`) can be made to apply attacker-supplied payload content to another merchant's data, or to poison per-shop caches/state keyed by `shop`.

### Likelihood Explanation
Exploitation requires no leaked credentials, no access token, and no privileged account beyond the trivially obtainable step of installing the target app on an attacker-controlled store to harvest one valid `(body, hmac)` sample — a normal, self-service, unprivileged action. The webhook HTTP endpoint is by design a public, unauthenticated endpoint (Shopify's webhook delivery model has no other transport-level auth), so replaying a captured request with a modified header is straightforward for any internet user who can reach that endpoint.

### Recommendation
Bind the shop identity into what is cryptographically verified: reject (or re-derive) the tenant identity independent of the client-supplied `shop-domain` header — e.g., resolve the shop via a lookup keyed by webhook subscription/target that was established at registration time, or require the caller to separately validate that `request.shop` corresponds to a shop with an active, previously-established session before trusting it, rather than passing the raw header value straight through to handlers as ground truth.

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com`, receiving a real webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(app_secret, B)`).
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint with the same body `B`, the same header `x-shopify-hmac-sha256: H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` recomputes `HMAC(app_secret, B)` and compares it to `H` via `OpenSSL.secure_compare` — it matches because the domain was never part of the signed content [5](#0-4) .
4. `Registry.process` proceeds and invokes the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the app to process attacker-controlled data as if it belongs to the victim tenant.
