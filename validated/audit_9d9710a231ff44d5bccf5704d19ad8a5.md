### Title
Webhook `shop` domain is trusted as tenant identity but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then hands the request's `topic`, `shop`, `webhook_id`, and `api_version` — all taken from unauthenticated HTTP headers — to the app's handler as an implicitly trusted `WebhookMetadata` struct. The `shop` field, which the gem's own documentation describes as "The shop domain of the webhook," is never included in the signed material and is never cross-checked against the shop that actually owns the `webhook_id`/topic, breaking the equality: `shop reported in WebhookMetadata == shop that produced/authorized this signed body`.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` show that only the raw JSON body is part of the signable content: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC over the body and then immediately trusts `request.shop` as the tenant identity, forwarding it unchanged into `WebhookMetadata`: [3](#0-2) 

`WebhookMetadata` is a plain struct with a `shop: String` field that carries no provenance/verification marker — it's structurally indistinguishable from a validated value: [4](#0-3) 

The library's own documentation instructs developers to treat `data.shop` as an authoritative field describing "The shop domain of the webhook," on par with `topic` and `body` (which *are* implicitly protected because they are inside the signed raw body), without any warning that `shop` is an unauthenticated header value: [5](#0-4) 

Because Shopify webhook HMACs are computed with the app's single `client_secret`, which is shared across every shop that installs the app, any legitimate installer of the app — an unprivileged internet user in the sense of not being a privileged operator of the target tenant — receives real, validly-signed webhook deliveries for their own shop. Since the header set (`shop-domain`, `topic`, `webhook-id`, etc.) is not part of the signed content, that same body+HMAC pair remains valid if replayed to the app's webhook endpoint with a different `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `Registry.process` will accept it (HMAC check passes because it only checks the body) and hand the handler a `WebhookMetadata` claiming an arbitrary attacker-chosen `shop`, `webhook_id`, and `topic` alongside a real, HMAC-valid `body`.

### Impact Explanation
This crosses a tenant boundary: a webhook payload legitimately generated for shop A can be relabeled and delivered as if it originated from shop B, with the gem providing no built-in defense (no binding of `shop` into the signature, no cross-check that `webhook_id` belongs to `shop`). If a host app follows the documented API and keys any per-tenant logic (data writes, cache invalidation, job enqueueing "for shop X" as shown in the gem's own example `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) off `data.shop`, this enables cross-tenant data confusion/injection using only a legitimately-obtained webhook of the attacker's own shop. This matches the "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is elevated because: (1) any developer/merchant who installs the target app can trivially obtain a valid signed webhook body+HMAC for their own shop; (2) the header value is fully attacker-controlled at replay time (no header signing, no TLS-client-cert binding referenced in this gem); (3) the documented usage pattern (`docs/usage/webhooks.md`) directly encourages using `data.shop` as if it were a verified value, making misuse in dependent apps likely rather than a mere theoretical misconfiguration.

### Recommendation
Bind the `shop` (and ideally `webhook_id`/`topic`) into the material verified by `HmacValidator`, or have `Registry.process` independently verify that the reported `shop` actually corresponds to a webhook registration/`webhook_id` known to belong to that shop, before constructing `WebhookMetadata`. At minimum, the documentation and the `WebhookMetadata` type should make explicit that `shop` is unauthenticated header data and must not be trusted as a tenant key without additional verification (e.g., matching against the app's known installed-shop list).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and legitimately receives a real webhook delivery, e.g. `orders/create`, with a valid `x-shopify-hmac-sha256` header computed over the raw body using the app's shared `client_secret`.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value (the HMAC is over body only, per `ShopifyAPI::Webhooks::Request#to_signable_string` [6](#0-5) ).
3. Attacker replays the identical raw body and HMAC to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a `webhook-id` copied from a real victim webhook if known/guessable).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only recomputes the HMAC over `@raw_body` [7](#0-6) .
5. The handler executes with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload's content actually originated from the attacker's shop, demonstrating the identity binding break.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
