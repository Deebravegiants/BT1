### Title
Webhook `shop` (and `topic`/`webhook-id`) header is trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates solely the JSON body against the app's static `api_secret_key`. The `shop`, `topic`, and `webhook_id` values that `Webhooks::Registry.process` hands to the merchant's handler are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) and are never part of the signed payload.

### Finding Description
`Request#hmac` reads the `hmac-sha256` header, `Request#to_signable_string` returns just `@raw_body` [4](#0-3) . `HmacValidator.validate_signature` recomputes the signature over `to_signable_string` and compares it to the header value using the app's `api_secret_key` [5](#0-4) . Because `api_secret_key` is the same static app secret for every shop that installs the app (not shop-specific), any unprivileged party who can install the app on a shop they control receives real webhooks with a raw body + valid HMAC signed under that shared secret. That party can then send an arbitrary HTTP POST directly to the host application's webhook endpoint, replaying that same `(raw_body, hmac)` pair but substituting the `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header with a victim shop's domain. `Registry.process` validates only the HMAC of the body, then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight from the unauthenticated headers and dispatches it to the app's handler [2](#0-1) . The identity binding broken is: `shop attested by HMAC == shop acted on by handler`; here the HMAC only attests to the body, while the handler trusts the header's shop unconditionally.

### Impact Explanation
This lets an attacker who legitimately controls one shop's installation impersonate any other shop when delivering webhook payloads to the app's endpoint, since the header value used to select/attribute tenant data (`shop`) is never bound to the signed body. This is a cross-tenant identity spoofing vector at the gem/library level: the gem's own webhook verification API returns "valid" for a body/shop combination the app never actually received from Shopify for that shop, and any app that trusts the gem's validation + `request.shop`/`WebhookMetadata#shop` value (which the docs instruct apps to use) to route/attribute webhook data by tenant is misled into cross-tenant processing.

### Likelihood Explanation
Requires only that the attacker can install the app on any shop (even a free/dev store) to obtain a validly-HMAC'd raw body, then send a direct HTTP request to the app's public webhook endpoint with a modified shop header — no access to the app's `client_secret`, no privileged account, and no other credential is needed beyond ordinary "install this app on my own shop" access.

### Recommendation
Do not trust `Request#shop`/`topic`/`webhook_id` from headers alone; include the header values that downstream code will act on (particularly `shop-domain`) as part of the signed string, or independently verify that the request originated for the shop referenced by validating it against an active, known session/webhook registration for that specific shop before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`, triggering any registered webhook topic; Shopify delivers `raw_body` with header `X-Shopify-Hmac-Sha256: H` computed as `HMAC-SHA256(api_secret_key, raw_body)` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs the same `raw_body` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id` if the app's chosen topic exists for the victim too).
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against `H` [6](#0-5) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using the attacker-controlled `victim.myshopify.com` header value and passed to the app's handler, which processes/persists it as data belonging to the victim's tenant [7](#0-6) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
