## Title
Webhook HMAC signature does not cover the `shop-domain` header, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the HMAC-signed material. `Utils::HmacValidator.validate` only proves that the body bytes were signed with the app's `api_secret_key`; it proves nothing about which shop that signature belongs to. Any party who can obtain one validly-signed webhook body for a shop where the app is installed (e.g., a merchant who installs the app on their own store and triggers a webhook) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and `Registry.process` will accept it and hand the attacker-chosen `shop` to the handler as if it were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request` builds its signable string from the raw body only: [1](#0-0) 

The `shop` accessor pulls from an unsigned header: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (body only) and, if it passes, immediately trusts `request.shop` to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` was signed with `Context.api_secret_key`; because the shop domain is outside that signed string, the equality the code implicitly relies on — "the shop that signed this payload" == "the shop named in the `shop-domain` header" — is never actually checked. [4](#0-3) 

Since the app's `api_secret_key` is shared across every shop that installs the app, a legitimate-but-malicious merchant can install the app on their own shop, trigger a real webhook to capture a validly-signed `(raw_body, hmac)` pair, then resend that exact body and HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. The signature still validates (it only checks the body bytes), so `Registry.process` calls the handler with `shop` = victim shop but `body` = attacker-controlled content.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to look up the corresponding merchant/session and then acts on `WebhookMetadata#body` (a common pattern — e.g., updating order/product state, provisioning, billing state), an attacker can inject forged data attributed to a victim shop without ever compromising that shop's credentials. This is a cross-tenant data-integrity break rooted entirely in this gem's webhook verification code, since the binding between "cryptographically verified payload" and "claimed shop" is never enforced by the library.

### Likelihood Explanation
Any actor who can install the target app on a shop they control (a normal, unprivileged onboarding action for most public/embedded Shopify apps) can capture a genuinely signed webhook and replay it with a different `shop-domain` header. No access token, `client_secret`, or privileged access is required — only a normal app install and the ability to send an HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the shop domain to the signature verification, e.g., include the `shop-domain` (and ideally `topic`) header values in `to_signable_string`, or separately verify that the shop present in the request matches an expected/registered shop before invoking the handler, so `HmacValidator.validate` actually authenticates the (shop, body) pair rather than the body alone.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) to capture the real request: raw body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's shared `api_secret_key`).
2. POST to the app's webhook endpoint with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (changed)
   - body `B` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and finds it matches `H`, so validation passes.
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, letting the attacker inject data attributed to a shop they don't control.
