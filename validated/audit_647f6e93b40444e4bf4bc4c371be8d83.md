### Title
Emporium `runAction` only accounts for tokens listed in `circomData.erc20TokenAddresses`, allowing any `stack.ops` call to silently drain any other ERC20 held by the Emporium contract - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` snapshots balances only for the attacker-supplied `circomData.erc20TokenAddresses` array and lets `stack.ops` make fully arbitrary external calls (`op.endpoint.call{value: op.value}(op.callData)`) with no restriction tying the call target to that array. An attacker can submit `erc20TokenAddresses=[tokenA]` (any short, non-empty array so the normal, non-Min circuit path is used) with a zero-amount valid proof for `tokenA`, while embedding an unrelated op that calls `tokenB.transfer(attacker, balance)` directly from the Emporium contract, draining any `tokenB` balance the contract holds without ever being checked.

### Finding Description
The equality that is supposed to hold is: **every token balance change caused by the ops in a transaction must be captured by the before/after accounting loop**, i.e. `balancesAfter[i] - balancesBefore[i]` for all tokens touched by `stack.ops` must equal what is reflected in `deltaAmountChanges`/`amountChanges`/UTXO outputs. Instead, `runAction` only computes: [1](#0-0) 
and later [2](#0-1) 
for `circomData.erc20TokenAddresses` alone - an array whose contents, length and ordering are fully chosen by the caller who also builds the entire `CircomData`/`Dimensions`/proof. Meanwhile the ops loop: [3](#0-2) 
executes `op.endpoint.call{value: op.value}(op.callData)` for any `op.endpoint`/`op.callData` in the stateless (Case 2) branch, with the only restriction being that the call's selector must not be `callHinkalWallet`/`doSendToRelay`. There is no check anywhere (`verifyWallet`, `dimensionsCheck`, `checkOnchainCreation`, `distinctErc20AddressChecks` in the circuit, or the outer `Hinkal.transact` balance loop) that constrains `op.endpoint` to be one of the declared `erc20TokenAddresses`, nor that the circuit or `calldataHash` binds ops to only move declared tokens - `calldataHash`/the EIP-712 signature only prove the ops weren't tampered with by a relay, not that they are limited to a token set.

Note also that the outer check in `Hinkal.sol::transact` reads balances of `address(this)` (the `Hinkal` contract), not the `Emporium` contract, so it cannot catch a balance change happening inside `Emporium`: [4](#0-3) 

Attacker's exact call: submit `transact(a,b,c,dimensions,circomData)` where `circomData.erc20TokenAddresses = [tokenA]`, `circomData.amountChanges = [0]`, a valid non-Min `MainEVMCircuit` proof for that trivial statement (zero in/out amounts, `inTotal + amountChanges === outTotal` trivially satisfied), `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: tokenB, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, tokenB.balanceOf(emporium)))}]`.

Exploit flow: `Hinkal.transact` → `_externalTransact` → `EmporiumUpgradeable.runAction`. `balancesBefore`/`balancesAfter` are computed only for `tokenA` (both 0, unaffected). The op executes `tokenB.transfer(attacker, allBalance)` directly from `Emporium`'s own storage (msg.sender = Emporium), succeeding and draining `tokenB`. `balanceChange` for `tokenA` is 0, `handleOut` does nothing, no revert occurs anywhere in the function.

### Impact Explanation
Any ERC20 balance sitting in the shared `Emporium` contract that is not explicitly declared by the caller's own `erc20TokenAddresses` array can be stolen outright by any unprivileged party, with a trivial (even zero-value) proof for an unrelated token. Since `Emporium` is a shared, multi-user contract used for swaps/DeFi interactions via `stack.ops`, realistic non-"user-mistake" sources of such balances include: DEX-swap rounding dust, unswept bonus/reward/referral tokens paid out by an invoked protocol as a side effect of an op, or third-party token distributions to the Emporium's address. This is direct theft of value custodied by the protocol/other users, matching the **Critical** bar (theft of shielded/in-flight user funds via an action that was never counted). It is fully repeatable for every token the Emporium accumulates and costs the attacker only gas plus a cheap circuit proof for a trivial zero-value statement.

### Likelihood Explanation
Preconditions: the attacker needs (1) ability to submit `transact` with a self-chosen `erc20TokenAddresses` array and matching valid proof (fully in attacker's control since they are an unprivileged prover of their own UTXOs/zero-value statement), and (2) the `Emporium` contract holding a non-zero balance of some `tokenB` not listed in their array. Because `Emporium` is architected as a shared, general-purpose intermediary for arbitrary DeFi calls (`stack.ops`), residual balances of tokens outside the declared set are a natural byproduct of normal usage (swap dust, reward tokens, etc.), making this feasible without relying on anyone's mistake. Attacker cost is minimal (one cheap circuit proof + one transaction), and the attack is repeatable against every stray token balance that accumulates over time.

### Recommendation
Constrain `EmporiumOperation.endpoint`/`callData` so that any token movement is provably confined to `circomData.erc20TokenAddresses`, e.g. by maintaining a per-transaction whitelist of allowed call targets derived from the declared token set (and their known router/adapter contracts), or by tracking the full token surface touched by each op (via return-data/selector inspection or a post-op enumeration of balance changes across a protocol-maintained token registry) and requiring that any token whose balance changed be included in the accounted array with matching UTXO/slippage bookkeeping. At minimum, forbid `op.endpoint` from being any address whose `balanceOf` changes are not reconciled by the existing before/after loop.

### Proof of Concept
Foundry test outline:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, mock `tokenA` and `tokenB` (both standard ERC20).
2. Seed `Emporium` with a `tokenB` balance (e.g. `tokenB.mint(emporium, 1000e18)`) to simulate residual/reward dust from prior legitimate DeFi usage - do not use a user-mistake transfer path, use e.g. a mock reward-paying router invoked in a prior legitimate transaction to make provenance realistic.
3. Attacker builds `CircomData` with `erc20TokenAddresses = [address(tokenA)]`, `amountChanges = [0]`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(tokenB), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, tokenB.balanceOf(emporium)))}]}`.
4. Generate a valid `MainEVMCircuit` proof locally for `tokenCount=1` with all-zero in/out amounts (formInputNormal path, since `erc20TokenAddresses.length == 1 != 0`).
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker EOA.
6. Assert: `tokenB.balanceOf(emporium) == 0` and `tokenB.balanceOf(attacker) == 1000e18` after the call, while the transaction succeeds without reverting on any `balanceDif`/`slippage`/`BalanceChangeShouldBePositive` check.
7. Assert on both sides of the broken equality: `balancesBefore/After` arrays inside `EmporiumUpgradeable.runAction` never reference `tokenB` (only length-1 arrays for `tokenA`), proving the value leaving the contract was never reconciled against any `deltaAmountChanges`/`amountChanges` entry.
