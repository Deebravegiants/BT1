### Title
Cross-chain governance can set an unbounded `challengePeriod`/`unbonding_period`, permanently freezing message delivery for a route - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost` validates `unStakingPeriod` on parameter updates but never bounds `challengePeriod`, and the equivalent Substrate path (`pallet_ismp::update_consensus_state` / `create_consensus_client`) never bounds `challenge_period` or `unbonding_period` either. Because `challenge_period` gates every incoming request/response/timeout, an unbounded update can push a route into a state where messages can never be delivered again, mirroring the `WITHDRAWAL_REQUEST_TIMEOUT` bug class in the external report (a risky, admin-settable timing parameter with no sanity bound that can brick protocol operation).

### Finding Description
`HostParams.challengePeriod` (EVM) and the per-`StateMachineId` `ChallengePeriod` storage (Substrate `pallet-ismp`) are used by `verify_delay_passed` to decide whether a state commitment may be used to verify incoming requests/responses/timeouts: [1](#0-0) 

`validate_state_machine`, called on every incoming request/response/timeout message, rejects the message with `ChallengePeriodNotElapsed` until the challenge period has passed: [2](#0-1) 

On the EVM side, `challengePeriod` is set through `updateHostParams`, reachable via cross-chain governance (`HostManager.onAccept` → `IHostManager.updateHostParams`). The validation performed on the incoming `HostParams` only bounds `unStakingPeriod` (must be ≥ 1 day) and a handful of address/array invariants — `challengePeriod` itself is copied into storage with no minimum or maximum check: [3](#0-2) [4](#0-3) 

`HostManager.onAccept` performs the `SetHostParam` action for any `HostParams` payload decoded from the governance request body without further sanity checks: [5](#0-4) 

The Substrate analog is identical: `update_consensus_state` (and `create_consensus_client`) let `T::AdminOrigin` set arbitrary `challenge_periods`/`unbonding_period` values with no bound checks before calling `store_challenge_period` / `store_unbonding_period`: [6](#0-5) 

If `challengePeriod`/`challenge_period` is (accidentally or via a faulty governance proposal) set to an extremely large value, `verify_delay_passed` can never return `true` for that state machine, so `validate_state_machine` will permanently reject every request, response, and timeout message routed through that consensus state — including the very `HostManager`/`update_consensus_state` governance messages needed to correct the parameter, since those governance requests are themselves delivered as ordinary ISMP `PostRequest`s subject to the same challenge-period gate. This can leave the route with no recovery path short of deploying a new consensus client/host, exactly analogous to the reported `WITHDRAWAL_REQUEST_TIMEOUT`/`exodusMode` failure mode.

### Impact Explanation
Impact is High: an unbounded challenge/unbonding period freezes message delivery for the affected route entirely — no `PostRequest`, `GetResponse`, or timeout can be processed once the challenge period exceeds any practically reachable elapsed time, and because governance itself is delivered as an ISMP message subject to the same gate, self-correction can be blocked, requiring a new consensus client or facet/contract deployment to recover (matching the "route unable to deliver messages" acceptance criterion).

### Likelihood Explanation
Likelihood is Low, consistent with the original report: this requires a governance/admin misconfiguration (extreme value) rather than an attacker-controlled unprivileged path, and `unStakingPeriod` already has protective bounds showing the team is aware of this risk class but omitted the same protection for `challengePeriod`/`unbonding_period`.

### Recommendation
Add explicit minimum and maximum bounds validation for `challengePeriod` in `EvmHost.updateHostParams` (mirroring the existing `InvalidUnstakingPeriod` check) and for `challenge_period`/`unbonding_period` in `pallet_ismp::create_consensus_client` / `update_consensus_state`, rejecting values that would make `verify_delay_passed`/`is_expired` unsatisfiable within a reasonable timeframe. Consider also allowing governance-originated messages to bypass the target route's own challenge-period gate so a misconfiguration can always be corrected.

### Proof of Concept
1. Governance (via `HostManager.onAccept` → `SetHostParam`, or `pallet_ismp::update_consensus_state`) submits a `HostParams`/`UpdateConsensusState` update setting `challengePeriod`/`challenge_period` to an extremely large value (e.g., `type(uint256).max` or a value far exceeding any realistic host uptime).
2. `EvmHost.updateHostParams` (evm/src/core/EvmHost.sol:601-645) or `store_challenge_period` (modules/pallets/ismp/src/lib.rs:429-434) accepts the value with no bound check.
3. Any relayer subsequently submits a `PostRequest`/`GetResponse`/timeout message for that state machine; `verify_delay_passed` (modules/ismp/core/src/handlers.rs:104-114) always returns `false`, so `validate_state_machine` (modules/ismp/core/src/handlers.rs:121-148) always errors with `ChallengePeriodNotElapsed`.
4. Because the corrective governance message must itself traverse the same `validate_state_machine` check, the route becomes permanently unable to deliver any message, including the fix.

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}

pub fn validate_state_machine<H>(
	host: &H,
	proof_height: StateMachineHeight,
) -> Result<Box<dyn StateMachineClient>, Error>
where
	H: IsmpHost,
{
	// Ensure consensus client is not frozen
	let consensus_client_id = host.consensus_client_id(proof_height.id.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized {
			consensus_state_id: proof_height.id.consensus_state_id,
		},
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	// Ensure client is not frozen
	host.is_consensus_client_frozen(proof_height.id.consensus_state_id)?;

	// Ensure delay period has elapsed
	if !verify_delay_passed(host, &proof_height)? {
		return Err(Error::ChallengePeriodNotElapsed {
			state_machine_id: proof_height.id,
			current_time: host.timestamp(),
			update_time: host.state_machine_update_time(proof_height)?,
		});
	}

	consensus_client.state_machine(proof_height.id.state_id)
}

    function onAccept(IncomingPostRequest calldata incoming)
        external
        override
        restrict(msg.sender, _params.host)
        restrict(incoming.relayer, _params.admin)
    {
        PostRequest calldata request = incoming.request;
        // Only the Hyperbridge parachain can send requests to this module.
        if (!request.source.equals(IHost(_params.host).hyperbridge())) revert UnauthorizedAction();

        OnAcceptActions action = OnAcceptActions(uint8(request.body[0]));
        if (action == OnAcceptActions.Withdraw) {
            // This is where governance & relayers can withdraw their revenue.
            WithdrawParams memory withdrawParams = abi.decode(request.body[1:], (WithdrawParams));
            IHostManager(_params.host).withdraw(withdrawParams);
        } else if (action == OnAcceptActions.SetHostParam) {
            HostParams memory hostParams = abi.decode(request.body[1:], (HostParams));
            IHostManager(_params.host).updateHostParams(hostParams);
        } else if (action == OnAcceptActions.SetAdmin) {
            // Rotates the governance relayer.
            address newAdmin = abi.decode(request.body[1:], (address));
            if (newAdmin == address(0)) revert InvalidAdmin();
            emit AdminUpdated({previous: _params.admin, current: newAdmin});
            _params.admin = newAdmin;
        }
    }

		/// Modify the unbonding period and challenge period for a consensus state.
		/// The dispatch origin for this call must be `T::AdminOrigin`.
		///
		/// - `message`: `UpdateConsensusState` struct.
		#[pallet::weight(<T as frame_system::Config>::DbWeight::get().writes(2))]
		#[pallet::call_index(3)]
		pub fn update_consensus_state(
			origin: OriginFor<T>,
			message: UpdateConsensusState,
		) -> DispatchResult {
			T::AdminOrigin::ensure_origin(origin)?;

			let host = Pallet::<T>::default();

			if let Some(unbonding_period) = message.unbonding_period {
				host.store_unbonding_period(message.consensus_state_id, unbonding_period)
					.map_err(|_| Error::<T>::UnbondingPeriodUpdateFailed)?;
			}

			for (state_id, period) in message.challenge_periods {
				let id =
					StateMachineId { state_id, consensus_state_id: message.consensus_state_id };
				host.store_challenge_period(id, period)
					.map_err(|_| Error::<T>::UnbondingPeriodUpdateFailed)?;
			}

			Ok(())
		}
