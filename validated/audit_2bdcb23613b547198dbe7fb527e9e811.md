### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, but exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain, unauthenticated HTTP header reads. `Registry.process` trusts these header-derived values (in particular `shop`) once the body-only HMAC check passes, breaking the binding `shop_authenticated == shop_used_by_handler`.

### Finding Description
`HmacValidator.validate` verifies a webhook request by calling `to_signable_string`, which for `Webhooks::Request` returns only `@raw_body`: [3](#0-2) 

Meanwhile, `shop` (and other routing metadata) is read directly from headers with no cryptographic binding to the signature: [2](#0-1) [4](#0-3) 

`Registry.process` validates the HMAC and, on success, immediately forwards `request.shop` (the unauthenticated header value) into the handler as the tenant identity: [1](#0-0) 

Because the shop domain is never part of the signed bytes, `hmac == HMAC(secret, raw_body)` remains valid regardless of what `shop-domain` header value is sent. An attacker who can obtain a single legitimate `(raw_body, hmac)` pair signed with the app's `client_secret` — for example, by installing the app on their own shop and receiving one real webhook delivery — can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` (or `x-shopify-shop-domain`) header. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` claiming to be from the victim shop, with attacker-chosen `topic`/`body` content already fixed by the replayed payload.

This breaks the equality that should hold: `shop_bound_by_hmac == shop_acted_on_by_handler`. Instead, `shop_acted_on_by_handler` is fully attacker-controlled while only the body bytes are authenticated.

### Impact Explanation
This enables cross-tenant confusion inside apps built on this gem: any handler that keys persistence, authorization, or session lookups off `WebhookMetadata#shop` (the documented/intended use, per `docs/usage/webhooks.md`) can be made to act on behalf of, or write data associated with, a shop the attacker does not control. Depending on the handler, this can lead to cross-tenant data corruption or disclosure — meeting the "cross-tenant access" bar for Critical/High severity in this class of bug, since the root cause is inside the gem's own HMAC-binding logic, not host misuse of an undocumented API.

### Likelihood Explanation
The attacker only needs one prior legitimate webhook delivery signed with the app's secret (trivially obtainable by installing the app on any shop they control and triggering any registered webhook topic) and the ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) inside `to_signable_string`, matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed payload: [5](#0-4) 
Alternatively/additionally, verify the HMAC using Shopify's actual signing scheme (which signs the raw body) but treat `shop-domain` strictly as informational unless independently cross-checked against a known/allow-listed shop identity for the topic, rejecting any request whose shop cannot be corroborated.

### Proof of Concept
```ruby
# Attacker first triggers/receives one real webhook for their own installed shop "attacker-shop.myshopify.com"
# capturing raw_body = '{"id":1}', hmac_header = "<valid base64 hmac for that body>"

# Attacker replays the identical body/hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",       # unchanged from captured request
  "x-shopify-hmac-sha256" => hmac_header,      # unchanged, still valid because body is unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":1}', headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds because it only checks raw_body against the HMAC.
# The registered handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
# even though the request was never sent by Shopify on behalf of that shop.
```
