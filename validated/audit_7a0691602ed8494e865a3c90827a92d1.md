This confirms the inconsistency: `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all call `Utils::ShopValidator.sanitize!(shop)` before using `shop` to build a session/request, but `Oauth.begin_auth` does not — it passes `shop` straight into `auth_base_uri(shop)`, which does raw string interpolation (`"https://#{shop}/admin"`) with no validation that `shop` is a trusted Shopify domain.

### Title
Unsanitized `shop` in `Oauth.begin_auth` allows authorize-URL host/redirect_uri injection - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorize URL by concatenating the caller-supplied `shop` string directly (`auth_base_uri(shop) + "/oauth/authorize?#{query_string}"`), with no call to `Utils::ShopValidator.sanitize!`. Every sibling credential-flow method (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) validates `shop` via `sanitize!` before using it, making `begin_auth` the outlier.

### Finding Description
The broken binding: `shop` used to construct `auth_route` is assumed to equal a validated, trusted Shopify domain (as in every other credential flow), but in `begin_auth` (lib/shopify_api/auth/oauth.rb:22-52), `shop == Utils::ShopValidator.sanitize!(shop)` never holds because `sanitize!` is never invoked. [1](#0-0) 

builds `query` (containing the real `client_id`, `scope`, real `redirect_uri`, and the freshly generated CSRF `state` nonce) and then does: [2](#0-1) 

`auth_base_uri` performs `"https://#{shop}/admin"` with no URI-encoding, no host-format check, and no call to `Utils::ShopValidator.sanitize!` (compare to [3](#0-2) , [4](#0-3) , and [5](#0-4) , each of which sanitizes before use). If `shop` contains `/`, `?`, `#`, or an arbitrary host (e.g. `attacker.com` or `attacker.com/x?redirect_uri=...`), the resulting `auth_route` string's host, path, and/or query composition changes: an attacker-chosen host makes the entire authorize URL point at a non-Shopify server, and injected `?`/`&` characters can add duplicate/extra query keys (e.g. a second `redirect_uri`) ahead of or alongside the legitimate ones.

`validate_auth_callback` (lib/shopify_api/auth/oauth.rb:60-113) later checks `state == auth_query.state` and calls `Utils::HmacValidator.validate`, but neither of these guards protects the *outbound* authorize-URL construction — they only validate the *inbound* callback, so they do not prevent `begin_auth` from producing a malformed/attacker-steerable `auth_route` in the first place.

### Impact Explanation
If the host application passes an attacker-influenced `shop` value into `begin_auth` (which the gem's own documentation pattern of reading `shop` from a request parameter/header encourages), the merchant's browser can be redirected to an attacker-controlled host carrying the real `client_id`, `scope`, real `redirect_uri`, and CSRF `state` as URL parameters, and/or have extra query parameters (e.g., a second `redirect_uri`) injected into the query string. This is a code-level flaw specific to this gem (missing `sanitize!` call that exists in every sibling flow) rather than a Shopify server behavior. The severity of the exploit is bounded by what a receiving party can do with these values: `client_id` and the app's real `redirect_uri` are not secret, and completing OAuth still requires the merchant to authenticate on genuine Shopify infrastructure, so full authorization-code exfiltration depends on how a downstream OAuth server (outside this gem) handles a malformed/duplicated query string — that part is not verifiable from this gem's code alone. What is verifiable and squarely in this gem is: the `shop` value is untrusted-and-unvalidated at the one call site where it is used to build a redirect target, which is inconsistent with the rest of the codebase and breaks the implicit invariant that `shop` fed into URL construction has already passed `ShopValidator.sanitize!`.

### Likelihood Explanation
Exploitability requires only that the host app forward an attacker-supplied `shop` value into `begin_auth`, which matches the gem's own documented integration pattern (reading `shop` from request parameters/headers) — no secrets, prior access, or privileged capability are needed by the attacker.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the top of `Oauth.begin_auth` (before computing `auth_base_uri`), mirroring `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, and use the sanitized/validated host for `auth_base_uri` construction and for the returned session context.

### Proof of Concept
Add a minitest to `test/auth/oauth_test.rb` (no live shop, no WebMock needed since `begin_auth` performs no HTTP call):
```ruby
def test_begin_auth_does_not_sanitize_shop
  ShopifyAPI::Context.setup(..., api_key: "test_key", host: "https://myapp.example")
  result = ShopifyAPI::Auth::Oauth.begin_auth(
    shop: "attacker.com/x?redirect_uri=https://attacker.com/steal",
    redirect_path: "/callback",
  )
  auth_route = result[:auth_route]

  # LHS of the binding: shop as passed in
  raw_shop = "attacker.com/x?redirect_uri=https://attacker.com/steal"
  # RHS of the binding: what a validated shop would look like
  refute_raises { ShopifyAPI::Utils::ShopValidator.sanitize!(raw_shop) }
  # asserting sanitize! actually raises Errors::InvalidShopError for this input,
  # proving begin_auth accepted a value that sanitize! would reject
  assert_raises(ShopifyAPI::Errors::InvalidShopError) do
    ShopifyAPI::Utils::ShopValidator.sanitize!(raw_shop)
  end

  # yet auth_route was built from the unsanitized value:
  assert_includes auth_route, "https://attacker.com/x?redirect_uri=https://attacker.com/steal/admin"
  refute_includes auth_route, "myshopify.com"
end
```
This demonstrates that `ShopValidator.sanitize!(raw_shop)` raises `Errors::InvalidShopError` (the value is not a trusted domain), while `begin_auth` happily builds `auth_route` from that same rejected value — proving the two call paths diverge on the same input, unlike `ClientCredentials`/`RefreshToken`/`TokenExchange`, which would have raised before reaching URL/body construction.
