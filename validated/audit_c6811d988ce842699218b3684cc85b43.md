## Analysis

The reported bug class (an "off-by-one" tier check) is not literally reachable in this Ruby gem, but its structural analog — **a field that is acted upon but not covered by the identity-binding signature** — is present in the webhook-processing path.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `hmac` is read from the `X-Shopify-Hmac-Sha256` header: [1](#0-0) [2](#0-1) 

`shop` is read from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header, which is **not part of the signed material**: [3](#0-2) 

`Utils::HmacValidator.validate` only verifies the raw body against the HMAC, never the shop header: [4](#0-3) 

`Registry.process` accepts the request once the body HMAC checks out, and then forwards `request.shop` — the unauthenticated header value — straight to the app's webhook handler as the tenant identity for that event: [5](#0-4) 

### Title
Webhook `shop` identity is taken from an HMAC-unprotected header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC of the raw request body via `Utils::HmacValidator.validate`. The `shop` (and `topic`, `webhook_id`, `api_version`) values are pulled from HTTP headers that are **not included in the signed payload**. Because the identity binding "authenticated body == body belonging to `shop` X" is never actually checked, an attacker who owns any shop that has the target app installed can capture one of their own genuinely-HMAC-signed webhook deliveries and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to a victim shop's domain. The signature still validates (it only covers the body), and `WebhookMetadata#shop` will report the victim's domain to the app's handler.

### Finding Description
The equality the app implicitly relies on is:
`HMAC-verified(bytes) == bytes belonging to shop S`

What is actually verified is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

`shop` is read independently from an unsigned header in `Request#shop` [3](#0-2)  and is never cross-checked against anything cryptographically tied to the body. `Registry.process` passes this untrusted `shop` value directly into the `WebhookMetadata` handed to the host application's handler [5](#0-4) , which is the only signal handler code has to determine which merchant/tenant the event concerns.

Any user who can install the target app on a shop they control (e.g., a free development store) can trigger legitimate webhook events (orders, products, `app/uninstalled`, GDPR topics, etc.) for that shop. Shopify will sign those payloads with the app's real `client_secret`, which the attacker never needs to know or steal — they only capture the already-signed request. The attacker then replays the identical body/HMAC pair to the app's public webhook URL while substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) for a victim shop. The gem's own validation logic offers no defense against this because it never binds `shop` to the signed bytes.

### Impact Explanation
This crosses a tenant boundary using data the app trusts as tenant-scoped truth: an attacker with only a self-owned shop can make the app process an event as if it belongs to an arbitrary victim shop, without any access token, session, or leaked secret. Depending on how the host app implements its handler (many implementations key data mutations, deletions, or session refresh purely off `data.shop`), this can lead to cross-tenant data corruption or state changes attributed to another merchant — satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple stores (which is virtually all Shopify apps): obtaining a validly-signed webhook only requires installing the app on an attacker-controlled store and triggering an event, both of which are unprivileged, self-service actions available to any developer/merchant.

### Recommendation
Bind the header-derived `shop` to the cryptographically verified material, e.g., include the shop domain in the HMAC-signable string (if Shopify's webhook signing supported it), or — more practically within this gem — have `Registry.process` cross-check `request.shop` against a caller-supplied allow-list/expected shop for the delivery channel, and clearly document in `Request`/`Registry` that `shop` is unauthenticated and callers must independently verify it (e.g., against a known/installed shop record) before trusting it for any tenant-scoped action.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# They capture a real, validly-signed webhook delivery for their own shop:
raw_body = '{"id": 1, "note": "hi"}'
real_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_from_shopify, # valid, computed by Shopify with the app's real secret
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# The HMAC only covers raw_body, so swapping the shop header does not
# invalidate the signature:
spoofed_headers = real_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HMAC validation, handler receives data.shop == "victim-shop.myshopify.com"
```
