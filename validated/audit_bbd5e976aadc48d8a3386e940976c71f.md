## Title
`SimplexPaymaster._getOraclePrice` accepts a Chainlink answer clamped at its aggregator's `minAnswer`/`maxAnswer`, letting mispriced gas payments drain the paymaster's EntryPoint deposit - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice()` only validates that a Chainlink `latestRoundData()` answer is positive and not stale; it never checks the answer against the feed's `minAnswer`/`maxAnswer` bounds [1](#0-0) . This is the same root cause as Sherlock M-5 in DODO's `D3Oracle.getPrice()`/`getOriginalPrice()`: Chainlink aggregators clamp reported prices to a configured range, so during a depeg or crash the feed keeps returning a stale-looking but "fresh" and "positive" price pinned at the boundary, silently diverging from the real market price.

### Finding Description
`_getOraclePrice` is the sole price source feeding `_tokenPrice`, which every UserOp routed through the paymaster uses to compute how much ERC-20 stablecoin/token to charge for gas [2](#0-1) . `_tokenPrice` is invoked from `_fetchDetails`, which runs in the validation path of every permissionless UserOp (mode `0x00` permit or mode `0x02` Permit2) [3](#0-2) .

The check performed is:
```solidity
(, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
if (block.timestamp - updatedAt > maxOracleAge) {
    revert StaleOraclePrice(address(oracle), updatedAt);
}
```
There is no comparison against the aggregator's configured `minAnswer`/`maxAnswer`. When the real-world price of the token or native asset moves outside that range (a stablecoin depeg, or a market crash of the native asset), Chainlink continues to publish a fresh, positive, in-range-looking round that is pinned to the boundary value rather than the true price. The paymaster has no way to detect this and treats the clamped value as ground truth.

`tokenPrice = (nativeUsd * 10^tokenDecimals * (1 + markupBps)) / tokenUsd` — if `tokenUsd` is clamped *above* the real (crashed/depegged) market price, `tokenPrice` comes out artificially low, meaning `_erc20Cost` charges the UserOp sender far fewer token units than the token's real value is worth, while the paymaster still pays the full real gas cost in native ETH out of its EntryPoint deposit [4](#0-3) . The same clamp risk exists on `nativeOracle`.

The contract's own design notes acknowledge oracle risk only for the permit-residual-allowance channel ("bounding exposure to the residual allowance even against a malicious oracle") [5](#0-4) , but this bound is per-op (the signed `permitAmount`/Permit2 amount), not a floor — it caps how much a single op can be over-charged, but nothing prevents an attacker from repeatedly submitting cheap-cost UserOps while the clamp condition persists, extracting real ETH from the paymaster's EntryPoint deposit each time at a fraction of its true cost.

### Impact Explanation
This is a fund-drain vector on the paymaster's EntryPoint stake: any address that can submit ERC-4337 UserOps through this permissionless paymaster (mode `0x00`/`0x02`) can, during a depeg/crash window where a registered token's or the native asset's Chainlink feed is clamped, repeatedly pay for real gas using a stablecoin whose real market value is materially below its clamped on-chain price. Each such UserOp under-pays the paymaster in genuine value while the paymaster reimburses full real gas from its EntryPoint deposit — concrete theft of protocol-held funds, not merely a stale-price inconvenience. This qualifies as Medium/High per the theft-of-funds acceptance criteria.

### Likelihood Explanation
Likelihood depends on external market conditions (a depeg or crash pushing the price outside the aggregator's configured bounds), which is exactly the scenario Chainlink's own documentation warns integrators to guard against, and is the precise condition the referenced M-5 report flags. Given the paymaster is described as accepting "any token with a Chainlink feed," including volatile-adjacent stablecoins (explicitly calling out BSC stablecoins), and is fully permissionless for UserOp submission, this is a realistic, externally-triggerable condition rather than a purely theoretical one.

### Recommendation
Extend `_getOraclePrice` to fetch and cache each feed's `minAnswer`/`maxAnswer` (or configure them via governance alongside `TokenConfig`/`Params`), and revert when `answer` is at or outside those bounds, mirroring the recommended Chainlink pattern:
```solidity
require(answer > minAnswer && answer < maxAnswer, "Chainlink: price out of bounds");
```
This should be applied to both `nativeOracle` and every `tokenConfigs[token].tokenOracle` lookup used in `_tokenPrice` and `swapAndDeposit`.

### Proof of Concept
1. Governance registers a stablecoin `X` with a Chainlink `X/USD` feed whose aggregator has `minAnswer = 0.90e8` (typical historical Chainlink stablecoin floor).
2. `X` depegs to a real market price of `$0.10` during a crash; the feed's `latestRoundData()` keeps returning `answer = 0.90e8`, `updatedAt = block.timestamp` (fresh) because the aggregator clamps to `minAnswer`.
3. `_getOraclePrice` passes both the `answer > 0` and staleness checks and returns `0.90e8` as `tokenUsd`, ~9x the real price [6](#0-5) .
4. Attacker acquires large amounts of `X` cheaply on the open market (at the real $0.10 price) and submits many UserOps through `SimplexPaymaster`, paying gas in `X`. `_tokenPrice` computes a `tokenPrice` based on the inflated `tokenUsd`, so the attacker's `erc20Cost` in `X` is ~9x lower than it should be relative to `X`'s real value [2](#0-1) .
5. Each UserOp still gets real gas paid from the paymaster's EntryPoint deposit in ETH, so the attacker repeatedly extracts real ETH value for near-worthless `X`, draining the paymaster's stake.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
