### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from an HTTP header that is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from the `X-Shopify-Shop-Domain` HTTP header, but `Utils::HmacValidator` only verifies the raw request body against the HMAC signature. Any attacker who can produce one validly-signed webhook body (e.g. a merchant who has legitimately installed the app on their own shop and thus receives real, correctly-signed webhooks) can replay that body to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. The signature check still passes because the header is never part of the signed material, so `Registry.process` dispatches the handler believing the event originated from a different, victim tenant.

### Finding Description
`Request#to_signable_string` — the only data fed into `HmacValidator.validate` — returns just `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body and then trusts `request.shop` (and `request.topic`) to build the metadata handed to the app's handler: [3](#0-2) 

This breaks the intended identity binding: **shop authenticated by the HMAC** should equal **shop the handler acts on**, but in reality `HMAC-covered bytes = raw_body` while `shop used by handler = unauthenticated header value`. Because a single app-level `client_secret` (via `Context.api_secret_key`) is shared across every shop that has installed the app, any tenant that receives one legitimately-signed webhook body can reuse that exact signature while claiming a different `shop-domain`, and the signature will still validate — since it never covered the header in the first place.

### Impact Explanation
This is a cross-tenant confusion: an attacker who is a legitimate (but malicious) installer of the app on their own shop can cause the host application to process a forged webhook event that is attributed to a shop they do not control, using a body of their choosing (subject to a body they can get validly signed, e.g. from their own shop's real webhook traffic, or any body for topics/mandatory webhooks where their own tenant's real payload structurally applies to other shops too, e.g. `app/uninstalled`, `shop/redact`). Downstream host applications that key data storage, deletion, or business logic off `WebhookMetadata#shop` (as the gem's documented model for identifying which tenant a webhook is for) can be tricked into acting on another merchant's records. This satisfies the "cross-tenant access" category.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the attacker to control a shop with the app installed (which is straightforward for anyone who can install a public/dev app) and to be able to reach the host application's webhook endpoint directly with custom headers (which is normal, since these are plain HTTP POST endpoints, not mTLS-restricted). No secrets or elevated privileges are required — only knowledge of one's own legitimately-received webhook body/HMAC pair and the ability to send arbitrary headers, which any unprivileged internet user/app-installer can do.

### Recommendation
Do not treat the `shop-domain` (or `topic`/`webhook_id`) header as trusted merely because the body's HMAC validates. Either:
- Include the shop domain (and topic) in the signed material used for HMAC verification, or
- Cross-check the header-derived `shop` against another authenticated source (e.g., correlate with a stored webhook `id`/session known to belong to that shop) before dispatching to handlers, or
- At minimum, clearly document in `ShopifyAPI::Webhooks::Request`/`Registry` that `shop`, `topic`, and `webhook_id` are unauthenticated header values and must not be used by host apps as the sole tenant-selection key without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":123}` with headers:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid signature for {"id":123}>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   ```
2. Attacker resends the exact same body and HMAC signature to the app's webhook endpoint, but changes only the shop header:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same valid signature, unchanged>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (the raw body) — this still passes because the body is unchanged. [4](#0-3) 
4. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...)`, causing the host app to process attacker-controlled data as if it came from the victim shop. [5](#0-4)
