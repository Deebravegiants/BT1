### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` is permanently locked in the contract - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native ETH via `msg.value` and swap it for the exact fee-token amount required using Uniswap V2's `swapETHForExactTokens`. Any ETH sent in excess of what the swap consumes is refunded by the Uniswap router — but to the **wrong recipient**: the router refunds to its own caller's `msg.sender`, which is the `EvmHost` contract itself, not the original end-user who called `dispatch()`/`fundRequest()`. Unlike `IntentGatewayV2`, which explicitly tracks a `msgValue` remainder and calls `_sendValue(msg.sender, msgValue)` to refund overpayment, `EvmHost` has no equivalent refund path for native token overpayment, and no admin/withdraw function was found to sweep stray native ETH out of the contract. This is the same bug class as the Haqq `Listing.buyFixedSale` report: users can overpay in a `payable` function and the surplus becomes permanently stuck.

`dispatch(DispatchGet)` follows the identical pattern: [2](#0-1) 

`fundRequest()` also follows the identical pattern: [3](#0-2) 

In each of these functions, `swapETHForExactTokens{value: msg.value}(...)` is called by `EvmHost` on the local Uniswap V2 router. The Uniswap V2 router's `swapETHForExactTokens` computes the exact ETH input needed for the requested `fee`/`amount` output and refunds the unused portion of `msg.value` to **its own caller** — i.e., to `address(this)` from the router's perspective, which is the `EvmHost` contract address, not the externally-originating account that funded the transaction. `EvmHost` never captures or forwards this refunded balance back to the caller.

This directly mirrors the reported bug pattern in `Listing.buyFixedSale`: a `payable` function accepts more native currency than strictly required, and the excess has no path back to the sender and no privileged withdrawal mechanism, permanently stranding it in the contract's balance.

By contrast, the `IntentGatewayV2` contracts in this same repo explicitly guard against this exact issue by tracking the remaining `msgValue` after the swap and refunding it to `msg.sender`: [4](#0-3) 

`EvmHost` has no analogous accounting/refund step, nor a documented sweep/withdraw function for native ETH balance in the reviewed sections of the contract.

### Impact Explanation
Any account calling `dispatch()`/`fundRequest()` on `EvmHost` with native ETH (which is a standard, documented user-facing payment flow per the docs "Native Token Payment" sections) that sends more than the exact amount the Uniswap swap consumes will have the surplus permanently trapped in `EvmHost`. Because this is the core dispatcher used by every ISMP application on the chain (POST/GET dispatch, relayer fee funding), this affects any unprivileged user or integrating app dispatching a cross-chain message with native-token payment — a widely reachable, single-transaction path. This constitutes permanent freezing of user funds, matching the accepted impact class "permanent freezing of funds."

### Likelihood Explanation
Overpayment is easy to trigger unintentionally because callers must estimate the amount of ETH needed to cover a Uniswap swap into the exact `feeToken` amount required; the docs explicitly warn that `quote()` is subject to slippage and should only be used off-chain, meaning users routinely pad `msg.value` above the estimated need to guarantee the swap succeeds. Any such padding is provably lost, making this a realistic and frequent occurrence rather than a contrived edge case, exactly as described in the original Haqq report's PoC (deliberately sending listing price + surplus).

### Recommendation
Mirror the pattern already used in `IntentGatewayV2`: after calling `swapETHForExactTokens`, capture the actual `amounts[0]` spent, compute `msg.value - amounts[0]`, and refund the remainder to `_msgSender()` via a safe ETH transfer in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`. As defense in depth, also add an access-controlled sweep function allowing `hostManager`/`admin` to recover any stray native ETH balance left in `EvmHost` from edge cases (e.g., direct transfers).

### Proof of Concept
1. Deploy/point at `EvmHost` with a configured Uniswap V2 router and `feeToken`.
2. Compute the exact ETH cost `X` to swap into `post.fee` fee-token units (e.g., via the router's `getAmountsIn`, as done in `EvmHostForkTest.quote()`).
3. Call `host.dispatch{value: X + surplus}(post)` from an EOA, where `surplus` is any extra ETH (e.g., 0.5 ether), analogous to the original PoC's `_nft_price + 2 ether` overpayment.
4. Observe: the Uniswap router refunds `surplus` back to `EvmHost`'s own address (its caller in the swap call), increasing `address(host).balance` by `surplus`.
5. Confirm the caller's ETH balance decreased by `X + surplus` (no refund reaches them), and that no function in `EvmHost` exists to withdraw this stranded native balance back to the caller or to governance — the surplus is permanently locked, exactly as in `EvmHostForkTest.testCanDispatchPostRequestWithNative`/`testCanDispatchFundRequestWithNative`, none of which assert or exercise any refund of leftover `msg.value`.     function testCanDispatchFundRequestWithNative() public {
        // dispatch request
        vm.prank(whaleAccount);
        bytes32 commitment = host.dispatch(
            DispatchPost({
                body: abi.encode(bytes32(0)),
                payer: whaleAccount,
                fee: 0,
                dest: StateMachine.evm(421614),
                timeout: 0,
                to: abi.encode(bytes32(0))
            })
        );
        assert(host.requestCommitments(commitment).sender == whaleAccount);
        assert(host.requestCommitments(commitment).fee == 0);

        // fund request
        vm.prank(whaleAccount);
        uint256 newfee = 10 * 1e18;
        host.fundRequest{value: quote(newfee)}(commitment, newfee);
        assert(host.requestCommitments(commitment).fee == newfee);

        // can't fund unknown requests
        uint256 cost = quote(newfee);
        vm.expectRevert(EvmHost.UnknownRequest.selector);
        vm.prank(whaleAccount);
        host.fundRequest{value: cost}(keccak256(hex"dead"), 10 * 1e18);
    }
