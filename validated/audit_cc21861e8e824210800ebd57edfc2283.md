### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but the shop identity attached to the resulting `WebhookMetadata` is read from an HTTP header that is never included in that HMAC computation. This breaks the binding "the shop that produced the signature equals the shop the handler is told the event came from," permitting cross-tenant spoofing of webhook events whenever an attacker can obtain a validly-signed request body (e.g. from their own store) and replay it with a different `shop-domain` header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`), with no cryptographic tie to the signed body: [2](#0-1) [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — which in turn only checks `request.to_signable_string` (i.e. the raw body) against the HMAC secret — and then forwards `request.shop` unchanged into `WebhookMetadata`, which is passed directly to the app's handler as the authoritative tenant identity: [4](#0-3) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) and the app's secret, with no reference to headers at all: [5](#0-4) 

This is exactly the bug class described in the external report by analogy: a privileged/tenant-scoped action (`handler.handle` acting "on behalf of" `data.shop`) is gated by a check (`HmacValidator.validate`) that does not cover the field the action actually keys off of (`request.shop`). The equality that should hold — `shop_verified_by_hmac == shop_used_by_handler` — does not, because `shop_verified_by_hmac` is undefined; only the body is verified.

### Impact Explanation
Any party who can obtain a request with a valid HMAC for the configured `api_secret_key` — trivially, the operator of any shop that has this app installed, since Shopify signs and delivers real webhooks to them for their own store — can replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with a victim shop's domain. Because the header is outside the signed content, `Registry.process` will accept the forged request as authentic and hand the handler a `WebhookMetadata` claiming the event originated from the victim shop, with attacker-controlled `topic`/`body` content. Any app logic that uses `data.shop` to look up per-tenant state, trigger per-tenant side effects, or route data (a very common pattern, since this is the only tenant identifier `Registry.process` exposes) is exposed to cross-tenant data corruption or disclosure. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the attacker controls, or can install the target app on, at least one Shopify shop (satisfying "unprivileged internet user," no leaked credentials or access tokens needed), and (2) the ability to send an arbitrary HTTP request with custom headers to the app's public webhook endpoint, which is by design internet-reachable. No knowledge of `api_secret_key` is required — the attacker reuses a signature Shopify itself computed for their own legitimate webhook. This is straightforward and repeatable, making likelihood high wherever a host app keys tenant-scoped logic off `WebhookMetadata#shop`.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind them to the body — e.g. compute the signable string as a canonical concatenation of `shop-domain`, `topic`, `webhook-id`, and `raw_body` rather than `raw_body` alone. At minimum, document this gap clearly and require host apps to independently validate that `data.shop` is on record as having genuinely installed the app (e.g. cross-check against known offline sessions) before trusting it, since today `ShopifyAPI::Webhooks::Registry.process` presents `shop` as if it were authenticated when it is not.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com`, which has the target app installed; Shopify sends the attacker a genuine webhook, e.g. `POST /webhooks` with body `{"id":123}`, headers `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker captures this request and resends it to the app's webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, leaving the body byte-for-byte identical.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `Utils::HmacValidator.validate` recomputes HMAC over the unchanged raw body and it matches, per `lib/shopify_api/utils/hmac_validator.rb` line 29-30 (`compute_signature(verifiable_query.to_signable_string, secret)` where `to_signable_string` is only the body, `lib/shopify_api/webhooks/request.rb` line 36-38).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 189-199) accepts the request and calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: {"id":123}, ...)`, causing the host app to act as though `victim-shop.myshopify.com` sent this webhook data, despite it never having done so.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
