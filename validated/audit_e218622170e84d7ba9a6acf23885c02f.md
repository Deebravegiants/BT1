### Title
Webhook `shop-domain` and `topic` headers are unauthenticated — HMAC only signs the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` — the value that the HMAC signature actually protects — is only the raw request body. `Registry.process` validates the HMAC and then trusts `request.shop`/`request.topic` to route and label the payload for the app's handler. Because the identity fields are never part of the signed material, any request bearing a body+HMAC pair that is valid for *some* shop can be replayed with an attacker-chosen `shop-domain` (and `topic`) header and will still pass HMAC verification, letting an attacker present shop A's legitimately-signed payload as if it came from shop B.

### Finding Description
The identity binding that should hold is:

`hmac_valid(request) == true` ⇒ `(body, shop, topic)` were all produced/authorized by Shopify for this specific webhook delivery.

In this gem, that binding is broken because the signable string excludes `shop` and `topic`: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body` — the header-derived `shop` (from `x-shopify-shop-domain`/`shopify-shop-domain`) and `topic` are never fed into the HMAC computation.

`HmacValidator.validate` computes/compares the signature strictly against `to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC first, then immediately trusts `request.shop` and `request.topic` to select the handler and build the metadata passed to the app's business logic: [4](#0-3) 

Attack sequence:
1. Attacker installs the target app on a shop they control ("Shop A") and legitimately receives a real, correctly-signed webhook delivery (body + `x-shopify-hmac-sha256` computed with the app's `client_secret` over that body).
2. Attacker replays that exact body and HMAC value to the app's webhook endpoint, but substitutes the `x-shopify-shop-domain` header with "Shop B" (a different, unrelated tenant of the same app) and/or a different `x-shopify-topic`.
3. `Utils::HmacValidator.validate(request)` still succeeds, because it only re-derives the signature from `@raw_body`, which is unchanged.
4. `Registry.process` dispatches to the handler for the attacker-chosen `topic`, and calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` — the app's handler now believes Shop A's body legitimately belongs to Shop B.

Before the attacker's action: `hmac_valid == true` implied `shop == <the shop whose secret truly produced this exact body>`.
After the attacker's action: `hmac_valid == true` while `shop` is attacker-chosen and unrelated to the signed body, since `shop` never entered the signable string.

### Impact Explanation
This is a cross-tenant identity-binding bypass reachable by any unprivileged internet user who has (or can obtain) one valid signed webhook body from the app (e.g., by installing the app themselves, which every merchant/attacker can do). Downstream host applications built on this gem are documented and expected to key business logic (order processing, data updates, feature toggles, sometimes session/access-token lookups) off `WebhookMetadata#shop` and `#topic`, since the gem provides no other way to determine which tenant a webhook is "for." An attacker can therefore inject arbitrary Shopify-looking webhook events labeled as belonging to a victim shop, causing cross-tenant data confusion/corruption in any host app that trusts `request.shop`/`request.topic` as authenticated — satisfying the "cross-tenant access" class of impact.

### Likelihood Explanation
High likelihood: no privileged credentials, access tokens, or `client_secret` are required. The only prerequisite is the ability to obtain one valid signed webhook (trivially available to any developer/merchant who installs the app on their own store), plus the ability to POST arbitrary headers to the app's public webhook endpoint — both are unprivileged, internet-reachable actions.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. Concretely, change `Webhooks::Request#to_signable_string` to incorporate these header values (in a fixed, canonical order) rather than the raw body alone, and update `HmacValidator`/callers accordingly so a mismatch between the signed body and the claimed `shop`/`topic` causes verification to fail.

### Proof of Concept
1. Configure the app with `api_secret_key = S`.
2. Legitimately receive/craft a webhook for shop `victim-a.myshopify.com` with body `B` and header `x-shopify-hmac-sha256 = HMAC_SHA256(S, B)` (base64-encoded).
3. Resend the same `body: B` and same HMAC header, but set `x-shopify-shop-domain: victim-b.myshopify.com` and/or a different `x-shopify-topic`.
4. Observe that `ShopifyAPI::Utils::HmacValidator.validate(request)` (as used in `ShopifyAPI::Webhooks::Registry.process`) returns `true`, and the handler receives `WebhookMetadata` attributing body `B` to `victim-b.myshopify.com` under the attacker-chosen topic — confirmed by inspecting `Webhooks::Request#shop`/`#topic` accessors (`lib/shopify_api/webhooks/request.rb`, lines 15–23) versus the signable string (lines 35–38), which never reference these header values.
