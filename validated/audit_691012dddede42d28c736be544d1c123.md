### Title
Webhook Shop/Topic Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, yet it trusts the `shop-domain`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers that are never included in the signed material. Any actor able to obtain one valid `(raw_body, hmac)` pair for *any* shop subscribed to the app (e.g. their own shop, on which they legitimately installed the app) can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header. The request still passes `HmacValidator.validate`, and the forged `shop` value is handed straight to the app's `WebhookHandler` as the trusted tenant identifier, resulting in cross-tenant data being attributed to (and processed for) a shop that never sent it.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, which are outside the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (i.e. body only) and, if valid, immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` object delivered to the app's handler — the value the host application is documented to treat as "The shop domain of the webhook": [3](#0-2) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`, so any header not included there is unauthenticated: [4](#0-3) 

The docs explicitly instruct app authors to trust `data.shop` as the shop identity after calling `Registry.process`, describing the flow as verifying "the request did indeed come from Shopify": [5](#0-4) [6](#0-5) 

**Identity binding broken:** `shop asserted to the handler (request.shop header) ≠ shop covered by the HMAC signature (raw_body only)`. Any party who can obtain a legitimate `(body, hmac)` pair for one shop's webhook (which is straightforward for an app user to do for their *own* shop — e.g. by creating an additional webhook subscription that points to an endpoint they control, or by logging the raw request/HMAC on their own server) can present that same pair to the target app's webhook endpoint with a forged `x-shopify-shop-domain` header naming a different, victim shop. Since the endpoint only checks the body's HMAC, the request is accepted and delivered to the handler tagged with the attacker-chosen shop.

### Impact Explanation
This crosses a tenant boundary without any credential belonging to the victim shop: an app user for shop A can inject fabricated (but Shopify-HMAC-valid) webhook events that the app's own processing pipeline attributes to shop B. Depending on how the host application uses `data.shop` (e.g. to key per-tenant billing counters, sync jobs, inventory updates, or trigger side effects scoped by shop), this enables cross-tenant data corruption or unauthorized actions performed "as" another merchant — matching the Critical "cross-tenant access" category, since the trust boundary the gem is documented to enforce (webhook authenticity == shop authenticity) is not actually provided.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop (ordinary, unprivileged onboarding, no special credentials), and (2) obtaining one raw body + `X-Shopify-Hmac-Sha256` pair for that shop's own webhook traffic — achievable without needing the app's `client_secret` since Shopify itself computes and delivers the HMAC to any endpoint the attacker registers for their own shop. No TLS interception, no stolen access tokens, and no privileged account are required, only ordinary use of a legitimate app installation.

### Recommendation
Bind the header-derived identity fields into the authenticated material before trusting them. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should not be the only signal used to authorize `shop`; the gem should require the host application (or the gem itself) to cross-check `request.shop` against the shop associated with the specific `webhook_id`/subscription (e.g. via a server-side lookup keyed by the registered webhook, not by trusting the header), or Shopify's HMAC scheme should be supplemented with a mechanism that also authenticates the delivery headers. Document prominently that `data.shop` is not itself covered by the HMAC and must not be used as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers the same webhook topic (e.g. `orders/create`) pointing at an endpoint they control, or otherwise captures a legitimate delivery's raw body and `X-Shopify-Hmac-Sha256` header sent by Shopify for their own shop.
2. Attacker sends this exact `raw_body` and `X-Shopify-Hmac-Sha256` value directly to the target app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a real installed shop of the same app) instead of their own domain.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body, and `Registry.process` calls `HmacValidator.validate`, which succeeds because the signature only covers `raw_body`, which is unmodified.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled data>, ...)`, causing the host application to process attacker-supplied data under the victim shop's identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
