### Title
`Wallet.addSeed` skips `assertMnemonic` word-count/checksum validation applied by `Wallet.import` - (File: features/wallet/module/wallet.js)

### Summary
`Wallet.addSeed` derives the seed via `mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })` and never calls `assertMnemonic` or `mnemonicIsInvalid`, unlike `Wallet.import`, which explicitly calls `assertMnemonic(mnemonic, this.#validMnemonicLengths)` before creating a seed. This creates an inconsistency between the two seed-import entry points, allowing a mnemonic that would be rejected by `import` (wrong word count or invalid BIP-39 checksum) to be accepted by `addSeed`.

### Finding Description
`Wallet.import` validates the mnemonic string with `assertMnemonic`, which checks word count against `validMnemonicLengths` and checksum validity via `mnemonicIsInvalid` [1](#0-0) [2](#0-1) . `Wallet.addSeed`, by contrast, only checks that the wallet is unlocked and then calls `mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })` directly, bypassing `assertMnemonic`/`mnemonicIsInvalid` entirely [3](#0-2) .

However, `mnemonicToSeed` itself only skips the BIP-39 checksum/wordlist validation (`mnemonicAssertValid`) when `validate: false`, per the library implementation [4](#0-3) . It still requires `mnemonic` to be a non-empty string, and derives a PBKDF2-based seed from whatever string is supplied — there is no wordlist/checksum requirement enforced at this layer. This means `addSeed` will happily accept a mnemonic with the wrong word count or an invalid checksum (e.g., 13 random words, or 12 words that fail the checksum) and derive a seed from it, then store it in `extraSeeds` and push it into the keychain via `this.#keychain.addSeed(data.seed)` [5](#0-4) . On subsequent `unlock()`, this stored extra seed is loaded and added to the keychain without any re-validation [6](#0-5) .

`addSeed` is exposed directly through the public wallet API surface (`features/wallet/api/index.js`) alongside `import`, `create`, etc., with no additional mnemonic validation wrapper [7](#0-6) .

### Impact Explanation
An unprivileged caller of `wallet.addSeed` (once the wallet is unlocked and multi-seed support is enabled, i.e. `maxExtraSeeds > 0`) can inject a seed derived from a non-BIP39-compliant mnemonic string into persistent `extraSeeds` storage and the live keychain, bypassing the `UnexpectedWordCount`/`InvalidPhrase` guarantees that are otherwise enforced uniformly for `import`. This breaks the invariant that "the same validation guarantees apply to every seed-import entry point," and results in storage/signing of a seed that would never have passed the app's own consent/validation UX for seed import. The seed itself is still cryptographically derived (via PBKDF2) and deterministic from the mnemonic input, so this is not a checksum-collision or key-recovery bug — the impact is limited to inconsistent input validation/state authenticity rather than key leakage or unauthorized signing with someone else's key.

### Likelihood Explanation
Requires the wallet to be unlocked and `maxExtraSeeds > 0` — both realistic preconditions in normal operation (multi-seed wallets, unlocked dapp/RPC session). The `addSeed` function is directly reachable by anyone/anything calling the public `wallet.addSeed` API method with no extra gating beyond `#assertWalletIsUnlocked`, so it is trivially and repeatably triggerable.

### Recommendation
Call `assertMnemonic(mnemonic, this.#validMnemonicLengths)` inside `Wallet.addSeed` before deriving the seed (or switch `mnemonicToSeed` to `validate: true` plus a word-count check), mirroring the validation performed in `Wallet.import`, so both seed-import code paths enforce identical mnemonic validation guarantees.

### Proof of Concept
Unit test in `features/wallet/module/__tests__/index.test.js`:
1. Construct a `Wallet` instance with `config.maxExtraSeeds = 1` and `validMnemonicLengths = [12, 24]`, unlock it.
2. Call `wallet.import({ mnemonic: '<13 random valid BIP39 words>' })` and assert it throws `UnexpectedWordCount`.
3. Call `wallet.addSeed({ mnemonic: '<same 13-word mnemonic>' })` and observe that it does NOT throw and instead succeeds, pushing a seed derived from an invalid mnemonic into `extraSeeds`/keychain — asserting parity failure between `import` and `addSeed`.
4. Repeat with a 12-word mnemonic that fails the BIP39 checksum (`mnemonicIsInvalid` returns `true`) to confirm `import` throws `InvalidPhrase` while `addSeed` succeeds.

```javascript
export const assertMnemonic = async (input, validMnemonicLengths) => {
  assert(typeof input === 'string', 'The secret phrase provided is not a string')

  if (!validMnemonicLengths.includes(input.split(/\s+/gu).length)) {
    throw new NamedError({ name: 'UnexpectedWordCount' })
  }

  if (await mnemonicIsInvalid({ mnemonic: input })) {
    throw new NamedError({ name: 'InvalidPhrase' })
  }
}
```

```javascript
export async function mnemonicToSeed({
  mnemonic,
  password = '',
  validate = true,
  wordlist = english,
  format = 'uint8',
}) {
  assert(typeof mnemonic === 'string' && mnemonic.length > 0, 'mnemonic must be a non-empty string')
  assert(typeof password === 'string', 'password should be a string')
  if (validate) await mnemonicAssertValid({ mnemonic, wordlist })
  const salt = `mnemonic${nfkd(password)}`
  return pbkdf2('sha512', nfkd(mnemonic), salt, { iterations: 2048, dkLen: 64 }, format)
}
```
